### Title
Webhook Shop/Topic/Webhook-ID Headers Are Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` trusts and hands to the host app's handler are read directly from unauthenticated HTTP headers. This breaks the identity binding `hmac_verified_bytes == acted_on_identity`: the HMAC only proves the *body* came from someone possessing `api_secret_key`, not that the accompanying `shop-domain`/`topic`/`webhook-id` headers are genuine for that body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic tie to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies exactly this `to_signable_string` value: [3](#0-2) 

`Registry.process` then accepts the request purely on that body-only HMAC check, and forwards the *unauthenticated* header-derived `shop`, `topic`, and `webhook_id` to the app's handler as if they were verified: [4](#0-3) 

Because Shopify apps share one `api_secret_key` across every installed shop (tenant), any shop that has installed the app receives its own legitimately HMAC-signed webhook bodies. An attacker who owns such a shop can capture one of these legitimate `(raw_body, hmac)` pairs and replay it directly to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers to any value of their choosing. The HMAC still validates (it only covers `raw_body`), so `Registry.process` proceeds and calls the app's handler with `WebhookMetadata` claiming the forged `shop`/`topic`/`webhook_id`: [5](#0-4) 

Equality that should hold but doesn't: `shop_bound_by_hmac == shop_used_by_handler`. In fact `shop_bound_by_hmac` doesn't exist at all — only `raw_body` is bound — so `shop_used_by_handler` is entirely attacker-controlled while still passing HMAC validation.

### Impact Explanation
Any host application that keys tenant-sensitive logic (e.g., looking up which shop's session/data to update, deciding which topic-specific handler logic to run, or de-duplicating by `webhook_id`) off `WebhookMetadata#shop`/`#topic`/`#webhook_id` can be tricked into processing another tenant's data under a victim shop's identity, or into re-processing/misrouting events under a spoofed topic — a cross-tenant confusion that maps to the "cross-tenant access" Critical impact category, since the HMAC check gives false assurance that these fields are authentic.

### Likelihood Explanation
Any shop that has installed the app is, from Shopify's point of view, an "unprivileged" tenant relative to other merchants using the same app instance, and can trivially obtain a valid `(body, hmac)` pair for its own account by intercepting the webhook delivery to its own configured endpoint (or a proxy under its control). Forging the headers and POSTing to the app's public webhook URL requires no secret knowledge beyond what the attacker already legitimately possesses for their own tenant.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them) in the HMAC signable string, or require the host application to independently verify the `shop-domain` header against a value obtained through an authenticated channel (e.g., matching the currently loaded session) before trusting `WebhookMetadata`. At minimum, document clearly that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated header values not covered by `Utils::HmacValidator.validate`, so consuming apps do not implicitly trust them for tenant routing.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and configures/observes the webhook delivery, capturing a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's `api_secret_key`.
2. Attacker sends a raw HTTP POST directly to the app's public webhook endpoint with:
   - Body: the captured `raw_body` (unchanged, so HMAC stays valid)
   - Header `X-Shopify-Hmac-Sha256`: the captured, still-valid HMAC
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`/`X-Shopify-Webhook-Id`: attacker-chosen values
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not authenticity, is checked): [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the payload never having been authenticated for that shop, letting the attacker inject events attributed to a victim tenant.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
