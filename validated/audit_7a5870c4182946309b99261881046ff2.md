### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated headers while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body, but the `shop`, `topic`, and `webhook_id` values used to route and scope the processed webhook to a specific merchant are read from HTTP headers that are never included in the HMAC computation. An attacker who can produce (or capture) one genuine `(raw_body, hmac)` pair signed with the app's `client_secret` — e.g., by installing the app on their own shop and receiving a real webhook — can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to claim any other shop, and the library will report the request as valid and hand `data.shop` to the host application's handler as trusted routing/tenant-key information.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all pulled directly from HTTP headers and are not part of `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string` (the raw body): [3](#0-2) 

`Registry.process` uses this same validator and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler, with no additional binding check between the verified bytes (body) and the header-derived identity fields: [4](#0-3) 

The library's own documentation states that `process` "will verify the request did indeed come from Shopify," implying the whole request (including `shop`) is authenticated, but in reality only the body bytes are covered: [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop used for tenant routing (data.shop, from X-Shopify-Shop-Domain header)` == `shop bound inside the HMAC-verified bytes (raw_body only)`. These are never checked to be equal, and the header is fully attacker-controlled once an attacker has any one valid `(raw_body, hmac)` pair for the app's shared `client_secret`.

Since a Shopify app's webhook HMAC secret is the app's single `client_secret`, shared across every merchant that installs the app, an attacker who installs the app on their own store legitimately obtains a valid `(raw_body, hmac)` pair. They can then replay that exact HTTP body and HMAC header to the app's public webhook endpoint while changing `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the (unchanged) body against the (unchanged) HMAC, and `Registry.process` forwards the forged `shop` value to the host application's handler as if Shopify had asserted it.

### Impact Explanation
This breaks the tenant/shop identity binding relied upon by any host application using `data.shop` from `WebhookMetadata` to select which merchant's session/data to act on (as shown in the gem's own usage docs, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). An attacker can inject data attributed to an arbitrary victim shop domain into the app's processing pipeline, causing the host app to process attacker-controlled body content as if it originated from a different merchant — a cross-tenant data-integrity/confidentiality violation depending on how the host app keys work off `data.shop`.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to first legitimately install the target app on a shop they control (to obtain a validly-HMAC'd body/header pair using the app's shared secret) — no leaked credentials or privileged access are needed since app installation is available to any unprivileged Shopify user. From there, forging a replayed request with a swapped `Shop-Domain` header is a simple HTTP replay against the public webhook endpoint.

### Recommendation
Bind the identity fields (`shop`, `topic`, `webhook_id`) into the value verified by HMAC, or otherwise re-derive/verify `shop` from the signed body content rather than the raw header (e.g., cross-check the body payload's own shop/domain data, or require the host app to enforce shop scoping using a previously-established session rather than the unauthenticated header). At minimum, document clearly that only the request body is authenticated by `Registry.process`, and that `data.shop`/`data.topic` are NOT guaranteed to be cryptographically bound to that body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook: raw body `B`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the app's `client_secret`).
2. Attacker captures this request (e.g., via a proxy they control receiving their own shop's webhooks).
3. Attacker sends a new HTTP request to the app's public webhook endpoint with the exact same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts it; `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only returns `B`, which is unchanged.
5. `Registry.process` calls the host handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the body content actually came from the attacker's own shop. [4](#0-3)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
