**Analysis:**

The attack path described is already blocked by existing custody checks in `account::create_resource_account`, which `create_resource_account_and_publish_package` calls before publishing.

When a caller (attacker or legitimate) attempts to create a resource account at a derived address that already exists on-chain, the function explicitly checks: [1](#0-0) 

1. If the address already corresponds to an initialized `Account` resource with `signer_capability_offer.for` already set (i.e., it's already a resource account owned by its signer capability), the call aborts with `ERESOURCE_ACCCOUNT_EXISTS`.
2. If the address has already committed a transaction (sequence number != 0), the call aborts with `EACCOUNT_ALREADY_USED`.

So a second `create_resource_account_and_publish_package` call targeting an address that already holds a resource account (with a package already published under it) will abort rather than silently overwriting ownership — exactly the assertion the proof idea proposes, and it already exists in the framework as a hard guard, not an incidental side effect.

Additionally, deriving a colliding `create_resource_address(attacker_addr, seed)` for an *arbitrary* existing target address requires inverting SHA3-256, which the domain-separation scheme byte (`DERIVE_RESOURCE_ACCOUNT_SCHEME = 255`) was specifically introduced to harden against: [2](#0-1) [3](#0-2) 

This is a documented, intentional design trade-off (probability `2^-256`), not an exploitable weakness, and the address derivation is deterministic based on the caller's own address plus seed — an attacker cannot choose an arbitrary target address's `source` to force a collision with a *victim's* resource account, since they don't control the victim's origin address input.

There is also an existing regression/e2e test pattern (`test_create_account_and_retrieve_cap`, `resource_account.spec.move`'s `RotateAccountAuthenticationKeyAndStoreCapabilityAbortsIf`) covering the abort behavior on duplicate resource-account claims: [4](#0-3) 

Since the unprivileged path already aborts rather than allowing ownership overwrite, and address collision requires breaking SHA3-256 preimage resistance (not a code-level bug), this does not meet the custody impact gate — no real custody boundary is crossed.
