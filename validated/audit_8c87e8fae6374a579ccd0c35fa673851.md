### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by HMAC-signing only the raw request body, while the `shop` (tenant) identifier used by the host application's webhook handler comes from an unauthenticated HTTP header. This breaks the identity binding `authenticated bytes == acted-upon tenant identity`, since the HMAC never covers the `shop-domain` header.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the value supplied in the request: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only the raw HTTP body: [2](#0-1) 

But the `shop` attribute — which identifies which merchant/tenant the webhook belongs to — is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, completely outside the HMAC signature scope: [3](#0-2) 

`Registry.process` validates only that the body's HMAC is correct, then immediately forwards `request.shop` (the unauthenticated header) to the app's handler as the trusted tenant identity: [4](#0-3) 

The equality the gem should enforce is:
`shop bound by HMAC == shop acted upon by handler`

But what is actually enforced is:
`body bytes covered by HMAC == body bytes received`, with `shop` entirely outside that binding.

### Impact Explanation
Because the shop-domain header is never part of the signed payload, any party capable of observing one legitimate webhook delivery for a body it can reproduce/replay (e.g., a merchant who has the app installed and receives real webhooks, or anyone who can capture a webhook with a known/fixed body such as `{}` or another shop-independent payload) can resend that same body+HMAC pair to the app's webhook endpoint with an arbitrary `shop-domain` header value. Since `Registry.process` only checks `HmacValidator.validate(request)` (body integrity) and never cross-checks the `shop` header against anything bound by the signature, the forged request passes validation and is dispatched to the handler as if it originated from the spoofed shop. This is a cross-tenant identity confusion in the webhook processing pipeline of the gem itself — the app's webhook handler receives attacker-controlled tenant attribution for a cryptographically "valid" webhook.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain (not forge) a body+HMAC pair, e.g., by being a legitimate merchant of the app (an "unprivileged" but real, low-trust actor) who intercepts their own real webhook deliveries, or by exploiting any webhook topic whose payload is static/predictable across shops. No knowledge of `client_secret` or `api_secret_key` is required — the attacker reuses a validly-signed body they already legitimately received.

### Recommendation
Include the `shop` identifier (and other identity-relevant metadata that the handler acts on) inside the HMAC-signed material, or otherwise independently verify that the `shop-domain` header corresponds to a shop that is expected/authorized for the given webhook delivery (e.g., cross-check against the shop's known access token/session, or bind the header value into the signable string used for validation).

### Proof of Concept
1. App has webhook handler registered for topic `orders/create` via `ShopifyAPI::Webhooks::Registry`.
2. Attacker (a merchant with the app installed on `attacker-shop.myshopify.com`) receives a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
3. Attacker resends a request to the app's webhook endpoint with the same body `B`, the same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are unaffected by the shop-domain header change (`lib/shopify_api/webhooks/request.rb:11-38`).
5. `HmacValidator.validate` succeeds because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:12-22`).
6. `Registry.process` forwards `shop: request.shop` = `"victim-shop.myshopify.com"` to the handler (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process an attacker-controlled payload under the victim's tenant identity.
