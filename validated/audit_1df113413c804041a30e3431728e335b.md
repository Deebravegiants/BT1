### Title
Webhook `shop-domain` header is not covered by HMAC, allowing tenant confusion via replayed webhook bodies - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that `HmacValidator.validate(request)` succeeds against `request.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only `@raw_body`. The `shop` (from the `x-shopify-shop-domain` header) is never part of the signed material, yet it is forwarded unauthenticated as the tenant identity in `WebhookMetadata` to every host application handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header [1](#0-0) , and computes the HMAC-verifiable string from only the raw request body [2](#0-1) . `HmacValidator.validate` verifies the received HMAC against `verifiable_query.to_signable_string` using `OpenSSL.secure_compare` [3](#0-2) . Since `to_signable_string` never incorporates `shop`, the identity binding `HMAC(secret, raw_body) == received_hmac` is completely independent of which `shop` value is asserted in the header.

`Registry.process` then only checks `Utils::HmacValidator.validate(request)` before dispatching, and directly forwards `request.shop` into `WebhookMetadata` passed to the app's handler [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field with no relation to the HMAC-covered bytes [5](#0-4) .

Because Shopify signs webhooks with a single `client_secret` shared across the app's full merchant base, any merchant who installs the app can capture one legitimate `(raw_body, hmac)` pair from their own shop's webhook delivery. That pair remains a valid HMAC for *any* `shop-domain` header value, since the header is excluded from the signed content. A malicious merchant/attacker can therefore replay the intercepted `raw_body`+`hmac-sha256` header while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks body vs. secret), and the host application's webhook handler receives `WebhookMetadata` claiming the data belongs to the victim tenant.

### Impact Explanation
This breaks the identity binding between the authenticated bytes (raw body) and the tenant claim (`shop`) that host applications rely on for per-merchant data isolation. Any host app that uses `data.shop` from the handler (a documented, intended usage per `docs/usage/webhooks.md`) to look up/write per-shop records, revoke or rotate secrets, or trigger customer-data actions (including the mandatory `customers/redact`, `shop/redact`, `customers/data_request` topics) can be tricked into cross-tenant data corruption, exfiltration, or improper redaction attributed to the wrong shop — a cross-tenant access impact, achievable by any attacker who has legitimately installed the app on one shop (an "unprivileged" relative to the victim tenant).

### Likelihood Explanation
Requires the attacker to install the target app on a shop they control (a normal, unprivileged action for any merchant) and to be able to POST a crafted HTTP request with an attacker-chosen `x-shopify-shop-domain` header to the app's webhook endpoint — no access token, API secret, or other privileged credential is needed. This is realistic since the gem's own `Webhooks::Request` explicitly reads whichever of `shopify-shop-domain` or `x-shopify-shop-domain` header is present, both of which are ordinary client-supplied HTTP headers, not something Shopify cryptographically ties to the payload from the gem's perspective.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the signable string verified by `HmacValidator`, or independently verify that `request.shop` matches the shop associated with the API key/secret pair used to compute the HMAC before trusting it as the tenant identity forwarded in `WebhookMetadata`.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent to the app's webhook endpoint — `H = Base64(HMAC-SHA256(client_secret, B))`.
2. Replay the exact same request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but replace the header `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares it to `H` — this still matches because `to_signable_string` is only `B` [2](#0-1) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` [6](#0-5) , causing the host app to process attacker-supplied data under the victim's tenant identity.
