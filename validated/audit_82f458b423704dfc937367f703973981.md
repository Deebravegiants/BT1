### Title
Permissionless pool creation can be front-run to permanently squat a market's deterministic AMM PDAs, blocking legitimate pool creation - (File: `program/src/processor.rs`)

### Summary
`Initialize2` derives every account that identifies a new AMM pool (`target_orders`, `lp_mint`, `coin_vault`, `pc_vault`, and the `AmmInfo` account itself) deterministically from the **market account's pubkey**, which is public, known ahead of time, and cannot be changed by the legitimate pool creator. Any unprivileged user can submit an `Initialize2` transaction for that same market with minimal (non-zero) seed liquidity and effectively "own" all those PDAs first. Once created, the accounts are no longer owned by the system program, so any subsequent, legitimate `Initialize2` call for that market permanently fails with `AmmError::RepeatCreateAmm`. This is the direct analog of the reported `loanId` front-running griefing bug: a resource identifier that the honest actor cannot choose freely (here, the market pubkey) is used as the sole uniqueness key, letting an attacker pre-claim it and permanently deny the honest user's resource creation.

### Finding Description
`process_initialize2` derives all of the pool's core accounts from `market_info.key` using fixed seed constants: [1](#0-0) 

Each derivation goes through `generate_amm_associated_account` / `generate_amm_associated_spl_mint` / `generate_amm_associated_spl_token`, which compute the PDA from `[program_id, market_account.key, associated_seed]`: [2](#0-1) 

If that derived address is not still owned by the system program (i.e., it was already created), the function returns `AmmError::RepeatCreateAmm` instead of proceeding: [3](#0-2) [4](#0-3) 

Because the seed is only `market_info.key` plus a fixed constant string (`AMM_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`), the resulting AMM addresses for a given market are 100% predictable off-chain by anyone before the legitimate pool creator's transaction lands. The only requirement to claim them is calling `Initialize2` with that market and non-zero `init_coin_amount`/`init_pc_amount` (checked only for `amount == 0`, no minimum-liquidity floor beyond the LP subtraction check): [5](#0-4) [6](#0-5) 

This mirrors the reported bug class exactly: the uniqueness key that guards resource creation (`loanId` in the report, the `market` pubkey here) is not something the legitimate actor controls independently — anyone who observes the target market/pending transaction in the mempool can submit a competing `Initialize2` first and permanently occupy the PDAs tied to that market.

### Impact Explanation
Once an attacker's `Initialize2` transaction lands first for a given market, the legitimate/intended pool for that market can **never** be created — every future `Initialize2` attempt for that market reverts with `AmmError::RepeatCreateAmm` because the target PDAs are already assigned to the program. This is a permanent denial of service on pool creation for that trading pair/market, matching "Griefing" impact. Additionally, since the attacker only needs to seed minimal non-zero liquidity, they capture the pool with a bad/skewed initial price and become the sole liquidity provider/owner of record for that market's AMM, which can be leveraged to disadvantage any future swappers who are directed to that (now squatted) pool.

### Likelihood Explanation
The attack requires only observing a pending `Initialize2` transaction (or simply knowing which markets are about to be onboarded) and submitting a single transaction with attacker-chosen accounts (the same `market_info`) and minimal token amounts — no privileged role, no leaked keys, and no non-default build assumptions are needed. This is directly reachable from the permissionless `Initialize2` instruction available to any wallet.

### Recommendation
Do not rely solely on the market pubkey as the sole seed determining pool address uniqueness for permissionless creation, or add an explicit authorization/allowlist step (e.g., only a specific config-approved fee payer or a two-phase commit binding the intended creator to the market) before the PDAs are claimable, so that an arbitrary third party cannot pre-empt the legitimate creator's `Initialize2` call for a given market.

### Proof of Concept
1. Alice (legitimate LP) prepares an `Initialize2` transaction for `market M` with real liquidity amounts, intending to bootstrap the pool.
2. Attacker observes `market M` (public on-chain data) or Alice's pending transaction in the mempool, and computes the same deterministic PDAs (`target_orders`, `lp_mint`, `coin_vault`, `pc_vault`, `amm_info`) from `[program_id, M, seed_constants]` exactly as `generate_amm_associated_account`/`generate_amm_associated_spl_mint` would.
3. Attacker submits their own `Initialize2` for market `M` first, with `init_coin_amount = 1`, `init_pc_amount = 1` (minimum non-zero amounts satisfying the checks at `program/src/processor.rs:858-866`), successfully creating the pool and assigning all PDAs to the program under attacker-controlled ownership/liquidity.
4. Alice's `Initialize2` transaction now executes and hits `generate_amm_associated_account`'s ownership check, reverting with `AmmError::RepeatCreateAmm` (`program/src/processor.rs:470-474`, `541-545`) because the PDAs are no longer owned by the system program.
5. Market `M` can never have its intended, properly-seeded pool created again — permanent griefing of the legitimate pool creation for that market.
