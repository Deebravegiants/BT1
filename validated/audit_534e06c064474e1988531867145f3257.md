### Title
Missing duplicate-authority check in BEEFY supermajority threshold - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The BEEFY consensus verifier's threshold check counts raw signature/vote entries rather than distinct authorities, and neither the Rust nor Solidity implementation rejects duplicate authority indices before or during the participation-threshold check.

### Finding Description
`verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs` computes `signatures_length = mmr.signed_commitment.signatures.len()` directly from the relayer-supplied `signatures` vector and passes it to `check_participation_threshold(signatures_length as u32, authority_set.len)` [1](#0-0) . This just checks `len >= ((2 * total) / 3) + 1` [2](#0-1) . Nowhere in this function (or anywhere else in the file) are the `sig.index` values checked for uniqueness before or after this count is taken — the loop that builds `authority_leaves`/`authority_indices` simply pushes one entry per signature in the caller-supplied array, without deduplicating `authority_indices` [3](#0-2) .

The Solidity equivalent, `EcdsaBeefy.verifyMmrUpdateProof`, has the identical shape: `sigLen = relayProof.signedCommitment.votes.length` is checked against the threshold via `checkParticipationThreshold(sigLen, authoritySet.len)` before any uniqueness constraint on `vote.authorityIndex` [4](#0-3) .

By contrast, other consensus verifiers in this codebase explicitly guard against this exact bug class: the Pharos BLS verifier's `verify_validator_membership` builds a `BTreeSet` of participant keys and rejects the proof with `Error::DuplicateParticipant` if `deduped.len() != participants.len()` [5](#0-4) . The BEEFY path has no analogous check.

Whether this is practically exploitable depends on whether the downstream merkle multi-proof verifier (`rs_merkle::MerkleProof::verify` in Rust, `MerkleMultiProof.VerifyProof` in the `solidity-merkle-trees` external library) itself rejects duplicate indices/leaves when reconstructing the root. I was not able to inspect the internals of either the `rs_merkle` crate or the external `solidity-merkle-trees` `MerkleMultiProof.sol` library (they are external dependencies not present in this repo's index), so I cannot confirm whether a crafted proof with a repeated `authority_index`/`authorityIndex` (paired with the same valid signature/leaf) would successfully reconstruct the authority-set root while inflating the apparent signature count past the true number of distinct signers.

### Impact Explanation
If the underlying multi-proof libraries do not themselves enforce strictly increasing/unique indices, an attacker (or a set of colluding authorities below the honest 2/3+1 threshold) could submit the same valid signature multiple times under the same `authorityIndex` to pad `signatures_length`/`sigLen` past the supermajority threshold without a real supermajority of distinct signers, forging BEEFY consensus updates that unlock unsound state commitments and downstream message delivery/proof verification on Hyperbridge — a critical bridge integrity failure. If the libraries do enforce uniqueness (e.g., by requiring strictly ascending indices in the multi-proof), then this specific path is not exploitable and the missing check in the ISMP-BEEFY layer is defense-in-depth only.

### Likelihood Explanation
Low-to-Medium confidence given the analysis is incomplete: the vulnerability's exploitability hinges entirely on unverified behavior of the external Merkle multi-proof libraries (`rs_merkle` and `polytope-labs/solidity-merkle-trees`), which are not indexed in this repository and could not be reviewed with the tools available.

### Recommendation
Regardless of the underlying library's behavior, add an explicit, defense-in-depth uniqueness check on `sig.index` / `vote.authorityIndex` before computing `signatures_length`/`sigLen` in both `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof` and `evm/src/consensus/EcdsaBeefy.sol::verifyMmrUpdateProof`, mirroring the `DuplicateParticipant` pattern already used in `modules/consensus/pharos/verifier/src/lib.rs`. This closes the gap unconditionally rather than relying on an unverified invariant of an external dependency.

### Proof of Concept
Not constructible without confirming the exact duplicate-index handling semantics of `rs_merkle::MerkleProof::verify` and the external `MerkleMultiProof.VerifyProof` Solidity library — both are outside this repo's indexed contents. A concrete PoC would require locally vendoring/reading those library sources (or running the existing Rust `verify_mmr_update_proof` test harness in `modules/consensus/beefy/verifier/src/test.rs` with a crafted `MmrProof` containing repeated `SignatureWithAuthorityIndex.index` values) to determine whether `merkle_proof.verify` accepts a duplicated index/leaf pair. I recommend starting a Devin session with access to the full dependency source to build and run this PoC.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
