### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing via body/HMAC replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery solely by validating the HMAC over the raw request body, but the `shop` identity that is handed to the app's `WebhookHandler#handle` (and used by the app to decide which tenant's data to mutate) comes from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from an HTTP header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the request purely via `HmacValidator.validate(request)`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC — i.e., it verifies bytes of the body, not the shop header: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (the unauthenticated header value) is placed directly into `WebhookMetadata`, which is the only tenant identifier passed to the app-supplied handler: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Because `shop-domain` is excluded from `to_signable_string`, this equality is never enforced — the HMAC only proves "this body was signed by our `client_secret`", not "this body belongs to shop X". Since a single app uses one shared `client_secret` (or `old_api_secret_key`) across every installed shop, any attacker who can obtain one valid `(raw_body, hmac)` pair — trivially, by installing their own free/dev shop with the app and capturing a real webhook delivery to their own publicly reachable endpoint — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still succeeds because the header isn't part of `to_signable_string`, and the handler receives `WebhookMetadata` claiming the body belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook delivery: an unprivileged attacker (any merchant who installs the app once) can make the app process attacker-controlled webhook payloads as if they originated from a different, victim shop. Depending on how the host app's handler uses `data.shop` (e.g., to look up the shop's record, write order/inventory data, or trigger side effects keyed by shop domain), this enables cross-tenant data corruption or state confusion under a shared `client_secret`, which matches the "cross-tenant access" class of Critical impact for this analysis.

### Likelihood Explanation
Moderate-to-high: no leaked secret, TLS interception, or privileged account is required. The only prerequisite is that the attacker can install the app on any shop they control (a normal, permitted first step for any Shopify app) and capture one webhook delivery — something the app owner cannot prevent, since webhook payloads are delivered to whatever public endpoint the app registers. Replaying the header-modified request against the same public endpoint is trivial for anyone able to reach it over the internet.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the verified HMAC to the specific shop before trusting the `shop-domain` header:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) in `to_signable_string`, matching what Shopify's own signature covers if possible, or
- Independently verify that `request.shop` matches a shop for which the app currently holds a valid session/access token before invoking the handler, so an unauthenticated header value can never redirect handling to an arbitrary tenant.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and lets Shopify deliver any real webhook, e.g. `orders/create`, to the app's public webhook endpoint. Attacker captures the raw HTTP request, including body and the `x-shopify-hmac-sha256` header — a valid `(raw_body, hmac)` pair signed with the app's shared `client_secret`.
2. Attacker resends the exact same HTTP request to the same endpoint, but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (or removes/spoofs `x-shopify-topic`/`webhook-id` as desired — those also aren't signed).
3. Server code calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) using the app's secret and finds it matches — validation succeeds — see [7](#0-6) .
   - The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `request.shop` now returns `"victim-shop.myshopify.com"` — see [5](#0-4)  and [2](#0-1) .
4. The host application processes attacker-controlled data under the victim shop's identity, despite the HMAC only proving the body's authenticity, not the shop association.
