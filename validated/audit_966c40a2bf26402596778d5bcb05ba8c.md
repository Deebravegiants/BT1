### Title
Address pre-funding lets an unprivileged attacker permanently DoS `CreateAccount`/`CreateAccountWithSeed` for any target address at negligible cost - (File: `programs/system/src/system_processor.rs`)

### Summary
The Folks Finance report describes a griefing DoS where a malicious user front-runs a deterministic-ID account creation, permanently blocking the legitimate creator because the target "already exists." The same bug class exists in Agave's System Program: `create_account` rejects creation whenever the target account already has any lamports, and any unprivileged user can give a target address non-zero lamports via a plain `Transfer` before the legitimate `CreateAccount`/`CreateAccountWithSeed` instruction lands, permanently blocking that specific address from ever being created via the normal path.

### Finding Description
`create_account` in `system_processor.rs` treats any non-zero lamport balance on the destination as proof the account is "already in use" and aborts: [1](#0-0) 

Because `SystemInstruction::Transfer` moves lamports to an arbitrary destination pubkey with no signature or ownership requirement from the recipient, any unprivileged user who can predict or observe a target address (e.g., a `CreateAccountWithSeed` address deterministically derived from a known `base`/`seed`/`owner`, or a freshly generated keypair address broadcast in an unconfirmed transaction) can send 1 lamport to it before the legitimate creation transaction is processed. The subsequent legitimate `CreateAccount`/`CreateAccountWithSeed` call then hits `to.get_lamports() > 0` and fails with `SystemError::AccountAlreadyInUse`, exactly mirroring the Folks Finance `accountId` squatting pattern (create-first-with-the-same-identifier to block the intended owner).

`CreateAccountWithSeed` is especially exposed: the derived `to_address` need not itself sign the transaction — only the `base` key must sign — and the address is fully deterministic from public inputs: [2](#0-1) [3](#0-2) 

That the Agave team itself recognizes this exact griefing vector is shown by the introduction of a new, explicitly-designed workaround instruction, `CreateAccountAllowPrefund`, whose doc comment states it exists for cases "where account has already had rent paid in whole or in part before creation": [4](#0-3) 

This new instruction is feature-gated and only takes effect if callers opt into it: [5](#0-4) 

Programs and CLI tooling that still use the classic `CreateAccount`/`CreateAccountWithSeed` instructions (the vast majority of on-chain programs and the `solana` CLI, e.g. nonce-account creation) remain fully exposed to this griefing vector, since the mitigation is opt-in per-instruction rather than a change to the vulnerable `create_account` check itself.

### Impact Explanation
Any unprivileged actor can permanently block the creation of a specific, predictable system/program account for the cost of a single lamport transfer (recoverable rent, near-zero net cost), denying service to legitimate users/protocols that rely on deterministic account addressing (seed-derived accounts, nonce accounts, pre-computed keypair addresses in offline-signed flows, etc.). This is a genuine griefing/DoS on unprivileged account-creation paths reachable by any transaction sender, not a validator/operator-only issue, and it results in denial of a specific on-chain operation (account creation) rather than mere inconvenience, matching the accepted "concrete value loss/denial" bar via undeclared/blocked account creation.

### Likelihood Explanation
High. No special privileges, timing precision beyond ordinary front-running, or elevated capital are required — a 1-lamport `Transfer` sent ahead of (or racing) the intended `CreateAccount`/`CreateAccountWithSeed` transaction is sufficient. Any address that is derivable or observable in advance (seed-based derivation, or addresses revealed in a not-yet-landed transaction) is a viable target.

### Recommendation
Since this is a design property inherent to the classic `CreateAccount`/`CreateAccountWithSeed` instructions and cannot be silently changed without breaking compatibility, the practical mitigation is: (1) continue rolling out and documenting `CreateAccountAllowPrefund` as the recommended replacement for flows using deterministic/seed-derived destination addresses, since it tolerates pre-funded lamports; (2) update first-party tooling (CLI nonce-account creation, SPL/program SDKs that use `create_account_with_seed`) to adopt `CreateAccountAllowPrefund` once broadly activated, rather than leaving it as an opt-in path that most callers never adopt; (3) clearly document in SDK/program-developer guidance that any deterministically-derived destination address is squattable via simple lamport transfers, so protocol designers avoid relying on classic `CreateAccount` semantics for security-critical, address-predictable flows.

### Proof of Concept
1. Attacker predicts/derives target address `to` (e.g., via `Pubkey::create_with_seed(base, seed, owner)`, or observes an unconfirmed transaction naming a fresh keypair as `to`).
2. Attacker submits `SystemInstruction::Transfer` sending 1 lamport from any of their own funded accounts to `to`.
3. Legitimate user submits `SystemInstruction::CreateAccount` (or `CreateAccountWithSeed`) naming `to` as the destination.
4. `create_account` executes the check at `programs/system/src/system_processor.rs:164-171`, sees `to.get_lamports() > 0`, and returns `SystemError::AccountAlreadyInUse`, permanently preventing that specific address from ever being created through the normal instruction (test coverage of this exact behavior exists in `test_create_already_in_use`): [6](#0-5)

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
