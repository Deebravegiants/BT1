## Title
Native-token overpayment to `EvmHost.dispatch()` gets permanently stuck in `EvmHost` instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

## Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept any `msg.value` and forward the entire amount to Uniswap's `swapETHForExactTokens`, which only spends up to `post.fee`/`get.fee` worth of ETH and refunds the unused portion. Because `EvmHost` itself is the caller of the router (`address(this)` is `EvmHost`, not the original dispatcher/app), Uniswap's refund of unused ETH lands back on `EvmHost`'s own balance rather than being returned to `_msgSender()`. This is the same root-cause class as the C4 finding: a `>=`/no-exact-match payment check allows overpayment, and the excess value is not routed back to the payer, leaving it stuck in the receiving contract.

## Finding Description
`EvmHost.dispatch(DispatchPost memory post)`: [1](#0-0) 

does:
```
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```

There is no upstream check that `msg.value` equals the amount actually required to buy `post.fee` fee-tokens — any caller can send more ETH than needed (analogous to the `>=`/lack-of-exact-match check in `EntityForging.forgeWithListed`). `swapETHForExactTokens` spends only `amountsIn <= msg.value` and refunds the unspent ETH (`msg.value - amountsIn`) to whichever address called the router — which is `EvmHost` (`address(this)` from the perspective of the router call), not the original transaction sender or the calling app contract. The identical pattern exists in `dispatch(DispatchGet memory get)`: [2](#0-1) 

No code path in `EvmHost.dispatch()` forwards this Uniswap refund back to `_msgSender()`/`post.payer`. Contrast this with the higher-level `IntentGatewayV2.placeOrder`/`fillOrder`, which the test suite explicitly proves refunds overpaid native ETH to the caller: [3](#0-2) [4](#0-3) 

Those tests confirm the protocol's design intent — overpaid native token used for fee-swaps should come back to the user — but they only validate this at the `IntentGatewayV2` layer, where the gateway itself appears to account for and forward the correct/leftover balance. Any *other* caller (a `HyperApp`, a custom `HyperFungibleToken`/`WrappedHyperFungibleToken` app, or a direct integrator, per the documented pattern) that calls `IDispatcher(host).dispatch{value: msg.value}(post)` directly — exactly as shown in the official docs — will lose any overpaid ETH to `EvmHost`'s balance: [5](#0-4) [6](#0-5) 

`WrappedHyperFungibleToken.send()` computes a `msgValue` remainder after WETH-wrapping the input amount and forwards that full remainder as `dispatch{value: msgValue}(request)`; if that remainder overshoots the exact ETH-to-feeToken swap requirement (which is very likely since the amount is a caller-supplied estimate, not the router's exact quote), the delta is silently absorbed by `EvmHost`, not by `WrappedHyperFungibleToken` or the end user.

I was unable to locate any `withdraw`/`sweep`/`rescue` function in `EvmHost.sol` to recover ETH accidentally accumulated there via this refund path (grep for `withdraw|onlyOwner|sweep|rescue|drain` in that file matched only unrelated occurrences of `onlyOwner`/similar tokens elsewhere in the file, not a native-ETH sweep entry point) — meaning any ETH that lands there via this path could be permanently unrecoverable, or at minimum requires a privileged/admin action to recover, which is outside normal user recourse.

## Impact Explanation
- Any unprivileged dispatcher/app/user that pays the dispatch fee in native token via `IDispatcher(host).dispatch{value: msg.value}(...)`, following the officially documented pattern, and supplies `msg.value` greater than what the Uniswap swap actually needs to buy `post.fee`/`get.fee` fee tokens, will have the excess ETH swept by the router back onto `EvmHost`'s balance rather than refunded to them.
- This is a direct value leak: funds sent by a legitimate, unprivileged caller become inaccessible to that caller. Given `EvmHost` handles cross-chain message dispatch fees continuously and is a widely-used entry point (also used by `HyperFungibleToken`/`WrappedHyperFungibleToken` bridging and any custom `HyperApp`), the aggregate leakage across dispatches over time can be material.
- This matches Medium severity per the cited precedent: "leak value with a hypothetical attack path with stated assumptions, but external requirements" — here the "external requirement" is simply overestimating the native-ETH amount needed to cover the swap (a routine and expected occurrence, since callers cannot cheaply predict Uniswap's exact `amountsIn` on-chain, and the docs explicitly warn against calling `quote()` on-chain due to sandwich-attack risk, implying most integrators will pass a safety-margin `msg.value` rather than the exact amount).

## Likelihood Explanation
High likelihood of occurrence in normal operation (not an edge case): the documented usage pattern instructs callers to send `msg.value` to cover fees without an exact quote mechanism recommended for on-chain use, so overestimation is expected/normal rather than a rare mistake. Any `HyperApp` or user directly following the documented "Native Token Payment" pattern is exposed. The `IntentGatewayV2` contracts appear to specifically guard against this at their layer (per passing tests), which itself is evidence that the underlying `EvmHost.dispatch()` primitive does not protect against it and needed a wrapper-level fix.

## Recommendation
1. In `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)`, after calling `swapETHForExactTokens`, capture the actual `amounts[0]` spent (the return value of `swapETHForExactTokens`) and refund `msg.value - amounts[0]` to `_msgSender()` (or `post.payer`/`get.payer`) explicitly, rather than relying on the router's refund destination.
2. Alternatively/additionally, add an explicit native-ETH sweep/rescue function restricted to protocol governance that can recover ETH accidentally stranded in `EvmHost`, in case any residual balance still accumulates from other paths.
3. Emit an event noting the refunded excess amount and destination for auditability, consistent with other refund flows in the codebase (e.g., relayer fee refunds on timeout).

## Proof of Concept
Conceptual PoC (Foundry-style, analogous to the referenced C4 PoC and to the existing `IntentGatewayV2SameChainTest.testPlaceOrder_RefundsExcessNativeToken`):

```solidity
function testDispatch_OverpaymentSticksInEvmHost() public {
    uint256 requiredFee = 1e18; // feeToken amount needed
    // Determine actual ETH needed via router.getAmountsIn off-chain/simulation, then intentionally overpay
    uint256 overpaidValue = actualEthNeeded * 5; // 5x the required amount

    uint256 hostBalBefore = address(host).balance;
    uint256 callerBalBefore = caller.balance;

    vm.prank(caller);
    host.dispatch{value: overpaidValue}(
        DispatchPost({
            body: abi.encodePacked(bytes32(0)),
            dest: StateMachine.evm(1),
            to: abi.encode(address(0x1)),
            timeout: 0,
            fee: requiredFee,
            payer: caller
        })
    );

    // Caller loses the full overpaidValue rather than getting the unused ETH back
    assertEq(caller.balance, callerBalBefore - overpaidValue, "Caller not refunded excess ETH");
    // The excess ETH accumulates in EvmHost itself, with no user-facing recovery path
    assertGt(address(host).balance, hostBalBefore, "Excess ETH stuck in EvmHost");
}
```
Note: I could not execute this test against the live repo in this session, so the concrete numeric magnitude of `amounts[0]` vs `msg.value` was not empirically verified here beyond reading the Uniswap V2 Router's well-known `swapETHForExactTokens` refund-to-caller semantics and the absence of a corresponding refund-forwarding line in `EvmHost.dispatch()`.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```
