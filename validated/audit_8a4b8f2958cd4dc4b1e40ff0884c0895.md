### Title
Webhook shop-domain identity spoofing due to HMAC not binding the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook using only the HMAC of the raw request body, but the `shop` value that identifies which tenant the webhook belongs to is taken from an unsigned HTTP header and is never covered by that HMAC. This breaks the identity binding `shop_header == shop_that_produced_the_HMAC`, letting anyone who can trigger a legitimately-signed webhook for their own store relabel it as coming from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` field with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` accepts the request as authentic once that body HMAC passes, and then forwards the attacker-controlled `request.shop` header straight to the app's webhook handler as the tenant identity: [4](#0-3) 

Because the shared `api_secret_key` is the same for every shop that has installed the app, any shop that installs the app (an ordinary, unprivileged action) can receive a genuinely-signed webhook — body + valid HMAC — for its own store. The HMAC never mentions which shop it belongs to, so that exact `(raw_body, hmac)` pair remains valid no matter what `shopify-shop-domain` header is later attached to it. An attacker can therefore replay their own valid webhook to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header, and the gem will report it as an authentic, verified webhook for the victim shop.

### Impact Explanation
This crosses a tenant boundary: the app's webhook handler receives `WebhookMetadata` with `shop` claiming to be a different, victim merchant, while the actual signer/body content originated from the attacker's own store. Any app logic that uses `request.shop`/`WebhookMetadata#shop` to select the tenant's session, database record, or business action (e.g., order/product upserts, billing events, uninstall handling) can be tricked into applying attacker-controlled data under another merchant's identity — a cross-tenant access/data-injection condition, since `Registry.process` treats the header-derived shop as trustworthy purely because the body HMAC passed.

### Likelihood Explanation
The only prerequisite is the ability to install the app on any shop (which is normal, unprivileged usage for public/multi-shop apps) in order to obtain one genuinely HMAC-signed webhook body, and then the ability to POST directly to the app's webhook endpoint with a modified `shop-domain` header — no access token, `client_secret`, or privileged account is required, only the gem's own verification logic being insufficient to bind the header to the signed content.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) value in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the header-derived shop to the payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not treat `shop` as authenticated data equivalent to the raw body.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header — this HMAC is valid because `Utils::HmacValidator.validate` only signs `@raw_body` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
2. Replay that exact `(raw_body, hmac-sha256)` pair to the app's webhook endpoint, but set `shopify-shop-domain: victim-shop.myshopify.com` instead of the attacker's own domain.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (`lib/shopify_api/webhooks/request.rb:45-63`), `Registry.process` validates the HMAC successfully (`lib/shopify_api/webhooks/registry.rb:190`), and the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) even though the payload/HMAC actually originated from the attacker's shop.
