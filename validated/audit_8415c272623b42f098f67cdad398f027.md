### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity headers are not covered by the HMAC signature, allowing a replayed webhook to be attributed to an arbitrary tenant - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/utils/hmac_validator.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, then hands the handler a `shop` identifier taken from an HTTP header that is never included in that HMAC computation. Because the tenant-identifying field (`shop`) is "acted on but not covered by the HMAC," a valid `(body, hmac)` pair captured from one shop's real webhook delivery can be replayed with a different `shop-domain` header and will still pass validation, letting an attacker attribute arbitrary (attacker-supplied) webhook data to a victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate_signature` computes the HMAC exclusively over that `to_signable_string` value and compares it to the `hmac` accessor (itself just the decoded `hmac-sha256` header): [2](#0-1) [3](#0-2) 

None of `topic`, `shop`, `api_version`, or `webhook_id` — all read from separate, unsigned HTTP headers — participate in the signed string: [4](#0-3) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the metadata passed to the registered handler — the same object the host application uses to identify which tenant/shop the webhook event belongs to: [5](#0-4) 

The equality the library implicitly claims to enforce is:
`shop_header == shop_that_produced_this_HMAC`

But the actual guarantee provided is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

These are not the same binding. Since `shop-domain` is not part of the signed payload, any request with a valid `(raw_body, hmac)` pair — regardless of who or what generated it — will be accepted for whatever `shop-domain` header value the requester supplies.

### Impact Explanation
An attacker who legitimately installs the app on their own (attacker-controlled) store — an ordinary unprivileged action requiring no credentials belonging to the app or to any victim — will receive genuine webhook deliveries containing a valid `raw_body` + `X-Shopify-Hmac-Sha256` pair signed with the app's shared secret (this is normal Shopify behavior; the secret used to sign is the app's `client_secret`, which the attacker never needs to know or possess). The attacker can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`/`Webhook-Id`, which are equally unauthenticated). `Utils::HmacValidator.validate` still returns `true` because it only checks the (unchanged) body, and `Registry.process` invokes the victim's registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`.

Any host application that uses this trusted `shop` field to look up/update per-tenant state (the documented purpose of `WebhookMetadata`) will process attacker-controlled data under the identity of a shop the attacker does not control — a cross-tenant data-integrity/confusion attack requiring no stolen credentials, no access token, and no `api_secret_key`. This satisfies the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
High. Obtaining a valid `(body, hmac)` pair requires nothing more than installing the target app on an attacker-owned/free development store — a normal unprivileged capability of any internet user with a Shopify Partner account — and capturing one webhook delivery. Forging the `shop-domain` header on the replay is a trivial HTTP header change; no cryptographic material or brute forcing is needed since that field is simply never checked against the signature.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise verify it out-of-band per event:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the string that is HMAC-verified (mirroring the pattern already used for `AuthQuery#to_signable_string`, which explicitly enumerates the fields it protects), or
- Have `Registry.process` independently verify (e.g., via a follow-up authenticated API call, or by requiring the host app to confirm the shop is one it has an active session/install for) that the header-derived `shop` is consistent with the webhook subscription that was registered for that specific shop, rather than trusting an unauthenticated header value directly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`). The app's endpoint receives:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-b64-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Webhook-Id: ...`
   - Body: `raw_body` (JSON payload, attacker fully controls its content because it is the attacker's own order data).
2. Attacker resends the exact same request to the app's public webhook endpoint, changing only the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` is unchanged and whose `shop` now returns `"victim-shop.myshopify.com"`. [6](#0-5) 
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only (unchanged) and returns `true`. [7](#0-6) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_json, ...)`, and the host application processes attacker-controlled webhook data as if it originated from `victim-shop.myshopify.com`. [8](#0-7)
