### Title
Personal Custody Package (biometric identity data) is uploaded to the backend before signup/fraud verification completes, allowing persisted biometric data upload despite orb-detected fraud or later signup rejection - ([File: src/plans/mod.rs])

### Summary
The reported reentrancy bug's root cause is a checks→effects→interactions ordering violation: state effects (`userStake.liquidity`) are committed before the corresponding invariant-restoring update (`incentive.liquidityStaked`), and an external interaction is triggered in between, letting the attacker exploit the inconsistent intermediate state. In `MasterPlan::do_signup` (`src/plans/mod.rs`), the same class of ordering flaw exists: the Personal Custody Package (PCP) — containing the user's iris/face biometric templates, keys, and identity binding data — is built and uploaded to the backend (`src/plans/mod.rs` lines 580-636) *before* the backend signup verification (`enroll_user::Plan::run`, called at line 647) confirms the signup is valid, non-duplicate, and non-fraudulent.

### Finding Description
In `do_signup`, fraud detection and pipeline evaluation determine `signup_reason` (`Normal`, `Fraud`, or `Failure`) at lines 563-571 [1](#0-0) . Immediately afterward, regardless of `signup_reason`, the code proceeds to build and upload the PCP:

```
let packages = match Box::pin(self.build_pcp(orb, credentials, &capture, pipeline.as_ref(), debug_report, signup_reason)).await { ... };
...
self.upload_pcp_tier_0(orb, &result.signup_id, &user_id, packages.tier0, packages.tier0_checksum, ...).await?
``` [2](#0-1) 

Only *after* this upload does the code call `enroll_user::Plan::run`, which performs the actual backend signup request/poll cycle (`signup_post::request` + `signup_poll::request`) that determines whether the backend accepts the signup as unique, non-fraudulent, and valid: [3](#0-2) [4](#0-3) 

The `signup_reason` value passed into `build_pcp`/upload is computed purely from the *orb's own* local fraud/pipeline check (line 563-571), not from the backend's authoritative verification. The backend-side check (duplicate detection, "backend fraud checks", MPC iris matching, etc., explicitly called out in `SignupReason::Fraud`'s doc comment "not to be confused with the backend fraud checks" in `src/backend/signup_post.rs` lines 78-81) happens strictly later, and its failure (`Status::SignupVerificationNotSuccessful`, `Status::ServerError`, etc.) does not roll back or invalidate the PCP tiers already persisted server-side. [5](#0-4) 

This mirrors the reentrancy report's structural flaw: an "effect" (state/data persisted — here, biometric identity data uploaded and bound to `user_id`/`signup_id`) is committed prior to the "check" (the interaction that validates the operation should be allowed), and there is no mechanism enforcing the correct order or reverting the effect if the check subsequently fails.

### Impact Explanation
Because the PCP — including iris/face biometric templates, encrypted keys, and the QR-derived `user_id` binding — is uploaded to the backend before the backend's own fraud/duplicate check runs, a signup that is ultimately rejected by the backend (duplicate account, backend-detected fraud, inflight match, etc.) still results in biometric data being persisted server-side and associated with that `user_id`/`signup_id`. This creates a cross-signup state bleed / unauthorized biometric data disclosure risk: an attacker who can force repeated signup attempts (e.g., replaying or manipulating QR codes across sessions) can get their biometric package uploaded and bound to identifiers even when the corresponding signup is never legitimately completed, independent of the eventual accept/reject outcome the rest of the system relies on for identity binding integrity.

### Likelihood Explanation
Reaching this code path requires only normal, unprivileged use of the orb signup flow (scanning QR codes and completing biometric capture) — no privileged access is needed. The upload-before-verify ordering is unconditional in `do_signup` for any signup that reaches the pipeline stage, including ones the orb's own fraud detector already flagged as `SignupReason::Fraud`, since fraud detection does not gate whether `build_pcp`/upload runs (it only affects the `signup_reason` field embedded in the package).

### Recommendation
Reorder the flow so that PCP tier uploads only occur after the backend's authoritative signup verification (`enroll_user::Plan::run`) has confirmed the signup is accepted, or gate the upload behind a check that aborts/rolls back if the subsequent backend enrollment check fails. Apply a strict checks→effects→interactions pattern: perform all validation (including backend-side fraud/duplicate checks) before persisting biometric identity data, and ensure that a failed enrollment leads to explicit invalidation/cleanup of any previously uploaded PCP tiers server-side.

### Proof of Concept
Not independently reproducible from static analysis alone — this requires confirming with the actual backend behavior (whether it accepts/stores PCP uploads keyed by `signup_id` prior to enrollment confirmation, and whether it purges them on later rejection). Based on the client-side code alone: any standard signup attempt that the pipeline flags as `SignupReason::Fraud` (or one that later fails backend verification via `enroll_user::Plan::run` returning `SignupVerificationNotSuccessful`) still passes through `build_pcp` → `upload_pcp_tier_0` → tier1/tier2 upload (`src/plans/mod.rs` lines 574-636) before the backend check is performed, demonstrating the effects-before-checks ordering.

**Uncertainty**: I could not fully verify server-side behavior (whether uploaded PCP tiers are actually discarded/invalidated on backend rejection) since that logic lives outside `orb-core`. This analysis is based solely on the client-side ordering in `src/plans/mod.rs`, `src/plans/enroll_user.rs`, and `src/plans/personal_custody_package.rs`, which is what orb-core controls.
