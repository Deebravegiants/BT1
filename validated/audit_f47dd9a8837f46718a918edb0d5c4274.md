## Finding

Chainlink's `webapi` trigger connector handler has an unbounded nested loop over all registered workflow triggers × attacker-supplied topics that runs on every message from the internet-facing gateway, before any per-workflow sender authorization is checked in the outer loop. This is a plausible analog to the reported unbounded-array DOS pattern (grow an unbounded, attacker-influenced array, then iterate the whole thing in a hot path).

### Title
Unbounded O(triggers × topics) loop in `processTrigger()` allows an unprivileged gateway sender to cause CPU-exhaustion DoS - (File: `core/capabilities/webapi/trigger/trigger.go`)

### Summary
`triggerConnectorHandler.HandleGatewayMessage` (invoked whenever the gateway relays an inbound `web-api-trigger` message from any external HTTP sender) calls `processTrigger`, which iterates every registered workflow trigger and, for each trigger, iterates every entry in the attacker-controlled `payload.Topics` array with no size cap on either dimension.

### Finding Description
`processTrigger` collects all currently registered triggers and does a nested loop against the request's `Topics` list: [1](#0-0) 
The `Topics` field comes directly from the unauthenticated/unprivileged request payload and has no `maxItems` or length constraint defined in its schema: [2](#0-1) 
The only upstream size guard is the generic gateway body-size limit (default up to `MaxRequestBytes`, e.g. 100000-1MiB depending on config) — see `httpServer.handleRequest`, which just caps raw bytes, not the number of array elements after JSON decoding: [3](#0-2) 
Because each topic can be a very short string (e.g. `"a"`), a single request within the byte-size budget can contain tens of thousands of topic entries. `processTrigger` is called for *every* inbound `MethodWebAPITrigger` message before any authorization decision is made for the topic/sender pair — the `allowedSenders` check happens only after a topic match is found inside the inner loop, i.e., an unauthenticated sender still forces full iteration cost: [4](#0-3) 
`HandleGatewayMessage` invokes `processTrigger` synchronously for each incoming gateway message with no rate limiting applied prior to this loop (rate limiting is only checked per matched trigger inside the loop, not globally per request): [5](#0-4) 

The number of registered triggers (`h.registeredWorkflows`) grows with the number of active workflows subscribed to this capability on the node, which can be in the hundreds-to-thousands range per the configured workflow limits (default `Global = 200`, soak-test configs use up to 5000): [6](#0-5) 

Combining a large registered-trigger count with an attacker-supplied topics array of thousands of entries yields a multiplicative (triggers × topics) cost per single incoming HTTP-triggered gateway message, repeatable at will by any external sender able to reach the gateway's webapi-trigger endpoint (no prior authorization is required to reach `processTrigger` — the sender-allowlist check happens only after the loop already begins).

### Impact Explanation
This can degrade or stall the node's ability to process further gateway messages (including trigger delivery for legitimate workflows), since `processTrigger` runs synchronously within `HandleGatewayMessage`. Repeated large-topics requests from any external, unauthenticated sender could cause sustained CPU consumption and message-processing delay/backlog on the node, a resource-exhaustion DoS on the internet-facing gateway path. It does not directly cause fund loss, but is a concrete "request pattern causing sustained crash or unbounded resource usage" per the audit method's own definition of in-scope classes.

### Likelihood Explanation
Medium. Reaching `processTrigger` requires only that some workflow with an active `web-api-trigger` registration exists on the DON and that the attacker can send messages recognized by the gateway service the workflow is bound to (the sender/topic-allowlist check happens *inside* the loop, after cost is already incurred, and does not gate entry to the loop itself). No credentials specific to the target workflow's allowedSenders are needed to trigger the expensive iteration — only to get a "fully matched" result, not to force the CPU cost.

### Recommendation
- Enforce a hard cap (`maxItems`) on `payload.Topics` in `TriggerRequestPayload`/schema and reject oversized requests early, before entering `processTrigger`.
- Restructure `processTrigger` to index triggers by topic (e.g., `map[topic][]*trigger`) instead of a full nested scan, so cost is proportional to matches, not to `triggers × topics`.
- Apply a per-sender/global rate limit before the loop begins, not only after a topic match is found.

### Proof of Concept
1. Have N (e.g., 200-5000, per configured `Workflows.Limits`) workflows register a `web-api-trigger` with the connector handler via `RegisterTrigger`.
2. As an unauthenticated external actor, send a `MethodWebAPITrigger` gateway message whose `TriggerRequestPayload.Topics` contains tens of thousands of short strings, keeping total payload under the configured `MaxRequestBytes`.
3. Observe `processTrigger` performs `N × len(topics)` map lookups and string comparisons synchronously inside `HandleGatewayMessage` for this single message; repeating the request rapidly drives sustained CPU load on the node processing gateway messages, independent of whether the sender is in any trigger's `allowedSenders`.
