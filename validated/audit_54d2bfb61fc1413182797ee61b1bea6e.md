### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop-domain` header to identify which merchant the payload belongs to. Because the HMAC signature never covers the `shop-domain` header, an attacker who owns a legitimate Shopify store can obtain a validly-signed webhook body (from their own shop) and replay it against the app's webhook endpoint with a forged `shop-domain`/`x-shopify-shop-domain` header claiming to be a different, victim shop. The library will report the HMAC as valid and hand the forged shop identity straight to the host app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication gate before trusting the request, then reads `request.shop` (sourced directly from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header) and forwards it to the handler as the tenant identity: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop that produced/authorized this payload == shop attributed to the payload by the library`. Because the header is not part of the signed material, this equality is never enforced — the HMAC only proves "this body was signed with the app's shared secret by *some* installed shop," not "this body belongs to the shop named in this header." Any holder of a valid `(body, hmac)` pair for shop A (i.e., any merchant who has installed the app and can trigger/capture one of their own webhooks) can substitute shop B's domain in the header and have the library treat the forged body as authoritative data for shop B.

### Impact Explanation
This breaks the tenant boundary that `Registry.process` is expected to enforce before invoking `handler.handle` with `WebhookMetadata#shop`. A host application that (as encouraged by the library's own documentation) looks up the merchant's session/store record using the `shop` field from `WebhookMetadata` will process attacker-controlled data under another merchant's identity — cross-tenant data injection/corruption via a security-relevant channel (webhooks are typically used to write to order/product/customer records). This matches the Critical "cross-tenant access" impact category, since it lets a low-privileged actor (any merchant who can install the target app) inject fraudulent, validly-"authenticated" data into a completely different tenant's context without needing that tenant's access token or credentials.

### Likelihood Explanation
Likelihood is realistic: exploitation only requires the attacker to be a legitimate merchant of the target app (any internet user can install a public app), capture one webhook delivered to their own endpoint (trivial, since they control the endpoint), and replay it to the target app's webhook URL with a modified `shop-domain` header. No secrets, tokens, or privileged access to the victim shop are required.

### Recommendation
Do not treat the `shop-domain` header as authenticated merely because the body HMAC validates. At minimum:
- Cross-check `request.shop` against a known, previously-installed shop registered for the app (e.g., an existing offline session) before invoking the handler, rejecting unknown shops.
- Document prominently in `docs/usage/webhooks.md` that the `shop` field on `WebhookMetadata` is not itself HMAC-verified and must be validated by the host app against its own tenant/session store prior to use.
- Where feasible, prefer deriving the shop for webhook-triggered logic from server-side lookups (e.g., existing session for the shop implied only after installation verification) instead of trusting the header value as ground truth.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives a webhook (e.g. `orders/create`) with a legitimately computed HMAC over some attacker-crafted order body `B`.
2. Attacker captures the delivered request: headers `x-shopify-hmac-sha256: <valid HMAC of B>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and raw body `B`.
3. Attacker resends this exact request to the same app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`, unchanged) and finds it valid — see [5](#0-4) .
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, and the host app processes attacker-supplied data as if it originated from `victim.myshopify.com`.
