### Title
Webhook HMAC signs only the request body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts `request.shop` when constructing the `WebhookMetadata` object passed to the app's handler, without that value ever being bound to the HMAC that "proves" the request is genuine.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  and `Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signature: [2](#0-1) .

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field: [3](#0-2) . Because `to_signable_string` for a webhook `Request` is just the raw body, this validation only proves "this body was HMAC-signed by Shopify at some point" — it proves nothing about which shop, topic, or webhook that signature was originally issued for.

`Registry.process` then uses the header-derived, unauthenticated `request.shop` (and `request.topic`) directly when building the data handed to the app's webhook handler: [4](#0-3) .

The security equality this breaks is: `shop authenticated-by-HMAC == shop acted-upon-by-handler`. In reality: `shop covered by HMAC` (nothing) `≠ shop used by handler` (`shopify-shop-domain` header, fully attacker-controlled).

### Impact Explanation
An unprivileged user who operates their own shop (Shop A) with the vulnerable app installed can capture one legitimate webhook delivery Shopify sends to the app for Shop A (a valid `raw_body` + valid `hmac-sha256` pair, computed with the shared `api_secret_key`). Because the signature covers only the body, the attacker can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., another merchant's shop, Shop B). `HmacValidator.validate` still succeeds (the body+hmac pair is valid), so `Registry.process` invokes the handler with `WebhookMetadata.shop == "shop-b.myshopify.com"` even though the payload actually originated from Shop A. Any app logic that trusts `WebhookMetadata#shop` to select which tenant's data/session/access token to act on (a standard pattern for multi-tenant Shopify apps) will perform actions against the wrong tenant using attacker-supplied body content — a cross-tenant data confusion/write primitive. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Webhook endpoints are internet-facing by design (Shopify posts to a public URL), so no privileged access is required to send crafted HTTP requests to this endpoint. The attacker only needs a shop of their own with the app installed to generate one authentic `body+hmac` pair (e.g., by triggering any webhook topic they subscribe to, such as `app/uninstalled` or any order/customer event on their own store), then replay it with a forged `shop-domain` header. No knowledge of `api_secret_key` is required. The bug is deterministic and requires no timing race or guessing.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signed string, or otherwise cryptographically bind them to the HMAC before trusting them — e.g., have `Request#to_signable_string` incorporate the shop domain, or have `Registry.process` re-derive/verify the shop from a source that is itself covered by the signature (such as looking up the shop via the delivered `webhook_id` against Shopify, or requiring apps to cross-check `shop` against an active session before acting). At minimum, document clearly that `WebhookMetadata#shop` is not authenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and captures one legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared secret), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request object whose `hmac` matches `H`. `Utils::HmacValidator.validate` (path shown at `lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks `B` against `H`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, even though `B` never originated from `victim-shop`.
5. Any handler logic keyed on `data.shop` (e.g., looking up the victim's stored session/access token and applying attacker-controlled fields from `B`) now operates cross-tenant using attacker-supplied body content.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
