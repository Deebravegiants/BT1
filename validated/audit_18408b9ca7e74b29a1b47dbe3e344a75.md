## Validation of the claimed equality

The claim is: `DepositOnChainUtxosExternalAction.runAction`'s `circomData.originalSender` (used as `_from` in `transferERC20TokenFrom`) is never bound to any proof-verified value, so an attacker can pass an arbitrary victim address as `originalSender` when `EmporiumUpgradeable` invokes it as a stateless `EmporiumOperation`.

Tracing the path confirms this is real, given the stated precondition (Emporium deployed as an allowed recipient of `DepositOnChainUtxosExternalAction`):

- `onlyAllowedRecipient` only checks `isAllowedRecipient[msg.sender]`, never `msg.sender == address(hinkal)`. [1](#0-0) 
- `EmporiumUpgradeable.runAction` decodes an `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and, for stateless ops (`invokeWallet=false`), makes an arbitrary raw `.call{value}(op.callData)` to `op.endpoint`, with no constraint on the target's calldata contents beyond forbidding the wallet selectors. [2](#0-1) 
- The Groth16 proof/public-input binding (`getSignedMessageHash`, `formBasicInput`) and the `calldataHash` integrity check (`getHashedCalldata1/2`) only cover the **outer** `circomData` fields (the Emporium-level `CircomData`, its `erc20TokenAddresses`, `amountChanges`, `slippageValues`, `externalActionData` struct as a whole, etc.). They do **not** decode into `externalActionMetadata`'s inner byte content (`stack.ops[i].callData`), so a `forgedCircomData` struct encoded inside `op.callData` (targeting a *different* external action, `DepositOnChainUtxosExternalAction.runAction`) is never constrained by the circuit or by `getHashedCalldata`. [3](#0-2) [4](#0-3) 
- Inside `DepositOnChainUtxosExternalAction.runAction`, `userAddress = circomData.originalSender` (taken from the forged, unverified struct) is used directly as `_from` in `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)`, with `msg.sender == EmporiumUpgradeable`. [5](#0-4) [6](#0-5) [7](#0-6) 
- `deltaAmounts[i] == 0` is trivially satisfied by the attacker since `deltaAmounts` is a param the attacker's forged call fully controls (it is not `Hinkal`'s own `deltaAmountChanges` computed from the outer `circomData` — it's whatever the attacker encodes into `op.callData` for this nested call). [8](#0-7) 
- None of the checks that gate `Hinkal.transact` (`performHinkalChecks`, `verifyProof`, `rootHashExists`, slippage/balance equalities, `insertNullifiers`) apply here, because this is a fully separate, attacker-crafted low-level call executed *inside* the Emporium's `runAction`, reachable only through the outer, legitimately-verified Emporium op — the outer proof says nothing about the semantics of `op.callData`'s bytes for a stateless call to an arbitrary `endpoint`. [9](#0-8) 

So the equality "AUTHORITY: `originalSender` bound to a proof-verified account" indeed breaks — the victim's ERC20 allowance to `DepositOnChainUtxosExternalAction` can be drained by anyone through `EmporiumUpgradeable`'s stateless-op mechanism, provided the precondition (Emporium listed in `_allowedRecipients` of that action, and victim having a standing approval to that action) holds. This is a real design flaw in the interaction between `onlyAllowedRecipient` (which trusts any allowed-recipient contract to have already validated the caller) and `EmporiumUpgradeable`'s unconstrained "call anything with any bytes" stateless-op feature.

### Title
Emporium stateless ops can call `DepositOnChainUtxosExternalAction.runAction` with a forged `originalSender` to drain victim ERC20 allowances - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s stateless-op branch performs an unconstrained `op.endpoint.call(op.callData)`, and `ExternalActionBaseV2.onlyAllowedRecipient` only checks `isAllowedRecipient[msg.sender]` without requiring the call to originate from `Hinkal.transact`. If `DepositOnChainUtxosExternalAction` lists Emporium as an allowed recipient, an attacker can drive Emporium (via their own valid, unrelated Emporium-level proof) to call `DepositOnChainUtxosExternalAction.runAction` with a forged `circomData.originalSender` set to a victim who has a standing ERC20 approval to that action, pulling the victim's tokens via `transferERC20TokenFrom`.

### Finding Description
The broken equality is: `circomData.originalSender` used inside `DepositOnChainUtxosExternalAction.runAction` as the `_from` of `transferFrom` must equal the account whose proof/signature authorized the current call. In this path, it does not — that `circomData` struct is fabricated inside `EmporiumOperation.callData`, which is never validated against any Groth16 public input, `calldataHash`, or `signedMessageHash`. The outer `Hinkal.transact` → `performHinkalChecks` → `verifyProof` machinery only validates the *outer* `circomData` presented to `Hinkal.transact`; the byte contents of `externalActionMetadata` (decoded as `EmporiumStack.ops[].callData`) are opaque to the proof system. `EmporiumUpgradeable.runAction`'s stateless branch (`invokeWallet==false`) then executes `op.endpoint.call{value: op.value}(op.callData)` with essentially no restriction other than blocking the `callHinkalWallet`/`doSendToRelay` selectors. Because `DepositOnChainUtxosExternalAction` trusts any `isAllowedRecipient[msg.sender]` caller (which includes Emporium, per the stated deployment precondition) without re-verifying that the original outer transaction was authorized by the `originalSender` embedded in the forged inner struct, the attacker's crafted call succeeds and drains the victim's pre-existing ERC20 allowance to `DepositOnChainUtxosExternalAction` into UTXOs credited to the attacker's Emporium session.

### Impact Explanation
Direct theft of a third party's approved ERC20 balance without any signature, proof, or on-chain action from that party — this is a fund-theft / authorization-bypass primitive matching the Critical category ("direct theft of shielded or in-flight user funds" / "executing calls or moving assets a wallet owner or prover never authorised"). The attack is repeatable against any victim with a standing approval to `DepositOnChainUtxosExternalAction`, limited only by the victim's approved amount.

### Likelihood Explanation
Requires the specific deployment precondition that `DepositOnChainUtxosExternalAction` was constructed with `EmporiumUpgradeable`'s address included in `_allowedRecipients`, and that a victim has left a standing ERC20 approval to `DepositOnChainUtxosExternalAction` (e.g., from prior legitimate on-chain-UTXO deposit flows where such approvals are a normal part of usage). Given that precondition, the attacker only needs their own valid, cheap Emporium-level proof for an unrelated small deposit — no privileged role or victim cooperation needed, and the attack is repeatable across any victim/approval pair.

### Recommendation
Add an explicit binding check to `ExternalActionBaseV2`/`DepositOnChainUtxosExternalAction` so that `msg.sender == address(hinkal)` is enforced for actions that trust `circomData.originalSender` for fund transfers, or require `EmporiumUpgradeable`'s stateless-op targets to be restricted to a curated allowlist of safe endpoints/selectors rather than arbitrary `onlyAllowedRecipient`-gated external actions. At minimum, `DepositOnChainUtxosExternalAction.runAction` should not accept nested/forged `circomData` from a non-`Hinkal` caller; it should only be invoked as `IExternalActionV2` directly from `Hinkal._externalTransact`.

### Proof of Concept
Foundry fork test:
1. Deploy `DepositOnChainUtxosExternalAction` with `_allowedRecipients = [address(emporium)]`.
2. Have victim `V` approve `DepositOnChainUtxosExternalAction` for token `T` (simulating leftover approval from prior legitimate on-chain deposit usage).
3. Attacker `A` builds a valid outer Emporium `CircomData`/proof for a trivial unrelated deposit through `Hinkal.transact`, with `externalActionMetadata` encoding an `EmporiumStack` containing one stateless `EmporiumOperation{endpoint: address(depositAction), invokeWallet: false, callData: abi.encodeWithSelector(DepositOnChainUtxosExternalAction.runAction.selector, forgedCircomData, deltaAmounts)}`, where `forgedCircomData.originalSender = V`, `forgedCircomData.erc20TokenAddresses = [T]`, `utxoAmounts` sized to `V`'s full allowance, and `deltaAmounts = [0]`.
4. Submit `A`'s transaction through `Hinkal.transact`.
5. Assert: `T.balanceOf(V)` decreases by the drained amount and `T.allowance(V, depositAction)` is consumed, while `V` never signed, proved, or submitted anything — demonstrating the AUTHORITY equality breaks (`originalSender` used for `transferFrom` ≠ account that authorized the transaction via any verified proof/signature).
