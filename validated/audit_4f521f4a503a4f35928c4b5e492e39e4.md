### Title
Chainlink oracle price feed in `SimplexPaymaster` does not check L2 sequencer uptime, allowing stale/frozen prices during sequencer downtime - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` is deployed on L2 rollups (Arbitrum, Base) per the operator config [1](#0-0) , and prices gas payments using Chainlink `AggregatorV3Interface.latestRoundData()` feeds through `_getOraclePrice` [2](#0-1) . This function validates only positivity of the answer and a maximum staleness window (`maxOracleAge`), but never verifies whether the L2's sequencer was recently down, which is the well-documented Chainlink L2 sequencer-feed risk.

### Finding Description
`_getOraclePrice` reads `latestRoundData()` and reverts only on `answer <= 0` (`InvalidOraclePrice`) or `block.timestamp - updatedAt > maxOracleAge` (`StaleOraclePrice`) [3](#0-2) . On Arbitrum/Optimism/Base-style L2s, when the sequencer goes down, the underlying Chainlink price feed can stop updating while remaining within the `maxOracleAge` staleness window (especially for feeds with longer heartbeats, as the code comment itself notes "Base/Ethereum stablecoins up to 24h" [4](#0-3) ), meaning the contract will happily accept a price that is stale-but-fresh-looking relative to `maxOracleAge`. Chainlink's official recommendation for any L2 deployment is to additionally check a sequencer uptime feed (`0xFdB631F5EE196F0ed6FAa767959853D9C81cf4A1` on Arbitrum, an analogous feed on other L2s) and reject prices during/soon-after an outage grace period. No such check exists anywhere in `SimplexPaymaster.sol` or its price-fetching path — confirmed by the absence of any "sequencer" reference in the EVM contracts directory.

This differs from ordinary staleness handling: during a sharp market move, the sequencer being down means the *last available* round is silently treated as current-and-valid market price by `_tokenPrice`, `getTokenPrice`, and `estimateTokenCost`, all of which route through `_getOraclePrice` [5](#0-4) .

### Impact Explanation
`_tokenPrice` determines the ERC-20 amount charged for gas sponsorship in every `PERMIT`/`PERMIT2` UserOperation processed by the paymaster, and also gates the oracle-derived slippage bound used in `swapAndDeposit`'s fee-recycling swap. If the sequencer is down and the last-reported price diverges materially from the true market price by the time service resumes (or is manipulated on the source chain feed provider side during the outage window), users could be overcharged or undercharged in stablecoin terms relative to native gas cost, and fee-recycling swaps could execute at a stale rate, directly affecting the treasury's markup surplus and the protocol's exposed token balances. This is a fund-integrity issue proportional to sponsored transaction volume, though bounded per the contract's own stated security model of "small permit amounts."

### Likelihood Explanation
L2 sequencer outages are infrequent but have occurred in practice on Arbitrum, which is one of the chains this paymaster targets [6](#0-5) . The condition requires no attacker action beyond ordinary use of the paymaster during/immediately after a real sequencer outage — any user or filler submitting a `PERMIT`/`PERMIT2` UserOperation, or the keeper calling `swapAndDeposit`, would trigger `_getOraclePrice` and receive a price the contract itself cannot distinguish from a healthy quote.

### Recommendation
Add a sequencer uptime feed check (e.g. Chainlink `AggregatorV3Interface` at the well-known sequencer-feed address for each L2) in `_getOraclePrice` or `_tokenPrice`, reverting if the sequencer is currently down or has been up for less than a grace period (commonly 1 hour) since the last outage, mirroring Chainlink's documented L2 pattern. This should be configurable per-chain in `Params`, since not every deployment target (e.g. BSC, Polygon, Ethereum mainnet) has a sequencer-feed equivalent.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum with `nativeOracle` pointed at a real Chainlink ETH/USD feed and `maxOracleAge` set to a typical heartbeat-derived value (e.g. 86400s per the config default in tests [4](#0-3) ).
2. Simulate an Arbitrum sequencer outage (as historically occurred): the sequencer halts, but the last Chainlink round's `updatedAt` remains within `maxOracleAge`.
3. Call `getTokenPrice`/`estimateTokenCost`, or submit a UserOperation using `PERMIT`/`PERMIT2` mode; `_getOraclePrice` passes both its checks (`answer > 0` and freshness within `maxOracleAge`) and returns the stale last-known price as if it were current.
4. Once the sequencer resumes and the true market price has moved, any UserOperations processed during the outage window were priced against the incorrect stale rate, and `swapAndDeposit`'s slippage bound (`swapSlippageBps`) was computed against the same stale reference, permitting an unfavorable swap execution.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
