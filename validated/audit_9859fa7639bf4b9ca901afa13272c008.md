### Title
PoA Bridge `describeWithdrawal` matches by `assetId` only, causing status/hash misattribution across withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status/hash for a withdrawal by matching the PoA Bridge indexer's response solely on `assetId`, ignoring the withdrawal's `index`, `destinationAddress`, and `amount`. When a caller batches multiple withdrawals of the same asset (a supported SDK use case) within one NEAR intent transaction, this lookup can return the wrong withdrawal record's status and destination transaction hash for a given index.

### Finding Description
`describeWithdrawal` is implemented as: [1](#0-0) 

The comment explicitly states the response list is unsorted and match is performed "by assetId instead of index" — but no other discriminator (destination address, amount, or index) is used. `args.tx.hash` (the shared NEAR intent transaction hash for the whole batch) is used to fetch all withdrawals for that transaction, and then `findMatchingWithdrawal` filters only on `assetId`.

The SDK explicitly supports batching multiple withdrawals of possibly the same asset in a single `createWithdrawalIntents`/`processWithdrawal` call, and assigns per-route index counters: [2](#0-1) 

All PoA-bridge withdrawals in the same batch (and same NEAR tx) share the same `bridge.route` counter and the same `tx.hash`, differing only by `index`. Because `describeWithdrawal` discards `index` and matches purely on `assetId`, two (or more) withdrawals of the same asset in the batch — e.g. same token sent to two different destination addresses/amounts — will both resolve to whichever single record `findMatchingWithdrawal` returns first, regardless of which index is queried.

This breaks the equality that should hold: "the status/txHash reported for withdrawal at index N is the on-chain outcome for withdrawal N," not for some other withdrawal N' sharing the same `assetId`.

### Impact Explanation
`watchWithdrawal`/`waitForWithdrawalCompletion` (used by `sdk.waitForWithdrawalCompletion` and `sdk.createWithdrawalCompletionPromises`) consumes this status directly: [3](#0-2) 

If withdrawal index 0 (destination A, amount X) and index 1 (destination B, amount Y) share `assetId`, an integrator polling index 1 could receive index 0's `completed` status and `txHash` before index 1 has actually completed (or vice versa). This is a status/hash misreport that can cause an integrator relying on this SDK signal to prematurely credit/mark-complete a withdrawal that has not actually settled on the destination chain, or to associate the wrong destination transaction hash with a withdrawal record — matching the "status or hash misreport making an integrator credit or refund twice" High-severity criterion.

### Likelihood Explanation
No privileged access or malicious actor is required — this triggers under ordinary, documented SDK usage (batching multiple withdrawals of the same asset, which the SDK's `estimateWithdrawalFee`/`processWithdrawal` APIs explicitly support via array `withdrawalParams`). Any integrator withdrawing the same PoA-bridged token to multiple destinations in one call is exposed to this misattribution as soon as more than one same-asset withdrawal is `PENDING`/`COMPLETED` concurrently.

### Recommendation
Change `findMatchingWithdrawal` to disambiguate using additional fields returned by the PoA indexer (e.g. destination `address`, `amount`, and/or an ordering/sequence field correlated with `index`) rather than `assetId` alone, so each `describeWithdrawal(index)` call can only resolve to the specific withdrawal record it represents.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents`/`sdk.processWithdrawal` with `withdrawalParams` = two entries for the same `assetId` (e.g. `nep141:btc.omft.near`), different `destinationAddress`/`amount`, executed in one NEAR transaction, routed through PoA Bridge.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals (same `tx.hash`, same bridge route).
3. Poll `bridge.describeWithdrawal` for `index: 0` and `index: 1`.
4. Because `findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` filters the indexer's unsorted `withdrawals` array by `assetId` only, both calls can return the same matched record (e.g. the one already `COMPLETED`), causing both indices to report `completed` with the same `txHash`, even though only one of the two underlying withdrawals has actually completed on-chain.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
