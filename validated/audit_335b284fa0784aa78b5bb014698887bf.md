### Title
Webhook shop/topic/webhook_id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, and `webhook-id` headers verbatim when constructing `WebhookMetadata` passed to the app's handler. Since those header fields are never included in the signed bytes, an attacker who obtains one validly-signed webhook body/HMAC pair (e.g., from webhooks Shopify sends for their own shop after installing the app) can replay that exact body+HMAC with a forged `shop-domain` header, causing the app's handler to process attacker-controlled data as if it originated from an arbitrary victim shop.

### Finding Description
The correct binding should be: `HMAC-verified bytes == bytes used to derive shop/topic/webhook identity`. In this gem that binding is broken.

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all read straight from HTTP headers, none of which participate in `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` only calls `verifiable_query.to_signable_string` (i.e., the body) to compute/compare the signature, never incorporating `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` handed to the app's business logic: [4](#0-3) 

Because the HMAC is computed by Shopify over the raw JSON body using the app's `client_secret`/`api_secret_key` (shared across every shop that installs the app), any shop that installs the app can receive a validly-signed body+HMAC pair for its own webhook. Since the headers carrying `shop-domain`, `topic`, and `webhook-id` are excluded from the signed payload, an attacker (an unprivileged shop owner who installed the target app) can replay that captured body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header to claim any victim shop, and/or the `topic`/`webhook-id` headers to claim a different event type. `HmacValidator.validate` will pass (the body bytes and HMAC still match), and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming the forged `shop`/`topic`/`webhook_id`, even though none of these were part of the cryptographic proof.

### Impact Explanation
This crosses a tenant boundary: the gem's own trust decision (`raise ... unless Utils::HmacValidator.validate(request)`) does not protect the very field (`shop`) that apps rely on to attribute the webhook payload to a tenant, matching the "field acted on but not covered by the HMAC" analog class. An app that uses `data.shop` from `WebhookMetadata` to look up which merchant's records to update (the documented, expected usage per `docs/usage/webhooks.md`) can be tricked into applying attacker-supplied body content under another merchant's identity, i.e., cross-tenant data injection through this gem's own webhook verification API.

### Likelihood Explanation
Any internet user can self-serve install the target Shopify app on their own shop (unprivileged, no special access needed), which causes Shopify to legitimately sign and deliver webhooks to the app for that shop, correctly HMAC'd with the app's shared secret. Capturing that body+HMAC pair and replaying it with a different `shop-domain`/`topic`/`webhook-id` header requires no secret knowledge, only observation of one's own legitimate webhook traffic and a raw HTTP request to the app's public webhook endpoint.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header values to the body before trusting them — e.g., include a canonicalized `shop|topic|webhook_id|raw_body` string in `to_signable_string`, or independently confirm the `shop-domain` header against Shopify by checking that the webhook subscription/webhook_id belongs to the claimed shop before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook, e.g. for `orders/create`, to the app's callback URL with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-webhook-id: <id>`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: attacker-controlled order JSON (attacker fully controls their own shop's order data).
2. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`) — headers are irrelevant to this check.
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, so the app processes attacker-controlled content as belonging to the victim shop.
