Confirmed: `sdk/packages/core/contracts/apps/IntentGatewayV2.sol` (the same version deployed to EVM-non-Tron chains via `evm/src/apps/IntentGatewayV2.sol`) has the actual-received-balance measurement fix, but `evm/tron/contracts/apps/IntentGatewayV2.sol` does not contain this logic at all — no `balanceOf` snapshot before/after `safeTransferFrom` exists in that file.

### Title
IntentGatewayV2 on Tron trusts nominal input amount instead of actual received balance for fee-on-transfer tokens, causing escrow over-crediting and stuck/insolvent order settlement - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-targeted `IntentGatewayV2.placeOrder` implementation escrows `order.inputs[i].amount` (the user-specified/nominal amount, reduced only by the protocol fee) without ever measuring what the contract actually received from `safeTransferFrom`. The mainline EVM contract fixed this exact class of bug by snapshotting `balanceOf(address(this))` before and after the transfer and using the delta, but the Tron variant was never updated with that fix.

### Finding Description
In `placeOrder` (non-predispatch branch), tokens are pulled with a plain `safeTransferFrom` and the escrow ledger `_orders[commitment][token]` is credited with `reducedInputs[i].amount`, which is derived purely from the caller-supplied `order.inputs[i].amount` minus the protocol fee — never from the gateway's actual token balance change: [1](#0-0) 

Contrast this with the corresponding EVM (mainline) implementation, which explicitly snapshots the balance before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual delta before it is ever used to compute `reducedInputs`, the commitment, or the escrow credit: [2](#0-1) 

The predispatch branch on Tron has the same defect: `_orders[commitment][token] += reducedInputs[i].amount` uses `reducedInputs[i].amount`, computed from the nominal `order.inputs[i].amount`, even though the actual sweep only measures `balance` against `requiredAmount` for a revert check, not to correct the escrowed amount: [3](#0-2) 

The commitment (`keccak256(abi.encode(order))`) is also computed from the nominal, un-adjusted amounts, so the on-chain escrow bookkeeping (`_orders` mapping) and the order commitment agree with each other but both diverge from the gateway's true token balance whenever a fee-on-transfer (or any transfer-amount-reducing) token is used as an input.

The fix was already applied to `evm/src/apps/IntentGatewayV2.sol` (see the Phase 1 "measure actual received" comment) and its `sdk/packages/core/contracts/apps/IntentGatewayV2.sol` counterpart, and is explicitly regression-tested for fee-on-transfer tokens in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceOrder_FeeOnTransferToken_Predispatch`) — but the identical fix was never ported to the Tron deployment of the same contract.

### Impact Explanation
When a fee-on-transfer input token is used to place an order on the Tron deployment of `IntentGatewayV2`:
- The escrow ledger `_orders[commitment][token]` records more tokens than the gateway actually holds.
- A solver filling the order and later redeeming escrow via `RedeemEscrow` will be entitled to withdraw an amount the contract cannot fully pay, because the contract's real token balance is short by the transfer fee.
- Because escrow accounting for multiple orders shares the same token balance pool, this creates an insolvency/shortfall condition: whichever solver/user redeems first can drain funds that were credited to other orders' escrow entries, causing later redeemers to have their withdrawal revert or be under-serviced (permanent freezing/loss of funds for other order participants).
- This is unbacked escrow accounting analogous to an unbacked mint — the contract believes it holds more of a token than it does, which cross-contaminates unrelated orders sharing the same token type.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder` on the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (or any ERC20 whose `transferFrom` delivers less than the requested amount, e.g. due to rebasing, deflationary burn-on-transfer, or proxy/wrapped tokens with transfer taxes) as an input asset. No special privileges, timing, or governance action is required — a single `placeOrder` call is sufficient to create an escrow entry that overstates the gateway's actual balance for that token.

### Recommendation
Port the balance-delta measurement fix from `evm/src/apps/IntentGatewayV2.sol` (Phase 1 logic) into `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` (or `balanceOf(dispatcher)` for the predispatch sweep) before and after each transfer, mutate `order.inputs[i].amount` to the measured delta, and only then compute `reducedInputs`, the commitment, and the `_orders` escrow credit from that actual-received amount — mirroring the same pattern already validated by the fee-on-transfer foundry tests for the mainline contract.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g. 1% fee) on the Tron-targeted deployment and mint tokens to `user`.
2. `user` approves `IntentGatewayV2` (Tron) for `inputAmount = 1000e18` and calls `placeOrder` with that token as the sole input, no `predispatch`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` only delivers `990e18` to the gateway (1% fee burned/redirected), matching the pattern already tested in `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` for the mainline contract.
4. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount` derived from the nominal `1000e18` (minus protocol fee, if any) — i.e. up to `1000e18`, not `990e18`.
5. A solver fills the order and later redeems escrow for `990e18`+ actual worth via `RedeemEscrow`; the gateway's real balance for that token is short, so either this redemption depletes balance belonging to other orders' escrow, or a later legitimate redemption for a different order reverts due to insufficient token balance — demonstrating fund freezing/loss caused by the discrepancy between recorded escrow and actual balance.
