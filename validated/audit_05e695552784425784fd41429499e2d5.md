### Title
Webhook topic and shop-domain headers are unauthenticated, allowing signed-body replay under an attacker-chosen topic/shop (`@registry[request.topic]&.handler` dispatch bypass) - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the request body but never the `X-Shopify-Topic` or `X-Shopify-Shop-Domain` headers. `Registry.process` then uses the unauthenticated `request.topic` value to look up `@registry[request.topic]&.handler` and dispatches with the unauthenticated `request.shop`, so a validly-signed webhook body captured for one topic/shop can be replayed with a different topic/shop header and still pass verification.

### Finding Description
The claimed broken binding, stated as an equality:

`HMAC(secret, signable_string)` where `signable_string == raw_body` (per `to_signable_string`, [1](#0-0) ) **should equal** `HMAC(secret, raw_body ++ topic ++ shop)` if topic/shop dispatch were meant to be authenticated. It does not — only the raw body is signed.

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares against `verifiable_query.hmac`: [2](#0-1)  — the topic and shop-domain headers never enter the computation.

`Registry.process` then trusts the raw header value `request.topic` (read directly from `@headers["shopify-topic"]`, attacker-controlled input, see [3](#0-2) ) to select the handler and to build `WebhookMetadata`, including `shop: request.shop` (also just a header read, [4](#0-3) ): [5](#0-4) 

**Exploit flow:** An app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app. An attacker installs the app on their own dev shop, points a webhook subscription at their own server, and triggers a low-sensitivity event (e.g. `app/uninstalled`). Shopify delivers a genuinely HMAC-signed body to the attacker using the real `api_secret_key`. Because the signature covers only the raw body, the attacker can then POST that exact same body to the target app's public webhook endpoint while setting `X-Shopify-Topic` to any other topic the app registered (e.g. `orders/create`, `customers/data_request`) and `X-Shopify-Shop-Domain` to an arbitrary victim shop. `HmacValidator.validate` still returns `true` (body unchanged, secret unchanged), `@registry[request.topic]&.handler` resolves to the real handler for the forged topic, and `handler.handle` executes with attacker-chosen `topic`/`shop` metadata and attacker-supplied body content.

**Why existing guards fail:** `HmacValidator.validate` (the only integrity check in the path) never inspects `to_signable_string` beyond the raw body, so it cannot detect topic/shop tampering. `ShopValidator`, `JwtPayload`, and OAuth `state` checks are not part of this webhook path at all — they guard the OAuth/session-token flows, not `Registry.process`.

### Impact Explanation
This lets an unprivileged attacker who legitimately installed the app on their own shop force execution of any of the app's registered webhook handlers (chosen from the public list of registered topics) with a body and declared `shop`/`topic` of their choosing, including handlers for sensitive topics like `orders/create` or `customers/data_request`. Because `shop` is also unauthenticated, the attacker can attribute the forged event to an arbitrary victim shop domain, giving this cross-tenant reach if the host app trusts `WebhookMetadata.shop` to look up merchant records. This matches the Critical category: authentication bypass (a webhook is accepted as authentic for a topic/shop it was never actually signed for) and potential cross-tenant access.

### Likelihood Explanation
Preconditions are low-cost and fully within the attacker's control: install the app on a dev shop (standard, unprivileged Shopify developer action), trigger any registered topic to obtain one genuinely signed body, then replay it directly to the app's public webhook endpoint with modified `X-Shopify-Topic`/`X-Shopify-Shop-Domain` headers. No secrets, tokens, or victim interaction are required, and this is repeatable against any topic the app registered via `Registry.add_registration` and against any shop domain.

### Recommendation
Include the `topic` and `shop-domain` (and ideally `webhook-id`) headers in the signable material used by `HmacValidator`, or otherwise cryptographically bind the dispatched topic/shop to the verified payload (e.g., Shopify's `X-Shopify-Hmac-Sha256` is documented as body-only, so instead the gem should independently verify that `request.shop` corresponds to a session/shop the app actually expects, and should not allow the header-declared topic to select a handler without also validating the body against that topic's expected shape/webhook-id via a server-side lookup, e.g., re-fetching or cross-checking the delivery via Shopify's API by `webhook_id`).

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb
require "test_helper"

class RegistryTopicConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Webhooks::Registry.clear
    @secret = "sekret"
    ShopifyAPI::Context.setup(api_secret_key: @secret, ...)

    @low_handler = Class.new { include ShopifyAPI::Webhooks::WebhookHandler
      def handle(data:); @@called = data; end
      def self.called; @@called; end }.new
    @high_handler = Class.new { include ShopifyAPI::Webhooks::WebhookHandler
      def handle(data:); @@called = data; end
      def self.called; @@called; end }.new

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "app/uninstalled", delivery_method: :http, path: "/wh", handler: @low_handler)
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/wh", handler: @high_handler)
  end

  def test_replayed_body_with_forged_topic_dispatches_high_sensitivity_handler
    raw_body = '{"id":1}' # body genuinely produced for app/uninstalled
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", @secret, raw_body))

    headers = {
      "shopify-topic" => "orders/create",       # forged: attacker relabels the topic
      "shopify-hmac-sha256" => hmac,            # still valid: signature is body-only
      "shopify-shop-domain" => "victim.myshopify.com", # forged shop
      "shopify-api-version" => "2024-01",
      "shopify-webhook-id" => "abc",
    }

    request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

    ShopifyAPI::Webhooks::Registry.process(request)

    # Assertion on the broken binding:
    # signature authenticated only raw_body; dispatch used attacker-chosen topic/shop
    assert_equal "orders/create", HighHandlerCalled.topic
    assert_equal "victim.myshopify.com", HighHandlerCalled.shop
  end
end
```
This demonstrates that a single genuinely-signed body can be relabeled to any registered topic/shop and still pass `HmacValidator.validate`, dispatching to a handler the attacker did not legitimately trigger.
