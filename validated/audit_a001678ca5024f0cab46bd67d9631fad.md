### Title
`validateDogeAddress()` accepts Base58-format Dogecoin addresses with an invalid checksum, allowing funds to be routed to an unowned address - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateDogeAddress()` in `packages/intents-sdk/src/lib/validateAddress.ts` validates only length, prefix (`D`/`A`), and Base58 charset via regex, and never decodes/verifies the Base58Check checksum, unlike its siblings `validateBtcBase58Address`, `validateLitecoinBase58Address`, `validateTronBase58Address`, and `validateDashAddress`, which all decode and verify the SHA256d checksum. Because `PoaBridge.validateWithdrawal()` calls `validateAddress()` as its sole address-correctness gate, a well-formed-looking but checksum-invalid Dogecoin address (i.e., a typo of a real address, same length/prefix/charset) passes validation and is written verbatim into the `ft_withdraw` intent's memo as `WITHDRAW_TO:<address>`.

### Finding Description
The claimed equality is: *the address string encoded in the intent memo == a real, spendable Dogecoin address (i.e., one whose Base58Check checksum is valid).*

- `validateDogeAddress(address)` at [1](#0-0)  only runs `/^[DA][1-9A-HJ-NP-Za-km-z]{25,33}$/.test(address)`. It never calls `base58.decode` or verifies the trailing 4-byte SHA256d checksum.
- Contrast with the equivalent Bitcoin/Litecoin/Tron/Dash validators, which all decode Base58, slice out `payload`/`checksum`, recompute `sha256(sha256(payload))`, and byte-compare, e.g. [2](#0-1)  and [3](#0-2) .
- `validateAddress()` dispatches Dogecoin to this weak check: [4](#0-3) .
- `PoaBridge.validateWithdrawal()` uses `validateAddress()` as the only address-format gate before proceeding to token lookup and amount checks: [5](#0-4) . There is no further checksum/validity check anywhere downstream in `validateWithdrawal`.
- `PoaBridge.createWithdrawalIntents()` then calls `createWithdrawIntentPrimitive()` which writes the raw, unvalidated address into the memo unchanged: [6](#0-5)  and [7](#0-6) .

Exploit input: an attacker (an ordinary user withdrawing their own DOGE) supplies a `destinationAddress` that is a real Doge address with one or more characters near the end flipped (still Base58 alphabet, same length, same `D`/`A` prefix), making it match the regex but fail the Base58Check checksum. Since no other stage of the SDK verifies the checksum, `createWithdrawalIntents()` succeeds and produces `WITHDRAW_TO:<invalid-checksum-address>` — an intent that the intents-contract will sign/execute, and the off-chain relayer/bridge will attempt to pay out to, an address string with no known private key (checksum broken → not a decodable/derivable hash160, and generally no wallet can be derived to match it). Funds sent off-chain to that string are unrecoverable through this SDK's mechanisms.

None of the existing guards catch this: `compareAddresses` only checks token self-address collisions, `supports()` ordering is unrelated, `FeeExceedsAmountError`/`getUnderlyingFee` deal with fees not addresses, and the NEAR intents contract itself only verifies signatures/nonces on the NEAR side — it has no knowledge of Dogecoin Base58Check semantics, so it cannot catch a malformed destination memo string.

### Impact Explanation
This is a Critical-severity finding under the given rubric ("funds delivered to a wrong address/chain/contract with no recovery"): the intent primitive is signed and submitted with a destination address that is not a valid, spendable Dogecoin address. If the PoA bridge's off-chain relayer does not independently re-verify checksum before broadcasting a real DOGE transaction (which is outside the scope of this repo per the rules, but the point is the *intents-sdk* layer that is supposed to guarantee "destination truth" fails to do so), the withdrawing user's own funds are irrecoverably misrouted. This is repeatable per call — any DOGE withdrawal request with a checksum-broken address will pass validation.

### Likelihood Explanation
Preconditions are trivial: the caller only needs to submit a `destinationAddress` for asset `nep141:doge.omft.near` that matches the 26–34-char Base58 charset regex with `D`/`A` prefix but has an invalid checksum (e.g., a single mistyped trailing character). This requires no special privileges — it is exactly the class of unprivileged, self-harming or integrator-forwarded-string input the rules deem in-scope. It's a one-line change to any valid Doge address to produce such a string, making this highly feasible and trivially reproducible.

### Recommendation
Implement full Base58Check decoding and checksum verification for `validateDogeAddress()`, mirroring the existing pattern used for Bitcoin/Litecoin/Tron/Dash: decode with `base58.decode`, require the decoded length to be 25 bytes (`version(1) + hash160(20) + checksum(4)`), validate the version byte(s) for Dogecoin mainnet (`0x1e` for P2PKH `D...`, `0x16` for P2SH), and compare `sha256(sha256(payload)).subarray(0,4)` against the trailing checksum bytes, returning `false` on any decode error or mismatch.

```ts
import { describe, it, expect, vi } from "vitest";
import { validateAddress } from "../src/lib/validateAddress";
import { Chains } from "../src/lib/caip2";
import { base58 } from "@scure/base";
import { sha256 } from "@noble/hashes/sha2";

// helper: take a known-valid Doge P2PKH address and corrupt the checksum
// by flipping one trailing base58 character, keeping length/prefix/charset intact.
const VALID_DOGE_ADDRESS = "D86DwJpYsyV7nTP2ib5qdwGsb2Tj7LgzPP"; // matches regex AND has a valid checksum
const CORRUPTED_DOGE_ADDRESS = "D86DwJpYsyV7nTP2ib5qdwGsb2Tj7LgzPQ"; // last char changed; same length/prefix/charset

describe("validateAddress - Dogecoin checksum gap", () => {
  it("regex passes for both valid and checksum-corrupted addresses", () => {
    expect(validateAddress(VALID_DOGE_ADDRESS, Chains.Dogecoin)).toBe(true);
    // BUG: should be false, checksum is invalid, but validateDogeAddress only checks regex
    expect(validateAddress(CORRUPTED_DOGE_ADDRESS, Chains.Dogecoin)).toBe(true);
  });

  it("independently confirms the corrupted address fails Base58Check", () => {
    const decoded = base58.decode(CORRUPTED_DOGE_ADDRESS);
    const payload = decoded.subarray(0, 21);
    const checksum = decoded.subarray(21, 25);
    const expected = sha256(sha256(payload)).subarray(0, 4);
    // Prove checksum mismatch — i.e., DESTINATION_TRUTH (address == real spendable address) is false
    expect(Buffer.from(checksum)).not.toEqual(Buffer.from(expected));
  });
});

// Integration-level: mock only HTTP (PoA bridge's getSupportedTokens), then assert
// bridge.validateWithdrawal() resolves and createWithdrawalIntents() returns an intent
// containing "WITHDRAW_TO:<CORRUPTED_DOGE_ADDRESS>" despite the failed checksum above.
```

The core assertion pair is:
- LHS (claimed truth): `destinationAddress` decoded and checksum-verified as a real Dogecoin address == `true`.
- RHS (actual system behavior): `validateAddress(CORRUPTED_DOGE_ADDRESS, Chains.Dogecoin)` == `true`, and `PoaBridge.validateWithdrawal(...)` resolves without throwing, and the resulting intent memo contains `WITHDRAW_TO:<CORRUPTED_DOGE_ADDRESS>`.

These two sides diverge before and after the call — proving `DESTINATION_TRUTH` is broken. [1](#0-0)

```typescript
function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
}
```

```typescript
export function validateDashAddress(address: string): boolean {
	try {
		const decoded: Uint8Array = base58.decode(address);

		// version (1) + payload (20) + checksum (4)
		if (decoded.length !== 25) return false;

		const version = decoded[0];
		if (
			version !== 0x4c && // P2PKH
			version !== 0x10 // P2SH
		) {
			return false;
		}

		const payload = decoded.subarray(0, 21);
		const checksum = decoded.subarray(21, 25);

		const hash1 = sha256(payload);
		const hash2 = sha256(hash1);
		const expectedChecksum = hash2.subarray(0, 4);

		for (let i = 0; i < 4; i++) {
			if (checksum[i] !== expectedChecksum[i]) return false;
		}

		return true;
	} catch {
		return false;
	}
}
```

```typescript
function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
```
