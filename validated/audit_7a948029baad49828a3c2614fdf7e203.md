### Title
Blocklistable-token beneficiary can permanently freeze IntentGateway escrow - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`_withdraw()`, the sole path that releases escrowed input tokens to a solver or refunds a user in the IntentGatewayV2 (`IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents`), performs a direct `IERC20.safeTransfer` (and a separate fee-token `safeTransfer`) to a fixed `beneficiary` address with no try/catch or fallback. For blocklist-capable tokens such as USDC/USDT, if the beneficiary is blocklisted by the token issuer, every attempt to withdraw for that order commitment reverts, and the escrow becomes permanently unrecoverable.

### Finding Description
`_withdraw` decrements `_orders[commitment][token]` and then calls `IERC20(token).safeTransfer(beneficiary, amount)` unconditionally (`IntentsBase.sol:464-469`). It's invoked by:
- `IntrinsicIntents._fillSameChain` for same-chain escrow release to the solver.
- `ExtrinsicIntents`'s `onAccept` (via decoded `WithdrawalRequest`) for cross-chain `RedeemEscrow` (release to solver) and `RefundEscrow` (refund to user) requests delivered through Hyperbridge.
- `onGetResponse`, used for source-chain cancellation, which also calls `_withdraw` to refund the user.

In all cross-chain flows, the beneficiary is fixed at the point the `WithdrawalRequest` is constructed on the destination/source chain (`msg.sender` solver at fill time, or `order.user` at cancel time) and is delivered as an immutable cross-chain message body — there is no mechanism to resubmit the message with a different beneficiary if delivery reverts. Because the Solidity transaction is atomic, a reverting `safeTransfer` also reverts the `_orders[...]` decrement and the `_filled` finalization, so the message can be retried indefinitely by a relayer but will keep reverting for as long as the beneficiary stays blocklisted — which, for USDC/USDT blocklist entries, is typically permanent (e.g., addresses linked to hacks or sanctions).

### Impact Explanation
If a solver's or user's address is added to a token issuer's blocklist (a decision entirely outside Hyperbridge's control, and which can be triggered by third parties, e.g. front-running a solver address with a phishing/hack association, or a sanctioned address being the destination beneficiary encoded in an order), the entire escrowed principal for that order, along with any accrued relayer fee-token balance, becomes permanently stuck in the `IntentGatewayV2` contract with no path to recovery — not even via governance, since `_sweepDust` only sweeps protocol-owned dust, not per-order escrow tied to a specific `commitment`. This is a permanent freezing-of-funds condition reachable by any order participant (user placing an order, or any solver filling it) without requiring privileged access.

### Likelihood Explanation
Reachable via the normal, unprivileged flow: any user places an order and any solver fills it. No special permissions are required to trigger the freeze — it only requires that the encoded beneficiary address (chosen freely by the order creator, or the filling solver's own EOA) becomes blocklisted by the underlying ERC-20 issuer at any point before withdrawal settles. Given USDC/USDT are both stablecoins commonly used as inputs/outputs in intent swaps and both maintain active blocklists, this is a realistic and moderately likely occurrence over the contract's operating lifetime.

### Recommendation
Wrap the token transfer in `_withdraw` (and the fee-token transfer) in a try/catch, and on failure, credit the amount to an internal "pending withdrawal" balance for the beneficiary (or an alternate, re-specifiable recovery address) rather than reverting the whole state transition. Alternatively, support a pull-based claim function that lets the affected party redirect payout to a different address if the original is blocklisted, so a single non-transferable beneficiary cannot brick settlement of an entire order's escrow.

### Proof of Concept
1. Deploy `IntentGatewayV2` with USDC-like input token supporting an issuer-controlled blocklist.
2. User places a cross-chain order with `inputs = [USDC, amount]`.
3. Solver fills the order on the destination chain; `_fillCrossChain` dispatches a `RedeemEscrow` `WithdrawalRequest` with `beneficiary = solver`.
4. Before the relayer delivers the message, the USDC issuer adds `solver` to its blocklist (e.g., due to unrelated flagged activity).
5. Relayer submits the proof; `onAccept` decodes the `WithdrawalRequest` and calls `_withdraw`, which calls `IERC20(USDC).safeTransfer(solver, amount)` — this reverts because `solver` is blocklisted.
6. Every retry of message delivery reverts identically; the escrowed USDC is permanently locked in `IntentGatewayV2` with no recovery path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
