### Title
Simplex Intent Solver Prices Uniswap V4-Funded Pairs from Manipulable Spot Tick with No TWAP, Unguarded by Default - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex's `FXFiller` intent-solver strategy prices "venue-priced" pairs (any curveless pair paired with a USD-stable `token0`) directly from a Uniswap V4 pool's instantaneous `sqrtPriceX96`/tick, read via `getSlot0` with no TWAP. This is the same root-cause class as the reported Curve `get_virtual_price` issue: a spot on-chain AMM price used as an oracle for value-critical decisions, manipulable within a single block/transaction via a large swap or flash loan.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` selects the most-liquid Uniswap V4 position for an exotic token and calls `computeDirectPoolPriceUsd`, which derives the price straight from the pool's current `sqrtPriceX96`/tick returned by `StateView.getSlot0` [1](#0-0) . The refresh path that feeds this price reads `getSlot0`/`getLiquidity` fresh at query time with no time-weighting [2](#0-1) .

This spot price is fed into `resolveLegRates`, which uses it as the fill rate for the leg whenever the pair is curveless (no `bidPricePolicy`/`askPricePolicy`) and `token0` is a USD stablecoin — the documented "pool-based pricing" mode [3](#0-2) . The as-designed flow is documented as: `getVenueUsdPrice` → `checkPriceGuard` → `rate = 1/venueUsd`, with the internal docs explicitly noting the guard is "the only defense on this path" and checks deviation from a static reference, not execution cost [4](#0-3) .

Critically, this guard is optional and disabled by default: the docs state "The two fields must be set together; omit both to leave the chain unguarded," and the unit test confirms `checkPriceGuard` "passes every quote when no guard is configured," even a 3x-off price ("5000" vs reference "1575") [5](#0-4) [6](#0-5) . Even when configured, the guard only bounds deviation against a static, operator-set reference value, not against a robust time-weighted or multi-source price — an attacker who moves the pool within the configured band still passes.

### Impact Explanation
An unprivileged actor can manipulate a thinly liquid Uniswap V4 pool (the same pool the solver's LP position is quoting from) via a large swap or a flash-loan-funded swap, moving `sqrtPriceX96`/tick, and then immediately submit (or have a colluding party submit) an `IntentGatewayV2` order sized to be filled by the venue-priced FX solver at the skewed rate. Because the price feeds `resolveLegRates`'s `rate = 1/venueUsd` directly into `computeLegPolicyOutput` with no size/impact adjustment (the pool fee tier is read but "never applied to the price," per the internal flow doc), the solver can be induced to deliver an exotic token at a price far off the true market, draining solver-held inventory or its Uniswap V4 LP position for underpriced consideration. This is direct loss of solver/vault funds analogous to the Curve LP price manipulation being used to mis-value collateral/borrowing power.

### Likelihood Explanation
Likelihood is moderate-to-high for any operator who runs venue-priced pairs without configuring `referencePrice`/`maxDeviationBps` (the default state, and the config schema treats it as fully optional) [7](#0-6) . Exploitation requires only a swap against the referenced pool (or a flash loan if the operator's own LP dominates the pool's depth) followed by placing an intent order — both are standard, permissionless, single-transaction-reachable actions requiring no privileged access. Even with the guard configured, an attacker constrained to move the price just inside `maxDeviationBps` still profits at reduced but nonzero magnitude.

### Recommendation
- Make the Uniswap V4 price guard mandatory for any venue-priced pair, rather than allowing `referencePrice`/`maxDeviationBps` to be omitted.
- Replace or supplement the spot `getSlot0` read with a Uniswap V4 TWAP (observation-based) price, or a Chainlink/off-chain reference feed, before trusting the pool as the price source, mirroring the sherlock recommendation for Curve.
- Add a minimum-liquidity/maximum-order-size-vs-pool-depth check so a single order cannot walk the price materially within the same block.
- Consider read-only-reentrancy-style protections and staleness checks (e.g., reject prices computed at a block where the pool's liquidity/tick shows an anomalous single-block delta) before using the quote to size a fill.

### Proof of Concept
1. Attacker identifies a chain/pair where the operator's `filler-config.toml` lists a `[vault.uniswapV4]` position for pair `USDC/EXOTIC` with no `referencePrice`/`maxDeviationBps` set (default/unguarded, confirmed possible per config and tests) [6](#0-5) .
2. Attacker swaps a large amount through the same Uniswap V4 pool (optionally via flash loan) to move `sqrtPriceX96`/tick sharply in their favor.
3. In the same or immediately following block, attacker (or a colluding solver-facing user) submits an `IntentGatewayV2` order requesting the EXOTIC token, sized so the FXFiller's `calculateProfitability`/`resolveLegRates` reads the skewed pool price via `getExoticTokenPrice` → `computeDirectPoolPriceUsd` [1](#0-0) .
4. The solver bids/fills at the manipulated rate (`rate = 1/venueUsd`), delivering EXOTIC tokens worth materially more than the USDC it receives, extracted from the solver's Uniswap V4 LP-funded inventory.
5. Attacker reverses/unwinds the pool swap, realizing profit while the solver realizes a loss.

Note: I was unable to fully trace the exact numeric mechanics of `computeLegPolicyOutput`'s size handling and the precise fill-execution contract path (`IntentGatewayV2`/`IntrinsicIntents`) beyond what is cited, due to index size limits on some files; a full Devin session could pull the complete `fx.ts` and `UniswapV4FundingPlanner.ts` source to confirm the exact numeric attack magnitude and any additional guards not surfaced in the indexed excerpts.

		cappedPairNotional: Decimal,

		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {

				// the venue-specific defense.

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
