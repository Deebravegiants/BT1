### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body, not the `shop`/`topic` headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` authenticates the body bytes only, using the app-wide `Context.api_secret_key` shared across every shop that has installed the app [2](#0-1) . `Registry.process` then dispatches to the handler using `request.topic` and `request.shop`, which come straight from the `x-shopify-topic`/`shopify-topic` and `x-shopify-shop-domain`/`shopify-shop-domain` headers with no cryptographic binding to the signed body at all [3](#0-2) [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac(body, secret) valid` ⇒ `(topic, shop, body)` all genuinely originated together from Shopify for that shop. In this gem, the equality actually enforced is only `hmac(body, secret) == received_hmac`; the `topic` and `shop` fields are never part of `to_signable_string` and are therefore unauthenticated. Because `api_secret_key` is the single app-wide client secret shared by all merchant installations (not a per-shop secret), any merchant who has legitimately installed the app can obtain a validly-signed `(body, hmac)` pair for real webhook traffic on their own store (e.g. by triggering an `orders/create` or `carts/update` event). That attacker-controlled body/HMAC pair remains cryptographically valid no matter what `shopify-shop-domain` or `shopify-topic` header values accompany it, since those headers are excluded from the signed content [5](#0-4) . The attacker can therefore POST that same body+HMAC to the app's public webhook endpoint while swapping in a victim's `shop-domain` (and/or a different `topic`), and `Registry.process` will accept it as an authentic webhook "from Shopify" for the victim shop [6](#0-5) . The `WebhookMetadata.shop` field handed to the handler is explicitly documented as "The shop domain of the webhook" and is the tenant key apps use to route/attribute the event [7](#0-6) , so this breaks the tenant-isolation equality `shop_authenticated == shop_acted_on`.

### Impact Explanation
This crosses a tenant boundary using only a legitimate-but-unprivileged install of the app on the attacker's own store — no access token, refresh token, or `client_secret` of the victim is required. Depending on how the host app uses `data.shop` (e.g. looking up the victim's stored offline access token to perform work, marking data as belonging to the victim shop, or triggering `app/uninstalled`/`shop/redact` style side effects for a shop the attacker doesn't own), this can enable cross-tenant data corruption or actions being taken against a victim merchant's account under attacker control.

### Likelihood Explanation
Requires only: (1) attacker installs the app on their own Shopify store (a normal, unprivileged action), (2) attacker captures one legitimate webhook delivery (body + HMAC) for that store, and (3) attacker replays it to the app's public webhook URL with modified `shop-domain`/`topic` headers. No secrets need to be stolen because the HMAC never covers those headers in the first place.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed content actually verified — e.g. compare `request.shop` against the shop associated with a stored session before trusting it, or verify the shop domain is one for which the app has an active installation/session using a secondary authenticated lookup, rather than trusting the raw header value as ground truth for tenant identity.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com", app installed there
# Real Shopify delivers a webhook the attacker fully observes:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
# ^ attacker cannot compute this themselves, but Shopify computes and delivers it to them for their own shop

# Attacker replays the exact same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- not covered by hmac
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body,
# and the handler receives WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)
