### Title
RAY value overflow in `scaled_to_original` permanently freezes a market before the index cap can engage - (File: common/src/rates/scaling.rs)

### Summary
The borrow/supply index caps (`MAX_BORROW_INDEX_RAY`, `MAX_SUPPLY_INDEX_RAY`) were designed to bound index growth, but accrual computes `scaled_to_original(supplied, index)` = `supplied * index / RAY` before checking the cap. On a large market the `i128`/`I256`→`i128` result overflows and panics with `MathOverflow` while the index is still below its cap. Because every controller verb accrues indexes first, the market freezes permanently: no repay, withdraw, borrow, or liquidation can ever execute again.

### Finding Description
`scaled_to_original` (`common/src/rates/scaling.rs:14`) calls `Ray::mul` → `fp_core::mul_div_half_up`, which panics with `GenericError::MathOverflow` when `scaled * index / RAY` exceeds `i128::MAX` (`common/src/math/fp_core.rs:108-118`). The same panic occurs inside `update_supply_index` (`supplied.mul(old_index)`), noted in `certora/common/spec/rates_rules.rs:316-320`.

Crucially, `update_indexes` accrues interest by unscaling the stored totals *before* the index cap is evaluated, so `MAX_*_INDEX_RAY` never engages first. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`) proves this end-to-end: at ~98% utilization on the steep XLM rate curve, `try_update_indexes_for` fails with `MATH_OVERFLOW` while `last.borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `try_withdraw_raw` and `try_repay` fail identically. The test comment explicitly states the bound claimed in `docs/reference/formulas.md` is wrong — the intended protection does not work.

An unprivileged attacker can set up the preconditions alone: `supply` a large amount of a high-decimal asset (caps can be raised by governance, but even existing caps suffice on 18-decimal assets), then `borrow` to drive utilization into the steep rate segment via `controller.borrow`. From there, passive interest accrual — or any user's `update_indexes` call — pushes the `borrowed * borrow_index` product past `i128::MAX`, and the market is bricked for everyone.

### Impact Explanation
Permanent freezing of funds and a contract unable to operate: once the product `scaled_amount * index` exceeds `i128::MAX`, every entrypoint that touches the market (`supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `update_indexes`) reverts in the accrual step. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad debt cannot be cleaned. The entire physical pool balance attributable to that book is frozen forever with no recovery path short of a contract upgrade.

### Likelihood Explanation
The trigger requires a large market (the test uses ~10^27 base units of an 18-decimal asset) and sustained high utilization so the borrow index compounds. It needs no privileges, no oracle manipulation, and no cooperation — a single funded account can supply and borrow the market into the steep curve region, after which ordinary accrual does the rest. The cost is capital and time rather than technical difficulty; on a long-lived deployment the condition can also arise organically.

### Recommendation
Cap or saturate the index *before* unscaling totals in `update_supply_index`/borrow-index accrual, or compute accrued rewards via a saturating/`try_` path (e.g., `mul_div_floor_saturating` or `try_mul_div_half_up`) and clamp the index to `MAX_*_INDEX_RAY` when the unscaled value would overflow, so accrual degrades gracefully instead of panicking. Alternatively, enforce a supply cap in RAY terms (`require_cap_within_asset_domain`) chosen so `supplied * MAX_INDEX / RAY` provably fits `i128`, and verify with the long-horizon harness test that the cap engages before the value ceiling.

### Proof of Concept
Existing executable PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`.

1. Create market `BIG18` (18 decimals) with the XLM rate curve; lift caps.
2. `BOB.supply(BIG18, 1e9 * 10^18)`; `ALICE.supply(COL, ...)`; `ALICE.borrow(BIG18, ~98% of principal)`.
3. Advance time in yearly steps calling `update_indexes` — all unprivileged calls.
4. After the index crosses ~170x, `update_indexes` panics `MathOverflow` inside `scaled_to_original`/`update_supply_index` with `borrow_index < MAX_BORROW_INDEX_RAY`.
5. `withdraw(1)` and `repay(1)` both revert with `MathOverflow` — the market is permanently frozen.

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // MathOverflow
}
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause: `common/src/rates/scaling.rs:14` `scaled.mul(env, index)` → `common/src/math/fp_core.rs:108` panics when `supplied * index / RAY` exceeds `i128::MAX`, and the cap in `common/src/rates/index.rs` is only applied to the index value itself, not the product, so it engages too late.
