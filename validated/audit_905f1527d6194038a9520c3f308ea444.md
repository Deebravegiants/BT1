### Title
Stale `deviceAuthTrigger`/`bioAuthTrigger` secrets from mode switching allow weaker `ACCESS_CONTROL_USER_PRESENCE` trigger to satisfy biometric-only auth - ([File: features/auth-mobile/module/auth.js])

### Summary
`Auth#enableBioAuth` calls `#setBioAuth(true, { useDeviceAuth })`, which only ever writes the keystore secrets for the *requested* mode (device-auth-with-fallback vs. pure biometric) and never deletes the secrets belonging to the *other*, previously-enabled mode. As a result, calling `enableBioAuth({fallbackToDevicePin:true})` followed by `enableBioAuth({fallbackToDevicePin:false})` leaves the stale `AUTH_KEYSTORE_DEVICE_AUTH_KEY`/`AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` secrets in place alongside the newly written `AUTH_KEYSTORE_BIO_AUTH_KEY`/`AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` secrets.

### Finding Description
`#setBioAuth` in [1](#0-0)  only performs cleanup of all four keys (`deleteSecret` for device+bio key/trigger) in the `!on` (disable) branch. When `on` is true, it branches on `useDeviceAuth` and writes only the two keys relevant to that branch — it never deletes the two keys belonging to the opposite branch.

`enableBioAuth` at [2](#0-1)  passes `fallbackToDevicePin` straight through as `useDeviceAuth` to `#setBioAuth` with no check of the prior mode and no call to `disableBioAuth`/cleanup first.

Given the sequence:
1. `enableBioAuth({ fallbackToDevicePin: true })` → writes `AUTH_KEYSTORE_DEVICE_AUTH_KEY` and `AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` with `accessControl: ACCESS_CONTROL_USER_PRESENCE` (see [3](#0-2) ), and merges `{ hasDeviceAuth: true }` into the atom.
2. `enableBioAuth({ fallbackToDevicePin: false })` → writes `AUTH_KEYSTORE_BIO_AUTH_KEY`/`AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` with `accessControl: ACCESS_CONTROL_BIOMETRY_CURRENT_SET` ( [4](#0-3) ), and merges `{ hasBioAuth: true }`. Because `#mergeIntoAtom` spreads `{...current, ...params}` ( [5](#0-4) ), the previously-set `hasDeviceAuth: true` is never cleared — it is only overwritten by explicit new params.

After this sequence, both `AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` (weak, `ACCESS_CONTROL_USER_PRESENCE`) and `AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` (strong, `ACCESS_CONTROL_BIOMETRY_CURRENT_SET`) exist simultaneously in the keystore. `getBioAuthTrigger` checks the device-auth trigger first and returns it if present, unconditionally preferring it over the biometric trigger: [6](#0-5) . Any caller that gates a "biometric-only" action on this trigger therefore actually authorizes via the weaker device-passcode-fallback secret, regardless of the caller's intent expressed through `fallbackToDevicePin: false`.

### Impact Explanation
Consent/authorization is bound to the wrong (weaker) auth mechanism than what the wallet/atom state and caller intent indicate. Wallet actions or approval flows that assume "biometric-only" protection (biometry only, no device-passcode fallback) can instead be satisfied by a device passcode, because `getBioAuthTrigger` returns the stale `ACCESS_CONTROL_USER_PRESENCE`-protected trigger. This is a privilege/auth-scope confusion issue: an authorization gate believed to require biometrics can be passed with a weaker factor, undermining the security guarantee the UI/atom claims to provide.

### Likelihood Explanation
This requires no privileged state or leaked keys — it is triggered purely by an ordinary sequence of two dapp/app-initiated calls to `enableBioAuth` with different `fallbackToDevicePin` values without an intervening `disableBioAuth`. This is a plausible legitimate user flow (e.g., a user first enables biometrics with passcode fallback, then later switches to "biometric only" via settings), and nothing in the code path prevents or warns against it, making it fully reproducible.

### Recommendation
In `#setBioAuth`, before writing the keys for the requested mode, delete the secrets belonging to the opposite mode (i.e., always clear both `AUTH_KEYSTORE_DEVICE_AUTH_KEY`/`AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` and `AUTH_KEYSTORE_BIO_AUTH_KEY`/`AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` prior to setting the new mode's pair), and ensure `#mergeIntoAtom` explicitly sets the opposite flag (`hasDeviceAuth`/`hasBioAuth`) to `false` when switching modes so atom state and keystore state stay consistent.

### Proof of Concept
Unit test (extending `features/auth-mobile/module/__tests__/auth.test.js`):
```js
await auth.enableBioAuth({ fallbackToDevicePin: true })
await auth.enableBioAuth({ fallbackToDevicePin: false })

// Assert stale device-auth secrets were deleted
expect(await keystore.getSecret('auth:deviceAuth')).toBeFalsy()
expect(await keystore.getSecret('auth:deviceAuthTrigger')).toBeFalsy()

// Assert only the strong biometric trigger remains and is returned
const trigger = await auth.getBioAuthTrigger()
expect(trigger).toBe(true) // should come from bioAuthTrigger, not deviceAuthTrigger
```
Currently this test fails because `auth:deviceAuthTrigger` remains set and `getBioAuthTrigger` returns it (the weaker `ACCESS_CONTROL_USER_PRESENCE`-protected secret) instead of the intended pure-biometric trigger.

  #setBioAuth = async (on, { useDeviceAuth } = {}) => {
    if (!on) {
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY))
      return
    }

    const keyOpts = {
      accessible: ACCESSIBLE_WHEN_UNLOCKED_THIS_DEVICE_ONLY,
    }

    if (useDeviceAuth) {
      // Android and iOS handle `ACCESS_CONTROL_USER_PRESENCE` differently when device auth
      // is not enabled. This check ensures consistent behavior across platforms.
      const canAuth = await this.canUseDeviceAuth()
      if (!canAuth) {
        throw new DeviceAuthenticationUnavailableError()
      }

      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_KEY), on, keyOpts)
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY), on, {
        ...keyOpts,
        accessControl: ACCESS_CONTROL_USER_PRESENCE, // This flag allows iOS to fallback to device pin.
      })
    } else {
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_KEY), on, keyOpts)
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY), on, {
        ...keyOpts,
        accessControl: ACCESS_CONTROL_BIOMETRY_CURRENT_SET,
      })
    }
  }

  #mergeIntoAtom = async (params) => {
    await this.#authAtom.set((current) => {
      const data = {
        ...current,
        ...params,
      }

      const { hasBioAuth, biometry, hasPin, hasDeviceAuth } = data

      data.hasBioAuth = hasBioAuth && !!biometry
      data.shouldAuthenticate = hasDeviceAuth || hasBioAuth || hasPin

      if (isEqual(current, data)) return current

      this.#logger.info('Updated auth data', data)
      return data
    })
  }
