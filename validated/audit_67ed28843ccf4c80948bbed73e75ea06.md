Found it: `Oauth.begin_auth` (`lib/shopify_api/auth/oauth.rb`) builds the OAuth authorization redirect URL and the `auth_base_uri` used to fetch the access token directly from the caller-supplied `shop:` parameter, with **no** call to `Utils::ShopValidator.sanitize!`. That validator exists precisely to bind a `shop` string to a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `spin.dev`, etc.) and is used elsewhere (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, `Clients::Graphql::Storefront#initialize`), but `Oauth.begin_auth`/`auth_base_uri` skip it entirely.

### Title
OAuth `begin_auth` builds the authorization/token-exchange host from an unsanitized `shop` parameter - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a `shop:` string and uses it, unsanitized, to build `auth_base_uri(shop)` [1](#0-0) , which is concatenated into the `/oauth/authorize` URL the user's browser is redirected to [2](#0-1) . Every other place in the gem that turns a caller-supplied `shop` string into a request host runs it through `Utils::ShopValidator.sanitize!`, which enforces the value resolves to a host under `TRUSTED_SHOPIFY_DOMAINS` [3](#0-2) [4](#0-3) [5](#0-4) . `begin_auth` has no equivalent check.

### Finding Description
This is an identity-binding break analogous to the bus-ID collision: the "host validated" side and "host that receives the app's credentials" side are supposed to be the same trusted Shopify domain, but here the value is never validated at all before being used as the host. If a host application passes through an attacker-influenced `shop` value (e.g. from a query string on an install/login route, which is common practice for multi-tenant Shopify apps, since `shop` is normally taken directly from the install URL) to `Oauth.begin_auth`, the gem will happily build `https://<attacker-controlled-value>/admin/oauth/authorize?...&client_id=...` and hand that URL back to the caller for redirection. This breaks the equality: `host receiving client_id/redirect_uri == trusted myshopify host`, because the gem itself performs no sanitization — unlike the `TokenExchange`/`ClientCredentials` paths which explicitly call `ShopValidator.sanitize!` before constructing the request host.

### Impact Explanation
The consequence is that the app's `client_id` and the OAuth `redirect_uri` (which will subsequently receive the authorization `code`) get sent to a host chosen entirely by the caller-supplied string, with no confirmation it is a genuine Shopify domain. Since the authorization `code` returned to `redirect_uri` can be exchanged for a merchant access token, an attacker who can influence the `shop` parameter reaching `begin_auth` can redirect the OAuth authorize request to an attacker-controlled host, potentially intercepting the flow or forcing OAuth completion against an unintended tenant — matching the High-severity class "SSRF with the app's credentials / forced OAuth completion."

### Likelihood Explanation
The `shop` value passed into `begin_auth` is entirely under the control of whatever the host application passes in; the gem provides no defense-in-depth here despite doing so consistently elsewhere (`ShopValidator.sanitize!` in `TokenExchange`, `ClientCredentials`, `Storefront`). Since `shop` is a value that Shopify apps conventionally read from the incoming request during install/login, the missing validation removes a safety net that this library otherwise treats as mandatory, making this a realistic gap rather than a purely theoretical one.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` (and use the sanitized value in `auth_base_uri`), mirroring the pattern already used in `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`, so the authorize-redirect host is bound to the same trust check as every other outbound-credential-bearing request in the gem.

### Proof of Concept
1. Host application exposes `/login?shop=<value>` and forwards `shop` unchanged into `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")`.
2. Attacker requests `/login?shop=evil.example.com`.
3. `begin_auth` calls `auth_base_uri("evil.example.com")`, which returns `"https://evil.example.com/admin"` unchanged (no domain check) [6](#0-5) .
4. The generated `auth_route` (`https://evil.example.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=...`) is returned to the caller and used as the redirect target, sending the app's `client_id` and intended `redirect_uri` to a non-Shopify host, and setting up a forced/attacker-influenced OAuth completion.

```ruby
        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
