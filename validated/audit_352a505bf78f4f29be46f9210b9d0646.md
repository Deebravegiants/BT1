### Title
Dangling ERC20 approvals set via `EmporiumUpgradeable.runAction` CASE 2 calls can be drained by any attacker who omits the token from their own `erc20TokenAddresses` list - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` never revokes ERC20 approvals granted through arbitrary CASE 2 `endpoint.call{value: op.value}(op.callData)` invocations, and both `EmporiumUpgradeable.runAction`'s and `Hinkal.transact`'s post-execution balance invariants are scoped only to the token list (`circomData.erc20TokenAddresses`) that the *current* caller chooses to submit. An attacker can therefore invoke a router/token endpoint that pulls tokens from Emporium via a stale `approve` left by an earlier `transact` (their own or a victim's), while simply excluding that drained token from their own `erc20TokenAddresses` array so no balance-diff check ever fires for it, and include only the output token to legitimately mint themselves a UTXO for the proceeds.

### Finding Description
The claimed equality is: `net tokens entering the swap == deltaAmountChanges the attacker's own transact call debited for that token`. This equality is enforced twice in the codebase, but both enforcement points are scoped by the caller-supplied `erc20TokenAddresses` array, not by all balances Emporium actually holds:

1. In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed only `for circomData.erc20TokenAddresses` [1](#0-0) , and the ops loop executes arbitrary CASE 2 calls without restriction on which token/router is touched [2](#0-1) . The final reconciliation loop that reverts on unexplained balance loss (`BalanceChangeShouldBePositive`) only iterates `circomData.erc20TokenAddresses.length` [3](#0-2) . Any token not included in that array is never checked, even though it is a token Emporium actually holds.

2. In `Hinkal.transact`, the top-level `balanceDif == amountChanges + utxoAmount` check is likewise scoped only to `circomData.erc20TokenAddresses` chosen freely by the caller [4](#0-3) . `dimensionsCheck` in `HinkalHelper.sol` only validates internal length consistency between arrays, not that the token list exhaustively covers every token balance Emporium holds [5](#0-4) .

3. Approvals granted via CASE 2 (`op.endpoint.call{value: op.value}(op.callData)`, e.g. calling `token.approve(router, amount)` or a router function that internally sets an allowance) are raw, persistent ERC20 storage on the token contract keyed by `(owner=Emporium, spender=router)`. `EmporiumUpgradeable` has no mechanism that resets approvals created this way — `unsafeApproveERC20Token`/`approveToken` in `Transferer.sol` are only invoked by contract-managed helpers (e.g. `Hinkal.sol`'s `HinkalWrapper` deposit flow), never by `runAction`'s generic op dispatch [6](#0-5) . If a prior `transact` (victim's or the attacker's own earlier call) approved a router for more than the router ultimately pulled in that same call (e.g. approve-then-swap patterns, or infinite/rounded approvals - the codebase's own `approveUnlimited` in `TransfererBase.sol` demonstrates this exact leftover-allowance pattern used elsewhere in the code, at `contracts/external-actions/swaps/LifiExternalAction.sol:30`), a nonzero allowance from Emporium to that router remains after the transaction ends.

Attacker's exploit call: submit a new `transact` where `circomData.externalActionData.externalActionId` routes to Emporium, `stack.ops` contains a single CASE 2 op whose `endpoint`/`callData` invokes the router function that performs `token.transferFrom(Emporium, router, amount)` using the dangling allowance (no approve op is needed since the allowance already exists), and where the attacker's own `circomData.erc20TokenAddresses` array/`deltaAmountChanges` omits the drained input token entirely and includes only the output token the router sends back to Emporium. Because the drained token is absent from the array used in both balance-diff checks (`EmporiumUpgradeable.runAction` lines 132-151 and `Hinkal.transact` lines 78-147), its balance decrease is invisible to every enforced equality. The output token's balance increase, however, is captured normally by `handleOut`, minted into a UTXO, and paid out to the attacker via `msg.sender` in `handleOut` [7](#0-6) .

### Impact Explanation
This is theft of another user's (or the attacker's own previously "wasted" allowance) shielded funds held on Emporium: tokens that legitimately belong to whichever UTXO owner funded the earlier approval flow are pulled out and converted into a UTXO credited to the attacker, with zero debit recorded against the attacker in any accounting path. This is a direct theft of shielded/in-flight user funds via a balance/proof-invariant bypass and qualifies as **Critical**. The attack is repeatable any time a dangling approval exists (e.g., through repeated use of routers with approve-then-swap patterns), and each stale allowance can be drained fully in one transaction.

### Likelihood Explanation
Preconditions: (1) Emporium must hold a nonzero ERC20 balance of the target token (achieved by any user's deposit/UTXO flow through Emporium), and (2) a nonzero residual `allowance(Emporium, router)` must exist from a prior CASE 2 op that approved more than was ultimately consumed. Precondition (2) is plausible but not guaranteed by every integration — it depends on the specific router's pull behavior (exact-input vs. approve-more-than-used patterns), so this is a conditional rather than universally-triggerable bug. The attacker's cost is a single `transact` call with a locally generated proof (no privileged role or victim key required — attacker only needs their own valid CircomData/proof and control of `erc20TokenAddresses`/`stack.ops`), making it cheap and fully repeatable whenever the precondition holds.

### Recommendation
Do not scope the post-execution balance reconciliation to only the caller-chosen `erc20TokenAddresses`. Either (a) require `EmporiumUpgradeable.runAction`/`Hinkal.transact` to snapshot and verify balances for every token any op in `stack.ops` could plausibly touch (e.g. by requiring the token list to include all `approve`/router-target tokens used in the ops), or (b) have `EmporiumUpgradeable` explicitly zero out any approval it granted via CASE 2 ops at the end of `runAction` (mirroring `unsafeApproveERC20Token`'s "approve 0 then approve amount" pattern) so no allowance can survive past a single `transact` call, eliminating cross-transaction dangling-allowance exploitation.

### Proof of Concept
1. Deploy a mock ERC20 and a mock router with a function `pull(uint256 amount)` that calls `token.transferFrom(msg.sender, address(this), amount)` and sends an output token back to `msg.sender`.
2. Fund `EmporiumUpgradeable` with the input token (simulate a prior legitimate deposit/UTXO).
3. Simulate the "victim" transact: craft a `stack.ops` with a CASE 2 op that calls `token.approve(router, X)` where `X` exceeds what any subsequent swap in that same call consumes (or simply leave the approval standalone with no consuming swap op to model the dangling-allowance precondition), then run `runAction`/`transact` successfully. Assert `token.allowance(Emporium, router) == X > 0` after the call returns.
4. As the attacker, craft a new `transact` call whose `circomData.erc20TokenAddresses` excludes the input token entirely and includes only the output token; `stack.ops` contains a single CASE 2 op calling `router.pull(X)`.
5. Assert: (a) the call succeeds without reverting on `BalanceChangeShouldBePositive` or the `Hinkal.sol` balance-diff `require`; (b) `token.balanceOf(Emporium)` decreased by `X` with no corresponding entry in attacker's `deltaAmountChanges`/`amountChanges` for that token; (c) the attacker receives a new UTXO/on-chain commitment for the output token funded entirely by the drained input token, with the attacker having deposited/debited nothing for it in this call.
