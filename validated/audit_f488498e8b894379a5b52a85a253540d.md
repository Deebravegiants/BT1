### Title
Webhook shop/topic/webhook-id/api-version identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body [1](#0-0) , using `Request#to_signable_string`, which returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` fields that get forwarded to the app's handler as trusted identity/routing data are all read straight from HTTP headers and are never included in the HMAC-signed material [3](#0-2) .

### Finding Description
The equality that this gem's webhook authentication is supposed to guarantee is:
`bytes verified by HMAC == bytes the app relies on to attribute the webhook to a shop/topic`

In `ShopifyAPI::Webhooks::Request`, `hmac` is computed over the `hmac-sha256` header value and checked against a signature computed from `to_signable_string`, which is defined as just `@raw_body` [4](#0-3) [2](#0-1) . `shop`, `topic`, `webhook_id`, and `api_version`, however, are pulled from `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers via `shopify_header` [3](#0-2) [5](#0-4) , none of which are part of the signed payload.

`Registry.process` validates only the HMAC and then dispatches to the app-registered handler with a `WebhookMetadata` struct built directly from these unauthenticated header values plus the parsed body: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` [1](#0-0) . The `WebhookMetadata#shop` field is a plain, unauthenticated `String` const with no further verification [6](#0-5) .

Because the app's shared `client_secret` is the same for every shop that installs the app, any developer can install the public app on a shop they control, receive a genuinely Shopify-signed webhook (valid `hmac-sha256` over a real body), and then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with an arbitrary victim shop's domain or a different topic. Since the HMAC only binds the body bytes and never the shop/topic headers, the forged request passes `HmacValidator.validate` unchanged, and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop/topic. This breaks the identity binding `shop authenticated == shop the handler trusts as the event source`.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem allows an unprivileged attacker (who only needs to install the app on their own shop — no special privileges, no leaked secrets) to make the host application process arbitrary genuinely-signed webhook bodies while attributing them to a different, victim shop. Any host application that uses `shop` from `WebhookMetadata` to look up/act on a specific merchant's records (a documented, expected usage pattern of this gem) can be tricked into applying another shop's data or a mismatched topic/handler logic against the victim shop's context, leading to cross-tenant data corruption/exposure — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for apps that are publicly installable: any developer can install the target app on their own store, capture one legitimately signed webhook (using tools freely available to any merchant, e.g. request logging on their own endpoint or a debugging proxy), and replay the unchanged body+HMAC with modified `shop-domain`/`topic` headers to the target endpoint. No secret material or privileged account is needed — the entire attack surface is the unauthenticated header set that this gem passes through unchecked into `WebhookMetadata`.

### Recommendation
Extend `Request#to_signable_string` (or add a companion verification step in `Registry.process`) so that the HMAC-signed material — or an equivalent authenticated binding — covers the shop domain, topic, and webhook id, not just the raw body. At minimum, `Registry.process` should cross check that `request.shop` corresponds to a shop with an active session/installation known to the host app before constructing `WebhookMetadata`, and document that host applications must not trust `shop`/`topic` header-derived values as authenticated without additional verification against their own session store.

### Proof of Concept
1. Attacker installs the target (public) Shopify app on `attacker-shop.myshopify.com`, using the app's real `client_secret` (shared across all installs).
2. Shopify sends a legitimately signed webhook to the attacker's endpoint, e.g. headers `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid signature over raw_body>`, with some `raw_body`.
3. Attacker captures `raw_body` and the valid `hmac-sha256` value.
4. Attacker replays a POST to the target app's webhook endpoint with the identical `raw_body` and `hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally changes `x-shopify-topic`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `@raw_body` [7](#0-6)  — validation succeeds because the body wasn't altered.
6. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` [8](#0-7)  and handed to the app's registered handler, which processes attacker-controlled body data as if it were an authentic event from the victim shop.
