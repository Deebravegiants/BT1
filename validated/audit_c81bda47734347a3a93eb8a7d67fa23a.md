### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing shop-domain spoofing on otherwise-authentic webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands the header-derived `shop` straight to the app's handler as the tenant identifier, breaking the binding `shop authenticated == shop the handler acts on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC, so it validates the body's authenticity but says nothing about which shop or topic the caller claims the body came from: [3](#0-2) 

`Registry.process` uses the validated-body request but forwards the *unauthenticated* `request.shop` to the handler as the tenant identity for that webhook payload: [4](#0-3) 

Because `shop-domain` (and `topic`/`webhook-id`) are excluded from the signed material, any party who has ever received one authentic webhook body+HMAC pair from Shopify (e.g., for their own shop) can resend that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it only re-derives the HMAC over the raw body, and the forged `shop` value is passed on to `WebhookMetadata`/the handler unchecked.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select which merchant's session/data to update (the intended and documented use of that field), an attacker can attribute a genuine, HMAC-valid webhook body to a victim shop of their choosing. Depending on the handler logic this enables cross-tenant data confusion/corruption — e.g., causing another merchant's records to be updated, deleted, or app-state to be desynced based on attacker-controlled body content attributed to that merchant. This matches the "cross-tenant access" impact category since the shop-authentication boundary that the HMAC is supposed to enforce does not actually cover the shop claim.

### Likelihood Explanation
Exploitation only requires that the attacker (as a genuine, unprivileged Shopify merchant/app installer) can trigger a webhook for their own shop and capture the raw body + `X-Shopify-Hmac-Sha256` header — something any app installer can do without any special privilege, since webhook bodies are frequently generic (e.g., empty `{}` payloads for certain topics, or bodies with attacker-controlled/predictable content depending on topic) and the HMAC only binds the body, not the sender. No credentials, tokens, or `client_secret` access are required — this is a pure header-vs-signed-bytes mismatch.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signable string, or otherwise cryptographically bind them to the signature (for example, by having `to_signable_string` concatenate the relevant headers with the body before hashing), so that a signature computed for one shop/topic cannot be replayed with a different `shop-domain` header and still validate.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook whose body is fixed/predictable (e.g., an empty JSON body `{}` for some topic, as used in the gem's own tests) — see `test/webhooks/registry_test.rb` lines 284-299, where the HMAC is computed purely over `"{}"`: [5](#0-4) 
2. Attacker captures the genuine `X-Shopify-Hmac-Sha256` header Shopify sent for that delivery.
3. Attacker replays the same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the body only) and succeeds because the body is unchanged: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the payload never having been signed for or sent about that shop, breaking the intended `shop` identity binding.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
