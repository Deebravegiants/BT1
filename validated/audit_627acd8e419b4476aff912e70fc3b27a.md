### Title
Governance-triggered `protocolFeeBps` update can front-run a user's `placeOrder()`, silently reducing the escrowed amount below what the user quoted - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` deducts a protocol fee from the user's escrowed input using whatever `protocolFeeBps` (or destination-specific override) happens to be stored in contract state at the moment the transaction executes, not the value the user observed when they built and signed the order off-chain (e.g. via the SDK's `quoteIntent()`/`readProtocolFeeBps()` helpers). If Hyperbridge governance's `UpdateParams` message lands in an earlier block/position than the user's `placeOrder()` transaction, the fee actually applied can be higher than the one the user was quoted, exactly mirroring the reported `AlloSettings`/`setReadyForPayout()` pattern where a fee-percentage update front-runs a transaction that implicitly depends on the "current" fee.

### Finding Description
`placeOrder()` reads the live fee rate and immediately bakes it into both the escrow amount and the order commitment hash: [1](#0-0) 

```
bytes32 destinationHash = keccak256(order.destination);
uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
if (protocolFeeBps == 0) {
    protocolFeeBps = _params.protocolFeeBps;
}
...
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
...
commitment = keccak256(abi.encode(order));
```

`protocolFeeBps` (and per-destination overrides in `_destinationProtocolFees`) are governance-controlled values that can be changed at any time via a cross-chain `UpdateParams` message processed in `_updateParams()`: [2](#0-1) 

There is no minimum/maximum staleness window, no timelock, and no snapshot of the fee at quote time — the value used is whatever is in storage the instant `placeOrder()` executes. Off-chain, the SDK explicitly reads this same live value to build quotes: [3](#0-2) 

Because the commitment is computed over the fee-*reduced* inputs, and solvers/relayers only ever see the on-chain result, a user has no way to guarantee their `placeOrder()` executes against the fee they quoted: any `UpdateParams` transaction (or the destination-fee variant) that is included before the user's transaction changes the effective fee for that call, exactly as `updateProtocolFeePercentage()` could unexpectedly change the fee that `setReadyForPayout()` applies in the original Gitcoin report.

### Impact Explanation
A user who computed and approved an input amount based on a quoted `protocolFeeBps` can have their order placed with a materially higher fee than expected if governance's fee update lands first. The impact is a permanent, protocol-level reduction of escrowed input relative to the user's expectation — the difference is retained by the protocol as "dust" (per `docs/content/developers/evm/intent-gateway/placing-orders.mdx`, the fee is not refundable on cancellation). Because `reducedInputs` is what's actually escrowed and hashed into `commitment`, the user's order may also end up materially smaller than intended relative to the requested output, degrading its attractiveness to solvers or leaving the user under-collateralized for an intended swap ratio. This is a direct loss-of-funds/economic-manipulation vector matching Medium severity of the original finding.

### Likelihood Explanation
Likelihood is moderate: it requires a `UpdateParams`/destination-fee governance message to be in flight (or intentionally submitted) around the same time users are placing orders. Fee changes are expected periodic governance operations (documented default is 5 bps, subject to change), and Hyperbridge relayers/dispatchers control message ordering into the destination chain, making intentional or coincidental front-running plausible without any special access beyond normal governance cadence — no malicious actor is required, mirroring the "unintentional front-run" framing of the original report.

### Recommendation
- Snapshot the effective `protocolFeeBps` at order-creation intent time (e.g. include an explicit `maxProtocolFeeBps` field in `Order` that the user signs, and have `placeOrder()` revert if the live fee exceeds it), so a user's expected fee ceiling is enforced on-chain rather than implicitly assumed.
- Alternatively, apply a timelock/delay to `UpdateParams` fee changes (and destination-fee overrides) so that in-flight orders built against the previous rate cannot be silently affected.
- Emit fee-effective-block metadata so off-chain quoting tools can detect staleness and re-quote before submission.

### Proof of Concept
1. Governance registers `_params.protocolFeeBps = 5` (0.05%) as documented in `docs/content/developers/evm/intent-gateway/placing-orders.mdx`.
2. A user calls the SDK's `readProtocolFeeBps()`/`quoteIntent()` off-chain, gets `protocolFeeBps = 5`, computes `reducedAmount = amount - amount*5/10000`, signs and submits `placeOrder(order, graffiti)`.
3. Before the user's transaction is included, a relayer delivers a pending `UpdateParams` message that governance had already queued, setting `_params.protocolFeeBps = 200` (2%) via `IntentsBase._updateParams()` [4](#0-3) .
4. The user's `placeOrder()` executes afterward, reading `protocolFeeBps = 200` from storage inside `placeOrder()` [5](#0-4) , deducting a 2% fee instead of the quoted 0.05% and escrowing a smaller `reducedAmount` than the user expected and approved for.
5. The user's order commitment is computed over this smaller, unexpected `reducedInputs`, and the extra fee is retained by the protocol as unrefundable dust — the user has no recourse even via `cancelOrder()`, which returns only the escrow and `order.fees`, not the protocol fee, per `docs/content/developers/evm/intent-gateway/placing-orders.mdx` line 111.

        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});

        for (uint256 i; i < update.destinationFees.length;) {

            if (feeBps >= 10_000) revert InvalidInput();

export async function readProtocolFeeBps(
	chainConfigService: ChainConfigService,
	source: IntentQuoteChainContext,
): Promise<bigint> {
	const gatewayAddress = chainConfigService.getIntentGatewayAddress(source.stateMachineId)
	if (!gatewayAddress || gatewayAddress === "0x" || gatewayAddress === zeroAddress) {
		throw new Error(`IntentGatewayV2 is not configured for chain ${source.stateMachineId}`)
	}

	const gatewayParams = (await source.client.readContract({
		address: gatewayAddress,
		abi: IntentGatewayV2.ABI,
		functionName: "params",
	})) as GatewayParams

	const protocolFeeBps = Array.isArray(gatewayParams)
		? BigInt(gatewayParams[4] as bigint | number | string)
		: BigInt((gatewayParams as GatewayParamsObject).protocolFeeBps ?? 0)
	if (protocolFeeBps < 0n || protocolFeeBps >= BPS_DENOMINATOR) {
		throw new Error(`Invalid IntentGateway protocol fee: ${protocolFeeBps} bps`)
	}
	return protocolFeeBps
}
