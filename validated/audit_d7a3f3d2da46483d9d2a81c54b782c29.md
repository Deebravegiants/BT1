This confirms the vulnerability. The `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` returns only `@raw_body`, and the `shop`, `topic`, `webhook_id`, `api_version` accessors read directly from unauthenticated HTTP headers, none of which are part of the HMAC-signed payload. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` validates the HMAC over the body only, then passes `request.shop` (the unsigned header) straight into `WebhookMetadata` for the handler to trust as the tenant identifier.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop` (tenant identifier) delivered to the host application's webhook handler is read from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC computation.

### Finding Description
`Registry.process` authenticates a webhook by calling `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares the HMAC over that value only: [1](#0-0) [1](#0-0) 

```
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are not part of that signed string: [2](#0-1) 

After validation succeeds, `Registry.process` forwards the unauthenticated `request.shop` value straight to the application's webhook handler as the tenant identity: [3](#0-2) 

Because the app's `client_secret` (used to compute the HMAC) is a single value shared across every shop that installs the app, the HMAC for a given raw body is identical regardless of which shop it originates from. This breaks the intended binding "the shop whose HMAC-signed webhook body was verified == `request.shop` reported to the handler". A user who legitimately controls one installation of the app (Shop A) can:
1. Capture a genuine webhook delivery for Shop A — this includes a raw body and a valid `X-Shopify-Hmac-Sha256` value signed by Shopify with the app's shared secret.
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` with Shop B's (victim's) domain.
3. `HmacValidator.validate` passes because it only checks the raw body against the secret — it never checks that the signature is bound to the claimed shop.
4. The handler receives `WebhookMetadata` claiming the event is for Shop B, even though Shop B never sent it.

This is exactly the "field acted on but not covered by the HMAC" class of bug: `shop` is acted upon (used to attribute/route the event to a tenant) but not cryptographically bound to the signature that authorizes the request.

### Impact Explanation
Any application built on this gem that uses `request.shop` / `WebhookMetadata#shop` to determine which merchant/tenant a webhook event belongs to (the standard, documented usage) can be tricked into processing data under the wrong tenant's identity. An attacker who is a legitimate merchant of the app (an unprivileged, ordinary internet user with respect to other tenants) can inject spoofed events attributed to any other shop, without ever needing that shop's or the app's `client_secret`. This is cross-tenant access/injection — one of the explicitly allowed Critical impacts.

### Likelihood Explanation
The attacker needs no special access beyond installing the app on their own store (a normal, unprivileged action) and capturing/replaying one webhook delivery they legitimately receive. No secrets, tokens, or elevated privileges are required, and predictable/near-static bodies (e.g. mandatory `shop/redact`, `customers/redact` payload shapes, or simply reusing the exact same body) make the replay trivial. This is a straightforward binding gap in the gem's own signature-verification logic, not a misuse of a documented API by the host app.

### Recommendation
Bind the claimed `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or have `Registry.process` cross-check the shop attributed to the request against an authenticated source (e.g., an active session/installation record for that shop) before dispatching to the handler. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted as a tenant boundary by host applications, and consider updating `to_signable_string`/`HmacValidator` to be tenant-aware.
