Found a solid analog. The `convert_to_balance` helper in the `hyper-fungible-token` pallet has the exact same decimal-precision defect pattern as the `WIchiFarm.burn` bug: it silently drops the scale-up case when the ERC20 side has fewer decimals than the local asset, causing severe under-crediting of minted/released tokens on `on_accept`. ### Title
Incoming `HyperFungibleToken` transfers under-credit recipients when the ERC20 side has fewer decimals than the local asset - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` converts an incoming ERC20 `U256` amount to the pallet's local balance type by dividing by `10^(erc_decimals.saturating_sub(local_decimals))`. This only handles the case where the remote EVM token has *more* decimals than the local asset. When the remote token has *fewer* decimals than the local asset (e.g. a 6-decimal ERC20 bridging into an 18-decimal local asset), `saturating_sub` clamps the exponent to `0`, so the raw ERC20 amount is credited to the beneficiary unscaled — off by `10^(local_decimals - erc_decimals)`.

### Finding Description
`convert_to_balance` is documented as "Divides by `10^(erc_decimals - local_decimals)` to scale down from ERC20 precision" [2](#0-1) , but it assumes `erc_decimals >= local_decimals` unconditionally. `erc_decimals.saturating_sub(local_decimals)` silently returns `0` whenever `local_decimals > erc_decimals`, turning the intended "scale-up" division into a no-op instead of the correct multiplication.

This is used on the receiving side of a cross-chain transfer, `on_accept`, per the pallet README: "`on_accept` — receives `Send` messages from the paired EVM contract... scales the amount using `Precisions`, then mints (non-native) or releases from escrow (native) to the beneficiary" [3](#0-2) . The `Precisions` storage records "the EVM-side decimals so amounts get scaled at the boundary" [4](#0-3) , per-pair, meaning arbitrary decimal combinations across chains are an explicitly supported configuration — not an edge case.

Contrast this with the reverse function `convert_to_erc20`, used in `send()`, which correctly multiplies to scale *up* from local to ERC20 precision using the same unguarded `saturating_sub` pattern, but in the opposite (safe) direction since sends only go from lower/local to higher/ERC20 precision in the typical case documented (EVM is "typically 18" [5](#0-4) ). The asymmetry is exactly the class of bug in the reported `WIchiFarm.burn` H-1: a decimal-precision assumption baked into a fixed-direction formula, silently wrong whenever the actual token decimals violate that assumption — resulting in far too few tokens transferred to the user.

### Impact Explanation
Any registered non-native asset pair where the local substrate asset has more decimals than its EVM/erc20 counterpart (e.g. local 18-decimal asset, remote 6-decimal stablecoin representation — an entirely plausible and supported configuration per `ChainConfig.decimals`) will have every inbound cross-chain transfer, refund, and mint under-credited by a factor of `10^(local_decimals - erc_decimals)`. Since decimals are governance-configured per `(asset, chain)` pair independently of any invariant enforcement, an honest configuration mismatch (not even malicious) permanently destroys value for every user bridging in that direction — tokens are burned/escrowed correctly on the source chain but the destination mint/release credits a negligible fraction of the intended amount, a permanent freezing/loss of user funds.

### Likelihood Explanation
This triggers on the ordinary `send` → `on_accept` path for any legitimately registered token pair configured with decreasing decimal precision (source EVM 6, dest Substrate 18, or similar) — a single relayed message is sufficient, no privileged or malicious actor is required. The only gating factor is that `register_token`/`update_token` (via `CreateOrigin`) sets up such a decimals pair, which is a normal governance configuration action, not an attack.

### Recommendation
Fix `convert_to_balance` to handle both directions explicitly, mirroring the correct pattern used elsewhere (e.g. `VWAPOracle._normalizeAmount`, which branches on `decimals < 18` vs `>= 18` instead of using `saturating_sub`) [6](#0-5) :
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}
```

### Proof of Concept
1. Governance registers a non-native asset with `local_decimals = 18` on the substrate chain and `erc_decimals = 6` for the paired `HyperFungibleToken` deployment on an EVM chain (a normal, supported configuration per `ChainConfig.decimals`).
2. A user on the EVM chain calls `send()` bridging `1_000_000_000` raw units (1000.000000 tokens at 6 decimals).
3. On `on_accept`, the pallet calls `convert_to_balance(1_000_000_000, erc_decimals=6, local_decimals=18)`.
4. `erc_decimals.saturating_sub(local_decimals)` = `6u8.saturating_sub(18)` = `0`, so the divisor is `10^0 = 1`.
5. The beneficiary is credited `1_000_000_000` local balance units, which at 18 decimals is `0.000000001` tokens — twelve orders of magnitude less than the 1000 tokens the user actually bridged, permanently freezing the rest.
