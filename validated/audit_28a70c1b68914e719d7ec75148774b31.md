Confirmed: `HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string`, and for webhooks that resolves to `Request#to_signable_string`, which returns only `@raw_body`. The `shop-domain` header is never part of the signed payload.### Title
`shop-domain` header is not bound to the HMAC signature, allowing cross-tenant `WebhookMetadata#shop` spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts `Request#shop`, which is read directly from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` HTTP header, while `Utils::HmacValidator.validate` only verifies the HMAC over `Request#to_signable_string`, which returns solely `@raw_body`. Because the shop-domain header is never part of the signed content, an attacker who possesses one validly-signed webhook body (e.g. from their own installed shop) can replay it with an arbitrary `shop-domain` header, and the signature check still passes, causing the handler to receive `WebhookMetadata#shop` equal to the forged victim domain.

### Finding Description
The claimed binding is: `WebhookMetadata#shop` (delivered to the handler) == the shop actually authenticated by the HMAC signature. Tracing the code shows this binding does not hold.

- `Request#shop` reads `shopify_header("shop-domain")`, an attacker-controlled HTTP header, with no cryptographic tie to the body: [1](#0-0) 
- `Request#to_signable_string` returns only `@raw_body`; the shop-domain header, topic header, and webhook-id header are excluded from what gets signed: [2](#0-1) 
- `HmacValidator.validate` / `validate_signature` compute `HMAC(secret, verifiable_query.to_signable_string)` and compare it to the received `hmac` header — it never inspects or incorporates the shop-domain header: [3](#0-2) 
- `Registry.process` calls `HmacValidator.validate(request)`, and on success builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, passing the unauthenticated `shop` value straight to the handler: [4](#0-3) 

Root cause: the signable string for webhooks is defined as raw body only, so the HMAC proves "this body was produced by Shopify with the app's secret," but proves nothing about which shop the body is associated to at the transport/header level. `Request` never cross-checks `shop-domain` (or `topic`, or `webhook-id`) against any value embedded in, or bound to, the signed body.

Exploit flow: the attacker installs the app on their own shop and lets Shopify deliver a genuinely signed compliance webhook (e.g. `customers/data_request`) to the app's endpoint. The attacker captures this raw body and its valid `X-Shopify-Hmac-Sha256` value, then replays the exact same body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with the victim's domain. `HmacValidator.validate` recomputes the HMAC of the (unchanged) raw body and it matches, so validation succeeds. `Registry.process` then constructs `WebhookMetadata` with `shop: "victim.myshopify.com"` and hands it to the host app's handler, which (per the documented usage pattern in `docs/usage/webhooks.md`) uses `data.shop` to decide whose merchant record/export destination to touch — now operating on the victim's tenant context using attacker-controlled body content.

No existing guard catches this: `ShopValidator.sanitize!`, `JwtPayload`'s `aud` check, and `HttpRequest#verify` are unrelated call paths (OAuth/session-token flows, not webhook processing); `Context.setup?`/`private?`/`embedded?` are configuration flags, not per-request checks; Sorbet signatures only enforce types (`String`), not value provenance.

### Impact Explanation
Any header value on the request is fully attacker-controlled and is delivered unauthenticated as `WebhookMetadata#shop` to every host-app webhook handler using this gem as documented. Because host apps are told (via `docs/usage/webhooks.md`) to key merchant-scoped logic off `data.shop`, this is a cross-tenant confusion: the handler thinks it's processing shop A's data. Combined with an attacker-supplied body (from a webhook topic where body content is influenced by the attacker's own shop configuration, or simply reused verbatim), this can cause the host app to associate the wrong merchant with exported/erased data, mis-route notifications, or otherwise cross tenant boundaries — matching "Critical: cross-tenant access." This is repeatable against arbitrary victim shop domains at will, as long as the attacker holds one valid (body, hmac) pair for any topic the app subscribes to; the domain field can be swapped freely per request since it is unauthenticated.

### Likelihood Explanation
Preconditions are minimal and attacker-achievable without any secrets: the attacker only needs to install the app on their own development shop (unprivileged, self-service) to receive a genuinely-signed webhook, then replay it with a different `Shop-Domain` header value to the same endpoint. No `api_secret_key`, access token, or victim credentials are required. The cost is a single HTTP capture-and-replay; feasibility is high and fully repeatable for any topic and target domain.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the value that is authenticated, or verify the header against a value discoverable only via configured session/shop lookups before trusting it. Concretely, change `Request#to_signable_string` (or add a secondary check in `HmacValidator`/`Registry.process`) so it incorporates the shop-domain header into the signed content, or require host apps to independently confirm the `shop` value in `WebhookMetadata` corresponds to a shop that actually has an active install/session before using it as a trust boundary for tenant-scoped operations. At minimum, document that `WebhookMetadata#shop` is not itself signature-authenticated in this gem and should not be trusted as a tenant-scoping boundary without cross-referencing installed-shop state.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require "test_helper"

class WebhookShopSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host: "https://app.test",
      scope: "read_products", is_embedded: false, api_version: "2024-01", is_private: false,
    )
    @topic = "customers/data_request"
    @body = '{"customer":{"id":123},"shop_id":1}' # genuine body signed for attacker's own shop
    @attacker_shop = "attacker.myshopify.com"
    @victim_shop = "victim.myshopify.com"

    @valid_hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @body),
    )
  end

  def test_shop_header_is_not_bound_to_signature
    handler = mock
    handler.expects(:handle).with(
      data: has_entries(shop: @victim_shop, body: JSON.parse(@body)),
    )

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: @topic, path: "path", delivery_method: :http, handler: handler,
    )

    forged_headers = {
      "x-shopify-topic" => @topic,
      "x-shopify-hmac-sha256" => @valid_hmac,   # valid signature over @body, signed for attacker's shop
      "x-shopify-shop-domain" => @victim_shop,  # forged: attacker sets victim's domain
      "x-shopify-webhook-id" => "any-id",
      "x-shopify-api-version" => "2024-01",
    }

    request = ShopifyAPI::Webhooks::Request.new(raw_body: @body, headers: forged_headers)

    # Binding check: HMAC validity does not depend on the shop header
    assert(ShopifyAPI::Utils::HmacValidator.validate(request), "signature should still validate")
    assert_equal(@victim_shop, request.shop)

    ShopifyAPI::Webhooks::Registry.process(request)
    # handler.handle received shop: victim_shop even though the HMAC secret only proves
    # authenticity of @body, not of the shop-domain header -> binding violated
  end
end
```
This demonstrates that `request.shop` (and therefore `WebhookMetadata#shop`) equals the attacker-forged victim domain while HMAC validation — which only covers `@raw_body` — still succeeds, confirming the two values (signed identity vs. delivered `shop`) diverge.
