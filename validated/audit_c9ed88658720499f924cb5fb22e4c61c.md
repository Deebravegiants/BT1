### Title
`EvmHost.dispatch()`/`fundRequest()` have no fallback when the UniswapV2 router used to pay native-fee dispatches reverts, DoS-ing the native-payment path for message dispatch - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` let any unprivileged caller pay Hyperbridge relayer fees in native currency by having the host swap `msg.value` into `feeToken()` through a single hardcoded `_hostParams.uniswapV2` router via `swapETHForExactTokens`. There is no check that the router is usable (not paused/deprecated/drained) and no fallback path — a revert from the external router call reverts the entire dispatch, exactly the "external protocol operation could be unavailable but the caller doesn't check/handle it" bug class from the reported `SFrxETHAdapter._stake()` issue. [1](#0-0) 

### Finding Description
`dispatch(DispatchPost)` is the primary unprivileged entry point any application/user calls to send a cross-chain ISMP POST request. When `msg.value > 0`, it unconditionally calls out to an external, admin-configured UniswapV2 router (`_hostParams.uniswapV2`) to swap ETH for the exact fee amount: [1](#0-0) 

The same pattern (swap-or-revert, no failure handling) is duplicated in `dispatch(DispatchGet)`: [2](#0-1) 

and again in `fundRequest()`: [3](#0-2) 

None of these call sites wrap the router interaction in a `try/catch`, check the router's pause/operational state, or fall back to the `feeToken()` `transferFrom` path when the swap is unavailable. Just as `frxETHMinter.submit()` can be paused by its own governance and `SFrxETHAdapter._stake()` never checks for that before calling it, the UniswapV2 router this code depends on is an external, separately-governed contract whose `swapETHForExactTokens` can revert for reasons entirely outside `EvmHost`'s control: the router (or its factory/pair) can be paused/deprecated by its own team, the WETH/feeToken pair can be drained of liquidity so the exact-output swap cannot be filled, or `_hostParams.uniswapV2` can be pointed at a router that no longer functions. Every one of these conditions causes `dispatch`, `dispatch(get)` and `fundRequest` to revert unconditionally whenever the caller pays in native currency, with no recovery path other than falling back to paying in `feeToken()` — which the caller may not hold or may not be aware they need to switch to.

### Impact Explanation
`dispatch()` is the core function used by every ISMP application (HyperFungibleToken, WrappedHyperFungibleToken, IntentGatewayV2, HyperbridgeLzEndpoint, etc.) to send outbound cross-chain messages when paying in native token, e.g. `HyperFungibleToken.send()` calls `IDispatcher(_host).dispatch{value: msg.value}(request)`: [4](#0-3) 

If the configured Uniswap V2 router becomes unusable (paused by its own admin, deprecated, or its WETH/feeToken pair drained/manipulated), this single external dependency permanently breaks the native-fee dispatch path host-wide, for every downstream application built on `EvmHost`, matching the rule's "route unable to deliver messages" acceptance criterion. This is a protocol-wide denial of service on a widely-used payment method for message dispatch, not an isolated single-app issue.

### Likelihood Explanation
Likelihood is Medium: it requires an external, independently governed contract (the UniswapV2 router or its liquidity pool) to become paused/deprecated/drained, which is outside Hyperbridge's control, similar to how `frxETHMinter.submitPaused` is outside the adapter's control. Given `EvmHost` is deployed across many EVM chains, some pointing to third-party or wrapper routers (`GnosisUniswapV2Wrapper`, `UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper` per the repo's `evm/src/utils/uniswapv2/` directory), the surface for a misbehaving/paused/deprecated router is non-trivial and has already prompted the project to build multiple router-wrapper shims, indicating recognized fragility of this dependency. [5](#0-4) 

### Recommendation
- Wrap the `IUniswapV2Router02(...).swapETHForExactTokens(...)` calls in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `try/catch`, and on failure either revert with a clear, distinguishable error (so callers know to retry with `feeToken()` payment) or automatically fall back to requiring the caller to have pre-approved `feeToken()`.
- Consider allowing governance to configure multiple router candidates or a router-agnostic swap adapter so a single paused/deprecated router cannot brick the native-fee path for the whole host.
- Add monitoring/alerts so a paused or malfunctioning configured router can be swapped out (`setUniswapV2Router`) quickly by governance before it causes widespread dispatch failures.

### Proof of Concept
1. Governance configures `_hostParams.uniswapV2` to a live UniswapV2 router `R`.
2. `R`'s own admin pauses the router (or the WETH/feeToken liquidity pool is drained below the requested `post.fee`).
3. Any unprivileged user/application calls `EvmHost.dispatch{value: fee}(post)` to send a cross-chain message paying in native ETH.
4. `IUniswapV2Router02(R).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` reverts (either because `R` is paused or the swap cannot be filled).
5. The entire `dispatch` call reverts — the message is never dispatched, and every other unprivileged caller attempting to pay fees in native currency is denied service until governance manually swaps out `_hostParams.uniswapV2` via a separate transaction, or until liquidity/pause conditions change on the third-party router.
