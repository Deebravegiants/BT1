## Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body, not the `shop`/`topic` headers - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook delivery solely by HMAC-signing the raw body, while the `shop`, `topic`, `api_version`, and `webhook_id` values that get handed to the app's business logic are taken verbatim from unauthenticated HTTP headers. Because the app's `api_secret_key` is shared across every shop that has installed the app, any unprivileged internet user who has installed the app on their own store can capture one of their own genuine webhook deliveries (a valid `(body, hmac)` pair) and replay it against the victim app's public webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header swapped to an arbitrary/victim shop. `HmacValidator.validate` will accept it because the signature check never touches those headers.

### Finding Description
`Registry.process` is the entry point invoked by the host app to authenticate and dispatch an inbound webhook: [1](#0-0) 

The authenticity check is delegated to `Utils::HmacValidator.validate(request)`: [2](#0-1) 

`validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field. For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body: [3](#0-2) 

Note that `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers (`shopify_header`) and are never included in `to_signable_string`. Once `process` validates the HMAC, it forwards these unauthenticated header values directly to the app's handler: [4](#0-3) 

The identity binding that should hold is:
```
HMAC(body, api_secret_key) == received_hmac  AND  shop_header == shop_that_actually_produced(body, hmac)
```
The gem only checks the first clause. It never binds `shop` (or `topic`) to the signature, so the equality `shop_header == shop_that_actually_produced(body, hmac)` can be false while `validate` still returns `true`.

Because `api_secret_key` is a single, app-wide secret shared by all merchants who install the app (not a per-shop secret), an attacker who legitimately installs the app on their own store receives real webhook deliveries whose bodies are validly HMAC-signed with that shared secret. They can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and, if desired, `X-Shopify-Topic`) for any other shop domain. `HmacValidator.validate` still succeeds (it never inspected the header), and `Registry.process` calls `handler.handle` with `shop` set to the attacker-chosen value while the JSON payload is under full attacker control (their own store's data). Any app logic that trusts `WebhookMetadata#shop` to key per-tenant records (order sync, billing, GDPR data, inventory, etc.) will act on the wrong tenant, an authentication/tenant-isolation bypass entirely reachable by an unprivileged internet user with no access to the victim's credentials.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), one of the Critical impact categories: an attacker who is merely a merchant of the app (not privileged, no access to the victim's tokens or the app's `client_secret`) can make the host application process and persist data under an arbitrary victim shop identity. Depending on how the host app uses `WebhookMetadata#shop`/`#topic`, this can lead to data corruption, unauthorized state changes, or disclosure across tenants.

### Likelihood Explanation
Likelihood is high for any app that (a) is installed by more than one merchant (so the shared `api_secret_key` assumption holds) and (b) trusts `data.shop`/`data.topic` from `WebhookMetadata` without independently confirming the deliverer. No secrets or privileged access are required — only installing the app on an attacker-controlled store and being able to POST to the target's public webhook endpoint.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed payload, so a signature computed for shop A's delivery cannot be replayed and reinterpreted as belonging to shop B. At minimum, document and enforce that `Registry.process` must be paired with an out-of-band verification that the `shop` header matches an installation actually known to the host app (e.g., verifying against a stored session/shop record) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`; the app is configured with a single shared `api_secret_key`.
2. Shopify delivers a genuine webhook to the attacker's endpoint (or attacker triggers one, e.g. `orders/create`), producing a valid pair:
   - `X-Shopify-Hmac-Sha256: <valid hmac over body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `body: {...attacker-controlled order JSON...}`
3. Attacker replays the exact same `body` and `X-Shopify-Hmac-Sha256` to the victim app's public webhook URL, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only recomputes over the body — the swapped header passes unnoticed: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)` and the host app processes attacker-controlled data as if it originated from the victim tenant.

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
