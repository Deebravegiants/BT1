Confirmed: `EvmHost.dispatchIncoming(PostRequest,...)` forwards an **unbounded gas** low-level `.call()` to whatever address `request.to` decodes to [1](#0-0) , and `HandlerV2.handlePostRequests` loops over an entire batch of requests in a single relayer transaction, invoking `host.dispatchIncoming` for each one without any per-call gas cap [2](#0-1) .

### Title
Unbounded gas forwarding to attacker-controlled `IApp` destinations in batched `handlePostRequests` allows gas-griefing of relayers - (File: `evm/src/core/EvmHost.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
The reported bug class (ERC777-style callback hooks used to control execution timing or exhaust a keeper's gas) maps to Hyperbridge's message delivery path: any destination module address embedded in a `PostRequest.to` field is called back via a low-level `.call` with all forwarded gas, inside a relayer-submitted batch transaction that processes many requests atomically.

### Finding Description
`EvmHost.dispatchIncoming` resolves `destination = _bytesToAddress(request.to)` and performs `destination.call(abi.encodeWithSelector(IApp.onAccept.selector, ...))` with no gas stipend, i.e. Solidity forwards essentially all remaining gas (63/64 rule) to the destination contract [1](#0-0) . `request.to` is attacker-controlled: any user can dispatch a `PostRequest` on the source chain destined to a contract they deploy on the destination chain (exactly analogous to a malicious ERC777 token contract receiving a callback). The relayer has no way to sandbox or gas-limit this call.

`HandlerV2.handlePostRequests` batches multiple `PostRequestLeaf` entries and, after MMR proof verification, iterates calling `host.dispatchIncoming(leaf.request, _msgSender())` for each one in a single transaction [3](#0-2) . Because the relayer batches deliveries to amortize proof-verification cost, a single malicious destination module placed anywhere in the batch can consume attacker-controlled amounts of gas (via a compute-heavy fallback/`onAccept` implementation) up to the full gas forwarded by the call. Repeated across many submitted requests/blocks, this forces relayers either to (a) always send oversized gas limits to survive worst-case malicious targets, or (b) have their batched deliveries run out of gas and revert, wasting the gas spent on proof verification and losing the relayer's fee for that batch. The same unbounded-call pattern also exists in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(...)` for POST/GET timeouts, all of which call arbitrary `IApp` implementations via `.call(...)` with no explicit gas cap [4](#0-3) .

### Impact Explanation
This does not create a mint/freeze/theft primitive on its own, but it degrades relayer economics and delivery reliability: a malicious app author can force wasted gas on relayers (who already spent gas verifying MMR/state proofs for the whole batch before the malicious call executes), discouraging relaying of legitimate messages batched alongside the malicious one, or causing repeated failed/retried deliveries. Since delivery is a prerequisite for cross-chain state to finalize (mint, unlock, calldata execution via `CallDispatcher`), a chronically griefed relayer set can degrade the liveness of the whole bridge for a route (a "route unable to deliver messages" condition), which is the accepted impact class per the validation rules.

### Likelihood Explanation
Likelihood is limited by relayer batching/module-filtering behavior and by relayers being able to set an overall transaction gas limit and simply exclude batches containing suspect destinations after the fact — but they cannot know in advance that a not-yet-executed `onAccept` will be malicious, since `request.to` is arbitrary and the call is unbounded. Any user with normal transaction access to `dispatch(DispatchPost)` on a source-chain `EvmHost` can create the malicious request, requiring no special privilege — matching the "single submitted transaction/relayed proof" reachability bar.

### Recommendation
Bound the gas forwarded to destination `IApp` callbacks in `EvmHost.dispatchIncoming`/`dispatchTimeOut` (e.g., `destination.call{gas: MAX_CALLBACK_GAS}(...)`) so a single malicious module cannot consume more than a fixed, predictable amount of gas, protecting the surrounding batch and giving relayers a bounded worst case per message to price into fees.

### Proof of Concept
Not independently reproduced in this analysis (no test harness was run); this is a static code-path analysis based on the cited `EvmHost.sol`/`HandlerV2.sol` logic. A concrete PoC would deploy a contract implementing `IApp.onAccept` that busy-loops until gas is nearly exhausted, register it as the `to` of a `PostRequest`, and have a relayer batch it together with legitimate requests in `handlePostRequests`, observing that the batch either reverts (out-of-gas) or forces the relayer to overprovision gas for every batch containing unknown third-party destinations.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
