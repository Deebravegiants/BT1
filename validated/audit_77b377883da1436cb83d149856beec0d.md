### Title
Unauthenticated stateless op in `EmporiumUpgradeable.runAction` (Min-circuit path) lets an attacker drain stale ERC20 router allowances from Emporium — ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which uses the trivial `MainEVMCircuitMin` circuit that constrains nothing about amounts, nullifiers, or roots. This makes every balance/slippage/nullifier guard in `Hinkal.transact` and `EmporiumUpgradeable.runAction` a no-op (all bounded by the zero-length `erc20TokenAddresses` array), while `EmporiumStack.signerAddress == address(0)` also skips the EIP-712 signature check in `verifyWallet`. The result is that any unprivileged attacker can force Emporium (`address(this)`) to `.call()` arbitrary `endpoint`/`callData` (CASE 2, stateless branch) with no check tying that call to the attacker's own funds, letting them redirect a stale `allowance(emporium, router)` swap output to themselves.

### Finding Description
The claimed equality is:

`allowance(emporium, router)_before == allowance(emporium, router)_after + tokensConsumedForEmporium'sBenefit`

Trace:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks(circomData, dimensions, msg.sender)` → `dimensionsCheck` only requires internal array-length consistency; with `dimensions.tokenNumber == 0` and `circomData.erc20TokenAddresses.length == 0` this passes trivially: [1](#0-0) .
2. `formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and calls `formInputEmporiumMin`, which builds only `[emporiumMessage, timeStamp, calldataHash]` as public input — no `amountChanges`, no nullifiers, no root hash: [2](#0-1) . The corresponding circuit `MainEVMCircuitMin` only pins `message <== Poseidon(messageSeed)`; it enforces nothing about spent UTXOs or amounts: [3](#0-2) . Since `emporiumMessage` is exactly `Poseidon(messageSeed)` for an attacker-chosen `messageSeed`, the attacker can trivially produce a valid proof for any `emporiumMessage` value of their choosing without any privileged secret.
3. Back in `Hinkal.transact`, the balance-diff/slippage/nullifier-insertion loop is bounded by `circomData.erc20TokenAddresses.length`, which is 0, so it never executes for any real token: [4](#0-3) .
4. `_externalTransact` calls `EmporiumUpgradeable.runAction`, whose own `balancesBefore`/`balancesAfter` diff-check loop is likewise bounded by `circomData.erc20TokenAddresses.length == 0`, so it never fires either: [5](#0-4) .
5. `stack.signerAddress` is decoded from attacker-supplied `externalActionMetadata`. Setting it to `address(0)` makes `verifyWallet` return immediately after marking the message used — no EIP-712 signature is required: [6](#0-5) .
6. With `signerAddress == address(0)` and `op.invokeWallet == false`, execution falls into CASE 2 (stateless): the only checks are that the call selector isn't `callHinkalWallet`/`doSendToRelay`; then Emporium itself performs `op.endpoint.call{value: op.value}(op.callData)`: [7](#0-6) .

Attacker's exact call: `op = {endpoint: router, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IRouter.swapExactTokensForTokens.selector, leftoverAllowance, 0, path, attackerEOA, deadline)}`, wrapped in an `EmporiumStack{signerAddress: address(0), ops: [op], ...}`, with `circomData.erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`. Because Emporium is `msg.sender` to the router, `router.transferFrom(emporium, router, leftoverAllowance)` succeeds against the stale approval left by a prior legitimate swap, and the router sends the output directly to `attackerEOA` (not to Emporium/`msg.sender` of the Hinkal call). No downstream check ever inspects Emporium's token balance because `circomData.erc20TokenAddresses` is empty for this action.

Why guards fail: `performHinkalChecks`'s `dimensionsCheck`/`checkOnchainCreation` only validate internal array-length consistency and are satisfied by an empty array; `getHashedCalldata`/`calldataHash` binds the proof to the attacker's own chosen call but does not require any UTXO ownership or authorization of *which* tokens Emporium may move; `verifyProof` only proves knowledge of a `messageSeed` preimage, unrelated to fund custody; the balance-diff/slippage checks in `Hinkal.transact` and `EmporiumUpgradeable.runAction` are structurally skipped since they iterate `erc20TokenAddresses.length == 0`; `insertNullifiers`/`rootHashExists` are likewise irrelevant to this path since no nullifiers are supplied. `onlyAllowedRecipient` only asserts the call is routed via the legitimate `Hinkal`→`_externalTransact` path, not that the specific `op` is authorized by anyone with a stake in the affected tokens.

### Impact Explanation
Critical — direct theft of protocol/shared-custody funds (approved-but-unspent ERC20 balance sitting under Emporium's control) with output delivered straight to the attacker's EOA, bypassing all balance/slippage accounting because the "Min" circuit path zeroes out the token list. This is repeatable for any token/router pair where Emporium has been left with a non-zero `allowance` from any prior legitimate operation, and for any other stateless external call an attacker can craft that benefits from Emporium's identity as `msg.sender` (e.g., any other pre-existing approval, permit, or callback state).

### Likelihood Explanation
Preconditions: Emporium must have a non-zero leftover `allowance(emporium, router)` from a prior legitimate partial-amount swap (a realistic and common state for approve-then-spend router patterns, e.g. `LifiExternalAction.approveUnlimited` unless every swap consumes exactly what's approved). The attacker needs only: (a) the ability to submit a `transact` call with `erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, (b) a locally-generated valid Groth16 proof for `MainEVMCircuitMin` (trivial, since it's just `Poseidon(messageSeed)` with a self-chosen seed), and (c) knowledge of the leftover allowance amount (readable on-chain). No relayer, admin, or victim cooperation is required, and the attack is repeatable per stale-allowance occurrence.

### Recommendation
Do not allow the "Min"/stateless op path to bypass balance accounting for arbitrary `endpoint`/`callData` calls. Specifically: (1) require Emporium's own balance-diff check (as done in the general `runAction` path) even for zero-token-count Emporium actions, or disallow zero-length `erc20TokenAddresses` for actions that execute arbitrary external calls; (2) require `stack.signerAddress != address(0)` (i.e., a valid EIP-712-signed `EmporiumOperation` list) for any CASE 2 op whose `endpoint` is not an allow-listed, value-neutral target, so an authenticated principal is always bound to funds movement; (3) ensure Emporium always revokes/limits approvals to `router` (e.g., set-then-reset to zero after each swap, or approve only the exact `inputAmount` per call) so no dust allowance persists between transactions; (4) add an explicit require that any output-recipient (`to`) field embedded in stateless calldata equals `address(this)` for calls Emporium initiates on behalf of pooled funds, if that is enforceable via a wrapper/allow-list rather than raw `call`.

### Proof of Concept
Foundry fork test plan:
1. Deploy a mock ERC20 pair and a mock/real UniswapV2-style router with `swapExactTokensForTokens`.
2. Simulate a legitimate prior Emporium swap op (via `EmporiumUpgradeable.runAction` CASE 2, with a proper non-empty `erc20TokenAddresses` circuit call) that approves `router` for `type(uint256).max` (mirroring `LifiExternalAction.approveUnlimited`) but only spends part of it, leaving `allowance(emporium, router) = leftoverAllowance > 0`.
3. As `attackerEOA`, build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData = {externalAddress: EmporiumUpgradeable, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [op]})}` where `op.callData = abi.encodeWithSelector(IRouter.swapExactTokensForTokens.selector, leftoverAllowance, 0, path, attackerEOA, deadline)`.
4. Generate a valid Groth16 proof locally for `MainEVMCircuitMin` using an attacker-chosen `messageSeed` (`emporiumMessage = Poseidon(messageSeed)`), with `dimensions.tokenNumber = 0`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from `attackerEOA`.
6. Assert: `token.balanceOf(emporium)` decreases by `leftoverAllowance` (equality broken: pre-call allowance ≠ post-call allowance + tokens benefiting Emporium), `token.allowance(emporium, router)` decreases to 0 (or by the consumed amount), and `outputToken.balanceOf(attackerEOA)` increases by the swap output — with no revert from `BalanceChangeShouldBePositive`, slippage checks, or nullifier/root validation, since none of those paths execute for `erc20TokenAddresses.length == 0`.

        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);

            return formInputNormal(chainId, verifyingContract, circomData);
        }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
