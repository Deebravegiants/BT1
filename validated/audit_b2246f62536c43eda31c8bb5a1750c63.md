Based on my investigation, I found the vulnerable path: `finalizeGraduation`'s `_swapBudget(99%)` mitigation is only applied to `_pairRebalance`'s swap sizing, but `_routerDepositAndDispose`'s `addLiquidity` call can still return `liquidity == 0` due to V2's integer-truncating LP-mint formula (`min(amount0·totalSupply/reserve0, amount1·totalSupply/reserve1)`) when the deposited amounts are tiny relative to existing reserves — a scenario the codebase's own comments acknowledge is possible ("`_routerDepositAndDispose` then skips `addLiquidity`... `LPLock.recordLock(...)` records a zero-sized lock") but `LPLock.recordLock` unconditionally reverts on `amount == 0` (`ZeroAmount`), which the comment does not account for.

### Title
Permissionless HyperSwap pre-seed griefing bricks `finalizeGraduation` forever via `LPLock.recordLock`'s zero-amount revert - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` unconditionally calls `LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity)` [1](#0-0)  after computing `liquidity` from `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`. `LPLock.recordLock` reverts with `ZeroAmount` whenever `amount == 0` [2](#0-1) . Because `finalizeGraduation` has no `try/catch` around `recordLock`, a `liquidity == 0` result from the deposit leg permanently reverts every future call to `finalizeGraduation` for that token — the lifecycle stays stuck at `Graduating` forever, with the token's real curve-raised LT and 250M reserved tokens locked in `Bonding` with no rescue path.

### Finding Description
A single unprivileged attacker can permissionlessly front-run `finalizeGraduation` by calling `factory.createPair(token, lt)` then `pair.mint(attacker)` against a tiny self-funded seed to bake a hostile reserve ratio into the pool, exactly the "Regime 3 — mint pre-seed" attack the protocol's own defense targets [3](#0-2) .

`_seedRebalancing` computes a swap via `_pairRebalance`, capped at `_swapBudget` (99% of the available side) specifically to leave enough of both sides for the subsequent deposit [4](#0-3) . But the 1% reserve is a heuristic sized against the *swap* budget, not against V2's LP-mint rounding. `_routerDepositAndDispose` calls `router.addLiquidity(...)` and takes `liquidity` verbatim from its return value [5](#0-4) . Uniswap V2's `mint()` computes `liquidity = min(amount0 * totalSupply / reserve0, amount1 * totalSupply / reserve1)`; against a pre-seeded pool with sufficiently large existing reserves relative to the (deliberately tiny, e.g. 1%-of-1% remaining) deposit amounts, this ratio truncates to `0` even though `remToken > 0 && remLT > 0` individually. The code's own comment acknowledges this exact `liquidity = 0` outcome is reachable ("`LPLock.recordLock(...)` records a zero-sized lock" [6](#0-5) ) but only reasons about the *pre-`_swapBudget`* world; the fix caps the swap, not the deposit-side rounding, so a sufficiently large-reserve pre-seed (well within the attacker's reach since the attacker fully controls the pre-seed's absolute size) can still drive `amount0*totalSupply/reserve0` or `amount1*totalSupply/reserve1` to `0` at the deposit step.

When that happens, `finalizeGraduation` proceeds to call `LPLock.recordLock(tokenAddress, lpPair, 0)`, which reverts `ZeroAmount` [7](#0-6) . Since `finalizeGraduation` performs the state transition (`info.lifecycle = Lifecycle.Graduated`) and the `recordLock` call **after** all reverting side effects, but before any lifecycle write persists (the whole call reverts), every subsequent call to `finalizeGraduation` re-runs the identical computation against the identical pre-seeded pool and reverts identically — an unrecoverable, permanently repeatable revert. This is the same bug class as CVE-2017-3256's "hang or frequently repeatable crash (complete DOS)" — here manifesting as a permanently un-callable state-critical function rather than a server crash, with the practical effect of freezing the token's entire curve-raised LT and 250M reserved tokens in `Bonding` forever, since `Lifecycle.Graduating` blocks `buy`/`sell` [8](#0-7)  and there is no admin bypass or alternate exit path documented anywhere in `Bonding.sol` or `LPLock.sol`.

### Impact Explanation
Permanent freezing of: (1) all curve-raised LT that Phase 1 already drained into `Bonding` via `Router.graduate` (documented as parked there between phases) [9](#0-8) , and (2) the 250M reserved tokens (`LP_RESERVE`) meant for LP seeding. Traders holding the token can never sell (blocked by `TokenIsGraduating`), and the token can never reach `Lifecycle.Graduated`. This meets the "permanent freezing of trader, creator or LP funds" bar explicitly called out as in-scope.

### Likelihood Explanation
Reachable by any unprivileged wallet at the cost of one `factory.createPair` + `pair.mint` pre-seed sized to make the LP-mint rounding degenerate — no special role, no timing race beyond front-running the ~60-second phase-1→phase-2 keeper window that the protocol's own docs acknowledge exists [10](#0-9) . The protocol's extensive "brick-resistance" test suite (`TwoPhaseGraduation.t.sol`) covers dust pre-seeds and the swap-side zero-liquidity case addressed by `_swapBudget`, but does not appear to assert `liquidity > 0` is guaranteed at the deposit-rounding boundary against a *large*, deliberately-sized pre-seed — the natspec explicitly frames the residual risk as "attacker's pre-existing LP becomes 100% of the pool," not as an unconditional revert via `LPLock`'s `ZeroAmount` guard.

### Recommendation
In `Bonding._routerDepositAndDispose` (or `finalizeGraduation`), guard the `LPLock.recordLock` call against `liquidity == 0`: either skip the call and treat a zero-liquidity deposit as a no-LP-but-still-graduated terminal state (burning/sweeping the residue as already done for TOKEN/LT remainders), or add an explicit floor so `remToken`/`remLT` are only used when the resulting `addLiquidity` mint is proven non-zero ahead of the call. Add a regression test that pre-seeds the HyperSwap pair with reserves large enough (relative to the graduation's `tokensForLP`/`ltFromPair`) to drive the post-`_swapBudget` deposit's V2 mint formula to `0`, and assert `finalizeGraduation` still succeeds.

### Proof of Concept
1. Launch and graduate a token normally via `Bonding.triggerGraduation`/the threshold-crossing buy so it enters `Lifecycle.Graduating`, caching `(tokensForLP, ltFromPair)`.
2. Before `finalizeGraduation` is called (front-run the keeper), an attacker EOA calls `IUniswapV2Factory(hyperFactory).createPair(token, lt)`, then transfers a large TOKEN/LT amount (sized so it dwarfs `tokensForLP`/`ltFromPair` by several orders of magnitude while keeping a skewed ratio) into the pair and calls `pair.mint(attacker)`.
3. Anyone calls `bonding.finalizeGraduation(tokenAddress)`. `_seedRebalancing`'s `_pairRebalance` swap is capped at 99% of budget, leaving 1% of `tokensForLP`/`ltFromPair` for `_routerDepositAndDispose`'s `addLiquidity`.
4. Because the pre-seeded reserves are large relative to that 1% remainder, `addLiquidity`'s internal `mint()` computes `liquidity = 0`.
5. `finalizeGraduation` calls `LPLock.recordLock(tokenAddress, lpPair, 0)`, which reverts `ZeroAmount`. The whole `finalizeGraduation` transaction reverts.
6. Every subsequent call to `finalizeGraduation(tokenAddress)` reproduces the same pre-seeded state and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`.

```text
        LPLockStorage storage $ = _s();
```

```markdown
- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).
```
