### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` validates that body against the HMAC while trusting the `shop` and `topic` values taken from unauthenticated headers to route the payload to a handler and stamp it into `WebhookMetadata`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhook requests that method is defined as: [1](#0-0) 

This means the signature only binds the raw JSON body. The `shop` and `topic` values are read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`) and are never included in the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then dispatches based on the unauthenticated `topic` header and stamps the unauthenticated `shop` header into the metadata handed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain field with no cryptographic binding to the actual originating shop: [4](#0-3) 

The identity-binding equality that breaks is: `shop used by the handler to select/authorize tenant data` ≠ `shop covered by the HMAC`. Any party who can obtain one validly-signed webhook body/HMAC pair for a given `api_secret_key` (e.g., an app's own test shop, or a shop they control that has the app installed) can resend that exact body/HMAC with the `x-shopify-shop-domain` and `x-shopify-topic` headers rewritten to any value, and `Registry.process` will accept it as authentic for the forged shop/topic, because those fields are never covered by the signature.

### Impact Explanation
This is a cross-tenant data-integrity issue: a host application that (as documented/intended) uses `WebhookMetadata#shop` from `Registry.process` to determine which merchant's data to update, or that dispatches purely by `WebhookMetadata#topic`, can be made to process attacker-labeled webhook events for a shop the attacker does not control, using only a webhook the attacker legitimately received for their own shop (no `api_secret_key`, access token, or privileged access required). Because `topic` is likewise unauthenticated, an attacker can also cause a body meant for one topic to be dispatched to a different topic's handler, potentially with a body shape mismatch. This does not itself leak a secret but it breaks the tenant/topic identity binding the gem is documented to provide via `Utils::HmacValidator.validate`, enabling cross-tenant data corruption in the host app.

### Likelihood Explanation
Requires only unprivileged internet access plus one legitimately-received webhook (obtainable by installing the app on any shop, including a free/dev store, which is trivial for any developer). No secrets, tokens, or elevated privileges are needed; only header manipulation on a raw HTTP POST to the app's own webhook endpoint.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them, e.g., by including the full raw headers used for routing) rather than trusting them as unauthenticated metadata. At minimum, document prominently that `Request#shop` and `Request#topic` are unauthenticated and must not be used for tenant-sensitive routing without independent verification (e.g., cross-checking against a known session for the shop).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `{"id":123}`, header `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`@raw_body` only), which matches, so `Registry.process` proceeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: {"id"=>123}, ...)`, causing the host app to act on data under the impersonated shop's identity despite the payload never having originated from or been authorized for that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
