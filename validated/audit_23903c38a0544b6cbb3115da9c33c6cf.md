### Title
`balanceDif` accounting can be double-counted via a "double-entry" ERC20 that lets two `erc20TokenAddresses` alias the same real balance, allowing shielded UTXOs to be minted without full backing - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots balances per-index with `getBalancesForArray` (calling `balanceOf`/ETH balance independently for each entry of `circomData.erc20TokenAddresses`) and then checks `balanceDif == (onChainCreation ? 0 : amountChanges[i]) + utxoAmount` per index, with no requirement that the addresses in the array be distinct/non-aliased. An attacker who deploys a token where two different addresses `A` and `B` read the *same* underlying real balance (e.g., two proxies sharing storage/logic, or a "mirror" contract whose `balanceOf` simply forwards to `A`) can make one real transfer of `X` show up as a balance increase of `X` at *both* index `A` and index `B`, letting each index independently satisfy the equality while crediting a shielded UTXO of `X` for both "assets." Net effect: `X` real tokens enter the vault, but `2X` of shielded value is minted.

### Finding Description
The invariant that should hold is:
`sum(real ERC20/ETH received by the vault) == sum(amountChanges credited) + sum(utxoAmount on-chain-created)`.

The code computes this per-index in `Hinkal.transact`: [1](#0-0) 
and enforces the equality at: [2](#0-1) 

`getBalancesForArray`/`getBalancesForArrayMemory` independently call `balanceOf` (or read ETH balance) for each entry in `erc20TokenAddresses`, with no deduplication or aliasing check: [3](#0-2) 

Neither `dimensionsCheck` nor `checkOnchainCreation` in `HinkalHelper.sol` requires `erc20TokenAddresses` entries to be unique or to correspond to distinct real balances: [4](#0-3) [5](#0-4) 

**Exploit flow (internal transact, `externalActionId == 0`):**
1. Attacker deploys a "double-entry" token: real ERC20 logic lives at address `A`; address `B` is a second, attacker-controlled contract whose `balanceOf(vault)` reads/forwards to the same underlying storage as `A` (e.g., shared eternal-storage proxy pattern), while `B.transferFrom`/`B.transfer` can be made a no-op that still returns `true` (satisfies `SafeERC20`).
2. Attacker calls `transact` with `erc20TokenAddresses = [A, B]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = msg.sender`. Attacker only actually holds/approves `X` tokens (not `2X`).
3. `_internalTransact` runs the deposit branch for both indices: [6](#0-5) 
   - For `A`: a genuine `safeTransferFrom` pulls `X` real tokens into the vault.
   - For `B`: `safeTransferFrom` calls the attacker's no-op `transferFrom`, which moves nothing but returns success.
4. `oldBalances = [S0, S0]` and `newBalances = [S0+X, S0+X]` because `B.balanceOf` mirrors `A`'s real storage, which only changed once (by `X`).
5. `balanceDif[A] = X` and `balanceDif[B] = X`. Both pass the per-index equality check with `amountChanges[A]=X` and `amountChanges[B]=X`, `utxoAmount = 0` for both.
6. The circuit's per-token constraint (`inTotal + amountChanges === outTotal`) independently mints a new off-chain shielded UTXO worth `X` for asset `A` and a separate shielded UTXO worth `X` for asset `B` — total `2X` shielded value credited for only `X` real tokens deposited.

Existing guards do not stop this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency and onChainCreation semantics, not address uniqueness or real-balance correspondence; `verifyProof` only enforces circuit-internal arithmetic per declared token index, which has no way to know that two declared "tokens" alias one real balance; `rootHashExists`/`insertNullifiers` operate on the shielded tree independent of this balance mismatch.

If, symmetrically, address `B` is later made to actually move the real shared storage on redemption (e.g., `B` is a genuine second proxy sharing the same logic/storage as `A`, not just a read-mirror), an attacker can subsequently redeem both minted UTXOs (`A,X` and `B,X`) for real value, draining `2X` of real backing from the shared pool that only ever received `X` — extracting the other `X` from the pool's other depositors' commingled real balance of the same underlying token.

### Impact Explanation
This mints shielded value without full 1:1 backing, directly matching the Critical category "minting shielded value without backing (protocol insolvency)." The attacker gains shielded credit (and, if the aliased token also aliases writes, ultimately real value) proportional to the number of aliased address-entries they can list, repeatable on every transaction, at the expense of the shared vault's solvency and other depositors' funds.

### Likelihood Explanation
Preconditions: attacker must deploy a custom token contract exposing two (or more) addresses whose `balanceOf` reports the same underlying balance while its transfer functions can be made to no-op or otherwise decouple stated transfer amount from real balance movement — fully within an unprivileged attacker's control per the rules (they may deploy arbitrary tokens/contracts and craft every `CircomData` field). No relayer, admin, or victim cooperation is required; a single `transact` call with `externalActionId == 0` suffices to mint the excess credit, and it is repeatable without limit since nothing in `dimensionsCheck`/`checkOnchainCreation`/`transact` deduplicates or validates that `erc20TokenAddresses` entries denote independent real balances.

### Recommendation
- Enforce uniqueness of `erc20TokenAddresses` entries within a single `transact` call (revert on duplicates), and/or
- Compute `balanceDif` using a single global running total per unique underlying token/storage rather than trusting independent `balanceOf` calls per declared address, and/or
- Require that each token's real balance delta be attributed to exactly the address whose transfer function was invoked, i.e., snapshot/verify balances per-transfer-operation rather than only once before and once after the whole batch, closing the aliasing gap between how many "assets" are declared and how many real balances actually exist.

### Proof of Concept
Foundry test plan:
1. Deploy `RealToken` (standard ERC20) at address `A`; mint `X` to attacker.
2. Deploy `MirrorToken` at address `B` whose `balanceOf(addr)` returns `RealToken(A).balanceOf(addr)`, and whose `transferFrom`/`transfer` are no-ops returning `true`.
3. Attacker approves vault for `X` on `A` only.
4. Construct `CircomData` with `erc20TokenAddresses=[A,B]`, `amountChanges=[X,X]`, `onChainCreation=[false,false]`, `slippageValues=[0,0]`, `externalActionData={externalActionId:0, externalAddress: attacker}`, and matching locally-generated proof/circuit inputs asserting off-chain UTXO creation of `X` for both `A` and `B`.
5. Call `Hinkal.transact(...)`.
6. Assert: `RealToken(A).balanceOf(vault) - oldBalanceA == X` (only `X` real tokens entered), while two new shielded commitments were inserted crediting `X` for asset `A` and `X` for asset `B` (`2X` total shielded credit) — i.e., `real tokens received (X) < credited shielded UTXO value (2X)`, violating the stated invariant `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)` in economic terms (the transaction's own bookkeeping is internally "consistent" per-index only because both indices read the same real delta twice).

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }

        address[] memory erc20TokenAddresses

        balances = new uint256[](erc20TokenAddresses.length);
