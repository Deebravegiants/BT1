### Title
Webhook Tenant Identity (`shop`) Not Bound to HMAC Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the tenant identifier (`shop`) delivered to the app's handler is read directly from an HTTP header that is never covered by that HMAC. Any actor who can obtain one validly-signed webhook body (e.g. by having the app installed on their own store) can replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop, and the app will accept and process it as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the HMAC-signed content: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. only the raw body for webhooks — it never inspects headers: [4](#0-3) 

`Registry.process` validates the HMAC and then hands `request.shop` — the unauthenticated header value — directly to the app's handler as the tenant identifier, without cross-checking it against anything bound by the signature: [5](#0-4) 

Because a single app has one `client_secret` shared across all shops that install it, the HMAC over a given body is valid regardless of which shop it is claimed to belong to. The binding that should hold is:

`shop header value == shop that the HMAC-signed body was actually generated for`

This equality is never checked. An attacker who legitimately installs the target app on a shop they control receives correctly-HMAC-signed webhook bodies for that shop. They can capture such a body (no TLS interception needed — it's delivered to their own server) and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Utils::HmacValidator.validate(request)` still returns `true` because it only checks the (unmodified) body against the shared secret, and `Registry.process` passes the attacker-chosen `shop` value straight to `handler.handle`, causing the app to process/store data as if it came from the victim tenant.

### Impact Explanation
This breaks tenant isolation: an app that keys any state (e.g. "last order for shop X", GDPR redaction records, inventory data) off `WebhookMetadata#shop` can be made to attribute attacker-controlled webhook content to a victim shop, or trigger shop-scoped side effects (e.g. `customers/redact`, `shop/redact` handling, order/inventory sync) against a tenant the attacker doesn't control. This is a cross-tenant access primitive, matching the Critical impact bar for this analog.

### Likelihood Explanation
Any developer/merchant can install a public app on their own store (no privileged access, no leaked secrets, no TLS interception required) and receive validly-signed webhook payloads for that store. Replaying that body with a modified `shop-domain` header against the same app's webhook endpoint is trivial and reproducible by any unprivileged internet user who can install the target app.

### Recommendation
Bind the shop identity to the HMAC-verified content instead of trusting the header. Options:
- Verify the `X-Shopify-Shop-Domain` header value against the shop associated with the webhook subscription/registration (e.g., correlate via `webhook_id` and stored subscription data) before dispatching to the handler.
- Alternatively, include the header value in the HMAC-signed input the gem verifies, or require host applications to cross-check `request.shop` against an installed-shop allowlist prior to trusting it — and document this requirement prominently since `Registry.process` currently implies the shop is trustworthy once `HmacValidator.validate` passes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g. updates a product) and captures the resulting POST to their webhook endpoint, including headers and raw body — the request is validly HMAC-signed with the app's `client_secret`.
3. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` header to the same app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since it only checks the (unchanged) body against the shared secret: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, and processes it as if it were a legitimate webhook from the victim shop.
