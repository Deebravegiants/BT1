### Title
Webhook `shop`/`topic` identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` and `topic` used to dispatch a webhook from HTTP headers that are never included in the HMAC signature, which is computed only over the raw request body. `Registry.process` trusts these header-derived values when invoking the merchant's handler, so the identity binding "HMAC-authenticated content == the shop/topic acted upon" does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic`, by contrast, are pulled straight from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`, `shopify-topic` / `x-shopify-topic`), with no cross-check against the signed body: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body HMAC, then constructs `WebhookMetadata` using `request.shop` and `request.topic` — values that were never part of the signed material — and forwards it to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body) == (shop_header == shop_that_produced_this_body) && (topic_header == topic_that_produced_this_body)`

but the gem only checks `hmac_valid(body)`. The `shop-domain` and `topic` headers are fully attacker-controlled at the HTTP layer independent of the HMAC.

### Impact Explanation
This is a cross-tenant boundary break with no privileged credentials required:
1. Any unprivileged internet user who is themselves a legitimate (even free/trial) merchant of the target app can trigger a real event in their own store, causing Shopify to deliver a genuine webhook — a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — to the app's public webhook endpoint.
2. The attacker captures that `(raw_body, hmac)` pair (it is delivered to a URL they control observation of, or they can simply issue their own HTTP request directly to the app's public webhook endpoint, since that endpoint is just an internet-reachable URL, not a Shopify-only channel).
3. The attacker replays the exact same body and `hmac-sha256` header, but sets the `shopify-shop-domain` header to an arbitrary victim shop domain (and/or a different `shopify-topic` header).
4. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim's domain.

Any host application that uses `shop` from `WebhookMetadata` to look up a stored session/access token, gate authorization, or attribute the webhook payload to a tenant will process attacker-supplied data under the wrong tenant's identity — i.e., cross-tenant access/confusion, matching the report's "Critical - cross-tenant access" category.

### Likelihood Explanation
The prerequisite (being any merchant who installs the app, or simply POSTing to the app's public webhook endpoint with a previously-observed valid body/hmac pair) requires no leaked secrets, no `api_secret_key`, and no privileged account — only ordinary use of the app as an unprivileged merchant/internet user. This mirrors the reported bug class precisely: a field ("shop") that is acted upon by downstream logic but not covered by the authentication check (HMAC).

### Recommendation
Bind the `shop` (and ideally `topic`) values into the material that is HMAC-verified, or otherwise cryptographically tie the header values to the authenticated payload — e.g., include them in `to_signable_string`, or independently verify `request.shop` against an expected/allow-listed shop domain (via `ShopifyAPI::Utils::ShopValidator`) and cross-check that the topic in the header matches a topic embedded in the signed body, before dispatching to the registered handler.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. As an ordinary, unprivileged merchant with the app installed on `attacker-shop.myshopify.com`, trigger an order creation to receive a legitimate webhook POST with a real `raw_body` and valid `x-shopify-hmac-sha256` header (computed by Shopify with the app's `api_secret_key`, which the attacker never possesses).
3. Send a raw HTTP POST directly to the app's public webhook endpoint using the captured `raw_body` and `hmac-sha256` header unchanged, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. Call:
   ```ruby
   request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: spoofed_headers)
   ShopifyAPI::Webhooks::Registry.process(request)
   ```
5. Observe `Utils::HmacValidator.validate(request)` returns `true` (body/hmac untouched), and the handler receives `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though that shop never sent this webhook, confirming the identity-binding break.
