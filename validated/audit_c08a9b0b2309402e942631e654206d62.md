### Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature, allowing cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an inbound webhook solely by HMAC-verifying the raw request body (`to_signable_string` returns `@raw_body` only), using a single app-wide secret (`Context.api_secret_key`) that is identical for every shop that installs the app. The `shop` field, which `ShopifyAPI::Webhooks::Registry.process` uses unmodified to build the `WebhookMetadata` handed to the app's handler, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never included in the signed content. This breaks the intended binding `hmac(body, secret) == hmac ⟹ shop == origin_shop`.

### Finding Description
- `Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `Request#shop` is read from an unauthenticated header: [2](#0-1) 
- `HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the body) against `Context.api_secret_key`, an app-level secret shared by all shops: [3](#0-2) 
- `Registry.process` validates the HMAC, then dispatches to the handler using `request.shop` verbatim, with no cross-check that the body actually originated from that shop: [4](#0-3) 
- The resulting `WebhookMetadata.shop` is a plain, unauthenticated field consumed directly by the app's `WebhookHandler#handle`: [5](#0-4) 

Because the HMAC secret is the *app's* secret (identical across all merchant installs), not a per-shop secret, `hmac(body)` is a function of body content alone — it does not depend on which shop the body came from. Any two shops that trigger webhooks producing the same `raw_body` will produce the same valid `hmac-sha256` value. This is exactly the reported bug class: "a field acted on (`shop`) but not covered by the HMAC" — the analog of `blockBuilderBLSKeyToAddress[key]` being writable without being bound to the entity that is later trusted.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (an ordinary, unprivileged merchant account — no special credentials, tokens, or `client_secret` required) can capture a genuine `(raw_body, hmac-sha256)` pair for a webhook topic whose payload is content-identical or predictable across tenants (e.g., topics with generic/empty bodies). They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. Because the library validates only the body's HMAC and blindly trusts the `shop` header for routing, the forged request passes validation and is dispatched to the handler as if it were an authentic event for the victim's shop. Depending on what the app does with `WebhookMetadata.shop` (e.g., using it as a lookup/session key to update tenant records, trigger data resets, or as an implicit "this shop confirmed X" signal), this results in cross-tenant data corruption or spoofed tenant-scoped actions — satisfying the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Moderate-to-High. It requires no privileged credentials, access tokens, or `client_secret` — only that the attacker install the app on a store they control (a normal, permission-free action) to obtain a valid signed body for a topic whose body content is not shop-specific. This is entirely within the reach of an "unprivileged internet user" and costs nothing beyond normal app usage.

### Recommendation
Bind the authenticated shop identity into what is actually verified:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signed content that `to_signable_string` returns, or
- Independently verify that `request.shop` corresponds to a shop the app has an active install/session for, and reject/flag webhooks whose `(topic, body)` combination has already been consumed for a different shop, or
- At minimum, document and enforce in `Registry.process` that `webhook_id` uniqueness/idempotency is checked per claimed shop, since Shopify's own delivery guarantees a unique `webhook_id` but this library does not use it to detect cross-shop replay.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and receives
# a real webhook whose raw body is topic-generic (no shop-specific fields), e.g.:
raw_body = '{"id":123}'
valid_hmac_b64 = "<hmac captured from the genuine request sent to attacker's own endpoint>"

# Attacker replays the identical body+hmac to the app's public webhook endpoint,
# but forges the shop header to target a victim tenant:
headers = {
  "x-shopify-topic" => "some/topic",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # unchanged — still valid because it only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id" => "attacker-controlled-or-replayed-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body against the
# app's shared secret; Registry.process then invokes the handler with
# WebhookMetadata.shop == "victim-shop.myshopify.com", even though the payload
# never originated from that shop.
```

**Uncertainty:** I could not verify the exact real-world Shopify webhook payload contents for specific topics (whether any mandatory/common topic body is truly shop-content-independent) since that is external to this repo; the root-cause code path (HMAC not covering `shop`, shared app-level secret, unauthenticated shop routing) is fully confirmed in-repo. Full exploitability depends on the existence of at least one webhook topic with shop-independent body content, which is a property of Shopify's webhook payload formats, not of this library.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
