Found the analog: in `IntrinsicIntents._fillSameChain`, the partial-fill path re-opens the reentrancy lock in the *same* transaction, exactly the "lock variable temporarily/finally cleared to unlocked value" pattern the Aloe report warns about — except here it's a genuine attacker-reachable bypass, not merely a hypothetical.

### Title
Partial-fill path clears the `_filled` reentrancy lock before external native-token refund, enabling reentrant re-fill - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` sets `_filled[commitment] = msg.sender` at the top (the CEI fix for the previously reported reentrancy), but on a **partial fill** it explicitly `delete`s `_filled[commitment]` (line 135) before the function's final external interaction — the native-token refund via `_sendValue(msg.sender, msgValue)` (line 141). This mirrors the Aloe `lastAccrualTime = 0` bug class: a "locked" sentinel meant to block reentrancy is reset to its unlocked value inside the very call it's supposed to protect, before all external calls have completed.

### Finding Description [1](#0-0) 
`_fillSameChain` sets the guard first: `_filled[commitment] = msg.sender;`.

The function then loops over outputs, doing `.call{value: ...}("")` transfers to `beneficiary` for ETH outputs [2](#0-1) , and afterward, on a partial fill, it deletes the guard and then refunds any unspent `msg.value` back to `msg.sender` (the solver) via `_sendValue` [3](#0-2) :
```
if (isFullyFilled) {
    _execute(order, outputsLen);
    emit OrderFilled(...);
} else {
    delete _filled[commitment];
    emit PartialFill(...);
}

if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```
Because `delete _filled[commitment]` happens *before* the `_sendValue` external call, a malicious `msg.sender` (the solver contract itself, not just the beneficiary) can re-enter `fillOrder` from its `receive()`/fallback during the refund. At that point `_filled[commitment]` is already zero (deleted), so the `Filled()` guard in `IntentGatewayV2.fillOrder` does not block a nested call, and `_fillSameChain` runs again against the same commitment while the outer call is still on the stack, before `_partialFills` state from the outer call's escrow release is finalized. This is a genuine (not merely storage-manipulated) unlock-then-external-call ordering bug, the same root cause class as the Aloe finding (guard reset to its "unlocked" sentinel value prior to completing all external interactions in the same call graph).

The dedicated reentrancy tests (`IntrinsicIntentsReentrancyTest.sol`) only exercise the **full-fill** path (`_filled` is never deleted before the tested external transfer) — they use single-output orders sized to be fully filled in one shot, so they never touch the `delete _filled[commitment]` branch reached on partial fills, and thus never test the sequence: partial-fill beneficiary transfer → `delete _filled` → refund reentry.

### Impact Explanation
A reentrant call during the native-token refund lands inside `_fillSameChain` again with the lock cleared, and can re-process escrow accounting (`_partialFills`, `_orders`) for the same order commitment before the outer invocation's `_withdraw` bookkeeping settles, permitting double-release of escrowed input tokens or manipulation of the surplus-splitting / partial-fill accounting to drain escrowed user funds — a concrete theft-of-funds vector reachable by any solver submitting a `fillOrder` transaction with a malicious refund-receiving contract as `msg.sender`.

### Likelihood Explanation
Reachable by an unprivileged solver: any address can call `IntentGatewayV2.fillOrder` with a contract as `msg.sender` for a same-chain, ETH-output order they intentionally structure to be partially filled (leaving `msgValue > 0` unspent so `_sendValue` executes), triggering the callback during the refund. This is a straightforward, low-cost attack path requiring only a crafted order and a malicious solver contract, no privileged role.

### Recommendation
Follow strict checks-effects-interactions consistently for the partial-fill branch: do not `delete _filled[commitment]` until after all external calls (including the trailing native-token refund) have completed, or re-set `_filled[commitment] = msg.sender` only after `_sendValue` returns, or move the refund to occur before any `_filled` mutation. Alternatively, add an explicit reentrancy guard (`nonReentrant`) around `fillOrder` independent of the `_filled` mapping's semantic double-duty as both a fill marker and a reentrancy lock.

### Proof of Concept
1. Attacker deploys a solver contract with a `receive()` that re-enters `IntentGatewayV2.fillOrder` on the same `commitment` when triggered.
2. Attacker places (as `order.user`) a same-chain order with an ETH output and multiple input tokens such that a single `fillOrder` call from the malicious solver only partially fills the order (e.g., supplies `options.outputs[i].amount < totalRequired` for at least one output, and overpays `msg.value` intentionally so `msgValue > 0` remains after the beneficiary transfer).
3. Solver calls `fillOrder{value: msgValue}(order, options)`; `_fillSameChain` sets `_filled[commitment] = solver`, transfers ETH to `beneficiary`, computes `isFullyFilled = false`, executes `delete _filled[commitment]`, then calls `_sendValue(solver, leftoverMsgValue)`.
4. The `_sendValue` call triggers solver's `receive()`, which re-enters `fillOrder` for the same `commitment`; since `_filled[commitment]` is now `0`, the `Filled()` guard does not block it, letting the solver re-run `_fillSameChain` and claim additional escrow release for the same order before the original call unwinds.
