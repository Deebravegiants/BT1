Based on my research, I found a concrete decimal-scaling bug in `pallet-hyper-fungible-token` that is structurally in the same bug class as the Balancer report (asymmetric/incorrect scaling between the two legs of a bridging round-trip), but with a materially worse impact than "rounding dust" — it can produce an outright magnitude mismatch rather than a 1-wei rounding bias.

### Title
Silent `saturating_sub` in HFT decimal conversion causes unbacked mint / value destruction when local decimals exceed EVM decimals - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`pallet-hyper-fungible-token` converts amounts between this chain's local decimals and a registered EVM peer's decimals using `convert_to_erc20` (outbound, `send`) and `convert_to_balance` (inbound, `on_accept`/`on_timeout`). Both functions compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`. If a token is registered with `local_decimals > erc_decimals`, the exponent silently clamps to `0` instead of scaling in the opposite direction, so the conversion becomes a no-op multiply/divide by `10^0 = 1` where a real `10^(local_decimals - erc_decimals)` scale-down/up was required.

### Finding Description
`convert_to_erc20` [1](#0-0)  multiplies the local `u128` balance by `10^(erc_decimals.saturating_sub(local_decimals))` to produce the ERC20-side `U256` amount encoded into the outbound ISMP `Message` and dispatched via `send` [2](#0-1) .

`convert_to_balance` [3](#0-2)  divides the incoming ERC20 `U256` amount by `10^(erc_decimals.saturating_sub(local_decimals))` in `on_accept`/`on_timeout` [4](#0-3)  and [5](#0-4) .

Both use `saturating_sub`, which returns `0` whenever `erc_decimals < local_decimals` (i.e., the registered EVM token has *fewer* decimals than the local asset). In that configuration:
- `send()` fails to scale the amount *down*, so the ERC20 message body carries an amount `10^(local_decimals-erc_decimals)` times *larger* than intended relative to the destination token's precision.
- `on_accept()`/`on_timeout()` fails to scale *up*, so the local balance minted/released is `10^(local_decimals-erc_decimals)` times *smaller* than it should be.

This is the same root-cause pattern as the reported Balancer issue — a single conversion helper reused on both legs of a paired operation (add/remove liquidity there; send/receive here) uses a rounding/scaling rule that is only correct for one ordering of the inputs, so the two legs of a round trip stop pricing consistently. Here, instead of a 1-unit dust discrepancy, the mismatch is a full power-of-ten factor.

### Impact Explanation
If any token is ever registered via `register_token`/`update_token` with `local_decimals > erc_decimals` for a given `(AssetId, StateMachine)` pair [6](#0-5) :
- An attacker calling `send()` with a small local amount would have the outbound message encode an amount inflated by `10^(local_decimals - erc_decimals)`, letting the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract mint or release far more value than was escrowed/burned on the substrate side — an unbacked mint on the EVM leg.
- Conversely, on the inbound path, tokens legitimately bridged from EVM would be credited at `10^-(local_decimals-erc_decimals)` of their true value, permanently destroying value for honest users.

This maps directly to the "concrete theft or permanent freezing of funds, unbacked mint" acceptance criterion.

### Likelihood Explanation
I could not verify, within the available tool budget, whether `register_token`/`update_token` (not shown in the retrieved code) validates that `erc_decimals >= local_decimals` before accepting a `Precisions` entry. If no such validation exists, this is trivially triggerable by governance misconfiguration (a plausible operational scenario given the wide variety of decimal conventions across EVM tokens, e.g., a local 18-decimal asset paired with a 6-decimal USDC-style EVM representation) and then exploitable by any unprivileged account calling the public `send` extrinsic. This uncertainty should be resolved by inspecting the registration code directly.

### Recommendation
1. Replace `saturating_sub` with a checked/explicit bidirectional scaling routine that multiplies or divides depending on the sign of `erc_decimals - local_decimals`, rather than silently clamping to a no-op.
2. Add an invariant check in `register_token`/`update_token` (or in the conversion helpers themselves) that rejects/reverts on decimal configurations that would silently truncate, or explicitly supports the `local_decimals > erc_decimals` case symmetrically in both `convert_to_erc20` and `convert_to_balance`.
3. Add fuzz/property tests asserting `convert_to_balance(convert_to_erc20(x, e, l), e, l) == x` (mod floor rounding of the correct scale) for all `e, l` orderings, not just `erc_decimals >= local_decimals`.

### Proof of Concept
Given `local_decimals = 18`, `erc_decimals = 6` (a plausible registration for a token native to substrate with 18 decimals, bridged to an EVM representation of a 6-decimal stablecoin):
- `convert_to_erc20(1_000000000000000000u128 /* 1 local token */, 6, 18)`: `erc_decimals.saturating_sub(local_decimals) = 6.saturating_sub(18) = 0`, so the function returns `U256::from(1_000000000000000000) * 10^0 = 1_000000000000000000`, i.e. it emits an ERC20 amount of `1e18` raw units to a 6-decimal token — 1,000,000,000,000 (one trillion) whole tokens instead of the intended 1 whole token.
- The reverse function `convert_to_balance` exhibits the mirror-image under-crediting for the same decimal pairing on the inbound path [7](#0-6) . [8](#0-7)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
