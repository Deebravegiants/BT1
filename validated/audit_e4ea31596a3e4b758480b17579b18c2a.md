### Title
Unbounded `Order.inputs` / `Order.output.assets` arrays can make `placeOrder`/`fillOrder` permanently un-fillable, freezing escrowed user funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2.placeOrder` accepts an `Order` struct whose `inputs` and `output.assets` (`TokenInfo[]`) arrays have no length cap. `fillOrder` and its internal `_fillSameChain`/`_fillCrossChain` handlers then iterate over these arrays doing per-token `ERC20`/native transfers, escrow bookkeeping, and (for cross-chain fills) building `outputFills`/dispatch bodies proportional to array size. This mirrors the reported `claimFees` bug class: an actor-controlled array with no bound can push a required transaction past the block gas limit, denying the core operation permanently.

### Finding Description
`placeOrder` (in `IntentGatewayV2.sol`, delegating to `IntrinsicIntents`/`ExtrinsicIntents`) escrows arbitrary numbers of input tokens supplied by an unprivileged user in `order.inputs`, and the counterpart `output.assets` is likewise attacker/user-supplied with no length limit enforced in `IntentsBase.sol` or the concrete fill paths. `_fillSameChain` and `_fillCrossChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:53-143`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`) loop `for (uint256 i; i < outputsLen; i++)` performing a `safeTransferFrom`/native transfer, surplus computation, and event-array writes per element — the *solver's* required transaction (`fillOrder`) whose gas cost grows linearly (and, given `SLOAD`/`SSTORE` per iteration plus external ERC20 calls, super-linearly in practice) with `outputsLen`/`inputsLen`. Because `placeOrder` is the unprivileged, permissionless entry point that determines these lengths and escrows the user's real funds (`IntentsBase._orders[commitment][token] += ...`), a user (or an attacker griefing another user's flow via a crafted quote, or simply a user who mis-sizes an order) can create an order whose `fillOrder` call can never fit within the destination chain's block gas limit. The `_execute`/sweep paths in `IntentsBase.sol` (`_execute`, lines 498-545) and the pre-dispatch transfer loops in `IntentGatewayV2.sol` (lines 241-300) similarly iterate proportional to `order.predispatch.assets.length` / `order.inputs.length`, compounding the gas cost for the same order. [4](#0-3) [5](#0-4) 

No maximum array-length check (e.g., `MAX_INPUTS`/`MAX_OUTPUTS`) was found in `IntentsBase.sol`, `IntentGatewayV2.sol`, `IntrinsicIntents.sol`, or `ExtrinsicIntents.sol`.

### Impact Explanation
If an order's `inputs`/`output.assets` array is large enough that no `fillOrder` transaction can complete within the destination chain's block gas limit, the order becomes permanently unfillable:
- Same-chain orders: the user's escrowed `inputs` (real ERC20/native tokens locked in `_orders[commitment][token]`, see `IntentsBase.sol:451-485`) can never be released via `_fillSameChain`, and cancellation requires waiting past `deadline` — funds are frozen for the deadline duration and, if the deadline is set very far out or the array is large enough that even cancellation-refund loops (`_withdraw`, same per-item loop) also fail, indefinitely.
- Cross-chain orders: `_fillCrossChain`'s per-output loop plus the `_post`/dispatch call means the escrow can never be redeemed on the source chain, freezing user funds that were escrowed there.

This satisfies "permanent freezing of funds" via "a route unable to deliver messages/fill orders" — the fill path itself becomes non-executable.

### Likelihood Explanation
Likelihood is bounded by real-world usage: a legitimate user/wallet integration would not normally submit orders with hundreds of token legs, and off-chain solver tooling (`sdk/packages/simplex`) iterates per-leg already assuming reasonable sizes. However, nothing on-chain prevents it, and the entry point (`placeOrder`) is fully permissionless and reachable by any address in a single transaction, so a malicious or buggy order-placer (or an attacker targeting their own escrow to force a griefed "stuck funds" narrative, or more importantly, a User Interface bug that lets a legitimate user accidentally batch too many token legs) can trigger it without any privileged role. This is a plausible Medium-severity finding, consistent with the original report's classification, since it requires a specific (large) input construction rather than being trivially triggered by default usage.

### Recommendation
Enforce an explicit upper bound on `order.inputs.length`, `order.output.assets.length`, and `order.predispatch.assets.length` in `placeOrder` (and mirror the check in `fillOrder`'s validation step, "Validates input/output array length consistency" per the existing docstring in `IntentGatewayV2.sol:433-438`), sized so that the worst-case `_fillSameChain`/`_fillCrossChain`/`_execute`/`_withdraw` loop plus any attached `output.call`/`predispatch.call` execution provably fits under the target chains' block gas limits with margin.

### Proof of Concept
1. Attacker (or careless user) calls `IntentGatewayV2.placeOrder` with an `Order` whose `output.assets` (for a cross-chain order) or `inputs`/`output.assets` (for a same-chain order) array contains, e.g., 500+ distinct ERC20 `TokenInfo` entries, each requiring a nonzero escrow amount — nothing in `placeOrder`, `IntentsBase._validateParams`, or the fill functions rejects this for length.
2. Order is escrowed: `_orders[commitment][token]` is set per input token (`IntentGatewayV2.sol` predispatch/input transfer loops, lines 241-300, and `IntentsBase.sol` escrow bookkeeping).
3. A solver calls `fillOrder`; `_fillSameChain`/`_fillCrossChain` must loop once per output asset doing a `safeTransferFrom`/native `.call` plus storage writes (`IntrinsicIntents.sol:65-119`, `ExtrinsicIntents.sol:173-199`). At sufficient array length the required gas exceeds the destination chain's per-block gas limit, so the transaction can never be mined.
4. The order is now permanently unfillable; escrowed input tokens remain locked until (same-chain) `deadline` passage allows a refund path — itself subject to the same per-item loop cost in `_withdraw` (`IntentsBase.sol:451-485`) — or (cross-chain) indefinitely, since redemption depends on the same oversized fill path executing successfully on the destination.

*Note: I was unable to locate an explicit numeric cap for `TokenInfo[]` array lengths anywhere in the intents contracts family (`IntentsBase.sol`, `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`, `IntentGatewayV2.sol`) via the available search tools; if such a cap exists elsewhere (e.g., in a validation helper not indexed here), this finding would not apply. A full-repository grep/build for a `MAX_INPUTS`/`MAX_OUTPUTS` style constant would confirm.*

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
