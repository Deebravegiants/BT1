### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` nonetheless treats `request.shop` as an authenticated tenant identifier and hands it straight to the app's handler via `WebhookMetadata`, so any party that can obtain one validly-signed `(body, hmac)` pair can replay it with an arbitrary `shop-domain` header and have it pass HMAC verification while impersonating a different tenant.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes_that_include_shop)`. In this gem it instead holds only `hmac == HMAC(secret, raw_body)`, with `shop` excluded entirely: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` only ever verifies `to_signable_string`, which is the body alone: [3](#0-2) 

`Registry.process` verifies the HMAC and then dispatches to the handler using `request.shop` — parsed directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header — as if it were verified tenant data: [4](#0-3) 

The gem's own documentation instructs handler authors to treat `data.shop` as "The shop domain of the webhook" with no caveat that it is unauthenticated, encouraging exactly this trust: [5](#0-4) 

Because the `shop` header sits outside the HMAC-protected byte range, the equality the app relies on for tenant attribution (`hmac verified` ⇒ `shop is genuine`) does not hold.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (Shop A) will receive genuine webhook deliveries from Shopify for Shop A, each with a valid `(raw_body, hmac)` pair signed with the app's shared `client_secret`. Because `shop-domain` is not part of the signed bytes, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (Shop B). `Registry.process` will validate successfully (the body is unchanged) and invoke the handler with `data.shop == "shop-b.myshopify.com"` and attacker-controlled `data.body`. Any host application that uses `data.shop` to key its per-tenant persistence/business logic (a common and gem-encouraged pattern) will apply attacker-controlled data to another merchant's tenant context — a cross-tenant data-integrity/cross-tenant access issue, without ever needing the victim's credentials or access token.

### Likelihood Explanation
Exploitation requires only an unprivileged Shopify Partner/developer account able to install the target app on a store they control — no special access, secrets, or social engineering is needed. Capturing one's own webhook deliveries and replaying them with a modified header is trivial once the app is installed, and this pattern is directly reachable from the gem's documented `Registry.process` API without the host app doing anything unusual.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed byte string, or otherwise cryptographically bind them to the body before verification (e.g., include them as part of an HMAC computed over `"#{shop}\n#{raw_body}"`), and clearly document that `data.shop` from `WebhookMetadata` is not currently covered by the HMAC so host applications cannot mistakenly treat it as a verified tenant identifier without an additional bound check (e.g., cross-referencing against the registered shop for the given `webhook_id`/subscription).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a real webhook, e.g. for topic `orders/create`, with headers `x-shopify-hmac-sha256: <valid_hmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `raw_body`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `HmacValidator.validate` recomputes HMAC over `raw_body` only, matching the supplied `hmac`, so validation succeeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)` — the app now processes attacker-controlled content as if it originated from `victim-shop.myshopify.com`.
