### Title
Webhook `shop` (and `topic`) attribution is derived from unauthenticated HTTP headers, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the intended binding `hmac-verified-content == tenant-attributed-content`: the signature proves the body is authentic, but the `shop`/`topic` values a host application uses to route/store webhook data are never bound to that signature.

### Finding Description
`Request#hmac` reads the signature from the `shopify-hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile, `shop` and `topic` — the very fields an app uses to decide *which tenant* the webhook belongs to — are pulled straight from headers that are entirely outside the signed content: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., against the body bytes alone: [4](#0-3) 

Because the shop-domain header is never included in `to_signable_string`, a valid HMAC only proves "this body came from Shopify for *some* topic/shop", not "this body came from Shopify *for the shop named in this specific request's headers*". This is exactly the class of flaw described in the reference report: the field that the application relies on for tenant attribution (`shop`) is decoupled from the field actually protected by the cryptographic check (`raw_body`).

### Impact Explanation
An attacker who legitimately installs the app on their own store (no privileged credentials, `api_secret_key`, or access token required) will receive genuine, correctly-HMAC-signed webhook deliveries for their own shop. Because the signature never binds to the `shop-domain` header, the attacker can replay the exact same `raw_body` + `hmac-sha256` header to the victim app's public webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still return `true` (the body/HMAC pair is legitimately signed by Shopify's secret), and any host application that trusts `request.shop` for tenant routing — as this gem's own documentation instructs apps to do — will process or store attacker-controlled data under the victim shop's identity. This is a cross-tenant data injection/impersonation vector reachable by any unprivileged internet user with only a normal (non-privileged) app installation of their own.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints by design (`raw_body`/`headers` come straight from the request), and any user can install a Shopify app trial/dev store to obtain a legitimately-signed payload for replay. The `shop`/`topic` accessors are the gem's documented, and only, method of learning webhook provenance, so any consumer following the gem's intended usage pattern inherits this gap without extra effort.

### Recommendation
Include the shop domain (and ideally the topic) as part of the material verified against the HMAC, or otherwise cryptographically bind the header-derived tenant identity to the signed body before exposing `shop`/`topic` as trusted values. At minimum, document explicitly that `Webhooks::Request#shop`/`#topic` are unauthenticated inputs and must not be used for tenant attribution without an independent, authenticated cross-check (e.g., matching against a previously-stored, install-time shop record) — mirroring the OAuth flow's binding of `shop` inside `AuthQuery#to_signable_string`, which correctly signs `shop` together with the rest of the callback parameters.

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`). The app's webhook endpoint receives a POST with header `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker sends a new POST to the same endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` and `to_signable_string` (body-only) match, so `HmacValidator.validate(request)` returns `true`.
5. The host app, trusting `request.shop` (`victim.myshopify.com`) per the gem's documented usage, ingests/stores the attacker-controlled payload as though it belongs to the victim shop.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
