### Title
Emporium wallet-fee signature binds `maxFee` amount but not `feeToken`, letting fee currency be swapped after signing - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
In the wallet-invoked ("stateful") Emporium flow, a user's `HinkalWallet` authorizes relay fee payments via an EIP-712 signature that only commits to a numeric `maxFee` cap — it never commits to the token (`feeToken`) in which that fee will actually be charged. The `feeStructure` (including `feeToken`) is instead supplied by whoever assembles `circomData` for the on-chain call, and is only checked for numeric bound against `maxFee`, not for currency. This is the same "fee amount and fee currency decoupled" bug class as the `Marketplace.tradeFee`/`acceptedCurrency` report, but applied to Hinkal's relay-fee-from-wallet path.

### Finding Description
`verifyWallet` recovers the signer over: [1](#0-0) 

and only enforces: [2](#0-1) 

The `EMPORIUM_SIGNATURE_TYPEHASH` itself excludes `feeToken` and `variableRate` entirely: [3](#0-2) 

Yet the actual token debited from the wallet is taken from `circomData.feeStructure.feeToken`, which is supplied by whoever submits the `transact` call (the relay/off-chain client), not the wallet owner who signed: [4](#0-3) 

When `signerAddress != address(0)` (the "Stateful Interaction"/wallet-fee-payment case), the fee is pulled straight from the wallet's own token balance via `doSendToRelay`, not from a shielded UTXO delta protected by the ZK proof's `calldataHash`/`signedMessageHash` binding: [5](#0-4) [6](#0-5) 

Note that while `feeStructure` is included in the `calldataHash` used by the *EdDSA-signed shielded transaction* (`getHashedCalldata2` / `getSignedMessageHash` in `CircomDataBuilder.sol`), that binding protects the shielded-account owner's spending key signature, not the separate `stack.signerAddress`/wallet EIP-712 signature that authorizes `doSendToRelay`. The wallet's own signature never commits to `feeToken`: [7](#0-6) 

Because the numeric cap (`maxFee`) is checked against `flatFee` regardless of which ERC-20 it is denominated in, an attacker (the relay/caller assembling `circomData`, who is unprivileged with respect to the wallet's key) can present the same signed `maxFee` value but set `feeToken` to a different, more valuable, or differently-decimaled token than the one the wallet owner intended when signing. `doSendToRelay` then transfers that amount of the attacker-chosen token out of the wallet — an asset movement the wallet owner never actually authorized in that currency.

### Impact Explanation
This lets an unprivileged relay/caller move wallet funds in a token the wallet owner never approved paying fees in, extracting value disproportionate to what the signed `maxFee` was meant to bound (e.g., signing `maxFee = 5` intending 5 USDC, but the relay sets `feeToken` to a token with fewer decimals or higher value, draining far more value than intended). This is "executing calls or moving assets a wallet owner or prover never authorised" — a High-impact category per the assessment rules.

### Likelihood Explanation
The bar to trigger this is low: whoever submits the `transact()`/`runAction` call (typically the relay, which is explicitly treated as an untrusted/unprivileged submitter here per the "no relayer trust assumptions" scope) controls `circomData.feeStructure.feeToken` at call time, independent of the wallet owner's earlier off-chain EIP-712 signature. No admin or owner key is required — only the ability to submit the transaction with a chosen `feeToken`, which is a standard capability of any relay/caller in this flow.

### Recommendation
Include `feeToken` (and `variableRate`, if it can also apply in this path) inside `EMPORIUM_SIGNATURE_TYPEHASH` so the wallet owner's signature cryptographically commits to the exact currency and rate the fee will be charged in, not just a numeric cap. Alternatively, restrict `feeToken` in the wallet-fee-payment path to a value fixed by the wallet/protocol rather than caller-suppliable `circomData`.

### Proof of Concept
1. Wallet owner signs an `EmporiumSignature` with `ops`, `maxFee = X`, `deadline`, intending fee to be paid in `USDC` (as communicated off-chain/by convention), producing `hashedMessage`/signature per `EmporiumUpgradeable.sol:318-328`.
2. Relay (unprivileged caller) constructs `circomData` for `Hinkal.transact()` → `_externalTransact()` → `EmporiumUpgradeable.runAction()`, setting `circomData.feeStructure = {feeToken: <some other token TKX>, flatFee: X, variableRate: ...}`. The check at `EmporiumUpgradeable.sol:346-348` only verifies `flatFee <= maxFee` numerically and passes.
3. `verifyWallet` recovers the signature successfully because the signed struct never referenced `feeToken` — signature validity is unaffected by the swapped token.
4. `payRelayFees` → `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, X, TKX)` executes, transferring `X` units of `TKX` (not `USDC`) out of the wallet to the relay — `EmporiumUpgradeable.sol:186-199, 262-282`.
5. If `TKX` is worth substantially more than `USDC` per unit (or has fewer decimals), the wallet loses far more value than the owner intended when bounding the fee to `X`.
