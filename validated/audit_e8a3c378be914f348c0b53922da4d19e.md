### Title
Unvalidated swap routes can execute malicious venue code under the caller's authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller forwards caller-supplied opaque `swap` bytes to the configured router without constraining the contracts that the route can invoke, while running inside the account owner's authorization tree. A malicious venue referenced by the route can therefore add unrelated token transfers beneath the caller's signed `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization and drain wallet assets outside the funds needed for the lending strategy.

### Finding Description
`swap_tokens` decodes nothing from `swap`; it snapshots the controller's input and output balances, authorizes exactly one controller-to-router input transfer, and invokes `router.execute_strategy(&controller, &amount_in, swap)`. [1](#0-0) 

The public strategy entrypoints accept the route as caller-controlled `swap: Bytes`; for example, `swap_collateral` takes `caller`, `account_id`, `current`, `amount`, `new`, and `swap`. [2](#0-1) 

The controller's post-call checks only bound the router's spending of `token_in` and require a positive increase in `token_out`; they do not restrict nested calls made by contracts selected inside the opaque route. [3](#0-2) 

Because venue calls remain inside the original transaction, malicious venue code can request authorization from the account owner and have that invocation recorded as a child of the owner's strategy authorization; if the wallet signs the displayed tree, the unrelated transfer executes even though the controller only intended to authorize the strategy input.

### Impact Explanation
An attacker can steal unrelated tokens held by the strategy caller, not merely the collateral or debt amount routed through the strategy. The amount is bounded by the victim's wallet balances and signed authorization rather than by the controller's `amount_in`, measured output, or final health-factor checks.

### Likelihood Explanation
The attacker must persuade a user or automated client to submit a malicious route and sign the resulting authorization tree, but no protocol privilege, leaked key, oracle manipulation, or compromised router is required. The attack is especially relevant where clients treat `swap` as opaque quote data instead of decoding every reachable venue and auditing the simulated authorization tree.

### Recommendation
Decode route payloads before execution and reject routes containing venues, token contracts, or pool contracts outside an explicit allowlist. Independently, wallets and SDKs should simulate the exact transaction and reject any authorization tree containing child invocations beyond the expected input transfer and strategy call. Longer term, prefer a route format in which every externally invoked contract is enumerated and validated before the router is invoked.

### Proof of Concept
1. The victim owns a solvent lending account and holds an unrelated token `T` in their wallet.
2. The attacker deploys a contract exposing the venue-compatible swap call expected by the router, but that call invokes `T.transfer(victim, attacker, balance)` before returning enough output for the route to satisfy its minimum.
3. The attacker supplies a `swap` payload that reaches the malicious contract.
4. The victim calls `swap_collateral(caller = victim, account_id = victim_account, current = current_market, amount = amount, new = new_market, swap = malicious_route)`. [2](#0-1) 
5. The controller authorizes only its intended `token_in.transfer(controller, router, amount_in)` and passes the opaque route onward. [4](#0-3) 
6. During route execution, the malicious venue requests `T.transfer(victim, attacker, balance)`; simulation records it beneath the victim's strategy authorization, and signing the poisoned tree makes the theft atomic with the swap.
7. The swap can still satisfy the controller's bounded-input and positive-output checks, so the transaction succeeds after the unrelated wallet transfer. [3](#0-2)
