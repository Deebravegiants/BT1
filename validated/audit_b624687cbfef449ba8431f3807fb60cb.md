### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`) purely from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. This breaks the binding `hmac(secret, signed_bytes) == hmac(secret, bytes_that_determine_identity)`, letting anyone who can obtain one genuinely-signed webhook (e.g., by installing the app on their own shop) replay it with a forged shop identity and have it accepted as coming from a different (victim) merchant.

### Finding Description
The identity binding that must hold is:
`shop_used_by_handler == shop_that_HMAC_actually_authenticates`

In this gem, that equality is broken:

- `Request#to_signable_string` returns only `@raw_body`, i.e., the HMAC signs the JSON body and nothing else. [1](#0-0) 

- `Request#shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of the signed bytes. [2](#0-1) 

- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body) and compares it to the received `hmac`; it never touches the shop header at all. [3](#0-2) 

- `Registry.process` validates the HMAC and then forwards `request.shop` directly to the host application's handler as the trusted merchant identity for that webhook payload. [4](#0-3) 

Because `shop` is excluded from `to_signable_string`, an attacker who legitimately installs the app on their own shop receives a genuinely HMAC-signed webhook (body + valid signature) from Shopify for their own tenant. The attacker can then re-deliver that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim's `myshopify.com` domain. `HmacValidator.validate` still succeeds — because the signature never depended on that header — and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

This exactly parallels the H-1 pattern: a value that downstream logic treats as authoritative (`bull`/shop identity) is not actually constrained by the check that is supposed to authenticate the request (the order hash/HMAC), so an attacker-crafted value flows through unguarded.

### Impact Explanation
Any consumer of this gem that uses `WebhookMetadata#shop` to determine which tenant/merchant a webhook's data belongs to (exactly as shown in this gem's own documented example, which passes `shop_domain: data.shop` downstream) is exposed to cross-tenant data injection: attacker-controlled webhook payloads can be attributed to and processed against a victim shop's account/session. This is a cross-tenant access impact, since a single malicious app install can forge events for merchants who never interacted with the attacker.

### Likelihood Explanation
The prerequisite is only an "unprivileged internet user" capability: install the app (or otherwise obtain one valid signed webhook for any shop) and replay the request with a modified header to the app's single public webhook endpoint. No access token, `client_secret`, or privileged credentials of the target shop are needed, and no host-application misuse beyond following this gem's own documented `data.shop` usage pattern is required.

### Recommendation
Include the shop identity (and ideally topic) in the HMAC-signed material, or otherwise cryptographically bind the `X-Shopify-Shop-Domain` header to the signature before it is trusted — e.g., verify the domain against previously known/authorized shops for the given HMAC, or require the host app to independently authenticate `data.shop` against its own session store before acting on it. At minimum, update `Request#to_signable_string`/`HmacValidator` so an attacker cannot swap `shop` while keeping a previously-issued valid HMAC.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, triggering a real webhook, e.g. `orders/create`, with body `B` and Shopify computing `HMAC = hmac(api_secret_key, B)` per Shopify's real signing.
2. Shopify POSTs to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: HMAC`, and body `B`.
3. Attacker captures this request (it's their own shop, so they can freely trigger and observe it) and resends it to the same endpoint, only changing the header to `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and `HMAC` identical.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `hmac(api_secret_key, B)` — unchanged — and matches the supplied `HMAC`, so validation passes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"` and attacker-controlled body `B`, which any host app following this gem's documented pattern will process as an event belonging to the victim shop.
