### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows the CSRF `state` nonce and OAuth authorization request to be redirected to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth "authorize" redirect URL directly from the caller-supplied `shop` string without ever validating it against `ShopifyAPI::Utils::ShopValidator`, unlike every other flow in the gem that accepts a `shop` string.

### Finding Description
`begin_auth` takes an unauthenticated, caller-supplied `shop` and feeds it straight into `auth_base_uri(shop)`, which becomes the host of the OAuth "authorize" redirect: [1](#0-0) 

`auth_base_uri` does no domain restriction beyond an internal dev-server special case; any string is turned into `https://#{shop}/admin`: [2](#0-1) 

The generated `auth_route` embeds `client_id`, the requested `scope`, the app's `redirect_uri`, and, most importantly, the freshly generated anti-CSRF `state` nonce (which is simultaneously placed in a cookie returned to the caller): [3](#0-2) 

Compare this to the other credential-issuing flows in the gem, which all sanitize the `shop`/host before using it: `ShopifyAPI::Auth::TokenExchange`, `ShopifyAPI::Auth::ClientCredentials`, `ShopifyAPI::Auth::RefreshToken`, and the storefront GraphQL client all reference `ShopifyAPI::Utils::ShopValidator.sanitize!`, which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [4](#0-3) 

`begin_auth`/`Oauth` is the only OAuth entry point in the gem that never calls `ShopValidator`. The identity binding that is broken is: *the host that receives the CSRF `state` nonce and OAuth parameters* should equal *a genuine Shopify domain*, but the gem never enforces this equality for `begin_auth`.

Because the host application typically derives `shop` directly from an unauthenticated query parameter on its login route (as shown in the gem's own docs, `shop = request.headers["Shop"]`), an unauthenticated internet user can supply an attacker-controlled value for `shop` and cause the app to:
1. Set the legitimate anti-CSRF `state` cookie in the victim's browser (chosen by the app, not the attacker).
2. Redirect the victim's browser to `https://<attacker-domain>/admin/oauth/authorize?...&state=<nonce>&client_id=...`, leaking the `state` nonce, `client_id`, and configured `redirect_uri`/`scope` to the attacker's server.

An attacker who receives this `state` value can then complete a legitimate OAuth authorization for a shop they control (or an app install flow) and redirect Shopify's real, HMAC-signed callback to the victim's callback endpoint using the leaked `state`, matching the cookie set on the victim's browser in step 1. Because `Oauth.validate_auth_callback` accepts any `state` that matches the cookie, and does not otherwise bind the callback to the original login attempt beyond that shared nonce, this enables a forced OAuth completion / session fixation: the victim's browser session ends up bound to the attacker's Shopify session inside the app, all without the attacker ever needing the app's `client_secret` or the victim's credentials. [5](#0-4) 

### Impact Explanation
This is a forced OAuth completion / session-fixation primitive reachable by any unauthenticated user who can get a victim to click a crafted login link on the host application (the standard `shop` query parameter pattern shown in the gem's own docs). It requires no possession of `api_secret_key`, access tokens, or any privileged account, and it crosses a tenant boundary by binding the victim's app session to a shop chosen by the attacker. This matches the "session fixation or forced OAuth completion" High-impact category.

### Likelihood Explanation
Exploitability depends on the host application passing an unauthenticated, attacker-influenced `shop` value straight into `begin_auth` (a very common integration pattern per the gem's documented usage, e.g. reading `shop` from a request header/query param before any Shopify-side validation has occurred), and on the app not independently sanitizing `shop` before calling `begin_auth`. Given `ShopValidator` exists in this gem specifically for this purpose and is used by sibling flows (`TokenExchange`, `ClientCredentials`, `RefreshToken`, storefront client) but is conspicuously absent from `Oauth.begin_auth`, this looks like an inconsistency/gap rather than an intentional design choice.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `Oauth.begin_auth`, restricting `shop` to `TRUSTED_SHOPIFY_DOMAINS` before it is used to construct `auth_base_uri`, mirroring the validation already performed in `TokenExchange`, `ClientCredentials`, and `RefreshToken`.

### Proof of Concept
1. Host application exposes `/auth?shop=<value>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`, per the gem's documented pattern.
2. Attacker sends victim a link: `https://victim-app.example.com/auth?shop=attacker-controlled.example`.
3. `begin_auth` sets the CSRF `state` cookie on the victim's browser and returns `auth_route = "https://attacker-controlled.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://victim-app.example.com/auth/callback&state=<nonce>"`.
4. Victim's browser is redirected to the attacker's server, leaking `state`, `client_id`, and `redirect_uri`.
5. Attacker uses the leaked `state` to complete a real OAuth authorization against Shopify for an attacker-controlled shop, causing Shopify to redirect to `https://victim-app.example.com/auth/callback?...&state=<nonce>&hmac=<valid-Shopify-signed-hmac>`.
6. `Oauth.validate_auth_callback` sees a valid Shopify HMAC and a `state` matching the victim's cookie, and creates/stores a session for the attacker's shop inside what the victim believes is their own authenticated app session. [1](#0-0) [5](#0-4)

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
