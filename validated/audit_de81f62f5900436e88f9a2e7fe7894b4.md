## Analysis

The joserfc report's core defect is a single attacker-controlled magnitude value (`p2c`) that drives proportional CPU cost, with **no upper bound enforced**, consumed **before** any authentication of the sender. The closest reachable analog in Hyperbridge is `pallet-ismp`'s unsigned message-batch entry point, which has the same two properties: an unbounded attacker-controlled batch size that drives real computation cost, and a **fixed, size-independent declared weight**, executed by every network node during unauthenticated mempool validation.

### Title
Unbounded `handle_unsigned` message-batch size with a fixed constant weight enables unauthenticated CPU-exhaustion DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an attacker-controlled `Vec<Message>` batch, but is annotated with a static weight, `weight()`, that returns `Weight::from_parts(300_000_000, 0)` regardless of how many messages, requests, or nested proof elements the batch contains. [1](#0-0)  Because this is an **unsigned** extrinsic, `ValidateUnsigned::validate_unsigned` runs the entire batch through `Self::execute(messages.clone())` — full proof verification and state-transition logic for every message — on every node that receives the gossiped extrinsic, before any fee is paid or block inclusion occurs. [2](#0-1) 

### Finding Description
`execute()` maps `handle_incoming_message` over the entire submitted `messages` vector with no cap on its length or on the size of nested collections inside each message (e.g., `requests`, `votes`, ancestry proofs, merkle-multiproof arrays decoded from SCALE-encoded call data). [3](#0-2)  This mirrors the PBES2 flaw exactly: a caller-supplied magnitude (batch/array length, standing in for `p2c`) directly and proportionally drives the amount of expensive cryptographic and merkle-proof work performed, with no validation that the magnitude is bounded to a sane maximum.

The `#[pallet::weight(weight())]` annotation is a compile-time constant, not a function of `messages.len()` or any per-message field, so the runtime's weight-metering — the mechanism that is supposed to make computational cost proportional to declared/charged cost — is completely decoupled from the actual cost incurred. Unlike EVM code paths in this repo where an oversized array simply exhausts the block gas limit and reverts cleanly, here the expensive work happens in `validate_unsigned`, which executes **before** block inclusion, during transaction-pool validation, run by every full node that receives the extrinsic over the network — this is the direct analog of the JWE `p2c` iterations running before any authentication.

### Impact Explanation
An unauthenticated party (no signature is required — `ensure_none(origin)` is the only origin check) [4](#0-3)  can construct a single `handle_unsigned` call whose `messages` field packs a large number of requests/responses/timeouts or a consensus message with maximally-sized nested proof structures. Every node that receives this extrinsic over the p2p transaction-gossip layer performs full ISMP message execution (state proof verification, hashing, membership checks) inside `validate_unsigned` for free, with the pallet's weight system reporting a flat, negligible cost (`300_000_000`) irrespective of the true cost. Repeated submission of such batches can degrade validation throughput network-wide — a resource-exhaustion Denial of Service against the message-dispatch path itself, reachable from a single relayed/dispatched message as required by scope.

### Likelihood Explanation
This is directly reachable by any relayer or dispatcher with network access — no privileged role, key compromise, or governance action is needed, matching the "unprivileged message dispatcher/relayer" reachability requirement. The batch size and nested-proof sizes are fully attacker-chosen at the SCALE-encoding layer, bounded only by the node's generic max-extrinsic-size limit rather than by any ISMP-specific cap tied to the declared weight.

### Recommendation
Compute `weight()` as a function of the actual batch content (e.g., `messages.len()` plus per-message-type benchmarked cost for nested collections such as `requests`, `votes`, `ancestry`, and proof node counts) rather than a fixed constant, and enforce a maximum batch size/nested-collection size in `validate_unsigned` before `Self::execute` is invoked, rejecting oversized batches early and cheaply (mirroring the `MAX_PROOF_DEPTH` and `MaxCallSize` patterns already used elsewhere in this codebase, e.g. `modules/consensus/pharos/primitives/src/spv.rs` and `modules/pallets/call-decompressor/src/lib.rs`).

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned` extrinsic whose `messages: Vec<Message>` contains many `Message::Request`/`Message::Response` entries, each with maximally-sized `requests`/proof fields, packed up to the node's extrinsic-size limit.
2. Submit it as an unsigned transaction to a Hyperbridge node's transaction pool.
3. Observe that `ValidateUnsigned::validate_unsigned` calls `Self::execute(messages.clone())`, which performs full state-proof/membership verification for every entry [5](#0-4)  — consuming CPU/time proportional to the attacker-chosen batch size — while the call's declared weight remains the fixed `300_000_000` regardless of batch content. [6](#0-5) 
4. Repeat submission from multiple source accounts/peers to amplify load across the network's mempool-validating nodes.

```rust
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
```
