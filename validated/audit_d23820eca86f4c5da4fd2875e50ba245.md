## Title
Silent Zero-Share Minting in `pool_u64::buy_in` Corrupts Custody Accounting in `staking_contract` and `vesting` Distribution Pools - (File: aptos-move/framework/aptos-stdlib/sources/pool_u64.move)

### Summary
`pool_u64::buy_in` is the shared share-accounting primitive used by `staking_contract.move` (for commission and unlock distributions) and `vesting.move` (for grant pools) to track claims on real, custody-held APT. Like the external report's unchecked `targetVault.deposit`, `buy_in`'s return value (new shares minted) is never validated by any of its callers, and the function itself can silently accept a non-zero `coins_amount` into `total_coins` while minting **zero shares** due to integer-division rounding.

### Finding Description
In `pool_u64::buy_in`: [1](#0-0) 

```
public fun buy_in(self: &mut Pool, shareholder: address, coins_amount: u64): u64 {
    if (coins_amount == 0) return 0;
    let new_shares = self.amount_to_shares(coins_amount);
    ...
    self.total_coins += coins_amount;   // real value credited to the pool
    self.total_shares += new_shares;    // may be 0 even though coins_amount > 0
    self.add_shares(shareholder, new_shares);
    new_shares
}
```

`amount_to_shares` computes `coins_amount * total_shares / total_coins` once the pool is non-empty, which rounds down to `0` whenever `coins_amount` is small relative to the existing `total_coins`/`total_shares` ratio (demonstrated by the framework's own test `test_buy_in_with_small_coins_amount`, which shows a depositor of `1` coin can receive a real credited share while an even smaller relative amount would round to `0`). [2](#0-1) 

When `new_shares == 0`, `add_shares` does not register the depositor as a shareholder at all if they weren't already one: [3](#0-2) 

Yet `total_coins` has already been permanently incremented by the real `coins_amount`. That value is not lost from the pool, but it is not attributed to anyone — it silently redistributes to the *other* existing shareholders (since their unchanged shares now represent a larger `total_coins`), while the depositor who contributed real custody value receives nothing in return and no error.

This exact `buy_in` return value is never checked by any of its custody-relevant callers:
- `staking_contract::add_distribution`, which credits commission/unlock amounts (real AptosCoin held in the resource-account-backed stake pool) to `distribution_pool.buy_in(recipient, coins_amount)`: [4](#0-3) 
- `vesting::create_vesting_contract`, which builds each shareholder's claim on the deposited `AptosCoin` grant via `pool_u64::buy_in`: [5](#0-4) 

None of these call sites assert `new_shares > 0`, mirroring precisely the unchecked-return-value pattern in the external report (`targetVault.deposit(...)` never validated for non-zero shares).

### Impact Explanation
`total_coins` and `total_shares` are the accounting fields that determine how much real APT (held under the staking-contract's resource account / stake pool, or the vesting contract's resource account) each shareholder can later redeem via `redeem_shares`. If a `buy_in` silently mints zero shares for a non-zero coin contribution, the depositor's contribution becomes non-recoverable — they hold no share claim to reclaim it, while the funds remain custodied in the pool and get redistributed pro-rata to the other existing shareholders (or the operator/staker on the other side) without their consent or accounting. This is a custody accounting corruption that moves value to the wrong holder and destroys the depositor's recovery rights over real, mainnet-relevant APT.

### Likelihood Explanation
This requires a `total_coins`/`total_shares` ratio and a `coins_amount` small enough to round to zero shares, which becomes increasingly likely for pools that have accrued large `total_coins` relative to `total_shares` over long-running staking or vesting periods, or for callers who trigger `buy_in` with very small residual amounts (e.g., small dust unlock/commission amounts in `add_distribution`, or a shareholder configured with a tiny `buy_in` grant relative to co-shareholders in `create_vesting_contract`). It does not require any privileged action or malicious actor — it is triggered by ordinary usage patterns and rounding, matching the "certain edge cases" framing of the external report.

### Recommendation
Have `pool_u64::buy_in` assert that a non-zero `coins_amount` yields a non-zero `new_shares` (or explicitly document/refund/round up in that case), and have callers such as `staking_contract::add_distribution` and `vesting::create_vesting_contract` validate the returned share count before proceeding, analogous to the recommended `require(sharesReceived > 0, ...)` pattern in the external report.

### Proof of Concept
Not independently executed against the live framework; the zero-share-mint-on-nonzero-deposit behavior is inferable directly from `pool_u64::amount_to_shares`'s integer division and confirmed conceptually by the framework's own `test_buy_in_with_small_coins_amount` test showing rounding-to-near-zero balances for small deposits, but I did not verify a concrete end-to-end runnable Move test reproducing `new_shares == 0` with `coins_amount > 0` through `staking_contract` or `vesting`. This would require constructing a pool with a specific `total_coins`/`total_shares` ratio (e.g., `total_shares = 1`, `total_coins = large_N`) and calling `buy_in` with `coins_amount < total_coins/total_shares`, then observing `total_coins` increase while `shareholders_count()`/`shares(depositor)` remain unchanged — this exact scenario is not present as an existing test in the codebase and should be added by a Devin agent to confirm before treating this as fully proven.

    /// Allow an existing or new shareholder to add their coins to the pool in exchange for new shares.
    public fun buy_in(self: &mut Pool, shareholder: address, coins_amount: u64): u64 {
        if (coins_amount == 0) return 0;

        let new_shares = self.amount_to_shares(coins_amount);
        assert!(MAX_U64 - self.total_coins >= coins_amount, error::invalid_argument(EPOOL_TOTAL_COINS_OVERFLOW));
        assert!(MAX_U64 - self.total_shares >= new_shares, error::invalid_argument(EPOOL_TOTAL_COINS_OVERFLOW));

        self.total_coins += coins_amount;
        self.total_shares += new_shares;
        self.add_shares(shareholder, new_shares);
        new_shares
    }

    fun add_shares(self: &mut Pool, shareholder: address, new_shares: u64): u64 {
        if (self.contains(shareholder)) {
            let existing_shares = self.shares.borrow_mut(&shareholder);
            let current_shares = *existing_shares;
            assert!(MAX_U64 - current_shares >= new_shares, error::invalid_argument(ESHAREHOLDER_SHARES_OVERFLOW));

            *existing_shares = current_shares + new_shares;
            *existing_shares
        } else if (new_shares > 0) {
            assert!(
                self.shareholders.length() < self.shareholders_limit,
                error::invalid_state(ETOO_MANY_SHAREHOLDERS),
            );

            self.shareholders.push_back(shareholder);
            self.shares.add(shareholder, new_shares);
            new_shares
        } else {
            new_shares
        }
    }

    public entry fun test_buy_in_with_small_coins_amount() {
        let pool = new(2);
        // Shareholder 1 buys in with 1e17 coins.
        pool.buy_in(@1, 100000000000000000);
        // Shareholder 2 buys in with a very small amount.
        assert!(pool.buy_in(@2, 1) == 1, 0);
        // Pool's total coins increases by 20%. Shareholder 2 shouldn't see any actual balance increase as it gets
        // rounded down.
        let total_coins = pool.total_coins();
        pool.update_total_coins(total_coins * 6 / 5);
        // Minus 1 due to rounding error.
        assert!(pool.balance(@1) == 100000000000000000 * 6 / 5 - 1, 1);
        assert!(pool.balance(@2) == 1, 2);
        pool.destroy_pool();
    }
