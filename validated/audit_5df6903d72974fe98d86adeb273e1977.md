### Title
Webhook shop identity is trusted from an unauthenticated header while only the request body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`) that gets handed to the app's webhook handler from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` checks only covers the raw request body. This breaks the intended binding "the shop the HMAC was computed for" == "the shop the handler is told the event belongs to," analogous to the reported Atlas issue where a value used for a security-relevant decision (bid token) was never cross-checked against the value that was actually authenticated.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (a header value that was never authenticated) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms the signature is computed only from `verifiable_query.to_signable_string`, i.e. the body, using `Context.api_secret_key`: [4](#0-3) 

The equality that should hold, but is not enforced, is:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`

Because the header is outside the signed material, any two (body, HMAC) pairs that are valid for *some* shop remain valid regardless of which `shop`-domain header accompanies them.

### Impact Explanation
An external, unprivileged party who can obtain any single valid `(raw_body, hmac)` pair for the target app - for example, by installing the app on their own shop and capturing one legitimate webhook delivery, since Shopify's own webhook signing scheme is documented to only ever cover the body, not headers - can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a different shop. `Registry.process` will pass HMAC validation and invoke the registered handler with a `WebhookMetadata` whose `shop` is the attacker-chosen value, not the shop for which the payload/signature was actually issued. Any host application that uses `WebhookMetadata#shop` to select which tenant's records to update, uses it as a trust boundary, or logs/acts on it as an authenticated tenant identifier is exposed to cross-tenant data confusion/corruption - the underlying vulnerability class here maps to "Cross-tenant access" under the accepted impact list, since the app is tricked into attributing a cryptographically-valid event to the wrong merchant.

### Likelihood Explanation
The only prerequisite is possession of one legitimate webhook body+HMAC pair for the target app (obtainable without any special privilege by simply installing the app on an attacker-controlled shop, which is the normal, unprivileged install flow of any Shopify app) and the ability to POST to the app's public webhook receiver with custom headers, which is trivial for any internet client. No `api_secret_key`, access token, or other privileged credential is required to mount the attack itself (only to have installed the app once, which any developer/merchant can do).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signable material, or otherwise cryptographically bind them to the body before validation - e.g. append/prepend the header values to the string that `to_signable_string` returns so `HmacValidator.validate` fails whenever the header values are altered. Alternatively, require host applications to independently look up/verify that the shop asserted in the webhook actually has an active session/access token before trusting `WebhookMetadata#shop`, and document this requirement clearly since the gem currently exposes the unauthenticated header value as if it were authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development shop (`attacker-shop.myshopify.com`), a normal unprivileged action.
2. Attacker captures one legitimate webhook delivery: raw body `B` and its valid `shopify-hmac-sha256` header `H` (computed by Shopify using the app's `api_secret_key`, which attacker never sees but doesn't need to).
3. Attacker sends a new HTTP POST to the app's public webhook endpoint with:
   - body = `B`
   - `shopify-hmac-sha256` = `H` (unchanged, still valid because HMAC only covers `B`)
   - `shopify-shop-domain` = `victim-shop.myshopify.com` (any other installed shop, or a plausible guessed domain)
   - `shopify-topic`, `shopify-webhook-id` optionally altered too, since none are covered by `H`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., the app processes an event as if it originated from `victim-shop.myshopify.com`, even though the cryptographic proof only ever authenticated the body content for `attacker-shop.myshopify.com`'s original delivery.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
