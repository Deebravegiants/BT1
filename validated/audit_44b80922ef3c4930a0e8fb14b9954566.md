### Title
Spending authority stays bound to the original minter after position-NFT transfer — previous owner can keep borrowing and withdrawing a sold account - (File: contracts/controller/src/account.rs)

### Summary
The controller checks borrow/withdraw/strategy authority against the `owner` field stored inside the `Account` record, which is written once at mint time and never updated when the position NFT changes hands. Owner-only maintenance (`add_delegate`, `remove_delegate`, `renew_account`) instead reads the live NFT owner via `storage::account_owner`. After an NFT `transfer`/`transfer_from`, the stored owner diverges from the real owner: the seller retains full spending authority over an account they no longer own, while the buyer cannot spend at all.

### Finding Description
`create_account_with` stamps `Account { owner: owner.clone(), .. }` where `owner` is the caller at mint time, and persists it in the account record (`contracts/controller/src/account.rs:64-71`). Every economically dangerous gate then compares the caller against that stored field:

- `is_owner_or_delegate` / `require_owner_or_delegate` use the `owner` argument passed as `&account.owner` (`account.rs:115-140`). Delegates are looked up under `storage::get_delegates(env, account_id, owner)` with the same stale key (`account.rs:126`).
- `process_withdraw` calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` and then pays out to `to.unwrap_or(caller)` (`contracts/controller/src/positions/supply.rs:147-157`). Borrow, multiply, flash_position, swap_debt, swap_collateral, repay_debt_with_collateral and migrate_from_blend take the same `&account.owner` path (`account.rs:101-108`, `contracts/controller/src/strategies/repay_debt_with_collateral.rs:51`).
- In contrast, `require_account_owner` resolves the live owner through `storage::account_owner(env, account_id)` (the NFT `owner_of` read, see `contracts/controller/src/external/position_nft.rs`) and is used only by delegate management and renewal (`account.rs:143-148`, `account.rs:217-250`).

The position NFT is the stock OpenZeppelin enumerable token; `transfer`/`transfer_from` only `require_auth` the current holder and write NFT storage (`scripts/permissionless_entrypoints.txt:111-114`). There is no hook back into the controller, and no controller code path rewrites `account.owner` after creation — grepping `contracts/controller/src` shows `account.owner` is read in many places but written only in `create_account_with`. The docs themselves assume the NFT holder is the controller of the account ("The position NFT holder controls the lending account", `docs/explanation/threat-model.md:77`) and that delegate grants "become inactive under another owner" (`docs/reference/invariants.md:36-38`), which only holds if `owner` tracks the NFT — it does not.

### Impact Explanation
Theft of user funds and permanent freezing of funds. After selling or transferring the NFT for an account holding collateral (e.g., via an OTC/account sale, since the NFT carries the whole position), the previous owner — still `account.owner` — calls `withdraw(caller=old_owner, account_id, withdrawals, to=Some(old_owner))` or `borrow` to an arbitrary `to`, passing `require_owner_or_delegate` trivially since `caller == account.owner`. Post-pool solvency does not protect the victim: borrowing to the LTV limit then leaving the account, or withdrawing all free collateral, transfers the account's value to the seller. Simultaneously the new NFT holder fails every `require_owner_or_delegate` check (their address never equals the stored owner, and any delegates they add via `add_delegate` are keyed under their live address — `storage::add_delegate(env, account_id, caller, delegate)` — a different key than the stale `account.owner` used at check time), so the buyer cannot withdraw a single unit: their collateral is permanently frozen until the previous owner chooses to act. Liquidation remains the buyer's only exit and it pays a bonus to a third party.

### Likelihood Explanation
Any unprivileged address can trigger this by design of the NFT: `position-nft::transfer` and `transfer_from` are in-scope reachable entrypoints (`position-nft::transfer`, `transfer_from`, `approve`, `approve_for_all` per `scripts/permissionless_entrypoints.txt:111-114`), and account sale/gift is a normal operation. No privileged role, oracle manipulation, or timing race is required — a single `transfer` followed by `withdraw`/`borrow` from the old owner executes the theft atomically across two transactions (or one via a contract caller). The same stale owner also keeps any previously added delegate grants permanently active, since they were recorded under the old owner's key and that key remains the one consulted forever.

### Recommendation
Make the spending gate read live NFT ownership, matching `require_account_owner`: inside `require_owner_or_delegate`/`is_owner_or_delegate`, resolve `owner` via `storage::account_owner(env, account_id)` (NFT `owner_of`) rather than trusting the stored `Account.owner` field, and key `storage::get_delegates` to that live owner — this also makes the documented "grant inactive under another owner" invariant (`INV-AUTH-02`) actually hold. Alternatively, drop `owner` from `Account` entirely so it can never go stale, and update `load_or_create_account`, `process_withdraw`, `process_borrow`, and every strategy guard to resolve the owner at call time.

### Proof of Concept
1. Alice calls `supply(caller=Alice, account_id=0, spoke_id=1, assets=[(USDC_key, 1000e7)])` → account `A` created; `Account.owner = Alice`; NFT `A` minted to Alice (`account.rs:62-73`).
2. Alice sells/gifts the account: `position_nft.transfer(Alice, Bob, A)` — authorized by Alice's `require_auth`, no controller involvement.
3. Bob now holds NFT `A`. `storage::account_owner(A)` returns Bob, but the stored `Account.owner` is still Alice.
4. Alice calls `borrow(caller=Alice, account_id=A, borrows=[(ETH_key, X)], to=Some(Alice))`. `require_owner_or_delegate` compares `caller == account.owner` → Alice == Alice → passes (`account.rs:121-122`, `supply.rs:147-150` analog for borrow). Post-borrow solvency passes up to LTV; the pool pays ETH to Alice.
5. Alice repeats `withdraw` for all free collateral. Bob's NFT now wraps a maximally leveraged/drained account; any `withdraw` Bob attempts reverts `NotAuthorized` since Bob ≠ stored `account.owner`, and `clean_bad_debt`/`liquidate` only crystallize his loss.

Caveat I could not fully verify within the index: whether `storage::get_account` re-derives `Account.owner` from the NFT at load time. `storage/account.rs` reads were not all visible; however the separate `storage::account_owner` live-read helper and its selective use in `require_account_owner` (rather than in `require_owner_or_delegate`) indicate the two sources are distinct by construction.
