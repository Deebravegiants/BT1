### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator` verifies the HMAC exclusively against that body [1](#0-0) . The `shop` attribute, however, is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header and is never included in the signed content [2](#0-1) . `Registry.process` accepts the request once the body-only HMAC passes, then forwards the untrusted `request.shop` value directly to the app's webhook handler as the tenant identifier [3](#0-2) .

### Finding Description
The gem's webhook authenticity check is: `HMAC(body, api_secret_key) == received_hmac`, computed in `HmacValidator.validate_signature` [4](#0-3) . Because `api_secret_key` is the same secret across every shop that has installed the app, and the `shop` header is not part of the signed payload, `(body, hmac)` is a valid pair for **any** shop header value.

Equality that should hold but does not: `shop_bound_by_hmac == shop_used_by_handler`. In reality, `shop_used_by_handler = request.shop` (attacker-controlled header) while `shop_bound_by_hmac = ∅` (the HMAC signs no shop identity at all).

An attacker who has installed the app on their own (free/dev) store is a legitimate recipient of real webhook deliveries for that store — obtainable via the app's own webhook endpoint traffic, Shopify's delivery logs/CLI (`shopify webhook trigger`), or their own tunnel (e.g., ngrok) used during normal app testing. This gives them a completely valid `(raw_body, hmac-sha256)` pair signed with the app's shared secret. They can then send this exact body+hmac to the app's public webhook endpoint while replacing only the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches to the handler with `WebhookMetadata` claiming the victim's shop [5](#0-4) .

### Impact Explanation
This is a cross-tenant identity confusion at the gem's authentication boundary: the primitive that is supposed to prove "this event genuinely originates from shop X" (the HMAC) proves nothing about `X`. Any downstream app logic that trusts `WebhookMetadata#shop` to look up the correct tenant's stored access token/session, update per-shop state, or attribute data will act on attacker-controlled webhook bodies under the identity of an arbitrary victim shop — a cross-tenant access condition.

### Likelihood Explanation
Exploitation requires only: (1) installing the app once on any shop the attacker controls (trivial, free), (2) observing one webhook delivery's raw body and HMAC header (available via standard dev tooling), and (3) replaying an HTTP POST to the app's known webhook URL with a modified `shop-domain` header. No access token, no `api_secret_key` knowledge, and no TLS interception of third-party traffic is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed content, or otherwise cryptographically bind the `shop` header to the HMAC before trusting it — e.g., verify `request.shop` against a per-shop stored value (like an installed offline access token) before processing, rather than trusting the header solely because the body-only HMAC validated.

### Proof of Concept
1. Install the app on an attacker-controlled dev store `attacker-shop.myshopify.com`.
2. Trigger any webhook topic (e.g. `orders/create`) and capture the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header value delivered to the app's endpoint.
3. Send a new HTTP POST to the same app webhook endpoint with:
   - Body: the exact captured `raw_body`
   - `X-Shopify-Hmac-Sha256`: the exact captured hmac
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (any other shop)
   - `X-Shopify-Topic`: same topic
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate(request)` returns `true` (body/hmac match), and `Registry.process` invokes the registered handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [3](#0-2) , even though the event never originated from that shop.
