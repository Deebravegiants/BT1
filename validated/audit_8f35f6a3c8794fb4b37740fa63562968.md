### Title
Permissionless consensus proof resubmission resets client freshness timer, masking staleness (`store_consensus_update_time` not gated on state change) - (File: modules/ismp/core/src/handlers/consensus.rs)

### Summary
The reported TraitForge bug is a class of vulnerability where an unprivileged, seemingly benign action (transferring an NFT to a contract and back) resets a timestamp used to gate a maturity/freshness requirement, undermining the invariant the timer was meant to enforce. Hyperbridge's ISMP consensus-update path has a structurally analogous defect: the Substrate-side handler unconditionally bumps the consensus client's "last updated" timestamp on every valid consensus message, even when the message carries no new state, whereas the EVM-side equivalent explicitly guards against exactly this no-op case.

### Finding Description
In `update_client` [1](#0-0) , after `verify_consensus` returns `new_state`, the handler unconditionally calls `host.store_consensus_update_time(msg.consensus_state_id, timestamp)?` regardless of whether `new_state` differs from the previously `trusted_state`. There is no equality check comparable to the one used on the EVM side.

By contrast, `HandlerV2.handleConsensus` on the EVM side explicitly short-circuits when the freshly verified state equals the previous state, before any state or metadata (including the freshness timestamp maintained via `EvmHost.storeConsensusState`) is persisted: [2](#0-1)  and [3](#0-2) .

`handle_unsigned` on the pallet-ismp side is a fully permissionless, unsigned extrinsic (`ensure_none(origin)?`) that anyone can submit with any syntactically/cryptographically valid consensus proof: [4](#0-3) . Because `store_consensus_update_time` is not gated on the underlying trusted state actually advancing, an attacker (or an automated relayer resubmitting proofs it already has) can repeatedly call `handle_unsigned` with proofs that verify successfully but produce an unchanged `new_state` (e.g., re-proving an already-finalized head, or any light-client proof format that can legitimately validate without extending finality). Each such call refreshes `ConsensusClientUpdateTime` used by `host.is_expired(...)` at the top of `update_client` [5](#0-4) , which is the safeguard intended to freeze/expire a consensus client once no genuine finality progress has occurred for longer than the configured unbonding period.

This mirrors the TraitForge bug's root cause exactly: a "round-trip"/no-op operation, performed by an unprivileged party, resets a timestamp meant to encode "time since the last meaningful state transition," defeating the invariant that timestamp is supposed to protect — except here the asymmetry is directly evidenced by the fact that the EVM handler for the same protocol explicitly implements the guard that the Substrate handler omits.

### Impact Explanation
The unbonding-period/staleness check exists to freeze a consensus client that has stopped receiving genuine finality updates (e.g., due to relayer collusion, chain halt, or a long-range attack window), preventing the bridge from continuing to trust an increasingly stale/forkable state. If the "last updated" timestamp can be refreshed indefinitely by permissionless no-op proof submissions, this expiry safeguard never triggers even though the consensus client has received no real finality progress, undermining a security control relied upon to prevent acceptance of forged/aged state for message dispatch, request handling, and state-proof verification across the whole ISMP pipeline (`handle_unsigned`, `handlePostRequests`/`request::handle`, `response::handle`, `timeout::handle`). This can enable a subsequently stale or compromised consensus client to keep processing messages as if fresh, risking forged message delivery or unsound state commitment acceptance downstream.

### Likelihood Explanation
`handle_unsigned` is intentionally open to anyone with a valid proof, and light clients that produce no-op/redundant valid proofs are an expected occurrence in this codebase (the EVM `HandlerV2` explicitly handles this exact case). Any actor can trigger the reset with a single unsigned extrinsic and no special privilege, cost, or timing constraint, so exploitation requires only minimal effort once a "no-progress-but-valid" proof shape exists for the deployed client type.

### Recommendation
Gate `store_consensus_update_time` in `update_client` on the same no-op check used in `HandlerV2.handleConsensus`: only update `ConsensusClientUpdateTime` when `new_state != trusted_state` (i.e., when genuine finality/consensus progress occurred), matching the EVM implementation's `keccak256(previousState) == keccak256(verifiedState)` short-circuit.

### Proof of Concept
1. Attacker (or automated relayer) obtains any consensus proof that `verify_consensus` accepts as valid but that yields `new_state == trusted_state` (a legitimately re-provable/no-op proof for the given light client, e.g. re-proving an already-committed finalized head).
2. Attacker submits it via the permissionless `handle_unsigned` extrinsic: [4](#0-3) .
3. `update_client` executes, `is_expired` check passes (client still "fresh" from a prior legitimate update), `verify_consensus` succeeds and returns the same state, and `host.store_consensus_update_time` is called unconditionally, resetting the freshness clock: [6](#0-5) .
4. Repeat step 2-3 indefinitely (no cooldown, no fee beyond gas/weight) to keep the client perpetually "fresh" per `is_expired`, even though no genuine finality progress has been recorded, in contrast to what the equivalent EVM check would allow (`ConsensusClientExpired` would eventually revert once no real update occurs) [7](#0-6) .

```rust
pub fn update_client<H>(host: &H, msg: ConsensusMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host.consensus_client_id(msg.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized { consensus_state_id: msg.consensus_state_id },
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;
	host.is_consensus_client_frozen(msg.consensus_state_id)?;
	host.is_expired(msg.consensus_state_id)?;

	let (new_state, intermediate_states) = consensus_client.verify_consensus(
		host,
		msg.consensus_state_id,
		trusted_state,
		msg.consensus_proof,
	)?;
	host.store_consensus_state(msg.consensus_state_id, new_state)?;
	let timestamp = host.timestamp();
	host.store_consensus_update_time(msg.consensus_state_id, timestamp)?;
```

```text
    function handleConsensus(IHost host, bytes calldata proof) external notFrozen(host) {
        uint256 delay = block.timestamp - host.consensusUpdateTime();
        if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();

        bytes memory previousState = host.consensusState();
        (bytes memory verifiedState, IntermediateState[] memory intermediates, uint256 nextAuthoritySetId) =
            IConsensusV2(host.consensusClient()).verify(previousState, proof);

        if (keccak256(previousState) == keccak256(verifiedState)) return;
        host.storeConsensusState(verifiedState);
```
