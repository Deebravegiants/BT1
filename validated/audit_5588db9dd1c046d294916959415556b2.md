### Title
Webhook `shop-domain` header is not covered by the HMAC signature, breaking the shop-authenticity binding - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read directly from the unauthenticated `X-Shopify-Shop-Domain` HTTP header. `Registry.process` validates the HMAC over the body only and then trusts `request.shop` to build the `WebhookMetadata` handed to the host app's `WebhookHandler#handle`. The binding that should hold is: `shop value the HMAC signature authenticates == shop value the handler acts on`. Because the header is outside the signed content, that equality does not hold.

### Finding Description
`VerifiableQuery#to_signable_string` is the only material the HMAC covers, and for webhooks it is implemented as: [1](#0-0) 

while the tenant identifier used everywhere downstream is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes `HMAC-SHA256(client_secret, raw_body)` and compares it to the value in the `X-Shopify-Hmac-Sha256` header via `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` performs exactly that body-only check and then immediately trusts `request.shop` (and `request.topic`) to dispatch to the registered handler: [4](#0-3) 

Because `shop-domain` (and `topic`, `api-version`, `webhook-id`) are excluded from the signed bytes, any client that can reach the app's webhook endpoint and obtain one validly-signed request body/HMAC pair for its own shop (e.g., its own dev store, which legitimately receives real Shopify webhooks) can replay that same body+HMAC while substituting an arbitrary `X-Shopify-Shop-Domain` header value. The HMAC still validates (it only checks the body), but `WebhookMetadata.shop` now reports an attacker-chosen shop domain to the host application's handler.

### Impact Explanation
This is a cross-tenant identity-binding failure: the value the signature authenticates ("this body came from Shopify for the merchant that owns `client_secret`") does not equal the value the handler consumes to determine *which* tenant the event is for. Any host app that uses `WebhookMetadata#shop` for authorization, data lookups, or writes (e.g., updating that shop's stored settings/access token record, deleting that shop's data, or scoping an update) can be tricked into performing that action against a different shop record than the one whose webhook actually triggered the signed body — a cross-tenant action performed under another merchant's identity. This matches the report's bug class (a value trusted for privileged action while the actual cryptographic/identity check covers a different, decoupled piece of state).

### Likelihood Explanation
Likelihood is high for any app relying on the gem's default `Registry.process`/`WebhookHandler` flow, since the vulnerable code path is the gem's own documented HMAC verification for webhooks, not a host-app misuse. All that's needed is a single legitimately-signed request (any request the attacker's own store receives, or any traffic they can capture at their own endpoint) to be replayable with a forged `shop-domain` header, since nothing in the gem re-derives or binds `shop` to the signed payload.

### Recommendation
Include `shop` (and ideally `topic`, `api-version`, `webhook-id`) in `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the shop domain to the verified payload (e.g., require the shop domain to be embedded in and derivable only from the signed JSON body, matching what Shopify actually signs). At minimum, document and enforce that `WebhookMetadata.shop` must not be treated as authenticated unless it is verified against a value covered by the HMAC.

### Proof of Concept
```ruby
# Attacker captures one legitimately Shopify-signed webhook delivered to
# their own store (raw_body + X-Shopify-Hmac-Sha256), then replays it
# against the target app's webhook endpoint with a different shop header:

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_valid_hmac,   # still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "1",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)

ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (checks raw_body only, see hmac_validator.rb:12-22)
# handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# -> host app now processes an event as if it came from "victim-shop.myshopify.com"
```
