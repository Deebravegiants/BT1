### Title
Webhook shop-tenant attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` verify a webhook's authenticity using an HMAC computed **only over the raw request body**, while the `shop` (tenant identity) that the gem hands to the app's handler is read unauthenticated from the `X-Shopify-Shop-Domain` header. This breaks the intended binding: `HMAC-verified bytes == bytes the handler trusts for tenant attribution`. Concretely, `verified(raw_body)` != `attributed(shop_header)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are parsed straight from headers with no relation to the signed content: [2](#0-1) 

`Registry.process` validates only that `Utils::HmacValidator.validate(request)` succeeds (i.e. that `HMAC(raw_body, api_secret_key)` matches), then immediately forwards `request.shop` (along with `request.topic`, `request.parsed_body`, etc.) to the app-supplied handler as the tenant identity for the event: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the digest purely from `verifiable_query.to_signable_string` (the raw body) and the app secret — it never incorporates the shop header: [4](#0-3) 

Because Shopify signs every merchant's webhook body with the **same, app-wide `client_secret`** (not a per-shop key), any attacker who legitimately installs the app on their own store (or otherwise obtains one valid `(raw_body, hmac)` pair for that app) can capture a real, validly-signed webhook and replay it to the app's webhook endpoint after swapping only the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to a victim shop's domain. The HMAC check still passes (it doesn't cover the header), and `WebhookMetadata.shop` — the value the docs explicitly instruct handlers to use as the tenant/shop identity — will now read as the victim shop: [5](#0-4) [6](#0-5) 

This is exactly the documented, gem-provided contract (`ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify"), so a host app following the gem's own documentation inherits the flaw — this is not a case of the host app ignoring the gem's guidance.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality that should hold is `hmac_verified_bytes ⊇ tenant_identity_bytes`, but here `hmac_verified_bytes = raw_body` while `tenant_identity_bytes = shop_header`, which are disjoint. An attacker (an unprivileged internet user who merely needs a developer/trial store to obtain one legitimately-signed webhook from the shared app) can cause the app to process attacker-controlled webhook bodies under an arbitrary victim shop's identity — e.g., triggering `orders/create`, `customers/data_request`, `shop/redact` or app-specific business logic (job enqueue, data writes, GDPR-flow triggers, cache invalidation) attributed to a shop the attacker doesn't own. This is a cross-tenant access vulnerability as defined by the Critical impact bucket.

### Likelihood Explanation
Moderate-to-high: exploitation requires no special credentials beyond signing up for the target app on any (even the attacker's own) store to obtain one valid `(body, hmac)` pair — a normal, unprivileged path available to any internet user. Replaying the captured payload with a substituted shop header is trivial (a single HTTP header edit) and works against every app built on this gem's documented webhook-processing pattern.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or independently authenticate the shop out-of-band (e.g., cross-check `shop` against the set of shops that have valid, stored sessions/webhook registrations, or require mutual TLS/webhook-specific per-shop secrets). At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not present `shop` as trusted output without documenting that it is unauthenticated, and `Registry.process` should reject requests whose `shop` cannot be correlated to an active registration for that specific webhook subscription/topic combination.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a benign event (e.g., `orders/create`) and capture the resulting POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since it's HMAC(`B`, shared `client_secret`)), along with `X-Shopify-Topic: orders/create`.
2. Replay the exact same request to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` from `attacker.myshopify.com` to `victim.myshopify.com` (and adjust `X-Shopify-Webhook-Id` if the app dedups by id, or omit for a fresh id).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B, client_secret)` and finds it matches `H` — validation passes, because `shop` is never part of the signed content: [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: B, ...)`, causing the app to process attacker-supplied data as if it originated from `victim.myshopify.com`.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. ```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
