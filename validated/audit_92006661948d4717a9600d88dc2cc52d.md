### Title
Livestream agent broadcasts raw biometric camera frames to any connected TCP peer with no data_policy/session gating - ([File: src/agents/livestream/mod.rs])

### Summary
The livestream `Agent::run` loop in `src/agents/livestream/mod.rs` unconditionally renders and forwards `IrEyeFrame`, `IrFaceFrame`, and `RgbFrame` payloads to whichever peer most recently connected on TCP port 9201, with no signup_id, user_id, or data_policy check anywhere in the dispatch path. Frame data is forwarded from `src/brokers/orb.rs` (`handle_ir_eye_camera`, `handle_ir_face_camera`, `handle_rgb_camera`) purely based on whether the livestream agent is compiled/enabled, never based on the active signup's `data_policy`.

### Finding Description
`Input` in `src/agents/livestream/mod.rs` (lines 33-72) carries only raw `camera::ir::Frame`/`camera::rgb::Frame` data - no `signup_id`, `user_id`, or `data_policy` field exists on the enum at all [1](#0-0) . In `Agent::run`, the match arms for `Input::IrEyeFrame`, `Input::IrFaceFrame`, and `Input::RgbFrame` push the frame straight into the GPU compositor with no policy check, and any accepted `downstream` connection receives the rendered buffer via `gpu.render(events, move |buffer| downstream.push(&buffer))` [2](#0-1) [3](#0-2) .

The upstream TCP listener (`src/agents/livestream/upstream.rs`) binds `0.0.0.0:9201` and accepts any incoming connection unconditionally, immediately setting up a `Downstream` targeting the connecting IP with no authentication or authorization check [4](#0-3) [5](#0-4) . `Downstream::new` then opens a GStreamer pipeline that immediately UDP-streams (`udpsink`) H264-encoded frames to that peer's IP on port 9200 [6](#0-5) .

On the producer side, `src/brokers/orb.rs` forwards every IR-eye, IR-face, and RGB camera frame to the livestream agent purely gated on `self.livestream.enabled()` (a compile-time/agent-liveness check), never on the current signup's `data_policy` or backend authorization state: [7](#0-6) [8](#0-7) [9](#0-8) 

Meanwhile, the actual `data_policy` (e.g. `DataPolicy::OptOut` vs `FullDataOptIn`) is tracked separately as part of `UserData`/QR-code decoding in `src/backend/user_status.rs` [10](#0-9) [11](#0-10) , but this value is never threaded into `livestream::Input` or checked before `send_now` calls to the livestream port. The `Clear` message sent at `start_signup` (`src/plans/mod.rs`) only clears the rendered texture at the start of a new signup - it does not gate or authorize which frames get pushed during the signup that follows [12](#0-11) .

### Impact Explanation
Any peer able to reach the orb's TCP port 9201 (livestream feature enabled) can trigger `Downstream::new` and receive live IR-eye, IR-face, and RGB camera frames of every subsequent signup performed on that orb, entirely independent of whether the signup's `data_policy` (e.g. opt-out) or backend authorization would permit external transmission of that biometric data. This violates the "biometric secrets stay contained" invariant: raw iris/face imagery is exfiltrated to a destination never authorized by the backend or the data policy negotiated for that signup. This matches a Worldcoin/Orb bounty impact of "sensitive biometric data disclosure to unauthorized parties," scoped to leaking IR/RGB frames outside the backend-authorized data path.

### Likelihood Explanation
The `livestream` Cargo feature is compiled in whenever the `stage` feature is active, and `stage` is part of the crate's `default` feature set (`default = ["v2_x_x", "stage"]`) [13](#0-12) . Whether production/customer-facing orb builds disable `stage`/`livestream` at build time could not be confirmed from the available index (this is a build-configuration fact outside what `codebase_search`/`grep_search` could surface); if `livestream` is compiled into any fielded firmware image, this is a real, always-reachable, unauthenticated network exposure requiring only that the attacker be an unprivileged peer able to connect to port 9201 on the orb's network - exactly the precondition stated in the question. No credentials, tokens, or prior signup access are required to trigger `Event::Connected`, and the leak repeats automatically for every subsequent camera frame and every subsequent signup while the TCP connection remains open.

### Recommendation
Thread the current signup's `data_policy`/authorization state into the livestream pipeline: extend `livestream::Input::IrEyeFrame`/`IrFaceFrame`/`RgbFrame` (or the broker's forwarding logic in `src/brokers/orb.rs`) to carry or be gated by the active `UserData::data_policy`, and make `Agent::run`/`Downstream::push` a no-op whenever no policy-authorized session is bound (e.g., default-deny before a signup begins and after `data_policy` disallows external transmission). Additionally, require authentication (e.g., a token issued to a locally-authorized debug client) before `Upstream` accepts a TCP peer at all, rather than unconditionally accepting any connection to port 9201.

### Proof of Concept
Unit/integration test plan for `src/agents/livestream/mod.rs` and `src/brokers/orb.rs`:
1. Construct a fake `Orb` broker with `livestream.enabled()` returning `Some(...)` and a mocked signup context where `UserData::data_policy == DataPolicy::OptOut` (transmission not authorized).
2. Feed a synthetic `camera::ir::Frame` through `handle_ir_eye_camera` and assert (currently failing) that `livestream.tx.send_now(...IrEyeFrame...)` is NOT called when `data_policy` disallows external transmission.
3. In `livestream::Agent::run`, add a test harness that connects a `Downstream`-equivalent mock via `Upstream`, then dispatches `Input::IrEyeFrame`, `Input::IrFaceFrame`, `Input::RgbFrame` without any bound/authorized session token, and assert `Downstream::push` is never invoked (currently it is always invoked once a peer is connected, regardless of policy).
4. Expected assertions after fix: `Input` variants for frame data carry or are matched against a bound `data_policy`/session identifier, and `Downstream::push` becomes a no-op absent an authorized session - both assertions currently fail against the existing code in `src/agents/livestream/mod.rs` lines 113-200 and `src/brokers/orb.rs` lines 1043-1135.

    pub fn new(addr: IpAddr) -> Result<Self> {
        let video_info =
            VideoInfo::builder(VideoFormat::Bgrx, LIVESTREAM_FRAME_WIDTH, LIVESTREAM_FRAME_HEIGHT)
                .build()?;
        let pipeline = Pipeline::with_name("livestream");
        let appsrc = AppSrc::builder().caps(&video_info.to_caps()?).build();
        let nvvidconv = ElementFactory::make("nvvidconv").build()?;
        let nvv4l2h264enc = ElementFactory::make("nvv4l2h264enc").build()?;
        let rtph264pay = ElementFactory::make("rtph264pay").build()?;
        let udpsink = ElementFactory::make("udpsink").build()?;
        pipeline.add_many([
            appsrc.upcast_ref(),
            &nvvidconv,
            &nvv4l2h264enc,
            &rtph264pay,
            &udpsink,
        ])?;
        nvv4l2h264enc.set_property_from_str("insert-sps-pps", "1");
        nvv4l2h264enc.set_property_from_str("insert-vui", "1");
        udpsink.set_property_from_str("host", &addr.to_string());
        udpsink.set_property_from_str("port", &PORT.to_string());
        appsrc.link(&nvvidconv)?;
        nvvidconv.link(&nvv4l2h264enc)?;
        nvv4l2h264enc.link(&rtph264pay)?;
        rtph264pay.link(&udpsink)?;
        pipeline.set_state(gstreamer::State::Playing)?;
        appsrc.set_block(true);
        Ok(Self { pipeline, appsrc, video_info })
    }
