## Analog Found

### Title
Biometric personal-custody package is irreversibly uploaded to the backend before enrollment/uniqueness verification succeeds, with no compensating deletion on failure, fraud, or duplicate detection - (File: `src/plans/mod.rs`)

### Summary
The Axelar report describes a pattern where an irreversible action (burning tokens on the source chain) is committed unconditionally before the paired action (minting on the destination chain) is confirmed to succeed, and no refund/rollback path exists when the second half fails. `orb-core` contains the same structural pattern in the signup flow: the user's personal custody package (PCP) — containing iris codes, iris code shares, normalized iris images, and face-identifier embeddings — is built and permanently uploaded to the backend *before* the backend has confirmed the signup is unique, non-fraudulent, and authorized. If the subsequent enrollment step fails (duplicate, fraud, server error, network error, software-version block), the already-uploaded biometric package is never deleted or revoked.

### Finding Description
In `Plan::do_signup`, the sequence is:
1. The PCP (tier0/tier1/tier2, containing raw iris/face biometric material) is built via `self.build_pcp(...)` and immediately uploaded with `self.upload_pcp_tier_0(...)` and then queued to `data_uploader` for tier1/tier2, all keyed by the real `user_id` and `signup_id`. [1](#0-0) 
2. Only *after* this irreversible upload does the code call `self.enroll_user(...)`, which performs the actual backend verification (`signup_post`/`signup_poll`) that determines whether the signup is accepted, a duplicate, fraudulent, or otherwise rejected. [2](#0-1) 
3. `enroll_user::Plan::run` explicitly documents that a "SIGNUP FAIL" outcome (`success:false`) can be caused by backend duplicates, backend fraud detection, or Orb-detected fraud/failures — i.e., outcomes that should invalidate the signup — yet nothing in this path triggers deletion of the biometric package that was already uploaded in step 1. [3](#0-2) 
4. `upload_personal_custody_package::request` and the `data_uploader` agent only ever *push* data to the backend; there is no corresponding delete/revoke call anywhere in the codebase for a package tied to a signup that later fails verification. [4](#0-3) [5](#0-4) 

This is the direct analog of the Axelar bug: the "burn" (irreversible upload of biometric data under the user's real identity) is committed unconditionally, and the "mint" (verified, authorized enrollment) may still fail afterward — with no refund/rollback mechanism, exactly as `deluca-mike` described for the token case ("there is no protection here... you'd still need cooperation... to sign the refund").

### Impact Explanation
Unlike a blockchain, the "asset" here is the user's biometric data (iris codes/shares, normalized iris images, face embeddings) rather than tokens. Because the upload happens unconditionally before the uniqueness/fraud/authorization check completes, the backend ends up storing full biometric packages for signups that are ultimately rejected as duplicates, fraud, or failures. This means biometric data is disclosed/persisted to the backend for signup attempts that were never authorized to complete — a direct analog to "biometric data disclosure" and to state that is never rolled back after invalidation of the paired action, matching the accepted impact classes (biometric data disclosure / cross-signup state bleed for repeated attempts by the same or a fraudulent user).

### Likelihood Explanation
This triggers on the normal signup path any time enrollment fails after the PCP has already been sent (network hiccup during `enroll_user`, backend duplicate detection, backend fraud detection, or software-version blocking) — all of these are explicitly enumerated as expected outcomes in `enroll_user.rs`, so this is not an edge case but a routine occurrence in the current design of `do_signup`.

### Recommendation
Do not treat the PCP upload as unconditionally final before enrollment is confirmed. Either:
- Defer the tier0/1/2 upload until after `enroll_user` returns `Status::Success`, or
- Add a compensating backend call to delete/invalidate an uploaded PCP package when `enroll_user` returns any non-success status (duplicate, fraud, server error, etc.), mirroring the "well-behaving validators can still sign a refund" mitigation acknowledged in the original report.

### Proof of Concept
1. Complete biometric capture and pipeline for a signup whose iris/face data is expected to match an existing enrolled identity (duplicate) or is flagged as fraud by the backend.
2. Observe that `build_pcp` → `upload_pcp_tier_0` (tier0) and the `data_uploader` queue (tier1/tier2) complete successfully at `src/plans/mod.rs:600-636`, uploading the full biometric package to the backend under the real `user_id`/`signup_id`.
3. Observe `enroll_user::Plan::run` subsequently returns `Status::SignupVerificationNotSuccessful` (duplicate/fraud) at `src/plans/enroll_user.rs:157-176`.
4. Confirm no deletion/revocation request is issued for the already-uploaded package — the biometric data remains stored on the backend despite the signup being rejected.

    let presigned_url::Response { url: presigned_url, fields: form_data_params } =
        if let Some(tier) = tier {
            presigned_url::request_tiered_package(
                &DATA_BACKEND_URL,
                signup_id,
                session_id,
                &BASE64.encode(checksum),
                tier,
            )
            .await?
        } else {
            presigned_url::request_package(
                &DATA_BACKEND_URL,
                signup_id,
                session_id,
                &BASE64.encode(checksum),
            )
            .await?
        };
    dd_timing!("main.time.signup.upload_custody_images.presigned", t0);
    tracing::debug!("Images self-custody presigned_url: {presigned_url:?}");
    tracing::debug!("Images self-custody form_data_params: {form_data_params:?}");
    let file = Part::bytes(data.to_vec())
        .file_name("package.tar.gz")
        .mime_str("application/octet-stream")?;
    let form = form_data_params
        .into_iter()

    let request =
        super::client_with_timeouts(backend_http_connect_timeout, backend_http_request_timeout)?
            .post(presigned_url)
            .multipart(form);
    tracing::debug!("Sending request {request:#?}");

    let response = request.send().await?;
    dd_timing!("main.time.signup.upload_custody_images.upload", t1);
    tracing::debug!("Received response {response:#?}");
    response.error_for_status()?;

impl Agent {
    async fn upload_pcp(&self, pcp: Pcp, id: u64) -> (u8, u64) {
        let Pcp { signup_id, user_id, data, checksum, tier } = pcp;
        tracing::info!(
            "Start uploading a personal custody package tier {tier} for signup_id={signup_id}"
        );
        let t = Instant::now();
        loop {
            let response = backend::upload_personal_custody_package::request(
                &signup_id,
                &user_id,
                checksum.as_ref(),
                &data,
                Some(tier),
                &self.config,
            )
            .await;
            match response {
                Ok(()) => {
                    dd_timing!("main.time.signup.upload_custody_images" + format!("t{}", tier), t);
                    tracing::info!(
                        "Personal custody package tier {tier} uploading completed in: {}ms",
                        t.elapsed().as_millis()
                    );
                    break;
                }
                Err(err) => {
                    tracing::error!("UPLOAD PERSONAL CUSTODY PACKAGE TIER {tier} ERROR: {err:?}");
                    dd_incr!(
                        "main.count.http.upload_custody_images.error.network_error",
                        "error_type:normal"
                    );
                    if let Some(reqwest_err) = err.downcast_ref::<reqwest::Error>() {
                        if let Some(status) = reqwest_err.status() {
                            if status.is_client_error() {
                                dd_incr!(
                                    "main.count.signup.result.failure.upload_custody_images",
                                    "type:network_error",
                                    "subtype:signup_request"
                                );
                                break;
                            }
                        }
                    }
                }
            }
        }
        (tier, id)
    }
