## Title
Unbounded per-request memory growth in Vault and Confidential Relay gateway handlers from unauthenticated fan-out requests - (File: core/services/gateway/handlers/vault/handler.go, core/services/gateway/handlers/confidentialrelay/handler.go)

## Summary
`newActiveRequest` in both `core/services/gateway/handlers/vault/handler.go` and `core/services/gateway/handlers/confidentialrelay/handler.go` inserts an entry into an in-memory `h.activeRequests` map keyed by the caller-supplied `req.ID`, guarded only by a duplicate-ID check, with no maximum-size enforcement. [1](#0-0) [2](#0-1)  This contrasts with the generic `RequestCache` used elsewhere in the gateway, which explicitly enforces `maxCacheSize` and rejects new requests once full. [3](#0-2) 

## Finding Description
Both `HandleJSONRPCUserMessage` entry points accept requests with an arbitrary caller-supplied `req.ID` (bounded only to 200 bytes) and call `newActiveRequest`, which stores the full request, a per-request response map, and callback in a mutex-protected map with no cap:
- `core/services/gateway/handlers/confidentialrelay/handler.go`'s `HandleJSONRPCUserMessage` performs no authorization or rate limiting at all before calling `newActiveRequest` and fanning the request out to nodes. [4](#0-3) 
- The vault handler's `MethodPublicKeyGet` path explicitly bypasses authorization ("Public key requests don't require authorization") when the value isn't cached, still calling `newActiveRequest`. [5](#0-4)  Other vault methods do go through `h.requestProcessor.ProcessRequest` (authorization/authentication) before `newActiveRequest` is called. [6](#0-5) 

Entries persist until either the periodic `removeExpiredRequests` sweep evicts them after `requestTimeout` [7](#0-6) [8](#0-7) , or quorum/completion is reached. This is a time-based eviction with no count-based cap, unlike `RequestCache`.

Both handlers do enforce a per-HTTP-request byte-size cap upstream (`MaxRequestBytesLimiter` in `core/services/gateway/network/httpserver.go`), and node-response processing (`HandleNodeMessage`) is protected by per-node/global rate limiters, but neither of these mechanisms limits the number of distinct concurrently-open `activeRequests` entries that an inbound stream of unique-`id` user requests can create.

For the confidential-relay handler specifically, the top-level `HandleJSONRPCUserMessage` has no authentication/authorization gate before the map insertion — confirmed by reading the full function body, which goes straight from request-ID validation to `newActiveRequest` and `fanOutToNodes`. This is a genuine gap relative to the vault handler, which at least authorizes most methods before insertion.

## Impact Explanation
This maps to a resource-exhaustion / denial-of-service class issue against gateway infrastructure shared by a DON. An attacker capable of reaching the gateway's public user-facing HTTP JSON-RPC endpoint (particularly for confidential-relay, which has no pre-insertion auth check) can grow the `activeRequests` map by submitting many uniquely-`id`'d requests faster than the timeout-based cleanup ticker runs, consuming memory proportional to attacker-controlled request volume rather than any authenticated/bounded quota. This is a legitimate design gap: the size-capped `RequestCache` pattern exists elsewhere in the codebase precisely to prevent this, but was not applied to these two handlers.

## Likelihood Explanation
For the confidential relay handler, the exploit path requires no authentication at all — any network client that can reach the gateway's user HTTP endpoint can trigger unbounded `activeRequests` growth up to the per-request 200-byte ID limit and per-request byte-size cap, sustained over time. For the vault handler, most methods require successful authorization first (limiting the impact largely to the uncached `MethodPublicKeyGet` path, which is explicitly documented as low-risk because of aggressive caching, reducing but not eliminating exposure).

## Recommendation
Add an explicit maximum concurrent `activeRequests` bound to both handlers (mirroring `RequestCache.maxCacheSize`), rejecting or backpressuring new requests once the limit is reached, and add authentication/authorization or per-sender rate limiting ahead of `newActiveRequest` in the confidential-relay handler's `HandleJSONRPCUserMessage`, consistent with the existing per-node rate limiting applied on the response path (`HandleNodeMessage`). Migrating both handlers onto the shared `RequestCache` abstraction would be the most direct fix.

## Proof of Concept
1. Send a burst of JSON-RPC requests to the gateway's confidential-relay user endpoint (`HandleJSONRPCUserMessage` → `newActiveRequest` → `fanOutToNodes`), each with a unique `id` (≤200 bytes) and no authentication.
2. Repeat faster than the `defaultCleanUpPeriod` (1 second for confidential-relay, 5 seconds for vault) cleanup sweep can expire and remove entries.
3. Observe `h.activeRequests` growing without any enforced cap, unlike the bounded `RequestCache.NewRequest` path used by other handlers, consuming gateway memory proportional to the attacker's request rate. A Go unit test analogous to `core/services/gateway/handlers/common/requestcache_test.go`'s max-size test, but calling `newActiveRequest` repeatedly on the vault/confidentialrelay handler and asserting no error/rejection occurs beyond some large N, would demonstrate the missing bound.
