## Analysis: Arbitrary runtime-call dispatch via unauthenticated `message.from` in pallet-hyper-fungible-token

The CVE-2023-0462 bug class — user-controlled data being deserialized/decoded and then acted on with insufficient authorization — has a strong analog in `on_accept` of `pallet-hyper-fungible-token`.

### Title
Arbitrary runtime call dispatched under a forged origin when `SubstrateCalldata.signature` is omitted - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` decodes an ABI-encoded `Message` from the body of an inbound ISMP `PostRequest`, and if `message.data` is non-empty, decodes it further into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }`. If `signature` is `None`, the pallet derives the dispatch origin purely from `message.from` (interpreted as an EVM or substrate account) with no cryptographic proof that the true sender authorized `runtime_call`, then dispatches it. [1](#0-0) 

### Finding Description
`on_accept` only authenticates the *source contract* (`ContractToAsset::<T>::get(source, &from)`), where `from` is the `PostRequest.from` field of the ISMP message. It does **not** authenticate the `message.from` field that is embedded inside the ABI-encoded `body` — that value is fully attacker-controlled data inside the payload, not a cryptographically verified sender identity: [2](#0-1) 

When `message.data` (the optional calldata) is present, it's decoded into `SubstrateCalldata`. The `signature` field is `Option<Vec<u8>>` — genuinely optional: [3](#0-2) 

In the `signature.is_none()` branch, the origin used to dispatch `runtime_call` is derived directly from `message.from` with no signature check at all: [4](#0-3) 

The call is then decoded and dispatched as that origin: [5](#0-4) 

The only mitigations here are `BaseCallFilter` (a runtime-wide, coarse allow/deny list, not an authorization check tied to identity) and the fact that the message must arrive from a registered source contract/asset pairing. Neither of these prevents an attacker who can get *any* payload accepted (e.g. controls or spoofs `message.from` inside the ABI body of a request from a registered source contract) from executing an arbitrary allowed `RuntimeCall` as an arbitrary account, without ever proving control of that account's key.

### Impact Explanation
This allows unauthorized dispatch of arbitrary runtime calls (subject only to `BaseCallFilter`) under any `AccountId` the attacker names in `message.from`, without any signature. Depending on what calls `BaseCallFilter` allows, this can lead to theft of funds (e.g. `Balances::transfer`, `Assets::transfer` from the named victim account), unauthorized administrative actions, or other state-changing calls executed with a forged identity — i.e., unauthorized app action / forged message delivery consequences called out in the validation criteria.

### Likelihood Explanation
Reachable from a single relayed cross-chain `PostRequest` — no privileged role needed, only a source contract already registered via `ContractToAsset`. The vulnerable path is only exercised when `signature` is `None`, which is a legitimate encoding of `SubstrateCalldata` accepted by the decoder; nothing forces callers to supply a signature.

### Recommendation
Require `SubstrateCalldata.signature` to be mandatory (not `Option`) whenever `runtime_call` executes a privileged action, or otherwise ensure the dispatch origin is only ever derived from a value that is either (a) cryptographically verified via the existing Ed25519/Sr25519/Ecdsa signature-verification code paths, or (b) strictly the sender identity that already passed the `ContractToAsset` authentication (i.e., derived from the ISMP `PostRequest.from`, not from the unauthenticated `message.from` field inside the attacker-controlled ABI body).

### Proof of Concept
1. Attacker controls (or has access to) a registered source contract/asset pair recognized by `ContractToAsset::<T>::get(source, &from)`.
2. Attacker constructs an ABI-encoded `Message` where `data` decodes to `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded call, e.g. Balances::transfer_all(victim_derived_account, ...)> }`, and sets `message.from` to bytes that convert to the **victim's** `AccountId` (e.g., the EVM address whose zero-padded/derived substrate account holds funds).
3. Relay this as a `PostRequest` to the destination chain running `pallet-hyper-fungible-token`.
4. `on_accept` decodes the message, sees `signature.is_none()`, derives `origin` from the attacker-chosen `message.from`, and dispatches `runtime_call` as `RawOrigin::Signed(origin)` — executing an arbitrary allowed call against the victim's account without ever verifying a signature from that account.

Note: I could not fully verify from the indexed contents whether the companion Solidity contract `HyperFungibleToken.sol` constrains `message.from` to `msg.sender` on the source chain (the file search for that contract did not return results in this session). If the Solidity side always forces `from = msg.sender`, the practical attack surface narrows to "attacker sends from their own address with no signature and executes calls as themselves" (much lower impact), but the pallet-side code shown does not itself enforce this — the trust boundary is only as strong as an off-chain/EVM guarantee that isn't visible from the Rust pallet. A Devin session with full repo access could confirm this by inspecting `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`.
