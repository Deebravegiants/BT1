### Title
Collator can permanently censor a specific queued DMP message via selective hashing while passing the weak `check_enough_messages_included_basic` rule - (File: cumulus/pallets/parachain-system/src/lib.rs / cumulus/pallets/parachain-system/src/parachain_inherent.rs)

### Summary
`Pallet::enqueue_inbound_downward_messages` only calls `AbridgedInboundMessagesCollection::check_enough_messages_included_basic`, which merely requires at least one full message to be present whenever `hashed_messages` is non-empty; it does not verify that as many full messages as possible (up to the size budget) were included. A collator can therefore include one arbitrary early message as `full_messages` and hash away a specific target message `k` (and everything after it), which still satisfies both the basic check and the MQC-head assertion, but permanently advances the local `LastProcessedDownwardMessage` pointer past message `k` so it is never re-presented to the runtime.

### Finding Description
`enqueue_inbound_downward_messages` performs only the weak check: [1](#0-0) 

The basic check's logic: [2](#0-1) 

versus the stronger, documented alternative that is aware of censorship risk but is not invoked here: [3](#0-2) 

Because `MessageQueueChain::extend_downward` for a full message and `extend_with_hashed_msg` for its `HashedMessage` compute the *identical* chain contribution (both ultimately hash `(prev_head, sent_at, msg_hash)`), a collator that correctly computes `msg_k`'s hash produces the exact same `dmq_head` as one that ships the full message: [4](#0-3) 

So the final assertion `assert_eq!(dmq_head.head(), expected_dmq_mqc_head, ...)` in `enqueue_inbound_downward_messages` cannot detect the substitution: [5](#0-4) 

Crucially, the loop that walks `hashed_messages` still advances the *local* bookkeeping pointer `LastProcessedDownwardMessage`, even though the message was never delivered via `T::DmpQueue::handle_messages`: [6](#0-5) 

That pointer is exactly what future blocks use to decide which messages have "already been processed" and can be dropped from consideration before even building the abridged collection: [7](#0-6) [8](#0-7) 

The result: once a single malicious/censoring collator hashes message `k` instead of delivering it, all subsequent block builders (even fully honest ones) will locally treat message `k` as already handled and `drop_processed_messages` will strip it out of the raw relay-supplied collection before abridging, so it is never again offered as a `full_messages` entry and never reaches `T::DmpQueue`/`DownwardMessageHandler`. Only its hash was ever recorded on-chain. No later invariant re-validates that a hashed message's full content was eventually delivered — the DMQ MQC-head check only verifies hash-chain continuity, not delivery.

### Impact Explanation
A single malicious or bribed collator can permanently drop a specific user's downward message (e.g., an XCM `Transact`/reserve-transfer intended to credit that user) from ever being executed on the parachain, while the block remains fully valid from the relay chain's perspective (MQC head matches, weight/queue checks pass). This is a targeted, permanent censorship/fund-freeze vector reachable purely through the standard collator block-authoring path (`set_validation_data` inherent), requiring no privileged runtime access — only collator control for one block.

### Likelihood Explanation
- Precondition confirmed: `enqueue_inbound_downward_messages` in this codebase calls only `check_enough_messages_included_basic`, not `check_enough_messages_included_advanced`, for DMP.
- The attacker is an unprivileged (from a governance perspective) collator producing an ordinary block; any rotation/any-collator set that eventually gets to build a block can do this once, and the effect (advanced `LastProcessedDownwardMessage` pointer) is durable in on-chain state, so no further collusion is needed afterward.
- The attack requires only correctly hashing the target message's data (public knowledge, since DMQ messages are visible on the relay chain) — no forged signatures, no bypassing origin/proxy/multisig checks are needed.
- A related fix (`check_enough_messages_included_advanced` plus PR titled "Make HRMP advancement rule more restrictive", `prdoc/stable2603/pr_9086.prdoc`) exists in the codebase for HRMP, indicating the maintainers are aware of this exact censorship class, but the DMP path in `enqueue_inbound_downward_messages` still uses the weaker basic check.

### Recommendation
Replace `check_enough_messages_included_basic("DMQ")` in `enqueue_inbound_downward_messages` with `check_enough_messages_included_advanced`, supplying an `AbridgedInboundMessagesSizeInfo` derived from `messages_collection_size_limit()`/the actual DMP size budget, so a collator cannot hash a message unless the size budget was truly exhausted. Additionally, consider decoupling `LastProcessedDownwardMessage` advancement from `hashed_messages` handling so that a message counted only via its hash does not silently get treated as "delivered" for purposes of future message-dropping.

### Proof of Concept
Rust unit test in `cumulus/pallets/parachain-system/src/parachain_inherent.rs`-style harness:
1. Build `InboundDownwardMessages` with 3 messages: `msg_1` (small, benign), `msg_k` (the "victim" XCM Transact payload), `msg_3`.
2. Construct `AbridgedInboundDownwardMessages` manually with `full_messages = [msg_1]`, `hashed_messages = [HashedMessage::from(msg_k), HashedMessage::from(msg_3)]`.
3. Call `messages.check_enough_messages_included_basic("DMQ")` and assert it does **not** panic (full_messages.len() == 1 ≥ 1), proving the weak check passes despite `msg_k` being omitted.
4. Call `Pallet::<T>::enqueue_inbound_downward_messages(expected_head, messages)` where `expected_head` is computed by chaining `extend_downward(msg_1)` then `extend_with_hashed_msg(&msg_k.into())` then `extend_with_hashed_msg(&msg_3.into())` — assert it succeeds without panicking (MQC head matches).
5. Assert `LastProcessedDownwardMessage::<T>::get()` now reflects `msg_3`'s `sent_at`, i.e., past `msg_k`.
6. Simulate a subsequent honest `do_create_inherent` call with the same raw relay downward-message list (still containing `msg_k`, since it was never truly consumed by an XCM executor) and assert that `drop_processed_messages` removes `msg_k` from consideration, and that `T::DmpQueue::handle_messages` is never invoked with `msg_k`'s payload — confirming permanent, unrecoverable censorship of that message.

	/// Drop all the messages up to `last_processed_msg`.
	pub fn drop_processed_messages(&mut self, last_processed_msg: &InboundMessageId) {
		let mut last_processed_msg_idx = None;
		let messages = &mut self.messages;
		for (idx, message) in messages.iter().enumerate().rev() {
			let sent_at = message.sent_at();
			if sent_at == last_processed_msg.sent_at {
				last_processed_msg_idx = idx.checked_sub(last_processed_msg.reverse_idx as usize);
				break;
			}
			// If we build on the same relay parent twice, we will receive the same messages again
			// while `last_processed_msg` may have been increased. We need this check to make sure
			// that the old messages are dropped.
			if sent_at < last_processed_msg.sent_at {
				last_processed_msg_idx = Some(idx);
				break;
			}
		}
		if let Some(last_processed_msg_idx) = last_processed_msg_idx {
			messages.drain(..=last_processed_msg_idx);
		}
	}

	/// Check that the current collection contains as many full messages as possible, taking into
	/// consideration the collection constraints.
	///
	/// The `AbridgedInboundMessagesCollection` is provided to the runtime by a collator.
	/// A malicious collator can provide a collection that contains no full messages or fewer
	/// full messages than possible, leading to censorship.
	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}

	/// Extend the hash chain with a `HashedMessage`.
	pub fn extend_with_hashed_msg(&mut self, hashed_msg: &HashedMessage) -> &mut Self {
		let prev_head = self.0;
		self.0 = BlakeTwo256::hash_of(&(prev_head, hashed_msg.sent_at, &hashed_msg.msg_hash));

	}
