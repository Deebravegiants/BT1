### Title
Creator fee claims are permanently frozen if a blacklist-capable fee token (USDC) blacklists the creator's address - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` pays out a creator's entire pooled USDC balance by transferring directly to `msg.sender`. Because the protocol's fee asset is USDC — a blacklist-capable token — if a creator's wallet is ever added to Circle's USDC blacklist (e.g. for unrelated sanctions/compliance reasons), `claim()` reverts unconditionally and permanently, and there is no alternate withdrawal path for the already-accrued balance.

### Finding Description
`FeeVault.claim()` reads and zeroes `creatorBalance[msg.sender]`, then does a hard `safeTransfer(msg.sender, amount)`: [1](#0-0) 

The vault's `usdc` is a real, blacklist-capable ERC20 (Circle USDC) per the docs (`accrue`/`claim` operate purely in USDC): [2](#0-1) . USDC's `transfer`/`transferFrom` revert when either the sender or the recipient is on Circle's blacklist. Since `claim()` always sends to `msg.sender` with no override address and no alternate sweep/rescue path, a creator whose address becomes blacklisted (independent of any protocol wrongdoing) can never retrieve their `creatorBalance`, even though the balance is correctly accounted for and fully backed by vault funds (`accrue`'s underfund invariant guarantees the USDC is present).

Unlike `Bonding.transferCreator`, which only changes *future* fee attribution (`info.creator`), it does not touch already-accrued balances sitting in `FeeVault.creatorBalance[oldCreator]` — those funds are permanently keyed to the (now-blacklisted) old address: [3](#0-2) [4](#0-3) 

This is the same bug class as the referenced Cooler.repay() finding: a hard-coded, un-redirectable transfer to a specific address that a blacklist-capable asset can permanently block, with no pull/rescue fallback.

### Impact Explanation
Any creator fees already accrued to a blacklisted creator address become permanently unclaimable — a direct, irreversible freeze of creator funds inside `FeeVault`. There is no owner or creator-side mechanism to redirect or rescue a specific creator's stuck balance (only `setFeeTo` exists for the protocol side, and `transferCreator` doesn't move historical balances). Given creators are the intended beneficiaries and USDC blacklisting is an externally-triggerable, out-of-protocol-control event, this is a realistic Medium-severity permanent loss-of-funds scenario for affected creators.

### Likelihood Explanation
Blacklisting is entirely outside the protocol's control and can be triggered by Circle for any reason unrelated to the alt.fun protocol (e.g., the creator's wallet being flagged elsewhere). Every token-launch creator accumulates a claimable USDC balance automatically via the 0.25% creator fee split on every buy/sell, so the affected balance grows continuously and passively even without the creator claiming, making the eventual impact non-trivial once triggered.

### Recommendation
Add a way to redirect/rescue a stuck creator balance, e.g.:
- Allow `claim(address to)` where `to` is caller-specified (with the same `msg.sender`-authorization for the *right* to claim, but destination controllable), or
- Allow `transferCreator`-style re-keying of already-accrued `creatorBalance` in `FeeVault` to a new address, or
- Add an owner-gated (or timelocked) rescue function that can move a specific creator's stuck balance to a creator-nominated alternate address after proof of blacklist status.

### Proof of Concept
1. `creator` launches a token via `Bonding.launch`/`Zap.createToken`; trades accrue USDC fees via `Zap` → `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`, incrementing `creatorBalance[creator]`. [5](#0-4) 
2. `creator`'s address is later placed on USDC's blacklist by Circle (independent event).
3. `creator` calls `FeeVault.claim()`. The internal `$.usdc.safeTransfer(msg.sender, amount)` reverts because USDC blocks transfers to a blacklisted recipient. [1](#0-0) 
4. `creator` calls `Bonding.transferCreator(token, newAddress)` to redirect *future* fees, but the already-accrued `creatorBalance[creator]` inside `FeeVault` is untouched and still keyed to the blacklisted address — the funds are permanently unclaimable, with no other function in `FeeVault` able to move that specific balance.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```markdown
## Fees & FeeVault

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
```

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```
