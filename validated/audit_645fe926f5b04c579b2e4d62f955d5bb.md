### Title
Unrestricted, non-reentrancy-guarded `CallDispatcher.dispatch()` allows any actor to execute untrusted calldata against assets held in the shared dispatcher, enabling theft of escrowed funds mid-flow - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated function with no reentrancy guard that forwards arbitrary `(to, value, data)` calls supplied by whoever invokes it. It is shared as a single deployed instance across `IntentGatewayV2` (predispatch/postdispatch order calldata) and the `HyperFungibleToken`/`WrappedHyperFungibleToken` apps (cross-chain message calldata), and temporarily custodies user/solver funds while multi-step flows execute. Because the dispatch target and calldata are attacker-controllable and the function has no caller restriction, this is a direct instance of "including functionality from an untrusted control sphere" into a privileged execution context that holds value — analogous to IPA's `grub-install` executing attacker-supplied image content inside a trusted chroot.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` has no access-control modifier at all: [1](#0-0) 

Any address — not just `IntentGatewayV2`, `HyperFungibleToken`, or `WrappedHyperFungibleToken` — can call it directly and force it to execute arbitrary `to.call{value: call.value}(call.data)` against any contract, using whatever ETH/token balance the dispatcher currently holds.

The dispatcher is used as a shared, stateful custodian mid-transaction in several flows:
- `IntentGatewayV2.placeOrder`: predispatch assets are transferred into the dispatcher, then `order.predispatch.call` (fully attacker/user-controlled bytes) is executed via `ICallDispatcher(dispatcher).dispatch(...)` before funds are swept back into escrow: [2](#0-1) 
- `IntentsBase._execute`: after a solver delivers output assets to the dispatcher, `order.output.call` — controlled by the **order creator**, not the solver — is dispatched, and only afterward are residual balances swept back: [3](#0-2) 
- `WrappedHyperFungibleToken(Upgradeable).onAccept` and `HyperFungibleTokenUpgradeable.onAccept` likewise call `ICallDispatcher(_dispatcher).dispatch(message.data)` with cross-chain-message-supplied calldata: [4](#0-3) 

Because `dispatch()` is globally callable and non-reentrant-guarded, one of the `Call.to` targets embedded in attacker-controlled calldata (e.g., `order.output.call`, set by the order creator) can be a malicious contract. When the dispatcher's own `.call()` invokes that malicious contract, the malicious contract's code runs with the dispatcher as the immediate caller and can *re-enter* `CallDispatcher.dispatch()` directly — since nothing prevents this — to drain whatever balance (the solver's just-delivered output assets, or another concurrent flow's escrowed assets) is sitting in the dispatcher at that moment, before the legitimate sweep-back step (`DustCollected`/transfer-to-gateway) executes.

The `ICallDispatcher` interface itself documents that it is meant to "Dispatch the encoded call(s)" for untrusted content: [5](#0-4) 
but nothing scopes *who* may trigger that dispatch or guards against reentrant self-invocation while value is parked in the contract.

### Impact Explanation
An order creator (an unprivileged, single-transaction actor reachable by any user of `IntentGatewayV2`) can encode `order.output.call` to include a call to their own malicious contract. During `fillOrder`, once the solver has transferred output assets into the shared `CallDispatcher` and `_execute` invokes `dispatch(order.output.call)`, the malicious contract executes and can call back into `CallDispatcher.dispatch()` to sweep the solver's just-delivered funds to an attacker address before the intended sweep/settlement logic runs. This is theft of solver funds reachable from a single submitted order/fill — a concrete loss of funds scenario, not merely a griefing or DoS issue. The same unrestricted-dispatch primitive also increases the blast radius for any other app sharing the singleton dispatcher, since balances left in transit for any of them are equally exposed to a directly-invoked `dispatch()` call from an unrelated address.

### Likelihood Explanation
High reachability: crafting `order.output.call` is entirely within the order creator's control at order-placement time (`placeOrder`), and `fillOrder`/`_execute` is the standard, expected code path executed for every cross-chain or same-chain fill — no special privileges, governance, or admin action are required. The only constraint is designing a `Call[]` whose `to` target is attacker-owned code, which is trivial.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to be callable only by the whitelisted app/gateway contracts that are expected to invoke it (e.g., an `onlyAuthorizedCaller` modifier set at deployment/configuration).
- Add a reentrancy guard to `dispatch()` so it cannot be re-entered while a prior dispatch (and the surrounding sweep) for the same transaction is in progress.
- Consider using a fresh, ephemeral dispatcher/escrow context per order/fill rather than a single shared, stateful singleton so no other flow's residual balance is ever exposed to an unrelated call.

### Proof of Concept
1. Attacker places an order via `IntentGatewayV2.placeOrder` with `order.output.call` encoding a `Call[]` where `to = AttackerContract`.
2. A solver calls `fillOrder`, transferring the order's output assets into the shared `CallDispatcher` and then invoking `_execute(order, outputsLen)`, which calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` (`evm/src/apps/intentsv2/IntentsBase.sol:501-502`).
3. `dispatch()` performs `AttackerContract.call{value: call.value}(call.data)` per `CallDispatcher.sol:59`, transferring control to attacker code with `CallDispatcher` as `msg.sender`'s eyes (i.e., balance owner).
4. `AttackerContract`'s fallback/receive/called function directly calls `CallDispatcher.dispatch(maliciousCalls)` again (this is legal since `dispatch` has no caller restriction and no reentrancy guard), where `maliciousCalls` transfers the dispatcher's *current* token/ETH balance — which at this point includes the solver's just-delivered output assets — to an attacker-controlled address.
5. Control returns to `_execute`, which sweeps whatever balance remains (now drained) back to the gateway, masking the theft as ordinary "dust" collection with zero or near-zero amounts.

Note: I was unable to fully read the complete `fillOrder` function body (final tool call was truncated by the iteration limit) to confirm the exact ordering of `nonReentrant` modifiers on `fillOrder` itself relative to `_execute`; this should be verified directly against `evm/src/apps/IntentGatewayV2.sol` before treating the PoC as fully confirmed, though the core primitive — an unauthenticated, unguarded `dispatch()` reachable with attacker-supplied targets while holding third-party funds — is directly evidenced by the cited code.
