### Title
Small LP withdrawals can permanently revert due to floor-rounding to zero in `process_withdraw` - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` computes a user's proportional share of `coin_amount` and `pc_amount` using floor-rounded division, then unconditionally rejects the entire withdrawal with `AmmError::InvalidInput` if either resulting amount is `0`. Because the check is a hard revert with no fallback path, an LP holder whose proportional share rounds down to zero for either token cannot withdraw any amount of their position — including their entire remaining balance — permanently freezing their LP tokens. This mirrors the `DelegatedStaking.redeemAllRewards` finding, where a strict `require(rewards > 0)` check reverted a legitimate operation because rounding/rate math could produce an unintended zero, with no way to bypass except an alternate path that isn't available here.

### Finding Description
In `process_withdraw`, the proportional token amounts are derived via floor division: [1](#0-0) 

The resulting amounts are checked and, if either is zero, the whole instruction fails: [2](#0-1) 

Additionally, a user is never permitted to withdraw the entire pool (`withdraw.amount >= amm.lp_amount` is rejected), so the maximum a holder can ever request is bounded below `amm.lp_amount`: [3](#0-2) 

If a pool's coin/pc vault balances become highly imbalanced relative to `amm.lp_amount` (e.g. after most liquidity is removed, after large `pnl` extraction via `calc_take_pnl`/`WithdrawPnl`, or simply for a very small LP holder in a large pool with skewed decimals), `RoundDirection::Floor` can drive `coin_amount` or `pc_amount` to `0` for every value of `withdraw.amount` up to that holder's full LP balance. Since the check unconditionally reverts on either amount being zero — with no alternate redemption function analogous to `redeemRewards` — the holder has no way to ever redeem their LP tokens.

This is structurally the same bug class as the external report: a strict post-hoc zero-check on a value derived from rate/ratio math causes reverts of a legitimately-owed operation, and unlike the delegated-staking case there is no secondary function to fall back on within this program.

### Impact Explanation
Affected LP holders lose all ability to redeem their deposited liquidity: their tokens are burned only on successful transfer, so a permanently reverting withdraw path means the LP position is stuck forever with no admin or user-level recourse (there is no partial/alternate withdrawal instruction). This is a permanent freezing of user funds, which the given severity rubric (medium/high impact via availability loss on legitimate value) supports as at least Medium severity.

### Likelihood Explanation
This requires a pool state where the vault-to-`lp_amount` ratio is skewed enough that floor rounding zeroes out one side for all values in a holder's balance range. This is most likely for: dust-sized LP holders in pools with large `sys_decimal_value` normalization differences between coin/pc decimals, or after significant PnL has been withdrawn via `WithdrawPnl`/`calc_take_pnl`, shrinking `total_pc_without_take_pnl`/`total_coin_without_take_pnl` relative to outstanding `lp_amount`. Reaching this state requires only ordinary pool activity (swaps, pnl withdrawals, other LPs withdrawing) rather than a privileged action, and the victim's own `Withdraw` call with attacker(user)-chosen `amount` is the single transaction that triggers the revert.

### Recommendation
Do not hard-fail the entire withdrawal solely because a computed side amount rounds to zero. Options:
- Allow proceeding when at least one of `coin_amount`/`pc_amount` is nonzero and skip the transfer/burn accounting for the zero side, or
- Round the LP-to-token computation using `RoundDirection::Ceiling` (or a minimum-of-1 floor) to guarantee any nonzero LP burn yields at least 1 unit on both sides, or
- Provide an alternate/forced-redeem path that lets a holder burn 100% of their remaining LP balance (relaxing the `withdraw.amount >= amm.lp_amount` restriction for a full-balance exit) so dust positions are not permanently unredeemable.

### Proof of Concept
1. Assume a pool where, due to decimal normalization and prior `WithdrawPnl` extractions, `total_pc_without_take_pnl` is very small relative to `amm.lp_amount` (e.g. `total_pc_without_take_pnl = 100`, `amm.lp_amount = 10_000_000`).
2. A holder owns `lp_balance = 50` LP tokens (all of it, well under the `amm.lp_amount` cap enforced at line 1716).
3. Any `withdraw.amount` in `[1, 50]` computed via `InvariantPool::exchange_pool_to_token(total_pc_without_take_pnl, Floor)` at line 1759-1761 yields `pc_amount = floor(100 * amount / 10_000_000) = 0` for every `amount <= 50`.
4. The check at line 1775-1777 triggers on every attempt, returning `AmmError::InvalidInput` and reverting the transaction; the holder can never burn their LP tokens or redeem the underlying assets, permanently freezing their position with no alternate function to call.
