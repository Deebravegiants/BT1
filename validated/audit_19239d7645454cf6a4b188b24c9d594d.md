### Title
POA Bridge withdrawal status matched only by `assetId` causes wrong status/tx-hash to be reported for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves each withdrawal's on-chain status by scanning the bridge API response and picking the first entry whose `near_token_id` matches `assetId`, completely ignoring the caller-supplied `index`. When a single NEAR intent transaction contains two or more withdrawals of the same asset (a supported "batch withdrawal" pattern in this SDK), every `describeWithdrawal` call for that asset — regardless of which withdrawal `index` is being tracked — returns the same matched entry's status and `txHash`.

### Finding Description
`findMatchingWithdrawal` is defined as: [1](#0-0) 

It is invoked from `describeWithdrawal`: [2](#0-1) 

The match key is `assetId` only — `index` is never consulted, and neither `destinationAddress` nor `amount` are compared. The `.find()` call in `findMatchingWithdrawal` (line 426) always returns the **first** array element with a matching `near_token_id`, so two `WithdrawalIdentifier`s that differ only by `index` (e.g., withdrawal 0 and withdrawal 1 of the same token from a single NEAR tx) resolve to the identical response object.

This breaks the equality the SDK is supposed to preserve: *the status/hash reported for withdrawal `i` must be the on-chain outcome of withdrawal `i`*, not of some other withdrawal that happens to share the same `assetId`.

The SDK explicitly supports and documents batch withdrawals tracked by index via `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`, where `promises[i]` is expected to correspond to `withdrawalParams[i]`: [3](#0-2) 

If `withdrawalParams` contains two entries with the same POA `assetId` but different `destinationAddress`/`amount` (e.g., splitting a refund between two recipients, or two legs of a multi-leg payout), both `promises[0]` and `promises[1]` will report the same `status` and `txHash` once the bridge API returns any matching entry — even though only one of the two withdrawals actually completed on-chain.

### Impact Explanation
This is a status/hash misreport: an integrator relying on `promises[i]`/`waitForWithdrawalCompletion` per-index results to credit or reconcile a destination transaction can be told withdrawal #2 "completed" with the tx hash that actually belongs to withdrawal #1, while the real withdrawal #2 may still be pending or may have failed. This can cause the integrator to record/credit the same destination hash twice, or mark a still-in-flight/failed withdrawal as completed — matching the listed High-impact class "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
No malicious actor is required; this triggers whenever a legitimate user (or the SDK's own batch API) creates two POA-bridge withdrawals of the same underlying token within one NEAR intent transaction — a pattern the SDK's own README and RFC documents as supported (e.g., "USDC to Solana + BTC refund"; same-token batches are not explicitly disallowed at the type level). The code comment at lines 412-416 itself acknowledges "multiple withdrawals of the same token in a single transaction are not supported," confirming the root cause is real and unresolved, only documented as a known limitation rather than guarded against.

### Recommendation
Disambiguate matching beyond `assetId`: incorporate `destinationAddress`/`amount`/order (e.g., sort both the POA API's `withdrawals` list and the local `withdrawalParams` batch by amount, as suggested in the existing comment) before matching by index, or reject/assert when multiple same-asset withdrawals are requested in a single batch until proper per-withdrawal disambiguation is implemented, so `describeWithdrawal` never returns another withdrawal's status/hash for the wrong index.

### Proof of Concept
1. Submit a batched NEAR intent with two POA-bridge withdrawal legs sharing the same `assetId` (e.g., `nep141:usdt.omft.near`) but different `destinationAddress`, via `sdk.createWithdrawalIntents`/`processWithdrawal`.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [legA, legB], intentTx })`.
3. Once the POA bridge API indexes only `legA`'s completion (`legB` still pending/failed on-chain), both `promises[0]` and `promises[1]` invoke `PoaBridge.describeWithdrawal`, which calls `findMatchingWithdrawal(response.withdrawals, assetId)` — returning the same `legA` entry for both indices (`poa-bridge.ts:319-322`, `418-427`).
4. Both promises resolve with `{ status: "completed", txHash: legA.txHash }`, even though `legB` never completed with that hash, causing the integrator's per-index bookkeeping to record `legA`'s tx hash twice.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
