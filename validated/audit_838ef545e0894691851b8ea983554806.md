### Title
Webhook shop-domain spoofing via HMAC that only covers the body, not the `shop` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `hmac` and `to_signable_string` only from the JSON body of the webhook request, while `topic`, `shop`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers and never enter the signed material. `Registry.process` accepts any request whose HMAC matches the body and then hands the caller-supplied `shop` header straight to the app's webhook handler as trusted tenant identity. This breaks the binding "shop authenticated == shop the handler acts on," letting anyone who can obtain one genuine `(body, hmac)` pair from Shopify (e.g. by installing the app on their own shop and receiving a legitimate webhook, since the HMAC secret is the app's single `client_secret` shared across every installing shop) replay that pair with an arbitrary `shop-domain` header to impersonate a different (victim) tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` extracts the signature from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` (and `topic`, `webhook_id`, `api_version`) are pulled from headers that are entirely separate from the signed string: [3](#0-2) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`: [4](#0-3) 

`Webhooks::Registry.process` relies solely on this HMAC check before trusting `request.shop` and forwarding it, unauthenticated, into the app's handler as the tenant identity for the event: [5](#0-4) 

Because the app's `client_secret` (used as the HMAC key) is identical for every shop that has installed the app, an unprivileged user who installs the app on their own shop will receive a genuinely Shopify-signed `(raw_body, hmac)` pair. Since the signature never covers the `shop-domain` header, that same body/HMAC pair remains valid when replayed to the app's webhook endpoint with the `shop-domain` header rewritten to any other (victim) shop domain. The identity equality the code implicitly assumes is:

```
shop authenticated by HMAC  ==  shop attributed to the processed webhook (request.shop)
```

but the left side is never checked at all — only the body is authenticated — so the equality is unenforced and forgeable.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker can cause the app's webhook handler to process attacker-controlled (but genuinely-signed) event data while `WebhookMetadata#shop` claims to be an arbitrary victim shop. Any host application that uses `request.shop` / `WebhookMetadata.shop` (as documented and demonstrated in `Registry.process`) to select which merchant's records to update, delete, sync, or notify will have its per-tenant isolation bypassed by a party who only needed to install the (public) app on their own store — no access token, `client_secret`, or privileged account is required.

### Likelihood Explanation
Likelihood is significant: obtaining a real `(body, hmac)` pair requires only installing the target app as an ordinary merchant and receiving one webhook of the desired topic — a normal, unprivileged interaction. Replaying it with a modified `shop-domain` header is a simple, direct HTTP request; no cryptographic secret needs to be recovered because the gem never checks that the claimed shop matches anything.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the value verified by `HmacValidator`, or otherwise cryptographically bind the `shop-domain` header to the signed payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, cross-check `request.shop` against a shop-scoped secret/session (per-shop token) rather than relying on the app-wide `client_secret` HMAC alone to authorize the shop attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and configures a webhook for, e.g., `orders/create`.
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: H = HMAC(client_secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and issues their own POST to the app's webhook endpoint, keeping `B` and `H` unchanged but setting `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(client_secret, B)`, which still equals `H` because `to_signable_string` never included the shop header — validation succeeds.
5. `Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on `B` under the identity of `victim.myshopify.com` even though the data actually originated from the attacker's own shop.
