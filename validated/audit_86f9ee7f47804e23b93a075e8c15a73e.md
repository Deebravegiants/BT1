### Title
Unauthenticated, front-runnable pool creation via `Initialize2` lets an attacker seize control of a target market's pool address and set an arbitrary initial price - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` (and the `Initialize2` instruction it services) can be invoked by any signer with no relationship to the intended pool operator. The `market_info` account, which is used purely as a seed to deterministically derive the AMM/vault/LP-mint/target-orders PDAs, is explicitly documented as "Just a seed for AMM account. Can be any account." and is never validated against the actual Serum/OpenBook market program or market state. Combined with the `AlreadyInUse` one-shot guard on `amm.status`, this reproduces the exact bug class from the reference report: whoever's `Initialize2` transaction lands first for a given `market_info` pubkey permanently claims that pool address, and every subsequent legitimate initialization attempt for the same market fails.

### Finding Description
`process_initialize2` derives every pool-related account (AMM account, LP mint, coin/pc vaults, target orders) from `market_info.key` using `get_associated_address_and_bump_seed` inside `generate_amm_associated_account` / `generate_amm_associated_spl_token` / `generate_amm_associated_spl_mint`: [1](#0-0) 

The instruction doc explicitly states the market account can be arbitrary: [2](#0-1) 

The only checks performed are: signer check on `user_wallet_info`, correct SPL/ATA/system program ids, correct AMM authority PDA/nonce, correct AMM config PDA, and that the AMM account status is `Uninitialized`: [3](#0-2) [4](#0-3) 

None of these checks tie the caller to any expected owner/creator of the pool, and none validate that `market_info` is a genuine market account for the coin/pc mint pair. The initial LP liquidity and price ratio are derived directly from whatever `init_coin_amount`/`init_pc_amount` the caller supplies: [5](#0-4) 

Because pool creation is fully permissionless and the deterministic pool address for a given market is publicly computable in advance, an attacker can observe/predict a legitimate team's intended `market_info` pubkey (typically a well-known, publicly deterministic OpenBook market for a specific coin/pc pair) and submit their own `Initialize2` transaction first, with attacker-chosen minimal deposit amounts (`init_coin_amount`, `init_pc_amount`), thereby:
1. Permanently occupying the pool PDA for that market (subsequent legitimate `Initialize2` calls fail with `AlreadyInUse`, mirroring the `ALREADY INITIALIZED` revert in the reference `Subaccount.sol` report).
2. Fixing an arbitrary, attacker-chosen initial price ratio (`coin_amount : pc_amount`) with only the minimal capital required to pass the `InvalidSupply` (amount != 0) and `InitLpAmountTooLess` checks.

### Impact Explanation
This lets an unprivileged attacker deny the legitimate pool creator control over their own market's pool and lock in a manipulated starting price with minimal capital. Once the pool is initialized at an attacker-favorable ratio, the attacker can immediately profit by swapping against the mispriced pool via `SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2` before real liquidity/arbitrage corrects it, or by having later depositors add liquidity at the skewed ratio. This is a concrete, fund-relevant griefing/economic exploit reachable from a single unprivileged transaction with attacker-chosen accounts and data, matching the report's "improper initialization / front-run before intended owner" bug class.

### Likelihood Explanation
High likelihood: the intended `market_info` address for a specific coin/pc pair is typically public/predictable ahead of the legitimate creation transaction (e.g., a known OpenBook market address), `Initialize2` requires no special role, and the attacker only needs trivial token amounts (just above the `10^lp_decimals` floor) to pass all checks and win the race via normal transaction ordering/priority fees.

### Recommendation
Add an access-control or commitment mechanism to `Initialize2`/`process_initialize2` so that pool creation for a given market can only be finalized by (or requires approval from) the intended creator — e.g., require a pre-registered creator pubkey per market seed, or use a two-phase commit (reserve then confirm) tied to a specific signer, and/or validate that `market_info` is a genuine market account (owned by the expected market program with matching mints) rather than treating it as an arbitrary seed, so that predicting/copying it does not let an attacker legitimately hijack pool creation.

### Proof of Concept
1. Legitimate project intends to create a Raydium pool for `COIN/PC` using a specific OpenBook market address `M` (publicly known/derivable in advance).
2. Attacker computes the same deterministic PDAs (`amm_info`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, `amm_target_orders`) from `M` using `get_associated_address_and_bump_seed`, exactly as `generate_amm_associated_account` would.
3. Attacker submits an `Initialize2` transaction first (front-running the legitimate creation tx) using their own wallet as `user_wallet_info`, market `M` as `market_info`, and attacker-chosen `init_coin_amount`/`init_pc_amount` set to a highly skewed ratio with minimal absolute amounts.
4. `process_initialize2` succeeds: it creates the PDAs seeded by `M`, sets `amm.status` away from `Uninitialized`, mints LP to the attacker, and records the skewed price via `amm.initialize(...)` and `target_order.check_init(...)`.
5. The legitimate creator's subsequent `Initialize2` call for market `M` now fails with `AmmError::AlreadyInUse` (`program/src/processor.rs:845-847`), permanently losing the ability to initialize the pool as intended; meanwhile the attacker can swap against the mispriced pool for profit.
