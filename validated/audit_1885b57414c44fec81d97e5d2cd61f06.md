### Title
Unauthenticated theft of Emporium-held assets via stateless (CASE 2) op with trivial proof and `signerAddress=address(0)` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium` for any attacker-supplied `endpoint`/`callData`, gated only by `onlyAllowedRecipient` (i.e. that the call comes from `Hinkal`) and, when `stack.signerAddress == address(0)`, `verifyWallet` returns immediately without any signature or ownership check. Combined with the fact that the accompanying zk-proof for this path (`MainEVMCircuitMin`) carries no ownership/authorization signal at all, an attacker can submit a self-crafted proof and an `EmporiumOperation` whose `callData` calls `transferFrom` on any ERC721/ERC20 asset the Emporium contract holds (e.g., a previously deposited LP position), stealing it.

### Finding Description
The broken equality: after the attack, `ownerOf(victimTokenId) == attacker`, while `AUTHORITY` requires `ownerOf(victimTokenId)` remain equal to the depositing user's stealth address / controlled wallet, since no proof of ownership or authorization was ever produced by the attacker for that NFT.

Code path:
1. `Hinkal.transact` (`contracts/Hinkal.sol:30-56`) calls `hinkalHelper.performHinkalChecks` which returns `inputForCircom` computed by `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`). When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, it routes to `formInputEmporiumMin`, which only feeds `emporiumMessage`, `timeStamp`, `calldataHash` into the circuit (`contracts/CircomDataBuilder.sol:150-161`).
2. The corresponding circuit, `MainEVMCircuitMin.circom`, only constrains `message == Poseidon(messageSeed)` — there is no nullifier check, no merkle-root membership check, no stealth-address/ownership signal whatsoever (`circuits/MainEVMCircuitMin.circom:1-18`). Since `messageSeed` is attacker-chosen private input, the attacker can trivially produce a valid proof for any `calldataHash`/`emporiumMessage`/`timeStamp` combination they want — the proof proves nothing about ownership of any UTXO or the Emporium-held asset.
3. `performHinkalChecks` only verifies self-consistency: `getHashedCalldata(circomData) == circomData.calldataHash` (`contracts/HinkalHelper.sol:221-225`), which is just an anti-tampering hash over the attacker's own submitted fields (including `externalActionData`, hence the malicious `ops`) — it does not authenticate that the caller has rights over any external asset.
4. `Hinkal._externalTransact` (`contracts/Hinkal.sol:234-261`) then calls `EmporiumUpgradeable.runAction` since Emporium is a registered `externalActionMap` target and satisfies `onlyAllowedRecipient` (`contracts/external-actions/ExternalActionBaseUpgradeable.sol:39-46`) — this modifier only checks the caller is `Hinkal`, not that the operation's target/asset is tied to the caller's proven ownership.
5. Inside `runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-118`): `verifyWallet(stack, circomData)` returns immediately when `stack.signerAddress == address(0)` (line 314-316), skipping the ECDSA signature check entirely. The loop then hits CASE 2 (`op.invokeWallet=false`) and executes `op.endpoint.call{value: op.value}(op.callData)` (line 112) — with `msg.sender == Emporium`. If `op.callData` encodes `positionManager.transferFrom(emporium, attacker, victimTokenId)`, this succeeds because `Emporium` is the actual on-chain owner of `victimTokenId` from a prior legitimate deposit.

Root cause: nothing in `runAction`, `verifyWallet`, or the circuit selection logic enforces that a CASE 2 (stateless) operation's target/callData is constrained to assets described by the prover's own UTXOs/`erc20TokenAddresses`/nullifiers, nor does it require `invokeWallet=true`/a valid signer for arbitrary calls against protocol-held state. The `balanceChange`/`deltaAmountChanges` accounting at the end of `runAction` only tracks `circomData.erc20TokenAddresses` (empty in this attack), so an ERC721 transferred out of Emporium is invisible to any balance-based safety check.

### Impact Explanation
Critical — direct theft of another user's shielded/protocol-held asset (an ERC721 LP position deposited into Emporium by a legitimate CASE 2 op) by a completely unrelated, unprivileged caller. The attacker needs no signature, no valid ownership proof, and no knowledge of the victim's keys — only the public `victimTokenId` (available via the `Transfer` event) and a trivially-forged `MainEVMCircuitMin` proof. This is repeatable against any Emporium-held asset (ERC721, or ERC20/ETH beyond what circomData declares in `erc20TokenAddresses`) whenever `stack.signerAddress == address(0)`.

### Likelihood Explanation
Preconditions are realistic: a prior CASE 2 deposit op leaving an asset (e.g. an LP NFT) owned by the Emporium contract, which the protocol's own design supports (`op.invokeWallet=false` stateless ops calling into the LP manager directly with `Emporium` as `msg.sender`, i.e. owner). Attacker cost is a single `Hinkal.transact` call with a self-generated proof for the `Min` circuit (cheap, no special access needed) and construction of `callData` for a public, standard ERC721 `transferFrom`. Fully repeatable per available asset; feasibility is high given no privileged role is required.

### Recommendation
- Require an authenticated/authorized signer (`stack.signerAddress != address(0)` with a valid EIP-712 signature over the full op set, or equivalent proof-bound authorization) for any CASE 2 operation whose `callData` can move assets out of the Emporium contract, not just for CASE 1.
- Alternatively, bind stateless (CASE 2) calls to only the tokens declared and accounted for in `circomData.erc20TokenAddresses`/`deltaAmountChanges`, and forbid arbitrary `callData` to endpoints holding protocol-custodied non-fungible/other assets unless signed by the depositing user.
- Do not allow `MainEVMCircuitMin` (no ownership/nullifier signal) to authorize any operation that can affect previously-deposited state; restrict its use to purely stateless, value-neutral, self-contained calls.

### Proof of Concept

1. Deploy `EmporiumUpgradeable`, `HinkalWallet`, `Hinkal`, `HinkalHelper`, and a mock ERC721 position manager.
2.
