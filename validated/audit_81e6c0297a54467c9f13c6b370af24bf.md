### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but passes the tenant-identifying `shop` value from an unsigned HTTP header straight to the app's webhook handler. Any actor who can obtain one validly-signed webhook payload (e.g., by installing the app on their own shop) can replay that body with a forged `X-Shopify-Shop-Domain`/`shopify-shop-domain` header pointing at a different shop, and the gem will accept it as authentic for that other tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e., the body, using the app's shared `api_secret_key`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC (which covers the body) and then forwards the *unauthenticated* `request.shop` value directly into `WebhookMetadata`, which is what app handlers use to identify which tenant the event belongs to: [4](#0-3) 

The identity binding that should hold is: `shop value cryptographically bound in the signed payload == shop value the handler acts on`. Because the HMAC only signs `@raw_body` and the secret (`api_secret_key`) is identical across every shop that has the app installed, this equality does not hold — `request.shop` can be swapped to any string while the HMAC check over the (unrelated) body still passes as long as that body/HMAC pair was legitimately issued for *some* shop using the app.

### Impact Explanation
An unprivileged internet user can install the target app on their own store (a normal, self-service action) and thereby receive genuinely-signed webhook deliveries. They can then replay that exact signed body to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never inspected the header), so `Registry.process` invokes the registered handler with `WebhookMetadata#shop` set to the victim's domain. Any app logic that uses this `shop` value to look up/update per-tenant records (session storage, GDPR redaction handling, `shop/update`, `app/uninstalled`, etc.) will act on the victim tenant's data using attacker-chosen body content, i.e., a cross-tenant write/impersonation primitive.

### Likelihood Explanation
Exploitation requires no privileged credentials, no access token, and no interception of TLS traffic — it only requires installing the app once (available to any internet user for apps in an app store or dev shops) and issuing a normal HTTP POST with a modified header, which is straightforward.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of the signed payload, or independently verify that the `shop-domain` header corresponds to a shop known to be legitimately associated with the app instance/session before acting on it, rather than trusting the header once only the body's HMAC has been validated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving a legitimately signed webhook, e.g. `customers/update`, with headers `shopify-hmac-sha256: <valid-hmac-of-body>` and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker crafts the webhook `body` to contain data they control (e.g., customer email/name fields relevant to the app's handler logic).
3. Attacker POSTs the identical `raw_body` (and identical `hmac` header) to the app's webhook endpoint, but changes the `shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` with the shared `api_secret_key` — identical to step 1. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>)`, so the app processes attacker-controlled data as if it originated from the victim shop.
