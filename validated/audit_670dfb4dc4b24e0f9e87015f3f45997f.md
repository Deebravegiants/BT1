### Title
Unconstrained public signals in `MainEVMCircuitMin` allow forging a valid proof for zero-token Emporium calls, bypassing all fund-ownership/authorization checks - (File: `circuits/MainEVMCircuitMin.circom`)

### Summary
The Emporium "callback"-style sub-operations (`EmporiumOperation[]` decoded from `externalActionMetadata`) are, in the general path, cryptographically bound to the ZK proof through `calldataHash` → `signedMessageHash`, which is checked inside the main circuit against the depositor's stealth key. However, for the "min" path (`externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`), the contract switches to `formInputEmporiumMin`, which is verified against `MainEVMCircuitMin`. That circuit template declares `calldataHash` and `outTimeStamp` as public inputs but never uses them in any constraint — the only real logic is `message <== Poseidon(1)([messageSeed])`, where `messageSeed` is a private input freely chosen by the prover.

### Finding Description
- `contracts/CircomDataBuilder.sol` `formInputForCircom` routes to `formInputEmporiumMin` whenever `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`: [1](#0-0) 
- The resulting public input vector only contains `emporiumMessage`, `timeStamp`, `calldataHash` — no `rootHashHinkal`, no `signedMessageHash`, no nullifiers, no stealth-address components.
- `circuits/MainEVMCircuitMin.circom` is the circuit meant to be verified against this input set, and it does not constrain `calldataHash` or `outTimeStamp` to anything: [2](#0-1) 
  Since `message` is derived solely from an attacker-chosen `messageSeed`, and `calldataHash`/`outTimeStamp` are declared "public" but unused, *any* value for these public signals passes verification as long as the attacker sets `emporiumMessage` (`input[0]`) equal to `Poseidon(messageSeed)` for a self-chosen `messageSeed`.
- `HinkalHelper.performHinkalChecks` only re-derives `calldataHash` from the rest of `circomData` (a deterministic, non-secret computation anyone can perform) and checks the on-chain historical Merkle root exists — neither of which requires knowledge of any private key or ownership of shielded funds: [3](#0-2) 
- `dimensionsCheck` requires `inputNullifiers.length == dimensions.tokenNumber` (0 in this path), so zero nullifiers are consumed and no spend-authorization is needed at all: [4](#0-3) 
- With a trivially-forged valid proof, `Hinkal.transact` calls `_externalTransact` → `EmporiumUpgradeable.runAction`, decoding attacker-controlled `EmporiumStack` from `externalActionMetadata`: [5](#0-4) 
- If the attacker sets `stack.signerAddress = address(0)`, `verifyWallet` performs **no signature check at all** and simply marks the message used: [6](#0-5) 
  This routes every `EmporiumOperation` into the "stateless" branch, which executes `op.endpoint.call{value: op.value}(op.callData)` directly **from the Emporium contract itself** with only a check against the `callHinkalWallet`/`doSendToRelay` selectors: [7](#0-6) 

The equality this breaks is the intended invariant that any operation authorized under a ZK proof must be tied to (a) knowledge of a spendable UTXO/nullifier chain rooted in a valid Merkle root, or (b) an explicit EIP-712 signature from a wallet owner. The min-circuit path satisfies neither: it is a proof of nothing but knowledge of a self-chosen preimage.

### Impact Explanation
Because `EmporiumUpgradeable` acts as a pooled recipient for shielded balances left un-withdrawn from prior transactions (UTXOs tracked in `handleOut`), any ERC20/ETH balance the Emporium contract holds belongs collectively to legitimate users. An unprivileged attacker with no relationship to any deposit can forge a trivially valid proof for the zero-token Emporium path and drive `op.endpoint.call` to move Emporium's own held assets (e.g., calling an ERC20 `transfer` with Emporium as `msg.sender`) to an address of their choosing. This is direct theft of shielded/pooled user funds held by the protocol's Emporium contract — Critical impact.

### Likelihood Explanation
High. No secrets, no valid nullifiers, and no signature are required. The attacker only needs to: pick any `messageSeed`, compute `message = Poseidon(messageSeed)`, set `emporiumMessage = message`, fill in any historical (public) `rootHashHinkal`, set `erc20TokenAddresses = []`, `inputNullifiers = []`, `stack.signerAddress = address(0)`, and craft `stack.ops` for arbitrary calls. Generating the SNARK proof itself is trivial since `MainEVMCircuitMin` imposes no real constraint tying the public signals to anything secret.

### Recommendation
`MainEVMCircuitMin` must constrain `calldataHash` (and ideally bind it into a signed message the way the full circuit does via `signedMessageHash`), so that the Emporium-min path cannot be satisfied without the same fund-ownership/authorization guarantees as the full path. At minimum, require the circuit to prove knowledge of a signature over `calldataHash`/`emporiumMessage` tied to a stealth key that is validated against `rootHashHinkal`, rather than leaving these public signals fully unconstrained.

### Proof of Concept
1. Attacker (arbitrary EOA, no prior deposit) picks a random `messageSeed`, computes `message = Poseidon(messageSeed)` off-chain (matches the circuit's only constraint).
2. Constructs `circomData` with: `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = <Emporium address>`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{ ops: [maliciousOp], signerAddress: address(0), maxFee: 0, deadline: <future> })`, `emporiumMessage = message`, and `rootHashHinkal` set to any historically-inserted root.
3. Computes `calldataHash = getHashedCalldata(circomData)` locally (public deterministic function, no secret required) and generates a valid `MainEVMCircuitMin` proof for public inputs `[timeStamp, calldataHash]` and output `message`.
4. Calls `Hinkal.transact(...)`. `performHinkalChecks` passes (hash matches, root exists, dimensions match zero-length arrays, zero nullifiers required). `verifyProof` succeeds because the min circuit imposes no real constraint. `_externalTransact` invokes `EmporiumUpgradeable.runAction`, which decodes attacker's `EmporiumStack`, skips signature verification (`signerAddress == address(0)`), and executes `maliciousOp.endpoint.call{value: maliciousOp.value}(maliciousOp.callData)` from the Emporium contract, e.g., transferring out any ERC20/ETH balance the Emporium contract holds to the attacker.

*Note: I was unable to directly inspect `buildVerifierId`/verifier-selection logic in `Hinkal.sol` or the `EmporiumStack`/`handleOut` definitions to fully trace the exact pooled-balance mechanics, since these were not returned by the available search tools within the iteration budget. The core defect — unconstrained public signals in `MainEVMCircuitMin` — is directly confirmed from source and is sufficient on its own to break the proof-authorization invariant for the zero-token Emporium path.*

        uint16 index = 0;
