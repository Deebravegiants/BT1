### Title
Emporium "min" (empty-token) transactions bypass balance accounting and stealth-address binding, allowing value moved by ops to escape the balance equation - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which produces a public-input vector containing only `emporiumMessage`, `timeStamp`, and `calldataHash` [1](#0-0) . Because `dimensions.tokenNumber == 0` in this path, `dimensionsCheck` forces `amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`, `outCommitments` to length 0 as well [2](#0-1) . Consequently, both the balance-diff/slippage equality in `Hinkal.transact()` and the per-token balance accounting inside `EmporiumUpgradeable.runAction` are skipped entirely, since each loops over `circomData.erc20TokenAddresses.length` (0 iterations) [3](#0-2) [4](#0-3) .

### Finding Description
The `EmporiumUpgradeable.runAction` still executes arbitrary `EmporiumOperation`s (stateful `invokeWallet` calls or stateless `endpoint.call{value: op.value}`) regardless of `erc20TokenAddresses.length` [5](#0-4) . The balance-tracking/UTXO-creation loop that is supposed to capture any resulting value change (`handleOut`, which mints an output UTXO bound to `circomData.stealthAddressStructure`) only runs `circomData.erc20TokenAddresses.length` times [6](#0-5) . When that length is 0 (the "Emporium Min" path), this loop is skipped, so any token/ETH inflow the ops produce is silently dropped — no UTXO is created to represent it, and no on-chain "balance moved == UTXOs created" equality is enforced by `Hinkal.transact()` either, because its own equivalent balance-diff loop is keyed to the same `erc20TokenAddresses.length` [7](#0-6) .

Additionally, `circomData.stealthAddressStructure` (the recipient of any output UTXO) is bound to the circuit's public inputs only in `formBasicInput` (the "normal" path) [8](#0-7)  and is absent from both `formInputEmporiumMin` and from `getHashedCalldata1`/`getHashedCalldata2` [9](#0-8) . In the Emporium-Min branch this field is neither part of the SNARK public inputs nor part of `calldataHash`, so nothing on-chain cryptographically ties the output recipient to the prover's intent in that mode (moot only because no UTXO is minted in this branch — but it demonstrates that the "min" input schema was designed to skip all balance/output-binding checks that the normal schema enforces).

This breaks the balance equality the protocol otherwise strictly enforces everywhere else: "change in Hinkal/Emporium balance == change in off-chain UTXOs + change in on-chain UTXOs" [10](#0-9) . Any relay fee payment, however, is still executed unconditionally via `payRelayFees`'s fallback branch even for 0-length `erc20TokenAddresses`, since that fallback isn't gated on token count [11](#0-10) , showing the "min" path is not simply a no-op path but one that can still move value while skipping accounting.

### Impact Explanation
If an Emporium-Min transaction's ops (`invokeWallet` calls into `IHinkalWallet`, or stateless `endpoint.call{value: op.value}`) cause any ERC20/ETH to flow into the Emporium/Hinkal contracts, that value is not captured into any UTXO and cannot be later spent by any user — it is permanently stranded (temporary/permanent freezing of protocol funds), because the protocol's sole mechanism for representing spendable value is the UTXO commitment set, and this path structurally skips UTXO creation for any funds received. Conversely, if ops move funds *out* of the Emporium contract (e.g., an `invokeWallet` op draining a `IHinkalWallet`'s balance) with `erc20TokenAddresses.length == 0`, no balance-underflow check (`BalanceChangeShouldBePositive`) is performed, so an authorized wallet action could exfiltrate value with zero accounting.

### Likelihood Explanation
This requires triggering the `HINKAL_EMPORIUM_ACTION_ID` action with `circomData.erc20TokenAddresses.length == 0` while crafting an `EmporiumStack` whose `ops` still move value (e.g., via a signed `invokeWallet` operation or an unsigned stateless call with `op.value > 0`). Since a wallet signer must sign the `EmporiumOperation[]` for the stateful path (`verifyWallet`) [12](#0-11) , exploitation in the stateful case needs a signer's cooperation or a legitimately signed message whose author did not anticipate the "min" dimension bypasses balance accounting — a realistic UX/protocol-design gap rather than a purely theoretical one, since nothing in the signed payload format prevents combining `invokeWallet=true` with `erc20TokenAddresses.length == 0`.

### Recommendation
Either (a) disallow the Emporium-Min circuit selection whenever any `EmporiumOperation` in the metadata could move value (validate that `op.value == 0` and that stateful ops cannot alter `IHinkalWallet` balances when `erc20TokenAddresses.length == 0`), or (b) remove the `erc20TokenAddresses.length == 0` special-case entirely and always run the full `formBasicInput` balance-accounting path for Emporium actions so that `handleOut`/UTXO creation and the `Hinkal.transact()` balance-diff equality are never skippable. Additionally bind `stealthAddressStructure` into `getHashedCalldata`/`formInputEmporiumMin` for consistency even when not currently required, to avoid latent risk if the "min" path is later extended to create outputs.

### Proof of Concept
1. A relay/user submits `Hinkal.transact()` with `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses = []` (so `dimensions.tokenNumber == 0`), which routes public-input formation to `formInputEmporiumMin` [1](#0-0) .
2. `circomData.externalActionData.externalActionMetadata` decodes to an `EmporiumStack` whose `ops` includes a signed `invokeWallet=true` operation calling `IHinkalWallet.callHinkalWallet` that instructs the user's Hinkal wallet to send ERC20/ETH to `EmporiumUpgradeable` (or any address), verified via `verifyWallet` [13](#0-12) .
3. Because `circomData.erc20TokenAddresses.length == 0`, the `balancesBefore`/`balancesAfter`/`handleOut` loop never executes [4](#0-3) , so no UTXO is minted for the received tokens, and `Hinkal.transact()`'s own balance-diff/UTXO equality loop is likewise skipped (`erc20TokenAddresses.length == 0`) [7](#0-6) .
4. The received value sits in the Emporium contract with no corresponding UTXO commitment inserted, making it permanently unspendable through the protocol's normal UTXO-based withdrawal path.

Note: I was unable to fully trace `HinkalWallet.sol`'s `callHinkalWallet`/`doSendToRelay` implementation and `EmporiumStack.sol`'s exact struct layout within the available tool budget, so the precise call semantics of the stateful `invokeWallet` path (e.g., whether it can be forced to move value even when the wallet owner did not intend a "min" mode call) could not be fully confirmed from source and should be verified directly in those files.

        );

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }

        if (utxoSetLength < circomData.erc20TokenAddresses.length) {
            utxoSet.skipLast(
                circomData.erc20TokenAddresses.length - utxoSetLength
            );

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
