## Title
Webhook cross-tenant impersonation via HMAC that never binds the `shop-domain` header - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the *unauthenticated* `X-Shopify-Shop-Domain` header to decide which merchant the payload belongs to. Because the signature never binds the shop identifier, any party who can obtain one valid `(body, hmac)` pair for the shared app secret (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC pair while substituting an arbitrary victim shop domain, and the gem will process it as if it originated from the victim shop. This mirrors the reported bug class of "a field acted on but not covered by the [validation]" — here the shop identity used downstream is not the shop identity that was cryptographically verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers and are never part of the signed string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the received HMAC: [3](#0-2) 

`Registry.process` gates on that same body-only HMAC and then unconditionally forwards `request.shop` (the unauthenticated header) to the webhook handler as the tenant identifier: [4](#0-3) 

Because a single app's `api_secret_key` is shared across every merchant that installs the app, the HMAC over an identical body (e.g. `"{}"`, or any topic payload with predictable/attacker-controllable content the attacker's own shop legitimately receives) is identical no matter which shop it was originally destined for. An attacker who operates their own store with the target app installed can:
1. Trigger (or passively receive) a legitimate webhook delivery to their own store, capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair.
2. Replay an HTTP request to the app's webhook endpoint with the same body/HMAC, but with `x-shopify-shop-domain` (or `shopify-shop-domain`) changed to the victim's shop domain.
3. `HmacValidator.validate` passes (it never looked at the shop header), and `Registry.process` calls the handler with `shop: <victim shop>`, `body: <attacker-chosen JSON>`.

This is exactly the pattern flagged in scope: "a shop authenticated versus the shop stored as a session key" — the value verified by the cryptographic check (body bytes signed with the shared secret) is not the same identity binding (`shop`) that the application logic keys its per-tenant processing on.

### Impact Explanation
Downstream host applications typically use `WebhookMetadata#shop` to look up/act on a specific merchant's stored data (e.g., update records, trigger uninstall/GDPR flows, mark subscription state, etc.) based solely on the trust that the gem gave them a validated webhook for that shop. Because the shop identifier carries no cryptographic binding to the payload, this enables cross-tenant confusion/injection of attacker-controlled webhook payloads attributed to a victim merchant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only that the attacker operate (or otherwise obtain webhooks from) any shop with the same app installed — a low bar, since apps are typically installed by many independent unprivileged merchants. No access token, `client_secret`, or privileged account is needed; the attacker only needs one legitimately-delivered webhook body+HMAC pair for their own shop and the ability to POST to the app's public webhook endpoint with a modified shop header.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the string that is HMAC-verified (or otherwise cryptographically bind them, e.g. via a per-shop signing context) so that a payload signed for one shop cannot be replayed and attributed to another shop. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain, and `HmacValidator`/`Registry.process` should reject webhooks whose header-derived shop cannot be tied to the signed content.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives (or triggers) a real webhook, e.g. topic `app/uninstalled` with body `{}`, capturing header `x-shopify-hmac-sha256: <H>` (computed as `HMAC-SHA256(api_secret_key, "{}")`, per `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `{}` and the same `x-shopify-hmac-sha256: <H>`, but sets:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <H>
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, "{}") == H`, per `lib/shopify_api/webhooks/registry.rb` line 190 and `lib/shopify_api/utils/hmac_validator.rb` lines 12-31.
4. The registered handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {}, ...)`, causing the host application to perform victim-shop-scoped actions (e.g., uninstall cleanup) triggered entirely by the attacker.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
