### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by webhook handlers directly from the unauthenticated `x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only verifies the raw request body against the shared `client_secret`. The shop identity that the application acts on is never bound to the value that was actually HMAC-signed by Shopify, breaking the equality `hmac_verified_bytes == identity_acted_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

and `shop` is pulled straight from the `x-shopify-shop-domain` (or legacy `shopify-shop-domain`) header without any cryptographic binding to that header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) — none of which are covered by that HMAC — to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the HMAC key is the app's `client_secret`, which is identical for every shop that has the app installed, any body+HMAC pair that Shopify legitimately delivered for one shop (e.g., a shop the attacker owns/controls, or one whose webhook payload the attacker can observe) remains a byte-for-byte valid signature no matter which `shop-domain` header value is attached to the replayed HTTP request. The signature proves only "this body was signed by our client_secret," not "this body originated from shop X." An attacker who possesses one valid (body, hmac) pair — trivially obtainable by installing the app on their own store and capturing the resulting outbound webhook — can replay that exact request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

This is the same class of bug as the reported issue: a value acted upon by the state machine (there, deposit signature outcome; here, the shop identity used to route/attribute webhook data) is not actually bound by the check that is supposed to authenticate it (there, the deposit signature check as gating logic; here, the HMAC as identity binding for the shop field).

### Impact Explanation
Any application relying on `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry.process` to select which tenant's data to create, update, or delete (a common and expected usage pattern per this gem's own documentation) can be made to apply attacker-controlled webhook payloads to a victim shop's tenant context, or vice versa attribute a victim's legitimate event data to an attacker-chosen shop record. This crosses a tenant boundary using only a replayed, previously-valid HTTP request with a modified header, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires: (1) obtaining one legitimate (body, hmac) pair, which any merchant who installs the app can trivially capture by observing traffic to their own webhook endpoint, and (2) replaying that request to the target app's public webhook URL with a modified `shop-domain` header. No access token, `client_secret`, or privileged account is needed — this is achievable by any unprivileged party who can install the target app once and control an HTTP client, which is a normal, low-barrier interaction with a public Shopify app.

### Recommendation
Bind the identity fields the application will act on to the HMAC-verified payload rather than trusting bare headers. Concretely, include `shop`, `topic`, and `webhook-id` in the signed string (`to_signable_string`) so `Utils::HmacValidator.validate` fails if any of them are altered, or cross-validate `request.shop` against the shop embedded in the parsed webhook body/session context before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as the sole tenant-selection key without additional verification (e.g., confirming an active, stored offline session exists for that shop before trusting the payload).

### Proof of Concept
1. App developer's app is installed on `attacker.myshopify.com`; Shopify sends a legitimate webhook:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `B`.
2. Attacker intercepts/observes this HTTP request (their own traffic to their own endpoint).
3. Attacker resends the identical body `B` and `hmac-sha256` value to the same app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) recomputes HMAC over body `B` only, matches the (unchanged) signature, and returns `true`.
5. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-200`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the app's handler, which now processes attacker-supplied content under the victim shop's identity.
