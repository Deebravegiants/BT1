### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) Header Values Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` (and `topic`, `webhook_id`, `api_version`) values taken from HTTP headers when constructing the `WebhookMetadata` passed to the app's handler. Because those header values are never included in the signed content, an attacker who possesses one genuine `(body, hmac)` pair can freely relabel which shop/tenant that payload is attributed to, breaking the binding between "bytes cryptographically verified" and "identity acted upon."

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for a webhook `Request` this method returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values, however, come from separate HTTP headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC, then builds `WebhookMetadata` directly from these unauthenticated headers and dispatches it to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop_header == shop_that_actually_produced(body)`.

In reality, the gem only proves `hmac_valid(body)`; it does nothing to prove that `shop_header` (or `topic`/`webhook_id`) is the value Shopify associated with that specific `body` when it signed it. Since the HMAC secret (`Context.api_secret_key`) is shared across all shops installed on the app, any party who can obtain one legitimate `(body, hmac)` pair — for instance, an unprivileged merchant who installed the app on their own shop and received a genuine webhook for that shop — can replay the same `body`/`hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a different, victim shop's domain/topic/id. `Registry.process` will still report `Utils::HmacValidator.validate(request)` as `true` (it never inspected the headers) and will forward a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
Because host applications are documented to rely on `data.shop` (and `data.topic`/`data.webhook_id`) from `WebhookMetadata` as the authoritative tenant identifier for processing/enqueuing work (as shown in the gem's own documentation example, which threads `data.shop` straight into `shop_domain` for later processing), this breaks the shop-authentication boundary and enables cross-tenant data injection/attribution — an app can be made to process, store, or act on webhook content under the wrong shop's identity. This satisfies the Critical "cross-tenant access" impact category: an unprivileged actor (a legitimately-installed but unrelated merchant) can make the app believe a payload originated from a shop they do not control.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action, requiring no special credentials or access token) automatically receives genuine webhook deliveries with valid `(body, hmac)` pairs for their own shop. Crafting a forged request that swaps only the `shop`/`topic`/`webhook_id` headers while keeping the same body/HMAC requires no cryptographic secret and no elevated access — only the ability to send an HTTP POST to the app's public webhook endpoint, which is by design internet-reachable. This makes exploitation straightforward for any party who has ever installed the app on any shop.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the HMAC-signed content (or otherwise cryptographically tie them to the verified body) rather than trusting header values that sit outside the signature. At minimum, `Utils::HmacValidator.validate` (or `Registry.process`) should include the `shop-domain`, `topic`, and `webhook-id` headers in the signable string so tampering with any of them invalidates the signature, matching what is actually authenticated versus what is acted upon.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `hmac` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `topic`/`webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(body) == H` — this still passes because `B` and `H` are unchanged. [3](#0-2) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
