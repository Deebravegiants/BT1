### Title
Zero-amount order inputs bypass validation in `placeOrder`'s predispatch escrow path - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` on the Tron deployment validates that every `order.inputs[i].amount` is non-zero only in the non-predispatch escrow branch, but omits this check entirely in the predispatch (call-dispatcher) escrow branch, allowing a user to register a committed order containing zero-value input legs.

### Finding Description
In the reference LooksRare bug, `depositETHIntoMultipleRounds` validated only the aggregate `msg.value` and not each individual `amounts[i]`, letting a caller push a `0` entry into the round's deposits while relying on other non-zero entries to pass the total check.

The same class of defect exists in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`. When an order carries `predispatch.call`/`predispatch.assets`, the escrow loop over `order.inputs` never checks `order.inputs[i].amount == 0`: [1](#0-0) 

Compare this to the `else` branch a few lines below, which is invoked when there is no predispatch, and does perform the per-element zero check before escrowing: [2](#0-1) 

The upstream/canonical `evm/src/apps/IntentGatewayV2.sol` implementation enforces the zero check in *both* branches of the equivalent logic (`if (order.inputs[i].amount == 0) revert InvalidInput();` appears both in the predispatch sweep loop and the non-predispatch loop): [3](#0-2) [4](#0-3) 

This confirms the Tron variant's predispatch branch is missing the same guard that exists in the sibling code path and in the "canonical" EVM contract, which is a direct structural analog of the reported `depositETHIntoMultipleRounds` defect (aggregate-only validation, no per-element check) — just relocated from a `msg.value` total check to a `balance < requiredAmount` per-token check that is trivially satisfied by `requiredAmount == 0`.

### Impact Explanation
An order with a `0`-amount input token is a legitimate-looking committed order (`OrderPlaced` is emitted, `_orders[commitment][token] += reducedInputs[i].amount` records a zero-value entry) despite representing no real escrowed value for that leg. Because `order.inputs` participates in the `commitment` hash and is echoed to solvers/fillers as part of what they must fill, a zero-value leg can be used to:
- Pollute the `inputs` array that downstream fill logic (`IntrinsicIntents`/`ExtrinsicIntents`) iterates over token-by-token, including a token entry the user never actually funded, potentially confusing fill/refund accounting keyed by `(commitment, token)`.
- Fabricate cheap/no-cost multi-leg orders that make the order eligible for behavior gated on "having N inputs" without correspondingly escrowing value for all of them, undermining the fairness/soundness assumption that every declared input is backed by real escrowed funds — directly analogous to inflating `round.deposits`/`round.numberOfParticipants` for free in the original report.

This is an unauthorized state manipulation (recording escrow bookkeeping for unfunded token legs) reachable by any unprivileged user submitting an order transaction, matching the required "unauthorized app action" severity bar.

### Likelihood Explanation
Trivial to trigger: any user simply calls `placeOrder` with `predispatch.call`/`predispatch.assets` non-empty and sets one of the `order.inputs[i].amount` entries to `0` (with at least one real predispatch asset so the branch is entered). No special privileges or timing are required — a single transaction from an ordinary caller is sufficient.

### Recommendation
Add the same zero-amount guard used in the non-predispatch branch to the predispatch sweep loop in `evm/tron/contracts/apps/IntentGatewayV2.sol`:

```solidity
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    address token = address(uint160(uint256(order.inputs[i].token)));
    ...
```
mirroring `evm/src/apps/IntentGatewayV2.sol` line 264, so every declared input leg is required to carry a non-zero amount regardless of which escrow path is taken.

### Proof of Concept
1. Caller builds `order.inputs = [ {token: TKN_A, amount: 0}, {token: TKN_B, amount: 100} ]`.
2. Caller sets `order.predispatch.call` and `order.predispatch.assets` to a valid non-empty predispatch (e.g., unwrap some LP position covering `TKN_B`'s 100 units), routing execution into the branch at lines 389–449.
3. `placeOrder` proceeds: the loop at lines 418–446 never reverts for `TKN_A` because `requiredAmount = 0` trivially satisfies `balance < requiredAmount`; `_orders[commitment][TKN_A] += reducedInputs[0].amount` (=0) is recorded.
4. `OrderPlaced` is emitted with `inputs` containing the zero-amount `TKN_A` leg, and the order is now live with a bogus, unfunded input leg baked into its commitment — something the non-predispatch branch (and the canonical EVM contract) would have rejected with `InvalidInput()`.
