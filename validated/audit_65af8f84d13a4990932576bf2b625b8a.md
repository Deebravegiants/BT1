### Title
Missing shop-domain allow-list check lets `client_secret` be sent to a host derived solely from an unvalidated JWT `dest` claim in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Utils::ShopValidator.sanitize!` was introduced specifically to restrict the shop domain used as the destination host for OAuth token requests to Shopify's trusted domain suffixes (`myshopify.com`, `shopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`) [1](#0-0) . Every sibling OAuth-token-issuing method calls it before building the request that carries `client_id`/`client_secret`: `ClientCredentials.client_credentials` [2](#0-1) , `RefreshToken.refresh_access_token` [3](#0-2) , and `TokenExchange.migrate_to_expiring_token` [4](#0-3) . `TokenExchange.exchange_token` — the primary, non-deprecated entry point for embedded-app token exchange — does not: it takes the destination shop straight from the JWT `dest` claim with no sanitization.

### Finding Description
In `exchange_token`, the target host is computed as: [5](#0-4) 

`jwt_payload.shop` simply strips `"https://"` from the raw `dest` claim with no domain allow-listing: [6](#0-5) 

`JwtPayload#initialize` verifies the HS256 signature and checks `aud == Context.api_key`, but never validates that `iss`/`dest` is a trusted Shopify domain: [7](#0-6) 

That unvalidated `shop` string is then used to construct the `HttpClient`, whose base URI is built directly from `session.shop`: [8](#0-7) 

so the POST body containing `client_id`/`client_secret` is sent to `https://#{dest_shop}/admin/oauth/access_token` with `dest_shop` unconstrained by `ShopValidator`.

The equality/binding that should hold — and does hold in every sibling method — is:
`host that receives client_secret == ShopValidator.sanitize!(shop)`

In `exchange_token` this instead becomes:
`host that receives client_secret == raw(jwt_payload.dest)`, i.e. the host is validated only by JWT-signature verification, not by the domain allow-list that the rest of the library treats as a required second control.

### Impact Explanation
This is a credential-exfiltration path for the app's `client_secret`: whoever controls, or can influence, the `dest` value inside a session token accepted by this code path can cause the app's server to make a same-request, credential-bearing POST to an attacker-chosen host. Because this control was deliberately added to every other token-issuing method (PR referenced in `CHANGELOG.md` under 16.3.0 — "Add `ShopifyAPI::Utils::ShopValidator`... Derive the target shop for `exchange_token` from the session token's `dest` claim"), its absence in `exchange_token` is an inconsistency in the gem's own trust model, not an intentional design choice, and is the exact class of "used the wrong/less-specific bound value" bug described in the reference report (using a broader/looser value where a scoped, validated one was expected elsewhere in the same code family).

### Likelihood Explanation
Exploitation requires a session token (`id_token`) that the gem accepts as validly signed (HS256 with `Context.api_secret_key`) but whose `dest` claim is not a genuine Shopify/myshopify domain. Under normal operation these tokens are minted only by Shopify, so likelihood is low absent secret compromise or an additional weakness allowing `dest` tampering (e.g., a future JWT-library behavior change, alternate signing-key handling via `Context.old_api_secret_key`, or any host-side logic that constructs/passes through a token without the same guarantees). This mirrors the referenced report's own framing: the flaw is real and provable in code today, but its practical trigger depends on a configuration/trust condition, hence "Medium impact, Low likelihood" is the appropriate rating, matching the reporter's own severity framing for an analogous "wrong-value" defect.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` the same way the other three methods do before using it to construct `shop_session`:
```ruby
dest_shop = ShopifyAPI::Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
This restores the invariant that `client_secret` is only ever sent to a host that has passed `ShopValidator.sanitize!`, matching `client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token`.

### Proof of Concept
Root-cause code path (no external report needed, purely from static review since dynamically forging a validly-signed token requires the secret, which is out of scope to demonstrate here):
1. `exchange_token` decodes an `id_token` via `JwtPayload.new(session_token)` — signature and `aud` are checked, `dest` is not domain-checked: [7](#0-6) 
2. `dest_shop = jwt_payload.shop` is used directly to build `shop_session`, with no call to `Utils::ShopValidator.sanitize!` anywhere in the method: [9](#0-8) 
3. `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` derives its request host from `session.shop` unconditionally: [8](#0-7) 
4. `client.request(...)` sends a POST whose body includes `client_id` and `client_secret` in plaintext to that host: [10](#0-9) 

Contrast with the three sibling methods, all of which insert `Utils::ShopValidator.sanitize!(shop)` between input and `Session.new(shop: ...)`, which is the missing line in `exchange_token`. [11](#0-10) [12](#0-11) [13](#0-12) 

**Note on uncertainty:** I could not fully verify whether any upstream/host-application-facing path allows a JWT with attacker-controlled `dest` to pass `JwtPayload`'s signature check without possessing `Context.api_secret_key` (which would be required to make this concretely exploitable end-to-end rather than a defense-in-depth gap). No such path was found within `lib/shopify_api/**` in this review.
