## Title
Excess native `msg.value` sent to `EvmHost.dispatch()`/`fundRequest()` is permanently trapped in the contract instead of refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all swap any supplied `msg.value` for an exact amount of fee token via `IUniswapV2Router02.swapETHForExactTokens`. This is the same class of "user pays more than the protocol actually needs" bug flagged in the external report, but here the consequence is worse: excess ETH is not returned to the user at all — it is refunded by Uniswap to `EvmHost` itself (since `EvmHost` is the caller of the router), permanently commingling it with protocol funds with no user-facing reclaim path.

### Finding Description
In `EvmHost.sol`, each of the three fee-collecting entry points forwards the caller's entire `msg.value` to Uniswap and requests an exact output amount: [1](#0-0) [2](#0-1) [3](#0-2) 

`IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` computes `amounts[0] = getAmountsIn(fee, path)[0]`, requires `msg.value >= amounts[0]`, performs the swap, and refunds any leftover ETH (`msg.value - amounts[0]`) to `msg.sender` of that call — which is `EvmHost`, not the original transaction sender. There is no code afterward in `dispatch()`/`fundRequest()` that forwards this refunded ETH back to `_msgSender()`/`post.payer`/`get.dest` payer; the ETH balance simply accrues on the `EvmHost` contract.

Because the Uniswap price used for `getAmountsIn` at execution time can differ from whatever off-chain `quote()` estimate the caller used (per the docs' own warning that `quote()` is vulnerable to sandwiching and slippage between quoting and execution — see `docs/content/developers/evm/messaging/post-requests.mdx:236-238`), callers routinely must send `msg.value` with some safety margin above the exact swap input, exactly the same “must overpay a little to avoid reverting” pattern the external report describes for `_createPool()`. Except here, instead of reverting on insufficient value, the code silently absorbs any *excess* value with no accounting and no attribution to the depositor.

The only way this stranded ETH can move is via `EvmHost.withdraw(WithdrawParams)`, restricted to `_hostParams.hostManager` (i.e., only cross-chain governance via `HostManager.onAccept`): [4](#0-3) 

That function pays out to an arbitrary `beneficiary` chosen by governance — it has no notion of "refund the original overpayer." So funds accidentally overpaid by any unprivileged user dispatching a message are, from that user's perspective, permanently unrecoverable; they can at best be swept by governance to some other address, never automatically returned.

### Impact Explanation
Any unprivileged user or integrating `HyperApp` contract calling `dispatch{value: msg.value}(...)` or `fundRequest{value: msg.value}(...)` with even a small safety margin above the exact required native amount (which is expected/recommended usage, since `quote()` is explicitly documented as an off-chain, slippage-prone estimate) loses that margin permanently — it is not refunded to them and cannot be reclaimed by them. This is a direct, unprivileged loss/freezing of user funds reachable from a single transaction, worse than the `Allo._createPool()` analog where the user merely has to compute an extra few wei of precision; here the user's genuine safety buffer against slippage is unconditionally forfeited.

### Likelihood Explanation
High. This triggers on completely ordinary usage: any dApp or user dispatching a POST/GET request or funding a request with native token and providing more than the exact minimum computed by Uniswap at execution time (which is essentially guaranteed whenever there is any price movement, rounding, or safety margin between quoting and execution) loses the excess. No special privileges or attacker setup are required.

### Recommendation
After the `swapETHForExactTokens` call, capture the actual amount spent (`amounts[0]` return value) and refund `msg.value - amounts[0]` back to `_msgSender()` (for `dispatch`) or the designated payer, instead of allowing Uniswap's refund to land on `EvmHost`'s own balance. Alternatively, precompute the exact required input via `getAmountsIn` before swapping and only forward that amount, refunding the remainder immediately.

### Proof of Concept
1. Caller estimates the native fee needed off-chain via `quote()`, which the docs explicitly warn is subject to sandwiching/slippage, and adds a safety buffer (e.g., 5%) before submitting the transaction.
2. Caller calls `IDispatcher(host).dispatch{value: quotedFee * 1.05}(post)`.
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` swaps only the exact ETH needed for `post.fee` fee tokens and refunds the remaining ~5% ETH to `address(this)` (`EvmHost`), because `EvmHost` is `msg.sender` in that call.
4. The refunded ETH is now part of `EvmHost`'s native balance with no record tying it to the original caller; it can only be extracted later via governance's `withdraw()` to an arbitrary beneficiary, never automatically back to the depositor. The caller's excess payment is permanently lost to them.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
