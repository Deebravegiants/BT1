### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not covered by the HMAC signature, allowing shop/tenant spoofing on webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop-domain` header (and `topic`, `webhook_id`, `api_version`) are taken directly from unauthenticated HTTP headers and are never part of the signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` to attribute the payload to a tenant after HMAC validation succeeds, breaking the intended binding between "HMAC-verified" and "came from the shop it claims to be from."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `to_signable_string` (the body) and compares it against the secret-derived HMAC — it never touches `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` raises if HMAC validation fails, then immediately hands the *unauthenticated* `request.shop` value to the handler as the tenant identifier, with no further check that it matches anything the app actually knows about that HMAC: [4](#0-3) 

The equality the gem implicitly claims to enforce is:
`shop that produced a valid HMAC == shop attributed to WebhookMetadata`

In reality the gem only proves:
`api_secret_key produced this HMAC over this raw_body`

Because the `shop-domain` (and `topic`/`webhook_id`) header is excluded from the signed string, any request carrying a `(raw_body, hmac)` pair that is valid for the app's shared `api_secret_key` will pass validation regardless of what `shop-domain` header accompanies it. Since a single app-level `api_secret_key` is shared across every shop that installs the app, an unprivileged merchant who has installed the app can capture a legitimately-signed webhook delivered to their own store (a valid `raw_body` + `hmac-sha256` pair) and replay it to the app's webhook endpoint with an arbitrary `shop-domain` / `topic` / `webhook_id` header of their choosing. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will hand the forged `shop` value straight to the host application's handler as `WebhookMetadata#shop`.

### Impact Explanation
This breaks tenant isolation for any application that trusts `WebhookMetadata#shop` (as the gem's own documented API tells developers to do) to route data into per-shop storage. A malicious merchant can inject attacker-controlled webhook data (order/customer/app-uninstalled payloads, etc., re-signed under their own valid HMAC) attributed to a victim shop, resulting in cross-tenant data confusion/injection — this falls under the Critical "cross-tenant access" category, since the vulnerability crosses the tenant boundary the gem is supposed to enforce via HMAC.

### Likelihood Explanation
The attacker only needs to be an unprivileged internet user who has installed the target app on their own store (a normal, unprivileged install) — no leaked `api_secret_key`, no access token, and no privileged account is required. They only need to legitimately receive one webhook to their own shop and replay it with modified headers, which is straightforward given the gem's `Request` class accepts headers directly from the caller (Rack env / controller headers) without any origin verification (e.g., no IP allow-listing is performed by this gem).

### Recommendation
Bind the shop/topic/webhook identity into the HMAC-verified payload rather than trusting bare headers post-validation. At minimum, `to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` (or the gem should document/enforce that host apps must independently verify `shop-domain` corresponds to a shop with an existing, valid session/webhook registration for that specific topic+id before trusting `WebhookMetadata#shop`). Practically, since Shopify's real webhook HMAC is computed only over the body by protocol, the gem should not silently expose `request.shop` as trustworthy from `HmacValidator.validate` alone — it should require the caller to check that a registration exists for `(shop, topic, webhook_id)` combination, or explicitly document this gap so host apps don't assume HMAC success implies shop authenticity.

### Proof of Concept
1. Merchant M installs the app; the app registers webhooks and Shopify begins sending signed webhooks to M's endpoint with `body`, and headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: m-shop.myshopify.com`, `x-shopify-topic`, `x-shopify-webhook-id`.
2. M captures one such delivery: `(raw_body, hmac)` is valid for the app's `api_secret_key` (shared across all installs).
3. M crafts a new HTTP request to the app's webhook endpoint using the same `raw_body`/`hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `topic`/`webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` parses these headers un-checked [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [6](#0-5) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and the host app processes/persists attacker-controlled data under the victim tenant's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
