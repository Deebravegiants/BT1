### Title
Emporium `signerAddress==0` ops bypass all balance accounting when `erc20TokenAddresses.length==0` (Min-circuit path) - arbitrary call as Emporium's identity with zero fund tracking - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `formInputForCircom` routes proof-building to `formInputEmporiumMin`, which only feeds `MainEVMCircuitMin` a trivial `message == Poseidon(messageSeed)` constraint [1](#0-0) [2](#0-1) . In `EmporiumUpgradeable.runAction`, `verifyWallet` skips all signature verification of the ops when `stack.signerAddress == address(0)`, only marking `usedMessages` [3](#0-2) , while the op-execution loop runs unconditionally regardless of `erc20TokenAddresses` length [4](#0-3) .

### Finding Description
The broken equality: **the set of assets Emporium's identity (`msg.sender == Emporium`) can move via `op.endpoint.call(...)` != the set of assets whose balance is tracked in `balancesBefore`/`balancesAfter`/`circomData.erc20TokenAddresses`**. When the attacker declares `erc20TokenAddresses = []`:

- `dimensionsCheck` in `HinkalHelper.sol` only requires `erc20TokenAddresses.length == dimensions.tokenNumber`, so `tokenNumber = 0` passes trivially [5](#0-4) .
- In `Hinkal.transact`, the entire balance-diff/slippage/UTXO-reconciliation loop iterates `circomData.erc20TokenAddresses.length` times — zero iterations — so no balance check of any kind is performed at the `Hinkal` level [6](#0-5) .
- In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed only over `circomData.erc20TokenAddresses` (empty), and `deltaAmountChanges` is also an empty array, so the entire `balanceChange`/`BalanceChangeShouldBePositive` reconciliation loop iterates zero times [7](#0-6) .
- Meanwhile the `for (uint256 i = 0; i < stack.ops.length; i++)` loop still executes every op via `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium` [8](#0-7) .
- `verifyWallet` requires **no signature at all** when `stack.signerAddress == address(0)` — it only checks/marks `usedMessages[emporiumMessage]` [9](#0-8) .
- The `calldataHash` check in `HinkalHelper.performHinkalChecks` only verifies self-consistency of the submitted calldata against its own hash (`getHashedCalldata(circomData) == circomData.calldataHash`) — it does not constrain the *content* of `externalActionMetadata`/ops to anything legitimate, nor does it require `signerAddress != 0` [10](#0-9) .
- The circuit itself (`MainEVMCircuitMin`) has zero constraints tying `emporiumMessage`, `stack.ops`, or `signerAddress` to any real UTXO ownership — it merely proves knowledge of a self-chosen `messageSeed` [2](#0-1) .

Consequently, any unprivileged caller can submit `transact` with `erc20TokenAddresses=[]`, an `EmporiumStack{signerAddress:0, ops:[...]}` containing an arbitrary call (e.g., `IERC20.transferFrom(victim, attacker, allowance)` against a router/contract that trusts Emporium or holds a stale approval from Emporium), and a real but trivial Min-circuit proof of a self-chosen `messageSeed`. No balance-based check anywhere in `Hinkal.sol` or `EmporiumUpgradeable.sol` records or restricts this movement, because the entire accounting mechanism is keyed off `circomData.erc20TokenAddresses`, which the attacker controls and sets to empty.

### Impact Explanation
Direct theft of third-party or protocol funds that are reachable through Emporium's `msg.sender` identity (approvals granted to Emporium, or balances resting in Emporium, or trust relationships where a downstream router treats `msg.sender == Emporium` specially) — with zero economic accounting or reversion. This is a Critical impact: it enables an unprivileged attacker to execute arbitrary calls as Emporium's identity, unconstrained by any proof of asset ownership, and is repeatable once per unused `emporiumMessage` value (attacker can pick a fresh one every transaction, so effectively unlimited repeats).

### Likelihood Explanation
Preconditions required: (1) some address must have granted Emporium an ERC20 allowance, left a balance in Emporium, or trust Emporium as a privileged caller (a realistic residual state from stuck swaps, dust, or misconfigured routers integrated with Emporium) and (2) a verifier for the Min-circuit at `dimensions = (tokenNumber:0, nullifierAmount:0, outputAmount:0)` combined with the Emporium action id must be registered and reachable via `buildVerifierId`/`VerifierFacade`. The attacker's cost is only generating one cheap Poseidon-preimage proof — no real UTXO or deposit is required. This is a very low-cost, highly repeatable attack once the preconditions exist; verifier registration for this dimension/action combination could not be confirmed from the reviewed files and would need to be checked in `VerifierFacade`/`contracts/verifiers` (out of scope per the rules) to establish full exploitability, but the on-chain authorization/accounting logic itself contains no independent barrier.

### Recommendation
- Do not allow `signerAddress == address(0)` to bypass authorization for stateless ops that call arbitrary `endpoint`/`callData` — require either a valid signature over the ops or restrict stateless (`signerAddress==0`) ops to a strict allowlist of endpoints/selectors known not to move third-party funds.
- Do not let `erc20TokenAddresses.length == 0` bypass balance tracking for the Emporium action; either forbid the Emporium action from using the Min-circuit path entirely, or independently track balances of any token that could be affected by the executed `ops`, not just the declared `erc20TokenAddresses`.
- Bind the circuit's public/private signals to the actual `EmporiumStack` (ops, endpoints, signer) so that `calldataHash`/circuit constraints tie the proved witness to the specific call being executed, rather than relying purely on a self-consistency hash check.

### Proof of Concept
Foundry fork test outline:
1. Deploy `EmporiumUpgradeable` (or use existing deployment) and set up a victim contract/EOA that grants an ERC20 `allowance(victim, Emporium address, X)` (simulating leftover approval from a prior interaction).
2. Deploy `Hinkal`, `HinkalHelper`, register Emporium as external action for `HINKAL_EMPORIUM_ACTION_ID`.
3. Craft `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = []`, `outCommitments = []`, `dimensions = {tokenNumber:0, nullifierAmount:0, outputAmount:0}`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress:address(0), ops:[{endpoint: erc20, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transferFrom,(victim, attacker, X))}]})`.
4. Compute `calldataHash = getHashedCalldata(circomData)` off-chain and set it in `circomData`.
5. Generate a real snarkjs proof for `MainEVMCircuitMin` with a self-chosen `messageSeed`, setting `emporiumMessage = Poseidon(messageSeed)`.
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from an attacker EOA with no prior deposits/UTXOs.
7. Assert: `victim`'s ERC20 balance decreases by `X`, attacker's balance increases by `X`, while `circomData.erc20TokenAddresses.length == 0` and no `require` in `Hinkal.transact` or `EmporiumUpgradeable.runAction` reverted or recorded any balance change (i.e., `balancesBefore.length == balancesAfter.length == 0`).

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
