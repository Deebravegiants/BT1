Confirmed: `CheckPasswordHash` uses `bcrypt.CompareHashAndPassword`, which is intentionally slow (~10s of milliseconds), while a failed `FindUser` SQL lookup returns immediately without ever reaching bcrypt.

### Title
Timing-based user enumeration on `/sessions` login endpoint via early-return on unknown email - (File: `core/sessions/localauth/orm.go`)

### Summary
The local authentication `CreateSession` flow calls `FindUser` first, and returns an error immediately for a nonexistent email — before ever invoking the constant-time email compare or the bcrypt password check. Because bcrypt hashing is deliberately expensive, requests for valid vs. invalid emails have measurably different response latencies, letting an unauthenticated caller enumerate registered node API user emails.

### Finding Description
`SessionsController.Create` (`core/web/sessions_controller.go:29-68`) accepts an unauthenticated POST to `/sessions` and forwards `sr` directly into `AuthenticationProvider().CreateSession`. For the local auth provider, `orm.CreateSession` (`core/sessions/localauth/orm.go:144-162`) is implemented as:

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	...
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) { ... }
	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) { ... }
``` [1](#0-0) 

`FindUser` is a straight `SELECT * FROM users WHERE lower(email) = lower($1)` (`core/sessions/localauth/orm.go:44-58`), which fails fast with `sql.ErrNoRows` for an unregistered email — the function returns before the `constantTimeEmailCompare` and, crucially, before `utils.CheckPasswordHash` is ever called. [2](#0-1) 

`CheckPasswordHash` wraps `bcrypt.CompareHashAndPassword`, which is intentionally computationally expensive (default cost factor), taking on the order of tens of milliseconds per call: [3](#0-2) 

So: a request with a **registered** email always pays the bcrypt cost (even with a wrong password), while a request with an **unregistered** email returns almost instantly after a single indexed DB lookup. This is exactly the same bug class as GHSA-5w46-g9pq-wh6f (Filament) — an observable timing discrepancy on the login endpoint that discloses account existence.

The `constantTimeEmailCompare` helper present in the same file (`core/sessions/localauth/orm.go:232-241`) demonstrates the authors were already aware of and mitigating a timing side channel for the email-match step, but the mitigation is bypassed by the early `return "", err` on `FindUser` failure — the constant-time compare code path is unreachable for nonexistent emails. [4](#0-3) 

The same pattern is duplicated in the LDAP and OIDC local-fallback authenticators: [5](#0-4) [6](#0-5) 

### Impact Explanation
An unauthenticated attacker hitting `POST /sessions` (`core/web/sessions_controller.go:29`) repeatedly with different candidate emails can distinguish registered vs. unregistered node API accounts purely from response latency, without needing valid credentials. This discloses which operator/admin email addresses exist on a chainlink node's Operator UI/API, which can be used to target credential-stuffing, phishing, or brute-force attempts against known valid accounts. Impact is limited to confidentiality of account existence (matches the CVSS `C:L/I:N/A:N` profile of the referenced advisory) — it does not itself grant a bypass of authentication.

### Likelihood Explanation
The `/sessions` endpoint is unauthenticated and directly reachable from any client with network access to the node's web/API port (`core/web/sessions_controller.go`, `core/web/auth/auth.go`). No special network position or credentials are required, and the timing gap (bcrypt cost, tens of ms) is well above typical network jitter, making the discrepancy practically measurable with a modest number of repeated/averaged requests.

### Recommendation
Ensure a constant-cost path regardless of whether the email exists: on `FindUser` failure, still perform a dummy bcrypt comparison against a fixed/precomputed hash before returning the generic "invalid email/password" error, so total latency is equalized between existing and non-existing accounts. Apply the same fix to the `localLoginFallback` implementations in `core/sessions/ldapauth/ldap.go` and `core/sessions/oidcauth/oidc.go`.

### Proof of Concept
1. Send `POST /sessions` with `{"email": "<known-registered-admin-email>", "password": "wrong"}` and measure response time — call reaches `utils.CheckPasswordHash` (bcrypt), response latency includes bcrypt cost.
2. Send `POST /sessions` with `{"email": "definitely-not-registered@example.com", "password": "wrong"}` and measure response time — call short-circuits at `FindUser`'s `sql.ErrNoRows`, response latency excludes bcrypt cost.
3. Repeat both requests N times and compare average latencies; the registered-email requests will show a consistent, measurable latency increase (bcrypt cost), confirming the email is registered.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")

const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}

func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}
