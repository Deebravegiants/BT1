### Title
Webhook `shop-domain` header trusted by `Registry.process` while excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` covers `@raw_body` alone. The `shop` value dispatched to the app's handler is read from the `shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes. This breaks the intended binding: `shop delivered to handler == shop that Shopify actually signed for`.

### Finding Description
`Webhooks::Registry.process` verifies authenticity purely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` is defined to be the raw HTTP body only: [3](#0-2) 

Yet the `shop` accessor used to build `WebhookMetadata` (which the app's handler consumes to decide which tenant's data to act on) is pulled straight from an HTTP header with no cryptographic tie to the body/signature: [4](#0-3) [5](#0-4) 

Equality that should hold: `shop_bound_by_hmac(request) == shop_delivered_to_handler(request)`. In this implementation, the left side is undefined (the HMAC binds zero bytes of shop identity), while the right side is attacker-controllable header content, so the equality is violated by construction — the "bytes verified vs bytes parsed" pattern called out in the rules.

### Impact Explanation
Because the signature only ever authenticates `raw_body`, anyone in possession of one valid `(body, hmac)` pair emitted by Shopify for topic T (e.g., the operator of their own shop, who can trivially trigger such an event on their own store and observe the webhook Shopify sends to any endpoint they control) can replay that exact body+hmac to the app's shared webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still pass (it never inspected the header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the attacker-chosen shop. Any host application that uses `data.shop` (as the gem's own doc examples do) to select which tenant's session/data to update is exposed to cross-tenant data confusion/injection — e.g. writing another merchant's order/product state, or triggering app-uninstall/GDPR-style logic against the wrong shop. This satisfies the "cross-tenant access" Critical-impact bucket.

### Likelihood Explanation
Medium. Exploitation doesn't require breaking the secret or MITM: an attacker only needs (a) the ability to legitimately trigger a webhook-eligible event on any shop they control (trivial — they are a merchant of their own install) and (b) the ability to send an HTTP POST to the target app's public webhook URL with custom headers (also trivial, since that endpoint is public by design). No access token, `api_secret_key`, or privileged access is needed — only ordinary internet access and a Shopify Partner/dev store, both attainable by any unprivileged user.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header bytes in the value that is HMAC-verified, or otherwise cryptographically bind the shop identity to the signed payload, so `Registry.process` cannot be fed a body/hmac pair captured from one shop while claiming to originate from another. At minimum, document that host applications must independently re-derive or reconcile the shop from a source that *is* signed (e.g. cross-check against the shop stored for the matching `webhook_id`/subscription) rather than trusting `WebhookMetadata#shop` directly for any tenant-scoping decision.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers an event for a registered webhook topic (e.g. `orders/create`).
2. Shopify sends `POST /webhooks` to the app with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <H>`, and body `B`; attacker captures `(B, H)` (they control the receiving endpoint or a proxy in front of it).
3. Attacker replays `POST /webhooks` to the same app endpoint with body `B`, the same `X-Shopify-Hmac-Sha256: <H>`, but header `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds `hmac` from the decoded header and `to_signable_string` returns `B`; `Utils::HmacValidator.validate` recomputes HMAC(secret, B) and it matches `<H>` because the signature never depended on the shop header.
5. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, letting the attacker inject attacker-authored event data attributed to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          end

          received_signature = verifiable_query.hmac

        end
