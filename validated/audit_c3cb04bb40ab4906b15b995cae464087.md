#### No vulnerability found for this question.

**Reasoning:** The claimed path is blocked by an existing guard. In `IntentsSDK.createWithdrawalIntents` [1](#0-0) , `actualAmount` is computed as `amount - feeEstimation.amount` when `feeInclusive` is true, and this is passed to `bridge.validateWithdrawal` **before** `bridge.createWithdrawalIntents` is ever invoked.

`PoaBridge.validateWithdrawal` enforces `args.amount < minWithdrawalAmount` unless `skipMinAmountValidation` is explicitly set [2](#0-1) . The `createWithdrawalIntents` call site in `sdk.ts` never sets `skipMinAmountValidation` (only `_estimateWithdrawalFee` sets it, and only when `amount === 0n && feeInclusive === false`) [3](#0-2) . Since `minWithdrawalAmount` is a non-negative `BigInt` parsed from the PoA bridge API's `min_withdrawal_amount` field [4](#0-3) , any negative `actualAmount` (i.e. `amount < feeEstimation.amount` with `feeInclusive: true`) will always satisfy `actualAmount < minWithdrawalAmount`, causing `MinWithdrawalAmountError` to be thrown before `bridge.createWithdrawalIntents` is called and before any intent is signed.

This holds regardless of whether the caller goes through `_estimateWithdrawalFee` (which has its own separate `FeeExceedsAmountError` guard) or supplies a caller-controlled `feeEstimation` directly via `signAndSendWithdrawalIntent` → `createWithdrawalIntents`, because the `validateWithdrawal` call inside `createWithdrawalIntents` is unconditional and independent of how `feeEstimation` was obtained.

Therefore the negative `actualAmount` never reaches `PoaBridge.createWithdrawalIntents` [5](#0-4) , and no malformed `'-N'` amount string is ever serialized into a signed intent. The equality claimed to break (`sum(debits) == amount + fee adjustments`, both non-negative) is preserved because the code throws before signing rather than producing an invalid negative amount.
