### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values used downstream by `ShopifyAPI::Webhooks::Registry.process` are never part of the signed material. Any unprivileged party who can obtain one genuinely-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a webhook delivery) can replay that same body/hmac pair to the app's webhook endpoint while freely rewriting the `shop-domain` and `topic` headers, since those fields are not bound to the signature check.

### Finding Description
The signable payload is defined as just the raw body: [1](#0-0) 

`hmac`, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic linkage to each other: [2](#0-1) 

`HmacValidator.validate` only checks `HMAC(secret, raw_body) == received_hmac`: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then dispatches the (unauthenticated) `shop`, `topic`, `webhook_id`, and `api_version` header fields straight to the app's handler: [4](#0-3) 

The equality that should hold is: **`(hmac, body, shop, topic)` as delivered by Shopify == `(hmac, body, shop, topic)` as verified by the gem**. In reality only `hmac == HMAC(secret, body)` is checked; `shop` and `topic` are parsed straight from unauthenticated headers and forwarded to `WebhookMetadata` without being covered by the signature. Because a single app-level `api_secret_key` is shared across every shop that installs the app, an attacker who installs the app on their own (or any) shop can capture one legitimately-signed `(body, hmac)` pair from Shopify, then POST that identical body+hmac to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain (and/or the `X-Shopify-Topic` header for a different topic). `HmacValidator.validate` still returns `true` because the body is unchanged, yet `Registry.process` invokes the handler with the attacker-chosen `shop` and `topic`.

### Impact Explanation
This breaks the tenant boundary the host application relies on: any code that trusts `WebhookMetadata#shop` to attribute the delivered body to the correct merchant (e.g., updating that shop's orders/customers/inventory records) can be made to apply attacker-controlled webhook content to a different tenant's data, or to route body content to the wrong topic handler. This is a cross-tenant data-integrity issue reachable by any unprivileged party capable of installing the app once (a standard, unprivileged action for any Shopify developer/merchant), with no access token, `api_secret_key`, or privileged account required.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that are publicly installable: obtaining one genuine `(body, hmac)` pair only requires installing the app on any store (including a free development store) and capturing a delivered webhook, which is well within reach of an "unprivileged internet user." No cryptographic secret needs to be recovered — only header fields that are outside the signed scope need to be altered.

### Recommendation
Bind the identity-critical fields into the signed material (or otherwise cryptographically verify them) before trusting them, e.g., have `Registry.process` independently verify that the `shop-domain` claimed in the request corresponds to a shop actually known/installed by the app (cross-check against stored session/shop records) and validate the `topic` header against an allow-list tied to the registered webhook rather than trusting it blindly. At minimum, document clearly that `request.shop` and `request.topic` are unauthenticated and must be revalidated by the host application before being used for any tenant-scoped operation.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker.myshopify.com`) and capture a legitimate webhook delivery, e.g. `orders/create`, giving a raw body `B` and its header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
2. Replay the following request to the app's webhook endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <anything>
   X-Shopify-Api-Version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unmodified: `request.shop == "victim-shop.myshopify.com"`, `request.hmac` matches `H`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(secret, B)` and compares to `H` — this succeeds regardless of the forged `shop-domain` header, per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
5. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the host application to process attacker-supplied order data as if it belonged to `victim-shop.myshopify.com`.
