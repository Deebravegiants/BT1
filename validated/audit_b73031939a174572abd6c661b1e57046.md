## Title
HOT Bridge withdrawal status reports "completed" without checking the `verified_withdraw` flag from the fallback API - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

## Summary
`HotBridge.describeWithdrawal()` falls back to the HOT `bridge_withdrawal_hash` API when the primary bridge indexer and on-chain contract state are unavailable. The API response schema requires and parses a `verified_withdraw: boolean` field per withdrawal record, but `fetchWithdrawalHashFromApi()` never reads or checks that field before returning the hash as proof of completion. Any withdrawal entry that matches the `nonce` and has a non-empty `hash` is treated as `"completed"`, even if `verified_withdraw` is `false`.

## Finding Description
The HOT API schema explicitly models withdrawal verification state: [1](#0-0) 

But `fetchWithdrawalHashFromApi()` only filters by `nonce` and checks that `hash` is present/hex-decodable — `verified_withdraw` is parsed into `parseResult.output.withdrawals` but is dropped on the floor: [2](#0-1) 

This function's return value is used directly as the `txHash` for a `"completed"` `WithdrawalStatus` in the caller: [3](#0-2) [4](#0-3) 

The equality broken is: *the status reported (`"completed"`) does not equal the actual on-chain/bridge-verified outcome*. The API contract signals this via `verified_withdraw`, and the code has the field in hand (it's required by the schema and present in every test fixture) but never consults it, so a hash that HOT itself has not verified is surfaced identically to a hash HOT has verified.

`describeWithdrawal()` feeds `watchWithdrawal()` in the withdrawal watcher, which stops polling and returns a final transaction result the moment `status === "completed"`: [5](#0-4) 

Any integrator using `sdk.waitForWithdrawalCompletion()` / `processWithdrawal()` treats that "completed" result as authoritative and typically finalizes off-chain bookkeeping (marks the withdrawal settled, credits the user, releases holds, etc.) at that point.

## Impact Explanation
This falls into the "status or hash misreport making an integrator credit or refund twice" High-impact category from the rules. If HOT's API returns a withdrawal record with a `hash` but `verified_withdraw: false` (e.g., a submitted-but-not-yet-confirmed/mismatched broadcast, or a hash HOT itself flags as unverified/suspect), the SDK reports it as fully `"completed"` with that hash. A downstream integrator relying on this status can:
- Treat the withdrawal as finished and release the corresponding credit/liability tracking, while the actual on-chain settlement to the destination chain is not confirmed by HOT.
- Later reconcile against the real (verified) state and discover a mismatch, or double-process the withdrawal.

This is not a DoS/rate-limit/timeout issue and does not depend on any privileged party acting maliciously — it's a straightforward logic gap where a documented, already-parsed verification flag is silently ignored on the primary code path that produces a completion signal.

## Likelihood Explanation
The API-fallback path is only exercised when both the bridge indexer and the primary contract-based signal are unavailable/inconclusive, which is an already-documented failure/fallback branch (per the code comments: "Fallback: API indexer (when contract returns null/pending)"). Reaching this path does not require attacker control of the intents-sdk itself — it happens naturally whenever HOT's indexer is degraded or slow, which the code's own comments acknowledge as an expected occurrence. Once in this branch, any `withdrawals[]` entry with `verified_withdraw: false` but a populated `hash` is silently accepted.

## Recommendation
In `fetchWithdrawalHashFromApi()`, require `withdrawal.verified_withdraw === true` in addition to the nonce match and non-empty/hex hash before returning a hash; otherwise return `null` (keep the withdrawal `"pending"`) so callers do not prematurely report `"completed"`.

## Proof of Concept
1. Contract view (`getGaslessWithdrawStatus`) returns `null`/pending, and the bridge indexer request fails or has no matching record — this forces the HOT API fallback branch.
2. Mock `hotSdk.api.requestApi` to return:
```json
{
  "hash": "0xDEADBEEF",
  "nonce": "1",
  "near_trx": "txhash",
  "withdrawals": [
    { "hash": "0xDEADBEEF", "nonce": "1", "near_trx": "txhash", "verified_withdraw": false, "chain_id": 56 }
  ]
}
```
3. Call `bridge.describeWithdrawal(wid)` for the matching `WithdrawalIdentifier`.
4. Observe the result is `{ status: "completed", txHash: "0xDEADBEEF" }` even though `verified_withdraw` is `false` — matching the existing test at `packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.test.ts:669-720` ("returns completed via API fallback ...") which only varies `verified_withdraw: true`; changing it to `false` produces the same "completed" result, confirming the field is unchecked.

	private async fetchWithdrawalHashFromApi(
		nearTxHash: string,
		nonce: bigint,
		logger?: ILogger,
	): Promise<string | null> {
		try {
			const response = await withTimeout(
				() =>
					this.hotSdk.api.requestApi(
						`/api/v1/evm/bridge_withdrawal_hash?near_trx=${nearTxHash}`,
						{ method: "GET" },
					),
				{ timeout: HotBridge.API_FALLBACK_TIMEOUT_MS },
			);
			const data: unknown = await response.json();

			const parseResult = v.safeParse(HotApiWithdrawalResponseSchema, data);
			if (!parseResult.success) {
				logger?.debug("HOT API response parse failed", {
					issues: parseResult.issues,
				});
				return null;
			}

			const withdrawal = parseResult.output.withdrawals.find(
				(w) => w.nonce === nonce.toString(),
			);

			if (withdrawal?.hash) {
				const hash = withdrawal.hash.replace(/^0x/, "");
				if (isHex(hash)) {
					logger?.info("HOT withdrawal hash found via API fallback", {
						nearTxHash,
						nonce: nonce.toString(),
					});
					return hash;
				}
			}
			return null;
		} catch (error) {
			logger?.debug("HOT API fallback failed", { error, nearTxHash });
			return null;
		}
	}
