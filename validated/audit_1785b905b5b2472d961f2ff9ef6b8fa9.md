### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](https://github.com))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` identity that the handler subsequently trusts is taken from an unauthenticated HTTP header, not from data covered by the HMAC. This breaks the intended binding `hmac_signed_bytes == bytes_the_shop_field_is_derived_from`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile, `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, completely independent of the HMAC computation [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, using it to route/attribute the webhook to a specific merchant: [4](#0-3) .

Because the shop header is not part of the signed payload, an attacker who has captured (or can generate, e.g. via their own legitimately-owned test shop) one valid `(raw_body, hmac)` pair can replay that exact body/HMAC while substituting an arbitrary `shopify-shop-domain` header value. The HMAC check in `HmacValidator.validate` still passes — it only validates that the body bytes were signed by Shopify's secret — but the `shop` value the host application receives and trusts for tenant attribution is attacker-controlled and never covered by that proof.

Equality that should hold: `hmac_signed_bytes == bytes(shop) ∪ bytes(body)`. Equality that actually holds: `hmac_signed_bytes == bytes(body)` while `shop` is read independently and unauthenticated.

### Impact Explanation
This qualifies as cross-tenant access: a webhook payload cryptographically proven to originate from Shopify for shop A can be replayed by anyone who can intercept/log/observe such a request (or who runs their own shop and captures their own valid webhook) with a forged `shop` header claiming to be shop B. Any host application that uses `WebhookMetadata#shop` from `Registry.process` (as the gem's own webhook processing API documents and expects) to look up per-merchant data, update per-merchant state, or key `SessionRepository` records will attribute Shopify-authenticated webhook data to the wrong tenant, since the gem provides no protection against this at the library level — the shop field is presented to the host application as if it were verified, but it is not covered by the cryptographic check the gem itself performs.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid `(raw_body, hmac)` pair — for example from their own store's webhook deliveries (which any merchant/developer can obtain by installing the app) or from a captured/logged request. Given that, replaying it with a different `shop` header requires only the ability to send an arbitrary HTTP request to the app's webhook endpoint (unprivileged internet capability, no `api_secret_key` or access token needed), satisfying the unprivileged-attacker requirement.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the signable payload used to compute/validate the webhook HMAC, or, at minimum, document and/or enforce that `Request#shop` must not be trusted for tenant identity unless independently corroborated (e.g., cross-checked against a known/registered shop for the specific webhook subscription, or bound by including the header value in the signature verification step performed in `Registry.process`). Since Shopify's actual HMAC computation is body-only by protocol design, the safer mitigation within this gem's `Registry.process` is to require callers to supply/verify the expected shop out-of-band before trusting `request.shop`, or to fetch/verify shop identity from the registered webhook subscription rather than solely from the header echoed back by the request.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger any webhook topic the app has registered for.
2. Capture the raw request body and the `X-Shopify-Hmac-Sha256` header for the resulting delivery (attacker legitimately owns this data since it's their own shop).
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks the body bytes against the HMAC [5](#0-4) .
5. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` set to `victim-shop.myshopify.com` [6](#0-5)  and passes it to the app's handler, which processes attacker-controlled data as if it came from `victim-shop.myshopify.com`.
