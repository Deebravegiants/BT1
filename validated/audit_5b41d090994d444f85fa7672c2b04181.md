Audit Report

## Title
External Initiators can trigger job runs even when the `ExternalInitiatorsEnabled` feature flag is disabled - ([File: core/web/auth/auth.go])

## Summary
`AuthenticateExternalInitiator`, the middleware that authenticates `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers and grants the caller the `UserRoleRun` role, never checks `JobPipeline.ExternalInitiatorsEnabled`. Only the initiator-creation endpoint enforces this flag, so a previously-created external-initiator credential remains fully functional to trigger job runs even after an operator disables the feature.

## Finding Description
The `ExternalInitiatorsEnabled` flag is checked exclusively in `ExternalInitiatorsController.Create` [1](#0-0)  when creating a new external initiator record. However, `AuthenticateExternalInitiator` — the authentication method that actually validates EI credentials on every authenticated request — only calls `store.FindExternalInitiator` and `bridges.AuthenticateExternalInitiator` to check the access key/secret, then unconditionally grants `clsessions.UserRoleRun`, with no reference to the config flag anywhere in the function [2](#0-1) .

Critically, this middleware is wired directly into the router for the job-run trigger endpoint: `core/web/router.go` sets up `userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession))` and registers `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` [3](#0-2) . `RequiresRunRole` only checks that `user.Role != clsessions.UserRoleView` [4](#0-3)  — it has no knowledge of the `ExternalInitiatorsEnabled` flag either. The `ExternalInitiator` struct itself carries no enabled/disabled state field [5](#0-4) , so there's no way for the authentication layer to even detect a "disabled" state at the record level — the only gate that exists is the config check that's skipped here.

This confirms the root cause: the feature-disable check is applied at credential-creation time but not re-applied at credential-use (authentication) time, so disabling the feature does not revoke already-issued credentials.

## Impact Explanation
This is a concrete node-API authorization-bypass: an operator who disables `JobPipeline.ExternalInitiatorsEnabled` — expecting to immediately shut off external-initiator-triggered job runs — is not protected, because any external initiator credential issued while the feature was enabled continues to authenticate successfully and trigger runs via `POST /v2/jobs/:ID/runs`. This maps to the in-scope "node API authentication or role bypass" / "unauthorized job run" impact category, since an unprivileged external caller retains the ability to invoke pipeline job runs against operator intent.

## Likelihood Explanation
Likelihood is realistic and deterministic, not speculative: it requires only (1) an EI having been created previously (a normal, supported workflow) and (2) later toggling the flag off. No attacker sophistication is needed — an unprivileged holder of a previously-issued, valid `AccessKey`/`Secret` pair simply continues sending the same requests they always could, and the flag disablement has zero effect on them, as confirmed by tracing the full router → middleware → role-check chain with no code path referencing the flag.

## Recommendation
Add an `ExternalInitiatorsEnabled` check inside `AuthenticateExternalInitiator` (in `core/web/auth/auth.go`), returning `auth.ErrorAuthFailed` when the feature is disabled, so that authentication (not just creation) is gated by the same flag. This requires passing the config (or a config accessor) into the `Authenticator`/`authMethod` call chain, since `AuthenticateExternalInitiator` currently only receives the `store Authenticator` argument.

## Proof of Concept
1. With `JobPipeline.ExternalInitiatorsEnabled = true`, create an external initiator via `POST /v2/external_initiators` and capture the returned `AccessKey`/`Secret`.
2. Set `JobPipeline.ExternalInitiatorsEnabled = false` and restart/reload the node.
3. Send `POST /v2/jobs/:ID/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the captured credential.
4. Observe that `AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-149`) succeeds, sets `SessionUserKey` to `UserRoleRun`, `RequiresRunRole` passes, and `PipelineRunsController.Create` executes the job run — despite the feature flag being disabled. A Go integration test hitting the router with this sequence (toggling `JobPipeline.ExternalInitiatorsEnabled` between creation and run-trigger requests) would deterministically reproduce and prove this.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
