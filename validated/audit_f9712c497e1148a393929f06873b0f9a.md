This is a strong structural analog to the Sherlock M-1 bug class: the invariant (a single, consistent config snapshot governing a signup's outcome) is not held atomically — different phases of the same signup independently re-read the live, mutable backend config, so a value legitimately changed by the backend mid-signup can be "read fresh" at exactly the decision point that benefits an unprivileged user, exactly like the backrun-`setEX128` exploit.

### Title
Non-atomic config re-reads during a single signup allow config-change race to force enrollment bypass at `enroll_user` gate - (File: `src/plans/mod.rs`)

### Summary
`do_signup` reads the shared, backend-mutable `Config` (`Arc<Mutex<Config>>`) multiple independent times at different phases of the *same* signup instead of taking one atomic snapshot at signup start [1](#0-0) . The `ignore_user_centric_signups` flag in particular is read fresh, at the very end of the pipeline, right before deciding whether to actually run server-side enrollment (`enroll_user`) or just locally mark the signup successful based on `signup_reason` [2](#0-1) . Because the flag is not fixed for the duration of a signup, its value can differ between the start of `do_signup` and this final gate.

### Finding Description
`Config` is downloaded from the backend on an interval and swapped into a shared `Arc<Mutex<Config>>` by the observer broker, independent of any in-progress signup [3](#0-2) . Multiple parts of `do_signup` each lock and re-read this shared config independently:
- Once at the top of `do_signup` for `self_serve`, `pcp_v3`, relay parameters [1](#0-0) .
- Again for the `DebugReport::builder` snapshot [4](#0-3) .
- Again inside `biometric_capture` for `self_serve_biometric_capture_timeout` [5](#0-4) .
- Again, freshly, at the enrollment decision point: `orb.config.lock().await.ignore_user_centric_signups` [6](#0-5) .

This mirrors the root cause of the Sherlock M-1 report: an invariant that should be evaluated once, consistently, for the whole operation (`target*n` in Burve; here, "should this signup actually be enrolled server-side") is instead re-derived from a value that can be changed out-of-band mid-operation by an authorized party (pool owner / backend operator), and the unprivileged party (the user, or a colluding operator) can "backrun" that change by simply timing their signup so the fresh read at the decision point observes a different value than was in effect earlier in the same signup.

Concretely: if the backend flips `ignore_user_centric_signups` from `false` to `true` while a `user_centric_signup` is in-flight (after capture/pipeline/fraud-check have already run under the assumption enrollment would happen), the code branches into the `debug_report.enrollment_status(...)` path and treats the signup as locally successful purely based on `signup_reason == SignupReason::Normal`, without ever calling `enroll_user` to perform the server-side, deduplicated enrollment/uniqueness check [2](#0-1) .

### Impact Explanation
If the true uniqueness/enrollment check (`enroll_user`) is skipped because the flag was flipped mid-signup, a signup can be marked `success = true` (and biometric PCP data uploaded/tier-0 committed) without the backend-side enrollment/duplicate-detection step being executed for that specific attempt. This is a cross-signup state inconsistency: the local decision of "did this identity get properly enrolled/deduplicated" no longer matches what actually happened server-side, opening the door to misattributed or duplicate signups being locally reported as successful even though the authoritative enrollment call was bypassed for that run.

### Likelihood Explanation
This requires the backend to actually change `ignore_user_centric_signups` (or another config field consumed at a late decision point) during the ~seconds-to-tens-of-seconds window of an in-progress signup, and requires the changed value to be fetched by the periodic `config_update` poll before the final `if user_centric_signup && !...ignore_user_centric_signups` check executes [3](#0-2) . This is a narrower race than the DeFi original (which is user-triggerable at will via a single transaction ordering), since here the timing depends on backend rollout cadence and the config-poll interval, not something a pure end-user can trigger on demand. I could not find any lock or version-pinning mechanism in `do_signup` that prevents this drift, but I also could not find code that explicitly demonstrates the backend changes this flag frequently in production — that operational detail is outside the indexed code and I flag it as unverified.

### Recommendation
Take a single, immutable snapshot of the entire `Config` (or at minimum every field consumed by `do_signup`) at the very start of `do_signup`/`start_signup`, and thread that snapshot through every phase of the signup instead of re-locking `orb.config` at each decision point (`biometric_capture`, `verify_user_qr_code`, the `ignore_user_centric_signups` check, etc.). This guarantees the enrollment-bypass decision and all other signup-lifecycle decisions are consistent with the state the signup began under, closing the "backrun" window analogous to the Burve fix that recomputes/pins the invariant when the underlying parameter changes.
