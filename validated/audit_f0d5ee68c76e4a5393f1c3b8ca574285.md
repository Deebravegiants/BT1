### Title
Reachable arithmetic-underflow Panic in `canGraduate`/`previewLtUntilGraduation` permanently bricks a curve's buy/sell path - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` and `Bonding.previewLtUntilGraduation` both compute `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no guard against `assetReserve < virtualLtReserve` [1](#0-0) [2](#0-1) . `virtualLtReserve` is an immutable value fixed at launch (`Pair.k() / Token.TOTAL_SUPPLY()`), and `assetReserve` is the pair's live stored LT reserve, which starts exactly equal to `virtualLtReserve` and is only supposed to move upward as real LT is raised. If `assetReserve` is ever pushed below `virtualLtReserve`, both functions revert with an unhandled Solidity Panic(0x11) instead of a clean custom error.

### Finding Description
The team already found and fixed one instance of this exact bug class: the code comment in `test/Zap.t.sol` explicitly documents that a prior version of `previewLtUntilGraduation`'s **supply leg** (`reserveToken - realBalance`) could underflow from a token donation and cascade into a `Zap.buy` DoS, and a guard (`if (realBalance >= reserveToken) return ltUntilThreshold;`) was added [3](#0-2) [4](#0-3) .

The **USD leg** subtraction, `realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(...)`, was never given the equivalent guard — in either `canGraduate` or `previewLtUntilGraduation` [5](#0-4) [6](#0-5) .

`Router._computeBuy` and `_computeSell` compute `tokensOut`/`assetOut` using floor-division on `k / newReserve`, which — since the subtracted term is always rounded *down* — systematically rounds the trader's output *up* on both buys and sells [7](#0-6) [8](#0-7) . `Pair.swap`'s K-invariant check is deliberately loose by design (`(newTokenReserve+1)*(newAssetReserve+1) < k` reverts, rather than an exact equality/≥ check) [9](#0-8) , so it tolerates the reserve state drifting slightly below the true k-product on every trade rather than rejecting it. An unprivileged trader who repeatedly round-trips (buy tokens, then immediately sell them back) on a single curve accumulates this favorable-rounding dust each cycle, slowly draining the pair's stored `assetReserve` below its immutable `virtualLtReserve` floor over many transactions — something the code assumes can never happen (as shown by the supply-leg fix, the team is aware this reserve-vs-virtual-floor invariant is not unconditionally safe).

Once `assetReserve < virtualLtReserve` for a token, every subsequent call to `canGraduate` or `previewLtUntilGraduation` reverts with a raw Panic instead of a decodable error.

### Impact Explanation
`canGraduate` is unconditionally invoked inside `Zap._sellInternal` before every sell on that token's curve [10](#0-9) , and `previewLtUntilGraduation` is unconditionally invoked inside `Zap._executeBuy` to pre-size every curve-path buy [11](#0-10) . Once the underflow condition is triggered, **every future `Zap.buy` and `Zap.sell` call on that token permanently reverts** with an undecodable Panic — the exact "reachable assertion → service becomes unavailable" pattern the rulex advisory describes, mapped onto a Solidity arithmetic Panic instead of a Rust slice-index panic. Because the curve can never reach the USD or supply graduation trigger cleanly again (the same broken subtraction feeds `_prepareGraduationLiquidity` indirectly via `canGraduate`'s gating of `_enterGraduating`), the token's entire remaining curve-raised LT and unsold token supply are permanently frozen in `Bonding`/`Pair` with no owner-level rescue path, matching the "permanent freezing of trader/creator funds" impact bar.

### Likelihood Explanation
This does not require any privileged role or off-chain component — any unprivileged trader can submit ordinary `Zap.buy`/`Zap.sell` transactions. The per-trade rounding advantage is small (bounded by integer-division floor error), so triggering the underflow in practice requires many round-trip transactions against a single curve to accumulate enough dust drain relative to `virtualLtReserve`'s wei-scale value; this bounds likelihood to Medium rather than High, consistent with the CVSS "Attack Complexity: Low, Privileges Required: Low" profile of the reference advisory. The fact that the team already patched the mathematically symmetric supply-leg underflow (via donation) but left the USD-leg subtraction unguarded strongly suggests this specific path was missed rather than intentionally accepted.

### Recommendation
Add the same defensive guard used for the supply leg to the USD-leg subtraction in both `canGraduate` and `previewLtUntilGraduation`: if `assetReserve < virtualLtReserve`, treat `realLtRaised` as `0` (or otherwise short-circuit) instead of performing an unchecked subtraction. Additionally, consider tightening `Pair.swap`'s K-invariant check (removing or reducing the `+1` slack, or accounting for it explicitly in `Router`'s rounding) so that the stored reserve can never legitimately drop below the invariant it's supposed to preserve.

### Proof of Concept
1. Launch a token via `Zap.createToken` so `Pair.assetReserve == virtualLtReserve` (0 real LT raised).
2. Have an unprivileged trader repeatedly: `Zap.buy(token, smallUsdcAmount, 0, address(0))` immediately followed by `Zap.sell(token, tokensJustReceived, 0)`, many times.
3. Each cycle nets the trader a small favorable-rounding gain (per `Router._computeBuy`/`_computeSell`'s floor-division asymmetry), slowly reducing `Pair.assetReserve` relative to the fixed `virtualLtReserve`.
4. Once `assetReserve` drops below `virtualLtReserve`, the next `Zap.buy` or `Zap.sell` call on this token reverts with an unhandled Panic (0x11) from `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(...)` inside `canGraduate`/`previewLtUntilGraduation`, permanently bricking further trading on that curve.

*(Note: I was not able to run this scenario against the actual test suite/fuzzer to empirically confirm the exact number of round trips required or rule out that some other invariant prevents `assetReserve` from ever dropping below `virtualLtReserve`; this assessment is based on static analysis of the cited rounding directions in `Router.sol`/`Pair.sol` and the precedent of the already-patched, mathematically symmetric supply-leg bug.)*

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
