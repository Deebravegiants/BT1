### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the **raw body**, then dispatches to the app's handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from HTTP headers. None of those header values are included in the HMAC's signable string, so the identity binding "shop the app acts on == shop Shopify actually signed the webhook for" does not hold.

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature only over `verifiable_query.to_signable_string`, and for webhooks that method returns just the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from HTTP headers with no cryptographic binding to the body or to the signature at all: [2](#0-1) 

`Registry.process` performs exactly one check — that the raw body's HMAC is valid using `Context.api_secret_key` — and then immediately trusts `request.shop` (and the other headers) to build the metadata passed to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`shop attributed to the webhook by the gem (request.shop header) == shop that Shopify's signature actually authenticates`

Because `to_signable_string` only covers the body bytes, this equality does not hold — the signature authenticates only "this body was produced using our `api_secret_key`," and says nothing about which shop it is for. All shops that install the same app share the same `api_secret_key`, so a valid `(raw_body, hmac)` pair generated for *any* shop connected to the app remains valid unmodified. An attacker who has access to their own store (which any unprivileged user can create as a Shopify Partner dev store and install the target app on) can capture a legitimate `(raw_body, hmac)` pair emitted by Shopify for a webhook fired from their own shop, then replay that exact body+hmac to the target app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged ⇒ signature unchanged), and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-controlled) payload came from the victim shop.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC check is supposed to enforce: an unprivileged attacker (any developer able to install the app on their own store) can make the app believe attacker-controlled webhook data belongs to a different, victim merchant. If the host application's webhook handler uses `data.shop` to select which shop record/session/access token to update, this results in cross-tenant data injection/corruption using forged data — i.e., cross-tenant access, without requiring the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Reaching this requires only: (1) installing the target Shopify app on an attacker-owned/free development store (a normal, unprivileged action any internet user with a Partner account can take), (2) triggering an event in that store to receive one legitimate `(body, hmac)` pair from Shopify, and (3) POSTing that pair directly to the app's public webhook endpoint with a forged `shop-domain` header. No secrets or victim credentials are needed — likelihood is moderate-to-high wherever the host app trusts `WebhookMetadata#shop` for tenant scoping, which the gem's own API design (returning `shop` unauthenticated alongside a "validated" webhook) actively encourages.

### Recommendation
Extend `VerifiableQuery`/`to_signable_string` (or the webhook validation path specifically) so the shop identity is cryptographically bound to the verified request — e.g., verify the `shop-domain` header against a known/expected shop for the given webhook subscription (or require callers to pass an expected shop and compare it) before constructing `WebhookMetadata`, rather than trusting an unauthenticated header. At minimum, document loudly and enforce in `Registry.process` that `shop` must be cross-checked against a shop the caller expects, since it carries no signature guarantee.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) in that store to receive a real request with a valid `x-shopify-hmac-sha256` header for the raw body.
3. Capture the raw body and its `hmac` header.
4. Send a new HTTP request to the app's webhook endpoint with:
   - the exact same raw body and `x-shopify-hmac-sha256` header captured above,
   - `x-shopify-shop-domain: victim-shop.myshopify.com`,
   - `x-shopify-topic` matching the same topic.
5. Observe that `ShopifyAPI::Utils::HmacValidator.validate` (called from `Registry.process`, `lib/shopify_api/webhooks/registry.rb:190`) returns `true` because only the (unmodified) body is checked, and the handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>)`.
