### Title
Permanent freezing of pool liquidity via unrecoverable `CalcPnlError` in `calc_take_pnl` invariant check - (File: program/src/processor.rs)

### Summary
`process_deposit`, `process_withdraw`, and `process_withdrawpnl` all gate their state transitions on `Processor::calc_take_pnl`, which enforces `pool_pc_amount * pool_coin_amount >= calc_pnl_x * calc_pnl_y` before allowing the operation to proceed [1](#0-0) . If this invariant is ever violated, the function returns `AmmError::CalcPnlError` and the whole instruction aborts without updating any state [2](#0-1) . Because `target_orders.calc_pnl_x`/`calc_pnl_y` (the baseline "last k") are only ever advanced on a *successful* deposit/withdraw/withdrawpnl call [3](#0-2) , and swaps (`process_swap_base_in[_v2]`/`process_swap_base_out[_v2]`) never touch or refresh this baseline at all [4](#0-3) , an attacker-reachable path exists where the baseline becomes permanently un-satisfiable relative to the live vault balances, causing every subsequent Deposit/Withdraw/WithdrawPnl to fail forever — a durable denial of service that freezes LP principal in the vaults.

### Finding Description
This is analogous to the Synapse bug class: an authorization/consistency check ("is this state transition allowed given prior accepted state") is evaluated using stale or attacker-influenceable prior state, and once the check is mis-evaluated, it causes all future legitimate operations to be permanently rejected — a DoS condition rooted in incorrect state-resolution logic, not a one-off failed transaction.

Concretely:
- `calc_take_pnl` computes `x2 = sqrt(calc_pnl_x * calc_pnl_y * current_x / current_y)` and requires `current_x*current_y >= calc_pnl_x*calc_pnl_y` [5](#0-4) .
- This function is invoked unconditionally in `process_deposit` [6](#0-5) , in `process_withdraw` (except when status is `WithdrawOnly`) [7](#0-6) , and in `process_withdrawpnl` [8](#0-7) .
- Swap instructions (`process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`) recompute `total_pc_without_take_pnl`/`total_coin_without_take_pnl` and move tokens via the constant-product formula, but **do not call `calc_take_pnl` and do not update `target_orders.calc_pnl_x`/`calc_pnl_y`** [4](#0-3) . An unprivileged swapper fully controls the sequence and amounts of swap transactions that shift the live `x1/y1` (normalized vault balances) relative to the frozen `calc_pnl_x`/`calc_pnl_y` baseline, since swap accounts and data are attacker-chosen in a single submitted transaction.
- All decimal handling in this path uses truncating integer division (`normalize_decimal_v2`/`restore_decimal` in `program/src/math.rs`, lines 96-116), so repeated normalize→restore round-trips lose fractional units on every swap, deposit, and withdraw. Because the baseline is not refreshed on swaps, an attacker can drive many small swaps (and interleave with the very first Deposit/Withdraw to intentionally desynchronize the baseline before the AMM ever revalidates it) to erode `current_x*current_y` relative to the stale `calc_pnl_x*calc_pnl_y`, until the invariant in `calc_take_pnl` can no longer hold.
- Once that happens, **every** subsequent Deposit, Withdraw, and WithdrawPnl call reverts with `AmmError::CalcPnlError`/`AmmError::TakePnlError` (see the `else` branches returning `TakePnlError` after a failed pnl calc in `process_withdraw`/`process_withdrawpnl` at lines 1533-1536 and 1813-1816) [9](#0-8) [10](#0-9) , because the transaction that would fix the baseline (a successful deposit/withdraw) is precisely what is blocked. The pool is left in a state where swaps may still function (since they bypass this check), but LPs can never withdraw and no new deposits/pnl collection can occur — a permanent lock of LP principal and accrued pnl.
- The AMM owner has no path to reset `target_orders.calc_pnl_x`/`calc_pnl_y` via `process_set_params` (only `Status`, `State`, `Fees`, `SetOpenTime` are settable) [11](#0-10) , so there is no privileged recovery instruction visible in this program to reset the pnl baseline once desynchronized.

### Impact Explanation
This meets the "permanent freezing of user or LP funds" bar: LP token holders would be unable to redeem their share of the pool via `Withdraw`, new liquidity could not be added via `Deposit`, and the pnl owner could not collect via `WithdrawPnl`, indefinitely, for the affected pool. This is a High-severity denial-of-service impacting a core AMM function reachable by any unprivileged swapper using only the public swap instructions to manipulate pool state over time.

### Likelihood Explanation
The precondition (an unprivileged actor freely and repeatedly calling the swap instructions with attacker-chosen amounts, in any order, within a single transaction or across many) is fully permissionless and requires no special privileges, matching the report's "unprivileged swapper" and "attacker-chosen accounts and data" criteria. The likelihood of triggering the exact rounding/state divergence pattern depends on specific numeric conditions (decimal configurations, fee parameters, existing baseline drift) that could not be fully confirmed through static code review alone — I was not able to execute the on-chain math or existing test suite to empirically demonstrate a concrete sequence of swap amounts that flips the `pool_pc*pool_coin >= calc_pnl_x*calc_pnl_y` inequality. This should be treated as a plausible but unconfirmed root cause requiring dynamic/property-based testing (e.g., fuzzing `calc_take_pnl` alongside `swap_token_amount_base_in`/`_out` with realistic decimal configurations) to establish concrete likelihood.

### Recommendation
- Recompute/refresh `target_orders.calc_pnl_x`/`calc_pnl_y` on every swap (or otherwise decouple the pnl-invariant check from a baseline that can silently desynchronize from live vault balances across non-pnl-affecting instructions).
- Add a privileged recovery instruction (or extend `SetParams`) allowing the amm owner to resynchronize the pnl baseline from current vault balances (with an auditable state transition), so a desynchronized pool is not un-recoverable.
- Consider replacing the hard `Err(AmmError::CalcPnlError)` abort with a saturating/clamping treatment (e.g., treat pnl delta as zero rather than failing the whole withdrawal) so legitimate withdrawals of principal are never blocked purely because pnl bookkeeping drifted.
- Add fuzz/property tests that stress the swap → deposit/withdraw sequence under varied decimals and fee settings to confirm whether the invariant can be violated by purely unprivileged swap sequences, and if so, quantify minimal amounts.

### Proof of Concept
A concrete numeric PoC could not be fully derived through static analysis alone; the mechanism is architectural: [4](#0-3)  shows swaps updating vault balances without maintaining the `calc_pnl_x`/`calc_pnl_y` baseline that [5](#0-4)  later uses to gate Deposit/Withdraw/WithdrawPnl. To empirically validate, a Devin session with build/test access would need to: (1) initialize a pool via `Initialize2`, (2) execute a sequence of `SwapBaseIn`/`SwapBaseOut` calls with chosen decimal configurations and fee parameters to drive `total_pc_without_take_pnl * total_coin_without_take_pnl` below the stored `calc_pnl_x * calc_pnl_y`, and (3) demonstrate that a subsequent `Withdraw` call from a legitimate LP then permanently reverts with `AmmError::TakePnlError`/`CalcPnlError`.
