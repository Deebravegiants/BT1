### Title
Webhook `shop-domain` header not covered by HMAC signature allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `ShopifyAPI::Utils::HmacValidator.validate` only verifies the body bytes against the HMAC and never binds the `shop`, `topic`, `webhook_id`, or `api_version` values that are read from unauthenticated HTTP headers [2](#0-1) [3](#0-2) . `Registry.process` trusts `request.shop` as the tenant identifier passed to the app's handler after only checking the body HMAC [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e., the tenant identity (`shop`) delivered to the app should be cryptographically bound to the same signature that authenticates the payload. In this gem, `to_signable_string` only returns `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers with no participation in the signature computation [3](#0-2) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. the body) and then immediately constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the unauthenticated headers and dispatches it to the app's handler [4](#0-3) .

Because the `shop-domain` header is not part of the signed content, any (body, HMAC) pair that is valid for the shared `client_secret` remains valid regardless of what value is placed in the `shopify-shop-domain` header. An unprivileged internet user who controls any Shopify store using the same app (e.g., a free development store that has installed the app) can trigger a legitimate webhook delivery to obtain a genuinely-signed `(body, hmac)` pair, then replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to name a different, victim merchant. The HMAC check still passes because it only verifies the body, and the app's webhook handler receives `shop: <victim-domain>` alongside attacker-controlled payload content, causing the host application to process attacker data under another tenant's identity.

### Impact Explanation
This breaks the tenant/shop identity binding for webhook processing, enabling cross-tenant data injection: an attacker can make the host app believe attacker-controlled webhook data originated from a shop they don't control. Depending on how the host app's webhook handler uses `shop` (e.g., to key database records, trigger fulfillment actions, or update per-merchant state), this can lead to cross-tenant data corruption or unauthorized actions attributed to a victim shop, matching the "cross-tenant access" impact tier.

### Likelihood Explanation
The webhook endpoint is public by design (Shopify posts to it over the internet), and `HmacValidator.validate` only inspects the raw body [2](#0-1) . Obtaining a validly-signed body/HMAC pair requires only installing the target app on any store (including a free development store) and capturing one real webhook delivery — no access to the app's `client_secret` is needed. This makes exploitation practical for any user able to install the app on their own store.

### Recommendation
Include the tenant-identifying and routing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable content used for HMAC validation, or otherwise cryptographically bind them to the signed payload, so that a signature valid for one shop/topic cannot be replayed with a different `shop` value.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify development store; trigger any webhook topic the app subscribes to (e.g. `products/update`) and capture the raw request body and the `x-shopify-hmac-sha256` header value sent by Shopify — this HMAC is valid because it's computed with the shared `client_secret` over the body.
2. Replay an HTTP POST to the app's public webhook endpoint using the captured `raw_body` and `x-shopify-hmac-sha256` unchanged, but set `x-shopify-shop-domain` to the victim shop's domain (e.g. `victim-shop.myshopify.com`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` [1](#0-0)  and succeeds, then dispatches `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop` set to the forged victim domain [4](#0-3) , causing the app to process attacker-supplied data as if it originated from the victim shop.
