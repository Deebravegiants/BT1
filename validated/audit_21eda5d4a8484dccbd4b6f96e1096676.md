### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` in `Registry.process` only authenticates the JSON payload bytes. The `shop-domain` and `topic` headers—which `Registry.process` uses to attribute the payload to a specific merchant and event type—are read directly from unauthenticated HTTP headers and are never part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. `shop` and `topic` are read from separate headers (`shopify-shop-domain`, `shopify-topic`) that are **not** included in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then trusts `request.topic` and `request.shop` — sourced from the unauthenticated headers — to route the payload to a handler and to build the `WebhookMetadata` that identifies which shop the data belongs to: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single, global client secret — it is not scoped per shop. Any merchant who installs the app receives legitimate webhook deliveries (valid `raw_body` + valid `hmac`) signed with that same global secret. An attacker who is a legitimate, unprivileged installer of the app can therefore capture one of their own genuine `(raw_body, hmac)` pairs and replay it to the app's public webhook endpoint while substituting the `shopify-shop-domain` and/or `shopify-topic` headers. Because `to_signable_string` never covers these headers, `Utils::HmacValidator.validate` still succeeds, and `Registry.process` will hand the forged `shop`/`topic` combination to the host application's handler as if it came from a different, victim merchant.

This breaks the intended binding: **shop attributed to the webhook data == shop that Shopify actually signed the event for**. Instead, the equality that holds is only **bytes verified (raw body) == bytes trusted for HMAC**, while **shop/topic acted upon != data covered by the HMAC**.

### Impact Explanation
This allows a low-privileged attacker (any merchant who can install the app) to forge webhook events that the host application will attribute to an arbitrary target shop and topic, using only a genuine payload obtained from their own installation. Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (e.g., to look up merchant records, trigger fulfillment, sync data, or grant application state changes), this constitutes cross-tenant data injection/confusion — the host app processes attacker-controlled data as if it belongs to another tenant. This satisfies the Critical impact category of "cross-tenant access."

### Likelihood Explanation
Likelihood is High: no special credentials beyond installing the app (a normal, low-privilege action any merchant can take) are required, and the replay technique (swap two header values, keep body+hmac unchanged) is trivial once a real webhook has been captured — e.g., via the attacker's own shop's webhook logs.

### Recommendation
Include the `shop-domain` and `topic` (and any other header used for downstream trust decisions, such as `api-version`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the payload before verification. If Shopify's out-of-band signing scheme cannot be changed, `Registry.process` should independently corroborate the `shop` claim (e.g., cross-check against the session/shop the webhook was registered for) rather than trusting it purely from headers once the body's HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, capturing the raw POST body and the `x-shopify-hmac-sha256` header (both valid under the app's global `api_secret_key`).
2. Attacker replays this exact body and HMAC header to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` and/or `x-shopify-topic` with a topic of choice.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the untouched raw body.
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-chosen `topic`, even though Shopify never sent that event for that shop.
