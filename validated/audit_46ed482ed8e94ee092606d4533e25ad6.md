### Title
Phantom-bid weighting and published pool rates can be manipulated via instantaneous Uniswap V4 `sqrtPriceX96` used as an unprotected price/weight oracle - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`, `sdk/packages/sdk/src/protocols/intents/uniswap-v4-position.ts`)

### Summary
`aggregatePhantomBids` weights a solver's phantom bid by the solver's ERC-20 balance plus the withdrawable amount of any declared Uniswap V4 position, computed via `positionAmountOfToken` using the pool's *live* `sqrtPriceX96`/tick read at aggregation time (`readV4Position` in `phantom-aggregation.ts`, called with `blockTag = "latest"`). This instantaneous, unguarded pool state directly determines both which solver's quoted price wins `weightedMedian` and how much weight a position contributes, exactly the same class of flaw as `AutoRedemption::checkUpkeep`/`calculateUSDsToTargetPrice` reading raw `slot0().sqrtPriceX96` with no TWAP or re-check.

### Finding Description
`positionAmountOfToken` (`sdk/packages/sdk/src/protocols/intents/uniswap-v4-position.ts:162-179`) computes how much of a leg's output token a declared V4 position is "worth" using `sqrtPriceX96` taken directly from `readV4Position`'s live `getSlot0` call: [1](#0-0) 

That value flows into `aggregatePhantomBids`' per-solver weight calculation, which is then used to pick the winning quote via `weightedMedian` — "a solver holding over half the leg's weight sets the published price verbatim": [2](#0-1) [3](#0-2) 

No TWAP, deviation guard, or re-check of the pool price is applied on this path (unlike the solver's own fill-pricing path in `fx.ts`, which does apply `checkPriceGuard` against a static reference before sizing a real trade): [4](#0-3) 

The resulting weighted-median quote is written into `PhantomOrderPriceSnapshotV2`, then renormalized by the indexer into the pool's `sellRate`/`buyRate`: [5](#0-4) 

And `IntentGateway.quoteIntent`'s default `indexed_rates` strategy consumes that published rate directly to compute the `amountIn`/`amountOut` of a real order that a taker submits and funds: [6](#0-5) 

An attacker-controlled solver can, in the same block/transaction context as its phantom bid, manipulate the declared position's pool (e.g., via a flash swap or JIT liquidity add/remove) to push `sqrtPriceX96`/tick to a value that inflates `positionAmountOfToken`'s output for the leg's output token, without needing multi-block manipulation — exactly the attack vector described in the report. This lets the attacker's bid dominate the weighted median and force an artificial price into `PhantomOrderPriceSnapshotV2`/`LiquidityPool.buyRate`/`sellRate`, which downstream `quoteIntent` callers use to size real, fund-moving orders.

### Impact Explanation
A manipulated instantaneous price inflates a colluding solver's weight, letting them dictate the published median price for a leg. Because that published rate feeds `IntentGateway.quoteIntent`'s default `indexed_rates` strategy — used to compute real `amountIn`/`amountOut` for actual intent orders — a manipulated price can cause takers to be quoted, and gateways to accept, an economically wrong exchange rate, resulting in fund loss for takers/other solvers or unfair extraction by the manipulating solver. This satisfies "concrete theft ... of funds" via a route reachable by an unprivileged intent solver.

### Likelihood Explanation
The declared position's pool is a normal, permissionless Uniswap V4 pool that any account (including the bidding solver) can move within a single block via a swap or JIT liquidity action, immediately before or during the bid window that `aggregatePhantomBids` reads at `blockTag = "latest"`. No re-check or TWAP defends this path, so a single manipulating transaction executed in temporal proximity to bid aggregation suffices — comparable in likelihood to the original `AutoRedemption` finding, which Cyfrin rated exploitable without multi-block MEV.

### Recommendation
Do not weight phantom bids using an instantaneous `sqrtPriceX96`/tick read. Either (a) use a Uniswap V3/V4 TWAP with a sufficiently large window (≥15–30 minutes, per the referenced fix) when valuing declared positions in `positionAmountOfToken`/`readV4Position`, or (b) apply the same `checkPriceGuard`/`maxDeviationBps` reference-price defense that `fx.ts`'s `referenceRate` already applies on the solver-fill path, to the aggregation path as well, rejecting or discounting a declared position whose pool price deviates materially from a trusted reference before it can influence `weightedMedian` or the published `LiquidityPool` rates.

### Proof of Concept
1. Attacker deploys/owns a solver account and holds a Uniswap V4 LP position in the pool used to price a phantom order's leg.
2. Attacker submits a phantom bid declaring that position (`uniswapV4Positions` in the paymaster declaration) alongside a favorable quoted `solverAmount`.
3. In the same block (or immediately before the aggregation's `blockTag: "latest"` read), attacker executes a swap or adds JIT liquidity to shift the pool's `sqrtPriceX96` so that `positionAmountOfToken` reports an inflated withdrawable amount of the leg's output token for their position.
4. `aggregatePhantomBids` computes the attacker's weight as dominant for that leg, so `weightedMedian` returns the attacker's quoted price verbatim.
5. The indexer's `updateLiquidityPools`/`poolRateFromQuote` publishes this manipulated price into `LiquidityPool.buyRate`/`sellRate`.
6. A legitimate taker calling `IntentGateway.quoteIntent` (default `indexed_rates` strategy) receives `amountIn`/`amountOut` computed from the manipulated rate and submits a real, funded order at an unfavorable price, or the attacker uses the manipulated rate to fill their own crafted order profitably.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

/**
 * A leg's quoted output, renormalized to the pool's rate convention: output units per ONE whole
 * input token, as a `POOL_RATE_DECIMALS` fixed-point integer.
 *
 * The quote was given for `standardAmount` of the input token, whatever the pallet configured, so
 * it is scaled back to one whole token. At the legacy probe of exactly one unit
 * (`standardAmount === 10 ** inDecimals`) the two powers cancel and this is precisely the old
 * `medianPrice * scale`, which is why raising the probe size cannot move a published rate.
 *
 * Every multiplication happens before the division, so only the final step truncates — by under
 * one unit of 1e18, and downward, the same conservative direction the filler's own quote is
 * floored in.
 */
export function poolRateFromQuote(
	medianPrice: bigint,
	resolved: Pick<ResolvedPoolLeg, "inDecimals" | "outDecimals">,
	standardAmount: bigint,
): bigint {
	const scale = 10n ** BigInt(POOL_RATE_DECIMALS - resolved.outDecimals)
	const inputUnit = 10n ** BigInt(resolved.inDecimals)
	return (medianPrice * scale * inputUnit) / standardAmount
}
