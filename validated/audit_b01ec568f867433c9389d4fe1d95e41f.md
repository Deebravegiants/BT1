### Title
Signature binding iris-code attestation to a signup omits the `signup_id`, enabling cross-signup replay of a captured biometric signature - (File: `src/plans/enroll_user.rs`)

### Summary
The Orb's `make_signature` function produces the Secure Element signature that is submitted alongside a signup to the backend as cryptographic proof that a specific biometric capture (iris codes) belongs to a specific user on a specific Orb. Like the `chain.id`-less deployment data in the referenced `LPTokenFactory.deployLPToken` finding, this signed payload omits the one field that uniquely scopes the action to a particular *context* — here, the `signup_id` of the enrollment attempt — even though `signup_id` is generated fresh for every signup and is the value the backend uses to key/deduplicate/track that signup session.

### Finding Description
`make_signature` hashes only the Orb identity, the user's QR-code `user_id`, and the biometric pipeline outputs, then signs the digest with the Secure Element: [1](#0-0) 

This signature is then submitted to the backend as the `signature` form field, while the `signup_id` that scopes the specific signup session is sent as a separate, unsigned path parameter: [2](#0-1) 

`signup_id` is generated independently, per signup attempt, as a random value unrelated to the signed material: [3](#0-2) 

Because the signature never incorporates `signup_id` (its "domain"/"chain" for this action), the signed tuple `(ORB_ID, user_id, iris codes/mask codes/versions)` is valid and verifiable under any `signup_id` the backend is later asked to process. Exactly as the audited `deployLPToken` case allowed an action signed/authorized in one domain (chain) to be replayed unmodified in a different domain, here a captured `(signature, user_id, iris/mask codes)` tuple from one signup attempt can be resubmitted by an attacker under a *different* `signup_id` and will pass Secure-Element signature verification on the backend, because nothing in the signed bytes ties it to the originating signup session.

### Impact Explanation
The enrollment plan itself demonstrates that the backend differentiates outcomes per `signup_id`, including detecting "Backend duplicates," "Backend inflight matches," and "Backend detected fraud" as distinct terminal states of a signup: [4](#0-3) 

Since the cryptographic attestation is not bound to `signup_id`, an attacker in a position to observe or reuse the multipart form contents of one signup (e.g., from logs, retried/failed requests, or a compromised transport leg before backend verification) can replay the identical signed material against the backend under a freshly generated `signup_id`, presenting it as a new signup attempt for the same `user_id`/iris data. This is a cross-signup state-bleed / signup misattribution vector: a signup that the backend previously flagged as fraud, failed, or duplicate can be re-presented as an unrelated "fresh" signup session, because the only thing distinguishing sessions (`signup_id`) is unauthenticated.

### Likelihood Explanation
Exploitation requires the attacker to already have or observe a valid signed enrollment payload for some prior signup attempt (no privileged Orb/backend access is required — the payload transits as an HTTP multipart request originating from the Orb). Given multiple retries per signup (`RETRIES_COUNT`) and separate poll cycles, and that no server-verifiable link exists between the signed bytes and `signup_id`, a network-adjacent or MITM-capable observer of Orb traffic (an "unprivileged user"/observer relative to the signing key) can trivially construct the replay by swapping only the `signup_id` path segment while resending the same multipart body.

### Recommendation
Include `signup_id` (and ideally a monotonic/one-time nonce or timestamp) inside the data hashed and signed in `make_signature`, so the Secure Element signature cryptographically binds the biometric attestation to the specific signup session it was created for:

```rust
fn make_signature(signup_id: &SignupId, user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(signup_id.to_string().as_bytes()); // domain separator, analogous to chain.id
    ctx.update(user_qr_code.user_id.as_bytes());
    ...
}
```
The backend should then verify that the `signup_id` used in the request path matches the one embedded in the signed payload before accepting the signup.

### Proof of Concept
1. Observe/capture a legitimate signup's multipart POST to `/api/v2/signups/{signup_id}` (built in `signup_post::request`, `src/backend/signup_post.rs:125-143`), containing `signature`, `userId`, and `codes`.
2. Note that `signature` was computed solely from `ORB_ID + user_id + pipeline biometric fields` (`src/plans/enroll_user.rs:290-304`) and never includes `signup_id`.
3. Re-issue the same multipart body to `/api/v2/signups/{new_signup_id}` with a different, freshly-generated `signup_id` (e.g., `SignupId::new(...)`), leaving `signature`, `userId`, and `codes` unchanged.
4. Because signature verification (on the backend) only checks the Secure Element signature against the hashed fields it actually covers, and those fields don't include `signup_id`, the replayed request is indistinguishable from a legitimate new signup for the same user/biometric data, allowing the same attested capture to be re-applied to an unrelated signup session.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
