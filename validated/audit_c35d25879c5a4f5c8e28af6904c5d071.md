### Title
Webhook `topic` and `shop` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then hands the handler `topic` and `shop` values that are read directly from unauthenticated HTTP headers. Because the `api_secret_key` is shared by the app across all shops that install it, any merchant who has installed the app can obtain a validly-signed `(body, hmac)` pair for their own shop and replay it against the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header, causing the app to process attacker-supplied data as though it originated from a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body, excluding every Shopify header: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version`, however, are all read straight from the (unauthenticated) headers: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then forwards these header-derived, unauthenticated fields directly to the app's handler as the trusted tenant identity and event type: [4](#0-3) 

The documented handler contract explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and `data.topic` is "The topic of the webhook" — i.e., authoritative identity fields intended to be trusted after `Registry.process` succeeds: [5](#0-4) 

This breaks the intended binding: `shop_header == shop_that_produced_signed_body` is never checked; only `HMAC(body, api_secret_key) == received_hmac` is checked. Since `api_secret_key` is one value per app (not per shop), any of the app's own installed shops can legitimately obtain `(body, hmac)` pairs and then submit a webhook request with an arbitrary `shop-domain` header — the HMAC will still validate because it never covered the shop field, and the handler will attribute the (attacker-controlled) body content to a victim shop of the attacker's choosing.

### Impact Explanation
This qualifies as cross-tenant access: a single malicious app installer can spoof webhook events (including sensitive body content) as belonging to a completely different merchant's shop, since the shop identifier reaching the handler is never bound to the HMAC-verified bytes. Any downstream logic that trusts `data.shop` to look up or mutate per-tenant records (a pattern encouraged by the gem's own documentation, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be corrupted with attacker-chosen data attributed to a victim tenant.

### Likelihood Explanation
Medium-to-High: exploitation requires only that the attacker be able to install the same app on their own store (a normal, unprivileged action for any merchant/developer), capture one legitimately delivered webhook (body + HMAC), and replay it to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or any other privileged credential is required.

### Recommendation
Bind the header-derived identity fields to the authenticated payload before trusting them:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC validation (matching Shopify's actual webhook delivery, where the body itself already encodes the resource, but the app should additionally verify that `shop` corresponds to a shop with an active, expected installation/session before dispatching to the handler), or
- Have `Registry.process` cross-check `request.shop` against a known/authorized shop list (e.g., an active `Session` for that shop) before invoking the handler, rejecting webhooks for shops the app cannot corroborate independently of the header value.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, thereby causing Shopify to deliver legitimate webhooks (e.g. `orders/create`) signed with the app's shared `api_secret_key`.
2. Attacker captures one such delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker crafts a new POST to the app's webhook endpoint using the same body `B` and HMAC header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `HMAC(B, secret) == H`), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` from the forged header alongside attacker-controlled body `B`, causing the host app to process attacker data as belonging to the victim tenant.
