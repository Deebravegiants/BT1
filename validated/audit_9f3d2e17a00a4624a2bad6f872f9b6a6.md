### Title
Permissionless HyperSwap pair pre-seeding during the graduation window can force the LP open away from the curve close price - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding`'s graduation is split into two independently-callable transactions with an unbounded gap between them. Phase 1 (`_enterGraduating`, fired inline or via the permissionless `triggerGraduation`) freezes the curve and pins `tokensForLP`/`ltFromPair` at the curve-close ratio, but Phase 2 (`finalizeGraduation`) — which actually creates/uses the HyperSwap V2 pair and deposits liquidity — is a separate permissionless transaction that anyone can delay or race. Because pair creation on HyperSwap's factory is itself permissionless, an attacker can pre-create the TOKEN/LT pair and hostile-mint-seed it with a skewed ratio before `finalizeGraduation` lands, exercising exactly the "Regime 3" hostile-pre-seed path that the protocol's own documentation says is no longer covered by automated tests.

### Finding Description
Phase 1 (`_enterGraduating`) computes and caches `tokensForLP`/`ltFromPair` purely from `Pair` reserves, then flips `lifecycle: Curve → Graduating` and emits `TokenGraduating`, with no on-chain guarantee about when Phase 2 runs: [1](#0-0) 

`finalizeGraduation` is permissionless and, per its own natspec, relies only on an off-chain keeper to close the window quickly ("~60s"); there is no on-chain deadline or staleness check preventing an unprivileged caller from acting first: [2](#0-1) 

`_ensureUniswapV2Pair` creates the HyperSwap V2 pair on demand if it doesn't exist yet — this call, and pair creation on the underlying HyperSwap factory, are both open to anyone, meaning an attacker can pre-create the pair between Phase 1 and Phase 2 and mint-seed it with an arbitrary (token, LT) ratio before the honest `finalizeGraduation` call runs: [3](#0-2) 

`_seedUniswapV2Direct` dispatches to the hostile-mint-pre-seed branch (`_seedRebalancing`) whenever `totalSupply() != 0` on the pair, i.e. whenever an attacker has already minted LP into it: [4](#0-3) 

The rebalance/deposit path explicitly caps the corrective swap at "our per-side budget," and only falls back to a full direct-mint override when the pre-seed is small on *both* sides relative to the cached `tokensForLP`/`ltFromPair` (governed by `DIRECT_MINT_PRESEED_BPS`): [5](#0-4) 

The AGENTS.md documentation for this exact code path explicitly states that the dedicated hostile-pre-seed integration suite was removed post-deployment, and that it was the suite responsible for enforcing "the wrong-opening-price / LP-capture scenarios, attacker-no-profit, leftover recovery, and concurrent-graduation isolation properties": [6](#0-5) 

This is the same bug class as CVE-2019-20384: a privileged/trusted artifact (there, the nagios plugins directory; here, the HyperSwap LP that will be locked via `LPLock` and treated as the canonical graduated market) is finalized in two non-atomic steps, and an unprivileged actor with legitimate, permissionless access to the intermediate state (there, the nagios OS account writing to the not-yet-`fowners`'d directory; here, any EOA calling HyperSwap's `createPair`/`mint` before `finalizeGraduation` runs) can plant hostile content into that window before it becomes trusted.

### Impact Explanation
When the rebalance swap budget is insufficient to fully correct a large or extreme hostile pre-seed ratio, `_routerDepositAndDispose`'s `addLiquidity`-based deposit is computed against the attacker-skewed post-swap reserves rather than the curve-close ratio pinned in Phase 1. This can (a) open the graduated LP at a price away from the curve close price, breaking the protocol's documented "zero-gap" invariant, and (b) let the attacker's own pre-existing LP shares capture a portion of the deposit under V2's `min()`-based mint/deposit formulas, effectively extracting value from the curve-raised LT/token pool that should have gone entirely into the locked LP. This directly matches the accepted impact categories ("an LP seeded away from the curve close price," "concrete theft ... of trader, creator or LP funds").

### Likelihood Explanation
No privileged role is required: `triggerGraduation` and `finalizeGraduation` are both permissionless, and HyperSwap's V2 factory `createPair`/pair `mint` are permissionless as well, so any address watching for `TokenGraduating` events (or predicting graduation via mempool monitoring of the threshold-crossing buy) can race the keeper. The protocol's own AGENTS.md flags this as an active gap: the tests that once validated "attacker-no-profit" and "wrong-opening-price" bounds for this exact scenario have been removed and are "no longer enforced by automated tests," which is a strong first-party signal that the mitigation's coverage against large/adversarial pre-seed shapes is unverified.

### Recommendation
- Re-introduce (or replace) `test/HostilePreSeed.t.sol`-equivalent coverage asserting a hard bound on attacker profit / LP price deviation for pre-seed sizes exceeding `DIRECT_MINT_PRESEED_BPS` on one side.
- Consider adding an on-chain staleness/deadline check or a `minTokensForLP`/`minLtFromPair`-style slippage guard in `finalizeGraduation` so it reverts (rather than silently depositing at a degraded ratio) if the pre-swap pair state deviates from the cached Phase-1 ratio beyond a safe tolerance, forcing recovery via a different remediation path instead of accepting value leakage.
- Evaluate widening `_pairRebalance`'s per-side swap budget or lowering `DIRECT_MINT_PRESEED_BPS` so more hostile-pre-seed shapes are captured by the direct-mint override rather than the partially-corrective rebalance/deposit path.

### Proof of Concept
1. Attacker monitors for a `TokenGraduating` event (Phase 1) or predicts the threshold-crossing buy in the mempool.
2. Before the keeper's `finalizeGraduation` call lands, attacker calls HyperSwap V2 factory `createPair(token, lt)` (permissionless), then transfers a hostile (token, LT) ratio to the pair and calls `pair.mint(attacker)`, establishing `totalSupply() != 0` with an off-ratio reserve.
3. `finalizeGraduation(tokenAddress)` is eventually called (by keeper or attacker); `_ensureUniswapV2Pair` finds the existing attacker-seeded pair, and `_seedUniswapV2Direct` routes to `_seedRebalancing` since `totalSupply() != 0`.
4. If the pre-seed exceeds `DIRECT_MINT_PRESEED_BPS` on at least one side, the swap-based rebalance runs but is capped at a per-side budget; residual imbalance persists into the `addLiquidity` deposit, letting the attacker's pre-existing LP shares capture value and/or opening the locked LP away from the curve close price.

I was not able to fully trace the exact numeric cap formula inside `_pairRebalance` (the function body beyond line 1300 was not retrieved before the tool budget was exhausted), so the precise magnitude of extractable value under this path is unverified and would need to be confirmed against the full `_pairRebalance`/`_routerDepositAndDispose` implementation and a fuzz/PoC test reproducing a profitable attacker ratio.

        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }
