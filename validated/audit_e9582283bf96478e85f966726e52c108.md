Based on my investigation, both the Arbitrum and Optimism ISMP consensus clients derive the L2 state root exclusively from a raw `host.state_machine_commitment(l1_state_machine_height)` lookup, with no challenge-period/delay check before that L1 commitment is used as a trust anchor for the L2 verification.

### Title
L1 state commitment used as untrusted trust anchor before its challenge period has elapsed - (File: modules/ismp/clients/ismp-arbitrum/src/lib.rs, modules/ismp/clients/ismp-optimism/src/lib.rs)

### Summary
The Arbitrum and Optimism `ConsensusClient::verify_consensus` implementations fetch the L1 state commitment directly via `host.state_machine_commitment(l1_state_machine_height)` and use its `state_root` as the trusted anchor to verify L2 rollup/fault-proof-game proofs, without checking that the L1 state machine's challenge (dispute) period has elapsed for that height, unlike the `validate_state_machine` path used for request/response handling.

### Finding Description
`update_client` in [1](#0-0)  calls `consensus_client.verify_consensus` directly on the trusted consensus state after only checking the consensus client isn't frozen/expired — it never enforces the per-state-machine challenge period.

That challenge-period enforcement only exists in the separate `validate_state_machine` helper, used by request/response message handling: [2](#0-1) .

The Arbitrum client pulls the L1 commitment straight from storage and treats its `state_root` as ground truth for verifying the rollup/BoLD proof: [3](#0-2) . This state root is then passed to `verify_arbitrum_payload`/`verify_arbitrum_bold` as the anchor against which the L2 assertion is checked: [4](#0-3) .

The Optimism client does the same for both `OpL2Oracle` and `OpFaultProofGames` proof types: [5](#0-4) .

The `state_machine_commitment` accessor simply reads from the committed-state storage populated by `update_client` — [6](#0-5)  — as soon as an L1 consensus proof (e.g. sync-committee/BEEFY/GRANDPA) is verified and stored, with no separate finality/challenge gate applied at read time by these L2 clients. This mirrors the CVE-2026-6091 pattern: a peer-relayed intermediate state (an L1 commitment that is not yet "final" per the configured challenge period) is accepted as the trust anchor for downstream verification, instead of anchoring to a state the protocol has fully vetted as final/canonical.

### Impact Explanation
If the L1 state machine's challenge period exists specifically to allow fishermen/relayers to dispute or reorg around a fraudulent/ambiguous L1 commitment, using that commitment as a trust anchor before the period elapses lets a relayer submit L2 (Arbitrum/Optimism) consensus updates anchored to a not-yet-final L1 state root. A subsequent L1 reorg or fraud-proof invalidation of that L1 height would leave the L2 client's `finalized_height`/state commitments permanently derived from an anchor that was never actually finalized, forging state commitments for the L2 chain that downstream apps (token bridges, intents, message delivery) rely on for unsound state commitment/forged message delivery.

### Likelihood Explanation
Reachable directly by any relayer submitting a `ConsensusMessage`/`update_client` extrinsic containing an `ArbitrumUpdate`/`OptimismUpdate` with an `l1_height` pointing at a very recently stored (but not yet challenge-period-cleared) L1 commitment; no special privilege is required beyond submitting a signed consensus update, and the L1 height is fully attacker-chosen within the range of committed heights.

### Recommendation
Before using `l1_state_commitment` as the trust anchor in both `ismp-arbitrum` and `ismp-optimism` clients, verify the L1 state machine height has cleared its configured challenge period (mirroring `verify_delay_passed`/`validate_state_machine` in [7](#0-6) ) before trusting its `state_root` for L2 proof verification.

### Proof of Concept
1. Attacker/relayer submits an L1 consensus update (e.g. sync-committee) that stores a new `state_machine_commitment` for the L1 state machine at height `H`.
2. Immediately (before `H`'s configured challenge period elapses), the same or colluding relayer submits an Arbitrum/Optimism `ConsensusMessage` with `ArbitrumUpdate { l1_height: H, proof }` / `OptimismUpdate { l1_height: H, proof }`.
3. `verify_consensus` in [3](#0-2)  reads `state_root` for height `H` unconditionally and uses it to validate the L2 proof, producing a new L2 `StateCommitmentHeight` that is persisted via `update_client`.
4. If the L1 commitment at `H` is later found fraudulent/reorged (which the challenge period exists to catch), the L2 state commitment derived from it remains accepted on Hyperbridge, enabling forged message delivery/state proofs for that L2 chain.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
