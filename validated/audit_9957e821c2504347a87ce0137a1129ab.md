Based on the investigation, the closest analog to the reported bug class exists in the signup-completion logic in `src/plans/mod.rs`. The report's bug pattern is: a state-mutating function that is supposed to run only after a value transitions from "pending" to "confirmed/active" is instead invoked based on a preliminary condition, bypassing the actual confirmation gate, causing state to be committed/counted before it is truly authoritative.

### Title
Local, unconfirmed enrollment success determination bypasses backend fraud/duplicate confirmation for user-centric signups - (File: src/plans/mod.rs)

### Summary
In the standard signup flow, `enroll_user::Plan::run` is the authoritative "confirmation gate": it submits the signup to the backend via `signup_post::request` and then polls `signup_poll::request` until the backend returns a terminal `Completed` status, explicitly checking for backend-side duplicates, "inflight matches," and backend-detected fraud before declaring `Status::Success`. [1](#0-0) 
However, when `user_centric_signup` is true, `do_signup` skips this backend confirmation step entirely and instead derives `enrollment_status`/`success` purely from the locally computed `signup_reason` (itself derived only from local pipeline execution and local `detect_fraud`): [2](#0-1) 

### Finding Description
The `signup_reason` used to gate success is computed entirely from local, on-orb signals (pipeline completion and `detect_fraud`), before the backend has ever been consulted about this signup attempt: [3](#0-2) 
For the non-user-centric path, this `signup_reason` is only a hint sent to the backend as part of `signup_post::request`, and the actual "success" gate is the backend's own accept/poll cycle, which is documented to catch backend-side duplicate/fraud/inflight cases: [4](#0-3) 
For the user-centric path, this backend confirmation step (`enroll_user::Plan::run`) is never invoked at all — `debug_report.enrollment_status` and `result.success` are set directly from the local `signup_reason`: [5](#0-4) 
This mirrors the report's root cause: a "final/active" state (verified, successful signup) is derived from a preliminary/local signal instead of waiting for the authoritative confirmation step that is responsible for catching duplicates and fraud, and the UI is driven directly off of this locally-derived state: [6](#0-5) 

### Impact Explanation
Because the backend's duplicate-detection and backend-side fraud checks are bypassed for `user_centric_signup` orbs, the local `debug_report.signup_status`/`SignupStatus::Success` (and the corresponding UI "success" signal, `orb.ui.signup_success()`) can be emitted for a signup that the backend would have flagged as a duplicate, an inflight match, or fraudulent, since that check simply never runs from orb-core's side in this branch. This is a misattributed-signup risk: the physical signup event (biometric capture, PCP upload) is reported locally as "successful"/verified independent of whether the backend will ultimately treat the identity as unique, decoupling the orb's local determination of "signup success" from the backend's authoritative source of truth — the same class of issue as the reported bug, where a "pending" (unconfirmed) state was mistakenly treated as "active" (confirmed).

### Likelihood Explanation
This code path is not a hypothetical edge case — it is a normal, first-class operating mode driven by the `user_centric_signup` flag returned by the backend in `UserData`, and is only skipped when `ignore_user_centric_signups` is explicitly configured: [7](#0-6) [8](#0-7) 
Any orb configured to honor `user_centric_signup` (the default unless explicitly overridden) reaches this branch on every signup where the app requests app-centric mode.

### Recommendation
Do not derive `enroll_user::Status::Success` / `SignupStatus::Success` purely from local `signup_reason` in the `user_centric_signup` branch. Either route user-centric signups through an equivalent backend confirmation/poll step before reporting local success, or ensure the local UI/debug-report "success" state is explicitly scoped to mean "capture/pipeline succeeded, pending backend confirmation" rather than "signup succeeded," so it cannot be conflated with a backend-confirmed, deduplicated, non-fraudulent signup.

### Proof of Concept
1. Configure/receive a QR-code payload from the backend such that `UserData.user_centric_signup == true` (default app-centric mode) and `ignore_user_centric_signups == false` (default). [9](#0-8) 
2. Complete a biometric capture/pipeline such that `detect_fraud` returns `false` locally (trivially true in the FOSS build since `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`, but also possible in the full build for any capture that passes purely local checks even if it is, e.g., a duplicate of an already-enrolled iris): [10](#0-9) 
3. `signup_reason` resolves to `SignupReason::Normal`; the `user_centric_signup` branch sets `enroll_user::Status::Success` and `success = true` without ever calling `signup_post`/`signup_poll` to let the backend confirm uniqueness/fraud status: [2](#0-1) 
4. `orb.ui.signup_success()` is triggered and `SignupStatus::Success` is recorded in the debug report, even though the backend was never asked to confirm the signup is unique/non-fraudulent.
