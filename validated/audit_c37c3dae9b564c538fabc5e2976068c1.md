### Title
RAY index accrual overflow permanently freezes an overgrown lending market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Interest accrual multiplies total scaled supply and debt by their RAY indexes without first enforcing a total-value ceiling. Once a sufficiently large market's index grows enough that `scaled * index` exceeds `i128::MAX`, accrual panics. Because every market mutation loads an interest-synced cache first, subsequent withdrawals, repayments, liquidations, and index updates in that market all fail, permanently freezing the market and its funds.

### Finding Description
`accrue_step` computes `borrowed_original` and `supplied_original` by multiplying the stored RAY share totals by the current indexes. [1](#0-0)  These calls use `scaled_to_original`, which performs the index multiplication. [2](#0-1)  The same step then multiplies the debt total by both the old and newly calculated borrow indexes in `calculate_supplier_rewards`. [3](#0-2) 

Pool operations do not operate directly on the stored state: `load_leg` calls `synced_market`, which calls `interest::global_sync` before resolving or mutating a position. [4](#0-3)  `global_sync` applies `accrue_step` for every elapsed interest chunk. [5](#0-4)  Repayment consequently reaches the accrual path before calling `resolve_repay`, while withdrawal reaches it before `resolve_withdrawal`. [6](#0-5) [7](#0-6) 

The borrow index is nominally capped at `MAX_BORROW_INDEX_RAY`, but that cap is applied only after `old_index.mul(interest_factor)` completes and does not constrain the separately calculated RAY-denominated debt value. [8](#0-7)  An existing regression test demonstrates the cliff: after a large 18-decimal market accrues enough interest, `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`, while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

### Impact Explanation
This is permanent freezing of user funds and market functionality. Once the value product exceeds the `i128` domain, the accrual prerequisite itself reverts, so depositors cannot withdraw, borrowers cannot repay, and liquidators cannot execute liquidation withdrawals through the affected market. The public `Controller::update_indexes` path is also unusable because it forwards to the pool's accrual operation. [10](#0-9) [11](#0-10) 

Because the failing calculation occurs before debt resolution or state commitment, no amount of repayment, recapitalization, or ordinary parameter update on the same market can reduce the stored scaled balances enough to avoid the panic. The market remains unable to operate.

### Likelihood Explanation
Likelihood is medium. The condition requires a very large market and sustained positive interest accrual, so it cannot be triggered by a small account at initialization. However, all required actions—supplying liquidity, supplying collateral, borrowing up to the market's configured liquidity and utilization limits, and later calling `update_indexes`—are reachable by unprivileged authenticated users. [12](#0-11) [10](#0-9)  The index-cap check does not prevent this failure mode because the account-value product can overflow before the index reaches its configured ceiling. [13](#0-12) 

### Recommendation
Add a protocol-enforced invariant that the projected RAY value of total supply and total debt remains below the checked fixed-point domain before allowing new supply or debt. During accrual, compute the new debt value with an overflow-aware comparison before multiplying, and clamp or reject growth at a dedicated market-value ceiling rather than allowing the multiplication to panic.

At minimum:

- check `scaled` against `floor(i128::MAX / index)` before `scaled * index`;
- expose the remaining RAY-value headroom in market data;
- enforce that headroom in `supply`, `borrow`, and strategy debt-mint paths;
- allow emergency exits or debt settlement using the last committed indexes without forcing accrual when stored totals are already at the representability boundary;
- add regression coverage showing that `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `recapitalize` remain executable near the numeric boundary.

### Proof of Concept
1. As an unprivileged supplier, call `Controller::supply(caller, 0, spoke_id, [(debt_asset, principal)])`, where `principal` is a very large amount of an 18-decimal asset.
2. Create or use a borrower account with sufficient collateral in another listed asset.
3. Call `Controller::borrow(borrower, borrower_account_id, [(debt_asset, borrowed_amount)], to)`, where `borrowed_amount` is close to the market's available cash and allowed utilization.
4. Advance ledger time and repeatedly call the permissionless `Controller::update_indexes(caller, [debt_asset])`.
5. Eventually `accrue_step` attempts `borrowed * borrow_index` where the product exceeds `i128::MAX`, and the call panics with `MathOverflow`. [14](#0-13) 
6. Subsequent calls to `Controller::withdraw`, `Controller::repay`, and liquidation paths touching the same market fail before their business logic because each pool leg first calls `global_sync`. [4](#0-3) 

The repository's regression test encodes this same sequence and confirms `MathOverflow` on `update_indexes`, `withdraw`, and `repay`, with the borrow index still below its maximum. [15](#0-14)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount

        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
