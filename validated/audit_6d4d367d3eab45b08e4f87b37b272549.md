## Title
Reward pool permanently bricked (DoS on stake/unstake/harvest) after `expiry_block` due to uncapped `last_update_block` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes rewardable blocks in `reward_per_token` by capping "now" at the pool's `expiry_block` via `last_block_reward_applicable`, but `update_pool_rewards` persists the *uncapped* current block number into `pool_info.last_update_block`. Once a pool expires and receives one post-expiry interaction, `last_update_block` exceeds `expiry_block`, and every subsequent call to `reward_per_token` underflows on `ensure_sub`, permanently reverting `stake`, `unstake`, and `harvest_rewards` for that pool.

## Finding Description
`reward_per_token` computes elapsed rewardable blocks as `last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)?`, where `last_block_reward_applicable` returns `min(now, expiry_block)`: [1](#0-0) [2](#0-1) 

However, `update_pool_rewards`, invoked immediately after `reward_per_token` inside `update_pool_and_staker_rewards`, always stores the raw uncapped block number: [3](#0-2) [4](#0-3) 

After a pool expires, the first post-expiry interaction sets `last_update_block = now` (which is `> expiry_block`). On any subsequent interaction, `last_block_reward_applicable` still returns the capped `expiry_block`, so `expiry_block.ensure_sub(last_update_block)` underflows, and `ensure_sub` returns `Err(ArithmeticError::Underflow)`, which is propagated via `?` through `reward_per_token` and `update_pool_and_staker_rewards`. Both `unstake` and `harvest_rewards` call `update_pool_and_staker_rewards` unconditionally at the start of the extrinsic, before any state mutation, so the underflow reverts the whole call with no path to recovery (there is no admin function to reset `last_update_block`).

## Impact Explanation
Once triggered, all further `stake`, `unstake`, and `harvest_rewards` calls on the affected pool permanently fail with `ArithmeticError::Underflow`, locking all stakers' frozen tokens and unclaimed reward tokens in that pool indefinitely, with no in-pallet recovery mechanism. This is a real fund-freezing DoS bug in pallet logic, not a theoretical or admin-only issue.

## Likelihood Explanation
Any pool that is allowed to reach and pass its `expiry_block` — an expected, normal lifecycle event since pools are explicitly created with a finite expiry — will trigger this after just two post-expiry interactions (the first sets the bad `last_update_block`, the second underflows). No special privilege, attacker capability, or unusual conditions are required; a legitimate unprivileged staker interacting normally with an expired pool is sufficient.

## Recommendation
In `update_pool_rewards`, store the expiry-capped value consistently with `reward_per_token`, e.g. replace `T::BlockNumberProvider::current_block_number()` with `Self::last_block_reward_applicable(pool_info.expiry_block)` when setting `new_pool_info.last_update_block`. This keeps the "cursor" and the capped "now" used for reward accrual consistent and eliminates the underflow.

## Proof of Concept
1. `create_pool` with `expiry_block = 100` and a nonzero `reward_rate_per_block`.
2. `stake` some tokens before block 100, so `last_update_block < 100`.
3. Advance to block 150 (`now > expiry_block`). Call `harvest_rewards` (or `unstake`/`stake`): `reward_per_token` computes `100 - last_update_block` successfully; `update_pool_rewards` then sets `last_update_block = 150`.
4. Advance to block 200. Call `harvest_rewards`/`unstake`/`stake` again: `last_block_reward_applicable(100) = 100`, and `100.ensure_sub(150)` underflows, returning `Err(ArithmeticError::Underflow)`. This fails identically for every future call, permanently freezing staked funds and unclaimed rewards for the pool. This can be codified as a unit test in the pallet's mock runtime asserting the second post-expiry call returns `Err(ArithmeticError::Underflow.into())`.
