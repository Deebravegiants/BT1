### Title
Lockup Factory account creation is front-runnable, letting an attacker hijack a victim's lockup contract configuration - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the deployed lockup contract's account ID deterministically from a hash of only the `owner_account_id` argument, with no binding to the caller (`predecessor_account_id`) or to any secret/commitment. This is the same root cause as the reported ENS `ETHRegistrarController` front-running bug: a "reservation" for a name/identity is not tied to the entity that is supposed to redeem it, so an unrelated party can race the legitimate transaction and consume it with attacker-chosen parameters.

### Finding Description
In `lockup-factory/src/lib.rs`, `create()` computes the target account as: [1](#0-0) 
using only `sha256(owner_account_id)`. Nothing in this derivation includes `env::predecessor_account_id()`, the attached deposit, or any secret supplied by the intended funder. The function is also `#[payable]` and callable by anyone, and it accepts caller-supplied `vesting_schedule`, `lockup_duration`, `lockup_timestamp`, `release_duration`, and, notably, an optional custom `whitelist_account_id` that overrides the factory's default whitelist: [2](#0-1) 

Because the resulting account name depends solely on the public `owner_account_id`, any observer of the mempool who sees a pending `create` transaction intended to fund a particular employee/owner can front-run it with their own `create` call using the *same* `owner_account_id` but attacker-chosen `whitelist_account_id`, `lockup_duration`, `release_duration`, or `vesting_schedule`. Since NEAR account creation is exclusive (the second `create_account` promise fails once the account exists), the legitimate funder's transaction will fail at the `create_account` step and simply be refunded via `on_lockup_create`: [3](#0-2) 

The attacker's transaction wins the race and permanently establishes the lockup contract's immutable configuration for that owner — most importantly, `staking_pool_whitelist_account_id`, which the lockup contract's owner-facing staking flow relies on to validate which staking pool contracts are safe to delegate to (as documented in the lockup README's staking-pool trust model): [4](#0-3) 

If the attacker substitutes a malicious whitelist contract (which they fully control) at creation time, the resulting lockup contract will trust that malicious whitelist forever, since this field is only set once in `LockupContract::new` and cannot be changed later: [5](#0-4) 

Later, when the legitimate owner attempts to select a staking pool via the owner-only method, the check of whether a pool is safe to delegate to will be evaluated against the attacker's whitelist contract instead of the real one, allowing the attacker to have malicious pools "pass" as whitelisted.

### Impact Explanation
This matches the "Critical: permanent freezing/loss of funds" and "High: unauthorized state-transition / trust-anchor hijack" impact classes. By winning a front-running race that costs only the minimum attach deposit, an unprivileged attacker can permanently fix a victim's lockup contract to trust an attacker-controlled staking-pool whitelist. When the (unaware) owner later delegates tokens to a pool that the compromised whitelist reports as legitimate, the owner's staked/locked NEAR can be routed to a malicious staking pool and lost, since the whitelist is the sole safety gate documented for this purpose.

### Likelihood Explanation
`create()` is fully public and payable by any account, the target account ID is fully predictable from the public `owner_account_id` argument before the transaction is included, and NEAR mempool transactions are visible before finality, giving an attacker a normal front-running window (submit with a higher gas/priority) to win the account-creation race. No privileged role or key is required — this fits the "strictly unprivileged, public-call entry" requirement.

### Recommendation
Bind the derived lockup account ID (or at minimum, gate the ability to set custom `whitelist_account_id`/schedule parameters) to the calling/funding account, e.g., include `env::predecessor_account_id()` in the hash used to derive `lockup_account_id`, or require a commit-reveal scheme where the committer's account is bound into the commitment (analogous to the ENS fix of tying `commit()`/`register()` to `msg.sender`). Alternatively, disallow arbitrary callers from overriding `whitelist_account_id` and vesting/lockup parameters for an owner they do not control, or require the `owner_account_id` itself (or a value it signs) to authorize contract creation.

### Proof of Concept
1. Employer Alice intends to fund a lockup contract for employee Bob and broadcasts `create({owner_account_id: "bob.near", lockup_duration: ..., whitelist_account_id: None})` with the required deposit.
2. Attacker Eve observes this pending transaction in the mempool and computes the same deterministic `lockup_account_id = sha256("bob.near")[..20] || factory_account`.
3. Eve submits her own `create({owner_account_id: "bob.near", whitelist_account_id: "evil-whitelist.near", ...})` call with a higher gas price/priority, winning the `create_account` race.
4. Alice's transaction's `create_account` promise fails because the account already exists; her deposit is refunded via `on_lockup_create`'s failure branch.
5. Bob's lockup contract is now permanently configured with `staking_pool_whitelist_account_id = "evil-whitelist.near"`, controlled by Eve, which will falsely report Eve's malicious staking pool as whitelisted whenever Bob tries to delegate funds.

Note: I was unable to fully read `lockup/src/owner.rs`'s `select_staking_pool` implementation in this session (tool access ended) to quote the exact whitelist cross-contract-call check line numbers; this should be verified directly to confirm the exact call site, though the README and `LockupContract::new` field wiring already establish the whitelist account as the trust anchor for staking pool selection.     pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
