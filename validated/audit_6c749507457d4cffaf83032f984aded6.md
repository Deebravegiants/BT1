### Title
Permissionless, front-runnable `Initialize2` lets an attacker seize a pool's deterministic PDA and dictate its opening price - ([File: program/src/processor.rs])

### Summary
`process_initialize2` (the analog of the reported `EmergencyOracle` deployment) is callable by any signer, with no restriction that the caller must be the intended pool creator, and every account it creates (`amm_info`, `amm_lp_mint`, coin/pc vaults, `amm_target_orders`) is derived as a deterministic PDA from `(program_id, market, seed)` rather than from the caller's identity. [1](#0-0) [2](#0-1) 

### Finding Description
`Initialize2` accepts `init_pc_amount`/`init_coin_amount` chosen entirely by the transaction sender, with the only checks being that the coin/pc mints differ and that the resulting vault balances are non-zero and the computed liquidity exceeds one unit of decimals. [3](#0-2) [4](#0-3) 

Because the AMM account, LP mint, and vault addresses are computed purely from `market_info.key` and fixed seed constants (`AMM_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, etc.) via `find_program_address`, anyone who knows (or observes in the mempool) the market/mint pair intended for a new pool can precompute the exact same addresses that a legitimate pool creator would use. [5](#0-4) [6](#0-5) 

An attacker can therefore submit their own `Initialize2` instruction for the same market/mints first, supplying whatever `init_coin_amount`/`init_pc_amount` ratio they choose (subject only to the minimum-liquidity check), thereby setting the pool's opening exchange rate and becoming the sole/majority LP holder before the legitimate creator's transaction lands. [7](#0-6) 
When the legitimate creator's transaction is subsequently processed against the same deterministic addresses, it fails with `RepeatCreateAmm` because the accounts are already assigned/initialized. [8](#0-7) 

This mirrors the report's root cause exactly: a privileged/first-mover initialization step (`EmergencyOracle`/pool creation) with a deterministically-derivable address and no access control, allowing an attacker's front-run transaction to seize control of the resulting state (there: the oracle price feed; here: the pool's price and LP supply).

### Impact Explanation
Once the attacker's skewed pool exists at the expected address, any user who later swaps or deposits against it (believing it to be the genuine, fairly-priced pool for that market/mint pair) trades against an attacker-controlled price ratio, and the attacker — as the majority/sole LP — can extract value from subsequent deposits and swaps priced off that manipulated ratio. This is a concrete theft vector against unsuspecting swappers/LPs interacting with the pool, satisfying the "insolvent/attacker-controlled pool accounting" impact class.

### Likelihood Explanation
Exploitation requires the attacker to learn the intended market/mint pair before (or as) the legitimate `Initialize2` transaction confirms — e.g., by monitoring the mempool for the pending creation transaction, or by independently creating the pool for a popular market ahead of the expected creator. This is feasible on Solana given transaction visibility prior to finalization, but it does require the attacker to act opportunistically rather than passively, so likelihood is Medium rather than High.

### Recommendation
- Require the pool creator to be an authorized/allow-listed signer (or gate `Initialize2` behind a permissioned "pool factory" step) for markets/mints that have not yet been paired, similar to the report's recommendation to restrict `newEmergencyOracle` to `onlyOwner`.
- Alternatively, bind the AMM PDA derivation to the creator's pubkey (or a creator-supplied nonce) in addition to the market, so an attacker cannot precompute and preempt the legitimate creator's specific pool address.
- Enforce a minimum absolute liquidity/notional-value requirement (not just a per-decimals liquidity floor) so that skewing the initial price is economically costly for an attacker.

### Proof of Concept
1. Legitimate user Alice prepares an `Initialize2` transaction for `market M`, `coin_mint`, `pc_mint` with a fair 1:1 value ratio and submits it.
2. Attacker Bob observes Alice's pending transaction (or independently targets the same market before Alice acts) and computes the same deterministic PDAs via `find_program_address([program_id, M, AMM_ASSOCIATED_SEED/...])`. [1](#0-0) 
3. Bob submits his own `Initialize2` with the same accounts but a heavily skewed `init_coin_amount`/`init_pc_amount` ratio and higher priority fee, landing before Alice's transaction.
4. Bob's transaction succeeds, creating the pool, minting LP tokens to Bob at the skewed ratio. [7](#0-6) 
5. Alice's original transaction now fails with `AmmError::RepeatCreateAmm` since the accounts are already assigned. [8](#0-7) 
6. Subsequent swappers/depositors interacting with the "M/coin_mint/pc_mint" pool trade against Bob's attacker-controlled price, allowing Bob to extract value as the majority LP.
