### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the acting shop identity from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC that `ShopifyAPI::Webhooks::Registry.process` verifies only covers the raw request body. Any attacker who can obtain one genuine, validly-signed webhook for the app (e.g. by installing the app on their own free development store, since the HMAC key is the single `client_secret` shared across every shop using the app) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop. The signature still validates because the header is never part of the signed data, so the app's handler executes believing the payload originated from the victim tenant.

### Finding Description
The identity binding that must hold is: `shop domain used by the handler == shop domain that the HMAC signature actually authenticates`. In this gem that equality is broken.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header with no cross-check against the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`, and never touches `shop`: [3](#0-2) 

`Registry.process` only calls `HmacValidator.validate(request)` and then immediately trusts `request.shop` when building the data passed to the app's handler: [4](#0-3) 

Because Shopify signs webhooks with the app's `client_secret` — which is identical for every shop that installs a given app — a request that is truly signed for shop A (obtainable by the attacker for their own store A) remains a byte-for-byte valid signature no matter which shop-domain header accompanies it. The gem performs no independent verification that the header's shop actually corresponds to the body/signature pair (e.g. no shop field embedded in and covered by the signed content, no expected-shop allow-list check against the caller's known installed shops). This is the direct analog of the reported bug class: a field that is acted upon (`shop`, used to select tenant context for the handler) is not covered by the authenticity check (`hmac` over `raw_body` only) that is supposed to bind the whole message to a specific identity.

### Impact Explanation
This allows cross-tenant confusion/injection: an unprivileged internet user who can install the app for free on any shop (dev/trial store) can craft forged webhook deliveries that the app will process as coming from a different, victim merchant shop. Any host application logic that keys behavior off `data.shop` from `WebhookMetadata` (e.g., updating that shop's local records, triggering `customers/redact` / `shop/redact` compliance flows, or other per-tenant side effects) can be manipulated to act against a shop the attacker does not control. This crosses the tenant boundary and matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitability requires only: (1) ability to install the target app on an attacker-controlled shop to receive one legitimately signed webhook (trivial and free via Shopify partner/dev stores), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with a modified shop-domain header — both are unprivileged, internet-reachable actions requiring no access token, no `client_secret`, and no social engineering.

### Recommendation
Bind the shop identity to the signed content instead of trusting an out-of-band header:
- Include the shop domain in `to_signable_string` (or otherwise incorporate it into the value being HMAC'd) so any substitution of the header invalidates the signature, or
- Require callers to supply/verify the expected shop out-of-band (e.g., match `request.shop` against the shop associated with the webhook subscription/session that originally registered for that topic) before invoking the handler, or
- At minimum, document/enforce that `Registry.process` callers must independently confirm `request.shop` is one of their known, installed shops before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Install the target Shopify app on attacker-owned dev store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to capture a real request with body `raw_body` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, raw_body)`.
2. Replay this exact `raw_body` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"victim.myshopify.com"` from the header (`lib/shopify_api/webhooks/request.rb:20-23`), while `to_signable_string` is unaffected by header changes (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, raw_body)` and matches `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), so `Registry.process` accepts the request and invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:190-199`) — even though Shopify never actually sent a webhook for `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
