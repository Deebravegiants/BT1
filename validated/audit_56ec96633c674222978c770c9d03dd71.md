### Title
Panic-based DoS in `pallet-hyper-fungible-token`'s `on_accept` via unchecked `message.from` length when dispatching calldata - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`IsmpModule::on_accept` in the hyper-fungible-token pallet derives a dispatch origin `AccountId` from the ABI-decoded `message.from` field whenever a cross-chain transfer carries optional `data` but no `signature`. Unlike every other place in this same file that converts an attacker-supplied byte slice into a fixed-size array, this code path performs a raw `copy_from_slice`/unchecked slice indexing with no length check, so a malformed message can panic the runtime the moment a relayer delivers it — exactly the "attacker picks a value that makes a length-sensitive conversion panic" bug class described in the Velociraptor `SetPassword` report.

### Finding Description
In `on_accept`, the recipient conversion is safely guarded: [1](#0-0) 

But the sender/origin conversion used to dispatch optional calldata is not: [2](#0-1) 

`message` is produced by `Message::abi_decode(&body)`, where `body` is the raw PostRequest payload originated on the *source* chain contract mapped via `ContractToAsset`: [3](#0-2) 

`message.from` is an ABI dynamic `bytes` field, so its length is fully controlled by whoever calls the source-chain bridge contract to originate the transfer (an ordinary bridge user, not a privileged actor) — it is not validated by consensus or the state-machine proof, only the *value* of `body` is authenticated as having originated from the mapped contract, not its internal field lengths.

The vulnerable branch executes only when `message.data` is non-empty and `substrate_data.signature` is `None`:
- If `source.is_evm()`: `&from_bytes[from_bytes.len() - 20..]` — if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows in `usize` arithmetic, causing an arithmetic-overflow panic (checked in debug, and the subsequent slice range panics in any build regardless, since a negative/huge start index is out of bounds).
- If `!source.is_evm()`: `account.copy_from_slice(from_bytes)` requires `from_bytes.len() == 32` exactly; the compiler-generated bounds check inside `copy_from_slice` panics on any other length.

This mirrors the pattern already recognized and fixed elsewhere in the codebase (e.g. `as_utf8_string` deserializer and `StateMachine::from_str` in `modules/ismp/core/src/host.rs`, both patched specifically because "it runs on untrusted... input, so it must never panic" and "a wasm trap reachable from untrusted input"): [4](#0-3) [5](#0-4) 

The same class of bug was left unfixed in `hyper-fungible-token`'s `on_accept`, even though the pallet's own `HftError` enum already has the analogous, unused validation path (`InvalidSenderLength`) applied correctly in `on_timeout` but not here: [6](#0-5) [7](#0-6) 

`on_accept` is invoked by ISMP's request-handling path when a relayer delivers a proven `PostRequest` (e.g. through `handle_unsigned`), which any unprivileged relayer can submit once a valid state/consensus proof exists for the source chain: [8](#0-7) 

### Impact Explanation
A panic inside pallet execution during message dispatch traps the WASM runtime call. Depending on how the executor handles this, it can abort transaction processing for the whole block, repeatedly deny block finalization if relayers keep resubmitting the same malformed message (unsigned extrinsics can be freely resubmitted by any relayer), or crash the node process executing the runtime call — a denial-of-service against the entire Hyperbridge (permanent halt of message delivery / freezing of the chain's liveness), which the analog explicitly requires ("a route unable to deliver messages").

### Likelihood Explanation
High reachability: any account able to call the source-chain HFT bridge contract (an unprivileged end user) can set an arbitrary-length `from` field and non-empty `data` with no `signature`, and any unprivileged relayer can then deliver the resulting `PostRequest` via `handle_unsigned`/`ismp::handle`. No special permissions, governance, or malicious validator role is required — matching the CVSS `PR:L`/`AC:L` profile of the reference report.

### Recommendation
Apply the same explicit length validation used elsewhere in this file (`InvalidRecipientLength`/`InvalidSenderLength` pattern) to the `message.from` conversion inside the calldata-dispatch branch of `on_accept`:
- For the EVM case, check `from_bytes.len() >= 20` before slicing, returning `HftError::InvalidSenderLength` otherwise.
- For the non-EVM case, check `from_bytes.len() == 32` before `copy_from_slice`, returning the same error otherwise.

### Proof of Concept
1. On the source EVM chain, call the HFT bridge contract to dispatch a `PostRequest` whose ABI-encoded `Message` sets `from` to a byte string of length ≠ 20/32 (e.g. 5 bytes) while `data` is non-empty `SubstrateCalldata` with `signature: None`.
2. Wait for/produce the state proof for that height (or use any other state machine already configured with a valid consensus client, per test flows shown in `parachain/simtests/src/pallet_ismp.rs`).
3. Submit the resulting `RequestMessage` via `Ismp::handle_unsigned` as an ordinary relayer, following the same pattern used in `tesseract/messaging/integration-test/src/lib.rs` (`send_unsigned_extrinsic(... "Ismp", "handle_unsigned" ...)`).
4. `on_accept` is invoked, reaches the `else` branch (no signature) at `modules/pallets/hyper-fungible-token/src/module.rs:176-186`, and panics on `copy_from_slice`/slice indexing due to the mismatched `from_bytes` length, aborting the runtime call that processed the block.
