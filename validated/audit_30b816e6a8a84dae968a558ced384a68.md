### Title
Webhook tenant identity (`shop`) is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is verified via `Utils::HmacValidator.validate`, but the HMAC only signs the raw request body (`to_signable_string` returns `@raw_body`). The `shop` attribute, which the host application uses to identify which merchant/tenant a webhook belongs to, is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed bytes.

### Finding Description
The identity-binding invariant that should hold is:
`shop authenticated by HMAC == shop used by the handler to select/attribute a tenant`

In this gem that invariant is broken:
- `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` — i.e., over `@raw_body` only [1](#0-0) [4](#0-3) .
- Once the HMAC check passes, `Registry.process` builds `WebhookMetadata` using `request.shop`, which is taken verbatim from the unsigned `shop-domain` header [2](#0-1) [3](#0-2) .
- The `shop` value is then handed directly to the app's `WebhookHandler#handle` implementation as the trusted tenant identifier via `WebhookMetadata` [5](#0-4) .

Because a single app shares one `client_secret`/`api_secret_key` across all merchants that install it, any unprivileged merchant who has installed the app can legitimately receive a validly-HMAC-signed webhook body for their own shop. Since the header carrying the `shop` value is outside the signed data, that same attacker-controlled HTTP request (same body/HMAC pair, replayed against the app's webhook endpoint with a different `x-shopify-shop-domain` header) still passes `HmacValidator.validate`, yet is now attributed by the gem to an arbitrary victim shop. This is exactly the "field acted on but not covered by the HMAC" analog: the gem verifies the bytes of the body but trusts the un-verified `shop` field for tenant attribution downstream.

### Impact Explanation
This directly enables cross-tenant confusion inside the host application: a webhook payload that is valid (HMAC-wise) can be attributed by the gem to any shop the attacker chooses, because `request.shop` is not bound to the HMAC. Any host app that uses `WebhookMetadata#shop` to look up a merchant record, session, or perform per-tenant side effects (as the gem's documented `WebhookHandler` API explicitly encourages) will act on forged tenant data despite the HMAC check having "succeeded." This matches the Critical "cross-tenant access" impact category, since the identity check that is supposed to bind the verified payload to a specific tenant is absent in the gem itself.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchants (the standard SaaS/embedded-app model): every installed merchant is an "unprivileged internet user" relative to other tenants of the same app, and each already possesses the legitimate ability to trigger real webhooks with valid signatures for their own shop. No secret material beyond what a normal merchant already has access to (the ability to generate their own store's webhook traffic) is required to construct the mismatched header/body combination, because the header is never covered by the signature.

### Recommendation
Bind the `shop` identity into the signed material used for webhook verification, or otherwise force the host app to reconcile it, e.g.:
- Extend `to_signable_string` (or add a separate authenticated check) to include the `shop-domain` header value in the HMAC computation, matching what Shopify's mandatory webhook contract actually signs, OR
- Require callers of `Registry.process`/`WebhookHandler#handle` to independently confirm `WebhookMetadata#shop` corresponds to a shop domain the app already has an active session/install record for before trusting it as a tenant key, and document this requirement prominently since the gem currently implies `shop` is trustworthy once `HmacValidator.validate` returns `true`.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and triggers a webhook (e.g. `orders/create`) for their own store, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — both are valid, since the HMAC is computed only over the body using the app's shared secret [6](#0-5) .
2. Attacker replays that exact body + HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object where `shop` returns `"victim.myshopify.com"` [2](#0-1) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and succeeds, since the body is unmodified [7](#0-6) .
5. `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` is passed to the app's handler, which now processes attacker-controlled data as if it originated from `victim.myshopify.com` [8](#0-7) .
