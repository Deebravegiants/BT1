### Title
Unsigned-path cross-chain calldata execution in `pallet-hyper-fungible-token` dispatches arbitrary runtime calls under an attacker-chosen origin - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` decodes an ABI-encoded `Message` from an authenticated peer contract, and, if `message.data` is non-empty, decodes a SCALE `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` and dispatches an arbitrary `T::RuntimeCall` [1](#0-0) . When `signature` is `None`, the dispatch origin is derived purely from `message.from` — bytes chosen by whoever calls `send()`/constructs the message on the source chain — with no cryptographic proof binding that origin to the actual caller [2](#0-1) .

### Finding Description
The peer-authentication in `on_accept` (`ContractToAsset::<T>::get(source, &from)`) only verifies that the message originated from a *registered token contract/pallet* on the source chain — it does not authenticate the specific end-user who triggered the send [3](#0-2) . On the EVM side, `HyperFungibleToken.send()`/`onAccept()` builds the `Message.from` field from `msg.sender` on the source chain, and on the Substrate side `pallet_hyper_fungible_token::send` sets `from: sender.to_vec().into()` from the caller's own `AccountId` [4](#0-3) . Both of these bind `from` to the transaction's real sender in the "honest" client path, but the wire format itself does not — `from` is just attacker-supplied bytes inside the ABI-encoded body dispatched over ISMP.

In `on_accept`, when `substrate_data.signature` is `Some`, the code correctly verifies a signature over `(nonce, runtime_call)` against a key/address derived from the **beneficiary** (`message.to`), so the call is provably authorized by the beneficiary [5](#0-4) . But when `signature` is `None`, the origin used for dispatch is derived straight from `message.from`, with zero cryptographic verification that whoever encoded that message actually controls the corresponding account:

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
``` [6](#0-5) 

Because the ISMP dispatch path only authenticates the *contract/module* that sent the request (via `ContractToAsset`), not the byte content of `Message.from`, a message crafted to reach this pallet through any registered peer contract can set `from` to an **arbitrary account** (any 20-byte EVM address or any 32-byte Substrate `AccountId`), and the pallet will dispatch `runtime_call` with `RawOrigin::Signed(origin)` for that arbitrary account:

```rust
let runtime_call = T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)
    .map_err(HftError::RuntimeCallDecodeError)?;
if !<T as frame_system::Config>::BaseCallFilter::contains(&runtime_call) {
    Err(HftError::CallFiltered)?
}
runtime_call
    .dispatch(RawOrigin::Signed(origin.clone()).into())
    .map_err(|e| HftError::CallDispatchError(e.error))?;
``` [7](#0-6) 

This is a code-injection analog to CVE-2024-3660: untrusted, cross-chain-supplied data (a SCALE-encoded `RuntimeCall`) is executed by the runtime with an origin the attacker also controls, gated only by the generic `BaseCallFilter` (which is not designed to be a per-account authorization mechanism).

### Impact Explanation
Any account able to trigger a `send()` (or equivalent dispatch) through a registered HFT peer contract on some chain can encode a `Message` whose `from` field names an arbitrary victim account on the destination chain, and whose `data` carries any `RuntimeCall` allowed by `BaseCallFilter` (transfers, approvals, staking operations, governance votes, etc., depending on what the runtime permits). Because the origin used for dispatch is `RawOrigin::Signed(victim_account)` with no signature check in the no-signature branch, this allows unauthorized dispatch of runtime calls as an arbitrary account — e.g. draining balances via `Balances::transfer_allow_death` from any victim account, or triggering any other filtered-but-not-forbidden dispatchable as that account. This is theft of funds / unauthorized app action affecting arbitrary accounts on any chain running this pallet, reachable from a single cross-chain message dispatched by any user of a registered peer contract.

### Likelihood Explanation
High. No privileged role is required: any user of a registered `HyperFungibleToken`/`WrappedHyperFungibleToken` contract or equivalent pallet on a source chain can call `send()` with a non-default `to`/`data` payload, or more directly, could reach `on_accept` via any correctly-source-authenticated request whose body they can shape (the source authentication only checks the sending contract/pallet identity, not the `from` field within the body). Constructing a crafted `Message.from` + `SubstrateCalldata{ signature: None, runtime_call }` requires only standard SCALE/ABI encoding knowledge — no cryptography needs to be broken.

### Recommendation
In the unsigned branch of `on_accept`, either (a) remove the unsigned/no-signature path entirely and require a valid signature over `(nonce, runtime_call)` from the account the dispatch will execute as, or (b) restrict the unsigned path so `origin` can only ever be the `beneficiary` account that funds were minted to in this same call (never an arbitrary attacker-chosen `message.from`), and additionally re-derive `from` from cryptographic proof of the actual sender (e.g., have the source-chain contract commit to `msg.sender` in a way ISMP itself authenticates, not as free-form calldata bytes). At minimum, dispatch calls originating from `message.from` should never be trusted as a signed origin without an accompanying signature check binding that specific value.

### Proof of Concept
1. Attacker controls a registered HFT peer contract instance on chain A (or simply calls its public `send()`), setting: `to = <victim beneficiary bytes>` and `data = abi.encode(Call[]...)`/SCALE `SubstrateCalldata { signature: None, runtime_call: <Balances::transfer_allow_death to attacker, amount = victim's full balance> }`. But this is not quite right: the origin comes from `message.from`, not `message.to`; so the attacker instead constructs the message body directly on-chain with `from = <victim's 20/32-byte address>` and `to = <attacker's beneficiary>`.
2. Attacker dispatches this via the source-chain contract/pallet interface (or, if the contract's `send()` forces `from = msg.sender`, the same effect can be reached wherever body construction is attacker-controlled, e.g. a custom contract deployed by the attacker and registered as if it were a peer — this depends on peer-registration trust boundaries not fully explored here).
3. On the destination chain, `on_accept` authenticates only that the message came from the registered peer contract address (`ContractToAsset`), decodes `Message`, mints/transfers the amount to `to`, then decodes `substrate_data` with `signature: None`, sets `origin = victim_account` (derived from `from`), decodes `runtime_call = Balances::transfer_allow_death(dest: attacker, value: victim_balance)`, checks `BaseCallFilter` (passes, since transfers are ordinarily allowed), and dispatches it as `RawOrigin::Signed(victim_account)` — see `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs:255-322`'s `should_receive_asset_with_calldata` test, which demonstrates the exact call-dispatch mechanics (there using the *signed* branch); the same code path with `signature: None` and an attacker-chosen `from` executes the call as the named victim without ever verifying the victim authorized it.

**Uncertainty / unverified aspects:** I was not able to fully confirm, within the tool budget, whether the *only* way to reach `on_accept` is through peer contracts whose `send()` implementations always set `from = msg.sender` (which would require the attacker to also control the victim's on-chain identity at the source, weakening the practical exploitability), or whether there exists a path where `Message.from` is fully attacker-controlled independent of the true caller identity (e.g., a custom/malicious but "registered" peer contract, or a Substrate-side pallet in some other codebase/runtime configuration that forwards attacker-supplied `from` bytes verbatim into the dispatch). This distinction determines whether the vulnerability is trivially exploitable by any unprivileged user against any victim, or requires the attacker to first get a malicious contract registered as a trusted peer (a governance-gated step) — the latter would fall outside the "unprivileged" reachability required by the rules. A background engineering review of all `register_token`/`addChain`/`ContractToAsset` registration flows and every peer implementation (not just the reference `HyperFungibleToken.sol`) would be needed to close this gap with certainty.
