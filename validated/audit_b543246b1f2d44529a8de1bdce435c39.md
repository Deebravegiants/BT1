### Title
`CallDispatcher.dispatch` treats a non-reverting-but-failed token call as success, allowing tokens routed through cross-chain calldata to be silently stranded - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch` only checks that each low-level `.call()` in a `Call[]` batch did not revert; it never inspects the ABI-encoded boolean return value of ERC20-style calls (e.g. `transfer`/`transferFrom`). This is the same class of bug as the reported `DssChangeRatesSpell.cast()` issue: a call can "succeed" (no revert) while the target signals failure through a `false` return value, and the caller has no way to know the intended state change did not happen.

### Finding Description
`CallDispatcher.dispatch` executes each `Call` in a batch and only reverts if the raw call reverts: [1](#0-0) 

```solidity
(bool success, bytes memory result) = to.call{value: call.value}(call.data);
if (!success) revert CallFailed(to, result);
```

There is no decoding/verification of `result` against an expected `true` for calls such as `IERC20.transfer`/`transferFrom`. Any ERC20 (or ERC20-like) implementation that returns `false` on failure instead of reverting — a well-known non-standard-but-legal ERC20 pattern — will make `dispatch` report success even though the transfer did not occur.

This contract is reachable directly from unprivileged, protocol-critical paths:
- `HyperFungibleToken.onAccept` / `HyperFungibleTokenUpgradeable.onAccept` / `WrappedHyperFungibleToken.onAccept` / `WrappedHyperFungibleTokenUpgradeable.onAccept` execute arbitrary relayer-delivered `message.data` (an ABI-encoded `Call[]`) via `ICallDispatcher(_dispatcher).dispatch(message.data)` right after minting/unlocking tokens to the beneficiary: [2](#0-1) [3](#0-2) 

- `IntentGatewayV2.placeOrder`/`IntentsBase._execute` route order predispatch/postdispatch calldata through the same `CallDispatcher`: [4](#0-3) [5](#0-4) 

`CallDispatcher` has no owner/rescue function; it is a stateless dispatcher with only `receive()` and `dispatch()`: [6](#0-5) 

Note: the *internally generated* sweep `Call[]` used inside `IntentGatewayV2`/`IntentsBase` (built with `abi.encodeWithSelector(IERC20.transfer.selector, ...)` for moving swept balances back to the gateway) are followed up with a `balanceOf` diff check by the calling contract, which mitigates the silent-failure risk for that specific internal step. However, this balance-diff safety net exists only for the gateway's own bookkeeping calls — it does **not** exist for the arbitrary, user/relayer-supplied `order.predispatch.call`, `order.output.call` (`PaymentInfo.call`), or the cross-chain `message.data` delivered to `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept`. Those calls can freely include a token `transfer`/`transferFrom` to a non-standard token that returns `false`; `CallDispatcher` will report the whole batch as successful.

### Impact Explanation
If a call inside a relayer-delivered or user-defined `Call[]` batch is a token transfer to/through the `CallDispatcher` that silently fails (returns `false` without reverting):
- Tokens that were pushed into the `CallDispatcher` as part of a multi-step swap/route (e.g., `HyperFungibleToken`'s cross-chain calldata execution, or `IntentGatewayV2`'s predispatch/postdispatch composable calls) can become permanently stranded in the `CallDispatcher` contract, since it has no sweep/rescue mechanism and its balance is not attributable to any specific order or user.
- The overall cross-chain delivery (mint, escrow release, order fill) is still marked as completed/finalized because `dispatch()` did not revert, so the relayer/user has no signal that the composed action failed. This matches the report's "spell marked done though target did not change" pattern, but here it can result in tokens being trapped with no recovery path — a permanent freezing of funds condition reachable by an unprivileged relayer delivering a cross-chain message or a user/solver constructing an order's calldata field.

### Likelihood Explanation
Reaching this requires only that one of the tokens used in composed calldata (input/output token of an intent order, or a token referenced in a HyperFungibleToken message's `data` field) be a non-standard ERC20 that returns `false` instead of reverting on failure — a documented and non-rare pattern among real-world tokens (e.g., some legacy or non-compliant tokens, and certain fee/allowance-restricted implementations). No special privileges are needed: any user placing an order with calldata, or any relayer delivering a cross-chain message whose payload references such a token, can trigger the condition. Likelihood is Medium: it depends on token choice rather than being universally exploitable with mainstream tokens (e.g., standard USDC/USDT/WETH all revert or correctly return true/false in ways SafeERC20 elsewhere in the codebase already guards against), but the protocol explicitly supports arbitrary tokens/calldata in these paths.

### Recommendation
**Short term:** Document that a call routed through `CallDispatcher` can be reported as successful even when an ERC20 transfer inside it returned `false`, and warn integrators/relayers that composed calldata must only use tokens that revert on failure, or that they must independently verify balance changes.

**Long term:** Have `CallDispatcher.dispatch` (or its callers) validate ERC20-style return values using OpenZeppelin's `SafeERC20`/`Address.functionCall` semantics (i.e., treat a `false` boolean return the same as a revert), and/or add a permissioned sweep/rescue function so tokens accidentally stranded in `CallDispatcher` are not permanently frozen.

### Proof of Concept
1. Deploy a non-standard ERC20 `EvilToken` whose `transfer`/`transferFrom` returns `false` (instead of reverting) once a certain internal condition is hit (e.g., after a blacklist flag, or simply always returns `false` for calls from a specific caller).
2. A user places an `IntentGatewayV2` order (or triggers an `HyperFungibleToken` cross-chain send) whose `predispatch.call`/`output.call`/`message.data` includes a `Call` to `EvilToken.transfer(finalRecipient, amount)`, after first funding the `CallDispatcher` with `EvilToken` via a prior `Call` in the same batch (e.g., `transferFrom(msg.sender, dispatcher, amount)` from a proxy call, or via the predispatch asset transfer path).
3. `CallDispatcher.dispatch` executes `EvilToken.transfer(finalRecipient, amount)`; the call does not revert but returns `false`. `dispatch()` sees `success == true` and proceeds without reverting the batch.
4. The overall transaction (order fill / cross-chain mint) completes successfully and is marked done, but `EvilToken` balance intended for `finalRecipient` never moves — it remains held by `CallDispatcher`, with no function available to recover it, resulting in permanently frozen funds for that intended recipient.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
