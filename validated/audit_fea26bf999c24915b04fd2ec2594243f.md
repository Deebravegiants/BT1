## Title
Unsafe raw `token.call` transfer pattern in Tron `IntentGatewayV2.withdraw`/`onAccept` bypasses ERC20 return-value validation, enabling silent transfer failures with escrow already decremented - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` (used for the Tron deployment of Hyperbridge's Intent Gateway) does not use `SafeERC20.safeTransfer` for releasing escrowed funds. Instead it performs a raw low-level `.call` with the `transfer` selector and only checks that the call itself did not revert (`success`), never decoding/validating the returned boolean.

### Finding Description
In `withdraw()`, which is invoked either directly for same-chain escrow releases or via `onGetResponse` for cross-chain refund confirmation, and in the `SweepDust` branch of `onAccept`, token payouts are performed like this: [1](#0-0) 

and [2](#0-1) 

and the `SweepDust` handler in `onAccept`: [3](#0-2) 

Each of these uses `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treats a call that merely didn't revert (`success == true`) as proof of a successful transfer, without decoding the ABI-encoded boolean return value. This is precisely the "unsafe `transfer` instead of `safeTransfer`" bug class from the referenced report: non-standard ERC20 tokens that return `false` on failure (rather than reverting) will make the low-level call succeed with `success = true` even though no tokens moved, since the call only checks for revert, not the encoded return data.

Critically, the accounting is updated unconditionally right after these calls, e.g. in `withdraw`: [4](#0-3) 

`_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set to the beneficiary regardless of whether the underlying `transfer` actually moved funds. Compare this to the mainline EVM `IntentGatewayV2`/`IntentsBase._withdraw`, which correctly uses `SafeERC20.safeTransfer`: [5](#0-4) 

### Impact Explanation
If the escrowed/dust token is a non-standard ERC20 (returns `false` on failed transfer instead of reverting — a well-documented pattern among real-world tokens), a failed release will still be treated as complete: the order is marked filled, the escrow ledger is decremented, and no revert occurs to allow the caller (or Hyperbridge-relayed `RedeemEscrow`/`RefundEscrow`/`SweepDust` message) to retry. The beneficiary permanently loses their entitled funds while the protocol's internal accounting believes the payout succeeded — this is a permanent freezing/loss-of-funds condition, satisfying the Medium+ severity bar for concrete fund loss.

### Likelihood Explanation
This path is reached by ordinary cross-chain intent settlement flows — `RedeemEscrow`/`RefundEscrow` requests processed via `onAccept` after being delivered by Hyperbridge, and `SweepDust` protocol messages — meaning any token configured for the Tron gateway that is non-conformant with the strict ERC20 boolean-return spec will trigger this on the very next payout under adverse token-side conditions (e.g., temporary blacklist, paused state, insufficient balance in the token's own accounting) without requiring any privileged or malicious actor.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the mainline EVM `IntentGatewayV2`/`IntentsBase` implementation, so that both call failure and a `false` boolean return revert the transaction and leave escrow accounting untouched.

### Proof of Concept
1. Deploy/configure the Tron `IntentGatewayV2` with an escrow token that returns `false` (rather than reverting) on a failed `transfer` (e.g., due to an internal pause/blacklist condition at payout time).
2. Have Hyperbridge relay a `RedeemEscrow` (or `RefundEscrow`) message that triggers `onAccept` → `withdraw` for that token/beneficiary, at a moment where the token's internal `transfer` returns `false`.
3. Observe: `token.call(...)` returns `success = true` (the call itself didn't revert), so the `if (!success) revert TransferFailed();` check passes; `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment]` is set — the order is marked resolved even though the beneficiary received zero tokens, permanently freezing the beneficiary's escrowed funds.
