Based on the analysis, I've confirmed the finding: the webhook HMAC in this gem verifies only the raw request body, but the `shop`, `topic`, and `webhook-id` values used to route and identify the tenant are taken from unauthenticated HTTP headers that are never included in the signed bytes.### Title
Webhook `shop`/`topic`/`webhook-id` identity is trusted from unauthenticated headers not covered by the HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then hands the caller a `WebhookMetadata` struct whose `shop`, `topic`, and `webhook_id` fields are read straight from HTTP headers that are never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively over that signable string using the app's `api_secret_key` [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`) with no cryptographic binding to the body or to each other [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before dispatching to the handler with these header-derived, unauthenticated values: [4](#0-3) . The resulting `WebhookMetadata` struct carries `topic`, `shop`, and `webhook_id` as trusted identity fields for the handler [5](#0-4) .

This breaks the intended identity binding: `HMAC(secret, bytes_verified) == HMAC(secret, raw_body)` is checked, but `shop_used_by_handler == shop_that_actually_sent_the_event` is never enforced, because `shop` is not part of `bytes_verified`. Since the `api_secret_key` used to sign webhooks is the same for every shop that installs the app (it is the app's own secret, not a per-shop secret), any two webhook deliveries produced by the same app share the same signing key. An attacker who is a legitimate merchant/tenant of the app can trigger a webhook to their own shop (e.g., place an order), capture the `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to the app's public endpoint, and then replay that exact body/HMAC pair to the same endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers with values belonging to a different tenant. `HmacValidator.validate` will still pass (it only checks the body), and the handler will receive `WebhookMetadata` claiming the event belongs to the victim shop/topic/webhook id.

### Impact Explanation
If a host application uses `data.shop`, `data.topic`, or `data.webhook_id` from `WebhookMetadata` to select which tenant's records to update (a standard pattern, e.g., "look up the shop's session/store by `data.shop` and mutate its data"), this allows a low-privilege attacker (any merchant/tenant who can generate at least one legitimate webhook for their own shop) to inject spoofed, attacker-controlled event data attributed to a shop they do not own — a cross-tenant integrity issue. This matches the Critical "cross-tenant access" impact category, because the vulnerable binding lives entirely in this gem's webhook authentication primitives (`Request`/`HmacValidator`/`Registry.process`), not in host misuse of an undocumented API — the documented `process` flow is exactly what's exploited.

### Likelihood Explanation
Moderate-to-high. It requires the attacker to be able to (a) generate at least one legitimate webhook to their own shop/topic (achievable by any installed merchant performing a normal store action) and (b) replay a POST to the app's public webhook endpoint with attacker-chosen headers, which is standard HTTP client capability once they've captured one legitimate delivery (e.g., via their own request logging, a proxy, or a webhook debugging tool they control). No knowledge of `api_secret_key` is required — only observation of one signed request they were legitimately entitled to receive.

### Recommendation
Bind the HMAC to the identity fields that the handler will trust. At minimum, `HmacValidator.validate` (or a dedicated webhook-specific check) should incorporate `shop`, `topic`, and `webhook_id` header values into the signed content, or `Registry.process` should independently verify that the `shop` header corresponds to a shop with an active, known installation/session for the exact webhook subscription referenced (e.g., look up by `webhook_id` and compare `shop`) before constructing `WebhookMetadata`. Failing that, the docs should explicitly and loudly warn implementers that the HMAC only guarantees body integrity from *some* installation of the app and that `shop`/`topic`/`webhook_id` must be independently cross-checked against the app's own record of active webhook subscriptions before being trusted as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures/observes a webhook to their own endpoint (or intercepts one delivered to the shared multi-tenant handler URL).
2. Attacker triggers an event (e.g., creates an order) causing Shopify to POST a legitimately-signed webhook: headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Webhook-Id: <id>`, `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` and/or `X-Shopify-Webhook-Id` to a value associated with the victim's subscription.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks the (unchanged) body against the (unchanged) HMAC [4](#0-3) .
5. The application's registered `WebhookHandler#handle` receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, `topic: "orders/create"`, and processes the attacker's body as if it were data from the victim shop, corrupting or leaking cross-tenant state depending on the handler's logic.
