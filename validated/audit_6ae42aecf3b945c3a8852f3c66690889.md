### Title
Missing allowlist / rate-limiting on `HandleLegacyUserMessage` allows any unprivileged client to trigger workflow execution on all DON nodes via the Gateway - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway capabilities handler's `HandleLegacyUserMessage` function, which processes `web_api_trigger` requests from external, unauthenticated HTTP clients, contains an explicit `// TODO: apply allowlist and rate-limiting here` comment immediately before it forwards the request to every node in the DON. This mirrors the reported bug class exactly: a setter/dispatch operation that is known to need access control (as evidenced by the developer's own TODO comment) but ships without it.

### Finding Description
`HandleLegacyUserMessage` is reached from the internet-facing gateway's `ProcessRequest` entrypoint (`core/services/gateway/gateway.go:220-295`) for any legacy (DON-ID-based) request whose signature validates (`msg.Validate()` only checks structural fields and recovers a signer address — it does not check that signer against any allowlist). Inside the handler: [1](#0-0) 
only a payload-format check, a non-zero timestamp check, and a staleness check are performed before the code explicitly notes that allowlist and rate-limiting are still missing: [2](#0-1) 
Immediately after, with no sender-identity/allowlist gate at all, the message is fanned out to every node in the DON: [3](#0-2) 

Any party capable of generating an ECDSA keypair (i.e., any unprivileged internet client — no chainlink account, session, or API token needed) can sign a well-formed `web_api_trigger` message and have it dispatched to all DON node capability engines, exactly analogous to the report's pattern of a setter that is known to need access control (per its own TODO) but has none.

### Impact Explanation
This allows an unprivileged actor to trigger workflow executions on every member node of a DON without being an allowlisted workflow owner, sender, or otherwise authorized entity. Depending on what capabilities/workflows are wired to `web_api_trigger`, this can cause unauthorized job/workflow runs, resource exhaustion of DON nodes (since there is no rate limiting for user-originated legacy trigger requests, unlike the node-originated `nodeRateLimiter` used for outgoing messages), and potential downstream effects if triggered workflows perform on-chain actions or move funds. This matches the report's required impact category of "unauthorized job run."

### Likelihood Explanation
Likelihood is high: the entrypoint is directly internet-facing (`gateway.ProcessRequest`), the only "authentication" is a self-generated ECDSA signature (which proves nothing about identity/authorization, just message integrity), and the missing check is explicitly flagged by the maintainers themselves via the TODO comment, confirming the gap is known and unaddressed at the time of this snapshot.

### Recommendation
Implement the allowlist/authorization check indicated by the TODO before dispatching `web_api_trigger` (and any other legacy) messages to DON nodes — verify `msg.Body.Sender` against a workflow-owner or sender allowlist (similar to the `allowListBasedAuth` pattern already used elsewhere in the codebase, e.g. `core/capabilities/vault/allow_list_based_auth.go`), and add per-sender rate limiting analogous to `nodeRateLimiter` but applied to inbound user messages, not just node-originated ones.

### Proof of Concept
1. An attacker with no Chainlink credentials generates an arbitrary ECDSA keypair.
2. They construct a `api.Message` with `Body.Method = "web_api_trigger"`, a valid `DonID`, and a `TriggerRequestPayload` containing a non-zero `Timestamp`, then sign it with their own key (`msg.Sign(privateKey)`).
3. They POST this JSON-RPC-wrapped legacy request to the gateway's HTTP endpoint, which reaches `gateway.ProcessRequest` → `handler.HandleLegacyUserMessage`.
4. `msg.Validate()` succeeds (it only checks structural constraints and recovers a signer, not authorization), the timestamp checks pass, and the method matches `MethodWebAPITrigger`.
5. Because the allowlist/rate-limit TODO is unimplemented, the request is forwarded via `don.SendToNode` to every member node of the target DON, executing the corresponding workflow trigger on the attacker's behalf with no prior authorization.
