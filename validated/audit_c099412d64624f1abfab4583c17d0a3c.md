## Title
Webhook `shop` (and `topic`/`webhook_id`) identifiers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the **raw HTTP body only**, while the shop, topic, and webhook-id used to attribute and dispatch the event are read from **unsigned HTTP headers**. This breaks the intended binding `hmac == HMAC(secret, body) AND body belongs-to shop-header`, allowing an attacker who can obtain any one valid `(body, hmac)` pair for the shared app secret to replay it with an arbitrary `x-shopify-shop-domain` header, causing the receiving app to process/attribute the webhook payload to a different tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies `computed_signature == received_signature`, where `computed_signature` is computed from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — never the shop, topic, or webhook id: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only this body HMAC and then constructs `WebhookMetadata` directly from the unauthenticated `shop`, `topic`, and `webhook_id` headers, handing them to the app's handler as trusted tenant/event identity: [3](#0-2) 

Because `Context.api_secret_key` is a single, app-wide secret shared across **every** shop that installs the app (it is not per-shop), the HMAC only proves "this body was signed by our app's secret" — it proves nothing about which shop, topic, or webhook id it is associated with. This is the identity-binding gap: `hmac verifies body` ≠ `hmac verifies (body, shop, topic)`. Just as the reported hard-fork bug fixes an identity value (`chainId`) at signing time and never re-derives it from the current authoritative source, here the "identity" (shop/topic) is never included in what's authenticated, and the header value is trusted unconditionally at dispatch time.

### Impact Explanation
An unprivileged internet user who can install the target app on their own (attacker-controlled) development store can trigger a legitimate webhook delivery for a body of their choosing (e.g., an `orders/create` or `app/uninstalled` payload with attacker-controlled field values), capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared secret. They can then replay that exact body and HMAC directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` dispatches the payload to the app's handler tagged as belonging to the victim shop. Depending on the handler logic (e.g., data sync, uninstall handling, GDPR/mandatory webhooks), this can corrupt or exfiltrate cross-tenant state, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Requires only: (1) ability to install/operate the target app on any shop (a normal unprivileged merchant action, not requiring the app's credentials), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — both trivially available to any internet user. No `api_secret_key`, access token, or privileged access is needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated material, e.g., include the `x-shopify-shop-domain` (and topic) header values in the HMAC signable string, or independently verify that the shop derived from the payload matches an out-of-band trusted association (e.g., a per-shop webhook secret, or cross-checking against a stored session/shop record) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, causing Shopify to deliver a webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(app_secret, B)`.
2. Attacker crafts a raw POST to the app's webhook endpoint reusing body `B` and header `H` unmodified, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `@raw_body` (`to_signable_string`) — see `lib/shopify_api/webhooks/request.rb#L35-L38` and `lib/shopify_api/utils/hmac_validator.rb#L27-L31`.
4. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` (= `"victim-shop.myshopify.com"`, an unverified header) and invokes the app's handler, which now processes attacker-supplied data under the victim shop's identity.
