## Analysis

The reported bug class — a `withdraw()` that decrements internal accounting before confirming the actual token balance is sufficient, causing withdrawals to revert (or funds to become unreachable) once the backing balance has been drawn down elsewhere — has a direct analog in Hyperbridge's relayer-fee withdrawal path.

### Title
Relayer fee ledger is zeroed before destination-chain settlement is confirmed, so withdrawals against a depleted `EvmHost` fee-token balance permanently strand the relayer's reward - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-relayer`'s `withdraw()` reads the relayer's accrued balance from local storage (`Fees<T>`), dispatches an asynchronous ISMP POST request instructing the destination chain's `HostManager`/`EvmHost` to pay out `available_amount` of the fee token, and then **immediately zeroes** the relayer's `Fees` entry — before the destination-side transfer has actually executed or been confirmed. The funds that back this payout are the `EvmHost` contract's own pooled `feeToken` balance on the destination chain, which is shared across every relayer's accumulated claims and is also drained by governance's own `IHostManager.withdraw()` (protocol revenue). If that shared balance is insufficient when the request lands, `EvmHost.withdraw()` reverts (`SafeERC20` transfer failure, exactly reproduced in `evm/tests/rust/src/tests/host_manager.rs::test_host_manager_insufficient_balance`), yet the relayer's Hyperbridge-side `Fees` ledger has already been reset to zero.

### Finding Description
`Pallet::<T>::withdraw` in [1](#0-0)  performs, in order:
1. Reads `available_amount = Fees::<T>::get(dest_chain, address)`.
2. Builds a `WithdrawalParams { amount: available_amount, token: params.fee_token, .. }` body and dispatches a POST request to the destination's `HostManager` via `dispatcher.dispatch_request(...)`.
3. Immediately after the *dispatch* call succeeds (which only means the request commitment was recorded on Hyperbridge, not that it was delivered or executed), it unconditionally zeroes the ledger: `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());`.

On the EVM destination, `EvmHost.withdraw()` [2](#0-1)  simply transfers `params.amount` of `params.token` out of the host's own balance via `SafeERC20.safeTransfer`, with no reserve/shortfall handling. This same balance is the pool that:
- backs **every relayer's** accumulated `Fees` claims for that chain, and
- is independently drained by governance's own protocol-revenue withdrawal through the identical `IHostManager.withdraw()` entrypoint (`restrict(_hostParams.hostManager)`).

The confirmed failure mode is exercised in `test_host_manager_insufficient_balance` [3](#0-2) , which shows the transfer reverting outright when the host's fee-token balance can't cover the requested amount — structurally identical to `USDMPegRecovery.withdraw()` reverting when the contract's own balance had been moved into the curve pool via `provide()`.

### Impact Explanation
Because `Fees<T>` is zeroed at dispatch time rather than at confirmed settlement time, a relayer whose withdrawal request fails to execute on the destination (due to the shared `EvmHost` fee-token balance being insufficient at execution time — whether from concurrent relayer withdrawals or a governance protocol-revenue sweep) has no on-chain accounting left to prove or re-claim the reward. The relayer's dispatched request can, in principle, be redelivered later (the POST has `timeout: 0`), but there is no guarantee the balance ever recovers before some other consumer of the same pool drains it again, and no retry/backstop path exists analogous to the report's recommended "pull from the pool when short." This is a decentralization/incentive risk: relayers — an explicitly permissionless, unprivileged role — can have already-earned rewards effectively frozen or lost, undermining the fee-accounting guarantees the module exists to provide.

### Likelihood Explanation
The `EvmHost` fee-token balance is a shared pool funded incrementally by dispatch fees and drained by an unbounded set of relayer withdrawals plus governance's own revenue withdrawal, with no reservation or accounting split between "owed to relayers" vs. "protocol revenue." Any chain with multiple active relayers or a governance sweep timed close to relayer withdrawals can trigger this: the `withdraw_fees` extrinsic is unsigned and callable by any relayer holding a valid signature, so the surface is fully permissionless and reachable via a single extrinsic — no privileged actor needed to trigger the race.

### Recommendation
Do not zero `Fees<T>` until destination-side settlement is confirmed (e.g., via a receipt/ack callback path, or by deferring the ledger decrement to the point the withdrawal request's delivery is proven), or alternatively have `EvmHost.withdraw()` cap the transfer to the available balance and emit a partial-withdrawal event, with the pallet reconciling the ledger to the actual amount disbursed rather than assuming full settlement.

### Proof of Concept
1. Multiple relayers accumulate `Fees` claims against `StateMachine::Evm(1)` whose `EvmHost` fee-token balance is `X`, with total claims potentially ≥ `X` (no on-chain invariant prevents this since `accumulate_fees` never checks the destination's live balance).
2. Relayer A calls `withdraw_fees`; `Fees<T>` for A is zeroed and a `WithdrawalParams` POST is dispatched to `HostManager`.
3. Before A's request is delivered, governance calls `IHostManager.withdraw()` (protocol revenue) or relayer B's earlier withdrawal is delivered first, draining `EvmHost`'s fee-token balance below A's `amount`.
4. A's request is delivered and `EvmHost.withdraw()` reverts per `test_host_manager_insufficient_balance` [3](#0-2) .
5. A's `Fees` entry is already `0` on Hyperbridge; A has no accounting record left to retry or reclaim the reward, matching the reported class of "withdraw takes funds from a balance that has been depleted elsewhere and reverts, stranding the claimant."

	pub fn withdraw(withdrawal_data: WithdrawalInputData) -> DispatchResult {
		let address = match &withdrawal_data.signature {
			Signature::Evm { address, .. } => address.clone(),
			Signature::Sr25519 { public_key, .. } => public_key.clone(),
			Signature::Ed25519 { public_key, .. } => public_key.clone(),
		};

		let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
		let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());

		match &withdrawal_data.signature {
			Signature::Evm { address, .. } => {
				let eth_address = withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
				if &eth_address != address {
					Err(Error::<T>::InvalidPublicKey)?
				}
			},
			Signature::Sr25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
			Signature::Ed25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
		};
		let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());

		if available_amount <
			Self::min_withdrawal_amount(withdrawal_data.dest_chain)
				.unwrap_or(MinWithdrawal::get())
		{
			Err(Error::<T>::NotEnoughBalance)?
		}

		let dispatcher = <T as Config>::IsmpHost::default();

		Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| {
			*value += 1;
			Ok::<(), ()>(())
		})
		.map_err(|_| Error::<T>::ErrorCompletingCall)?;

		let beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone());
		let (to, body) = match withdrawal_data.dest_chain {
			s if s.is_substrate() => (
				HYPERBRIDGE_MODULE_ID.to_vec(),
				Message::WithdrawRelayerFees(WithdrawalRequest {
					amount: available_amount.low_u128(),
					account: AccountId32::try_from(&beneficiary_address[..])
						.map_err(|_| Error::<T>::InvalidPublicKey)?,
				})
				.encode(),
			),
			_ => {
				let HostParam::EvmHostParam(params) =
					HostParams::<T>::get(withdrawal_data.dest_chain)
						.ok_or_else(|| Error::<T>::MissingMangerAddress)?;

				let body = WithdrawalParams {
					beneficiary_address: beneficiary_address.clone(),
					amount: available_amount.into(),
					token: params.fee_token,
				}
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidPublicKey)?;

				(params.host_manager.0.to_vec(), body)
			},
		};

		let post = DispatchPost {
			dest: withdrawal_data.dest_chain,
			from: MODULE_ID.to_vec(),
			to,
			body,
			timeout: 0,
		};

		// Account is not useful in this case
		dispatcher
			.dispatch_request(
				DispatchRequest::Post(post),
				FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
			)
			.map_err(|_| Error::<T>::DispatchFailed)?;

		Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());

		Self::deposit_event(Event::<T>::Withdraw {
			address: sp_runtime::BoundedVec::truncate_from(address.clone()),
			beneficiary_address: sp_runtime::BoundedVec::truncate_from(beneficiary_address),
			state_machine: withdrawal_data.dest_chain,
			amount: available_amount,
		});

		Ok(())
	}

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

#[test]
fn test_host_manager_insufficient_balance() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Host has no fee tokens; withdraw attempt should fail on SafeERC20 transfer
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");
	assert!(!err.is_empty(), "expected non-empty revert data");
}
