This confirms the finding. The docs explicitly promise: `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md` line 125), and `WebhookMetadata#shop` is documented as trustworthy tenant identity ("The shop domain of the webhook", `docs/usage/webhooks.md` line 14). But the HMAC only covers the raw body, not the `shop-domain` header, so `process` authenticates the *payload* while trusting an out-of-band, unauthenticated `shop` value for tenant identity.

### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` struct whose `shop` field app authors are told identifies "the shop domain of the webhook." In reality, the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body — the `shop-domain` header used to populate `WebhookMetadata#shop` is never part of the signed material. Because the same `api_secret_key` is shared by the app across every merchant/shop that installs it, any shop that has the app installed (an "unprivileged" tenant relative to other merchants) can capture a legitimate, validly-signed webhook body+HMAC pair from their own store and replay it to the app's webhook endpoint with the `shop-domain` (or `X-Shopify-Shop-Domain`) header swapped to a victim shop. `HmacValidator.validate` will still accept it because it only checks the body against the shared secret, and `Registry.process` will happily dispatch the forged event to the handler as if it came from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from an unauthenticated header with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates only on this body HMAC, then forwards the caller-supplied `request.shop` directly into `WebhookMetadata`, which the handler uses as the authoritative tenant identifier: [4](#0-3) [5](#0-4) 

This breaks the identity binding: **shop authenticated (via HMAC) ≠ shop used as the tenant key** by the handler. The signature proves "this body was produced with knowledge of `api_secret_key`," not "this body originated from shop X." Since `api_secret_key` is one value shared by the app across all installing shops (it is not per-shop), any merchant who legitimately receives real webhooks from Shopify for their own store can capture a `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with an arbitrary `shop-domain` header, forging an apparently-authentic event for any other tenant.

This is the same class of bug as the report's `RekeyTo` finding: a value that is *acted upon* by downstream logic (there: the vault's rekey state; here: the tenant/shop identity) is not covered by the cryptographic check that is supposed to make the whole operation trustworthy (there: no `RekeyTo` check on the transaction; here: no `shop` binding in the HMAC).

### Impact Explanation
This qualifies as **cross-tenant access**: an attacker with a legitimate, unprivileged install of the app can inject fabricated webhook events (e.g., `orders/create`, `app/uninstalled`, `shop/redact`, `customers/data_request`) that the host application will attribute to any other merchant's shop domain, because `Registry.process` and `WebhookMetadata.shop` provide no proof that the body actually originated from that shop. Depending on what the host app does with `data.shop` (e.g., look up/update per-tenant records, trigger data deletion for GDPR topics, mark a shop as uninstalled), this can lead to cross-tenant data corruption, spoofed compliance actions, or state confusion between tenants — consequences the gem's own documentation ("will verify the request did indeed come from Shopify") explicitly promises will not happen.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs the app installed on at least one shop they control (a low bar for public apps) to obtain a valid `(body, hmac)` sample, and needs to know or guess the victim's target endpoint and shop domain (`myshopify.com` domains are enumerable/guessable, and many are public). No access token, `client_secret`, or privileged credential is required — only observation of the attacker's own legitimately-received webhook traffic and replay with a modified header, which is fully achievable by an unprivileged internet user/merchant.

### Recommendation
**Short term:** Do not treat the `shop-domain` header as trusted tenant identity on its own. At minimum, document/require that host apps cross-check `data.shop` against a shop for which a webhook of that `topic`/`webhook_id` was actually registered, and de-duplicate/track `webhook_id` per expected shop.

**Long term:** Extend `VerifiableQuery`/`HmacValidator` (or add a dedicated webhook verification path) so that the shop domain (and ideally topic and webhook id) are part of the signed/verified material, or provide an API that lets host apps supply the expected shop and have the library assert equality before dispatching to the handler — mirroring the audit's long-term recommendation to not let unauthenticated data drive privileged actions.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends the same `B`/`H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and adjusts `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as desired for the target topic).
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers))`.
4. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` — this matches `H` regardless of the `shop-domain` header, since `to_signable_string` never includes it (`lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to act on data it believes came from `victim-shop.myshopify.com`, though it was actually forged by the attacker.
