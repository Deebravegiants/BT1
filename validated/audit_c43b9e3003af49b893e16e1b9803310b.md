## Title
Webhook shop-domain spoofing via HMAC that only covers the request body, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook signature verification only binds the HMAC to the raw request body, never to the `shop`/`shop-domain` header that the library (and any app built on it) treats as the authenticated tenant identity. Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, a valid `(body, hmac)` pair obtained from one shop's webhook can be replayed against the same endpoint with the `x-shopify-shop-domain` header rewritten to a different (victim) shop, and it will still pass verification. This breaks the identity equality `shop claimed in header == shop bound by HMAC`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) [2](#0-1) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac-sha256` header: [4](#0-3) 

`Webhooks::Registry.process` relies solely on this HMAC check before dispatching the webhook to the app's handler, passing `request.shop` (the unauthenticated header value) straight into `WebhookMetadata`: [5](#0-4) 

Because `Context.api_secret_key` is the single shared secret for the whole app across all installed shops (as also seen in `HmacValidator.validate` and its use for OAuth callbacks), any actor who can obtain one valid `(raw_body, hmac)` pair — e.g., from their own shop's legitimate webhook traffic, since they control what events they trigger and can observe the delivered payload/signature — can resend that exact body+signature to the app's webhook endpoint while substituting a different shop's domain in the `x-shopify-shop-domain` header. The signature check in `HmacValidator.validate` still succeeds because the header is never part of `to_signable_string`, so `Registry.process` invokes the handler believing the event legitimately originates from the victim shop.

### Impact Explanation
This is a cross-tenant identity break: the gem gives applications no cryptographic assurance that the `shop` value delivered to their webhook handler is the shop that actually produced the signed body. An attacker-controlled shop domain header combined with attacker-controlled (though HMAC-valid) body content lets an attacker inject events attributed to an arbitrary victim shop into the host application's webhook processing pipeline — for example, triggering `app/uninstalled`, order, or customer-data-related handlers for a shop the attacker doesn't own, potentially causing state corruption, unauthorized data writes, or logic bound to per-shop trust (e.g. deprovisioning, billing, GDPR data handlers) to run against the wrong tenant. This matches the Critical "cross-tenant access" impact category, since the library, not just an app misuse, fails to bind the two together at the HMAC layer.

### Likelihood Explanation
Exploitation requires only capturing one legitimate `(body, hmac)` pair — trivial for anyone who runs their own installation of the app (a normal, unprivileged merchant/attacker capability) and observes the webhook they receive/trigger — plus rewriting one header when re-POSTing to the public webhook endpoint. No access to `api_secret_key`, tokens, or TLS interception is required. The only constraint is that the forged event's body content is whatever the attacker's own shop produced (attacker doesn't get free-form body forgery), but many high-value webhook topics (e.g., `app/uninstalled`, or topics with attacker-influenceable fields such as customer or order webhooks the attacker can shape via their own store's data) make this practically exploitable.

### Recommendation
Bind the shop identity into the verified material: either include the `shop-domain` (and ideally `topic`, `webhook-id`) in the signable string used for HMAC computation, or require applications to cross-check `request.shop` against a shop the app has an active, previously-established session/installation for before trusting it, and document this gap clearly if the header truly cannot be covered by Shopify's HMAC scheme. At minimum, the library should surface a documented warning that `request.shop` is not authenticated by `HmacValidator.validate` and must be revalidated by the host app against its own session/shop registry before use.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`. Attacker triggers/observes a legitimate webhook delivery to their app endpoint: headers include `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some JSON body `B`.
2. Attacker resends the exact same body `B` and `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `request.to_signable_string` (`@raw_body`, unchanged) and matches the supplied HMAC — validation succeeds. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though the body and signature never originated from that shop.
