### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (tenant identifier) is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only and then dispatches the handler using the unauthenticated `shop` value, letting an attacker rebind a legitimately signed payload to an arbitrary victim shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` only: [2](#0-1) 

`shop` is pulled from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is completely independent of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which uses `to_signable_string`, i.e., body only) and then constructs `WebhookMetadata` using the unauthenticated `request.shop`: [4](#0-3) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`: [5](#0-4) 

The binding the code implicitly assumes is:
`hmac_valid(body, secret) == true` implies `shop_header == the_shop_that_secret_was_issued_for`

but the actual check only proves:
`hmac_valid(body, secret) == true`

with no cryptographic tie between `body` and `shop`. Since the app's `client_secret` (and therefore the HMAC key) is shared across every shop that has installed the app, any (body, hmac) pair that was legitimately produced by Shopify for one installation remains "valid" when replayed with a different `shopify-shop-domain` header value.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically verified content and the shop the handler believes it is operating on, an unprivileged-internet-user analog to the report's "field acted on but not covered by the HMAC" pattern. A user who has installed the app on their own shop can capture one genuine webhook delivery (body + valid HMAC, signed with the app's shared secret) and replay it to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header. `Registry.process` will accept the request (HMAC check passes because it only checks the body) and invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain. Any host application logic that uses this `shop` value to select tenant state, look up sessions, or attribute data will act on the victim tenant using attacker-supplied/attacker-timed content — a cross-tenant access condition.

### Likelihood Explanation
Likelihood is realistic for any multi-tenant app built on this gem: the attacker only needs to be a legitimate, unprivileged user of the app on any one shop (to obtain one valid signed payload) and network-level ability to POST to the app's public webhook endpoint with custom headers — no access token, `api_secret_key`, or privileged account is required.

### Recommendation
Bind the tenant identity into the signed material used for verification, e.g., include `shop` (and other trust-relevant headers like `topic`/`webhook_id`) in `to_signable_string`/the value handed to `HmacValidator`, or require the host application to independently verify that `request.shop` corresponds to a shop with an active session/install before trusting it, and document this requirement clearly in `docs/usage/webhooks.md`. At minimum, `Registry.process` should not treat `request.shop` as authenticated data derived from the HMAC check alone.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/captures one genuine webhook delivery, e.g. `orders/create`, capturing the raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(client_secret, B)`).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-topic: orders/create` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(client_secret, B)` and finds it equal to `H` — validation passes.
4. The handler is invoked via `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed_body, ...))`, causing the app to process attacker-controlled order data as if it originated from `victim.myshopify.com`.
