### Title
`object::delete` Can Permanently Strand Fungible-Asset Custody by Removing `ObjectCore` Without Checking for a Live `FungibleStore` Balance - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::delete` (the generic object-deletion entry point tied to `DeleteRef`) only removes `ObjectCore` (and `Untransferable`, if present). It never checks whether the same address also holds a `FungibleStore` (or other value-bearing resource) with a non-zero balance. The framework's own, safe deletion path for fungible stores — `fungible_asset::remove_store` — does enforce `balance == 0` before allowing deletion, but that check lives only in `fungible_asset.move`, not in `object::delete` itself. Any code path that calls the generic `object::delete` on an object address that still has an active `FungibleStore` will silently orphan the store and its balance. [1](#0-0)

### Finding Description
`DeleteRef` is a generic, type-erased capability — `object::generate_delete_ref` hands it out at object-construction time without any knowledge of what resources will later be `move_to`'d onto that object address (e.g. `FungibleStore` via `fungible_asset::create_store`). The intended safe teardown for an object holding fungible assets is `fungible_asset::remove_store(delete_ref)`, which explicitly asserts `balance == 0` (and the `ConcurrentFungibleBalance` aggregator is also zero) before consuming the `DeleteRef` and destroying `ObjectCore`.

However, `object::delete` is a separate, `public` function that takes the exact same `DeleteRef` type and unconditionally removes only `ObjectCore` (plus `Untransferable`), with **no assertion that `FungibleStore` doesn't exist or is empty**: [1](#0-0) 

Because `DeleteRef` carries no type/resource information, any module or code path holding a `DeleteRef` for an object that also has a live `FungibleStore` can call `object::delete()` instead of `fungible_asset::remove_store()` — bypassing the balance check entirely. After this call:
- `ObjectCore` is gone, so `exists_at`, `object::owns`, `object::owner`, and `is_owner` all treat the address as if the object never existed (`EOBJECT_DOES_NOT_EXIST`).
- The `FungibleStore` resource (and its balance field) remains in global storage, unreachable by any framework API, because every fungible-asset entry point (`withdraw`, `deposit`, `transfer`, `balance`, `primary_fungible_store::*`) gates access through `object::owns`/`ObjectCore`-based checks.
- No `TransferRef`/`BurnRef`/`MintRef` operation can recover the balance because they too resolve through the (now-deleted) `ObjectCore` ownership model.

This is a broken custody invariant: "object deletion must preserve the intended controller's ability to recover object-held value" is violated because a single generic capability (`DeleteRef`) can be used to bypass the value-specific safety check that exists in a sibling module (`fungible_asset::remove_store`). The root cause is structural — the safety invariant ("don't delete an object that still holds value") is enforced in only one of two possible deletion entry points for the same `DeleteRef` type, and `object.move` has no way to know at deletion time that a `FungibleStore` (or any other future value-bearing extension) exists at that address.

This is directly analogous to the external bug's custody invariant: a generic, unguarded operation (`swap()`'s `msg.value` forwarding / here, `object::delete`'s blanket resource removal) fails to account for value that a more specific, "aware" code path (input-token transfer check / `remove_store`'s balance assertion) would have protected, resulting in value becoming permanently unreachable.

### Impact Explanation
Any FA balance (APT via its paired FA, custom coins on primary or secondary stores, marketplace escrow objects, pool-held liquidity, etc.) held in a `FungibleStore` at an address whose `DeleteRef` is deleted via `object::delete` instead of `fungible_asset::remove_store` becomes **permanently and non-recoverably locked**. This meets the custody impact gate's "Permanent lock or non-recoverable loss of object-held value" and "Supply or custody accounting corruption that ... destroys recovery rights" categories at Critical severity, since:
- There is no admin/governance backdoor to reattach an `ObjectCore` to an address.
- The lost value still counts in the fungible asset's global `Supply`, permanently reducing the economically recoverable circulating balance versus the tracked supply — a supply/custody accounting mismatch.
- The pattern is realistic: many modules in this very repo (e.g. `collection_offer.move`, marketplace escrow contracts) store a raw `DeleteRef` alongside a `Coin`/`FungibleAsset`-holding object precisely so they can tear the object down later; a coding mistake, a compromised/malicious extension of such a module, or an upgrade that swaps `remove_store` for the generic `delete` (an easy, plausible refactor since both take a `DeleteRef` and look interchangeable) silently converts "clean up an empty object" into "brick the object and its funds."

### Likelihood Explanation
The likelihood hinges on a `DeleteRef` for a `FungibleStore`-bearing object being routed to `object::delete` instead of `fungible_asset::remove_store`. Both functions are `public`, take the identical `DeleteRef` type, and neither the type system nor the module boundary prevents this — a developer error, an unaudited third-party module extending an object, or a future framework/first-party module refactor (there is no compiler warning steering the caller to the FA-safe teardown) can trigger it. Given that the codebase already has patterns of storing `DeleteRef` inside structs together with value-bearing resources (e.g. `collection_offer::CollectionOffer.delete_ref`), the precondition for triggering this — "hold a DeleteRef and also have a nonzero-balance FungibleStore at that address" — is a normal, not contrived, state. I could not find any compensating check elsewhere in the indexed code (`object.move`, `object.spec.move`) that prevents `delete` from being called while a `FungibleStore` exists.

### Recommendation
Add a defense-in-depth check in `object::delete` (or a `friend`-gated internal function shared by both deletion paths) that aborts if a `FungibleStore` (or, more generally, other registered value-bearing resource types) exists at the address, mirroring the assertion already present in `fungible_asset::remove_store`:

```move
public fun delete(self: DeleteRef) {
    assert!(
        !fungible_asset::store_exists(self.self),
        error::permission_denied(ECANNOT_DELETE_NONEMPTY_STORE)
    );
    let object_core = move_from<ObjectCore>(self.self);
    ...
}
```

Since `object.move` cannot depend on `fungible_asset.move` (circular dependency), an alternative is to expose a `friend`-only registration mechanism where modules that create value-bearing resources on objects (like `fungible_asset::create_store`) register a "has value" flag/resource that `object::delete` checks generically, or to make `DeleteRef` non-consumable by `object::delete` once a `FungibleStore` has been attached (e.g., via a marker resource set by `create_store` and cleared only by `remove_store`).

### Proof of Concept
```move
// 1. Attacker/careless module creates an object and a fungible store on it.
let constructor_ref = object::create_object(signer::address_of(user));
let store = fungible_asset::create_store(&constructor_ref, metadata);
let delete_ref = object::generate_delete_ref(&constructor_ref);

// 2. Fund the store (e.g., via a normal deposit/transfer).
primary_fungible_store::transfer(user, metadata, store.object_address(), 1000);
// balance(store) == 1000

// 3. Instead of the safe teardown:
//        fungible_asset::remove_store(&delete_ref); // would abort: EBALANCE_IS_NOT_ZERO
// the code calls the generic, unchecked teardown:
object::delete(delete_ref);

// 4. Result: ObjectCore is gone.
// object::owns(store, user) now aborts with EOBJECT_DOES_NOT_EXIST.
// fungible_asset::withdraw/transfer/balance on `store` are unreachable
// because they all route through object::owns/ObjectCore.
// The FungibleStore resource with balance == 1000 remains in global
// storage at `store.object_address()`, permanently unrecoverable.
```
