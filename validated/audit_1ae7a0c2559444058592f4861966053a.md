### Title
Unhandled decimal-scaling direction in `pallet-hyper-fungible-token`'s ERC20⇄local conversion causes silent under-crediting or unbacked over-minting of bridged tokens - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` in `modules/pallets/hyper-fungible-token/src/impls.rs` assume `erc_decimals >= local_decimals` in one direction and `local_decimals` never exceeds `erc_decimals` in the other, using `saturating_sub` to compute the scaling exponent. When the assumption is violated (local asset decimals higher than the paired EVM token's decimals), the scaling factor silently collapses to `10^0 = 1`, so no compensating scale is applied. This is the same bug class as the double-normalization defect described in the external report: a value crossing a decimal-precision boundary is transformed with an incorrect (here, missing) scaling factor rather than the correct one, producing amounts that do not represent the real transferred value.

### Finding Description
The pallet stores per-`(asset, chain)` EVM decimals in `Precisions` and mixes them with the local asset's own decimals (`T::Decimals` for the native asset, or `fungibles::metadata::Inspect::decimals` for others) to convert amounts crossing the ISMP boundary: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions use `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent:
- `convert_to_erc20` (used on `send`, before dispatching the outgoing message) *multiplies* by `10^(erc_decimals - local_decimals)`. This is only correct when `erc_decimals >= local_decimals`. If the local asset's decimals exceed the destination EVM token's decimals, `saturating_sub` returns `0`, so the raw local balance (already in high-precision units) is emitted verbatim as the ERC20 `amount` field with **no down-scaling** — inflating the value that the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint/unlock by `10^(local_decimals - erc_decimals)`.
- `convert_to_balance` (used on `on_accept`, when receiving from the EVM side) *divides* by the same exponent. In the same decimals configuration (`erc_decimals < local_decimals`), the exponent again collapses to `0`, so the incoming raw ERC20 amount is credited **without scaling up** to local precision — crediting the beneficiary far less than the equivalent value actually represented by the message, silently destroying most of the transferred value.

These are the mint/transfer-crediting path in `on_accept` (a pallet-ismp `IsmpModule` handler invoked by any relayed proof/message delivered through `pallet-ismp`) and the refund path in `on_timeout`.

### Impact Explanation
This defect sits directly in the token-bridge mint/burn path reachable from a single relayed ISMP message: `on_accept` mints (non-native asset) or releases escrow (native asset) using the miscalculated `amount`, and the `send` extrinsic burns/escrows the local balance while emitting a miscalculated ERC20 `amount` for the counterpart chain to mint/unlock.
- If `local_decimals > erc_decimals` for a registered pair, `send()` on the substrate side would cause the EVM contract to mint/unlock an amount inflated by `10^(local_decimals - erc_decimals)` relative to what was actually escrowed/burned — an unbacked mint on the destination chain, i.e., theft of protocol funds / arbitrary value creation.
- Symmetrically, `on_accept()` on the substrate side under the same configuration would credit the beneficiary with an amount deflated by the same factor, i.e., permanent value loss/freezing of the user's bridged funds (their tokens were burned/locked on the EVM chain but they receive a negligible fraction on the substrate chain).

This is not a peer/governance-corruption scenario — `register_token`/`update_token` are permissioned to set up a *legitimate* pair (e.g., an asset minted at 18 decimals locally bridged against a 6-decimal ERC20 stablecoin on the EVM side, a very ordinary configuration for stablecoins like USDC/USDT). No malicious admin action is required; a routine, correctly-intentioned registration with this decimal relationship is enough to trigger unbacked minting or fund loss on every subsequent transfer.

### Likelihood Explanation
The trigger condition — a registered asset whose local (substrate) decimals exceed the destination chain's ERC20 decimals — is a common real-world configuration (e.g., 18-decimal substrate assets paired with 6-decimal ERC20 stablecoins), not an edge case requiring adversarial setup. Every `send`/`on_accept`/`on_timeout` operation on such a pair is affected deterministically, with no additional preconditions beyond normal token registration and a normal cross-chain transfer.

### Recommendation
Replace the one-directional `saturating_sub` scaling in both `convert_to_balance` and `convert_to_erc20` with logic that handles both scaling directions explicitly (multiply when the target has more decimals, divide when it has fewer), analogous to the fix applied for the reported double-normalization bug — i.e., compute the actual signed decimal delta and scale accordingly instead of assuming a fixed ordering, and add explicit tests covering `local_decimals > erc_decimals` for both `send`/`convert_to_erc20` and `on_accept`/`on_timeout`/`convert_to_balance`.

### Proof of Concept
Given a registered non-native asset with `local_decimals = 18` and `Precisions::<T>::get(asset, dest) = erc_decimals = 6` (a realistic pairing, e.g. local 18-decimal representation of a 6-decimal ERC20 stable):

1. User calls `send(asset_id, destination, amount = 1_000 * 10^18)` (1000 tokens, local precision).
2. Pallet burns `1000 * 10^18` of the local asset.
3. `convert_to_erc20(1000 * 10^18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so the emitted ERC20 `amount` field is `1000 * 10^18` unchanged — instead of the correct `1000 * 10^6`.
4. The destination `HyperFungibleToken` contract (configured for 6-decimal precision) mints/unlocks `1000 * 10^18` raw units, `10^12`x more than the `1000` tokens actually burned — an unbacked mint of the destination-chain representation, confirmed by the exact code path at `modules/pallets/hyper-fungible-token/src/impls.rs:57-59` feeding `modules/pallets/hyper-fungible-token/src/module.rs` (`send`) and consumed on `on_accept` symmetrically deflating value in the reverse direction.
