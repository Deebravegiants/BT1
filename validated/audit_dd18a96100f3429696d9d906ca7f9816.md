Confirmed: the webhook HMAC only signs `@raw_body` [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are pulled unauthenticated straight from HTTP headers [2](#0-1)  and then dispatched to the handler as trusted tenant/topic identity in `Registry.process`.

### Title
Webhook `shop` and `topic` headers are not covered by the HMAC, enabling cross-tenant webhook spoofing via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `HmacValidator.validate` cryptographically authenticates the payload bytes but not the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers. Those headers, however, are exactly what `Registry.process` uses to select the handler and to build the `shop`/`topic` identity passed to the host app's business logic.

### Finding Description
`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it with the value from `verifiable_query.hmac`: [3](#0-2) 

For webhook requests, `to_signable_string` is only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are covered by that signature: [2](#0-1) 

`Registry.process` then trusts these unauthenticated header-derived values to select a handler and to build the identity object passed to the app's business logic: [4](#0-3) 

Because Shopify signs only the body bytes with HMAC-SHA256 using the shared `client_secret` — the same secret used for every shop/topic combination on a given app — any legitimate webhook payload+HMAC pair a shop received (e.g., an `orders/create` webhook delivered to the attacker's own installed shop, whose body is largely attacker-controlled through the order they place) remains a **valid** `(raw_body, hmac)` pair for *any* header combination, since the headers play no role in the signature. An unprivileged shop owner who is a legitimate but low-trust tenant of the app can therefore:
1. Capture a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to their own shop.
2. Replay that exact body and HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain and/or `X-Shopify-Topic` with a different registered topic.
3. `HmacValidator.validate` still returns `true` because the signed bytes (`raw_body`) are unchanged, and `Registry.process` dispatches the (attacker-chosen) `shop`/`topic`/`webhook_id` to the app's handler as if Shopify had certified them.

This breaks the intended binding: `hmac-verified bytes == (shop, topic) attributed to those bytes`. In reality, only `hmac-verified bytes == raw_body` holds; `shop`/`topic` are asserted by the untrusted network client.

### Impact Explanation
This crosses a tenant boundary: the host application's webhook handler receives `WebhookMetadata` (topic/shop/body/webhook_id) that it reasonably treats as Shopify-certified for that specific shop and topic, per this library's stated guarantee ("verify the request did indeed come from Shopify"). An attacker-controlled shop can forge webhook deliveries that are attributed to a different, victim shop, or can relabel one topic's payload as another topic, causing the app to execute tenant-scoped business logic (data writes, notifications, state transitions, access-token-scoped API calls performed by the handler) against the wrong tenant. This matches the "cross-tenant access" Critical impact category, since the gem's own header-vs-signed-bytes mismatch is the root cause, not a host-application misuse of a documented contract.

### Likelihood Explanation
Any shop that installs the app (a normal, unprivileged, self-service action available to any internet user via the Shopify App Store or a public/dev install link) automatically receives real webhook deliveries with valid HMACs for their own shop domain. Capturing one such payload requires no special access — merely running the app on one's own store and observing an inbound webhook. Replaying it with modified headers against the same public webhook endpoint requires only a basic HTTP client.

### Recommendation
Include the security-critical headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signed material that `HmacValidator` checks, or otherwise cryptographically bind them to the raw body (e.g., have `Webhooks::Request#to_signable_string` return a canonical concatenation of the raw body with the header values) so a valid signature can only be produced/replayed for the exact header/body combination Shopify actually sent.

### Proof of Concept
1. Legitimate shop `attacker.myshopify.com` installs the app; the app registers an `orders/create` webhook.
2. Attacker places an order in their own shop with body content they control, and Shopify delivers a webhook with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - raw body `B`
3. Attacker replays the exact same `B` and `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — validation passes.
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`, and the host app executes order-processing logic attributing `attacker`'s order body to `victim`'s shop.
