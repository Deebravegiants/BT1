### Title
Cross-chain token transfer amount silently rounds down to zero for small transfers, permanently locking source-chain escrow with no destination-chain credit - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance`, used by `pallet-hyper-fungible-token`'s ISMP `on_accept` and `on_timeout` handlers, converts an incoming ERC20-denominated `U256` amount to the local balance type by integer division. Because `erc_decimals` is always configured `>= local_decimals` (enforced at `register_token`/`update_token`), any relayed message whose ERC20 amount is smaller than `10^(erc_decimals - local_decimals)` truncates to `0`, exactly mirroring the reported "mint amount rounding down to 0 for cheap token" bug class (division-before-scaling truncation), but here it can permanently strand funds rather than just cause an unfair mint.

### Finding Description
`convert_to_balance` divides first and then converts to string/parses, with no post-check that the result is non-zero: [1](#0-0) 

`register_token` and `update_token` only enforce `config.decimals >= local_decimals`, i.e. `erc_decimals - local_decimals >= 0`, meaning the division factor `10^(erc_decimals - local_decimals)` is routinely non-trivial (e.g. an 18-decimal EVM token bridged to a 12-decimal or lower local asset): [2](#0-1) 

The vulnerable conversion is invoked directly in the unprivileged message-delivery path `on_accept`, which any relayer can trigger by delivering a proof for a message that originated from a `send()` call on the peer EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract (any user can call `send` with an arbitrarily small amount that has already been escrowed/burned on the source chain): [3](#0-2) 

If `amount` truncates to `0`, the code proceeds to call `NativeCurrency::transfer`/`Assets::transfer`/`Assets::mint_into` with `0`, which for most Substrate `Currency`/`fungibles::Mutate` implementations succeeds as a no-op, and the handler emits `TokenReceived { amount: 0, .. }` and returns `Ok(..)` — i.e., the message is recorded as successfully delivered: [4](#0-3) [5](#0-4) 

The same unchecked pattern is reused in `on_timeout` for refunds, so a timed-out small-amount send can also refund `0` back to the original sender while the request is marked handled: [6](#0-5) 

Because ISMP request delivery is idempotent/one-shot (a `PostRequest`/timeout is only ever processed once by `pallet-ismp`), there is no retry path once the message commitment is consumed. The user's ERC20 tokens were already escrowed (native asset) or burned (mint/burn asset) on the source chain in `send()`'s pre-dispatch step; once the destination side processes the message with a truncated-to-zero amount, those source-side funds are unrecoverable.

### Impact Explanation
This is a concrete permanent loss-of-funds bug reachable by an ordinary user's own cross-chain send (no privileged relayer/admin action required beyond normal message delivery) or exploitable by anyone who can induce/observe a legitimate small transfer being delivered. The severity mirrors, and arguably exceeds, the referenced USSD finding: instead of merely minting 0 stablecoin for a paid deposit, here the source-chain collateral/native asset is irreversibly locked in the pallet's custodial account (for native/custody assets) or permanently burned (for mint/burn assets), while the destination side registers the transfer as fully settled with zero value delivered.

### Likelihood Explanation
Likelihood is Medium-to-High for tokens registered with a large decimals gap (e.g., 18-decimal EVM token bridged to a lower-decimals local asset) or for any token whose price/decimals combination make small nominal amounts common. A relayer delivering routine small transfers (dust, fee remainders, low-value tokens, or user error) will trigger this without any special conditions — it requires only `amount < 10^(erc_decimals - local_decimals)`, which the registration process explicitly permits.

### Recommendation
In `convert_to_balance`, reject (or the caller should reject) conversions that round down to zero when the input `value` was non-zero, e.g. return an error such as `AmountTooSmall` before minting/transferring, so `on_accept`/`on_timeout` abort rather than silently consuming the message with a zero-value credit. Additionally, consider requiring a minimum transferable amount on the EVM `send()`/`HyperFungibleToken` side (reject `_amount` that would convert to `0` local units) before escrowing/burning, consistent with the original report's recommendation to add a "returned amount is not 0" check.

### Proof of Concept
1. Register a token via `register_token` where `local_decimals = 6` and the EVM peer's `config.decimals = 18` (allowed since `18 >= 6`), giving `Precisions::<T>::get(asset, evm_chain) = 18`.
2. A user calls `send()` on the EVM `HyperFungibleToken` contract (or the wrapped variant) with `amount = 1` (1 wei, i.e., `10^-18` of a token). The EVM side escrows/burns this `1` unit and dispatches a `PostRequest` with `message.amount = 1` (ERC20 denomination).
3. A relayer delivers the proof; `pallet-ismp` routes it to `Pallet::<T>::on_accept`.
4. `erc_decimals = 18`, `local_decimals = 6`, so `convert_to_balance` computes `1 / 10^(18-6) = 1 / 10^12 = 0` (integer division floors to zero): [7](#0-6) 
5. `amount = 0` flows into `NativeCurrency::transfer`/`Assets::mint_into` (no-op success), `TokenReceived { amount: 0 }` is emitted, and `on_accept` returns `Ok(..)` — the request is now considered delivered/settled.
6. The user's `1` wei of the EVM token remains permanently escrowed (or was already burned) on the source chain, and they received `0` on the destination chain, with no mechanism to retry or reclaim the difference.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
