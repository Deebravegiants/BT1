### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC-SHA256 signature that `Registry.process` verifies covers the body bytes alone. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken verbatim from unauthenticated HTTP headers — are never bound to that signature, yet they are trusted as the tenant/topic identity handed to the app's webhook handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the raw body (`@raw_body`) is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived fields to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only confirms that `HMAC(api_secret_key, raw_body) == received_hmac`; it says nothing about which shop or topic the body was generated for: [4](#0-3) 

**Identity binding broken:** the equality the library implicitly claims is `hmac_verified(shop_header) == shop_that_generated_this_body`, but the actual binding enforced is only `hmac_verified(raw_body_bytes)`. Because Shopify signs webhooks with the app's single `api_secret_key` (shared across every shop that installs the app), any shop that can trigger a webhook delivery for itself obtains a `(raw_body, hmac)` pair that remains valid regardless of which `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` header accompanies it. An attacker who controls one shop installation of the app can capture a legitimately-signed webhook body and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop (and/or a forged topic/webhook-id), and `Registry.process` will accept it as authentic because only the body's HMAC is checked.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee for webhook consumers: `WebhookMetadata#shop` is the only signal host applications have to know which merchant a webhook event belongs to, and it is delivered to the handler with no verification. A malicious merchant can produce cross-tenant webhook events, causing the host app to process, store, or act on data as if it originated from a different shop (cross-tenant access/confusion), meeting the Critical bar for cross-tenant access.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to run the app on at least one shop (or otherwise capture one valid signed webhook body) and control the ability to send arbitrary HTTP requests with forged headers to the app's public webhook endpoint — both easily achievable by any merchant/installer of the app, without needing the app's `api_secret_key` or an access token.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise re-verify that the shop/topic claimed in headers match Shopify's expectations independently of the body signature (e.g., cross-check the shop against a known/registered set, or require the host application to validate `shop` against its own tenant registry before trusting it). At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are **not** authenticated by `HmacValidator.validate` so host apps do not treat them as trusted tenant identifiers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic to receive a real request with body `B` and a valid `x-shopify-hmac-sha256` header `H = HMAC(api_secret_key, B)`.
2. Replay the exact same body `B` and header `H` to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally change `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(api_secret_key, B)` and compares it to `H` — this still succeeds because `B` and `H` are unchanged.
4. The handler registered for the topic receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app processes attacker-controlled data as if it came from the victim shop.
