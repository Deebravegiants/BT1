### Title
Deflationary/fee-on-transfer underlying tokens desync the WrappedHyperFungibleToken lock/unlock pool, causing later bridge-backs to fail while earlier ones drain the pool - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken` is a **shared custody pool** for a single underlying ERC20 across all users bridging that token out and back. `send()` locks tokens via a nominal `safeTransferFrom(msg.sender, address(this), params.amount)` and encodes that same *nominal* `params.amount` into the cross-chain `Message`, without ever measuring what the contract actually received. `onAccept()` (bridge-back path) and `onPostRequestTimeout()` (refund path) both pay out exactly `message.amount` via `safeTransfer`, again with no check against actual pool balance. If the configured `underlying` token charges a transfer fee or otherwise rebases/deflates balances on transfer, the pool's real balance permanently lags the nominal amount that was "locked" and subsequently minted 1:1 on the remote `HyperFungibleToken`. This is the same class of bug as the reported "unfair withdrawn amount": nominal accounting diverges from actual token balance in a pool shared by multiple depositors, so redemption order determines who gets paid in full and who is left short or unable to withdraw at all.

### Finding Description
`send()`: [1](#0-0) 

locks tokens with `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and never re-derives the actually-received amount from the pool's balance delta (unlike `IntentGatewayV2.placeOrder`, which explicitly measures the post-transfer balance to handle fee-on-transfer tokens — see `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2441-2494`). The nominal `params.amount` is what gets ABI-encoded into `Message.amount` and dispatched cross-chain: [2](#0-1) 

On the remote chain, `HyperFungibleToken.onAccept` mints exactly `message.amount` to the beneficiary — i.e., 1:1 with the nominal locked amount, not the actual amount received by the home-chain pool: [3](#0-2) 

When tokens are later bridged back, `WrappedHyperFungibleToken.onAccept` unconditionally pays out `message.amount` from the pool: [4](#0-3) 

and the timeout-refund path does the same: [5](#0-4) 

If `underlying` is a fee-on-transfer (deflationary) token — exactly the token class the external report's PoC uses — every `send()` locks less than `params.amount`, but the remote side always mints/tracks the full nominal `params.amount`. The pool's real balance is therefore permanently below the sum of nominal amounts owed. Redemption is first-come-first-served against actual balance: whoever calls `onAccept` (bridges back) first drains real tokens 1:1 with their nominal claim; once the deflation gap accumulates enough, a later bridge-back reverts inside `safeTransfer` for insufficient balance — permanently freezing that user's funds (their remote-side tokens were already burned as part of `HyperFungibleToken.send()`, so they cannot recover on the remote chain either). This mirrors the reported bug precisely: users depositing identical nominal amounts receive different outcomes purely based on withdrawal order, with the added severity that Hyperbridge's version can outright brick withdrawals rather than merely shortchange them.

The security notes documentation for a different contract in this repo (the streaming-yield-vault) explicitly calls out this exact class of risk and mitigates against it ("Standard ERC-20 only. Fee-on-transfer and rebasing assets desync the vault's accounting"), but no equivalent guard or documentation warning exists for `WrappedHyperFungibleToken`, and nothing in `configure()` restricts `underlying` to standard-conforming tokens: [6](#0-5) 

### Impact Explanation
This is a shared-custody bridge pool reachable by any unprivileged user who calls `send()`/bridges tokens back. Any deployer (or attacker who tricks an integrator/DAO into configuring) a fee-on-transfer/deflationary/rebasing ERC20 as the `underlying` creates a pool where nominal nobody-privileged accounting permanently exceeds actual custody. Consequences: (1) permanent freezing of funds for later bridge-back callers whose `safeTransfer` reverts against insufficient real balance, since their remote-chain HFT balance was already burned; (2) unfair/unbacked value extraction by earlier redeemers who drain real balance 1:1 while later legitimate claim-holders get nothing — a direct analog of "unbacked mint" since remote-chain HFT tokens are minted 1:1 against a pool that does not actually hold that much value.

### Likelihood Explanation
Requires the token deployer/owner to configure a fee-on-transfer or rebasing ERC20 as `_underlying` via `configure()` — this is a legitimate, expected use case for this general-purpose bridging primitive (the docs advertise it as "a cross-chain wrapper for existing ERC20 tokens", not restricted to a fixed safe-list), and the codebase already demonstrates elsewhere (IntentGatewayV2, streaming-yield-vault docs) that fee-on-transfer/rebasing tokens are a known, real-world concern the team actively guards against in other components — but not here. No malicious admin/governance action is needed beyond the routine act of onboarding a new token, which is a normal, expected operational flow for this contract.

### Recommendation
Measure the actual balance delta of `_underlying` before/after `safeTransferFrom` in `send()` and encode that measured amount (not `params.amount`) into `Message.amount`, mirroring the pattern already used in `IntentGatewayV2.placeOrder` for fee-on-transfer tokens. Alternatively/additionally, explicitly document and enforce (e.g., via an allow-list or an ERC20 balance-delta assertion) that `configure()` only accepts standard, non-fee-on-transfer, non-rebasing tokens, consistent with the security posture already applied to the streaming-yield-vault.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` (home chain) and `HyperFungibleToken` (remote chain), configure `_underlying` as a 1% fee-on-transfer token (e.g., the `FeeOnTransferToken` test helper already present in this repo at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2701-2735`).
2. Alice calls `send({amount: 1000})`. `safeTransferFrom` moves 1000 nominal but the pool only receives 990 (1% fee burned in transfer). `Message.amount = 1000` is dispatched; remote `HyperFungibleToken.onAccept` mints Alice 1000 HFT.
3. Bob and Eve repeat step 2 identically. Pool now holds 2970 real tokens but owes 3000 nominal across the three remote balances.
4. Alice bridges her 1000 HFT back first: remote `HyperFungibleToken.send()` burns 1000, `Message.amount = 1000` dispatched home; `WrappedHyperFungibleToken.onAccept` calls `safeTransfer(Alice, 1000)` — succeeds, pool now holds 1970 real tokens but still owes 2000 nominal to Bob+Eve.
5. Bob bridges back 1000 HFT: `onAccept` transfers 1000, pool now holds 970, still owes 1000 to Eve.
6. Eve bridges back her 1000 HFT: `onAccept` attempts `safeTransfer(Eve, 1000)` against a pool holding only 970 — reverts (or, on a returning-token-with-failed-boolean, silently keeps Eve's tokens burned with no payout). Eve's remote-side tokens are already burned, so her funds are permanently frozen/lost, while Alice and Bob withdrew in full — reproducing and amplifying the "unfair withdrawn amount" scenario from the reference report.

            dest: params.dest,
            to: dest,

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
