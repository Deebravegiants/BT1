## Title
Webhook shop identity spoofing via `X-Shopify-Shop-Domain` header not covered by HMAC — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the webhook HMAC to the raw body bytes only, while the `shop` (and `topic`/`webhook_id`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's webhook handler are read straight from unauthenticated HTTP headers. This breaks the identity binding `hmac == HMAC(shop, body)` down to `hmac == HMAC(body)`, letting any merchant who has installed the app on their own store forge a webhook that the library will accept as valid but attribute to an arbitrary victim shop.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

Note that `to_signable_string` returns only `@raw_body`: [2](#0-1) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) as the tenant identity for the delivered payload: [4](#0-3) 

Because `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the raw body) against `Context.api_secret_key`: [5](#0-4) 

the equality the code *should* enforce is:
`hmac == HMAC(api_secret_key, shop ‖ topic ‖ body)`

but what it actually enforces is:
`hmac == HMAC(api_secret_key, body)`

The `api_secret_key` (client secret) is a single, per-app secret shared across every shop that installs the app — not a per-shop secret. Consequently, any unprivileged internet user who installs the target app on their own (even free/dev) store receives genuine webhook deliveries correctly signed with the app's `client_secret`. They can capture one such `raw_body` + `X-Shopify-Hmac-SHA256` pair (the HMAC will validate because the body is unmodified) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to point at a victim shop that also has the app installed. `Registry.process` will accept the forged request (HMAC check passes since body is untouched) and dispatch the handler with `shop: <victim-shop>`, causing the app to process/store attacker-controlled payload data under the victim tenant's identity.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who is a legitimate but unprivileged app installer on their own store can make the library-integrated app believe a webhook (and its arbitrary/attacker-influenced body content, e.g. `orders/create`, `customers/update`, `app/uninstalled`) originated from a different, victim shop. Any app logic keyed off `WebhookMetadata#shop` (session/token lookup, data writes, triggering of shop-scoped actions) can be corrupted or manipulated for a tenant the attacker does not control — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
High. The only prerequisite is that the attacker can install the target Shopify app on any store they control (a normal, unprivileged action available to any merchant/developer), then capture and replay one genuine webhook delivery while swapping the shop-domain header — no access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the shop (and topic) into the signed material, or otherwise cryptographically/independently verify the header-derived `shop` against the specific installation the webhook subscription belongs to (e.g., cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription looked up via the Admin API, or include the header values in the HMAC computation if Shopify's delivery format supports it). At minimum, document that `request.shop` must not be trusted for cross-tenant authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`.
2. Attacker triggers/receives a legitimate webhook, capturing `raw_body` and the valid `X-Shopify-Hmac-SHA256` header (both signed with the app's single, shared `client_secret`).
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-SHA256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unmodified) `raw_body`, so it passes.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, causing the app to act on/attribute this data to the victim tenant.
