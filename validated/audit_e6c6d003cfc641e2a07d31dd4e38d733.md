### Title
Permanent market freeze from RAY-scaled debt-value overflow - (File: common/src/rates/scaling.rs)

### Summary

An unprivileged user can permanently freeze a lending market after its scaled debt grows past the `i128`-representable RAY domain. The permissionless `Controller::update_indexes` path calls `pool_update_indexes`, which runs `interest::global_sync`; `accrue_step` then computes `borrowed * new_borrow_index` through `scaled_to_original`/`Ray::mul` and reverts with `MathOverflow` once the product exceeds `i128::MAX`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description

`accrue_step` first unscales the existing borrowed and supplied balances, derives utilization and the new borrow index, and then calls `calculate_supplier_rewards`. [5](#0-4)  `calculate_supplier_rewards` computes both the old and new aggregate debt with `borrowed.mul(index)` and subtracts them. [6](#0-5)  `scaled_to_original` delegates directly to `Ray::mul`, whose multiplication is bounded by the `i128` result domain. [7](#0-6) [8](#0-7) 

The index cap alone does not prevent this condition: `update_borrow_index` clamps the index only after multiplying it by the interest factor, while the subsequent aggregate debt multiplication can still overflow if the scaled debt share count is large enough. [9](#0-8) [6](#0-5)  Once that boundary is crossed, every market mutation that performs `global_sync` encounters the same overflow before it can reduce debt or supply. [10](#0-9) [11](#0-10) 

The production-path regression test demonstrates this exact state transition: a one-billion-whole-token, 18-decimal market at 98% utilization eventually makes `try_update_indexes_for` return `MathOverflow`, after which both withdrawal and repayment fail with the same error. [12](#0-11) 

### Impact Explanation

The affected market permanently loses its state-transition path: suppliers cannot withdraw, borrowers cannot repay, and liquidations cannot proceed because those operations must accrue the market before applying their mutation. [13](#0-12) [14](#0-13) [15](#0-14)  This is permanent freezing of user funds and pool liquidity, not merely a failed edge input. [16](#0-15) 

### Likelihood Explanation

The trigger requires a very large market and enough elapsed accrual for `scaled_debt * borrow_index / RAY` to leave the `i128` domain, so it is a high-capital, market-dependent condition rather than an arbitrary input-only exploit. [4](#0-3)  Nevertheless, the triggering call is permissionless: `Controller::update_indexes(caller, assets)` only requires caller authorization and forwards the attacker-selected `HubAssetKey` list to the pool. [1](#0-0) [2](#0-1)  The existing test shows that a whale can reach the condition through ordinary `supply` and `borrow` actions and then let time advance; no privileged call is needed for the final freeze. [17](#0-16) 

### Recommendation

Enforce a hard market-size invariant at every share-minting boundary: total scaled debt and total scaled supply must remain small enough that `scaled * MAX_*_INDEX / RAY` cannot exceed `i128::MAX`. This should be checked in `mint_debt`, supply minting, and any revenue-share minting path, rather than relying only on asset-unit caps or the index ceiling. [18](#0-17) [19](#0-18)  If that bound is not feasible, accrual needs an explicit bounded fallback that caps the aggregate value calculation and permits repayment or withdrawal to reduce state before the arithmetic overflow becomes unrecoverable. [5](#0-4) 

### Proof of Concept

1. In a listed high-decimal market with sufficient cap, an attacker supplies a very large amount through `Controller::supply`; the fixture uses `1_000_000_000` whole 18-decimal tokens. [20](#0-19) 
2. Using separate collateral, the attacker calls `Controller::borrow` for 98% of that market’s liquidity. [21](#0-20) 
3. After enough ledger time passes, the attacker submits `Controller::update_indexes(caller, vec![HubAssetKey { hub_id, asset }])`. [1](#0-0) 
4. The pool accrual reaches `calculate_supplier_rewards`, where `borrowed.mul(new_borrow_index)` overflows before the index ceiling can make the operation safe. [22](#0-21) 
5. The checked harness confirms `update_indexes` fails with `MathOverflow`, and subsequent `withdraw` and `repay` calls fail identically. [23](#0-22)

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);

        GenericError::RepayRoundsToZeroShares

    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
