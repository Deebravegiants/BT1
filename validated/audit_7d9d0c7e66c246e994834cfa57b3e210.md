### Title
No vulnerability found for this question.

### Summary
The `JwtPayload#initialize` dual-secret decode fallback in [1](#0-0)  retries decoding against `Context.old_api_secret_key` only after the primary key fails, but both calls route through `decode_token`, which pins the algorithm explicitly.

### Finding Description
The binding claimed to be at risk is: `alg` header value chosen by attacker == `algorithm` enforced by `JWT.decode`. Tracing `decode_token`, the call is `JWT.decode(token, api_secret_key, true, leeway: JWT_LEEWAY, algorithm: "HS256")` with `true` for signature verification and `algorithm: "HS256"` hard-coded, as shown at [2](#0-1) . The `ruby-jwt` gem uses this explicit `algorithm:` option as the sole trusted algorithm for verification, ignoring/rejecting any `alg` value asserted in the attacker-supplied token header that doesn't match (e.g., `none` or `HS512`) — it does not defer to the token's own header to pick the verification algorithm. Any decode failure (bad signature, wrong alg, malformed token) raises `JWT::DecodeError`, which is caught and re-raised as `ShopifyAPI::Errors::InvalidJwtTokenError` at line 80. Since the attacker does not hold `api_secret_key` or `old_api_secret_key`, they cannot produce a valid HS256 signature for either key, and no alg-confusion vector exists because the algorithm is not attacker-selectable in this call. The fallback to `old_api_secret_key` only changes which known secret is used to verify against, and never bypasses signature verification itself, as shown by the rescue clause in `initialize` at line 27-30. `session_id_from_shopify_id_token` in [3](#0-2)  only proceeds past `Auth::JwtPayload.new(id_token)` if that constructor succeeds, so an unforgeable token never reaches session-id derivation.

### Impact Explanation
No exposure: the attacker gains nothing per request, and no cross-tenant, authentication-bypass, or credential-theft primitive is created by this path. Existing guard: `algorithm: "HS256"` pinning in `JWT.decode` combined with unforgeable HMAC secrets.

### Likelihood Explanation
Not applicable — the equality (attacker-chosen alg vs. enforced HS256) does not hold in the attacker's favor under any configuration, including the key-rotation scenario with `Context.old_api_secret_key` set.

### Recommendation
No change needed for this specific path; the existing explicit `algorithm: "HS256"` argument is the correct and sufficient mitigation against alg-confusion attacks.

### Proof of Concept
Not applicable — this is a negative finding confirming the binding holds.
