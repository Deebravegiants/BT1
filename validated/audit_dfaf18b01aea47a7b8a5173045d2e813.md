### Title
Permissionless `recapitalize` refunds "excess" out of supplier custody while the cash book still reports the market solvent - (File: contracts/pool/tests/flows.rs)

### Summary
The pool's `recapitalize` path treats the internal cash book as proof of backing and pays any amount above the computed shortfall back to the caller as a refund. Because the refund is measured against the book rather than against verified post-transfer custody, an unprivileged caller can invoke `recapitalize` with an amount equal to the pool's real balance, receive a payout that drains the pool's actual token custody to zero, and leave the cash book still claiming the suppliers' deposits exist. The market then reports itself solvent while every supplier exit fails inside the SAC transfer — economically identical to the Bitsane exit-scam shape: user deposits vanish while the venue's own accounting insists they are there.

### Finding Description
`recapitalize` is a permissionless controller/pool entrypoint intended to fill a backing shortfall after bad-debt socialization, refunding the excess to the payer (`docs/reference/runbooks/force-socialize-bad-debt.md`, "recapitalize can fill an existing backing shortfall and refunds excess. A fully backed market accepts no fill"). The in-repo regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates the flaw end-to-end: after a legitimate `10_000_000_000` supply (book cash == pool balance), calling `pool.recapitalize(hub, payer, custody)` transfers the entire pool balance out to `payer` while `state_snapshot().cash` still reports `>= deposit`. The supplier's subsequent `withdraw` passes the pool's own liquidity guards (`InsufficientLiquidity`, `PoolInsolvent` do not fire — the book says the cash is there) and instead reverts inside the Stellar Asset Contract with `BalanceError = 10`, i.e., insufficient custody. The root cause is that the solvency/liquidity checks (`require_reserves`, the solvency guard) and the recapitalize refund computation both read the cash book, not the measured token balance. A refund computed against an overstated or pre-transfer book value can be funded out of suppliers' custody, and nothing after the payout reconciles `cash` with the real balance. This mirrors the "direct token transfers to the pool / measured-receipt settlement" failure class: amounts are settled against accounting state instead of exact-balance measurement as used elsewhere (e.g., the exact-balance cash flash loan and balance-delta output measurement in the router paths).

### Impact Explanation
Theft of user funds. A single unprivileged address drains a market's entire token custody through `recapitalize`'s excess refund, leaving supply positions nominally intact but permanently unpayable — every subsequent `withdraw` reverts inside the SAC transfer rather than at a pool guard. The protocol continues to report solvency, so the loss is silent until suppliers attempt to exit. This satisfies both "theft of user funds" and "permanent freezing of funds" under the acceptance criteria.

### Likelihood Explanation
Medium. `recapitalize` is permissionless (listed in `scripts/permissionless_entrypoints.txt` and reachable via controller `recapitalize`), requires only that the caller hold/authorize the token amount for the pull, and needs no oracle, governance delay, or position setup. The exploit is atomic: pull, refund, gone. The main precondition is a market whose book-claimed cash permits a refund-sized payout; the in-repo test shows the drain succeeding against a fully backed market. Constrained to a single market per call but repeatable across markets.

### Recommendation
Settle `recapitalize` against measured custody, not the cash book. Concretely: (1) compute the refundable excess only after the inbound transfer has been measured via balance delta (`balance_after - balance_before`), so the refund can never exceed what the payer actually contributed plus a true, custody-verified shortfall remainder; (2) after the refund payout, reconcile `cash` with the actual pool balance or require `balance >= cash` as a post-condition the same way `enforce_post_pool_solvency` guards withdrawals; (3) cap the refund at `max(0, amount_in - shortfall)` where `shortfall` is derived from real balance, not book. Add a regression asserting `token.balance(pool) >= state.cash` after `recapitalize`.

### Proof of Concept
Reproduced verbatim by the existing test `contracts/pool/tests/flows.rs::test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (lines 3408-3483): mint `deposit = 10_000_000_000` to the pool via `supply`, call `client().recapitalize(&hub(&asset), &payer, &custody)` where `custody = token.balance(pool)`, observe `token.balance(pool) == 0` while `state_snapshot().cash >= deposit`, then `try_withdraw(receiver, false, wdr(supplied, i128::MAX, 0))` fails with SAC `BalanceError = 10` rather than `InsufficientLiquidity` or `PoolInsolvent`, and `receiver` holds nothing.
```rust
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
    // The failure must come from custody, not from a pool guard. The SAC
    // reports insufficient balance as its own contract error `BalanceError = 10`.
    // The asserts check that exact code and that neither pool liquidity guard
    // fired: `require_reserves` read the book and let the exit through.
    const SAC_BALANCE_ERROR: u32 = 10;
    match outcome {
        Err(Ok(err)) => {
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::InsufficientLiquidity as u32),
                "the pool's own liquidity guard must NOT be what stopped this -- \
                 it reads the cash book, which still shows the funds"
            );
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::PoolInsolvent as u32),
                "the pool's solvency guard must NOT be what stopped this either"
            );
            assert_eq!(
                err,
                Error::from_contract_error(SAC_BALANCE_ERROR),
                "the exit must fail inside the SAC transfer for want of custody"
            );
        }
        Err(Err(host_abort)) => panic!("expected a SAC contract error, got {host_abort:?}"),
        Ok(_) => unreachable!("asserted is_err above"),
    }
    assert_eq!(token.balance(&receiver), 0, "the supplier received nothing");
```
