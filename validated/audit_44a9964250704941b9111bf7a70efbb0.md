### Title
Fee-on-transfer underlying tokens cause unbacked minting/insolvent escrow in WrappedHyperFungibleToken - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 by calling `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message encoding `params.amount` as the amount to mint/unlock on the peer chain, without verifying that `params.amount` was actually received by the contract.

### Finding Description
In `send()`: [1](#0-0) 

the ERC20 lock path (`else` branch) performs `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and immediately builds the dispatch message via `_buildDispatchPost(params)`, which encodes `params.amount` verbatim into the `Message.amount` field: [2](#0-1) 

If `_underlying` is a fee-on-transfer or rebasing/deflationary ERC20 (e.g. a USDT-style token with fees enabled, or any deflationary token), the actual balance increase of the contract will be less than `params.amount`. The peer `HyperFungibleToken.onAccept()` on the destination chain decodes the message and unconditionally mints `message.amount` to the beneficiary: [3](#0-2) 

This is precisely the accounting corruption bug class described in the external report: the amount recorded/propagated by the protocol is decoupled from the amount actually received by the escrow contract. The codebase clearly recognizes this bug class and defends against it elsewhere — `IntentGatewayV2.placeOrder` explicitly captures `balBefore`/`balAfter` around `safeTransferFrom` and uses the actual delta to size escrow, as proven by the `FeeOnTransferToken` test: [4](#0-3) [5](#0-4) 

but the identical pattern was not applied to `WrappedHyperFungibleToken.send()`, nor is there any restriction preventing an owner from configuring `_underlying` to a fee-on-transfer token.

### Impact Explanation
Every `send()` call with a fee-on-transfer underlying mints more tokens on the destination chain(s) than are actually escrowed on the home chain. Over repeated sends this creates unbacked supply of the wrapped representation across all peer `HyperFungibleToken` deployments. Because the wrapped supply is only redeemable by burning on a remote chain and unlocking (`safeTransfer`, at full `message.amount`) from the home-chain escrow, the escrow becomes structurally insolvent: eventually some legitimate holders' redemption (`onAccept`/burn-and-unlock) calls will fail or drain the escrow such that later redeemers cannot be paid — a permanent freezing/loss of funds condition, compounded on every single send transaction. This can also be exploited deliberately: an attacker deploys or discovers a fee-on-transfer token registered as `_underlying`, repeatedly sends small amounts to inflate wrapped supply on a destination chain by the fee delta, then redeems the inflated balance for full-value underlying elsewhere, effectively minting value from nothing.

### Likelihood Explanation
Likelihood depends on `_underlying` being a fee-on-transfer/deflationary token, which is an owner/deployment choice rather than a value intrinsic to the protocol's dispatch/verification logic — but the report's own precedent (USDT's dormant fee switch, and the many actively deflationary ERC20s in production) plus the fact that the sibling `IntentGatewayV2` contract already had to be hardened against exactly this token class shows it's a realistic, anticipated integration scenario, not a theoretical edge case. No malicious admin action is required beyond a token integration decision, and the bug is triggered by a single, ordinary user `send()` transaction.

### Recommendation
In `WrappedHyperFungibleToken.send()`, measure `address(this)` balance of `_underlying` before and after `safeTransferFrom`, and use the actual received delta (not `params.amount`) when building the dispatched `Message.amount`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol`, which contains an identical `send()` implementation.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a token that charges a 10% fee on transfer (e.g. USDT-style with fee enabled, or any deflationary token).
2. User calls `send({dest: chainB, to: recipient, amount: 1000e18, ...})`.
3. `safeTransferFrom(user, address(this), 1000e18)` results in only 900e18 actually credited to the contract's balance; the other 100e18 is burned/fee'd by the token contract.
4. `_buildDispatchPost` nonetheless encodes `amount: 1000e18` in the dispatched `Message`.
5. On chain B, `HyperFungibleToken.onAccept()` mints `1000e18` to `recipient` — 100e18 more than is actually backing it in the chain-A escrow.
6. Repeating this creates ever-growing unbacked wrapped supply; when enough holders attempt to redeem (send back to unlock on chain A), `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` in `onAccept` will eventually revert for lack of escrowed balance, or drain remaining legitimate depositors' funds — freezing/losing funds for the last redeemers.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }
