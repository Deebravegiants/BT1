## Analog Found

### Title
Self-relaying an oversized, self-dispatched request lets an attacker mint unbacked `ReputationAsset` and buy a Collator seat for free - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
The reported Flat Money bug lets a trader inflate `additionalSize` (a metric it fully controls, with no cost proportional to the resulting reward) to mint disproportionate points, exit, and repeat. The structural analog in Hyperbridge is `pallet-messaging-incentives`, which mints `ReputationAsset` to a "relayer" proportional to raw request-body byte count — a metric the message's own dispatcher controls and can inflate arbitrarily — with no fee or stake proportional to the resulting reward.

### Finding Description
`pallet-messaging-incentives::on_executed` mints `bytes × MintPerByte` of `ReputationAsset` to whichever account's sr25519 signature is recovered from a delivered `Request`/`Response` message, where `bytes` is simply `max(body.len(), 32)` summed over the request payloads: [1](#0-0) 

This mint has no relationship to any real fee or capital committed by the recipient. Dispatching itself is explicitly free at the runtime layer — Hyperbridge "no longer charges a protocol fee on Polkadot-SDK chains," and even the relayer fee is optional and can be zero for self-relay: [2](#0-1) [3](#0-2) 

So any module able to call `IsmpDispatcher::dispatch_request` can craft a `PostRequest` with an arbitrarily large `body`, targeting a destination the same operator also relays for. Once the message is genuinely delivered (a real state/consensus proof is still required — this is not a forged-message bug), `on_executed` mints reputation proportional purely to the body size the attacker chose, to whichever account's signature the attacker attaches as `signer`. The only real cost is the weight/storage fee for including a larger payload — a cost with no designed relationship to the `MintPerByte` reward rate governance sets.

This mirrors the reported issue precisely: a self-controlled metric (`additionalSize` for the trader; raw byte count for the dispatcher/relayer) drives a reward mint (`Points`/`ReputationAsset`) that is not backed by any commensurate stake or fee, so the actor can maximize the metric cheaply and repeat.

### Impact Explanation
`ReputationAsset` is not merely cosmetic — it directly determines the Hyperbridge Collator set. `pallet-collator-manager::new_session` ranks bonded candidates strictly by their controller's `ReputationAsset` balance and selects the top holders as block-producing Collators: [4](#0-3) 

Collators are paid `0.7 $BRIDGE` per authored block from the treasury, and reputation is explicitly described as "the primary factor in Collator selection": [5](#0-4) 

An attacker who inflates reputation via oversized self-dispatched/self-relayed messages (rather than by doing real, economically costed relaying/proving work) can outrank honest operators for collator seats — a real, transferable-value outcome (treasury-funded block rewards) — and additionally gains control of block production, which also underpins Hyperbridge's fisherman/state-commitment veto mechanism. This is a real path to unbacked-mint-driven unauthorized privilege acquisition, not merely a cosmetic score inflation.

### Likelihood Explanation
The mechanism is live and reachable by any account able to dispatch a request through `IsmpDispatcher` and subsequently deliver/relay it — no special privilege is required beyond `MintPerByte` being non-zero, which is the intended, governance-enabled operating mode of the pallet (it "only fires on successful message execution," is designed to reward every relayer, and the repo's own comment acknowledges awareness of gaming via payload size, but only guards the trivial zero-byte case, not the large-byte inflation case): [6](#0-5) 

Because dispatch itself is free and relaying requires no fee for self-relay, the only friction is ordinary block-weight/storage cost for a larger payload, which is not designed to track `MintPerByte`. An attacker fully controls both ends (dispatcher and relayer signer) when relaying between two state machines it operates or between itself and any destination it self-relays to.

### Recommendation
Do not mint `ReputationAsset` directly proportional to raw, dispatcher-controlled payload size. Either: cap the per-message mintable bytes to a value close to typical real message sizes so inflating body size yields no more than marginal gain over its real transaction/weight cost; require the reward to be bounded by, or a fraction of, an actual fee paid by a third party (akin to `OutboundRequestDeliveryReward`/`OutboundConsensusDeliveryReward`, which are flat governance-set amounts uncorrelated to attacker-chosen inputs); or require that the relayer be distinct from the request's originating module/account before minting reputation, closing the self-dealing loop.

### Proof of Concept
1. Governance sets `MintPerByte::<T>` to a non-zero value (the intended operating state of the pallet).
2. Attacker controls a module capable of `IsmpDispatcher::dispatch_request` (e.g., a custom pallet or an accessible demo/ping module) and dispatches a `PostRequest` with a body far larger than any realistic application payload (e.g., hundreds of KB), destined for a chain the attacker also relays to, with `fee = 0` (self-relay, no cost).
3. The same attacker acts as the relayer, submits the message for delivery on the destination and observes/produces the proof of delivery back to the source (`pallet-ismp`'s normal message execution path) — a real but comparatively cheap cost (only weight/storage, no protocol fee).
4. `pallet_ismp::Pallet::execute` invokes `FeeHandler::on_executed`, which calls into `pallet-messaging-incentives::on_executed`, computing `bytes = body.len()` (attacker-chosen, large) and minting `bytes × MintPerByte` of `ReputationAsset` to the attacker's signer account: [7](#0-6) 
5. Attacker repeats the cycle (or issues one large batch) to accumulate `ReputationAsset` far in excess of what honest, appropriately-sized relaying/proving work would earn.
6. At the next session boundary, `pallet-collator-manager::new_session` ranks candidates by this inflated `ReputationAsset` balance, and the attacker's controller is selected as a Collator ahead of genuinely active operators, subsequently earning real `$BRIDGE` block rewards from the treasury: [8](#0-7)

```rust
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
```

```rust
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
```

```text
# Hyperbridge Fees

Hyperbridge no longer charges a protocol fee on Polkadot-SDK chains. Dispatching is free at the runtime layer — applications only need to attach an optional **relayer fee** if they want third-party relayers to deliver their messages.

## Relayer Fees

The relayer fee is an optional incentive provided by applications initiating cross-chain transactions. It compensates Hyperbridge's decentralized relayers for delivering messages to the destination chain. Apps that prefer to self-relay can leave the fee at zero.

The fee is collected by `pallet-ismp`'s `IsmpDispatcher` from the configured `Currency` (typically a stablecoin). It's escrowed into the `RELAYER_FEE_ACCOUNT` and paid out to the relayer that delivers the message (or refunded to the payer on timeout).
```

```text
Collators are block producers for the Hyperbridge blockchain. They are essential for keeping the chain live and processing transactions, and
they double as the network's fraud-detection layer for the L2s Hyperbridge messages with: every collator runs an in-node fisherman task that
```

```markdown
1. `pallet-ismp` finishes executing a batch of messages and invokes
   [`FeeHandler::on_executed`].
2. This pallet reads the current `MintPerByte` rate. If it is zero, nothing
   happens (the pallet stays installed but inactive).
3. For each `Request`/`Response` message it:
   - Computes `bytes = max(body_size, 32)` — the same floor `pallet-bandwidth`
     uses, so trivial payloads can't game the mint by costing zero.
   - Multiplies `bytes × MintPerByte` to get the mint amount.
   - Recovers the relayer's account from the sr25519 signature on the message's
     `signer` field.
   - Mints that amount of `ReputationAsset` to the relayer.
4. Consensus messages and any non-Request/Response variants are skipped.
5. `pays_fee = Pays::No` on the dispatch info — the relayer is never charged
   here.
```
