### Title
Fee evasion via attacker-controlled router calldata in LiFi swap output measurement - (File: contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` measures the swap's output solely by taking a before/after balance snapshot of the `LifiExternalAction` contract itself around an arbitrary, fully attacker-crafted `externalActionMetadata` call to the fixed LI.FI router. Since the router calldata (including the swap's output receiver) is entirely attacker-controlled and unvalidated, an attacker can route part of the true swap output directly to their own external address instead of back to the action contract, making the measured `swappedAmount` (and therefore `hinkalFee`/`relayFee`, which are computed as a percentage of `swappedAmount`) understate the real value produced by the swap.

### Finding Description
The broken equality is: fee owed to relay/protocol should be `percentage(trueSwapOutput)`, but the code computes `hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, variableRate)` where `swappedAmount = getERC20OrETHBalance(outputToken)_after - getERC20OrETHBalance(outputToken)_before` [1](#0-0) , computed strictly from the action contract's own balance around the `router.call(externalActionMetadata)`. Because `externalActionMetadata` is attacker-supplied calldata forwarded verbatim to the router with no constraint that the swap's output receiver is `address(this)`, the attacker can structure the LI.FI route so that a portion (or nearly all) of the real output is delivered to an address they control, while only a small residual lands in the action contract. `swappedAmount` then reflects only that residual.

Downstream, `ExternalActionSwap.swap` computes `hinkalFee`/`relayFee` off this artificially small `swappedAmount` [2](#0-1) , and then honestly forwards `amountToSendToHinkal = swappedAmount - totalFee` to Hinkal and mints a UTXO of exactly that value [3](#0-2) . Hinkal's balance-diff invariant in `transact` (`balanceDif == amountChanges[i] + utxoAmount`) is satisfied because the action's self-reported delivery exactly matches what it actually transferred to Hinkal [4](#0-3) ; this guard verifies internal consistency of the action's own numbers, not that those numbers reflect the true value the router produced. Consequently, the UTXO credited is not "larger than delivered" — it exactly matches what's delivered — but the *fee base* itself is manipulable, letting the attacker siphon most of the swap's real output to a private address while paying `hinkalFee`/the variable-rate portion of `relayFee` on only the small residual amount.

### Impact Explanation
This lets the attacker (who must supply their own shielded input funds, since nullifiers/proofs are self-owned) evade paying the protocol's/relay's variable-rate fee on the bulk of a swap's true output by diverting it out-of-band via router calldata, while still receiving a valid (small) UTXO for the residual. This is a permanent underpayment/theft of protocol and relay fee revenue — High severity per the stated categories ("theft ... of protocol/relay fees"). It is repeatable on every LiFi swap transaction the attacker initiates and does not require any privileged role.

### Likelihood Explanation
Feasibility depends on whether the LI.FI router/route the contract calls into supports specifying an arbitrary receiver for (part of) the swap output — a common feature of DEX aggregator calldata. No special preconditions beyond normal deposit/UTXO ownership are needed; the attacker only needs to be able to craft `externalActionMetadata` for their own transaction, which the rules grant them. Cost is limited to gas and the router's own fee/slippage mechanics for constructing a split route.

### Recommendation
Do not trust a self-measured balance delta as the sole source of truth for fee calculation. Either (a) require the router calldata to encode `address(this)` as the sole/enforced receiver (validate the encoded receiver field, if the router/LI.FI API supports doing so safely), or (b) compute fees from an independently attested/quoted output amount rather than solely the post-call balance delta of the action contract, or (c) restrict `externalActionMetadata` to a decoded, whitelisted call shape where the receiver parameter is forcibly set/overwritten by the contract rather than accepted verbatim from the caller.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock "router" contract that decodes an extra `receiver` field from calldata and, on `callRouter`, sends `X%` of a simulated output token mint to `address(this)` (the action) and `(100-X)%` directly to an attacker-chosen address encoded in the calldata.
2. Craft `circomData.externalActionData.externalActionMetadata` so `X` is small (e.g., 5%).
3. Run `Hinkal.transact` with a valid proof spending the attacker's own UTXO as input.
4. Assert: `hinkalFee` and the variable portion of `relayFee` charged equal `variableRate * (5% of true output)`, not `variableRate * (true output)`; assert attacker's external wallet received `95%` of true output outside of any Hinkal-tracked UTXO or fee accounting; assert `balanceDif == amountChanges[outputIdx] + utxoAmount` still passes in `Hinkal.transact` despite the fee shortfall, confirming the existing guard does not catch the manipulation.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
