Audit Report

## Title
CORS wildcard origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` matches wildcard CORS entries (e.g. `*.ethereum.org`) using `strings.HasSuffix(originHost, allowedHost)` without requiring a domain-label boundary. This lets an attacker who registers a domain like `evilethereum.org` satisfy a `*.ethereum.org` allowlist entry, causing the gateway to reflect the attacker's `Origin` value into `Access-Control-Allow-Origin`.

## Finding Description
The relevant code is: [1](#0-0) 

`strings.HasSuffix` only checks literal string suffix equality — it does not verify that the character preceding the matched suffix is a `.`. So for an allowlist entry `*.ethereum.org` (stripped to `ethereum.org`), a request `Origin: https://evilethereum.org` satisfies `strings.HasSuffix("evilethereum.org", "ethereum.org")` even though `evilethereum.org` is a wholly separate, attacker-controllable domain and not a subdomain of `ethereum.org`.

The result feeds directly into the CORS response headers with no further validation: [2](#0-1) 

The existing test suite exercises negative cases like `https://ethereum.remix.org` (doesn't end with the suffix at all) and scheme/port mismatches, but does not test the boundary-confusion case (`evilethereum.org` vs `*.ethereum.org`): [3](#0-2) 

This confirms none of the existing checks (scheme match, port match, exact host match) catch this case, and the wildcard branch is the only path with the flaw.

## Impact Explanation
This is a genuine CORS allowlist bypass on the gateway's internet-facing HTTP server. Assuming an operator has configured a wildcard `CORSAllowedOrigins` entry (a supported, documented pattern exercised by the project's own tests), any attacker who registers a suffix-colliding domain can have a browser at that domain read gateway API responses cross-origin, defeating the intended origin restriction. This maps to the "allowlist bypass" impact category for the gateway's internet-facing entry point.

## Likelihood Explanation
Exploitation requires: (1) a wildcard CORS entry being configured — a normal, supported configuration option, not a misconfiguration outside intended use, and (2) the attacker registering/controlling any domain ending in the same label string. No credentials or elevated access are needed beyond getting a victim browser to visit an attacker page that issues a cross-origin request; this is a plausible unprivileged-attacker scenario reachable via a standard browser request against the gateway's public endpoint.

## Recommendation
Require a true subdomain boundary in the wildcard match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```

## Proof of Concept
1. Configure `CORSEnabled = true` and `CORSAllowedOrigins = []string{"https://*.ethereum.org"}` as in `startNewServer` from `core/services/gateway/network/httpserver_test.go`.
2. Send an HTTP request to the gateway path with header `Origin: https://evilethereum.org`.
3. Observe the response contains `Access-Control-Allow-Origin: https://evilethereum.org`, because `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true` in `isAllowedOrigin` at [4](#0-3) , even though `evilethereum.org` is not a subdomain of `ethereum.org`. This can be added as a Go unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`.
