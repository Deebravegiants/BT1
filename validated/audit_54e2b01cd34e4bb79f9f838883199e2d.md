### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload as only the raw HTTP body [1](#0-0) , while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values used to route and process the webhook are taken directly from attacker-controllable HTTP headers, entirely outside the HMAC's coverage [5](#0-4) . `Utils::HmacValidator.validate` only proves that the body bytes were signed by Shopify's secret; it says nothing about which shop or topic those bytes belong to [6](#0-5) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, shop || topic || body)`, i.e., the authenticated shop identity should equal the shop the HMAC was computed for. Instead the gem only checks `hmac == HMAC(secret, body)` and separately trusts the `shop-domain` header verbatim (`Registry#process` calls `Utils::HmacValidator.validate(request)` then immediately uses `request.shop` and `request.topic` to look up and invoke the handler, without any additional binding) [4](#0-3) . Because the signed material is body-only, any two shops that ever receive a webhook with an identical body (which is common — many topics such as `app/uninstalled` or minimal-payload topics produce constant or predictable bodies) produce the *same* valid HMAC. An attacker who installs the target app on their own store receives a legitimately-signed webhook request (Shopify signs it with the app's real `api_secret_key`) for their own shop. The attacker can capture that `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header for a victim shop's domain. `HmacValidator.validate` still succeeds because it only re-derives the signature from `raw_body` [2](#0-1) , and `Registry.process` will dispatch the handler believing the event originated from the victim shop [4](#0-3) .

### Impact Explanation
This breaks the shop-tenant boundary that host applications rely on this gem to enforce for webhook authenticity. A host app's webhook handler typically uses `WebhookMetadata#shop` to locate a merchant's session/tenant record and apply the event data [7](#0-6) . An attacker able to forge the shop association for a valid HMAC can inject spoofed webhook data attributed to a victim shop — cross-tenant data corruption or spoofed state changes — which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any developer/attacker can freely install the target app on their own Shopify development store, which is a normal, unprivileged action, and capture genuinely-signed webhook deliveries for topics with static or highly predictable bodies (e.g., `app/uninstalled` typically delivers `{}`), then replay the exact bytes with a different `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key` or any merchant credential is required — only the ability to receive one's own legitimately signed webhook and resend it with modified headers.

### Recommendation
Bind the shop (and ideally topic) to the signed material, or otherwise re-verify header identity against a source Shopify itself signs. Since Shopify's own HMAC scheme is body-only by design, the gem should additionally reject `shop-domain` values it cannot independently corroborate — e.g., only accept webhooks for shops with an existing installed session/known shop, and document clearly that `request.shop`/`request.topic` are unauthenticated header values that host applications must not trust as an identity proof without additional verification (such as maintaining a source IP allowlist for Shopify's webhook senders, or cross-checking against an active session for that shop before processing).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures a webhook for a topic with a constant/predictable body, e.g. `app/uninstalled` (`raw_body = "{}"`).
2. Shopify delivers a real webhook to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of "{}" with the app's real secret>`
3. Attacker captures this exact HTTP request, then re-sends it to the same public webhook endpoint, only changing the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: ...)` is constructed with the forged shop header; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC [2](#0-1) .
5. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` [4](#0-3) , causing the host app to act on the victim shop's tenant record using attacker-supplied (replayed) data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
