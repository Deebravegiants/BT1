## Finding: Webhook shop identity not bound by HMAC allows cross-tenant webhook forgery

The gem's webhook processing pipeline validates only the **request body** against the HMAC signature, but the **`shop-domain` header used as the tenant identity** is never covered by that signature. This is the same class of bug as the report's core issue: a value that determines *who benefits* from a signed action (there, "who becomes primary stakeholder"; here, "which shop the payload is attributed to") is not itself bound by the authentication mechanism.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers, with no participation in the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `raw_body`), then immediately trusts `request.shop` — taken from the unauthenticated header — as the tenant identity passed to the app's handler: [3](#0-2) 

The equality the system implicitly relies on is:
`shop authenticated by HMAC == shop delivered to handler as WebhookMetadata#shop`

But the actual binding is:
`shop authenticated by HMAC (over body only) != shop-domain header (unauthenticated) used to build WebhookMetadata`

### Exploit path

1. An attacker who is a legitimate, unprivileged tenant (a normal merchant that has installed the host app) triggers or receives one of their own genuine webhooks — e.g. an `orders/create` webhook with a known/reproducible body (many webhook payloads, especially test/mandatory webhooks, are deterministic or attacker-influenced, e.g. the attacker's own order data). This gives them a **valid `(body, hmac)` pair signed with the app's real secret**, without ever learning `api_secret_key`.
2. The attacker resends this exact `(body, hmac)` pair to the app's webhook endpoint but swaps the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop's domain.
3. `Utils::HmacValidator.validate` still succeeds because HMAC only covers `raw_body`, which is unchanged: [4](#0-3) 
4. `Registry.process` dispatches to the handler with `shop: request.shop` set to the victim's domain, so the host application processes attacker-controlled webhook data as if it originated from the victim tenant.

### Impact

This breaks cross-tenant isolation: an unprivileged attacker (any installed merchant) can make the host application believe attacker-supplied webhook data belongs to a different shop, without needing `api_secret_key`, an access token, or any privileged access — matching the Critical "cross-tenant access" bar.

### Recommendation

Bind the shop/topic/webhook-id identity into the signed content that `HmacValidator` checks (e.g., include the `shop-domain`, `topic`, and `webhook-id` headers in `to_signable_string`, not just the raw body), or require the host application to cross-check `request.shop` against a shop known independently of the webhook headers before trusting it.       def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
