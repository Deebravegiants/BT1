## Title
Proposer task panics (unrecoverable crash) via unconditional `U256` underflow in `construct_state_proposal` when the OP-stack dispute game factory has zero games — (File: `tesseract/consensus/op-host/src/host.rs`)

### Summary
This is the same bug class as the external report: `getTimeToNextGame` in viem crashed because it assumed the dispute game factory always has at least one (or two) games and performed unchecked arithmetic on the count. The Hyperbridge OP-stack consensus client (`op-host`) makes the identical assumption in its proposer loop: it reads `DisputeGameFactory.gameCount()` and immediately subtracts `1` from it without checking for zero, using `sp_core::U256`, whose `Sub` implementation panics unconditionally (not just in debug builds) on underflow.

### Finding Description
In `construct_state_proposal`, the proposer fetches the total dispute game count and computes the index of the most recent game: [1](#0-0) 

```rust
let latest_game_count =
    contract.gameCount().block(BlockId::latest()).call().await?;
let latest_game_index = alloy_u256_to_primitive(latest_game_count) - U256::one();
```

`U256` here is `sp_core::U256`, imported at the top of the file: [2](#0-1) 

`sp_core::U256` is generated via the `uint` crate's `construct_uint!` macro, whose `Sub` operator panics unconditionally (regardless of release/debug profile) on underflow. If `gameCount()` returns `0` — e.g. right after a chain's dispute game factory is deployed and configured for Hyperbridge but before the official op-proposer (or anyone) has created a single dispute game — `alloy_u256_to_primitive(0) - U256::one()` panics.

This code path is reached from the always-running proposer task, which is spawned whenever a state machine has both a `dispute_game_factory` and `proposer_config` set: [3](#0-2) 

The trigger condition for entering the vulnerable branch is simply the presence of a `PostRequest` or `GetRequest` ISMP event in the queried range — i.e., any unprivileged party dispatching a single cross-chain message/request against this state machine causes the proposer to run `construct_state_proposal` on the next tick: [4](#0-3) 

Because `tokio::spawn(proposer_loop)`'s `JoinHandle` is discarded (not awaited or monitored), a panic inside the spawned task silently kills that task forever, with no restart or error surfaced to the top-level `start_consensus` error path — the process keeps running but the proposer permanently stops: [5](#0-4) 

### Impact Explanation
Once the proposer task panics and dies, no further OP-stack output-root/state proposals are ever submitted by this relayer instance for that state machine. Since dispute-game-based state commitments are the mechanism by which Hyperbridge verifies OP-stack L2 state (and thus authorizes delivery of requests/responses whose proofs are checked against that state commitment), a stalled proposer degrades to "a route unable to deliver messages" for that state machine until the operator notices and restarts the relayer. This is triggerable by an ordinary, unprivileged message dispatcher simply sending a request to a freshly configured (zero-dispute-game) OP-stack state machine — no admin, governance, or privileged access is required.

### Likelihood Explanation
Likelihood is highest during onboarding of a new OP-stack chain to Hyperbridge (before the chain's official op-proposer has created its first dispute game) or on any state machine whose dispute game factory happens to have zero games at the time a message is dispatched. Any user dispatching a `PostRequest`/`GetRequest` to that state machine can trigger the vulnerable code path on the very next 30-second proposer tick.

### Recommendation
Guard the subtraction: if `gameCount() == 0`, skip proposal construction for this tick (log and return `Ok(None)`) instead of subtracting. Additionally, monitor/restart the `proposer_loop`/`proposal_submit_loop` `JoinHandle`s (or use `tokio::spawn` + supervision) so a panic in either task is surfaced and recovered rather than silently killing the proposer permanently.

### Proof of Concept
1. Configure `op-host` for a state machine whose `DisputeGameFactory` has been deployed but has `gameCount() == 0` (no games created yet), with `dispute_game_factory` and `proposer_config` both set.
2. Have any user dispatch a `PostRequest` or `GetRequest` targeting that state machine so `query_ismp_events` returns a matching event.
3. On the next proposer tick, `construct_state_proposal` executes `alloy_u256_to_primitive(0) - U256::one()`, which panics inside the spawned `proposer_loop` task, permanently terminating output-root proposal generation for that chain without any visible top-level error.
