### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing tenant-attribution forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value used to identify the tenant that "owns" the webhook is read from an HTTP header that is never included in the signed data. This breaks the binding *bytes verified == bytes acted on*: the signature authenticates the body, but the shop attribution consumed by the handler comes from an unauthenticated header.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed string at all: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC and, if it passes, immediately forwards `request.shop` (the unauthenticated header) to the handler as the tenant identity for the event, with no separate check binding it to the signed body: [5](#0-4) 

The identity equality that should hold is:
`shop attributed to the event == shop whose secret produced the HMAC over the body`

Because `shop-domain` is excluded from `to_signable_string`, this equality is never enforced by the library. An attacker who legitimately owns/installs the app on their own shop (or who otherwise obtains one valid `(body, hmac)` pair signed with the app's real `client_secret`, e.g. from a legitimate webhook delivery to their own store) can resend the exact same body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` will still pass, since it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` object claiming the payload came from the victim shop.

### Impact Explanation
This crosses a tenant boundary within the gem's own webhook-processing pipeline: the value the library asserts as "the shop this webhook is for" is not cryptographically bound to the payload it just validated. Any host application that trusts `WebhookMetadata#shop`/`request.shop` as an authenticated tenant identifier (which is the documented purpose of this field, since it comes from `Registry.process` right after HMAC validation succeeds) can be made to attribute attacker-supplied data to a different, victim tenant — a cross-tenant data-integrity/confusion issue reachable by any unprivileged party who can trigger delivery of at least one legitimate webhook to their own shop (e.g., by installing the app), matching the "Critical - cross-tenant access" impact category, since the trust boundary the HMAC is meant to enforce (this webhook truly belongs to shop X) is bypassed for the shop field.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to first obtain one valid `(raw_body, hmac)` pair generated with the app's real secret. The simplest path is installing the app on an attacker-controlled shop and capturing a real webhook delivery — an action available to any unprivileged internet user with no special credentials, satisfying the "unprivileged internet user" threat model. The attacker never needs `api_secret_key`, an access token, or any other credential; they only replay bytes that were already legitimately signed for their own store while forging the shop header.

### Recommendation
Include the shop-domain (and ideally the webhook `topic`/`api_version`/`webhook_id`) as part of the signed material that `to_signable_string` produces, or otherwise cryptographically bind the asserted `shop` to the verified body before it is handed to `WebhookMetadata`/the handler in `Registry.process`. At minimum, document and/or enforce that `request.shop` must not be treated as authenticated on its own, and consider validating it against a known/expected shop from the caller's own session store before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., updates a product), causing Shopify to POST a signed webhook with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the real `client_secret`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this `(B, H)` pair.
3. Attacker resends a POST to the app's webhook endpoint with the same body `B`, same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (= `B` only) — the check passes because `H` is a valid signature for `B`: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, even though nothing about the request was ever validated against the victim shop.
