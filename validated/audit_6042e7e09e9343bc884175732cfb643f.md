### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header. `Utils::HmacValidator.validate` verifies only the body against the HMAC, never binding the `shop` header to that signature. `Webhooks::Registry.process` then forwards this unauthenticated `shop` value directly to the app's handler as the tenant identity.

### Finding Description
`HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just `@raw_body`, completely excluding all headers: [2](#0-1) 

`shop` is derived independently from the `shop-domain` header: [3](#0-2) 

`Registry.process` validates only the HMAC-over-body, then trusts `request.shop` (an unsigned header) as the tenant identity passed into the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop bound by HMAC == shop delivered to handler`. Instead the code enforces `body bound by HMAC == body delivered to handler`, and separately trusts `shop header == shop delivered to handler` with no cryptographic tie between the two. This is the same class of defect as the reported `LiquidityPool.withdraw()` bug: a value used to make a security decision (`shop`/tenant identity) is disjoint from the value actually protected by the check (`raw_body`).

Critically, `Context.api_secret_key` is a single, app-wide secret shared across **all** shops that install the app — it is not shop-specific. So any merchant who installs the app receives genuine `(raw_body, hmac)` pairs valid under that same shared secret. Since the shop header isn't part of the signed material, an attacker who is a legitimate (even free/trial) installer of the app can:

1. Capture a real webhook delivery to their own endpoint: a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with an arbitrary victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looks at the header).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with the attacker-chosen victim shop domain.

### Impact Explanation
This lets an unprivileged app installer inject webhook events that the host application will attribute to an arbitrary, victim shop — a cross-tenant identity confusion carrying the app's own (shared) HMAC credential as apparent "proof of authenticity." The gem's own documentation instructs consumers to trust `data.shop` directly (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`), so this is not a case of the host ignoring the documented API — it is following it as designed while the gem fails to bind the identity field to the signature.

### Likelihood Explanation
Any actor able to install the app on a shop (which for public/embedded Shopify apps can be effectively any Shopify user) can obtain a valid `(raw_body, hmac)` pair from their own legitimate webhook deliveries and immediately replay it with a forged `shop-domain` header against the shared public webhook endpoint. No access to `api_secret_key`, access tokens, or TLS interception is required.

### Recommendation
Include the shop-domain header (and other identity-bearing headers such as `topic`) in the signed/verified material for webhook requests, or otherwise cryptographically bind `shop` to the HMAC before it is surfaced via `WebhookMetadata`. Alternatively, validate `request.shop` against an independently trusted source (e.g. a known/registered shop for that webhook subscription) rather than trusting the header verbatim.

### Proof of Concept
```ruby
# Attacker owns Shop A and receives a legitimate webhook:
raw_body = '{"id":123}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), shared_api_secret_key, raw_body)

# Attacker replays it against the same public endpoint, spoofing Shop B:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # still valid, body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...)
