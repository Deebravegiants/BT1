Audit Report

## Title
Bridge and External Initiator outgoing authentication tokens disclosed to view-only API users via `GET /v2/bridge_types` and `GET /v2/external_initiators` - (File: core/web/presenters/bridges.go, core/web/presenters/external_initiators.go)

## Summary
`BridgeResource.OutgoingToken` and `ExternalInitiatorResource.OutgoingToken` lack `omitempty`/redaction and are unconditionally populated from the persisted `OutgoingToken` secret on every read, unlike `IncomingToken`, which is intentionally redacted (`omitempty`) after initial creation. Because `GET /v2/bridge_types`, `GET /v2/bridge_types/:name`, and `GET /v2/external_initiators` are all reachable by the lowest-privilege `UserRoleView` role, any authenticated view-only API user can retrieve these outgoing secret tokens for every configured bridge and external initiator.

## Finding Description
`NewBridgeResource` copies `bridge.OutgoingToken` into the JSONAPI response unconditionally: [1](#0-0)  The `Index` and `Show` controller actions call this constructor directly for list/detail responses without any redaction or role check inside the presenter layer: [2](#0-1)  The token itself is a persisted secret generated via `utils.NewSecret(24)`, used to authenticate the node's outgoing calls to an external adapter: [3](#0-2)  By contrast, `IncomingToken` is explicitly marked `omitempty` and is only ever populated in the `Create` handler's response (`resource.IncomingToken = bta.IncomingToken`), never on `Index`/`Show`/`Update`/`Destroy`, showing the codebase's own established convention that this class of secret should not be returned on read paths. `OutgoingToken` breaks that convention.

The route-level RBAC test table confirms `GET /v2/bridge_types`, `GET /v2/bridge_types/:name`, and `GET /v2/external_initiators` are all marked `viewOnlyAllowed: true`, and `TestRBAC_Routemap_ViewOnly` asserts that a `UserRoleView` client does not receive `Unauthorized`/`Forbidden` for these routes: [4](#0-3) [5](#0-4)  The same unconditional exposure pattern exists in the GraphQL resolver, `BridgeResolver.OutgoingToken()`, and in `ExternalInitiatorResource`.

## Impact Explanation
A user granted only the `view` role (the lowest permission level, intended for read-only/monitoring access) can retrieve the `OutgoingToken` secret for every configured bridge and external initiator without any edit/admin privileges. This is a genuine secret/credential disclosure to an under-privileged role: possession of the outgoing token could let a lower-privileged authenticated user impersonate the node's outgoing callback authentication toward the external adapter/initiator, which maps to an in-scope key/secret exfiltration or authentication/role-bypass impact.

## Likelihood Explanation
This requires only an authenticated API caller holding a `view`-role token/session — a documented, intended, low-trust role that Chainlink operators commonly grant to monitoring/read-only users. No host access, database access, or admin credentials are needed, and the RBAC test suite itself demonstrates that `view` role callers can successfully hit these exact endpoints. The exploit path is a plain unprivileged (relative to bridge/EI secrets) authenticated GET request, fully reproducible.

## Recommendation
Apply the same redaction convention already used for `IncomingToken`: mark `OutgoingToken` as `json:"outgoingToken,omitempty"` in both `BridgeResource` and `ExternalInitiatorResource`, and only populate it in the `Create` response path (as done for `IncomingToken` in `bridge_types_controller.go`), not in `Index`/`Show`/`Update`/`Destroy` responses. Apply the equivalent fix to the GraphQL `BridgeResolver.OutgoingToken()` resolver. Alternatively, gate `OutgoingToken` visibility in read responses to `admin`/`edit` roles only.

## Proof of Concept
1. As an admin/edit user, `POST /v2/bridge_types` to create a bridge; capture the returned `attributes.outgoingToken`.
2. Authenticate as a user with `sessions.UserRoleView` (or an API token restricted to that role).
3. Call `GET /v2/bridge_types/<name>` (or `GET /v2/bridge_types`) with the view-role credentials.
4. Observe the response body's `attributes.outgoingToken` field returns the same plaintext secret from step 1, despite the caller holding only view-level access — confirmed reachable per the `viewOnlyAllowed: true` entries and `TestRBAC_Routemap_ViewOnly` test in `core/web/auth/auth_test.go`.
5. Repeat with `GET /v2/external_initiators` to confirm the same disclosure for `ExternalInitiatorResource.OutgoingToken`.
