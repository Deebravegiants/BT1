### Title
Webhook shop/topic spoofing via header-body signature decoupling — `HmacValidator` only signs `@raw_body`, not `shop`, `topic`, or `webhook_id` (`lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Registry.process` builds `WebhookMetadata` from `request.topic`, `request.shop`, and `request.webhook_id` — values pulled straight from HTTP headers that are never part of the HMAC-covered string [2](#0-1) . An attacker who obtains one genuinely Shopify-signed `(body, hmac)` pair for their own shop's webhook can replay that exact body/hmac to the app's webhook endpoint with forged `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers, and `HmacValidator.validate_signature`'s `OpenSSL.secure_compare` will still pass because it only re-derives the HMAC over the body [3](#0-2) .

### Finding Description
The binding the code implicitly assumes is: `valid_hmac(body) == authentic(shop, topic, webhook_id, body)`. In reality `HmacValidator.validate_signature` only proves `HMAC(secret, verifiable_query.to_signable_string) == received_signature` [3](#0-2) , and for `Webhooks::Request`, `to_signable_string` equals `@raw_body` alone [1](#0-0) . Meanwhile `topic`, `shop`, `webhook_id`, and `api_version` are read directly out of attacker-controllable HTTP headers via `shopify_header` [4](#0-3) [5](#0-4) .

`Registry.process` trusts these header-derived fields as authenticated once `HmacValidator.validate` returns true: it passes `topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id` into `WebhookMetadata`, which is handed to the app's registered `handler.handle` [2](#0-1) . Because `secure_compare` never inspects those header values, an attacker can:
1. Install the app on a development shop they control, register their own webhook handler, and capture one legitimate `(raw_body, X-Shopify-Hmac-SHA256)` pair delivered by Shopify.
2. Send an HTTP POST directly to the victim app's public webhook endpoint using the same `raw_body` and `hmac`, but with `shopify-shop-domain: victim-shop.myshopify.com`, and/or `shopify-topic` set to any topic the app has registered a handler for (e.g. `app/uninstalled`, `shop/redact`).
3. `HmacValidator.validate` recomputes `HMAC(secret, raw_body)`, which is unchanged and still matches, so the request is accepted as authentic [6](#0-5) .
4. `Registry.process` looks up the handler for the forged `topic` and invokes it with `shop: request.shop` set to the forged victim domain [2](#0-1) .

No existing guard closes this gap: `HmacValidator.validate` only checks the digest [6](#0-5) ; there is no comparison of `request.shop` against a known/installed shop, and no binding of `topic`/`webhook_id` into the signed payload. This differs from `AuthQuery#to_signable_string`, which does include `code`, `host`, `shop`, `state`, and `timestamp` in the signed string [7](#0-6) , so the OAuth callback path is not vulnerable to this specific coverage gap — the flaw is isolated to the webhook path.

### Impact Explanation
An attacker who has ever received one legitimate webhook (trivially obtainable by installing the app on their own free/dev shop) can forge the `shop` and `topic` claims presented to any handler registered via `Registry.add_registration`, for arbitrary victim shops, repeatably and at will. This is a cross-tenant authenticity bypass: the app is led to believe an authenticated, Shopify-originated event occurred for a shop/topic the attacker never controls. Depending on what the app's handlers do with `WebhookMetadata#shop`/`#topic` (e.g. GDPR redact handlers, uninstall cleanup, inventory sync), this can cause unauthorized data deletion, incorrect session/token invalidation, or corrupted state for a victim tenant — matching the "cross-tenant access" / "Critical - authentication bypass" category, since a value the app treats as authenticated (`shop`, `topic`) is not actually covered by the signature.

### Likelihood Explanation
Preconditions are minimal: the app must use `Webhooks::Registry.process` as documented (the intended usage), and the app's webhook endpoint must be reachable over the internet (true for any Shopify webhook receiver). The attacker only needs to install the app once on a shop they control to obtain one valid `(body, hmac)` pair — no secret, token, or victim credential is required. The attack is trivially repeatable against any topic the app has registered and any target shop string, at zero marginal cost per forged request.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header-derived field the app relies on) inside the signed content evaluated by `HmacValidator`, or independently verify `request.shop` against the set of shops actually installed/known to the app before trusting it in `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not be the sole source of truth for authenticity when downstream code (`Registry.process`) also treats header-derived `topic`/`shop`/`webhook_id` as authenticated; these should be cryptographically bound to the signature or revalidated against known-good state (e.g., confirm `shop` matches a session/shop that has an active installation) before dispatching to handlers.

### Proof of Concept
```ruby
# test/webhooks/registry_forgery_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryForgeryTest < Test::Unit::TestCase
      def setup
        super
        @secret = ShopifyAPI::Context.api_secret_key
        @body = '{"id":1,"note":"legit webhook for attacker-shop"}'
        @hmac_b64 = Base64.strict_encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), @secret, @body)
        )

        handled = []
        handler = Class.new do
          define_method(:handle) { |data:| handled << data }
        end.new
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "app/uninstalled", delivery_method: :http, path: "/webhooks",
          handler: handler,
        )
        @handled = handled
      end

      def test_forged_shop_and_topic_pass_validation
        # Attacker's genuinely-signed body/hmac from their own shop's webhook,
        # replayed with forged headers claiming a different shop and topic.
        forged_headers = {
          "shopify-topic" => "app/uninstalled",
          "shopify-hmac-sha256" => @hmac_b64,
          "shopify-shop-domain" => "victim-shop.myshopify.com",
          "shopify-webhook-id" => "forged-id",
          "shopify-api-version" => "2024-01",
        }
        request = ShopifyAPI::Webhooks::Request.new(raw_body: @body, headers: forged_headers)

        # BINDING UNDER TEST:
        # HmacValidator.validate(request) == true
        # even though request.shop / request.topic were never part of to_signable_string
        assert(ShopifyAPI::Utils::HmacValidator.validate(request))

        ShopifyAPI::Webhooks::Registry.process(request)
        assert_equal("victim-shop.myshopify.com", @handled.first.shop)
      end

      def test_encoding_is_irrelevant_to_verification
        utf8_body = @body.dup.force_encoding(Encoding::UTF_8)
        binary_body = @body.dup.force_encoding(Encoding::ASCII_8BIT)
        headers = {
          "shopify-topic" => "app/uninstalled",
          "shopify-hmac-sha256" => @hmac_b64,
          "shopify-shop-domain" => "any-shop.myshopify.com",
          "shopify-webhook-id" => "id",
          "shopify-api-version" => "2024-01",
        }
        req_utf8 = ShopifyAPI::Webhooks::Request.new(raw_body: utf8_body, headers: headers)
        req_bin = ShopifyAPI::Webhooks::Request.new(raw_body: binary_body, headers: headers)

        assert_equal(
          ShopifyAPI::Utils::HmacValidator.validate(req_utf8),
          ShopifyAPI::Utils::HmacValidator.validate(req_bin),
        )
      end
    end
  end
end
```
Both assertions demonstrate the gap: (1) `shop`/`topic` forged in headers are accepted as authenticated because they lie outside `to_signable_string`; (2) verification verdict depends only on raw bytes of the body, confirming the signature's coverage is strictly narrower than what downstream code treats as authenticated.
