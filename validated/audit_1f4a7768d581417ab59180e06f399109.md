Based on my investigation, I found a concrete analog in the `hyper-fungible-token` pallet's `on_accept` handler.

### Title
Cross-chain calldata execution as the sender's derived account permits arbitrary runtime call dispatch on token transfer with unauthenticated origin fallback - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The CVE describes Kata Containers executing attacker-supplied binaries specified via untrusted annotations without validation. The closest reachable analog in this codebase is `HyperFungibleToken::on_accept`, which decodes an ISMP `PostRequest` body into a `Message` containing an arbitrary `data` field, then — when no signature is supplied — dispatches an arbitrary `T::RuntimeCall` using an origin *derived directly from the attacker-controlled `message.from` field*, rather than from any independently verified identity.

### Finding Description
In `on_accept`, after minting/transferring the bridged token, optional calldata is executed [1](#0-0) . If no `signature` is present in the `SubstrateCalldata`, the origin used to dispatch the call is derived purely from `message.from`/`message.to` bytes present in the message body itself: [2](#0-1) 

This `from` value is part of the ABI-decoded `Message` body — data supplied by whoever calls the paired ERC20/bridge contract on the source chain, not a value independently authenticated by ISMP's proof/consensus layer (which only proves that *some* message was sent by the registered `ContractToAsset` source contract, not that `message.from` correctly identifies the real token sender). The only gate on the dispatched call is the runtime's `BaseCallFilter`: [3](#0-2) 

The `BaseCallFilter` check is a generic, chain-wide policy filter (e.g., blocking calls during maintenance mode) — it does not validate that the calling account should be able to invoke the specific dispatchable being requested. Since the signature is optional and, when omitted, the origin is taken verbatim from message-embedded bytes, any unprivileged caller that can trigger a `PostRequest` through a registered source contract can effectively impersonate an arbitrary Substrate/EVM-derived account and get the runtime to execute any dispatchable that account is nominally authorized to call — including transfers, approvals, or other state-mutating calls from that beneficiary account.

### Impact Explanation
An unprivileged relayer or token bridger can craft a cross-chain message whose `data` field encodes a `RuntimeCall` while setting `message.from` to any 20/32-byte value. Since no signature is required, this allows dispatching calls "as" the corresponding derived account without proof that entity actually authorized it, causing unauthorized app actions and potential asset movement (e.g., forcing spend/approval-style calls) attributable to victims who never signed anything for that specific action. This maps to "unauthorized app action" / theft of funds category from the validation criteria.

### Likelihood Explanation
The path is reachable from a single cross-chain token transfer message dispatched by any account holding a registered bridge contract mapping (`ContractToAsset`), and requires no privileged access. The signature-based path is optional, so an attacker can simply omit it and rely on the "from"-derived origin fallback, making exploitation straightforward once the message reaches `on_accept`.

### Recommendation
Require the `signature` field to always be present and verified for any dispatched `runtime_call`, removing the unauthenticated "derive origin directly from `message.from`" fallback path, or restrict the unsigned fallback to a narrowly scoped, harmless subset of calls (e.g., only allow it for actions the beneficiary is already implicitly entitled to receive, such as deposits) rather than arbitrary `T::RuntimeCall` dispatch.

### Proof of Concept
1. Attacker controls (or is) a registered source contract mapped via `ContractToAsset` for some `local_asset_id`.
2. Attacker sends a `PostRequest` whose ABI-encoded body decodes to a `Message` with `to` = victim's beneficiary bytes, `from` = victim's account bytes (no real authorization from victim), and `data` containing `SubstrateCalldata { signature: None, runtime_call: <arbitrary encoded call> }`.
3. `on_accept` mints/transfers the bridged amount, then reaches the `else` branch at [4](#0-3) , converting `from_bytes` into an origin account without any signature check.
4. The pallet dispatches `runtime_call` with `RawOrigin::Signed(origin)` at [5](#0-4) , executing arbitrary logic as that account, subject only to the generic `BaseCallFilter`.

*Note: I was unable to fully trace the EVM-side `HyperFungibleToken.sol` contract's `Message.from` construction within available search results (content not returned by the index), so I cannot definitively confirm whether the EVM contract independently constrains `from` to always equal `msg.sender` at encoding time. If it does enforce `from == msg.sender` on the EVM side, the severity of this finding is substantially reduced, since an attacker could then only impersonate themselves. This should be verified directly against `HyperFungibleToken.sol`'s `teleport`/dispatch function before treating this as fully confirmed.*
