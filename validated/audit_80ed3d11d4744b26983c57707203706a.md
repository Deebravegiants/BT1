### Title
Webhook HMAC only signs the request body, not the `shop`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` authenticates nothing but the JSON payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which `Registry.process` trusts as the tenant identity for the webhook — are never covered by the HMAC. An attacker who has legitimately received one valid `(body, hmac)` pair for the shared app secret (e.g. by installing the app on their own store and capturing the callback) can replay that exact body/HMAC while forging the `shop-domain` header to impersonate a different merchant, since the signature check never binds body-to-shop.

### Finding Description
The webhook verification pipeline is:
1. `Request#hmac` decodes the `hmac-sha256` header. [1](#0-0) 
2. `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from unauthenticated HTTP headers. [2](#0-1) 
3. `Request#to_signable_string` — the bytes that are actually HMAC-verified — is defined as just the raw body: [3](#0-2) 
4. `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`, using only that signable string. [4](#0-3) 
5. `Registry.process` calls `HmacValidator.validate(request)` (body-only check) and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, handing it to the app's handler as trusted tenant/event identity: [5](#0-4) 

The documented contract explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and shows it being used to key application state (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), i.e. the gem presents `shop` as an authenticated identity field, but it never binds `shop` into the signature. [6](#0-5) 

The identity binding that should hold is:
`shop header value == shop the HMAC actually authenticates`

But the HMAC authenticates nothing about `shop` (or `topic`/`webhook_id`) — it authenticates only `raw_body` under the app's shared `client_secret`. Because the same `client_secret` is used to sign webhooks for every shop that has the app installed, any party who has obtained one valid `(body, hmac)` pair — trivially available to any merchant that installs the app themselves and inspects the raw callback it receives — can resend that identical body/HMAC pair to the app's webhook endpoint with an arbitrary forged `shop-domain` (and `topic`/`webhook-id`) header. `HmacValidator.validate` will still return `true` because it never looks at those headers, and `Registry.process` will happily hand the forged shop/topic to the handler as if it were an authentic event for that other tenant.

### Impact Explanation
This breaks the shop-identity binding the gem is supposed to provide via HMAC verification and lets an unprivileged actor (any merchant who installs the app once) inject payloads that the app processes under an arbitrary, attacker-chosen shop identity — i.e., cross-tenant event/data injection using only a body they already legitimately have. This maps to the Critical "cross-tenant access" category: the app's downstream per-shop logic (order/inventory sync, billing state, webhook_id dedupe, etc.) can be corrupted for a tenant the attacker does not control, using data that was never signed for that tenant.

### Likelihood Explanation
Exploitation requires only: (a) install the app once on an attacker-controlled shop (a normal unprivileged action, or simply intercepting one's own installed app's webhook traffic), (b) capture one `(raw_body, hmac)` pair from a real webhook delivered to that shop, and (c) POST that identical body + hmac to the app's webhook endpoint with a different `shop-domain`/`topic`/`webhook-id` header. No access to the app's `client_secret`, no privileged account, and no host-application misuse is required — the vulnerability is entirely inside `Webhooks::Request`/`HmacValidator`/`Registry.process` as shipped.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material — e.g. by changing `Request#to_signable_string` to canonicalize and include these header values alongside the body — or have `Registry.process` independently verify `request.shop` against the shop stored for the session/webhook_id before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `{"id":1}"`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker resends the exact same body and `hmac-sha256` value to the app's public webhook endpoint, but swaps the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Webhooks::Request.new(raw_body: body, headers: forged_headers)` is constructed; `to_signable_string` still returns the same `raw_body`. [3](#0-2) 
4. `Registry.process(request)` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unchanged from step 1 — and passes. [7](#0-6) 
5. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: request.topic, body: request.parsed_body, ...)` is built and delivered to the host app's handler, which acts on `data.shop == "victim-shop.myshopify.com"` even though the payload was never signed for that shop. [8](#0-7)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
