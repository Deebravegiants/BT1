Based on my investigation, I found a directly analogous pattern in `EvmHost.sol`.

### Title
Native-token dispatch fee payments are swapped through UniswapV2 without a user-supplied minimum output / slippage limit - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost` accepts native-token payment for dispatch fees and internally swaps the native token for the `feeToken` via a configured `UniswapV2Router02` (`_hostParams.uniswapV2`) [1](#0-0) . As documented, "the Hyperbridge protocol ultimately collects its fees in the `feeToken`... but it can also accept native token payments, which are automatically swapped for the `feeToken` using the local AMMs like Uniswap" [2](#0-1) . This is structurally identical to the FraxPoolV3 `mintFrax` bug class: an amount that a user is charged (or receives) is dynamically computed from a live, manipulable/movable price (the AMM pool reserves) at execution time, with no caller-supplied bound on acceptable slippage.

### Finding Description
Any unprivileged caller dispatching an ISMP POST/GET request and paying the relayer/protocol fee with native tokens (`msg.value`) triggers a swap on `uniswapV2` from native token to `feeToken` inside `EvmHost`. Unlike `mintFrax`, this swap's output (the amount of `feeToken` credited from the user's native payment) depends on the pool's exchange rate at the exact block of execution. If the dispatch call is analogous to `mintFrax` in that it lacks a `maxIn`/`minOut`-style protection parameter enforced by the swap call (e.g. `amountOutMin`), a user's transaction can execute against a moved/manipulated price — via normal market movement or MEV sandwich attacks against the local UniswapV2 pool — resulting in far fewer `feeToken` units credited (and the dispatch failing to have sufficient fee, or the excess being lost) than the user expected when they signed the transaction.

I was not able to fully confirm within the available tool budget whether the internal `swapExactETHForTokens` call passes a non-zero, caller-supplied `amountOutMin` — this would need to be verified directly in `EvmHost.sol`'s dispatch/fee-handling function before treating this as more than an analog hint.

### Impact Explanation
If the swap lacks a user-enforced slippage bound, an attacker can sandwich a victim's dispatch transaction on the local UniswapV2 pool, extracting most of the native-token value the victim intended to convert to fee tokens — a direct loss of user funds reachable from a single unprivileged dispatch transaction, matching the "concrete theft... via a single dispatched request" bar in the validation criteria.

### Likelihood Explanation
Likelihood depends on: (1) whether `uniswapV2` is configured to point at a pool with meaningful liquidity/manipulability, and (2) confirmation that no `amountOutMin` parameter is exposed/enforced on the public dispatch path. This is plausible given the documented "automatically swapped" fee-payment design, but requires source-level confirmation of the swap call site.

### Recommendation
- Short term: Expose a `minFeeTokenOut` (or equivalent) parameter on the public dispatch functions that accept native payment, and pass it through as `amountOutMin` to the UniswapV2Router call, reverting if the swap output is below the caller's specified minimum.
- Long term: Apply the same principle to any other dynamically priced amount reachable from a single unprivileged transaction across the codebase (e.g. the IntentGateway/Simplex FX filler's overfill/venue-priced paths, which already show similar unclamped payout patterns) [3](#0-2) .

### Proof of Concept
Not fully constructible without confirming the exact swap invocation and parameters in `EvmHost.sol`'s native-fee dispatch path; recommend a Devin session with full repo access to locate the `swapExactETHForTokens`/`swapExactTokensForETH` call sites in `EvmHost.sol` and verify the `amountOutMin` argument before finalizing a PoC.
