### Title
Aurora Engine bridge computes `storage_deposit` against `auroraEngineContractId`'s storage balance but credits it to `receiver_id: proxyTokenContractId` in the proxy-token withdrawal flow - ([File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts])

### Summary
`AuroraEngineBridge.estimateWithdrawalFee` always queries `getNearNep141StorageBalance` for `args.withdrawalParams.routeConfig.auroraEngineContractId` regardless of whether `proxyTokenContractId` is set, and this `feeAmount` is fed straight into `createWithdrawIntentPrimitive`'s `storageDeposit` parameter. When `proxyTokenContractId != null`, `createWithdrawIntentPrimitive` builds an `IntentFtWithdraw` whose `receiver_id` is `proxyTokenContractId`, not `auroraEngineContractId`, but the emitted `storage_deposit` value is the shortfall computed for the wrong account.

### Finding Description
The broken equality is: the account whose NEP-141 storage balance is checked (`auroraEngineContractId`) must equal the account that the on-chain `ft_withdraw` intent will actually register storage for (`receiver_id`).

In `aurora-engine-bridge.ts`:
```
getNearNep141StorageBalance({
  contractId: tokenAccountId,
  accountId: args.withdrawalParams.routeConfig.auroraEngineContractId,
  nearProvider: this.nearProvider,
});
``` [1](#0-0) 

This is unconditional — it never branches on `routeConfig.proxyTokenContractId`. The resulting `feeAmount` (`minStorageBalance - userStorageBalance`) is returned as `underlyingFees[RouteEnum.VirtualChain].storageDepositFee` [2](#0-1) , and later passed unchanged as `storageDeposit` into `createWithdrawIntentPrimitive` in `createWithdrawalIntents`:
```
storageDeposit: getUnderlyingFee(args.feeEstimation, RouteEnum.VirtualChain, "storageDepositFee")
``` [3](#0-2) 

`createWithdrawIntentPrimitive` then, in the proxy-token branch, sets `receiver_id: params.proxyTokenContractId` while attaching that same (wrong-account) `storage_deposit` value:
```
return {
  intent: "ft_withdraw",
  token: tokenAccountId,
  receiver_id: params.proxyTokenContractId,
  ...
  storage_deposit: params.storageDeposit > 0n ? params.storageDeposit.toString() : undefined,
  ...
};
``` [4](#0-3) 

Per the intents contract schema, `storage_deposit` is explicitly documented as "make `storage_deposit` for `receiver_id` on `token`" [5](#0-4) , i.e. it must correspond to `receiver_id`, not to `auroraEngineContractId`. Since the estimate never checks `proxyTokenContractId`'s storage balance, the two can diverge in either direction:
- `auroraEngineContractId` is already registered (fee computed as `0`) while `proxyTokenContractId` is not registered on `tokenAccountId` → no `storage_deposit` is attached, and the resulting `ft_transfer_call`/`ft_transfer` to the unregistered `receiver_id` can fail. The schema explicitly warns: "NOTE: No refund will be made in case of insufficient `storage_deposit` on `token` for `receiver_id`" [6](#0-5) , meaning the withdrawn tokens can be lost with no on-chain recovery path.
- `auroraEngineContractId` needs storage (nonzero fee charged and quoted from the user) while `proxyTokenContractId` is already registered → the user is charged/quoted an unnecessary storage fee that doesn't correspond to any real registration need for the actual receiver.

None of the existing guards (`validateWithdrawal`, `supports()`, `FeeExceedsAmountError`, `getUnderlyingFee`, contract-side signature/nonce checks) validate that the storage-balance account matches `receiver_id`; they only validate the destination EVM address format and fee/quote bounds.

### Impact Explanation
This affects the amount actually debited/registered on-chain for a "Flow for transferring a base token to a virtual chain with a non-standard (non-ETH) base token" withdrawal (i.e., any withdrawal using `createVirtualChainRoute(auroraEngineContractId, proxyTokenContractId)` with a non-null `proxyTokenContractId`). It is not attacker-privileged in the sense of stealing other users' funds directly, but it does cause the withdrawing user's own funds to be at risk of being sent with no valid storage registration for the true receiver, and per the contract's own documentation such a failure is **not refunded**. This falls in the "funds delivered/registered against the wrong account with potential loss and no recovery" category. It reoccurs on every proxy-token virtual-chain withdrawal where the storage state of `auroraEngineContractId` and `proxyTokenContractId` on `tokenAccountId` diverge.

### Likelihood Explanation
Preconditions: an integrator/user must use `createVirtualChainRoute` with a non-null `proxyTokenContractId` (this is a legitimate, documented use case for "non-ETH base token" virtual chains, not an attacker escape hatch) and the storage-registration states of `auroraEngineContractId` vs `proxyTokenContractId` on the token contract must differ at withdrawal time — a state fully controllable/observable by anyone since NEP-141 storage registration is a normal, permissionless on-chain state. No special privilege is required; this triggers on ordinary use of the documented non-standard-decimals virtual-chain flow.

### Recommendation
In `AuroraEngineBridge.estimateWithdrawalFee`, query `getNearNep141StorageBalance` for the account that will actually be `receiver_id` in the withdraw intent — i.e., `routeConfig.proxyTokenContractId ?? routeConfig.auroraEngineContractId` — instead of unconditionally using `auroraEngineContractId`.

### Proof of Concept
```ts
// aurora-engine-bridge.test.ts
it("estimateWithdrawalFee checks storage balance of the actual receiver (proxyTokenContractId), not auroraEngineContractId", async () => {
  const bridge = new AuroraEngineBridge({ envConfig, nearProvider: mockProvider });

  // Mock: auroraEngineContractId IS registered (0 shortfall)
  // proxyTokenContractId is NOT registered (shortfall = minStorageBalance)
  mockGetNearNep141MinStorageBalance.mockResolvedValue(1250000000000000000000n);
  mockGetNearNep141StorageBalance.mockImplementation(({ accountId }) => {
    if (accountId === "aurora-engine.near") return Promise.resolve(1250000000000000000000n); // registered
    if (accountId === "proxy-token.near") return Promise.resolve(0n); // NOT registered
    throw new Error("unexpected accountId");
  });

  const fee = await bridge.estimateWithdrawalFee({
    withdrawalParams: {
      assetId: "nep141:wrap.near",
      routeConfig: createVirtualChainRoute("aurora-engine.near", "proxy-token.near"),
    },
  });

  // Left side of equality: shortfall for the account actually checked (auroraEngineContractId) = 0
  // Right side: shortfall for the account actually credited (proxyTokenContractId, receiver_id) = 1250000000000000000000n
  // Current code returns storageDepositFee = 0n, which is WRONG for receiver_id = proxy-token.near
  expect(fee.underlyingFees[RouteEnum.VirtualChain].storageDepositFee).toBe(0n); // demonstrates the bug: should be 1250000000000000000000n
});
```
This demonstrates that the `storage_deposit` charged in `createWithdrawIntentPrimitive` (derived from this `storageDepositFee`) does not equal the true storage shortfall for `receiver_id: proxyTokenContractId`, breaking the required equality between the account checked and the account credited.
