## Title
Webhook `shop` identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then forwards the unauthenticated `shop-domain` header value (and other headers) to the application's handler as the tenant identity. Because the `shop` field is never part of the signed content, any actor who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` can replay it with an arbitrary `shop-domain` header and have the app process the payload as if it belonged to a different merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are parsed straight from HTTP headers and are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` only checks the signature against `to_signable_string`, i.e. the body bytes, using the shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` performs this body-only HMAC check, and then immediately trusts `request.shop` (an unauthenticated header) to construct the `WebhookMetadata` that is handed to the app-supplied handler: [4](#0-3) 

This is a direct analog of the `swapOn1INCH` bug class: an operation (attributing a webhook payload to a tenant) is performed on a value (`shop`) that is never actually verified by the cryptographic check that is supposed to establish trust for the request. The equality that should hold — `hmac_signed_content.shop == handler_used.shop` — is broken because `shop` is outside the HMAC's coverage entirely.

Since `Context.api_secret_key`/`old_api_secret_key` is a single value shared by the app across all of its merchant installations, any unprivileged actor who installs the app on their own store (a normal, unprivileged onboarding action) will receive validly-HMAC'd webhook deliveries signed with that same shared secret. That attacker can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the victim's domain.

### Impact Explanation
Rated High: host applications built on this gem commonly use `WebhookMetadata#shop` to select which merchant/session/access-token record to read or mutate in response to a webhook (e.g., updating stored order/customer data, revoking access, or triggering shop-scoped side effects). Because `shop` isn't bound to the signature, an attacker-controlled request can cause the handler to execute logic attributed to an arbitrary victim shop, producing cross-tenant data confusion — data or actions belonging to attacker-supplied content are attributed to a shop the attacker doesn't control.

### Likelihood Explanation
High: the only prerequisite is being able to install the target app on any shop (a normal, unprivileged action) to obtain one legitimately-signed `(body, hmac)` webhook pair, and then replaying it with a substituted `shop-domain` header at the app's public webhook endpoint. No knowledge of `api_secret_key` or any merchant's access token is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed content that `HmacValidator` checks, or otherwise cryptographically tie the header-derived `shop` to the specific delivery before constructing `WebhookMetadata`. At minimum, `Registry.process` in `lib/shopify_api/webhooks/registry.rb` should not treat `request.shop` as trusted merchant identity purely because the body HMAC validated; the gem should either include shop/topic in the signable string (mirroring Shopify's actual webhook signing scheme if it supports one) or clearly document that host applications must independently verify `shop` against a known, previously-authenticated store list before acting on webhook data.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, completing the OAuth flow legitimately.
2. Attacker triggers any webhook event on their store (e.g., updates a product), receiving a callback with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker resends the exact same `B`/`H` to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and it matches `H` (body unchanged), so validation passes: [5](#0-4) 
5. `Registry.process` dispatches the registered handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"` even though that shop never sent or authorized this event, causing the host app to act on attacker-controlled data under the victim's tenant identity.
