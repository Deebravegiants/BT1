### Title
Webhook `shop` field is trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the `shop`, `topic`, `webhook_id`, and `api_version` values (all sourced from unauthenticated HTTP headers) are never part of the signed material. The handler is still invoked with `data.shop` taken straight from the header, and host apps are documented to key their tenant/session lookup off that value.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field via `OpenSSL.secure_compare` [1](#0-0) . For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors are all pulled from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are not included in this signable string [3](#0-2) .

`Registry.process` only checks the HMAC over the body and then dispatches to the handler using the unauthenticated `request.shop` value with no additional binding check: [4](#0-3) 

The documented contract explicitly tells host apps to trust `data.shop` as "The shop domain of the webhook" and use it to key their per-tenant work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) 

The broken identity binding is:
`shop_bound_by_hmac (∅, not signed) != shop_used_by_handler (request.shop header)`

Because a single `api_secret_key` is shared across all shops that install the same app, any unprivileged internet user who can install the app on their own store (a normal, unprivileged action any merchant can take) receives genuinely Shopify-signed webhooks for their own shop. Since the signature only covers the JSON body, and many webhook bodies for a given topic are shop-agnostic or attacker-controlled (the attacker's own shop generates the body, e.g. by creating an order with attacker-chosen content), the attacker can replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with the victim's shop domain. `HmacValidator.validate` will pass (it only checks the body/secret), and the handler will be invoked believing the data belongs to the victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker-controlled, Shopify-signed payload can be attributed to an arbitrary victim shop domain purely by forging an HTTP header, since that header is outside the cryptographic envelope. Any host application that follows the documented pattern (using `data.shop` to select the tenant/session, queue keys, or database records to update) can be made to process attacker-supplied data under the identity of another merchant — a cross-tenant access primitive per the rules' Critical impact bucket.

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the attacker needs their own or any legitimately-installed shop to generate/receive a real, signed webhook (trivial and unprivileged — any user can install a public app or use a dev store), and (2) the impact is fully realized only insofar as the host application's handler logic trusts `data.shop` for tenant-scoping without independently cross-checking the shop against something authenticated (e.g., an existing OAuth session/access token for that shop, which is a separate call). The gem's own webhook-processing surface (`Registry.process`) performs no such secondary binding check, and its documentation encourages using `data.shop` directly, so the vulnerable pattern is the natural, intended usage rather than a misuse of undocumented behavior.

### Recommendation
Bind the tenant identity into the signed material or otherwise cryptographically verify it before handing `shop` to the handler:
- Cross-check `request.shop` against a known/authorized shop for the webhook's `webhook_id` (Shopify does not sign headers, so this cannot be fixed purely by re-including headers in the HMAC string; the gem should document/enforce that callers must verify `data.shop` corresponds to a registered session for that shop before trusting it), or
- Have `Registry.process` require and verify the shop against `ShopifyAPI::Auth::Session`/token storage prior to dispatch, rather than passing the raw header value through untouched.
- At minimum, strengthen documentation in `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not authenticated by the HMAC and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (a normal, unprivileged flow) and configures a webhook subscription for a topic whose body content is attacker-influenced (e.g., `orders/create` with attacker-chosen line-item text/note fields).
2. Shopify sends a legitimately HMAC-signed webhook request to the app's callback endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, body: attacker-controlled JSON.
3. Attacker captures this request and replays it to the same endpoint, only replacing the `x-shopify-shop-domain` header with `victim.myshopify.com` (or `x-shopify-topic`/`x-shopify-webhook-id` if desired) while keeping the exact same raw body and `hmac` value untouched.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` [6](#0-5) [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` is `"victim.myshopify.com"`, despite the payload originating from and being signed for the attacker's own shop [4](#0-3) .
6. Any host application logic that keys tenant-scoped work off `data.shop` (as shown in the gem's own documented example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) now processes attacker-controlled data under the victim shop's identity [8](#0-7) .

          received_signature = verifiable_query.hmac

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
