### Title
Overflow before borrow-index cap permanently freezes a high-value market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Interest accrual unscales the full scaled borrow and supply balances before applying `MAX_BORROW_INDEX_RAY`; once a very large market's index is high enough, `scaled_to_original` overflows and every state-changing operation on that market reverts. [1](#0-0) [2](#0-1) 

### Finding Description
`global_sync` runs before pool mutations and splits elapsed time only into bounded chunks; each chunk calls `accrue_step`. [3](#0-2)  `accrue_step` first computes `borrowed * borrow_index` and `supplied * supply_index` to derive utilization, so the multiplication can exceed `i128` before the separately capped borrow index is ever updated. [4](#0-3)  The cap protects the index value itself, not the scaled-share-to-value conversion used for utilization. [2](#0-1) 

The repository has a direct regression test for this condition: a one-billion-token, 18-decimal market at 98% utilization eventually makes `update_indexes` fail with `MATH_OVERFLOW`, while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [5](#0-4)  The same test proves that subsequent withdrawals and repayments revert because they must accrue first. [6](#0-5) 

### Impact Explanation
Once this state is reached, the affected market is permanently unusable rather than merely returning an unsafe price or rejecting one bad input. [7](#0-6)  Suppliers cannot withdraw, borrowers cannot repay, liquidations that touch the market cannot proceed, and even the permissionless `update_indexes` maintenance call cannot recover it because accrual itself panics. [8](#0-7)  This is permanent freezing of user funds and can leave debt uncollectible while the market's cash remains trapped. [9](#0-8) 

### Likelihood Explanation
An unprivileged borrower can create the precondition on a listed high-decimal market by supplying enough of the asset and borrowing at sustained high utilization, subject to that market's configured caps. [10](#0-9)  The demonstrated setup uses one billion 18-decimal tokens and 98% utilization, so exploitation is capital-intensive and requires a market configuration that permits the needed utilization, but it needs no privileged call, leaked key, oracle dishonesty, or malformed token behavior. [11](#0-10)  Ordinary accumulation can also carry an already-large, highly utilized market across the same threshold over time. [12](#0-11) 

### Recommendation
Make accrual saturate safely before any `scaled * index` value can exceed `i128`. In particular, cap or saturate the utilization inputs inside `accrue_step`, or apply the borrow-index ceiling before evaluating current-value products, while preserving ceil-valued debt for safety checks. [4](#0-3)  Add a regression test proving that `update_indexes`, `repay`, `withdraw`, and liquidation remain callable after the index reaches the configured cap or the value-representation ceiling. [13](#0-12) 

### Proof of Concept
1. On a listed 18-decimal market with caps permitting the position, an attacker calls `controller.supply(caller, 0, spoke_id, [(hub_asset, 1_000_000_000 * 10^18)])`, then supplies sufficient collateral and calls `controller.borrow(caller, account_id, [(hub_asset, 980_000_000 * 10^18)], None)`. [10](#0-9) 
2. Leave the market at sustained high utilization until index growth makes `borrowed * borrow_index` exceed `i128`. [9](#0-8) 
3. Call the permissionless `controller.update_indexes(caller, [hub_asset])`; it reverts with `MathOverflow` while the stored index is still below `MAX_BORROW_INDEX_RAY`. [14](#0-13) 
4. Attempt `controller.repay(...)`, `controller.withdraw(...)`, or a liquidation touching that market; each path first accrues and therefore hits the same overflow. [7](#0-6) [6](#0-5)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
