### Title
CatFee API key and secret are logged in plaintext at TRON client startup - (File: `tesseract/messaging/tron/src/lib.rs`)

### Summary
`TronClient::new` logs the entire `CatFeeConfig` struct — which contains the plaintext `api_key` and `api_secret` used to authenticate with the CatFee bandwidth/energy-purchasing service — to the relayer's `info`-level log/stdout whenever CatFee integration is configured. This is the same bug class as GHSA-c37v-3c8w-crq8 (zot logging an OIDC `clientsecret` at container startup): a credential intended to stay secret is unconditionally written to process logs.

### Finding Description
`CatFeeConfig` derives `Debug` with no redaction on its two secret fields: [1](#0-0) 

When a relayer operator configures TRON with `catfee_api_key` / `catfee_api_secret` (documented as "CatFee integration for purchasing energy/bandwidth"), `TronClient::new` builds the `CatFeeConfig` and immediately logs it with the `{:#?}` (pretty Debug) formatter at `info` level: [2](#0-1) 

Because `Debug` is derived automatically (not hand-written to mask fields), the pretty-printed output includes `api_key: "..."` and `api_secret: "..."` verbatim. The relayer's logging setup writes `info`-level records to stdout/stderr by default via `tracing_subscriber::fmt()`: [3](#0-2) 

In any deployment where relayer logs are captured (container logs, log aggregators, CI output, support bundles), this exposes the CatFee credentials to anyone with read access to those logs — exactly the exposure vector described in the zot advisory (secrets printed to stdout at startup).

### Impact Explanation
An attacker or any party with log-read access (log aggregation platform, container runtime, support/bug-report bundle, CI artifact) recovers the operator's CatFee `api_key`/`api_secret`. With these HMAC credentials, the attacker can impersonate the relayer operator against the CatFee service (`https://api.catfee.io`), potentially placing energy/bandwidth purchase orders billed to the operator's account, draining funds tied to that account, or disrupting the relayer's ability to submit TRON transactions (since CatFee is used to reduce TRX costs for TRON message delivery). This is a credential-exposure issue reachable by anyone the relayer's log stream reaches — matching the Medium severity and CWE-532 classification of the original advisory.

### Likelihood Explanation
Likelihood is high for any operator who enables CatFee (a documented, supported feature for TRON relayer instances) and runs the relayer under standard container/log-collection practices (Docker logs, Kubernetes log aggregation, systemd journal, etc.), which is the norm for tesseract relayer deployments as shown in the operator docs (`docker logs -f tesseract`). No attacker action against the protocol is required — the leak happens automatically on every relayer startup with CatFee configured.

### Recommendation
- Remove the `#[derive(Debug)]` blanket derive on `CatFeeConfig`, or implement a custom `Debug` that redacts `api_key` and `api_secret` (e.g., print `"***REDACTED***"` or show only a short prefix/hash).
- Change the log statement in `TronClient::new` to avoid `{:#?}` on the raw config; log only non-sensitive fields (e.g., `api_base`, `timeout`) or a masked summary.
- Apply the same review to any other config struct that logs via `{:#?}`/`{:?}` at startup (e.g., `TronConfig`, `EvmConfig.signer`) to ensure no other secret leaks through derived `Debug` output.

### Proof of Concept
1. Configure a TRON relayer chain block with `catfee_api_key` and `catfee_api_secret` set.
2. Start the tesseract relayer (`./target/release/tesseract --config=config.toml ...`) or run it via the documented Docker command (`docker run ... polytopelabs/tesseract:latest --config=/home/root/config.toml`).
3. Observe/capture stdout (`docker logs -f tesseract`) — the line `Initialized ... CatFee integration enabled: CatFeeConfig { api_key: "<value>", api_secret: "<value>", ... }` appears at `info` level, exposing both secrets in plaintext in the container/relayer logs. [4](#0-3)
