This is a genuine finding: the webhook signature covers only the body, not the shop or topic headers, breaking the binding between "the shop asserted by headers" and "the shop that was actually verified."

### Title
Webhook HMAC does not bind the shop-domain header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` checks the HMAC solely against that body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never included in the signed material, yet `Registry.process` trusts `request.shop` (parsed straight from the unauthenticated header) to attribute the webhook to a tenant.

### Finding Description
`Webhooks::Request` reads `shop`, `topic`, `webhook_id`, and `api_version` directly from HTTP headers via `shopify_header`, with no cryptographic binding to the request body: [1](#0-0) 

`to_signable_string` returns `@raw_body` only, so `Utils::HmacValidator.compute_signature` (`OpenSSL::HMAC.hexdigest(sha256, secret, signable_string)`) is computed purely over the body bytes: [2](#0-1) 

`Registry.process` validates only that HMAC, then immediately dispatches to the app's handler using the *unauthenticated* `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

The intended binding is: `HMAC-verified(shop, topic, body) == (shop header, topic header, body)` asserted to the handler. What is actually verified is only `HMAC-verified(body) == body`; `shop` and `topic` are taken on faith from the request headers. This is structurally the same class of bug as the LibMuon report: fields that participate in downstream logic (`shop`, `topic`) are excluded from the authenticated hash, so they can be substituted independently of the value that was actually signed.

An attacker who can obtain any single valid `(raw_body, hmac)` pair — e.g., by installing the target app on their own store and receiving a genuine webhook for their own shop — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a different, victim shop. `HmacValidator.validate` still passes because it never inspected the header, and `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` claiming the payload came from the victim shop.

### Impact Explanation
This breaks tenant isolation: a host application built on this gem's documented webhook API (`ShopifyAPI::Webhooks::Registry.process`) cannot distinguish "Shopify attests this event is for shop X" from "the attacker's header claims shop X." Any host logic keyed on `data.shop` (e.g., updating per-merchant state, triggering merchant-scoped side effects, redact/GDPR handlers) can be invoked for an arbitrary victim shop using a webhook the attacker legitimately received for their own shop. This is a cross-tenant confusion rooted entirely in this gem's signature-verification code, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High likelihood for any real-world app: any internet user can create a free Shopify development store, install the target app, and trigger/observe a genuine webhook (same topic types are attacker-controllable, e.g., `app/uninstalled`, `customers/data_request`, or any topic the app registers) to obtain a valid `(body, hmac)` pair for their own shop, then replay it against the same public endpoint with a forged `shop-domain` header. No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include the header-derived, security-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used for verification, or otherwise cryptographically bind them to the body before trusting them — e.g., require the caller to additionally confirm `request.shop` against a shop record established via OAuth for that specific webhook subscription, or have `to_signable_string` incorporate the headers (matching Shopify's actual webhook verification guidance, which signs the body but expects callers to separately validate that the shop belongs to an installed session before acting on webhook data). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must be cross-checked by the host app against known installed shops before use.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives (or synthetically has, since they control their own shop and can
# trigger topics like app/uninstalled) a genuine webhook:
body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Legit request as received:
legit_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker.myshopify.com",
}

# Replayed request: same body + same hmac, forged shop header
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# Passes HMAC validation because to_signable_string only returns @raw_body:
ShopifyAPI::Utils::HmacValidator.validate(forged_request) # => true

# Registry.process dispatches the handler believing the event is for victim-shop:
ShopifyAPI::Webhooks::Registry.process(forged_request)
# handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
This demonstrates that the `shop`/`topic` headers can be freely substituted without invalidating the HMAC, because they are never part of the signed string in [4](#0-3) .
