Audit Report

## Title
Node crash via nil-params `vault_publicKeyGet` request bypassing params validation - (File: core/capabilities/vault/gw_handler.go)

## Summary
The Vault gateway path explicitly fast-tracks `vault_publicKeyGet` requests without going through the shared `GatewayVaultRequestProcessor.ProcessRequest` pipeline that validates `req.Params != nil` for other vault methods. On the node side, `GatewayHandler.HandleGatewayMessage` routes `MethodPublicKeyGet` directly to `handlePublicKeyGet`, which unconditionally dereferences `*req.Params` in `json.Unmarshal(*req.Params, r)` without a nil check, unlike every other handler-adjacent code path (`processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) which explicitly check `if req.Params == nil` before unmarshalling.

## Finding Description
`GatewayHandler.HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` straight to `h.handlePublicKeyGet(ctx, gatewayID, req)` without any params-presence check: [1](#0-0) 

`handlePublicKeyGet` then dereferences `req.Params` immediately: [2](#0-1) 

By contrast, every method routed through `GatewayVaultRequestProcessor.processRequest` explicitly guards against nil params before unmarshalling, e.g.: [3](#0-2) 

On the gateway side, `HandleJSONRPCUserMessage` explicitly bypasses the authorization/validation pipeline for `MethodPublicKeyGet` when there is no cached public key, forwarding the request onward via `handlePublicKeyGet(ctx, ar)` instead of `requestProcessor.ProcessRequest`: [4](#0-3) 

On the node side, this request is read in `connector.go`'s `readLoop`, which invokes `handler.HandleGatewayMessage` directly in the read goroutine with no `recover()` anywhere in the call path: [5](#0-4) 

A confirmed `grep` for `recover()` across `core/services/gateway/**` found no matches outside an unrelated test file, confirming there is no panic guard on this path.

If `req.Params` is `nil` (JSON `"params": null` or omitted), `*req.Params` in `handlePublicKeyGet` is a nil-pointer dereference that panics, and since nothing recovers it in `readLoop`, the panic propagates and crashes the entire node process — this is a genuine, code-verified gap distinct from the properly-guarded methods.

## Impact Explanation
This is a legitimate unauthenticated node-crash / denial-of-service. The `vault_publicKeyGet` method is explicitly designed (per the code comment) to skip authorization, so any client able to reach the gateway can trigger this with no credentials, JWT, or allowlist entry — provided the gateway's public-key cache is empty (e.g., right after startup/cache expiry) so the request is forwarded to the DON node's `GatewayHandler.HandleGatewayMessage` rather than answered from cache. This maps to an in-scope "node crash / DoS via unauthenticated request" impact class.

## Likelihood Explanation
High reachability, conditioned on cache-miss timing: the code path is unconditionally reachable by design (no auth/param validation gate for this method on either the gateway or node handler), and the missing nil-check is directly visible by contrasting `handlePublicKeyGet` with the parallel-but-guarded `processDeleteSecretsRequest`/`processListSecretIdentifiersRequest` functions. The existing test `TestVaultHandler_PublicKeyGet` only exercises the gateway-side `handlePublicKeyGet` with `Params: nil`, not the node-side `GatewayHandler.HandleGatewayMessage`/`handlePublicKeyGet` path, confirming the gap is untested.

## Recommendation
Add an explicit `req.Params == nil` check in `GatewayHandler.handlePublicKeyGet` (core/capabilities/vault/gw_handler.go) before dereferencing/unmarshalling, returning a JSON-RPC error response (e.g. `api.UserMessageParseError`) instead of panicking. Additionally, wrap `handler.HandleGatewayMessage` in `connector.go`'s `readLoop` with a `recover()` so a single malformed/malicious message cannot take down the whole node process, consistent with defense-in-depth already applied to other vault methods via `GatewayVaultRequestProcessor`.

## Proof of Concept
1. As an unauthenticated client, send to the gateway's vault HTTP endpoint (at a time when the gateway's public-key cache is empty, e.g. shortly after gateway startup):
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault_publicKeyGet","params":null}
```
2. `handler.HandleJSONRPCUserMessage` detects `cachedPublicKey == nil`, skips authorization, and forwards the raw request (with `Params == nil`) to a DON node via the active-request/fan-out mechanism.
3. On the DON node, `connector.go`'s `readLoop` unmarshals the forwarded request (`Params` remains `nil`) and calls `GatewayHandler.HandleGatewayMessage`, which routes to `handlePublicKeyGet`.
4. `json.Unmarshal(*req.Params, r)` in `handlePublicKeyGet` panics on the nil-pointer dereference, and since no `recover()` exists in `readLoop`, the panic is unrecovered and crashes the node process.
5. As a Go unit test: construct a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and call `GatewayHandler.HandleGatewayMessage` directly (mocking `secretsService`/`gatewayConnector`), asserting it panics instead of returning a graceful error response — contrasting with a similarly-constructed nil-params request for `MethodSecretsDelete`, which returns a clean `InvalidVaultParamsError` via `processDeleteSecretsRequest`.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
