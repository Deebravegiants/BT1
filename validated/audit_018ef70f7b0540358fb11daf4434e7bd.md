### Title
LI.FI swap sweeps stranded/residual token balance into attacker's own output UTXO via unlimited router approval - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Finding Description
The invariant that should hold is: *tokens leaving the action to the caller in a tx == `-deltaAmountChanges` Hinkal sent it that tx*. `ExternalActionSwap.swap` computes `inputAmount = uint256(-deltaAmounts[0])` [1](#0-0)  but never verifies that the router actually consumed only `inputAmount` of `inputToken`. `LifiExternalAction.callRouter` grants the LI.FI `router` an unlimited (`type(uint256).max`) approval on `inputToken` via `approveUnlimited`, then executes attacker-supplied `externalActionMetadata` as an arbitrary call to that router [2](#0-1) , and measures `swappedAmount` purely as the output-token balance delta across that call [3](#0-2) . The unlimited approval is never reset to zero after use and persists across transactions [4](#0-3) .

Because `externalActionMetadata` is fully attacker-crafted calldata to the router (not constrained by the circuit or by `swap`), an attacker whose `inputToken` for this tx happens to equal a token that was ever used as `inputToken` in a *previous* swap (and for which residual/stranded balance — dust, an incomplete route, or a direct donation — now sits in the action contract) can encode a router call that pulls the **entire** action balance of that token (not just this tx's deposited `inputAmount`) using the still-valid unlimited allowance. The resulting `swappedAmount` (and thus `amountToSendToHinkal`, and the attacker's own `utxoSet[0].amount`) is inflated by the stranded balance, while Hinkal only ever sent this tx's `-deltaAmounts[0]` into the action.

`Hinkal.transact`'s balance-equality checks do not catch this: they only verify that Hinkal's *own* balance change for each token matches `circomData.amountChanges[i] + utxoAmount` [5](#0-4) . Since the attacker controls their own proof/`CircomData`, they simply set `amountChanges[1]` (output token, positive) to match whatever inflated `swappedAmount` they engineer, and the circuit constraint `inTotal + amountChanges[i] === outTotal` [6](#0-5)  is satisfied because it only checks internal consistency of the attacker's own declared UTXOs, not that the action's real token consumption matched the declared deposit. Nothing in `_externalTransact` [7](#0-6)  or `swap` verifies input-side consumption against `inputAmount`.

Note: the "tree has exactly one leaf / `roots[MINIMUM_INDEX]`" condition mentioned in the question is unrelated to this bug — it concerns `MerkleBase`/`Merkle` root-lookup logic, not the swap action's balance accounting, and doesn't gate or enable this exploit path.

### Impact Explanation
An unprivileged attacker can capture value that: (a) belongs to a previous user whose swap left residual input-token dust in the action (e.g., partial-fill routes, rounding, or a donation), or (b) any stranded balance of a token the action has previously approved to the router. This is direct theft of in-flight/shielded funds routed through the action, matching Critical severity (direct theft of shielded/in-flight user funds). It is repeatable any time residual balance of a previously-used input token accumulates in the action contract, and the attacker only needs to craft appropriate LI.FI calldata and set their own `erc20TokenAddresses`/`amountChanges` to claim it.

### Likelihood Explanation
Preconditions: some non-zero balance of a token must be sitting in the `LifiExternalAction` contract that was previously granted unlimited approval to `router` (i.e., previously used as an `inputToken`), which is plausible given LI.FI multi-hop/partial-fill swaps often leave dust, and the contract keeps whatever it fails to sweep. The attacker's cost is just one transaction with self-generated proof/UTXOs and crafted `externalActionMetadata`; no special privileges are required, matching the stated attacker model.

### Recommendation
- After the router call, explicitly measure and enforce that the router consumed at most `inputAmount` of `inputToken` (i.e., check `inputBalanceBefore - inputBalanceAfter <= inputAmount`, or transfer/approve exactly `inputAmount` rather than the full balance).
- Avoid `approveUnlimited`; approve exactly `inputAmount` before the call and revoke to zero afterward (already done in `unsafeApproveERC20Token`/`approveERC20Token`, but `approveUnlimited` bypasses per-tx exactness).
- Alternatively, sweep any pre-existing balance to a safe destination (e.g., treasury) before running the swap so it can never be attributed to a later `swappedAmount`.

### Proof of Concept
Foundry plan:
1. Deploy `LifiExternalAction` with a mock router.
2. Simulate a prior tx that leaves `D` units of `tokenX` stuck in the action while granting the router unlimited approval on `tokenX` (e.g., call `swap` once with `inputToken = tokenX`, and have the mock router only consume part of the transferred `inputAmount`, leaving `D` behind).
3. As an unrelated attacker, call `Hinkal.transact` with `erc20TokenAddresses = [tokenX, tokenY]`, depositing a small `inputAmount2` of `tokenX`, and `externalActionMetadata` that instructs the mock router to pull `inputAmount2 + D` of `tokenX` (using the still-valid unlimited allowance) and mint/transfer proportional `tokenY` back to the action.
4. Assert: `amountToSendToHinkal` (and thus the attacker's UTXO amount for `tokenY`) reflects value derived from `D`, i.e., strictly greater than what corresponds to `inputAmount2` alone — violating `tokens leaving the action == -deltaAmountChanges Hinkal sent it`.
5. Assert the attacker successfully withdraws/claims this inflated UTXO, confirming theft of the stranded `D` value.
