### Title
Unrestricted `fillOrder()` when `solverSelection` is disabled enables mempool front-running of solver fills, stealing fill opportunities and surplus - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.fillOrder()` only checks `msg.sender` against an authorized solver when the governance parameter `_params.solverSelection` is enabled [1](#0-0) . When that flag is off, any address can call `fillOrder()` for any placed order commitment as soon as it provides the required output amounts, with no binding to a specific solver, auction winner, or session key. Because `Order` and `FillOptions` are fully public (either observable in the mempool once a legitimate solver submits its fill transaction, or via the public bid stream on Hyperbridge before selection), an attacker can copy a pending `fillOrder` transaction's parameters and resubmit it with higher gas to be included first — a direct analog of the front-running vector described in the external `Trading.sol._matchOrders` report.

### Finding Description
`fillOrder()` performs the solver-authorization check only conditionally:

```solidity
if (_params.solverSelection) {
    bytes32 storedSelectionHash;
    assembly { storedSelectionHash := tload(commitment) }
    bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
    if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
}
``` [1](#0-0) 

Outside the `solverSelection` path there is no per-caller restriction — the first transaction to satisfy `options.outputs.length`/amount checks and reach `_fillSameChain`/`_fillCrossChain` wins the escrowed inputs, tokens are transferred to the caller (solver) and `_filled[commitment]` is set [2](#0-1) . This is exactly the "first submitted transaction wins the trade" pattern the external report flags for `_matchOrders`: whoever gets included first captures the fill, and losing transactions simply revert on `Filled()` wasting the honest solver's gas.

The intent-gateway docs and tests confirm the solver-authorization enforcement is opt-in via `solverSelection`, and describe the SolverAccount/session-key binding as existing specifically to prevent unauthorized/front-run fills — implying that without it, fills are unauthenticated races [3](#0-2) . The test suite explicitly demonstrates the two states: `testFillOrderWithSolverSelection` (protected) vs. the default gateway configuration used elsewhere in the suite where any filler can call `fillOrder` directly [4](#0-3) .

Additionally, the surplus mechanism compounds the impact: when a solver provides more than the required output amount, the excess is split per `surplusShareBps` between beneficiary and protocol [5](#0-4) . A front-runner observing a generous pending fill (with surplus) can resubmit the exact same order with only the minimum required outputs, capturing the escrowed inputs for less value delivered and depriving the user/beneficiary of the surplus the original solver intended to provide.

### Impact Explanation
- Any solver's `fillOrder` transaction sitting in the public mempool (or a solver's own on-chain fill call made after winning an off-chain auction, when `solverSelection` is disabled) can be copied and front-run by a third party willing to pay higher gas.
- The front-runner captures escrowed user inputs meant for the legitimate/selected solver, and the original solver's transaction reverts (`Filled()`), burning gas with no fill.
- Where surplus economics apply, front-running lets an attacker minimize the output delivered to just the required amount, denying the user/protocol the surplus the honest solver would have paid.
- This degrades solver competition into a pure gas-priority race whenever `solverSelection` is off, undermining the auction model the SDK's bid/auction flow assumes (`BidManager.selectAndExecuteBest`, `executeBest`) [6](#0-5) .

This meets the "Medium" bar: it does not permanently freeze funds or forge messages, but it is a concrete value-extraction/MEV vector reachable by any unprivileged address submitting a transaction, causing economic loss (wasted gas, lost surplus) to legitimate solvers/users.

### Likelihood Explanation
Likelihood is Medium-High whenever a gateway deployment runs with `solverSelection = false` (a valid, supported configuration per the `Params` struct and tests) and orders/fills involve any surplus or valuable arbitrage spread. No special privileges are required — only mempool visibility and higher gas, standard MEV tooling.

### Recommendation
- Make solver authorization to `fillOrder()` unconditional (remove the `solverSelection`-gated branch, or default it to `true` and disallow disabling it), so every fill must be tied to a session-key-authorized solver via `select()` + transient storage, closing the open race entirely.
- If an unauthenticated "first solver wins" mode must remain supported, consider commit-reveal for fills or an escrowed minimum-bond/slippage-protection mechanism so front-running cannot reduce the value delivered to the user below what was quoted (e.g., require the same-tx surplus commitment recorded off-chain to match, or use private relay/flashbots-style submission for solver fills).
- Document and strongly discourage disabling `solverSelection` in any deployment where surplus sharing or public auctions are used.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `Params.solverSelection = false` (the non-selection configuration exercised throughout `evm/tests/foundry/IntentGatewayV2Test.sol`).
2. User places an `Order` with `session = address(0)` (no selection binding).
3. Solver A, having won an off-chain auction, prepares and broadcasts `fillOrder(order, options)` with `options.outputs` exceeding the required amount (providing surplus).
4. Attacker B observes Solver A's pending transaction in the mempool, copies `order` and constructs `FillOptions` with `outputs` set to exactly the minimum required amounts, and submits with a higher gas price.
5. Attacker B's transaction is mined first: `_filled[commitment]` is set, escrowed inputs transferred to B, and B delivers only the minimum required output tokens.
6. Solver A's transaction reverts with `Filled()` [7](#0-6) , wasting Solver A's gas and denying the user/beneficiary the surplus A intended to provide.

Note: I could not fully verify the default value of `_params.solverSelection` at deployment (e.g., in `DeployIntentGateway.s.sol`) within the available index; confirming whether production deployments run with `solverSelection` enabled or disabled by default would materially affect real-world likelihood and should be checked directly in the repository before treating this as exploitable in a specific live deployment.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }
    }

## Solver Selection

When `solverSelection` is enabled in the intent gateway parameters, orders are protected from unauthorized fills. At order placement, the user specifies a `session` key — a temporary keypair generated for this order. Only a solver explicitly authorized by the session key can fill the order.

### `SolverAccount`

The SolverAccount is a smart account designed for solvers that combines [ERC-4337](https://eips.ethereum.org/EIPS/eip-4337) (account abstraction), [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702), and [ERC-7821](https://eips.ethereum.org/EIPS/eip-7821) (batch execution) to batch `gateway.select(...)` and `gateway.fillOrder(...)` into a single atomic UserOperation. Solvers delegate their EOA to the SolverAccount via EIP-7702 and submit bundled operations through the ERC-4337 EntryPoint.

    function testFillOrderWithSolverSelection() public {
        // Enable solver selection
        Params memory newParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: true,
            surplusShareBps: 10000,
            protocolFeeBps: 0,
            priceOracle: address(0)
        });

        IntentGatewayV2 gatewayWithSelection = _deployGatewayProxy();
        gatewayWithSelection.initialize(newParams, new bytes[](0), address(0));

        uint256 inputAmount = 1000 * 1e6;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(uint256(uint160(user))),
            source: host.host(),
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: 0,
            session: vm.addr(1), // Session key
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        usdc.approve(address(gatewayWithSelection), inputAmount);
        gatewayWithSelection.placeOrder(order, bytes32(0));
        vm.stopPrank();

        bytes32 commitment = keccak256(abi.encode(order));

        // Create EIP-712 signature from session key
        bytes memory sessionSignature = _createSelectSolverSignature(
            commitment,
            filler,
            1, // Session key private key
            address(gatewayWithSelection)
        );

        // Solver selects themselves
        vm.startPrank(filler);
        gatewayWithSelection.select(
            SelectOptions({commitment: commitment, solver: filler, signature: sessionSignature})
        );

        // Filler fills order
        dai.approve(address(gatewayWithSelection), type(uint256).max);

        TokenInfo[] memory solverOutputs = new TokenInfo[](1);
        solverOutputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        gatewayWithSelection.fillOrder(
            order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: solverOutputs})
        );
        vm.stopPrank();
    }
