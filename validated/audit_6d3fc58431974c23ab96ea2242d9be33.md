### Title
Unbounded solver fee accepted when `feeInclusive: false` — no sanity check on `fee.amount` vs `withdrawalParams.amount` - (File: packages/intents-sdk/src/sdk.ts)

### Finding Description
The broken equality: **debited swap output should equal `withdrawalParams.amount` (delivered to the user) plus `fee.amount` (paid to the solver), where `fee.amount` is bounded by some real solver cost.** In `_estimateWithdrawalFee` [1](#0-0) , the fee returned by `bridge.estimateWithdrawalFee` (which internally is populated from a solver-provided quote) is bound-checked against `withdrawalParams.amount` only inside the `feeInclusive === true` branch:

```
if (args.withdrawalParams.feeInclusive) {
    if (args.withdrawalParams.amount <= fee.amount) {
        throw new FeeExceedsAmountError(fee, args.withdrawalParams.amount);
    }
}
``` [2](#0-1) 

When `feeInclusive === false`, `actualAmount` is simply `args.withdrawalParams.amount` unchanged [3](#0-2) , and `fee.amount` is passed straight through to `bridge.validateWithdrawal` and then returned to the caller with **no upper bound whatsoever** relative to `withdrawalParams.amount`. The same asymmetry repeats in `createWithdrawalIntents`, which only subtracts fee from amount when `feeInclusive` is true and otherwise blindly forwards `args.feeEstimation` to `bridge.createWithdrawalIntents` [4](#0-3) .

Since `fee.amount` ultimately originates from a solver-controlled quote (via `getFeeQuote`/quoting path in the underlying bridge, referenced by the prior finding), a malicious or misbehaving solver can return an artificially inflated exact-out quote. In the `feeInclusive: false` flow this inflated `fee.amount` is never checked against the withdrawal amount and is used verbatim to build the fee-consuming intent (e.g. a `token_diff` intent in the bridge's `createWithdrawalIntents`), so a fee that is many multiples of any reasonable bridging cost — potentially even larger than `withdrawalParams.amount` itself — will be signed and executed without the SDK ever raising `FeeExceedsAmountError` or any other guard.

### Impact Explanation
The caller signs and sends an intent that debits `amount + fee` from their balance, where `fee` can be inflated arbitrarily by a solver with no cap in the `feeInclusive: false` path. This is a fee overcharge that can drain a material share (or more) of the amount the user intended to move, matching the "fee error draining a material share of the amount" Critical category. The party harmed is the withdrawing NEAR Intents user; the attacker is the solver responding to the fee quote. This is fully repeatable per withdrawal call since the check is structurally absent for the `feeInclusive: false` branch, not just a one-off edge case.

### Likelihood Explanation
Preconditions: an integrator calls `estimateWithdrawalFee`/`processWithdrawal` with `feeInclusive: false` (a normal, documented, non-misuse mode) and a solver returns an inflated fee quote for that route/asset. The attacker's cost is simply answering the quote request with an unfavorable price — no privileged access needed, matching the "permissionless solver answering a quote" threat model. Feasibility is high because no code path in `_estimateWithdrawalFee` sanity-checks the fee magnitude when `feeInclusive` is false, and the check in the `true` branch demonstrates the codebase already recognizes and defends this exact concern for one branch but not the other.

### Recommendation
Apply a symmetric sanity check on `fee.amount` regardless of `feeInclusive`. At minimum, validate that `fee.amount` does not exceed `withdrawalParams.amount` (or some proportional cap) even when `feeInclusive === false`, and consider validating `fee.amount` against an independently-computed expected fee bound (e.g. from `getUnderlyingFee`) rather than trusting the solver's raw quote unconditionally.

### Proof of Concept
Vitest plan for `packages/intents-sdk/src/sdk.estimateWithdrawalFee.test.ts` style setup:
1. Mock a bridge's `estimateWithdrawalFee` (HTTP-level solver quote mock) to return `fee.amount` equal to, say, 95% of `withdrawalParams.amount` (or larger), with `withdrawalParams.feeInclusive: false`.
2. Call `sdk.estimateWithdrawalFee({ withdrawalParams, quoteOptions })`.
3. Assert that no `FeeExceedsAmountError` is thrown and `fee.amount` returned equals the malicious oversized quote.
4. Feed this `feeEstimation` into `createWithdrawalIntents`/`signAndSendWithdrawalIntent` and assert on the resulting intent's amount fields (e.g. `-amount_in` on the `token_diff` intent) that the actual debit equals `withdrawalParams.amount + fee.amount`, showing the fee consumes nearly the entire signed swap versus the real minimal solver cost — i.e., LHS (`debited amount`) != RHS (`amount + reasonable fee`).

	protected async _estimateWithdrawalFee(args: {
		withdrawalParams: WithdrawalParams;
		quoteOptions?: QuoteOptions;
		logger?: ILogger;
	}): Promise<FeeEstimation> {
		for (const bridge of this.bridges) {
			if (await bridge.supports(args.withdrawalParams)) {
				const fee = await bridge.estimateWithdrawalFee({
					withdrawalParams: args.withdrawalParams,
					quoteOptions: args.quoteOptions,
					logger: args.logger,
				});

				if (args.withdrawalParams.feeInclusive) {
					if (args.withdrawalParams.amount <= fee.amount) {
						throw new FeeExceedsAmountError(fee, args.withdrawalParams.amount);
					}
				}
				const actualAmount = args.withdrawalParams.feeInclusive
					? args.withdrawalParams.amount - fee.amount
					: args.withdrawalParams.amount;

				await bridge.validateWithdrawal({
					assetId: args.withdrawalParams.assetId,
					amount: actualAmount,
					destinationAddress: args.withdrawalParams.destinationAddress,
					feeEstimation: fee,
					routeConfig: args.withdrawalParams.routeConfig,
					logger: args.logger,
					destinationMemo: args.withdrawalParams.destinationMemo,
					// When estimating fees before the exact amount is known, skip minimum amount validation while keeping all other validation intact.
					skipMinAmountValidation:
						args.withdrawalParams.amount === 0n &&
						args.withdrawalParams.feeInclusive === false,
				});

				return fee;
			}
		}

		throw new Error(
			`Cannot determine bridge for withdrawal = ${stringify(
				args.withdrawalParams,
			)}`,
		);
	}
