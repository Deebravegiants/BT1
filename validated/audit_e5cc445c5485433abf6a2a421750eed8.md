### Title
QR_CODE_V2 regex accepts truncated, non-canonical UUIDs as `user_id`, binding signup identity without format validation - ([File: src/plans/qr_scan/user.rs])

### Summary
The `QR_CODE_V2` regex in `src/plans/qr_scan/user.rs` makes the final two UUID segments (`-xxxx-xxxxxxxxxxxx`) optional, so a QR code like `userid:3bcf883d-ce22-4a03:1` is accepted and produces `Data { user_id: "3bcf883d-ce22-4a03", ... }` via `Data::from_v2`. This value flows unchanged into `Data::Normal`/`user::Data` used for signup identity binding, with no canonical-UUID validation anywhere in this parsing path.

### Finding Description
`QR_CODE_V2` is defined with an optional capture group for the last two UUID segments: [1](#0-0) 

`Data::try_parse` falls back to this regex when `orb_qr_link::decode_qr` fails, and directly returns `Data::from_v2(&captures)` with no further validation of the `user_id` string's shape or length: [2](#0-1) 

`Data::from_v2` copies the raw regex-captured string as-is into `user_id: String` — there is no call to `uuid::Uuid::parse_str` or any canonicalization/length check: [3](#0-2) 

The existing test `test_v2_shortened` confirms this behavior is intentional/accepted by the current implementation, not merely a theoretical regex edge case: [4](#0-3) 

The doc comment on the struct field asserts an invariant that is not enforced in code: `user_id` is documented as "User ID in format of 128-bit UUIDv4" but the type is a bare `String` with no validation gate: [5](#0-4) 

The `operator.rs` `Data::try_parse` wraps this same `user::Data::try_parse` for the `Data::Normal` variant used in the operator QR flow, inheriting the same lack of validation: [6](#0-5) 

I was not able to locate, within the available index for this repository, the downstream signup/backend-upload code that consumes `user::Data::user_id` to confirm whether a server-side or session-layer check re-validates canonical UUID format before capture/upload begins. This limits my ability to prove end-to-end cross-signup attribution collision (that requires backend behavior outside this repo's visible scope), but the client-side parsing layer itself does not enforce the stated "128-bit UUIDv4" invariant, which is the boundary this repo controls.

### Impact Explanation
If any downstream backend call accepts this truncated identifier as a valid session/user identifier (e.g., via prefix matching, truncated storage keys, or logging/attribution keyed on this string), a truncated ID could collide with, or be mistaken for, a different legitimate user's identifier, causing an iris code/custody package to be attributed to the wrong `user_id`. This maps to a "wrong-identity binding" / biometric-attribution integrity issue. Even absent a proven backend collision, this is a genuine violation of the "identity binding is exact" invariant at the client validation boundary, weakening defense-in-depth against malformed identifiers reaching capture and signing logic.

### Likelihood Explanation
Exploitability requires no privileged access — an attacker only needs to present an arbitrary QR code to the operator/user camera. However, actual exploitation is contingent on backend/session-layer behavior (e.g., whether the backend performs exact-match validation or rejects non-canonical UUIDs) which is not visible in this repository, so the real-world likelihood cannot be fully confirmed from client code alone.

### Recommendation
Remove the optional segment group from `QR_CODE_V2` so it only matches a full canonical UUID (8-4-4-4-12 hex), and additionally validate the captured `user_id` with `uuid::Uuid::parse_str` in `Data::from_v2`, rejecting the QR code (returning `None`) if parsing fails or the string isn't returned in canonical hyphenated lowercase form.

### Proof of Concept
Add a regression test in `src/plans/qr_scan/user.rs` asserting rejection of non-canonical UUIDs:
```rust
#[test]
fn test_v2_rejects_truncated_uuid() {
    let text = "userid:3bcf883d-ce22-4a03:1";
    assert!(QR_CODE_V2.captures(text).is_none()); // should fail to match after fix
}
```
Fuzz plan: generate UUID-like strings with valid-per-current-regex but truncated segment lengths (8-4-4, 8-4, 8, etc.) and assert `Data::try_parse` returns `None` unless `uuid::Uuid::parse_str(&captures["user_id"])` succeeds, ensuring every accepted `user_id` is a full canonical UUIDv4 before it can reach `Data::Normal` and any downstream signup/capture logic.
