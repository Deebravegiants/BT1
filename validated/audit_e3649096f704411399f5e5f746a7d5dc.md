### Title
Emporium relay fees can be entirely bypassed by extracting Emporium-held token balances that are not declared as a withdrawal `deltaAmountChange` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`payRelayFees()` in `EmporiumUpgradeable.sol` only charges a relay fee for a token when that token's `deltaAmountChanges[i]` is negative (i.e. explicitly declared as a withdrawal in the proof). Any value that the executed `ops` cause the Emporium contract's balance to increase for a token whose declared `deltaAmountChanges[i]` is `>= 0` is still paid out to the caller via `handleOut()`, but it is never charged a fee, because the fee loop simply `continue`s for that token index.

### Finding Description
`runAction()` executes the caller-supplied `EmporiumOperation[]` (arbitrary external calls / wallet calls), then calls `payRelayFees()`, then computes `balanceChange = balancesAfter[i] - balancesBefore[i]` per token and sends any positive `balanceChange` to `msg.sender` via `handleOut()`: [1](#0-0) 

The fee logic explicitly skips any token whose declared `deltaAmountChanges[i]` is non-negative, on the stated assumption that "tokens deposited into Emporium are not charged": [2](#0-1) 

However, `deltaAmountChanges[i]` is merely the prover's *declared* intended change for that token, taken from the ZK-proven `circomData` fields — it is not tied to what the arbitrary `ops` calls actually do to the contract's real ERC20/ETH balance. Since `ops` can call any `endpoint` with arbitrary `callData` (subject only to the `IHinkalWallet.callHinkalWallet`/`doSendToRelay` selector guard for stateless calls), a user can:

1. Declare `deltaAmountChanges[i] = 0` (or positive) for a token `T` that is not actually being deposited.
2. Include an `op` that causes the Emporium contract's balance of `T` to increase (e.g., calling a `claim`/`harvest`/`withdraw`-style function on an external protocol that pays out `T` to `address(this)`, or that pulls out previously-parked balance).
3. Because `deltaAmountChanges[i] >= 0`, `payRelayFees()` `continue`s and charges no fee on token `T` at all.
4. `handleOut()` then computes `balanceChange = balancesAfter[T] - balancesBefore[T] > 0` and transfers the *entire* extracted amount to `msg.sender`, minting a fresh out-UTXO for it, with zero relay compensation.

This breaks the intended equality that every unit of value extracted from the shielded pool via an external action pays the configured relay fee (`flatFee` + `variableRate`). The relay's `require(circomData.relay == address(0) || hasPaidToRelay, ...)` style guard from the internal-transact path (`Hinkal.sol`) does not exist for the Emporium fee path — `payRelayFees()` never asserts that *all* extracted value across all tokens was fee-charged, only that whichever token happens to be `feeStructure.feeToken` and has a declared negative delta was charged.

This is directly analogous to the reported class of bug: a real, protocol-recognized value transfer ("borrowing"/extraction) happens, but the code's obligation-settlement check (`forceReplenish`/fee charge) is keyed off a separate, gameable signal (collateral surplus threshold / declared `deltaAmountChanges` sign) rather than the actual value moved, letting a user structure their calldata to permanently avoid paying what they owe.

### Impact Explanation
This is a High-severity issue: theft of protocol/relay fees. A relayer submits and pays gas for the transaction expecting to be compensated per `feeStructure`, but a user can construct `ops` so that value is extracted from the Emporium contract into their own UTXO while systematically avoiding the fee charge on that value, permanently freezing/stealing the relay's expected fee revenue for that transacted value.

### Likelihood Explanation
Likelihood is Medium-High for a knowledgeable user: it requires crafting an `EmporiumOperation` whose target `endpoint`/`callData` causes the Emporium's balance to rise for a token not declared as a withdrawal — a normal pattern for DeFi actions such as claiming rewards, harvesting, or unwrapping to an underlying asset. No special privileges are needed; the caller only needs `onlyAllowedRecipient` access, i.e., normal use of the External Action through `Hinkal.transact()`.

### Recommendation
Charge (or at minimum evaluate) the relay fee based on the actual realized `balanceChange` computed after the `ops` execute, not solely on the prover-declared `deltaAmountChanges` sign. Concretely, compute `balanceChange` for every token first, and require that the fee logic run for every token with a positive realized outflow to `msg.sender`, regardless of what `deltaAmountChanges[i]` claims — or add an explicit check that the sum of fees charged corresponds to the total value sent out via `handleOut()`, similar to the `hasPaidToRelay` require pattern used in `Hinkal._internalTransact()`.

### Proof of Concept
1. User submits a `transact()` call with `externalActionId` pointing to `EmporiumUpgradeable`, `erc20TokenAddresses = [rewardToken]`, and `amountChanges/deltaAmountChanges` set so that `deltaAmountChanges[0] = 0` (no declared withdrawal of `rewardToken`).
2. `stack.ops` contains one operation calling a yield/reward contract's `claim()` (or similar) function that pays `rewardToken` directly to the Emporium contract (`address(this)`).
3. `payRelayFees()` iterates tokens; for `rewardToken`, `deltaAmountChanges[0] >= 0` so the loop `continue`s — no fee charged (assuming `foundToken` doesn't force the fallback fee path, e.g., `feeStructure.flatFee == 0` or `feeStructure.feeToken` is a different token already found elsewhere).
4. `balancesAfter[0] - balancesBefore[0]` is the full claimed `rewardToken` amount; `handleOut()` sends 100% of it to `msg.sender` and mints an out-UTXO for it.
5. Relay/relayer receives $0 for facilitating extraction of `rewardToken`, despite having paid gas and expecting fee revenue per `feeStructure`.
