### Title
Unvalidated octal QR-code parameter causes panic/DoS in signup-extension configuration parsing - (File: `src/plans/biometric_capture/focus_sweep.rs`, `src/plans/biometric_capture/mirror_sweep.rs`, `src/plans/biometric_capture/overcapture.rs`)

### Summary
The `AaveDistributionManager` bug class (missing length/bounds validation on attacker-influenced input before it is used to index a fixed-size table) has a structural analog in orb-core's signup-extension "sweep configuration" parsing: an operator/user-controlled QR-code parameter string is parsed as an octal `u8` and then converted to a fixed-width binary representation that is assumed — but never actually enforced by the input's own grammar — to be exactly 3 bits, before that representation is used to index a fixed 3-element lookup table.

### Finding Description
The QR-code regex used to capture signup-extension parameters is permissive: `parameters` is defined as `[a-z0-9:]+` [1](#0-0) . This same `parameters` string is later parsed with `u8::from_str_radix(parameter, 8)` in `focus_sweep::Plan::from` and `mirror_sweep::Plan::from` [2](#0-1) [3](#0-2) , and via `parse_u8_octal` in `overcapture::Plan::from` [4](#0-3) , [5](#0-4) .

The resulting `configuration_value: u8` is passed into `SweepConfiguration::new`/`Configuration::new`, which calls `parse_configuration_value`/`parse_wavelength_configuration`. That function formats the value as `format!("{configuration_value:0>3b}")` and immediately asserts the result is exactly 3 characters long before iterating character indices `n` to index the fixed-size `WAVELENGTH_LUT: [IrLed; 3]`: [6](#0-5) [7](#0-6) [8](#0-7) 

The comment on the octal parsing calls explicitly flags this as unvalidated/unsafe: "TODO: Move parsing of configuration flag to QR code scanning phase -> Handle/Fail early" [9](#0-8) .

The root cause: while octal digits `0`–`7` in a single position always produce a 3-bit value, the code does not restrict the *string* to a single octal digit — `u8::from_str_radix` accepts multi-digit octal strings (e.g. `"77"` = 63, `"10"` = 8, `"777"` overflows and errors, but many multi-digit combinations like `"77"`, `"17"`, `"37"` parse successfully to values ≥ 8). Any parsed `u8` value ≥ 8 produces a binary representation longer than 3 characters, which fails the `assert_eq!(binary_repr.chars().count(), 3, ...)` check and panics — this is the equivalent of the missing `emissionSchedule.length` check in the reported Solidity bug: a length/format precondition on attacker-controlled configuration data is not validated before being relied upon by downstream fixed-size indexing logic. Unlike the reference bug (which leads straight to an out-of-bounds read), here the code happens to `assert!` first, converting the missing-validation defect into a guaranteed panic (Rust's safe-index bound check) rather than an out-of-bounds memory read — but the underlying defect (accepting unbounded/unvalidated length attacker input intended to be bounded) is the same class, and the impact is an unhandled panic in the signup pipeline.

### Impact Explanation
Reaching this code path requires:
1. The `internal-data-acquisition` cargo feature to be compiled in (gates `QR_CODE_SIGNUP_EXTENSION` regex matching and the extension `SignupMode`s) [10](#0-9) [11](#0-10) .
2. A crafted operator/user QR code presenting a `mode` matching `FocusSweepExtension`/`MirrorSweepExtension`/`Overcapture` with a `parameters` value like `"77"` or similar multi-digit octal string ≥ 8 decimal.

If reachable in a deployed build, an unprivileged party who can present a QR code to the orb (an operator-class or user-class actor per the signup flow) can crash the `orb-core` process via an `assert_eq!` panic during `biometric_capture()` [12](#0-11) , disrupting an in-progress signup (denial of service). It does not directly cause unauthorized signup attribution, biometric data disclosure, or attestation forgery — the strongest concrete outcome supported by the code is a crash/DoS during signup, not the higher-severity impacts (misattributed signup, biometric disclosure, fraud bypass) the validation rules require for full acceptance.

### Likelihood Explanation
Likelihood depends heavily on whether `internal-data-acquisition` is enabled in production builds; multiple other files gate behavior behind it (`src/plans/mod.rs`, `src/agents/image_notary.rs`, `src/backend/user_status.rs`, `src/bin/orb-core.rs`), suggesting it may be a build-time flag for special/test hardware rather than the default consumer signup path. I was unable to conclusively determine from the indexed content whether this feature is active on production orbs. If it is test/internal-only, this weakens the finding per the "reject test-only paths" rule.

### Recommendation
Regardless of the feature-gating question, add an explicit bounds/format check when parsing the octal `parameters` string (or clamp/validate the resulting `u8` to 0–7) before it reaches `parse_configuration_value`/`parse_wavelength_configuration`, replacing the `assert_eq!` panics with graceful rejection (e.g., falling back to a default configuration and logging an error) — mirroring the recommended Solidity fix of validating the length precondition before it's relied upon by downstream indexing logic.

### Proof of Concept
1. Build orb-core with `internal-data-acquisition` feature enabled.
2. Present a QR code matching `QR_CODE_SIGNUP_EXTENSION`, e.g. `userid:<uuid>:1::2:77::` (mode `2` = `FocusSweepExtension`, parameters `77`).
3. `SignupMode::FocusSweepExtension` is selected; `focus_sweep::Plan::from` calls `u8::from_str_radix("77", 8)` → `63`.
4. `SweepConfiguration::new(63)` → `parse_configuration_value(63)` → `format!("{:0>3b}", 63)` = `"111111"` (6 chars) → `assert_eq!(6, 3, ...)` panics, crashing the signup task/process. [13](#0-12)

impl From<biometric_capture::Plan> for Plan {
    fn from(biometric_capture: biometric_capture::Plan) -> Self {
        let config = biometric_capture
            .signup_extension_config
            .as_ref()
            .and_then(|config| config.parameters.as_ref());
        let (wavelength_parameter, duration_parameter) =
            config.map_or((1, Duration::from_millis(DEFAULT_OVERCAPTURE_DURATION)), |parameters| {
                parameters.split_once(':').map_or(
                    (
                        parse_u8_octal(parameters, 1),
                        Duration::from_millis(DEFAULT_OVERCAPTURE_DURATION),
                    ),
                    |(wavelength, duration)| {
                        (
                            parse_u8_octal(wavelength, 1),
                            parse_duration(duration, DEFAULT_OVERCAPTURE_DURATION),
                        )
                    },
                )
            });
