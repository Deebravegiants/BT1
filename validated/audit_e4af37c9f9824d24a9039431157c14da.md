### Title
Weak `xpub` validation allows malformed/attacker-controlled data to be persisted in wallet storage - (File: features/public-key-provider/module/store/formats/serialization/xpub.ts)

### Summary
`serialization.xpub.validateSerialized` only checks that a value is a string starting with `'xpub'`, without any BIP32/base58check structural validation. Any caller that reaches `PublicKeyStore.add`/`addMany` (e.g. via `MockablePublicKeyProvider`'s config-driven `#ingestMocks`, or hardware-wallet key sync flows) can pass an arbitrary attacker-controlled string as long as it has the `'xpub'` prefix, and it will pass `assertStorageFormatLegacy` and be durably persisted to the `softwareWalletPublicKeysAtom`/`hardwareWalletPublicKeysAtom`.

### Finding Description
`validateSerialized` in `features/public-key-provider/module/store/formats/serialization/xpub.ts` is defined as: [1](#0-0) 

It performs no base58check decoding, length check, or version-byte validation — it is a pure prefix check. This function is invoked from `assertStorageFormatLegacy`, the sole gatekeeper used both when constructing a `StorageFormatLegacyBuilder` from external data and when serializing it back out: [2](#0-1) 

`StorageFormatLegacyBuilder.addMany` accepts `key.xpub` as long as it is truthy, writes it into `#data`, and the outer `PublicKeyStore.addMany` then serializes it (`serialization.xpub.serialize` is also a pass-through identity function) and persists it via `#setData` → `atom.set` / `walletAccounts.setAccounts`: [3](#0-2) 

A concrete reachable path is `MockablePublicKeyProvider`, which is driven by a `config.xpubs` object (attacker-influenced remote config or ingest-mock data) and calls `#publicKeyStore.addMany({ walletAccount, keys })` directly with whatever `xpub` string is present in config, with no format validation before the store layer: [4](#0-3) 

Because `validateSerialized` never checks base58check checksum, decoded length (78 bytes), or BIP32 version bytes, a string like `'xpub' + garbage` passes both the ingestion check and the persistence-time `assertStorageFormatLegacy` check unchanged.

### Impact Explanation
Malformed/non-conformant xpub strings can be durably written into wallet storage (`softwareWalletPublicKeysAtom` / hardware wallet accounts via `walletAccounts.setAccounts`), violating storage integrity — the persisted public-key state is not guaranteed to be a well-formed extended public key. This is a scoped storage-integrity defect: it does not by itself leak secrets or forge signatures, but it corrupts a security-relevant cache that other code paths (address derivation, restore, `get()` → `serialization.xpub.deserialize`) trust as valid, and could cause downstream failures/DoS or inconsistent address derivation whenever that entry is later consumed and parsed by a real BIP32 implementation.

### Likelihood Explanation
The precondition is explicit in the scoped question: an attacker who controls a remote-config response, imported backup file, or RPC payload consumed by any call path that reaches `PublicKeyStore.add`/`addMany` (e.g. `MockablePublicKeyProvider`'s config-driven mock ingestion) can supply a garbage string prefixed with `'xpub'`. No authentication, lock-state bypass, or privileged access is required beyond controlling that input surface, and the check is deterministic and always passes for any string starting with the 4-character prefix.

### Recommendation
Replace the prefix-only check in `validateSerialized` with real structural validation: decode with base58check, verify the checksum, confirm the total decoded length is 78 bytes, and validate the version bytes/depth/fingerprint/index fields conform to BIP32 extended-key encoding (and optionally that the embedded public key is a valid compressed secp256k1 point). Reject anything that fails decoding or structural checks before it reaches `StorageFormatLegacyBuilder.addMany`.

### Proof of Concept
Add unit tests to `features/public-key-provider/module/store/__tests__/storage-format-legacy.test.ts` (or a new test for `xpub.ts`) asserting rejection of non-conformant inputs:

```ts
import serialization from '../formats/serialization/xpub.js'
import { assertStorageFormatLegacy } from '../formats/storage/legacy.js'

it('rejects xpub-prefixed garbage', () => {
  expect(serialization.default.validateSerialized('xpub' + 'A'.repeat(50))).toBe(false) // currently true, should be false
})

it('assertStorageFormatLegacy should throw for malformed xpub', () => {
  const malformed = {
    wallet_0: {
      "m/84'/0'/0'": { xpub: 'xpubGARBAGEBYTESNOTVALIDBIP32', chain: [0, 0, 0] },
    },
  }
  expect(() => assertStorageFormatLegacy(malformed as any)).toThrow() // currently does not throw
})
```
Both assertions currently fail (the malformed value is accepted), demonstrating the gap.
