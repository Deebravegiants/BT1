### Title
Webhook tenant identity (`X-Shopify-Shop-Domain`) is not covered by the HMAC signature, allowing shop-confusion / cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) values from raw, unauthenticated HTTP headers, while `to_signable_string` — the value actually HMAC-verified — is only the raw request body. `Registry.process` validates the HMAC and then dispatches the handler using the unauthenticated `shop` header value as the trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) . Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from the (attacker-controllable, unsigned) `X-Shopify-*` headers: [3](#0-2) .

`Registry.process` uses this unauthenticated `shop` value as the authoritative tenant identity once the (body-only) HMAC check passes, and hands it directly to the app's webhook handler: [4](#0-3) .

This breaks the identity binding: `shop` used to route/tag webhook data ≠ `shop` covered by the HMAC. Concretely: any party that has captured one legitimately-signed webhook `(raw_body, X-Shopify-Hmac-Sha256)` pair — e.g., a merchant who has the app installed on their own store and can trigger/capture their own webhook deliveries — can replay that exact body+HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with any other tenant's shop domain. `Utils::HmacValidator.validate` will still return `true` (it never inspects the headers), and `Registry.process` will invoke the topic handler with `WebhookMetadata` claiming the forged `shop`, `webhook_id`, and `api_version`, together with the replayed body.

### Impact Explanation
This is a cross-tenant identity-binding break in the gem's own webhook-authentication primitive: an entity that never had any relationship with the victim shop can make the host application process attacker-chosen webhook content while it is durably tagged and stored as belonging to another merchant's shop, without ever needing `api_secret_key`, an access token, or any credential of the app. Any app logic keyed off `WebhookMetadata#shop` (e.g. per-shop data writes, uninstall/GDPR handling, order/customer sync) can be corrupted or spoofed for an arbitrary tenant this way, matching the "cross-tenant access" High-impact category.

### Likelihood Explanation
The prerequisite (capturing one's own valid webhook body+HMAC pair) is trivial for any developer/merchant who can install the target app on a store they control (a normal unprivileged capability of the Shopify app ecosystem), and the forgery step is a single HTTP replay with a modified header — no cryptographic material or secret is required.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the HMAC-covered signable string (or otherwise cryptographically bind them to the body), so that `Utils::HmacValidator.validate` fails if any of these tenant-identifying fields are altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`).
2. Attacker's endpoint captures the raw request body `B` and the `X-Shopify-Hmac-Sha256` header value `H` for that delivery — both are for their own shop and pass validation.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` at [5](#0-4)  returns `true` because it only checks `B`/`H`.
5. `Registry.process` dispatches the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to act on attacker-controlled data attributed to the victim tenant.
