Webhook `shop` identity used by handlers is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` identity that gets handed to the app's `WebhookHandler` (and that apps use to look up sessions / attribute data to a tenant) is read from the unsigned `x-shopify-shop-domain` header. Because the tenant-identifying field is not part of the signed content, a party who possesses one valid `(body, hmac)` pair (e.g. from a webhook legitimately delivered to their own shop) can resend it to the app's webhook endpoint with a different `shop-domain` header and have it accepted as valid, causing the app to process/attribute that payload to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read from a separate header that is never included in what gets signed/verified: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the signature over `verifiable_query.to_signable_string` (i.e., the body), and never inspects or binds `shop`: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then forwards `request.shop` straight to the app's handler as an authenticated field, with no additional verification tying it to the signed body: [4](#0-3) 

The resulting `WebhookMetadata` struct carries `shop` as a trusted, verified-looking field: [5](#0-4) 

This breaks the intended equality: `shop_the_HMAC_authenticates == shop_the_handler_acts_on`. In reality, the HMAC authenticates *only the body bytes*; the `shop` value handed to the tenant-scoped handler is an independent, unauthenticated header. Any unprivileged user who can obtain one legitimately-signed `(raw_body, hmac)` pair for *their own* shop (trivial: install the app on their own/dev store and let Shopify deliver a real webhook) can replay that exact body+hmac to the app's public webhook endpoint while substituting `x-shopify-shop-domain` for a different (victim) shop. `Registry.process` will accept it (HMAC over body validates) and hand the handler `WebhookMetadata.new(shop: "<victim-shop>", body: <attacker's-own-webhook-body>, ...)`. Any app logic that trusts `data.shop` to select which tenant's session/record to update (a common pattern shown in the library's own docs and `webhook_handler.rb` contract) will act on the victim tenant using attacker-supplied body content — a cross-tenant data-integrity/confusion issue rooted entirely in this gem's webhook verification code, not in host-application misuse of a documented API (the library returns `shop` as if it were verified, with no caveat that it is unauthenticated).

### Impact Explanation
This is a cross-tenant access issue: an unprivileged internet user can cause the app to process arbitrary attacker-controlled webhook body content under an arbitrary victim shop's identity, without needing the app's `client_secret`/access tokens — they only need one valid HMAC/body pair for any shop (including their own). Depending on the topic (e.g., `orders/create`, `app/uninstalled`, `shop/update`), this can corrupt per-tenant state, trigger side effects (fulfillment, notifications, uninstall handling) attributed to the wrong merchant, or be used to inject attacker-chosen data into a victim's tenant-scoped records — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Moderate-to-high likelihood: any developer/attacker can register their own (potentially free/dev) Shopify store, install the target app, and receive real, validly-HMAC'd webhook deliveries. Capturing the raw POST body and `X-Shopify-Hmac-Sha256` header requires no privileged access — just running an HTTP proxy/logger in front of their own store's install. Replaying the request with a modified `shop-domain` header to the app's public webhook URL requires nothing beyond a basic HTTP client. No secrets, tokens, or victim credentials are needed.

### Recommendation
Do not treat `shop-domain` (or any other webhook header) as authenticated. Options:
1. Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or
2. Independently verify that the shop asserted in the header actually owns/matches an installation record (session) known to the app before trusting `WebhookMetadata#shop`, and/or
3. Explicitly document in `WebhookMetadata`/`WebhookHandler` that `shop` is unauthenticated and require handlers to cross-check it against their own session store keyed by verified webhook_id/topic, rather than presenting it as a trusted field of a "verified" webhook.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g. updates an order) and captures the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify to the app's webhook endpoint — `H` is a valid HMAC-SHA256 of `B` under the app's `api_secret_key`.
3. Attacker POSTs the exact same `B` and `H` to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of their own domain.
4. Server-side, `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B` (`to_signable_string` returns `B`, independent of the shop header).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), topic: ..., webhook_id: ..., api_version: ...)`.
6. Any handler logic keyed off `data.shop` now operates on `victim-shop.myshopify.com` using attacker-controlled `B`, even though Shopify never sent this webhook for that shop.
