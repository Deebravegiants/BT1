Confirmed: the OAuth callback flow in this gem does **not** validate that `shop` is a genuine `myshopify.com` domain before using it to build the URL that receives the app's `client_id`/`client_secret`.

### Title
OAuth callback sends `client_secret` to an attacker-controlled `shop` host without domain validation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds an HTTP client whose base URI is derived directly from `auth_query.shop` and posts the app's `client_id` and `client_secret` (plus the authorization `code`) to `https://#{shop}/admin/oauth/access_token`. The `shop` value is never passed through `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, which exists in this gem specifically to enforce that a shop string belongs to a trusted Shopify domain.

### Finding Description
`validate_auth_callback` only checks that the HMAC over `code/host/shop/state/timestamp` is valid and that `state` matches the session cookie: [1](#0-0) 

The HMAC check proves the query was signed with the app's secret for *some* `shop` value, but it does not restrict `shop` to `*.myshopify.com` (or the other `TRUSTED_SHOPIFY_DOMAINS`). That `shop` string is passed unmodified into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, and `HttpClient#initialize` builds `@base_uri` from `session.shop` verbatim: [2](#0-1) 

The request that is then sent contains `client_id`, `client_secret`, and the OAuth `code` in the POST body to that host: [3](#0-2) 

Notably, `Utils::ShopValidator` exists precisely to prevent this class of bug (validating shop domains against `TRUSTED_SHOPIFY_DOMAINS = ["shopify.com", "myshopify.io", "myshopify.com", "spin.dev", "shop.dev"]`), and is used by other OAuth-adjacent flows such as `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb` — but it is conspicuously **not** invoked in `oauth.rb`'s `validate_auth_callback`/`auth_base_uri` path: [4](#0-3) 

This breaks the intended binding: *host validated == host that receives the `client_secret`*. Here, the host that receives the `client_secret` is whatever `shop` string appears in the callback query, without being checked against the trusted-domain allowlist that this very library provides for that purpose.

### Impact Explanation
If a shop value that isn't a genuine Shopify domain reaches `validate_auth_callback` (e.g., a host application that echoes back a request parameter without itself re-validating it, or any code path that constructs an `AuthQuery`/session with attacker-influenced `shop`), the gem will POST the app's `client_id` and `client_secret` to that attacker-controlled host. This is a direct `client_secret` exfiltration path (Critical impact category: "theft or exfiltration of ... the app's `client_secret`").

### Likelihood Explanation
Exploitability depends on whether the HMAC actually binds `shop` tightly enough in the deployed flow and whether the host application passes through an unsanitized `shop`. Given the HMAC does cover `shop`, a purely external attacker cannot forge the callback query without the secret — but the library itself provides no defense-in-depth (`ShopValidator.sanitize!`) at this specific chokepoint even though it does so in every other OAuth-secret-bearing flow in the same codebase, making this an inconsistency/gap rather than a fully demonstrated exploit given only the in-scope library code available to me.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (or `sanitize_shop_domain`) at the start of `validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, before constructing `null_session`/`auth_base_uri`, mirroring the pattern already used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

### Proof of Concept
Not fully constructible from the in-scope library code alone, because the HMAC over `AuthQuery` does cover `shop`, so a pure external attacker cannot supply an arbitrary `shop` without the app's secret through the documented callback entry point. This finding is reported as a defense-in-depth / consistency gap identified by comparing `oauth.rb` against the `ShopValidator` usage pattern established elsewhere in the same library; I could not verify within the available index whether any other code path in this gem constructs `AuthQuery`/`Session` from unsanitized `shop` in a way that a remote unprivileged user could reach without already controlling the app's secret.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
