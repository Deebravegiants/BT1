### Title
Webhook HMAC only authenticates the raw body, not the `shop-domain` header — allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while the `shop` (and `topic`, `webhook_id`) values are read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC over that raw body [3](#0-2) , then passes the unauthenticated `request.shop` value straight into the handler as the tenant identifier. Since the webhook HMAC secret (`Context.api_secret_key` / the app's `client_secret`) is shared across every shop that has installed the app, any shop that installs the app can harvest a valid `(body, hmac)` pair from its own legitimate webhook deliveries and replay it to the app's webhook endpoint with a forged `shopify-shop-domain` header, causing the app to process the webhook as if it belonged to a different (victim) shop.

### Finding Description
The binding that should hold is:
`shop authenticated by HMAC == shop used to attribute/act on the webhook`

In this gem that binding is broken:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the header-provided `hmac` [4](#0-3) .
- For `Webhooks::Request`, `to_signable_string` is just `@raw_body` [1](#0-0)  — none of `shop`, `topic`, or `webhook_id` are part of the signed bytes.
- `shop`, `topic`, and `webhook_id` are pulled from HTTP headers with no cryptographic binding to the HMAC at all [5](#0-4) .
- `Registry.process` only asserts `Utils::HmacValidator.validate(request)` (i.e., body integrity) before handing `request.shop`, `request.topic`, and `request.webhook_id` to the app's handler as trusted metadata [3](#0-2) .

Because the HMAC secret is the app-level `client_secret`, not a per-shop secret, it is identical for every merchant that installs the app. Any merchant can install the app, receive one legitimate webhook (any topic) with a valid `hmac-sha256` header for a given body, and then re-POST that exact `(body, hmac)` pair to the app's public webhook URL while substituting `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) with an arbitrary victim shop domain. `HmacValidator.validate` will still pass because it only checks the (unchanged) body bytes against the (unchanged) hmac; the forged `shop` header is never checked against anything.

### Impact Explanation
This is a cross-tenant boundary break: a malicious, unprivileged internet user (any merchant who can install the app) can make the app believe a webhook event — and the associated payload — pertains to a shop they don't own/control. Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., matching stored sessions, triggering redact/GDPR flows such as `shop/redact`, `customers/redact`, `customers/data_request`, or writing state keyed by shop), this can be leveraged to inject or corrupt data attributed to a victim shop, or falsely trigger shop-scoped side effects for a shop the attacker doesn't control — a cross-tenant access primitive.

### Likelihood Explanation
Exploitation requires no secrets, no privileged account, and no credential leakage — only the ability to install the target app on any shop (a normal, unprivileged action for any Shopify merchant/developer) and to send an HTTP POST to the app's public webhook endpoint, which by design accepts unauthenticated requests validated solely by this HMAC check.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or independently verify that `request.shop` matches an expected/known shop for the session context before trusting it, rather than relying on HMAC-over-body alone to authenticate the tenant. At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are **not** covered by the HMAC and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a normal unprivileged action.
2. Shopify delivers a legitimate webhook to the app's endpoint, e.g. body `{"id":123}` with header `shopify-hmac-sha256: <valid-hmac-for-body>` and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body and `shopify-hmac-sha256` value to the same endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and any topic/webhook-id).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body against the hmac and passes [6](#0-5) ; the forged `shop` header is never validated.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, believing the event originated from `victim-shop.myshopify.com` [7](#0-6) .
