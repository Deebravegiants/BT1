## Title
`IntentGatewayV2.placeOrder` does not validate `order.output.beneficiary`, causing solver-provided output tokens to be permanently burned to `address(0)` — (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` validates that `order.inputs.length != 0` but never validates that `order.output.beneficiary` is non-zero. The same missing check exists in the Tron variant. Because the beneficiary is later derived directly from user-supplied order data and used as the destination of a raw token/ETH transfer in the fill path, an order placed with a zero (or otherwise unset) `beneficiary` causes the solver's output tokens to be sent to `address(0)` and burned, while the order is still marked filled and the user's escrowed input tokens are released to the solver.

### Finding Description
`placeOrder` accepts an arbitrary `Order` struct, including `order.output.beneficiary` (a `bytes32`-encoded EVM address), with only an input-length check: [1](#0-0) 

No check ensures `order.output.beneficiary != bytes32(0)`. The same absence exists in the Tron contract's `placeOrder`: [2](#0-1) 

The beneficiary is later decoded and used unchecked as the transfer target in both the same-chain and cross-chain fill paths: [3](#0-2) [4](#0-3) 

and for cross-chain fills: [5](#0-4) 

In both cases, `beneficiary` is used directly as the target of `_sendValue`/`.call{value:}` or `IERC20.safeTransferFrom`/`safeTransfer`, with no zero-address guard. If `beneficiary == address(0)`, ETH sent via a low-level call to `address(0)` succeeds (any code can call `address(0).call{value}("")`) and ERC20 `transferFrom`/`transfer` to `address(0)` also generally succeeds for standard tokens (no revert), so the output tokens/ETH are irrecoverably burned.

Regardless of who initiates the fill, the order is marked filled (`_filled[commitment] = msg.sender`), and the escrowed input tokens are still released to the filler via `_withdraw`, meaning the exchange is fully consummated on-chain even though the intended recipient (the user, or whichever party `beneficiary` was meant to represent) never receives the output.

This directly mirrors the reported bug class: a user-supplied "receiver"-equivalent field (`beneficiary`) that is unvalidated leads to permanent fund loss if it is left as zero, whether by front-end/SDK mistake, direct low-level contract interaction, or a malformed integration.

### Impact Explanation
If an order is placed with `beneficiary` left at its zero-value default:
- For same-chain orders, the solver's output assets sent as beneficiary payment are burned to `address(0)`, while the solver still claims the user's full escrowed input tokens — the intended recipient never receives anything.
- For cross-chain orders, the same burn occurs on the destination chain, and the source-chain escrow is still released to the solver via `RedeemEscrow`.

This is a concrete, permanent loss of funds reachable from a single user-submitted `placeOrder` transaction combined with a subsequent `fillOrder` call (which requires no special privilege — any solver, or even the order's own placer acting as solver in the same-chain case, can trigger it). It qualifies as Medium severity per the rules (concrete permanent freezing/loss of funds via an unprivileged, single-transaction path).

### Likelihood Explanation
`beneficiary` is a raw `bytes32` field supplied directly by the caller of `placeOrder` with no SDK-side or contract-side enforcement preventing a zero value. This can occur from: a struct/tuple that is only partially populated by calling code, an integration bug that forgets to set the field (exactly the class of user error the referenced report warns about), or direct low-level calls to the contract bypassing SDK helpers. Because `placeOrder` and `fillOrder` are both open, permissionless entry points, the path from mistake to permanent loss requires no privileged actor.

### Recommendation
Add an explicit zero-value check on `order.output.beneficiary` in `placeOrder` (both `evm/src/apps/IntentGatewayV2.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol`), reverting with `InvalidInput()` if `beneficiary == bytes32(0)`. As defense in depth, also validate the decoded `beneficiary` address is non-zero at the point of use in `IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain` before transferring output assets.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` with `order.output.beneficiary = bytes32(0)` and valid `inputs`/other fields — this succeeds because only `order.inputs.length == 0` is checked: [1](#0-0) 
2. A solver calls `fillOrder` with sufficient output amounts. `_fillSameChain` (or `_fillCrossChain` for cross-chain) decodes `beneficiary = address(uint160(uint256(order.output.beneficiary)))` = `address(0)` and transfers the solver's output tokens/ETH there: [4](#0-3) 
3. The transfer to `address(0)` succeeds silently (both native-value low-level calls and standard ERC20 transfers to the zero address do not revert), burning the solver's output funds.
4. `_withdraw` still releases the user's escrowed input tokens to `msg.sender` (the solver), and `OrderFilled` is emitted — the order is fully settled on-chain despite the output funds being irrecoverably lost.
