### Title
Retroactive application of vault interest-rate/reserve-factor changes to already-elapsed, un-accrued time - (File: local-testing/contracts/vault/vault-stx.clar, vault-sbtc.clar, vault-usdc.clar, vault-usdh.clar, vault-ststx.clar, vault-ststxbtc.clar and their mainnet counterparts `v0-vault-*.clar`)

### Summary
This is the same bug class as Neobase M-04: a governance-adjustable parameter that feeds into a time-delta-based accrual calculation is not "settled" (accrued) before the parameter changes, so the new parameter is applied retroactively to a period during which the old parameter was actually in effect.

### Finding Description
Each vault (`vault-stx.clar`, `vault-sbtc.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststx.clar`, `vault-ststxbtc.clar`) tracks a `last-update` timestamp and an `index`/`lindex` pair, and computes accrued interest lazily via `accrue`, which calls `next-index`/`next-liquidity-index` and computes the DAO-treasury reserve cut using the *currently stored* `fee-reserve`, `points-util`/`points-rate` curve values [1](#0-0) .

Governance can update the interest-rate curve and reserve factor at any time via `set-points-util`, `set-points-rate`, and `set-fee-reserve`, exposed through DAO proposals such as `proposal-set-stx-interest-rates.clar` [2](#0-1) . Because `accrue()` computes the entire elapsed interval `now - last-update` using whatever curve/reserve-factor values are stored *at the moment `accrue` finally runs* (not the values that were actually in force during each sub-interval), any elapsed-but-unaccrued time window that straddles a governance parameter change will have its interest and reserve-factor split computed entirely with the *new* parameters. This mirrors the LendingLedger issue precisely: the retroactive effect stems from the state of the contract (whether `accrue`/`update_market` was called in the same block as the parameter change), not from any incorrect governance input.

The identity broken is:
```
interest_accrued(last_update -> now) should equal
  interest(rate_old, last_update -> t_change) + interest(rate_new, t_change -> now)
```
but the actual code computes:
```
interest_accrued(last_update -> now) = interest(rate_new_or_old_whichever_is_current_at_call_time, last_update -> now)
```
This over- or under-mints reserve shares to `.dao-treasury` and over- or under-credits the liquidity index used to compute suppliers' redemption value [3](#0-2) .

### Impact Explanation
Because `reserve-inc`/treasury minting and the liquidity index (`lindex`) that determines supplier redemption value are miscalculated for any vault that isn't accrued in the same block as a rate/reserve-factor change, this results in incorrect distribution of unclaimed yield between suppliers and the DAO treasury — either theft of unclaimed yield from suppliers (if reserve factor is retroactively raised) or dilution/loss to the treasury (if lowered), and this affects every vault that has debt/deposits outstanding at the time of the governance call, not just the caller.

### Likelihood Explanation
Likelihood is comparable to the original finding: any DAO proposal like `proposal-set-stx-interest-rates.clar` that calls `set-points-util`/`set-points-rate`/`set-fee-reserve` without first triggering `accrue()` on the same vault in the same block will produce this drift. There is no code enforcing that `accrue` is called immediately before these setters, and no warning comment analogous to the one in the original `LendingLedger.sol`, so this is a latent, easily-triggered operational condition rather than a rare edge case.

### Recommendation
Have `set-points-util`, `set-points-rate`, and `set-fee-reserve` (and any other function mutating the interest-rate curve/reserve-factor) call `accrue()` on the vault as their first action, so that all interest and reserve calculations are settled using the outgoing parameters up to the exact block of the change, before the new parameters take effect for subsequent accruals.

### Proof of Concept
Conceptually (Clarity pseudo-sequence, analogous to the Solidity PoC in the report):
1. Vault has outstanding debt; `last-update` = T0, current time = T0 + Δ (no `accrue` call in between).
2. Governance calls `proposal-set-stx-interest-rates` → `set-points-rate` changes the borrow-rate curve to a much higher rate.
3. Anyone (or the next borrow/repay/redeem operation) triggers `accrue()`.
4. `accrue()` computes `next-index` over the *entire* interval `[T0, T0+Δ]` using the *new* higher rate curve, even though for most of that interval the old (lower) rate was actually in force — retroactively inflating debt owed by borrowers and/or the reserve cut minted to `dao-treasury`, exactly mirroring `testInsecureRewardUpdate` from the referenced Neobase report.

Note: I was unable to retrieve the exact body of `set-points-util`/`set-points-rate`/`set-fee-reserve` within the tool budget to confirm with 100% certainty whether they explicitly call `accrue()` first; the analysis is based on the confirmed `accrue()` implementation reading live `var-get` state (rather than snapshotted historical parameters) [1](#0-0)  and the setter call sites reachable from DAO proposals [2](#0-1) . If `accrue()` is in fact invoked as the first statement inside each setter, this finding would not apply — this should be verified directly against `set-points-util`/`set-points-rate`/`set-fee-reserve` in `vault-stx.clar`/`v0-vault-stx.clar` before treating this as confirmed.

  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
