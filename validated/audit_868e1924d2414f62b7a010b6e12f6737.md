### Title
Unbounded `Vec::with_capacity` allocation from attacker-controlled length in Pharos validator-set storage-proof decoding, before any Merkle verification - ([File: modules/consensus/pharos/verifier/src/state_proof.rs])

### Summary
`verify_validator_set_proof` (called from `verify_pharos_block`, which any relayer reaches by submitting a Pharos consensus update/validator-set-rotation proof) first calls `compute_all_storage_keys`, which parses the "Solidity long string" length header of `proof.storage_values[idx]` via `bls_data_slots_from_header` **before** the storage values are checked against the trusted state root by `verify_all_storage_proofs`. The same untrusted, unverified header bytes are later re-parsed in `decode_bls_key_from_string_slot`, which does `Vec::with_capacity(str_len)` where `str_len` is derived directly from an attacker-controlled 256-bit storage value with essentially no upper bound check, analogous to the JBIG2/Xpdf class of decoder bugs where an unchecked, attacker-controlled length field drives an allocation/arithmetic operation.

`str_len` has essentially no bound: only `header_val`'s lowest bit needs to be odd. An attacker can set the header 32-byte storage value to any odd, arbitrarily large `U256`, so `str_len` can be truncated to a value close to `usize::MAX` (or `u64::MAX` on 64-bit targets, or `u32::MAX` on 32-bit/wasm targets). This value is used unchecked in `Vec::with_capacity(str_len)`, which immediately panics with a "capacity overflow"/allocation-failure abort when it exceeds `isize::MAX` or fails to allocate — independent of whether the accompanying storage-proof will later be found invalid.

Note also that `(str_len + 31)` is computed with a plain `+` and can itself overflow/wrap on the boundary values, undermining the `data_slots.len() < slots_needed` guard that is supposed to prevent an under-sized slot vector from reaching this point.

This is directly analogous to `JLSEC-2026-80` (Xpdf/JBIG2 `readTextRegionSeg` integer overflow): an attacker-controlled length field taken from untrusted, not-yet-authenticated input data drives unchecked memory-sizing arithmetic/allocation, leading to a crash.

### Impact Explanation
This is reachable by any unprivileged relayer submitting a Pharos consensus update through the ISMP consensus-client dispatch path (`verify_pharos_block` → `state_proof::verify_validator_set_proof`), whenever the observed epoch increments and a `validator_set_proof` is supplied. Because the vulnerable parsing (`compute_all_storage_keys`/`bls_data_slots_from_header`) runs before the state-root Merkle verification, the attacker does not need a genuinely valid proof — merely a malformed `storage_values` entry with the right shape reaches the allocation before rejection. A single malicious/malformed message can crash or abort the node process handling consensus verification for the Pharos state machine, denying service to the light client/consensus update path and halting message delivery for that route (a "route unable to deliver messages" condition per the scan's acceptance criteria).

### Likelihood Explanation
High for a determined attacker: no cryptographic material or valid signatures are required to trigger the crash, since the vulnerable code executes before the storage-proof-to-state-root Merkle verification (`verify_all_storage_proofs`) and before the BLS block-signature check (`verify_block_signature`). The attacker only needs to submit an epoch-incrementing update carrying a `validator_set_proof` whose `storage_values[idx]` (the BLS header slot) is an arbitrary odd 32-byte value.

### Recommendation
- Bound `str_len` (and the intermediate `length`) to a sane maximum (e.g. reject if `header_val` exceeds a small constant, or if `str_len` exceeds a small max string length such as 128) before doing any further arithmetic or allocation.
- Compute `slots_needed` using checked/saturating arithmetic (`str_len.checked_add(31)` / `saturating_add`) rather than raw `+`.
- Avoid `Vec::with_capacity(str_len)` driven directly by unauthenticated input; either cap the capacity to the already-verified `data_slots.len() * 32` bound, or build the vector incrementally without pre-reserving attacker-controlled capacity.
- Move any parsing of unauthenticated `storage_values` (including `compute_all_storage_keys`/`bls_data_slots_from_header`) to occur only after `verify_all_storage_proofs` has authenticated each value against the trusted state root, or re-validate lengths defensively at every stage regardless of ordering.

### Proof of Concept
1. As a relayer, construct a Pharos `VerifierStateUpdate` with `observed_epoch = trusted_epoch + 1` and a `validator_set_proof` (`ValidatorSetProof`) containing:
   - `storage_values[1]` (activePoolSets length) = a small valid count, e.g. `1`.
   - `storage_values[pool_set_start]` = an arbitrary 32-byte pool id.
   - `storage_values[idx]` (the BLS header slot for that validator) = a 32-byte big-endian value that is odd and very large, e.g. `0xFFFF...FFFF` (odd), so `bls_data_slots_from_header` decodes `str_len` as a huge number.
   - `storage_proof`/other fields can be arbitrary/garbage since they are not checked before the crash point.
2. Submit this update through the ISMP dispatch path that invokes `verify_pharos_block` for the Pharos consensus client.
3. Execution reaches `verify_validator_set_proof` → `compute_all_storage_keys` → `bls_data_slots_from_header`, deriving a huge `str_len`; later in `decode_validator_set_from_storage` → `decode_bls_key_from_string_slot`, `Vec::with_capacity(str_len)` is invoked with the huge value, causing an allocation-failure panic/abort in the verifying node before any cryptographic or Merkle check has succeeded.

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
