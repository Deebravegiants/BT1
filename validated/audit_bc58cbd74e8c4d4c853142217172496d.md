### Title
Arithmetic overflow before the borrow-index cap permanently freezes a high-value market - (File: common/src/rates/scaling.rs) [1](#0-0) 

### Summary
A market whose aggregate debt value exceeds the `i128` RAY domain during accrual becomes permanently unusable because every mutating pool operation synchronizes interest before applying the requested action. [2](#0-1)  The overflow occurs while unscaling accrued debt with `scaled.mul(index)` and raises `MathOverflow` before `MAX_BORROW_INDEX_RAY` can cap the index. [3](#0-2)  The repository’s integration test demonstrates that this state blocks `update_indexes`, `withdraw`, and `repay`, and notes that liquidation encounters the same mandatory accrual. [4](#0-3) 

### Finding Description
`global_sync` runs `accrue_step` on every elapsed chunk before the operation-specific mutation proceeds. [5](#0-4)  `accrue_step` evaluates the scaled debt against both the old and new borrow indexes through `scaled_to_original`, which is `scaled.mul(index)`. [6](#0-5)  That multiplication returns a RAY-scaled `i128`; although the fixed-point implementation widens the intermediate product to `I256`, it still requires the final quotient to fit in `i128` and otherwise returns `MathOverflow`. [7](#0-6) 

The borrow-index ceiling does not prevent this condition because it is applied only to the index after the interest factor is calculated, while the vulnerable value multiplication is `borrowed × index`. [8](#0-7)  Therefore, a sufficiently large `borrowed` share total can overflow the value domain while the index itself remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

An unprivileged account can reach the setup through ordinary controller `supply` and `borrow` calls on a configured market, and any account can subsequently invoke `update_indexes` or an exit operation after enough time has passed. [10](#0-9)  Once the first accrual fails, `last_timestamp` is not advanced and every later call starts from the same failing accrual window. [11](#0-10) 

### Impact Explanation
The market permanently freezes: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot process the debt, and recapitalization or other market mutations cannot proceed because they also load an interest-synced cache first. [2](#0-1)  This leaves user collateral and supplied liquidity inaccessible through protocol paths and prevents the protocol from resolving its outstanding debt. [4](#0-3) 

The condition does not require privileged input after market configuration because it depends on reachable market totals, utilization, and elapsed time rather than on an attacker-controlled arithmetic type conversion. [12](#0-11)  The demonstrated failure is `MathOverflow`, not a transaction-local revert that can be avoided by changing the requested withdrawal or repayment amount. [13](#0-12) 

### Likelihood Explanation
The trigger requires an extremely large market and sustained high utilization; the regression test uses one billion 18-decimal tokens supplied and approximately 98% utilization under the steep XLM curve. [14](#0-13)  Those amounts are within the protocol’s admitted arithmetic domain for token-to-RAY conversion, but accrual later pushes `borrowed × borrow_index` beyond the RAY value domain before the index reaches its configured ceiling. [15](#0-14)  Once those market conditions exist, no attacker needs special authorization: the next permissionless `update_indexes` or ordinary user exit hits the overflow deterministically. [16](#0-15) 

### Recommendation
Bound accrued aggregate debt before index growth, rather than relying only on `MAX_BORROW_INDEX_RAY`. [8](#0-7)  In `accrue_step`, compute the maximum `borrowed` scaled total that remains representable for the prospective index and clamp the index before calling the final debt-value multiplication; alternatively, maintain a checked aggregate-debt ceiling and return a recoverable market state rather than letting accrual enter an unreversible overflow state. [6](#0-5)  An emergency no-accrual settlement path should also be available for withdrawal, repayment, liquidation, and bad-debt processing after this ceiling is reached. [2](#0-1) 

### Proof of Concept
1. Configure an 18-decimal market with the steep `xlm_curve`, then have a supplier call controller `supply` with `1_000_000_000 * 10^18` base units. [17](#0-16) 
2. Have a borrower supply sufficient collateral elsewhere and call controller `borrow` for approximately 98% of that market’s principal. [18](#0-17) 
3. Advance ledger time and invoke permissionless controller `update_indexes`; accrual eventually panics with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`. [19](#0-18) 
4. Call controller `withdraw` or `repay`; both call the pool’s `synced_market` path, repeat the same failing accrual, and revert before mutating the position. [2](#0-1) 
5. The repository’s executable regression demonstrates both user exits returning `MathOverflow` after the index-update failure. [20](#0-19)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
