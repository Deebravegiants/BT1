Based on my investigation, I've confirmed the concrete vulnerability pattern. This gem's webhook HMAC validation covers only the raw request body and never binds the `shop`, `topic`, or `webhook-id` values that the library trusts and hands off to the app's webhook handler.

### Title
Webhook HMAC validation does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/verifies the HMAC purely against that signable string [2](#0-1) . Meanwhile `Registry.process` trusts `request.shop` (sourced from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) and forwards it directly to the app's handler as the tenant identifier [3](#0-2) [4](#0-3) .

### Finding Description
The equality this code implicitly assumes is: `shop reported in HMAC-signed content == shop used to attribute the webhook event`. In reality, `shop` (and `topic`, `webhook_id`, `api_version`) come from HTTP headers that are never part of `to_signable_string`, so they are never covered by the HMAC in `HmacValidator.validate_signature` [2](#0-1) . Any request whose body+HMAC pair is valid for the configured `api_secret_key`/`old_api_secret_key` will pass validation in `Registry.process` [5](#0-4)  regardless of which `shop-domain` header accompanies it. An attacker who controls (or has previously captured) one legitimate, correctly-signed webhook body/HMAC pair — e.g., from their own installed test shop, since a merchant can trigger events on their own store and capture the delivered payload/HMAC — can resend that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim shop. `HmacValidator.validate` still returns `true` because it only ever re-derives the HMAC from `@raw_body` [1](#0-0) , and `Registry.process` then dispatches the handler with `shop: request.shop` set to the attacker-chosen value [6](#0-5) .

### Impact Explanation
This breaks the tenant-isolation binding the gem is expected to provide: an app author who trusts `WebhookMetadata#shop` (as passed by `Registry.process`) because the HMAC "validated" is actually processing attacker-forged shop attribution. Depending on the handler's logic (e.g., persisting state, revoking data, updating billing, or driving `customers/redact`/`shop/redact` GDPR handlers which are also dispatched through this same path) this enables cross-tenant data corruption or spoofed compliance actions against a shop the attacker does not control — a cross-tenant access vulnerability carrying the app's trusted webhook-authentication guarantee.

### Likelihood Explanation
Exploitation requires the attacker to have at least one legitimately signed body+HMAC pair, which is trivially obtainable by installing the app on any shop (including their own free/dev store) and capturing a delivered webhook. The only other requirement is the ability to POST an HTTP request with a spoofed header to the app's public webhook endpoint, which by definition is internet-reachable. No access to `api_secret_key`, tokens, or the victim's credentials is needed.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable content, or otherwise ensure `Registry.process`/`WebhookMetadata` cross-checks the `shop-domain` header against a value that is itself authenticated (e.g., verify the shop is independently known/authorized before dispatch), so the shop attribution cannot be forged independently of the signed body.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and capture a delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's `api_secret_key`).
2. Send a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic` set to any registered topic.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers since only body-derived HMAC is checked [5](#0-4) ; `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the app to process attacker-supplied data as if it originated from the victim shop.
