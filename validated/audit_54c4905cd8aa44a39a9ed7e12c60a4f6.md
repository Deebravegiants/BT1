### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value that is handed to the app's webhook handler (and used to attribute the event to a tenant) is read from an HTTP header that is never included in the signed material. Any actor able to obtain one validly-signed webhook payload (e.g., any merchant who installs the app, since the HMAC secret — the app's `api_secret_key` — is shared across all shops of the app, not per-shop) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header value, and the gem will report the request as validly authenticated for the spoofed shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery`, whose `to_signable_string` is the only data covered by the HMAC: [1](#0-0) 

Note that `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string`, i.e., the body, and returns a boolean — it has no knowledge of the `shop` field at all: [3](#0-2) 

`Registry.process` uses this boolean result to gate processing, then passes the *unauthenticated* `request.shop` directly into the `WebhookMetadata` that is forwarded to the app's handler: [4](#0-3) 

The gem's own documentation instructs app developers to trust `data.shop` as "The shop domain of the webhook" without warning that this value is unauthenticated: [5](#0-4) 

This is the same bug class as the reported Solidity issue: a value that is *used* to make a security-relevant decision (fee amount / tenant attribution) is not actually *covered* by the integrity check (parenthesized division / HMAC signature) that is supposed to bind it. Here, the broken identity-binding equality is:

`verified_bytes (raw_body signed by HMAC-SHA256 with api_secret_key) != shop_attribution_bytes (shop-domain header trusted by Registry.process/WebhookMetadata)`

Contrast this with the OAuth callback path, where `shop` *is* included in the HMAC-signed parameters via `AuthQuery#to_signable_string`, so the same class of bug does not exist there: [6](#0-5) 

### Impact Explanation
Because the app's `api_secret_key` is shared across every shop that installs the app (it is not shop-specific), any merchant that installs the app can legitimately receive real webhook deliveries with a valid HMAC computed over some body. That merchant (an "unprivileged" actor relative to other tenants of the same app) can capture such a delivery and replay the identical `(raw_body, hmac)` pair to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop's domain. `Registry.process` will validate the HMAC successfully (since it only checks the body) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application that uses `data.shop` to select the tenant record to update (a pattern explicitly encouraged by this gem's documentation and sample handler) will write or act on data under the wrong tenant — a cross-tenant integrity/confidentiality violation, which maps to the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop to have the app installed and receive at least one real webhook (trivial, normal onboarding flow), and (2) the ability to send an HTTP POST to the app's public webhook endpoint with a modified header, which is inherent to how webhook endpoints are exposed. No access to `api_secret_key`, access tokens, or any privileged account is required, and no host-application misuse of the API beyond following the documented `data.shop` usage pattern is needed.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) as part of the material that is verified against the HMAC, or independently verify that `request.shop` corresponds to a shop with a currently valid installation/session before trusting it for tenant attribution, e.g., have `Request#to_signable_string`/`HmacValidator` bind the shop header into the signed value it checks, or have `Registry.process` cross-check `request.shop` against an out-of-band authoritative source instead of trusting the header verbatim.

### Proof of Concept
1. App merchant A installs the app; their shop receives a legitimate webhook delivery with body `B` and header `shopify-hmac-sha256: H` (computed by Shopify using the app's shared `api_secret_key`), plus `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (merchant A) records `(B, H)`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `shopify-hmac-sha256: H` unchanged, but `shopify-shop-domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "shop-victim.myshopify.com", body: request.parsed_body, ...))` is invoked, and the host app processes/attributes the webhook data to `shop-victim`, despite it never having sent this webhook.
