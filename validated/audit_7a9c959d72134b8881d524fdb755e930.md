### Title
Unchecked ERC20 `transfer` return value in Tron IntentGatewayV2 withdraw/sweep paths permanently locks escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed intent funds and sweeps protocol dust using a raw low-level `.call` to the ERC20 `transfer` selector, checking only that the call did not revert, not that the token's returned boolean indicates success.

### Finding Description
In `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`) and in the `SweepDust` branch of `onAccept`, token payouts are performed as: [2](#0-1) [3](#0-2) 

`success` here only reflects whether the external call reverted, not the ABI-encoded boolean that many ERC20 implementations return to signal a failed transfer without reverting (e.g. tokens following the "return false on failure" pattern, or tokens with no return value at all which happen to work only by coincidence). If a token returns `false` instead of reverting, this code treats the transfer as successful.

Critically, before this loop runs, `withdraw()` already commits the order to a finalized state: [4](#0-3) 

`_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented regardless of whether the token was actually delivered to the beneficiary. Since `onAccept` is invoked once via the ISMP host on message delivery and `_filled`/`_orders` accounting is irreversible from this code path, a silently-failed transfer leaves the escrowed tokens permanently stuck in the contract with no beneficiary and no retry mechanism — the commitment is already marked filled, so the withdrawal cannot be attempted again through any user-facing entry point. This is directly analogous to the reported "use safeTransfer instead of transfer" issue: the reachable path here is delivery of a `RedeemEscrow`/`RefundEscrow`/`SweepDust` ISMP message, which any relayer can trigger by delivering a valid cross-chain message for a legitimately placed intent order.

### Impact Explanation
Permanent freezing of escrowed intent funds for any input/output token that signals transfer failure by returning `false` rather than reverting. Because `_filled` and `_orders` are updated unconditionally in the same function before/around the transfer attempt, there is no compensating control and no way to retry or recover the tokens through the contract's public interface — this matches the Medium/High "concrete...permanent freezing of funds" bar for a reachable, unprivileged (relayer-delivered) path.

### Likelihood Explanation
Likelihood depends on whether any configured input/output token on the Tron intents deployment can return `false` on failed transfer instead of reverting (a known non-standard ERC20 behavior, common enough that OpenZeppelin's `SafeERC20` exists specifically to guard against it — which the sibling `evm/src/apps/intentsv2/IntentsBase.sol` correctly uses via `safeTransfer`/`safeTransferFrom`). Any order using such a token, or any dust-sweep involving such a token, triggers the bug on ordinary, permissionless message delivery — no privileged or malicious actor required.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler of `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the already-correct implementation in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()` and `_sweepDust()` (which the Tron contract already imports `SafeERC20` and applies `using SafeERC20 for IERC20;` for, but never uses in these two functions).

### Proof of Concept
1. Deploy/register an ERC20-like token (e.g., a Tron TRC20 following the "return false, don't revert" convention) as an order's input token.
2. User places an order via `placeOrder`, escrowing that token; solver fills the order on the destination chain.
3. Hyperbridge relays the `RedeemEscrow` POST request; `onAccept` → `withdraw()` executes.
4. The token's `transfer(beneficiary, amount)` call returns `false` (insufficient allowance/internal blacklist/etc.) but does not revert; `token.call(...)` succeeds (`success == true`).
5. `withdraw()` proceeds to set `_filled[commitment] = beneficiary` and decrement `_orders[commitment][token] -= amount` as if the transfer succeeded.
6. Beneficiary never receives tokens; the commitment is now finalized, and the escrowed balance remains locked in the contract with no way to retry the withdrawal.
