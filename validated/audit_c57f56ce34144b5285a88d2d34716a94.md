### Title
User account enumeration via differing login error messages on session creation - (File: core/web/sessions_controller.go)

### Summary
The `/sessions` login endpoint returns the raw, unmodified backend error message to an unauthenticated caller. Because the underlying authentication providers (`localauth`, `ldapauth`, `oidcauth`) return distinguishable error strings depending on whether the submitted email corresponds to an existing account, an unprivileged remote client can enumerate valid user accounts simply by submitting different emails and observing the returned error text — the same bug class (CWE-200) as the referenced Plone `membership_tool.py` account-enumeration advisory.

### Finding Description
`SessionsController.Create` passes any error from `AuthenticationProvider().CreateSession` straight to the client via `jsonAPIError`, which serializes `err.Error()` into the JSON response body: [1](#0-0) [2](#0-1) 

In the local auth provider, `CreateSession` first calls `FindUser`, which executes a raw SQL lookup and returns the underlying `sql.ErrNoRows` error unmodified when the email does not exist. If the email does exist but the password is wrong, a distinctly different, hand-crafted error `"Invalid password"` (or `"Invalid email"`) is returned instead: [3](#0-2) [4](#0-3) 

The same pattern exists in the LDAP authenticator, where a nonexistent user yields `"no users found with provided email"` while an existing user with wrong credentials yields `"invalid password"`/`"invalid email"`: [5](#0-4) [6](#0-5) 

And in the OIDC authenticator's local-admin fallback path: [7](#0-6) 

Because these three distinct error strings ("no rows"/"no users found" vs. "Invalid email" vs. "Invalid password") propagate unmodified to the HTTP response body, an unauthenticated caller hitting `POST /sessions` can distinguish "account does not exist" from "account exists, wrong credentials" purely from the response content — a textbook account enumeration oracle, directly analogous to the Plone `membership_tool.py` CVE-2012-5497 bug class.

### Impact Explanation
An unauthenticated, unprivileged remote attacker can enumerate valid Chainlink node operator email/usernames by brute-forcing the `/sessions` endpoint and observing which error string is returned. This discloses which accounts exist on the node, which can then be used to focus credential-stuffing or password-guessing attacks against known-valid accounts, and can leak operational/organizational information (e.g., confirming an admin's email exists). This matches CWE-200 (Information Exposure) with limited confidentiality impact, consistent with the CVSS vector in the reference advisory (`C:L/I:N/A:N`).

### Likelihood Explanation
High likelihood: the `/sessions` endpoint is reachable without authentication by any network client with access to the node's operator API, requires no special conditions, and the differing error text is returned deterministically based solely on the submitted email.

### Recommendation
Normalize all authentication failure responses returned by `SessionsController.Create` (and the underlying `CreateSession`/`FindUser` implementations in `localauth`, `ldapauth`, and `oidcauth`) to a single generic message (e.g., `"invalid credentials"`) regardless of whether the email exists, the password is wrong, or MFA fails, and ensure timing is constant-time across these branches to avoid timing-based enumeration as well.

### Proof of Concept
1. `POST /sessions` with `{"email":"knownadmin@example.com","password":"wrongpassword"}` → response body contains `"Invalid password"`.
2. `POST /sessions` with `{"email":"doesnotexist@example.com","password":"wrongpassword"}` → response body contains a different message (e.g., `"sql: no rows in result set"` or, for LDAP, `"no users found with provided email"`).
3. Comparing the two distinct response bodies across many candidate emails allows an attacker to build a list of valid account emails on the node without any authentication.

// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the LDAP server
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
