### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the HMAC solely against that raw body with the app's single `api_secret_key`. The `shop` (tenant) identifier that the registry hands to the app's webhook handler is read from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, which is never included in the signed material.

### Finding Description
`Request#to_signable_string` is defined as simply the raw body: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC using `verifiable_query.to_signable_string` (the body) and `Context.api_secret_key`: [2](#0-1) 

`Registry.process` calls this validator and then, once it passes, blindly trusts `request.shop` (parsed from the unauthenticated header) to build the `WebhookMetadata` object passed into the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header used to attribute the webhook == shop cryptographically bound by the HMAC`. Here, the equality is broken — the HMAC only proves "this body byte-stream was signed with this app's shared `client_secret`," it proves nothing about which shop the header claims to be from. Because a single app-level `client_secret` is used for every shop that has installed the app (there is no per-shop signing key in this design), any tenant that has legitimately installed the app can capture a validly-HMAC'd webhook body/signature pair from their own store's webhook deliveries and replay the same body+HMAC while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still return `true` because it never inspects the shop header, and the (forged) `shop` value flows straight into the handler as an authenticated tenant identifier.

This is the same root-cause pattern as the reported analog class: a field (`shop`) that is acted upon by downstream logic is not covered by the integrity check (HMAC) that is supposed to authenticate the whole request.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` as the tenant key to look up/update per-shop state (the documented and expected usage pattern shown throughout `docs/usage/webhooks.md` and the handler contract), a malicious/compromised merchant with a legitimate install can forge webhook deliveries "from" a victim shop, causing cross-tenant data confusion (e.g., orders/customers/inventory events attributed to, and acted on behalf of, a different tenant). This matches the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only that the attacker (1) have their own legitimate install of the target app (any real merchant qualifies, not a privileged account within this gem's threat model) and (2) be able to POST directly to the app's public webhook endpoint with attacker-chosen headers, which any unauthenticated internet user can do since Shopify webhook endpoints are plain HTTP endpoints with no other transport-level authentication. No secrets, tokens, or social engineering are needed — only body/HMAC pairs the attacker already legitimately possesses from their own shop's traffic.

### Recommendation
Include the shop domain (and ideally the webhook id/topic) inside the HMAC-signed material, or otherwise cryptographically bind the shop header to the signature, e.g., by having `to_signable_string` incorporate `shop` alongside the body, or by validating the shop domain against a stored/expected value (e.g. compare to shop associated with a known offline session/webhook id) rather than trusting the header outright. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated header data and must never be used as a sole tenant key without additional server-side verification (e.g. cross-checking against the shop recorded when the specific `webhook_id` was registered).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook, capturing:
   - Raw body `B`
   - Header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` computed with the app's `client_secret`)
2. Attacker replays a POST to the app's webhook endpoint with:
   - Body `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since HMAC only covers `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and performs tenant-scoped actions under the attacker-controlled `shop` value. [6](#0-5)

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
