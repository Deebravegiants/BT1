### Title
Fee-on-transfer underlying tokens cause `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` to dispatch cross-chain messages crediting more than actually locked - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin) locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then encodes `params.amount` — the amount the caller *requested*, not what the contract *actually received* — into the cross-chain `Message` that gets dispatched via ISMP. For fee-on-transfer/deflationary underlying tokens, the contract receives less than `params.amount`, yet the destination-chain peer will unlock/mint the full, unreduced `message.amount` to the beneficiary.

### Finding Description
In `send()`: [1](#0-0) 

`IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` is called without measuring the actual token balance delta. `_buildDispatchPost` then encodes `amount: params.amount` (the pre-fee, requested amount) into the message body: [2](#0-1) 

This uncorrected amount is what the destination-chain contract pays out in `onAccept`: [3](#0-2) 

This is precisely the bug class described in the external report: an amount that should reflect actual tokens received is instead recorded/propagated using the pre-fee nominal amount, causing accounting (here, the ISMP message payload driving the destination unlock) to diverge from the tokens actually custodied by the contract. The identical pattern exists in the upgradeable variant: [4](#0-3) 

Notably, the codebase's own `IntentGatewayV2` contract already fixes this exact class of bug elsewhere by diffing balances before/after transfer and mutating the escrowed/committed amount accordingly: [5](#0-4) 
This confirms the project is aware of and defends against fee-on-transfer discrepancies in one bridging path (`IntentGatewayV2`) but not in the `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lock-and-release bridge.

### Impact Explanation
`WrappedHyperFungibleToken` implements a lock-on-source/unlock-on-destination token bridge: each side holds a pool of the underlying token that backs cross-chain transfers. If `_underlying` is a fee-on-transfer token, every `send()` call locks strictly less than `params.amount`, but the destination peer still unlocks the full `params.amount` from its own token pool. This creates a persistent, cumulative shortfall between what's locked on the source chain and what's paid out on the destination chain (and vice versa for return transfers), progressively draining the destination pool's underlying token reserves until later legitimate `onAccept`/timeout-refund calls cannot be honored — i.e., permanent freezing/loss of funds for other users of the same bridge instance. This is an unbacked-mint/unlock analog: value paid out exceeds value actually escrowed.

### Likelihood Explanation
Triggerable by any unprivileged user calling `send()` with a fee-on-transfer underlying token configured via `configure()`/`addChain()`. No special privileges are required beyond owning/approving the fee-on-transfer token; each call directly reduces backing while the destination side is instructed via the ISMP dispatched message to pay the full nominal amount. The likelihood depends on the owner choosing a fee-on-transfer/deflationary ERC20 as `_underlying`, which is a normal, expected configuration risk for a generic "wrap any ERC20" bridge.

### Recommendation
In `send()`, measure the actual balance delta after `safeTransferFrom` (as already done in `IntentGatewayV2.placeOrder`) and use that measured amount — not `params.amount` — when building the dispatched `Message`/`DispatchPost`. Alternatively, explicitly document and enforce (e.g., via a token allow-list or transfer-amount validation) that fee-on-transfer/rebasing tokens are unsupported as `_underlying`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a fee-on-transfer token (e.g., 1% fee) and registers a peer contract/module on chain B.
2. Alice calls `send({amount: 1000e18, to: bob, dest: chainB, ...})`. Contract A actually receives only 990e18 (1% fee burned/redirected), confirmed by `balanceOf(address(this))` diff, but the dispatched `Message.amount` is 1000e18.
3. Once relayed and proven, chain B's `onAccept` executes `IERC20(_underlying).safeTransfer(bob, 1000e18)`, paying out 1000e18 from chain B's pool even though chain A's pool only holds 990e18 of backing for this transfer.
4. Repeating this drains chain B's pool by 1% of every FOT transfer's notional value, eventually leaving it insolvent for other users' legitimate unlocks/refunds.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
