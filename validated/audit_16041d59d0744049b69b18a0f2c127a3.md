## Title
Webhook `shop` identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) identity purely from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature it validates against only covers the raw request body. Any attacker who can obtain one valid `(raw_body, hmac)` pair for their own installation can replay it with a different `shop-domain` header and have `ShopifyAPI::Webhooks::Registry.process` treat the payload as authentic for an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body — no header, including `shop`, is part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-sourced, none HMAC-covered) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The binding the code implicitly assumes but never enforces is:
```
hmac_valid(raw_body) == true  ⇒  shop_header == shop_that_actually_produced(raw_body)
```
This equality does not hold. The HMAC secret (`api_secret_key`) is shared across *all* shops that install the app — it is not shop-specific. So `HMAC(secret, body)` is valid for that `body` regardless of which shop it was originally sent for. An attacker who legitimately installs the app on their own (e.g., free Shopify Partner dev) store will receive real webhook deliveries containing a valid `raw_body` + `hmac` pair signed with the app's shared secret. They can then replay that exact `raw_body`/`hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` (it never inspects the header), and `Registry.process` dispatches the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to scope any webhook side effects (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, or custom topics that delete/rotate data, revoke sessions, or write to a shop-scoped record) to the correct tenant. Because the gem provides no protection and documents `shop` as coming straight from the header, an attacker can trigger handler logic keyed to a victim shop id/domain — i.e., cross-tenant access/action forgery — satisfying the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Any unprivileged internet user can self-install the target app on their own dev/trial store (something Shopify's platform allows for free), which is sufficient to obtain one authentic `(body, hmac)` pair signed by the app's shared secret. No access to the app's `client_secret`, access tokens, or victim credentials is required — only the ability to receive one webhook delivery for their own tenant and replay it to the endpoint with a modified header, which is trivial for anyone who can send arbitrary HTTP requests to the app's public webhook route.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the HMAC-signed material, or otherwise cryptographically bind the header values to the verified body (e.g., include the header set in `to_signable_string`, or require the caller to independently confirm `shop` is a currently-installed/expected tenant with an existing session before trusting it). At minimum, document and enforce that `WebhookMetadata#shop` must not be treated as authenticated by `HmacValidator.validate` alone, and provide a method that fails closed unless the shop is cross-checked against a known session store.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers/receives a webhook, capturing the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`: unchanged or any registered topic
3. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes `HMAC(secret, B)` and compares to `H`, per [1](#0-0) .
4. `Registry.process` proceeds and calls the registered handler with `shop: "victim-shop.myshopify.com"` per [4](#0-3) , causing the host application to execute tenant-scoped logic against the victim shop using attacker-supplied body content.
