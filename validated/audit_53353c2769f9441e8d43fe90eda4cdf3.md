### Title
Unbounded `order.inputs`/`output.assets` arrays let a placer permanently brick fill, refund, and cancel of their own order via out-of-gas - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` accepts an `Order` whose `inputs` array length is only checked to be non-zero (`evm/src/apps/IntentGatewayV2.sol` line 195: `if (order.inputs.length == 0) revert InvalidInput();`). No upper bound exists. `fillOrder` requires `order.output.assets.length == order.inputs.length` (line 476), and every settlement path — fill, cancel, and cross-chain refund — ultimately calls `IntentsBase._withdraw`, which loops once per escrowed token performing an `SLOAD`, an `SSTORE`, and an external `transfer`/native send per iteration (`evm/src/apps/intentsv2/IntentsBase.sol` lines 451-470). This is structurally the same bug class as OpenQ H-7: an attacker-controlled, unbounded array drives a for-loop whose gas cost the attacker — not the protocol — controls, and once that cost exceeds the block gas limit, no transaction that touches the loop can ever succeed again.

### Finding Description
`placeOrder` escrows one entry per element of `order.inputs` (`evm/src/apps/IntentGatewayV2.sol` lines 228-329, 364-373), rejecting only duplicate tokens within a single order, not the array length. A placer can therefore construct an order with hundreds or thousands of distinct (self-deployed, trivial) ERC-20 tokens as inputs, each escrowed for a minimal amount (down to 1 wei), and a matching number of `output.assets` entries (`fillOrder` enforces `order.inputs.length == outputsLen`, line 476).

Every path that releases or refunds escrow funnels through `_withdraw`:

This is reached from `_fillSameChain`/`_fillCrossChain` (via `fillOrder`), `_cancelSameChain`, `_cancelFromSource`, and `_cancelFromDest` (via `cancelOrder`), all in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`. Because `body.tokens` is sized to `order.inputs.length` for the whole order (no partial-array slicing on full fills/cancels), a sufficiently large `inputs` array makes the loop's gas cost exceed the destination chain's block gas limit. At that point:
- No solver can call `fillOrder` (the loop inside `_withdraw` alone OOGs before delivering outputs).
- No one can `cancelOrder` on a same-chain order (`_cancelSameChain` → `_withdraw` OOGs).
- The cross-chain cancel path also calls `_withdraw` on the source chain once the refund message arrives (`_cancelFromSource`), so even that route is permanently blocked.

The escrowed input tokens (and any protocol/relayer fees deposited with the order) become permanently locked in the `IntentGatewayV2` contract, with no code path able to unwind them, mirroring the OpenQ `DepositManager.refundDeposit()` OOG bug: an unbounded, attacker-sized array iterated in a fund-release loop with no cap.

### Impact Explanation
This is a **permanent freezing of funds**: escrowed input tokens and Hyperbridge relayer fees for the crafted order become irrecoverable once the array is large enough to OOG every code path that reads it (fill, same-chain cancel, and the destination-side leg of a cross-chain cancel). Because `placeOrder` is a permissionless, single-transaction entry point reachable by any user, this is a High severity availability/fund-freezing issue: any placer can self-grief (locking their own funds, which is limited impact) but more importantly, if this pattern is combined with a partial-fill/partial-cancel accounting bug or reused for orders funded by others (e.g., via `session`/paymaster flows or Solver-side escrow paid on behalf of another beneficiary), it generalizes to third-party fund loss. Even limited to self-lock, it is a concrete violation of "escrowed funds must always be redeemable by cancel/refund," which the protocol's own design (same-chain cancel is documented as "immediate" — `docs/content/developers/evm/intent-gateway/overview.mdx` line 27) promises.

### Likelihood Explanation
Likelihood is high: constructing the order requires only deploying N minimal ERC-20 contracts (cheap, a few thousand gas each, can be done ahead of time and reused across many orders) and calling `placeOrder` once with N inputs and N dummy outputs. No privileged role, collusion, or special timing is needed — this is reachable from a single submitted transaction by any unprivileged user, satisfying the required "single transaction/order" reachability bar. The only variable is exactly how large N needs to be relative to the deployed chain's gas limit, but there is no cap in the code preventing N from growing arbitrarily.

### Recommendation
Bound `order.inputs.length` (and correspondingly `order.output.assets.length`) to a small protocol-defined maximum in `placeOrder`, enforced before escrow, e.g. `if (order.inputs.length > MAX_ORDER_ASSETS) revert InvalidInput();`. Additionally, consider decoupling the cost of `_withdraw`'s loop from a single atomic call (e.g., allow per-token/batched release with a gas-safe upper bound per call) so that even a legitimately large multi-asset order cannot brick its own settlement.

### Proof of Concept
1. Attacker deploys `N` (e.g., 2,000) minimal ERC-20 tokens, each with trivial `transfer`/`balanceOf` implementations, and mints/approves 1 wei of each to themselves.
2. Attacker calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.inputs` containing all `N` distinct token addresses (amount = 1 wei each) and `order.output.assets` containing `N` matching dummy entries so `fillOrder`'s length check passes; source == destination (same-chain) for the simplest repro.
   - `evm/src/apps/IntentGatewayV2.sol` lines 194-415 accepts this; no bound rejects large `N`.
3. Escrow for all `N` tokens is recorded in `_orders[commitment][token]` (line 364-373).
4. Any solver attempting `fillOrder(order, options)` triggers `_fillSameChain` → `_withdraw`, whose `for` loop over `N` tokens (`IntentsBase.sol` lines 456-470) exceeds the block gas limit and reverts every time, regardless of gas supplied up to the block limit.
5. The order placer calls `cancelOrder(order, options)`; since `isSameChain` is true, `_cancelSameChain` also calls `_withdraw` over the same `N`-length array and OOGs identically.
6. Escrowed tokens and any deposited relayer fees for this commitment are now unrecoverable through any exposed function. [1](#0-0) [2](#0-1) [3](#0-2)

```text
    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }
    }
```
