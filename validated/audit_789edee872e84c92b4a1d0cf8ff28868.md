## Analysis

The reported bug class (`StoreChunksRequest` accepted without a signature/authentication root, so requests can't be attributed to a legitimate sender) maps to an analogous pattern in `orb-core`'s self-serve signup relay integration.

### Title
Unsigned `RelayPayload` messages are trusted based solely on unauthenticated `src.id` field, allowing spoofed control of the self-serve signup flow - (File: `orb-relay-client/src/client.rs`)

### Summary
`orb-core` uses `orb-relay-client` to exchange self-serve signup control messages (`StartCapture`, `RequestState`, `CaptureTriggerTimeout`, `SignupEnded`, etc.) between the Orb and a user's phone app over the Orb-Relay service. Authentication (token or ZKP) is only performed once, at connection establishment time, via `send_connect_request` [1](#0-0) . Individual `RelayPayload` messages delivered afterward carry no signature or other cryptographic binding to that authenticated identity — the client's only "authentication" check on each incoming payload is a plaintext string comparison of the payload's `src.id` field against the locally configured `dst_id`.

### Finding Description
In the main receive loop, the client dispatches any payload whose `src.id` matches the configured peer id directly into the message buffer that drives orb behavior: [2](#0-1) 

There is no signature field on `RelayPayload` and no verification that this specific message actually originated from the entity that completed the token/ZKP handshake — `src` is just data embedded in the message by whichever party (the relay service, or anything able to inject on that stream) constructs the response. This is structurally the same gap as the reported `StoreChunksRequest` issue: a message-processing endpoint accepts and acts on request data with no signature tying it to an authenticated principal, relying only on unauthenticated metadata fields for attribution.

This trust is then used to drive safety/state-affecting decisions in the signup plan. For example, `proceed_with_biometric_capture` blocks on receiving a `self_serve::app::v1::StartCapture` message from the relay and, once received, immediately starts biometric capture and reports `CaptureStarted`: [3](#0-2) 

The relay session itself is set up using `orb_relay_app_id`, which comes straight from the (unprivileged) user's QR code data returned by the backend during signup, and is only cryptographically checked as part of the broader `UserData` verification, not per relay message: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because individual relay messages are not signed, any component able to place a payload on the stream with a forged `src` field matching the configured peer can control the state of an in-progress self-serve signup: it can spoof `StartCapture` to force premature biometric capture, spoof `RequestState`/replay logic to desynchronize state (see the special-case in the main loop that replays `last_message` for `RequestState`), or forge `SignupEnded`/`CaptureTriggerTimeout` to prematurely terminate or bleed state across what should be an isolated signup session. This is a cross-signup state-bleed / misattribution risk consistent with the "medium risk" classification of the original report, since it lets non-authenticated-per-message data influence signup/biometric-capture control flow that should only be actionable by the specific paired app session.

### Likelihood Explanation
Exploitation requires only the ability to inject a `RelayConnectResponse::Payload` on the already-open bidirectional stream with a `src.id` equal to the peer's configured id — no signature or proof of possession of the peer's authenticated session is required, since the client performs no per-message signature check, only the string comparison shown above.

### Recommendation
Add a per-message signature (or MAC bound to the session's authenticated key material established at connect time) to `RelayPayload`, and verify it in the receive loop in `orb-relay-client/src/client.rs` before accepting a message into the buffer, rather than relying solely on the unauthenticated `src.id` string field.

### Proof of Concept
Not directly reproducible from `orb-core` alone (the relay transport/server enforcement lives outside this repo), but conceptually: connect two clients through Orb-Relay, then craft/replay a `RelayConnectResponse::Payload` whose `src` is set to the victim's peer identity — `orb-relay-client/src/client.rs` lines 425-453 will accept and forward this payload to the signup logic (`src/plans/mod.rs` lines 2068-2106) with no signature verification.

                        signal: z.signal.clone(),
                        nullifier_hash: z.nullifier_hash.clone(),
                        proof: z.proof.clone(),
                    }),
                }),
            })),
        })
        .await
        .wrap_err("Failed to send connect request")

async fn proceed_with_biometric_capture(orb: &mut Orb) -> Result<bool> {
    let Config {
        self_serve,
        self_serve_app_skip_capture_trigger,
        self_serve_app_capture_trigger_timeout,
        ..
    } = *orb.config.lock().await;
    if !self_serve || self_serve_app_skip_capture_trigger {
        // Biometric capture not gated by a user action. Continue.
        orb.ui.signup_start();
        return Ok(true);
    }

    let orb_relay = orb.orb_relay.as_mut().expect("orb_relay to exist");

    tracing::info!("Waiting for self-serve biometric-capture trigger...");
    if let Err(e) = orb_relay
        .wait_for_msg::<self_serve::app::v1::StartCapture>(self_serve_app_capture_trigger_timeout)
        .await
    {
        if let Err(e) = orb_relay.send(self_serve::orb::v1::CaptureTriggerTimeout {}).await {
            tracing::warn!("failed to send CaptureTriggerTimeout: {e}");
        };
        orb.ui.signup_fail(SignupFailReason::Timeout);
        tracing::warn!("Self-serve biometric-capture start was not triggered: {e}");
        return Ok(false);
    };

    tracing::info!("Self-serve biometric-capture start triggered");
    orb.ui.signup_start();

    tracing::info!("Self-serve: Informing orb-relay that biometric_capture has started");
    orb_relay
        .send(self_serve::orb::v1::CaptureStarted {})
        .await
        .inspect_err(|e| tracing::error!("Relay: Failed to CaptureStarted: {e}"))?;

    Ok(true)
}
