### Title
Unconditional revert on native-ETH payout to non-payable beneficiary permanently freezes escrowed order funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` request handler push native ETH to a beneficiary/recipient address using a raw `.call{value: amount}("")`, and `revert` the *entire* transaction if the low-level call fails. Since the beneficiary address is attacker/order-creator controlled and can be a contract with no payable `receive()`/`fallback()`, this mirrors the `AvailBridge::sendETH` bug class: any recipient that rejects plain ETH transfers causes the whole escrow-release/refund/dust-sweep call to revert, rather than degrading gracefully.

### Finding Description
In `withdraw()`, escrowed native tokens are released to `beneficiary` with:
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [1](#0-0) 

The same unconditional-revert pattern for a native transfer appears in the `SweepDust` handling branch:
```solidity
if (token == address(0)) {
    (bool sent,) = req.beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [2](#0-1) 

`withdraw()` is invoked from `onGetResponse`, the callback the ISMP host calls when a cross-chain response proving an order fill/refund is delivered:
```solidity
function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
    if (incoming.response.values[0].value.length != 0) revert Filled();
    WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
    withdraw(body, true);
}
``` [3](#0-2) 

The `beneficiary` value comes from `body.beneficiary`, itself decoded from the original order/request data — a value fully controlled by whoever created the order (the order's `msg.sender`, or a solver/relayer supplying `WithdrawalRequest.beneficiary` when constructing the outgoing dispatch). If that address is a contract without a payable fallback (or one that deliberately reverts, e.g. by consuming all gas or via a griefing contract), the `beneficiary.call{value: amount}("")` fails, and `withdraw()` reverts the entire delivered ISMP response/GET message. Because `_filled[body.commitment]` was already set before the transfer attempt (line 693) and the whole function reverts on failure, **no state change persists** — the escrow entry remains, but the delivery message that carried the proof is consumed/rejected on this attempt, and the relayer that submitted the proof pays gas for a reverted transaction with no compensation.

This is a stronger instance of the reported bug class ("recipient contract without receive() causes revert"), because here the affected value is *escrowed principal funds belonging to a third party* (the order's committed input/output tokens) sitting behind an ISMP message delivery, not a simple bridge withdrawal. A user or solver can set `beneficiary` to a non-payable contract (either by mistake or intentionally as a griefing vector against relayers who must repeatedly resubmit the same delivery, paying gas each time with no way to force success), permanently blocking the release/refund of the escrowed order and repeatedly wasting relayer gas on every redelivery attempt, since there is no fallback path (unlike `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which explicitly re-wrap to WETH and fall back to an ERC-20 transfer on failed native push — see lines 316-321 and 354-359 of `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`).

### Impact Explanation
- Escrowed funds tied to an order (`_orders[commitment][token]`) can never be released to the intended beneficiary if that beneficiary is a contract that rejects plain ETH transfers, permanently freezing the escrowed principal for that order (no ERC-20/WETH fallback path exists, unlike the `WrappedHyperFungibleToken` app in the same codebase).
- Every relayer/solver attempt to deliver the GET response/refund proof for that order reverts, wasting relayer gas indefinitely and effectively creating a permanently undeliverable route for that specific order's settlement message — a denial-of-service on message delivery for that commitment.
- This qualifies as "permanent freezing of funds" and "a route unable to deliver messages" per the acceptance criteria.

### Likelihood Explanation
Reachable by any unprivileged party that can create an intent order or specify a `beneficiary`/refund address (a normal, permissionless action), and requires only deploying a trivial contract with no payable fallback (or one that reverts) as the beneficiary — no special privileges needed. Likelihood is high because it can happen accidentally (user mistake) or be triggered intentionally as a griefing vector against relayers/solvers.

### Recommendation
Do not let a failed native-ETH push abort the whole withdrawal/settlement flow. Options used elsewhere in this same codebase:
- Mirror the pattern in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`: on `sent == false`, wrap the ETH (e.g., via WETH) and deliver it as an ERC-20 credit to the beneficiary instead of reverting.
- Alternatively, use a pull-based withdrawal (credit an internal balance mapping on failure, letting the beneficiary claim later) instead of push-based `.call{value:}` combined with a hard revert.

### Proof of Concept
1. Attacker/user deploys `EvilBeneficiary`, a contract with no `receive()`/payable `fallback()` (or one that reverts on receiving ETH).
2. Attacker creates an intent order (or is designated as `beneficiary`/refund recipient) with `EvilBeneficiary` as the beneficiary for a native-ETH-denominated escrow.
3. A solver fills the order (or the order times out), and a relayer submits the proof, triggering `onGetResponse` → `withdraw(body, true)`.
4. `beneficiary.call{value: amount}("")` fails inside `withdraw()`; `revert InsufficientNativeToken()` unwinds the whole transaction.
5. Every subsequent relayer attempt to redeliver this proof/response reverts identically — the escrowed input tokens for this order are permanently stuck and every delivery attempt burns relayer gas for no result. [4](#0-3)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
