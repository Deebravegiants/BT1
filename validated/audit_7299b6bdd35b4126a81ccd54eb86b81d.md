### Title
Config parameter re-read mid-signup allows `ignore_user_centric_signups`/`user_centric_signup` decision to bypass backend enrollment check - ([File: src/plans/mod.rs])

### Summary
`orb-core` polls the backend config endpoint on a fixed background interval and atomically replaces the entire shared `Config` behind `Arc<Mutex<Config>>` with no versioning/epoching [1](#0-0) . During a single signup, `do_signup` reads config values from this shared, mutable object at multiple different points in time rather than checkpointing a single consistent snapshot for the whole signup: once at the very top [2](#0-1) , again to build the `debug_report` audit snapshot [3](#0-2) , and again independently at the enrollment decision point [4](#0-3) . This is the same bug class as the reported Solidity issue: a value that should be fixed for the duration of one "operation" (a stake claim / here, a signup) is instead re-evaluated against whatever the current global parameter is, so a parameter change mid-flight is applied retroactively/inconsistently to that operation.

### Finding Description
`Config::download`/`download_and_store` replace the whole config object under a `Mutex` every `CONFIG_UPDATE_INTERVAL` (10s) [5](#0-4) [6](#0-5) . There is no "parameters-updated-at" boundary, no per-signup checkpoint, and no epoch numbering — exactly the missing mechanism called out in the report's recommendation ("introduce parameter epochs ... or force a global checkpoint").

Inside `do_signup`, the decision of whether to actually invoke the backend-verified `enroll_user` flow (which performs `signup_post::request`/polling against the backend, i.e., the actual dedup/uniqueness enforcement) or to instead take a purely local "user-centric" success path is:
```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason)).await.is_success()
};
``` [4](#0-3) 

`orb.config.lock().await.ignore_user_centric_signups` is read fresh at this exact moment, not from the `Config` snapshot captured into `debug_report` at signup start [3](#0-2) . Because the value can be flipped by the background poller at any time during the multi-second capture/pipeline flow (face detection, biometric capture, biometric pipeline all take multiple seconds and each independently re-locks `orb.config` for their own parameters, e.g. `self_serve`, `self_serve_biometric_capture_timeout` [7](#0-6) ), a signup that started under one value of `ignore_user_centric_signups` can be finalized under a different value. If the backend (or a race with its own periodic refresh) transiently serves `ignore_user_centric_signups = false` at the finalization instant while a `user_centric_signup = true` flag was present on the user's QR code, the orb takes the local-declaration branch and never calls `enroll_user`, i.e. never performs the backend network round-trip that enforces uniqueness/dedup for that user.

`user_centric_signup` itself originates from data parsed off the user's QR code (`qr_codes.user_data.user_centric_signup`), which is attacker-influenced input [8](#0-7) .

### Impact Explanation
If the value used to decide "skip real backend enrollment" is inconsistent with the value recorded in the audit trail (`debug_report`), a signup can be declared `Success` locally purely from the local `signup_reason` (which, notably, is also always benign in this FOSS build since fraud checks are stubbed out — `detect_fraud` always returns `Ok(false)` [9](#0-8) ) without the orb ever contacting the backend `enroll_user`/`signup_post` endpoint that performs uniqueness enforcement. This is a concrete misattributed/unauthorized-signup risk: the orb's local success determination and the uploaded debug-report config snapshot can silently diverge from the actual parameter that governed the enrollment decision, allowing a signup to be accepted as "enrolled" without the intended backend verification step, and without an accurate audit record of which config epoch produced that outcome.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires (a) the backend to actually toggle `ignore_user_centric_signups` (an operational config flag, plausible during rollout/rollback of a feature) while (b) a signup with `user_centric_signup=true` is in flight, and the timing window is the multi-second interval between the `debug_report` config snapshot and the final enrollment-decision line. It does not require any special hardware access or privileged operator role — it is exploitable purely from the unprivileged user/QR-code side combined with normal backend config-refresh timing, which matches the reported bug class of "updates can be timed to skew" the outcome.

### Recommendation
Capture a single, immutable `Config` snapshot at the very start of `do_signup` (as is already partially done for other fields at line 497 and for `debug_report` at line 517) and use that same snapshot for every config-dependent decision made throughout the signup, including the `ignore_user_centric_signups` check at line 639, rather than re-locking `orb.config` at each decision point. This ensures the audit trail (`debug_report`) and the actual enrollment-path decision are always derived from the same config epoch, eliminating the possibility of a mid-signup parameter change silently altering whether backend-side uniqueness enforcement is invoked.

### Proof of Concept
1. Orb starts a signup with a user QR code where `user_data.user_centric_signup = true`.
2. At `debug_report` construction time (`src/plans/mod.rs:517`), backend config has `ignore_user_centric_signups = true`, so the snapshot recorded for audit purposes indicates the "real" `enroll_user` path should run.
3. During the several seconds spent in face detection / biometric capture / biometric pipeline, the background `Observer::config_update` task (`src/brokers/observer.rs:187-205`) refreshes `orb.config` and the backend now serves `ignore_user_centric_signups = false`.
4. At the enrollment decision (`src/plans/mod.rs:639`), `orb.config.lock().await.ignore_user_centric_signups` now evaluates to `false`, so the condition `user_centric_signup && !ignore_user_centric_signups` is `true`, and the orb takes the local branch, declaring `Success` based solely on `signup_reason == SignupReason::Normal` — without ever calling `enroll_user`/`signup_post::request` against the backend.
5. The uploaded `debug_report` reflects the config state captured in step 2, misrepresenting the parameter epoch that actually governed the enrollment outcome, while the backend's uniqueness/dedup check for this signup was never performed.

Note: I could not find any explicit backend-side documentation in this repo confirming how frequently/under what operational conditions `ignore_user_centric_signups` is toggled in practice; that operational detail (and thus a tighter likelihood bound) would require inspecting backend-side config management, which is outside this repo's scope.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}

                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }

    /// Downloads the latest configuration from the backend and updates the
    /// shared configuration object.
    pub async fn download() -> Result<Config> {
        let res = backend::config::request().await.map_err(|e| {
            tracing::error!("Config request failed: {:?}", e);
            dd_incr!("main.count.http.config_update.error");
            e
        })?;

        if let Some(config) = Config::from_backend(res) {
            dd_incr!("main.count.http.config_update.success");
            Ok(config)
        } else {
            dd_incr!("main.count.http.config_parse.error");
            Err(eyre!("invalid config"))
        }
    }

    /// Downloads the latest configuration from the backend, updates the shared
    /// configuration object, and stores the updated configuration to the file
    /// system.
    pub async fn download_and_store(config: Arc<Mutex<Config>>) -> Result<()> {
        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }
