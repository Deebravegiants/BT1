### Title
Optional `serverId` domain binding in `@exodus/auth-client-base` allows authentication-challenge signatures to be replayed across different backend services - (File: libraries/auth-client-base/client.js)

### Summary
`@exodus/auth-client-base` implements a pseudonymous, signature-based authentication scheme where a client-held keypair signs a server-issued challenge to obtain an auth token. The scheme optionally prefixes the challenge with a `serverId` before signing, but this domain-separation step is not mandatory. This is the same bug class as the Futureswap `instantWithdraw` finding: a signature over data that lacks a mandatory, service-specific binding can be replayed against a different verifier that speaks the same generic protocol.

### Finding Description
In `_authenticate()`, the client fetches a base64 `challenge` from `authChallengeUrl`, optionally concatenates a `serverId` in front of it, and signs the result: [1](#0-0) 

```js
let encodedChallenge = Buffer.from(challenge, 'base64')
if (serverId) {
  encodedChallenge = Buffer.concat([Buffer.from(serverId), encodedChallenge])
}
const signedChallenge = await keyPair.sign(encodedChallenge)
```

`serverId` comes from `this._config`, i.e., is caller-supplied and optional — nothing in this library enforces its presence [2](#0-1) . The example usage in the package does not set a `serverId` at all: [3](#0-2) 

If `serverId` is omitted (or if two different services that both consume this client happen to configure the same `serverId`, or if the challenge value/format from one service's `authChallengeUrl` is otherwise compatible with another's `authTokenUrl` verifier), the resulting `signedChallenge` is a signature over just the raw base64-decoded challenge bytes — with no cryptographic binding to which specific backend/service requested it. This mirrors exactly the root cause described in the external report: a user (here, the client keypair) signs a structurally generic payload (public token address/amount/nonce in the Futureswap case; a bare challenge byte string here) that carries no service-specific domain separator, so a signature solicited by one relying party can be captured and replayed to another relying party that accepts the same signing format.

Because this is a shared library (`@exodus/auth-client-base`) intended to be reused "for when your auth scenario requires the client to generate its own keypair and sign requests with it" [4](#0-3) , any two Exodus backend services that (a) both use this client with the pseudonymous keypair, and (b) either omit `serverId` or use overlapping/predictable `serverId` values, are exposed to cross-service replay of authentication challenge signatures.

### Impact Explanation
If a malicious or compromised service (or a man-in-the-middle observing a legitimate `authChallengeUrl`/`authTokenUrl` exchange) can obtain a signed challenge intended for Service A, and Service B's challenge/verification flow accepts the same raw challenge format without an enforced service-specific binding, the attacker can replay that signature to authenticate as the same pseudonymous keypair against Service B. This does not directly compromise wallet funds/private keys — the signing key here is a pseudonymous auth keypair, not the asset-holding keypair — but it can lead to unauthorized authentication/session establishment against a service using the victim's pseudonymous identity, which is an auth-bypass/cross-service privilege-bleed impact analogous in class (not in blast radius) to the original finding.

### Likelihood Explanation
Exploitability depends entirely on integrators of this shared client library: if every consumer sets a unique, mandatory `serverId` and the challenge issuance/verification endpoints are strictly scoped per-service, the risk is not realized. However, because the library treats `serverId` as optional with no enforcement or warning, and the documented example omits it, this is a latent footgun that downstream consumers can easily fall into. I could not verify from the indexed code which production services actually configure `serverId` and whether any two Exodus backend consumers share overlapping challenge formats — this would require inspecting the actual backend service configurations, which are likely outside the `hydra` client repo's index coverage.

### Recommendation
Make domain separation mandatory rather than optional in `@exodus/auth-client-base`: require `serverId` (or an equivalent audience/service identifier) to be present and non-empty, and enforce that the server-side challenge issuance/verification ties the challenge to a specific `serverId`/audience so a signed challenge cannot be replayed against a different relying party. This is analogous to the fix in Futureswap PR #495, which added the Futureswap-specific `Registry` contract address into the signed struct.

### Proof of Concept
Conceptual PoC (cannot be fully executed without the paired backend, which is out of scope of this client repo):
1. Configure `MyClient`/`createClient` with `config.keyPair` set but `config.serverId` left `undefined`, matching the documented example: [3](#0-2) .
2. Trigger `_authenticate()` against Service A's `authChallengeUrl`; capture the resulting `{ publicKey, signedChallenge }` pair sent to `authTokenUrl` in `_authenticate()` [5](#0-4) .
3. Replay the identical `{ publicKey, signedChallenge }` payload to Service B's `authTokenUrl`, assuming Service B issues challenges in the same base64 format and also omits (or shares) a `serverId`.
4. If Service B's verifier accepts it, the pseudonymous identity is authenticated on Service B without Service B ever having issued that specific challenge — demonstrating the replay.

```javascript
  _authenticate() {
    const { keyPair, authChallengeUrl, authTokenUrl, serverId } = this._config
    this._authPromise = (async () => {
      if (!keyPair) {
        return
      }

      const { challenge } = await this._request('POST', authChallengeUrl, {
        auth: false,
        data: {
          publicKey: keyPair.publicKey.toString('hex'),
        },
      })

      let encodedChallenge = Buffer.from(challenge, 'base64')

      if (serverId) {
        encodedChallenge = Buffer.concat([Buffer.from(serverId), encodedChallenge])
      }

      const signedChallenge = await keyPair.sign(encodedChallenge)
      const { token } = await this._request('POST', authTokenUrl, {
        auth: false,
        data: {
          publicKey: keyPair.publicKey.toString('hex'),
          signedChallenge: signedChallenge.toString('base64'),
        },
      })
```
