### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator` verifies the HMAC exclusively against that body. The `shop`, `topic`, `webhook-id`, and `api-version` values are all read from unauthenticated HTTP headers and are never part of the signed material. `Webhooks::Registry.process` forwards the unverified `request.shop` straight into `WebhookMetadata`, which is the only tenant identifier the host application's handler receives.

### Finding Description
The security guarantee an app developer relies on is: "if `HmacValidator.validate(request)` passes, this webhook body genuinely originated from the shop identified by `request.shop`." In reality the equality that should hold — `HMAC(secret, body ++ shop)` verified `==` `shop used as tenant key` — does not hold, because only `body` is signed: [3](#0-2) [4](#0-3) 

Since the app's `client_secret` (and therefore the HMAC) is shared across every shop that installs the app, and only the body bytes are hashed, any party who can obtain one valid `(raw_body, hmac)` pair for the app — e.g., by installing the app on their own store and capturing a genuine webhook delivery — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still return `true` because the signature check never looks at the header. `Registry.process` then dispatches the payload to the handler with the attacker-chosen `shop`: [1](#0-0) 

This breaks the binding "shop authenticated via HMAC == shop used as tenant/session key," matching the report's underlying bug class (data used by the system is not covered by the same validation that is supposed to bind it).

### Impact Explanation
High to Critical depending on host app usage: webhook handlers commonly use `data.shop` to look up the session/access token for that tenant or to write data scoped to that shop (e.g., `orders/create`, `customers/data_request`, `app/uninstalled`). Forging the `shop` value lets an attacker impersonate another merchant's webhook stream, causing cross-tenant data corruption, false uninstall/GDPR-redact triggers against a victim shop, or state confusion between tenants — all while presenting a signature the app believes to be authentic.

### Likelihood Explanation
Moderate: exploitation only requires the attacker to install the target app on any shop they control (a normal, low-privilege interaction), capture one webhook body+HMAC pair, and replay it with a modified shop header at the app's public webhook endpoint. No access to the `api_secret_key` or another merchant's credentials is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) values in the signed material, or otherwise cryptographically bind the header-derived tenant identity to the verified payload before it is handed to `WebhookMetadata`/the handler. At minimum, document that `data.shop` is unauthenticated and must never be trusted as a tenant key without independently confirming it against a value the app itself associated with the delivery.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid for `HMAC(secret, B)`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives `HMAC(secret, B)` and ignores the shop header.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and, if it trusts `shop` as the tenant key, performs actions attributed to `victim.myshopify.com` using attacker-controlled `B`.
