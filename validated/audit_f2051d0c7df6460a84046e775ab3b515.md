### Title
Emporium wallet-authorization signature does not bind the shielded output destination, tokens or fee/relay parameters, letting the transaction submitter redirect swapped funds to their own stealth address - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.verifyWallet` recovers the `HinkalWallet` owner's EIP-712 signature over only `(emporiumMessage, opsHash, maxFee, deadline)`. It never binds `circomData.stealthAddressStructure` (who receives the resulting shielded UTXO), `circomData.erc20TokenAddresses`, `circomData.feeStructure`, or `circomData.relay`. The overall ZK proof that accompanies the transaction does not fill this gap either, because when no real shielded UTXO is being spent (`inAmounts[i][j] == 0` for all slots), `MainEVMCircuit`'s merkle-root check is disabled (`enabled <== inAmounts[i][j]`) and `spendingPublicKey`/`eddsaSignature` can be freshly, self-generated by whoever submits the transaction. This mirrors the reported `permitSingle`-not-bound-to-order bug: an authorization for one purpose (moving funds via `ops`) can be freely paired with unrelated destination data supplied by the party who submits the transaction on-chain.

### Finding Description
`EmporiumUpgradeable.verifyWallet` computes: [1](#0-0) 

The hashed message only commits to `emporiumMessage`, the `ops` array hash, `maxFee` and `deadline` — never to `circomData.stealthAddressStructure`, `circomData.erc20TokenAddresses`, `circomData.feeStructure`, or `circomData.relay`: [2](#0-1) 

After `ops` run against the wallet owner's real token balance held in `HinkalWallet`, `handleOut` unconditionally routes the resulting balance increase into a new shielded UTXO addressed to whatever `circomData.stealthAddressStructure` the *caller* supplied — not the wallet owner: [3](#0-2) 

The only other artifact tying the transaction together is the ZK proof checked in `Hinkal.transact`/`performHinkalChecks`, whose public inputs are built by `CircomDataBuilder.formBasicInput`/`getSignedMessageHash`, which does include `stealthAddressStructure` — but that binding is enforced only by the circuit's EdDSA check over a *self-chosen* `spendingPublicKey`/`eddsaSignature` pair: [4](#0-3) 

Crucially, when no genuine shielded UTXO is being spent for a token slot (`inAmounts[i][j] == 0`, the normal case for Emporium since the funds come from the wallet, not from the shielded pool), the merkle-root equality check for that slot is disabled via `ForceEqualIfEnabled().enabled <== inAmounts[i][j]`: [5](#0-4) 

This means the "spending" signature check inside the circuit does not prove ownership of any real value or authorization by the `HinkalWallet` owner — the caller can generate `spendingPublicKey`/`eddsaSignature`/`messageSeed` themselves and still produce a valid proof, as long as the output/amount arithmetic balances (`inTotal + amountChanges[i] === outTotal`, with `inTotal = 0`). Consequently, whoever assembles and submits the `Hinkal.transact` call (necessarily whoever executes the ops on behalf of the wallet owner, e.g. a relay/executor holding the signed `EmporiumStack`) fully controls `circomData.stealthAddressStructure`, `erc20TokenAddresses`, `feeStructure`, and `relay` — none of which the wallet owner's ECDSA signature constrains.

### Impact Explanation
An attacker who is given (or intercepts) a valid `EmporiumStack` signature — meant to authorize execution of specific `ops` against a user's `HinkalWallet` balance — can submit that same signature to `Hinkal.transact` while substituting their own `stealthAddressStructure` as the output destination. The `ops` execute using the wallet owner's real token balance exactly as authorized, but the resulting shielded UTXO created by `handleOut` is minted to the attacker's own shielded address instead of the wallet owner's, directly stealing the swapped/withdrawn funds. This is a direct theft of user funds via unauthorized asset movement, satisfying the Critical impact bar (direct theft of shielded/in-flight user funds; proof/nullifier verification effectively bypassed for authorization purposes since the "spending" signature proves nothing about the wallet owner's intent).

### Likelihood Explanation
Any party in possession of a validly-signed `EmporiumStack` (which, by design, must be handed to someone to submit the on-chain transaction, e.g. a relay/executor) can exploit this without needing the wallet owner's private key, spendingPrivateKey, or any additional cooperation — they only need to construct their own arbitrary `circomData`/proof, which the circuit permits since no real UTXO ownership is enforced when `inAmounts == 0`. This requires only the standard flow of using a relay/executor to submit a pre-signed Emporium operation, making it highly likely in normal operation of this feature.

### Recommendation
Bind the full economic effect of the operation into the EIP-712 signed message that `EmporiumUpgradeable.verifyWallet` recovers: include `circomData.stealthAddressStructure` (H0/H1/stealthAddress), `circomData.erc20TokenAddresses`, `circomData.feeStructure`, and `circomData.relay` (or a hash of the full `circomData` analogous to `calldataHash`) in `EMPORIUM_SIGNATURE_TYPEHASH`, so a signed authorization can only be executed with the exact destination and token/fee parameters the wallet owner approved — mirroring the recommended fix of validating that permit/signature data corresponds to the specific order/operation it is used with.

### Proof of Concept
1. Wallet owner Alice signs an `EmporiumStack` authorizing `ops` (e.g., call a DEX router to swap TokenA held in her `HinkalWallet` for TokenB) with `signerAddress = Alice's wallet`, `maxFee`, `deadline`, intending the resulting TokenB to be shielded to her own stealth address, and hands the signed stack to a relay/executor to submit.
2. The relay/executor (attacker) calls `Hinkal.transact` with `circomData.externalActionData.externalActionMetadata = abi.encode(stack)` where `stack` is Alice's untouched signature/ops/maxFee/deadline, but sets `circomData.stealthAddressStructure` to the attacker's own stealth address, and picks `erc20TokenAddresses`/`amountChanges` matching the resulting TokenB delta.
3. The attacker generates a fresh, arbitrary `spendingPublicKey`/`nullifyingPrivateKey`/`eddsaSignature`/`messageSeed` (no relation to Alice) since `inAmounts[i][j] = 0` for all slots disables the merkle-root check in `circuits/MainEVMCircuit.circom` (`enabled <== inAmounts[i][j]`), and produces a valid proof satisfying `inTotal (0) + amountChanges[i] === outTotal`.
4. `EmporiumUpgradeable.verifyWallet` recovers Alice's signature successfully (it only checks `emporiumMessage`, ops hash, `maxFee`, `deadline` — all unchanged), `runAction` executes the swap using Alice's real wallet balance, and `handleOut` transfers the resulting TokenB and mints the shielded UTXO to the attacker's `stealthAddressStructure` instead of Alice's.
5. Alice's TokenA is spent as authorized, but the swap proceeds are stolen by the attacker; Alice receives nothing.

    function _hashEmporiumOps(
        EmporiumOperation[] memory ops
    ) private pure returns (bytes32) {
        bytes32[] memory opHashes = new bytes32[](ops.length);
        for (uint256 i = 0; i < ops.length; i++) {
            opHashes[i] = keccak256(
                abi.encode(
                    EMPORIUM_OPERATION_TYPEHASH,
                    ops[i].endpoint,
                    ops[i].invokeWallet,
                    ops[i].value,
                    keccak256(ops[i].callData)
                )
            );
        }
        return keccak256(abi.encodePacked(opHashes));
    }
