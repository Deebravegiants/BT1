IntentGatewayV2.placeOrder() correctly refunds unspent native tokens via `_sendValue(msg.sender, msgValue)` after computing `amounts[0]` consumed by the swap [1](#0-0) , so that path is not vulnerable. However, `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` do not track `amounts[0]` returned by `swapETHForExactTokens` and never refund any leftover ETH to the caller.

### Title
Lost `msg.value` refund from Uniswap V2 swap in `EvmHost.dispatch()` and `fundRequest()` - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are `payable` entry points that let any user pay Hyperbridge dispatch/relayer fees in native token by forwarding the entire `msg.value` to `IUniswapV2Router02.swapETHForExactTokens`. This router call only consumes the exact amount of ETH needed to buy `post.fee`/`get.fee`/`amount` fee tokens and refunds the unused ETH — but the refund goes to `msg.sender` of the router call, which is `EvmHost` itself, not the original caller. `EvmHost` never reads the `amounts` return value nor forwards the leftover ETH back to the user.

### Finding Description
In all three functions the pattern is:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [2](#0-1) [3](#0-2) [4](#0-3) 

`UniswapV2Router02.swapETHForExactTokens` refunds `msg.value - amounts[0]` to its caller (`msg.sender` in that inner call context), i.e. to `EvmHost`, not the end user who called `dispatch`/`fundRequest`. Since `EvmHost` doesn't capture `amounts[0]` or forward any excess back to `_msgSender()`, any ETH sent beyond what's needed to buy the exact fee amount is permanently absorbed into the `EvmHost` contract balance with no accounting or recovery path for the original payer.

This is the exact bug class from the external report: a `payable` function accepts `msg.value` but doesn't enforce/refund the exact amount consumed, causing users to lose the difference. Here it's worse because the function is a core, permissionless, single-transaction entry point (`dispatch`) used by every app on Hyperbridge for native-fee payments, not just an edge integration.

### Impact Explanation
Any user who slightly overestimates the ETH needed for `swapETHForExactTokens` (due to normal price movement between quote and execution, or by passing `msg.value` greater than the fee's ETH-equivalent) permanently loses the difference — it is stuck in `EvmHost` with no withdrawal mechanism tied to the original payer. Given `dispatch()` is the primary entry point invoked by every `HyperApp`/`HyperFungibleToken`/`IntentGatewayV2` integration doing native-fee dispatch (as shown in the SDK/docs examples using `dispatch{value: msg.value}(post)`), this is a systemic loss-of-funds issue affecting a broad set of unprivileged callers across the protocol, meeting the Medium bar for concrete permanent fund loss.

### Likelihood Explanation
High likelihood: this occurs on virtually every native-token dispatch since Uniswap swap outputs and required ETH input fluctuate with pool state between the time a client estimates `msg.value` and the transaction's execution; any overestimation, even by a small margin, or any legitimate client sending a safety buffer causes silent fund loss without reverting.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` to `_msgSender()` in `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`, mirroring the refund pattern already implemented in `IntentGatewayV2.placeOrder()` [1](#0-0) .

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.9 ether` worth of ETH to purchase via `swapETHForExactTokens`.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` consumes `0.9 ether` and refunds `0.1 ether` to `msg.sender` of the router call, which is `address(this)` (`EvmHost`), not the user.
3. `EvmHost.dispatch` never reads the refunded amount nor transfers it back to the original caller; the `0.1 ether` remains stuck in `EvmHost`'s balance with no accounting entry tying it back to the user.
4. Repeating this for any user who overestimates `msg.value` (a normal occurrence given AMM price fluctuation) permanently drains ETH from users into the `EvmHost` contract.
