## Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop` value extracted from an *unsigned* HTTP header when dispatching the event to the host application's handler. Because the `shop` identifier is not covered by the HMAC, any party who can obtain one valid `(raw_body, hmac)` pair (e.g., by triggering a webhook to their own store) can replay that exact pair while substituting the `shop-domain` header of a different, victim shop, and the library will accept it as an authentic event for the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `shop` is read from an HTTP header that is never included in that signable string: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate`, which internally calls `to_signable_string` (body only) — the `shop` header is never checked — and then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator#validate_signature` confirms the comparison is performed only against `verifiable_query.to_signable_string`: [4](#0-3) 

The resulting `WebhookMetadata.shop` field is a plain, unauthenticated `String` handed to the host application's `WebhookHandler#handle`: [5](#0-4) 

The identity binding that should hold is: `hmac_verified_bytes == bytes_the_handler_trusts_as_tenant_identity`. Here, the HMAC only covers the JSON body, while the tenant identity (`shop`) is taken from a separate, unsigned header — breaking that equality. Anyone able to produce one legitimate `(body, hmac)` pair (trivial: install the app on any store, even a free/dev store the attacker fully controls) can replay the identical body and HMAC to the app's webhook endpoint while swapping only the `shopify-shop-domain` / `x-shopify-shop-domain` header value to a victim shop's domain. `HmacValidator.validate` still succeeds because the signed bytes (the body) are unchanged, and `Registry.process` calls the handler with `shop: <victim-domain>`.

### Impact Explanation
This breaks the cross-tenant boundary the HMAC check is meant to enforce: it lets an unprivileged internet user (anyone who can install the app on a store they control, which is the normal, unprivileged installation flow) forge webhook events that the host application will attribute to an arbitrary other shop. Any application logic keyed off `data.shop` (e.g., updating that shop's local records, triggering side effects tied to that tenant, or acting on data as if it originated from the victim's store) can be manipulated cross-tenant, without any credential belonging to the victim. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one valid `(raw_body, hmac)` pair, which any developer/attacker can generate by installing the app on their own store and receiving a real webhook, and (2) sending an HTTP POST to the app's public webhook endpoint with that same body/HMAC but a different `shop-domain` header — both trivially scriptable and require no secrets, tokens, or special access. The gem does not offer any mechanism (and the library's own `to_signable_string`/`HmacValidator` code path shows none) to bind the shop domain to the signature, so likelihood is high for any app that trusts `WebhookMetadata#shop` for tenant-scoped logic.

### Recommendation
Include the shop domain (and/or topic, webhook-id) as part of the HMAC-signed material, or otherwise cryptographically bind the header value used for tenant identification to the request signature, before constructing `WebhookMetadata`. At minimum, document/require that consuming apps cross-check `request.shop` against a shop already known/authorized in their own session store rather than trusting it as an authenticated identity on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (a normal, unprivileged action) and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header value sent by Shopify.
2. Attacker replays the exact same HTTP request to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but changing `x-shopify-shop-domain` (or `shopify-shop-domain`) to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` field decodes the same signature, and whose `shop` returns `"victim-shop.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` (the body) is unchanged.
5. The registered handler's `handle(data:)` is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store — demonstrating the cross-tenant identity forgery.
