### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop-identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then passes `request.shop` straight into the handler's `WebhookMetadata`, meaning the tenant identity delivered to the host application's business logic is never bound by the cryptographic signature that is supposed to authenticate the whole request.

### Finding Description
`Utils::HmacValidator.validate` only checks that `compute_signature(verifiable_query.to_signable_string, secret) == hmac`, and for webhooks `to_signable_string` is defined as just `@raw_body`: [1](#0-0) 

The `shop` accessor used everywhere downstream is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC-of-body and then trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` object handed to the app's webhook handler: [3](#0-2) 

This breaks the equality the HMAC is meant to guarantee: `hmac == HMAC(secret, body)` should imply `(shop, topic, body)` all genuinely originated together from Shopify for that merchant. In reality the guarantee only covers `body`; `shop` is a free variable that any party capable of producing one valid `(body, hmac)` pair (e.g., a merchant who has installed the app and can trigger webhooks for their own store, since the HMAC secret is the app's single shared `client_secret` used across all tenants) can pair with an arbitrary `shop-domain` header value when replaying the request to the app's webhook endpoint. Because the HMAC secret is identical for every shop that installs the same app, a legitimate installer can capture one of their own genuinely-signed webhook deliveries and resend it to the app's public webhook endpoint with the `shop-domain` header changed to point at a different, victim shop — the signature still validates because it only covers the body bytes.

### Impact Explanation
This is a cross-tenant identity-binding failure inside the gem's own webhook-verification code: `bytes verified` (the raw body) diverges from `bytes/fields acted on` (`shop`, used as the tenant key for dispatch). A host application that uses `WebhookMetadata#shop` — exactly as intended by this library — as the tenant identifier for persisting or acting on webhook data can be made to apply an attacker's forged/replayed body under a different shop's identity, which is a cross-tenant access primitive delivered entirely through this gem's `Registry.process`/`Request` verification path.

### Likelihood Explanation
Any merchant who installs the app is, by design, capable of generating a validly-HMAC-signed webhook body for their own shop (Shopify signs and delivers it to the app using the app's `client_secret`, which is common to all installs). That merchant only needs to capture one such delivery (e.g., from their own store's webhook logs or a proxy) and resend it to the app's public webhook endpoint with a different `shop-domain` header value — no access to the app's `client_secret`, another merchant's token, or TLS interception is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them to the body, e.g. by requiring the host application to independently verify that `shop` corresponds to a session/install known to be associated with the delivered `webhook_id`/`topic`), so that `HmacValidator.validate` actually authenticates the full tuple of fields the registry hands to handlers, not just the raw body.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same app, same `client_secret`).
2. The attacker controls `shop-a.myshopify.com` and captures one genuine webhook delivery Shopify sends to the app's endpoint, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid hmac of raw body, computed with the shared client_secret>
   X-Shopify-Shop-Domain: shop-a.myshopify.com
   Body: {"id": 1, ...attacker-controlled order fields...}
   ```
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks the body's HMAC.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`) with `shop == "shop-b.myshopify.com"`, so the host application processes attacker-supplied data as if it belonged to `shop-b`, a tenant the attacker does not control.
