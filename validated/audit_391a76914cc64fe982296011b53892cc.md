### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant confusion via payload replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. This breaks the identity binding `HMAC-authenticated bytes == bytes used to attribute the webhook to a tenant`, allowing an attacker who obtains one valid `(body, hmac)` pair to replay it while substituting an arbitrary `shop-domain` header, causing the host application to process genuine, HMAC-valid webhook data under a different (attacker-chosen) shop identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is instead read straight from an untrusted, unauthenticated header: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks the signable string (i.e. the body) against the HMAC, and never touches `shop`, `topic`, `webhook_id`, or `api_version`: [4](#0-3) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` dispatched to the host app's handler — there is no cross-check that the header-derived `shop` corresponds to the body that was actually signed: [5](#0-4) 

Equality that should hold but doesn't:
`shop used to route/attribute the webhook (header, unauthenticated)` == `shop implicitly bound by the HMAC-covered bytes (body only)`.

Because these two are decoupled, any party in possession of one legitimately-signed `(raw_body, hmac)` pair — e.g. captured from application logs, error-tracking tools, a browser/proxy, or a misconfigured logging pipeline that a webhook is routed through — can resend that exact body/HMAC pair to the app's webhook endpoint with a different `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` since it only checks the body, and `Registry.process` will hand the (unmodified, genuinely-signed) body to the handler tagged with the attacker-chosen `shop`.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to key per-tenant state (a very common pattern — e.g., updating orders/inventory/customer records "for this shop"), this allows cross-tenant data confusion: data legitimately belonging to Shop A can be attributed to and merged into Shop B's tenant state purely by manipulating an unauthenticated header, without needing the `api_secret_key`, an access token, or any Shopify credential. This matches the Critical "cross-tenant access" impact category, since the binding between authenticated bytes and the tenant identifier is broken.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair for the target endpoint (via log leakage, network capture, browser devtools during testing, a proxy, or any other exposure of a previously delivered webhook) — the attacker never needs the secret itself. Given webhook payloads are frequently logged or visible in request-inspection tooling during development/debugging, and the endpoint performs no replay protection (no nonce/timestamp binding is enforced by this gem, only header-comparison with `secure_compare` on the body signature), this is a realistic vector once such data leaks.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signable string in `Webhooks::Request#to_signable_string`, so that any header tampering invalidates the HMAC. At minimum, `Registry.process` should refuse to process a webhook whose `shop` cannot be cryptographically tied to the signed body, and host apps should be documented to never trust `WebhookMetadata#shop` unless it is bound by the signature.

### Proof of Concept
1. Capture a genuine webhook delivery for `shop-a.myshopify.com`: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app secret) — e.g., from an app's request logs.
2. Replay the exact same `B` and `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`: [6](#0-5) 
4. `Registry.process` dispatches the handler with `shop: "shop-b.myshopify.com"` and the body originally intended for `shop-a`: [5](#0-4) 
5. The host application processes Shop A's data under Shop B's tenant context.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
