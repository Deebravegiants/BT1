Confirmed: no sweep/rescue function exists in `ExternalActionSwap`, `LifiExternalAction`, or `ExternalActionBaseV2`, so any fee amount stuck in the action contract is permanently unreachable through any normal code path.

### Title
Fee funds permanently frozen in ExternalActionSwap/LifiExternalAction when relay is address(0) - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` always computes `hinkalFee`/`relayFee` from `circomData.feeStructure` and subtracts `totalFee` from the amount forwarded to Hinkal, but the actual transfer of that fee to `circomData.relay` is a no-op whenever `relay == address(0)`. Since a self-relaying caller is a legitimate, unprivileged flow permitted by `HinkalHelper.performHinkalChecks`, an attacker can set `relay = address(0)` while keeping `feeStructure.flatFee`/`variableRate` nonzero, causing `totalFee` worth of `outputToken` to remain stranded in the action contract forever.

### Finding Description
Broken equality: `totalFee` (computed and subtracted from `amountToSendToHinkal` in `swap()`) should equal the sum of balance increases at `circomData.relay`, but when `relay == address(0)` that increase is `0`, since `sendToRelay` is a no-op guarded by `if (relay != address(0) && actualAmount > 0)`: [1](#0-0) 

In `swap()`, `hinkalFee` is computed unconditionally from `swappedAmount` via `hinkalHelper.calculateRelayFee`, and `relayFee` is set from `feeStructure.flatFee` regardless of `relay`: [2](#0-1) 

`sendToRelay` is called with `circomData.relay` — if it is `address(0)`, both calls silently do nothing, yet `totalFee` (`hinkalFee` + optionally `relayFee`) is still subtracted from `amountToSendToHinkal`, which is the only token leaving the action to `msg.sender` (Hinkal). The difference (`totalFee`) stays as ERC20/ETH balance inside `ExternalActionSwap`/`LifiExternalAction` with no other transfer path.

The attacker's exact call: invoke `Hinkal.transact` with `circomData.externalActionData.externalActionId` pointing at a swap action (e.g. `LifiExternalAction`), `circomData.relay = address(0)`, `circomData.originalSender = msg.sender` (required for `relay == address(0)` per `performHinkalChecks`), and `circomData.feeStructure.flatFee`/`variableRate` set to nonzero values. This passes `performHinkalChecks`: [3](#0-2) 

`relayerIsValid` only validates `relay` when it is non-zero, so a zero relay bypasses whitelist checks entirely: [4](#0-3) 

`dimensionsCheck` only bounds `variableRate <= 10000`, it does not force `feeStructure` to zero when `relay == address(0)`: [5](#0-4) 

No circom circuit file constrains `feeStructure.flatFee`/`variableRate` (confirmed no matches for these fields in `circuits/**/*.circom`), so the circuit places no constraint tying `feeStructure` to `relay`. The `swap()` function itself never checks `circomData.relay != address(0)` before computing/deducting `totalFee`.

Note: this affects `ExternalActionSwap`/`LifiExternalAction` specifically. The internal-transfer path in `Hinkal._internalTransact` and the Emporium's `payRelayFees`/`payRelay` both correctly guard fee deduction with `if (circomData.relay != address(0))`, so this class of bug does not exist there: [6](#0-5) [7](#0-6) 

`ExternalActionSwap`/`ExternalActionBaseV2`/`LifiExternalAction` have no sweep, rescue, or withdraw function, so stranded tokens can never be reclaimed by any actor through a normal code path. [8](#0-7) 

### Impact Explanation
Each swap performed with `relay = address(0)` and a nonzero `feeStructure` permanently strands `totalFee` worth of `outputToken` (and, if `feeToken != outputToken`, also `relayFee` worth of `feeToken`, deducted from `inputAmount` before the router call) inside the action contract. This is not stolen by the attacker — it is neither returned to the depositor nor sent to any relay — it is simply lost from circulation, forever locked in `ExternalActionSwap`/`LifiExternalAction`. This matches the "High — permanent freezing of protocol/relay fees" impact category. It is fully repeatable: any unprivileged user can call `transact` any number of times using this pattern, growing the stuck balance without bound (each occurrence is a fresh, independent loss, not a compounding drain of protocol reserves beyond what each individual swap forfeits).

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: an EOA depositing/using their own UTXOs, generating a valid proof for `originalSender == msg.sender` and `relay == address(0)` (an explicitly supported, unprivileged self-relay path), and choosing any nonzero `feeStructure.flatFee`/`variableRate` (bounded only by `variableRate <= 10000`). No relay whitelist check applies. No special tree state or victim cooperation is needed — only that a swap external action (e.g. `LifiExternalAction`) is registered, which is a normal deployment configuration. Attacker cost is just gas plus the value of the fee they choose to set (which they lose, so this is more a footgun than griefing others, but per the given impact categories, "permanent freezing of protocol/relay fees" is explicitly in scope regardless of who set the fee).

### Recommendation
In `ExternalActionSwap.swap`, skip fee computation/deduction entirely when `circomData.relay == address(0)`, mirroring the pattern already used in `Hinkal._internalTransact` and `EmporiumUpgradeable.payRelay`:
```solidity
uint256 relayFee = circomData.relay != address(0) ? circomData.feeStructure.flatFee : 0;
uint256 hinkalFee = circomData.relay != address(0)
    ? hinkalHelper.calculateRelayFee(swappedAmount, 0, circomData.feeStructure.variableRate)
    : 0;
```
Alternatively, add a global invariant check that `feeStructure.flatFee == 0 && feeStructure.variableRate == 0` whenever `relay == address(0)`, enforced centrally in `HinkalHelper.performHinkalChecks` (or `dimensionsCheck`) so every current and future external action automatically benefits from the guarantee instead of each action having to replicate the `relay != address(0)` gating individually.

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`, `HinkalHelper` (with `HINKAL_HELPER_MANAGER`/owner privileges only for setup, not used by attacker), a mock router, `LifiExternalAction`, and register it via `registerExternalAction` (owner-only, one-time setup — not part of the attacker's privileges).
2. As an unprivileged attacker EOA, deposit a UTXO of `inputToken`.
3. Generate a valid Circom proof for `transact()` with:
   - `circomData.externalActionData.externalActionId` = LifiExternalAction id
   - `circomData.relay = address(0)`
   - `circomData.originalSender = attacker`
   - `circomData.feeStructure = { feeToken: outputToken, flatFee: 0, variableRate: 500 }` (5%)
   - valid `externalActionMetadata` calling the mock router to swap `inputToken` → `outputToken`
4. Record `outputToken.balanceOf(LifiExternalAction)` before the call — call it `balBefore` (should be 0).
5. Call `Hinkal.transact(...)`.
6. Assert: `outputToken.balanceOf(LifiExternalAction) - balBefore == hinkalFee` where `hinkalFee` is independently computed off-chain as `calculateRelayFee(swappedAmount, 0, 500)`.
7. Assert the emitted UTXO's `amount` equals `swappedAmount - hinkalFee` (i.e., the attacker/relayer, `msg.sender`, only receives `swappedAmount - hinkalFee`, not `swappedAmount`), confirming `outputToken` leaving the action (`amountToSendToHinkal`) ≠ `-deltaAmountChanges` reported/expected (`swappedAmount`).
8. Assert no subsequent call (owner functions, `setAllowedRecipients`, another `transact`, etc.) can move the stranded `hinkalFee` balance out of `LifiExternalAction` — confirming permanent freezing.

        require(

        _;

            isAllowedRecipient[recipients[i]] = true;
        }
    }
