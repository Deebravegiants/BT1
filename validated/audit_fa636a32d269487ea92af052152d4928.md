### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as the raw request body only, while the `shop` (tenant identifier) is read from the unauthenticated `X-Shopify-Shop-Domain` header. `Registry.process` validates the HMAC and then trusts `request.shop` to attribute the payload to a tenant, breaking the intended binding `authenticated(shop) == signed(shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content at all: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string` (the raw body) against `verifiable_query.hmac` (derived from the `hmac-sha256` header): [3](#0-2) [4](#0-3) 

`Registry.process` then calls the validator and, once it passes, hands `request.shop` straight to the application handler as the tenant identifier for the webhook, with no further check that `shop` is bound to the signed body: [5](#0-4) 

Because `shop-domain` is a plain HTTP header that is never mixed into the HMAC computation, the equality the gem is supposed to enforce — "the shop attributed to this webhook" == "the shop whose secret produced this signature" — does not hold. An attacker who can reach the app's webhook endpoint and who possesses any one validly-signed `(raw_body, hmac)` pair (e.g., a webhook delivery to their own store, or any signed payload) can resend it with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still passes because it only checks the body/secret pair, and `Registry.process` will dispatch the handler with `WebhookMetadata` claiming the victim shop, causing the host application to process attacker-controlled data under a different tenant's identity — a cross-tenant confusion at the gem's authentication boundary.

### Impact Explanation
This crosses the tenant boundary the gem is meant to guarantee for webhook processing: the `shop` field passed to `WebhookHandler#handle` is not authenticated by the HMAC at all, so an attacker-controlled `shop-domain` header is trusted downstream as if it were verified. Any host application that keys per-shop state, records, or actions off `WebhookMetadata#shop` (the documented/expected use, per `docs/usage/webhooks.md`) can be made to associate a validly-signed payload with the wrong shop — a cross-tenant data confusion at the gem's trust boundary.

### Likelihood Explanation
High reachability: any caller of the standard `Registry.process(request)` flow is affected, since the only gate is `Utils::HmacValidator.validate`, which by construction never examines `shop`. No secret knowledge beyond a single valid `(body, hmac)` pair for any shop is required to forge the `shop` attribution of that pair.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed content, or otherwise cryptographically bind them to the signed body, so `Utils::HmacValidator.validate` fails whenever the `shop` attributed to a webhook differs from the shop under whose secret the payload was actually signed.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with raw body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker (who observed/received this delivery, e.g. as the owner of `shop-a`) resends a request to the same webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are unaffected by the header change (they only look at `raw_body` and the `hmac-sha256` header).
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` and finds it equal to `H`, returning `true`.
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the host app to process/store `B` as if it belongs to `shop-b`, even though it was never signed for `shop-b`.
