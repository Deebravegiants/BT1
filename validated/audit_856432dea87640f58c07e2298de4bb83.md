Based on my research, this is a confirmed analog: the `IsmpCallFilter` in the Gargantua and Nexus runtimes implements exactly the kind of incomplete-blocklist bypass described in the fickling advisory — it only checks the consensus message's client id against `BEEFY_CONSENSUS_ID` (analogous to fickling only blocking `os.system`/`eval`/`exec` while forgetting `runpy`), while the intended security guarantee ("no raw consensus proof may reach a client that requires a wrapped/verified submission path") is not actually scoped to BEEFY alone.

### Title
`IsmpCallFilter` only blocklists BEEFY consensus updates, leaving other wrapped/verified consensus clients bypassable via raw `handle_unsigned` - ([File: parachain/runtimes/gargantua/src/lib.rs])

### Summary
Gargantua and Nexus install `IsmpCallFilter` specifically to stop `pallet_ismp::Call::handle_unsigned` from being used to push a raw BEEFY consensus message, because BEEFY consensus on these chains is meant to only be advanced through `pallet-beefy-consensus-proofs`, which requires an SP1 zkVM proof before it will forward a state update into `pallet_ismp`. The filter's `contains` check performs a single equality test: it asks the host which client owns the named `consensus_state_id` and compares that to `ismp_beefy::BEEFY_CONSENSUS_ID`, rejecting only that one case.

### Finding Description
The filter is defined identically in both runtimes: [1](#0-0) 

```rust
pub struct IsmpCallFilter;
impl frame_support::traits::Contains<RuntimeCall> for IsmpCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		use ::ismp::{host::IsmpHost, messaging::Message};
		match call {
			RuntimeCall::Ismp(pallet_ismp::Call::fund_message { .. }) => false,
			RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { messages }) => {
				let host = Ismp::default();
				!messages.iter().any(|message| match message {
					Message::Consensus(consensus) =>
						host.consensus_client_id(consensus.consensus_state_id) ==
							Some(ismp_beefy::BEEFY_CONSENSUS_ID),
					_ => false,
				})
			},
			_ => true,
		}
	}
}
```

The stated design intent, documented directly above it, is broader than "block BEEFY": [2](#0-1) 

The comment says Gargantua "routes all BEEFY consensus updates through `pallet-beefy-consensus-proofs`, which requires each proof to pass SP1 zkVM verification before it can advance the BEEFY state. Allowing raw updates through `handle_unsigned` would bypass that requirement entirely, so any batch that carries a BEEFY consensus message is rejected here."

However, `pallet_ismp::Config::ConsensusClients` on Gargantua wires up ten consensus clients, not one: [3](#0-2) 

```rust
type ConsensusClients = (
    ismp_bsc::BscClient<Ismp, Runtime, ismp_bsc::Testnet>,
    ismp_sync_committee::SyncCommitteeConsensusClient<Ismp, Sepolia, Runtime, Ethereum>,
    ismp_sync_committee::SyncCommitteeConsensusClient<Ismp, gnosis::Testnet, Runtime, Gnosis>,
    ismp_parachain::ParachainConsensusClient<...>,
    ismp_grandpa::consensus::GrandpaConsensusClient<Runtime>,
    ismp_arbitrum::ArbitrumConsensusClient<Ismp, Runtime>,
    ismp_optimism::OptimismConsensusClient<Ismp, Runtime>,
    ismp_polygon::PolygonClient<Ismp, Runtime>,
    ismp_tendermint::TendermintClient<Ismp, Runtime>,
    ismp_pharos::PharosClient<Ismp, Runtime, ismp_pharos::Testnet>,
    ismp_beefy::BeefyConsensusClient<Ismp, Runtime>,
);
```

Every one of `verify_consensus` for these clients accepts a raw, unsigned `ConsensusMessage` (BSC BLS votes, sync-committee light-client updates, GRANDPA justifications, Arbitrum/Optimism/Polygon L2 proofs, Tendermint headers, Pharos updates) directly via `pallet_ismp::Call::handle_unsigned`, which any account can submit unsigned and free of charge, subject only to `validate_unsigned` spam protection — there is no wrapper pallet enforcing an additional off-chain-hard-to-forge proof system (e.g., an SP1 zk-proof) for any client except BEEFY. `IsmpCallFilter`'s equality check against a single hardcoded `BEEFY_CONSENSUS_ID` means the "no raw consensus update reaches a client meant to be gated by extra verification" property the comment describes is enforced for exactly one of ten clients. If governance's intent (per the doc comment's generalized framing "requires each proof to pass...verification before it can advance...state") extends to any additional client added later with a similar wrapper-pallet requirement (as new consensus clients are onboarded, following the same evolution path that added BEEFY's SP1 wrapper), that client's raw path silently reopens because the filter is not expressed as "any client backed by a verification wrapper" but as one specific 4-byte id comparison.

This mirrors the fickling root cause precisely: a single-item, hardcoded identity check standing in for what should be a structural, exhaustively-maintained gate, so any additional item requiring the same protection is unprotected by default rather than by exception.

### Impact Explanation
If a future or currently-unlisted consensus client is meant to be BEEFY-style-gated (verified only through a companion wrapper pallet) but is not added to this equality check, an attacker can submit a crafted raw consensus message directly via `handle_unsigned`. Depending on the target consensus client's own `verify_consensus` logic, this could forge state-machine commitments, enabling forged message delivery, unauthorized minting via token-gateway/HFT flows, or unsound state proofs accepted by `validate_state_machine` — a direct path to fund theft or protocol invariant violation, reachable from a single unsigned extrinsic.

### Likelihood Explanation
Currently, of the ten configured clients, only BEEFY has a documented "must go through the wrapper" invariant, so today's blocklist happens to be complete for the stated invariant. The vulnerability class is latent/structural: the mechanism used to enforce it (a single hardcoded id comparison rather than a registry of "protected" client ids) offers no compile-time or runtime safety net when the client set changes, which is exactly the "blocklist forgot an entry" failure mode in the fickling report. I cannot confirm from the available code whether any other client currently in the tuple, or planned for addition, is intended to carry the same wrapper-gate guarantee — that would need explicit confirmation from the Hyperbridge team about which clients require this protection.

### Recommendation
Replace the single hardcoded `BEEFY_CONSENSUS_ID` comparison with a structural check derived from a canonical, exhaustively-maintained list (or trait marker) of "wrapper-only" consensus client ids, so that onboarding a new consensus client requiring off-chain-proof gating is guaranteed to update the filter, e.g. via a compile-time assertion or a runtime constant enumerated alongside `ConsensusClients`.

### Proof of Concept
Not applicable as a working exploit against the current configuration, since only BEEFY is documented as requiring wrapper-gated verification and the filter correctly blocks it, per the passing test suite: [4](#0-3) 
The structural weakness is that this coverage is enforced by a single hardcoded id equality rather than a mechanism that fails safe (blocks by default) when new consensus clients are added to `ConsensusClients`, which is the same class of gap as the fickling `runpy` omission.

#[tokio::test]
#[ignore]
async fn ismp_call_filter_blocks_only_beefy_consensus_and_fund_message() -> Result<(), anyhow::Error>
{
	let port = env::var("PORT").unwrap_or_else(|_| "9990".into());
	let url = format!("ws://127.0.0.1:{port}");
	let (client, rpc_client) =
		subxt_utils::client::ws_client::<Hyperbridge>(&url, u32::MAX).await?;

	// Bind one state to BEEFY and one to the parachain client. `UNMAPPED_STATE_ID` is left out
	// so it resolves to no client at all.
	let kv_list: Vec<(Vec<u8>, Vec<u8>)> = vec![
		(consensus_state_client_key(&BEEFY_STATE_ID), BEEFY_CONSENSUS_ID.encode()),
		(consensus_state_client_key(&OTHER_STATE_ID), PARACHAIN_CONSENSUS_ID.encode()),
	];
	let set_storage =
		subxt::dynamic::tx("System", "set_storage", vec![storage_kv_list_to_value(&kv_list)]);
	submit_sudo(&client, &rpc_client, set_storage).await?;

	// fund_message is always filtered.
	let err = dispatch_error(&client, &rpc_client, fund_message(), Keyring::Bob).await?;
	assert!(is_call_filtered(&err), "fund_message must be filtered, got {err:?}");

	// handle_unsigned carrying a BEEFY consensus update is filtered.
	let err =
		dispatch_error(&client, &rpc_client, consensus_batch(BEEFY_STATE_ID), Keyring::Bob).await?;
	assert!(
		is_call_filtered(&err),
		"beefy consensus handle_unsigned must be filtered, got {err:?}"
	);

	// A batch is filtered as long as it carries a BEEFY update, even mixed with others.
	let mixed = subxt::dynamic::tx(
		"Ismp",
		"handle_unsigned",
		vec![messages_to_value(vec![
			consensus_message(OTHER_STATE_ID),
			consensus_message(BEEFY_STATE_ID),
		])],
	);
	let err = dispatch_error(&client, &rpc_client, mixed, Keyring::Bob).await?;
	assert!(
		is_call_filtered(&err),
		"mixed batch with a beefy update must be filtered, got {err:?}"
	);

	// A consensus update for a non-BEEFY client passes the filter and reaches the body.
	let err =
		dispatch_error(&client, &rpc_client, consensus_batch(OTHER_STATE_ID), Keyring::Bob).await?;
	assert!(
		is_bad_origin(&err),
		"non-beefy consensus handle_unsigned must pass the filter, got {err:?}"
	);

	// An unmapped consensus state resolves to no client, so it is not treated as BEEFY.
	let err =
		dispatch_error(&client, &rpc_client, consensus_batch(UNMAPPED_STATE_ID), Keyring::Bob)
			.await?;
	assert!(
		is_bad_origin(&err),
		"unmapped consensus handle_unsigned must pass the filter, got {err:?}"
	);

	Ok(())
}
