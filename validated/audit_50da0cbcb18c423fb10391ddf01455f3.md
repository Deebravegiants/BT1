## Custody Analog Found

### Title
`transfer_from` signed-approval replay allows unlimited unauthorized draining of USDK stablecoin funds - (File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move)

### Summary
The `usdk.move` example stablecoin implements an ERC20-`permit`-style delegated transfer, `transfer_from`, that authorizes a `spender` to move funds out of an `owner`'s primary fungible-asset store based on an off-chain signed `Approval` message. The message's replay-protection `nonce` is bound to `account::get_sequence_number(from)` — the owner's *account* transaction sequence number — rather than to a dedicated, incrementing "approval nonce" that is consumed by `transfer_from` itself.

### Finding Description [1](#0-0) 

The flow is:
1. `owner` signs an `Approval{owner, to, nonce, chain_id, spender, amount}` message off-chain, where `nonce = account::get_sequence_number(from)` at signing time.
2. Any account can act as `spender` and call `transfer_from`, which reconstructs the exact same `expected_message` using the **current** `account::get_sequence_number(from)`, verifies the signature via `account::verify_signed_message`, then calls `primary_fungible_store::transfer_with_ref` to move `amount` from `from`'s store to `to`'s store using the module's privileged `TransferRef`.

Critically, `transfer_from` never increments, marks, or otherwise consumes the `nonce`/sequence number it validated against. The only thing that would ever change `from`'s sequence number is `from` submitting its own on-chain transaction. Because `spender`-initiated calls to `transfer_from` do not touch `from`'s account sequence number, the *same* signed `Approval` message remains valid indefinitely and can be replayed by `spender` an unbounded number of times, each time invoking `transfer_with_ref` for the full `amount` again, as long as `from`'s balance in its `FungibleStore` remains sufficient and `from` does not submit an intervening transaction (which is not something `owner` is guaranteed to do promptly, especially for delegated/relayer use cases this pattern is meant to support).

This directly parallels the reported USDT/Arrakis bug-class: an authorization primitive (ERC20 allowance vs. here, a signed transfer authorization) is intended to be single-use/bounded, but the implementation fails to reset/consume that authorization after it is exercised, so it can be exploited again by the same unprivileged counterparty (`spender`) beyond what the owner intended.

### Impact Explanation
`spender` is an arbitrary, unprivileged account (anyone who obtains/observes the signed proof — which must be handed to them off-chain to be relayed, or which could leak via mempool/indexer observation if ever submitted once) can drain `owner`'s entire USDK balance in repeated `transfer_with_ref` calls using one single stale signature, instead of the one intended single transfer of `amount`. This corrupts custody of the fungible asset: value that should only move once per approval moves an unbounded number of times to `to` (which is also attacker-controlled/spender-controlled, since `to` is a caller-supplied parameter, not part of any commitment tied to a one-time use). This is a direct token-theft primitive against the `TransferRef`-backed `FungibleStore`, i.e. unauthorized transfer/custody-corruption of the stablecoin's held value — a high/critical custody impact.

### Likelihood Explanation
Likelihood is high in any real deployment that uses this `transfer_from` pattern for relayed/gasless transfers (the evident design intent, given `spender` pays gas on behalf of `owner`): every legitimate use of the feature produces a signature that is trivially replayable by the same `spender` (who by design already holds the proof) until the owner happens to submit an unrelated transaction. No cryptographic weakness or race condition is needed — this is a straightforward missing nonce-consumption bug in the intended common workflow, not merely a theoretical edge case.

### Recommendation
Do not derive the anti-replay nonce from `account::get_sequence_number(from)`, since that value is under the control of the owner's own transactions, not of `transfer_from`. Instead, maintain a dedicated per-owner (or per-owner/spender) approval nonce or "used proof" set (e.g., a `Table<address, u64>` of `used_nonce` per owner or a set of already-consumed proof hashes) stored in the stablecoin's own state, and increment/mark it as part of `transfer_from` itself before or after calling `transfer_with_ref`, so each signed `Approval` can be honored exactly once (or exactly up to its intended count) regardless of whether `owner` submits any other transactions.

### Proof of Concept
1. `owner` wants to pay `to` exactly `amount` USDK once via a gasless relay, and signs `Approval{owner=from, to, nonce=account::get_sequence_number(from) /* e.g. 5 */, chain_id, spender, amount}` and hands the proof + params to `spender`.
2. `spender` calls `usdk::transfer_from(spender, proof, from, scheme, pubkey, to, amount)`. `account::get_sequence_number(from)` is still `5` (unchanged, since `from` submitted no transaction), so `verify_signed_message` succeeds, and `amount` is moved from `from` to `to`.
3. `spender` calls `usdk::transfer_from` again with the identical arguments. `account::get_sequence_number(from)` is still `5` (assuming `from` still hasn't transacted), so the same signature verifies successfully again, and another `amount` is drained from `from`'s store.
4. Repeat step 3 until `from`'s balance is exhausted — all without any new authorization from `owner` beyond the single original signature. [2](#0-1) 

**Note on confidence:** This is example/reference code (`move-examples/fungible_asset/stablecoin`) rather than the core `aptos-framework` runtime, so its custody-relevance depends on whether this pattern is deployed as-is on mainnet by a stablecoin issuer; I could not verify deployment status from the repository alone. The underlying `account::verify_signed_message` and `primary_fungible_store::transfer_with_ref`/`TransferRef` mechanics are core-framework and behave exactly as described.

```text
    /// Allow a spender to transfer tokens from the owner's account given their signed approval.
    /// Caller needs to provide the from account's scheme and public key which can be gotten via the Aptos SDK.
    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,
    ) acquires Management, State {
        assert_not_paused();
        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }
```
