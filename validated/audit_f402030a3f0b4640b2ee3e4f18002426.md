**No Vulnerability found for this question.**

Reasoning:

The three functions in question — `sha2_512_internal`, `sha3_512_internal`, and `ripemd160_internal` — are declared as **private** `native fun` (no `public` modifier) inside `module aptos_std::aptos_hash` in [1](#0-0) .

In Move, a private function can only be called from within the module that declares it. This is enforced by the bytecode verifier as part of Move's module privacy/access-control model, not by application-level logic. An attacker's own module cannot reference `aptos_hash::sha2_512_internal` — any such attempt fails at compile/verification time with a visibility error; it is not merely convention, it's a hard boundary enforced by the VM. The only call sites for these internals are the public wrapper functions `sha2_512`, `sha3_512`, and `ripemd160`, which do perform the `features::sha_512_and_ripemd_160_enabled()` check before invoking the internal native [2](#0-1) .

The Rust-level native implementations in `aptos-move/framework/natives/src/hash.rs` themselves contain no feature check [3](#0-2) , but that is by design — the feature gate is enforced at the Move call-site (the wrapper), and the native registration only exposes these as named natives resolvable through the module's function table, which is still subject to the module's own visibility declarations at the Move bytecode level. There is no separate "backdoor" entrypoint that bypasses Move's visibility system for these specific natives.

Even hypothetically, if this bypass were possible, the scenario described (an unvetted hash algorithm enabling a "custom account-abstraction `authenticate()`") does not establish a custody break: any account-abstraction dispatch function must be explicitly deployed and opted into by the account owner (a privileged action by that account), so it can't be used to hijack unrelated accounts' assets from an unprivileged position. This fails the review's "unprivileged input crosses a real custody boundary" standard, since (a) the described bypass is blocked by Move's built-in private-function visibility enforcement, and (b) even granting the premise, no unprivileged path to controlling another party's assets is shown.

    context: &mut SafeNativeContext,

    mut args: VecDeque<Value>,

    debug_assert!(_ty_args.is_empty());
