<title>
Webhook HMAC Verification Does Not Cover Shop, Topic, or Webhook-ID, Enabling Cross-Tenant Webhook Forgery - (File: lib/shopify_api/webhooks/request.rb)
</title>

### Summary
The webhook HMAC verification in this gem computes and checks the signature over the raw request body only. The `shop-domain`, `topic`, and `webhook-id` headers — all of which are trusted and acted upon by `ShopifyAPI::Webhooks::Registry.process` — are never included in the signed material. An attacker who can obtain any one validly-signed webhook payload (e.g., the operator of a malicious/legitimate merchant install of a multi-tenant app, who naturally receives real signed webhooks for their own shop) can replay that exact body while forging the `shop-domain` (and/or `topic`/`webhook-id`) header to any other value, and the HMAC check still passes. This breaks the equality that should hold: `shop asserted by the signed payload == shop the app attributes the event to`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it to the `hmac` value with `OpenSSL.secure_compare`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers, with no cryptographic binding to the signed body: [3](#0-2) [4](#0-3) 

`Registry.process` gates only on the body's HMAC, then dispatches to the handler using these unauthenticated header values as the identity of the event (topic and shop): [5](#0-4) 

Because the signature never binds `shop-domain`, `topic`, or `webhook-id` to the body, any request whose body byte-for-byte matches a previously-observed, validly-signed webhook body will pass `Utils::HmacValidator.validate` regardless of which shop or topic headers are attached. This is precisely the "field acted on but not covered by the signature" class of bug (the chainId analog): the signature secures the body bytes, but the identity fields the application trusts and routes on (`shop`, `topic`, `webhook_id`) are outside that scope, so a signature valid in one context (one shop/topic) can be replayed to satisfy a different context.

### Impact Explanation
An attacker who operates (or compromises) one tenant installation of a multi-tenant Shopify app receives genuinely-signed webhook deliveries for their own shop. Because the signature covers only the raw body, they can capture such a delivery and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop domain (or the `topic`/`webhook-id` headers rewritten). `Registry.process` will accept it as authentic (`Utils::HmacValidator.validate` returns `true`) and hand the forged `shop`/`topic`/`webhook_id` straight to the app's handler via `WebhookMetadata`. Any app logic that uses `data.shop` to select which merchant's records to update, delete, or resync — or `data.topic` to decide which mutation to perform (e.g. `app/uninstalled`, `shop/redact`) — can be tricked into acting on/against a shop the attacker does not control, i.e. cross-tenant data corruption/exfiltration attributed to the wrong merchant. This matches the Critical impact category of cross-tenant access defined by the rules.

### Likelihood Explanation
Exploitability requires only: (1) the attacker have (or install) one tenant of the target multi-tenant app to receive a legitimately signed webhook of their choosing (body content the attacker fully controls, e.g. by performing the triggering shop action themselves), and (2) the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint (trivial for any internet-facing app). No access token, `client_secret`, or credential leak is required — only observation of one's own legitimately delivered webhook, which any merchant/app-installer naturally has. This makes the likelihood high for any app that keys business logic on the header-derived `shop`/`topic`/`webhook_id` rather than independently re-verifying tenant identity.

### Recommendation
Bind the identity fields into the verified material instead of trusting header values that sit outside the HMAC's scope:
- Include `shop-domain`, `topic`, and `webhook-id` (or at minimum `shop-domain`) in the string that is HMAC-verified, mirroring the chainId fix pattern (bind the context that the signature is meant to authorize), or
- Independently cross-check the `shop-domain` header against a shop known to have received a webhook with that exact `webhook-id`/body combination (e.g., idempotency/dedup tracking keyed by `webhook_id` plus verified shop), or
- At minimum, document prominently that `Registry.process`'s HMAC check does not authenticate `request.shop`/`request.topic`/`request.webhook_id`, and require host applications to treat these as untrusted unless corroborated by another mechanism (e.g. comparing against the shop tied to the currently active session before performing tenant-scoped writes).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise obtains one legitimate webhook delivery). Shopify sends a validly signed webhook:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B, computed by Shopify with app's client_secret>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: real-webhook-id
Body: B
```
2. Attacker resends the identical body `B` with the same untouched `x-shopify-hmac-sha256` value, but rewrites the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same HMAC as step 1, unchanged>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: real-webhook-id
Body: B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`B`) — identical to step 1 — so validation succeeds: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., webhook_id: "real-webhook-id")`, even though Shopify never issued this event for `victim-shop.myshopify.com`: [7](#0-6) 
Any app logic keyed on `data.shop` (e.g., "sync order data for this shop") now runs against the wrong tenant.
