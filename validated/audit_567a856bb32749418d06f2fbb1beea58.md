### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value delivered to the app's handler is read from an unauthenticated header that is never included in the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `Utils::HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string using the app's `api_secret_key` (shared across every shop that installs the app) [3](#0-2) . Meanwhile, `Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header with no cryptographic binding to the body or the HMAC [1](#0-0) . `Registry.process` validates the HMAC and then forwards `request.shop` directly to the handler as the tenant identity in `WebhookMetadata` [4](#0-3) .

The identity binding broken here is: *the shop whose secret validated the HMAC* (any shop that has installed the app and can trigger a webhook with attacker-influenced body content) is not equal to *the shop attributed to the event* (`data.shop`, taken from an unsigned header). Because the API secret is shared by the app across all its installations, any merchant that installs the app can obtain body+HMAC pairs that validate successfully, then replay them with a substituted `x-shopify-shop-domain` header pointing at a victim shop. The gem's own webhook handler will pass `Utils::HmacValidator.validate` and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
The gem's own documentation instructs developers to key their downstream processing directly off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) . Any host application following this documented, expected usage will process attacker-supplied body content under the identity of a shop the attacker does not control, i.e., cross-tenant data injection/spoofing — attributing fabricated order/product/customer events to another merchant's store, using that store's session/access token context for further processing.

### Likelihood Explanation
Exploitation only requires the attacker to install (or otherwise operate) any single shop instance of the target app — no privileged credentials, `api_secret_key`, or access token belonging to the victim are needed. The attacker generates a legitimately HMAC-signed webhook for their own shop (fully under their control, including the JSON body content) and simply changes the `x-shopify-shop-domain` header before delivering it to the app's public webhook endpoint.

### Recommendation
Bind the shop domain into the HMAC-verified data: include the `shop`/`x-shopify-shop-domain` value (and ideally `topic`/`webhook-id`) inside `to_signable_string`, or otherwise cryptographically verify that the shop asserted in the header matches a shop known to have that webhook subscription/secret, before handing `WebhookMetadata` to application handlers.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) on that shop, capturing the resulting HTTP POST — this yields a raw body plus a correctly computed `x-shopify-hmac-sha256` for that body (signed with the app's shared `api_secret_key`).
3. Replay the captured request to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header value with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks the (unchanged) body against the (unchanged) HMAC and succeeds. The registry then invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host application to process attacker-controlled data as if it originated from the victim shop.
