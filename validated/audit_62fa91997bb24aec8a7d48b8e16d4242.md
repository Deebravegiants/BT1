### Title
Biometric PCP tier-1/tier-2 data silently dropped from upload queue while signup is reported successful - ([File: src/agents/data_uploader.rs])

### Summary
The MasterChef "deposit fee not credited" bug class describes a case where value taken from a user is subtracted from accounting without ever being credited anywhere, causing permanent, silent loss with no error signaled to the depositor. The `data-uploader` agent in orb-core exhibits the same root-cause pattern: personal-custody-package (PCP) tier-1/tier-2 biometric payloads are pushed into a bounded queue after a signup completes, and when the queue reaches its "dropping threshold" the oldest queued package is silently discarded — with no error surfaced, no retry, and no effect on the already-reported signup success/failure status.

### Finding Description
After a signup, `Plan::do_signup` builds the PCP (tier0/tier1/tier2) and:
1. Uploads tier0 synchronously with retries via `upload_pcp_tier_0`; only *this* upload's success/failure determines whether the signup is reported as failed (`return Ok(result)` on failure). [1](#0-0) 
2. Fire-and-forgets tier1 and tier2 into the `data_uploader` agent's queue via `port::Input::new(data_uploader::Input::Pcp(...))`, only awaiting that the message was *enqueued*, not that it was *uploaded*. [2](#0-1) 

Inside the `data_uploader` agent, each tier has its own bounded queue with a `dropping_threshold`. When a new `Pcp` is pushed and the queue is already at the dropping threshold, the **oldest** entry in that queue is unconditionally evicted and its underlying data (and on-disk directory, in the persistent-queue variant) is deleted — with only a `tracing::error!`/log side effect, no propagation back to the plan/backend, and no accounting update: [3](#0-2) [4](#0-3) 

Crucially, the eviction is *silent* to the caller: `Agent::run`'s `Input::Pcp` handler never notifies anyone that a package was dropped, and the earlier `wait_queues`/`WaitQueues` blocking mechanism only prevents *new* signups from starting while queues are above a *blocking* threshold — it does nothing to protect already-enqueued packages from a subsequent signup's push once the dropping threshold is hit. [5](#0-4) 

This is structurally identical to the MasterChef bug: a value accepted from the user (here, the tier-1/tier-2 encrypted biometric package that the signup pipeline already treated as "delivered" once enqueued) is subtracted from the queue/state without ever being credited to its destination (the backend), and the loss is permanent and unrecoverable — the on-disk copy is deleted (`remove_dir_all`) with no retry path.

### Impact Explanation
Because tier0 upload success is the sole gate for reporting `SignupStatus::Success` / `debug_report.signup_successful()` in `report_signup_reason`, a dropped tier1/tier2 package causes:
- The Orb, backend enrollment record, and user-facing UI to report the signup as **successful**, even though a subset of the user's biometric self-custody encrypted data (tier1) and backend tier2 payload is permanently lost.
- Because packages are evicted oldest-first from a **shared per-tier queue that different signups push into**, a single signup can cause **another, unrelated signup's** already-enqueued PCP tier1/tier2 package to be evicted — a cross-signup state bleed where User B's queued upload can be silently destroyed by User A's subsequent signup without either user or the backend being informed.
- This can permanently strand a user's biometric self-custody package (the copy the user is meant to be able to recover/download later) with no server-side or Orb-side error record tying the loss back to that specific signup.

Given orb-core's stated priority on "Permanent lock, freeze, or unrecoverable corruption of user/project state," this qualifies as a genuine, reachable, no-privilege-required data-loss/integrity issue.

### Likelihood Explanation
Reachability requires no privileged access — any operator/user performing signups through the Orb hits this path on every successful biometric capture and pipeline run (`pcp_version >= 3` path). Triggering queue eviction requires sustained signup throughput exceeding the configured `pcp_tier1_dropping_threshold` / `pcp_tier2_dropping_threshold` faster than uploads can drain (e.g., degraded/slow network conditions combined with rapid consecutive signups, which is realistic in field deployment and is exactly the scenario the blocking/dropping-threshold mechanism was designed to handle, but handles by data destruction rather than backpressure/retry). I was unable to inspect the exact numeric default values of `pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold`/`pcp_tier1_blocking_threshold`/`pcp_tier2_blocking_threshold` in `src/config.rs` before running out of tool budget, so the precise queue depth required to trigger the drop (and thus the exact operational likelihood) is unconfirmed.

### Recommendation
- Do not silently drop packages on `dropping_threshold`; instead block/backpressure (as already partially done via `blocking_threshold`/`wait_queues`) until capacity is available, or explicitly fail the signup and surface a retryable error to the backend/UI when a package must be evicted.
- If eviction must remain for resource-exhaustion protection, tie it to `SignupReason`/`debug_report` state so that any signup whose tier1/tier2 package was evicted is not reported as `Success`, and emit a durable audit record (e.g., datadog metric + backend notification) identifying which `signup_id`/`user_id` lost data.
- Consider tier-specific accounting so a queue-full condition for one signup cannot silently evict a different signup's pending upload.

### Proof of Concept
1. Configure/observe a deployment where `pcp_tier1_dropping_threshold` is reached under normal network conditions (e.g., intermittent connectivity causing `upload_pcp` retries to stay in-flight while new signups keep enqueuing tier1 packages).
2. Perform signup A successfully; its tier1 `Pcp` is enqueued via `data_uploader::Input::Pcp` [6](#0-5) .
3. Before signup A's tier1 package is drained (uploaded) by an available `uploaders` slot, perform enough subsequent signups to hit `queues[i].len() == dropping_thresholds[i]`, causing the queue push handler to call `queues[i].drop_oldest().await` [7](#0-6) , which evicts and deletes signup A's queued tier1 package [4](#0-3) .
4. Observe: signup A was already reported `Success` in `report_signup_reason` based solely on tier0 upload and pipeline/fraud status [8](#0-7) ; there is no subsequent correction, retry, or notification indicating that signup A's tier1 (and potentially tier2) biometric package was never delivered to the backend.

                            break;

    async fn drop_oldest(&mut self) {
        match self {
            Self::Memory { queue } => {
                queue.pop_back();
            }
            Self::Persistent { path, queue, .. } => {
                let Some(id) = queue.pop_back() else { return };
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during drop_oldest, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {}
                }
            }
        }
    }
