## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop` is read directly from the `X-Shopify-Shop-Domain` header without being part of the signed payload. Any party who can trigger a genuine webhook delivery for one shop (e.g., a malicious merchant who has installed the app on their own store) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `shop-domain` header. `Utils::HmacValidator.validate` will still succeed, because it never checks the header value, and `Webhooks::Registry.process` will hand the attacker-chosen `shop` straight to the app's handler as if it were authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read verbatim from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not included anywhere in the signable string: [2](#0-1) 

`HmacValidator.validate_signature` computes and compares the signature only over `verifiable_query.to_signable_string`, i.e. the body, never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` straight to the registered handler without any additional binding check: [4](#0-3) 

This is exactly the identity-binding break described by the bug class: the field the app *acts on* (`shop`, used by the handler to attribute/store the webhook data) is not the field that was actually *authenticated* (only the body bytes are HMAC-covered). Formally, the equality the code implicitly assumes — `shop_that_authenticated == shop_the_data_is_attributed_to` — does not hold, because `shop_that_authenticated` is undefined (the header is outside the MAC) while `shop_the_data_is_attributed_to = request.shop` is attacker-controlled.

Because the `api_secret_key` is shared by the app across *all* installed shops (it is not shop-specific), any merchant who has the app installed on their own store legitimately receives real webhooks with a valid HMAC over the body. That HMAC/body pair remains valid for the same body when replayed to the app's public webhook endpoint with a forged `shop-domain` header pointing at a victim shop.

### Impact Explanation
This qualifies as a Critical-tier finding under the given impact categories — cross-tenant access — because a low-privilege actor (a merchant who installed the app) can make the host application process/store attacker-supplied webhook data under a victim shop's identity, without ever needing the `client_secret`/`api_secret_key`. Any downstream logic that uses `WebhookMetadata#shop` (returned to the handler) to look up sessions, update per-shop records, or trigger shop-scoped side effects is directly exposed to cross-tenant data injection/corruption.

### Likelihood Explanation
Likelihood is high for any consumer of this gem: capturing a legitimate webhook only requires installing the app on any shop (something attackers can do without special privilege for public apps), and replaying it with a modified header is trivial (no cryptographic work needed since the body bytes, and thus the HMAC, are unchanged).

### Recommendation
Bind the shop identity into the signed material, or otherwise ensure the shop used by the handler matches the shop the caller is authorized to act as (e.g., look up the session for `request.shop` and reject if no matching, previously-established session/install exists for that exact shop before invoking the handler). At minimum, document prominently that `Webhooks::Request#shop` is unauthenticated and must never be trusted for identity/authorization decisions without independently verifying that the shop has an active, previously-created session in the host application's own store.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and lets it trigger any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's shared `api_secret_key`.
2. Attacker sends a POST request directly to the app's webhook endpoint with:
   - Body: the exact same bytes `B`
   - Headers: `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create` (unchanged), `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new` parses the headers/body successfully.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `B` with the shared secret — identical to `H`. [4](#0-3) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body `B`, and the host app processes/stores it as legitimate data for the victim tenant.
