### Title
Excess native token sent to `EvmHost.dispatch`/`fundRequest` is permanently stuck in the host contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` accept `payable` calls and forward the entire `msg.value` into `IUniswapV2Router02.swapETHForExactTokens`, an exact-output swap that only consumes as much ETH as needed to produce the requested fee-token output and refunds any unused ETH to its caller. Because `EvmHost` is the direct caller of the router, that refund lands in `EvmHost`'s own balance rather than being returned to the end user. None of these three functions read the `amounts` array returned by the swap or otherwise compute/forward the leftover value back to `_msgSender()`, so any overpayment of native token is stranded inside the `EvmHost` contract.

### Finding Description
Any unprivileged actor — an app contract or end user dispatching a POST/GET request through Hyperbridge, or funding an existing request — that sends more native token than the swap actually requires will have the surplus trapped in `EvmHost`. The three affected code paths are:
- `dispatch(DispatchPost memory post)` [1](#0-0) 
- `dispatch(DispatchGet memory get)` [2](#0-1) 
- `fundRequest(bytes32 commitment, uint256 amount)` [3](#0-2) 

In every case, `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is invoked without capturing its return value. `swapETHForExactTokens` is an exact-output-token / max-input-ETH swap: it only pulls in `amounts[0] <= msg.value` ETH and refunds `msg.value - amounts[0]` to the calling address (here, `EvmHost`). Since `EvmHost` never reads `amounts[0]` and never sends any ETH back to `_msgSender()`, that refunded ETH permanently accumulates in the contract with no code path exposed to the caller to reclaim it.

This is the exact bug class from the referenced report: a payable function forwards a `value`/`msg.value` amount into a downstream call without reconciling actual consumption against what was sent, so any surplus is stuck with no user-facing refund. The difference from the original finding is that here the "surplus" specifically arises from Uniswap's exact-output refund mechanics rather than a raw excess-value passthrough, but the root cause and the outcome (value stuck, unrecoverable by the depositor) are identical. The codebase's own `IntentGatewayV2.placeOrder` demonstrates the maintainers are aware of and mitigate this exact problem by capturing `amounts[0]` and refunding the difference [5](#0-4) , but the equivalent fix was not applied to `EvmHost` itself.

### Impact Explanation
Any caller who sends more native token than strictly needed for the Uniswap exact-output swap (which is the normal/expected way to call these functions, since callers must overestimate slippage/price to avoid reverts) loses the difference permanently to the `EvmHost` contract balance, with no function exposed to withdraw it back to the original payer. This is a direct, protocol-level fund-loss bug reachable from a single unprivileged transaction dispatching a POST/GET request or funding a pending request — core, frequently used entry points of the messaging system. This is rated Medium severity: it does not compromise message integrity, consensus, or allow theft of other users' funds, but it causes concrete, permanent loss of the caller's own funds on every overpaid dispatch/fundRequest call, and is highly likely to occur in practice since exact quoting via Uniswap spot price at call time is inherently imprecise (slippage between quote-time and execution-time) and documentation elsewhere in the repo explicitly instructs users to overpay and expects a refund ("Estimate Fees Off-Chain" callout, and IntentGatewayV2's own refund behavior sets that expectation).

### Likelihood Explanation
Likelihood is high: any app or user dispatching a request with native-token payment (the documented default usage path per `docs/content/developers/evm/messaging/post-requests.mdx` and `get-requests.mdx`) that supplies a safety margin above the quoted fee (standard practice to avoid revert from price movement) will trigger this loss on every single call. No adversarial conditions are required — it happens under normal, honest usage.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()` via a safe ETH transfer, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires ~0.1 ETH worth of the fee token at current Uniswap spot price (a normal safety margin against slippage).
2. Inside `dispatch`, `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` executes, consuming only ~0.1 ETH and refunding ~4.9 ETH to `address(this)` (`EvmHost`), per Uniswap V2 Router semantics.
3. `dispatch` never reads the swap's `amounts` return value and has no logic to forward any refund to `msg.sender`.
4. The ~4.9 ETH surplus remains in the `EvmHost` contract balance indefinitely; the caller has no function to reclaim it. Repeating this across many callers accumulates permanently stuck ETH in `EvmHost`. [1](#0-0)
