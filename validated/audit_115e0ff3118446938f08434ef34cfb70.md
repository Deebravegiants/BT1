### Title
Token Exchange accepts non-admin (buyer-facing) session tokens, allowing privilege escalation to a full merchant access token - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` performs an OAuth token exchange using only the `dest` and `aud` claims of a supplied session token, without verifying that the token's `iss` claim identifies it as an **admin** session token. Session tokens signed with the app's `client_secret` are also issued by Shopify for buyer-facing surfaces (e.g. checkout UI extensions), which are handed to unauthenticated/unprivileged customers, not merchant staff. Because `exchange_token` does not bind the "is this an admin token" identity check that the library itself defines (`JwtPayload#admin_session_token?`), a buyer-facing token can be exchanged for a full merchant **offline** access token.

### Finding Description
`ShopifyAPI::Auth::JwtPayload` decodes any JWT signed with `Context.api_secret_key` and only validates `aud == Context.api_key` and expiry/nbf: [1](#0-0) 

The class itself distinguishes admin tokens from other token types via `admin_session_token?`, but this check is only used to gate `shopify_user_id`, not to gate general trust of the token: [2](#0-1) [3](#0-2) 

`TokenExchange.exchange_token` decodes the supplied `session_token`, takes its `shop` (from `dest`), and immediately performs a token exchange against Shopify's OAuth endpoint with the app's `client_id`/`client_secret`, **without checking `admin_session_token?`**: [4](#0-3) 

The gem's own documentation states the expected input is the admin session token "provided by App Bridge... when the app is loaded in Admin," i.e. an admin-scoped identity: [5](#0-4) 

However, Shopify also issues structurally identical JWTs (signed with the same app `client_secret`, same `aud`) for other surfaces such as checkout UI extensions, where `iss` ends with `/checkouts` instead of `/admin` and `sub` is a customer GID rather than a merchant staff user id, as reflected in the library's own test fixtures: [6](#0-5) 

Such checkout-extension tokens are delivered to the **buyer's browser** during checkout — an unprivileged, unauthenticated-to-the-merchant context. The identity binding that should hold is: `session_token used for merchant token exchange` ⇔ `session_token.iss identifies an admin session`. `TokenExchange.exchange_token` breaks this equality by trusting `dest`/`aud` alone and never checking `iss`.

### Impact Explanation
An attacker who obtains a valid, Shopify-issued but buyer-scoped session token (e.g. from a checkout UI extension context they have access to as a shopper) can pass it to `TokenExchange.exchange_token` with `RequestedTokenType::OFFLINE_ACCESS_TOKEN` and receive back a full **offline merchant access token** for that shop — the same credential normally obtained only through merchant-authorized OAuth/managed installation. This is a critical authentication bypass and access-token theft: it converts a buyer-level, session-scoped credential into a merchant-wide, long-lived API credential, breaking the tenant-privilege boundary the token-exchange flow is meant to enforce.

### Likelihood Explanation
Exploitation requires only a Shopify-signed session token of any type for the target app (aud must match the app's `api_key`) — no merchant credentials, secrets, or admin access are needed. Because host apps calling this library follow the documented `exchange_token(session_token:, requested_token_type:)` API exactly as intended, and the library performs no `iss`/token-type check itself, this is directly reachable through this gem's own code path, not merely a host-application misuse.

### Recommendation
In `TokenExchange.exchange_token`, validate `jwt_payload` is an admin session token (e.g. require `jwt_payload.send(:admin_session_token?)` or expose and check an equivalent public predicate) before proceeding with the exchange, raising `ShopifyAPI::Errors::InvalidJwtTokenError` otherwise.

### Proof of Concept
1. Attacker obtains a valid checkout UI extension session token for shop `victim.myshopify.com` (delivered to their own browser as a shopper during checkout — no merchant privileges required). This token is signed with the app's real `client_secret`, has `aud == app_api_key`, `dest == "victim.myshopify.com"`, and `iss` ending in `/checkouts`.
2. Attacker calls:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: stolen_checkout_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `JwtPayload.new` accepts the token (only checks `aud` and expiry) at [7](#0-6) ; `exchange_token` never checks `iss` and proceeds to POST to `/admin/oauth/access_token` with the app's `client_secret` and the stolen token as `subject_token`, per [8](#0-7) .
4. Shopify returns a valid offline access token for `victim.myshopify.com`, which the attacker now controls despite never having merchant/admin access.
