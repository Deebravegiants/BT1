This confirms the vulnerability: the gem's own documentation explicitly presents `data.shop` as a trusted, verified field for the host application to key its shop-scoped logic on — the docs describe `Registry.process` as verifying "the request did indeed come from Shopify" before dispatching `data.shop` to the handler.

### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `HmacValidator.validate` verifies the HMAC solely against that signable string [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all read from HTTP headers [3](#0-2)  that are never part of the signed bytes. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop bound in the HMAC-verified payload == shop delivered to the handler`. In this gem, HMAC verification only proves `bytes_verified(raw_body) == bytes_signed_by_secret(raw_body)`; it says nothing about the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers [5](#0-4) . `Registry.process` raises `InvalidWebhookError` only if the HMAC computed over the body fails [6](#0-5) , then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, none of which were cryptographically bound to that body [7](#0-6) .

Because the app-supplied `handler.handle(data:)` is documented as receiving a trusted `shop` domain to key shop-scoped processing (job dispatch, DB record lookups, etc.) [8](#0-7) , an unprivileged internet user can:
1. Obtain one legitimately-signed webhook delivery (raw body + `X-Shopify-Hmac-Sha256`) for any shop — trivially available to any merchant/attacker who installs the app on their own shop and captures their own webhook traffic.
2. Replay that same body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header value for a *different* victim shop.
3. `HmacValidator.validate` passes because it only checks the body signature [9](#0-8) , and `Registry.process` dispatches the attacker-chosen `shop` value straight to the handler [10](#0-9) .

This breaks the equality `shop authenticated by HMAC == shop acted upon by the handler`, letting an attacker cause the host application to attribute another tenant's webhook body to a victim shop of the attacker's choosing (or attribute the attacker's own data under a spoofed topic), enabling cross-tenant data confusion.

### Impact Explanation
This falls under Critical - cross-tenant access: the app's webhook processing pipeline can be tricked into applying legitimately-signed webhook content under an attacker-chosen shop/tenant identity, since the `shop` value the handler trusts is not part of what the HMAC actually authenticates.

### Likelihood Explanation
Likelihood is realistic: any actor who can install the app on any shop (including their own, as an unprivileged merchant) can capture one valid signed webhook and replay it against the shared webhook endpoint with a forged `shop-domain` header, with no need for the `api_secret_key`, TLS interception, or privileged access.

### Recommendation
Bind the shop (and topic/webhook id) identity into the HMAC-verified surface rather than trusting unauthenticated headers: derive `shop` used for handler dispatch from a value carried inside the signed body when Shopify includes it, or require the app to independently verify that the header-provided `shop` corresponds to a webhook subscription actually registered for that shop/topic/webhook_id combination (e.g., cross-check `webhook_id` against Shopify's API) before invoking the handler in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
```ruby
# Attacker captures a legitimately-delivered webhook for their own shop "attacker.myshopify.com"
raw_body = '{"id": 123, "note": "legit order"}'
valid_hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body))

# Attacker replays the same body/HMAC but swaps the shop-domain header to a victim shop
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,       # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
# HMAC validation succeeds because it only checks raw_body against valid_hmac;
# the shop attribution is fully attacker-controlled.
```

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }
