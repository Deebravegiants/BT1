### Title
OmniBridge `describeWithdrawal` matches transfer by raw array index instead of recipient/asset, risking wrong-withdrawal status/hash reporting - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal` picks the transfer to report on purely by numeric array position (`args.index`) into the list returned by `omniBridgeAPI.getTransfer({ transactionHash })`, with no verification that the element at that position actually corresponds to the withdrawal being queried (no match on recipient, asset, or amount). This is the direct structural analog of the reported `GetVoterIndex` bug class: a caller trusts that a positional/index lookup into an externally-supplied list is stable and correctly ordered, without verifying identity.

### Finding Description
`createWithdrawalIdentifiers` assigns each withdrawal a purely local, per-bridge-route sequence counter (`index`) based on the order withdrawals appear in `withdrawalParams`: [1](#0-0) 

This `index` is later used by `OmniBridge.describeWithdrawal` to directly index into the array returned by the Omni Bridge indexer API for a given NEAR transaction hash: [2](#0-1) 

Nothing in this code establishes that the ordering of `omniBridgeAPI.getTransfer(...)` results matches the local submission-order counter assigned in `createWithdrawalIdentifiers`. Contrast this with the POA bridge's `describeWithdrawal`/`findMatchingWithdrawal`, which explicitly avoids trusting the API's ordering and instead matches by `assetId`, with an explicit comment stating the reason: [3](#0-2) [4](#0-3) 

The Omni Bridge path has no equivalent safeguard: it assumes `getTransfer` always returns transfers for a multi-withdrawal batch in the exact order they were included in the withdrawal batch. If the indexer's storage/query returns transfers in a different order (e.g., by internal transfer ID, chain, or finalization time rather than submission order within the tx) — which is exactly the scenario the POA bridge code explicitly guards against for its own API — `args.index` will select the wrong transfer object.

### Impact Explanation
If the transfer at position `args.index` does not correspond to the withdrawal actually being polled (e.g., in a batch withdrawal with two different assets/recipients bridged via Omni Bridge in the same NEAR tx), `describeWithdrawal` will report the `txHash` and completion `status` of a *different* withdrawal as if it belonged to the one being watched. Downstream consumers (`watchWithdrawal`, `createWithdrawalCompletionPromises`, `waitForWithdrawalCompletion`) resolve based on this status, so an integrator could:
- Mark withdrawal A as "completed" using withdrawal B's destination tx hash, causing the integrator to credit/reconcile using an unrelated transaction hash for the wrong recipient/amount.
- Prematurely resolve one leg of a batch withdrawal while silently masking the true state of another leg.

This matches the "status or hash misreport making an integrator credit or refund twice" High-severity class, since it swaps which withdrawal is deemed completed and with which txHash, without any funds actually moving incorrectly on-chain — but it corrupts the SDK's completion/status equality between the withdrawal being tracked and the withdrawal actually reported.

### Likelihood Explanation
This can only be triggered in genuine multi-withdrawal-via-OmniBridge batches within a single NEAR transaction (an intended, real use case — the README/RFC explicitly documents batch withdrawals with distinct legs). Whether the underlying Omni Bridge indexer's `getTransfer` actually returns entries in strict submission order could not be confirmed from the SDK repo (external indexer behavior is out of scope to verify here), so this is reported as a code-level equality gap (assumed-stable index vs. actual API ordering) rather than a confirmed live exploit — the same posture the POA bridge code explicitly hedges against for its own API.

### Recommendation
In `OmniBridge.describeWithdrawal`, do not select the transfer purely by `args.index`. Match the correct transfer using an identity field that is guaranteed to be stable per withdrawal (e.g., filter by `recipient`/destination address and asset, similar to `findMatchingWithdrawal` in `poa-bridge.ts`), falling back to positional indexing only after confirming order stability with the indexer team, or by requesting an explicit per-transfer index/ID from the Omni Bridge API that is guaranteed to match submission order.

### Proof of Concept
1. Submit a batch withdrawal with two Omni Bridge legs in a single NEAR tx: Transfer #1 (USDC → recipient X) and Transfer #2 (BTC → recipient Y).
2. `createWithdrawalIdentifiers` assigns `index: 0` to the USDC withdrawal and `index: 1` to the BTC withdrawal (per-route counters), per `withdrawal-watcher.ts:80-107`.
3. Assume `omniBridgeAPI.getTransfer({ transactionHash })` returns the BTC transfer first and USDC transfer second (order not guaranteed to match submission order).
4. `describeWithdrawal` for the USDC withdrawal (`args.index = 0`) reads array position `[0]`, which is actually the BTC transfer, and returns its `txHash`/status as if it belonged to the USDC withdrawal.
5. The integrator, using `waitForWithdrawalCompletion`, credits/reconciles the USDC withdrawal using the BTC transaction hash — a status/hash misreport.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
