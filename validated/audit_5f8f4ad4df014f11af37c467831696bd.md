### Title
Unisolated per-leaf validation in `HandlerV2` batch handlers lets a single stale/duplicate message revert delivery of an entire batch of unrelated valid messages - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts` and `handleGetRequestTimeouts` each iterate over an array of independent, unrelated ISMP messages proven together under a single MMR/state-trie proof, and revert the *entire* call the instant any single element fails a per-item check (timeout, duplicate receipt, unknown request). There is no per-message isolation (e.g. try/catch or skip-and-continue), so one stale or already-delivered leaf blocks delivery of every other, still-valid message batched alongside it — the exact "missing per-item check + all-or-nothing loop" root cause described in the source report for `SafEth::stake()`.

### Finding Description
`handlePostRequests` first loops over every leaf checking destination and timeout, reverting the whole transaction on the first failure: [1](#0-0) 

then, after the merkle multiproof is verified, loops again and reverts atomically on any duplicate receipt before dispatching the rest: [2](#0-1) 

`handleGetResponses` has the identical pattern (`revert UnknownMessage()` / `revert DuplicateMessage()` abort the whole loop): [3](#0-2) 

`handlePostRequestTimeouts` / `handleGetRequestTimeouts` follow the same all-or-nothing per-item validation before dispatch: [4](#0-3) 

These handlers are explicitly **permissionless** — "anyone can call them to relay messages," and the SDK/docs advertise self-relaying by any user, not just the operator relayer: [5](#0-4) [6](#0-5) 

The off-chain relayer batches many independent requests into one `handlePostRequests`/`handleGetResponses` call per MMR proof to save gas, chunking large sets of unrelated messages together: [7](#0-6) 

Unlike `EvmHost.dispatchIncoming`, which deliberately swallows a failing app-level `onAccept` call so the rest of the batch still proceeds: [8](#0-7) 

the handler-level per-leaf checks (timeout, duplicate, unknown-request) have **no equivalent isolation** — they use `revert` directly inside the loop, so a single bad item unconditionally aborts the whole call, undoing the verification work and gas already spent for every other, otherwise-deliverable message in the batch.

### Impact Explanation
Because delivery is permissionless and batches are built by grouping many unrelated requests under one MMR/state proof for gas efficiency, one item that has already timed out, already been delivered (duplicate receipt), or is otherwise invalid poisons the entire submission. An adversary (or ordinary network delay/reordering) can:
- Front-run a relayer's `handlePostRequests` tx by individually delivering one of its bundled leaves, so by inclusion time that leaf's receipt already exists, causing `DuplicateMessage()` and reverting the relayer's whole multi-message batch — griefing the relayer's gas and delaying delivery of every unrelated valid request bundled in it.
- Include (or wait for) one imminently-timing-out request in a large chunk; if the transaction is delayed past its timeout by mempool congestion, the entire chunk (potentially dozens of unrelated valid, still-live requests) fails atomically and must be rebuilt and resubmitted.

This is a route made "unable to deliver messages" reliably — an accepted Medium/High-class impact — even though ISMP's request/response semantics allow safe retry (no receipt is persisted on revert), the effect is a systemic denial-of-service on batched relaying that scales with batch size and directly increases operational cost and latency for the permissionless message-delivery path.

### Likelihood Explanation
Likelihood is meaningful but not universal: message composition mostly comes from real on-chain queues so an attacker cannot inject non-existent requests, but they can cheaply (a) submit their own request with a very short timeout and let it be swept into a relayer's batch, or (b) race-deliver one leaf of an observed pending batch tx to trigger `DuplicateMessage()`. Both require only a single ordinary transaction/extrinsic from an unprivileged actor, and the underlying condition (timeouts elapsing under normal network delay) can also occur without any adversary at all, especially for large batches under `chunk_size`.

### Recommendation
Wrap the per-leaf checks and dispatch in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` so that a single invalid/expired/duplicate item is skipped (and optionally emits a "SkippedMessage" event) rather than reverting the whole call, mirroring the isolation already used for `dispatchIncoming`'s app callback. At minimum, filter out to-be-rejected leaves from the merkle multiproof set before constructing the batch on the relayer side, and additionally harden the on-chain handler so an already-processed or expired leaf degrades gracefully instead of aborting sibling messages.

### Proof of Concept
1. Relayer A observes N pending POST requests destined for chain B, all provable under the same MMR root at height H, and batches them into a single `PostRequestMessage` for gas efficiency (`batch_requests` in `retries.rs`).
2. Relayer A submits `handlePostRequests(host, message)` to `HandlerV2`.
3. Before A's tx is mined, an unprivileged actor (or Relayer C) submits a `handlePostRequests` call containing only request #k from that same set, which lands first and stores its receipt via `host.dispatchIncoming`.
4. When A's transaction lands, the second loop in `handlePostRequests` hits `if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();` for leaf #k and reverts the entire call.
5. All N-1 other still-valid requests in A's batch fail to deliver despite having valid proofs and no timeout, forcing A to rebuild and resubmit a smaller batch excluding #k, at the cost of the reverted transaction's gas. [2](#0-1)

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }

## Self Relayed Requests

Self-relaying allows you to deliver POST requests to the destination chain yourself, instead of relying on the Hyperbridge relayer network. This is useful when you want full control over delivery timing, need to save on relayer fees, or want to guarantee delivery for critical requests.

The `@hyperbridge/sdk` provides tools to track POST requests and automatically generates the calldata needed to execute [`handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) on the destination chain's [`IHandler`](/developers/evm/api/ihandler) contract.

To learn how to self-relay requests:

1. **[Get Started with the SDK](/developers/sdk/getting-started)** - Install and set up the Hyperbridge SDK
2. **[Track POST Requests](/developers/sdk/tracking/post-requests)** - Monitor request status and extract delivery calldata
3. **[IsmpClient API](/developers/sdk/api/ismp-client)** - Use the [`postRequestStatusStream()`](/developers/sdk/api/ismp-client#postrequeststatusstream) method to get calldata when `HYPERBRIDGE_FINALIZED` status is reached

The SDK automatically generates the [`PostRequestMessage`](/developers/evm/api/ihandler#postrequestmessage) proof and calldata you need to call the [`IHandler.handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) function on the destination chain. You can make your users self-relay requests or run a server which can relay requests on behalf of users.

	ctx: &RetryContext,
	profitable: &[(PostRequest, Query)],
	height: StateMachineHeight,

	let dest_state_machine = ctx.dest.state_machine_id().state_id;
	let mut messages = vec![];

	for chunk in profitable.chunks(chunk_size(dest_state_machine)) {
		let (requests, queries): (Vec<_>, Vec<_>) = chunk.iter().cloned().unzip();

			.hyperbridge
			.query_requests_proof(height.height, queries, dest_state_machine)
			.await?;

		messages.push(Message::Request(RequestMessage {
			requests,
			proof: Proof { height, proof },
			signer: ctx.dest.address(),
		}));
	}
