### Title
Webhook `shop-domain` header is trusted as the tenant identifier but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so `Utils::HmacValidator.validate` only proves that the *body* was signed with `api_secret_key`. The `shop-domain` header, which `ShopifyAPI::Webhooks::Registry.process` passes straight into `WebhookMetadata#shop` and hands to the app's `WebhookHandler`, is never included in the HMAC computation. Any principal capable of producing one valid `(body, hmac)` pair for the app (i.e. a merchant who has installed the app and receives real webhooks for their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will report the request as HMAC-valid and dispatch it to the handler labeled with the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (attacker-controlled, unauthenticated-by-signature) header: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards `request.shop` unchanged into `WebhookMetadata`, which is the documented tenant-identifying field handed to the app's handler: [3](#0-2) 

The docs explicitly instruct apps to treat `data.shop` as the shop/tenant identifier for the webhook (e.g. to enqueue per-shop jobs): [4](#0-3) 

The identity binding broken is: `hmac-signed(body) == hmac-signed(body, shop)`. In reality the gem verifies `hmac == HMAC(secret, body)` but then trusts `shop` as if it too were covered by that HMAC. Since `api_secret_key` is shared across every shop that installs the app, any shop that legitimately receives a webhook (with a valid body+HMAC for a topic it can trigger, e.g. `app/uninstalled`, `orders/create`, etc.) can capture that pair and resend it to the app's public webhook endpoint with a different `shopify-shop-domain` header naming a victim shop. `Utils::HmacValidator.validate` still passes because it only checks `verifiable_query.to_signable_string` (the body), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain while the body content is really the attacker's own shop's data.

### Impact Explanation
This is a cross-tenant identity confusion in a multi-tenant app: a merchant that has installed the app (a low-privileged, unauthenticated-relative-to-other-tenants actor) can cause the app's webhook handler to process/attribute a forged shop identity for arbitrary victim shops that also use the same app. Depending on how the host app uses `data.shop` (e.g., to select which shop's DB row/session to update, uninstall/redact, mark data deleted, etc.), this enables cross-tenant data corruption or state confusion for shops the attacker does not control, which maps to the "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-high: it requires the attacker to already be a legitimate (even trial) merchant of the app so they can generate one valid signed webhook body, and requires them to guess/know a victim's `myshopify.com` domain (public information) and to know a topic whose forged body content doesn't need to make semantic sense to the handler (e.g. mandatory topics like `app/uninstalled`, `shop/redact`) to cause impact. No possession of `api_secret_key` or access tokens is required beyond what any installer already implicitly has via real webhook deliveries.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed payload the gem verifies, or otherwise cryptographically bind `shop-domain` to the HMAC before trusting it. Since Shopify's own HMAC only signs the body, the safer fix within this gem is to require host apps to cross-check `request.shop` against an independently known/authorized shop (e.g., a shop with an existing installed session) before dispatching, and to document/enforce this in `Registry.process`, rather than passing the raw unauthenticated header value directly into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `app/uninstalled`).
2. Shopify delivers a legitimate webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`. Attacker captures `B` and the HMAC value from their own inbound traffic (e.g., via a webhook debugging proxy they control).
3. Attacker POSTs to the app's public webhook endpoint with the exact same body `B` and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which matches, so `Registry.process` proceeds: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the body content is the attacker's own shop's webhook payload, causing the app to act on/attribute data for a shop the attacker does not control.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
