### Title
SDK relayer-fee quoting for L2/L2-rollup destinations omits L1 data/rollup fee, causing under-funded dispatches that no relayer will deliver - ([File: sdk/packages/sdk/src/chains/evm.ts])

### Summary
The Elfi-protocol M-15 report describes keepers being under-compensated because `GasProcess.processExecutionFee` only reimburses L2 execution gas (`usedGas * tx.gasprice`) and ignores the L1 rollup/data fee that keepers actually pay on L2s such as Arbitrum/Optimism-stack chains. Hyperbridge has the analogous fee-quoting responsibility split between two independent implementations: the Rust relayer (`tesseract`) correctly adds the L1 data fee via `get_l2_data_cost`, but the TypeScript SDK helpers that end users/integrators call to compute the `relayerFee` attached to a dispatch — `EvmChain.estimateGas` [1](#0-0)  — only call `estimateContractGas` and add a flat 600k for consensus verification, with **no L1 data-fee component** for OP-stack (or Arbitrum-orbit) destinations.

### Finding Description
`EvmChain.estimateGas` estimates the destination-chain gas units for `handlePostRequests` and adds a fixed consensus-verification adder, but never queries the destination's `OVM_GasPriceOracle.getL1Fee` (or equivalent Arbitrum L1 pricing) to account for the L1 data/rollup fee component of the transaction cost: [2](#0-1) 

This helper is consumed directly by fee-quoting logic that sets the actual `relayerFee` field encoded into dispatched requests:
- `TokenGateway.quoteNative` uses it to compute `gasCostInNative = gas * gasPrice` for the relayer fee on a teleport, with only a flat 1% buffer, no L1-fee term: [3](#0-2) 
- `HyperFungibleToken`'s dispatch path derives its default `relayerFeeInSourceFeeToken` from the same `estimateGas` call with a 10% gas-price bump but again no L1-fee term: [4](#0-3) 

By contrast, the actual delivering relayer's profitability logic in `tesseract` (Rust) correctly computes L1 data cost for OP-stack chains via `OvmGasPriceOracleInstance::getL1Fee` and folds it into `execution_cost`: [5](#0-4) [6](#0-5) 

The relayer only delivers a message if `fee_metadata >= fee_with_profit`, where `fee_with_profit` is the L1-inclusive `execution_cost` plus the configured profit margin: [7](#0-6) 

Because the SDK's `relayerFee` quote for a dispatch to an OP-stack (or similar) destination is missing the L1 data-fee term that the relayer's profitability gate actually requires, a message dispatched using the SDK-quoted fee can be perpetually below the relayer's break-even threshold. No permissionless relayer will ever pick it up, since it is unprofitable by design of the profitability check.

### Impact Explanation
This is the direct token-bridger/message-dispatcher analog of the ElFi bug: a dispatcher relying on the SDK's fee quote under-funds the relayer fee for cross-chain messages (TokenGateway teleports and HyperFungibleToken bridging) to L2 rollup destinations, since the L1 rollup/data-fee component is silently dropped. The result is a route that cannot deliver the message — the request just sits, unrelayed, because it fails every relayer's profitability check — matching the accepted impact "a route unable to deliver messages." Funds (the dispatched relayer fee, and for `TokenGateway`/`HyperFungibleToken` also the bridged principal held in escrow pending redemption on the destination) become effectively stuck until the request times out and is refunded, or until a user manually calls `fundRequest` with a correctly-computed additional fee — which requires already knowing about this shortfall.

### Likelihood Explanation
Likelihood is high for teleports/bridges targeting popular OP-stack L2 destinations (Base, Optimism, etc.), since every unprivileged caller of `TokenGateway.quote()`/`quoteNative()` or `HyperFungibleToken`'s default fee path is affected automatically whenever they don't manually override `relayerFee`. The gap is systematic (missing calculation, not a bug triggered by adversarial input), so it reproduces on every default-fee dispatch to such chains, especially when L1 base fees are elevated.

### Recommendation
Extend `EvmChain.estimateGas` (or its callers) to query the destination chain's L1 data-fee oracle — `OVM_GasPriceOracle.getL1Fee(txData)` for OP-stack chains and the Arbitrum `ArbGasInfo` L1 pricing equivalent for Arbitrum-orbit chains — and add that cost (converted to native/fee-token as appropriate) to the `relayerFee` computed by `TokenGateway.quoteNative` and `HyperFungibleToken`'s default-fee path, mirroring the L1-inclusive `execution_cost` calculation already implemented in `tesseract/messaging/evm/src/gas_oracle.rs`/`provider.rs`.

### Proof of Concept
1. Call `TokenGateway.quote()`/`quoteNative()` (or dispatch via `HyperFungibleToken` with no explicit `relayerFee`) targeting an OP-stack destination (e.g., Base).
2. Observe the computed `relayerFee` is `gas * gasPrice * 1.01` (or `*1.10`), sourced purely from `EvmChain.estimateGas`, which never calls the destination's L1 data-fee oracle.
3. Compare against the fee a tesseract relayer requires to consider the same delivery profitable, computed via `get_current_gas_cost_in_usd` + `get_l2_data_cost`, which includes the L1 `getL1Fee` component.
4. When the L1 base fee is non-trivial relative to L2 execution gas price, the SDK-quoted `relayerFee` falls below the relayer's real profitability floor, and the dispatched request is never delivered by any permissionless relayer until manually topped up via `fundRequest`.

/// Returns the L2 data cost for a given transaction data in usd
pub async fn get_l2_data_cost(
	rlp_tx: AlloyBytes,
	chain: StateMachine,
	client: Arc<AlloyProvider>,
	// Unit wei cost in 27 decimals
	unit_wei_cost: U256,
) -> Result<Cost, anyhow::Error> {
	let mut data_cost = U256::zero();
	match chain {
		StateMachine::Evm(inner_evm) => match inner_evm {
			id if is_op_stack(id) => {
				let ovm_gas_price_oracle =
					OvmGasPriceOracleInstance::new(Address::from_slice(&OP_GAS_ORACLE), client);
				let data_cost_bytes = alloy_u256_to_primitive(
					ovm_gas_price_oracle.getL1Fee(rlp_tx).block(BlockId::latest()).call().await?,
				);
				data_cost = data_cost_bytes * unit_wei_cost
			},

			_ => {},
		},
		_ => Err(anyhow!("Unknown chain: {chain:?}"))?,
	}

	Ok(convert_27_decimals_to_18_decimals(data_cost)?.into())
}
