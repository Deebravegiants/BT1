### Title
Webhook `shop` and `topic` identity fields are unauthenticated (not covered by HMAC) allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the app's HMAC verification only to the raw request body, while the `shop` and `topic` values that are used downstream to route and attribute the webhook to a specific merchant are read directly from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and this is what `Utils::HmacValidator.validate` verifies against `Context.api_secret_key`: [1](#0-0) 

However, `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers that are **not** part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` and `request.topic` to construct the `WebhookMetadata` passed to the app's handler, which is the tenant-identifying data the host application uses to attribute and act on the webhook (e.g., select which shop's data/session to update): [3](#0-2) 

Because `api_secret_key` is a single shared secret across every shop that installs the app (not a per-shop secret), `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` is valid for *any* shop's payload as long as the body matches. The identity binding that should hold is:

`HMAC-verified header fields == fields the handler acts on`

but instead the actual binding is:

`HMAC-verified bytes (body only) != fields the handler acts on (shop, topic, headers)`

An attacker who controls their own shop installed on the victim's app receives legitimate Shopify webhook deliveries with a valid HMAC computed over the body using the same shared `api_secret_key`. Because the `shop-domain` (and `topic`) headers are excluded from the signed content, the attacker can replay that captured `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain or a different topic. `HmacValidator.validate` will still pass because it only re-computes the HMAC over `raw_body`, and the forged `shop`/`topic` values will be handed to the app's webhook handler as if genuinely originating from Shopify for that shop/topic.

### Impact Explanation
This crosses a tenant boundary: a webhook payload legitimately signed for shop A's data can be attributed to shop B by manipulating an unsigned header, or a webhook body intended for one topic (e.g. `orders/create`) can be dispatched to a handler registered for another topic. Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (e.g., looking up the merchant's session/access token to act on their behalf, updating billing/subscription state, or triggering data mutations), this enables cross-tenant data confusion/access — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to run their own shop with the target app installed (a standard, unprivileged, developer-obtainable position — same "unprivileged internet user" threat model used throughout this scan), capture one legitimate webhook delivery from Shopify to learn a valid `(body, hmac)` pair, and send a forged HTTP request directly to the app's public webhook endpoint with a swapped `shop-domain`/`topic` header. No possession of `api_secret_key`, access tokens, or any privileged credential is required.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., verify them against a per-shop record established during OAuth rather than trusting the header value verbatim). At minimum, document and enforce that `Request#shop`/`Request#topic` must never be treated as authenticated until independently validated against the app's own shop registry.

### Proof of Concept
1. App A is installed on attacker's shop `attacker.myshopify.com` and on victim's shop `victim.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app for `attacker.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(api_secret_key, B)` — valid because `Request#to_signable_string` only covers the body:
   `lib/shopify_api/webhooks/request.rb:36-38`.
3. Attacker (who controls their own inbound traffic/network position, or intercepts their own delivered webhook) resends the same `(B, hmac)` pair directly to the app's webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim.myshopify.com` (and/or the `x-shopify-topic` header).
4. `Utils::HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb:13-22` succeeds because it only checks `hmac` against `raw_body`.
5. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:190-199` dispatches the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-controlled data under the victim's tenant identity.
