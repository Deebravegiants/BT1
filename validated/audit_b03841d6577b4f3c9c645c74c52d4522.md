### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify," but the HMAC check only covers the raw request body, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. An unprivileged attacker who can obtain one legitimately-signed webhook body/HMAC pair (e.g., by installing the app on their own store and triggering an event) can replay that exact body+HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. The signature check passes, and the host app - following this gem's own documented pattern - attributes the payload to the attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the request "did indeed come from Shopify" (per the gem's docs) and then builds `WebhookMetadata` directly from the *unverified* `shop`, `topic`, `api_version`, and `webhook_id` headers: [3](#0-2) 

Those accessors read straight from attacker-suppliable HTTP headers with no cross-check against the signed body: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`, i.e. the tenant identity (`shop`) should be part of what's authenticated. Instead the binding actually enforced is only `hmac == HMAC(secret, body)`, while `shop` (the field the app acts on to select a tenant) is taken from an unauthenticated header. Before the attacker's request: `verified_bytes = body`, `acted_upon_field = shop_header` — these are already disjoint even for a legitimate webhook. An attacker exploits this disjunction by keeping `body`/`hmac` from a webhook Shopify signed for shop A, and substituting `shop_header = shop_B`. `HmacValidator.validate` still returns `true` because it never inspects `shop_header`.

### Impact Explanation
This breaks the tenant/identity binding for webhook processing: the host application, following the gem's documented `Registry.process` contract that claims to verify Shopify origin, receives a `WebhookMetadata` whose `shop` field is fully attacker-controlled despite HMAC validation succeeding. Any app logic that uses `data.shop` (as instructed by the gem's own webhook docs) to select which merchant's records to update, create, or delete will apply the attacker-known body content to a shop the attacker never controls — a cross-tenant data-integrity/confusion issue reachable by any user who can install the app on a shop they control (i.e., any unprivileged internet user with a Shopify Partner/dev account), no leaked credentials or access token required.

### Likelihood Explanation
Any unprivileged user can install a target app for free/dev testing on their own store, trigger a webhook whose body they can partially influence (e.g., a product/order field), capture the resulting `(raw_body, hmac-sha256)` pair over the wire (no TLS interception needed — it's their own traffic), and replay it to the app's public webhook endpoint with a substituted `X-Shopify-Shop-Domain`/`X-Shopify-Webhook-Id` header naming the victim shop. No secret material or privileged access is required.

### Recommendation
Bind the tenant/topic identity into the verified bytes, or otherwise cryptographically tie the headers to the signed payload before trusting them: e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (if compatible with Shopify's actual signing scheme), or require the host application to independently confirm that `shop` belongs to a session/webhook registration the app itself created before acting on it. At minimum, update `Registry.process`/docs so they don't claim the shop identity is verified when only the body is.

### Proof of Concept
1. Attacker creates/uses their own development shop `attacker.myshopify.com` and installs the target app; app registers webhook subscriptions via `ShopifyAPI::Webhooks::Registry.register`.
2. Attacker triggers an event whose payload content they control or predict (e.g., updates a product title to an arbitrary string), causing Shopify to POST a legitimately-signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`, body: `{"title":"..."}`
3. Attacker captures `raw_body` and the valid `hmac-sha256` value from this request (own traffic, no interception needed).
4. Attacker sends a new POST to the same app endpoint with the identical `raw_body`/`hmac-sha256`, but headers changed to `X-Shopify-Shop-Domain: victim.myshopify.com` and a benign/unused `X-Shopify-Webhook-Id`.
5. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` since it only re-computes HMAC over `raw_body`.
6. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, and any app logic keyed on `data.shop` acts on the victim tenant using attacker-supplied data — a cross-tenant confusion caused entirely by the gem's HMAC-vs-header binding gap.
