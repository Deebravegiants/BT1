### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's authenticity solely by checking the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from an HTTP header that is never included in the signed material. This breaks the identity binding `shop authenticated == shop used for tenant identification`, analogous to the reported nimiq-blockchain issue where an attacker-influenced field (`HistoricTransaction.block_number`) was used/acted on before being properly bound/checked against the object it claims to belong to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, entirely outside the HMAC-signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) and then immediately trusts `request.shop` to build `WebhookMetadata`, which is handed to the host application's handler as the tenant identifier: [3](#0-2) [4](#0-3) 

`HmacValidator.validate`/`validate_signature` compute and compare the signature strictly against `verifiable_query.to_signable_string`, i.e., the raw body only: [5](#0-4) 

By contrast, the OAuth callback path (`Auth::Oauth::AuthQuery#to_signable_string`) *does* include `shop` in the signed string, correctly binding the shop to the HMAC: [6](#0-5) 

This asymmetry shows the webhook path is the outlier: the equality that should hold — `shop covered by HMAC == shop delivered to the handler` — does not hold for webhooks. Since the body content alone determines the signature, any bytes captured with a valid signature (e.g., a webhook body/HMAC pair the attacker legitimately received, such as one delivered to their own trial/dev shop after installing the app) remain valid when replayed with a *different* `shop-domain` header value. `Registry.process` will accept it as authentic and hand the forged shop identity to the handler.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to select the tenant/session/store context for processing the webhook body, an attacker who can obtain one validly-signed webhook body (trivially available to any developer who installs the app on their own store, since Shopify signs the same static/predictable payload shapes, e.g., `shop/redact`, `customers/redact`) can replay it against the endpoint with an arbitrary victim shop domain in the header. The gem's own HMAC check passes because the header is not part of the signed content, resulting in cross-tenant data being attributed to, or acted upon under, a shop the attacker does not control. This matches the report's "High - cross-tenant access" impact bucket, since the identity binding between authenticated bytes and the tenant identifier is broken by this gem's own verification routine, not merely by host misuse.

### Likelihood Explanation
The webhook endpoint is intentionally exposed to the public internet, so no credentials, tokens, or `api_secret_key` knowledge are required — the attacker only needs a single legitimately-signed webhook payload (obtainable from their own store) and the ability to POST to the target app's public webhook route. This is a realistic, low-effort, unprivileged-internet-user path.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the HMAC-verified material, or require the host-application handler to cross-check `WebhookMetadata#shop` against an independently trusted source (e.g., an installed-shop registry) before trusting it, and document this requirement prominently. At minimum, `Webhooks::Request#to_signable_string` should not present `shop` as if it were verified when it is not covered by `HmacValidator`.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, triggering a legitimate webhook delivery to the app's public webhook endpoint with a valid `x-shopify-hmac-sha256` over some raw body `B`.
2. Attacker replays the exact same body `B` and HMAC header to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `request.to_signable_string` (`@raw_body`, unaffected by the header change) — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"`, an unauthenticated attacker-controlled value, even though the HMAC only ever certified body `B`.
