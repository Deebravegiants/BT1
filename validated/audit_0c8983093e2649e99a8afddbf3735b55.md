### Title
Missing L2 sequencer-uptime check on Chainlink oracle reads lets mispriced gas be extracted from `SimplexPaymaster` during sequencer downtime - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` is a permissionless ERC‑4337 paymaster deployed identically (same CREATE2 address) across every Hyperbridge mainnet chain, including several OP‑Stack/Orbit L2s (Arbitrum, Optimism, Base, Soneium — confirmed by the chain list in `tesseract/consensus/beefy/tests/mainnet_rotation.rs`, `CHAINS` constant, and the shared `HOST`/`HANDLER` CREATE2 addresses). Its pricing logic (`_tokenPrice` / `_getOraclePrice`) reads Chainlink `AggregatorV3Interface.latestRoundData()` directly and only checks answer positivity and staleness against `maxOracleAge`. It never checks an L2 sequencer-uptime feed, unlike Chainlink's documented requirement for L2 price consumers.

### Finding Description
`_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` (lines 662-676) is:

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
``` [1](#0-0) 

This is called from `_tokenPrice` (used by `getTokenPrice`, `estimateTokenCost`, and — critically — `_fetchDetails`, which is invoked on every `PaymasterERC20.postOp`/validation cycle for a `UserOperation`) and from `swapAndDeposit`. [2](#0-1) [3](#0-2) 

Only `maxOracleAge` bounds staleness (up to `MAX_ORACLE_AGE = 7 days`, and the comment even notes "Base/Ethereum stablecoins up to 24h"), meaning a fairly wide staleness window is tolerated by design on these chains. [4](#0-3) [5](#0-4) 

Chainlink's guidance for OP-Stack/Arbitrum L2s is that consumers must additionally check the `SequencerUptimeStatusFeed` because during a sequencer outage price feeds stop updating, and a `latestRoundData()` call made right after the sequencer resumes can still return a price answer whose `updatedAt` sits well inside `maxOracleAge` yet reflects pre-outage market conditions (or, on resumption, a burst of transactions racing to arbitrage the stale price the feed briefly serves). A grep across the repo confirms there is no `sequencerUptimeFeed`/`SequencerUptime`/`GRACE_PERIOD` handling anywhere in the codebase, so this check is entirely absent for `SimplexPaymaster` on every L2 deployment.

### Impact Explanation
Any unprivileged actor can submit an ERC-4337 `UserOperation` (via a normal bundler, or — during/at the edge of a sequencer outage — via forced inclusion on the L1 inbox once the sequencer resumes) whose gas is charged in an ERC-20 token via `SimplexPaymaster`. `_fetchDetails` prices that token against `nativeOracle`/`tokenOracle` using the exact function above, with no sequencer-liveness gate. If either oracle's last recorded answer is stale relative to true market price because of a sequencer outage (but still fresh enough to pass `maxOracleAge`), the computed `tokenPrice` will misprice gas: a user can pay far less ERC-20 than the fair USD value of the gas consumed, directly draining `SimplexPaymaster`'s treasury/deposit funds, or (less severely) overpay, harming users. Because the paymaster's ERC-20 surplus/EntryPoint deposit is real, protocol-owned value, this is a concrete fund-drain vector reachable from a single unprivileged transaction — satisfying the "concrete theft ... of funds" bar.

### Likelihood Explanation
L2 sequencer outages are rare but have occurred on every major OP-Stack/Arbitrum rollup Hyperbridge deploys to (Arbitrum, Optimism, Base, Soneium). The attack requires no special privilege — just submitting UserOperations that route through `SimplexPaymaster` during/immediately after such an outage — and the contract's own staleness bound is generous (up to 7 days configurable, with real chains configured up to 24h), widening the exploitable window well beyond typical outage durations. Given the paymaster is intentionally deployed identically across all these chains, the exposure is systemic rather than one-off.

### Recommendation
Add an L2 sequencer-uptime check (Chainlink's `SequencerUptimeStatusFeed`, e.g. via `latestRoundData()` on the standard `0x...FeedRegistry`/per-chain sequencer-uptime aggregator) to `_getOraclePrice`, reverting if the sequencer is currently down or if it has been up for less than the recommended grace period (typically 1 hour) since the last outage, mirroring the pattern Chainlink publishes for `AggregatorV3Interface` consumers on Arbitrum/Optimism/Base. This check should gate both `_tokenPrice` (paymaster pricing path) and `swapAndDeposit`'s oracle-derived slippage bound.

### Proof of Concept
1. `SimplexPaymaster` is deployed with identical bytecode/address on Arbitrum, Optimism, Base, and Soneium (see `HOST`/`HANDLER` addresses shared across the 9 mainnet chains in `tesseract/consensus/beefy/tests/mainnet_rotation.rs`).
2. On one such L2, the sequencer experiences downtime; Chainlink's `tokenOracle`/`nativeOracle` feeds on that chain stop updating (no new rounds pushed) while `block.timestamp` still advances only up to the point where the sequencer resumes producing blocks.
3. Once the sequencer resumes, transactions land using the last pushed Chainlink round, whose `updatedAt` is still within `maxOracleAge` (up to 24h per the configured governance param) but whose `answer` no longer reflects current market price (e.g., a native-asset price crash/spike during the outage that the feed missed).
4. An attacker submits a `UserOperation` with `paymasterData` mode `0x00`/`0x02` naming a token whose true USD value has diverged from the stale oracle price. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the stale-but-"fresh-enough" price and returns a `tokenPrice` that undercharges the attacker relative to the real gas cost in USD.
5. `PaymasterERC20._prefund`/`_postOp` charges the attacker the mispriced (too-low) token amount for the wei of gas actually consumed, draining the difference from `SimplexPaymaster`'s accumulated surplus/EntryPoint deposit — repeatable every block until the price gap closes or governance intervenes via `UpdateParams`/`DeactivateToken`.
