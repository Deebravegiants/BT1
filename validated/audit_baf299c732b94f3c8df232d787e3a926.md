### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant shop spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook only by checking that `Utils::HmacValidator.validate(request)` passes over the raw body, then hands the handler a `WebhookMetadata` built from `request.shop`, which is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header. Since the HMAC signature never covers the shop header, the "shop" identity delivered to the app's handler is unauthenticated relative to the signature that is supposed to prove the payload's legitimacy.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`, and `hmac` is parsed from the `hmac-sha256` header — neither of which include the shop domain: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (sourced from the `shop-domain` header) to build the metadata passed to the app-defined handler: [3](#0-2) 

Because the `api_secret_key` (client secret) used to compute the HMAC is the same for every shop that has installed a given app, any merchant who legitimately installs the app can obtain a *valid* `(raw_body, hmac)` pair from their own genuine webhook deliveries. Nothing in `HmacValidator.validate` or `Webhooks::Request` binds that valid `hmac` to the specific `shop-domain` header value. An attacker who controls a legitimate shop can therefore take a real webhook delivery for their own shop and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain: the signature check in `HmacValidator.validate_signature` (`path="lib/shopify_api/utils/hmac_validator.rb" start="27" end="31"`) still succeeds because it only checks the (unmodified) `raw_body`/`hmac` pair, while `request.shop` now equals the victim's domain.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the gem implicitly assumes — `shop-domain header == the shop the HMAC-signed body actually originated from` — does not hold, because the HMAC scope is `{raw_body}` while the field acted upon by the handler is `{shop header}`.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as delivered by `Registry.process`) to select which tenant's data/session/store to update, log, or act on is exposed to cross-tenant confusion: an unprivileged holder of one shop's genuine app installation can cause the handler to execute with an attacker-chosen `shop` value while `HmacValidator.validate` still reports success. This satisfies the "cross-tenant access" criterion, since it lets one tenant force the app to process (attacker-supplied) webhook data attributed to a different tenant, without any credential belonging to that other tenant.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate app-installing merchant (unprivileged internet user relative to other tenants) who can receive genuine webhooks for their own shop and replay the HTTP request to the app's public webhook endpoint with one header value changed. No `api_secret_key`, access token, or privileged access to Shopify internals is needed — only observation of one's own valid webhook traffic, which is trivially available to any shop owner using the app.

### Recommendation
Bind the shop identity into the HMAC-signed material (or otherwise cryptographically verify it) before trusting `request.shop`, e.g. by including the `shop-domain` header in `to_signable_string` if Shopify's signature scheme supports it, or by independently confirming (via a signed/mac'd channel, not a bare header) that the `hmac-sha256` value was actually generated for the shop asserted in `shop-domain`. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification, and provide a way for consuming apps to reject requests where the header-asserted shop cannot be corroborated.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, headers including `shopify-hmac-sha256: H` (valid for `B`) and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but replacing `shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` (`B`) and compares to `H` — this still matches, so validation passes.
4. The handler executes with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
