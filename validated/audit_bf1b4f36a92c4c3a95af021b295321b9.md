### Title
Unauthenticated Origin Impersonation in Cross-Chain Calldata Execution - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an attacker-supplied ABI `Message` (from an ERC20 token bridge message body) and, when the optional `data` field is populated, decodes it into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }`. If `signature` is `None`, the dispatch origin is derived directly from `message.from` — a field fully controlled by whoever calls `send`/`transfer` on the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract — without any cryptographic proof that the caller controls the corresponding substrate account.

### Finding Description
In `on_accept`, once the token leg of the message is processed, optional calldata execution proceeds as: [1](#0-0) 

If a `signature` is present, it is verified against `(nonce, runtime_call)` using the beneficiary's key material — this path is sound. But if no signature is supplied, the code falls back to deriving the origin purely from `message.from`: [2](#0-1) 

`message.from` is part of the ABI-encoded `Message` struct (`bytes from; bytes to; uint256 amount; bytes data;`) documented as "original sender (for timeout refunds)": [3](#0-2) 

Unlike the ISMP `PostRequest.from`/`.source` fields — which are authenticated by the consensus/state-proof machinery that verifies the sending contract's address — `Message.from` is an arbitrary byte string chosen by whoever encodes the ABI payload passed to the bridge contract's send function. Nothing on the EVM side or in `on_accept` binds `Message.from` to `msg.sender`, nor is there a decode-time equality check between `message.from` and `message.to`/`beneficiary`. The decoded `runtime_call: Vec<u8>` is then unconditionally dispatched: [4](#0-3) 

The only gate is `BaseCallFilter`, which restricts *which pallets* can be called, not *whose account* is used as origin. As a result, an attacker who can call the source-chain bridge contract (an unprivileged, permissionless action — anyone can bridge tokens) can:
1. Set `message.to` to an account they control (to receive minted tokens / satisfy `beneficiary`).
2. Set `message.from` to the raw bytes of a *victim* account (e.g., a treasury, sudo-adjacent, or any account holding assets) they do not control.
3. Provide `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary allowed call> }`.

The pallet decodes and dispatches `runtime_call` with `RawOrigin::Signed(<victim account derived from from>)`, executing an arbitrary (filter-permitted) runtime call as if it originated from the victim, without any proof of ownership of that account. This is analogous to the CVE's root cause — an externally-reachable component deserializes and executes attacker-controlled data (`ReceiveVarData<T>`/`BinaryFormatter` in the advisory vs. SCALE-decoded `RuntimeCall` here) without the necessary type/identity restrictions on that untrusted input, letting the caller dictate execution as an arbitrary principal.

### Impact Explanation
Any runtime call not excluded by `BaseCallFilter` can be dispatched under an arbitrary victim's identity — e.g., `Balances::transfer_all` draining the impersonated account, approving allowances, staking/nomination changes, or invoking other bridge/pallet extrinsics that trust `frame_system::ensure_signed` as proof of authorization. This is theft of funds / unauthorized privileged action reachable from a single unprivileged token-bridge send on the EVM side, satisfying the "unauthorized app action" / "concrete theft of funds" bar.

### Likelihood Explanation
High: the path is reachable by any unprivileged user calling the standard `send`/`transfer` function on the deployed `HyperFungibleToken`/`WrappedHyperFungibleToken` contract with attacker-chosen ABI-encoded `data`; no relayer collusion, governance, or special privilege is needed — only that a message with the crafted body gets relayed and processed through normal ISMP delivery, which is the intended, permissionless flow for this pallet.

### Recommendation
Never derive a dispatch origin from unauthenticated, attacker-supplied bytes. Require a `signature` for every calldata-execution path (reject `None` when `runtime_call` is non-empty and origin would otherwise be attacker-chosen), or restrict the unsigned path so `origin` can only ever be the same account that will also serve as `beneficiary`/`to` (i.e., derive origin exclusively from parties whose funds the sender is already moving, never from a caller-supplied `from`). At minimum, add an explicit check binding `message.from` to `message.to`/`beneficiary` before allowing unsigned dispatch, or drop the unsigned fallback entirely and mandate a valid `MultiSignature` whenever `runtime_call` is present.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send(...)` (or the equivalent public transfer entrypoint) on the EVM side, ABI-encoding a `Message` where:
   - `to` = attacker's own 32-byte substrate account (to satisfy `beneficiary`).
   - `from` = the 20/32-byte representation of a victim account with funds on the destination substrate chain.
   - `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded pallet_balances::Call::transfer_all { dest: attacker, keep_alive: false }> }` (or any call allowed by `BaseCallFilter`).
2. The message is relayed via normal ISMP delivery and reaches `on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs`.
3. Because `substrate_data.signature` is `None`, the code enters the `else` branch, converting `message.from` (the victim's bytes) into the dispatch `origin` with no ownership proof.
4. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes the victim's funds transfer, or any other allowed call, without the victim's consent. [5](#0-4)
