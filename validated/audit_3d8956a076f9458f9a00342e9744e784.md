The premise doesn't hold up under inspection of the actual code paths. The cost model's [1](#0-0)  reads the declared signature count solely from `instruction.data.first()` — but the actual precompile verifiers (`secp256k1::verify`, `ed25519::verify`, `secp256r1::verify`) derive their loop iteration count from that *exact same* first byte:

- secp256k1: `let count = data[0] as usize;` then `for i in 0..count` [2](#0-1) 
- ed25519: `let num_signatures = data[0] as usize;` then `for i in 0..num_signatures` [3](#0-2) 
- secp256r1: `let num_signatures = data[0] as usize;` (capped at 8) [4](#0-3) 

Since both the cost-model's charged count and the verifier's actual loop bound come from the identical byte, there is no divergence to exploit. Additionally, all three verifiers explicitly compute `expected_data_size` from the declared count and bail out early with `PrecompileError::InvalidInstructionDataSize` if the actual data buffer is shorter than required — e.g. secp256k1's `if data.len() < expected_data_size { return Err(...) }` [5](#0-4) . So a "declared count higher than actual payload" scenario causes the verifier to reject the instruction immediately (cheap failure), not perform extra expensive crypto work — the real work performed is always bounded above by the declared count, never below it decoupled in the attacker's favor. The invariant "declared signature cost upper-bounds real verification work" therefore holds by construction, since both quantities are driven by the same source byte and malformed/truncated data can only cause early termination (less work), never additional iterations.
