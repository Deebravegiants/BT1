### Title
Webhook shop-domain (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC signature that is verified only covers the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values that identify *which tenant* the webhook belongs to are read straight from unauthenticated HTTP headers and are never included in the signed bytes. An attacker who can obtain any single genuinely-signed webhook body (e.g., by installing the app on a shop they control) can replay that exact body with a forged `x-shopify-shop-domain` header pointing at a victim shop, and the gem will accept it as valid and hand it to the host application's handler labeled as belonging to the victim.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are not part of the signed data: [2](#0-1) 

`Registry.process` verifies only this body-based HMAC and then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and secure-compares it to the received HMAC — it never binds the `shop` header into the signature: [4](#0-3) 

The broken identity binding is:
`HMAC-verified bytes (raw_body only)` ≠ `shop identity acted upon (request.shop from an unauthenticated header)`

Because the signature is computed only over the body, any two webhooks with identical bodies (e.g., the trivial `"{}"` body used for `orders/create` test/mandatory topics, or any webhook whose JSON payload an attacker can reproduce) will have byte-identical, valid HMACs regardless of which shop header accompanies them. An attacker who legitimately installs the app on a shop they control receives real Shopify-signed webhook requests to the app's public webhook endpoint. They can capture one such request and replay it with the `x-shopify-shop-domain` header changed to a victim's `*.myshopify.com` domain (and, if desired, other headers like `topic`/`webhook_id` since neither is bound to the signature either). `Utils::HmacValidator.validate` still succeeds because it only checks the raw body, so `Registry.process` calls the host app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is entirely attacker-controlled despite "signature verification" having passed.

This directly contradicts the gem's own documented guarantee: "This will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md`), while in fact only the payload bytes — not the tenant attribution — are verified.

### Impact Explanation
Host applications built on this gem reasonably rely on `Registry.process` to authenticate both the webhook's origin and its shop attribution, since that is the documented contract. Because `shop` is not covered by the HMAC, an attacker who owns any single install of the app can forge webhook deliveries that the gem will authenticate as coming from an arbitrary victim shop domain. Downstream, apps typically use `data.shop` to look up the victim's stored session/access token and process billing, inventory, or order-processing side effects "on behalf of" that shop — i.e., cross-tenant confusion/injection under the identity of another merchant, without ever needing that merchant's credentials. This matches the "cross-tenant access" high/critical impact category, since the tenant boundary (`shop`) that the API contract is supposed to authenticate is not actually bound by the cryptographic check.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on any shop the attacker controls (a normal, unprivileged action for any Shopify merchant/developer), (2) capturing one legitimate webhook delivery to the app's public endpoint, and (3) replaying it with a modified `shop-domain` header (and optionally topic/webhook-id headers, since none of these are HMAC-bound). No access to `api_secret_key`, access tokens, or any privileged account of the victim is required.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise independently verify `request.shop` against a value derived from data that is authenticated (for example, cross-check the `shop-domain` header against the shop id resolved from a per-shop webhook secret or session lookup) before trusting it. At minimum, update `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` so the signable string incorporates the shop domain, topic, and webhook id headers (mirroring what is actually verified), and clearly document that `shop`/`topic`/`webhook_id` are unauthenticated unless the host application performs additional verification (e.g. matching against a known/installed shop list) before acting on them.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = "{}" # attacker captures/reuses a real webhook body from their own shop install

hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
signature = Base64.encode64(hmac)

# Attacker-forged headers: shop-domain swapped to a victim shop
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => signature,          # unchanged, still valid because body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# Passes cleanly: only the body's HMAC is checked
ShopifyAPI::Webhooks::Registry.process(request)
# => Handler invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though "victim-shop" never sent this webhook.
```
