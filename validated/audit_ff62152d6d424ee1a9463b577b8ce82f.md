### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an inbound HTTP request as authentic Shopify traffic once `Utils::HmacValidator.validate(request)` succeeds. That validator, however, only recomputes and compares the HMAC over `request.to_signable_string`, which is defined as the raw request body only. The `shop` (tenant identity), `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers that are never part of the signed material, yet they are forwarded unchanged into `WebhookMetadata` and handed to the app's `WebhookHandler#handle` as the trusted tenant/topic identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers, independent of the signed body: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (i.e., the body) and never incorporates the headers: [3](#0-2) 

`Registry.process` accepts the request purely on that body-only HMAC check, then immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` as authenticated fields and passes them to the app-supplied handler: [4](#0-3) 

The handler contract (`WebhookMetadata`) documents `shop` as "The shop domain of the webhook" with no caveat that it is unauthenticated, and the official usage docs instruct apps to key persistence/business logic directly off `data.shop`: [5](#0-4) [6](#0-5) 

**Identity binding that should hold but does not:**
`shop_header_verified_by_HMAC == shop_used_for_tenant_routing`

In reality: `shop_used_for_tenant_routing = shop_header_value` (unauthenticated), while `HMAC` only proves `raw_body` was produced with the app's `api_secret_key` — it says nothing about which header set accompanied that body.

**Exploitability without any privileged credential:** The `api_secret_key` used to sign webhooks is the app's single shared secret, identical for every shop that has installed the app — it is not shop-specific. A malicious/unprivileged actor who installs the target app on their own store (a routine, permissionless action for any public app) receives genuine Shopify-signed webhooks containing a valid `(raw_body, hmac)` pair for topics with body payloads that carry no shop identifier of their own (many topics carry ids/fields but not necessarily the domain in the body). The attacker can then replay that exact `raw_body` + `hmac` to the app's registered webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) headers to point at a victim shop. `HmacValidator.validate` still succeeds because it only ever checked the body, and `Registry.process` will dispatch to the handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant boundary the app relies on to route webhook data: `Registry.process` → `WebhookMetadata.shop` is the sole tenant identifier passed to host applications for persistence/business logic (per the gem's own documented usage pattern: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). Forging this value allows a low-privilege actor (any user who can install/trial the app) to inject attacker-controlled webhook bodies that host apps will process as belonging to an arbitrary victim shop — i.e., cross-tenant data injection/confusion, satisfying the "Critical - cross-tenant access" bar, since the trust boundary between tenants is defined entirely by this unauthenticated header value.

### Likelihood Explanation
Likelihood is meaningfully high for any adversary who is a legitimate app installer (no special access needed — no `api_secret_key` leak, no TLS interception, no social engineering): the attacker leverages their own genuine webhook deliveries and only forges HTTP headers on replay, which are fully attacker-controlled on any raw HTTP request they construct to the app's public webhook endpoint.

### Recommendation
Bind the header-derived identity to the signed payload, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the request before trusting them:
- Compute the HMAC over a canonical string that includes `shop`, `topic`, `api_version`, and `webhook_id` in addition to the raw body (this requires coordinated change on the Shopify webhook-signing side, so as a library-side mitigation at minimum), or
- Require callers to independently confirm that `request.shop` matches a shop for which the app currently holds an active session/installation *and* document loudly that `WebhookMetadata.shop`/`topic` are unauthenticated header values that must not be trusted for authorization decisions without additional verification, or
- Where feasible, verify webhook authenticity using a per-shop secret/session context rather than a single app-wide shared secret, so that a valid HMAC for one merchant's webhook cannot be replayed as if it belonged to another merchant.

### Proof of Concept
1. Attacker registers/installs the target app on `attacker-shop.myshopify.com` (permissionless, standard OAuth install).
2. Shopify delivers a genuine webhook to the app's endpoint for a topic whose body has no shop-identifying content, e.g. `{}` or a generic payload, together with headers:
   ```
   x-shopify-topic: some/topic
   x-shopify-hmac-sha256: <valid HMAC of body, computed with the app's shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   ```
3. Attacker captures this exact `(raw_body, x-shopify-hmac-sha256)` pair.
4. Attacker sends a forged HTTP request directly to the app's webhook route with the same body and HMAC header, but with:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the unchanged raw body) and it matches — validation passes.
6. `Registry.process` builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and dispatches it to the app's handler, which (per the gem's own documented pattern) uses `data.shop` to route/store the (attacker-controlled) payload against the victim tenant. module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
