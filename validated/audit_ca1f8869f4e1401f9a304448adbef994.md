### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body only and then passes the header-derived `shop` value straight into the handler as trusted data, breaking the binding: `hmac(secret, body) == received_hmac` should imply `shop == authenticated_shop`, but it does not.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as `@raw_body` only [1](#0-0) , while `shop`, `topic`, `api_version` and `webhook_id` are all read straight from HTTP headers without any cryptographic binding to the signature [2](#0-1) .

`Registry.process` validates only that `Utils::HmacValidator.validate(request)` succeeds — i.e. that the HMAC over the raw body matches — and then immediately trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) .

The HMAC secret (`Context.api_secret_key`) is the single app-level `client_secret`, shared across every shop that has installed the app — it is **not** shop-specific [4](#0-3) . Because the signable string is body-only, any two webhook deliveries with identical bodies (e.g., an app installed on two different shops that both create an order with the same payload shape, or any deterministic/guessable payload) produce identical valid HMACs regardless of which shop they are "from" — since neither `shop` nor `topic` is part of the signed data.

This breaks the intended identity binding: `shop` (used by the handler to key application logic, session lookup, or data attribution) ≠ `shop` (the value that was actually authenticated by the HMAC, which is none — the body is all that's authenticated). An unprivileged internet user who has access to their own shop's valid webhook deliveries (i.e., any merchant who installs the app in scope — a completely unprivileged, self-service action) can capture a body+HMAC pair from their own shop, then replay that exact HTTP request while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) header for a victim shop domain. `HmacValidator.validate_signature` will still pass because it never looks at the shop header [5](#0-4) , and `Registry.process` will hand the forged `shop` value to the host application's webhook handler as if it were authentic [6](#0-5) .

### Impact Explanation
Host applications built on this gem commonly use the `shop` field from `WebhookMetadata` to look up the tenant's session/access token, update per-shop billing/inventory state, or trigger tenant-scoped side effects, trusting that it was cryptographically verified by the HMAC check that just preceded it in `Registry.process`. Because `shop` is not bound to the signature, a malicious merchant (an unprivileged actor with respect to any other shop) can inject webhook events that the host app will process under a victim shop's identity — this is a cross-tenant identity confusion at the gem's trust boundary, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs a body+HMAC pair that the host app's handler will meaningfully act on for a *different* shop (bodies for order/customer webhooks usually reference shop-specific IDs, though topic-only or empty-body webhooks, or webhooks whose body doesn't include shop-identifying fields, are trivially exploitable). Still, no privileged credentials, TLS interception, or social engineering are required — only normal, unprivileged use of the app (installing it and receiving one's own legitimate webhook) plus a forged HTTP request to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and any other header-derived fields the handler relies on in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g., by validating against Shopify's own webhook signature scheme which Shopify computes over the raw body server-side — but additionally re-deriving/cross-checking `shop` against a trusted, independently verified source such as an active session/install record rather than trusting the header value outright). At minimum, document that `request.shop` is unauthenticated and must not be used for tenant-sensitive dispatch without additional verification (e.g., confirming the shop has an active installation/session before trusting webhook content for it).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (fully unprivileged, self-service).
2. Attacker triggers/receives a legitimate webhook delivery, capturing `raw_body` and the valid `x-shopify-hmac-sha256` header Shopify computed with the app's single `client_secret`.
3. Attacker replays the exact same HTTP request to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `x-shopify-topic`/`x-shopify-webhook-id`).
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only and finds it matches (secret is shared across shops) — verification succeeds.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and invokes the host app's handler as though the event genuinely originated from `victim-shop.myshopify.com`.
