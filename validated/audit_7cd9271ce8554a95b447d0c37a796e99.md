Based on my investigation, I found a valid analog: the webhook `shop` identity field is not covered by the HMAC signature, exactly matching the report's bug class of "a field acted on but not covered by the HMAC."

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook relabeling - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes the HMAC signature over the raw body only, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed material. Any consumer following the documented `Registry.process` flow trusts `request.shop`/`data.shop` as an authenticated tenant identifier, even though it is not bound to the HMAC that `Registry.process` validates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor instead reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed content: [2](#0-1) .

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (i.e., only the body) and compares it against the `hmac` header value using `OpenSSL.secure_compare`: [3](#0-2) . After this single check passes, `Registry.process` immediately forwards `request.shop` unmodified into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identity: [4](#0-3) . The `WebhookMetadata` struct itself has no invariant tying `shop` to the signed payload: [5](#0-4) .

The identity binding that should hold is: `hmac == HMAC(secret, raw_body || shop)`, but the gem only enforces `hmac == HMAC(secret, raw_body)`. Because `shop` is excluded from the signable string, an attacker who legitimately controls one shop (Shop A) and receives a real, correctly-HMAC'd webhook for Shop A can resend that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (Shop B). `Utils::HmacValidator.validate` still succeeds, since it never looks at the shop header, and the app's handler receives `data.shop == "shop-b.myshopify.com"` bound to attacker-controlled body content, achieving cross-tenant confusion in any app logic keyed off `data.shop` (e.g., looking up the session/access token for Shop B and processing attacker data as if it originated from Shop B).

### Impact Explanation
This breaks the tenant/shop identity boundary the HMAC is supposed to guarantee. Any downstream app logic that uses `data.shop` to select which merchant's session, records, or access token to act on (the exact pattern shown in the gem's own documentation: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into applying attacker-controlled webhook content to a different, victim tenant — a cross-tenant access/data-integrity issue, consistent with the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs to operate their own legitimate Shopify shop installed on the target app (a normal, unprivileged capability), capture one real webhook delivery (body + valid `hmac-sha256` header) for any topic/shape they want, and replay it to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or the target shop's credentials is required, since the signature check never considers the shop header.

### Recommendation
Include the shop domain (and ideally other identity-relevant headers) in the signed/verified material, or independently verify that `request.shop` corresponds to a shop that installed the app for the given webhook topic/subscription id before trusting it. At minimum, `to_signable_string` (or the HMAC validation path) should bind the `shop-domain` header value to the HMAC check so that swapping it invalidates the signature, matching Shopify's documented webhook verification guidance of authenticating the whole request context, not just the body.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and configures/triggers a webhook (e.g., `orders/create`) so Shopify delivers a legitimately HMAC-signed request:
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body with app's api_secret_key>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - body: `{"id": 1, ...attacker-controlled order data...}`
2. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [6](#0-5)  — validation succeeds because the body/HMAC pair is untouched.
4. The registered handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and the attacker's body, as shown in the test fixture pattern for `request.shop`/`data.shop` [7](#0-6) , causing the app to process attacker data under the victim's tenant identity.
