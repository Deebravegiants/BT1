### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) values that the host application uses to attribute the webhook to a specific merchant/tenant are taken from unauthenticated HTTP headers that are never included in the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from HTTP headers without being part of the HMAC-signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates `hmac` against `to_signable_string`, i.e. the raw body only) before dispatching the handler with `request.shop` taken verbatim from the header: [4](#0-3) 

`Utils::HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the header-supplied HMAC — it never binds `shop-domain` to the signature: [5](#0-4) 

This breaks the identity binding: `HMAC(raw_body, api_secret_key) == received_hmac` is verified, but the tenant identifier the app acts on, `shop == header["shop-domain"]`, is never part of that equality. Because every shop using the same Shopify app shares the same `api_secret_key`, a merchant who has legitimately installed the app can trigger a real webhook on their own store (obtaining a raw body + a correctly computed HMAC signed with the shared secret), then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value for a different (victim) shop. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards `shop: request.shop` (the attacker-controlled header) to the handler, per the documented contract that `shop` is `"The shop domain of the webhook"`: [6](#0-5) 

Any host application that follows this gem's documented `data.shop` contract for tenant attribution (e.g. persisting/updating orders, redact requests, or metafield jobs keyed by `data.shop`) can be tricked into ingesting attacker-supplied webhook data under another merchant's identity — a cross-tenant confusion that mirrors the "field acted on but not covered by HMAC" identity-binding break called out for this scan.

### Impact Explanation
This is a cross-tenant data-integrity issue: an authenticated attacker (any merchant who has installed the app) can spoof webhook attribution for other shops that share the same app credentials, causing the host application to associate attacker-controlled webhook data/business events with an arbitrary victim shop identifier. This matches the "Critical - cross-tenant access" impact category since the boundary broken is the per-tenant identity binding for webhook processing.

### Likelihood Explanation
Likelihood is significant for real-world apps: the attacker only needs to be a legitimate merchant of the same app (no privileged secret or token needed), be able to trigger a webhook topic they're allowed to receive, capture the raw body/HMAC pair, and replay it with a modified `shop-domain` header to the app's public webhook endpoint. No cryptographic secret needs to be known or broken — only the (unauthenticated) header is manipulated.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`) values in the HMAC-signed material, or independently verify the `shop-domain` header against a shop known to be associated with the app/session before acting on it. At minimum, the gem should document explicitly that the `shop` field on `WebhookMetadata` is unauthenticated and must be corroborated against server-side state (e.g. a stored session for that shop with an active webhook subscription ID) before being trusted for tenant-scoped operations.

### Proof of Concept
1. App is installed on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing the same `api_secret_key`.
2. Attacker triggers a real webhook (e.g. `orders/create`) on `attacker-shop.myshopify.com`, capturing the raw POST body and the resulting `x-shopify-hmac-sha256` header — both validly computed by Shopify with the shared secret.
3. Attacker replays this exact `raw_body` + `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body)` — this passes because the body/HMAC pair is genuinely valid. [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker's data, ...)`, and any host logic keyed on `data.shop` processes attacker-controlled content under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
