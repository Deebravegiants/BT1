### Title
Case-sensitive `compareAddresses` for Bitcoin-family chains lets a re-cased bech32 destination bypass `DestinationAddressMatchesTokenAddressError`, sending funds to the token's own custody address - ([File: packages/intents-sdk/src/lib/compareAddresses.ts])

### Summary
`PoaBridge.validateWithdrawal` guards against withdrawals to the token's own `origin_chain_address` by calling `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)`. For `Chains.Bitcoin`/`BitcoinCash`/`Litecoin`/`Dogecoin`/`Zcash`/`Dash`, `compareAddresses` falls through to a raw `a === b` string comparison instead of canonical decoding, so a bech32 address that is byte-identical but differently cased (e.g. fully upper-cased) is treated as a different address.

### Finding Description
The broken equality: `origin_chain_address` (token custody address for the asset, lowercase as returned by the PoA supported-tokens API) vs `destinationAddress` supplied by the caller — both should be considered equal when they decode to the same witness program, but `compareAddresses` returns `false` when casing differs.

Code path:
1. `PoaBridge.validateWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:181-219) first checks `validateAddress(args.destinationAddress, assetInfo.blockchain)`.
2. For Bitcoin, `validateAddress` delegates to `validateBtcAddress` → `validateBtcBech32Address` (packages/intents-sdk/src/lib/validateAddress.ts:129-202), which decodes via `bech32.decode`/`bech32m.decode`. The bech32 spec allows an address to be entirely lowercase or entirely uppercase and still decode to the same bytes; the code only does `decoded.prefix.toLowerCase() !== "bc"` for the HRP check and never rejects an all-uppercase input. This is confirmed directly by the existing test suite, which asserts `validateAddress("BC1Q973XRRGJE6ETKKN9Q9AZZSGPXEDDATS8CKVP5S", Chains.Bitcoin)` returns `true` (packages/intents-sdk/src/lib/validateAddress.spec.ts:85-86, 94-96).
3. Having passed format validation, `validateWithdrawal` then calls `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)` (poa-bridge.ts:207-214). In `compareAddresses` (packages/intents-sdk/src/lib/compareAddresses.ts:48-60), `Chains.Bitcoin` (along with `BitcoinCash`, `Zcash`, `Dogecoin`, `Litecoin`, `Dash`, `Near`, `Solana`, `Fogo`, `XRPL`, `Cardano`, `Aleo`) falls into the `return a === b;` branch — a raw case-sensitive string comparison, unlike the EVM branch (`getAddress` checksum normalization), the Aptos/Sui/Starknet branch (`compareHexAddress`), TON (`compareTonAddress`), Tron (`compareTronAddress`), or Stellar (`toUpperCase()` normalization).
4. If `tokenInfo.origin_chain_address` is lowercase (as returned by the API) and the attacker submits the exact same address fully upper-cased as `destinationAddress`, `validateAddress` returns `true` (format valid), but `compareAddresses` returns `false` (strings differ), so `DestinationAddressMatchesTokenAddressError` is never thrown, and the withdrawal proceeds to what is effectively the token's own custody address.

Existing guards do not catch this: `validateAddress` only checks format, not canonical identity against another address; `compareAddresses` is the only identity check and it is broken specifically for the bech32-based chains listed above.

### Impact Explanation
An attacker (an ordinary user issuing their own withdrawal, or a counterparty whose `destinationAddress` an integrator forwards unmodified) can cause funds to be routed to the token's own bridge/custody address instead of being rejected. This matches the Critical category: "funds delivered to a wrong address/chain/contract with no recovery" — once funds land at the custody address there is no SDK-level path to recover them. The bug is repeatable for every Bitcoin-family withdrawal where the attacker controls or can present a re-cased form of the token's origin address as the destination.

### Likelihood Explanation
Preconditions: the PoA bridge's supported-tokens API must return `origin_chain_address` in a fixed case (the finding assumes lowercase, consistent with typical bech32 API conventions) for the relevant asset/chain; the destination chain must be one using the `a === b` branch (Bitcoin, BitcoinCash, Litecoin, Dogecoin, Zcash, Dash — note only the bech32 sub-formats of these are affected by same-bytes-different-case; base58 addresses are case-sensitive by design and not affected). The attacker only needs to re-case a public, known address (the token's own custody address, which is discoverable via the same supported-tokens API) and submit it as `destinationAddress` in a withdrawal call — this costs nothing beyond calling the public SDK method with attacker-chosen input, and is straightforward and repeatable.

### Recommendation
Fix `compareAddresses` for the affected chains to perform canonical bech32/base58 decoding and byte-level comparison, mirroring the pattern already used for EVM (`getAddress`), Tron, and TON:
- For Bitcoin/Litecoin/BitcoinCash (bech32 branches) and Dogecoin/Zcash/Dash where applicable, decode both addresses using the same decoding logic as `validateAddress` (bech32/bech32m/base58, case-normalized to lowercase before `bech32.decode`), extract the witness program (or hash payload for base58), and compare the resulting bytes — falling back to `false` on decode failure, consistent with the function's documented contract ("Returns false on malformed input").
- At minimum, normalize casing (`a.toLowerCase() === b.toLowerCase()`) for bech32-capable chains before comparing, though full canonical decoding is preferred since it also handles cross-encoding equivalence issues.

    const lower = "bc1q973xrrgje6etkkn9q9azzsgpxeddats8ckvp5s"; // e.g. tokenInfo.origin_chain_address

    // Both are valid per validateAddress (see validateAddress.spec.ts:85-86)

  });
