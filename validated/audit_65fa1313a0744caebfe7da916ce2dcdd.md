I found a confirmed cross-workflow response cache confusion bug that matches the accepted "cross-user response confusion" category.

### Title
HTTP Action response cache key omits `WorkflowID`, allowing cross-workflow response leakage - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP capability response cache is documented and intended to be workflow-isolated ("Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" per [1](#0-0) ), but the actual cache key generated by `OutboundHTTPRequest.Hash()` explicitly ignores `WorkflowID` while including `WorkflowOwner`. This is proven by the handler's own test suite: [2](#0-1)  asserts "having different workflowID results in same Hash", directly contradicting the README's isolation guarantee.

### Finding Description
`responseCache` keys stored HTTP responses solely by `req.Hash()` [3](#0-2) , and both `Fetch` and `Set` use this same hash as the map key [4](#0-3) . Since two workflows belonging to the *same* `WorkflowOwner` but different `WorkflowID` (e.g., different named workflows, different versions/tags of the same workflow, or workflows created via different deployments) will collide on the identical cache key if they issue an outbound HTTP action with the same method/URL/headers/body/owner, one workflow's HTTP-action response is served directly to a different workflow.

The comment atop `responseCache` claims the key is "a hash of the request (method, URL, headers, body, workflowOwner)" [5](#0-4) , confirming `WorkflowID` is deliberately excluded, while the package README promises workflow-ID-level isolation [6](#0-5) . This is a genuine cross-workflow response confusion: an unprivileged workflow author (an "unprivileged client" in the gateway's threat model, since any registered workflow can request the HTTP capability) can receive cached HTTP response bodies fetched for a request initiated by a *different* workflow owned by the same address, as long as method/URL/headers/body match.

The outbound request flow that populates this cache is entered directly from `HandleNodeMessage`/`makeOutgoingRequest`, which is invoked whenever a workflow DON node sends a JSON-RPC HTTP action message via `HandleJSONRPCUserMessage`/`makeOutgoingRequest` [7](#0-6) , so the gateway request path is directly reachable by any workflow node without additional privilege checks beyond the standard node auth.

### Impact Explanation
This breaks the stated workflow isolation guarantee for HTTP-action responses. If two different workflows (same owner) make a matching outbound HTTP request (e.g., fetching an API endpoint with an owner-scoped token in headers/body that happens to also match), one workflow can read the cached response destined for the other. Because HTTP action responses can carry API responses containing sensitive or workflow-specific data (pricing quotes, off-chain computation results, signed data used to drive on-chain actions), cross-workflow leakage of this cached data can lead to incorrect computations or unintended data exposure across workflows deployed by the same owner, and — if workflow-specific secrets or tokens end up embedded in cache-relevant fields not covered by the hash — response confusion between logically distinct executions.

### Likelihood Explanation
This is a straightforward collision, not a race condition requiring adversarial timing: any two workflows from the same owner that call the HTTP action capability with identical `Method`/`URL`/`Headers`/`Body` and non-zero `CacheSettings.MaxAgeMs`/`Store` will collide by design given the excluded `WorkflowID`, as directly demonstrated by the repository's own unit test asserting equal hashes for differing `WorkflowID` [2](#0-1) . No malicious action by a peer or node operator is required — it's an inherent gap in the cache key vs. the documented isolation contract.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the value hashed by `OutboundHTTPRequest.Hash()` so that cache entries are strictly scoped per-workflow as documented, matching the README's stated guarantee.

### Proof of Concept
1. Workflow A (owner `0xOwner`, workflowID `wf-A`) issues an HTTP action: `GET https://example.com/api` with `CacheSettings{Store:true, MaxAgeMs:600000}`, receiving and caching response `R_A`.
2. Workflow B (same owner `0xOwner`, different workflowID `wf-B`) issues the identical `GET https://example.com/api` request with the same `CacheSettings`.
3. Because `Hash()` excludes `WorkflowID` (confirmed by [2](#0-1) ), `Fetch` returns the cached `R_A` to workflow B without ever calling the fetch function, per the `Fetch` cache-hit path [8](#0-7) .

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
