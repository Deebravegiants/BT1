## Title
Multisig timelock-bypass `override_threshold` is recomputed live and can be silently weakened by removing an owner, letting a pending high-risk transaction skip its intended unanimous-consent delay - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account.move` implements an optional `MultisigAccountTimeLock` with an `override_threshold`: a higher approval count than `num_signatures_required` that, if met, lets a transaction execute immediately, bypassing the mandatory `timelock_period` delay. This mirrors the SALT bug class exactly: a quorum-like value (`override_threshold`) is stored as a single mutable global field and is re-read at execution-check time (`can_be_executed`) instead of being snapshotted per-transaction when the transaction was created. `update_owner_schema` actively clamps `override_threshold` down whenever an owner is removed and the old override value would exceed the new owner count. [1](#0-0) 

### Finding Description
When owners are removed via `remove_owners`/`remove_owner` (which route through `update_owner_schema`), the function clamps `MultisigAccountTimeLock.override_threshold` down to the new `num_owners` if it now exceeds the owner count: [1](#0-0) 

This clamp is applied globally and retroactively to the account's timelock configuration — it is not scoped to future transactions. Any `MultisigTransaction` that is already pending (created and partially approved before the owner removal) is checked against the *current* value of `override_threshold` at execution time, not the value that existed when the transaction was proposed. The test suite confirms this behavior explicitly:

- `test_owner_removal_clamps_override_threshold`: with a 3-of-3 override configured over 3 owners, removing one owner (after lowering `num_signatures_required` to keep the invariant `override_threshold > num_signatures_required` satisfied) clamps the override from 3 down to 2.
- `test_timelock_with_override_at_boundary`: demonstrates that a transaction with only 2 approvals is normally blocked from immediate execution because `2 < override_threshold(3)`. [2](#0-1) 

Combining these: if a transaction is created while `override_threshold = 3` (requiring unanimous 3-of-3 approval to bypass the timelock) and receives only 2 approvals, it should remain locked and cannot execute until `timelock_period` elapses. However, once any owner removal occurs (an ordinary multisig action requiring only the *base* `num_signatures_required`, e.g. 2-of-3 — far weaker than unanimity) and `override_threshold` clamps down to 2, the same already-approved, still-pending 2-approval transaction now satisfies the (weakened) override condition and can execute immediately, skipping the timelock delay that was in force and relied upon when it was created.

This is the exact custody invariant break identified in the SALT report: a threshold/quorum value used to gate finalization is computed dynamically from live global state (owner count) rather than fixed at the object's (transaction's) creation time, so an action unrelated to voting on that specific transaction (owner removal) can retroactively change whether it can be finalized.

### Impact Explanation
The `override_threshold` mechanism exists specifically as a custody safeguard: high-value or sensitive multisig transactions (e.g., asset transfers, code-object upgrades, resource-account control changes) can be configured to require a higher bar of consensus in order to bypass a deliberate delay window (`timelock_period`), which exists to give other owners/monitors time to detect and react to malicious proposals. If that higher bar can be silently reduced for already-pending transactions via an unrelated, lower-threshold owner-removal action, an owner coalition that only controls the base `num_signatures_required` (not the full unanimous set intended to gate immediate execution) can force early execution of a transaction that was supposed to require near-unanimous consent or wait out the timelock. This directly undermines a custody control protecting multisig-held assets/upgrade authority, since it lets a smaller-than-intended set of owners bypass the additional safety delay designed to protect asset transfers, freezes, or code-object/resource-account control changes.

### Likelihood Explanation
Exploitation requires only that: (1) a timelock with an `override_threshold` is configured, (2) a transaction is pending with approvals below the override but at or above `num_signatures_required`, and (3) the base quorum of owners (not unanimous) subsequently executes any owner-removal transaction. Since owner removal is a normal, expected multisig operation (unrelated in intent to the pending transaction), this can occur incidentally or be deliberately orchestrated by a colluding subset of owners meeting only the base threshold. No special privileges beyond normal multisig operation are needed.

### Recommendation
Snapshot the effective `override_threshold` (and `timelock_period`) into each `MultisigTransaction` at the time it is created, and evaluate `can_be_executed`/timelock-bypass logic against that stored, immutable value rather than re-reading the live `MultisigAccountTimeLock` resource. This prevents unrelated owner-set changes from retroactively altering the finalization conditions of already-pending transactions, mirroring the confirmed SALT fix of storing `requiredQuorum` at proposal-creation time.

### Proof of Concept
1. Create a multisig account with 3 owners, `num_signatures_required = 2`, and configure `MultisigAccountTimeLock` with `override_threshold = Some(3)` (unanimous bypass) and a non-trivial `timelock_period`.
2. Owner 1 creates a sensitive transaction (e.g., transferring custody-held assets). Owner 2 approves it — 2 approvals total. Per `test_timelock_with_override_at_boundary`, this is correctly blocked from immediate execution since `2 < override_threshold(3)` and the timelock has not elapsed. [3](#0-2) 
3. Separately, owners 1 and 2 (meeting only the base `num_signatures_required = 2`) pass a routine `remove_owner` transaction removing owner 3, reducing owner count to 2. `update_owner_schema` clamps `override_threshold` from 3 down to 2 as shown in `test_owner_removal_clamps_override_threshold`. [4](#0-3) 
4. The original transaction from step 2, still holding only its original 2 approvals, now satisfies the clamped `override_threshold = 2` and becomes immediately executable, bypassing the timelock delay that was in effect and expected when it was created.

**Uncertainty note:** I was not able to retrieve the exact body of `can_be_executed`/`can_be_rejected` (the function that reads `override_threshold` at execution-check time) within the available tool budget, so the precise comparison logic (`>=` vs strict `>`, and whether it re-reads the live resource vs. a cached value) is inferred from the clamp logic and the test names/assertions rather than directly confirmed by reading that function's source. Confirming the exact `can_be_executed` implementation would be the first step for a background agent validating and fixing this issue.
