### Title
Initial liquidity calculation permits `user_lp_amount == 0` when `sqrt(pc*coin) == 10^decimals`, permanently freezing the pool creator's deposit and desynchronizing LP accounting - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` computes the LP amount to mint to the pool creator by subtracting the minimum-liquidity constant (`10^decimals`) from the computed `liquidity`, using `checked_sub(...).ok_or(AmmError::InitLpAmountTooLess)`. This only errors when `liquidity < 10^decimals`; when `liquidity == 10^decimals` exactly, the subtraction succeeds and produces `user_lp_amount = 0`, so the pool is initialized and the creator's tokens are pulled into the vaults while **zero** LP tokens are minted to them. [1](#0-0) 

### Finding Description
The intended invariant (mirroring the standard "lock a minimum liquidity amount" pattern used by most AMMs) is that the very first depositor should receive `liquidity - MINIMUM_LIQUIDITY` LP tokens, with `MINIMUM_LIQUIDITY` conceptually reserved/burned. Here, that reserved amount is never actually minted anywhere (not even to a burn address) — `amm.lp_amount` is set to the full `liquidity` value, but `lp_mint.supply` only reflects whatever was minted to the user. [2](#0-1) 

When `init_pc_amount` and `init_coin_amount` are chosen (by any unprivileged pool creator calling `Initialize2`) such that `sqrt(init_pc_amount * init_coin_amount) == 10^lp_mint.decimals`, `user_lp_amount` becomes `0`. The pool initializes successfully: `amm.lp_amount = liquidity` (nonzero) while `lp_mint.supply` remains `0` because nothing was minted.

This breaks the core invariant that `process_withdraw` and `process_deposit` rely on. `process_withdraw` explicitly requires `withdraw.amount <= lp_mint.supply`: [3](#0-2) 

With `lp_mint.supply == 0`, this check makes every withdrawal revert (`NotAllowZeroLP`) since no positive `withdraw.amount` can be `<= 0`. Meanwhile `process_deposit` computes minted LP proportional to `amm.lp_amount` (not `lp_mint.supply`): [4](#0-3) 

so subsequent deposits still succeed and mint real, spendable LP tokens, but every future depositor's share is permanently diluted by the phantom, never-minted `10^decimals` worth of `amm.lp_amount` that nobody holds or can ever redeem.

### Impact Explanation
- The pool creator's initial `init_pc_amount`/`init_coin_amount` deposit is irrecoverably locked in the vaults — they receive `0` LP tokens and can never construct a valid withdraw (permanent freezing of user funds).
- `amm.lp_amount` (internal supply accounting) and `lp_mint.supply` (real token supply) permanently diverge, corrupting pool accounting used by every subsequent deposit/withdraw proportional-share calculation (insolvent/incorrect pool accounting) for the lifetime of the pool.
- This is triggerable by any unprivileged pool creator invoking `Initialize2` with attacker-chosen `init_pc_amount`/`init_coin_amount` and decimals, i.e., reachable from a single transaction with attacker-controlled instruction data.

### Likelihood Explanation
Any user calling `Initialize2` can pick `init_pc_amount` and `init_coin_amount` such that `sqrt(init_pc_amount * init_coin_amount)` lands exactly on `10^decimals` (e.g., for 6-decimal mints, `init_pc_amount = init_coin_amount = 1_000_000`, giving `sqrt(1e12) = 1_000_000 = 10^6`). This is a simple, deterministic, attacker-computable input, making the condition trivially reachable without any race condition or privileged access.

### Recommendation
Require `liquidity` to be strictly greater than `10^decimals` (i.e., reject when `liquidity <= 10^decimals`, not just `< `), or, preferably, follow the standard pattern of actually minting the `MINIMUM_LIQUIDITY` amount to a permanently-unspendable/burn address so `lp_mint.supply` and `amm.lp_amount` never diverge, and revert `Initialize2` when the resulting user-mintable amount would be `0`.

### Proof of Concept
1. Attacker (as pool creator) calls `Initialize2` with a coin/pc mint pair both having `decimals = 6`, and funds `amm_coin_vault`/`amm_pc_vault` such that `amm_coin_vault.amount = amm_pc_vault.amount = 1_000_000`.
2. `liquidity = sqrt(1_000_000 * 1_000_000) = 1_000_000 = 10^6`.
3. `user_lp_amount = liquidity.checked_sub(10^6) = Some(0)` — no error raised.
4. `Invokers::token_mint_to(..., user_lp_amount = 0)` mints zero LP tokens to the creator; `amm.lp_amount` is set to `1_000_000`.
5. The creator's `init_coin_amount`/`init_pc_amount` are now stuck in the vaults with `lp_mint.supply == 0`; any later `Withdraw` from the creator fails the `withdraw.amount > lp_mint.supply` check permanently, and pool accounting (`amm.lp_amount` vs. real minted supply) is desynchronized for all future participants.
