### Title
Silently swallowed MCU acknowledge-error causes commands (e.g. IR LED / biometric-capture hardware triggers) to be reported as successful when they actually failed - (File: `src/mcu/can.rs`)

### Summary
The `FeeDisburser` bug is a class of "unchecked/ignored failure of a critical operation, so the caller proceeds as if it succeeded." The same bug class exists in orb-core's MCU communication layer: `Can::handle_input` receives an acknowledge (`Ack`) from the microcontroller and is supposed to translate an MCU-reported error into a `completion_result = Err(...)` that is forwarded to the caller of `Mcu::send`. Instead, the code that would set `completion_result` to `Err` on an MCU error is commented out, so a failed hardware operation is reported to the caller as `Ok(())`.

### Finding Description
`Mcu::send()` in [1](#0-0)  sends a command to the microcontroller and waits on a `oneshot::Receiver<Result<(), Error>>` (`ResultSender`), retrying only `if let Err(error) = completion_rx.await?`. The value received on that channel comes from `completion_result` populated in `Can::handle_input`: [2](#0-1) 

When the MCU ack reports a recognized `ErrorCode` other than `Success`, the code only logs `tracing::error!` and the line that would set `completion_result = Err(...)` is commented out. The same happens for an unknown/incompatible error code. In both cases `completion_result` remains its initialized value `Ok(())` from [3](#0-2) , and that `Ok(())` is sent back to the caller via `completion_tx.send(completion_result).ok();` at [4](#0-3) .

This directly mirrors the reported bug class: a downstream failure (MCU rejecting/failing a command) is not propagated to the caller, so the caller's code proceeds down the "success" path — no retry (`Mcu::send`'s retry logic never triggers), and no error bubbles up through `?` in call sites such as:
- `orb.main_mcu.send(mcu::main::Input::IrLed(ir_led_wavelength)).await?` in `set_ir_wavelength` [5](#0-4) 
- `orb.main_mcu.send(mcu::main::Input::TriggeringIrEyeCamera(true)).await?` in `start_ir_eye_camera` [6](#0-5) 

These sends control hardware state (IR illumination, camera triggering, mirror motion, etc.) that biometric capture and its downstream liveness/fraud logic implicitly depend on being actually applied.

### Impact Explanation
If the microcontroller returns a legitimate error acknowledge for a command critical to biometric capture setup (e.g. enabling the correct IR LED wavelength before iris capture, or triggering the IR eye camera), orb-core will treat the command as having succeeded. The capture pipeline would then proceed under the false assumption that the required hardware state (illumination, camera trigger, mirror position) was established, potentially capturing/processing images under conditions the safety/liveness logic did not intend. This does not directly forge signups or leak biometric data, but it silently defeats the reliability guarantee that hardware preconditions for a valid capture were met, which is the same silent-failure/bypass root cause as the external report — an operation's failure is dropped instead of being surfaced, letting execution continue on a false-success path.

### Likelihood Explanation
Requires the MCU firmware to actually return a non-`Success` ack (a hardware/firmware-reported error), which is not attacker-controlled through the QR/network interface and depends on real hardware fault conditions or firmware bugs. This limits likelihood similarly to the original report's "unlikely but possible" characterization — it is a real defect in error propagation, but exploiting it deterministically requires influencing MCU behavior, which is outside a purely unprivileged software attacker's reach.

### Recommendation
Uncomment/restore the `completion_result = Err(...)` assignments for both the recognized-error and unknown-error-code branches in `Can::handle_input` (`src/mcu/can.rs` lines ~129 and ~136), so `Mcu::send` correctly retries or surfaces the failure instead of returning `Ok(())` on MCU-reported errors.

### Proof of Concept
1. Have the Main MCU firmware respond to a `IrLed` (or any) command with an `Ack` whose `error` field is a valid non-`Success` `ErrorCode` (or an unrecognized code).
2. In `Can::handle_input`, the branch at [7](#0-6)  only logs the error; `completion_result` (initialized to `Ok(())` at line 82) is never reassigned.
3. `completion_tx.send(completion_result)` forwards `Ok(())` to `Mcu::send`'s `completion_rx.await?`, which sees `Ok(())` and returns success without retrying at [8](#0-7) .
4. Callers like `set_ir_wavelength`/`start_ir_eye_camera` proceed as if the hardware command succeeded, even though the MCU reported an error.

    /// Sends a message to the microcontroller and waits for the acknowledge.
    fn send(&mut self, input: I::Input) -> Pin<Box<dyn Future<Output = Result<()>> + Send + '_>> {
        Box::pin(async move {
            let mut retries = SEND_RETRY_COUNT;
            'retry: loop {
                let (completion_tx, completion_rx) = oneshot::channel();
                self.tx_mut().send((input.clone(), Some(completion_tx))).await?;
                if let Err(error) = completion_rx.await? {
                    if retries > 0 {
                        tracing::warn!("Retrying last µC message... [{}]", retries);
                        retries -= 1;
                        continue 'retry;
                    }
                    tracing::error!("Maximum µC send retries reached, aborting with Error");
                    return Err(error);
                };
                break 'retry;
            }
            if let Some(log) = self.log_mut() {
                I::log_input(log, &input);
            }
            Ok(())
        })
    }
