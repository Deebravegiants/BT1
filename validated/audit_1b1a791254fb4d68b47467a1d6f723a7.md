Found the analog: in `IntentGatewayV2.fillOrder` (`evm/src/apps/IntentGatewayV2.sol:445`), the expiry check is `if (order.deadline < blockNumber) revert Expired();`. This means when `order.deadline == blockNumber`, the fill is still allowed to proceed — the boundary block is treated as still valid, exactly the same off-by-one class as the GMX `_setPrices` report (`>` instead of `>=`, here `<` instead of `<=`).

### Title
Off-by-one deadline check lets `fillOrder` execute exactly at the expiry block - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`fillOrder`'s expiry guard uses `order.deadline < blockNumber` to decide whether an order has expired [1](#0-0) . This is a strict-less-than comparison, so a fill submitted in the exact block equal to `order.deadline` is accepted rather than rejected — the boundary block is inclusive of validity when the documented and system-wide intent is that `deadline` marks the last block at which the order is *not yet* expired for cancellation/phantom-order purposes.

### Finding Description
The comment above `fillOrder` states the check is meant to validate "the order has not expired (deadline >= current block)" [2](#0-1) , but the actual code only reverts when `order.deadline < blockNumber`, i.e. it *allows* `order.deadline == blockNumber`. This directly parallels the GMX `_setPrices` OCL-3 finding: a boundary block-number value that should be treated as expired/invalid is instead accepted because `<`/`>` is used where `<=`/`>=` was intended.

Critically, this off-by-one is inconsistent with how the rest of the intents subsystem defines "expired." The SDK's phantom-order/filler logic explicitly encodes the invariant that `fillOrder` reverts `Expired()` once `deadline < block.number`, and treats `deadline == currentBlock` as **still fillable** (not yet expired) — this is asserted directly in the filler's test suite: `"refuses an order whose deadline is exactly the current block"` because `"fillOrder's check is deadline < block.number, so deadline == head is fillable"` [3](#0-2) . The filler's phantom-order defense-in-depth relies on the pallet stamping a *confirmed* (already past) height as an intentionally unfillable deadline; the off-by-one at the deadline boundary is exactly the edge the filler must special-case to avoid quoting a genuinely executable order as a phantom one [4](#0-3) .

### Impact Explanation
Functionally this is a boundary/off-by-one validation defect in the escrow/intents settlement path reachable by any solver submitting a fill transaction (the exact class of actor called out in scope: an intent solver). The immediate effect is that an order intended to be expired at block `deadline` can still be filled in that same block, extending the effective validity window by one block beyond what `deadline` is documented to mean. Because the SDK/filler code has had to explicitly codify and test for this exact behavior as a security-relevant edge case (to avoid mistaking a real, still-executable order for an already-expired "phantom" order), the boundary condition is a genuine, non-cosmetic discrepancy between documented/intended semantics and enforced semantics, and it demonstrates the on-chain check is the source of truth other components must awkwardly work around rather than trust.

### Likelihood Explanation
Likelihood of triggering is high mechanically (any solver can time a fill transaction to land in the exact `deadline` block, and the mempool/gas market let it happen without needing precise control) but likelihood of it causing loss is low: the primary consequence is a one-block extension of fillability, not fund theft, and it does not break any invariant of proof verification or state commitment. This mirrors the acknowledged-but-low-severity GMX report: an easily reachable off-by-one that violates documented boundary semantics without directly enabling theft or forgery.

### Recommendation
Change the check in `fillOrder` to `if (order.deadline <= blockNumber) revert Expired();` (or equivalently define `deadline` as inclusive and update the SDK/filler invariant/tests accordingly) so that `order.deadline == blockNumber` is treated as expired, consistent with the function's own doc comment ("deadline >= current block" as the *valid* condition) and eliminating the special-casing currently required in `sdk/packages/simplex/src/core/filler.ts`.

### Proof of Concept
1. A user places an order via `placeOrder` with `order.deadline = D`.
2. At block `D`, before any cancellation is processed, a solver calls `fillOrder(order, options)`.
3. `_blockNumber() == D`, so `order.deadline < blockNumber` evaluates to `D < D == false`; the `Expired()` revert is skipped and the fill proceeds [1](#0-0) .
4. This contradicts the function's own documentation of the intended check (`deadline >= current block` should be required for the order to still be valid) and the invariant hard-coded/tested elsewhere in the SDK [3](#0-2) .
