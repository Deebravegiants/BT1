### Title
Unaccounted asset theft via `EmporiumUpgradeable.runAction` CASE 2 calls on assets outside `circomData.erc20TokenAddresses` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable` is a single shared contract used by every Hinkal user (registered once via `Hinkal.registerExternalAction` and gated only by `onlyAllowedRecipient`, not per-user identity) [1](#0-0) . Its `runAction` value-conservation check only measures balances of the tokens listed in `circomData.erc20TokenAddresses` before/after the op loop [2](#0-1) [3](#0-2) , while CASE 2 "stateless" ops let the caller invoke an arbitrary `op.endpoint.call{value: op.value}(op.callData)` with the only restriction being a selector check against `callHinkalWallet`/`doSendToRelay` [4](#0-3) .

### Finding Description
The equality the balance/UTXO logic is supposed to enforce is: **for every asset that leaves or enters Emporium during `runAction`, `balancesAfter[i] - balancesBefore[i]` (adjusted by `deltaAmountChanges[i]`) accounts for it, and the resulting `utxoSet` reflects the true net value moved.** This only holds for `i` ranging over `circomData.erc20TokenAddresses` — an array fully chosen by the calling user themselves in their own `transact` call.

Because `EmporiumUpgradeable` is a shared, stateful singleton (its `usedMessages` mapping in `EmporiumStorage` persists across all users' transactions [5](#0-4) ), any non-ERC20/ETH asset that ends up custodied under Emporium's address as a side effect of an earlier CASE 2 op (e.g., an ERC721 staking receipt, a Uniswap V3 position NFT, or a limit-order id recorded against `msg.sender == Emporium` in some external protocol) remains reachable by *any subsequent caller*, because CASE 2's `op.endpoint.call(op.callData)` executes with `msg.sender == Emporium` regardless of which end-user submitted the current `transact`.

An attacker's own `transact`:
1. Sets `circomData.erc20TokenAddresses` to a list that excludes the receipt/position asset entirely.
2. Includes a CASE 2 op whose `callData` calls the external staking/order/AMM contract's withdrawal function (e.g., `withdraw(receiptId, attacker)` or `cancelAndRefund(orderId, attacker)`), directing the underlying value straight to the attacker's own address.
3. `runAction`'s balance loop at lines 132-151 never observes this transfer because it only iterates `erc20TokenAddresses`, and `handleOut` only ever moves tokens present in that same array [6](#0-5) .

None of the existing guards prevent this: `verifyWallet`/EIP-712 signature checks only apply when `stack.signerAddress != address(0)` (CASE 1, stateful path) and are irrelevant to CASE 2 [7](#0-6) ; the selector guard in CASE 2 only blocks calling `IHinkalWallet` functions, not arbitrary third-party contract functions [8](#0-7) ; and there is no allowlist restricting `op.endpoint` to a fixed, curated set of protocols with per-user isolated custody.

### Impact Explanation
An attacker can drain any non-ERC20 asset (staking receipts, LP/position NFTs, order book claims, or any other externally-tracked value) that any prior user's transaction left custodied under the shared `Emporium` address, by simply crafting a CASE 2 op targeting the same external protocol with the recipient set to themselves. This is theft of another user's in-flight/unclaimed position with zero accounting in Hinkal's own balance/UTXO conservation logic — matching the Critical category (direct theft of shielded/in-flight user funds) since the position was created through Hinkal flows and is invisible to Hinkal's own solvency bookkeeping. The attack is repeatable against every such stranded position and against every future user who uses Emporium for multi-step strategies that leave custodial receipts between transactions.

### Likelihood Explanation
Preconditions: some earlier CASE 2 op (by any user, including the victim) must leave a non-ERC20 claim with the external protocol recording `Emporium` (not the individual end-user) as owner/holder — this is an inherent property of routing all users' external calls through one shared contract address, not an edge case. The attacker needs no special privilege: they only need their own `transact` with self-chosen `circomData` fields and knowledge of the receipt/position id (often public, e.g., an NFT `tokenId` or order id emitted on-chain). Cost is a single normal-priced transaction.

### Recommendation
Do not scope `runAction`'s conservation check solely to `circomData.erc20TokenAddresses`. Either (a) require every CASE 2 `op.endpoint` to be drawn from a per-action allowlist of protocols whose only externally observable effect is ERC20/ETH balance changes at Emporium (disallow protocols that mint non-fungible/off-list claims to `msg.sender`), or (b) require any asset received by Emporium in one transaction (NFT, receipt, order id) to be immediately and atomically tied back to the depositing user's UTXO/commitment (e.g., via an explicit on-chain registry keyed by depositor, checked before allowing any subsequent withdrawal op to target it), or (c) disallow CASE 2 ops from calling any endpoint that is not present in `circomData.erc20TokenAddresses`-scoped protocol registry, closing the gap between "assets Emporium can hold across transactions" and "assets `runAction` actually accounts for."

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, register it as an external action on `Hinkal`, deploy a mock staking contract with `stake()` (records `owner[receiptId] = msg.sender`) and `withdraw(receiptId, to)` (transfers underlying ERC20 to `to`, requires `owner[receiptId] == msg.sender` i.e. `Emporium`).
2. Victim calls `transact` with a CASE 2 op: `stakingMock.stake(...)` from Emporium, producing `receiptId` with `owner[receiptId] == emporiumAddress`. Assert `balancesAfter == balancesBefore` for `circomData.erc20TokenAddresses` in that tx (i.e., the check passes with no anomaly, hiding the new receipt).
3. Attacker calls `transact` with `circomData.erc20TokenAddresses` excluding the staked token, and a CASE 2 op: `stakingMock.withdraw(receiptId, attacker)`.
4. Assert: `runAction` succeeds and returns a `utxoSet` whose total `amount` is unchanged/unaffected by the withdrawal; assert `attacker`'s balance of the underlying ERC20 increases by the full staked amount; assert `sum(circomData.erc20TokenAddresses balances tracked in step 3) does not decrease` while `sum(actual value removed from Emporium's custody, i.e., staking receipt value) > 0`, proving `Σ counted balanceChange != Σ actual value moved out of Emporium`.
