### Title
RAY-denominated market totals can overflow before the index cap and permanently freeze a market - (File: `common/src/rates/simulate.rs`)

### Summary
Accrual unscales the pool's total borrowed and supplied shares into RAY-denominated values before calculating utilization. These products are not checked against the `i128` domain. For a sufficiently large market, ordinary interest growth can therefore panic before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`, after which every pool operation that accrues the market reverts.

### Finding Description
Permissionless `Controller::update_indexes` forwards caller-selected markets to `pool_update_indexes_call` after only caller authorization. [1](#0-0)  The pool's `update_indexes` calls `ops::market::accrue`, which loads each market and invokes `interest::global_sync`. [2](#0-1)  `global_sync` splits elapsed time into bounded chunks and calls `accrue_step` for each chunk. [3](#0-2) [4](#0-3) 

The first operations inside `accrue_step` calculate `borrowed * borrow_index` and `supplied * supply_index` through `scaled_to_original`. [5](#0-4)  `scaled_to_original` is a direct `Ray::mul`, so an accrued value larger than `i128::MAX` panics rather than saturating or applying a market-specific bound. [6](#0-5)  The index ceilings are much weaker protection: they clamp the index itself at `1e36` raw RAY, but the multiplication by already-stored shares happens before any effective total-value bound. [7](#0-6) [8](#0-7) 

The repository contains a deterministic reproduction: a one-billion-whole-token, 18-decimal market at sustained high utilization eventually panics inside `scaled_to_original`, while the borrow index remains below its configured cap. [9](#0-8)  Because repayment and withdrawal also accrue before changing the market, the test demonstrates that both remain permanently unavailable after the overflow. [10](#0-9) 

### Impact Explanation
Once the product crosses the `i128` boundary, the market cannot accrue and therefore cannot safely repay, withdraw, borrow, liquidate, claim revenue, or otherwise mutate its state under the deployed code. Supplier cash in the affected market is frozen, borrower debt cannot be serviced, and liquidation cannot reduce the risk position. This is permanent freezing of funds unless governance upgrades the implementation.

### Likelihood Explanation
Likelihood is constrained by the required market size, configured caps, and sustained interest-bearing utilization. The admitted cap domain only ensures that the initial asset-to-RAY conversion fits `i128`; it does not reserve multiplicative headroom for the `1e9x` index ceiling. [11](#0-10)  An unprivileged address can create and fund accounts through `supply`, borrow through its own authorized account, and later call `update_indexes`; it does not need a privileged runtime action once a market's configured caps permit the necessary totals. [12](#0-11)  Consequently, this is a realistic protocol-level arithmetic limit for sufficiently large or high-decimal markets, although reaching it requires substantial liquidity and enough accrued growth.

### Recommendation
Bound stored scaled market totals against the maximum possible index, rather than validating only the initial asset-unit cap. In particular, enforce an invariant such as `scaled_total * MAX_INDEX_RAY / RAY <= i128::MAX` for both `supplied` and `borrowed`, accounting for revenue-share minting and bad-debt index reductions. Alternatively, perform utilization, reward, and market-total calculations in a wider representation and define a safe recovery behavior at the index ceiling. The current index cap alone is insufficient because the stored-share multiplication can overflow before the cap is relevant.

### Proof of Concept
The existing reproduction constructs an 18-decimal market, supplies `1_000_000_000` whole tokens, borrows 98% of that liquidity, and advances/accrues the market until `try_update_indexes_for` returns `MATH_OVERFLOW`. [13](#0-12)  The stored borrow index is asserted to remain below `MAX_BORROW_INDEX_RAY`, proving that the index ceiling did not prevent the failure. [14](#0-13)  Subsequent minimum-sized `withdraw` and `repay` calls both return the same overflow, proving the market is frozen rather than merely rejecting one oversized input. [15](#0-14)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// capped at `MAX_BORROW_INDEX_RAY`.
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
