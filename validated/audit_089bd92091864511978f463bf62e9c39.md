### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing a replayed payload to be attributed to a different shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, but then forwards the unauthenticated `shop-domain` header to the handler as the tenant identifier, breaking the intended binding `hmac ⟺ (body, shop)` down to only `hmac ⟺ body`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC and then immediately trusts `request.shop` (and the other unauthenticated headers) to construct the metadata handed to the app's handler: [3](#0-2) 

The `HmacValidator.validate` call verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. body-only, using the app's `api_secret_key`: [4](#0-3) 

This is the same bug class described in the report: an identity-binding field (`shop`) is *acted on* (used to identify which tenant's data this is: `WebhookMetadata.new(... shop: request.shop ...)`), but is *not covered* by the authentication mechanism (`hmac` only signs `@raw_body`). Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string`, which correctly includes `shop` (and `host`) in the signed payload: [5](#0-4) 

The documentation instructs developers to trust `data.shop` directly as the tenant key (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 

### Impact Explanation
Because the `shop` header is unauthenticated, anyone who has captured a single valid `(raw_body, hmac)` pair for their own shop's webhook endpoint (they legitimately receive these for their own store) can resend the exact same body/HMAC to the app's shared webhook endpoint while substituting a different `shop-domain` header. `Registry.process` will pass the HMAC check (it never inspects `shop`) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. If the host app follows the gem's documented pattern and uses `data.shop` as the tenant key to persist/dispatch the payload, this results in cross-tenant data confusion — data legitimately produced by shop A gets attributed to and processed under shop B. This matches the High-impact category "cross-tenant access" via breaking an identity-binding equality (`hmac-signed-shop == acted-upon-shop`), not merely a documentation/best-practice note, since the vulnerable binding is implemented in this gem's own `Request`/`Registry` classes and is the exact API path documented for use.

### Likelihood Explanation
Likelihood is moderate-to-low in absolute terms because it requires the attacker to already have a legitimate signed webhook payload from Shopify (i.e., they must control a shop that also uses the vulnerable app, or otherwise capture one payload/hmac pair) and requires the target app's webhook endpoint to be reachable by an unprivileged internet user (which it is, by design, since Shopify sends webhooks over plain internet POST requests). No secret key, access token, or privileged account is required — only observation of one's own legitimately delivered webhook.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated before it is trusted, e.g.:
- Have `Registry.process` require the caller to independently know/verify the expected shop (e.g., look up an active session for `request.shop` and reject if none exists) before dispatching to the handler, rather than presenting `data.shop` as if it were already authenticated by the HMAC check.
- Document explicitly in `docs/usage/webhooks.md` that `data.shop` is *not* covered by the HMAC and must be independently verified against a known/installed shop before being used as a tenant key.

### Proof of Concept
1. Shop A installs the app and has a webhook subscription (e.g. `orders/create`) delivered to `https://app.example.com/callback/orders/create`.
2. Attacker (who controls Shop A) captures a legitimately delivered webhook request, including the raw body and the `X-Shopify-Hmac-Sha256` header (a valid HMAC for that body, computed by Shopify with the app's real secret).
3. Attacker resends the identical raw body and HMAC header to the same endpoint, but changes the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and successfully matches — the forged `shop` header is never checked.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ..., ...)`, causing the app (following the documented pattern) to persist/process Shop A's order data as though it belongs to Shop B.

```ruby
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
