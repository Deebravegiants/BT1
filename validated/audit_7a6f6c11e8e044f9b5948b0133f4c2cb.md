### Title
Emporium "message-only" proof path (`MainEVMCircuitMin`) provides no ownership/authorization check, letting any unprivileged caller execute arbitrary Emporium operations - ([File: circuits/MainEVMCircuitMin.circom], [File: contracts/CircomDataBuilder.sol], [File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
The external report flags an inconsistency where some functions enforce a strict input‑format check and others don't, letting an attacker slip in an unexpected value. The exact same class of bug exists in this repo's "message-only" (Emporium, zero-token) transaction path: the reduced circuit used for that path (`MainEVMCircuitMin`) omits the ownership/signature check (`SignatureVerifier`) that every other circuit variant enforces, so the "authorization" it produces can be self-forged by anyone with no private key at all.

### Finding Description
For a normal transaction, `MainEVMCircuit` requires the prover to supply a valid EdDSA signature over `signedMessageHash` bound to `spendingPublicKey` [1](#0-0) [2](#0-1) . This binds the emitted `message` value to a real Hinkal spending key.

`formInputForCircom` however routes any transaction where `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0` to a completely different, minimal circuit path (`formInputEmporiumMin`) instead of the normal one [3](#0-2) . The circuit used for that path, `MainEVMCircuitMin`, has **no** `spendingPublicKey`, no `eddsaSignature`, no `SignatureVerifier`, and no root-hash/nullifier verification whatsoever - it only computes `message <== Poseidon(1)([messageSeed])` [4](#0-3) .

Critically, `formInputEmporiumMin` feeds `circomData.emporiumMessage` into the public-input slot that Circom's calling convention reserves for the circuit's **output** signal `message` (outputs are ordered first in the public signal vector) [5](#0-4) . Since `message` is only constrained to `Poseidon(messageSeed)` with no tie to any secret key, an attacker can pick an arbitrary `messageSeed`, compute `emporiumMessage = Poseidon(1)([messageSeed])` themselves off-chain, and produce a fully valid Groth16 proof — no ownership of a Hinkal spending key, nullifier, or Merkle leaf is required.

This forged "message" is then consumed by `EmporiumUpgradeable.verifyWallet`, which only performs an EIP-712 signature check when `stack.signerAddress != address(0)`; when `signerAddress == address(0)` ("stateless" operations) it just marks the message as used and returns, relying entirely on the SNARK proof/message having proven legitimate authorization [6](#0-5) . Because that "proof" is trivially self-forgeable as shown above, `runAction` will execute the attacker's arbitrary `EmporiumOperation[]` list via `op.endpoint.call{value: op.value}(op.callData)` from the Emporium contract's own address/balance [7](#0-6) .

All the other on-chain checks in `Hinkal.transact` / `HinkalHelper` are trivially satisfiable by an unprivileged EOA in this path: `dimensionsCheck`/`relayerIsValid` only require self-consistent, non-relay-routed fields (`relay == address(0)`, `originalSender == msg.sender`) [8](#0-7) , and `rootHashExists` only requires `rootHashHinkal` to be *some* historical root, not one whose leaves the attacker owns [9](#0-8) . Since `erc20TokenAddresses.length == 0`, the balance-equation loop in `Hinkal.transact` (lines 97-147) never executes, so no balance-diff constraint applies either.

### Impact Explanation
This breaks the equality the whole "message" scheme is supposed to enforce: `message` (public input) should only be producible by someone who legitimately signed with their Hinkal spending key, but in the Min-circuit path it is producible by anyone. This is a proof/authorization bypass that lets an unprivileged EOA get `EmporiumUpgradeable` to execute arbitrary external calls with the Emporium contract as `msg.sender` and arbitrary attacker-chosen `op.value` drawn from the Emporium contract's own ETH balance, without any wallet signature or ZK ownership proof. If the Emporium contract (or any contract relying on `msg.sender == Emporium`, e.g., holding token allowances or `payRelayFees`-collected balances) holds funds, this enables direct theft of protocol/relay funds - a Critical/High-impact unauthorized asset movement and proof-verification bypass.

### Likelihood Explanation
High. No special privileges, relay whitelisting, or valid Hinkal identity are needed. An attacker only needs to: (1) pick any `messageSeed`, (2) compute `Poseidon(1)([messageSeed]))` off-chain to get a "message" value, (3) generate a Groth16 proof for the trivial `MainEVMCircuitMin` circuit (no meaningful constraints to satisfy), and (4) call `transact()` directly (no relay). This requires no code compromise, no operator/relayer key, and works purely from the publicly known ABI and circuit artifacts.

### Recommendation
Apply the same "always enforce the check" principle the report recommends for pubkey length checks to the message/authorization scheme: either (a) remove the message-only/minimal circuit path entirely and always use a circuit variant that includes `SignatureVerifier` binding `message`/`emporiumMessage` to a real `spendingPublicKey`, or (b) if a reduced circuit for zero-token Emporium calls is required, require it to still verify an EdDSA/ownership signature over `emporiumMessage`, and require `EmporiumUpgradeable.verifyWallet` to always validate a wallet-level signature/authorization regardless of `signerAddress`, rather than trusting an easily-forgeable circuit output.

### Proof of Concept
1. Attacker (any EOA, no Hinkal deposits) picks `messageSeed = 1234` and computes `m = Poseidon(1)([1234])` off-chain.
2. Attacker generates a valid Groth16 proof for `MainEVMCircuitMin` with `messageSeed = 1234`, `outTimeStamp = t`, `calldataHash = h` — all self-chosen, no secret key needed.
3. Attacker builds `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: <target>, invokeWallet: false, value: <Emporium's ETH balance>, callData: <arbitrary> }], ... })`, `emporiumMessage = m`, `relay = address(0)`, `originalSender = msg.sender`, and dummy but length-consistent `slippageValues`/`onChainCreation`/`onChainEncryptedOutput`/`stealthAddressStructure.H0x != 0`.
4. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)`. `performHinkalChecks` and `rootHashExists` pass trivially; `verifyProof` succeeds because the forged proof is valid for the (unconstrained) Min circuit; `_externalTransact` calls `EmporiumUpgradeable.runAction`.
5. `verifyWallet` sees `stack.signerAddress == address(0)`, marks `emporiumMessage` used, and returns without any signature check.
6. The attacker's `ops[0].endpoint.call{value: op.value}(op.callData)` executes from the Emporium contract, moving its ETH balance to an address of the attacker's choosing — with no wallet authorization and no genuine ZK proof of key ownership.
