### Title
Shopify webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then reads the `shop` (tenant identity) directly from an unauthenticated HTTP header and forwards it unchanged to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. only the raw body: [3](#0-2) 

`Registry.process` then trusts `request.shop` to construct the data passed to the app's handler, without any independent check binding the header value to the signed payload: [4](#0-3) 

The equality this breaks is: `hmac_verified(body)` should imply `shop == tenant_that_generated(body)`, but the gem only guarantees `hmac_verified(body)`; the `shop` field consumed by the handler is taken from an entirely separate, unauthenticated header (`x-shopify-shop-domain` / `shopify-shop-domain`). Since only the raw body is covered by the signature, an attacker who possesses one authentic webhook body/signature pair signed with the app's secret (e.g., from their own shop's installation of the app, which they can trivially obtain by installing the app themselves and triggering any webhook) can resend that exact body with the HMAC unchanged, but with the `shop-domain` header rewritten to name a different, victim shop. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will call the app's handler with `shop: <victim-shop>` even though the body actually originated from the attacker's own tenant.

### Impact Explanation
This breaks the tenant identity binding that webhook consumers (via `shopify_app` or custom handlers) rely on: they trust `WebhookMetadata#shop` to know which merchant's data is contained in `body`/to key their database writes and side effects. An attacker can leverage this to make the app believe attacker-controlled webhook content belongs to an arbitrary victim shop, resulting in cross-tenant data corruption/injection in any app whose handler logic uses the reported `shop` to scope storage, side effects, or state transitions (a High-severity cross-tenant issue per the given impact taxonomy, since the app-level identity/tenant boundary is bypassed even though the gem-level `Utils::HmacValidator` "passes").

### Likelihood Explanation
Likelihood is realistic: the attacker only needs an authentic webhook payload and signature that they can freely obtain by having their own store install the target app (a normal, unprivileged action for any internet user) — no access to the app's `client_secret`, access tokens, or any privileged account is required. HTTP headers are fully attacker-controlled on any request they craft, so forging the `shop-domain` header on replay requires no special capability.

### Recommendation
Bind the `shop` value to the signed content instead of trusting an unauthenticated header:
- Verify that the `shop`/`shop-domain` value used by the handler corresponds to a shop that actually has an active registration/session for the received `webhook_id`/topic before dispatching, or
- Require the HMAC to be computed over the header value in addition to the body (not possible unilaterally since Shopify controls the signature scheme), or, more practically,
- Document and enforce that consuming applications must cross-check `WebhookMetadata#shop` against their own known set of installed shops and treat it as untrusted input for authorization decisions, and consider exposing a helper that validates `shop` against `ShopValidator` and against locally stored session/shop records before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`) and triggers any webhook subscription (e.g. `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` sent by Shopify (both are legitimately signed with the app's `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `HMAC(secret, B)` — it never inspects the `shop-domain` header: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, causing the app to process attacker-controlled data under the victim's tenant identity.
