Based on my investigation, `BandwidthManager.sol` has the same class of bug as the reported ERC1155Bridgable issue: it can be instructed to pay out native ETH but has no `receive()`/`fallback()` function, so it can never actually hold ETH to pay out.

### Title
BandwidthManager cannot receive ETH, permanently blocking native-token treasury withdrawals dispatched by governance - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.onAccept` implements an `OnAcceptActions.Withdraw` action that explicitly supports withdrawing native ETH (`w.token == address(0)`) via `w.beneficiary.call{value: w.amount}("")` [1](#0-0) . However, the contract defines no `receive()` or `fallback()` function anywhere in the file, and `purchase()` — the only funds-inbound entrypoint — only ever pulls the fee token via `IERC20(feeToken).safeTransferFrom`, never accepting `msg.value` [2](#0-1) .

### Finding Description
The governance docs for the bandwidth pallet explicitly describe a native-ETH withdrawal path from this exact manager contract: *"If token == address(0): beneficiary.call{value: amount}("") — reverts with InsufficientNativeToken if the call fails... The token field is named explicitly because the host occasionally swaps fee tokens (e.g. accepting native ETH on dispatch and routing through Uniswap). Stale balances of an old fee token still sit in the manager and are recoverable..."* [3](#0-2) . This confirms the design intent that `BandwidthManager` is expected, at some point, to hold native ETH balance (e.g. leftover ETH from a fee-token swap scenario, or direct ETH sends) that governance can later recover via `dispatch_withdraw`.

But unlike every other ETH-handling contract in this codebase — `CallDispatcher.sol` [4](#0-3) , `SimplexPaymaster.sol` [5](#0-4) , `IntentGatewayV2.sol` [6](#0-5) , `WrappedHyperFungibleToken.sol` [7](#0-6) , and the Uniswap wrapper contracts [8](#0-7)  — `BandwidthManager` has zero `receive`/`fallback` capability. Any ETH sent to it (whether by direct transfer, a future payable purchase path, or an EvmHost fee-token swap remainder) will simply revert at the EVM level, exactly analogous to the ERC1155Bridgable report.

### Impact Explanation
Because `onAccept`'s `Withdraw` action for `token == address(0)` assumes the contract holds an ETH balance, and there is no way for that balance to ever be nonzero, the native-ETH withdrawal branch is dead code that will always either (a) never be triggered with a meaningful amount, or (b) if ETH is ever sent to the contract by any means, it permanently reverts and that ETH is unrecoverable (stuck funds), since there's no way to add a `receive()` after deployment. This matches the "permanent freezing of funds" acceptance criterion — any ETH mistakenly or intentionally routed to `BandwidthManager` (e.g., through a future host fee-token migration to native ETH as the docs allude to) is irrecoverably locked, and the governance-triggered `Withdraw(token=0)` path can never succeed.

### Likelihood Explanation
Medium-to-High: the docs explicitly reference a scenario ("the host occasionally swaps fee tokens, e.g. accepting native ETH on dispatch") where ETH could end up in this contract's balance, and the withdrawal payload format (`Withdrawal{token, beneficiary, amount}`) is built specifically to support `token == address(0)` as a first-class recovery case. This means the vulnerability is reachable via governance's own documented workflow (`dispatch_withdraw` with `fee_token_address = H160::zero()`), not merely a theoretical edge case [9](#0-8) .

### Recommendation
Add a `receive() external payable {}` function to `BandwidthManager.sol`, mirroring the pattern already used consistently across `CallDispatcher.sol`, `SimplexPaymaster.sol`, `IntentGatewayV2.sol`, and the Uniswap wrapper contracts in the same repository, so any ETH the contract is expected to hold (per the documented withdrawal semantics) can actually be received and later recovered via the existing `Withdraw` governance action.

### Proof of Concept
1. Deploy `BandwidthManager` and set its host, as in `BandwidthManagerTest.t.sol` [10](#0-9) .
2. Attempt `payable(address(manager)).call{value: 1 ether}("")` from any account — this reverts because no `receive()`/`fallback()` is defined, confirming the contract structurally cannot hold ETH [11](#0-10) .
3. Consequently, dispatching `dispatch_withdraw` from governance with `fee_token_address = H160::zero()` targeting this manager, as documented, can never successfully recover any ETH balance because that balance can never be established in the first place; if ETH is ever forcibly sent (e.g., via `selfdestruct` or being set as a block's coinbase), it becomes permanently stuck since `onAccept`'s ETH-withdraw branch depends on a contract balance that was reachable only through a reverting inbound path.

## Treasury Withdrawals

The fee tokens collected by `BandwidthManager.purchase()` accumulate in the manager contract. Governance drains them with `dispatch_withdraw`:

```rust
BandwidthPallet::dispatch_withdraw(
    RawOrigin::Root.into(),
    StateMachine::Evm(8453),
    fee_token_address,              // ERC-20 to withdraw. Use H160::zero() for native ETH.
    treasury_address,               // Beneficiary.
    U256::from(1_000_000_000u128),  // Amount, in fee-token decimals.
);
```

The pallet dispatches `[ACTION_WITHDRAW, abi.encode(Withdrawal)]` where `Withdrawal { token, beneficiary, amount }`. The manager's `onAccept` handler:

- If `token != address(0)`: `IERC20(token).safeTransfer(beneficiary, amount)`.
- If `token == address(0)`: `beneficiary.call{value: amount}("")` — reverts with `InsufficientNativeToken` if the call fails (insufficient balance, beneficiary rejects ETH, etc.).

The `token` field is named explicitly because the host occasionally swaps fee tokens (e.g. accepting native ETH on dispatch and routing through Uniswap). Stale balances of an old fee token still sit in the manager and are recoverable by specifying the old token's address.
