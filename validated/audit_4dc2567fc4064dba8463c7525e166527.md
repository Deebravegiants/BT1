Audit Report

## Title
Cross-caller response hijacking via unkeyed `MessageID` collision in gateway WebAPI trigger handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` in the gateway's legacy WebAPI trigger handler stores the caller's response callback in `h.savedCallbacks` keyed only by the client-supplied `MessageID`, with no binding to sender identity. Since `MessageID` is fully attacker-chosen (validated only for length/format in `Message.Validate`), two unrelated unauthenticated submitters using the same `MessageID` will collide, silently overwriting one another's saved callback, so the DON's eventual response (matched purely by `MessageID` in `handleWebAPITriggerMessage`) can be delivered to the wrong caller.

## Finding Description
`HandleLegacyUserMessage` accepts an inbound `api.Message` and, after only basic payload/timestamp/method validation, stores the caller's callback keyed solely by `msg.Body.MessageID`: [1](#0-0) 

There is no uniqueness or ownership check at this point, in contrast to the shared `RequestCache` abstraction used elsewhere in the gateway (e.g., target/action), which explicitly keys pending requests by `{sender, id}` and rejects duplicates outright: [2](#0-1) 

`MessageID` is validated only for length and null-byte suffix in `Message.Validate`, and `Sender` is derived from the signature but never cross-checked against `MessageID` uniqueness: [3](#0-2) 

Any signer holding a valid ECDSA key (an unauthenticated action available to any external caller, since there is no allowlist gate before this point — the TODO comment confirms this) can choose an arbitrary `MessageID`: [4](#0-3) 

When a node later responds, `handleWebAPITriggerMessage` looks up, deletes, and routes the response purely by `MessageID`, with no sender/requester correlation check: [5](#0-4) 

The handler's own test file explicitly flags this gap as an open, unresolved TODO ("Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated"), confirming the maintainers are aware this protection does not currently exist: [6](#0-5) 

This is architecturally distinct from the confirmed-safe `common.RequestCache`, which composes a `globalID{Sender, MessageID}` key and explicitly errors on duplicates — the WebAPI trigger handler bypasses this and uses its own bespoke, non-scoped `map[string]*savedCallback`: [7](#0-6) [8](#0-7) 

## Impact Explanation
Any unprivileged caller able to sign and POST a `web_api_trigger` message to the gateway can:
- Overwrite another concurrent submitter's `savedCallbacks` entry silently (no error is returned, unlike `RequestCache.NewRequest`), causing that submitter's HTTP request to hang/never resolve (until pruning via `pruneCallbacks`).
- Receive the DON's response payload intended for the earlier submitter's trigger request, since the response is routed to whichever callback currently occupies the `MessageID` slot.

This maps to the in-scope "cross-user response corruption" / "gateway request impersonation" impact category, as it allows response confusion/misdelivery across unrelated, unauthenticated callers on a gateway that has no per-message allowlist or rate limiting yet in this path.

## Likelihood Explanation
Reachable by any external caller with a valid ECDSA keypair (the gateway signature check only verifies the message is validly signed — it does not require the signer to be pre-authorized, per the explicit `// TODO: apply allowlist and rate-limiting here` comment). `MessageID` is entirely caller-controlled with no per-sender scoping (`Message.Validate` only checks length/format), so triggering a collision deliberately (e.g., always submitting the same `MessageID` value, as the project's own example script and test helper `triggerRequest` do with a hardcoded `"12345"`) is trivial and repeatable, and could also occur accidentally under concurrent load.

## Recommendation
- Scope `savedCallbacks` (and the corresponding lookup in `handleWebAPITriggerMessage`) by a composite key that includes `msg.Body.Sender`, mirroring the `{sender, id}` keying already implemented in `common.RequestCache`.
- Reject (rather than silently overwrite) registration of a duplicate key, as `RequestCache.NewRequest` already does.
- Migrate this legacy trigger path onto the shared `RequestCache` implementation instead of the bespoke `savedCallbacks` map.
- Implement the still-outstanding "apply allowlist and rate-limiting" TODO for this handler.

## Proof of Concept
1. Submitter A signs and sends a `web_api_trigger` message with `MessageID = "X"` to the gateway; `HandleLegacyUserMessage` registers A's callback in `h.savedCallbacks["X"]` and forwards the request to all DON members (`core/services/gateway/handlers/capabilities/handler.go` L411-419).
2. Before any DON node responds, Attacker B (a different, unrelated signer) sends a second `web_api_trigger` message also using `MessageID = "X"`; this overwrites `h.savedCallbacks["X"]` with B's callback, with no error surfaced to either party.
3. When a DON node responds to A's forwarded request (echoing `MessageID = "X"`), `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's response payload to B (`handler.go` L148-162).
4. This can be reproduced as a Go unit test extending `TestHandlerReceiveHTTPMessageFromClient` in `core/services/gateway/handlers/capabilities/handler_test.go`: call `HandleLegacyUserMessage` twice with two different signers but the same `MessageID`, then call `HandleNodeMessage` for the first request's expected response and assert that the *second* signer's callback (not the first's) receives the response.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {

	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
