### Title
Unchecked ERC20 transfer in `IntentGatewayV2.placeOrder` predispatch sweep lets escrow be credited without tokens actually being received - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.sol` (Tron variant) uses `IERC20.transfer` via a raw `abi.encodeWithSelector` call dispatched through `CallDispatcher`, whose `dispatch()` only checks the low-level `call` `success` flag and never inspects the ERC20 boolean return value. In the predispatch branch of `placeOrder`, the code credits the order's escrow (`_orders[commitment][token] += reducedInputs[i].amount`) unconditionally after issuing this unchecked sweep, without verifying that the gateway's token balance actually increased.

### Finding Description
`CallDispatcher.dispatch` only reverts if the low-level `.call` itself reverts: [1](#0-0) 

For a non-standard/non-reverting ERC20 token that returns `false` on a failed `transfer` instead of reverting (the exact bug class in the referenced report), this call succeeds at the low level even though zero tokens moved.

`IntentGatewayV2.placeOrder`'s predispatch path builds a sweep call using the raw `transfer` selector (not `safeTransfer`) to move the gateway's expected input tokens back from the `CallDispatcher` to the gateway: [2](#0-1) 

Crucially, unlike the balance-delta verification performed elsewhere in the sibling EVM contract (`evm/src/apps/IntentGatewayV2.sol`, which recomputes `order.inputs[i].amount` from an actual before/after `balanceOf` diff at lines 291-311 and later credits escrow from that verified amount at lines 363-373), this code path credits `_orders[commitment][token] += reducedInputs[i].amount` directly from the requested/expected amount, with no post-transfer balance check: [3](#0-2) 

If the swept token's `transfer` call returns `false` without reverting (or if the token behaves non-standardly on this particular chain/environment), the escrow accounting is inflated relative to the tokens the gateway actually holds — an unbacked escrow credit.

### Impact Explanation
An unbacked `_orders[commitment][token]` credit means the gateway believes it holds tokens it does not actually possess. When that order is later filled or refunded, the contract will attempt to pay out (`safeTransfer`) tokens from its balance for an amount it never received, which can only be paid using tokens escrowed by *other* users' orders. This is a permanent-freezing/insolvency vector: legitimate users can lose their escrowed funds because the pooled token balance becomes insufficient to cover all outstanding escrow credits.

### Likelihood Explanation
Exploitation requires a token used as a `predispatch` input whose `transfer` implementation returns `false` on failure instead of reverting, combined with a predispatch call that leaves the `CallDispatcher` short of the required balance (e.g., a lossy/failing swap or a malicious/non-standard token supplied by the order creator). Since `predispatch.assets`/`order.inputs` and the predispatch calldata are all attacker (order-placer) controlled inputs, an attacker can deliberately choose or arrange for this condition, making exploitation practical rather than purely theoretical.

### Recommendation
Use `SafeERC20.safeTransfer`/`safeTransferFrom` (as already done in the non-predispatch branch and in `evm/src/apps/IntentGatewayV2.sol`'s Phase 1) for the sweep calls dispatched through `CallDispatcher`, and/or verify the gateway's actual post-sweep balance delta (as done in `evm/src/apps/IntentGatewayV2.sol` lines 291-311) before crediting `_orders[commitment][token]`, rather than crediting the pre-computed `reducedInputs[i].amount` unconditionally.

### Proof of Concept
1. Attacker calls `placeOrder` with `predispatch.call`/`predispatch.assets` set up so that the `CallDispatcher` ends up holding a non-standard ERC20 token (one that returns `false` on failed `transfer` rather than reverting) whose balance the sweep will attempt to move.
2. The sweep call `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` is dispatched via `CallDispatcher.dispatch`, which only checks `success` of the raw call, not the returned boolean.
3. If the transfer silently fails and returns `false`, `CallDispatcher` still reports success, so `dispatch` does not revert.
4. `placeOrder` proceeds to execute `_orders[commitment][token] += reducedInputs[i].amount` (line 441) even though the gateway's actual token balance did not increase.
5. The order is now escrowed on-chain for an amount not actually backed by tokens; subsequent `fillOrder`/refund/`withdraw` flows pay this out from the shared token pool, depleting funds legitimately escrowed by other orders. [2](#0-1) [1](#0-0)
