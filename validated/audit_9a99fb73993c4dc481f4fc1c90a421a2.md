I found a strong analog: the `HyperFungibleToken`/`pallet-hyper-fungible-token` cross-chain decimal-scaling path burns/escrows the *full* real value on the sending chain, then divides by a scaling factor on the receiving chain with no minimum-amount or zero-check, allowing the credited amount to round down to zero while the source-side funds are irrecoverably gone.

### Title
Cross-chain amount rounds to zero on decimal-down-scaling, burning/escrowing real value while crediting nothing to the beneficiary - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `send` extrinsic burns or escrows a user's full asset amount on the local chain, encodes it for the destination chain by *multiplying* to a higher decimal precision (`convert_to_erc20`), and dispatches an ISMP POST request. On the EVM side, `HyperFungibleToken.send()` similarly burns the caller's full `params.amount` before dispatching. On the receiving side, both `HyperFungibleToken.onAccept` (mint, no scaling — EVM decimals fixed at 18) and, more importantly, `pallet-hyper-fungible-token`'s `on_accept` (`convert_to_balance`, which *divides* by `10^(erc_decimals - local_decimals)`) can round the credited amount down to zero for small-but-nonzero inputs, with no revert or minimum-amount guard.

### Finding Description
`convert_to_balance` performs integer division with no zero-result check: [1](#0-0) 

This is invoked in the incoming-message handler `on_accept`, which mints or releases `amount` to the `beneficiary` unconditionally, even when `amount == 0`: [2](#0-1) 

The counterpart chain's `send` extrinsic burns/escrows the *sender's full, un-rounded* balance before dispatch, using the up-scaling conversion (`convert_to_erc20`, a multiply — lossless), so the source-side debit is always for the real requested amount: [3](#0-2) 

On the EVM side, `HyperFungibleToken.send()` burns the caller's tokens unconditionally before dispatch as well: [4](#0-3) 

Because `Precisions`/`ChainConfig.decimals` can differ arbitrarily per chain pair (e.g. benchmarking uses `LOCAL_DECIMALS = 12` vs `EVM_DECIMALS = 18`, a scale factor of `10^6`), any EVM→substrate transfer whose `message.amount` is smaller than `10^(erc_decimals - local_decimals)` (up to `10^6`, `10^12`, etc., depending on registered precision) computes `amount == 0` in `convert_to_balance`, yet `on_accept` proceeds to "mint" or "transfer" zero to the beneficiary and emits `TokenReceived` as if the transfer succeeded. The tokens burned/locked on the EVM side (which uses the real, unscaled `message.amount` and is not decimal-adjusted downward) are permanently gone, and the beneficiary receives literally nothing.

This is structurally identical to the referenced Notional H-3 bug: a value conversion with mismatched precision (`erc_decimals` vs `local_decimals`, analogous to `BALANCER_PRECISION` vs `INTERNAL_TOKEN_PRECISION`) that can round down to zero, with no `require`/revert guard before crediting the recipient, while the corresponding debit on the other side has already been taken for the full amount.

### Impact Explanation
This is a direct, permanent loss of user funds reachable by any unprivileged party performing an ordinary cross-chain `send`/`teleport`. Depending on the configured `Precisions` for a token pair (which can be governance-set to any decimals spread, and pallet registration doc explicitly supports arbitrary decimals like "10-decimal DOT on Polkadot vs 18-decimal DOT on Ethereum"), the dust threshold below which funds are destroyed can be economically meaningful (e.g., with a 10^12 scale factor, any transfer under 1 unit of the 12-decimal asset, worth real money at 18-decimal ERC20 precision, is annihilated). There is no recovery path: `on_timeout` only fires for undelivered requests, not for a message that was successfully delivered and just credited zero.

### Likelihood Explanation
Likelihood is low-to-moderate: exploiting this for guaranteed harm to a third party is not directly possible (the sender chooses their own amount), but it is a realistic footgun for normal users, especially:
- Automated systems, contracts, or scripts computing incoming amounts programmatically (e.g., forwarding partial/remaining balances, small residual sweeps) can trigger this without the sender noticing until funds are already burned.
- The larger the `erc_decimals - local_decimals` gap (chosen by the token registrant, not bounded by protocol), the larger the "dead zone" of amounts that silently destroy value — increasing the chance of accidental triggering as adoption of tokens with big decimal gaps grows.

### Recommendation
In `pallet-hyper-fungible-token`'s `on_accept` (and `on_timeout`, which uses the same `convert_to_balance` path), reject the message (or refuse to mint/transfer and instead trigger a refund path) when the computed `amount == 0` after scaling. Symmetrically, the EVM-side `HyperFungibleToken.onAccept` should validate that `message.amount != 0` before minting, and `send()`/`pallet-hyper-fungible-token::send` should validate that the down-scaled destination amount is nonzero before burning/escrowing, so the debit is never taken for a transfer that cannot deliver value.

### Proof of Concept
1. Register a token pair with `local_decimals = 12` and `erc_decimals = 18` (scale factor `10^6`), as used in the pallet's own benchmarking setup (`modules/pallets/hyper-fungible-token/src/benchmarking.rs`, `LOCAL_DECIMALS`/`EVM_DECIMALS`).
2. On the EVM side, a user calls `HyperFungibleToken.send(params)` with `params.amount = 500_000` wei (0.0000000000005 of the 18-decimal token) targeting the substrate chain. `_burn(msg.sender, 500_000)` executes, permanently destroying that balance. [5](#0-4) 
3. The ISMP POST is delivered and `pallet-hyper-fungible-token::on_accept` runs `convert_to_balance(500_000, 18, 12)` = `500_000 / 10^6` = `0`. [1](#0-0) 
4. `on_accept` proceeds to mint/transfer `0` to the beneficiary and emits `TokenReceived { amount: 0, .. }` as a "successful" delivery — no revert, no error. [6](#0-5) 
5. Net result: 500,000 wei of real ERC20 value is burned on the EVM chain; the beneficiary receives zero tokens on the substrate chain, with no recovery mechanism.

**Uncertainty note:** I could not confirm from the indexed code whether `<T as Config>::NativeCurrency>::transfer` or `Assets::mint_into`/`transfer` in this runtime silently succeed as no-ops for a zero amount or return an error (some Substrate currency implementations reject zero-value transfers). If a zero-value transfer/mint were to error out, the message delivery itself would fail and could potentially be retried/timed-out instead of silently "succeeding" with zero credit — this would reduce (but not eliminate, since the source-side burn already happened before any of this) the severity of the impact. A Devin session with full repository/build access would be needed to trace the exact `NativeCurrency`/`Assets` trait implementations configured in the runtime to confirm this behavior definitively.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
