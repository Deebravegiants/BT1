### Title
Unbounded `keys` array in `DispatchGet`/`GetRequest` allows an unprivileged dispatcher to force unbounded proof-verification work in `pallet-ismp::handle_unsigned` - (File: `evm/src/core/EvmHost.sol`, `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`EvmHost.dispatch(DispatchGet)` and pallet-ismp's `dispatch_request(DispatchRequest::Get(...))` accept a caller-supplied `keys: bytes[]` / `Vec<Vec<u8>>` with no length (or per-key size) limit before committing the request and emitting it for relaying. Because any GET request must eventually be answered by a `GetResponse` or a `GetRequestTimeout` that is delivered through `pallet_ismp::Call::handle_unsigned`, and that call is fully executed inside `ValidateUnsigned::validate_unsigned` (i.e., during transaction-pool validation on every full node, for free, before any fee is charged), an attacker can dispatch a GET request with an extremely large `keys` array to force disproportionate non-membership/state-proof verification work onto every node validating the eventual timeout/response extrinsic. This mirrors the reported CoreDAO/geth bug class: an array-sized user input (`topics` there, `keys` here) is not bounded at the point of intake, only downstream during expensive processing.

### Finding Description
- `EvmHost.dispatch(DispatchGet)` builds a `GetRequest` directly from the caller-supplied `get.keys` array with no cap on `keys.length` or per-key size, then commits it: [1](#0-0) 
- The Substrate-side dispatcher does the same for `DispatchGet.keys` before calling `Pallet::<T>::dispatch_request`, again with no bound: [2](#0-1) 
- `DispatchGet.keys` is documented as an arbitrary `Vec<Vec<u8>>`/`bytes[]` of raw storage keys with no stated limit: [3](#0-2) 
- Once dispatched, GET requests are only resolved via `GetResponse` or `GetRequestTimeout` messages submitted as **unsigned** extrinsics through `pallet_ismp::Call::handle_unsigned`. Crucially, `ValidateUnsigned::validate_unsigned` does not merely check a lightweight signature — it calls `Self::execute(messages.clone())`, i.e., it runs full message execution (including proof verification over all keys in the message) during mempool validation, for every node, before the extrinsic is even included in a block: [4](#0-3) 
- The call itself is documented as executing "for free" as an unsigned transaction: [5](#0-4) 
- On the EVM handler side, `handleGetResponses` similarly loops over every response leaf (and its associated `values`, which mirror the request's `keys`) to build MMR leaves before verifying the multiproof, with the expense/complexity growing along with the number of keys used to build the original request: [6](#0-5) 

Because the number of keys in a GET request is only implicitly bounded by extrinsic/calldata size limits (not by an explicit, cheap, early check), a dispatcher can construct a request whose downstream proof verification (non-membership proofs for a timeout, or storage-value verification for a response) is disproportionately expensive relative to the trivial cost of dispatching the GET request itself.

### Impact Explanation
An unprivileged caller (any contract or account able to call `dispatch(DispatchGet)` on `EvmHost` or the Substrate `read_state`/`dispatch_request` entrypoint) can create GET requests with maximal `keys` arrays. When these requests time out or receive responses, the resulting `handle_unsigned` extrinsic is executed in full during `validate_unsigned` on every full node in the transaction-pool validation path — a computationally heavy step that runs for free and prior to any economic cost being charged. Repeated submission of such requests (or their timeouts/responses) could degrade node performance across the network, delaying legitimate message delivery — a route-unable-to-deliver-messages condition consistent with the report's DoS class. This satisfies the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Dispatching a GET request with a large `keys` array requires no special privilege — it is a normal, permissionless dispatcher call, and the cost to the attacker is limited to whatever gas/fee is charged for the dispatch call itself, not for the (larger) downstream verification cost. The downstream execution during `validate_unsigned` runs on every node attempting to relay/validate the corresponding timeout or response, making this an amplification vector rather than a one-off cost to the attacker.

### Recommendation
Enforce an explicit, low-cost limit on the number of keys (and/or total byte size of `keys`) at the earliest possible point — i.e., inside `EvmHost.dispatch(DispatchGet)` and `pallet_ismp::dispatcher::dispatch_request` for the `Get` variant — rejecting requests whose `keys.length` (or cumulative key size) exceeds a configured maximum before any commitment is stored or the request is emitted for relaying. This prevents the expensive downstream path (proof verification during `validate_unsigned`) from ever being reached with oversized inputs, analogous to enforcing the topic-count limit during `FilterCriteria` unmarshaling rather than later during filtering.

### Proof of Concept
1. Call `EvmHost.dispatch(DispatchGet)` (or the Substrate `read_state` extrinsic) with a `keys` array containing the maximum number of entries permittable by calldata/extrinsic size limits (e.g., tens of thousands of 52-byte entries), each requesting an arbitrary counterparty storage key.
2. The request is committed with no rejection, since `dispatch()` performs no length check on `get.keys` [7](#0-6) .
3. When the request times out (or is answered), the corresponding `GetTimeoutMessage`/`ResponseMessage` is submitted to Hyperbridge via `pallet_ismp::Call::handle_unsigned`.
4. Every node in the network that receives this unsigned extrinsic executes `Self::execute(messages.clone())` inside `validate_unsigned` — running full non-membership/state-proof verification across every one of the attacker-chosen keys — before the extrinsic is even accepted into a block [8](#0-7) .
5. Repeating this with many such oversized GET requests can be used to impose disproportionate validation cost on the network relative to the attacker's dispatch cost.

**Note on verification limits:** I was not able to fully inspect `modules/pallets/state-coprocessor/src/impls.rs::handle_get_requests` (only located it via grep, could not retrieve its full body through the index), so I cannot confirm whether the state-coprocessor pallet already imposes its own key-count cap when generating state proofs for the Substrate side. This should be checked directly in the repository, ideally via a full Devin session, since the index used here may not include the full file contents.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }
