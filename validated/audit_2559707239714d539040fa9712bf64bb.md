Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` identity that is handed to the app's webhook handler — and that the handler is expected to trust as "which tenant this event belongs to" — comes from the `shopify-shop-domain` HTTP header, which is never included in the HMAC computation. This breaks the intended binding: `hmac_valid(raw_body) == true` is treated as equivalent to `shop_header == true_originating_shop`, but those are two independent, unlinked pieces of data.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `hmac` and `to_signable_string`. For webhooks, `to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop` accessor, by contrast, is read straight from an unauthenticated header and is never mixed into the signable string: [2](#0-1) 

`Registry.process` validates only this HMAC-over-body check, then immediately trusts `request.shop` (along with `topic`/`webhook_id`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The library's own documentation confirms the intended contract — that calling `process` "will verify the request did indeed come from Shopify" — and instructs app authors to trust `data.shop` as "The shop domain of the webhook" without any further verification, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. Since `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) only ever hashes `verifiable_query.to_signable_string` (the body) with the app's secret, the `shop` header can be swapped freely without invalidating the signature, as long as the body itself is unchanged.

This is exactly the identity-binding failure described in the report's bug class: a field that is *acted on* (the shop the event is attributed to) is not covered by the authenticity check (the HMAC), so `shop_header == originating_shop` no longer holds after the check passes.

### Impact Explanation
An attacker who can obtain any single valid `(raw_body, hmac)` pair — trivially available to any developer/merchant who installs the app on their own store and receives one real webhook from Shopify — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g. a victim merchant's domain). `Registry.process` will pass HMAC validation (the body is unmodified and signed with the correct secret) and will hand the handler a `WebhookMetadata` object claiming the event is for the victim shop. Any host application that follows the documented pattern (using `data.shop` to select which tenant's records to create/update/delete, e.g. `orders/create`, `app/uninstalled`, `shop/redact`) will process attacker-supplied event data under the victim's tenant context — a cross-tenant data-integrity/confidentiality breach purely through this gem's documented API, satisfying the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required beyond what any ordinary app install already grants (one legitimate webhook delivery). The endpoint is by definition internet-reachable (Shopify must be able to POST to it), and the vulnerable trust pattern (`data.shop`) is the one explicitly documented and recommended by this gem's own usage docs, making the vulnerable pattern the "correct" way to use the library rather than a misuse.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting an unauthenticated header:
- Include the `shopify-shop-domain` (and ideally `webhook-id`, `topic`) header value in the string that is HMAC-verified, or
- Require/encourage callers to cross-check `request.shop` against the shop associated with the session/webhook subscription they registered, before dispatching to the handler, or
- At minimum, document prominently that `data.shop` is not authenticated by `Registry.process` and must be independently validated by the host application (e.g., against a known list of installed shops) before being used for any tenant-scoping decision.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 123, ...}` (attacker-controlled order content since it's their own store)
3. Attacker captures this raw body and its valid HMAC.
4. Attacker POSTs to the same webhook endpoint, replaying the identical body and HMAC, but changes the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes the raw body — validation succeeds.
6. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...attacker content...}, ...)`.
7. Any host application logic that uses `data.shop` to select/create/update records for that tenant now operates on the victim's tenant using attacker-supplied data — a cross-tenant integrity/confidentiality violation achieved entirely through this gem's documented `Registry.process`/`WebhookMetadata` contract.
