### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, but exposes `shop` (and `topic`, `api_version`, `webhook_id`) as separate, unauthenticated header values that are trusted as-is by `Registry.process` and forwarded to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
```
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`Utils::HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string`: [2](#0-1) 

Meanwhile, `Request#shop` is read directly from an attacker-controllable header, independent of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches the handler using this unauthenticated `shop` value, with no check that it matches the shop that actually produced the signed body: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop that produced the HMAC-signed body`. Because the header is not part of `to_signable_string`, this equality is never checked — only "HMAC(body) is valid for *some* shop that shares this app's `client_secret`" is checked, not "HMAC(body) was produced for *this* shop-domain."

Webhook signing secrets (`api_secret_key`) are shared across all shops that have a given app installed — Shopify signs every shop's webhook payload with the same per-app secret. This means any unprivileged user who installs the target app on their own (attacker-owned) shop can trigger a webhook, capture a validly-signed `(body, hmac)` pair, and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: <victim-shop>`.

### Impact Explanation
Any host application that uses `request.shop` (or the `shop` field of `WebhookMetadata`) to key data updates, cache invalidation, session lookups, or other per-tenant business logic — which is the intended and documented use of this field — can be made to apply attacker-controlled data under a victim shop's identity. This is a cross-tenant boundary violation: the attacker never needs the victim's or the app's secret; they only need their own (legitimately installed) shop and the shared per-app secret they already have via their own webhook deliveries.

### Likelihood Explanation
Requires only that the attacker run their own shop with the target app installed (a normal, unprivileged install) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — both trivially available to any internet user. No access token, `client_secret`, or victim credentials are needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed payload verification (or independently authenticate the shop-domain header against session/shop records established via OAuth) before trusting it in `Registry.process`, so the binding "signed body ⇔ claimed shop-domain" is actually enforced rather than assumed.

### Proof of Concept
1. Install the vulnerable app on an attacker-owned shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook event; capture the raw body and `x-shopify-hmac-sha256` value delivered by Shopify (both valid, signed with the app's shared `api_secret_key`).
3. Replay the exact same body + HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:26-31) succeeds because it only checks the body/HMAC pair.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the host app to act as though the event originated from the victim tenant.
