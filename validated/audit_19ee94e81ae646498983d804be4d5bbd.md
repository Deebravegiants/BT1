### Title
Paymaster trusts Chainlink price without a deviation/sanity bound, enabling drain during oracle mispricing events - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` converts ERC-20 payment amounts into gas cost using two Chainlink `latestRoundData()` feeds (native/USD and token/USD) with only staleness and non-positive checks, no maximum-deviation/sanity bound against a reference price [1](#0-0) . This mirrors the LUNC/Anchor incident's root cause: an oracle reporting a value far from the real market price was accepted at face value with no anomaly guard, letting an unprivileged user extract value at the protocol's expense.

### Finding Description
`_getOraclePrice` only enforces `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`; it applies no bound on how far `answer` may deviate from a trusted reference or from the prior observed price [1](#0-0) . `_tokenPrice` feeds this raw value directly into the token-cost formula used by `estimateTokenCost`/`_erc20Cost` to size how many ERC-20 tokens a UserOperation's sender pays for real, ETH-denominated gas that the paymaster fronts via the EntryPoint deposit [2](#0-1) .

Notably, the contract's own security-model comment elsewhere in the file explicitly names this exact risk class — "a malicious oracle" — and states the mitigation relies on clients voluntarily "keeping permit amounts small," not on any on-chain deviation check [3](#0-2) . By contrast, the project's own intent-solver pricing path (Uniswap V4 venue pricing) explicitly adds a `referencePrice`/`maxDeviationBps` guard specifically to protect against "a manipulated, stale, or thin pool returning a bad quote" [4](#0-3)  — no equivalent bound exists for the Chainlink feeds consumed by `SimplexPaymaster`.

If a token/USD or native/USD Chainlink feed reports an anomalous but fresh, positive price — the same fact pattern as LUNC's oracle briefly reporting $5 against a much lower real value during the Terra 2.0 migration — any unprivileged UserOperation sender reaching `_validatePaymasterUserOp`/`postOp` can pay a drastically undervalued amount of the ERC-20 token for real gas sponsorship, draining value from the paymaster's EntryPoint deposit/treasury over repeated transactions, all without needing governance, a compromised relayer, or any privileged role.

### Impact Explanation
This is a real, unbacked economic loss vector: the paymaster fronts genuine ETH-denominated gas to the EntryPoint but collects ERC-20 tokens priced off a momentarily wrong-but-valid oracle reading, so the treasury/deposit is drained relative to true value — directly analogous to Anchor's $800k free lending against a wrong LUNC price. Because this reaches production paymaster funds through a single, unprivileged UserOperation, it satisfies the "concrete theft of funds" bar.

### Likelihood Explanation
Requires a genuine but anomalous Chainlink round (a real-world precedent class, as in the LUNC case) — not an attacker directly manipulating the feed. It is not attacker-controlled at will, but the contract has no on-chain defense (deviation cap, circuit breaker, TWAP cross-check) beyond staleness/positivity, and the mitigation documented in the code is an off-chain client convention (small permit amounts), not an enforced protocol invariant, so exposure is bounded only by voluntary client behavior rather than contract logic.

### Recommendation
Add a maximum per-round deviation bound (or a rolling TWAP sanity check) against the previously accepted oracle price for both `nativeOracle` and each token's `tokenOracle` in `_getOraclePrice`, reverting (or falling back to a governance-set floor/ceiling) when the deviation exceeds a configurable threshold — mirroring the `maxDeviationBps` guard already used for the Uniswap V4 venue pricing path.

### Proof of Concept
1. A Chainlink feed used by `SimplexPaymaster` (native/USD or token/USD) reports a fresh, positive but anomalously mispriced value during a market dislocation (analogous to the LUNC oracle reporting $5).
2. `_getOraclePrice` passes the value through unchecked beyond staleness/sign [1](#0-0) .
3. Any user submits a UserOperation using mode 0x00/0x02 paymasterData; `_tokenPrice` computes a token cost using the mispriced feed [2](#0-1) .
4. The paymaster sponsors real ETH gas from its EntryPoint deposit while collecting a token amount far below its true USD value, repeatable across multiple UserOperations until the anomaly clears — draining paymaster funds analogous to Anchor's $800k extraction.

```text
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
