### Title
Webhook `shop-domain` header is trusted by the app handler without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body alone and then hands the header-derived `shop` straight to the app's webhook handler as the trusted tenant identifier, without the HMAC ever binding body-to-shop.

### Finding Description
`Webhooks::Request` exposes `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` header: [1](#0-0) 
but the HMAC is computed and verified only over the raw body: [2](#0-1) 
`Registry.process` verifies this body-only HMAC and then constructs `WebhookMetadata` using `request.shop`, which the documented app-handler contract treats as the authoritative tenant for downstream side effects (enqueuing jobs, looking up shop records, etc.): [3](#0-2) [4](#0-3) 

This breaks the intended binding `hmac_signed_bytes == bytes_the_handler_acts_on`: the signature only proves the body originated from Shopify using this app's shared `client_secret`, it proves nothing about which shop the body belongs to. The `shop` value used for authorization/tenant-scoping decisions (`data.shop` in the documented handler pattern) is disjoint from the signed content.

### Impact Explanation
Because the app's `client_secret` (and thus the HMAC key) is shared across every shop that has installed the app, any shop that legitimately installs the app is an "unprivileged internet user" relative to other tenants, yet can obtain valid `(body, hmac)` pairs for their own webhooks. If they replay a genuine `(body, hmac)` pair while substituting the `shop-domain` header for a victim shop, `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. For any handler that uses `data.shop` to select which tenant's records to update/create/delete based on `data.body` (the pattern explicitly recommended in `docs/usage/webhooks.md`), this allows cross-tenant data injection/corruption using another merchant's identity — a cross-tenant access violation.

### Likelihood Explanation
Exploitability depends on: (1) the attacker being able to install the target app on their own shop (a normal, unprivileged action for any Shopify merchant/dev store), (2) obtaining a webhook whose body content does not itself carry the shop identity conflicting with a victim (many webhook topics, e.g. `app/uninstalled`, empty-body test webhooks, or filtered payloads via `fields`, are shop-content-agnostic), and (3) the target app trusting `WebhookMetadata#shop` for authorization as the docs suggest. This is a realistic but not universal path — it requires a specific combination of webhook topic/body shape and handler logic, so likelihood is moderate rather than trivial.

### Recommendation
Do not treat the `shop-domain` (or `topic`/`webhook_id`/`api_version`) headers as authenticated data based solely on the body HMAC. Either include these header values in the signable string(s) actually verified, or require the app to independently confirm that the `shop` in the webhook maps to an installation whose access token/session was already established, rather than trusting the header value implicitly for tenant-scoped writes. At minimum, document explicitly (beyond the current guidance) that `data.shop` is not itself HMAC-bound and must not be used as the sole tenant-authorization key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, giving Shopify's servers the ability to deliver genuine webhooks signed with the app's `client_secret`.
2. Attacker registers for a topic whose payload is shop-agnostic or configures `fields`/`filter` such that the delivered body (e.g. `{}` for `app/uninstalled`) is generic.
3. Attacker captures the legitimate request: raw body `B` and header `x-shopify-hmac-sha256: H` (a valid signature of `B` under the shared `client_secret`), as computed identically to: [5](#0-4) 
4. Attacker POSTs to the app's public webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [6](#0-5) 
6. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)` and, following the documented pattern of using `data.shop` to scope side effects, performs an action against the victim tenant using attacker-controlled body content — a cross-tenant action performed under the victim's identity without any credential belonging to the victim.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
