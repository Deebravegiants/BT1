This confirms the key asymmetry: in `AuthQuery` (OAuth callback), `shop` is explicitly included in `to_signable_string` and therefore bound by the HMAC verified in `HmacValidator.validate` [1](#0-0) . But in `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, so `shop`, `topic`, `webhook_id`, and `api_version` headers are never covered by the HMAC computation [2](#0-1) .

### Title
Webhook `shop` domain is trusted for tenant routing without being bound to the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)` [3](#0-2) , and that validator computes the signature only over `request.to_signable_string`, which for `Webhooks::Request` is the raw HTTP body (`@raw_body`) [4](#0-3) . The `shop` value, read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header [5](#0-4) , is never part of the signed content, yet it is passed straight into `WebhookMetadata.shop` and handed to the app's handler as the identifier of which tenant/shop the event belongs to [6](#0-5) . The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6) , which overstates what is actually verified — only body integrity, not the shop attribution.

### Finding Description
The identity binding that should hold is: `hmac_valid(request) ⇒ shop_header == shop_that_authored(raw_body)`. Because `to_signable_string` excludes the `shop` header, this equality is not enforced anywhere in the gem. Contrast this with `Auth::Oauth::AuthQuery`, where `shop` is explicitly folded into `to_signable_string` and therefore is cryptographically bound to the HMAC before `Session.from` uses it to construct a session [1](#0-0) . The webhook path has no equivalent binding for `shop`, `topic`, `webhook_id`, or `api_version` — an attacker who obtains any one raw body + valid HMAC pair signed with the app's own `api_secret_key` (e.g. by capturing a genuine webhook delivered to their own store, which they legitimately control) can resubmit that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different (victim) shop. `HmacValidator.validate` will report success because it only recomputes the digest over `raw_body` [8](#0-7) , and `Registry.process` will dispatch to the handler with the attacker-chosen `shop` value as if Shopify itself vouched for that association [9](#0-8) .

### Impact Explanation
This crosses a tenant boundary within any multi-tenant app built on this gem: the `shop` field is the sole tenant discriminator the library hands to `WebhookHandler#handle`, and the documented example immediately uses it to route work per-shop (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [10](#0-9) . An attacker who is any unprivileged internet user with a legitimate (even trial) shop installation of the same app can craft webhook deliveries that the app will process under a different merchant's identity — e.g., causing data belonging to shop A's payload to be recorded/acted upon as shop B's data, or triggering shop-scoped side effects (billing, entitlements, data writes) against a victim tenant. This is a cross-tenant confusion enabled purely by a field that is acted upon but not covered by the HMAC, matching the required High-severity class.

### Likelihood Explanation
The webhook HTTP endpoint is by necessity public (Shopify must be able to reach it over the internet), so no privileged access is needed to submit requests to it. The only "external condition" is that the attacker needs one valid `(raw_body, hmac)` pair, which is trivially obtainable by installing the app on any shop they control and capturing one of their own real webhook deliveries — no secret material is required since the attacker never needs to compute an HMAC themselves. This makes the attack practical for any developer/tester with a normal store, not just someone with elevated access.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) to the same authenticated context the app relies on for tenant identity: rather than trusting the `x-shopify-shop-domain` header as authoritative, cross-check it against a shop the app has an active, previously-established session/webhook registration for, or extend `to_signable_string`/verification so that the header set is included in what's authenticated, mirroring what `AuthQuery#to_signable_string` already does for OAuth. At minimum, update the documentation so it does not claim the full request (including the shop attribution) is verified, when in fact only the raw body's integrity is checked.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body plus its legitimate `x-shopify-hmac-sha256` header — both are computed by Shopify using the app's real `api_secret_key`, which the attacker never needs to know.
2. Replay that exact request to the app's public webhook endpoint, but change only the `x-shopify-shop-domain` header to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the digest solely from `request.to_signable_string` (`= @raw_body`) [4](#0-3)  — the unchanged body still matches the unchanged HMAC, so validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [9](#0-8)  and processes the attacker's payload as if it belonged to the victim shop.
