### Title
Chain-agnostic MIN-path Emporium proof replay when `signerAddress == address(0)` — ([File: contracts/CircomDataBuilder.sol], [File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
For Emporium transactions routed through `formInputEmporiumMin` (`circomData.erc20TokenAddresses.length == 0`), the circuit's public inputs contain no chain or contract identifier, and when `EmporiumStack.signerAddress == address(0)`, `verifyWallet` returns before ever computing the EIP-712 `_hashTypedDataV4` domain hash. This means neither the SNARK public-input vector nor the Emporium-level signature check binds the transaction to a specific `(chainid, verifyingContract)` pair, so an identical `(a,b,c,circomData)` tuple accepted on chain A is also accepted on an identically-deployed chain B.

### Finding Description
**Equality that should hold but doesn't:** for any accepted `runAction` invocation, the tuple `(proof, circomData)` valid on chain A with `chainid = X` should be invalid (or at least distinguishable) when replayed on chain B with `chainid = Y ≠ X`, for an identically-addressed Emporium deployment. In this MIN-path/relay-only branch, that equality is *not* broken by any code — i.e., the two sides are actually equal (the same input is valid on both), which is the vulnerability.

Trace:
1. `HinkalHelper.performHinkalChecks` builds the public-input vector via `CircomDataBuilder.formInputForCircom(block.chainid, hinkalAddress, circomData)` [1](#0-0) . When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, it dispatches to `formInputEmporiumMin`, which builds the input vector as `[emporiumMessage, timeStamp, calldataHash]` — `chainId` and `verifyingContract` are silently dropped and `getSignedMessageHash` (which is the only place `chainId`/`verifyingContract` get folded in) is never called [2](#0-1) .
2. The corresponding circuit, `MainEVMCircuitMin`, only constrains `outTimeStamp` and `calldataHash` as public signals and outputs `message = Poseidon(messageSeed)`; it has no `signedMessageHash`/chain-binding signal at all [3](#0-2) . `VerifierEVMMin0v4` accepts exactly 3 public inputs, matching this reduced set [4](#0-3) .
3. `EmporiumUpgradeable.runAction` decodes `stack` and calls `verifyWallet(stack, circomData)` [5](#0-4) .
4. `verifyWallet` marks `usedMessages[circomData.emporiumMessage] = true` (a per-contract-instance storage slot, not globally shared across chains) and then, if `stack.signerAddress == address(0)`, returns immediately — before ever calling `_hashTypedDataV4`, i.e. before the EIP-712 domain separator (which contains `block.chainid` and `address(this)`) is even computed [6](#0-5) .
5. When `signerAddress == address(0)`, every operation in `stack.ops` — regardless of `op.invokeWallet` — falls into the "stateless" `else` branch and is executed directly as `op.endpoint.call{value: op.value}(op.callData)` from the Emporium contract itself, spending the Emporium's own pooled ETH/token balance [7](#0-6) .

**Root cause:** with `erc20TokenAddresses.length == 0` and `signerAddress == address(0)`, none of: (a) the circuit's public inputs, (b) the EIP-712 domain check, (c) any nullifier or root check (there are no tokens/nullifiers in this path), constrain the transaction to a specific chain or a specific Emporium contract instance. The only per-transaction replay guard is `usedMessages[emporiumMessage]`, which is local storage to one deployed contract and does not extend across separately deployed (even identically-addressed) instances on other chains.

**Attacker's exact call:** the attacker (any unprivileged, allowed-recipient-routed caller through `Hinkal.transact`) generates one MIN-path proof/`circomData` where `emporiumMessage`, `timeStamp`, `calldataHash` are the only public signals, with `stack.signerAddress = address(0)` and `stack.ops` containing calls that pay out value from the Emporium's balance to attacker-controlled endpoints. This is accepted on chain A. The attacker then submits the byte-for-byte identical `(a,b,c)` proof and `circomData` to `Hinkal.transact` on chain B (same verifying key/bytecode, independent `usedMessages` mapping, independent Merkle tree/roots), and it passes `verifyProof`, `rootHashExists` (assuming the same `rootHashHinkal` also exists there — trivial if chain B's tree state mirrors chain A's, e.g. deterministic/forked deployments), and `verifyWallet`'s early return, re-executing the same value-extracting ops a second time.

**Why existing guards fail:** `performHinkalChecks`'s calldata-hash integrity check only validates internal consistency of `circomData` fields against `circomData.calldataHash`, not chain identity [8](#0-7) . `dimensionsCheck`/`checkOnchainCreation` don't reference chain/contract identity either. `rootHashExists` is per-chain Merkle-tree state and does not prevent replay across independently-mirrored trees. `usedMessages` is per-instance. `verifyWallet`'s EIP-712 domain — the one place that would have bound `block.chainid` and `address(this)` — is unreachable in this branch.

### Impact Explanation
An attacker can replay a single generated proof to trigger duplicate execution of arbitrary `op.endpoint.call{value: op.value}(op.callData)` invocations funded from the Emporium contract's own balance on every additional identically-deployed chain, extracting value that was never re-authorized or re-proven for that chain. This constitutes proof/message verification bypass and theft of pooled protocol/user funds held in the Emporium contract, matching the Critical category ("proof or nullifier verification bypass" / "direct theft of shielded or in-flight user funds").

### Likelihood Explanation
Preconditions: (1) Hinkal/Emporium is deployed with identical bytecode (and ideally identical addresses) across multiple chains — standard practice for cross-chain privacy protocols; (2) an Emporium-min transaction exists where `signerAddress == address(0)` (relay-only mode, explicitly supported by the code, not merely theoretical); (3) `rootHashHinkal` chosen by the attacker must exist as a valid root on the target chain's tree, which is easy to satisfy if trees are mirrored or if the attacker crafts a MIN-path proof independent of tree state changes (MIN path has zero nullifiers/tokens, so this constraint is comparatively weak). Attacker cost is a single proof generation, replayable an unlimited number of times across any number of chains sharing the same verifying key.

### Recommendation
Include `block.chainid` and `address(this)` (or equivalently a domain-bound hash) as a public input in `formInputEmporiumMin`/`MainEVMCircuitMin`, and remove the early return in `verifyWallet` for `signerAddress == address(0)` — instead compute and check a domain-bound hash of `circomData.calldataHash`/`emporiumMessage` unconditionally, or fold `chainId`/`verifyingContract` directly into `circomData.calldataHash`'s pre-image so the calldata integrity check enforces chain binding for all Emporium paths, not only the ones using `getSignedMessageHash`.

### Proof of Concept
Foundry fork test plan:
1. Deploy identical `Hinkal` + `EmporiumUpgradeable` + `VerifierEVMMin0v4` stacks on two simulated chains (`vm.chainId` toggled between calls, same contract addresses/bytecode/state via `vm.selectFork`/manual state cloning to mirror `rootHashHinkal`).
2. On chain A (`block.chainid = X`), locally generate a valid MIN-path proof with `circomData.erc20TokenAddresses.length == 0`, `EmporiumStack.signerAddress = address(0)`, and `stack.ops` = one call to an attacker-deployed endpoint that forwards `op.value` (funded from Emporium ETH balance) to the attacker.
3. Call `Hinkal.transact` on chain A; assert success and attacker balance increased by `op.value`.
4. Switch `block.chainid` to `Y` on the mirrored instance (fresh `usedMessages` mapping, same `rootHashHinkal` present in tree), replay the identical `(a,b,c,dimensions,circomData)`.
5. Assert `Hinkal.transact` succeeds again (no revert on `UsedMessage`, `Invalid Proof`, or `InvalidSignature`) and attacker balance increases by `op.value` a second time — proving the equality "input valid only on chain X" ≠ actual behavior "input valid on chain X and chain Y".

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
