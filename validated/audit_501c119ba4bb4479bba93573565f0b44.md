### Title
NFTX Duplicate-Receiver Analog: Webhook `shop`/`topic` identity not bound by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The NFTX bug class is "an identifier that downstream logic trusts is never checked/bound at the point of verification." The reachable analog here is that `ShopifyAPI::Webhooks::Request` only signs the raw body over HMAC, while `shop` and `topic` — which the registry uses to route and to construct the trusted `WebhookMetadata` handed to app handlers — are taken from unauthenticated HTTP headers that are outside the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` and `topic` accessors are parsed straight from headers with no cryptographic binding: [2](#0-1) .

`Utils::HmacValidator.validate` computes and compares the signature purely against `verifiable_query.to_signable_string` (i.e., the body only) using the app's single, global `api_secret_key`: [3](#0-2) .

`Webhooks::Registry.process` calls this validator and then, once it passes, unconditionally trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed to the app's registered handler: [4](#0-3) .

Because the secret is app-wide (not per-shop) and the signature covers only the body bytes, any body+hmac pair that is valid for *one* shop's webhook delivery is equally valid for *any* other shop's webhook delivery — the HMAC does not bind `shop` (tenant identity) or `topic` to the payload it authenticates.

### Impact Explanation
This breaks the identity equality that the report's bug class targets: the value verified (raw body bytes, checked against the shared secret) is not the value the application trusts (`shop`, used by `handler.handle` to attribute the event to a specific merchant/tenant). An attacker who owns any Shopify shop (freely obtainable, no privilege required) can capture one authentic `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to their own webhook endpoint for a mundane event (e.g. `orders/create`), then replay that exact body/hmac to the target app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header for a victim shop. `HmacValidator.validate` still passes because it never inspects those headers, and the app's webhook handler will process the forged event believing it originates from the victim tenant — a cross-tenant data-confusion / cross-tenant access condition (Critical per the given rubric).

### Likelihood Explanation
High/likely: no access token, no `client_secret`, no TLS interception, and no privileged account are required — only ownership of any store that installs the target app (or any shop that can trigger a webhook to be delivered, which is trivial and free), plus the ability to send an HTTP POST to the app's known, public webhook URL with modified headers.

### Recommendation
Bind the tenant/topic identity into the authenticated material, e.g. include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (or verify them out-of-band against a per-shop record established during OAuth, not from the unauthenticated header alone), so a valid signature for one shop's payload cannot be replayed as if it belonged to another shop/topic.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (free/trivial) and triggers any webhook-generating event (e.g., place a test order) to receive one legitimate webhook delivery:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Raw body: `<json>`
2. Attacker resends the exact same raw body and HMAC header value to the target app's public webhook endpoint, but with the header changed to:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` using the app's `api_secret_key` — identical to step 1, so it returns `true`: [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker-controlled JSON>, ...)`, causing the app to act on forged data under the victim tenant's identity: [6](#0-5) .
