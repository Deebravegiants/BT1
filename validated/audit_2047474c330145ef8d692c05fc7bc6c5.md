## Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, but the `shop` identity that the host application later uses to route/attribute the webhook data is read from an unauthenticated HTTP header that is never included in the signed material. Because all shops installed on a given app share the same `api_secret_key`, this breaks the binding "bytes verified by HMAC" == "shop identity acted on", allowing a malicious but unprivileged merchant (who has installed the app on their own store and thus can legitimately obtain valid `(body, HMAC)` pairs) to replay that valid pair while claiming an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the signature only over `to_signable_string` (i.e., the raw body) using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly this body-only HMAC check and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the host application's handler, with no further correlation between the verified bytes and the asserted shop: [4](#0-3) 

Because a single `api_secret_key` is shared by every shop that has installed the app, HMAC validity proves only "this body was signed by the app's secret" — it does not prove "this body belongs to the shop named in this header." The equality that should hold is:

`shop asserted in header == shop that the HMAC-verified body was generated for`

This equality is never checked. Any actor who can obtain one legitimately signed `(raw_body, HMAC)` pair — trivially available to any merchant who installs the app on their own store and observes an outgoing webhook — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. The HMAC still validates (it only checks the body), and `Registry.process` hands the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: a merchant with no relationship to the victim's data can cause the host application to process webhook data under the victim shop's identity, because the shop attribution is not part of the authenticated content. Depending on how the host app keys per-tenant storage/side effects off `WebhookMetadata#shop`, this can lead to cross-tenant data corruption, unauthorized state changes, or misattributed application events for a shop the attacker does not control.

### Likelihood Explanation
High: the prerequisite (a legitimately signed webhook body/HMAC pair) is obtainable by any unprivileged actor who installs the target app on their own store — a routine, unprivileged action requiring no access to `api_secret_key`, no access token, and no TLS interception. Forging the header value is trivial HTTP manipulation against the app's public webhook receiver endpoint.

### Recommendation
Bind the asserted `shop` to the authenticated payload instead of trusting a bare header: include the `shop` (and `webhook_id`/`topic`) in the signable string used for HMAC validation, or independently correlate the header-provided shop against a value embedded in and covered by the signed body/topic-specific secret, so a replay with a substituted `shop` header fails validation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a genuine webhook event (e.g., updates a resource) and captures the resulting HTTP request the app receives: raw body `B`, and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker crafts a new POST to the app's webhook endpoint using the same body `B` and same HMAC header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` → `Utils::HmacValidator.validate` passes because it only checks `B` against `H` with the shared secret [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled data as if it originated from the victim shop.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
