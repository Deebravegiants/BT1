### Title
Blacklistable/pausable input tokens permanently freeze escrow for the entire order in `_withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` iterates over all tokens escrowed for an order commitment and calls `IERC20.safeTransfer` for each one in a single atomic loop. If any one of the input tokens for that order is a token that can block/deny transfers to the beneficiary (pausable, blacklist/blocklist, e.g. USDT-style denylists), the entire `_withdraw` call reverts, which blocks release of *every other, unrelated* escrowed token for that same order — permanently, if the block condition (e.g. a blacklisted beneficiary or a permanently paused token) never clears.

### Finding Description
`_withdraw` releases escrow for a cross-chain (or same-chain) order by looping over `body.tokens` and unconditionally transferring each to the beneficiary: [1](#0-0) 

There is no isolation between tokens in the loop — a revert from any single `safeTransfer` call (caused by a paused token, a blacklisted/denylisted beneficiary address, or any other transfer-blocking mechanism) reverts the whole function, including the `_orders[...] -= amount` accounting and the release of the other, unaffected tokens in the same order.

This function is reached from the ISMP delivery path (`onAccept`) when a `RedeemEscrow`/withdrawal message arrives from the destination chain after a solver fills a cross-chain order: [2](#0-1) 

Per the relayer-gating comment in the same contract, a revert from the module callback is recorded by the host as an undelivered message that "the authorised relayer can resubmit": [3](#0-2) 

That resubmission model only recovers from *transient* failures. If the transfer failure is not transient — e.g. the beneficiary address is permanently blacklisted by the token issuer (common with USDT/USDC-style compliance denylists), or the token is permanently paused/deprecated — no amount of relayer resubmission will ever let `_withdraw` succeed. Since all tokens for that order commitment are drained through the same atomic call, the unrelated (non-blacklisted) tokens escrowed for that order are frozen alongside the problematic one, with no code path to skip/quarantine the bad token and release the rest.

### Impact Explanation
An order can escrow multiple distinct input tokens (`order.inputs` is an array of `TokenInfo`). A user or solver placing/filling a multi-token order where one of the tokens is later paused, or where the beneficiary is later blacklisted on just one of the tokens, causes indefinite freezing of the entire escrowed basket for that order — not merely the affected token. This is a permanent loss of access to funds for legitimate counterparties (users/solvers), matching the "permanent freezing of funds" class of impact.

### Likelihood Explanation
Moderate: it requires (a) an order/withdrawal with multiple input tokens where at least one enforces a denylist/pause (real-world tokens like USDC, USDT, and various compliance-gated stablecoins support this), and (b) that condition becoming permanent for the specific beneficiary/token pair (e.g., OFAC-style blacklisting or a token permanently paused/deprecated after being listed). Given Hyperbridge/IntentGateway is permissionless as to which ERC-20 addresses can be used as `order.inputs`/`order.output.assets`, any user or solver can construct such a multi-token order without protocol-level restriction.

### Recommendation
Do not process all escrow releases for an order atomically in a single revert-or-succeed call. Options:
- Wrap each per-token `safeTransfer` in a try/catch (or use low-level `call` and check return data) so a single failing token does not block release of the others; track/queue the failed token+amount for later retry or a separate sweep/claim function.
- Alternatively, allow beneficiaries to specify an alternate recipient address for a stuck token, or provide an escrow-hatch/rescue function gated to the affected commitment so non-blacklisted tokens are not held hostage by one problematic token.

### Proof of Concept
1. User places a cross-chain order with two inputs: `TOKEN_A` (a normal ERC20) and `TOKEN_B` (a USDT/USDC-style token supporting a blacklist), escrowed via `placeOrder` in `IntentGatewayV2`/`ExtrinsicIntents`.
2. A solver fills the order on the destination chain via `_fillCrossChain`, which dispatches a `RedeemEscrow` `WithdrawalRequest` covering both `TOKEN_A` and `TOKEN_B` back to the source chain: [4](#0-3) 
3. Before the message is relayed/settled, `TOKEN_B`'s issuer blacklists the solver (beneficiary) address, or pauses the token.
4. When the withdrawal message reaches `onAccept` on the source chain and calls `_withdraw`, the loop's `safeTransfer` for `TOKEN_B` reverts, reverting the whole call — `TOKEN_A`, which has no transfer restriction, is never released to the solver either: [5](#0-4) 
5. Because the blacklist/pause condition is permanent, every relayer resubmission of the same message fails identically, permanently freezing both `TOKEN_A` and `TOKEN_B` in escrow.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }
