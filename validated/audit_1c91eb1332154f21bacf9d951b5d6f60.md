### Title
Webhook `shop` identity field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request body, but the `shop` value that is subsequently trusted and handed to the host application's handler is read from an HTTP header that is excluded from that HMAC computation. This breaks the identity binding: `shop-authenticated == shop-used-as-tenant-key`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `to_signable_string` to represent exactly what the HMAC was computed over. For webhooks, `to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then dispatches to the app's handler using the unauthenticated `shop` header value: [3](#0-2) 

That value flows directly into `WebhookMetadata#shop`, the field the host app is expected to trust as the tenant identifier for the webhook payload: [4](#0-3) 

Because the HMAC is computed only from the raw body with the shared `api_secret_key`, and the same secret is shared across every shop that installs the app, any unprivileged user who installs the target app on their own shop receives genuine, validly-signed webhooks. Because the shop-domain header is excluded from the signature, that same attacker can replay the captured `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim's `.myshopify.com` domain). `Utils::HmacValidator.validate` will still return `true` because it only recomputes the signature over `raw_body`: [5](#0-4) 

The app therefore processes attacker-controlled body content while believing it originated from — and pertains to — a different tenant (`shop`) than the one that actually sent it.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the host application a `shop` value in `WebhookMetadata` that it presents as authenticated, but that value was never covered by the cryptographic check. Any app that uses this `shop` field to route data into per-tenant storage, trigger per-tenant side effects (e.g. processing `orders/create`, `customers/data_request`, or the mandatory `shop/redact` topic), or to look up/act on another shop's session can be made to associate attacker-supplied webhook content with an arbitrary victim shop, or vice versa — a cross-tenant access/data-integrity break rooted entirely in this gem's verification logic.

### Likelihood Explanation
Likelihood is high for any attacker who is capable of installing the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) — they need no access token, no `api_secret_key`, and no privileged account on the victim shop. They only need to capture one legitimate webhook delivery from their own installation and resend it with a modified shop-domain header to the app's public webhook endpoint.

### Recommendation
Include the shop-domain header (and topic/api-version, if they are meant to be trusted) in the value that is verified, e.g., bind them into the signable string or, at minimum, cross-check that the `shop` claimed in the header corresponds to a shop for which the app currently holds an active session/registration before acting on the payload. Do not treat header-derived fields excluded from `to_signable_string` as authenticated in `WebhookMetadata`.

### Proof of Concept
1. Install the target app (using this gem) on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook topic the app subscribes to; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because `HmacValidator.validate` recomputes it purely from `raw_body` per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
3. Replay the exact same body and HMAC to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the (unchanged) HMAC successfully and invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_controlled_body, ...)`, causing the host app to process attacker-controlled data under the victim's tenant identity.
