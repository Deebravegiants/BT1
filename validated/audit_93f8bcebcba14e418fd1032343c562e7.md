### Title
Unbounded protocol/destination fee basis-points in Tron `IntentGatewayV2.onAccept` `UpdateParams` handler can permanently brick order placement - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2` applies incoming `UpdateParams` governance messages directly to `_params` and `_destinationProtocolFees` without any bounds validation, unlike the canonical EVM implementation (`IntentsBase._validateParams` / `_updateParams`) which explicitly caps `protocolFeeBps` (`< 10_000`), `surplusShareBps` (`<= 10_000`) and per-destination `destinationFeeBps` (`< 10_000`). This mirrors the reported `TokenBridgeBase.sol` pattern of fee setters with no upper bound.

### Finding Description
In the canonical EVM path, `IntentsBase._validateParams` and `_updateParams` enforce bounds before committing new fee parameters: [1](#0-0) 

In the Tron variant, the equivalent `onAccept` branch for `RequestKind.UpdateParams` copies `update.params` into `_params` and `update.destinationFees[i].destinationFeeBps` into `_destinationProtocolFees` with **no call to any validation function** and no `feeBps >= 10_000` guard: [2](#0-1) 

`protocolFeeBps` and `destinationFeeBps` are later used unchecked in `placeOrder`'s fee-reduction arithmetic (`protocolFee = (originalAmount * protocolFeeBps) / 10_000; reducedAmount = originalAmount - protocolFee;`), the same computation pattern shown in the EVM version: [3](#0-2) 

If a `feeBps` value of `10_000` or greater is ever applied (accidental misconfiguration, encoding error, or any process able to reach this authenticated-but-unvalidated path), `protocolFee >= originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows, causing every subsequent `placeOrder` call for that destination/gateway to revert.

### Impact Explanation
Because `placeOrder` reverts for any order once an out-of-range fee is set, this is a denial-of-service on the order-placement route for the affected chain — new intents cannot be created, and cross-chain liquidity routing through this gateway is blocked until governance ships a corrective `UpdateParams` message. This matches the "route unable to deliver messages" / freezing-of-funds class of impact called out in the validation criteria, and is reachable purely through the existing, already-authenticated `UpdateParams` cross-chain message path with no additional privilege escalation, exactly as in the original acknowledged `TokenBridgeBase` finding.

### Likelihood Explanation
Likelihood is Medium: the write path is gated to messages sourced from the Hyperbridge parachain (`request.source == hyperbridge`) and delivered by the host, so it is not exploitable by an arbitrary unprivileged actor. However, unlike the EVM implementation — which was hardened specifically against this class of mistake (see the extensive `testRevert_UpdateParams_DestinationFeeBpsTooHigh` / `testRevert_SetParams_ProtocolFeeBpsTooHigh` test coverage in `IntentGatewayV2Test.sol`) — the Tron fork has silently dropped this safety check, meaning a single malformed or miscalculated governance update (e.g., basis-points vs. percentage confusion, off-by-order-of-magnitude bug in the encoding tooling) is sufficient to trigger the underflow/DoS, with no on-chain guard to catch it.

### Recommendation
Port the same validation used in `IntentsBase._validateParams`/`_updateParams` into the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch: reject `params.protocolFeeBps >= 10_000`, `params.surplusShareBps > 10_000`, and any `destinationFees[i].destinationFeeBps >= 10_000` before committing the update, so the Tron deployment has parity with the audited EVM behavior.

### Proof of Concept
1. Hyperbridge governance (or any process producing a malformed `UpdateParams` payload that reaches the authenticated `onAccept` path) dispatches a `RequestKind.UpdateParams` POST request to the Tron `IntentGatewayV2` with `destinationFees[0].destinationFeeBps = 10_000` (or `params.protocolFeeBps = 10_000`).
2. `onAccept` applies the update unchecked (`evm/tron/contracts/apps/IntentGatewayV2.sol:644-660`), storing the invalid fee.
3. Any subsequent `placeOrder` call for that destination/gateway computes `protocolFee = originalAmount * 10_000 / 10_000 = originalAmount`, then `reducedAmount = originalAmount - protocolFee = 0`... for values above `10_000`, `protocolFee > originalAmount` and the subtraction underflows, reverting the transaction — permanently blocking order placement until another governance message corrects the value.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }

            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
