### Title
Fee-on-transfer / deflationary tokens cause escrow accounting mismatch in Tron `IntentGatewayV2.placeOrder` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits `_orders[commitment][token]` using the nominal (pre-fee) input amount instead of the tokens actually received by the contract. Unlike the mainline EVM `IntentGatewayV2.sol`, which was explicitly hardened against this class of bug, the Tron contract's non-predispatch escrow path lacks the balance-before/balance-after reconciliation, reproducing the exact accounting-mismatch bug class described in the external report for fee-on-transfer/deflationary ERC-20 tokens.

### Finding Description
In the non-predispatch branch of `placeOrder`, tokens are pulled with a plain `safeTransferFrom` and the escrow ledger is incremented by the full (fee-adjusted-only-by-protocol-fee) requested amount, not by what the contract actually received: [1](#0-0) 

Compare this to the mainline (non-Tron) `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf(address(this))` before and after the `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received amount before it is used to compute `reducedInputs`/the commitment/escrow: [2](#0-1) 

The Tron predispatch branch does perform a `balanceOf` check on the *dispatcher* to validate `requiredAmount` was reached, and emits `DustCollected` for any surplus over `requiredAmount`, but it still stores `reducedInputs[i].amount` (derived from the caller-supplied `order.inputs[i].amount`, only reduced by protocol fee) into `_orders`, not the balance actually swept into the gateway: [3](#0-2) 

For a token with a transfer fee (or any token whose `transferFrom` delivers less than the requested `amount`), the gateway's actual token balance after `placeOrder` will be strictly less than the sum of `_orders[commitment][token]` recorded for that order (plus any other orders' escrow already sitting in the same pooled contract balance). This is functionally identical to the reported `DonationVotingMerkleDistributionVaultStrategy.claim` bug: the accounting ledger (`_orders`/`claims`) overstates the actual token balance held by the contract.

### Impact Explanation
When a solver later fills the order and the withdrawal logic (`withdraw`/`_withdraw`, reached via `fillOrder` or cross-chain settlement `onAccept`) transfers out `_orders[commitment][token]` to the solver, the contract will either:
1. Revert due to insufficient balance (denial of service — the user's principal becomes stuck/unfillable, and on the cross-chain path the corresponding source-chain escrow can never be released since the destination fill never completes), or
2. Successfully transfer the recorded (inflated) amount by drawing on token balance that belongs to escrow from *other, unrelated orders* held in the same contract, silently under-funding those other orders and letting the solver (or a colluding user) receive tokens they aren't entitled to.

This is a fund-freezing/fund-theft class issue affecting escrowed user principal in the Intent Gateway, which handles arbitrary ERC-20 assets across chains — a direct token-bridge/intents-escrow accounting bug matching the requested analog scope.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder` with a fee-on-transfer or rebasing/deflationary ERC-20 as an input token — no privileged role or governance action is required. The mainline `evm/src/apps/IntentGatewayV2.sol` and its Foundry test suite (`IntentGatewayV2SameChainTest.sol`, `FeeOnTransferToken` mock) demonstrate this exact scenario was identified and specifically fixed for the primary EVM deployment, confirming fee-on-transfer tokens are a recognized and reachable threat model for this contract family. The Tron deployment, however, was not updated with the same fix, so it remains exploitable whenever such a token is whitelisted/used as an order input on that chain.

### Recommendation
Apply the same balance-before/after reconciliation used in `evm/src/apps/IntentGatewayV2.sol` to the Tron `IntentGatewayV2.sol`:
- In the non-predispatch branch, snapshot `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom`, and use the delta (actual received amount) as the basis for `reducedInputs[i].amount` and the value stored in `_orders[commitment][token]`.
- In the predispatch branch, use the actually-swept amount transferred to the gateway (rather than the nominal `order.inputs[i].amount`/protocol-fee-reduced amount) when crediting `_orders`, consistent with how the mainline contract measures `received` after the sweep and mutates `order.inputs` before computing `reducedInputs`.
- Ensure the commitment hash used for cross-chain settlement is computed from the actual received/escrowed amounts, matching the mainline behavior, so source and destination chains agree on the true escrowed value.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC-20 (e.g., 1% fee, as modeled by the `FeeOnTransferToken` mock used in the mainline test suite: `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2689-2735) as an accepted input token.
2. User A calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}` (no predispatch). `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000e18)` transfers only 990e18 to the gateway due to the 1% fee, but `_orders[commitment][token] += reducedInputs[i].amount` credits (at minimum) close to 1000e18 (line 463 of `evm/tron/contracts/apps/IntentGatewayV2.sol`).
3. Gateway's actual FOT balance is 990e18, but the escrow ledger records ~1000e18 for this order alone.
4. When a solver fills the order and withdrawal releases `_orders[commitment][token]` to the solver, the transfer either reverts (insufficient balance if this is the only order using that token) or succeeds by consuming FOT balance escrowed for other orders in the same contract, permanently freezing or misallocating those other users' funds.
