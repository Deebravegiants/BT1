Audit Report

## Title
Client-controlled `message_id` allows cross-user WebAPI trigger response hijacking in Gateway capabilities handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
The Gateway's `capabilities` handler keys its pending-callback cache (`savedCallbacks`) solely by `MessageBody.MessageID`, which is copied verbatim from the client's JSON-RPC request `ID` with no per-sender scoping, uniqueness check, or collision protection. Any unprivileged user submitting a `web_api_trigger` request can pick a `message_id` colliding with an in-flight victim request, overwriting the victim's callback entry so the DON's later response (which merely echoes the same ID) is delivered to the attacker instead.

## Finding Description
`ValidatedMessageFromReq` sets `m.Body.MessageID = req.ID` directly from the untrusted client request, and `Message.Validate()` only checks length bounds and a null-byte suffix — no uniqueness enforcement exists at any layer (`core/services/gateway/handlers/common/message_util.go:51-52`, `core/services/gateway/api/message.go:61-66`). `HandleLegacyUserMessage` then unconditionally writes `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` without checking for an existing entry at that key (`core/services/gateway/handlers/capabilities/handler.go:411-414`). Later, `HandleNodeMessage` → `handleWebAPITriggerMessage` looks up, deletes, and delivers the response purely by `msg.Body.MessageID` — a value the DON node simply echoes back from the original request — with no verification that the callback's original sender matches the request that produced the response (`core/services/gateway/handlers/capabilities/handler.go:148-162`, `248-267`). The `HandleNodeMessage` sender check only verifies the DON node's identity (`msg.Body.Sender != nodeAddr`), not the original requesting user's identity, so it does not prevent this class of bug. The gateway's per-request flow in `gateway.go:267-288` confirms each HTTP request synchronously registers a callback and awaits a response, matching the race window described in the claim. This matches an explicit acknowledged gap in the code: a TODO in the handler ("apply allowlist and rate-limiting here") and in the test file ("Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated").

## Impact Explanation
This allows an unprivileged user to hijack another user's WebAPI trigger response and/or silently deny the legitimate user their response, mapping to the "cross-user response corruption" impact class. Depending on the trigger response payload, this could leak information intended for a different caller.

## Likelihood Explanation
Exploitation requires only unprivileged access to the gateway's user-facing HTTP endpoint and the ability to choose an arbitrary `message_id` (bounded to reasonable length, no trailing null byte) while racing another in-flight request with the same ID. No special role, credential, or node/operator access is needed — this is directly reachable from the internet-facing gateway API.

## Recommendation
- Scope `savedCallbacks` keys by `(Sender, MessageID)` instead of `MessageID` alone.
- Reject `HandleLegacyUserMessage` requests whose `MessageID` collides with a live entry rather than silently overwriting it.
- Bind delivery in `handleWebAPITriggerMessage` to the original requester's sender/session, not just the shared ID.

## Proof of Concept
1. User A sends a `web_api_trigger` request with `message_id = "X"` to the gateway; `HandleLegacyUserMessage` stores A's callback in `savedCallbacks["X"]`.
2. Before the DON responds, Attacker B sends their own `web_api_trigger` request with the same `message_id = "X"`, overwriting `savedCallbacks["X"]` with B's callback.
3. A DON node responds to A's original request, echoing `message_id = "X"`. `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's response to B.
4. B receives A's trigger response; A's HTTP request in `gateway.go`'s `callback.Wait(ctx)` times out with no response.

This can be verified with a Go unit/integration test in `core/services/gateway/handlers/capabilities/handler_test.go` that calls `HandleLegacyUserMessage` twice with the same `MessageID` but different callbacks/signers, then dispatches a single `HandleNodeMessage` response and asserts which callback receives it.
