### Title
Webhook `shop` identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by HMAC-checking the raw request body, then dispatches the handler using a `shop` value taken from an HTTP header that is never included in that signature. An attacker who has captured any one valid `(body, hmac)` pair (e.g. from a webhook legitimately delivered to a shop the attacker controls) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process attacker-supplied webhook data attributed to a shop of the attacker's choosing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed payload: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the signature purely over `verifiable_query.to_signable_string` (i.e. the body): [4](#0-3) 

`Registry.process` gates on this HMAC check and then forwards `request.shop` — the unauthenticated header value — directly to the handler as the shop identity for the event: [5](#0-4) 

The equality the code implicitly assumes is:
`shop bound by HMAC == shop delivered to handler.handle`

In reality:
`HMAC covers only raw_body` and `shop comes from an unsigned header`, so the two are never cryptographically linked. Because the HMAC secret (`Context.api_secret_key`) is a single app-level shared secret used for every shop's webhooks (not shop-specific), any `(body, hmac)` pair that validates for shop A also validates unchanged for any other `shop-domain` header value, since the header plays no role in signature computation.

### Impact Explanation
This breaks the tenant identity binding that a webhook consumer relies on to know which merchant an inbound event belongs to. An attacker who is able to obtain one genuine `(raw_body, hmac)` pair — trivially possible if they operate any shop that has this app installed and receives webhooks — can replay it to the same public webhook endpoint with a forged `shop-domain` header pointing at a different, arbitrary merchant. Because `Registry.process` treats HMAC success as validation of the whole request, and hands `request.shop` straight to the application handler as trusted event metadata (`WebhookMetadata#shop`), the host application's per-shop business logic (order/customer processing, data writes keyed by shop, cache/state updates, etc.) can be driven by attacker-controlled content that is falsely attributed to a victim shop. This is a cross-tenant identity confusion at the library layer feeding the host application's authorization/routing decisions.

### Likelihood Explanation
Any developer or account that operates a store which has the target app installed can harvest a legitimate webhook delivery (body + valid `x-shopify-hmac-sha256`) for a topic of their choosing, since webhooks are delivered to a URL they control on their own server, or can be observed via any logging/proxy on their end. Replaying that exact byte sequence to the same publicly reachable webhook endpoint with a different `shop-domain` header requires no secret knowledge and no interaction with Shopify's platform beyond the initial legitimate delivery. The only constraint is that the replayed body must be a body the attacker was able to obtain a valid signature for; this is easily satisfied for arbitrary content since the attacker controls what actions occur in their own shop (e.g. creating orders/products with attacker-chosen field values) to generate a signed body of their choosing.

### Recommendation
Bind the `shop` identity into the value that is HMAC-validated, or otherwise cryptographically or out-of-band verify it before dispatch:
- Include the shop domain (and other identity-relevant headers) in the signable string used for HMAC verification, if protocol changes are feasible, or
- Require/encourage the host application to cross-check `request.shop` against the shop that owns the specific webhook subscription/topic/ID (`webhook-id`) recorded at registration time, rather than trusting the header value as authoritative, and document this requirement prominently in `WebhookMetadata`/`Registry.process` so library consumers do not assume `data.shop` is authenticated.
- At minimum, clearly document in `docs/usage/webhooks.md` and in `WebhookMetadata`'s API that `shop` is derived from an unauthenticated header and must be independently validated by the host app against known shop-webhook associations before being trusted for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers an event (e.g., creates an order) that causes Shopify to deliver a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value (e.g., via their own reverse proxy/logging in front of their webhook receiver, or any MITM-free observation they control).
3. Attacker sends a new POST directly to the app's public webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key`, per [6](#0-5) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, per [7](#0-6) , causing the host application to process attacker-controlled webhook content under the victim shop's identity.
