Confirmed: the webhook processing flow validates the HMAC only over the raw body while `shop` (and `topic`, `webhook_id`, `api_version`) are taken from unauthenticated headers and passed straight through to the app's handler as the trusted tenant identity.I have enough evidence now to write the final answer.

### Title
`Registry.process()` trusts the `shop`/`topic` headers that are not covered by the webhook HMAC - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's authenticity solely by checking the HMAC over the raw request body, then forwards the `shop`, `topic`, `webhook_id`, and `api_version` values — all read from unauthenticated HTTP headers — directly to the app's handler as trusted, tenant-identifying metadata.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and its `hmac` reader is likewise derived only from the `hmac-sha256` header value: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — for webhook requests this only ever authenticates the body bytes: [3](#0-2) 

`Registry.process` then reads `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight from the (unsigned) `shopify-shop-domain`/`shopify-topic`/etc. headers and passes them into `WebhookMetadata`, which app handlers use as the authoritative tenant/topic identity: [4](#0-3) [5](#0-4) 

Because the app's `api_secret_key` is shared across every shop the app serves, the identity binding the gem should enforce is: **`shop` claimed in `WebhookMetadata.shop` == the shop whose data actually produced the signed bytes.** That binding is never checked — only `hmac == HMAC(secret, raw_body)` is checked; `shop` (and `topic`) sit outside the signed material entirely, exactly the "field acted on but not covered by the HMAC" bug class from the reference report (there, `totalReclaimed` was excluded from the guarded arithmetic; here, `shop`/`topic` headers are excluded from the guarded HMAC digest).

### Impact Explanation
Any user of the multi-tenant app who has installed it on their own shop (the "attacker") legitimately receives real webhook deliveries — bodies + valid HMACs signed with the app's shared secret. They can capture one such `(raw_body, hmac)` pair from their own shop and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`) for a victim shop. `HmacValidator.validate` still passes because it never inspects the header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as `shop` with attacker-controlled body content. Any downstream logic that keys storage, entitlements, or side effects off `data.shop`/`data.topic` (exactly as the gem's own documentation instructs — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) is now cross-tenant poisoned: attacker data gets attributed to and processed under the victim tenant's identity. This is a cross-tenant identity confusion carried entirely through this gem's own verification API, matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that follows the documented pattern (`docs/usage/webhooks.md`) of trusting `data.shop`/`data.topic` from `Registry.process` without independent verification, since:
- No secret material beyond what the attacker already legitimately possesses (their own valid webhook deliveries) is required.
- The header/body decoupling is baked into `Request#to_signable_string` and `Request#shop`/`#topic`, so every consumer of `Registry.process` inherits the gap identically; it's not an app-side misuse of an undocumented feature — the gem's own `process` method performs the header-trusting behavior.

### Recommendation
Include the tenant-identifying header (`shop-domain`) and `topic` in the signable string / HMAC computation for webhook requests, or otherwise cryptographically bind them to the body (e.g., compute the HMAC over `raw_body + shop + topic` or require callers to pre-validate `shop` against a known/installed-shop list before trusting `WebhookMetadata`). At minimum, document prominently that `WebhookMetadata.shop`/`.topic` are unauthenticated and must be independently cross-checked by the host app against its own session/install records before being used for any tenant-scoped action.

### Proof of Concept
1. App `A` serves shops `victim.myshopify.com` and `attacker.myshopify.com` with the same `api_secret_key`.
2. Attacker installs the app on `attacker.myshopify.com` and lets Shopify deliver a real webhook, capturing `raw_body` and the resulting `shopify-hmac-sha256` value (both are visible to the attacker's own endpoint/logs).
3. Attacker sends the same `raw_body` and same `hmac` to the app's webhook endpoint, but with header `shopify-shop-domain: victim.myshopify.com` (and desired `shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against `hmac` — the shop header is irrelevant to the digest (`lib/shopify_api/webhooks/hmac_validator.rb` / `request.rb`, `to_signable_string`).
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: attacker_body, ...))`, and any handler logic keyed on `data.shop` now applies attacker-controlled data to the victim tenant.
