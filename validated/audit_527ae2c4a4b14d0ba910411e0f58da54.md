### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless trusts `request.shop` (parsed straight from the unauthenticated header) and hands it to the app's webhook handler as the tenant identifier. This breaks the identity binding `hmac_verified_bytes == bytes_the_handler_acts_on`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the `@raw_body` is included. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to that signature: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then constructs the `WebhookMetadata` passed to the merchant's handler using the unauthenticated `shop` header value: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely against `to_signable_string` (i.e., the body): [4](#0-3) 

So the equality the gem should enforce — "the shop attributed to this webhook == the shop whose secret produced this HMAC" — never holds; only "the body bytes == the HMAC'd bytes" is checked, while `shop` (the tenant key) rides in on an unverified header.

### Impact Explanation
Because the signature never covers `shop-domain`, an attacker who owns or can trigger delivery of *any* legitimately Shopify-signed webhook (e.g., from their own installed app/store) can capture the `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will pass HMAC validation (only the body is checked) and dispatch to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any app logic that trusts `data.shop` to select which tenant's records to create/update/delete (a very common pattern for webhook handlers, e.g., `customers/redact`, `shop/redact`, order/product sync) can be tricked into acting on/against the wrong tenant — a cross-tenant integrity violation.

### Likelihood Explanation
Exploitability requires only network access to the app's public webhook endpoint plus possession of one validly-signed `(body, hmac)` pair, which any developer/attacker can obtain by installing the app on their own store and capturing its own outbound webhook. No merchant access token, `client_secret`, or privileged account is required — only the gem's own webhook-processing path is used as designed. This satisfies the "field acted on but not covered by the HMAC" analog called out in scope.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them, e.g., via a signed header set) so `HmacValidator.validate` actually authenticates the tenant/topic metadata the handler consumes, not just the raw body. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop-domain` header value used downstream in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled store `attacker.myshopify.com`; trigger any registered webhook topic (e.g., `orders/create`). Capture the raw POST: headers include `X-Shopify-Hmac-Sha256: <valid_hmac>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`, with body `B`.
2. Replay the exact same body `B` and `X-Shopify-Hmac-Sha256: <valid_hmac>` to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (`to_signable_string`) — validation succeeds since body/hmac are untouched. [3](#0-2) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the HMAC was never generated for that shop, allowing the app to act on/write data attributed to `victim.myshopify.com` based on attacker-controlled input.
