## Title
Reentrancy in `IntentGatewayV2.withdraw()` (Tron fork) — external transfer before escrow accounting update, reachable via unprotected `cancelOrder()` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` contains a `withdraw()` function that sends native ETH / ERC-20 tokens to a caller-controlled `beneficiary` (or calls an arbitrary `token` contract) **before** decrementing the corresponding `_orders` escrow balance, violating checks-effects-interactions. Unlike the sibling (already-audited and fixed) EVM contract, this function is reachable directly by any unprivileged user through the public, non-`onlyHost` `cancelOrder()` entry point, and carries no `nonReentrant` guard.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` performs, for every token in the withdrawal request:
1. a presence check `_orders[commitment][token] == 0`,
2. an external call (`beneficiary.call{value: amount}("")` for native tokens, or `token.call(transfer(...))` for ERC-20s),
3. only **after** that, the escrow decrement `_orders[body.commitment][token] -= amount`. [1](#0-0) 

The tx-fee payout at the end of the same function has the identical ordering issue — external call to `feeToken`, then `delete`: [2](#0-1) 

Critically, `withdraw` is **not** restricted to `onlyHost`. It is invoked directly from the user-facing `cancelOrder()` function on the same-chain path, gated only by an `order.user == msg.sender` check and a `_filled[commitment] != 0` check performed one call-frame up: [3](#0-2) 

This is a clear regression against the pattern the project itself already identified and fixed elsewhere. The parallel, already-patched implementation (`IntentsBase._withdraw`, used by the mainline EVM `IntentGatewayV2`) decrements the escrow mapping **before** performing the external transfer: [4](#0-3) 

and the project has a dedicated regression-test suite (`IntrinsicIntentsReentrancyTest.sol`) explicitly documenting that `_filled[commitment]` must be set — and, more importantly, escrow state finalized — *before* any external call, precisely to block this class of exploit: [5](#0-4) 

The Tron fork does set `_filled[body.commitment] = beneficiary` at the very top of `withdraw` (line 693), which blocks a reentrant call from re-triggering `cancelOrder`/`withdraw` a second time for the *same* commitment. However, the per-token `_orders` decrement inside the loop, and the fee decrement/deletion at the end, still occur strictly after their respective external calls — the CEI violation the sibling contract fixed was not fully carried over here, and no `nonReentrant` modifier exists anywhere in this contract.

### Impact Explanation
A native-ETH beneficiary that is a contract, or an ERC-20/ERC-777/ERC-1363-style token with a transfer callback used as an order's input asset, gains code execution mid-`withdraw()` while the contract's escrow bookkeeping for that order is still stale (pre-decrement) and while `TRANSACTION_FEES` accounting for the order is also still unresolved. Because `withdraw()` is reachable without any host authentication via `cancelOrder()`, this materially expands the attack surface beyond the host-only delivery path (`onAccept`/`onGetResponse`) that the rest of the protocol relies on for authorization, and removes a defense-in-depth layer (reentrancy guard / CEI ordering) that the equivalent, audited EVM contract already enforces. This qualifies as High severity per the reachable-fund-accounting bug class described in the report (external call before state update in a token/escrow release function).

### Likelihood Explanation
The vulnerable function is reached with a single, unprivileged transaction (`cancelOrder`) from any user who places an order with a malicious token or a beneficiary contract they control — no relayer, consensus proof, or governance interaction is required. The primary mitigating factor is the early `_filled` write, which blocks straightforward same-commitment double-withdrawal; a full fund-drain exploit therefore requires additional creativity (e.g., interaction with the still-undecremented `TRANSACTION_FEES` slot, or a token/beneficiary contract that reaches into other state-changing paths of the gateway during the callback window). This tempers likelihood relative to a textbook drain but the underlying CEI violation is objectively present and inconsistent with the rest of the codebase's own remediation.

### Recommendation
Apply the same fix already implemented in `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (and delete/zero the `TRANSACTION_FEES` entry) **before** making any external call, and add a `nonReentrant` modifier to `withdraw()` (and to `cancelOrder()`, which is its only unauthenticated entry point) as defense in depth, consistent with the OpenZeppelin `ReentrancyGuard` recommendation from the referenced report.

### Proof of Concept
1. Attacker deploys a malicious ERC-20-like `token` contract, or simply a plain contract with a `receive()` hook, to act as the order's escrowed input asset / beneficiary.
2. Attacker calls `placeOrder()` on the Tron `IntentGatewayV2` with `order.source == order.destination` (same chain), `order.user = attacker`, and an input token controlled by the attacker.
3. Attacker calls `cancelOrder(order, options)`. Since `order.user == msg.sender` and `_filled[commitment] == 0`, execution reaches the same-chain branch which calls `withdraw(body, true)` directly — no `onlyHost` check. [6](#0-5) 
4. Inside `withdraw`, the loop calls `token.call(...)` / `beneficiary.call{value:...}("")` (line 703/706) *before* `_orders[body.commitment][token] -= amount` executes (line 710); the malicious token/beneficiary's callback fires in this window, while `_orders[commitment][token]` and the `TRANSACTION_FEES` entry are still un-decremented, giving the attacker a reentrant execution window against a fund-release function with no `nonReentrant` protection.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
