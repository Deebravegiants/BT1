### Title
Stale `_defaultRelayerFee` cached from feeToken decimals at `setHost()` desyncs from live `EvmHost.feeToken()` after a fee-token swap - ([File: sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol])

### Summary
`HyperbridgeLzEndpoint.setHost()` caches a relayer-fee constant (`_defaultRelayerFee`) computed once from the fee token's `decimals()` at bind time. `EvmHost` allows the fee token to be replaced later via governance (`updateHostParams`), but the endpoint never refreshes its cached fee, exactly mirroring the M-3 pattern of caching a mutable config value instead of always reading it live.

### Finding Description
`setHost()` derives and permanently stores a relayer fee denominated in the *current* fee token's decimals: [1](#0-0) 

`_defaultRelayerFee` is then used as-is (or via `_relayerFees[dstEid]`, which is also set once, in absolute raw units) whenever a message is dispatched: [2](#0-1) 

Meanwhile, `EvmHost.updateHostParams` explicitly permits changing `feeToken`, guarded only by a check that the *old* token's balance is zero (not by any restriction on the new token's decimals): [3](#0-2) 

`send()` correctly re-reads the *address* of the live fee token before approving (`IDispatcher(_host).feeToken()`), but it never re-reads or rescales the raw fee *amount* it passes as `DispatchPost.fee`: [4](#0-3) 

If the host's fee token is swapped for one with different decimals (e.g. 18-decimal → 6-decimal, or vice versa), `_defaultRelayerFee` (and any `_relayerFees[dstEid]` set under the old token's scale) becomes wrong by orders of magnitude while still being denominated as if it were in the new token's raw units — the same class of bug as `BlueBerryBank` caching `feeManager` instead of reading `config.feeManager()` live.

### Impact Explanation
Two failure modes follow directly from the stale cache:
- **Under-priced fee (old token had fewer decimals than the new one, or decimals dropped):** the raw fee amount collapses toward zero relative to the new token's value. Relayers have no economic incentive to deliver the dispatched message, permanently starving the route — a "route unable to deliver messages" condition.
- **Over-priced fee (decimals increased):** the raw fee amount balloons by 10^n. Combined with `send()`'s pattern of `forceApprove(_host, balanceOf(this))` and letting the host "take what it needs," this either reverts (denial of service on every send) or, if enough balance sits in the contract, drains an unintended, un-scaled amount of the fee token from the endpoint on every dispatch — a fund-loss condition for the OApp/users funding the endpoint.

This is not a "malicious admin" scenario: it is triggered by an ordinary, legitimate governance action (rotating the fee token) that `EvmHost` explicitly supports, exactly as the original M-3 report describes a legitimate `feeManager` update on `Config` desyncing `BlueBerryBank`.

### Likelihood Explanation
Fee-token migrations are a supported, documented governance path in `EvmHost` (`updateHostParams` with the `CannotChangeFeeToken` check only preventing changes while old balance is non-zero — it does not forbid decimal changes). Any chain operator who rotates the fee token to a token with different decimals (e.g., swapping a legacy 18-decimal wrapped token for a 6-decimal stablecoin, or vice versa) will silently desync every LZ-endpoint deployment on that chain unless someone remembers to also call `setDefaultRelayerFee`/`setRelayerFee` on every `HyperbridgeLzEndpoint` instance. Given this is an operational/governance action rather than an attacker-controlled one, likelihood is moderate but the blast radius (every OApp routed through the endpoint) is large.

### Recommendation
Do not cache a decimals-derived constant at bind time. Either:
- Store `_defaultRelayerFee`/`_relayerFees` in a decimals-agnostic unit (e.g., USD-cents) and rescale on every read using `IERC20Metadata(IDispatcher(_host).feeToken()).decimals()` read live, or
- Require governance to call `setDefaultRelayerFee`/`setRelayerFee` atomically as part of any fee-token migration, and add a guard in `send()`/`quote()` that reverts (rather than silently mispricing) if the cached fee's implied decimals no longer match the live fee token's decimals.

### Proof of Concept
1. Deploy `HyperbridgeLzEndpoint` and call `setHost(hostAddr, eid)` while `EvmHost.feeToken()` is an 18-decimal token → `_defaultRelayerFee = 0.3e18`.
2. Governance later calls `EvmHost.updateHostParams` (after draining the old token's balance to zero, satisfying `CannotChangeFeeToken`) to switch `feeToken` to a 6-decimal stablecoin.
3. Any OApp calls `HyperbridgeLzEndpoint.send()`. `relayerFee(dstEid)` still returns `0.3e18`, but the contract now approves/transfers in the 6-decimal token. `0.3e18` raw units of a 6-decimal token is `300,000,000,000` tokens — the transfer either reverts (bricking every subsequent `send()`, i.e., the route can no longer deliver messages) or, in the inverse decimals direction, silently pays a near-zero fee that leaves messages undeliverable by relayers.

    function setHost(address hostAddr, uint32 localEid) external onlyOwner {
        _host = hostAddr;
        _eid = localEid;

        // Set default relayer fee to $0.30 based on feeToken decimals
        address feeToken = IDispatcher(hostAddr).feeToken();
        uint8 decimals = IERC20Metadata(feeToken).decimals();
        _defaultRelayerFee = (3 * 10 ** decimals) / 10; // 0.30
    }
