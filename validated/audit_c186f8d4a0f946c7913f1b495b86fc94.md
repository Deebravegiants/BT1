### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `Request#to_signable_string` method used for that HMAC returns only `@raw_body`, never the `shop-domain`, `topic`, or `webhook-id` headers [2](#0-1) . Those header-derived fields are nevertheless trusted and forwarded verbatim to the app's `WebhookHandler#handle` as `WebhookMetadata.shop`/`topic`/`webhook_id` [1](#0-0) [3](#0-2) .

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [4](#0-3) . For webhooks, `hmac` is read from the `hmac-sha256` header and `to_signable_string` is just `@raw_body` [5](#0-4) . The `shop`, `topic`, and `webhook_id` accessors read straight from HTTP headers with no cryptographic binding to the signed body [6](#0-5) .

Because the app's HMAC secret (`Context.api_secret_key`) is the same for every shop that installs the app, any unprivileged party who can install the app on their own (even a free/trial) store can receive a legitimate, correctly-signed webhook for a body of their choosing, then replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with a victim shop's domain. `Registry.process` will accept it: `Utils::HmacValidator.validate(request)` passes because the body/HMAC pair is genuinely valid, and the equality that should hold — *the shop attributed to the webhook == the shop whose secret/body actually produced the signature* — is broken because the `shop` field is never part of `to_signable_string`. The forged `WebhookMetadata.shop` value is then handed to the host application's handler as if it were an authenticated fact [1](#0-0) .

Host applications built on top of this gem (per its documented usage, e.g. `docs/usage/webhooks.md`) are expected to trust `data.shop`/`data.topic` to route work to the correct tenant (look up that shop's session, apply body data to that shop's records, trigger shop-scoped side effects). This gem provides no mechanism for the handler to distinguish a genuine webhook for shop A from a replayed body falsely labeled as shop B, because the binding `hmac(body) ⟺ shop` is never enforced.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately controls one tenant (their own installed shop) can cause the app to process webhook data under the identity of a different, victim tenant. Depending on how the host app's handler trusts `data.shop` (e.g., to select the target shop's access token/session, write to that shop's data store, or trigger `shop/redact`/`customers/redact` GDPR flows on an arbitrary shop), this can lead to cross-tenant data corruption or spoofed compliance/administrative actions attributed to a shop that never sent that webhook — squarely a "cross-tenant access" class issue.

### Likelihood Explanation
Likelihood is high for any determined attacker: acquiring a free Shopify development/trial store and installing a target app is trivial and requires no privileged credentials from the app itself. Capturing one's own legitimate webhook deliveries (body + valid HMAC) is inherent app behavior. Forging the `X-Shopify-Shop-Domain` header on the replayed HTTP request requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint, which is by definition internet-reachable.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated signable content, or otherwise cryptographically verify that the `shop-domain` header corresponds to the shop for which the signature was generated (e.g., re-verify against a shop-specific expectation, or require the handler to independently confirm that the shop currently has an active installation/session before trusting `data.shop`). At minimum, `Request#to_signable_string` should not be limited to `@raw_body` when other trusted-but-unsigned header values are exposed to callers as though they were verified.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify development store (`attacker.myshopify.com`); trigger any webhook topic the app subscribes to (e.g. `orders/create`) so Shopify sends a legitimately-signed request: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture that request.
3. Replay the exact same body `B` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B)` [5](#0-4) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` [1](#0-0) , causing the host app to process attacker-controlled data under the victim shop's identity.
