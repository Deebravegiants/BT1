### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC validates, then dispatches to the app's handler using the header-derived `shop`, without any binding between the two. An attacker who controls a legitimately-installed shop (which shares the app's single `api_secret_key` across all shops) can capture one of their own valid, HMAC-signed webhook deliveries and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop, producing a request that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw request body: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers that are never mixed into the signed string: [3](#0-2) 

`Registry.process` validates the HMAC of the body and, if it passes, dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body, secret) == true` ⟺ `(shop, topic, body)` all originate from the same Shopify-issued delivery.

In this implementation the equality only covers `body`; `shop` (and `topic`) are unbound free variables supplied by the caller. Because a single app has one `api_secret_key` shared by every shop that installs it, any attacker who installs the app on their own (even free/dev) shop can trigger a real webhook delivery from Shopify, capture the resulting valid `(raw_body, x-shopify-hmac-sha256)` pair, and then resend that exact body/HMAC pair to the app's webhook endpoint with `x-shopify-shop-domain` (and optionally `x-shopify-topic`) rewritten to a victim shop's domain. `HmacValidator.validate` will still succeed because the body bytes and signature are unchanged, but `Registry.process` will invoke the handler with `WebhookMetadata` claiming the victim shop: [5](#0-4) 

Any host application that uses `data.shop` to select which tenant's records to create/update/delete (the documented and expected usage pattern of this API) will apply attacker-controlled webhook body content to a shop it does not control — a cross-tenant write, not just a read.

### Impact Explanation
This breaks the tenant-identity boundary the gem is supposed to enforce for webhook delivery: the HMAC is meant to prove "this webhook body genuinely came from Shopify for this shop," but the implementation only proves "this body came from Shopify for *some* shop that installed this app." Since `shop` is the field host apps rely on to scope all subsequent writes, this allows an attacker to spoof webhook events across tenants (cross-tenant access), which meets the Critical impact bar defined by the rules (cross-tenant access via this gem's own verification logic).

### Likelihood Explanation
High. Exploitation only requires the attacker to install the target app on any shop under their control (a normal, unprivileged action for any Shopify developer/merchant), receive one real webhook, and replay it with a modified header — no access to `api_secret_key`, tokens, or the victim's credentials is needed. Free/dev shops are trivially obtainable, so this is reachable by an ordinary internet user, not a privileged actor.

### Recommendation
Bind the shop (and topic) identity into the signed material, or otherwise cryptographically tie the verified header set to the body before trusting `request.shop`:
- Compute the HMAC over a canonical string that includes `shop`, `topic`, and the body (this requires the caller to receive an equivalent signed value from Shopify, e.g., verifying against Shopify's actual webhook signing scheme rather than body-only), or
- At minimum, have `Registry.process` cross-check `request.shop` against an expected/allow-listed set of shops known to have installed the app (e.g., looking up an existing session for that shop) before invoking the handler, so a body that is valid for shop A cannot be attributed to shop B.
- Document prominently that `request.shop` is **not** authenticated by `HmacValidator.validate` and must not be trusted for tenant selection without an independent check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they control) and registers/receives a real webhook (e.g. `orders/create`).
2. Shopify sends a legitimately signed request:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: ...

   {"id": 123, ...attacker-controlled-order-body...}
   ```
3. Attacker replays the identical body and `x-shopify-hmac-sha256` value, changing only:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the unchanged HMAC: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata`/`data.shop == "victim-shop.myshopify.com"` and the attacker-controlled body, exactly as if Shopify itself had sent this event for the victim shop: [5](#0-4) 
6. A host app trusting `data.shop` to scope tenant data will process attacker-supplied content under the victim's tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
