### Title
POA bridge withdrawal status matched only by `assetId`, causing status/txHash misattribution between multiple same-token withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain status of a specific withdrawal (identified by `landingChain` + `index` + `withdrawalParams`) by calling `findMatchingWithdrawal()`, which selects a record from the bridge's `withdrawal_status` response using only an `assetId` string equality check, ignoring `index`, `destinationAddress`, and `amount`. [1](#0-0) [2](#0-1) 

### Finding Description
The SDK supports submitting multiple withdrawals in one NEAR transaction; `createWithdrawalIdentifiers()` builds a `WithdrawalIdentifier` per withdrawal, tracking a per-bridge `index` counter, and each is watched independently via `watchWithdrawal()` → `bridge.describeWithdrawal()`. [3](#0-2) 

For the POA bridge, `describeWithdrawal()` fetches all withdrawals tied to the originating NEAR tx hash and then picks the one whose `near_token_id` matches the requested `assetId` — it does not disambiguate by `index`, destination address, or amount:
```
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [4](#0-3) 

The code comment explicitly acknowledges the gap: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."* [5](#0-4) 

If a single NEAR transaction contains two or more withdrawal intents for the same token (e.g., two `ft_withdraw` legs of the same `nep141:xxx.omft.near` asset but with different `destinationAddress`/`amount`, as can be produced through the SDK's batch-withdrawal flow referenced in `docs/design/rfc-batch-withdrawal-granular-control.md`), `Array.prototype.find` always returns the **first** matching record in the API response for every caller regardless of which `index` was requested. Consequently:
- `watchWithdrawal()` for withdrawal index 1 can be resolved using the status/`transfer_tx_hash` that actually belongs to withdrawal index 0 (or vice versa), because both calls hit the same `findMatchingWithdrawal` logic with the same `assetId` and get the same first match. [6](#0-5) 
- This breaks the equality "status/txHash reported for the on-chain outcome actually corresponds to the exact withdrawal that was requested." One withdrawal that is still `PENDING` on the bridge can be reported as `completed` with a `txHash` belonging to a different destination address/amount, and the truly-completed one can be starved indefinitely (reported `pending` because it never gets matched — `find` always returns the same first hit).

### Impact Explanation
An integrator/relayer polling `waitForWithdrawalCompletion` (built on `watchWithdrawal`) for two same-asset withdrawals in one batch transaction can receive a `completed` status and `txHash` for the wrong withdrawal leg. This is a "status reported that is not the on-chain outcome" class of bug: the integrator could credit/finalize the wrong destination/amount as complete, or believe funds moved when they did not, while the correct leg silently never resolves to `completed` (it will forever match the same record and thus never see its true terminal status), leaving actually-completed funds unaccounted for or making a still-pending withdrawal look done. Per the impact bar, this is a status misreport that can cause an integrator to credit/refund incorrectly — categorized as High.

### Likelihood Explanation
Exploitability doesn't require a malicious counterparty — an ordinary user or integrator batching two withdrawals of the same token asset in a single NEAR transaction triggers this deterministically (the code's own comment confirms this is an unhandled, known case rather than a hypothetical edge case). Likelihood is bounded by how often batch-withdrawal of the identical `assetId` is actually exercised by callers of the SDK; if the currently shipped withdrawal APIs never build multiple same-asset legs into one call, the condition is unreachable, but the RFC document referencing "batch withdrawal granular control" indicates this is an intended supported feature direction.

### Recommendation
Disambiguate `findMatchingWithdrawal` using more than `assetId`: match on `destinationAddress`, `amount`, and/or explicit `index`/ordering that mirrors the intents' relative order (as the existing comment itself suggests — sort both local params and API results by amount, since fees are identical per token). Until the POA bridge API exposes a stable per-leg identifier, the SDK should refuse to support (throw, as it already does for `routeConfig` mismatches) more than one withdrawal of the same `assetId` in a single transaction rather than silently mismatching the wrong record.

### Proof of Concept
1. Caller submits one NEAR transaction with two `ft_withdraw` intents for `nep141:btc.omft.near`: leg A → `destinationAddress: addrA, amount: 100000`, leg B → `destinationAddress: addrB, amount: 200000`.
2. `createWithdrawalIdentifiers` assigns `index: 0` to leg A and `index: 1` to leg B for the `PoaBridge` route. [7](#0-6) 
3. Both `watchWithdrawal` calls invoke `PoaBridge.describeWithdrawal` with the same `tx.hash` and `assetId = "nep141:btc.omft.near"` but different `index`. [8](#0-7) 
4. The POA API returns two withdrawal records for that tx hash, one `COMPLETED` (leg A, `transfer_tx_hash: "txA"`) and one `PENDING` (leg B).
5. `findMatchingWithdrawal` ignores `args.withdrawalParams.index`/amount/address and returns whichever record in the array satisfies `nep141:${near_token_id} === assetId` first — for both watchers this is the same element (leg A's `COMPLETED` record). [4](#0-3) 
6. The watcher tracking leg B (still pending on-chain, funds not sent to `addrB`) incorrectly resolves as `{status: "completed", txHash: "txA"}`, while leg A's watcher may also resolve identically — an integrator relying on this signal treats leg B as delivered when it is not.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

async function findBridgeForWithdrawal(
	bridges: Bridge[],
	params: WithdrawalParams,
): Promise<Bridge | undefined> {
	for (const bridge of bridges) {
		if (await bridge.supports(params)) {
			return bridge;
		}
	}
	return undefined;
}
