### Title
Duplicate input-token accumulation in Tron `IntentGatewayV2.placeOrder` allows escrow inflation and multi-output over-release — analog of the Folks-Finance zero-amount collateral-array exploit ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's root cause is a state-tracking accumulator (`colPools`) that is updated with `+=`/push semantics per deposit **without deduplicating the key** (poolId), letting a user's collateral be counted multiple times for the same underlying pool. Hyperbridge's mainline EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:194-373`) already closes this exact bug class: it explicitly rejects duplicate output tokens via transient-storage dedup [1](#0-0)  and rejects duplicate input tokens by reverting instead of accumulating: `if (_orders[commitment][token] != 0) revert InvalidInput(); _orders[commitment][token] = reducedInputs[i].amount;` [2](#0-1) , with regression tests explicitly documenting this as a fix for "same-chain partial fills over-release repeated input escrow" and "prematurely finalize repeated output legs" [3](#0-2) [4](#0-3) .

However, the **Tron variant of the same contract**, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does **not** carry this fix. It has no duplicate output-token check, and its escrow-accounting loop uses `_orders[commitment][token] += reducedInputs[i].amount;` instead of a `!= 0` guard, meaning a single `placeOrder` call with two input legs referencing the same token accumulates both amounts into one `_orders[commitment][token]` slot [5](#0-4) [6](#0-5) .

### Finding Description
`placeOrder` in the Tron gateway builds `order.inputs[]` from user-supplied `TokenInfo[]` and loops over them without any check that a token address is unique across `inputs[]` [7](#0-6) . Both escrow paths (the predispatch/call-dispatcher path and the plain transferFrom path) then accumulate into the same `_orders[commitment][token]` accounting slot with `+=` rather than the single-write-with-revert-on-collision pattern used upstream [8](#0-7) [9](#0-8) .

This mirrors the Folks-Finance flaw precisely: a per-key ledger entry (`_orders[commitment][token]` here, `loan.collaterals[poolId].balance` there) that is fed by an unguarded loop over an attacker-supplied list (`order.inputs[]` here, deposit calls there), lacking a "have I already seen this key" dedup check. Where Folks-Finance's downstream consumer (`getLoanLiquidity`) summed `colPools` naively to over-credit collateral, the Tron gateway's downstream consumers — `IntrinsicIntents._fillSameChain`/`_cancelSameChain` style logic that reads `_orders[commitment][token]` per input index to compute escrowed/withdrawable amounts — will read the merged, doubled value for each of the duplicate legs. Concretely, on a same-chain order with two input legs both pointing at the same ERC-20 token (amounts A and B), the escrow map ends up holding `A+B` under a single token key, but the order's `inputs[]` array (used by the fill/cancel logic to compute per-leg proportional releases such as `escrowedAmount = order.inputs[i].amount` or `(order.inputs[i].amount * fillAmount) / totalRequired`, per the pattern documented in `IntrinsicIntents.sol`) still treats each leg as independently backed by the full escrow balance [10](#0-9) [11](#0-10) . This double counting can be used to over-withdraw/over-release escrow on fill or cancellation — the same "one deposit event counted N times against a shared collateral/escrow ledger" bug class as the report, and the upstream Foundry regression comment ("same-chain partial fills over-release repeated input escrow") confirms this is a real, previously-fixed exploitable path on the mainline contract.

### Impact Explanation
An attacker placing a same-chain (or cross-chain) order with duplicate input tokens on the Tron deployment can inflate the escrow accounting for that token beyond what any single input leg's proportional release logic expects, enabling over-release of escrowed funds to the attacker (as beneficiary/filler) or double-refund on cancellation, draining gateway-held liquidity for that token — a direct theft of user/protocol funds analogous to the report's "attacker can drain a pool" impact.

### Likelihood Explanation
High reachability: `placeOrder` is a fully permissionless, unprivileged entry point callable by any user/message dispatcher with an arbitrary `Order` struct; constructing two `TokenInfo` entries with the same `token` value and different `amount`s requires no special privilege, matching the "single submitted transaction" trigger criterion. The existence of upstream regression tests explicitly built to catch this exact class (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateOutputTokens`) confirms the maintainers already recognize and consider it exploitable/high severity — but that fix was applied to `evm/src/apps/IntentGatewayV2.sol` and not mirrored into `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Recommendation
Port the mainline fix to the Tron contract:
1. Add a duplicate-output-token rejection loop (transient storage or a `seen` mapping/array) before Phase 1 of `placeOrder`.
2. Replace the `_orders[commitment][token] += reducedInputs[i].amount;` accumulation with a single-write-with-collision-revert: `if (_orders[commitment][token] != 0) revert InvalidInput(); _orders[commitment][token] = reducedInputs[i].amount;` in both the predispatch and non-predispatch escrow branches.
3. Add the equivalent Foundry regression tests (`testRevert_PlaceOrder_DuplicateInputTokens[_WithProtocolFee]`, `testRevert_PlaceOrder_DuplicateOutputTokens`) against the Tron contract to lock in the fix.

### Proof of Concept
Concrete on-chain reproduction against the deployed Tron contract could not be executed in this environment (no filesystem/terminal access to fork Tron/run Foundry). Conceptually, the PoC mirrors `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`'s `testRevert_PlaceOrder_DuplicateInputTokens` [12](#0-11) , but run against `evm/tron/contracts/apps/IntentGatewayV2.sol`: submit an `Order` with `inputs = [ {token: USDC, amount: A}, {token: USDC, amount: B} ]`; on the mainline contract this reverts with `InvalidInput`, but on the Tron contract it succeeds, leaving `_orders[commitment][USDC] == A + B` while `order.inputs[0].amount == A` and `order.inputs[1].amount == B` are each treated as independently fully-escrowed by the fill/cancel logic — enabling over-release.         // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;

                    ++i;
                }

            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
