### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by checking the HMAC of the raw request body, while the `shop-domain` header — which is used by the host application to attribute the webhook payload to a specific merchant/tenant — is never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw HTTP body: [2](#0-1) 

The `shop` accessor, however, is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cross-check against the signed body: [3](#0-2) 

That unauthenticated `shop` value is exactly what gets forwarded to the application's handler as the tenant identifier for the event: [4](#0-3) 

The identity binding that should hold is:
`hmac_signed_bytes == (raw_body, shop-domain)`
but the actual implementation enforces only:
`hmac_signed_bytes == (raw_body)`, while `request.shop` is taken from an unsigned header.

Because all shops installed against the same Shopify app share one `api_secret_key`, any actor who can trigger a legitimate webhook to their own shop (any account holder with the app installed) obtains a `(raw_body, valid_hmac)` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still succeed (it only checks the body/secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim's shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (i.e. `request.shop`) as the tenant key to look up a session, write data, or make authorized decisions — which is the documented and expected usage pattern shown in the gem's own webhook docs and tests — an attacker can inject or attribute forged webhook data to a different merchant's tenant context. This is a cross-tenant confusion vulnerability rooted in the gem's own authentication primitive (`HmacValidator` + `Webhooks::Request`), not merely a host misuse, since the gem asserts "Invalid webhook HMAC" protection while silently leaving the shop identity outside that protection.

### Likelihood Explanation
Exploitation only requires possession of one legitimate app installation (any developer/merchant account) to harvest a valid `(body, hmac)` pair, plus the ability to send an HTTP request with a modified `shop-domain` header to the app's public webhook endpoint — no access to `api_secret_key` or any privileged credential is needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the bytes that are HMAC-verified, or otherwise cryptographically bind the shop identity to the signed body before it is trusted, similar to how `Auth::Oauth::AuthQuery#to_signable_string` incorporates `shop` into the signed parameter set (`lib/shopify_api/auth/oauth/auth_query.rb`).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger a webhook (e.g., `orders/create`) to capture a valid `(raw_body, x-shopify-hmac-sha256)` pair.
2. Send this raw body and HMAC header unmodified to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds (it only checks `raw_body` against the shared secret), and `Registry.process` invokes the app handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the body actually originated from the attacker's own shop.
