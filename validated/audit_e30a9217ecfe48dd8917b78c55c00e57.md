## Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` enables sandwich-style value extraction during XCM fee refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` swaps unused `Target` fee credit back to the user's original fee-payment asset via `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, meaning the reverse swap accepts any output amount regardless of pool price. Since `pallet_asset_conversion::do_swap_exact_tokens_for_tokens` only enforces a minimum-output check `if let Some(amount_out_min) = amount_out_min`, passing `None` disables that protection entirely, allowing a block-producing collator to manipulate the relevant pool's reserves immediately before the refund executes and capture the difference.

## Finding Description
`SwapFirstAssetTrader` is a `WeightTrader` implementation used for XCM execution fee payment with non-`Target` assets. Its `buy_weight` correctly uses `swap_tokens_for_exact_tokens` to obtain an exact `Target` fee amount, but `refund_weight` performs the reverse conversion at [1](#0-0) 
with the `amount_out_min` argument fixed to `None`. Inside `pallet_asset_conversion::do_swap_exact_tokens_for_tokens`, the minimum-output enforcement is entirely conditional on this parameter being `Some`: [2](#0-1) 
When `None` is passed, as it always is in `refund_weight`, no output-amount floor is checked, so the swap accepts whatever the pool returns at execution time regardless of price. This is confirmed as production code (not a mock/test-only path) — `SwapFirstAssetTrader` is wired into `asset-hub-rococo`, `asset-hub-westend`, and `penpal` XCM configs, per grep results across `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/xcm_config.rs`, `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, and `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs`.

Notably, the file already has the tooling to compute a safe minimum via `QuotePrice`/`quote_price_exact_tokens_for_tokens`, confirmed present in the same file (used by `quote_weight`), but this capability is not used in `refund_weight`, demonstrating the omission is not due to lack of available primitives.

## Impact Explanation
The impact is a bounded funds-loss issue: the fee payer who receives a refund in their original asset can have that refund's value reduced by a party who manipulates the swap pool's price immediately around the refund swap's execution (a sandwich). The loss is capped by the size of `self.total_fee` outstanding at refund time (i.e., the unspent portion of the estimated weight fee), not the whole pool or pallet balance, matching the "bounded" characterization in the original report.

## Likelihood Explanation
Exploitation requires control over transaction/message ordering relative to the block containing the refund — i.e., a collator/block-author role in the Cumulus block-authoring model, which is a realistic and permissionless-set threat actor (analogous to a miner/validator in the original Uniswap report). Any parachain configuring `SwapFirstAssetTrader` for non-native XCM fee payment backed by `pallet_asset_conversion` is exposed whenever a refund with a non-zero residual is triggered, which is a routine occurrence (weight overestimation is common). The code path is confirmed live in shipped parachain configs (Asset Hub Rococo/Westend, Penpal), increasing realistic exposure.

## Recommendation
Compute a non-`None` `amount_out_min` for the `refund_weight` swap using `QuotePrice::quote_price_exact_tokens_for_tokens` (already available/used in `quote_weight` in the same file) with an acceptable slippage tolerance, and treat swap failure due to insufficient output as "no refund achievable via swap" — falling back to retaining the credit in `Target` (as the existing `Err` branch already does) rather than accepting an arbitrarily bad price.

## Proof of Concept
1. Configure a parachain runtime with `SwapFirstAssetTrader` as a `WeightTrader`, backed by `pallet_asset_conversion` (mirrors production configs in Asset Hub Rococo/Westend, Penpal).
2. A user sends an XCM message paying weight fees in a non-`Target` asset `X`; `buy_weight` swaps `X → Target` for the exact estimated fee via `swap_tokens_for_exact_tokens`.
3. Actual weight consumed is less than the estimate, triggering `refund_weight`, which extracts the excess `Target` credit and calls `swap_exact_tokens_for_tokens(vec![Target, X], refund, None)` at `cumulus/primitives/utility/src/lib.rs:540-544`.
4. A block-producing collator, prior to including the extrinsic/message that triggers this refund, submits `pallet_asset_conversion::swap_*` extrinsics (or other XCM `AssetExchange` operations) against the `X`/`Target` pool to skew reserves unfavorably for the refund swap's direction, lets the refund execute at the manipulated price, then reverses the trade — a standard sandwich — capturing the difference between the fair and manipulated refund amounts. A unit/integration test asserting `refund_weight`'s output amount before/after a pool-manipulating trade injected between `buy_weight` and `refund_weight` calls would demonstrate the reduced refund value.
