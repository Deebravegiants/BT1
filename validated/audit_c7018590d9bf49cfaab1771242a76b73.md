I have confirmed the vulnerable code path and its exposure through the public API.

### Title
isOwnAddress returns false-positive ownership when address equals the abstractAccounts asset's `noAccountYet` placeholder - ([File: features/address-provider/module/address-provider.js])

### Summary
For abstractAccounts assets (e.g. `eosio`), `AddressProvider#getMainAccountName` falls back to the asset's static `noAccountYet` placeholder string when no `mainAccountName` has been set yet for the wallet account. `isOwnAddress` then compares the caller-supplied `address` against this fallback value using strict equality, so passing the placeholder string as `address` yields `true` even though the account does not exist and no keys/ownership were derived.

### Finding Description
`#getMainAccountName` reads `accountStates[walletAccount]?.[assetName]?.mainAccountName` and falls back to `this.#getAsset(assetName).noAccountYet` when unset: [1](#0-0) . `isOwnAddress` for abstractAccounts assets does `return address === mainAccountName` using whatever `#getMainAccountName` returned, without checking that a real account name has actually been assigned: [2](#0-1) . This is reachable through the public API `addressProviderApi.isOwnAddress`, which only requires the wallet to be unlocked (`lockedAtom`) and resolves the `walletAccount` instance — it performs no additional authorization or origin check: [3](#0-2) . The existing test suite documents the fallback behavior for `getReceiveAddress` (returning `noAccountYet` until a `mainAccountName` is set) but the equivalent unsafe case is not covered for `isOwnAddress` — only the case of an arbitrary non-matching string ("Wayne Tower") is tested for "no main account name": [4](#0-3)  and [5](#0-4) . Because `noAccountYet` is a fixed, publicly-known constant per asset (not secret, not derived from keys), any caller who knows or can retrieve it (e.g., via `getReceiveAddress`/`getReceiveAddressObject` on the same asset before an account exists) can pass it into `isOwnAddress` and get `true` returned for an address the wallet does not actually own.

### Impact Explanation
`isOwnAddress` is a public API method (`addressProviderApi.isOwnAddress`) intended to answer "does this wallet control this address" for abstractAccounts assets such as EOS-style accounts. A caller that treats this as an ownership/trust signal (e.g. to decide whether to treat an incoming transaction/account as self-owned, to skip a warning, or to gate a UI/consumer-side authorization decision) can be misled into believing an account exists and belongs to the wallet before it actually does. This is a logic/authorization-signal integrity bug rather than key or fund compromise, since no signing or secret disclosure is involved — the impact is scoped to false "own address" assertions for abstractAccounts assets prior to account creation.

### Likelihood Explanation
The precondition is narrow but realistic: the wallet must be unlocked (satisfied for any active dapp session) and the target `walletAccount` must not yet have received a `mainAccountName` for the abstractAccounts asset (e.g. a fresh EOS/abstract-account asset that hasn't been activated). The placeholder value is deterministic and asset-static, discoverable simply by calling `getReceiveAddress`/`getReceiveAddressObject` for that asset beforehand, as shown in the existing test: [5](#0-4) . No privileged state or secret is required, matching the "unprivileged dapp" threat model.

### Recommendation
In `#getMainAccountName`, distinguish "no account yet" from a real account name (e.g., return `undefined`/`null` or a discriminated result) rather than silently returning the `noAccountYet` placeholder to `isOwnAddress`. In `isOwnAddress`, only compare against an actual `mainAccountName`; if none exists, return `false` regardless of what `address` is passed, e.g.:
```js
if (asset.api.features.abstractAccounts) {
  const { value: accountStates } = await this.#accountStatesAtom.get()
  const mainAccountName = accountStates[walletAccount]?.[assetName]?.mainAccountName
  return Boolean(mainAccountName) && address === mainAccountName
}
```

### Proof of Concept
Add a unit test in `features/address-provider/__tests__/module/seed/eos.test.js`:
```js
it('should return false when address equals noAccountYet placeholder and no account exists yet', async () => {
  await expect(
    addressProvider.isOwnAddress({
      walletAccount,
      assetName: 'eosio',
      address: assets.eosio.noAccountYet,
    })
  ).resolves.toBe(false) // currently resolves to true, demonstrating the bug
})
```
Run against current code: the assertion fails because `isOwnAddress` returns `true`, confirming the false-positive ownership result.
