Confirmed: the `shop-domain` header is not included in the HMAC-signed content for webhook requests, which is a genuine identity-binding gap analogous to the operator bug's assumption-breaking effect.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook deliveries - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Registry.process` trusts `request.shop` (parsed from the `x-shopify-shop-domain`/`shopify-shop-domain` header) as the tenant identity forwarded to the app's handler, after validating only the body's HMAC. The header carrying the shop identity is never bound to the signature that `HmacValidator` checks, so the value that is *authenticated* (the body bytes) is not the value that is *acted on* (the shop identity).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` only, not the headers. `Registry.process` validates the HMAC over that signable string and, if it passes, forwards `request.shop` — sourced purely from the `shop-domain` header — into `WebhookMetadata` without any additional binding check: [2](#0-1) 
`request.shop` itself is read directly from the header with no relation to the signed bytes: [3](#0-2) 

This breaks the identity binding: `shop_header_value == shop_used_by_handler` is enforced, but `shop_header_value == shop_the_signature_actually_vouches_for` is not, since the signature only vouches for the body. Any request whose body HMAC matches (e.g. a body that was legitimately signed by Shopify for the attacker's own shop, such as from an app the attacker installed for a shop they control) will pass `HmacValidator.validate`, and the attacker fully controls what `shop-domain` header accompanies that body when replaying it to the app's webhook endpoint.

### Impact Explanation
Apps built on this gem's documented webhook pattern (see `docs/usage/webhooks.md` lines 123-136 and `BREAKING_CHANGES_FOR_V15.md`, which explicitly hand `data.shop` to app code as the trusted tenant identifier) will process webhook payloads under the wrong shop's identity. An attacker who owns a legitimate Shopify shop with the same app installed can capture a validly-signed webhook body for their own shop, then re-POST that body to the target app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The HMAC still validates (it only covers the body), and the app's handler executes attributing the event to the victim shop — a cross-tenant identity-binding bypass matching the Critical "cross-tenant access" impact category, since downstream app logic (data updates, session/webhook bookkeeping, redaction flows, etc.) keyed on `data.shop` would operate against the wrong tenant.

### Likelihood Explanation
Requires only an internet-accessible webhook endpoint and an attacker who can obtain any one validly-signed webhook body for a shop they control (trivial — install the app on a free dev/test shop and trigger any webhook topic). No access token, `client_secret`, or privileged credential is needed, satisfying the unprivileged-internet-user constraint.

### Recommendation
Bind the shop identity into the HMAC-verified payload rather than trusting an unauthenticated header: either include the `shop-domain` header value in `to_signable_string`, or cross-check `request.shop` against an expected/known value (e.g., the shop associated with the webhook subscription being processed) before invoking the handler, and reject processing on mismatch.

### Proof of Concept
1. Attacker installs the victim app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `app/uninstalled`), receiving a request with a body `B` and a valid `x-shopify-hmac-sha256` computed only over `B`.
2. Attacker replays `POST /webhook` to the target app with body `B` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against the secret — this passes.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` from the attacker's own shop event, processing it as if it originated from the victim tenant.
