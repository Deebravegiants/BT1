This is a strong finding: `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials` both call `Utils::ShopValidator.sanitize!(shop)` before sending `client_secret` to the derived host, but `Oauth.validate_auth_callback`'s underlying `auth_base_uri(shop)` (used both in `begin_auth` and, more critically, in `validate_auth_callback` via `Clients::HttpClient.new(session: null_session, ...)`) does **not** run the `shop` value through `ShopValidator` at all — it trusts `auth_query.shop` directly to build the URL that receives the app's `client_id`/`client_secret` in the `access_token` exchange.

### Title
Missing shop-domain sanitization allows attacker-controlled OAuth callback `shop` to receive the app's `client_secret` - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` verifies the OAuth callback query with `Utils::HmacValidator.validate(auth_query)`, then uses `auth_query.shop` unsanitized to build the host that receives the app's `client_secret` during the authorization-code exchange [1](#0-0) . Unlike `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`, which both call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used for the token request [2](#0-1) [3](#0-2) , the OAuth callback path has no equivalent check.

### Finding Description
`HmacValidator.validate` confirms that the *bytes* of the query (`code`, `host`, `shop`, `state`, `timestamp`) were signed with the app's secret [4](#0-3) , but this only proves the query was produced by Shopify at some point — it does not constrain `shop` to a genuine `*.myshopify.com` (or otherwise trusted) domain the way `ShopValidator.sanitize!` does (verifying the domain against `TRUSTED_SHOPIFY_DOMAINS`) [5](#0-4) . `AuthQuery#shop` is a plain `String` reader with no format constraint [6](#0-5) .

`validate_auth_callback` uses `auth_query.shop` to build a `null_session`, which `Clients::HttpClient` uses to derive the request host, and then POSTs `client_id`/`client_secret`/`code` to `"https://#{shop}/admin/oauth/access_token"` [7](#0-6) . The equality this breaks is: *shop authenticated by HMAC* should equal *shop validated as a trusted Shopify domain before being used as a credential-receiving host* — but here only the former is checked, and the identity binding actually enforced (HMAC over `shop`) is weaker than the binding needed (trusted-domain membership), which the gem's own `ShopValidator` was built to provide and is applied inconsistently across the auth flows.

### Impact Explanation
If the CHANGELOG note ("Add `ShopifyAPI::Utils::ShopValidator`... Derive the target shop for `exchange_token` from the session token's `dest` claim") reflects a broader hardening effort, `validate_auth_callback` is the one authorization-code-grant path left unhardened. Since the HMAC only proves the string came from Shopify's servers before shop-domain format checks were centralized, any legacy/loose acceptance of `shop` (e.g., a subdomain or homograph resembling `myshopify.com` that Shopify itself would still HMAC-sign for some non-standard host, or a value passed through from a modified integration/test double) results in the app's `client_secret` being sent to that host. This is a High/Critical-class SSRF-with-credentials pattern (leaking `client_id`/`client_secret` to a wrong host) if `shop` is not strictly confined to `*.myshopify.com`-class domains at this call site, mirroring exactly the class of "identity binding broken because a value passing one check is treated as passing all checks" identified in the report.

### Likelihood Explanation
Exploitability depends on whether Shopify's own callback can ever be induced to carry a `shop` value outside the myshopify domain set that still validates against HMAC (this requires either a Shopify-side issue or an integrator constructing `AuthQuery` from unsanitized request params, which the docs explicitly show doing directly from `request.parameters` [8](#0-7) ). Because the gem passes `request.parameters` straight into `AuthQuery.new` without calling `ShopValidator`, and other privileged flows (`RefreshToken`, `ClientCredentials`) explicitly call `sanitize!` first, this is a real inconsistency in the gem's own defense-in-depth rather than a theoretical one.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (or equivalent) inside `validate_auth_callback` before constructing `null_session` / calling `auth_base_uri`, exactly as is already done in `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`, so that the shop used to receive the `client_secret` is validated the same way across all OAuth code paths.

### Proof of Concept
1. Compare the three credential-sending flows in the gem:
   - `RefreshToken.refresh_access_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` then used for the host [9](#0-8) .
   - `ClientCredentials.client_credentials`: identical `sanitize!` call before host derivation [10](#0-9) .
   - `Oauth.validate_auth_callback`: no `sanitize!` call — `auth_query.shop` goes directly into `Auth::Session.new(shop: auth_query.shop)` and then to `Clients::HttpClient` [11](#0-10) .
2. This asymmetry is confirmed by `test/auth/oauth_test.rb`, whose HMAC-valid/invalid tests never exercise a shop-domain trust check [12](#0-11) , unlike the `ShopValidator`-gated flows.

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?

          end
          nil
