### Title
Webhook shop identity spoofing via `X-Shopify-Shop-Domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value it hands to the app's handler is read from an unauthenticated HTTP header that is never part of the signed bytes. Any request bearer who can obtain one validly-signed webhook body (e.g. by owning any shop that installs the app) can replay that body with a forged `shop-domain` header and have it processed as if it came from a different, arbitrary shop.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` expose the value used for signature verification, and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `verifiable_query.to_signable_string`, i.e., the raw body, using the app's shared `api_secret_key`: [2](#0-1) 

`Registry.process` accepts the request once this body-only HMAC check passes, then dispatches to the app's handler using `request.shop`, which is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never included in the signable string: [3](#0-2) [4](#0-3) 

The identity binding broken is: `shop authenticated by HMAC == shop delivered to handler`. In reality, the HMAC secret (`api_secret_key`) is shared across every shop that installs the same app, and the signature covers only the JSON body — not the topic, webhook id, api version, or shop-domain headers. This is exactly the "field acted on but not covered by the HMAC" pattern: an attacker who legitimately installs the app on their own store (an ordinary, unprivileged merchant relative to the target) receives real, correctly-signed webhook deliveries for their own shop. Because the signature is independent of the `shop-domain` header, the attacker can replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header. `HmacValidator.validate` still succeeds (it never looks at headers), so `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled-but-signed body>, ...)` — the app is told data belongs to a shop it never actually originated from.

The gem's own documentation instructs apps to trust `data.shop` as the tenant identifier straight out of `WebhookMetadata`: [5](#0-4) [6](#0-5) 

so this is not a case of the host app ignoring documented API — the gem's documented contract is precisely what enables the mix-up.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to guarantee: the gem asserts "this webhook was verified to come from Shopify for shop X," but shop X is attacker-controlled while only the payload authenticity (not its shop attribution) is actually verified. Any downstream logic that keys off `data.shop` (e.g., writing order/customer data into the victim shop's tenant record, triggering fulfillment or GDPR/webhook-driven side effects, invalidating or updating another merchant's cached state) can be poisoned by an attacker who merely operates their own installation of the app — a cross-tenant data confusion vector.

### Likelihood Explanation
Exploitation only requires that the attacker be a legitimate, unprivileged merchant of the target app (any Shopify merchant can install a public app), receive one of their own real webhook deliveries, and replay it against the app's webhook endpoint with the `shop-domain` header changed. No access token, API secret, or other credential is needed — the HMAC validates because the secret is shared per-app, not per-shop, and headers are outside the signed content.

### Recommendation
Bind the shop identity into the verified material: either (a) include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for HMAC computation, or (b) after HMAC validation, cross-check `request.shop` against a per-shop-verified value (e.g., confirm the shop is a known/installed shop associated with the specific webhook id via Shopify's API) before dispatching to the handler. At minimum, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) to receive a real Shopify-delivered POST with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and matches `H` (secret is shared across shops), so validation passes: [7](#0-6) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the app to process attacker-controlled data as though it originated from the victim's store.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
