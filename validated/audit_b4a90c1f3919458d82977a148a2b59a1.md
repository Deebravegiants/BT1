Confirmed: `WebhookMetadata.shop` (from `request.shop`, i.e. the `x-shopify-shop-domain`/`shopify-shop-domain` header) is passed directly to the host app's handler, while the HMAC signature verified by `HmacValidator.validate` is computed only over `request.to_signable_string`, which returns the raw body exclusively.

### Title
Webhook `shop` (tenant identity) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` binds a webhook's tenant identity to the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, but the HMAC integrity check performed by `ShopifyAPI::Utils::HmacValidator.validate` only signs the raw request body via `Request#to_signable_string`, which returns `@raw_body` alone. [1](#0-0)  The `shop` value is never included in the signable content, so it can be modified independently of the HMAC-signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by calling `Utils::HmacValidator.validate(request)`, which checks the HMAC against `request.to_signable_string` (the raw body only): [2](#0-1) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`request.shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body that was HMAC-verified: [3](#0-2)  and [4](#0-3) .

This breaks the equality that should hold: `shop_authenticated_by_HMAC == shop_used_for_tenant_dispatch`. Because the signable string is `raw_body` only, two requests with identical bodies (thus identical valid HMACs, since the same secret/body pair produces the same digest) but different `shop` headers will both pass `HmacValidator.validate`. Any party who can obtain one genuine `(raw_body, hmac)` pair for a webhook topic that has a body content they control or that is predictable/replayable (e.g., an app installed on their own store, generating events with attacker-influenced body content such as an order note, customer field, product description, etc.) can resend that exact body with an altered `shop` header pointing at a victim tenant. `HmacValidator.validate` will accept it because it only recomputes the HMAC over the untouched raw body, and `Registry.process` will then hand `WebhookMetadata` with the victim's `shop` value to the host application's handler, which typically uses `shop` to key its tenant data store.

### Impact Explanation
This is a cross-tenant access vector: an unprivileged operator of their own installed store can forge webhook deliveries that the gem will authenticate as originating from a different, victim shop, since the tenant-identifying `shop` field is acted upon by `Registry.process`/`WebhookHandler.handle` but is outside the HMAC's protected scope. Depending on how the host app uses `WebhookMetadata#shop` (typically to look up/update per-shop records), this enables injection of attacker-controlled webhook bodies into another tenant's data path — a Critical-class cross-tenant access issue per the report's impact classification.

### Likelihood Explanation
Requires only an attacker who can trigger a real webhook to their own store (e.g., installing the app themselves, no elevated access needed) and can control or predict the raw body bytes for the webhook, then replay that valid `(body, hmac)` pair with a modified shop-domain header value against the app's public webhook endpoint. No possession of `api_secret_key` or any privileged credential is required, satisfying the unprivileged-internet-user threshold.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signed content, or otherwise cryptographically verify that the delivered `shop` value matches the value the HMAC's secret-holder intended, rather than trusting it as a bare unauthenticated header. At minimum, `Request#to_signable_string` should incorporate the shop domain so `HmacValidator.validate` fails whenever the header is altered relative to the originally signed delivery.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; attacker triggers a webhook event whose body content they control (e.g., a `products/update` webhook body containing attacker-chosen text) — Shopify computes and delivers a valid `x-shopify-hmac-sha256` for that exact raw body using the app's real secret.
2. Attacker captures the raw body bytes and the corresponding valid HMAC header from this legitimate delivery.
3. Attacker sends a new HTTP POST directly to the app's webhook endpoint, reusing the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` and `to_signable_string` (raw body) match, so `Utils::HmacValidator.validate` returns `true` [5](#0-4) .
5. `Registry.process` proceeds and calls the host app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-controlled body, even though the request never originated from Shopify for that shop [2](#0-1) .
