Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` proves nothing about the `shop-domain` header. `Registry.process` nonetheless trusts `request.shop` (taken straight from that header) as the tenant identity attached to the webhook payload it hands to the app's handler.

### Finding Description
The identity binding that should hold is:
`HMAC_valid(raw_body, api_secret_key) == trust(shop-domain header value as tenant identity)`

This binding is broken because the HMAC only covers `raw_body`: [1](#0-0) [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac-sha256` header: [4](#0-3) 

`Registry.process` validates only that HMAC, then immediately trusts the unauthenticated `shop-domain` header to construct the tenant-scoped metadata passed to the app's webhook handler: [5](#0-4) 

Because `shop` is read straight from the HTTP header without any cryptographic binding to the body/HMAC: [2](#0-1) 

An unprivileged internet user who has legitimately received one authentic webhook for this app (e.g. by installing the app on their own free/dev store, which any developer can do) obtains a valid `(raw_body, hmac-sha256)` pair signed with the app's shared `api_secret_key`. Since the HMAC never binds to `shop-domain`, that exact same body+HMAC pair remains valid when replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to an arbitrary victim shop. `Registry.process` will pass HMAC validation and deliver the attacker's payload to the handler tagged as coming from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the host application webhook data whose HMAC only proves "signed by this app's secret" but whose tenant attribution (`shop`) is fully attacker-controlled. Any downstream logic in the app that trusts `WebhookMetadata#shop` to scope data writes, cache invalidation, entitlement changes, or redaction requests (e.g. `customers/redact`, `shop/redact`) can be tricked into acting on a victim shop's tenant using attacker-supplied body content — a cross-tenant access vector, which is listed as Critical impact.

### Likelihood Explanation
Any developer can install an app that uses this gem on their own store to obtain one legitimately signed webhook body+HMAC pair, then replay it against the app's public webhook endpoint with a modified shop header — no access token, no `api_secret_key`, and no privileged account is required. The only requirement is that the webhook endpoint is internet-reachable, which is inherent to the webhook delivery model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header value to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that consuming applications must independently verify that `shop` corresponds to a shop that actually has this app installed before acting on webhook data, since `to_signable_string` in `lib/shopify_api/webhooks/request.rb` does not include it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid under the app's shared `api_secret_key`.
2. Attacker POSTs the exact same body/HMAC pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only (`to_signable_string`) and it matches, since `shop-domain` was never part of the signed content.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim.myshopify.com"`, even though the payload originated from the attacker's own store, achieving cross-tenant data injection.
