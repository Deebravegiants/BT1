### Title
Panic on malformed cross-chain `from` field in `HyperFungibleToken` message delivery causes runtime halt - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`HyperFungibleTokenModule::on_accept` decodes an ABI-encoded `Message` from an incoming `PostRequest.body` and, when the message carries optional calldata with no signature, derives the dispatch origin directly from the message's `from` field by slicing/copying it without first checking its length, unlike the sibling `to` field a few lines above which is explicitly length-checked.

### Finding Description
In `on_accept`, the recipient (`to`) bytes are validated before use: [1](#0-0) 

But the sender (`from`) bytes used to compute the calldata-execution origin are not: [2](#0-1) 

For an EVM source, `&from_bytes[from_bytes.len() - 20..]` underflows/panics if `from_bytes.len() < 20`. For a non-EVM source, `account.copy_from_slice(from_bytes)` panics unless `from_bytes.len() == 32` exactly. Both are the same bug class as the Penumbra advisory referenced (fix: panic when sending funds to invalid address, #3457) — an externally supplied variable-length field is consumed with an infallible slice/copy operation instead of a length-checked, fallible conversion.

`body` originates from a `PostRequest` delivered via `pallet-ismp`'s unsigned `handle_unsigned` extrinsic, which any unprivileged relayer can submit with a valid state/consensus proof: [3](#0-2) 

`ContractToAsset::<T>::get(source, &from)` only authenticates that the low-level ISMP-dispatching contract address is a registered pair for the asset; it does not re-validate the *inner* ABI field `message.from` that this contract encodes into `body`: [4](#0-3) 

Because `message.from` is ABI type `bytes` (a dynamic byte array with no length constraint enforced by the ABI decoder), its length is determined entirely by whatever the sending contract or pallet encodes, and this decode path performs no defensive length check before the slice/copy operations that assume exactly 20 or 32 bytes.

### Impact Explanation
A panic inside `on_accept`, which is invoked from `pallet_ismp::Pallet::execute` during `handle_unsigned` execution, is not just a call-level `DispatchError` — it is a Rust-level panic reachable from processing an incoming, relayer-submitted message. Because block execution for `handle_unsigned` runs the same deterministic code across all validating nodes, a reproducible panic on a specific malformed message can halt or repeatedly fail block execution/import for that message, which matches the "route unable to deliver messages" / DoS criterion. This is distinct from and stronger than an ordinary `DispatchError`, since the code path assumed length invariants without validating them before performing raw slice/copy operations.

### Likelihood Explanation
Exploitability depends on whether a length-violating `from` value can reach this branch. The registered paired contract for a given asset is expected to always encode a fixed-size sender identifier (20 bytes for EVM, 32 for Substrate), so under normal, correctly-implemented paired contracts this path is not directly triggerable by an arbitrary third party. However, any drift between the registered contract's encoding and this pallet's fixed-length assumption — a buggy, upgraded, or newly-registered paired contract, or a Substrate-side counterpart that encodes `from` differently — turns this into a directly relayer-triggerable panic, since the relayer only needs to replay/deliver a message whose body was produced upstream; it does not need special privilege on the destination chain. This is a real, concrete gap (missing the same defensive check already applied to the adjacent `to` field), which is why I flag it as Medium likelihood/impact rather than a definite critical.

### Recommendation
Apply the same explicit length validation used for `to_bytes` to `from_bytes` before using it: check `from_bytes.len() == 20` (EVM) or `== 32` (non-EVM) and return a `HftError` (e.g., a new `InvalidSenderLength(usize)` variant) instead of slicing/copying unconditionally. Use `H160::from_slice`/`TryFrom` guarded by an explicit length check (mirroring the `to_bytes` pattern) rather than raw arithmetic (`from_bytes.len() - 20`) and `copy_from_slice`, both of which panic on invalid input.

### Proof of Concept
1. Register (via governance) or compromise a paired contract/pallet for a given `(source, from)` in `ContractToAsset`.
2. Have that contract dispatch a `PostRequest` whose ABI-encoded `body` decodes to a `Message` with non-empty `data` (calldata), no `signature`, and a `from` field of length other than 20 (if `source.is_evm()`) or other than 32 (otherwise) — e.g., 0 bytes.
3. A relayer submits this request via `pallet_ismp::handle_unsigned` with a valid proof.
4. `HyperFungibleTokenModule::on_accept` reaches `&from_bytes[from_bytes.len() - 20..]` or `account.copy_from_slice(from_bytes)` and panics, aborting execution of the extrinsic/block on every node that processes it. [2](#0-1)
