### Title
Response cache key omits WorkflowID, causing cross-workflow response leakage in HTTP Action caching - (`core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The `responseCache.Fetch`/`Set` logic keys cached HTTP action responses using `gateway.OutboundHTTPRequest.Hash()`, whose test-verified behavior deliberately ignores `WorkflowID` while including `WorkflowOwner`. This is analogous to the reported bug class: a state/pricing value is computed using an incomplete/incorrect scope (only part of the relevant "pending" state is considered), letting an unprivileged actor obtain a value/response that should not be available to them, at the expense of another party's isolation guarantee.

### Finding Description
`responseCache.isExpiredOrNotCached`, `Fetch`, and `Set` all use `req.Hash()` as the sole cache key: [1](#0-0) [2](#0-1) [3](#0-2) 

The struct comment claims the hash is derived from "method, URL, headers, body, workflowOwner" — but not `WorkflowID`: [4](#0-3) 

This is directly confirmed by the test suite, which explicitly asserts WorkflowID has no effect on the hash while WorkflowOwner does: [5](#0-4) 

The `gatewayHandler.makeOutgoingRequest` populates and stores/fetches using this same `OutboundHTTPRequest` (including `CacheSettings.Store`/`MaxAgeMs` controlled by the calling workflow) without any additional workflow-scoping: [6](#0-5) 

The README explicitly documents an isolation guarantee that the code does not implement: [7](#0-6) 

Root cause mirrors the reported bug class structurally: a shared resource's identity/scope key (pool token price’s burn accounting scope vs. cache entry’s workflow scope) is computed using an incomplete input set (missing pending future burns vs. missing `WorkflowID`), letting one actor's operation silently affect or read state that should be isolated to another actor/scope.

### Impact Explanation
If two different workflows under the same `WorkflowOwner` (a very common multi-workflow-per-owner scenario in CRE) issue outbound HTTP Action requests with identical method/URL/headers/body but different intended targets or expecting fresh data, one workflow can receive the cached response fetched for another workflow. This is a **cross-user (cross-workflow) response confusion**: workflow A's `Set`-cached response (which may contain data intended only within A's execution context, e.g., API responses containing account-specific data returned for A's parameters) can be served to workflow B via `Fetch`, or vice versa, purely because the cache key collapses distinct workflows under one owner into the same slot. This violates the documented "workflow-scoped caching" / "Workflow Isolation" security property and can leak one workflow's HTTP response data into another workflow's execution.

### Likelihood Explanation
Requires: (1) same `WorkflowOwner` operating multiple workflows that both use HTTP Action with caching (`CacheSettings.Store` / `MaxAgeMs` set), and (2) those requests happening to have identical method+URL+headers+body — which is plausible for shared/templated HTTP integrations (e.g., calling the same public API endpoint) reused across an owner's workflows. No privileged access is required; any workflow author under the same owner triggering an HTTP action with the same request shape encounters this by design of the flawed hash function, not by attacker sophistication.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation used as the cache key, so responses cached for one workflow cannot be returned to a different workflow's HTTP Action call, matching the documented "Workflow Isolation" guarantee. Update `TestRequestHash`'s "having different workflowID results in same Hash" test to instead assert `WorkflowID` differences produce different hashes.

### Proof of Concept
1. Workflow `wf-A` (owner `0xOwner1`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", WorkflowOwner: "0xOwner1", WorkflowID: "wf-A", CacheSettings: {Store: true}}`. The gateway fetches and caches the response keyed by `req.Hash()`.
2. Workflow `wf-B` (same owner `0xOwner1`, different `WorkflowID`) issues an identical request except `WorkflowID: "wf-B"` and `CacheSettings: {MaxAgeMs: 600000}`.
3. Because `Hash()` ignores `WorkflowID`, `Fetch` for `wf-B` computes the same cache key as `wf-A`'s stored entry and returns `wf-A`'s cached response directly to `wf-B`, as demonstrated by the existing unit test asserting hash equality across differing `WorkflowID` values [8](#0-7)  and by the `Fetch` cache-hit path returning `cachedResp.response` without any workflow check [9](#0-8) .

## 3. HTTP Action Message Handling

### 3.1 Process Flow

1. **Request Reception**: Gateway receives HTTP action request from a workflow node
2. **Rate Limiting**: Validates node rate limits
3. **Request Parsing**: Extracts `OutboundHTTPRequest` from the JSON-RPC message
4. **Cache Check**: Determines if request should use cached response or fetch fresh data
5. **HTTP Execution**: Makes actual HTTP request to external endpoint
6. **Response Caching**: Stores cacheable responses (2xx, 4xx status codes) only if `CacheSettings.Store` is `true`
7. **Node Response**: Sends HTTP response back to requesting node

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage
