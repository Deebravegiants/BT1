### Title
Webhook `shop` field trusted for tenant routing without HMAC coverage, enabling cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the webhook solely by checking `Utils::HmacValidator.validate(request)` against that body-only signable string before dispatching to the handler [2](#0-1) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC-covered body [3](#0-2) . That unauthenticated `shop` value is then forwarded verbatim into `WebhookMetadata` and handed to the host application's handler as the tenant identifier for the payload [4](#0-3) [5](#0-4) .

This is the same bug class as the reported Solidity finding: an identifier that gate-keeps a security-relevant invariant (`blacklistAddresses` entries vs. `inBlacklist` map) is mutated/consumed independently of the data structure meant to enforce consistency. Here, the identity binding that should hold is:

`shop asserted in WebhookMetadata.shop == shop cryptographically bound by the HMAC signature`

Before the request: Shopify signs `hmac-sha256` over the exact raw body it sends for a specific shop's event, and its infrastructure sets the `shop-domain` header to match. After an attacker's request: the attacker supplies any raw body and matching HMAC they can obtain from a legitimate delivery to their own store, but freely rewrites the `shop-domain` header to name a different (victim) shop. `HmacValidator.validate` still returns `true` because it only recomputes the signature over `@raw_body` and never incorporates `shop` into `to_signable_string` [6](#0-5) [1](#0-0) . The equality the gem is supposed to enforce — "authenticated shop == acted-upon shop" — is broken because `shop` is verified-absent from the bytes that are verified.

### Impact Explanation
An attacker who controls one legitimate shop (or otherwise obtains one valid `(raw_body, hmac)` pair, e.g., by subscribing their own store to a webhook topic) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop domain. Because `Registry.process` accepts the request as valid and passes the attacker-chosen `shop` straight to the handler, any host application that uses `WebhookMetadata#shop` to select which tenant's data/session to mutate (the documented and expected usage pattern) will process attacker-controlled webhook content under the wrong tenant. This is a cross-tenant data confusion / cross-tenant access vector, since the boundary between one merchant's data and another's is enforced only by a value that is not authenticated.

### Likelihood Explanation
Exploitation requires only unprivileged access to a Shopify store capable of receiving at least one legitimately signed webhook delivery for the target app (or interception of one delivery in transit) — no `api_secret_key`, access token, or privileged account is needed, since the attacker never needs to forge an HMAC, only replay one paired with a different header value. The webhook endpoint is, by design, an internet-facing, unauthenticated POST endpoint, so header tampering on replay is trivial.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified signable material, or otherwise cryptographically tie the shop domain to the signed payload, so that `Registry.process` cannot accept a signature-valid body under an attacker-chosen shop header. At minimum, document/enforce that `WebhookMetadata#shop` must never be trusted for tenant selection unless independently cross-checked (e.g., against a shop already registered with a valid offline token), and consider validating `shop` with `ShopValidator` combined with a lookup that ties it to the specific webhook subscription rather than the raw header.

### Proof of Concept
1. Attacker subscribes their own shop `attacker.myshopify.com` to a webhook topic handled by the target app; Shopify delivers a request with header `x-shopify-shop-domain: attacker.myshopify.com`, raw body `B`, and `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker captures `(B, H)` and issues their own POST to the same webhook endpoint with headers `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-hmac-sha256: H`, and body `B` unchanged.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` (from `Request#to_signable_string` returning `B`) and it matches `H`, so `Registry.process` treats the request as authentic [7](#0-6) .
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim.myshopify.com"` even though the payload `B` actually originated from `attacker.myshopify.com` [4](#0-3) .
5. The host application's handler, trusting `data.shop` as the tenant key, applies attacker-controlled webhook content to the victim shop's records.
