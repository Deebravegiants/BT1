## Analysis

The DIP incident's root cause was a token contract that didn't correctly account for the actual amount transferred (a `_transfer()` bug caused tokens to move twice), and the exploiting protocol trusted a *nominal* transfer amount instead of verifying the *actual* balance change, letting the attacker desynchronize internal accounting from real token balances.

The strongest reachable analog in this codebase is in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` — Hyperbridge's lock/unlock cross-chain bridge for arbitrary ERC20 tokens — reachable by any unprivileged user calling `send()`.

### Title
Unverified ERC20 transfer amount in `WrappedHyperFungibleToken.send()` allows unbacked cross-chain minting for non-standard tokens - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks `params.amount` of the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then unconditionally dispatches a cross-chain message crediting `params.amount` to the destination `HyperFungibleToken`, without verifying that the contract's balance actually increased by that amount. [1](#0-0) 

### Finding Description
`send()` performs:
```
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
DispatchPost memory request = _buildDispatchPost(params); // encodes params.amount as the credited amount
``` [2](#0-1) 

`_buildDispatchPost` embeds `params.amount` directly into the cross-chain `Message.amount` field, which the peer `HyperFungibleToken` on the destination chain will mint verbatim to the beneficiary in `onAccept`: [3](#0-2) 

There is no balance-delta check (`balanceBefore`/`balanceAfter`) around the `safeTransferFrom` call, unlike the pattern the codebase itself already uses elsewhere to defend against non-standard ERC20 behavior — e.g. `IntentGatewayV2` explicitly measures `balanceOf` before/after a `transferFrom` and uses the *actual received amount* rather than the nominal parameter, precisely to protect against fee-on-transfer/deflationary/double-transfer tokens: [4](#0-3) [5](#0-4) 

If the underlying token deployed as a `WrappedHyperFungibleToken` custody asset:
- transfers **less** than `params.amount` (fee-on-transfer, deflationary, or a buggy `_transfer` that silently short-transfers), the wrapper still dispatches a message minting the *full* `params.amount` on the destination `HyperFungibleToken`. The destination mint is now unbacked by real escrowed collateral.
- transfers **more** than requested (the DIP-style "double transfer due to missing return" bug class), attacker-controlled excess sits in the wrapper but nothing prevents draining escrow separately through the deficit case above.

This same unchecked pattern also exists in `onPostRequestTimeout`, which unlocks the full original `message.amount` from escrow on timeout regardless of what was actually locked: [6](#0-5) 

Repeated `send()` calls with such a token cause escrow balance to progressively diverge from the sum of amounts credited across all destination chains, eventually letting a legitimate or attacker-controlled beneficiary redeem (via a bridge-back `send()`/`onAccept()` round trip) more underlying collateral than the wrapper actually holds — draining the shared escrow and leaving later redeemers unable to withdraw (permanent freezing) or letting an attacker extract excess value first (theft).

### Impact Explanation
Any ERC20 that doesn't transfer exactly the requested amount (fee-on-transfer tokens, rebasing/deflationary tokens, or tokens with the exact double-transfer class of bug seen in the DIP incident) can be wrapped via `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` by anyone calling `configure`/`addChain` for their own deployment, or maliciously if an operator wraps such a token without realizing its non-standard behavior. Once wrapped, the mismatch between nominal `params.amount` and actual escrowed balance directly produces unbacked cross-chain mints or an insolvent escrow, i.e., theft of funds / permanent freezing of funds for other holders of the wrapped asset — the core impact categories in scope.

### Likelihood Explanation
This is triggerable by a single unprivileged `send()` call from any user against any underlying token that is not a "clean" 1:1 ERC20 (very common in practice — many popular tokens implement transfer fees or rebasing). No special privileges, governance, or malicious operator collusion required; only a token whose `transfer`/`transferFrom` doesn't move exactly the requested amount, which the contract makes no attempt to detect or reject.

### Recommendation
In `send()` (both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`), measure `balanceOf(address(this))` before and after `safeTransferFrom`, and encode the **actual received delta** — not `params.amount` — into the dispatched `Message.amount`, mirroring the pattern already implemented in `IntentGatewayV2`. Similarly ensure `onPostRequestTimeout` only unlocks the amount actually escrowed for a given commitment, not the raw message amount.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, `configure()` it with an ERC20 `underlying` that charges a transfer fee (e.g., 5%) or has a double-transfer bug like DIP's.
2. Attacker calls `send({dest, to: attacker2, amount: 1000e18, ...})`. `safeTransferFrom` moves attacker's tokens, but the wrapper only actually receives 950e18 (5% fee) while `Message.amount = 1000e18` is dispatched.
3. Destination `HyperFungibleToken.onAccept` mints 1000e18 to `attacker2` — 50e18 unbacked by escrow.
4. Repeating this (or bridging back via `send()` on the destination chain then `onAccept`/timeout redemption on the origin) drains the wrapper's real underlying balance below what other legitimate depositors are owed, freezing their funds or letting the attacker redeem more collateral than they ever deposited.     function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(incoming.request.body, (HyperFungibleTokenUpgradeable.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
