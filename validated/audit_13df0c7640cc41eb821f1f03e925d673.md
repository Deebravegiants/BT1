### Title
`Bonding.transferCreator` performs a single-step, non-reversible role transfer instead of a two-step push/pull — ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.transferCreator` immediately overwrites `tokenInfo[token].creator` in a single transaction with no acceptance step by the new address. This is the exact `changeAdmin` bug class from ADM-1: the protocol already recognized the risk of single-step role transfers for the contract-level `owner` role and hardened `Bonding`, `FeeVault`, and `Zap` with `Ownable2StepUpgradeable` (push/pull) — [2](#0-1) [3](#0-2)  — but it left the parallel, per-token "creator" role on the same single-step footing.

### Finding Description
`transferCreator` is a public, permissionless-to-the-current-creator function that mutates `info.creator` directly in one call: [4](#0-3) 

The only checks are `newCreator != address(0)` and `newCreator != info.creator` — there is no acceptance/confirmation step by `newCreator`. If the creator mistypes the destination address, pastes a checksum-mismatched address, or targets a contract without a way to call back into `Bonding`/`FeeVault`, the `creator` role for that token is permanently reassigned to an address nobody controls, with no recovery path (no admin override, no `NotCreator`-gated `renounce`/`revert` function exists for this role).

This is materially the same "wrong address" transfer risk the team already mitigated for the contract-level `owner()` role via `Ownable2StepUpgradeable`, evidenced by the explicit natspec rationale on `Bonding` and `FeeVault` calling out exactly this failure mode for `transferOwnership`. The `creator` role received no equivalent protection despite being the sole key for future fee attribution.

### Impact Explanation
The `creator` field is the sole attribution key for creator-side protocol fees: `Zap` calls `FeeVault.accrue(token, creator, ...)` using `Bonding.tokenInfo(token).creator`, and `FeeVault.claim()` pays out strictly to `msg.sender` based on `creatorBalance[msg.sender]`: [1](#0-0) 

Once `transferCreator` sends the role to an uncontrolled/wrong address, every future 0.25% creator-side fee accrued on that token (`FeeAccrued` events, `creatorBalance` increments) becomes permanently unclaimable by the original team — a permanent freezing of ongoing creator fee revenue for the life of the token, with no admin-level remediation function in `Bonding` or `FeeVault`. This satisfies the "permanent freezing of creator funds" impact bar.

### Likelihood Explanation
Likelihood is realistic but bounded: it requires the legitimate creator (an unprivileged but token-launching address explicitly in scope per the reachable-path rules) to make a fat-finger/typo error or target an address that can't act on-chain, exactly the same human-error class the report and the project's own `Ownable2StepUpgradeable` adoption acknowledge is common enough to defend against for the `owner` role. There is no malicious precondition needed — only the same operational mistake the team already engineered against elsewhere in the codebase.

### Recommendation
Apply the same push/pull pattern already used for `owner()` transfers to the `creator` role: add a `pendingCreator[token]` slot set by `transferCreator` (renamed to something like `proposeCreatorTransfer`), and a new `acceptCreatorTransfer(token)` callable only by `pendingCreator[token]` that finalizes the swap and clears the pending slot, mirroring `Ownable2StepUpgradeable.transferOwnership` / `acceptOwnership`. Optionally allow the current creator to cancel a pending proposal by passing `address(0)`.

### Proof of Concept
1. `creator` launches a token via `Bonding.launch`, becoming `tokenInfo[token].creator`.
2. Trading accrues creator fees over time via `Zap.buy`/`sell` → `FeeVault.accrue(token, creator, ...)`.
3. `creator` calls `bonding.transferCreator(token, newCreator)` intending to move the role to a new EOA but mistypes one character of the address (a different, valid, but uncontrolled address is produced) — the call succeeds because the only checks are `newCreator != address(0)` and `newCreator != info.creator`: [5](#0-4) 
4. `info.creator` is now the mistyped address; `CreatorTransferred` is emitted and cannot be reverted by anyone, including the protocol owner.
5. All subsequent `FeeVault.accrue` calls credit `creatorBalance[mistypedAddress]`; the original creator can never call `FeeVault.claim()` to retrieve them, and neither can anyone else, since `claim()` only pays `msg.sender`.

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
