### Title
Emporium "Min" proof path lets an unprivileged attacker execute arbitrary, unauthenticated calls from the Emporium contract with zero balance accounting - ([File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a value the attacker fully controls with no link to any UTXO, nullifier, or signature. `EmporiumUpgradeable.runAction`'s op-execution loop is independent of `erc20TokenAddresses.length`, so an attacker can submit an `EmporiumStack` with `signerAddress == address(0)` (skipping `verifyWallet`'s ECDSA check entirely) whose ops perform arbitrary `endpoint.call{value}(callData)` directly as the Emporium contract, while every balance-accounting loop (`balancesBefore`/`balancesAfter` in Emporium, and the per-token diff loop in `Hinkal.transact`) executes zero iterations because it is sized by the empty `erc20TokenAddresses` array.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. The Min path breaks this because the set of tokens the accounting loops iterate over (`circomData.erc20TokenAddresses`, forced to length 0 to select the Min circuit) is decoupled from the set of operations actually executed (`stack.ops`, decoded from attacker-controlled `externalActionMetadata`).

Code path:
1. `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`) selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`.
2. `formInputEmporiumMin` (`contracts/CircomDataBuilder.sol:150-161`) builds only 3 public inputs: `emporiumMessage`, `timeStamp`, `calldataHash` — matching `MainEVMCircuitMin.circom`, which only constrains `message <== Poseidon(1)([messageSeed])` [1](#0-0) . No root membership, no nullifier, no EdDSA signature, no `rootHashHinkal` binding is proven — anyone can produce a valid proof for any `messageSeed`/`emporiumMessage` of their choosing.
3. `HinkalHelper.dimensionsCheck` (`contracts/HinkalHelper.sol:64-171`) forces `amountChanges.length`, `inputNullifiers.length`, `outCommitments.length`, `onChainCreation.length`, `slippageValues.length` to also equal 0 (`dimensions.tokenNumber == 0`), so `Hinkal.transact`'s balance-diff/slippage loop (`contracts/Hinkal.sol:97-147`) performs zero iterations — no check ties any moved value back to `amountChanges`.
4. `Hinkal._externalTransact` builds `deltaAmountChanges` sized to the empty `erc20TokenAddresses` array and calls `EmporiumUpgradeable.runAction` (`contracts/Hinkal.sol:234-261`).
5. In `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`), `balancesBefore`/`balancesAfter` are computed over the same empty array, so the "BalanceChangeShouldBePositive" check and `handleOut` also never execute. Crucially, the `for (uint256 i = 0; i < stack.ops.length; i++)` loop that actually executes operations is **not gated by `erc20TokenAddresses.length` at all**.
6. `verifyWallet` (lines 302-349) returns immediately without any signature check when `stack.signerAddress == address(0)` (line 314-316), only marking `emporiumMessage` as used.
7. In the ops loop, when `signerAddress == address(0)`, `op.invokeWallet && stack.signerAddress != address(0)` is false, so execution falls to the "CASE 2: Stateless Interaction" branch: `op.endpoint.call{value: op.value}(op.callData)` — executed with `msg.sender == EmporiumUpgradeable` and fully attacker-chosen `endpoint`/`callData`/`value`.

Attacker's exact call: submit `Hinkal.transact` with `relay = address(0)`, `originalSender = msg.sender` (self), a locally-generated valid Groth16 proof for `MainEVMCircuitMin` with an arbitrary `messageSeed`, `dimensions` all zeroed for token-related fields, `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress` = the registered Emporium proxy, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({v:0,r:0,s:0, signerAddress:address(0), ops:[{endpoint: victimToken, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker, EmporiumBalance))}], maxFee:0, deadline: futureTs}))`. `rootHashExists` still passes trivially since any historical root (e.g. genesis root) satisfies it and is unrelated to the Min circuit's public inputs.

Existing guards fail to prevent this because: the calldata-hash integrity check only ensures the metadata submitted matches what was hashed for the proof (not that its *contents* are constrained by the circuit); `dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency, not that zero-length arrays are safe when the external action can still move value; `verifyWallet`'s signature check is bypassed entirely by `signerAddress == address(0)`; and the balance-accounting loops in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` are both indexed by the attacker-chosen (empty) `erc20TokenAddresses`, not by anything derived from `stack.ops`.

### Impact Explanation
Any ERC20 or ETH balance resting in the `EmporiumUpgradeable` contract (e.g., dust/leftover funds from multi-step swaps such as LiFi routes, funds temporarily routed through Emporium as an intermediary, or accumulated fees) can be transferred, approved, or otherwise moved out by an unprivileged attacker with no accounting check and no valid signature, using a proof that only demonstrates knowledge of a self-chosen preimage. This is direct theft of shielded/in-flight user funds held by the protocol's external-action contract — Critical severity. It is repeatable for as long as any exploitable balance exists in Emporium, and each `emporiumMessage` value can only be used once, but the attacker can generate an unlimited number of fresh `messageSeed`/`emporiumMessage` pairs and proofs at negligible cost.

### Likelihood Explanation
Preconditions: `EmporiumUpgradeable` must hold some balance (ERC20 or ETH) at the time of the attack — plausible given its role as an intermediary for external swaps/routing, or via griefing deposits sent directly to it beforehand by the attacker to bootstrap the exploit, then draining more than deposited if other legitimate flows have left residual balance. No privileged role, no valid EdDSA/ECDSA signature, and no real UTXO ownership is required. The attacker only needs to run the publicly available Circom Min circuit locally (`messageSeed` is free to choose) and call `Hinkal.transact` directly (`relay = address(0)`), making this fully permissionless and cheap (one transaction, standard gas cost, no capital other than gas required).

### Recommendation
Do not allow the "stateless" op-execution branch to run with `signerAddress == address(0)` when it can call arbitrary `endpoint`/`callData` without any accounting; either (a) require `erc20TokenAddresses.length > 0` (and thus the full, ownership-proving `MainEVMCircuit` path) whenever `stack.ops.length > 0` and `signerAddress == address(0)`, or (b) restrict unsigned ("keeper"/protocol-run) ops to a fixed allow-list of endpoints/selectors that cannot exfiltrate arbitrary balances, or (c) make the Min-circuit path strictly non-value-moving (e.g., disallow it from reaching `runAction`'s op-execution loop at all, only usable for message cancellation/no-op flows). Additionally, tie `stack.ops` targets/values to values actually constrained by the proof/dimensions rather than allowing them to be fully independent of `erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `VerifierFacade` with registered `VerifierEVMMin0v4`/`mainEVMCircuitMin0v4`, and `EmporiumUpgradeable` registered as an external action with `Hinkal` as `allowedRecipient`.
2. Fund `EmporiumUpgradeable` with e.g. 1000 `TestERC20` tokens (simulate leftover/in-flight balance) — `assertEq(token.balanceOf(address(emporium)), 1000e18)`.
3. As `attacker` (unprivileged EOA), generate `messageSeed` and compute `emporiumMessage = Poseidon(messageSeed)` off-chain; generate a valid Groth16 proof for `MainEVMCircuitMin` with public inputs `[emporiumMessage, timeStamp, calldataHash]`.
4. Build `circomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `relay = address(0)`, `originalSender = attacker`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: emporiumProxy, externalActionMetadata: abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))})], maxFee:0, deadline: block.timestamp+1000, v:0,r:0,s:0})) }`, with `calldataHash` computed via `CircomDataBuilder.getHashedCalldata`.
5. Call `hinkal.transact(a,b,c, dimensions, circomData)` from `attacker`.
6. Assert both sides of the broken equality: before the call `emporium.balanceOf(token) == 1000e18` and `attacker.balanceOf(token) == 0`; after the call assert `emporium.balanceOf(token) == 0` and `attacker.balanceOf(token) == 1000e18`, while `dimensions.tokenNumber == 0` (i.e., zero tokens were "accounted for" in `Hinkal.transact`'s balance-diff loop and in `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loops) — demonstrating assets moved without any accounting check firing.

template MainEVMCircuitMin() {
