### Title
Webhook `shop` tenant field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the tenant identifier (`shop`) that the gem hands to the app's handler is read from an unsigned HTTP header, not from the signed payload. This breaks the binding `shop_authenticated == shop_used_by_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines: [1](#0-0) [2](#0-1) [3](#0-2) 

`hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. `shop` (line 21-23) is read from the `shop-domain` header and is **not** included in the signed string at all.

`Registry.process` then does: [4](#0-3) 

It validates `Utils::HmacValidator.validate(request)` (which only checks the body/HMAC pair against the app's single, shared `api_secret_key`) and, once that passes, forwards `request.shop` — an unauthenticated header value — into `WebhookMetadata` as the trusted tenant identifier for the handler.

`Utils::HmacValidator.validate_signature` confirms this: the signable string used for comparison is `verifiable_query.to_signable_string`, i.e. the raw body only: [5](#0-4) 

Because every shop that installs the same app authenticates webhooks with the exact same `api_secret_key` (the secret is per-app, not per-shop), any merchant that has legitimately installed the app can capture a real `(raw_body, hmac)` pair generated for their own store, then replay an HTTP POST to the app's webhook endpoint with the same body/HMAC but a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body against the secret; `Registry.process` then calls the handler with `shop: request.shop` set to the victim's domain, i.e., the gem itself vouches for a shop value that was never bound by the cryptographic signature. This is the direct analog of the external report's root cause: the field used to key/attribute the action (`shop`, analogous to "which pair owns the liquidity") is not verified as belonging to the entity the signature actually covers (the body, analogous to "the tick range's actual liquidity provider").

### Impact Explanation
Host applications built on this gem key tenant-scoped state (session lookup, data deletion for `shop/redact`/`customers/redact`, order/customer processing, subscription state, etc.) off `WebhookMetadata#shop`, trusting that the gem has authenticated it. Since the gem's own `Registry.process`/`HmacValidator` cannot distinguish "signed body, attacker-chosen shop" from "signed body, correct shop," an attacker with access to any installed store's legitimate webhook traffic can inject payloads attributed to an arbitrary victim shop, causing cross-tenant data confusion/corruption (e.g., triggering privacy-mandated data deletion for a shop that never requested it, or feeding a victim's tenant context with attacker-controlled body content). This matches the Critical "cross-tenant access" impact category, since the tenant/session boundary that host apps rely on this gem to enforce is not actually enforced by the gem.

### Likelihood Explanation
Any user who can install the app on their own store (a normal, unprivileged merchant — no special credentials, tokens, or `api_secret_key` needed) can capture a legitimate webhook delivery to their own endpoint and replay it with a modified shop header; this requires only a network client and does not require breaking any cryptography, since the HMAC never covered the shop field to begin with.

### Recommendation
Bind the shop identity to the verified content: either
1. include the `shop-domain` (and `topic`, `webhook_id`) header values inside the signable string that is HMAC-verified (would require a mirrored change on Shopify's signing side, so more practically),
2. Have `Registry.process`/`HmacValidator` reject the request unless `request.shop` matches a shop the app can independently corroborate (e.g., cross-checked against an active, previously stored offline session for that shop before trusting the header), rather than passing the raw header value straight into `WebhookMetadata` right after a body-only HMAC check, or
3. At minimum, clearly document in `ShopifyAPI::Webhooks::Request` that `shop` is not authenticated by `HmacValidator.validate` and must not be trusted for authorization decisions without additional verification by the host app.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Attacker triggers a real webhook (e.g. `orders/create`) and captures the raw request: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid signature of `B` under the app's shared `api_secret_key`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker sends a new POST to the app's webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header; `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B` (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31), which is unchanged.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, causing the host application to act on attacker-controlled data as if it originated authentically from the victim shop.
