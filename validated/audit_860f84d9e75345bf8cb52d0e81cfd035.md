### Title
Webhook HMAC Signature Covers Only the Raw Body, Not the `shop-domain` Header — Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The external report describes Cryptopunks failing because the marketplace's trust logic implicitly assumes every traded asset conforms to the `ERC721` interface it verifies against, when in fact Cryptopunks' actual transfer mechanism is out of band from what's checked. The Shopify-API-Ruby analog is structurally the same "verified surface vs. acted-upon surface" mismatch: `ShopifyAPI::Webhooks::Registry.process` validates an HMAC that covers only the webhook's raw body, but then trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that HMAC — as the authoritative tenant identity for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validator computes/compares the signature purely over that signable string: [2](#0-1) 

Yet `Registry.process` uses `request.shop`, `request.topic`, and `request.webhook_id` — all parsed straight from headers and never included in the HMAC computation — to construct the `WebhookMetadata` handed to the app's handler as the trusted identity of the event: [3](#0-2) 

`Request#shop`, `#topic`, and `#webhook_id` are simple header reads with no cryptographic binding to the signature: [4](#0-3) 

This breaks the identity binding: **the shop that is HMAC-verified (verified over body bytes only) ≠ the shop that the application acts on (`request.shop`, taken from an unauthenticated header)**. Because the same app `client_secret` is shared by Shopify across every shop using the app, any two webhooks whose bodies happen to be byte-identical (which happens easily for generic or empty payloads, or payloads an attacker can engineer as one of their own shops) will produce an identical valid HMAC regardless of which shop it was actually sent for. An attacker who owns/controls one shop that has installed the target app can capture a legitimate `(raw_body, hmac)` pair from a webhook Shopify sent them, then replay that raw body and HMAC to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header swapped to a victim shop. `HmacValidator.validate` will still return `true` because it never inspects the headers, so `Registry.process` will hand the handler a `WebhookMetadata` claiming to be about the victim shop.

### Impact Explanation
This is a cross-tenant confusion vector: the host application's webhook handler receives an event attributed to a shop domain it did not actually originate from, verified only by an HMAC that never bound that domain. If the handler uses `data.shop` to look up sessions, update per-shop state, or make authorization decisions (the documented, expected usage per `docs/usage/webhooks.md`), an attacker-controlled shop can inject events that the host app believes came from a different tenant — a cross-tenant access/data-integrity breach that maps directly to this assessment's Critical category (cross-tenant access).

### Likelihood Explanation
Exploitability requires only that the attacker run their own shop with the target app installed (no privileged credentials, access tokens, or `client_secret` needed) and be able to induce or await a webhook whose body matches (or can be engineered to match) content valid for the victim tenant, then replay it with a modified `shop-domain` header to the app's public webhook endpoint. The library provides no mitigation — `to_signable_string` structurally excludes headers from the signed content, so any consumer that trusts `WebhookMetadata#shop` without independent verification is exposed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`/`api-version`) header values in the HMAC-signed content used by `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request`, or otherwise cryptographically bind the shop domain to the signature so header tampering invalidates the HMAC. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker registers/owns Shop A, which has the target app installed; Shopify sends a webhook to the app's endpoint: body `{}`, header `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of "{}">` (valid because `HmacValidator` only signs `raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`).
2. Attacker captures this request and replays it to the same endpoint, substituting `x-shopify-shop-domain: victim-shop.myshopify.com` while keeping the same body `{}` and same HMAC value.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `raw_body` — it never looks at `shop-domain` (`lib/shopify_api/webhooks/registry.rb:188-200`).
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: {}, ...)`, and any app logic keyed on `data.shop` now believes this event is legitimately about `victim-shop`, despite that shop never having sent it.
