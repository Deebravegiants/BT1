### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify with the app's `api_secret_key`. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read directly from unauthenticated request headers and passed straight through to the host application's handler, without ever being covered by the HMAC. This breaks the identity binding: "shop attributed to the webhook" ≠ "shop bound to the HMAC-verified bytes."

### Finding Description
`Registry.process` only checks the HMAC over the body before dispatching: [1](#0-0) 

`Request#hmac` is computed from the `hmac-sha256` header, and `to_signable_string` — the value that is actually HMAC-verified — is just `@raw_body`: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from headers with no cryptographic binding to the HMAC at all: [3](#0-2) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [4](#0-3) 

Because `api_secret_key` is a single shared secret across every shop that installs the app (not a per-shop secret), any legitimate/authenticated webhook body+HMAC pair a merchant can generate (or capture) for their own shop remains valid when replayed with the `shop-domain` header changed to a different, victim shop domain — the signature still validates because the header isn't part of the signed content. `Registry.process` then constructs `WebhookMetadata` using this unauthenticated `request.shop` value and hands it to the app's handler: [1](#0-0) 

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` (along with `code`, `host`, `state`, `timestamp`) *is* included in `to_signable_string` and thus is properly HMAC-bound: [5](#0-4) 

This is the exact bug class described in the external report — a field that is *acted upon* (here, tenant/shop attribution for webhook processing) is not covered by the integrity check (here, the HMAC), even though a sibling code path (`AuthQuery`) in the same gem correctly includes the field in the signed payload.

### Impact Explanation
Any host application that relies on `ShopifyAPI::Webhooks::Registry.process` / `WebhookMetadata#shop` to determine which merchant's tenant data a webhook payload belongs to can be tricked into attributing attacker-controlled webhook body content (e.g., product/order fields the attacker's own shop can freely set) to an arbitrary victim shop, since the `shop-domain` header is never authenticated. This is a cross-tenant access vector: data belonging to one tenant can be forged to appear as belonging to a different tenant, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker control (or install the app on) one legitimate shop and be able to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers alongside a body+HMAC pair that is valid for their own shop's real webhook traffic (all webhooks for a given app share the same `api_secret_key`, so the HMAC over the body is shop-independent). No credentials, access tokens, or privileged access are needed beyond normal app installation, making this practically reachable for any unprivileged internet user who is a merchant on the platform.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`/`api-version`) header values into the HMAC-verified signable content, or otherwise cryptographically bind them to the payload, so that `Utils::HmacValidator.validate` fails if any of these attribution fields are altered independently of the signed body. At minimum, document prominently that `request.shop` is not authenticated and must not be trusted for tenant-scoping decisions without additional verification (e.g., cross-checking against a stored session/shop record).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and receives a legitimate Shopify webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` — the `shop-domain` header is never part of `to_signable_string`, see: [6](#0-5) 
4. `Registry.process` dispatches to the handler with `shop: request.shop == "victim-shop.myshopify.com"`, even though the body `B` originated from and was signed for `attacker-shop.myshopify.com`, see: [7](#0-6) 
5. If the host application's handler uses `data.shop` to select which tenant's records to create/update from `data.body`, attacker-controlled content is written under the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
