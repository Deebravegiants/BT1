### Title
Webhook `shop` identity is trusted from an unauthenticated header while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `x-shopify-shop-domain` header straight through to the app's handler as the trusted tenant identifier, without that header ever being covered by the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload [2](#0-1) . `Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which HMACs `to_signable_string`, i.e. the body) and then immediately builds `WebhookMetadata` using `request.shop` from the unsigned header, passing it to the registered handler as the tenant identity [3](#0-2) .

This breaks the intended identity binding: `shop header used by handler == shop bound by HMAC`. In reality, the HMAC binds only the body bytes to the app's `api_secret_key`; it says nothing about which shop's header accompanies that body. Any request whose body+HMAC pair is a validly-signed pair (e.g., replayed from a previously delivered, legitimately-signed webhook, or from a webhook topic where the body's own shop context does not match the header) will pass `HmacValidator.validate` regardless of what value is placed in the `shop-domain` header, because that header byte range is never fed into `compute_signature` [4](#0-3) .

### Impact Explanation
This is a cross-tenant identity-confusion issue: an unprivileged attacker who can capture (or otherwise obtain) one validly-signed webhook body/HMAC pair — which is not treated as a secret and is delivered over plain HTTP callback endpoints controlled by the merchant's app — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary value for the `x-shopify-shop-domain` header. `Registry.process` will accept it (HMAC validation only checks the body) and dispatch `WebhookMetadata.shop` set to the attacker-chosen shop string to the app's `handler.handle` callback [5](#0-4) . If the host application (reasonably, given the gem's own `WebhookMetadata#shop` field and documented use) trusts this field to select which merchant's tenant data/session/access token to act on, this allows cross-tenant data poisoning or actions attributed to the wrong shop, without any credential, access token, or `client_secret` in the attacker's possession — only knowledge of a previously-observed valid (topic, body, hmac) triple.

### Likelihood Explanation
Exploitation requires the attacker to have seen at least one legitimately signed webhook delivery (body + HMAC), which is plausible for topics with static, predictable, or attacker-observable payload content (e.g., a webhook whose body doesn't itself embed a shop identifier, or a topic replayed from a public/test store the attacker controls, since normal merchants also receive their own webhook signed with the same shared `api_secret_key` used across the app for all its installed shops). Because the `shop-domain` header is entirely decoupled from the signature, the reuse works for any body regardless of source shop, and the gem provides no built-in defense (no nonce/timestamp uniqueness check, no binding of shop to signature) beyond what's shown here.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable string for webhook requests, or otherwise cryptographically bind the `shop-domain` header value to the signed body before exposing it via `WebhookMetadata`. At minimum, document/enforce that `WebhookMetadata#shop` must be cross-validated against a known/expected shop before being trusted by the host application, and consider deduplicating on `webhook_id` to prevent raw replay.

### Proof of Concept
1. Attacker (or app) legitimately receives (or is the recipient of) a real webhook: body `B`, `x-shopify-hmac-sha256: H` (valid signature of `B` under the app's `api_secret_key`), and `x-shopify-shop-domain: legit-shop.myshopify.com`.
2. Attacker resends the identical `B` and `H` to the same app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (or any other tenant string known to the attacker).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `to_signable_string` returns `B` only [1](#0-0) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and compares against `H` — this succeeds because `B` and `H` are unchanged [6](#0-5) .
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...))` [5](#0-4) , causing the app's handler to process content `B` as if it originated from `victim-shop.myshopify.com`, despite the signature never having attested to that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
