Audit Report

## Title
Missing `return` after failed email-claim extraction allows OIDC session creation with an empty/unverified email - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
In `oidcAuthenticator.handleTokenExchange`, the `email, ok := claims["email"].(string)` type assertion failure branch logs an error and writes a `500` response but does not `return`, unlike every other validation branch in the function. Execution continues to role mapping and to the `INSERT INTO oidc_sessions` statement, persisting a session bound to an empty `user_email` string, and the handler proceeds to set the session cookie as if authentication succeeded.

## Finding Description
`handleTokenExchange` at `core/sessions/oidcauth/oidc.go` lines 163-270 handles the OIDC token exchange callback. All prior failure conditions (bad JSON, bad state, exchange failure, missing `id_token`, verification failure, claims parse failure, `ExtractIDClaimValues` failure) call `return` immediately after writing the error response. The `email` extraction branch at lines 226-230 breaks this pattern: it writes the error but has no `return`, so execution falls through to `IDClaimsToUserRole` (line 234) and then to the `oi.ds.ExecContext` INSERT into `oidc_sessions` (lines 250-256) using the zero-value `email` (`""`). The subsequent code also does not `return` on the INSERT error (line 257-260), and unconditionally proceeds to set the session cookie via `ginSession.Set(webauth.SessionIDKey, clSession.ID)` and `ginSession.Save()` at lines 264-270. This is a genuine, deterministic control-flow defect: the existing validation is checked but not enforced.

## Impact Explanation
If the configured OIDC identity provider returns an ID token/claims payload lacking a usable `email` field (a string) while still including group claims that map to a role via `IDClaimsToUserRole`, the handler creates a persisted `oidc_sessions` row with `user_email=''` and an assigned role, and returns a valid session cookie to the caller. This is an authentication/session-integrity defect in the node's admin API auth layer: it decouples the session/role binding from a verified email identity, weakening RBAC and audit-trail integrity for the node's admin API, matching the "node API authentication or role bypass" impact category.

## Likelihood Explanation
Triggering this requires the OIDC identity provider used by the node to return claims without a valid `email` field but with group claims sufficient for `IDClaimsToUserRole` to succeed. This depends on the specific IdP's behavior/configuration and is not directly controllable by an arbitrary unauthenticated internet client absent influence over the configured IdP's responses; however, the code defect itself is deterministic and unconditional once that claims shape occurs (e.g., misconfigured or loosely-validating IdPs, or IdPs that allow optional/omittable email claims). This is a real, reproducible logic bug distinct from a purely speculative or unreachable condition.

## Recommendation
Add a `return` statement immediately after writing the error response in the `email` extraction failure branch (and also after the INSERT error branch at line 257-260, which has the same missing-return defect):
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally add a check rejecting empty `email` strings before the INSERT, and add a regression test asserting that a claims payload lacking a usable `email` results in no `oidc_sessions` row and no session cookie being issued.

## Proof of Concept
1. Configure the node with `AuthenticationMethod = "oidc"` and a test/mock OIDC provider.
2. Drive `/oidc/authenticate/callback` with a valid `state` and a `code` that exchanges for an ID token whose claims include group claims mapping to a role (e.g. `EditClaim`) but omit the `email` claim (or set it to a non-string value).
3. Observe the server logs `"Failed to get email from claims..."` and writes a `500` body, but does not stop: a Go handler integration test (using `httptest`) can assert a new row is inserted into `oidc_sessions` with `user_email=''` and that `ginSession.Get(webauth.SessionIDKey)` is set in the response cookie, proving the missing `return` allows session creation with an unverified/empty email.
