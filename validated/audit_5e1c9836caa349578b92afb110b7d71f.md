### Title
Webhook shop/topic identity is trusted from unauthenticated headers while only the body is HMAC-covered, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator` covers exclusively the JSON payload bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in the signed content, yet `Registry.process` forwards them unchecked to the app's handler as if they were authenticated.

### Finding Description
`Request#hmac`/`#to_signable_string` bind the HMAC signature to `@raw_body` only: [1](#0-0) 
All identity-relevant fields are parsed from headers with no cryptographic binding: [2](#0-1) 
`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` (unauthenticated header values) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The binding that should hold is: `shop reported to the handler == shop that produced the HMAC-signed body`. Because the signature only certifies the body bytes, this equality does not hold — any request whose body byte-for-byte matches a body that was legitimately HMAC-signed for the sender's own shop will pass `Utils::HmacValidator.validate`, regardless of what `shop`/`topic` headers accompany it.

### Impact Explanation
An unprivileged app user who has their own legitimate shop installation (and therefore legitimately receives webhooks HMAC-signed with the shared `api_secret_key`) can capture one of their own valid webhook deliveries and replay the identical body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a different, victim tenant. `Utils::HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the event belongs to the victim shop. Any app that uses `data.shop` from the handler (as the library's own documentation instructs) to select which tenant's data to update/create will process attacker-controlled data under another merchant's identity — a cross-tenant confusion/injection primitive, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires possessing one's own legitimate app installation (any customer of a multi-tenant Shopify app) and the ability to replay an HTTP POST with attacker-chosen headers — no access to the `api_secret_key`, access tokens, or any other tenant's credentials is needed. This is a realistic, low-effort attack path for any external, unprivileged user who is simply an ordinary merchant/customer of the app.

### Recommendation
Bind the shop/topic identity into the signed material used for HMAC verification (e.g., include the `shopify-shop-domain` and `shopify-topic` header values in `to_signable_string`, or independently verify that `request.shop` matches a shop the app has an active session/registration for) before handing `WebhookMetadata` to handlers.

### Proof of Concept
1. App merchant M installs the app; Shopify sends M a legitimate webhook `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: m-shop.myshopify.com`.
2. M's own client resends the identical body `B` and the identical, still-valid HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — it passes.
4. `handler.handle(data: WebhookMetadata.new(shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though Shopify never issued this webhook for that shop, letting M inject/forge data attributed to `victim-shop`.
