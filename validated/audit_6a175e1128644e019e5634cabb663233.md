### No vulnerability found for this question.

**Rationale:** In `prepareSwapSignedData` (packages/internal-utils/src/utils/prepareBroadcastRequest.ts), the `TRON` branch simply reformats the wallet-provided signature into the `tip191` payload shape using `transformERC191Signature`, and does not use `userInfo.userAddress` at all in the returned object [1](#0-0) . The same is true for the sibling `ERC191` branch, which also omits `userInfo.userAddress` from its output [2](#0-1) . There is no client-side derivation of a `signer_id` from `userInfo.userAddress` for these signature types that could be "broken" by a mismatched key — the function is purely a serialization/formatting step used by `publishIntent`, which forwards the resulting `signed_data` to the solver relay / intents contract unchanged [3](#0-2) .

The actual cryptographic binding between the tip191/erc191 signature bytes and the signer identity is established by the intents contract itself when it recovers the secp256k1 address from the signature and derives `signer_id` from that recovered address — not from any client-supplied `userAddress` string. Since the SDK never asserts or relies on `userInfo.userAddress == recovered address` for this signature standard, and downstream on-chain verification is exactly what determines the true signer, an attacker submitting their own signature cannot cause funds to be attributed to a victim's `signer_id`; the contract will simply process the intent as signed by the attacker's own recovered address. This falls under the excluded category of "trust assumptions about... the intents contract's own signature and nonce verification," which is explicitly the mechanism preventing this divergence from having real impact.
