### Title
OAuth callback `shop` parameter is not validated against `ShopValidator`, allowing the app's `client_id`/`client_secret` to be sent to an attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` build the token-exchange request host directly from the caller-supplied `shop` string, without ever routing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. Every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, `RefreshToken`, `Clients::Graphql::Storefront`) explicitly validates the shop domain with `ShopValidator` before using it as a request host, but the classic authorization-code OAuth path does not.

### Finding Description
`validate_auth_callback` takes an `AuthQuery` built from raw HTTP callback parameters and, after a successful HMAC check, does the following: [1](#0-0) 

The HMAC check (`Utils::HmacValidator.validate(auth_query)`) verifies that `shop` (among other fields) was part of a string that was signed with the app's `api_secret_key`: [2](#0-1) [3](#0-2) 

This proves the `shop` value has not been *tampered with in transit*, but it does **not** prove the `shop` value is a legitimate `*.myshopify.com` (or other trusted Shopify) domain — the HMAC only binds "whatever bytes the caller supplied" to a valid signature, it doesn't bind "these bytes are a Shopify hostname." `Session.new(shop: auth_query.shop)` is then used directly, unsanitized, to build the request: [4](#0-3) 

This session is passed into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which builds the destination URL from `session.shop` and then POSTs a body containing `client_id` and `client_secret` to `https://#{shop}/admin/oauth/access_token`. The identity binding that should hold is: **the host that receives `client_secret` == a Shopify-trusted domain**. Here that binding is broken because nothing enforces the right-hand side — `auth_query.shop` (and, symmetrically, the `shop:` parameter accepted by `begin_auth`) is used verbatim as the request host: [5](#0-4) 

Compare this with the other OAuth-adjacent flows in the same file/module family, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing a session/host from a caller-supplied `shop` string: [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` exists precisely to prevent host strings like `attacker.example`, `myshopify.com.evil.com`, or `shop.myshopify.com@evil.com` from being treated as a legitimate Shopify host: [8](#0-7) [9](#0-8) 

The classic OAuth callback path (`oauth.rb`) is the one flow that skips this check entirely (confirmed by `grep` showing no `ShopValidator` usage in `oauth.rb`, versus its use in `client_credentials.rb`, `token_exchange.rb`, `refresh_token.rb`, and `graphql/storefront.rb`).

### Impact Explanation
This qualifies as High impact per the rules: "SSRF with the app's credentials." If a host application passes a hosting application's raw `shop` query parameter through to `AuthQuery`/`begin_auth` without independently sanitizing it (which the library's own documented usage pattern in `docs/usage/oauth.md` — `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters.symbolize_keys.except(:controller, :action))` — does not do), an attacker who can influence the `shop` query parameter of the callback (or the initial login flow) can redirect the token-exchange POST containing the app's `client_id` and `client_secret` to an arbitrary host they control, exfiltrating the app's `client_secret`.

### Likelihood Explanation
Likelihood is constrained by two factors: (1) `validate_auth_callback` requires a valid HMAC over the query including `shop`, so exploiting it end-to-end against `validate_auth_callback` requires either a valid HMAC-signed request from Shopify for an attacker-influenced `shop` (not achievable without the secret) — however `begin_auth`, which has no HMAC gate at all, accepts `shop:` directly from the caller and builds `auth_base_uri(shop)` with no validation, so any host application that forwards a user/query-controlled `shop` value into `begin_auth` (a documented, expected usage pattern — e.g. `shop = request.headers["Shop"]` per `docs/usage/oauth.md`) sends `client_id` in the authorize redirect to that host. (2) Whether `client_secret` leaks depends on the host app's fidelity in passing unsanitized `shop` values, but the gem provides no defense-in-depth here, unlike its sibling flows.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` in `begin_auth` before constructing `auth_base_uri`, and in `validate_auth_callback` before constructing `null_session`/before using `auth_query.shop` to build the token-exchange session and subsequent `Session.from` call — mirroring the pattern already used in `client_credentials.rb` and `token_exchange.rb#migrate_to_expiring_token`.

### Proof of Concept
1. Host application implements the documented pattern for login: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` (as shown in `docs/usage/oauth.md`).
2. Attacker sends `shop = "attacker.example"` (no validation is performed inside `begin_auth`).
3. `auth_base_uri("attacker.example")` returns `https://attacker.example/admin`, and the resulting `auth_route` (containing `client_id`) is returned to be used as a redirect.
4. If the host app also forwards this same unsanitized `shop` into the callback's `AuthQuery` and a matching state/HMAC pair is ever produced against `attacker.example` (e.g., through a self-signed callback replay or a host app that stores/regenerates state per `shop`), `validate_auth_callback` will POST `client_id`/`client_secret` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app secret. The core root-cause defect — `oauth.rb` never sanitizing `shop` via `ShopValidator`, unlike `client_credentials.rb`/`token_exchange.rb` — is confirmed directly by code inspection.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
```
