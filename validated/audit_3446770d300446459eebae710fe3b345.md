Audit Report

## Title
HTTP Action response cache key omits `WorkflowID` and mTLS credentials, contradicting documented workflow isolation and enabling cross-workflow response leakage - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's HTTP Action response cache (`responseCache`) is documented as workflow-isolated ("Cache Key: Generated from workflow ID and request hash", "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage") but the cache key is derived solely from `gateway.OutboundHTTPRequest.Hash()`, which the repository's own test suite proves is identical across different `WorkflowID`s and is only differentiated by `WorkflowOwner`. Additionally, mTLS client credentials (`OutboundHTTPRequest.Mtls`), which determine which authenticated HTTP client executes the request, are not folded into the hash, so a response fetched using one workflow's mTLS certificate can be served from cache to a subsequent request for the same owner/method/URL/headers/body that lacks (or has different) mTLS credentials.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` key the cache map exclusively by `req.Hash()`: [1](#0-0) [2](#0-1) 

The README explicitly documents workflow-scoped cache keys and isolation: [3](#0-2) 

But the repository's own test suite, `TestRequestHash`, asserts the opposite behavior for `Hash()` — that differing `WorkflowID` values produce an *identical* hash, while only `WorkflowOwner` differentiates it: [4](#0-3) 

This is a genuine contradiction between the documented security guarantee and the code's actual (and test-verified) behavior: two different workflows sharing the same `WorkflowOwner` that issue byte-identical outbound HTTP requests (method, URL, headers, body) will collide on the same cache key in `rc.cache`, and `Fetch`/`Set` perform no additional per-workflow segregation before reading or writing that entry. Separately, `gatewayHandler.send` selects a throwaway mTLS-authenticated client keyed on `req.Mtls`, but this field is not part of `Hash()`, so credential material is decoupled from cache key derivation. `makeOutgoingRequest` calls into the cache using attacker/workflow-controlled `CacheSettings.MaxAgeMs`/`Store` fields, so this path is reachable by ordinary workflow-originated HTTP Action requests, not requiring any special privilege beyond running a workflow under a shared owner.

## Impact Explanation
This is a cross-workflow (cross-tenant, within the same owner) response confusion bug in the internet-facing HTTP capability handler of the gateway. A workflow operator running multiple workflows (or an owner whose workflows share default/templated headers) can have one workflow's cached HTTP response — potentially including data fetched via mTLS-authenticated calls — silently served to a different, unrelated workflow. This breaks the documented workflow-isolation guarantee and can leak privileged response content across the workflow boundary; it maps to the "cross-user response corruption" impact class for the gateway.

## Likelihood Explanation
The bug is deterministic and requires only that two workflows under the same `WorkflowOwner` issue outbound HTTP requests with matching method/URL/headers/body and have `CacheSettings.Store`/`MaxAgeMs` set (both workflow-controlled fields) — a realistic condition for workflows built from shared templates hitting common APIs. No operator, admin, or host-level access is needed; it's reachable purely through normal HTTP Action capability usage.

## Recommendation
Fold `WorkflowID` into `OutboundHTTPRequest.Hash()` (or key the cache directly on `WorkflowID` per the documented design) so cache entries cannot cross workflow boundaries. Additionally, hash a fingerprint of `Mtls` credentials into the cache key (or exclude Mtls-bearing requests from caching entirely) so credentialed responses cannot leak to uncredentialed callers. Add regression tests asserting different `WorkflowID`s and different `Mtls` values produce different hashes, matching the README's isolation claim.

## Proof of Concept
1. Construct `OutboundHTTPRequest` `req1` with `WorkflowOwner="0xOwner"`, `WorkflowID="wf-A"`, `Method=GET`, `URL="https://api.example.com/data"`, `CacheSettings={MaxAgeMs:60000, Store:true}`; call `responseCache.Fetch(ctx, req1, fetchFn, true)` — this populates `rc.cache[req1.Hash()]`.
2. Construct `req2` identical except `WorkflowID="wf-B"`.
3. Call `responseCache.Fetch(ctx, req2, fetchFn2, true)` and observe `fetchFn2` is never invoked and `req1`'s cached response is returned, because `req1.Hash() == req2.Hash()` — directly demonstrated by the existing test `TestRequestHash/having_different_workflowID_results_in_same_Hash` in `response_cache_test.go` (lines 139-149).

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
