### Title
Webhook shop-domain/topic identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the raw request body against the `hmac-sha256` header, then forwards the **unauthenticated** `shop-domain` and `topic` headers to the app's handler as trusted identity fields.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that signable string using the app's `api_secret_key` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` performs exactly one check — `HmacValidator.validate(request)` — and then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . The gem's own documentation instructs apps to treat `data.shop` as the authenticated shop identity and to key downstream work (e.g. job enqueueing) off it directly: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) , and states that `process` "will verify the request did indeed come from Shopify" [6](#0-5) , without qualifying that only the body — not the shop/topic headers — is verified.

This breaks the intended identity binding: `HMAC(body, secret) == received_hmac` is verified, but the binding `shop_header == shop_that_produced_this_body` is never checked. Any party that can obtain one valid `(raw_body, hmac)` pair signed with the app's secret for any topic (e.g. a merchant who installs the app on their own store, shop A, and receives a legitimate webhook) can replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (shop B) and/or `x-shopify-topic` header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and the handler receives `WebhookMetadata` claiming the payload belongs to shop B/topic X when it actually originated from shop A/topic Y.

### Impact Explanation
This is a genuine violation of the "bytes verified vs. bytes parsed / field acted on but not covered by HMAC" bug class: the app's tenant-scoping decision (`data.shop`) and the semantic type of the payload (`data.topic`) are trusted headers that fall outside the cryptographic envelope. Depending on how the host app uses `data.shop` (which the docs explicitly instruct apps to do — to select which merchant's session/store the webhook data applies to), this enables **cross-tenant data injection**: an attacker-controlled shop's legitimate webhook traffic can be relabeled to appear to originate from a victim shop, causing the app to write/process data (orders, customer data-requests, `app/uninstalled`, etc.) under the wrong tenant. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is bounded by the need for an attacker to first obtain one valid `(raw_body, hmac)` pair. This is trivially satisfiable by any unprivileged internet user who installs the app on their own (attacker-owned) shop — a normal, unprivileged onboarding flow requiring no special access, no leaked credentials, and no privileged account. Shopify will deliver legitimate, correctly-signed webhooks to that installer for their own shop, giving the attacker a valid signed body they can freely replay with forged `shop`/`topic` headers against the same public webhook endpoint.

### Recommendation
Bind the shop, topic, and other routing metadata into the HMAC-verified signable string (or otherwise cryptographically/independently confirm the shop-domain header against a value derived from the signed payload/session before constructing `WebhookMetadata`), and update `docs/usage/webhooks.md` to make clear that only the body is HMAC-verified, so host apps do not treat `data.shop`/`data.topic` as fully authenticated without additional server-side tenant confirmation (e.g. cross-checking against a shop that is already known to have the webhook topic registered).

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker-shop.myshopify.com`, completing legitimate OAuth.
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and its valid HMAC, then re-sends an HTTP request to the same endpoint with the identical body `B` and HMAC header, but with `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Registry.process` calls `HmacValidator.validate(request)` [7](#0-6) , which succeeds because it only checks `B` against the HMAC — it never inspects the `shop-domain` header.
5. The handler is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` while the body content actually belongs to `attacker-shop.myshopify.com`, allowing the app to process/store attacker-controlled data under the victim shop's tenant context.
