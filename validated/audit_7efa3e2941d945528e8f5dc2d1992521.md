## Analysis

The Fleet vulnerability's bug class is: a caller-supplied "options" object is merged onto a target structure without filtering out security-sensitive keys, letting the caller silently overwrite fields it should never control. The direct analog in this repo is in the intent payload merge logic of `IntentExecuter`.

### Root cause [1](#0-0) 

`mergeIntentPayloads` takes the SDK-computed `defaultPayload` (whose `verifying_contract` is fixed to `this.envConfig.contractID`, the actual on-chain intents contract for the configured environment) and unconditionally spreads the caller-supplied `customPayload` on top of it:

```
return defaultIntentPayloadFactory(salt, {
    ...basePayload,
    ...customPayload,   // <-- can override verifying_contract, signer_id, deadline
    intents: ...
});
```

`customPayload` is the return value of `intentPayloadFactory`, which is exposed publicly through `SignAndSendArgs.payload` [2](#0-1)  and is documented only as a way to "add or modify intent primitives," with the example limited to the `intents` array. The type, however, is `Partial<IntentPayload>` [3](#0-2) , which also includes `verifying_contract` and `signer_id` — fields that are supposed to be fixed by the SDK/environment, not by the payload-modification hook.

The same pattern exists one level lower: `IntentExecuter.signAndSendIntent` itself destructures `...intentParams` from its arguments and spreads it directly after the computed `verifying_contract`: [4](#0-3) 

```
const verifyingContract = this.envConfig.contractID;
let intentPayload = defaultIntentPayloadFactory(salt, {
    verifying_contract: verifyingContract,
    ...intentParams,   // <-- can also override verifying_contract
});
```

`IntentExecuter` is exported from the package entrypoint (`packages/intents-sdk/index.ts`), making it part of the public API surface that integrators can instantiate and call directly (not only through `IntentsSDK.signAndSendIntent`, which happens to pass a fixed whitelist of fields and is therefore not exploitable through that specific call site).

### Why this matches the Fleet bug class

The equality that should hold is: `verifying_contract` used when signing == `envConfig.contractID` for the configured environment (the value the SDK computed and intends to enforce). Because the merge does not filter this key out of the caller/factory-supplied object, an integrator who forwards a payload-modification object built from external/less-trusted input (e.g., quote/solver metadata, or naive request forwarding as suggested by the documented "modify the draft" pattern) can cause `intentSigner.signIntent` to sign against an attacker-chosen `verifying_contract` instead of the real intents contract — analogous to how Fleet's `namespaceLabels` merge let an attacker overwrite protected `pod-security.kubernetes.io/` labels.

### Title
Unfiltered merge of caller-supplied payload/options overrides protected `verifying_contract`/`signer_id` in `IntentExecuter` — ([File: packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts])

### Summary
`mergeIntentPayloads` and the top-level `IntentExecuter.signAndSendIntent` spread caller-supplied objects (`intentPayloadFactory` return value / raw call args) over the SDK-computed intent payload without excluding the security-sensitive `verifying_contract` and `signer_id` fields, allowing them to be overwritten before signing.

### Finding Description
`signAndSendIntent` computes `verifying_contract` from `this.envConfig.contractID` — this value is meant to bind every signed intent to the correct on-chain intents contract for the configured environment. That computed value is then spread first and `...intentParams` (the rest of the call arguments) is spread after it, so any `verifying_contract` key present in the caller's arguments silently wins. The same problem repeats in `mergeIntentPayloads`, where `...customPayload` (the object returned by the user-supplied `intentPayloadFactory` hook, documented and typed only as a way to add/modify `intents`) is spread after `...basePayload`, again allowing override of `verifying_contract` and `signer_id`. Neither call site strips these protected keys before merging, unlike, e.g., how Fleet's patch strips `pod-security.kubernetes.io/` keys before applying namespace label options.

### Impact Explanation
If `verifying_contract` is overridden to a value different from `envConfig.contractID`, `intentSigner.signIntent` produces a signature bound to the wrong contract. Depending on the signing standard, this can either invalidate the intent (denial for the user) or, more seriously, produce a valid signature over a payload whose domain/contract binding differs from what the user/wallet UI implies is being authorized — matching the "High: a signature bound to the wrong contract, signer, or nonce" impact category.

### Likelihood Explanation
Exploitation requires an integrator to pass through a caller/factory-supplied object that includes a `verifying_contract` or `signer_id` field into `IntentExecuter.signAndSendIntent` or into an `intentPayloadFactory` callback — which the documented API surface (`SignAndSendArgs.payload`, typed as `Partial<IntentPayload>`) does not prevent, since it exposes fields beyond `intents`. This does not require the top-level `IntentsSDK.signAndSendIntent` wrapper (which whitelists fields) to be bypassed, but does require use of the lower-level, exported `IntentExecuter` class or a `payload` factory that echoes untrusted data — a realistic integration pattern given the class is part of the public SDK entrypoint and the documented purpose of the hook.

### Recommendation
Explicitly strip `verifying_contract`, `signer_id`, and `nonce` from `customPayload`/`intentParams` before merging in both `mergeIntentPayloads` and `IntentExecuter.signAndSendIntent`, so these fields can only be set by the SDK's internal computation (mirroring Fleet's fix of filtering out `pod-security.kubernetes.io/`-prefixed keys before applying `namespaceLabels`).

### Proof of Concept
```ts
const exec = new IntentExecuter({
  envConfig, intentSigner, intentRelayer,
  intentPayloadFactory: async () => ({
    verifying_contract: "attacker-contract.near", // not filtered out
  }),
});

await exec.signAndSendIntent({
  intents: [{ intent: "transfer", receiver_id: "alice.near", tokens: { "wrap.near": "1000" } }],
  salt,
});

// instead of envConfig.contractID

async function mergeIntentPayloads(
	defaultPayload: IntentPayload,
	intentPayloadFactory: IntentPayloadFactory,
	salt: Salt,
): Promise<IntentPayload> {
	const customPayload = await intentPayloadFactory(defaultPayload);
	const customPayloadIntents = customPayload.intents ?? [];

	const { nonce: _nonce, ...basePayload } = defaultPayload;

	return defaultIntentPayloadFactory(salt, {
		...basePayload,
		...customPayload,
		intents: Array.from(
			new Set([...customPayloadIntents, ...basePayload.intents]),
		),
	});
}
