This confirms the vulnerability. `HmacValidator.validate` calls `compute_signature(verifiable_query.to_signable_string, secret)` and `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while the HMAC comparison itself is only computed over that signable string and the received `hmac` header [2](#0-1) . The `shop-domain` header is never included in the signed material, and `Registry.process` forwards `request.shop` — the raw, unvalidated header value — straight into `WebhookMetadata.new(shop: request.shop, ...)` after only checking the HMAC [3](#0-2) . `ShopValidator.sanitize!` is never called anywhere in the webhook path .

### Title
`Webhooks::Registry.process` trusts unauthenticated `shop-domain` header not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Webhooks::Request#shop` returns the raw `x-shopify-shop-domain`/`shopify-shop-domain` header value with no sanitization, and the HMAC verification performed in `Utils::HmacValidator.validate` only covers `@raw_body` (`to_signable_string`), never the shop header. Since an attacker who owns a legitimate development shop can receive genuinely HMAC-signed webhooks for their own shop/body pair, they can replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value, and `Registry.process` will forward that forged `shop` value unchanged to the app's handler inside `WebhookMetadata`.

### Finding Description
The binding the gem is supposed to guarantee is: **shop identified by the HMAC-signed material == `shop` delivered to the handler**. In reality the equality that holds is only: **HMAC validates `raw_body` == `raw_body` signed with `api_secret_key`**, with `shop` excluded entirely from that computation.

Code path:
1. `Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
2. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the request's `hmac` header via `OpenSSL.secure_compare` — no shop-related data enters this comparison [2](#0-1) .
3. `Webhooks::Request#shop` simply reads `shopify_header("shop-domain")` with a `T.cast(..., String)` and no format/domain validation, sanitation, or cross-check against the HMAC-signed payload [4](#0-3) .
4. `Registry.process` checks only `Utils::HmacValidator.validate(request)`, then immediately constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the app's `handler.handle` [3](#0-2) .

`Utils::ShopValidator.sanitize!` exists elsewhere in the codebase (used in OAuth/token-exchange flows) [5](#0-4)  but is never invoked in the webhook path, so nothing normalizes or validates `request.shop` before it reaches app code.

Attacker flow: The attacker installs the app on their own shop A, registers a webhook endpoint, and lets Shopify deliver a genuine webhook `POST` with a valid `x-shopify-hmac-sha256` computed over some `raw_body` for shop A. The attacker then replays that exact `raw_body` and `hmac` value to the app's webhook endpoint, but substitutes the `x-shopify-shop-domain` header with victim shop B's domain. `HmacValidator.validate` still returns `true` because it only checks `raw_body` against `hmac`, which is unchanged. `Registry.process` then calls the handler with `WebhookMetadata#shop == "shop-b.myshopify.com"` even though Shopify never signed anything for shop B and the payload content is really shop A's.

### Impact Explanation
If the app developer's webhook handler uses `data.shop` (per the documented `WebhookMetadata` contract) to look up per-tenant access tokens, write to per-tenant tables, or otherwise scope side effects, this allows one merchant (attacker, shop A) to inject apparently-legitimate webhook payloads under an arbitrary victim merchant's (shop B) identity — a cross-tenant data integrity/access issue. The attacker fully controls the `raw_body` content of their own genuine webhooks (e.g., customer/order data, GDPR payloads, etc.), and each of their own real webhook deliveries can be relayed under any victim shop identity, repeatable indefinitely and against any known/guessed victim shop domain.

### Likelihood Explanation
Preconditions: the app must use this gem as documented (`Webhooks::Registry.process` + `Webhooks::Request`), and the vulnerable handler logic must trust `data.shop` for tenant scoping — which is exactly the documented purpose of `WebhookMetadata#shop`. The attacker's cost is trivial: install the app once on a shop they control (free dev store), capture one genuine webhook delivery, and replay it with a modified header to the app's public webhook endpoint. No secrets, credentials, or privileged access are required, and the attack is fully repeatable against any target shop domain string.

### Recommendation
Do not trust `Webhooks::Request#shop` as authenticated data. Either include the shop domain in the HMAC-signed material (not possible without changing Shopify's webhook signing, which only signs the body), or — more practically — have `Registry.process`/the app cross-check `request.shop` against a shop already known to be legitimately associated with the registered webhook subscription (e.g., verify it matches a shop with an active session/access token in the app's own session storage) before trusting it for tenant-scoped operations, and call `Utils::ShopValidator.sanitize!` on `request.shop` to at least reject malformed/non-Shopify domains. Document clearly that `WebhookMetadata#shop` is not cryptographically authenticated by the HMAC and must not be used as sole tenant-identity proof.

```ruby
require_relative "../test_helper"

class WebhookShopSpoofTest < Minitest::Test
  def test_process_forwards_forged_shop_domain_with_valid_hmac
    real_body = "{}"
    hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, real_body)

    # Attacker's own genuinely-signed webhook (shop A)
    headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => Base64.encode64(hmac),
      "x-shopify-shop-domain" => "victim-shop-b.myshopify.com", # forged: attacker swaps in shop B
    }

    received_shop = nil
    handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shop = data.shop })
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", path: "path", delivery_method: :http, handler: handler)

    request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: headers)

    # HMAC over raw_body still validates (body unchanged)
    assert(ShopifyAPI::Utils::HmacValidator.validate(request))

    ShopifyAPI::Webhooks::Registry.process(request)

    # Binding broken: forged shop-domain reaches the handler unchanged, despite not being part of the signed material
    assert_equal("victim-shop-b.myshopify.com", received_shop)
  end
end
```
This demonstrates that `HmacValidator.validate` returns `true` (equality holds on `raw_body`/`hmac`) while `request.shop`/`data.shop` (the value delivered to app code) diverges from any shop that Shopify actually signed the request for, breaking the intended "signed shop == delivered shop" binding.
