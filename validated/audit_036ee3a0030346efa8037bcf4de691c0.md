### Title
Single-Step `transferCreator` Permanently Freezes Creator Fee Attribution to an Incorrect Address - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator()` lets the current token creator reassign the `creator` role for a launched token in a single, irreversible step, directly overwriting `TokenInfo.creator` in storage. Unlike the protocol's admin-ownership contracts (`Bonding`, `Zap`, `LPLock`, `FeeVault`), which all use `Ownable2StepUpgradeable` specifically to prevent single-step transfers to a wrong address, `transferCreator` has no such two-step confirmation. A creator who fat-fingers the `newCreator` argument, or transfers to a contract/address that cannot call `FeeVault.claim()`, permanently and irrevocably strands all future (and any already-accrued but unclaimed) creator fee income for that token.

### Finding Description
`transferCreator` only checks that `newCreator` is non-zero and that the caller is the current creator, then immediately commits the new address: [1](#0-0) 

```
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
```

`info.creator` is the sole source of fee attribution: every buy/sell fee split routes 0.25% of volume to `FeeVault.accrue(token, creator, ...)` keyed on this address, and only that exact address can later call `FeeVault.claim()` to withdraw its pooled balance: [2](#0-1) 

There is no `pendingCreator` / `acceptCreator` step, no ability for the old creator to cancel, and no admin override to redirect a stuck creator balance. Contrast this with the rest of the protocol, which explicitly hardens `transferOwnership` against exactly this footgun via `Ownable2StepUpgradeable`, as documented and tested in `OwnershipTransferTest`: [3](#0-2) 

`transferCreator` is reachable by any unprivileged token creator with no additional authorization — it is not admin-gated — and directly overwrites the fee-attribution key with no confirmation step, matching the exact bug class in the external report (single-step ownership/role transfer with no safeguard against an incorrect destination).

### Impact Explanation
If `newCreator` is mistyped, is a contract without a mechanism to call `claim()`, or is an address the caller does not control, then:
- All future trading fees (0.25% of every subsequent buy/sell on that token, forever) accrue to `FeeVault.creatorBalance[newCreator]` and become permanently unclaimable.
- The prior creator can no longer claim fees either (`info.creator` no longer matches them), and there is no on-chain path to revert or correct the assignment.

This is a permanent freezing of creator funds inside `FeeVault`, consistent with the "permanent freezing of trader, creator, or LP funds" impact bar. Because there is no cap on trading volume or duration on the curve/post-graduation, the frozen amount can grow unbounded over the token's lifetime.

### Likelihood Explanation
Likelihood is driven purely by user error (fat-fingering an address, or choosing an address/contract that cannot interact with `FeeVault.claim()`), which is a realistic and common occurrence for any ownership/role-transfer function lacking a two-step confirmation — precisely the failure mode the rest of the protocol's admin roles were hardened against. No malicious actor or special privilege is required; the current creator triggers the loss themselves with a single normal transaction.

### Recommendation
Convert `transferCreator` into a two-step process analogous to `Ownable2StepUpgradeable`, e.g., add `pendingCreator[token]` set by the current creator and require `acceptCreator(token)` called by `newCreator` to finalize the change, mirroring the pattern already used for `Bonding`, `Zap`, `LPLock`, and `FeeVault` ownership.

### Proof of Concept
1. Creator launches a token via `Bonding.launch`, becoming `TokenInfo.creator`.
2. Trading occurs; fees accrue to `FeeVault.creatorBalance[creator]` via `Zap`'s fee split and `FeeVault.accrue`.
3. Creator calls `Bonding.transferCreator(tokenAddress, newCreator)` with a mistyped `newCreator` address (non-zero, but not controlled by anyone, e.g. a burn-style or unintended address).
4. Call succeeds — `info.creator` is now the wrong address; `CreatorTransferred` is emitted.
5. All subsequent `FeeVault.accrue` calls attribute the 0.25% creator share to the wrong address.
6. No one can call `FeeVault.claim()` as `newCreator` to retrieve the funds; the balance is permanently stuck in `FeeVault`, and there is no on-chain recovery path since `transferCreator` provides no cancellation or two-step accept mechanism.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
