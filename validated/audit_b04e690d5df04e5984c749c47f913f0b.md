### Title
Webhook shop/topic/webhook-id attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable string used for HMAC validation from the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are actually acted upon by `Registry.process` are read from unauthenticated HTTP headers. The identity binding "shop that produced/authorized this webhook" is never verified against "shop the app attributes the event to," so a party who can obtain one valid `(raw_body, hmac)` pair can replay it with an arbitrary `shop-domain` header and have it accepted as coming from a different tenant.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled straight from client-supplied headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check and then dispatches using the unauthenticated `shop`, `topic`, and `webhook_id` fields, with no additional check that the asserted shop is the one the HMAC actually attests to: [4](#0-3) 

The broken identity binding, stated as an equality that fails to hold:
`shop authenticated by HMAC (none — HMAC only covers @raw_body) != shop used as the tenant key for dispatch (request.shop, taken verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header)`.

Because the signature covers only the byte content of the body, any two requests with identical bodies produce identical valid HMACs regardless of which `shop-domain` header accompanies them. A user who legitimately receives one genuine, correctly-signed webhook for their own shop (e.g., by installing the app on a store they control and triggering an event whose body content they can predict or reuse, such as `app/uninstalled`, `customers/redact`, or any webhook with attacker-influenced/static content) can resend that exact `(raw_body, hmac-sha256)` pair while substituting a victim's `shop-domain` value. `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata` claiming the victim shop.

### Impact Explanation
This crosses a tenant boundary: the app's webhook handler receives and acts on data purportedly from `shop = <victim>` when the cryptographic proof only established "some holder of the shared secret produced this exact body," not "this event originated from this shop." Depending on how the host application's handler uses `data.shop` (looking up the shop's stored session/access token, gating compliance actions like GDPR redact webhooks, updating per-shop state, etc.), this enables cross-tenant data injection or spoofed lifecycle events attributed to a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app or otherwise obtain one legitimate `(raw_body, hmac)` pair for a webhook whose body content is attacker-known/predictable (many mandatory/compliance topics have small, structured, largely static bodies), and (2) the ability to POST an HTTP request with a forged `shop-domain` header to the app's public webhook endpoint. No `api_secret_key`, access token, or privileged account is needed — this is reachable by any unprivileged actor who can trigger or capture one valid webhook delivery for themselves.

### Recommendation
Bind the identity fields into the signed material rather than trusting headers verbatim:
- Extend `to_signable_string` (or add a secondary check) so that `shop`, `topic`, and `webhook_id` are covered by the HMAC verification, consistent with how `Oauth::AuthQuery#to_signable_string` already includes `shop` in its signable params (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`).
- Alternatively, require `Registry.process` callers to supply/verify the expected shop out-of-band (e.g., cross-check `request.shop` against a shop resolved independently of the header before invoking the handler), and document that consumers must not trust `request.shop`/`request.topic` as authenticated unless such a check is performed.

### Proof of Concept
1. Register a handler for topic `T` and capture a real webhook delivery for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid since `H = HMAC(secret, B)`).
2. Resend the same request to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H`, but set `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:26-31) recomputes over `B` only and returns `true`.
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) invokes the handler with `WebhookMetadata.new(topic: T, shop: "shop-victim.myshopify.com", body: parsed(B), ...)`, even though the HMAC never attested to `shop-victim`.
