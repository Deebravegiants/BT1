### Title
`describeWithdrawal` for PoA-bridge withdrawals matches by `assetId` only, causing two same-token withdrawals in one batch to resolve to the same status/txHash - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the correct withdrawal via `findMatchingWithdrawal`, which matches purely by `nep141:<near_token_id> === assetId` and ignores `WithdrawalIdentifier.index` entirely. When two withdrawals of the same PoA token are made in a single `createWithdrawalIntents` batch (e.g., two `nep141:usdt.omft.near` withdrawals to different `destinationAddress`), both `watchWithdrawal` calls (index 0 and index 1) query the same `getWithdrawalStatus` response and both resolve to whichever matching entry `Array.prototype.find` returns first.

### Finding Description
The broken equality: `(status, txHash)` returned for withdrawal at `index:1` should equal the outcome of the withdrawal actually sent to `withdrawalParams[1].destinationAddress`, not the outcome of `withdrawalParams[0]`.

Code path:
- `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns per-bridge `index` values (0, 1, ...) purely based on ordering, with no correlation to any bridge-side withdrawal identity [1](#0-0) .
- `watchWithdrawal` calls `bridge.describeWithdrawal({...args.wid, logger})` per identifier [2](#0-1) .
- `PoaBridge.describeWithdrawal` fetches the withdrawal list for the intent tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, never consulting `args.index` [3](#0-2) .
- `findMatchingWithdrawal` explicitly matches only by `assetId`, documented in its own comment as not supporting multiple withdrawals of the same token in one transaction: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."* [4](#0-3) .

Attacker input: an ordinary user calls `sdk`'s withdrawal creation twice for `nep141:usdt.omft.near` with two different `destinationAddress` values in one multi-payload intent. Nothing in `createWithdrawalIntents` (which just builds independent `IntentPrimitive`s per call, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:142-162`) prevents or dedups this, since each call is unaware of any other pending withdrawal for the same token.

Exploit flow: the PoA bridge indexer returns both completed withdrawals with distinct `transfer_tx_hash`/`address`; `Array.find` returns the first array element for both `describeWithdrawal` calls (index 0 and index 1), so `promises[0]` and `promises[1]` both resolve to the same `{status: "completed", txHash: withdrawals[0].data.transfer_tx_hash}` even though withdrawal 1 actually landed at a different `transfer_tx_hash`/address.

Existing guards do not prevent this: `validateAddress`, `compareAddresses`, `validateWithdrawal`, and `supports()` operate on a single withdrawal in isolation and have no cross-withdrawal dedup/ordering logic; the intents contract's own nonce/signature checks only guarantee the intent was authorized, not which watcher index corresponds to which on-chain withdrawal.

### Impact Explanation
This is a status/txHash misreport, not an on-chain fund misroute — the actual withdrawal amounts still go to their correct `destinationAddress` on the bridge side; what's wrong is what the SDK caller is told about which withdrawal completed with which hash. An integrator that calls `sdk.createWithdrawalCompletionPromises()` and credits/refunds per-index based on `(status, txHash)` can end up crediting the same destination twice (using withdrawal 0's hash for both) or missing the real hash for withdrawal 1's destination — this matches the "High" impact category explicitly listed in the rules ("a status or hash misreport making an integrator credit or refund twice"), not necessarily Critical fund misrouting, since the underlying token movement to `destinationAddress` is unaffected.

### Likelihood Explanation
Preconditions: only require the user to submit two withdrawals of the exact same PoA `assetId` (e.g. same `nep141:...omft.near` token) in one `intents.near` multiPayload, to different addresses — something entirely within an ordinary user's control and explicitly acknowledged as unsupported in the code comment itself. No special token state, solver cooperation, or privileged access needed. Fully repeatable and at zero cost beyond the withdrawal amounts themselves.

### Recommendation
Disambiguate withdrawals belonging to the same `assetId` by an additional bridge-side correlator (e.g., sort matching candidates by `amount`/`destinationAddress`/creation order and consume matched entries so the same withdrawal record cannot satisfy two indices), or reject/refuse batches containing duplicate PoA `assetId` withdrawals at `createWithdrawalIntents`/`validateWithdrawal` time until the POA Bridge API supports per-withdrawal correlation as noted in the existing code comment.

		args: WithdrawalIdentifier & { logger?: ILogger },

		// Response list is unsorted, so we match by assetId instead of index

		if (withdrawal == null) {
			return { status: "pending" };

			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {

				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
