## Analysis Result

The docs explicitly promise: *"This will verify the request did indeed come from Shopify"* (`docs/usage/webhooks.md:125`), and expose `data.shop` from `ShopifyAPI::Webhooks::Registry.process` as an authenticated field the handler is meant to trust (`docs/usage/webhooks.md:14,25-26`). Examining the implementation shows this identity binding is broken.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC computed/verified by `HmacValidator.validate` covers **only the request body**, never the `shop`, `topic`, `webhook_id`, or `api_version` values, which are all pulled straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` taken from that unauthenticated header, passing it directly to the app's handler as the trusted shop identity [3](#0-2) .

Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, an attacker who controls one shop with the app installed can trigger a legitimate webhook (e.g. `orders/create`) to obtain a valid `(raw_body, hmac)` pair signed with the app's real secret. They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds, because the shop header was never part of the signed content, and `Registry.process` calls the handler with `shop: <victim-domain>` — a spoofed identity binding: `hmac_verified(body) == true` does not imply `shop_header == shop_that_sent_request`.

This is not the host application ignoring the gem's contract — the gem's own documentation and the `WebhookMetadata.shop` field advertise `shop` as verified/trustworthy webhook data, while the implementation never binds it into the HMAC-verified payload.

### Title
Webhook `shop` (and `topic`/`webhook_id`) not covered by HMAC verification allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` come from unauthenticated headers. `Registry.process` verifies the HMAC and then forwards these unauthenticated header values to the app's handler as if they were verified, allowing an attacker who obtains any valid `(body, hmac)` pair for the app to relabel it as coming from an arbitrary victim shop.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` this returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers with no cryptographic binding to the HMAC [2](#0-1) . `Registry.process` treats a successful `HmacValidator.validate(request)` as proof the whole request — including `request.shop` — is authentic, then hands `request.shop` to the app's handler via `WebhookMetadata` [3](#0-2) . The documented contract tells integrators `shop` is "The shop domain of the webhook" [4](#0-3)  and that `process` "will verify the request did indeed come from Shopify" [5](#0-4) , encouraging apps to key their per-shop persistence/business logic off this value without re-validating it (see sample handler using `data.shop` directly) [6](#0-5) . Since `api_secret_key` is one static value shared by the app across all installed shops (used identically in `HmacValidator.validate`) [7](#0-6) , any shop with the app installed can generate a validly-signed `(body, hmac)` and relabel it with an arbitrary `shop-domain` header.

### Impact Explanation
This breaks the identity binding `hmac_verified(payload) → shop_header == originating_shop`. An attacker-controlled shop can produce data that the app processes and stores as belonging to a victim shop (cross-tenant data confusion/injection), satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Requires only an unprivileged internet user who can install the target app on their own store (or otherwise obtain one valid webhook body+HMAC for the app) and send a crafted HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — no access token, secret, or privileged account needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed content (or otherwise cryptographically bind them, e.g., by including them in `to_signable_string`), so the signature covers the full set of trusted metadata, not just the raw body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering `orders/create`. Shopify sends a webhook to the app with body `B` and header `X-Shopify-Hmac-Sha256: H` computed over `B` using the app's shared `client_secret`.
2. Attacker captures `(B, H)`.
3. Attacker sends `POST /callback/orders/create` to the app with body `B`, `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` → `HmacValidator.validate` recomputes HMAC over `B` only [8](#0-7) , matches `H`, passes.
5. Handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-supplied `body`, and processes it as authentic data for the victim shop [9](#0-8) .
