### Title
Webhook HMAC Does Not Bind the `shop` (or `topic`) Identity, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `Utils::HmacValidator.validate` never covers the `shop` (or `topic`) that `ShopifyAPI::Webhooks::Registry.process` trusts and hands to the app's handler. This breaks the identity binding `HMAC-verified data == data acted upon`: the signature proves the body came from an entity holding the app's `client_secret`, but the `shop` used to route/attribute the webhook is unauthenticated header data.

### Finding Description
`Registry.process` verifies the webhook solely via `Utils::HmacValidator.validate(request)`, then dispatches to the handler using `request.shop` (from `WebhookMetadata`): [1](#0-0) 

The HMAC is computed over `to_signable_string`, which is defined as just the raw body — `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated headers and are not part of the signed material: [2](#0-1) 

This is a self-inflicted design gap in this gem, not an inherent limitation: the sibling `AuthQuery` (used for the OAuth callback HMAC) explicitly folds `shop` into `to_signable_string` so the shop is bound to the signature: [3](#0-2) 

No equivalent binding exists for `Webhooks::Request`. Since Shopify webhook signing uses one `client_secret` shared across every shop that has the app installed (the same key validated in `Utils::HmacValidator.validate`), a valid `(body, hmac)` pair obtained from a genuine webhook delivered to *any* installed shop remains valid when replayed with the `shop` header swapped to a different (victim) shop domain — the signature check in `hmac_validator.rb` cannot detect the substitution because `shop` was never part of the signed string: [4](#0-3) 

The gem's own documentation confirms host apps are expected to trust `data.shop` as verified webhook data after calling `process`, so this is not a case of the host app ignoring documented API — the gem itself asserts `shop` is authenticated: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any merchant who has installed the app (an unprivileged, non-elevated party relative to other tenants) legitimately receives real Shopify-signed webhooks for their own store. They can capture one `(raw_body, X-Shopify-Hmac-Sha256)` pair and replay it to the app's webhook endpoint with `X-Shopify-Shop-Domain` set to a victim shop's domain. `Registry.process` will validate the HMAC successfully (it only checks the body) and invoke the app's handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain, causing the host application to write/attribute data under the wrong tenant. This is a cross-tenant integrity/confidentiality break rooted entirely in this gem's signature construction.

### Likelihood Explanation
Exploitation only requires installing the app on one shop (a normal, low-privilege action) and capturing a single legitimate webhook delivery, then replaying it with a modified header — no access to `api_secret_key`, tokens, or Shopify infrastructure is needed.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the material verified against the HMAC, e.g., by having `Webhooks::Request#to_signable_string` combine the raw body with the shop/topic headers used downstream, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`. At minimum, `Registry.process` should cross-check that the shop asserted in headers matches an independently established identity before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a genuine webhook, e.g., `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC_SHA256(client_secret, B)`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC_SHA256(client_secret, B)` from `to_signable_string` (body only) and matches `H` — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, and the host app processes attacker-controlled body data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
