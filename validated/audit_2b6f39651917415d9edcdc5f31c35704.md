### Title
Webhook `shop` identity is taken from an unauthenticated header, not from the HMAC-signed bytes, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [1](#0-0) , while the `shop` identity used downstream by the registry's dispatch logic is read straight from the `X-Shopify-Shop-Domain` HTTP header, which is not covered by the signature at all [2](#0-1) . `Registry#process` validates only that the body's HMAC is correct, then trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`, all header-derived) when constructing `WebhookMetadata` passed to the app's handler [3](#0-2) . This breaks the identity binding: `hmac(body) == valid` should imply `shop == the tenant that produced this body`, but here `shop` is parsed from bytes that were never part of what was verified.

### Finding Description
The Shopify webhook HMAC signature (`X-Shopify-Hmac-Sha256`) is computed by Shopify over the raw JSON body only, using the app's single, shared `client_secret`/API secret key — the same secret is used for every shop that has the app installed. `HmacValidator.validate` correctly checks `hmac(raw_body, secret)` against the header value [4](#0-3)  and `Request#to_signable_string` returns exactly `@raw_body` [1](#0-0) .

However, `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers via `shopify_header` [5](#0-4)  — none of these header values are part of the signed payload. Because the same API secret is shared across all shops that install the app, any unprivileged internet user who runs their own Shopify store, installs the target app, and receives a legitimately-signed webhook for their own shop possesses a `(raw_body, valid hmac)` pair that is valid under the app's secret. That attacker can then POST that same body+HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to point at a victim shop. `Registry#process` will accept it — the HMAC check passes because the body is unmodified — and will invoke the app's handler with `shop: request.shop` set to the victim's domain [6](#0-5) .

This is the same rounding/identity-binding class as the report's stETH issue in structure: the report shows a "quantity acted upon" not being the same as the "quantity actually verified" (transferred shares vs. requested amount). Here, the "shop acted upon" (header) is not the same as the "content actually verified" (HMAC over body only) — an unprivileged party can supply verified bytes for one identity while claiming a different identity.

### Impact Explanation
This is a cross-tenant identity confusion: any user with legitimate but unprivileged access to the app (an ordinary merchant install) can forge/replay webhook deliveries attributed to a different shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up per-shop sessions/access tokens and perform actions, or to update per-shop state), this can lead to cross-tenant data corruption or actions performed against a shop the attacker does not own, satisfying the "cross-tenant access" impact bucket.

### Likelihood Explanation
Requires only: (1) the attacker be an app user with their own myshopify store, capable of installing the app and receiving one legitimate webhook (a trivial, low-privilege operation), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with attacker-chosen headers — both are available to any unprivileged internet user/app installer. No secrets, tokens, or privileged access are required beyond installing the app on one's own store.

### Recommendation
Bind the trusted shop identity to something actually covered by the cryptographic check, not to a raw header:
- Prefer deriving `shop` from the signed body content (most webhook payload topics include shop-scoped identifiers, or the registry can require the caller to supply the expected shop out-of-band, e.g., from the URL path tied to a session) rather than trusting `X-Shopify-Shop-Domain` unconditionally.
- At minimum, document/enforce that `Registry#process` callers must independently correlate `request.shop` with an already-authenticated session/webhook subscription record (e.g., verify the `webhook_id` returned belongs to a subscription registered for that specific shop) before trusting it, rather than treating a body-only HMAC pass as proof of the header's shop value.

### Proof of Concept
1. Attacker creates a free/dev Shopify store `attacker.myshopify.com` and installs the victim app, receiving a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `HMAC(secret, B) == H`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same `B`/`H` to the app's public webhook endpoint, replacing the header `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts the request (all required headers present) [7](#0-6) , `HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` using the shared secret [4](#0-3) .
4. `Registry#process` proceeds to call the app's handler with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, despite `B` never having been authenticated as originating from `victim.myshopify.com` [6](#0-5) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
