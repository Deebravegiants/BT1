### Title
`Auth::Oauth.begin_auth` builds `auth_route` from unvalidated `shop` parameter, enabling forced OAuth redirect to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`begin_auth` never calls `ShopValidator.sanitize!` (or any equivalent check) on the `shop` argument before using it to construct `auth_base_uri(shop)`, which becomes the host of the returned `auth_route`. If the calling app passes through an unvalidated `shop` query parameter (as the gem's own documentation example does — `shop = request.headers["Shop"]` then directly into `begin_auth`), an attacker can force the victim's browser to be redirected to `https://<attacker-controlled-string>/admin/oauth/authorize?...`.

### Finding Description
The claimed binding is: `URI(auth_route).host == ShopValidator.sanitize!(shop)` (i.e., the host that receives the OAuth authorize request must be a value that has passed through Shopify-domain validation). Tracing `begin_auth` in [1](#0-0) , the `shop` parameter is passed straight to the private `auth_base_uri` method without any call to `Utils::ShopValidator.sanitize!` or `sanitize_shop_domain`: [2](#0-1)  constructs `"https://#{shop}/admin"` directly from the raw string. `auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"` at [3](#0-2)  then becomes the URL the app is expected to redirect the browser to.

The `redirect_uri` embedded in the query string is indeed built from the trusted `Context.host`, so that specific value is safe — but the *outer* host of `auth_route` (where the browser is actually sent) is fully attacker-controlled if the host app forwards an unsanitized `shop` value. `ShopValidator.sanitize!`/`sanitize_shop_domain` exist in the codebase specifically to prevent exactly this class of bug [4](#0-3) , but `begin_auth` does not invoke them anywhere.

The gem's own documented usage pattern in `docs/usage/oauth.md` shows `shop = request.headers["Shop"]` passed directly into `begin_auth(shop: domain, ...)` with no sanitization step shown, reinforcing that this is the expected call pattern and that the gem itself is the point where validation should occur — but doesn't.

Neither `HmacValidator.validate`, the `state` cookie comparison, `JwtPayload`'s `aud` check, nor `Context.setup?`/`private?`/`embedded?` guards in `begin_auth` [5](#0-4)  have any bearing on the `shop` value used to build `auth_base_uri`; none of them validate that `shop` resolves to a trusted Shopify domain.

Exploit flow: attacker sends the victim a link to the app's login route with `shop=attacker.example` (or any arbitrary string). The host app (following the documented pattern) calls `begin_auth(shop: "attacker.example", redirect_path: "/cb")`. `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=...&redirect_uri=https://<trusted-host>/cb&state=...&..."`. The app 307-redirects the browser there. The browser now lands on the attacker's server with the real `client_id` and `state` in the query string, and the attacker's server can render a fake Shopify consent page (or itself redirect to the real Shopify authorize endpoint with the captured params, or to a shop the attacker controls) to complete forced OAuth against a shop of the attacker's choosing, potentially binding the app's OAuth session cookie/state to an attacker-orchestrated flow.

### Impact Explanation
This is a High-severity SSRF/forced-OAuth-completion class issue matching the rules' "SSRF driving an authenticated request to an unintended host... or forced OAuth completion" category: the client_id (not itself secret, but sensitive) and the `state` nonce leak to an attacker-chosen host, and the OAuth flow can be steered so that the resulting install/callback is completed against a shop the attacker controls, rather than the shop the app operator intended. It is repeatable against any victim who can be induced to hit the login route with an attacker-supplied `shop` value, and does not depend on any specific victim shop — the blast radius is any merchant/user of an app built on this gem that forwards `shop` from user input into `begin_auth` without separately calling `ShopValidator.sanitize!` first.

### Likelihood Explanation
Preconditions: the host application must pass an attacker-influenced `shop` string into `begin_auth` without independently sanitizing it first. This is not hypothetical — it is exactly the pattern shown in the gem's own docs example (`shop = request.headers["Shop"]` → `begin_auth(shop: domain, ...)`), and the gem exposes no other automatic enforcement point (no sig-level runtime validation beyond `String` type, no internal call to `ShopValidator`). `Context.host` being configured is a normal precondition of any app using this gem and doesn't mitigate this bug since it only affects the inner `redirect_uri`, not the outer host. Attacker cost is a single crafted link with a `shop=` value; no credentials or preconditions beyond normal internet access are required, making this highly feasible and repeatable.

### Recommendation
In `Auth::Oauth.begin_auth`, before building `auth_base_uri(shop)`, call `shop = Utils::ShopValidator.sanitize!(shop)` (mirroring what `TokenExchange`/`ClientCredentials`/`RefreshToken` already do per the earlier grep showing `sanitize!`/`sanitize_shop_domain` usage in `token_exchange.rb` and `client_credentials.rb`), so that any `shop` value that doesn't resolve to a `TRUSTED_SHOPIFY_DOMAINS` domain raises `Errors::InvalidShopError` instead of being used to construct the redirect target.

### Proof of Concept
```ruby
# test/auth/oauth_test.rb (new test)
def test_begin_auth_rejects_untrusted_shop_host
  ShopifyAPI::Context.setup(
    api_key: "test_key",
    api_secret_key: "test_secret",
    host_name: "trusted.example.com",
    api_version: "unstable",
    is_private: false,
    is_embedded: false,
  )

  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example", redirect_path: "/cb")
  end
end
```
Currently this raises nothing: `begin_auth(shop: "attacker.example", redirect_path: "/cb")[:auth_route]` returns `"https://attacker.example/admin/oauth/authorize?client_id=test_key&scope=&redirect_uri=https%3A%2F%2Ftrusted.example.com%2Fcb&state=...&grant_options%5B%5D=per-user"` — i.e. `URI(result[:auth_route]).host == "attacker.example"`, violating the intended binding that the host must equal `ShopValidator.sanitize!(shop)` (which would raise `InvalidShopError` for this input). No live shop or network access needed; the bug is demonstrated purely by inspecting the returned string.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
