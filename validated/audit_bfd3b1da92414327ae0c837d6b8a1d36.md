### Title
Webhook HMAC verification does not bind the `shop` domain or `topic`, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw HTTP body only. The `shop`, `topic`, `webhook_id`, and `api_version` values — which `ShopifyAPI::Webhooks::Registry.process` uses to route the payload and identify the tenant — are read straight from HTTP headers that are **not** covered by the HMAC signature. Anyone who can obtain one validly-signed `(body, hmac)` pair (e.g. by installing the app on their own store and receiving a genuine webhook) can replay that exact pair to the app's webhook endpoint with a forged `shop-domain`/`topic` header, and the signature check will still pass.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are outside that signed string: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then dispatches to a handler using the unverified `shop`, `topic`, and `webhook_id` header values: [4](#0-3) 

The equality the library implicitly claims to enforce is: `hmac == HMAC(secret, body ‖ shop ‖ topic)` i.e. that the tenant identity (`shop`) and event type (`topic`) delivered to the handler are the ones Shopify actually signed. In reality the enforced equality is only `hmac == HMAC(secret, body)`; `shop` and `topic` are trusted but never bound to the signature. This is confirmed by the library's own test fixture, which computes the HMAC purely over `"{}"` while freely setting `shopify-shop-domain`/`shopify-topic` headers to arbitrary values: [5](#0-4) 

### Impact Explanation
An app can receive webhooks for many merchant shops. Because `shop` (the tenant identifier passed to `WebhookMetadata`) is not part of the signed content, a party who possesses any one legitimately-signed `(body, hmac)` pair — for instance from a webhook Shopify sent them for their own store — can resubmit that same pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop, or the `shopify-topic` header for a different mandatory topic (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`). The app's handler will process the forged event as if it were authoritative data for the victim tenant, since nothing in the gem detects the substitution. Depending on what the host application's `WebhookHandler` does with `data.shop`/`data.topic` (deleting data, revoking sessions, marking the app uninstalled, etc.), this crosses a tenant boundary — the report's listed "shop authenticated versus shop stored/acted upon" identity-binding class — without requiring the attacker to know `api_secret_key` or possess any merchant's access token.

### Likelihood Explanation
Exploitation requires only capturing one legitimate webhook delivery (any topic, any shop that has the app installed — trivially obtainable by installing the app on the attacker's own development/test store) and replaying it with modified headers to the publicly reachable webhook callback endpoint. No credentials, TLS interception, or privileged access are required, and the vulnerable code path (`Registry.process` / `Request`) is the exact code path documented for all HTTP webhook consumers of this gem.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the request, e.g. via a per-topic/per-shop signed manifest fetched from Shopify), rather than trusting header values that sit outside `to_signable_string`. At minimum, document and enforce that `shop`/`topic` must be cross-checked against an out-of-band source of truth (such as the shop's active session) before handlers act on them.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for topic `orders/create`. When an order is created, Shopify sends a webhook with body `B` and a valid `X-Shopify-Hmac-Sha256` computed over `B` using the app's real secret — the attacker captures `(B, HMAC)`.
2. Attacker sends a forged HTTP request directly to the app's webhook callback endpoint with:
   - Body: the captured `B` (unchanged)
   - `X-Shopify-Hmac-Sha256`: the captured `HMAC` (unchanged)
   - `X-Shopify-Shop-Domain`: `victim.myshopify.com`
   - `X-Shopify-Topic`: `shop/redact` (or any topic registered by the app)
3. `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC: [6](#0-5) 
4. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` and `topic: "shop/redact"`, even though Shopify never sent this event for that shop/topic combination: [4](#0-3)
