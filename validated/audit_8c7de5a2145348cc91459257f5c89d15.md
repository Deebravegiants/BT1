### Title
Unbounded-length `from` bytes cause an out-of-bounds panic during cross-chain token/calldata delivery - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`HyperFungibleToken::Message.from` is an attacker-controlled, arbitrary-length ABI `bytes` field carried in a relayed ISMP `PostRequest`. In `on_accept`, when the request's optional calldata carries no signature, the fallback origin-resolution branch reads a fixed number of bytes out of `from_bytes` without first validating its length, unlike every sibling code path in the same file that does check length before slicing.

### Finding Description
`Pallet::on_accept` decodes the incoming request body into a `Message` (`from`, `to`, `amount`, `data`), an ABI struct whose `from`/`to` fields are unconstrained `bytes` set by the source-chain sender [1](#0-0) . Every other place `from`/`to` bytes are consumed in this file validates the length is exactly 20 or 32 bytes before use — see `to_bytes` handling [2](#0-1)  and the `on_timeout` handling of `from_bytes` [3](#0-2) .

However, when `message.data` carries a `SubstrateCalldata` with `signature == None`, the unsigned-origin fallback skips that validation entirely: [4](#0-3) 

- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing either a panic (debug) or a huge wrapped index that panics on the subsequent out-of-bounds slice (release) — `from_bytes[from_bytes.len() - 20..]`.
- If `source` is not EVM and `from_bytes.len() != 32`, `account.copy_from_slice(from_bytes)` panics on the length mismatch (`copy_from_slice` requires equal lengths).

This mirrors the CVE-2023-37281 bug class exactly: a length-controlled field is trusted and read/copied at a fixed size without a bounds check that is already performed everywhere else nearby for the same kind of field.

### Impact Explanation
This code executes inside `on_accept`, the `IsmpModule` handler invoked by `pallet-ismp`'s message-dispatch path when *any* relayer delivers a `PostRequest` destined to a contract registered against this pallet via `ContractToAsset` [5](#0-4) . Any unprivileged relayer/token bridger can construct a cross-chain message with the required contract mapping, embed `SubstrateCalldata { signature: None, runtime_call }` in `message.data`, and set `message.from` to a byte string of the "wrong" length (e.g. empty, or any length other than 20/32 for the corresponding source chain type) to trigger a Rust panic during on-chain message dispatch. A panic (as opposed to a returned `Err`) inside runtime execution is not a graceful failure; it produces a WASM trap during extrinsic execution, which can abort block execution for that transaction and constitutes a "route unable to deliver messages" condition for that specific incoming request path — the request can never be successfully processed once dispatched this way, and worse, it can DoS the executing node/block author attempting to include it.

### Likelihood Explanation
High. The precondition is only that a relayer has (or fabricates) a valid ISMP `PostRequest` addressed to a mapped `HyperFungibleToken` contract on the source chain, with an attacker-chosen `from` field length and attacker-chosen `SubstrateCalldata` with no signature — all of which are entirely within the sender/relayer's control when constructing the cross-chain message payload. No special privileges, governance, or races are required.

### Recommendation
Add the same length validation used for `to_bytes` (in `on_accept`) and `from_bytes` (in `on_timeout`) to the unsigned-origin fallback branch before slicing/copying: require `from_bytes.len() == 20` when `source.is_evm()` and `from_bytes.len() == 32` otherwise, returning a `HftError` (e.g. `InvalidSenderLength`) on mismatch instead of panicking.

### Proof of Concept
1. Register a `ContractToAsset` mapping for `(source, from)` so `on_accept` proceeds.
2. Craft an ABI-encoded `Message` where `data` decodes to `SubstrateCalldata { signature: None, runtime_call: <any valid encoded call> }`.
3. Set `Message.from` to a byte string whose length is, e.g., 0 bytes (for an EVM `source`) — any length other than 20.
4. Relay this as a `PostRequest` through `pallet-ismp`'s message handling so `Pallet::on_accept` is invoked.
5. Execution reaches `from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() == 0`, causing an integer-underflow/out-of-bounds panic instead of a handled error.
