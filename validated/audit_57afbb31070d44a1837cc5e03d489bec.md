### Title
Native ETH refunded by the LI.FI router mid-swap is stranded in `LifiExternalAction` and never returned to the depositor - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction.callRouter` forwards the *entire* `inputAmount` as `msg.value` to the immutable LI.FI `router` and only checks `success`, then computes `swappedAmount` solely from the **output token's** balance delta. When `inputToken == address(0)` and `outputToken != address(0)`, any native ETH the router legitimately refunds back to `msg.sender` (i.e. to `LifiExternalAction` itself) for unconsumed input value is never measured, never converted into a UTXO, and never returned to the depositor — it is permanently orphaned inside the `LifiExternalAction` contract.

### Finding Description
The equality that should hold is: *all native ETH debited from the depositor's shielded balance and forwarded to the external action must end up either consumed by the swap or returned to the depositor as value.* In `ExternalActionSwap.swap()` (contracts/external-actions/swaps/ExternalActionSwap.sol:44-102), `inputAmount` is computed once from `deltaAmounts[0]` and handed to `callRouter`. In `LifiExternalAction.callRouter` (contracts/external-actions/swaps/LifiExternalAction.sol:16-36): [1](#0-0) 
`balanceBefore`/`balanceAfter` are only taken for `outputToken`. The native `router.call{value: inputAmount}(...)` result is checked only for `success`; if the router (a real, external LI.FI diamond contract whose calldata the depositor fully controls when constructing `externalActionMetadata`) refunds unused native value back to `msg.sender` — a documented and common pattern for aggregator routers when the encoded swap consumes less than the forwarded value — that ETH lands in `LifiExternalAction`'s own balance and is invisible to the rest of the flow.

Back in `swap()`, only `outputToken`'s balance delta (`swappedAmount`) is turned into the outgoing UTXO (contracts/external-actions/swaps/ExternalActionSwap.sol:93-101). There is no code path that inspects `address(this).balance` for native leftovers when `outputToken != address(0)`, so the refunded ETH is not forwarded to `msg.sender` (Hinkal), not paid to the relay, and not wrapped into any UTXO.

Critically, `Hinkal.sol`'s own conservation check (`balanceDif == amountChanges[i] + utxoAmount`, contracts/Hinkal.sol:134-146) does **not** catch this, because Hinkal already transferred the full `inputAmount` out of its own balance to `LifiExternalAction` *before* `runAction`/`swap` executes (contracts/Hinkal.sol:247-256). From Hinkal's perspective the native-token balance decreased by exactly `inputAmount`, which matches `amountChanges[0]` (negative) plus zero native `utxoAmount` — the equation is satisfied regardless of what `LifiExternalAction` does internally with that ETH afterward. Hinkal's guard only protects Hinkal's own ledger; it explicitly does not, and cannot, verify how the delegated external action spends the funds once they leave the pool.

### Impact Explanation
The depositor's shielded balance is debited for the full `inputAmount`, but only `amountToSendToHinkal` (derived from the output-token delta) is returned as a new UTXO. Any native ETH refunded to `LifiExternalAction` by the router is permanently locked in that contract with no owner-only or public sweep/rescue function exposed (`ExternalActionBaseV2`/`OwnerHinkal` only expose `setAllowedRecipients`, `setHinkalHelper`, `renounceOwnership`-revert). This is a permanent freezing of user funds — Critical impact, matching the listed category exactly ("permanent freezing of user funds").

### Likelihood Explanation
The only precondition is that the depositor (unprivileged, since they craft their own `externalActionMetadata` and proof) route the call through a legitimate LI.FI router function/path that refunds unconsumed native value — a real, externally-controlled but well-documented behavior of aggregator routers, not a malicious/compromised dependency. Every such swap (native-in, ERC20-out) is affected identically; the loss is proportional to the router's refund amount and is fully reproducible each time this code path is exercised.

### Recommendation
In `LifiExternalAction.callRouter`, capture the native balance delta of `LifiExternalAction` itself (not just the output token) around the `router.call{value: inputAmount}` branch, and in `ExternalActionSwap.swap()` forward any leftover native ETH back to `msg.sender` (Hinkal) or fold it into an additional UTXO for the depositor's stealth address, mirroring the pattern already used in `EmporiumUpgradeable.handleOut`/`balancesBefore`/`balancesAfter` accounting.

### Proof of Concept
Foundry fork test outline:
1. Deploy `LifiExternalAction` pointed at a mock router that, given calldata for `inputAmount`, only consumes half and does `payable(msg.sender).call{value: inputAmount/2}("")` to refund the rest.
2. Perform a `Hinkal.transact` with `erc20TokenAddresses = [address(0), ERC20_OUT]`, native input, ERC20 output, valid proof/UTXOs for `inputAmount`.
3. Assert: `address(LifiExternalAction).balance` increases by `inputAmount/2` after the tx.
4. Assert: the emitted UTXO set only contains the ERC20 output UTXO — no native UTXO/refund exists for the depositor.
5. Assert Hinkal's own conservation check (`balanceDif == amountChanges[i] + utxoAmount`) still passes for both token indices, proving Hinkal-level accounting cannot detect the loss.
