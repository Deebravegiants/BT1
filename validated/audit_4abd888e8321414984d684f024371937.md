### Title
POA Bridge withdrawal status matched only by `assetId`, causing status/hash misreport for multiple same-asset withdrawals in one transaction — (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal identified by `{tx.hash, index}`, but the matching logic against the POA bridge indexer response ignores `index` entirely and matches purely by `assetId`. When a single NEAR transaction contains more than one withdrawal of the same token (e.g. two POA withdrawals of `nep141:btc.omft.near` batched together), every one of those withdrawals resolves to the *same* indexer record — whichever the underlying array happens to return first.

The function's own comment documents the limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." The duplicate implementation in `waitForWithdrawalCompletion.ts` carries the identical caveat: [3](#0-2) .

Crucially, the caller does *not* treat "unsupported" as a hard failure — `createWithdrawalIdentifiers` happily assigns sequential per-bridge indices to withdrawals of the same asset routed to the same bridge: [4](#0-3) . Each resulting `WithdrawalIdentifier` (index 0, index 1, …) is then independently polled via `watchWithdrawal`/`createWithdrawalCompletionPromises`: [5](#0-4)  and [6](#0-5) .

Because `findMatchingWithdrawal` ignores `index` and returns the first array element whose `near_token_id` matches the assetId, both the index-0 and index-1 polling calls for the same NEAR tx converge on the identical indexer record. If the first withdrawal in the pair actually completes, the *second, still-pending or even failed* withdrawal will also be reported `{ status: "completed", txHash: <same-hash-as-withdrawal-0> }` — an outcome that does not correspond to that specific withdrawal's real on-chain state.

### Impact Explanation
This breaks the equality "status/hash reported == actual on-chain outcome of *this* withdrawal." An integrator building on `IntentsSDK` who watches multiple same-asset withdrawal legs from one NEAR transaction (a supported and expected usage pattern, since `withdrawalParams` is an array and indices are assigned automatically) will see both legs resolve to `completed` with the same destination tx hash, even though only one on-chain transfer occurred. That is a textbook double-credit/refund vector matching the rubric's High-impact category ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
No malicious actor is required — an ordinary user or integrator submitting two withdrawals of the same POA-bridged asset in a single NEAR transaction (e.g., batching withdrawals to two different destination addresses) triggers this deterministically. It requires no privileged action, no external RPC compromise, and no reliance on price feeds or relayer misbehavior — it's a pure logic defect in first-party matching code.

### Recommendation
Extend the POA bridge indexer response (or the SDK-side matching) to disambiguate withdrawals sharing the same `assetId` within one transaction — e.g., match by `(assetId, destinationAddress, amount)` tuple, or by stable ordering/index once POA API support lands, as the code comments already anticipate. Until fixed, `describeWithdrawal` should refuse to report `completed` for index > 0 when multiple pending withdrawals share an assetId and cannot be disambiguated, rather than silently reusing another withdrawal's status/hash.

### Proof of Concept
1. User submits one NEAR intents transaction containing two POA withdrawal intents for the same asset, `nep141:btc.omft.near`, to two different destination addresses (index 0 and index 1 under `RouteEnum.PoaBridge`).
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals for the `PoaBridge` route (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`).
3. The SDK begins polling both via `watchWithdrawal` in parallel.
4. The POA bridge processes and completes withdrawal 0 on-chain (`transfer_tx_hash: "dest-tx-hash-0"`); withdrawal 1 is still pending/unprocessed.
5. `PoaBridge.getWithdrawalStatusWithRetry` returns the indexer's withdrawal list containing only the completed record for `near_token_id: "btc.omft.near"`.
6. Both `describeWithdrawal({index:0, assetId: "nep141:btc.omft.near", ...})` and `describeWithdrawal({index:1, assetId: "nep141:btc.omft.near", ...})` call `findMatchingWithdrawal`, which matches solely on `assetId` and returns the same record for both calls (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:409-427`).
7. Both promises resolve `{ status: "completed", txHash: "dest-tx-hash-0" }`, even though withdrawal 1 has not actually landed on-chain — an integrator relying on this signal to credit/settle the second withdrawal will do so erroneously.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
