### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop` value that webhook handlers rely on to identify which merchant the event belongs to is read from an unsigned HTTP header. Because the HMAC does not bind the `shop` field, a valid `(body, hmac)` pair captured from one tenant's webhook delivery can be replayed against the app's webhook endpoint with a different `x-shopify-shop-domain` header, and the gem will accept it as authentic and hand it to the app's handler as if it belonged to the spoofed shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop` is parsed directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the shared secret: [3](#0-2)  so the header-derived `shop` never enters the signature computation.

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, dispatching it to the app-provided handler: [4](#0-3) 

This is a genuine gap, not a documentation nuance: the sibling OAuth flow (`ShopifyAPI::Auth::Oauth::AuthQuery`) explicitly includes `shop` inside its signable string so the shop identity *is* bound by the HMAC there: [5](#0-4)  The webhook path breaks the analogous binding: `shop used by the handler == shop covered by the HMAC` does not hold, since the HMAC only covers the body.

### Impact Explanation
An attacker who is themselves a legitimate (unprivileged) merchant of the target app can capture a valid `(raw_body, x-shopify-hmac-sha256)` pair delivered by Shopify to their own installation (e.g. via a logging proxy in front of their self-hosted webhook receiver, or any tooling that surfaces the raw delivery). Because the signature is independent of the `shop` header, the attacker can replay that exact body+HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still succeeds, and the app's registered handler receives `WebhookMetadata` claiming the event originated from the victim shop, potentially causing cross-tenant data corruption, spurious session/state changes (e.g. simulating `app/uninstalled` or order/customer events) for a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to make outbound HTTP requests to the app's public webhook callback URL plus knowledge of one valid `(body, hmac)` pair, which any merchant using the app can obtain for their own tenant without needing `api_secret_key` or any elevated privilege. No TLS interception or social engineering is required.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed payload before trusting it — for example by verifying that the shop encoded in the webhook body (where Shopify includes it, e.g. via GraphQL webhook payload metadata) matches the header, or by requiring apps to cross-check `request.shop` against a shop known to have an active session/registration before processing, consistent with how `AuthQuery` includes `shop` in its `to_signable_string`.

### Proof of Concept
1. Register a webhook handler with the gem for topic `T` on your own app installation for `shopA.myshopify.com`.
2. Capture a real inbound webhook delivery for `shopA` (raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`).
3. Send a new HTTP request to the app's webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: shopB.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which only checks `B` against `H` — this passes. [4](#0-3) 
5. The app's handler receives `WebhookMetadata` with `shop: "shopB.myshopify.com"` even though the payload was never issued by Shopify for `shopB`, demonstrating the cross-tenant spoof.
