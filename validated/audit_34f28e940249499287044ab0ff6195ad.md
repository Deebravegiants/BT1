### Title
Webhook shop-domain header is not covered by the gem's HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers that are never included in the bytes signed by Shopify's HMAC, yet `ShopifyAPI::Webhooks::Registry.process` treats `request.shop` as an authenticated tenant identifier and forwards it unmodified to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) . `HmacValidator.validate` computes the HMAC exclusively over that signable string with the app's `client_secret`: [2](#0-1) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body or the HMAC: [3](#0-2) .

`Registry.process` validates only the HMAC and then constructs `WebhookMetadata` using `request.shop` as the trusted tenant identifier passed to the app's handler: [4](#0-3) .

Because Shopify signs webhooks for every shop that installs a given app with the **same** `client_secret` (this is the same secret used everywhere in the gem, e.g. `Context.api_secret_key` in `HmacValidator`), a valid HMAC only proves "this body was signed by Shopify for *some* shop using this app's secret" — it does not prove which shop. An unprivileged attacker who controls one shop that has the app installed (a legitimate, unprivileged action — installing a public/free app requires no special privilege) can capture one genuinely-signed webhook delivery from their own shop, then replay that exact `raw_body`/`hmac-sha256` pair directly at the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (the signed bytes are unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop as the source: [5](#0-4) .

The broken binding, stated as an equality that the gem fails to enforce:
`shop asserted in WebhookMetadata.shop` (from an unauthenticated header) **≠** `shop cryptographically bound by the HMAC` (which binds nothing about shop, since `to_signable_string` = raw body only).

### Impact Explanation
This is a cross-tenant attack: the app's handler (documented to trust `data.shop` as "The shop domain of the webhook", per `docs/usage/webhooks.md`) will process attacker-controlled payload content while believing it originates from an arbitrary victim shop of the attacker's choosing. Depending on what the topic's payload triggers (e.g., order/customer/inventory sync, credential rotation notices, uninstall/`app/uninstalled` handling), this can lead to data being written into, or actions performed against, a different merchant's tenant record than the one that actually sent the request — a cross-tenant boundary violation entirely within code this gem controls (header parsing + HMAC scope), not merely "the host ignored documented behavior," since the documented and only verification primitive the gem offers (`HmacValidator.validate`) structurally cannot detect this.

### Likelihood Explanation
Any entity capable of installing the app on one Shopify store (a normal, unprivileged action available to any internet user for public apps) can capture one legitimately-signed webhook body from their own store and replay it against the shared webhook endpoint with a forged shop header — no access token, `client_secret`, or victim credentials are required.

### Recommendation
Bind the shop domain to the signature validation, or cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription server-side before trusting it, and document that the header-derived `shop`/`topic` values are unauthenticated inputs that must not be used as a sole tenant-selection key. At minimum, extend `VerifiableQuery`/`to_signable_string` for webhook requests to incorporate `shop`, or require callers to correlate `request.shop` against a known/expected shop for the delivery before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate, unprivileged action).
2. Shopify sends a legitimately HMAC-signed webhook (e.g., `orders/create`) to the app's registered endpoint for `attacker-shop.myshopify.com`; attacker captures the raw body and the `x-shopify-hmac-sha256` value.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` are unaffected by the header change (they don't include shop), so `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` returns `true`.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the app to process attacker-controlled data attributed to the victim tenant.
