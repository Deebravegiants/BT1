Confirmed: the webhook HMAC binding covers only the raw body, while the `shop` field used for routing/tenant identification comes from an unsigned header.### Title
Webhook shop-domain identity spoofing via HMAC that covers only the request body, not the routing headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is not part of the signed material — as the tenant identity used to route the payload to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, to_signable_string)` and constant-time-compares it against the `hmac` extracted from the `hmac-sha256` header [2](#0-1) . Critically, `shop`, `topic`, `webhook_id`, and `api_version` are all read from separate, un-signed HTTP headers [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `request.shop` straight into the handler's `WebhookMetadata`, with no additional binding between the authenticated body and the claimed shop: [4](#0-3) .

This breaks the identity equality that the HMAC is meant to enforce: the gem's authentication check answers `HMAC(secret, body) == signature`, but the value that actually determines *whose* data the app processes — `shop-domain` — is never covered by that equality. Any bytes with a valid `(body, hmac)` pair captured from one delivery (e.g., a webhook from an attacker's own trial/dev store, which they can freely generate since they control that store and know its content) can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop domain, and the signature check will still pass because it never inspected that header.

### Impact Explanation
This is a cross-tenant identity/authentication issue: an unprivileged internet user who can capture (or generate, via their own store) one valid `(body, hmac)` pair can cause the app to process attacker-controlled webhook data under a victim shop's identity. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., to look up sessions, update shop-scoped records, or trigger GDPR-type actions like `customers/redact` on behalf of a shop that never actually sent the event), this can lead to cross-tenant data corruption or unauthorized actions attributed to the wrong merchant — the class of harm cited in the prompt's Critical/High bar ("cross-tenant access").

### Likelihood Explanation
Exploitability requires only network access to the app's public webhook endpoint and one legitimately-signed body (trivially obtainable by installing/subscribing a webhook on the attacker's own store, which is unprivileged relative to the target). No secret material, TLS interception, or privileged account is needed to mount the header-substitution replay. This satisfies the "unprivileged internet user" threat model in the rules.

### Recommendation
Bind the tenant/topic identity into the authenticated material, or otherwise cryptographically or contractually associate the verified body with the `shop-domain` header before dispatch:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or verify them out-of-band against known session/shop records) so the HMAC check enforces `HMAC(secret, body || shop || topic) == signature`.
- At minimum, `Registry.process` should require the caller to supply/verify the expected `shop` for the delivery (e.g., cross-check against an active session or a shop the app knows it installed) instead of trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs (or otherwise interacts with) the target app on their own store `attacker-shop.myshopify.com`, and captures one legitimate webhook delivery: raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's real secret over `B`).
2. Attacker POSTs to the app's public webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: <same topic>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H`, so validation succeeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on data `B` as if it belonged to `victim-shop.myshopify.com`, despite `B` never having been generated for that shop.
