### Title
Rebasing/balance-decreasing token vaults permanently freeze the pool via `checked_sub` underflow in `calc_total_without_take_pnl_no_orderbook` - ([File: program/src/math.rs])

### Summary
`Calculator::calc_total_without_take_pnl_no_orderbook` subtracts a monotonically-accruing, internally-tracked "amount owed to protocol" field (`amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin`) from the vault's *live* SPL token balance read at call time. Unlike the Teller `CollateralEscrowV1` bug (a stale cached `_amount` vs. real balance mismatch), here the mismatch runs in the opposite, more dangerous direction: the AMM's internal liability bookkeeping keeps growing regardless of what actually happens to the token balance in the vault. If the coin or pc mint is a token whose balance can decrease independently of AMM-mediated transfers (rebase-down tokens, or any token whose `balanceOf`/vault amount can drop without an explicit AMM instruction), `need_take_pnl_pc`/`need_take_pnl_coin` can end up larger than the vault's real amount, and the `checked_sub` fails, reverting the transaction.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` computes the pool's usable balance as vault balance minus the accrued pnl liability: [1](#0-0) 

`need_take_pnl_pc`/`need_take_pnl_coin` are accrued (only incremented, never re-derived from real balances) inside `calc_take_pnl`, which runs on every Deposit, Withdraw, Swap, and WithdrawPnl call: [2](#0-1) 

They are only ever reset to zero inside `process_withdrawpnl`, which is gated to the privileged `pnl_owner`/`amm_owner` signer: [3](#0-2) 

Crucially, `calc_total_without_take_pnl_no_orderbook` is invoked from every unprivileged, user-reachable entrypoint using the vault's *current* live balance (`amm_pc_vault.amount`, `amm_coin_vault.amount`, freshly unpacked from the SPL token account each call):

- `process_deposit`: [4](#0-3) 
- `process_withdraw`: [5](#0-4) 
- `process_swap_base_in`: [6](#0-5) 
- `process_swap_base_out`: [7](#0-6) 
- `process_swap_base_in_v2`: [8](#0-7) 
- `process_swap_base_out_v2`: [9](#0-8) 

Because `need_take_pnl_pc`/`need_take_pnl_coin` never shrink except via the privileged `WithdrawPnl` call, and because they are computed purely from the AMM's internal virtual price-invariant bookkeeping (`calc_pnl_x`/`calc_pnl_y`) rather than from the actual current vault balance, any external event that reduces the real vault balance without going through the AMM's transfer paths (e.g. a rebasing-down token, or any token mechanic that can shrink a held balance out-of-band) can push `need_take_pnl_*` above the real vault amount. From that point on, the `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?` in `calc_total_without_take_pnl_no_orderbook` returns an error on **every single Deposit, Withdraw, SwapBaseIn, and SwapBaseOut call** (both v1 and v2 variants), because all of them call this function before doing anything else.

This is the direct analog of the reported bug class: an internally tracked "amount" (here, accrued protocol pnl liability) is compared/subtracted against the real, live token balance without ever being able to shrink in step with a balance decrease that the AMM did not itself cause, and the mismatch causes an unconditional revert of withdrawal-class instructions.

### Impact Explanation
Once `need_take_pnl_pc` or `need_take_pnl_coin` exceeds the corresponding vault's real balance, **all** unprivileged pool operations — Deposit, Withdraw, SwapBaseIn, SwapBaseOut (and their v2 counterparts) — revert with `AmmError::CheckedSubOverflow`. This permanently freezes all LP funds in the pool (LPs can no longer withdraw their share) and halts all trading, with no user-accessible recovery path, since the only function that reduces `need_take_pnl_*` (`process_withdrawpnl`) is restricted to the protocol's privileged pnl owner and only reduces the liability variables, it does not address a vault balance shortfall caused by a rebase-down event that reduced actual holdings below the recorded liability.

### Likelihood Explanation
Reachability requires the pool to be created against a coin or pc mint whose real balance can decrease independently of AMM-mediated transfers (e.g. a rebasing token). Given that a pool creator or any unprivileged user can call `Initialize2` for any two SPL mints, and any user's subsequent swaps naturally accrue `need_take_pnl_*` over time via `calc_take_pnl`, a pool paired with such a token type will eventually and predictably hit this condition purely from normal usage plus the underlying token's rebase mechanics — no attacker privilege or malicious validator behavior is needed to trigger the freeze once such a mint is paired.

### Recommendation
Do not treat `need_take_pnl_pc`/`need_take_pnl_coin` as an unconditionally growing liability subtracted from a live-read balance. Either: (1) clamp `need_take_pnl_*` to the actual current vault balance (`min(need_take_pnl_x, vault.amount)`) when computing `total_*_without_take_pnl`, treating any shortfall as unrealized/lost, or (2) explicitly detect and reject rebasing-style tokens at `Initialize2` time, or (3) re-derive/reconcile `need_take_pnl_*` against the real vault balance on every operation instead of purely incrementing it in `calc_take_pnl`.

### Proof of Concept
1. Create a pool via `Initialize2` where the coin or pc mint is a rebasing SPL token wrapper (or any token type whose holder balance can be reduced externally without an explicit transfer instruction from the AMM).
2. Perform normal swaps; each swap invokes `calc_take_pnl`, incrementing `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` (`program/src/processor.rs:244-254`).
3. Trigger (or wait for) a rebase-down event on the token, reducing the AMM vault's actual SPL token balance without any AMM instruction being called.
4. Once `need_take_pnl_pc` (or `need_take_pnl_coin`) exceeds the vault's now-reduced real balance, call any of Deposit, Withdraw, SwapBaseIn, or SwapBaseOut. The very first line of pool-state computation, `Calculator::calc_total_without_take_pnl_no_orderbook` (`program/src/math.rs:243-248`), executes `pc_amount.checked_sub(amm.state_data.need_take_pnl_pc)` (or the coin equivalent), which returns `None` and the instruction reverts with `AmmError::CheckedSubOverflow`.
5. All subsequent Deposit/Withdraw/Swap calls on this pool fail identically, permanently freezing all LP funds and halting trading; only the privileged pnl owner via `process_withdrawpnl` can reset the liability counters, and doing so does not restore the missing balance.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
