### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body, while the `shop` (tenant) value is read from an unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC, then hands the unsigned `shop` value to the app's webhook handler as the authoritative tenant identity. This breaks the intended binding: `hmac == HMAC(body)` is not equivalent to `hmac == HMAC(body, shop)`, so `shop` can be swapped without invalidating the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed content: [2](#0-1) 

`Webhooks::Registry.process` verifies the HMAC over the request, then immediately forwards the unsigned `request.shop` to the registered handler as the tenant identity, with no check that the shop is bound to the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) — it never incorporates `shop`: [4](#0-3) 

Because `shop` is excluded from the signed bytes, any party who can obtain one valid `(raw_body, hmac)` pair signed by the app's secret (e.g., a merchant who has legitimately installed the app on their own store and thus receives real Shopify webhooks with a valid HMAC computed from the app's `client_secret`) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds (body and HMAC are unmodified and match), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, causing the host application to process or persist the payload under the wrong tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the value the application uses to select/scope tenant data (`shop`) is verified only by "is this header present," not by the HMAC that is supposed to authenticate the whole request as coming from Shopify for that shop. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., to look up/write records, revoke access, or trigger data-deletion flows for GDPR topics), an attacker can cause the application to attribute a crafted payload to an arbitrary victim shop, i.e., cross-tenant data corruption/impersonation — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
The prerequisite is modest: the attacker needs a valid `(body, hmac)` pair produced with the app's `client_secret`, which they can obtain by being a legitimate (even free/trial) merchant with the app installed, without ever learning the secret itself, and without any elevated privilege on the victim's shop. They only need to know/guess the app's public webhook endpoint and swap one header on replay — no TLS interception, no leaked credentials, no access token needed.

### Recommendation
Include the shop (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified payload (e.g., require the app to independently confirm the `shop` against a known/expected value per registered webhook subscription rather than trusting the header verbatim). At minimum, document that `request.shop` is unauthenticated and must not be trusted as a tenant boundary without additional binding.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com` and receives a legitimate webhook: body `B` with header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the identical request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — passes validation.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, so the application processes attacker-controlled data as belonging to `victim.myshopify.com`. [3](#0-2)
