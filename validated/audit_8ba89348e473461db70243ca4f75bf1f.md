## Valid Analog Found

### Title
IntentGatewayV2 (Tron) withdraw/sweep paths do not check ERC20 `transfer` return value, permanently freezing escrowed funds on tokens that return `false` on failure - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles escrowed order funds and sweeps protocol dust using a raw low-level `.call()` to the token's `transfer` selector, and only checks that the *call itself* did not revert (`success`). It never decodes/validates the actual `bool` return value that ERC20 tokens like ZRX return on failure. This is the exact bug class in the referenced Sherlock M-7 finding (AutoRoller `eject`): tokens that signal failure by returning `false` instead of reverting bypass the check entirely, while the contract's internal escrow accounting is already decremented as if the transfer succeeded.

### Finding Description
In `withdraw()`, which is invoked whenever an order's escrow is redeemed (`RequestKind.RedeemEscrow`) or refunded (`RequestKind.RefundEscrow`) — both authenticated cross-chain paths reachable by any relayer delivering a Hyperbridge message — the contract does: [1](#0-0) 

```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`_orders[body.commitment][token] -= amount` is decremented unconditionally right after the transfer attempt, regardless of whether the token's `transfer` call actually moved funds. If the ERC20 `transfer` implementation returns `false` on failure (e.g. blacklist, paused, insufficient-balance edge case) rather than reverting, `success` is still `true` because the low-level call itself did not revert — only the encoded return data indicates failure, and that return data is discarded. The identical unchecked pattern also settles transaction fees: [2](#0-1) 

and is used again for protocol-dust sweeping in `onAccept`'s `SweepDust` handling: [3](#0-2) 

Notably, the main EVM (non-Tron) version of the same contract and `IntentsBase.sol` were already hardened with `SafeERC20.safeTransfer`/`safeTransferFrom` for the equivalent code paths: [4](#0-3) 

confirming that the Tron deployment of `IntentGatewayV2` was not updated to use the safe-transfer pattern and remains vulnerable to this exact bug class.

### Impact Explanation
Once `withdraw()` (or the `SweepDust` handler) executes against a token whose `transfer` returns `false` instead of reverting, `_orders[commitment][token]` is zeroed/decremented and `_filled[commitment]` is set to the beneficiary — the order is marked settled — but the tokens never leave the gateway. The beneficiary permanently loses the escrowed funds: there is no remaining accounting path to re-claim them (the commitment is already marked filled/refunded), and the tokens sit stuck in the `IntentGatewayV2` contract balance. This is a concrete permanent freezing/loss of user/solver funds in the intents escrow flow, matching the Medium-severity impact of the original AutoRoller finding.

### Likelihood Explanation
The intent gateway is a generic cross-chain intents system that supports arbitrary ERC20 tokens as escrowed inputs/outputs (`order.inputs`, `TokenInfo.token`), so it is entirely plausible for a user or integrator to specify a non-standard ERC20 (deflationary/blacklist/pausable token) as an input asset. The vulnerable code path (`withdraw`) is triggered on every single order settlement and refund — it is not a rare edge case but the core redemption logic for the Tron deployment, making the likelihood of encountering an incompatible token realistic for any protocol integration accepting arbitrary listed tokens.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer` (as already done in `evm/src/apps/intentsv2/IntentsBase.sol`), which decodes and validates the returned boolean (or handles no-return-value tokens) and reverts on any failure mode, ensuring `_orders[...]` accounting is only ever decremented when the transfer genuinely succeeded.

### Proof of Concept
1. A user places an order via `IntentGatewayV2` (Tron) with an input token `T` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., the token blacklists the beneficiary address, or has some other silent-failure condition) — see escrow set-up at [5](#0-4) .
2. The order is cancelled/refunded, or filled and redeemed cross-chain, triggering `onAccept` → `withdraw(body, isRefund)` with `beneficiary` set to an address the token contract will silently reject (or under any condition causing `transfer` to return `false` without reverting).
3. In `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, encoded_false)` — the outer call succeeds, so `success == true` and no revert occurs.
4. `_orders[body.commitment][token] -= amount` executes, zeroing the escrow record, and `_filled[body.commitment] = beneficiary` marks the order settled, emitting `EscrowRefunded`/`EscrowReleased`.
5. The tokens remain in the `IntentGatewayV2` contract's balance; the beneficiary receives nothing and has no further on-chain mechanism to reclaim the escrow, since the commitment is already recorded as filled/refunded.
