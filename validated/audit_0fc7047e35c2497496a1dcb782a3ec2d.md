### Title
Batched POST request delivery can be entirely reverted by a single already-delivered or timed-out leaf, DOS'ing message delivery for the whole batch - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` and `handleGetResponses` process an entire batch of unrelated cross-chain messages (all requests bundled under one MMR proof) as a single atomic transaction. If any single leaf in the batch is a duplicate, targets the wrong destination, or has timed out, the whole call reverts, forcing the relayer to fail delivery of every other otherwise-valid request bundled alongside it. This mirrors the reported "Transfer design prone to DOS" pattern where a single failing settlement step reverts an entire batch of unrelated operations, instead of isolating the failure.

### Finding Description
`handlePostRequests` builds `leaves` for every request in the batch, verifies them together against one Merkle Mountain Range proof, and then, in a second loop, dispatches each request — but reverts the *entire call* the moment any single request fails a per-item check: [1](#0-0) 

Specifically:
- The first loop reverts with `InvalidMessageDestination()` or `MessageTimedOut()` for the whole batch if just one leaf fails those checks.
- The second loop reverts with `DuplicateMessage()` for the whole batch if just one leaf's request commitment was already delivered.

Because `handlePostRequests` is permissionless (any relayer or self-relaying user can call it), an adversary can grief a batch by delivering (or causing to time out) a single request contained in someone else's pending, larger multi-request MMR batch before that batch is submitted. When the honest relayer later submits their full batch, the transaction reverts on the poisoned leaf, and every other legitimate request in that batch fails to be delivered in that transaction, even though they are individually valid and provable.

The same structural pattern exists in `handleGetResponses`: [2](#0-1) 

This is architecturally the same problem flagged in the external report: batched settlement/execution units are not isolated from each other — one bad item aborts the whole unit — instead of using a try/catch-and-continue (or per-leaf skip) pattern that lets the rest of the batch settle.

Note this is distinct from `IHandlerV2.batchCall`'s intentionally atomic multi-call batching (explicitly documented and tested as atomic-by-design, e.g. `testBatchCallRevertsAtomically`), which is a deliberate relayer convenience feature, not the code path examined here. The per-leaf batching inside `handlePostRequests`/`handleGetResponses` is not something callers explicitly opt into per item; it's determined by how the relayer/tesseract groups deliverable messages under one MMR proof.

### Impact Explanation
A single already-delivered, mis-destined, or timed-out request forces a relayer's entire multi-request delivery transaction to revert, delaying delivery of all other valid requests bundled with it. This degrades the reliability of the message route: legitimate cross-chain requests (including token transfers built on top of ISMP, e.g. `HyperFungibleToken`/`WrappedHyperFungibleToken` `send()` flows) can be repeatedly stalled by griefing individual leaves, and time-sensitive requests risk crossing their `timeoutTimestamp` while relayers repeatedly rebuild and resubmit batches — this falls under "a route unable to deliver messages" in the accepted impact categories.

### Likelihood Explanation
Calling `handlePostRequests`/`handleGetResponses` is fully permissionless, and duplicate/timeout conditions are easy and cheap for any actor to trigger by submitting a small, single-leaf delivery for one message inside a larger pending batch (visible off-chain via the relayer network or mempool). No privileged role or governance action is required.

### Recommendation
Process each leaf in `handlePostRequests`/`handleGetResponses` independently after proof verification: catch failures per-leaf (e.g., skip and emit an event/continue instead of reverting) so that a duplicate, mis-destined, or timed-out request only fails delivery for that single item, not for the entire batch. This mirrors the report's recommendation to isolate settlement failures (try/catch per unit of work) rather than reverting the aggregate operation.

### Proof of Concept
1. Relayer A builds an MMR proof covering requests `R1..R20` destined for chain `X` and prepares to call `handlePostRequests(host, {proof, requests: [R1..R20]})`.
2. Attacker observes `R5` in the mempool/relayer network and submits their own `handlePostRequests` call delivering only `R5` (using a valid sub-proof for that single leaf) before Relayer A's transaction lands.
3. Relayer A's transaction executes; in the second loop of `handlePostRequests` (`evm/src/core/HandlerV2.sol:204-209`), `host.requestReceipts(R5.hash())` is now non-zero, so `revert DuplicateMessage()` fires, aborting delivery of `R1..R20` in the same call — even though `R1-R4` and `R6-R20` were never previously delivered.
4. Relayer A must rebuild and resubmit a new batch excluding `R5`, delaying delivery of 19 otherwise-valid requests, and repeating this griefing per submission can be used to indefinitely stall specific corridors or time-sensitive messages.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }
