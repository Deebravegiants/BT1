### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `x-shopify-shop-domain` (or `shopify-shop-domain`) header as the shop identity passed to the app's handler. Because the shop header is not part of the signed material, an attacker who legitimately receives one authentic, correctly-signed webhook (e.g., by installing the app on their own store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different shop domain in the header, and the library will accept it as authentic and hand it to the handler labeled as coming from the victim shop.

### Finding Description
The bug-class in the report is "a check on the wrong data" — here it is a value (the shop identity) that is *acted upon* by the application but never covered by the cryptographic binding (the HMAC) that is supposed to authenticate the whole message.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC only over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates all processing on that same HMAC check, then immediately trusts `request.shop` (an unauthenticated header) to build the metadata delivered to the app-supplied handler: [4](#0-3) 

The equality the code implicitly assumes is:
`shop_used_by_handler(request.shop) == shop_that_produced_and_signed_this_body`

But the HMAC only proves `hmac == HMAC(secret, body)`; it says nothing about which shop the body belongs to. Since a single app has one shared `api_secret_key` across all shops that install it, any tenant of the app can generate a validly-signed `(body, hmac)` pair for their own shop (by simply receiving one of their own real webhooks), then resend that exact pair to the app's endpoint with the `x-shopify-shop-domain` header changed to a different (victim) shop. The HMAC check still passes because the body is unmodified, and the handler executes with `shop: <victim shop>` while the actual body content originated from the attacker's own store.

### Impact Explanation
This breaks the tenant identity binding: an attacker-controlled webhook payload is processed by the app's business logic under another merchant's `shop` identity. Depending on what the app's webhook handler does with `data.shop` (e.g., looking up that shop's session/access token, updating shop-scoped records, triggering shop-scoped side effects), this can lead to cross-tenant data corruption or cross-tenant actions being taken against a shop the attacker does not control — matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only:
1. The attacker installs the app on any shop they control (a normal, unprivileged action any internet user can perform for apps with public/dev installs), and
2. The attacker captures one legitimate webhook `(raw_body, hmac header)` pair delivered to their own endpoint, then
3. Replays it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header.

No knowledge of `api_secret_key`, access tokens, or any other credential is required — the exploit only depends on the header not being part of the signed content, which is a property of this gem's `Webhooks::Request`/`HmacValidator` design, not of the host application.

### Recommendation
Bind the shop identity to the authenticated request instead of trusting an unsigned header:
- Require the app to independently verify that `request.shop` corresponds to a shop it has an active session/installation for, and reject webhooks for shops it does not recognize (partial mitigation, still doesn't stop same-app cross-tenant replay).
- Stronger fix: include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them to the payload) so the HMAC covers the full identity tuple, not just the body, preventing header substitution on a captured valid payload.
- Track/reject replay of previously seen `webhook_id` values to prevent replay entirely.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a real webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 123, ...}`
3. Attacker captures this exact `(body, hmac)` pair.
4. Attacker resends the same request to the app's webhook endpoint, only changing the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - same body, same `x-shopify-hmac-sha256`
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the secret.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-199` invokes the app handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though that body never originated from `victim-shop`.
