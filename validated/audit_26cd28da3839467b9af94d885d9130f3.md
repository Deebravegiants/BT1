### Title
Webhook Shop/Topic Identity Not Bound to HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed unchecked into the webhook handler by `Registry.process`. Any party who can obtain one valid `(body, hmac)` pair — which any unprivileged user can, simply by installing the target app on their own shop — can replay that pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain`/`topic` header, and the library will accept it as authentic.

### Finding Description
The analog to the reported bug class is an identity-binding mismatch: the field the handler acts on (`shop`, `topic`) is not the field covered by the cryptographic check (`hmac` over raw body only).

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers that are never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC solely from `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.topic` and `request.shop` to route/dispatch the webhook, without any additional binding check that ties those header values to the specific signed payload: [4](#0-3) 

Equality that should hold but does not: `hmac == HMAC(secret, body ‖ shop ‖ topic)`. In reality the code only enforces `hmac == HMAC(secret, body)`, so `shop` and `topic` are free variables an attacker fully controls via headers, as long as the body bytes are unchanged.

### Impact Explanation
Because the same shared `api_secret_key` is used for every shop that installs the app, and the HMAC never binds to `shop`/`topic`, an unprivileged user who installs the app on their own store can capture a legitimate `(body, hmac)` pair from a webhook their own shop legitimately receives (many topics, e.g. `app/uninstalled`, carry an empty or predictable body `{}`). They can then replay that exact body/hmac to the app's public webhook endpoint while setting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) to a different, victim shop's domain. `Utils::HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the event belongs to the victim shop. This is a cross-tenant identity spoof — the classic "field acted on but not covered by the HMAC" bug class — and can be used to trigger shop-scoped side effects (e.g., data deletion/resync logic keyed on `app/uninstalled`, or other topic handlers) against a tenant the attacker does not control.

### Likelihood Explanation
High/likely for any multi-tenant app built on this gem: no credential or privileged access is required beyond the trivial ability to install the target app on a free/attacker-controlled Shopify development store (an action available to any internet user), after which a valid signed webhook body is obtainable and directly replayable with modified identity headers.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-validated signable content (or otherwise cryptographically verify them against the source of the request, e.g., by cross-checking `shop` against a session/shop record the app already trusts for that installation) instead of trusting them as bare, unauthenticated headers. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain and topic so that `HmacValidator.validate` fails if any of these values are altered from what was actually signed.

### Proof of Concept
1. Attacker creates a free Shopify dev store and installs the vulnerable app (no privileged access needed).
2. App registers a webhook (e.g. topic `app/uninstalled`) for the attacker's own shop; Shopify later delivers:
   ```
   POST /webhooks
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <valid HMAC of "{}">
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {}
   ```
3. Attacker records this exact `(body="{}", hmac)` pair.
4. Attacker sends a forged request to the app's public webhook endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <same HMAC as captured>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {}
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from the body `"{}"` only — it matches, since the body is unchanged.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", body: {})`, causing the app to process a tenant-scoped event for `victim-shop.myshopify.com` that the attacker never legitimately triggered — a cross-tenant spoof enabled purely by headers that fall outside the HMAC's coverage.
