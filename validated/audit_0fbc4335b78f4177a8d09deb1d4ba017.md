### Title
Redeploying a gateway instance via `NewDeployment` misroutes settlement for orders escrowed under the old instance, permanently freezing funds - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`IntentsBase._instances[chain]` is a mutable mapping from a state-machine ID to "the current gateway address on that chain." `_post()` looks up this mapping *at fill/cancel time* to build the `to` field of the cross-chain settlement message, rather than using the address that was live when the order's escrow was created. If Hyperbridge governance issues a `NewDeployment` request that rotates a chain's registered gateway address (a normal, non-malicious migration action, analogous to `TellerV2.setLenderManager()`), any order whose escrow currently sits in the *old* gateway on the source chain, but which is filled/cancelled on the destination chain *after* the rotation, has its `RedeemEscrow`/`RefundEscrow` message routed to the *new* (empty) gateway contract instead of the old one holding the escrow.

### Finding Description
`_post` builds the outgoing settlement message's recipient from the live registry, not from any value pinned to the order:

```solidity
function _post(Order calldata order, bytes memory body, uint256 relayerFee, uint256 nativeFee) internal {
    DispatchPost memory request = DispatchPost({
        dest: order.source,
        to: abi.encodePacked(_instance(order.source)),   // <-- resolved NOW, not at order-placement time
        ...
    });
``` [1](#0-0) 

`_instance()` simply returns whatever is currently stored:
```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
``` [2](#0-1) 

That registry is overwritten unconditionally by `_addDeployment`, reachable only from a `NewDeployment` request sent by Hyperbridge itself:
```solidity
function _addDeployment(Deployment memory body) internal {
    _instances[keccak256(body.chain)] = body.gateway;
    emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
}
``` [3](#0-2) 

Sequence:
1. A user places a cross-chain order on chain A (old gateway `G_A_old`). Input tokens are escrowed in `_orders` on `G_A_old`.
2. Before the order is filled, Hyperbridge governance redeploys the gateway on chain A and dispatches `NewDeployment` to every other chain, updating `_instances[chainA] = G_A_new` everywhere (a routine, intended migration — not malicious governance).
3. A solver later fills the still-pending order on the destination chain. `_fillCrossChain` calls `_post(order, RedeemEscrow-body, ...)`, which resolves `to: _instance(order.source)` — now `G_A_new`, not `G_A_old`.
4. The `RedeemEscrow` message lands on `G_A_new`, which has no record of the commitment (its own `_orders`/`_filled` mappings are empty for that commitment), so the withdrawal has no matching escrow to release. `G_A_old` — which actually holds the user's escrowed tokens — never receives the settlement message and the escrow is not released.
5. The escrowed input tokens remain locked in `G_A_old._orders[commitment][token]` indefinitely, with no code path to redirect a correctly-authenticated `RedeemEscrow`/`RefundEscrow` message to it after the instance rotation.

This mirrors the reported TellerV2 pattern exactly: a single mutable "current owner/location" address (`lenderManager` / `_instances[chain]`) is substituted for the value that should have been pinned to the record at creation time, so a subsequent (legitimate) rotation causes assets tied to the old value to be unreachable through the normal flow.

### Impact Explanation
Any in-flight cross-chain order whose source-chain escrow predates a `NewDeployment` gateway rotation for that chain becomes unredeemable/unrefundable through the standard fill/cancel flow: its settlement message is misdirected to the new gateway instance, which holds no matching state. The user's escrowed input tokens remain stuck in the old gateway contract's storage, and the filler who already delivered output tokens on the destination chain never receives the promised inputs. This is a Medium-severity concrete loss/freezing of funds triggered by a normal (not malicious) governance action, exactly matching the analog's severity class.

### Likelihood Explanation
Gateway redeployments (`NewDeployment` to rotate a chain's registered instance) are an expected part of the protocol's governance surface — the same request kind is also used to register brand-new chains, so it is not a rare emergency-only code path. Any order left un-settled across a redeployment window (a normal race between order lifetime and a scheduled migration) triggers the freeze without any attacker action.

### Recommendation
Snapshot the destination gateway address into the order/escrow state at the time escrow is created (or at least at fill/cancel time compare against the instance that was live when the order was placed), or have `onAccept`'s `_authenticate` accept messages `from` any *previously registered* instance for that source chain (an allow-list/history of instances) rather than only the current one, and correspondingly retain the ability to route settlement to the specific instance address recorded on placement rather than looking it up fresh via `_instance()`.

### Proof of Concept
1. Deploy `ExtrinsicIntents`/`IntentGatewayV2` on chain A (`G_A_old`) and chain B (`G_B`), with `_instances` cross-registered.
2. On chain A, place a cross-chain order with `source = chainA`, `destination = chainB`; escrow lands in `G_A_old._orders`.
3. Deliver a `NewDeployment` request (from Hyperbridge) to `G_B` updating `_instances[chainA] = G_A_new` (a freshly deployed, empty gateway on chain A).
4. On chain B, call `fillOrder` for the pending order. `_fillCrossChain` → `_post` computes `to = _instance(order.source)` = `G_A_new`.
5. Deliver the resulting `RedeemEscrow` PostRequest to chain A; it lands on `G_A_new` (per `to`), whose `_orders`/`_filled` mappings have no entry for the commitment — the withdrawal is a no-op there.
6. Confirm `G_A_old._orders[commitment][inputToken]` is unchanged (still escrowed) and no code path exists to route the message there, while the filler already delivered output tokens on chain B — a stuck/lost fund state exactly analogous to `getLoanLender()` returning the stale `lenderManager` address after rotation.
