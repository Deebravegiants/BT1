### Title
Webhook `shop-domain` header used to identify tenant is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw JSON body, but then dispatches to the app's handler using a `shop` value taken from an HTTP header that is never included in the signed payload. This breaks the identity binding: `shop used by the handler != shop covered by the HMAC`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and the HMAC is validated against that raw body via `Utils::HmacValidator.validate`: [1](#0-0) [2](#0-1) 

Meanwhile, `Webhooks::Request#shop` (and `topic`, `api_version`, `webhook_id`) is read straight from an unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`): [3](#0-2) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (from the header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the header is not part of the signed data (`to_signable_string` = raw body only), an attacker who has captured (or replays/relays) a single legitimately-HMAC-signed webhook body from Shopify — e.g., their own store's `orders/create` webhook, which they control and can trigger themselves — can resubmit that exact same body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The HMAC check still passes because it's computed only over the (unaltered) body, but `Registry.process` reports the attacker-chosen `shop` to the app handler. Any app that keys tenant-specific side effects (session lookup, database routes, per-shop crediting/logic) off `data.shop` in the handler is thus tricked into acting as if the payload belongs to a different, victim shop — a cross-tenant confusion.

This matches the bug class from the report: the code validates one representation of the data (the HMAC over `raw_body`) but acts on a separate representation (the `shop` header) that isn't bound to that validation, analogous to `_getTokenIn`'s `path` not being updated so the check operates on stale/wrong data.

### Impact Explanation
This allows cross-tenant confusion: an attacker with any legitimate shop can obtain a validly-signed webhook body (since they can trigger events in their own store) and replay it to the target app with a forged `shop-domain` header, causing the app to process/act on the webhook payload under a different shop's identity. Depending on how the consuming app uses `WebhookMetadata#shop` (e.g. to select credentials, associate data, or write records), this can lead to cross-tenant data corruption or leakage — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to control at least one Shopify shop that installs the target app (to generate a validly HMAC-signed body) and requires the consuming application to trust `data.shop` from `WebhookMetadata` for tenant-scoped actions without independent verification (e.g. cross-checking against a known list of subscribed shops or the webhook's registered path). This is a realistic setup since webhook shop scoping is exactly the documented purpose of the `shop` field, and the gem provides no protection against header spoofing since it explicitly reads `shop` from an HTTP header outside the signed payload.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values into the HMAC-verified data, or independently validate that the header's shop domain corresponds to the shop for which the given webhook topic/registration was set up before dispatching to the handler. At minimum, document that `data.shop` in `WebhookHandler#handle` must not be trusted for tenant isolation without further verification, or change `Request#to_signable_string` so the shop header is authenticated as part of the request signature (in line with how Shopify's REST/GraphQL clients bind shop domains into a session).

### Proof of Concept
1. Attacker owns shop `attacker.myshopify.com`, which has installed the target app.
2. Attacker triggers a webhook event (e.g. `orders/create`) in their own shop, causing Shopify to POST a body `B` with a valid `x-shopify-hmac-sha256` header computed as `HMAC-SHA256(api_secret_key, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (== raw body `B`, unchanged) and successfully matches the untouched signature: [5](#0-4) .
5. `WebhookMetadata` is built with `shop: request.shop` == `"victim.myshopify.com"` (from the forged header), and the app's handler is invoked believing the webhook belongs to `victim.myshopify.com`: [6](#0-5) .

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
