## Finding: POA Bridge `describeWithdrawal` Matches Withdrawal by Asset Type Only, Not by Withdrawal Identity — Misreports Status/Hash for Multi-Withdrawal Transactions

The reported CVE (GHSA-wx8q-rgfr-cf6v) is an "insufficient granularity of access control" bug: an operation intended to act on a specific record (a verification code by UUID) instead matched too broadly (any code with a guessable UUID across realms), letting an action be applied to the wrong record. The closest analog in this repo is in the POA bridge's withdrawal-status lookup, where a specific withdrawal (identified by NEAR tx hash + index + destination + amount) is looked up using only the asset type, so a different withdrawal's completion status/hash can be reported for the one being queried.

### Finding Description

`PoaBridge.describeWithdrawal` in [1](#0-0)  retrieves all withdrawals for a NEAR tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` to pick the record corresponding to the specific `WithdrawalIdentifier` (`{ landingChain, index, withdrawalParams, tx }`) being described.

`findMatchingWithdrawal` only compares `nep141:${w.data.near_token_id} === assetId` [2](#0-1) . It ignores `index`, `destinationAddress`, and `amount` entirely — the very fields that make a `WithdrawalIdentifier` unique among sibling withdrawals in the same NEAR transaction. The code comment even documents this limitation explicitly ("multiple withdrawals of the same token in a single transaction are not supported"), but there is no runtime guard: `.find()` silently returns the *first* array element whose token matches, with no assertion that it's the only one and no validation against `destinationAddress`/`amount` of the identifier being queried.

This is confirmed by the test at [3](#0-2)  titled "matches withdrawal by assetId, not by index," which shows the intended (documented) behavior is asset-only matching — but the same mechanism means that if a NEAR account issues a batch withdraw with two outputs of the same token (e.g., two different destination addresses, same asset, different amounts, as legitimately supported by `createWithdrawalIntents`/multi-intent batches), `describeWithdrawal(index=1)` can return the status/`txHash` that actually belongs to withdrawal `index=0` (or vice versa), because both share the same `near_token_id`.

The equality that should hold — "the withdrawal status/txHash returned matches the exact withdrawal (destination + amount + index) requested" — is broken. Instead, the caller may receive the outcome of a *different* withdrawal that merely shares the token type.

### Impact Explanation

`describeWithdrawal`'s result flows into `watchWithdrawal` in [4](#0-3) , which resolves to a `txHash`/`completed` status that integrators use to credit users or mark withdrawals as settled. If withdrawal A (small amount, address X) and withdrawal B (large amount, address Y) share the same asset in one NEAR tx, and B completes while A is still pending (or A fails while B succeeds), the SDK can report B's `txHash`/completed status for A's identifier. An integrator polling per-withdrawal status could then:
- mark a still-pending/failed withdrawal as completed with an unrelated tx hash (double-credit / incorrect settlement bookkeeping), or
- surface the wrong destination's transaction hash to the wrong user.

This matches the in-scope impact category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation

This requires no privileged or malicious actor — any normal user/integrator issuing a batch withdrawal with two same-asset outputs (a supported, unprivileged usage pattern via the intents SDK's multi-withdrawal creation path) triggers the ambiguous matching. The bug is deterministic once such a batch exists and the two same-asset withdrawals settle at different times/outcomes, which is plausible under normal bridge processing latency.

### Recommendation
`findMatchingWithdrawal` should disambiguate using all identifying fields available in the `WithdrawalIdentifier` (destination address, amount, and/or a stable per-intent sequence number), not just `assetId`, and should assert uniqueness of the match rather than silently taking `.find()`'s first hit. If the POA bridge API cannot yet return enough data to disambiguate deterministically (as the comment suggests), `describeWithdrawal` should refuse to report `completed` for ambiguous multi-match cases and keep status `pending` (or explicitly error) rather than risk cross-reporting.

### Proof of Concept
1. Build a batch NEAR transaction containing two POA withdrawal intents for the same `assetId` (e.g. `nep141:eth.omft.near`): withdrawal `index=0` to address `X` for amount `100`, and `index=1` to address `Y` for amount `100000`.
2. Only withdrawal `index=1` (to `Y`) settles and appears in the POA API response with `status: "COMPLETED"`, `transfer_tx_hash: "0xY..."`; withdrawal `index=0` is still `PENDING` upstream but not yet reflected, or the API returns only one row for that asset at query time.
3. Call `bridge.describeWithdrawal({ ...identifierForIndex0 })`. Because `findMatchingWithdrawal` filters solely on `nep141:eth.omft.near === assetId`, it returns the `index=1` row, and `describeWithdrawal` reports `{ status: "completed", txHash: "0xY..." }` for the `index=0` identifier — i.e., the caller is told withdrawal to `X` is complete with a hash that actually belongs to the transfer to `Y`.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
