### Title
Webhook `shop` identity is trusted for tenant routing but is never covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) identity from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature verified by `HmacValidator.validate` is computed only over `@raw_body` (`to_signable_string` returns `@raw_body` alone). The `shop` value that the registry hands to application webhook handlers is therefore never bound to the HMAC that authenticates the request.

### Finding Description
`Webhooks::Registry.process` accepts a request as valid webhook traffic solely based on `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to build the signed material: [1](#0-0) 

The HMAC is computed only from the raw body: [2](#0-1) 

But the `shop` attribute — used to build `WebhookMetadata` and passed straight to the application's registered handler as the tenant identifier — is read from an HTTP header that is completely outside the signed material: [3](#0-2) [4](#0-3) 

The identity binding broken is: `shop authenticated (bytes covered by HMAC) != shop used as tenant key (header value handed to the handler)`. `HmacValidator.compute_signature`/`validate_signature` only ever operate on `verifiable_query.to_signable_string`, and for `Request` that string is `@raw_body` — the `shop-domain` header is never mixed into the signable string, unlike `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly includes `shop` in the signed parameters: [5](#0-4) [6](#0-5) 

Because a valid HMAC for a given `raw_body` is reusable with any `shop-domain` header, an unprivileged attacker who has ever received one legitimate webhook body/HMAC pair for a shop under the same app (e.g. from their own store) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will pass because the signature check never inspects the header, and `Registry.process` will dispatch the event to the app's handler with `data.shop` set to the attacker-chosen value.

### Impact Explanation
This is a cross-tenant confusion vector for host applications that rely on this gem's `Webhooks::Registry.process`/`WebhookMetadata#shop` to determine which merchant's data/session/access token to act on. An attacker who controls one legitimate webhook payload/HMAC pair (from their own shop) can cause the app to process/attribute that event under a different, victim shop domain, since the library performs no binding between the authenticated bytes and the tenant identifier it exposes to the handler. This matches the "Critical — cross-tenant access" category, as it breaks the tenant isolation the HMAC check is meant to provide.

### Likelihood Explanation
Likelihood is High for any app that installs on multiple merchants and trusts `WebhookMetadata#shop`/`request.shop` after `HmacValidator.validate` succeeds, which is exactly the intended usage pattern documented via `Registry.process`. No credentials, secrets, or privileged access are required — only the ability to send an HTTP request with attacker-controlled headers and a previously-observed valid `(body, hmac)` pair from any shop using the same app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signed material, or independently verify the `shop-domain` header against a known/authorized value before dispatching to handlers. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (mirroring how `AuthQuery#to_signable_string` includes `shop`), so that tampering with the tenant-identifying header invalidates the signature.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker (who owns `shop-a` or otherwise observed this `(B, H)` pair) resends the identical request to the app's webhook endpoint but sets `shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `to_signable_string` returns `B` unchanged.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B) == H` — passes, since the shop header was never part of the signed input: [7](#0-6) 
5. `Registry.process` dispatches to the handler with `shop: "shop-victim.myshopify.com"` even though the payload/signature actually belongs to `shop-a`: [1](#0-0)
