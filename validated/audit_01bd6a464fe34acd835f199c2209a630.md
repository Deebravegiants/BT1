Confirmed. The Tron `IntentGatewayV2.sol` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) has the exact bug class: it credits escrow accounting (`_orders[commitment][token] += reducedInputs[i].amount`) based on the *assumed pre-sweep* `balance` at the `CallDispatcher`, before actually verifying the low-level `transfer` call succeeded — unlike the newer mainline `evm/src/apps/IntentGatewayV2.sol`, which measures `balancesBefore`/`balancesAfter` deltas post-sweep to derive the real received amount. Combined with `CallDispatcher.dispatch` only checking `success` of the raw `.call` (not the ERC20 boolean return), a non-reverting-but-failing `transfer` (e.g., malicious/non-standard token, or blacklist/pause condition) lets the contract record full escrow credit for tokens that never actually left the `CallDispatcher`.

### Title
Tron `IntentGatewayV2.placeOrder` credits escrow for predispatch-swept tokens without verifying the sweep transfer actually succeeded - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2`, when an order has `predispatch` calldata, input tokens are produced inside the untrusted `CallDispatcher` (e.g., via a swap) and then must be swept back to the gateway using a raw `IERC20.transfer` call routed through `CallDispatcher.dispatch`. The gateway credits `_orders[commitment][token] += reducedInputs[i].amount` based on the balance observed at the dispatcher *before* the sweep succeeds, and never re-checks the gateway's own balance after the sweep completes.

### Finding Description
`CallDispatcher.dispatch` only reverts if the low-level `.call` itself reverts; it does not decode/check the boolean return value of the ERC20 `transfer` call: [1](#0-0) 

In the Tron `placeOrder` predispatch branch, the gateway computes `balance = IERC20(token).balanceOf(dispatcher)` and builds a `transfer` call using `IERC20.transfer.selector` (raw selector, not `safeTransfer`), then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` and only afterward dispatches the actual transfer calls: [2](#0-1) 

Because the escrow accounting update happens before, and independent of, verification of the swept balance actually arriving at the gateway, a token that returns `false` on `transfer` (a widely-known non-standard-ERC20 pattern, or a token that can be paused/blacklisted/rebased mid-flight by the same user's own predispatch call) causes `CallDispatcher.dispatch`'s inner `.call` to report `success = true` even though no tokens moved. The gateway then believes it holds `reducedInputs[i].amount` of the token in escrow when it does not.

This differs materially from the mainline EVM `IntentGatewayV2.sol`, which snapshots `balancesBefore`, dispatches the sweep, and then computes `received = balanceOf(this) - balancesBefore[i]` before crediting `order.inputs[i].amount`, so its accounting is always backed by actually-received tokens: [3](#0-2) 

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) becomes unbacked by real token balance. Since `_withdraw`/settlement logic pays out from this same accounting on fill, cancel, or refund paths (`IERC20(token).safeTransfer(beneficiary, amount)`), an attacker can construct an order whose predispatch call uses a token contract they control (or a known non-compliant token) that silently no-ops the sweep `transfer`, then have the gateway record full escrow credit for tokens it never received. When the order is later filled or refunded, the gateway pays out real tokens (drawn from other users' legitimately escrowed balances) against phantom escrow, directly enabling theft of funds from the shared token pool / insolvency of the escrow contract.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with an order that sets `predispatch.call` and `predispatch.assets`, using an input token that is non-standard (returns `false` instead of reverting on failed transfer) or that the attacker controls to intentionally return `false`/no-op under attacker-chosen conditions inside their own predispatch call. No special privileges, governance, or relayer collusion are required — a single crafted transaction suffices.

### Recommendation
Mirror the mainline `evm/src/apps/IntentGatewayV2.sol` pattern in the Tron contract: snapshot the gateway's token/native balance before dispatching the sweep `Call[]`, dispatch the sweep, then compute the actually-received amount as the post-sweep balance delta, and only credit `_orders[commitment][token]` with that verified amount (reverting or reducing accordingly if less than `requiredAmount`). Additionally, replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` construction with a pattern that uses `safeTransfer` semantics (e.g., have `CallDispatcher` decode and check the boolean return data for `IERC20`-selector calls, or perform sweeps outside the untrusted dispatcher using `safeTransferFrom`/`safeTransfer` directly in the gateway) so silent transfer failures cannot be interpreted as success.

### Proof of Concept
1. Attacker deploys a token contract `EvilToken` implementing ERC20 `balanceOf`/`transfer` where `transfer(address to, uint256 amount)` returns `false` without reverting whenever `to == gatewayAddress` (or unconditionally, mimicking known non-compliant tokens like older USDT variants that don't revert on failure in some paths).
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0].token = EvilToken`, `order.predispatch.assets` funding the `CallDispatcher` with `EvilToken` (or any asset that predispatch call swaps into `EvilToken` on the dispatcher), and `order.predispatch.call` a no-op/self call.
3. Execution reaches lines 427-441 in `evm/tron/contracts/apps/IntentGatewayV2.sol`: `balance = IERC20(EvilToken).balanceOf(dispatcher)` is read, `requiredAmount` check passes, `transferCalls[i]` is built with the raw `transfer` selector, and `_orders[commitment][EvilToken] += reducedInputs[i].amount` is credited immediately.
4. `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` executes the sweep; `EvilToken.transfer` returns `false` but does not revert, so `CallDispatcher`'s `success` check at line 59-60 of `CallDispatcher.sol` passes and no tokens are actually moved to the gateway.
5. The gateway now shows escrow credit for `EvilToken` inputs it never received. When this or another order later triggers `_withdraw`/settlement paying out `EvilToken` (or the accounting cross-contaminates pooled accounting logic), the gateway pays out from balance actually contributed by other legitimate depositors, resulting in fund loss/insolvency.
