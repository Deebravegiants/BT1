Confirmed. The `Webhooks::Request` class validates the HMAC solely over the raw HTTP body (`to_signable_string` returns only `@raw_body`), while the `shop`, `topic`, and `webhook_id` fields — which `Registry.process` trusts to route and identify the tenant — are read straight from unauthenticated HTTP headers with no cryptographic binding to the signed payload.

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC, enabling cross-tenant webhook spoofing/replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies solely that the body bytes match the `hmac` header signature. The `shop`, `topic`, and `webhook_id` values that `Webhooks::Registry.process` uses to dispatch the webhook to the correct handler and tenant come from separate, unsigned HTTP headers.

### Finding Description
The binding an app relies on is: `shop used to route/act on the webhook == shop the signed body was actually produced for`. In `Webhooks::Request`: [1](#0-0) [2](#0-1) 

`hmac` is computed over `@raw_body` only; `shop`, `topic`, and `webhook_id` are pulled from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are never mixed into `to_signable_string`. `HmacValidator.validate` then checks only body-vs-hmac: [3](#0-2) 

`Registry.process` trusts the header-derived `shop` (and `topic`) unconditionally once the body/hmac pair is valid: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop installed on the app (it is not a per-shop secret), a merchant who legitimately receives a real, validly-signed webhook for their own shop can capture the `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers changed. Since none of those header fields are part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the app's handler believing the (unmodified, validly-signed) body belongs to a different shop and/or topic: [5](#0-4) 

Before the attack: `shop_header == shop_that_produced_body` (both equal shop A). After the attacker replays with a modified header: `shop_header (shop B) != shop_that_produced_body (shop A)`, yet the check in `Registry.process` treats them as equal because it never verifies that equality — it only checks the HMAC over the body.

### Impact Explanation
This is a cross-tenant data-integrity/authentication issue: an app that persists or acts on webhook data keyed by `WebhookMetadata#shop` (returned from `request.shop`) can have shop A's genuine, signed event data attributed to shop B, or have a topic re-labelled via the unsigned `topic` header while keeping a validly-signed body from a different event. This crosses the tenant boundary the gem is expected to enforce for webhook authenticity, without requiring the app's `api_secret_key`, an access token, or any privileged access — only receipt of one legitimate webhook to the attacker's own store and the ability to send an arbitrary HTTP request to the app's public webhook endpoint.

### Likelihood Explanation
Any merchant/developer who installs the app is, by design, entitled to receive real webhooks for their own shop. Capturing one webhook's raw body and HMAC (e.g., via their own server logs) and re-POSTing it with a different `shop-domain` header requires no special access, no TLS interception, and no secret material — only a standard HTTP client.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the signed material verified by `to_signable_string`, or otherwise cryptographically bind them to the request before use (e.g., derive shop identity solely from a value that is part of the HMAC-covered content, or require the host application to independently confirm the header-derived shop matches an installation record before invoking `Registry.process`). At minimum, document that `request.shop`/`request.topic` are unauthenticated and must not be trusted without an out-of-band tenant check.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key # shared across all shops on this app
body   = '{"id":123,"note":"legit order for shop-a"}'
hmac   = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body))

# Attacker captured this genuine (body, hmac) pair for their own store "shop-a.myshopify.com"
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,          # unchanged, still valid for `body`
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # attacker-controlled, spoofed
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only body+hmac checked),
#    handler.handle is invoked with shop: "shop-b.myshopify.com" even though
#    the signed body was produced for shop-a.
```
