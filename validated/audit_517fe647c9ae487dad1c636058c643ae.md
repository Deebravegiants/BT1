### Title
`Registry.process` trusts the unsigned `shop-domain`/`topic`/`webhook-id` headers as authenticated shop identity - (`lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` only proves that `Utils::HmacValidator.validate` accepts the raw request body; it then builds `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id`, all of which come from HTTP headers that are never included in the HMAC-signed string. An attacker who can obtain one validly-signed webhook body/HMAC pair (trivially, by registering their own development shop and triggering a real webhook) can replay that exact body+HMAC to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the handler will process it as authentic data for the spoofed shop.

### Finding Description
The binding the code implicitly relies on is: `verified(signable_string) == identity_used_by_handler`, i.e. `to_signable_string == {shop, topic, webhook_id}`. That binding is false.

- `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `shop`, `topic`, and `webhook_id` are read straight from unsigned HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no cryptographic binding to the body [2](#0-1) .
- `HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header [3](#0-2) .
- `Registry.process` calls `HmacValidator.validate(request)` to prove the body is signed, then immediately pulls `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` (all unsigned headers) into `WebhookMetadata` and hands that to the merchant's `handler.handle` [4](#0-3) .
- `WebhookMetadata#shop` is a plain `String` field with no additional validation performed by `Registry` or `WebhookHandler` before being trusted [5](#0-4) .
- There is no call to `Utils::ShopValidator.sanitize!` (or any equivalent) anywhere on this path; that validator is only used in the OAuth/token-exchange flows, not in webhook processing.

Exploit flow: an attacker registers their own development shop, installs the target app, and lets the app register a webhook subscription (e.g. `orders/create`). Shopify delivers a real webhook to the app with a valid `X-Shopify-Hmac-SHA256` computed over the body, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. The attacker captures this exact body + HMAC pair (they own the shop, so they can trivially trigger and observe it) and replays it directly to the app's public webhook endpoint, substituting `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Webhook-Id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because the signature only covers the untouched body. `Registry.process` then dispatches `handler.handle` with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload actually originated from, and describes, the attacker's own shop.

None of the existing guards catch this: `HmacValidator.validate` only checks body integrity, not header/body binding; `ShopValidator.sanitize!` is not invoked in this path at all; there is no Sorbet runtime check that ties `shop` to the signed payload (Sorbet only enforces the header value is a `String`, not that it was covered by the signature).

### Impact Explanation
Any app handler that uses `WebhookMetadata#shop` to select which merchant's tenant data to read, write, or key by (a extremely common pattern — e.g. updating per-shop order counters, writing customer data for `customers/data_request`/`customers/redact`/`shop/redact`, or invalidating per-shop caches) can be made to attribute attacker-controlled body content to an arbitrary victim shop domain string. This is a cross-tenant data-integrity/authentication issue: the app "authenticates" the request via HMAC but then trusts an unauthenticated field (`shop`) as if it were verified, satisfying the "unauthenticated value trusted as authenticated" impact class. It is repeatable indefinitely and against any victim shop domain the attacker chooses to type into the header, since the domain string itself needs no proof of ownership.

### Likelihood Explanation
Preconditions: the target app must (a) use `ShopifyAPI::Webhooks::Registry` for webhook dispatch (as documented) and (b) have at least one webhook topic registered with a handler that trusts `WebhookMetadata#shop` for tenant-scoped logic — both are the documented, expected usage pattern of this gem. Attacker cost is minimal: create a free development shop, install the app, trigger one real webhook event, capture body+HMAC via their own server, then POST it to the app's known webhook endpoint with a modified `Shop-Domain` header. No secrets, no TLS interception, and no privileged access are required — matching the attacker model in scope.

### Recommendation
Bind shop identity to the signed payload before trusting it: either (1) include the shop-identifying header(s) in the string handed to `HmacValidator` (i.e., extend `to_signable_string` to cover `shop`, `topic`, and `webhook_id`, matching what is computed on Shopify's side, if Shopify's signature scheme supports it), or (2) independently corroborate `request.shop` against a value obtained through an authenticated channel (e.g., verify the shop is one that legitimately has this webhook topic subscribed via a stored, previously-authenticated registration, not solely via the inbound header) before constructing `WebhookMetadata` in `Webhooks::Registry.process`. At minimum, document loudly that `WebhookMetadata#shop`/`topic`/`webhook_id` are NOT covered by the HMAC and must not be used for authorization decisions without additional verification.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require "test_helper"

class RegistryShopSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
  end

  class CapturingHandler
    include ShopifyAPI::Webhooks::WebhookHandler
    attr_reader :captured
    def handle(data:)
      @captured = data
    end
  end

  def test_shop_header_is_not_covered_by_signature
    handler = CapturingHandler.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks",
      handler: handler,
    )

    body = '{"id":1,"note":"attacker shop order"}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", "secret", body)
    )

    # Attacker replays the exact body+hmac pair captured from their own
    # legitimately-owned shop, but rewrites the shop-domain header.
    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen
        "x-shopify-api-version" => "2024-01",
        "x-shopify-webhook-id" => "1",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(request)

    # Assert the binding is broken: HMAC validated successfully (proving only
    # the body), yet the handler received an attacker-chosen shop identity
    # that was never part of the signed string.
    assert_equal "victim-shop.myshopify.com", handler.captured.shop
    refute_includes ShopifyAPI::Webhooks::Request.new(
      raw_body: body, headers: request.instance_variable_get(:@headers)
    ).to_signable_string, "victim-shop.myshopify.com"
  end
end
```
This demonstrates that `to_signable_string` (the string actually covered by `HmacValidator`) never contains the shop value, while `Registry.process` dispatches to the handler using that unverified shop value as if it were authenticated.
