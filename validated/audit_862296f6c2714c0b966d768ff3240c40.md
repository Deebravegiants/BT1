### Title
Fee-on-transfer token accounting mismatch in `evm/tron/contracts/apps/IntentGatewayV2.sol` `placeOrder` (non-predispatch path) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, the direct-escrow branch (no predispatch) blindly credits escrow with `reducedInputs[i].amount` — a value derived from the user-declared `order.inputs[i].amount` minus the protocol fee — without ever verifying how much of the ERC20 token the gateway actually received via `safeTransferFrom`. For a fee-on-transfer (FOT) token, the contract's actual token balance increase is smaller than the amount recorded in `_orders[commitment][token]`.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the code calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally does `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is computed earlier purely from the declared `order.inputs[i].amount` and `protocolFeeBps`: [2](#0-1) 

No `balanceOf` snapshot before/after the transfer is taken in this branch, unlike the predispatch branch just above it which explicitly measures `balance = IERC20(token).balanceOf(dispatcher)` and emits `DustCollected` for any shortfall/excess (lines 417-446). This means the escrow ledger `_orders[commitment][token]` can be credited with more tokens than the gateway actually holds whenever the input token charges a transfer fee (e.g., some stablecoins/deflationary tokens can be configured this way), inflating internal accounting relative to the real balance.

This directly mirrors the reported bug class: an internal "amount received" accounting variable (analogous to `poolAmount` in the referenced Allo `QVBaseStrategy`) is assumed equal to the nominal transferred amount, but is not reconciled against the real balance delta for FOT tokens.

Notably, the sibling production file `evm/src/apps/IntentGatewayV2.sol` (the canonical EVM IntentGatewayV2) already fixes this exact issue by measuring `balBefore`/`balAfter` around the transfer in the non-predispatch branch and mutating `order.inputs[i].amount` to the actual received value before computing `reducedInputs`/commitment/escrow: [3](#0-2) 
and this fix is extensively tested with a `FeeOnTransferToken` mock: [4](#0-3) 
The Tron fork at `evm/tron/contracts/apps/IntentGatewayV2.sol` still contains the vulnerable, unfixed pre-patch logic for its non-predispatch escrow path.

### Impact Explanation
Escrow (`_orders[commitment][token]`) is the internal accounting used both by `fillOrder`/solver repayment and by `cancelOrder`/`withdraw` refund logic to release tokens back to the order owner or pay the filler. If `_orders[commitment][token]` is inflated above the contract's actual token balance for that token (because the FOT token skimmed a fee on the way in), the gateway's aggregate liabilities recorded across all outstanding orders can exceed its actual token holdings. When orders using such a token are cancelled or the funds otherwise withdrawn, the contract will attempt to pay out more than it received, which either reverts (denial of service / stuck funds for legitimate users sharing the pooled token balance) or — if the gateway holds a surplus of that token from other orders — drains that surplus, effectively causing insolvency/fund loss for other order owners of the same token. This is a fund-safety issue triggerable by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer ERC20 as input.

### Likelihood Explanation
Likelihood depends on whether fee-on-transfer tokens are permitted as intent inputs on the Tron deployment; the codebase's own test suite (added to the canonical EVM version) proves this is an explicitly anticipated and supported token class for `IntentGatewayV2`, and the fix was already applied to the primary EVM contract but missed in the Tron fork. Any user can trigger the mismatch with a single `placeOrder` call using such a token, requiring no special privileges — likelihood is therefore not merely theoretical, it is a straightforward reachable path once a FOT token is whitelisted/used as input.

### Recommendation
Port the balance-delta fix from `evm/src/apps/IntentGatewayV2.sol` (lines ~312-329) into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s non-predispatch branch: snapshot `balanceOf(address(this))` before `safeTransferFrom`, compute `received = balanceOf(address(this)) - balBefore`, mutate `order.inputs[i].amount` to `received`, and only then compute `reducedInputs`/protocol fee/commitment/escrow credit from the actual received amount, consistent with the predispatch branch's dust-accounting approach.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with `protocolFeeBps = 0` for simplicity.
2. Deploy a fee-on-transfer ERC20 (e.g. the `FeeOnTransferToken` mock used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, 1% fee) and mint 10,000 tokens to `user`.
3. `user` approves the gateway for `inputAmount = 1000e18` and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no predispatch.
4. Inside `placeOrder`, `safeTransferFrom(user, gateway, 1000e18)` actually delivers only `990e18` to the gateway (1% fee burned/skimmed), but `_orders[commitment][FOT] += reducedInputs[0].amount == 1000e18` (since `protocolFeeBps == 0`, `reducedInputs == order.inputs`).
5. Now `_orders[commitment][FOT] = 1000e18` while `IERC20(FOT).balanceOf(gateway) == 990e18` — a 10e18 accounting overstatement for this single order, which compounds across all FOT orders and can be exploited via `cancelOrder`/`withdraw` to redeem more than the gateway actually holds, at the expense of other orders' escrowed balance of the same token.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
