Audit Report

## Title
Debug-level logging of full JSON-RPC request (including bearer `Auth` token) in Vault gateway handler leaks credential material to node logs - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire incoming `*jsonrpc.Request[json.RawMessage]` at Debug level via `reqLggr.Debugw("received message from gateway", "req", req)` before any authorization or redaction occurs. Because `jsonrpc.Request` carries the caller's bearer/JWT token in its `Auth` field (used throughout `authorizer.go` and gateway test helpers as the sole proof of authorization), this causes the full credential to be serialized into node logs whenever Debug logging is enabled.

## Finding Description
`HandleGatewayMessage` at [1](#0-0)  builds a request-scoped logger and immediately logs the whole `req` object before it reaches `h.requestProcessor.ProcessRequest`, which is the code path that performs authorization via `Authorizer.AuthorizeRequest`. That authorizer explicitly treats `req.Auth` as the bearer/JWT credential distinguishing allowlist-based auth from JWT-based auth: [2](#0-1) . Gateway/system-test helpers confirm `req.Auth` is the literal bearer token forwarded as `Authorization: Bearer <token>` and must be explicitly stripped before outbound serialization via `outboundRequestWithoutAuth`: [3](#0-2) . No equivalent stripping/redaction happens before the internal `Debugw` call — the handler logs the raw struct as received, including `Auth`. The dedicated test `TestVaultHandler_InvalidParamsDoesNotLogRawParams` deliberately observes logs at Info level specifically "so the pre-existing whole-request Debug log is excluded" from its assertions, confirming the log statement's existence is a known, unaddressed gap rather than something already mitigated: [4](#0-3) .

## Impact Explanation
If Debug-level logging is enabled on the node (a common operational/troubleshooting configuration) and an attacker gains read access to node logs (log aggregation, support bundles, misconfigured shared storage), the leaked bearer/JWT token can be replayed via `Authorization: Bearer <token>` to impersonate the original caller for Vault secret operations (create/update/list/delete), since `req.Auth` is the sole credential checked by the authorization pipeline. This maps to the in-scope "key/secret exfiltration" and "gateway request impersonation" impact categories.

## Likelihood Explanation
Triggering the log write requires no special privilege: any external/unprivileged caller whose request reaches `HandleGatewayMessage` — including normal legitimate Vault gateway traffic — causes their own token to be logged. The precondition for exploitation (Debug logging enabled + log read access) is a realistic operational scenario, not a privileged-admin-only precondition, since debug logging is a commonly used and documented node configuration for troubleshooting.

## Recommendation
Remove or redact the raw `req` object from the `Debugw("received message from gateway", "req", req)` call. Log only non-sensitive correlation fields (`requestID`, `method`, `gatewayID`, similar to `requestLogger`), and explicitly clear/mask `req.Auth` (and raw `Params`, consistent with the redaction already applied on the invalid-params path) before any logging of the request object.

## Proof of Concept
1. Run the Vault `GatewayHandler` with `Log.Level = 'debug'`.
2. Send a Vault JSON-RPC request (e.g., `vault.secrets.create`) with `req.Auth` set to a valid bearer/JWT token, following the pattern in `sendVaultSignedOCRRequestToGateway` (`system-tests/tests/smoke/cre/vault_don_test_helpers.go:547-559`).
3. Observe node logs at Debug level: the `Debugw("received message from gateway", "req", req)` call in `core/capabilities/vault/gw_handler.go:182` serializes the full request, including `Auth`, into the log stream — this can be directly verified with a unit test using `logger.TestObserved(t, zapcore.DebugLevel)` and asserting the `req.Auth` string appears in the captured log entry's fields.
4. An actor with read access to these debug logs extracts the token and replays it as `Authorization: Bearer <token>` against the gateway HTTP endpoint to issue further Vault requests as the original caller.
