### Title
Missing zero/invalid authority validation in `authorize_nonce_account` can permanently lock a nonce account and its lamports - (`programs/system/src/system_instruction.rs`)

### Summary
The Agave System Program's nonce-authorization instruction accepts any arbitrary `Pubkey` as the new nonce authority without any sanity check that the value is a usable/controllable key. This mirrors the reported `Governable.transferGovernor()` bug class: a privileged "owner-style" transfer function that blindly overwrites the current authority with an attacker/user-supplied value, with no protection against setting it to an address that can never sign again (e.g. `Pubkey::default()`), permanently bricking the account.

### Finding Description
`authorize_nonce_account` in `programs/system/src/system_instruction.rs` takes a raw `nonce_authority: &Pubkey` and, after checking the account is writable and the current authority signed, unconditionally calls the nonce state's `authorize()` and persists the new authority with no validation of the new value: [1](#0-0) 

This is invoked from `system_processor.rs`'s instruction dispatch for `SystemInstruction::AuthorizeNonceAccount`, again with no additional validation of the supplied authority pubkey: [2](#0-1) 

Once the nonce authority is set to a value nobody can produce a valid signature for (e.g. the all-zero `Pubkey::default()`, which is also the System Program ID), every subsequent privileged operation on that nonce account—`AdvanceNonceAccount`, further `AuthorizeNonceAccount`, and `WithdrawNonceAccount`—requires the (now unobtainable) authority's signature, since each of those instructions checks the current authority via the same `Versions`/`Data` state that was just overwritten. The account, and any lamports held in it, become permanently inaccessible. The existing unit tests for this instruction (`authorize_inx_ok`, `authorize_inx_bad_authority_fail`) even freely use `Pubkey::default()` as a "valid" authority value with no rejection: [3](#0-2) 

This is directly analogous to the reported Solidity issue: `transferGovernor()` in `Governable.sol` had no zero-address check on `newGovernor`, letting the current governor accidentally brick all `onlyGovernor` functionality. Here, the "governor" role is the nonce authority, and the same missing-validation pattern is present in the durable-nonce path, one of the explicitly in-scope areas (nonce/blockhash replay).

### Impact Explanation
Any nonce account owner who (accidentally, or via a malicious front-end/CLI/dApp tricking them) authorizes their nonce account to an unusable pubkey permanently loses the ability to advance, re-authorize, or withdraw that account. This is concrete, irreversible value loss (locked lamports and loss of the durable-nonce functionality) for the affected account, matching the "concrete value loss" acceptance bar. It is self-contained to the account owner's own funds (no cross-node divergence or protocol halt), which keeps the severity Low—consistent with how the original report was rated.

### Likelihood Explanation
The likelihood of accidental triggering is low but nonzero (e.g., a scripting/typo error passing a default/zero pubkey, or a malicious dApp asking a user to sign an `AuthorizeNonceAccount` transaction with a manipulated "new authority" value that the user doesn't carefully verify, similar to how the original Solidity bug is normally triggered by operator mistake rather than remote attacker exploitation).

### Recommendation
Add a check in `authorize_nonce_account` (`programs/system/src/system_instruction.rs`) rejecting `nonce_authority == Pubkey::default()`, returning `InstructionError::InvalidArgument` (or similar) before calling `Versions::authorize`. Consider also flagging this in `solana_cli` (`cli/src/nonce.rs::process_authorize_nonce_account`) as a client-side warning/guard, mirroring the recommendation to validate the new authority both at the on-chain instruction level and at the calling/initialization boundary.

### Proof of Concept
1. Create and fund a durable nonce account, initializing it with authority `A` via `system_instruction::create_nonce_account`.
2. As authority `A`, submit `system_instruction::authorize_nonce_account(&nonce_pubkey, &A, &Pubkey::default())`.
3. The instruction succeeds (see `authorize_inx_ok` test using `Pubkey::default()` without rejection: [3](#0-2) ), setting `nonce_authority = Pubkey::default()`.
4. Any subsequent `AdvanceNonceAccount`, `AuthorizeNonceAccount`, or `WithdrawNonceAccount` instruction on this nonce account now requires a signature from `Pubkey::default()`, which cannot be produced—the account and its lamports are permanently frozen.

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
