## Analysis

Reducing the Sherlock H-11 bug to its custody invariant: **a single participant's own state (an unprivileged, self-controlled flag/token state) can cause a "distribute to everyone" batch function to revert, permanently freezing custody of funds for *all other* honest parties in the same batch**, because the underlying language/runtime has no try/catch to isolate one recipient's failure from the rest.

I traced this pattern to Aptos-native staking/vesting distribution code, which is asset-custody-relevant (APT reward/vesting payouts) and does not involve governance, leaked keys, or the excluded categories.

### Title
Single opted-out shareholder permanently blocks reward/vesting distribution for all other shareholders in `staking_contract::distribute` and `vesting::distribute` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`, `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`staking_contract::distribute_internal` and `vesting::distribute` push APT rewards/vested coins to every shareholder in a pool inside one atomic transaction via `aptos_account::deposit_coins`. `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has called the fully unprivileged, self-service `set_allow_direct_coin_transfers(false)` and has no registered `CoinStore`/primary store for `AptosCoin`. Because Move has no try/catch, a single such recipient anywhere in the shareholder set makes the *entire* distribution transaction revert, blocking payout to every other shareholder and the operator's commission, indefinitely.

### Finding Description
`staking_contract::distribute_internal` loops while there are shares left in `distribution_pool`, redeeming shares and calling `aptos_account::deposit_coins(recipient, ...)` for each shareholder in the pool: [1](#0-0) 

`vesting::distribute` similarly iterates over all shareholders in `grant_pool` and calls `aptos_account::deposit_coins` for each, inside `shareholders.for_each_ref`: [2](#0-1) 

`aptos_account::deposit_coins` asserts `can_receive_direct_coin_transfers(to)` and aborts if false when the recipient is not registered for the coin type: [3](#0-2) 

`can_receive_direct_coin_transfers` reads `DirectTransferConfig.allow_arbitrary_coin_transfers`, which any account can flip to `false` via the fully permissionless `set_allow_direct_coin_transfers` entry function (self-controlled, no admin/root cause other than the caller's own preference).

Because Move transactions are all-or-nothing, if *any single* shareholder in the pool has opted out of direct coin transfers (and has no registered store for AptosCoin), the abort inside `deposit_coins` unwinds the entire `distribute`/`distribute_internal` call — including the `stake::withdraw_with_cap` that already pulled funds out of the stake pool. This is the direct Aptos analog of the Solidity bug: an unprivileged, self-controlled action by one party (opting out of receiving coins ≈ burning the NFT) causes a revert deep in a shared custody-critical function (`deposit_coins` ≈ `ownerOf`) that blocks a state transition (`distribute`/`vest` completion ≈ `lockCapital`) intended to benefit *other* parties, not just the actor who caused the revert.

### Impact Explanation
Once one shareholder in a `staking_contract`/`vesting::VestingContract` pool opts out of direct coin transfers without a registered store:
- `staking_contract::distribute` can never succeed again for that operator's pool — all other stakers and the operator/beneficiary permanently lose access to their already-unlocked/withdrawn stake rewards, since the funds were pulled from the stake pool inside the same reverted transaction (no partial distribution is possible).
- `vesting::distribute` (and therefore `vest()`'s eventual reliance on distribution, plus `terminate_vesting_contract`, which calls `distribute` first) is similarly bricked for the whole vesting contract, freezing the entire vesting grant for all shareholders, not just the one who opted out.

This is a permanent, non-recoverable loss/lock of resource-account-held APT for uninvolved third parties, caused solely by one unprivileged party's own action — matching the "Permanent lock or non-recoverable loss of ... resource-account-held value" custody impact category.

### Likelihood Explanation
Likelihood is high: `set_allow_direct_coin_transfers(false)` is a standard, permissionless, well-documented user action (also the default account state can arrive at "not registered + not accepting transfers" without ever calling `register`). Any shareholder — including a griefing shareholder who has little of value themselves — can trigger this to hold the entire pool hostage, and no admin/owner code path exists to skip or force past a blocked recipient in either `distribute_internal` or `distribute`.

### Recommendation
Do not let a single recipient's inability to accept a push-deposit block payouts to everyone else. Options:
- Wrap the per-recipient deposit attempt so failure is isolated (e.g., use `coin::is_account_registered` / a safe check before calling `deposit_coins`, and if the recipient cannot accept a direct transfer, credit their amount to a per-shareholder claimable balance in the `StakingContract`/`VestingContract` resource that they can withdraw later, instead of forcing a push transfer).
- Alternatively, process each shareholder's payout in its own isolated call/resource update so that one recipient's opted-out status cannot make the whole batch revert.

### Proof of Concept
1. Admin creates a `vesting::VestingContract` (or `staking_contract`) with shareholders `[A, B, C]`.
2. Shareholder `B` calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account and never registers a `CoinStore`/primary store for `AptosCoin`.
3. Stake pool accrues rewards; `vesting::distribute(contract_address)` (or `staking_contract::distribute(staker, operator)`) is called.
4. The function withdraws unlocked stake, then iterates shareholders `A, B, C`, calling `aptos_account::deposit_coins(B, ...)`.
5. `deposit_coins` hits `assert!(can_receive_direct_coin_transfers(B), ...)` → aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The whole transaction reverts; `A` and `C` receive nothing, and every subsequent call to `distribute`/`vest`/`terminate_vesting_contract` on this contract fails identically as long as `B` remains opted out — permanently freezing rewards/vested APT for `A` and `C`.

Note: I was not able to fully verify from the indexed snippets whether `pool_u64`'s `shareholders()` ordering or removal semantics allow any workaround (e.g., an admin function to remove/skip a shareholder) inside `staking_contract.move`/`vesting.move`; a full review of `pool_u64.move` and the complete `vesting.move`/`staking_contract.move` files (beyond the indexed excerpts) would be needed to confirm there is no existing mitigation such as a per-shareholder retry or admin bypass. I'd recommend starting a full Devin session with repository access to confirm this and implement the fix.
