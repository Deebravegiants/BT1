### Title
Fee-on-Transfer Underlying Token Breaks 1:1 Backing in WrappedHyperFungibleToken `send` - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`WrappedHyperFungibleTokenUpgradeable.send()` (and its non-upgradeable twin `WrappedHyperFungibleToken.sol`) locks the underlying ERC20 via `safeTransferFrom` and then dispatches a cross-chain message encoding the user-requested `params.amount`, without verifying that the contract actually received that full amount. If `_underlying` is a fee-on-transfer token, the contract receives less than `params.amount`, yet the destination chain's peer contract will unlock/deliver the full `params.amount` of its own locked underlying reserve upon `onAccept`.

### Finding Description
In `send()`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
bytes memory body = abi.encode(HyperFungibleTokenUpgradeable.Message({..., amount: params.amount, ...}));
``` [1](#0-0) [2](#0-1) 

Unlike `IntentGatewayV2.sol`, which correctly measures fee-on-transfer discrepancies by snapshotting `balanceOf` before/after every `safeTransferFrom` and mutating `order.inputs[i].amount` to the actual received amount before computing the commitment [3](#0-2) , `send()` never re-measures the locked balance and instead trusts the caller-supplied `params.amount` verbatim when building the cross-chain `Message`.

On the destination chain, `onAccept()` unconditionally transfers out the encoded `message.amount` from its own underlying reserve:
```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
``` [4](#0-3) 

If the underlying token deducts a transfer fee, the source contract locks strictly less than `message.amount`, but the destination contract pays out the full `message.amount` from its reserve pool. The same unconditional-amount pattern also applies to the timeout refund path, `onPostRequestTimeout()` [5](#0-4) , and is duplicated in the non-upgradeable `WrappedHyperFungibleToken.sol` contract.

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying creates a permanent deficit between what is actually locked on the source chain and what is promised/paid out on the destination chain. Any unprivileged user can dispatch such a message directly by calling `send()` once the token pair is configured with a fee-on-transfer underlying, progressively draining the destination-side reserve pool relative to what was actually escrowed — an unbacked-mint/permanent-fund-drain condition for that bridged asset, reachable from a single submitted transaction with no privileged role required.

### Likelihood Explanation
Requires the deployment/governance to configure a fee-on-transfer ERC20 as `_underlying` for a given `WrappedHyperFungibleToken(Upgradeable)` pair. This is plausible since the contract explicitly documents wrapping "existing ERC20 tokens," and nothing in `configure()` restricts underlying token type. Once such a token is configured, exploitation requires no special privileges — just calling `send()` — so likelihood is contingent but the trigger itself is trivial and repeatable.

### Recommendation
In `send()`, measure the contract's actual token balance before and after `safeTransferFrom`, and use the delta (actual received amount) both for the escrow accounting and for the `amount` field encoded into the dispatched `Message`, mirroring the pattern already used in `IntentGatewayV2.sol` (`order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;`). Apply the same fix to `WrappedHyperFungibleToken.sol`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleTokenUpgradeable` with `_underlying` set to a fee-on-transfer ERC20 (e.g., 1% fee) on both source and destination chains, each holding its own locked reserve of that token.
2. User calls `send({amount: 1000e18, to: recipient, dest: chainB, ...})`. `safeTransferFrom` moves only 990e18 into the contract (1% fee burned/redirected), but `body` encodes `amount: 1000e18`.
3. Message is delivered and `onAccept` is invoked on chain B's peer contract, which calls `safeTransfer(beneficiary, 1000e18)` — paying out 1000e18 from chain B's reserve while only 990e18 was ever locked on chain A.
4. Repeating this bleeds 10e18 (1%) out of the shared backing per round-trip, eventually draining reserves and leaving legitimate later transfers unable to be honored (`safeTransfer` reverts on insufficient balance) — a fund-freezing/fund-loss condition for the bridge's underlying pool.

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(incoming.request.body, (HyperFungibleTokenUpgradeable.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
