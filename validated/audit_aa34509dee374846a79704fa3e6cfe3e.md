## Title
Webhook Shop/Topic Identity Not Bound to HMAC, Enabling Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` therefore only proves that *some* valid body was signed with the app's secret — it proves nothing about which shop or topic that body belongs to. Because a single app's `api_secret_key` is shared across every shop that installs it, an attacker who controls one (even unprivileged) installation of the app can capture one of their own legitimate webhook deliveries and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or topic) header, causing the app to process the event under a different shop's identity.

### Finding Description
The equality the gem should enforce is:
`shop_that_produced_and_signed(body) == shop_attributed_to_the_processed_event`

Instead, the gem enforces only:
`HMAC(body, api_secret_key) == received_hmac`

`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC, then trusts the unauthenticated header-derived fields to build the metadata handed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain struct field with no further validation: [4](#0-3) 

`HmacValidator.validate` performs a straightforward HMAC comparison against `verifiable_query.to_signable_string`, which for webhooks is only the raw body: [5](#0-4) 

The gem's own documentation instructs apps to treat `data.shop` as the authoritative shop identity for downstream processing (e.g., looking up the shop's session, enqueuing per-shop background jobs): [6](#0-5) 

### Impact Explanation
All shops that install a given app share the same `api_secret_key`. An attacker who installs the app on their own (low-privilege) store can legitimately receive a webhook (body + valid `hmac-sha256`) addressed to their own shop, then resend that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary value in `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`). Because none of those headers are covered by the signature, the request still passes `HmacValidator.validate`, and the app's handler receives a `WebhookMetadata` claiming the event belongs to a shop the attacker does not control. If the host app follows the gem's documented pattern of keying storage/session lookups or background jobs off `data.shop`, this results in cross-tenant data confusion — attacker-supplied payload data gets attributed to, and can overwrite state for, a victim shop. This satisfies the "cross-tenant access" High/Critical impact category, since a tenant boundary (shop identity) is crossed using only a credential (`api_secret_key`) that is shared across tenants and not shop-specific.

### Likelihood Explanation
Likelihood is high for any developer/attacker who can install the target app on even one shop (a normal, unprivileged flow for public apps) and observe one webhook delivery. No access token, `client_secret`, or privileged account is required — only the ability to capture one legitimate webhook body+HMAC pair addressed to their own store, which is inherent to normal app usage.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-signable material, or otherwise cryptographically verify that the `shop-domain` header matches the shop the webhook subscription was registered for (e.g., cross-check against the webhook subscription's known shop via a lookup keyed on `webhook_id`, or require the host app to pass the expected shop as part of validation). At minimum, document prominently that `data.shop`/`data.topic` are unauthenticated header values not covered by the HMAC and must not be trusted as the sole tenant-identity signal.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — this is a valid `(body, hmac)` pair signed with the app's shared `api_secret_key`.
2. Resend the identical raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) validates successfully because it only checks the raw body.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the app's handler, which — per the gem's documented usage — processes/stores data as belonging to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
