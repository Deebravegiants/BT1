Confirmed the finding is grounded in code. The `Registry.process` and `Request` classes bind the HMAC only to the raw body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — including the tenant-identifying `shop-domain` header — are trusted unauthenticated and handed to the app's handler as if verified.

### Title
Webhook `shop`/`topic` Headers Trusted Without HMAC Binding Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body-only string before dispatching `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all taken verbatim from unauthenticated HTTP headers — to the app's registered handler as trusted `WebhookMetadata`. The equality the gem implicitly promises but does not enforce is: `hmac_secret_signs(shop, topic, body) == received_hmac`. In reality it only enforces `hmac_secret_signs(body) == received_hmac`, so `shop` and `topic` are never bound to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC using that signable string and, once it passes, unconditionally trusts the header-derived `shop` and `topic` values to select the handler and populate `WebhookMetadata`: [2](#0-1) 

`Request#shop` and `Request#topic` are read straight from the `shopify-shop-domain` / `shopify-topic` headers with no cross-check against the signed content and no validation via `Utils::ShopValidator`: [3](#0-2) 

Because the app's `client_secret` (the webhook HMAC key) is shared across every shop that installs the app — it is not shop-specific — any merchant who installs the app on their own store legitimately receives real Shopify webhooks with a valid HMAC computed only over the JSON body. Since headers are excluded from the signed content, that same `(raw_body, hmac)` pair remains valid regardless of which `shopify-shop-domain` or `shopify-topic` header accompanies it. An attacker who controls the delivery of the HTTP request to the app's webhook endpoint (e.g., replaying/relaying their own legitimately-signed webhook payload with a substituted `shop-domain` header naming a different, victim shop that also installed the app) will pass `Utils::HmacValidator.validate` and have the forged `shop` value delivered to the handler as if Shopify itself vouched for it. The gem's own documentation instructs apps to treat `data.shop` from `WebhookMetadata` as the authenticated shop identity, e.g. keying background jobs by `shop_domain: data.shop`: [4](#0-3) 

This breaks the identity binding `shop_that_signed_body == shop_attributed_to_the_data`, letting a malicious, low-privilege actor (a legitimate install of the app on their own low-value shop) inject data attributed to a different tenant.

### Impact Explanation
This is a cross-tenant confusion vulnerability reachable by any unprivileged user who can install the shared app on a shop of their own and control/replay the HTTP delivery to the app's webhook route. It lets that user cause the app to process attacker-controlled body content under an arbitrary other shop's identity, since the gem exposes `shop`/`topic` as pre-verified fields in `WebhookMetadata` without binding them cryptographically. Depending on how the host app uses `data.shop` (e.g., as a lookup/write key for orders, customers, or session data), this can enable cross-tenant data corruption or unauthorized actions performed under another merchant's identity — meeting the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Likelihood is limited by the requirement that the attacker be able to control or intercept the delivery path to the app's public webhook endpoint (e.g., a party sitting between Shopify and the app, or one capable of directly POSTing to the app's known webhook route with a captured/self-generated valid body+HMAC pair from their own shop). Any legitimate merchant who installs the app can obtain a valid `(body, hmac)` pair for their own shop trivially, and since the webhook route is a normal, discoverable public HTTP endpoint (not gated by any additional secret in the request), the practical difficulty is solely in submitting the forged header, not in obtaining a valid signature.

### Recommendation
Bind `shop` and `topic` (and any other header value that is trusted downstream) into the HMAC-signed content instead of relying on body-only signing, and use `Utils::ShopValidator.sanitize!` on `request.shop` before it is used or handed to handlers. Alternatively, require the host app to independently confirm that `data.shop` matches a shop known to have registered that specific webhook subscription (e.g., via a per-shop webhook secret or a registered-webhook-id lookup) before trusting it as an authenticated tenant identifier.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key  # shared client_secret, same for all shops
body = '{"id":1,"note":"hello"}'
hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body))

# Attacker legitimately obtains this valid (body, hmac) pair from a webhook
# delivered to their OWN shop ("attacker-shop.myshopify.com").

# They then replay the exact same body + hmac to the app's webhook endpoint,
# but swap the shop-domain header to a victim shop that also installed the app:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not bound to the HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation succeeds because to_signable_string only covers `body`.
# The app's handler receives WebhookMetadata with shop == "victim-shop.myshopify.com",
# even though that shop never sent this webhook.
```
