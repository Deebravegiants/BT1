Based on my investigation, this is confirmed as a genuine analog to the bug-class hint. The `ShopifyAPI::Webhooks::Request` HMAC only covers the raw body, while the `shop` field—used by the gem's own `Registry.process` to construct `WebhookMetadata` handed to app handlers as the tenant identifier—is read from an unauthenticated header and never included in the signed payload.

### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate(request)` verifies solely the HTTP body against the app's shared `api_secret_key`. However, `Request#shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of the signed content at all. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`) trusts this unauthenticated header value and forwards it as the tenant identifier (`WebhookMetadata#shop`) to the app's registered handler.

### Finding Description
The intended binding should be: `shop == the tenant that the HMAC-signed body actually originated from`. Instead, the gem enforces only `hmac == HMAC(secret, raw_body)`, with `shop` entirely excluded from the signable string: [1](#0-0) [2](#0-1) 

Since `api_secret_key` is a single shared secret across all shops using the app (not shop-specific), any party who can obtain one valid `(raw_body, hmac)` pair for the app — for example by installing the app on their own shop and triggering a webhook, which they fully control as an "unprivileged internet user" relative to other merchants — can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it only checks the body: [3](#0-2) 

`Registry.process` then builds `WebhookMetadata` directly from this unverified `request.shop` and dispatches it to the app's handler as the authoritative tenant identifier: [4](#0-3) [5](#0-4) 

The documented handler contract explicitly instructs apps to key their business logic off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing that this field is meant to be a trustworthy tenant identity, per the gem's own documentation: [6](#0-5) 

This breaks the identity binding `shop authenticated == shop that produced the signed bytes`, matching the bug-class pattern of "a field acted on but not covered by the HMAC."

### Impact Explanation
This enables cross-tenant confusion: an attacker who legitimately controls their own shop's webhook stream can forge a webhook event that the receiving app attributes to a victim shop of their choosing, because `shop` is never bound by the signature. Depending on how the host app uses `data.shop` (e.g., as a lookup/foreign key for merchant-scoped data, triggering redaction, updating per-shop state, or invoking privileged per-shop workflows), this can lead to cross-tenant data corruption or unauthorized actions being attributed to/affecting another merchant's tenant — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is High: the attacker only needs to be a legitimate (if unprivileged relative to other merchants) app installer on their own shop to generate a valid `(body, hmac)` pair, then send a raw HTTP POST with a modified shop-domain header to the app's public webhook endpoint. No secrets, tokens, or privileged access to the victim are required — only the ability to send arbitrary HTTP requests, which matches the "unprivileged internet user" threat model.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable content, or independently verify that the shop domain in the header matches an expected/registered shop for the given webhook subscription before trusting it. At minimum, `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the shop-domain header value so that `HmacValidator.validate` fails if it's tampered with.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `api_secret_key`.
2. Replay that exact `raw_body` and `x-shopify-hmac-sha256` value in a new POST request to the same app's webhook endpoint, but set the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret [7](#0-6) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [8](#0-7)  and processes the attacker-controlled body as though it belongs to the victim shop, exactly as the documented handler pattern expects [9](#0-8) .
