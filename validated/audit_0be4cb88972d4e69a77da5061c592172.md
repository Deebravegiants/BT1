### Title
Webhook `shop` domain is not covered by HMAC signature, enabling cross-tenant webhook data injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an unauthenticated HTTP header, while the HMAC signature verified by `Utils::HmacValidator` covers only the raw request body. This breaks the intended binding `HMAC-verified bytes == data trusted as authentic`, because the `shop` field is trusted without being part of what the HMAC actually verifies.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, unconditionally trusts `request.shop` when building the data handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and secret-compares it to the decoded `hmac` header — it never factors in `shop`, `topic`, or `webhook_id`: [4](#0-3) [5](#0-4) 

The `shop` value is then propagated into `WebhookMetadata`, which is the gem's documented mechanism for identifying which merchant/tenant a webhook belongs to; the gem's own docs show apps using `data.shop` directly as the tenant key when enqueuing downstream work: [6](#0-5) [7](#0-6) 

Because the header is outside the signed payload, the equality the library implicitly promises — `shop that data.shop reports == shop whose secret actually produced the HMAC` — does not hold. Anyone who can produce one *genuinely* HMAC-signed webhook body (trivially available to any developer who installs the app on their own store and receives real Shopify webhooks) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` string to the handler as if Shopify had authenticated it.

### Impact Explanation
This is a cross-tenant boundary violation: the gem lets an attacker who legitimately controls one shop forge which shop a webhook payload is attributed to, from the perspective of any app built on this gem's documented webhook API. If the host app follows the gem's documented pattern of using `data.shop` to route/attribute webhook data to a merchant record (exactly as shown in the gem's own `docs/usage/webhooks.md` example), an attacker can inject data that appears to originate from a victim shop, without ever needing that shop's credentials. This qualifies as cross-tenant access under the specified Critical impact category.

### Likelihood Explanation
Likelihood is realistic for any developer/attacker who can install the target app (or any app using this gem) on a shop they control: they receive a real webhook with a valid HMAC for arbitrary body content they can influence (e.g., via `orders/create`, product updates, etc.), then replay that raw body/HMAC pair against the victim app's webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged access is required — only the ability to receive one legitimately signed webhook, which any store owner can do.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed payload verification, or otherwise cryptographically tie the header-derived `shop` to the signature — e.g., require the HMAC to be recomputed over `shop + raw_body` (matching what Shopify actually signs) instead of `raw_body` alone, or reject the header value if it doesn't match a shop the app expects for pending webhook subscriptions. At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated and must not be used as a tenant key without additional verification (e.g., cross-checking against the app's known shop-session store).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`) with attacker-controlled body content.
2. Shopify sends a legitimately signed webhook: headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, plus the raw JSON body.
3. Attacker captures this raw body and HMAC header, then POSTs to the victim app's webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged but setting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`raw_body` only) and matches the supplied header — validation passes: [8](#0-7) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, and any downstream logic keyed on `data.shop` now attributes attacker-controlled data to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
