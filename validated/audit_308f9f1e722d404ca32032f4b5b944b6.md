### Title
`liquidate` accepts a repayment whose entire seizure rounds to zero — the call succeeds, burns the borrower's debt, pulls the liquidator's tokens, and delivers no collateral — (`contracts/controller/src/positions/liquidation/plan.rs`, `contracts/controller/src/positions/liquidation/math.rs`)

### Summary
Analogous to the reported `computeVote` issue (an operation that cannot fulfill its purpose silently succeeds and emits an event indistinguishable from a real success), `Controller::liquidate` does not fail when the pro-rata seizure plan resolves to zero collateral legs. `build_liquidation_plan` only releases the repayment when `unbacked_usd > 0`, but `unbacked_usd` is accumulated solely inside the sub-`MIN_BORROWABLE_ASSET_DECIMALS` whole-unit floor branch (`math.rs:401-416`). For ordinary assets (≥3 decimals), a leg whose seizure floors to zero shares (`seized_scaled <= Ray::ZERO`, `math.rs:456`) or zero token units (`capped_amount <= 0`, `math.rs:465`) is silently `continue`d with no unbacked-USD accounting. If every collateral leg drops this way, `seized` is empty while `repayment.repaid` is untouched, so `require_non_empty_payments(env, &result.repaid)` (`mod.rs:66`) still passes, `apply_liquidation_repayments` pulls the liquidator's debt tokens and burns the borrower's debt, `apply_liquidation_seizures` iterates an empty vector, and a `LiquidationEvent` with a nonzero `repaid_usd_wad` is published — outwardly identical to a successful seizure.

### Impact Explanation
A single unprivileged liquidator calling `liquidate(liquidator, account_id, debt_payments, SeizeMode::Transfer)` loses the full pulled repayment and receives nothing. The borrower gains a free, third-party-funded debt repayment while keeping all collateral. Because `seized` emptiness is not checked anywhere in `mod.rs` (only `repaid` non-emptiness is enforced), and the event stream shows a normal liquidation with nonzero `repaid_usd_wad`, the failure is silent and repeatable. This is theft of user funds (the liquidator's tokens) caused by a failure path that succeeds instead of reverting.

### Likelihood Explanation
Reachable whenever the offered repayment is small relative to collateral granularity: each pro-rata leg's `capped_ray.div_floor(supply_index)` yields zero shares once the leg's seized RAY value is below the supply index, and `capped_ray.to_asset_floor` yields zero units once it is below one base unit. A tiny offer — e.g., one base unit of a cheap debt token against an account with several collateral positions — drops every leg while `unbacked_usd` stays zero because no leg enters the sub-3-decimal accounting branch. The protocol's own operator documentation confirms the contract accepts this state: "The contract accepts a liquidation that repays debt and seizes nothing, so the liquidator would pay and receive no collateral" (`skills/xoxno-lending-liquidations/SKILL.md`). A borrower can also deliberately shape an account (many small collateral positions, dust debt) to maximize the chance that bots offering small repayments hit the all-dropped case, harvesting free repayments. Likelihood is bounded by liquidators submitting only what they offer, keeping this Medium rather than High.

### Recommendation
In `build_liquidation_plan`, after `calculate_seized_collateral`, revert with `CollateralError::InvalidPayments` (or release the entire repayment into `refunds`, which makes `require_non_empty_payments(&result.repaid)` fail downstream) whenever `seized_collaterals.is_empty()` — not only when `unbacked_usd > 0`. Alternatively, accumulate the USD value of every dropped leg into `unseized_usd` in `calculate_seized_collateral` so the existing release path covers zero-share/zero-unit drops for all decimals. This makes the operation fail loudly instead of emitting a success-shaped `LiquidationEvent` for a no-seizure settlement.

### Proof of Concept
1. Borrower opens account, supplies `N` collateral positions in standard ≥7-decimal assets (e.g., USDC, XLM), borrows a cheap high-decimal debt token, and lets HF fall below 1.
2. Attacker/keeper calls `liquidate` with `debt_payments = [(hub_asset(debt_token), 1)]` — a one-base-unit offer worth far less than one base unit of each collateral asset.
3. `calculate_seized_collateral` computes each leg's `seizure_ray < supply_index` and/or `capped_ray < one base unit`; `seized_scaled`/`capped_amount` floor to zero; every leg hits `continue` at `math.rs:456` or `math.rs:465`. No leg adds to `unseized_usd` because that accumulation only runs under `feed.asset_decimals < MIN_BORROWABLE_ASSET_DECIMALS` (`math.rs:401`).
4. Back in `plan.rs:76`, `unbacked_usd == 0`, so the release-all guard is skipped; `repayment.repaid` stays non-empty; `plan.validate` passes.
5. `mod.rs:68-94`: `apply_liquidation_repayments` transfers the liquidator's token to the pool and burns the borrower's debt share; `apply_liquidation_seizures` iterates an empty `seized` vector and transfers nothing.
6. `LiquidationEvent` publishes `repaid_usd_wad > 0`, `bonus_bps > 0` — indistinguishable from a profitable liquidation. Net effect: liquidator −1 base unit of debt token, borrower's debt reduced, collateral untouched.

Uncertainty: I did not read the body of `LiquidationPlan::validate` or `apply_liquidation_repayments` directly in this pass; the conclusion relies on the guard structure in `plan.rs:76`, the `continue` sites in `math.rs:419-467`, the absence of any seized-emptiness check in `mod.rs:66-94`, and the explicit confirmation in `skills/xoxno-lending-liquidations/SKILL.md` that the contract accepts a nothing-seized liquidation.
