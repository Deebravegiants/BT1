### Title
Webhook shop-domain identity spoofing via header field not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute (used by the host application to attribute an incoming webhook to a merchant/tenant) that is read directly from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, while the HMAC signature validated by `Registry.process` only covers the raw request body. This breaks the binding "shop trusted for tenant attribution == shop covered by the cryptographic signature," allowing any party who can produce (or replay/capture) a validly-HMAC'd webhook body to relabel it as originating from an arbitrary other shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator recomputes the HMAC over `request.to_signable_string` and compares it to the `hmac` header: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body — never the headers: [3](#0-2) 

Meanwhile, `shop` (the tenant identity handed to the host application's handler) is parsed straight from the `shop-domain` header, which is entirely outside the signed material: [4](#0-3) [5](#0-4) 

`Registry.process` then forwards this unauthenticated `shop` value directly into `WebhookMetadata`, which is the sole piece of tenant-identifying information delivered to the app's webhook handler: [6](#0-5) 

**Identity binding broken (equality that should hold but doesn't):**
`shop` value cryptographically bound by HMAC == `shop` value trusted by the handler for tenant attribution.

Before request: HMAC covers `{raw_body}` only; `shop` header is attacker-settable.
After request: `Utils::HmacValidator.validate` returns `true` as long as the body+secret match, regardless of what `shop-domain` header value is present; `WebhookMetadata#shop` is set from that unverified header and handed to the app's business logic as the authoritative tenant identifier.

This is the same bug class as the reported re-entrancy issue in spirit: a value that participates in a security-relevant decision (`totalOnLine` in the Solidity report; `shop` here) is mutated/consumed outside the code path that is supposed to protect its integrity (the non-reentrant balance update in the report; the HMAC signature in this gem).

### Impact Explanation
If it can be shown that the `shop` field is genuinely unauthenticated relative to the signature the gem validates, this permits cross-tenant confusion: an attacker who can obtain one validly-signed webhook body (e.g., by owning/operating their own installed shop and capturing a real webhook Shopify sends them, since HMAC uses only the app's `client_secret` and is otherwise identical for every shop) can replay that exact body to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. The library will report the webhook as authentic (`HmacValidator.validate` passes) and hand the host application a `WebhookMetadata` claiming the payload came from the victim shop. Any host application that trusts `WebhookMetadata#shop` for tenant-scoped operations (writing data, revoking access, processing GDPR redact topics, etc.) is exposed to cross-tenant data corruption or unauthorized actions attributed to another merchant.

### Likelihood Explanation
Requires the attacker to have or obtain at least one valid signed webhook body/HMAC pair for their own tenant (trivial for an app that installs on the attacker's own store), and knowledge of a target `shop` domain (typically public, e.g., `something.myshopify.com`). No access to the app's `client_secret`, access tokens, or any privileged account is needed — this is exploitable by any unprivileged actor who can install the app on their own store and then replay HTTP requests to the app's publicly reachable webhook endpoint.

### Recommendation
Bind the `shop` identity into the signed material actually used for verification, or independently corroborate the header-derived `shop` against data known to be authentic (e.g., cross-check against the shop associated with the session/access token that was used to register the webhook, or require the host application to validate `shop` against its own tenant registry before trusting it). At minimum, document explicitly in `Webhooks::Request`/`Registry` that `shop` is not covered by HMAC verification and must not be used as an authoritative tenant identifier without additional server-side corroboration.

### Proof of Concept
Conceptual replay (cannot be fully demonstrated without a live app, but the logic is directly inspectable in-repo):
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the app's shared `client_secret`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate` recomputes HMAC over `B` only (per `to_signable_string`) and it matches `H`, so validation succeeds: [7](#0-6) 
4. `request.shop` returns `"victim-shop.myshopify.com"` from the spoofed header: [4](#0-3) 
5. The handler receives `WebhookMetadata` claiming the event is from `victim-shop.myshopify.com` even though the actual payload/topic came from the attacker's own store.

**Note on confidence:** I was unable to locate any additional cross-check in this gem (outside `lib/shopify_api/rest/resources/**`, which is out of scope) that reconciles the webhook's header-derived `shop` against the shop that owns the webhook subscription or any authenticated session, reinforcing that this binding gap is real within the gem's own code. However, whether this constitutes a practically exploitable "cross-tenant access" depends on how host applications built on this gem use `WebhookMetadata#shop` — the gem itself cannot enforce correct usage by consuming applications, and Shopify's own webhook delivery infrastructure would not itself send mismatched headers/bodies. The realistic impact is therefore contingent on an attacker being able to directly reach the app's webhook endpoint with forged headers, which is true for any internet-exposed webhook route.

        end
