## Analysis

The claim conflates two facts that don't combine into an exploitable custody bug:

1. `RecoveryId::parse` in `native_ecdsa_recover` does accept values 0, 1, 2, 3 as documented, and the Move wrapper `ecdsa_recover` explicitly allows all four values. [1](#0-0) [2](#0-1) 

2. However, `ecdsa_recover` is a generic primitive whose own doc comment explicitly warns callers that the recovered public key is only meaningful "if `pk` is the 'right' one," and that callers must independently verify the recovered key/address against a known expected identity. [3](#0-2) 

The only production custody-relevant caller of `ecdsa_recover` in this codebase is `ethereum_derivable_account.move`, used for domain account abstraction authentication. There, two things close the path:

- `recover_public_key` only accepts `v == 27` or `v == 28` (i.e., `recovery_id` 0 or 1), so recovery IDs 2/3 are never reachable through this entrypoint. [4](#0-3) 
- After recovery, the code independently re-derives the Ethereum address from the recovered key and asserts it matches the account's already-known `ethereum_address` before treating the signer as authenticated. Any recovered key (canonical or otherwise) that doesn't hash to the exact expected address is rejected. [5](#0-4) 

Even hypothetically, for the "alternate" recovered key from a different recovery_id to "collide" with a legitimate token owner's authentication key, an attacker would need to find a signature/message pair where the *incorrect* recovery id happens to recover a public key whose derived address exactly matches a specific target victim's address — this is a second-preimage/collision problem on keccak256 over a 160-bit space, not a logic flaw in the native or the framework's usage of it. No custody code path in this repo trusts a recovered key without such an independent match-check against a pre-existing owner identity, so the authority checks (recommendation #4 of the review path) already close this path.
