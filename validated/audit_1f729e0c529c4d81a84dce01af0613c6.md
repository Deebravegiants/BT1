Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook HMAC only against the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) fields used by `Registry.process` to attribute and route the webhook are taken from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)` and then builds `WebhookMetadata` from the request, passing `shop: request.shop` to the app-supplied `handler.handle` [1](#0-0) . But `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `shop`, `topic`, `api_version`, `webhook_id` are all read straight from HTTP headers (`shopify-shop-domain`, etc.) with no cryptographic binding to those headers [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac-sha256` header value [4](#0-3) .

The identity binding that should hold is: `shop header used to attribute a webhook == shop bound inside the HMAC-signed payload`. In this code that equality does not hold — the HMAC only authenticates *bytes of the body*, not *which shop the body is attributed to*. Any request whose body+signature pair is a valid Shopify webhook for shop A will pass `HmacValidator.validate` regardless of what `shopify-shop-domain` header is attached, because that header is outside the signed string.

### Impact Explanation
An attacker who owns/operates their own (unprivileged) Shopify store can install the target app on their own shop and legitimately receive real, correctly-signed webhook deliveries (e.g. `customers/data_request`, `customers/redact`, `orders/create`, etc.) for that shop. Because the signature covers only the body, the attacker can resend the exact same body+HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) with a different value. `HmacValidator.validate` still returns `true` since the body bytes and HMAC are unchanged, and `Registry.process` will construct `WebhookMetadata` claiming the (attacker-chosen) `shop` value, then invoke the app's handler as if the event genuinely originated from that other shop. Depending on how the host app's `WebhookHandler#handle` implementation trusts `data.shop` (e.g., to look up per-tenant sessions, write to per-tenant storage, or run GDPR redaction/data-request flows keyed by shop), this can lead to cross-tenant data/action confusion — the impact category is cross-tenant access, since events for one tenant can be attributed to another tenant purely by resending a header the app never verified.

### Likelihood Explanation
This requires no privileged secret: the attacker only needs to be a normal merchant capable of installing the app on their own store to obtain a validly-signed webhook body/HMAC pair, then can freely rewrite the routing headers when replaying it to the app's public webhook endpoint. No `api_secret_key`, access token, or TLS interception is required. The main precondition is that the host application actually trusts `WebhookMetadata#shop` for tenant-sensitive logic (which is the documented/intended purpose of this field), making this a realistic misuse path rather than a purely theoretical one.

### Recommendation
Include the routing/identity fields (`shop`, `topic`, `webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., verify them against a signed manifest, or require the host app to independently confirm `shop` against a known/installed-shop list before trusting `WebhookMetadata#shop`). At minimum, document clearly that `Request#shop`/`#topic`/`#webhook_id` are NOT covered by `HmacValidator.validate` and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `customers/data_request`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value sent by Shopify.
2. Attacker POSTs the identical raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a shop they do not own).
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)` [5](#0-4) , which calls `Utils::HmacValidator.validate(request)` — this passes because it only hashes `@raw_body` [2](#0-1) [6](#0-5) .
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the app's `handler.handle`, even though the request never touched Shopify's systems for that shop [7](#0-6) [8](#0-7) .
