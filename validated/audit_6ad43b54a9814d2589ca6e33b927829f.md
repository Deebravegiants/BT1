### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook forgery via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw JSON body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `api_version`, and `webhook_id` values consumed by the app are read directly from HTTP headers that are never included in the signed payload.

### Finding Description
`Registry.process` treats a webhook as authentic solely by checking `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` (the raw body only) and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header value [3](#0-2) . However `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` are all read from separate, unsigned headers [2](#0-1) . Because the HMAC only binds the body bytes, these header fields can be swapped without invalidating the signature: `shop` acted-on (used for tenant identification in `WebhookMetadata.shop`) ≠ `shop` covered-by-HMAC (not present in the signed string at all). Any party capable of obtaining one valid `(body, hmac)` pair for a topic they legitimately receive (e.g., a shop where they install the app themselves) can replay that exact body+HMAC pair while substituting a different `shop-domain` header value, and the gem will accept it as valid and hand it to the host app's handler as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the webhook subsystem is supposed to provide: an app relying on `WebhookMetadata#shop` (as documented and used in `Registry.process`) to scope data writes/deletes per tenant can be tricked into applying a replayed payload under an attacker-chosen shop domain, since the header is never covered by HMAC. This falls under cross-tenant access impact — a malicious app installer can inject events attributed to another tenant's shop without ever needing that shop's or the app's own `client_secret`.

### Likelihood Explanation
The attacker does need at least one legitimately-signed webhook body from Shopify (e.g., from their own shop where the app is installed), but no leaked secrets, tokens, or privileged access. The webhook receiving endpoint is public-facing by design, and header manipulation is trivial once a valid `(body, hmac)` sample is captured. Exploitability depends on whether the specific host application's webhook handler actually branches logic based on `data.shop` (which is the documented purpose of the field per `WebhookMetadata.new(topic:, shop:, ...)` in `Registry.process`) [4](#0-3) .

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signed string that `to_signable_string` returns, or otherwise cryptographically bind them to the body before HMAC validation, so that any tampering with these headers invalidates the signature — matching how Shopify's own webhook signing is documented to work (HMAC over raw body) but requiring the gem to additionally assert header/body consistency where the app relies on header-derived identity fields.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `{"...":"..."}`, header `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends this exact HTTP POST to the app's webhook endpoint, keeping body and `x-shopify-hmac-sha256` unchanged but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [5](#0-4) ; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the unchanged body against the unchanged HMAC [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., the app processes attacker-controlled data as if it belongs to the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
