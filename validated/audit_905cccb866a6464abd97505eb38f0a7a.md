### Title
`HinkalHelper.dimensionsCheck` never enforces `tokenNumber > 0`, letting a `tokenNumber=0` transaction bypass all balance reconciliation for any external action that doesn't self-guard — concretely exploitable via `EmporiumUpgradeable.runAction` - ([File: contracts/HinkalHelper.sol])

### Summary
`dimensionsCheck` in `contracts/HinkalHelper.sol` only checks that array lengths *match* `dimensions.tokenNumber`, never that `tokenNumber > 0`, so `tokenNumber=0` is a fully valid, always-available proof shape (`MainEVMCircuit(0, inputCount, outputCount, treeDepth)` is a legal verifier selection via `VerifierFacade.buildVerifierId`). With `tokenNumber=0`, `circomData.erc20TokenAddresses` is empty, which makes every reconciliation loop in `Hinkal.transact` (`oldBalances`/`newBalances`/`balanceDif`) a no-op, so the invariant "value leaving/entering an external action equals its `amountChanges`" is vacuously satisfied even when real value moves.

### Finding Description
**Equality that should hold:** for every token `i` actually moved by an external action, `balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` (enforced at `contracts/Hinkal.sol:137-146`). This is only checked inside `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` (`contracts/Hinkal.sol:97`). If `tokenNumber=0`, this array is empty and the loop body — including the slippage check and the balance-diff equality — never executes.

`dimensionsCheck` (`contracts/HinkalHelper.sol:64-171`) requires `erc20TokenAddresses.length == dimensions.tokenNumber`, `amountChanges.length == dimensions.tokenNumber`, etc., but nowhere requires `dimensions.tokenNumber > 0`. `checkOnchainCreation` (`contracts/HinkalHelper.sol:173-202`) iterates `circomData.onChainCreation.length`, which is also 0, so it is vacuously satisfied. Nothing in `Hinkal.transact` or `CircomDataBuilder` rejects `tokenNumber=0` either.

I traced `_externalTransact` (`contracts/Hinkal.sol:234-261`): with an empty `erc20TokenAddresses`, `deltaAmountChanges` is an empty array, and `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` is invoked with empty arrays. I then checked every currently-registered/derivable `IExternalActionV2` implementation for a self-guard against empty arrays:
- `DepositOnChainUtxosExternalAction.runAction` explicitly reverts: `require(tokenCount > 0 && ...)` at `contracts/external-actions/DepositOnChainUtxosExternalAction.sol:26-29` — **not exploitable**.
- `ExternalActionSwap.swap` (base for LiFi/router swap actions) directly indexes `circomData.erc20TokenAddresses[0]` and `[1]` at `contracts/external-actions/swaps/ExternalActionSwap.sol:44,51` — an empty calldata array access reverts — **not exploitable**.
- `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) has **no such guard**. Its `stack.ops` come from `abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack))`, entirely independent of `erc20TokenAddresses`/token count. The op-execution loop (`op.endpoint.call{value: op.value}(op.callData)`, line 112) runs regardless of `tokenNumber`. `verifyWallet` (line 302) only requires a signature when `stack.signerAddress != address(0)`; when `signerAddress == address(0)` it returns immediately after marking the message used (lines 314-316) — no signature required at all. The post-hoc balance reconciliation loop (`for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)`, line 132) is also empty when `tokenNumber=0`, so `BalanceChangeShouldBePositive` can never fire.

**Attacker's exact call:** call `Hinkal.transact` with `dimensions.tokenNumber=0`, `circomData.externalActionData.externalActionId` set to Emporium's id, `externalActionData.externalActionMetadata` ABI-encoding an `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: attackerContract, invokeWallet: false, value: <EmporiumBalance>, callData: ""}] }`, and all zero-length arrays (`erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `outCommitments`, `slippageValues`, `onChainCreation`, `encryptedOutputs` all length 0, satisfying `dimensionsCheck`). A `MainEVMCircuit(0,...)` proof is generated for this trivially-empty statement (no meaningful constraints to satisfy for the empty token loop) and passed to `verifyProof`. `checkOnchainCreation` is vacuous, `performHinkalChecks` passes, `verifyProof`/`rootHashExists` pass (a valid Merkle root just needs to exist), `_externalTransact` calls `Emporium.runAction` with empty `deltaAmountChanges`, which executes the attacker-chosen `call{value: op.value}` against `Emporium`'s own ETH/token balance — balance that represents pooled/custodied funds from other users' shielded UTXOs that have been routed through Emporium but not yet withdrawn.

**Why guards fail:** `dimensionsCheck` never rejects `tokenNumber=0`; `Hinkal.transact`'s balance-diff/slippage loop is keyed off `erc20TokenAddresses.length`, which is 0; `Emporium.runAction`'s own balance check loop is likewise keyed off `circomData.erc20TokenAddresses.length`, so it's skipped too. No other check (root hash, nullifier insertion, proof verification) constrains the value of `op.value` or the destination `op.endpoint`.

### Impact Explanation
This is a direct theft path: an unprivileged attacker drains ETH/ERC20 balance held in custody by `EmporiumUpgradeable` — funds belonging to other users' shielded, in-flight balances — to an attacker-controlled contract, with zero reconciliation by `Hinkal.transact`. This matches the Critical category: "direct theft of shielded or in-flight user funds." It is repeatable per available Emporium balance and requires only a single proof for an always-valid `tokenNumber=0` circuit shape.

### Likelihood Explanation
Preconditions: (1) `EmporiumUpgradeable` must hold non-zero native/token balance from other users' pending operations (a normal operating state for the intended pooled-wallet design), and (2) the attacker needs a `tokenNumber=0` `MainEVMCircuit` verifier deployed/registered (verified via `VerifierFacade.buildVerifierId`, out-of-scope for deep dive but assumed available per the question's precondition). Cost to the attacker is a single proof generation and gas; no privileged role, no victim cooperation, and no reliance on any race condition are required — fully feasible for an unprivileged EOA.

### Recommendation
Add `require(dimensions.tokenNumber > 0, "tokenNumber must be greater than zero")` in `HinkalHelper.dimensionsCheck` for any transaction with `externalActionData.externalActionId != 0` (or globally, if `tokenNumber=0` internal transactions have no legitimate use). Additionally, harden `EmporiumUpgradeable.runAction` (and any future `IExternalActionV2` implementation) to independently `require(circomData.erc20TokenAddresses.length > 0)` so it does not rely solely on the caller's dimension checks.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register Emporium under an `externalActionId`, and register/deploy a `tokenNumber=0` `MainEVMCircuit` verifier reachable through `buildVerifierId`.
2. Fund `EmporiumUpgradeable` with ETH (simulating pooled/in-flight user balance) via a legitimate prior transaction.
3. Deploy a malicious "sink" contract with a `receive()` function.
4. Craft `CircomData` with `dimensions.tokenNumber=0`, all token/amount/nullifier/commitment arrays empty, `externalActionData.externalActionId` = Emporium's id, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: sink, invokeWallet:false, value: EmporiumBalance, callData: ""}]}`.
5. Generate a valid proof for the (trivial) `tokenNumber=0` circuit and a valid Merkle root.
6. Call `Hinkal.transact(...)` from an unprivileged EOA.
7. Assert: (a) `sink.balance` increases by `EmporiumBalance` (attacker gained value never accounted for), (b) `Hinkal`'s `oldBalances`/`newBalances` diff check never executed (loop bound `circomData.erc20TokenAddresses.length == 0`), (c) `EmporiumUpgradeable`'s balance dropped to 0 with no corresponding entry in `amountChanges`/`deltaAmountChanges` (both empty arrays), demonstrating the equality `balanceDif == amountChanges + utxoAmount` was never evaluated while real ETH left custody.
