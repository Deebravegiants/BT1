### Title
Webhook shop identity spoofable because `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop identity (`shop`), event `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler as trusted tenant-identifying data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` signs/verifies exactly that string: [1](#0-0) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then constructs `WebhookMetadata` directly from these unauthenticated header values and forwards it to the app's handler as the source of truth for which shop/tenant the event belongs to: [3](#0-2) 

This breaks the identity binding: `shop` used to attribute/act on a webhook event ≠ `shop` covered by the HMAC. Since Shopify computes the webhook HMAC using the app's `client_secret`, which is shared across every merchant that has installed the app, any unprivileged user who installs the app on their own (attacker-controlled) shop receives genuinely-signed webhook deliveries with a valid HMAC over a body they control. Because the `shop-domain` (and `topic`/`webhook-id`) headers are outside the signed content, that attacker can replay the same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

This is the exact bug class from the report: a value that is acted upon (`endMonth`/here `shop`) is not actually validated/covered by the mechanism meant to guarantee its integrity (month-range check / HMAC), letting attacker-influenced input pass through into the trusted decision-making path.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to key its per-tenant session lookup, data writes, or authorization decisions (the intended and documented use of this field, since the gem hands it directly to handlers), an attacker can forge which shop a legitimately-signed webhook is attributed to. This enables cross-tenant confusion/access: attacker-controlled webhook content can be processed as if it belongs to a victim merchant, or attacker can trigger handler logic scoped to another tenant's data purely by manipulating an unsigned header, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (which is the common case for Shopify apps): any user who installs the app on their own store automatically obtains validly-HMAC-signed webhook deliveries under the shared `client_secret`, and only needs to intercept/replay the HTTP request to the app's webhook endpoint with a modified `shop-domain` header — no access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signable content used for HMAC verification, or otherwise cryptographically/independently bind `request.shop` to the verified payload (e.g., cross-check it against the list of shops for which the app holds an active, previously-established session/installation before trusting it for any tenant-scoped action). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must not be used as sole tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g. body `{"id":1}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `HmacValidator.validate(request)` in `Registry.process` (lib/shopify_api/webhooks/registry.rb:190) succeeds because it only checks the raw body against the HMAC, which is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim.myshopify.com"` (lib/shopify_api/webhooks/registry.rb:198), and the app's handler executes tenant-scoped logic believing the event genuinely originated from `victim.myshopify.com`.
