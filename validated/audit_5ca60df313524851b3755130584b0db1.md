### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler. Because the app's `client_secret` (`Context.api_secret_key`) used to compute the HMAC is shared across every shop that installs the app, an attacker who obtains one valid `(body, hmac)` pair for their own shop can replay it against the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop, and `Utils::HmacValidator.validate` will still report the request as authentic.

### Finding Description
`HmacValidator.validate` verifies only `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw request body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are pulled from HTTP headers with no cryptographic binding to that body: [3](#0-2) 

`Registry.process` trusts these unauthenticated header-derived fields once the body-only HMAC check passes, and forwards them straight to the app's handler: [4](#0-3) 

The equality this breaks is: `shop authenticated` (the shop the HMAC proves the payload came from) should equal `shop the handler acts on` (`request.shop`, taken from `x-shopify-shop-domain`). Here, the HMAC only proves "this body was signed with the app's `client_secret`" — it says nothing about which shop's header should accompany that body. Since the same `client_secret` is valid for every shop installing the app, any merchant/attacker who installs the app on their own store can capture a legitimate `(body, x-shopify-hmac-sha256)` pair from their own webhook traffic, then resend that exact body to the app's webhook endpoint with `x-shopify-shop-domain` swapped to a victim's domain (and/or `x-shopify-topic`/`x-shopify-webhook-id` altered). `HmacValidator.validate` recomputes the HMAC over the body alone, finds it matches, and `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop`/`topic` are the attacker-forged values.

### Impact Explanation
If the host application uses `request.shop` (as delivered through `WebhookMetadata`) to key session/store lookups, apply the payload to shop-specific data, or otherwise attribute the webhook body to a tenant — which is the intended and documented usage pattern of this field — an attacker can inject data or trigger side effects under an arbitrary victim shop's identity using their own genuinely-signed webhook traffic as the carrier. This is a cross-tenant integrity/identity-binding break: the field the handler acts on (`shop`) is not the field the HMAC actually authenticates (`body`).

### Likelihood Explanation
Exploitability requires only: (1) the attacker installs the target app on any shop they control (a normal, unprivileged action any merchant can take), (2) capture one legitimate webhook `(body, hmac)` pair sent to their own endpoint, and (3) replay it to the app's webhook endpoint with a different `x-shopify-shop-domain` header. No access to `api_secret_key`, access tokens, or the victim's credentials is needed — only network access to the app's public webhook URL, which is inherently internet-reachable. This fits squarely in the "unprivileged internet user" threat model.

### Recommendation
Bind the shop (and ideally topic/webhook id) identity into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the specific webhook delivery — e.g., cross-check `request.shop` against an out-of-band, per-shop record (such as the shop's stored access token/session) before dispatching to the handler, rather than trusting the raw header once a body-only HMAC succeeds. At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are unauthenticated header values and must not be trusted for tenant attribution without additional verification by the host application.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify (computed with the app's shared `client_secret`).
2. Send a new HTTP request to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B` only) and matches `H`, per `lib/shopify_api/webhooks/request.rb` lines 35-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 188-200 — the app processes attacker-controlled data as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
