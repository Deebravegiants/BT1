### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the shop identity that the app trusts downstream (`x-shopify-shop-domain` header) is never included in what is verified. Any merchant/attacker who legitimately receives webhooks for their own store (an unprivileged, non-secret-holding actor) can capture a valid `(body, hmac)` pair and replay it against the app's webhook endpoint with an arbitrary `shop-domain` header, causing the app to process the payload as if it originated from a different (victim) tenant.

### Finding Description
`Distributor::addRewards` in the external report fails to validate that an attacker-supplied parameter (`token1`/`quoteAsset`) is legitimate before trusting it to inflate an accounting value. The same "field acted on but not authenticated" pattern exists in this gem's webhook verification path.

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw request body, while `hmac` is decoded from the `hmac-sha256` header: [2](#0-1) 

Critically, `shop` is read directly from the `shop-domain` header and is **not** part of `to_signable_string`: [3](#0-2) 

`Registry.process` validates only the body-based HMAC, then forwards `request.shop` — the unauthenticated header — straight into `WebhookMetadata`, which the app's handler treats as the trusted tenant identity for the event: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`hmac == HMAC(secret, body || shop)` — i.e., the shop the handler acts on must be cryptographically bound to the signed content.

What is actually checked is:
`hmac == HMAC(secret, body)` — the `shop` header is a free-form, attacker-controlled value with no cryptographic tie to the signature at all.

Because every shop installed on a given app shares the same `api_secret_key` (the app's client secret, not a per-shop secret), a valid `(body, hmac)` pair generated for one shop (e.g., the attacker's own store, which legitimately receives real webhooks) is a **valid signature for any shop domain**, since the shop value is never part of what's hashed. An attacker who owns a store that has the app installed can:
1. Install the app on their own shop and capture a genuine webhook `(raw_body, x-shopify-hmac-sha256)`.
2. Replay that exact body+HMAC to the app's webhook endpoint, but with `x-shopify-shop-domain` (or `shopify-shop-domain`) set to a victim shop's domain.
3. `HmacValidator.validate` succeeds (it never looked at the shop header), and `Registry.process` dispatches to the app's handler with `data.shop == "victim-shop.myshopify.com"`.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: it allows an attacker who is merely a legitimate (unprivileged) user of the app on their own store to forge webhook events that the host application will process as originating from a different, victim merchant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the merchant's session/access token by shop domain to act on their store, updating per-shop billing/state, or triggering emails/notifications), this enables cross-tenant data corruption or actions taken against another merchant's account under the attacker's chosen payload — satisfying the "cross-tenant access" criterion. No `api_secret_key`, access token, or privileged credential is required; only attacker control of their own store's genuine webhook traffic.

### Likelihood Explanation
High. Capturing a legitimate webhook `(body, hmac)` pair requires nothing more than operating a store with the app installed and receiving one webhook (trivial for any developer/merchant testing the app). Replaying it with a modified `shop-domain` header against the app's public webhook endpoint requires only basic HTTP tooling. There is no rate limiting, nonce, or timestamp field checked in the signable string that would prevent reuse across different declared shops.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified content, or otherwise require the app to independently confirm that the shop asserted in the header actually corresponds to the app's known installation state before trusting it as the identity used to process the webhook. At minimum, document/require that `Registry.process` callers cross-check `request.shop` against a known/authorized shop list rather than trusting it purely because the body-only HMAC validated.

### Proof of Concept
1. Attacker's own store `attacker-shop.myshopify.com` has the app installed; Shopify sends a legitimate webhook:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id": 1, ...}`
2. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, replacing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. Server code:
   ```ruby
   request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: modified_headers)
   ShopifyAPI::Webhooks::Registry.process(request)
   ```
4. `HmacValidator.validate(request)` returns `true` (per [1](#0-0) ) because it only hashes `@raw_body`, ignoring the shop header.
5. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the host app to process the attacker's payload under the victim's tenant identity.
