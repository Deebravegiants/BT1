## #Vulnerability found for this question.

### Title
Unchecked ERC20 `transfer()` return value in `IntentGatewayV2.withdraw()` allows permanent loss of escrowed intent funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent funds using a raw low-level `.call()` invoking `IERC20.transfer.selector` and only checks that the *external call itself* did not revert (`success`). It never decodes and validates the ERC20 boolean return value. Non-reverting ERC20 tokens that signal failure by returning `false` (rather than reverting) will silently fail the transfer while the contract still decrements escrow accounting and marks the order as filled/refunded — permanently freezing the beneficiary's funds inside the contract with no recovery path.

### Finding Description
`IntentGatewayV2.withdraw()` is the function that pays out escrowed input tokens (and accumulated transaction fees) to a solver or user once a `RedeemEscrow`/`RefundEscrow` message is delivered from the source chain, or once a `GET` cancellation response proves the order was unfilled: [1](#0-0) 

The transfer of the escrowed token is done as:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and the fee token transfer a few lines later uses the identical unsafe pattern: [2](#0-1) 

The same unchecked pattern also appears in the `SweepDust` handling in the same contract: [3](#0-2) 

In all three places, `success` only reflects whether the external call reverted — it does **not** decode the ABI-encoded boolean that a standard ERC20 `transfer()` returns. Per the ERC20 specification, implementations are allowed to return `false` on failure instead of reverting (this is exactly why `SafeERC20.safeTransfer` exists — to decode and enforce the return value). The contract itself imports and uses `SafeERC20` (`using SafeERC20 for IERC20;`) and correctly calls `safeTransferFrom` elsewhere (e.g. `placeOrder`), but `withdraw()` and the dust-sweep path bypass this and use the unchecked raw-call pattern instead — this is the exact bug class described in the reference report (`AssetVault.claimWithdrawalRequest` not checking `asset.transfer`'s return value; recommendation: use `safeTransfer`).

Critically, regardless of whether the token-level transfer succeeded or silently failed, the function unconditionally proceeds to decrement escrow accounting:
```solidity
_orders[body.commitment][token] -= amount;
```
and marks `_filled[body.commitment] = beneficiary`, finalizing the order.

### Impact Explanation
For any ERC20 asset used as an intent input/fee token that does not revert on failed transfers (e.g. contracts that return `false` on insufficient balance, paused state, blacklist checks, or other custom failure conditions — a known real-world pattern), the beneficiary (solver completing a cross-chain fill, or the user cancelling/refunding an order) will not actually receive the promised tokens. Because escrow accounting is still decremented and the order is marked filled/refunded, there is no way to retry or reclaim the funds — they remain permanently locked in the `IntentGatewayV2` contract. This is a direct, unrecoverable loss of user/solver funds reachable through the normal intents escrow settlement flow (solver fills order → `RedeemEscrow` message delivered by any relayer → `withdraw()` executes the faulty transfer).

### Likelihood Explanation
This path is triggered on every cross-chain intent settlement and every order cancellation/refund — it is not a rare edge case but the standard payout mechanism. It requires only that the escrowed/fee token be a non-standard-but-common ERC20 that returns `false` instead of reverting, which does not require any privileged or malicious actor — an ordinary user or solver choosing (or being routed via `order.inputs`) a token with this behavior is sufficient to trigger fund loss. Given that `IntentGatewayV2` is permissionless with respect to which ERC20 tokens can be used as order inputs, likelihood is moderate-to-high in an open deployment.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()`, the fee-redemption branch, and the `SweepDust` handler with `SafeERC20.safeTransfer` (the library is already imported and used elsewhere in the same contract), which properly decodes and enforces the ERC20 return value and reverts on failure before any escrow accounting is mutated.

### Proof of Concept
1. Deploy (or use) an ERC20 token as an order's input/fee token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., insufficient balance due to some external condition, or a deliberately crafted malicious/non-compliant token).
2. A user places an order with this token as input via `placeOrder` (escrow flow uses `safeTransferFrom`, so escrow is correctly funded).
3. A solver fills the order cross-chain; `RedeemEscrow` is dispatched and relayed to the source chain, invoking `onAccept` → `withdraw()`.
4. Cause the token's `transfer()` call to return `false` without reverting when paying the solver (e.g., by having the token's internal invariant fail silently).
5. `withdraw()` observes `success == true` (the call itself didn't revert) and proceeds to decrement `_orders[commitment][token]` and finalize `_filled[commitment]`, even though the solver received zero tokens — the escrowed balance is permanently stuck in the `IntentGatewayV2` contract with no path to reclaim it.
