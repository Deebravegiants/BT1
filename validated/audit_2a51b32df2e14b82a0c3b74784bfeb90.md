### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but binds the HMAC signature only to the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
But the identity fields that the registry acts on — most importantly `shop` — are pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 
`HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string`, i.e. the body bytes, using `Context.api_secret_key`: [3](#0-2) 
Once that check passes, `Registry.process` forwards the unauthenticated `request.shop` value straight into `WebhookMetadata` that is handed to the app's webhook handler: [4](#0-3) 

This is the exact bug class called out in scope: "a field acted on but not covered by the HMAC." The equality the gem is supposed to enforce is:
`shop asserted to the handler == shop that actually generated/authorized this signed payload`
but the code only proves `hmac == HMAC(body, secret)`; it proves nothing about which shop's header value was attached to that body.

### Impact Explanation
Any unprivileged internet user who can obtain one genuine `(raw_body, hmac)` pair signed with the app's secret — trivially achievable by installing the app on their own free/dev store and letting Shopify deliver a real webhook to the app's public endpoint — can replay that exact body and HMAC to the same public endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` will still succeed (it never inspects headers), and `Registry.process` will dispatch the handler with `WebhookMetadata(shop: <victim-shop>, ...)`. Any app logic that trusts this `shop` value to look up state, update per-tenant data, or make authorization decisions keyed off the shop is now operating on attacker-chosen tenant identity — a cross-tenant confusion/access primitive achieved purely through this gem's request/verification code, without any credentials belonging to the victim.

### Likelihood Explanation
The prerequisite (a single legitimate webhook delivery, obtainable by installing the app on an attacker-controlled store) is trivial for any external, unauthenticated party to satisfy, and the webhook endpoint is by design internet-reachable. No secret, token, or privileged account for the victim is required, only the app's own webhook signing secret being reused across all merchants (which is how Shopify apps work). Likelihood is therefore high wherever the host app relies on `WebhookMetadata#shop`/`#topic` for tenant-scoped logic, which is the documented and expected usage pattern of this gem's webhook API.

### Recommendation
Bind the header-derived identity fields into the signed material verified by `HmacValidator`, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` if Shopify's signing scheme supports it, or — since Shopify's HMAC is body-only — have `Registry.process`/`WebhookMetadata` require the caller to independently verify that `request.shop` corresponds to a shop with an active installation/session before dispatching, and document this requirement prominently so host apps cannot mistake header `shop`/`topic` values as authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app's public webhook endpoint, capturing the raw body `B` and the header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(secret, B)`).
2. Attacker (or a script) sends a new HTTP request to the same public endpoint with:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256` = `H` (unchanged)
   - `x-shopify-shop-domain` = `victim.myshopify.com` (changed)
   - `x-shopify-topic` = same or different registered topic
3. `Webhooks::Request.new` parses this into `shop = "victim.myshopify.com"`, `hmac = H`.
4. `HmacValidator.validate(request)` computes `HMAC(secret, B)` which still equals `H`, so validation passes: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: ..., body: parsed_body(B), ...)`: [4](#0-3) 
6. The app's handler now performs whatever webhook-driven action (data sync, cache invalidation, order/customer record updates, etc.) against the victim shop's tenant record, using attacker-supplied body content, despite the request never having been produced or authorized by the victim.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
