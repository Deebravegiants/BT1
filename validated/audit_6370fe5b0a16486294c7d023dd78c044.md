### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but then trusts the `shop` and `topic` values taken from separate, unsigned HTTP headers to route and attribute the payload. Anyone who can obtain one validly-signed webhook body (e.g., by owning a single Shopify store that receives webhooks) can replay that body to the app's webhook endpoint while freely substituting the `shopify-shop-domain` and `shopify-topic` headers, causing the host application to process attacker-chosen data as if it originated from a different shop/topic.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC using `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [1](#0-0) 

For webhook requests, the signable content is the raw JSON body only — the test fixture demonstrates the HMAC is computed purely over the body string (`"{}"`), while `shopify-shop-domain` and `shopify-topic` are separate headers that are never part of the signed material: [2](#0-1) 

`Registry.process` then validates only this body-derived HMAC and, once it passes, unconditionally trusts `request.topic` and `request.shop` (sourced from the unsigned headers) to look up a handler and construct the metadata handed to application code: [3](#0-2) 

The identity binding that should hold is:
`HMAC(secret, signed_bytes) == received_hmac` should imply `shop == the shop that produced signed_bytes` **and** `topic == the topic that produced signed_bytes`.

Because `shop` and `topic` are excluded from `signed_bytes`, this equality does not hold — the HMAC only proves the body was signed by the app's secret at some point, for some webhook, from some shop; it says nothing about which shop or which topic. An attacker who owns any single shop installed on the app receives legitimately HMAC-signed webhook deliveries for that shop. They can capture one such delivery and resend the identical `(body, hmac)` pair to the app's webhook endpoint while changing the `shopify-shop-domain` header to a victim shop's domain and/or the `shopify-topic` header to a different registered topic. `Registry.process` will pass HMAC validation (since it only checks the body) and will invoke the handler with attacker-chosen `shop`/`topic` values.

### Impact Explanation
This breaks the shop-authenticated vs. shop-attributed binding, allowing cross-tenant data injection: an app storing/acting on webhook data keyed by `request.shop` (e.g., updating shop-scoped state, uninstall/GDPR handling, order/product data ingestion) can be made to attribute attacker-controlled payloads to an arbitrary victim shop, or to trigger a different topic's handler than what was actually signed (e.g., replaying a low-sensitivity webhook body into a sensitive topic's handler). This matches the "Cross-tenant access" / "authentication bypass" impact category, since the tenant (shop) identity used by the application is not actually authenticated by the cryptographic check performed.

### Likelihood Explanation
Any merchant that installs the app receives legitimately signed webhooks for their own store and can capture and replay them with modified headers using standard HTTP tooling — no access to the app's `client_secret`, tokens, or any privileged account is required. This is a realistic "unprivileged internet user" (any store owner who installs the app) attack path.

### Recommendation
Include `shop` and `topic` (and any other header-derived identity fields used downstream) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and registers/receives a legitimate webhook for topic `orders/create` with body `B`; Shopify computes `hmac = HMAC(secret, B)` and sends headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: hmac`.
2. Attacker captures `(B, hmac)`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same `hmac`, but headers `shopify-shop-domain: victim-shop.myshopify.com` and/or `shopify-topic: customers/data_request`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `hmac`.
5. `Registry.process` looks up the handler for the attacker-supplied topic and invokes it with `shop: "victim-shop.myshopify.com"`, causing the application to process attacker-controlled data as if it came from the victim shop.
