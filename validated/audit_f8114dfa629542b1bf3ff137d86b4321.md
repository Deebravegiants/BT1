### Title
Ceiling-division overflow cap in `Router._computeBuy` can revert or produce an inconsistent `amountInUsed` for an oversized closing buy - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap branch reproduces the exact anti-pattern flagged in the external report: it computes a ceiling division by adding the numerator and a near-max denominator-adjacent term before dividing, instead of using an overflow-safe `ceilDiv` (e.g. OpenZeppelin's `Math.ceilDiv`, which the repo already imports and uses elsewhere in `Bonding.sol`/`Zap.sol`).

### Finding Description
`Router._computeBuy` is reachable by any unprivileged trader through `Bonding.buy` → `Zap.buy`/`Zap.buyPermit` with an oversized `amountIn` (the "overflow buy cap" documented in `packages/contracts/AGENTS.md`). When the naive constant-product `tokensOut` exceeds the pair's real token balance, the function re-derives the LT actually consumed with a hand-rolled ceiling division: [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
    amountInUsed = cappedReserveAsset - reserveAsset;
}
```

This is structurally identical to the reported `ceilDiv` pattern: it adds `k` and `cappedReserveToken - 1` before dividing, rather than computing `(k - 1) / cappedReserveToken + 1` (the overflow-safe form Solidity's/OZ's `Math.ceilDiv` uses, as seen in the vendored `Math.sol`: [2](#0-1) 

). `k` is `tokenReserve * assetReserve`, fixed once at `Pair.mint` and never re-derived: [3](#0-2) 

`tokenReserve` is the virtual reserve set to `Token.TOTAL_SUPPLY()` (1B * 1e18), and `assetReserve` is the launch-time virtual LT reserve derived from `VIRTUAL_LIQUIDITY_USD` combined with the LT's `exchangeRate()` at launch time — a value read from an external, live-priced, rebasing token (`IBounceLeveragedToken.exchangeRate`) that the protocol does not control or bound. In Solidity 0.8.24, `k + cappedReserveToken - 1` is a **checked** addition, so if `k` were close to `type(uint256).max` this line would revert (DoS on the closing buy) rather than silently wrapping — but the underlying pattern is the same "unchecked-style ceilDiv formula" flagged in the report, and it is present in a hot, trader-reachable path (every large/closing buy near graduation) rather than a dead code path.

### Impact Explanation
If `k` ever grows close to `type(uint256).max` (extreme LT `exchangeRate` combined with a very large `VIRTUAL_LIQUIDITY_USD` configuration, or a future change that removes today's practical bounds on launch-time virtual reserves), the addition `k + cappedReserveToken - 1` reverts on overflow. Since this is the **overflow-cap branch** that exists specifically to let the "last buy" complete and trigger the supply-based graduation trigger (`IPair.tokenBalance() == 0`), a revert here would deny the closing buy — and by extension, the supply-based path to graduation for the token — a **medium-severity availability/fund-freezing issue** consistent with the "no impact vs. real impact" bar in the rules (permanent inability to complete a graduating buy would strand curve-raised LT and 250M reserved tokens on `Bonding` indefinitely).

### Likelihood Explanation
Low-to-medium under current deploy parameters: `AGENTS.md` and the test suite (`test/GraduationInvariants.t.sol::test_inv_overflowCap_refundsLt`, `test/Router.t.sol::test_getAmountOut_buy_capsAtSellableBalance`) show the cap branch is exercised in normal operation with realistic reserve sizes, and `k` stays far below `type(uint256).max` for any economically sane LT price and seed size. The report itself notes this class is "not identified as a threat in the current codebase" but flags it as latent risk if unvalidated inputs (e.g., an extreme `exchangeRate()` value from the external LT, or a future change to `VIRTUAL_LIQUIDITY_USD`/launch-seeding limits) ever push `k` toward the top of the `uint256` range.

### Recommendation
Replace the manual `(k + cappedReserveToken - 1) / cappedReserveToken` (and the analogous pattern at `Router.sol:181`'s sibling `_computeSell`, and any other hand-rolled ceiling divisions in `Router.sol`) with OpenZeppelin's `Math.ceilDiv(k, cappedReserveToken)`, which the codebase already imports and uses in `Bonding.sol`/`Zap.sol`. This removes the addition-before-division overflow surface entirely, matching the upstream fix pattern referenced in the external report (PR #236).

### Proof of Concept
Conceptual (parameter-dependent, not exploitable under the currently deployed constants):
1. `Pair.mint` is called once at `Bonding.launch()`/`Zap.createToken` with `tokenReserve = TOTAL_SUPPLY` and `assetReserve` derived from `VIRTUAL_LIQUIDITY_USD` and the LT's `exchangeRate()` at that block [3](#0-2) .
2. If `assetReserve` were large enough that `k = tokenReserve * assetReserve` approaches `type(uint256).max` (e.g. via an LT with an extreme `exchangeRate()` at launch, or a future config change removing today's implicit bounds), any subsequent oversized buy that trips the overflow-cap branch in `_computeBuy` [1](#0-0)  would revert with a checked-arithmetic panic on `k + cappedReserveToken - 1`, rather than completing the capped buy.
3. Because this branch is the mechanism that lets a trader's buy consume exactly the remaining sellable supply and drive `IPair.tokenBalance()` to `0` (the supply-side graduation trigger documented in `AGENTS.md`), a revert here would block that token's graduation via the supply trigger, freezing the LT already raised on the curve and the 250M `LP_RESERVE` tokens parked on `Bonding` until a workaround (e.g., relying solely on the USD trigger) succeeds — which may not be possible if the LT's price crashed.

Note: I could not find any current code path or deployment parameter (`VIRTUAL_LIQUIDITY_USD`, seed limits, LT `exchangeRate` bounds) that actually drives `k` near `type(uint256).max` in this codebase; the finding is therefore a valid structural analog of the reported bug class (same unsafe ceiling-division formula, in a trader-reachable hot path) but, like the original report, is not demonstrated to be triggerable with today's real-world inputs.

```text
    function ceilDiv(uint256 a, uint256 b) internal pure returns (uint256) {
        if (b == 0) {
            // Guarantee the same behavior as in a regular Solidity division.
            Panic.panic(Panic.DIVISION_BY_ZERO);
        }

        // The following calculation ensures accurate ceiling division without overflow.
        // Since a is non-zero, (a - 1) / b will not overflow.
        // The largest possible result occurs when (a - 1) / b is type(uint256).max,
        // but the largest value we can obtain is type(uint256).max - 1, which happens
        // when a = type(uint256).max and b = 1.
        unchecked {
            return SafeCast.toUint(a > 0) * ((a - 1) / b + 1);
        }
    }
```
