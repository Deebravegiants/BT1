### Title
Webhook HMAC only covers the request body, allowing shop/topic identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC signature it validates only covers the raw request body. The `shop-domain`, `topic`, and `webhook-id` headers that are handed to the app's handler as trusted tenant/event identity are never included in the signed bytes, so any party who can obtain one legitimately-signed `(body, hmac)` pair can replay it with a different shop/topic header and it will still pass validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely over that signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the whole request is authentic, then forwards the *unauthenticated* `shop`, `topic`, and `webhook_id` header values straight to the app-supplied handler: [3](#0-2) 

Those accessors read directly from HTTP headers with no cross-check against the signed payload: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the full request — including which shop and topic it is for — is authenticated: [5](#0-4) 

In reality only the byte-for-byte body is bound to the signature; `shop-domain` is not. Since the webhook secret (`api_secret_key`/`client_secret`) is shared across every shop that has installed the app, a merchant on their own store can legitimately trigger a webhook to their own endpoint, capture the resulting `(raw_body, hmac-sha256)` pair from a real Shopify delivery, and then re-POST that exact body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain (and/or a different `shopify-topic`/`shopify-webhook-id`). `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` dispatches to the handler with the attacker-chosen `shop`/`topic`/`webhook_id`, breaking the equality that should hold: `shop authenticated by HMAC == shop acted upon by the handler`.

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop`/`#topic` (as this gem's own documentation and example handler code does) to determine which tenant's data to update can be tricked into applying another shop's webhook payload as if it belonged to the attacker-chosen shop, resulting in cross-tenant data corruption/access — a Critical-class impact per the scope's "cross-tenant access" category. No credentials, tokens, or elevated access are required beyond the ability to install the app on one's own store and call the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is significant: installing an app and receiving a legitimate webhook is a routine unprivileged action. Replaying the exact captured body with a modified header requires no cryptographic material — the fields the exploit depends on (`shop-domain`, `topic`, `webhook-id`) are explicitly excluded from the HMAC input, so no secret is ever needed to forge the identity portion of the request.

### Recommendation
Extend `VerifiableQuery`/`Request#to_signable_string` (or add a separate binding check in `Registry.process`) so the `shop-domain`, `topic`, and `webhook_id` headers are cryptographically bound to the signature — e.g., include them in the HMAC input, or require host applications to be explicitly warned in `Registry.process`/docs that `shop`/`topic` are unauthenticated and must be independently validated against the app's known installed-shop list before use.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and register a webhook (e.g., `orders/create`) pointing at the app's public callback URL.
2. Trigger the webhook (e.g., create an order) and capture the raw POST: headers `x-shopify-hmac-sha256: <HMAC>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and the raw JSON body.
3. Re-send the identical raw body and identical `x-shopify-hmac-sha256` value to the same endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. Observe that `ShopifyAPI::Utils::HmacValidator.validate` (called inside `ShopifyAPI::Webhooks::Registry.process`) still returns `true` because it only hashes `@raw_body`, and the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though Shopify never sent this request for that shop.
