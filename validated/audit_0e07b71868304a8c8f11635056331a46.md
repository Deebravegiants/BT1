### Title
Attacker-controlled flash receiver can smuggle arbitrary caller-authorized token transfers into the signed auth tree - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` authenticates the caller, accepts an arbitrary deployed `receiver` and opaque `data`, and then invokes that receiver before finalizing the position. A malicious receiver can invoke an unrelated token’s `transfer(caller, attacker, amount)` during the callback; Soroban records that call as a child of the caller’s signed authorization tree, so the transfer executes if the caller signs the poisoned tree. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The only receiver checks are that it is deployed Wasm code and is not the controller or pool; there is no receiver allowlist or behavioral constraint. [4](#0-3)  The controller places the entire receiver invocation inside the flash-guarded callback window and passes attacker-controlled `data` directly to `execute_flash_position`. [5](#0-4) [6](#0-5)  Because callback code runs below the caller-authorized controller invocation, a nested token transfer requiring `caller.require_auth()` is added to that invocation’s auth tree and executes when the caller signs it. [7](#0-6)  The exploit does not need the stolen asset to be declared: undeclared callback assets are neither supplied nor refunded, so the unrelated stolen token can simply remain with the attacker. [8](#0-7) 

### Impact Explanation
A malicious receiver can steal arbitrary token balances held by the victim while still returning the borrowed asset or another collateral token to satisfy the declared collateral minimum. [9](#0-8) [10](#0-9)  This is theft of user funds rather than a route-quality issue: the stolen asset need not participate in the lending market, flash-position debt, collateral declaration, or refund list. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
Any unprivileged user can call `flash_position` with a self-selected receiver and payload, while an existing account additionally requires owner-or-delegate authority over that account. [13](#0-12) [14](#0-13)  Execution requires the victim to sign the simulated authorization tree containing the unexpected token transfer, so wallet and client auth-tree inspection bound the attack’s practicality. [15](#0-14) [7](#0-6) 

### Recommendation
Restrict flash-position callbacks to governance-approved receiver contracts or replace the arbitrary callback with a fixed, audited receiver interface that cannot introduce caller-authorized side effects. [4](#0-3)  Until then, clients and wallets must decode the signed authorization tree and reject any child invocation other than the expected token transfers; the repository’s own threat model describes this boundary. [16](#0-15) 

### Proof of Concept
Deploy `RogueReceiver` with an `execute_flash_position` callback that first calls `token::Client::new(env, WALLET_TOKEN).transfer(initiator, attacker, victim_balance)` and then transfers the received debt token to the controller. [2](#0-1) [17](#0-16)  Have the victim call `flash_position(victim, 0, spoke_id, PositionMode::Multiply, debt_asset, amount, rogue_receiver, data, [(debt_asset, amount)], [])`; returning the borrowed asset satisfies the collateral measurement when that asset is collateralizable, while the unrelated `WALLET_TOKEN` transfer remains outside the collateral/refund accounting. [9](#0-8) [12](#0-11)  The repository’s authorization-tree test demonstrates that the nested transfer is recorded under the caller’s controller authorization and succeeds when that poisoned child is signed. [18](#0-17) [19](#0-18)

**File:** docs/reference/endpoints.md (L84-86)
```markdown
Refund assets must be unique, listed in the debt hub and account spoke, disjoint from collateral declarations, and bounded by the maximum supply-position count. Refund eligibility requires an active spoke and an existing listing; it does not check collateralizable, borrowable, paused or frozen flags. Only positive balance changes above pre-callback balances return to the caller. The debt token can be a refund asset, but refunding it does not repay the minted debt.

Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint. Refunds produce token transfer events, without a dedicated controller refund event.
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
