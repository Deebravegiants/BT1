### Title
Unbounded WebSocket Message Size on Authenticated Node Connection Allows Gateway OOM - (File: core/services/gateway/network/wsconnection.go)

### Summary
The Chainlink Gateway's `webSocketServer` enforces a request-size limit only for the single handshake-response frame via `conn.SetReadLimit(int64(maxRequestBytes))` in `core/services/gateway/network/wsserver.go` (line 150). Once the handshake completes, the same `*websocket.Conn` is handed off to `wsConnectionWrapper.Reset()` in `core/services/gateway/network/wsconnection.go`, which starts a long-lived `readPump` goroutine that calls `conn.ReadMessage()` in a loop for the lifetime of the connection, with no size bound applied to this ongoing read path.

### Finding Description
`core/services/gateway/network/wsserver.go` bounds only the handshake frame: [1](#0-0) 

After the handshake succeeds, `FinalizeHandshake` in `core/services/gateway/connectionmanager.go` sets a read deadline and pong handler but never re-applies a message size limit before giving the connection to the long-lived wrapper: [2](#0-1) 

The connection is then driven by `readPump`, which loops on `conn.ReadMessage()` indefinitely with no per-call size constraint: [3](#0-2) 

Because gorilla/websocket's default max message size is unlimited unless `SetReadLimit` is invoked on that specific connection, and the only `SetReadLimit` call in the codebase is scoped to the pre-handshake read in `wsserver.go`, an already-authenticated node (or an attacker who has otherwise obtained valid node credentials/signing key) can send an arbitrarily large single WebSocket frame on the persistent connection. `ReadMessage()` will allocate a buffer sized to the entire incoming frame before returning it to `readPump`, which then pushes it onto `c.readCh` for JSON unmarshalling in `donConnectionManager.readLoop` (`core/services/gateway/connectionmanager.go` lines 382–396). Repeated or large-enough messages can exhaust gateway server memory, matching the reported bug class of unbounded allocation on a message-processing channel from an already-connected peer.

### Impact Explanation
This is a resource-exhaustion / denial-of-service issue: a single authenticated node connection can crash or degrade the shared Gateway process serving all DONs/nodes behind it by exhausting memory, since no cap exists on frame size for the ongoing read loop. This does not lead to authentication bypass, secret disclosure, or fund movement, but availability impact (crash/OOM of the Gateway) is realistic and directly reachable from a connected node's normal message-sending capability.

### Likelihood Explanation
Requires a valid node identity/signing key to complete the WebSocket handshake (`StartHandshake`/`FinalizeHandshake` in `connectionmanager.go`), so it is not exploitable by a fully anonymous, unauthenticated actor over the network — it requires PR:H-equivalent access (a legitimate but compromised/rogue node), consistent with the CVSS vector in the referenced advisory (PR:H). Once connected, triggering the issue is trivial (one oversized WriteMessage from the node side), with no rate limiting or per-connection byte quota blocking it.

### Recommendation
Call `conn.SetReadLimit(...)` using the same `MaxRequestBytesLimiter`-derived value on the connection object before or immediately after `FinalizeHandshake` hands it to `wsConnectionWrapper.Reset()`, so the limit persists for the lifetime of the connection rather than only the single handshake read. Consider re-validating/resetting this limit whenever the connection is reset via `Reset()` in `wsconnection.go`, since the limit is a property of the `*websocket.Conn`, not the wrapper.

### Proof of Concept
1. Node completes a legitimate handshake against `webSocketServer.handleRequest` (`core/services/gateway/network/wsserver.go`), which succeeds and calls `FinalizeHandshake`.
2. Node then sends a single WebSocket binary frame far exceeding `MaxRequestBytes` (e.g. gigabytes) on the same connection.
3. `wsConnectionWrapper.readPump` in `core/services/gateway/network/wsconnection.go` (line 200) calls `conn.ReadMessage()`, which — absent a `SetReadLimit` call on this conn post-handshake — allocates a buffer for the full frame, consuming attacker-controlled amounts of Gateway memory and potentially causing an OOM crash affecting all DONs served by that Gateway instance.

func (c *wsConnectionWrapper) readPump(conn *websocket.Conn, closeCh chan<- error) {
	defer c.wg.Done()
	for {
		msgType, data, err := conn.ReadMessage()
		if err != nil {
			c.lggr.Errorw("failed to read message, closing connection", "error", err)
			var closeErr error
			if c.conn.CompareAndSwap(conn, nil) {
				closeErr = conn.Close()
				if closeErr != nil {
					c.lggr.Errorw("error closing connection", "error", closeErr)
				}
			}
			closeCh <- closeErr
			close(closeCh)
			return
		}
