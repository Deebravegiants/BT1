### Title
Emporium value-conservation bypass via empty `erc20TokenAddresses` lets an attacker drain ETH parked at Emporium - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only records and validates balance changes for the tokens listed in `circomData.erc20TokenAddresses`. When an attacker submits a `transact` call with `erc20TokenAddresses = []`, the entire balance-accounting/slippage machinery — both the loop in `EmporiumUpgradeable.runAction` (lines 85-151) and the mirrored loop in `Hinkal.transact` (lines 78-147) — is skipped, while `op.endpoint.call{value: op.value}(op.callData)` (line 112) still executes and can drain any ETH resting in Emporium's own balance to an attacker-controlled endpoint.

### Finding Description
The invariant that should hold is:

`sum(ETH/ERC20 leaving Emporium via ops) == -sum(deltaAmountChanges for those tokens)`

This is enforced only inside the `for (i < circomData.erc20TokenAddresses.length)` loop in `runAction`: [1](#0-0) 

If `circomData.erc20TokenAddresses` is empty, this loop body never runs — no `balancesBefore`/`balancesAfter` comparison, no `BalanceChangeShouldBePositive` check, no UTXO creation. Yet the ops loop that actually moves value still executes unconditionally: [2](#0-1) 

In the stateless branch (`stack.signerAddress == address(0)`), `verifyWallet` performs no EIP-712 signature check on the `ops` array at all — it only marks the `emporiumMessage` nonce as used: [3](#0-2) 

So an unprivileged attacker fully controls `op.endpoint`, `op.value`, and `op.callData` with no signature or balance-accounting constraint, as long as `erc20TokenAddresses` is empty. The `op.value` spent in `op.endpoint.call{value: op.value}` is paid out of Emporium's own ETH balance (the contract's `receive() external payable {}` at line 369 lets it accumulate ETH unconditionally from any prior interaction — dust, partial refunds, or ETH meant for a later step of a multi-call flow tied to a user's `signerAddress`/EIP-712 wallet session).

The mirrored check at the `Hinkal.transact` level is equally blind to this outflow because it also iterates only over `circomData.erc20TokenAddresses`: [4](#0-3) 

Since both loops key off the same (attacker-supplied, empty) array, no code path anywhere records that Emporium's ETH balance decreased by `op.value`. The circuit does not constrain this either — `ops`/`externalActionMetadata` is opaque calldata to the circuit, and the on-chain balance-diff loop was the sole mechanism meant to bind arbitrary external calls to the ZK-proved `amountChanges`. With `erc20TokenAddresses = []`, that binding mechanism is fully bypassed.

### Impact Explanation
Any ETH resting in the Emporium contract — which can legitimately accumulate there through the receive() fallback, dust from prior stateless/stateful op sequences, or ETH parked mid-flow for a signed wallet session — can be swept by any attacker who crafts a zero-token `transact` call with an `ops` entry whose `value` equals the target balance and `endpoint` is attacker-controlled. This is direct theft of funds not belonging to the attacker (Critical: direct theft of protocol/other users' in-flight funds), and it is repeatable every time Emporium's ETH balance is nonzero.

### Likelihood Explanation
Preconditions are minimal and attacker-achievable: Emporium must hold ETH > 0 (trivially satisfied — the attacker can even seed it with a plain transfer to demonstrate the bug, though the real target is ETH belonging to others/protocol residue), and the attacker must produce a valid proof for a circuit variant that accepts zero-length token arrays (the "Min" circuit path referenced in the report). The attacker fully controls all `CircomData`/`Dimensions`/`EmporiumStack` fields per the threat model, and the stateless path requires no signature over `ops`. Cost is a single `transact` call with a self-generated proof.

### Recommendation
Do not allow the value-moving ops loop to bypass balance accounting when `erc20TokenAddresses` is empty. At minimum:
- Require that if any `op.value > 0` or any `op.callData` targets a non-allow-listed endpoint, `address(0)` (native ETH) must be present in `circomData.erc20TokenAddresses` so the balance-diff/slippage checks in both `runAction` and `Hinkal.transact` actually execute.
- Alternatively, independently track `address(this).balance` for ETH before/after the ops loop regardless of whether `address(0)` is included in `erc20TokenAddresses`, and revert if it decreases without an offsetting `deltaAmountChanges`/UTXO entry.
- Ensure `verifyWallet` (or an equivalent check) commits to and validates the full `ops` array even in the stateless (`signerAddress == address(0)`) case, so arbitrary unaccounted value transfers cannot be crafted purely by the calling attacker.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a malicious `AttackerEndpoint` contract with a `receive()`/fallback that just accepts ETH.
2. Fund Emporium with ETH: send `X` ETH via plain `.call{value: X}("")` to Emporium's `receive()` (representing residual/other users' parked ETH).
3. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `slippageValues = []`, `onChainCreation = []`, and `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack` with `signerAddress = address(0)`, `ops = [{endpoint: attackerEndpoint, invokeWallet: false, value: X, callData: ""}]`.
4. Generate a valid `MainEVMCircuitMin` proof for this zero-token shape (locally, using snarkjs with the project's circuit build artifacts).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: `attackerEndpoint.balance == X` after the call; Emporium's ETH balance dropped by `X`; and in `Hinkal.transact`, the `newBalances == oldBalances` / `balanceDif` require blocks at lines 111-146 were never entered (loop bound is `circomData.erc20TokenAddresses.length == 0`), confirming the outflow was never checked against any equality.
