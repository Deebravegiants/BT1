### Title
Webhook `shop` (and `topic`/`webhook-id`) fields are trusted by handlers without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header straight into the `WebhookMetadata` object handed to the app's handler. This breaks the identity binding `hmac_signed_bytes == bytes_the_handler_trusts_as_the_tenant_identifier`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then forwards `request.shop` — an unverified header — to the handler as the tenant identifier: [4](#0-3) 

The `WebhookMetadata` struct that the handler receives carries this unauthenticated `shop` value alongside the verified `body`: [5](#0-4) 

This is the same bug class as the referenced report: `getDpxEthPrice`/`getEthPrice` being used for the wrong side of the swap meant a value that *looked* validated wasn't actually the value being acted upon. Here, the HMAC validation gives host applications false confidence that the entire webhook request — including which shop it came from — is authentic, when in fact **only the body bytes** are authenticated; `shop` (the tenant-identifying field the handler dispatches on) is not.

Because the app's `client_secret`/HMAC key is shared across **all shops** that have installed the same app (it is not a per-shop secret), any merchant who installs the app can generate an arbitrarily-bodied webhook with a **valid** HMAC signature for that body (Shopify will sign it, or the merchant can trigger events in their own store to get a real signed payload). That merchant can then replay the identical `body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only recomputes and compares the HMAC of the raw body — it never binds `shop` into the signature: [6](#0-5) 

By contrast, the OAuth callback path in this same library correctly includes `shop` (and `host`, `code`, `state`) inside the signed payload before HMAC verification: [7](#0-6) 

which shows the library's HMAC design elsewhere binds the tenant identifier into the signature — the webhook path does not.

### Impact Explanation
Applications built on this gem typically use `WebhookMetadata#shop` to determine which merchant/tenant an incoming event belongs to (e.g., looking up that shop's stored access token, updating that shop's records, or triggering shop-scoped side effects), trusting that a passing HMAC check means the whole request — including the shop attribution — is authentic. Since `shop` is not covered by the HMAC, any installer of the app can spoof events "from" an arbitrary victim shop domain with an app-chosen body, leading to cross-tenant data injection/confusion in the host application (e.g., poisoning another merchant's order/product data, forging fulfillment or GDPR-mandatory webhook payloads attributed to a shop the attacker doesn't control). This is a cross-tenant boundary violation, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be an installed (unprivileged) merchant of the target app — no access to the app's `client_secret`, no privileged account, and no interception is needed, since the attacker legitimately receives HMAC-signed webhooks for their own shop and can freely alter the (unsigned) `shop-domain` header on replay. This satisfies the "unprivileged internet user" threat model required by scope.

### Recommendation
Bind the tenant-identifying headers into the signed material, or otherwise re-verify `shop` against a source of truth after HMAC validation. Concretely, extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to require that `shop` (and ideally `topic`/`webhook_id`) is derived from data that participates in the HMAC computation — matching the pattern already used for `AuthQuery#to_signable_string`, which incorporates `shop` into the signed payload. At minimum, document/require that host applications independently authorize the incoming `shop` value against their session/tenant store rather than trusting the header solely because `HmacValidator.validate` returned `true`.

### Proof of Concept
1. App `X` uses `ShopifyAPI::Webhooks::Registry.process` with a handler that trusts `WebhookMetadata#shop` to select the tenant record to update.
2. Attacker installs app `X` on their own shop `attacker.myshopify.com` and receives (or triggers) a legitimately-signed webhook: body `B`, header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker resends an HTTP POST to the app's webhook endpoint with the exact same body `B` and header `H`, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares it to `H` — validation succeeds since only `B` is signed: [8](#0-7) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and processes attacker-controlled data as if it came from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
