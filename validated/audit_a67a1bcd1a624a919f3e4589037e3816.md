### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `Registry.process` accepts any request whose body HMAC is valid and passes `request.shop` straight into the handler's `WebhookMetadata`, so an attacker who possesses one valid `(body, hmac)` pair signed with the app's `api_secret_key` can replay it with an arbitrary `shop-domain` header value to make the app believe the event belongs to a different, victim shop.

### Finding Description
`HmacValidator.validate` calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header value using `OpenSSL.secure_compare`: [4](#0-3) 

For webhook requests, `to_signable_string` is defined as just `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic binding to the body or the HMAC: [5](#0-4) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., the body signature) before dispatching the handler with `shop: request.shop` taken verbatim from the header: [6](#0-5) 

The identity equality the code should be enforcing is: `shop asserted by the header == shop the HMAC actually authenticates`. Because the HMAC authenticates only the body bytes, this equality never holds — the header is fully attacker-controlled while the signature validates independently of it. Any body+hmac pair produced by Shopify for one shop (e.g., a shop the attacker legitimately owns/installs the app on, since a public app's `api_secret_key` is shared across all installing shops) remains valid when replayed with a forged `shop-domain` header pointing at an arbitrary victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is meant to enforce: an app relying on `WebhookMetadata#shop` to decide which merchant's data to modify, delete, or resync (e.g., `shop/redact`, `app/uninstalled`, `orders/*`) can be tricked into performing that action against a shop the attacker does not own, using a validly-signed body captured from their own shop's webhook traffic. This is a cross-tenant access/integrity issue reachable by any unprivileged user who can install the public app on their own store and capture one legitimate webhook delivery.

### Likelihood Explanation
Any developer/merchant can install a public Shopify app on their own (free) development store, which causes Shopify to deliver real webhooks — each a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` — to the app's webhook endpoint. Capturing such a pair requires no special privilege beyond normal app installation. Replaying the same body with a different `shop-domain` header is trivial once the endpoint is reachable over the internet, and the gem itself performs no additional binding check.

### Recommendation
Include the shop domain (and ideally topic) in the signed material verified for webhooks, or otherwise cryptographically/contextually bind the `shop-domain` header to the specific installation before trusting it — for example, cross-check `request.shop` against the shop associated with the session/token used to register that specific webhook subscription, or verify the header against Shopify's `X-Shopify-Webhook-Id` combined with a stored expected shop mapping, rather than trusting the header value used only for routing.

### Proof of Concept
1. Install a public Shopify app on an attacker-controlled development store (`attacker-shop.myshopify.com`); this is a normal, unprivileged action.
2. Trigger any registered webhook topic (e.g., `orders/create`) on `attacker-shop`. Capture the resulting POST request: its raw body and the valid `X-Shopify-Hmac-Sha256` header, both signed with the app's real `api_secret_key`.
3. Replay this exact `(body, hmac)` pair to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the (unchanged) body against the (unchanged) hmac.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim-shop.myshopify.com"`, even though nothing about `victim-shop` was ever verified — the app now acts on behalf of a shop the attacker never authenticated as.
