This confirms the vulnerability. The `Request#hmac` field is computed over `shopify_header("hmac-sha256")` and validated against `to_signable_string` which returns only `@raw_body` [1](#0-0) [2](#0-1) . The `shop` field used for tenant identification is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the HMAC signature computation [3](#0-2) . `Registry.process` validates the HMAC over the body only and then dispatches to the handler using `request.shop` as the tenant identifier without any additional binding check [4](#0-3) .

### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from only the raw request body [2](#0-1) , but the `shop` attribute that the registry uses to attribute the webhook to a tenant is taken from an HTTP header (`shopify-shop-domain`/`x-shopify-shop-domain`) that is completely outside the HMAC's coverage [3](#0-2) .

### Finding Description
`HmacValidator.validate` verifies the HMAC by recomputing it over `verifiable_query.to_signable_string` and comparing to `verifiable_query.hmac` [5](#0-4) . For webhook requests, `to_signable_string` returns only `@raw_body` — the `shop`, `topic`, `api_version`, and `webhook_id` fields, which are all sourced from HTTP headers set by the caller, are never part of the signed content [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before dispatching the webhook to the app's handler using `request.shop` as the tenant/shop context passed into `WebhookMetadata` [4](#0-3) . The binding the code implicitly assumes — "the `shop` header equals the tenant that produced the HMAC-signed body" — does not actually hold, because the header is never covered by the signature.

Because webhook HTTP endpoints are exposed to the internet (any host receiving Shopify webhooks must be internet-reachable to receive callbacks), an unprivileged attacker who has captured or replayed one genuine webhook payload+HMAC pair from a shop they control (e.g., their own trial/dev store) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still succeed, since it only re-hashes `@raw_body`, and the handler will process the payload as if it originated from the victim shop named in the header — a cross-tenant data confusion inside the host application's webhook handler.

### Impact Explanation
This breaks the tenant binding `shop authenticated == shop the handler acts on`, since the `shop` value handed to `WebhookHandler#handle` via `WebhookMetadata` is unauthenticated header data [7](#0-6) . Any app whose webhook handler uses `data.shop` to look up per-tenant state, credentials, or to write/merge data keyed by shop (a very common pattern for GDPR "customers/redact", "shop/redact" mandatory topics and ordinary business webhooks) can be made to process an attacker-supplied, HMAC-valid payload under another merchant's identity — i.e., cross-tenant access/confusion.

### Likelihood Explanation
The attacker needs only to be a legitimate Shopify merchant/developer (able to generate at least one real webhook with a valid HMAC using their own store, since `client_secret` is not required — the app owns that secret, but the merchant's own webhook events are HMAC-signed by Shopify with the app's secret and delivered to the app) and network access to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is required; this is reachable by any unprivileged internet user capable of triggering a webhook delivery to themselves and then replaying/relaying it with a modified shop header.

### Recommendation
Include the `shop` (and ideally `topic`/`api_version`) header values in the signable string bound into the HMAC check, or otherwise cross-verify `request.shop` against a value derived from data that is covered by the HMAC before dispatching to the handler, so that the header cannot be altered independently of the signed body.

### Proof of Concept
1. App registers a webhook and receives a genuine delivery for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid over `B`).
2. Attacker (who owns `shop-a` or intercepts/replays this delivery) resends the same `B` and `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `Request#hmac`/`to_signable_string` are computed independent of the shop header [8](#0-7) ; `HmacValidator.validate` returns `true` since it only checks `B` against `H` [5](#0-4) .
4. `Registry.process` proceeds to call the handler with `shop: request.shop` set to `shop-victim.myshopify.com`, even though the signed payload actually originated from `shop-a` [4](#0-3) .
