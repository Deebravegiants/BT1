### Title
Non-embedded session lookup trusts unauthenticated, predictable cookie bytes as the session identifier - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps (and as a fallback for embedded apps without a JWT), `ShopifyAPI::Utils::SessionUtils.current_session_id` resolves the "current session id" directly from a raw, unsigned cookie value, whereas the embedded/JWT path cryptographically derives the session id from an HMAC-signed token. Because this gem also defines the session id format itself as a deterministic function of the shop domain (`"offline_#{shop}"` / `"#{shop}_#{user_id}"`), an attacker who can supply this cookie can make the host application resolve a *different* merchant's session id without ever proving control of that merchant's shop.

### Finding Description
Two code paths exist to compute the acting session id:

1. Embedded / JWT path — cryptographically bound: [1](#0-0) 
Here `shop`/`sub` come from `Auth::JwtPayload`, which verifies the signature against `Context.api_secret_key` before trusting any claim: [2](#0-1) 

2. Cookie path — unauthenticated, used for all non-embedded apps and as the embedded fallback: [3](#0-2) [4](#0-3) 

`cookie_session_id` simply returns `cookies[SessionCookie::SESSION_COOKIE_NAME]` verbatim — there is no HMAC, signature, or any binding of this value to the request/browser that produced it. Compare this to every other identity-carrying value in the gem (webhook HMAC, OAuth `AuthQuery` HMAC, JWT signature) which are all validated with `Utils::HmacValidator` or `JWT.decode` before being trusted.

Making this worse, the gem itself defines the session id as a fully deterministic function of the shop domain, with no random/secret component: [5](#0-4) [6](#0-5) 

The `SessionCookie` struct written after OAuth simply carries this predictable `session.id` value with no cryptographic signing of the cookie itself: [7](#0-6) [8](#0-7) 

The equality this design is supposed to guarantee is:
`session_id_returned_by_gem == session_id_of_the_shop_that_actually_authenticated_via_OAuth`

But the actual guarantee, for the cookie path, is only:
`session_id_returned_by_gem == raw_bytes_of_a_client_supplied_cookie`

Since the value space of valid session ids is public knowledge (`"offline_" + shop_domain`, where `shop_domain` is normally a public/discoverable `*.myshopify.com` name), any client can construct a valid-looking, "current" session id for a shop it does not own, and the gem will hand it straight back to the host application as if it were authenticated.

### Impact Explanation
`current_session_id`/`cookie_session_id` are the gem's documented mechanism for host apps to find "the session for the current request" and subsequently fetch the corresponding `Auth::Session` (containing the merchant's `access_token`) from their session storage: [9](#0-8) 

Because the returned id is (a) unauthenticated and (b) predictable, an attacker who simply sets `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` on a request is handed back the exact storage key for the victim shop's session. If the host loads that session and uses its `access_token` to act on the attacker's request (the intended and documented use of `current_session_id`), this is a cross-tenant access primitive: one merchant's (or any client's) request can be resolved to a completely different merchant's authenticated session and access token, purely from a self-supplied cookie value, with no proof of having gone through OAuth for that shop.

### Likelihood Explanation
The session id format is deterministic and only depends on the public shop domain, which is typically known or trivially guessable (`myshopify.com` subdomains, often the same as the store's own custom domain). No secret, token, or OAuth completion is required to construct a syntactically valid session id — only the ability to set an HTTP cookie header on a request to the app, which is possible for any unauthenticated client making a direct request.

### Recommendation
Do not trust the raw cookie value as the effective session id. Either:
- Sign/HMAC the cookie value (using `Context.api_secret_key`) when writing it in `Oauth.validate_auth_callback`, and verify that signature in `SessionUtils.cookie_session_id` before returning it, mirroring what is already done for `AuthQuery` and `Webhooks::Request`; or
- Make session ids non-deterministic (include a random component) so they cannot be guessed/constructed without having completed OAuth, and bind the returned id to additional server-side session state (e.g., a nonce set during `begin_auth` and checked here) rather than trusting the cookie contents outright.

### Proof of Concept
1. App is configured as non-embedded (`is_embedded: false`), using `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` per the documented pattern.
2. Attacker sends a request to any endpoint of the host app with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. `SessionUtils.current_session_id` → `cookie_session_id` returns `"offline_victim-shop.myshopify.com"` unchanged, with no verification: [10](#0-9) 
4. The host application (following the gem's documented pattern) loads the `Auth::Session` for that id from its session storage and uses its `access_token` to serve the attacker's request — granting the attacker access to `victim-shop`'s data using the app's stored credentials for that shop, despite the attacker never completing OAuth for `victim-shop`.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end

            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

          end
        end

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
