### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated for a given shop purely because the HMAC check passes, but the HMAC is computed only over the raw request body, not the `shop-domain` header that the library trusts as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. The `shop` accessor, however, is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: ` [2](#0-1) `.

`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)` — which only checks the HMAC against `to_signable_string` (i.e., the body) — and then immediately forwards `request.shop` to the app's handler as the authenticated tenant identifier, with no additional binding between the shop header and the signed payload: ` [3](#0-2) `. `HmacValidator.validate` itself only compares the computed signature of `to_signable_string` against the received `hmac`, and never inspects or incorporates the shop header: ` [4](#0-3) `.

`WebhookMetadata.shop` is then passed straight through to the app-supplied handler as trusted tenant context: ` [5](#0-4) `, and the library's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with `data.shop` as the shop domain: ` [6](#0-5) ` ` [7](#0-6) `.

The identity binding this breaks, expressed as an equality that the library implies but does not enforce:
`shop attributed by Registry.process(request) == shop cryptographically bound to the signed payload`

In fact, `shop attributed` is read from a header outside the HMAC's protected byte range, while `shop bound to the signature` is nothing at all — the signature only certifies the body's authenticity, and Shopify's own real webhook delivery mechanism does put the shop domain in a header (consistent with real Shopify behavior), but this gem exposes that header to the handler as if the whole `Request` object — including `shop` — were HMAC-verified.

### Impact Explanation
An attacker who runs their own store (thus legitimately receiving valid, Shopify-signed webhooks for their own shop, e.g. `orders/create`) can capture a webhook's raw body and its accompanying valid `hmac-sha256` value, then replay that exact `(raw_body, hmac)` pair to the victim app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g. a victim shop the attacker wants to target, or an arbitrary string). `HmacValidator.validate` still succeeds because it only checks the body against the HMAC, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen value. Any app logic keyed on `data.shop` (as directed by the gem's own webhook documentation) — for example writing/merging order or product data into per-shop tenant storage — can be corrupted or misattributed to a shop the attacker does not own, resulting in cross-tenant data contamination/access without needing the target's access token or `client_secret`.

### Likelihood Explanation
Moderate-to-high: any unprivileged internet user can install the target app on their own (attacker-controlled) trial/dev shop to obtain legitimately signed webhook payloads, then freely replay them with a forged shop header to the app's public callback URL, since nothing about `Request`/`Registry.process` binds the shop identity to the signature. This requires no secrets beyond what any app installer already receives.

### Recommendation
Bind the shop identity into the value that is actually authenticated: either include the shop domain (and ideally topic/webhook-id) in the signable string used for HMAC validation, or, at minimum, have `Registry.process` cross-check `request.shop` against an already-known/authorized shop (e.g. an existing session record) rather than passing the raw header value through unchecked to `WebhookMetadata`. Document explicitly that `request.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for `orders/create` webhooks.
2. Shopify delivers a webhook to the app with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
3. Attacker captures `raw_body` and `shopify-hmac-sha256` value.
4. Attacker sends a new HTTP POST to the app's webhook endpoint with the same `raw_body` and same `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: ` [8](#0-7) `.
6. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, and processes/stores the (attacker-controlled) body under the victim's tenant context.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
