### Title
Unauthenticated runtime-call dispatch as an arbitrary account via unsigned `SubstrateCalldata` in `hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`on_accept` in the `hyper-fungible-token` ISMP module executes an attacker-supplied `runtime_call` under `RawOrigin::Signed(origin)`, where, on the "no signature" branch, `origin` is derived straight from the message's `from` field rather than from any cryptographically verified identity [2](#0-1) . That `from` field is part of the ABI-encoded `Message` body dispatched from the EVM contract, where it is fixed at `msg.sender` inside `_buildDispatchPost` for genuine bridge sends [1](#0-0) . However, `on_accept`'s authentication only checks the ISMP `request.from`/`source` against `ContractToAsset` to authorize which token contract is allowed to mint — it never checks that `message.from` (the business-layer sender embedded in the ABI-encoded body) equals `request.from` or any other cryptographically-bound value [3](#0-2) .

### Finding Description
Any registered EVM `HyperFungibleToken` contract on the source chain is a general-purpose relay for ABI-encoded `Message{from, to, amount, data}` payloads; nothing on that chain forces `Message.from` to equal `msg.sender` except the specific `send()` codepath. Since Hyperbridge routes cross-chain apps by contract "module id" (source address), any code that can get itself registered as, or spoof the address of, an EVM `HyperFungibleToken`/token contract for a given chain (or any future/alternate frontend to this pallet that constructs the same ABI-encoded body) determines `message.from` arbitrarily.

More fundamentally: the destination pallet's own authentication model treats `message.from` as trusted identity data for privileged dispatch (`RawOrigin::Signed(origin)`), but the only authentication actually performed on the incoming ISMP request is over `request.from`/`source`(which chain a request came from and which contract sent it) — it never binds `message.from` to `request.from`. So if `message.from` differs from the real EVM sender that dispatched the underlying transfer (which is entirely legal ABI — nothing in the wire format, at the pallet's decode layer, enforces `message.from == request.from`), the pallet will:

1. Mint/transfer tokens to `message.to` (the beneficiary) — normal behavior.
2. If `message.data` is non-empty and decodes to a `SubstrateCalldata` with `signature: None`, derive a dispatch origin purely from `message.from` (EVM-address-to-substrate-account conversion, or a raw 32-byte copy for non-EVM sources) [4](#0-3) .
3. Dispatch the attacker's `runtime_call` as `RawOrigin::Signed(origin)`, subject only to the runtime's `BaseCallFilter` [5](#0-4) .

Because `origin` is not proven to be controlled by whoever actually dispatched the message (no signature is required on this branch, and `message.from` is attacker-supplied wire data, not a chain-verified sender identity), this is an unauthorized-action / spoofed-origin primitive: an attacker able to dispatch a POST from a chain/contract this pallet trusts for token transfers can pick `message.from` to be any account (or any EVM address, converting to any substrate account) and cause a runtime call to execute as that account.

### Impact Explanation
This allows dispatching arbitrary permitted runtime calls (anything not excluded by `BaseCallFilter`) on behalf of any account on the destination substrate chain, without that account's authorization, purely by controlling the `from` field of an ABI-encoded cross-chain message. Depending on what dispatchables the runtime's `BaseCallFilter` allows, this ranges from account nonce/state griefing to spending/approving assets, governance voting, or other privileged actions attributed to a victim account — i.e., unauthorized app action performed on behalf of arbitrary users, which the "Validate" criteria call out explicitly ("unauthorized app action").

### Likelihood Explanation
Reachable from a single relayed/dispatched cross-chain POST request through the pallet's `on_accept`, which is exactly the "handle_unsigned"/dispatch entry point pattern the scan rules call reachable. It requires only that an attacker can get a POST accepted from a source chain/contract pair registered in `ContractToAsset` with attacker-controlled `message.from` and `message.data` — no privileged role, no signature, no governance action needed on the destination side.

### Recommendation
Do not trust `message.from` as an authenticated identity for dispatching calls. Either (a) always require and verify `substrate_data.signature` before dispatching any `runtime_call` (never allow the unsigned branch to derive an origin from unauthenticated payload data), or (b) bind `message.from` cryptographically to the actual ISMP request sender (e.g., require `message.from == request.from` when `from`/`source` denotes a single EOA-equivalent identity, and only allow the unsigned convert-from-EVM-address path when that address is provably `msg.sender` on the source chain, e.g., by having the EVM contract itself sign or by removing the unsigned dispatch path entirely and mandating a signature check for any calldata execution).

### Proof of Concept
1. Attacker controls (or spoofs, if reachable) a source-chain call path into a registered `HyperFungibleToken`-compatible contract/module that can construct and dispatch an ABI-encoded `Message` where `from` is set to bytes representing a victim's EVM address (e.g., 20 bytes of the victim's address) rather than `msg.sender`.
2. Attacker sets `data` to a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary allowed call> }`.
3. On the destination chain, `on_accept` mints tokens to `message.to`, then decodes `SubstrateCalldata`, takes the `signature: None` branch, converts the victim's EVM address in `message.from` to a substrate `AccountId` via `EvmToSubstrate::convert`, and dispatches `runtime_call` as `RawOrigin::Signed(victim_account)` [6](#0-5) .
4. The victim's account executes an action it never authorized.

Note: I was unable to fully verify whether every EVM-side deployment path (including `HyperFungibleTokenUpgradeable.sol`, which I did not have time to inspect) rigidly enforces `from == msg.sender` for all message-construction call sites, or whether `ContractToAsset` registration is itself permissioned in a way that prevents an attacker from ever controlling a trusted source/from pair with attacker-chosen `message.from`. If registration of `ContractToAsset` entries is fully governance-gated and every legitimate frontend contract enforces `from == msg.sender` with no alternate/legacy path, the practical attack surface narrows to any future or non-audited frontend to this pallet; the root-cause issue — that the pallet's dispatch-origin derivation trusts unauthenticated payload data on the unsigned branch — stands regardless.
