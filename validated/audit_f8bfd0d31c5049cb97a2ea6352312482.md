## Analysis

The external report's bug class is about a check that can behave inconsistently for a value that flows through code without being properly bound to what was actually authenticated. Mapping this to the gem, the closest concrete analog is in the webhook processing pipeline: the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, but the `shop` (tenant identity) used downstream is taken from an HTTP header that is never covered by that signature. ### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [4](#0-3) , so `Utils::HmacValidator.validate` authenticates the body bytes only [3](#0-2) . However `Registry.process` trusts `request.shop`, which is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header [5](#0-4) , and passes it unchecked into the `WebhookMetadata` delivered to the app's handler [2](#0-1) . The identity binding `shop authenticated == shop acted upon` does not hold: the HMAC authenticates "these bytes were signed with the app's client_secret," while the code acts on "whatever shop-domain header came with the request," which is a disjoint, unauthenticated field.

### Finding Description
Because the app's webhook HMAC secret (`client_secret`) is shared across every shop that installs the app, any merchant who legitimately installs the app receives genuinely-signed webhook deliveries for their own shop. Since the signature covers only the JSON body and never the `shop-domain` header, an attacker who controls a shop (or otherwise obtains one valid `(body, hmac)` pair) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in `X-Shopify-Shop-Domain`. `Registry.process` will pass HMAC validation (the body and signature still match) and forward the attacker-chosen `shop` value straight to the registered handler as if it were an authenticated fact [2](#0-1) . Nothing in this gem cross-checks the header-derived shop against the set of shops that actually have the app installed, or binds it into the signed payload.

### Impact Explanation
Applications built on this gem commonly key their persisted data (sessions, tokens, installation state) by the `shop` value delivered in webhook metadata — for example handling `app/uninstalled`, `shop/redact`, or `customers/redact` topics. Because `shop` is not authenticated, an attacker can make the app believe a webhook (with attacker-controlled/replayed body content) originated from a victim shop, leading to cross-tenant confusion/actions (e.g., triggering uninstall cleanup, data-redaction logic, or state changes) against a tenant the attacker does not control. This falls under cross-tenant access, a Critical-impact category per the scope rules.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate installation of the target app on any shop (to obtain one valid `(body, hmac)` pair for a chosen topic), and (2) sending a forged HTTP request to the app's public webhook endpoint with the captured body/HMAC but a different `shop-domain` header — no access to `api_secret_key`, tokens, or privileged accounts is needed. This is a realistic capability for any unprivileged internet user who can install a public app on a free/trial store.

### Recommendation
Do not treat the header-derived `shop` as authenticated by HMAC verification alone. At minimum, document/require that consuming applications cross-reference `WebhookMetadata#shop` against their own record of installed shops (mapped by `webhook_id`/subscription rather than by trusting the header), and consider incorporating the shop domain into the value that is verified (e.g., validating it against `ShopifyAPI::Utils::ShopValidator` and treating it as untrusted input until corroborated by the app's own session store) before using it for any privileged or tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a genuine webhook delivery (e.g., `app/uninstalled`) with body `B` and header `X-Shopify-Hmac-Sha256: H` — `H` is valid because the signature covers only `B`.
2. Attacker sends a POST to the app's public webhook route with the same raw body `B`, the same header `H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `B` against `H` — this passes [6](#0-5) .
4. `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: ..., ...)` is forwarded to the app's handler, which acts as if the (possibly destructive) event genuinely came from `victim-shop.myshopify.com` [7](#0-6) .
