Audit Report

## Title
Unsynchronized read of `authorizedKeys` map in `WorkflowMetadataHandler.Authorize` races with concurrent `syncMetadata` writes, allowing signer authorization bypass or panic under concurrent HTTP trigger requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` at [1](#0-0)  without acquiring `h.mu`, while the background `syncMetadata` goroutine replaces the entire `h.authorizedKeys` map under `h.mu.Lock()` at [2](#0-1) . This is a genuine data race between an unlocked reader and a locked writer of the same map field, which can cause a Go runtime fatal crash (`fatal error: concurrent map read and map write`) or undefined read behavior during the authorization check.

## Finding Description
`Authorize` is called on every incoming HTTP trigger request to validate whether a signer's key is authorized for a `workflowID`. The lookup `keys, exists := h.authorizedKeys[workflowID]` at [1](#0-0)  accesses the map field directly with no lock. Meanwhile `syncMetadata`, invoked periodically via `h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)` at [3](#0-2) , reassigns `h.authorizedKeys = authorizedKeys` under `h.mu.Lock()` at [4](#0-3)  and [5](#0-4) . Every other accessor of the protected fields — `WorkflowShards` [6](#0-5) , `GetWorkflowID` [7](#0-6) , and `GetWorkflowReference` [8](#0-7)  — correctly takes `h.mu.RLock()`. `Authorize` is the sole outlier. This confirms the broken security assumption: `h.mu` is meant to protect all reads/writes of `authorizedKeys`, `workflowRefToID`, `workflowIDToRef`, and `workflowShards`, but `Authorize` bypasses it entirely.

## Impact Explanation
This is a genuine, reproducible Go data race (confirmable with `go test -race` or `go build -race`) on a map field that is read unsynchronized in `Authorize` while concurrently reassigned wholesale under lock in `syncMetadata`. The concrete, realistic in-scope impact is availability: an unlucky interleaving during the map header swap can, under Go's runtime, trigger `fatal error: concurrent map read and map write`, crashing the gateway process — a DoS reachable by any client sending ordinary HTTP trigger requests while the periodic sync ticker fires. This maps to the "unauthorized action / instability of gateway request handling" category. The claim's secondary suggestion of an authorization-bypass consequence (returning a stale/garbage `keys` map due to lack of synchronization) is a real theoretical possibility of unsynchronized map access in Go, though the primary demonstrable defect is the race itself.

## Likelihood Explanation
`syncMetadata` runs unconditionally on a fixed ticker for the lifetime of the handler (`MetadataAggregationIntervalMs`, default 60000ms per [9](#0-8) ), and `Authorize` is invoked on every unprivileged HTTP trigger request. Any gateway under sustained request traffic will periodically race the sync tick, making the crash condition reachable without special timing control — pure request volume increases the probability of a hit.

## Recommendation
Take `h.mu.RLock()`/`RUnlock()` in `Authorize` around the read of `h.authorizedKeys[workflowID]`, mirroring `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. Since `syncMetadata` replaces the inner map wholesale rather than mutating it in place, it suffices to snapshot the `keys` reference under the read lock before releasing it and performing the membership check outside the lock.

## Proof of Concept
1. Configure a `WorkflowMetadataHandler` with a short `MetadataAggregationIntervalMs` (e.g., 10ms) so `syncMetadata` continuously rebuilds `h.authorizedKeys` via the ticker started in `Start`/`runTicker`.
2. From a separate goroutine, repeatedly call `Authorize(workflowID, validToken, req)` in a tight loop, simulating concurrent unprivileged HTTP trigger requests.
3. Run under `go test -race`; the race detector will flag the unsynchronized read at line 92 against the locked write at line 178, and under sufficient load the process can hit `fatal error: concurrent map read and map write`.
