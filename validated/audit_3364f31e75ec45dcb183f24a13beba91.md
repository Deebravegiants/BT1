### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body only and then forwards `request.shop` (and `request.topic`) unchecked to the handler as the tenant identifier, exactly matching the analog bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhook requests that method returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id` and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then unconditionally forwards `request.shop` as the tenant-identifying field consumed by the app's handler: [4](#0-3) 

This creates the equality break the rules describe: **the field the application acts on (`shop`) ≠ the bytes the HMAC actually authenticates (`raw_body` only)**. Because a single app-level `api_secret_key` is shared across *every* shop that has installed the app, any shop that has installed the app can legitimately receive real webhook deliveries with valid `(raw_body, hmac)` pairs signed by that shared secret. Nothing in `HmacValidator.validate` or `Request` ties the signed body to the `shop-domain` header, so the same valid `(body, hmac)` pair remains "valid" when replayed with an arbitrary `X-Shopify-Shop-Domain` header value substituted in.

### Impact Explanation
This is a cross-tenant confusion vector (High/Critical bucket "cross-tenant access"): a shop that has installed the app — a low-privilege, unauthenticated-relative-to-other-tenants actor — can capture a validly-signed webhook payload for its own store and resubmit it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a *different* installed shop. Because `Registry.process` never checks that `request.shop` is bound to the HMAC, the app has no way to detect the substitution and will hand off attacker-influenced body content to the handler under the identity of the victim shop. Any downstream logic keyed off `data.shop` (e.g. looking up the victim's session/access token, writing records under the victim's tenant, triggering side effects scoped to the victim) is exposed to cross-tenant data injection.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to control (or have installed) the app on at least one shop to receive genuinely-signed webhook traffic, and the webhook `topic`/body content is otherwise fairly constrained by what Shopify's platform actually sends for that topic (limiting free-form injection). However, no additional secret, token, or elevated privilege is required beyond ordinary app installation, and the vulnerable code path (`Request#to_signable_string`, `Registry.process`) is exercised on every webhook delivery this gem's users implement per the documented pattern in `docs/usage/webhooks.md`.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the signable string (or otherwise cryptographically bind the header set to the body before computing the HMAC), and/or require host applications to cross-check `request.shop` against a per-shop-known value rather than trusting the raw header unconditionally. At minimum, document prominently that `data.shop` is unauthenticated and must be re-validated by the host app before being used to select tenant context.

### Proof of Concept
1. App is installed on Shop A and Shop B, sharing the same `api_secret_key`.
2. Attacker (owner/operator of Shop A) triggers a webhook event on Shop A and captures the resulting HTTP request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker resends this exact `(B, H)` pair to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with `shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC_SHA256(api_secret_key, B)`, which still equals `H` since the signable string never included the shop header — validation passes.
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)`, i.e., Shop A's captured payload is now processed under Shop B's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
