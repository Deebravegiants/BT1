### Title
`placeOrder` predispatch escrow crediting trusts absolute dispatcher balance instead of the delta actually contributed for the order - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` (Tron variant) credits an order's escrow based on the *absolute* token/native balance sitting on the shared `_params.dispatcher` contract after predispatch execution, rather than the amount actually contributed for that specific order. This is the same "balance check instead of accounted amount" bug class as the AuctionHouse M‑01 finding, where `address(this).balance` was checked against `reservePrice` instead of the tracked `_auction.amount`, letting a donated balance stand in for a legitimate bid.

### Finding Description
In `placeOrder`'s predispatch branch, the caller-controlled `order.predispatch.call` is dispatched through a single, protocol-wide `dispatcher` (`_params.dispatcher`), shared by every user who places an order with predispatch calldata: [1](#0-0) 

Escrow crediting then measures how much to sweep and how much to record as "dust" purely from the dispatcher's current, absolute balance: [2](#0-1) 

`balance = address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)` is not the amount the caller contributed in this transaction — it is whatever total sits on the shared `dispatcher` address at that moment, which is externally influenceable: any ordinary token transfer or forced ETH send (e.g. `selfdestruct`) to `dispatcher` by any third party, or leftover balance from another in-flight/prior predispatch execution, inflates this figure. Because `predispatch.assets[i].amount` has no zero-amount guard in this variant (unlike the sibling fix), a caller can supply `amount = 0` for the predispatch transfer while still passing the `balance >= requiredAmount` check purely off pre-existing/donated balance, then have the entire swept balance credited to `_orders[commitment][token] += reducedInputs[i].amount` for their own order.

The maintained EVM contract explicitly fixes this exact pattern by snapshotting per-token balances *before* the predispatch dispatch call and crediting only the measured delta: [3](#0-2) 

The Tron contract was never updated to this delta-based accounting, and additionally lacks the `nonReentrant` guard present on the fixed version's `placeOrder`: [4](#0-3) [5](#0-4) 

The missing reentrancy guard compounds the issue: since `order.predispatch.call` is caller-supplied and dispatched via `ICallDispatcher(dispatcher).dispatch(...)`, a malicious predispatch call can re-enter `placeOrder` (or otherwise manipulate `dispatcher`'s balance) mid-flight, further decoupling the swept "balance" from what was actually contributed for the order being processed.

### Impact Explanation
An attacker can get an order's `_orders[commitment][token]` escrow entry credited with an amount backed by donated or pre-existing balance on the shared `dispatcher`, rather than assets they actually escrowed for that order. Once such an order is later filled cross-chain, `onAccept`/`withdraw()` pays the solver the escrowed input based on this unbacked credit — the protocol effectively mints/authorizes a withdrawal of tokens that were never legitimately deposited for that order, resulting in fund loss to the protocol/solver or to whichever party's balance was actually swept from the shared dispatcher. This is a concrete theft / unbacked-escrow vector on a path (`placeOrder`) directly reachable by any unprivileged user with a single transaction.

### Likelihood Explanation
Likelihood is high for anyone who places an order using the predispatch feature: the shared, protocol-wide `dispatcher` address is a known, callable target that can be pre-funded with a plain ERC20 transfer or a forced ETH send (`selfdestruct`) with no special privileges required, and `order.predispatch.assets[i].amount` is not validated to be non-zero, so an attacker fully controls how little they actually contribute versus how much they claim as `order.inputs[i].amount`.

### Recommendation
Adopt the same fix already present in the maintained EVM contract: snapshot each token's/native balance on the dispatcher (and on `address(this)`) immediately before executing `order.predispatch.call` and the subsequent sweep, then credit escrow strictly by the measured delta (`received = balanceAfter - balanceBefore`) rather than the absolute post-call balance. Additionally, add `nonReentrant` to `placeOrder` in the Tron contract and reject zero-amount predispatch asset entries, matching `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker identifies the shared `dispatcher` address returned by `_params.dispatcher` in the Tron `IntentGatewayV2`.
2. Attacker sends `requiredAmount` worth of the target `token` (or native ETH via a `selfdestruct`-backed contract) directly to `dispatcher`, independent of any order.
3. Attacker calls `placeOrder` with `order.predispatch.call` set to a no-op/valid call, `order.predispatch.assets[i].amount = 0` for that token, and `order.inputs[i].amount = requiredAmount`.
4. In the sweep loop (`evm/tron/contracts/apps/IntentGatewayV2.sol:416-446`), `balance = IERC20(token).balanceOf(dispatcher)` (or `.balance` for native) already equals `requiredAmount` from step 2, so `balance < requiredAmount` is false; the full balance is swept to the gateway and `_orders[commitment][token]` is credited with `reducedInputs[i].amount`, even though the attacker contributed nothing for this specific order via `predispatch.assets`.
5. A solver later fills this order in good faith, and on settlement the escrowed (unbacked) amount is released to the solver/beneficiary, completing the theft/mismatch between claimed and actually-deposited funds.
