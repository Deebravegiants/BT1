## Analysis

The external bug's core custody invariant is: **a batch of independent value-transfers must all succeed atomically, and a single non-cooperating leg can permanently lock funds belonging to unrelated parties.** I traced this pattern through several Aptos custody flows (delegation pool withdrawals, multisig execution, managed fungible-asset batch ops) and found the strongest, self-contained analog in `aptos_framework::staking_contract`'s and `aptos_framework::vesting`'s **unconditional payout loops over a shares pool**, which call `aptos_account::deposit_coins` per recipient with no isolation between recipients.

### Title
Unprivileged shareholder can permanently freeze all co-shareholders' staking rewards by blocking the shared `distribute` payout loop - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` and `vesting::distribute` both redeem an entire shares-based distribution pool in a single atomic loop, pushing coins to every shareholder via `aptos_account::deposit_coins`. Neither function isolates failures per recipient. If `deposit_coins` aborts for any one recipient, the whole transaction — and thus the payout for every other recipient — reverts. This function is not only called by the permissionless `distribute()` entrypoint but is also a required internal step of `request_commission`, `unlock_stake`, and `switch_operator`, so one poisoned recipient blocks the entire staking/vesting contract's custody operations, not just their own withdrawal.

### Finding Description
`distribute_internal` in `staking_contract.move` drains the stake pool's inactive/pending_inactive balance and then iterates over every shareholder with a nonzero share in `distribution_pool`, redeeming their shares and depositing coins in one unbroken loop: [1](#0-0) 

Critically, `distribute_internal` is invoked as a mandatory precondition ("Force distribution of any already inactive stake") from `request_commission`, `unlock_stake`, and `switch_operator` — meaning any of these unrelated operations will also abort if the loop cannot complete: [2](#0-1) [3](#0-2) [4](#0-3) 

The identical pattern exists in `vesting::distribute`, which loops over `grant_pool.shareholders()` and deposits to each, with no ability to skip a failing recipient: [5](#0-4) 

The framework's own formal-verification spec acknowledges this exact gap ("Can't handle abort in loop"), confirming the code path is unverified/unbounded with respect to per-recipient abort behavior: [6](#0-5) 

The payout uses `aptos_account::deposit_coins`, whose module declares `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, i.e., it can abort when the destination account exists, has not pre-registered a `CoinStore<AptosCoin>`, and has disabled arbitrary direct coin transfers via its own `DirectTransferConfig`: [7](#0-6) [8](#0-7) 

Because this configuration flag is unilaterally controlled by the recipient account itself (any staker, or any vesting shareholder), a shareholder can independently flip themselves into a state where `deposit_coins` aborts on them — permanently corrupting the shared payout loop for every other legitimate party sharing the same `distribution_pool` / `grant_pool`.

### Impact Explanation
Once a poisoned shareholder holds any nonzero share of the `distribution_pool` (staking_contract) or `grant_pool` (vesting), every subsequent call to `distribute`, `request_commission`, `unlock_stake`, or `switch_operator` for that staker/operator pair (or vesting contract) will revert at the `deposit_coins` step. This locks the pending rewards of ALL co-shareholders/operator — parties who have no relationship to the poisoning shareholder and no way to remove them from the pool, since removal only happens by fully redeeming their shares via the very same loop that is now unexecutable. This is a permanent, non-recoverable freeze of custody-held APT rewards for uninvolved third parties — a direct match to the external bug's "funds stuck if one withdrawal request cannot be finalized" pattern, since the corrupted value here is the entire shared `distribution_pool`/`grant_pool` balance, not merely the misbehaving party's own funds.

### Likelihood Explanation
The trigger requires only a standard account-level toggle (opting out of unsolicited direct coin transfers while not holding a pre-registered `CoinStore<AptosCoin>`), performable by any of the pre-existing shareholders/operator/staker without any elevated privilege. No external protocol dependency, oracle, or malicious governance action is required — it is entirely self-contained in framework Move code and can be triggered any time after a shareholder is added to the pool.

### Recommendation
Make the payout loop resilient to a single failing recipient: wrap each `aptos_account::deposit_coins` call so that failures are isolated (e.g., attempt registration/deposit defensively, or fall back to crediting an on-chain claimable balance / `CoinStore` bypass such as `coin::deposit` semantics that don't require opt-in) rather than aborting the whole batch. Alternatively, process each shareholder's payout as an independent sub-transaction/resource so that one recipient's inability to receive funds cannot block distribution to the rest of the pool.

### Proof of Concept
Not executed (static analysis only, ask-only mode). Conceptual PoC:
1. Staker creates a `staking_contract` with an operator and additional stake from a second delegator/staker path that ends up as a shareholder in `distribution_pool` (e.g., via `unlock_stake`, which calls `add_distribution`).
2. The malicious shareholder calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account and ensures they have no `CoinStore<AptosCoin>` registered.
3. Any party calls `staking_contract::distribute`, `request_commission`, `unlock_stake`, or `switch_operator`; `distribute_internal`'s loop reaches the poisoned shareholder and `aptos_account::deposit_coins` aborts, reverting the whole transaction.
4. All other shareholders' and the operator's already-inactive rewards remain permanently locked in the stake pool, unretrievable through any of the four entrypoints.

Note: I was unable to execute this in a live Move test harness under ask-only mode; the abort condition for `deposit_coins` is inferred from the error constant and partial function body I could read [8](#0-7)  — the full body of `deposit_coins` (and confirmation of the exact abort branch) should be verified in a Devin session with full file access before treating this as fully confirmed.
