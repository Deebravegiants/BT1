### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted by `Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `HmacValidator.validate` only checks that HMAC against the body [1](#0-0) . The `shop`, `topic`, and `webhook_id` values consumed downstream come exclusively from HTTP headers that are never included in the signed material [2](#0-1) . `Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` handed to the app's handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop that authorized/produced the signed body == shop attributed to the webhook event`. Because `to_signable_string` returns only `@raw_body` [1](#0-0) , the HMAC computed by `HmacValidator.compute_signature`/`validate_signature` binds only the body bytes to the shared secret [4](#0-3) . The `shop`, `topic`, and `webhook_id` accessors read straight from attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are never fed into the signable string [2](#0-1) .

`Registry.process` does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [3](#0-2) 

So the only thing cryptographically verified is "this body was HMAC-signed with our secret at some point" — not which shop or topic that body belongs to. Any party who can obtain one valid `(body, hmac)` pair signed with the app's secret (e.g., a merchant who installed the app on their own store legitimately receives such a webhook from Shopify, or any observer of a webhook delivery) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it never inspects headers, and the handler will be invoked believing the event originated from the attacker-chosen shop.

This is the direct analog of the reported bug class: a field that is *acted on* by downstream logic (`shop`, used to attribute/route the webhook data) is not covered by the integrity check (the HMAC), exactly like the `interfaceId` compatibility flag that is checked against the wrong branch and produces an incorrect trust decision.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to look up/update per-tenant state (the documented purpose of webhook processing — attributing an event's `body` to `shop`), a replayed cross-tenant request lets an attacker cause the app to process another shop's webhook body under a shop identifier of the attacker's choosing (or vice versa: attribute their own data to a victim shop's identifier). This crosses the tenant boundary this gem is responsible for enforcing via `HmacValidator`, since the shop value handed to the app is not authenticated at all — it is bound to nothing.

### Likelihood Explanation
Requires only a previously observed/legitimate `(body, hmac)` pair (e.g., from a webhook the attacker's own store received, since a merchant can install the target app and generate/observe such webhooks without any special privilege) and network access to the app's webhook endpoint; no `api_secret_key` or access token is needed to mount the replay itself, only knowledge of one valid signed body captured from normal use.

### Recommendation
Include the identity-binding headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signed material verified by `HmacValidator`, or otherwise independently authenticate `shop`/`topic` (e.g., cross-check against a value embedded in the signed body, or require the caller to additionally validate the shop against session/install records) before trusting them in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives one legitimate webhook, capturing `raw_body` and its valid `x-shopify-hmac-sha256` header (both are visible to the receiving app, i.e., accessible to anyone who controls a store where the app is installed).
2. Attacker replays the exact same `raw_body` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the secret and passes [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, so the app processes attacker-controlled data under the victim shop's identity [6](#0-5) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
