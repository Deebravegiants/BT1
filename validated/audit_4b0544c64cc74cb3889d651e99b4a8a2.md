### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable payload from the raw HTTP body only, while the `shop` (tenant) and `topic` values are read from unauthenticated HTTP headers and forwarded to the caller's handler as if they had been verified.

### Finding Description
`Webhooks::Registry.process` verifies a webhook by calling `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [1](#0-0) 

`Request#to_signable_string`, which is the only input to the HMAC comparison in `HmacValidator.validate_signature`, returns just `@raw_body`: [2](#0-1) 

Meanwhile `shop` and `topic` are pulled straight from the `shopify-shop-domain` / `shopify-topic` (or `x-shopify-*`) headers, which are never mixed into the signed string: [3](#0-2) 

`HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (i.e., the body), never over the headers: [4](#0-3) 

The binding that should hold is:
`hmac_verified(bytes) == bytes_the_app_attributes_to(shop, topic)`

but in this code the equality actually enforced is only `hmac_verified(raw_body) == raw_body`; `shop` and `topic` are bytes that are *parsed* but never *verified*. This is exactly the "bytes verified versus bytes parsed" identity-binding gap called out in scope: an attacker who can obtain any single legitimate `(raw_body, hmac)` pair produced with the app's own `client_secret` (e.g., because they are a merchant who installed the app on their own store and thus legitimately receive real webhook deliveries for it) can replay that exact body/HMAC pair to the app's webhook endpoint while freely rewriting the `shopify-shop-domain` and `shopify-topic` headers to any value, since the gem never checks that those headers are consistent with the signed content.

### Impact Explanation
`Registry.process` hands the attacker-chosen `shop` value straight to the host application's webhook handler as an "authenticated" tenant identifier once `HmacValidator.validate` returns true. Any consumer of this gem that relies on `WebhookMetadata#shop` (as documented) to select which merchant's data/session the webhook body belongs to will attribute attacker-controlled, replayed content to a shop the attacker does not own — a cross-tenant confusion condition rooted entirely in this gem's own `Request`/`Registry`/`HmacValidator` code, not in host-application misuse.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(body, hmac)` pair signed with the app's `client_secret`. This is realistically obtainable without ever learning the secret itself: any merchant who installs the app on their own (possibly free/dev) store receives real, correctly-signed webhook deliveries from Shopify for that store. Because the gem's verification never binds `shop`/`topic` to the signature, that merchant can trivially replay the captured request against the app's webhook endpoint with a forged `shopify-shop-domain` header naming a different, victim shop.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the string that is HMAC-signed/verified, or otherwise cross-check the header-derived `shop`/`topic` against the value in the parsed body / a separately authenticated channel before handing them to the handler as trusted identifiers. At minimum, document clearly that `request.shop` and `request.topic` are not covered by the HMAC and must not be treated as authenticated by callers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify delivers a real webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)` — valid per `lib/shopify_api/utils/hmac_validator.rb`.
2. Attacker resends the exact same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb:190` succeeds because it only checks `H` against `B` (`to_signable_string`), which is unchanged.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198`), causing the app to process/store attacker-supplied content under the victim tenant's identity.
