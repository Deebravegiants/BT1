### Title
Bad-debt wipeout clamps `supply_index` to a floor instead of zeroing shares, leaving phantom supplier claims that drain future deposits - (File: contracts/pool/src/interest.rs)

### Summary
Analogous to CVE-2020-27815 (attacker-controlled input corrupts kernel memory state beyond its intended bounds), `apply_bad_debt_to_supply_index` corrupts the pool's accounting state when socialized bad debt meets or exceeds total supplied value: it clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) rather than zeroing supply shares. Every pre-existing supplier keeps a live claim worth `shares × RAY/1000`, payable in real tokens against future liquidity.

### Finding Description
`apply_bad_debt_to_supply_index` (`contracts/pool/src/interest.rs:73-89`) computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)`, derives `reduction_factor = remaining / total_supplied_value`, and sets `supply_index = supply_index * reduction_factor`. When bad debt ≥ total supplied value, `reduction_factor = 0`, but the result is clamped: `set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)))`. The shares (`cache.supplied`) are untouched, so each wiped-out supplier retains a positive `unscale_supply_floor` claim.

The path is reachable by an unprivileged caller: the in-scope `clean_bad_debt` entrypoint on the controller emits `PoolSeizeEntry { side: Borrow, scaled_amount }`, and `pool::ops::seize::apply` (`contracts/pool/src/ops/seize.rs:18-34`) computes `bad_debt = unscale_borrow_ceil_ray(position)` and calls `apply_bad_debt_to_supply_index` directly — no privileged gate on the seize amount. The repo's own unit test demonstrates the theft mechanics: a stranded wiped position withdraws `gross = fresh_cash`, leaving pool cash below a fresh supplier's claim (`contracts/pool/tests/interest.rs:372-427`).

### Impact Explanation
Theft of user funds / protocol insolvency. Suppliers whose positions were already written down to ~0 retain claims valued at `1/1000` of their original share base in RAY terms. Once the market attracts any new deposit, the stranded claim withdraws real tokens, directly reducing cash below what legitimate suppliers are owed — an unbacked payout minted from thin air.

### Likelihood Explanation
Requires a market where a `clean_bad_debt` (or liquidation borrow-side seize) entry's ceiling-scaled debt ≥ total supplied value — i.e., a full wipeout of a market's lenders, achievable after a severe bad-debt event that `clean_bad_debt` is explicitly designed to process permissionlessly. No special privilege needed for the seize call itself; the attacker only needs the wipeout condition to occur and then a victim to supply fresh liquidity, or the attacker supplies dust to self-settle the stranded claims. Impact is bounded to 1/1000 of wiped share base per market, which still maps cleanly to theft of user funds once any cash exists.

### Recommendation
When `bad_debt >= total_supplied_value`, zero the supply shares (or equivalently zero `supply_index` and reset `supplied`/`revenue` share totals) instead of clamping to `SUPPLY_INDEX_FLOOR_RAW`. Alternatively, proportionally burn shares so that `supplied` shares × clamped index never exceeds the true residual value. The floor exists to avoid division-by-zero for future mints; pair it with share cleanup so no stale `scaled_amount` survives the write-down.

### Proof of Concept
```text
1. Attacker's borrow position accrues bad debt on hub market M until
   liquidations leave residual debt; any user calls controller
   clean_bad_debt / liquidation seize with PoolSeizeEntry{side: Borrow}.
2. seize::apply computes bad_debt = unscale_borrow_ceil_ray(position);
   bad_debt >= supplied * supply_index, so reduction_factor = 0 and
   supply_index clamps to RAY/1000; supplied shares are NOT burned.
3. Any supplier (or the attacker pre-positioning supply shares) calls
   withdraw(i128::MAX-equivalent 0 sentinel) → resolve_withdrawal burns
   all shares and pays floor(old_scaled × RAY/1000) in real tokens.
4. Pool cash is debited for a claim that should have been written to
   zero; subsequent legitimate suppliers' claims are now undercollateralized.
```
Demonstrated end-to-end by `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` at `contracts/pool/tests/interest.rs:373-427`, which asserts the stranded claim pays out `fresh_cash` and leaves `cash < fresh_claim`.

Note: I verified the pool-side mechanics and the seize path, but could not fully trace the controller's `clean_bad_debt` preconditions (dust threshold checks, who may submit entries) within available iterations; the analog assumes the wipeout entry can be submitted permissionlessly once bad debt exists, consistent with `clean_bad_debt` being listed as an unprivileged entrypoint.
