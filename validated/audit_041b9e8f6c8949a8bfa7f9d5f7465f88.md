### Title
Attacker-controlled swap routes can attach unrelated user token transfers to a controller strategy authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` authenticate the caller once, then execute a caller-controlled route through the configured swap aggregator. Because route hops can execute arbitrary venue contracts, a malicious venue can invoke `token.transfer(victim, attacker, amount)` while the victim's authorization context is active. During simulation, that transfer is attached as an additional child of the victim's controller authorization; if the victim signs the resulting tree—particularly when the transaction is presented as an ordinary lending operation—the unrelated wallet token is transferred to the attacker. The repository's regression harness demonstrates both the recorded poisoned authorization tree and successful movement when that tree is signed. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`process_swap_collateral` authenticates `caller` with `require_authorized_caller`, verifies control of `account_id`, and passes the caller's `swap` bytes to `withdraw_and_swap_from_supply`. [4](#0-3)  `withdraw_and_swap_from_supply` forwards those same bytes to `swap_tokens_or_passthrough`, and `swap_tokens` invokes `router.execute_strategy(controller, amount_in, swap)` under the flash guard. [5](#0-4) [1](#0-0) 

The controller correctly limits its own invoker authorization to `controller -> router` for `amount_in`, but it does not restrict which third-party code the route may execute or what unrelated `require_auth` calls that code may place inside the caller's authorization tree. [1](#0-0)  The harness models this with a route-selected contract whose `swap` function calls `token.transfer(victim, attacker, amount)`. [6](#0-5) 

Simulation records the rogue wallet transfer as a child of Alice's `swap_collateral` authorization, and enforcing mode succeeds when the transaction includes that simulated child invocation. [7](#0-6) [8](#0-7)  This is the same trust-boundary failure as the reference origin-spoofing bug: attacker-controlled payload contents cause a trusted user-facing operation to request authorization for an unrelated action.

### Impact Explanation
A victim who signs a maliciously constructed but otherwise successful `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` transaction can lose tokens unrelated to the lending operation. The demonstrated path drains the victim's entire balance of an unlisted wallet token while still crediting the expected strategy output, so the primary operation appears successful. [9](#0-8)  This qualifies as theft of user funds.

### Likelihood Explanation
The attacker cannot execute the transfer without the victim's authorization: an honest authorization tree containing only the controller call is rejected by the host. [10](#0-9)  The practical attack is phishing or malicious route generation: an attacker provides route bytes that produce the expected swap output while embedding a malicious venue that adds the extra token-transfer requirement to the simulation result. A wallet or interface that emphasizes the trusted controller call while presenting the opaque `swap` bytes and generated authorization tree inadequately can cause the victim to approve both actions. The harness confirms that source-account credentials also execute the rogue transfer once the generated child invocation is present. [11](#0-10) 

### Recommendation
Do not permit arbitrary venue contracts to execute under a user's lending authorization context. Maintain a governance-controlled allowlist of audited venue/pool addresses, or otherwise constrain route execution to known immutable adapters that cannot make unrelated calls on behalf of the caller. At minimum, interfaces and wallets should decode and prominently display every nested authorization generated by a strategy route, but the stronger contract-side fix is venue allowlisting because opaque route bytes make effective user review unreliable.

### Proof of Concept
The repository already contains a working reproduction:

1. Alice owns a lending account with USDC collateral and holds `WALLET_BALANCE` of a token that is not a protocol market asset. [12](#0-11) 
2. The attacker deploys `RogueHopPool` with a stored plan `(victim = alice, wallet_token, to = attacker, amount = WALLET_BALANCE)`. [13](#0-12) 
3. Alice submits `swap_collateral(alice, account_id, USDC_market, SWAP_IN_USDC, ETH_market, route)`, where `route` selects the malicious pool. [14](#0-13) 
4. During simulation, the malicious hop calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`, and the host records it under Alice's controller authorization. [15](#0-14) 
5. With the poisoned simulated authorization tree included, the transaction succeeds: Alice's wallet token balance becomes zero, the attacker receives the full balance, and Alice still receives the expected ETH collateral output. [8](#0-7)

/// Withdraws to the controller, then swaps its measured receipt into `token_out`.
/// Matching assets pass through unchanged; returns the available output.
pub(crate) fn withdraw_and_swap_from_supply(
    env: &Env,
    account: &mut Account,
    cache: &mut Context,
    caller: &Address,
    from: &HubAssetKey,
    amount: i128,
    token_out: &Address,
    swap: &StrategySwap,
    action: events::PositionAction,
) -> i128 {
    let supply_pos = get_supply_position_or_panic(env, account, from);

    let actual_withdrawn = withdraw_collateral_to_controller(
        env,
        account,
        cache,
        StrategyWithdraw {
            hub_asset: from,
            amount,
            position: &supply_pos,
            action,
        },
    );

    swap_tokens_or_passthrough(env, caller, &from.asset, actual_withdrawn, token_out, swap)
}
