### Title
Emporium's op.endpoint.call can move any ERC20/ETH balance not listed in the caller's circomData.erc20TokenAddresses, letting any unprivileged user sweep residual funds left on Emporium without triggering any balance/accounting check - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`/`handleOut` only reconciles token balance changes for addresses that the *caller themselves* lists in `circomData.erc20TokenAddresses`; any token that a call omits from that array is completely invisible to the before/after accounting loop [1](#0-0) . Since `op.endpoint.call{value}(op.callData)` executes with Emporium as `msg.sender`, an attacker can encode an op that calls `transfer(attacker, amount)` directly on any ERC20 token Emporium happens to hold, and — as long as that token address is absent from their own `erc20TokenAddresses` array — neither `EmporiumUpgradeable.runAction`'s `balanceChange` check nor `Hinkal.transact`'s balance-diff loop will ever observe or reject the outflow.

### Finding Description
Broken equality: "assets accounted in `balancesBefore`/`balancesAfter` (and in `Hinkal.transact`'s `oldBalances`/`newBalances` loop, both indexed by `circomData.erc20TokenAddresses`)" should equal "assets Emporium's `op.endpoint.call` is capable of moving." In reality Emporium can call **any** address with **any** calldata chosen by the caller [2](#0-1) , while the accounting arrays are sized and populated purely from the *same caller's* `circomData.erc20TokenAddresses` [3](#0-2) [4](#0-3) . Nothing forces `op.endpoint`/`op.callData` targets to be a subset of that array, and `Hinkal.transact`'s slippage/balance-diff loop is likewise only iterated over `circomData.erc20TokenAddresses` [5](#0-4) .

In the degenerate "Min path" described in the question (`dimensions.tokenNumber == 0`), `circomData.erc20TokenAddresses` is length 0, so `balancesBefore`/`balancesAfter` are empty arrays and the entire `for` loop in `runAction` that would call `handleOut` and revert on negative `balanceChange` never executes at all [6](#0-5) . But the vulnerability is not limited to the all-empty case: for *any* transaction, any token address simply left out of `circomData.erc20TokenAddresses` is outside the accounting entirely, regardless of how many other tokens are listed.

Attacker's exact call: submit `Hinkal.transact` with a self-generated valid proof for a transaction whose `circomData.externalActionData.externalActionId` maps to `EmporiumUpgradeable`, and whose `externalActionMetadata` decodes to an `EmporiumStack` containing one stateless op: `{ endpoint: <dustToken>, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dustAmount) }`. The attacker's own `circomData.erc20TokenAddresses` need not (and must not) include `<dustToken>`. Because `IHinkalWallet.callHinkalWallet`/`doSendToRelay` selectors are the only ones blocked [7](#0-6) , an ERC20 `transfer` call is permitted. Emporium executes `transfer` as `msg.sender=Emporium`, silently moving `dustToken` balance to the attacker with no revert path, since `dustToken` never appears in `balancesBefore`/`balancesAfter` (Emporium-level) nor in `oldBalances`/`newBalances` (Hinkal-level).

Existing guards fail to catch this because:
- `performHinkalChecks`/`dimensionsCheck` only validate internal-array-length consistency for the caller's *own* declared `tokenNumber`; they impose no relationship between `erc20TokenAddresses` and the tokens actually reachable by `op.endpoint.call` [8](#0-7) .
- `verifyProof`/circuit constraints bind the shielded amounts (`inTotal + amountChanges === outTotal`) to the *declared* token set, but say nothing about arbitrary calldata executed by external actions on unrelated token contracts (this is a Solidity-side accounting gap, not a circuit-constrained field).
- `rootHashExists`, `insertNullifiers`, `nonReentrant`, `onlyAllowedRecipient` restrict who can invoke `runAction` (only Hinkal itself) and prevent replay/double-spend of the attacker's own leaves, but do not restrict what `op.endpoint.call` can do once inside a legitimately-authorized `runAction` invocation.

### Impact Explanation
Any residual ERC20/ETH balance that accumulates on the shared `EmporiumUpgradeable` contract (e.g., dust or partial leftovers from any prior legitimate multi-op action, rounding, or a self-serving flow that first pulls funds in and only partially re-extracts them) can be permanently and directly stolen by any unprivileged Hinkal user, repeatedly, one dust-sweep per unaccounted token per transaction, with zero UTXOs burned to pay for it. This is direct theft of value that never leaves the Hinkal accounting system as an authorized flow — it bypasses the balance-diff/slippage invariant entirely — matching "Critical: direct theft of shielded or in-flight user funds."

### Likelihood Explanation
Preconditions: (1) Emporium must hold some non-zero balance of a token not referenced by the attacker's own `erc20TokenAddresses` array — realistic any time a prior legitimate multi-step Emporium op leaves float, or even via ETH dust from `value`-carrying ops. (2) The attacker needs a valid ZK proof for their own minimal/self-owned UTXO transaction routed through `EmporiumUpgradeable` as the external action — this requires only that a verifier for the chosen `Dimensions`/`externalActionId` combination is registered by the owner (an operational fact this review cannot confirm from the repo alone, since verifier registration lives in `VerifierFacade.registerVerifiers` and is owner-controlled off-chain configuration [9](#0-8) ). Cost to the attacker is limited to gas and proof generation; the technique is repeatable against every token/dust amount Emporium ever holds.

### Recommendation
In `EmporiumUpgradeable.runAction`, restrict `op.endpoint` calls so they cannot target arbitrary ERC20 token contracts with transfer-type selectors unless that token is part of `circomData.erc20TokenAddresses` for the current call (or maintain a full balance snapshot/diff over the union of all tokens Emporium can plausibly hold, not just the caller-declared subset). Alternatively, disallow any op whose target is one of the caller-known ERC20 tokens' `transfer`/`transferFrom`/`approve` selectors unless it is included and accounted for in the current call's `erc20TokenAddresses`, and add an explicit invariant test that Emporium's balance for any token can only decrease through the accounted `handleOut` path.

### Proof of Concept
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register a verifier for `Dimensions{tokenNumber:1, nullifierAmount:X, outputAmount:Y}` with `externalActionId` pointed at Emporium.
2. Legitimate user runs an Emporium action (`ops` with 2+ steps) that deposits `TokenA` into Emporium then withdraws slightly less than deposited (simulating dust/partial-fill leftover); assert Emporium's `TokenA.balanceOf(Emporium) > 0` afterward.
3. Attacker generates their own valid proof for a `transact` call whose `circomData.erc20TokenAddresses` contains only `TokenB` (or is empty), and whose Emporium `EmporiumStack.ops` = `[{endpoint: TokenA, invokeWallet:false, value:0, callData: transfer(attacker, TokenA.balanceOf(Emporium))}]`.
4. Assert: (a) the attacker's `transact` call succeeds without reverting on `BalanceChangeShouldBePositive` or the `Hinkal.transact` "Balance Diff Should be equal..." check; (b) `TokenA.balanceOf(attacker)` increases by the full stolen amount; (c) no UTXO for `TokenA` was minted/issued to the attacker, and no nullifier for `TokenA` was spent — proving the theft occurred entirely outside the shielded-accounting equality.
