### Title
Timeout delivery (fund-recovery path) is blocked by the same coarse `FrozenStatus` flag as message delivery, with no way to keep it open — (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2` gates every incoming/timeout entrypoint with a single `notFrozen(host)` modifier that reverts whenever `FrozenStatus` is `Incoming` or `All` [1](#0-0) . This modifier is applied identically to `handlePostRequests`/`handleGetResponses` (new message delivery) and to `handlePostRequestTimeouts`/`handleGetRequestTimeouts` (the mechanism users rely on to reclaim funds/fees for requests that failed to deliver) [2](#0-1) [3](#0-2) . There is no separate flag to disable new message delivery while still allowing timeout/withdrawal-style recovery — exactly the gap described in the external report (no way to "retire"/pause new activity while keeping exits open).

### Finding Description
`FrozenStatus` only has four coarse states — `None`, `Incoming`, `Outgoing`, `All` [4](#0-3) . `EvmHost.setFrozenState` lets the `admin` or `handler` set any of these with no cooldown-bounded auto-unlock and no separate control for "recovery" operations [5](#0-4) .

Once `Incoming` (or `All`) is set — the state an operator would use during a security incident (e.g. a compromised consensus client, malicious relayer, or forged-message risk) — `HandlerV2`'s `notFrozen` modifier blocks not only new inbound deliveries but also `handlePostRequestTimeouts` and `handleGetRequestTimeouts`, the only mechanisms by which a user who dispatched a `PostRequest`/`GetRequest` from this host can get `host.dispatchTimeOut(...)` invoked to release their locked funds/fees back to them [6](#0-5) [7](#0-6) . Unlike lending protocols (per the external report) that keep withdraw/repay open while disabling deposit/borrow, Hyperbridge's `EvmHost`/`HandlerV2` has no equivalent split: the exact operation a user needs during an incident to exit/reclaim funds (timeout processing) is coupled to the same emergency flag that blocks new message intake, with no independent "still allow timeouts" mode and no bound on how long the freeze can persist.

### Impact Explanation
Any time an admin (or the handler itself, e.g. via `ConsensusClientExpired` reasoning in `handleConsensus`) sets `FrozenStatus.Incoming` or `All` to respond to a genuine security concern, users with outstanding, timed-out `PostRequest`/`GetRequest` commitments on that host are unable to have their timeout processed and their locked fee/funds released via `dispatchTimeOut` until the freeze is lifted [8](#0-7) . Since there is no maximum duration or forced auto-unfreeze in `EvmHost` (freeze persists until an explicit `setFrozenState(None)` call), funds can be frozen indefinitely for legitimate users purely as a side effect of an incident response action that was only meant to stop new/incoming traffic — a freezing-of-funds condition for money that should be recoverable regardless of the incident.

### Likelihood Explanation
This triggers under the routine, expected operational scenario of the protocol pausing incoming traffic during a consensus/relayer incident — a scenario the codebase itself anticipates (`ConsensusClientExpired`, admin `setFrozenState`) [9](#0-8) . Any legitimate freeze inherently and unavoidably blocks all pending timeout recoveries for the duration of the freeze, making this reachable without any malicious actor — it's a direct consequence of normal, intended admin/security use of `setFrozenState`.

### Recommendation
Split `FrozenStatus` (or add a dedicated modifier) so that `handlePostRequestTimeouts` and `handleGetRequestTimeouts` are not gated by the same `Incoming`/`All` flags used for new inbound message delivery. Timeout processing should remain permissible (similar to "withdraw/repay" staying open in lending protocols) even while `Incoming` delivery is frozen, since it only releases already-locked user funds and does not admit new, potentially forged, cross-chain state. Consider a distinct `RecoveryPaused` flag with its own admin control, separate from the flag used to block new message intake during incidents.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost{...})` locking a fee via `_requestCommitments` (per `testFundRequest`) [10](#0-9) .
2. Admin detects a security incident (e.g. suspected forged consensus proof) and calls `host.setFrozenState(FrozenStatus.Incoming)` to stop new deliveries, per intended design [5](#0-4) .
3. The user's request times out on the destination chain. The user (or relayer on their behalf) submits `handlePostRequestTimeouts` with a valid non-membership proof to reclaim the locked fee.
4. The call reverts with `HostFrozen()` because `notFrozen(host)` checks the same `Incoming`/`All` flag [1](#0-0) [2](#0-1) .
5. Until the admin explicitly unfreezes the host (no automatic time-bound exists, unlike the report's 30-day auto-unpause), the user's funds remain locked and unrecoverable, even though the incident being mitigated has nothing to do with legitimate timeout recovery.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }

 * @title FrozenStatus
 * @notice Represents the frozen state of the Host for security and emergency situations
 * @dev Used to halt specific protocol operations during security incidents or upgrades
 */
enum FrozenStatus {
    /// @notice Normal operation - all functions are enabled
    None,
    /// @notice Incoming messages are blocked - prevents receiving cross-chain messages
    Incoming,
    /// @notice Outgoing messages are blocked - prevents sending cross-chain messages
    Outgoing,
    /// @notice All operations are frozen - complete protocol halt
    All
}
