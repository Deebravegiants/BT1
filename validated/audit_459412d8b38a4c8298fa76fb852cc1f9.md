### Title
Webhook `shop-domain` and `topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw body, then dispatches the handler using the `shop` and `topic` values taken from HTTP headers that are never included in the signed material. Because the app's webhook HMAC secret (`Context.api_secret_key`) is the *same* secret for every shop that has installed the app, any shop that can obtain one valid `(raw_body, hmac)` pair (e.g. by observing its own legitimate webhook deliveries) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header. The HMAC check still passes because it only ever verifies `@raw_body`, so the app's webhook handler will process attacker-chosen `shop`/`topic` values as if Shopify itself sent them for that tenant/topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` and `topic` are read straight from headers and are not part of the signed string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac` header — it never binds `shop` or `topic`: [3](#0-2) 

`Registry.process` trusts this same unauthenticated `request.shop`/`request.topic` when dispatching to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`HMAC-covered bytes (raw_body only)` ≠ `bytes acted upon (raw_body + shop-domain header + topic header)`.

Since `Context.api_secret_key` is a single per-app secret shared across every installed shop (not a per-shop secret), a valid `(raw_body, hmac)` pair computed for shop A's webhook is equally valid when replayed with shop B's `shop-domain` header and/or a different `topic` header — the signature check cannot detect the substitution because it was never computed over those fields.

### Impact Explanation
This breaks the tenant/topic binding that `Registry.process` implicitly assumes holds between the cryptographically verified body and the headers used for dispatch. An attacker who is merely a legitimate (even free-tier) merchant of a multi-tenant app can capture one authentic webhook delivery for their own shop and replay it against the app's public webhook endpoint with a forged `shop-domain` (impersonating a different merchant) and/or forged `topic` (causing the body to be processed by a handler for an unrelated event type). Depending on what the app's webhook handlers do with `shop`/`topic`/`body` (e.g., updating billing state, order data, or GDPR-related records keyed by `shop`), this can result in cross-tenant data corruption or unauthorized actions attributed to another shop — a cross-tenant access violation performed by an otherwise unprivileged internet user (any app installer), without needing the app's `client_secret` or any merchant's access token.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as any regular merchant (or otherwise observing one legitimate webhook delivery, e.g. via browser devtools/network capture on your own shop), and (2) sending a crafted HTTP POST to the app's public webhook endpoint with the captured body/HMAC and modified headers. No access token, `client_secret`, or elevated privilege is needed — only network access to the endpoint, which is unprivileged-internet-user reachable by design. The main variable is what the specific app's handler does with the spoofed `shop`/`topic`, so severity varies by app but the gem itself provides no defense.

### Recommendation
Include `shop` and `topic` (and any other header fields relied upon by handlers) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before dispatch — e.g., verify that the `shop` header corresponds to a shop with an active session/installation known to the app, and reject requests where headers can't be corroborated. At minimum, document prominently that `shop`/`topic` are unauthenticated and must be revalidated by the host app against its own tenant records before use.

### Proof of Concept
1. As a merchant who installs the target app, capture a legitimate webhook delivery, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid-hmac-for-body>
x-shopify-shop-domain: my-shop.myshopify.com
Body: {"id":1,...}
```
2. Replay the exact same body and `hmac` header, but change:
```
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-topic: customers/data_request
```
3. `ShopifyAPI::Webhooks::Request.new` accepts these headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
which succeeds because it only checks the (unchanged) body — despite `shop` and `topic` being forged — and the handler for `customers/data_request` is invoked with `shop: "victim-shop.myshopify.com"`, `topic: "customers/data_request"` and the attacker's original order body, none of which Shopify actually signed together.
