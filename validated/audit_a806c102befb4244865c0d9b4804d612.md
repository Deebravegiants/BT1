### Title
Zap._sellInternal blocks all sells (freezes exit) when the LT's exchangeRate() reads/rounds to zero - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._sellInternal` gates every sell on a pre-`redeem()` estimate computed from `IBounceLeveragedToken.exchangeRate()`, rather than on the actual `redeem()` output. If that externally-controlled, off-chain-influenced price feed (`exchangeRate()`) reports (or rounds down to) zero for any reason — a leveraged token being wiped out by an extreme underlying move, a stale/zero read, or any other degenerate state of the LT — every sell attempt through `Zap`, for both on-curve and post-graduation tokens, permanently reverts before `redeem()` is even called. This is the same bug class as GMX M-20: an external price oracle reporting zero makes the "liquidation" (here: exiting a position via sell) path permanently unreachable, trapping trader funds and any value backing those tokens.

### Finding Description
`Zap._sellInternal` computes: [1](#0-0) 

```solidity
uint256 ltReceived = bonding_.isGraduated(tokenAddress)
    ? _sellOnUniswapV2(tokenAddress, lt, tokenAmount)
    : _sellOnCurve(tokenAddress, tokenAmount);

uint256 grossUsdcEstimate = (ltReceived * IBounceLeveragedToken(lt).exchangeRate()) / 1e18;
if (grossUsdcEstimate / 1e12 < minUsdcAmount()) revert BelowMinAmount();

uint256 grossUsdc = IBounceLeveragedToken(lt).redeem(address(this), ltReceived, 0);
```

The tokens (and LT) have already been pulled from the seller and swapped on the curve/pool into `ltReceived` LT by this point. The contract then computes `grossUsdcEstimate` purely from `exchangeRate()`, an external view on the BounceTech LT interface: [2](#0-1) 

If `exchangeRate()` is zero (or rounds `grossUsdcEstimate` down to zero) at the moment of the call, `grossUsdcEstimate / 1e12` is `0`, which is always `< minUsdcAmount()`, so the function unconditionally reverts with `BelowMinAmount()` — regardless of the sell size, and *before* the real, authoritative `redeem()` call is ever reached. This is a self-imposed liveness gate that has no fallback: there is no path in `_sellInternal` that skips the estimate and calls `redeem()` directly.

This mirrors the reported bug class precisely: a price read of zero from an external source (`exchangeRate()` here, Chainlink/off-chain oracle price there) makes the exit/liquidation function permanently revert, even though the underlying mechanism (`redeem()`/liquidation execution) might otherwise still be callable and produce a meaningful (even if reduced) result.

Unlike the buy side and unlike graduated-pool holders who can route around `Zap` via HyperSwap directly, curve-stage (non-graduated) token holders have no other exit: `Bonding.sell`/`Router.sell` is only reachable through `Zap`, so this estimate-based gate is the sole choke point for every curve-stage seller.

### Impact Explanation
If the paired BounceTech LT's `exchangeRate()` ever reports zero — a plausible state for a leveraged token whose underlying collateral value has been wiped out by an extreme move, which is exactly the kind of "unlikely but reachable" scenario Sherlock accepted as Medium in the referenced GMX finding — then:
- Every seller of that token (on-curve or post-graduation, since the fee/policy path is identical) is permanently blocked from selling through `Zap`, regardless of trade size, including full-balance exits.
- Curve-stage holders have no alternative exit path, since `Bonding.sell`/`Router.sell` is not directly callable by an unprivileged trader outside of `Zap`.
- Meanwhile, any remaining LT value still sitting in the curve `Pair`/`Bonding` (real, non-virtual reserve) becomes permanently unreachable by ordinary users, and trader capital is frozen indefinitely — a fund-freezing condition, not merely an inconvenience.

This matches the "Reject ... no-impact analogs" and "Accept ... permanent freezing of trader ... funds" criteria in the validation rules.

### Likelihood Explanation
Leveraged tokens are explicitly designed to track underlying price moves with leverage and can be driven to (near) zero value by a sufficiently large adverse move in the underlying, especially for higher-leverage products; the codebase itself documents `targetLeverage()` as a first-class LT parameter and treats `exchangeRate()` drift/staleness as an accepted risk elsewhere (`docs/contracts-scope.md`'s "Exchange-rate freshness on the USD trigger" section acknowledges `exchangeRate()` can read anomalously). No privileged action is required to trigger it — any trader attempting to sell at that moment hits the gate. Likelihood is comparable to the accepted Medium classification of the original GMX finding: unlikely under normal conditions, but a real, reachable market state for a leveraged reserve asset.

### Recommendation
Remove (or make advisory-only) the pre-`redeem()` estimate check in `Zap._sellInternal`. Instead, call `redeem()` first and validate the actual `grossUsdc` returned against `minUsdcOut`/`minUsdcAmount()` floors, mirroring how the buy path validates against real minted amounts rather than a separately-computed price estimate. If a pre-check is still desired to save gas on obviously-dust sells, it should not be capable of unconditionally reverting all sells when `exchangeRate()` degenerates to zero — e.g., skip the pre-check entirely when `exchangeRate() == 0` and rely solely on the authoritative `redeem()` outcome and the existing `minUsdcOut` slippage guard.

### Proof of Concept
1. A token is trading on-curve (not yet graduated), paired with LT `lt`.
2. `lt.exchangeRate()` degenerates to `0` (e.g., in tests, `MockLeveragedToken.setExchangeRate(0)`, modeling a leveraged token wiped out by an extreme underlying move).
3. A holder calls `Zap.sell(tokenAddress, tokenAmount, 0)`.
4. `_sellInternal` pulls the tokens, swaps them on the curve via `_sellOnCurve` into some nonzero `ltReceived`.
5. `grossUsdcEstimate = (ltReceived * 0) / 1e18 = 0`; `0 / 1e12 = 0 < minUsdcAmount()` is always true, so the call reverts with `Zap.BelowMinAmount()` at line 445, before `redeem()` is ever invoked: [3](#0-2) 
6. Every subsequent sell attempt for this token, at any size, reverts identically, since the gate is independent of `tokenAmount`/`ltReceived` scale whenever `exchangeRate()` is zero — sellers are permanently locked out of exiting through `Zap`, with no alternative route for curve-stage tokens.
