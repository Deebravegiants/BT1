## Title
`validateBchAddress`'s legacy branch accepts base58 strings with no checksum verification, letting funds be withdrawn to an unrecoverable address - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

## Summary
`validateBchAddress` treats any string matching `/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/` or `/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/` as a valid BCH legacy address, purely by regex, without ever base58-decoding it or verifying the base58check checksum. This is inconsistent with the sibling function `validateBtcAddress`/`validateBtcBase58Address`, which does decode and verify the checksum for the identical address format. The unvalidated address then flows unchanged into `createWithdrawIntentPrimitive` → `createWithdrawMemo`, producing a `WITHDRAW_TO:<address>` memo submitted on-chain.

## Finding Description
Broken equality: **DESTINATION TRUTH** — the address accepted by `validateAddress(address, Chains.BitcoinCash)` should equal a checksum-valid, payable base58check address. Instead: [1](#0-0) 

only checks character set and length via regex, and returns `true` immediately without computing `sha256(sha256(payload))` and comparing against the trailing 4 checksum bytes — the exact check that `validateBtcBase58Address` performs for the very same `1.../3...` format: [2](#0-1) 

An attacker (any unprivileged caller supplying `destinationAddress` for a BCH withdrawal) can submit a string that matches the regex (correct charset/length) but has a corrupted/incorrect 4-byte checksum. `PoaBridge.validateWithdrawal` calls `validateAddress` first and, since it returns `true`, proceeds past the only address-format gate: [3](#0-2) 

The withdrawal intent is then built by `createWithdrawIntentPrimitive`, which passes `destinationAddress` straight through to `createWithdrawMemo`, embedding it verbatim in the `WITHDRAW_TO:<address>` memo with no further checksum validation anywhere in the SDK: [4](#0-3) 

Neither `compareAddresses` nor `supports()` ordering nor any intents-contract-side check re-verifies the BCH checksum — the contract only verifies signatures/nonces, not destination-address cryptographic validity, and the relayer/solver that ultimately pays out BCH is out of scope but receives a memo the SDK itself certified as "valid."

## Impact Explanation
A withdrawal intent gets signed and submitted with a BCH memo pointing at an address string with an invalid checksum. No real private key can derive/spend from an address with a broken checksum in this format, so a downstream bridge/relayer that pays out based on the raw memo would send funds to a destination that cannot be recovered by the user or the counterfeit "recipient." This matches the **Critical** category: "funds delivered to a wrong address/chain/contract with no recovery." The exploit is repeatable per withdrawal call — any BCH withdrawal by any caller can be constructed with a mangled checksum and will pass client-side validation.

## Likelihood Explanation
- Preconditions: a BCH withdrawal via `PoaBridge` (route must support BCH, i.e., an `assetId` mapping to `Chains.BitcoinCash`).
- Attacker cost: trivial — flip any character in a syntactically valid legacy address to break its checksum while keeping charset/length intact; no cryptographic effort or special access needed.
- The bug is fully within the caller-controlled `destinationAddress` parameter path, requires no relayer/RPC/contract misbehavior, and is reproducible with pure unit tests (no network needed for `validateAddress`/`createWithdrawIntentPrimitive`).

## Recommendation
Make `validateBchAddress`'s legacy branch perform full base58check decoding and checksum verification (mirroring `validateBtcBase58Address`), i.e., decode via `base58.decode`, confirm length is 25 bytes, version byte is `0x00` (P2PKH) or `0x05` (P2SH), and verify `sha256(sha256(payload))` matches the trailing 4 bytes, before returning `true`.

## Proof of Concept
```ts
// packages/intents-sdk/src/lib/validateAddress.spec.ts (illustrative)
import { validateBchAddress } from "./validateAddress";
import { createWithdrawIntentPrimitive } from "../bridges/poa-bridge/poa-bridge-utils";
import { base58 } from "@scure/base";
import { sha256 } from "@noble/hashes/sha2";

test("legacy BCH branch accepts a checksum-corrupted address", () => {
  // Build a syntactically valid P2PKH payload, then corrupt the checksum.
  const version = 0x00;
  const hash160 = new Uint8Array(20).fill(1);
  const payload = new Uint8Array([version, ...hash160]);
  const goodChecksum = sha256(sha256(payload)).subarray(0, 4);
  const badChecksum = new Uint8Array(goodChecksum);
  badChecksum[0] ^= 0xff; // corrupt checksum

  const corrupted = base58.encode(
    new Uint8Array([...payload, ...badChecksum]),
  );

  // Equality LHS: validated legacy-format address (broken)
  expect(/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(corrupted)).toBe(true);
  expect(validateBchAddress(corrupted)).toBe(true); // BUG: should be false

  // Equality RHS: the intent primitive still embeds the bad address in memo
  const intent = createWithdrawIntentPrimitive({
    assetId: "nep141:bch.omft.near",
    destinationAddress: corrupted,
    destinationMemo: undefined,
    amount: 1000n,
  });
  expect(intent.memo).toBe(`WITHDRAW_TO:${corrupted}`);
});
```
This demonstrates that a checksum-invalid, unspendable "address" both passes `validateAddress` for BCH and is committed into the on-chain-bound withdrawal memo unchanged.

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
}

export function validateBchAddress(address: string): boolean {
	// Legacy address format (same as Bitcoin)
	if (
		/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address) ||
		/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address)
	) {
		return true;
	}

	// CashAddr format
	return validateBchCashAddr(address);
}

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	destinationAddress: string;
	destinationMemo: string | undefined;
	amount: bigint;
}): Extract<IntentPrimitive, { intent: "ft_withdraw" }> {
	const { contractId: tokenAccountId } = utils.parseDefuseAssetId(
		params.assetId,
	);
	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: tokenAccountId,
		amount: params.amount.toString(),
		memo: createWithdrawMemo({
			receiverAddress: params.destinationAddress,
			xrpMemo: params.destinationMemo,
		}),
		min_gas: MIN_GAS_AMOUNT,
	};
}

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
