Confirmed root cause. The `Registry.process` method identifies the tenant (`shop`) purely from an unauthenticated header, while HMAC integrity only covers the raw body bytes.

### Title
Webhook Shop Identity Not Bound to HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, which validates the HMAC solely against `request.to_signable_string` (the raw request body) [1](#0-0) . The `shop` value used to identify which tenant the webhook belongs to is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header and is never included in the HMAC-signed payload [2](#0-1) [3](#0-2) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over that string using `Context.api_secret_key` [4](#0-3) . Meanwhile `Request#shop` is parsed straight from the `shopify-shop-domain` header with no cryptographic binding to the signed body [2](#0-1) .

`Registry.process` uses `Utils::HmacValidator.validate(request)` only to gate whether the body is "authentic," then unconditionally trusts `request.shop` to construct `WebhookMetadata` and dispatches it to the registered handler as the tenant identity for that webhook [5](#0-4) .

This breaks the intended binding: `bytes verified (raw body via HMAC)` ≠ `identity acted on (shop header used for tenant routing)`. Any HTTP request bearing a body/HMAC pair that is valid for the app's `client_secret` — including one captured from a webhook that a merchant legitimately received on their own shop (e.g., by inspecting their own webhook delivery logs, using a request-capture endpoint, or replaying content from `orders/create` where they control fields such as line-item properties or notes) — can be resubmitted to the app's public webhook endpoint with an arbitrary `shopify-shop-domain` header. The `HmacValidator` still reports the request as valid because it never inspected the shop field, and the handler then processes attacker-controlled body content under the identity of a victim shop.

### Impact Explanation
This enables cross-tenant data injection: a host application relying on this gem's `Registry.process` to authenticate incoming webhooks will accept attacker-controlled payloads while believing they originated from a shop chosen by the attacker rather than the shop that actually triggered the webhook. Depending on how the host stores/acts on `WebhookMetadata#shop` (e.g., updating per-shop order/customer/product records), this can lead to cross-tenant record corruption or unauthorized state changes attributed to another merchant's shop — meeting the Critical "cross-tenant access" bar since no per-tenant secret or scope check exists to prevent it.

### Likelihood Explanation
An attacker only needs their own working installation of the app (any unprivileged merchant with a valid app install can generate legitimately-signed webhooks containing content they control) plus the ability to capture the raw HTTP request Shopify delivers to the app's webhook URL (e.g. via a proxy/capture tool placed in front of their own endpoint, or by using an endpoint they control before forwarding). No possession of `api_secret_key` is required — the valid HMAC is produced by Shopify itself for the attacker's own shop and is simply replayed with a substituted `shop-domain` header, since that header is outside the signed payload.

### Recommendation
Bind the shop identity to the authenticated payload: include the `shop` domain (and ideally `topic`/`webhook-id`) inside the HMAC-signable string in `Request#to_signable_string`/`VerifiableQuery`, or otherwise validate that the shop asserted by the header matches an expected value (e.g., cross-check against the session/shop the webhook was registered for) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document that `request.shop` from `Registry.process` is unauthenticated and must not be used as a trust boundary without further verification by the host application.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# Shopify sends a legitimately signed webhook to the app's endpoint, e.g.:
#   headers: { "x-shopify-hmac-sha256" => "<valid-hmac-of-body>",
#              "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
#              "x-shopify-topic" => "orders/create" }
#   body: '{"id":1,"note":"<attacker-controlled-content>"}'
#
# Attacker captures this raw body + hmac (e.g. via a logging proxy in front of
# their own webhook receiver) and replays it directly to the same public
# webhook endpoint, only changing the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_valid_hmac,   # unchanged, still valid for this body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/HMAC pair is valid),
#    handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the request never came from victim-shop.
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
