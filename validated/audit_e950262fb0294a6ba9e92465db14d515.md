### Title
Permanent market freeze from `i128` overflow during interest accrual - ([File: common/src/rates/simulate.rs])

### Summary
A sufficiently large market can enter a state where every state-changing operation reverts because accrual multiplies scaled `RAY` balances by their indexes using bounded `i128` arithmetic before the configured borrow-index cap can engage. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Every pool action loads a `Cache` and calls `interest::global_sync`, and `global_sync` invokes `accrue_step` for each elapsed interval. [4](#0-3) [5](#0-4) 

`accrue_step` first calculates `borrowed_original` and `supplied_original` through `scaled_to_original`, which performs `scaled.mul(index)`. [6](#0-5) [2](#0-1) 

When `scaled * index` exceeds `i128::MAX`, this conversion raises `MathOverflow` before `update_borrow_index` can clamp the next index to `MAX_BORROW_INDEX_RAY`. [3](#0-2) 

The in-repository stress scenario demonstrates the exact cliff: a one-billion-token, 18-decimal market at 98% utilization eventually fails accrual with `MathOverflow`, while the stored borrow index remains below its cap. [7](#0-6) [8](#0-7) 

### Impact Explanation
The failed conversion permanently freezes the affected market because withdrawals and repayments both call `ops::load_leg`, which synchronizes interest before mutating the position. [9](#0-8) [10](#0-9) 

The regression test confirms that both supplier withdrawal and borrower repayment revert after the cliff is reached, leaving supplied funds and debt accounting inaccessible. [11](#0-10) 

Liquidation and other market mutations that call `synced_market` or `load_leg` encounter the same failed accrual, so the market cannot recover through its normal settlement paths. [4](#0-3) 

### Likelihood Explanation
Reaching the state requires an extremely large high-decimal market, sustained high utilization, sufficient collateral and liquidity, and market caps that permit the required balances. [12](#0-11) 

Once those market conditions exist, any unprivileged address can trigger the transition by calling `update_indexes`, after which ordinary users can no longer repay, withdraw, or liquidate that market. [13](#0-12) 

This is a Medium-severity issue because the impact is a persistent freeze of user funds, but the trigger requires extreme scale and prolonged accrual rather than a single inexpensive transaction. [7](#0-6) 

### Recommendation
Enforce a market-level invariant that `scaled_balance * MAX_BORROW_INDEX_RAY` and `scaled_supply * MAX_SUPPLY_INDEX_RAY` cannot exceed the representable `RAY` domain before accepting additional supply or debt. [14](#0-13) 

Alternatively, compute utilization and total-debt transitions through `I256` or another overflow-safe representation and clamp the index before converting scaled balances back to `Ray`. [15](#0-14) 

The cap check should occur before the fallible `scaled_to_original` multiplication, because clamping only the newly calculated index is too late once the stored balance and index product already exceeds `i128::MAX`. [2](#0-1) 

### Proof of Concept
1. Configure a high-decimal market using the test’s 18-decimal asset and steep rate curve, then set caps high enough to accept a one-billion-token position. [16](#0-15) [17](#0-16) 
2. Call `supply` with the `BIG18` hub asset and `amount = 1_000_000_000 * 10^18` atomic units. [18](#0-17) 
3. Supply sufficient collateral and call `borrow` with approximately `98%` of that `BIG18` amount, as demonstrated by `principal / 100 * 98`. [19](#0-18) 
4. Advance ledger time and repeatedly call `update_indexes` for `BIG18` until accrual returns `MathOverflow`. [20](#0-19) 
5. Subsequent `withdraw` and `repay` calls both fail with `MathOverflow` because they accrue interest before processing their requested action. [21](#0-20) [11](#0-10)

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
