The webhook HMAC (`Utils::HmacValidator.validate`) verifies the signature against `to_signable_string`, which for `Webhooks::Request` returns only `@raw_body` [1](#0-0) . Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) , and `Registry.process` forwards `request.shop` straight into the `WebhookMetadata` passed to the app's handler without any cross-check against the signed body [3](#0-2) .

### Title
Webhook shop identity is not bound by HMAC, allowing shop spoofing in `Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the HMAC signature validated by `Utils::HmacValidator.validate` covers the body bytes exclusively. The `shop-domain` (and `topic`, `api-version`, `webhook-id`) HTTP headers, which are exposed as `request.shop` and consumed by the app's `WebhookHandler` via `WebhookMetadata`, are never included in the signed content. This breaks the identity binding: `HMAC(secret, raw_body) == valid` should imply `shop == header_shop`, but the header is not part of the signed material, so any request carrying a previously-valid `(raw_body, hmac)` pair can have its `shop-domain` header swapped freely while still passing verification.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it via `OpenSSL.secure_compare` to the caller-supplied HMAC [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors pull straight from the `@headers` hash built from the raw HTTP headers passed into `Request.new`, with no cryptographic tie to the signature [5](#0-4) .

`Registry.process` validates only the HMAC and then hands `request.shop` (an unauthenticated header value) directly to the registered handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

Since the body/HMAC pair is valid for *any* shop that produced that exact body (the secret is shared per app, not per shop), an attacker who owns or controls one installed shop can capture a genuine webhook delivery (raw body + `X-Shopify-Hmac-Sha256`) from their own store and replay it directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The HMAC check still passes because the header is not part of the signed string, so the handler processes attacker-controlled body content under the victim's tenant identity — breaking the equality `authenticated_shop == shop_used_for_tenant_routing`.

### Impact Explanation
This crosses a tenant boundary: an unprivileged party who can obtain one valid signed webhook body (e.g. from their own Shopify store, which they legitimately control) can inject that payload into another merchant's tenant context inside the host app, since the app's webhook handler trusts `WebhookMetadata#shop` for routing/storing data per merchant. This matches the "Critical - cross-tenant access" category: data intended for tenant A can be attributed to tenant B purely by header manipulation, without any credential belonging to tenant B.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook receiving endpoint and one legitimately-signed webhook body (obtainable by installing the app on any store, including a free/dev store, and capturing its own webhook deliveries). No access token, `client_secret`, or victim credentials are required — only the ability to send an HTTP POST with attacker-chosen headers and a previously-observed valid `(body, hmac)` pair.

### Recommendation
Include the `shop`, `topic`, `api_version`, and `webhook_id` header values as part of the signed content that is HMAC-verified (or otherwise cryptographically bind them to the request), matching the pattern used for OAuth's `AuthQuery#to_signable_string`, which folds `code`, `host`, `shop`, `state`, and `timestamp` into the signed string [6](#0-5) . At minimum, document that `WebhookMetadata#shop` must not be trusted for tenant routing without an out-of-band verification that the shop is one the app actually installed for, and consider validating that the shop was previously registered/authorized before dispatching to handlers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com` and trigger a webhook (e.g. `orders/create`) so Shopify delivers a request with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's `client_secret`.
2. Capture the raw body and the `X-Shopify-Hmac-Sha256` header value from that delivery.
3. Send a new POST request directly to the app's webhook endpoint with the same raw body and HMAC header, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the raw body only) and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the app to process attacker data under the victim's tenant.
