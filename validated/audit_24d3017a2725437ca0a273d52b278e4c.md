Confirmed: `Vote.signature` in `evm/src/consensus/Types.sol:141-146` is a Solidity dynamic `bytes` field with no length constraint, and the ABI-decoded value flows unchecked into a fixed-size copy in Rust.

### Title
Unchecked-length Vote.signature causes panic in NTLM-analog fixed-buffer copy during BEEFY consensus proof conversion - (File: evm/rust/src/conversions.rs)

### Summary
`Vote.signature` is declared as an unconstrained dynamic `bytes` in Solidity [1](#0-0) . When a submitted `BeefyConsensusProof` is ABI-decoded and converted into the Substrate-side `SignatureWithAuthorityIndex` type, the conversion copies the raw `signature` bytes directly into a fixed 65-byte array with `copy_from_slice` and no length check beforehand [2](#0-1) .

### Finding Description
The Hydra NTLM bug class is: attacker-controlled variable-length field copied into a fixed-size buffer without a length check before the copy. The same pattern exists here: `impl From<Vote> for SignatureWithAuthorityIndex` does `let mut signature: TSignature = [0u8; 65]; signature.copy_from_slice(&sig_bytes);` where `sig_bytes` comes straight from the attacker-supplied `Vote.signature` (an unconstrained Solidity `bytes`) with no `if sig_bytes.len() != 65` guard [2](#0-1) . Rust's `copy_from_slice` panics whenever source and destination lengths differ, so any vote with a signature length other than exactly 65 bytes triggers an unconditional panic. This conversion is reachable from `beefy-consensus-proofs::verify_and_apply`, which ABI-decodes a submitted proof (`ismp_abi::ecdsa_beefy::BeefyConsensusProof`) and calls `.into()` to produce the SCALE-encoded consensus proof consumed by `handle_incoming_message` [3](#0-2) . Because `verify_and_apply` is invoked from an unsigned/permissionless extrinsic path that submits consensus proofs (any relayer or attacker can submit a proof pointing at the `PROOF_TYPE_NAIVE`/ECDSA path), an attacker only needs to submit a `Vote` whose `signature` bytes length is not 65 to trigger the panic during extrinsic dispatch.

### Impact Explanation
Unlike the original Hydra C stack overflow (memory corruption/RCE), Rust bounds-checks the copy and panics instead of corrupting memory, so this is not remote code execution. However, a panic occurring inside pallet dispatch/runtime logic during block execution is a runtime trap; depending on how `verify_and_apply` is wired into the dispatchable (whether the panic unwinds safely inside a `Result`-returning boundary or escapes into `on_initialize`/apply_extrinsic), this can abort block execution entirely, effectively halting BEEFY consensus-proof ingestion or, in the worst case, causing block-import failure network-wide — a denial-of-service on the message-relay/consensus-update path that "delivers messages" from the relay chain. This blocks all downstream state commitments and message delivery relying on BEEFY consensus updates until a patched runtime is deployed.

### Likelihood Explanation
High: `Vote.signature` has no length constraint in the Solidity struct [1](#0-0) , ABI decoding does not enforce a fixed length for `bytes`, and the conversion path executes unconditionally for every vote in a submitted commitment before any signature verification occurs, so a single malformed proof submission is sufficient.

### Recommendation
In `evm/rust/src/conversions.rs`, validate `sig_bytes.len() == 65` before `copy_from_slice` and return/propagate a proper `TryFrom` error instead of an infallible `From` implementation that can panic; propagate this as a decode/verification error through `beefy-consensus-proofs::verify_and_apply` so malformed proofs are rejected gracefully rather than panicking during dispatch.

### Proof of Concept
1. Submit a `BeefyConsensusProof` (via the extrinsic that calls `verify_and_apply`) containing a `SignedCommitment.votes[i].signature` of length ≠ 65 (e.g., 64 or 66 bytes) — this is unconstrained by the Solidity `bytes` type.
2. `verify_and_apply` ABI-decodes the payload and calls `.into()`, invoking `impl From<Vote> for SignatureWithAuthorityIndex` [2](#0-1) .
3. `signature.copy_from_slice(&sig_bytes)` panics because the slice length does not match the fixed 65-byte destination, aborting the extrinsic/block execution.
