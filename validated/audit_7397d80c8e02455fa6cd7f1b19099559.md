### Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards `request.shop` — a value taken from an **unsigned HTTP header** — to the app's handler as the tenant identifier. Because the `shop` field is never part of the signed content, a shop that legitimately possesses a validly-signed webhook body (from its own store) can replay it while substituting an arbitrary `x-shopify-shop-domain` value, causing the app to process attacker-controlled data as if it belonged to a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header without any cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the raw body) against the HMAC, so it never verifies which shop the body actually belongs to: [3](#0-2) 

`Registry.process` accepts the request as authentic purely on that body-only HMAC check, then dispatches to the handler using the unauthenticated `request.shop` value as the tenant/session key: [4](#0-3) 

This breaks the identity binding: `shop authenticated by HMAC != shop attributed to the data by Registry.process`. Since the app's `client_secret` (used to compute the webhook HMAC) is shared across every shop that has installed the app, any shop that is a genuine, unprivileged installer of the app receives correctly-HMAC'd webhook deliveries for its own data. That attacker-controlled shop can capture one of its own valid `(body, hmac)` pairs and POST it directly to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `Registry.process` will validate the HMAC successfully (it only checks the body) and hand the handler a `WebhookMetadata` object whose `shop` claims to be the victim, while the body content is actually the attacker's own (or attacker-crafted, if the attacker controls the underlying resource being described in the webhook body, e.g. `app/uninstalled`, `customers/data_request`, order webhooks for a shared resource, etc.).

### Impact Explanation
This is a cross-tenant identity confusion: attacker-controlled webhook data can be attributed to another merchant/shop inside the host application, letting a low-privilege actor (any shop that installs the app) inject or forge data belonging to another tenant. Given the rules' Critical bucket includes "cross-tenant access," and the root cause is squarely inside this gem's own HMAC verification code (only the body is authenticated, not the header-derived shop), this qualifies as in-scope.

### Likelihood Explanation
Requires only that the attacker's own shop has the app installed (an unprivileged, self-serve action) and the ability to send a raw HTTP POST to the app's public webhook endpoint with a modified header — both trivially available to any internet user testing a merchant-installed app. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered content, or independently verify that the shop in the header corresponds to a shop with an active app installation/subscription for that topic before trusting `request.shop` in `Registry.process`. At minimum, document that host applications must not treat `WebhookMetadata#shop` as authenticated without separately confirming the shop has a stored, valid session/installation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's `client_secret`.
3. Attacker intercepts/replays this exact `(raw_body, hmac)` pair via a direct HTTP POST to the same webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (`hmac` validated against `@raw_body` only), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds since it never inspects `shop`.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)` and processes/stores the attacker's data under the victim's tenant.
