Audit Report

## Title
Front-running of vesting-claim `dest` account blocks legitimate victim's later claim via `VestedBalanceExists` - (File: polkadot/runtime/common/src/claims/mod.rs)

## Summary
`Pallet::process_claim` gates vesting-schedule application to a caller-chosen `dest` account solely on whether that account already has a vesting balance (`T::VestingSchedule::vesting_balance(&dest).is_some()`), with no check that the entity installing an existing vesting lock has any legitimate relationship to a later claimant intending to use the same `dest`. Since `dest` is fully attacker-controlled and only bound by an ECDSA signature the attacker produces themselves, any holder of a valid vesting-flagged Ethereum claim can front-run and permanently occupy an arbitrary `dest` account, causing any different account's later vesting claim to that same `dest` to fail with `VestedBalanceExists`.

## Finding Description
`claim` and `claim_attest` are unsigned extrinsics validated only via ECDSA signature recovery over the caller-supplied `dest` value, with no origin/proxy binding tying `dest` selection to any specific claimant identity. `process_claim` retrieves the signer's optional vesting schedule and, if present, checks only `T::VestingSchedule::vesting_balance(&dest).is_some()` before calling `add_vesting_schedule(&dest, ...)`. This check verifies a property of the destination account, not any relationship between the current claim and whoever previously installed a lock there. An attacker who controls any Ethereum key with a registered vesting claim (even trivial in size) can sign over an arbitrary `dest = X`, submit `claim`/`claim_attest` first, and install a vesting lock on `X` — permanently causing a legitimate, unrelated claimant's later attempt to use `dest = X` to fail via the same `VestedBalanceExists` error path, since the existing check makes no distinction between "self re-claiming" and "different claimant's lock occupies this account."

## Impact Explanation
This is a destination-account-scoped denial-of-service/griefing vulnerability, not fund theft or unconditional fund freezing. The victim's underlying claim entry (`Claims`/`Vesting`, keyed by their Ethereum address) is untouched by the attacker's action and remains claimable to any other destination account. Real-world impact is therefore limited to scenarios where the victim is constrained to use one specific, attacker-predictable `dest` (e.g., a fixed off-chain/exchange deposit address), making this a griefing/availability issue against a specific account choice rather than a fund-loss vulnerability.

## Likelihood Explanation
Exploitation requires only that the attacker (a) control an Ethereum key with a valid vesting-flagged claim entry already registered in `Claims`/`Vesting` storage (via genesis config or root-authorized `mint_claim`), and (b) know or guess the victim's intended `dest` in advance, then submit an unsigned `claim`/`claim_attest` transaction ahead of the victim's. No special privilege, proxy approval, or victim mistake beyond predictable `dest` reuse is required, making the attack deterministic and repeatable once preconditions hold.

## Recommendation
- Avoid using destination-account state alone as the guard for "already vested"; consider recording which claim/signer installed a vesting schedule on a given `dest`, or otherwise distinguish "self already vested" from "different claimant's lock occupies this account" with a clearer error path.
- Consider documenting/enforcing at the wallet/UX layer that `dest` accounts for vesting claims should not be predictable or shared across independent claimants, since the current design intentionally permits any valid claim holder to choose an arbitrary `dest`.

## Proof of Concept
1. Register two Ethereum claim entries with vesting schedules in genesis/test config: an "attacker" key with a small claim, and a legitimate "victim" key (e.g., `alice()`) with a larger claim.
2. Submit `Claims::claim(RuntimeOrigin::none(), dest=X, attacker_sig_over_X)`; assert success and that `T::VestingSchedule::vesting_balance(&X)` is now `Some(..)`.
3. Submit `Claims::claim(RuntimeOrigin::none(), dest=X, victim_sig_over_X)`; assert it returns `Error::<T>::VestedBalanceExists`.
4. Submit `Claims::claim(RuntimeOrigin::none(), dest=Y, victim_sig_over_Y)` for a different `Y`; assert success, confirming the victim's claim entry is intact and the DoS is scoped to the specific contested `dest`.
