### Title
Operator QR-code authentication bypass via client-controlled `signup_extension` flag - ([File: src/plans/mod.rs])

### Summary
The reported bug class ("public setter with no access control that permanently fixes critical state, callable by anyone") maps onto a functionally analogous, and reachable, orb-core pattern: `verify_operator_qr_code` accepts operator identity/location as valid **without ever contacting the backend** whenever the QR code presented to the camera declares itself a `signup_extension` code, or when a CLI-provided operator QR override is set. Just like the `Auction.sol` example where `setIDOLContract()` trusted an unauthenticated caller to set irreversible critical state, this function trusts an attacker/unprivileged-user-controlled input (the raw content of a scanned QR code) to short-circuit the operator authorization check that is otherwise meant to be enforced by the backend.

### Finding Description
`verify_operator_qr_code` in `src/plans/mod.rs` is the function responsible for validating an operator QR-code against the backend before allowing a signup session to proceed: [1](#0-0) 

The critical branch is:
```
if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
    return Ok(Some((0, backend::operator_status::LocationData { ... })));
}
```
`qr_code` here is `qr_scan::user::Data`, which is parsed directly from the content of a physically scanned QR-code (an untrusted, unprivileged-user-controlled input), via `qr_scan::operator::Data::try_parse` / `user::Data::try_parse`: [2](#0-1) 

Rather than only trusting `signup_extension` under a build-time flag such as `internal-data-acquisition`, the check inside `verify_operator_qr_code` is unconditional at this code site — any QR code whose parsed `Data` structure reports `signup_extension() == true` causes the function to return a synthetic "valid" location/authorization result with zero backend round-trip, exactly mirroring the reported anti-pattern of an access-control-free function that sets a security-critical value ("this operator QR is authenticated") based purely on attacker-supplied input.

Downstream, this bypass propagates into `OperatorData`, which is subsequently used to gate the entire signup flow (`scan_initial_qr_codes`, `scan_remaining_qr_codes`, `handle_user_qr_code`) and is embedded into the signup POST request as the authenticated `distributorId`: [3](#0-2) [4](#0-3) 

While there is a partial mitigating filter elsewhere (`handle_user_qr_code`, `scan_operator_qr_code`) that rejects `signup_extension` QR codes when the `internal-data-acquisition` feature is *not* compiled in: [5](#0-4) 
this filtering is inconsistent — it is applied in the QR-scanning helper functions but the authorization bypass itself lives in `verify_operator_qr_code`, which does not re-check the `internal-data-acquisition` feature flag before trusting `signup_extension()`. I was not able to fully verify, within the remaining search budget, whether every code path that calls `verify_operator_qr_code` is guaranteed to have already filtered out `signup_extension` QR codes in all builds, or whether a code path exists (e.g., via `scan_initial_qr_codes`'s self-serve loop, which does not appear to apply the `internal-data-acquisition` filter before calling `verify_operator_qr_code`) that would let an attacker-crafted QR code reach this bypass in a production (non-data-acquisition) build.

### Impact Explanation
If reachable in a production build, this allows an unprivileged individual holding a physical, self-crafted QR code to be scanned by the orb to have the operator-authorization step accepted without any backend validation, using synthetic/dummy location data (`"DEV"`, `0.0, 0.0`). This is a direct analog to "unauthorized signup" / "misattributed signup" impact: the identity binding between a signup session and a legitimately-vetted operator/distributor is broken, letting an attacker impersonate an authorized operator and initiate signups (and thus biometric capture/enrollment sessions) that should require backend-verified operator credentials.

### Likelihood Explanation
Likelihood depends entirely on whether the `signup_extension`-driven bypass in `verify_operator_qr_code` is reachable outside of the `internal-data-acquisition`-gated code paths. The QR-scanning entry points (`scan_operator_qr_code`, `handle_user_qr_code`) do filter `signup_extension` codes when that feature is disabled, but I could not confirm from the available index that `scan_initial_qr_codes`'s self-serve branch (which calls `verify_operator_qr_code` directly after `handle_magic_operator_qr_code`) applies the same filter before validation in non-data-acquisition builds. This uncertainty should be resolved by a full read of `src/plans/mod.rs` and `src/plans/qr_scan/user.rs` (`signup_extension()`, `signup_extension_config`) to confirm build-flag gating end-to-end.

### Recommendation
- Move the `internal-data-acquisition` feature check (or an equivalent explicit authorization check) directly inside `verify_operator_qr_code`, rather than relying on upstream callers to have already filtered `signup_extension` QR codes.
- Never allow client/QR-supplied data alone (`qr_code.signup_extension()`) to substitute for backend-verified operator location/validity data in production builds; require the backend call unconditionally unless a compile-time, non-attacker-controllable flag explicitly enables the test/data-acquisition bypass.
- Add a regression test asserting that in a build without `internal-data-acquisition`, no QR code content can cause `verify_operator_qr_code` to return `Some(...)` without invoking `backend::operator_status::request`.

### Proof of Concept
Note: full exploitability could not be confirmed within the available tool budget. Conceptual PoC:
1. Craft a QR code payload that `user::Data::try_parse` parses such that `signup_extension() == true` (with `signup_extension_config` present, per the filter in `qr_scan::operator::Data::try_parse`, `src/plans/qr_scan/operator.rs:40-45`).
2. Present this QR code to the orb camera as the "operator" QR-code during the self-serve QR scanning loop (`scan_initial_qr_codes`, `src/plans/mod.rs:749-786`).
3. If this path does not apply the `internal-data-acquisition` filter (as `scan_operator_qr_code` does at `src/plans/mod.rs:906-916`), `verify_operator_qr_code` (`src/plans/mod.rs:1550-1557`) short-circuits and returns `Ok(Some((0, LocationData{ team_operating_country: "DEV", ... })))` without any backend call, granting operator authorization to an unverified party.

    /// Checks if `qr_code` is a valid operator QR-code through the backend.
    #[allow(clippy::cast_possible_truncation)]
    async fn verify_operator_qr_code(
        &self,
        orb: &mut Orb,
        qr_code: &qr_scan::user::Data,
        qr_capture_start: Instant,
    ) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
        if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
            return Ok(Some((0, backend::operator_status::LocationData {
                team_operating_country: "DEV".to_string(),
                session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
                stationary_location_coordinates: None,
            })));
        }
        let http_start = Instant::now();
        match backend::operator_status::request(qr_code).await {
            Ok(backend::operator_status::Status { valid: true, location_data, reason: _ }) => {
                let location_data = location_data
                    .expect("to always have a result from the backend if valid == true");
                orb.ui.qr_scan_success(QrScanSchema::Operator);
                dd_incr!("main.count.global.distr_code_validated");
                tracing::info!("Operator QR-code validated: {qr_code:?}");
                dd_timing!("main.time.signup.distr_qr_code_capture", qr_capture_start);
                return Ok(Some((http_start.elapsed().as_millis() as u64, location_data)));
            }
            Ok(backend::operator_status::Status { valid: false, .. }) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
                dd_incr!("main.count.signup.result.failure.distr_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
            }
        }
        Ok(None)
    }
