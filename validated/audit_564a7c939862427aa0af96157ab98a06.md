### Title
Webhook `shop-domain` header is trusted as the tenant identifier without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by HMAC-validating only the raw request body, then passes the shop identity taken from an unauthenticated header directly to the app's webhook handler as the tenant for that event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is completely outside that signable string: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only proves the raw body bytes were signed with the app's secret; it says nothing about the headers: [4](#0-3) 

Yet `Registry.process` uses that same unauthenticated `request.shop` value as the tenant identity forwarded to the app's business logic: [5](#0-4) 

This is inconsistent with how the gem treats `shop` elsewhere: in the OAuth callback flow, `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` inside the HMAC-covered payload, so the shop cannot be swapped without invalidating the signature: [6](#0-5) 

The webhook path breaks the same binding that the OAuth path enforces: `shop authenticated (via HMAC) != shop acted upon (via header, used as tenant key)`. Because the app-wide `client_secret`/`api_secret_key` used to compute the webhook HMAC is shared across every shop that installs the app, any merchant that installs the app can receive a genuinely-signed webhook delivery to their own endpoint, then intercept/replay it while altering only the `x-shopify-shop-domain` header (and/or reusing that valid body+HMAC pair for a different topic-compatible body payload) before it reaches `Registry.process`. The signature still validates because the header is not part of the signed content, but `request.shop` — trusted as the tenant identity — now points at an arbitrary attacker-chosen value.

### Impact Explanation
Any consumer of this gem that uses `WebhookMetadata#shop` (populated from `request.shop`) to select which merchant's session/record to mutate is exposed to cross-tenant data corruption: an attacker with a legitimate installation of the app can cause webhook-driven writes/reads to be attributed to a different shop than the one that actually produced the signed payload, since the shop identity is never bound to the HMAC. This matches the "cross-tenant access" Critical impact category since the shop identity used to route/act on data is forgeable independent of the cryptographic authenticity check.

### Likelihood Explanation
The only requirement to exploit this is having your own legitimate app installation that receives real webhook deliveries (something any unprivileged merchant/attacker with the app installed can obtain) and the ability to replay an HTTP request to the app's own webhook endpoint with a modified header — no access to `api_secret_key`, tokens, or any privileged credential is needed.

### Recommendation
Include the shop-identifying header (and other headers the app is expected to trust, e.g. `topic`, `api-version`, `webhook-id`) inside the HMAC-covered signable content for webhook requests, mirroring how `Auth::Oauth::AuthQuery` binds `shop` into its `to_signable_string`. At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/etc. are NOT authenticated by the HMAC check and must not be used as a trust boundary by consuming applications, or provide a verified variant that cryptographically binds these fields.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook to the app's callback URL with headers `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
2. Attacker captures this request (they control network traffic to their own endpoint) and resends it to the app's endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping `raw_body`/`hmac` untouched.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC: [7](#0-6) 
4. `handler.handle` receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload never touched Shopify's systems for that shop: [5](#0-4) 
5. Any host application logic keyed off `WebhookMetadata#shop` now acts on the wrong tenant.
