Confirmed: `Registry.process` at [1](#0-0)  passes `request.shop` (the `x-shopify-shop-domain` header) straight into the `WebhookMetadata` handed to the app's handler, while the HMAC signature only ever covers the raw body via `to_signable_string` returning `@raw_body` at [2](#0-1)  and `shop` is read from an unsigned header at [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC exclusively to the raw request body, but `Registry.process` trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identity for dispatch to host application webhook handlers.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body` [4](#0-3) . `HmacValidator.validate` recomputes the HMAC over `to_signable_string` and compares it to the received value [5](#0-4) . Since `to_signable_string` never includes `shop`, `topic`, `api_version`, or `webhook_id`, none of these fields are cryptographically bound to the signature — only the JSON body is.

`Registry.process` calls `Utils::HmacValidator.validate(request)` (validating only the body) and, if it passes, immediately constructs `WebhookMetadata` using `request.shop`, which is read straight from the mutable header via `shopify_header("shop-domain")` [1](#0-0) [3](#0-2) . This breaks the identity binding `HMAC-signed-shop == dispatched-shop`: the HMAC only proves "this app's secret produced a signature for this exact body," it proves nothing about which shop that body belongs to.

An attacker who can obtain (or replay) any single valid `(body, hmac)` pair delivered to the app's webhook endpoint — e.g. a webhook for their own store, or one observed via a shared/logging proxy, load balancer, or any intermediary that is not the direct Shopify-to-app TLS channel — can resubmit the identical body/hmac pair to the app's webhook endpoint while substituting an arbitrary value in `x-shopify-shop-domain`. The HMAC check still passes because it only verifies the body bytes, so `Registry.process` will invoke the host application's `WebhookHandler#handle` with `WebhookMetadata.shop` set to the attacker-chosen shop string, alongside another shop's real payload body.

### Impact Explanation
Applications commonly key their persistence, session lookup, or per-tenant business logic off `WebhookMetadata.shop` (this is exactly why the gem exposes it as the tenant identifier in the callback). Because `shop` is unauthenticated relative to the HMAC, an attacker controlling only the header of a resent/observed request can cause the host app to attribute one tenant's data to a different tenant string of the attacker's choosing — a cross-tenant data confusion/injection primitive stemming purely from this gem's signature scope, not from any misuse of a documented API.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid `(body, hmac)` pair for the app's secret — most straightforwardly their own store's outgoing webhook, since any store can trigger webhooks the app receives (e.g. `shop/redact`, `orders/create` if the attacker has a store installed against the same app). No possession of `api_secret_key` or any access token is required; only network delivery/replay of an intercepted-or-self-generated legitimate webhook body+hmac with a forged shop header is needed, which is a realistic capability for any merchant/tenant of a multi-tenant app.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string alongside the raw body (or otherwise cryptographically bind them, e.g. via a canonical string prefix before HMAC verification), so `HmacValidator.validate` fails whenever any of these header-derived fields are altered relative to what was originally signed by Shopify.

### Proof of Concept
1. App receives a legitimate webhook for `victim-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker (who owns their own store registered with the same app, or otherwise obtains `B`/`H`) resends a request to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: attacker-controlled-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) — this matches `H`, so validation passes [6](#0-5) .
4. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, body: request.parsed_body, ...))` with `shop` equal to the attacker-forged domain, while `body` is the victim's real payload [7](#0-6) .
5. The host application, trusting the gem's binding of body-to-shop, processes victim data under the attacker's shop identity (or vice versa), causing cross-tenant data confusion entirely due to this gem's incomplete HMAC scope.
