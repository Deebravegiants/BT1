### Title
Unbounded recursive traversal of attacker-controlled `error.cause` chain in `@exodus/json-rpc` can crash/hang the wallet RPC bridge - (File: libraries/json-rpc/index.js)

### Summary
The Hats Protocol report describes recursive functions (`isAdminOfHat`, `getImageURIForHat`, `getTippyTopHatDomain`, `noCircularLinkage`) that walk an attacker-influenceable linked structure with no depth cap, letting an adversary grow the structure until traversal exhausts the available resource (gas) and blocks legitimate operations. The Hydra codebase's `@exodus/json-rpc` package contains a structurally analogous pattern: `RPC._createRecursiveError()` recursively walks an `error.cause` chain taken directly from a JSON-RPC response with no depth limit, and this RPC channel is the bridge used between the extension's privileged background (which hosts `@exodus/keychain` and signs transactions) and the content-script/webpage side.

### Finding Description
`RPC._makeErrorObject()` is invoked from `_processResponse()` whenever an incoming message contains an `error` field, and it calls `_createRecursiveError(cause)` on `errorData.data.cause`: [1](#0-0) 

```js
_createRecursiveError(error) {
  if (typeof error !== 'object' || error === null) {
    return null
  }
  let cause = null
  if (error.cause) {
    cause = this._createRecursiveError(error.cause)   // unbounded recursion
  }
  ...
}
```

`error.cause`/`error.data.cause` originates from the raw parsed RPC message, which is attacker/counterparty-controlled: [2](#0-1) . There is no depth counter, no maximum-nesting check, and no schema validation on the shape of `errorData.data` before recursing, unlike the analogous `SafeError`/`linkedErrors` handling elsewhere in the codebase which explicitly caps depth (`MAX_LINKED_ERRORS_DEPTH`): [3](#0-2) . `@exodus/json-rpc` itself has no such cap.

This `RPC` class is the base for both the SDK bridge and the browser-extension bridge:
- `@exodus/sdk-rpc`'s `RPC` extends `JsonRPC` directly and is used to expose the full wallet SDK (`headless`) over a transport (window/webview transport) between the UI process and the API/background process: [4](#0-3) .
- `@exodus/browser-extension-rpc/inapp.js` instantiates `@exodus/json-rpc`'s `RPC` directly on a `createWindowRpcTransport`, which is the channel used on the in-page/content-script side facing the webpage: [5](#0-4) , relayed through `content.js`'s window-postMessage transport: [6](#0-5) .

Because `parse` defaults to `JSON.parse` and there is no depth check before `_createRecursiveError` recurses, a peer on either end of this bridge (e.g. a malicious or compromised counterparty able to inject a crafted `{"error": {"data": {"cause": {"cause": {"cause": ... }}}}}` payload with deep nesting) can force the process handling that response into unbounded synchronous recursion, causing a stack overflow / hang on the thread processing RPC traffic.

### Impact Explanation
If this hang/crash occurs on the same JS process/thread that also handles signing requests, subsequent legitimate signing/approval RPC calls queued or dispatched after the malicious payload can be blocked or the process itself can crash, denying wallet operations (analogous to the Hats issue's "won't be possible to perform actions... funds can be lost"). This is a denial-of-service on a trust-boundary-crossing channel (RPC bridge between privileged wallet backend and web content), not a Solidity gas-based issue, but it maps to the same root cause class: attacker-controlled recursion depth with no cap.

### Likelihood Explanation
Requires a peer able to send a crafted JSON-RPC error response over one of these transports (e.g., a malicious/compromised UI-side process, a malicious page interacting through the extension bridge, or any transport implementer that doesn't otherwise sanitize responses). Depth of recursion needed to overflow the stack is not exotic (a few thousand nested objects), and the payload can be constructed with a small script producing a large but not enormous JSON string, so it is practically achievable if reachable through an unprivileged/less-trusted side of the channel.

### Recommendation
Add a maximum recursion/depth guard in `_createRecursiveError` (and ideally validate the general shape/size of `errorData.data` before processing), mirroring the `MAX_LINKED_ERRORS_DEPTH` cap already used in `@exodus/errors`'s `SafeError`. Alternatively, convert the recursive walk to an iterative one with an explicit depth limit, and reject/truncate `cause` chains beyond the threshold instead of recursing unbounded.

### Proof of Concept
Send an RPC response over any transport in which a counterparty can inject the "error" JSON payload processed by `_processResponse`/`_makeErrorObject`, e.g.:
```json
{
  "jsonrpc": "2.0",
  "id": 0,
  "error": {
    "code": -32000,
    "message": "boom",
    "data": { "cause": { "cause": { "cause": { "...nested 50,000 times..." } } } }
  }
}
```
When the recipient's `RPC` instance (using `@exodus/json-rpc`'s `_processResponse` → `_makeErrorObject` → `_createRecursiveError`) parses this, it recurses once per nesting level with no cap, producing a `RangeError: Maximum call stack size exceeded` (or, on some engines/large-enough payloads, extended blocking before overflow), potentially crashing/hanging the process handling the RPC channel used for wallet signing operations.

Note: I could not fully verify from the indexed code whether the browser-extension/webpage side of this bridge can directly control the `error` object delivered to the extension background's privileged `RPC` instance in the current build (vs. only UI↔background), since the full runtime wiring (`channel.call`, `port.postMessage` handlers) wasn't completely available in the index. A Devin session with full repo access would be needed to confirm the exact reachable trust boundary and to trace whether an unprivileged webpage can reach the background-side `RPC._processResponse` path.

export const createRPCProxy = ({ extensionName, channelName }) => {
  if (typeof extensionName !== 'string' || typeof channelName !== 'string') {
    throw new TypeError(`Unable to create RPC because channelName or extensionName are missing`)
  }

  const channel = channels[channelName]
  const transport = createWindowRpcTransport({
    name: `${extensionName}-${channelName}`,
    target: `${extensionName}-${channelName}-window`,
  })

  transport.on('data', async (event) => {
    const isResponse = !JSON.parse(event).method
    const senderMetadata = await metadata
    const options = { senderMetadata }

    if (isResponse) {
      channel.sendMessage(event, options)
    } else {
      channel.call(event, options).then(transport.write)
    }
  })

  channel.onMessage((message, sender) => {
    if (sender.tab) return
    transport.write(message)
  })
}
