### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate` succeeds, and then passes the caller-supplied `x-shopify-shop-domain` header straight to the handler as the tenant identifier. The HMAC, however, only ever covers the raw request body — not the shop-domain header — so the "verified" bytes (the body) and the "used" identity (the shop) are decoupled, exactly the mismatch pattern described in the report (data verified for one context being reused for a different, unverified context).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the signature purely from that signable string: [2](#0-1) 

`Registry.process` uses this single check to gate the entire request, then reads `request.shop` (the `x-shopify-shop-domain`/`shopify-shop-domain` header, never covered by the HMAC) and forwards it to the merchant-facing handler as the trusted tenant identity: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`shop_used_by_handler == shop_that_the_HMAC-verified_body_actually_belongs_to`

but the code only proves `body_bytes == HMAC(body_bytes, client_secret)`; it never proves the header-supplied `shop` is bound to that body. Because a single app's `client_secret` is shared across every shop that installs the app, any actor who can trigger a legitimate webhook to themselves (e.g., by installing the app on their own store, a normal, unprivileged action) obtains a valid `(body, hmac)` pair signed with the app's real secret. They can then replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at the shop header), so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain, `even though the payload was never generated for that shop`. This lets an unprivileged internet user forge webhook events attributed to an arbitrary tenant, exactly the cross-tenant boundary break the rules call out ("a shop authenticated versus the shop stored as a session key").

The library's own documentation reinforces the false assumption that `Registry.process` fully authenticates the request ("This will verify the request did indeed come from Shopify"), without noting that the shop identity itself is unverified, so host apps have no signal that they must independently bind `data.shop` to a known/active session before trusting it.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker can make the host application process attacker-controlled webhook data as if it belonged to a different merchant/shop, corrupting per-tenant state, queuing spoofed background jobs (`perform_later(shop_domain: data.shop, ...)` as shown in the gem's own documented example), or triggering shop-scoped business logic for a shop the attacker has no relationship with. This matches the High-impact category of a scope/tenant boundary bypass driven by a credential-binding gap in the gem's own webhook verification code path.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one valid `(body, hmac)` pair only requires installing the app on the attacker's own shop (a normal, unprivileged flow available to anyone), and constructing the replayed request only requires basic HTTP tooling to swap one header. No access to `api_secret_key`, tokens, or the victim's credentials is required.

### Recommendation
Bind the shop identity into the verified signal before trusting it:
- Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or
- After HMAC validation, require that `request.shop` correspond to a shop for which the app already holds an active, previously-established session/registration before invoking the handler, and reject/flag mismatches, and
- Update `docs/usage/webhooks.md` to explicitly state that `Registry.process` only proves body integrity, not the shop's authenticity, so integrators know they must cross-check `data.shop` against known installed shops.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify send a legitimate webhook; attacker captures the raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify using the app's shared `client_secret`).
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers; `HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so `Registry.process` proceeds: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as if it were genuine data from the victim shop.
