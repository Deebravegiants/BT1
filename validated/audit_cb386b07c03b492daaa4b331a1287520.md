## Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to identify and route the webhook are read from unauthenticated HTTP headers. `Registry.process` verifies the body's HMAC but then dispatches the handler using these unauthenticated header values, breaking the binding `hmac == f(shop, body)` that a webhook consumer should be able to rely on.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`, and hands this directly to the host application's handler: [3](#0-2) 

This differs materially from the OAuth callback flow in this same gem, where the equivalent identity field (`shop`) *is* part of the signed payload: [4](#0-3) 

For webhooks, the equality the consumer expects — "the shop this payload is attributed to" == "the shop the HMAC was computed for" — does not hold, because the HMAC only proves "the app's secret produced/knows this exact `hmac-sha256` value for this exact body," not "this body belongs to shop X." An unprivileged actor who controls or can observe any single genuine webhook delivery for their own shop (i.e., a legitimate merchant installing the app, who receives real `body` + `hmac-sha256` pairs from Shopify for their own store) can replay that same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`/`webhook-id`) header value. `Utils::HmacValidator.validate` will still pass because it only checks the body against the secret, never binding the header-derived shop/topic to the signed content: [5](#0-4) 

### Impact Explanation
Handlers registered via `ShopifyAPI::Webhooks::Registry` are typically used by host applications to key per-tenant state changes (e.g., uninstall cleanup, GDPR redact operations, plan/billing state, order/customer data sync) off of `WebhookMetadata#shop`. Because that value isn't bound to the HMAC, an attacker who is a legitimate (even free/unprivileged) merchant of the app can forge cross-tenant webhook deliveries, causing the host app to process attacker-supplied body content under a victim shop's identity. This is a cross-tenant identity-binding break consistent with the Critical impact category ("cross-tenant access").

### Likelihood Explanation
Exploitation requires only: (1) installing the app as any ordinary merchant to receive at least one genuine webhook (topic/body/HMAC triple) from Shopify, and (2) sending a forged HTTP request with the same raw body + HMAC header but a different `x-shopify-shop-domain` value to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — this satisfies the "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (whatever is used for dispatch/attribution) as part of the HMAC-signable content in `Request#to_signable_string`, or independently verify that the shop resolved from the header matches a shop the app expects for that specific signed payload before dispatching to handlers, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. App merchant M installs the app; Shopify delivers a webhook to the app with body `B`, headers `x-shopify-shop-domain: m-shop.myshopify.com`, `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Attacker (= merchant M) replays: `POST /webhooks` with body `B`, `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, and performs its tenant-scoped action as though it originated from the victim shop.
