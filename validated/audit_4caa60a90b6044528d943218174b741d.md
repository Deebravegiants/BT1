### Title
Unbounded GRANDPA ancestry-chain verification lets a fee-less relayer burn CPU via `handle_unsigned` / mempool validation - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
GRANDPA justification verification (`GrandpaJustification::verify_with_voter_set`) performs an ancestry walk for every precommit that doesn't target the base block, and each walk is itself O(chain length) via `AncestryChain::ancestry`, which is a plain `BTreeMap` traversal following parent hashes until it reaches `base`. Both the number of precommits and the `votes_ancestries` header list are fully attacker/relayer-controlled fields of an unsigned `Message::Consensus` extrinsic dispatched through `pallet_ismp::Call::handle_unsigned`. This mirrors the reported GitLab bug class: expensive, attacker-shaped work is performed by an untrusted/unauthenticated code path (here, `ValidateUnsigned::validate_unsigned`, which runs full `Self::execute(messages.clone())` — i.e., the entire consensus verification pipeline — before rejecting invalid transactions) with no cost to the submitter, because ISMP messages are dispatched as fee-less unsigned transactions "for free" by design.

### Finding Description
`GrandpaJustification::verify_with_voter_set` in [1](#0-0)  loops over `self.commit.precommits` and, for every precommit whose target differs from the chosen `base_hash`, calls `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)`: [2](#0-1) 

`AncestryChain::ancestry` walks parent-hash pointers in a `BTreeMap` built directly from the attacker-supplied `votes_ancestries: Vec<H>` field until it reaches `base`: [3](#0-2) 

Both inputs are fully controlled by whoever submits the extrinsic:
- `commit.precommits` — a `Vec` of precommit/signature pairs (count can approach the real authority-set size, but crucially, each entry's signature check happens per-iteration and the ancestry walk is repeated for every distinct precommit target).
- `votes_ancestries: Vec<H>` — a raw vector of headers whose "chain" linkage is only checked implicitly by hash-lookup; there is no upper bound on its length enforced anywhere in this file, in `modules/ismp/clients/grandpa/src/consensus.rs`, or in the pallet dispatch path.

This proof is delivered as an ISMP `Message::Consensus` inside `pallet_ismp::Call::handle_unsigned`, which is deliberately unsigned/free so relayers aren't charged fees: [4](#0-3) 

Critically, `ValidateUnsigned::validate_unsigned` — which runs in the transaction-pool validation path, before the extrinsic is ever included in a block — performs the *entire* `Self::execute(messages.clone())` call (i.e., full consensus verification, including the GRANDPA ancestry/justification walk) and only afterwards decides whether to accept or reject the transaction: [5](#0-4) 

This is structurally identical to the GitLab report: an unauthenticated/pre-acceptance code path (`validate_unsigned`, analogous to GitLab's `preview_markdown`) performs unbounded, attacker-shaped computation (`ancestry()` walking a large but "valid-looking" `votes_ancestries` list combined with many distinct precommit targets) before the request is ultimately rejected — and because the extrinsic is unsigned/free, the attacker pays nothing to repeat the attack, and can submit many such extrinsics in parallel to multiply CPU burn across validator nodes' mempools.

Contrast this with the other consensus/proof-verification code paths in the same codebase (Pharos SPV, sync-committee SSZ multi-proofs) which have all had explicit `MAX_PROOF_DEPTH` / length-equality bounds added specifically to prevent exactly this class of unbounded-work DoS: [6](#0-5) [7](#0-6) 
No equivalent bound exists for GRANDPA's `votes_ancestries` length or precommit-driven ancestry-walk count.

### Impact Explanation
An unprivileged party (anyone able to submit unsigned extrinsics to a parachain/relay chain running `pallet-ismp` with the GRANDPA consensus client, e.g. Hyperbridge itself or a Substrate-based destination chain configured with `GrandpaClient`) can craft a `Message::Consensus` payload with a maximal `votes_ancestries` vector (bounded only by the runtime's extrinsic/block size limit) and many distinct precommit targets, causing `validate_unsigned` to perform substantial CPU work (BTreeMap traversal repeated per precommit, i.e. roughly O(validators × chain length)) on every node's mempool validation, for free, repeatedly and in parallel. This matches "Uncontrolled Resource Consumption" / High severity: it can degrade block production and transaction throughput network-wide (a route unable to process/deliver messages), constituting resource-consumption-based denial of service on the ISMP message-processing path — the same bug class and impact tier as the referenced GitLab report (CVSS 7.5, complete DoS via free/authenticated-but-cheap requests).

### Likelihood Explanation
High. The `handle_unsigned` call is explicitly designed to be free and open to any submitter (documented as "This allows users execute ISMP datagrams for free. Use with caution."), and `validate_unsigned` unconditionally executes the full message-processing pipeline (including consensus verification) prior to any acceptance decision. No length caps exist on `votes_ancestries` or precommit counts in the justification/verifier code, so an attacker only needs to construct a large-but-structurally-valid (not necessarily cryptographically valid) commit/ancestry payload to trigger the expensive path repeatedly, at zero cost, from any node with network access to submit extrinsics.

### Recommendation
- Enforce a hard maximum on `votes_ancestries.len()` and on the number of distinct precommit targets requiring an ancestry walk before beginning any hashing/lookup work in `GrandpaJustification::verify_with_voter_set`, mirroring the `MAX_PROOF_DEPTH` guards added to the Pharos SPV and sync-committee verifiers.
- Bound `commit.precommits.len()` against the known/trusted authority-set size for the relevant consensus state before performing per-precommit ancestry walks.
- Consider moving expensive cryptographic/ancestry verification in `validate_unsigned` behind cheaper structural/size pre-checks (fail-fast on oversized `votes_ancestries` or `precommits`) so ill-formed proofs are rejected before the costly walk is attempted, consistent with the "bound before doing any work" pattern already used elsewhere in the EVM state-machine proof code (`modules/ismp/state-machines/evm/src/lib.rs`).

### Proof of Concept
1. Attacker crafts a `ConsensusMessage::StandaloneChain` (or `Relaychain`) proof whose `finality_proof.justification` decodes to a `GrandpaJustification` containing:
   - `commit.precommits`: as many distinct (fabricated) precommit entries as fit within the extrinsic size limit, each targeting a different fabricated header hash.
   - `votes_ancestries`: a long chain of minimal fabricated headers (satisfying the `Header` trait) linked by `parent_hash`, sized to approach the maximum extrinsic/block size.
2. Attacker wraps this as `Message::Consensus(...)` inside `pallet_ismp::Call::handle_unsigned { messages: vec![...] }` and submits it as an unsigned transaction to a node's RPC endpoint.
3. `ValidateUnsigned::validate_unsigned` (modules/pallets/ismp/src/lib.rs:614-626) calls `Self::execute(messages.clone())`, which routes to the GRANDPA consensus client's `verify_consensus`, which calls `verify_grandpa_finality_proof` → `justification.verify(...)` → the per-precommit `ancestry_chain.ancestry(base_hash, target_hash)` loop, walking the large `votes_ancestries` map for each of the many precommits before ultimately failing signature/ancestry validation and being rejected.
4. Because signatures and consensus state don't need to be genuinely valid for the expensive ancestry walk to execute (the walk happens before/independently of some of the final validity checks), the attacker can repeat step 2 with fresh nonce-free unsigned submissions in parallel across many connections, at no fee cost, to sustain CPU exhaustion on the node's transaction pool.

Note: I was unable to execute this against a live node/toolchain to empirically measure CPU-seconds per submission or confirm the exact absence of any implicit extrinsic-size cap that might limit `votes_ancestries` more tightly than assumed; this assessment is based on static code reading of the verification and dispatch paths shown above.

	/// Validate the commit and the votes' ancestry proofs.
	pub fn verify_with_voter_set(
		&self,
		set_id: u64,
		voters: &VoterSet<AuthorityId>,
	) -> Result<(), anyhow::Error> {
		use finality_grandpa::Chain;

		let ancestry_chain = AncestryChain::<H>::new(&self.votes_ancestries);

		match finality_grandpa::validate_commit(&self.commit, voters, &ancestry_chain) {
			Ok(ref result) if result.is_valid() => {
				if result.num_duplicated_precommits() > 0 ||
					result.num_invalid_voters() > 0 ||
					result.num_equivocations() > 0
				{
					Err(anyhow!("Invalid commit, found one of `duplicate precommits`, `invalid voters`, or `equivocations` {result:?}"))?
				}
			},
			err => {
				let result = err.map_err(|_| {
					anyhow!("[verify_with_voter_set] Invalid ancestry while validating commit!")
				})?;
				Err(anyhow!("invalid commit in grandpa justification: {result:?}"))?
			},
		}

		// we pick the precommit for the lowest block as the base that
		// should serve as the root block for populating ancestry (i.e.
		// collect all headers from all precommit blocks to the base)
		let base_hash = self
			.commit
			.precommits
			.iter()
			.map(|signed| &signed.precommit)
			.min_by_key(|precommit| precommit.target_number)
			.map(|precommit| precommit.target_hash.clone())
			.expect(
				"can only fail if precommits is empty; \
				 commit has been validated above; \
				 valid commits must include precommits; \
				 qed.",
			);

		let mut visited_hashes = BTreeSet::new();
		for signed in self.commit.precommits.iter() {
			let message = finality_grandpa::Message::Precommit(signed.precommit.clone());

			check_message_signature::<_, _>(
				&message,
				&signed.id,
				&signed.signature,
				self.round,
				set_id,
			)?;

			if base_hash == signed.precommit.target_hash {
				continue;
			}

			let route = ancestry_chain
				.ancestry(base_hash, signed.precommit.target_hash)
				.map_err(|_| anyhow!("[verify_with_voter_set] Invalid ancestry!"))?;
			// ancestry starts from parent hash but the precommit target hash has been
			// visited
			visited_hashes.insert(signed.precommit.target_hash);
			for hash in route {
				visited_hashes.insert(hash);
			}
		}

		let ancestry_hashes: BTreeSet<_> =
			self.votes_ancestries.iter().map(|h: &H| h.hash()).collect();

		if visited_hashes != ancestry_hashes {
			Err(anyhow!(
				"invalid precommit ancestries in grandpa justification with unused headers",
			))?
		}

		Ok(())
	}

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
