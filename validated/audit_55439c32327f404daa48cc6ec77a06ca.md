### Title
Reserve fee permanently lost when vault's outstanding debt persists after total LP-share supply is fully redeemed to zero - ([File: mainnet/contracts/vault/v0-vault-ststxbtc.clar])

### Summary
`accrue()` in each Zest v2 lending vault computes the DAO-treasury's cut of newly accrued interest (`reserve-inc`) and converts it into LP shares (`treasury-lp`) by multiplying against the *current* `total-supply`. If `total-supply` is `u0` at accrual time — which is reachable because `redeem()` allows LP holders to fully exit while borrower debt remains outstanding — `treasury-lp` is forced to `u0` regardless of how large `reserve-inc` is, and that period's reserve fee is permanently discarded rather than deferred or tracked.

### Finding Description
`accrue()` computes: [1](#0-0) 

The key line is:
```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```
`treasury-lp` is the amount of `zft` minted to `.dao-treasury` to represent its claim on the reserve fee. Because `mul-div-down` multiplies by `(total-supply)`, when `total-supply` is `u0` the result of `mul-div-down reserve-inc u0 X` is `u0` **no matter how large `reserve-inc` is** — the treasury simply gets nothing minted for that accrual, even though `reserve-inc` (real, borrower-paid interest owed to the treasury) was non-zero.

The same pattern appears in the "preview" helper used for deposit/redeem pricing: [2](#0-1) 

`total-supply` can legitimately reach zero while debt is still outstanding: `redeem()` only checks the caller's own balance, available liquidity, and slippage — it never checks whether `total-debt()`/`total-borrowed` is zero: [3](#0-2) 

Sequence:
1. LP depositors deposit; a borrower calls `system-borrow` against that liquidity, creating outstanding `principal-scaled`/`total-borrowed`.
2. All LP depositors call `redeem()` and fully exit; `total-supply` (the `zft` supply) drops to `u0`. The borrower's debt is untouched — `redeem()` has no dependency on debt state.
3. Interest continues to accrue on the outstanding debt. Every `accrue()` call (triggered by any subsequent `system-repay`, `system-borrow`, or admin action) computes a non-zero `reserve-inc` from `debt-delta`, but `treasury-lp` mints `u0` because `total-supply` is `u0`.
4. This repeats for as long as `total-supply` remains `u0` (which can be an arbitrarily long period, since nothing forces new deposits). All treasury reserve fees accrued in this period are irrecoverably lost — there is no pending/accumulator variable that stores the skipped `reserve-inc` for later minting once `total-supply` becomes non-zero again.

This is structurally identical to the reported `CDSLib::calculateCumulativeRate()` bug: a fee that should always be tracked is instead conditioned on a supply/pool-size variable being non-zero, and when that variable is zero the fee is silently dropped rather than deferred, permanently losing protocol yield.

### Impact Explanation
This causes permanent loss of protocol reserve-fee revenue (the DAO treasury's cut of borrower interest) for any period during which the vault has outstanding debt but zero LP-share supply. Because nothing accumulates the missed `reserve-inc`, once `total-supply` becomes non-zero again the lost fee cannot be recovered — it is gone forever, not merely delayed. This matches "permanent freezing/loss of unclaimed yield" that the reserve fee represents.

### Likelihood Explanation
Reachable without any privileged action: any set of ordinary users can deposit, borrow, then fully redeem (redeem has no debt-outstanding guard), leaving debt active with `total-supply == 0`. This is a normal, permissionless usage pattern (e.g., last depositor exits before a borrower repays), so likelihood is not negligible, though it requires the specific timing where redemptions fully drain LP supply while debt remains open.

### Recommendation
Do not gate `treasury-lp` (or the underlying fee-accrual bookkeeping) on `total-supply` being non-zero in a way that discards the fee. Instead, accumulate the un-mintable `reserve-inc` into a persistent variable (e.g., `pending-reserve-fees`) whenever `total-supply` is zero, and mint the equivalent `treasury-lp` shares (using the then-current conversion rate) as soon as `total-supply` becomes non-zero again, so the treasury's claim on interest is never lost regardless of the LP supply's state at accrual time.

### Proof of Concept
Conceptual sequence (applies to any `v0-vault-*.clar`, e.g. `v0-vault-ststxbtc.clar`):
1. Depositor A calls `deposit` with `amount`, minting shares; `total-supply > 0`.
2. Authorized borrower calls `system-borrow` to draw down `amount` (via `try! (check-caller-auth)`), creating `principal-scaled > 0`.
3. Time passes so `interest-rate()` accrues on the debt.
4. Depositor A calls `redeem` for their full balance; `redeem()` succeeds because it only checks `available-assets`/`balance`, not outstanding debt, driving `total-supply` to `u0`.
5. More time passes; borrower's debt keeps growing.
6. Any call that triggers `accrue()` (e.g., `system-repay`, or an admin `set-fee-reserve`) computes `reserve-inc > u0` from `debt-delta`, but `treasury-lp` evaluates to `u0` because `(total-supply)` is `u0` in `(mul-div-down reserve-inc (total-supply) ...)` — the fee for this period is lost with no persisted record.
7. Depositor B later deposits, restoring `total-supply > 0`; no compensating mint occurs for the fee lost in step 6. [4](#0-3)
