### Title
Static, size-independent extrinsic weight for `handle_unsigned` allows batch-size DoS in `pallet-ismp` - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is a permissionless, unsigned, fee-free extrinsic that accepts an unbounded `Vec<Message>` and is declared with a **fixed** pre-dispatch weight, regardless of how many messages/requests/responses are packed into the call. This mirrors the root cause of CVE-2017-10910 (mqtt): input whose processing cost scales with attacker-controlled batch size is admitted/accounted for as if it had constant, bounded cost, letting an unprivileged submitter force disproportionate resource consumption relative to what the node budgeted for it.

### Finding Description
`handle_unsigned` takes `messages: Vec<Message>` with no `BoundedVec`/length cap: [1](#0-0) 

Its declared weight is a hard-coded constant, independent of `messages.len()` or of how many `PostRequest`/`GetRequest` items each message batches internally: [2](#0-1) 

The comment explicitly acknowledges this is a placeholder ("Static weights because these should get overridden by the FeeHandler"), but the `FeeHandler::on_executed` mechanism only adjusts `actual_weight`/fees **after** execution completes (used for refunds/fee charging), not for the pre-dispatch admission-control decision a block author/validator must make before running the extrinsic: [3](#0-2) 

Because `#[pallet::weight(weight())]` supplies the only figure used to decide whether an extrinsic fits the remaining block weight budget, a single `handle_unsigned` call carrying an arbitrarily large `Vec<Message>` (each with its own `Vec<PostRequest>`/`Vec<GetRequest>` and MMR multiproof) is treated by weight accounting as costing a flat ~300,000,000 weight units — while its actual execution cost (multiproof verification, per-request `IsmpModule::on_accept`/`on_response` dispatch, offchain writes, event emission) scales with the number of entries in the batch: [4](#0-3) 

This is additionally amplified because `handle_unsigned` is validated via `ValidateUnsigned::validate_unsigned`, which runs the **entire** `Self::execute(messages.clone())` pipeline (full proof verification + module dispatch) at transaction-pool validation time — for free, for every full node that receives the gossiped transaction, and can be re-validated repeatedly while the transaction sits in the pool (`longevity: 25` blocks): [5](#0-4) 

The pallet does already defend against some adjacent spam vectors (duplicate-request dedup via `dedup_requests`, content-unique `provides` tags to prevent mempool duplication, and a zstd-bomb size gate in `call-decompressor`), which shows the team is aware of this class of issue, but none of those bound the *size* of a single valid batch nor make the declared extrinsic weight scale with it.

### Impact Explanation
An unprivileged relayer (any account, since this is an unsigned/permissionless call) can submit `handle_unsigned` batches whose true execution cost is far larger than the weight the runtime accounted for. Because Substrate's weight system is the mechanism that keeps block execution time bounded, a batch that is admitted based on an artificially low declared weight but takes disproportionately long to actually execute can push block execution over its time budget, delaying or destabilizing block production/import across the network — a Denial of Service on the coprocessor chain that all ISMP routes depend on for message delivery. This directly threatens the "route unable to deliver messages" outcome called out as in-scope impact, since the coprocessor chain (Hyperbridge/Nexus) is the central dispatch/relay point for all connected state machines.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to supply *valid* proofs and previously-undelivered requests/responses (invalid batches are rejected by `validate_unsigned`), so this cannot be triggered with arbitrary garbage data. However, a relayer (or colluding relayer/module) that has legitimate access to a large backlog of real, valid, undelivered requests/responses (which accumulate naturally under normal operation, or can be engineered by an app that dispatches many outgoing requests to itself) can trivially construct oversized-but-valid `handle_unsigned` batches and submit them for free, with no economic disincentive since these calls are fee-free by design.

### Recommendation
Make the declared `#[pallet::weight(...)]` for `handle_unsigned` a function of `messages.len()` and, ideally, of the number of inner `requests`/`responses` per message (e.g., linear component per request/response plus a base weight, similar to standard FRAME benchmarking practice), so the runtime's pre-dispatch admission control reflects real execution cost. Additionally consider bounding the maximum number of messages/requests per `handle_unsigned` call (e.g., via a `BoundedVec` with a `T::MaxMessagesPerBatch`), and reconsider whether `validate_unsigned` needs to run the full `execute()` (including all module `on_accept`/`on_response` callbacks) rather than a lighter-weight proof-only pre-check, to reduce the free computational cost imposed on every full node during pool validation/re-validation.

### Proof of Concept
1. Attacker (any account, no signature required) accumulates or engineers a large number of legitimately outstanding, valid `PostRequest`s/`GetRequest`s destined for/from a state machine it controls or has access to as a relayer.
2. Attacker constructs a single `Ismp::handle_unsigned` call with `messages: Vec<Message>` containing, e.g., thousands of `RequestMessage`/`ResponseMessage` entries batched into one multiproof, sized up to the runtime's max extrinsic/block length.
3. Because `#[pallet::weight(weight())]` returns a fixed `Weight::from_parts(300_000_000, 0)` regardless of batch size (`modules/pallets/ismp/src/lib.rs:727-730`), the block author's weight accounting treats this call as cheap and includes it, while `Pallet::execute` (`modules/pallets/ismp/src/impls.rs:40-79`) performs full MMR/multiproof verification and per-item `IsmpModule::on_accept`/`on_response` dispatch for every entry in the batch — real execution time far exceeding the declared weight.
4. Repeating this (further amplified by every full node's `validate_unsigned` executing the same full pipeline for free before/while the call is in the pool) can be used to push node execution time beyond the allotted per-block budget, degrading block production/finality for the coprocessor chain that all Hyperbridge message routes rely on.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;
