This confirms it: `ShopValidator.sanitize!` exists and is used in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `graphql/storefront.rb` to validate shop domains before making credentialed requests — but `lib/shopify_api/auth/oauth.rb` (`begin_auth` and `validate_auth_callback`) never calls it. `begin_auth` takes an unvalidated `shop:` argument straight from the caller (the docs example even shows it sourced directly from a request header) and uses it to build `auth_base_uri(shop)` for the authorization redirect [1](#0-0) . `validate_auth_callback` then relies solely on HMAC validation of the callback query, and the HMAC binds `shop` only to `code/host/state/timestamp` — it never checks that `auth_query.shop` is a genuine `*.myshopify.com`-family host before constructing `null_session = Auth::Session.new(shop: auth_query.shop)` [2](#0-1) . That session is fed to `HttpClient.new(session: null_session, base_path: "/admin/oauth")`, where `@base_uri = "https://#{api_host || session.shop}"` — i.e. `session.shop` (attacker-influenceable) directly becomes the HTTPS host that receives the POST body containing `client_id`, `client_secret`, and the authorization `code` [3](#0-2) .

### Title
OAuth `shop` parameter is never validated against `ShopValidator` before being used as the access-token request host, unlike every other credentialed flow - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange`, `ClientCredentials`, `RefreshToken`, and `Clients::Graphql::Storefront` all call `Utils::ShopValidator.sanitize!` to confirm a `shop` value is a genuine Shopify-owned domain before using it to build a request host [4](#0-3) . `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback` are the sole exceptions: they accept a caller-supplied or callback-supplied `shop` string and use it unsanitized to compute `auth_base_uri(shop)`, which later becomes the literal HTTPS host that `Clients::HttpClient` connects to when exchanging the OAuth `code` for an access token, carrying `client_id` and `client_secret` in the POST body [5](#0-4) .

### Finding Description
The binding that should hold is: `shop` used to build the access-token request host == a value proven to be `*.myshopify.com`/`myshopify.io`/etc. (i.e., what `ShopValidator.sanitize!` enforces elsewhere in this gem). In `oauth.rb` this equality is never checked. `begin_auth(shop:, ...)` takes `shop` straight from the caller — the gem's own documentation example sources it directly from an unauthenticated request header (`shop = request.headers["Shop"]`) [6](#0-5)  — and passes it unchecked into `auth_base_uri(shop)` to build the outbound `auth_route` [1](#0-0) .

`validate_auth_callback` only verifies the HMAC over `{code, host, shop, state, timestamp}` via `Utils::HmacValidator.validate` [7](#0-6)  — this proves the query was signed with `Context.api_secret_key`, but does not independently constrain what `shop` value is permitted to reach the token exchange. That HMAC-validated `auth_query.shop` is used verbatim to build `null_session`, which `HttpClient` turns directly into `@base_uri = "https://#{api_host || session.shop}"` [3](#0-2) , the exact host that receives `client_id`/`client_secret`/`code` in the POST to `/admin/oauth/access_token` [8](#0-7) .

Compare this to `TokenExchange`, `ClientCredentials`, and `RefreshToken`, which call `ShopValidator.sanitize!` specifically to prevent an application-provided or otherwise externally-influenced `shop` string from being turned into an arbitrary outbound host carrying the app's secret. `Auth::Oauth` has no equivalent guard, making it the one asymmetric path in this gem's credentialed-request code where the shop-to-host binding is left entirely to the host application to enforce, contrary to the gem's own internal precedent.

### Impact Explanation
If a host application follows this gem's own documented pattern of sourcing `shop` for `begin_auth` from a value not yet validated as a genuine Shopify domain (as literally shown in `docs/usage/oauth.md`), an unprivileged internet user can control the domain reached by `begin_auth`'s redirect and, more critically, the host that `validate_auth_callback` will POST `client_id`/`client_secret`/`code` to during the token exchange. Since none of `Auth::Oauth`'s functions apply `ShopValidator.sanitize!`, the gem provides no defense-in-depth here even though it does so uniformly elsewhere for the same class of shop-to-host binding, elevating the risk of the app's `client_secret` being sent to an attacker-controlled host (SSRF carrying the app's credentials) if the calling app doesn't itself sanitize the value before calling into this gem's OAuth API.

### Likelihood Explanation
Exploitation depends entirely on the host application not sanitizing `shop` before calling `begin_auth`/constructing `AuthQuery` — behavior this gem's own docs sample code encourages. Within this gem, `validate_auth_callback`'s HMAC check does bind `shop` to a signature computed with `Context.api_secret_key`, meaning a fully malicious `shop` value would only reach the token-exchange POST if Shopify itself (holder of the shared secret) produced that HMAC for it, or if the calling application short-circuited/misused the flow. This significantly limits the likelihood of a purely unauthenticated exploit against `validate_auth_callback` alone, but `begin_auth` has no such HMAC gate and is exploitable purely through host-application misuse matching the documented pattern.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: ...)` at the top of `Auth::Oauth.begin_auth` and again on `auth_query.shop` inside `Auth::Oauth.validate_auth_callback`, exactly as is already done in `TokenExchange`, `ClientCredentials`, and `RefreshToken`, before the value is used to construct any outbound request host.

### Proof of Concept
1. A host app builds its login route by taking `shop` from an attacker-controlled input (per the gem's own documented example: `shop = request.headers["Shop"]`).
2. Attacker requests `/login` with `Shop: attacker-controlled-host.example.com`.
3. `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker-controlled-host.example.com", redirect_path: "/auth/callback")` builds `auth_route = "https://attacker-controlled-host.example.com/admin/oauth/authorize?..."` with no validation [9](#0-8) .
4. If the app's flow is later driven such that `validate_auth_callback` receives an `AuthQuery` with that same `shop`, and if the app itself (not this gem) fails to constrain the shop, the resulting token-exchange request sends `client_id`/`client_secret`/`code` to `https://attacker-controlled-host.example.com/admin/oauth/access_token` because `HttpClient` uses `session.shop` verbatim as the request host [10](#0-9) .
