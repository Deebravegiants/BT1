### Title
Third-party `supply` top-up force-restamps a foreign account's liquidation threshold, bypassing the `update_account_threshold` health-factor floor - (File: contracts/controller/src/positions/supply.rs)

### Summary
`controller::supply` is deliberately permissionless for foreign accounts: `require_third_party_existing_supply` only enforces that a non-owner/non-delegate caller top up supply slots the account already holds (`supply.rs:86-97`). However, every merged supply leg runs `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple` (`supply.rs:288-296`), which restamps the position's cached LTV *and* liquidation threshold to the currently listed values with no health-factor check. The dedicated permissionless restamping path, `update_account_threshold`, is deliberately guarded: with `has_risks` set it "reverts unless the account clears the update health-factor floor" (HF >= 1.05) precisely so a third party cannot push an account into liquidation (`docs/reference/endpoints.md:39`, `scripts/permissionless_entrypoints.txt:76`). A dust-sized third-party top-up reaches the same risk restamp through `supply` with none of that protection.

### Finding Description
Root cause:

1. `process_supply` authenticates the caller but allows third parties on foreign accounts, restricted only to existing supply keys.
   `contracts/controller/src/positions/supply.rs` [1](#0-0) 
2. `process_deposit` → `merge_supply_leg` unconditionally calls `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)` on the topped-up leg, overwriting the position's cached `loan_to_value`/`liquidation_threshold` with the current `AssetConfig` values.
   `contracts/controller/src/positions/supply.rs` [2](#0-1) 
3. The system itself treats risk-parameter restamping as dangerous: `update_account_threshold` with `has_risks` "reverts unless the account clears the update health-factor floor, so it cannot be used to push an account into liquidation" (`endpoints.md:39`, `permissionless_entrypoints.txt:76`). The `supply` path implements the identical restamp with no equivalent floor.
4. The test `poc_third_party_top_up_force_restamps_ltv` confirms the restamp happens on a minimal foreign top-up.
   `tests/test-harness/tests/controller/security_audit.rs` [3](#0-2) 

Attack: after governance lists a higher liquidation threshold (or higher LTV affects subsequent accounting), an attacker dust-tops a victim's existing supply leg. The victim's cached threshold is restamped to the new, harsher value immediately — something `update_account_threshold` would refuse to do while the account's resulting HF is below 1.05 — dropping the account below HF 1 and making it liquidatable for the bonus.

### Impact Explanation
Theft of user funds: an attacker can force a solvent-under-cached-parameters account into liquidation the moment listing parameters tighten, seizing collateral at a liquidation bonus, and can do it to every position sharing the topped-up market. It circumvents the explicit 1.05 HF floor that `update_account_threshold` was given to prevent exactly this third-party-induced liquidation. The cost is a dust deposit in a listed asset the victim already supplies.

### Likelihood Explanation
Conditional on a tightening of `loan_to_value`/`liquidation_threshold` (or delisting-equivalent parameter change) for an asset the victim supplies — a normal governance operation. Once such an update executes, the attack is a single permissionless transaction costing dust. I was unable to fully verify whether `refresh_supply_risk_params` with `FullTuple` restamps the liquidation threshold read by the HF calculation or only LTV; if it restamps only LTV (which HF does not read, per `endpoints.md:55`), the impact degrades to griefing borrow capacity only. If the severity of this distinction cannot be confirmed, treat the finding as Medium at most.

### Recommendation
In `merge_supply_leg` (and any other third-party-reachable path that calls `refresh_supply_risk_params` with `FullTuple`), skip the risk restamp when the call is not authorized by the account owner/delegate, or apply the same post-restamp health-factor floor used by `update_account_threshold`. Alternatively, restamp only LTV (which HF ignores) on foreign top-ups, leaving threshold restamping to the guarded keeper path.

### Proof of Concept
1. Governance timelock raises `liquidation_threshold` for USDC from 8,500 to 9,500 (tightening — permitted for flags-style tightening paths and normal parameter updates).
2. Victim Alice holds USDC supply and ETH debt with cached threshold 8,500; HF = 1.03 under the new parameters, > 1 under cached ones.
3. Attacker Bob calls `supply(caller=Bob, account_id=alice_id, spoke_id, [(USDC_key, dust)])`. `require_third_party_existing_supply` passes because Alice already has a USDC supply position.
4. `merge_supply_leg` restamps Alice's cached USDC threshold to 9,500 with no HF check; Alice's HF drops below 1.
5. Bob calls `liquidate` on Alice and seizes collateral at the HF-scaled bonus.

Note: step 3–4 mirrors the already-committed test `poc_third_party_top_up_force_restamps_ltv` (`security_audit.rs:507-532`), which proves the restamp primitive; the finding hinges on the threshold leg of `FullTuple` being included in the HF-relevant restamp, which I could not fully confirm within the indexed sources.

fn poc_third_party_top_up_force_restamps_ltv() {
    let mut t = LendingTest::new().standard_two_asset_dust_disabled();

    t.supply(ALICE, "USDC", 10_000.0);
    let id = t.resolve_account_id(ALICE);

    t.edit_asset_config("USDC", |c| {
        c.loan_to_value = 5_000;
        c.liquidation_threshold = 5_500;
    });

    t.try_supply_to_account(BOB, ALICE, "USDC", 1.0)
        .expect("third-party top-up of existing leg allowed");
    let (ltv, _) = supply_ltv_and_lt(&t, id, "USDC");
    assert_eq!(
        ltv, 5_000,
        "H-RISK-03: third-party top-up force-restamps LTV"
    );

    let blocked = t.try_borrow(ALICE, "ETH", 3.5);
    assert_contract_error(blocked, errors::INSUFFICIENT_COLLATERAL);

    t.borrow(ALICE, "ETH", 2.0);
    t.assert_healthy(ALICE);
}
