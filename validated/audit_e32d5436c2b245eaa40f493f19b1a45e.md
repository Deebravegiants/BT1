### Title
`DeleteAccountAction` allows specifying a non-existent `beneficiary_id`, causing the account's remaining balance to be irrecoverably burnt - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction.beneficiary_id` is validated only for account-id *syntax*, not for account *existence*, before the delete is executed. The remaining balance of the deleted account is sent to `beneficiary_id` as a refund receipt. If that account doesn't exist (and is not itself a valid implicit-account address), the refund receipt fails and the funds are permanently burnt instead of refunded to the actor or any recoverable party — the exact analog of the Sherlock finding "transfer position to 0 address," where a missing recipient-validity check on a fund-transferring action causes assets to become unrecoverable.

### Finding Description
`DeleteAccountAction` carries a `beneficiary_id: AccountId` that receives the deleted account's remaining balance. [1](#0-0) 

The only pre-execution validation performed on this field is `validate_action_account_id`, which merely checks that the string is a syntactically valid `AccountId` — it does not check whether the account actually exists on-chain: [2](#0-1) 

When the delete executes, the account's remaining `amount()` is unconditionally pushed as a `Receipt::new_balance_refund` targeting `beneficiary_id`, with no existence check performed at this point either: [3](#0-2) 

This refund is a system-predecessor ("refund") receipt. When such a receipt is later processed against the (possibly non-existent) `beneficiary_id`, `check_account_existence` is invoked for the inner `Transfer` action. If the account is missing, it falls through to `check_transfer_to_nonexisting_account`, which only allows implicit account auto-creation, and explicitly documents that "refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse": [4](#0-3) [5](#0-4) 

If `beneficiary_id` is a syntactically valid, non-implicit, non-existent account name (e.g., `"nosuchaccount.near"`), this refund transfer fails with `AccountDoesNotExist`. Because the receipt's predecessor is `system` (i.e., it is a refund), the runtime's failure-handling path burns the deposit instead of retrying or returning it to anyone: [6](#0-5) 

This is architecturally the same class of bug as the reported Solidity issue: a user-facing action that transfers value to an attacker/user-controlled "recipient" field lacks a check that the recipient is a valid, reachable destination, so funds sent there are permanently lost.

### Impact Explanation
Any account holder who calls `DeleteAccount` with a `beneficiary_id` that is syntactically valid but does not correspond to an existing (and non-implicit) account will have their entire remaining NEAR balance burnt rather than refunded to a real party. This is a concrete, irreversible loss of user funds triggered entirely by a normal, permissionless transaction — no validator or attacker cooperation required. It also silently reduces total token supply outside of the documented burn accounting for gas/fees, which is an unintended economic side effect.

### Likelihood Explanation
Likelihood is moderate: it requires the user (or a wallet/dApp bug) to supply an incorrect `beneficiary_id` — e.g. a typo'd account name, or an account that has itself been deleted between when the transaction was signed and when it executes (a legitimate, non-adversarial race). Because `validate_delete_action` only checks account-id format and not existence, and because the runtime documentation for `DeleteAccountAction` explicitly notes only the `InvalidAccountId` validation error class (no `AccountDoesNotExist` pre-check for the beneficiary), nothing prevents this at signing time or wallet-level static validation, and the user has no visibility into it until after the transaction has already executed and burnt the funds.

### Recommendation
Add an existence check for `beneficiary_id` before or during `action_delete_account` (or fail the whole `DeleteAccount` action, not just the ensuing refund receipt) when `beneficiary_id` does not exist and is not a valid implicit-account id — for example, look up the beneficiary account in `state_update` in `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) and return an actionable `ActionErrorKind` (e.g., reuse/extend `AccountDoesNotExist`) instead of generating a refund receipt destined to fail and burn funds.

### Proof of Concept
1. Account `alice.near` holds a non-zero balance.
2. `alice.near` submits a transaction with a single `DeleteAccount { beneficiary_id: "doesnotexist.near" }` action (a syntactically valid, but non-existent, non-implicit account id). `validate_delete_action` passes because it only checks id format. [2](#0-1) 
3. `action_delete_account` deletes `alice.near` and unconditionally emits `Receipt::new_balance_refund(&"doesnotexist.near", account_balance)`. [3](#0-2) 
4. When this refund receipt is processed, `check_account_existence` sees `doesnotexist.near` has no account and is not implicit, returning `AccountDoesNotExist`. [4](#0-3) 
5. Because the receipt's predecessor is `system` (refund), the failed result causes the deposit to be added to `other_burnt_amount` instead of refunded anywhere. [6](#0-5) 
6. Net effect: `alice.near`'s entire balance is permanently burnt with no recipient receiving it, purely due to a missing existence check on `beneficiary_id`.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
