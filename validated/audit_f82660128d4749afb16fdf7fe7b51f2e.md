### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The reported Ajna bug is a classic "identity used downstream is not the identity that was authenticated" flaw. The same class of bug exists in this gem's webhook processing: `ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw body, while the `shop` (and `topic`, `api_version`, `webhook_id`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler come from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only the raw body**: [3](#0-2) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, which are never part of the signed payload: [4](#0-3) 

After HMAC validation succeeds, `process` passes `request.shop` — the unauthenticated header value — directly into `WebhookMetadata` given to the app's handler: [5](#0-4) 

The binding that should hold is:
`HMAC_secret(shop || topic || body) == received_signature`

What is actually checked is:
`HMAC_secret(body) == received_signature`, while `shop` (the tenant identity) is taken from an unsigned header.

Any entity that can obtain one valid `(body, hmac)` pair signed with the app's shared secret for *any* shop it controls (e.g., an attacker who installs the app on their own store and captures a legitimate webhook delivery) can replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. Because the shop header is not covered by the signature, `HmacValidator.validate` still returns `true`, and the handler executes with `data.shop` set to the attacker-chosen shop.

### Impact Explanation
This breaks the shop-identity binding that webhook handlers rely on to route/attribute per-tenant work (e.g., looking up a session for `data.shop`, updating that shop's records, or triggering shop-scoped side effects). An attacker can cause the app to act on/impersonate a shop it does not own, which is a cross-tenant access issue — the app has no gem-level way to distinguish a payload that was truly destined for shop A from a replayed payload with a forged shop header for shop B, since only the body is authenticated.

### Likelihood Explanation
Likelihood is realistic for any publicly installable app: an attacker only needs to become a legitimate merchant of the target app (install it on their own development store, which is unprivileged/free) to receive one authentically HMAC-signed webhook. They can then replay that exact `(raw_body, hmac)` pair against the app's webhook endpoint with a different `shop-domain` header value, since nothing in this gem's webhook-processing path binds the header to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed payload, so `HmacValidator.validate` fails if the `shop`, `topic`, or other identity-bearing headers are altered relative to what was actually signed by Shopify. At minimum, document/require that consuming apps independently verify `data.shop` corresponds to a shop with an active, previously-established session before trusting it, but the safer fix is to make the gem itself bind these fields into the HMAC-checked content.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery with body `{}` and header `x-shopify-hmac-sha256: <valid HMAC of "{}">` computed with the app's `api_secret_key`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(body)` — this still matches, so validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though Shopify never sent this webhook for `victim-shop.myshopify.com`: [5](#0-4) 

This is corroborated by the test setup, which shows the HMAC is computed solely over the JSON body (`"{}"`) irrespective of the `shop-domain` header value: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
