### Title
Webhook `shop-domain` Header Not Bound to HMAC Signature Enables Cross-Tenant Shop Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook `HmacValidator` verifies the integrity of the request body only, but the `shop` identity that is trusted and forwarded to the host application's `WebhookHandler` is taken from an HTTP header that is never included in the signed payload. An attacker who can obtain (or trigger) one legitimately-signed webhook can replay it with an arbitrary `shop-domain` header and still pass HMAC validation, causing the host application to process the payload as if it originated from a different, victim merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent from the signed content: [2](#0-1) 

`Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) [4](#0-3) 

Once validation succeeds, `request.shop` (the unauthenticated header value) is passed straight into `WebhookMetadata` and handed to the host application's handler as the trusted tenant identifier: [5](#0-4) [6](#0-5) 

This breaks the identity binding `signed(shop) == processed(shop)`: the byte range verified by the HMAC is `raw_body`, while the byte range acted upon as the tenant identity is the `shop-domain` header — a field acted on but not covered by the HMAC.

### Impact Explanation
Because the app's `client_secret` (used as the HMAC key) is shared across all shops that have the app installed, a signature that is valid for one shop's webhook delivery is equally valid for the same body delivered with a forged `shop-domain` header claiming to be any other shop. An attacker who controls (or has installed the app on) any shop can capture one legitimately Shopify-signed webhook for their own store, then resend the exact same body/HMAC to the app's webhook endpoint while substituting a different, victim merchant's shop domain in the header. `HmacValidator.validate` still returns `true` (it never inspected `shop`), so `Registry.process` dispatches the payload to the handler tagged with the victim's shop. If the host application uses `WebhookMetadata#shop` to select which merchant's session/access token/data record to update (the intended and documented use of this field), this results in cross-tenant data confusion/injection — writing or acting on data under the wrong tenant's identity, which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires an attacker who has app access on any single shop (e.g., a free/test install) to receive one real webhook and replay it with a modified header to the same publicly reachable webhook endpoint — no access token, `client_secret`, or privileged credentials are needed. This is a realistic, low-effort request-forgery scenario reachable directly through the gem's own `Registry.process`/`HmacValidator` code path.

### Recommendation
Bind the shop identity into the verified signature space, or otherwise cryptographically tie the `shop-domain` header to the signed body — e.g., include the shop domain (and ideally the raw target URL) as part of `to_signable_string`, or independently verify that the shop the webhook claims to be from matches an installation-scoped secret/session rather than trusting the unauthenticated header directly. At minimum, the library should document that `WebhookMetadata#shop` is unauthenticated header data and must not be used by host applications as an identity boundary without additional verification (e.g., correlating against a known, previously stored shop/session).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) to receive a legitimately Shopify-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
4. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...))` is invoked, causing the host app to process attacker-controlled data under the victim shop's identity.
