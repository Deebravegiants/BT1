Based on my investigation, I've confirmed the vulnerability. The webhook HMAC only authenticates the raw request body, while the `shop` (tenant identity) and `topic` fields — which are used directly by the application's webhook handler — come from unauthenticated HTTP headers.

### Title
Webhook `shop` and `topic` identity are not bound to the HMAC signature, enabling cross-tenant webhook spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the body bytes were signed by the app's `api_secret_key` [2](#0-1) . However `Registry.process` uses the unauthenticated `shop-domain` and `topic` headers to build the `WebhookMetadata` passed to the app's handler [3](#0-2) , and `Request#shop`/`Request#topic` are read straight from headers with no cryptographic binding to the signed body [4](#0-3) .

### Finding Description
The broken binding is: `HMAC_valid(raw_body) == true` is treated by `Registry.process` as proof that `(shop, topic, raw_body)` as a tuple originated from Shopify for that specific shop, when in fact only `raw_body` is covered by the signature.

Concretely:
- `Request#hmac` decodes the `hmac-sha256` header [5](#0-4) .
- `Request#to_signable_string` returns `@raw_body` — nothing else [1](#0-0) .
- `Registry.process` raises only if `HmacValidator.validate(request)` fails, then immediately trusts `request.topic` and `request.shop` to construct `WebhookMetadata` for the handler [3](#0-2) .

Because a merchant who has the app installed on their own shop legitimately receives real webhook deliveries (valid `raw_body` + valid HMAC computed with the real `api_secret_key`, which they never need to know or derive), that same unprivileged merchant can capture one such delivery and replay the identical `raw_body`/`hmac-sha256` value to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic` header) with a different shop's domain or a different topic. `Registry.process` will still consider the HMAC valid (it only checks the body) and will invoke the handler believing the event came from the spoofed shop/topic. Any app logic that trusts `WebhookMetadata#shop` to select which tenant's data to update (e.g., processing an `orders/create` payload and crediting/updating records keyed by `data.shop`) can be tricked into applying another (or fabricated) shop's identity to real, replayed body content — a cross-tenant confusion primitive entirely reachable without any credentials.

This matches the report's underlying bug class: a field (`shop`/`topic`) is acted upon by the application without being covered by the HMAC that is supposed to authenticate the request.

### Impact Explanation
This is a cross-tenant identity-binding break reachable by any unprivileged party who can install the app on a shop they control (or otherwise obtain one legitimate webhook delivery) and then directly POST to the app's webhook endpoint with a forged `shop-domain`/`topic` header. Depending on how the host app's `WebhookHandler` uses `WebhookMetadata#shop`, this can let an attacker attribute events, mutate records, or trigger business logic for a shop that isn't theirs — a cross-tenant impact.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to first obtain at least one legitimately-signed webhook body (trivial for a merchant using the app on their own store), and then send a raw HTTP POST directly to the app's public webhook endpoint (bypassing the normal Shopify origin) with modified headers. No secret key, access token, or elevated privilege is required — only observation of one's own webhook traffic and the ability to issue arbitrary HTTP requests to the app's endpoint.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body (e.g., concatenate headers + body before computing/verifying the signature, mirroring how `AuthQuery#to_signable_string` binds `shop`/`state`/etc. into the signed string [6](#0-5) ). At minimum, document prominently that `Request#shop`/`Request#topic` are NOT authenticated by the HMAC check and must not be trusted as tenant identity without additional verification (e.g., cross-checking against a known/allow-listed shop for that app installation).

### Proof of Concept
1. App developer registers a handler for `orders/create` via `ShopifyAPI::Webhooks::Registry.add_registration`, whose `handle` method trusts `data.shop` to select which tenant record to update.
2. Attacker installs the app on their own shop `attacker.myshopify.com` and receives one legitimate `orders/create` webhook: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC_sha256(api_secret_key, B)`).
3. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - Body: the exact same `B`
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body is unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - `X-Shopify-Topic: orders/create` (unchanged or forged to another registered topic)
4. `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H` [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's own order data>, ...)` [8](#0-7) , causing the app to process attacker-controlled order data as if it belonged to `victim.myshopify.com`.
