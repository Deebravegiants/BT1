### Title
Fail-open error handling in OIDC token exchange handler allows session creation despite failed validation - ([File: core/sessions/oidcauth/oidc.go])

### Summary
The OIDC callback handler `handleTokenExchange` in `core/sessions/oidcauth/oidc.go` checks the results of two security-relevant operations but, unlike every other error branch in the same function, fails to `return` after logging the failure. Execution falls through and completes the login flow (issuing a session cookie and reporting success) even though the checked condition failed — the same "checked-but-ignored" control-flow pattern as the reported unchecked `IERC20.approve()` return value, where a failure signal is observed but not acted upon before the sensitive operation (fund transfer / session issuance) proceeds.

### Finding Description
In `handleTokenExchange`, every other failure path calls `return` immediately after writing an error response: [1](#0-0) 

But two branches omit the `return`:

1. Email claim extraction — if the `email` claim is missing or not a string, `ok` is `false`, an error is logged/written, but execution continues with `email == ""`: [2](#0-1) 

2. Session persistence — if the `INSERT INTO oidc_sessions` fails, the error is logged/written, but execution continues to set the session cookie and report success anyway: [3](#0-2) 

Immediately after case (2), the code still sets the authenticated session cookie and returns HTTP 200 success: [4](#0-3) 

This mirrors the reported bug class exactly: the "return value" of a sensitive operation (email extraction / DB persistence) is checked, logged as failed, but the failure is not enforced — subsequent security-relevant logic (`role` mapping, `INSERT`, session-cookie issuance, `AuthLoginSuccessNo2FA` audit log) executes unconditionally regardless of the checked failure.

### Impact Explanation
- If the identity provider's token response omits an `email` claim (or returns a non-string value), the handler still creates a persisted `oidc_sessions` row and a valid, working session cookie with `user_email` set to the empty string, and logs `AuthLoginSuccessNo2FA` with `email: ""`. The `role` is still derived from group claims via `IDClaimsToUserRole`, so a fully authenticated, role-bearing session is minted under a corrupted/empty identity. Downstream audit trails and any code that keys off session email (e.g. audit logging, admin visibility) are silently populated with an incorrect identity, undermining accountability and per-user tracing of privileged (edit/admin/run) OIDC sessions.
- If the DB insert fails, the client is told `Success: true` and is handed a session cookie for a session that was never persisted — a fail-open response on the auth boundary that misrepresents whether authentication state was durably established.

### Likelihood Explanation
Reachable directly by any client completing the OIDC `/sessions/exchange`-style flow (`handleTokenExchange` is the public callback endpoint of the internet-facing gateway/login flow); no privileged access is required. The missing-`email`-claim condition can occur naturally with IdPs/configurations that don't include the `email` scope claim or where `email_verified`/`email` mapping differs, and is under partial influence of client-supplied/IdP-returned token content that this code parses.

### Recommendation
Add `return` immediately after both fail branches, matching the pattern used elsewhere in the function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
...
_, err = oi.ds.ExecContext(ctx, "INSERT INTO oidc_sessions ...", clSession.ID, strings.ToLower(email), role)
if err != nil {
    oi.lggr.Errorf("unable to create new session in oidc_sessions table %v", err)
    c.String(http.StatusInternalServerError, "Error creating session")
    return
}
```

### Proof of Concept
1. Configure/point the OIDC provider (or intercept its response in a test harness) so the returned ID token claims omit `email` (valid per OIDC spec when `email` scope isn't granted or provider omits it).
2. Complete the OAuth2 code exchange via `POST /sessions/exchange` (or equivalent route wired to `handleTokenExchange`) with a valid `code`/`state`.
3. Observe: `claims["email"].(string)` assertion fails (`ok == false`); handler logs the error and writes a 500 body, but does not `return`.
4. Execution continues: `IDClaimsToUserRole` maps the group claims to a role, `INSERT INTO oidc_sessions` persists a row with `user_email = ''`, `ginSession.Set(...)`/`Save()` issues a valid session cookie, and the handler finally emits `c.JSON(http.StatusOK, {"success": true})` — i.e., the response body contains a `success:false`-style 500 write followed by an overriding 200 JSON success, and the client walks away with a working authenticated session tied to an empty-email identity.
