### Title
Escrow accounting updated after external token/native transfer in `IntentGatewayV2.withdraw()` violates CEI — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2`'s internal `withdraw()` function transfers escrowed tokens/native currency to the beneficiary *before* decrementing the corresponding `_orders[commitment][token]` escrow accounting entry, breaking Checks-Effects-Interactions. This is the exact bug class flagged in the report (external transfer/mint before internal ledger update), and it is directly reachable by an unprivileged order owner via the same-chain `cancelOrder()` path.

### Finding Description
In `withdraw()`:
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:691-714
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- effect happens AFTER interaction
        unchecked { ++i; }
    }
    ...
}
```
The external call (`beneficiary.call{value: amount}("")` or `token.call(...transfer...)`) executes before `_orders[body.commitment][token]` is decremented — the same anti-pattern reported for `SolverVault`. This is reachable from an unprivileged transaction through the same-chain cancellation path:
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:516-539
function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
    ...
    if (isSameChain) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        ...
        withdraw(body, true);
    }
```
`order.user == msg.sender` is enforced, so the caller fully controls the beneficiary address used inside `withdraw()`, and can supply a contract with a `receive()`/token hook that reenters the gateway mid-transfer, while `_orders[commitment][token]` for that token is still at its pre-payout value.

By contrast, the mainline/fixed EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol` applies the correct CEI ordering, decrementing the ledger before making the external transfer:
```solidity
// evm/src/apps/intentsv2/IntentsBase.sol:461-469
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;      // effect first
if (token == address(0)) {
    _sendValue(beneficiary, amount);                       // interaction after
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```
This fix, and the dedicated regression suite `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, confirm that the project has already identified and mitigated this exact CEI-violation bug class in the fill/withdraw paths of the primary EVM contracts (`IntrinsicIntents.sol`/`ExtrinsicIntents.sol`), by additionally setting `_filled[commitment]` before any loop/interaction. The Tron variant of `IntentGatewayV2.sol` still contains the vulnerable pre-fix ordering for the `_orders` ledger decrement.

### Impact Explanation
`withdraw()` does set `_filled[body.commitment]` before the loop, which blocks a reentrant call from re-entering `cancelOrder()`/`onAccept`/`onGetResponse` for the *same* commitment (the top-level double-redemption vector demonstrated in `IntrinsicIntentsReentrancyTest.sol` is closed here too). However, the per-token escrow ledger `_orders[commitment][token]` itself remains stale (not yet decremented) during the external call. Any ERC-20 used as an order input with a transfer hook (fee-on-transfer/rebasing/ERC-777-style callback token, or a malicious token the order creator chooses for their own order) can reenter the gateway during that window while `_orders[commitment][token]` still reflects the pre-payout balance. Because the safety net here is the `_filled` flag rather than intrinsic CEI ordering, this is a residual/defense-in-depth deviation from the pattern the project explicitly hardened elsewhere; any future code path that reads or reasons about `_orders[commitment][token]` without also checking `_filled` (e.g., partial-fill or dust-sweep logic added later) would reintroduce a genuine double-spend of escrowed funds.

### Likelihood Explanation
Medium. Exploitation requires the attacker to control (or convince the gateway to escrow) a token with a transfer callback for their own order, and depends on the absence of any additional guard beyond `_filled` on other code paths that consult `_orders[commitment][token]`. Direct double-withdrawal of the *same* commitment is currently blocked by the `_filled` check, but the ledger-after-interaction ordering is a structural regression relative to the fixed sibling contract and is the identical fragile pattern that was previously proven exploitable (per the project's own reentrancy test suite) before the `_filled`-first fix was added.

### Recommendation
Apply the same CEI fix already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` (and the fee entry) *before* performing the native/ERC-20 transfer in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`. Also prefer `SafeERC20.safeTransfer` over raw low-level `.call` to avoid silently succeeding on tokens that return `false` instead of reverting.

### Proof of Concept
1. Attacker (as `order.user`) places a same-chain order via `placeOrder`, using a token they control with a `transfer()` callback hook, or native ETH with `order.user` set to their own malicious contract.
2. Attacker calls `cancelOrder(order, options)` on the same chain; this enters `withdraw(body, true)`.
3. `withdraw()` sets `_filled[commitment] = beneficiary`, then in the loop performs `beneficiary.call{value: amount}("")` (or `token.call(transfer(...))`) for the escrowed input token **before** executing `_orders[body.commitment][token] -= amount`.
4. During the callback, the malicious beneficiary/token attempts to re-enter; direct re-entry into `cancelOrder`/`withdraw` for the same commitment is blocked by `_filled`, but the ledger for that specific token entry is observably stale for the duration of the external call — any code path added or reachable that consults `_orders[commitment][token]` without checking `_filled` would allow a second payout against the same stale balance.
