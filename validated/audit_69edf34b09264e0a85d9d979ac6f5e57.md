## Title
Webhook shop-domain and topic headers are not covered by HMAC validation, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only, then hands the unauthenticated `shop` header value straight to the app's handler as the tenant identifier.

### Finding Description
The webhook HMAC binding should equal:
`HMAC(secret, signed_bytes) == received_hmac` where `signed_bytes` includes everything the app trusts as coming from Shopify for a specific tenant.

In this gem, `to_signable_string` only returns `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers that are never part of the signed bytes: [2](#0-1) 

`Registry.process` validates only the body-bound HMAC, then trusts `request.shop`/`request.topic` (unauthenticated headers) to dispatch to a handler and construct `WebhookMetadata`: [3](#0-2) 

Because the api_secret_key is shared across all shops installed on a given app (it is not per-tenant), any merchant who has installed the app can receive a legitimately-signed webhook for their own store (valid `body` + valid `hmac` computed with the app's shared secret), then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` recomputes the HMAC only over `@raw_body`, which is unchanged, so validation succeeds: [4](#0-3) 

The handler then receives `WebhookMetadata` with the attacker-chosen `shop`, which the documentation explicitly recommends using as the tenant key for follow-up work (e.g., `shop_domain: data.shop`): [5](#0-4) 

This breaks the identity binding "shop authenticated via HMAC" == "shop used by the app to select/update tenant data" — the shop value delivered to app code is not covered by the signature that is supposed to prove it came from Shopify for that specific store.

### Impact Explanation
This allows a malicious merchant (who is a legitimate, but unprivileged w.r.t. other tenants, installer of the app) to inject spoofed webhook events attributed to any other shop using the app, by simply changing an HTTP header on a replayed request. Depending on how the host application consumes `data.shop` (e.g., to look up/update per-tenant records, trigger side effects, or provision resources), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's tenant context — squarely a cross-tenant access issue.

### Likelihood Explanation
Exploitation only requires an attacker to control one legitimate installation of the target app (any merchant can do this by installing an app that uses this gem) and the ability to send arbitrary HTTP headers to the app's public webhook endpoint — no access to the `api_secret_key`, access tokens, or the target shop's credentials is needed. This is straightforward to carry out.

### Recommendation
Include the shop domain (and other trusted metadata such as topic/webhook_id/api_version) in the HMAC-signed payload evaluated by `to_signable_string`, or otherwise cryptographically bind the `X-Shopify-Shop-Domain` header to the signature (mirroring how the OAuth `AuthQuery#to_signable_string` binds `shop` into its signable string). At minimum, document loudly that `request.shop`/`request.topic` are not covered by the HMAC and must not be trusted as a tenant identifier without additional verification (e.g., cross-checking against a known/expected shop for the installation).

### Proof of Concept
1. App using this gem installs webhooks for two shops: `victim.myshopify.com` and attacker's own `attacker.myshopify.com`.
2. Attacker's shop receives a legitimate webhook: `raw_body = B`, headers include `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(secret, B)`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker POSTs the same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — still true. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, and the host app processes it as if Shopify sent this event for `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
