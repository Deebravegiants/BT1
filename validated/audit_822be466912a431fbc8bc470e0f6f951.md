## Title
Webhook shop identity spoofing via header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values from HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. Because a single `api_secret_key` is shared across every shop that installs the app, any merchant who legitimately receives one valid webhook can replay its body+HMAC while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature purely from `to_signable_string`, i.e. only the body: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then forwards the header-derived `shop` value directly to the handler without any additional binding check between the signed body and the shop identity: [4](#0-3) 

The equality the code implicitly (and incorrectly) assumes is:
`valid_hmac(raw_body) == true` implies `shop_header == actual_shop_that_generated_body`

But since the HMAC is computed with the app-wide `api_secret_key` (not a per-shop secret) and covers only the body, the real invariant that holds is much weaker: `valid_hmac(raw_body)` only proves *some* shop that has this app installed produced this exact body — it says nothing about which shop's domain header is attached to the request.

### Impact Explanation
Any merchant that has installed the app (an "unprivileged" party from the perspective of other tenants) can capture one legitimate webhook delivery (body + `X-Shopify-Hmac-Sha256`) for their own store, then resend an HTTP request to the app's webhook endpoint with the identical raw body/HMAC but a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. `HmacValidator.validate` will still succeed because the signature never covered the header, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the victim shop as the source. If the host application's webhook handler uses `data.shop` to look up/update per-tenant records (the standard and shown usage pattern), this results in cross-tenant data corruption or unauthorized actions attributed to another merchant's store — a cross-tenant access issue.

### Likelihood Explanation
Any app developer/merchant who can install the target app and receive at least one real webhook (a routine, non-privileged action) can perform this attack; no possession of `api_secret_key`, access tokens, or other privileged credentials is required, only a captured legitimate body/HMAC pair and the ability to POST to the app's public webhook endpoint with custom headers.

### Recommendation
Bind the shop domain (and topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header claims to the signed payload — for example, include the `shop-domain` header in `to_signable_string`, or independently verify the shop against the session/subscription that owns the webhook topic before dispatching to handlers.

### Proof of Concept
1. Merchant A installs the app and the app registers a webhook (e.g. `orders/create`).
2. Shopify sends a webhook to the app for shop A with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and JSON body `B`.
3. Attacker (Merchant A) captures body `B` and the HMAC.
4. Attacker POSTs the same body `B` and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks the body.
6. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `shop: "shop-victim.myshopify.com"`, causing the app to process attacker-controlled data as if it originated from the victim shop.
