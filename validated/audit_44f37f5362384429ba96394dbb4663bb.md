### Title
Webhook `shop` identity is trusted from an HTTP header that is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` domain used to route and label webhook data from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. An attacker who can reach the app's webhook endpoint can pair a previously-observed valid `(raw_body, hmac)` pair with an arbitrary forged shop-domain header, and the HMAC check will still pass.

### Finding Description
`Request#shop` reads the shop identity straight out of a header: [1](#0-0) 

but `to_signable_string`, which is what `HmacValidator` actually verifies, only returns the raw body bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and other headers) to build the `WebhookMetadata` passed to the app's handler, without any additional binding between the shop header and the signed bytes: [3](#0-2) 

Because Shopify webhook HMACs are computed with the app's single `client_secret` (shared across every shop that installs the app) over the raw body only, the signature proves "this body was produced using our secret" but proves nothing about which shop it came from. The `shop` field is a field acted on but not covered by the HMAC, exactly the class of binding break in scope: the equality `hmac_signed(shop) == shop_used_by_handler` never holds — the shop value is never part of the signed content at all.

### Impact Explanation
Any party capable of sending an HTTP POST to the app's webhook endpoint (this includes anyone who has ever received/captured one legitimate webhook body+HMAC pair, e.g. from their own shop's webhook, or via a network intermediary) can resubmit that exact body with a different `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will return true because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the payload belongs to a different, victim shop. If the host application uses `data.shop` (as documented in `docs/usage/webhooks.md`) to select which tenant's records to update, this allows cross-tenant data confusion/corruption — writing shop-A's webhook payload into shop-B's tenant context.

### Likelihood Explanation
Likelihood is realistic for any multi-tenant app built on this gem's documented pattern (`data.shop` is the officially documented way to select the tenant, per `docs/usage/webhooks.md`), since obtaining one valid `(body, hmac)` sample is trivial for any shop that has installed the app (their own store's webhooks), and the shop-domain header is fully attacker-controlled on replay.

### Recommendation
Bind the shop identity into the verified signature material, or otherwise cryptographically tie the `shop` header to the specific shop's registered/expected value (e.g., compare against a shop looked up independently, or include the shop domain in the HMAC-signed payload/derivation) before trusting `request.shop` in `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked against a known session/shop record before being used for tenant routing.

### Proof of Concept
1. App installed on `attacker-shop.myshopify.com`; attacker triggers a webhook (e.g., `orders/create`) and captures the raw POST body and the `x-shopify-hmac-sha256` header — both are computed with the app's single shared `client_secret`.
2. Attacker replays the exact same body/HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` (lines 12-22) recomputes the HMAC only from `to_signable_string` (the raw body) and succeeds.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` and invokes the app's handler, which per the gem's own documentation uses `data.shop` to select the tenant to act on.
