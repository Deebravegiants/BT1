### Title
Webhook shop domain is trusted by the handler but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read directly from the `X-Shopify-Shop-Domain` header, but `HmacValidator.validate` only verifies `to_signable_string`, which returns the raw body only. The shop domain is never part of the signed material, so the identity binding `shop authenticated == shop delivered to handler` does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop` method simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header verbatim, with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body for webhook requests) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then immediately trusts `request.shop` and hands it to the registered handler as the tenant identifier: [4](#0-3)  The documented/intended usage constructs `WebhookMetadata` with `shop: request.shop` for the app to key its per-tenant business logic on: [5](#0-4)  and the gem's own docs instruct apps to use `data.shop` as the tenant key (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

Since Shopify apps share a single `api_secret_key` across every shop that installs the app, the HMAC secret is not shop-specific. An attacker who installs the target public app on their own (attacker-controlled) development/trial store receives real Shopify webhooks with a valid `hmac-sha256` signature computed over a body they fully control (they can trigger events, e.g. by editing their own products, or in the extreme, they can also compute the signature offline given any raw body since the signature depends only on the app secret and body — but even without that, they can capture their own legitimate webhook and replay it). They can then replay that request to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain. `HmacValidator.validate` still passes because the signature never covered the shop header, so `Registry.process` will call the handler believing the event came from the victim tenant.

### Impact Explanation
This breaks the identity binding "the shop authenticated by the HMAC == the shop delivered to the tenant-scoped webhook handler," enabling cross-tenant impersonation of webhook events. An attacker (an unprivileged internet user who can install the app on their own store — no leaked credentials or privileged account required) can spoof `orders/create`, `app/uninstalled`, `shop/update`, or any other subscribed webhook as if it originated from a victim shop, letting them inject attacker-controlled data or trigger tenant-specific side effects (data writes, session/token revocation flows, billing state changes, etc.) under a victim shop's identity in any host application that follows this gem's documented usage of `data.shop`. This satisfies the cross-tenant access impact category.

### Likelihood Explanation
Likelihood is high: the only prerequisite is that the attacker can install the target app on any store they control (a normal, low-privilege action for any app listed on the Shopify App Store, or a dev/partner store) to obtain a validly-signed webhook body, then replay it with a forged shop header. No leaked secrets, tokens, or elevated privileges are needed — the vulnerability is purely a consequence of the gem's `to_signable_string` implementation excluding the shop domain from the signed payload.

### Recommendation
Bind the shop domain into the material that is HMAC-verified, or otherwise cryptographically tie the header value to the signed body/topic — e.g., include the `shop`, `topic`, and `webhook_id` in the signable string (mirroring how `AuthQuery#to_signable_string` binds `shop` into its signed query), or independently verify `request.shop` against a shop that has an active, previously-registered webhook subscription/session before trusting it. Document clearly that `request.shop` is unauthenticated header data if a full fix cannot be made without breaking compatibility with Shopify's existing HMAC scheme (which Shopify itself only signs over the raw body) — but in that case, this crosses from a gem-only bug into a Shopify-webhook-protocol-level property, so it is worth confirming whether this exact behavior (signing raw body only, not headers) matches Shopify's official server-side spec before treating it purely as a library defect.

### Proof of Concept
1. Attacker installs the victim app on their own store `attacker.myshopify.com` (no special privilege needed).
2. Attacker triggers a subscribed event (e.g., updates a product) on their store, causing Shopify to send a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's `api_secret_key`.
3. Attacker intercepts/replays this exact request to the same endpoint, but rewrites the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (unchanged) and succeeds: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, and the host app processes attacker-controlled data as if it came from the victim tenant.
