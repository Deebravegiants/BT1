### Title
Stale `account.owner` lets a former position-NFT holder keep borrowing and withdrawing after transferring the position — (`contracts/controller/src/account.rs`)

### Summary
The controller authorizes `borrow`, `withdraw`, and every strategy entrypoint by comparing the caller to the `owner` field stored inside the `Account` record (`account.owner`), not to the live owner reported by the position-NFT contract. The position NFT is a stock OpenZeppelin enumerable with no transfer hook into the controller, so `account.owner` is never updated when the NFT changes hands. The previous holder therefore retains full spending authority over an account they no longer own — the same bug class as the TypeBot `getSheets` advisory (a handler authorizing against stale/absent ownership state rather than the current owner).

### Finding Description
`require_owner_or_delegate` in `contracts/controller/src/account.rs` gates all economically sensitive position operations:

```rust
// contracts/controller/src/account.rs
if caller == owner {           // `owner` is &account.owner, a stored field
    return true;
}
let active_manager =
    storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
```

It is invoked by `process_borrow` (`positions/debt.rs`), `process_withdraw` (`positions/supply.rs`), the `Migrate`/`Multiply` account guards, and the swap/repay-with-collateral/flash_position strategies — each passing `&account.owner` read from storage.

Only `require_account_owner` (used by `renew_account`, `add_delegate`, `remove_delegate`) actually consults the NFT:

```rust
let owner = storage::account_owner(env, account_id);  // live owner_of
assert_with_error!(env, owner == *caller, ...);
```

The position-NFT (`contracts/position-nft/src/contract.rs`) implements plain `NonFungibleToken`/`NonFungibleEnumerable`; its `transfer`/`transfer_from`/`approve` paths are inherited from `stellar_tokens` and perform no callback into the controller, and no controller code path rewrites `account.owner`. So after a legitimate NFT transfer (or sale on a marketplace), the stored `account.owner` is permanently stale.

### Impact Explanation
Theft of user funds. Any account that has ever been transferred has a second, invisible principal: the seller. The former owner can call `borrow(caller=old_owner, account_id, borrows, to=Some(attacker))` to draw the account's full borrowing capacity to an external recipient, and `withdraw` its free collateral — up to the solvency limit — draining value that now belongs to the NFT buyer. Because delegates can also designate `to` recipients, the entire economic value of the position is extractable. Every transferred position on the protocol is affected; positions sold or moved between a user's own wallets are silently back-doored.

### Likelihood Explanation
Requires only that a position NFT has changed hands — a normal operation (marketplace sale, wallet rotation, OTC deal). The attacker is the prior holder, needs no privilege, and the calls are ordinary `borrow`/`withdraw` invocations that pass all auth checks because `account.owner` still names them. If `account.owner` is in fact synchronized somewhere on transfer, the finding collapses — but no such update path exists in `contract.rs`, and the NFT has no mechanism to notify the controller, so none can exist on-chain.

### Recommendation
In `require_owner_or_delegate` and `is_owner_or_delegate`, resolve the owner via `storage::account_owner(env, account_id)` (the live NFT `owner_of`) instead of the stored `account.owner` field, or remove the field entirely so there is a single source of truth. As defense-in-depth, also key delegate grants to the live NFT owner at check time, so grants made by a prior owner cannot linger.

### Proof of Concept
```rust
// Alice supplies and borrows, then transfers her position NFT to Bob.
nft.transfer(&alice, &bob, &account_id);
// account.owner in controller storage is still ALICE.

// Alice (no longer the NFT owner) drains Bob's new position:
ctrl.borrow(
    &alice,            // caller auth: alice signs — she still passes the check
    &account_id,
    &vec![&env, (eth_market, max_borrowable)],
    &Some(attacker),   // 'to' may be any external address
);
ctrl.withdraw(&alice, &account_id, &vec![&env, (usdc_market, 0 /* all */)], &Some(attacker));
```
`require_owner_or_delegate` returns `true` on `caller == account.owner` (stale ALICE), solvency is re-proven against the account's collateral, and funds are paid to `attacker`. Bob's newly purchased position is left maximally leveraged with its collateral pulled out — pure theft enabled by the stale authorization field.
