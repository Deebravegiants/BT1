### Title
Webhook shop-domain is not bound to the HMAC, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then trusts the unauthenticated `shop-domain` header to attribute the event to a tenant. This is the same bug class as the reported oracle issue: a value used downstream (`ethUsdPrice`/`arbUsdPrice` in the report, `shop` here) is not covered by the integrity check that is supposed to bind it (staleness/heartbeat check there, HMAC coverage here).

### Finding Description
The HMAC signature is verified only over the raw webhook body: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes and compares the signature using exactly that signable string, with a single global secret (`Context.api_secret_key`, shared across every shop that installs the app): [2](#0-1) 

`Registry.process` then uses `request.shop` — read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is **not** part of the signed bytes — to build the `WebhookMetadata` that is handed to the app's handler as the tenant identity for that event: [3](#0-2) 

The identity binding that should hold is:
`shop_header == shop_actually_bound_by_HMAC`

but in fact `shop_actually_bound_by_HMAC` is undefined — the HMAC only proves "this body was signed with the app's secret," not "this body came from shop X." Because the secret (`api_secret_key`) is the same for all shops that install the app, any merchant who installs the app on their own store can:
1. Trigger a real webhook delivery to their own endpoint (or otherwise obtain a body + valid HMAC pair signed with the shared secret), and
2. Replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop that also has the app installed.

`Utils::HmacValidator.validate` will return `true` (it only checks the body against the secret), and `Registry.process` will hand the forged payload to the handler tagged with the victim's shop domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged, arbitrary Shopify merchant (attacker) can cause data to be injected/attributed into another tenant's (victim's) session/data path inside the host app, i.e., cross-tenant access — one of the explicitly in-scope Critical impacts. The host application has no way to detect the spoofing because the gem's own HMAC validation utility (`Utils::HmacValidator`) is the trust boundary and it does not bind the shop identifier at all.

### Likelihood Explanation
Likelihood is high for any app that (a) uses a single, app-wide `api_secret_key` (the default/only mode supported by `ShopifyAPI::Context`) and (b) is installed by more than one shop — which is the normal operating mode for any public Shopify app. The attacker needs no privileges beyond installing the app on a store they control, which is the baseline "unprivileged internet user" capability for this threat model.

### Recommendation
Bind the shop identity into the value that is actually verified, rather than trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) header content as part of the string passed to `Utils::HmacValidator.validate`/`to_signable_string` in `lib/shopify_api/webhooks/request.rb`, matching how `AuthQuery#to_signable_string` already includes `shop` in its signed parameters (`lib/shopify_api/auth/oauth/auth_query.rb`).
- Alternatively/additionally, require callers to supply the expected shop (from their own session/tenant lookup) and have `Registry.process` assert that it matches `request.shop` before invoking the handler, rather than only relying on Chainlink-style "signature over body only" trust.

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and `victim.myshopify.com`; both share the same `Context.api_secret_key`.
2. Attacker triggers any webhook event on their own store, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` value `H` (valid because `H = HMAC(secret, B)`, independent of shop).
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, and header `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` → passes, because it only checks `B` against `H`.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)` — the host app processes attacker-controlled data under the victim tenant's identity.
