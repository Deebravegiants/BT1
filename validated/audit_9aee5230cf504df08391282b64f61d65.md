### Title
Webhook `shop-domain` header is trusted as the tenant identifier without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `HmacValidator` only verifies the raw request body. `Registry.process` passes this unauthenticated `shop` value straight into `WebhookMetadata`, which the gem's documentation instructs host applications to trust as the tenant identifier for the webhook. The equality the gem should, but does not, enforce is: `hmac_signed_bytes == bytes_that_determine_the_tenant`. Instead, `hmac_signed_bytes == raw_body` while `tenant_identifier == shop-domain header` (unsigned).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read directly from a caller-supplied header with no cross-check against the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over that body-only signable string, then immediately forwards `request.shop` into `WebhookMetadata` for the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string`, so any field excluded from that string (here, the whole `shop-domain` header) is never authenticated: [4](#0-3) 

The gem's own documentation tells developers that `data.shop` is "The shop domain of the webhook" and shows it being used directly to key business logic (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing that host apps are expected to trust this field as an authenticated tenant identifier — which it is not.

### Impact Explanation
Because the HMAC only proves "this body was produced with the app's client secret" and not "this body belongs to shop X," an attacker who obtains any single valid `(raw_body, hmac)` pair for the app (e.g., from a webhook delivered to their own installed/test shop, which is trivially available to any developer who can install the app) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still returns `true` because the body and HMAC match, but `WebhookMetadata#shop` now reports the attacker-chosen victim domain. Any host application that uses `data.shop` to select which tenant's records to update (exactly as the gem's own docs recommend) processes attacker-supplied data under the wrong tenant's identity — a cross-tenant data integrity/confusion issue reachable by any unprivileged user who can install the app once and target another known shop domain.

### Likelihood Explanation
No access token, `client_secret`, or privileged account is required. The only prerequisite is possession of one legitimate `(body, hmac)` pair, obtainable by any developer/attacker who installs the app on their own store, since Shopify sends real webhook deliveries as soon as the app is installed and subscribed. Combined with knowledge of a target shop's public `.myshopify.com` domain, this makes the attack straightforward and repeatable for any topic/body the attacker has previously captured.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie `shop` to the verified payload, before exposing it as trusted metadata:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string` so the HMAC covers them, if Shopify's signing scheme is updated to support this, or
- At minimum, document loudly (and enforce where possible) that `WebhookMetadata#shop` is an **unauthenticated** hint and that host applications must independently verify the shop is one they have an active, matching session/installation for before trusting the payload for that tenant, and add duplicate/webhook-id + shop consistency checks recommended by Shopify's replay-protection guidance.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com` and subscribe to a webhook topic (e.g., `orders/create`).
2. Capture one legitimate delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Send a forged HTTP request to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H`, so validation succeeds: [5](#0-4) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from, nor was authenticated for, that shop — demonstrating the missing binding between the HMAC-verified bytes and the tenant identifier the app is told to trust.
