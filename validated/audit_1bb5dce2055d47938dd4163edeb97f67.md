### Title
`HyperFungibleToken.register_token`/`update_token` don't check whether `token_contract` is already bound to a different asset, allowing silent cross-asset mint confusion - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet_hyper_fungible_token::register_token` and `update_token` write the bidirectional mapping between a local `AssetId` and a remote EVM contract address (`TokenContracts` / `ContractToAsset`) without ever verifying that the supplied `token_contract` is not already bound to a *different* local asset on that chain. This is the same defect pattern as `BlueBerryBank.addBank()`, which fails to verify that `token` is actually the underlying asset of `cToken` before wiring the two together.

### Finding Description
`register_token` unconditionally inserts into both storage maps: [1](#0-0) 

and `update_token`'s `add_chains` path does the same, only removing the *old* mapping for the asset currently being updated, never checking whether the new `token_contract` is already claimed by another asset: [2](#0-1) 

Because `TokenContracts` is keyed by `(StateMachine, AssetId)` but `ContractToAsset` is keyed by `(StateMachine, Vec<u8> contract)`, it is possible for two distinct local assets, `A` and `B`, to both have `TokenContracts` entries pointing at the *same* remote contract address on the same chain (e.g. via an admin typo, a copy-pasted address, or a legitimate reuse of a proxy/factory-deployed address). When that happens, `ContractToAsset` can only hold one value for that `(chain, contract)` key, so whichever asset is registered/updated last silently overwrites the reverse mapping. There is no `ensure!` check anywhere in `register_token`/`update_token` guarding against this, unlike `BlueBerryBank.addBank()`'s recommended `require(token == cToken.underlying())` check.

On `on_accept`, the pallet trusts `ContractToAsset` exclusively to determine which local asset an inbound message credits: [3](#0-2) 

So once the reverse mapping is captured by asset `B`, any inbound `Send` message from that contract — including ones that were actually meant to settle outbound transfers of asset `A` — will be decoded and minted/released as asset `B`: [4](#0-3) 

Meanwhile, outbound `send()` for asset `A` still dispatches to the same shared contract address recorded in `TokenContracts`, since that lookup is unaffected by the `ContractToAsset` collision: [5](#0-4) 

The result: asset `A`'s escrowed/burned funds can never be correctly returned (the pallet will never again resolve an inbound message from that contract to asset `A`), while asset `B` receives unbacked mints/releases for events that never corresponded to it.

### Impact Explanation
- **Unbacked mint / balance duplication** for asset `B`: it is credited for value that actually originated from asset `A`'s locked/burned funds.
- **Permanent freezing of funds** for asset `A`: because `ContractToAsset` for that `(chain, contract)` pair now permanently resolves to `B`, any inbound settlement message intended for `A` will be misrouted, and the pallet has no code path to reclaim or redirect misattributed inbound messages back to `A`.
- This is a High-severity issue consistent with the reported class: an unprivileged bridging error becomes irrecoverable once triggered, and the collision can persist even if the `CreateOrigin` later tries to "fix" one of the assets, since `update_token`/`register_token` never validate uniqueness of the reverse mapping.

### Likelihood Explanation
`register_token`/`update_token` are gated by `T::CreateOrigin`, which per the runtime config is intended to be root/governance — but exactly like `BlueBerryBank.addBank()` (also `onlyOwner`), the underlying report treats "no cross-validation between the two bound identifiers" as a real vulnerability regardless of caller privilege, because a single honest configuration mistake (address typo, copy-paste from the wrong deployment, re-registering a proxy address after redeploying `A`'s contract) is sufficient to trigger it, and there is no on-chain safeguard preventing it.

### Recommendation
In both `register_token` and `update_token`, before inserting into `TokenContracts`/`ContractToAsset`, check that the target `(chain, token_contract)` key in `ContractToAsset` is either unset or already bound to the *same* asset being registered/updated:
```rust
if let Some(existing) = ContractToAsset::<T>::get(chain, &token_contract) {
    ensure!(existing == registration.local_id, Error::<T>::ContractAlreadyBoundToAnotherAsset);
}
```
This mirrors the recommended fix for `BlueBerryBank.addBank()` — validating the correspondence between the two identifiers being bound before committing them to storage.

### Proof of Concept
1. Governance/`CreateOrigin` calls `register_token` for asset `A` with `chains = { Evm(1) => ChainConfig { token_contract: 0xCCCC..., decimals: 18 } }`. Now `TokenContracts[(Evm(1), A)] = 0xCCCC...` and `ContractToAsset[(Evm(1), 0xCCCC...)] = A`.
2. A user calls `send` to move `X` units of asset `A` to chain `Evm(1)`; the pallet locks/burns `X` and dispatches a `Send` POST to `0xCCCC...`.
3. Before the response/ack lands, governance registers a second asset `B` and, due to a copy-paste error, reuses the same contract address: `register_token` for `B` with `chains = { Evm(1) => ChainConfig { token_contract: 0xCCCC..., decimals: 18 } }`. This overwrites `ContractToAsset[(Evm(1), 0xCCCC...)] = B`, with no error raised.
4. The counterpart EVM contract at `0xCCCC...` eventually sends a `Send` message back (e.g., a corresponding transfer unrelated to step 2, or the same settlement flow). `on_accept` resolves `ContractToAsset::get(Evm(1), 0xCCCC...)` to `B` and mints/releases `X` units of asset `B` to the beneficiary — asset `A` is never credited back, and its escrowed/burned `X` units are permanently unaccounted for.
