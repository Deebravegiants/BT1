Confirmed: `Config::validate` at src/config.rs:324-326 only checks `sound_volume`, and the `.filter(Self::validate)` in `from_backend` never inspects the PCP threshold fields, so arbitrary `u32` values (including `u32::MAX`, or `dropping_threshold < blocking_threshold`) pass straight through.

### Title
Unvalidated backend-supplied PCP thresholds allow unbounded biometric custody-package queue growth - (File: src/config.rs)

### Summary
`Config::from_backend` (src/config.rs:152-287) copies `pcp_tier1_blocking_threshold`, `pcp_tier1_dropping_threshold`, `pcp_tier2_blocking_threshold`, and `pcp_tier2_dropping_threshold` directly from the backend response with only `Option::unwrap_or(default)`, and `Config::validate` (src/config.rs:324-326) checks only `sound_volume`. A backend response (reachable using only the orb's own signup token against its own `/api/v1/orbs/{id}` endpoint) can therefore set these thresholds to pathological values, e.g. `blocking_threshold = u32::MAX` and/or `dropping_threshold` set below/above the blocking threshold in unsafe ways, which the data-uploader queue logic accepts unconditionally.

### Finding Description
`backend::config::request` -> `Config::from_backend` is the only place these four `u32` fields are validated, and no bounds/relationship checks exist between blocking and dropping thresholds or against sane absolute caps [1](#0-0) . `Config::validate` only asserts `sound_volume <= MAX_SOUND_VOLUME` [2](#0-1) , so a config with `pcp_tier1_blocking_threshold = u32::MAX` and `pcp_tier1_dropping_threshold = 0` passes `.filter(Self::validate)` and is accepted (src/config.rs:286).

Downstream, `data_uploader::Agent::run` (src/agents/data_uploader.rs:95-166) uses these thresholds directly:
- Blocking check: `queue.len() >= blocking_thresholds[i] as usize` (src/agents/data_uploader.rs:108-115) — with `blocking_threshold = u32::MAX`, this condition is unreachable in practice, so `check_blocking` never returns `true` and signups are never throttled via `wait_queues`.
- Dropping check: `if queues[i].len() == dropping_thresholds[i] as usize { queues[i].drop_oldest().await; }` (src/agents/data_uploader.rs:143-145) — this uses strict equality (`==`), not `>=`. Combined with a backend-controlled `dropping_threshold`, an attacker-controlled backend can pick a value that the queue length skips over (or set it absurdly high), causing the drop-oldest safety valve to never fire, so packages accumulate without bound in the in-memory `VecDeque<Pcp>` (src/agents/data_uploader.rs:57-60).

Because each `Pcp` embeds actual biometric image/data payloads (`data: Vec<u8>`) (src/agents/data_uploader.rs:41-55), unbounded accumulation directly grows memory usage with sensitive biometric custody-package content, and combined with a stalled/failing uploader (e.g. induced by the same malicious backend returning persistent errors from the upload endpoint), the queue can grow without any backpressure or retention bound.

### Impact Explanation
This is a resource-exhaustion / retention-policy-violation issue: the orb's own custody-package queue (containing iris/face biometric data) can grow unbounded in memory (or, in the persistent-queue mode, on disk) because the "blocking" and "dropping" backpressure mechanisms both depend entirely on unvalidated `u32` values from the backend response. This matches the "resource exhaustion / DoS" and "biometric custody data retention" class of impact, though it does not lead to unauthorized signups, identity mis-binding, or biometric disclosure — it is a config-validation gap that can be leveraged by a compromised/malicious backend endpoint (in-scope since the attacker's own orb session hits this endpoint with only its own token, no operator privileges needed).

### Likelihood Explanation
Feasibility is high in the sense that reaching this code path requires no special privileges — any orb performing its normal `/api/v1/orbs/{id}` config fetch with its own token will parse whatever `Config` JSON is returned (src/backend/config.rs:79-90). However, exploitation requires the *backend itself* (or a MITM within the attacker's own TLS session, which is normally prevented by TLS/cert pinning if present) to return the malicious config — this is a "malicious/compromised backend" precondition, not something an unprivileged external attacker without backend control can trigger on someone else's orb. Given the stated precondition ("no operator access needed, only the orb's own token, standard config fetch"), this is reachable for an attacker who controls or spoofs their own backend responses.

### Recommendation
Add explicit validation in `Config::validate` (or a dedicated check in `Config::from_backend`) enforcing sane relationships and bounds, e.g.:
- `pcp_tier1_dropping_threshold` and `pcp_tier1_blocking_threshold` (and tier2 equivalents) must be within a fixed absolute maximum (e.g. a small constant reflecting real memory/disk budgets).
- `dropping_threshold >= blocking_threshold` should be enforced (or rejected) so the drop safety-valve always fires before/at the blocking limit.
- Change the dropping check in `data_uploader.rs` from `queue.len() == dropping_thresholds[i] as usize` to `queue.len() >= dropping_thresholds[i] as usize` so it is a robust threshold rather than an exact-match, closing the "skip-over" edge case.
