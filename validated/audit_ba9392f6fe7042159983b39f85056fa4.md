### Title
Flashloan-inflated balance lets a single solver set the published phantom-order price and liquidity depth ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` weights every phantom-order bid by a **live, unpinned** `balanceOf`/vault-`maxWithdraw` read of the solver's output-token inventory, then feeds those weights into `weightedMedian`, which is a *selection*, not a blend — the bidder holding over half the leg's weight has its exact quoted price published verbatim. Because the balance read defaults to chain head (`blockTag = "latest"`) rather than a fixed historical block, a solver can flashloan-borrow the output token immediately before the snapshot is computed, dominate the weight, dictate the published price/liquidity, and repay the loan afterward — exactly the balance-based-check bypass pattern in the reference report, applied to a price/liquidity oracle instead of a token allowlist.

### Finding Description
The weight used to price a phantom-order leg and to populate solver liquidity rows comes from a spot balance read: [1](#0-0) 

`getTotalSolverBalance` defaults `blockTag` to `"latest"`, and the decision record explicitly documents that the periodic/window-close snapshot path (used by `aggregatePhantomBids`) intentionally reads every chain at its head, unlike the per-event refresh path which pins reads to a specific historical block: [2](#0-1) 

That live balance becomes the weight for `weightedMedian`, which is documented and implemented as a *selection*: the bidder whose cumulative weight crosses 50% has its exact price returned as the leg's `medianPrice`/`lowestPrice`/`highestPrice`: [3](#0-2) 

The whole flow is invoked, unprivileged, by any address that can get itself EIP‑7702‑delegated to a chain's `SolverAccount` and place a phantom bid — the verification only checks the bid's own signature and delegation, not that the balance backing it is durable: [4](#0-3) 

The resulting `medianPrice` is persisted to `PhantomOrderPriceSnapshotV2` and immediately folded into the pool's public `sellRate`/`buyRate` and depth: [5](#0-4) 

Those pool rates are not merely informational — they are read directly by the SDK's `quoteIntent()` to size **real** cross-chain intent orders when `strategy: "indexed_rates"` is used, with "no automatic fallback to another price source": [6](#0-5) 

### Impact Explanation
An attacker who is (or controls) a delegated solver can:
1. Flash-borrow the leg's output token on the destination chain.
2. Submit a phantom bid at an arbitrary price while holding the inflated balance, so its weight exceeds 50% of the leg's total and `weightedMedian` returns that attacker-chosen price verbatim (documented behavior: "a solver holding over half the leg's weight sets the published price verbatim").
3. Repay the flash loan once the snapshot RPC read completes.

This lets the attacker single-handedly set the published `sellRate`/`buyRate` for a `LiquidityPool` to any value, which:
- Corrupts prices used by `quoteIntent()` to construct real orders (`amountIn`/`amountOut`), causing legitimate users to place cross-chain orders at a manipulated rate — economic loss for the user or unfair extraction for the manipulating solver, who can then be the one to fill the mispriced order.
- Inflates `PoolBidder.liquidity`/`PoolChainLiquidity.depth`/`PoolRoute` rows with capital that no longer exists once the flashloan is repaid, advertising fillable depth and cross-chain routes that are not actually backed — a route unable to deliver at the size/price it publishes.

### Likelihood Explanation
Reachable by any unprivileged address that can obtain solver delegation and win/hold a flashloan-sized position for the short window the aggregation's `eth_call`s execute; no governance or admin action is required. The bug is a direct consequence of a documented design choice (window-close reads pinned to "latest" rather than a historical block), so it is deterministic once an attacker times the flashloan around the bid window's close.

### Recommendation
Do not use a live spot `balanceOf`/`maxWithdraw` read as bid weight for price selection. Options: pin the weighting read to a block from before the bid window opened (as already done for the per-event refresh path), require a time-locked/staked balance rather than a spot balance, or cap a single bidder's influence on `weightedMedian` regardless of its instantaneous balance (e.g., weight caps, TWAP-style balance averaging across the window).

### Proof of Concept
1. Attacker delegates an address to the destination chain's `SolverAccount`.
2. At/just before the phantom order's bid window closes (`PhantomBidWindowExhausted` is about to fire), attacker flash-borrows a large amount of the leg's output token into the delegated solver address.
3. Attacker submits a phantom bid quoting an arbitrary, favorable price for that leg.
4. `aggregatePhantomBids` reads the solver's balance at chain head (unpinned `"latest"`), sees the flash-loan-inflated balance, and the bid's weight dominates `weightedMedian`, which returns the attacker's exact quoted price (`phantom-aggregation.ts:709-724`).
5. Attacker repays the flashloan in the same transaction/block.
6. `handlePhantomOrderPrices` persists this manipulated price into `PhantomOrderPriceSnapshotV2` and `updateLiquidityPools`, corrupting the pool's public `sellRate`/`buyRate` and depth, which `quoteIntent()` then serves to real users placing real orders.

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

export async function getTotalSolverBalance(
	evmRpcUrl: string,
	chain: string,
	token: string,
	solver: string,
	yieldVaults: YieldVaultMap,
	blockTag = "latest",
): Promise<bigint> {
	const padded = solver.replace("0x", "").padStart(64, "0")
	const raw = await ethCallUint(evmRpcUrl, token, `0x70a08231${padded}`, blockTag) // balanceOf(address)
	const vaults = yieldVaults[chain]?.[token.toLowerCase()] ?? []
	const vaultBalances = await Promise.all(
		vaults.map((v) => ethCallUint(evmRpcUrl, v, `0xce96cb77${padded}`, blockTag)), // maxWithdraw(address)
	)
	return vaultBalances.reduce((acc, b) => acc + b, raw)
}

### quoteIntent(params)

Quotes an intent from the latest aggregate pool buy or sell rate published by the indexer. The pool rate is depth-weighted from fresh chain samples. Pass token addresses directly—the SDK resolves their configured symbols and decimals. No `strategy` option is needed for indexed-rate quotes.

Indexed-rate quotes require an attached Hyperbridge indexer client. There is no automatic fallback to another price source.

Use `amountIn` and `amountOut` when constructing the `inputs` and `output.assets` for an IntentGateway V2 order.

```typescript lineNumbers
import { createQueryClient, IntentGateway } from "@hyperbridge/sdk";

const gateway = (await IntentGateway.create(source, dest)).withQueryClient(
  createQueryClient({ url: "https://nexus.indexer.polytope.technology" }),
);

const quote = await gateway.quoteIntent({
  tokenIn: "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
  tokenOut: "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F",
  amountIn: 100_000_000n,
});

console.log(quote.amountIn, quote.amountOut);
if (quote.strategy === "indexed_rates") {
  console.log(quote.quoteMetadata.rateSide, quote.quoteMetadata.rate);
}
```

The order's source and destination chains select the configured token deployments. The SDK uses the pool's indexed buy rate when the order buys the quote token with the base token, and the indexed sell rate for the reverse direction. If that direction has no indexed rate, the quote fails clearly instead of using a different market.

The previous Phantom snapshot source remains available with `strategy: "phantom_snapshot"`. Pass `strategy: "uniswap_v4"` only when explicitly requesting a Uniswap quote.
