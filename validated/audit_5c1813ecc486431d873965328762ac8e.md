## Analysis

The reported ETH re-entrancy bug is not applicable to this Ruby gem (no EVM/ETH transfer code exists here), but the report's general bug class — "unprotected data are trusted based on a check that covers something narrower" — maps to a concrete identity-binding gap in the webhook HMAC verification path.

### Root cause

`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but signs **only the raw request body**: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` values are read straight from HTTP headers and are **not** part of the signed payload: [2](#0-1) 

`Registry.process` verifies the HMAC over the body only, then trusts the unauthenticated `request.shop` header to build the `WebhookMetadata` passed to the app's handler — the value host apps commonly use as the tenant key: [3](#0-2) 

`HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the body) matches the signature, never binding it to the `shop` header: [4](#0-3) 

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC that `Registry.process` verifies covers the body but not the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. The `shop` value that is handed to the app's webhook handler as the tenant identifier is therefore attacker-controllable independent of signature validity.

### Finding Description
The identity binding that should hold is: `hmac_verified_bytes == bytes_that_determine_the_tenant`. Here that equality is broken: `hmac_verified_bytes = raw_body` while `bytes_that_determine_the_tenant = header["shop-domain"]`, and the header is never included in `to_signable_string`. Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, any tenant that can obtain one valid `(raw_body, hmac)` pair for the app (e.g., by triggering a webhook to its own store, or capturing any legitimately delivered webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will report success because it never inspects the shop header, and `Registry.process` will pass the forged `shop` value straight to the application's handler.

### Impact Explanation
This is a cross-tenant identity confusion at the point the gem hands data to the merchant's application: an unprivileged actor who controls one installation of the app can cause webhook events (with an attacker-influenced body, since it's their own shop's webhook) to be attributed to a different, victim shop domain. Applications commonly use `WebhookMetadata#shop` as the row/tenant key when persisting orders, inventory, GDPR events, etc., so this can lead to cross-tenant data corruption or disclosure without needing the target's access token or `client_secret`.

### Likelihood Explanation
Any merchant who installs the app already possesses a way to obtain a validly signed body (their own webhook deliveries use the same app-wide secret). The webhook HTTP endpoint is public by design (Shopify posts to it over the internet), so replaying a captured request with a modified header requires no privileged access, TLS interception, or leaked secrets — only observing one's own legitimate webhook traffic.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed payload used for verification, or otherwise cryptographically bind the `shop` header to the signature before trusting it as a tenant identifier — e.g., have `to_signable_string` incorporate the shop domain, or have `Registry.process` independently confirm that the `shop` claim matches a value obtained through an authenticated channel (such as a session already scoped to that shop) rather than trusting the header verbatim.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both signed with the same `client_secret`.
2. Attacker triggers/receives a legitimate webhook for their own shop, capturing `raw_body` and its valid `x-shopify-hmac-sha256`.
3. Attacker POSTs the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because `to_signable_string` only ever compares `raw_body`.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-supplied data under the victim's tenant identity.
