## Answer

The strongest analog to the OpenQ "native token gets locked when overspecified" bug class is in `EvmHost`'s native-fee payment path: `dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()` all swap `msg.value` for the exact fee-token amount via Uniswap V2's `swapETHForExactTokens`, but none of them capture the router's return value to refund the *unused* ETH back to the caller.

### Title
Excess native ETH sent to `EvmHost.dispatch`/`fundRequest` is permanently stranded in the Host, not refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)` and `fundRequest()` accept `msg.value` and call Uniswap V2's `swapETHForExactTokens{value: msg.value}(fee, ...)`, but discard the returned `amounts` array and never refund any leftover native token to the caller.

### Finding Description

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

`swapETHForExactTokens` on the Uniswap V2 router only spends the amount of ETH actually required to produce the requested `fee`/`amount` output; any leftover ETH from `msg.value` is refunded by the router to whoever called the router — which is `EvmHost` itself (`address(this)` in that call context), not the original transaction sender. None of these three functions capture the `amounts[]` return value or use the leftover to send an explicit refund back to `_msgSender()`. As a result, any wei sent above the exact amount needed for the swap is retained inside `EvmHost`'s balance permanently, with no `withdraw`/`sweep` function surfaced for that scenario in the reachable code paths reviewed.

This is the same root-cause pattern as the OpenQ report: a payable entrypoint that accepts a native-token payment sized independently of the exact amount consumed internally, with no accounting/refund of the surplus, causing funds to become stuck in the contract.

Notably, the codebase's own documentation for the Uniswap fallback path elsewhere assumes the router refunds excess ETH to the *original depositor*: [4](#0-3) 
This comment reflects the same incorrect assumption baked into `EvmHost`: the refund actually lands on the immediate caller of the router (the Host contract), not the end user, unless a contract explicitly forwards it back.

Contrast this with `IntentGatewayV2.placeOrder`, which handles the identical Uniswap refund pattern correctly by capturing the spent amount and explicitly refunding the remainder to `msg.sender`: [5](#0-4) 
This shows the project is aware such refunds must be handled explicitly, but `EvmHost.dispatch`/`fundRequest` (the more fundamental, universally-reached dispatch/fee entrypoint used by every `HyperApp`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and the LayerZero endpoint adapter) lack this handling.

### Impact Explanation
Any unprivileged caller — a user calling a `HyperApp`'s `send`/message function with slightly more `msg.value` than the exact quoted amount (which is expected and encouraged, since `quote()` is explicitly documented as an off-chain, slippage-sensitive estimate — see the "Estimate Fees Off-Chain" warning), or a contract like `HyperFungibleToken.send()` or the LayerZero adapter that forwards `msg.value` to `EvmHost.dispatch()` — will have the unspent portion of their ETH permanently trapped in `EvmHost`. Since the fee estimate is explicitly approximate and subject to sandwich/slippage per the docs, any margin added by an integrator or wallet UI (a very common defensive practice) to guarantee the swap succeeds directly translates into permanently locked funds. This is a Medium-severity fund-freezing bug reachable from a single unprivileged dispatch transaction.

### Likelihood Explanation
High likelihood: overpaying `msg.value` for a Uniswap-based fee swap is a normal/expected user behavior (buffer for slippage, as the docs and `HyperbridgeLzEndpoint.quote` explicitly apply a "generous 2x buffer") and requires no privileged role or unusual setup — merely sending a POST/GET dispatch or `fundRequest` call with `msg.value` exceeding the exact swap requirement.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`), or require exact-value matching with a revert on overpayment.

### Proof of Concept
1. Deploy `EvmHost` with a configured Uniswap V2 router and fee token, as in the existing foundry test setup.
2. Call `dispatch(DispatchPost)` (or `dispatch(DispatchGet)` / `fundRequest`) with `msg.value` set to, e.g., 2x the amount quoted by `HyperApp.quote()`.
3. Observe: the transaction succeeds, `post.fee`/`amount` worth of fee token is credited internally, but `address(EvmHost).balance` increases by the unspent ETH instead of it being returned to the caller.
4. Confirm no function exists in the reachable/reviewed `EvmHost` surface to recover or forward that stranded native balance back to the original depositor.

Note: I could not fully verify within the available search scope whether `EvmHost` has any owner-only sweep/withdraw function for accumulated native balance; if such exists, the funds would only be recoverable by governance rather than the depositor, which is still an unauthorized/mismatched fund-flow relative to the depositor's intent, though it would reduce this from "permanent freeze" to "freeze recoverable only by admin."
