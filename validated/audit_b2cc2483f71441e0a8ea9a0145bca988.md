### Title
No per-eye/cross-eye fraud or liveness enforcement exists before `format_pipeline` serializes `Pipeline.v2.eye_left`/`eye_right` into one `CodesV2` record - ([File: src/backend/signup_post.rs])

### Finding Description
`biometric_capture::Plan` captures the left and right eye in two sequential phases driven by `target_left_eye` (`src/plans/biometric_capture/mod.rs:270-379`), storing whatever iris/face frames are on-target for each side independently into `Capture.eye_left` / `Capture.eye_right` [1](#0-0) . Nothing in `into_capture()` or anywhere else checks that the left and right captured frames belong to the same physical eyes/person, or carries any per-eye liveness/fraud verdict — `EyeCapture` only holds raw frames and net estimates [2](#0-1) .

`biometric_pipeline::Plan::run` independently runs the iris model on `eye_left`/`eye_right` frames and simply stores whatever comes back into `iris_left`/`iris_right` with no cross-eye comparison or gating logic [3](#0-2) . `EyePipeline` itself has no liveness/fraud verdict field at all [4](#0-3) .

The only fraud-check hook, `Self::detect_fraud` in `src/plans/mod.rs`, is a stub that unconditionally returns `Ok(false)` with the comment "FOSS: WE HAVE DELETED ALL FRAUD CHECKS" [5](#0-4) . This is corroborated by `src/plans/fraud_check.rs`, where `N_FRAUD_CHECKS = 0` ("FOSS: This is set to 0 because we manually deleted all fraud checks"), `Report::fraud_checks()` returns an empty array, and `FraudChecks::run()` always returns an empty `Report {}` [6](#0-5) [7](#0-6) . Consequently `fraud_detected()` on an empty check-set is always `false` [8](#0-7) .

`format_pipeline`/`format_eye_pipeline` then serialize `pipeline.v2.eye_left` and `pipeline.v2.eye_right` verbatim into one `CodesV2` and this is what gets uploaded via `request()` under a single `signup_id` [9](#0-8) . Because no stage (capture, pipeline construction, or `detect_fraud`) ever compares or gates on left/right liveness/fraud verdicts, there is no code path that can "refuse to build a Pipeline" on disagreement — disagreement is never even computed. An attacker who presents a genuine iris to one eye and a spoofed/printed/synthetic iris (or a different person's iris) to the other during the same sequential left/right capture window will have both accepted and bundled into a single coherent `CodesV2` record sent to the backend.

### Impact Explanation
This allows biometrically inconsistent (partially spoofed or mixed-identity) iris data to be packaged and submitted as one signup, since Orb-side fraud/liveness gating has been entirely removed rather than merely weakened for the cross-eye case. This maps to a liveness/fraud-bypass and identity-binding-integrity impact under the Orb bounty program, scoped to signups whose validity now depends entirely on backend-side verification (which is outside this codebase and not assessed here).

### Likelihood Explanation
Precondition is only that the attacker can present two different ocular inputs sequentially to the Orb's left/right optics during one capture session — no privileged access, tampering, or social engineering required. Given `detect_fraud` and `fraud_check::Report` are hard-coded no-ops in this build, the behavior is fully deterministic and repeatable on every signup attempt, not a race condition or edge case.

### Recommendation
Reintroduce fraud/liveness checks (or equivalent Orb-side heuristics) that are computed per eye and enforced for cross-eye/identity consistency before `biometric_pipeline::Plan::run` returns a `Pipeline`, and make `detect_fraud`/`fraud_check::Report::fraud_detected` fail-closed (return `true`/block) whenever such checks are absent or disagree, rather than the current fail-open stub that always yields `Ok(false)`.

### Proof of Concept
Integration test plan:
1. Construct two `Capture` fixtures (or one `Capture` with `eye_left`/`eye_right` populated from different source images, similar to `CiHacks::replace_captured_eyes` in `src/plans/integration_testing.rs:81-107`) representing a genuine left iris and a printed/synthetic or different-person right iris.
2. Run `biometric_pipeline::Plan::new(&capture, signup_id)?.run(orb)` and assert it returns `Ok(Pipeline { .. })` — demonstrating no rejection occurs despite inconsistent inputs.
3. Call `Self::detect_fraud(orb, debug_report, Some(&pipeline))` and assert it always returns `Ok(false)`.
4. Call `signup_post::format_pipeline(&pipeline)` and assert the resulting `CodesV2.left`/`CodesV2.right` both serialize successfully into one record, showing the mismatched eyes are combined and would be sent under a single `signup_id` via `request()`.

Expected (currently failing/absent) assertion for a fixed system: step 2 or 3 should return an error/`true` (fraud detected) when cross-eye/liveness verdicts disagree, preventing `format_pipeline`/`request()` from ever being reached with inconsistent eye data.

/// Serializes pipeline outputs into backend format.
#[must_use]
pub fn format_pipeline(pipeline: &Pipeline) -> Vec<CodesV2> {
    vec![CodesV2 {
        left: format_eye_pipeline(&pipeline.v2.eye_left),
        right: format_eye_pipeline(&pipeline.v2.eye_right),
        ir_net: pipeline.v2.ir_net_version.clone(),
        iris: pipeline.v2.iris_version.clone(),
    }]
}

fn format_eye_pipeline(eye: &EyePipeline) -> Vec<IrisData> {
    vec![IrisData {
        code: eye.iris_code.clone(),
        mask: eye.mask_code.clone(),
        code_version: eye.iris_code_version.clone(),
    }]
}
