### Title
Webhook Shop/Topic Identity Spoofing via HMAC Signature Covering Only the Request Body, Not the `shop-domain`/`topic` Headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values that are actually acted upon (and handed to the app's business logic) come from HTTP headers that are **not** included in the signed payload. An unprivileged merchant who has the app installed on their own store can capture a Shopify-signed webhook (raw body + valid HMAC) and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointing at a victim shop. The HMAC check still passes because it never covered those headers, causing the host application to process the event as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC-SHA256 only against `verifiable_query.to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` performs this single check and then dispatches the handler using the unauthenticated header-derived `shop`, `topic`, `webhook_id`, and `api_version`: [4](#0-3) 

The binding that should hold is: **`shop` (and `topic`) used by the handler == `shop` (and `topic`) cryptographically bound to the signed payload**. Instead, only `raw_body == raw_body` is verified; `shop`/`topic` are parsed but never verified. This mirrors the reported bug class ("a field acted on but not covered by the HMAC"): here it is the identity/routing headers of a webhook, not the payload contents, that are trusted without being covered by the signature.

### Impact Explanation
Any unprivileged user who can install the app on their own (attacker-controlled) shop can legitimately receive Shopify webhooks for that shop, complete with a valid `X-Shopify-Hmac-Sha256` value computed over a known raw body. Because the signature never binds to `shop-domain`/`topic`, that same (body, hmac) pair remains valid when replayed with a different `X-Shopify-Shop-Domain` or `X-Shopify-Topic` header. Host applications built on this gem key their business logic (e.g., session/data lookups, uninstall handling, order processing) off `WebhookMetadata#shop`/`#topic`, per `Registry.process`'s dispatch shown above, so the forged request is processed as if it belongs to a different, victim tenant. This is a cross-tenant identity-spoofing condition satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires nothing more than: (1) installing the target app on an attacker-owned store (a normal, unprivileged action any merchant can perform), (2) capturing one legitimately Shopify-signed webhook request sent to the app's endpoint, and (3) resending it to the same endpoint with a modified `shop-domain`/`topic` header. No access token, `api_secret_key`, or privileged credential is required — the attacker never needs to compute a valid HMAC, only reuse one Shopify already produced for their own shop.

### Recommendation
Bind the header-derived identity fields into the signed payload verification instead of trusting them independently:
- Extend `VerifiableQuery`/`HmacValidator` (or `Registry.process`) to additionally verify the `shop` (and ideally `topic`) header against an expected/allow-listed value tied to the session or app installation the webhook is meant for, or
- Compute/verify an HMAC that incorporates the shop domain and topic headers alongside the body, so a captured signature cannot be replayed against a different `shop-domain`/`topic` pair.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and trigger a webhook (e.g. `orders/create`) so Shopify sends a POST to the app's registered webhook endpoint with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw body B>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
2. Capture the raw body `B` and the valid `X-Shopify-Hmac-Sha256` value.
3. Replay a new request to the same endpoint with the same body `B` and the same HMAC header, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or a different registered `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-derives the HMAC from `raw_body` (`to_signable_string`) — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31` — so validation succeeds.
5. The handler is invoked via `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`) with `shop == "victim.myshopify.com"`, causing the host app to execute webhook logic attributed to the victim tenant despite the payload never being signed for that shop.
