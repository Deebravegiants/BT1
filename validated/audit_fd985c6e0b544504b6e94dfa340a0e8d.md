Confirmed. The vulnerability is fully supported by the code: `ShopifyAPI::Webhooks::Request#hmac` is computed only over the raw request headers `hmac-sha256`/`shop-domain`, and `Registry.process` validates the HMAC against `to_signable_string`, which returns only `@raw_body` — the `shop-domain` header is never part of the signed content.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop` value passed to the app's handler is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is **not** included in the signed payload. Any party capable of producing a request whose body+HMAC pair is valid for the app's shared `api_secret_key` can freely set the `shop-domain` header to any value, and the gem will hand that attacker-chosen shop identity to the host application as if it were authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

- `hmac` reads the `hmac-sha256` header.
- `shop` reads the `shop-domain` header.
- `to_signable_string` returns **only** `@raw_body`.

`Registry.process` verifies the HMAC and then forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata`, which is delivered to the app's handler as the trusted tenant identifier: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC — the `shop` field is entirely outside the cryptographic binding: [3](#0-2) 

Shopify apps share a single `api_secret_key` across **all** installing shops — the secret is not per-tenant. This means any merchant who has installed the app receives legitimate webhook deliveries (valid body + HMAC, computed with the app's shared secret) for their own shop. Because the `shop-domain` header sits outside the signed content, that same merchant can replay the identical raw body and HMAC pair while substituting the `shop-domain` header with a different (victim) shop's domain. `Registry.process` will still consider the request authentic (HMAC checks out) and will report the *victim's* shop identity to the handler as `WebhookMetadata#shop`, per the documented interface: [4](#0-3) 

This is the direct analog of the external report's root cause: an identity/ownership field (`followerProfileId`/target relationship in Lens; `shop` here) that is *acted upon* but not *covered by the same integrity check* (`SelfFollow` revert check vs. `tryMigrate`'s missing check; HMAC-signed body vs. unsigned `shop-domain` header). The broken binding as an equality is::
`authenticated_request(hmac) == request.shop` — which does not hold, since `hmac` authenticates `raw_body` only, while `shop` is read independently from an unsigned header.

### Impact Explanation
This breaks cross-tenant isolation (Critical impact per the given classification): a host application built on this gem's documented API (`docs/usage/webhooks.md`, using `data.shop` exactly as instructed to key session lookups, database writes, job enqueues, etc.) will process attacker-supplied "webhook events" under an arbitrary victim shop identity. Any unprivileged merchant who has installed the app (no special privileges, no access token or `api_secret_key` theft required — they already legitimately receive signed webhooks for their own shop) can trigger this. Depending on how the host app uses `data.shop` (e.g., to look up the victim's stored access token/session and perform actions, or to write attacker-controlled `body` content attributed to the victim shop), this can lead to cross-tenant data corruption or unauthorized actions performed in the context of a different merchant's shop.

### Likelihood Explanation
Likelihood is high: exploitation requires nothing beyond being a normal, unprivileged installer of the app who has received at least one legitimate webhook (capturing a valid `raw_body`/`hmac-sha256` pair), then replaying that exact body/HMAC to the app's webhook endpoint with a modified `shop-domain` header. No credentials, tokens, or `api_secret_key` knowledge are needed — only observation of one's own legitimate webhook traffic.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed content, or otherwise cryptographically bind the shop domain to the payload (e.g., cross-check the header against a shop specifically expected for the topic/registration, since a single shared secret is used across all tenants). At minimum, `Request#to_signable_string` should not silently ignore `shop-domain`; `Registry.process` should not treat the header-derived `shop` as authenticated purely because the raw body's HMAC checks out.

### Proof of Concept
```ruby
# Merchant M installs the app and legitimately receives a webhook for their own shop.
# They capture the raw body and the valid HMAC Shopify sent (both are legitimate,
# since the app's api_secret_key is shared across all shops, not per-tenant).
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker (merchant M) replays the same body/HMAC pair to the app's webhook
# endpoint, substituting the shop-domain header with the VICTIM's shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,       # still valid: signs only raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Registry.process succeeds: HMAC validates against raw_body only.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now believes this event genuinely originated from victim-shop.
