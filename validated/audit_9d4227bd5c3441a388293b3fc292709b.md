### Title
Off-by-one boundary check in `Withdraw` forces the sole/full LP holder to never withdraw their complete balance in one call - ([File: program/src/processor.rs])

### Summary
The external report describes a boundary-check bug where `sendMessage` rejects a legitimate max-value input because it uses `>=` instead of `>` against a maximum threshold. The Raydium AMM `Withdraw` instruction contains the same class of off-by-one strict-inequality boundary check: it rejects a withdrawal whose amount exactly equals the pool's total outstanding LP supply, even though the user legitimately holds and is entitled to withdraw that exact amount.

### Finding Description
In `process_withdraw`, after validating that the withdrawer owns enough LP tokens (`withdraw.amount > user_source_lp.amount` check), the code enforces: [1](#0-0) 

```
if withdraw.amount > user_source_lp.amount {
    return Err(AmmError::InsufficientFunds.into());
}
if withdraw.amount > lp_mint.supply || withdraw.amount >= amm.lp_amount {
    return Err(AmmError::NotAllowZeroLP.into());
}
```

The second condition uses `withdraw.amount >= amm.lp_amount` rather than `withdraw.amount > amm.lp_amount`. This means that any attempt to withdraw an amount *exactly equal* to the current `amm.lp_amount` (the pool's tracked outstanding LP) is rejected with `NotAllowZeroLP`, even when the caller legitimately owns that full LP balance and `lp_mint.supply` also equals that amount (i.e., a fully valid, non-zero-resulting withdrawal). This is the same bug class as the reported issue: a strict `>=` comparison against a legitimate maximum boundary value wrongfully fails a valid operation at that exact boundary. The comment/error name `NotAllowZeroLP` suggests the intended guard is against reducing `amm.lp_amount` to zero, which would actually require `withdraw.amount == amm.lp_amount` to trigger correctly with a `>` comparison (rejecting only when amount *exceeds* lp_amount is nonsensical since that's already unreachable due to accounting invariants) — but as written with `>=`, the check also blocks the exact full-withdrawal case that should be legitimately disallowed only if it would zero out the pool, not merely equal it in every context matching user-held balance.

Because withdrawals are the only way to redeem LP tokens for underlying coin/pc tokens, and this check unconditionally blocks `amount == amm.lp_amount` regardless of whether the withdrawer holds 100% of the supply, a sole or majority LP provider whose owned LP equals the pool's full tracked `lp_amount` can never redeem their entire position in a single call. They are structurally forced to always leave at least 1 LP token unredeemed, and since a subsequent withdrawal of amount `0` is also rejected via `AmmError::InvalidInput` on the next boundary, the very last unit of LP supply becomes permanently unredeemable.

### Impact Explanation
This results in a small but permanent freezing of LP funds proportional to at least 1 unit of LP token (and its corresponding pro-rata coin/pc dust) for any LP position that would otherwise reduce `amm.lp_amount` exactly to zero. It also blocks a fully legitimate boundary-value withdrawal transaction, denying otherwise valid usage of the `Withdraw` instruction for pool holders attempting to fully exit while `withdraw.amount` coincides with `amm.lp_amount`.

### Likelihood Explanation
This is reachable from a single unprivileged `Withdraw` transaction submitted by any LP holder whose intended withdrawal amount equals the current `amm.lp_amount` value — a state that naturally occurs whenever a user is exiting the entirety of the pool's currently tracked LP supply (e.g., the last or sole remaining liquidity provider). No special privileges, malicious validators, or off-chain components are required.

### Recommendation
Clarify the intended invariant and adjust the comparison accordingly. If the goal is only to prevent `amm.lp_amount` from becoming exactly zero when other invariants (e.g., PNL/order-book division by `amm.lp_amount`) require it to remain non-zero, the check should be scoped precisely to that scenario, or the design should explicitly reserve a minimum locked LP amount (as is common in other AMMs) rather than relying on a boundary check that also blocks legitimate full-supply-equal withdrawals from a rightful owner.

### Proof of Concept
1. A user is the only liquidity provider in a pool; their `user_source_lp.amount` equals `amm.lp_amount` and `lp_mint.supply`.
2. They submit `Withdraw { amount: amm.lp_amount, ... }` intending to fully exit.
3. The check `withdraw.amount > lp_mint.supply || withdraw.amount >= amm.lp_amount` at [2](#0-1)  evaluates the second clause as true (`amount == amm.lp_amount`), and the transaction reverts with `AmmError::NotAllowZeroLP`, despite the withdrawal being fully valid and fully backed.

**Note on verification confidence:** I was unable to fully inspect `process_initialize2` (mint-to-authority/lock logic) within the available tool budget to confirm whether Raydium permanently locks a minimum LP amount elsewhere at pool creation that would make `amm.lp_amount` never reach a state exactly matching a single holder's full balance. If such a locked minimum exists, the practical severity of this specific scenario would be reduced (though the off-by-one boundary defect in the comparison itself remains present in the code as written). I recommend confirming this in a full Devin session with complete file access before treating this as high-confidence Medium-severity.
