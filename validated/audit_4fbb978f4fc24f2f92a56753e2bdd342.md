### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC of the raw request body only [1](#0-0) . The `shop` identity that is handed to the app's webhook handler, however, comes from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of the signed payload [2](#0-1) . This breaks the identity binding `HMAC-verified bytes == data acted upon`, since the tenant identity (`shop`) that flows into `WebhookMetadata` is never bound to the same bytes that were HMAC-verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Request#shop` is read directly from the `shopify-shop-domain` header without any cryptographic binding to the body/HMAC: [4](#0-3) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it against `request.hmac`, so it never validates that the claimed `shop` header actually corresponds to the shop that generated the signed body: [5](#0-4) 

`Registry.process` performs this HMAC check and then immediately forwards the unauthenticated `request.shop` into `WebhookMetadata`, which is the tenant-identifying field passed to the app's `WebhookHandler#handle`: [6](#0-5) [7](#0-6) 

Because the `api_secret_key` used to compute the HMAC is a single app-level secret shared across every shop that has the app installed (not shop-specific), any body+HMAC pair the attacker can legitimately obtain (e.g., by installing their own shop and receiving a genuine webhook) remains a valid HMAC regardless of which `shop` header accompanies it. An attacker who owns/controls one shop with the app installed can capture one legitimate webhook delivery (body + `x-shopify-hmac-sha256`), then POST the identical `raw_body`/`hmac` pair to the same webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only checks the body signature, and `Registry.process` will call the handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`, causing the host application to attribute the attacker's payload/event to the victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged internet user (who only needs to install the target app on a shop they control — no privileged credentials, no access token, no leaked secrets) can make the gem report an event as belonging to an arbitrary victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select which tenant's session/data to update, mark uninstalled, trigger data deletion/redaction for GDPR mandatory topics, etc.), this can result in cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since the vulnerability lets an attacker's request be authenticated as originating from a different tenant.

### Likelihood Explanation
Likelihood is Medium-High: any developer/attacker can freely create a Shopify development store and install any public app that has webhooks configured, which is enough to legitimately receive one signed webhook body/HMAC pair. Replaying that pair with a modified `shop` header against the app's public webhook endpoint requires no special access — just a normal HTTP POST. The only constraint is that the attacker cannot choose the webhook's `body` content (it is whatever event fires on their own shop), but for topics such as `app/uninstalled`, `shop/update`, or mandatory compliance topics, this is often enough to trigger meaningful tenant-scoped side effects in the host application when it trusts `WebhookMetadata#shop`.

### Recommendation
- Short term: Bind the `shop` domain (and ideally `topic`/`webhook_id`) into the HMAC-signed payload, or independently verify that the claimed `shop` header matches a shop known to have a webhook subscription matching the delivered `webhook_id`/topic before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must not be used as a sole tenant-selection key without additional verification (e.g., cross-checking against the app's own webhook subscription records or session store for that shop).
- Long term: Extend `Utils::VerifiableQuery`/`HmacValidator` so all identity-relevant fields used downstream by host applications (shop domain, topic) are included in `to_signable_string`, ensuring the authenticated bytes and the bytes acted upon are provably the same.

### Proof of Concept
1. Attacker creates a Shopify development store and installs the target app (a normal, unprivileged action).
2. The app receives a genuine webhook delivery for the attacker's own shop, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {}
   ```
3. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the same webhook endpoint, but changes only the shop header:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same-valid-hmac-of-body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {}
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and finds it valid (matching step 2's genuine signature) [1](#0-0) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [8](#0-7) , causing the host application to process an `app/uninstalled` (or other) event as if it came from the victim shop, despite the victim never having triggered or authorized it.
