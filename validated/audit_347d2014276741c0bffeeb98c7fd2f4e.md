## Finding

### Title
`SignerCapabilityOfferProofChallengeV2` omits chain-id domain separation, enabling cross-network replay of signer-capability delegation - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The external report's root cause is a signed authorization message that (1) embeds a mutable, externally-influenced value at signing time and (2) lacks chain/expiration binding, allowing signatures to be replayed outside their intended context. Aptos' `account.move` fixed exactly this class of bug for `RotationCapabilityOfferProofChallengeV2` by adding a `chain_id` field, but the sibling struct `SignerCapabilityOfferProofChallengeV2` — used to authorize delegation of an account's `SignerCapability` (full programmatic control over the account) — was never given the same treatment and still lacks `chain_id`.

### Finding Description
`account.move` defines two "V2" proof-challenge structs used to safely delegate account capabilities via an out-of-band signature (to defend against TOCTOU-style attacks, per the code comments): [1](#0-0) 

`RotationCapabilityOfferProofChallengeV2` explicitly documents and includes `chain_id` "which prevents replaying the challenge message" across networks, but `SignerCapabilityOfferProofChallengeV2` has no `chain_id` field — only `sequence_number`, `source_address`, and `recipient_address`.

`offer_signer_capability` builds this challenge purely from on-chain state and verifies the caller-supplied signature against it: [2](#0-1) 

The signature is checked via `verify_signed_message`, which BCS-encodes the message together with its Move `TypeInfo` (module address/name/struct name) before verification: [3](#0-2) [4](#0-3) 

Because `0x1::account::SignerCapabilityOfferProofChallengeV2` is the same fully-qualified type on every Aptos-based chain (module address `0x1` is identical across networks), the `TypeInfo` wrapper provides no cross-chain domain separation. The only per-account binding is `sequence_number`, `source_address`, and `recipient_address` — none of which differ between chains that share the same account-derivation/address space (e.g., testnet vs. mainnet, or any Aptos fork/devnet using the same genesis-derived addressing). This mirrors precisely the gap the external report flags: a signed authorization "can be reused for a rollup that follows the same message format and is signed by the same user" when chain id is omitted from the signed payload — except here the analog is Aptos-native chains rather than L1/L2 rollups, and the delegated authority is `SignerCapability`, which lets its holder call `create_signer_with_capability` and fully impersonate the account, including moving all APT/fungible assets it holds.

By contrast, `multisig_account::MultisigAccountCreationMessage` (used for an analogous "authorize on my behalf" flow) does include `chain_id`, confirming the framework authors are aware of this exact class of risk but did not apply the fix uniformly: [5](#0-4) 

### Impact Explanation
`SignerCapability` grants the holder the ability to generate a `signer` for the offering account at will via `create_signer_with_capability`, which is full custody over that account's resources — APT, fungible assets, object ownership, everything the account controls. A replayed `offer_signer_capability` signature from one Aptos network onto another lets an attacker (or an unintended party) obtain this capability on the victim's account on the second network without the victim's consent for that specific network, resulting in unauthorized takeover of the account and everything it holds. This satisfies the custody gate ("unauthorized takeover of ... resource-account control ... tied to live assets").

### Likelihood Explanation
Exploitation requires: (a) the same account address/private key pair to exist and hold a live-network account with a matching `sequence_number` on two Aptos-based networks (realistic since users/wallets frequently reuse keys across mainnet/testnet/devnet, and fresh accounts commonly sit at `sequence_number = 0` for a long time), and (b) the same `recipient_address` existing on both. This is a plausible but not universal scenario — it depends on cross-network key/address reuse and matching state, so likelihood is moderate rather than trivially guaranteed, but the missing domain separator is an unambiguous, unprivileged root cause with no mitigating check anywhere in the call path.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`), populate it with `chain_id::get()` in `offer_signer_capability`, and bump to a `V3` struct with a proper migration/deprecation path for the old `V2` verification code. Consider also adding an expiration mechanism for offer-style proofs, consistent with the report's broader recommendation.

### Proof of Concept
1. On Chain A (e.g., testnet), Alice's account exists at address `A` with `sequence_number = 0`.
2. Alice signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: A, recipient_address: R }` off-chain (e.g., as part of some dApp onboarding flow that requests delegation to a fixed service address `R`), as shown in the existing test harness pattern: [6](#0-5) 
3. Because the struct has no `chain_id`, the exact same signature bytes are valid on Chain B (e.g., mainnet or another Aptos-derived network) if Alice's account also exists at address `A` with `sequence_number = 0` there, and `R` also exists.
4. Anyone submits `offer_signer_capability(account=A's own txn only... )` — note the caller must literally be `A`'s transaction; however, if `R` (or anyone who obtains the leaked/observed signature) can convince/trick account `A` to co-submit, or if the flow is embedded in tooling that resubmits the same pre-signed payload across networks (a common integration mistake), the call on Chain B succeeds using the Chain-A-signed bytes, granting `R` `SignerCapability` over Alice's Chain B account and all its assets, without Alice ever intending to authorize delegation on Chain B.     public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
