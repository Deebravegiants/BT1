### Title
Unchecked ERC20 boolean return in `IntentGatewayV2.withdraw()` and `SweepDust` allows silent transfer failures to permanently lock/lose escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` handler on the Tron variant of `IntentGatewayV2` release escrowed tokens using a raw low-level `.call` to the ERC20 `transfer` function, but only check that the call did not revert. They never decode and validate the boolean return value that `transfer()` is supposed to return. Any ERC20 that returns `false` on failure instead of reverting (a well-known non-standard-but-valid ERC20 behavior) will make the gateway believe the transfer succeeded, while escrow accounting is already decremented and the order marked filled.

### Finding Description
`withdraw()` iterates over the escrowed tokens for an order and pays out the beneficiary: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
    ...
}
```

`success` here only reflects whether the low-level call reverted, not whether the ERC20 `transfer()` returned `true`. Standard-but-non-compliant tokens (e.g., ones that return `false` when the transfer cannot be completed, or tokens with blacklist/pause logic implemented as a `return false` rather than a `revert`) will make `success == true` while no tokens actually move. Because the return data is discarded and never `abi.decode`d, the code proceeds to:
- Mark the order as filled/refunded via `_filled[body.commitment] = beneficiary` (already set before the transfer even executes), preventing retries or alternate resolution.
- Decrement `_orders[body.commitment][token] -= amount`, permanently zeroing the escrow record for those funds.

The same unchecked pattern for `SweepDust` exists in the `onAccept` handler: [2](#0-1) 

Both call sites use `SafeERC20`'s import (`using SafeERC20 for IERC20;` for other paths) but bypass it here in favor of raw `.call`, unlike the equivalent escrow-side `safeTransferFrom` calls used earlier in `placeOrder`, which do enforce return-value correctness via OpenZeppelin's `SafeERC20`.

### Impact Explanation
`withdraw()` is reached via `onAccept`, i.e., processing of a relayed ISMP POST request delivering a `WithdrawalRequest` for order fulfillment/refund — a path directly reachable by any relayer submitting a validly-proven cross-chain message, requiring no special privilege beyond normal message relaying. If the token used for escrow is one of the many real-world ERC20 tokens that return `false` instead of reverting on failed transfers, or if a transfer edge case (e.g., blacklist enforcement, paused state) causes such behavior, the gateway permanently records the order as filled and decrements the escrow ledger without delivering the tokens to the beneficiary. This is an unrecoverable loss of the escrowed user/solver funds, since `_filled` blocks any future settlement attempt for that commitment and the internal accounting no longer reflects the outstanding balance for recovery.

### Likelihood Explanation
Likelihood is contingent on the escrowed token's ERC20 implementation returning `false` rather than reverting under some condition (well documented class of tokens, e.g. old USDT-style tokens for approve, and various tokens with blacklist/pause features that return `false`). Since `IntentGatewayV2` accepts arbitrary caller-specified ERC20 tokens as `order.inputs`/`order.output.assets` (no allowlist enforcement visible in the reviewed excerpt), an attacker or unlucky solver can construct or select an order using such a token to trigger silent failure, or the condition can arise organically for popular non-standard tokens.

### Recommendation
Replace the raw `token.call(...)` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` usage already used elsewhere in the same contract (e.g., in `placeOrder`):

```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```

This reverts on both a reverted call and a `false` boolean return, ensuring `_filled`/`_orders` state updates only occur after tokens are verifiably moved. Apply the same fix to the `SweepDust` handler and the fee-transfer path near line 720 of the same file.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer()` implementation returns `false` under some condition instead of reverting (e.g., a blacklist-gated token where the beneficiary is blacklisted, or a token paused mid-flight).
2. A user places an order via `placeOrder` escrowing this token; `_orders[commitment][token]` is credited.
3. A relayer submits a valid ISMP POST carrying a `WithdrawalRequest` for this commitment/beneficiary, invoked through `onAccept` → `withdraw()`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` succeeds at the EVM call level (`success == true`) but the token's internal logic returns `false` and never moves the balance.
5. `_filled[body.commitment] = beneficiary` remains set and `_orders[body.commitment][token] -= amount` executes, permanently closing out the order while the beneficiary's token balance is unchanged — funds are lost/locked in the gateway with no path to reclaim them.
