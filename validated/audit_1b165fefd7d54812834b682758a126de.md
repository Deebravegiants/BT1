### Title
Webhook `X-Shopify-Shop-Domain` header (and `topic`/`api-version`/`webhook-id`) is trusted despite not being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` uses `request.shop` (derived from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) to build the `WebhookMetadata` handed to the app's webhook handler. The shop identity that the handler acts on is never bound by the HMAC that `Utils::HmacValidator.validate` checks.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is "the HMAC covers `to_signable_string`." For webhooks this is defined as: [1](#0-0) 
i.e. only `@raw_body` is signed. The `shop` accessor, however, is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (along with `topic`, `api_version`, `webhook_id`, none of which are signed either) to build the metadata passed to the app's handler: [3](#0-2) 

The documented usage pattern shows apps using `data.shop` directly as the tenant key to route/store the webhook payload (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [4](#0-3) 

The binding that should hold is:
`HMAC-verified-bytes == bytes that determine tenant (shop) attribution`

but the actual state is:
`HMAC-verified-bytes (raw_body only) != bytes used to select the shop (shop-domain header, unauthenticated)`

Because `OpenSSL::HMAC.hexdigest` is computed over `@raw_body` alone (see `HmacValidator#compute_signature`), any request with a *body* that Shopify has genuinely signed for the app's `client_secret` remains valid no matter what shop-domain header is attached to it. [5](#0-4) 

### Impact Explanation
This breaks the tenant-identity binding at the core of multi-tenant webhook processing: an unprivileged attacker who can obtain one legitimately-signed webhook body/HMAC pair for their own store (trivial for any public app — install it on a free development store and capture a real webhook delivery) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain. `Registry.process` will accept the HMAC as valid and dispatch `handler.handle` with `WebhookMetadata#shop` set to the attacker-chosen value, causing the host application to persist/act on webhook data under the wrong tenant. This is a cross-tenant integrity/confidentiality violation of exactly the kind called out as in-scope Critical impact ("cross-tenant access"), reachable entirely through this gem's own `Webhooks::Request`/`Webhooks::Registry` code, with no need for the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Likelihood is fairly high for any app that: (a) is a public app that can be installed by arbitrary shops (so an attacker can get one authentic signed payload/body pair from their own store), and (b) whose webhook handler uses `data.shop` (as demonstrated in the gem's own docs) to attribute the incoming payload to a tenant record, without independently re-deriving/cross-checking the shop from a trusted source (e.g. looking the webhook up by `webhook_id` registered per-shop). The gem provides no protection or warning that `shop`/`topic`/`api_version`/`webhook_id` are unauthenticated, and its own documentation encourages using `data.shop` directly.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the HMAC-signable string for `ShopifyAPI::Webhooks::Request`, or otherwise cryptographically bind them, e.g.:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{topic}\n#{api_version}\n#{webhook_id}\n#{@raw_body}"
end
```
This requires computing the HMAC server-side to match, which isn't compatible with Shopify's actual webhook HMAC scheme (Shopify only signs the raw body). Since the signature scheme itself cannot be changed unilaterally by this gem, the safer fix is to make the trust boundary explicit: document prominently (and/or raise/warn) that `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are **not** covered by the HMAC and must not be used as the sole tenant key — apps must instead correlate the delivery to the shop registered for `webhook_id`, or otherwise independently verify the shop out-of-band before acting on `data.shop`.

### Proof of Concept
1. Attacker (unprivileged) installs the target public app on their own low-value development shop `attacker.myshopify.com`, and triggers a webhook delivery (e.g. `orders/create`), capturing the exact `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` header — both are legitimately produced by Shopify using the app's real `client_secret`, but the attacker never needs to know the secret itself.
2. Attacker replays a POST to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a topic/webhook-id of their choosing).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` == `@raw_body` only — unchanged from step 1 — so validation succeeds: [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop` header, and invokes `handler.handle(data: ...)`: [7](#0-6) 
5. The host application's handler (per the gem's documented pattern) stores/dispatches the attacker's own webhook payload under `victim.myshopify.com`'s tenant context, achieving cross-tenant data injection/confusion.
