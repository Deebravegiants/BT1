The docs explicitly claim `Registry.process` "will verify the request did indeed come from Shopify" — but the HMAC verification (`lib/shopify_api/utils/hmac_validator.rb`) only signs `request.to_signable_string`, which for `ShopifyAPI::Webhooks::Request` returns the raw body only, not the `shop`, `topic`, `webhook_id`, or `api_version` headers. This confirms the identity-binding gap.

### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are trusted from unauthenticated headers while only the body is HMAC-verified - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` extracts and passes straight to the app's handler are read from HTTP headers and are never part of the signed material [2](#0-1) .

### Finding Description
`Registry.process` raises `InvalidWebhookError` unless `HmacValidator.validate(request)` succeeds, then immediately trusts `request.topic`, `request.shop`, and `request.webhook_id` to build `WebhookMetadata` for the handler [3](#0-2) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [4](#0-3) . Because `to_signable_string` for a webhook `Request` is only the raw body, the equality actually being enforced is:

`HMAC(secret, raw_body) == received_hmac`

not

`HMAC(secret, raw_body ++ shop ++ topic ++ webhook_id) == received_hmac`

The identity binding the app relies on — "the `shop` attached to this event is the shop that Shopify authenticated the delivery for" — is never checked. The `api_secret_key` used to sign webhooks is a single per-app secret shared across every shop that has the app installed, not a per-shop secret. Consequently, any of the app's own installed shops (an "unprivileged internet user" with respect to other tenants — they only need to install the app on their own store, no special credentials, no access token) can capture one of their own genuinely-signed webhook deliveries and resubmit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to a victim shop. The HMAC still validates because it only covers the untouched raw body, letting the forged request masquerade as an event for a different tenant.

The gem's own documentation reinforces that callers rely on `Registry.process` for full authentication of the request: "This will verify the request did indeed come from Shopify" [5](#0-4) , yet the header fields consumed by the handler are excluded from that verification.

### Impact Explanation
This breaks the identity binding `shop-header == shop-that-was-actually-signed-for`, allowing cross-tenant data injection/confusion: a handler that uses `data.shop` to decide which tenant's stored session/state to act on (exactly as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` in `docs/usage/webhooks.md`) can be made to apply attacker-supplied body content under a victim shop's identity, or to process/replay events tagged with a forged `webhook_id`/`topic` to bypass idempotency/duplicate-detection logic. This matches the Critical "cross-tenant access" impact category, since it lets one tenant's authenticated channel be used to inject data attributed to another tenant.

### Likelihood Explanation
Any shop that can install the app (no special access token, no privileged account, no secret knowledge needed) can obtain a validly-signed webhook body/HMAC pair for arbitrary topics/content they can trigger on their own store (e.g. `orders/create` with attacker-chosen order fields), then simply replay that exact body+HMAC pair to the shared webhook endpoint with a modified `shop-domain` header. No cryptographic break is required — the signature check is satisfied by construction because it never covered the header fields being trusted downstream.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie the `shop`/`topic`/`webhook_id` to the verified payload before trusting them: e.g., look up the expected shop for the webhook subscription (via the app's own stored session/webhook registration state, not the header) rather than trusting `request.shop` directly, or require out-of-band verification (e.g., cross-check `webhook_id` against Shopify's Admin API for the claimed shop) before acting on tenant-identifying fields extracted from unauthenticated headers.

### Proof of Concept
1. App has topic `orders/create` registered via `Registry.add_registration`, handler stores data keyed by `data.shop`.
2. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers an `orders/create` event, capturing the genuine webhook POST: raw body `B`, header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the identical body `B` and identical `X-Shopify-Hmac-Sha256: H` to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `HmacValidator.validate` recomputes `HMAC(secret, B)` (per `to_signable_string` returning only `@raw_body`) and it matches `H`, so validation passes [1](#0-0) .
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"` even though Shopify never signed anything for `victim.myshopify.com` [3](#0-2) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
