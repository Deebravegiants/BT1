### Title
`liquidate` accepts a debt repayment while returning zero seized collateral - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
The liquidation path validates that the liquidator supplied a nonempty debt-payment list and that the normalized repayment remains nonempty, but it does not validate that the resulting seizure list is nonempty. Consequently, an unprivileged caller can transfer debt tokens to the pool and burn part or all of an unhealthy account’s debt while receiving no underlying collateral in `SeizeMode::Transfer` or no supply shares in `SeizeMode::Credit`.

### Finding Description
The public liquidation flow calls `process_liquidation`, which authenticates only the liquidator and accepts a `Vec<HubPayment>` plus a `SeizeMode`. It rejects an empty input payment vector, builds the liquidation plan, rejects an empty normalized repayment vector, and then unconditionally performs the repayment transfer through `apply_liquidation_repayments` before applying `seized`. [1](#0-0) [2](#0-1) 

`apply_liquidation_repayments` performs a measured token transfer from `liquidator` to the pool for each planned repayment leg and pushes the corresponding pool repayment action. [3](#0-2) 

The seizure calculation can legitimately produce an empty vector. In particular, `calculate_seized_collateral` immediately returns an empty `seized` vector when total collateral is zero, and later drops any leg whose RAY seizure, scaled seizure, or token-unit seizure rounds to zero. [4](#0-3) [5](#0-4) [6](#0-5) 

`LiquidationPlan::validate` checks positivity only for seizure entries that are present; it has no `!seized.is_empty()` requirement. `process_liquidation` therefore proceeds from a nonempty repayment to an empty seizure list, iterating over no seizure legs while retaining the completed repayment. [7](#0-6) [8](#0-7) 

### Impact Explanation
A liquidator can permanently lose the entire debt-token amount delivered to the pool and receive no asset or supply-share consideration. The borrower’s debt is nevertheless reduced because repayment actions are applied before the empty seizure loop executes.

This is directly analogous to paying an auction price while receiving no assets: the settlement checks validate the payment side but fail to require a nonzero consideration side.

### Likelihood Explanation
An unprivileged liquidator can reach this path by calling `liquidate` on an unhealthy account whose collateral produces no executable seizure leg. The simplest reachable state is an account with residual debt and zero valued collateral; the planner accepts a positive payment for an existing debt position, while `calculate_seized_collateral` returns empty when `total_collateral <= 0`.

A related low-decimal rounding case can drop every leg below one token unit, although configurations that admit extremely valuable low-unit collateral may additionally require governance listing assumptions and should not be needed for the base scenario.

### Recommendation
After `build_liquidation_plan` and receipt-scaling, require `seized` to contain at least one positive, executable consideration leg before pulling repayment. Alternatively, pull repayments only after settlement has confirmed nonzero seizure value, so an empty consideration list reverts atomically rather than retaining the transfer.

At minimum:

- reject `result.seized.is_empty()` before `apply_liquidation_repayments`;
- recheck `scale_seizures_to_received` output for a positive executable leg before applying repayment;
- make the estimate invariant explicit by rejecting estimates whose `seized_collaterals` list is empty;
- add regression coverage for zero-collateral debt and all-legs-rounded-to-zero liquidation.

### Proof of Concept
1. Create or identify account `A` with an existing debt position and no effective collateral.
2. Ensure `A` has `health_factor < Wad::ONE`, which follows from positive debt and zero total collateral.
3. As liquidator `L`, call `Controller::liquidate` with:
   - `account_id = A`
   - `debt_payments = [((hub_id, debt_asset), positive_amount)]`
   - `seize_mode = SeizeMode::Transfer`
4. `require_non_empty_payments` passes because the input payment vector is nonempty.
5. `calculate_repayment_amounts` accepts the positive leg because it references an existing debt position.
6. `calculate_seized_collateral` returns an empty vector when total collateral is zero.
7. `LiquidationPlan::validate` succeeds because it validates only entries inside the empty vector.
8. `require_non_empty_payments(&result.repaid)` succeeds because repayment remains nonempty.
9. `apply_liquidation_repayments` transfers `positive_amount` from `L` to the pool and applies the debt repayment.
10. Both seizure branches iterate over the empty `seized` vector, so `L` receives neither underlying collateral nor credited shares while the payment remains applied.

    /// Validates repayment totals and both seizure representations: positive
    /// amounts, fees bounded by gross seizure, bonus shares bounded by seized
    /// shares, and fee rates below 100%. Credit splits are checked at each use.
    pub(crate) fn validate(&self, env: &Env) {
        self.repayment.validate(env);

        for entry in self.seized.iter() {
            if entry.amount <= 0 || entry.protocol_fee < 0 || entry.protocol_fee > entry.amount {
