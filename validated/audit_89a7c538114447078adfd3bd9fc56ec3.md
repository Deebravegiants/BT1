This confirms the vulnerability: `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never included in the HMAC-signed content [2](#0-1) . `HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header [3](#0-2) . `Registry.process` then trusts `request.shop` (and other headers) to build `WebhookMetadata` passed to the app's handler without any additional binding check [4](#0-3) .

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, but exposes `shop`, `topic`, `webhook_id`, and `api_version` as separate accessors sourced from unauthenticated HTTP headers. `Utils::HmacValidator.validate` verifies only that the body matches the signature computed with the app's `api_secret_key`; it never binds the `shop-domain` header (or any other header) to that signature. Because the same `api_secret_key` is shared across every shop that installs the app, anyone who owns a shop that installs the app receives genuine, validly-signed webhook deliveries for their own store. They can then replay that exact `(raw_body, hmac-sha256)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` dispatches the forged request to the merchant's webhook handler as `WebhookMetadata` claiming it originated from the victim shop.

### Finding Description
The identity binding that should hold is: `shop_header == shop_that_signed(raw_body)`. In reality, the HMAC only authenticates `raw_body` (via `to_signable_string`) [1](#0-0) , while `shop`, `topic`, and `webhook_id` are parsed straight from caller-supplied headers with no cryptographic tie to the signature [2](#0-1) . `HmacValidator.validate_signature` compares only `verifiable_query.to_signable_string` against the received HMAC [3](#0-2) , so the header fields can be freely altered post-signing without invalidating the HMAC check. `Registry.process` then uses these unverified header values directly to identify the tenant for the webhook handler [4](#0-3) .

Before the attack: `request.shop` (legit) == the shop that actually owns the signed body.
After the attacker's request sequence (same `raw_body`/`hmac-sha256`, altered `x-shopify-shop-domain`): `request.shop` (victim, attacker-chosen) != the shop that produced the signed body (attacker's own shop) — yet `HmacValidator.validate` still returns `true`, and the equality the app relies on is broken.

### Impact Explanation
This crosses a tenant boundary (Critical: cross-tenant access). An app that keys any state, authorization decision, deduplication, or data write off `WebhookMetadata#shop`/`webhook_id` (as the shipped `Registry.process` does by construction [5](#0-4) ) can be made to process attacker-controlled body content while it is mislabeled as belonging to a shop the attacker does not own, since Shopify's HMAC signing secret is the same app-wide `api_secret_key` for all installs.

### Likelihood Explanation
Any unprivileged internet user who installs the target app on their own (attacker-controlled) development/free shop automatically receives real webhook deliveries signed with the app's shared secret for events they trigger themselves (e.g., `app/uninstalled`, `products/create`). No special access, leaked secret, or privileged account is required — only a normal app install, which is the standard, low-barrier way any user can interact with a public/embedded app.

### Recommendation
Include the tenant-identifying headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signable content, or otherwise cryptographically bind them to the signature, matching Shopify's own webhook signing guarantee. If header values must remain outside the signed payload, the gem should document/require that consumers not trust `WebhookMetadata#shop` for authorization decisions without independently confirming the shop against their own installed-shop store, and this library should not present `shop` as if it were validated by `HmacValidator.validate`.

### Proof of Concept
1. Attacker creates a shop and installs the merchant app that uses this gem.
2. Shopify sends the attacker a legitimately signed webhook, e.g. `POST /webhooks` with body `{"id": 1}}`, headers `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the same endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object where `shop` returns `"victim-shop.myshopify.com"` [6](#0-5) .
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives the HMAC from `raw_body` [7](#0-6) .
6. The app's handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and processes attacker-controlled data attributed to the victim tenant [5](#0-4) .
