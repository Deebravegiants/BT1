### Title
Crafted swap route hides a wallet-draining token transfer under the caller's signed authorization tree on controller strategy verbs - (File: contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2023-4901 is a security-UI spoofing bug: a crafted HTML page makes a dangerous browser prompt look trustworthy. The on-chain analog in XOXNO Lending is the router strategy path: `swap_tokens` grants the router one exact input transfer, but the router then executes an attacker-constructed route whose venue contracts run beneath the caller's `require_auth` tree. Any code on that stack can issue `token.transfer(victim, attacker, x)` for any token the victim holds, and Soroban records it as a child of the caller's single authorization entry. The wallet signature screen then presents one legitimate-looking `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` call, while the signed tree silently carries a transfer that drains an unrelated wallet token — the same "dangerous action disguised as a safe prompt" shape as the CVE.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` does three things: it authorizes exactly one `token_in` transfer to the configured router (`authorize_transfer_as_current`, line 34), calls `router.execute_strategy(controller, amount_in, swap)` under the flash guard (line 37), then validates only the controller's input/output balance deltas (lines 41-54). The `swap` payload names arbitrary pool/venue addresses; the router keeps no venue allowlist (documented in `docs/explanation/threat-model.md:154-165`), so a route can place attacker-deployed code on the call stack *below the caller's root `require_auth`*.

Under Soroban authorization semantics, a `from.require_auth()` issued by any contract deeper in that stack resolves against the caller's root auth entry and is recorded as a sub-invocation of it. `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates this end to end: `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 194-227) shows simulation returning Alice's auth tree with the rogue `transfer(Alice → attacker, WALLET_BALANCE)` attached as a child of her `swap_collateral` entry, and her wallet token balance going to zero while the swap itself pays out correctly (`FAIR_OUT_ETH` delivered, line 226). `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 229-269) shows the host refuses the transfer only if the signed tree omits it — but an honest simulation presents it as part of Alice's own authorization, so a client that signs the simulated tree authorizes the theft. The same exposure exists on every route-taking entrypoint (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`) and on the router's direct `execute_strategy` (threat-model lines 160-165).

### Impact Explanation
Theft of user funds. The stolen amount is the victim's *wallet* balance of any arbitrary token — completely unbounded by the routed amount, the payload minimum, or the post-swap account risk gates, which all pass because the swap itself settles honestly (test line 226 confirms a fair output lands as collateral). An attacker loses nothing: they only need to publish or serve a poisoned route to a victim. This matches the CVE's `UI:R` shape — victim interaction (signing) is required — but the signed UI cannot distinguish the malicious child from the protocol's legitimate one-transfer child without decoding the full route.

### Likelihood Explanation
Reachable by a single unprivileged address: the attacker deploys a rogue "pool" contract that calls `token.transfer(victim, attacker, x)` and embeds it in the `swap_xdr`/route payload served to the victim (e.g., via a quote API or phishing frontend) — no privileged role needed, since the router executes payload-named venues and the victim supplies the signature. Exploitation requires the victim's wallet/client to sign the simulation-produced auth tree without rejecting the extra child; the protocol's own guidance (`skills/xoxno-swap-aggregator/payload.md`, threat-model line 162) acknowledges clients must decode the route and refuse unexpected children, meaning the defense is entirely client-side and the default sign-the-simulation flow authorizes the theft. Medium severity aligns with the CVE's medium rating: user interaction required, bounded by one user's wallet, no protocol insolvency.

### Recommendation
Add a server-side invariant instead of relying on client decoding. Options: (a) have the router record the set of token `transfer` authorizations it legitimately triggers and enforce that no address other than the router/pool contracts issues a `require_auth` during route execution — e.g., wrap hop dispatch so that any sub-invocation authorized against the `sender` beyond the declared hop pull fails; (b) maintain a venue/pool allowlist for strategy routes (mirroring the Blend approval list, INV-STRAT-03) so only reviewed contracts can sit under the caller's auth tree; (c) at minimum, emit events and document a machine-checkable auth-tree shape so wallets can mechanically reject any `swap_collateral`/`multiply`/`execute_strategy` signature whose auth tree contains children not strictly required by the declared route legs.

### Proof of Concept
The repository ships the working exploit as a test. In `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. `Scene::new` (lines 82-109) gives Alice 10 000 USDC supplied plus `WALLET_BALANCE` of an unlisted token, and registers `RogueHopPool` — an attacker contract whose `swap()` performs `token.transfer(alice, attacker, WALLET_BALANCE)` (lines 62-71).
2. `route_through_pool_stealing` (lines 111-125) encodes a route through that pool into the `swap` bytes passed to `swap_collateral`.
3. Line 194 test: after simulation and execution, `recorded` shows Alice's single auth entry for `controller.swap_collateral` carrying the stolen `transfer` as its only sub-invocation (lines 206-222); `s.wallet(&alice) == 0` and `s.wallet(&attacker) == WALLET_BALANCE` (lines 224-225), while the swap itself settled correctly (`FAIR_OUT_ETH` collateral, line 226).
4. Line 229 test: signing the simulation-returned tree in enforcing mode executes the drain (`expect` succeeds, lines 259-268); signing an honest root-only tree makes the whole call fail with a host auth error and rolls back the swap (lines 243-256) — proving the theft rides inside the caller's own signature, exactly the spoofed-security-UI class of CVE-2023-4901.

Caveat: this behavior is documented as a residual risk in `docs/explanation/threat-model.md:154-165`, so a reviewer could classify it as an accepted design boundary; however it is a genuine, in-scope theft-of-funds path that no on-chain check bounds, which is why it is reported rather than dismissed.
