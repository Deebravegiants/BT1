### Title
Caller-controlled route payload invokes arbitrary pool/token contract code under the caller's authorization, enabling wallet-draining transfers below a signed `swap_collateral`/`execute_strategy` auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The Roundcube bug class is "attacker-supplied identifier resolves to code the application loads and runs" (plugin-name path traversal → LFI/RCE). In XOXNO Lending, the analog is the route payload: a swap's `swap`/`swap_xdr` bytes name pool and token addresses by registry index, and neither the controller nor the router validates those addresses against any allowlist or interface check before invoking them. A route can therefore name an attacker-deployed contract, which then executes arbitrary calls — including `token.transfer(victim, attacker, amount)` on unrelated tokens — underneath the caller's `require_auth` invocation. Soroban records that nested transfer as a child of the caller's auth entry, so the standard simulate-then-sign flow produces a signed tree that authorizes the theft.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-38` authorizes exactly one input transfer to the configured router and then calls `router.execute_strategy(controller, amount_in, swap)`, forwarding the raw caller-supplied `swap` bytes. On the router side, `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:34-40` selects a venue adapter purely by opcode and invokes whichever `pool`/`token` addresses the payload's `assets` registry names — there is no venue allowlist, pool-registry check, or contract-interface verification. The packed-program decoder (`Program::decode`) checks only structural properties: index bounds, token ordering, opcode range, split weights (see `skills/xoxno-swap-aggregator/payload.md:40-88`). The threat model itself states: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization … The loss is then the caller's wallet" (`docs/explanation/threat-model.md:154-165`).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the mechanics end to end: `RogueHopPool::swap` (lines 62-71) calls `token::transfer(alice, attacker, WALLET_BALANCE)` on a token the protocol never listed; simulation records that transfer as a child of Alice's `swap_collateral` auth entry (lines 195-227); and enforcing mode executes it once the signed tree contains it (lines 259-268).

### Impact Explanation
Theft of user funds beyond the routed amount. Neither the payload `min_out`, the controller's `RouterOverspend`/`NoSwapOutput` measurements (`swap.rs:42-54`, `75-84`), nor the final account health check bound the loss, because the rogue transfer moves tokens that never touch the swap accounting — the victim's entire balance of any token the attacker chooses can be drained in the same transaction that still delivers a "fair" swap output. Affected entrypoints: `execute_strategy` on the router directly, and every controller strategy that forwards caller-supplied route bytes: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`.

### Likelihood Explanation
Likelihood is constrained but real. The attacker cannot inject a route into a victim's call — the victim supplies `swap_xdr` — so exploitation requires the victim to consume an attacker-influenced route (malicious quote source, phishing route, or any third party that builds `routeXdr` on the user's behalf). However, the dangerous step is invisible to normal signing flow: `simulateTransaction` runs recording mode, attaches the rogue `transfer` as a child of the caller's entry, and the wallet signs the returned tree verbatim. Nothing in the transaction preview distinguishes the poisoned child from the honest single input transfer, so a victim who signs simulated auth (the standard flow) is fully exposed. Severity: High (Critical-class impact, but requires route-supply-chain access to the victim rather than pure on-chain reachability).

### Recommendation
- Maintain an on-chain venue/pool allowlist (or per-venue pool registry) and have `dispatch_hop` reject any `hop.pool`/`token` address not registered for that opcode.
- Alternatively, execute each hop through a fixed venue-adapter trampoline that constrains the callee's interface, and reject auth-recording of nested invocations that are not the single authorized `token_in.transfer`.
- Until fixed, clients must decode `swap_xdr` and refuse to sign any auth tree containing children other than the expected input transfer — this is already documented as mandatory client behavior in the threat model.

### Proof of Concept
1. Attacker deploys `RogueHopPool` (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:51-72`), whose `swap` calls `token::transfer(victim, attacker, wallet_balance)` on an arbitrary token held by the victim.
2. Attacker serves the victim a route whose `assets` registry places the rogue pool at the hop's `idx_a` and encodes opcode `Aquarius` (or any venue) with a fair `min_out`.
3. Victim calls `controller.swap_collateral(account, token_in, amount, token_out, route)` (or `router.execute_strategy` directly). `swap_tokens` authorizes the input transfer and forwards the route (`swap.rs:34-38`); `dispatch_hop` invokes the attacker's contract address (`venues/mod.rs:34-40`).
4. Simulation records the rogue `transfer` under the victim's `swap_collateral` entry; the victim signs that tree; the host accepts it.
5. Result (asserted by the test): victim's wallet token balance goes to 0, attacker receives `WALLET_BALANCE`, and the victim still receives the fair swap output — the theft is undetectable by `RouterOverspend`, `NoSwapOutput`, `min_out`, or the final health-factor check.
