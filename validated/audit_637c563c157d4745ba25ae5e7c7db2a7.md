## Title
Webhook Shop and Topic Identity Not Bound to HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop` and `topic` values taken from unauthenticated HTTP headers to route and label the event. Because the app's `api_secret_key` used to compute the HMAC is a single, app-wide secret shared by every shop that has installed the app (not per-tenant), any merchant who has installed the app can capture one of their own legitimately-signed webhook deliveries and replay the exact `(raw_body, hmac)` pair while substituting a different `shopify-shop-domain` (and/or `shopify-topic`) header. The signature still validates — because it only ever covered the body — while the shop identity the handler receives is attacker-controlled. This breaks the equality that should hold: `shop_verified_by_hmac == shop_delivered_to_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are all read directly from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it to the received `hmac` header, never incorporating `shop` or `topic`: [3](#0-2) 

`Registry.process` validates that HMAC and then immediately trusts the header-derived `request.shop`/`request.topic` to dispatch to the handler: [4](#0-3) 

Because `Context.api_secret_key` is one value shared across all shops that install the app (it is the app's OAuth client secret, not a per-shop value — see its use in `Oauth`, `TokenExchange`, `RefreshToken`, `ClientCredentials`), a valid `(body, hmac)` pair obtained from a webhook delivered to shop A remains valid when replayed with headers claiming it originated from shop B. The gem provides no mechanism (e.g., binding shop/topic into the signed material, or checking `shop` against an expected value/session) to prevent this substitution.

### Impact Explanation
This crosses a tenant boundary: a party who legitimately controls one shop installation (an "unprivileged" actor with respect to any other merchant) can cause the host application to process a webhook labeled as belonging to a different, victim shop while the cryptographic check still reports success. Depending on the topic (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, `customers/data_request`), a forged shop-domain header can trigger cross-tenant side effects such as marking another shop as uninstalled, deleting/redacting another shop's stored data, or corrupting per-shop state — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment relying solely on this gem's `Registry.process`/`HmacValidator` for webhook authentication: any actor who can install the app on at least one shop (which is the normal, unprivileged flow for any merchant) can capture one legitimate `(raw_body, hmac)` pair from their own shop and replay it with a modified `shop-domain`/`topic` header pointed at another shop, since nothing in this gem binds those header values to the signature.

### Recommendation
Bind the tenant/topic identity into the authenticated material or verify it out-of-band: include `shop` and `topic` in the signed string checked against the HMAC (would require Shopify-side signing changes), or, at minimum, have `Registry.process`/`HmacValidator` reject webhooks whose header-derived `shop` does not correspond to a shop currently known to have a valid session/installation in the host app before dispatching to handlers, and document this requirement prominently since the gem cannot enforce it unilaterally from body content alone.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, and receives a legitimate webhook, e.g. `app/uninstalled` with body `{}` and header `x-shopify-hmac-sha256: <H>` computed over `{}` using the shared `api_secret_key`.
2. Attacker resends the exact same raw body `{}` and `x-shopify-hmac-sha256: <H>` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally changes `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `HMAC(api_secret_key, "{}")`, unaffected by the header change: [4](#0-3) 
4. The registered handler is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"`, causing the host app to act as though the event came from the victim shop.

          received_signature = verifiable_query.hmac
