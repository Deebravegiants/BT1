### Title
Withdrawal completion status/tx-hash can be mismatched between concurrent same-asset withdrawals in a single intent - (File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts, packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`waitForWithdrawalCompletion`/`PoaBridge.describeWithdrawal` resolve which POA withdrawal record belongs to which requested withdrawal purely by matching `assetId` (`near_token_id`), never by amount, destination address, or index — the exact same equality gap ("orderId not checked against the specific purchase it belongs to") described in the external report.

### Finding Description
`findMatchingWithdrawal` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (lines 144-153) selects the withdrawal record purely by:
```
withdrawals.find((w) => `nep141:${w.data.near_token_id}` === criteria.assetId)
```
This mirrors `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`), which is explicitly documented and tested to "match by assetId instead of index" (see the test `matches withdrawal by assetId, not by index`, `poa-bridge.test.ts:1054`). Neither function checks the requested `amount` or `destinationAddress`, and the code comment in `waitForWithdrawalCompletion.ts:135-142` self-acknowledges: *"Currently only matches by assetId (near_token_id). This means multiple withdrawals of the same token in a single transaction are not supported."*

The equality that should hold is: **the withdrawal status/tx-hash reported to the caller for withdrawal request N == the actual on-chain settlement corresponding to withdrawal N's amount/destination.** Because matching is collapsed to `assetId` only, if a single intents transaction contains two or more withdrawals of the *same* asset (e.g., two separate NEP-141 `ft_withdraw` legs to different destination addresses, or an amount-split withdrawal), `.find()` returns the *first* array match for all of them. Both callers of `describeWithdrawal`/`waitForWithdrawalCompletion` will then report the same `txHash`/`status` for what may be two distinct on-chain transfers to two distinct destinations — an integrator relying on this event to link on-chain settlement to their internal order records (the exact off-chain reconciliation use case highlighted in the original report) can attribute the wrong destination/amount to the wrong withdrawal.

### Impact Explanation
This falls under the "status or hash misreport making an integrator credit or refund twice" High-impact category. An integrator polling `sdk.waitForWithdrawalCompletion` (`packages/intents-sdk/src/sdk.ts`, via `packages/intents-sdk/src/core/withdrawal-watcher.ts`) or `PoaBridge.describeWithdrawal` for multiple same-asset withdrawals in one transaction could:
- Credit/confirm withdrawal #2 as complete using withdrawal #1's `transfer_tx_hash`, and vice-versa, both reporting the same on-chain proof for two different recipients/amounts.
- This is functionally identical to the Halborn finding: an off-chain system trusts an on-chain-derived identifier (here, position/leg of a withdrawal) that isn't actually validated against the specific transfer it claims to represent.

### Likelihood Explanation
Requires a caller to submit multiple withdrawals of the *same* `assetId` within one signed intent/transaction (a supported and plausible batching pattern via `createWithdrawalIdentifiers`/`withdrawalParams: WithdrawalParams[]` in `sdk.ts`). No malicious actor action is required — a normal user or integrator batching withdrawals of the same token to different addresses triggers the mismatch. The bug is already known/documented in code comments and tests, which supports it being a genuine, reachable limitation rather than a theoretical one.

### Recommendation
Extend `findMatchingWithdrawal` (both in `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` and `PoaBridge.describeWithdrawal`) to disambiguate same-asset withdrawals by additional fields returned by the POA API (e.g., `amount`, `address`/destination, and ordering/index), analogous to how the Halborn remediation bound `orderId` to `purchaser` and `amountRequested` rather than trusting the identifier alone. If the API cannot currently support this, explicitly reject/guard batched same-asset withdrawals in the same transaction rather than silently mismatching.

### Proof of Concept
Using the existing test harness pattern (`waitForWithdrawalCompletion.test.ts:141-176`), submit two withdrawals of `nep141:usdc.token.near` in a single transaction to different destination addresses/amounts. Mock `getWithdrawalStatus` to return two `COMPLETED` records with the same `near_token_id` but different `transfer_tx_hash`/`amount`/`address`. Call `waitForWithdrawalCompletion` (or `PoaBridge.describeWithdrawal`) twice, once for each of the two original withdrawal requests — both calls return the *first* matching record's `transfer_tx_hash`, incorrectly reporting the same destination tx hash for both distinct withdrawals. /**
```typescript
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
```

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```
