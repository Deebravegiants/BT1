This confirms the finding: the webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are all extracted from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version` per `lib/shopify_api/webhooks/request.rb:15-33`), while `to_signable_string` — the value HMAC-verified — only covers the raw JSON body (`lib/shopify_api/webhooks/request.rb:35-38`). `Registry.process` trusts `request.shop` and `request.topic` after only validating the body's HMAC (`lib/shopify_api/webhooks/registry.rb:188-199` shown earlier), so the header-derived identity fields are never bound to the signature.

### Title
Webhook shop/topic/webhook-id identity headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , but `Registry.process` uses `request.shop`, `request.topic`, and `request.webhook_id` — all read from HTTP headers that are never part of the signed bytes — to route and label the webhook before invoking the app's handler [2](#0-1) . The identity binding "shop that produced this signed payload == shop attributed to this webhook" is broken because only `raw_body` is authenticated, while `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are authenticated by nothing.

### Finding Description
`HmacValidator.validate(request)` calls `Utils::HmacValidator.validate_signature`, comparing a computed HMAC of `to_signable_string` against `request.hmac` [3](#0-2) . For `Webhooks::Request`, `to_signable_string` is defined as `@raw_body` only [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers via `shopify_header` [4](#0-3) .

Because the app's `api_secret_key` is a single shared secret for the whole app (not per-shop), any shop that has installed the app can legitimately receive a genuine `(body, hmac)` pair from Shopify. That valid pair passes `HmacValidator.validate` regardless of which `shop-domain`/`topic`/`webhook-id` header values accompany it, since those headers are excluded from `to_signable_string`. An attacker who controls (or has installed the app on) Shop A can capture one legitimate webhook body+HMAC, then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to Shop B (or any topic/webhook-id changed), and `Registry.process` will pass this forged identity straight to the handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) . The equality that should hold — "shop bound in the authenticated signature == shop passed to the handler" — is broken because the shop is not part of the signed bytes.

### Impact Explanation
This is a cross-tenant identity-binding break: a handler acting on `WebhookMetadata#shop` (e.g., updating per-shop records, uninstall/redact flows, or the mandatory `shop/redact`/`customers/redact` compliance topics processed by this same `Registry.process` path) can be made to act on behalf of an arbitrary shop domain chosen by the attacker, using a signature that was only ever valid for the attacker's own shop's payload. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to already be able to receive at least one legitimate webhook for some shop under the same app (e.g., by installing the app themselves, which is normal, unprivileged access to any public app), then replay it with modified headers to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the shop's real credentials is needed — only header manipulation on an HTTP request the attacker fully controls.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed body before `Registry.process` trusts `request.shop`/`request.topic` to build `WebhookMetadata`. At minimum, document that consuming apps must independently verify `request.shop` against their own list of installed/authorized shops before acting on webhook data, since the gem's own `HmacValidator` does not do so.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker resends the exact same body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and/or `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: <attacker-chosen>, ...)`, causing the app to act as though this webhook genuinely originated from `victim.myshopify.com` [2](#0-1) .
