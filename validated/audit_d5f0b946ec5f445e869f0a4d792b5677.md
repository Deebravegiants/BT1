### Title
Webhook `shop` (and other Shopify-* headers) are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining `to_signable_string` as `@raw_body` only, while `shop`, `topic`, `api_version`, and `webhook_id` are read from HTTP headers that play no part in the signature. `Registry.process` treats HMAC success as proof of authenticity for the whole request, including `request.shop`, and passes it straight to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled unauthenticated from headers: [2](#0-1) 
`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`, so it never binds `shop` to the signature: [3](#0-2) 
`Registry.process` trusts this validation and forwards `request.shop` to the app-level handler as authenticated tenant context: [4](#0-3) 

The broken binding, expressed as an equality that should hold but doesn't:
`HMAC-verified bytes (raw_body)` ≠ `identity used downstream (request.shop from header)`.

An unprivileged internet user who controls a shop (e.g., a free/dev Shopify store) can:
1. Trigger a real webhook delivery to their own endpoint, obtaining a valid `(raw_body, hmac)` pair signed with the app's `client_secret` for a generic/templated event body (many webhook payloads, e.g. `app/uninstalled`, contain little to no shop-specific data, or the attacker can normalize/predict the body).
2. Replay that exact `raw_body` + `hmac` to the app's webhook endpoint directly (bypassing Shopify's delivery infra, since nothing but knowledge of the endpoint URL is required), while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because the signature only ever covered `raw_body`, which is unchanged.
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-chosen victim shop domain, causing the host application to act on the victim's tenant data/session (cross-tenant confusion) using a message the attacker fully controls.

### Impact Explanation
This breaks the tenant isolation guarantee that host applications rely on: "if the webhook HMAC validates, the shop header can be trusted as the origin shop." Any app that looks up its stored session/access token using `data.shop` from a validated webhook (a common, encouraged pattern in the gem's docs) can be tricked into executing app-triggered side effects (e.g., inventory sync, order actions, uninstall/reinstall bookkeeping) against a different merchant's tenant than the one that actually sent the payload — cross-tenant access without holding that tenant's access token or credentials.

### Likelihood Explanation
Exploitability requires no privileged credentials — only control of any Shopify store (trivially obtainable, e.g., a free dev store) to legitimately harvest one valid `(body, hmac)` pair for a topic with a predictable/generic payload, plus the ability to send a raw HTTP POST directly to the target app's public webhook endpoint with forged headers. No `api_secret_key` or access token is needed, satisfying the "unprivileged internet user" bar.

### Recommendation
Include `shop`, `topic`, and any other header fields the handler/host app treats as trusted identity in the HMAC-signed payload, or independently verify `request.shop` corresponds to a shop that has a matching, previously-established session before trusting `WebhookMetadata#shop`. At minimum, document that `request.shop`/`request.topic` are NOT authenticated by `Utils::HmacValidator.validate` and must be independently confirmed against stored session data before being used for tenant-scoped actions.
