### Title
Stale delegate grants re-arm after a position NFT round-trip, allowing unauthorized collateral withdrawal and borrowing - ([File: contracts/controller/src/storage/account.rs](contracts/controller/src/storage/account.rs))

### Summary
Controller delegate grants are stamped with `granted_by` but are not deleted when the position NFT moves. Ownership is resolved live from the NFT, so a grant becomes inactive while a different address owns the token, but the stored grant becomes valid again if the token ever returns to the original `granted_by` address. A previously revoked delegate can then act on the account again without a fresh grant.

### Finding Description
`contracts/position-nft` treats the NFT owner as the sole account owner; the controller performs a live `owner_of` lookup instead of caching ownership. Delegate authorization is implemented through stored `DelegateGrant` entries: `add_delegate` writes a grant stamped with the current owner, and `is_owner_or_delegate` accepts a delegate when `granted_by` equals the current NFT owner.

The vulnerability is the stale-grant revival path:

1. Alice owns `account_id` and grants delegate `mallory`.
2. Alice transfers the account NFT to Bob. The grant stops matching because `granted_by == alice` while `owner_of(account_id) == bob`.
3. The grant is not erased; Bob's `add_delegate` would overwrite it, but a transfer alone leaves it in storage.
4. Bob later transfers the same NFT back to Alice.
5. `owner_of(account_id) == alice` again, so the old `DelegateGrant { granted_by: alice, delegate: mallory }` matches again.
6. `mallory` is accepted by `require_owner_or_delegate` without Alice granting it again after the return.

The relevant behavior is documented in `contracts/position-nft/README.md`: delegates lapse on transfer, but “the stale grant stays in storage and re-arms if the token returns to `granted_by`.” The test `delegates_of_previous_owner_read_as_empty` confirms the grant is not read under the new owner, but the same storage entry remains.

### Impact Explanation
A re-armed delegate can use owner-level position verbs. In `contracts/controller/src/positions/supply.rs::process_withdraw`, an authorized caller may withdraw collateral to `to`, and in `contracts/controller/src/positions/debt.rs::process_borrow`, an authorized caller may borrow to `to`. Therefore, once the NFT returns to the prior owner, the old delegate can withdraw all withdrawable collateral to itself and/or borrow the maximum permitted amount to itself while leaving the debt on the victim’s account.

This is theft of user funds or creation of debt against the user’s collateral without fresh authorization.

### Likelihood Explanation
Exploitation requires three conditions:

- the victim previously granted an active position-manager delegate;
- the position NFT is transferred away and later transferred back to the same `granted_by` address;
- the stale delegate is still controlled by the attacker.

NFT marketplace flows, custodial transfers, collateral trading, accidental round-trips, or returning a position after temporary transfer can all satisfy the second condition. No privileged caller, oracle manipulation, upgrade, or leaked key is needed at execution time.

### Recommendation
Invalidate delegate grants permanently on NFT ownership changes rather than matching `granted_by` to the live owner. Practical fixes include:

- store an explicit transfer epoch or NFT ownership generation in `AccountMeta` or storage and include it in `DelegateGrant`, so grants from an earlier ownership epoch never match;
- emit/clear all delegate grants when the controller observes an owner change during `adopt_account` or any owner/delegate resolution path;
- or require delegates to carry a nonce/signature from the current owner after every transfer.

### Proof of Concept
Conceptual sequence, assuming an already-active position manager `mallory`:

```text
// Alice owns account_id = 7 with collateral.
controller.add_delegate(caller=alice, account_id=7, delegate=mallory)

// Alice transfers position NFT token 7 to Bob.
position_nft.transfer(from=alice, to=bob, token_id=7)

// Grant is inactive while Bob owns it: get_delegates(7, bob) returns empty.
// The old grant remains in controller storage.

// Bob later transfers the same NFT back to Alice.
position_nft.transfer(from=bob, to=alice, token_id=7)

// Stale grant now matches again because granted_by == alice == owner_of(7).
// Mallory calls an owner/delegate verb despite no new grant:
controller.withdraw(
    caller=mallory,
    account_id=7,
    withdrawals=[(collateral_hub_asset, 0)], // withdraw all
    to=Some(mallory)
)

// Or borrow out all remaining capacity:
controller.borrow(
    caller=mallory,
    account_id=7,
    borrows=[(debt_hub_asset, max_amount)],
    to=Some(mallory)
)
```

Expected result: `require_owner_or_delegate` accepts `mallory` because the stale grant’s `granted_by` equals the current NFT owner after the round-trip, even though Alice never re-approved `mallory` after regaining ownership.
