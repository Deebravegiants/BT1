## Finding: POA Bridge status lookup matches by `assetId` only, misreporting the wrong destination tx/hash when a batch contains duplicate-asset withdrawals

### Summary
`PoaBridge.describeWithdrawal` (and the equivalent used by `internal-utils`'s `waitForWithdrawalCompletion`) resolves the on-chain withdrawal status for a specific withdrawal in a batch by looking up the *first* entry in the POA bridge's response whose `near_token_id` matches the requested `assetId` — it ignores `index`, `amount`, and `destinationAddress` entirely. When a batch withdrawal (a single intent that withdraws the same token to two different destinations/amounts — a supported and documented use case) is processed, every withdrawal item sharing that `assetId` resolves to the exact same underlying `withdrawal` record, so distinct withdrawals in the batch get reported with the same `txHash`/`status`, i.e., the completion status returned for withdrawal #2 may actually be the on-chain outcome of withdrawal #1 (or vice versa).

### Finding Description
`findMatchingWithdrawal` matches purely by `assetId`: [1](#0-0) 

It's called from `describeWithdrawal`, which is invoked once per `WithdrawalIdentifier` (which does carry an `index`, but that index is never used for matching): [2](#0-1) [3](#0-2) 

The same pattern is duplicated in `internal-utils`, with the same acknowledged limitation in the comment: [4](#0-3) 

The SDK explicitly supports batch withdrawals of the same asset to different destinations — this is a normal, unprivileged flow, not an attack requiring malicious input: [5](#0-4) 

When `sdk.waitForWithdrawalCompletion` or `sdk.createWithdrawalCompletionPromises` is called with `withdrawalParams` containing two entries with the same `assetId` (e.g., same token, different `destinationAddress`/`amount`), each per-index `describeWithdrawal` call queries the same bridge transaction and both resolve to `Array.prototype.find`'s first match. Both indices then report identical `status`/`txHash`, even if only one of the two withdrawals has actually completed on the destination chain, or if the two completed to different destination addresses.

### Impact Explanation
This breaks the equality "a status reported ... is [the] on-chain outcome" called out in scope. An integrator relying on `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`/`describeWithdrawal` per-index results to mark individual withdrawals as settled (e.g., to release funds, mark an order complete, or decide whether to refund) can be told that withdrawal #2 (going to address B) completed with a specific `txHash`, when that `txHash` in fact corresponds to withdrawal #1 (going to address A). This is a "status or hash misreport making an integrator credit or refund twice" — explicitly listed as a High-impact class in scope. A service that pairs status-to-withdrawal on assetId identity could double-credit one destination while incorrectly believing an unrelated destination is also settled, or fail to detect that a distinct withdrawal never landed.

### Likelihood Explanation
This requires no attacker action or privileged access — merely constructing a normal batch withdrawal where two items share the same `assetId` (a legitimate, documented pattern: e.g., splitting a single token withdrawal across two recipients, or a primary+refund of the same asset). The code comments themselves acknowledge "multiple withdrawals of the same token in a single transaction are not supported" by this matching logic, confirming the condition is reachable and known-broken, not merely theoretical.

### Recommendation
Match withdrawals using a unique identifier tying each request to its bridge-side counterpart (e.g., match by `destinationAddress` + `amount` + `assetId`, or track POA's per-withdrawal id if the API surfaces one), and when duplicates in a batch cannot be disambiguated, either serialize/space out same-asset withdrawals in a batch, or throw/require callers to avoid duplicate `assetId` entries in a single batch rather than silently returning a match against the wrong entry.

### Proof of Concept
1. Submit an intent containing two `ft_withdraw` items for the same token to different destination addresses/amounts (a supported "batch withdrawal" per the SDK docs).
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [paramsA, paramsB], intentTx })` where `paramsA.assetId === paramsB.assetId`.
3. Internally, both `describeWithdrawal` calls hit `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: tx.hash })`, which returns both withdrawal entries; `findMatchingWithdrawal` returns the same first entry for both index 0 and index 1.
4. Both `promises[0]` and `promises[1]` resolve with the identical `{ status: "completed", txHash }`, even though the second physical withdrawal has a different actual destination/hash (or is still pending) — causing the caller to misattribute settlement. [6](#0-5)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
