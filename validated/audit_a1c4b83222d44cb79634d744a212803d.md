### Title
Fee-only transaction fallback underprices loaded_accounts_data_size when rollback accounts are zero-data/zero-lamport, bypassing block cost-model accounting - ([File: svm/src/account_loader.rs])

### Summary
When `feature_set.define_ltds_fee_only_semantics` is inactive, `load_transaction` computes the `loaded_accounts_data_size` of a `FeesOnlyTransaction` from `RollbackAccounts::data_size()` instead of the bytes actually scanned during the aborted load. An attacker can craft a transaction that touches many large accounts and then fails at `MaxLoadedAccountsDataSizeExceeded` or `ProgramAccountNotFound`/`InvalidProgramForExecution`, while ensuring the fee-payer/nonce rollback accounts have zero-length data, causing the reported cost to collapse to (near) zero even though the validator did the full account-load work.

### Finding Description
In `load_transaction` (`svm/src/account_loader.rs:456-468`), on a load failure the `loaded_accounts_data_size` field of `FeesOnlyTransaction` is set as:
```
loaded_accounts_data_size: if account_loader.feature_set.define_ltds_fee_only_semantics {
    loaded_transaction_data_size.into()
} else {
    tx_details.rollback_accounts.data_size() as u32
},
``` [1](#0-0) 

`RollbackAccounts::data_size()` only sums the data length of the fee payer (and nonce account, if present) — i.e., only the accounts tracked for rollback, not the accounts that were actually traversed by `load_transaction_accounts` before the failure:
```
pub(crate) fn data_size(&self) -> usize {
    let mut total_size: usize = 0;
    for (_, account) in self.iter() {
        total_size = total_size.saturating_add(account.data().len());
    }
    total_size
}
``` [2](#0-1) 

`load_transaction_accounts` (`svm/src/account_loader.rs:522-620`) still walks every account key in the message and every program id before returning `Err`, meaning any large accounts referenced earlier in the transaction are fully loaded (I/O + memory) even though the failure occurs later (e.g., on the final, missing program id). This actual work is what `loaded_transaction_data_size` (an accumulator) tracks, but that accumulator is discarded in the legacy branch.

Since a typical System-owned wallet or a freshly-created nonce account can have `data().len() == 0` bytes captured as `AccountSharedData` (wallets have 0 data length; nonce accounts have fixed but small data), the fallback `data_size()` can be driven arbitrarily low relative to the real bytes scanned. The existing repo test `fee_only_loaded_transaction_data_size` explicitly documents this: with `define_ltds_fee_only_semantics == false`, both the "fail due to limit" and "fail due to program id" cases report `loaded_accounts_data_size == 0`, regardless of how many/large the accounts scanned were:
```
assert_eq!(
    if define_ltds_fee_only_semantics { size_limit } else { 0 },
    fail_limit_loaded_size,
);
...
assert_eq!(
    if define_ltds_fee_only_semantics { loaded_fee_payer_size + other_accounts_size } else { 0 },
    fail_program_id_loaded_size,
);
``` [3](#0-2) 

This underreported `loaded_accounts_data_size` flows directly into cost accounting used for block-cost enforcement. `create_commit_results` (bank.rs) propagates `loaded_accounts_data_size` into `CommittedTransaction.loaded_account_stats` [4](#0-3) , and `get_transaction_costs` feeds `committed_tx.loaded_account_stats.loaded_accounts_data_size` into `CostModel::calculate_cost_for_executed_transaction`, which computes `loaded_accounts_data_size_cost` via `calculate_pages_for_bytes`/`calculate_pages_cost` [5](#0-4) [6](#0-5) . Zero bytes yields zero pages and zero cost, which is then summed into the transaction's total cost used by `cost_tracker.try_add` for block/account cost limit enforcement [7](#0-6) .

No existing sanitization prevents this: `load_transaction_accounts` performs no early-exit optimization to avoid loading large accounts before hitting a downstream failure, and the fallback path is unconditional whenever the feature is inactive.

### Impact Explanation
This is a cost/compute underpricing bug: an unprivileged attacker can submit transactions that force the validator to perform substantial account-loading I/O/memory work (multiple large accounts, up to the loaded-accounts-data-size limit) while being charged/tracked as consuming zero (or near-zero) bytes in the cost model. Repeated at scale, this lets an attacker's failing transactions consume real leader-side load work without being reflected in `cost_tracker`'s block cost or account-data-size accounting, allowing more such transactions to be packed into a block than the cost model intends — a violation of `COST_UPPER_BOUND`. This matches the Agave bounty category for cost model / resource-accounting bypasses that enable degraded block-production throughput.

### Likelihood Explanation
The precondition is simply that `define_ltds_fee_only_semantics` is not active (this is the legacy/pre-SIMD-0186-amendment behavior retained in the codebase specifically for pre-activation compatibility, as noted in the code comment "This function will be removed by the fee-payer data size amendment to SIMD-186"). Any unprivileged user can craft a transaction referencing several large pre-existing accounts followed by a non-existent/invalid program id, or one that exceeds `set_loaded_accounts_data_size_limit`, to reliably trigger `FeesOnlyTransaction` with a fee payer/nonce having zero/near-zero data length. This is fully reproducible with a standard transaction (no privileged access, no gossip/snapshot manipulation needed).

### Recommendation
Remove/disable the legacy `RollbackAccounts::data_size()` fallback path (or force `define_ltds_fee_only_semantics` semantics unconditionally) so that `FeesOnlyTransaction::loaded_accounts_data_size` always reflects `loaded_transaction_data_size` (the actual bytes accumulated during the aborted load), matching the fix already implemented behind the feature gate. Until the feature is activated cluster-wide, consider expediting its activation given the identified underpricing risk.

### Proof of Concept
Reuse `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs:3624` with `define_ltds_fee_only_semantics = false` (the `"old_fee_only"` test case already exists) and zero-data fee payer/nonce accounts:
1. Set up several large accounts (512B–8KB range as in the existing test).
2. Build a transaction referencing those accounts followed by a nonexistent program id (triggers `ProgramAccountNotFound`) or set a `loaded_accounts_data_size_limit` below the sum (triggers `MaxLoadedAccountsDataSizeExceeded`).
3. Execute via `SvmTestEnvironment` and assert `output.processing_results[i].loaded_accounts_data_size()` — with the feature off, current code returns `0` (or the tiny rollback-account size) regardless of `other_accounts_size`, confirming the fee-only charge/cost tracking is disproportionate to the bytes actually loaded. Extend the assertion to explicitly fail if `fail_limit_loaded_size`/`fail_program_id_loaded_size` is less than a fraction of `other_accounts_size`, demonstrating the invariant violation.
