### Title
Webhook Shop/Topic/Metadata Spoofing via HMAC That Only Covers the Raw Body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers and passes them straight to the host application's handler. Because those fields are never included in the HMAC-signed material, any bytes+HMAC pair the attacker legitimately obtains (e.g., from a real webhook delivered to their own shop) can be replayed with a different `shop-domain` header to make the host application believe the payload originated from a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers and are not part of the signed material at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the raw body) and compares it with `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate, then forwards the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to the app-registered handler as trusted `WebhookMetadata`: [4](#0-3) 

The binding that should hold is:
`shop_header == shop_that_the_signed_body_actually_originated_from`

But the HMAC only proves `body == body_signed_by_app_secret`; it says nothing about which shop the body came from. Since an attacker fully controls every header of the HTTP request they send to the app's public webhook endpoint, they can take a genuinely signed `(raw_body, hmac)` pair — obtainable from any real webhook delivered to a shop where they control the app installation (e.g., their own free development store) — and resend it to the same endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header. `Registry.process` will accept it as valid and hand the host app a `WebhookMetadata` claiming to be from a different tenant.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to decide which tenant's data a webhook payload applies to. Since `api_secret_key` is shared across all shops that install the app, any single installer can forge webhooks purporting to be from a different, unrelated shop, enabling cross-tenant data corruption/impersonation (e.g., triggering `app/uninstalled`, `customers/redact`, or order/product mutation handlers scoped by `data.shop` for a victim tenant). This matches the Critical "cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Exploitation requires only an internet-reachable webhook endpoint (which every Shopify app must expose publicly) and a legitimately signed body/HMAC pair, which any user can obtain by installing the app on their own store and capturing the webhook Shopify sends them. No access token, `client_secret`, or privileged account is required — this is fully reachable by an unprivileged, differently-tenanted internet user.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signed/verified material (or otherwise cryptographically bind them to the body), or validate that the `shop` header value corresponds to a shop session/installation the app already trusts (e.g., cross-check against stored session data) before dispatching to handlers. At minimum, document/require that host apps must independently verify `data.shop` against their own installation records rather than trusting the webhook header outright.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a legitimate webhook (any topic, e.g. `orders/create`), capturing the raw body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker sends a new HTTP request to the app's webhook endpoint reusing the exact same raw body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over the raw body — this check passes because the body/HMAC pair is genuinely valid.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `request.shop` now equals the attacker-controlled `"victim-shop.myshopify.com"`, even though the payload never originated from that shop. [5](#0-4)
