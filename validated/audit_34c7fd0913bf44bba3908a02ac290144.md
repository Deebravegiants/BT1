### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking only that the HMAC over the raw request body matches, then hands the handler a `shop` value taken from an unauthenticated HTTP header. Since the app's `api_secret_key` is shared across all shops installed on the app, a party who has captured (or otherwise obtained) one genuinely signed webhook body/HMAC pair for any shop can resend it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header and the signature check still passes, causing the app to attribute the payload to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which itself computes the signature only from `to_signable_string` (i.e., the body) — and then forwards `request.shop` to the handler as if it were authenticated: [3](#0-2) 

`HmacValidator.validate` never inspects any field other than what `to_signable_string` returns: [4](#0-3) 

Because the HMAC only covers the JSON body, and the same `Context.api_secret_key` is used for every shop installed on the app, the following equality that the gem implicitly promises to hold is broken:

`shop authenticated by HMAC == shop attributed by Registry.process to the handler`

Before the attacker's request: a legitimate webhook for shop A arrives with a body `B`, HMAC `H = HMAC(secret, B)`, and header `x-shopify-shop-domain: A`. `HmacValidator.validate` recomputes `HMAC(secret, B)` and confirms it equals `H`; `request.shop` returns `A`, which is correct because the header happens to match the body's origin.

After the attacker's request: the attacker resends body `B` and signature `H` unchanged (still valid, since neither depends on the shop header) but sets `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds because it only checks `B` against `H`. `Registry.process` then constructs `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., topic: ..., webhook_id: ..., api_version: ...)` and invokes the app's handler with that forged shop value, even though the payload actually originated from a completely different shop: [3](#0-2) 

The gem is documented and used precisely this way — the handler is expected to trust `WebhookMetadata#shop` as authenticated once `Registry.process` has run, since HMAC validation happened before the handler was ever invoked. There is no host-application misuse involved; the gem itself fails to bind the header value it hands out to the signature it verifies.

### Impact Explanation
This is a cross-tenant data confusion / spoofing primitive: an unprivileged actor who has visibility into any single valid webhook delivery for the app (their own shop's webhook, which Shopify sends them nothing of, but which is visible in transit to anyone who can observe or replay HTTP traffic to the app's public webhook endpoint, e.g. by directly POSTing a previously-seen payload) can cause the app to process that webhook's data as if it belongs to an arbitrary other shop of their choosing. Depending on how the host app's webhook handlers key off `WebhookMetadata#shop` (e.g., updating shop-scoped records, triggering side effects, invalidating sessions, writing audit logs), this can lead to cross-tenant data corruption or disclosure. This falls under the Critical "cross-tenant access" impact category defined by the rules.

### Likelihood Explanation
Exploitation requires no secrets, no privileged account, and no host-application misconfiguration — only the ability to send arbitrary POST requests to the app's public webhook endpoint with attacker-chosen headers and a previously-observed (body, HMAC) pair. All webhook endpoints are public HTTP endpoints by design, so this is directly reachable by any internet user who has captured or otherwise obtained one valid signed body/HMAC pair for the app. The relative difficulty is only in obtaining a single valid `(body, hmac)` pair, which is trivial for merchants who install the app themselves and can inspect/replay their own shop's incoming webhooks against the same public endpoint with a spoofed shop header.

### Recommendation
Include the identity-defining headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for HMAC verification, or otherwise cryptographically bind the shop attribution to the verified body (e.g., derive `shop` only from data embedded and covered inside the signed body/JWT rather than from a bare unauthenticated header). At minimum, `to_signable_string` should incorporate the `shop`, `topic`, and `webhook_id` header values so that tampering with them invalidates the HMAC check.

### Proof of Concept
```ruby
# Attacker captures (raw_body, hmac) from any real webhook delivery of THEIR OWN shop
raw_body = '{"id":123,"note":"legit order for attacker shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),   # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds because it only checks raw_body against hmac
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily dispatches to the handler with the forged shop
ShopifyAPI::Webhooks::Registry.process(request)
# handler receives WebhookMetadata#shop == "victim-shop.myshopify.com"
# even though the payload actually came from the attacker's own shop
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
