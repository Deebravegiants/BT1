### Title
Withdraw's `target_orders` PnL bookkeeping can underflow and panic due to decimal round-trip precision loss in `calc_take_pnl` - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` (and identically `process_deposit`) update `target_orders.calc_pnl_x` / `calc_pnl_y` using a chain of `checked_sub(...).unwrap()` operations that mix a value computed once in "sys decimal" normalized units (`x1`, `y1`) with a second value that is derived from raw token amounts and then converted back into normalized units via `Calculator::normalize_decimal_v2`, alongside a `delta_x`/`delta_y` value produced by `Processor::calc_take_pnl`. Because the normalize/restore decimal conversions use truncating integer division, the two independently rounded quantities are not guaranteed to satisfy `x1 >= normalize(pc_amount) + delta_x`, so the final `.checked_sub(...).unwrap()` can panic and abort the transaction — the same root cause pattern as the reported issue (two values computed via different paths/precision sources being subtracted without a bounds check, causing a legitimate operation to revert). [1](#0-0) 

### Finding Description
`calc_take_pnl` computes `x1`/`y1` from the *current* pool reserves (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`) normalized into `sys_decimal_value` units, then computes `delta_x`/`delta_y` (the PnL share to skim) and mutates the *raw* `total_pc_without_take_pnl` / `total_coin_without_take_pnl` in place by subtracting `pc_pnl_amount`/`coin_pnl_amount` (values obtained via `restore_decimal`, i.e. a second, independent decimal conversion): [2](#0-1) 

In `process_withdraw`, the withdrawable `coin_amount`/`pc_amount` are computed from the *already-pnl-adjusted* `total_pc_without_take_pnl` (mutated above) via `InvariantPool::exchange_pool_to_token` (floor rounding), and the pnl target accounting is then updated by subtracting both this freshly rounded, re-normalized amount *and* `delta_x`/`delta_y` from the *original* `x1`/`y1`: [3](#0-2) 

The exact double-subtraction pattern (`x1.checked_sub(normalize_decimal_v2(pc_amount,...)).unwrap().checked_sub(U128::from(delta_x)).unwrap()`) is reproduced verbatim in the project's own precision test, which the authors named `test_calc_pnl_precision` — itself an indication that the precision interplay between `normalize_decimal_v2`/`restore_decimal` (truncating integer division) and the pool/token exchange rounding (`RoundDirection::Floor`/`Ceiling`) was recognized as a fragile area: [4](#0-3) 

Because `normalize_decimal`/`normalize_decimal_v2`/`restore_decimal` all truncate (`checked_div` with no rounding-up), and `pc_amount`/`coin_amount` are computed from the *raw* mutated reserve while `x1`/`y1`/`delta_x`/`delta_y` are derived from *normalized* values computed at a different point in the pipeline, the two decimal-domain quantities are not provably consistent: `normalize_decimal_v2(pc_amount) + delta_x` can exceed `x1` for adversarially chosen `withdraw.amount` (an unprivileged LP fully controls the `withdraw.amount` argument to `Withdraw`, and hence controls `pc_amount`/`coin_amount` via the pool-share fraction), causing the final `.checked_sub(...).unwrap()` to panic and abort the whole withdraw instruction — mirroring exactly the referenced report's root cause: two quantities computed through different math paths being subtracted without a floor/guard check.

### Impact Explanation
A reverting `checked_sub().unwrap()` panics the Solana program, aborting the transaction. If the underflow condition is a function of the current pool state (accumulated rounding drift in `target_orders.calc_pnl_x`/`calc_pnl_y` versus the live vault balances) rather than solely the caller-chosen `withdraw.amount`, this can make `Withdraw` (and the analogous `Deposit` path) unusable for some or all LP position sizes against that pool, i.e. a Medium/High severity denial-of-service that can permanently prevent LPs from withdrawing their proportional share of pool funds until/unless `target_orders` state is otherwise repaired — matching the "permanent freezing of LP funds" impact bar.

### Likelihood Explanation
This path is reachable by any unprivileged LP holding LP tokens, using only the standard `Withdraw` instruction with an attacker-chosen `amount`, no privileged signer or special build required. Likelihood of triggering it in practice depends on the pool's accumulated PnL-taking history and decimal configuration (larger `native_decimal` vs `sys_decimal_value` gaps and low-liquidity pools amplify truncation-driven drift), so it is state-dependent rather than trivially triggerable on every pool, which is reflected in Medium likelihood.

### Recommendation
Replace the unconditional `checked_sub(...).unwrap()` chains used to update `target_orders.calc_pnl_x`/`calc_pnl_y` in `process_withdraw` (and the corresponding additive path in `process_deposit`) with saturating arithmetic or an explicit bounds check, e.g.:
```rust
let diff = x1.checked_sub(normalize_pc).unwrap_or(U128::from(0));
target_orders.calc_pnl_x = diff.checked_sub(U128::from(delta_x)).unwrap_or(U128::from(0)).as_u128();
```
or recompute `calc_pnl_x`/`calc_pnl_y` directly from the post-transfer live vault balances rather than by subtracting independently-rounded intermediate quantities, eliminating the cross-path precision dependency entirely.

### Proof of Concept
1. Pool is initialized and operated for a period such that repeated `calc_take_pnl` calls (triggered by `Deposit`/`Withdraw`/`WithdrawPnl`) accumulate rounding drift between `target_orders.calc_pnl_x/y` (normalized, truncated) and the true vault reserves, as demonstrated by the project's own `test_calc_pnl_precision` chaining two withdrawals and printing drifting `calc_pnl_x`/`calc_pnl_y` values. [5](#0-4) 
2. An unprivileged LP calls `Withdraw` with an `amount` chosen (via pool-share fraction) such that `normalize_decimal_v2(pc_amount) + delta_x > x1` (equivalently for the coin side), which is achievable because `pc_amount`/`coin_amount` are floor-rounded from the raw, already-pnl-mutated reserve while `x1`/`delta_x` come from a separately truncated normalization path. [6](#0-5) 
3. The subsequent `target_orders.calc_pnl_x = x1.checked_sub(...).unwrap().checked_sub(U128::from(delta_x)).unwrap()` panics, aborting the transaction and, if the underlying drift persists across the range of feasible withdraw amounts for that pool, permanently blocking withdrawals for that pool. [7](#0-6)

        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {

            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())

        ret
    }
