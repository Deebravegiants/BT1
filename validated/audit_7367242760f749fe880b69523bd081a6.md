### Title
Missing shop-domain validation on JWT `dest` claim before sending `client_secret` in token exchange - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request directly from the unsanitized `dest` claim of the caller-supplied session token, and never runs it through `Utils::ShopValidator.sanitize!` — unlike the sibling methods `client_credentials`, `refresh_token`, and `migrate_to_expiring_token` (the latter defined in the very same file), which all call `Utils::ShopValidator.sanitize!(shop)` before building the outbound request host. This breaks the equality the gem otherwise enforces: `host validated == host that receives client_secret`.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#shop` simply strips the `"https://"` prefix off the raw `dest` JWT claim with no format check, no comparison against `iss`, and no membership check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [1](#0-0) 

`JwtPayload#initialize` only verifies the JWT signature and that `aud == Context.api_key`; it never validates `dest` against a trusted domain list: [2](#0-1) 

`TokenExchange.exchange_token` takes that raw `dest_shop` and uses it, unvalidated, to build the session whose `shop` becomes the request host, then sends `client_secret` in the POST body to that host: [3](#0-2) 

`Clients::HttpClient#initialize` builds the base URI directly from `session.shop` with no sanitization: [4](#0-3) 

Contrast this with the three other credential-sending call sites in the same module/file, which all sanitize the shop before use: [5](#0-4) [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` restricts hosts to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an explicit configured `myshopify_domain`: [8](#0-7) 

Because `exchange_token` skips this check, the invariant "the value validated as a legitimate Shopify shop domain is the same value used as the destination for the request carrying `client_secret`" does not hold for this code path, while it holds for every other credential-sending method in the library.

### Impact Explanation
If the `dest` claim of a session token ever resolves to a value outside `TRUSTED_SHOPIFY_DOMAINS` (via a token issuer that isn't Shopify's canonical admin/checkout signer, a malformed/legacy `dest` format, or any future non-`*.myshopify.com` `dest` value the app forwards to this SDK), `exchange_token` will silently issue a POST containing the app's `client_secret` to that host — an SSRF-with-credentials condition, one of the explicitly in-scope High-impact categories. This is exactly the missing-check pattern the migration guide (report analog) describes: a security-relevant computation performed without validating the identity/address input that the rest of the module treats as mandatory.

### Likelihood Explanation
Exploitability depends on whether a caller can get `ShopifyAPI::Auth::JwtPayload.new` to accept a token whose `dest` is not a genuine merchant domain while still passing signature verification (`aud == Context.api_key`, correct HMAC). Since signature verification uses the app's own `Context.api_secret_key`, this SDK's `JwtPayload` cannot be fooled by an outsider without that secret in the normal flow — but the code contains no defense-in-depth check on `dest` at all, unlike its sibling functions, so any future issuer bug, misconfiguration, or additional token source (e.g., non-Shopify id-token integrations sharing the same secret) has no protection against exfiltrating `client_secret` to attacker infrastructure.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_token`) before constructing `shop_session`, and raise `Errors::InvalidShopError` if it fails validation. Consider also making `JwtPayload` itself enforce a trusted-domain check on `dest` at decode time.

### Proof of Concept
Not exploitable without knowledge of `api_secret_key` to forge/replay a token whose `dest` value falls outside `TRUSTED_SHOPIFY_DOMAINS`; this finding documents a missing defense-in-depth invariant (present everywhere else in the module but absent here) rather than a demonstrated end-to-end exploit with attacker-only capabilities.
