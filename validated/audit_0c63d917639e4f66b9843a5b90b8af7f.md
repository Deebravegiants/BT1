- `withdrawal.rs::message(nonce, dest_chain, beneficiary)` → `keccak256((nonce: u64, dest_chain: StateMachine, beneficiary: Vec<u8>).encode())`, used to authorize `withdraw_fees`, and reads/increments `Nonce::<T>::get(address, dest_chain)`. [1](#0-0)

[2](#0-1) [3](#0-2) 

Both `Fees` and `Nonce` are `StorageDoubleMap<StateMachine, Vec<u8>, ...>` / `StorageDoubleMap<Vec<u8>, StateMachine, u64, ...>` shared by both flows, and both extrinsics are unsigned/permissionless (`ensure_none(origin)`), dispatchable by any relayer/bystander who can produce a valid state proof for the same delivery. [4](#0-3) [5](#0-4) 

For a given `(nonce, state_machine/dest_chain, beneficiary)` triple, `message(...)` and `beneficiary_message(...)` produce **byte-identical SCALE encodings and therefore identical signatures** — this is exactly the "same signature, different function" collision described in H-17, except here it is a shared nonce/message-format collision across two different unsigned extrinsics rather than shared calldata offer structs.

### Title
Signature Format Collision Between `withdraw_fees` and `accumulate_fees` Beneficiary Redirect Enables Nonce-Griefing / Front-Run of Relayer Fee Payouts - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-ismp-relayer` signs two functionally distinct authorizations — an immediate fee **withdrawal** (`withdraw_fees`) and a fee **accumulation beneficiary redirect** (`accumulate_fees`) — using the identical SCALE-encoded tuple `(nonce: u64, StateMachine, beneficiary: Vec<u8>)` and the identical shared `Nonce` storage counter. A signature a relayer produces for one extrinsic is valid, byte-for-byte, for the other.

### Finding Description
`message()` (used by `withdraw_fees`) and `beneficiary_message()` (used by `accumulate_fees`) both hash `(nonce, chain, beneficiary).encode()` with no function-specific domain tag, and both read/consume the same `Nonce::<T>` entry keyed by `(address, state_machine)`. Since both extrinsics are unsigned and publicly visible pre-inclusion (`ensure_none(origin)`, `validate_unsigned`), any observer who sees a relayer's pending `withdraw_fees` signature for `(nonce, chain, beneficiary)` can lift it and submit it instead as `accumulate_fees`'s `beneficiary_details` (supplying their own otherwise-valid `WithdrawalProof` for a delivery by the same relayer address on the same chain), or vice-versa. Whichever call lands first consumes the shared nonce and executes its own semantics — the loser's signed extrinsic then fails nonce/signature checks (`InvalidSignature`/nonce mismatch), forcing the relayer to re-sign and resubmit. [2](#0-1) [6](#0-5) 

### Impact Explanation
The direct effect is that a third party can pick which of the two functions a relayer's signed authorization is realized under, front-running the relayer's intended `withdraw_fees` dispatch by consuming the same nonce via `accumulate_fees`. Because `withdraw_fees` reads `available_amount = Fees::get(...)` at execution time (not the amount at signing time), and `accumulate_fees`'s redirect can be triggered ahead of an anticipated fee accrual, the two paths are not merely permission-format twins but different money-moving/accounting operations sharing one authorization surface, in the same bug class as the Gondi finding (a struct/signature intended for one privileged function silently accepted by another with different economic effect). At minimum this causes forced nonce desynchronization/DoS of a relayer's withdrawal; depending on relative fee balances at call time it can also cause an unintended amount to be paid out or redirected under a signature the relayer did not create for that specific action.

### Likelihood Explanation
Both extrinsics are unsigned and go through the public transaction pool (`validate_unsigned`), so the signed payload is visible before inclusion. No cryptographic domain separator (function selector, action tag) distinguishes the two message hashes, and the shared `Nonce` map is the only replay guard, which itself is symmetric between the two functions. Exploiting this requires only a permissionless proof-crafting step available to any relayer who has independently delivered messages for the victim relayer's address, which is realistic given the module's design as an open beneficiary-redirect mechanism.

### Recommendation
Include a function-specific domain separator (e.g., a fixed byte tag or distinct type-hash string, analogous to the mitigation applied to `RenegotiationOffer` for `addNewTranche` vs `refinanceFull`) in both `message()` and `beneficiary_message()` so that a signature computed for one cannot decode as valid input for the other, even when `(nonce, chain, beneficiary)` coincide. Alternatively, maintain separate nonce counters per action so consuming one does not desynchronize the other.

### Proof of Concept
1. Relayer R has accrued fees on `state_machine = SM` at `Nonce[R, SM] = n`.
2. R signs `message(n, SM, beneficiary)` and submits `withdraw_fees` (unsigned extrinsic, visible in mempool before finalization).
3. Attacker A observes the pending extrinsic, extracts `(n, SM, beneficiary, signature)`.
4. A separately assembles a valid `WithdrawalProof` for any not-yet-claimed request delivered by R on `SM` (public chain data), sets `beneficiary_details = Some((beneficiary, signature))`, and submits `accumulate_fees` with higher priority/first inclusion.
5. `accumulate_fees` succeeds: `signature.verify(beneficiary_message(n, SM, beneficiary))` passes because it is byte-identical to `message(n, SM, beneficiary)`; `Nonce[R, SM]` increments to `n+1`; fees are redirected to `beneficiary` instead of disbursed.
6. R's original `withdraw_fees(n, SM, beneficiary, signature)` extrinsic subsequently fails because `Nonce::get(R, SM)` is now `n+1`, forcing R to re-sign and resubmit, while the timing/amount of the payout has been altered from what R intended.
