### Title
Emporium `runAction` performs zero balance accounting for tokens excluded from `circomData.erc20TokenAddresses`, allowing theft of any resident Emporium ERC20 balance via the Min-circuit path - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When a `transact()` call targets the Emporium action with `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` switches to `formInputEmporiumMin`, whose public-input vector is only `[emporiumMessage, timeStamp, calldataHash]` [1](#0-0) . Because `EmporiumUpgradeable.runAction`'s balance-accounting loop is bounded by `circomData.erc20TokenAddresses.length` [2](#0-1) , an empty `erc20TokenAddresses` array means *no* token balance is measured before/after the `stack.ops` are executed, so any ERC20 balance the Emporium proxy currently holds can be pulled out by a CASE-2 stateless op with zero on-chain accounting or revert.

### Finding Description
The claimed broken equality is: *"net tokens leaving Emporium via this action == -deltaAmountChanges credited into the proof"*. For the Min-circuit path this equality is never even constructed, because `deltaAmountChanges` (computed in `Hinkal._externalTransact` by iterating `circomData.erc20TokenAddresses.length`, which is 0) is an empty array [3](#0-2) , and `EmporiumUpgradeable.runAction`'s post-op balance/UTXO-creation loop is likewise bounded by `circomData.erc20TokenAddresses.length == 0`, so it executes zero iterations [4](#0-3) .

The attacker's path:
1. Attacker calls `Hinkal.transact` directly (no relay), so `circomData.originalSender == msg.sender` and `circomData.relay == address(0)` is permitted by `performHinkalChecks` [5](#0-4) .
2. Attacker sets `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0` (satisfies `dimensionsCheck`, which only requires all array lengths match `dimensions.tokenNumber`) [6](#0-5) . A verifier for this exact 0-token dimension (`VerifierEVMMin0v4`) exists, confirming this is a supported code path, not an edge case that is rejected.
3. `EmporiumStack.signerAddress = address(0)` so `verifyWallet` returns immediately without any signature or op validation [7](#0-6) .
4. The attacker crafts a CASE 2 op — `op.invokeWallet = false`, `op.endpoint = <victim token>`, `op.callData = transfer(attackerEOA, amount)` — which is executed via a raw, unauthenticated external call [8](#0-7) .
5. Because `erc20TokenAddresses` is empty, `balancesBefore`/`balancesAfter` are empty arrays, the `balanceChange < 0` revert check never runs for the stolen token, and no UTXO is created/consumed to compensate the drained balance [9](#0-8) .

No other guard catches this: `performHinkalChecks` only checks calldata-hash integrity and array-length consistency, not that "any token actually moved" is included in `erc20TokenAddresses`; `verifyProof` only proves the Min-circuit's 3 public signals (message/timestamp/calldataHash), which say nothing about token custody; `Hinkal.sol`'s outer balance/slippage loop is likewise indexed only over `circomData.erc20TokenAddresses.length`, so it also skips the stolen token entirely [10](#0-9) .

### Impact Explanation
Any ERC20 balance the `EmporiumUpgradeable` contract holds at call time (e.g., dust/leftovers from previous swap ops, fee-token float, or any token a prior interaction routed through/left in the Emporium proxy) can be transferred out to an attacker-controlled address with zero accounting, zero UTXO consumption, and zero revert condition. This is direct theft of protocol/relay/resident funds custodied by the Emporium contract — repeatable every time the contract holds a nonzero ERC20 balance of any token, at negligible attacker cost (one self-submitted `transact()` with a trivial zero-token dimension proof).

### Likelihood Explanation
Preconditions: the Emporium contract must hold a nonzero balance of some ERC20 token that the attacker targets. This is plausible any time swaps/ops leave dust or fee-token reserves in the contract (the code's own `payRelayFees` "Gas Token in Emporium is not found" fallback assumes Emporium can legitimately hold token balances). The attacker needs no privileged role, no relay, no victim cooperation, and no valid Merkle proof of ownership over the stolen tokens — only the ability to self-submit a `transact()` call with a 0-token Min-circuit proof, which the protocol explicitly supports via a dedicated verifier (`VerifierEVMMin0v4`). This makes the attack highly feasible and fully repeatable.

### Recommendation
Do not let `circomData.erc20TokenAddresses` be attacker-selectable independent of what tokens the `EmporiumStack.ops` actually touch. Options: (1) require `EmporiumUpgradeable.runAction` to snapshot and diff the balance of every token address referenced by `op.endpoint`/decoded from `op.callData` regardless of `erc20TokenAddresses` length, or (2) disallow the Min-circuit (0-token) path whenever `stack.ops` contains any CASE-2 op capable of moving ERC20 tokens, or (3) require the Emporium contract to hold zero token balances between transactions (sweep-to-zero invariant) enforced at the end of every `runAction` call, reverting if any tracked-or-untracked token balance changes without a corresponding accounted `deltaAmountChanges`/UTXO entry.

### Proof of Concept
Hardhat test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a mock ERC20 `Dust`.
2. Seed `EmporiumUpgradeable` with `Dust` tokens directly (`Dust.transfer(emporium.address, 100e18)`) to simulate resident/dust balance.
3. As attacker EOA (unprivileged, no relay), build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `dimensions.tokenNumber = 0`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: Dust, invokeWallet: false, value: 0, callData: Dust.transfer(attacker, 100e18)}], maxFee: 0, deadline: MAX}))`.
4. Generate a valid Min-circuit proof (`emporiumMessage`, `timeStamp`, `calldataHash` only) locally with `VerifierEVMMin0v4`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from attacker EOA.
6. Assert: `Dust.balanceOf(attacker)` increases by `100e18`, `Dust.balanceOf(emporium.address)` decreases by `100e18`, while `circomData.amountChanges.length == 0` and `circomData.erc20TokenAddresses.length == 0` (no on-chain accounting entry exists for the moved value), and the transaction does not revert.
