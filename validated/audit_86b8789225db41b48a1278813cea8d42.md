### Title
Single `maxOracleAge` staleness threshold shared across all Chainlink price feeds with differing heartbeats enables use of genuinely stale prices - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payment using two Chainlink feeds — the native asset oracle and the per-token oracle — but validates the freshness of both against one single, contract-wide `maxOracleAge` value, even though the code's own comments acknowledge that Chainlink heartbeats "vary per chain (BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h)". This is the same root cause as the referenced report: one staleness threshold applied to multiple feeds that actually have very different true heartbeats.

### Finding Description
`maxOracleAge` is a single storage variable set once via `_setParams` and reused for every oracle read in `_getOraclePrice`: [1](#0-0) 

```
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
```

Both `nativeOracle` and every `TokenConfig.tokenOracle` are checked against this same `maxOracleAge`, as seen in `_tokenPrice` [2](#0-1)  and `swapAndDeposit` [3](#0-2) .

The contract's own documentation and deployment script confirm the true heartbeats diverge sharply across the supported feeds: [4](#0-3) [5](#0-4) 

Governance is only bounded by `MAX_ORACLE_AGE = 7 days` [6](#0-5) , and the deploy script's default is `90_000` seconds (25h) tuned specifically for the 24h-heartbeat stablecoin feeds [7](#0-6) . That same 25h (or any single governance-chosen value) is then also applied to feeds with a genuinely short heartbeat (e.g. BNB/USD on BSC, ~27s), so a price that has stopped updating for far longer than its real heartbeat — but still within `maxOracleAge` — will be accepted as fresh by `_getOraclePrice` for every UserOperation that reaches `_fetchDetails`/`_tokenPrice`.

### Impact Explanation
Since `_fetchDetails` (and thus `_tokenPrice`/`_getOraclePrice`) is invoked on every ERC-4337 `UserOperation` that uses this paymaster — reachable by any unprivileged bandwidth purchaser submitting a UserOp — an oracle that has genuinely stalled (feed contract bug, sequencer/network issue, chain-specific liveness failure) but has not yet crossed the shared `maxOracleAge` window can still be used to price gas. Because the true heartbeat for that specific feed (e.g. ~27s) has already been violated well before `maxOracleAge` (tuned for a 24h feed) elapses, a stale, favorable, or unfavorable price can be used for pricing far longer than intended. An attacker who observes a stalled fast-heartbeat feed can submit gas-paying UserOps priced off the stale value to systematically underpay for gas (extracting value from the paymaster's treasury/deposit) until the shared, overly permissive threshold finally trips.

### Likelihood Explanation
Requires an oracle that legitimately halts or lags its real heartbeat (a known, non-rare failure mode for chain-specific feeds, especially on less liquid pairs/chains) combined with governance choosing a `maxOracleAge` sized for the slowest configured feed (which the deploy script explicitly does by default). No malicious admin/oracle collusion is needed — an ordinary oracle staleness event on the fast-heartbeat chain is sufficient to open the mispricing window, and exploitation only requires submitting an ordinary UserOperation.

### Recommendation
Replace the single contract-wide `maxOracleAge` with a per-oracle staleness threshold (e.g., a `maxAge` field alongside `AggregatorV3Interface` in `TokenConfig`/`nativeOracle`, set from each feed's documented Chainlink heartbeat plus a small buffer), and pass the correct threshold into `_getOraclePrice` for each specific oracle instead of the single global variable.

### Proof of Concept
1. Governance deploys `SimplexPaymaster` with `maxOracleAge = 90_000` (25h), matching the 24h heartbeat of the USDC/USDT stablecoin feeds it primarily targets, per `DeploySimplexPaymaster.s.sol`.
2. Governance also configures `nativeOracle` = BNB/USD on BSC, whose real Chainlink heartbeat is ~27s (per the contract's own comment).
3. The BNB/USD feed's `latestRoundData()` stalls (e.g., a chain-specific liveness fault) for several hours, well beyond its true ~27s heartbeat, but under 25h.
4. `_getOraclePrice(nativeOracle, ...)` still passes the `block.timestamp - updatedAt > maxOracleAge` check because 25h has not elapsed, so `_tokenPrice`/`_fetchDetails` returns a stale `tokenPrice` to any submitted UserOperation.
5. An attacker submits gas-paying UserOps priced off this stale (and now inaccurate) BNB/USD rate, extracting value from the paymaster versus what an accurate, heartbeat-correct freshness check would have rejected.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
