### Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant shop spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook delivery by validating the HMAC over the raw body only, but the `shop` (and `topic`/`webhook_id`) values that the registry hands to the host application's handler are read from unauthenticated HTTP headers, breaking the equality `shop authenticated-by-HMAC == shop delivered-to-handler`.

### Finding Description
`Utils::HmacValidator.validate` verifies a webhook by recomputing `HMAC(api_secret_key, to_signable_string)` and comparing it to the `hmac-sha256` header [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to that signature [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (the unauthenticated header value) straight into the `WebhookMetadata` passed to the host app's handler [4](#0-3) . Nothing in this gem ties the `shop-domain` header to the HMAC-verified bytes, so the "shop that was cryptographically verified" (none — the body only) and "the shop the handler is told the event is for" are two different, unbound values.

### Impact Explanation
If an attacker can obtain any one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., because they observe/replay a webhook delivered for their own shop, which any merchant who installs the app can trigger for their own store), they can resend that same body+signature to the app's public webhook endpoint while changing only the `shop-domain` header. `HmacValidator.validate` will still pass because it only checks the raw body, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the event belongs to an arbitrary victim shop. If the host application uses `data.shop` as the tenant key to store/attribute webhook data (the intended and documented use of this field), this results in cross-tenant data confusion in the host application, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Low-to-medium. The attacker cannot forge an arbitrary new body/HMAC pair without the app's `client_secret`, so this is a header-spoofing/replay issue rather than full forgery — the attacker needs to have legitimately received (or otherwise obtained) at least one real webhook body+signature for the target app (e.g., from their own installed shop), and then resend it to the app's endpoint with a modified `shop-domain` header. This is plausible for an unprivileged user who has installed the target app in their own store and controls network requests to the app's public webhook URL, but it does not constitute a full, self-contained forgery from an attacker with no relationship to the app.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) headers in the HMAC signable string, or otherwise have `Registry.process`/`WebhookMetadata` derive the shop only from a value that is cryptographically bound to the verified payload, so that the header used by the host application to attribute data to a tenant cannot be altered independently of the HMAC-verified body.

### Proof of Concept
1. Attacker installs the target app in their own development store, causing Shopify to deliver a legitimate webhook (`raw_body`, `x-shopify-hmac-sha256`) to the app's registered endpoint.
2. Attacker captures that `(raw_body, hmac)` pair (e.g., via their own reverse proxy/logging on infrastructure they control that forwards to the app).
3. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain` to a victim shop's domain.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks the body against the HMAC. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` forwards `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the host app's handler, which processes attacker-controlled data as if it belongs to the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
