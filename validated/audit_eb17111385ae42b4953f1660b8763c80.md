## Title
Webhook shop domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body. The `shop` (and `topic`) values that the gem hands to the application's webhook handler are read directly from unauthenticated HTTP headers and are never included in the signed material, so they can be swapped for any other shop's domain without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by making `to_signable_string` return only the raw HTTP body: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `verifiable_query.hmac` matches `HMAC(secret, to_signable_string)`: [3](#0-2) 

`Registry.process` trusts this single check and then forwards `request.shop`, taken straight from the `shop-domain` header, to the app's handler as authenticated data: [4](#0-3) 

Because the `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that installs a given app (it is not per-shop), and because the HMAC only binds the *body*, not the `shop-domain` header, any two requests with identical bodies produce identical valid HMACs regardless of which shop the header claims to be. This is exactly the "field acted on but not covered by the HMAC" class of bug: the code verifies `HMAC(secret, raw_body) == received_hmac` (an equality over body bytes only) but then *acts on* `shop` as if that same equality also authenticated the shop identity — it does not.

### Impact Explanation
An attacker who installs the target app on a shop they control receives legitimate, validly-signed webhooks for that shop (the body content of many webhook topics is attacker-influenced, e.g. order/product/customer webhooks reflect data the attacker shop owner can set). By replaying the exact `raw_body` + `X-Shopify-Hmac-Sha256` pair while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain, the attacker can make `Registry.process` deliver attacker-controlled `body`/`topic` data to the handler while asserting it belongs to the victim shop's tenant (`WebhookMetadata#shop`). Any host application logic that uses `shop` to select the tenant record, session, or access token to act on (the gem's own docs describe this as the standard usage pattern) will process forged, attacker-controlled data under a victim's identity — a cross-tenant access/data-integrity break, matching the Critical impact bar (cross-tenant access) defined in scope.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the app on any shop (a normal, unprivileged action for a public/embedded app) and to send a crafted HTTP request to the app's public webhook endpoint with attacker-chosen headers — no access token, `api_secret_key`, or privileged account is needed. This is directly reachable through the gem's documented `Registry.process` entry point.

### Recommendation
Bind the shop identity into the authenticated material before trusting it:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string used for HMAC verification, or
- Require callers of `Registry.process` to pass the expected shop (e.g., resolved from the session/store being targeted) and assert `request.shop == expected_shop` in addition to the HMAC check, so the header can't be swapped independently of the signed body.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) whose body they control.
2. Shopify sends: headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid>`, and the attacker-controlled JSON body.
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:13-21` succeeds because it only checks `HMAC(secret, raw_body)`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:189-199` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker's forged body, which the host application will treat as legitimate data for the victim tenant.
