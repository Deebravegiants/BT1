### Title
Webhook HMAC only authenticates the raw body, not the `shop`/`topic` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body [1](#0-0) . The `shop`, `topic`, and `webhook_id` values used downstream are read directly from unauthenticated HTTP headers [2](#0-1) , and are never included in the HMAC computation performed by `Utils::HmacValidator.validate` [3](#0-2) . `Registry.process` trusts these header-derived values to route and label the webhook to a specific handler and shop after only checking the HMAC of the body [4](#0-3) .

### Finding Description
The binding that should hold is: `shop_authenticated_by_hmac == shop_passed_to_handler`. In this gem, that equality is never enforced — only `raw_body` is signed and verified:

- `Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only [5](#0-4) .
- `Request#shop`, `Request#topic`, and `Request#webhook_id` are plain, unauthenticated header reads, not covered by the signature at all [2](#0-1) .
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header using `OpenSSL.secure_compare` — again, this only covers the body string [3](#0-2) .
- `Registry.process` raises `InvalidWebhookError` only if the body HMAC fails, then immediately dispatches `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` using the unauthenticated `shop`/`topic` headers [4](#0-3) .

Shopify signs webhooks for every shop that has an app installed using the **same app `api_secret_key`** — the secret is per-app, not per-shop. Consequently, any merchant who installs the app on their own (attacker-controlled) shop legitimately receives valid `(raw_body, hmac)` pairs signed with the app's secret. Because the `shop-domain` and `topic` headers are outside the signed material, that attacker can replay the exact same body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (a victim shop) and/or `x-shopify-topic` header. `HmacValidator.validate` will report success (the body and secret match), and `Registry.process` will hand the attacker-chosen body to the handler labeled as belonging to the victim shop/topic.

### Impact Explanation
This breaks the tenant identity binding the HMAC check is supposed to provide, letting an unprivileged app-installer (any merchant who can install the target app on their own store) inject attacker-controlled webhook payloads that are processed by the host application as if they originated from a different, victim shop. Any host app that keys persistence, authorization, or business logic off `WebhookMetadata#shop`/`#topic` — the documented, intended use of this API — inherits cross-tenant data corruption/disclosure risk purely from this gem's incomplete signature scope. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability only requires the ability to install the target app on an attacker-owned development/trial shop (no leaked secrets, no privileged account, no host application misuse) to obtain one valid `(raw_body, hmac)` pair, then replay it with a forged `shop-domain`/`topic` header to the app's public webhook endpoint. No interaction with a higher-privileged user or social engineering is required, unlike the analog report's own attack.

### Recommendation
Include the shop domain, topic, and webhook id (and ideally api-version) in the signed/verified material for webhook requests, or otherwise cryptographically bind these header values to the raw body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document clearly that `request.shop`/`request.topic` are unauthenticated and must not be trusted for authorization decisions without additional verification (e.g., cross-checking against a shop that is independently known/expected).

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, signed by Shopify with the app's `api_secret_key`:
   - `raw_body = '{"id":1,...attacker-controlled order payload...}'`
   - `hmac = Base64(HMAC-SHA256(api_secret_key, raw_body))`
2. Attacker captures this `(raw_body, hmac)` pair (their own traffic to their own endpoint).
3. Attacker resends the exact same `raw_body` and `hmac` header to the app's public webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: orders/create` (or a more sensitive topic the attacker wants to spoof)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against `hmac` using the shared app secret [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)` [7](#0-6) , causing the host application to process attacker-controlled data under the victim shop's tenant context.
