### Title
Unbounded ownership-chain walk in `object::root_owner` permanently bricks code-object publishing/lazy-init once an object is self-owned - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner` walks the ownership chain of an object without the cycle/depth protection (`MAXIMUM_OBJECT_NESTING`) that every other ownership-walking function in the same module (`owns`, `verify_ungated_and_descendant`) enforces. `root_owner` is wired directly into custody-critical logic: `code::publish_package` (records/consumes the root owner for code-object gating) and `init::assert_may_self_initialize` (the lazy module self-initialization gate for object-hosted modules). Since Move's own object model allows an object to become self-owned (a 1-cycle) via an ordinary, unprivileged `object::transfer` call, any code object that reaches this state causes `root_owner()` to loop forever (until out-of-gas) on every future package publish/upgrade and every lazy self-init check for modules hosted at that address - permanently locking the ability to (re)initialize or upgrade that code object.

### Finding Description
In `aptos-move/framework/aptos-framework/sources/object.move`: [1](#0-0) 

```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```

This loop has no bound and no cycle check, unlike its sibling ownership-walkers in the same file, `owns` and `verify_ungated_and_descendant`, both of which explicitly guard against cycles/deep nesting with `MAXIMUM_OBJECT_NESTING`: [2](#0-1) 

An object can be made to own itself with a single, ordinary, unprivileged `object::transfer` call where `to` equals the object's own address - this is a known, already-tested behavior of the framework (the test even documents it as creating a "cycle (self-loop) in ownership)"): [3](#0-2) 

Once an object is self-owned, `root_owner()` on it (or on any descendant whose ownership chain passes through it) never terminates.

`root_owner()` is not a peripheral view function - it is load-bearing for code-object custody:

- `code::publish_package` calls it on every (re)publish/upgrade of a code object to record the "deploy owner" used to gate the object's lazy self-initialization: [4](#0-3) 

- `init::assert_may_self_initialize` calls it on every lazy self-init check (`internal_maybe_initialize`) to decide whether the object-hosted module may obtain a signer for its own address and run its (compiler-generated) lazy initializer: [5](#0-4) [6](#0-5) 

If the object address ever becomes self-owned, both `publish_package` (any future upgrade of that code object) and `internal_maybe_initialize`/`assert_may_self_initialize` (any future lazy self-init of modules there) will call `root_owner()` and loop until the transaction runs out of gas, aborting every time. There is no recovery path in the module: nothing in `object.move`, `code.move`, or `init.move` detects or repairs a self-owned object, and `object::transfer_with_ref`/`transfer_raw` do not prevent creating the self-loop either (only the higher-nesting multi-hop cycle case is bounded, and even that only aborts rather than repairing state).

### Impact Explanation
This breaks the custody invariant that "code-object ownership and control must remain governable" (custody pivot: "Multisig-owned assets, resource accounts, and code objects must not leak upgrade, freeze, or transfer authority to unprivileged callers" / "Permanent lock or non-recoverable loss of ... resource-account-held value"). Once a code object hosting live modules (potentially holding capabilities, `ExtendRef`s, fungible-asset controller state, resource-account signer capabilities, mint/freeze capabilities, etc. behind lazy `init_module`-style initialization) is put into a self-owned state:
- The code object can never be upgraded again (`code::publish_package` aborts via infinite loop / out-of-gas on every future publish attempt for that address).
- Any module at that address relying on lazy self-initialization (`internal_maybe_initialize`) can never complete its one-time initialization, permanently blocking creation of whatever custody resources (signer capabilities, capability structs, etc.) that initializer was supposed to `move_to` under the object's own signer.
- There is no way to un-self-own the object using the standard object API once this occurs (any subsequent transfer attempt targeting/for the object still requires walking or re-establishing ownership through the same broken chain in some flows, and no repair function exists in `object.move`/`code.move`/`init.move`).

This is a corruption of the "root owner" control field used specifically to gate code-object initialization/publish rights, leading to a non-recoverable loss of the ability to initialize or upgrade custody-relevant state at that address.

### Likelihood Explanation
Reaching the self-owned state requires only a single unprivileged, standard `object::transfer_call`/`object::transfer` where `to` equals the object's own address - no special privilege beyond being the current owner (which for a fresh code object is the deployer/`ConstructorRef` holder) is needed, and the framework's own test suite demonstrates this transfer succeeds today: [7](#0-6) 
The realistic trigger is either an owner mistake (accidentally passing the object's own address as the transfer destination) or a malicious/compromised frontend/dApp constructing a `transfer_call`/`upgrade`-adjacent transaction that sets `to == object address` for a code object whose owner is about to invoke `object_code_deployment::upgrade` or similar flows. Because the object owner still legitimately controls signing at that moment, this is not privilege escalation by a third party, but it is an easily-triggerable, code-level bug (missing the same guard present in sibling functions) that produces a permanent, non-recoverable custody freeze - which is why it is reported as a code root cause rather than "admin/owner mistake" alone.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING`-bounded loop protection used in `owns` and `verify_ungated_and_descendant` to `root_owner`, aborting with a clear error (e.g., `EMAXIMUM_NESTING`) instead of looping unboundedly:
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    let count = 0;
    while (is_object(obj_owner)) {
        count += 1;
        assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Additionally, consider disallowing an object from being transferred to its own address in `transfer_raw`/`verify_ungated_and_descendant` outright (reject `to == object`), since a self-owned object is a degenerate state with no legitimate use case and currently has no recovery mechanism once created.

### Proof of Concept
1. Deploy a code object and publish a package to it with the lazy-module-initialization feature enabled (`object_code_deployment::publish` / `resource_account`/object-based publishing flow), so that `code::publish_package` records `deploy_owner` via `object::root_owner()`.
2. As the object owner, call `object::transfer_call(owner, object_address, object_address)` (i.e., transfer the object to itself) - this succeeds today, as shown by the existing framework test: [8](#0-7) 
3. Attempt to upgrade the code object (`object_code_deployment::upgrade` → `code::publish_package_txn` → `code::publish_package`) or trigger any lazy self-init (`internal_maybe_initialize`) for a module at that address.
4. Both paths call `object::root_owner()` (directly in `code.move` line 183, or transitively via `init::assert_may_self_initialize` line 78), which now loops forever on the self-owned `ObjectCore`, exhausting gas and aborting every such transaction from then on - permanently locking the code object's upgrade/init capability.

Note: I was not able to execute this end-to-end in a live Move VM/gas-metered environment as part of this review; the analysis is based on static code reading of `object.move`, `code.move`, and `init.move` plus the framework's own existing unit test that confirms self-transfer succeeds (`test_cyclic_ownership_transfer_should_fail`, `test_cyclic_ownership_owns_should_fail`). Confirming the exact gas-exhaustion behavior and absence of any out-of-band recovery path would benefit from a Devin session with local test execution.

    /// gated: an object must still have the transitive root owner recorded for this module at
