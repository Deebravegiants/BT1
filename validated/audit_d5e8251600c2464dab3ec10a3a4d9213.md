This confirms the identity-binding gap. The `Registry.process` method verifies `Utils::HmacValidator.validate(request)` against `request.to_signable_string`, but `to_signable_string` returns only `@raw_body` [1](#0-0) . Meanwhile, `request.topic`, `request.shop`, `request.api_version`, and `request.webhook_id` — the fields actually acted upon by `Registry.process` and dispatched to the handler via `WebhookMetadata` — are all pulled from HTTP headers that are never included in the HMAC-signed payload [2](#0-1) [3](#0-2) .

### Title
Webhook tenant/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature exclusively to the raw request body, while the `shop`, `topic`, `webhook-id`, and `api-version` fields — used by `Registry.process` to route the webhook to a handler and to identify the tenant for the app's business logic — are read straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over that signable string and compares it against `request.hmac` (also read from a header) [4](#0-3) [5](#0-4) . Once the body-signature check passes, the code trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all derived from `shopify_header`, i.e. plain HTTP headers with zero cryptographic binding to the signature [2](#0-1) [6](#0-5) . These untrusted values are then forwarded into `WebhookMetadata` and handed to the app's registered handler for topic-specific business logic, which typically uses `shop` to select the tenant record to act on [7](#0-6) .

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed, an attacker who controls one shop installation of the app receives legitimately-signed webhook deliveries (signed by Shopify with the app-wide secret) for their own store. Since the signature never covers `shop-domain`, `topic`, or `webhook-id`, the attacker can capture one such valid `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop, or the `shopify-topic`/`shopify-webhook-id` headers rewritten to a different value, and the signature check in `Registry.process` still passes. This breaks the identity binding: `hmac(raw_body) == valid` should imply `shop == victim's actual originating shop`, but the code accepts `hmac(raw_body) == valid` and `shop == attacker-supplied header` as if they were the same statement.

### Impact Explanation
This allows cross-tenant confusion in webhook handling: an app's handler logic that keys off `WebhookMetadata#shop` (e.g., to look up and mutate per-merchant records, deactivate a subscription, or reset settings for "shop X") can be triggered by an attacker for an arbitrary victim shop domain, using only a webhook payload the attacker legitimately received for their own store. This maps to a cross-tenant access impact, since the app is induced to act on tenant data with no server-side proof that the payload actually originated for that tenant.

### Likelihood Explanation
Any developer/merchant who can install the app (a normal, unprivileged action) automatically becomes a source of validly-signed webhook payloads for their own shop, and the webhook endpoint is a public HTTP endpoint, so no additional privileges, credentials, or social engineering are required to attempt this replay/header-tamper.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed payload (i.e., extend `to_signable_string` to bind the header-derived identity fields, not just `@raw_body`), or independently authenticate/bind the shop domain against session/tenant records before dispatching to handlers, so that a signature valid for one shop's payload cannot be replayed against another shop's identity.

### Proof of Concept
```ruby
# Attacker installs the app on shop-a.myshopify.com and captures a legitimately
# signed webhook delivery for a topic they control, e.g. orders/create:
raw_body = '{"id":1,...}'                      # legitimate body Shopify sent them
valid_hmac = captured_headers["x-shopify-hmac-sha256"]  # valid signature for raw_body

# Attacker replays the exact same (raw_body, hmac) pair but swaps only the
# shop-domain header to the victim shop, and/or the topic/webhook-id:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,        # unchanged, still verifies against raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled value
  "x-shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# Utils::HmacValidator.validate(request) succeeds because it only checks raw_body,
# and the handler now receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
