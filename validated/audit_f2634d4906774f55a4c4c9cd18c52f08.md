## Finding [1](#0-0) 

### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable content for HMAC verification from the raw request body alone, while the shop identity used to attribute the webhook to a tenant is read from a separate, unsigned HTTP header. The HMAC therefore proves only that the body bytes are authentic; it proves nothing about which shop the body belongs to. Anyone who can obtain one valid `(body, hmac)` pair — trivially done by installing the app on a store they control — can replay that pair against the app's webhook endpoint with an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header, and `Registry.process` will accept it and hand the attacker-chosen shop to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Request#shop` is parsed independently from a header that is never mixed into that signable string: [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate` verifies the HMAC purely over `to_signable_string` (i.e., the raw body) against the app secret, and returns a boolean with no binding to `shop`: [5](#0-4) 

`Registry.process` uses that boolean check to gate processing, then forwards `request.shop` — the unauthenticated header value — straight into the handler as the tenant identity: [6](#0-5) 

This is the exact bug class described in the report: a value that is *acted on* (here, the tenant/shop binding used by the handler) is not covered by the integrity check (the HMAC), while a different, unrelated value (the raw body) is. Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** folded into `to_signable_string` and thus is cryptographically bound to the HMAC: [7](#0-6) 

The equality that should hold is: `shop_bound_by_HMAC == shop_acted_on_by_handler`. In `Webhooks::Request`, this is false — `shop_bound_by_HMAC` doesn't exist (only the body is bound), while `shop_acted_on_by_handler = header value`, which is fully attacker-controlled once a valid `(body, hmac)` pair is obtained for any shop.

### Impact Explanation
An unprivileged attacker can install the target app on a store they own (any internet user can do this for free), causing Shopify to deliver a legitimately signed webhook (`raw_body`, `hmac`) to them. The attacker then replays that exact body+HMAC to the victim merchant's app-hosted webhook endpoint, substituting the `shopify-shop-domain` header with the victim's shop domain. `HmacValidator.validate` still succeeds (it only checks the body against the secret), and `Registry.process` invokes the app's handler with `WebhookMetadata` claiming the victim's shop, causing the host application to process attacker-supplied data under the victim's tenant context — a cross-tenant data/identity confusion inside this gem's own verification and dispatch path. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app author who trusts `request.shop`/`WebhookMetadata#shop` as an authenticated tenant identifier (a reasonable assumption given it flows through the library's own `Registry.process` gate immediately after the HMAC check succeeds). No credentials, tokens, or privileged access are required — only the ability to install the app once on an attacker-controlled store to harvest one valid signed payload.

### Recommendation
Bind the shop identity (and other headers used for routing/attribution, e.g. `topic`, `webhook-id`) into the value that is HMAC-verified, or otherwise cryptographically/contextually tie `request.shop` to the verified body (e.g., cross-check it against a shop value embedded in the verified payload, or require callers to pass the expected shop and compare). At minimum, document that `request.shop` is unauthenticated and must not be used as a tenant boundary without additional verification, and consider raising in `Registry.process` if the header-derived `shop` cannot be corroborated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`. Shopify delivers a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret `S`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/registry.rb:190`).
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to act on attacker-controlled body content under the victim's shop identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
