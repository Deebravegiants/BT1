### Title
`begin_auth` fails to validate the `shop` host before redirecting the merchant browser and issuing the app's OAuth `client_id`/`redirect_uri`/`state` to it - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop` string without ever routing it through `ShopifyAPI::Utils::ShopValidator`, the module this gem ships specifically to confirm a `shop` value is a trusted Shopify host. Because `shop` at this stage of the flow carries no HMAC or other signature (the HMAC only appears later, on the callback), an unprivileged caller of the host application's login endpoint can supply an arbitrary host and have the app redirect the merchant's browser to it, carrying the app's public `client_id`, the constructed `redirect_uri`, and the freshly minted anti-CSRF `state` value.

### Finding Description
`begin_auth` takes `shop` as a plain `String` and passes it straight to `auth_base_uri(shop)`: [1](#0-0) 

`auth_base_uri` performs no domain allow-listing — it just interpolates the string into a URL: [2](#0-1) 

Compare this to the purpose-built `ShopifyAPI::Utils::ShopValidator`, which exists precisely to reject any `shop` value whose host is not one of the trusted Shopify domains (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`): [3](#0-2) 

`begin_auth` never calls `ShopValidator.sanitize!` (or `sanitize_shop_domain`) on `shop`. The `hmac`-based authenticity check in this gem is only applied later, to the *callback* query (`AuthQuery#to_signable_string` signs `code`, `host`, `shop`, `state`, `timestamp` and is validated in `validate_auth_callback`): [4](#0-3) [5](#0-4) 

So the identity binding that breaks is: *the `shop` host that `begin_auth` trusts enough to redirect the browser to (and disclose `client_id`/`redirect_uri`/`state` to) ≠ the `shop` host that is actually verified as a genuine Shopify domain.* The first `shop` value a merchant-facing app receives (typically from an unauthenticated `?shop=` query parameter on its own login route) is exactly the value fed into `begin_auth`, unauthenticated and unvalidated by this library.

### Impact Explanation
This matches the allowed "session fixation or forced OAuth completion" impact class: an attacker who controls where `begin_auth`'s `shop` value points can have the victim's browser sent to an attacker-controlled host carrying the app's `client_id`, the app's real `redirect_uri`, and the app-issued `state` nonce (which is also placed in a cookie on the victim's browser by the same response). Because the attacker's page now has the legitimate `redirect_uri` and `state`, they can drive their own, attacker-owned Shopify store through a real OAuth authorization (which they can trivially obtain, since they can install their own app on their own store) and redirect the browser back to the app's callback URL with the stolen `state`, causing the victim's app session to complete OAuth against the attacker's shop instead of the one the victim intended — a forced OAuth completion / session-fixation style attack. It does not, by itself, leak the app's `client_secret` (that is sent only during the HMAC-protected callback step) — the classification of Critical (credential theft) does not apply, but High (forced OAuth completion) does.

### Likelihood Explanation
Medium: it requires the host application to pass through an unauthenticated `shop` query parameter to `begin_auth` without its own validation — a common pattern for Shopify apps' login/entry routes (`GET /login?shop=...`) — and it requires the attacker to also control (or use) a real Shopify store to complete a legitimate authorize flow for a stolen `state`. This mirrors a well-known class of Shopify-app vulnerabilities that the shipped `ShopValidator` module is meant to prevent, but `begin_auth` does not use it.

### Recommendation
Sanitize `shop` at the very start of `begin_auth` using the library's own `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (raising `Errors::InvalidShopError` for anything that isn't a trusted Shopify domain) before it is used to build `auth_base_uri`/`auth_route`.

### Proof of Concept
1. Host application exposes `GET /login?shop=<value>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` — a pattern explicitly shown in this gem's own OAuth docs.
2. Attacker sends a victim merchant a link: `https://app.example.com/login?shop=evil-attacker.example.com`.
3. `begin_auth` builds `auth_route = "https://evil-attacker.example.com/admin/oauth/authorize?client_id=<real_client_id>&scope=...&redirect_uri=https://app.example.com/auth/callback&state=<nonce>&grant_options[]=..."` and sets the `state` cookie on the victim's browser, then redirects.
4. The attacker's server (posing as the OAuth authorize page) now has the app's real `client_id`, `redirect_uri`, and `state`.
5. The attacker performs a genuine OAuth authorization for their own real Shopify store and directs the victim's browser to `https://app.example.com/auth/callback?shop=attacker-store.myshopify.com&code=<real_code>&state=<stolen_state>&hmac=<valid_shopify_hmac>&timestamp=...`.
6. `validate_auth_callback` passes (the HMAC and `state` are both genuinely valid, since Shopify computed the HMAC for the attacker's own real store and the `state` matches the victim's cookie), and the victim's app session/cookie becomes bound to `attacker-store.myshopify.com` instead of the shop the victim intended to authorize — a forced OAuth completion.           state = SecureRandom.alphanumeric(NONCE_LENGTH)

            scope: scope.to_s,

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
