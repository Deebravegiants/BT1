### Title
Unvalidated swap routes can smuggle unauthorized token transfers into the caller's authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept caller-supplied `StrategySwap` bytes and forward them to the configured router after authorizing only the expected input-token transfer. Because those bytes can name an arbitrary pool/venue address, nested route code can execute attacker-controlled calls beneath the account owner's authorization. If simulation records and the user signs the resulting poisoned authorization tree, the nested contract can transfer unrelated wallet tokens to an attacker while still producing valid swap output.

### Finding Description
`swap_tokens` accepts non-empty `swap` bytes, snapshots balances, grants the configured router one exact `token_in.transfer(controller, router, amount_in)` invocation, and calls `router.execute_strategy(controller, amount_in, swap)` without constraining the contracts embedded in the route. [1](#0-0) 

The reachable controller operations include `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`; for example, `process_swap_collateral` authenticates the account owner or delegate, then passes the caller-provided `swap` object into `withdraw_and_swap_from_supply`. [2](#0-1) 

The router decodes the payload's caller-controlled `assets` registry and uses one element as the `pool` address for each swap hop. [3](#0-2) 

For a Soroswap-labelled hop, production code invokes `get_reserves` and `swap` on that payload-selected address, giving attacker-deployed code execution inside the transaction. [4](#0-3) 

The repository's threat model confirms there is no route-address allowlist and that a nested token transfer from the caller is recorded as a child of the caller's authorization entry. [5](#0-4) 

The included host-level test demonstrates that simulation records `token.transfer(alice, attacker, WALLET_BALANCE)` under Alice's `swap_collateral` authorization, and that signing that tree moves her entire unrelated wallet-token balance to the attacker. [6](#0-5) 

### Impact Explanation
An unprivileged attacker can steal arbitrary token balances from a strategy caller, including tokens unrelated to the lending position, by inducing the caller to submit a malicious route and sign the authorization tree returned by simulation. This is theft of user funds beyond the authorized swap input.

The attack does not require compromising governance, the pool, the controller, an oracle, or a token contract. The malicious component can be deployed by the attacker, while the fair output transfer allows all swap settlement and final account-risk checks to pass.

### Likelihood Explanation
Likelihood depends on a user consuming attacker-influenced route bytes and signing the authorization tree without decoding its nested calls. That is materially broader than a private-key or privileged compromise because route bytes are untrusted input supplied to strategy calls, and wallet or aggregator clients may present the top-level strategy while users do not inspect every recorded child invocation.

The attack is not fully unauthenticated: the victim must authorize the poisoned tree. Nevertheless, the route-selection flow creates the dangerous authorization, and the test proves both recording and enforcing behavior.

### Recommendation
Do not permit route payload bytes to select arbitrary executable pool addresses for externally invoked venue calls. Enforce a governance-managed venue/pool allowlist at the trust boundary, or encode only immutable venue identifiers whose contract addresses are resolved from protocol configuration.

Until route destinations are constrained, clients must simulate `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and direct `execute_strategy` transactions and reject any authorization tree containing children other than the explicitly expected input transfer. This client-side check should be treated as a temporary mitigation rather than the contract-level fix.

### Proof of Concept
The repository already contains a working reproduction in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice supplies USDC and holds `77_770_000_000` units of an unrelated token. [7](#0-6) 
2. The route names an attacker-deployed `hop_pool` while still paying the expected ETH output. [8](#0-7) 
3. During the nested hop, `RogueHopPool::swap` calls `wallet_token.transfer(alice, attacker, amount)`. [9](#0-8) 
4. Recording mode attaches that transfer beneath Alice's `swap_collateral` authorization, drains Alice's unrelated wallet token, and credits the attacker while the swap itself remains successful. [6](#0-5) 
5. In enforcing mode, the rogue transfer fails when omitted from the signed tree but succeeds when the simulated poisoned child is included. [10](#0-9)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
