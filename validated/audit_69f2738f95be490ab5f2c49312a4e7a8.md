### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identifier) is read directly from an HTTP header that is never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands the unauthenticated `shop` value straight to the app's webhook handler, so an attacker who can produce (or replay) one validly-signed body/HMAC pair for their own shop can relabel it for a victim shop and have the app act as if the event came from the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads the tenant identifier from the `shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string`, i.e. the raw body only: [3](#0-2) 

`Registry.process` checks only that the HMAC is valid, then immediately forwards `request.shop` (an unauthenticated header value) into `WebhookMetadata`, which is passed to the app's handler as the trusted tenant identifier: [4](#0-3) 

This is the same class of bug described in the external report: the value the code *acts on* (here, the shop the event is attributed to) is not the value that was actually *verified* (here, only the raw body bytes). The equality that should hold — "the shop the HMAC was computed for" == "the shop the handler receives" — is not enforced; the HMAC binds nothing about `shop`, `topic`, `webhook_id`, or `api_version`.

### Impact Explanation
Any entity that can obtain one genuinely Shopify-signed webhook delivery (which is trivial: create/own any shop that installs the app, or otherwise trigger any webhook topic on a shop you control) can capture the exact `raw_body` + `x-shopify-hmac-sha256` pair. They can then replay that identical body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different, victim shop domain that also has the app installed. `Registry.process` will validate the HMAC successfully (it only checks the body) and dispatch the event to the handler tagged with the victim's shop. Depending on what the host app does in its handler (e.g., `app/uninstalled` cleanup, `orders/create` processing, data sync keyed by shop), this enables cross-tenant data corruption, spoofed business events attributed to another merchant, or triggering destructive/administrative logic against a tenant the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
The precondition (owning/controlling any shop that can install the target app or otherwise receive one legitimately-signed webhook) is achievable by an unprivileged internet user — Shopify development stores are freely obtainable. No access token, `client_secret`, or leaked credential is required; only a single observed legitimate webhook body/signature pair for a topic that exists in the app is needed. The replay itself is a simple HTTP POST with a modified header, fully within the capability of an internet-based attacker.

### Recommendation
Bind the tenant/shop (and ideally topic, webhook id, api version) into the value that is cryptographically verified, or otherwise cross-check the header-derived `shop` against server-side state (e.g., confirm the shop is expected to be able to send this webhook, or include shop in the signed payload contract used by the app). At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a sole tenant-authorization key without additional verification, and consider having `Registry.process` require callers to supply/verify the expected shop before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (freely creatable dev store).
2. Attacker triggers a benign event (e.g., updates a product) causing Shopify to send a legitimately HMAC-signed webhook with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(B, client_secret)` to the app's webhook endpoint, with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same webhook endpoint but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (leaving `raw_body` and the HMAC header untouched).
4. `Utils::HmacValidator.validate(request)` returns `true` because the HMAC only covers `raw_body`, which is unchanged: [5](#0-4) 
5. `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the handler with `shop == "victim-shop.myshopify.com"`, causing the app to act on the victim's tenant using attacker-controlled body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
