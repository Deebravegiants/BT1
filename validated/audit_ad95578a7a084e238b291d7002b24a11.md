### Title
Unallowlisted route venues let attacker-supplied pool code run inside the victim's signed authorization tree, stealing wallet funds - (File: contracts/swap-aggregator/src/venues/mod.rs, dispatch_hop)

### Summary
CVE-2026-62902's class is "inclusion of functionality from untrusted control sphere": a parsed artifact pulls in attacker code that executes with the victim's trust. The XOXNO analog is the swap router's route payload: `StrategyPayload.assets` is a caller-supplied address registry, every swap instruction resolves its `pool` from that registry, and the router calls it with `env.invoke_contract` while the victim's `sender.require_auth()` is the root of the auth tree. There is no venue/pool allowlist, so an attacker-named contract runs inside the victim's authorized invocation and can attach `token.transfer(victim → attacker, X)` sub-invocations to the tree the victim signs.

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` decodes `StrategyPayload { amounts, assets, ops }` where `assets` is an arbitrary address list and `ops` indexes pools out of it (`contracts/swap-aggregator/src/types.rs`, `program.rs`). Dispatch calls `dispatch_hop`, which measures router balance deltas around `invoke_contract(&hop.pool, ...)`, e.g. `phoenix.rs` line 25, `comet.rs` lines 30-34, `sushi.rs` lines 20-50. The only auth is `sender.require_auth()` plus one nested `token_in.transfer(sender → router, total_in)` — the threat model states the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md`).

The same path is reachable through the controller: `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` forward a caller-provided `swap_xdr` to the configured aggregator after `caller.require_auth()` and `authorize_transfer_as_current`, so the victim's lending entrypoint is itself the auth root under which rogue pool code executes.

### Impact Explanation
Theft of user funds beyond the routed amount. A rogue "pool" contract's `swap` function executes `token::Client::new(victim_chosen_token).transfer(&victim, &attacker, &balance)`. That `require_auth` is recorded as a child of the victim's root entry in simulation; if the victim signs the simulated tree (the standard wallet flow), the transfer executes — draining any token the victim holds, not just the swap input. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: Alice's unrelated `WALLET_BALANCE` token moves to the attacker when the poisoned tree is signed, while neither the payload `min_out` nor the controller's post-swap risk gates bound it.

### Likelihood Explanation
Requires a victim to sign a route containing the attacker's pool — realistic via a malicious/compromised quote, phishing UI, or pasted `routeXdr`, since the route bytes are opaque XDR that honest simulation will faithfully wrap into the auth tree. No protocol privilege, timing, or price manipulation is needed; the attacker is a single unprivileged address deploying a contract and supplying a route. Severity is bounded by needing the victim's signature on the poisoned tree, so Medium rather than High.

### Recommendation
Maintain an owner-governed allowlist of venue pool addresses in the swap-aggregator and reject routes whose `assets` pool entries are not listed; alternatively have the controller constrain `swap_xdr` pools to venues it recognizes. Clients should also decode the signed auth tree and reject any sub-invocation beyond the single input transfer.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `UnlistedPoolRouter::execute_strategy` invokes the payload-named `hop_pool`; `RogueHopPool::swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)`. `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows the theft recorded under Alice's `swap_collateral` auth entry, and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows it executes when the simulated tree is signed — Alice's wallet balance goes to 0 while the swap itself produces a "fair" output and passes all controller checks.

Note: `docs/explanation/threat-model.md` (lines 154-165) already acknowledges this exposure and assigns the mitigation to clients ("a client must decode the route it signs"), so reviewers may treat it as a known, documented risk rather than a new finding.
