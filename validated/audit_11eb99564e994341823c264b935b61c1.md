### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body, while the `shop` value handed to the app's webhook handler is read directly from the unauthenticated `X-Shopify-Shop-Domain` header. Because the HMAC never binds the header to the body, an attacker can take a validly-signed webhook payload (obtained from their own, attacker-controlled shop installation of the app) and replay it against the app's webhook endpoint with an arbitrary `shop` header, causing the app to process the webhook as if it came from a different, victim tenant.

### Finding Description
The webhook signature check is implemented as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop` accessor is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (i.e. the body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates only this body HMAC, then forwards the *unverified* `request.shop` value straight into `WebhookMetadata` that is delivered to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_bound_by_hmac == shop_delivered_to_handler`

In reality:
`shop_bound_by_hmac` = ∅ (the HMAC certifies only the body bytes)
`shop_delivered_to_handler` = attacker-controlled header value

Since a single app has one `client_secret`/`api_secret_key` shared across *every* shop that installs it, any unprivileged user who installs the app on their own (attacker-controlled) shop can legitimately receive a body + HMAC pair signed with the app's secret. That attacker can then replay the exact same body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspected the header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the spoofed victim domain.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (or `Request#shop`) to decide which merchant's session/data/state to act on — e.g., looking up the victim's stored offline access token by shop domain, updating per-shop settings, or triggering per-shop side effects — can be tricked into acting on behalf of a shop the attacker does not control. This is a cross-tenant confused-deputy condition: an unprivileged actor forges the tenant identity of an otherwise correctly authenticated webhook delivery.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the same public/custom app on their own store (a normal, unprivileged action available to anyone who can add an app), (2) capturing one webhook delivery for a body they control, and (3) replaying it with a modified `shop` header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required — the `api_secret_key` is never exposed to the attacker, only its output (HMAC) for content they legitimately received.

### Recommendation
Do not treat `Request#shop` / `WebhookMetadata#shop` as authenticated by the HMAC check alone. Either:
- Bind the shop domain into the signed material (not possible without changing Shopify's webhook signing scheme, which signs body only), or
- Require/encourage host applications, and add gem-level guidance/checks, to cross-verify `request.shop` against an already-established, independently authenticated session/shop record before using it to select which tenant's data or credentials to act on, rather than trusting the header value as an implicit tenant identifier once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid HMAC of body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the raw body signature (`lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/request.rb#to_signable_string`).
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb#process`), and any host-app logic keyed off `shop` now operates under the victim's identity despite the request never being authenticated for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
