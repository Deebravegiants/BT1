### Title
Webhook HMAC does not bind the trusted `shop` (or `topic`/`webhook_id`) header, allowing tenant/topic spoofing in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` only proves that the body bytes were signed by the app's `client_secret` — it proves nothing about the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers. `Registry#process` nonetheless treats `request.shop` and `request.topic` as authenticated and forwards them unchanged as the tenant identifier and dispatch key to the host application's `WebhookHandler`.

### Finding Description
The equality the library implicitly claims to enforce is:
`hmac_valid(body, secret) ⇒ trust(shop_header, topic_header, webhook_id_header)`

But the actual signed string is only the body: [4](#0-3) 

And `shop`, `topic`, `webhook_id`, `api_version` are pulled straight from attacker-controllable HTTP headers with no cryptographic tie to the signature: [5](#0-4) 

`Registry.process` validates only the body HMAC, then immediately builds `WebhookMetadata` from these unauthenticated headers and hands them to the developer's handler as the routing/tenant key: [2](#0-1) 

Because `client_secret` (and thus the HMAC) is per-app, not per-shop, any merchant who has legitimately installed the app can capture one authentic webhook delivery (raw body + valid `X-Shopify-Hmac-Sha256`) from their own store, then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) for a victim shop. `HmacValidator.validate` will still pass because it only checks the body bytes against the secret, and the app's own webhook documentation instructs developers to trust `data.shop` as the identifying tenant for storage/lookup/enqueuing (`docs/usage/webhooks.md`, lines 12-29). This breaks the identity binding between the cryptographically-verified payload and the tenant/topic the application acts on — the exact bug class in the report (an owner/attacker able to substitute an unverified field before/around a signed operation).

### Impact Explanation
This falls under the "credential leakage / cross-tenant" bucket: an attacker (a merchant who installed the app, i.e., an "unprivileged internet user" relative to other tenants) can cause the host application to process a forged shop identity/topic combination with a validly-signed body, injecting spoofed or replayed webhook events attributed to a different shop. Depending on how a host app uses `data.shop` (e.g., to look up which shop's access token to use, or to write data keyed by shop), this can result in cross-tenant data corruption or actions being taken under another merchant's identity.

### Likelihood Explanation
Likelihood is moderate-to-high: no `access_token` or `client_secret` is needed by the attacker — only a valid webhook delivery from a shop the attacker legitimately controls (any developer/merchant installing the app can obtain one), which is then replayed with tampered headers against the app's public webhook endpoint. All identity/topic headers are demonstrated in tests to be freely supplied by the caller with no relationship to the signature (`test/webhooks/registry_test.rb` builds the HMAC solely from the body and independently sets the shop/topic headers).

### Recommendation
Include `shop`, `topic`, and `webhook_id` (at minimum `shop`) in the HMAC-signed payload verification, or otherwise cryptographically bind the header-derived identifiers to the signed body before trusting them in `WebhookMetadata`. Shopify's actual webhook signature does cover only the body by design, so the fix should be at the trust boundary: document/require that host apps must independently corroborate `shop` against their own session storage (e.g., verify the shop is a known installed shop) rather than treating the header as an authenticated value, or have the gem reject/flag `shop` values that were not part of the signed material when strict verification is required.

### Proof of Concept
```ruby
# Attacker owns shop A, installed the app, and receives one legitimate webhook:
raw_body = '{"id":123}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
# (This is the exact signature Shopify would have sent to the app for shop A's webhook)

# Attacker replays the same body+hmac but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, not covered by hmac
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) returns true (body+secret match),
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)) is invoked,
# even though Shopify never actually sent a webhook for victim-shop with this content.
```
