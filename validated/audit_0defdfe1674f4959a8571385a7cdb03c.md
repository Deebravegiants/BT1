### Title
Webhook Shop Domain and Topic Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC signature over the raw request body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted and passed unauthenticated into the webhook handler. This breaks the intended binding `HMAC-verified bytes == all data attributed to the webhook`, allowing an attacker who possesses any single genuine `(body, hmac)` pair from Shopify (trivially obtainable by installing the app on their own store) to replay that pair against the same endpoint with a forged `shop-domain` header, causing the app to process attacker-supplied body content under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is read straight from the `hmac-sha256` header: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that the computed HMAC of `to_signable_string` (i.e. the raw body) matches the supplied `hmac`: [3](#0-2) 

However, `Webhooks::Registry.process` uses `request.topic` and `request.shop` — both taken directly from unauthenticated headers — to route the request to a handler and to construct the `WebhookMetadata` passed to application code: [4](#0-3) 

The identity binding that should hold is: `shop attributed to this webhook == shop that Shopify actually generated the HMAC for`. Because `shop`, `topic`, `webhook-id`, and `api-version` are not part of the signable string, this equality is never checked — only the body's integrity is checked, not its provenance/context (which shop and topic it belongs to).

### Impact Explanation
An attacker can install the target app on their own (freely creatable) Shopify development store, trigger a webhook of a chosen topic, and capture the genuine `(raw_body, x-shopify-hmac-sha256)` pair Shopify sends to the app's public webhook endpoint — no `api_secret_key`, access token, or victim credentials are needed. The attacker then replays that exact body/HMAC pair to the same public endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes, so `Registry.process` dispatches attacker-controlled body content into the handler tagged as if it originated from the victim shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the victim's stored session/access token to fetch or act on further data, or to write attacker data into the victim's per-shop store), this enables cross-tenant data injection/confusion.

### Likelihood Explanation
Exploitation requires only the ability to install the app on any store (including a free development store) and to send an HTTP POST to the app's own public webhook endpoint — both of which are available to any unprivileged internet user with no leaked secrets, tokens, or social engineering required.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers in the signable string used by `HmacValidator`, so the HMAC covers everything the application acts upon, or otherwise cryptographically bind the shop/topic to the request before dispatching to handlers. At minimum, `WebhookMetadata#shop` should not be trusted unless it is confirmed to correspond to a shop with an active app session/installation, and should not be usable to select victim-specific behavior without independent verification.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (self-controlled store) and trigger any webhook topic (e.g. `orders/create`).
2. Capture the resulting POST request to the app's webhook endpoint, including `x-shopify-hmac-sha256` and the raw body.
3. Replay the identical body and `x-shopify-hmac-sha256` header to the same endpoint, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic` unchanged or altered to another registered topic.
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13) returns `true` because it only recomputes HMAC over the untouched raw body.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the application to process attacker data under the victim shop's identity.
