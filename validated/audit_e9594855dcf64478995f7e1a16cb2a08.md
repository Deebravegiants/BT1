### Title
Unauthenticated `address` field in `pallet-state-coprocessor::handle_unsigned` lets any submitter divert relayer reputation and fee-receipt credit to an arbitrary account - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`pallet-state-coprocessor`'s `handle_unsigned` extrinsic processes a `GetRequestsWithProof` payload containing an `address: Vec<u8>` field described as "Address that should be credited with fees." [1](#0-0)  Unlike the sibling `pallet-messaging-incentives`, which cryptographically recovers the relayer's account from a signature embedded in the message before minting reputation [2](#0-1) , `handle_get_requests` mints reputation and records the response receipt using the caller-supplied `address` with no signature or authorization check binding it to whoever actually produced/verified the proof. This is the same root-cause pattern as the reported `notifyFor` bug: a state-mutating, unprivileged entry point takes a "credit this account" parameter that is never validated against the actual acting party, so any caller can redirect rewards to any address of their choosing.

### Finding Description
`handle_unsigned` is a `ensure_none` (unsigned, permissionless) extrinsic: [3](#0-2)  `validate_unsigned` re-executes `handle_get_requests` for mempool admission and computes the "provides" dedup tag purely from the hash of the `requests` (Get request contents), not from `address`: [4](#0-3) 

Inside `handle_get_requests`, after verifying the source membership proof and destination state proof (the legitimate, expensive "work" being rewarded), the pallet mints `messaging_incentives` reputation directly to whatever 32-byte `address` was supplied in the message, with no check that this address corresponds to the entity that produced the state proof, submitted the transaction, or has any relationship to the request at all: [5](#0-4) 

The same untrusted `address` is also persisted as the attributed relayer on the response receipt and event: [6](#0-5) [7](#0-6) 

Because the request/response proofs themselves are public, deterministic pieces of state (verifiable membership/state proofs against already-committed roots), an attacker does not need to do anything beyond copying a `GetRequestsWithProof` message circulating in the transaction pool (or reconstructing one from public chain state) and resubmitting it with `address` set to their own account. Since the mempool "provides" dedup tag depends only on the request hashes and not on `address`, an attacker's copy directly competes with the legitimate submitter's transaction for inclusion — whichever lands first wins the mint, exactly mirroring how `notifyFor` let anyone force a credit update using the wrong principal (`balanceOf(msg.sender)` instead of `balanceOf(account)`).

### Impact Explanation
Successful exploitation lets an unprivileged party permanently and repeatedly redirect `MintPerByte`-rate reputation-asset mints (a real fungible asset minted via `T::ReputationAsset::mint_into`) away from the relayer that actually performed the verification work, to any address of the attacker's choosing — including themselves — for zero real relaying effort beyond copying already-broadcast proof data. This is an unbacked/arbitrary mint of a protocol-tracked reward asset to an attacker-controlled account and a permanent loss of earned reward for the legitimate relayer, satisfying the "unbacked mint" / "theft of relayer reward accounting" impact class.

### Likelihood Explanation
High for any chain running `pallet-state-coprocessor` with a non-zero `MintPerByte` rate: the attack requires no special privileges, only observing a pending/gossiped `handle_unsigned` extrinsic (or reconstructing an equivalent proof once the underlying commitments are public) and resubmitting it with a modified `address`, which is a pure client-side, always-available action (front-running by any full node or mempool observer).

### Recommendation
Bind the credited `address` to a value that is cryptographically or structurally guaranteed to represent the actual submitter/verifier — e.g., recover it from a signature over the message contents (as `pallet-messaging-incentives::relayer_for` already does), or derive it from the transaction's signed origin instead of accepting it as an unauthenticated field of the unsigned payload. Alternatively, remove reputation/fee-credit attribution from this permissionless path entirely and route it exclusively through the signed relayer-fee flow.

### Proof of Concept
1. Governance sets `pallet_messaging_incentives::MintPerByte` to a non-zero rate (normal operation).
2. Relayer R constructs and broadcasts a valid `GetRequestsWithProof { requests, source, response, address: R }` via `handle_unsigned`.
3. Attacker A observes this pending extrinsic in the gossip/mempool, copies `requests`/`source`/`response` verbatim (all publicly verifiable data), and resubmits `GetRequestsWithProof { requests, source, response, address: A }`.
4. Both transactions hash to the same `provides` tag (`impls.rs` hash is over `requests` only, not `address`), so they compete for block inclusion; whichever is included first calls `handle_get_requests`, which mints reputation to `address` — `A` — via `ReputationAsset::mint_into` at `impls.rs` line 172, per [8](#0-7) .
5. R's original transaction, once it reaches the pool, is rejected as a duplicate (same `provides` tag already consumed), so R never receives the reward despite having verified the underlying source/response proofs first.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
