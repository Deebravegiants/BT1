### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant identifier) is read from a separate, unsigned HTTP header. Any party capable of replaying a genuinely-signed webhook body (e.g. a legitimate merchant who received a real webhook for their own shop) can swap the `shop-domain`/`x-shopify-shop-domain` header value to claim the payload belongs to a different shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it because HMAC validation never inspects the header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac` (also derived from headers), but never binds the `shop` value into the signed material: [3](#0-2) 

`Registry.process` trusts the HMAC check and then dispatches to the app's handler using `request.shop` taken straight from the unauthenticated header: [4](#0-3) 

The binding that should hold is: `shop` value trusted by the handler == `shop` value cryptographically bound to the signed payload. Because the HMAC only signs `@raw_body`, this equality is not enforced — `shop` can be swapped independently of the signature that authenticates the body.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery. An attacker who is a merchant on shop A (and therefore legitimately receives HMAC-valid webhooks addressed to their own app installation) can take a body+HMAC pair they legitimately received and resubmit it to the app's webhook endpoint with the `shop-domain` header changed to shop B. `ShopifyAPI::Webhooks::Registry.process` will pass HMAC validation (since only the body is checked) and will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop B, causing shop A's webhook body to be processed as though it originated from and pertains to shop B. Depending on how the host application uses `data.shop` (e.g., to look up the shop's stored session/access token, or to attribute the payload to a tenant record), this can lead to cross-tenant data corruption, incorrect authorization decisions, or the app taking the wrong action against the wrong merchant's data — a cross-tenant access violation.

### Likelihood Explanation
No secret or privileged access is required beyond being an ordinary merchant/installer of the app on any shop — a capability freely available to any unprivileged internet user who installs a public app. The attacker only needs to capture one legitimately delivered webhook (trivial, since apps commonly log/inspect webhook bodies) and replay it with a modified header value; no cryptographic material needs to be forged.

### Recommendation
Include the shop identifier (and any other fields the app relies on for tenant attribution, such as topic/api-version if security-relevant) inside the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the payload before trusting it. At minimum, `Request#to_signable_string` should not be the sole authentication mechanism for a value that is read from a separate, unsigned header and then used as the tenant key for dispatch.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker-shop.myshopify.com`, and receives a legitimate webhook with a valid `x-shopify-hmac-sha256` header computed over the raw body `{"foo":"bar"}`.
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates the (unchanged) raw body against the (unchanged) HMAC — the modified `shop` header is never checked.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.
