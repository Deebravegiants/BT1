Audit Report

## Title
Cross-workflow response cache confusion via workflow-owner-scoped-only cache key - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's `responseCache` used for HTTP-action outbound responses keys cache entries solely by `gateway.OutboundHTTPRequest.Hash()`, which the package's own test suite confirms includes `WorkflowOwner` but explicitly excludes `WorkflowID`. This contradicts the component's documented design ("Cache Key: Generated from workflow ID and request hash" / "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" in the README), and allows two distinct workflows sharing the same `WorkflowOwner` to collide on a cache entry if they issue HTTP actions with identical method/URL/headers/body.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` use `req.Hash()` as the sole cache key: [1](#0-0) [2](#0-1)  The struct comment states the hash covers "method, URL, headers, body, workflowOwner" — notably omitting `WorkflowID`: [3](#0-2) 

The package's own test explicitly proves that differing `WorkflowID` produces the *same* hash, while differing `WorkflowOwner` produces a different hash: [4](#0-3) [5](#0-4)  This directly contradicts the handler's own README claim that "Cache Key: Generated from workflow ID and request hash" and "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage": [6](#0-5) 

The cache is invoked from `makeOutgoingRequest`, which is the single dispatch path handling all outbound HTTP-action requests for the gateway node, with no code path that further namespaces the cache by `WorkflowID`: [7](#0-6)  I was unable to find any additional workflow-ID-based partitioning of the `responseCache` instance elsewhere in `http_handler.go` (no `WorkflowOwner`/`WorkflowID` references found there beyond the request struct fields themselves), which is consistent with the map being globally shared across all workflows processed by the same gateway node/handler instance.

Because `Hash()` is implemented in the external `chainlink-common` module (`github.com/smartcontractkit/chainlink-common/pkg/types/gateway`) and not in this repository, I could not directly inspect its source in this repo, but its documented and tested behavior (as verified through the local test file `response_cache_test.go`, which exercises the real dependency) is unambiguous and directly demonstrates the vulnerable behavior.

## Impact Explanation
This is a genuine data-isolation defect matching the "cross-user response corruption" impact category: any actor operating (or later redeploying) multiple workflows under one `WorkflowOwner` address can cause one workflow's cached HTTP response to be silently substituted into a sibling workflow's execution whenever the request shape (method/URL/headers/body) coincides, for up to `OutboundRequestCacheTTLMs` (default 10 minutes). Since workflow HTTP actions can feed decision logic or trigger fund movement/job execution, this substitution is a real data-integrity break, not merely cosmetic, and it is caused entirely by this repo's cache-key design decision (using `Hash()` without adding `WorkflowID`), not by any external/malicious-node behavior.

## Likelihood Explanation
The precondition — multiple workflows registered under the same `WorkflowOwner` — is a normal, unprivileged, permission-free workflow-authoring scenario (one EOA can own many workflows). No operator, admin, or host access is required, and the behavior is deterministically reproducible and already covered/verified by the repository's own test suite (`TestRequestHash`), which is strong evidence this is real, current runtime behavior rather than a hypothetical or previously acknowledged/fixed issue.

## Recommendation
Include `WorkflowID` (and ideally `WorkflowExecutionID` for per-execution isolation) as part of the cache key — either by updating `OutboundHTTPRequest.Hash()` in `chainlink-common` to incorporate `WorkflowID`, or by having `responseCache` compose its map key as `req.WorkflowID + ":" + req.Hash()` in `response_cache.go`, so implementation matches the README's documented "workflow-scoped caching" guarantee.

## Proof of Concept
1. Register two workflows `wfA` and `wfB` under the same `WorkflowOwner` address on the same gateway node.
2. `wfA` issues an HTTP action `GET https://example.com/api` with `CacheSettings.Store=true`; gateway executes it and caches the response via `responseCache.Set`/`Fetch` keyed by `req.Hash()`.
3. Within `CacheSettings.MaxAgeMs`, `wfB` issues an identical `GET https://example.com/api` HTTP action (same method/URL/headers/body, same owner, different `WorkflowID`).
4. Per `makeOutgoingRequest` → `responseCache.Fetch`, `wfB` receives `wfA`'s cached response without the gateway executing `wfB`'s own request.
5. This is directly provable as a unit test: extend `response_cache_test.go`'s `TestFetch` to call `cache.Fetch` twice with two `OutboundHTTPRequest` values that differ only in `WorkflowID`, and assert the second call returns the first's cached response without invoking a fresh `fetchFn` — which follows directly from the existing `TestRequestHash` assertion that `WorkflowID` does not affect `Hash()`.

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
