Confirmed. The `ShopifyAPI::Webhooks::Request` class computes its HMAC only over `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers that are never included in the signed content [2](#0-1) . `Registry.process` validates only this body-derived HMAC and then hands the header-derived `shop` straight to the app's webhook handler [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify with the app's secret — it proves nothing about the `x-shopify-shop-domain` (or `topic`/`webhook-id`) headers, which are read straight from the request with no cryptographic binding [4](#0-3) . `Registry.process` trusts `request.shop` as the tenant identity after only checking the HMAC over the body [5](#0-4) .

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook == shop the HMAC signature actually authenticates`. Because `to_signable_string` signs only `raw_body`, this equality does not hold — the HMAC authenticates *content*, not *origin/tenant*. Any party who legitimately receives one valid Shopify webhook (e.g., a merchant/developer installing the app on their own store, who can trivially trigger webhooks like `orders/create` on their own shop) obtains a `(raw_body, hmac)` pair that is valid forever for that exact body under the app's secret. They can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a different, victim shop that is also installed on the same app. `HmacValidator.validate` still returns `true` because the body/signature pair is unmodified and valid, and `Registry.process` then invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is the attacker-controlled, unauthenticated header value [6](#0-5) .

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: an unprivileged attacker (any merchant able to install the app and generate one legitimate webhook from their own store) can make the host application process attacker-chosen body content under a victim shop's identity, since the only authenticated field is the body, not the shop. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up which tenant's DB row/session to update), this can lead to cross-tenant data corruption or data leakage — matching the "Critical: cross-tenant access" impact category, since the binding between authenticated bytes and the shop identity is exactly what's broken.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that installs on multiple shops: the attacker only needs their own (real) install of the target app to harvest one valid `(body, hmac)` pair per topic they care about, then replay it with a forged `shop-domain` header against the same public webhook endpoint. No secret, token, or privileged access is required — only normal, self-service app installation, which is within the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed content, or otherwise cryptographically bind `request.shop` to the verified payload before it is trusted. At minimum, `Utils::VerifiableQuery`/`to_signable_string` for `Webhooks::Request` should incorporate the shop header (and other identity-bearing headers) into the signable string so `HmacValidator.validate` actually authenticates the tenant, not just the body bytes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker replays this exact body + HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (a shop also installed on the same app).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature matches `@raw_body`, which was never modified [7](#0-6) .
4. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's data>, ...)` [6](#0-5) , causing the host application to process attacker-supplied data as if it originated from the victim's store.
