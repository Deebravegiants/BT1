### Title
Non-embedded `current_session_id` trusts a raw, unsigned, deterministically-forgeable cookie value as the session id - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`current_session_id` in the non-embedded (and JWT-fallback) branch returns whatever string is present in `cookies[SessionCookie::SESSION_COOKIE_NAME]` with zero cryptographic validation. Because `offline_session_id(shop)` is just `"offline_#{shop}"` — a pure, secret-independent function of a public shop domain — and this is exactly the value the gem sets as that cookie's value in `Oauth.validate_auth_callback`, any party who can place an arbitrary `Cookie` header on a request to the host app (which requires no browser, no XSS, and no relationship to the real merchant) can present `offline_<victim-shop>.myshopify.com` and have the host app treat it as an authenticated session id.

### Finding Description
The broken binding: the code assumes `cookie_value == "a value only obtainable by completing this exact browser's real OAuth/session flow"`, but in fact `cookie_value == offline_session_id(shop) == "offline_#{shop}"`, a value fully computable by anyone who knows `shop` (a public domain string), with no HMAC, nonce, or secret involved anywhere in its construction.

Code path:
- `SessionUtils.current_session_id(shopify_id_token, cookies, online)` — for `Context.embedded? == false`, or for embedded apps falling back when no `shopify_id_token` is present — does: `raise ... unless cookies[SESSION_COOKIE_NAME]` then `cookie_session_id(cookies)` which is literally `cookies[SESSION_COOKIE_NAME]` [1](#0-0) , [2](#0-1) . This is a raw hash read from the caller-supplied cookie map — no signature, no MAC, no comparison against anything derived from `Context.api_secret_key`.
- The value that gets placed into this cookie by the gem itself, in `Oauth.validate_auth_callback`, for non-embedded apps, is `session.id` [3](#0-2) , and for offline sessions `session.id` is built from `offline_session_id(shop) == "offline_#{shop}"` [4](#0-3) , ` [5](#0-4) `.
- Root cause: the "session id" used both as the storage key and as the bearer value transmitted in a cookie is a deterministic, public-input function (`"offline_" + shop_domain`), with no per-installation secret mixed in anywhere in `session_utils.rb`. Any code path that reads this cookie (`current_session_id`) simply echoes it back as "the session id" with no cryptographic binding to the party who actually completed OAuth.
- Attacker's exact request: send an HTTP request directly to any endpoint on the host app that calls `current_session_id(nil, cookies, false)` (the non-embedded path or the embedded fallback path), with header `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com`. If the host app then does `SessionStorage.load_session(id)` (the documented pattern in `docs/usage/oauth.md`) and finds a previously-stored real session for that shop (created when the actual merchant installed the app), the attacker's request is now treated as authenticated for that shop and the attacker can drive API calls using that shop's real offline `access_token`.
- Why guards don't stop this: `HmacValidator.validate` and the OAuth `state` comparison only protect the OAuth callback itself, not this cookie-read path; `Context.embedded?`/`private?` gate which branch runs but not the trustworthiness of the cookie value; `JwtPayload`'s `aud` check only applies to the JWT branch, which is bypassed entirely when no `shopify_id_token` is supplied; nothing in `session_utils.rb` uses `Context.api_secret_key` on this path at all, confirming the premise that offline session derivation is fully secret-independent.

### Impact Explanation
Any attacker who knows a target shop's `.myshopify.com` domain (public information, easily discoverable) and who can reach the host app's endpoints can construct the exact cookie value used to key that shop's stored offline session, and use it to have the app's session-lookup logic resolve to that shop's real `access_token`. This is a cross-tenant authentication bypass leading to theft/use of another merchant's offline access token — Critical, matching "theft or exfiltration of a merchant access token" and "cross-tenant access." It is fully repeatable against any shop that has ever completed OAuth with the app, requiring only the shop's domain name each time.

### Likelihood Explanation
Preconditions: the host app must be non-embedded (or embedded with the id-token fallback path reachable), must implement session storage keyed by this session id string as documented, and the target shop must have already completed OAuth with the app once (a real merchant installation, independent of the attacker). Given those (standard, documented) conditions, attacker cost is minimal — no credentials, no browser, no XSS, just one crafted HTTP request with a forged `Cookie` header containing a value computed from public information. This is highly feasible and trivially repeatable across shops.

### Recommendation
Do not use a deterministic, publicly-derivable string as both the session storage key and the literal bearer value transmitted via cookie. Bind the cookie value to something unforgeable: e.g., store the deterministic id server-side but never echo it into an unsigned cookie, or wrap/sign the cookie value with an HMAC keyed by `Context.api_secret_key` (or rely on the host framework's signed/encrypted cookie jar) and verify that signature in `current_session_id` before trusting the extracted id. At minimum, document/enforce that hosts must use a signed cookie jar, and consider adding integrity verification for the offline cookie path inside `session_utils.rb` itself so the gem does not depend entirely on host-framework hygiene it cannot verify.

```ruby
# test/utils/session_utils_forged_cookie_test.rb (proof-of-concept sketch)
require "test_helper"

class SessionUtilsForgedCookieTest < Test::Unit::TestCase
  def test_offline_session_id_is_pure_and_secret_independent
    shop = "victim-shop.myshopify.com"
    # No Context.api_secret_key involved anywhere in this computation.
    forged_id = ShopifyAPI::Utils::SessionUtils.offline_session_id(shop)
    assert_equal("offline_victim-shop.myshopify.com", forged_id)
  end

  def test_forged_cookie_is_accepted_as_valid_session_id_non_embedded
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Context.stubs(:embedded?).returns(false)

    victim_shop = "victim-shop.myshopify.com"
    forged_cookie_value = ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop)

    cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

    resolved_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

    # Binding under test: resolved_id should require proof of prior legitimate
    # authentication/possession, not merely knowledge of `shop`.
    assert_equal(forged_cookie_value, resolved_id)
    assert_equal("offline_#{victim_shop}", resolved_id)
    # No HMAC/secret was consulted to accept this id, demonstrating the
    # secret-independent forgery of the offline session id.
  end
end
```
This demonstrates: (1) `offline_session_id` is a pure function requiring no secret, and (2) `current_session_id` accepts that value directly from an attacker-suppliable `cookies` hash with no cryptographic check, confirming the finding.
