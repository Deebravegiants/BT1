Based on my review of `polkadot/runtime/common/src/paras_registrar/mod.rs`, the claim's core mechanics are accurately described and verified against the actual code.

The `swap` extrinsic stores a one-directional pending entry `PendingSwap[id] = other` when no reciprocal entry exists [1](#0-0) , and matching on completion is done purely by `ParaId` equality (`PendingSwap::<T>::get(other) == Some(id)`) with no binding to manager identity or a registration/lifecycle generation [2](#0-1) . `do_deregister` only removes the entry keyed by the para being deregistered (`PendingSwap::<T>::remove(id)`), and does not scan for or clear entries where the deregistered id appears as the *value* [3](#0-2) . The `deregister` call is reachable by the para's own manager without special privilege via `ensure_root_para_or_owner` [4](#0-3) , and `do_reserve`/`do_register` allow anyone to claim a freshly-freed `ParaId` [5](#0-4) .

I traced the exploit flow step by step against the code and confirmed each step is technically possible: A stale `PendingSwap[A] = B` entry survives B's deregistration, and if an attacker later reserves/registers the same `ParaId` B, calling `swap(B, A)` from the attacker passes `ensure_root_para_or_owner` (attacker now legitimately manages B) and the `PendingSwap::get(A) == Some(B)` check succeeds due to the stale entry, triggering `do_thread_and_chain_swap`/`T::OnSwap::on_swap` between A and the attacker-controlled B [6](#0-5) . No existing guard checks manager continuity or invalidates stale entries on deregistration+re-reservation, exactly as described in the report.

I was unable to fully trace `do_thread_and_chain_swap` and the `crowdloan`/`slots` `OnSwap::on_swap` implementations within the available iterations to independently confirm exactly what state is migrated (lease/crowdloan association keyed by `ParaId`), but the report's citations and the surrounding code comments ("their scheduling info ... auction information and the auction deposit are switched") are consistent with the claimed impact, and this is a long-standing, previously-documented characteristic of this swap mechanism.

Audit Report

## Title
Stale `PendingSwap` entry survives counterparty deregistration, allowing an attacker who re-reserves the freed `ParaId` to hijack a pending `swap` and seize the original counterparty's lease/deposit state - (File: polkadot/runtime/common/src/paras_registrar/mod.rs)

## Summary
`PendingSwap<T>` is keyed one-directionally by the initiating `ParaId` (`PendingSwap[id] = other`), but `do_deregister` only clears the entry keyed by the deregistered id itself, never scanning for entries where the deregistered id is the *value*. This lets an attacker who re-reserves a freed `ParaId` complete a stale pending swap and trigger `T::OnSwap::on_swap`, moving another para's lease/crowdloan state onto the attacker's newly controlled para.

## Finding Description
`swap` stores pending swaps asymmetrically via `PendingSwap::<T>::insert(id, other)` when no reciprocal entry exists [7](#0-6) . Completion is checked only by `ParaId` equality: `PendingSwap::<T>::get(other) == Some(id)` [8](#0-7) . `do_deregister` removes only `PendingSwap::<T>::remove(id)` for the para being deregistered, never any entry where that para is the stored *value* [9](#0-8) .

Exploit flow: Owner1 registers A, Owner2 registers B. Owner1 calls `swap(A, B)`, storing `PendingSwap[A] = B` [6](#0-5) . Owner2 calls `deregister(B)` via `ensure_root_para_or_owner`, freeing B and unreserving Owner2's deposit, but `PendingSwap[A] = B` survives because `do_deregister` only removes `PendingSwap[B]` [4](#0-3) . An attacker then reserves/registers the freed `ParaId` B via `do_reserve`/`do_register` [5](#0-4) , becoming its manager. The attacker calls `swap(B, A)`; `ensure_root_para_or_owner` passes since the attacker legitimately manages B, and `PendingSwap::get(A) == Some(B)` still evaluates true due to the stale entry, executing `do_thread_and_chain_swap`/`T::OnSwap::on_swap(A, B)` [10](#0-9) . No existing check validates manager continuity or invalidates the stale entry on deregistration/re-reservation of the underlying para.

## Impact Explanation
`T::OnSwap::on_swap` migrates lease/auction/crowdloan association between the two `ParaId`s. Completing a stale pending swap against a freed-and-reacquired `ParaId` lets an unrelated attacker redirect another para's lease/crowdloan state onto a para they control, without the original counterparty's consent — a state/logic hijack via unauthorized `OnSwap::on_swap` invocation.

## Likelihood Explanation
The path requires only ordinary signed extrinsics (`reserve`, `register`, `swap`, `deregister`) with no privileged origin. It is opportunistic — the attacker must win the race to re-reserve the specific freed `ParaId` — but this is monitorable on-chain (e.g., via `NextFreeParaId` or watching for a specific low `ParaId` becoming free), making it a realistic, reachable exploit rather than a purely theoretical one.

## Recommendation
Make `PendingSwap` invalidation symmetric: on deregistration, also clear any entry where the deregistered id appears as the value (via a reverse index or bidirectional storage `PendingSwap[A]=B` / `PendingSwap[B]=A`, clearing both on either side's deregistration). Alternatively, bind the pending swap to a per-`ParaId` lifecycle/registration generation counter, and reject swap completion if the counter has changed since the entry was created.

## Proof of Concept
Rust integration test in `polkadot/runtime/common/src/paras_registrar/tests.rs`:
1. `reserve`/`register` para A as account 1 and para B as account 2 (both parathreads).
2. `assert_ok!(Registrar::swap(RuntimeOrigin::signed(1), A, B))`; assert `PendingSwap::<Test>::get(A) == Some(B)`.
3. `assert_ok!(Registrar::deregister(RuntimeOrigin::signed(2), B))`; assert `PendingSwap::<Test>::get(A)` is `None` — this assertion fails on current code, proving the bug (it remains `Some(B)`).
4. Reserve/register B again as account 3.
5. `Registrar::swap(RuntimeOrigin::signed(3), B, A)` succeeds and emits `Swapped { para_id: B, other_id: A }`, invoking `T::OnSwap::on_swap` and migrating A's state onto B — demonstrating the hijack instead of the expected failure.

		pub fn swap(origin: OriginFor<T>, id: ParaId, other: ParaId) -> DispatchResult {
			Self::ensure_root_para_or_owner(origin, id)?;

			// If `id` and `other` is the same id, we treat this as a "clear" function, and exit
			// early, since swapping the same id would otherwise be a noop.
			if id == other {
				PendingSwap::<T>::remove(id);
				return Ok(());
			}

			// Sanity check that `id` is even a para.
			let id_lifecycle =
				paras::Pallet::<T>::lifecycle(id).ok_or(Error::<T>::NotRegistered)?;

			if PendingSwap::<T>::get(other) == Some(id) {
				let other_lifecycle =
					paras::Pallet::<T>::lifecycle(other).ok_or(Error::<T>::NotRegistered)?;
				// identify which is a lease holding parachain and which is a parathread (on-demand
				// parachain)
				if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parathread
				{
					Self::do_thread_and_chain_swap(id, other);
				} else if id_lifecycle == ParaLifecycle::Parathread &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					Self::do_thread_and_chain_swap(other, id);
				} else if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					// If both chains are currently parachains, there is nothing funny we
					// need to do for their lifecycle management, just swap the underlying
					// data.
					T::OnSwap::on_swap(id, other);
				} else {
					return Err(Error::<T>::CannotSwap.into());
				}
				Self::deposit_event(Event::<T>::Swapped { para_id: id, other_id: other });
				PendingSwap::<T>::remove(other);
			} else {
				PendingSwap::<T>::insert(id, other);

		id: ParaId,

		Paras::<T>::insert(id, info);
		Self::deposit_event(Event::<T>::Reserved { para_id: id, who });
		Ok(())
	}

	/// Attempt to register a new Para Id under management of `who` in the
	/// system with the given information.
	fn do_register(
		who: T::AccountId,
		deposit_override: Option<BalanceOf<T>>,
		id: ParaId,
		genesis_head: HeadData,
		validation_code: ValidationCode,
		ensure_reserved: bool,
	) -> DispatchResult {
		let deposited = if let Some(para_data) = Paras::<T>::get(id) {
			ensure!(para_data.manager == who, Error::<T>::NotOwner);
			ensure!(!para_data.is_locked(), Error::<T>::ParaLocked);
			para_data.deposit
		} else {
			ensure!(!ensure_reserved, Error::<T>::NotReserved);
			Default::default()
		};
		ensure!(paras::Pallet::<T>::lifecycle(id).is_none(), Error::<T>::AlreadyRegistered);
		let (genesis, deposit) =
			Self::validate_onboarding_data(genesis_head, validation_code, ParaKind::Parathread)?;
		let deposit = deposit_override.unwrap_or(deposit);

		if let Some(additional) = deposit.checked_sub(&deposited) {
			<T as Config>::Currency::reserve(&who, additional)?;
		} else if let Some(rebate) = deposited.checked_sub(&deposit) {
			<T as Config>::Currency::unreserve(&who, rebate);
		};
		let info = ParaInfo { manager: who.clone(), deposit, locked: None };

		Paras::<T>::insert(id, info);
		// We check above that para has no lifecycle, so this should not fail.
		let res = polkadot_runtime_parachains::schedule_para_initialize::<T>(id, genesis);
		debug_assert!(res.is_ok());
		Self::deposit_event(Event::<T>::Registered { para_id: id, manager: who });
		Ok(())
	}

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
