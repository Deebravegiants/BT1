### Title
Webhook HMAC signature covers only the raw body, not the `shop`, `topic`, or `webhook_id` headers, allowing cross-tenant identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers — it only proves the body bytes are unmodified.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
This means `HmacValidator.validate_signature` computes `HMAC(secret, raw_body)` and compares it only to the `hmac-sha256` header: [2](#0-1) 
Meanwhile, `Registry.process` extracts `request.shop`, `request.topic`, and `request.webhook_id` directly from HTTP headers, which are read verbatim with no cross-check against the signed payload: [3](#0-2) [4](#0-3) 
These header-derived values are then trusted and handed to the host app's handler as `WebhookMetadata`, which the gem's own documentation instructs apps to use as the tenant identifier (`shop_domain: data.shop`) when enqueuing work: [5](#0-4) 

This breaks the identity binding: `signed(shop) == acted_on(shop)` does not hold. The bytes verified by HMAC (`raw_body`) are disjoint from the bytes the handler acts on for tenant scoping (`shop-domain` header). Any client capable of triggering delivery of one legitimately-signed webhook body (e.g., a malicious merchant installing the app on their own low-privilege shop and triggering an event) can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header (and/or `x-shopify-topic`/`x-shopify-webhook-id`). `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will dispatch the forged `shop` value to the handler as if Shopify had certified it.

### Impact Explanation
This is a cross-tenant identity-binding bypass at the gem level: the `shop` value the gem asserts is authenticated ("came from Shopify for this shop") is not actually bound to the HMAC that supposedly authenticates the request. Any host application that follows the gem's documented pattern of using `data.shop` to scope work to a tenant (as shown in the gem's own `docs/usage/webhooks.md` example) inherits a cross-tenant confusion vector: webhook body content genuinely originating from shop A can be attributed to shop B purely by header manipulation, with a request that still passes the gem's own signature check.

### Likelihood Explanation
Exploitation requires the attacker to be able to obtain at least one legitimately HMAC-signed `(raw_body, hmac)` pair — attainable by any unprivileged party who can install the app on their own shop and trigger a webhook event (a normal, unprivileged capability), then replay it to the app's public webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers. No access to `api_secret_key` or any privileged credential is needed.

### Recommendation
Include `topic`, `shop-domain`, and `webhook-id` in the signable string used for HMAC computation (or otherwise bind them cryptographically to the payload before delivery/validation), so that `HmacValidator.validate` fails if any of these values are altered independently of the body.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and its valid `x-shopify-hmac-sha256` header `H` — both correctly signed with the app's real secret for that legitimate delivery.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers))`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes `HMAC(secret, B)` and compares to `H`, per `to_signable_string` returning `@raw_body`: [1](#0-0) .
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` to the app's handler, per [4](#0-3) , causing the host app to process attacker-controlled body content under the identity of an unrelated shop.
