### Title
Webhook HMAC does not cover the `shop`, `topic`, `webhook-id` or `api-version` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop`, `#topic`, `#webhook_id` and `#api_version` are all read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then unconditionally trusts `request.shop` as the tenant identity handed to the app's webhook handler, breaking the intended binding: `HMAC-verified bytes == identity used for tenant routing`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that is defined as just the raw body: [1](#0-0) [2](#0-1) 

None of the Shopify-supplied headers — `shop-domain`, `topic`, `webhook-id`, `api-version` — are included in the signed content, yet `Registry.process` treats `request.shop` as an authenticated tenant identifier after the HMAC check passes: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across all shops that install the app, any shop that has the app installed will legitimately receive webhook deliveries whose body+HMAC pair is valid for that secret. An attacker controlling such a shop can capture one of their own genuine webhook deliveries (valid body + valid HMAC signature), then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` calls the app handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop.

This exactly matches the requested analog class: "a field acted on but not covered by the HMAC" — here the acted-upon field is the tenant-identifying `shop` (and topic/webhook_id), and the equality that should hold but does not is:
`shop used for tenant dispatch (request.shop from header) == shop actually authenticated by the HMAC (none, since headers aren't signed)`.

### Impact Explanation
Any host application built on this gem that uses the `shop` field from `WebhookMetadata` to route webhook data to per-tenant storage/state (exactly as documented in `docs/usage/webhooks.md`, which describes `data.shop` as "The shop domain of the webhook") is exposed to cross-tenant data injection: an attacker-controlled shop can inject webhook payloads (e.g. `orders/create`, `app/uninstalled`, `shop/redact`, `customers/data_request`) that the app will process and attribute to a different, victim shop. Depending on the handler's logic this can corrupt or leak another merchant's data, trigger uninstall/redaction side effects for a shop the attacker doesn't control, or otherwise cross the tenant boundary — this is a Critical, cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires the attacker to operate one shop with the target app installed (no `api_secret_key`, no access token theft, no TLS interception needed) and to be able to POST to the app's public webhook endpoint with attacker-controlled headers — both are realistic for any external, unprivileged actor who installs the app once. The vulnerable code path (`Request#to_signable_string`, `Request#shop`, `Registry.process`) is exercised on every webhook delivery, and the gem provides no way for a consuming app to detect the mismatch since it never signs or cross-checks the header values.

### Recommendation
Bind the tenant/topic identity into the signed content, or otherwise cross-validate it independently of the header value alone. Concretely: incorporate the `shop-domain`, `topic`, and `webhook-id` headers into `Webhooks::Request#to_signable_string` (mirroring how OAuth's `AuthQuery` binds `shop`, `host`, etc. into `to_signable_string`), so `HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a genuine webhook, e.g. `orders/create`, to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over body, keyed with app client_secret>`
   - body: `{"id": 1, ...}`
3. Attacker intercepts/replays this exact request but rewrites only the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   (body and HMAC header left untouched)
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (the raw body only) and it matches, since the body was not altered — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/webhooks/registry.rb:190`.
5. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:20-23`), even though the delivery was never signed for, nor originated from, that shop.
6. The app's handler processes/stores this payload as belonging to `victim-shop.myshopify.com`, completing the cross-tenant spoof.
