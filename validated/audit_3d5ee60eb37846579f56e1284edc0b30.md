## Finding

### Title
Webhook shop/topic identity not covered by HMAC verification allows cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop`, `topic`, `api-version`, and `webhook-id` values used to route and attribute the event are read from unauthenticated HTTP headers that are never included in the signed payload. This breaks the identity binding "shop authenticated == shop the event is attributed to," letting any holder of a validly-signed body (obtainable from the attacker's own shop) relabel it as belonging to any victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over exactly this signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` only calls this body-only HMAC check before dispatching to the handler, and it passes `request.shop` and `request.topic` — both read straight from headers that are excluded from the signature — into `WebhookMetadata` that the host application's handler uses to identify the tenant and event type: [3](#0-2) 

`shop` and `topic` are simple header lookups with no cross-check against the signed body: [4](#0-3) 

Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app (it is not per-shop), a party who legitimately installs the app on their own store receives a validly HMAC-signed webhook body. That signature remains valid for that exact body regardless of which `shop-domain`/`topic` header accompanies it, since those header values are never part of `to_signable_string`. This is precisely the "shop authenticated versus shop stored as a session/routing key" binding break: `HMAC-verified(body) == true` says nothing about `header[shop-domain] == actual originating shop`, yet the library treats the header value as trusted tenant identity.

### Impact Explanation
A host application's webhook handler typically uses `WebhookMetadata#shop` as the tenant key to look up the shop's stored access token/session and to persist or act on the event data (e.g., update inventory, create orders, trigger fulfillment) — this is the documented usage pattern shown for `Registry.process`. An attacker can:
1. Install the target app on a shop they control and legitimately receive a validly-signed webhook (any topic).
2. Replay that exact `raw_body` + `hmac-sha256` header value to the app's webhook endpoint while substituting the `shop-domain` (and optionally `topic`) header to reference a victim shop.
3. `Registry.process` accepts it — the HMAC check passes because it only verifies the body bytes — and the handler executes attacker-controlled event data attributed to the victim shop's tenant context.

This is a cross-tenant data-integrity/confusion vulnerability: the app processes attacker-supplied data as if it originated from, and pertains to, an arbitrary victim shop.

### Likelihood Explanation
Any unprivileged internet user can install a public app on a shop they control (no privileged credentials required) to obtain one valid signed webhook body/HMAC pair, and can freely forge the accompanying headers when replaying the request to the app's own webhook endpoint, since the gem performs no IP allow-listing, nonce/replay protection, or binding of headers to the signed payload.

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting them for dispatch/attribution. Short of that, document clearly that host applications must independently verify `shop` against a known/expected value (e.g., the session used to register the webhook) before acting on webhook data, and reject requests where the header-derived shop was not the one that originally registered for that topic.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook delivery with a valid signature
#    (secret is the app-wide api_secret_key, not shop-specific):
raw_body = '{"id":1,"note":"legit order from attacker-owned shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# 2. Attacker replays the same body/hmac but swaps the shop header to the victim
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # still valid: body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # unauthenticated field
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HMAC validation (lib/shopify_api/utils/hmac_validator.rb#validate_signature)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-controlled data as belonging to victim-shop.
``` [5](#0-4) [6](#0-5)

module ShopifyAPI

      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
