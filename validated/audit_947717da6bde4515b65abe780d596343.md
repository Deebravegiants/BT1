### Title
Missing Backend Authorization Check Allows User-Centric Signups to Bypass Server-Side Enrollment Validation - (File: `src/plans/mod.rs`)

### Summary
The external report describes `SellerFinancing.sol` allowing a sanctioned/blocked party to complete a privileged state-transfer action because the code trusts a locally-computed condition instead of calling the authoritative check (`_requireIsNotSanctioned`) before mutating state. The same bug class — completing a privileged, identity-bound action by relying on a local decision instead of the backend's authoritative validation — exists in orb-core's signup-completion path in `MasterPlan::do_signup`.

### Finding Description
In `do_signup`, after biometric capture and personal-custody-package upload, the orb decides whether the signup is a "success" via two mutually exclusive branches: [1](#0-0) 

When `user_centric_signup` is `true` and the operator config `ignore_user_centric_signups` is `false` (the default, per `src/config.rs`), the orb **never calls the backend enrollment endpoint** (`enroll_user::Plan::run`, which POSTs to `/api/v2/signups/{signup_id}` via `signup_post::request` and polls `/api/v1/signups/{signup_id}` via `signup_poll::request`). Instead it derives `success` purely from the locally computed `signup_reason`: [2](#0-1) 

`signup_reason` is `Normal` unless `detect_fraud` reports fraud. However, `detect_fraud` in this build unconditionally returns `false`: [3](#0-2) 

This means for any user-centric signup, the orb marks the enrollment as `Success` and reports `signup_successful()` without the backend ever performing its authoritative server-side checks (duplicate detection, backend fraud/ban rules, in-flight-match detection, or any other "sanctioned"-style gate) — the same class of check that the `enroll_user::Plan`/`signup_poll` path enforces for non-user-centric signups (see `SIGNUP FAIL` handling for backend duplicates/legacy/in-flight matches/fraud in `src/plans/enroll_user.rs` lines ~157-176). The orb effectively becomes the sole arbiter of a privileged, identity-bound state transition (a completed signup) that should be gated by the backend, exactly analogous to `_transfer` completing a token transfer without calling `_requireIsNotSanctioned`.

### Impact Explanation
A signup can be locally marked `Success` (and later can affect UI feedback, telemetry, and downstream systems relying on `SignupResult.success` / `enroll_user::Status::Success`) even though the backend was never asked to authorize/validate it via `signup_post`/`signup_poll`. This creates a path where identity-bound signup completion state can be attested by the orb alone, bypassing the backend's fraud/duplicate/ban enforcement that exists specifically to prevent unauthorized or misattributed signups — mirroring the impact category of unauthorized/misattributed signup or fraud-bypass called out as acceptable impact.

### Likelihood Explanation
This is not a rare edge case: `user_centric_signup` is a normal, backend-controlled flag returned per-user from `backend::user_status::request` (`orb_qr_link::UserData.user_centric_signup`), and `ignore_user_centric_signups` defaults to `false` in `Config::default()` (`src/config.rs` line 436). Any signup flow where the backend flags the user as "user-centric" takes this branch by default, making the bypass reachable under normal operating configuration rather than requiring an unusual state.

### Recommendation
Do not derive final enrollment success solely from client-local `signup_reason`/`detect_fraud` results for user-centric signups. Always perform (or require confirmation of) the backend authoritative enrollment check — i.e., always call the equivalent of `enroll_user`/`signup_post`+`signup_poll` (or a dedicated backend "finalize user-centric signup" endpoint) before setting `success = true`, so the backend's fraud/duplicate/ban checks remain the actual source of truth, consistent with how non-user-centric signups are validated.

### Proof of Concept
1. Configure/serve a user QR-code response where `authenticated_app_data.user_centric_signup = true` (as the backend can already do, e.g. as seen in the test/dev stub in `src/backend/user_status.rs` lines 100-107).
2. Ensure `ignore_user_centric_signups` remains `false` (default).
3. Complete biometric capture; since `detect_fraud` always returns `Ok(false)` (line 1390-1406), `signup_reason` is `Normal`.
4. In `do_signup`, the branch at lines 639-656 sets `success = true` and `debug_report.enrollment_status(Success)` without ever invoking `enroll_user`/`signup_post`/`signup_poll`, so no backend-side sanction/fraud/duplicate check is performed before the signup is reported as successful.
