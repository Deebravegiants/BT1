### Title
Webhook HMAC signature does not cover the `shop-domain` header, allowing shop-identity spoofing in processed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the HMAC-verifiable material via `to_signable_string`, which returns **only** the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` treats a passing `Utils::HmacValidator.validate(request)` check as proof the *entire* request "did indeed come from Shopify" (per the gem's own documentation) and then forwards `request.shop` — an unverified header value — to the app's handler as the shop identity for the event.

### Finding Description
The identity binding that should hold is:

`shop value trusted by the webhook handler == shop value cryptographically bound inside the HMAC-signed bytes`

This binding is broken. The HMAC is computed and checked only over `@raw_body`: [1](#0-0) 

and validated by: [2](#0-1) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) come straight from attacker-controllable HTTP headers, not from anything inside the signed payload: [3](#0-2) 

`Registry.process` gates only on the HMAC check and then hands the unauthenticated `request.shop` to the app's handler as the trusted shop identity: [4](#0-3) 

The gem's own documentation promises stronger guarantees than what is actually implemented: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and explicitly instructs handler authors to trust `data.shop` as "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that has installed the app, any merchant/attacker who has legitimately installed the app receives genuinely-signed webhooks for their own shop. That attacker can replay the exact same raw body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. The HMAC check still passes (it only validates the body bytes), so `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` reporting the victim's domain, even though the payload was never sent by Shopify for that shop.

### Impact Explanation
Any app that follows the gem's documented pattern (using `data.shop` to key per-tenant work, e.g. `perform_later(shop_domain: data.shop, ...)` as shown in the docs) is exposed to cross-tenant data confusion: an attacker-controlled shop can inject fabricated webhook events attributed to an arbitrary victim shop domain, since the HMAC check does not bind the shop identity to the signed bytes. This satisfies the "cross-tenant access" criterion because the shop identity used to dispatch/attribute the webhook data is forgeable by any party with the ability to install the app once and capture one genuine signed request.

### Likelihood Explanation
No special access is required beyond installing the app once as any shop (a normal, unprivileged action any merchant can perform) and then replaying a webhook POST with a modified `shop-domain` header to the app's public webhook endpoint. This requires no knowledge of `api_secret_key`, no token theft, and no TLS interception — only observation of one legitimate webhook delivery to their own shop.

### Recommendation
Bind the shop identity (and ideally topic/webhook id) into the HMAC-covered signable string, or independently verify that the claimed `shop-domain` header corresponds to a shop with an active, valid session/installation known to the app before trusting it, rather than relying solely on a body-only HMAC check to authenticate header-derived metadata. At minimum, update `docs/usage/webhooks.md` to stop asserting that `Registry.process` "verifies the request did indeed come from Shopify" as a whole, and explicitly warn that `data.shop` is not covered by the HMAC.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a real Shopify webhook delivery, e.g.:
```
POST /callback/orders/create
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of raw_body using app's shared client_secret>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {"id":1,...}
```
2. Replay the identical body and HMAC header, but change the header to:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
3. `Utils::HmacValidator.validate` in [2](#0-1)  passes because it only checks the raw body's HMAC.
4. `Registry.process` in [4](#0-3)  calls the app handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process/attribute attacker-supplied data as if it belonged to the victim shop.
