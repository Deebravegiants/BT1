### Title
Webhook shop/topic identity spoofing due to fields acted upon not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook signature validation in this gem only authenticates the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are taken from unauthenticated HTTP headers. This mirrors the escher `FixedPrice.sol` bug class: an action (fee deduction / here, webhook processing keyed on shop identity) is performed using data that is not actually covered by the value that was supposed to bind/authenticate the whole operation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers, which are never included in the HMAC-signed material: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived) to build `WebhookMetadata` and dispatch it to the registered handler: [3](#0-2) 

Because `HmacValidator.validate` computes `HMAC(secret, raw_body)` and never incorporates the shop domain, topic, or webhook id into the signed string, the HMAC signature is identical for a given body regardless of which shop it is claimed to originate from. The equality the code implicitly (and incorrectly) relies on is:

`HMAC(secret, raw_body) valid ⇒ shop header == genuine originating shop`

but the actual binding provided by the signature is only:

`HMAC(secret, raw_body) valid ⇒ raw_body was produced/known by Shopify (or anyone who has seen a legitimate raw_body+hmac pair)`

Any webhook payload (body + hmac pair) legitimately delivered to the app for shop A can be replayed by an unprivileged internet user directly to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to shop B, and/or the topic/webhook-id headers changed. `HmacValidator.validate` will still return `true` because it only checks the body against the secret, so `Registry.process` will invoke the handler believing the event came from shop B with the attacker-chosen topic/webhook id.

### Impact Explanation
This breaks the tenant identity binding for webhook processing: the app's webhook handler logic (which typically keys off `data.shop` to look up per-shop state/records) can be made to act on/for the wrong shop using another shop's legitimate webhook payload as raw material, or to be invoked with attacker-chosen topic/webhook_id metadata paired with valid-but-mismatched body content. This falls under cross-tenant access impact, since data intended to be scoped and authenticated per-shop is dispatched to app handlers with an unauthenticated, attacker-controlled shop identifier.

### Likelihood Explanation
Exploitation requires the attacker to have observed at least one legitimate `(raw_body, hmac)` pair — for example from webhooks delivered to their own shop/app installation, which is trivially obtainable by any developer/merchant who installs the app (an unprivileged action, no special credentials needed). No `api_secret_key` or access token is required to perform the replay itself; only knowledge of one valid signed body, which is not treated as secret by Shopify's webhook delivery mechanism.

### Recommendation
Include `shop`, `topic`, and (if used for dedup/handling) `webhook_id`/`api_version` in the value that is HMAC-verified, or independently validate that the `shop` header corresponds to a shop the app has an active session/installation for before dispatching to handlers. At minimum, `Registry.process` should cross-check `request.shop` against known installed shops rather than trusting it unconditionally alongside a body-only HMAC.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com` and capture a legitimate incoming webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), along with `X-Shopify-Topic` and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. As an unprivileged user, POST the same raw body `B` and same `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a shop the attacker does not control) and/or a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3)  which succeeds because it only checks `B` against `H`; the header values are never part of the signed payload [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop-b.myshopify.com` and topic, even though these were never authenticated [5](#0-4) .
