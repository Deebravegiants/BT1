### Title
Webhook shop attribution spoofing via unsigned `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by the webhook handler from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, not this header. This breaks the intended binding: `hmac_valid ⇒ (body, shop) both authentic`, when in fact `hmac_valid ⇒ body authentic only`.

### Finding Description
`Registry.process` authenticates an incoming webhook solely via:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop` is read directly, unsigned, from the header: [4](#0-3) 

After a successful HMAC check, `Registry.process` passes this unauthenticated `shop` value straight into the handler: [5](#0-4) 

So the equality actually enforced is `HMAC(body) == received_hmac`, while the equality the application logic implicitly relies on is `shop_header == shop_that_produced_this_body`. These are never checked to match. Since the app's `api_secret_key` is shared across every shop that has installed the app, any merchant who has legitimately installed the app can capture a genuine, correctly-signed webhook delivered to their own endpoint for their own shop, then replay that exact body (with its still-valid HMAC) to the app's webhook endpoint while altering only the `shop-domain` header to name a different, victim shop. `Registry.process` will validate the HMAC (unchanged body ⇒ still valid) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to attribute, store, or act on the payload for a particular tenant (e.g., writing order/inventory data keyed by shop, or triggering per-shop side effects) without independently verifying that the shop is the one it actually holds an active session/installation for, an attacker can inject spoofed data attributed to an arbitrary victim shop. This is a cross-tenant integrity violation reachable purely through the webhook-processing surface this gem exposes, using nothing but the attacker's own legitimate (low-privilege) app installation — no leaked secret, no privileged account required.

### Likelihood Explanation
Low-to-moderate. It requires the attacker to be a legitimate installer of the target app (to receive at least one real, validly-signed webhook) and to be able to POST directly to the app's public webhook endpoint with modified headers, which is generally possible since webhook endpoints are internet-reachable and this gem does not restrict by source IP. It also requires the host application to trust `WebhookMetadata#shop` for tenant attribution without cross-checking against a known session/installation — a pattern the gem's own documentation implicitly encourages, since `Registry.process` is presented as the complete verification step.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the signed material, or otherwise verify them independently of the header:
```diff
- sig { override.returns(String) }
- def to_signable_string
-   @raw_body
- end
+ # No safe way to bind headers into Shopify's existing HMAC scheme;
+ # instead, Registry.process should require callers to confirm `request.shop`
+ # matches a known/expected shop (e.g., an existing installation record)
+ # before trusting it for tenant attribution.
```
At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a known store/installation before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and legitimately receives a webhook, e.g. an `orders/create` POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts a new HTTP request to the same app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (`B`) only — validation succeeds because `B` and `H` are unchanged. [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., data legitimately produced for the attacker's own shop is now falsely attributed to the victim shop. [5](#0-4)
