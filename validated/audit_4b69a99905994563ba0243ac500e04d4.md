### Title
No vulnerability: static/ALT Pubkey collisions are rejected by `validate_account_locks` before any lock-taking or loading occurs - (File: transaction-status/src/parse_accounts.rs)

### Summary
The premise that `parse_v0_message_accounts` and `TransactionAccountLocksIterator::accounts_with_is_writable` can produce two different writability verdicts for the same physical account is moot: any v0 message whose ALT-resolved Pubkey collides with a static account key is rejected with `TransactionError::AccountLoadedTwice` by `validate_account_locks`/`has_duplicates` before `Accounts::lock_accounts` ever computes per-index writability or before `account_loader` loads anything. `parse_v0_message_accounts` itself is a display-only function used by `transaction-status`/RPC JSON encoding, not part of the lock or load path.

### Finding Description
`has_duplicates` in [1](#0-0)  iterates over the *combined* `AccountKeys` iterator, which chains static keys with the ALT-resolved writable and readonly keys. `validate_account_locks` is called in `Accounts::lock_accounts` with `tx.account_keys()` *before* `TransactionAccountLocksIterator::accounts_with_is_writable()` is even constructed: [2](#0-1)  — the `.and_then(...)` short-circuits on the validation result, so `accounts_with_is_writable` is only invoked when `validate_account_locks` returned `Ok`. This means a v0 message where an ALT writable-index resolves to a Pubkey duplicated among static `account_keys` is caught as a duplicate in `has_duplicates` and rejected with `AccountLoadedTwice` prior to any per-index writability computation or account loading (`account_loader::load_transaction_account`). This exact scenario (static key duplicated by a dynamic/ALT key) is covered by the existing unit test `test_validate_account_locks_duplicate_dynamic`: [3](#0-2) , which asserts `Err(TransactionError::AccountLoadedTwice)`.

Separately, `parse_v0_message_accounts` in `transaction-status/src/parse_accounts.rs` ( [4](#0-3) ) is only used to build JSON-RPC display metadata (`UiParsedMessage`) from an already-executed/committed transaction's `LoadedMessage`, via `EncodableWithMeta::encode_with_meta` for `v0::Message` ( [5](#0-4) ) and `VersionedTransactionWithStatusMeta::build_json_accounts` ( [6](#0-5) ). It has no role in account locking, loading, budget, fee, rent, or commit logic, and it can never be reached for a transaction containing a static/ALT collision because such a transaction is rejected at `validate_account_locks` and never gets committed or given a `TransactionStatusMeta` with `loaded_addresses` reflecting a colliding key.

### Impact Explanation
No impact: the invariant "only accounts declared writable and unlocked by the message may be mutated" is never violated. The transaction is rejected with `TransactionError::AccountLoadedTwice` at the account-lock stage (`Accounts::lock_accounts` → `validate_account_locks` → `has_duplicates`), long before `account_loader` loads or `TransactionAccountLocksIterator` locks anything. `parse_v0_message_accounts` divergence, even if it existed, would only affect RPC display metadata of an already-finalized transaction and cannot cause account-lock/writable-declaration bypass or undeclared mutation.

### Likelihood Explanation
Not applicable — the described precondition (a v0 message with an ALT writable-index resolving to a Pubkey duplicated among static account keys) is already comprehensively guarded against by existing consensus-critical validation (`validate_account_locks`), which is called at every relevant entry point (`Accounts::lock_accounts`, `Bank::try_lock_accounts_with_results`, `blockstore_processor::validate_entry_transactions`, unified-scheduler task creation) as documented in `unified-scheduler-logic/src/lib.rs` [7](#0-6) .

### Recommendation
No fix needed; the existing `validate_account_locks`/`has_duplicates` check already enforces the required invariant across static and ALT-resolved account keys.

### Proof of Concept
The existing unit test already serves as the proof: `test_validate_account_locks_duplicate_dynamic` in `accounts-db/src/account_locks.rs` constructs a static key list containing `duplicate_key` and a `LoadedAddresses` whose `readonly` list also contains `duplicate_key`, and asserts `validate_account_locks(...)` returns `Err(TransactionError::AccountLoadedTwice)` — i.e., the rejection happens deterministically before any lock or load. A fuzz test generating arbitrary v0 messages with static/ALT collisions would need to assert the same outcome, which is already guaranteed by this code path.

/// Check for duplicate account keys.
fn has_duplicates(account_keys: AccountKeys) -> bool {
    // Benchmarking has shown that for sets of 32 or more keys, it is faster to
    // use a HashSet to check for duplicates.
    // For smaller sets a brute-force O(n^2) check seems to be faster.
    const USE_ACCOUNT_LOCK_SET_SIZE: usize = 32;
    if account_keys.len() >= USE_ACCOUNT_LOCK_SET_SIZE {
        HAS_DUPLICATES_SET.with_borrow_mut(|set| {
            let has_duplicates = account_keys.iter().any(|key| !set.insert(*key));
            set.clear();
            has_duplicates
        })
    } else {
        for (idx, key) in account_keys.iter().enumerate() {
            for jdx in idx + 1..account_keys.len() {
                if key == &account_keys[jdx] {
                    return true;
                }
            }
        }
        false
    }
}

pub fn parse_v0_message_accounts(message: &LoadedMessage) -> Vec<ParsedAccount> {
    let mut accounts: Vec<ParsedAccount> = vec![];
    for (i, account_key) in message.account_keys().iter().enumerate() {
        let source = if i < message.static_account_keys().len() {
            ParsedAccountSource::Transaction
        } else {
            ParsedAccountSource::LookupTable
        };
        accounts.push(ParsedAccount {
            pubkey: account_key.to_string(),
            writable: message.is_writable(i),
            signer: message.is_signer(i),
            source: Some(source),
        });
    }
    accounts
}
