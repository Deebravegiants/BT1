## Finding

### Title
Webhook shop identity is taken from an unauthenticated header while the HMAC only covers the request body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed solely over the raw request body, then hands the handler a `shop` value read directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header — a value that is never included in the HMAC computation. Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret` shared across every shop that has installed the app, any attacker who controls one legitimately-installed shop can capture a valid `(raw_body, hmac)` pair from their own webhook deliveries and replay it to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop. The signature check still passes because it never inspected the shop header, so the application processes attacker-controlled webhook data under a different tenant's identity.

### Finding Description
- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the request's `hmac` value: [1](#0-0) 
- For webhooks, `to_signable_string` returns only `@raw_body` — the shop, topic, and webhook-id headers are excluded from what is signed: [2](#0-1) 
- `shop` is read straight from an attacker-controllable HTTP header with no cryptographic binding to the body or HMAC: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [4](#0-3) 

This is the exact class of bug described in the report analog: "a field acted on but not covered by the HMAC" — here the identity-binding equality that should hold is `hmac == HMAC(secret, body ‖ shop)`, but the actual check is `hmac == HMAC(secret, body)` while `shop` is consumed independently and unauthenticated.

### Impact Explanation
Because `Context.api_secret_key` is the single `client_secret` for the app (not a per-shop secret), any merchant who has legitimately installed the app can obtain a valid `(body, hmac)` pair from their own store's webhook traffic. They can then forge a webhook delivery to the app's endpoint for an arbitrary victim shop by reusing that valid `(body, hmac)` pair with the `shop-domain` header set to the victim's domain. The app's webhook handler will process this as authentic data attributed to the victim shop — a cross-tenant data/identity confusion that can corrupt the victim tenant's data, trigger unintended business logic (e.g., order/fulfillment/customer webhooks), or exfiltrate the attacker's data into the victim's record scope. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be an unprivileged holder of one legitimate install of the target app (any developer can install a public app on their own test store), then capture one real webhook delivery and its headers, and resend it with a modified `shop-domain` header to the app's public webhook URL. No access to `api_secret_key`, tokens, or the victim's environment is required, making this readily reachable by any unprivileged internet user relative to the victim tenant.

### Recommendation
Bind the shop identity into what is authenticated: either include `shop` (and ideally `topic`/`webhook-id`) inside the signed payload verification, or require server-side confirmation that the resolved `shop` matches a shop record already known to have this `webhook_id`/topic combination (Shopify's webhook IDs are unique per delivery) before invoking the handler. At minimum, do not treat `request.shop` as a trusted tenant boundary based solely on HMAC-of-body success.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a legitimate webhook, capturing the raw body `B` and its valid header `x-shopify-hmac-sha256: H` (computed with the app's shared `client_secret`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` from the header and invokes the registered handler as if the (attacker-controlled) body genuinely originated from the victim shop: [6](#0-5)
