### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while only the raw body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the request body against the `X-Shopify-Hmac-SHA256` header, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from separate, unsigned HTTP headers to build the `WebhookMetadata` object dispatched to the app's handler. Because the HMAC signature covers only the raw body and never binds it to those header values, an attacker who can obtain one valid `(body, hmac)` pair for an app-wide shared secret can replay it with forged `shop-domain`/`topic`/`webhook-id` headers, making the app process attacker-chosen webhook data as if it originated from a different topic or a different merchant's shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

All the other attributes used by the registry - `topic`, `shop`, `api_version`, `webhook_id` - are parsed straight out of HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only that body/hmac pair, then trusts the header-derived `topic` and `shop` to route and build the dispatched metadata: [3](#0-2) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, i.e. the body, using the app's single, shop-independent `api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`bytes verified by HMAC == bytes acted upon (topic, shop, webhook_id)`

In this implementation that equality does not hold: bytes verified = raw body only; bytes acted upon = arbitrary attacker-supplied headers. Since the same `api_secret_key` is used for every shop that has installed the app (it is not a per-shop secret), a `(body, hmac)` pair legitimately produced for one merchant/topic remains a valid signature for the same body no matter which `shop-domain`/`topic`/`webhook-id` headers are attached to the replay.

### Impact Explanation
An attacker who controls one tenant of the app (i.e., who can install the app on their own development/trial store and thus receive real, validly-signed webhook deliveries) can capture a legitimate `(raw_body, X-Shopify-Hmac-SHA256)` pair and replay it directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop and/or the `X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers for a different topic. `Registry.process` will accept it (the HMAC check only covers the body) and hand a `WebhookMetadata` claiming a victim's shop/topic to the app's registered handler, since the gem itself never re-derives or cross-checks `shop`/`topic` against the verified content. This is a cross-tenant identity-binding failure, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires network access to the app's public webhook endpoint and possession of at least one valid `(body, hmac)` pair, which any attacker can obtain simply by installing the app on their own store (no privileged credentials, access tokens, or `api_secret_key` needed) and capturing one of their own inbound webhook deliveries. No TLS interception or social engineering is required.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise validate `shop`/`topic`/`webhook_id` against data already trusted by the app (e.g., cross-check `shop` against a stored, previously-authenticated session/shop record, and include `topic`/`shop`/`webhook_id` in the signable string used by `HmacValidator`) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`, trigger `orders/create`, and capture the raw POST body `B` and header `X-Shopify-Hmac-SHA256: H` (a valid HMAC of `B` under the app's shared secret).
2. Replay the exact same body `B` and hmac `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and/or `X-Shopify-Topic: orders/create` (or any other registered topic).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and succeeds, since `H` is a valid signature of `B`.
4. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `victim.myshopify.com` / topic values and dispatches it to the app's handler as if it were an authentic webhook for the victim shop. [3](#0-2)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
