### Title
Webhook Shop-Domain Header Is Not Covered by the HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then trusts the `shop` field taken from the `x-shopify-shop-domain` header — which is never covered by that HMAC — and hands it unmodified to the app's handler. Any party that can obtain one validly-signed webhook body/HMAC pair from the target app (e.g. by installing the app on their own store) can replay that exact body to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates authenticity like this: [1](#0-0) 

The HMAC validity check delegates to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only the raw JSON body — never the headers: [3](#0-2) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a value that is completely outside the HMAC's coverage: [4](#0-3) 

After the HMAC check passes, `process` builds `WebhookMetadata` directly from this unauthenticated header and forwards it to the app's registered handler as the shop identity for the event: [5](#0-4) 

The gem's own documentation instructs developers to key business logic off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this field is meant to identify which tenant/shop the event belongs to: [6](#0-5) 

This breaks the intended identity binding: **bytes verified (raw body) ≠ bytes used to determine the tenant (shop header)**. Because the shop domain is never part of the signed content, the HMAC only proves "this body was signed with the app's secret at some point by Shopify for some shop" — it proves nothing about which shop the request is currently claiming to be from.

### Impact Explanation
Any unprivileged user who can install the target app on a shop they control (a routine, unprivileged action — e.g. via the Shopify App Store or a free/dev store) will receive genuinely Shopify-signed webhooks for that shop, with bodies they can influence (e.g., by editing their own products/orders to control field content). By capturing one such `(raw_body, hmac)` pair and replaying it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain, the attacker gets the app to execute `handler.handle` believing the event originated from the victim shop. If the app looks up per-shop session/state (a normal pattern per the gem's own docs) using `data.shop`, this results in cross-tenant confusion: attacker-controlled webhook content is processed under a different merchant's identity/session context. This matches the "cross-tenant access" criterion for Critical severity.

### Likelihood Explanation
Likelihood is realistic: no access to `api_secret_key`, access tokens, or any privileged capability is required — only the ability to install the app on any shop (including the attacker's own) to harvest a legitimately-signed body/HMAC pair, and the ability to send an HTTP request to the app's public webhook callback URL with a forged header. The gem provides no mechanism to bind the `shop` header to the signed payload, so this is exploitable against every app built on this gem's webhook processing flow as documented.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the HMAC-covered signable content, or otherwise cryptographically bind the `x-shopify-shop-domain` header to the verified payload before it is trusted and forwarded to handlers in `ShopifyAPI::Webhooks::Registry.process`. At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted for authorization decisions, and provide an API that lets integrators verify the shop against their own session store rather than relying on the header value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a webhook event (e.g. `orders/create`) with body content of their choosing and captures the resulting `x-shopify-hmac-sha256` header — a value Shopify computed as `HMAC-SHA256(api_secret_key, raw_body)`, valid because `raw_body` is unchanged.
3. Attacker POSTs the exact same `raw_body` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` while keeping the original `x-shopify-hmac-sha256`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the signature over `raw_body` only and finds it matches — passing validation.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata` with `shop: request.shop` set to `"victim-shop.myshopify.com"` and invokes the app's handler, which acts on attacker-controlled data as though it came from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
