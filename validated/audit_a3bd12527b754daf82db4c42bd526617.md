### Title
`EvmHost.dispatch` and `IntentGatewayV2.placeOrder`'s native-fee swap has no slippage bound, letting a sandwich attacker force the depositor's ETH to be drained at a manipulated price - (File: `evm/src/core/EvmHost.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
Both `EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)` and `IntentGatewayV2`'s order-placement path convert a caller's native token into the protocol `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, using the *entire* `msg.value` (or remaining `msgValue`) as the implicit `amountInMax`, and `block.timestamp` as the deadline. There is no independent, caller-supplied maximum acceptable input, so the actual ETH cost of acquiring the fixed `fee`/`post.fee`/`get.fee` amount of `feeToken` is whatever the spot AMM reserves say at execution time. This is the same root cause as the Velocimeter H-5 finding: a fixed target amount is purchased against live, unprotected spot reserves inside the victim's own transaction, so a searcher can sandwich the call and force it to execute at the worst price the caller's ETH allows.

### Finding Description
`EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)` do the swap identically: [1](#0-0) [2](#0-1) 

`path[0] = WETH`, `path[1] = feeToken()`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. The exact-output amount (`post.fee`/`get.fee`) is fixed by the caller, but the maximum acceptable input is implicitly `msg.value` — there is no separate `amountInMax` parameter the caller controls independently of how much ETH they attach, and the deadline is `block.timestamp`, which provides no MEV protection (it is always satisfied in the same block). If the router requires more WETH than `msg.value` to fill the exact output, the whole call reverts, but any amount up to `msg.value` can be silently consumed. Nothing in `EvmHost.dispatch` refunds the caller for the difference between `msg.value` and the actual amount spent (`amounts[0]`) — the code moves straight to building `commitment` and does not send back unspent value, unlike the sibling flow in `IntentGatewayV2`.

`IntentGatewayV2`'s order-placement path has the analogous swap and an explicit refund of leftover `msgValue`: [3](#0-2) 

Here `msgValue` (the ETH left over after covering `order.inputs`) is passed wholesale as `value` to `swapETHForExactTokens`, again with `order.fees` as the fixed output and no caller-supplied slippage bound distinct from `msgValue` itself, and `block.timestamp` as the deadline. A front-runner can manipulate the WETH/`feeToken` pool immediately before this call so that `amounts[0]` (ETH actually spent) rises toward the ceiling of `msgValue`, minimizing what gets refunded at line 396. Because `msgValue` here is often sized generously by the caller/SDK to cover normal price movement (or, in `EvmHost`, is the entire `msg.value` with no refund path at all), the attacker can extract the difference between the fair-market ETH cost of `order.fees`/`post.fee` and the manipulated cost, exactly mirroring how the Velocimeter bug let an attacker imbalance a pool so a fixed `_amount` bought disproportionately less liquidity.

The docs even flag the *view*-only `quote()` helper in `HyperApp.sol` as sandwich-vulnerable and explicitly warn it must never be called on-chain: [4](#0-3) 

But the state-changing swap paths in `EvmHost.dispatch` and `IntentGatewayV2`'s fee-swap block have the identical spot-price dependency baked directly into an on-chain, value-moving call, with no equivalent warning or mitigation (e.g., a caller-supplied `feeInNativeMax` distinct from `msg.value`, or a TWAP-based bound).

### Impact Explanation
Any unprivileged user who dispatches a POST/GET request with native-token payment, or places a cross-chain intent order paying fees in native token, is exposed to a sandwich attack that forces their transaction to buy the fixed fee-token amount at a manipulated, worse exchange rate. In `EvmHost.dispatch`, because there is no refund of unspent value at all, the attacker can cause the dispatcher to permanently lose the ETH consumed by the inflated price — actual loss of user funds on a core, frequently-used dispatch path. In `IntentGatewayV2`, the loss is bounded by the refund of any true leftover `msgValue`, but the attacker still extracts the price-impact difference from the depositor for every order that pays fees in native token, which is a medium-severity but still concrete value loss on every affected order placement.

### Likelihood Explanation
`dispatch()` is the primary entry point for every native-token-funded cross-chain message and `placeOrder` (fee-in-native path) is used by ordinary IntentGateway users, so the attack surface is triggered by routine, permissionless transactions. Any searcher/MEV bot monitoring the mempool for `dispatch`/`placeOrder` calls carrying `msg.value` can sandwich the WETH/`feeToken` pool trade with ordinary front-run/back-run swaps, exactly as demonstrated in the referenced report's PoC. No privileged role or unusual condition is required — only that the local Uniswap V2 WETH/feeToken pool has exploitable liquidity/slippage, which is typical for smaller feeToken pools.

### Recommendation
Add a caller-supplied maximum acceptable native-token spend (`amountInMax`) that is independent of `msg.value`/`msgValue`, so the swap can be bounded to a value the caller actually agreed to (rather than "whatever `msg.value` happens to be"), and enforce a real (short, non-`block.timestamp`) deadline. In `EvmHost.dispatch`, additionally refund any unspent native token back to the caller after the swap, matching the pattern already used in `IntentGatewayV2`. Consider deriving the acceptable price bound from a TWAP/oracle-based reference rather than trusting the spot AMM reserves at call time, consistent with how the Velocimeter fix addressed the analogous `OptionTokenV4.exerciseLP` issue.

### Proof of Concept
1. Attacker observes a pending `EvmHost.dispatch(DispatchPost)` (or `IntentGatewayV2` order placement) transaction in the mempool that sends `msg.value` in native token to cover `post.fee` in `feeToken`.
2. Attacker front-runs with a large swap on the local Uniswap V2 WETH/`feeToken` pool that shifts the price so that acquiring `post.fee` units of `feeToken` now costs close to the victim's full `msg.value`.
3. Victim's transaction executes `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` (`EvmHost.sol` lines 921-932) at the manipulated price, consuming far more ETH than the fair-market cost of `post.fee`.
4. Attacker back-runs to restore the pool price and pockets the price-impact profit (as in the referenced report's `test_swapAndSee` pattern, adapted to `swapETHForExactTokens`'s exact-output/max-input side).
5. In `EvmHost.dispatch`, since no refund logic exists for leftover value, the victim's excess ETH is unrecoverable; in `IntentGatewayV2`, the victim receives a reduced refund at line 396, realizing the same loss in a smaller, bounded form.
