### Title
Chainlink Single Price Feeds Lack `minAnswer`/`maxAnswer` Circuit-Breaker Validation, Enabling Stale-Clamped Price Exploitation in `SimplexPaymaster` - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` fetches `latestRoundData()` from a Chainlink `AggregatorV3Interface` and only rejects `answer <= 0` and staleness beyond `maxOracleAge`. It never checks the returned answer against the aggregator's own `minAnswer`/`maxAnswer` bounds, so if the underlying asset (native gas token or a registered ERC-20, e.g. a depegging stablecoin) crashes below the feed's configured `minAnswer`, Chainlink will keep reporting the clamped floor value rather than the true crashed price, and the contract will treat that clamped value as valid, fresh data.

### Finding Description
`_getOraclePrice` is used everywhere pricing decisions are made in this permissionless, unprivileged-caller-reachable contract:
- `_tokenPrice` computes `tokenPrice = nativeUsd * 10^tokenDecimals * (10000+markup) / (tokenUsd * 10000)` using two independent `_getOraclePrice` calls — one for the native asset, one for the ERC-20 token being used to pay gas [2](#0-1) .
- `_fetchDetails`, called from `_validatePaymasterUserOp` on every UserOp, uses this token price directly to determine how much ERC-20 to charge a permissionless caller for gas [5](#0-4) .
- `swapAndDeposit` uses the same unclamped-bounds price to compute `amountOutMin` for swapping accrued token fees to native asset [4](#0-3) .

If a registered ERC-20 token depegs toward zero (analogous to LUNA/UST in the referenced report) while its Chainlink feed's `minAnswer` floor keeps the reported price artificially high, `tokenUsd` in `_tokenPrice` stays inflated relative to the real market value. This directly reduces the computed `tokenPrice` (token base units the paymaster charges per wei of native gas), since `tokenUsd` is in the denominator. Any unprivileged UserOp submitter can then pay for real gas (refunded from the paymaster's EntryPoint deposit, itself funded from real native assets) using a token now worth near zero, at the stale inflated valuation — draining paymaster-held native value while remitting worthless tokens. No admin, governance, or off-chain component prevents this; it is purely a function of the Chainlink aggregator's built-in floor and this contract's failure to detect it.

### Impact Explanation
This is a fund-drain vector reachable by any address submitting a `PackedUserOperation` through the ERC-4337 EntryPoint against this permissionless paymaster. During a genuine depeg event of a registered token, an attacker can systematically submit gas-sponsored UserOps paid in the depegged token at the stale minAnswer-clamped rate, extracting real native value from the paymaster (and ultimately the treasury/EntryPoint stake) while paying in an asset that is functionally worthless. This matches the "unbacked value extraction from clamped price" impact class of M-19, scoped here to the paymaster's own funds rather than third-party collateral.

### Likelihood Explanation
Low-to-medium likelihood — it requires a genuine severe depeg or price-crash event in one of the governance-registered tokens or the native asset feed, similar in kind to historical events like LUNA/UST or USDC's 2023 depeg. The contract already implements staleness (`maxOracleAge`) and non-positive answer checks, showing oracle-safety was considered, but the `minAnswer`/`maxAnswer` circuit-breaker case was not addressed at all.

### Recommendation
Extend `_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` to fetch each Chainlink aggregator's `minAnswer`/`maxAnswer` (or governance-configured equivalents, since `AggregatorV3Interface` alone doesn't expose them — the underlying `AggregatorV2V3Interface`/proxy's `aggregator()` does) and revert (or mark `_isValid = false`) when `answer` is at or near those bounds, applying a reasonable gap as recommended in the source report (`minAnswer + gap > returned value`) rather than an exact equality/inequality check.

### Proof of Concept
1. Governance registers token `T` with Chainlink feed `F` whose aggregator has `minAnswer = 0.90e8` (assume $1 peg, 8 decimals).
2. `T` depegs catastrophically to a real market price of $0.01, but `F.latestRoundData()` continues returning `answer = 0.90e8` because the underlying aggregator clamps output at `minAnswer` and neither halts nor flags this in `roundId`/`updatedAt`.
3. `_getOraclePrice(F, 8)` in `evm/src/utils/SimplexPaymaster.sol:662-676` passes both the `answer <= 0` check and the staleness check (the feed is still updating with clamped values), returning `0.90e8` as if it were the true price.
4. An attacker submits UserOps with `paymasterData` mode `0x00`/`0x02` selecting token `T`; `_fetchDetails`/`_tokenPrice` price gas using the inflated `0.90e8` `tokenUsd`, letting the attacker pay ~90x less real value than the token's true worth for sponsored gas, repeatedly draining the paymaster's native reserves.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
