## Title
Webhook Shop/Topic Identity Not Bound to HMAC — Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all of which are handed unmodified to the app's webhook handler — are read from HTTP headers that are **not** part of the signed payload. Because the same `api_secret_key` is shared by the app across every shop that has installed it, any shop that legitimately triggers a webhook to itself (i.e., a normal, unprivileged app-install tenant) can capture a validly-HMAC'd body/signature pair and replay it against the app's webhook endpoint with an arbitrary `shop-domain` header, causing `ShopifyAPI::Webhooks::Registry.process` to invoke the app's handler as if the event came from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` includes `Utils::VerifiableQuery` and defines: [1](#0-0) 

```ruby
sig { override.returns(String) }
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`to_signable_string` returns only `@raw_body` — `topic`, `shop`, `webhook_id`, and `api_version` are all sourced from headers and are excluded from the signed string. Verification is performed by `Utils::HmacValidator.validate`, which computes the signature purely over `to_signable_string` and compares it with `OpenSSL.secure_compare`: [2](#0-1) 

The processing path then trusts `request.shop` unconditionally once the body HMAC checks out: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The binding that is expected to hold is:
`shop_that_triggered_the_signed_body == shop_delivered_to_the_handler`

That equality is never checked. The HMAC only proves `body == signed_body`; it says nothing about which shop the body was generated for. Since `api_secret_key` is a single per-app secret shared across all installed shops (not a per-shop secret), any of the app's own tenants — an "unprivileged" one from the perspective of other merchants — can:
1. Trigger a real event (e.g., `orders/create`) on their own low-privilege shop, capturing the body Shopify sends and its valid `x-shopify-hmac-sha256`.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's identifiers.
3. `HmacValidator.validate` passes because it only checks the body signature, and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain.

If the host application's webhook handler uses `data.shop` to select which merchant record/session to update (the documented and expected usage pattern, per `docs/usage/webhooks.md`), this allows a tenant to inject fabricated events attributed to a different merchant — a cross-tenant data integrity break.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: the `shop` value handed to the application is not cryptographically bound to the payload it is provided with. A malicious/compromised existing tenant can inject arbitrary webhook payloads (of topics they can themselves trigger) that appear to originate from any other shop, letting them corrupt or manipulate another merchant's data/state inside the host application — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is significant for any real-world deployment: the attacker only needs to be an existing, unprivileged installer of the target app (a "shop"), a role trivially obtainable for a public Shopify app. They do not need the app's `api_secret_key`, an access token, or any privileged account — just the ability to trigger a webhook-generating action on their own store and forward the observed headers/body to the app's public webhook endpoint with a substituted `shop-domain` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed content, or independently verify that the `shop-domain` header corresponds to a shop the app actually expects for that specific webhook delivery (e.g., cross-check against the shop associated with the merchant's existing installation/session before invoking the handler), rather than trusting `request.shop` as truthful once only the raw body's HMAC has been validated.

### Proof of Concept
1. App tenant "attacker.myshopify.com" installs the app and registers for `orders/create`.
2. Attacker creates an order on their own store, capturing the resulting webhook request: `raw_body` and header `x-shopify-hmac-sha256` (valid, computed by Shopify with the app's shared `api_secret_key`).
3. Attacker POSTs this exact `raw_body` to the app's webhook endpoint, replacing headers:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - keeping `x-shopify-hmac-sha256` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `Digest(raw_body)` against the (unchanged, still-valid) hmac.
5. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled order data>, ...)`, and the host app processes it as if it originated from the victim shop.
