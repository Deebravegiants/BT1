### Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing tenant-attribution spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` fields that get passed to the app's handler and used to attribute the event to a tenant are read straight from HTTP headers, which are never part of the signed bytes [2](#0-1) . Anyone who has ever received one legitimate webhook (e.g. from their own, self-owned store) obtains a body+HMAC pair that stays valid forever for that body, and can then replay it with an arbitrary `shopify-shop-domain` header to make the app process/attribute the payload as coming from a different, victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhooks that is defined as just the raw body: [3](#0-2) 

None of `topic`, `shop`, `api_version`, or `webhook_id` — all sourced from headers — are included in the signable string: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived fields to construct the `WebhookMetadata` that is handed to the app's handler as the identity of the event's origin shop: [1](#0-0) 

The identity binding that should hold is: `hmac_valid(body) == true` implies `shop header == the shop that generated body`. In this gem, the equality actually checked is only `hmac_valid(body)`; the header-carried `shop` (and `topic`/`webhook_id`) are never bound into that check. Before the attacker's request: a legitimate webhook for shop A produces `(body_A, hmac_A)` where `hmac_A = HMAC(secret, body_A)`. After the attacker's request: the same `(body_A, hmac_A)` pair is replayed with `shopify-shop-domain: shop-B.myshopify.com` (or any topic/webhook_id) substituted. `HmacValidator.validate` still returns `true` because it only re-derives `HMAC(secret, body_A)` and compares it to `hmac_A` — it never inspects the shop header. `Registry.process` then dispatches to the handler with `shop: "shop-B.myshopify.com"`, `topic` and `webhook_id` fully attacker-controlled, while `body` is whatever content was originally signed for shop A.

### Impact Explanation
This breaks the shop-to-payload identity binding that host applications rely on to know which tenant a webhook event belongs to. An attacker who legitimately receives one webhook (trivial: install/own any Shopify dev store and trigger any webhook topic) can replay that exact body under a spoofed `shop`, `topic`, and `webhook_id` header combination. Depending on how the host app's handler uses `WebhookMetadata#shop`/`#topic` (e.g. looking up the session/store record by shop domain, or dispatching topic-specific business logic keyed by the declared topic), this enables cross-tenant data injection — content genuinely signed for the attacker's own shop gets processed as if it originated from an arbitrary victim shop, or a body meant for one topic gets dispatched to a handler for another topic. This matches the Critical "cross-tenant access" impact category since it lets an unprivileged internet user (who only needs their own legitimate webhook capture, no `api_secret_key`, no access token, no privileged account) cause the app to misattribute signed data across tenant boundaries.

### Likelihood Explanation
Medium-to-High. No secrets are required — only capture of one's own legitimate webhook delivery (any app installer can generate these on demand from their own store) and the ability to POST arbitrary headers to the app's public webhook endpoint, which is standard and normally internet-reachable by design. The only constraint is that the resulting exploitation power depends on what the host app does with `shop`/`topic` in its handler, but the gem itself provides no protection against this header/HMAC mismatch, and nothing in `Registry.process` or `Request` cross-checks header values against the signed body.

### Recommendation
Bind the tenant/topic identity into the authenticated data instead of trusting unauthenticated headers post-hoc:
- Prefer deriving `shop`/`topic` from the JSON body content itself when the payload includes it, or
- Require the host application to independently verify that the `shop` header corresponds to a shop with an active, previously-established session/installation before trusting it, and
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT covered by HMAC verification and must not be used as sole tenant-authorization input without an additional installed-shop lookup.

### Proof of Concept
1. Install a Shopify dev app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook topic (e.g. `orders/create`) to receive a legitimate delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (`H = HMAC_SHA256(secret, B)`), plus header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the captured request to the same app endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally alter `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's original body content, even though that body was never signed in association with `victim.myshopify.com` [6](#0-5) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
