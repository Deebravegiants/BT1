### Title
Missing shop-domain validation in OAuth callback allows `client_secret`/`client_id` exfiltration to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` take the `shop` value and pass it straight into `auth_base_uri(shop)` / `Auth::Session.new(shop: auth_query.shop)` without ever running it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing flow in the gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, and the storefront client all call `ShopValidator.sanitize!` first). The unsanitized shop string is then used by `Clients::HttpClient` to build the literal request host (`@base_uri = "https://#{api_host || session.shop}"`) that receives the POST body containing `client_id` and `client_secret`, so an unvalidated shop value directly controls where the app's `client_secret` is sent.

### Finding Description
This mirrors the reported bug class: a value is trusted and acted upon (used to build the outbound request target) without being bound/verified against the identity check that is supposed to protect it.

- `begin_auth(shop:, ...)` builds the authorize URL as `auth_base_uri(shop) + "/oauth/authorize?..."` where `auth_base_uri` is just `"https://#{shop}/admin"` — no call to `Utils::ShopValidator.sanitize!` anywhere in this path. [1](#0-0) 
- `validate_auth_callback` verifies the query's HMAC, then immediately builds `null_session = Auth::Session.new(shop: auth_query.shop)` from the raw `auth_query.shop` field and uses that session to send the access-token exchange request. [2](#0-1) 
- `Clients::HttpClient#initialize` derives the actual HTTP host it will talk to directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"`, and the request body containing `client_id`/`client_secret` is POSTed to that host. [3](#0-2) 
- Every other flow that builds a `Session` for a credential exchange calls `Utils::ShopValidator.sanitize!(shop)` first, restricting the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [4](#0-3) [5](#0-4) 

The identity-binding equality that should hold is: `shop used to build the outbound request host == shop restricted to TRUSTED_SHOPIFY_DOMAINS by ShopValidator.sanitize!`. In `oauth.rb` this equality is broken — `auth_query.shop` (and the `shop` passed into `begin_auth`) is used verbatim as the request host, never passed through `ShopValidator`. The HMAC in `validate_auth_callback` only proves the `shop` string was part of a signature computed with `Context.api_secret_key`; it says nothing about whether that string is a well-formed `*.myshopify.com` host rather than, e.g., `attacker.example.com` or a value crafted to smuggle userinfo/path components (`evil.com@shop`, `shop.com/../attacker.com`, etc.) into the resulting URI. Since `begin_auth`'s `shop` parameter is typically taken directly from an unauthenticated incoming HTTP request in the host application (the standard "start install" endpoint takes a `?shop=` query parameter before any HMAC exists), and `auth_base_uri` performs no domain restriction, a caller/host app that forwards this parameter as documented can have the library issue authorize redirects and, more importantly, the subsequent token-exchange POST carrying `client_id`+`client_secret`, to a host that is not constrained to Shopify's own domains.

### Impact Explanation
This is High/Critical: it results in the app's `client_secret` (and `client_id`) being transmitted, by the gem's own logic, to a host determined by an insufficiently validated `shop` string rather than one constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Leakage of `client_secret` allows full impersonation of the app (forging HMACs/JWTs for any shop, minting fraudulent OAuth completions), i.e., cross-tenant compromise and credential theft, matching the "SSRF with the app's credentials" / "credential leakage" impact categories in scope.

### Likelihood Explanation
Medium: exploitability depends on the host application passing an unsanitized `shop` value into `begin_auth`/`validate_auth_callback`, which is the documented calling pattern for this library (the gem does not sanitize on its own, contrary to its own `ClientCredentials`/`TokenExchange` code paths, which shows the sanitization was intended but omitted here specifically). The `validate_auth_callback` side additionally requires the HMAC check to pass, but the HMAC check validates authenticity of the byte string, not the domain-safety of the `shop` value contained within it — so even a value that passed HMAC validation legitimately (e.g., relayed from a real Shopify redirect with an oddly formatted shop parameter, or a raw callback hit with a still-good stale signed URL) is never format-restricted.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`, rejecting on `nil`) on the `shop` parameter inside `begin_auth` before constructing `auth_base_uri(shop)`, and likewise sanitize `auth_query.shop` in `validate_auth_callback` before it is used to build `null_session`/`Session.from`. This brings `oauth.rb` in line with `client_credentials.rb` and `token_exchange.rb`, ensuring the host that ultimately receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Host application's install endpoint calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params["shop"], redirect_path: "/auth/callback")` with an unauthenticated request parameter, per the documented usage of this method.
2. Attacker requests the install endpoint with `shop=attacker-controlled.example.com`.
3. `auth_base_uri("attacker-controlled.example.com")` returns `https://attacker-controlled.example.com/admin`, unmodified by any `ShopValidator` check. [1](#0-0) 
4. If the flow reaches `validate_auth_callback` with a query carrying that same `shop` value and a state/HMAC that can be produced for it (e.g., a replayed/legitimately-obtained callback tied to the same state cookie), `Auth::Session.new(shop: auth_query.shop)` and the subsequent `Clients::HttpClient` POST send `client_id`/`client_secret` to `https://attacker-controlled.example.com/admin/oauth/access_token`. [6](#0-5) [3](#0-2) 
5. Contrast with `ClientCredentials.client_credentials`, where the same `shop` input is first passed through `Utils::ShopValidator.sanitize!`, which would raise `Errors::InvalidShopError` for `attacker-controlled.example.com` and prevent the secret from ever being sent there. [7](#0-6)
