This is a genuine identity-binding gap in `ShopifyAPI::Webhooks::Request`: the `hmac` computed for verification (`Utils::HmacValidator.validate`) signs only `@raw_body` (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream in `WebhookMetadata` (and therefore in any host-app tenant routing) are read from unauthenticated HTTP headers with no cryptographic binding to the HMAC-signed body.

### Title
Webhook `shop` domain used for tenant identification is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC verified in `Utils::HmacValidator.validate` binds solely to the JSON payload bytes. The `shop` (and `topic`/`webhook_id`/`api_version`) values that `Registry.process` hands to the host application's webhook handler via `WebhookMetadata` come straight from the `x-shopify-shop-domain` header, which carries no HMAC coverage at all.

### Finding Description
`Request#hmac` decodes the `X-Shopify-Hmac-Sha256` header, and `Request#to_signable_string` supplies `@raw_body` as the bytes to re-sign: [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header value — this proves only that the *body* was signed by Shopify with `Context.api_secret_key`: [2](#0-1) 

`Registry.process` then trusts `request.shop` (read from the unauthenticated `shop-domain` header) to build the `WebhookMetadata` that is passed to the app's handler, and this is the value host apps use to identify which merchant/tenant the webhook belongs to: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`shop header used by the app == shop that produced/authorized the signed body`

but the gem only proves `hmac header == HMAC(body)`. The `shop-domain`, `topic`, and `webhook-id` headers are outside the signed material, so nothing in this gem stops those header values from being swapped for an arbitrary value while keeping a *validly signed body* from a different (attacker-controlled or otherwise legitimately-obtained) webhook delivery. Concretely: if the attacker can obtain any one legitimately-signed webhook body+HMAC pair (e.g., from their own shop, or from a shop where they can trigger a webhook, or from a leaked delivery), they can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `Registry.process` will pass HMAC validation (body unchanged) and hand the handler `WebhookMetadata.new(shop: <attacker-chosen victim domain>, ...)`, causing the host app to attribute the payload to the wrong tenant.

This differs from Shopify's documented server-side webhook design where the `X-Shopify-Shop-Domain` header is expected to be trustworthy purely because HMAC covers the body and the header is delivered over TLS from Shopify directly; but this gem's own verification logic does not itself bind the header to the signature, so any host application that reasonably assumes `HmacValidator.validate(request) == true` implies the entire `Request` (including `shop`) is authentic is misled by the gem's API surface.

### Impact Explanation
This is a cross-tenant data/action confusion: an attacker who can deliver an HTTP request to the app's webhook endpoint with a validly-signed body (its own shop's webhook, or any signed body they can obtain) can cause the host app to process that payload under a victim shop's identity, since `Request#shop` — the only tenant-identifying field the framework exposes as "HMAC validated" — is never part of the signed bytes. Depending on the webhook topic (e.g. `app/uninstalled`, `customers/data_request`, order/customer webhooks), this can lead the host app to delete/rotate credentials for the wrong shop, process GDPR-like data actions against the wrong tenant, or otherwise take actions attributable to a shop the attacker does not control. This satisfies "cross-tenant access" (Critical) because the security boundary broken is exactly the shop/tenant identity that `Registry.process` and `WebhookMetadata` rely on, and the gem's `Utils::HmacValidator.validate` gives host applications false confidence that the whole `Request`, not just its body, is authentic.

### Likelihood Explanation
Moderate-to-high: the attacker does not need Shopify credentials, an access token, or the app's `client_secret` — they only need any one previously-observed valid `(raw_body, hmac)` pair (trivially obtainable from their own store's webhook deliveries, which any unprivileged Shopify merchant/dev-store owner can generate) and the ability to send an HTTP request to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No TLS interception or privileged account is required.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the bytes covered by `to_signable_string`, or otherwise cryptographically bind them (e.g., derive the signed payload from headers+body rather than body alone), so that `Utils::HmacValidator.validate` proves the entire `Request` — including `shop` — is authentic, not merely the JSON body.

### Proof of Concept
1. Attacker triggers/observes a legitimate webhook delivery from their own shop `attacker-shop.myshopify.com`, capturing `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` value (valid because it was genuinely signed by Shopify with the app's shared secret).
2. Attacker sends a POST to the victim host app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` — unchanged — so validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and the host app processes the attacker's payload as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
