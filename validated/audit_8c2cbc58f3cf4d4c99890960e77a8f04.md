Confirmed: `HttpClient#initialize` (lib/shopify_api/clients/http_client.rb:16-18) builds the request target directly from `session.shop` (`"https://#{api_host || session.shop}"`), with no re-validation at that layer. This means whichever caller constructs the `Session` controls exactly where the app's `client_id`/`client_secret` get sent.

### Title
Unsanitized JWT `dest` claim used as OAuth token-exchange host, unlike every sibling flow - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` is the only OAuth-credential-sending flow in this gem that skips `Utils::ShopValidator.sanitize!` before using an attacker-influenced "shop" value as the HTTP host that receives the app's `client_id`/`client_secret`.

### Finding Description
`ShopValidator.sanitize!`/`sanitize_shop_domain` (`lib/shopify_api/utils/shop_validator.rb:9-64`) is the gem's designated binding check between an arbitrary "shop" string and an actual trusted Shopify host — it restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `shopify.com`, `spin.dev`, etc.) before that string is ever used to build a URL. Every OAuth-credential-sending method in `lib/shopify_api/auth/` enforces this binding: `ClientCredentials.client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25`), `RefreshToken.refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb:24`), and `TokenExchange.migrate_to_expiring_token` (`lib/shopify_api/auth/token_exchange.rb:103`) all call `Utils::ShopValidator.sanitize!(shop)` and use the *validated* result to build the `Session` that `Clients::HttpClient` turns into a request host (`lib/shopify_api/clients/http_client.rb:16-18`, `@base_uri = "https://#{api_host || session.shop}"`).

`TokenExchange.exchange_token` breaks this pattern: it takes `dest_shop = jwt_payload.shop` (`lib/shopify_api/auth/token_exchange.rb:40-41`) — derived from the `dest` claim of `JwtPayload` (`lib/shopify_api/auth/jwt_payload.rb:33-49`) — and feeds it *directly*, unsanitized, into `Session.new(shop: dest_shop)` (`lib/shopify_api/auth/token_exchange.rb:51`), which is then used to build the `HttpClient` that POSTs `client_id`/`client_secret`/`subject_token` to `https://#{dest_shop}/admin/oauth/access_token` (`lib/shopify_api/auth/token_exchange.rb:53-65`).

`JwtPayload#initialize` only checks `aud == Context.api_key` (`lib/shopify_api/auth/jwt_payload.rb:43-44`) and JWT signature/exp/nbf via `Context.api_secret_key`; it performs **no equality check that `dest`'s host is a trusted Shopify domain**, unlike `ShopValidator`. The identity binding that should hold is:
`host receiving client_secret == host validated by ShopValidator as a genuine Shopify shop`
For this one method, that binding is never enforced — `host receiving client_secret == raw JWT "dest" claim`, whatever it says.

### Impact Explanation
If an app ever calls `exchange_token` with a JWT whose `dest` value is not itself already constrained to a `myshopify.com`/trusted host (e.g., a custom/malformed session token, a token from a differently configured environment, or any code path where `Context.api_secret_key`/`old_api_secret_key` validation is looser than expected), the gem will send the app's `client_id` and `client_secret` to whatever host is in `dest`, i.e., SSRF carrying the app's OAuth credentials to an arbitrary host — meeting the High-impact bar ("SSRF with the app's credentials"). This is exactly the class of bug in the analog report: a check (`ShopValidator.sanitize!`) that the sibling code paths apply consistently is silently skipped for one specific route, letting a value bypass a security-relevant restriction.

### Likelihood Explanation
Exploitability is bounded by the fact that `JwtPayload` still requires a validly-HMAC-signed token under `Context.api_secret_key` (or `old_api_secret_key`) — so a token must be considered "genuine" by the app's own configured secret(s). This is markedly lower likelihood than a fully-unauthenticated SSRF, but it is a genuine inconsistency: the same trust level (a JWT session token, which is inherently less strictly scoped than an OAuth `code` from Shopify's redirect) is treated with a stronger binding check everywhere else (`migrate_to_expiring_token` uses the *same kind* of subject token type flow but does call `sanitize!`) except in `exchange_token`, indicating the omission is a code defect, not an intentional trust decision.

### Recommendation
In `TokenExchange.exchange_token` (`lib/shopify_api/auth/token_exchange.rb:29-89`), sanitize `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` before constructing `shop_session` and before returning it in `Session.from(shop: dest_shop, ...)`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Obtain/produce a session token that is validly signed under the app's configured `api_secret_key` (or `old_api_secret_key`) but whose `dest` claim is set to an attacker-controlled or non-`myshopify.com` host (e.g. because the value originates from a differently-trusted JWT issuer path, or a testing/staging secret is reused).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `lib/shopify_api/auth/token_exchange.rb:51` builds `Session.new(shop: dest_shop)` with the raw `dest` value, and `Clients::HttpClient` (`lib/shopify_api/clients/http_client.rb:18`) issues `POST https://<dest_shop>/admin/oauth/access_token` with `client_id`/`client_secret` in the body — sent to the attacker-chosen host, unlike the equivalent `migrate_to_expiring_token` call which would have rejected an untrusted `shop` via `ShopValidator.sanitize!`.         [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
