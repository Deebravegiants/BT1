Based on my investigation, I found a legitimate identity-binding gap in the webhook processing path, distinct from the OAuth callback path (which correctly binds `shop`/`host` into the HMAC via `AuthQuery#to_signable_string`, see [1](#0-0) ).

### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop` (and `topic`/`webhook_id`) values used by the app to attribute the webhook to a tenant are read from unauthenticated HTTP headers that are never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) . The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never mixed into `to_signable_string`: [3](#0-2)  and [4](#0-3) .

`Utils::HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (the raw body) and compares it with `verifiable_query.hmac`: [5](#0-4) . `Registry.process` calls exactly this check and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional binding check between the signed body and the shop header: [6](#0-5) .

The identity binding that should hold is: `shop header == tenant bound by the HMAC-signed payload`. Instead, only `raw_body == HMAC(raw_body, secret)` is verified; `shop` is parsed but never verified. An attacker who owns any shop with the app installed can capture one of their own legitimately-signed webhooks (valid `raw_body` + valid `hmac` for their own shop), then replay it to the app's public webhook endpoint after rewriting only the `shopify-shop-domain` header to a victim shop's domain. Because the header is excluded from the signable string, `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop` set to the victim shop while `body` still contains the attacker's own data: [7](#0-6) .

### Impact Explanation
Apps built on this gem are documented to trust `data.shop` from the processed webhook to perform shop-scoped actions (look up the shop's stored access token/session, write shop-scoped records, etc.), as shown in the gem's own webhook usage guidance: [8](#0-7) . Since `shop` is not bound to the HMAC-verified payload, an attacker who legitimately controls one tenant (any developer/merchant who can install the app) can make the library report a completely different, victim tenant as the origin of an HMAC-valid webhook carrying attacker-chosen content. This crosses a tenant boundary because the app cannot distinguish "this body legitimately originated from shop X" from "this body was replayed and re-labeled as shop X," which can lead to cross-tenant data corruption or actions being performed against the victim shop's stored credentials using attacker-controlled webhook body content.

### Likelihood Explanation
Requires only that the attacker be able to install the same public/third-party app on a shop they control (a normal, unprivileged capability for any Shopify merchant/developer) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access to the app's `client_secret` or any privileged Shopify credential is needed, since the legitimate HMAC from the attacker's own webhook is reused unmodified.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or otherwise verify that the shop domain header is consistent with a value cryptographically tied to the signed body (e.g., include it as part of the HMAC input, or require the consuming application to cross-check the header-derived shop against a shop already known to be associated with the specific webhook subscription/access token before trusting it for tenant-scoped operations).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H = HMAC(B, client_secret)`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) and compares to `H` — validation succeeds because `shop` was never part of the signed string, as shown in [2](#0-1)  and [9](#0-8) .
4. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` equal to the attacker's own data, as constructed in [7](#0-6) , despite the payload never having been produced by or for the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
