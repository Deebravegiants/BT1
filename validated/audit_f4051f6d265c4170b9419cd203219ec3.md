Audit Report

## Title
Cross-workflow denial-of-service via globally-scoped `requestID` collision in HTTP trigger gateway handler - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

## Summary
The gateway's `httpTriggerHandler` tracks in-flight trigger requests in `h.callbacks`, a map keyed solely by the client-supplied JSON-RPC `req.ID` string, with no binding to the `workflowID` or the authorized owner resolved during `authorizeRequest`. Any caller who can get *any* workflow request authorized (a normal, permissionless action) can pick a `requestID` that collides with a value used by an unrelated victim workflow, causing the victim's legitimate, correctly authorized request to be rejected with `jsonrpc.ErrConflict` and never dispatched to the DON.

## Finding Description
`HandleUserTriggerRequest` processes requests in order: validate → `resolveWorkflowID` → `authorizeRequest` (JWT check scoped to that specific `workflowID`) → `checkRateLimit` → `setupCallback` [4](#0-3) . `setupCallback` inserts into `h.callbacks[requestID]`, and if that key already exists — regardless of which workflow created it — the new (potentially entirely unrelated) request is rejected [2](#0-1) . The struct definition and test suite confirm the map is a single global `requestID -> savedCallback` table shared across every workflow the gateway serves [5](#0-4) [6](#0-5) . `authorizeRequest` verifies only that the signature is valid for the `workflowID` present in that request; it neither reserves nor scopes the `requestID` namespace per workflow [3](#0-2) . `validateRequestID` only rejects empty IDs and IDs containing `/`; it performs no per-workflow uniqueness scoping [1](#0-0) .

## Impact Explanation
A successful collision drops the legitimate request with `jsonrpc.ErrConflict` before it is dispatched to the DON, so the victim's workflow execution never starts — a targeted denial of service triggerable by an unrelated party. This matches an in-scope "unauthorized blocking of legitimate job/workflow execution" DoS impact class.

## Likelihood Explanation
Exploitation requires the attacker to have some authorized workflow of their own (permissionless, low cost to obtain) and to predict or race the exact `requestID` string the victim will use. Since `requestID` is entirely client-chosen with no server-enforced entropy or workflow-scoped namespace, the collision is far more feasible than intended whenever request IDs are non-random or predictable (e.g., sequential/deterministic client SDK IDs, retried requests). This is a real, reachable design flaw, not a hypothetical one — the collision path and rejection are directly demonstrated in the code and reproduced by existing tests that key `handler.callbacks` purely by `req.ID` [7](#0-6) .

## Recommendation
Scope the in-flight request guard to `(workflowID, requestID)` or bind it to the resolved `AuthorizedKey`/owner rather than `requestID` alone, e.g., use a composite key such as `workflowID + ":" + requestID` for `h.callbacks`, so no external, unrelated workflow can occupy or collide with another workflow's request-tracking slot.

## Proof of Concept
1. Attacker registers their own workflow `W_attacker` and obtains a valid signing key for it (ordinary, permissionless developer action) — passes `authorizeRequest` for `W_attacker`.
2. Attacker calls `HandleUserTriggerRequest` with `req.ID = "shared-id-123"` and `Workflow.WorkflowID = W_attacker`, which reaches `setupCallback` and inserts `h.callbacks["shared-id-123"]` [2](#0-1) .
3. Victim's client, authorized for a completely different workflow `W_victim`, sends a legitimate request also using `req.ID = "shared-id-123"`.
4. Because `h.callbacks` is keyed only by `req.ID`, the victim's `setupCallback` call finds the slot already occupied and returns `jsonrpc.ErrConflict`, and the victim's execution is never dispatched to the DON.
5. A Go unit test extending `TestHttpTriggerHandler_HandleUserTriggerRequest` to register two distinct workflows and issue two `HandleUserTriggerRequest` calls with the same `req.ID` but different `Workflow.WorkflowID` values, asserting the second returns `jsonrpc.ErrConflict`, would confirm this cross-workflow collision.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
