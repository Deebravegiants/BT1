## Analog Found

### Title
Loss of overpaid native token in `swapETHForExactTokens` due to non-standard Gnosis wrapper always consuming full `msg.value` - (File: `evm/src/utils/uniswapv2/GnosisUniswapV2Wrapper.sol`)

### Summary
On Gnosis, `EvmHost` and `IntentGatewayV2` use `GnosisUniswapV2Wrapper` as the configured `uniswapV2` router for converting native-token fee payments into the Hyperbridge `feeToken`. Unlike the real UniswapV2Router (which computes the exact input required for a requested output and automatically returns unspent native value to the caller), this wrapper's `swapETHForExactTokens` treats the *entire* `msg.value` as "spent" and mints/transfers WETH-equivalent for the whole amount, regardless of the requested `amountOut`.

### Finding Description
Every code path that pays Hyperbridge fees in native token relies on the standard Uniswap contract behavior where `swapETHForExactTokens(amountOut, ...)` spends only the computed `amounts[0]` (≤ `msg.value`) and refunds the difference, so calling code can safely compute `msgValue -= amounts[0]` and refund the remainder to the end user/solver.

`GnosisUniswapV2Wrapper.swapETHForExactTokens` breaks this contract:
```solidity
function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
    external payable returns (uint256[] memory)
{
    if (amountOut > msg.value) revert MsgValueLessThanExactAmount();
    (bool sent,) = WETH().call{value: msg.value}("");
    if (!sent) revert DepositFailed();
    IERC20(WETH()).safeTransfer(msg.sender, msg.value);
    uint256[] memory out = new uint256[](1);
    out[0] = msg.value;   // always equals the full value sent, not amountOut
    return out;
}
``` [1](#0-0) 

It only checks `amountOut <= msg.value` and then wraps and forwards the **whole** `msg.value`, reporting `amounts[0] = msg.value` no matter how much larger `msg.value` is than the actual `amountOut` needed. Every caller in the protocol assumes `amounts[0]` reflects the true cost and computes leftover as `msgValue -= amounts[0]`:

- `IntentGatewayV2.placeOrder` fee-escrow logic: `uint256[] memory amounts = ...swapETHForExactTokens{value: msgValue}(order.fees, ...); msgValue -= amounts[0];` then refunds any remaining `msgValue` to `msg.sender`. [2](#0-1) 
- `EvmHost.dispatch` and `EvmHost.fundRequest` forward `{value: msg.value}` directly to the router for fee payment with no independent tracking of leftover value. [3](#0-2) [4](#0-3) 

Because the Gnosis wrapper always reports `amounts[0] == msg.value`, `msgValue` is driven to zero regardless of the real required fee, so the "refund unspent native tokens" branches never trigger — the entire overpayment is silently absorbed as fee-token balance held by the gateway/host rather than returned to the payer.

### Impact Explanation
Any unprivileged user placing an order, filling an order, dispatching a POST/GET request, or funding a request with a native-token fee payment on a Gnosis deployment — while providing more native value than the exact fee required (a common and expected UX pattern, since users typically add slippage/safety margin, or bundle `nativeValue` for the fee plus native-token order inputs/outputs) — will have their entire excess native token permanently converted and retained by the protocol contract instead of refunded. This is a direct, unprivileged loss of user/solver funds reachable from a single transaction (`placeOrder`, `fillOrder`, `dispatch`, `fundRequest`), matching the reported bug class of "transferred Ether lost when amount sent doesn't exactly match the required swap amount."

### Likelihood Explanation
High likelihood: the SDK/tooling and documentation explicitly instruct users to send `nativeValue`/`msg.value` including margin for the fee-token swap (e.g., quoting via `quoteOrderFees`), and any solver/user sending marginally more than the exact fee (a standard practice to avoid transient price-slippage reverts) will trigger the loss on every affected call. No adversarial conditions or special permissions are required — it happens under normal usage on any chain configured with `GnosisUniswapV2Wrapper` as `uniswapV2`.

### Recommendation
Fix `GnosisUniswapV2Wrapper.swapETHForExactTokens` to only consume/wrap exactly `amountOut` of `msg.value`, transfer only `amountOut` worth of WETH to `msg.sender`, report `out[0] = amountOut`, and refund the difference (`msg.value - amountOut`) back to the original caller (or leave it un-deposited so the caller's own leftover-refund logic works correctly) — mirroring the real UniswapV2Router's exact-output semantics.

### Proof of Concept
1. Deploy `IntentGatewayV2`/`EvmHost` on Gnosis with `uniswapV2 = GnosisUniswapV2Wrapper`.
2. User calls `placeOrder` with `order.fees = X` and sends `msg.value = X + Y` (Y = accidental/intentional overpayment margin) as the native fee payment.
3. Inside `placeOrder`, `swapETHForExactTokens{value: X+Y}(X, ...)` is invoked; the wrapper wraps and transfers `X+Y` worth of WETH to the gateway and returns `amounts[0] = X+Y`.
4. `msgValue -= amounts[0]` yields `0`; the "refund unspent native tokens" branch never executes.
5. The user has paid `X+Y` in ETH for a fee that should have cost only `X`; `Y` is irrecoverably retained by the gateway as fee-token balance with no path for the user to reclaim it.
