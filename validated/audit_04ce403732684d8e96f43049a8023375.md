### Title
Unauthenticated, user-supplied QR `user_id` allows attacker-controlled account/signup misattribution - (File: `src/plans/qr_scan/user.rs`, `src/backend/user_status.rs`)

### Summary
The Sherlock finding is a "caller-specified account" bug class: a privileged operation (`rebalance`) lets an unprivileged caller name an arbitrary `account` whose approved funds are moved, instead of binding the operation to `msg.sender`. The orb-core analog is the legacy user-QR-code path, where the account/identity that a signup gets attributed to (`user_id`) is taken directly from an unauthenticated, attacker-suppliable string rather than being cryptographically bound to the physical person being scanned.

### Finding Description
`qr_scan::user::Data::try_parse` accepts three QR formats. The primary format relies on `orb_qr_link::decode_qr`, which returns a `user_data_hash` used later to cryptographically verify the backend-supplied `authenticated_app_data` via `user_data.verify(user_data_hash)` [1](#0-0) . However, the legacy `QR_CODE_V2` format is a bare, unsigned string `userid:<uuid>:<data_policy>` with no signature or hash at all [2](#0-1) , and it is parsed into a `Data` struct whose `user_data_hash` field is simply `None` [3](#0-2) . Notably, the regex even accepts a "shortened" partial UUID as a valid `user_id`, as demonstrated by the codebase's own test [4](#0-3) .

When `backend::user_status::request` receives a `valid: true` response without `backend_keys`/`authenticated_app_data` (the "old QR-code format" branch), it unconditionally treats the scanned `qr_code.user_id` as authoritative and returns a `UserData` with no cryptographic public keys and `id_commitment: None` [5](#0-4) . This `user_id` string — fully controlled by whatever is printed/displayed in the QR code shown to the camera — is then the value used to attribute the entire signup: it is sent to the backend as `userId` in the signup request [6](#0-5) , and used as the key for uploading the Personal Custody Package data (`upload_pcp_tier_0`, tier1/tier2) [7](#0-6) .

The only local guard against QR misuse is a same-code check between operator and user QR (`user_qr_code.user_id == operator_data.qr_code.user_id`) [8](#0-7)  — this does not verify that the presented `user_id` actually corresponds to the person standing at the Orb; it only prevents someone from reusing the operator badge as the "user" QR.

This mirrors the reported bug class precisely: just as `rebalance(account, ...)` let an unprivileged caller name whose approved assets get moved, orb-core's legacy path lets whoever controls the physically-presented QR code (not necessarily the enrolling person) name whose account identity the freshly captured biometric signup gets bound to at the backend, with no cryptographic binding equivalent to `msg.sender`.

### Impact Explanation
If exploited, an attacker who can generate/display a QR code containing another user's (or a targeted/guessed, given short-UUID acceptance) `user_id` could cause a signup performed by a different physical person to be uploaded and attributed to that `user_id` at the backend — a misattributed/cross-account signup. This is a data-integrity and identity-binding failure at the Orb-core layer: the code establishes no local guarantee that the enrolling human and the claimed `user_id` are the same entity when the legacy/unsigned QR path is exercised.

### Likelihood Explanation
Exploitability depends on backend-side acceptance of the legacy QR format returning `valid: true` without `authenticated_app_data`; that trust decision lives in the backend, outside orb-core. Within orb-core, the acceptance and downstream use of the unauthenticated `user_id` is unconditional whenever that backend response shape occurs, and the QR format itself permits attacker-chosen/short UUIDs, making the client-side logic a facilitating weak link with no additional local checks.

### Recommendation
Do not accept "valid" user QR-code responses that lack `authenticated_app_data`/cryptographic binding for account attribution; require the same `user_data_hash` verification path (`user_data.verify`) for all signup-attribution flows before using `user_id` to tag uploaded PCP tiers or the `signup_post` request, and reject/flag legacy-format QR-codes as non-authoritative rather than treating them as valid on par with the cryptographically verified format.

### Proof of Concept
1. Attacker crafts a QR code string `userid:<victim-uuid>:1` (accepted per `QR_CODE_V2`, including a truncated 8-4-4 partial UUID as validated by the existing unit test `test_v2_shortened`) [4](#0-3) .
2. Attacker (or any third party standing at the Orb) presents this QR as the "user" code; `try_parse` accepts it with `user_data_hash: None` [3](#0-2) .
3. If the backend's `/api/v1/user/{user_id}/status` (or v2 session endpoint) responds `valid: true` without `authenticated_app_data` (legacy branch), orb-core proceeds to run the full biometric capture on whoever is physically present and uploads the resulting PCP/tier data and signup record tagged with the attacker-supplied `user_id` [5](#0-4) [9](#0-8) .
4. Result: signup data for one physical person is uploaded and attributed to a `user_id` the attacker chose, without any cryptographic proof the enrolling person controls that identity.
