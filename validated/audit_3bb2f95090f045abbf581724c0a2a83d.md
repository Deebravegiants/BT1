### Title
`Application.unlock()` Flips `lockedAtom` to Unlocked Before Awaiting Lifecycle Hooks, So a Single Failing Plugin Hook Leaves the Wallet in a Desynced "Unlocked" Internal State - (File: `features/application/src/modules/application.ts`)

### Summary
The `SponsorVault` bug class is: a single external/plugin call that can revert causes an entire critical cross-cutting flow to break down entirely (denial-of-service). In hydra's `Application` module, the analogous cross-cutting flow is the lifecycle-hook broadcast performed by `fire()`, which is invoked from `unlock()`/`lock()` to notify every registered feature/plugin (`onUnlock`, `onMigrate`, etc.) that the wallet state changed. Unlike `lock()`, `unlock()` sets the wallet's internal locked-state atom to `false` **before** the hooks that can fail are awaited, so a single throwing hook (owned by any one feature — the same "any-one-party-breaks-everything" failure mode as `SponsorVault`) leaves `#lockedAtom` desynced from the actual outcome of `unlock()`.

### Finding Description
`fire()` runs each registered hook sequentially and re-throws on the first failure: [1](#0-0) [2](#0-1) 

`unlock()` sets `#lockedAtom` to `false` immediately after `#wallet.unlock(opts)` succeeds, and only afterwards awaits `fire(Hook.Migrate)` and `fire(Hook.Unlock)`: [3](#0-2) 

Because `fire()` aborts as soon as any one hook function throws (line-level behavior at `application.ts:236-243`), any plugin's `onUnlock`/`onMigrate` implementation throwing an error — for example due to a bug in one feature module, a storage/migration error, or an unexpected exception in a third-party-supplied adapter — will cause the `unlock()` promise itself to reject and propagate to the caller. However, `#lockedAtom` was already flipped to `false` on line 414, *before* the failing hook ran. This mirrors the `SponsorVault` root cause exactly: a single failing external/plugin call (`s.sponsorVault.reimburseLiquidityFees`/`reimburseRelayerFees` in the C4 report vs. any one plugin's `onUnlock`/`onMigrate` hook here) is allowed to corrupt/abort a shared critical transition that many independent parties rely on, with no isolation (no try/catch or fail-safe wrapping) around the individual hook calls at the point where state has already been mutated.

Numerous features observe or gate behavior directly on this locked/unlocked atom rather than on the `unlock()` promise outcome — e.g. `connectedOriginsPlugin.onUnlock` starts broadcasting `connectedOriginsAtom` and begins observing `enabledWalletAccountsAtom` to push account data to connected dApp origins as soon as its own `onUnlock` runs: [4](#0-3) 

and `hardwareWalletsPlugin.onUnlock`/`assets-feature` `onUnlock` similarly start pushing live state to the UI/port on `Hook.Unlock`: [5](#0-4) [6](#0-5) 

Since `#lockedAtom` is set to `false` before the hook chain finishes, and hooks run in priority order with each earlier hook's side effects (atom observers starting, RPC/port emission) already committed by the time a later hook throws, callers of `application.unlock()` that receive a rejected promise (and may re-prompt for a passphrase assuming the wallet is still locked) can be left with a wallet whose internal `#lockedAtom` says "unlocked" and whose earlier-priority plugins have already begun exposing account/session state over the port to connected origins/UI.

### Impact Explanation
This is a state-consistency / auth-bypass-adjacent flaw, not a pure DoS: the wallet's canonical lock indicator (`#lockedAtom`), which many other modules and UI surfaces treat as the source of truth for "is the wallet safe to interact with," can be `false` even though `unlock()` reported failure to its caller. Any consumer that gates sensitive operations (mnemonic access, signing, connected-origin account exposure) on `#lockedAtom`/`isLocked` rather than on successful resolution of the `unlock()` call could treat the session as authenticated/unlocked prematurely, which is a state-desync class of auth bypass consistent with the required "auth bypass / cross-origin/account privilege bleed" impact bar. It is bounded by the fact that a hook failure requires an actual bug/exception in one of the built-in plugins (there is no external "SponsorVault"-style pluggable third party in this specific flow), which is a difference from the original report's fully third-party-controlled trust boundary.

### Likelihood Explanation
Likelihood depends on any registered `onUnlock`/`onMigrate` plugin throwing during normal operation (e.g., storage errors, malformed migration data, or a bug in any one of the many first-party feature plugins wired via `attachPlugins`/`ioc.getByType('plugin')`). Given the large and growing number of independently maintained plugins hooked into the same `Hook.Unlock`/`Hook.Migrate` chain (auth, connected-origins, hardware-wallets, assets-feature, wallet-accounts, market-history, fusion-local, etc., all shown wired via `sdks/headless/src/plugins/attach.js`), any single one throwing is sufficient to trigger the desync — this is a realistic and not merely theoretical occurrence.

### Recommendation
Do not commit `#lockedAtom` (or any similarly load-bearing state atom) to its "unlocked" value until all `unlock()`-time hooks have successfully completed, or explicitly roll it back to `true` (and treat the wallet as still locked) if `fire(Hook.Migrate)`/`fire(Hook.Unlock)` throws. Additionally, apply the same fail-isolation pattern recommended in the original report: wrap individual hook invocations in `fire()`/`executeHooks` so that one failing plugin cannot abort the propagation of `Hook.Unlock` to all other registered plugins, and surface hook failures via error tracking rather than allowing them to leave shared security-relevant state inconsistent.

### Proof of Concept
1. Register a plugin whose `onUnlock` throws (any bug in a first-party feature's `onUnlock`/`onMigrate` implementation reproduces this; for a minimal repro, register a definition analogous to the test harness in `sdks/headless/__tests__/attach-plugins.test.js` with `onUnlock: () => { throw new Error('boom') }`).
2. Call `exodus.application.unlock({ passphrase })` (`features/application/src/modules/application.ts:409-426`).
3. Observe: `await this.#wallet.unlock(opts)` succeeds, `await this.#lockedAtom.set(false)` executes (line 414), then `await this.fire(Hook.Unlock)` (line 417) throws because the malicious/buggy plugin's hook rejected.
4. The `unlock()` promise rejects to the caller (who may treat the wallet as still locked and re-render a passphrase prompt), but `#lockedAtom` remains `false` and any plugin with higher priority than the failing one (e.g., `connectedOriginsPlugin`, which starts pushing `enabledWalletAccountsAtom` data to connected dApp origins on `onUnlock`) has already run and begun exposing unlocked-session state.
