### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not bound by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only. The `shop`, `topic`, `webhook_id`, and `api_version` values — all of which are read from unauthenticated HTTP headers and then trusted by `Webhooks::Registry.process` to route/attribute the webhook — are never included in the signed material. This breaks the identity binding `hmac(body) == hmac(body)` **with respect to shop**, i.e. `authenticated_shop == acted_upon_shop` no longer holds.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms the signature by recomputing HMAC over `verifiable_query.to_signable_string` (the raw body) using the app's shared `client_secret`: [4](#0-3) 

Because the same `client_secret` is used for every shop that has the app installed, any two webhook deliveries with identical raw bodies (which is common — many topics such as `app/uninstalled`, and several mandatory GDPR topics, deliver a fixed/empty JSON body like `{}`, and even non-trivial payloads can be predicted or reused) produce an identical HMAC value **regardless of which shop generated them**. An attacker who installs the app on their own store (an ordinary, unprivileged action) can capture such a genuine `(raw_body, hmac)` pair from a webhook Shopify sends to the app's public endpoint, then replay the exact same body and HMAC to the same endpoint while forging the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` will accept it because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This allows cross-tenant impersonation in webhook processing: the app's business logic (installed by the integrator on top of this gem) will act as if an event happened for shop B when it was actually forged by an unprivileged user who only controls shop A. Depending on how the host app uses `WebhookMetadata#shop` (e.g. to look up/mutate per-shop state, trigger `shop/redact`, `app/uninstalled` cleanup, or write to a datastore keyed by shop), this can lead to cross-tenant state corruption, denial of a legitimate merchant's app functionality, or data leakage — matching the "cross-tenant access" High/Critical impact class, since the identity boundary the gem is supposed to enforce (verified shop == acted-upon shop) is not actually enforced.

### Likelihood Explanation
Moderate-to-high: the webhook endpoint is by necessity a public HTTP endpoint reachable by anyone; obtaining a valid `(body, hmac)` pair only requires installing the app once as an ordinary merchant (no special privilege, no leaked secret needed) and triggering (or waiting for) any webhook with a fixed/predictable body. No access to `client_secret`, access tokens, or TLS interception is required.

### Recommendation
Bind the security-relevant identity fields into the signed material, or otherwise cryptographically tie the trusted `shop`/`topic`/`webhook_id` values to the specific delivery. At minimum:
- Do not trust `request.shop` purely from the header for tenant-sensitive actions; look up the shop's own webhook signing/session and re-verify identity server-side.
- Consider making `Utils::HmacValidator` reject topic/shop mismatches by requiring the consuming app to cross-check `shop` against a known/installed-shop list before acting, and document this requirement prominently since the gem itself cannot include `shop` in the HMAC (Shopify signs only the body).
- At minimum, add explicit documentation/guardrails warning integrators that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC and must not be treated as authenticated without additional verification (e.g., matching against a shop known to have this webhook subscription registered).

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com` and lets it fire a webhook with a fixed/empty body, e.g. `app/uninstalled` with body `{}`.
2. Attacker records the HMAC header Shopify sent for that delivery: `hmac = OpenSSL::HMAC.digest("sha256", client_secret, "{}")` (attacker doesn't need to know `client_secret`; they just capture the value Shopify computed and sent).
3. Attacker sends a forged POST to the app's public webhook endpoint with the same raw body `{}` and the same `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks the body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to perform uninstall/cleanup logic for the victim shop even though the victim shop never sent this event.

          received_signature = verifiable_query.hmac
