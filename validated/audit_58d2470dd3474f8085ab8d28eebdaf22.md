### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` for a webhook exclusively from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that the gem verifies only covers the raw request body. Because the app's webhook HMAC secret (`Context.api_secret_key`) is the same for every shop that installs the app, any shop that has genuinely installed the app can capture one of its own valid, HMAC-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` will still report the signature as valid because it never checks the shop field, so the app processes the forged webhook as if it came from the victim tenant.

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` and exposes `shop` straight from a header, but signs only the body: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC strictly over `to_signable_string`, which for a webhook `Request` is just `@raw_body`: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the metadata handed to the app's handler, without any additional binding check between the verified body and the claimed shop: [3](#0-2) 

The equality this breaks is: `shop authenticated by HMAC` should equal `shop the handler acts on`. Instead, only `body authenticated by HMAC == body handler receives` holds; `shop` is parsed but never part of the signed bytes. Since the app's webhook secret (`api_secret_key`) is identical across all of the app's installed shops (it's the developer's app-level client secret, not a per-shop secret), a genuine — but otherwise unprivileged relative to other tenants — merchant who installs the app can:
1. Receive one authentic webhook from Shopify for their own shop (any topic the app registers), capturing raw body + `X-Shopify-Hmac-Sha256` header — both valid.
2. Replay that exact body/HMAC pair to the app's webhook endpoint, only changing the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`, since that also isn't signed) header to point at a victim shop.
3. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body, and `Registry.process` dispatches the handler using the attacker-supplied `shop` value.

### Impact Explanation
This achieves cross-tenant access: an app processing this forged, "verified" webhook will attribute the event's side effects (e.g., record updates, entitlement changes, data written keyed by shop, uninstall/GDPR handling, order/customer data processing) to a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since any app that keys persistence or business logic in its webhook handler off `WebhookMetadata#shop` can be manipulated by one tenant to affect another tenant's data/state.

### Likelihood Explanation
Likelihood is realistic for any app that installs on multiple shops (a standard use case for apps built on this gem): the attacker needs only to be a legitimate (even trial) installer of the app to obtain one authentic signed webhook, then replay it with a modified header — no access to `api_secret_key` or any victim credentials is required, only network access to the app's public webhook endpoint and the app's own registered webhook.

### Recommendation
Bind `shop` (and `topic`/`webhook_id` if used for authorization decisions) into the HMAC-signed content, or otherwise cryptographically bind the verified body to the claimed shop before dispatch — e.g., have `Webhooks::Request#to_signable_string` include the shop/topic headers in the signed string (matching what Shopify's HMAC actually protects would require Shopify's cooperation), or, more practically, have the gem document/enforce that consuming apps must validate `request.shop` against the shop that originally registered the specific `webhook_id`/subscription rather than trusting the header verbatim.

### Proof of Concept
1. Install the target Shopify app as Shop A (a normal merchant action) and subscribe to any webhook topic the app registers.
2. Capture a genuine webhook delivery to the app's endpoint: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`).
3. Re-send an HTTP request to the same endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. In the app, `Utils::HmacValidator.validate(request)` returns `true` (line `lib/shopify_api/utils/hmac_validator.rb:12-31`, since only `B` is checked), and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to perform Shop A's webhook action against Shop B's tenant data.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
