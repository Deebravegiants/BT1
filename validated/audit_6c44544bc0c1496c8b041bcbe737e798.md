### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook by validating the HMAC over the **raw body only**, but the `shop` value that the gem hands to the app's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is **not included in the signed data**. Any party that possesses one valid `(raw_body, hmac)` pair (e.g., a webhook delivered to their own, legitimately-installed shop) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the HMAC check will still pass. This breaks the binding "shop authenticated == shop the body's HMAC was computed for."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop` is derived purely from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `request.hmac` against `compute_signature(request.to_signable_string, secret)` — i.e., against the raw body, never against `request.shop`: [3](#0-2) [4](#0-3) 

After the HMAC check succeeds, the (unauthenticated) `request.shop` is passed straight into `WebhookMetadata`, which the app's own handler relies on to identify which tenant/shop the webhook belongs to: [5](#0-4) 

The documented integration pattern feeds the entire HTTP header hash — fully attacker-controlled when the request is delivered directly to the app's public webhook route — straight into `Request.new`: [6](#0-5) 

Root cause equality that should hold but doesn't:
`shop authenticated by HMAC` == `shop delivered to the handler as the tenant identity`.
Here, the HMAC only authenticates `raw_body`; `shop` is an independent, unsigned header value, so the equality can be broken by anyone who owns a valid `(raw_body, hmac)` pair for any shop (including their own) and simply changes the header when replaying it to the app's public webhook endpoint.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who legitimately receives a webhook for their own store (installing any public app is unprivileged, self-service access — no `api_secret_key`, token, or special privilege needed) can capture that valid `(body, hmac)` pair and replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop. Because `Registry.process` never checks that the signed body actually corresponds to the claimed shop, the app's handler will process/store the replayed event as if it originated from the victim tenant — e.g., corrupting the victim's per-shop state, triggering shop-scoped side effects (inventory/order updates, uninstall/GDPR handling, billing changes) keyed on `data.shop`. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High/likely for any app that trusts `WebhookMetadata#shop` (as the gem's own documentation instructs) without independently re-validating it against a known/authorized shop list. No secrets are required — only a genuine webhook delivery to an attacker-owned store, which is trivially obtainable by installing the public app.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the signed material, or otherwise verify server-side that the shop asserted in the header is one that is registered/authorized for this app before trusting `request.shop`. At minimum, `to_signable_string` should incorporate the `shop-domain` header (mirroring how `AuthQuery#to_signable_string` binds `shop` into the OAuth callback signature) so the HMAC check fails if the header is altered independently of the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`).
2. Attacker's server captures the genuine delivery: `raw_body` and header `X-Shopify-Hmac-Sha256: <valid_hmac>` (both are visible to the attacker, since it is delivered to infrastructure they control).
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only re-hashes `raw_body`:
```ruby
def to_signable_string
  @raw_body
end
```
5. `Registry.process` invokes the app handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the app to process attacker-supplied data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
