Confirmed: `FeeVault.claim()` reads `creatorBalance[msg.sender]`, zeroes it, and does `$.usdc.safeTransfer(msg.sender, amount)` — the claimant identity, the balance key, and the payout recipient are all the same fixed `msg.sender` address, with no separable "pay-to" parameter.This confirms the mechanism: `Bonding.transferCreator` (`packages/contracts/src/Bonding.sol:738-748`) only mutates `info.creator` — it never touches `FeeVault.creatorBalance`, which is keyed on the creator address that was in effect at the time each `Zap._accrueFee` call ran. ### Title
Creator fee balances in FeeVault become permanently unclaimable if the creator address is a USDC-blacklisted or otherwise transfer-incompatible address, with no `_to` override or balance-migration path - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` couples three things to a single fixed address, `msg.sender`: the identity used to look up `creatorBalance[msg.sender]`, the address whose balance is zeroed, and the recipient of the `safeTransfer`. There is no `_to` parameter, so a creator can never redirect the payout to an address capable of receiving it.

### Finding Description
`FeeVault.claim()` is: [1](#0-0) 

Fee accrual (`Zap._accrueFee` → `FeeVault.accrue`) attributes fees to `Bonding.tokenInfo(token).creator` at the time of each buy/sell: [2](#0-1) 

The reserve/fee asset is real USDC, which the codebase's own dependency tree explicitly models as having an address-level blacklist (`isBlacklisted`), a real-world Circle-governed mechanism unrelated to any protocol logic: [3](#0-2) 

If a creator's address is later added to Circle's USDC blacklist (or is a smart-contract wallet that reverts/self-destructs/becomes otherwise unable to receive), every future `claim()` call from that address reverts inside `SafeERC20.safeTransfer`, because `IERC20.transfer` itself reverts for blacklisted addresses. The only "recipient redirection" primitive in the system, `Bonding.transferCreator`, only reassigns `info.creator` for *future* fee attribution — it does not touch `FeeVault`'s existing `creatorBalance[oldCreator]` mapping entry: [4](#0-3) 

Because `creatorBalance` is keyed strictly by the historical creator address baked into past `accrue()` calls, and `claim()` always pays `msg.sender` with no override, the stranded balance for the blacklisted/incompatible address can never be moved to a new, working address by any function in `FeeVault` or `Bonding`. This mirrors the reported bug class exactly: eligibility address == payout address, with no separation allowing redirection.

### Impact Explanation
Any amount of accrued USDC creator fees sitting in `creatorBalance[creator]` at the moment `creator` becomes blacklisted (or otherwise incapable of receiving a plain ERC20 transfer) is permanently frozen inside `FeeVault`. `totalAccruedCreator` still counts it as backed, so the funds are never recoverable via `sweepDonations()` either (that function only sweeps the *unbacked* surplus). There is no admin override, timelock recovery, or governance path to move a stuck balance — this is a permanent, protocol-wide freezing of legitimately earned creator funds for any launched token whose creator's address is later blacklisted.

### Likelihood Explanation
This does not require any protocol bug or attacker action beyond a real-world event: Circle blacklisting a USDC address is a documented, non-hypothetical occurrence (sanctions compliance, stolen-fund freezes, etc.), and any creator of any launched token is a candidate. Given the protocol's stated design of USDC as the sole fee currency and permissionless `Bonding.launch`/creator assignment, likelihood is non-trivial over the system's lifetime, though it depends on an external factor (Circle's blacklist action) rather than being attacker-triggerable at will.

### Recommendation
Separate the balance lookup/zeroing key from the payout destination in `claim()`:
```solidity
function claim(address to) external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(to, amount);
    emit CreatorFeesClaimed(msg.sender, to, amount);
}
```
This lets a creator whose own address is later blacklisted still authorize payout to a fresh, working address using the same `msg.sender`-based authorization the protocol already relies on, without introducing any new privileged role.

### Proof of Concept
1. `creator` launches a token via `Bonding.launch`; trades accrue fees via `Zap._accrueFee` → `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`, building up `creatorBalance[creator]`.
2. Circle blacklists `creator`'s address on USDC (external event, not a protocol action).
3. `creator` calls `Bonding.transferCreator(token, newAddress)` to try to move future attribution — this only updates `info.creator`; `FeeVault.creatorBalance[creator]` is untouched (`packages/contracts/src/Bonding.sol:738-748`).
4. `creator` (or anyone acting on their behalf) calls `FeeVault.claim()` from the blacklisted address — the internal `safeTransfer(msg.sender, amount)` reverts because USDC's `transfer` reverts for a blacklisted `to`.
5. There is no other function in `FeeVault` that can move `creatorBalance[creator]` to `newAddress` or any other address — the entire pooled balance is permanently stuck.
