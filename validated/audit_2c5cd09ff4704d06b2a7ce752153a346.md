## Finding

### Title
Share-pool zero-total-coins branch lets stale shareholders steal newly deposited stake after slashing — [File: aptos-move/framework/aptos-stdlib/sources/pool_u64.move]

### Summary
The report's core invariant is: *"a proportional relation (quotient/remainder or share-price) must not be silently reset to a trivial value when the divisor becomes zero while the other side of the relation is still non-zero."* In EraVM, `q=0,rem=0` when divisor is zero broke the `src0 = q*src1+rem` relation. The Aptos-native analog is `pool_u64::amount_to_shares_with_total_coins`, which treats a pool as "fresh" whenever `total_coins == 0`, even when `total_shares != 0` — i.e. it silently drops the share-price relation `new_shares = coins_amount * total_shares / total_coins` instead of preserving it, exactly like the EraVM bug dropped the `mul/div` relation for a zero divisor.

### Finding Description
`amount_to_shares_with_total_coins` computes new shares for a deposit: [1](#0-0) 

When `total_coins == 0` (regardless of whether `total_shares` is also 0), the function falls into the "fresh pool" branch and mints `coins_amount * scaling_factor` shares, completely ignoring any pre-existing `total_shares`. This is safe only if `total_coins == 0` implies `total_shares == 0` — an invariant that normally holds because `buy_in`/`redeem_shares` change both fields together.

That invariant is broken by `delegation_pool::synchronize_delegation_pool`, which sets `total_coins` directly from the real, on-chain stake amount rather than from `pool_u64`'s own bookkeeping: [2](#0-1) [3](#0-2) 

The comment `// handle any slashing applied to \`active\` stake` at line 1896-1897 confirms the code is explicitly designed to allow `active` (and thus the pool's `total_coins`) to fall below the shares-pool's previously recorded value, including down to `0`, while `active_shares.total_shares()` remains non-zero (existing delegators still hold shares in `active_shares`).

Once `active_shares.total_coins() == 0` with `total_shares > 0`, the next `add_stake` call: [4](#0-3) 
routes through `buy_in`/`amount_to_shares`, which hits the zero-`total_coins` branch and mints the new depositor `coins_amount * scaling_factor` shares while `total_shares` is bumped by that same amount: [5](#0-4) 

The pre-existing (now worthless) shareholders are never removed or reset — they keep their old share count. Once `total_coins` becomes non-zero again (topped up entirely by the new depositor), those stale shares instantly represent a proportional claim on the new depositor's funds via `shares_to_amount`: [6](#0-5) 

### Impact Explanation
This corrupts custody accounting by moving value to the wrong holder: shareholders whose stake was reduced to (near) zero can passively regain a proportional claim on stake deposited by an unrelated, later delegator, without contributing any coins themselves. Depending on the ratio of stale `total_shares` to the new deposit, a substantial fraction of a new delegator's stake can be diluted away to old shareholders — a direct transfer of custody-held value to unauthorized parties, matching the "Supply or custody accounting corruption that moves value to the wrong holder" impact bucket.

### Likelihood Explanation
The trigger condition (`active_shares.total_coins()` dropping to exactly/near zero while `total_shares` remains positive) requires the underlying stake pool's `active` stake to be reduced far more than delegator withdrawals reduce `total_shares` in lockstep — i.e. a slashing-like event. I could not confirm within this codebase that Aptos mainnet currently has an active, triggerable slashing mechanism that reduces `active` stake independent of the delegation-pool's own withdrawal accounting; the `synchronize_delegation_pool`/`calculate_stake_pool_drift` code explicitly anticipates and handles this case ("handle any slashing applied"), but I did not locate the code path that actually invokes such a stake-reduction in this repo within the available context. This materially limits confidence that the precondition is currently reachable on mainnet, so likelihood is uncertain/low pending verification of an active slashing trigger.

### Recommendation
In `pool_u64::amount_to_shares_with_total_coins` (and the `pool_u64_unbound` equivalent), only treat the pool as "fresh" when **both** `total_coins == 0` and `total_shares == 0`. If `total_coins == 0` but `total_shares > 0`, either abort (pool has stranded, unredeemable/valueless shares that must be resolved via an explicit path) or require callers to reconcile/zero out `total_shares` before allowing further `buy_in`, rather than silently minting new shares that let stale shareholders claim newly deposited coins.

### Proof of Concept
1. Delegator A adds stake; `active_shares.total_coins = X`, `total_shares = X` (1:1 initially).
2. A slashing-like event reduces the stake pool's real `active` stake to `0` (per `calculate_stake_pool_drift`'s `active < pool_active` branch).
3. `synchronize_delegation_pool` calls `pool.active_shares.update_total_coins(0)` — now `total_coins = 0`, `total_shares = X > 0`.
4. Delegator B calls `add_stake` with `amount = Y`. `buy_in_active_shares` → `amount_to_shares` hits the `total_coins == 0` branch and mints `Y * SHARES_SCALING_FACTOR` shares to B, while A's stale `X` shares remain untouched. `total_shares` becomes `X + Y*scaling_factor`, `total_coins` becomes `Y`.
5. `shares_to_amount` for A now returns `X/(X+Y*scaling_factor) * Y` coins — a positive amount funded entirely by B's deposit, even though A contributed nothing after the slashing event.

Note: step 2 (an actual, exploitable stake-reduction mechanism) could not be independently confirmed in the explored code; this should be verified against `stake.move`/governance slashing logic before treating this as confirmed-exploitable on mainnet.

```text
    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }
```

```text
    /// Return the number of coins `shares` are worth in `self` with a custom total coins number.
    /// `shares` needs to big enough to avoid rounding number.
    public fun shares_to_amount_with_total_coins(self: &Pool, shares: u64, total_coins: u64): u64 {
        // No shares or coins yet so shares are worthless.
        if (self.total_coins == 0 || self.total_shares == 0) {
            0
        } else {
            // Shares price = total_coins / total existing shares.
            // Shares worth = shares * shares price = shares * total_coins / total existing shares.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(shares, total_coins, self.total_shares)
        }
    }
```
