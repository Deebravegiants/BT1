### Title
Attacker-crafted swap route executes arbitrary contracts under the caller's authorization tree, enabling theft of unrelated wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The XStream report's bug class — attacker-controlled serialized input deserialized into objects/code paths the victim never intended (used there for SSRF) — maps directly onto the controller's strategy path: the `swap` argument is an opaque attacker-supplied XDR payload that the router deserializes into contract addresses and invokes, with no allowlist of pools, tokens, or venues. A malicious route names an attacker-deployed "pool" contract; when that code runs inside `swap_collateral` (or `swap_debt`, `repay_debt_with_collateral`, `multiply`), any `token.transfer(victim, attacker, x)` it makes is recorded as a child of the victim's own authorization entry, and simulation returns that poisoned tree for the victim to sign.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` passes the user-supplied `StrategySwap` XDR straight to `router.execute_strategy` after authorizing only one exact input transfer (`authorize_transfer_as_current`, line 34). The controller grants invocation authority, not an allowance, and correctly bounds its own exposure — but it performs zero validation on which contracts the payload will cause to run. `docs/explanation/threat-model.md:154-165` states the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" and that the resulting loss "is then the caller's wallet, not the routed amount." The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the mechanism end-to-end: a `RogueHopPool` named in the route calls `transfer(alice, attacker, WALLET_BALANCE)` on an unrelated token during `swap_collateral`; recording-mode simulation attaches that transfer under Alice's `swap_collateral` auth entry (lines 195-227), and signing that tree authorizes the theft in enforcing mode (lines 258-269). The controller's measured-output check (`verify_router_output`, lines 75-84) and the final health-factor gates all pass because the rogue pool can still pay fair `token_out` — the theft is orthogonal to the swap economics.

### Impact Explanation
Theft of user funds. A victim running `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` with a route built by an attacker (e.g., via a malicious quote API or frontend) loses arbitrary balances of arbitrary tokens held in their wallet — including tokens the protocol never listed. The theft amount is unbounded by `amount_in`, the payload `min_out`, or the controller's risk gates; it is bounded only by what the victim's signed auth tree covers, which simulation populates automatically with the rogue transfer. The protocol itself remains solvent, but the user-facing loss is total for the targeted wallet token.

### Likelihood Explanation
Exploitation requires the victim to submit a controller strategy call carrying the attacker's route XDR and to sign the auth tree simulation returns. Soroban auth trees are opaque to most signers — the extra `transfer` child is a nested XDR entry that wallets do not render plainly — so a victim expecting an ordinary "approve this swap" prompt will sign the poisoned tree. No privileged role, leaked key, or protocol misconfiguration is needed; the attacker only needs to get a crafted route in front of a user, the same phishing surface the XStream gadget exploits at the deserialization layer. The threat model itself acknowledges this path and shifts verification to off-chain clients ("a client must decode the route it signs"), which is a mitigation, not a protocol-level guard — the contracts enforce nothing.

### Recommendation
Enforce a venue/pool allowlist at the point the route is consumed: the router (or the controller before dispatch) should validate that every pool and token address referenced by the deserialized `StrategyPayload` belongs to a governance-managed registry, analogous to the Blend-pool approval list used for `migrate_from_blend`. Alternatively, the controller could require the swap path to run under `authorize_as_current_contract` with a fixed sub-invocation shape so that calls outside the expected hop set cannot be attached to the caller's auth tree. At minimum, emit/route-hash validation so the signed payload is bound to a route the operator has vetted rather than raw attacker XDR.

### Proof of Concept
A working demonstration exists at `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool` (lines 52-72) configured via constructor to call `wallet_token.transfer(alice, attacker, amount)` from its `swap` entrypoint.
2. Attacker constructs a `RoutedSwap` XDR naming that pool as the hop (lines 111-125) and gets it in front of Alice as a swap quote.
3. Alice calls `controller.swap_collateral(alice, account_id, USDC_key, 5_000 USDC, ETH_key, route)`. Simulation in recording mode executes the rogue pool, and the host records the wallet-draining `transfer` as a sub-invocation of Alice's `swap_collateral` entry (asserted at lines 206-222); Alice's wallet is emptied (lines 224-225).
4. In enforcing mode, signing exactly the tree simulation returned authorizes the theft — `try_swap_with_signed_tree` with the `stolen_transfer` child succeeds and `assert_eq!(s.wallet(&s.alice), 0)` (lines 258-268). An honest root-only tree is correctly refused (lines 240-256), which is precisely why victims are taught to "just sign what simulation returns" — the very behavior the rogue payload weaponizes.
