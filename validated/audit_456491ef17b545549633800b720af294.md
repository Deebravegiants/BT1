### Title
`decode_public_key` performs only length validation, allowing degenerate/low-order Curve25519 keys to defeat `sealedbox::seal` encryption of biometric data - ([File: src/backend/user_status.rs])

### Summary
`decode_public_key` in `src/backend/user_status.rs` accepts any base64 string that decodes to exactly 32 bytes as a valid `sodiumoxide::crypto::box_::PublicKey`, with no check that the bytes represent a valid, non-degenerate Curve25519 point. These attacker/backend-supplied keys are stored as `Credentials::backend_iris_public_key`, `backend_normalized_iris_public_key`, `backend_face_public_key`, `backend_tier2_public_key`, and `self_custody_user_public_key`, and are fed directly into `encrypt()` in `src/plans/personal_custody_package.rs`, which calls `sodiumoxide::crypto::sealedbox::seal`.

### Finding Description
`decode_public_key` only checks base64-decodability and exact 32-byte length before wrapping the bytes in `PublicKey`: [1](#0-0) 

These keys flow unchecked from the backend's `/status` response (`BackendKeys`/`UserData`) through `request()`: [2](#0-1) 

into `personal_custody_package::Credentials` via `TryInto` conversion, and then into `Package::build`, where each biometric artifact (iris IR images, normalized iris images/masks, face images, tier2 data, and the tier0/tier1/tier2 outer archives) is sealed using these keys: [3](#0-2) 

`encrypt()` simply calls `sodiumoxide::crypto::sealedbox::seal(data, public_key)` and asserts only that ciphertext differs from plaintext — no check on key validity or resulting shared-secret strength: [4](#0-3) 

X25519 (used internally by `crypto_box_seal`/`sealedbox`) clamps private scalars to multiples of 8. Any public key that is a low-order point (order dividing 8 — e.g., the all-zero point or other known small-order Curve25519 points) will, when multiplied by *any* clamped private scalar, always produce the same fixed/degenerate shared secret, independent of the ephemeral secret key generated internally by `seal()` for every call. Because `decode_public_key` performs no point-validity/order check, and `encrypt()` performs no rejection of such degenerate keys, an attacker who supplies (through their own signup session's backend response) a low-order 32-byte value as `iris`/`normalizedIris`/`face`/`tier2` `publicKey` or as `selfCustodyPublicKey` causes every subsequent `sealedbox::seal` call using that key to derive a shared secret from a small, publicly known set of values — computable without knowledge of any private key. This lets the attacker (posing as, or through, the fake/compromised backend response of their own signup session) decrypt the sealed iris/normalized-iris/face biometric tiers that are supposed to be confidential to the real backend private key holder.

### Impact Explanation
This breaks the core containment guarantee of the Personal Custody Package: iris images, normalized iris images/masks, and face images are supposed to be encrypted such that only the party holding the actual backend/self-custody private key can decrypt them. With a degenerate public key accepted uncontested by `decode_public_key`, the confidentiality of biometric data (iris/face/normalized-iris) is broken for that signup, which matches "biometric data disclosure" impact under the Worldcoin/Orb bounty program.

### Likelihood Explanation
Exploitation only requires an attacker able to influence the `backend_keys`/`authenticated_app_data` values received during their own signup session's `/status` response (the scenario in scope per the rules: "backend responses within that session"). No operator/root access, hardware tampering, or leaked keys are needed — the vulnerable code path (`decode_public_key` → `Credentials` → `encrypt`) is always exercised on every signup that receives `backend_keys`, and there is no logic anywhere in the reachable path that validates key order/strength beyond length, making this reliably reproducible.

### Recommendation
In `decode_public_key`, after parsing the 32-byte array, reject known low-order/degenerate Curve25519 points (the standard list of ~7-8 small-order points, including the all-zero key) before constructing the `PublicKey`. Alternatively/additionally, check the return code of the underlying libsodium `crypto_box_seal`/`crypto_scalarmult` calls (sodiumoxide's `seal()` wrapper currently discards this) and fail loudly (return `Result`/panic) rather than silently proceeding when the crypto primitive rejects a degenerate key.

### Proof of Concept
Unit/fuzz test plan:
1. Unit test: call `decode_public_key` with `BASE64.encode(&[0u8; 32])` and other known Curve25519 low-order point byte patterns (e.g., `0x00...00`, `0x01,0,...,0`, and the other 6 documented low-order values) and assert it currently returns `Ok(PublicKey(...))` for all of them (proving no validation beyond length).
2. Fuzz test: generate arbitrary 32-byte sequences, feed through `decode_public_key`, and confirm `Ok` is always returned regardless of point validity (only length differences produce `Err`).
3. Crypto PoC: use the all-zero (or other low-order) key as `backend_iris_public_key` in `dummy_credentials`, call `Package::build`, capture the produced `tier0`/`tier1` ciphertext for the iris tar, then independently (outside the orb code, using libsodium/X25519 directly) demonstrate that the resulting shared secret used inside `sealedbox::seal` is a fixed, precomputable value for that class of low-order keys — i.e., decrypt the sealed box without ever knowing a "private key," confirming the containment break.

fn decode_public_key(payload: &str) -> Result<PublicKey> {
    let bytes = BASE64.decode(payload.as_bytes())?;
    let bytes = <[u8; 32]>::try_from(bytes)
        .map_err(|x| eyre!("incompatible public key length: {}", x.len()))?;
    Ok(PublicKey(bytes))
}
