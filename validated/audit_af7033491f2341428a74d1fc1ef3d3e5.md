### Title
Webhook HMAC does not bind the `shop-domain` header to the signed payload, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are taken from unauthenticated HTTP headers. The HMAC check in `Utils::HmacValidator` therefore only proves the *bytes of the body* were signed by Shopify's secret — it proves nothing about which shop, topic, or webhook ID that signature is supposed to be associated with. This mirrors the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`: [2](#0-1) 

`validate_signature` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value. For `Webhooks::Request`, both of these are defined as: [3](#0-2) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are **not** part of the signed content at all: [4](#0-3) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values and hands them to the app's handler as the trusted tenant identity for the event: [5](#0-4) 

**Equality that should hold but doesn't:** `shop` used to authorize/attribute the webhook == `shop` bound inside the HMAC-covered signable string. Instead, the gem checks `hmac(raw_body) == hmac_header` and separately trusts `shop_header` with no cryptographic link between the two.

### Impact Explanation
Any shop where the app is installed can obtain genuinely Shopify-signed webhook deliveries (bodies + valid HMACs) for its own store. Because the signature covers only the raw body — and many webhook payloads/topics have body shapes that are shop-agnostic or replayable — an attacker who receives such traffic can resend the identical `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`/`webhook-id`) header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` then dispatches the handler with the attacker-chosen `shop` value in `WebhookMetadata`. If the host application uses that `shop` field (as documented/intended) to look up per-tenant state, apply the event, or trigger tenant-scoped side effects, this results in cross-tenant data or state confusion — the target impact category of "cross-tenant access."

### Likelihood Explanation
Exploitation requires the attacker to control (or have installed the app on) at least one legitimate shop capable of receiving webhooks — a normal, unprivileged use of the app, not a privileged credential. No secret material is needed; the attacker only replays data Shopify already sent them and forges HTTP headers on their own request to the app's public webhook endpoint. This is a low-effort, realistically reachable path through the gem's own header-parsing and HMAC-verification logic, matching the "unprivileged internet user" threat model in scope.

### Recommendation
- Include `shop`, `topic`, and `webhook_id` in the signable content that is HMAC-verified, or otherwise cryptographically bind them to the raw body (e.g., verify signature over a canonical string containing all header fields Shopify guarantees, not just the body).
- At minimum, document and/or enforce that consuming applications must not treat `WebhookMetadata#shop` (or `topic`/`webhook_id`) as authenticated unless additional binding is added, since today only the raw body is HMAC-protected.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers an event so Shopify sends a legitimately signed webhook: raw body `B`, header `shopify-hmac-sha256: HMAC_SECRET(B)`, `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `B` and same `hmac-sha256` header value to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (no validation ties them to the body) at [6](#0-5) .
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes `HMAC_SECRET(B)` and compares — unaffected by the swapped `shop-domain` header, per [7](#0-6) .
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` inside `WebhookMetadata`, despite the payload never having been signed for that shop, per [5](#0-4) .
