### Title
Pool `repay` computes the overpayment refund from the attacker-declared action amount instead of a measured inbound transfer, refunding unbacked custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's repay leg derives the refund (`overpayment`) purely from `action.amount` — a caller-controlled field — without verifying that the declared amount was actually transferred in. On a market with little or no outstanding debt, the entire declared amount is classified as overpayment and paid out of real pool custody to the caller-chosen `payer`. This mirrors the cjose flaw: a value supplied by the attacker is used where the protocol should enforce a fixed/measured quantity.

### Finding Description
`ops::repay::apply` calls `accounting(env, action)`, which reads `action.amount` directly, resolves `burned`/`overpayment` via `cache.resolve_repay(amount, position)`, and then `transfer_out(payer, overpayment)` sends tokens to the caller-named `payer` address (`contracts/pool/src/ops/repay.rs:25-34`, `40-66`). The function never measures the pool's token balance delta for the inbound leg — it assumes the controller prefunded the pool before calling. The `RepayRoundsToZeroShares` guard explicitly passes when `net_repay == 0`, so a repay against a zero-debt position takes the full-close branch in `resolve_repay`, makes `overpayment == amount`, burns nothing, credits nothing to `cash`, and still executes the refund transfer.

The project's own test demonstrates the drain: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `repay(&payer, &ract(0, custody_before))` with a freshly generated payer, no inbound transfer, and zero debt, then asserts the refund "drained custody" (`contracts/pool/tests/flows.rs:3590-3611`). Every other inbound path in the codebase uses `transfer_amount_measured`/`balance_delta_since` precisely because declared transfer amounts cannot be trusted (`contracts/controller/src/payments.rs`, `common/src/token.rs`); the pool-side repay/refund and `recapitalize` excess paths are the exceptions noted in the test comment at `flows.rs:3578-3588`. There is no `require_reserves` check on the refund, so the payout comes out of other suppliers' real token balance.

### Impact Explanation
If the pool's `repay` entrypoint is reachable with the caller supplying `payer` (the tests invoke it with an arbitrary generated `Address`, and `payer` controls both the auth and the refund recipient), an unprivileged attacker declares `amount = pool_token_balance` on a market where the referenced position has zero debt. `resolve_repay` classifies the whole amount as overpayment and `transfer_out` sends the full custody balance to the attacker — direct theft of all suppliers' tokens in that market. Even if reachability is intended to be controller-only, the refund is still computed from a declared rather than measured inbound amount, so any inbound-funding gap (e.g., a controller path that does not prefund, or a direct call with mockable auth) silently converts book-keeping into real custody loss.

### Likelihood Explanation
The vulnerable arithmetic is unconditional: zero/under-collateralized debt plus any positive declared `amount` yields `overpayment == amount` and a real `transfer_out`, with the `net_repay == 0` disjunct deliberately bypassing the zero-shares guard. Likelihood therefore hinges entirely on pool `repay`'s authorization: the pool test suite reaches it with a self-generated `payer` and no controller in the call path, and no measured-balance check exists to catch an unfunded call. I was unable to fully confirm the auth gate on the pool's `repay` entrypoint within the available iterations; if it strictly requires the controller address as caller, severity reduces to a latent trust-boundary flaw rather than an immediately exploitable theft.

### Recommendation
Verify the inbound leg instead of trusting `action.amount`: snapshot the pool's token balance (or accept a measured `amount_in` proven by the caller), and cap the refund at the measured receipt — `overpayment = min(declared_overpayment, measured_inbound - net_repay)`. Alternatively, gate `repay` to the configured controller and assert `transfer_out(payer, overpayment)` cannot exceed the balance increase attributable to this call. Apply the same fix to `ops::recapitalize::apply`'s excess refund, which shares the declared-amount pattern.

### Proof of Concept
1. Identify a listed market whose repay position has zero (or dust) outstanding debt.
2. Call pool `repay` with `payer = attacker` and `action.amount = pool_custody_balance` (declared only; transfer nothing in).
3. `resolve_repay` sees `current_debt_ceil == 0`, takes the full-close branch, sets `overpayment = amount`, `net_repay = 0`; the `net_repay == 0` disjunct bypasses `RepayRoundsToZeroShares`.
4. `cache.transfer_out(attacker, overpayment)` pays the full declared amount out of the pool's real token balance; the cash book is untouched and no reserves check runs.
5. Result: attacker receives the market's entire custody balance. This is exactly what `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590-3611`) demonstrates in-test.
