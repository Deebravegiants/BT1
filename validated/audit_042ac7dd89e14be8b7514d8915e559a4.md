### Title
Zero-length `erc20TokenAddresses` array (via `dimensions.tokenNumber = 0`) skips all balance-conservation checks for Emporium-routed value movement - (File: `contracts/Hinkal.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When an attacker submits `Hinkal.transact` with `dimensions.tokenNumber = 0`, `dimensionsCheck` forces `circomData.erc20TokenAddresses.length == 0`. Both `Hinkal.transact`'s per-token balance-conservation loop and `EmporiumUpgradeable.runAction`'s per-token balance-change loop are bounded by `circomData.erc20TokenAddresses.length`, so they execute zero iterations, meaning the equality `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` is never checked for the transaction.

### Finding Description
The equality that is supposed to hold once per token:
`balanceDif == (circomData.onChainCreation[i] ? 0 : circomData.amountChanges[i]) + int256(utxoAmount)`
is enforced inside `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` in `Hinkal.transact` [1](#0-0) .

`dimensionsCheck` in `HinkalHelper.sol` requires `circomData.erc20TokenAddresses.length == dimensions.tokenNumber` [2](#0-1) , so an attacker setting `dimensions.tokenNumber = 0` forces this array (and `amountChanges`, `onChainCreation`, `slippageValues`) to length 0, and the entire loop in `Hinkal.transact` never executes a single iteration — no `require` in that block ever runs.

Crucially, this bypass propagates into the Emporium external action. `EmporiumUpgradeable.runAction` performs its own per-token balance-change enforcement in a loop also bounded by `circomData.erc20TokenAddresses.length` [3](#0-2) . With an empty array, this loop is also skipped, and no `UTXO`/balance capture occurs for whatever the `EmporiumStack` ops actually do. Meanwhile, `stack.ops` execution itself is unconditional and unbounded by `erc20TokenAddresses`: `for (uint256 i = 0; i < stack.ops.length; i++) { ... op.endpoint.call{value: op.value}(op.callData); ... }` [4](#0-3) . For the "Stateless Interaction" branch (`invokeWallet == false`), no wallet or signature is required at all if `stack.signerAddress == address(0)`: `verifyWallet` simply returns after marking the message used, performing no EIP-712 signature check whatsoever in that case [5](#0-4) .

Root cause: the protocol conflates "no tokens declared for Hinkal's proof" with "no value moves through Emporium," and lets `tokenNumber = 0` disable both the outer (`Hinkal.sol`) and inner (`Emporium`) balance-conservation loops simultaneously, while leaving the ops-execution loop itself completely unconstrained by that same array length. `formInputForCircom` even special-cases this: when `externalActionId == HINKAL_EMPORIUM_ACTION_ID && circomData.erc20TokenAddresses.length == 0`, it swaps to a reduced `formInputEmporiumMin` circuit input [6](#0-5) , confirming this "Min" path is an intentionally reduced-constraint code path, not an edge case guarded elsewhere.

Attacker call: `transact(a, b, c, dimensions{tokenNumber:0,...}, circomData)` where `circomData.externalActionData.externalActionId` is Emporium's id, `circomData.erc20TokenAddresses = []`, `circomData.amountChanges = []`, `circomData.onChainCreation = []`, and `circomData.externalActionData.externalActionMetadata` encodes an `EmporiumStack` with `signerAddress = address(0)` and one or more ops with `invokeWallet = false`, arbitrary `endpoint`/`callData`/`value`. Since `deltaAmountChanges` (built from the same empty array in `_externalTransact`) is also empty, no funds are pre-transferred by Hinkal into Emporium, but the ops themselves execute unconditionally using Emporium's own on-hand ETH/token balance (`msg.sender == Emporium` for these calls) or interacting with any external contract that trusts calls originating from Emporium's address, with zero after-the-fact reconciliation on either side.

### Impact Explanation
Critical: this removes the core value-conservation invariant of Hinkal for the entire class of Emporium/"Min-circuit" transactions. Any ETH/ERC20 balance the Emporium contract holds (fee dust, leftover balances, or tokens/contracts that grant Emporium special trust) can be moved by an unprivileged attacker with zero balance/signature verification, and neither `Hinkal.sol`'s nor `EmporiumUpgradeable.sol`'s conservation loops will ever fire to detect or reject the discrepancy. This is repeatable on every call as long as `tokenNumber = 0` is accepted and Emporium is the target action.

### Likelihood Explanation
Preconditions are entirely attacker-controlled: `dimensionsCheck`, `checkOnchainCreation`, and proof verification for the `formInputEmporiumMin` path only need consistent zero-length arrays and a valid proof for the reduced circuit — none of which require special privilege, another user's key, or a particular tree state. The attacker needs only to author their own `EmporiumStack` and generate their own proof for the "Min" circuit, both fully within an unprivileged EOA's capability. The magnitude of value actually at risk depends on how much ETH/ERC20 balance genuinely accumulates in the Emporium contract in practice; I could not conclusively verify a specific always-present, attacker-independent source of such balance from the reachable code (e.g., I did not find evidence of ERC20 `approve`/`transferFrom` patterns granting Emporium standing allowances), so the realized value stolen per call may vary, but the structural absence of any balance check is unconditional and verified directly in code.

### Recommendation
Do not let `dimensions.tokenNumber == 0` bypass balance/UTXO accounting when the external action is Emporium (or any action capable of arbitrary external calls). Either (a) forbid `formInputEmporiumMin`/zero-length `erc20TokenAddresses` whenever `stack.ops` contains non-wallet-invoked (`invokeWallet == false`) operations or when `signerAddress == address(0)`, or (b) always run the balance-conservation loop over the full set of tokens actually touched by `stack.ops` (derived independently of the possibly-empty `circomData.erc20TokenAddresses`), so that any net balance change in Emporium is captured and reconciled regardless of `tokenNumber`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`; fund the Emporium contract with a nonzero ETH balance (e.g., simulate residual dust by sending ETH directly, or via a legitimate prior transaction that leaves dust) so `address(emporium).balance > 0`.
2. As an unprivileged attacker EOA, construct `circomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData.externalActionId = EMPORIUM_ID`, and `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: attackerControlledReceiver, invokeWallet: false, value: <emporium's full ETH balance>, callData: ""}]}`.
3. Generate a valid proof for the `formInputEmporiumMin` circuit with `dimensions.tokenNumber = 0`.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
5. Assert: (a) the `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` loop in `Hinkal.transact` executes 0 times (instrument via a modified harness or trace), (b) the Emporium contract's ETH balance is fully drained to the attacker's receiver, (c) no `require` from the balance-conservation block reverted the transaction, confirming both sides of the equality were never evaluated.
