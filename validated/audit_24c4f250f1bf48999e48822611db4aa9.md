Audit Report

## Title
Not a vulnerability: unauthenticated `PATCH /v2/resume/:runID` is a documented, intentional design keyed by an unguessable per-task-run UUID - (File: core/web/router.go)

## Summary
The claim asserts that registering `PATCH /v2/resume/:runID` on the unauthenticated router group (`unauthedv2`) in `v2Routes` is a missing-authorization bug analogous to a state-mutating function lacking an access-control modifier. Inspection of `PipelineRunsController.Resume` shows the "authentication" for this endpoint is intentionally the possession of an unguessable, randomly generated UUID (the pipeline task run ID), not session/token auth — this is a known async-callback pattern (bridge/external-adapter continuation), not a broken authorization control, and the code explicitly logs the action via `audit.UnauthedRunResumed`, indicating the unauthenticated nature is deliberate and acknowledged in the codebase itself.

## Finding Description
`v2Routes` registers `unauthedv2.PATCH("/resume/:runID", prc.Resume)` outside of the `authv2`/`userOrEI` authenticated groups. [1](#0-0)  `PipelineRunsController.Resume` parses `runID` strictly as a `uuid.Parse` value (`taskID`), decodes a `pipeline.ResumeRequest` body, and calls `prc.App.ResumeJobV2(ctx, taskID, result)`, then explicitly records an audit event named `audit.UnauthedRunResumed` with the `runID` — the naming itself signals this route's unauthenticated status is a known, intentional design decision rather than an oversight. [2](#0-1)  This mirrors the well-established Chainlink pattern where async/bridge pipeline tasks are suspended pending an external callback, and the callback URL embeds a cryptographically random, per-task-run UUID that functions as the bearer credential for resuming that specific task — this is standard practice for webhook-style callbacks (e.g., Stripe/PagerDuty-style opaque callback tokens), not an authorization bypass, since the "identity" being authenticated is knowledge of the unguessable UUID itself.

The report explicitly acknowledges it could not verify whether `runID` values are guessable/enumerable or inspect `Resume`'s implementation, calling this "a limitation of the current investigation, not a claim that no PoC exists" and stating the analysis "requires reading `PipelineRunsController.Resume`." Having now read that file, `Resume` requires a valid `uuid.UUID` (`uuid.Parse(c.Param("runID"))`), which is a 128-bit random value with no discoverable enumeration path exposed through this or any other in-scope endpoint reviewed. The claim provides no evidence that these UUIDs are generated non-randomly, leaked elsewhere, or otherwise obtainable by an unprivileged, unauthenticated actor — it only speculates that this "depends entirely" on unverified guessability, which fails the requirement for a concrete, non-hypothetical exploit path.

## Impact Explanation
No concrete in-scope impact is demonstrated. The claim's impact rests entirely on the unproven and unverified premise that `runID` is "guessable/enumerable," which the reporter explicitly could not confirm. Without a demonstrated way for an unauthenticated actor to obtain or predict a valid pending task-run UUID, there is no established unauthorized job-run manipulation, fund movement, or cross-user data corruption attributable to this code.

## Likelihood Explanation
Likelihood is speculative. The report itself states it is uncertain whether the precondition (predictable/enumerable `runID`) holds, and no enumeration or disclosure mechanism for these UUIDs was identified in the reviewed code or router. Since the security model here relies on the UUID itself acting as the credential (standard for async callback endpoints), and there is no evidence of a leak or predictability, the likelihood of exploitation by an unprivileged actor is not established.

## Recommendation
No fix required based on the evidence presented. If it can be independently demonstrated that pipeline task-run UUIDs are ever exposed to unauthorized parties (e.g., logged, returned in another unauthenticated response, or generated non-randomly), that would constitute a separate, narrower finding requiring its own proof; absent that, the current design (unguessable UUID as the resume credential) is the intended and standard pattern for this class of endpoint.

## Proof of Concept
Not provided by the reporter and not reproducible from the evidence given — the report only proposes a hypothetical `curl -X PATCH .../v2/resume/<runID>` without demonstrating how an unauthenticated attacker would first obtain or guess a valid, pending `runID` UUID, which is the essential precondition for any exploit.

func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
