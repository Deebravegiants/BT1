### Title
Vault `deposit` mints shares without checking for zero, permanently freezing a depositor's principal - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and all sibling vaults)

### Summary
Every tokenized vault (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`) mirrors the classic wstETH bug: the conversion helper `convert-to-shares-preview` can legitimately return `u0` for a non-zero deposit, but unlike `redeem` (which explicitly reverts with `ERR-OUTPUT-ZERO` when the computed output is zero), `deposit` has no equivalent guard on the minted-shares side.

### Finding Description
`convert-to-shares-preview` rounds down and returns `u0` whenever `mul-div-down(amount, ts, ta)` underflows to zero (i.e. when the share price `ta/ts` has grown above 1 and the deposit `amount` is small relative to it): [1](#0-0) 

`deposit` computes `inkind` from this helper, but only checks `amount > 0` and the caller-supplied `min-out` slippage bound — never that `inkind` (the actual shares to mint) is non-zero: [2](#0-1) 

Compare this with `redeem`, which explicitly asserts `(> inkind u0) ERR-OUTPUT-ZERO` before proceeding: [3](#0-2) 

If a user (or an integrator/contract calling with `min-out = 0`, the natural default for "accept any amount") deposits a small `amount` at a moment when `total-assets-preview / total-supply-preview > 1` (which happens naturally as interest accrues and inflates `total-assets` relative to `total-supply`, since `total-assets-preview` adds accrued interest on top of `assets`), `ft-mint? zft inkind recipient` mints `0` shares while `receive-underlying` still pulls the full `amount` of underlying from the depositor and `assets` is incremented by that `amount`: [4](#0-3) 

This breaks the identity that must hold for every deposit:
`shares_minted > 0  whenever  assets_deposited > 0`

The depositor's underlying tokens are absorbed into the vault's `assets` variable — silently increasing the redeemable value backing every *other* shareholder's existing shares — while the depositor themselves receives zero shares and has no way to reclaim the value they deposited. This is identical in mechanism to the WstETH report: a conversion function returning zero for a non-zero input, with no guard preventing the caller from proceeding on a worthless (zero) output.

### Impact Explanation
The depositing user's principal is absorbed by the vault with no shares issued in return, permanently freezing/losing their deposited funds while diluting that value across existing shareholders. This falls under permanent freezing of user funds.

### Likelihood Explanation
This does not require any privileged action, oracle manipulation, or DAO compromise — only that the share price (`total-assets-preview / total-supply-preview`) exceed 1 (a natural outcome of interest accrual over the vault's lifetime, since `total-assets-preview` includes uncollected interest on top of `assets`) and that a small-enough deposit amount is made with a non-restrictive `min-out`. Any wallet/integration that defaults `min-out` to `0` (a common pattern to "accept market rate") is exposed by default.

### Recommendation
Add an explicit zero-output guard to `deposit`, mirroring the one already present in `redeem`:
```clojure
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` check in every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Vault is live with non-zero `total-supply` and `total-assets-preview` such that `total-assets-preview / total-supply-preview` is comfortably above 1 (achieved organically as accrued interest builds up over time, since `total-assets-preview` = `assets + interest`).
2. A depositor calls `deposit(amount, 0, recipient)` with a small `amount` such that `mul-div-down(amount, total-supply-preview, total-assets-preview)` computes to `0`.
3. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially since `min-out = 0` and `inkind = 0`.
4. `receive-underlying` transfers the full `amount` from the depositor into the vault; `ft-mint? zft 0 recipient` mints zero shares; `assets` is incremented by `amount`.
5. The depositor now holds `0` vault shares and has no mechanism to redeem the `amount` they deposited — it is permanently lost to them and diluted across other shareholders' redeemable value. [2](#0-1)

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))

(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (account contract-caller)
      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))

    (print {
      action: "deposit",
      caller: contract-caller,
      data: {
        depositor: account,
        recipient: recipient,
        amount: amount,
        shares-minted: inkind,
        assets: (+ current-assets amount)
      }
    })

    (ok inkind)))
