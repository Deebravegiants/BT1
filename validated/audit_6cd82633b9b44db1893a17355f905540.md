### Title
Unbounded `Bytes.substr` read of MMR-root digest data allows out-of-bounds memory read when decoding a BEEFY-finalized parachain header - (File: `evm/src/consensus/Types.sol`)

### Summary
`HeaderImpl.stateCommitment()` extracts the MMR root and child-trie root from a SCALE digest's `data` field by calling `Bytes.substr(self.digests[j].consensus.data, 0, 32)` and `Bytes.substr(self.digests[j].consensus.data, 32)` without first checking that `data.length >= 64`. This is the same bug class as CVE-2018-11731: a length-prefixed, attacker/relayer-influenced field is trusted to be long enough for a fixed-size field extraction, and a short field triggers an out-of-bounds read instead of a controlled failure.

### Finding Description
`Codec.DecodeHeader` (`evm/src/consensus/Codec.sol:70-102`) SCALE-decodes an arbitrary parachain header supplied inside a `ParachainProof` by the relayer, including a `Digest[]` array. Each digest item is decoded via `decodeDigestItem` (`Codec.sol:104-110`), which reads a SCALE-`Compact<u32>` length and then `Bytes.read(slice, length)` — so `digest.data.length` is fully attacker-controlled (any value ≤ remaining header bytes, including 0).

`HeaderImpl.stateCommitment` (`evm/src/consensus/Types.sol:211-231`) is then called on this decoded header from `EcdsaBeefy.verifyParachainHeaderProof` (`evm/src/consensus/EcdsaBeefy.sol:218`) and analogously from the SP1 BEEFY path. When a digest is tagged `ISMP_CONSENSUS_ID`, the code unconditionally does:
```solidity
mmrRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 0, 32));
childTrieRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 32));
``` [1](#0-0) 
There is no `require(data.length >= 64)` guard before these reads, unlike `Codec.read`'s own bounds check (`require(self.offset + len <= self.data.length)`, `evm/src/consensus/Codec.sol:114`) or `readByte`'s check (`Codec.sol:126`). If `data.length` is anything less than 64 bytes but the digest is otherwise well-formed and tagged with the ISMP consensus ID, `Bytes.substr`/`Bytes.toBytes32` read past the end of the allocated `bytes` memory buffer — a heap-based buffer over-read, structurally identical to the disputed libfsntfs bug where an attribute's declared length was trusted without validating it against the buffer bounds.

The critical point for reachability: **the header's digest content is not itself independently re-validated against a commitment before this parsing runs.** The header is only checked for MMR-leaf inclusion via `keccak256(header bytes)` matching a leaf hash inside `verifyMmrLeaf`/`verifyParachainHeaderProof`'s multiproof — i.e., *any* byte sequence that hashes correctly and satisfies the merkle proof is accepted as "the header," and its digest list, including the crafted short ISMP digest, is exactly what a malicious/compromised parachain collator (not the relaychain authority set) can freely construct, since the parachain header itself is produced by parachain collators, not signed byte-for-byte by BEEFY validators individually — the BEEFY signature only attests to the MMR root over parachain head hashes, not to header well-formedness.

### Impact Explanation
An out-of-bounds `Bytes.substr` read in Solidity does not "leak" attacker-desired heap data the way libfsntfs's over-read does (Solidity's revert semantics and memory model differ), but the read can pull in adjacent unrelated memory (subsequent struct fields, array data, or later `bytes` allocations) as the `mmrRoot`/`childTrieRoot`, producing a corrupted, attacker-influenced `StateCommitment`. Because `stateCommitment()` output becomes the trusted `overlayRoot`/`stateRoot` for the destination parachain's state machine height (`IntermediateState.commitment` consumed by `EvmHost`/`HandlerV2` for all subsequent request/response state proofs), a garbage or attacker-shaped commitment can corrupt state-proof verification for that height — a route capable of delivering forged/incorrect proof outcomes, i.e., unsound state commitment ingestion.

### Likelihood Explanation
Reachable from a single relayed consensus proof: any relayer can submit a `ParachainProof` containing a header whose ISMP digest has `data.length < 64`, so long as the header hash still satisfies the MMR-leaf multiproof (which only constrains the header's hash, not its digest content structure beyond what's committed on the relaychain side — the header bytes for a given parachain block are produced by that parachain's block author, not attested field-by-field by BEEFY signers). No governance or validator compromise is required.

### Recommendation
Add an explicit length check before slicing in `HeaderImpl.stateCommitment`, e.g. `require(self.digests[j].consensus.data.length >= 64)`, mirroring the bounds checks already present in `Codec.read`/`Codec.readByte`, and revert (rather than silently truncate/over-read) on malformed ISMP consensus digests.

### Proof of Concept
1. Construct a parachain header whose SCALE digests include one `DigestItem` with `id == ISMP_CONSENSUS_ID` (`"ISMP"`) and `data` of length < 64 bytes (e.g., 4 bytes).
2. Ensure this header's SCALE-encoded bytes hash correctly into a valid MMR leaf under a legitimately BEEFY-signed MMR root (achievable by a malicious/compromised parachain collator producing this header as its actual block, since BEEFY only signs over the MMR root of parachain head hashes, not header digest content).
3. Submit via `EcdsaBeefy.verify` (or the SP1 path) with a valid `RelayChainProof`/`ParachainProof`.
4. `Codec.DecodeHeader` decodes the malformed digest without complaint (length is self-consistent with the header bytes).
5. `HeaderImpl.stateCommitment()` executes `Bytes.substr(data, 0, 32)`/`Bytes.substr(data, 32)` on the 4-byte `data`, reading past its allocated bounds and producing an incorrect `mmrRoot`/`childTrieRoot` used as the trusted state commitment for that height.
