This is exactly the analogous bug class: a security-critical bound/validation check is applied only inside a conditional branch, with no equivalent guard in the alternative path, letting untrusted attacker-controlled data flow through unvalidated. In `StrategyUtils` the slippage bound is only enforced `if useDynamicSlippage`; in orb-core, the `user_data_hash` verification (the check that binds the QR-code data to the backend-issued `authenticated_app_data`, analogous to the "bound" check in the report) is only compiled/enforced `#[cfg(not(feature = "skip-user-qr-validation"))]`, i.e. it is entirely skipped in the alternate build configuration rather than being a runtime-safe default.

### Title
Missing default-deny fallback for user QR-code hash verification allows unauthenticated signup binding when `skip-user-qr-validation` path is compiled - (File: src/backend/user_status.rs)

### Summary
`backend::user_status::request` only checks `user_data.verify(user_data_hash)` inside a `#[cfg(not(feature = "skip-user-qr-validation"))]` block [1](#0-0) . Just like the Curve Vault's `_executeTradeExactIn`, which only bounds `oracleSlippagePercentOrLimit` when `useDynamicSlippage` is true and leaves the value completely unchecked otherwise, this function only binds/authenticates `authenticated_app_data` to the scanned QR code when the "normal" build path is active. Under the alternate compile-time path (`do_request` under `#[cfg(feature = "skip-user-qr-validation")]`), the code fabricates a fully "valid" `Response` with attacker-independent keys and `identity_commitment: "test"` without ever cross-checking it against `qr_code.user_data_hash` [2](#0-1) .

### Finding Description
The `user_data_hash` field on `qr_scan::user::Data` is derived from parsing the physical user QR code via `orb_qr_link::decode_qr` [3](#0-2) . This hash is the cryptographic binding between what the Orb physically scanned and the backend-asserted `authenticated_app_data` (identity commitment, self-custody public key, data policy, etc.) returned by `do_request`. The verification `user_data.verify(user_data_hash)` is the sole mechanism ensuring the backend's asserted identity actually corresponds to the QR-code the Orb scanned [1](#0-0) .

Just as `StrategyUtils._executeTradeExactIn` guards the slippage bound only `if (useDynamicSlippage)` and takes `params.oracleSlippagePercentOrLimit` unchecked otherwise, this Orb code guards the hash-binding check only under one compile configuration (`not(feature = "skip-user-qr-validation")`) and takes the unverified `authenticated_app_data` unconditionally under the other. There is no runtime/internal guardrail (mirroring `jeffywu`'s point about lacking guardrails against the unsafe branch being reachable) preventing this feature flag from being enabled in a production-adjacent build — the check exists in only one of two logically parallel code paths rather than as a universally enforced invariant.

### Impact Explanation
If a build is produced with `skip-user-qr-validation` enabled (even unintentionally, e.g. a mis-tagged release, CI artifact, or a debug/test build shipped to a device), the QR-to-identity cryptographic binding is entirely bypassed: the software will accept any scanned user QR code as validated and enroll using synthetic/test key material and `identity_commitment: "test"` rather than data actually verified against the physical QR code. This directly maps to the "unauthorized or misattributed signup" impact category — a signup could be committed under keys/identity not genuinely tied to the QR the user presented, since the cross-check that binds scanned QR data to backend identity is structurally absent in that path.

### Likelihood Explanation
Likelihood depends entirely on whether `skip-user-qr-validation` can be enabled in a shipped/production Orb binary. As with the audit discussion where `jeffywu` flagged that "we don't have guardrails against this method being called ... by a non-authenticated account from an internal code perspective," this repo has no runtime assertion (e.g., a hard build-time or startup check refusing to run in this mode outside test contexts) preventing this feature-gated bypass from being present in a released binary — the safety of the whole binding relies solely on build configuration discipline, not on defense-in-depth in the code path itself.

### Recommendation
Do not rely on a `cfg`-gated skip path to omit the identity-binding verification. Instead:
1. Restrict the `skip-user-qr-validation` feature to test/dev builds only via a compile-time assertion (e.g., `#[cfg(all(feature = "skip-user-qr-validation", not(test)))] compile_error!(...)`), or explicitly gate it behind `#[cfg(test)]` only, so it cannot exist in any non-test artifact.
2. Alternatively, always perform the `user_data.verify(user_data_hash)` check unconditionally, and only bypass generation of `backend_keys`/`authenticated_app_data` fetching (not verification) under the test-only path, mirroring the report's recommendation to add an explicit bound/guard for the "unsafe" branch instead of omitting the check outright.

### Proof of Concept
1. Build orb-core with `--features skip-user-qr-validation`.
2. Trigger a signup flow; `backend::user_status::do_request` returns a `Response` with `valid: true`, synthetic `backend_keys`, and `authenticated_app_data { identity_commitment: "test", ... }` regardless of the actual scanned QR code content [4](#0-3) .
3. Because the `#[cfg(not(feature = "skip-user-qr-validation"))]` block containing the `user_data.verify(user_data_hash)` check is compiled out, `request()` proceeds directly to using `authenticated_app_data` for the signup/enrollment flow without any check that it corresponds to the physically scanned QR code [1](#0-0) .
