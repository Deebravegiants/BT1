### Title
Delegates registered under `account_id` survive NFT ownership transfer, leaving a dangling authorization on the released account - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary

The kernel bug class is a release path that fails to clear a registration marker (`po->num`), letting a stale entry in a tracking structure (`fanout arr[]`) re-attach privileges to a released object. The analogous structure in XOXNO Lending is the controller's delegate table: delegates are stored keyed by `account_id`, not by owner, and nothing in the position-NFT `transfer`/`approve` path clears or restamps them. An account's stored `owner`/`AccountMeta` and its delegate registrations are independent of the NFT's current `owner_of`, so an authorization registered before the ownership change remains linked to the account afterward — a dangling registration on a re-owned object, exactly the "socket re-registered into `f->arr[]` after `packet_release`" shape.

### Finding Description

Account identity for positions is `account_id` (`ControllerKey::SupplyPositions/BorrowPositions/AccountMeta`), while ownership is the position NFT. `resolve_seize_receiver` shows the authorization model: `require_owner_or_delegate(env, requested, liquidator, &receiver.owner)` admits either the owner **or a stored delegate** of the account [1](#0-0) . The harness test `a_stranger_cannot_grant_or_revoke_a_delegate_on_another_owners_account` confirms delegates are added/removed via `add_delegate(caller, account_id, delegate)` keyed by `account_id` [2](#0-1) . INV-STOR-01 documents that **account removal** deletes delegates — but there is no corresponding clearing on NFT transfer [3](#0-2) .

The NFT itself is freely transferable even when the account is underwater and remains a valid liquidation target afterwards, i.e., `account_id` state (positions, meta, and therefore delegates) is untouched by transfer [4](#0-3) .

Attack shape: an attacker mints a position account, calls `add_delegate(attacker, account_id, attacker_alt)` registering an address they control, then transfers/sells the position NFT to a victim. The victim's `account_id` still carries the attacker's delegate registration — the fanout "arr[]" slot that `fanout_release` never cleaned. The attacker can then act on the victim's account through any entrypoint gated by `require_owner_or_delegate` (e.g., withdraw the collateral the victim paid for, or borrow against it to the delegate's benefit), until the victim discovers and calls `remove_delegate`.

### Impact Explanation

Theft of user funds: an unprivileged seller of a position NFT retains a live authorization on the sold account and can withdraw its collateral or draw borrows against it after the sale, stealing value the buyer owns. This requires only `add_delegate` + `transfer` + a delegate-authorized verb — all unprivileged, in-scope entrypoints.

### Likelihood Explanation

Requires a victim to acquire a position NFT without auditing the delegate set (there is no documented requirement that buyers enumerate delegates; `account_exists`/attribute views do not expose them in the composing docs). Delegate-mediated calls additionally may require the delegate path to be usable — for `run_script` the delegate must be an admin-enabled position manager, which would narrow this to manager-contract-mediated theft; for direct owner-or-delegate entrypoints (as used in `resolve_seize_receiver`) a plain attacker address suffices. **Uncertainty:** I could not fully verify which user-facing verbs (withdraw/borrow/liquidate) accept a non-manager delegate as caller, nor confirm that no code path restamps delegates on transfer — if the index omits a transfer hook that clears delegates, this collapses to a no-finding. The delegate-storage and ownership-model facts above are verified; the transfer-time clearing question is not.

### Recommendation

On NFT `transfer` (or on controller detection of an `owner_of` change), clear the delegate set for `account_id`, mirroring how INV-STOR-01 deletes delegates on account removal. Alternatively, bind each delegate grant to the current NFT owner and revalidate owner identity at grant-use time, so a grant registered under a previous owner is inert after transfer.

### Proof of Concept

1. Attacker calls `supply` to create `account_id` A with collateral (or leaves it empty — the delegate grant survives regardless).
2. `add_delegate(attacker, A, attacker_alt)`.
3. Attacker calls position-NFT `transfer(attacker, victim, A)`; victim now owns the account but the delegate entry `(A, attacker_alt)` is still stored.
4. Attacker's `attacker_alt` invokes `withdraw(caller=attacker_alt, account_id=A, ...)` (or `borrow`) on the victim's account, passing `require_owner_or_delegate` via the stale delegate registration and receiving the collateral/debt proceeds.
5. `remove_delegate` by the victim is the only cleanup — the "release" never zeroed the marker.

```rust
fn underwater_position_transfers_freely_and_stays_liquidatable() {
    // Same unhealthy-position setup as liquidation.rs; the account is
    // transferred but never adopted into a harness user's bookkeeping, then
    // a third party liquidates it keyed directly by account_id -- owner
    // identity is irrelevant to solvency machinery.
    let mut t = LendingTest::new().standard_two_asset().build();

    t.supply(ALICE, "USDC", 10_000.0);
    t.borrow(ALICE, "ETH", 3.0);
    let account_id = t.account_id(ALICE);
    t.set_price("USDC", usd_cents(50));
    t.assert_liquidatable(ALICE);

    t.nft_transfer(ALICE, BOB, account_id);
    assert_eq!(t.nft_owner_of(account_id), t.get_or_create_user(BOB));

    let debt_before = t.borrow_balance_for(BOB, account_id, "ETH");

    let liquidator_addr = t.get_or_create_user(LIQUIDATOR);
    let eth_decimals = t.resolve_market("ETH").decimals;
    let eth_asset = t.resolve_asset("ETH");
    let raw_amount = f64_to_i128(0.5, eth_decimals);
    t.resolve_market("ETH")
        .token_admin
        .mint(&liquidator_addr, &raw_amount);

    let ctrl = t.ctrl_client();
    let payments = asset_payment_vec(&t.env, eth_asset, raw_amount);
    ctrl.liquidate(
        &liquidator_addr,
        &account_id,
        &payments,
        &SeizeMode::Transfer,
    );

    assert!(
        t.borrow_balance_for(BOB, account_id, "ETH") < debt_before,
        "third-party liquidation keyed by account_id must reduce debt regardless of NFT owner"
    );
```
