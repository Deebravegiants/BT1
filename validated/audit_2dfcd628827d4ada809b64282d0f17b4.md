### Title
Webhook HMAC validation does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`/`webhook_id`) values that are handed to the application's webhook handler are read from unauthenticated HTTP headers that are never included in the signed payload. Because the signature covers only the body, any request carrying a body/HMAC pair that is valid for shop A can be replayed with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to shop B, and it will still pass validation while being delivered to the handler as if it originated from shop B.

### Finding Description
`Webhooks::Request#hmac` decodes the signature from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC and then immediately trusts `request.shop` (and other header-derived fields) to build the data passed to the app's handler: [3](#0-2) 

The equality the gem is implicitly asserting is: `hmac_is_valid(raw_body) == request_is_authentically_from(shop_header)`. In fact the HMAC only proves `hmac_is_valid(raw_body)`; it says nothing about which shop the body/headers claim to be from. A party who has access to any one legitimately-signed webhook body for the app (e.g., a merchant who installed the app receives real webhooks addressed to their own store, signed with the app's shared secret) can take that untouched body + HMAC pair and resend it to the app's public webhook endpoint with a different `shop-domain` header value pointing at a victim shop. `HmacValidator.validate` will return true (body/signature match), and `Registry.process` will construct `WebhookMetadata` with the attacker-chosen `shop`, causing the host application's handler to act on/attribute data to the wrong tenant.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: a merchant with only their own legitimate webhook traffic (and thus their own valid HMAC/body pairs) can impersonate a different shop's webhook to the host application, achieving cross-tenant confusion/access in any application that trusts `WebhookMetadata#shop` returned by this library (e.g., to look up per-shop session/state, apply changes, or trigger per-shop side effects), matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any account holder able to install the app on a shop they control receives genuine webhook deliveries signed with the app's secret for their own shop; capturing and replaying such a request with an altered shop header requires no secrets and no special privilege beyond having installed the app — an "authenticated but low-privileged" actor in the same sense as the analog report (any user with `Storage` access could trigger the cross-tenant file move). The only prerequisite is that the host application relies on this gem's `Registry.process`/`Webhooks::Request#shop` for tenant attribution without independently re-validating the shop against the source of the request (e.g., IP allow-listing), which is the intended and documented usage pattern of this API.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed payload verification, e.g., by computing/verifying the HMAC over a canonical string that includes the `shop-domain` header value in addition to the raw body, or by requiring the caller to supply the expected shop and rejecting requests where the header value does not match the shop context that requested the given webhook subscription. At minimum, document prominently that `request.shop` is not authenticated by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., matching the topic/webhook id against a subscription record known to belong to that shop).

### Proof of Concept
1. App merchant M installs the app on `m-shop.myshopify.com`; Shopify delivers a legitimate webhook to the app's endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's secret), and `X-Shopify-Shop-Domain: m-shop.myshopify.com`.
2. M captures this raw request (body `B`, header `H` unchanged).
3. M resends the identical body `B` and hmac `H` to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` returns `true` because only `B` and `H` are checked: [4](#0-3) 
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and performs its normal per-shop side effects against `victim-shop`, even though the request never originated from Shopify on behalf of that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
