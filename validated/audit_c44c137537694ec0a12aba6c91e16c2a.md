### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC, allowing cross-tenant webhook attribution - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then dispatches the handler using the `shop` (and `topic`/`webhook_id`) values taken directly from HTTP headers, which are never included in the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` verifies this HMAC, then immediately builds `WebhookMetadata` for the handler using `request.shop`, `request.topic`, and `request.webhook_id`, which are all read from unauthenticated headers: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop value cryptographically bound by HMAC == shop value the handler acts on`. Because the HMAC only covers the JSON body, that equality does not hold — an attacker who has captured (or otherwise obtains) one genuine, HMAC-valid webhook delivery for any shop can replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with an arbitrary value. `HmacValidator.validate` still succeeds because it only recomputes HMAC over `@raw_body`, and `Registry.process` passes the attacker-controlled `shop` string straight into `WebhookMetadata` for the host application's handler.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to key persistence/lookup (a documented and expected usage pattern for this gem, per `docs/usage/webhooks.md`), will process/attribute an authentic-looking (HMAC-valid) webhook event under the wrong tenant. This breaks the shop-authenticated-vs-shop-acted-upon binding described in scope and results in cross-tenant data confusion: order/customer/data payloads intended for shop A get written into or triggered against shop B's records, purely because the identity header is unauthenticated while the gem still reports the webhook as "verified."

### Likelihood Explanation
Exploitation requires only capturing one legitimately delivered, HMAC-signed webhook body (e.g., from a shop the attacker controls, or a public/replayable webhook payload) and replaying it to the same app endpoint with a modified `shop-domain` header — no access to `api_secret_key`, access tokens, or any privileged credential is needed, and the gem's own `HmacValidator`/`Registry.process` will treat it as fully authenticated.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values as part of the signable payload verified by the HMAC (or otherwise cryptographically bind them), so that `Registry.process` cannot dispatch a handler with an identity value that was not covered by the signature check.

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a forged HTTP request to the target app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body successfully (see `lib/shopify_api/webhooks/request.rb:45-63`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`@raw_body` = `B`) and compares to `H` — it matches (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using `shop = "victim-shop.myshopify.com"` taken straight from the forged header, and invokes the host app's handler with this attacker-chosen shop value (`lib/shopify_api/webhooks/registry.rb:198-199`).
6. The host application's handler processes/persists the attacker's event content under `victim-shop.myshopify.com`, even though the payload never originated from or was authorized for that shop.
