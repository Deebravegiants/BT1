### Title
Divide-by-zero panic in `calc_take_pnl` when a decimal-normalized pool balance floors to zero, permanently bricking Deposit/Withdraw/WithdrawPnl - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`Processor::calc_take_pnl` (invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`) performs `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` and, inside `Calculator::calc_x_power`, `checked_mul(...).unwrap().checked_div(current_y).unwrap()`, using the decimal-normalized pool balances `x1`/`y1` as divisors without validating that they are non-zero. `Calculator::normalize_decimal_v2` (`program/src/math.rs:106-116`) computes `val * sys_decimal_value / 10^native_decimal`, an integer division that can floor a small but strictly-positive raw vault balance down to `0` when `native_decimal` (pc/coin decimals) is large relative to `sys_decimal_value`. This is directly analogous to the ImageMagick `AdaptiveThresholdImage` bug: a dimension/quantity of zero is produced by an intermediate computation and is not validated before being used as a divisor/index in downstream arithmetic, leading to an out-of-bounds/undefined operation (here, a Rust panic from `.unwrap()` on `None`).

### Finding Description
`normalize_decimal_v2` is used throughout `processor.rs` to convert raw vault token amounts into a fixed "system decimal" scale before they are fed into `calc_take_pnl`: [1](#0-0) 

`process_deposit`, `process_withdraw`, and `process_withdrawpnl` all normalize `total_pc_without_take_pnl` / `total_coin_without_take_pnl` and pass the results (`x1`, `y1`) into `calc_take_pnl`: [2](#0-1) [3](#0-2) 

Inside `calc_take_pnl`, once the "current k >= last k" branch is taken (which is the common case, since accumulated swap fees make the pool's constant product monotonically non-decreasing over time), the code computes: [4](#0-3) 

`Calculator::calc_x_power` divides by `current_y` (`y1`) with an unchecked `.unwrap()`: [5](#0-4) 

and immediately afterward `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` divides by `x1` the same way. Neither `x1` nor `y1` is checked for zero anywhere before these divisions, mirroring the ImageMagick pattern where a "height of zero" (an attacker/state-influenced quantity that can legitimately become zero) is "mishandled" by code that assumes it is always positive.

`x1`/`y1` can become zero even though the underlying raw vault balance (`total_pc_without_take_pnl`/`total_coin_without_take_pnl`) is non-zero: swap instructions only guard that the *raw* output amount stays below the raw pool total (`swap_amount_out >= total_pc_without_take_pnl` → `InsufficientFunds`), e.g.: [6](#0-5) 
This permits the raw pool-side balance to be driven down to a very small positive value (e.g., 1–999 raw units for a 9-decimal token with `sys_decimal_value = 1_000_000`), which `normalize_decimal_v2` then floors to `0`.

### Impact Explanation
Once `x1` (or `y1`) is `0`, every subsequent call into `calc_take_pnl` — triggered by *any* unprivileged user calling `Deposit`, `Withdraw`, or `WithdrawPnl` on that pool — panics inside `checked_div(...).unwrap()`. Because the divisor is derived deterministically from the current (drained) vault balance, and depositing/withdrawing normal liquidity is itself blocked by the panic, the pool's LP/PnL-accounting paths become unusable: liquidity providers can no longer deposit or withdraw, permanently freezing LP funds already locked in the pool (only swap, which does not call `calc_take_pnl`, may remain partially functional). This matches the "permanent freezing of user or LP funds" impact bar required by the validation rules.

### Likelihood Explanation
Reaching the vulnerable state requires an attacker to swap one side of the pool down to a small raw remainder (feasible via `SwapBaseIn`/`SwapBaseOut`, which are unprivileged, attacker-controllable-amount instructions), which is easiest on pools with low-liquidity/high-decimal tokens and default `sys_decimal_value`. The triggering call itself (any subsequent `Deposit`/`Withdraw`/`WithdrawPnl`) is a single, ordinary transaction with attacker-chosen or victim-chosen accounts/data — no privileged signer or off-chain component is required. The "current k >= last k" branch (needed to reach the division) is the common/expected path because swap fees make `k` monotonically non-decreasing, so the branch is not hard to satisfy.

### Recommendation
- In `Calculator::calc_x_power` and in `calc_take_pnl`'s `y2` computation, explicitly check `current_y != 0` and `x1 != 0` before dividing, returning an `AmmError` (e.g., `AmmError::CalcPnlError` or a new `ZeroDivisor` variant) instead of panicking.
- More generally, replace `unwrap()` on `checked_div`/`checked_mul` throughout `math.rs`/`processor.rs` pnl and swap math with proper error propagation so a degenerate/zero intermediate value produces a graceful instruction failure rather than a panic that can recur indefinitely for the same pool state.
- Consider bounding `normalize_decimal_v2` inputs or enforcing a minimum post-swap remaining balance so that normalization can never floor a positive raw balance to zero.

### Proof of Concept
1. Create a pool via `Initialize2` where the pc (or coin) mint has a high `decimals` value (e.g., 9) relative to `amm.sys_decimal_value` (default `1_000_000`), with modest initial liquidity.
2. Repeatedly call `SwapBaseIn`/`SwapBaseOut` (unprivileged, attacker-funded) in the `PC2Coin`/`Coin2PC` direction that reduces `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) toward its minimum allowed raw value (any value `< total` is accepted per the `swap_amount_out >= total_..._without_take_pnl` check), driving the raw pc balance to a small value such as `1`–`999`.
3. At this point `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, pc_decimals=9, sys_decimal_value=1_000_000)` returns `0` because `1 * 1_000_000 / 10^9 = 0` (integer floor).
4. Any subsequent call to `Deposit`, `Withdraw`, or `WithdrawPnl` on this pool invokes `calc_take_pnl` with `x1 = 0`; the branch computing `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` (or the `checked_div` inside `calc_x_power`) executes `checked_div(0)`, which returns `None`, and `.unwrap()` panics, aborting the transaction and leaving the pool's LP deposit/withdraw paths permanently unusable for all users.

*Note: the exact minimum swap amount needed to reach the zero-floor threshold, and whether other invariants (e.g., `min_size`/`InitLpAmountTooLess` checks) further constrain reachability, were not fully re-verified against the complete `calc_total_without_take_pnl_no_orderbook` implementation, which the available index did not fully expose; a full Devin session with file access is recommended to confirm exact numeric bounds before treating this as a confirmed exploit.*
