### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop` value that downstream handlers rely on for tenant attribution is read from an HTTP header that is never included in the HMAC-covered content. This breaks the binding `shop-covered-by-HMAC == shop-attributed-to-payload`, allowing any request bearing a validly-signed body (which any shop that has the app installed can legitimately obtain) to be replayed with a forged shop-domain header naming a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only against `to_signable_string` (i.e., the body), so it never covers the shop header: [3](#0-2) 

`Registry.process` passes the unauthenticated `request.shop` straight into the handler's `WebhookMetadata` after only checking the HMAC, with no cross-check that the header matches the shop the signed body actually originated from: [4](#0-3) 

Because the app's `client_secret` (`Context.api_secret_key`) used to compute the HMAC is shared across every shop that has the app installed, a body+HMAC pair legitimately produced for shop A remains valid when replayed with the `shop-domain` header rewritten to shop B. This is exactly the injection prompt's target pattern: "a field acted on but not covered by the HMAC."

### Impact Explanation
This is a cross-tenant access vulnerability (Critical). An attacker who has installed the app on their own shop can generate a validly-HMAC-signed webhook body of their choosing (by triggering the corresponding store event), then replay that request body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim shop's domain in the shop-domain header. The receiving application, trusting `WebhookMetadata#shop` (built from `request.shop`), will process the attacker-controlled payload as if it belongs to the victim's tenant — potentially corrupting victim shop records, triggering unauthorized data-subject actions (e.g., `customers/data_request`, `shop/redact`), or otherwise causing state changes attributed to a shop the attacker does not control.

### Likelihood Explanation
Likelihood is High: no leaked credentials, TLS interception, or privileged account are needed. Only two unprivileged actions are required — (1) install the target app on an attacker-controlled shop (any developer/merchant can do this) and trigger an event to obtain a validly signed body/HMAC pair, and (2) POST that captured body with a modified shop-domain header directly to the app's webhook endpoint, which is a public internet-facing URL by design. Nothing in `Request` or `HmacValidator` prevents this replay because the header is never covered by the signature.

### Recommendation
Bind the shop identity to the signed content, e.g. include the `shop-domain` (and `topic`) header value in `to_signable_string` so the HMAC covers it, or independently verify that `request.shop` corresponds to a shop session/installation that is expected to have produced this specific webhook (e.g., cross-check against a known/installed shop list before dispatching to handlers). At minimum, document and enforce that consuming applications must not trust `WebhookMetadata#shop` for tenant attribution without additional verification.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger a webhook-emitting action (e.g., create an order) to receive a legitimately HMAC-signed webhook POST at the app's public endpoint — capture `raw_body` and the `x-shopify-hmac-sha256` value.
2. Replay the exact same `raw_body` and `hmac-sha256` header to the same endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key` — the header substitution is invisible to it (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host application to act on the victim shop's tenant data using attacker-supplied content.
