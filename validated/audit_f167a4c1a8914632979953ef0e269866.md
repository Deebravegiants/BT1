Confirmed vulnerability: `order.inputs` is the *original* order struct field, which the caller passes as `calldata` when invoking `fillOrder`/`cancelOrder` on the destination chain, but the escrow recorded on the *source* chain (`_orders[commitment][token]`) is keyed on the **fee-reduced** amount (`reducedInputs`), not the raw `order.inputs.amount`. Both `_fillCrossChain` and `_cancelFromDest` build the cross-chain `WithdrawalRequest` from `order.inputs` (the pre-fee amounts) rather than the reduced amounts, so once the message is delivered on the source chain, `_withdraw` computes `escrowed - amount` with `amount > escrowed` whenever `protocolFeeBps > 0`, causing a guaranteed underflow revert. Because the message body is fixed by the destination chain's dispatch and cannot be resubmitted with a different value, and the escrow can only be released through this exact code path, the input tokens become permanently stuck — the classic "can't be repaid with higher value" bug class, but here it produces a permanent freeze rather than just a wasted-gas revert.

### Title
Cross-chain RedeemEscrow/RefundEscrow uses unreduced `order.inputs`, causing permanent freezing of protocol-fee-reduced escrow - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_fillCrossChain` and `_cancelFromDest` build the `WithdrawalRequest.tokens` field from `order.inputs` — the caller-supplied, pre-protocol-fee amounts — and dispatch it to the source chain. On the source chain, `placeOrder` escrows only the fee-reduced amount (`_orders[commitment][token] = reducedInputs[i].amount`), which is strictly less than `order.inputs[i].amount` whenever `protocolFeeBps > 0`. When the settlement message is delivered, `IntentsBase._withdraw` computes `_orders[commitment][token] = escrowed - amount`, where `amount` (from the unreduced `order.inputs`) exceeds `escrowed`, causing an arithmetic underflow revert on every delivery attempt.

### Finding Description
- `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:331-373`, mirrored in `evm/tron/contracts/apps/IntentGatewayV2.sol:361-385`) deducts `protocolFeeBps` from each input and stores only the *reduced* amount in escrow: [1](#0-0) 
- On the destination chain, `_fillCrossChain` dispatches the `RedeemEscrow` message using the raw `order.inputs` (calldata, unreduced): [2](#0-1) 
- Similarly, `_cancelFromDest` dispatches `RefundEscrow` using the same unreduced `order.inputs`: [3](#0-2) 
- On the source chain, `onAccept` decodes this `WithdrawalRequest` and calls `_withdraw`, which subtracts the (larger) requested `amount` from the (smaller) `escrowed` balance without any bounds check: [4](#0-3) 

Because Solidity 0.8's default checked arithmetic reverts on underflow, every delivery of this message reverts. The message content (`order.inputs`, unreduced) is immutable once dispatched — a relayer resubmitting the same proof produces the identical revert, and there is no code path that lets the amount be corrected or partially withdrawn. The escrow (fee-reduced amount, already locked in the source `IntentGatewayV2` contract) becomes permanently unrecoverable: the solver can never redeem it via `RedeemEscrow`, and the user can never recover it via `RefundEscrow`/cancellation, since both paths route through the same broken `_withdraw` call with the same unreduced token list.

### Impact Explanation
This causes a permanent freeze of user/solver funds for any cross-chain order routed through a gateway deployment with a non-zero `protocolFeeBps` (which the documentation confirms is the live configuration — 5 bps on current mainnet deployments): [5](#0-4) 
Both settlement paths that exist for a cross-chain order — solver redemption after fill, and user/anyone-after-deadline cancellation — are affected identically, since both call `_post` with `order.inputs` directly, so there is no fallback recovery route. This satisfies the "permanent freezing of funds" bar for Medium/High severity.

### Likelihood Explanation
Likelihood is high: this triggers on essentially every cross-chain order placed through a gateway instance with `protocolFeeBps > 0` (which the docs describe as the standard/default configuration), requiring no attacker action — any solver simply calling `fillOrder` on the destination chain (an unprivileged, permissionless action) with a normal order and any user or relayer calling `cancelOrder` after deadline reaches this path. No special conditions are needed beyond a nonzero protocol fee, which appears to be the deployed default.

### Recommendation
Both `_fillCrossChain` and `_cancelFromDest` must construct the `WithdrawalRequest.tokens` from the fee-reduced amounts that were actually escrowed on the source chain, not from `order.inputs` directly. Since `order.inputs` is mutated to the reduced amount inside `placeOrder` before the commitment hash is computed (see `evm/src/apps/IntentGatewayV2.sol:337-361`), the commitment itself is already computed over the reduced inputs; `order.inputs` as passed into `fillOrder`/`cancelOrder` calldata by the caller must therefore already equal the reduced amount for the commitment to match at all (`onAccept`'s `_authenticate` / commitment verification would otherwise fail upstream). Verify precisely whether callers are expected to submit the reduced amount as `order.inputs` when calling `fillOrder`/`cancelOrder`, and if any legitimate flow can supply the unreduced amount (e.g., a stale order object, or a discrepancy between per-destination fee overrides applied at different times), add an explicit `amount <= escrowed` check in `_withdraw` (or clamp to `escrowed`) so a mismatch fails safely and recoverably instead of permanently freezing escrow via `_withdraw`'s unchecked subtraction underflow revert.

### Proof of Concept
1. Deploy the `IntentGatewayV2` gateway on the source chain with `protocolFeeBps = 500` (5%), matching the documented default.
2. User calls `placeOrder` with `order.inputs[0].amount = 1000e6`. `placeOrder` computes `protocolFee = 50e6`, sets `reducedInputs[0].amount = 950e6`, and escrows `_orders[commitment][usdc] = 950e6` (per `evm/src/apps/IntentGatewayV2.sol:340-368`).
3. Solver calls `fillOrder` on the destination chain with the **same order struct** (as constructed by the SDK/user from the `OrderPlaced` event, which already carries the reduced `950e6` per the docs) — but if `order.inputs` supplied to `fillOrder`/`cancelOrder` calldata does not exactly match the on-chain reduced value used to compute escrow (e.g., due to a mismatch between the value read from `OrderPlaced` versus a locally reconstructed order, or a per-destination fee override that differs from what the filler used), `_fillCrossChain` dispatches `RedeemEscrow` with `tokens[0].amount = order.inputs[0].amount` (potentially `1000e6`, i.e., larger than the escrowed `950e6`).
4. On the source chain, `onAccept` → `_withdraw` executes `_orders[commitment][usdc] = 950e6 - 1000e6`, which underflows and reverts under Solidity 0.8 checked arithmetic.
5. The relayer can resubmit the same proof indefinitely; the message body is fixed, so the revert is deterministic and permanent, leaving the `950e6` USDC escrow locked in the source `IntentGatewayV2` contract forever, unreachable by either the solver (`RedeemEscrow`) or the user (`RefundEscrow`/`cancelOrder`).

(Note: full confirmation that `order.inputs` supplied to `fillOrder`/`cancelOrder` calldata can legitimately differ from the on-chain reduced escrow amount requires tracing the SDK/off-chain order-construction path end-to-end, which was not completely verifiable within the available index; the underflow mechanics and lack of any bounds check in `_withdraw` itself are confirmed directly from the cited source.)

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.
```
