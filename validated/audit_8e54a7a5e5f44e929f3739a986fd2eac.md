## Title
Stale `need_take_pnl_pc`/`need_take_pnl_coin` cache can exceed live vault balance, causing every swap/deposit/withdraw to permanently revert - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
This is the same bug class as the Derby `blacklistProtocol` issue: a cached total (`savedTotalUnderlying` there, `need_take_pnl_pc`/`need_take_pnl_coin` here) is subtracted with `checked_sub` from a freshly-read live balance. If the live balance ever falls below the cached figure, the subtraction underflows and the whole instruction path reverts, permanently freezing the affected pool.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` is the first accounting step of every core AMM instruction reachable by unprivileged users — swap, deposit, and withdraw: [1](#0-0) 

It computes the LP-owned reserve by subtracting the cached, delayed "protocol pnl" amounts from the current vault token balances with `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?`. This same call is used to gate:
- `process_swap_base_in` / `process_swap_base_out`: [2](#0-1) 
- deposit: [3](#0-2) 
- withdraw: [4](#0-3) 
- withdrawpnl: [5](#0-4) 

`need_take_pnl_pc`/`need_take_pnl_coin` are updated only inside `calc_take_pnl`, which credits the owner's pnl cut and debits the LP-side "without pnl" totals so that, by design, `vault_balance == total_without_pnl + need_take_pnl` should hold: [6](#0-5) 

The code base itself anticipates this invariant can break: `process_withdrawpnl` explicitly checks `need_take_pnl_coin <= amm_coin_vault.amount && need_take_pnl_pc <= amm_pc_vault.amount` before paying out, and returns `AmmError::TakePnlError` otherwise instead of assuming the invariant always holds: [7](#0-6) 

If, due to accumulated rounding in `exchange_pool_to_token`/`exchange_token_to_pool` (Floor/Ceiling roundings used across deposit/withdraw) or any other drift between the LP-share bookkeeping and the physical vault balances, `need_take_pnl_pc`/`need_take_pnl_coin` ever exceeds the live vault token amount, then:
1. `process_withdrawpnl` starts failing with `TakePnlError` (the owner can no longer flush the pnl cache), and
2. Every subsequent swap, deposit, and withdraw call — reachable from a single unprivileged transaction with attacker-chosen accounts — reverts via `AmmError::CheckedSubOverflow` in `calc_total_without_take_pnl_no_orderbook`, because it is the very first accounting step of all these instructions.

There is no code path that resets or self-heals `need_take_pnl_pc`/`need_take_pnl_coin` once it drifts above the vault balance, so the pool becomes permanently unusable — identical in shape to the Derby report where `blacklistProtocol` could permanently revert because a stale cached total no longer matches live protocol balances.

### Impact Explanation
If triggered, this permanently freezes all LP funds in the affected pool: swaps, deposits, and withdrawals all revert, and the accrued pnl fee for the pool owner also becomes unrecoverable via `withdrawpnl`. This matches the "permanent freezing of user or LP funds" bar for a valid Medium/High finding, since ordinary users interacting through `SwapBaseIn`/`SwapBaseOut`/`Deposit`/`Withdraw` cannot recover the pool once the condition occurs.

### Likelihood Explanation
The likelihood depends on whether rounding drift or another benign path can actually push `need_take_pnl_pc/coin` above the live vault balance without any operator error, which I could not fully trace to a concrete, reproducible transaction sequence purely from code inspection. The presence of the explicit `<=` guard in `process_withdrawpnl` (rather than an `unwrap`) indicates the developers considered this a real, reachable state, but I could not conclusively construct the exact rounding/ordering sequence that forces the invariant to break using only the available source.

### Recommendation
In `Calculator::calc_total_without_take_pnl_no_orderbook`, replace the hard `checked_sub(...).ok_or(CheckedSubOverflow)?` with a saturating computation (clamp `need_take_pnl_*` to the live balance, treating any excess as zero remaining "without pnl" balance) so that a drift between the cached pnl amount and the live vault balance degrades gracefully instead of permanently bricking swap/deposit/withdraw for the whole pool. Additionally, add an instrumented invariant check/alert path so any drift is caught long before it can exceed the vault balance.

### Proof of Concept
A definitive PoC transaction sequence that forces `need_take_pnl_pc`/`need_take_pnl_coin` above the live vault balance could not be constructed from static code review alone; the finding is reported based on the structural parallel with the Derby `blacklistProtocol` bug and the codebase's own defensive check in `process_withdrawpnl` implying the underlying invariant is not unconditionally guaranteed.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
