### Title
Tokens transferred directly to the pool by mistake are permanently frozen with no recovery path - (File: contracts/pool/src/lib.rs)

### Summary
The Liquidity Pool contract keeps `cash` as a pure accounting book that is deliberately decoupled from the physical token balance. Every token-moving entrypoint either (a) pays out at most the booked cash amount (`withdraw`, `claim_revenue`, `borrow`, `flash_loan`) or (b) credits cash only up to a booked shortfall (`recapitalize`). There is no sweep/rescue entrypoint — not even an owner-gated one — so any token amount sent directly to the pool address outside the controller-orchestrated flows is never credited to anyone and can never leave.

### Finding Description
The pool's accounting model is documented in `docs/reference/architecture.md`: "The pool tracks cash in an accounting book… direct donations do not automatically increase booked cash." All mutation entrypoints in `contracts/pool/src/lib.rs` are `#[only_owner]` (the controller), and every payout is bounded by the booked `cash` figure, not the actual token balance:

- `withdraw` debits cash and transfers only the booked amount to `receiver` (`contracts/pool/src/lib.rs:154-163`).
- `claim_revenue` pays `min(cash, revenue)` — again booked cash, not balance (`contracts/pool/src/lib.rs:250-252`).
- `recapitalize` books `min(amount, backing_shortfall)` based on the `amount` argument supplied by the controller, which transfers the tokens in beforehand; it does not measure the pool's pre-existing balance (`contracts/pool/src/ops/recapitalize.rs:44-58`). A stray balance already sitting in the contract is ignored, and any excess over the shortfall is refunded to the payer, not swept.
- `flash_loan` only pays out against booked cash and pulls back principal + fee.

Unlike the swap-aggregator, which has `sweep_balance` to recover non-fee balances (`contracts/swap-aggregator/src/lib.rs:189-202`), the pool exposes no analogous function. The only owner-only escape is `upgrade`, i.e., a code change — not a recovery mechanism.

This mirrors the nounsDAO Stream finding exactly: after tokens land in the contract outside the intended flow, no actor — payer, recipient, or even governance through normal execution — can move them back out.

### Impact Explanation
Permanent freezing of funds. A user who mistakenly calls `token.transfer(user → pool, amount)` (e.g., supplying via the token contract directly instead of through `controller.supply`, or fat-fingering the destination address) loses the full amount forever. The tokens inflate the pool's physical balance above its booked cash but are never credited to any position, never counted as revenue, and never payable on withdrawal. The loss is borne entirely by the sender with no recourse.

### Likelihood Explanation
Requires a user error (direct transfer to the pool address), which is why this is Medium rather than High. The scenario is realistic: on Stellar, a SAC `transfer` to a contract address is a single call, and users accustomed to EOA-style deposit patterns can easily send funds straight to the pool. The pool's address is public and is the actual custodian of all market liquidity, making it a plausible mistaken destination. No attacker action is needed; the freeze is a structural property of the code.

### Recommendation
Add a recovery path for unbooked token balances. Options:

1. An owner-gated `sweep(hub_asset/token, recipient)` that transfers `balance - total_booked_cash_across_hubs` for that token. Because one physical balance backs multiple hub markets, the sweep must compute the surplus as `token.balance(pool) - sum(cash over all markets of that token)`, not per-market cash.
2. Alternatively, let `recapitalize` measure the actual received delta (like `repay`'s measured settlement) so pre-existing stray balances can be absorbed into booked cash during a shortfall — though this donates the funds to suppliers rather than returning them, so option 1 is the closer analog to the report's recommendation.

### Proof of Concept
```rust
// Mistaken sender transfers directly to the pool, bypassing the controller.
token.transfer(&user, &pool_address, &1_000_000);

// The donation never reaches the book:
// - get_reserves(hub_asset) is unchanged (cash is an accounting entry).
// - user holds no supply position; withdraw() has nothing to pay.
// - claim_revenue() pays min(cash, revenue); revenue is unchanged.
// - recapitalize() books min(amount_arg, shortfall) — it ignores the
//   pre-existing balance and would still pull tokens from `payer`.
//
// No entrypoint in LiquidityPoolInterface can move the surplus:
// every mutator is owner-only AND bounded by booked cash, and no
// sweep/rescue function exists. The 1_000_000 is locked permanently.
```

Supporting evidence: `contracts/pool/src/lib.rs:33-36` documents cash as a separate accounting book; `docs/reference/architecture.md:57-61` states direct donations do not increase booked cash; `contracts/pool/src/ops/recapitalize.rs:52` credits only `min(amount, backing_shortfall)` from the argument; contrast with the aggregator's `sweep_balance` at `contracts/swap-aggregator/src/lib.rs:189-202`, which the pool lacks.
