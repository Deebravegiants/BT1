## Title
Webhook shop-tenant identity spoofed via unauthenticated `X-Shopify-Shop-Domain` header, not covered by HMAC — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value it hands to the application's handler is read from an HTTP header that is never included in the HMAC-signed bytes. This breaks the intended binding `shop_authenticated == shop_acted_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor, however, is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, completely outside the signed material [2](#0-1) .

`Registry.process` validates the request via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the raw body) and `request.hmac` (also from a header, `hmac-sha256`) [3](#0-2) [4](#0-3) . After this check passes, the handler is invoked with `shop: request.shop` taken straight from the unauthenticated header [5](#0-4) .

Because the HMAC is computed over the raw body bytes only, an attacker who can produce (or replay) a body/HMAC pair that is valid for their own shop can attach an arbitrary `X-Shopify-Shop-Domain` header value and cause the gem to report a different tenant's shop to the host application's webhook handler. Concretely: if the body content for a given topic is not tenant-specific (or an attacker's own legitimately-signed webhook body happens to be replayable against a different shop context), the HMAC check alone cannot detect that the `shop` header was swapped, since `shop` is never mixed into the signed string. This is exactly the "field acted on but not covered by the HMAC" bug class from the report analog: refund/recipient (shop) is trusted from an out-of-band value while only a different, unrelated field (body) is what's actually authenticated.

The equality that should hold is: `shop_used_for_tenant_dispatch == shop_bound_by_hmac_signature`. Here it is actually `shop_used_for_tenant_dispatch == shop_header_value` (unauthenticated), while `hmac` only binds `raw_body`.

### Impact Explanation
If a host application trusts `WebhookMetadata#shop` to determine which merchant's data record to update/create/delete (a very common integration pattern, e.g. keying database rows by `shop`), an attacker able to obtain one validly-signed webhook (from their own installed/dev store, which is trivial to obtain since app installation is self-service) can potentially cause tenant confusion by manipulating only the header, without ever needing the app's `client_secret`. This crosses the tenant boundary called out in the rules ("cross-tenant access") because the *acted-upon* identity value is unauthenticated even though the request as a whole "passes" HMAC validation.

### Likelihood Explanation
Exploitability depends on whether the attacker can produce or replay a raw body whose HMAC is valid while freely varying the header. Since HMAC is over the body only, and headers are fully attacker-controlled by anyone who can reach the app's public webhook endpoint (webhooks are delivered to a public HTTP callback URL), the header can be freely modified on any request satisfying the HMAC check for its own body — no secret needed to change the header. The remaining constraint is obtaining at least one valid `(body, hmac)` pair, which any developer/attacker can get by installing the app on their own store and capturing a real webhook delivery, or by triggering webhooks with attacker-influenced body content matching another shop context (e.g., app/uninstalled, or topics with app-agnostic payload). This is a realistic, moderate-likelihood path reachable by any unprivileged internet user who can register/install the target app.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the HMAC-signed material, or otherwise cryptographically verify the header value against a value obtained from an authenticated channel (e.g., cross-check against the session/shop the webhook subscription was registered for). At minimum, `to_signable_string` should not be limited to `@raw_body` when other header-derived fields are used for authorization-sensitive routing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving genuine webhook deliveries with a valid `X-Shopify-Hmac-Sha256` computed over the raw body by Shopify using the real `client_secret`.
2. Attacker replays that exact `(raw_body, hmac)` pair to the app's webhook endpoint but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this still matches, since the header changed but the signed bytes did not [6](#0-5) .
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [5](#0-4)  and the host application processes the (attacker-supplied) body under the victim shop's tenant context.

Note: This finding was derived purely from static analysis of `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, and `lib/shopify_api/utils/hmac_validator.rb`; I could not execute the test suite to empirically confirm exploitability end-to-end (e.g., whether real-world webhook body content ever varies meaningfully by shop for the same signed bytes), so likelihood should be treated as an assessed estimate rather than a proven exploit chain.
