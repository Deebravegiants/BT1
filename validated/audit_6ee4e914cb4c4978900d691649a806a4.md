### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant shop spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to route and label the webhook to a specific tenant are taken from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header without any cryptographic binding to that body [2](#0-1) . `Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header value [3](#0-2) . `Registry.process` then trusts `request.shop` as the tenant identity and forwards it, unverified, straight into the handler's `WebhookMetadata` [4](#0-3) [5](#0-4) .

The identity binding broken is: `hmac-signed bytes (raw_body)` ≠ `bytes acted on for tenant identification (shop-domain header)`. Because the shop domain is never part of the signable string, a valid HMAC (computed by Shopify with the app's shared `client_secret`) for one webhook delivery remains valid for that same body no matter what value is placed in the `shop-domain` header. Any party capable of relaying/replaying a captured, legitimately-signed webhook request (e.g., a webhook proxy, logging middleware, browser extension, or network intermediary sitting in front of the app's public webhook endpoint) can swap the `shop-domain` header to an arbitrary other tenant string while keeping the same body and HMAC, and the app will accept it as valid and dispatch it as if it originated from the spoofed shop.

The documentation confirms host apps are expected to trust `data.shop` directly as the tenant identifier when processing side effects (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) , so this gem's own contract is that `shop` is a trusted, per-tenant identity value — yet it structurally cannot be, since it sits outside the signed envelope.

### Impact Explanation
This allows cross-tenant data confusion: webhook data legitimately generated for Shop A can be attributed to Shop B in the host application merely by altering an unauthenticated header, without needing the `client_secret` or any credentials for Shop B. Depending on how the host app uses `data.shop` (e.g., record lookups, billing/order state per merchant, queue partitioning), this can lead to cross-tenant data leakage or corruption — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be positioned to relay/replay a captured legitimate webhook payload+HMAC to the app's public webhook endpoint with a modified shop header (e.g., via a network position between Shopify and the app, a shared webhook relay/proxy, or logging infrastructure that echoes webhook traffic). This is a plausible but non-trivial precondition (it is not a purely "attacker sends one request" exploit — it needs a captured valid body+HMAC pair), so likelihood is moderate rather than certain, but the root cause (headers excluded from the signed payload) is clearly present in the gem's own verification logic.

### Recommendation
Bind the tenant/shop identity to the signed payload. This can't be perfectly enforced client-side because Shopify's HMAC scheme signs only the body, but the gem should at minimum document the residual trust boundary and encourage cross-checking `request.shop` against the app's known-installed shops with an offline session lookup before acting on webhook data, rather than treating `data.shop` in `WebhookMetadata` as an authenticated identity purely by virtue of passing `HmacValidator.validate`.

### Proof of Concept
1. Shopify sends a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. An intermediary (e.g., a shared webhook relay/proxy in front of the app, or anyone able to replay the captured request) resends the same body `B` and the same header `H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC-SHA256(client_secret, B) == H` [7](#0-6)  — this passes because `B` and `H` are unchanged.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)` [8](#0-7) , attributing Shop A's webhook data to Shop B.
