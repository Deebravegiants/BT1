### Title
`_swapBudget`'s 1% reservation is the *only* guard preventing a hostile-mint pre-seed from letting the rebalance swap consume 100% of one side, zeroing the LP deposit and recording a permanent zero-sized `LPLock` — the contract's own natspec documents this as the exact failure mode - ([File: packages/contracts/src/Bonding.sol])

### Summary
The external report's bug class is a moving offset (`src`) that is supposed to stay bounded by a fixed destination buffer but is allowed to overrun it because the bounding check is inadequate, corrupting adjacent state. The alt.fun analog is `Bonding._pairRebalance`'s swap input `s`, which is supposed to stay bounded within a "budget" (the analog of the destination buffer) so that `_routerDepositAndDispose`'s subsequent `addLiquidity` always has a non-zero remainder on both sides. The only thing keeping `s` inside that bound is `_swapBudget`'s hard-coded `99/100` shrink of the raw balance — a single-degree-of-freedom guard whose own natspec explicitly states that without it, the swap can consume the *entire* available side, causing `_routerDepositAndDispose` to skip `addLiquidity`, `finalizeGraduation` to return `liquidity = 0`, and `LPLock.recordLock` to lock a zero-sized position permanently.

### Finding Description
`_seedRebalancing` computes `maxSwap` for the hostile-mint-pre-seed rebalance leg as `_swapBudget(_ltSwapInventory(lt, protectedLT))` or `_swapBudget(IERC20(tokenAddress).balanceOf(address(this)))` [1](#0-0) . `_swapBudget` caps that at 99% of the raw balance specifically "so the subsequent `addLiquidity` always has a non-zero amount of BOTH sides to deposit" [2](#0-1) .

The natspec on `_swapBudget` spells out the failure mode verbatim: "Without this, an extreme hostile pre-seed (massively imbalanced reserves) drives the unconstrained `_noFeeSwapInput` past our per-side budget, `_pairRebalance` clamps to the full budget, and the swap consumes 100% of one side. `_routerDepositAndDispose` then skips `addLiquidity` (`remToken == 0` or `remLT == 0`), `finalizeGraduation` returns `liquidity = 0`, and `LPLock.recordLock(...)` records a zero-sized lock — the attacker's pre-existing LP becomes 100% of the pool" [3](#0-2) .

This is structurally the same shape as `execute_filter_delta`'s bug: a computed offset (`s = sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn`, capped at `maxSwap`) is meant to stay strictly inside an allotted region (the side's balance minus what must remain for the deposit), but the actual containment is delegated to a single arithmetic margin (`* 99 / 100`) rather than to the invariant itself. `_noFeeSwapInput` clamps `s` to `maxSwap` [4](#0-3) , and `_pairRebalance` executes that swap unconditionally once `s > 0` and the pair's quote is non-zero [5](#0-4) . If `maxSwap` (i.e., the 99% margin) is ever insufficient — e.g., an attacker pre-seeds the pair with reserves skewed so extremely that even 1% of `remToken`/`remLT` genuinely reaching zero after fees/rounding, or a future edit changes/removes the `_swapBudget` shrink — `_routerDepositAndDispose` observes `remToken == 0 || remLT == 0`, silently skips `addLiquidity`, and returns `liquidity = 0` with no revert [6](#0-5) .

`LPLock.recordLock` is a permissionless, one-shot call from `finalizeGraduation` that cannot be skipped or retried once graduation has finalized (per the project's own AGENTS.md characterization of `LPLock` as "no withdraw in v1" and `recordLock` as one-shot) — so a zero-sized lock is not recoverable.

### Impact Explanation
A zero-sized `LPLock.recordLock` means the protocol's entire LP-seeding step for that graduation produces no locked liquidity while the attacker's pre-existing dust LP (minted via the front-run `pair.mint(attacker)` step of the hostile pre-seed attack) becomes effectively 100% of the pool's LP supply. This is a permanent freezing/misallocation of the curve-raised LT and the 250M-token `LP_RESERVE` that were supposed to back the graduated pool, and hands full LP control (and the swap-back arbitrage/fee capture) to the attacker — a direct violation of the "one-shot `LPLock.recordLock` that `finalizeGraduation` cannot skip" invariant the codebase calls out as load-bearing. This qualifies as permanent freezing of creator/trader funds routed through graduation.

### Likelihood Explanation
The codebase's own comments assert the 1% margin is currently sufficient for "any realistic pre-seed" and only "kicks in for catastrophic pre-seeds beyond our budget capacity." This significantly lowers likelihood under the current constants, but the finding is that correctness rests entirely on this single hard-coded ratio holding under all reachable pre-seed shapes (uint112-bounded reserves, arbitrary attacker-chosen ratios, and fee/rounding behavior of the live HyperSwap pair `getAmountOut`), rather than on an invariant that is provably always satisfied (unlike the `tokensForLP ≤ LP_RESERVE` parabola invariant elsewhere in the same file, which the team treats as "not a runtime guess"). Any future edit to `_swapBudget`, `DIRECT_MINT_PRESEED_BPS`, or the fee-charging pair mock/real HyperSwap pair fee percentage shifts this margin without an explicit test asserting `remToken > 0 && remLT > 0` is unconditionally guaranteed, so likelihood is Medium: reachable only through the same unprivileged front-run-the-pair griefer path already described as "the actual exploit" in AGENTS.md, at the boundary of the currently-documented safety margin.

### Recommendation
Replace the probabilistic 99% margin with an explicit invariant check: after computing `s` (before executing the swap), assert that the resulting `remToken`/`remLT` that `_routerDepositAndDispose` will see are strictly greater than zero, and fall back to `_seedDirectMint` (as is already done when `_pairRebalance` returns `false`) whenever that can't be guaranteed — rather than allowing `_routerDepositAndDispose` to silently no-op `addLiquidity` and return `liquidity = 0`. Add a fuzz test that specifically drives `reserveToken`/`reserveLT` to the uint112 ceiling at maximally hostile ratios and asserts `finalizeGraduation`'s resulting `liquidity > 0` in every case, not just that it doesn't revert.

### Proof of Concept
Not independently reproducible from static review alone; the codebase's own natspec on `_swapBudget` in `packages/contracts/src/Bonding.sol` lines 1356-1378 already documents the exact PoC shape (an "extreme hostile pre-seed" with "massively imbalanced reserves" via the front-run-and-mint-dust-LP pattern demonstrated in `test/TwoPhaseGraduation.t.sol`'s `_grieferMintPreSeed` helper). Confirming whether any input within the reachable uint112/attacker-controlled space can still exhaust the 1% margin (e.g., via `getAmountOut`'s fee rounding at extreme skew) requires running/extending `test/NoFeeSwapInput.t.sol`'s fuzz suite against `_routerDepositAndDispose`'s zero-remainder branch directly, which is beyond static index inspection — recommend a Devin session with full repo/test access to fuzz this boundary before treating it as confirmed exploitable versus a defense-in-depth gap.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _routerDepositAndDispose(
        address tokenAddress,
        address lt,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        BondingStorage storage $ = _s();
        address routerAddr = $.uniswapV2Router;
        address lpLock_ = $.lpLock;
        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));
        // Subtract `protectedLT` (LT that doesn't belong to this graduation
        // — concurrent escrows or stray dust, snapshotted at the top of
        // `finalizeGraduation`) so the deposit allowance can never pull
        // another graduation's earmark or accidentally absorb dust into a
        // locked LP.
        uint256 ltBal = IERC20(lt).balanceOf(address(this));
        uint256 remLT = ltBal > protectedLT ? ltBal - protectedLT : 0;

        if (remToken > 0 && remLT > 0) {
            IERC20(tokenAddress).forceApprove(routerAddr, remToken);
            IERC20(lt).forceApprove(routerAddr, remLT);
            (,, liquidity) = IUniswapV2Router02(routerAddr)
                .addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock_, block.timestamp);
            IERC20(tokenAddress).forceApprove(routerAddr, 0);
            IERC20(lt).forceApprove(routerAddr, 0);
        }

        // Burn off-ratio TOKEN remainder (`Bonding` is the Token owner).
        // Hostile pre-seeds reduce circulating supply by the attacker's
        // wasted-side share, net positive for honest holders.
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
        // LT remainder is third-party — we cannot burn it. It stays in
        // this contract until `finalizeGraduation`'s post-bookend sweeps
        // it to the owner. Honest graduations never reach this code path,
        // so the residue is zero outside attack scenarios.
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
