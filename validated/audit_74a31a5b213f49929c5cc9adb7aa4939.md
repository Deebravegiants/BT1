## Analysis

The report is about weak PBKDF2 parameters (unrelated key-derivation issue), which is out of scope directly. Mapping this to the required bug class ("a field acted on but not covered by the HMAC") points to the webhook HMAC validation logic in this gem.

`ShopifyAPI::Webhooks::Request` computes its signable string strictly from the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `to_signable_string` (the raw body) — none of those header fields are part of the signed bytes: [3](#0-2) 

`Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id` directly after this body-only HMAC check succeeds, dispatching the handler and constructing `WebhookMetadata` from these unauthenticated header values: [4](#0-3) 

### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are acted on but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body via `Utils::HmacValidator.validate`. The HMAC signable string is only the raw body; the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used to route and attribute the webhook are never included in the signed material.

### Finding Description
Shopify signs a webhook body with the app's shared `client_secret`, identical for every shop that has the app installed. Because the HMAC covers only `@raw_body` (`Request#to_signable_string`), any HMAC-valid `(body, hmac)` pair generated for **one** shop's webhook delivery remains valid for **any** combination of `shop-domain`, `topic`, or `webhook-id` header values, since none of those headers factor into the signature. `HmacValidator.validate_signature` recomputes the signature purely from `verifiable_query.to_signable_string` and compares it to the received HMAC — it has no knowledge of, and does not bind, the header fields that `Registry.process` subsequently trusts (`request.shop`, `request.topic`, `request.webhook_id`) to build `WebhookMetadata` and select/run the handler. This breaks the intended binding: `shop authenticated == shop the payload data is attributed to`.

### Impact Explanation
An attacker who is any unprivileged merchant with the app installed on their own shop can receive a legitimately Shopify-signed webhook body+HMAC for their own store, then resend that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (a victim shop) and/or a different `shopify-topic`/`webhook-id`. `Registry.process` still validates the HMAC (body untouched) and will invoke the registered handler believing the data originated from and belongs to the spoofed shop/topic — a cross-tenant data-attribution break, and a way to trigger handler logic for topics/webhook IDs the request never truly represents.

### Likelihood Explanation
Any merchant who installs the app can trivially capture a genuine webhook (e.g. via `orders/create` on their own store) and replay it with modified headers to the app's public webhook URL — no privileged credentials, `client_secret`, or access token needed. This is straightforward to automate.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise separately bind/verify these values (e.g., cross-check `shop-domain` against a known installed-shop list, or embed them in the signable string) before trusting them in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the app on shop A (`shop-a.myshopify.com`); trigger a webhook (e.g. `orders/create`) and capture the raw POST: headers `x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-shop-domain: shop-a.myshopify.com`, and the raw body.
2. Resend the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `shop-b.myshopify.com` (a victim shop) and/or change `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the untouched raw body against the HMAC.
4. The handler executes with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: <attacker-chosen>, ...)`, attributing shop A's data to shop B / an arbitrary topic.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
