### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the unauthenticated `shopify-shop-domain` HTTP header, but the HMAC signature computed by `HmacValidator` only covers the raw request body. `Registry.process` validates the HMAC and then forwards this unauthenticated `shop` value straight to the handler as the tenant identifier, breaking the binding between "the body verified by the shared secret" and "the shop the payload is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the (attacker-controllable at the HTTP layer) header, with no cryptographic tie to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes and constant-time-compares the HMAC exclusively against `verifiable_query.to_signable_string` (i.e. the body), never the headers: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the whole request, then forwards the unauthenticated `shop` header value to the handler as `WebhookMetadata#shop`: [4](#0-3) 

Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app, any holder of one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on an attacker-controlled store and capturing (or self-generating, since they can also just compute a valid HMAC using known `code`/body content sent to their own store) a delivery — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` reports success because it never inspects the header, and `Registry.process` hands the attacker-chosen `shop` to the handler as if it were authenticated.

This is the same "field acted on but not covered by the HMAC" class from the report: the reward-pool/gauge mismatch let a wrong address be trusted for state-changing action; here the wrong (attacker-chosen) `shop` is trusted for tenant-scoped state-changing action (e.g. GDPR compliance webhooks) despite HMAC validation succeeding.

### Impact Explanation
Webhook handlers built on this gem are documented to key merchant-specific behavior off `WebhookMetadata#shop` (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics registered via `Registry::MANDATORY_TOPICS`). A forged `shop` value that survives HMAC validation lets an attacker cause the host application to execute merchant-scoped actions (including destructive data-redaction flows) attributed to a victim shop they do not control — a cross-tenant identity-binding bypass reachable by any unprivileged internet user who can reach the app's public webhook endpoint and who has legitimately installed the app on any single shop (including a free/dev store) to obtain one valid signed payload.

### Likelihood Explanation
Webhook endpoints are plain internet-reachable HTTP(S) endpoints (that is the entire point of webhook delivery), so no privileged access to Shopify or the target merchant is required. The only barrier is knowledge of one valid `(body, hmac)` pair signed under the app's shared secret, which any developer/attacker can generate for themselves simply by installing the app on their own (or a trial) store and observing a legitimate delivery — no theft of `api_secret_key` is needed, since the attacker's own shop already receives correctly signed payloads.

### Recommendation
Bind the asserted `shop` (and other identity-bearing headers such as `topic`/`webhook-id`) into the HMAC-covered signable content, or otherwise require host applications to cross-check the header `shop` against an independently verified session/installation record before trusting it, and document this requirement explicitly. At minimum, `HmacValidator`/`Webhooks::Request` should not present `shop` as if it were part of the verified payload without this caveat.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture one legitimate webhook delivery, e.g. `customers/redact` with body `{"customer": {...}}` and its valid `x-shopify-hmac-sha256` value (computed by Shopify using the app's shared `api_secret_key`).
2. Send a POST directly to the app's public webhook endpoint with the exact same body and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `@raw_body` (identical to step 1) — the shop header is never checked.
4. The registered handler receives `WebhookMetadata.new(topic: "customers/redact", shop: "victim.myshopify.com", ...)` and performs the redaction/compliance action against `victim.myshopify.com`, even though the payload never legitimately originated from Shopify for that shop.
