## Title
Ambiguous FA/Pool seed concatenation lets an attacker front-run and hijack the deterministic object address of a not-yet-launched `name`/`symbol` pair, redirecting victim APT into an attacker-controlled pool - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/bonding_curve_launchpad.move`, `aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move`)

### Summary
`bonding_curve_launchpad::create_fa` and `liquidity_pairs::register_liquidity_pair`/`get_pair_obj_address`/`get_fa_obj_address` all derive the deterministic object address for a Fungible Asset and its liquidity pool by naively concatenating the user-supplied `name` and `symbol` strings with a single, unescaped `"-"` byte separator, with no normalization or delimiter-collision protection. Because `name` and `symbol` are unrestricted strings that may themselves contain `"-"`, two semantically different `(name, symbol)` pairs can serialize to the identical seed bytes, and therefore to the identical Aptos object address (`object::create_object_address`). This is the same "lack of input normalization" bug class as the external report, but here it produces a genuine custody hazard: whichever creator claims the colliding address first permanently owns the FA metadata object, the `FAController`/`TransferRef`, and the `LiquidityPair` object at that address, and any subsequent caller who supplies the *other* colliding `(name, symbol)` string pair (e.g., via `swap`) will unknowingly operate on the attacker's FA/pool instead of the pair they intended.

### Finding Description
The seed construction is repeated identically in three places: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

In every case the seed is built as `bytes(name) || b"-" || bytes(symbol)`, with no length-prefixing, no escaping of `"-"` inside `name`/`symbol`, and no character-set validation before it is fed into `object::create_object_address` / `object::create_named_object`. Since `object::create_object_address` is a pure deterministic hash of `(creator, seed)` [5](#0-4) , any two `(name, symbol)` pairs whose concatenation with `"-"` yields the same byte string collide to the same object address, the same `FAController`/metadata object, and the same `LiquidityPair` object.

The custody-relevant break is in `create_fa`'s existence check and `swap`'s address resolution:

- `create_fa` only guards against re-creating the *exact same* address via `object::object_exists<FAController>(get_fa_obj_address(name, symbol))` [6](#0-5) . It does nothing to prevent a *different* string pair mapping to that same address before the intended owner launches.
- `swap` blindly trusts the caller-supplied `name`/`symbol` to resolve the FA/pool address and moves real APT/FA value through it: [7](#0-6) .

So an attacker can pre-launch a project under a `(name, symbol)` pair engineered to collide with a `(name, symbol)` pair that a legitimate project intends to (or has publicly announced it will) launch. The attacker's `create_fa_pair` call succeeds first and creates the `FAController` (holding `TransferRef`) and `LiquidityPair` object at the colliding address, fully attacker-controlled. When the legitimate `(name, symbol)` pair is later interacted with — either the real project's `create_fa_pair` call (which will simply abort with `EFA_EXISTS_ALREADY`, denying them the intended identity) or, more importantly, any user calling `swap(name, symbol, ...)` using the legitimate strings — that call resolves to the *same* object address as the attacker's pool and moves the victim's APT into the attacker-controlled `LiquidityPair.apt_reserves`/`fa_store`, in exchange for the attacker's junk FA.

### Impact Explanation
This is a custody-accounting corruption: APT submitted by a victim who believes they are swapping into a legitimate `(name, symbol)` liquidity pool is instead deposited into a `LiquidityPair` object entirely owned/controlled by the attacker (`extend_ref`, `fa_store`, reserves), because the deterministic address derivation collapses two distinct logical identities into one Aptos object address. The attacker fully controls that object's `ExtendRef`/`TransferRef` and can withdraw the accumulated APT reserves via the normal swap/graduation paths. This matches the Custody Impact Gate criterion "Supply or custody accounting corruption that moves value to the wrong holder," and constitutes value theft against any user or subsequent legitimate `create_fa_pair` caller relying on the `(name, symbol)` identity to be unique.

### Likelihood Explanation
Likelihood is high in this specific contract: `name` and `symbol` are entirely attacker-controlled arguments to a public entry function (`create_fa_pair`), with no assertion preventing `"-"` characters or otherwise disambiguating the seed. Constructing a colliding pair (`name="AB-C", symbol="D"` vs `name="AB", symbol="C-D"`) requires no special privilege — any account can front-run a known/anticipated project name and symbol combination before the legitimate launch transaction lands, which is realistic given mempool visibility of pending `create_fa_pair` transactions or public pre-announcement of a project's ticker/name.

### Recommendation
Do not build the object seed by naive string concatenation with an unescaped delimiter. Instead, length-prefix each component (e.g., BCS-serialize `(name, symbol)` as a tuple, or prepend each field's byte length before its bytes) before hashing into the seed, in both `bonding_curve_launchpad::create_fa`/`get_fa_obj_address` and `liquidity_pairs::get_pair_obj_address`/`register_liquidity_pair`. Additionally, reject `name`/`symbol` values containing the separator byte (or any character outside an allow-listed set) before using them as a seed component, consistent with the report's original recommendation to normalize and reject non-conforming input.

### Proof of Concept
1. Attacker calls `bonding_curve_launchpad::create_fa_pair(attacker, apt_amount_in=0, name="AB-C", symbol="D", ...)`.
   - Seed computed in `create_fa`: `bytes("AB-C") || b"-" || bytes("D")` = `"AB-C-D"`.
   - This creates FA metadata + `FAController` and, via `register_liquidity_pair`, a `LiquidityPair` object both at `object::create_object_address(fa_generator_address / pairs_signer_address, "AB-C-D")`, fully owned by the attacker's `FAController.transfer_ref` / `LiquidityPair.extend_ref`.
2. Later, a legitimate project intends to launch `name="AB"`, `symbol="C-D"`.
   - Seed computed for their call: `bytes("AB") || b"-" || bytes("C-D")` = `"AB-C-D"` — identical to step 1.
   - Their `create_fa_pair` call hits `assert!(!does_fa_exist, EFA_EXISTS_ALREADY)` and aborts, since the address is already claimed by the attacker.
3. A victim user, believing `name="AB"`/`symbol="C-D"` is (or will be) the legitimate project, calls `bonding_curve_launchpad::swap(victim, name="AB", symbol="C-D", swap_to_apt=false, amount_in=X)`.
   - `get_fa_obj_address("AB","C-D")` resolves to the same colliding address from step 1.
   - The victim's APT is transferred via `liquidity_pairs::swap_apt_to_fa` into the attacker-controlled `LiquidityPair`'s `apt_reserves`/pool, and the victim receives the attacker's FA in return.
4. The attacker, holding `TransferRef`/`ExtendRef` for that pool, can subsequently withdraw or otherwise control the accumulated APT reserves.

**Note on verification limits:** I was unable to confirm from the index whether `fungible_asset::create_primary_store_enabled_fungible_asset` enforces any character-set restriction (e.g., disallowing `-`) on `name`/`symbol`, since the `MAX_NAME_LENGTH`/`MAX_SYMBOL_LENGTH` validation logic in `fungible_asset.move` was not fully retrievable via search in this session. If such a restriction already forbids the `-` delimiter character inside `name`/`symbol`, the specific collision construction shown here would not compile/execute successfully, though the underlying design flaw (delimiter-based seed without length-prefixing) would still be present and exploitable via other byte sequences unless the character restriction is comprehensive. I recommend confirming this in a live Devin session by inspecting `aptos-move/framework/aptos-framework/sources/fungible_asset.move` in full.

    public fun create_object_address(source: &address, seed: vector<u8>): address {
        let bytes = bcs::to_bytes(source);
        bytes.append(seed);

        from_bcs::to_address(hash::sha3_256(bytes))
