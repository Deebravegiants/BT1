Audit Report

## Title
Freezable collateral in AMM liquidity pools permits permanent lock of counterparty funds - (File: `substrate/frame/asset-conversion/src/lib.rs`, `substrate/frame/assets/src/lib.rs`)

## Summary
`pallet-assets` grants the per-asset `Freezer` role the ability to call `freeze(origin, id, who)` on any account holding that asset, which sets `AccountStatus::Frozen` and blocks all outgoing transfers from that account via `reducible_balance`'s `ensure!(!account.status.is_frozen(), Error::<T, I>::Frozen)` check. Because `pallet-asset-conversion` pools deposits from arbitrary liquidity providers into a shared `pool_account` and later calls `T::Assets::transfer(asset, &pool_account, withdraw_to, ...)` in `remove_liquidity`/swaps, an attacker who creates their own asset (retaining the `Freezer` role) and pairs it in a pool can later freeze the `pool_account` for that asset, permanently blocking withdrawal of both pooled legs for any innocent LP.

## Finding Description
`pallet_assets::freeze` is gated only by `origin == d.freezer`, not by any special privilege beyond being the asset's freezer, and directly flips the target account's status to `Frozen`: [1](#0-0) . That status is enforced in `reducible_balance`, which underlies all transfer paths: [2](#0-1) . `pallet-asset-conversion`'s `do_create_pool` derives a deterministic `pool_account` for an arbitrary pair of `T::AssetKind` and touches accounts for both assets there: [3](#0-2) , and `remove_liquidity` transfers both legs out of that same `pool_account`: [4](#0-3) , [5](#0-4) . Critically, in every production runtime configuration examined — `asset-hub-westend`, `asset-hub-rococo`, and `staking-async parachain` — the `TrustBackedAssetsInstance` of `pallet-assets` uses `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>`, i.e. asset creation is permissionless for any signed account (gated only by a deposit), and the creator becomes the asset's `owner`/`admin`/`issuer`/`freezer` by default per `do_create`/`create`: [6](#0-5) , [7](#0-6) . `pallet-asset-conversion`'s `Config` in these runtimes has no `CreatePoolOrigin`/allowlist restricting which `T::AssetKind` may be paired into a pool — pool creation is reachable via a signed extrinsic against `T::Assets` (which wraps these freezable trust-backed/foreign assets): [8](#0-7) .

## Impact Explanation
This confirms the claimed root cause: any unprivileged account can create an asset it controls the freezer role for, pool it against a legitimate asset, wait for third-party LPs to add liquidity, and then permanently freeze the pool account for that asset. Since `remove_liquidity` atomically transfers both legs and fails entirely if either transfer fails, this traps the innocent LP's funds in both assets with no recovery path via any `pallet-asset-conversion` dispatchable — only the attacker (as the freezer) can `thaw`, and they have no incentive to. This is a concrete, realistic fund-lock affecting non-privileged counterparties, matching the claim's assessed impact.

## Likelihood Explanation
The exploit path requires only standard, permissionless extrinsics available to any signed account in the examined production runtimes: `pallet_assets::create` (deposit-gated but not privilege-gated), `pallet_asset_conversion::create_pool` (no `CreatePoolOrigin` restriction found in Asset Hub Westend/Rococo or the staking-async parachain runtime), `add_liquidity` by the victim, and `pallet_assets::freeze` by the attacker (who is the asset's freezer by default). No governance, root, or node-level access is needed, and this is repeatable across any new asset the attacker creates.

## Recommendation
- Require or allow configuring an `AssetKind` filter/allowlist in `pallet-asset-conversion` (e.g. via a `CreatePoolOrigin`/pool-creation guard) so pools can only be created for assets known not to have an untrusted, mutable freezer.
- Provide a governance/`AdminOrigin`-gated recovery dispatchable (e.g. `force_remove_liquidity`) to rescue LP funds if a pool account becomes frozen on one leg.
- Document that pallets accepting arbitrary `T::AssetKind` as collateral/pool assets must verify the asset's freezer/admin is trusted or absent before accepting deposits.

## Proof of Concept
1. Attacker `A` calls `pallet_assets::create` (`CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` in Asset Hub) to create asset `X`, becoming its `admin`/`freezer` per `do_create`.
2. `A` calls `AssetConversion::create_pool(origin=A, asset1=Native, asset2=X)`, which succeeds since `do_create_pool` imposes no asset-trust check beyond `asset1 != asset2` and deposit payment.
3. Victim LP `B` calls `AssetConversion::add_liquidity(..., asset1=Native, asset2=X, ...)`, depositing `Native` and `X` into `pool_account`.
4. `A` calls `pallet_assets::freeze(origin=A, id=X, who=pool_account)`, setting `pool_account`'s status to `Frozen` for asset `X` (`substrate/frame/assets/src/lib.rs:1192-1213`).
5. `B` calls `AssetConversion::remove_liquidity(...)`; the internal `T::Assets::transfer(asset2=X, &pool_account, withdraw_to, amount2, Expendable)` fails with `Error::Frozen` (`substrate/frame/asset-conversion/src/lib.rs:951-952`, enforced via `substrate/frame/assets/src/functions.rs:253-256`), reverting the whole extrinsic and permanently trapping `B`'s deposited liquidity.

		pub fn freeze(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Frozen;
				Ok(())
			})?;

				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

				T::Assets::touch(asset2.clone(), &pool_account, creator)?
