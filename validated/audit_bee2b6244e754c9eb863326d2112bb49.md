This confirms the finding: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header independently and never enters the HMAC-signed material (`lib/shopify_api/webhooks/request.rb:20-23`). `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity forwarded to the app's handler (`lib/shopify_api/webhooks/registry.rb:189-199`), so the "shop" bound to a webhook payload is never cryptographically tied to that payload.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, and `Registry.process` accepts any `shop-domain` header value as long as the (header-independent) body HMAC validates. This breaks the intended binding `shop-authenticated-by-HMAC == shop-delivered-to-handler`, letting an attacker with any genuine, validly-signed webhook payload relabel it as belonging to a different shop.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` this method is: [1](#0-0) 

Only `@raw_body` is signed. The `shop` accessor, however, is parsed straight from an HTTP header that is never part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (derived purely from the header) as the tenant identity handed to the app's business logic: [3](#0-2) 

Because the `hmac-sha256` header is computed and validated only against the body, an attacker who possesses *any* genuinely Shopify-signed webhook body+HMAC pair for a shop they control can resend the identical body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g., a victim shop's domain). `Utils::HmacValidator.validate` will still return `true` because it only recomputes the signature over `@raw_body`: [4](#0-3) 

The library documents `data.shop` as the trusted tenant identity handlers should key off of (e.g., to look up sessions or route work), reinforcing that this field is expected to be authenticated: [5](#0-4) 

This is the exact identity-binding failure class described in the report: a field (`shop`) that is acted upon (used for tenant routing/session lookup) is not covered by the HMAC that is supposed to authenticate the whole webhook, so the shop the signature vouches for and the shop the handler is told to trust can diverge.

### Impact Explanation
Any app built on this gem that keys per-tenant logic (session/store lookup, data writes, job dispatch) off `WebhookMetadata#shop` is exposed to cross-tenant webhook injection: an attacker who legitimately installs the app on their own shop (or otherwise obtains one valid signed webhook body/HMAC pair) can cause the app to process that payload as if it originated from an arbitrary victim shop domain, since only the body — not the shop — is authenticated. This can lead to cross-tenant data confusion/corruption (e.g., an attacker's order data being attributed to and processed under a different merchant's shop), which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires no access to the app's `api_secret_key`: it only requires the attacker to legitimately receive one valid webhook (trivial by installing the app on a shop they control, if self-serve installs are allowed) and the ability to POST arbitrary headers to the app's public webhook callback endpoint, which is by design internet-reachable. No TLS interception or credential theft is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signable material, or otherwise cryptographically bind the shop domain to the payload before validation — e.g., have `Webhooks::Request#to_signable_string` incorporate the shop-domain header, or require callers to separately verify that `request.shop` matches an expected/registered shop for the given webhook registration before trusting it in `WebhookMetadata`.

### Proof of Concept
1. App has a shop `attacker.myshopify.com` installed; Shopify sends a legitimate webhook with body `B` and a correctly computed `X-Shopify-Hmac-Sha256: H` header, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures this genuine request (`B`, `H`) from their own shop.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B`, the same header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` — validation succeeds: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload was never authenticated for that shop, and processes it as victim-shop data.
