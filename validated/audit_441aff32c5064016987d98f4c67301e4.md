### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-verified payload. `Utils::HmacValidator.validate` only proves the raw body bytes were signed by Shopify; it says nothing about which shop the header claims the webhook came from. `Registry.process` then hands that unverified `shop` value straight to the app's webhook handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which is not part of `to_signable_string`: [2](#0-1) 

`Registry.process` validates only that the body matches the HMAC, then immediately trusts `request.shop` (from the header) to build `WebhookMetadata` passed to the app-registered handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (body only) and compares against the `hmac` header: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" pattern from the report: the identity-binding equality `shop-domain header == shop that authored/signed the payload` is never checked. `shop-domain` and `hmac-sha256` are both merely "required headers to be present" — https://github.com/Alyssadaypin/shopify-api-ruby--013/blob/main/lib/shopify_api/webhooks/request.rb#L50-L59 — but their consistency with each other is never verified.

Because the shop-domain header is unauthenticated, any actor capable of delivering a byte-for-byte valid `(raw_body, hmac-sha256)` pair for a webhook they legitimately received (e.g., a merchant who installed the app on their own store and captured one of their own webhook deliveries) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never looks at the header, and `Registry.process` will invoke the app's handler with `shop: <attacker-chosen value>` alongside the original tenant's body data.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is meant to enforce: an app that keys per-tenant records, authorization, or side effects off `WebhookMetadata#shop` (the documented/intended use, since that's the only shop identifier `Request` exposes) can be made to attribute a legitimately-signed payload to a different, attacker-chosen shop. Depending on how the host app uses this field (e.g., looking up which merchant's data/subscription/order the payload updates, or which stored session/access token to act with), this results in cross-tenant data corruption or cross-tenant action, i.e., "cross-tenant access" per the Critical severity bar — without needing `api_secret_key`, an access token, or any privileged credential; only delivery of a previously-seen (or captured) legitimate webhook body/HMAC pair with a forged domain header.

### Likelihood Explanation
Moderate-to-high: unlike forging an HMAC (which requires the secret), this requires no secret at all — only reusing an already-valid `(body, hmac-sha256)` pair while changing one plain HTTP header. Any tenant that can install the app (an "unprivileged internet user" relative to other tenants) can capture their own valid webhook deliveries and replay them with a spoofed `shop-domain` header at the app's public webhook endpoint.

### Recommendation
Bind the `shop-domain` header into the HMAC-signable material, or otherwise verify that the shop present in the parsed body matches the `shop-domain` header before trusting either for tenant dispatch. At minimum, `Request#to_signable_string` (or `Registry.process`) should incorporate/cross-check the shop header so that `Utils::HmacValidator.validate` fails whenever the shop attribution differs from what was actually signed by Shopify for that payload.

### Proof of Concept
1. App owner (attacker) installs the app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `shopify-hmac-sha256: H`, header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint but changes only the `shopify-shop-domain` header to `victim-shop.myshopify.com` (leaving `B` and `H` untouched).
3. `Utils::HmacValidator.validate(request)` recomputes HMAC over `to_signable_string` (`= B`) and compares to `H` — passes, since `B`/`H` are unmodified: [5](#0-4)  / [6](#0-5) 
4. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's own body data, causing the host app to process/attribute the payload as belonging to `victim-shop`: [7](#0-6)
