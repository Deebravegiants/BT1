My analysis confirms the invariant `tokenBalance() < reserveToken()` is not enforced on-chain — it is described in `packages/contracts/test/GraduationInvariants.t.sol` (`test_inv_virtualReserveAlwaysExceedsRealBalance`) purely as an emergent property of "honest" curve usage (buys only), but nothing in `Pair.sol` or `Router.sol` stops an unprivileged holder from breaking it via a plain ERC20 donation of previously-bought `Token` supply back into the `Pair`.

### Title
Direct Token donations into `Pair` can push `tokenBalance() ≥ reserveToken`, permanently disabling the overflow-buy cap and the supply-based graduation trigger - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` relies on the invariant that a curve pair's live `tokenBalance()` is always strictly less than its stored virtual `reserveToken`, so that the overflow-cap branch (`cappedReserveToken = reserveToken - tokensOut`) never divides/reverts on `0`, and so the "supply exhausted" graduation trigger (`tokenBalance() == 0`) is reliable. That gap (`reserveToken - tokenBalance == LP_RESERVE == 250M` at launch, per `Bonding._deployAndSeed`) is only maintained because every path that removes tokens from the pair (`Router.buy`'s `transferToken`) also decrements `reserveToken` by the same amount via `Pair.swap`. A plain ERC20 `transfer` of `Token` into the `Pair` (unrelated wallet or the buyer itself, reachable per the scope rules) increases `tokenBalance()` without touching `_pool.tokenReserve`, which can shrink or eliminate the 250M gap. [1](#0-0) 

### Finding Description
`Bonding._deployAndSeed` mints the `Pair` with a virtual `tokenReserve = TOTAL_SUPPLY` (1B) while only transferring `curveSupply = 75%` (750M) real tokens, leaving `LP_RESERVE` (250M) permanently unbacked in the pair's accounting: `tokenBalance() == reserveToken - 250M` as long as the only balance-moving path is `Router.buy`'s `transferToken`, which always moves in lockstep with `Pair.swap`'s reserve update. [2](#0-1) 

`Pair.sol` has no hook analogous to UniswapV2's `sync()`/skim reconciliation between live ERC20 balance and stored reserves; `tokenBalance()` is a raw `balanceOf`, while `reserveToken`/`assetReserve` live in `_pool` and are mutated only by `mint`/`swap`. [3](#0-2) 

A trader can buy `X` tokens off the curve (both `tokenBalance()` and stored `reserveToken` drop by `X`, gap unchanged), then send those same `X` tokens directly to the `Pair` address via `Token.transfer` (an ordinary ERC20 call, not through `Router`/`Bonding`). This restores `tokenBalance()` to (approximately) its pre-buy level while `reserveToken` stays at the post-buy (reduced) value. If `X > LP_RESERVE (250M)`, the donation flips the invariant: `tokenBalance() > reserveToken`. `Router._computeBuy` caps `tokensOut` at `realBalance = pair.tokenBalance()` only when the uncapped `tokensOut` (which is always `≤ reserveToken`) exceeds `realBalance`; once `realBalance` is inflated above `reserveToken`, that branch can never fire again, silently disabling the documented overflow-buy protection for the remainder of that token's curve life. Separately, in the narrow case where a later large buy computes `tokensOut == realBalance == reserveToken` exactly, `cappedReserveToken = reserveToken - realBalance == 0` triggers a hard revert (`OverflowCapDegenerate`), bricking that specific buy size on that curve — the exact "invariant that was assumed always to hold quietly stops holding, and a bound check that used to be unreachable now trips" class of bug the Xen advisory illustrates, mapped onto alt.fun's curve accounting rather than Xen's event-channel bounds. [4](#0-3) 

The same donation also corrupts the supply-side graduation trigger `IPair.tokenBalance() == 0`, which the docs describe as the deterministic fallback for flat/bear markets where the USD leg never fires: [5](#0-4) 

With `tokenBalance()` inflated above the real sellable remainder, the curve can never reach exactly `0` via normal buys again (every buy still transfers real tokens out, but the padding from the donation means the live balance bottoms out above zero, or requires draining more than the true 750M-curveSupply accounting expects), stalling the only graduation path available when the LT never appreciates enough to hit the USD threshold.

### Impact Explanation
This is a griefing/DoS vector against a specific token's bonding curve, reachable by any address that has bought tokens on that curve (no privilege required, no cost beyond the buy itself — the donated tokens are the attacker's own, already paid for). It can (a) permanently disable the overflow-buy safety cap `Router._computeBuy` documents as load-bearing (`AGENTS.md`: "Router.sol | AMM math, buy/sell execution with **overflow buy cap**"), letting a subsequent oversized buy silently skip the intended "cap at real balance, refund unused LT" behavior instead of failing safe, and (b) freeze the supply-based graduation trigger, potentially trapping a token permanently in `Lifecycle.Curve` if the USD trigger never fires (an LT that never appreciates), denying creators/holders the graduation path and the associated LP formation — a form of permanent freezing of the mechanism the protocol relies on for exit liquidity.

### Likelihood Explanation
Medium. It requires the attacker to accumulate more than `LP_RESERVE` (250M, one-third of the sellable 750M curve supply) in tokens before donating them back — expensive in LT/USDC terms for a healthy curve, but achievable by a single well-funded trader or via a fresh/thin curve early in its life, and it is a one-time, irreversible action (donated tokens can't be un-donated) that leaves the affected curve permanently degraded.

### Recommendation
Have `Router._computeBuy` (and the graduation supply-trigger check in `Bonding.canGraduate`) reconcile `tokenBalance()` against the stored `reserveToken` net of the known `LP_RESERVE` offset rather than trusting the raw live balance directly, or add a UniswapV2-style `skim()`/`sync()` path so any surplus balance beyond `reserveToken - LP_RESERVE` can be swept out of the pair (e.g., to `FeeVault` or burned) before it can corrupt the cap/trigger logic. At minimum, assert `tokenBalance() < reserveToken` defensively at the top of `_computeBuy` and treat a violation as a hard error state routed to a recovery path rather than allowing it to silently disable the cap.

### Proof of Concept
1. `creator` launches a token via `Zap.createToken` with a modest seed; curve opens with `reserveToken = 1e9e18`, `tokenBalance() = 750_000_000e18` (`Bonding._deployAndSeed`, `Router.addInitialLiquidity`).
2. `attacker` calls `Zap.buy` repeatedly (or one large buy) to acquire `X > 250_000_000e18` tokens from the curve. Each buy decrements both `_pool.tokenReserve` and the pair's live `Token` balance by the amount bought (`Router.buy` → `Pair.transferToken` + `Pair.swap`), preserving the `250M` gap.
3. `attacker` calls `Token(tokenAddr).transfer(pairAddr, X)` directly (plain ERC20 transfer, no `Zap`/`Bonding` involved) — this raises `pair.tokenBalance()` by `X` without touching `_pool.tokenReserve`.
4. Now `pair.tokenBalance() > pair.getReserves().tokenReserve` (`X > 250M` gap flip). Verify via `IPair(pairAddr).tokenBalance()` vs `IPair(pairAddr).getReserves()` that the `test_inv_virtualReserveAlwaysExceedsRealBalance` property from `GraduationInvariants.t.sol` no longer holds.
5. Any subsequent buy sized so the uncapped `_computeBuy` output equals the (now-inflated) `realBalance` exactly triggers `cappedReserveToken == 0` → `Router.OverflowCapDegenerate()` revert, denying that buyer service; smaller/larger buys silently skip the overflow-buy cap entirely for the rest of the curve's life, and `Bonding.canGraduate`'s supply leg (`tokenBalance() == 0`) becomes unreachable through ordinary selling of the remaining supply.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;

    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
