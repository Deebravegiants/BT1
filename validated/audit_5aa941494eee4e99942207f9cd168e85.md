### Title
Reachable panic in `calc_take_pnl` via unguarded `checked_sub().unwrap()` on `x1`/`y1` vs. `integer_sqrt`-derived `x2`/`y2` can permanently freeze `Deposit`/`Withdraw`/`WithdrawPnl` - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes the "post-PNL" reserve values `x2`/`y2` from an integer square root and then subtracts them from the current normalized reserves `x1`/`y1` using unchecked `.unwrap()` calls on `checked_sub`. The guard that precedes this block only checks that native-unit `k` has not decreased; it does not guarantee `x2 <= x1` and `y2 <= y1` hold for every possible reserve/target-orders combination once integer-sqrt truncation and cross-multiplication rounding are taken into account. Because this function is called on every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction, an attacker-influenced pool state (reachable purely through normal deposit/withdraw activity with attacker-chosen amounts) can drive the stored `TargetOrders.calc_pnl_x/calc_pnl_y` and vault balances into a combination where `x2 > x1` or `y2 > y1`, causing `checked_sub(..).unwrap()` to panic and abort the transaction. This is directly analogous to CVE-2024-50613's reachable-assertion bug class: attacker-influenced numeric input reaches a hard invariant assumption (`assert`/`unwrap`) that is not actually guaranteed by the preceding validation, and the resulting panic aborts execution.

### Finding Description
In `calc_take_pnl`: [1](#0-0) 

The function first checks `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` (native-unit `k` non-decrease check) at [2](#0-1) , then computes `x2 = integer_sqrt(x2_power)` where `x2_power = target.calc_pnl_x * target.calc_pnl_y * x1 / y1` at [3](#0-2) , and finally performs `x1.checked_sub(x2).unwrap()` and `y1.checked_sub(y2).unwrap()` at [4](#0-3) .

The `k`-non-decrease guard is a necessary but not sufficient condition for `x2 <= x1`/`y2 <= y1` to hold exactly under integer arithmetic: `integer_sqrt` truncates, and `y2` is derived via a separate `checked_mul`/`checked_div` chain (`x2 * y1 / x1`) rather than being algebraically tied to `x1`/`x2` by construction. When the current price ratio (`x1/y1`) diverges from the stored `target.calc_pnl_x/calc_pnl_y` ratio in specific ways (e.g., extreme reserve imbalance introduced by successive attacker-controlled swaps/deposits/withdraws before the guarded call), rounding in the sqrt/multiply/divide chain can push `x2` marginally above `x1` (or `y2` above `y1`) even though the coarse `k` check passed, since the `k` check does not validate the derived `x2`/`y2` pair directly.

This code path is reached from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`, all callable by any unprivileged liquidity provider or the configured PNL owner with attacker-chosen deposit/withdraw amounts (subject only to slippage/min-amount checks), meaning the pool's internal reserve/target-orders state can be steered toward the panic-triggering condition through ordinary permissionless transactions. ### Impact Explanation
Because `TargetOrders.calc_pnl_x`/`calc_pnl_y` are on-chain state updated only within this same function (and rolled back together with the panicking transaction), once the reserve/target ratio reaches the panic-triggering region, every subsequent `Deposit`, `Withdraw`, or `WithdrawPnl` call recomputes the same inputs and panics again, since none of these paths succeed in advancing `calc_pnl_x`/`calc_pnl_y` past the bad state. This effectively permanently freezes liquidity providers' ability to deposit or withdraw from the affected pool, and blocks the `WithdrawPnl` path used to sweep protocol PNL - a permanent freezing of user/LP funds condition.

### Likelihood Explanation
Reaching the exact rounding edge case requires a specific reserve-to-target-orders ratio, which is not trivially reachable from a single transaction but is derivable through crafted sequences of deposits/withdraws/swaps (all callable by an unprivileged actor with attacker-chosen amounts) that skew `x1/y1` relative to `target.calc_pnl_x/calc_pnl_y` while still satisfying the coarse `k`-non-decrease guard. This places it below trivially-always-reachable but still realistically triggerable by a determined unprivileged actor without any special permissions.

### Recommendation
Replace the unchecked `.unwrap()` calls on `x1.checked_sub(x2)` and `y1.checked_sub(y2)` with saturating subtraction (clamping to zero) or an explicit `if x2 > x1 { x2 = x1 }` / equivalent clamp for `y2`, and return a typed `AmmError` instead of panicking when the derived `x2`/`y2` exceed `x1`/`y1`, so that a benign rounding edge case degrades to "no PNL taken this call" rather than aborting/bricking the instruction path.

### Proof of Concept
1. Initialize a pool with asymmetric `pc_decimals`/`coin_decimals` (e.g., 2 and 9, as used in the existing `test_calc_take_pnl`/`test_calc_pnl_precision` unit tests) via `Initialize2`. [7](#0-6) 
2. Perform a sequence of `Deposit`/`Withdraw`/`SwapBaseIn`/`SwapBaseOut` calls with attacker-chosen amounts to skew `total_pc_without_take_pnl`/`total_coin_without_take_pnl` relative to the stored `target.calc_pnl_x`/`calc_pnl_y` while keeping native `k` non-decreasing (so the guard at lines 188-192 still passes).
3. Trigger a subsequent `Deposit`, `Withdraw`, or `WithdrawPnl` call; the resulting `x2 = integer_sqrt(x2_power)` (or the separately-derived `y2`) exceeds `x1` (or `y1`) due to integer rounding, causing `x1.checked_sub(x2).unwrap()` (or the `y1` equivalent) at lines 213-214 to panic and abort the transaction.
4. Because the panic prevents `target.calc_pnl_x`/`calc_pnl_y` from being updated, every future call into `calc_take_pnl` with the same (or further-skewed) state repeats the panic, permanently blocking `Deposit`/`Withdraw`/`WithdrawPnl` for the pool.
