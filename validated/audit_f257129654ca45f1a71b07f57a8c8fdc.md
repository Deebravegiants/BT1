### Title
Permanently stuck `Lifecycle.Graduating` state via catastrophic HyperSwap V2 pre-seed that unconditionally reverts `finalizeGraduation` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
CVE-2018-19964 describes a lock (Xen's p2m lock) that becomes unavailable indefinitely because certain error conditions on the locking path are never cleared, causing a host-wide DoS. The analogous "lock" in alt.fun is `TokenInfo.lifecycle == Lifecycle.Graduating`: once phase 1 (`_enterGraduating`) fires, trading is frozen (`buy`/`sell` revert with `TokenIsGraduating`) and the only way to release the lock is a successful `finalizeGraduation` call [1](#0-0) . If `finalizeGraduation` can be made to revert unconditionally, the token is stuck in `Graduating` forever, exactly mirroring the Xen bug's "lock remains unavailable indefinitely in certain error conditions."

### Finding Description
`finalizeGraduation` is `nonReentrant` but otherwise permissionless and idempotent-on-revert: no state is persisted until the function completes without reverting [2](#0-1) . Phase 2 LP seeding for a hostile "mint pre-seed" pair goes through `_seedRebalancing` → `_pairRebalance` (direct `pair.swap` to correct the pool ratio, capped at `_swapBudget`, i.e. 99% of *this graduation's own* LT/token balance) → `_routerDepositAndDispose` (a HyperSwap V2 `addLiquidity` call with `amountAMin = amountBMin = 1`) [3](#0-2) [4](#0-3) .

The rebalance swap's size is capped by `maxSwap = _swapBudget(balance)`, which is bounded by this graduation's own LT/token inventory — it can never exceed `ltFromPair`/`tokensForLP` [5](#0-4) . An attacker can permissionlessly create the HyperSwap V2 `TOKEN/LT` pair and `pair.mint` an arbitrarily large, extremely lopsided reserve ratio ahead of graduation (the scope explicitly calls out "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation" as reachable). If the pre-seed skew is large enough that the budget-capped corrective swap cannot bring the pool back near the `tokensForLP/ltFromPair` ratio, the subsequent `addLiquidity(remToken, remLT, 1, 1, ...)` computes an optimal counter-amount via `quote()` against the still-skewed pool reserves; when that computed optimal amount rounds down to `0`, the V2 router's `require(amountB >= amountBMin)` (or the `A` side) fails and `addLiquidity` reverts. Since `finalizeGraduation` performs no state writes before this call and the attacker's pre-seed ratio persists across calls, every subsequent call to `finalizeGraduation(tokenAddress)` fails the same way — the token is permanently parked in `Lifecycle.Graduating`.

The contract's own natspec documents that this defense was previously covered by a dedicated integration suite that was later deleted, and explicitly disclaims ongoing verification of exactly this property: "the wrong-opening-price / LP-capture scenarios, attacker-no-profit, leftover recovery, and concurrent-graduation isolation properties are no longer enforced by automated tests" [6](#0-5) .

### Impact Explanation
A permanently bricked `finalizeGraduation` freezes:
- The 250M `LP_RESERVE` tokens and all curve-raised LT (`ltFromPair`) held by `Bonding` for that token, unrecoverable since there is no admin rescue/skip path for a stuck `Graduating` token.
- All trading on that token (`buy`/`sell` revert with `TokenIsGraduating`), a permanent freeze of trader funds already committed to the curve and of the creator's ability to ever complete graduation.

This matches the "Validate" bar: permanent freezing of trader/creator/LP funds and an LP that can never be seeded at all (worse than merely off-price).

### Likelihood Explanation
Reachable by any unrelated wallet with sufficient capital: create the HyperSwap V2 pair and `pair.mint` a large one-sided reserve before the target token's curve crosses the graduation threshold, then let/trigger graduation. No privileged role is required, and `Bonding._ensureUniswapV2Pair` will happily reuse an attacker-created pair rather than requiring a fresh one [7](#0-6) . The severity of the pre-seed skew needed scales with the size of `tokensForLP`/`ltFromPair` for the specific token, so this is most exploitable against lower-liquidity graduations, but the underlying budget cap makes it always theoretically possible given enough attacker capital.

### Recommendation
- Add a bounded fallback in `_routerDepositAndDispose` (or `_seedRebalancing`) that falls back to `_seedDirectMint`-style behavior (or `skim`+direct mint into a fresh effective pool) when the router's `addLiquidity` would revert, instead of letting the revert propagate out of `finalizeGraduation`.
- Alternatively, wrap the `addLiquidity` call in a low-level `call` and treat failure as "insufficient counter-liquidity", routing to the direct-mint/burn disposal path used elsewhere in the same function, so no pre-seed shape can cause `finalizeGraduation` to revert unconditionally.
- Restore/re-add the deleted hostile-pre-seed integration coverage (`HostilePreSeed.t.sol`) specifically for the catastrophic-skew case where the budget-capped rebalance cannot reach a safe deposit ratio.

### Proof of Concept
1. Attacker (unprivileged EOA) calls `IUniswapV2Factory.createPair(token, lt)` (or lets `Bonding._ensureUniswapV2Pair` create it later) and directly funds/`mint`s the pair with an extremely lopsided `(tokenReserve, ltReserve)`, e.g. depositing a huge amount of `TOKEN` (which the attacker can acquire cheaply pre-graduation on the curve) against a minimal `LT` reserve, far beyond the scale of the target token's eventual `tokensForLP`/`ltFromPair`.
2. Curve trading proceeds normally until the token crosses the graduation threshold and enters `Lifecycle.Graduating` via `_enterGraduating`/`triggerGraduation`.
3. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedRebalancing` computes the corrective swap capped at `_swapBudget(ownBalance)`; because the pre-seed skew vastly exceeds what this graduation's own `ltFromPair`/`tokensForLP` inventory can correct within the 99% budget, the post-swap pool ratio remains far from `tokensForLP/ltFromPair`.
4. `_routerDepositAndDispose` calls `addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock, block.timestamp)`; the router's `quote()`-derived optimal counter-amount rounds to `0` against the still-skewed reserves, and the router's minimum-amount check reverts the call.
5. `finalizeGraduation` reverts with no state change; the token remains in `Lifecycle.Graduating` on every future call as long as the attacker maintains the skewed pool ratio (trivially, since no other liquidity provider can interact meaningfully with the tiny/inaccessible corrective side), permanently freezing the token's curve-raised LT and 250M reserved tokens inside `Bonding`.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _seedRebalancing(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        (uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();
        bool tokenIs0 = IUniswapV2Pair(pair).token0() == tokenAddress;
        (uint256 reserveToken, uint256 reserveLT) = tokenIs0 ? (uint256(r0), uint256(r1)) : (uint256(r1), uint256(r0));

        // Below the band on BOTH sides, overpower the pre-seed with a direct
        // mint at the cached ratio: the rebalance swap is too coarse to reach
        // the ratio against such small reserves, and the pre-existing LP's
        // claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`. A
        // side that is large relative to its LP target still takes the
        // rebalance path so it isn't donated under the empty-mint `min()`.
        if (
            reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS
                && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS
        ) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Budget reads `balanceOf(this)` rather than `tokensForLP` /
        // `ltFromPair` so any skim donation contributes to the rebalance
        // and not only to `_routerDepositAndDispose`'s deposit.
        // Direction: pool TOKEN-rich vs target ⇒ swap LT in (TOKEN out).
        // Pool LT-rich ⇒ swap TOKEN in (LT out). Bounded by uint112 reserves
        // and curve-close-shape targets, both products fit in uint256.
        // When `_pairRebalance` returns false the seed is too small for any
        // swap to move the ratio (its fee-charging quote rounds to zero), so
        // the reserves are negligible against this graduation's inventory:
        // overpower them with a direct mint at the cached ratio rather than
        // letting the router deposit at the attacker's ratio. A swap that
        // does fire leaves the pool ≈ at target for the router deposit.
        if (reserveToken * ltFromPair > reserveLT * tokensForLP) {
            // Pool TOKEN-rich. tokenIn = lt, tokenOut = tokenAddress.
            // tokenInIs0 = (lt is token0) = !tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: lt,
                        tokenInIs0: !tokenIs0,
                        reserveIn: reserveLT,
                        reserveOut: reserveToken,
                        targetN: ltFromPair,
                        targetD: tokensForLP,
                        maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        } else if (reserveToken * ltFromPair < reserveLT * tokensForLP) {
            // Pool LT-rich. tokenIn = tokenAddress, tokenInIs0 = tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: tokenAddress,
                        tokenInIs0: tokenIs0,
                        reserveIn: reserveToken,
                        reserveOut: reserveLT,
                        targetN: tokensForLP,
                        targetD: ltFromPair,
                        maxSwap: _swapBudget(IERC20(tokenAddress).balanceOf(address(this)))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        }
        // else: pool already at curve-close ratio (rare — e.g. attacker
        // pre-seeded at exactly target). Skip swap, deposit directly.

        return _routerDepositAndDispose(tokenAddress, lt, protectedLT);
    }

    function _routerDepositAndDispose(
        address tokenAddress,
        address lt,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        BondingStorage storage $ = _s();
        address routerAddr = $.uniswapV2Router;
        address lpLock_ = $.lpLock;
        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));
        // Subtract `protectedLT` (LT that doesn't belong to this graduation
        // — concurrent escrows or stray dust, snapshotted at the top of
        // `finalizeGraduation`) so the deposit allowance can never pull
        // another graduation's earmark or accidentally absorb dust into a
        // locked LP.
        uint256 ltBal = IERC20(lt).balanceOf(address(this));
        uint256 remLT = ltBal > protectedLT ? ltBal - protectedLT : 0;

        if (remToken > 0 && remLT > 0) {
            IERC20(tokenAddress).forceApprove(routerAddr, remToken);
            IERC20(lt).forceApprove(routerAddr, remLT);
            (,, liquidity) = IUniswapV2Router02(routerAddr)
                .addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock_, block.timestamp);
            IERC20(tokenAddress).forceApprove(routerAddr, 0);
            IERC20(lt).forceApprove(routerAddr, 0);
        }

        // Burn off-ratio TOKEN remainder (`Bonding` is the Token owner).
        // Hostile pre-seeds reduce circulating supply by the attacker's
        // wasted-side share, net positive for honest holders.
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
        // LT remainder is third-party — we cannot burn it. It stays in
        // this contract until `finalizeGraduation`'s post-bookend sweeps
        // it to the owner. Honest graduations never reach this code path,
        // so the residue is zero outside attack scenarios.
    }
