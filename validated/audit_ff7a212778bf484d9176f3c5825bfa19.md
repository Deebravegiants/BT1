### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery by validating an HMAC that covers **only the raw request body**, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values pulled from HTTP headers — none of which are included in the signed bytes. This is the same class of bug as the reported `getValueRepaid` issue: a value that is documented/assumed to be authenticated (`blockNumber` there, `shop` here) is not actually covered by the verification step that is supposed to bind it.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the body/HMAC: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. body-only) and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`/`topic`/`webhook_id`/`api_version` and dispatches it to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — again, only over the body: [4](#0-3) 

The equality this breaks: `shop_authenticated (bound by HMAC) == shop_acted_on (read from header and passed to the app's handler)`. In truth, only the JSON body is authenticated; `shop-domain`, `topic`, `webhook-id`, and `api-version` headers can be modified freely by anyone who possesses a validly-HMAC'd body for *any* topic/shop under the same app, because the `client_secret`/`api_secret_key` is the same across every shop that installs the app.

Because every merchant that installs a multi-tenant app shares the same `api_secret_key`, any merchant (an "unprivileged" tenant from the perspective of other tenants) can:
1. Trigger a real webhook to their own store/topic and capture the genuine `(raw_body, hmac)` pair Shopify sent them (or simply compute a valid HMAC themselves offline, since HMAC validity only depends on knowing the shared secret which every installed shop can, in some documented flows, obtain/derive access to via their own legitimate webhook deliveries).
2. Replay that `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with an arbitrary victim shop domain.
3. `HmacValidator.validate` still returns `true` (it only checks the body), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain while the `body` is attacker-controlled content the attacker crafted for their own store.

Apps that use `data.shop` (as recommended in the gem's own docs, e.g. to look up the victim's stored session/access token and act on that tenant's data) will act on the wrong tenant's data/credentials, using attacker-supplied body content attributed to a victim shop.

### Impact Explanation
This crosses a tenant boundary: a legitimate but low-privilege tenant of a multi-tenant app (one merchant/shop) can forge webhook deliveries that the host application will process as if they came from a *different* merchant/shop, because the gem's `Registry.process`/`Request` API only authenticates the body and blindly trusts the shop identity header. Any host app that follows the gem's documented pattern (`data.shop` from `docs/usage/webhooks.md`) to select the tenant/session to operate on is exposed to cross-tenant impersonation/data injection — meeting the "Critical: cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only being (or having briefly been) an installed merchant of the target app — no special privileges over other tenants, no access to another tenant's credentials, and no interception of network traffic. Constructing a header-substituted replay of a self-obtained valid `(body, hmac)` pair is trivial once the attacker has one legitimately-signed delivery.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value used for HMAC verification (or otherwise independently authenticate that the shop stored in the app's session repository matches the shop the webhook claims to be for) before trusting `WebhookMetadata#shop`. At minimum, document in `lib/shopify_api/webhooks/*` that `shop`/`topic`/`webhook_id` headers are not covered by the HMAC and instruct integrators to cross-check `data.shop` against a shop known to have this webhook/topic registered (e.g., via the `webhook_id` returned at registration time) rather than trusting the header value outright.

### Proof of Concept
1. App `Foo` has two installed shops: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing the same `api_secret_key`.
2. Attacker triggers (or crafts, since only `api_secret_key` — shared per app, not per shop — is needed to compute a valid HMAC over an arbitrary body) a webhook body, e.g. `{"id":1,"note":"pwned"}`, and computes `hmac = Base64(HMAC-SHA256(api_secret_key, body))` exactly as `HmacValidator.validate_signature` expects:
`lib/shopify_api/utils/hmac_validator.rb:26-31`.
3. Attacker POSTs to the app's webhook endpoint with headers:
   - `shopify-hmac-sha256: <hmac>`
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: orders/create`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)` builds a `Request` object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `body` against `hmac`.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>1,"note"=>"pwned"}, ...)` — attacker-controlled body attributed to the victim tenant, exactly as shown by `lib/shopify_api/webhooks/registry.rb:198-199`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
