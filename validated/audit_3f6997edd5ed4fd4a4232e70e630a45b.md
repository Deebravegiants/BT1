### Title
Creator fee balances in `FeeVault` are permanently frozen if the creator's address is blacklisted by the USDC token contract - (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` pays out a creator's entire pooled USDC balance via `safeTransfer(msg.sender, amount)` with no ability to specify an alternate recipient. Real-world USDC (the mainnet HyperEVM USDC used at deploy, `0xb88339CB7199b77E23DB6E890353E22632Ba630f`, is Circle-model USDC) implements an issuer-controlled blacklist that makes `transfer`/`transferFrom` revert for a blacklisted address. If a creator's wallet is ever added to that blacklist (compliance action, malicious activity from that address, etc.), every future `claim()` call for that creator permanently reverts, and there is no admin or alternate-recipient path to recover the funds — mirroring the pattern in the referenced report where a blacklisted USDT address froze protocol-held collateral.

### Finding Description
`FeeVault.accrue()` credits `creatorBalance[creator]` in USDC based on `creator`, the address recorded in `Bonding.tokenInfo(token).creator` at the time of the trade: [1](#0-0) 

Withdrawal is exclusively via `claim()`, which transfers to `msg.sender` and offers no destination override: [2](#0-1) 

Because the mapping key is `msg.sender`'s own address, and there is no `claim(address to)` variant, no owner-level rescue for a specific creator's `creatorBalance`, and `sweepDonations()` only sweeps USDC *above* the backed total (it explicitly protects `totalAccruedCreator` from being swept): [3](#0-2) 

the accrued balance for a blacklisted creator becomes permanently unreachable. `Bonding.transferCreator` only re-points *future* fee attribution on `Bonding` — it does not, and cannot, move an already-accrued `FeeVault.creatorBalance[oldCreator]` entry to the new creator address: [4](#0-3) 

Since `Ownable2StepUpgradeable`/UUPS give the owner no function to redirect a specific creator's balance, and `claim()` is the only exit, once that specific `msg.sender` is denylisted by the USDC issuer, the funds are stuck in `FeeVault` forever, exactly analogous to the underlying report's blacklisted-address collateral freeze.

### Impact Explanation
This is a permanent freezing of creator funds held by the protocol (High severity per the rules: "permanent freezing of trader, creator or LP funds"). The amount at risk is every fee ever accrued to that creator across all tokens they've launched (`lifetimeCreatorEarned` shows the balance grows unbounded over the creator's lifetime of launches), with zero recovery path short of a contract upgrade.

### Likelihood Explanation
Likelihood is bounded by an external event (the creator's address getting added to USDC's blacklist) rather than an on-chain attacker action, so it is not something a random unprivileged party can trigger against another user at will. However, unlike the original BaseVault report, this needs no attacker cooperation from the creator: any compliance/enforcement action against that specific address (a realistic, non-hypothetical event for Circle-model USDC) is sufficient, and the freeze is deterministic and irreversible once it happens — there is no workaround inside the protocol.

### Recommendation
Add a `claim(address to)` (or `claimFor(address creator, address to)` restricted to `msg.sender == creator`) variant that lets a creator redirect payout to an alternate, non-blacklisted address, while keeping the existing `claim()` for backward compatibility. Alternatively, add an owner-gated `rescueCreatorBalance(address creator, address to)` that can only move a specific creator's balance to a caller-specified address after some grace period, so the funds are not solely gated by the possibly-blacklisted `msg.sender`.

### Proof of Concept
1. `Zap.buy`/`Zap.sell` trades on a token accrue creator fees via `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`, incrementing `creatorBalance[creator]`.
2. USDC's issuer (Circle-model token deployed at `Deploy.s.sol`'s `USDC` constant) adds `creator` to its blacklist.
3. `creator` calls `FeeVault.claim()`. Execution reaches `$.usdc.safeTransfer(msg.sender, amount)`; the underlying USDC `transfer` reverts because `to` is blacklisted, reverting the whole `claim()` call.
4. Every subsequent `claim()` call from `creator` reverts identically. `creatorBalance[creator]` keeps growing with every future trade on that creator's tokens (via `accrue`) but can never be withdrawn — the USDC is permanently locked in `FeeVault`, with `transferCreator` unable to move the already-accrued balance and no owner rescue function available.

            revert UnderfundedAccrual();
        }

    }

        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
