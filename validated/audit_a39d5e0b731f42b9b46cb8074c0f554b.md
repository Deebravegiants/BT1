## Valid Analog Found

### Title
Unchecked slice-length subtraction causes an out-of-bounds panic when processing an attacker-controlled cross-chain token message - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s ISMP `on_accept` handler decodes an ABI-encoded `Message` body from an incoming `PostRequest` and, when the message carries optional calldata with no attached Substrate signature, derives the dispatch origin from `message.from` without validating its length before slicing it. Any account able to dispatch a `HyperFungibleToken.send()` on a registered peer chain (an unprivileged token bridger) fully controls the `from` field's byte length and can trigger an out-of-bounds/underflow panic on delivery, mirroring the QEMU ATI-VGA `ati_cursor_define` bug class (unchecked index/length arithmetic on attacker-reachable input causing OOB access and a crash).

### Finding Description
In `on_accept`, the outer `PostRequest.from` (the registered peer contract address, checked via `ContractToAsset::get`) is distinct from the inner ABI-decoded `message.from` field, which is fully attacker-controlled Solidity `bytes` chosen by whoever calls `send()` on the source-chain token contract: [1](#0-0) 

The recipient (`message.to`) is explicitly length-checked (32 or 20 bytes, else a typed error): [2](#0-1) 

But in the optional-calldata branch, when no Substrate signature is attached, `message.from` is read raw and, for EVM sources, sliced with `from_bytes.len() - 20` with no length check at all: [3](#0-2) 

If `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`. This either panics directly (overflow-checks enabled) or wraps to a huge value that then panics on the subsequent out-of-bounds slice index — either way the runtime panics while executing an ISMP message. The very same field is handled safely elsewhere in the same file, in `on_timeout`, which explicitly checks for length 32 or 20 and returns a typed error otherwise: [4](#0-3) 

This shows the length-check pattern was known and applied consistently elsewhere but omitted specifically in the `on_accept` calldata-origin derivation path — the exact "unchecked index arising from untrusted external input" bug class described in the CVE (there, `ati_cursor_define` indexed VGA registers without validating bounds during an MMIO write; here, `on_accept` indexes a byte slice without validating its length during ISMP message delivery).

### Impact Explanation
`on_accept` is invoked by `pallet-ismp`'s message-execution pipeline when delivering a `PostRequest` addressed to this module, which is reachable via the unsigned, permissionless `handle_unsigned` extrinsic (anyone with a valid consensus/state proof can submit ISMP messages for free): [5](#0-4) 

Because the sender of a `HyperFungibleToken.send()` on the source chain fully controls `message.from` (it is just `abi.encodePacked(msg.sender)` or arbitrary bytes they choose to encode) and `message.data` (to enter the calldata branch), and needs no signature to enter the vulnerable branch, an unprivileged actor can craft a message whose ABI body has a `from` field shorter than 20 bytes while targeting an EVM destination and attaching non-empty `data`. Delivering it triggers a panic inside `on_accept`, which executes inside the runtime's message-execution path — this can abort/panic block execution for that extrinsic, disrupting message delivery for the pallet and, depending on how the panic unwinds through `execute`, potentially halting further processing of the batch or the node's transaction-pool validation logic (since `handle_unsigned` validity is checked by re-executing `Self::execute` in `validate_unsigned`). This satisfies the "route unable to deliver messages" acceptance criterion for a Medium-severity DoS analog.

### Likelihood Explanation
High reachability: `send()` on `HyperFungibleToken`/`WrappedHyperFungibleToken` is a public, unprivileged function on any registered peer chain, and the `data`/`from` fields of the ABI-encoded `Message` struct are entirely caller-supplied. No governance, admin, or validator collusion is required — only a legitimate, already-registered token peer (the normal bridging path) and a relayer to deliver the resulting proof, exactly the "relayed proof" / "token bridger" actor class in scope.

### Recommendation
Add the same length validation already used for `message.to` (in `on_accept`) and for `message.from` (in `on_timeout`) before deriving the calldata-execution origin in the no-signature branch: require `from_bytes.len() == 20` for EVM sources (and `== 32` otherwise) and return a typed `HftError` (e.g. `InvalidSenderLength`) instead of slicing unconditionally.

### Proof of Concept
1. On the source chain, deploy/use a registered peer `HyperFungibleToken` contract for a destination Substrate chain running `pallet-hyper-fungible-token`.
2. Call `send()` with `SendParams.data` set to a non-empty ABI-encoded `Call[]`/`SubstrateCalldata` blob that has no `signature`, and with the inner `Message.from` field manually crafted (via a custom sender contract or direct ABI encoding) to be fewer than 20 bytes (e.g. 4 bytes), while `Message.to`/`amount` are otherwise valid.
3. Relay this `PostRequest` to the destination chain via the normal proof-relaying path (`handle_unsigned`).
4. `pallet-hyper-fungible-token::on_accept` reaches the branch at `module.rs:176-181`; since `source.is_evm()` is true and `from_bytes.len() < 20`, the subtraction `from_bytes.len() - 20` underflows, causing a runtime panic during message execution instead of a graceful `HftError`.
