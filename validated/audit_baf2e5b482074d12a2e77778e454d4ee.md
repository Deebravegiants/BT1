### Title
Unbounded `secp256k1_recover` loop in BEEFY consensus verification lets a relayer force expensive computation on an oversized, invalid signature set before rejection - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
`verify_mmr_update_proof` in the BEEFY Rust verifier performs `secp256k1_recover` for *every* entry in the relayer-supplied `signed_commitment.signatures` vector before any merkle membership check runs. The only guard before the loop, `check_participation_threshold`, is a lower-bound (supermajority) check — it does not cap the number of signatures a submitter may include. This mirrors the OpenSSL `EVP_PKEY_public_check()` issue: an expensive per-item cryptographic computation is performed on an attacker-controlled, unbounded input before the input is determined to be invalid.

### Finding Description
In `verify_mmr_update_proof`: [1](#0-0) 

`signatures_length` is taken directly from the untrusted proof (`mmr.signed_commitment.signatures.len()`), and `check_participation_threshold` only enforces `signatures_length >= (2*authority_set.len)/3 + 1` — it never verifies an *upper* bound tied to the actual (small, trusted) authority set size: [2](#0-1) 

The verifier then iterates over every signature and performs a full `secp256k1_recover` (an expensive elliptic-curve operation) for each one, *before* any of the recovered addresses are checked against the trusted authority-set merkle root: [3](#0-2) 

Only after this entire loop completes does the code call `merkle_proof.verify(...)`, which is where garbage/duplicate/invalid signatures would actually be rejected. A submitter can pad `signatures` with a large number of syntactically-valid-but-meaningless (or duplicate) signature entries, driving the recovery loop's cost far beyond what `check_participation_threshold` intends to bound, exactly as the RSA advisory describes computation proportional to attacker-chosen input size rather than to the legitimate problem size.

This verifier is reached from the permissionless `pallet-ismp` consensus-message dispatch path used by both the direct `ismp-beefy` consensus client: [4](#0-3) 

and the `pallet-beefy-consensus-proofs::submit_proof` naive-proof path, which decodes a caller-submitted proof and routes it into the same `verify_consensus` via `handle_incoming_message`: [5](#0-4) 

Both are reachable from a single, unprivileged relayer-submitted extrinsic/consensus message — matching the "message dispatcher / relayer" reachability criteria in scope.

### Impact Explanation
An attacker who can submit a BEEFY consensus proof (any permissionless relayer) can inflate the `signatures` vector with a large number of entries. Since Substrate pallet extrinsics are weight-metered by *declared* weight, not by dynamically-measured execution time, and the loop's real cost (N `secp256k1_recover` calls) is not obviously reflected/capped by an upfront bound check, a single extrinsic can consume disproportionate CPU time relative to its charged weight. This can degrade block production / import performance for the coprocessor chain, i.e., resource exhaustion affecting message delivery for the whole bridge — the same class of impact as the OpenSSL advisory (DoS via expensive computation on attacker-controlled input), which the scope classifies as a route being made unable to deliver messages under load.

### Likelihood Explanation
Medium. The attack requires only crafting a `ConsensusMessage`/`Sp1BeefyProof`-shaped payload (or the naive ABI-encoded `BeefyConsensusProof`) with an inflated `signatures` array of syntactically well-formed 65-byte ECDSA signatures (they need not recover to real authorities — `secp256k1_recover` still performs its full computation on garbage input, and only fails to produce a *matching* authority afterward at the merkle-proof stage). No special privileges, key compromise, or governance access are required — this is exactly the "relayer submits a proof" class of transaction this scope targets. The actual severity depends on how large `signatures` can practically get (bounded only by the general extrinsic/proof size limit, not by a dedicated per-signature cap), which was not fully confirmed within the available context — I could not verify a `MaxEncodedLen`/bounded-vec constraint on `SignedCommitment.signatures` nor the exact declared extrinsic weight formula for `pallet-beefy-consensus-proofs::submit_proof`, so the precise achievable multiplier is uncertain.

### Recommendation
Add an explicit upper bound check on `signatures_length` before entering the recovery loop, tying it to the known authority-set size (e.g., reject if `signatures_length > authority_set.len`), mirroring the pattern already used elsewhere in this codebase (e.g., `MAX_PROOF_DEPTH` bound in the Pharos SPV verifier, and the BSC `validators_bit_set` beyond-length rejection) to fail fast on oversized/garbage inputs before performing the expensive per-item cryptographic work. Apply the same bound to the equivalent Solidity path in `EcdsaBeefy.verifyMmrUpdateProof`, which has the identical unbounded `sigLen` loop over `ECDSA.recover`.

### Proof of Concept
1. Construct a `ConsensusMessage` (or SP1/naive ABI proof) whose `signed_commitment.signatures` vector contains, say, 10,000–50,000 syntactically valid 65-byte ECDSA signatures (arbitrary/garbage signatures recover to arbitrary addresses; they do not need to belong to real authorities).
2. Ensure `signatures_length` satisfies `check_participation_threshold` against the claimed `authority_set.len` (trivial since only a lower bound is enforced).
3. Submit this as a `PROOF_TYPE_NAIVE` payload via `pallet-beefy-consensus-proofs::submit_proof` (or directly via the `ismp-beefy` consensus client's `verify_consensus` if independently reachable).
4. Observe that `verify_mmr_update_proof` performs `secp256k1_recover` once per submitted signature — computation scaling with the attacker-chosen array length — before failing at the subsequent `MerkleProof::verify` call, at a cost far exceeding what the declared extrinsic weight/gas budget for a legitimate BEEFY proof accounts for.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}
