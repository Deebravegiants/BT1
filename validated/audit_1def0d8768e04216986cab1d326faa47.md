### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` restricts the HMAC-verified payload to the raw HTTP body only, while `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers to identify which shop a webhook event applies to. This breaks the intended identity binding `HMAC-authenticated body == event attributed to shop X`, letting anyone who can produce (or capture) one valid `{raw_body, hmac}` pair for the app's `api_secret_key` relabel that payload as belonging to a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhook requests, `to_signable_string` returns only `@raw_body`, excluding all HTTP headers [2](#0-1) .

`Registry.process` relies solely on this HMAC check to decide the request is legitimate, then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id`, all of which are read straight from HTTP headers and are never included in the signed bytes: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are extracted from headers with no cryptographic tie to the body/HMAC: [4](#0-3) 

Because the same `api_secret_key` is shared by the app across every shop that installs it, any tenant that legitimately receives one authentic webhook (a valid `raw_body` + its HMAC, exactly as Shopify sent it to that tenant's own endpoint) possesses a `{body, hmac}` pair that will pass `HmacValidator.validate` regardless of which `shop-domain` header accompanies it. That tenant — an "unprivileged" party with respect to any other tenant's data — can replay the identical body and HMAC to the shared webhook endpoint while substituting `x-shopify-shop-domain` (and, if desired, `x-shopify-topic`/`x-shopify-webhook-id`) to name a different shop. `Registry.process` will pass the forged `shop` value straight into `WebhookMetadata`, and the handler will treat the event as if it happened on the victim's store: `assert_equal(@shop, data.shop)` in the test suite confirms `data.shop` is taken verbatim from the header, unrelated to the signed body [5](#0-4) .

This is the direct analog of the report's "insolvency settled out of loop" bug class: an operation (attributing a signed action to a shop) is decoupled from the identity check that should gate it, so the equality `verified_secret_bytes == identity_used_by_the_handler` does not hold — `hmac` verifies `body` only, but `shop` (the tenant boundary) is asserted independently of that verification.

### Impact Explanation
This crosses a tenant boundary using only the app's shared secret and data the attacker legitimately possesses for their own store — no access token or victim credential is required. It qualifies as **cross-tenant access**: an app relying on this gem's webhook dispatch (as documented in `docs/usage/webhooks.md` and exercised by `Registry.process`) can be made to process events under the wrong shop identity — enqueuing background jobs, updating records, or triggering mandatory-compliance actions (e.g. `customers/redact`, `shop/redact`) against a shop that never actually sent that event. Because merchant apps commonly key their persisted state by `data.shop`, this can lead to writing/deleting a victim shop's data based on an attacker's own store's payload, or suppressing/duplicating a mandatory compliance webhook for an arbitrary shop.

### Likelihood Explanation
High reachability: `ShopifyAPI::Webhooks::Registry.process` and `ShopifyAPI::Webhooks::Request` are the gem's documented, sole primitives for webhook verification, and the gem performs no additional binding of `shop` to the signed payload. Any app following the documented usage pattern (`docs/usage/webhooks.md`) inherits this gap. Exploitation requires only that the attacker be a legitimate (even free/trial) merchant of the target app, able to observe their own shop's webhook traffic — a low bar, and independent of `api_secret_key` secrecy or TLS interception.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified surface, or otherwise cryptographically tie the header-derived identity to the verified body, e.g. by including the `shop-domain`, `topic`, and `webhook-id` header values in `to_signable_string`, or by validating that the shop asserted in the request matches an actively-registered/expected session for that webhook before dispatch. At minimum, document that consumers must not trust `data.shop` from `WebhookMetadata` without independently confirming that the shop is one for which the app expects webhooks, and consider re-deriving shop identity from something covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and captures one authentic webhook delivery, e.g. `orders/create`, obtaining the exact `raw_body` and the accompanying `x-shopify-hmac-sha256` header (valid because it was HMAC-signed by Shopify using the app's shared `api_secret_key`).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint using the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only checks presence, not binding) [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it verifies only `raw_body` against the (unchanged) HMAC [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` [8](#0-7) , causing the app to process the attacker's own order data (or any structurally valid payload) as if it belonged to the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
