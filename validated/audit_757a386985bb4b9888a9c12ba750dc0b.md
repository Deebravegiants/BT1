### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [3](#0-2) . `Registry.process` validates only this body-only HMAC and then passes the header-derived `shop` straight to the merchant-facing handler [2](#0-1) , so the equality the gem is supposed to guarantee — "the shop that authorizes this request equals the shop the handler is told to act on" — is never actually checked.

### Finding Description
`HmacValidator.validate` computes `verifiable_query.to_signable_string` and HMAC-compares it against the `hmac` value [4](#0-3) . For OAuth's `AuthQuery`, `to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` together [5](#0-4)  — every field that is later acted upon is covered by the signature. `Webhooks::Request` breaks this pattern: its `to_signable_string` returns only `@raw_body` [1](#0-0) , but `shop`, `topic`, and `webhook_id` — the fields that determine *which tenant* the webhook is attributed to and *which handler* processes it — come from `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers that are never mixed into the signed bytes [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., the body signature) before looking up the handler for `request.topic` and constructing `WebhookMetadata` from `request.shop` [2](#0-1) . Because the secret (`api_secret_key`) is per-app, not per-shop, any valid `(body, hmac)` pair obtained from **any** shop using the app can be replayed with `shop-domain` and `topic` headers swapped to arbitrary values, and the HMAC check still passes. The host app's handler — following the gem's own documented pattern of trusting `data.shop` to route/attribute data (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5)  — then processes attacker-controlled body content under a victim shop's identity.

### Impact Explanation
This breaks the tenant-authentication binding the gem is expected to provide: "the shop asserted by the verified request equals the shop the signature actually authenticates." An unprivileged internet user who legitimately installs the same app on their own store (a normal, unprivileged action) receives a genuine webhook delivery with a valid HMAC over a body they control the shape of. They can replay that request directly to the app's public webhook endpoint with the `shopify-shop-domain` header changed to point at a different, victim shop and `shopify-topic` changed to whichever registered topic they want to trigger. The gem passes this through to the app's handler as if it were an authentic webhook for the victim shop, causing cross-tenant data confusion in any app whose handler trusts `data.shop`/`data.topic`/`data.body` together — matching the report's underlying bug class of "checks that bind an identity are looser than the actions actually gated by them."

### Likelihood Explanation
Requires only the ability to install the app as an ordinary merchant (or otherwise obtain one legitimate webhook delivery) and the ability to POST directly to the app's public webhook route with modified headers — both are unprivileged-internet-user actions, with no access token, `api_secret_key`, or leaked credential needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content for `Webhooks::Request` (or otherwise cryptographically bind them to the raw body), so `HmacValidator.validate` fails if any of these header-derived identity fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for topic `orders/create`.
2. Shopify delivers a webhook to the app's callback URL with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and some JSON body.
3. Attacker resends the exact same body and HMAC header to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#shop` returns `"victim.myshopify.com"` [7](#0-6) ; `HmacValidator.validate` still passes because it only checks the untouched body bytes [8](#0-7) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [9](#0-8) , causing the app to process attacker-supplied content as authentic data for the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
