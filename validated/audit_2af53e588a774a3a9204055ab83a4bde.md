### Title
Emporium's ERC20-only balance accounting lets any unprivileged CASE 2 op steal ERC721/non-ERC20 state (e.g., LP position NFTs) left stranded on the shared Emporium contract - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` performs completely unrestricted low-level calls in "CASE 2" (`stack.invokeWallet=false`/`stack.signerAddress=0`), with `op.endpoint.call{value: op.value}(op.callData)` executed with `Emporium` itself as `msg.sender`. The only post-call accounting performed is an ERC20 balance diff over `circomData.erc20TokenAddresses`; any non-ERC20 asset (e.g. an ERC721 LP position) that ends up owned by `Emporium` through one user's op is never captured into a UTXO and is left "stranded" at the Emporium contract, with zero access control tying it to the depositing user.

### Finding Description
The claimed broken equality is: `owner(tokenId)` after a victim's mint-to-`msg.sender` op should equal `victim.stealthAddressStructure` (i.e., be represented as a UTXO the victim shielded-controls), but instead `owner(tokenId) == address(Emporium)` and stays that way indefinitely, because:

- `runAction` only snapshots/diffs balances for `circomData.erc20TokenAddresses`: [1](#0-0)  and [2](#0-1) . An ERC721 `ownerOf`/`tokenId` is never part of this array or loop, so a mint to `Emporium` produces no UTXO and no on-chain record tying it to the victim.
- CASE 2 execution is a fully unrestricted low-level call from `Emporium` with no endpoint whitelist and no restriction on `op.callData` beyond blocking the two `IHinkalWallet` selectors: [3](#0-2) .
- `verifyWallet` (called before the ops loop) does nothing when `stack.signerAddress == address(0)`, other than marking `emporiumMessage` used — it does not tie the op set to any prior state or to the depositor of any stranded asset: [4](#0-3) .
- `onlyAllowedRecipient` only restricts `msg.sender` of `runAction` to be the `Hinkal` contract itself (or another registered allowed recipient) — it is not per-user or per-position: [5](#0-4) .
- `Hinkal.transact` / `_externalTransact` only requires that `circomData.externalActionData.externalAddress` match a registered `externalActionMap` entry and that the attacker's own proof and calldata-hash checks pass; none of these checks relate calldata content to any previous transaction's stranded assets: [6](#0-5) , [7](#0-6) .

Exploit flow: victim calls `transact()` with a CASE 2 op whose `callData` mints an ERC721 position to `msg.sender` (i.e., `Emporium`, since the call executes with `Emporium` as caller). Because `erc20TokenAddresses`/balance-diff logic never references the NFT, the mint is entirely invisible to Emporium's accounting and produces no UTXO for the victim - the NFT is simply left owned by `Emporium`. The attacker, with no special privilege, submits their own `transact()` (using their own valid proof/UTXOs and an independent `emporiumMessage`) with a CASE 2 op calling `transferFrom(Emporium, attacker, tokenId)` on the same endpoint. Because that call doesn't touch any `erc20TokenAddresses` balance, the balance-diff invariant is trivially satisfied (net change 0), the call succeeds, and `ownerOf(tokenId)` flips to the attacker.

### Impact Explanation
This allows direct theft of a victim's in-flight/finalized non-ERC20 asset (e.g., a Uniswap-V3-style LP position NFT) that was legitimately created through a valid, victim-authorized Hinkal transaction but is left custodied by the shared `Emporium` contract with no ownership binding. Any unprivileged attacker who can observe the endpoint address and `tokenId` (both public on-chain after the victim's mint) can redirect it to themselves in a fully independent transaction requiring only their own proof/UTXOs. This is repeatable for every non-ERC20 asset any user (or the protocol design) ever routes into Emporium via CASE 2. This qualifies as Critical: direct theft of a victim's shielded/in-flight funds through the Hinkal-authorized action path.

### Likelihood Explanation
Preconditions: (1) some usage of Emporium's CASE 2 stateless mode that ends with `Emporium` holding a non-ERC20 asset (e.g., interacting with any ERC721-minting protocol, real or attacker-deployed, through Emporium) and (2) the resulting `tokenId`/endpoint being discoverable on-chain (trivial, since the victim's mint tx and any subsequent transfer events are public). Attacker cost is a single `transact()` call with their own funds/proof - no special role, no race condition needed beyond ordering their tx after the victim's. This is highly feasible and repeatable against every future occurrence of the pattern.

### Recommendation
Do not allow CASE 2 (or any Emporium mode) to leave arbitrary non-accounted assets owned by the shared `Emporium` contract. Options: (1) extend Emporium's post-call reconciliation to explicitly account for and mint UTXOs for any declared non-ERC20 assets (e.g., accept an `erc721Tokens`/`tokenId` list in `CircomData`/metadata and verify ownership transfer into a UTXO analogous to the ERC20 balance diff), or (2) require CASE 2 ops that can result in asset custody to immediately forward the asset out of `Emporium` to the caller/stealth address within the same call sequence, with an explicit ownership check (`ownerOf(tokenId) == attacker.stealthAddress` or reverts), or (3) restrict `op.endpoint` to a whitelist of vetted, Emporium-aware adapters that guarantee no assets are left custodied by `Emporium` between transactions.

### Proof of Concept
Foundry fork/unit test:
1. Deploy a minimal ERC721 mock with `mint(address to) returns (uint256 tokenId)` and standard `transferFrom`.
2. Register the mock as an allowed CASE 2 endpoint target is unnecessary (no whitelist exists) - just note its address.
3. Victim: submit `Hinkal.transact()` with a valid Groth16 proof and `circomData.externalActionData` pointing at `Emporium`, `externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [ { endpoint: mockNFT, invokeWallet: false, value: 0, callData: abi.encodeCall(mockNFT.mint, (address(this))) } ] }`. Assert after the tx: `mockNFT.ownerOf(tokenId) == address(Emporium)` and that the victim's returned `utxoSet` contains no entry referencing the NFT (only ERC20 UTXOs, if any).
4. Attacker: submit an independent `Hinkal.transact()` with attacker's own valid proof/UTXOs, `externalActionMetadata` = `EmporiumStack{ signerAddress: address(0), ops: [ { endpoint: mockNFT, invokeWallet:false, value:0, callData: abi.encodeCall(mockNFT.transferFrom, (address(Emporium), attacker, tokenId)) } ] }`.
5. Assert the equality flips: before attacker tx `ownerOf(tokenId) == address(Emporium)`; after attacker tx `ownerOf(tokenId) == attacker`, proving the victim's asset was diverted with no corresponding authorization, nullifier, or UTXO ever referencing `tokenId`.
