### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an incoming webhook purely by validating an HMAC over the raw request body, then forwards the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers to the host application's handler. Because these header fields are never included in the signed payload, an attacker who owns a legitimate, HMAC-signed webhook for *their own* shop (same app, same shared `client_secret`) can replay that valid body+HMAC pair while forging the `x-shopify-shop-domain` (and/or `topic`/`webhook-id`) headers to impersonate a different, victim tenant.

### Finding Description
Webhook validation flows through `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` to build the string that is HMAC-verified: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw HTTP body — none of the Shopify headers are part of the signed material: [2](#0-1) 

Yet `shop`, `topic`, and `webhook_id` — all read straight from attacker-controllable HTTP headers — are exactly the fields used to route and attribute the webhook: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the HMAC (over the body) and then hands the header-derived `shop`/`topic`/`webhook_id` straight to the registered handler as trusted tenant identity, with no cross-check that these headers correspond to the shop/topic the HMAC was actually generated for: [5](#0-4) 

The identity binding that should hold is: `shop header used by handler == shop the HMAC signature was actually computed for`. Since the HMAC only signs the body, this equality is never enforced — `shop` (and `topic`/`webhook_id`) are "fields acted on but not covered by the HMAC."

By contrast, the OAuth callback verification (`AuthQuery#to_signable_string`) does bind `shop` into the signed content, so an attacker cannot forge the shop for OAuth callbacks: [6](#0-5) 
This asymmetry highlights that the webhook path is missing an equivalent binding.

**Exploit path:** An attacker who has installed the same app on their own (attacker-controlled) development store receives legitimate webhooks from Shopify for that store, each with a body and a valid `x-shopify-hmac-sha256` signature computed with the app's shared `client_secret` (the same secret is used for every shop that installs the app — this is normal Shopify behavior, not a leaked secret). The attacker can then resend that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`/`x-shopify-webhook-id`). `HmacValidator.validate` still succeeds because it only checks the body against the HMAC, and `Registry.process` will invoke the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from, and was HMAC-signed for, the attacker's own store.

### Impact Explanation
This breaks the tenant/shop identity binding of an authenticated webhook without requiring the app's `client_secret`, `access token`, or any privileged credential — only participation as a normal merchant/installer of the target app (a capability any unprivileged internet user can obtain by installing a public app on a free dev store). Depending on how the host application's `WebhookHandler#handle` uses `data.shop` (e.g., updating shop-scoped state, triggering `shop/redact` or `customers/redact` mandatory compliance webhooks, invalidating sessions, or writing to a datastore keyed by shop), this can result in cross-tenant data corruption or an attacker being able to trigger shop-scoped side effects attributed to a victim shop they do not control. This matches the "cross-tenant access" criterion in scope.

### Likelihood Explanation
High: no secret, session, or elevated privilege is required — an attacker merely installs the public app (or reuses a webhook from their own installation) and replays the body/HMAC pair with forged headers. The vulnerability is exploitable by any unprivileged, unauthenticated actor able to reach the app's webhook endpoint.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the signature (e.g., sign `shop|topic|webhook_id|body` instead of `body` alone) in `Webhooks::Request#to_signable_string`, so `HmacValidator.validate` cannot succeed if any of those header values have been altered relative to what Shopify actually signed.

### Proof of Concept
1. App developer's own dev store `attacker-shop.myshopify.com` has the app installed; Shopify sends a legitimate webhook:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: abcd-1234
   Body: {"id": 1, ...}
   ```
2. Attacker captures this request and resends it to the same endpoint, unmodified except:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `Webhooks::Request.new` parses headers/body normally (`request.rb` lines 45-63). `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged body) — validation passes because the body wasn't modified (`registry.rb` line 190, `request.rb` lines 35-38).
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ..., ...)`, causing the host app to process/attribute this webhook as if it came from the victim shop (`registry.rb` lines 198-199).

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
