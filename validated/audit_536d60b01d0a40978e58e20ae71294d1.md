### Title
`PoaBridge.describeWithdrawal` matches withdrawals by `assetId` only, misreporting status/txHash for batched same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` intentionally ignores the `index` field of the `WithdrawalIdentifier` and instead resolves the correct withdrawal record from the PoA relayer's (unsorted) response list purely by matching `withdrawalParams.assetId`. [1](#0-0)  When the SDK batches multiple withdrawals in the same intent transaction that share the same `assetId` (e.g. two withdrawals of the same token to two different destination addresses), this lookup can return the wrong withdrawal record for one of the calls, causing the SDK to report a completion status/tx hash that does not correspond to the withdrawal actually being polled.

### Finding Description
`createWithdrawalIdentifiers` assigns a per-bridge `index` to every withdrawal in a batch so each one can be tracked independently: [2](#0-1)  and `createWithdrawalCompletionPromises` maps this index-per-withdrawal to independent polling promises. [3](#0-2) 

For the PoA bridge, `describeWithdrawal` explicitly discards `index` "because the response list is unsorted" and instead matches solely on `assetId`: [1](#0-0)  If two withdrawals in the same NEAR intent transaction withdraw the same `assetId` (a supported scenario — batch withdrawals with `withdrawalParams: WithdrawalParams[]`), both index-0 and index-1 calls into `describeWithdrawal` resolve to `findMatchingWithdrawal` with the identical `assetId` argument. Since the underlying relayer response order is unspecified/unsorted, the function has no way to disambiguate which of the two same-asset withdrawal records belongs to which requested `index`/`destinationAddress` — it will return the same record (or the wrong one) for both polling calls.

This breaks the equality that the reported `status`/`txHash` for a given withdrawal index/destination corresponds to the actual on-chain outcome for that specific withdrawal — the same defect class as the reported bug, where a shared/ambiguous piece of UI or state (there: the sidebar's single top-of-stack layer; here: assetId-only lookup key) causes one action's confirmation/result to be attributed to a different action.

### Impact Explanation
If an integrator uses `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` to track completion per withdrawal (as documented) and one withdrawal's `txHash` is misreported as another's, the integrator could mark the wrong destination address's withdrawal as completed (crediting/confirming based on a transaction hash that actually belongs to a different destination), or resolve two independent withdrawal promises with the same `txHash`/status, potentially causing a double credit or a stuck/undetected pending withdrawal for the other address. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Requires the caller to submit a batch withdrawal (`withdrawalParams: WithdrawalParams[]`) containing two or more entries with the same `assetId` routed through the PoA bridge — a legitimate, unprivileged usage pattern (e.g., splitting one token withdrawal to multiple destination addresses), not requiring any malicious actor. The relayer's own comment ("Response list is unsorted") confirms ordering cannot be relied upon, making collision realistic whenever same-asset batches occur.

### Recommendation
Disambiguate `findMatchingWithdrawal` using more than `assetId` — include `destinationAddress` and/or `amount`, and only fall back to positional/index matching once assetId+address+amount uniquely identify the withdrawal record; if uniqueness cannot be established, return `pending` rather than an arbitrary match.

### Proof of Concept
1. Submit a NEAR intents transaction withdrawing the same `assetId` (e.g. `nep141:usdc.omft.near`) twice, to two different destination addresses (`addrA`, `addrB`), via `sdk.processWithdrawal`/`createWithdrawalCompletionPromises` with `withdrawalParams: [{assetId, destinationAddress: addrA, ...}, {assetId, destinationAddress: addrB, ...}]`.
2. The PoA relayer's `getWithdrawalStatus` response contains both withdrawal records with `defuse_asset_identifier` equal for both, differing only in `address`/`transfer_tx_hash`.
3. `findMatchingWithdrawal(response.withdrawals, assetId)` for index 0 and index 1 calls resolves the same (or wrong) record, as demonstrated by `poa-bridge.test.ts`'s explicit "matches withdrawal by assetId, not by index" test which only validates disjoint assetIds — no test covers the same-assetId, multi-destination batch case. [4](#0-3) 
4. The integrator observes `promises[1]` resolving with the `txHash` that actually belongs to `addrA`'s withdrawal, incorrectly treating `addrB`'s withdrawal as completed.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
