This confirms the vulnerability. The `shop` field delivered to `WebhookMetadata` (and used by any host app as the tenant key, per the documented usage pattern `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while `Utils::HmacValidator.validate` only signs `request.to_signable_string`, which is defined as the raw body alone.### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against Shopify's HMAC, but the tenant-identifying `shop` value that is handed to the app's handler is read from an HTTP header that is never covered by that signature. This breaks the identity binding: **shop verified by HMAC (the body) ≠ shop trusted by the handler (the header)**.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, and for webhooks that method returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Registry.process` uses this HMAC check purely as a gate, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all of which are parsed straight out of unauthenticated HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) — to build the `WebhookMetadata` that is handed to the developer's handler: [3](#0-2) [4](#0-3) 

The gem's own documentation instructs developers to key their business logic (job enqueueing, tenant lookups, per-shop data mutation) directly off `data.shop`: [5](#0-4) 

Because `shop-domain` is not part of the signed content, any party capable of producing one validly-HMAC'd `(body, hmac)` pair for a topic they control (e.g., their own app installation, which routinely receives real, Shopify-signed webhooks for topics like `orders/create`, `app/uninstalled`, `customers/redact`, `shop/redact`) can replay that same body+hmac to the app's webhook endpoint while swapping the `shop-domain` header to name an arbitrary victim shop. `Registry.process` will pass HMAC validation (since the body is unchanged and still signed correctly by Shopify) and will then dispatch to the handler with `shop` set to the attacker-chosen value, impersonating another merchant. This equality that should hold — "shop bound by the cryptographic signature" == "shop the handler acts on" — is violated.

### Impact Explanation
This crosses a tenant boundary: it lets an attacker who is a legitimate (even low-privilege) app/shop owner forge webhook events attributed to a different shop. Depending on how the host application implements its handler (which the gem explicitly encourages to key off `data.shop`), this can cause cross-tenant data corruption/injection, spoofed GDPR-mandated erasure (`customers/redact`, `shop/redact`) against a victim's data, or spoofed `app/uninstalled` events that wipe/deactivate another merchant's app state. This matches the "cross-tenant access" class of Critical impact called out in scope.

### Likelihood Explanation
Any developer using this gem's documented API is affected, because the vulnerability lives in the gem's own `Request`/`Registry` classes, not in host-application misuse. The prerequisite — possessing one topic's raw body + its real HMAC — is trivially satisfied by any actor who has an app installed on any shop and therefore receives genuine Shopify-signed webhooks for that shop; no access token, API secret, or privileged credential is required to mount the replay against a different target shop.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header value into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the header-derived shop to the payload before it is passed to `WebhookHandler#handle`. At minimum, `to_signable_string` for `Webhooks::Request` should incorporate the shop domain header so that an attacker cannot swap it without invalidating the HMAC.

### Proof of Concept
1. Install a test app on `attacker-shop.myshopify.com` and receive a genuine webhook for `customers/redact` (or any subscribed topic), capturing the raw body `B` and its valid header `x-shopify-hmac-sha256: H` (H is a correct HMAC of `B` under the app's `client_secret`, computed by Shopify).
2. Send a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, `x-shopify-topic: customers/redact` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) and matches `H`, so validation passes: [6](#0-5) 
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the host app's handler executes tenant-scoped logic (e.g., data redaction, cache invalidation, job dispatch) against the victim shop, as encouraged by the gem's docs.
