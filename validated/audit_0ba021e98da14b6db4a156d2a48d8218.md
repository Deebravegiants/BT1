## Title
Webhook shop/topic/webhook-id are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the shop, topic, and webhook-id used to route and process the webhook are taken from unauthenticated HTTP headers. Any party able to obtain one validly-signed webhook body for the app (e.g., by installing the app on their own store and triggering an event) can replay that body with forged `shop-domain`/`topic` headers to make the app process it as if it came from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` only checks that `HMAC(api_secret_key, raw_body)` matches the `hmac` header — it never touches `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` trusts the request's HMAC validity as proof of authenticity for the whole request, then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

Because the app's `api_secret_key` (its client secret) is the same value used to sign webhooks for *every* shop that has the app installed, and the HMAC only binds the body bytes — not the shop identity — the equality that should hold is:

`shop asserted by the HMAC-covered payload == shop used by the host application to attribute/process the webhook`

but the actual binding is only:

`bytes verified (raw_body) == bytes signed (raw_body)`, with `shop`/`topic`/`webhook_id` taken from headers that are never authenticated.

An unprivileged user who installs the app on their own development/test store can trigger events (e.g., `orders/create`, `products/update`) whose body content they substantially control (titles, custom fields, etc.), and receive a validly HMAC-signed webhook for that body. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop domain. Since `HmacValidator.validate` and `Request#to_signable_string` never verify the shop header is bound to the signature, the request passes validation and is dispatched to the handler as if it genuinely originated from the victim shop, along with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem's webhook processing lets an attacker who controls one tenant (their own shop) forge webhook events attributed to another tenant, with body content and topic partially attacker-controlled. Applications built on this gem typically use `WebhookMetadata#shop` to look up/modify shop-scoped records, making this a cross-tenant data integrity/spoofing issue meeting the "cross-tenant access" bar.

### Likelihood Explanation
Any developer/merchant can freely install a Shopify app on a store they control and trigger events to obtain a validly signed webhook body; no privileged access, leaked secrets, or the app's `client_secret` are required. The forged header injection only requires the ability to send an arbitrary HTTP request to the app's public webhook endpoint (a POST with custom headers), which is trivial for an unprivileged internet user.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the payload (e.g., verify the shop domain against a value derived from data inside the signed body, or require the host app to independently confirm that the shop has this webhook/topic actively registered before trusting `request.shop`). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be used for tenant attribution without an additional check.

### Proof of Concept
1. Install the app (as any user) on `attacker.myshopify.com`; trigger an event (e.g., update a product) so Shopify sends a real webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture `B` and its valid HMAC.
3. Send a new POST request to the app's webhook endpoint with the same body `B` and same HMAC header, but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` (via `Request#to_signable_string`, which is just `@raw_body`) succeeds because only `B` is signed. [5](#0-4) 
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim.myshopify.com"` — a value never covered by the HMAC — causing the host application to process attacker-controlled data as if it came from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
