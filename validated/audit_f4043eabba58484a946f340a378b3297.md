### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` fields are trusted by the app without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates an incoming webhook by checking an HMAC signature, and the docs claim this "will verify the request did indeed come from Shopify." However, the HMAC is computed only over the raw request body, while the `shop`, `topic`, `webhook-id`, and `api-version` values are read from unauthenticated HTTP headers and passed straight through to the app's handler as trusted identifiers. Any party capable of obtaining one valid `(body, hmac)` pair — for example a merchant receiving legitimate webhooks for their own store — can replay that exact body/signature pair with a forged `X-Shopify-Shop-Domain` header, causing the host application to attribute the webhook to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) .

`Registry.process` validates only this body-only HMAC via `Utils::HmacValidator.validate(request)`, then immediately constructs `WebhookMetadata` using the unverified header-derived `request.shop`, `request.topic`, and `request.webhook_id`, and dispatches it to the app's handler: [3](#0-2) .

`HmacValidator.validate` itself only computes `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` — i.e., only the JSON body is hashed with the shared `api_secret_key`; the shop domain never enters the signed material: [4](#0-3) .

The `WebhookMetadata` struct explicitly carries `shop` as an attribute that handlers are told to trust: [5](#0-4) . The gem's own documentation instructs developers to key their side effects off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), and states the `process` call itself "will verify the request did indeed come from Shopify," implying `shop` is authenticated: [6](#0-5) , [7](#0-6) .

The broken identity binding is:
`hmac_verified_bytes == raw_body` — proven — but the gem (and, per its own docs, downstream apps) treat this as if `hmac_verified_shop == request.shop`, which does **not** hold, because `shop` was never part of the signed data.

### Impact Explanation
Because the shared `api_secret_key` is identical across all shops installed on a multi-tenant app, a valid `(body, hmac)` pair generated for one shop's legitimate webhook is equally valid for any other shop header value paired with the same body. A malicious but otherwise unprivileged merchant who has installed the app can capture a real webhook body+signature sent to their own registered endpoint (trivial — they operate the receiving server) and replay the identical bytes with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to a victim shop's domain. `Registry.process` will accept it as validly signed and hand `WebhookMetadata` with the spoofed `shop` to the app's handler, which — per the gem's documented pattern — uses that value to attribute data/actions to a tenant. This enables cross-tenant data injection/corruption (e.g., another shop's order/product data appearing to belong to, or triggering actions for, the victim shop), which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant with the app installed on their own store (no `api_secret_key`, access token, or privileged access required) — they merely intercept/replay their own inbound webhook traffic with a modified header, which any HTTP client can do since headers are entirely attacker-controlled once they proxy or reconstruct the request to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before constructing `WebhookMetadata`. At minimum, cross-check `request.shop` against an expected/registered shop associated with the specific webhook subscription (Shopify's webhook payload includes shop identifiers in the JSON body for many topics) rather than trusting the raw header value outright.

### Proof of Concept
1. App merchant "Attacker Shop" (`attacker.myshopify.com`) installs the vulnerable multi-tenant app and receives a legitimate webhook, e.g.:
```
POST /callback/orders/create HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid-hmac-over-body>
X-Shopify-Shop-Domain: attacker.myshopify.com
Content-Type: application/json

{"id":1,"note":"hello"}
```
2. Attacker captures this exact body and HMAC value (they control the receiving endpoint).
3. Attacker resends the identical body and HMAC to the same endpoint, only changing the shop header:
```
POST /callback/orders/create HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <same-valid-hmac-over-same-body>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
Content-Type: application/json

{"id":1,"note":"hello"}
```
4. `HmacValidator.validate` recomputes the HMAC over the identical body and it matches (`lib/shopify_api/utils/hmac_validator.rb:26-40`), so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though `victim-shop.myshopify.com` never sent this webhook.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
