### Title
Webhook shop-domain identity spoofing via unsigned header (HMAC binds only body, not shop) - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as the raw request body only [1](#0-0) . The `shop` (tenant identity), `topic`, and `webhook_id` fields consumed by `Registry.process` are read straight from HTTP headers that are never included in that signable string [2](#0-1) . Because Shopify apps share a single `api_secret_key` across all shops that install the app, any shop that legitimately receives one authentic webhook (with a valid HMAC over some body) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different shop, and the library will accept it as validly signed and dispatch it as if it came from the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is simply `@raw_body`, and the HMAC therefore authenticates only the byte content of the body, not which shop or topic it was delivered for [1](#0-0) . `Registry.process` raises only if `Utils::HmacValidator.validate(request)` fails [5](#0-4) , then looks up the handler by `request.topic` and calls it with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` — both taken from unauthenticated headers [6](#0-5) .

This breaks the intended identity binding: `hmac == HMAC(secret, body)` is verified, but the consuming code treats it as if `hmac` also authenticates `shop == request.shop`. Since the `api_secret_key` is shared across every shop that has installed a given app (it is not shop-specific), any tenant of a multi-tenant app can obtain one genuine webhook delivery for their own store (any topic that produces a body they can predict or capture, e.g. `app/uninstalled` or an order webhook with attacker-controlled content sent to their own shop) and then forge new deliveries to the app's webhook endpoint with the same body+hmac but an arbitrary `X-Shopify-Shop-Domain` header value, causing the host application's handler to process attacker-supplied data as though it came from a victim shop.

### Impact Explanation
This is a cross-tenant data/identity confusion: the shop identity used by the application's webhook handler is not actually covered by the cryptographic proof the library performs, letting one tenant impersonate another tenant's webhook traffic. This matches the "Critical – cross-tenant access" category, since a handler that keys its behavior or data writes on `WebhookMetadata#shop` (as the library's own API encourages, per `WebhookMetadata.new(topic: ..., shop: request.shop, ...)`) can be tricked into acting on behalf of, or writing data attributed to, a shop the attacker does not control.

### Likelihood Explanation
Exploitation only requires that the attacker be a legitimate (even free/trial) installer of the target app on their own store — an "unprivileged internet user" relative to other tenants — and be able to capture one webhook payload+HMAC pair delivered to their own endpoint (which the app necessarily sends them as part of normal webhook delivery). No access to the `api_secret_key` itself is needed; the attacker reuses a signature Shopify already computed for them.

### Recommendation
Include the shop domain (and topic/webhook id, as appropriate) in the signed material that `to_signable_string` protects, or otherwise cryptographically bind the header-derived `shop` to the verified body (e.g., require the host app validate that `request.shop` matches an expected/installed shop associated with the delivery, and reject unknown shops before dispatch). At minimum, document and enforce that `Registry.process` must not trust `request.shop`/`request.topic` unless they are cross-checked against the app's own installed-shop registry.

### Proof of Concept
1. App has two shops installed: `victim.myshopify.com` and `attacker.myshopify.com`, both share the same app `api_secret_key`.
2. Shopify delivers a legitimate webhook to the app for `attacker.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
3. Attacker (who controls their own network egress / can intercept their own webhook deliveries) resends `POST /webhooks` with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses `shop` as `victim.myshopify.com` [7](#0-6) .
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H` [8](#0-7) .
6. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host application processes attacker-controlled data as if it originated from the victim shop [3](#0-2) .
