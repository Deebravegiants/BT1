### Title
Phantom Fraud-Detection Function Silently Bypasses Fraud Enforcement - (File: src/plans/mod.rs)

### Summary
`MasterPlan::detect_fraud` in [1](#0-0)  is invoked during every signup as the authoritative fraud-check gate, but its body has been permanently gutted (`// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`) and it unconditionally returns `Ok(false)`. This mirrors the reported bug class: a function that outwardly presents itself as performing a security-relevant check (like `permit`), but is in fact a no-op that neither reverts nor signals its own inapplicability, silently returning a "safe" result regardless of input.

### Finding Description
The signup pipeline calls `detect_fraud` and treats its boolean return value as the ground truth for whether a signup is fraudulent: [2](#0-1) 

Internally, `detect_fraud` sets the phase to `"Fraud detection"`, unwraps the pipeline, and then—instead of running any check—drops straight to `Ok(false)`: [3](#0-2) 

The supporting `fraud_check` module corroborates that all real checks were stripped: `N_FRAUD_CHECKS` is hardcoded to `0` and every check array (`fraud_checks`, `enabled_checks_from_config`, `feedback_messages`) returns empty arrays, so `Report::fraud_detected()`/`fraud_detected_with_config()` can never report fraud either: [4](#0-3) [5](#0-4) 

Unlike the reported pattern's suggested fix (explicitly reverting/erroring when an unsupported operation is invoked), this code path performs no explicit signal that fraud checking is inert. It behaves exactly like calling a phantom `permit()` on an asset that doesn't support it: the call succeeds, returns a value that looks legitimate (`false` = "no fraud"), and callers proceed as if a genuine security check was performed.

### Impact Explanation
Because `fraud_detected` is unconditionally `false`, the `signup_reason` computed in `do_signup` can never become `SignupReason::Fraud` through this path [6](#0-5) , meaning liveness/fraud enforcement is not actually enforced by orb-core itself. Any deployment relying on this code as-is for local fraud enforcement (as opposed to purely backend-side detection) would accept signups that should have been flagged as fraudulent, directly matching the "fraud/liveness bypass" impact criteria.

### Likelihood Explanation
This is not conditional on attacker behavior—it triggers on every single signup, unconditionally, since there is no code path in `detect_fraud` that can return `true`. The only mitigating factor is that `SignupReason::Fraud` might also be set elsewhere (e.g., backend-side checks in `signup_post`/`signup_poll`), but the local orb-side check is completely inert.

### Recommendation
If this behavior is intentional for the open-source release (real fraud logic being proprietary/closed-source), this should be explicitly and loudly signaled at the type/API level rather than silently returning `false`—e.g., by having `detect_fraud` return an explicit `Unimplemented`/`NotSupported` variant that forces callers to make a deliberate decision (fail-closed) rather than silently treating "no fraud logic available" the same as "no fraud detected." This directly parallels the recommendation from the reported issue: unsupported/phantom operations should fail loudly and explicitly rather than silently returning a benign-looking result.

### Proof of Concept
1. Trigger any signup flow that reaches `do_signup` in [7](#0-6) .
2. Regardless of the biometric pipeline output, `self.detect_fraud(...)` at [3](#0-2)  returns `Ok(false)` unconditionally.
3. `signup_reason` is therefore never `SignupReason::Fraud` via this local check, and enrollment proceeds as `SignupReason::Normal` even for signups that should be flagged, confirming the fraud-check gate is a phantom no-op.
