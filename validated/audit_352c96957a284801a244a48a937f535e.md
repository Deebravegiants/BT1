The core finding: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, meaning the HMAC computed by `HmacValidator.validate` authenticates the body bytes but never binds `shop` or `topic` (both taken verbatim from unauthenticated request headers) to that signature.### Title
`Utils::HmacValidator.validate` authenticates only the webhook body, letting an attacker relabel `shop`/`topic` headers on a genuinely-signed webhook and have it accepted as if it belonged to any shop/topic — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`HmacValidator.validate` proves that the *body bytes* were HMAC-signed with the app's secret; it never proves which shop or which topic that signature was issued for. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` and `topic` come straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` trusts `request.topic` to select the handler and forwards `request.shop` straight into `WebhookMetadata` as the authenticated shop identity [3](#0-2) , after only checking `Utils::HmacValidator.validate(request)` [4](#0-3) .

### Finding Description
The broken binding: the audit assumes `HMAC_valid(body, secret) == true` implies `shop_header == signed_shop AND topic_header == signed_topic`. In this codebase that equality does not hold, because the signable string for webhooks is body-only: [1](#0-0) 

`HmacValidator.validate` (shared arbiter for both OAuth callback and webhooks) simply recomputes `HMAC(secret, verifiable_query.to_signable_string)` and compares to the supplied `hmac` header [5](#0-4) . For `Webhooks::Request`, `to_signable_string` never includes `shop-domain` or `topic`, so those two header values are completely outside the signature's scope, while `hmac` itself is read from `shopify-hmac-sha256` [6](#0-5) .

Attack flow (no secrets required, single "single identity" invariant broken):
1. Attacker creates their own development shop, installs the app, and lets it register a webhook — Shopify legitimately delivers a webhook body `B` with a valid `X-Shopify-Hmac-SHA256` signed with the app's shared `api_secret_key` (same secret across *every* installing shop).
2. Attacker replays `B` and its unchanged HMAC to the app's webhook endpoint, but swaps `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` and/or `X-Shopify-Topic` to a different registered topic.
3. `HmacValidator.validate` recomputes the HMAC over `B` only — it matches, because `shop`/`topic` were never part of the signed content.
4. `Registry.process` dispatches based on the attacker-controlled `topic`, and constructs `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-controlled `shop` value [7](#0-6) , handing the host application's handler a forged, "authenticated-looking" `(shop, topic, body)` triple that Shopify never actually issued for that shop/topic combination.

None of the existing guards catch this: `HmacValidator.validate` only checks body integrity [8](#0-7) ; there is no separate check anywhere in `Registry.process` that the signed content is bound to the `shop`/`topic` headers [9](#0-8) . (Note: for the **OAuth callback** path, `AuthQuery#to_signable_string` *does* include `shop`, `state`, `code`, `host`, `timestamp` in the signed string [10](#0-9) , so the shop identity in OAuth callback flow *is* cryptographically bound — the divergence is specific to the webhook path, not the OAuth path or the `old_api_secret_key` fallback window itself, which behaves as documented key-rotation logic and does not by itself introduce a new forgery primitive.)

### Impact Explanation
This matches the listed Critical category "authentication bypass (forged webhook … accepted)": an unprivileged attacker who legitimately installs the app on their own store can forge webhook deliveries that `Registry.process` accepts as authentic for an **arbitrary shop domain and arbitrary registered topic**, since `HmacValidator.validate` never binds those fields to the signature. Any host application relying on `WebhookMetadata#shop`/`#topic` as authenticated (e.g., to select which merchant's data/session to update, or to react to lifecycle events like uninstall/redact) can be manipulated across tenants — the impact is bounded by what the host app does with `shop`/`topic`, but the gem itself hands the host app values it should never trust as authenticated. This is repeatable against arbitrary victim shop domains at will (the attacker just changes a header string), with no rate limiting inherent in the check.

### Likelihood Explanation
Preconditions: attacker needs only a legitimate install of the target app on their own (even free development) shop to receive at least one genuinely-signed webhook body/HMAC pair, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (a documented, always-exposed entrypoint). No secrets, tokens, or privileged access needed. Cost is minimal and the technique is trivially repeatable for any topic the app has registered and any target shop domain string.

### Recommendation
Bind `shop` and `topic` into the webhook signable string (or otherwise verify them against Shopify's authenticated source) instead of using only `@raw_body` in `Webhooks::Request#to_signable_string`; at minimum, `Registry.process` should independently validate that the `shop-domain`/`topic` headers match values obtained from an authenticated channel (e.g., a corresponding registered/expected topic set per delivery, or verifying against Shopify's published webhook payload schema) before constructing `WebhookMetadata`.

### Proof of Concept
Minitest + WebMock plan (extending `test/webhooks/registry_test.rb`):
```ruby
def test_hmac_valid_but_shop_and_topic_are_forged
  real_body = "{\"id\":1}"
  real_hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, real_body)
  )

  forged_headers = {
    "x-shopify-topic" => "shop/redact",              # topic attacker did not actually receive
    "x-shopify-hmac-sha256" => real_hmac,             # untouched, valid HMAC over real_body
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # shop attacker never controls
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)

  # Binding under test: HMAC-valid  =>  shop/topic authenticated
  assert(ShopifyAPI::Utils::HmacValidator.validate(request))       # passes: HMAC check succeeds
  assert_equal("victim-shop.myshopify.com", request.shop)          # unauthenticated value accepted as shop identity
  assert_equal("shop/redact", request.topic)                       # unauthenticated value accepted as topic identity
end
```
This demonstrates that `HmacValidator.validate` returns `true` for a `(body, shop, topic)` triple that Shopify never jointly signed, confirming the broken binding.
