### Title
Webhook `shop` (and topic/api_version/webhook_id) identity fields are not covered by the HMAC signature, allowing cross-tenant spoofing via header substitution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over the body alone. The `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's webhook handler come exclusively from unsigned HTTP headers, so any body+HMAC pair produced with a legitimate `client_secret` can be replayed with an arbitrary `shop-domain` header and still pass validation.

### Finding Description
`Registry.process` treats a webhook request as authentic for a given shop purely because the raw body's HMAC matches the app's secret: [1](#0-0) 

The HMAC is computed by `HmacValidator.validate_signature` over `verifiable_query.to_signable_string`, and for webhook requests that method returns only `@raw_body`: [2](#0-1) [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` — the values that identify *which tenant* the webhook is for — are parsed straight from request headers with no cryptographic binding to the signed bytes: [4](#0-3) 

These unauthenticated header values are then passed unchanged into `WebhookMetadata`, which is delivered to the host app's handler as the trusted shop identity for the webhook: [5](#0-4) [6](#0-5) 

The equality that should hold is: `shop bound by the verified HMAC == shop delivered to the handler`. Instead, the HMAC only binds the body bytes, while `shop` is taken from `headers["shopify-shop-domain"]`/`headers["x-shopify-shop-domain"]`, an entirely separate, unauthenticated channel. Because any merchant can install the target app on their own store, they can capture a webhook body legitimately signed by Shopify for their own shop (using the app's real `client_secret`, which they never need to know), then resend an HTTP request to the app's webhook endpoint with the same body/HMAC but a different `shopify-shop-domain` header claiming to be a victim shop. `HmacValidator.validate` still succeeds because it only checks the body, and the handler receives `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an unprivileged internet user who has installed the app on any shop they control can make the app process arbitrary Shopify-signed webhook payloads under the identity of a shop they do not own, because `shop` is never part of the signed material. Downstream host-app code that relies on `data.shop` from `WebhookMetadata` to select the tenant/session to act on (as documented in `docs/usage/webhooks.md` and `BREAKING_CHANGES_FOR_V15.md`) will act on the wrong tenant, constituting cross-tenant access via a documented, intended API of this gem — not a host-app misuse.

### Likelihood Explanation
Likely reachable by any actor who can install the target app on a shop they control (a normal, unprivileged action) and issue an HTTP request to the app's public webhook endpoint with attacker-controlled headers. No access to `api_secret_key`, TLS interception, or privileged accounts is required — the attacker reuses a genuinely-signed body/HMAC pair they legitimately received and only changes the header that this gem fails to bind into the signature.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `api_version`, `webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload, so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` reflects all data trusted by downstream handlers, not just the raw body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, which they control.
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and `x-shopify-hmac-sha256` computed over `B` with the app's real `client_secret`.
3. Attacker captures this request (e.g., via their own reverse proxy/logging on infrastructure they control) and resends it to the app's webhook endpoint, keeping body `B` and the same `x-shopify-hmac-sha256`, but replacing the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and matches the unchanged `hmac` header — validation succeeds as shown in [7](#0-6) .
5. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and pertains to `attacker-shop.myshopify.com`.
