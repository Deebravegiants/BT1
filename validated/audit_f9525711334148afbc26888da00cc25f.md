### Title
CallDispatcher accounts orders by live `balanceOf()` instead of call-scoped deltas, letting anyone route donated or approved tokens into another user's escrow - (File: evm/src/apps/intentsv2/IntentsBase.sol / evm/src/utils/CallDispatcher.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch flow and `IntentsBase._execute`'s output-sweep flow both size "received" tokens by reading the shared `CallDispatcher`'s **live spot balance** (`IERC20(token).balanceOf(dispatcher)`) after an arbitrary user-supplied call, rather than the precise delta the current call produced. `CallDispatcher.dispatch` itself is a public function with no caller restriction, so any address can inject or pull tokens into/out of it at will. This is the same root cause as the Spartan exploit: accounting off a mutable, externally-donatable spot balance instead of an isolated, call-scoped delta.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol` (lines 268-306, mirrored in `evm/tron/contracts/apps/IntentGatewayV2.sol:421-469`), after the user-controlled `order.predispatch.call` is dispatched: [1](#0-0) 
the code reads `balance = IERC20(token).balanceOf(dispatcher)` — the *entire* current token balance sitting in the shared `CallDispatcher` — and sweeps that whole balance into the gateway, then credits it as the order's escrowed input: [2](#0-1) 

`CallDispatcher.dispatch` has no access control at all: [3](#0-2) 
Anyone can call it directly, encoding a `Call[]` that executes `token.transferFrom(approver, dispatcher, amount)` against any account that still has an outstanding ERC20 allowance to the `CallDispatcher` address. Such allowances are a documented, expected pattern of this exact contract — the HyperFungibleToken calldata-execution docs explicitly warn that approvals granted to the dispatcher for one call's swap/deposit step should be exact, "since the dispatcher contract holds tokens temporarily during execution," implying unlimited or stale allowances are a known but unenforced risk: [4](#0-3) 

The same balance-not-delta pattern also appears in `IntentsBase._execute`, which sweeps the dispatcher's whole balance after arbitrary output calldata runs: [5](#0-4) 

Because the dispatcher is a single stateless, permissionless router shared by every order and every user, any token balance that lands in it — whether from a stale approval pulled by an attacker's own crafted `Call[]`, or dust left behind by a prior order's predispatch call that produced more of a token than that order itself declared in `order.inputs` — is fair game for the *next* `placeOrder` predispatch flow to sweep and credit as if it were that caller's own deposit. This is structurally identical to Spartan Protocol's flaw of computing LP shares/withdrawals from `balanceOf()` instead of tracked, isolated reserves, letting donated/injected balances be misattributed to whichever operation reads the balance next.

### Impact Explanation
An attacker who can locate any live ERC20 allowance to the `CallDispatcher` address (a pattern the protocol's own documentation acknowledges as a risk surface) can call `CallDispatcher.dispatch()` directly to pull those tokens into the dispatcher, then immediately call `placeOrder` with a no-op/minimal predispatch listing that token as an input — crediting the pulled tokens to the attacker's own order escrow at zero cost. Since escrowed inputs are exactly what solvers/relayers redeem on order fill or refund, this is direct theft of funds routed through the shared dispatcher, satisfying "concrete theft ... unauthorized app action."

### Likelihood Explanation
Exploitability depends on the existence of a stale/unlimited approval to `CallDispatcher` from some prior interaction (predispatch or output-calldata execution), which the project's own docs treat as a realistic occurrence they merely recommend against rather than prevent in code. Given `CallDispatcher.dispatch` is unconditionally public and the gateway trusts its live balance unconditionally, any single lapse in "use exact approvals" produces an immediately and permissionlessly exploitable path — no privileged role, governance, or off-chain component is required, only a single crafted transaction.

### Recommendation
Do not size received inputs from `CallDispatcher`'s live `balanceOf()`. Instead, restrict `CallDispatcher.dispatch` to authorized callers (e.g., only the gateway contract that owns the current execution context), or have the gateway compute received amounts strictly from the delta produced by calls it itself constructs and are scoped to the current order (e.g., require the predispatch call to transfer tokens directly to the gateway, or have the dispatcher return/attest to per-call output amounts instead of exposing a sweep-everything primitive). At minimum, never trust a shared, permissionless contract's spot balance as proof that "this order" produced those funds.

### Proof of Concept
1. Some user's earlier order execution (predispatch or output calldata via `_execute`) leaves an ERC20 approval from their wallet to `CallDispatcher` that is not fully exhausted (docs explicitly flag this as a foreseeable misconfiguration: `evm/tron` and `sdk/packages/core` HFT docs, `docs/content/developers/evm/hyper-fungible-token/overview.mdx:96`).
2. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transferFrom.selector, victim, address(callDispatcher), remainingAllowance)})]))` directly — no permission is required per `evm/src/utils/CallDispatcher.sol:44-62`.
3. Attacker immediately calls `IntentGatewayV2.placeOrder` with `predispatch.call` a trivial no-op and `order.inputs[i].token == token`, `amount <= remainingAllowance`.
4. `placeOrder`'s predispatch branch reads `balance = IERC20(token).balanceOf(dispatcher)` (now inflated by the victim's pulled tokens), sweeps it into the gateway, and computes `received = balanceOf(this) - balancesBefore >= order.inputs[i].amount`, crediting the full amount as the attacker's escrowed input (`evm/src/apps/IntentGatewayV2.sol:273-306`) — funds the attacker never paid for from their own wallet.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
