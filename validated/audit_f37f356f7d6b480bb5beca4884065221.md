### Title
Fee overcharge from duplicated storage-deposit top-up computation in batched Omni Bridge withdrawals - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
When multiple withdrawals of the same NEP-141 token are batched in a single `estimateWithdrawalFee`/`createWithdrawalIntents` call, each withdrawal independently computes the same NEAR storage top-up requirement for `OMNI_BRIDGE_CONTRACT` on that token's contract, and each embeds a full copy of that top-up amount into its own `ft_withdraw` intent's `storage_deposit` field. All copies execute in the same batch, so the top-up is paid multiple times even though only one payment is required, and per the protocol's own documentation this excess is never refunded.

### Finding Description
`estimateWithdrawalFee` reads the current storage balance for the token contract via `getCachedStorageDepositValue(assetInfo.contractId)` and computes the shortfall: [1](#0-0) 

That value only gets cached when the balance is already *sufficient* (`result[1] >= result[0]`): [2](#0-1) 

so whenever a top-up is actually needed, the cache is bypassed and a fresh RPC read of the *pre-transaction* on-chain balance is performed for every call. The `storageDepositFee` (the shortfall) then flows into `deriveOmniWithdrawIntentParams`, which sets it as the `storage_deposit` amount on the `ft_withdraw` intent: [3](#0-2) 

`sdk.ts`'s batch APIs (`estimateWithdrawalFee`, `createWithdrawalIntents`/`signAndSendWithdrawalIntent`) process each withdrawal in the batch independently via `Promise.all`/`.map`, then concatenate all resulting intents into one signed payload: [4](#0-3) [5](#0-4) 

Because all these per-item estimates run before any of the resulting intents execute on-chain, if two or more withdrawals in the same batch target the same token contract (same `assetInfo.contractId`), each one independently sees the same insufficient/absent storage balance and independently computes the full shortfall as its own `storage_deposit` amount. All of these `ft_withdraw` intents with duplicated `storage_deposit` amounts are then bundled into a single signed intent and executed together, so the top-up is paid N times for N batched withdrawals of the same token, when the actual on-chain requirement is to pay it once. Per the ABI's own documentation, "the `wNEAR` will not be refunded in any case," so the extra N-1 payments are a permanent loss charged to the user.

This mirrors the referenced bug class: a value dependent on shared, mutable on-chain state (`accRewardPerShare` / here, the storage-balance shortfall) is computed multiple times against the same pre-update state instead of being computed once and reserved/deducted for subsequent computations — breaking the "amount debited = shortfall paid exactly once" equality.

### Impact Explanation
This causes the withdrawing user to be overcharged native NEAR/wNEAR fee (via `storage_deposit` amounts embedded in the batched `ft_withdraw` intents) that is never recoverable, since NEP-141 storage deposits for the bridge contract account are not refunded. This matches the "High – a fee overcharge" impact category, and could reach "Critical" magnitude if the storage top-up required is proportionally large relative to a small withdrawal amount and repeated across many batched withdrawals of the same token.

### Likelihood Explanation
This does not require any malicious party — it is triggered purely by a normal, documented SDK feature (batch withdrawals of multiple assets/positions, including multiple withdrawals of the same token, as advertised in the README's "Batch Withdrawals" section) combined with the token's `OMNI_BRIDGE_CONTRACT` storage balance being below the minimum threshold at estimation time. Any integrator batching several withdrawals of the same Omni-Bridge-routed token while the bridge contract's storage balance on that token is insufficient will hit this.

### Recommendation
Track and reserve the storage-deposit shortfall across all withdrawals of the same token within a single batch (e.g., compute it once per unique `assetInfo.contractId` per batch call, and only include the `storage_deposit` field in the first intent for that token, setting it to `0`/`undefined` for subsequent ones), rather than recomputing and re-embedding the full shortfall independently for every withdrawal item in the batch.

### Proof of Concept
1. Call `sdk.estimateWithdrawalFee({ withdrawalParams: [ {assetId: "nep141:TOKEN.omft.near", amount: A1, destinationAddress: X, feeInclusive:false, routeConfig: omniBridgeRoute}, {assetId: "nep141:TOKEN.omft.near", amount: A2, destinationAddress: Y, feeInclusive:false, routeConfig: omniBridgeRoute} ] })` where `TOKEN`'s `OMNI_BRIDGE_CONTRACT` storage balance is below `minStorageBalance` by `Δ`.
2. Both returned `FeeEstimation`s report `underlyingFees[RouteEnum.OmniBridge].storageDepositFee === Δ` (each computed independently against the same un-topped-up on-chain balance).
3. Call `sdk.signAndSendWithdrawalIntent({ withdrawalParams, feeEstimation })`; the resulting signed intent contains two `ft_withdraw` intents, each with `storage_deposit: Δ.toString()`.
4. On execution, the NEAR contract processes both `ft_withdraw` calls in the same transaction/batch, resulting in `2Δ` total wNEAR/native deposited to top up storage that only required `Δ` — the extra `Δ` is non-refundable per protocol semantics, permanently overcharging the user.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
