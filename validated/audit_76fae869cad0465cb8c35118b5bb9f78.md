### Title
Overwriting a gateway's remote `NewDeployment` mapping permanently strands in-flight `RedeemEscrow`/`RefundEscrow` messages - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` gates delivery of cross-chain `RedeemEscrow` and `RefundEscrow` settlement messages on a single, overwritable per-chain address mapping (`_instances`). Exactly like IronBank's `setCreditLimit()` requiring `isListed` for both entry and exit, here the *same* `_instance(...)` lookup is used to authorize both normal fills/cancels and to authenticate delivery of messages dispatched in the past. When Hyperbridge dispatches a `NewDeployment` update (a routine, non-malicious re-registration of a chain's gateway address, e.g. after a redeploy/migration), any settlement message that was already in flight from the *old* address becomes permanently unauthorizable, and — per the documented ISMP retry semantics — it can be retried forever without ever succeeding.

### Finding Description
`_authenticate()` requires the incoming request's `from` address to equal the *current* value of `_instance(request.source)`: [1](#0-0) 

`_instance()` is a single-slot mapping keyed only by chain id, with no history of prior addresses: [2](#0-1) 

`onAccept` routes `RedeemEscrow`/`RefundEscrow` bodies through `_authenticate` before calling `_withdraw`, and routes `NewDeployment` updates (which overwrite `_instances[...]`) only when the caller is Hyperbridge itself: [3](#0-2) 

Sequence that permanently strands funds:
1. A solver fills a cross-chain order on the destination chain (`_fillCrossChain`), dispatching a `RedeemEscrow` POST back to the order's *source* chain via `_post`, addressed to `_instance(order.source)` — the gateway address registered *at fill time*. [4](#0-3) [5](#0-4) 
2. Before that message is delivered on the source chain, Hyperbridge dispatches a `NewDeployment` for that same chain (e.g. a legitimate gateway redeploy/migration), overwriting `_instances[keccak256(order.source)]` to a new address.
3. When the `RedeemEscrow` message is finally delivered, `_authenticate` compares the message's *old* `from` address against the *new* `_instance(order.source)` and reverts with `Unauthorized()`.
4. Per the documented ISMP delivery model, a reverting `onAccept` leaves no receipt, so the message is retryable — but every retry re-checks against the same now-permanently-different `_instance` value and reverts identically. The escrow (input tokens the user already deposited) is never released to the solver, nor can the order be otherwise unwound, since `_filled[commitment]` was already set on the destination chain, blocking any further fill/cancel path there.

The same failure mode applies to `RefundEscrow` messages generated by `_cancelFromDest`, permanently blocking a user's legitimate refund after cancellation.

### Impact Explanation
This is a permanent freeze of escrowed user/solver funds on the source chain: once a `NewDeployment` update supersedes the address a message was dispatched to, that specific in-flight settlement message can never be authorized again, and the escrow it references becomes unrecoverable through any code path in the contract (no admin sweep exists for `_orders[...]` balances tied to a specific commitment other than `_withdraw`, which is unreachable once `_authenticate` permanently fails). This mirrors the "Medium" severity of the source report: legitimate, expected administrative/protocol action (re-registering a deployment) silently breaks an already-committed state transition with no recovery path.

### Likelihood Explanation
`NewDeployment` re-registration is an expected part of the protocol's operational lifecycle (contract migrations/redeployments across the many supported EVM chains), and cross-chain settlement delivery is inherently asynchronous with delivery lag/backlog, retries, and relayer downtime. Any order that is filled or cancelled shortly before a deployment update lands on the source chain is affected — no attacker action is required, only ordinary timing between a routine governance/ops action and message delivery.

### Recommendation
Do not gate delivery of an already-dispatched settlement message on the *current* value of `_instances`. Options:
- Record and pin the expected sender address (or an accepted set/generation of addresses) into the request context or commitment at dispatch time, and validate against that pinned value on delivery instead of the live mapping.
- Keep a bounded history of prior registered addresses per chain (e.g., a mapping of address → validity window, or an allow-list of "any previously registered address until the message it dispatched has settled") so in-flight messages authored under the old registration still authenticate.
- Alternatively, require that `NewDeployment` updates only take effect for messages dispatched *after* the update, and drain/flush any pending settlement traffic addressed to the prior instance before allowing the mapping to change.

### Proof of Concept
1. On chain B, solver calls `fillOrder` for an order whose `source == chain A`. `_fillCrossChain` dispatches `RedeemEscrow` to `_instance(A) == GatewayA_v1`.
2. Before this message lands on chain A, Hyperbridge dispatches `NewDeployment{stateMachineId: A, gateway: GatewayA_v2}` (e.g., a legitimate redeploy), and `onAccept` on chain A executes `_addDeployment`, setting `_instances[A] = GatewayA_v2`. [6](#0-5) 
3. The `RedeemEscrow` message from `GatewayA_v1` is delivered on chain A. `_authenticate` computes `_instance(A) == GatewayA_v2 != GatewayA_v1` and reverts `Unauthorized()`. [1](#0-0) 
4. Per ISMP semantics, the revert leaves no receipt and the message is resubmitted indefinitely, but `_instances[A]` never reverts back to `GatewayA_v1`, so every resubmission fails identically — the solver's escrowed reimbursement on chain A is permanently locked.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }
