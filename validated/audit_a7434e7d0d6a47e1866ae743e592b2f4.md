## Title
WrappedHyperFungibleToken locks less than the promised amount for fee-on-transfer underlying tokens, causing insolvency and stuck user funds - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` pulls the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but never verifies how much the contract actually received. It then dispatches a cross-chain message that always encodes the full, requested `params.amount` — not the actual balance delta. On the destination chain (or on timeout, on the same chain), the peer contract unlocks/refunds the full nominal `message.amount`. If the underlying token charges a transfer fee (fee-on-transfer / deflationary tokens), the wrapper locks strictly less than what it later promises to release, causing the contract's underlying-token balance to fall behind its liabilities over time.

### Finding Description
In `send()`: [1](#0-0) 

the ERC20 branch does:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
```
with no balance-before/after check, unlike `IntentGatewayV2.placeOrder`, which explicitly guards against this same class of bug: [2](#0-1) 

`_buildDispatchPost` then embeds the caller-supplied `params.amount` (not the actual received amount) into the cross-chain `Message`: [3](#0-2) 

When the message is delivered (or times out), the wrapper releases the full nominal `message.amount` of underlying tokens to the beneficiary/refundee: [4](#0-3) 

The identical pattern exists in the upgradeable variant: [5](#0-4) 

This mirrors the `YollloStaking.accruePackageReward` bug class: the contract assumes it received the full transferred amount and accounts/promises rewards (here, unlock/refund liabilities) based on that assumption, while any transfer fee means the actual balance held is smaller than the recorded liability.

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying token creates a liability (`params.amount`, dispatched as `message.amount`) that exceeds the tokens actually locked in the contract (`params.amount − transferFee`). Because `onAccept`/`onPostRequestTimeout` always release the full nominal amount, the wrapper's underlying-token balance is progressively drained below what is required to service other pending unlocks/refunds. Eventually, legitimate unlock/refund calls for other users' orders will revert with insufficient balance (denial of withdrawal) or, if enough headroom exists from prior over-collateralized sends, later users effectively receive funds subsidized by the shortfall — a permanent, systemic freezing/loss-of-funds condition for the pool of users bridging that asset through this contract. This matches the "Medium" classification of the original report (insufficient tokens for some users' releases) and is a token-bridge lock/unlock path directly reachable by any user calling `send()` with an approved fee-on-transfer token.

### Likelihood Explanation
Reachable from a single unprivileged `send()` call by any user who bridges a fee-on-transfer ERC20 through a `WrappedHyperFungibleToken` deployment configured with `isWeth = false`. No special privileges or governance action are required; the deployer/operator only needs to configure the wrapper for a token that happens to charge a transfer fee (a known common token category, e.g. deflationary/tax tokens). Given the contract accepts an owner-configured arbitrary `_underlying` ERC20 with no restriction against fee-on-transfer semantics, this is a realistic configuration risk with immediate on-chain occurrence on the very first bridge transaction of such a token.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.placeOrder`: measure the actual amount received via balance-before/after around the `safeTransferFrom` call in `send()`, and use that measured amount (not the caller-supplied `params.amount`) both for the dispatched `Message.amount` and for any emitted event/accounting. Alternatively, explicitly document and enforce (e.g., via an allowlist or a post-transfer balance assertion that reverts on any fee) that only standard, non-fee-on-transfer ERC20 tokens may be configured as `_underlying`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, configure `_underlying` as a token with e.g. 1% transfer fee (matching `FeeOnTransferToken` test helper already present in the repo's test suite: `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2690-2735`).
2. User calls `send({..., amount: 1000e18, ...})`. `safeTransferFrom` moves only 990e18 into the wrapper (10e18 burned as fee), but the dispatched `Message.amount` is `1000e18`.
3. On destination delivery (or on timeout back on source), `onAccept`/`onPostRequestTimeout` calls `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)` — 10e18 more than was ever locked for this transfer.
4. Repeating this (or aggregating across multiple sends) drains the wrapper's actual underlying balance faster than its recorded liabilities, so a subsequent legitimate unlock/refund for another user's locked tokens reverts due to insufficient contract balance.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
