## Title
EvmHost dispatch and fundRequest use a self-referential `block.timestamp` as the Uniswap V2 swap deadline, providing no real expiration protection - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment and swap it for `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` (read at execution time) as the `deadline` argument. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The Uniswap V2 router's `deadline` check is `require(deadline >= block.timestamp)`. When the caller passes `block.timestamp` evaluated *inside* the same transaction execution as the deadline, this check is trivially and permanently satisfied - it can never expire, because the value being compared is read at the exact instant of comparison. This is functionally identical to the audited pattern flagged in the external report (`deadline: block.timestamp`) and defeats the entire purpose of a deadline: it places no bound on how long the caller's transaction can sit in the mempool, or on the block/validator/relayer that ultimately includes it, before the swap executes.

All three of these entry points - `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` - are `external payable notFrozen` functions with no access restriction, callable by any unprivileged account that wants to pay Hyperbridge dispatch/fund fees in native token instead of the `feeToken()`. [4](#0-3) [5](#0-4) [6](#0-5) 

Because there is no meaningful deadline, a transaction paying native ETH for a dispatch/fund operation can be strategically held and included by a block builder/relayer at an advantageous moment (classic time-bandit/MEV sandwich pattern), extracting value from the caller's supplied ETH before the fee-token swap executes, exactly the value-leak mechanism described in the source report.

### Impact Explanation
Any unprivileged user dispatching a POST/GET request or funding a pending request with native ETH is exposed to unbounded execution timing on the ETH→feeToken leg of their transaction. Because the deadline never actually constrains inclusion time, the swap can be sandwiched or delayed to a less favorable price window, causing the caller's ETH to be converted at a worse rate than intended, or to be exploited via MEV extraction, a leak of value from the dispatcher's own transaction. This affects the core `EvmHost` dispatch path used to send/fund every cross-chain message paid for in native token, which is Medium severity per the report's classification (loss of value from unprotected DEX interaction, not outright fund freezing).

### Likelihood Explanation
Likelihood is moderate: it requires the caller to pay in native ETH (an explicitly supported code path) and for the transaction to be observed and manipulated by a searcher/validator before inclusion, which is a routine capability on public EVM chains. No privileged role is required, this is directly reachable by any ordinary dispatch/fundRequest caller.

### Recommendation
Do not compute the Uniswap deadline as `block.timestamp` inside the swap-triggering function. Instead, accept a caller-supplied `deadline` parameter (or a bounded `block.timestamp + maxDelay`) in `DispatchPost`, `DispatchGet`, and `fundRequest`, and pass that fixed, externally meaningful value to `swapETHForExactTokens`, so the router's check actually enforces a real time bound on inclusion.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `msg.value > 0` to cover `post.fee` in native ETH.
2. Internally, `path = [WETH, feeToken()]` and `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is invoked, where `block.timestamp` is read live during the router call. [7](#0-6) 
3. Because `deadline == block.timestamp` at the moment of comparison inside the router, the check `deadline >= block.timestamp` always passes, regardless of how long the transaction sat in the mempool or which block ultimately includes it.
4. A block builder/searcher can therefore delay inclusion and/or sandwich the swap around the user's ETH-for-feeToken conversion without the deadline ever blocking it, extracting value from the user's supplied ETH.
