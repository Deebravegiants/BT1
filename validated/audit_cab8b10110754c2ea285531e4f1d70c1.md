### Title
Webhook shop-domain identity spoofing due to HMAC not covering the `shop` field - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC over the raw request body only, using the app's single, shop-independent `api_secret_key`. The `shop` value handed to the app's webhook handler is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes. This breaks the identity binding `shop_authenticated == shop_acted_on`, letting anyone who can produce one valid HMAC (e.g., the operator of their own store using the same app) relabel the payload as belonging to any other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read separately from an unsigned header: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC of `to_signable_string` (the body) against `Context.api_secret_key`, which is the same secret for every shop that has installed the app - it is not shop-specific: [3](#0-2) 

`Registry.process` uses this body-only HMAC check as the sole authenticity gate, then forwards `request.shop` (the unauthenticated header) straight into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the signature covers only the body and the secret is shared across all tenants of the app, a request with a *valid* signature says only "this body was HMAC'd with our app's secret" - it proves nothing about which shop the body belongs to. The gem's own documentation instructs handlers to trust `data.shop` as the shop identity for downstream processing (e.g. enqueuing jobs keyed by shop domain): [5](#0-4) [6](#0-5) 

**Identity binding broken:** `shop_that_produced_valid_hmac == shop_attributed_to_the_event` is assumed true by `Registry.process`/`WebhookMetadata`, but is never actually checked - the header can be set to any value independent of the body/HMAC.

### Impact Explanation
An attacker who legitimately installs the app on their own store (an unprivileged action any merchant can do) can capture one of their own valid, correctly-HMAC'd webhook deliveries (same shared `api_secret_key` for the app), then replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still passes because it only checks the body bytes, so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain. Any app logic that trusts `data.shop` to select which tenant's session/data to act on (session lookup, cache invalidation, GDPR/data-erasure handling, uninstall cleanup, order/customer sync) can be triggered against a shop the attacker does not control - this is a cross-tenant confusion primitive reachable purely from the gem's documented API.

### Likelihood Explanation
Requires only that the attacker install the target app on a store they control (a normal, unprivileged flow), capture one webhook delivery, and replay it with a rewritten header to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is required, and the vulnerable code path (`Registry.process` / `Request#to_signable_string` / `HmacValidator`) is exactly as shipped in this gem.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the signature (e.g., verify the shop is one associated with the app's stored sessions before dispatching to handlers). At minimum, document that `data.shop` from `WebhookMetadata` is not authenticated by the HMAC and must be independently corroborated (e.g., against known installed shop sessions) before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate, unprivileged installation).
2. Shopify sends the attacker a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(app.api_secret_key, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H` (their own webhook, no secret needed).
4. Attacker POSTs to the app's webhook route with the same body `B` and same header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds because `to_signable_string` only checks `B` against `H` using the shared `api_secret_key` [7](#0-6) .
6. The app's handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` and performs shop-scoped work (e.g., session/data operations) attributing the attacker's event to the victim shop.
