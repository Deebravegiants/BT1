### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC signature over the raw request body only, but the `shop` value it hands to the application's webhook handler is read from an unauthenticated HTTP header that is never included in the signed bytes. An attacker who can obtain one valid `(body, hmac)` pair — for example by installing the target app on their own shop and receiving a genuine webhook for it — can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header, and the gem will treat the request as authentically originating from the victim shop.

### Finding Description
The HMAC binding equality that should hold is:
`hmac == HMAC(secret, bytes-that-include-shop)`

Instead, the gem implements:
`hmac == HMAC(secret, raw_body)`, while `shop` is read independently and forwarded unchecked.

`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic relationship to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (i.e., body only) and then, on success, forwards `request.shop` straight to the application handler as the authenticated tenant identifier: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm the check is computed purely from `verifiable_query.to_signable_string`, with no shop binding: [4](#0-3) 

Because `shop` is outside the signed payload, any `(body, hmac)` pair that is valid for one shop remains valid — HMAC-wise — for a request that claims to originate from a *different* shop. An unprivileged attacker doesn't need the app's `api_secret_key`: they only need to be a legitimate merchant/installer of the app on their own store to receive one authentic webhook (body + HMAC) for an event they can trigger themselves (e.g. `app/uninstalled`, `orders/create` with attacker-controlled order data, `customers/redact`, etc.), then replay that exact body/HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to the victim shop's domain.

### Impact Explanation
`WebhookMetadata.shop` — built directly from the unauthenticated header — is what host applications use to key their tenant data (session lookup/deletion, order/customer records, uninstall handling). Since the HMAC check in this gem never binds `shop` to the payload, an attacker can make the library report a webhook as validly originating from a shop they do not control, enabling cross-tenant data injection and, notably, spoofed `app/uninstalled` events that could cause the host app to delete another merchant's stored session/access token. This satisfies the High-severity "cross-tenant access" criterion.

### Likelihood Explanation
Medium/High: no secret or privileged access to the target is required — only self-service installation of the same public app on an attacker-controlled store to harvest one valid `(body, hmac)` pair, plus the ability to send an HTTP request with a forged header to the app's public webhook endpoint.

### Recommendation
Bind `shop` (and other identity-relevant headers, such as `topic`) into the signable bytes that are HMAC-verified, or otherwise cryptographically tie the declared shop domain to the payload before it is trusted downstream (e.g. reject/flag when the declared `shop` cannot be corroborated against session/shop state already known to the app). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-identity source by consuming applications.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (attacker-owned) shop `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g. `app/uninstalled` or `orders/create`) and captures the raw POST body and its `x-shopify-hmac-sha256` value sent by Shopify to the app's webhook endpoint.
3. Attacker resends the identical body and HMAC header to the same webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC successfully (it only checks the body) via `Utils::HmacValidator.validate`, then constructs `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the registered handler, which the host app trusts as an authentic event for the victim tenant: [3](#0-2)
