## Analysis

The reported bug class—continuing execution after an unchecked/failed critical operation, creating state inconsistency across two systems that are supposed to stay synchronized—maps to a real pattern in `orb-core`'s Personal Custody Package (PCP) upload flow.

In `do_signup` (`src/plans/mod.rs`), tier-0 of the PCP is uploaded via `upload_pcp_tier_0`, whose boolean success result *is* checked before continuing. However, for `pcp_version >= 3`, tiers 1 and 2 (which contain the iris/face/normalized-iris encrypted biometric tars) are merely enqueued to the `data_uploader` agent with `.send(...)` and never awaited for actual upload success: [1](#0-0) 

The `.send()` calls only confirm the item was placed into the agent's internal port queue — not that the HTTP upload to the backend succeeded. The actual upload happens later, asynchronously, in `Agent::upload_pcp`: [2](#0-1) 

Here, if the upload fails with a client error (or exhausts `RETRIES_COUNT`), the loop simply `break`s and the function returns `(tier, id)` with **no error signal propagated anywhere** — the caller (the main event loop in `Agent::run`) only uses the tuple to update internal queue bookkeeping: [3](#0-2) 

Meanwhile, back in `do_signup`, execution proceeds immediately to enrollment/signup-success determination without any dependency on whether tiers 1/2 actually reached the backend: [4](#0-3) 

### Title
Unchecked/Unawaited Tier-1/Tier-2 PCP Upload Result Allows Signup Success Despite Silent Biometric Upload Failure - (File: src/plans/mod.rs)

### Summary
`do_signup` fire-and-forgets the tier-1 and tier-2 Personal Custody Package uploads to the `data_uploader` agent and never checks whether those uploads actually succeeded on the backend before deciding and reporting signup success, mirroring the reported bug class of proceeding with dependent logic without validating that a critical, possibly-failing external operation actually completed.

### Finding Description
For PCP version ≥ 3, `do_signup` pushes tier-1 and tier-2 payloads into the `data_uploader` port queue via `.send(...)`, which only confirms enqueueing, not upload completion [1](#0-0) . The actual HTTP upload occurs later inside `Agent::upload_pcp`, and on failure (e.g., a client error response or exhausting `RETRIES_COUNT` retries) the function silently `break`s out of its retry loop and returns without any error being surfaced to the plan/signup flow [5](#0-4) . The event loop consuming this result only uses it for queue/backpressure bookkeeping, never for signal propagation back to the enrollment decision [3](#0-2) . Consequently `do_signup` proceeds directly to compute enrollment/`success` and reports `SignupReason::Normal`/`signup_successful()` independent of whether tiers 1/2 (which contain the encrypted iris/normalized-iris/face biometric tars) were ever durably stored on the backend [4](#0-3) .

### Impact Explanation
This creates the same class of cross-system inconsistency described in the report: one side (the Orb, analogous to the "source chain") records/reports the operation (signup) as successful, while the other side (the backend, analogous to the "destination chain") may be missing the corresponding biometric data due to a silently failed upload. This can cause incomplete biometric retention (missing tier1/tier2 data for a signup that is reported/enrolled as successful), and — depending on downstream reliance on tier1/tier2 for later verification/self-custody flows — a state where a user is enrolled without the backend holding the expected encrypted biometric package.

### Likelihood Explanation
This can be triggered by ordinary transient network conditions (dropped connections, backend 4xx/5xx responses, or retry exhaustion) without any special privileges — it is purely a robustness gap in the standard signup path used by every unprivileged end user, not something requiring a malicious operator/peer.

### Recommendation
`do_signup` should await confirmation of tier-1/tier-2 upload completion (or have `data_uploader` surface success/failure back through a channel, similar to how tier-0's `upload_pcp_tier_0` returns `Result<bool>`), and only report signup success / proceed with enrollment once all required tiers have been confirmed as durably uploaded, or explicitly retry/fail the signup when they are not.

### Proof of Concept
1. Start a signup with `pcp_version >= 3`.
2. Simulate the backend returning a client error (4xx) for the tier-1 or tier-2 upload request handled by `backend::upload_personal_custody_package::request` inside `Agent::upload_pcp`.
3. Observe that `upload_pcp` breaks out of its retry loop and returns without any error propagated [6](#0-5) .
4. Observe that `do_signup` still proceeds to `enroll_user`/`signup_successful()` logic without any dependency on this failure [4](#0-3) , resulting in a signup marked successful despite missing tier1/tier2 backend data.

impl Agent {
    async fn upload_pcp(&self, pcp: Pcp, id: u64) -> (u8, u64) {
        let Pcp { signup_id, user_id, data, checksum, tier } = pcp;
        tracing::info!(
            "Start uploading a personal custody package tier {tier} for signup_id={signup_id}"
        );
        let t = Instant::now();
        loop {
            let response = backend::upload_personal_custody_package::request(
                &signup_id,
                &user_id,
                checksum.as_ref(),
                &data,
                Some(tier),
                &self.config,
            )
            .await;
            match response {
                Ok(()) => {
                    dd_timing!("main.time.signup.upload_custody_images" + format!("t{}", tier), t);
                    tracing::info!(
                        "Personal custody package tier {tier} uploading completed in: {}ms",
                        t.elapsed().as_millis()
                    );
                    break;
                }
                Err(err) => {
                    tracing::error!("UPLOAD PERSONAL CUSTODY PACKAGE TIER {tier} ERROR: {err:?}");
                    dd_incr!(
                        "main.count.http.upload_custody_images.error.network_error",
                        "error_type:normal"
                    );
                    if let Some(reqwest_err) = err.downcast_ref::<reqwest::Error>() {
                        if let Some(status) = reqwest_err.status() {
                            if status.is_client_error() {
                                dd_incr!(
                                    "main.count.signup.result.failure.upload_custody_images",
                                    "type:network_error",
                                    "subtype:signup_request"
                                );
                                break;
                            }
                        }
                    }
                }
            }
        }
        (tier, id)
    }
