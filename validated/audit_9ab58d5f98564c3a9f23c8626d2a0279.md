This confirms `WebhookMetadata.shop` is passed directly from the unauthenticated header into the app's handler as the tenant identifier, alongside `body`, `topic`, `webhook_id` — none of which are covered by the HMAC.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not bound to the HMAC-verified body, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates nothing but the request body. The `shop`, `topic`, and `webhook_id` values — read straight from HTTP headers — are handed to the app's `WebhookHandler#handle` as trusted tenant/context metadata without ever being covered by the signature.

### Finding Description
`Webhooks::Registry.process` only verifies `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

The HMAC check compares `HMAC(secret, request.to_signable_string)` to the `hmac` header, and `to_signable_string` is defined as just the raw body: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are all read from headers that are never part of the signed content: [3](#0-2) 

These unauthenticated values are then packaged as trusted context and passed to the app-supplied handler: [1](#0-0) [4](#0-3) 

The identity binding that should hold is: `shop header == shop that produced/authorized this exact body`. Because the HMAC only proves "this body was produced by someone holding `client_secret`," and `client_secret` is shared across every shop that has the app installed, any merchant who installs the app on their own store (an ordinary, unprivileged action) can trigger a real webhook delivery, capture a valid `(raw_body, hmac)` pair from Shopify, and then replay that exact body/HMAC to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header. The HMAC check still passes (the body is untouched), but the `shop` value the handler receives is now attacker-chosen and disconnected from the event that actually produced the body.

### Impact Explanation
This breaks tenant isolation for any app that uses `WebhookMetadata#shop` to key data (which is the intended and documented use of this field). An attacker who owns any store where the target app is installed can:
- Forge events attributed to a victim shop (e.g. `orders/create`, `customers/create`) using content from their own store, polluting or corrupting the victim's records in the app's database.
- Trigger destructive mandatory webhooks (e.g. `shop/redact`, `customers/redact`, `app/uninstalled` cleanup logic) against a victim shop they don't control, since the handler trusts `data.shop` as the tenant to act on.

This qualifies as cross-tenant access under the stated Critical impact criteria, since it lets one tenant's authenticated request be attributed to and acted upon another tenant's data without any credential belonging to that tenant.

### Likelihood Explanation
Requires only an ordinary app installation by the attacker on a store they control (no `api_secret_key`, no TLS interception, no privileged account of the victim) plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers, which is inherent to how public webhook receivers work. The bug is entirely in this gem's `Request`/`HmacValidator`/`Registry` chain, which never binds `shop` to the signed payload.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified, or otherwise require the host application to cross-check `request.shop` against an independently known, previously-registered shop for that installation/session before dispatching to `handle`. At minimum, document that `shop` is unauthenticated and must be validated by the app before being trusted as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers `orders/create` (a webhook they can freely produce, e.g. by placing a test order).
2. Shopify delivers a POST to the app's public webhook URL with a valid `x-shopify-hmac-sha256` header computed over the JSON body using the app's `client_secret`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker crafts a new POST to the same public webhook URL with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks the (unchanged) body against the secret: [5](#0-4) 
6. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` and the attacker's own order body, which the app treats as an authentic event for the victim tenant.
