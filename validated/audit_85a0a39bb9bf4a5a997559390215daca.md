Audit Report

## Title
ERC20 Asset Transactor assumes exact-amount ERC20 `transfer()` semantics, breaking accounting for fee-on-transfer/rebasing tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens through a shared `TransfersCheckingAccount` by calling `IERC20::transfer(amount)` and unconditionally trusting that the requested `amount` equals the actual balance delta produced by the call, without ever reading `balanceOf` before/after. [1](#0-0) [2](#0-1)  This breaks the runtime's internal accounting for any ERC20 that does not implement strict 1:1 exact-amount transfer semantics (fee-on-transfer, deflationary burn-on-transfer, or rebasing tokens).

## Finding Description
In `withdraw_asset_with_surplus`, the function calls `transfer(checking_address, amount)` and, on a `true` boolean return, unconditionally constructs an `AssetsInHolding` credit for the full nominal `amount` requested — not the amount actually received by the checking account: [3](#0-2) 

In `deposit_asset_with_surplus`, the function similarly calls `transfer(address, amount)` from the checking account to the beneficiary for the same nominal `amount` credited earlier, with no verification of the checking account's actual balance before or after the call: [4](#0-3) 

Neither function measures `balanceOf(checking_account)` deltas; both rely solely on the boolean success return of `IERC20::transfer`, which is standards-compliant for exact-transfer ERC20s but not for fee-on-transfer or rebasing tokens. Since `TransfersCheckingAccount` is a single pooled account shared across all ERC20 transfers routed through this transactor, a divergence introduced by one non-standard token can affect the ability to process other pending transfers of that same asset through the same account. No existing guard (balance check, invariant assertion, or registration-time compliance test) mitigates this in the shown code.

## Impact Explanation
If a registered ERC20 token deviates from exact-transfer semantics (fee-on-transfer, deflationary, or rebasing), the pooled `TransfersCheckingAccount`'s real balance can diverge from the sum of amounts the runtime believes it holds. This can cause subsequent `deposit_asset_with_surplus` calls for that asset to fail (stuck funds) if the account is under-funded relative to nominal accounting, or cause unaccounted value drift. This is a genuine accounting-assumption bug in an in-scope, reachable code path, not a theoretical/mocked issue — the impact is concrete for any such deployed token.

## Likelihood Explanation
Exploitability is conditioned on a non-standard ERC20 (fee-on-transfer/rebasing) being deployed via `pallet-revive` and matched by the runtime's `Matcher: MatchesFungibles` configuration for use with `ERC20Transactor`. `ERC20Transactor` is confirmed as a live, wired-in component referenced from `asset-hub-westend`'s runtime code and is exercised in tests, indicating it is a real, non-mocked production path. [5](#0-4)  Once such a token is registered (which may require an asset-registration action, but exploitation itself needs no elevated privilege thereafter), any user transferring that token through XCM can trigger the divergence. The core code behavior matches the claim exactly.

## Recommendation
Measure `balanceOf(checking_account)` (and beneficiary balance) before and after the `transfer` call in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, and credit/report the actual observed delta rather than the nominal requested `amount`. Alternatively, restrict `MatchesFungibles` asset registration to enforce/verify strict exact-transfer ERC20 compliance before a token can be used with `ERC20Transactor`.

## Proof of Concept
1. Register (via the runtime's `MatchesFungibles` matching configuration) an ERC20 deployed through `pallet-revive` that implements a fee-on-transfer or rebasing mechanism.
2. Initiate an XCM transfer of `amount = 1000` of this token; `withdraw_asset_with_surplus` calls `transfer(checking_account, 1000)`, but due to the fee the checking account's real balance only increases by e.g. `990`, while the function still credits `AssetsInHolding` with `1000` (lines 195–203 of `erc20_transactor.rs`).
3. When `deposit_asset_with_surplus` later attempts to release the credited `1000` to a beneficiary via `transfer(beneficiary, 1000)` from the checking account (lines 253–266), the checking account may lack sufficient real balance if it is not backstopped by other users' pooled funds, causing the transfer to revert/return `false` and the deposit to fail with `XcmError::FailedToTransactAsset`, or — if backstopped by other pooled balances — silently consume funds nominally attributed to unrelated users, breaking the 1:1 accounting invariant.
