## #VulnerabilityFound

### Title
Webhook `shop` tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) value from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies is computed over the raw body only. Because the two pieces of data are decoupled, an attacker who can produce or obtain a valid `(body, hmac)` pair for the app's `client_secret` (trivially available to them by installing the app on their own shop and receiving genuine webhook deliveries) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. The signature check passes, and the payload is dispatched to the app's handler tagged with the attacker-chosen shop, breaking the equality `shop_verified_by_hmac == shop_acted_on`.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes/compares the signature against `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only the raw body** — the `shop` value used downstream comes from a separate, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`): [3](#0-2) 

After validation succeeds, `shop` is handed to the app's handler as the trusted tenant identifier: [4](#0-3) 

Since the app's `client_secret` HMAC-signs identical payload bytes regardless of which of the app's installed shops originated the delivery, any shop that has the app installed can capture one of its own legitimate `(raw_body, hmac)` pairs and replay it against the app's public webhook URL with a different `shop-domain` header. The library performs no binding check between the header-derived `shop` and the HMAC-verified bytes, so `HmacValidator.validate` returns `true` and `Registry.process` invokes the handler with the attacker-chosen `shop`, e.g. `WebhookMetadata.new(topic: ..., shop: request.shop, body: ...)` — attributing forged/replayed data to a tenant that never sent it.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `hmac_signed_bytes ⊇ {body, shop}`, but in reality `hmac_signed_bytes = {body}` while `shop` is trusted downstream unchecked.

### Impact Explanation
This allows an unprivileged party (any merchant/store that can install the target app) to make the app believe arbitrary webhook payloads originated from a different, victim tenant of the same app. Depending on the host app's handler logic (e.g., updating order/customer/inventory records keyed by `shop`), this can lead to cross-tenant data corruption or state confusion — meeting the "cross-tenant access" Critical impact bar, since no access token, `api_secret_key`, or credential leak is required, only normal use of the gem's documented webhook processing API.

### Likelihood Explanation
Any actor who can install the target app on a shop they control receives genuine, correctly-signed webhook deliveries for arbitrary self-triggered events (e.g., creating a test order), giving them a valid `(body, hmac)` pair at will. Sending an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header requires no special access, TLS interception, or secrets — just a normal internet-reachable request. Likelihood is High for apps whose webhook handlers act on `shop` without independent tenant verification.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived tenant to the signed payload before it is trusted. At minimum, `Webhooks::Registry`/`Request` should require the host app to cross-check the resolved `shop` against a known/expected shop (e.g., one with a stored session) before invoking handlers, and documentation should explicitly warn that the `shop` header is not covered by the HMAC signature.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a real event (e.g., `orders/create`) so Shopify delivers a genuinely signed webhook to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body B>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Capture the exact raw body `B` and the valid `hmac` value from that delivery.
3. Send a new POST directly to the app's public webhook endpoint reusing body `B` and the same `hmac`, but replace the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate` succeeds because it only re-derives the signature from `B` (`to_signable_string` returns `@raw_body`), never inspecting `shop-domain`.
5. `Registry.process` calls the registered handler with `shop: "victim.myshopify.com"`, causing the host app to process attacker-authored data as if it came from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
