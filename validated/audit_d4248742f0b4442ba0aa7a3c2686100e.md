### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` binds nothing but the body bytes. The `shop-domain`, `topic`, and `webhook-id` headers used downstream in `Registry.process` are read straight from the unauthenticated headers and never bound to the signature, breaking the identity binding `shop (authenticated) == shop (acted upon)`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` only, and `hmac` is parsed straight from the `hmac-sha256` header: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are likewise parsed directly from headers with no cryptographic binding to the signed payload: [3](#0-2) 

`Registry.process` verifies the HMAC and, once it passes, trusts `request.shop`, `request.topic`, and `request.webhook_id` unconditionally to build `WebhookMetadata` for the handler: [4](#0-3) 

Because the app's `client_secret` (`Context.api_secret_key`) is shared across every merchant that installs the app, any merchant can legitimately install the app on their own store and receive genuinely-signed webhook deliveries (valid `raw_body` + `hmac-sha256` pair). Since the signature covers only the body and not the shop/topic headers, that attacker can replay the exact same signed body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (body bytes unchanged, secret is the shared app secret), and `Registry.process` will dispatch the handler with `shop: request.shop` set to the attacker-chosen victim domain.

This is the same class of bug identified in the external report — a value the calling code trusts and acts upon (`shop`) is not covered by the value that was actually verified (the HMAC over the body only) — except here it manifests as an unprivileged internet user being able to break the equality `verified_shop == acted_upon_shop`.

### Impact Explanation
This allows a low-privilege attacker (any merchant who can install the target app) to have host application logic attribute attacker-controlled, cryptographically "verified" webhook data to an arbitrary victim shop, crossing the tenant isolation boundary that the library's HMAC check is supposed to enforce. Depending on how the host app uses `WebhookMetadata#shop`/`#body` (e.g., upserting orders/customers/products keyed by shop), this can result in cross-tenant data injection or corruption attributed to a shop the attacker does not own.

### Likelihood Explanation
Moderate-to-high: the attacker only needs to install the target app once (a normal, unprivileged action any Shopify merchant can perform), capture one legitimately delivered webhook (body + `hmac-sha256`), and replay it to the same public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or elevated access are required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise validate that the `shop-domain` header corresponds to a shop that legitimately owns/expects this specific signed payload before trusting it in `Registry.process`. At minimum, document that host applications must independently verify `request.shop` against their own installed-shop records before acting on webhook content, and add unit tests asserting that a valid HMAC computed for shop A's raw body cannot be replayed with a modified shop header and be accepted for shop B.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(app_secret, B)`.
3. Attacker replays the exact same `B` and `H` to the same endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(app_secret, request.to_signable_string)` — which is `HMAC(app_secret, B)` — and it matches `H`, so validation passes: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `shop: request.shop` equal to `"victim.myshopify.com"`, even though the body content actually originated from the attacker's own shop.
