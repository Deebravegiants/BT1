### Title
Webhook processing trusts the unauthenticated `shop-domain` header for tenant attribution while the HMAC only signs the raw body — cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity solely by checking the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop` (and `topic`/`webhook_id`) values that are handed to the app's handler are read straight from HTTP headers (`shop-domain`), which are never part of the signed payload. Since the app's webhook signing secret (`Context.api_secret_key`) is the same `client_secret` shared across every shop that installs the app — not a per-shop secret — any merchant who legitimately receives a signed webhook for their own shop can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting a different `shop-domain` header. The signature check still passes because it is computed only over `@raw_body`, so the handler is invoked believing the payload originated from the attacker-chosen shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from HTTP headers that are outside this signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata object dispatched to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the digest exclusively from `verifiable_query.to_signable_string` (the raw body for webhooks) against `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is the app-level `client_secret`, identical across all merchants who install the app, HMAC validity proves only "this body was signed with this app's secret at some point" — it does not bind the `shop-domain` header to that body. The equality the code implicitly (and wrongly) assumes is:

`hmac_valid(raw_body) == (shop_header authentically corresponds to raw_body)`

but the correct equality that should hold before trusting `request.shop` is:

`shop_header ∈ signed_bytes(raw_body, hmac)`

which is false here, since `shop-domain` is not part of `to_signable_string`.

### Impact Explanation
Any merchant with the app installed on their own store receives legitimate, correctly-signed webhooks addressed to their shop. By capturing one such `(raw_body, x-shopify-hmac-sha256)` pair and re-POSTing it to the app's webhook endpoint with a forged `shop-domain`/`x-shopify-shop-domain` header pointing at a victim shop, the attacker causes the app to process attacker-controlled webhook content under the victim tenant's identity. Depending on the handler's logic (e.g., `orders/create`, `app/uninstalled`, mandatory `customers/redact`, `shop/redact` handlers), this enables cross-tenant data confusion, forged business events attributed to another merchant, or triggering destructive/administrative actions (like data-redaction or uninstall handling) against a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires being an ordinary, unprivileged merchant who has the target app installed on any shop (to obtain one valid signed webhook) and the ability to send an HTTP POST to the app's public webhook endpoint with modified headers — no access to `api_secret_key`, access tokens, or privileged accounts is needed. The webhook endpoint is by design internet-reachable and unauthenticated aside from the HMAC check, making this readily reproducible.

### Recommendation
Bind the shop (and topic/webhook id) to the signed material instead of trusting headers verbatim:
- Include `shop-domain`/`topic`/`webhook-id` in the HMAC-signed payload check (e.g., verify these values also appear/are consistent with a signed envelope), or
- Require callers to separately verify the `shop-domain` header against the session/tenant that the app already has on record before dispatching to a handler, and reject/flag any mismatch between the previously known shop for that webhook subscription and the header-supplied shop.
- At minimum, document prominently that `request.shop` is unauthenticated and must not be used for tenant-scoping decisions without additional server-side correlation (e.g., checking the shop is one the app has an active session/install for, and rate-limiting/deduplicating by `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a benign event (e.g., updates a product) to receive a legitimate webhook POST from Shopify containing a raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the exact same POST to the app's public webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256: H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `shop` returns `"victim-shop.myshopify.com"` while `to_signable_string` still returns `B`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares to `H` — this succeeds because `B` and `H` are unmodified.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied content as if it came from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
