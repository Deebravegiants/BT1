### Title
Escrowed Intent Funds Permanently Frozen When Beneficiary Address Is Blocklisted by the Escrowed ERC20 Token — (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` (used by `ExtrinsicIntents.onAccept`/`onGetResponse` for `RedeemEscrow`/`RefundEscrow`, and mirrored by `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol`) pushes escrowed tokens directly to a beneficiary address taken from the cross-chain `WithdrawalRequest` with no fallback if that push reverts. If the beneficiary is later blocklisted by a compliant ERC20 (e.g. USDC/USDT-style transfer-denylist) or is a contract that unconditionally reverts on receiving native value, every delivery attempt of that message reverts and the escrow can never be released to anyone — mirroring the `SellerFinancing._conditionalSendValue()` bug where a sanctioned recipient's inability to receive funds permanently locks value with no redirect/refund path.

### Finding Description
`_withdraw()` unconditionally transfers escrowed tokens to `body.beneficiary`: [1](#0-0) 

For the `RefundEscrow` path, the beneficiary is `order.user` — the same address that escrowed the tokens when placing the order: [2](#0-1) 

If `order.user` (or, for `RedeemEscrow`, the filling solver `msg.sender`) is subsequently added to a compliance blocklist by the escrowed ERC20 (Circle/Tether-style `transfer`/`transferFrom` denial) or is a contract designed to reject `.call{value:}("")`, then:
- `IERC20(token).safeTransfer(beneficiary, amount)` or `_sendValue(beneficiary, amount)` reverts every time.
- The entire `onAccept` call reverts, so `EvmHost.dispatchIncoming` deletes the receipt "so that it can be retried": [3](#0-2) 

Because the blocklist status (or the malicious contract's revert behavior) does not change, "retryable" is meaningless here — every future relayer resubmission fails identically. There is no alternate claim path: no pull-based withdrawal, no ability for the user/solver to redirect the beneficiary, and no timeout/expiry mechanism for `_withdraw()` once the request has authenticated. The `_orders[commitment][token]` escrow balance is decremented only transactionally with the transfer (both revert together), so the funds remain locked in the gateway contract forever, unreachable by the rightful owner.

This is structurally identical to the reported `SellerFinancing._conditionalSendValue()` issue: a payment path that pushes value to a party whose ability to receive funds can be revoked by a token's compliance layer, with no fallback that lets the counterparty (or the funds' true beneficiary) reclaim the value through an alternate route.

### Impact Explanation
Any input tokens escrowed by `IntentGatewayV2`/`ExtrinsicIntents` for an order whose `order.user` (refund beneficiary) or filling solver becomes blocklisted by the escrowed ERC20 are permanently frozen — a direct, unrecoverable loss of user funds with no governance or protocol-level recovery mechanism exposed in this code path (the only override, `Execute`, delegatecalls governance-controlled logic but no such recovery function exists in the current implementation). This satisfies the "permanent freezing of funds" bar for Medium/High severity.

### Likelihood Explanation
Reachable from a single order placement plus normal cancellation/fill flow — no privileged role needed. The trigger condition (the address becoming blocklisted by a widely-used compliant stablecoin, or being a deliberately hostile contract set as `order.output.beneficiary`/order creator) is realistic given USDC/USDT-class tokens are common intent-settlement assets, and a griefing user could deliberately place an order using a contract beneficiary that reverts on receipt to grief a solver's `RedeemEscrow`, or self-lock their own refund path as a way to force perpetual escrow (denial of settlement) that also blocks the commitment slot from ever finalizing.

### Recommendation
Update `_withdraw()` (and the Tron `withdraw()` equivalent) to isolate the per-beneficiary transfer failure from the overall message processing: attempt the transfer in a way that cannot revert the whole delivery (e.g. try/catch around the ERC20 transfer and native `.call`), and on failure record the amount as claimable by the beneficiary via a separate pull-based `claim()`/`rescue()` function, or allow governance/the order owner to redirect an un-deliverable payout to an alternate address after a grace period — analogous to the recommended fix of refunding the buyer when the seller is sanctioned in `SellerFinancing.sol`.

### Proof of Concept
1. User places a cross-chain order via `placeOrder`, escrowing ERC20 `USDC` as `order.inputs`, with `order.user` set to their own address `A`.
2. Address `A` is later added to `USDC`'s blocklist (or, for a synthetic PoC, deploy a `RevertingBeneficiary` contract implementing no `receive()`/rejecting ERC20 callbacks that is *never* blocklisted but is chosen as `order.output.beneficiary`/`order.user` at order-placement time).
3. After `order.deadline` passes without a fill, anyone calls `cancelOrder` → `_cancelFromDest`, which dispatches a `RefundEscrow` message back to the source chain gateway with `beneficiary = order.user = A`.
4. The relayer delivers the message via `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` → `IntentsBase._withdraw()`.
5. `IERC20(USDC).safeTransfer(A, amount)` reverts because `A` is blocklisted. The whole `onAccept` call reverts; `EvmHost.dispatchIncoming` deletes the receipt and returns, leaving the message "retryable."
6. Every subsequent relayer resubmission of the identical `RefundEscrow` message reverts identically because `A`'s blocklist status is unchanged. The escrowed `USDC` for this commitment is now permanently unrecoverable — no other function in `IntentsBase`/`ExtrinsicIntents` can redirect or claim it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
