### Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header — cross-tenant data confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the shop identity attached to the processed data (`WebhookMetadata#shop`) is taken from an unauthenticated HTTP header. The HMAC never binds the header-derived shop to the body it protects, breaking the identity equality: `shop asserted to the app handler == shop that produced the signed payload`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns just the raw body — it does not incorporate `shop`, `topic`, `webhook_id`, or `api_version`: [2](#0-1) 

Those fields are read straight from attacker-visible/attacker-settable HTTP headers with no cryptographic binding to the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then hands the *unauthenticated* `request.shop` straight to the app's handler as the tenant identity for the payload: [4](#0-3) 

Because Shopify webhook HMACs are computed with the app's single `client_secret`/`api_secret_key`, shared across *every* shop that installs the app — not a per-shop secret — a valid HMAC only proves "this body was signed by someone who possesses this app's shared secret," which every merchant installation legitimately receives from Shopify. It proves nothing about *which* shop the body belongs to; that binding exists only in the unsigned `shop-domain` header.

### Impact Explanation
An unprivileged internet user who installs the target app on their own store (a fully legitimate, low-privilege action available to anyone) receives genuine Shopify webhooks with a valid HMAC computed under the app's shared secret. They can capture `raw_body` + `hmac` from their own store's webhook delivery, then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with the victim merchant's domain. `HmacValidator.validate` still passes (body untouched), so `Registry.process` dispatches to the handler with `WebhookMetadata#shop` equal to the victim's domain while `body` is attacker-controlled content originating from the attacker's own shop. Any host app that uses `data.shop` to select the tenant/session context to persist or act on `data.body` will attribute attacker-controlled data to the victim's tenant — cross-tenant data confusion/injection.

### Likelihood Explanation
The precondition (installing the app on one's own store) is available to any unprivileged user and requires no leaked credentials or privileged account. Capturing one's own valid webhook body+HMAC and replaying it with a modified header requires only basic HTTP tooling; the gem performs no defense against it because it never signs the header fields.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-covered signable string, or require callers to independently verify `request.shop` against the shop associated with the session/store the handler is about to act on before trusting `WebhookMetadata#shop` for tenant resolution. At minimum, document that `request.shop` is unauthenticated and must be cross-checked by the host application against a known, previously-established shop record before use.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(app_secret, B)`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the identical `B` and `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only checks `B` against `H` — passes.
5. `request.shop` returns `"victim.myshopify.com"` (attacker-supplied), and the handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's own shop's parsed body>, ...)`, causing the app to process attacker-controlled data under the victim's tenant context.
