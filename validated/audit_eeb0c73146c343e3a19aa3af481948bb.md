### Title
Reachable arithmetic-underflow panic in `canGraduate` / `_prepareGraduationLiquidity` bricks a token's curve permanently - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate`, `Bonding.previewLtUntilGraduation`, and `Bonding._prepareGraduationLiquidity` all compute `realLtRaised`/`ltFromPair` as `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with an unchecked Solidity subtraction. `_launchTimeVirtualLtReserve` derives the launch-time virtual LT reserve as `Pair.k() / Token.TOTAL_SUPPLY()` [1](#0-0) , an exact rational value, while the live `assetReserve` is only ever mutated by `Pair.swap`, which enforces the K-invariant with a `+1` slack on both reserves rather than the exact product [2](#0-1) . That `+1` slack lets `newAssetReserve` settle marginally below the exact `k / tokenReserve` value the curve was seeded with, which is exactly the value `_launchTimeVirtualLtReserve` reconstructs. An unprivileged trader who buys the curve's tokens and sells them back to the boundary where `tokenReserve` returns to `TOTAL_SUPPLY` can push `assetReserve` to sit fractionally under `virtualLtReserve`, making `assetReserve - _launchTimeVirtualLtReserve(...)` underflow and panic (`Panic(0x11)`), exactly the "reachable assertion" bug class in the reference advisory (an internal invariant assumed always non-negative that a remote/unprivileged caller can violate through ordinary protocol calls).

### Finding Description
`canGraduate` reads:
```
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [3](#0-2) 

and `_prepareGraduationLiquidity` performs the identical subtraction to compute `ltFromPair` during graduation [4](#0-3) , as does `previewLtUntilGraduation` [5](#0-4) .

The developer comments themselves acknowledge this class of risk elsewhere: `finalizeGraduation` explicitly switches to a *saturating* subtract for an analogous LT-balance comparison specifically "to keep finalize from bricking on a Panic if any future code path ... briefly violates the invariant" [6](#0-5) . The `canGraduate` / `_prepareGraduationLiquidity` / `previewLtUntilGraduation` subtractions were not given the same treatment, even though they rely on the same non-atomic identity: `Pair.k()` is fixed forever at `mint`-time as `tokenReserve_init * assetReserve_init` [7](#0-6) , while `Pair.swap`'s invariant check only guarantees `(newTokenReserve+1)*(newAssetReserve+1) >= k`, not `newTokenReserve*newAssetReserve >= k`. This `+1/+1` looseness (also used by `Router._computeSell` to price sells [8](#0-7) ) permits `newAssetReserve` to fall slightly below the exact `k / newTokenReserve` ratio as `newTokenReserve` approaches its ceiling (`TOTAL_SUPPLY`, reached when all curve-bought tokens are sold back to the pair). At that boundary, `assetReserve` can land strictly below `k / TOTAL_SUPPLY` == `_launchTimeVirtualLtReserve`, causing the unchecked subtraction to underflow.

`canGraduate` is not an isolated view — it is invoked from every hot trading path:
- After every buy, via `_executeBuy` [9](#0-8) 
- On every sell [10](#0-9) 
- On the permissionless `triggerGraduation` [11](#0-10) 

Once the underflow condition is hit, `canGraduate` reverts with a panic on every subsequent call, which means **every** subsequent `buy`, `sell`, and `triggerGraduation` for that token reverts as well — the curve becomes permanently un-tradable and un-graduatable, freezing all creator/trader LT and the 250M curve-side tokens locked in the `Pair` with no recovery path (there is no owner rescue for a `Pair` in `Curve`/stuck lifecycle).

### Impact Explanation
This permanently bricks a launched token's curve: all further `Zap.buy`/`Zap.sell` calls and `triggerGraduation` revert, and the token can never graduate, permanently freezing the real LT raised by traders and the tokens/LT reserved on the curve inside `Pair`. This matches the "permanent freezing of trader, creator or LP funds" acceptance criterion.

### Likelihood Explanation
Reaching the exact 1-wei boundary requires precise manipulation of buy/sell sizes to drive `tokenReserve` back to `TOTAL_SUPPLY` at a rounding point where the `+1` K-slack yields `assetReserve` just below `virtualLtReserve`. This is arithmetically tight and requires careful crafting (an unprivileged attacker computing exact buy/sell amounts against `Router._computeBuy`/`_computeSell`'s rounding), so likelihood is lower than a trivially-reachable bug, but it is reachable purely through permissionless `Zap.buy`/`Zap.sell` calls with no privileged capability required, matching the reachable-assertion class of the reference report (attacker-controlled routine call hits an unguarded arithmetic assumption).

### Recommendation
Replace the unchecked subtractions in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` with saturating subtraction (as already done for the `ltBalance`/`p.ltFromPair` comparison in `finalizeGraduation`), or tighten `Pair.swap`'s invariant check to eliminate the `+1/+1` slack allowing `assetReserve` to dip below the exact seeded ratio.

### Proof of Concept
1. A token launches via `Zap.createToken`, seeding `Pair` with `tokenReserve_init = TOTAL_SUPPLY`, `assetReserve_init = virtualLtReserve`, `k = TOTAL_SUPPLY * virtualLtReserve` [12](#0-11) .
2. An unprivileged trader buys the full `curveSupply` (75% of `TOTAL_SUPPLY`) via `Zap.buy`/`Bonding.buy`, driving `tokenReserve` down and `assetReserve` up along the curve.
3. The same trader sells the tokens back via `Zap.sell`/`Bonding.sell`, driving `tokenReserve` back up toward `TOTAL_SUPPLY`. Because `Router._computeSell`'s `assetOut = reserveAsset - (k / newReserveToken)` uses floor division while `Pair.swap`'s K-check only requires `(newTokenReserve+1)*(newAssetReserve+1) >= k`, a sell sized to land `newTokenReserve` at (or asymptotically near) `TOTAL_SUPPLY` can legally reduce `newAssetReserve` to 1 wei below `k / TOTAL_SUPPLY`.
4. Any subsequent call touching `canGraduate(token)` — the very next `buy`, `sell`, or `triggerGraduation` — executes `assetReserve - _launchTimeVirtualLtReserve(...)` with `assetReserve < _launchTimeVirtualLtReserve`, underflows, and reverts with `Panic(0x11)`, permanently DoS'ing the token's curve.
