### Title
Surplus-share obligation can be permanently zeroed via a dust partial fill on `IntrinsicIntents._fillSameChain` - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` only computes and distributes solver-overpayment ("surplus") to the beneficiary/protocol when the output-token pair has never been partially filled before (`alreadyFilled == 0`). A solver can submit a trivial dust fill for that output pair first, which sets `_partialFills[commitment][outputToken]` to a non-zero value without triggering the surplus branch, and then complete the remainder of the order in a follow-up fill. Because `alreadyFilled != 0` on the second fill, the surplus-computation branch is structurally unreachable, so any amount above `remaining` the solver could have paid is simply never taken from them and the beneficiary/protocol split defined by `surplusShareBps` is permanently bypassed — the exact "collect the accrued value through an intervening low-cost operation that resets the delta the penalty/fee logic keys off of" pattern described in the JIT liquidity penalty report.

### Finding Description
`_fillSameChain` computes surplus only in this branch: [1](#0-0) 

```
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
...
if (alreadyFilled == 0 && solverAmount > totalRequired) {
    fillAmount = totalRequired;
    (protocolShare, beneficiaryShare) =
        _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);
} else {
    fillAmount = solverAmount > remaining ? remaining : solverAmount;
}
```

The surplus split (`_splitSurplus`, which divides overpayment between the beneficiary and the protocol per `surplusShareBps`) is gated on `alreadyFilled == 0` — i.e., it applies "only on the first fill of each output token pair," as documented: [2](#0-1) 

Because `fillAmount` is capped to `remaining` once `alreadyFilled != 0`, any amount the solver is willing to overpay beyond `remaining` is never transferred and never split — it is simply discarded from consideration, not collected as protocol dust. A solver that wants to avoid sharing overpayment with the beneficiary/protocol can:

1. Call `fillOrder` with a dust `solverAmount` (e.g., 1 wei) for the target output pair. Since `solverAmount` is not `> totalRequired`, the surplus branch never triggers, but `_partialFills[commitment][outputToken]` becomes non-zero (`alreadyFilled = 1 wei`), and `isFullyFilled` becomes `false`, so the order remains open (`delete _filled[commitment]` runs, per lines 134-137).
2. Call `fillOrder` again (in a second transaction, from the same or a different address they control) to complete the remaining amount. Now `alreadyFilled != 0`, so the `if (alreadyFilled == 0 && ...)` branch can never execute regardless of how much the solver is economically willing to overpay — `fillAmount` is simply capped at `remaining` and the surplus-share mechanism is permanently disabled for that pair.

This mirrors the JIT liquidity penalty bypass exactly: a strategically timed, minimal, and cheap prerequisite operation (`increaseLiquidity` with 1 wei / a dust `fillOrder`) resets the state that the "penalty"/fee-owed logic keys off of (`feesOwed` / `alreadyFilled == 0`) before the real value-generating operation (`removeLiquidity` / the full fill) executes, so the redistribution mechanism computes zero even though it should have applied.

### Impact Explanation
The surplus-sharing mechanism exists specifically to give the order's beneficiary and the protocol a cut when a solver is willing to pay more than the order strictly requires (this happens for oracle-priced or best-execution-style intents where a solver might route through a better price and capture excess). Bypassing it via a dust first fill lets any solver capture 100% of the overpayment for itself instead of splitting it per `surplusShareBps`, permanently denying the beneficiary and the protocol treasury value they are entitled to on every affected order. This is a repeatable, cost-free (dust-amount) griefing/self-dealing vector reachable by any unprivileged solver on a single ordinary intent fill, with concrete economic loss to intent users and protocol revenue (dust sweep to treasury). This is a Medium/High-severity value-diversion bug.

### Likelihood Explanation
High likelihood: any solver filling a same-chain order can trivially perform a dust partial fill before the real fill, with no special privileges, front-running requirements, or complex timing — only two ordinary `fillOrder` transactions for the same commitment. It requires no cooperation from the order's user and no external conditions besides `order.output.call.length == 0` (calldata orders already forbid partial fills, so this only affects non-calldata orders, which is the common case for plain swaps/intents).

### Recommendation
Do not key the surplus-eligibility check purely on whether the specific output pair has ever received any fill (`alreadyFilled == 0`). Instead, either (a) always compute and split any amount paid above `remaining` on every fill regardless of `alreadyFilled`, so overpayment on a later fill is still shared per `surplusShareBps`, or (b) require that surplus can only be forfeited if the *first* fill for that pair fully completes it (i.e., disallow the state where a partial dust fill can precede a large payment without capturing any excess above `remaining`). The safest general fix is to remove the `alreadyFilled == 0` short-circuit and instead compute `protocolShare`/`beneficiaryShare` from `solverAmount - fillAmount` whenever `solverAmount > remaining`, on every fill, not just the first.

### Proof of Concept
1. User places a same-chain order requiring `1000 DAI` output for `1000 USDC` input, with `surplusShareBps` configured to split overpayment 50/50 between beneficiary and protocol, and no output calldata.
2. Attacker-controlled solver A calls `fillOrder` with `outputs[0].amount = 1` (1 wei of DAI). `alreadyFilled == 0` but `solverAmount (1) <= totalRequired (1000e18)`, so the `else` branch runs: `fillAmount = 1`. `_partialFills[commitment][DAI]` becomes `1`. `isFullyFilled = false`, so `_filled[commitment]` is deleted and the order stays open (see [3](#0-2)  and [4](#0-3) ).
3. Attacker-controlled solver B (or A again) calls `fillOrder` offering `outputs[0].amount = 1100e18` DAI (100 DAI "surplus" they were willing to pay). Now `alreadyFilled = 1 wei != 0`, so the `if (alreadyFilled == 0 ...)` branch is skipped entirely; `remaining = totalRequired - 1`, and `fillAmount = min(solverAmount, remaining) = remaining`. The solver only ever transfers `beneficiaryTotal = fillAmount` (no `protocolShare`, no `beneficiaryShare`), completing the order for effectively the exact required amount and keeping any willingness-to-overpay entirely off-chain/unrealized instead of splitting it as intended.
4. Result: the beneficiary and protocol never receive the 50/50 split of the 100 DAI surplus that `testPartialFill_SurplusOnFullFill` (evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1544-1572) shows would normally be collected on a genuine single-shot overpaid fill. The existing test `testPartialFill_SurplusOnlyWhenNotPartiallyFilled` (evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1506-1542) already demonstrates and asserts this exact "no surplus on partially filled pair" behavior — confirming the bypass is reachable and reproducible on-chain today.
