### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `hmac` and `to_signable_string` values solely from the raw request body, while the `shop` (tenant identifier) is read from an unauthenticated header. `Webhooks::Registry.process` validates only the HMAC-over-body and then dispatches the handler using this unauthenticated `shop` value, breaking the intended binding `HMAC-verified bytes == data acted upon`.

### Finding Description
For OAuth callbacks, `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed string: [1](#0-0) 

By contrast, for webhooks, `Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `shop` is read straight from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, entirely outside the signed material: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only compares the HMAC computed over `to_signable_string` (i.e., only the body) against the received `hmac`: [4](#0-3) 

`Webhooks::Registry.process` calls this validator and, once it passes, hands the handler the unauthenticated `request.shop` value as the tenant identity for the event: [5](#0-4) 

**Binding that should hold:** `hmac_valid(raw_body) == true` should imply `(raw_body, shop_header)` as a whole were produced by Shopify for that specific shop. Instead the gem's actual binding is `hmac_valid(raw_body) == true` regardless of `shop_header`, i.e. the `shop` field is "acted on but not covered by the HMAC."

**Exploit path:** any party that has ever received one legitimately-HMAC-signed webhook delivery for their own shop (e.g., a malicious merchant who installed the app) possesses a `(raw_body, hmac)` pair that is valid forever for that body, independent of the `shop-domain` header. They can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim's `victim-shop.myshopify.com`). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata` carrying the forged `shop`, causing the host application's webhook handler to process/attribute data under another tenant's identity.

### Impact Explanation
This is a cross-tenant boundary break: the gem provides no cryptographic assurance that the `shop-domain` header genuinely corresponds to the HMAC-signed payload, so an attacker in control of one legitimate webhook delivery can impersonate any other shop to any handler that trusts `WebhookMetadata#shop` (the standard integration pattern documented for this gem, per `Registry.process`/`handler.handle`). Any host application storing/routing data by that `shop` value (order updates, uninstall/GDPR events, etc.) can be tricked into acting on forged data attributed to a different merchant, meeting the "cross-tenant access" Critical bar.

### Likelihood Explanation
Requires an attacker to have obtained at least one genuine webhook body+HMAC pair addressed to their own store (trivial for anyone who installs the app, since all merchants receive live webhooks), plus the ability to POST to the app's public webhook endpoint with a spoofed header — both are unprivileged, internet-reachable actions with no secret material needed. The `shop` header spoof itself requires no cryptographic work.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) values in the signed material verified against the HMAC, or otherwise cryptographically bind the header-derived tenant identity to the HMAC-covered body before it is trusted in `Webhooks::Registry.process`/`WebhookMetadata`. At minimum, document that host applications must independently re-verify the `shop` against an internally tracked value and must not treat `request.shop` as trusted merely because `HmacValidator.validate` succeeded.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives (or forges by controlling their own shop's data) a legitimate webhook delivery:
   - `raw_body = '{"id":1,"note":"hi"}'`
   - `hmac = Base64(HMAC-SHA256(raw_body, api_secret_key))` (computed and sent by Shopify, unknown secret to attacker but the resulting header value is observed).
2. Attacker replays to the app's webhook endpoint the exact same `raw_body` and `hmac` header, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Webhooks::Request.new(raw_body:, headers:)` builds a request whose `shop` returns `"victim-shop.myshopify.com"`. [6](#0-5) 
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `raw_body` (identical to the original valid delivery) and compares against the (still-valid) `hmac`. [7](#0-6) 
5. `handler.handle` is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this payload for that shop. [8](#0-7)
