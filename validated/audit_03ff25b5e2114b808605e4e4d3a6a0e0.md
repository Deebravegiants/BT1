### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` attribute used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant is read from an unsigned HTTP header. Any party able to trigger one legitimate (HMAC-valid) webhook delivery for a shop they control can replay that exact body/HMAC pair while substituting the `shop-domain` header for an arbitrary victim shop, and the gem's own `HmacValidator` will report the request as authentic. This breaks the identity binding `shop_claimed == shop_that_produced_signed_bytes`, exactly the class of bug described in the reference report (a field acted upon but excluded from the cryptographic check).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is derived purely from an attacker-controllable HTTP header, not from anything covered by that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` signs/compares only `verifiable_query.to_signable_string` (i.e., the raw body) against the app's `api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` performs this HMAC check and then immediately trusts `request.shop`, forwarding it uncontested to the app's handler as the tenant identifier: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that handlers should key their per-tenant logic off `data.shop`: [5](#0-4) [6](#0-5) 

Because the same `api_secret_key` is used to validate webhooks for every shop installed on a given app (it is an app-level secret, not per-shop), a valid HMAC for a body proves only "this body was signed by Shopify for this app" — it says nothing about which shop that body was signed for. The `shop` value that callers are told to trust for tenant routing is carried in a plain header that sits entirely outside the signed bytes.

### Impact Explanation
An attacker who legitimately installs the target app on any shop they control (a normal, unprivileged action available to any internet user/developer) can:
1. Trigger a webhook delivery from their own shop (any subscribed topic), capturing the valid `raw_body` + `X-Shopify-Hmac-Sha256` pair Shopify sent to the app's endpoint.
2. Replay that exact body and HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to an arbitrary victim shop's domain.
3. `HmacValidator.validate` still passes (the body/secret pair is unchanged), and `Registry.process` dispatches `WebhookMetadata` claiming to be from the victim shop.

Any app whose webhook handler uses `data.shop` (as the gem's own documentation instructs) to select which merchant's session/records to act on will process attacker-supplied data under the victim's tenant context — e.g., creating/updating records, invalidating caches, or triggering shop-scoped side effects for a shop the attacker never installed the app on and has no access token for. This is a cross-tenant access vulnerability rooted entirely in this gem's verification logic, matching the Critical impact category (cross-tenant access).

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem's documented webhook pattern: the attacker needs only a free/dev Shopify store to install the app and legitimately receive one webhook, then a trivial HTTP replay with a modified header — no access token, no `client_secret`, and no privileged access to the victim shop are required.

### Recommendation
Include the shop domain (and other Shopify-supplied identifying headers, e.g. `webhook-id`, `api-version`) in the HMAC-signed content that `to_signable_string` returns, or otherwise cryptographically bind the claimed `shop` value to the verified payload before it is handed to application handlers, so that `HmacValidator.validate` fails whenever the shop header is altered relative to what was actually signed.

### Proof of Concept
1. Configure `ShopifyAPI::Context` with a real `api_secret_key` for app "MyApp".
2. Install "MyApp" on attacker-owned shop `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g. `products/update`) so Shopify POSTs a body `B` to the app's webhook route with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of B>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Capture `B` and the HMAC value.
4. Re-POST to the same endpoint with the identical body `B` and identical HMAC header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. Observe that `ShopifyAPI::Webhooks::Registry.process`:
   - `Utils::HmacValidator.validate(request)` returns `true` (compares only against `@raw_body`, per `to_signable_string`) — [1](#0-0) 
   - dispatches `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` to the app's handler — [7](#0-6) 

The victim shop's tenant-scoped logic executes on attacker-controlled data, despite the attacker never holding an access token or session for `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
