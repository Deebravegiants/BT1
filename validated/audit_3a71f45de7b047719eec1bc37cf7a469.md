### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` binds only the request body to the app's secret. The `shop-domain` header — which is used unauthenticated as the tenant identity for the webhook handler — is never part of the signed material.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header and `Request#shop` reads the `shop-domain` header independently [1](#0-0) . `to_signable_string` only returns the raw body, excluding the shop header entirely from what is HMAC-signed [2](#0-1) .

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` (i.e., body-vs-hmac) before dispatching the webhook, and then constructs `WebhookMetadata` using `request.shop` taken straight from the unauthenticated header, passing it to the app-registered handler as the trusted tenant identifier [3](#0-2) . `HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and only checks that against the `hmac` field, never referencing `shop` [4](#0-3) .

The identity binding that should hold is:
`shop_header_value == shop_that_the_secret-holder_authenticated_the_body_for`

But because `shop` is excluded from the signed string, the gem only proves:
`hmac == HMAC(secret, body)`

which is independent of `shop`. Since the app's `api_secret_key` is the same secret used for every shop/tenant that has installed the app (it is not per-shop), any party capable of obtaining one genuine `(body, hmac)` pair — e.g., by installing the app on their own store and receiving a legitimate webhook, or by triggering a webhook whose body content they influence — can replay that exact `body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header value naming a different, victim tenant. `HmacValidator.validate` still passes because it never checked the shop field, and `Registry.process` hands the handler a `WebhookMetadata` claiming to be from the victim shop [3](#0-2) .

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an attacker who is merely an unprivileged internet user with a legitimate app installation on their own store can cause the gem to attribute webhook data/actions to a different, victim shop. Any application logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop records, triggering per-shop side effects, or session/data lookups keyed by shop) will operate on the wrong tenant's context, i.e., cross-tenant access/data confusion — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High: exploitation requires only (1) the ability to obtain any one genuine `(raw_body, hmac-sha256)` pair signed by the app's shared secret — trivially available to any developer/store that installs the app themselves and receives real webhooks — and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header, which is standard webhook-endpoint reachability with no other credential required.

### Recommendation
Include the shop identity in the signed material that `HmacValidator` verifies for webhook requests, or otherwise cryptographically/contextually bind the `shop-domain` header to the verified body (e.g., require the receiving application to independently authenticate/allow-list the shop, or have `to_signable_string` incorporate the shop header alongside the body) so that a valid HMAC for one shop's body cannot be replayed as if it originated from another shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`) and registers a webhook, e.g., `orders/create`.
2. Attacker triggers/receives a genuine webhook delivery: raw body `B` and header `shopify-hmac-sha256: H` where `H = Base64(HMAC-SHA256(api_secret_key, B))`, plus `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker crafts a new HTTP POST to the app's public webhook endpoint reusing body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H` [4](#0-3) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [5](#0-4) , causing the app to process attacker-supplied body content under the victim shop's tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
