### Title
Excess native token sent to `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host contract, not the original caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` allow users to pay Hyperbridge fees with native ETH. When `msg.value > 0`, the Host calls `swapETHForExactTokens{value: msg.value}(fee, path, address(this), ...)` on the configured Uniswap V2-compatible router/wrapper. This swap only spends the exact fee amount and refunds any unused ETH to `msg.sender` of that inner call — but `msg.sender` there is `EvmHost` itself (since `EvmHost` is the one calling the router), not the original end user who sent the excess `msg.value` to `dispatch()`/`fundRequest()`. No code afterward forwards this refunded ETH back to the caller.

The identical pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 

And in `fundRequest`: [3](#0-2) 

None of these functions check `msg.value` against `getFee()`-equivalent required amount, nor do they capture/forward the refund produced by the swap. Any wrapper contract used as `_hostParams.uniswapV2` (e.g. `UniV3UniswapV2Wrapper.sol`) explicitly refunds unspent ETH to its immediate caller: [4](#0-3) 

Since `EvmHost` is the direct caller of `swapETHForExactTokens`, that `msg.sender.call{value: refund}("")` sends the refunded ETH to `EvmHost`'s own address, not back to the user who originally overpaid. This ETH then sits in `EvmHost`'s balance with no visible function in the reviewed code to route it back to affected users or explicitly account for it.

This is the same root-cause bug class as the reported AvailBridge issue: a payable entrypoint that accepts `msg.value` for a fee but has no mechanism to return any surplus to the actual payer.

By contrast, the `IntentGatewayV2.placeOrder`/`fillOrder` flows in this same codebase correctly refund unspent `msg.value` back to `msg.sender` after performing the same kind of fee swap: [5](#0-4) 

This shows the pattern is well understood and fixed elsewhere in the codebase, but is missing in `EvmHost.sol`.

### Impact Explanation
Any unprivileged user calling `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` on `EvmHost` with `msg.value` greater than the required fee (e.g., due to slippage buffering, gas-estimation padding, or simply overestimating) will have the excess ETH permanently misdirected to the Host contract instead of refunded to them. Because the Host is the caller of the swap, ordinary users cannot recover this value through any documented user-facing mechanism. This constitutes a direct, permanent loss of user funds — classified High since it is a straightforward, repeatable fund-loss condition reachable by any user dispatching a message with native-token payment.

### Likelihood Explanation
Likelihood is high in practice: docs explicitly instruct integrators to estimate fees off-chain and pad the sent value (`quote()` warnings about sandwich-attack risk encourage buffering), and `HyperbridgeLzEndpoint.sol` itself applies a "generous 2x buffer" when computing native fee quotes for users calling into `dispatch`. Any such buffered overpayment through the raw `EvmHost.dispatch`/`fundRequest` path (as opposed to going through `IntentGatewayV2`, which does refund) will be trapped.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`: after the `swapETHForExactTokens` call, capture the actual returned `amounts[0]` spent (or measure `address(this).balance` delta) and refund any leftover native ETH from `EvmHost` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 2 ether}(post)` where `post.fee` only requires `0.1 ether` worth of `feeToken`.
2. `EvmHost` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: 2 ether}(post.fee, path, address(this), block.timestamp)`.
3. The router/wrapper spends only what's needed to acquire `post.fee` in `feeToken` and refunds the remaining ETH — but to `msg.sender`, i.e., `EvmHost`, per [4](#0-3) .
4. `EvmHost.dispatch` returns without forwarding this refund to the user; the user's excess ~1.9 ether is now held by `EvmHost` and not recoverable by them, matching the exact scenario in the referenced AvailBridge report.
