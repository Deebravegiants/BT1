### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying an HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to attribute the webhook to a specific tenant. This breaks the intended binding `hmac_signed_bytes == bytes_the_shop_field_is_taken_from`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `verifiable_query.to_signable_string` (i.e., the body) against the secret, and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the application handler: [3](#0-2) [4](#0-3) 

The documented handler contract explicitly tells app developers that `data.shop` is "the shop domain of the webhook" and is safe to use as a tenant key (e.g. `shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), an unprivileged user who installs the app on their own shop can receive a genuine, validly-signed webhook (HMAC computed over the raw body with the shared secret). They can then replay that exact raw body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (only the body is checked), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain while `body` contains the attacker's own shop's data. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold, `shop-domain header == hmac-authenticated shop`, does not — the gem authenticates *bytes* but attributes them to an unauthenticated *tenant identifier*.

### Impact Explanation
Any host application that follows the documented pattern of using `data.shop` as a tenant key when persisting/acting on webhook data (as the gem's own documentation instructs) is exposed to cross-tenant data injection/corruption: an attacker-controlled shop's webhook payload can be attributed to and processed against a different, victim tenant's records. This matches the Critical "cross-tenant access" impact category, since it lets one authenticated tenant (the attacker's own shop) inject data attributed to another tenant purely by forging an HTTP header, without needing the app's `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must first be a legitimate, unprivileged install of the target app (to obtain a validly-signed body/HMAC pair for at least one topic/payload), and the impact is contingent on the host app trusting `data.shop` for tenant identification exactly as the gem's own documentation recommends. Given that the doc explicitly instructs developers to key off `data.shop`, this is a realistic, low-effort exploitation path (single header rewrite) once the attacker has a legitimate account.

### Recommendation
Include the `shop-domain` header (and other identity-relevant headers such as `webhook_id`/`api_version` if desired) in the HMAC-covered signable string, or otherwise cryptographically bind the shop identity to the verified payload before constructing `WebhookMetadata`. At minimum, the gem should not read `shop` from an unauthenticated header and hand it to caller code as if it had been verified — either drop the guarantee in documentation or extend `Request#to_signable_string`/`HmacValidator` to cover the shop-domain value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify sends a webhook to the app with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`. Attacker captures `B` and the valid HMAC.
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and same valid HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` passes because only `B` is hashed (`lib/shopify_api/webhooks/request.rb` line 36-38, `lib/shopify_api/utils/hmac_validator.rb` line 27-31).
5. `Registry.process` calls the host app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb` line 198-199), causing the app to process attacker-controlled data under the victim tenant's identity.
