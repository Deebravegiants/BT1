## Finding: Stale `TombStone.original_owner` Allows a Prior Owner to Hijack Objects After Ownership Has Changed

### Title
Object ownership can be hijacked via stale `TombStone` metadata that survives ordinary transfers - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::burn` records the caller as `TombStone.original_owner` but does **not** change `ObjectCore.owner`, and its comment describes it purely as an indexer-visibility flag. Ordinary ownership transfers (`transfer`, `transfer_call`, `transfer_to_object`, all of which route through `transfer_raw_inner`) never inspect or clear this `TombStone`. Only the privileged `transfer_with_ref` path (using a `LinearTransferRef`) clears it. This asymmetry lets a `TombStone` written by owner A survive an arbitrary number of subsequent, fully legitimate ownership transfers, and later be honored by `unburn` even though the object's current true owner is unrelated to A.

### Finding Description
- `burn<T>(owner, object)` (object.move:645-651) requires `owner` to be the current owner, then `move_to(&create_signer(object_addr), TombStone { original_owner })` — it does **not** touch `ObjectCore.owner` or `allow_ungated_transfer`. [1](#0-0) 

- Ordinary transfers go through `transfer_raw` → `transfer_raw_inner`, which only reads/writes `ObjectCore.owner` and emits a `Transfer` event. It has no awareness of `TombStone` at all: [2](#0-1) 

- By contrast, the privileged `transfer_with_ref` (only reachable via a `TransferRef`/`LinearTransferRef` that the object creator/owner explicitly generated) *does* clean up a stale `TombStone`: [3](#0-2) 

- `unburn<T>(original_owner, object)` (object.move:654-676) trusts the stored `TombStone.original_owner` field when the object's current owner is `BURN_ADDRESS`, and transfers the object back to that stored address without verifying any chain-of-custody since the `TombStone` was created: [4](#0-3) 

**Attack trace:** Owner A calls `object::burn` on an object they own (adds `TombStone{original_owner: A}`, owner remains A, ungated transfer is still enabled). A then legitimately sells/transfers the object via ordinary `object::transfer` to B (ungated transfer is not disabled by `burn`, so this succeeds and the stale `TombStone` is not cleared). B, now the rightful owner, later transfers the object to `BURN_ADDRESS` through an ordinary `transfer` call (e.g., as part of an application's own "burn" UX, or an accidental/legitimate disposal) — this also does not clear or check `TombStone`. At this point `ObjectCore.owner == BURN_ADDRESS` and the stale `TombStone{original_owner: A}` is still present. A now calls `unburn(A, object)`; since `owner == BURN_ADDRESS` and `TombStone.original_owner == A`, the check passes and the object is transferred back to A — even though A had no ownership claim at the time B sent it to `BURN_ADDRESS`.

### Impact Explanation
This breaks the object-ownership custody invariant that object control should track the current, legitimate owner. A former owner (A) can reclaim an object/asset that a legitimate subsequent owner (B) intentionally sent to the canonical burn address, effectively stealing value or NFTs/objects that B believed were destroyed or under their sole control, and destroying B's own recovery rights simultaneously. Because objects can hold fungible-asset stores, token objects, or other value-bearing resources, this can result in outright theft/misdirection of custody for any asset routed through the standard object-transfer/burn model.

### Likelihood Explanation
The preconditions are simple and require no privileged access: any account can call `object::burn` on an object it owns, then transfer that object normally any number of times, and any subsequent owner sending it to `BURN_ADDRESS` via a plain transfer (not the explicit burn/unburn flow) reactivates the stale tombstone. Given `burn`/`transfer`/`unburn` are all public entry functions with no special permissions, this is exploitable by any unprivileged user who previously owned the object.

### Recommendation
- Clear (`move_from<TombStone>`) any existing `TombStone` on every ownership-changing path, not just `transfer_with_ref`. Specifically, `transfer_raw_inner` should remove a stale `TombStone` whenever `object_core.owner` actually changes, mirroring the logic already present in `transfer_with_ref` (object.move:529-532).
- Alternatively, bind the `TombStone.original_owner` check in `unburn` to also assert that no ownership transfer has occurred since the tombstone was created (e.g., store the owner at burn time and require it still equals the value directly preceding the `BURN_ADDRESS` transfer), or disallow `unburn`'s address-recovery branch entirely for objects that changed hands since burning.

### Proof of Concept
1. A creates/owns `Object<T>` at address `obj`.
2. A calls `object::burn(A, obj)` → `TombStone{original_owner: A}` stored at `obj`; `ObjectCore.owner` stays `A`.
3. A calls `object::transfer(A, obj, B)` (ordinary ungated transfer) → `ObjectCore.owner = B`; `TombStone{original_owner: A}` unchanged/stale.
4. B, unaware of the stale tombstone, calls `object::transfer(B, obj, BURN_ADDRESS)` to intentionally destroy/burn the object → `ObjectCore.owner = BURN_ADDRESS`.
5. A calls `object::unburn(A, obj)`. Since `ObjectCore.owner == BURN_ADDRESS` and `TombStone.original_owner == A`, the check at object.move:665-672 passes and `transfer_raw_inner(obj, A)` executes, returning the object/asset to A instead of leaving it burned or returning it to B.

Note: This analysis is based on directly-read source in `object.move`. I was not able to fully trace whether `primary_fungible_store::burn_object_with_transfer` (which also references this mechanism, per `aptos-move/framework/aptos-framework/sources/primary_fungible_store.move`) adds any additional safeguards that could mitigate this path for fungible-asset-holding objects specifically — a background agent should verify that call site as well before treating this as fully confirmed end-to-end for FA custody.     public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
        };

        let object = borrow_global_mut<ObjectCore>(self.self);
        assert!(
            object.owner == self.owner,
            error::permission_denied(ENOT_OBJECT_OWNER),
        );
        event::emit(
            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }

        let original_owner = signer::address_of(owner);

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
