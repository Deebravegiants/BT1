### Title
Overflowing scaled debt valuation permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts aggregate scaled debt and supply back to RAY-denominated value through `scaled_to_original`, which performs checked `scaled * index` arithmetic over `i128`. [1](#0-0) [2](#0-1)  Large markets can overflow this aggregate valuation before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`, so the index cap does not protect the protocol. [3](#0-2) [4](#0-3)  Once the boundary is crossed, every pool operation that accrues the market reverts before committing, permanently freezing withdrawals, repayments, liquidations, and further index updates. [5](#0-4) [6](#0-5) 

### Finding Description
`accrue_step` first evaluates `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`, then computes interest and revalues debt again inside `calculate_supplier_rewards`. [7](#0-6) [8](#0-7)  `scaled_to_original` delegates to `Ray::mul`, whose multiply-divide operation panics with `MathOverflow` when the resulting aggregate value cannot fit `i128`. [2](#0-1) [9](#0-8)  The code bounds the index itself at `MAX_BORROW_INDEX_RAY`, but does not bound `borrowed * borrow_index`, which is the quantity that actually overflows. [10](#0-9) 

`global_sync` calls `accrue_step` for each elapsed chunk and marks the market accrued only after all chunks complete, so the panic leaves `last_timestamp` and the stored indexes unchanged. [5](#0-4) [11](#0-10)  Consequently, the next operation starts from the same state and reaches the same overflowing conversion again. [12](#0-11) 

The user-facing path is reachable through `Controller::supply`, `Controller::borrow`, and the permissionless keeper-style `Controller::update_indexes`, which only requires the caller's authorization before forwarding the request to the pool. [13](#0-12) [14](#0-13)  `withdraw` and `repay` are also exposed to ordinary users, while `liquidate` is permissionless. [15](#0-14)  These pool legs load the market through `ops::load_leg`, whose documented behavior accrues interest before mutation. [16](#0-15) [17](#0-16) [18](#0-17) [19](#0-18) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected market rather than a request-local denial of service. [5](#0-4)  Suppliers cannot withdraw their remaining claims, borrowers cannot repay or close debt, and liquidators cannot execute liquidation because each path attempts the same accrual first. [4](#0-3)  Pool cash and scaled user balances remain locked under a market state that can no longer be advanced or safely unwound. [20](#0-19) [21](#0-20) 

### Likelihood Explanation
Reaching the condition requires a very large market and sustained outstanding debt, but those inputs are within the protocol's scaled accounting domain and do not require privileged calls, leaked keys, oracle dishonesty, or malformed token semantics. [22](#0-21)  A funded unprivileged address can create separate owned accounts for liquidity and borrowing, execute `supply` and `borrow`, and later submit `update_indexes` or simply let the next ordinary market operation trigger accrual. [13](#0-12) [14](#0-13)  The in-repository regression test demonstrates that the aggregate value overflows before the borrow-index ceiling and that subsequent withdrawal and repayment attempts return `MathOverflow`. [23](#0-22) 

### Recommendation
Widen aggregate `scaled * index` valuation and interest-delta calculations to an `I256` intermediate or another representation that can safely span the configured maximum index and share totals. [24](#0-23) [8](#0-7)  If `i128` remains the accounting bound, enforce a stronger market invariant such as `borrowed * MAX_BORROW_INDEX_RAY / RAY <= i128::MAX` and the corresponding supply-index bound at every share-minting path, including protocol-revenue mints. [3](#0-2) [25](#0-24)  Merely capping the index is insufficient because stored share totals can make the aggregate valuation overflow before the index reaches its cap. [26](#0-25) 

### Proof of Concept
The following sequence uses one unprivileged caller that owns two accounts, mirroring the funded supplier and borrower roles exercised by the existing regression test. [27](#0-26) 

```rust
let target = HubAssetKey {
    hub_id: HUB_ID,
    asset: big18_asset,
};
let collateral = HubAssetKey {
    hub_id: HUB_ID,
    asset: collateral_asset,
};

let target_amount: i128 = 1_000_000_000i128 * 10i128.pow(18);
let collateral_amount: i128 = 3_000_000_000i128 * 10i128.pow(7);

// One unprivileged caller creates a supplier account.
let supplier_id = controller.supply(
    attacker.clone(),
    0,
    SPOKE_ID,
    vec![(target.clone(), target_amount)],
);

// The same caller creates a separate borrower account with collateral.
let borrower_id = controller.supply(
    attacker.clone(),
    0,
    SPOKE_ID,
    vec![(collateral.clone(), collateral_amount)],
);

// Borrow 98% of the supplied target liquidity.
controller.borrow(
    attacker.clone(),
    borrower_id,
    vec![(target.clone(), target_amount * 98 / 100)],
    Some(attacker.clone()),
);

// After ledger time advances at sustained utilization, the next accrual
// makes borrowed_scaled * new_borrow_index / RAY exceed i128::MAX.
controller.update_indexes(attacker.clone(), vec![target.clone()]);
// => MathOverflow

// The stored state remains unaccrued, so later user paths hit the same panic.
controller.withdraw(attacker.clone(), supplier_id, vec![(target.clone(), 0)], None);
// => MathOverflow

controller.repay(attacker.clone(), borrower_id, vec![(target.clone(), 1)]);
// => MathOverflow

controller.liquidate(
    attacker,
    borrower_id,
    vec![(target, 1)],
    SeizeMode::Transfer,
);
// => MathOverflow before liquidation accounting
```

This behavior is directly represented by `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which asserts `MathOverflow` on `update_indexes`, `withdraw`, and `repay` before the index ceiling is reached. [28](#0-27)

```rust
/// Accrues interest, resolves the repay amount into burned debt shares and
/// overpayment, burns the shares, and credits the net repay to cash without
/// transferring the overpayment refund. Panics if a positive net repay would
/// burn zero scaled shares.
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
```
