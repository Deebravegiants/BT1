Found the analog. `session_id_from_shopify_id_token` derives the session id directly from the `shop`/`sub` claims of a JWT signed by `Context.api_secret_key`, and the JWT payload's `iss` and `dest` (the source of `shop`) are never checked against `ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Title
Session-token `dest`/`shop` claim is trusted to build the session key without domain validation - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`SessionUtils.session_id_from_shopify_id_token` builds the session lookup key (`"#{shop}_#{user_id}"` or `"offline_#{shop}"`) purely from the JWT `dest` claim (`payload.shop`), never running it through `ShopValidator.sanitize_shop_domain`/`TRUSTED_SHOPIFY_DOMAINS`, unlike the OAuth callback and other flows that do sanitize shop input.

### Finding Description
`Auth::JwtPayload#initialize` decodes the token with `Context.api_secret_key` and only checks that `aud == Context.api_key` [1](#0-0) . It never validates `iss`/`dest` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, unlike `Auth::Oauth.validate_auth_callback`/`ShopValidator` elsewhere in the gem which explicitly sanitizes shop input against `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [2](#0-1) .

`SessionUtils.session_id_from_shopify_id_token` then takes `payload.shop` (which is just `@dest.gsub("https://", "")`, i.e. attacker-influenced/host-application-supplied claim data) and uses it verbatim as the session identifier for both online (`jwt_session_id`) and offline (`offline_session_id`) sessions [3](#0-2) .

The identity binding that should hold is: `session_id == f(shop_that_was_actually_verified_as_a_trusted_myshopify_tenant)`. Instead the binding is `session_id == f(dest_claim_as_written_by_whoever_can_get_the_gem's_own_api_secret_key_to_sign_a_token)`. Since the only claim checked is `aud == api_key` (a public value, the app's client id, not a secret) and there is no cryptographic tie between the HMAC of a specific merchant/tenant and the `dest`/`shop` value stored inside it, nothing in this gem enforces that `dest` is a genuine `*.myshopify.com` (or other trusted) domain. The value is used to derive/collide with another tenant's session id.

### Impact Explanation
This maps to a scope/tenant-binding issue: the session key derivation trusts an unvalidated claim (`dest`) rather than a value proven to be a real, trusted Shopify shop domain, which is analogous to "a JWT claim trusted without being bound" and "a session id derived from unauthenticated/unverified bytes" listed in the rules. If a host application or an upstream component ever forwards session tokens whose `dest` was not independently confirmed to be a `myshopify.com` domain (e.g. a token for one tenant reused/crafted with a different `dest` value under the same signing key, or a proxy that mints tokens with attacker-influenced `dest`), the gem will happily compute a session id for that manipulated shop domain and let calling code merge/create sessions under it — a cross-tenant session collision.

### Likelihood Explanation
Likelihood is low-to-moderate on its own within this gem, because exploiting it in the strict "unprivileged internet user" sense requires a means to get a validly-signed JWT (signed with `Context.api_secret_key`) with an attacker-chosen `dest` — which normally only Shopify or the app itself can produce. However, this is exactly the same class of gap the report highlights: a value used to derive/aggregate a critical accounting or identity number is not cross-checked against the source of truth (`ShopValidator`) even though the sibling OAuth path enforces that check. Given the gem exposes `ShopValidator` specifically for this purpose but never applies it in the JWT/session path, this is a real, in-scope binding gap.

### Recommendation
Validate `dest`/`iss` in `JwtPayload` (or in `SessionUtils.session_id_from_shopify_id_token`) against `ShopifyAPI::Utils::ShopValidator.sanitize_shop_domain` before using it to build session identifiers, mirroring the sanitization already performed for OAuth callback shop values.

### Proof of Concept
1. Obtain/produce a session token whose `dest` claim is `https://attacker-controlled-or-mismatched-value` while `aud` still equals the app's `api_key` (e.g., via any code path where a caller supplies an id token — direct JWT forgery is not possible without the secret, but any component that lets `dest` be set independently of a confirmed trusted domain reaches this gap).
2. Call `ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token(id_token: token, online: false)` [4](#0-3) .
3. Observe the returned session id `"offline_#{shop}"` is derived straight from `dest` with no check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [2](#0-1) , unlike the OAuth flow which sanitizes shop values before establishing a session.

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

        sig { params(shop: String, user_id: String).returns(String) }
        def jwt_session_id(shop, user_id)
          "#{shop}_#{user_id}"
        end

        sig { params(shop: String).returns(String) }
        def offline_session_id(shop)
          "offline_#{shop}"
        end
