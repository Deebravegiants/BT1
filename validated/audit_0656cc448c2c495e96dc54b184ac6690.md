### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never included in the signed payload. `Registry.process` validates the HMAC and then trusts `request.shop` unconditionally when building `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle`.

### Finding Description
`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` accessor [3](#0-2) . For webhooks, `Request#to_signable_string` is defined as just `@raw_body` [4](#0-3) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled from HTTP headers via `shopify_header` [5](#0-4) , none of which participate in the signed string.

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the body+secret produce the given `hmac-sha256` header) before immediately trusting `request.shop` to build the `WebhookMetadata` struct passed to the app's handler [1](#0-0) . The `shop` field of `WebhookMetadata` is a plain `String` with no further validation [6](#0-5) .

The binding this breaks, expressed as an equality that should hold but doesn't:
`shop_that_produced_the_signed_body == shop_attributed_to_the_request_by_the_library (request.shop)`

Before the attack: a legitimate webhook for shop A produces `(raw_body_A, hmac_A)` where `hmac_A = HMAC(secret, raw_body_A)`, and headers correctly say `shop-domain: A`.

After the attack: an attacker who owns shop A (e.g., installs the app on their own store, a completely unprivileged/free action) captures a real `(raw_body_A, hmac_A)` pair from any webhook topic they can trigger, then replays it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to `B` (victim's shop). Since `hmac_A` only certifies `raw_body_A`, not the shop header, `HmacValidator.validate` still succeeds, and `Registry.process` builds `WebhookMetadata.new(shop: "B", body: parsed(raw_body_A), ...)`, misattributing attacker-controlled content to a victim tenant.

The library's own documentation instructs apps to trust `data.shop` for tenant scoping (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing the assumption that this field is authenticated the same way the body is—but it is not.

### Impact Explanation
This breaks the tenant/shop identity binding that the whole webhook subsystem is meant to guarantee, letting an attacker (who only needs to be able to trigger any webhook for a shop they control, which requires no privilege beyond installing/using the app on their own store) inject attacker-chosen webhook bodies attributed to an arbitrary victim shop domain. Depending on how the host app uses `data.shop` (as the docs demonstrate—for job scoping, record lookups, cache keys, etc.), this can lead to cross-tenant data corruption/injection: e.g., forging `app/uninstalled` to make the app tear down a victim's stored session/access token, or forging `orders/create`/`customers/update` bodies to be processed under a victim shop's record. This is a cross-tenant access issue at the credential/tenant boundary this gem is responsible for enforcing.

### Likelihood Explanation
High. No secret knowledge is required—only the ability to receive one legitimate webhook HMAC+body pair from any shop (trivial, e.g. by installing a free/dev app instance on an attacker-controlled store) and the ability to POST an HTTP request with custom headers to the app's public webhook endpoint, which is inherent internet-reachable functionality.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signed content that `to_signable_string` returns, or otherwise cryptographically bind them to the verified body (e.g., HMAC over a canonical concatenation of headers + body) so an attacker cannot mix a valid signature for one shop's payload with a forged shop-domain header. At minimum, document prominently that `data.shop`/`request.shop` is unauthenticated and must not be trusted for tenant scoping without independently confirming the shop is one that legitimately installed the app and matches out-of-band metadata.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook topic (e.g. `app/uninstalled` or `orders/create`), capturing the real request: body `B` and header `x-shopify-hmac-sha256: H` where `H = Base64(HMAC-SHA256(secret, B))`.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (using only `@raw_body`), matches `H`, and returns `true` [7](#0-6) .
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_from_attacker, ...)` [1](#0-0) , causing the host app to process attacker-controlled data under the victim tenant's identity.
