### Title
Webhook `shop-domain` is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating the HMAC-SHA256 signature over the **raw request body only**, then trusts the `shop-domain` header — which is completely outside the signed material — to decide which tenant/shop the event belongs to. Because the app's `api_secret_key` is shared across every shop that has the app installed, any merchant who has the app installed on their own store (an "unprivileged internet user" from the app's perspective — anyone can install a public app on a free dev store) can obtain a genuinely-signed webhook body+HMAC pair for their own shop, then replay that identical body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value naming a different, victim shop. The signature check still passes because the header is never part of the signed string, so the handler is invoked believing the event originated from the victim shop.

### Finding Description
`Request#to_signable_string` (used by `Utils::HmacValidator`) only returns the raw JSON body: [1](#0-0) 

The `shop` accessor is read straight from an unauthenticated header, with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` (and `validate_signature`) only ever hashes `verifiable_query.to_signable_string` — i.e., the body — against the secret: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality that the HMAC is expected to protect — `shop (header, used by handler) == shop (that generated/authorized this exact byte payload)` — is never actually checked; only `body == body` is checked. Since `api_secret_key` is a single app-wide secret shared by every installed shop (not per-shop), any shop that has the app installed can generate a legitimately-signed body/HMAC pair (by triggering the relevant event in their own store, e.g. `orders/create`) and then resend that exact body and HMAC value to the endpoint with a forged `shop-domain` header pointing at a different, victim shop that also has the app installed. The signature verification (`OpenSSL.secure_compare`) succeeds because it never inspects the header, so the handler executes believing the payload came from the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to guarantee: it is a cross-tenant confusion primitive. Any handler that uses `WebhookMetadata#shop` to key writes, cache invalidation, billing events, inventory sync, or other per-tenant side effects can be tricked into applying attacker-controlled (but validly-signed-body) data under a different shop's identity — this is a cross-tenant access/data-integrity issue, matching the "Critical - cross-tenant access" category.

### Likelihood Explanation
The attack requires no special access: the attacker only needs to be able to install the app on their own store (or any dev store) and trigger a webhook-eligible action there — something available to any user of the app, i.e. no leaked credentials, no `api_secret_key`, no TLS interception, and no privileged account are required. The only "difficulty" is that the forged shop must also have installed the app (so the app has a live webhook endpoint/config for both shops), which is trivially satisfiable for any public/multi-tenant app.

### Recommendation
Bind the shop identity into the authenticated material before trusting it:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string that is HMAC-verified, or
- After verifying the HMAC over the body, independently verify that the shop asserted in the header corresponds to a shop session/installation that is expected to be delivering *this* body content (e.g., cross-check against a known/allow-listed set of shop domains for the app, or require correlation with a per-shop webhook signing secret rather than only the app-wide `api_secret_key`), or
- Follow Shopify's guidance to treat the `shop-domain` header as untrusted metadata and never key persistence/authorization decisions on it without an additional binding check.

### Proof of Concept
1. Malicious operator installs the target app on `attacker-shop.myshopify.com` (their own store) and installs it legitimately.
2. They trigger an event (e.g., create an order) causing Shopify to deliver a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. The attacker captures this `(B, H)` pair from their own delivery (no interception of anyone else's traffic needed — it's their own webhook).
4. The attacker crafts a new HTTP request to the same webhook endpoint using the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a different shop that also has the app installed).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only hashes `B`, matches `H`, and passes.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process/attribute the attacker's event data as if it came from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
