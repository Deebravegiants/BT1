## Title
Challenge-period-elapsed check uses inconsistent boundary conditions between the EVM `HandlerV2` and the Rust ISMP core `handlers::verify_delay_passed`, mirroring the `roundHasEnded`-style modifier inconsistency - (File: `evm/src/core/HandlerV2.sol`, `modules/ismp/core/src/handlers.rs`)

### Summary
The "has the challenge period elapsed" check — the ISMP analog of the reported `roundHasEnded` boundary bug — is defined with two different comparison operators in two different implementations of the same protocol invariant: the EVM message handler treats the challenge period as elapsed at `delay == challengePeriod` (`>=`), while the Rust `ismp-core` handler requires strictly `delay > challenge_period` before allowing the same class of proof to be processed.

### Finding Description
`HandlerV2.sol` gates every message-processing entrypoint (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) with:
```solidity
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(...);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
``` [1](#0-0) [2](#0-1) 

This reverts only if `challengePeriod > delay`, i.e. it treats the challenge period as satisfied ("elapsed") as soon as `delay >= challengePeriod` — the boundary tick (`delay == challengePeriod`) is accepted.

The equivalent Rust-side gate used by `pallet-ismp`/`ismp-core` when validating state-machine proofs for the same purpose (`validate_state_machine`, used for request/response handling) is `verify_delay_passed`:
```rust
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error> {
    let update_time = host.state_machine_update_time(*proof_height)?;
    let delay_period = host.challenge_period(proof_height.id)...;
    let current_timestamp = host.timestamp();
    Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
``` [3](#0-2) 

This requires a **strict** `>` — at `delay == delay_period` exactly, `verify_delay_passed` returns `false` and the caller raises `Error::ChallengePeriodNotElapsed`: [4](#0-3) 

Both code paths implement the exact same protocol-level security control — "reject message processing until the fraud-proof/challenge window for a state commitment has elapsed" — but one uses `>=`-equivalent semantics (elapsed at the boundary) and the other uses strict `>` (not elapsed at the boundary). This is precisely the same bug class as the external report: two definitions of the same time-gated modifier disagree at the boundary instant, so a proof/message that is rejected by one host implementation is accepted by the other for the exact same `delay == challengePeriod` timestamp.

### Impact Explanation
The challenge period exists specifically to give fishermen a window to submit fraud proofs before a state commitment can be relied upon to process requests, responses, or timeouts (per `docs/content/protocol/interoperability/consensus-proofs.mdx` "Optimistic Bridging" section and `ChallengePeriodNotElapsed` semantics). Because the EVM handler's boundary condition is off by one tick relative to the Rust core implementation, a relayer can get a request/response/timeout processed on an EVM-hosted chain exactly one second earlier than the canonical Substrate-side ISMP semantics would permit, shrinking the fraud-proof window by exactly that unit for every message processed at the boundary. Since `IsmpModule::on_accept`/`on_timeout` callbacks can move funds or mint/settle cross-chain effects, accepting a state commitment before its intended challenge window truly closes weakens the safety guarantee the challenge period is meant to provide, and creates cross-implementation inconsistency: the same proof/timestamp pair is treated differently as "final" depending on which host (EVM vs Substrate) processes it.

### Likelihood Explanation
This triggers deterministically any time a relayer or unprivileged caller submits a message whose `delay` from `stateMachineCommitmentUpdateTime` exactly equals the configured `challengePeriod` — an easily reachable, permissionless condition since `handlePostRequests`/`handleGetResponses`/timeout handlers are all callable by anyone with a valid proof, and the relayer fully controls the submission timestamp/block.

### Recommendation
Unify the boundary semantics for "challenge period elapsed" across both implementations. Pick one canonical definition (e.g., elapsed when `delay >= challengePeriod`) and apply it consistently in `HandlerV2.sol` and `modules/ismp/core/src/handlers.rs::verify_delay_passed`, ideally factoring the check into a single shared helper/spec referenced by both to prevent future divergence.

### Proof of Concept
1. Configure a non-zero `challengePeriod` for a state machine on both an EVM-hosted deployment and a Substrate/`pallet-ismp` deployment tracking the same source chain and update time.
2. Wait until `current_timestamp - stateMachineCommitmentUpdateTime == challengePeriod` exactly (i.e., `delay == challengePeriod`).
3. Submit `handlePostRequests` (or `handleGetResponses`/timeout handler) to the EVM `HandlerV2` at this exact boundary: `challengePeriod > delay` is `false`, so it does **not** revert with `ChallengePeriodNotElapsed` — the message is processed.
4. Submit the analogous `Message::Request`/`Message::Response` to `pallet-ismp`'s `handle_unsigned` at the identical boundary: `verify_delay_passed` computes `current_timestamp.saturating_sub(update_time) > delay_period` as `false` (since it's `==`, not `>`), so `validate_state_machine` returns `Error::ChallengePeriodNotElapsed`, rejecting the same message.
5. This demonstrates the same proof/timestamp is accepted by one host implementation and rejected by the other, confirming the inconsistent modifier boundary.
