### Title
`Factory.initialize()` and `Router.initialize()` lack access control and are front-runnable, permanently seizing `DEFAULT_ADMIN_ROLE` and bricking or hijacking all curve trading - ([File: packages/contracts/src/Factory.sol, packages/contracts/src/Router.sol])

### Summary
`Factory.initialize()` and `Router.initialize()` are `external` functions guarded only by OpenZeppelin's `initializer` modifier (one-time-call protection), with no `onlyOwner`/deployer check. Unlike `Bonding`, `Zap`, `FeeVault`, and `LPLock` — which are deployed behind an `ERC1967Proxy` whose constructor atomically bundles deployment and `initialize` via `abi.encodeCall` — `Factory` and `Router` are deployed as **plain contracts** (`new Factory()`, `new Router()`) with `initialize()` called in a **separate, later transaction**, per `packages/contracts/script/Deploy.s.sol`: [1](#0-0) 

This is exactly the gap the external report describes: a public `initialize()` that sets vital state (here, `DEFAULT_ADMIN_ROLE`) can be observed in the mempool between contract creation and the `initialize()` call, and front-run by an unrelated address.

### Finding Description
`Factory.initialize()` grants `DEFAULT_ADMIN_ROLE` to `msg.sender` with no restriction on who that caller is: [2](#0-1) 

`Router.initialize(address factory_)` does the same, additionally taking an attacker-controllable `factory_` argument: [3](#0-2) 

The `AGENTS.md` notes confirm `Router` is deliberately non-upgradeable and deployed via `new Router()` "rather than behind an `ERC1967Proxy`," making the constructor→initialize window a real, observable gap on-chain, not a theoretical one: [4](#0-3) 

Since both contracts are deployed and initialized as two separate top-level transactions in `_deploy`, an attacker watching the mempool can submit their own `initialize()` call with higher gas to land between `new Factory()`/`new Router()` and the deployer's own `initialize()` call.

### Impact Explanation
If the attacker front-runs `Factory.initialize()`, they become the sole `DEFAULT_ADMIN_ROLE` holder. The deployer's subsequent `factory.grantRole(factory.BONDING_ROLE(), bondingProxy)` call reverts (deployer lacks admin), so `Bonding` can never obtain `BONDING_ROLE` and `Factory.createPair` (gated `onlyRole(BONDING_ROLE)`) can never succeed — permanently bricking token launches. Worse, the attacker — now holding admin — can call `Factory.setRouter(maliciousRouter)` themselves, since `Factory.router` is a **one-shot** field: [5](#0-4) 

Because `Pair`'s constructor wires in whatever `Factory.router` is at `createPair` time (per `AGENTS.md`), and `Pair`'s `onlyRouter`-gated transfer functions trust that address permanently, an attacker-controlled `router_` (satisfying only the `IRouter(router_).factory() == address(this)` check) becomes the immutable trusted router for **every future `Pair`** ever created on this `Factory` — enabling outright theft of all curve-side LT/token funds moved through `Pair.transferToken`/`transferAsset` in every subsequent launch.

Analogously, front-running `Router.initialize()` lets the attacker seize `DEFAULT_ADMIN_ROLE` on `Router`, block the deployer from granting `BONDING_ROLE` to `Bonding`, and permanently prevent `Bonding.buy`/`sell`/`Router.graduate` (all `onlyRole(BONDING_ROLE)`) from ever executing — a permanent denial-of-service on all trading and graduation.

### Likelihood Explanation
This requires an attacker to observe a specific deployment transaction sequence in the mempool and race it — feasible for a bot monitoring `Factory`/`Router` deployment bytecode or well-known deployer addresses, especially since deployments are typically manual/scripted and gas-competitive front-running is cheap. The likelihood is bounded by the deployer's operational security (e.g., using a private mempool/Flashbots for deployment), but the contract code itself provides no on-chain defense — matching the report's core claim that access control, not operational luck, should prevent this class of bug.

### Recommendation
Add a constructor to `Factory` and `Router` that sets the deployer as the sole authorized initializer (e.g., `_disableInitializers()` is not applicable here since these aren't proxies, but an immutable `deployer` address set in the constructor and checked in `initialize()`), or deploy both behind an `ERC1967Proxy`/atomic-init pattern identical to `Bonding`/`Zap`/`FeeVault`/`LPLock`, so `initialize()` is called in the same transaction as deployment and cannot be observed/front-run separately.

### Proof of Concept
1. Deployer broadcasts `Factory factory = new Factory();` — the resulting address is deterministic/observable pre-confirmation (or immediately after, before `initialize()` lands).
2. Attacker submits `factory.initialize()` with a higher gas price, landing before the deployer's own `factory.initialize()` call; the attacker's tx succeeds and grants `DEFAULT_ADMIN_ROLE` to the attacker (deployer's later call reverts with `InvalidInitialization`).
3. Attacker calls `factory.setRouter(attackerRouter)`, where `attackerRouter` is a contract satisfying `IRouter(attackerRouter).factory() == address(factory)`; since `pairCount == 0`, this succeeds and is permanently frozen thereafter per `Factory.setRouter`'s `RouterFrozen` check.
4. The deployer's `factory.grantRole(factory.BONDING_ROLE(), bondingProxy)` reverts (deployer no longer holds `DEFAULT_ADMIN_ROLE`), so `Bonding.launch`/`createPair` never functions with the legitimate router — or, if the attacker instead grants `BONDING_ROLE` themselves to a malicious contract, every `Pair` created thereafter is wired to the attacker's `Router`, letting the attacker drain curve funds via `Pair.transferToken`/`transferAsset` on every future launch.
