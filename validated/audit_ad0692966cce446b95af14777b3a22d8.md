Confirmed: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` with no domain validation [1](#0-0) , and the app's `client_secret` is placed in the POST body sent to that host [2](#0-1) .

### Title
Token exchange sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange request solely from the `dest` claim of the caller-supplied session token, with no check that this value is a trusted `*.myshopify.com`/Shopify domain, before sending the app's `client_secret` and the raw `subject_token` to that host over HTTPS.

### Finding Description
`exchange_token` decodes the session token via `JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` [3](#0-2) . `JwtPayload#shop` performs no domain allow-listing — it simply strips the `https://` prefix from the raw `dest` claim: `@dest.gsub("https://", "")` [4](#0-3) . `JwtPayload#initialize` only checks the `aud` claim against `Context.api_key`; `iss` and `dest` are stored unchecked [5](#0-4) .

This unvalidated `dest_shop` value is used to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, and that session is handed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, which builds the request base URI as `"https://#{api_host || session.shop}"` — i.e., directly from the untrusted claim, with no call to `Utils::ShopValidator.sanitize!` [1](#0-0) . The client then POSTs a body containing `client_id`, `client_secret`, and the raw `subject_token` (the caller's own session token) to `https://#{dest_shop}/admin/oauth/access_token` [6](#0-5) .

Notably, the sibling method `migrate_to_expiring_token` in the same file *does* validate its shop argument via `Utils::ShopValidator.sanitize!(shop)` before constructing the session [7](#0-6) , and this behavior is enforced by test `test_migrate_to_expiring_token_rejects_non_shopify_domain` [8](#0-7) . No equivalent sanitization or test exists for `exchange_token`'s `dest_shop`, confirming the asymmetry is not an intentional design choice elsewhere in the same file.

This breaks the intended binding "host that receives the app's `client_secret` == a trusted Shopify domain." The `dest` claim is documented as attacker-influenceable input in this exact code path: the library's own docs state "Its `dest` claim determines which shop receives the token exchange request," describing `session_token` as data "provided by App Bridge in either the request 'Authorization' header or URL param" [9](#0-8) , i.e., something the host application typically forwards from the incoming client request without an independent trust boundary at this layer of the gem.

### Impact Explanation
If a session token with an attacker-influenced `dest` claim reaches `exchange_token` (still requiring a signature verifiable by the correct HS256 secret, since `JwtPayload` verifies signature before using `dest`), the gem will construct an HTTPS request that carries the app's `client_secret` to whatever host is present in that claim rather than to a verified Shopify domain. This is an SSRF-with-credentials pattern: the app's `client_secret` (and the raw session token as `subject_token`) is sent to a host chosen from unvalidated claim data instead of the validated, allow-listed host that `ShopValidator` enforces elsewhere in the same module for the same purpose. This matches the High-impact category "SSRF with the app's credentials."

### Likelihood Explanation
Exploitation still depends on the host application's handling of the session token before calling `exchange_token`, and on whether any component signs a token with the correct secret while allowing `dest` to be attacker-controlled — this is a real, but not fully proven within the boundaries of this gem alone, dependency. However, within the gem's own code, this is a structural inconsistency: the exact same file enforces host validation for `migrate_to_expiring_token` but not for `exchange_token`, showing that the correct control (`Utils::ShopValidator.sanitize!`) exists and is trivially applicable but was omitted for the `dest`-derived value.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent trusted-domain check) before constructing `shop_session`, mirroring the existing protection in `migrate_to_expiring_token`. Additionally, consider validating `iss`/`dest` shape in `JwtPayload` itself so all consumers of `JwtPayload#shop` receive an already-trusted domain.

### Proof of Concept
1. Configure `ShopifyAPI::Context` as an embedded app with a known `api_secret_key`.
2. Craft (or obtain) a session token whose `aud` equals `Context.api_key` but whose `dest` claim is set to an untrusted/attacker-controlled host, e.g. `dest: "https://attacker.example"`.
3. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: crafted_token, requested_token_type: ...)`.
4. Observe that `Clients::HttpClient` builds the request URI as `https://attacker.example/admin/oauth/access_token` (per `lib/shopify_api/clients/http_client.rb:18`) and that the outgoing POST body includes `client_secret` in plaintext (per `lib/shopify_api/auth/token_exchange.rb:52-59`), with no `ShopValidator` check in the code path, unlike `migrate_to_expiring_token`.
