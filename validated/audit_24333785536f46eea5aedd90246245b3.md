### Title
`convert_to_erc20`/`convert_to_balance` use `saturating_sub` for decimal deltas, silently skipping down-scaling and misvaluing cross-chain token amounts by orders of magnitude - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
Analogous to the `MagicLpAggregator` bug (a decimals-normalization step that is applied asymmetrically and silently drops the correction when the delta runs the "wrong" direction), the `hyper-fungible-token` pallet's decimal-conversion helpers `convert_to_erc20` and `convert_to_balance` compute the scaling exponent with `saturating_sub`, which clamps to zero instead of applying the required inverse (division) operation when the local asset's decimals exceed the destination ERC20's decimals (or vice versa for the receive path). This causes amounts dispatched to, or received from, a chain with different token decimals to be scaled by the wrong factor.

### Finding Description
`convert_to_erc20` is documented as "Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision" but is implemented as: [1](#0-0) 

`erc_decimals.saturating_sub(local_decimals)` returns `0` whenever `local_decimals >= erc_decimals` (e.g. a local asset registered with 18 decimals being sent to a destination `HyperFungibleToken` deployed with 6 decimals). In that case the function returns `value` unscaled instead of dividing by `10^(local_decimals - erc_decimals)` as required, and `send()` forwards this unscaled `erc20_amount` verbatim in the dispatched `Message`: [2](#0-1) 

The mirrored helper `convert_to_balance`, used in `on_accept`/`on_timeout`, has the same flaw in the opposite direction: it is documented as dividing by `10^(erc_decimals - local_decimals)` but again uses `saturating_sub`, so it fails to multiply (scale up) when `local_decimals > erc_decimals`: [3](#0-2) 

On the receiving side, `on_accept` calls `convert_to_balance` with the destination's local decimals and the source's `erc_decimals` to compute how much to mint/release to the beneficiary: [4](#0-3) 

Because the destination EVM contract's `mint`/burn functions treat `amount` as a raw ERC20 balance with no independent decimal reconciliation: [5](#0-4) 

any token pair whose local (Substrate) asset decimals differ from the destination chain's registered ERC20 `decimals` (via `Precisions`/`ChainConfig.decimals`) in the direction where `local_decimals >= erc_decimals` (send path) or `local_decimals > erc_decimals` (receive path) will silently skip the required scale-down/scale-up step, producing an amount off by a factor of `10^|local_decimals - erc_decimals|`.

### Impact Explanation
This is directly reachable by any unprivileged user calling the `send` extrinsic once a token is registered with mismatched decimals across chains — exactly the class of asymmetric-normalization bug in the reference report, but here it can cause either:
- Under-scaling on send: a user escrows/burns a small local amount but the message dispatched to the destination encodes an amount many orders of magnitude larger, letting the destination contract mint far more tokens than were locked/burned (unbacked mint / permanent freezing-by-drain of the destination-side backing).
- Under-scaling on receive: `convert_to_balance` failing to multiply up means an inbound transfer credits the beneficiary with far too few tokens relative to what was escrowed/burned on the source chain, permanently freezing the difference in the pallet's custodial account.

Either direction violates fund-conservation across a `pallet-ismp` message dispatch and would be triggered by a single legitimate cross-chain transfer once any registered asset pair has this decimal relationship — no privileged action required.

### Likelihood Explanation
Likelihood depends on whether any token registered via `register_token`/`update_token` (`ChainConfig.decimals`) actually has `local_decimals >= erc_decimals` for the send path (e.g. a Substrate asset with 18 decimals bridged to a 6-decimal ERC20, a very common stablecoin pattern) or the inverse for the receive path. The `BridgeToken` test fixture in the repo explicitly demonstrates a scaling scenario (18 vs 12 decimals, "pallet scales by 10^6 in both directions"), confirming decimal mismatches across chains are an expected, supported configuration, not an edge case: [6](#0-5) 
This makes the vulnerable code path realistically reachable in production configurations.

### Recommendation
Replace `saturating_sub` with logic that scales in the correct direction for both signs of the decimal delta, mirroring how `_normalizeAmount` in `VWAPOracle.sol` correctly branches on `<` vs `>=`: [7](#0-6) 

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}

pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}
```
Add unit tests covering both directions of the decimals delta (local > erc, local < erc, local == erc) for both `send` and `on_accept`/`on_timeout` paths.

### Proof of Concept
1. Register a local asset with `local_decimals = 18` and configure `ChainConfig.decimals = 6` for a destination EVM chain via `register_token`.
2. User calls `send` with `amount = 1_000_000_000_000_000_000` (1 token, 18 decimals). The pallet burns/escrows this amount from the sender.
3. `erc_decimals = 6`, `decimals = 18` ⇒ `erc_decimals.saturating_sub(decimals) = 0` ⇒ `convert_to_erc20` returns `value` unchanged: `erc20_amount = 1_000_000_000_000_000_000`, instead of the correct `1_000_000` (scaled down by `10^12`).
4. The dispatched `Message.amount` therefore encodes `1e18` raw units. On the destination `HyperFungibleTokenImpl`/gateway, this raw value is minted directly via `_mint(to, amount)`, crediting the beneficiary with `1e18` base units of a 6-decimal token — i.e. `1,000,000,000,000` whole tokens instead of `1`, for burning only 1 token's worth on the source chain: an unbacked mint by a factor of `10^12`.     function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
