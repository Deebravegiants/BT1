### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , and `HmacValidator.validate` checks the HMAC only against that raw body using the app's single, shop-agnostic `api_secret_key` [2](#0-1) . The `shop` value used downstream by `Registry.process` is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header and handed to the app's webhook handler without any binding to the HMAC [3](#0-2) [4](#0-3) .

### Finding Description
The identity binding that should hold is: `authenticated_shop == shop_the_handler_acts_on`. In this gem, the HMAC only proves "this raw body byte-string was signed with the app's `api_secret_key`" — it says nothing about which shop the body belongs to, because the shop-domain header is excluded from `to_signable_string` [1](#0-0) .

Since `api_secret_key` is the app's single `client_secret`, shared across every shop that installs the app (not a per-shop key), any merchant that legitimately installs the app receives genuinely-signed webhooks (valid `body` + `hmac` pair) for their own shop. Because the HMAC does not bind the body to a specific shop, that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `Registry.process` only checks `Utils::HmacValidator.validate(request)` [5](#0-4)  — which passes, since the body/hmac pair is valid — and then dispatches to the handler using the attacker-controlled `shop` field [6](#0-5) .

Root cause: `shop` is verified as "present" (`Request#initialize` only checks the header exists) but never verified as authentic [7](#0-6) , and it is excluded from the signable string that the HMAC actually protects [1](#0-0) .

### Impact Explanation
This breaks the tenant boundary between shops of the same app. An attacker who is a legitimate (even free-tier) installer of the app can forge webhook events "on behalf of" any other shop using the app, by replaying a genuinely-signed body with a spoofed shop header. Depending on how the host app's handler uses `data.shop` (e.g., to look up per-shop config, write per-shop data, or trigger shop-scoped actions such as data deletion/redaction mandatory webhooks), this enables cross-tenant data injection or corruption — matching the Critical "cross-tenant access" impact category, since no merchant-specific secret is required, only the shared app secret that any installer's webhook traffic is signed with.

### Likelihood Explanation
Likelihood is realistic for any app used by multiple untrusted merchants: the attacker only needs to install the app once (an unprivileged action available to any internet user with a Shopify dev store) to receive real signed webhook traffic, then can capture and replay `(body, hmac)` with an altered `shop-domain` header. No access to `api_secret_key`, tokens, or another merchant's credentials is required.

### Recommendation
Bind the shop identity into what the HMAC protects, or otherwise verify the `shop` header against a known-good value before trusting it:
- Include the `shop-domain` header (and other identity fields) in the signed payload validated by `HmacValidator`, or
- After verifying the HMAC on the body, cross-check the header-provided `shop` against the shop associated with the webhook subscription (e.g., resolve via `webhook_id` against Shopify, or require the host app to validate `shop` against its own installed-shops list) before invoking the handler in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (legitimate, unprivileged action).
2. App triggers a real webhook to attacker's endpoint; attacker's server (fully attacker-controlled) records the exact raw body and the `x-shopify-hmac-sha256` value Shopify sent — both valid per `HmacValidator.validate`.
3. Attacker sends a new HTTP request to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present) [7](#0-6) ; `Registry.process` validates the HMAC successfully (it only checks the body) [5](#0-4)  and calls the handler with `shop: "victim-shop.myshopify.com"` [8](#0-7) , even though the payload was never actually generated for that shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
