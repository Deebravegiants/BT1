## Title
Successful GET response delivery permanently leaks `_requestCommitments` storage, letting a relayer front the fee and never trigger cleanup - (File: evm/src/core/EvmHost.sol)

## Summary
`dispatchIncoming(GetResponse, address)` in `EvmHost.sol` reads the fee from `_requestCommitments[commitment]` to pay the relayer on a successful GET-response delivery, but never deletes that storage entry on the success path — unlike every other terminal path for a request (POST/GET timeout), which does `delete _requestCommitments[commitment]`.

## Finding Description
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` [1](#0-0)  is the terminal handler for a successfully verified GET response, invoked by `HandlerV2` after state-proof verification. On success it does:

```solidity
uint256 fee = _requestCommitments[commitment].fee;
if (fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
emit GetRequestHandled({commitment: commitment, relayer: relayer});
```

It reads `_requestCommitments[commitment]` but never calls `delete _requestCommitments[commitment]`, leaving the `FeeMetadata` struct (sender, fee, and any other packed fields) permanently in storage for every GET request that is ever successfully answered.

Contrast with the two sibling functions that also consume a `_requestCommitments` entry, `dispatchTimeOut(GetRequestTimeout, ...)` and `dispatchTimeOut(PostRequestTimeout, ...)`, both of which explicitly `delete _requestCommitments[commitment]` for replay protection and cleanup [2](#0-1) . Note also that `dispatchIncoming(PostRequest, ...)` correctly cleans up its own replay-protection map on the failure path (`delete _requestReceipts[commitment]`), and `dispatchIncoming(GetResponse, ...)` does the same for `_responseReceipts` on failure [3](#0-2) . Only the success path of the GET-response case skips clearing the resource table it just consumed.

This is directly analogous to the reported Wasmtime `fd_renumber` bug: the guest-visible operation (delivering the GET response, paying the relayer, emitting the completion event) completes correctly, but the underlying host-side resource table entry (`_requestCommitments`) is never released, so it accumulates indefinitely — exactly the "succeeds from the caller's perspective but leaks a resource that isn't cleaned up" pattern in the advisory.

## Impact Explanation
Every successfully delivered GET response leaves one non-zero storage slot (a `FeeMetadata` struct — `sender` + `fee`, and any other fields in that struct) permanently occupied in `_requestCommitments`, with no code path that ever clears it. Any unprivileged actor able to dispatch a GET request and have a relayer deliver its response — the normal, expected happy path of the protocol — causes this leak on every single call; it costs nothing extra to trigger and requires no adversarial timeout or failure. Over the life of the contract this is unbounded storage growth. It also has an authorization-adjacent effect: because the entry is never deleted, `_requestCommitments[commitment].fee` remains non-zero, and if for any reason `dispatchIncoming(GetResponse,...)` (or a path reading the same commitment key) were reachable again for the same commitment via a re-entrant or repeated `handler`-issued call, `fee` could be paid out more than once from the stale entry (the `_responseReceipts` map is the only replay guard for this exact call, but any other host logic keyed off `_requestCommitments` non-zero fee is now permanently poisoned for this commitment). At minimum this is a permanent state-bloat / stuck-storage bug tied 1:1 to legitimate protocol usage, satisfying "route unable to deliver messages cleanly / unsound state commitment cleanup" from the acceptance criteria, driven purely by an unprivileged relayer delivering a GET response.

## Likelihood Explanation
High. This is not a corner case — it fires on every single successful GET response delivery, which is core, expected traffic for the bridge (intent solvers, token bridgers, and general dApp GET requests). No malicious actor, governance, or admin action is required; a normal relayer submitting a valid proof for a valid GET response triggers the leak every time.

## Recommendation
Add `delete _requestCommitments[commitment];` on the success path of `dispatchIncoming(GetResponse memory response, address relayer)` immediately after reading the fee (and before/after the transfer, consistent with checks-effects-interactions), mirroring the cleanup already done in `dispatchTimeOut` for GET and POST timeouts. If the entry needs to be read for any additional post-delivery bookkeeping, cache the `FeeMetadata` in memory first, then delete storage.

## Proof of Concept
1. User dispatches a GET request via `IDispatcher.dispatch(...)`, which stores `_requestCommitments[commitment] = FeeMetadata{sender, fee}`.
2. A relayer submits a valid consensus + state proof to `HandlerV2`, which calls `EvmHost.dispatchIncoming(GetResponse, relayer)`.
3. `onGetResponse` succeeds on the destination app; the function pays `fee` to `relayer` and emits `GetRequestHandled`.
4. Inspect `_requestCommitments[commitment]` after the call — it still returns the original `FeeMetadata` (fee, sender) rather than the zeroed/deleted struct, unlike the timeout paths where the same slot is provably deleted (`delete _requestCommitments[commitment]` in `dispatchTimeOut`). Repeating steps 1–3 for N GET requests grows `_requestCommitments` by N permanently-occupied slots with no corresponding cleanup, confirmed by comparing against the `delete` calls present in the two `dispatchTimeOut` overloads at [4](#0-3)  and [5](#0-4) .

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
