### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing via HMAC replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the *body bytes* only. The `shop` (`shop-domain`), `topic`, `api_version`, and `webhook_id` fields that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler as tenant/context identifiers come straight from unauthenticated HTTP headers, so they can be modified freely without invalidating the HMAC.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` alone - the `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers and are excluded from the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` passed to the app's registered `WebhookHandler`: [3](#0-2) 

The gem's own documentation instructs apps to use `data.shop` as the tenant identifier for routing/queuing work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so trusting this field is the gem's intended, documented usage, not host misuse: [4](#0-3) 

The identity binding that should hold is: `HMAC(api_secret_key, raw_body)` authenticates the tuple `(shop, topic, body)` as coming from that specific shop. In this implementation the binding actually only holds for `raw_body`: `verified_bytes = raw_body ≠ acted_upon_fields = {shop, topic, api_version, webhook_id, raw_body}`. Since every merchant installation of the same app shares the same `api_secret_key`, any shop that has the app installed can legitimately receive a real webhook delivery (valid HMAC over some `raw_body`), then replay that exact `raw_body`+HMAC pair while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header to name a different, victim shop. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still succeeds because it only recomputes the signature over `raw_body`: [5](#0-4) 

The app's handler then processes the forged request believing it originates from the victim shop — a cross-tenant identity break.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: a request whose payload authenticity is verified can carry an attacker-chosen `shop` value, causing the host application (following the gem's documented pattern) to attribute webhook data/processing to an arbitrary shop chosen by the attacker. Depending on what the host app does with `data.shop` (e.g., looking up/store session data, triggering per-shop side effects, updating per-shop records), this enables cross-tenant access/confusion — classified as Critical under the stated rules ("cross-tenant access").

### Likelihood Explanation
Any developer/merchant who can install the app on their own shop obtains legitimate, validly-signed webhook deliveries for that shop (no secret leakage required — it's the normal course of using a multi-tenant app). Replaying the body+HMAC while rewriting the `shop-domain` header is a purely mechanical HTTP-level change; the gem performs no validation tying `shop` to the signed bytes, so exploitation requires no privileged access to the app's `client_secret` and no interaction with the merchant being targeted.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify `shop` against a per-shop stored token/context rather than trusting the header verbatim). At minimum, document clearly that `WebhookMetadata#shop`/`topic` are not covered by Shopify's HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against the caller's known/expected shop for that endpoint).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g.:
```
POST /callback/orders/create
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid HMAC over body B>
X-Shopify-Shop-Domain: attacker.myshopify.com
Body: B
```
2. Attacker resends the identical body `B` and identical `X-Shopify-Hmac-Sha256` value, but changes only the shop header:
```
POST /callback/orders/create
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <same HMAC over body B>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
Body: B
```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds a `Request` whose `to_signable_string` is still `B`; `Utils::HmacValidator.validate(request)` recomputes the same signature over `B` and succeeds.
4. `Registry.process` calls the app's `WebhookHandler#handle` with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: ..., ...)`, and the app processes the (attacker-controlled) data as if it came from `victim-shop.myshopify.com`, even though only the attacker's shop ever produced a valid signature.
