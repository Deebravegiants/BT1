### Title
`limitSecretReferences` fails to validate `Projected` volume `Secret` sources, bypassing the mountable-secrets restriction - ([File: plugin/pkg/admission/serviceaccount/admission.go])

### Summary
`(s *Plugin) limitSecretReferences` only inspects `volume.VolumeSource.Secret` when enumerating pod volumes, but never inspects `volume.VolumeSource.Projected.Sources[].Secret`. A namespaced user who can create Pods (but is not authorized to read arbitrary Secrets) can reference any Secret in the namespace through a `Projected` volume's `SecretProjection` and have it mounted by the kubelet, completely defeating the `EnforceMountableSecretsAnnotation` / `LimitSecretReferences` guarantee that a pod may only mount secrets its ServiceAccount explicitly references.

### Finding Description
`limitSecretReferences` builds the `mountableSecrets` allow-list from `serviceAccount.Secrets`, then walks `pod.Spec.Volumes` checking only the direct `VolumeSource.Secret` field: [1](#0-0) 

It does not walk `volume.VolumeSource.Projected.Sources`, whose elements (`api.VolumeProjection`) may contain a `Secret` field (`SecretProjection`) referencing an arbitrary Secret name. Neither the container-env checks (`EnvFrom`/`ValueFrom.SecretKeyRef`) nor the volume check cover this path. Note that the mirror-pod path in `Validate` does correctly call `podutil.VisitPodSecretNames`, which is aware of Projected sources, but that helper is *not* used for the mountable-secrets enforcement path — only for the mirror-pod "no secrets at all" check: [2](#0-1) 

Attack flow:
1. Attacker holds a namespace-scoped identity that can `create` Pods (a very common minimal RBAC grant, e.g. for CI/build controllers) but has no `get`/`list` on Secrets.
2. The namespace's target ServiceAccount (or the attacker's own, if the annotation `kubernetes.io/enforce-mountable-secrets=true` is set, or the plugin runs with `LimitSecretReferences=true`) does not list the target Secret in `.secrets[]`.
3. Attacker crafts a Pod using `pod.Spec.ServiceAccountName` = an SA with mountable-secrets enforcement, and adds a `Volume` with `VolumeSource.Projected.Sources[].Secret.Name = "<victim-secret>"`.
4. `limitSecretReferences` never inspects `Projected`, so admission allows the Pod.
5. The kubelet, using node authorization (which permits reading any Secret referenced by a Pod scheduled on that node, regardless of the creating user's own RBAC), fetches and mounts the Secret content into the container.
6. The attacker's workload now has the plaintext contents of a Secret the enforcing ServiceAccount was never authorized to mount — the exact scenario `LimitSecretReferences`/`EnforceMountableSecretsAnnotation` was designed to prevent.

The question specifically asks about `container.Env` `ValueFrom` too; that surface is actually enumerated (`SecretKeyRef`/`EnvFrom.SecretRef` are checked for both init and regular containers), so the Env-based bypass does **not** exist. The real gap is the `Volumes[].Projected.Sources[].Secret` path.

### Impact Explanation
This is an admission/validation bypass that defeats a documented security control (`ServiceAccount` admission plugin's mountable-secrets restriction), enabling unauthorized cross-secret access within a namespace without requiring `get`/`list` RBAC on Secrets — only Pod-create rights on the target ServiceAccount. This matches the Kubernetes bug bounty "admission bypass leading to unauthorized data access / secret exfiltration" impact class.

### Likelihood Explanation
- Requires only namespace-scoped RBAC to create Pods against a ServiceAccount that has mountable-secrets enforcement enabled (either cluster-wide `LimitSecretReferences=true` or the per-SA annotation).
- Fully deterministic and repeatable — no timing/race conditions or special node/kubelet cooperation needed beyond normal secret volume mounting.
- Feature is old and stable (`Projected` volumes and `SecretProjection` are GA), so this is broadly applicable wherever the admission plugin's `LimitSecretReferences`/annotation feature is actually turned on (its own comment notes it defaults to `false` in-tree, but the annotation-based per-SA opt-in is commonly used by cluster operators).

### Recommendation
Extend `limitSecretReferences` to walk `volume.VolumeSource.Projected.Sources` (and any other secret-bearing volume types, e.g. CSI ephemeral volumes' secret refs, if added in future) and reject any `SecretProjection.Name` not present in `mountableSecrets`. Prefer reusing/extending `podutil.VisitPodSecretNames` (which already understands Projected sources) inside `limitSecretReferences` and `limitEphemeralContainerSecretReferences` instead of hand-rolled field-by-field checks, so future PodSpec fields referencing Secrets are covered automatically.

### Proof of Concept
Table/unit test to add to `plugin/pkg/admission/serviceaccount/admission_test.go`:
1. Build a `corev1.ServiceAccount` named `"default"` with `Secrets: []corev1.ObjectReference{{Name: "allowed-secret"}}` and annotation `EnforceMountableSecretsAnnotation: "true"`.
2. Build an `api.Pod` with `Spec.ServiceAccountName = "default"` and a `Volume`:
   ```go
   api.Volume{
     Name: "victim",
     VolumeSource: api.VolumeSource{
       Projected: &api.ProjectedVolumeSource{
         Sources: []api.VolumeProjection{
           {Secret: &api.SecretProjection{LocalObjectReference: api.LocalObjectReference{Name: "victim-secret"}}},
         },
       },
     },
   }
   ```
3. Call `plugin.Validate(ctx, admission.NewAttributesRecord(pod, ...), o)`.
4. Expected (secure) behavior: `Validate` returns a `forbidden` error referencing `"victim-secret"`, matching the existing pattern for direct `VolumeSource.Secret` rejections.
5. Current actual behavior: `Validate` returns `nil` (admits the pod), demonstrating the bypass — confirmed by inspection of `limitSecretReferences` at plugin/pkg/admission/serviceaccount/admission.go:317-332, which contains no branch for `volume.VolumeSource.Projected`.

```go
func (s *Plugin) limitSecretReferences(serviceAccount *corev1.ServiceAccount, pod *api.Pod) error {
	// Ensure all secrets the pod references are allowed by the service account
	mountableSecrets := sets.NewString()
	for _, s := range serviceAccount.Secrets {
		mountableSecrets.Insert(s.Name)
	}
	for _, volume := range pod.Spec.Volumes {
		source := volume.VolumeSource
		if source.Secret == nil {
			continue
		}
		secretName := source.Secret.SecretName
		if !mountableSecrets.Has(secretName) {
			return fmt.Errorf("volume with secret.secretName=\"%s\" is not allowed because service account %s does not reference that secret", secretName, serviceAccount.Name)
		}
	}
```
