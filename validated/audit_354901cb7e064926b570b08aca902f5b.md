This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate` only checks the HMAC over `to_signable_string` (the body) [3](#0-2) , so the `shop` field is never bound to the signature. `Registry.process` still trusts `request.shop` as the tenant identity passed to the host app's handler [4](#0-3) .

### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body (`to_signable_string`). The `shop` value is passed unauthenticated to `handler.handle` as part of `WebhookMetadata`, which host applications use as the tenant key to route webhook processing (look up sessions, apply data, etc.). This breaks the binding: `hmac == HMAC(secret, body)` is verified, but there is no guarantee that `shop == the tenant that produced body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Request#shop` is read straight from `shopify_header("shop-domain")`, an HTTP header fully controlled by whoever sends the request to the app's webhook endpoint [2](#0-1) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against the received HMAC — the `shop` header plays no role in this computation [5](#0-4) . `Registry.process` validates the HMAC and then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the same untrusted `Request` object and dispatches it to the app-supplied handler [4](#0-3) .

The `api_secret_key` used to sign webhooks is the app's single client secret, shared across every shop that has installed the app — it is not shop-specific. Consequently:
1. An attacker who controls any shop that has installed the app (an unprivileged tenant of the app) legitimately receives real webhooks from Shopify with valid HMACs for that shop's own body content.
2. The attacker replays that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but substitutes the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still returns `true` because it only checks `body` against the shared secret; the forged `shop` value passes through untouched into `WebhookMetadata#shop`.
4. The host application's handler — which, per the gem's documented usage, keys its logic and session/data lookups off `data.shop` [6](#0-5)  — now processes attacker-supplied webhook content attributed to a different tenant.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality `verified_bytes == identity_bytes` does not hold, since only `body` is verified while `shop` (the tenant identity) is parsed independently from an unauthenticated header.

### Impact Explanation
Any handler that uses the unauthenticated `shop` field to select which tenant's session/state/data to mutate (a pattern the gem's own docs recommend: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into applying attacker-controlled webhook content under a victim shop's identity — a cross-tenant confusion enabled entirely by this gem's request/verification design, since the gem is the boundary that is supposed to authenticate `shop` alongside the payload but does not.

### Likelihood Explanation
Requires only that the attacker operate/install the app on their own (unprivileged) shop to obtain a validly-signed webhook body/HMAC pair, then replay it with a modified header to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signable content, or otherwise cross-check `request.shop` against an out-of-band trusted source (e.g., verify the shop against the session/webhook subscription that was registered, or include shop in the HMAC-covered content) in `ShopifyAPI::Webhooks::Request#to_signable_string` / `HmacValidator`, so that spoofing the `shop` header alone cannot pass validation.

### Proof of Concept
1. App has two installed shops: `attacker-shop.myshopify.com` (attacker-controlled) and `victim-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled-order-data...}
   ```
3. Attacker captures this exact `(Body, X-Shopify-Hmac-Sha256)` pair (they own this shop, so they can trivially trigger and observe it any number of times with attacker-chosen order content).
4. Attacker replays the identical body/HMAC to the app's webhook endpoint, only changing the header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same-valid-hmac-for-body>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled-order-data...}
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `body` against the shared `api_secret_key` [3](#0-2) .
6. `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...))` is invoked, and the host application's tenant-scoped logic (per the documented `data.shop`-keyed pattern) processes attacker data under the victim's identity.
