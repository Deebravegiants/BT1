## Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header is not covered by the HMAC signature, allowing shop-spoofing / cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop identity (`X-Shopify-Shop-Domain`) that the library hands to the app's webhook handler is taken from an HTTP header that is never included in that signature. Any party who can produce (or replay) one validly-HMAC'd webhook body can attach an arbitrary `shop-domain` header and have the library report it as authentic, breaking the binding between "HMAC verified" and "shop the data belongs to."

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and, if it passes, immediately trusts `request.shop` as the tenant identity, forwarding it to the app's handler: [3](#0-2) 

Compare this with the OAuth callback path, `Auth::Oauth::AuthQuery`, where `shop` **is** part of the signed payload: [4](#0-3) 

This is the exact bug class from the external report generalized to this gem: the identity field ("shop") that downstream code treats as authenticated is not covered by the same integrity check (`HMAC`) that's used to declare the message "valid." In the OAuth flow the binding `hmac_covers(shop) == true` holds; in the webhook flow it does not — `HmacValidator.validate` only proves `hmac == HMAC(body)`, not `hmac == HMAC(body, shop)`.

### Impact Explanation
Any unprivileged actor who can obtain one genuine `(body, hmac)` pair for the app's own secret — trivially available to any merchant who has installed the app and can trigger/capture a webhook for their own store, since HMAC uses `Context.api_secret_key` common to all shops sharing that app installation — can replay that exact body to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different shop. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` calls the app's handler with `WebhookMetadata` claiming the forged shop. This is a cross-tenant identity confusion: data legitimately generated for Shop A is attributed to Shop B in the app's webhook processing, which can pollute/mutate Shop B's records, invalidate its state, or leak Shop A's data into Shop B's context if the handler acts on `data.shop` for storage or access decisions. This falls under "cross-tenant access" (Critical/High per the rubric).

### Likelihood Explanation
Likelihood is meaningful: no access token, `api_secret_key`, or TLS interception is required — an ordinary merchant/app user, who is inherently "unprivileged" with respect to other tenants of the same app, can capture a real webhook delivered to their own shop and simply resend it with a different `shop-domain` header value. The only constraint is knowing another shop's domain name (public information, e.g., `victim.myshopify.com`), which is trivial to obtain.

### Recommendation
Bind the shop (and ideally topic/api_version/webhook_id) into the signed payload check, e.g. by having `Webhooks::Request#to_signable_string` incorporate the shop-domain header the same way `AuthQuery#to_signable_string` incorporates `shop`, or by requiring the webhook handler to independently confirm `request.shop` corresponds to an installed session/access-token for that shop before trusting it. At minimum, document/enforce that `shop` from `Webhooks::Request` must never be treated as authenticated on its own.

### Proof of Concept
1. Attacker is a merchant with the target app installed on `attacker-shop.myshopify.com`; they trigger a real webhook (e.g., `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker resends the identical `B`/`H` pair to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `shop` becomes `"victim-shop.myshopify.com"` [5](#0-4) .
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` only and it matches `H`, so validation succeeds [6](#0-5) .
5. `Registry.process` calls the app's handler with `WebhookMetadata` where `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the app to process attacker-supplied data as if it belonged to the victim shop.
