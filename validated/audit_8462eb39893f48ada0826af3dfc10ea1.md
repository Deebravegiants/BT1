### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from HTTP headers that are never included in the signed content. `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's shared `api_secret_key`; it says nothing about which shop the request claims to be from. Since Shopify webhook HMACs are computed with the app-wide `api_secret_key` (the same secret for every shop that installs the app), any party who can obtain one validly-signed webhook (for example by installing the app on their own store and capturing a real webhook delivery) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` still returns `true`, and `Webhooks::Registry.process` forwards the attacker-chosen `shop` straight into the handler.

### Finding Description
- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the received HMAC: [1](#0-0) 
- For webhook requests, `to_signable_string` is defined as just the raw body, deliberately excluding all headers: [2](#0-1) 
- `shop`, `topic`, `webhook_id`, and `api_version` are all derived from headers that are outside the signed scope: [3](#0-2) 
- `Registry.process` trusts `request.shop` (and `request.topic`) once `HmacValidator.validate` passes, and passes it straight to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_claimed_in_header == shop_that_the_HMAC_actually_authenticates`

But because the HMAC only authenticates the byte string of the body (and is computed with a secret that is shared across every shop that has installed the app, not a per-shop secret), the binding never actually holds. `HmacValidator.validate(request)` returns `true` for *any* header combination as long as the body bytes match a signature that was valid for the app's secret on some shop. This is the "shop authenticated versus the shop stored as a session key" binding-break pattern: the HMAC proves "this body was signed by app secret X", not "this body came from shop Y".

### Impact Explanation
An attacker who installs the app on their own shop (or otherwise obtains one legitimately-signed webhook payload/HMAC pair for a topic whose body they can predict or that is attacker-influenceable, e.g. `app/uninstalled`, `shop/update`, `customers/redact`, or any topic with attacker-controlled resource data) can replay that body to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header set to a victim shop's domain. The host application, trusting `WebhookMetadata#shop` as an authenticated identity, will process the webhook as if it came from the victim shop — this can trigger cross-tenant state changes (e.g. spoofing an uninstall/GDPR redact event for a shop the attacker doesn't own, or injecting attacker-controlled data attributed to another tenant). This is a cross-tenant identity binding bypass, matching the "cross-tenant access" Critical-impact category, since the confidentiality/integrity boundary between merchant tenants is broken using only the ability to install the app once.

### Likelihood Explanation
Likelihood is realistic: any user can install the target app on a store they control, which is enough to obtain valid `(body, hmac)` pairs signed with the app's real secret. No access to `api_secret_key`, access tokens, or any privileged account is required — only normal app installation, which is the assumed capability of an "unprivileged internet user" acting as a merchant.

### Recommendation
Bind the claimed shop (and topic) into the signed material, or otherwise cryptographically tie the header identity to the HMAC before trusting `request.shop`/`request.topic` downstream. At minimum, `to_signable_string` should incorporate the `shop-domain` (and ideally `topic`/`webhook-id`) header alongside the raw body so that a signature computed for one shop's payload cannot be replayed under a different shop's identity. Applications relying on `ShopifyAPI::Webhooks::Registry.process` should also be warned in documentation that `WebhookMetadata#shop` is not itself covered by HMAC verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, causing Shopify to send a real webhook (e.g., `app/uninstalled`) with a body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `B` and `H` (they own the shop and can log the request their own server receives, or intercept it themselves).
3. Attacker sends a POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: app/uninstalled` (unchanged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) and finds it matches `H` → validation passes.
5. `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` is handed to the app's registered handler, which now processes an uninstall/event as if `victim-shop` triggered it — despite the request never having originated from Shopify on behalf of that shop. [4](#0-3)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
