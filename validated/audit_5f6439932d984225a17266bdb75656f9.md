### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant data spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) values from unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. Because the identity of the tenant (`shop`) is never cryptographically bound to the signature, a request with a legitimate `(body, hmac)` pair can be replayed with an attacker-forged `shop-domain` header, and it will still pass HMAC validation while `ShopifyAPI::Webhooks::Registry.process` dispatches the (forged-shop-labelled) payload to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight out of attacker-controllable HTTP headers with no cryptographic linkage to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `to_signable_string`, i.e. only the body: [3](#0-2) 

`Webhooks::Registry.process` trusts this unverified `shop` field once the (body-only) HMAC check passes, and forwards it directly to the app's handler as the tenant identity: [4](#0-3) 

The binding that should hold is:
`hmac == HMAC(secret, body ‖ shop ‖ topic)` ⇒ but the gem only enforces `hmac == HMAC(secret, body)`, with `shop` supplied out-of-band via an unauthenticated header.

Since an app's `client_secret`/`api_secret_key` is shared across *every* shop that has installed that app (it is a per-app secret, not a per-shop secret), any shop that installs the app is a legitimate, unprivileged holder of `(body, hmac)` pairs produced with that shared secret (e.g., by triggering a real webhook, such as `orders/create`, in their own store). That merchant can then capture the raw body and its valid `X-Shopify-Hmac-Sha256`/`shopify-hmac-sha256` value and POST it directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain`/`shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` will report success because it only ever checks the body against the signature, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC is meant to enforce: it lets one shop (an unprivileged, low-trust principal in a multi-tenant app) inject attacker-chosen webhook payloads that the host application believes originated from a different shop. Any app logic that trusts `WebhookMetadata#shop` (data sync, provisioning, billing, per-shop authorization decisions, audit logs) can be corrupted or triggered under a victim's identity — this is a cross-tenant access issue, matching the Critical impact class ("cross-tenant access").

### Likelihood Explanation
Exploitation requires only:
1. Being any existing (even free/trial) tenant of the target app to legitimately obtain one valid `(body, hmac)` pair, or intercepting/observing a single previously-delivered webhook.
2. The ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — always possible for any internet user, since webhook endpoints are public HTTP routes by design.

No access token, secret key, or privileged account is required beyond standard multi-tenant app installation, so likelihood is high wherever the host application trusts `request.shop`/`WebhookMetadata#shop` for tenant-sensitive logic.

### Recommendation
Bind the tenant identity to the signed payload instead of trusting an unauthenticated header field:
- Include `shop` (and ideally `topic`) in the signable string used for HMAC verification, or
- Require host applications to independently verify that the `shop` reported by the webhook belongs to a session/store they already know about (e.g., cross-check against a previously stored offline session for that shop) before trusting `WebhookMetadata#shop`, and document this requirement prominently, or
- At minimum, document clearly in `ShopifyAPI::Webhooks::Request`/`Registry` that `shop` is unauthenticated and must not be used as a sole tenant-identity check by consuming applications.

### Proof of Concept
```ruby
# Attacker is a legitimate (but unprivileged) merchant of the app, or has
# observed one real webhook delivery for shop "attacker.myshopify.com".
real_body = '{"id":1,"note":"legit order"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, real_body)
encoded_hmac = Base64.encode64(real_hmac)

# Attacker forges the shop-domain header to point at a victim shop while
# reusing the same body + valid hmac pair.
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => encoded_hmac,     # still valid: only body is signed
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unverified
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body-only check passes)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app's webhook handler now processes attacker-controlled data believing
# it came from "victim-shop.myshopify.com".
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
