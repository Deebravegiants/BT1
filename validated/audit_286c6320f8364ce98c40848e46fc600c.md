### Title
Missing owner enforcement in Vault gateway `Delete` handler allows cross-owner secret deletion - (File: `core/capabilities/vault/gw_handler.go`)

### Summary
The Vault gateway node-side handler enforces the authorized owner on the `Secrets.List` path but not on the `Secrets.Delete` path, allowing any allowlisted/authorized caller to delete another owner's secrets by supplying an arbitrary `Owner` field inside the request payload.

### Finding Description
`GatewayHandler.HandleGatewayMessage` routes `MethodSecretsDelete` requests through `requestProcessor.ProcessRequest` for authorization/validation and then dispatches to `handleSecretsDelete`: [1](#0-0) 

`handleSecretsDelete` unmarshals the client-controlled `DeleteSecretsRequest` (whose `Ids` entries each carry their own `Owner` field) and passes it straight to `secretsService.DeleteSecrets` without ever rewriting the `Owner` fields to the authorized owner returned by the authorizer: [2](#0-1) 

By contrast, `handleSecretsList` explicitly overwrites the request owner with the value derived from authentication before calling the service, demonstrating that the codebase's intended security invariant is "trust only the authenticated owner, never the client-supplied owner": [3](#0-2) 

Upstream, `GatewayVaultRequestProcessor.processDeleteSecretsRequest` only validates request structure (`ValidateDeleteSecretsRequest`) and stamps the request ID/namespace defaults — it does not cross-check that the `Owner` field on each `SecretIdentifier` in `deleteReq.Ids` matches `authResult.AuthorizedOwner()`: [4](#0-3) 

The `allowListBasedAuth.AuthorizeRequest` mechanism authorizes based on a digest of the *entire* request (method + params), which binds a specific owner to a specific *allowlisted* request, but it does not evaluate whether the semantic `Owner` fields inside the payload belong to the authorized workflow owner: [5](#0-4) 

Because a workflow owner is allowlisted per-request-digest (not per-payload-semantics), and because `handleSecretsDelete` trusts the client-supplied `Owner` field on each identifier instead of re-stamping it with `authResult.AuthorizedOwner()`, a request that is legitimately authorized under one owner's allowlist entry can still carry `Ids[].Owner` values pointing at a different owner's namespace, and the backend `DeleteSecrets` call will act on those victim-owned identifiers.

### Impact Explanation
An attacker who can get any single delete request allowlisted for their own workflow (a normal, expected operation for any DON participant) can craft the `DeleteSecretsRequest.Ids` payload to reference `Owner` values belonging to other tenants/workflow owners. If the downstream `SecretsService.DeleteSecrets` implementation does not independently re-verify ownership (nothing in the reachable request pipeline forces it to), this results in unauthorized destruction of another user's vault secrets — a direct integrity/availability breach of the Vault capability analogous to unauthorized asset/fund loss in the external report (unauthorized action taken against another party's protected assets due to a broken access-control boundary).

### Likelihood Explanation
Likelihood is contingent on whether `SecretsService.DeleteSecrets` re-validates ownership internally (this could not be fully confirmed from the available index, as `plugin.go`'s `DeleteSecrets` implementation was not fully inspected). Within the reachable gateway/handler code that was inspected, no ownership re-stamping occurs for the delete path, which is inconsistent with the explicit re-stamping done for the list path — a clear code-level asymmetry indicating the delete path was likely overlooked when the ownership-enforcement pattern was introduced.

### Recommendation
In `handleSecretsDelete` (`core/capabilities/vault/gw_handler.go`), overwrite the `Owner` field of every entry in `DeleteSecretsRequest.Ids` with `authResult.AuthorizedOwner()` before calling `secretsService.DeleteSecrets`, mirroring the pattern already used in `handleSecretsList`. Additionally, add an explicit ownership assertion in `GatewayVaultRequestProcessor.processDeleteSecretsRequest` (and `processCreateSecretsRequest`/`processUpdateSecretsRequest`, if not already covered) that rejects any request whose payload-declared owners do not match `authResult.AuthorizedOwner()`, rather than relying solely on request-digest allowlisting.

### Proof of Concept
1. Workflow owner `A` obtains a valid allowlist entry for a `Secrets.Delete` JSON-RPC request (a normal, permitted operation for owner A).
2. Owner `A` crafts the `DeleteSecretsRequest.Ids` array so that `SecretIdentifier.Owner` is set to victim owner `B`'s address instead of `A`'s own.
3. The request digest matches the allowlisted entry (digest is over the full request including these attacker-chosen params), so `allowListBasedAuth.AuthorizeRequest` succeeds and returns `AuthorizedOwner() == "A"`.
4. `handleSecretsDelete` does not overwrite `Owner` on the `Ids`, so `secretsService.DeleteSecrets` is invoked with `Owner: "B"`, deleting owner `B`'s secrets under owner `A`'s authorization.

func (h *GatewayHandler) handleSecretsDelete(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.DeleteSecretsRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized delete secrets request", "request", r.String())
	resp, err := h.secretsService.DeleteSecrets(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to delete secrets: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}

func (p *GatewayVaultRequestProcessor) processDeleteSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var deleteReq vaultcommon.DeleteSecretsRequest
	if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		deleteReq.RequestId = req.ID
		if err := marshalVaultParams(req, &deleteReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		deleteReq.RequestId = coalesceRequestID(deleteReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateDeleteSecretsRequest(ctx, &deleteReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		deleteReq.RequestId = prefixedRequestID
		vaultutils.ApplySecretIdentifierNamespaceDefaults(deleteReq.Ids)
		return marshalVaultParams(req, &deleteReq)
	})
}

// AuthorizeRequest authorizes a request using AllowListBasedAuth.
// It does NOT check if the request method is allowed.
func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}

	if time.Now().UTC().Unix() > int64(allowlistedRequest.ExpiryTimestamp) {
		authorizedRequestStr := string(allowlistedRequest.RequestDigest[:])
		r.lggr.Debugw("AllowListBasedAuth authorization expired", "method", req.Method, "requestID", req.ID, "authorizedRequestStr", authorizedRequestStr, "expiryTimestamp", allowlistedRequest.ExpiryTimestamp)
		return nil, errors.New("request authorization expired")
	}

	digestKey := string(allowlistedRequest.RequestDigest[:])
	r.lggr.Debugw("AllowListBasedAuth authorization succeeded", "method", req.Method, "requestID", req.ID, "authorizedRequestStr", digestKey, "owner", allowlistedRequest.Owner.Hex(), "expiryTimestamp", allowlistedRequest.ExpiryTimestamp)
	return &AuthResult{
		workflowOwner: allowlistedRequest.Owner.Hex(),
		digest:        digestKey,
		expiresAt:     int64(allowlistedRequest.ExpiryTimestamp),
	}, nil
}
