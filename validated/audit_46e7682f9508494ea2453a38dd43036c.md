### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, but the `shop` value that is subsequently trusted and handed to the app's webhook handler is taken from an unauthenticated HTTP header. This breaks the intended binding `hmac_verified_bytes == identity_used_for_processing`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`), not from anything covered by the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the raw body) and secure-compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate, then forwards `request.shop` (the unauthenticated header value) directly into `WebhookMetadata`, which is the identity the host application's handler uses to attribute the webhook to a tenant: [4](#0-3) [5](#0-4) 

The documentation confirms `data.shop` is meant to be the trusted "shop domain of the webhook" that handlers key their business logic on (e.g. `shop_domain: data.shop`): [6](#0-5) 

By contrast, `Auth::Oauth::AuthQuery#to_signable_string` correctly includes `shop` inside the signed payload for OAuth callbacks, showing the gem is capable of binding the tenant identifier into the HMAC input elsewhere but does not do so for webhooks: [7](#0-6) 

This is the exact analog of the reported bug class: `sameType()` compared bytes that were not the ones actually meant to be authenticated (missing bits in the shift), causing the comparison to validate less than intended. Here, `HmacValidator.validate` validates the body bytes but the identity field (`shop`) that the rest of the pipeline treats as authenticated is never part of what was hashed — the binding `verified_bytes == bytes_used_for_tenant_identity` does not hold.

### Impact Explanation
Any unprivileged internet user who has (or creates) their own legitimate Shopify development/trial store and app installation can capture one genuine `(raw_body, hmac)` pair issued by Shopify for their own shop (since Shopify's webhook signing key is the app's `client_secret`, and any installed shop can trigger a webhook for itself). Because the header `shopify-shop-domain` is not part of the signed content, the attacker can replay the same `raw_body` + `hmac` to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still report success (it only checks the body), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that uses `data.shop` to select which tenant's records to create/update/delete (exactly as shown in the gem's own documented example) will perform that action against the wrong tenant — a cross-tenant data integrity/confidentiality breach reachable without any credentials beyond having installed the app on one's own shop.

### Likelihood Explanation
The attack requires no `api_secret_key`, no access token and no interception — only the ability to install the app on an attacker-controlled store (a normal, unprivileged install flow) and the ability to POST to the app's publicly reachable webhook endpoint, both of which are standard capabilities of any Shopify app user. The gem's documented handler pattern (`shop_domain: data.shop`) shows this is precisely how consuming applications are expected to use the field, making the exploitation path realistic rather than theoretical.

### Recommendation
Bind the tenant identity into the authenticated material for webhooks, mirroring what is already done for OAuth's `AuthQuery`:
- Change `Webhooks::Request#to_signable_string` (or the validator) to incorporate `shop` (and ideally `topic`/`webhook_id`) into the HMAC input, or
- If Shopify's webhook HMAC scheme cannot be changed (it is fixed to sign only the raw body per Shopify's webhook spec), the gem should not expose `shop` from an unauthenticated header as a trusted identity to handlers without documenting this risk, and/or should provide/require an independent mechanism (e.g., matching against the registry's expected shop for that specific webhook endpoint/session) before trusting `data.shop` for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's endpoint, capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's real `client_secret` over `B`).
2. Attacker sends a new POST to the same public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (forged)
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` with the app secret, matches `H`, and returns `true` — see: [8](#0-7) 
4. `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [9](#0-8) 
5. The host application's handler processes the attacker's data as if it belonged to the victim's shop.
