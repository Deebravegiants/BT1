### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable content solely from the raw request body, while the tenant-identifying `shop-domain` header (along with `topic` and `webhook-id`) is read independently and passed downstream unverified. This breaks the binding `hmac_signed_bytes == bytes_the_handler_trusts_for_tenant_identity`, letting an attacker who can obtain any one validly-signed webhook body (e.g. by installing the app on their own store) replay it to the app's public webhook endpoint with an arbitrary `shop-domain` header, causing the app to process attacker-controlled data as if it belonged to a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, and `#webhook_id` are pulled directly from unauthenticated HTTP headers, separate from the signed body: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (i.e., only the body) and compares it against the `hmac` header: [3](#0-2) [4](#0-3) 

Once the HMAC check passes (because the body is untouched and its HMAC is valid), the unverified `request.shop` value is forwarded straight into `WebhookMetadata` and handed to the app's registered handler as the tenant identity:



Because the HMAC only binds the body, the equality that should hold — `hmac(secret, body ‖ shop ‖ topic ‖ webhook_id) == received_hmac` binding the shop identity to the signature — instead degenerates to `hmac(secret, body) == received_hmac`, with `shop` entirely outside the signed material. Any attacker who can obtain one legitimately-signed webhook body (trivial: install the app on their own free/dev store and trigger any webhook event to their own listener) can then relay that exact body+hmac to the target app's public webhook endpoint while substituting an arbitrary `shop-domain`/`shopify-shop-domain` header value naming a different (victim) shop, and the check in `HmacValidator.validate` still passes because it never looks at headers.

### Impact Explanation
This is a cross-tenant identity confusion: the app will invoke its webhook handler believing the event originates from shop B ("dest"/tenant) while the payload and HMAC actually originated from shop A (attacker's own store). Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to look up/update the tenant's local records, revoke access, trigger billing/GDPR-related actions, or index data), this enables cross-tenant data injection or corruption purely by controlling headers on an unauthenticated HTTP request to a public endpoint. Per the rules this satisfies "cross-tenant access", a Critical-severity impact.

### Likelihood Explanation
Likelihood is high for any app exposing this gem's webhook processing endpoint publicly (the standard deployment): the attacker needs only (a) their own store, or any means to legitimately trigger any webhook of any topic for any shop, since the body's HMAC does not depend on the topic/shop at all, and (b) the ability to send an HTTP POST with custom headers to the target's public webhook URL — both are unprivileged-internet-user capabilities requiring no `api_secret_key`, no access token, and no social engineering.

### Recommendation
Include the header-derived, tenant-identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them (e.g., verify HMAC over `body + headers` the same way Shopify computes it, or reject/ignore header values that aren't corroborated by an independent authenticated source). At minimum, `Request#to_signable_string` must not diverge from the set of fields the application treats as trusted identity (`shop`, `topic`, `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (`attacker-shop.myshopify.com`) and configures a webhook listener they control (or intercepts the delivery).
2. Shopify delivers a legitimately HMAC-signed webhook, e.g.:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled JSON...}
   ```
3. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` header to the victim app's public webhook endpoint, but replaces:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb:190` recomputes the HMAC over `@raw_body` only (per `Request#to_signable_string`) — since the body is unchanged, the check passes.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled webhook data attributed to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
