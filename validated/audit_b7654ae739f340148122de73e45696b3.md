### Title
Unauthenticated `handle_unsigned` mempool validation performs full, unbounded consensus/state-proof verification for free, enabling a repeatable CPU-exhaustion DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp` exposes `handle_unsigned`, an unsigned extrinsic that lets anyone submit a batch of ISMP `Message`s (consensus updates, requests, responses, timeouts, fraud proofs) for free execution. Substrate's transaction-pool validation path (`ValidateUnsigned::validate_unsigned`) does not perform a cheap pre-check — it calls `Self::execute(messages.clone())`, which runs the *entire* message-handling pipeline (GRANDPA/BEEFY consensus verification, ancestry-chain construction/walks, MMR/merkle proof verification, storage-proof/trie verification) on every node that receives the gossip, before any fee, signature, or lightweight sanity bound is checked. There is no cap on the number or size of messages/headers/proof nodes in a single call beyond the generic block/extrinsic byte-size limit.

Because `handle_unsigned` is unsigned and free (`Pays::No`-equivalent, explicitly documented as "executed for free as unsigned transactions"), and `validate_unsigned` runs on *every* full node during transaction-pool admission and *every* re-validation on gossip/re-broadcast, an attacker can flood the network with maximally-sized, ultimately-invalid `handle_unsigned` batches to force each node to repeatedly perform expensive cryptographic/ancestry work before rejecting the transaction — directly analogous to the GitLab statement-timeout DoS, where a crafted but cheap-looking request triggers disproportionately expensive backend computation that is not properly bounded/cached against abuse by an unauthenticated actor. ### Impact Explanation
This is reachable by any unprivileged actor (no signature, no fee, no prior relationship to the chain) submitting a single extrinsic that is gossiped to the entire validator/full-node set. Because `validate_unsigned` performs the full consensus/state-proof verification workload before rejecting the message, an attacker can repeatedly force expensive CPU work (BLS/Ed25519 signature checks, BTreeMap ancestry construction and traversal, merkle/MMR/trie verification) across the network at effectively zero cost, degrading block production and transaction throughput — a network/route-level denial of service that can prevent the Hyperbridge route from delivering legitimate messages (matches the "route unable to deliver messages" impact class).

### Likelihood Explanation
High: `handle_unsigned` and its `validate_unsigned` implementation are permanently enabled, require no privilege, no stake, and no fee, and the network explicitly propagates unsigned ISMP transactions for validation by design. Constructing a large but structurally valid (though ultimately rejected) `Vec<Message>`/`FinalityProof` payload requires no special access — only encoding cost on the attacker's side, which is far cheaper than the verification cost imposed on every recipient node.

### Recommendation
Add cheap, bounded pre-checks in `validate_unsigned` before invoking `Self::execute` — e.g., enforce hard caps (via `BoundedVec` or explicit length checks) on `messages.len()`, `unknown_headers.len()`, `votes_ancestries.len()`, and proof-node counts, and reject batches exceeding these caps with `InvalidTransaction` prior to any cryptographic verification. Consider adding lightweight structural/format validation (e.g., quick hash/format sanity checks) that can filter clearly malformed submissions before the costly ancestry/consensus verification path is entered.

### Proof of Concept
1. Craft a `Message::FraudProof` (or `Message::Consensus`) payload containing two `FinalityProof<SubstrateHeader>` structures, each with `unknown_headers` populated with the maximum number of minimal dummy headers that fit within the extrinsic/block size limit (headers can be near-empty since only `parent_hash`/`number` matter for `AncestryChain` construction).
2. Submit this as an unsigned `pallet_ismp::Call::handle_unsigned` extrinsic to a full node.
3. Observe that `validate_unsigned` invokes `Self::execute` → `handle_incoming_message` → GRANDPA `verify_fraud_proof`, which builds two `BTreeMap`-based `AncestryChain`s and performs `ancestry()` walks and justification decoding over the full unknown_headers set, before ultimately rejecting the transaction as invalid.
4. Repeat/broadcast many such transactions in parallel from multiple source addresses (no fee/signature required) to amplify CPU load across all full nodes performing pool validation, degrading network throughput and delaying/blocking delivery of legitimate ISMP messages.

```rust
pub struct AncestryChain<H: HeaderT> {
	ancestry: BTreeMap<H::Hash, H>,
}

impl<H: HeaderT> AncestryChain<H> {
	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
