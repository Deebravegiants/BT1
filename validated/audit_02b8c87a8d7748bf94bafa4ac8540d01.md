### Title
Webhook shop identity not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values that are subsequently trusted and handed to the app's handler are taken from unsigned HTTP headers that the HMAC never covers.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, and for a webhook `Request`, `to_signable_string` returns just `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read directly from the `x-shopify-*`/`shopify-*` HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` passed to the app's handler, without any check that the `shop` header was itself covered by the signature: [3](#0-2) 

The identity binding this breaks, stated as an equality that should hold but does not:
`shop authenticated by HMAC` == `shop header value delivered to the handler`.

Because the HMAC only binds `secret + raw_body -> hmac`, any request bearing a `raw_body`/`hmac` pair that was validly produced for shop A can be replayed with the `x-shopify-shop-domain` header changed to shop B (or any topic/webhook-id header changed) and will still pass `HmacValidator.validate`. The gem hands this attacker-controlled `shop` value straight to the host app's webhook handler as the authenticated tenant identity.

### Impact Explanation
An app built on this gem uses `WebhookMetadata#shop` as the trusted tenant identifier to route/persist webhook data per merchant. Since `shop` is not bound to the HMAC, a party who has observed one legitimately signed webhook body (e.g., their own store's webhook, which Shopify or any recipient of that webhook can capture) can replay it while substituting a different `shop` header, and the library will report it as "verified" and dispatch it under the attacker-chosen shop identity — a cross-tenant identity confusion inside a security boundary the gem is supposed to enforce (`Errors::InvalidWebhookError` is meant to reject exactly this class of forgery).

### Likelihood Explanation
Exploitation requires only capturing/observing one valid `(raw_body, hmac)` pair for any shop using the target app (trivial for an unprivileged merchant who installed the app, or anyone who can sniff/replay an HTTP POST to the webhook endpoint) and reissuing it with a modified `shop-domain` header — no access to `api_secret_key`, access tokens, or privileged accounts is needed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signable content that `HmacValidator` verifies, or otherwise independently re-derive/verify the shop from data that is actually covered by the signature, rather than trusting header values that sit outside the HMAC's protection boundary.

### Proof of Concept
1. App receives a legitimate Shopify webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker (any party able to POST to the app's public webhook endpoint) resends the exact same body `B` and `hmac` header `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) proceeds and calls the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, even though the payload was never actually signed for `shop-b`. [4](#0-3)
