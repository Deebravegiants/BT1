### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` is computed only over the raw request body. An unprivileged attacker who owns any shop that has the app installed can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, while the HMAC signature remains valid because it never covered that header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` reads `shopify_header("shop-domain")` independently: [1](#0-0) 

`HmacValidator.validate` verifies the signature purely against `to_signable_string` (the body), so any header value, including `shop`, `topic`, `webhook-id`, and `api-version`, is unauthenticated: [2](#0-1) 

`Registry.process` trusts `request.shop` directly and forwards it, unauthenticated, to the app's registered webhook handler as the tenant identifier: [3](#0-2) 

This breaks the intended identity binding: `hmac-verified(bytes) == shop-that-produced-bytes`. In reality the gem verifies `hmac-verified(raw_body)` but hands the app `shop = header value`, and the header is never part of the bytes that were verified. Any attacker who is a valid merchant on the app (i.e., who can trigger a real webhook delivery for their own shop and capture the valid `hmac-sha256` header alongside the raw body) can resend that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still pass because the body/HMAC pair itself is untouched.

### Impact Explanation
This is a cross-tenant data-confusion vector: the webhook handler in the host application receives `WebhookMetadata` claiming to originate from the victim shop while actually carrying the attacker's own webhook payload (e.g., an `orders/create`, `app/uninstalled`, or `customers/data_request` payload). Depending on how the host app keys per-tenant state off `data.shop`, this can lead to writing/mutating another tenant's records, triggering GDPR-erasure-style logic for the wrong shop, or otherwise crossing the tenant boundary that the gem is documented to enforce via HMAC validation — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite is modest: attacker needs only to be a legitimate (even trial) merchant with the vulnerable app installed, which is an "unprivileged internet user" relative to other merchants' data. No access to `api_secret_key`, tokens, or the victim's credentials is required — only the ability to receive one webhook for their own shop and replay it with a modified header, since the gem performs no binding between the verified bytes and the `shop` value it hands to the app.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the verified payload, so a valid HMAC for one shop's payload cannot be replayed under another shop's identity. At minimum, document prominently that `Request#shop` is unauthenticated and host apps must independently verify shop identity (e.g., against a known/registered shop list) before trusting it.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and legitimately triggers a webhook (e.g., updates a product to fire `products/update`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header from the real request Shopify sent.
2. Attacker resends this exact body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. In the gem: `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged header as `shop`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds because the body/HMAC pair is unchanged — see: [4](#0-3) 
4. The app's handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker's data>, ...)` and processes it as though it were victim data/event, despite the HMAC never having authenticated that shop value.
