### Title
Permanent market freeze: `borrowed * index / RAY` overflows `i128` in interest accrual before `MAX_BORROW_INDEX_RAY` can engage - (File: common/src/rates/index.rs)

### Summary
Analogous to the OpenEXR report (an intermediate product overflowed `int32` because a widened-cast site was missed), every interest accrual in the pool computes the total debt value as `borrowed * borrow_index / RAY` via `Ray::mul` → `fp_core::mul_div_half_up`, which returns `MathOverflow` once the product leaves `i128`. `update_borrow_index` clamps the *index* at `MAX_BORROW_INDEX_RAY` (= `1e36`, i.e. a 1-billion-fold index), but the *value* ceiling `i128::MAX` (~`1.7e38` ray) is hit far earlier — for a book near the governance cap, at an index of only ~1.7–170×RAY. Every state-changing pool entrypoint calls `global_sync` (accrual) first, so once the product exceeds `i128::MAX` the market reverts permanently on every interaction.

### Finding Description
`global_sync` in `contracts/pool/src/interest.rs:20-53` runs `accrue_chunk` → `accrue_step` → `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`), which evaluates `borrowed.mul(env, new_borrow_index)`. `Ray::mul` (`common/src/math/fp.rs:50-52`) delegates to `mul_div_half_up` (`common/src/math/fp_core.rs:108-118`): the `I256` widened path keeps the intermediate exact but `.to_i128()` on the quotient returns `None` when the result exceeds `i128`, so the function panics with `GenericError::MathOverflow`. The same panic path exists in `update_supply_index` (`supplied.mul(env, old_index)`, index.rs:34) and `scaled_to_original` (`common/src/rates/scaling.rs:14-16`). `MAX_BORROW_INDEX_RAY` in `common/src/constants/pool.rs:19` is `1e36` raw — a factor of ~1e9×RAY — yet the value ceiling `i128::MAX` is only ~170× a `1e36`-ray book, so the cap never engages before the overflow. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-360`) demonstrates exactly this: accrual panics with `MATH_OVERFLOW`, `borrow_index < MAX_BORROW_INDEX_RAY`, and both `withdraw` and `repay` then revert with the same error.

### Impact Explanation
Permanent freezing of funds for the affected (hub, token) book. Because accrual precedes every verb, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `update_indexes`, `clean_bad_debt`, and `recapitalize` all hit the same panic in `accrue_chunk`. No recovery path exists without a code upgrade. All user funds in that book are frozen indefinitely.

### Likelihood Explanation
Reachable by unprivileged addresses through ordinary `supply`/`borrow` (or `multiply`/`flash_position`) calls; no privilege, leaked key, or oracle manipulation is required. The trigger is a large book (near the market's governance-set cap) at sustained high utilization on a steep rate curve so the borrow index grows enough that `borrowed * index / RAY > i128::MAX`. The requirement is real but restrictive — it needs a whale-scale market and years of high utilization as the test shows — so likelihood is moderate-low; impact is maximal, making this High severity.

### Recommendation
Cap the index by the *value* ceiling, not the raw index: before applying `new_borrow_index`/`new_supply_index`, verify `borrowed * index / RAY` fits `i128` (e.g. via `try_mul_div_half_up`/`I256`) and clamp the index to `i128::MAX / borrowed * RAY`-equivalent so accrual stays total. Alternatively, use a saturating mul-div for `calculate_supplier_rewards`/`update_supply_index` so accrual degrades gracefully instead of reverting, keeping `repay`/`withdraw`/`liquidate` usable.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance years at 98% utilization until:
assert_contract_error(failed, errors::MATH_OVERFLOW);          // update_indexes reverts
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY);             // cap never engaged
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

An unprivileged caller supplies a large position, a second (or the same) address borrows ~98% of it, and `update_indexes` is called periodically by anyone. Once `borrowed * new_borrow_index / RAY > i128::MAX`, `accrue_chunk` panics inside `calculate_supplier_rewards` (`index.rs:80`), permanently DoSing every entrypoint that accrues — `withdraw`, `repay`, `liquidate`, `update_indexes` — freezing all funds in the book.
