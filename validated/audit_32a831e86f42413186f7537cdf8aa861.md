### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant attribution despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` passes this unauthenticated `shop` value straight into `WebhookMetadata` given to the host app's handler, breaking the intended binding: `shop attributed to the payload == shop that actually sent the payload`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` verifies the signature using `verifiable_query.to_signable_string`, i.e. only the body, against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` checks only that this body-only HMAC is valid, then immediately hands the caller-supplied, unauthenticated `request.shop` (and `request.topic`) to the registered handler: [4](#0-3) 

Equality broken: `shop bound by the HMAC == shop attributed to the webhook payload by Registry.process` is **false** — the HMAC binds nothing about `shop`, only the raw body bytes.

### Impact Explanation
Any actor able to obtain one genuinely HMAC-signed webhook body+signature pair for a topic (e.g., an actor operating their own merchant store that has the app installed, which is the normal, unprivileged way third parties interact with a multi-tenant Shopify app's webhook endpoint) can replay that exact `(raw_body, hmac)` pair directly against the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. Because the signature check in this library only covers the body, the forged request passes `Utils::HmacValidator.validate` and is dispatched to the handler with `shop: request.shop` set to the attacker-chosen value. Any host application that uses this `shop` field to key per-tenant state (e.g. "delete this shop's data", "update settings for this shop", "look up encrypted credentials for this shop" as is typical for the mandatory `shop/redact`, `customers/redact`, and `customers/data_request` topics this gem explicitly special-cases) will perform that action against the wrong tenant using data that Shopify never actually signed for that tenant — a cross-tenant integrity violation.

### Likelihood Explanation
Reachable by any party that can trigger at least one legitimate webhook delivery to the app (i.e., any merchant who installs the app, which requires no elevated privilege and no leaked secret). The signature bytes and header values are both attacker-visible/attacker-suppliable in a direct HTTP request to the app's webhook route, since this gem performs no header-body binding. No `api_secret_key` or access token is required to mount the replay — only a previously captured legitimate signed body for any shop.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material, or otherwise cross-check the header-derived `shop`/`topic` against values embedded in the verified payload before dispatching to handlers, so that the identity attributed to a webhook cannot be forged independently of the HMAC-covered body.

### Proof of Concept
1. Attacker operates (or compromises) `attacker-shop.myshopify.com`, which has the target app installed. Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: customers/redact`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body `B`.
2. Attacker replays this exact request directly to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, keeping the same body `B` and the same (still-valid) `X-Shopify-Hmac-Sha256` value.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body` (`request.rb:35-38`, `hmac_validator.rb:26-31`).
4. `Registry.process` finds the `customers/redact` handler and invokes it with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: B, ...)` (`registry.rb:188-200`), causing the host app to act on `victim-shop.myshopify.com` using attacker-supplied data that Shopify never signed for that shop.

**Note on verification limits:** I was not able to fully inspect `lib/shopify_api/webhooks/webhook_handler.rb` and `WebhookMetadata`'s exact struct definition due to index coverage limits; the impact assumes (consistent with the gem's own mandatory-topic handling for `shop/redact`, `customers/redact`, `customers/data_request`) that host applications key privileged, per-tenant actions off the `shop` field passed to handlers, which is the documented purpose of that field.
