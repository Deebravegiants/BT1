### Title
`update_token` re-pointing a chain's contract without checking in-flight transfers can permanently strand user funds - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet_hyper_fungible_token::update_token` lets `CreateOrigin` overwrite `TokenContracts`/`ContractToAsset` for an `(asset, chain)` pair at any time, with no check for outstanding cross-chain messages already dispatched to/from the old contract address. Because `on_accept` and `on_timeout` authenticate incoming messages solely by looking up the *current* `ContractToAsset` mapping, any message that was already in flight through the old contract address at the moment of the update becomes unroutable and reverts on delivery, permanently stranding the user's escrowed/burned funds on the sending side with no compensating mint/refund on the receiving side.

### Finding Description
`TokenContracts` maps `(StateMachine, AssetId) → contract address`, and this address is used verbatim as the `to` field of outgoing `DispatchPost` requests in `send`: [1](#0-0) 

`ContractToAsset` is the reverse lookup that `on_accept` uses to authenticate the *source* of an incoming message: [2](#0-1) 

and that `on_timeout` uses to authenticate the destination contract of a timed-out request in order to refund the original sender: [3](#0-2) 

`update_token` mutates both `TokenContracts` and `ContractToAsset` for a chain unconditionally — it removes the old reverse mapping and installs the new one in the same call, with zero check for whether any dispatched-but-undelivered request (from `send`) still references the old contract as its destination, or whether any inbound message that was already sent by the old EVM contract is still in flight toward this pallet: [4](#0-3) 

Concretely:
1. A user calls `send` on this pallet (or the counterpart EVM `HyperFungibleToken` contract) — funds are escrowed/burned locally, and a `DispatchPost` is created addressed to the currently-configured contract on the destination chain.
2. Before that request is delivered/finalized, `CreateOrigin` calls `update_token` to re-point the chain's `token_contract` (e.g. because the EVM contract was redeployed, migrated, or reconfigured — a routine operational action, not necessarily malicious).
3. `update_token` immediately removes `ContractToAsset[chain][old_contract]` and installs `ContractToAsset[chain][new_contract]`.
4. When the in-flight message is eventually delivered, `on_accept`/`on_timeout` look up `ContractToAsset::get(source_or_dest, &from_or_to)` using the address baked into the already-created request (the old contract), which is now unmapped, so the call reverts with `UnknownSourceContract`/`UnknownContractOnTimeout`.
5. Because the request fails to be processed, the beneficiary never receives the minted/unlocked tokens, and (for the send direction) the sender's escrowed/burned tokens are also never refunded, since a rejected delivery is not treated as a `pallet-ismp` timeout that would trigger `on_timeout`'s refund path.

This mirrors the reported pattern in `UXDController.setRedeemable`: a single-shot config setter for a critical bridging/redemption address can be updated freely, and users who initiated an operation under the old configuration have no path to complete or reverse it once the configuration changes underneath them.

### Impact Explanation
Funds already escrowed or burned by a user (or minted-in-transit) can become permanently unredeemable if the chain's registered contract address is updated while their transfer is in flight. There is no on-chain safeguard (e.g., draining/checking pending requests before changing contract mapping, or preserving old mappings until pending requests clear) as exists elsewhere in the codebase — e.g., `EvmHost.updateHostParamsInternal` explicitly guards against orphaning funds by requiring the old `feeToken` balance be zero before allowing the fee-token address to change (`CannotChangeFeeToken`), and the `HostManager` rotation flow is carefully designed to always address governance traffic to the manager that is authorized at dispatch time. `update_token` has no analogous protection for the `TokenContracts`/`ContractToAsset` mapping it mutates, so an ordinary operational config change (not requiring compromise or malice) permanently loses user funds.

### Likelihood Explanation
This requires `CreateOrigin` to invoke `update_token` while at least one cross-chain transfer using the affected `(asset, chain)` pair is in flight — a plausible and even routine scenario (contract redeployment/migration, decimal correction, peer contract rotation) rather than an attack requiring privilege escalation. Given that Hyperbridge cross-chain messages can take a non-trivial time to finalize (source chain finality + Hyperbridge consensus + relay), the window during which a legitimate `update_token` call can strand in-flight transfers is realistic.

### Recommendation
Before allowing `update_token` (or the corresponding "remove chain" path) to overwrite/delete an existing `(chain, asset)` contract mapping, either:
- Retain the old `ContractToAsset` entry (in addition to adding the new one) for a configurable grace/challenge period so in-flight deliveries and timeouts against the previous contract can still be authenticated and resolved, or
- Require that no pending dispatched/undelivered requests exist for the `(chain, asset)` pair being updated before allowing the swap (analogous to the `CannotChangeFeeToken` balance check in `EvmHost`), or
- Version the contract mapping so `on_accept`/`on_timeout` can resolve against the mapping that was active when the request was originally dispatched, rather than the current one.

### Proof of Concept
1. `CreateOrigin` registers asset `A` on `StateMachine::Evm(X)` pointing to contract `C1` via `register_token`.
2. User calls `send` for asset `A` to `Evm(X)`: local tokens escrowed/burned, `DispatchPost{ to: C1, ... }` created and dispatched (not yet finalized/delivered).
3. `CreateOrigin` calls `update_token` with `add_chains = { Evm(X): ChainConfig { token_contract: C2, ... } }` — this removes `ContractToAsset[Evm(X)][C1]` and inserts `ContractToAsset[Evm(X)][C2]`.
4. The EVM-side counterpart contract at `C1` (or the relayed message referencing `C1` as `to`) eventually attempts delivery/timeout handling on this pallet; `on_accept`/`on_timeout` call `ContractToAsset::get(Evm(X), &C1)`, which now returns `None`, causing `Err(HftError::UnknownSourceContract)` / `Err(HftError::UnknownContractOnTimeout)`.
5. The user's originally escrowed/burned tokens from step 2 are never refunded (delivery/timeout processing reverted rather than crediting the refund path), and any counterpart-side minted/locked tokens intended for the beneficiary are never released — funds are stranded.

Note: I was unable to trace the exact `pallet-ismp` behavior for a request whose destination-module `on_accept` call reverts (whether it is retried, dropped, or eventually surfaces via `on_timeout` with the *current* mapping) since that logic lives outside the `hyper-fungible-token` pallet; verifying this end-to-end path in `pallet-ismp`'s dispatch/timeout machinery would require a dedicated Devin session with full repository and test execution access.

		pub fn update_token(
			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}

	fn on_timeout(&self, request: Request) -> Result<Weight, anyhow::Error> {
		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
				}
				let beneficiary: T::AccountId = sender_bytes.into();
