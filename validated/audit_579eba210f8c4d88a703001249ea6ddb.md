Found the exact binding break: `ShopifyAPI::Webhooks::Request#shop` (the `shop-domain` header) is used by `ShopifyAPI::Webhooks::Registry.process` to build the `WebhookMetadata` handed to the app's handler, but the HMAC covers only `@raw_body`, not the `shop-domain` header.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-spoofing on valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , while `shop` is read directly from the `shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that signature [2](#0-1) . `Registry.process` validates the HMAC against the body only, then trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Finding Description
The equality broken is: **shop bytes verified by HMAC ≠ shop bytes acted upon by the handler**. `HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string`, which for `Request` is exclusively `@raw_body` [4](#0-3) [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled straight from attacker-controllable HTTP headers [5](#0-4) , with no inclusion in the signed payload. This is the same class of bug as the report: a value acted upon (`shop`, analogous to the vote-reset flag) is not covered by the check that is supposed to validate it (HMAC, analogous to `_reset()` clearing state) — so it stays trusted/"true" for a value the verification step never touched.

### Impact Explanation
An attacker who can produce (or replay) an HTTP request with a body whose HMAC matches the app's secret for *some* shop's legitimate webhook (e.g., by observing/replaying a legitimately delivered webhook, or if any request forwarding/relay preserves the body but not headers) can substitute an arbitrary `shop-domain` header. `Registry.process` will pass this attacker-chosen shop identity to the handler [6](#0-5) , which most host apps use as a tenant key to look up the shop's session/data. This crosses the cross-tenant boundary: a webhook payload validated as authentic can be attributed to the wrong shop, letting one tenant's event data be processed under another tenant's identity — matching the "cross-tenant access" Critical impact category, since downstream apps commonly key session lookups purely off `WebhookMetadata#shop`.

### Likelihood Explanation
Exploitation requires an attacker to control or intercept the delivery path enough to change headers while keeping the body (and thus HMAC) intact — e.g., a reverse proxy, load balancer, or webhook-relay misconfiguration that forwards/duplicates requests but rewrites/omits the `shop-domain` header, or an attacker capturing one shop's webhook body and replaying it with a forged `shop-domain` header alongside the original (still-valid, since unbound) HMAC. This does not require the `client_secret` or an access token, matching the "unprivileged internet user" threat model.

### Recommendation
Include the shop-identifying header (`shop-domain`) in the HMAC-signable string, or independently verify the shop domain (e.g., cross-check it against session storage or the known set of installed shops) before dispatching to a handler, so the shop the signature vouches for is provably the same as the shop the app acts on. Alternatively, document/require that the signable string cover the exact headers exposed via `WebhookMetadata`.

### Proof of Concept
```ruby
raw_body = '{"id": 1}'
secret = ShopifyAPI::Context.api_secret_key
valid_hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body))

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,      # HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body,
# yet request.shop ("victim-shop.myshopify.com") is handed to the handler unverified.

          unless handler
