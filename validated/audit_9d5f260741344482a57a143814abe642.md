## Title
Webhook shop-domain header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` (derived from the `X-Shopify-Shop-Domain` HTTP header) as the tenant identifier used by webhook handlers, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, not any header. This breaks the binding: `shop == authenticated tenant` while the HMAC only certifies `raw_body == signed by api_secret_key`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns solely the raw body: [1](#0-0) 

`shop` is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` (the raw body) only: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` directly to the app's handler as the authenticated tenant, with no cross-check that the body actually belongs to that shop: [4](#0-3) 

Because the HMAC is computed only over the raw body and the shared `api_secret_key` is the same for every merchant of a given app, any merchant who installs the app can receive a validly-signed webhook for their own shop (e.g. a webhook whose body they can predict or influence, such as `app/uninstalled` or a metafield/product webhook with attacker-supplied content). That merchant can then replay the exact same body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The signature still validates because the header is not part of the signed content, so `Registry.process` will invoke the handler with `shop: <victim shop>` and the attacker-controlled body — a cross-tenant confusion.

### Impact Explanation
This is a cross-tenant identity-binding break: the value the gem asserts as "shop" is not bound to the payload the merchant secret actually signed. Depending on the topic/handler, an attacker-controlled webhook body can be misattributed to an arbitrary victim shop, letting an unprivileged (but app-installed) attacker inject fabricated events (e.g., fake `app/uninstalled`, fake GDPR/customer data, or fake resource-update payloads) that the host application will process as though they originated from a different merchant's store. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to install the app on their own store (a normal, unprivileged action available to anyone who can install a public/custom Shopify app) and to have any webhook topic whose body is attacker-influenced or predictable enough to be replayed against a different shop's identity. No secrets, tokens, or privileged access are required — only observation/capture of one genuinely-signed webhook request sent to the app's own publicly reachable webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or independently verify that the shop-domain header corresponds to a shop that is entitled to produce the given body/topic combination before dispatching to the handler. At minimum, `Webhooks::Request#to_signable_string` should not be limited to the raw body when the gem intends `shop` to be a trusted, tenant-scoped value.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or otherwise obtains) a legitimately Shopify-signed webhook delivery to the app's endpoint, e.g. topic `app/uninstalled`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw body, computed with the app's shared api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker resends the identical raw body and HMAC header to the same endpoint but replaces the header with:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks the raw body against the HMAC), and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"`, causing the host application to process an attacker-forged event as if it came from the victim's store.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
