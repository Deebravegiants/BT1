### Title
Escrow release/refund to a fixed, non-updatable beneficiary can be permanently blocked by token-level address blocklisting - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`'s escrow release path (`_withdraw`) always sends tokens directly to a beneficiary address that is fixed at order-placement (`order.user`) or fill-time (the filler's `msg.sender`) and can never be changed afterward. If that address becomes blocklisted by the underlying ERC-20 token (e.g. USDC/USDT-style compliance blacklists) before the cross-chain settlement message is delivered, the transfer permanently reverts and the escrowed funds can never be released, mirroring the reported RFPSimpleStrategy issue where a recipient blocked by the token cannot receive funds and has no way to update the payout address.

### Finding Description
`_withdraw` in `IntentsBase.sol` transfers escrowed tokens straight to `beneficiary` with no fallback or recovery path: [1](#0-0) 

The beneficiary for a `RedeemEscrow` message is the filler's address, fixed the moment they call `fillOrder` on the destination chain (`bytes32(uint256(uint160(msg.sender)))`): [2](#0-1) 

The beneficiary for a `RefundEscrow`/cancellation is always `order.user`, and the documentation explicitly states this cannot be changed by anyone, including a relayer acting on the user's behalf: "The caller pays the dispatch cost, but cannot change `WithdrawalRequest.beneficiary`: the refund always goes to `order.user`." [3](#0-2) 

When the settlement message (`RedeemEscrow`/`RefundEscrow`) is delivered via ISMP, `EvmHost.dispatchIncoming` performs a raw `.call` to `onAccept`. If it reverts, the receipt is deleted "so it can be retried" — but a token-level blocklist on the beneficiary makes the transfer inside `_withdraw` deterministically revert every single retry, forever: [4](#0-3) 

Unlike `WrappedHyperFungibleToken.onAccept`, which explicitly hedges against a beneficiary unable to receive value (native-ETH push failure) by falling back to an ERC-20 transfer, and unlike `HyperbridgeLzEndpoint.onAccept`, which isolates the downstream call in a `try/catch` and persists a retryable/recoverable payload hash so a stuck delivery doesn't brick the channel, `IntentGatewayV2`/`IntentsBase._withdraw` has no such isolation, no alternate-beneficiary mechanism, and no recovery primitive (`retryPayload`, `clear`, `nilify`, etc.): [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by an unprivileged party through the ordinary intents flow: any solver/filler who fills a cross-chain order, or any user who places/cancels an order, is exposed. If the beneficiary address is added to a token's blocklist after the order is placed/filled but before the corresponding `RedeemEscrow`/`RefundEscrow` message settles (a realistic timing window given cross-chain finality delays), the escrowed input tokens become permanently unrecoverable — there is no owner override, no beneficiary-change function, and no fallback transfer path in `_withdraw`. This matches the "Medium" severity class of the original report: legitimate funds are permanently locked due to an unchangeable recipient address colliding with token-level access control.

### Likelihood Explanation
Likelihood depends on the beneficiary being blocklisted by a compliant/blacklist-capable ERC-20 (USDC, USDT, and similar centrally-administered stablecoins are common intent-gateway assets) within the window between order placement/fill and settlement delivery. This is not attacker-controlled but is a realistic external event (regulatory/compliance blocklisting, sanctions, exchange freezes) that the protocol has no mitigation for, and once triggered, the outcome (permanent freeze, not just delay) is deterministic and irreversible under the current code.

### Recommendation
Add a pull-based/claimable withdrawal fallback in `_withdraw` (or a subsequent explicit call) that traps the transfer failure (e.g., via a low-level call/try-catch as done in `WrappedHyperFungibleToken`) and credits the beneficiary in an internal claims ledger instead of reverting on failure, plus an admin/user-triggered mechanism to redirect the payout to a new address, or an escape hatch after a timeout period.

### Proof of Concept
1. A user places a cross-chain order via `placeOrder`, escrowing USDC on the source chain with `order.user = U`.
2. A solver fills the order on the destination chain (`_fillCrossChain`), which dispatches a `RedeemEscrow` message with `beneficiary = solver` back to the source chain.
3. Before the `RedeemEscrow` message settles, either `U`'s address (in a cancellation scenario) or the solver's address is added to USDC's blocklist by Circle.
4. When the relayer delivers the message, `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept` → `_withdraw`, which calls `IERC20(USDC).safeTransfer(beneficiary, amount)`; this reverts because USDC's `transfer` reverts for blocklisted recipients.
5. `dispatchIncoming` catches the failure, deletes the request receipt "so it can be retried" — but every future retry hits the same blocklist check and reverts identically.
6. The escrowed USDC remains locked in the `IntentGatewayV2` contract indefinitely, with no function available to redirect it to a different address. [1](#0-0) [7](#0-6)

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
