The gem's webhook processing pipeline replicates the analog bug class exactly: a field that is *acted on* (routing/tenant identity) is not covered by the HMAC that is *verified*.

### Title
Webhook `shop-domain` and `topic` headers are unauthenticated and can be freely spoofed on any valid `(body, HMAC)` pair, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — all of which are used by `Registry.process` to select the handler and to build `WebhookMetadata` passed to app code — come from unsigned HTTP headers. This breaks the identity binding: `hmac_verified(body) == true` is treated as proof that `(shop, topic)` are also authentic, but they are never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are read directly from attacker-controlled headers (`x-shopify-shop-domain` / `shopify-shop-domain`, `x-shopify-topic` / `shopify-topic`) with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate_signature` verifies the HMAC only over `to_signable_string` (i.e., the body), so it never checks that `shop`/`topic` match what was actually signed: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC passes, then routes using the unauthenticated `request.topic` and forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which the host application uses as the tenant identity for the event: [4](#0-3) 

Because the HMAC signs only the raw body, any `(body, hmac)` pair that was ever valid for *any* shop/topic combination remains valid forever for *every* shop/topic combination — the equality the code implicitly assumes, `hmac_valid(body) ⇒ shop_header == originating_shop`, does not hold.

### Impact Explanation
An attacker who is themselves a merchant/tenant of the host app (or who otherwise obtains one legitimate `(body, hmac)` pair delivered to their own shop, which requires no privileged access to the app's `client_secret`) can replay that exact body with the identical HMAC while substituting the `shop-domain` header for a victim shop and the `topic` header for any registered topic (e.g. `app/uninstalled`, `customers/data_request`, or an order/customer webhook). `Registry.process` will validate the HMAC successfully and dispatch the forged event as if it genuinely originated from the victim shop. Any host application that keys tenant state, access-token revocation, or data updates off `WebhookMetadata#shop`/`#topic` is exposed to cross-tenant data corruption or forced state changes for a shop the attacker does not own — this is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to have received at least one legitimate webhook delivery (for any topic) to their own store, which is trivial for any merchant who has installed the app — no secret, token, or privileged access is required. Once obtained, forging the headers to target an arbitrary victim shop/topic requires no cryptographic work.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (or otherwise cryptographically bind them to the body before verification) so that a verified HMAC also attests to the header values that the app relies on, instead of trusting `x-shopify-shop-domain`/`x-shopify-topic` as unauthenticated input.

### Proof of Concept
```ruby
# Step 1: Attacker's own shop legitimately receives any webhook delivery, e.g.:
raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
# captured from attacker's own store's genuine "orders/create" webhook to attacker.myshopify.com

# Step 2: Attacker resends the SAME body+hmac to the app's webhook endpoint,
# but swaps the shop-domain and topic headers:
headers = {
  "x-shopify-topic" => "app/uninstalled",          # forged topic
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # unchanged, still valid because body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Step 3: HMAC check passes because it only checks raw_body, not shop/topic
ShopifyAPI::Webhooks::Registry.process(request)
# => handler for "app/uninstalled" is invoked with WebhookMetadata.shop == "victim-shop.myshopify.com"
``` [4](#0-3) [5](#0-4)

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
