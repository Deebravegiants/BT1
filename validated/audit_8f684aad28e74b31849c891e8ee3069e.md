### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted by the handler but not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw JSON body of an inbound webhook, while the `shop-domain`, `topic`, and `webhook-id` values that `ShopifyAPI::Webhooks::Registry.process` passes on to the app's handler are taken from unauthenticated HTTP headers. This breaks the intended binding `hmac == HMAC(secret, body ‖ shop ‖ topic)`; only `hmac == HMAC(secret, body)` actually holds. Since the app's `client_secret` used to sign Shopify webhooks is a single per-app secret (not per-shop), any merchant who has installed the app can generate a legitimately-signed webhook (by performing the triggering action, e.g. creating an order in their own store) and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the `X-Shopify-Shop-Domain` header. `Registry.process` accepts it as valid and calls the handler with `shop: <attacker-chosen value>`, causing cross-tenant data confusion in any host application that uses `data.shop` to key storage or authorization decisions.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers, with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the body) and compares it to the header-supplied `hmac-sha256` value, using the app's single shared `api_secret_key`: [3](#0-2) 

`Registry.process` gates only on this body-only HMAC check, then forwards the unauthenticated `shop`/`topic`/`webhook_id` header values straight into `WebhookMetadata` for the handler to act on: [4](#0-3) 

Because Shopify signs webhooks with the app's `client_secret` (a per-app secret shared across every shop that has installed the app, not a per-shop secret), a malicious merchant who has installed the app can:
1. Trigger a real webhook to their own shop (e.g., `orders/create`) and capture the raw body plus the genuinely-valid `X-Shopify-Hmac-SHA256` header Shopify sends them.
2. Replay that exact `(body, hmac)` pair to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain (and/or a different `X-Shopify-Topic`/`webhook-id`).
3. `HmacValidator.validate` still succeeds because it only checks that the body matches the app secret's HMAC — it never verifies that the shop/topic claimed in the headers is the one Shopify actually associated with that signature.

The equality the gem should be enforcing is:
`hmac == HMAC(secret, body, shop, topic)` (i.e., the shop/topic the app acts on == the shop/topic Shopify actually signed for)

but the gem only enforces:
`hmac == HMAC(secret, body)`

This is the exact bug class described in the analog report: a field the code acts on (here, `shop`) is not covered by the integrity check that's supposed to authenticate the whole request (here, the webhook HMAC), letting an attacker overwrite/misattribute state for a target that they don't control — the multi-tenant equivalent of overwriting another user's `pendingFlashDecision` in the original finding.

### Impact Explanation
This is a cross-tenant integrity issue: any application built with this gem that trusts `WebhookMetadata#shop` (as documented/intended usage, since `Registry.process` is the only sanctioned way to dispatch verified webhooks) can be made to process attacker-supplied, but "HMAC-validated," webhook data under a victim shop's identity. Depending on what the host app does with webhook data (updating per-shop records, triggering per-shop side effects, uninstall/GDPR handling, etc.), this enables cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control, without needing the victim's or the app's access token — only requiring the attacker to be a legitimate (even free/trial) installer of the same app. This matches the Critical/High "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that has more than one installing merchant and where at least one merchant is malicious or compromised: capturing a valid webhook payload/HMAC is trivial (the attacker is a legitimate recipient of their own shop's webhooks), and re-sending an HTTP request with a modified header requires no special access, credentials, or knowledge of the `client_secret`.

### Recommendation
Include the fields the application is expected to trust (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for verification, or otherwise cryptographically bind them, e.g. by having `to_signable_string` combine the raw body with a canonical representation of these headers, or by not exposing/relying on unauthenticated headers at all and instead recommending consumers only trust the fields Shopify's HMAC actually covers. At minimum, document clearly that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT authenticated by `Utils::HmacValidator.validate`, so host apps do not assume otherwise.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers an `orders/create` webhook handler via `ShopifyAPI::Webhooks::Registry`.
2. Attacker creates an order in their own store, causing Shopify to POST a legitimately HMAC-signed webhook to the app, e.g.:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-signature-over-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 123, ...}
   ```
3. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(api_secret_key, raw_body)` — unaffected by the header change: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body, believing it is a genuine webhook from the victim shop.

(Note: I could not fully inspect `lib/shopify_api/webhooks/webhook_handler.rb` and `WebhookMetadata`'s exact field list due to the final iteration limit, but `registry.rb` lines 198-199 confirm `shop: request.shop` is passed directly from the unauthenticated header into the data structure delivered to host-app handlers.)
