### Title
Cross-tenant webhook spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, never the shop header. `Registry.process` verifies the HMAC and then hands `request.shop` straight to the app's webhook handler as trusted tenant identification, so the shop attribution can be forged independently of the signature check.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read from a header that is not part of that signable content: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`, i.e. only the body, and never touches the shop header: [4](#0-3) 

`Registry.process` validates the HMAC and then trusts `request.shop` to build the metadata handed to the app's registered handler, without any additional binding between the verified body and the shop header: [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop header value used for tenant routing` ≠ `shop value covered/authenticated by the HMAC signature`.

Because the app's `api_secret_key` is a single value shared by the app across every merchant installation (it is not per-shop), any merchant who installs the app on their own store obtains a source of validly HMAC-signed webhook deliveries (signed with the app's one client secret). Such a merchant — an "unprivileged" party relative to any other merchant's tenant data — can capture one of their own legitimate webhook deliveries and replay it with only the `X-Shopify-Shop-Domain` header modified. `Utils::HmacValidator.validate` and `Registry.process` will accept it as valid because the signature only ever depended on the body, and `request.shop` will report the victim shop's domain to the application's webhook handler.

### Impact Explanation
If the host application (following this gem's documented pattern of using `WebhookMetadata#shop` to select the tenant record/session to act on, as done in `Registry.process`) trusts `request.shop` for routing, an attacker-controlled shop label reaching application logic under a validly-signed envelope enables cross-tenant data confusion: attacker-supplied webhook payloads can be attributed to, and processed against, a victim shop's stored session/state. This satisfies the "cross-tenant access" criterion, since the trust boundary between tenants (shops) is bypassed using only the attacker's own legitimate installation, not the victim's credentials.

### Likelihood Explanation
Likelihood is limited by the need to already be a legitimate merchant/installer of the target app (to obtain a validly signed webhook envelope from the shared `client_secret`), but no other privilege, secret, or victim credential is required — replaying a captured webhook with a modified, unsigned header is trivial. This is a plausible motivated-insider / competitor scenario rather than a fully anonymous internet attacker, but it crosses the tenant isolation boundary this gem is expected to enforce for HTTP webhook delivery.

### Recommendation
Bind the `shop` identity to the HMAC-verified content: reject webhook processing unless the shop domain is confirmed against data authenticated independently of client-controlled headers (e.g. cross-check against the shop recorded when the corresponding webhook subscription/session was registered), or include the shop domain in the signable string used for HMAC verification so any tampering with the header invalidates the signature.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook HTTP request delivered by Shopify (body `B`, valid `X-Shopify-Hmac-Sha256` computed over `B` with the app's single `api_secret_key`, and header `X-Shopify-Shop-Domain: attacker.myshopify.com`).
2. Replay the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`. The HMAC value is left untouched.
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered header into `shop`; `Utils::HmacValidator.validate` succeeds because it only checks `body` against the unchanged signature (`hmac_validator.rb:26-31`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting `victim.myshopify.com` (`registry.rb:198-199`), causing the application to process attacker-supplied data as belonging to the victim tenant.

          received_signature = verifiable_query.hmac
