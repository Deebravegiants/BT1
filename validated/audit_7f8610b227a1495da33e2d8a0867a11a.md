### Title
Webhook HMAC does not bind the `shop-domain` header, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` then verifies the HMAC solely against that raw body. Because the `shop-domain` header used to identify the tenant is never part of the signed content, a request whose body/HMAC pair is genuinely valid (signed by Shopify for one shop) can be replayed with an arbitrary `shop-domain` header and will still pass HMAC validation, letting an attacker impersonate any other shop to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` purely from headers: [1](#0-0) 

But the value that is actually HMAC-verified is only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` (both header-derived, unsigned) to build `WebhookMetadata` that is handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Because the HMAC only covers the body, this equality does not hold — an attacker can keep a valid `(body, hmac)` pair (obtained from a webhook Shopify legitimately delivered for their own store, since all shops share the same app `client_secret`/HMAC key) and swap the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to any other shop domain. `HmacValidator.validate` still returns `true` because it never looks at those headers, and `Registry.process` forwards the forged `shop` straight to the handler as authenticated data.

### Impact Explanation
This breaks tenant isolation at the gem level: the library's own webhook-authenticity primitive gives host applications no cryptographic guarantee that the `shop` (or `topic`/`webhook_id`) it reports actually corresponds to the shop that produced the signed payload. A host app that trusts `WebhookMetadata#shop` (which is the documented, intended use of this API) can be made to process/store attacker-supplied data under a victim shop's identity — a cross-tenant data-injection primitive, which the rules classify as Critical impact.

### Likelihood Explanation
The attacker needs only an account they control: any store where they can install the target app (development/trial store) receives real webhooks HMAC-signed with the app's single, shop-independent `client_secret`. They capture one `(raw_body, X-Shopify-Hmac-Sha256)` pair from a delivery they legitimately received, then POST it to the app's public webhook endpoint again while replacing `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with the victim's values. No secret material, session, or privileged access is required — only a normal, unprivileged Shopify Partner/dev account and knowledge of the app's (typically single, static) webhook URL.

### Recommendation
Bind the tenant/topic identity into what is verified: either include `shop`, `topic`, and `webhook_id` in the value that `HmacValidator` verifies (Shopify webhook signature itself only covers body per Shopify's spec, so this must be enforced at the app layer), or have `Registry.process`/`Webhooks::Request` require the caller to supply the expected shop (from the app's own installed-shop lookup) and assert it matches the header value before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must be cross-checked by the host application against a known/installed shop list before being trusted for tenant-scoped operations.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own dev store "attacker.myshopify.com"
#    and receives a legitimate webhook delivery, e.g. orders/create with body B and
#    a valid X-Shopify-Hmac-Sha256 header H (H = HMAC-SHA256(client_secret, B)).

# 2. Attacker replays the exact same body B and hmac H to the app's public
#    webhook endpoint, but swaps the shop-domain header:
POST /webhooks HTTP/1.1
Host: victim-app.example.com
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H            # unchanged, still valid for body B
X-Shopify-Shop-Domain: victim-shop.myshopify.com   # forged
X-Shopify-Webhook-Id: attacker-controlled

B

# 3. ShopifyAPI::Webhooks::Registry.process(request) calls:
#    Utils::HmacValidator.validate(request)  # => true, since it only checks HMAC(B) == H
# 4. The handler receives WebhookMetadata with shop: "victim-shop.myshopify.com"
#    and body B, as if Shopify itself had delivered this data for the victim shop.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
