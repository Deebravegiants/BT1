## Finding

### Title
`EvmHost.dispatch()`/`fundRequest()` and `IntentGatewayV2.placeOrder()` price relayer-fee swaps off the live, unprotected Uniswap V2 spot price, letting a sandwiching attacker extract value from any native-token dispatcher/order placer - (File: `evm/src/core/EvmHost.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
Both `EvmHost` (the core dispatcher) and `IntentGatewayV2` (the intents module) let a caller pay a Hyperbridge relayer fee in native token, converting it to `feeToken` via `IUniswapV2Router02.swapETHForExactTokens` using the pool's instantaneous, unbounded spot price - no TWAP, no explicit `amountInMax`, no minimum-output/slippage guard beyond the `msg.value` supplied. This is the same bug class as the referenced Derby `claimTokens`/`withdrawRewards` report: a swap amount is derived from a manipulable on-chain quote at the moment of a permissionless call.

### Finding Description
`EvmHost.dispatch(DispatchPost)` swaps native token to `feeToken` for the relayer fee using the router's live reserves: [1](#0-0) 

The same unguarded pattern recurs in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

and in `IntentGatewayV2.placeOrder`, which escrows `order.fees` by swapping any attached native value into `feeToken` the same way: [4](#0-3) 

All of these use `swapETHForExactTokens{value: <caller-supplied native amount>}(feeAmount, [WETH, feeToken], ..., block.timestamp)`, i.e. the caller's entire native remittance is offered as `amountInMax`, and the router prices `feeAmount` at whatever the current pool reserves say. There is no TWAP oracle and no independent minimum-received check on the ETH side. `dispatch()` in `EvmHost.sol` additionally has no refund path at all for any ETH left unconsumed by the swap - unlike `IntentGatewayV2.placeOrder`, which explicitly computes `msgValue -= amounts[0]` and refunds the caller (lines 386, 395-397 in `IntentGatewayV2.sol`), `EvmHost.dispatch()` simply forwards `msg.value` to the router and never returns the router's refund (paid to `address(this)`, i.e. the host) back to the caller.

An attacker can flash-loan-manipulate the configured `uniswapV2Router`'s WETH/feeToken pool immediately before a victim's `dispatch{value: ...}(...)` (or `fundRequest`/`placeOrder`) transaction lands, spiking the WETH price of `feeToken`. The victim's fixed-output swap then consumes more of the supplied native value than the fair-price amount would require (or reverts if the buffered `msg.value` is insufficient), while the attacker profits from unwinding the manipulated position afterward - a textbook sandwich against a spot-priced, permissionless swap, exactly the vulnerability class flagged in the referenced report. On `EvmHost.dispatch`, because unconsumed ETH is never returned to the caller, any favorable price movement's "refund" is a locked donation to the host instead of the payer, compounding the fund-loss/fund-freezing surface.

### Impact Explanation
Any account can call `dispatch()`, `fundRequest()`, or `IntentGatewayV2.placeOrder()` with native token - no privilege required. A sandwich against the live spot price directly overcharges the native amount consumed for a fixed `feeToken` output, transferring value from the dispatcher/order-placer to the attacker, and separately, `EvmHost.dispatch()`'s missing refund path permanently strands any leftover ETH in the host contract instead of returning it to the caller. This satisfies the "theft of funds" / "permanent freezing of funds" bar via a manipulated, unbounded on-chain swap quote reachable from a single dispatched request or placed order.

### Likelihood Explanation
Any liquidity-light or thinly-traded `uniswapV2` WETH/feeToken pool configured for a given `EvmHost`/`IntentGatewayV2` deployment is directly sandwichable with a flash loan, and the attack requires no special permissions - just watching the mempool for native-value `dispatch`/`fundRequest`/`placeOrder` calls, which are a normal, expected usage path documented for user-facing apps.

### Recommendation
- Require an explicit, caller-supplied `amountInMax` (or `minAmountOut` equivalent) validated against a TWAP or an off-chain-quoted bound, rather than implicitly using the full `msg.value` as slippage tolerance.
- Refund any native token not consumed by the swap back to `msg.sender`/`post.payer` in `EvmHost.dispatch`, `dispatch(DispatchGet)`, and `fundRequest`, mirroring the refund already implemented in `IntentGatewayV2.placeOrder`.
- Consider pricing the native-to-feeToken conversion from a TWAP oracle (e.g., Uniswap V3 TWAP or an external price feed) instead of the instantaneous V2 reserves, consistent with the original report's recommendation.

### Proof of Concept
1. Attacker monitors the mempool for a `dispatch{value: v}(post)` (or `fundRequest`/`placeOrder`) call targeting `EvmHost`'s configured `uniswapV2Router` WETH/feeToken pool.
2. Attacker front-runs with a large WETH→feeToken swap (or flash-loan-funded swap) to spike the WETH price of `feeToken`.
3. Victim's transaction executes `swapETHForExactTokens{value: v}(post.fee, [WETH, feeToken], address(this), block.timestamp)` at the manipulated price - it either reverts (griefing) or consumes a larger share of `v` than fair value, with any excess refunded to the host contract, not the victim (`evm/src/core/EvmHost.sol:921-932`).
4. Attacker back-runs, reversing the price manipulation and capturing the difference as profit; any ETH stranded in the host from step 3 remains permanently inaccessible to the victim.
