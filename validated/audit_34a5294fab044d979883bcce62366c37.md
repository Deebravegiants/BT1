This confirms the documentation explicitly claims `Registry.process` "will verify the request did indeed come from Shopify" (line 125 of `docs/usage/webhooks.md`), and that `data.shop` is a trustworthy field returned to the handler (line 14). This is a documented guarantee that the gem itself does not fully deliver on, since `topic`/`shop`/`webhook_id`/`api_version` headers are excluded from the HMAC-protected payload.

### Title
Webhook shop/topic/webhook_id/api_version headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the body bytes, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [2](#0-1) . Yet `Registry.process` treats `request.shop` (and `request.topic`) as an authenticated tenant identifier and forwards it unmodified into the handler's `WebhookMetadata` [3](#0-2) . This breaks the intended binding `authenticated_body == body_the_shop_header_claims_to_belong_to`.

### Finding Description
`Request` parses the shop domain, topic, webhook id, and API version purely from unauthenticated headers [4](#0-3) , while the only value fed into the signature check is `@raw_body` [1](#0-0) . `HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) and does a secure compare against the supplied `hmac` header [5](#0-4) . Because every shop that has this multi-tenant app installed shares the same `Context.api_secret_key`, any tenant can obtain a validly HMAC'd `(body, hmac)` pair for their own store (simply by triggering a subscribed event in their own shop) and then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header naming a victim shop. `HmacValidator.validate` still returns `true` because the header fields it never inspects were changed, and `Registry.process` dispatches the (attacker-controlled but victim-attributed) request to the handler as if it genuinely originated from the victim shop [3](#0-2) . The docs advertise `Registry.process` as verifying "the request did indeed come from Shopify" and that `data.shop`/`data.topic` are reliable fields for the handler to act on, reinforcing that host apps are expected to trust these values as authenticated. This is the same bug class as the reported Solidity issue: a field that is acted upon downstream (the access-list item / the shop-domain header) is not actually covered by the cryptographic check (RLP re-encoding / HMAC), so the verified bytes and the bytes trusted for identity diverge.

### Impact Explanation
This breaks the tenant-isolation binding `hmac_verified_payload == shop_the_handler_attributes_it_to`, allowing a malicious but otherwise unprivileged merchant who has installed the app on their own store to make the host application ingest their crafted event data under another merchant's identity (cross-tenant data confusion/injection). Depending on how the host app uses `data.shop` (e.g., to look up the tenant's session/access token, update per-tenant database records, or trigger tenant-scoped side effects), this can lead to cross-tenant data corruption or actions being taken against the wrong merchant account — a Critical, cross-tenant impact per the accepted impact categories.

### Likelihood Explanation
Exploitation requires no possession of `api_secret_key`, no access token, and no privileged account — only a normal, unprivileged installation of the app on the attacker's own shop (which any merchant can do) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (which must be internet-reachable for Shopify to call it). The attacker only needs to capture one legitimately signed webhook delivered to their own installation and replay it with a modified `shop-domain`/`topic` header.

### Recommendation
Bind the header-derived identity fields into the authenticated payload, e.g., include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (mirroring how `AuthQuery#to_signable_string` binds `shop`, `code`, `host`, `state` into its HMAC input [6](#0-5) ), or otherwise have `Registry.process`/the handler cross-check the header `shop` against an independently verified session/shop record before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (a normal, unprivileged installation).
2. Attacker triggers a subscribed webhook event (e.g., `orders/create`) in their own store; Shopify POSTs to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request (they control the receiving traffic since it targets their own registered endpoint/proxy) and replays it to the same endpoint, keeping body `B` and the HMAC header identical, but changing `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the unchanged HMAC [1](#0-0) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B` (attacker-crafted content, e.g., a fabricated order), which the host app processes as authentic data belonging to the victim tenant [3](#0-2) .
