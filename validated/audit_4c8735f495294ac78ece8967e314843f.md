This confirms the critical finding: the docs explicitly claim `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and the sample handler treats `data.shop` as the authenticated tenant identifier for downstream work (`shop_domain: data.shop`) [2](#0-1) . But the shop value is never cryptographically bound to the signed content.

### Title
Webhook shop-domain identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity solely by checking the HMAC of the raw body, yet passes the unauthenticated `shop-domain` header through to the app's handler as the trusted tenant identifier. Because the HMAC secret (`api_secret_key`) is shared by every shop that installs the app, any merchant (an ordinary, unprivileged internet user who installs the public app on their own store) can obtain a genuinely-signed `(raw_body, hmac)` pair for their own shop, then replay it with the `shop-domain` header swapped to any other shop, and it will pass verification while being attributed to the victim shop.

### Finding Description
`Registry.process` performs exactly one authenticity check:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [3](#0-2) 

`HmacValidator.validate` calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string`: [4](#0-3) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body — no headers are included:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [5](#0-4) 

Meanwhile `shop` is read directly from an attacker-controllable header with no cryptographic binding to the signature:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

This is exactly the identity-binding break called out in the analog class: **a field acted on (`shop`, used as the tenant key passed to the handler) but not covered by the HMAC** that is verified. The equality that should hold — `hmac_signed_scope == shop_used_for_tenant_attribution` — does not; the HMAC only proves `body` integrity, never `shop`.

Because `api_secret_key` is a single per-app secret shared across every installing shop (not a per-shop secret), any of the app's own merchants — a fully unprivileged actor from the app's perspective — can generate a validly-signed `(raw_body, hmac)` pair by simply triggering a webhook-eligible event (e.g., updating a product) on their own store, capture that legitimate webhook, and then re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to any other shop's domain. `HmacValidator.validate` still succeeds because it only checks `@raw_body` against the HMAC, and `Registry.process` forwards `request.shop` (now the victim's domain) straight into `WebhookMetadata` without any secondary tie-back to the signed bytes.

### Impact Explanation
This crosses a tenant boundary: an app whose webhook handler uses `data.shop` to key persistence, trigger per-shop side effects, or make security decisions (exactly as shown in the gem's own documented example) will attribute an attacker-controlled body to an arbitrary victim shop while still believing it is "verified... did indeed come from Shopify." This qualifies as **Critical — cross-tenant access**, since a party with a valid installation of the app can forge state changes and data attributed to any other shop the app serves, and the gem's own documentation explicitly promises that `process` verifies the request came from Shopify without noting the shop identity remains unauthenticated.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker must (a) be a legitimate/free installer of the same app (trivial on Shopify, since dev stores are free) so as to receive genuinely HMAC-signed webhooks with the shared `api_secret_key`, and (b) know or guess a target shop's domain (`*.myshopify.com` names are often discoverable/public). No access token, `client_secret`, or privileged account is required — only the ability to install a public app on one's own store, which is the definition of an "unprivileged internet user" in this ecosystem.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`) header values into the signed content the HMAC covers — e.g., verify the shop against a list of shops known to have valid, active sessions/installations for this app (as Shopify's own developer documentation recommends), or require callers of `Registry.process` to supply the expected shop and compare it before dispatching to the handler. At minimum, update `lib/shopify_api/webhooks/request.rb`'s `to_signable_string` documentation/behavior and `docs/usage/webhooks.md` to make explicit that only body integrity — not sender/shop identity — is verified by `HmacValidator`, so host apps do not conflate "HMAC passed" with "this data belongs to `data.shop`."

### Proof of Concept
```ruby
# Attacker legitimately installs the target app on their own store "attacker.myshopify.com"
# and triggers a real webhook (e.g., orders/create), capturing the raw body Shopify sent
# and its accompanying X-Shopify-Hmac-Sha256 header - both are validly signed with the
# app's single, shared api_secret_key.

raw_body = '{"id":1,"note":"malicious payload"}'   # genuine Shopify webhook body for attacker's own shop
hmac     = "…"                                      # genuine X-Shopify-Hmac-Sha256 for that body

headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,               # untouched, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # swapped to the victim
  "x-shopify-webhook-id"   => "attacker-controlled-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Passes verification because only raw_body is HMAC-checked:
ShopifyAPI::Webhooks::Registry.process(request)
# => WebhookHandler#handle receives data.shop == "victim-shop.myshopify.com"
#    with attacker-controlled body, even though victim-shop never sent this webhook.
```
