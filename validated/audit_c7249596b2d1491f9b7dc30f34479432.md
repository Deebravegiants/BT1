Based on my investigation, there is a valid analog matching the bug-class pattern described in the rules — a field acted on by the application but not covered by the HMAC signature.

### Title
Webhook `shop` field is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant) value is read directly from an unauthenticated HTTP header and handed to the webhook handler as-is.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Webhooks::Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed data: [2](#0-1) 

`Registry.process` validates the HMAC over the request, then immediately forwards `request.shop` (the unverified header value) to the handler alongside the verified body: [3](#0-2) 

Because the HMAC is computed with `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, signable_string)` where `signable_string == raw_body` only, and `api_secret_key` is a single app-wide secret shared across every shop that installs the app, the following equality is expected but not enforced:

`shop authenticated (bound into the HMAC) == shop acted upon (request.shop passed to handler)`

In reality the check only proves `HMAC(raw_body, api_secret_key)` is valid — it proves nothing about which shop the body belongs to.

### Impact Explanation
An unprivileged internet user who has installed the app on their own shop (Shop B) is a legitimate recipient of correctly-HMAC-signed webhooks from Shopify for Shop B. Because the shop-domain header is excluded from the signed payload, that same person can replay a captured (or freshly triggered) webhook body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header to claim it originates from a different shop (Shop A). `Utils::HmacValidator.validate` still succeeds because it only checks the raw body signature, and `Registry.process` dispatches the handler with `shop: request.shop` set to the attacker-chosen tenant. This is a cross-tenant boundary break: the app processes attacker-controlled webhook data/topic combinations under the identity of a shop the attacker does not control, which can corrupt tenant-scoped data, trigger privileged app-side operations (e.g., mandatory compliance topics like `customers/redact`, `shop/redact`), or desynchronize per-shop state — all without the target shop's involvement.

### Likelihood Explanation
Exploitation only requires installing the app on any shop (a normal, low-privilege action) and capturing/replaying a single legitimate webhook while modifying one header, since the vulnerable primitive (`request.shop`) is a public class in the gem's own webhook-processing pipeline used exactly as documented. No access to `api_secret_key`, tokens, or the target shop's credentials is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content, or otherwise cryptographically associate the header-derived shop with the raw body before dispatching to handlers — e.g., include the `shopify-shop-domain` header in `to_signable_string`, or require host applications to independently verify the `shop` value against a session/shop record before trusting `WebhookMetadata#shop`, and document this requirement prominently since the current API implies the shop passed to the handler is already trustworthy.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, receiving a legitimately Shopify-signed webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(B, api_secret_key)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same body `B` and same HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the request; `Utils::HmacValidator.validate(request)` recomputes `HMAC(B, api_secret_key)` — matches, since the domain header is not part of the signed string. [4](#0-3) 
4. The handler executes with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, believing the data originated from the victim tenant.
