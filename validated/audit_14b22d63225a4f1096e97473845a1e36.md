### Title
Unsynchronized `clear()` vs `#loadDataIntoAtom` race allows stale pre-clear wallet address cache to survive wallet/seed switch - ([File: features/address-provider/module/address-cache/index.js])

### Summary
`AddressCache.clear()` clears `#storage` and resets `#addressCacheAtom`, but it is not covered by `restrictConcurrency` and does not reset `#atomInitialized`. If `#enabledWalletAccountsAtom.observe` fires concurrently (as happens on a wallet/seed switch) and triggers `#loadDataIntoAtom`, that function reads `#addressCacheAtom.get()` as `oldState` and merges it *on top of* the freshly (storage-)loaded caches, because `#atomInitialized` is already `true`. If this read happens before `clear()`'s `atom.set(Object.create(null))` resolves, the old wallet's cached addresses are re-merged into the atom and persist into the new wallet-account context.

### Finding Description
`clear()` is implemented as:
```js
clear = async () => {
  this.#storage.clear()
  await this.#addressCacheAtom.set(Object.create(null))
}
``` [1](#0-0) 

It is not wrapped by `restrictConcurrency`, unlike `#update`, and does not reset the `#atomInitialized` flag. Meanwhile, `#loadDataIntoAtom` (invoked from the `#enabledWalletAccountsAtom.observe` callback set up once in `#load`) does:
```js
if (this.#atomInitialized) {
  const oldState = await this.#addressCacheAtom.get()
  await this.#addressCacheAtom.set(merge(Object.create(null), { caches, mismatches }, oldState))
} else {
  await this.#addressCacheAtom.set({ caches, mismatches })
  this.#atomInitialized = true
}
``` [2](#0-1) 

Because `oldState` is the *last* argument to `lodash.merge`, its (deep-merged) properties win over the freshly computed `{ caches, mismatches }` for any overlapping keys (e.g., the same default `walletAccountName` such as `exodus_0` reused for a different seed after a wallet switch). If the read of `this.#addressCacheAtom.get()` inside `#loadDataIntoAtom` races ahead of the `await this.#addressCacheAtom.set(Object.create(null))` in `clear()`, `oldState` contains the pre-clear (previous wallet/seed) cache data, which then survives into the atom state served to the newly-switched wallet context via `get()`.

The trigger path for this race is real: `addressProviderPlugin.onClear` calls `addressCache.clear()` **without awaiting it**:
```js
onClear: async () => {
  addressCache.clear()
  await seedAddressProvider?.clear?.()
},
``` [3](#0-2) 

This fire-and-forget call widens the race window between `clear()`'s two internal steps and any concurrent `enabledWalletAccountsAtom` change notification that fires `#loadDataIntoAtom` (e.g., during a wallet-account/seed switch flow), since nothing serializes `clear()` against the `#load`/`#loadDataIntoAtom` path (`restrictConcurrency` only wraps `#update`, not `clear()` or `#loadDataIntoAtom`).

### Impact Explanation
If exploitable, this would let cached receive addresses belonging to a previous wallet/seed context leak into and be served for a newly switched wallet/seed context via `AddressCache.get()`, which is consumed by `features/address-provider/module/address-provider.js` for `useCache: true` receive-address lookups. This is a cross-wallet/cross-seed data isolation violation ("locked means locked" / secret-adjacent boundary), potentially causing a user to be shown or use a stale/incorrect receive address tied to a different seed context after switching wallets.

### Likelihood Explanation
This requires a specific timing race: `clear()` (triggered via `onClear`, itself unawaited) racing against a concurrent `enabledWalletAccountsAtom` observer firing (triggered by a wallet-account/seed switch) such that `#loadDataIntoAtom`'s `this.#addressCacheAtom.get()` resolves before `clear()`'s `atom.set(Object.create(null))` resolves. Both are async, in-process JS promise races (not attacker-controlled network/RPC timing), so it depends on the atom implementation's microtask/scheduling behavior and how quickly wallet-switch flows fire the accounts-changed observer relative to `clear()`. I was unable to fully verify from the available index whether `walletAccountName` values (e.g., `exodus_0`) are actually reused verbatim across different seeds/wallets in this codebase (which is required for the merge collision to expose *specific* stale data rather than just leftover keys), nor could I confirm the exact call ordering of `onClear` relative to the wallet-accounts atom update during a real wallet-switch flow — this needs further verification in a live/integration environment.

### Recommendation
- Wrap `clear()` with the same `restrictConcurrency` mechanism (or a shared mutex) also used to guard `#loadDataIntoAtom`/`#load`, so the two can't interleave.
- Reset `#atomInitialized = false` inside `clear()` before/while clearing storage and atom, or otherwise make `#loadDataIntoAtom` re-read storage strictly after `clear()` completes and skip merging any state older than the clear operation (e.g., via a monotonically increasing "clear epoch"/generation counter checked before applying `oldState`).
- Await `addressCache.clear()` in `addressProviderPlugin.onClear` instead of firing it without `await`.

### Proof of Concept
Integration test plan (in `features/address-provider/module/address-cache/__tests__/module.test.js` style):
1. Load `addressCache` and `set()` an address for `walletAccountName: 'exodus_0'` so it exists in both storage and the atom (`#atomInitialized` becomes `true` via initial `#loadDataIntoAtom`).
2. Stub/delay `#addressCacheAtom.set` (or the underlying atom's `set`) with a deferred promise so `clear()`'s `atom.set(Object.create(null))` doesn't resolve immediately.
3. While `clear()` is in-flight (storage already cleared, atom `set` still pending), trigger the `enabledWalletAccountsAtom.observe` callback for a "new wallet" with the same account name `exodus_0`, invoking `#loadDataIntoAtom(['exodus_0'])`, and let its `this.#addressCacheAtom.get()` resolve with the pre-clear atom value.
4. Resolve both deferred promises and await completion of both operations.
5. Assert `addressCache.get({ walletAccountName: 'exodus_0', baseAssetName: 'bitcoin', derivationPath: ... })` still returns the old (pre-clear) address — demonstrating the invariant violation — versus the expected `undefined`.
