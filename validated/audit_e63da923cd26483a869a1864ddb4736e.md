### Title
Reentrancy in `IntentGatewayV2.withdraw` via external token transfer before escrow accounting update - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` contract violates the checks-effects-interactions pattern: it performs the external token transfer to `beneficiary` before decrementing the corresponding `_orders[commitment][token]` escrow balance, and does the same for the transaction-fee payout before deleting the fee entry. [1](#0-0) 

### Finding Description
In `withdraw(WithdrawalRequest memory body, bool isRefund)`, for each token in the withdrawal list the function checks `_orders[body.commitment][token] == 0`, then immediately makes a low-level external call transferring the token (or native currency) to `beneficiary`, and only *after* the call returns does it execute `_orders[body.commitment][token] -= amount;`: [2](#0-1) 

The same ordering flaw applies to the transaction-fee payout, where the fee transfer happens before `delete _orders[body.commitment][TRANSACTION_FEES]`: [3](#0-2) 

This is unlike the sibling implementation in the main EVM codebase (`IntentsBase._withdraw`), which correctly decrements `_orders[body.commitment][token]` *before* performing the transfer: [4](#0-3) 

`withdraw()` is reachable through `cancelOrder()`'s same-chain branch, which any order owner can call directly in a single transaction with no privileged role required: `cancelOrder` computes `commitment`, checks `_filled[commitment] == address(0)`, and for the `isSameChain` case calls `withdraw(body, true)` directly, passing `order.inputs` as the token list: [5](#0-4) 

Because `order.inputs` are arbitrary tokens chosen by the order creator at `placeOrder` time, an attacker can escrow a token they control (e.g., an ERC-777-style or otherwise callback-enabled token) alongside another legitimate token in the same order, then call `cancelOrder()`. During the callback-token transfer inside `withdraw()`'s loop, `_orders[commitment][token]` for the *other* (not-yet-processed) token in the list is still un-decremented, and `_filled[commitment]` has already been set at the top of `withdraw()` (line 693) but only for that call frame — however, `cancelOrder()` itself does not set `_filled` for the same-chain path before invoking `withdraw`, so if the reentrant callback calls back into `cancelOrder()` for the same order/commitment before `_filled[commitment]` is set (it's set inside `withdraw`, at line 693, which does execute before the loop — this partially mitigates repeat top-level calls to `cancelOrder`/`withdraw` for the *same* commitment, but does **not** protect against a nested call that targets the still-nonzero escrow of the *other, not-yet-decremented* token within the same in-progress loop iteration set, since the check-then-transfer-then-decrement pattern is per-token and not atomic across the whole withdrawal list).

### Impact Explanation
If exploitable, this allows draining more of the escrowed collateral than was ever recorded as released, directly leading to fund loss for the protocol/other users, since the accounting decrement is executed after the external call rather than before, breaking the CEI invariant relied upon elsewhere in the fee/escrow accounting.

### Likelihood Explanation
Medium: the entry point (`cancelOrder`, same-chain path) is unauthenticated aside from requiring `order.user == msg.sender`, and reachable by any user in a single transaction with an order they placed themselves, using a token of their choosing as one of the escrowed inputs. The main mitigating factor — and the reason I cannot assert High confidence without further code (e.g. full modifier list, `_filled` set order relative to the loop, and whether `token.call` with a callback-capable token is realistically escrow-able through `placeOrder`'s `safeTransferFrom` checks) — is that `_filled[commitment]` is set at the very start of `withdraw()` (line 693) before the loop runs, which blocks a second top-level call into `withdraw`/`cancelOrder` for the *same* commitment during reentrancy. The residual risk is specifically to multi-token orders where one token in the list has transfer callbacks and another item in the same list has not yet been decremented at the time of the callback.

### Recommendation
Apply the checks-effects-interactions pattern consistently: decrement `_orders[body.commitment][token] -= amount;` (and `delete _orders[body.commitment][TRANSACTION_FEES];`) *before* making the external transfer call, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw` function [4](#0-3) .

### Proof of Concept
1. Attacker calls `placeOrder()` with two inputs: `tokenA` (a callback-capable ERC-20 the attacker controls/deploys) and `tokenB` (e.g., USDC), escrowing both under one `commitment`. [6](#0-5) 
2. Before the order is filled, attacker calls `cancelOrder()` on the same chain; this routes to `withdraw(body, true)` with `body.tokens = order.inputs = [tokenA, tokenB]`. [7](#0-6) 
3. Inside `withdraw`, the loop processes `tokenA` first: checks `_orders[commitment][tokenA] != 0`, calls `tokenA.call(transfer(...))`, which triggers the attacker's callback logic — at this point `_orders[commitment][tokenB]` has not yet been touched/decremented. [8](#0-7) 
4. The attacker's callback (within `tokenA`'s transfer hook) can further manipulate order state (e.g., via other order-scoped functions that read `_orders[commitment][tokenB]` before it is decremented back in the outer frame), enabling double accounting of `tokenB`'s escrow relative to the single decrement performed by the outer call.

Verification of the exact secondary re-entry path (i.e., a concrete second function that reads `_orders[commitment][tokenB]` mid-loop) requires reviewing the remainder of `evm/tron/contracts/apps/IntentGatewayV2.sol` beyond what was retrieved (lines 601–630 for `fillOrder`/`select`, which were not fully returned within the available iterations) to conclusively confirm a second entry point exists that isn't blocked by `_filled[commitment]`. This should be checked before treating the PoC as fully proven end-to-end.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
