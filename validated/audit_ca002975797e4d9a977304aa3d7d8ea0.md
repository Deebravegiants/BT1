### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` are trusted from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw request body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` validates the HMAC and then unconditionally forwards these unverified header values to the app's webhook handler as the "verified" tenant/topic context, breaking the binding `shop authenticated == shop acted upon`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with zero cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` performs that HMAC check and then immediately trusts the unauthenticated `shop`, `topic`, and `webhook_id` fields to build the metadata handed to the app's handler: [4](#0-3) 

Because the signature covers only the body bytes, an unprivileged internet user can obtain one legitimately-signed `(raw_body, hmac)` pair for a topic of their choosing — trivially, by installing the app on their own free/dev store and triggering any webhook event (they are a legitimate merchant of their own shop, and Shopify will sign that webhook body with the app's real `api_secret_key`) — and then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop and/or the `x-shopify-topic` header for a different registered topic. The HMAC check still passes because it never inspects those headers, so `Registry.process` will dispatch to the handler believing the event legitimately originated from the victim shop/topic. This directly breaks the equality `shop verified by HMAC == shop the handler acts on`, since the shop that is actually protected by the signature is nothing (no shop is signed at all) — the effective binding is `bytes verified (body only) != bytes/headers used to determine tenant (shop, topic, webhook_id)`.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to key tenant data (e.g., process an order, mark a shop uninstalled/redacted on `shop/redact` or `app/uninstalled`, update per-shop settings, delete records) can be made to apply attacker-chosen webhook payloads against an arbitrary victim shop's tenant record, i.e., cross-tenant access/action — satisfying the "Critical - cross-tenant access" impact bar, since the identity of the acted-upon tenant is fully decoupled from the cryptographic proof.

### Likelihood Explanation
No secrets, tokens, or privileged access are required. The only prerequisite is the ability to receive one legitimately-signed webhook, which any user can obtain simply by being a merchant who installs the target app on their own (free) store and triggering any subscribed event — a normal, unprivileged interaction with the app. From there, forging headers on a direct HTTP POST to the app's public webhook endpoint is trivial.

### Recommendation
Include the identity-relevant fields (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the header values to the signature (e.g., have `HmacValidator`/`Registry.process` reject a request unless the `shop` header matches a shop that is independently known/authorized for this app, rather than trusting it purely from an unsigned header).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the resulting request: raw body `B`, and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's `api_secret_key`), and `x-shopify-topic: orders/create`.
2. Attacker sends a new POST to the app's webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) and succeeds, since headers are irrelevant to the check: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process/act on data as if it legitimately originated from `victim-shop.myshopify.com`, despite that shop never having sent this request.
