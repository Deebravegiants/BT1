The external report describes a Solidity-specific bug: `ERC20ConvictionScore._updateConvictionScore` returns a positive `governanceDelta` from `getPriorConvictionScore` even when a user should be removed from governance, and that positive value is incorrectly added to `TOTAL_GOVERNANCE_SCORE` instead of being subtracted.

I checked the closest analogs in core-contracts for a similar "delta sign flipped when decreasing a running total" pattern:

- `voting/src/lib.rs` `vote()` correctly computes `self.total_voted_stake = self.total_voted_stake + account_stake - voted_stake`, properly subtracting a validator's old stake when it changes or is withdrawn [1](#0-0) .
- `staking-pool/src/internal.rs` `internal_stake` and `inner_unstake` correctly use `+=`/`-=` on `total_staked_balance` and `total_stake_shares` for both directions of the operation, with no case where a decrease is mistakenly applied as an increase [2](#0-1) [3](#0-2) .

There is no equivalent "total score/stake accumulator" in the NEAR core-contracts scope (lockup, staking-pool, staking-pool-factory, whitelist, multisig) that mirrors the ERC20ConvictionScore governance-removal accounting path, and the existing running-total updates in `voting/src/lib.rs` and `staking-pool/src/internal.rs` handle increases and decreases with correct signs. No reachable root cause analogous to the reported bug exists in the in-scope production files.
