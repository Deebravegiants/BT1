### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC only against the body and then blindly trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, breaking the binding "shop the HMAC vouches for == shop attributed to the webhook".

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` header without any cryptographic binding: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body` — none of the headers (shop, topic, webhook_id, api_version) are included in the signable content used for HMAC verification.

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then constructs `WebhookMetadata` directly from `request.shop` (the unauthenticated header) without any additional check that this shop matches the body that was actually HMAC-signed: [4](#0-3) 

Because the HMAC only proves "this exact body was signed by Shopify with the app's shared secret," it says nothing about which shop the body came from. Any party who can obtain one legitimate `(body, hmac)` pair — for example a malicious merchant who installs the app on their own store and triggers a webhook by editing data on their own store (Shopify will sign that body with the app's real secret) — can replay that exact HTTP request to the app's public webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop domain. The HMAC check still passes because it only re-verifies the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: <victim>` together with attacker-crafted body content.

The gem's own documentation instructs apps to key their business logic off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

so any consuming app that trusts `data.shop` as the tenant identifier (to route data updates, revoke access on `app/uninstalled`, fulfill GDPR `customers/redact`/`shop/redact` mandatory topics, etc.) will apply attacker-controlled webhook content under a spoofed tenant identity — a cross-tenant integrity/authorization violation.

### Impact Explanation
This breaks the equality "shop attested by the signed webhook payload == shop delivered to the app's business logic." An attacker (any unprivileged internet user who can install the app on a shop they control, which is the normal, unprivileged install flow for any public/embedded app) can forge webhook deliveries that appear to originate from a completely different, victim shop while the HMAC still validates. Depending on how the host app uses `data.shop` (which the gem explicitly recommends trusting), this enables cross-tenant data corruption, forged mandatory-compliance webhooks (`customers/redact`, `shop/redact`), or forged `app/uninstalled` events that could cause the app to revoke/delete a victim shop's stored session or data — i.e., cross-tenant access/impact without needing the victim's credentials.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker needs (a) their own working shop/installation of the target app (a low bar for any public app — free Shopify dev/trial stores are readily available), and (b) the ability to make a direct HTTP POST to the app's public webhook endpoint with custom headers (webhook endpoints are, by design, public unauthenticated URLs). No access to the app's `api_secret_key` or any victim credentials is required — the attacker rides on a legitimately Shopify-signed body from their own store and only forges the unauthenticated header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable string, or otherwise cryptographically bind them to the request (e.g., verify `shop` against session/topic-registration expectations before dispatching to the handler). At minimum, document prominently that `data.shop` is not authenticated by the HMAC and must not be trusted as a tenant identifier without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and provides valid access token/session.
2. Attacker updates a resource on their own store so Shopify sends a real webhook, e.g. `customers/redact`, whose body they can influence, and receives from Shopify a POST to the app's registered callback URL with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body, computed with the app secret>`
   - raw body: `{"shop_id": ..., "shop_domain": "attacker.myshopify.com", ...}` (or another topic body they can shape)
3. Attacker captures this exact `(raw_body, hmac)` pair and replays it directly to the app's public webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only — it matches, so `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, even though Shopify never sent this payload for `victim.myshopify.com`.
