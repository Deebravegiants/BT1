### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a shop host derived from the JWT `dest` claim without the trusted-domain validation applied elsewhere in the same module - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` value used to build the outbound request host directly from the `dest` claim of the caller-supplied session token, via `ShopifyAPI::Auth::JwtPayload#shop`, and never runs it through `ShopifyAPI::Utils::ShopValidator`. The sibling method in the very same module, `migrate_to_expiring_token`, does call `ShopValidator.sanitize!` on its `shop` argument before using it. This mirrors the disclosed bug class: one code path enforces an identity/host binding, a parallel path handling the same trust-sensitive operation (a request that carries the app's `client_secret`) does not.

### Finding Description
`JwtPayload#shop` simply strips the scheme from the `dest` claim with no allowlist check: [1](#0-0) 

`exchange_token` uses this unsanitized value as the destination host for the token-exchange HTTP call, which includes `client_id`/`client_secret` in the POST body: [2](#0-1) 

`HttpClient` builds the request URL directly from `session.shop`: [3](#0-2) 

By contrast, `migrate_to_expiring_token` (same file/module) explicitly validates the shop before use, and the test suite documents this expectation: [4](#0-3) 

The `ShopValidator` module that exists precisely to bind "shop" values to a fixed set of trusted Shopify domains is never invoked in `exchange_token`: [5](#0-4) 

So the equality that should hold — "host that receives the `client_secret`" == "a value validated against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`" — is enforced in `migrate_to_expiring_token` but broken in `exchange_token`.

### Impact Explanation
If the `dest` claim of the session token can ever resolve to a host outside the intended myshopify domain space (e.g. a JWT the application accepts from a non-`/admin` issuer, a preview/spin domain, or any future/边缘 issuer not restricted at decode time), `exchange_token` will make a server-side HTTP POST carrying the app's `client_id`/`client_secret` to that attacker-influenced host — an SSRF that exfiltrates the app's `client_secret` (High/Critical per the report's own impact categories).

### Likelihood Explanation
Low-to-Medium. `JwtPayload` does verify the JWT's HMAC signature against `Context.api_secret_key`/`old_api_secret_key` and checks `aud == Context.api_key`, so under normal operation `dest` is set by Shopify's own token minting and not directly attacker-controlled. The real risk is the code-path inconsistency itself: nothing in `exchange_token` prevents a `dest` value that fails the same trusted-domain policy the codebase already enforces one method away, and any relaxation of decode-time checks (algorithm confusion, key rotation edge cases, non-`/admin` issuers used by extensions) removes the only remaining protection.

### Recommendation
Apply `ShopifyAPI::Utils::ShopValidator.sanitize!` (or equivalent) to `jwt_payload.shop` in `exchange_token` before it is used to construct `shop_session`/the outbound request host, exactly as already done in `migrate_to_expiring_token`, so both methods enforce the same shop/host binding before sending the `client_secret`.

### Proof of Concept
1. Root-cause comparison (no external network access needed to prove the asymmetry):
   - `lib/shopify_api/auth/token_exchange.rb:40-51` — `dest_shop = jwt_payload.shop` is used unchecked to build `shop_session` and subsequently the request host.
   - `lib/shopify_api/auth/token_exchange.rb` (`migrate_to_expiring_token`) validates via `ShopValidator.sanitize!`, confirmed by `test/auth/token_exchange_test.rb:258-265` (`test_migrate_to_expiring_token_rejects_non_shopify_domain`).
2. No analogous test exists asserting `exchange_token` rejects a non-Shopify `dest` claim, confirming the gap is unguarded in that path.
