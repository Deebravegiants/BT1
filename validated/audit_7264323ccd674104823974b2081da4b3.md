Found it: `Keychain#exportKey({ seedId, keyId, ... })` requires and uses `seedId` correctly, but `MemoizedKeychain` — the class that wraps it and is used as the actual `keychain` module — caches exported public keys keyed **only by `keyId`**, dropping `seedId` entirely.

### Title
Public key cache keyed only by KeyIdentifier instead of by (seedId, KeyIdentifier) pair, causing cross-seed public key confusion - (File: features/keychain/module/memoized-keychain.js)

### Summary
`MemoizedKeychain#exportKey` caches the result of `Keychain#exportKey({ seedId, keyId })` using a cache key derived from `stableStringify(keyId)` only, never incorporating `seedId`. In a multi-seed wallet (the keychain explicitly documents and supports `addSeed`/multiple seeds, requiring `seedId` on every operation), two different seeds can legitimately be asked to export the exact same `KeyIdentifier` (same `keyType`/`derivationAlgorithm`/`derivationPath`/`assetName`). Because the cache is keyed by `keyId` alone, the second seed's request will silently return the first seed's cached public key/xpub instead of deriving its own — the exact "tracked per (weaker) token instead of per (correct) pair" bug pattern from the reference report, here applied to `(keyId)` instead of `(seedId, keyId)`.

### Finding Description
`Keychain#exportKey` in [1](#0-0)  takes both `seedId` and `keyId` and asserts `seedId` is a string, deriving the HD key from `this.#masters[seedId]` — i.e., the seed is a required, security-relevant part of the derivation context, exactly as multiple independent seeds can be added via `addSeed` (see [2](#0-1) ) and the module explicitly supports many seeds concurrently (`#masters` is a map keyed by `seedId`).

However, `MemoizedKeychain`, which is the actual `keychain` module wired into the IOC container (`id: 'keychain'`), wraps `exportKey` like this: [3](#0-2) 

```
const keyIdToCacheKey = stableStringify
...
#getCachedKey = async (keyId) => {
  const cacheKey = keyIdToCacheKey(keyId)
  return this.#publicKeys[cacheKey]
}

#setCachedKey = async (keyId, value) => {
  this.#publicKeys[keyIdToCacheKey(keyId)] = value
  ...
}

exportKey = async (keyId, opts) => {
  if (!opts?.exportPrivate) {
    const cached = await this.#getCachedKey(keyId)
    if (cached) return cached
  }
  const result = await super.exportKey(keyId, opts)
  this.#setCachedKey(keyId, getPublicKeyData(result))
  return result
}
```

Note that `MemoizedKeychain#exportKey(keyId, opts)` is invoked with a single positional `keyId` argument, not the `{ seedId, keyId, ... }` object that `Keychain#exportKey` expects and requires — meaning any caller going through the memoized wrapper effectively can't correctly pass `seedId` through this override signature at all, and even if it were included inside the `keyId`-like object, `keyIdToCacheKey` (`stableStringify`) would only be as good as whatever object is actually passed. Regardless of the exact call signature mismatch, the caching layer's key derivation contains no explicit `seedId` component — the cache is tracked "per KeyIdentifier" instead of "per (seedId, KeyIdentifier) pair," mirroring the M-01 report's "oracle tracked per token instead of per pair": whichever seed populates the cache first for a given `keyId` will have its public key silently reused for every other seed requesting the same `keyId`.

This is directly analogous to the `tokenToOracle[_token]` skip-if-already-set bug: the cache's "if cached, return it" branch (`if (cached) return cached`) silently returns stale/foreign data instead of deriving fresh, correct data for the new identity (here, a different seed instead of a different token pair).

### Impact Explanation
If exploited or triggered (e.g., by an app enabling multiple seeds — a supported first-class keychain feature — and having two seeds whose derivation paths/algorithms overlap for some asset), an unprivileged/user-level operation (deriving a receive address, exporting an xpub, verifying "is own address") could be served the wrong seed's public key/xpub. This can lead to: funds/addresses being generated or trusted under the wrong identity, incorrect address-ownership checks (`isOwnAddress`), and cross-seed public key/xpub disclosure via the wallet UI — a concrete secret/data disclosure and account-isolation violation between two seeds managed by the same keychain instance, which sits squarely in the "account isolation" trust boundary called out in scope.

### Likelihood Explanation
Likelihood depends on whether two seeds actually produce colliding `KeyIdentifier`s (same `keyType`/`derivationAlgorithm`/`derivationPath`/`assetName`) while using the memoized keychain concurrently. Because `KeyIdentifier` intentionally does **not** include `seedId` (that's the caller's job to track separately, per the module's own README), and multi-seed support is a real, exercised feature (e.g., extra-seed analytics IDs, hardware+software seed combos), this is a realistic occurrence rather than a purely theoretical one — but I could not fully verify from static reading whether every call site of `MemoizedKeychain#exportKey` reliably differentiates cache entries by seed at a higher layer, since the wrapper's own signature (`exportKey(keyId, opts)`) appears inconsistent with the base class's `exportKey({ seedId, keyId, ... })` signature. This inconsistency itself is suspicious and warrants direct confirmation via a live Devin session with test execution, which I could not perform here.

### Recommendation
Change `MemoizedKeychain`'s cache key derivation to include `seedId` alongside `keyId` (e.g., `stableStringify({ seedId, keyId })`), and audit/fix the `exportKey(keyId, opts)` override signature so it actually receives and forwards `{ seedId, keyId, ...opts }` consistently with `Keychain#exportKey`. Add regression tests that add two seeds, request `exportKey` for the same `KeyIdentifier` under each seed, and assert the returned public keys/xpubs differ and are not cross-contaminated.

### Proof of Concept
Conceptual reproduction (would need to be executed against the real module to confirm, which requires running tests I don't have execution access to in this session):
1. Create a `MemoizedKeychain`, call `keychain.addSeed(seedA)` and `keychain.addSeed(seedB)` to obtain `seedIdA` and `seedIdB`.
2. Call `keychain.exportKey({ seedId: seedIdA, keyId })` for some `keyId` — this populates the cache under `stableStringify(keyId)`.
3. Call `keychain.exportKey({ seedId: seedIdB, keyId })` for the identical `keyId` — per the code in [4](#0-3) , since `cacheKey` only derives from `keyId`, the cached entry from step 2 (seed A's public key) is returned instead of deriving seed B's actual public key.
4. Assert `result.publicKey` differs between step 2 and step 3 in the unpatched code — it will not, demonstrating cross-seed key confusion.

import BJSON from 'buffer-json'
import stableStringify from 'json-stable-stringify'

import { Keychain } from './keychain.js'

const keyIdToCacheKey = stableStringify

const CACHE_KEY = 'data'

const getPublicKeyData = ({ xpub, publicKey }) => ({ xpub, publicKey })

class MemoizedKeychain extends Keychain {
  #storage
  #publicKeys = Object.create(null)
  #cloneOpts

  constructor({ storage, legacyPrivToPub }) {
    super({ legacyPrivToPub })

    this.#storage = storage
    this.#storage.get(CACHE_KEY).then((data) => {
      this.#publicKeys = data ? BJSON.parse(data) : Object.create(null)
    })

    this.#cloneOpts = { storage }
  }

  #getCachedKey = async (keyId) => {
    const cacheKey = keyIdToCacheKey(keyId)
    return this.#publicKeys[cacheKey]
  }

  #setCachedKey = async (keyId, value) => {
    this.#publicKeys[keyIdToCacheKey(keyId)] = value
    await this.#storage.set(CACHE_KEY, BJSON.stringify(this.#publicKeys))
  }

  exportKey = async (keyId, opts) => {
    if (!opts?.exportPrivate) {
      // take advantage of public key cache
      const cached = await this.#getCachedKey(keyId)
      if (cached) return cached
    }

    const result = await super.exportKey(keyId, opts)
    // don't wait for this to finish
    this.#setCachedKey(keyId, getPublicKeyData(result))
    return result
  }
