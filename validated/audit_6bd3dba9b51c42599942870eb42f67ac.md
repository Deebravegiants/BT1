### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request **body**, then unconditionally trusts the `shop-domain` header value to identify which merchant/tenant the event belongs to. Because the header is never part of the signed material, the "shop that was authenticated" and the "shop that is delivered to the handler" are two different, independently-controlled values — breaking the identity binding `hmac-authenticated-shop == request.shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read directly from an HTTP header and is not fed into the signable string at all: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) to identify the tenant for the handler: [3](#0-2) 

`HmacValidator.validate` computes the digest purely from `verifiable_query.to_signable_string` and the app's `api_secret_key`: [4](#0-3) 

Critically, `api_secret_key` is a single, app-wide secret shared across **every** shop that installs the app — it is not per-tenant. Any merchant who has installed the app receives genuine webhook deliveries with valid `body + hmac` pairs signed with that same shared secret. Such a merchant (an "unprivileged" party with respect to other tenants of the same app) can capture one of these legitimately-signed `(body, hmac)` pairs and re-POST it directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` will still return `true`, since it only checks the body against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop: [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `authenticated_tenant == acted_upon_tenant`, but here `authenticated_tenant` (implicit in a valid HMAC over the shared secret) is disjoint from `acted_upon_tenant` (`request.shop`, an arbitrary attacker-supplied header).

### Impact Explanation
This crosses the tenant boundary this gem is responsible for enforcing: a webhook payload that Shopify only ever intended for the sender's own store can be replayed and falsely attributed to a different merchant's shop, without needing that merchant's access token, `client_secret`, or any other privileged credential. Any host application that uses `Registry.process`/`WebhookMetadata#shop` to key persistence, authorization, or business logic (e.g., "look up this shop's record and update it based on the webhook body") is exposed to cross-tenant data corruption or information disclosure — one merchant can inject data into another merchant's account context. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as an ordinary merchant (or otherwise receiving one legitimate webhook delivery for any topic), and (2) sending a raw HTTP POST directly to the app's public webhook endpoint with the captured body/HMAC pair and a forged shop header — both are within reach of an unprivileged, already-onboarded tenant and require no secrets belonging to the app or to other merchants. The webhook endpoint is inherently internet-facing, so no additional network position is needed.

### Recommendation
Bind the shop identity to the authenticated payload. Options:
- Have the app-side handler cross-check `request.shop` against a shop it knows to be legitimately associated with the delivered `webhook_id`/topic via a separate authenticated lookup, or
- Extend `VerifiableQuery`/`to_signable_string` for webhooks to include the `shop-domain` (and `topic`) header values in the signed material check performed by the library (this would require matching Shopify's actual signing behavior, so at minimum the docs/API should make explicit that `request.shop` is unauthenticated and must not be trusted as a tenant key without additional verification).
- At minimum, document prominently in `docs/usage/webhooks.md` and in `WebhookMetadata` that `shop` is derived from an unauthenticated header and must be independently validated/looked up by the host app before being used for any tenant-scoped action.

### Proof of Concept
1. App merchant A installs the app; app delivers/receives a legitimate webhook to A's endpoint with body `B` and header `Shopify-Hmac-Sha256: H` (valid because computed with the app's shared `api_secret_key`).
2. Attacker (merchant A, or anyone who intercepted this one delivery) sends a raw POST to the app's webhook endpoint:
   - Body: `B` (unchanged)
   - Headers: `shopify-hmac-sha256: H` (unchanged), `shopify-topic: <same topic>`, `shopify-shop-domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — matches `H` — validation passes: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act as if this event came from `victim-shop`.
