### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Registry.process` only covers the raw request body. The `shop` value is trusted and forwarded to the host application's webhook handler without being cryptographically bound to the same signature that authenticates the payload.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop` is read from an HTTP header that is completely outside the signed material: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without any additional check that `shop` corresponds to the shop that actually produced the signed body: [3](#0-2) [4](#0-3) 

This is the same bug class as the external report's core issue: a value used downstream by the system (`withdrawReserveReceived` / here, the `shop` tenant identity) is not linked to the value that was actually verified/authenticated (the drained assets / here, the HMAC-covered body). The equality that should hold is:

`shop bound by HMAC == shop acted on by the handler`

but the implementation instead allows:

`shop acted on by the handler != shop that produced the HMAC-signed body`

Since any merchant can install the app on their own shop and thus legitimately receive Shopify-issued webhooks with a valid HMAC over a chosen/observable body (e.g., an `orders/create` payload with attacker-controlled order content), that same merchant can replay the identical body to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value (e.g., a victim shop domain, or a fixed/predictable shop that the app treats specially). The HMAC still validates because it only checks the raw body, but `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen domain instead of the shop that Shopify actually associated with that payload.

### Impact Explanation
If a host application uses `data.shop` from `WebhookMetadata` to look up or scope tenant data (session/access token lookup, database records, billing state, etc.) — which is the documented and expected usage pattern shown in `docs/usage/webhooks.md` — an attacker who controls one shop's webhook traffic can forge webhook events attributed to a different shop. This breaks the tenant-identity binding that should be guaranteed by the HMAC check, enabling cross-tenant data confusion/access, matching the High-impact class of "scope or expiry check bypass"/"cross-tenant access" analog called out in the rules.

### Likelihood Explanation
Any user who can install the app on a shop they control can generate this attack with no special privileges: they simply need to capture one legitimately-signed webhook body from their own shop (trivial — Shopify sends these automatically) and POST it to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No access token, `client_secret`, or leaked credential is required. `WebhookController` example code in the docs simply forwards raw headers and body without extra shop verification, confirming this is the expected integration path.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) to the HMAC-covered material, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed string: [5](#0-4) 

Since Shopify's actual webhook HMAC is computed only over the raw body (this is fixed by Shopify's wire format and cannot be changed unilaterally by the gem), the gem should instead document/require that host applications cross-check `request.shop` against a shop already known/authorized for that installation (e.g., an existing stored session) before trusting it, and should surface this caveat prominently in `docs/usage/webhooks.md`, since developers otherwise reasonably assume the header is authenticated the same way the body is.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets it register the `orders/create` webhook.
2. Shopify sends a webhook POST to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and a JSON body the attacker fully controls (order content).
3. Attacker replays the exact same raw body to the same webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC only over the (unchanged) raw body and returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-controlled data as if it originated from the victim shop.
