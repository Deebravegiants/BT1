Based on my review, this specific vulnerability class does **not** have a valid analog in this Polkadot SDK codebase.

**Why the Gelato/ERC-2771 issue doesn't map here:**

The external report's root cause is that `GelatoRelayContext`'s `_msgSender()` returns the relayer's address instead of the original user's address, because the contract lacks the ERC-2771 trusted-forwarder logic that decodes and authenticates the original sender from relayer-supplied calldata.

Polkadot SDK's analogous "gasless/relayed transaction" feature is `pallet-meta-tx` (`substrate/frame/meta-tx/src/lib.rs`), which implements exactly this pattern but avoids the vulnerability by design:

- A meta transaction is built with a target `call` plus `Extension` (typically `pallet_verify_signature::VerifySignature`) that carries the signer's own cryptographic signature over the call and its extension data. [1](#0-0) 
- The relayer submits the `dispatch` extrinsic with `_origin: OriginFor<T>` deliberately unused/ignored — the origin actually used to execute the wrapped call is derived from `meta_tx.extension.dispatch_transaction(...)`, which runs the signature-verification extension and only succeeds if the embedded signature is valid, setting the origin to the *verified signer*, not the relayer.

/// Meta Transaction type.

#[derive(Encode, Decode, PartialEq, Eq, TypeInfo, Clone, Debug, DecodeWithMemTracking)]

	/// The target call to be executed on behalf of the signer.

	/// The extension version.
