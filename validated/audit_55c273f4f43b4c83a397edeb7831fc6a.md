### Title
Fraud-flagged Signups Still Upload Full Biometric Personal Custody Package to Backend Before Enforcement — ([File: src/plans/mod.rs])

### Summary
The Proteus report describes a parameter (`metadata`) that exists specifically to let a caller encode a protective constraint (slippage), but the contract logic never checks it before executing the action, so the action proceeds unconstrained. The orb-core master signup flow has the same class of defect: `signup_reason` (an enum carrying, among other things, `SignupReason::Fraud`) is computed by `detect_fraud()` and threaded all the way into the personal-custody-package (PCP) builder and uploader, but it is used only to *label/salt* metadata inside the package (`info.json`) — it is never checked to gate or abort the construction and upload of the user's full biometric bundle (iris codes, normalized iris images, face embeddings/thumbnail). The upload happens unconditionally, and only *after* the upload completes does the code branch on `signup_reason` to decide whether to report the signup as successful.

### Finding Description
In `Plan::run_signup_or_whatever` (the block spanning `src/plans/mod.rs:558-663`), the sequence is:

1. `detect_fraud()` is called and its boolean result feeds `signup_reason`: [1](#0-0) 

2. Regardless of whether `signup_reason` is `Fraud`, `Failure`, or `Normal`, the code unconditionally proceeds to build and upload the biometric personal custody package: [2](#0-1) 

3. `build_pcp` passes `signup_reason` down into `personal_custody_package::Plan`, but the plan only uses it as a *string label* embedded (and salted-hashed) into `info.json` — it never inspects it to short-circuit the build/upload: [3](#0-2) [4](#0-3) 

4. Only *after* `build_pcp` has already produced and `upload_pcp_tier_0`/tier1/tier2 have already sent the encrypted iris/face biometric tarballs to the backend does the code use `signup_reason` to decide local enrollment success/failure: [5](#0-4) 

The `detect_fraud` function itself is presently a stub in this build (`// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`, always returning `Ok(false)`): [6](#0-5) 

but the structural defect is independent of that stub: even when `detect_fraud` is restored to a real fraud/liveness engine and returns `true` (setting `signup_reason = SignupReason::Fraud`), the current control flow still builds and uploads the complete biometric PCP (iris codes, normalized iris images, face embeddings and thumbnail) to the backend before any fraud-based gate is applied. The "protective parameter" (`signup_reason`) is present and threaded through the whole call chain exactly like the AMM's unused `metadata` field, but it is consumed only for reporting/labeling, not for enforcement.

### Impact Explanation
This allows a signup that the Orb itself has determined to be fraudulent (spoofed/replayed liveness, duplicate/fraud detection, etc.) to still result in the user's or attacker's raw biometric artifacts (iris code shares, normalized iris images, face embeddings/thumbnail) being packaged, encrypted, and uploaded to the backend's storage before the fraud determination is enforced. This is exactly the "liveness/fraud enforcement" and "biometric upload and retention" bug class named in the analog rules: an existing signal meant to block/limit an action (upload of sensitive biometric data) is computed but not actually used to prevent the action, only to annotate it after the fact.

### Likelihood Explanation
The vulnerable code path is on the main, always-executed signup flow (`Plan::run_signup_or_whatever` → `build_pcp` → `personal_custody_package::Plan::run` → `upload_pcp_tier_0`) and requires no special privileges beyond completing the normal unprivileged signup/biometric-capture flow that triggers a fraud flag (e.g., replay/spoof attempt detected post-capture). No malicious operator, peer, or hardware access is required — it is purely a control-flow ordering defect in code reachable by any end user attempting to complete a signup.

### Recommendation
Move the `signup_reason`/fraud check earlier: gate `build_pcp`/`upload_pcp_tier_0` (and the underlying encryption/tar construction of iris and face biometric data) behind a check that `signup_reason != SignupReason::Fraud` before any biometric package is built or uploaded. If the biometric package must still be constructed for audit purposes, ensure it is not transmitted to the backend when fraud has been detected locally, and reorder `detect_fraud()` to run and be enforced strictly before any biometric upload step, rather than only being embedded as a data field consumed for post-hoc reporting.

### Proof of Concept
1. Complete a normal signup flow through biometric capture so that `biometric_pipeline()` returns `Some(pipeline)`.
2. Have `detect_fraud()` return `true` (as it will once the deleted fraud/liveness checks are restored, or via any future liveness/replay detector) so `signup_reason = SignupReason::Fraud` at `src/plans/mod.rs:567-568`.
3. Observe that execution still proceeds unconditionally into `self.build_pcp(...)` at `src/plans/mod.rs:580-587`, which calls `personal_custody_package::Plan::run()` and builds the full tier0/tier1/tier2 encrypted biometric tarballs (`src/plans/personal_custody_package.rs:213-279`).
4. Observe `upload_pcp_tier_0` and the tier1/tier2 `data_uploader` sends at `src/plans/mod.rs:600-636` execute and transmit this data to the backend, all prior to the `signup_reason == SignupReason::Normal` check at `src/plans/mod.rs:645` that determines local success/failure — confirming the fraud signal never gated the biometric upload, only the post-hoc "success" bookkeeping.
