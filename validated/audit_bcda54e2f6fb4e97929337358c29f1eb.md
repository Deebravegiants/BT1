Confirmed: `docs/usage/webhooks.md` explicitly documents that `Registry.process` "will verify the request did indeed come from Shopify" and hands the handler a `shop` field intended to identify which tenant/shop the webhook belongs to [1](#0-0) , and the documented handler example uses `data.shop` directly for tenant-scoped work (e.g. `shop_domain: data.shop`) [2](#0-1) . This confirms the `shop` field is the gem's documented tenant-identity binding, while the code only signs `@raw_body`, giving a solid basis for the finding below.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [3](#0-2) . However, the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler receives and acts on come from HTTP headers that are never included in the signed material [4](#0-3) . This breaks the identity binding `bytes verified == bytes acted on`: only `raw_body` is verified, but `shop` (the tenant identifier) is parsed from an unauthenticated header and passed straight to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [5](#0-4) 

`Utils::HmacValidator.validate` calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the header-supplied HMAC, so it authenticates the body bytes only [6](#0-5) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from headers with no cryptographic binding to the HMAC or the body:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [7](#0-6) 

`Registry.process` validates the HMAC and then forwards the header-derived `shop` value, unmodified, to the app's handler as the tenant identity for the webhook:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

Because the app's `client_secret` (`api_secret_key`) is the same across all shops/tenants of the app (it's a single per-app secret, not per-shop), any party who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body and HMAC while substituting the `x-shopify-shop-domain` header for a different (victim) shop. `HmacValidator.validate` only checks the body bytes, so the swapped header passes verification, and the handler is invoked believing the event belongs to the victim shop. The binding the gem should be enforcing — `shop authenticated by the signature == shop delivered to the app` — does not hold, because `shop` is parsed but never verified.

### Impact Explanation
This is a cross-tenant identity-binding break: the app processes a webhook payload as belonging to shop B (attacker-chosen) when the HMAC only proves that a shop A (attacker-controlled) received the signed body from Shopify. Depending on how the host app uses `data.shop` (as documented, e.g., to scope database writes, enqueue jobs, or invalidate/replace tenant data as shown in the gem's own usage example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables an attacker to inject arbitrary-looking "verified" webhook events attributed to a shop they do not own/operate, i.e., cross-tenant data confusion/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only an unprivileged attacker who can install the target app on their own Shopify store (a normal, low-privilege action for any Shopify app that is publicly installable) and capture one legitimate webhook delivery for their own shop. From there, no access to the app's `client_secret`, a real access token, or the victim's credentials is needed — the attacker directly manipulates only the header they control (`shop-domain`) after copying a validly-signed body.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified material, or otherwise cryptographically bind them (e.g., verify them out-of-band against Shopify's known webhook delivery records / the `shop` recorded for the session used to register that specific webhook, or ensure the HMAC covers a canonical string including these header values) so `to_signable_string` cannot be satisfied by tampering with headers alone.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving a request with a valid `x-shopify-hmac-sha256` computed over the JSON body and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only and it matches (unchanged body) [8](#0-7) .
4. `Registry.process` calls the handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the payload actually originated for the attacker's own shop [9](#0-8) .
