### Title
Webhook `shop`, `topic`, and `webhook-id` fields are trusted by the handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body via `to_signable_string`, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and are never included in the HMAC-covered bytes. `Registry.process` validates the HMAC and then unconditionally forwards these header-derived values to the app's `WebhookHandler#handle` via `WebhookMetadata`, so the tenant/topic identity that the handler acts on is not the identity that was cryptographically verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from the (attacker-controllable, in a replay/relay scenario) HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` checks this body-only HMAC and, once it passes, builds `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` fields, handing them to the app-supplied handler as trusted identity data: [4](#0-3) [5](#0-4) 

This is the exact bug class in the report — "a field acted on but not covered by the HMAC." Here the field is `shop` (the tenant identifier), not the body. The equality that should hold and is broken is:

`shop authenticated by HMAC` ≠ `shop delivered to handler (WebhookMetadata#shop)`

Before the attack: a legitimate webhook for shop A has `raw_body_A` + `hmac = HMAC(secret, raw_body_A)` + header `shop = A`. Because the signature never binds to the header, an attacker who can obtain any validly-signed `(raw_body, hmac)` pair from the same app (e.g., by triggering a webhook on their own development/trial shop that uses the same app installation and thus the same `client_secret`) can resend that exact body/hmac pair with the `shop-domain` header (and/or `topic`/`webhook-id` headers) rewritten to target shop B. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will happily construct `WebhookMetadata.new(shop: "B", ...)` and invoke the handler, which will act as if shop B sent that data.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as documented/intended) to select which tenant's data to update, delete, or key application state by, an attacker who controls one shop instance of a public app can forge webhook deliveries attributed to a different, victim shop merely by relaying a validly-signed payload with substituted headers. This is a cross-tenant data integrity/confidentiality issue (Critical: cross-tenant access) achievable by an unprivileged internet user who only needs their own valid installation of the same app — no access token, `client_secret`, or privileged account is required, since HMAC verification still "passes."

### Likelihood Explanation
Likelihood is moderate to high in realistic deployments: any app author following the gem's documented pattern of trusting `WebhookMetadata#shop`/`topic` for dispatch (this is the only shop/topic information the gem's webhook API exposes to handlers) is exposed. The prerequisite — obtaining one validly HMAC-signed body from the same app (e.g., install the app on an attacker-controlled dev store and capture a webhook) — is trivial for any public Shopify app.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed content, or otherwise validate them against the body of the webhook payload before constructing `WebhookMetadata`. At minimum, `to_signable_string` should incorporate the canonicalized headers so `HmacValidator.validate` fails if any of `shop`, `topic`, or `webhook_id` are altered after signing.

### Proof of Concept
1. Install the target app on an attacker-owned/free development shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST: `raw_body`, and header `X-Shopify-Hmac-Sha256: hmac`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Confirm `hmac == Base64(HMAC-SHA256(client_secret, raw_body))` per `HmacValidator.validate_signature`.
3. Resend the identical `raw_body` and `hmac` to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this only checks `raw_body` against `hmac`, which is unchanged, so validation passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: "…", shop: "victim.myshopify.com", body: parsed_body, …)` and invokes the app's handler as though the data came from `victim.myshopify.com`, even though no request from that shop actually occurred — demonstrating the identity binding break.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
