### Title
Off-chain relayer hosts compute `unbonding_period` with an extra factor of 60 (67.5 days instead of 27 days), loosening the consensus-client freshness/expiry check that guards against long-range fork attacks - (File: `tesseract/consensus/beefy/src/host.rs`, `tesseract/consensus/bsc/src/host.rs`, `tesseract/consensus/grandpa/src/host.rs`, `tesseract/consensus/sync-committee/src/host.rs`)

### Summary
The `unbonding_period` value seeded into `CreateConsensusState` by the BEEFY, BSC, GRANDPA, and sync-committee relayer hosts is computed as `60 * 60 * 60 * 27` seconds (67.5 days) instead of the evidently-intended `60 * 60 * 24 * 27` (27 days) - an extraneous `60` in place of `24`. This value becomes the on-chain `unbonding_period` that `IsmpHost::is_expired` uses to decide whether a consensus client may still accept new consensus updates, so the freshness/staleness guard ends up 2.5x looser than intended across four independent consensus clients.

### Finding Description
`IsmpHost::is_expired` is the on-chain freshness check for every consensus client: it compares `host.timestamp() - consensus_update_time` against the stored `unbonding_period`, and only rejects a consensus update (`Error::UnbondingPeriodElapsed`) once that period has elapsed: [1](#0-0) 

This mechanism exists specifically "to mitigate any potential long fork attacks that may arise due to a loss of liveness of consensus clients," per the protocol docs: [2](#0-1) 

`update_client` is a permissionless, unsigned-extrinsic path (`handle_unsigned` "permits anyone execute ISMP messages for free"), so any relayer can submit `ConsensusMessage`s as long as `is_expired` and the underlying consensus verification pass: [3](#0-2) [4](#0-3) 

The `unbonding_period` supplied at client-creation time is meant to track the *real* economic security window of the underlying chain (i.e., the staking/validator unbonding period, after which previously-honest validators could withdraw stake and their old signing keys carry no slashable risk). The relayer hosts compute this value as: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

`60 * 60 * 60 * 27` = 5,832,000 seconds = 67.5 days, whereas the comment/intent ("27") together with the analogous, correctly-written on-chain BEEFY pallet configuration elsewhere in the codebase (`21 * 24 * 60 * 60` = 21 days) confirms the intended formula is `seconds * minutes * hours * days`, i.e. `60 * 60 * 24 * 27` = 2,332,800 seconds = 27 days: [9](#0-8) 

Other host implementations in the same codebase get this right (e.g. Polygon and Tendermint express hours directly as `82 * 3600`), which further indicates the `60*60*60*27` pattern shared verbatim across BEEFY, BSC, GRANDPA and sync-committee is a copy-pasted typo rather than an intentional value: [10](#0-9) [11](#0-10) 

### Impact Explanation
The staleness threshold that gates whether a consensus client can keep accepting new finality proofs is 2.5x wider than intended for four consensus clients (BEEFY, BSC, GRANDPA, sync-committee). If the real chain's staking/validator unbonding period (Polkadot/Kusama era-based unbonding, BSC validator unstaking, etc.) is shorter than 67.5 days - as it typically is - a consensus client that has gone unmaintained for longer than its true economic-security window, but less than 67.5 days, will still be considered "not expired" on Hyperbridge. Any permissionless relayer can then submit a `ConsensusMessage` referencing that stale client; because `is_expired` does not reject it, the message proceeds to `verify_consensus`, which can be satisfied by validator keys/stake that have already exited and lost their slashing risk. This directly undermines the "long fork attack" mitigation the freshness check is documented to provide, enabling acceptance of unsound/forged state commitments for the affected state machines.

### Likelihood Explanation
The bug is deterministic and present at the point every affected consensus client is bootstrapped (`query_initial_consensus_state`), so it applies to every deployment using these host implementations unless an admin later corrects it via `update_consensus_state`. Exploitation additionally requires the target chain's actual unbonding/economic-security period to fall inside the 27–67.5 day gap and an adversary controlling or having purchased stale validator keys - a non-trivial but realistic long-range attack precondition, consistent with the "Medium" severity of the analogous oracle-freshness report.

### Recommendation
Fix the `unbonding_period` computation in the affected host files to `60 * 60 * 24 * 27` (or otherwise use the chain-specific real unbonding period, expressed explicitly like `82 * 3600` is elsewhere) so the value matches the intended 27-day (or chain-correct) security window: [12](#0-11) [13](#0-12) [14](#0-13) [15](#0-14) 

Also audit any already-created consensus states created with this buggy value and correct their stored `unbonding_period` via `update_consensus_state`.

### Proof of Concept
1. A BEEFY (or BSC/GRANDPA/sync-committee) consensus client is created on Hyperbridge via `create_consensus_client` using `CreateConsensusState.unbonding_period` returned by `query_initial_consensus_state`, which evaluates to `60*60*60*27` = 5,832,000 seconds (67.5 days) instead of the intended 27 days.
2. The relayer/light-client for that chain stops submitting updates (loss of liveness) for, say, 40 days - longer than the chain's actual staking-unbonding period (e.g., ~21-28 days for Polkadot/Kusama-style unbonding), but still under 67.5 days.
3. `is_expired` still returns `Ok(())` because `now - last_update (40 days) < unbonding_period (67.5 days)`, so the client is not frozen.
4. A permissionless relayer submits `Message::Consensus(ConsensusMessage { .. })` via `handle_unsigned`. `update_client` calls `is_expired` (passes) then `verify_consensus`, which can be satisfied using signatures from validators who have already exited/unbonded and no longer risk slashing for equivocation.
5. The forged/insecure state commitment is stored and used to justify subsequent request/response/timeout message delivery on Hyperbridge, defeating the long-range-fork-attack mitigation the freshness check exists to provide.

```rust
	/// Check if the client has expired since the last update
	fn is_expired(&self, consensus_state_id: ConsensusStateId) -> Result<(), Error> {
		let host_timestamp = self.timestamp();
		let unbonding_period = self
			.unbonding_period(consensus_state_id)
			.ok_or(Error::UnnbondingPeriodNotConfigured { consensus_state_id })?;
		let last_update = self.consensus_update_time(consensus_state_id)?;
		if host_timestamp.saturating_sub(last_update) >= unbonding_period {
			Err(Error::UnbondingPeriodElapsed { consensus_state_id })?
		}

		Ok(())
	}
```
