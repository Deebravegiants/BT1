### Title
Pause bypass in `HyperbridgeLzEndpoint.retryPayload` allows delivery of inbound LZ messages while the endpoint is paused - (File: `sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`)

### Summary
`HyperbridgeLzEndpoint` gates its two primary cross-chain entry points, `send()` and `onAccept()`, with `whenNotPaused` so the owner can halt outbound dispatch and inbound delivery during an incident. However `retryPayload()`, the permissionless recovery function that performs the exact same privileged action as `onAccept()` (calling `lzReceive` on the destination OApp), has no `whenNotPaused` modifier at all, so anyone can still deliver stored inbound messages while the contract is paused.

### Finding Description
`send()` and `onAccept()` are both explicitly protected: [1](#0-0) [2](#0-1) 

When `onAccept` fails to deliver a message (e.g. the OApp reverts), the payload hash is stored for later retry: [3](#0-2) 

`retryPayload()` is the documented mechanism to push that stored payload through later, and it performs the identical action `onAccept` performs (a direct `lzReceive` call to the destination OApp), but it is missing the `whenNotPaused` guard present on `send` and `onAccept`: [4](#0-3) 

The function is explicitly documented as "Permissionless: anyone may push a stuck payload through" — the only check is that the caller supplies a `(guid, message)` pair matching a stored hash; there is no owner/host/pause check. Because a stored payload can exist for any previously-failed delivery, and because the owner's `pause()`/`unpause()` toggle the same `Pausable` state used by `send` and `onAccept`: [5](#0-4) 

any unprivileged caller can invoke `retryPayload` to force delivery of an inbound cross-chain message to an OApp (triggering `lzReceive`, e.g. minting on an OFT) even while the owner has paused the endpoint to stop exactly this kind of delivery.

### Impact Explanation
This breaks the emergency-stop guarantee of the pause mechanism for one specific but security-critical class of inbound deliveries. If the endpoint is paused in response to a detected exploit or bad state on the source chain, an attacker who has (or can create) a stuck/retryable payload can still force it through `retryPayload`, causing the destination OApp to execute `lzReceive` with attacker-controlled `executor`/`extraData` and a native-value passthrough (`msg.value`), potentially minting tokens or triggering other OApp logic that the pause was meant to prevent. This is a Medium-severity access-control gap analogous to the reported `getReward()`/`claimRewards()` bypass: a properly-paused primary function (`onAccept`) has an unguarded twin (`retryPayload`) that reaches the same sensitive effect.

### Likelihood Explanation
Likelihood is moderate: it requires a previously stored failed payload (created naturally whenever an OApp's `lzReceive` reverts during normal `onAccept` processing) and does not require any privileged role — any address can call `retryPayload` once such a payload exists, including during a pause window that the owner intended to be a full-stop of inbound delivery.

### Recommendation
Add the `whenNotPaused` modifier to `retryPayload()` (and review `onPostRequestTimeout`, `sendCompose`, and `lzCompose` for similar omissions) so pausing the endpoint fully halts all message-delivery paths, not just the primary `send`/`onAccept` entry points.

### Proof of Concept
1. Owner calls `pause()`, setting the `Pausable` state to paused, intending to halt all send/receive activity.
2. Prior to pausing, an inbound message for OApp `X` had failed delivery in `onAccept` (e.g., the OApp reverted due to a transient condition), so `_inboundPayloadHashes[X][srcEid][sender][nonce]` holds the stored hash.
3. Any address calls `retryPayload(X, origin, guid, message)` with the matching `(guid, message)`. Because `retryPayload` has no `whenNotPaused` check, the call succeeds and invokes `ILayerZeroReceiver(X).lzReceive(...)`, delivering the message and executing OApp logic despite the pause — matching the same bypass pattern as `getReward()` bypassing `claimRewards()`'s `whenNotPaused` guard in the referenced report.

     * @notice Retries an inbound delivery whose OApp `lzReceive` previously reverted in {onAccept}.
     * @dev Mirrors {onAccept}'s direct call to the OApp (the adapter is the caller, so the OApp's
     * `onlyEndpoint` check still passes). Permissionless: anyone may push a stuck payload through
     * once it is executable again. On success the stored payload hash is cleared; if delivery
     * reverts again the whole call reverts and the payload remains recoverable.
     * @param receiver The destination OApp
     * @param origin The (srcEid, sender, nonce) of the stored payload
     * @param guid The original message guid
     * @param message The original message payload (must match the stored hash)
     */
    function retryPayload(
        address receiver,
        Origin calldata origin,
        bytes32 guid,
        bytes calldata message
    ) external payable {
        bytes32 stored = _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];
        if (stored == bytes32(0) || stored == NIL_PAYLOAD_HASH || stored != keccak256(abi.encode(guid, message))) {
            revert InvalidPayloadHash();
        }

        // Clear first; if the retry reverts, this deletion rolls back with the rest of the tx and
        // the payload remains recoverable.
        delete _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];

        ILayerZeroReceiver(receiver).lzReceive{value: msg.value}(origin, guid, message, msg.sender, "");
        emit InboundPayloadResolved(receiver, origin.srcEid, origin.sender, origin.nonce);
    }
