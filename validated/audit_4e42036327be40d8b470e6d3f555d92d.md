### Title
Webhook HMAC Validation Does Not Cover `shop-domain`, `topic`, or `webhook-id` Headers, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook signature check in this gem binds the HMAC exclusively to the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that a host application relies on to attribute an inbound webhook to a specific merchant are read from unauthenticated HTTP headers. This breaks the identity binding: `HMAC(raw_body) == valid` should not be treated as equivalent to `shop-domain header == authentic shop for this body`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and the accessors for `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from request headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e., the body) against the HMAC: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then constructs `WebhookMetadata` directly from the unauthenticated header fields (`shop`, `topic`, `webhook_id`, `api_version`), handing them to the app's registered handler as trusted data: [4](#0-3) 

Because the HMAC never covers `shop-domain`/`topic`/`webhook-id`, any party that can obtain one valid `(raw_body, hmac)` pair signed with the app's shared secret — for example a merchant who installs the app on their own store and receives a genuine webhook delivery — can replay that same body and HMAC to the app's webhook endpoint while substituting arbitrary values for `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id`. The signature still validates (it only checks the body), yet `WebhookMetadata.shop`/`.topic`/`.webhook_id` are now attacker-controlled, even though the app has no way to detect this because the gem presents them as if they came from an authenticated Shopify request.

### Impact Explanation
This breaks the tenant-isolation guarantee that "HMAC valid" implies "this event genuinely originates from the claimed shop and topic." A host application that keys per-tenant side effects (e.g., mapping `app/uninstalled`, `customers/redact`, `shop/redact`, billing, or entitlement changes) off `WebhookMetadata.shop`/`.topic` — which is exactly the intended usage pattern documented for this gem's webhook registry — can be made to process a forged event for a shop/topic combination the attacker chose, using a body they legitimately obtained from their own store's webhook feed. This is a cross-tenant confusion vulnerability directly rooted in the gem's own signature-verification scope, meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (or otherwise obtain one legitimate webhook delivery, e.g., via test webhooks from the Shopify admin) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — both of which are available to an unprivileged internet user with no access to `api_secret_key`, tokens, or the merchant's credentials. No cryptographic secret needs to be broken; only the pre-existing gap in what the HMAC covers needs to be exploited.

### Recommendation
Extend the HMAC-verified signable content (or add a second, mandatory verification step) to bind `shop-domain`, `topic`, and `webhook-id` to the same signature that covers the body, so that tampering with any of these header values invalidates the check — mirroring how `AuthQuery#to_signable_string` binds `shop`, `code`, `state`, `host`, and `timestamp` together for OAuth callbacks. Alternatively/additionally, document and enforce that `WebhookMetadata.shop` must be cross-checked by the host application against the shop associated with the specific `webhook_id` at registration time, rather than trusted as self-authenticating.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers/receives a real webhook, e.g. topic `orders/create`, capturing the raw body `B` and the corresponding header `x-shopify-hmac-sha256: H`, which is a valid `HMAC-SHA256(app_secret, B)`.
2. Attacker sends a new HTTP request to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any other sensitive topic string, provided the handler for that topic is registered)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — verification succeeds per [5](#0-4) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `topic: "app/uninstalled"`, and the host application performs the corresponding tenant-scoped action (e.g., disabling the app, deleting data, or altering billing state) against the victim shop it never actually took that action for.
