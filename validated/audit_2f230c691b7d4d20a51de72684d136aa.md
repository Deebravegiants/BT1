## Finding: Webhook `shop` (and other metadata) not covered by HMAC signature

### Title
Webhook shop/topic/id metadata excluded from HMAC verification allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate` returns true, then hands `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as trusted identifiers. However, the HMAC signature only ever covers the raw request body — none of the "Shopify-*" headers (including `shop-domain`) are part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` performs the authentication check with: [1](#0-0) 

and it forwards `request.shop` into `WebhookMetadata` as an authenticated tenant identifier once validation succeeds: [2](#0-1) 

The HMAC check itself is generic — `Utils::HmacValidator.validate` recomputes the HMAC over whatever `to_signable_string` returns and compares it to `verifiable_query.hmac`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` is defined to be only the raw body: [4](#0-3) 

while `shop`, `topic`, and `webhook_id` are all pulled from unauthenticated HTTP headers: [5](#0-4) 

So the equality the library implicitly promises to the host app — "HMAC valid" ⇒ "`request.shop` is the shop that actually sent this event" — does not hold. Only "HMAC valid" ⇒ "`@raw_body` bytes are unmodified" holds. The `shop-domain` (and `topic`/`webhook-id`) header is a field acted on (passed to the handler as the tenant key) but not covered by the HMAC, matching the bug class described in the report (an identity-binding field that isn't actually bound by the cryptographic check).

### Impact Explanation
Because the app's client secret (`api_secret_key`) used to sign webhooks is shared across every shop that installs the app, any unprivileged user can install the target app on their own (free/dev) Shopify store, trigger a real webhook event, and capture a fully valid `(raw_body, HMAC)` pair from Shopify. That pair remains cryptographically valid no matter what `x-shopify-shop-domain` header value is sent with it, because the header is never part of the signed content. The attacker can then replay the request to the app's webhook endpoint with the header rewritten to point at a victim shop. `Webhooks::Registry.process` will still pass HMAC validation and will invoke the handler with `WebhookMetadata#shop` set to the victim's domain — Critical, cross-tenant access/data confusion (e.g., forged `app/uninstalled`, `orders/create`, or GDPR webhooks attributed to a shop that never sent them).

### Likelihood Explanation
High. The only prerequisite is the ability to install the app on any store (a normal, unprivileged action for any Shopify Partner/dev account) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint — no access token, no leaked credentials, and no privileged account are required.

### Recommendation
Include the tenant-identifying headers in the signed/verified material, or otherwise cryptographically bind `shop` to the payload before the app is allowed to trust it — e.g., extend `Webhooks::Request#to_signable_string` (or add a separate check in `Registry.process`) so that `shop-domain`, `topic`, and `webhook-id` are part of what's verified, not just the raw body. At minimum, the library's documentation/API should make explicit that `request.shop` is unauthenticated and must be cross-checked by the host app against its own session store before being trusted, and `WebhookMetadata` should avoid conflating "HMAC-verified" with "shop-verified."

### Proof of Concept
1. Attacker creates a Shopify dev store and installs the target app (grant type: normal install, unprivileged).
2. Attacker triggers a real event (e.g., updates a product) causing Shopify to send a legitimately-signed webhook: `POST /webhooks` with `X-Shopify-Hmac-Sha256: <valid_hmac_of_body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request but rewrites `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) to `victim-shop.myshopify.com`, keeping body and HMAC untouched.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, which still matches, so `Registry.process` calls the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` — the app now processes attacker-controlled data as if it originated from the victim's store.
