### Title
Gas-griefing "poison message" in `EvmHost.dispatchIncoming` can DoS an entire batched `handlePostRequests` delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` forwards **all remaining gas** to the destination app via an unbounded `.call()` when delivering a POST request. Because `HandlerV2.handlePostRequests` iterates over an array of proven request leaves and invokes `dispatchIncoming` once per leaf in the same transaction, an attacker can permissionlessly dispatch a request whose destination (`to`) is their own malicious contract that deliberately burns almost all forwarded gas. When that request lands in the same batch/transaction as other, legitimate requests, the gas-exhaustion in the malicious call leaves too little gas for the remaining loop iterations, causing the whole `handlePostRequests` transaction to run out of gas and revert — rolling back delivery of every other request bundled in that proof, even though those other requests were otherwise valid and deliverable. This mirrors the NFTX `_sendForReceiver` pattern: an attacker-controlled callee consumes the caller's gas budget via an uncapped external call inside a loop, turning itself into a "poison pill" that denies service to unrelated participants sharing the same transaction/batch.

### Finding Description
`dispatchIncoming` for POST requests performs:
```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [1](#0-0) 
with no gas stipend, so `destination` (fully attacker-controlled via the `to` field of any dispatched request, and reachable since `dispatch()`/`dispatchWithFeeToken` is permissionless) receives essentially all gas left in the call. If the callee spends nearly all of it in a self-contained way (e.g., a bounded busy loop that reverts internally on out-of-gas), `success` is `false` and the host just deletes the receipt and returns without reverting the outer call:
```solidity
if (!success) {
    // so that it can be retried
    delete _requestReceipts[commitment];
    return;
}
``` [2](#0-1) 
That comment (and the identical one in the `extcodesize` check above it) shows the authors were already aware that a single bad request must not blow up the calling batch — but they only handled *explicit call failure*, not the *gas-exhaustion side effect* on the remaining loop.

The caller is `HandlerV2.handlePostRequests`, which loops over `request.requests` and calls `dispatchIncoming` once per proven leaf, all inside one transaction:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [3](#0-2) 
Because EIP-150 lets a callee consume up to 63/64 of the gas forwarded to it before the caller regains control, an attacker's malicious destination contract can leave the remaining loop iterations (and thus the rest of the batch's `dispatchIncoming` calls, plus any subsequent MMR/receipt bookkeeping) with insufficient gas to complete, causing the entire `handlePostRequests` transaction to run out of gas and revert. This reverts *every* request in that proof/transaction, not just the malicious one, denying delivery for all the legitimately bundled requests.

### Impact Explanation
This is a route-level denial of service: relaying software (or anyone submitting `handlePostRequests`/`batchCall` with multiple proven leaves for gas efficiency) can be forced into an all-or-nothing failure by a single attacker-dispatched "poison" request whose destination contract is engineered to burn gas. Legitimate cross-chain messages sharing a batch with the poison request become permanently stuck/undeliverable in that transaction attempt, and relayers must detect and manually isolate the offending leaf (extra operational cost and delay) to make progress — a "route unable to deliver messages" condition for the affected batch. Any application that dispatches messages through `EvmHost.dispatch`/`dispatchWithFeeToken` can be affected if its message happens to be bundled with an attacker's poison message.

### Likelihood Explanation
Dispatching a POST request with an arbitrary `to` address is fully permissionless (`IDispatcher.dispatch`/`dispatchWithFeeToken`), so any attacker can deploy a gas-guzzling contract and target it as the destination of their own message at near-zero cost. The only precondition is that a relayer or third party batches this poison request together with other pending requests into a single `handlePostRequests`/`batchCall` invocation, which is the normal, gas-efficient way batching is designed to work in this codebase (`IHandlerV2.batchCall`, `HandlerV2.handlePostRequests` processing arrays of leaves). No governance, admin, or privileged role is required.

### Recommendation
Cap the gas forwarded to destination apps in `EvmHost.dispatchIncoming` (and the analogous `onGetResponse`/timeout dispatch calls) with an explicit `call{gas: G}(...)`, sized to a safe fixed budget (with any excess app logic simply failing and being retried individually, as the existing failure path already supports). This bounds the worst-case gas any single malicious destination can consume, preventing it from starving the remaining iterations of a batched delivery.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept` that runs an unbounded/near-gas-limit compute loop (e.g., repeated hashing until `gasleft()` is nearly zero) and does not revert cleanly — it simply consumes essentially all gas passed to it, causing the call itself to run out of gas.
2. Attacker calls `EvmHost.dispatch` (or the appropriate cross-chain send) with `to = address(EvilApp)` on the destination chain, paying a minimal/zero relayer fee.
3. A relayer collects this request along with several unrelated legitimate pending requests destined for the same chain and submits them together via `HandlerV2.handlePostRequests` (or `batchCall`) in one transaction, as `tesseract/messaging/evm/src/tx.rs`'s batch-building logic is designed to do.
4. Inside the loop, `dispatchIncoming` forwards nearly all remaining gas to `EvilApp.onAccept`, which consumes it; per EIP-150 the outer frame is left with roughly 1/64 of the pre-call gas.
5. With too little gas left, subsequent `dispatchIncoming` calls in the loop (or state writes/emitting events) run out of gas, and the entire `handlePostRequests` transaction reverts, rolling back delivery of all requests in the batch — including the legitimate ones — even though only the attacker's own request was malicious.
