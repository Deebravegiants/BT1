## Finding

### Title
Webhook shop/topic/webhook-id identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once its HMAC validates, and then dispatches business logic using `request.shop`, `request.topic`, and `request.webhook_id` taken straight from HTTP headers. However, the HMAC signature only ever covers the raw request body — none of the identifying headers are part of the signed material. Anyone who can obtain one valid `(body, hmac)` pair (e.g. from their own shop's legitimate webhook deliveries) can replay it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the gem will still report the HMAC as valid and hand the forged shop identity to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

None of `topic`, `shop`, `webhook_id`, or `api_version` — all parsed unauthenticated from headers — are included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string`: [3](#0-2) 

`Registry.process` gates on this HMAC check and then forwards the *unverified* `shop`, `topic`, and `webhook_id` fields directly into `WebhookMetadata`, which the host app's handler trusts as the tenant identity for the event: [4](#0-3) 

**Binding broken (as an equality):** the gem's contract is effectively `hmac_valid(body) == identity_of(shop, topic, webhook_id)`, but in reality `hmac_valid` only proves `hmac_valid(body)`; `shop`/`topic`/`webhook_id` are attacker-controlled headers with no cryptographic tie to the signed body. This is the same class of bug as the reference finding: a field (the vault to slash / here, the shop the webhook is attributed to) is acted upon without being covered by the authenticity check that gates the action.

Before the attacker's request: a legitimately signed webhook body+HMAC exists only for the shop it was actually generated for (e.g., the attacker's own shop, or any body they can otherwise obtain).
After the attacker's request: by replaying the same body+HMAC to the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header, `Utils::HmacValidator.validate` still returns `true` (it never examined those headers), and `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain.

### Impact Explanation
This lets an unprivileged internet user who possesses any one valid signed webhook body (trivially available to any merchant who has installed the app, since they receive their own webhooks) forge webhook deliveries attributed to a different, arbitrary shop domain. Host applications that build their entire trust model on `Registry.process`'s HMAC gate (as documented) will process business-critical webhook data (order/customer/app-uninstall events, etc.) as if it came from a different tenant, i.e. cross-tenant confusion/access driven entirely by unauthenticated header values. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
High. No secret material is required — the attacker only needs one legitimately delivered `(raw_body, hmac)` pair (their own webhook traffic is sufficient) and access to the app's public webhook HTTP endpoint, which by design accepts unauthenticated POSTs validated only via this HMAC check.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the material that is authenticated, or otherwise re-derive/verify shop identity independent of headers before dispatching to handlers — e.g., extend `Webhooks::Request#to_signable_string` to incorporate these header values (matching how `Auth::Oauth::AuthQuery#to_signable_string` binds all relevant fields), so that tampering with any of them invalidates the HMAC.

### Proof of Concept
```ruby
# Attacker has legitimately received one webhook for their own shop:
raw_body = '{"id":123}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker crafts a new request reusing the same body+hmac but a different shop domain:
forged_headers = {
  "x-shopify-topic"       => "customers/data_request",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary, attacker-chosen
  "x-shopify-webhook-id"  => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation passes because only raw_body is signed:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process dispatches to the handler with the forged shop identity:
ShopifyAPI::Webhooks::Registry.process(request)
# handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
