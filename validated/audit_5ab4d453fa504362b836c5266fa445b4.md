### Title
Underflow-Panic Denial of Service on Graduation via the Pair `+1` K-Slack Rounding Wei - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._prepareGraduationLiquidity` (and the identically-shaped USD-trigger check inside `canGraduate`) recover the launch-time virtual LT reserve and unconditionally subtract it from the pair's live stored `assetReserve`:

```solidity
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
``` [1](#0-0) 

This subtraction assumes `assetReserve >= virtualLtReserve` always holds. The invariant is documented as resting on `Pair.k()` never changing after mint and reserves only moving through curve trades, but `Pair.swap`'s own K-invariant check tolerates a `+1` rounding slack on the output side (explicitly called out in the scope rules as one of alt.fun's real bug-prone areas). A sequence of sells that repeatedly exploits that 1-wei slack can walk the pair's stored `reserve1` (`assetReserve`) down by cumulative rounding error until it drops one wei below the recovered `virtualLtReserve`, exactly analogous to the external report's root cause: code that dereferences/consumes a value without validating it can be in the invalid (null/out-of-range) state, causing an unconditional crash instead of a graceful revert or safe path.

### Finding Description
`_launchTimeVirtualLtReserve` recovers the launch-time virtual reserve as `Pair.k() / Token.TOTAL_SUPPLY()`, relying on `_pool.k` being fixed forever at `totalSupply * virtualLtReserve_init` from `Pair.mint`, while `assetReserve` is the *live*, mutable stored reserve that every subsequent `Pair.swap` call updates subject only to the K-floor check (`newReserve0 * newReserve1 >= k`), not an exact equality. [2](#0-1) 

Because the K-floor check is a `>=` inequality with a `+1` slack (per the scope description of `Pair.swap`'s K-check), successive sells can each round the effective output down by up to that slack, letting the stored `assetReserve` drift below the theoretically exact `virtualLtReserve` floor by accumulated rounding wei — a state the code never validates for. When that state is reached, `assetReserve - _launchTimeVirtualLtReserve(...)` underflows a `uint256`, and Solidity 0.8's checked arithmetic reverts with a `Panic(0x11)` instead of any custom, catchable error.

This same subtraction pattern is documented as also being the core of the USD graduation trigger (`(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ threshold`), and `canGraduate` is invoked unconditionally at the end of *every* buy inside `Bonding._executeBuy`:
```solidity
if (canGraduate(tokenAddress)) {
    _enterGraduating(tokenAddress);
}
``` [3](#0-2) 

Once the underflow condition is reached, every future call that evaluates this subtraction — the inline `canGraduate` check at the tail of `Bonding.buy`, the permissionless `Bonding.triggerGraduation`, and `_prepareGraduationLiquidity` itself — panics and reverts. Since `Zap.sell` also calls into `Bonding.triggerGraduation`/`canGraduate` on the same code path when a sell lands while the token is "ripe," sells are bricked too. The curve for that token becomes permanently untradeable: no buy, no sell, no graduation, with the creator's and traders' curve-raised LT and the 250M `lpReserve` tokens permanently stuck in `Bonding` between phases — exactly the "parks all curve-raised LT and 250M tokens on Bonding between phases" state the scope calls out as sensitive, now with no way out.

### Impact Explanation
This is a permanent freeze of trader and creator funds: once triggered, the affected token's `Pair` can never buy, sell, or graduate again, because the crash occurs inside the mandatory graduation-check codepath shared by both `buy` and `sell`. All LT raised by the curve and the 250M reserved tokens remain locked in `Bonding` with no recovery function, satisfying the "permanent freezing of trader, creator or LP funds" bar for a valid finding.

### Likelihood Explanation
Reachable purely through `Zap.sell` calls by any unprivileged trader — no privileged role, no upgrade, no off-chain component required. The attacker needs only enough sell volume/iterations against a single curve to accumulate the rounding slack that the K-floor's `+1` tolerance permits; this is bounded by gas/transaction count rather than any protocol permission, making it fully executable by a single unrelated wallet.

### Recommendation
Replace the unchecked subtraction in `_launchTimeVirtualLtReserve`-derived math (`_prepareGraduationLiquidity` and the equivalent computation inside `canGraduate`) with a saturating subtraction (clamp to 0 when `assetReserve <= virtualLtReserve`), mirroring the defensive `ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0` pattern already used in `finalizeGraduation`. Additionally, verify whether `Pair.swap`'s K-floor slack can ever let `reserve1` fall below the launch-time virtual seed at all, and if so tighten the K-check so that boundary can't be crossed in the first place.

### Proof of Concept
1. Launch a token via `Zap.createToken`, establishing `Pair.k() = totalSupply * virtualLtReserve_init`.
2. As an unprivileged trader, repeatedly `Zap.buy` then `Zap.sell` small amounts against the same curve, each round-trip landing on the `+1` K-floor slack on the sell leg so the stored `reserve1` (`assetReserve`) is nudged down by 1 wei relative to the theoretical floor.
3. After enough iterations, `assetReserve` sits one (or more) wei below `Pair.k() / Token.TOTAL_SUPPLY()`.
4. Submit one more `Zap.buy` (or call `Bonding.triggerGraduation` directly): the inline `canGraduate` check (or `_prepareGraduationLiquidity` inside `_enterGraduating`) executes `assetReserve - virtualLtReserve`, underflows, and the transaction reverts with `Panic(0x11)`.
5. From this point, every subsequent `Zap.buy`/`Zap.sell`/`Bonding.triggerGraduation` call on that token reverts identically — the curve, its raised LT, and the reserved 250M tokens are permanently stuck.

Note: I was not able to inspect `Pair.swap`'s exact K-floor comparison or `Router._computeSell`'s rounding formula within the available tool budget to fully confirm the precise number of sell iterations needed to accumulate the 1-wei drift; the underflow mechanics of `_prepareGraduationLiquidity`/`canGraduate`'s subtraction, and its reachability from every buy/sell via `_executeBuy`, are confirmed directly from the cited source.

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }
```
