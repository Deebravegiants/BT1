### Title
Emporium `runAction` CASE 2 arbitrary external call lets any user steal non-ERC20 assets (e.g. Uniswap V3 LP NFTs) that end up owned by the Emporium contract - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` lets any caller with a valid Hinkal proof execute an arbitrary `op.endpoint.call(op.callData)` (CASE 2, `invokeWallet=false`), with essentially no restriction on `endpoint` or `callData` beyond blocking two specific wallet selectors. Because Emporium's post-call accounting (`getBalancesForArray`/`handleOut`) only tracks ERC20/ETH balances listed in `circomData.erc20TokenAddresses`, any ERC721 (or other non-listed asset) that ends up owned by the Emporium contract (e.g. a victim minting a Uniswap V3 LP position with `recipient=Emporium`) is never converted into a UTXO for the depositor and is left as bare contract-owned state that any subsequent unrelated caller can drain via their own `runAction` call.

### Finding Description
The claimed invariant is: `owner of every asset created by op.callData == circomData.stealthAddressStructure of the wallet that produced the proof`. This invariant is never enforced anywhere in the contracts — Hinkal's balance-accounting loop in `Hinkal.transact` and `EmporiumUpgradeable.runAction`/`handleOut` only reconciles ERC20/ETH balances that appear in `circomData.erc20TokenAddresses`: [1](#0-0) 
An ERC721 minted to `address(this)` (Emporium) via CASE 2's unrestricted external call is simply never observed by this loop: [2](#0-1) 
`Transferer.onERC721Received` unconditionally accepts any NFT transfer, so the mint succeeds and the token is simply held by Emporium with no on-chain record tying it to the depositor: [3](#0-2) 

Because the NFT is now owned by Emporium itself, any other unprivileged user can call `EmporiumUpgradeable.runAction` with their own valid proof (for their own unrelated deposit/withdraw — no connection to the victim required) and craft an `EmporiumStack` with `signerAddress = address(0)` (CASE 2, no signature check needed beyond `usedMessages` nonce uniqueness): [4](#0-3) 
and an operation `{endpoint: positionManager, callData: transferFrom(Emporium, attacker, tokenId)}`. Since the actual `.call` is made by the Emporium contract (`op.endpoint.call{value: op.value}(op.callData)`), `msg.sender` inside `positionManager.transferFrom` is `Emporium`, which is the token owner, so `_isApprovedOrOwner` passes trivially. `onlyAllowedRecipient` only checks that the caller of `runAction` is the Hinkal contract, not any property of `op.endpoint`/`op.callData`: [5](#0-4) 
None of `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, or `rootHashExists` constrain the contents of `externalActionMetadata`/`EmporiumStack.ops` beyond calldata-hash integrity of the attacker's own submitted data — they only validate the attacker's own proof against the attacker's own UTXOs, never against what assets Emporium happens to be holding.

### Impact Explanation
Direct theft of a shielded user's non-fungible/other-untracked asset (Uniswap V3 LP NFT or any other token/asset acquired via a CASE-2 external call to `Emporium`) by any unrelated, unprivileged attacker, with no relation between the attacker's proof/UTXOs and the victim's. This is repeatable for every asset that ends up owned by Emporium outside the ERC20/ETH balance-tracking loop (any ERC721/ERC1155, or any other stateful position such as staking receipts, that isn't represented in `erc20TokenAddresses`). This matches "Critical — direct theft of shielded or in-flight user funds ... executing calls or moving assets a wallet owner or prover never authorised" and also independently matches "High — executing calls or moving assets a wallet owner or prover never authorised" for the attacker's arbitrary-call capability itself.

### Likelihood Explanation
Preconditions: a victim (or the protocol via a supported integration) performs a CASE-2 Emporium action whose `callData` causes a non-ERC20 asset to be transferred/minted to `address(this)` (Emporium) — e.g. Uniswap V3 `mint(recipient=Emporium)`. Attacker cost: one ordinary Hinkal transaction of their own funds (even dust amounts) plus crafting `EmporiumStack` with `signerAddress=address(0)` and an op targeting the known Emporium address and known token id (discoverable on-chain via `Transfer`/mint events). No privileged role, no victim key, no relayer collusion required — fully within the "unprivileged attacker" threat model.

### Recommendation
- Restrict CASE 2 `op.endpoint` calls to a whitelist of vetted, side-effect-safe endpoints, or require that any asset acquired by Emporium be immediately forwarded out of Emporium (not left custodied) within the same `runAction` call.
- Explicitly track and reconcile non-ERC20 assets (ERC721/ERC1155 token ids) received during `runAction`, minting a corresponding UTXO/ownership record bound to `circomData.stealthAddressStructure`, mirroring the ERC20 balance-diff accounting.
- Alternatively, disallow/deny-list `onERC721Received`/`onERC1155Received` on Emporium entirely unless the receiving flow immediately attributes and forwards the asset to the depositor within the same transaction, closing the custody gap that this finding exploits.

### Proof of Concept
Hardhat fork test (mainnet fork with real Uniswap V3 `NonfungiblePositionManager`):
1. Deploy Hinkal stack with `EmporiumUpgradeable` as allowed external action; whitelist relevant tokens.
2. Victim deposits WETH/USDC into Hinkal, then submits `transact` with `externalActionData.externalActionId = Emporium`, `externalActionMetadata` = `EmporiumStack{signerAddress:0, ops:[{endpoint: positionManager, invokeWallet:false, callData: mint({... recipient: EmporiumAddress ...})}]}`. Assert `positionManager.ownerOf(tokenId) == EmporiumAddress` after the tx (equality 1: NFT owner == Emporium, not victim's stealth address — this is the broken side).
3. Attacker (separate EOA, unrelated deposit of e.g. 1 wei of a token) submits their own `transact` call with a fresh `emporiumMessage`, `externalActionMetadata` = `EmporiumStack{signerAddress:0, ops:[{endpoint: positionManager, invokeWallet:false, callData: transferFrom(EmporiumAddress, attacker, tokenId)}]}`.
4. Assert the attacker's `transact` succeeds (no revert), and `positionManager.ownerOf(tokenId) == attacker` post-tx — confirming theft of the victim's LP NFT with no relation between attacker's proof/UTXOs and the victim's deposit.
