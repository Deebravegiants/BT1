### Title
Webhook `shop` field is trusted for tenant identification despite being unauthenticated by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but the `shop` value the gem hands to the app's handler is read straight from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. This breaks the identity binding `HMAC-verified bytes == data acted on`, exactly the class of bug described in the external report (packing arguments that are checked together but not actually bound together during verification).

### Finding Description
`Registry.process` treats a request as authentic Shopify traffic purely based on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the shop domain header is intentionally excluded from the signed data: [3](#0-2) [4](#0-3) 

Yet `request.shop` (the unauthenticated header) is what gets forwarded to the app's handler as the tenant identifier for the webhook event: [5](#0-4) 

The documented handler contract explicitly instructs integrators to key off `data.shop` as "The shop domain of the webhook," reinforcing that this field is meant to be trusted as the tenant identity once `process` succeeds: [6](#0-5) 

The equality that should hold is: `shop bound inside HMAC-verified bytes == shop used to attribute the event`. In this implementation that equality is never enforced — the verified bytes are `raw_body` only, while the attributed tenant (`shop`) comes from an out-of-band header that any client can set arbitrarily on the HTTP request.

### Impact Explanation
Any unprivileged internet user who can install the app on their own store (or otherwise obtain one legitimately signed `(body, hmac)` pair for a webhook topic from their own shop) can capture that pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body/HMAC pair, which is genuine), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. If the host app's handler uses `data.shop` to look up the merchant/session and perform actions or store data (the exact usage pattern shown in the gem's own documentation, e.g. `perform_later(shop_domain: data.shop, ...)`), this results in cross-tenant data injection/attribution — writing or reacting to attacker-controlled webhook bodies under a victim shop's identity. This matches the Critical "cross-tenant access" impact bucket in scope.

### Likelihood Explanation
The attacker only needs to be a legitimate (even free/trial) merchant of their own shop with the target app installed — no `api_secret_key`, access token, or network interception is required, since replaying an HTTP request with a modified header is trivial once the attacker possesses one authentic body+HMAC pair from their own tenant. The gem provides no additional binding (e.g., verifying the header shop against a value embedded in the signed body, or against an expected shop for a known webhook id) to prevent this.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` as authenticated. Either:
- Include the shop domain (and other identity-relevant headers) in the HMAC-covered signable string (this requires a corresponding change to how Shopify signs webhooks, so is likely infeasible unilaterally), or
- Require the consuming application to cross-check `request.shop` against the shop already associated with the specific `webhook_id`/subscription id in their own registered-webhooks records before acting on the payload, and clearly document that `shop` is not itself covered by the HMAC signature, or
- At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is unauthenticated and must not be used alone to key merchant data lookups without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook (e.g. `orders/create`) — capturing the raw POST body and the genuine `X-Shopify-Hmac-Sha256` header Shopify computed with the app's real secret.
2. Attacker replays that exact request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Utils::HmacValidator.validate` succeeds because it only re-hashes `raw_body`, which is unchanged.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, per the flow at: [1](#0-0) 
5. A handler written per the gem's documented pattern (`perform_later(shop_domain: data.shop, webhook: data.body)`) now processes attacker-controlled content attributed to the victim shop.

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
