### Title
Unbounded order.inputs / order.output.assets arrays in IntentGatewayV2 allow permanent freezing of escrowed funds via out-of-gas withdrawal - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder()` in `IntentGatewayV2` accepts an `Order` struct whose `inputs` (a `TokenInfo[]`) and `output.assets` arrays have no length cap, and every element is escrowed and iterated over again later during redemption/refund. An unprivileged user placing an order with a very large number of distinct input tokens can create escrow state whose later withdrawal loop exceeds the destination/source chain's block gas limit, permanently freezing the escrowed funds — the same bug class as the referenced Splits `distribute()` report, but here in Hyperbridge's Intents escrow rather than a payment splitter.

### Finding Description
`placeOrder()` loops over `order.inputs` and `order.output.assets` multiple times with no upper bound on `inputsLen` / `outputsLen_`: [1](#0-0) [2](#0-1) 
Each accepted input token amount is written into escrow storage individually: [3](#0-2) 

There is no `validate()`-style check limiting `order.inputs.length` (unlike the reported Splits fix, which caps `recipients.length`). Later, when the order is redeemed (`RedeemEscrow`) or refunded (`RefundEscrow`) via a cross-chain message delivered by any relayer, `withdraw()` iterates over `body.tokens`, performing an external token transfer (native call or `IERC20.transfer`) for every entry: [4](#0-3) 
This function is reached from the unprivileged, relayer-delivered dispatch path: [5](#0-4) 

Because `body.tokens` mirrors `order.inputs` (set at order-placement time by an ordinary user), a maliciously (or carelessly) crafted order with hundreds/thousands of distinct token entries produces a withdrawal transaction whose gas cost scales linearly with the number of tokens — exactly analogous to the Splits `distribute()` report, where a large `recipients` array made `distribute()` unexecutable within the block gas limit. If the resulting `withdraw()` call cannot fit in a block, the RedeemEscrow/RefundEscrow message can never be successfully delivered, and the escrowed input tokens remain locked in the `IntentGatewayV2` contract indefinitely, with no privileged recovery path comparable to a Splits wallet owner's `execCalls()`.

### Impact Explanation
This is a concrete, permanent freezing-of-funds vector: user assets escrowed by `placeOrder()` can become permanently unrecoverable if the corresponding fill/refund message can never be delivered because its `withdraw()` execution exceeds the destination chain's block gas limit. Unlike the cited Splits report (which had an owner-controlled escape hatch via `execCalls()`), `IntentGatewayV2` has no analogous privileged recovery for escrowed order funds, making the freeze effectively permanent. This qualifies as a Medium/High severity permanent-freezing-of-funds finding reachable from a single unprivileged `placeOrder()` transaction.

### Likelihood Explanation
Likelihood is moderate: it requires either a malicious order creator intentionally padding `order.inputs`/`order.output.assets` with many token entries to grief their own or others' funds (e.g., to test/exploit relayer economics or as a self-DoS proof), or an unaware integrator (e.g., building a large multi-token bundle order) hitting the limit unintentionally. As with the original Splits report, this doesn't require any privileged role and is directly reachable by any address calling `placeOrder()`.

### Recommendation
Add an explicit upper bound check on `order.inputs.length` and `order.output.assets.length` in `placeOrder()` (and correspondingly validate `WithdrawalRequest.tokens.length` before processing), similar to the recommended Splits fix, e.g.:
```solidity
if (order.inputs.length > MAX_TOKENS || order.output.assets.length > MAX_TOKENS) revert InvalidInput();
```
choosing `MAX_TOKENS` conservatively based on gas benchmarks of `withdraw()`'s per-token cost versus the target chains' block gas limits, with sufficient safety margin for tokens with expensive `transfer()` implementations.

### Proof of Concept
Not independently re-derived against this repo's test suite (no PoC harness available in the retrieved context), but conceptually mirrors the cited report's methodology: construct an `Order` with `inputs` containing N distinct token addresses (N large enough, e.g. 500–1000+, based on `withdraw()`'s per-iteration cost of an `IERC20.transfer` call plus storage writes/reads), call `placeOrder()` to escrow it, then attempt to deliver the corresponding `RedeemEscrow`/`RefundEscrow` message and measure the gas consumed by `withdraw()` against the destination chain's block gas limit, analogous to the `testZach_distributeGas` PoC in the original report.
