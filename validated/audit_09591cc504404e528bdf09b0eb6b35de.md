## Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant impersonation via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, and `ShopifyAPI::Webhooks::Registry.process` validates only that body-derived HMAC. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken directly from HTTP headers — are never included in the signed payload, so any bytes in those headers can be swapped without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the request purely through this body-only signature and then immediately trusts the header-derived `shop`, `topic`, and `webhook_id` to build the dispatched metadata: [2](#0-1) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from headers with no relationship to the HMAC-covered bytes: [3](#0-2) 

The equality this breaks: `HMAC-verified bytes == webhook identity used for tenant/topic dispatch`. Only the JSON body is authenticated; the tenant-identifying `shop-domain` header (and `topic`/`webhook_id`) are authenticated-in-name-only. Any unprivileged internet user who owns any Shopify development/trial store (no privileged credentials, no `api_secret_key`, no access token needed) can obtain one genuinely-signed webhook from Shopify for their own shop, then replay that exact body/HMAC pair to the target app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header to name a victim shop or a different topic. `HmacValidator.validate` will still pass because it only recomputes the signature over `@raw_body`: [4](#0-3) 

The app's handler then receives `WebhookMetadata` with an attacker-chosen `shop` and/or `topic`, believing it was authenticated end-to-end.

### Impact Explanation
This lets an attacker cause the receiving application to process webhook data under an arbitrary `shop` identity of the attacker's choosing (cross-tenant), or reinterpret one topic's payload as belonging to another topic, without ever possessing the app's `client_secret`/`api_secret_key`. Because host applications key their per-shop state/session lookups off `WebhookMetadata#shop`, this is a cross-tenant data-injection/spoofing primitive — matching the Critical "cross-tenant access" impact category, since the shop binding that should be cryptographically tied to the authenticated payload is not.

### Likelihood Explanation
Requires only a store the attacker legitimately controls (any Shopify dev/partner store is free and unprivileged to create) to harvest one valid `(body, hmac)` pair for any subscribed topic, plus a public POST to the target app's webhook endpoint. No secrets, tokens, or social engineering needed — purely a replay with header substitution.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed payload (or otherwise cryptographically bind them to the body, e.g. by verifying the shop is one the app has legitimately installed for and cross-checking it against the OAuth-obtained record for the `webhook_id`) rather than trusting these header values outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`) — Shopify sends a request with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's real secret.
2. Attacker captures this raw body and HMAC value.
3. Attacker POSTs the identical body + HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because it only checks `@raw_body` against the HMAC.
5. The handler executes with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: ...)`, causing the app to act as if Shopify sent this data on behalf of the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
