Based on my investigation, I found a concrete, exploitable vulnerability analogous to the Aave incident.

### Title
Persistent ERC20 approvals granted through `CallDispatcher` can be replayed to drain any funds later routed through the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes fully attacker-controlled `Call[]` arrays — including arbitrary `to`/`data` — in its own (non-delegatecall) context, and is invoked with unfiltered, cross-chain-message-supplied calldata from both `HyperFungibleToken.onAccept` and `IntentGatewayV2`/`IntentsBase._execute`. Because the dispatcher is a single shared contract address configured across multiple apps (HFT, WrappedHFT, IntentGatewayV2), any unprivileged sender can plant a standing `approve(attacker, type(uint256).max)` for a high-value token (e.g. USDC) from the dispatcher's own address, then later drain any balance of that token that transiently passes through the dispatcher on behalf of unrelated users — directly via `transferFrom` on the token contract, bypassing all of the dispatcher's, gateway's, and app's own logic. This mirrors the Aave "peripheral contract, arbitrary call, approval abuse" bug class: a helper contract makes attacker-influenced arbitrary calls, and leftover approvals from that helper are later exploited to steal funds that pass through it.

### Finding Description
`CallDispatcher.dispatch` has no access control and no restriction on the `to`/`data` fields of each `Call`: [1](#0-0) 

This function is called with attacker-controlled `data`:
- In `HyperFungibleToken.onAccept`, `message.data` comes straight from the cross-chain `Message` body, which is fully controlled by whoever calls `send()` on the source chain (`params.data` is passed through unmodified into the message and later `abi.decode`d as `Call[]` for dispatch): [2](#0-1) [3](#0-2) 

- In `IntentsBase._execute` / `IntentGatewayV2`, `order.output.call` and `order.predispatch.call` are likewise forwarded to `ICallDispatcher(dispatcher).dispatch(...)` without validating the call targets: [4](#0-3) [5](#0-4) 

Docs confirm the dispatcher is a small set of shared, chain-wide singleton deployments referenced by config across all apps ("Existing `CallDispatcher` deployments are listed on the contract addresses page"), and explicitly warn that approvals issued through it persist beyond the triggering transaction: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution."

Because an ERC20 `approve()` call executed by the dispatcher (`msg.sender == dispatcher`) writes a permanent allowance entry keyed by `(dispatcher, spender)` on the token contract, this state is **not reset** after the current calldata-execution finishes, regardless of whether the intended swap/DeFi call in the same batch succeeds. Any attacker can:
1. Send a trivial cross-chain HFT transfer (or place a self-fillable intent order) whose `data`/`output.call` contains a single `Call{ to: USDC, data: approve(attacker, type(uint256).max) }`. This executes through the shared `CallDispatcher`, granting `USDC.allowance(dispatcher, attacker) = max`.
2. Wait for any unrelated legitimate user's HFT calldata-execution transfer or IntentGatewayV2 order fill that routes USDC through the same dispatcher (e.g., `to: CallDispatcher` mint target, or predispatch/output asset transfers to the dispatcher before the sweep-back step).
3. Front-run/race and call `USDC.transferFrom(dispatcher, attacker, balance)` directly on the token contract — no interaction with `dispatch()`, `onlyHost`, or any gateway checks required — draining the victim's tokens while they transiently sit in the dispatcher.

### Impact Explanation
This allows a single unprivileged transaction (an HFT `send()` with crafted `data`, or an intent order with a crafted `output.call`) to set up a persistent backdoor allowance on any ERC20 token from the shared `CallDispatcher`, which can later be exploited to steal funds belonging to unrelated users whose cross-chain transfers or order fills momentarily route the same token through that same dispatcher instance. This is concrete theft of funds reachable from a single relayed message/dispatched request, satisfying the Medium/High impact bar (direct fund loss, not merely griefing), and is a direct structural analog of the Aave "arbitrary call in a peripheral contract" incident.

### Likelihood Explanation
Likelihood is high: the attack requires only one cheap cross-chain transfer/order to plant the approval, no privileged role, and the shared dispatcher is a core, actively-used part of every HFT calldata-execution flow and IntentGatewayV2 fill. The attacker only needs to monitor the dispatcher's token balance/mempool activity to time the `transferFrom` call, which is a plain, unrestricted ERC20 call requiring no special access.

### Recommendation
- Have `CallDispatcher` revoke/reset any non-zero allowances it granted to third-party spenders at the end of every `dispatch()` call (or restrict `approve`-style calls to same-transaction "exact amount, single-use" patterns enforced on-chain).
- Alternatively, deploy an ephemeral/ per-call dispatcher (e.g., via `CREATE2` + `SELFDESTRUCT`-style cleanup, or a minimal proxy created per execution) so no state (including allowances) persists across unrelated calls to different apps/users.
- Add a check that any token/spender approved through `dispatch()` has its allowance swept to zero before the call returns, and monitor/alert on non-zero allowances left on the shared dispatcher.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send()` on chain A with `params.data = abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})])` and `params.to` set to any address (amount can be dust/zero-value transfer, cost is only gas + relayer fee).
2. Relayer delivers the message; `onAccept` at [6](#0-5)  calls `ICallDispatcher(_dispatcher).dispatch(message.data)`, executing `USDC.approve(attacker, max)` from the dispatcher's address.
3. At any later point, when a legitimate user's HFT transfer-and-swap or IntentGatewayV2 fill causes USDC to be minted/transferred to the same `CallDispatcher` address (e.g., `to: CALL_DISPATCHER` per the documented "mint to CallDispatcher" pattern), attacker calls `USDC.transferFrom(dispatcher, attacker, currentBalance)` directly, draining the victim's funds before the intended swap/sweep executes.
