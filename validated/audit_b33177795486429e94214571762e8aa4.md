### Title
Webhook shop/topic/webhook_id identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are the values the library and the app's handler actually act on — are read directly from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` decodes the `hmac-sha256` header value: [1](#0-0) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the body) and compares it to the supplied `hmac`: [2](#0-1) 

`Registry.process` accepts the request once the body HMAC checks out, then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` — all of which came from headers that were never part of the signed bytes: [3](#0-2) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` says only "this body byte-string was signed by someone holding `api_secret_key`" — it says nothing about which shop, topic, or webhook id the signer intended. The library nevertheless treats `request.shop` as trustworthy tenant identity for the handler (`WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`), i.e. it conflates "bytes verified" with "shop/topic verified."

Compare this to `Auth::Oauth::AuthQuery`, where `shop` is explicitly included in `to_signable_string` and therefore is bound by the HMAC: [4](#0-3) 

The webhook path has no equivalent binding for `shop`/`topic`/`webhook_id`.

### Impact Explanation
An attacker who can obtain one legitimately-signed webhook delivery for a body they control (e.g., by installing the app on their own store and triggering any webhook topic whose payload doesn't happen to embed the destination shop, or simply by capturing any webhook the app receives) possesses a `(raw_body, hmac)` pair that will pass `HmacValidator.validate` for *any* header values, because headers are excluded from the signed content. The attacker can then POST that same body/HMAC pair directly to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to name a different, victim shop. `Registry.process` will accept it as a validly-authenticated webhook and hand the attacker-chosen body to the handler tagged with the victim's shop identity — a cross-tenant data-integrity break (the app will act on/store data as if it came from a shop it did not come from). This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Webhook endpoints exposed by apps using this gem are public HTTP endpoints (that is the point of webhook delivery), so no privileged credential is required to reach them. The only prerequisite is having observed one valid `(body, hmac)` pair for the target app/secret, which is achievable by any developer who installs the app on their own store (a normal, unprivileged action) and captures their own webhook traffic. No knowledge of `api_secret_key` is needed to mount the replay/header-substitution.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed content that `HmacValidator` verifies for webhooks, mirroring what `AuthQuery#to_signable_string` already does for OAuth. Concretely, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` (and `topic`) header values, not just the raw body, so the HMAC cryptographically commits to which shop/topic the payload is for. Additionally, `Registry.process` should require the caller to reconcile `request.shop` against a known, currently-installed session/shop before invoking the handler.

### Proof of Concept
1. App developer installs their app on `attacker-shop.myshopify.com` and lets Shopify deliver a webhook, e.g. `orders/create`, capturing the raw POST: headers `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and body `B` (order JSON that contains no explicit destination-shop field).
2. Attacker replays the exact same request to the app's public webhook endpoint but rewrites the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   keeping `X-Shopify-Hmac-Sha256: H` and body `B` unchanged.
3. In the gem, `Webhooks::Request#hmac` decodes the unchanged header, `#to_signable_string` returns the unchanged `B`, so `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: B, ...)`, even though Shopify never sent this event for `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
