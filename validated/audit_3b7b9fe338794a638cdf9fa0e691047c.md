### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the `shop` identity that the handler uses to attribute the webhook data to a tenant comes from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, which is **not** included in the signed bytes. This is the same class of bug as the GoldLink `isLiquidationFinished` report: a value that drives a security-relevant decision (there, market token identity; here, tenant/shop identity) is taken from a source disjoint from the value that was actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates the webhook via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only the raw body: [3](#0-2) 

But `shop` is read from an HTTP header that is never part of the signed material: [4](#0-3) 

That unauthenticated `shop` value is then passed straight into the handler as the tenant identifier: [5](#0-4) 

The identity binding that should hold is:
`shop-domain header used for tenant dispatch == shop bound inside the HMAC-verified bytes`

but the code instead verifies `HMAC(raw_body)` and separately trusts `headers["shop-domain"]` with no cryptographic link between the two — exactly the "field acted on but not covered by the HMAC" pattern called out as an admissible analog.

Because a single app's `api_secret_key` is shared across every shop that installs the app, any shop that receives a legitimate webhook (e.g., by triggering a test webhook delivery from its own Shopify admin) obtains a body + HMAC pair that is valid for that shared secret. That shop-domain owner can then replay the identical body/HMAC to the app's webhook endpoint while substituting a different `shop-domain` header value. `HmacValidator.validate` still returns `true` (it only checks the body), so `Registry.process` dispatches the (attacker-controlled) payload to the handler tagged with an arbitrary victim shop domain.

### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to enforce for webhook processing: a request can be made to appear as though it originated from a different merchant's shop than the one that actually holds a valid HMAC for the payload. If the hosting app uses `WebhookMetadata#shop` to look up/update per-shop records (a documented, expected usage pattern), an attacker who is a legitimate (but unprivileged w.r.t. other tenants) installer of the app can inject or overwrite data attributed to another shop — a cross-tenant access impact.

### Likelihood Explanation
Any shop that has installed the app can generate a validly-HMAC'd webhook body for itself (e.g. via Shopify's "send test notification" feature or simply waiting for a real event), then replay that body to the app's webhook URL with a forged `shop-domain` header. No secrets, TLS interception, or privileged access are required beyond being a normal installer of the target app — matching the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the verified body (e.g., look up the expected shop/secret pair server-side rather than trusting the header verbatim), so that `Utils::HmacValidator.validate` cannot succeed for a payload whose claimed shop differs from the shop the HMAC was actually computed for.

### Proof of Concept
1. App installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, sharing one `api_secret_key`.
2. Attacker controls `shop-a.myshopify.com` (a normal, unprivileged installer) and triggers/collects a real webhook: raw body `B` and header `shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`).
3. Attacker POSTs the same `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds a request object; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H`, so validation passes [6](#0-5) .
5. `Registry.process` dispatches to the handler with `shop: "shop-b.myshopify.com"` [5](#0-4) , causing the app to process attacker-supplied data under shop B's tenant context despite the payload only ever being validated for shop A.
