### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross‑tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with the webhook's `shop` field. In reality, the HMAC signature only covers the raw request body — it never binds the `X-Shopify-Shop-Domain` header that the handler trusts as the tenant identifier. Because the signature is computed solely from `(app_secret, raw_body)` with no shop-specific input, any attacker who legitimately obtains one valid `(body, hmac)` pair (e.g., by installing/uninstalling the app on their own store) can replay that exact pair against the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and the request will pass verification as if it were an authentic webhook for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers, independent of the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it to the received signature — no shop/topic binding is included: [3](#0-2) 

`Registry.process` uses this same validator, then passes the caller-supplied `request.shop` straight into `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The library's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" — implying it is trustworthy once `process` succeeds: [5](#0-4) [6](#0-5) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop authenticated by HMAC` ≠ `shop delivered to the handler as data.shop`

Since the signature is `HMAC(app_secret, raw_body)` with no shop component, the same valid `(raw_body, hmac)` pair is valid for *every* shop that uses the app. Many webhook topics have fixed, predictable, or attacker‑triggerable bodies (e.g., `app/uninstalled` typically has an empty/minimal JSON body). An attacker who controls any one shop that has the app installed can trigger such a webhook, capture the genuine `(body, hmac)` pair Shopify sends to their own endpoint, and then replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header set to an arbitrary victim shop. `Registry.process` will accept it as authentic and invoke the handler believing it is a real event for the victim tenant.

### Impact Explanation
This breaks the tenant boundary: an attacker with no relationship to (and no credentials for) the victim shop can make the app process arbitrary webhook topics attributed to that victim shop — including sensitive lifecycle events like `app/uninstalled`, `shop/redact`, or `customers/redact`, whose handlers typically wipe/deactivate the victim's stored session, delete data, or process GDPR redaction against the wrong tenant. This is a cross-tenant access/forgery vulnerability satisfying the Critical impact bucket (cross-tenant access) since the security boundary the app relies on (verified `shop` identity from `ShopifyAPI::Webhooks::Registry.process`) is not actually enforced by the gem.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on at least one store they control (a normal, unprivileged action for any Shopify user, including free development stores) and who can observe/trigger a webhook with a fixed or guessable body. No access to `api_secret_key`, tokens, or the victim's infrastructure is required — only the ability to send an HTTP POST to the app's public webhook endpoint with forged headers.

### Recommendation
Bind the shop identity into the verified material rather than trusting it from an unauthenticated header. Options:
- Include the `X-Shopify-Shop-Domain` (and ideally topic/webhook-id) in the string that is HMAC-verified, if Shopify's delivery format permits it (e.g., by including these headers, when present, in `to_signable_string`, or by additionally validating the shop against the value returned from a corroborating source such as the registered webhook endpoint's own subscription per shop).
- At minimum, update documentation to make clear that `Registry.process`'s verification only guarantees the body's integrity/origin, not the `shop` field's authenticity, so integrators know they must independently confirm the shop is one they have an active, corresponding session/install for before acting on webhook data.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com`.
2. Attacker uninstalls the app (or triggers any webhook topic with a fixed/predictable body, e.g. `app/uninstalled` with body `{}`), and captures the genuine request Shopify sends to the app's webhook endpoint, including the real `X-Shopify-Hmac-Sha256` header — this header is valid for that exact raw body against the app's `api_secret_key`, independent of shop.
3. Attacker replays this exact HTTP POST (same raw body, same `X-Shopify-Hmac-Sha256`) to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the secret — it never inspects the shop header.
5. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)` is passed to the app's handler, which performs the corresponding action (e.g., deactivate/delete the victim's stored session) as if it were an authentic event for `victim-shop.myshopify.com`.
