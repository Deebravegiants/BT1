### Title
Tron `IntentGatewayV2.onAccept` omits the relayer authentication gate present in the EVM `ExtrinsicIntents` implementation - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM intent gateway (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`, used by `IntentGatewayV2`) gates every incoming ISMP delivery behind a relayer allowlist check, `_checkRelayer(incoming.relayer)`, run before the request body is even decoded [1](#0-0) . The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical `onAccept` dispatch-by-`RequestKind` logic (RedeemEscrow/RefundEscrow/NewDeployment/UpdateParams/SweepDust) but never calls any relayer check — a `grep` for `_relayer`, `relayer()`, `checkRelayer`, or `setRelayer` across that file returns zero matches [2](#0-1) .

### Finding Description
The relayer allowlist was deliberately added to the intent gateway as a defense-in-depth control: per the project's own changelog, `onAccept` and `onGetResponse` deliveries are meant to be accepted "only from a single authorised relayer stored at `_relayer`", with the check running "before the message body is decoded, so escrow redemptions, refunds and every governance action, upgrades included, are covered" [3](#0-2) . The accompanying flow documentation explains why this matters: the relayer gate is the last line of defense if the underlying `EvmHost`/handler is ever compromised (e.g. via a forged consensus proof that swaps in a malicious handler reporting an arbitrary relayer address) — "a delivery from anyone but the authorised relayer never decodes the body, never runs `_authenticate`, and leaves no receipt" [4](#0-3) .

The Tron deployment target of `IntentGatewayV2` is structurally identical to the EVM contract — same `RequestKind` enum, same `authenticate()`-based source check for `RedeemEscrow`/`RefundEscrow`, same Hyperbridge-source check for `NewDeployment`/`UpdateParams`/`SweepDust` — but it is missing the `_checkRelayer` call entirely [5](#0-4) . This is exactly the bug class described in the external report: a generic/alternate creation-and-delivery path (here, the Tron port of the gateway) that omits an authentication boundary the primary/canonical path enforces for the same operation.

### Impact Explanation
Any message that reaches `onAccept` through `dispatchIncoming` (i.e., any relayer who submits a state proof to `HandlerV2`/host, restricted only to `onlyHost`) is processed on the Tron gateway without the relayer allowlist check that exists specifically to prevent an unauthorised or malicious relayer from exploiting a compromised handler/consensus path to move escrowed funds or governance state. Because `authenticate()` only checks that `request.source`/`request.from` matches the registered peer gateway address — not who relayed the message — the relayer-specific protection layer documented as covering "escrow redemptions, refunds and every governance action, upgrades included" is absent on Tron. This weakens the funds-custody and governance model for intents on that chain relative to the audited/hardened EVM path, directly matching "unbacked mint/unauthorized app action" impact categories for the intents escrow domain in scope.

### Likelihood Explanation
Reachability is high: `onAccept` is called by the host for every relayed, proof-verified request and is not further gated by an application-level relayer allowlist on Tron, whereas the equivalent EVM path was hardened specifically because relayer-level gating was judged necessary. Exploitation requires the same conditions the EVM gate was built to defend against (a compromised/forged proof or handler condition), so likelihood tracks the same threat model documented for the EVM gateway, but without the mitigating control on Tron.

### Recommendation
Port the `_relayer` state, `_checkRelayer` modifier/check, `setRelayer`, and the associated `RelayerUpdated` event/`onAccept`/`onGetResponse` gating from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol` so both deployment targets enforce an identical authentication boundary for incoming ISMP deliveries. Add a regression test (mirroring `evm/tests/foundry/IntentGatewayV2Test.sol`'s relayer-gate cases) confirming an unauthorised relayer delivery reverts on the Tron contract exactly as it does on the EVM contract.

### Proof of Concept
Not exploitable purely by code inspection without a forged/compromised proof; the concrete PoC path is: (1) an attacker obtains or forges a valid state proof / compromises the handler binding on the Tron deployment (the precondition the EVM relayer-gate was built to mitigate, per `how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md`), (2) submits a `RedeemEscrow`/`RefundEscrow`/governance-kind `PostRequest` through any relayer address to the Tron `IntentGatewayV2`, (3) `onAccept` on Tron processes it because there is no `_checkRelayer` gate to reject a non-whitelisted relayer, whereas the identical delivery would revert with `Unauthorized` on the EVM contract. I was not able to fully verify the Tron file's imports/inheritance chain (e.g., whether it shares `IntentsBase` with the EVM contract or is a fully standalone copy) due to index size limits on this codebase; a Devin session with full file access would be needed to confirm the exact diff and finalize the patch.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
            _instances[keccak256(body.stateMachineId)] = body.gateway;

            emit NewDeploymentAdded({stateMachineId: body.stateMachineId, gateway: body.gateway});
        } else if (kind == RequestKind.UpdateParams) {
            // Decode the body which includes optional destination-specific protocol fee updates
            ParamsUpdate memory update = abi.decode(incoming.request.body[1:], (ParamsUpdate));
            emit ParamsUpdated({previous: _params, current: update.params});
            _params = update.params;

            // Update destination-specific protocol fees if provided
            for (uint256 i; i < update.destinationFees.length;) {
                bytes32 stateMachineId = update.destinationFees[i].stateMachineId;
                uint256 feeBps = update.destinationFees[i].destinationFeeBps;
                _destinationProtocolFees[stateMachineId] = feeBps;

                unchecked {
                    ++i;
                }
                emit DestinationProtocolFeeUpdated(stateMachineId, feeBps);
            }
        } else if (kind == RequestKind.SweepDust) {
            SweepDust memory req = abi.decode(incoming.request.body[1:], (SweepDust));

            uint256 outputsLen = req.outputs.length;
            for (uint256 i; i < outputsLen;) {
                TokenInfo memory info = req.outputs[i];
                address token = address(uint160(uint256(info.token)));
                uint256 amount = info.amount;

                if (token == address(0)) {
                    (bool sent,) = req.beneficiary.call{value: amount}("");
                    if (!sent) revert InsufficientNativeToken();
                } else {
                    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
                    if (!success) revert TransferFailed();
                }
                unchecked {
                    ++i;
                }
                emit DustSwept(token, amount, req.beneficiary);
            }
        }
    }

# 2026-09-03 — Relayer allowlist on the intent gateway

The gateway now accepts `onAccept` and `onGetResponse` deliveries only from a single authorised
relayer stored at `_relayer` (slot 13, packed behind `_paused`). The check runs before the message
body is decoded, so escrow redemptions, refunds and every governance action, upgrades included, are
covered. A refused delivery reverts, which the host records as undelivered, so the authorised
relayer can submit the same message later. `setRelayer(address)` is callable by the immutable
`_owner` and by the host; the host branch exists so a governance `UpgradeContract` can carry the
call as its migration calldata and arm the relayer in the upgrade transaction (`upgradeToAndCall`
delegatecalls that calldata with the host still as `msg.sender`).
