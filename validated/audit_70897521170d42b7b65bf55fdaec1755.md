### Title
Webhook shop-domain header is not covered by HMAC, allowing tenant spoofing of processed webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop` (and `topic`/`api_version`) values are read straight from HTTP headers that are never included in the signed payload, so `Registry.process` accepts any shop-domain header as long as the body+HMAC pair is genuine, breaking the intended binding between "HMAC-verified sender" and "shop the event is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — no header data is folded into the signed string. `shop` is pulled directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC and then dispatches to the app's handler using `request.shop` as the trusted tenant identifier: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only checks `verifiable_query.to_signable_string` (i.e., the body) against the app's `client_secret`-derived HMAC, and never incorporates the shop header into the signed material: [4](#0-3) 

Because the webhook HMAC secret is the app's single `client_secret` shared across every shop that installs the app, any user of the app (including an attacker who installs the app on their own store) can obtain a genuine `(raw_body, hmac)` pair by receiving a real webhook (e.g. `customers/data_request`, `orders/create`) from their own shop. They can then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop that also has the app installed. `HmacValidator.validate` still passes (body and secret are genuine), and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, exactly as documented in `docs/usage/webhooks.md` lines 12-14 and 25-26 — the app is told the event legitimately concerns the victim's shop. This is the same class of bug as the reported issue: a field (`shop`) is acted upon by the trust boundary without being covered by the authenticity check (HMAC), analogous to `txData_[0]` being applied without going through the `_updateTxData` binding check.

### Impact Explanation
This is a cross-tenant identity-binding break: the app cannot distinguish which shop a processed webhook actually originates from beyond an attacker-controlled header. Depending on the topic registered, this enables cross-tenant data corruption/injection (e.g., forging `orders/create`/`products/update` events attributed to a victim shop with attacker-chosen body content) or forging mandatory compliance webhooks (`customers/redact`, `shop/redact`, `customers/data_request`) against a shop the attacker does not control — since these are explicitly built into the registry as `MANDATORY_TOPICS`. Any host app that trusts `WebhookMetadata.shop` as this gem instructs it to (per the gem's own documentation) inherits this cross-tenant spoofing, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (installing a public Shopify app is unauthenticated/self-service for any Shopify merchant) and can send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account of the victim is needed — only genuine webhook traffic addressed to the attacker's own shop, which every app installer receives by design.

### Recommendation
Include the shop-domain (and ideally topic/api_version) header values in the HMAC-signed payload check, e.g. by overriding `to_signable_string` to fold in the normalized header values that are consumed downstream, or by having `Registry.process`/`WebhookMetadata` treat the shop header as untrusted unless it is cross-checked against an out-of-band verified value (such as a shop stored per-webhook-id or validated via a session lookup). At minimum, document that `request.shop` is unauthenticated and must be independently verified by the host app before being trusted as a tenant boundary.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving a legitimate webhook delivery for a registered topic (e.g. `orders/create`) with body `raw_body` and header `X-Shopify-Hmac-Sha256: <valid hmac of raw_body under app's client_secret>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop that also installed the app).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches — validation passes despite the spoofed shop header. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"` even though Shopify never sent this event about that shop, and the app processes it (e.g. queues a job, mutates records, or fulfills a compliance redact request) under the wrong tenant.
