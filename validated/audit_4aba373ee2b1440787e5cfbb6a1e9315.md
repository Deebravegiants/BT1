## Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` value that the rest of the pipeline treats as the authenticated tenant identifier is taken from an unsigned HTTP header and is never included in the signed material. This breaks the intended binding: *"shop that produced a validly-signed payload" == "shop the handler is told the event came from."*

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e., only that `raw_body` matches the HMAC computed with the app's shared `api_secret_key` — and then immediately hands `request.shop` to the handler as the trusted tenant identifier: [3](#0-2) 

`HmacValidator.validate_signature` confirms this: it only compares `compute_signature(verifiable_query.to_signable_string, secret)` against the provided `hmac`, and `to_signable_string` for a webhook `Request` is just `@raw_body` — `shop` never enters the computation: [4](#0-3) 

Because the webhook HMAC secret (`Context.api_secret_key`) is the same for every shop that has installed the app, an unprivileged attacker who controls their own (legitimately installed) shop can:
1. Trigger a real webhook delivery to their own endpoint with attacker-chosen body content (many topics allow attacker-controlled fields — e.g. product/customer/order attributes, or GDPR `customers/redact` payloads containing chosen IDs).
2. Capture the `raw_body` and its valid `x-shopify-hmac-sha256` value (this HMAC is valid because it's signed with the shared app secret, not a shop-specific one).
3. Replay that exact `raw_body` + valid HMAC header to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain.

`Registry.process` will accept this as authentic — the HMAC check passes (body untouched) — and pass `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...)` to the app's handler as if the victim shop produced that event.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive: the gem asserts a shop identity to the host application's webhook handler without that identity being covered by the cryptographic proof. Host applications built on the documented API (`Registry.process`) reasonably trust `WebhookMetadata#shop` as authenticated, since it comes from a component whose stated purpose is HMAC verification of webhooks. Depending on how the host app uses `shop` (e.g., looking up the victim's session/access token to act on their store, processing a forged `app/uninstalled` or `customers/redact` event, or writing attacker data under the victim's identity), this can result in cross-tenant actions being taken against a shop the attacker does not control — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires an attacker to have installed the target app on any shop they control (an ordinary, unprivileged action app developers must support), plus the ability to send an HTTP POST to the app's public webhook endpoint with custom headers — no leaked credentials, access tokens, or `client_secret` needed. Capturing a valid raw_body/HMAC pair from one's own store's real webhook traffic is trivial.

### Recommendation
Include `shop` (and ideally `topic`) as part of the signed material verified for webhooks, or alternatively validate that the `shop` header value is a shop your application actually expects/has an active session for before trusting it in `WebhookMetadata`. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host application against its own shop/session registry before being used for any tenant-scoped action.

### Proof of Concept
```ruby
# Attacker owns install on attacker-shop.myshopify.com and receives a real,
# validly-signed webhook for their own store (e.g. products/update):
raw_body = '{"id":1,"title":"attacker-controlled-title"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body) # captured from real delivery

# Attacker replays it to the same endpoint, spoofing the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (only raw_body is checked); handler is invoked
#    with WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker_body)
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
