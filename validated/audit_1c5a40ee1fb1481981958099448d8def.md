### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identifier) is read from an HTTP header that is never included in the signed material. `Webhooks::Registry.process` verifies the HMAC and then dispatches the handler using this unauthenticated `shop` value, breaking the binding `hmac_verified(body) == shop_trusted_by_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against a signature computed from `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` trusts this validation, then builds `WebhookMetadata` directly from `request.shop` — the unauthenticated header — and hands it to the host application's handler as the tenant identity for the event: [4](#0-3) 

Because `shop` is never part of `to_signable_string`, the HMAC check passes for *any* `shop` header value as long as the body+hmac pair is valid for some shop. This is the exact analog of the report's bug class: "a field acted on but not covered by the HMAC" — here the acted-upon field is the tenant (`shop`), and the covered field is only the raw body.

### Impact Explanation
An unprivileged internet user who controls (or has legitimately installed the app on) their own store can capture a genuine, validly-signed webhook body+HMAC pair sent to their own endpoint by Shopify. They can then replay that exact request to the same endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` dispatches the event to the host app's handler tagged with the victim's shop. Any handler logic that uses `WebhookMetadata#shop` to look up sessions, write data, or take shop-scoped actions will now act under a falsified tenant identity — a cross-tenant confusion/access vulnerability.

### Likelihood Explanation
Exploitation requires only: (1) being (or briefly becoming) an installed merchant of the target app to receive one legitimate webhook, and (2) sending an HTTP request with a modified header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required, which fits the "unprivileged internet user" threat model.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the HMAC-covered material, or independently authenticate the `shop` header against Shopify's canonical value (e.g., by having Shopify's signature scheme cover headers, or by cross-checking the shop against a value bound to the specific webhook subscription/session rather than trusting the header verbatim).

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and receives a legitimate webhook:
raw_body = '{"id":123}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), API_SECRET, raw_body)

# Attacker replays the same body+hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Passes HMAC validation and invokes the handler with shop = "victim-shop.myshopify.com"
```
