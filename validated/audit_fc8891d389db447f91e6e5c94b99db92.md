### Title
Webhook shop-domain identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook confusion - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop`, `topic`, `webhook-id`, and `api-version` headers are never mixed into the signed material. This breaks the equality the app relies on: `shop_bound_by_hmac == shop_used_to_route_and_process_the_webhook`. A holder of one validly-signed `(body, hmac)` pair (e.g., a merchant on their own store, who legitimately receives Shopify webhooks signed with the app's shared `client_secret`) can replay that exact body+HMAC to the app's webhook endpoint while substituting a different value in the `shop-domain` header. The signature still validates because it never included the shop, so the handler is invoked with `shop: <victim-shop>` even though the payload was never signed for that shop — a cross-tenant confusion attack.

### Finding Description
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` is read straight from an unauthenticated header, with no relation to the signed body: [2](#0-1) 
- `HmacValidator.validate_signature` computes the signature strictly over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header, never touching `shop`: [3](#0-2) 
- `Registry.process` gates entirely on that body-only HMAC check, then immediately trusts `request.shop` (and `request.topic`/`request.webhook_id`) to build `WebhookMetadata` and dispatch to the app's handler: [4](#0-3) 

The binding the gem should enforce is: *the shop that receives the effects of the webhook must equal the shop for which the HMAC was computed*. Because the shop is carried in a header excluded from the signable string, that equality is never checked — only `hmac(body) == received_hmac` is checked, independent of which shop domain accompanies it.

### Impact Explanation
Any actor who can obtain one legitimately-signed `(raw_body, hmac)` pair for the shared app secret — trivially available to any merchant who installs the app on their own store and receives a single real webhook — can forge a webhook delivery for an arbitrary other shop by keeping the body/HMAC and swapping only the `shop-domain` header. `Registry.process` will accept it as valid and hand the attacker-chosen `shop` value plus the original body to the app's webhook handler as if it were an authentic webhook from that other shop. If the host application uses `WebhookMetadata#shop` to key persistence, trigger side effects, or scope data mutation (the intended and documented use of this field), this yields cross-tenant data corruption/injection — one merchant can inject fabricated webhook events attributed to another merchant's shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is meaningful but not universal: it requires the attacker to already have received at least one authentic webhook (trivial for any merchant using the same app) and requires the host application to trust `WebhookMetadata#shop` for tenant-scoped effects (the field is provided by the gem specifically for that purpose, so this is the expected/documented usage pattern, not a misuse of an undocumented API). No access token, `client_secret`, or privileged account is needed — only observing one's own genuine webhook traffic, which is inherent to operating a store with the app installed.

### Recommendation
Include the tenant-identifying fields (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the material that is cryptographically bound to the request, or otherwise cross-check the header-derived shop against an independently trusted source before dispatch. Since Shopify's wire format signs only the body, the gem should treat `request.shop` as unauthenticated input and document/enforce that consumers must not rely on it for tenant scoping without an additional binding (e.g., correlating against the webhook the app itself registered per shop, or requiring mutual TLS/allowlisted callback source). At minimum, `Registry.process` should refuse to trust `request.shop` for anything security-sensitive until it is bound into the signature.

### Proof of Concept
1. App has one shared `client_secret` used to validate all webhook HMACs (per `HmacValidator.validate`, using `Context.api_secret_key`). [5](#0-4) 
2. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and captures a real webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and finds it equals `H` — validation passes. [6](#0-5) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to process an attacker-controlled event as if it originated from the victim shop — despite the HMAC never having covered that shop identity.
