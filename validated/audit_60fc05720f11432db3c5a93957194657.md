Audit Report

## Title
LDAP Distinguished Name (DN) Injection via Filter-Only Escaping of User-Controlled Email in Login Bind - (File: core/sessions/ldapauth/ldap.go)

## Summary
`ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` build the LDAP bind DN by escaping the unauthenticated, user-supplied `email` with `ldap.EscapeFilter` (RFC 4515 filter escaping), then embed it via `fmt.Sprintf` into a DN string used directly as the bind DN in `conn.Bind`. `EscapeFilter` does not escape RFC 4514 DN metacharacters (notably comma), so an attacker-controlled email containing a comma is not neutralized before being interpreted as introducing additional RDN components in the DN structure.

## Finding Description
`sr.Email` reaches `CreateSession` unauthenticated and unvalidated for DN-safety: the HTTP handler `SessionsController.Create` binds JSON directly into `sr` and passes it straight to `AuthenticationProvider().CreateSession` with no email format check. In `CreateSession`, `escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))` followed by `searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())` is passed to `conn.Bind(searchBaseDN, sr.Password)`. The same pattern exists in `TestPassword`. `ldap.EscapeFilter` escapes only `\`, `*`, `(`, `)`, and NUL — characters relevant to LDAP search filter syntax — not the DN-reserved characters (`,`, `+`, `"`, `<`, `>`, `;`, leading `#`/space) that matter when a value is embedded as an RDN value in a DN string via plain string concatenation. This contrasts with `FindUser`'s correct use of `EscapeFilter` inside an actual filter expression (`filterQuery`), confirming the escaping function is contextually correct there but misapplied for DN construction in `CreateSession`/`TestPassword`.

## Impact Explanation
An attacker-controlled email containing a comma can alter the RDN sequence of the DN string passed to `conn.Bind`, since the comma is not neutralized. This is a legitimate escaping-context defect (CWE-116) reachable via the unauthenticated login/test-password paths, and can at minimum produce malformed bind requests or altered DN targeting, and depending on the specific LDAP directory's parsing behavior for malformed DNs, could affect bind resolution behavior. This maps to the node's authentication logic being subject to unauthenticated input-driven bind-target manipulation — an in-scope authentication-integrity concern for the login flow.

## Likelihood Explanation
The vulnerable code is directly reachable by any unauthenticated caller submitting a `POST /sessions` request with an `email` field containing DN metacharacters; no credential, privilege, or session state is required to reach the flawed escaping logic.

## Recommendation
Use RFC 4514 DN escaping (or an equivalent library function) when constructing DN strings from user-controlled input, instead of `ldap.EscapeFilter`. Alternatively, validate/reject emails containing DN-reserved characters before using them to build a bind DN, and prefer DN-composition APIs that build RDNs structurally rather than through string formatting.

## Proof of Concept
1. Send `POST /sessions` with body `{"email":"attacker,ou=admins,dc=example,dc=com","password":"anything"}`.
2. `ldap.EscapeFilter` leaves the comma unescaped since it's not a filter-reserved character.
3. `searchBaseDN` becomes `uid=attacker,ou=admins,dc=example,dc=com,<UsersDN>,<BaseDN>` — a DN whose RDN sequence has been altered by attacker input rather than treating the whole string as a single RDN value.
4. `conn.Bind(searchBaseDN, sr.Password)` is issued against this attacker-influenced DN, deviating from the intended `uid=<email>,<UsersDN>,<BaseDN>` structure. A Go unit test mocking `LDAPConn.Bind` to capture and assert the DN argument passed for such an email input would confirm the injected structure, matching the existing test patterns in `core/sessions/ldapauth/ldap_test.go` (e.g., `TestORM_CreateSession_UpstreamBind`).
