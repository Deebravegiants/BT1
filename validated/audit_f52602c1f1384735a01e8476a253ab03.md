### Title
Webhook `shop` identity is not bound to the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies the HMAC exclusively against that raw body [4](#0-3) [5](#0-4) . Meanwhile `Registry.process` trusts `request.shop`, sourced from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, as the tenant identity handed to the app's webhook handler [3](#0-2) . Because the shop header is never part of the signed material, the byte range that is HMAC-verified (body only) does not equal the byte range that determines the tenant (body + shop header).

### Finding Description
`Request#shop` reads directly from the `shopify-shop-domain` header without any cryptographic binding to the HMAC signature: [6](#0-5) . The signable string used for HMAC verification is only the raw JSON body: [4](#0-3) . `HmacValidator.validate_signature` computes the HMAC over that body-only string and compares it with the received signature [2](#0-1) . `Registry.process` gates on this HMAC check but then forwards `request.shop` unmodified to `WebhookMetadata`, which the host application's handler uses to identify which merchant/tenant the payload belongs to [3](#0-2) , and the gem's own documentation instructs handlers to key off `data.shop` [7](#0-6) .

Equality that should hold but doesn't: `shop_bound_by_HMAC == shop_used_by_handler`. In this gem, `shop_bound_by_HMAC` is undefined (empty set — the HMAC signable string never contains the shop domain), while `shop_used_by_handler = header["x-shopify-shop-domain"]`, an attacker-controllable field once any valid `(body, HMAC)` pair for the app's shared `client_secret` is obtainable (e.g., from the attacker's own shop, which is a legitimate merchant that installed the same app). Replaying that same body+HMAC pair with a different `shop-domain` header value passes `HmacValidator.validate` unchanged (it never looks at the header) and causes the handler to process/act on data as if it came from an arbitrary victim shop.

### Impact Explanation
This breaks the tenant identity binding for webhook delivery: an attacker who controls one legitimate installation of the app (their own shop) can generate arbitrarily-timed, validly-HMAC'd webhook bodies for topics they can trigger (e.g., `orders/create`, `app/uninstalled`), then replay the request to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop's domain. Since the library's HMAC validation passes, the host application (following the gem's documented API, which supplies only `data.shop` without a way to check it against the payload's provenance) is very likely to process this as authoritative data for the victim shop, leading to cross-tenant data corruption or unauthorized actions attributed to another merchant.

### Likelihood Explanation
An attacker only needs a legitimate app installation on their own store (any developer/merchant can install a public app or use a partner test store) to produce a validly-signed webhook body, then can freely rewrite HTTP headers (which are not part of the signed material) when replaying the request to the endpoint. No access to `client_secret`, tokens, or the victim's credentials is required — only the ability to trigger a webhook event on one's own shop and control raw HTTP headers when forwarding it.

### Recommendation
Include the shop domain (and ideally topic/webhook id) header values in the HMAC signable payload, e.g., have `to_signable_string` incorporate `shopify_header("shop-domain")` alongside `@raw_body`, and require server implementations to verify the header set was covered by the signature before trusting `request.shop`. Alternatively, document and enforce that the `shop` field returned by `Request` must be cross-checked by the host app against a known/installed-shop list before being trusted, and ensure `HmacValidator` cannot be satisfied unless the shop-identifying header matches what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the shared `client_secret`).
2. Attacker crafts a new HTTP request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/acts on `B` as though it originated from the victim's store [8](#0-7) .
