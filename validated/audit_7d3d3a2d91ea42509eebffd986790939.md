### Title
Webhook `shop-domain` header trusted as tenant identity without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and passed downstream as the trusted tenant identifier for the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC via `HmacValidator.validate(request)`, which only checks `to_signable_string` (i.e., body) against the computed signature — it never verifies that `shop` is bound to that signature — and then immediately builds a `WebhookMetadata` object using `request.shop` as the tenant identity handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm the check is purely over `to_signable_string` (body), with no shop binding: [4](#0-3) 

`WebhookMetadata.shop` is the field host apps are expected to use to key their per-tenant business logic (e.g., "which merchant does this event belong to"): [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" class from the report: the equality the code implicitly assumes is `shop (verified by HMAC) == shop (used for tenant routing)`, but in reality only the raw body is HMAC-covered — `shop` is not. An attacker who owns any legitimate Shopify store can trigger a webhook delivery to their own registered endpoint, capture a genuine `(raw_body, hmac)` pair from Shopify (valid under the app's `client_secret`), then replay that exact body+HMAC to the target app's webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header for a different (victim) shop. Because `to_signable_string` never includes `shop`, the forged request still passes `HmacValidator.validate`, and `Registry.process` will hand the app's handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: `shop` is delivered to app code as an authenticated fact, when it is not authenticated at all. Any app that uses `WebhookMetadata#shop` to select the tenant record to mutate (order updates, app-uninstalled cleanup, GDPR/compliance actions, billing state, access revocation, etc.) can be tricked into acting on the wrong merchant's data using an attacker-controlled shop value, which is a cross-tenant access primitive.

### Likelihood Explanation
Exploitation requires only an internet-reachable attacker who controls at least one Shopify store (to obtain a genuine body+HMAC pair) and the ability to send arbitrary HTTP requests to the target app's public webhook endpoint with custom headers — no access token, secret, or privileged account is required. The main practical constraint is finding webhook topics whose body content is static/predictable or attacker-influenced enough to reuse across shops (e.g., topics with minimal or templated payloads), which is a likelihood-reducing but not likelihood-eliminating factor.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the header-derived shop to the verified payload before handing it to `WebhookHandler#handle`. At minimum, document/require that consuming apps must independently confirm the `shop` matches shop-webhook registration state (e.g., look up by `webhook_id` against Shopify, not trust the header), since the gem currently offers no protection here and silently presents an unauthenticated header value as verified data.

### Proof of Concept
1. Attacker registers/owns Shopify store `attacker.myshopify.com` and installs the target app, receiving a genuine webhook delivery for some topic with a static/predictable body, e.g.:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`
   - Body: `{}` (or another template body identical across shops for that topic)
2. Attacker replays the identical raw body and HMAC header to the same app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` succeeds because it only checks the (unchanged) body against the HMAC: [6](#0-5) 
4. `Registry.process` invokes `handler.handle` with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the app performs tenant-scoped actions (e.g., uninstall cleanup, data deletion, cache invalidation) against `victim-shop` even though the request was never authenticated for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
