### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` header value taken from the same request to identify which merchant/tenant the payload belongs to. Because the `shop` value is never included in the signed content, and the app's `client_secret` (the HMAC key) is identical for every shop that has the app installed, a valid `(body, hmac)` pair obtained from any one tenant can be replayed against the app with an arbitrary `X-Shopify-Shop-Domain` header, and it will still pass verification.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body — none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are part of the signed content: [2](#0-1) 

`request.shop` is read straight from the (unsigned) header: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then forwards `request.shop` unchecked as the tenant identifier passed to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `HMAC_valid(body, secret) == true` is treated as proof that `shop header == originating tenant`, but the equality that actually holds is only `HMAC_valid(body, secret)`, independent of `shop`. Since `secret` (the app's `client_secret`) is shared across every shop that installs the app, any shop that legitimately receives a Shopify webhook (i.e., any attacker who installs the target app on their own store) obtains a `(body, hmac)` pair that is valid for that secret regardless of which shop is named in the accompanying header. That pair can then be POSTed to the same webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to any victim shop domain, and `Utils::HmacValidator.validate` will still return `true`.

### Impact Explanation
`WebhookMetadata.shop` (populated from the forged header) is the value host applications are documented to use to look up/act on a specific merchant's records: [5](#0-4) 
An attacker who is a legitimate (unprivileged, relative to the victim) merchant on the same app can therefore inject attacker-controlled webhook payloads that the app processes as belonging to a different, victim tenant — a cross-tenant data-integrity/impersonation issue. Depending on how the host application uses `shop` (e.g., updating order/product/customer records keyed by shop, triggering redaction, syncing data), this can result in cross-tenant data corruption or disclosure attributed to the wrong merchant, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to have (or create) a shop with the target app installed so they can capture at least one legitimately Shopify-signed webhook body/HMAC pair for that app's shared `client_secret` (trivial — any developer can install any public app on a free development/partner store), then replay it with a different `shop` header. No access to the app's `client_secret`, access tokens, or victim credentials is required — only the ability to receive one webhook and modify one HTTP header on replay, both purely "unprivileged internet user" actions.

### Recommendation
Bind the shop (and ideally topic) into the authenticated content, or at minimum have `Registry.process`/the host app cross-check `request.shop` against the shop for which the webhook was registered/expected before dispatching to a handler. Concretely:
- Include `shop-domain` in `Webhooks::Request#to_signable_string` if compatible with Shopify's signing scheme, or
- Require callers of `Registry.process` to supply the expected shop and raise `Errors::InvalidWebhookError` if it doesn't match `request.shop`, closing the gap where the identity used for authorization is not the identity that was authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's endpoint; the attacker captures the raw body `B` and header `X-Shopify-Hmac-Sha256: H`, both valid under the app's shared `client_secret`.
2. Attacker crafts a new HTTP POST to the same webhook endpoint with the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic` to a topic of choice.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers (`lib/shopify_api/webhooks/request.rb` L45-63); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `B` against `H` (`lib/shopify_api/webhooks/request.rb` L35-38, `lib/shopify_api/utils/hmac_validator.rb` L12-22).
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb` L198-199), causing the host application to process attacker-controlled data under the victim shop's identity.
