## Title
Open-redirect-style authentication bypass via default-to-self peer fallback in `IntentGatewayV2.instance()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` authenticates incoming cross-chain messages by comparing the sender module address against `instance(request.source)`. Unlike the canonical EVM `IntentGatewayV2`/`IntentsBase`, whose `_instance()` reverts with `UnknownInstance()` when a source chain has no registered peer [1](#0-0) , the Tron variant's `instance()` silently falls back to `address(this)` for any unregistered `stateMachineId` [2](#0-1) . This is the same bug class as the GHSA-xm3x-4ph3-3x9c open-redirect: an "exact match" check (registered peer == sender) is replaced by a loose default that accepts an unintended value (the contract's own address) whenever the real target isn't configured.

### Finding Description
`authenticate()` gates `RedeemEscrow`/`RefundEscrow` message handling: [3](#0-2) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

Because `IntentGatewayV2` is deployed via CREATE2 so that "peer bound to address(this)" holds identically across chains (see the initialization test asserting `gateway.instance(bytes("SOURCE_CHAIN")), address(gateway)` [4](#0-3) ), the deployment address is a known, low-entropy, reproducible value. Any `request.source` state machine that the gateway operator has never called `NewDeployment` for (i.e., not present in `_instances`) is authenticated against `address(this)` instead of being rejected. An attacker who can dispatch a genuine ISMP POST request from *any* Hyperbridge-connected but unpeered state machine (e.g., an EVM chain Hyperbridge already supports but this gateway hasn't been deployed/registered on), with `from` set to a contract they deploy at the same CREATE2 address as this Tron gateway, will pass `authenticate()`.

`onAccept()` then calls `withdraw()` on attacker-supplied `WithdrawalRequest` data for `RedeemEscrow`/`RefundEscrow`, transferring the escrowed order tokens to an attacker-chosen `body.beneficiary`: [5](#0-4) [6](#0-5) 

### Impact Explanation
This permits an unprivileged actor to forge a "known instance" message and drain any existing order's escrowed input tokens (`_orders[commitment][token]`) by fabricating a `RedeemEscrow`/`RefundEscrow` request from an unregistered/unpeered source chain, matching only the CREATE2 self-address rather than a real peer gateway. This is a direct theft-of-funds path reachable from a single relayed cross-chain message, matching the "concrete theft ... of funds" bar.

### Likelihood Explanation
Exploitability depends on the attacker being able to (a) find or deploy a contract at the gateway's own CREATE2 address on some chain Hyperbridge already routes for but that this particular gateway instance has not registered a peer on, and (b) dispatch a real POST request from that chain with `from` = that address. Since `IntentGatewayV2` intentionally standardizes on identical addresses via CREATE2 across all deployments, and Hyperbridge already routes many chains it isn't deployed on, this is a realistic, low-cost attack path, materially weaker than the exact peer-registry check used by the EVM sibling contract.

### Recommendation
Change `instance()` (and `authenticate()`) in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g., `UnknownInstance`) when no explicit peer is registered for `stateMachineId`, mirroring `IntentsBase._instance()` in the EVM codebase, rather than defaulting to `address(this)`.

### Proof of Concept
1. Attacker identifies/deploys a contract at the same address as the target Tron `IntentGatewayV2` proxy on any EVM chain Hyperbridge supports but for which this gateway has no `NewDeployment` entry in `_instances`.
2. From that contract, dispatch a POST request to the Tron gateway with body `bytes1(RequestKind.RedeemEscrow) + abi.encode(WithdrawalRequest({commitment: <existing order commitment>, tokens: <order tokens>, beneficiary: <attacker>}))`.
3. On delivery, `authenticate()` calls `instance(request.source)`, finds no registered peer, returns `address(this)`, which equals `request.from` — authentication passes.
4. `onAccept` → `withdraw()` transfers the escrowed tokens to the attacker's `beneficiary`.
