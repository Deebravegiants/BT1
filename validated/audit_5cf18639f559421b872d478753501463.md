### Title
Rebasing ERC20 rewards accrue to the Hinkal pool and are permanently frozen, unclaimable by any depositor - ([File: contracts/Hinkal.sol])

### Summary
Hinkal tracks each user's shielded balance as a fixed `amount` inside a UTXO/commitment that is set once at deposit time and never re-derived from the token's live `balanceOf`. If a rebasing ERC20 (e.g. an aToken-style token whose `balanceOf()` grows for every holder over time) is used as a pool token, the rebase rewards accrue to the Hinkal contract's on-chain balance but are never reflected in any UTXO, and can never be withdrawn by depositors, the relay, or the protocol.

### Finding Description
Deposits and withdrawals in `transact()` are settled through an exact balance-diff equality check: [1](#0-0) 

`oldBalances`/`newBalances` are read from the live token via `getBalancesForArray` → `getERC20OrETHBalance` (i.e. `balanceOf(address(this))`): [2](#0-1) 

The check only constrains the *intra-transaction* delta: `balanceDif == amountChanges[i] + utxoAmount`. Any balance the contract already holds before the transaction (including rebase interest that accrued between transactions) is simply folded into `oldBalances` and is never associated with any commitment, nullifier, or public input. Withdrawals in `_internalTransact` only ever move the fixed `amountChanges[i]` (i.e. `sumAbs`) that the prover committed to when the UTXO was created — not the token's current, rebased balance: [3](#0-2) 

The same fixed-amount-at-creation pattern applies to blocked UTXOs created via `DepositOnChainUtxosExternalAction`, where `tokenTotal` transferred in equals the sum of UTXO amounts recorded, with no live-balance reconciliation: [4](#0-3) 

Because every UTXO amount is fixed at creation and the strict equality in `transact()` only reconciles the delta caused by the current call, any rebase growth of the underlying token balance sits permanently in the Hinkal contract with no code path (no admin sweep, no pro-rata claim mechanism, no UTXO re-issuance) that lets depositors, the relay, or anyone else claim it. This is the same failure mode described in the referenced Cally finding: reward value accrues to the vault/pool but is structurally unreachable by any withdrawal path because withdrawal amounts are pinned to values fixed at deposit time rather than derived from the live, rebased balance.

### Impact Explanation
This is a permanent freezing of user funds: rebase rewards that economically belong pro-rata to the depositors of that ERC20 are locked in the `Hinkal` contract forever, with no mechanism in `Hinkal.sol`, `HinkalHelper.sol`, `Transferer.sol`, or the on-chain-UTXO external actions to distribute or reclaim them. This matches the "permanent freezing of user funds" High-severity category.

### Likelihood Explanation
No malicious action or privileged key is required — this occurs any time a rebasing ERC20 is used as a pool token and normal deposit/withdrawal activity happens over time, exactly mirroring the passive, code-inspection-identified nature of the original Cally finding. Likelihood is tied entirely to whether such a token is added as a supported `erc20TokenAddresses` entry; nothing in `Hinkal.sol`/`HinkalHelper.sol` restricts the token address space to non-rebasing tokens.

### Recommendation
Either explicitly disallow rebasing/interest-bearing tokens as supported pool tokens, or add an accounting mechanism (e.g. track a global "shares to underlying" index per token, or a sweep function that distributes/redistributes any excess `balanceOf(this)` over the sum of outstanding committed UTXO amounts) so that any rebase growth can be attributed to and claimed by depositors rather than being permanently stranded.

### Proof of Concept
1. Protocol adds an aToken-style rebasing ERC20 `R` to `circomData.erc20TokenAddresses` for deposits/withdrawals through `transact()`.
2. User A deposits `1000 R` via `_internalTransact` (contracts/Hinkal.sol:172-187); a UTXO/commitment is created encoding `amount = 1000`.
3. Time passes; `R.balanceOf(address(Hinkal))` rebases up to `1050` (the extra `50` belongs pro-rata to depositors of `R`, as with any rebasing token).
4. User A later withdraws by spending their nullifier; `_internalTransact` transfers exactly `1000` (the fixed committed `amountChanges[i]`), not `1050` (contracts/Hinkal.sol:188-224). The `transact()` balance equality (contracts/Hinkal.sol:134-146) is satisfied because it only checks the delta of *this* transaction (`-1000`), independent of the pre-existing extra `50` sitting in `oldBalances`.
5. The `50 R` of rebase interest remains in the `Hinkal` contract indefinitely. No UTXO, nullifier, or admin function exists to claim it — it is permanently frozen.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }
