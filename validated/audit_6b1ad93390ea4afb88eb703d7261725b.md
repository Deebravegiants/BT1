## Title
Unprotected Uniswap V2 spot-price swap in `EvmHost.dispatch()` permanently strands user-supplied native token as "dust" instead of refunding it, and the amount lost is attacker-controllable via spot-price manipulation - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` let any unprivileged caller pay the relayer fee in native token. The host swaps the supplied `msg.value` for an exact amount of `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, priced entirely off the router's live reserves (spot price), with no TWAP, oracle bound, or slippage cap other than `msg.value` itself. Any native token sent above the amount the swap actually consumes is refunded by the router to `msg.sender`, but `msg.sender` in that inner call is `EvmHost` itself, not the original dispatcher. The refund is explicitly designed to accumulate in the host (`receive() external payable {}` is commented as collecting "dust"), so it is never returned to the paying application. Because the swap price is a manipulable AMM spot price, an attacker can move the pool at the moment of a victim's dispatch to widen the gap between the fair value and the exact `post.fee`/`get.fee` output amount, maximizing the ETH silently retained by the host at the paying application's expense — the same class of unprotected-spot-price-as-value-source flaw that underlies the Moola Market price-manipulation incident, here manifesting as loss/freezing of dispatcher funds rather than direct oracle-driven overborrowing.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 

```
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
```

The identical pattern exists in the GET-request dispatcher: [2](#0-1) 

`swapETHForExactTokens` computes the required `amountIn` purely from the pool's current reserves (a spot price with zero manipulation resistance), reverting only if `amountIn > msg.value`. Any leftover ETH (`msg.value - amountIn`) is refunded by the Uniswap router to its caller — `EvmHost` — not to `_msgSender()`, the address that actually supplied the value. The contract's own comment confirms this is treated as intentional revenue collection rather than a bug to fix: [3](#0-2) 

```
/*
 * @dev receive function for UniswapV2Router02, collects all dust native tokens.
 */
receive() external payable {}
```

Because applications cannot predict the exact `amountIn` a spot-priced AMM will require at execution time, every integrator is forced to send `msg.value` with a safety margin. The SDK itself demonstrates this necessity, quoting via the same unprotected mechanism and then padding the result: [4](#0-3) 

```
const { result } = await this.source.client.simulateContract({
    ...
    functionName: "quote",
    ...
});
totalNativeCost = ((result as bigint) * 101n) / 100n // 1% buffer
```

`HyperApp.quote()` sources this estimate from the same manipulable spot price: [5](#0-4) 

Any buffer smaller than the price impact an attacker can inflict on the pool (trivial on thin `WETH/feeToken` pools, which is exactly the kind of pool `EvmHost` is configured with) either (a) causes the dispatch to revert — a route temporarily unable to deliver messages — or (b) causes the swap to consume less ETH than the buffered `msg.value`, with the surplus permanently retained by `EvmHost` as "dust" rather than returned to the paying application. An attacker who can move the pool immediately before a victim's `dispatch()` call (front-run/sandwich or flash-loan-funded swap) directly controls how much of the victim's buffer is converted into un-refundable host revenue, extracting value from the dispatching application without its consent — root-caused by treating an unprotected AMM spot price as an authoritative fee-conversion source, precisely the bug class flagged by the Moola Market report.

### Impact Explanation
Every unprivileged application or user that pays Hyperbridge dispatch fees in native token is exposed. Legitimate integrators must always over-provision `msg.value` to avoid reverts against price drift; that over-provisioned amount is not the dispatcher's to reclaim — it is unconditionally absorbed by `EvmHost` due to the refund-to-self design. An attacker who manipulates the underlying Uniswap V2 pool at the moment of dispatch maximizes this loss precisely and repeatedly across every native-fee dispatch on a chain, and can independently grief dispatches into reverting by pushing price the other way, degrading Hyperbridge's ability to deliver messages from that chain. This satisfies the "permanent freezing of funds" and "route unable to deliver messages" impact criteria via a single unprivileged dispatch transaction interacting with `EvmHost` dispatch/delivery, which is squarely in scope.

### Likelihood Explanation
`dispatch()` is a permissionless, unauthenticated entry point invoked by any contract or EOA paying with native token — no special privileges are required. Manipulating a Uniswap V2 pool's spot price with a flash loan or simple sandwich is a well-established, low-cost technique, especially against the thin `WETH/feeToken` pools that back Hyperbridge's fee token on most chains. The absence of any oracle sanity check, TWAP, or minimum-refund-to-sender logic means exploitation requires no protocol bug beyond normal, expected usage of `dispatch()` with a native-token payment.

### Recommendation
- Track the actual `_msgSender()` of `dispatch()` (not the swap's internal caller) and refund any `msg.value - amountIn` surplus directly to that sender instead of silently retaining it in `EvmHost`.
- Bound the acceptable swap price against a TWAP or external price reference (e.g., a Chainlink feed similar to `SimplexPaymaster`'s `_getOraclePrice`) and revert if spot price deviates beyond a configured tolerance, preventing single-block manipulation from being economically meaningful.
- Consider allowing callers to supply an explicit `amountInMax` distinct from `msg.value`, so slippage bounds are set intentionally by the caller rather than being an accidental byproduct of the buffer needed to avoid reverts.

### Proof of Concept
1. Attacker identifies a target chain's `EvmHost` and its configured `uniswapV2Router`/`WETH`/`feeToken` pool (`_hostParams.uniswapV2`, `feeToken()`), typically a low-liquidity pool.
2. Attacker observes a pending `dispatch(DispatchPost)` (or `DispatchGet`) call from a victim application supplying `msg.value` with the standard SDK 1% buffer over the quoted `getAmountsIn(post.fee, [WETH, feeToken])` result (see `HyperApp.quote()` and the SDK's `1% buffer` in `hyperFungibleToken.ts`).
3. Attacker front-runs with a swap that shifts the pool's `WETH/feeToken` ratio such that `getAmountsIn(post.fee, path)` at execution time returns a value meaningfully lower than the victim's buffered `msg.value` (achievable when the manipulated price swing exceeds 1%, trivial for thin pools).
4. Victim's `dispatch()` call executes: `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` consumes only the reduced `amountIn`; the router refunds `msg.value - amountIn` to `EvmHost` (`msg.sender` from the router's perspective), which is retained permanently as "dust" per the contract's own `receive()` comment, and is never returned to the victim.
5. Attacker reverses their initial swap (or simply lets arbitrageurs restore the price), recovering their capital while the victim's overpaid ETH remains stuck in `EvmHost`, recoverable only through cross-chain-governance-restricted `withdraw()` — never back to the victim.
