### Title
Emporium `CASE-2` stateless op performs an unconstrained arbitrary external call that, combined with `erc20TokenAddresses=[]` (Min-circuit path), drains stranded ERC20 balances with zero nullifier/commitment bookkeeping - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `stack.signerAddress == address(0)`, `verifyWallet` skips all signature verification and only marks `emporiumMessage` as used, so any unprivileged caller can supply arbitrary `op.endpoint`/`op.callData` for a "Stateless Interaction" (`CASE 2`), executed as `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own address/balance. Because the attacker also controls `circomData.erc20TokenAddresses` and sets it to `[]` to route to the Min circuit, both `runAction`'s balance-diff loop and `Hinkal.transact`'s balance-conservation loop never execute, so the stolen value is transferred with no `BalanceChangeShouldBePositive` check, no UTXO/commitment creation, and no nullifier insertion.

### Finding Description
Broken equality: "every ERC20 value that leaves the protocol contracts must correspond to exactly one inserted leaf/nullifier pair validated by the circuit's public inputs" — here value leaves Emporium via a raw external call with **no** corresponding leaf or nullifier at all.

Path:
1. `verifyWallet` in `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:302-316` returns immediately (skipping the entire EIP-712 signature check) whenever `stack.signerAddress == address(0)`, only enforcing `usedMessages[circomData.emporiumMessage]`. [1](#0-0) 
2. `CASE 2` then executes `op.endpoint.call{value: op.value}(op.callData)` with attacker-chosen `endpoint`/`callData`, forbidding only the `callHinkalWallet`/`doSendToRelay` selectors — any other call (e.g. `IERC20.transfer(attacker, amount)` on a token Emporium holds) succeeds. [2](#0-1) 
3. The circuit selected for this call, `MainEVMCircuitMin`, only constrains `message === Poseidon(messageSeed)` — it never references `op.endpoint`, `op.callData`, `op.value`, or any amount. [3](#0-2) 
4. Because `circomData.erc20TokenAddresses.length == 0` (required to route to `formInputEmporiumMin`), `runAction`'s post-call loop that computes `balanceChange`, reverts on negative balance change, and mints an outgoing UTXO never executes. [4](#0-3) [5](#0-4) 
5. `runAction` therefore returns an empty `utxoSet`, and in `Hinkal.transact`, the balance-conservation loop that would create `OnChainCommitment`s and enforce `balanceDif == amountChanges + utxoAmount` also never runs (loop bound is `circomData.erc20TokenAddresses.length == 0`). [6](#0-5) 
6. `insertNullifiers`/`insertCommitments` are then called with effectively empty/zero data for this action, so no leaf or nullifier tracks the value that left the contract. [7](#0-6) 

Attacker call: `transact(a,b,c,dimensions, circomData)` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `externalActionMetadata` ABI-encoding `EmporiumStack{signerAddress: address(0), ops: [{endpoint: strandedToken, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount)}]}`, and a fresh `emporiumMessage` each time (only requirement is `usedMessages[emporiumMessage] == false`, checked in `verifyWallet`). Existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`) never inspect `op.endpoint`/`op.callData` content or bind it to any amount, so none of them stop this.

### Impact Explanation
Direct theft of ERC20/ETH value held by the Emporium contract (protocol/victim-stranded funds) with zero corresponding Merkle leaf or nullifier — a full bypass of the single-spend/tree-truth invariant. This is repeatable per fresh `emporiumMessage` until the stranded balance is fully drained. Matches Critical: direct theft of user/protocol funds with proof/nullifier-verification bypass.

### Likelihood Explanation
Requires only: (a) the stated precondition that some ERC20 balance is sitting on the Emporium contract, (b) the attacker's own trivially self-satisfiable Min-circuit proof (`messageSeed` chosen freely), and (c) crafting `EmporiumStack` with `signerAddress = address(0)`. No privileged role, victim key, or relay cooperation is needed — fully within the unprivileged attacker capability set. Cost is normal gas per `transact()` call, fully repeatable.

### Recommendation
- Do not allow `CASE 2` (`signerAddress == address(0)`, unsigned) stateless calls to arbitrary `endpoint`/`callData`; restrict endpoints to an explicit allowlist, or require every op affecting token balances to be authenticated (mandatory signature) regardless of `erc20TokenAddresses` length.
- Make the on-chain balance-diff/UTXO-creation loop in `runAction` and the balance-conservation loop in `Hinkal.transact` independent of `circomData.erc20TokenAddresses` being non-empty — track and validate balance deltas for every token actually touched by the ops, not only attacker-declared tokens.
- Bind `op.endpoint`, `op.callData`, and `op.value` (or a hash of them) as real circuit constraints instead of leaving them entirely off-circuit.

### Proof of Concept
Foundry test:
1. Deploy the full Hinkal/HinkalHelper/EmporiumUpgradeable stack with real verifiers; register `mainEVMCircuitMin0v4` verifier for the Min dimension/`HINKAL_EMPORIUM_ACTION_ID`.
2. Simulate the stranded-balance precondition by minting `strandedAmount` of a test ERC20 directly to the `EmporiumUpgradeable` proxy address.
3. As an unprivileged attacker EOA, locally generate a valid Min-circuit proof for `messageSeed = arbitrary`, `calldataHash` matching a `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` encoding `EmporiumStack{signerAddress: address(0), ops:[{endpoint: token, invokeWallet:false, value:0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount)}]}`, fresh `emporiumMessage`.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
5. Assert: `token.balanceOf(attacker)` increased by `strandedAmount`; `token.balanceOf(address(emporium))` decreased by `strandedAmount`; Hinkal's Merkle root (`getRoot()`/latest root index) is unchanged before/after; `nullifiers[...]` mapping has no new entries; no `NewCommitment`/`Nullified` events emitted for this call.
6. Repeat with a new `emporiumMessage` to show the drain is chainable across multiple `transact()` calls until the Emporium balance is fully exhausted, while tree/nullifier state never changes.
