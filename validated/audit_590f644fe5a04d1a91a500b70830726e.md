### Title
Webhook shop identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` identity from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature it verifies via `Utils::HmacValidator` only covers the raw request body, never the shop-domain header. This breaks the intended binding: `shop_used_by_handler == shop_covered_by_hmac`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from an attacker-controlled HTTP header with no cryptographic coverage [2](#0-1) .

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` and compares it to the `hmac` field [3](#0-2) . Since `to_signable_string` is just the raw body, the header-derived `shop` value is never part of what's authenticated.

`Registry.process` validates only the HMAC and then forwards `request.shop` directly into `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` as the trusted tenant identifier [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field with no independent verification [5](#0-4) .

Because the app's `client_secret` (used for HMAC) is the same for every shop that installs the app, a merchant who owns "shop A" and has the app installed will legitimately receive real Shopify webhooks with a valid HMAC over some JSON body B. That HMAC only proves "this body B was signed by Shopify with our app secret" — it proves nothing about which shop the body belongs to. An attacker who controls shop A can capture one of these genuine `(body, hmac)` pairs and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (body/hmac untouched), `Registry.process` accepts the request, and the handler receives `WebhookMetadata` claiming the body originated from the victim shop.

### Impact Explanation
This lets an unprivileged attacker (any merchant who has installed the app, with zero access to `api_secret_key` or any access token) forge webhook events attributed to a different tenant. Depending on how the host app's webhook handlers act on `data.shop` (e.g., writing to per-shop records, triggering shop-scoped side effects, or updating tenant state keyed by `shop`), this is a cross-tenant data-integrity/confidentiality break — data belonging to shop A can be injected/attributed to shop B purely by manipulating an unauthenticated header, which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker able to install the app on their own store (a normal, unprivileged action): they need only capture one legitimate webhook delivery (trivial, since they run their own HTTP endpoint) and replay it with a modified header. No secret material, TLS interception, or social engineering is required — only observation of traffic the attacker legitimately receives.

### Recommendation
Include the shop domain (and other trust-critical headers such as topic/webhook-id/api-version) in the HMAC-signed content, or otherwise cryptographically bind `shop` to the body/HMAC (e.g., have `to_signable_string` concatenate the shop header with the raw body in a canonical form), and reject any request where the header-derived value isn't authenticated. At minimum, document that host applications must independently verify the shop identity from a trusted source (e.g., their own webhook registration record for that topic) rather than trusting the unauthenticated header value.

### Proof of Concept
1. Attacker installs the target app on their own store, `attacker-shop.myshopify.com`, and receives a legitimate webhook, e.g. `orders/create`, with body `{"id":1,...}` and header `X-Shopify-Hmac-Sha256: <valid hmac over body>`.
2. Attacker sends a new HTTP request to the app's webhook receiver endpoint with:
   - Body: unchanged `{"id":1,...}`
   - `X-Shopify-Hmac-Sha256`: unchanged (still valid, since HMAC is only over the body)
   - `X-Shopify-Shop-Domain`: changed to `victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `Request#to_signable_string` is just `@raw_body` [1](#0-0) .
4. The app's registered `WebhookHandler#handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the host application to process attacker-supplied data under a victim tenant's identity.
