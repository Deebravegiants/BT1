Confirmed: there is no token whitelist/registry anywhere in `HinkalHelper.performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, or `CircomDataBuilder` — `erc20TokenAddresses` are arbitrary attacker-supplied addresses, the only constraint being pairwise distinctness of the raw address *value* enforced in the circuit (`circuits/MainEVMCircuit.circom` `distinctErc20AddressChecks`), which does not (and cannot) constrain what a given address's `balanceOf` actually reads from.

### Title
Aliased-balance ERC20 addresses allow minting unbacked shielded UTXOs via per-index balance-diff check - (File: contracts/Hinkal.sol :: transact / _internalTransact)

### Summary
`Hinkal.transact` verifies solvency per `erc20TokenAddresses[i]` entry by independently snapshotting `balanceOf` before/after via `getBalancesForArray` and checking `balanceDif == amountChanges[i] + utxoAmount` for each index separately. Because the circuit only forbids two entries in `erc20TokenAddresses` from being the *same address value* (`distinctErc20AddressChecks` in `circuits/MainEVMCircuit.circom` lines 171-182), an attacker can supply two distinct contract addresses that both proxy `balanceOf`/`transfer` calls to one shared real balance (e.g., both forward to the real underlying token, such as USDC). A single real deposit then shows up as a balance increase under both addresses, letting the attacker credit two independent shielded UTXOs (one per alias) for the price of one real transfer.

### Finding Description
The claimed invariant "net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)" is broken per-token, because the check operates on `newBalances[i] - oldBalances[i]` computed via `getERC20OrETHBalance` [1](#0-0) , called once per array index with no cross-index correlation of the underlying storage the `balanceOf` call actually reads.

Exploit flow (internal transact, `externalActionId == 0`):
1. Attacker deploys two contracts `A` and `B` that are thin proxies exposing standard `balanceOf`/`transfer`/`transferFrom`, both delegating reads/writes to one shared real ERC20 balance (Hinkal's balance in the real token).
2. Attacker calls `transact` with `erc20TokenAddresses = [A, B]`, `amountChanges = [+100, +100]`, `onChainCreation = [false, false]` (mandatory for internal path, enforced by `checkOnchainCreation` in `contracts/HinkalHelper.sol` lines 173-202).
3. `oldBalances = getBalancesForArray([A,B])` snapshots the same real underlying balance twice [2](#0-1) .
4. `_internalTransact` sees `deltaAmountChange > 0` for index 0 (token A) and calls `transferERC20TokenFromOrCheckETH(A, ..., 100)` [3](#0-2) , which triggers exactly one real transfer of 100 tokens into Hinkal via `A.transferFrom`. Because `deltaAmountChange` for index 1 (token B) is also `> 0`, `_internalTransact` additionally requires a transfer via `B`, but since `B` is a proxy for the *same* real balance, the attacker can implement `B.transferFrom` to be a no-op that returns `true` without moving further real value (or route it back to the same balance) — the code does not verify per-token distinctness of the moved value, only that `transferERC20TokenFromOrCheckETH` succeeds.
5. `newBalances = getBalancesForArray([A,B])` now shows +100 under both index 0 and index 1, since both proxy to the same real balance.
6. `_internalTransact`'s per-index loop [4](#0-3)  computes `balanceDif[0] = 100` and `balanceDif[1] = 100`, and both satisfy `balanceDif == amountChanges[i] + utxoAmount` (utxoAmount is always 0 for internal transact, since `utxoSet` is only populated in `_externalTransact`).
7. Both checks pass, and the circuit-verified proof mints two independent shielded UTXOs of 100 each (one denominated in token `A`, one in token `B`) via `insertCommitments` [5](#0-4) , backed by only one real 100-unit deposit.
8. Later, the attacker withdraws both UTXOs. The withdrawal for the `A`-denominated UTXO calls `transferERC20TokenOrETH(A, recipient, 100)`, and the withdrawal for the `B`-denominated UTXO calls `transferERC20TokenOrETH(B, recipient, 100)` — both of which resolve to the *same* real token's `transfer` function, draining 100 extra real tokens that were never deposited, at the expense of other depositors' shielded balances (protocol insolvency).

Existing guards do not catch this: `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, and `rootHashExists` never inspect what a token address's `balanceOf`/`transfer` actually resolves to — they operate purely on the numeric address values and circuit-computed sums, which are internally consistent with the (forged) per-index balance readings. The circuit's `distinctErc20AddressChecks` (circuits/MainEVMCircuit.circom lines 171-182) only guarantees the raw address integers differ, which is trivially satisfiable by two different contract addresses sharing one real balance.

### Impact Explanation
This mints shielded value without real backing and enables direct theft of other users'/protocol funds from `Hinkal` — Critical severity per the rules ("minting shielded value without backing (protocol insolvency)"). The attack is fully repeatable: each malicious token pair can be reused, or new pairs deployed, to keep minting unbacked shielded credit denominated in whatever real token is aliased (e.g., a valuable asset like USDC/WETH held by Hinkal), then draining it via legitimate-looking withdrawal transactions.

### Likelihood Explanation
Preconditions are entirely within an unprivileged attacker's control: deploying arbitrary "token" contracts, choosing arbitrary `erc20TokenAddresses`, `amountChanges`, and generating a valid proof for their own UTXOs (the circuit does not constrain token semantics, only arithmetic consistency of the provided public inputs). No relay, admin, or victim cooperation is required. Attacker cost is limited to gas plus the one real deposit needed to seed the shared balance; the return is a duplicated shielded credit against that same real balance. This is feasible on any chain where Hinkal is deployed, including both Base and Arbitrum with the same proxy-token bytecode/preimage, since nothing in `Hinkal.sol` or the circuit ties `erc20TokenAddresses` correctness to chain-specific state beyond `block.chainid` inclusion in the signed-message hash — which does not prevent redeploying the identical aliasing token contracts on each chain and repeating the exploit independently per chain (this is two independent exploitations of the same code path, not a "replay" of a single signature/proof across chains, since a proof/signature bound with `chainId` will not verify on the other chain).

### Recommendation
Do not trust independent `balanceOf` snapshots per declared `erc20TokenAddresses[i]` as a solvency proof. Options:
- Require that `erc20TokenAddresses` be drawn from an admin-curated allowlist of tokens known not to alias shared storage, rejecting arbitrary attacker-supplied token contracts.
- Track a single canonical per-token internal accounting ledger (increment/decrement based on actual observed transfer amounts returned by `SafeERC20`, not independent `balanceOf` diffs) so that no two array entries can double count the same physical asset movement.
- Cross-check that no two entries in `erc20TokenAddresses[]` produce the same `balanceOf(address(this))` value/delta within a single transaction before trusting them as independent balances, or restrict `erc20TokenAddresses.length` per-token to one canonical address that has been pre-verified to be a standard, non-aliased ERC20.

### Proof of Concept
Foundry test plan:
1. Deploy `RealToken` (standard ERC20) and mint the attacker 1000 units.
2. Deploy `AliasA` and `AliasB`, thin proxy contracts whose `balanceOf(address who)`, `transferFrom`, and `transfer` all delegate to `RealToken.balanceOf(who)` / `RealToken.transferFrom` / `RealToken.transfer`, with `AliasB.transferFrom` implemented as a no-op returning `true` (or crediting `RealToken` from a pre-approved allowance that only actually moves 0 units).
3. Attacker approves `AliasA`/`RealToken` for Hinkal, then calls `Hinkal.transact` with `circomData.erc20TokenAddresses = [AliasA, AliasB]`, `amountChanges = [100, 100]`, `onChainCreation = [false, false]`, valid nullifiers/roots/proof for an internal transact minting two 100-unit UTXOs.
4. Assert: `RealToken.balanceOf(hinkal)` only increased by 100 (`vault balance delta == 100`), while `sum(amountChanges) == 200` and two 100-unit UTXO commitments were inserted (`credited UTXO value == 200`), i.e. `vault balance delta (100) < credited UTXO value (200)`.
5. Follow up with two withdrawal `transact` calls redeeming both UTXOs (via `AliasA` and `AliasB` respectively) and assert `RealToken.balanceOf(hinkal)` goes negative relative to actual deposits, demonstrating drained value exceeding what was ever deposited.
