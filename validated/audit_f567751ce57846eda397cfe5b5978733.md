## Analysis

The Pendle report's bug class is: a value-moving operation is allowed to complete while the code that is supposed to verify the actual value received/moved is bypassed (there `minTokenOut=0`; here the entire balance-equation check is skipped). The reachable analog in this repo breaks the same equality Hinkal relies on everywhere else: `balanceDif == amountChanges + utxoAmount`.

`contracts/Hinkal.sol` normally enforces this per-token by iterating `circomData.erc20TokenAddresses` [1](#0-0) . `CircomDataBuilder.formInputForCircom` has a special "Emporium min" path that is taken whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && circomData.erc20TokenAddresses.length == 0`, producing a public-input vector containing only `emporiumMessage`, `timeStamp`, `calldataHash` — notably *not* `getSignedMessageHash(...)` which is what binds `rootHashHinkal`, `amountChanges`, nullifiers and commitments to the EdDSA signature in the normal path [2](#0-1) . `HinkalHelper.dimensionsCheck` accepts `dimensions.tokenNumber == 0` unconditionally, since it only checks that all `circomData` array lengths equal `dimensions.tokenNumber` [3](#0-2) , so a zero-token transaction is a legitimate, reachable configuration for any caller.

With `erc20TokenAddresses.length == 0`, the loops in `Hinkal.transact()` that compute `oldBalances`/`newBalances` and enforce `balanceDif == amountChanges + utxoAmount` never execute [4](#0-3) . The call is routed to `EmporiumUpgradeable.runAction`, whose own balance-diff loop is likewise bounded by `circomData.erc20TokenAddresses.length` and therefore also does nothing [5](#0-4) . When `stack.signerAddress == address(0)`, `verifyWallet` only marks the message used and returns without any EIP-712 check [6](#0-5) , after which the stateless branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract with attacker-chosen `endpoint`, `value`, and `callData` [7](#0-6) .

### Title
Emporium "zero-token" mode bypasses Hinkal's balance-diff equality check, allowing unauthorized arbitrary calls and drain of Emporium's residual balance - (File: contracts/Hinkal.sol, contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `circomData.erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `CircomDataBuilder.formInputEmporiumMin` produces a public-input vector that omits the `signedMessageHash` binding, and `dimensionsCheck` permits `tokenNumber == 0`. Because every balance-verification loop in `Hinkal.transact()` and `EmporiumUpgradeable.runAction()` is bounded by `erc20TokenAddresses.length`, this configuration causes the core balance equation (`balanceDif == amountChanges + utxoAmount`) to be skipped entirely, and (when `stack.signerAddress == address(0)`) the EIP-712 wallet-authorization check is also skipped, letting an unprivileged EOA drive an arbitrary `endpoint.call` from the Emporium contract.

### Finding Description
Hinkal's fund-safety invariant is that any external action's real balance movement must equal the values in `circomData.amountChanges`/UTXO outputs, checked in `Hinkal.transact()` [8](#0-7) . This check, and the mirrored check in `EmporiumUpgradeable.runAction`, iterate over `circomData.erc20TokenAddresses`. Supplying an empty `erc20TokenAddresses` array (a value that `dimensionsCheck` accepts as long as all other arrays are also empty [9](#0-8) ) makes both loops no-ops, so no balance/UTXO equality is ever enforced for this call.

Simultaneously, `formInputForCircom` special-cases this configuration into `formInputEmporiumMin`, whose public-input vector is only `[emporiumMessage, timeStamp, calldataHash]` [10](#0-9) , in contrast to the normal path which also publicly commits `getSignedMessageHash(...)` binding `rootHashHinkal`, `amountChanges`, nullifiers and commitments to the prover's EdDSA signature [11](#0-10) . Since `tokenCount == 0` also means the circuit's per-token loop (nullifier/commitment verification) never executes [12](#0-11) , the resulting ZK proof does not prove ownership of any real shielded UTXO — the prover can supply a self-chosen `spendingPublicKey`/`eddsaSignature`/`signedMessageHash` triple satisfying only `SignatureVerifier` [13](#0-12) , which is trivially satisfiable by anyone.

The only remaining gate is `verifyWallet` in `EmporiumUpgradeable`, but when `stack.signerAddress == address(0)` it returns immediately after marking `emporiumMessage` used, with no signature check [6](#0-5) . The subsequent stateless branch then executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract using attacker-controlled `endpoint`/`value`/`callData` decoded from `externalActionMetadata` [7](#0-6) .

This breaks the same class of equality identified in the report: a value-moving path (the Emporium's arbitrary call) is not counted/constrained by the balance/signature equations that are supposed to authorize it (`calldataHash`/`signedMessageHash`/public-input vector), analogous to `SY.redeem()` moving real value that the oracle's public accounting never captures.

### Impact Explanation
Any funds sitting on the Emporium contract (protocol/relay fees, leftover token dust from `handleOut`'s "balance before call" carry-over comment at `EmporiumUpgradeable.sol:141`, or any token the Emporium has been approved to pull) can be moved out via an arbitrary `call` triggered by an unprivileged caller with no valid shielded-fund ownership proof and no wallet-owner signature. This is theft/permanent freezing of protocol or relay funds and unauthorized asset movement — meeting the High/Critical bar (unauthorized calls/moving assets nobody authorized, theft of protocol fees).

### Likelihood Explanation
The path is reachable purely through public functions (`Hinkal.transact()` with `dimensions.tokenNumber = 0` and `externalActionId = HINKAL_EMPORIUM_ACTION_ID`), requires no privileged role, admin, relay, or victim key, and only requires generating a Groth16 proof for the trivially-satisfiable zero-token circuit instantiation — well within reach of any user capable of running the existing proving toolchain.

### Recommendation
Reject `externalActionId == HINKAL_EMPORIUM_ACTION_ID` transactions with `erc20TokenAddresses.length == 0` unless a genuine authorization path exists (e.g., always require `stack.signerAddress != address(0)` and a valid EIP-712 signature for any Emporium execution, and/or always bind `getSignedMessageHash` into the public inputs regardless of token count so the proof cannot be trivially forged). Additionally, ensure the balance-diff verification cannot be skipped by an empty token array — e.g., require `erc20TokenAddresses.length > 0` for any externalActionId that executes calls capable of moving value, or track Emporium's own balance invariants independent of `circomData`.

### Proof of Concept
1. Caller crafts `circomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one stateless `EmporiumOperation{endpoint: <target>, invokeWallet: false, value: <amt>, callData: <arbitrary calldata, e.g. ERC20.transfer(attacker, balance)>}`.
2. Caller sets `dimensions.tokenNumber = 0` and generates a Groth16 proof for `MainEVMCircuit(0,0,0,treeDepth)` using a freshly generated EdDSA keypair (no real shielded deposit needed), satisfying only `SignatureVerifier` since the token loop never executes.
3. Caller calls `Hinkal.transact(a,b,c,dimensions,circomData)`. `performHinkalChecks` verifies `calldataHash` and dimensions (both self-consistent with an empty array), `verifyProof` succeeds against the reduced `formInputEmporiumMin` public inputs.
4. `_externalTransact` routes to `EmporiumUpgradeable.runAction`; `verifyWallet` skips signature verification because `signerAddress == address(0)`; the stateless branch calls `endpoint.call{value: op.value}(op.callData)` directly from Emporium, moving out any token/ETH balance the Emporium holds or can command.
5. Back in `Hinkal.transact()`, the `erc20TokenAddresses`-bounded balance-diff loop has zero iterations, so no revert occurs regardless of what value left the Emporium contract.
