### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are taken from unauthenticated HTTP headers that are never included in the HMAC. This breaks the intended binding `HMAC(secret, raw_body) == received_hmac` from also covering `shop-domain` and `topic`, allowing those fields to be forged independently of a valid signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates only that `Utils::HmacValidator.validate(request)` succeeds — i.e., that `hmac == HMAC(secret, raw_body)` — and then unconditionally trusts `request.shop` and `request.topic` (taken from the unsigned headers) to route the webhook and construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms this — it only ever inspects `verifiable_query.hmac` and `verifiable_query.to_signable_string`, never any header/field beyond what the object chooses to sign: [4](#0-3) 

The identity binding that should hold is:
`HMAC(secret, raw_body ‖ shop ‖ topic) == received_hmac`
but what is actually verified is:
`HMAC(secret, raw_body) == received_hmac`, with `shop` and `topic` accepted from bytes that were never part of that verification (bytes verified vs. bytes parsed diverge).

### Impact Explanation
Any entity that can obtain one legitimately-signed webhook body+HMAC pair for the app's secret — most simply, a merchant who has installed the app on their own store and can trigger a webhook whose body content they control (e.g., `products/create` with an attacker-chosen title, or any webhook topic they can trigger) — can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain and/or the `X-Shopify-Topic` header with a different topic. The gem will report the HMAC as valid (it only checks the body) and will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop under a topic the attacker chose. Any app logic keyed on `WebhookMetadata#shop` (e.g., updating per-shop records, triggering per-shop side effects) is deceived into acting on cross-tenant, attacker-controlled data attributed to a shop the attacker does not control. This is a cross-tenant identity-binding bypass rooted entirely in this gem's webhook verification method.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment that relies on this gem's webhook signature check as its sole trust mechanism (as the documented usage pattern implies): an attacker only needs one valid signed webhook of their own (trivial to obtain by installing the app on a shop they control and triggering any webhook with attacker-influenced body fields) and the ability to POST to the app's public webhook endpoint with modified headers, both of which require no privileged credentials.

### Recommendation
Include the shop domain, topic, and any other fields used downstream for authorization/routing decisions in the HMAC-signable string (or otherwise cryptographically bind them to the verified body), so that `HmacValidator.validate` fails if any of these fields are altered independently of the body. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for business-logic purposes unless they are covered by the verified signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook whose body they can influence (e.g., `products/create` with a crafted title/body). Shopify sends the app a valid `X-Shopify-Hmac-Sha256` for that exact `raw_body`.
2. Attacker captures that `raw_body` and its valid `hmac-sha256` header value.
3. Attacker POSTs to the app's public webhook endpoint using the captured `raw_body` and `hmac-sha256`, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: <topic of attacker's choosing>`
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only checks presence, not binding) — see [5](#0-4) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes `HMAC(secret, raw_body)` — see [6](#0-5) .
6. The registered handler receives `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` — see [7](#0-6) , causing the app to act on forged cross-tenant data despite a "valid" HMAC.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
