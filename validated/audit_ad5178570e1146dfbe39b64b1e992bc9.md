### Title
`whenNotPaused` on `HyperFungibleToken.onPostRequestTimeout` permanently blocks refunds of already-burned tokens while the contract is paused - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol)

### Summary
`HyperFungibleToken` burns tokens on `send()` before a cross-chain ISMP POST request is dispatched, and only re-mints them back to the sender in `onPostRequestTimeout` if the request times out. This refund entrypoint is gated by `whenNotPaused`, so if the owner pauses the contract (e.g. in response to an incident) any pending timeout for an already-burned transfer cannot be delivered while paused, exactly mirroring the `sDaiStrategy` bug class where a pause blocks the "give the user their assets back" path rather than only blocking new deposits/sends.

### Finding Description
`send()` immediately burns `params.amount` from the caller and dispatches an ISMP request [1](#0-0) . The only way those burned funds return to the user if the cross-chain message is never delivered is via `onPostRequestTimeout`, which re-mints the amount to the original sender [2](#0-1) . That function, however, carries the `onlyHost whenNotPaused` modifiers [3](#0-2) .

This is the same bug class as the `sDaiStrategy` finding: pausing is meant to stop *new* risk-taking operations (here, `send()`/`onAccept()` for new mints), but it also blocks the recovery/refund path for value the user has already given up (burned tokens awaiting a timeout refund). Once the owner pauses the token (for any reason — a suspected exploit, a misbehaving peer chain, an emergency stop), any user whose transfer subsequently times out is stuck: they already lost their tokens to the burn, and the only path back to them reverts with `Pausable: paused` until the owner unpauses.

### Impact Explanation
Because ISMP timeout delivery is typically a one-shot handler call (the ISMP host processes a timeout receipt and invokes `onPostRequestTimeout` on the app once), a revert here means the relayer's submitted timeout-proof transaction fails. Depending on how the underlying `HandlerV2`/`EvmHost` timeout-processing records state, this can either require costly re-delivery attempts once the pause is lifted, or in the worst case (if the ISMP receipt/commitment bookkeeping marks the timeout as consumed on a reverted call at a different layer, or if the pause is never lifted, e.g. due to abandoned governance or intentional indefinite pause after an incident) permanently strand the user's already-burned tokens with no recovery path. This is a freezing-of-funds condition for any user whose in-flight transfer times out during a pause window, directly analogous to the Medium-severity `sDaiStrategy` report where withdrawals — the loss-mitigation path — were blocked by the same pause flag that blocks deposits.

### Likelihood Explanation
Likelihood is Medium: it only manifests when the owner pauses `HyperFungibleToken` (an operational/incident-response action expected to be infrequent and transient) while there are still in-flight, not-yet-timed-out transfers. Any relayer or unprivileged party attempting to deliver a legitimate timeout proof during that window will trigger the revert, so this is reachable without any privileged action from the party attempting the refund — only the initial pause action is privileged, matching the analog's requirement that only the pause condition, not the withdrawal attempt, involves an admin.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout` (and consider doing the same for `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`/`HyperFungibleTokenUpgradeable`, which mirror this same pattern [4](#0-3) ) so that refunds of already-burned/escrowed value can always be processed regardless of pause state, while keeping `whenNotPaused` on `send()`/`onAccept()` to stop new mints/burns during an incident.

### Proof of Concept
1. User calls `send()` on `HyperFungibleToken`; `params.amount` is burned and an ISMP POST request with a timeout is dispatched [1](#0-0) .
2. Before the request is delivered, the owner calls `pause()` (e.g., due to a suspected issue on a peer chain) [5](#0-4) .
3. The request times out on the source host. A relayer submits the timeout proof, which the ISMP host relays into `onPostRequestTimeout(incoming)`.
4. The call reverts with `Pausable: paused` because of the `whenNotPaused` modifier [3](#0-2) , so the user's already-burned tokens cannot be re-minted back to them for as long as the pause remains active.

Note: I was unable to fully verify, within tool budget, whether `HandlerV2`'s timeout-processing path allows the same timeout proof to be resubmitted after unpausing (partial mitigation) or whether it is a one-shot commitment that gets consumed regardless of the app callback's revert (full/permanent freeze) — this last piece would need to be checked in `evm/src/core/HandlerV2.sol` and `evm/src/core/EvmHost.sol`'s timeout handling to confirm whether the impact is "temporary freeze until unpause" or "permanent loss."
