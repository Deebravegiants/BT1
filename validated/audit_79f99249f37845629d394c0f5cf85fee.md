Audit Report

## Title
Gateway HTTP-action response cache key omits `WorkflowID`, breaking the documented workflow-isolation guarantee and allowing cross-workflow response/cache confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The `responseCache` used by the Gateway's HTTP Action handler stores/retrieves cached HTTP responses keyed solely by `req.Hash()`, but this hash does not incorporate `WorkflowID` or `CacheSettings`, contradicting the package's documented "workflow-scoped" isolation guarantee. Two distinct workflows sharing the same `WorkflowOwner` and issuing outbound HTTP requests with identical method/URL/headers/body will collide on the same cache slot, allowing one workflow to be served a response fetched/cached in the context of a different workflow.

## Finding Description
`gatewayHandler.makeOutgoingRequest` unmarshals a caller-supplied `OutboundHTTPRequest` from a node message and dispatches it through `responseCache.Fetch` or `responseCache.Set` using `req` as-is: [1](#0-0) 

The cache implementation keys all operations (`Fetch`, `Set`, `isExpiredOrNotCached`) purely by `req.Hash()`: [2](#0-1) 

The package README explicitly documents the intended security property that the cache key is "Generated from workflow ID and request hash" and that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage": [3](#0-2) 

However, the unit test `TestRequestHash` proves the opposite: `WorkflowID` and `CacheSettings` have no effect on the hash value, only method/URL/headers/body (and `WorkflowOwner`) matter: [4](#0-3) 

This is a genuine root-cause discrepancy between documented behavior and implementation: the cache is keyed at the `WorkflowOwner`+request level, not `WorkflowID`+request level as documented, so two different workflows under the same owner making an identical outbound request collide on the same cache entry regardless of each workflow's own `CacheSettings.MaxAgeMs`/`Store`.

## Impact Explanation
This breaks the explicitly documented workflow-isolation control. A workflow with a strict freshness need can be served a response that was fetched/cached to satisfy a different workflow's request (as long as it falls within the requester's own `MaxAgeMs` window), since the stored entry's producing `WorkflowID` and its `CacheSettings` are not encoded in the key. This maps to a cross-user/cross-workflow response corruption class issue: workflow execution context confusion, not confidential-data leakage across unrelated owners (since `WorkflowOwner` is still included in the hash, per `createTestRequest`/`TestRequestHash` "having same workflowOwner results in the same Hash" test, isolation across different owners appears preserved at the hash level, only same-owner different-`WorkflowID` collisions are demonstrated). Severity is bounded: it requires two distinct workflows under the *same* owner issuing outbound requests with identical method/URL/headers/body, and the disclosed content is the (identical) fetched HTTP response body/headers, not secrets belonging to a different owner.

## Likelihood Explanation
The condition is reachable by any node/workflow already authorized to use the HTTP action capability through the Gateway's normal `HandleNodeMessage` outbound-HTTP flow — no privilege escalation or additional bypass is required beyond what any authorized capability node can already send. The main constraint is that it requires two workflows under the *same* `WorkflowOwner` to issue requests with an identical hash input (method, URL, headers, body); this is plausible for workflows querying the same well-known third-party endpoint with default parameters, though it is not universally trivial to engineer without knowledge of another workflow's exact request shape and timing.

## Recommendation
Incorporate `WorkflowID` (and ideally `CacheSettings`) into the cache key computed in `response_cache.go`, e.g., derive `cacheKey := hash(req.WorkflowID, req.Hash())` or otherwise partition the cache map by `WorkflowID` before falling back to `req.Hash()`, so `Fetch`/`Set`/`isExpiredOrNotCached`/`DeleteExpired` all operate on truly workflow-scoped keys, matching the README's documented behavior.

## Proof of Concept
1. Workflow A (`WorkflowID = "wf-A"`, `WorkflowOwner = "owner-1"`) sends an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings:{Store:true, MaxAgeMs:600000}}` through the Gateway; the response is stored under `req.Hash()` via `responseCache.Fetch`/`Set`.
2. Workflow B (`WorkflowID = "wf-B"`, same `WorkflowOwner = "owner-1"`) sends an outbound request with the same method/URL/headers/body but its own `CacheSettings.MaxAgeMs`.
3. Run `TestRequestHash`'s "having different workflowID results in same Hash" subtest (`core/services/gateway/handlers/capabilities/v2/response_cache_test.go` lines 139-149) to confirm `req1.Hash() == req2.Hash()` when only `WorkflowID` differs — proving Workflow B's `Fetch` call will read Workflow A's cached entry as long as it is within Workflow B's own `MaxAgeMs` window.

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

// Fetch fetches a response from the cache if it exists and
// the age of cached response is less than the max age of the request.
// If the cached response is expired or not cached, it fetches a new response from the fetchFn
// and caches the response if it is cacheable and storeOnFetch is true.
//
// The mutex is only held during cache map access (microseconds), not during fetchFn execution.
// Singleflight deduplicates concurrent requests to the same cache key so only one fetchFn
// runs per key, while requests to different keys execute in parallel.
// Cache read and write happen inside the singleflight callback to ensure the key remains
// in-flight until the result is stored, preventing duplicate fetches.
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
