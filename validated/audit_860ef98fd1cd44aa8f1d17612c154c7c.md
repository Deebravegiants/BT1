### Title
`IntentGatewayV2.placeOrder` (Tron) credits escrow from declared amounts instead of actual transferred amounts, with no reentrancy guard - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the order `commitment` and credits `_orders[commitment][token]` using the fee-reduced *declared* input amounts (`reducedInputs[i].amount`), but never re-measures the actual token balance received by the gateway before crediting escrow in the non-predispatch path, and the function carries no reentrancy guard. This is the same bug class as the Arcadia report: a value (collateral/liquidity in the original report, escrow amount here) is computed/cached from pre-transfer state and trusted afterward, while an attacker-controlled callback during the token transfer (an ERC-777 `tokensToSend` hook, or any non-standard token) can manipulate what actually lands in the contract, or reenter the contract, before the trusted value is used.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`: [1](#0-0) 

The function is declared `public payable` with **no `nonReentrant` modifier** — unlike the mainline EVM contract, whose `placeOrder` is `nonReentrant`: [2](#0-1) 

`reducedInputs` (the escrowed amount per token) and `commitment` are derived purely from the caller-declared `order.inputs[i].amount`, before any token transfer happens: [3](#0-2) 

In the non-predispatch branch, tokens are pulled with a plain `safeTransferFrom` and the escrow is credited with the *pre-computed* `reducedInputs[i].amount` — there is no balance-before/after check to confirm that amount was actually received: [4](#0-3) 

Compare this to the mainline EVM `placeOrder`, which explicitly measures `balBefore`/`balAfter` around the transfer and mutates `order.inputs[i].amount` to the *actual* received amount before the commitment/escrow amounts are ever computed, precisely to defend against fee-on-transfer or hook-based tokens: [5](#0-4) 

Because the Tron path both (a) trusts a value computed before the transfer instead of re-verifying it afterward, and (b) has no reentrancy guard, a malicious/non-standard ERC-20-like token used as an order input (a fee-on-transfer token, or an ERC-777/hooked token whose `tokensToSend`/similar callback fires during `safeTransferFrom`) lets an attacker:
- receive escrow credit (`_orders[commitment][token] += reducedInputs[i].amount`) for more tokens than the gateway actually holds (fee-on-transfer under-delivery is never detected), and/or
- reenter `placeOrder` (or other unguarded gateway functions) from the token's transfer hook while the outer call's escrow bookkeeping is mid-flight, since nothing blocks a nested call.

This mirrors the Arcadia root cause exactly: a collateral/escrow value is cached/derived from pre-transfer declared state and used without re-validating it against the state that exists after the transfer (and any reentrant callback) completes.

### Impact Explanation
An attacker can place orders backed by a malicious input token that either short-delivers to the gateway (fee-on-transfer) or reenters during transfer, causing `_orders[commitment][token]` to record more escrowed value than the gateway actually received. When a solver later fills the order and the destination-chain `withdraw()`/settlement path releases funds against this inflated escrow record, the gateway can pay out real assets (from its shared token balance, or fee-token reserve) that were never actually deposited — a direct fund-drain / insolvency of the escrow accounting, i.e., unbacked "mint" of escrow value on this chain's IntentGateway deployment. This qualifies as concrete theft / permanent freezing risk for the protocol's escrowed funds, matching the Medium/High bar.

### Likelihood Explanation
Reachable by any unprivileged user in a single transaction: simply call `placeOrder` with an order whose input token is attacker-deployed (fee-on-transfer or ERC-777-style with a registered hook). No governance, admin, or relayer privilege is required — only that the deployment lists (or can be induced to list) such a token as an accepted order input, and/or that predispatch/CallDispatcher composition is used to route through such tokens. Given IntentGateway is meant to be generically composable with arbitrary ERC-20-shaped tokens (the mainline EVM contract explicitly defends against fee-on-transfer tokens via balance-diff), the likelihood that this token class reaches the Tron deployment is non-trivial, and the missing `nonReentrant` guard compounds the risk versus the already-hardened mainline contract.

### Recommendation
- Add the same reentrancy protection (`nonReentrant`) that the mainline EVM `IntentGatewayV2.placeOrder` has to the Tron variant.
- In the non-predispatch escrow branch, measure `balanceOf(address(this))` before and after `safeTransferFrom` and use the actual received delta (analogous to the mainline contract) to compute `reducedInputs`/escrow credit and the `commitment`, rather than trusting the caller-declared `order.inputs[i].amount`.
- Ensure the predispatch branch's dust/requiredAmount handling is likewise driven by measured balances, not just a "balance >= requiredAmount" sufficiency check, so that escrow credit always equals actually-held tokens.

### Proof of Concept
1. Attacker deploys (or uses) an ERC-20-shaped token with fee-on-transfer behavior (e.g., 100 bps fee) or an ERC-777-compatible token with a `tokensToSend` hook registered to attacker's own contract.
2. Attacker calls `IntentGatewayV2(tron).placeOrder(order, graffiti)` with `order.inputs[0] = {token: feeToken, amount: 1000}` and no predispatch.
3. `placeOrder` computes `reducedInputs[0].amount = 1000` (minus protocol fee) and `commitment` before transferring.
4. `IERC20(feeToken).safeTransferFrom(msg.sender, address(this), 1000)` executes; due to the fee, the gateway actually receives e.g. 990 tokens (or, for a hook-token, the attacker's hook reenters `placeOrder` to place a second order using the same not-yet-debited allowance/balance before the outer call finishes).
5. `_orders[commitment][feeToken] += reducedInputs[0].amount` credits escrow for the full declared amount (990/1000 discrepancy, or a duplicated credit from the reentrant call), which is more than the gateway's real token balance for that commitment.
6. When a solver fills the order and destination-chain settlement calls `withdraw()`/`_withdraw()` to release the escrowed `feeToken` amount, the payout is sized to the inflated `_orders[commitment][token]` value, draining real balance backing other users' unrelated escrowed orders in the same token.

A full runnable Foundry PoC would require deploying a fee-on-transfer/ERC-777-style token fixture against the Tron contract build and is not included here, per the same reasoning the original report gives — the mechanism is a direct code-level trust-without-reverification issue, verifiable by inspection of the cited lines.
