### Title
Silent Eviction of Queued Personal-Custody (Biometric) Packages in `data_uploader::Agent` Causes Undetected Loss of Iris/Face Biometric Data - ([File: src/agents/data_uploader.rs])

### Summary
The `data_uploader` agent that queues personal-custody packages (PCP tiers 1 and 2, which carry normalized iris images, iris codes, and face-identifier biometric bundles) for background upload silently drops the oldest queued item whenever a tier queue reaches its `dropping_threshold`, with no error or notification propagated back to the caller that enqueued the (now-dropped) package. This mirrors the reported bug class: an operation that can partially/silently fail under resource pressure, without surfacing the failure to the orchestrating logic, which then proceeds as if the operation had succeeded — leaving the signup marked complete while biometric custody data was never uploaded.

### Finding Description
In `src/plans/mod.rs`, after a successful signup, tier-1 and tier-2 personal-custody packages (iris normalized images, iris codes, face-identifier bundle/embeddings) are fired into the `data_uploader` agent via `port::Outer::send`, which only confirms that the message was placed on the local mpsc channel to the agent task — it does **not** wait for or report on the outcome of the agent's internal enqueue/upload logic: [1](#0-0) 

Inside `data_uploader::Agent::run`, each `Input::Pcp` is pushed into a per-tier `Queue`. Critically, if the queue for that tier is already at its configured `dropping_threshold`, the **oldest** entry is evicted (`drop_oldest`) to make room for the new one — silently, with only a `tracing::error!`/debug log and no signal back to any caller: [2](#0-1) 

The `drop_oldest` implementation permanently discards the evicted package (and its on-disk representation in the persistent-queue variant) with no recovery mechanism: [3](#0-2) 

The only feedback mechanism exposed to callers is `wait_queues`, which merely blocks until the queue is below the *blocking* threshold — it says nothing about whether a specific package was already dropped, and it is called *before* enqueueing tier-0, not after enqueueing tier-1/tier-2: [4](#0-3) [5](#0-4) 

This is structurally identical to the reported bug class: a downstream component (jetton_minter / data_uploader) is given insufficient "capacity" (gas / queue slots) to guarantee delivery of every unit of work (mint messages / biometric packages), the failure mode when capacity is exhausted is silent (mode-1 send with no bounce / drop_oldest with no notification), and the upstream orchestrator (factory / MasterPlan signup flow) has no way to detect the partial failure and therefore finalizes success/committed state (DAO active / signup marked successful and `after_signup` proceeds) despite incomplete data propagation.

### Impact Explanation
If enough signups occur in quick succession (e.g., under network slowness/backpressure causing packages to queue up, or an operator/attacker driving rapid concurrent signups), the tier-1/tier-2 dropping thresholds can be reached, causing the oldest queued personal-custody package — belonging to an *earlier, potentially different signup* — to be silently discarded before it is ever uploaded. Because the `plans::mod.rs` signup flow does not check for or react to this eviction, the affected signup is still reported to the backend/UI as completed/successful (`debug_report.signup_successful()`), even though that user's tier-1/tier-2 biometric custody package (iris normalized images, iris codes, face-identifier embeddings used for self-custody) was never persisted to the backend. This is a genuine biometric-data-retention/availability failure with cross-signup state bleed characteristics: one signup's queued data can be evicted purely because of a later, unrelated signup's traffic, and no operator or user is alerted.

### Likelihood Explanation
The eviction path is reachable purely through normal, unprivileged signup flow — no privileged access or malicious peer/hardware access is required. It depends on ordinary operational conditions (upload backlog due to slow network, high signup throughput, or backend unavailability) which are realistic on a field-deployed device with intermittent connectivity. The `dropping_threshold` mechanism exists specifically to bound memory/disk usage, meaning it is expected to trigger under sustained backpressure, making this a plausible, not merely theoretical, occurrence.

### Recommendation
1. Propagate an explicit signal (e.g., add an `Output` variant to `data_uploader::Agent`, currently `Infallible`, or track dropped package IDs) whenever `drop_oldest` is invoked, so the broker/plan layer can detect the loss.
2. In `src/plans/mod.rs`, after enqueueing tier-1/tier-2 packages, use `wait_queues` (or an equivalent readiness/ack check) to detect and react to drops before declaring the signup successful, or retry/escalate instead of silently continuing.
3. Consider making `drop_oldest` evict data associated with the *current* signup rather than an arbitrary older one, or reject the incoming push (backpressure) rather than silently destroying another user's already-queued biometric package.
4. Emit a `dd_incr`/alerting metric distinct from existing counters specifically for "PCP dropped due to queue overflow" so operational monitoring can detect and act on data loss, and correlate it with the affected `signup_id` for later reconciliation/re-upload.

### Proof of Concept
1. Configure (or naturally reach, under degraded connectivity) `pcp_tier1_dropping_threshold` (or tier2) to a small value.
2. Drive N signups faster than the backend can accept `upload_personal_custody_package` requests, so `queues[i].len()` reaches `dropping_thresholds[i]` in `data_uploader::Agent::run`.
3. On the next `Input::Pcp` push for tier 1/2, `drop_oldest` fires and permanently removes the oldest queued signup's package: [6](#0-5) .
4. That earlier signup's `do_signup`/`after_signup` flow in `src/plans/mod.rs` already returned `Ok(result)`/proceeded without any indication of failure — its `debug_report.signup_successful()` (or equivalent) path completes normally, and the UI reports success to the operator/user even though the corresponding biometric custody package was never uploaded.

**Uncertainty note:** I could not fully verify the exact numeric defaults for `pcp_tier1_dropping_threshold` / `pcp_tier2_dropping_threshold` / their blocking counterparts, nor how `backend::config` overrides these at runtime, because the relevant sections of `src/config.rs` and `src/backend/config.rs` were only partially indexed. A Devin session with full repository access would be needed to confirm the exact threshold values and any additional guards that might mitigate this in practice.

    async fn drop_oldest(&mut self) {
        match self {
            Self::Memory { queue } => {
                queue.pop_back();
            }
            Self::Persistent { path, queue, .. } => {
                let Some(id) = queue.pop_back() else { return };
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during drop_oldest, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {}
                }
            }
        }
    }

/// Waits for all queues to be not full.
pub async fn wait_queues(port: &mut port::Outer<Agent>) -> Result<()> {
    let (tx, rx) = oneshot::channel();
    port.send(port::Input::new(Input::WaitQueues(tx))).await?;
    Ok(rx.await?)
}
