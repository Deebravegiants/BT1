### Title
Webhook Shop/Topic Headers Are Not Bound to the HMAC-Verified Body, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler subsequently *acts on* are taken from unauthenticated HTTP headers that are never included in the signed bytes. Any party who can obtain a single genuinely-signed webhook body/HMAC pair (e.g. by having the app installed on their own store) can replay that exact body with a forged `shop-domain` header claiming it originated from an arbitrary victim shop, and the library will accept it as valid.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from HTTP headers and are never part of the signed input: [3](#0-2) 

`Utils::HmacValidator.validate` verifies exactly this `to_signable_string` value against the received `hmac`, so it only proves the *body* bytes were produced by the app's secret — it says nothing about which shop or topic the body is claimed to belong to: [4](#0-3) 

`Registry.process` performs the HMAC check and then unconditionally trusts `request.shop` (and `request.topic`) to route and label the webhook, handing them straight to the app's handler: [5](#0-4) 

The test suite confirms this: the HMAC is computed over the JSON body alone (`"{}"`), while `shop`, `topic`, `webhook_id`, and `api_version` are set as separate, unsigned headers: [6](#0-5) 

This is structurally the same defect class as the `increaseAmountFor` report: a value that downstream logic acts on (there, the deposit amount driving the voting multiplier; here, the `shop`/`topic` used to attribute and route the webhook) is not covered by the integrity check that is supposed to bind the whole action together (there, the veToken accounting; here, the HMAC signature). The broken equality is:

`HMAC-verified bytes (raw_body only) != data acted upon (shop, topic, webhook_id, api_version headers)`

### Impact Explanation
Because `shop` is not bound to the signed payload, an attacker who legitimately installs the app on their own store (an ordinary, unprivileged action requiring no secret, token, or credential) receives at least one genuinely HMAC-signed webhook body for their own shop. They can then replay that exact body to the app's public webhook endpoint with a forged `shop-domain` (and/or `topic`) header naming an arbitrary victim shop. `Registry.process` will pass HMAC validation (since only the body is checked) and will invoke the app's handler with `WebhookMetadata.new(shop: <forged shop>, topic: <forged topic>, body: <replayed body>, ...)`. Any host application that uses `shop` from `WebhookMetadata` as a lookup/session key (the documented and expected usage pattern) will process attacker-controlled data under another tenant's identity — a cross-tenant integrity/data-attribution break with no credential belonging to the victim required.

### Likelihood Explanation
The webhook endpoint is, by design, unauthenticated at the HTTP layer (Shopify's servers call it directly), so it is reachable by anyone on the internet. Obtaining one valid signed body requires nothing more than installing the app as a normal merchant — no `api_secret_key`, access token, or privileged account is needed. Forging the headers is trivial once a valid body/HMAC pair is captured.

### Recommendation
Bind the `shop`, `topic`, `webhook_id`, and `api_version` values into the signed material that `HmacValidator` checks (e.g., include them in `to_signable_string`, or otherwise cryptographically bind them to the signature), so that the HMAC verifies the full identity context of the webhook, not just the raw body bytes. Alternatively, document prominently that `Registry.process` does not authenticate the `shop`/`topic` headers and that host applications must independently verify the shop against out-of-band state (e.g., a known/installed shop list) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker-shop.myshopify.com`; capture a legitimately delivered webhook, e.g. `orders/create`, with its real `X-Shopify-Hmac-Sha256` header and raw JSON body `B`.
2. Send a new HTTP request to the app's webhook endpoint with the exact same body `B` and the exact same `X-Shopify-Hmac-Sha256` value, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com` (and optionally alter `X-Shopify-Topic`).
3. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:10-13,35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: "victim-shop.myshopify.com"`, even though the body and signature never originated from that shop — demonstrating the unauthenticated shop/topic binding.
