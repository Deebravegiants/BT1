### Analysis

**The equality claimed to be broken:** "workchain parsed by `tryParseTonAddress` from a raw `wc:hex` string" vs "workchain that the bridge/contract will treat the address as belonging to." The premise is that an out-of-range decimal `wc` could be mis-parsed by `tryParseTonAddress`/`parseTonRawAddress` as `0` or `-1` due to a sign-parsing or off-by-one bug.

**Actual code path:**
- `parseTonRawAddress` splits on `:` and parses the workchain with plain `parseInt(parts[0]!, 10)` [3](#0-2) . This is a direct decimal string-to-integer parse, not a byte-level/two's-complement decode. `"255:...".split(":")[0]` parses to `255`, `"-2:..."` to `-2`, `"127:..."` to `127`, `"-128:..."` to `-128` — none of these collide with `0` or `-1`.
- The only place a two's-complement/sign-extension trick exists is in `parseTonUserFriendlyAddress`, which sign-extends a single decoded **byte** (`wcByte > 0x7f ? wcByte - 0x100 : wcByte`) for the base64 "friendly" address form [4](#0-3) . This applies only to the friendly form (bounded to a single byte, i.e., -128..127), and only `0x00`→`0` and `0xFF`→`-1` map into the accepted set; no other byte value collides with those two.
- `tryParseTonAddress` dispatches strictly: raw form (contains `:`) goes to `parseTonRawAddress`; anything else goes to `parseTonUserFriendlyAddress` [5](#0-4) . There is no cross-contamination between the two parsers.
- `validateTonAddress` then strictly checks `parsed.workchainId !== TON_WORKCHAIN_BASECHAIN && parsed.workchainId !== TON_WORKCHAIN_MASTERCHAIN` and rejects otherwise [6](#0-5) .
- `compareTonAddress` in `compareAddresses.ts` also calls the same `tryParseTonAddress`, so it is subject to the identical (correct) parsing logic [7](#0-6) .
- Downstream, `HotBridge.createWithdrawalIntents` forwards `args.withdrawalParams.destinationAddress` unchanged as the `receiver` [1](#0-0) , so whatever string was validated is exactly what's used to build the intent — there is no re-derivation step that could re-normalize an out-of-range workchain into an in-range one.

**Boundary enumeration** (`-2, 2, 127, -128`): all parse via `parseInt` to their literal decimal values, none of which equal `0` or `-1`, so `validateTonAddress` correctly returns `false` for all of them. There is no off-by-one or sign-collision bug in this code.
