### Title
Front-running `payout`/`create_account` with an attacker-supplied vesting schedule causes indefinite `VestingScheduleExists` DoS on a legitimate purchaser - (File: polkadot/runtime/common/src/purchase/mod.rs)

### Summary
Both `create_account` and `payout` gate on `T::VestingSchedule::vesting_balance(&who).is_none()` to reject accounts that already have a vesting lock. Any unprivileged signed account can call the vesting pallet's `vested_transfer` extrinsic to attach an arbitrary-duration vesting schedule to any target `AccountId`, including a legitimate purchaser's account, before `payout` is called. This causes `payout(origin, who)` to permanently return `Error::VestingScheduleExists`, freezing that purchaser's DOT payout with no pallet-level recovery mechanism.

### Finding Description
`payout` re-checks vesting status right before mutating `Accounts`: [1](#0-0) 
and the same check exists in `create_account`: [2](#0-1) 

The check relies on `pallet_vesting`'s `VestingSchedule::vesting_balance`, which returns `None` only when the target has **no** vesting storage entry at all, and `Some(_)` (including `Some(0)` for a fully-vested-but-not-yet-cleared schedule) whenever any entry exists: [3](#0-2) 

Crucially, `pallet_vesting::vested_transfer` is a normal, permissionless, signed extrinsic that lets **any account** push a vesting schedule onto **any target `AccountId`** — the target's consent is not required: [4](#0-3) 

An attacker can therefore:
1. Wait for a legitimate purchaser `who` to be `create_account`'d by `T::ValidityOrigin` and validated (`ValidLow`/`ValidHigh`).
2. Call `pallet_vesting::Pallet::vested_transfer(attacker_origin, who, VestingInfo::new(locked, per_block, start))` with `per_block` set to the smallest possible unit and `locked` set to (at least) `MinVestedTransfer`, maximizing `duration = locked / per_block` blocks.
3. When `PaymentAccount` later calls `payout(origin, who)`, the check `T::VestingSchedule::vesting_balance(&who).is_none()` fails because `Vesting::<T>::get(who)` is `Some(..)`, returning `Error::<T>::VestingScheduleExists` before any state in `Accounts` is touched.

Because the vesting entry remains in storage until it is either fully vested or merged/removed via `vest`/`vest_other`, and `vest_other` can only strip fully-elapsed schedules (`locked_at == 0`) from the vector, the attacker can make the schedule active for `duration = locked/per_block` blocks — bounded only by `MinVestedTransfer` and the smallest currency unit, which for realistic configurations can be an astronomically large number of blocks. There is no code path in the `purchase` pallet (no override, no admin bypass, no alternate ensure) that lets `payout` proceed despite an existing vesting schedule; the check is unconditional. This is a real, reachable state where a signed, non-privileged actor can permanently (for all practical chain lifetimes) block a specific victim's `payout` call.

### Impact Explanation
This matches the scoped impact: it is a griefing/DoS, not fund theft. A legitimate, fully-validated purchaser whose `AccountStatus.validity` is `ValidLow`/`ValidHigh` can have their `payout` permanently blocked by a third party's cheap, unprivileged `vested_transfer` call targeting their `AccountId`. The purchaser's owed free/locked balance sits configured in pallet state but can never be transferred out via `payout`, and `create_account` for the same address would similarly be blocked going forward. `PaymentAccount`'s funds are not at risk of theft — only the specific victim's payout is frozen.

### Likelihood Explanation
Highly feasible and repeatable: the attacker needs only a signed account with a small balance ≥ `MinVestedTransfer` and knowledge of the victim's `AccountId` (public, e.g. observable at `create_account` time or even beforehand). No collusion with `PaymentAccount` or `ValidityOrigin` is required. The attack is cheap (funds sent are locked to the victim, not lost) and can be repeated/extended if the schedule ever fully vests, by adding a fresh schedule before `payout` is retried, since nothing prevents re-adding a schedule as long as it doesn't exceed `MaxVestingSchedules`.

### Recommendation
Do not let `payout`'s success depend on an externally-controllable precondition (an arbitrary third party's ability to attach a vesting schedule to the victim). Options: remove the `VestingScheduleExists` check from `payout` (the pallet already computes and applies its own vesting schedule to `who` right after the transfer, so a pre-existing external schedule should be merged/handled rather than treated as a fatal, unrecoverable error), or have `payout` account for and merge with any pre-existing vesting schedule instead of failing, or restrict who is allowed to call `vested_transfer` on an account that is mid-flight in the `Purchase` pallet (e.g., via a filter/hook), or provide an admin/`ValidityOrigin`-gated recovery extrinsic to clear an externally injected vesting schedule for a `Purchase`-tracked account before payout.

### Proof of Concept
Rust unit test (in `polkadot/runtime/common/src/purchase/tests.rs` style, using the pallet's mock runtime):
1. Set up mock with `ValidityOrigin` creating account `who` via `create_account`, then `update_validity_status(who, ValidLow)` and `update_balance(who, free, locked, vat)`.
2. As an unrelated, unprivileged account `attacker` (not `PaymentAccount`, not `ValidityOrigin`), call the mock's vesting trait directly through an extrinsic-equivalent (`<Test as Config>::VestingSchedule::add_vesting_schedule(&who, locked, per_block, start)` simulated via `pallet_vesting::vested_transfer` in a full-runtime integration test) targeting `who`.
3. Call `Purchase::payout(RawOrigin::Signed(payment_account).into(), who)`.
4. Assert `Err(Error::<Test>::VestingScheduleExists)`.
5. Advance blocks to just before full vesting and repeat `payout`; assert it still fails.
6. Show no extrinsic in the `purchase` pallet can clear this state for `who` other than waiting out the (attacker-chosen, arbitrarily long) vesting duration and then calling `vest`/`vest_other`, demonstrating the practical permanence of the freeze.

	fn vesting_balance(who: &T::AccountId) -> Option<BalanceOf<T>> {
		if let Some(v) = Vesting::<T>::get(who) {
			let now = T::BlockNumberProvider::current_block_number();
			let total_locked_now = v.iter().fold(Zero::zero(), |total, schedule| {
				schedule.locked_at::<T::BlockNumberToBalance>(now).saturating_add(total)
			});
			Some(T::Currency::free_balance(who).min(total_locked_now))
		} else {
			None
		}
	}
