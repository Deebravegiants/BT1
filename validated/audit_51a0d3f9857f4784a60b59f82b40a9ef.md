### Title
Withdraw can permanently revert for legitimate non-zero LP redemptions due to floor-rounding of `coin_amount`/`pc_amount` to zero - (File: `program/src/processor.rs`)

### Summary
`Processor::process_withdraw` computes the coin/pc amounts owed to an LP holder by floor-dividing `withdraw.amount * total_token_without_take_pnl / amm.lp_amount`, then unconditionally reverts the whole instruction if either result is `0`, even though the caller supplied a valid non-zero `withdraw.amount` backed by real LP token holdings. This mirrors the exact bug class from the referenced report: a proportional/ratio-based conversion that legitimately returns `0` for a non-zero input causes the entire redemption to revert, with no way for the caller to work around it.

Because `coin_amount = floor(withdraw.amount * total_coin_without_take_pnl / amm.lp_amount)` and `pc_amount = floor(withdraw.amount * total_pc_without_take_pnl / amm.lp_amount)` are two independent proportional conversions against the *same* `withdraw.amount`/`amm.lp_amount` ratio but against reserves that can have very different magnitudes (different decimals, different token prices, or one side heavily reduced by prior `withdrawpnl`/`calc_take_pnl` extraction), it is entirely possible for one side to floor to `0` while the other is non-zero. When that happens the transaction reverts with `AmmError::InvalidInput`, exactly as in the reported `WstEth.withdraw()` case where `unwrap()`/`getPooledEthByShares()` floors to zero for a non-zero share amount.

The pool also forbids draining `amm.lp_amount` to zero: [4](#0-3) 

so an LP holder can never withdraw more than `amm.lp_amount - 1` in a single call. If a holder's proportional share is small relative to `amm.lp_amount` for one of the two reserves (e.g. because the reserve for the low-value/low-decimal side has been drawn down through repeated `withdrawpnl` calls, or the coin/pc reserves differ by orders of magnitude due to decimals or price), then even withdrawing their full allowed balance can floor one leg to `0`, and the entire withdrawal reverts. Unlike a swap, there is no way to split or resize the request to fix the ratio — the ratio is fixed by pool state (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`, `amm.lp_amount`), all of which are outside the caller's control.

### Impact Explanation
An LP holder whose position ends up in this ratio "dead zone" cannot redeem any of their LP tokens — every `Withdraw` call for any amount up to the maximum allowed will revert with `InvalidInput`, since decreasing `withdraw.amount` only shrinks both outputs further toward zero. This is a permanent freeze of that user's LP position (their share of pool funds) until pool-wide state changes (e.g., another depositor increases reserves relative to `amm.lp_amount`), which the trapped user has no control over. This matches the "permanent freezing of user or LP funds" impact class.

### Likelihood Explanation
This condition becomes more likely as `withdrawpnl` (owner-only PnL extraction) reduces `total_pc_without_take_pnl`/`total_coin_without_take_pnl` relative to outstanding `amm.lp_amount`, or when a pool's two mints have very different decimals/price magnitudes so one side's per-LP-unit value is extremely small. It is a normal, unprivileged interaction (`Withdraw`) reachable by any LP holder submitting a single transaction with their own LP token account and no special accounts.

### Recommendation
Do not hard-fail the whole withdrawal when only one of `coin_amount`/`pc_amount` floors to zero while `withdraw.amount > 0` and the corresponding reserve is non-zero. Instead:
- Round in favor of the protocol only for the affected leg (e.g. skip the zero-value transfer for that token rather than aborting), or
- Enforce a minimum `withdraw.amount` per LP unit ratio at withdraw time so users can always increase the amount, and clearly document/queryable minimum viable LP withdrawal size, or
- Recompute using higher precision (e.g. normalize both reserves before the pool-share division, matching the `normalize_decimal_v2` approach already used for pnl accounting) so small-decimal tokens don't floor to zero prematurely.

### Proof of Concept
1. Pool has `coin_decimals = 9`, `pc_decimals = 0` (or any large decimal skew), and, over time, repeated `withdrawpnl` calls by the `pnl_owner` reduce `total_pc_without_take_pnl` (see `process_withdrawpnl`, `program/src/processor.rs:1376-1537`) to a small value while `amm.lp_amount` stays large.
2. An LP holder calls `Withdraw` with `withdraw.amount` equal to their full balance (constrained to `< amm.lp_amount` by the `NotAllowZeroLP` check at `program/src/processor.rs:1716-1718`).
3. `InvariantPool::exchange_pool_to_token` (`program/src/math.rs:434-455`) computes `pc_amount = floor(withdraw.amount * total_pc_without_take_pnl / amm.lp_amount) == 0` because the holder's proportional pc share rounds down to zero, while `coin_amount` may be non-zero.
4. `program/src/processor.rs:1775-1777` reverts the entire instruction with `AmmError::InvalidInput`.
5. The holder cannot construct any `withdraw.amount` (bounded above by `amm.lp_amount - 1`) that avoids this, so their LP position becomes permanently unwithdrawable until unrelated pool activity changes the ratio.

    /// Exchange rate
    pub fn exchange_pool_to_token(
        &self,
        token_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
