### Title
Empty-string `icon` in token update silently no-ops `storeIcons`, leaving stale icon persisted - (adapters/storage-icons-browser/src/icons-storage.js)

### Summary
`storeIcons` branches on `if (icon) {...} else if (isNull(icon)) {...}`, which treats an empty string (`''`) as neither a store-request nor a delete-request. A remote token-list/update entry with `icon: ''` for a previously-icon'd `assetName` therefore causes the icon store/delete logic to be skipped entirely, leaving the old icon bytes persisted under that asset name even though the token record itself is treated as updated.

### Finding Description
In `adapters/storage-icons-browser/src/icons-storage.js`:
```
storeIcons = async (tokens) => {
  return Promise.all(
    tokens.map(async (token) => {
      const { icon, ...rest } = token
      if (isUndefined(icon)) return rest
      if (icon) {
        await this.#storeIcon(token)
      } else if (isNull(icon)) {
        await this.#deleteIcon(token)
      }
      return token
    })
  )
}
``` [1](#0-0) 
The same falsy/`isNull` branching pattern exists in `adapters/storage-icons-mobile/src/icons-storage.js`: [2](#0-1) 

`storeIcons` is invoked by `AssetsModule#storeIcons` from `#fetchUpdates`, which is fed directly by validated/normalized data coming from the remote Custom Token Registry (`this.#fetch('updates', ...)`): [3](#0-2) [4](#0-3) 

The three-state contract (`undefined` = no change, `null` = delete, truthy string = store) does not define a fourth state (`''`). Since `''` is falsy, `if (icon)` is `false`; and `isNull('')` is also `false`, so neither `#storeIcon` nor `#deleteIcon` executes. The function returns `token` unchanged and no exception/log is raised, so the code path is a silent no-op. `getIcon(assetName)` will keep returning the previously stored SVG for that asset name.

Whether an attacker-controlled remote CTR response can actually reach this code with `icon: ''` depends on upstream schema validation performed by `@exodus/asset-schema-validation` (`isValidCustomToken`/`validateCustomToken`) in `#fetchUpdates`: [5](#0-4) 
That package is an external dependency and its schema (in particular whether it enforces `minLength: 1` on `icon` or otherwise rejects empty strings) is not present in this repository's index, so it cannot be confirmed from this codebase whether empty-string icons are filtered out before reaching `storeIcons`.

### Impact Explanation
If reachable, the practical effect is that an asset's icon can become "stuck" showing a previous (potentially attacker-controlled, e.g., previously fetched from an attacker-influenced CTR response) icon even though the token entry has otherwise been updated. This is limited to UI-level asset-icon staleness/spoofing (asset-identity confusion) — it does not by itself grant signing capability, secret disclosure, auth bypass, or account/origin confusion, so it does not meet the "critical wallet compromise" bar described in the rules; it is a UI/display integrity issue at most.

### Likelihood Explanation
Feasibility hinges entirely on an unverified precondition: that the CTR schema validation upstream (`isValidCustomToken`) permits `icon: ''` to pass through to `storeIcons`. This could not be confirmed because `@exodus/asset-schema-validation` is an external package not present in this repo's index. Without confirming that the empty string survives validation, the exploit chain from "unprivileged attacker" to "silent no-op in storeIcons" is unproven from the available code.

### Recommendation
Regardless of upstream validation, harden `storeIcons` to treat empty string explicitly (e.g., `if (icon) {...} else if (isNull(icon) || icon === '') {...}` treating both as delete, or `if (isUndefined(icon)) return rest; if (icon) await this.#storeIcon(token); else await this.#deleteIcon(token)`), so there is no silently-ignored input state, in both `adapters/storage-icons-browser/src/icons-storage.js` and `adapters/storage-icons-mobile/src/icons-storage.js`.

### Proof of Concept
Unit test against `adapters/storage-icons-browser/src/icons-storage.js`:
1. `await iconsStorageModule.storeIcons([{ name: 'token', icon: validGzippedSvgBase64 }])`
2. `expect(await iconsStorageModule.getIcon('token')).toEqual(expectedSvg)`
3. `await iconsStorageModule.storeIcons([{ name: 'token', icon: '' }])`
4. Assert intended behavior (e.g., `getIcon('token')` returns `undefined`/`null` after an intended clear) — currently it will still return the stale `expectedSvg`, demonstrating the no-op.

Note: this PoC verifies the code-level logic bug in `icons-storage.js` in isolation; it does not by itself confirm end-to-end reachability from an unprivileged remote attacker, since that requires confirming `@exodus/asset-schema-validation` permits `icon: ''` through `#fetchUpdates`, which could not be verified in this codebase.
