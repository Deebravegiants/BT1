## Title
Unrestricted, unauthenticated `CallDispatcher.dispatch()` allows any account to drain funds and outstanding approvals held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, unprivileged-callable contract used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2` and `ExtrinsicIntents` to execute arbitrary user-supplied `Call[]` batches during token minting/unlocking and order predispatch/postdispatch. Its `dispatch()` function performs no validation of the caller and only a minimal `extcodesize` check on the call target — mirroring the "lack of validation for action targets" bug class from the external report, but compounded by a total absence of access control on who may invoke it.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` is declared `external` with no modifier restricting the caller: [1](#0-0) 

The only check performed on each `Call.to` target is that it has code (`extcodesize(to) != 0`); there is no allowlist, no restriction to a specific caller (e.g. `onlyHFT`/`onlyGateway`), and no verification that the call originated from a legitimate bridging/intents flow: [2](#0-1) 

The same contract accepts native ETH unconditionally via a public `receive()`: [3](#0-2) 

`HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`ExtrinsicIntents` all temporarily route assets (minted tokens, unlocked/unwrapped tokens, escrowed swap inputs/outputs) through this exact dispatcher instance before sweeping residual balances back: [4](#0-3) [5](#0-4) 

Because `dispatch()` has no caller restriction, any unprivileged account can invoke it directly — completely bypassing `IHyperFungibleToken`/`IntentGatewayV2` — with an attacker-chosen `Call[]`. This lets an attacker: (1) sweep any native ETH balance sitting on the `CallDispatcher` at the time of the call (e.g., dust from an in-flight predispatch/postdispatch sequence, stray direct transfers, or ETH left after a partial/failed sweep), and (2) exploit any outstanding ERC20 approval the dispatcher previously granted to a router/spender (the documentation itself flags this as a live risk, recommending exact rather than unlimited approvals) by calling `transferFrom` through that approved spender, or directly transferring out any ERC20 balance currently held by the dispatcher.

### Impact Explanation
Any funds or lingering approvals held even momentarily by the shared `CallDispatcher` — used by every deployment of `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` on a chain — can be stolen by an arbitrary, unprivileged third party, since `dispatch()` performs no caller authentication at all. This is a direct theft-of-funds vector reachable from a single unprivileged transaction, matching the report's "unsafe/unintended target" bug class but is strictly worse because the entry point itself has zero access control.

### Likelihood Explanation
`dispatch()` is a plain `external` function with no guard, so exploitation requires nothing beyond crafting a `Call[]` and calling the dispatcher directly — no proof, consensus interaction, or governance is needed. The trigger condition (residual balance/approval on the dispatcher) is created routinely by the very apps that use it (predispatch/postdispatch flows, mint-then-execute flows), making this reachable in normal operation, not just a contrived edge case.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a configured set of authorized callers (e.g., an `onlyAuthorized` modifier checking `msg.sender` against the registered `HyperFungibleToken`/`IntentGatewayV2` instances), and/or deploy per-app or ephemeral dispatcher instances so no shared, permanently-deployed contract can accumulate exploitable residual balances or approvals. Additionally, ensure token approvals granted within `Call[]` batches are revoked or use exact amounts as already documented, and audit/sweep logic to guarantee no dust window is exploitable between the execution and sweep-back calls.

### Proof of Concept
1. Observe or induce a state where `CallDispatcher` holds a residual native ETH balance or ERC20 tokens/approval — e.g., a user sends ETH directly to the publicly payable `CallDispatcher` address, or a prior `HyperFungibleToken.onAccept`/`IntentGatewayV2.placeOrder` predispatch call leaves dust before the sweep-back `dispatch()` call executes.
2. As an arbitrary unprivileged account, call `CallDispatcher.dispatch(abi.encode(calls))` directly (not through `HyperFungibleToken` or `IntentGatewayV2`) with `calls = [Call({ to: attackerControlledOrTokenContract, value: <dispatcher's ETH balance>, data: <transfer to attacker> })]`.
3. Since `dispatch()` performs no caller check, the call executes with `msg.sender == CallDispatcher`, transferring the dispatcher's ETH/token balance to the attacker, or spending residual ERC20 approvals via `transferFrom`.

```text
    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
