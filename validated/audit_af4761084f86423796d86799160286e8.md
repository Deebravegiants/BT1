### Title
Unbounded token array in `WithdrawalRequest` allows gas-exhaustion permanent freezing of escrowed intent funds - (File: `sdk/packages/core/contracts/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` / `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`)

### Summary
`Order.inputs` and `WithdrawalRequest.tokens` are unbounded `TokenInfo[]` arrays with no on-chain size cap. The order placer fully controls the length of `inputs` at `placeOrder` time, and this length flows unchanged into the `WithdrawalRequest.tokens` array carried in the cross-chain `RedeemEscrow`/`RefundEscrow` message that later triggers `_withdraw`/`withdraw`. This is structurally the same bug class as the Moloch `_ragequit` unbounded-token-loop issue: an attacker can inflate the array to a size whose processing exceeds the destination chain's block gas limit, permanently freezing the escrowed funds since the only path to release them is this same unbounded loop.

### Finding Description
In `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`, `Order.inputs` is a `TokenInfo[]` with no length restriction: [1](#0-0) 

`placeOrder` is externally callable by anyone with an arbitrary `order.inputs` array (an unprivileged message dispatcher — the order placer): [2](#0-1) 

When the order is later filled or refunded, the resulting `WithdrawalRequest` (whose `tokens` array is derived from the order's escrowed tokens/inputs) is dispatched cross-chain and delivered via `onAccept`, and processed by `_withdraw` (main EVM implementation) / `withdraw` (Tron implementation), both of which iterate the full length of the token array with no bound: [3](#0-2) [4](#0-3) 

Each loop iteration performs a storage read/write on `_orders[body.commitment][token]` plus an external `safeTransfer`/low-level `call` — the same class of per-item state-and-external-call cost that made Moloch's `_ragequit` gas-unbounded. There is no `MAX_TOKEN_...` constant, no cap on `Order.inputs.length`, and no cap enforced when the escrow-release `WithdrawalRequest` is constructed and dispatched cross-chain.

### Impact Explanation
This is reachable from a single unprivileged `placeOrder` call: an attacker creates an order with an oversized `inputs`/output-token array (bounded only by calldata size and the source chain's gas limit for `placeOrder` itself, which is much cheaper per token than the destination-side `_withdraw`/`withdraw` loop with external transfers). Once escrowed, the only code path capable of releasing (or refunding) those funds is `_withdraw`/`withdraw`, invoked from a relayed Hyperbridge message. If the number of tokens is large enough that the loop's gas cost (storage writes + external token transfer per token) exceeds the destination chain's block gas limit, the delivery transaction can never succeed, and the escrowed funds become permanently frozen — matching the report's "if the number of tokens is too big ... all funds will be blocked forever." This is a concrete freezing-of-funds vulnerability against the intents escrow, one of the explicitly in-scope surfaces.

### Likelihood Explanation
Likelihood is realistic but requires an attacker to place a specially crafted order with an oversized token array and fund/escrow it (paying gas and any escrowed amounts, which can be trivial/dust amounts per token). Because `placeOrder` has no explicit limit on `order.inputs.length` (or the output token list feeding the withdrawal), and gas costs for `SSTORE` + external transfer calls scale linearly and are significantly more expensive than reading/decoding on the source side, the number of tokens needed to hit the destination block gas limit is within reach of a single crafted order and calldata within reasonable size limits.

### Recommendation
Add an explicit maximum on the number of distinct input/output tokens allowed per `Order` (validated in `placeOrder`/`fillOrder`), mirroring the referenced Moloch mitigation of separate limits for "active" vs "processed" counts. Enforce the same cap wherever a `WithdrawalRequest.tokens` array is constructed for cross-chain dispatch, so a malicious placer cannot construct an order whose eventual redemption/refund loop cannot fit within any destination chain's block gas limit.

### Proof of Concept
1. Call `placeOrder` with `order.inputs` containing e.g. 500–1000+ distinct dust-amount `TokenInfo` entries (whitelisted/real ERC20 addresses, minimal amounts each) — no length check rejects this in `placeOrder`/`fillOrder`.
2. The order is escrowed; per-token entries accumulate in `_orders[commitment][token]`.
3. On fill or timeout, a `WithdrawalRequest` carrying that same token list is dispatched via Hyperbridge and delivered through `onAccept` → `_withdraw`/`withdraw`.
4. The destination transaction attempting `handlePostRequests`/`onAccept` must execute the full loop (N `SSTORE`s + N external token `transfer` calls) in a single transaction; once N is large enough, gas required exceeds the destination chain's block gas limit and the transaction can never be mined, permanently locking the escrowed tokens with no alternative release path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
