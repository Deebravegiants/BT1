### Title
Emporium min-proof path lets an unprivileged attacker drain any ERC20/ETH balance held by the Emporium contract via unconstrained self-executed ops - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` — the circuit `MainEVMCircuitMin` itself only proves `message == Poseidon(messageSeed)` with an attacker-chosen private `messageSeed`. This lets an unprivileged attacker generate a trivially valid proof with no root, nullifier, or amount constraints, then drive `EmporiumUpgradeable.runAction` with an `EmporiumStack{signerAddress: address(0)}` whose `ops` array is executed against arbitrary endpoints, while every balance-accounting loop in both `Hinkal.transact` and `runAction` iterates the (attacker-forced) empty `erc20TokenAddresses` array and enforces nothing.

### Finding Description
The broken equality is: *assets Emporium can move in a transaction* == *assets accounted for in `balancesBefore`/`balancesAfter` (and the top-level `oldBalances`/`newBalances` in `Hinkal.transact`)*.

Path:
1. `HinkalHelper.dimensionsCheck` only requires `erc20TokenAddresses.length == dimensions.tokenNumber` etc. — it is fully satisfiable with `tokenNumber = 0` and all associated arrays empty (`amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`, `outCommitments`, `encryptedOutputs` all `[]`). [1](#0-0) 
2. `CircomDataBuilder.formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and calls `formInputEmporiumMin`, which builds public input containing only `emporiumMessage`, `timeStamp`, `calldataHash`. [2](#0-1) 
3. The corresponding circuit, `MainEVMCircuitMin`, only proves `message === Poseidon(messageSeed)` from a fully attacker-known private `messageSeed` — no UTXO ownership, no root, no nullifier, no amount is proven. [3](#0-2) 
4. `Hinkal.transact` calls `_externalTransact`, which for `erc20TokenAddresses.length == 0` builds an empty `deltaAmountChanges` array and calls `EmporiumUpgradeable.runAction` with it. [4](#0-3) 
5. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed over the empty `erc20TokenAddresses` array (i.e., track nothing), `verifyWallet` short-circuits with no signature check at all when `stack.signerAddress == address(0)` (it only marks the message used), and the ops loop then performs arbitrary `op.endpoint.call{value: op.value}(op.callData)` calls from the Emporium contract's own identity — the only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors, not the target contract. [5](#0-4) [6](#0-5) 
6. The post-loop accounting (`balanceChange`, `handleOut`, UTXO creation) and the top-level `Hinkal.transact` balance/slippage checks both iterate `circomData.erc20TokenAddresses`, which is forced empty by the attacker to reach this code path — so any token moved by an op that is *not* listed in that (empty) array is never checked, never slippage-gated, and never turned into (or debited from) a UTXO. [7](#0-6) [8](#0-7) 

Attacker's exact call: `Hinkal.transact(a, b, c, dimensions={tokenNumber:0,...}, circomData)` where `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: <TOKEN_HELD_BY_EMPORIUM>, invokeWallet:false, value:0, callData: transfer(attacker, balance)}]})`, and a locally generated Min-circuit proof for an attacker-chosen `messageSeed`.

Existing guards that fail to prevent this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency, which is trivially satisfied by all-empty arrays; `verifyProof` succeeds because the Min circuit's public inputs never encode `erc20TokenAddresses`, `amountChanges`, nullifiers or roots; `rootHashExists` is checked against `circomData.rootHashHinkal` but that value is never bound to anything meaningful for the Min path since the circuit doesn't constrain it either; the balance-diff loops in `Hinkal.transact` and `EmporiumUpgradeable.runAction` are keyed exclusively off `circomData.erc20TokenAddresses`, which the attacker controls and sets to empty.

### Impact Explanation
This is a Critical vulnerability: any funds currently held by the deployed `EmporiumUpgradeable` contract (e.g., ETH or ERC20 balances left "parked" there between legs of a multi-step composed operation, or any residual balances belonging to any user) can be transferred out by an unprivileged attacker in a single transaction with no accounting, no signature requirement (`signerAddress == 0`), and no real zero-knowledge proof of ownership. This is direct theft of in-flight/parked user or protocol funds, repeatable for any balance the Emporium contract holds at the time of attack.

### Likelihood Explanation
Preconditions: the Emporium external action must be registered (`Hinkal.registerExternalAction`) and a verifier for the `(tokenNumber=0, nullifierAmount, outputAmount, HINKAL_EMPORIUM_ACTION_ID)` dimension tuple must be registered — a `mainEVMCircuitMin0v4` verifier contract exists in the repo, indicating this path is intended to be live. The attacker only needs: (a) ability to call `Hinkal.transact` (any EOA), (b) ability to generate a proof for the trivial Min circuit locally (no secrets required beyond a self-chosen `messageSeed`), and (c) any balance sitting in the Emporium contract at attack time (which arises naturally from its intended multi-leg/park-and-continue design). Cost is a single transaction; feasibility is high and fully deterministic; the attack is repeatable every time Emporium holds a balance.

### Recommendation
The Min-circuit/empty-array path must not be allowed to execute arbitrary `stack.ops` with no balance accounting. Specifically:
- Require `stack.signerAddress != address(0)` (i.e., a valid EIP-712 signature) whenever the Min proof path is used, or disallow the Min path entirely for stateless ops (`invokeWallet == false`).
- Track and enforce full balance conservation across *every* token the ops loop could touch, not just `circomData.erc20TokenAddresses` — e.g., by requiring `erc20TokenAddresses` to explicitly list every token/ETH balance the intended ops can affect, and rejecting the Min/empty-array path for any op whose target is not previously authorized/allow-listed.
- Alternatively, restrict `formInputEmporiumMin`/Min-circuit usage strictly to a `cancel`-only or metadata-only action (no `ops` execution), since the circuit provides no economic guarantees.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register the Emporium external action and a verifier for `(tokenNumber=0, ..., HINKAL_EMPORIUM_ACTION_ID)` matching `MainEVMCircuitMin`.
2. Fund `EmporiumUpgradeable` with an ERC20 token balance (simulate "parked" balance from a legitimate prior multi-leg operation).
3. As attacker EOA, generate a local proof for `MainEVMCircuitMin` with an arbitrary `messageSeed`, compute `message = Poseidon(messageSeed)`.
4. Build `circomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: token, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker, parkedBalance))}], maxFee:0, deadline: block.timestamp})`, matching `dimensions.tokenNumber = 0`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker.
6. Assert: `token.balanceOf(emporium)` before == `parkedBalance`; after == `0`; `token.balanceOf(attacker)` increased by `parkedBalance`; and that `balancesBefore == balancesAfter == []` inside `runAction` (i.e., the accounting arrays never observed the transfer) — demonstrating the equality *assets moved == assets accounted* is violated.
