## Finding: Webhook shop/topic identity not bound by the HMAC signature

### Title
Webhook Handler Trusts Unsigned `shop`/`topic` Headers While Only the Body Is HMAC-Verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` only returns the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all taken from unauthenticated HTTP headers and are never included in the signed material. `Registry.process` validates the HMAC and then dispatches the handler using these unverified header values, exactly mirroring the reported bug pattern: the code enforces one invariant (HMAC over the body) but then acts on a different, unauthenticated field (`shop`) as if it had been verified together with it — breaking the intended binding `verified_bytes == acted_upon_identity`.

### Finding Description
- `HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`: [1](#0-0) 
- For webhooks, `to_signable_string` returns only `@raw_body`; the `shop`, `topic`, `api_version`, and `webhook_id` accessors read straight from HTTP headers and are not part of the signed payload: [2](#0-1) 
- `Registry.process` validates only the HMAC/body pairing, then immediately trusts `request.shop` and `request.topic` (both unsigned) to route and label the webhook payload delivered to the app's handler: [3](#0-2) 

Because the signature only binds the body bytes to the app's shared `api_secret_key` — not to the shop the webhook is claimed to be from — any request bearing a *valid (body, hmac) pair for the app* (which is trivially available to any shop that has this same app legitimately installed, since Shopify computes and delivers that pair to them) can be replayed to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a different, victim shop of the same app: [4](#0-3) 

This is the direct analog of the reported issue: instead of using the "well function" (i.e., the actual signed invariant — the raw body under the shared secret) to derive the trusted identity, the code separately trusts an out-of-band field (`shop` header) for tenant attribution.

### Impact Explanation
An attacker who legitimately installs the vulnerable app on their own shop can capture genuine `(body, hmac)` pairs Shopify sends them, then relabel the shop header and replay the webhook to make the app process attacker-controlled body content under a victim tenant's identity. Any app logic keyed off `WebhookMetadata#shop` (e.g., "update this shop's local record using the payload") can be poisoned this way — a cross-tenant data injection/confusion impact.

### Likelihood Explanation
Requires only that the attacker have the app installed on at least one shop (an ordinary, unprivileged action for any Shopify merchant), and that they can reach the app's public webhook endpoint. No `api_secret_key`, access token, or other privileged credential needs to be leaked — the attacker only replays a signature that Shopify itself already handed them for their own shop's webhook traffic.

### Recommendation
Include `shop`, `topic`, and other routing-critical identifiers in the signed payload verification (Shopify's own webhook HMAC only ever covers the body, so the fix must be in the consuming app/gem layer): bind the `shop` value used for dispatch to a source that cannot be spoofed independently of the signature — e.g., cross-check the header `shop` against the shop associated with the specific webhook subscription/session that was registered, rather than trusting the header value alone in `Registry.process`.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger a webhook event so Shopify sends a POST with a valid `X-Shopify-Hmac-Sha256` for a chosen body and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture this `(raw_body, hmac)` pair.
3. Replay the same POST to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the secret [5](#0-4) ; `Registry.process` then calls the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body [6](#0-5) , causing the app to act on victim-tenant data using attacker-supplied content.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
