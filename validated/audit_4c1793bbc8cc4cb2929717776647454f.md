## #Vulnerability found for this question.

### Title
Solvers can redeem full escrow for free on cross-chain "phantom" orders with a zero-required output leg - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2`/`ExtrinsicIntents._fillCrossChain` enforces `solverAmount >= totalRequired` per output leg, but `placeOrder` never rejects an output leg whose required amount is `0`. This zero-required-output design is intentionally used by "phantom" orders (confirmed by the pallet-side comment "the output amount is what fillers quote, so the request leaves it at zero" and the SDK's phantom-order tests), which are meant to be priced through an off-chain bidding/auction process. Because the on-chain `fillOrder` path does not special-case a zero requirement, any address can call `fillOrder` directly, satisfy the zero-required leg with `solverAmount = 0`, and since cross-chain fills are all-or-nothing, the contract still dispatches a `RedeemEscrow` message carrying the *entire* `order.inputs` array — including the real, non-zero input escrowed against that zero-priced leg — to the caller for free.

### Finding Description
`placeOrder` validates that every **input** amount is non-zero (`evm/src/apps/IntentGatewayV2.sol` lines 264, 314, 344), but places no such restriction on `order.output.assets[i].amount`. [1](#0-0) 

Phantom orders are constructed with a real, non-zero input and a deliberately zero-required output — this is documented as intentional in the coprocessor test suite: [2](#0-1) 
and mirrored in the SDK's phantom order fixtures: [3](#0-2) 

The intended flow is that solvers *quote* against this zero via an off-chain bid (`FillOptions.outputs[i].amount`), so the "market" (not `0`) determines the fill price — directly analogous to the reported auction pattern where the reserve price is set to `0` so the *community* is meant to determine the real price via bidding, yet the settlement path doesn't enforce that a real, non-zero value was actually provided.

On the cross-chain fill path, the per-leg check only rejects amounts strictly below the required amount: [4](#0-3) 

When `totalRequired == 0`, `solverAmount = 0` trivially satisfies `solverAmount < totalRequired` being false, so the check passes with the caller providing nothing. Because cross-chain fills are all-or-nothing (no partial fills), the same call still proceeds to dispatch the escrow release, and that release uses the **original, full** `order.inputs` array rather than anything scoped to what was actually paid: [5](#0-4) 

This mirrors the report's root cause precisely: the contract that settles the auction/order does not special-case the "zero bid/zero required output" outcome the same way it handles the "no bid/burn" outcome — it simply transfers value as if a legitimate price had been paid.

### Impact Explanation
Any unprivileged address (not necessarily a registered solver, not necessarily going through the intents-coprocessor bidding auction) can call `fillOrder` directly on a phantom order and claim the full escrowed input token amount corresponding to the zero-required leg without providing any value in return. This is a direct theft of escrowed user funds routed through Hyperbridge's cross-chain `RedeemEscrow` settlement message, i.e. concrete theft of funds reachable from a single transaction against `IntentGatewayV2`.

### Likelihood Explanation
Phantom orders with zero-required output legs are a first-class, intentionally-supported order shape (per the coprocessor and SDK code), not an edge case that requires misconfiguration. Any party monitoring `OrderPlaced` events for such orders can front-run the legitimate solver-bidding flow and call `fillOrder` on-chain directly with a `0` output for that leg, since nothing on-chain requires the caller to have gone through bid selection/simulation.

### Recommendation
- Require the caller to actually provide the market-determined amount for phantom/zero-required legs — e.g., reject `fillOrder` calls whose `solverAmount == 0` unless a corresponding non-zero minimum has been established via the `select()`/session-bound bid mechanism.
- Alternatively, scope the `RedeemEscrow` body to only the inputs actually paid for (proportional/leg-aware), rather than always redeeming the full, original `order.inputs`, so a `0`-output leg cannot pull real escrowed value.
- Disallow placing orders (or at least cross-chain orders) with any output leg amount of `0` unless routed exclusively through a path that cryptographically binds the fill to a signed, non-zero bid before `fillOrder` can execute.

### Proof of Concept
1. A user places a cross-chain phantom-style order via `placeOrder`: `inputs = [{token: USDC, amount: 5_000_000}]`, `output.assets = [{token: USDT, amount: 0}]`.
2. Any address (not necessarily a registered/verified solver) calls `fillOrder(order, options)` on the destination chain with `options.outputs[0] = {token: USDT, amount: 0}`.
3. `_fillCrossChain`'s check `solverAmount < totalRequired` evaluates `0 < 0 == false`, so no revert occurs and no output tokens are transferred to the beneficiary.
4. Execution proceeds to dispatch `RedeemEscrow` with `order.inputs` (the full 5,000,000 USDC), which is delivered back to the source chain and released to `msg.sender` — the caller has obtained the escrowed 5,000,000 USDC for paying nothing.
