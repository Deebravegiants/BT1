### Title
Webhook shop/topic identity spoofing via unauthenticated headers - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are covered by that HMAC — to route the payload to the app's tenant-specific handler logic.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For a webhook `Request`, `to_signable_string` returns only the raw HTTP body — none of the identity-bearing headers: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately hands the *unauthenticated* header-derived `shop` value to the app's webhook handler as the tenant identity for the event, alongside the (also unauthenticated) topic and webhook id: [4](#0-3) 

The identity binding that should hold is: `shop == the tenant whose secret produced this HMAC`. Because the HMAC only covers the raw body bytes and never binds the `shop-domain` (or `topic`/`webhook-id`) header, that equality is never checked. Any actor who is able to obtain one validly-HMAC-signed webhook body from the app (e.g. a merchant/tenant that has the app installed and receives its own legitimate webhooks) can replay that exact body to the app's webhook endpoint while substituting a different `shop-domain` header (and/or `topic`/`webhook-id`). `Utils::HmacValidator.validate` will still pass, because it only checks the body bytes, and the host application's handler will process the event as if it came from the spoofed tenant.

This is the same root-cause pattern as the H-4 report: a value that is *used* to make a security-relevant decision (there: liquidity feeding IV/LTV; here: `shop`/`topic` feeding tenant-scoped webhook processing) is derived from data that is not bound by the mechanism meant to guarantee its integrity (there: single-block liquidity outside the TWAP; here: headers outside the HMAC digest).

### Impact Explanation
This breaks the tenant-identity binding for a multi-tenant app: a party controlling one legitimately-signed webhook body can cause the app to attribute that event to an arbitrary `shop` (or dispatch it under an arbitrary `topic`) of the app's choosing, since the HMAC never authenticates those fields. Depending on how the host application relies on `WebhookMetadata#shop`/`#topic` (e.g., to select the tenant record to write to, delete, or the handler branch to execute), this is a cross-tenant access primitive — exactly the "cross-tenant access" impact category called out as Critical.

### Likelihood Explanation
Exploitation requires possession of at least one validly HMAC-signed webhook body for the given `api_secret_key` (obtainable by any tenant that has the app installed, since Shopify sends them real webhooks), plus the ability to POST arbitrary headers to the app's webhook endpoint — both are within reach of an unprivileged, low-trust actor (a legitimate low-privilege merchant of a multi-tenant app), with no need for `api_secret_key`, access tokens, or social engineering.

### Recommendation
Include the security-relevant identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string, or otherwise cryptographically bind them to the body before `Utils::HmacValidator.validate` is trusted to authorize header-derived routing decisions in `Registry.process`.

### Proof of Concept
1. Attacker owns/operates Shop A, which has App installed; App's webhook endpoint receives a legitimate webhook for topic `orders/create` with body `{}` (or any body attacker can reproduce), including a valid `x-shopify-hmac-sha256` computed by Shopify over that body with the app's `api_secret_key`.
2. Attacker resends the identical raw body and HMAC header to the same webhook endpoint, but changes `x-shopify-shop-domain` to Shop B's domain (a shop the attacker does not own) and/or changes `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (`lib/shopify_api/webhooks/request.rb:45-63`); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop`/`topic` values (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process/act on data attributed to Shop B despite the event actually originating from (and only provably signed for) Shop A's payload.
