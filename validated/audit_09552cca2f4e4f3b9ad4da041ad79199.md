### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` value handed to the application's webhook handler is read directly from the unauthenticated `shop-domain` header. This breaks the equality "shop authenticated by HMAC == shop passed to the tenant-scoped handler," letting a request with a valid (body, HMAC) pair be replayed with an attacker-chosen `shop-domain` header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is read straight from the `shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed material: [2](#0-1) .

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `validate_signature` and compares `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` against the received HMAC — again, using only the body: [3](#0-2) . Immediately after this check passes, `process` builds `WebhookMetadata` using `request.shop`, the unauthenticated header value, and hands it to the app's handler: [4](#0-3) . The handler interface (`WebhookHandler#handle`) receives this `shop` field as the tenant identifier for the webhook payload: [5](#0-4) .

Because a single app `client_secret` is shared across every shop that installs the app, any legitimate webhook delivery to the app (e.g., one triggered by the attacker's own store, or one the attacker otherwise obtains with a valid body/HMAC pair) produces a `(raw_body, hmac)` pair that is valid for *any* shop, since the HMAC computation never binds the signature to the shop domain. An attacker who controls or has access to such a legitimate delivery can replay the exact same body and HMAC to the app's webhook endpoint while substituting a victim's `shop-domain` header. `Registry.process` will accept the HMAC (it never changed) and dispatch the payload to the handler labeled as coming from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the authentication check (HMAC over body) validates that Shopify's servers produced this body, but the tenant attribution (`shop`) used downstream by the host application to select session state, access tokens, or shop-scoped records is taken from an unauthenticated header. Any consuming application that uses `data.shop` from `WebhookMetadata` to look up per-shop session/access-token data or to write shop-scoped records (the documented and expected usage pattern) can be made to associate attacker-supplied webhook content with a victim shop, resulting in cross-tenant data/state corruption without needing the victim's credentials.

### Likelihood Explanation
The attacker needs only the ability to trigger, capture, or otherwise obtain a single legitimate webhook delivery for this app (e.g., by installing the app on their own free/trial shop and generating an event) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint — both are unprivileged-internet-user capabilities requiring no leaked secrets, tokens, or elevated access. This makes the analog readily reachable through this gem's own `Registry.process` / `HmacValidator.validate` code path.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values as part of the signable material used for HMAC verification, or otherwise cryptographically bind the shop domain to the signature before it is trusted as a tenant identifier. At minimum, `Utils::HmacValidator` should not be the sole gate for trusting `request.shop`; the gem should document/enforce that `shop` cannot be relied upon for tenant isolation unless bound to the signature.

### Proof of Concept
1. Install the target app (using the shared `client_secret`) on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) on that shop; Shopify delivers a POST with headers `x-shopify-hmac-sha256: <valid hmac over raw body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture the raw body and HMAC header from this request.
4. Replay the identical raw body and HMAC to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because the body is unchanged, then dispatches `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` to the app's handler, causing attacker-controlled data to be processed as if it belonged to `victim.myshopify.com`.
