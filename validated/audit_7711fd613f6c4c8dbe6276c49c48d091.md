### Title
Crafted swap route can smuggle an unrelated token transfer into the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller swap strategies authenticate the account `caller`, then forward caller-controlled route bytes to the configured router, allowing route-selected external pool code to execute inside the same authorization tree. [1](#0-0) [2](#0-1)  If simulation records a malicious nested `token.transfer(victim, attacker, amount)` beneath the strategy invocation and the victim signs that tree, the attacker can steal unrelated wallet tokens while the swap itself still returns valid output. 

### Finding Description
`swap_collateral` accepts a `swap: Bytes` argument and authorizes `caller` before checking account ownership and withdrawing the selected collateral. [3](#0-2) [4](#0-3)  The controller then withdraws collateral into its own custody and passes the opaque route to `swap_tokens_or_passthrough`. [5](#0-4)  `swap_tokens` narrowly authorizes only `token_in.transfer(controller, configured_router, amount_in)` for the controller, but invokes the router while the user’s root `caller.require_auth()` authorization remains the transaction boundary. [2](#0-1) [1](#0-0)  Because pool/venue addresses are selected by route data rather than confined to a controller-approved set, a compatible attacker-controlled venue can request an unrelated token transfer from `caller` and have that request recorded as a child authorization.  The controller’s balance-delta checks can still pass because the malicious venue or another hop can return sufficient `token_out`, and the strategy then redeposits it and applies the normal final account-risk gate. [6](#0-5) [7](#0-6) 

### Impact Explanation
A successful attack steals user funds outside the routed collateral amount, including arbitrary unrelated tokens held by the victim’s wallet.  The stolen transfer does not need to break pool accounting, router output measurement, liquidation rules, or final solvency because it is an extra caller-authorized token movement hidden inside the strategy’s invocation tree. [8](#0-7)  This is theft of user funds, not merely poor route quality or information disclosure. 

### Likelihood Explanation
The attacker can deploy the malicious venue and supply enough output liquidity for a superficially valid route, while the victim must submit a strategy using the crafted route and sign the authorization tree containing the extra token transfer. [9](#0-8)  This mirrors the report’s crafted-page/user-interaction pattern: the victim’s signature is required, but the unexpected cross-boundary action is embedded in an authorization tree that users and clients may not decode correctly.  The issue affects every route-bearing owner-or-delegate strategy path that reaches `swap_tokens`, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [10](#0-9) 

### Recommendation
Do not execute arbitrary route-selected venue or pool contracts inside a transaction whose root invocation is authorized by the account owner. [11](#0-10)  Constrain route execution to governance-approved venue/pool addresses or immutable route manifests, and enforce that allowlist on-chain before invoking external code rather than relying on users to inspect simulated authorization trees.  Client-side mitigation should additionally reject any authorization tree containing children beyond the expected collateral/account operations, but contract-level venue admission is required to remove the boundary violation. 

### Proof of Concept
1. Victim owns a controller account with supplied `USDC` collateral and holds an unrelated wallet token `VICTIM_TOKEN`. [12](#0-11) 
2. Attacker deploys a pool-compatible contract containing `token::Client::new(&env, &VICTIM_TOKEN).transfer(&victim, &attacker, &victim_balance)` and funds the route so it can return the promised `ETH` output. 
3. Victim calls `swap_collateral(caller=victim, account_id=victim_account, current=(hub_id, USDC), amount=N, new=(hub_id, ETH), swap=crafted_route)`. [3](#0-2) 
4. The controller obtains `victim.require_auth()`, verifies account authority, withdraws `N` USDC into controller custody, authorizes only the controller-to-router input transfer, and invokes the configured router with `crafted_route`. [4](#0-3) [9](#0-8) 
5. Simulation records the venue’s unrelated `VICTIM_TOKEN.transfer(victim, attacker, victim_balance)` as a child invocation of the victim’s `swap_collateral` authorization. 
6. If the victim signs the resulting tree, the malicious transfer executes while the route still returns positive `ETH` output, so `verify_router_output` and `strategy_finalize` do not detect the theft. [6](#0-5) [7](#0-6) 
7. Final state: the victim’s account receives valid replacement collateral, but the attacker also receives the victim’s unrelated `VICTIM_TOKEN` balance.
