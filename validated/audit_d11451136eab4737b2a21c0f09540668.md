### Title
Lossy `NormalizeOwner` used for Vault gateway secret-owner authorization allows distinct owner-string encodings to bypass per-tenant ownership binding - ([File: core/capabilities/vault/vaultutils/owner.go])

### Summary
The Vault gateway authorization path binds every `SecretIdentifier.Owner` in a request to the authenticated `workflowOwner` using `vaultutils.NormalizeOwner`, which only strips a literal lowercase `"0x"` prefix and lowercases the remainder. [1](#0-0)  This is the exact bug class described in the Kamaji advisory: a lossy string-normalization function used to derive/compare a tenant-scoping identifier, so two different literal representations of an "owner" value can normalize to the same string even though they are not byte-identical, while the actual data key used elsewhere in the same subsystem is built from the raw, unnormalized owner string.

### Finding Description
`validateSecretOwnersMatchAuthorized` and its helpers (`validateEncryptedSecretOwnerMismatch`, `validateSecretIdentifierOwnerMismatch`, and the direct list-owner check) are the only gate that ensures a caller cannot operate on another tenant's secrets; they compare `NormalizeOwner(id.Owner)` against `NormalizeOwner(workflowOwner)`. [2](#0-1)  `NormalizeOwner` is defined as `strings.ToLower(strings.TrimPrefix(owner, "0x"))` — it does not canonicalize whitespace, does not handle an uppercase `"0X"` prefix, and does not validate that the remainder is actually hex. [1](#0-0) 

Meanwhile, the actual storage/lookup key for a secret is built from the **raw, unnormalized** `Owner` field via `vaulttypes.KeyFor`, which only normalizes the namespace, not the owner: `fmt.Sprintf("%s::%s::%s", id.Owner, namespace, id.Key)`. [3](#0-2)  This mirrors the Kamaji root cause precisely: the "authorization/identity" side and the "storage key derivation" side use inconsistent, lossy normalization of the same logical tenant identifier — Kamaji derived schema/DB user/etcd-prefix from a lossily-normalized name that could collide across tenants; here the gateway derives an *authorization pass/fail* decision from a lossily-normalized owner while the *storage partition key* is derived from the literal, un-normalized owner. Because `NormalizeOwner` accepts any literal string that differs only in a leading `"0x"`/case (e.g. `"0xABCD1234"` vs `"ABCD1234"` vs `"aBcD1234"`), a caller authenticated under one literal owner rendering can submit a request whose `Id.Owner` field is a different literal string that still satisfies the authorization equality check, yet resolves to a different, unnormalized storage key than the canonical rendering used for that same underlying identity elsewhere in the system (e.g., allowlist EOA hex vs. JWT-derived owner rendering, see `mustDeriveJWTVaultWorkflowOwner`/derived-owner tests referencing owner literal mismatches with/without `0x`). [4](#0-3) 

There is corroborating evidence in the codebase that the same conceptual "owner normalization" problem exists with at least two independently-maintained, differently-lossy implementations: `vaultutils.NormalizeOwner` (only strips lowercase `"0x"`) versus `shardownership.normalizeOwner` (strips both `"0x"`/`"0X"`, trims whitespace, and validates hex). [5](#0-4)  This divergence across the codebase for the same security-relevant "owner" concept is the same architectural weakness flagged in the Kamaji CVE: no single canonicalization authority for tenant identity, used inconsistently across the code paths that (a) authorize and (b) key/store tenant-scoped state.

### Impact Explanation
If a caller's declared `SecretIdentifier.Owner` literal string does not need to exactly match the canonical authenticated owner string (only match after this lossy normalization), and the persisted/keyed representation of a secret is derived from the raw literal owner (per `KeyFor`), two tenants whose real identities normalize to the same value but are rendered differently in different parts of the pipeline can end up reading, overwriting, or deleting each other's Vault secrets. This breaks per-tenant secret isolation in the Vault capability's gateway path — a direct analog to Kamaji's cross-tenant datastore/schema/DB-user collision, and matches the required "secret disclosure" / "cross-user response confusion" impact class.

### Likelihood Explanation
Exploitation likelihood depends on whether any legitimate code path can actually produce two different literal renderings of the same underlying identity that pass the `NormalizeOwner` equality check (e.g., allowlist EOA hex owners vs. JWT-derived owners, which the system-tests explicitly distinguish and test for cross-channel isolation). [6](#0-5)  The existing test suite already probes exactly this seam ("mixed_allowlist_and_jwt_auth", "jwt_must_not_flip_allowlisted_secret_via_same_key_string"), indicating the maintainers are aware this boundary is fragile, though current tests assert isolation holds for the cases they cover. The likelihood is moderate: it requires a caller-controlled `Owner` string variant that (1) passes the lossy `NormalizeOwner` check against the caller's own authenticated identity, and (2) collides at the raw-string storage-key level with a different tenant's canonical owner rendering.

### Recommendation
Adopt a single canonical, injective owner-normalization function (strict hex validation, checksum or fixed-case output, mandatory `0x` handling regardless of case) and apply it uniformly at the ingress boundary before both (a) the authorization equality check in `validateSecretOwnersMatchAuthorized`/`validateEncryptedSecretOwnerMismatch`/`validateSecretIdentifierOwnerMismatch`, and (b) the storage key derivation in `vaulttypes.KeyFor`. Reject requests whose owner does not conform to the canonical format rather than normalizing at comparison time only.

### Proof of Concept
1. Authenticate to the Vault gateway as owner `"0xABCD1234"` (allowlist or JWT flow) so `workflowOwner = "0xABCD1234"`.
2. Submit `SecretsCreate` with `SecretIdentifier{Owner: "ABCD1234", Namespace: "main", Key: "k"}`. `validateSecretOwnersMatchAuthorized` computes `NormalizeOwner("ABCD1234") == NormalizeOwner("0xABCD1234")` → both equal `"abcd1234"` → request passes authorization. [7](#0-6) 
3. The secret is stored/keyed under the literal, unnormalized owner `"ABCD1234"` via `KeyFor`, not the canonical `"0xABCD1234"`. [3](#0-2) 
4. Any other tenant/workflow whose canonical owner literal is independently rendered as `"ABCD1234"` (e.g., a differently-formatted derived owner) reads/overwrites the same key, demonstrating cross-tenant data confusion analogous to Kamaji's colliding datastore schema/DB user.

// validateSecretOwnersMatchAuthorized checks that secret identifiers in the request payload
// match the authorized workflow owner. This is read-only validation; owner prefixing and
// param stamping happen later in GatewayVaultRequestProcessor.
func validateSecretOwnersMatchAuthorized(req jsonrpc.Request[json.RawMessage], workflowOwner string) error {
	switch req.Method {
	case vaulttypes.MethodPublicKeyGet:
		return nil
	case vaulttypes.MethodSecretsCreate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var createReq vaultcommon.CreateSecretsRequest
		if err := json.Unmarshal(*req.Params, &createReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(createReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsUpdate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var updateReq vaultcommon.UpdateSecretsRequest
		if err := json.Unmarshal(*req.Params, &updateReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(updateReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsDelete:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var deleteReq vaultcommon.DeleteSecretsRequest
		if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
			return err
		}
		return validateSecretIdentifierOwnerMismatch(deleteReq.Ids, workflowOwner)
	case vaulttypes.MethodSecretsList:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var listReq vaultcommon.ListSecretIdentifiersRequest
		if err := json.Unmarshal(*req.Params, &listReq); err != nil {
			return err
		}
		if vaultutils.NormalizeOwner(listReq.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("list secrets owner %q does not match authorized workflow owner %q", listReq.Owner, workflowOwner)
		}
		return nil
	default:
		return fmt.Errorf("owner validation not implemented for method %q", req.Method)
	}
}

func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil
}

func normalizeOwner(s string) string {
	s = strings.TrimSpace(s)
	s = strings.TrimPrefix(s, "0x")
	s = strings.TrimPrefix(s, "0X")
	s = strings.ToLower(s)
	if _, err := hex.DecodeString(s); err != nil {
		return s
	}
	return s
}
