### Title
Retroactive `challengePeriod` reduction via `updateHostParams` immediately unlocks previously-recorded state commitments before their originally-promised fraud-proof window - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost` stores a single, global `challengePeriod` in `_hostParams` and checks it against `_stateCommitmentsUpdateTime[...]` at the moment a message is verified, not at the moment the state commitment was recorded. When cross-chain governance calls `updateHostParams`/`updateHostParamsInternal` to shrink `challengePeriod`, every state commitment already stored under the *old*, longer challenge period is retroactively subjected to the *new*, shorter one. This mirrors the reported Aloe issue exactly: a global rate/config parameter changes and prior "principal" (here, already-anchored but not-yet-finalized state commitments) is settled under the new rule instead of the rule that was in force when it was created.

### Finding Description
`updateHostParamsInternal` writes the new `challengePeriod` directly into storage with no snapshotting or per-commitment recording of the challenge period that was active when each `StateMachineHeight` was committed: [1](#0-0) 

`HandlerV2` then reads the *current* `challengePeriod` via `host.challengePeriod()` and compares it against `block.timestamp - host.stateMachineCommitmentUpdateTime(height)` for every message class (post requests, get responses, post/get timeouts): [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The protocol's own design intent is that the challenge period is a fixed security window fishermen rely on to detect and veto fraudulent commitments before they are usable: [6](#0-5) 

and the equivalent pallet-ismp implementation stores `challenge_period` per state-machine-id rather than mutating a single live value applied to all historical timestamps identically: [7](#0-6) 

Because `EvmHost` keeps only one mutable `challengePeriod` value in `_hostParams` and applies it uniformly to `stateMachineCommitmentUpdateTime` (recorded once, at commitment time) for every height, a governance-initiated reduction of `challengePeriod` (e.g., during a parameter re-tuning, migration, or in response to relayer complaints about latency) instantly shortens or eliminates the remaining challenge window for state commitments that were stored *before* the update — commitments that fishermen/watchers were still within their old, longer window to inspect and veto. This is directly analogous to the referenced Lender.sol bug: a mutable "rate" governing pending state is changed and then retroactively applied to state accrued under the old rate, instead of accruing/settling under the previous rule first.

### Impact Explanation
If `challengePeriod` is reduced by governance while state commitments recorded under the old (longer) period are still within their original window, a relayer can immediately submit `handlePostRequests`/`handleGetResponses`/timeout messages referencing those commitments the instant the new shorter delay is satisfied — even though fishermen had not yet exhausted the window they were promised to detect and veto fraud. Since `veto_state_commitment` is the sole on-chain defense against a fraudulent/eclipsed consensus update, shrinking the effective observation window for already-pending commitments increases the probability that a forged or byzantine state commitment (per the documented eclipse-attack threat model) is used to deliver forged messages before fishermen react, enabling forged message delivery / unsound state commitment usage and consequent fund loss in dependent applications (e.g., token bridges relying on `IHost` state proofs).

### Likelihood Explanation
This requires a legitimate governance-initiated `updateHostParams` call that reduces `challengePeriod` — a normal operational action (rebalancing security/latency tradeoffs, migrating consensus clients, etc.), not an attack by a malicious admin. Given the explicit rule set excludes malicious-governance scenarios, the realistic trigger here is a well-intentioned parameter change combined with in-flight commitments and an attacker who has already forged/eclipsed a state update and is racing the challenge window — a scenario the protocol's own documentation says the challenge period exists to prevent. Likelihood is Medium: it depends on the timing coincidence of an in-flight fraudulent commitment and a challenge-period reduction, but the reachable path (permissionless `handlePostRequests`/timeout handlers) requires only a single relayed message once the shortened window is satisfied.

### Recommendation
Snapshot the `challengePeriod` value effective at the time each `StateMachineHeight` commitment is stored (e.g., alongside `_stateCommitmentsUpdateTime`), and have `HandlerV2` compare elapsed time against that stored value rather than the live `_hostParams.challengePeriod`. Alternatively, when `updateHostParamsInternal` shortens `challengePeriod`, only apply the new value to commitments recorded after the update, preserving the original challenge window for commitments already pending — analogous to accruing under the old rate model before switching to the new one.

### Proof of Concept
1. Governance sets `challengePeriod = 7 days` at deployment.
2. A consensus proof for state machine `S` is verified and `storeStateMachineCommitment` records height `H` with `stateMachineCommitmentUpdateTime = T0` (via `HandlerV2` consensus handling, e.g. lines 156-163 shown above).
3. At `T0 + 1 hour`, a byzantine/eclipsed authority set's forged state at height `H` is under fisherman review; fishermen have until `T0 + 7 days` to call `veto_state_commitment`.
4. Governance (through `HostManager.onAccept` → `IHostManager(_params.host).updateHostParams`) legitimately reduces `challengePeriod` to `1 hour` as part of a routine parameter update: [8](#0-7) 
5. `updateHostParamsInternal` immediately overwrites `_hostParams.challengePeriod = 1 hour` with no adjustment to already-stored `stateMachineCommitmentUpdateTime` values.
6. At `T0 + 2 hours` (long before the originally-promised `T0 + 7 days` fisherman review window), a relayer calls `handlePostRequests` with a proof anchored at height `H`; `HandlerV2` computes `delay = 2h`, reads the new `challengePeriod = 1h`, and passes the check (`challengePeriod > delay` is false), dispatching the request even though the state commitment had not survived its originally-guaranteed observation window.
7. If height `H`'s commitment was fraudulent, the forged request is now delivered to a destination module before fishermen could act within the window they were told applied when the commitment was made.

        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
