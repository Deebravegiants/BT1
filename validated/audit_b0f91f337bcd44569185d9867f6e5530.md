### Title
Malicious order creator can escrow a "trap" ERC-20 as `order.inputs` to permanently block `RedeemEscrow` settlement and freeze a solver's already-delivered funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` lets any caller choose arbitrary ERC-20 contracts as `order.inputs` with no whitelist or validation [1](#0-0) . On a cross-chain fill, the solver delivers real output tokens on the destination chain first, and only afterward can redeem the escrowed `order.inputs` via a `RedeemEscrow` message processed by `IntentsBase._withdraw`, which iterates over every input token and performs an unconditional `safeTransfer` with no isolation between tokens [2](#0-1) . If any one of those tokens is a malicious contract engineered to always revert its `transfer` to the solver, the whole `_withdraw` call reverts, `EvmHost.dispatchIncoming` simply deletes the receipt "so it can be retried" [3](#0-2) , but every retry hits the same deterministic revert. This is the same bug class as the H-3 report: a party fully in control of an on-chain object referenced by the withdrawal path (there, the NFT owner; here, the escrowed token contract) can make that object permanently unusable, and the code has no fallback/try-catch to route around it, so the settlement can never complete and the solver's already-delivered assets are permanently unrecoverable.

### Finding Description
1. `placeOrder` accepts `order.inputs` as arbitrary `(token, amount)` pairs supplied by the order creator and performs `IERC20(token).safeTransferFrom(msg.sender, address(this), amount)` for each, with no check that `token` is a "safe"/whitelisted token [4](#0-3) . Nothing prevents the creator from using a token contract they wrote themselves.
2. For a cross-chain order, the solver calls `fillOrder` on the destination chain and delivers the real output assets to the beneficiary immediately (this is an irreversible action - real value leaves the solver). Only after that does `ExtrinsicIntents` dispatch a `RedeemEscrow`/`RedeemEscrow`-carrying POST back to the source chain so the solver can claim the input escrow [5](#0-4) .
3. On the source chain, `onAccept` calls `_withdraw(body, kind == RequestKind.RefundEscrow, true)`, which loops over `body.tokens` (the exact tokens from `order.inputs`) and does `IERC20(token).safeTransfer(beneficiary, amount)` for each with no try/catch and no per-token isolation [2](#0-1) . A revert on any single token transfer aborts the entire withdrawal, including the release of all the other (perfectly fine) escrowed tokens and the transaction fee payout.
4. `EvmHost.dispatchIncoming` treats every `onAccept` failure identically: it deletes the request receipt and returns without reverting the outer batch "so that it can be retried" [6](#0-5) . This design assumes failures are transient/recoverable (e.g., temporary out-of-gas or an unrelated bug), but it has no way to distinguish that from a deterministic, attacker-engineered permanent revert. Repeated relayer submissions of the same message will fail forever.
5. Because the malicious token is entirely under the order creator's control (deployed and chosen by them at order-placement time), they can make `transfer()` unconditionally revert (e.g., always `revert()`, or `revert()` for any recipient other than themselves), guaranteeing the solver can never successfully redeem — the exact same "attacker permanently disables the object the repayment path depends on" pattern as the source report's NFT-burn/`ownerOf()` revert.

### Impact Explanation
This permanently freezes/loses solver funds: the solver has already delivered the real cross-chain output tokens to the beneficiary (an irreversible transfer, since same-chain fills settle atomically and cross-chain fills release output immediately upon fill, before any settlement round-trip [7](#0-6) ), but can never claim the input escrow it was promised because `_withdraw` will deterministically revert forever on the malicious token. This is a permanent freezing/loss of funds for an unprivileged, non-admin participant (the solver), triggered entirely by a single unprivileged `placeOrder` transaction from the order creator — no special role required. It also blocks that specific ISMP message from ever being delivered, which is one of the explicitly in-scope impact categories (route unable to deliver messages).

### Likelihood Explanation
High likelihood: any address can call `placeOrder` and pick any ERC-20 contract as an input token — there is no allowlist, no minimum-liquidity check, and no restriction that the token be well-behaved. Writing a token whose `transfer()` reverts for anyone other than the deployer is trivial. The only precondition is that a solver actually fills the order (standard economic incentive to earn the spread), at which point the trap is sprung irreversibly.

### Recommendation
- In `_withdraw` (`IntentsBase.sol`), wrap each per-token `safeTransfer`/native send in a try/catch (or use low-level `.call` with a captured `success` bool per token) so that one poisoned token cannot block release of the other escrowed tokens or the transaction fee. Tokens whose transfer fails should be tracked and made separately claimable/sweepable rather than blocking the whole withdrawal.
- Consider validating input tokens at `placeOrder` time (e.g., a minimal ERC-20 sanity probe, or a governance-managed token allowlist for use as order inputs) so solvers can determine upfront whether a given order's inputs are safe to fill against.
- At minimum, add a permissioned "force-settle" / dust-sweep path so that if a token permanently reverts, the protocol (via Hyperbridge governance, similar to `SweepDust`) can still release the remaining tokens and compensate the affected solver, rather than the whole redeem being wedged forever.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer(to, amount)` succeeds only when `to == attacker`, and reverts for every other recipient (including the gateway's transfers to solvers).
2. Attacker calls `placeOrder` on the source chain with `order.inputs = [{token: EvilToken, amount: X}, {token: USDC, amount: Y}]` and a legitimate output requirement on the destination chain [8](#0-7) .
3. A solver, seeing a profitable cross-chain order, calls `fillOrder` on the destination chain and delivers the real `output.assets` to the beneficiary; the destination gateway dispatches a `RedeemEscrow` POST back to the source chain [5](#0-4) .
4. A relayer delivers the `RedeemEscrow` message on the source chain; `onAccept` calls `_withdraw`, which attempts `IERC20(EvilToken).safeTransfer(solver, X)` first (or in whatever order the tokens array places it) and reverts [9](#0-8) .
5. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and returns without reverting the batch [6](#0-5) ; the relayer (or anyone) can resubmit the same message indefinitely, but `EvilToken.transfer` always reverts for the solver, so the message can never be delivered successfully.
6. Result: the solver's real output assets sent in step 3 are permanently lost, and the escrowed USDC (and the EvilToken) sit frozen in the gateway forever with no recovery path in the current code.

```text
    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
```

```text
### Fill Flow

The solver calls `fillOrder(order, options)` on the **destination chain**. The function verifies the order hasn't expired (`order.deadline >= block.number`), confirms execution is on the correct chain, and checks the order hasn't already been filled. The solver must provide output amounts greater than or equal to the order's required amounts — any amount below the required amount reverts with `InvalidInput()`.

If the solver provides more tokens than required, the excess (surplus) is split according to `surplusShareBps`. If the order includes calldata, 100% of surplus goes to the protocol to prevent manipulation.

After delivering output tokens to the beneficiary, the contract dispatches a cross-chain `RedeemEscrow` message back to the source chain.
```
