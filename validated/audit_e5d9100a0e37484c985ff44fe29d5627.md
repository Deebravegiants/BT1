### Title
Permanent freeze of graduating-token funds via `Math.mulDiv` overflow revert in `Bonding._noFeeSwapInput` during hostile HyperSwap V2 pre-seed rebalancing - ([File: packages/contracts/src/Bonding.sol])

### Summary
An attacker can pre-seed the HyperSwap V2 `TOKEN/LT` pair with an extreme reserve ratio (up to `uint112.max` on each side) combined with driving the curve's `tokenReserve`/`assetReserve` ratio to an extreme via ordinary buys near the bonding-curve's asymptote. When `finalizeGraduation` later runs `_seedRebalancing → _pairRebalance → _noFeeSwapInput`, the `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` call can overflow uint256 and revert unconditionally. Because a token in `Lifecycle.Graduating` can never `buy`/`sell` again (`TokenIsGraduating` guard) and `finalizeGraduation` has no fallback or admin rescue path, this permanently bricks the token: the curve-raised LT already pulled into `Bonding` by `_prepareGraduationLiquidity`/`router.graduate`, and the tokens already committed to the curve, become permanently inaccessible to creator/traders — mirroring the referenced CVE's "manipulated input permanently locks legitimate users out of their own data/funds" bug class.

### Finding Description
`_prepareGraduationLiquidity` computes `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` purely from the curve `Pair`'s stored reserves at the moment graduation triggers [1](#0-0) . Because the bonding curve is a constant-product curve with a virtual reserve, an attacker who buys aggressively near the curve's asymptote can drive `tokenReserve` toward its floor while pushing `ltFromPair` (the real LT raised) arbitrarily high, making `tokensForLP` round down to a tiny non-zero value (e.g. 1 wei) while `ltFromPair` remains large.

Separately, the attacker permissionlessly pre-creates the HyperSwap V2 `TOKEN/LT` pair and self-funds a `mint` with a hostile, heavily skewed ratio approaching `uint112.max` reserves on each side — the "Regime 3" hostile mint pre-seed explicitly anticipated by `_seedUniswapV2Direct`'s natspec [2](#0-1) .

When `finalizeGraduation` runs, it reaches `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`:

```
uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
``` [3](#0-2) 

`reserveIn`/`reserveOut` are attacker-controlled (bounded only by `uint112.max` ≈ 5.19e33 each), and `targetN = ltFromPair` can be large while `targetD = tokensForLP` can be forced to a tiny value via the curve manipulation above. The product `reserveIn * reserveOut * targetN` can exceed `type(uint256).max` even though OZ's `Math.mulDiv` uses a 512-bit intermediate, because the final quotient (after dividing by a tiny `targetD`) still overflows 256 bits. The contract's own comment acknowledges this exact failure mode: *"Constructed adversarial inputs that violate this would revert rather than silently truncate, which is the correct failure mode."* [4](#0-3) 

That "correct failure mode" is a revert with no recovery: `finalizeGraduation` is the only function that can move a token out of `Lifecycle.Graduating`, it has no try/catch or alternate path around `_seedUniswapV2Direct` [5](#0-4) , and both `buy` and `sell` explicitly reject any token whose lifecycle is `Graduating` [6](#0-5) . The real LT already drained from the curve `Pair` via `_s().router.graduate(tokenAddress, ltFromPair)` inside `_prepareGraduationLiquidity` [7](#0-6)  sits in `Bonding` with no owner-callable rescue for a permanently-reverting graduation, and holders' curve tokens can never be sold back.

### Impact Explanation
This is a permanent freeze of funds: the LT raised by all curve traders for that token, plus the traders' launched-token balances, become permanently unusable once the token enters `Lifecycle.Graduating` and `finalizeGraduation` unconditionally reverts. No admin function exists to force-finalize, skip the rebalance branch, or refund the frozen LT/tokens. This matches the "Accept only concrete theft or permanent freezing of trader, creator or LP funds" validation bar and directly parallels the referenced CVE's permanent-denial-of-access bug class.

### Likelihood Explanation
The attack requires two permissionless, unprivileged actions reachable by a single actor: (1) buying deep into the curve's asymptote to skew `tokenReserve`/`assetReserve` so `tokensForLP` rounds to a tiny value, and (2) pre-creating/self-seeding the HyperSwap V2 pair with an extreme, oppositely-skewed ratio before `finalizeGraduation` runs. Both are named in-scope reachable primitives (`Zap.buy`, and "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation"). It requires meaningful capital to push reserves toward `uint112` extremes and to buy the curve to its tail, but no privileged role or timing race is needed, and the code's own comments show the developers were aware overflow was reachable for "constructed adversarial inputs" yet left it as a hard revert rather than a bounded/capped computation.

### Recommendation
Bound `_noFeeSwapInput`'s intermediate computation so it cannot revert on legitimate-but-extreme inputs: clamp `targetD`/`tokensForLP` away from near-zero before it is used as a rebalancing divisor (e.g., fall back to `_seedDirectMint` whenever `tokensForLP` is below a minimum absolute or relative threshold, not just when both reserves are within `DIRECT_MINT_PRESEED_BPS`), and/or wrap the `_seedRebalancing` path in a try/catch inside `finalizeGraduation` that falls back to the always-safe `_seedDirectMint`/skim path on any failure so a hostile pre-seed can never permanently brick graduation.

### Proof of Concept
1. Attacker (or colluding party) launches or targets an existing curve token and buys aggressively near the curve's tail (large `amountIn` via `Zap.buy`) so that on the threshold/sellout-triggering buy, the curve's `tokenReserve` is driven very low relative to `assetReserve`, causing `_prepareGraduationLiquidity`'s `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` to round to a tiny value (e.g. 1) while `ltFromPair` is large — token enters `Lifecycle.Graduating`.
2. Before `finalizeGraduation` is called, attacker permissionlessly creates the HyperSwap V2 `TOKEN/LT` pair (or reuses `_ensureUniswapV2Pair`) and calls `mint` after transferring reserves close to `uint112.max` on each side in a ratio far from the curve-close price.
3. Anyone (or a keeper) calls `Bonding.finalizeGraduation(tokenAddress)`. Execution reaches `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, where `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` overflows uint256 and reverts.
4. `finalizeGraduation` reverts every time it is called (deterministic given the frozen `pendingGraduation` state and the pre-seeded pair reserves). The token is stuck in `Lifecycle.Graduating` forever: `buy`/`sell` both revert with `TokenIsGraduating`, and the LT already moved into `Bonding` by step 1's `router.graduate` call is unrecoverable.

        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
