Audit Report

## Title
JWT replay-protection check-then-act race in `WorkflowMetadataHandler.Authorize` allows single-use JWT to authorize more than one workflow execution - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`WorkflowMetadataHandler.Authorize` performs the JWT replay check (`isReplay`) and the replay record (`recordUsage`) as two separately-locked operations with unrelated authorization work executed in between, rather than as a single atomic check-and-set. This is a genuine TOCTOU race: two concurrent `workflows.execute` HTTP trigger requests carrying the same signed JWT can both pass the "not yet used" check before either records usage, allowing a JWT that is meant to authorize exactly one execution to authorize two (or more) concurrent executions.

## Finding Description
`Authorize` is reached from an unprivileged external caller through `httpTriggerHandler.HandleUserTriggerRequest` → `authorizeRequest` [1](#0-0) . Inside `Authorize`, `h.jwtCache.isReplay(claims.ID)` is checked first, and `h.jwtCache.recordUsage(claims.ID)` is only called after the `authorizedKeys` map lookup and signer comparison [2](#0-1) . `isReplay` takes an `RLock` and releases it immediately after checking the map; `recordUsage` takes a fully independent `Lock` later [3](#0-2) . No lock spans both operations, so two goroutines processing the same `jti` concurrently can both observe `exists == false` in `isReplay` before either calls `recordUsage`.

The JWT is bound to a specific request digest (`req.Digest()`) verified in `VerifyRequestJWT`, confirming the token is meant to authorize exactly one execution instance [4](#0-3) , so the single-use cache is a real security control, not incidental logging.

## Impact Explanation
This is a legitimate check-then-act race that can let one previously-issued, validly-signed JWT authorize more than one workflow execution when two requests carrying it race through `Authorize` concurrently. This maps to the "unauthorized job run" impact category: the JWT's one-time-use guarantee is a real control against duplicate/replayed workflow triggers, and the race defeats it. The severity is bounded, however: the JWT is already scoped to a signer who is authorized for that specific workflow, so this does not grant execution rights to an otherwise-unauthorized party — it only enables one extra execution of a workflow the caller was already entitled to trigger once, subject to the requestID-uniqueness check in `setupCallback` [5](#0-4)  and downstream rate limiting [6](#0-5) .

## Likelihood Explanation
Exploitation requires a caller who already possesses one valid, previously-authorized JWT (signed by a key authorized for the target workflow) to submit it via two concurrent `workflows.execute` requests with distinct `requestID`s (to avoid the `setupCallback` dedupe) before either `isReplay`/`recordUsage` pair completes. The race window is small (a map lookup and a few in-memory comparisons) but is not gated by any additional synchronization, making it a real, reproducible race rather than a purely theoretical one; it requires no operator/admin privileges, only possession of a signed JWT the caller already legitimately holds.

## Recommendation
Make the replay check-and-record atomic by combining `isReplay` and `recordUsage` into a single method (e.g., `checkAndRecord(jti) bool`) that holds one write lock across both the existence check and the insertion, and call it as the very first step of `Authorize` before any other authorization logic executes.

## Proof of Concept
1. Sign one JWT (`jti` = X) authorizing a `workflows.execute` request digest for a workflow with a known authorized signer.
2. Concurrently invoke `WorkflowMetadataHandler.Authorize` (or `HandleUserTriggerRequest` end-to-end) twice with the same `token`/`req.Auth` but distinct `req.ID` values, using goroutines synchronized to start simultaneously.
3. Observe that both calls can return successfully (no "JWT token has already been used" error) because both reach `isReplay` before either reaches `recordUsage`.
4. A Go unit test using two goroutines and a `sync.WaitGroup`/barrier calling `Authorize` concurrently with the same `claims.ID` would deterministically reproduce the race under `go test -race` with sufficient iterations.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
