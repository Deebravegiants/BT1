### Title
Unbounded combinatorial expansion in RBAC escalation-prevention check allows a low-privileged user to DoS the kube-apiserver - (File: `staging/src/k8s.io/component-helpers/auth/rbac/validation/policy_comparator.go`)

### Summary
`Covers`/`BreakdownRule` in the RBAC escalation guard expand every `PolicyRule` a user submits into the cartesian product of its `APIGroups × Resources × Verbs × ResourceNames` fields, and then compares each resulting sub-rule against every rule the caller already owns. Because `Role`/`ClusterRole`/`RoleBinding`/`ClusterRoleBinding` field validation does not cap the number of entries in these list fields, an authenticated but otherwise unprivileged user (anyone allowed to `create`/`update` `roles`/`clusterroles`, which is common for namespace-admin type users) can submit a small object with a few hundred short strings in each of `apiGroups`, `resources`, `verbs`, and `resourceNames` to force this code to materialize and compare millions of synthetic rules on every request, consuming disproportionate CPU on the API server.

### Finding Description
`Covers` is the core of the "no privilege escalation" check performed on every `Role`/`ClusterRole`/`RoleBinding`/`ClusterRoleBinding` mutation by a caller lacking the `escalate` verb: [1](#0-0) 

The breakdown step performs a 4-way nested loop over user-controlled arrays inside a single `PolicyRule`, without any bound on their sizes: [2](#0-1) 

This function is invoked from `ConfirmNoEscalation`, which is called from the policy-based storage layer for `ClusterRole`s (and analogously for `Role`, `RoleBinding`, `ClusterRoleBinding`) on every `Create`/`Update` when the caller does not have `escalate` rights: [3](#0-2) [4](#0-3) 

`ConfirmNoEscalation` is reached unconditionally for any non-escalation-authorized `PolicyRule` submission — the exact array-size limits on `PolicyRule.APIGroups`, `.Resources`, `.Verbs`, and `.ResourceNames` were not found in the RBAC validation package searched (`pkg/apis/rbac/validation/validation.go`), so their bound, if any, could not be confirmed in this pass; the API type only marks these as `+listType=atomic` slices with no documented max length: [5](#0-4) 

If there is no per-field item-count cap enforced before this code runs, an attacker-controlled `PolicyRule` with, e.g., 100 `apiGroups` × 100 `resources` × 100 `verbs` × 100 `resourceNames` (a payload well under normal etcd/object size limits, since each string can be a few characters) expands to 100,000,000 synthetic sub-rules in `BreakdownRule`, each of which is then compared against every rule the caller already owns in `Covers`'s O(subrules × ownerRules) inner loop. This is directly analogous to the reported PoolTemplate.sol bug class: unbounded iteration driven by an attacker-controlled array size causing resource exhaustion/denial of service on core functionality (here, Role/ClusterRole/RoleBinding mutation and the escalation check that guards RBAC privilege boundaries).

### Impact Explanation
This directly threatens availability of the kube-apiserver process handling the request (and potentially the whole API server given Go's cooperative scheduling and shared worker pools), which underlies a core authorization safety mechanism (the RBAC escalation guard). A successful attack could stall or crash the RBAC admission path, denying legitimate Role/ClusterRole/Binding operations cluster-wide for the duration of the attack, and is triggerable by any authenticated user permitted to create/update RBAC objects in their own namespace (a very common, low-privilege capability, e.g., namespace admins who are intentionally *not* granted `escalate`).

### Likelihood Explanation
Likelihood is high assuming no per-field cap exists on `PolicyRule.APIGroups/Resources/Verbs/ResourceNames`: crafting such a payload requires only standard RBAC object creation permissions in a single namespace and does not require any special roles, cluster-admin access, or race conditions. The exact likelihood is somewhat uncertain because this analysis could not confirm within the RBAC validation package whether a bound on these list lengths exists elsewhere (e.g., a generic list-length limit enforced by the API machinery); this should be verified before treating the issue as fully exploitable.

### Recommendation
- Enforce a strict maximum item count on `PolicyRule.APIGroups`, `.Resources`, `.Verbs`, and `.ResourceNames` (and `.NonResourceURLs`) in RBAC object validation (`pkg/apis/rbac/validation/validation.go`), similar to the existing 64-item cap pattern used for webhook `matchConditions`.
- Bound the total number of sub-rules `BreakdownRule` may generate per `PolicyRule` and fail fast (return an error) if the cartesian product would exceed a safe threshold, rather than materializing it.
- Consider replacing the O(subrules × ownerRules) nested scan in `Covers` with indexed/set-based lookups keyed by group/resource/verb to reduce worst-case complexity even for legitimately large but bounded inputs.

### Proof of Concept
Not independently executed in this pass (no runtime access), but the code path is deterministic and confirmed by static analysis:
1. As a user with `create`/`update` on `clusterroles` (or `roles` in a namespace) but without `escalate` rights, submit:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: dos-poc
rules:
- apiGroups: ["g1","g2", ... ,"g100"]
  resources: ["r1","r2", ... ,"r100"]
  verbs: ["v1","v2", ... ,"v100"]
  resourceNames: ["n1","n2", ... ,"n100"]
```
2. This is routed through `Storage.Create` → `ConfirmNoEscalation` → `validation.Covers` → `BreakdownRule`, which computes 100×100×100×100 = 10^8 synthetic `PolicyRule`s for a single rule entry before comparison against the caller's owned rules, consuming excessive CPU/memory on the API server for the duration of the request. // Covers determines whether or not the ownerRules cover the servantRules in terms of allowed actions.
// It returns whether or not the ownerRules cover and a list of the rules that the ownerRules do not cover.
func Covers(ownerRules, servantRules []rbacv1.PolicyRule) (bool, []rbacv1.PolicyRule) {
	// 1.  Break every servantRule into individual rule tuples: group, verb, resource, resourceName
	// 2.  Compare the mini-rules against each owner rule.  Because the breakdown is down to the most atomic level, we're guaranteed that each mini-servant rule will be either fully covered or not covered by a single owner rule
	// 3.  Any left over mini-rules means that we are not covered and we have a nice list of them.
	// TODO: it might be nice to collapse the list down into something more human readable

	subrules := []rbacv1.PolicyRule{}
	for _, servantRule := range servantRules {
		subrules = append(subrules, BreakdownRule(servantRule)...)
	}

	uncoveredRules := []rbacv1.PolicyRule{}
	for _, subrule := range subrules {
		covered := false
		for _, ownerRule := range ownerRules {
			if ruleCovers(ownerRule, subrule) {
				covered = true
				break
			}
		}

		if !covered {
			uncoveredRules = append(uncoveredRules, subrule)
		}
	}

	return (len(uncoveredRules) == 0), uncoveredRules
}

// BreadownRule takes a rule and builds an equivalent list of rules that each have at most one verb, one
// resource, and one resource name
func BreakdownRule(rule rbacv1.PolicyRule) []rbacv1.PolicyRule {
	subrules := []rbacv1.PolicyRule{}
	for _, group := range rule.APIGroups {
		for _, resource := range rule.Resources {
			for _, verb := range rule.Verbs {
				if len(rule.ResourceNames) > 0 {
					for _, resourceName := range rule.ResourceNames {
						subrules = append(subrules, rbacv1.PolicyRule{APIGroups: []string{group}, Resources: []string{resource}, Verbs: []string{verb}, ResourceNames: []string{resourceName}})
					}

				} else {
					subrules = append(subrules, rbacv1.PolicyRule{APIGroups: []string{group}, Resources: []string{resource}, Verbs: []string{verb}})
				}

			}
		}
	}

	// Non-resource URLs are unique because they only combine with verbs.
	for _, nonResourceURL := range rule.NonResourceURLs {
		for _, verb := range rule.Verbs {
			subrules = append(subrules, rbacv1.PolicyRule{NonResourceURLs: []string{nonResourceURL}, Verbs: []string{verb}})
		}
	}

	return subrules
}

// PolicyRule holds information that describes a policy rule, but does not contain information
// about who the rule applies to or which namespace the rule applies to.
type PolicyRule struct {
	// verbs is a list of Verbs that apply to ALL the ResourceKinds contained in this rule. '*' represents all verbs.
	// +listType=atomic
	// +required
	// +k8s:beta(since: "1.37")=+k8s:required
	Verbs []string `json:"verbs" protobuf:"bytes,1,rep,name=verbs"`

	// apiGroups is the name of the APIGroup that contains the resources.  If multiple API groups are specified, any action requested against one of
	// the enumerated resources in any API group will be allowed. "" represents the core API group and "*" represents all API groups.
	// +optional
	// +listType=atomic
	APIGroups []string `json:"apiGroups,omitempty" protobuf:"bytes,2,rep,name=apiGroups"`
	// resources is a list of resources this rule applies to. '*' represents all resources.
	// +optional
	// +listType=atomic
	Resources []string `json:"resources,omitempty" protobuf:"bytes,3,rep,name=resources"`
	// resourceNames is an optional white list of names that the rule applies to.  An empty set means that everything is allowed.
	// +optional
	// +listType=atomic
	ResourceNames []string `json:"resourceNames,omitempty" protobuf:"bytes,4,rep,name=resourceNames"`

	// nonResourceURLs is a set of partial urls that a user should have access to.  *s are allowed, but only as the full, final step in the path
	// Since non-resource URLs are not namespaced, this field is only applicable for ClusterRoles referenced from a ClusterRoleBinding.
	// Rules can either apply to API resources (such as "pods" or "secrets") or non-resource URL paths (such as "/api"),  but not both.
	// +optional
	// +listType=atomic
	NonResourceURLs []string `json:"nonResourceURLs,omitempty" protobuf:"bytes,5,rep,name=nonResourceURLs"`
}
