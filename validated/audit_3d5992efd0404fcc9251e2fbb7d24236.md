### Title
Fee-on-transfer underlying tokens cause unbacked releases in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` `send()` - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin) locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message that always carries the *requested* `params.amount`, never the amount the contract actually received. If the configured `_underlying` token deducts a fee on transfer (e.g. USDT-style fee-on-transfer tokens, or any token with transfer hooks that skim value), the contract locks strictly less than `params.amount`, yet the destination-chain deployment unconditionally releases the full `message.amount` of its own underlying-token pool to the beneficiary.

### Finding Description
In `send()`: [1](#0-0) 
the contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` without ever measuring the actual balance delta. `_buildDispatchPost` then encodes `params.amount` verbatim into the `Message` body dispatched to the destination chain: [2](#0-1) 

On the destination chain, `onAccept` unconditionally transfers `message.amount` of its own local underlying pool to the beneficiary: [3](#0-2) 

This is the same root cause identified in the external report: the code assumes `transferFrom` moves the requested amount 1:1 and never verifies actual received balance before using that value in downstream accounting. `IntentGatewayV2.sol` was hardened against exactly this class of bug — it snapshots balances before/after every `safeTransferFrom` and mutates `order.inputs[i].amount` to the *actually received* amount before computing the commitment/escrow — see the explicit "Phase 1" comment and logic: [4](#0-3) 
No equivalent balance-delta measurement exists in `WrappedHyperFungibleToken.send()` or `WrappedHyperFungibleTokenUpgradeable.send()`.

### Impact Explanation
Each `send()` call using a fee-on-transfer underlying silently locks `amount - fee` on the source chain while instructing the destination deployment to release the full `amount` from its own underlying-token reserve. Because this is a lock/unlock (pool-to-pool) bridge rather than burn/mint — `onAccept` calls `safeTransfer` from the destination contract's own held balance rather than minting — every such transfer creates a permanent, uncompensated deficit in the destination pool equal to the fee skimmed on the source side. Repeated over many transfers, this drains destination-side reserves backing *other* users' locked balances, ultimately leaving some users unable to redeem/unlock their legitimately locked funds (permanent freezing/loss of funds for the pool, effectively theft from later "unlockers" who find the destination pool insolvent). Unlike the original Auction finding — which just causes a revert/DoS — here there is no revert at all: the mismatch is silently absorbed into a growing pool insolvency.

### Likelihood Explanation
Reachable by any unprivileged user who calls the public, non-owner-gated `send()` function once the operator configures `_underlying` to a fee-on-transfer (or any non-standard, non-1:1-transferring) ERC20 — a configuration decision entirely orthogonal to any security assumption enforced by the contract itself; nothing in `configure()` restricts `_underlying` to strictly-conforming tokens. Given the documented intent to support "existing ERC20 tokens" generically (per the contract's own NatSpec), and the known prevalence of fee-on-transfer tokens in the wild (USDT, various rebasing/tax tokens), this is a realistic deployment scenario, not a contrived one.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.placeOrder`: measure `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) both for the dispatched `Message.amount` and for the emitted `Sent` event. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Operator deploys `WrappedHyperFungibleToken` on chain A and chain B, both configured with the same fee-on-transfer token address family (or any underlying that takes a 1% fee on `transferFrom`) as `_underlying`, and registers each other via `addChain`.
2. Chain B's contract is pre-funded with underlying liquidity (as required for any lock/unlock bridge to support redemptions).
3. Alice on chain A calls `send({dest: chainB, to: bob, amount: 1000e18, ...})`. `safeTransferFrom(alice, address(this), 1000e18)` executes, but due to the 1% fee, chain A's contract balance only increases by `990e18`.
4. The dispatched `Message.amount` is still `1000e18` (per `_buildDispatchPost`, using `params.amount` directly).
5. Once relayed and proven, chain B's `onAccept` calls `IERC20(_underlying).safeTransfer(bob, 1000e18)`, paying out `10e18` more than was ever actually locked on chain A.
6. Repeating this operation drains chain B's underlying reserve by the fee percentage on every transfer, eventually leaving it unable to honor other users' redemptions — i.e., permanent fund loss/insolvency for the pool.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
