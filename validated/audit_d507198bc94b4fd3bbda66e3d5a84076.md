This confirms the exact vulnerability: the gem's official documented pattern (`docs/usage/webhooks.md`) explicitly promises that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and instructs the handler to key its per-tenant business logic (`shop_domain: data.shop`) directly off `data.shop` [2](#0-1) , but the HMAC that `process` validates never actually covers that field.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , while `#shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signed payload [4](#0-3) . `Registry.process` validates the HMAC and, once it passes, immediately trusts `request.shop` as the tenant identity handed to the app's handler [5](#0-4) . The equality the code implicitly assumes — "shop the HMAC authenticates" == "shop the handler acts on" — does not hold, because the header is outside the signed string.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(verifiable_query.to_signable_string, api_secret_key)` and compares it to the `hmac` field via `OpenSSL.secure_compare` [6](#0-5) . For webhook requests, `to_signable_string` is exactly the raw JSON body [3](#0-2)  — this is by design, matching Shopify's webhook signing scheme, which signs only the body.

The `api_secret_key` used to compute this signature is the app's single client secret, shared across every shop that installs the app — it is not shop-specific. Consequently, a valid `(body, hmac)` pair generated for one shop's event is cryptographically valid for that exact body regardless of which shop domain accompanies it, because the shop domain is never part of the signed material.

`Registry.process` uses this fact unsafely: it validates the HMAC of the body, then builds the `WebhookMetadata` passed to the developer's handler using `request.shop`, taken straight from the unauthenticated header [7](#0-6) . Any internet client that can reach the app's public webhook endpoint (no other authentication exists on that route — the whole point of the HMAC is to be the sole authentication mechanism) can submit an HTTP POST with:
- a `raw_body` + `x-shopify-hmac-sha256` pair that is valid (attacker obtains this pair legitimately once, e.g., by installing the app on their own store and capturing one delivered webhook, since the body/signature relationship depends only on body content and the shared secret, not on the sender), and
- an arbitrary `x-shopify-shop-domain` header claiming to be any other installed shop.

`Registry.process` will accept it (HMAC checks out because it never inspected the header) and dispatch it to the handler tagged with the attacker-chosen `shop` value. Since the documentation explicitly tells developers this `shop` field is what identifies "The shop domain of the webhook" and to key downstream work off it (`shop_domain: data.shop`) [8](#0-7) , this breaks the identity binding "HMAC-authenticated sender" == "shop attributed to the event," letting an attacker inject a webhook of their choosing that the app processes as belonging to an unrelated, victim tenant — cross-tenant data confusion/injection using only unprivileged internet access to the public webhook endpoint.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged internet user (who only needs to install the app once on a shop they control, or otherwise obtain one valid signed body) can cause the app to process attacker-controlled webhook content while attributing it to any other shop domain of the attacker's choosing. Depending on how the host app uses `data.shop` (as documented, to select DB records, background jobs, or session lookups per merchant), this enables cross-tenant data corruption/injection — one of the explicitly in-scope Critical impacts (cross-tenant access).

### Likelihood Explanation
Likelihood is moderate-to-high for apps built directly against the documented API: the gem's own docs instruct developers to trust `data.shop` for tenant selection with no caveat that it is unauthenticated, and the webhook endpoint is public by design (there is no other authentication layer). Any developer following `docs/usage/webhooks.md` as written inherits this gap.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered material, or require the caller to separately verify that `request.shop` corresponds to a shop that legitimately has that topic registered (e.g., cross-check against stored webhook registrations) before trusting it in `WebhookMetadata`. At minimum, update `Utils::VerifiableQuery`/`HmacValidator` usage for webhooks so `to_signable_string` binds the headers that downstream code treats as authenticated, and update `docs/usage/webhooks.md` to make explicit that `data.shop` is not covered by the signature if that binding is not fixed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers an event (e.g., `orders/create`), causing Shopify to POST a webhook to the app's public endpoint with a genuine `raw_body` and valid `x-shopify-hmac-sha256` (computed with the app's shared `api_secret_key`).
2. Attacker crafts their own HTTP POST to the same public endpoint, reusing the exact `raw_body` and `x-shopify-hmac-sha256` values, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` [3](#0-2)  — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop == "victim-shop.myshopify.com"` [9](#0-8) , even though the event content originated from the attacker's own shop — a cross-tenant identity break confirmed purely from this gem's code path.
