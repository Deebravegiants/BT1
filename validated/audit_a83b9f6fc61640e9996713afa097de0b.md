### Title
Webhook `shop` (and `topic`) Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`, `webhook-id`, `api-version`) values that the library hands to the host application's webhook handler as the identity of the tenant are taken directly from unauthenticated HTTP headers and are never included in the signed material. This breaks the intended binding `hmac_signed_content == shop_the_app_acts_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from the `x-shopify-*`/`shopify-*` HTTP headers, which are attacker-controlled on any request reaching the app's webhook endpoint: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, and then immediately trusts `request.shop`/`request.topic` (read from the unsigned headers) to build the `WebhookMetadata` passed to the host app's handler: [3](#0-2) 

`HmacValidator.validate` only re-derives the signature from `verifiable_query.to_signable_string` (i.e. the body) and compares it to the supplied `hmac`; it never checks that the `shop` header used by the caller matches anything cryptographically bound to that body: [4](#0-3) 

Because the signature only covers the body, any two webhook deliveries that happen to carry byte-identical bodies (which is common — many Shopify webhook topics, e.g. `app/uninstalled`, `app/scopes_update`, or bulk/inventory pings, have small, generic, or empty JSON bodies) produce identical valid HMACs regardless of which shop or topic header accompanies them. An attacker who legitimately installs the app on a shop they control can trigger such a webhook, capture the `(body, hmac)` pair from a genuine Shopify delivery, and then replay it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop (and/or a forged `x-shopify-topic`). `HmacValidator.validate` reports the forged request as valid because it only checks the body signature, and `Registry.process` dispatches it to the handler tagged with the attacker-chosen `shop`/`topic`.

This is precisely the "field acted on but not covered by the HMAC" pattern from the report: the byte range verified (`raw_body`) is disjoint from the field the host application uses as the tenant/session key (`shop` header) and dispatch key (`topic` header).

### Impact Explanation
This crosses a tenant boundary: an attacker with a legitimate install on Shop A can cause a webhook to be processed by the app as if it originated from Shop B, with a topic of the attacker's choosing (as long as they can find/produce a body that is valid for both the real and forged topic, or a topic-body pair with no shop-specific content). Depending on the handler logic in the host application, this can trigger actions against victim tenant data using a webhook that was never actually sent by Shopify for that shop/topic — e.g. spoofing an `app/uninstalled` event for a victim shop to wipe/deactivate stored sessions, or invoking business logic keyed only off `topic`+`shop` with attacker-supplied body content. This matches the Critical "cross-tenant access" category since the confidentiality/integrity boundary between merchants is broken using only a legitimate install of the app by the attacker on their own shop — no leaked secrets or privileged access are required.

### Likelihood Explanation
Exploitability requires the attacker to install the app on a shop they control (a normal, unprivileged action) and to find a webhook whose body content is generic/shop-agnostic (several standard Shopify topics qualify, e.g. `app/uninstalled` which typically has an empty or minimal body). The webhook endpoint is public by design (Shopify calls it over the internet), so replaying a captured `(body, headers, hmac)` tuple with modified `shop`/`topic` headers is trivial once such a body is identified.

### Recommendation
Include the values the application actually trusts for identity/dispatch — at minimum `shop` and `topic` (and ideally `webhook_id`) — in the signed material that `HmacValidator` checks, or otherwise cryptographically bind them to the body before dispatch. Since Shopify's HMAC only ever signs the body (this cannot be changed unilaterally by the gem), the library should not expose `shop`/`topic` as trusted values to be used for tenant/session identification without documenting this gap explicitly and/or offering an API that lets the host app assert its own out-of-band shop verification (e.g. requiring the caller to confirm the header-derived `shop` against a previously-registered webhook endpoint URL or a known active session), rather than treating `request.shop` as verified once `HmacValidator.validate` returns `true`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control).
2. Attacker triggers a webhook topic with a generic/empty body, e.g. `app/uninstalled`, and captures the delivered request: `raw_body = "{}"`, headers include `x-shopify-hmac-sha256: <valid_hmac_for_"{}">`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `"{}"` and finds it matches — validation passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)`, causing the host application to act on `victim-shop.myshopify.com` even though Shopify never sent this webhook for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
