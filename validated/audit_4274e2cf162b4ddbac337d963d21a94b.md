### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-attribution spoofing on otherwise-genuine webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. `Registry.process` trusts `request.shop` for tenant attribution after validating only the body's HMAC, so the "authenticated" bytes (body) and the "trusted" bytes (shop header) are not bound together.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` for tenant attribution when constructing the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

The identity binding this breaks, expressed as an equality that should hold but doesn't:
`shop attributed to the webhook (request.shop, read from an unauthenticated header)` ≠ `shop bound inside the HMAC-covered bytes (nonexistent — body/HMAC carries no shop identity at all)`.

Because the header is outside the signed envelope, any party capable of relaying HTTP requests to the app's webhook endpoint (e.g., a merchant installing the app on their own store, who legitimately receives genuine Shopify-signed webhook deliveries for their own shop) can capture one of their own valid `(body, hmac)` pairs and resend the exact same body/HMAC to the app's endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` because the body bytes are unchanged, and `Registry.process` will hand the attacker-chosen `shop` value to the app's `WebhookHandler`, which many host apps use directly to select or write into per-tenant storage (session/data lookup keyed by shop).

### Impact Explanation
This is a cross-tenant identity-binding break: a request that Shopify only ever authenticated for shop A can be replayed by anyone who received it to make the gem report shop B as the source, letting an attacker feed forged tenant attribution into the app's persistence/business logic while still passing HMAC validation. This matches the Critical bucket "cross-tenant access" since the gem itself hands the host application data mislabelled with an attacker-chosen tenant identity, despite claiming it passed integrity verification.

### Likelihood Explanation
Any user who can install the app on a shop they control (an "unprivileged internet user" in the sense of not needing the app's `client_secret` or access tokens) can capture a real webhook delivery for their own store and replay the raw body/HMAC with a modified shop-domain header to the same public webhook endpoint URL. No secrets are required — only the ability to observe one's own legitimately-delivered webhook and resend it with a different header.

### Recommendation
Bind the shop identity into the HMAC-verified content, or otherwise cryptographically tie the `shop-domain` header to the request before trusting it: e.g., include the shop domain in `to_signable_string` (matching what Shopify actually signs, if it does), or require host apps to cross-verify `request.shop` against the shop embedded in `parsed_body` (most webhook payloads include store metadata) before using it for tenant-scoped lookups. At minimum, document prominently that `request.shop` is not covered by HMAC verification and must not be trusted for tenant attribution without additional validation.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the genuine `raw_body` and `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker POSTs the same `raw_body` and same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only checks `raw_body` against the same secret: [5](#0-4) 
4. `request.shop` returns `"victim.myshopify.com"`, and `WebhookMetadata.new(topic: ..., shop: request.shop, body: ..., ...)` is passed to the app's `WebhookHandler#handle`, causing the host application to process/store the data under the wrong ("victim") tenant despite the payload never actually originating for that shop.
