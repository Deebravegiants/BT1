### Title
Zero-decimal coin/pc mints let a pool creator shrink the LP "minimum liquidity" buffer to 1, re-enabling first-depositor share-price inflation via floor-rounded Deposit/Withdraw math - ([File: program/src/processor.rs])

### Summary
Raydium's `Initialize2` already implements a Uniswap‑V2‑style "locked minimum liquidity" defense against the exact rounding attack described in the external report: it computes `liquidity = sqrt(pc_amount * coin_amount)` and only mints `user_lp_amount = liquidity - 10^lp_decimals` LP tokens to the creator, while `amm.lp_amount` (the internal share-accounting denominator used by `Deposit`/`Withdraw`) is set to the full, un-discounted `liquidity`. This creates a permanent gap between the tracked `amm.lp_amount` and the real circulating `lp_mint.supply`, which should prevent the denominator from ever collapsing to a trivially small number the way `totalDepositShares` did in the Sentiment bug. However, `lp_decimals` is not a fixed protocol constant - it is taken directly from the attacker-supplied `coin_mint`'s decimals field (`let lp_decimals = coin_mint.decimals;`). Any permissionless pool creator can mint/select a `coin_mint` with `decimals = 0`, making the locked buffer `10^0 = 1` instead of the intended large buffer (e.g. `10^9`). With the buffer reduced to 1, an attacker can withdraw the pool down until `amm.lp_amount` is minimal (the `Withdraw` check only forbids `withdraw.amount >= amm.lp_amount`, i.e. it allows leaving `amm.lp_amount` at just the buffer + 1), reproducing the same near-zero-denominator state (`totalDepositShares ≈ 1`) that the Sentiment report exploited, and then repeatedly loop `Deposit`→`Withdraw` using the floor-rounding in `InvariantPool::exchange_token_to_pool` to inflate the effective share price before an unsuspecting depositor arrives.

### Finding Description
The relevant "minimum liquidity" logic: [1](#0-0) 

`lp_decimals` is derived from `coin_mint.decimals`, and `coin_mint` is an arbitrary SPL mint account chosen by whoever calls `Initialize2` (a permissionless instruction reachable by any wallet with a single transaction): [2](#0-1) 

Here `liquidity = sqrt(pc_amount * coin_amount)` is used as `amm.lp_amount` (the denominator for all future share math), while only `liquidity - 10^lp_decimals` LP tokens are actually minted to the creator. If `lp_decimals == 0` (fully legal for many real SPL tokens, e.g. NFT-like or whole-unit tokens), the buffer collapses to `1`, defeating the purpose of the discount (which mirrors Uniswap V2's `MINIMUM_LIQUIDITY` burn-to-`address(0)` mitigation, referenced explicitly in the external report's recommendation).

`Withdraw` only guards against fully draining shares to zero, not against shrinking to a trivial nonzero value: [3](#0-2) 

Because `withdraw.amount >= amm.lp_amount` is the only floor, an attacker holding essentially all outstanding LP tokens can withdraw down to `amm.lp_amount == 10^lp_decimals + 1` (i.e. `2` when `lp_decimals = 0`), which is functionally identical to the Sentiment PoC's `totalDepositShares = 1, totalDepositAssets = 2` state.

`Deposit`'s share-mint math floors the result, exactly mirroring the Sentiment `convertToShares` rounding bug: [4](#0-3) [5](#0-4) 

With `amm.lp_amount` reduced to a tiny value, and `total_coin_without_take_pnl` derived straight from the live SPL vault balance (`amm_coin_vault.amount`) which any account can inflate via a bare SPL token transfer to the vault (no `Deposit` call required), the attacker can replicate the Sentiment loop: deposit `total+1` tokens, receive `1` share due to floor rounding, withdraw that `1` share back, and repeat - each iteration inflating `total_coin_without_take_pnl` / `total_pc_without_take_pnl` relative to the near-constant `amm.lp_amount == 1` (in supply terms), driving the effective share price up arbitrarily. A subsequent honest depositor whose deposit amount is not an exact multiple of the manipulated price then loses a rounding-down share of their deposit to the existing (attacker) LP holder, up to the ~33% loss profile described in the source report.

### Impact Explanation
An attacker who creates a pool (which is fully permissionless via `Initialize2`) using a zero-decimal `coin_mint` can defeat the anti-inflation buffer that Raydium otherwise relies on, and manipulate the LP share price for that pool before advertising/attracting depositors. Victims depositing into such a pool can lose a meaningful, attacker-controlled fraction of their deposited assets to floor-rounding, which is a direct theft of LP funds - this satisfies the "concrete theft ... of user or LP funds" bar. The blast radius is limited to pools whose `coin_mint` has 0 decimals (or very few decimals), which is a real, common configuration for some SPL tokens, and the attacker must also be the pool's first LP (which is trivial to arrange since anyone can call `Initialize2`).

### Likelihood Explanation
Medium. `Initialize2` is fully permissionless and reachable from a single attacker-controlled transaction with attacker-chosen accounts (including `coin_mint`), so setting up a vulnerable pool costs nothing beyond normal pool-creation fees/rent. Exploiting it further requires the attacker to be able to donate tokens directly to the vault and perform several `Deposit`/`Withdraw` transactions in a loop, all of which are ordinary, unprivileged instructions. The main constraint on likelihood is that the attacker must also lure/wait for a victim to deposit into their manipulated pool rather than a legitimate high-decimal pool, which is a social/economic precondition rather than a technical one.

### Recommendation
- Do not derive `lp_decimals` (and thus the size of the locked minimum-liquidity buffer) from the attacker-controlled `coin_mint.decimals`; use a fixed, sufficiently large constant (e.g. Raydium's conventional `9`) for the LP mint decimals/buffer regardless of the underlying token decimals, as is done for `initialize` pools elsewhere in the protocol.
- Enforce an absolute minimum value (not just a formula relative to token decimals) for `amm.lp_amount` after `Initialize2`, and similarly enforce that `Withdraw` cannot drive `amm.lp_amount` below that same absolute floor (currently it only prevents reaching exactly 0).
- Consider rounding LP-mint calculations in the depositor's favor when `total_deposit_shares` is at/near the protective floor, or reject `Deposit`s that would produce `mint_lp_amount` disproportionate to `deduct_coin_amount`/`deduct_pc_amount` (sanity-check price impact), similar to the BalancerV2/UniswapV2 style mitigations cited in the source report.

### Proof of Concept
Conceptual sequence (cannot be executed here; requires a Devin session with the full test harness to implement as a Rust program test):
1. Attacker calls `Initialize2` supplying a `coin_mint` with `decimals = 0` (e.g. mint 100 units of coin, 100 units of pc). `liquidity = sqrt(100*100) = 100`; `user_lp_amount = 100 - 10^0 = 99` minted to attacker; `amm.lp_amount = 100`.
   - [2](#0-1) 
2. Attacker calls `Withdraw` repeatedly (or once) with `withdraw.amount = 98`, the maximum allowed since `withdraw.amount >= amm.lp_amount` is forbidden (`98 < 100` passes when `amm.lp_amount` was 100, iteratively reducing it). After withdrawing down to the floor, `amm.lp_amount` settles at `10^0 + 1 = 2`, while attacker still holds ~1 real LP token.
   - [3](#0-2) 
3. Attacker transfers extra coin/pc tokens directly to `amm_coin_vault`/`amm_pc_vault` (plain SPL `Transfer`, not through `Deposit`), inflating `amm_coin_vault.amount`/`amm_pc_vault.amount`, which flow straight into `total_coin_without_take_pnl`/`total_pc_without_take_pnl` via `calc_total_without_take_pnl_no_orderbook`.
4. Attacker loops `Deposit(total_coin+1, ...)` → receives `mint_lp_amount = floor((total_coin+1) * amm.lp_amount / total_coin) ≈ 1` share (rounding-down bug in `exchange_token_to_pool`), then `Withdraw(1 share)` to redeem it back, each iteration doubling `total_coin_without_take_pnl` while `amm.lp_amount` stays pinned near `2`.
   - [4](#0-3) 
   - [5](#0-4) 
5. A victim later calls `Deposit` into this pool; because the effective share price has been inflated by the attacker's loop, the victim's `mint_lp_amount` floors down disproportionately, transferring value to the attacker's remaining share - mirroring the ~33% loss demonstrated in the source Sentiment PoC.

    /// Exchange rate
    pub fn exchange_token_to_pool(
        &self,
        pool_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
