## Title
Unchecked ERC20 `transfer` return value in intent escrow withdrawal/dust-sweep allows permanent freezing of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` handler in `onAccept()` on the Tron variant of the intents gateway pay out ERC20 tokens using a raw low-level `call` to `IERC20.transfer.selector`, but only check that the *call itself* did not revert (`success`). They never decode/verify the boolean return value that ERC20 `transfer` is supposed to return. This is the exact "unchecked ERC20 return value" bug class from the referenced report, reachable from the cross-chain message-delivery path that anyone can relay.

### Finding Description
In `withdraw()`, escrowed token payouts and fee payouts are executed like this: [1](#0-0) 

and dust sweeping uses the identical pattern: [2](#0-1) 

Both call sites use `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the outer `success` boolean returned by the low-level `call`, never inspecting the ABI-decoded return data. For a token that does not revert on failure (returns `false` instead — e.g. legacy/non-compliant ERC20s, or any token whose `transfer` implementation can legitimately return `false`), `success` will be `true` even though no tokens were actually moved. Note this contrasts with the rest of the same contract and the EVM-native `IntentGatewayV2.sol`, `HyperFungibleToken*.sol`, `EvmHost.sol`, and `UniV4UniswapV2Wrapper.sol`, which consistently use OpenZeppelin's `safeTransfer`/`safeTransferFrom` (e.g. `IERC20(token).safeTransferFrom(...)` at [3](#0-2) ), confirming the raw-call sites in `withdraw()`/`SweepDust` are the outlier.

`withdraw()` is reached from `onAccept()` (called by the host on a relayed cross-chain `RedeemEscrow`/`RefundEscrow` message) and from `onGetResponse()` (called by the host after a relayed GET-response proof): [4](#0-3) [5](#0-4) 

Both paths are ultimately triggered by any unprivileged relayer submitting a valid cross-chain proof/message — no special privilege is needed to trigger the payout attempt.

### Impact Explanation
Regardless of whether the `transfer` call actually moved funds, `withdraw()` unconditionally decrements the escrow accounting (`_orders[body.commitment][token] -= amount;`) and emits `EscrowReleased`/`EscrowRefunded`, and `SweepDust` emits `DustSwept`. If the payout silently fails (returns `false` without reverting), the contract's bookkeeping is updated as if the beneficiary was paid, while the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them — the commitment's escrow entry is now zeroed/consumed, so `_orders[body.commitment][token] == 0` will make any retry revert with `UnknownOrder()`. This is a permanent freezing of escrowed intent funds, and is reachable purely by proof/message delivery, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
The Tron deployment target increases the practical likelihood: Tron's TRC20 token ecosystem includes tokens (e.g. ports of legacy ERC20 templates, and tokens following older/looser transfer semantics) that are more likely than mainstream EVM ERC20s to return `false` on failure instead of reverting. Given the intents gateway is designed to escrow arbitrary user/solver-selected input and output tokens (`order.inputs`/`order.output.assets`), a solver or order-creator effectively chooses which token is escrowed, making it straightforward for a non-compliant or intentionally crafted token to trigger this path either accidentally or as a griefing vector against the protocol's own escrowed balance accounting.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (lines ~706, ~720) and the `SweepDust` branch of `onAccept()` (line ~674) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (as already done for `safeTransferFrom` calls in the same file), so that non-standard tokens returning `false` cause a revert instead of a silently "successful" no-op payout.

### Proof of Concept
1. Deploy/select a TRC20/ERC20-like token whose `transfer` implementation returns `false` on failure instead of reverting (e.g. due to a paused state, blacklist, or insufficient allowance-style internal check) and use it as an order's input token when calling `placeOrder`.
2. Have hyperbridge relay a `RedeemEscrow`/`RefundEscrow`/`SweepDust` message that triggers `onAccept` → `withdraw()` (or the `SweepDust` branch) for that commitment, at a moment where the token's `transfer` call returns `false` without reverting.
3. Observe: `success` from the low-level `call` is `true` (the call executed without reverting), so `TransferFailed()` is not raised; `_orders[commitment][token]` is decremented to zero and `EscrowReleased`/`EscrowRefunded`/`DustSwept` is emitted, even though the beneficiary's token balance did not increase.
4. Any subsequent attempt to redeem the same commitment/token now reverts with `UnknownOrder()` (`_orders[commitment][token] == 0`), while the tokens remain permanently stuck in the `IntentGatewayV2` contract.
