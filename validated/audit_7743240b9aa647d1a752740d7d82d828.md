**Analysis:** `handle_ir_face_camera` in the `biometric_capture::Plan` (invoked via the broker's dispatcher in `src/brokers/orb.rs`) is not a stage-transition function at all — it simply caches the most recent IR face frame: `self.last_face_ir = Some(output.value)` [1](#0-0) . It contains no flag-based gating and does not advance any signup stage.

The actual signup stage sequencing lives in `do_signup` in `src/plans/mod.rs`, and each stage strictly requires the typed output of its predecessor rather than a boolean/None-tolerant flag:
- `biometric_capture` returns `Option<biometric_capture::Capture>`, and the code immediately does `let Some(capture) = capture else { return Ok(result); }` before any further stage can run [2](#0-1) .
- `biometric_pipeline` is called with `&capture` (the typed struct, not a flag) and returns `Option<biometric_pipeline::Pipeline>` [3](#0-2) .
- `detect_fraud` explicitly requires `pipeline.as_ref()` and short-circuits via `let Some(_pipeline) = pipeline else { return Ok(false) }`, so fraud detection can't be spoofed by a boolean alone [4](#0-3) .
- `enroll_user` and `build_pcp` take `&capture` and `pipeline: Option<&biometric_pipeline::Pipeline>` as typed parameters, and `signup_reason` is derived from `pipeline.is_none()` mapping to `SignupReason::Failure` [5](#0-4) .

This is precisely the invariant the question asks about — each stage consumes the typed output of its predecessor, and Rust's ownership/type system enforces that `Capture` and `Pipeline` values must actually exist (be produced by their respective stages) before being passed downstream. There is no boolean/`Option`-tolerant bypass path reachable from `handle_ir_face_camera`, because that function is a per-frame data sink, not a state-machine driver.
