### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the webhook belongs to. The `shop` value used to dispatch to the handler is never part of the signed data, so `shop` (the tenant-identity claim consumed by the app) is not bound to the HMAC that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates the HMAC using `HmacValidator.validate`, which checks `verifiable_query.hmac` against `HMAC-SHA256(secret, verifiable_query.to_signable_string)` — i.e. only the body — and then unconditionally trusts `request.shop` to build the metadata handed to the app's handler: [3](#0-2) [4](#0-3) 

For comparison, in the OAuth callback flow this gem correctly binds `shop` into the signed string (`AuthQuery#to_signable_string` includes `shop`), showing the gem is capable of, and elsewhere does, bind the tenant identifier into the HMAC: [5](#0-4) 

The binding this breaks is: **HMAC-authenticated body == tenant identity claim (`shop`) trusted by the handler**. Because `shop` is excluded from the signed bytes, "bytes verified" (the raw JSON body) ≠ "bytes/claims acted on" (`topic`, `shop`, `webhook_id`, `api_version`, all pulled from unsigned headers and handed to the handler as authenticated `WebhookMetadata`): [6](#0-5) 

Crucially, `api_secret_key` is a single app-level secret shared across every shop that installs the app — it is not per-shop. Any merchant who installs the app is an "unprivileged internet user" with respect to other tenants of the same app, yet they legitimately receive real Shopify webhooks (with valid HMACs) for their own shop. Because the HMAC never covers `shop`, that same attacker can take a genuinely-signed webhook body+HMAC pair (from their own shop) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop domain. `HmacValidator.validate` will still pass (the body/HMAC pair is untouched), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` equal to the victim's domain, causing the host application to process attacker-controlled webhook data as if it originated from the victim tenant.

### Impact Explanation
This breaks tenant isolation for any app that keys per-shop logic (e.g., updating shop-specific data, associating a webhook payload with a shop's session, or triggering privileged per-shop actions) off `WebhookMetadata#shop`, since that field is unauthenticated despite being surfaced by the gem as part of the verified webhook flow. This matches the "Critical - cross-tenant access" impact category: an attacker in tenant A can cause the application to process fabricated events as belonging to tenant B, using only a legitimately obtained (own-shop) HMAC-signed webhook and a forged HTTP header — no `api_secret_key`, access token, or victim credentials are required.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate app installation to obtain one validly-signed webhook body/HMAC pair for a topic the app subscribes to, and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a spoofed `shopify-shop-domain` header — both trivially available to any unprivileged merchant using the app. The gem provides no mechanism to bind `shop` to the signature, and the vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler dispatch) is the only verification step documented and exercised by this library.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed material verified for webhook requests, or otherwise cryptographically bind the tenant identifier to the HMAC-covered bytes before it is exposed via `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and that consuming applications must independently verify the shop against a known/expected value (e.g., compare against the shop tied to the registration or an active session) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook to the app: body `B`, header `x-shopify-hmac-sha256: H = HMAC-SHA256(api_secret_key, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute the same value as before (body unchanged), so `HmacValidator.validate` returns `true`: [7](#0-6) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...))`, and the host application processes attacker data believing it is from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
