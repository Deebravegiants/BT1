### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `Utils::HmacValidator` only verifies the raw request body. `Registry.process` treats a passing HMAC check as validation of the *entire* request, then forwards the unauthenticated `shop` (plus `topic`, `webhook_id`, `api_version`) into `WebhookMetadata`, which host apps use to attribute webhook data to a tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers, which are never part of the signed string: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` only (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates the whole request on this body-only HMAC check, then immediately reuses the unauthenticated `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

This exactly mirrors the report's bug class: a "verification" step (`HmacValidator.validate`, analogous to `intToUint`/`toScaledUint`) is treated as validating the full object, but it actually only covers a subset (the body) while a security-critical field (`shop`) silently passes through unchecked - breaking the equality `shop authenticated by HMAC == shop trusted by the handler`.

### Impact Explanation
Because `shop` is not bound to the HMAC, an attacker who has legitimate access to the app on **any one shop** (e.g., their own store where the app is installed) can capture a real, correctly-signed webhook (raw body + valid HMAC computed with the app's real `api_secret_key`) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop. `HmacValidator.validate` still passes (it only checks the body/HMAC pair), and `WebhookMetadata#shop` is populated with the attacker-chosen victim domain. Any host application following this gem's documented contract (`data.shop`) for tenant routing/authorization will process or persist data under the wrong tenant - a cross-tenant identity confusion driven entirely by this gem's own validation logic.

### Likelihood Explanation
Any merchant/developer with the app installed on their own store can capture a genuine webhook payload+HMAC pair from Shopify (no privileged access, no `api_secret_key` needed) and immediately reuse it against the same public webhook endpoint with a forged shop header. `Registry.process`'s HMAC gate provides no protection for the `shop` field, so the forged request is indistinguishable from an authentic one to the gem.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the verified body), so `HmacValidator.validate` fails whenever any identity-bearing header is altered. Short term, at minimum document/enforce that `WebhookMetadata#shop` must be cross-checked against a known/installed shop list before use, since it is currently unauthenticated in `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) and `HmacValidator` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).

### Proof of Concept
1. Install the app on attacker-controlled shop `eve.myshopify.com`; wait for/trigger a genuine webhook (e.g. `orders/create`) and capture the raw body `B` and its `X-Shopify-Hmac-Sha256: H` header (both real, produced by Shopify with the app's real `api_secret_key`).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` accepts it (only checks header *presence*, not value binding) - `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` → passes - `lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `WebhookMetadata.new(..., shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and handed to the app's handler, which (per the gem's own documented usage) uses `data.shop` to route/persist data - `lib/shopify_api/webhooks/registry.rb:198-199`, `docs/usage/webhooks.md:12-17` (docs excluded from scope but shown here only to establish the intended/trusted use of `data.shop`).
6. The host app now believes attacker-controlled webhook content originated from the victim shop, causing cross-tenant data confusion using only the app's own valid signature and Eve's unprivileged access to her own store.
