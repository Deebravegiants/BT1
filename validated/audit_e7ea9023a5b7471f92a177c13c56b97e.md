Audit Report

## Title
Claims pallet skips vesting-capacity pre-check when destination already has active (non-fully-vested) schedules, allowing silent `add_vesting_schedule` failure to leave claimed funds fully liquid - (File: polkadot/runtime/common/src/claims/mod.rs)

## Summary
`Claims::process_claim` gates the `T::VestingSchedule::can_add_vesting_schedule` pre-check behind `T::VestingSchedule::vesting_balance(&dest).is_none()`, so the capacity check is skipped whenever the destination already has an active (non-fully-vested) vesting schedule. The subsequent `add_vesting_schedule` call at the end of `process_claim` is only guarded by `debug_assert!`, which is compiled out in release builds, so a failure there (e.g., `Error::AtMaxVestingSchedules`) is silently swallowed after the claim balance has already been deposited and the claim/vesting storage entries removed.

## Finding Description
In `polkadot/runtime/common/src/claims/mod.rs`, `process_claim` reads the pending `Vesting::<T>` entry for the signer, conditionally calls `T::VestingSchedule::can_add_vesting_schedule` only when `vesting_balance(&dest)` is `None`, then unconditionally performs `Total::<T>::put`, `Claims::<T>::remove`, `Vesting::<T>::remove`, and `CurrencyOf::<T>::deposit_creating(&dest, balance_due)`, followed by `T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)` whose result is only checked with `debug_assert!(res.is_ok(), ...)` [1](#0-0) .

`vesting_balance` in `pallet_vesting` (`substrate/frame/vesting/src/lib.rs`) returns `Some(_)` whenever the account has an active, non-fully-vested lock, and `None` only for accounts with no locked vesting balance [2](#0-1) . An attacker can fill `MaxVestingSchedules` slots on their own account via repeated, unprivileged `pallet_vesting::vested_transfer` calls, producing exactly the "active, non-fully-vested schedule" state that causes `process_claim`'s pre-check to be skipped. When the claim is then processed, `add_vesting_schedule` internally does `schedules.try_push(...).map_err(...)?`, which fails with `Error::AtMaxVestingSchedules`, but this failure is discarded by the no-op `debug_assert!` in production builds — after the currency deposit and storage cleanup have already committed. This leaves the claimed balance fully liquid with no vesting lock, breaking the invariant that a claim with `vesting_schedule = Some(..)` must always result in a locked balance.

## Impact Explanation
An unprivileged attacker can permanently bypass the intended vesting lock on a claims-based token grant, converting what should be a linearly-vesting, locked balance into an immediately transferable one. This is a concrete accounting/invariant violation in an in-scope pallet (`pallet-claims` used by the relay chain runtime), not a theoretical or admin-only issue.

## Likelihood Explanation
The exploit requires only ordinary, unprivileged extrinsics: (1) repeatedly calling `pallet_vesting::vested_transfer` to fill `MaxVestingSchedules` with active schedules on the destination account, then (2) triggering `Claims::claim`/`claim_attest` for a claim entry with `vesting_schedule = Some(..)` targeting that account. No governance, no privileged origin, and no race condition are needed, making this fully repeatable by any user controlling the destination account and possessing (or colluding with) a valid Ethereum-linked claim signature.

## Recommendation
Remove the `vesting_balance(&dest).is_none()` gating and always invoke `can_add_vesting_schedule` (or equivalent capacity validation) before any state mutation whenever `vesting.is_some()`. Additionally, replace the `debug_assert!` on the final `add_vesting_schedule` call with real error propagation — either perform the currency deposit/storage removal only after `add_vesting_schedule` succeeds, or wrap the whole sequence in a storage-transactional block that reverts on failure, ensuring a failed vesting attachment aborts the entire claim rather than leaving funds credited and unlocked.

## Proof of Concept
1. In a test using `polkadot/runtime/common/src/claims/tests.rs` mock runtime, call `Vesting::vested_transfer` `MaxVestingSchedules` times for the attacker's destination account with small locked amounts and non-trivial `per_block` so the schedules remain active (not fully vested).
2. Populate `Claims::Vesting` and `Claims::Claims` for the attacker's Ethereum-linked signer with `vesting_schedule = Some((locked, per_block, starting_block))` and nonzero `balance_due`.
3. Call `Claims::claim` (or `claim_attest`) for that signer.
4. Assert that if the call returns `Ok(())`, `Balances::locks(&dest)` should contain a vesting lock covering `balance_due`.
5. In a release-profile build (where `debug_assert!` is a no-op), observe the call returns `Ok(())`, `Balances::free_balance(&dest)` increases by `balance_due`, but no corresponding vesting lock exists — demonstrating the funds are fully liquid despite `vesting_schedule` being set.
