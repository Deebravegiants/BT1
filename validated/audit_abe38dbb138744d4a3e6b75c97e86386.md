## Finding

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (tenant identifier) is read from an unrelated, unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands the unverified `shop` value straight to the host application's webhook handler as the tenant key. Anyone who can obtain one legitimately-signed webhook body (e.g. by installing the app on their own store) can replay that exact body with a different `shopify-shop-domain` header and have it accepted as a valid, authentic webhook "from" any other shop.

### Finding Description
`Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac == HMAC(secret, to_signable_string)`, i.e. it only authenticates the body bytes, never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` directly from `request.shop`, passing it to the host application's handler as the authenticated tenant identity: [4](#0-3) 

This reproduces the M03 bug class exactly as described in the rules: "a field acted on but not covered by the HMAC" — here, `shop` is acted on (used as the tenant key by every downstream handler, as confirmed by the gem's own tests asserting `data.shop == @headers["x-shopify-shop-domain"]`) but is never part of the signed payload. The equality that should hold — `shop authenticated == shop the handler acts on` — is broken because the HMAC binds only to `raw_body`, not to `shop-domain`. [5](#0-4) 

### Impact Explanation
An attacker who is a normal, unprivileged Shopify merchant (installs the target app on their own store, which is the ordinary self-service flow for most apps) will receive genuine webhook deliveries for their own shop, signed by Shopify with the app's real `api_secret_key`. Because the HMAC covers only the body, the attacker can resend the exact same signed body to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Registry.process` will accept the forged request as authentic (the HMAC still validates) and invoke the host app's handler with `shop` set to the victim's domain and attacker-controlled body content. Any host application that follows the gem's documented pattern of using `WebhookMetadata#shop` to select/scope tenant data will process attacker-controlled data under a victim tenant's identity — a cross-tenant access/data-integrity breach (e.g. forging `orders/create`, `app/uninstalled`, or other lifecycle events for a shop the attacker does not control).

### Likelihood Explanation
Exploitation requires no access to the app's `client_secret`, no access token, and no privileged account beyond normal (self-service) app installation on the attacker's own store — a capability any internet user with a Shopify store has. The webhook endpoint is public by design. This is not a misuse of undocumented behavior: the gem's own test suite (`test/webhooks/registry_test.rb`) demonstrates that `WebhookMetadata#shop` is the documented, intended way for host apps to determine which tenant a webhook belongs to, while the underlying HMAC check in this gem never binds that value.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version/webhook-id) in the HMAC-covered payload, or otherwise cryptographically bind the shop header to the request before it is trusted (e.g., store the expected shop-per-topic pairing at registration time and re-derive/verify it independently, or require verification that the shop the app registered the webhook for matches an authoritative source rather than the client-supplied header). At minimum, `Utils::HmacValidator` should be updated so the signable content used for webhooks incorporates all header fields that host applications are expected to rely on for authorization decisions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary merchant onboarding).
2. Attacker triggers a real webhook event (e.g., updates a product) and captures the raw POST body and its `x-shopify-hmac-sha256` header, both computed by Shopify using the app's real `api_secret_key`.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)`: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and, following the gem's documented pattern, processes it as an authentic event for `victim-shop.myshopify.com`.
