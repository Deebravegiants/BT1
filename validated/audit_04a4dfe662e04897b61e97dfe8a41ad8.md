### Title
Unauthorised `transferFrom` of Arbitrary Approved Users' Tokens via `DepositOnChainUtxosExternalAction.originalSender` - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction()` pulls ERC20 tokens with `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` where `userAddress = circomData.originalSender` [1](#0-0) [2](#0-1) . Unlike `Hinkal._internalTransact()`, which explicitly requires `circomData.externalActionData.externalAddress == msg.sender` before pulling deposit funds [3](#0-2) , this external action never checks that `originalSender` is the actual transaction sender/prover. Any address that has ever left a standing ERC20 `approve()` for this contract (a normal residue of prior legitimate use, since `Transferer.approveToken` sets exact allowances per call [4](#0-3) , but any user-set infinite/leftover approval also qualifies) can have its tokens pulled by anyone who submits a `transact()` call naming that address as `originalSender`.

### Finding Description
`Hinkal.transact()` dispatches to `_externalTransact()` for external-action transactions, which forwards `circomData` unchanged to `runAction()` [5](#0-4) . `DepositOnChainUtxosExternalAction.runAction()` is guarded only by `onlyAllowedRecipient`, i.e. it trusts any registered `Hinkal`/relay contract to supply well-formed `CircomData` [6](#0-5) . Nothing in this action, nor in `Hinkal.transact()`'s post-execution checks, ties `circomData.originalSender` to `msg.sender` or to any value bound by the ZK proof's authorization of spend. The proof only proves knowledge of the prover's own shielded-note nullifiers/outputs — it says nothing about the identity or consent of `originalSender`, whose only real-world link to the transaction is an on-chain ERC20 allowance previously granted to this contract address.

The global balance equation in `Hinkal.transact()` only enforces value conservation (`balanceDif == amountChanges/0 + utxoAmount`) [7](#0-6) ; it does not enforce that the funds came from an authorized party. Since the attacker mints the shielded UTXOs to `circomData.stealthAddressStructure` (an attacker-controlled recipient descriptor) while the underlying tokens are pulled from the victim's wallet, the balance equation is self-consistently satisfied while ownership is stolen.

### Impact Explanation
This is a direct theft of a third party's on-chain approved ERC20 balance, converted into shielded value controlled by the attacker — matching the "Critical: direct theft of shielded or in-flight user funds" category. The victim's approval, once granted for any legitimate deposit flow to this contract, becomes a standing attack surface usable by anyone who can submit a valid proof for their own unrelated shielded notes.

### Likelihood Explanation
Exploitation requires only (1) a victim address with a non-zero ERC20 allowance to `DepositOnChainUtxosExternalAction`, and (2) an attacker able to submit any valid `transact()` proof for their own shielded UTXOs (a normal, permissionless capability of every Hinkal user/relay). No admin, relay, or victim key is required — the attacker fully controls `circomData.originalSender`, `externalActionMetadata` (the `utxoAmounts`), and `stealthAddressStructure`.

### Recommendation
Bind `originalSender` (or eliminate it) so that ERC20 pulls in this action can only be authorized by the actual depositor: require `circomData.originalSender == msg.sender` at the `Hinkal.transact()` level (mirroring the check already used in `_internalTransact`), or require `originalSender` to be cryptographically committed inside the ZK proof's signed public input, and additionally verify the caller supplied a matching signature/approval for that specific `tokenTotal` rather than relying on a pre-existing standing allowance.

### Proof of Concept
1. Victim `V` previously used `DepositOnChainUtxosExternalAction` (or otherwise approved it) and still has `allowance(V, DepositOnChainUtxosExternalAction) >= X` for token `T`.
2. Attacker `A` builds a valid ZK proof for their own shielded notes (any legitimate self-contained transaction), sets `externalActionId` to this action's id, `circomData.originalSender = V`, `circomData.erc20TokenAddresses = [T]`, `deltaAmounts[i] = 0`, `onChainCreation[i] = true`, and `externalActionMetadata` encoding `utxoAmounts = [[X]]`, with `stealthAddressStructure` pointing to `A`'s own stealth key.
3. `Hinkal.transact()` calls `_externalTransact` → `runAction()`, which executes `transferERC20TokenFrom(T, V, msg.sender=Hinkal, X)` [2](#0-1) , pulling `X` tokens from `V` without `V`'s transaction-level consent.
4. The resulting UTXO of amount `X` is inserted as an on-chain commitment owned by `A`'s stealth address; `A` later spends it, completing the theft.
