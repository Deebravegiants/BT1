Audit Report

## Title
`assigned_slots::TemporarySlots`/`TemporarySlotCount` desync via `paras_registrar::deregister` on a not-yet-leased temporary slot - (File: polkadot/runtime/common/src/assigned_slots/mod.rs)

## Summary
`assign_temp_parachain_slot` records a `TemporarySlots` entry and increments `TemporarySlotCount` unconditionally, but only calls `configure_slot_lease` (which drives the para's `ParaLifecycle` toward `Parachain` via `T::Leaser::lease_out`) when `SlotLeasePeriodStart::Current` is chosen and the active-slot cap isn't reached. [1](#0-0)  When `SlotLeasePeriodStart::Next` is used (or the cap is saturated), the para's `ParaLifecycle` stays `Parathread`, and `paras_registrar::do_deregister` — which gates solely on `ParaLifecycle` — will allow that para's manager to deregister it, leaving a stale `TemporarySlots` entry and an un-decremented `TemporarySlotCount`. [2](#0-1) 

## Finding Description
`assign_temp_parachain_slot` inserts into `TemporarySlots` and increments `TemporarySlotCount` unconditionally at the end of the extrinsic, but the actual lease creation (`configure_slot_lease`, which internally calls `T::Leaser::lease_out` and eventually flips the para's lifecycle away from `Parathread`) is conditional on `lease_period_start == SlotLeasePeriodStart::Current` and `ActiveTemporarySlotCount::<T>::get() < T::MaxTemporarySlotPerLeasePeriod::get()`. [3](#0-2) 

`configure_slot_lease` merely forwards to `T::Leaser::lease_out`; it is the only path in this pallet that changes on-chain lease/lifecycle state for a temporary slot. [4](#0-3) 

Meanwhile, `paras_registrar::do_deregister` allows deregistration whenever the para's lifecycle is `Parathread` or `None`, with no awareness of `assigned_slots` state at all: [2](#0-1) 

The `deregister` extrinsic is reachable by a signed para manager via `ensure_root_para_or_owner`, which accepts the para's manager as a valid caller as long as the para isn't locked: [5](#0-4) [6](#0-5) 

There is no cleanup hook wired between `paras_registrar` and `assigned_slots` for the deregistration path — the only cross-pallet hook (`T::OnSwap`) fires on the `swap` extrinsic, not on `deregister`, and in the runtimes examined it is wired to `coretime::Pallet::on_legacy_lease_swap`, not to `assigned_slots`. `assigned_slots` only clears its own storage inside `unassign_parachain_slot`, which is a privileged (`AssignSlotOrigin`) call that the para manager cannot themselves trigger. [7](#0-6) 

This confirms the claim's exploit chain: assign a temporary slot with `SlotLeasePeriodStart::Next` (or while `ActiveTemporarySlotCount` is at cap) → `ParaLifecycle` stays `Parathread` → manager calls `deregister` → `do_deregister` succeeds because its only check passes → `TemporarySlots`/`TemporarySlotCount` are left stale, permanently desynchronized from the actual registered-para set.

## Impact Explanation
The stale `TemporarySlots` entry and un-decremented `TemporarySlotCount` permanently strand a unit of capacity against the governance-configured `MaxTemporarySlots` cap, since nothing decrements it for a deregistered `ParaId`. The orphaned entry is also iterated by `allocate_temporary_slot_leases`, which will attempt `configure_slot_lease` for a `ParaId` that no longer exists, wasting weight in a periodic `on_initialize` hook and behaving unpredictably against a nonexistent para. This is a real accounting-desync/griefing issue: it reduces available temporary slot capacity for future legitimate parathreads and pollutes periodic scheduler logic, but it does not cause fund loss or a chain halt.

## Likelihood Explanation
The precondition (temporary slot assigned with `SlotLeasePeriodStart::Next`, or cap saturation at assignment time) is a normal governance-driven state of `assigned_slots`, not a contrived edge case — `SlotLeasePeriodStart::Next` is an explicitly supported option of the extrinsic. Once that state exists, any ordinary para manager can trigger the desync with a single unprivileged `deregister` call, with no special access needed beyond being that para's manager, making this readily repeatable.

## Recommendation
`paras_registrar::do_deregister` should reject deregistration if the para still has any `assigned_slots::PermanentSlots`/`TemporarySlots` entry, or `assigned_slots` should expose a cleanup hook invoked by `do_deregister` to remove/decrement the corresponding entry and counters, mirroring the cleanup already performed in `unassign_parachain_slot`.

## Proof of Concept
In `polkadot/runtime/common/src/assigned_slots/mod.rs` test module:
1. Register a para as an on-demand parathread via `TestRegistrar::register`.
2. Call `AssignedSlots::assign_temp_parachain_slot(RuntimeOrigin::root(), id, SlotLeasePeriodStart::Next)`; assert `TemporarySlots::<Test>::get(id).is_some()`, `TemporarySlotCount::<Test>::get() == 1`, and `TestRegistrar::<Test>::is_parachain(id) == false`.
3. As the para's signed manager, call `paras_registrar::Pallet::deregister(RuntimeOrigin::signed(manager), id)` and assert `Ok(())`.
4. Assert `paras::Pallet::<Test>::lifecycle(id).is_none()`.
5. Assert `TemporarySlots::<Test>::get(id).is_some()` and `TemporarySlotCount::<Test>::get() == 1`, demonstrating the stale, un-decremented accounting.

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
