### Title
Silent u128→u64 truncation of pnl amounts in `calc_take_pnl` breaks pool accounting - (File: `program/src/processor.rs`)

### Summary
`Calculator::calc_take_pnl` (in `program/src/processor.rs`) computes `pc_pnl_amount` and `coin_pnl_amount` as `U128` values and casts them down to `u64` with a bare `.as_u64()` call, exactly the same unchecked-downcast pattern flagged in the Caviar `buy()`/`sell()` report (`uint128(netInputAmount - feeAmount - protocolFeeAmount)`). Unlike Caviar, the underlying `uint` crate's `U128::as_u64()` performs a silent, non-panicking truncation (it simply returns the low 64 bits), so if the pre-cast `U128` value ever exceeds `u64::MAX`, the on-chain state is corrupted without any revert.

### Finding Description
In `calc_take_pnl`, the pnl deltas are derived from **normalized** reserve amounts: [1](#0-0) 

`diff_x`/`diff_y` come from `normalize_decimal_v2`, which scales the raw `u64` vault amount by `sys_decimal_value` and divides by `10^native_decimal`: [2](#0-1) 

`restore_decimal` then reverses that scaling using the token's own `native_decimal`: [3](#0-2) 

The result `diff_pc_pnl_amount` / `diff_coin_pnl_amount` is multiplied by `pnl_numerator`/`pnl_denominator` and then cast with a bare `.as_u64()` — not via `Calculator::to_u64`, which safely uses `try_into` and errors out on overflow: [4](#0-3) 

For comparison, other parts of the codebase intentionally use the safe `Self::to_u64` (checked) path: [5](#0-4) 

Because `restore_decimal` multiplies by `10^native_decimal` (the coin/pc mint's own decimals, which is attacker/creator controllable at pool `Initialize2` time via any SPL mint) before dividing by the fixed `sys_decimal_value`, a token with unusually high decimals (analogous to the "High Decimals Token" PoC in the Caviar report) can push the intermediate `U128` value for `diff_pc_pnl_amount`/`diff_coin_pnl_amount` far above `u64::MAX` even though the underlying vault balances themselves are legitimate `u64` amounts. The subsequent `.as_u64()` silently truncates to the low 64 bits instead of erroring, producing an arbitrary, attacker-influenced `pc_pnl_amount`/`coin_pnl_amount`.

This corrupted value is then used to update the AMM's take-pnl accounting via `checked_add`/`checked_sub` on `amm.state_data.need_take_pnl_pc/coin` and `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, breaking the `x*y=k` accounting invariant that the swap math (`swap_token_amount_base_in/out`) relies on for pricing: [6](#0-5) 

`calc_take_pnl` is invoked from `process_deposit`/withdraw and swap paths that any unprivileged LP/swapper can trigger by simply calling `Deposit`/`Withdraw`/`SwapBaseIn`/`SwapBaseOut` on a pool whose `TargetOrders` state satisfies the `pool_pc*pool_coin >= calc_pc*calc_coin` branch: [7](#0-6) 

### Impact Explanation
If the truncation triggers, `need_take_pnl_pc`/`need_take_pnl_coin` and `total_pc_without_take_pnl`/`total_coin_without_take_pnl` become desynchronized from the pool's real token balances. Since every subsequent swap price/output (`swap_token_amount_base_in`/`swap_token_amount_base_out`) and every deposit/withdraw LP-token mint/burn is computed from these `total_*_without_take_pnl` figures, a corrupted value permanently distorts the pool's invariant, enabling incorrect swap pricing, unbacked LP token issuance, or drainage of vault funds by the party who benefits from the mis-accounted reserves — the same class of impact the original H-03 finding was rated High for (breakdown of the `x*y=k` equation with pool/LP fund loss).

### Likelihood Explanation
Reaching the vulnerable branch requires a `TargetOrders`-integrated pool (Raydium OpenBook/Serum-integrated markets) where `calc_take_pnl`'s conditional branch executes, and a coin/pc mint with sufficiently large `native_decimal` relative to `sys_decimal_value` so the intermediate `restore_decimal` product overflows `u64` before the final fee multiply/divide. Since pool creation and mint choice for AMM markets is constrained by Raydium's own market-creation process (not fully permissionless per-pool the way Caviar pools are), likelihood is lower than the original Caviar bug, but the code path itself contains the identical unchecked-downcast defect and is reachable from ordinary `Deposit`/`Withdraw`/swap instructions without any privileged signer.

### Recommendation
Replace the bare `.as_u64()` calls on `pc_pnl_amount`/`coin_pnl_amount` (and any other direct `U128`→`u64` downcasts in `calc_take_pnl`) with the checked `Calculator::to_u64` helper (which already exists and is used elsewhere) so overflow causes a transaction revert (`AmmError::ConversionFailure`) instead of silently truncating and corrupting pool accounting: [5](#0-4) 

### Proof of Concept
Conceptual PoC (mirrors the Caviar "HighDecimalsToken" PoC):
1. Create/target an AMM pool where the pc or coin mint has an unusually large number of decimals relative to `sys_decimal_value` used by the AMM (`amm.sys_decimal_value`, set at `Initialize2`).
2. Build vault balances and `TargetOrders.calc_pnl_x/y` state such that the `pool_pc*pool_coin >= calc_pc*calc_coin` branch in `calc_take_pnl` is taken. [8](#0-7) 
3. Trigger the branch via a normal `Deposit`, `Withdraw`, or swap instruction; because `restore_decimal` scales `diff_x`/`diff_y` by `10^native_decimal`, choose decimals large enough that `diff_pc_pnl_amount`/`diff_coin_pnl_amount` (as `U128`) exceeds `u64::MAX` prior to the `.as_u64()` cast at lines 237/243 of `processor.rs`.
4. Observe that `pc_pnl_amount`/`coin_pnl_amount` wrap to an unrelated small/garbage value, and `amm.state_data.need_take_pnl_pc/coin` and `total_pc_without_take_pnl`/`total_coin_without_take_pnl` are updated with this corrupted figure instead of reverting, permanently desynchronizing on-chain reserve accounting from actual vault balances.

Note: full confirmation of the exact numeric bound (whether real-world SPL mint decimal limits and `sys_decimal_value` configuration make the overflow practically reachable) requires reading `state.rs`'s `initialize2`/decimals validation logic and `instruction.rs`'s `sys_decimal_value` constant in full, which the current index did not return before the tool budget was exhausted — a Devin session with full repo access would be needed to verify the concrete decimal bounds and finalize a numeric exploit.

    }
