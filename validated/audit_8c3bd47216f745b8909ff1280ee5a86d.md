## Analysis Result

### Title
Webhook Shop-Domain and Topic Headers Are Not Covered by HMAC, Enabling Cross-Tenant Webhook Forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop`, `topic`, and `webhook_id` fields used to route and attribute the webhook to a tenant are read straight from unauthenticated HTTP headers. This breaks the identity binding: `HMAC-verified bytes == raw_body` but `shop/topic used by the handler == unauthenticated header`, allowing a party who has intercepted one valid `(raw_body, hmac)` pair issued for their own shop to replay it against the app's webhook endpoint with forged `shop`/`topic` headers, causing cross-tenant webhook processing.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body — none of the Shopify headers are included in the signed material: [2](#0-1) 

`Registry.process` uses that same HMAC-validated request object to pull `shop`, `topic`, and `webhook_id` from headers and hands them directly to the app's business-logic handler as trusted tenant-identifying data: [3](#0-2) 

Because a given Shopify app uses **one shared `client_secret`/`api_secret_key` across every installed shop**, any merchant that legitimately receives a real webhook for their own shop possesses a valid `(raw_body, hmac)` pair signed with that shared secret. Since headers are not part of the signed payload, that same pair remains valid when replayed with a different `x-shopify-shop-domain` and/or `x-shopify-topic` header. The identity binding the code implicitly assumes — "`hmac` authenticates `shop`" — does not actually hold; `hmac` only authenticates `raw_body`.

### Impact Explanation
This is a cross-tenant integrity break: an attacker who is a legitimate (unprivileged, from the app's perspective) installer of the app for their own shop can cause the host application to process a forged webhook payload attributed to a *different* merchant's shop, since `WebhookMetadata#shop` (trusted by the handler for tenant lookup/dispatch) is taken from the unauthenticated header rather than anything covered by the HMAC. Depending on how the host app uses `data.shop` (e.g., loading that shop's session/access token, updating billing/subscription state, processing `app/uninstalled`, order or customer data events under another tenant's identity), this can lead to cross-tenant data corruption or unauthorized actions taken against another merchant's account — matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only that the attacker possesses one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and capturing any webhook delivery, or even by using known-plaintext topics like `app/uninstalled` sent from a controlled shop. No access token, `client_secret`, or privileged account is required; the attacker only needs to be able to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include the tenant/topic-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material actually verified against the HMAC, or otherwise cryptographically bind them (e.g., re-validate `shop` against the body's own `shop_id`/`myshopify_domain` field, or require the host app to cross-check `data.shop` against a known, already-authenticated tenant before trusting it) before dispatching to `handler.handle`.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and captures a real, validly-signed webhook delivery, e.g. for
#    topic "app/uninstalled":
#
#    headers:
#      x-shopify-topic: app/uninstalled
#      x-shopify-hmac-sha256: <valid HMAC over raw_body, computed w/ shared api_secret_key>
#      x-shopify-shop-domain: attacker.myshopify.com
#    raw_body: '{"id": 12345}'
#
# 2. Attacker replays the identical raw_body + hmac-sha256 header, but
#    swaps the shop-domain (and/or topic) header to target a victim shop:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => captured_valid_hmac,   # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)

# 3. HMAC validation passes because it only checks raw_body against the shared secret:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)
# The host app now processes an uninstall (or any other) event as if it came from victim-shop,
# despite the request being fully attacker-controlled aside from the reused raw_body/hmac.
