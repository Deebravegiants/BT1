### Title
Fixed per-module `OutboundRequestDeliveryReward` is uncoupled from the volume/cost of dispatches an allowlisted module can produce, enabling cheap redemption of an oversized treasury reward - ([File: modules/pallets/relayer/src/lib.rs])

### Summary
`pallet-relayer` pays a **governance-set, fixed BRIDGE reward per delivered request** to whoever proves delivery of a hyperbridge-originated request from an allowlisted `module_id`, regardless of how cheaply that module can be made to emit another dispatchable request. This mirrors the `WhereIsMyDragonTreasure` bug class exactly: a fixed redemption price paid per unit, while the marginal cost of producing another redeemable unit is far below that price.

### Finding Description
`OutboundRequestDeliveryReward<T>` is a `StorageMap<ModuleId, BalanceOf<T>>` set by governance via `set_outbound_request_delivery_reward` [1](#0-0) . Any module whose `from` field matches an allowlisted `module_id` earns a *flat* reward for **every distinct request commitment** it dispatches, paid from `TreasuryPalletId` on `claim_outbound_request_delivery_reward` [2](#0-1) . The only anti-replay control is idempotency per-commitment (`OutboundRequestsClaimed`), not a cap on the number of commitments a module can produce, nor any linkage between the reward and the actual dispatch cost.

The demonstrated production pattern for this reward, `pallet-ismp-demo`'s `dispatch_to_evm`, shows the shape of the flaw concretely: any signed, unprivileged account can call it with an attacker-chosen `count`, generating that many `PostRequest`s from a single `module_id`, each charged only the pallet's flat extrinsic weight and `fee: Default::default()` [3](#0-2) . Once governance sets a non-zero reward for that `module_id` (exactly the workflow documented for enabling incentivization) [4](#0-3) , each of those cheaply-produced commitments becomes independently claimable for the full fixed reward once delivered and proven — via the same relayer, acting in its own interest, both delivering and claiming.

The design doc itself frames the reward level as "the right level of control" set once by governance per module, explicitly *not* tied to per-byte/per-request dispatch cost [5](#0-4) . This confirms the reward is a fixed price, decoupled from the true cost of producing a redeemable unit (the dispatched request) — the same root cause as `WhereIsMyDragonTreasure`, which paid a fixed `_singleReward` per legendary card while the effective mint cost via cheap recipes was lower.

### Impact Explanation
Any module that governance allowlists with a non-zero `OutboundRequestDeliveryReward`, and that permits even semi-cheap, high-volume, unprivileged triggering of dispatches (the `pallet-ismp-demo` pattern, or any future module - the docs explicitly reference "future modules like bandwidth" being in scope for this reward system), lets an attacker mass-produce request commitments at near-zero marginal cost and redeem the treasury's BRIDGE balance repeatedly, since the reward is flat per commitment with no cap. This is theft/unbacked drain of the `TreasuryPalletId` account, a real fund-loss vector once any such module is enabled with a reward.

### Likelihood Explanation
Currently `pallet-ismp-demo` (the concrete module exhibiting the exploitable dispatch pattern) is only wired into the `gargantua` testnet runtime, not the `nexus` production runtime, and the reward for it was only set via testnet `Sudo`. This significantly limits exploitability in production **today**. However, the reward mechanism itself lives in the shared `pallet-relayer` code that both runtimes could use, and the documented intent is to allowlist additional modules (host-executive, intents-coprocessor, token-governor, bandwidth) for the same flat reward without adding any dispatch-volume accounting. Likelihood is therefore **module-selection dependent**: safe as long as governance only allowlists modules whose dispatch triggers are privileged/rate-limited, but structurally unsafe against any future or overlooked allowlisted module that an unprivileged party can trigger cheaply and repeatedly.

### Recommendation
- Do not size `OutboundRequestDeliveryReward` as a flat per-commitment amount decoupled from dispatch cost; cap the number of rewarded commitments per module per time window, or size the reward against measured per-request cost (e.g., proportional to body size/weight, similar to the per-byte discipline used elsewhere).
- Before allowlisting any module for a reward, verify (and continue to verify on every future addition) that the module's dispatch path is either privileged, rate-limited, or itself charges a fee that meets/exceeds the configured reward, closing the arbitrage margin that this reward design otherwise creates.
- Add a governance-configurable per-module cap on outstanding/claimed rewards per block or per epoch as defense in depth, independent of which specific module is allowlisted.

### Proof of Concept
Not independently reproduced end-to-end (this analysis is based on static code/doc review, not an executed exploit). The mechanics validated from the codebase:
1. Governance calls `Relayer::set_outbound_request_delivery_reward(module_id, REWARD)` for a module, as documented and exercised on the `gargantua` testnet [6](#0-5) .
2. Any signed account calls that module's cheap dispatch entrypoint with a large `count`/loop to mint many `PostRequest`s from the same `module_id`, e.g. `pallet_ismp_demo::dispatch_to_evm` [3](#0-2) .
3. The attacker (or a colluding relayer) delivers each request to the destination chain and submits `claim_outbound_request_delivery_reward` for each resulting commitment, each payout of the full fixed `REWARD` coming out of `TreasuryPalletId` [7](#0-6) , with idempotency only preventing re-claiming the *same* commitment, not capping total volume.

Because the concretely demonstrated trigger (`pallet-ismp-demo`) is testnet-only in this snapshot of the codebase, I could not confirm a currently-live mainnet path exercising this specific module; the finding is reported as a structural design flaw in the reward mechanism itself, reachable in production the moment any unprivileged-dispatch module is allowlisted with a reward.

```rust
				new_reward: amount,
```

```markdown
## Why this shape and not the alternative

The other option was to attach a real fee at dispatch time, paid from a system-owned PalletId account, so that `RequestPayments` gets populated and the existing `accumulate_fees` flow Just Works. That sounds appealing because it reuses more code, but it has two problems.

First, `accumulate_fees` reads a *source* state proof to find the fee. For hyperbridge-originated requests the source *is* hyperbridge itself, so verifying a proof of hyperbridge state on hyperbridge is meaningless. It would need a new code path that reads local child-trie storage directly, which is the same thing we would have to add for the new claim anyway.

Second, the per-byte fee schedule was designed for protocol-fee economics on the source chain. Using it to size relayer rewards conflates two different knobs. A governance-set per-module reward is the right level of control, same as `OutboundConsensusDeliveryReward`.
```
