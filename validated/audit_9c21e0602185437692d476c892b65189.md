### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value that is handed to the application's handler (and used to attribute the event to a tenant) is read from an HTTP header that is not covered by that signature at all. This breaks the identity binding the report's bug class calls out: "a field acted on but not covered by the HMAC."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines `to_signable_string` to return only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors, however, are read directly from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) with no cryptographic binding to those header values: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per its implementation — computes the HMAC over `to_signable_string` (the body only) and compares it against the `hmac` header: [3](#0-2) 

After that check passes, `Registry.process` immediately forwards `request.shop` — the unauthenticated header value — into `WebhookMetadata`, which is what the app-supplied handler acts on: [4](#0-3) [5](#0-4) 

The equality the code implicitly assumes is:
`shop used by handler (request.shop from header) == shop that produced the signed body`

But the actual guarantee provided by `HmacValidator.validate` is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

Nothing ties the `shop-domain` header to the signed bytes. An unprivileged attacker who can obtain one legitimate `(raw_body, hmac)` pair for *any* shop (e.g., their own store, on which they can install the app and observe a real webhook delivery) can resend that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` passes the attacker-chosen shop straight to the handler as trusted, authenticated identity.

### Impact Explanation
This is a cross-tenant identity-binding bypass: webhook data that is cryptographically proven only to have originated from Shopify for *some* shop gets attributed to a `shop` value the attacker fully controls. Any host application that keys per-tenant logic (e.g., data deletion/redaction handling for `shop/redact`, `customers/redact`, updating tenant records, billing/state webhooks, `app/uninstalled`, etc.) off `WebhookMetadata#shop` can be made to act on behalf of, or against, a shop the attacker does not control, without ever having the target shop's `client_secret` or access token. This matches "cross-tenant access," a Critical-impact class per the fixed impact list.

### Likelihood Explanation
Exploitation requires only:
1. Ability to install the app once on any shop (including the attacker's own free/dev shop) to observe one legitimate webhook body+HMAC pair, and
2. Ability to send an HTTP POST with attacker-controlled headers to the app's public webhook endpoint (any unprivileged internet user can do this once they know the endpoint).

No knowledge of `api_secret_key`, no access token, and no privileged account on the target shop are required, and the request forgery works against any topic that the app has registered, since the signature check is topic/shop agnostic and only covers the byte-identical body.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated material, e.g., by including the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header values in the string that is HMAC-verified, or by deriving `shop` exclusively from a value that is itself covered by the signature (many webhook payloads include the shop domain in the JSON body — that body-derived value, not the header, should be what `WebhookMetadata#shop` exposes). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be used for tenant-scoped decisions until independently verified against the signed body content.

### Proof of Concept
1. Install the target app on shop A (attacker-controlled or public dev store) and capture one legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's real secret, since Shopify itself computed it for shop A).
2. Replay an HTTP POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (any shop string of the attacker's choosing).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(B, secret)` and compares to `H` — this succeeds because `B` and `H` are unmodified. [6](#0-5) 
4. `request.shop` returns the attacker-supplied `victim-shop.myshopify.com` header value [7](#0-6) , which is passed unchanged into `WebhookMetadata` and delivered to the app's `handler.handle`, causing the app to process the payload as if it legitimately originated from `victim-shop.myshopify.com`.
