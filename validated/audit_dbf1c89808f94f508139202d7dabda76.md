### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted as authenticated tenant identifiers but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook only by checking `Utils::HmacValidator.validate(request)`, and the HMAC signature computed for that check covers **only the raw request body**. The `shop-domain`, `topic`, `webhook-id` and `api-version` HTTP headers — which are handed to the app's handler as trusted, tenant-identifying metadata — are never included in the signed bytes, so any actor who can reach the app's public webhook endpoint can forge these header values while keeping a previously-observed valid `(body, hmac)` pair, causing the app to process the payload under an attacker-chosen shop/topic identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exactly over that `to_signable_string` value and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` and then immediately forwards `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` to the developer's handler as `WebhookMetadata`, with no additional check that these fields correspond to the shop/topic that actually produced the signed body: [4](#0-3) 

The library's own documentation tells the integrator that `process` "will verify the request did indeed come from Shopify" and that `data.shop`/`data.topic` are trustworthy fields to key business logic on (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

This is the exact bug-class pattern from the report: a field that is *acted on* (`shop`, used as the tenant key for the handler's business logic) is *not covered* by the HMAC that is supposed to authenticate the whole request. The binding the code implicitly claims to hold is:
`hmac_verified(request) == "shop, topic, webhook_id came from Shopify for this body"`
but what is actually proven is only:
`hmac_verified(request) == "this exact body byte-string was produced with the secret"`.

Any internet-reachable holder of one legitimate `(raw_body, hmac)` pair for their own shop (which any merchant who installs the app naturally receives) can replay that pair against the same endpoint with a different `shop-domain`/`topic`/`webhook-id` header set, since none of those headers affect signature validity.

### Impact Explanation
If the host application's webhook handler uses `data.shop` (as the docs recommend) to select which tenant's records to update, enqueue jobs against, or attribute the webhook body to, an attacker can make the app believe a webhook belongs to a different, victim shop while supplying an arbitrary attacker-controlled body from their own genuinely-signed webhook. This is a cross-tenant data confusion/cross-tenant access primitive: the app's decision of "which shop does this webhook belong to" is not authenticated, even though the app (per this gem's own documentation) treats it as if it were. Because `topic` is also unauthenticated, an attacker can additionally redirect a validly-signed body into a handler registered for a different topic than what Shopify actually sent.

### Likelihood Explanation
Exploitation requires only: (1) reachability of the app's public webhook HTTP endpoint (by design, unauthenticated/internet-facing), and (2) possession of one legitimately-signed `(body, hmac)` pair, which any user who installs the app on their own store and receives real webhooks obtains trivially and repeatedly. No access token, `client_secret`, or privileged account is needed — this is entirely reachable by an unprivileged internet user with a normal merchant/dev-store relationship to the app.

### Recommendation
Include the tenant/topic-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed bytes checked by `HmacValidator`, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`. At minimum, `Registry.process`/the documentation should make clear that `data.shop` and `data.topic` are **not** authenticated by the HMAC check and that integrators must independently verify the shop is one they have an active session/registration for before acting on the webhook.

### Proof of Concept
1. Merchant A installs the app; the app registers webhooks for shop `a.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: a.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id": 1, ...}`
3. Attacker (who is merchant A, or anyone who captured/replayed this request) resends the identical body and `hmac` header to the same endpoint but changes:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still returns `true` because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb` `to_signable_string`), which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-200) calls the handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"`, even though Shopify never sent this webhook for that shop.
6. Any handler logic keyed on `data.shop` (as recommended in `docs/usage/webhooks.md`) now operates on the wrong tenant.

```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
