### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, and `webhook_id` fields that drive downstream processing are read from unauthenticated HTTP headers that are never covered by that signature. This breaks the identity binding `bytes verified (raw_body) == bytes trusted for tenant identity (shop-domain header)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all pulled straight from HTTP headers with no cryptographic relationship to the HMAC: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery` — only checks `hmac` against `to_signable_string` (i.e. the raw body): [3](#0-2) [4](#0-3) 

Because `request.shop` is passed straight to the handler as the authoritative tenant identity without being part of the signed bytes, `WebhookMetadata.shop == raw_body-signed shop` does not hold — the shop is trusted despite being outside the signed payload.

### Impact Explanation
Any unprivileged internet user who can install the host app on their own Shopify store (a normal, unprivileged action) can obtain a genuinely-signed `(raw_body, hmac-sha256)` pair for a webhook targeting their own shop. Because the signature never covers the `shop-domain` (or `topic`/`webhook-id`) header, the attacker can replay that exact `raw_body` + valid `hmac-sha256` value to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it only re-derives the signature from `raw_body`. The host app's `WebhookHandler` then processes the payload believing it originated from the victim shop, causing the app to attribute the attacker's own data/event to a shop they do not control — a cross-tenant identity confusion mapped onto whatever state-changing action the app's webhook handler performs (e.g., writing/deleting per-shop records, triggering re-sync, disabling features) for the victim tenant.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop (no privilege beyond a free Shopify store), (2) capturing one legitimate webhook delivery for a topic the app subscribes to, and (3) sending a crafted HTTP request with the original body/HMAC but a forged shop header to the app's public webhook endpoint. No access to `client_secret`, tokens, or the victim's credentials is required, making this a directly reachable, low-effort attack path fully inside this gem's verification logic.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body — for example by including the normalized headers in `to_signable_string`, or by requiring callers to independently confirm `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker's own shop `attacker.myshopify.com`; trigger a subscribed webhook (e.g. `orders/create`) so Shopify sends a real `POST` with body `B` and header `x-shopify-hmac-sha256: H` (a valid signature of `B` using the app's real `client_secret`).
2. Capture `B` and `H` from the attacker's own webhook delivery.
3. Send a new HTTP request to the app's webhook endpoint with the same `raw_body = B`, same `x-shopify-hmac-sha256 = H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com"})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only compares `HMAC(B, secret)` to `H`, matching regardless of the shop header value: [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to process attacker-supplied data under the victim shop's identity.
