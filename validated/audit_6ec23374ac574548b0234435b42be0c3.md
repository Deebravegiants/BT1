## Finding

The webhook processing path in this gem validates the Shopify HMAC signature only over the raw request body, while the `shop` domain used to attribute the event to a tenant is taken from an HTTP header that is **not** part of the signed content. Since the webhook secret (`Context.api_secret_key`) is the same for every shop that installs the app, this breaks the binding `hmac_signed_bytes == bytes_that_determine_tenant_identity`. ### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the `shop-domain` header used later to attribute the event to a tenant is completely excluded from the signed payload.

### Finding Description
`Registry.process` performs:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac-sha256` header value. [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` is `@raw_body`, while `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed bytes:
```ruby
def to_signable_string
  @raw_body
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) 

Because `Context.api_secret_key` is the app-wide secret shared across every shop that installs the app (not a per-shop secret), a legitimate but low-privilege actor — anyone who installs the app on their own store — can obtain a correctly HMAC-signed `(body, hmac)` pair for their own shop's webhook traffic, then replay that exact body/hmac to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed because the header is not part of the signed content, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the forged victim domain. Equality that should hold — "the shop the event is attributed to" == "the shop whose secret/traffic produced the signature" — is broken.

### Impact Explanation
This is a cross-tenant confusion vector: an attacker who controls one shop (any free/dev store that installs the target app) can make the app process fabricated webhook events (e.g., `app/uninstalled`, `orders/create`, `customers/redact`, etc.) as if they originated from an arbitrary other shop using the app, because the tenant-selecting field (`shop`) is unauthenticated with respect to the signature that is supposed to prove the request's authenticity. Depending on how the host application keys business logic and data lookups off `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or triggering privileged per-shop actions for a shop the attacker does not control.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have any shop of their own with the app installed (a widely available, unprivileged action for public Shopify apps), and requires them to replay a raw HTTP POST to the app's known webhook endpoint with an altered header — no secret material, TLS interception, or privileged Shopify credentials are needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content that `HmacValidator` verifies, or otherwise independently authenticate the shop header against a trusted, previously established per-shop record (e.g., only accept `shop` values for shops that have prior authenticated sessions in this app's session storage) before acting on `WebhookMetadata#shop`. At minimum, document that `request.shop` is unauthenticated and must not be trusted for tenant attribution without an out-of-band check.

### Proof of Concept
1. Attacker creates `attacker-shop.myshopify.com`, installs the target app (a normal, unprivileged action), and subscribes to a webhook topic (e.g., `orders/create`).
2. Attacker triggers the event on their own store, capturing the resulting webhook HTTP POST: body `B` and header `x-shopify-hmac-sha256: H` (correctly computed with the app's shared `api_secret_key`, valid for `B`).
3. Attacker resends this exact request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act as though the event came from the victim shop.
