### Title
Reentrancy-protection heuristic misclassifies non-zero-value stipend calls as unprotected `AllowReentry` - (File: substrate/frame/revive/src/vm/evm/instructions/contract.rs)

### Summary
The `run_call` heuristic in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` decides the `ReentrancyProtection` mode from a tuple match on `(value.is_zero(), gas_limit == CALL_STIPEND)`. Because the `(false, _)` arm is matched first, any call with a non-zero `value` — including the canonical Solidity `.transfer()`/`.send()` pattern that always sends `value > 0` together with the fixed `2300` gas stipend — is forced into `ReentrancyProtection::AllowReentry`, bypassing the `AllowNext` protection the code explicitly says it wants to apply to stipend-limited calls.

### Finding Description
`run_call` builds the tuple `(value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))` and matches it as: [1](#0-0) 

```
(false, _) => (true, ReentrancyProtection::AllowReentry),
// Heuristic: detect when solc passes `gas_limit = 2300` (the call stipend).
// For zero-value transfer/send, solc injects `gas_limit = 2300` explicitly.
(_, true) => (true, ReentrancyProtection::AllowNext),
(_, _) => (false, ReentrancyProtection::AllowReentry),
```

The `(false, _)` arm has priority over `(_, true)` in Rust match evaluation order, so whenever `value != 0` the branch that checks `gas_limit == CALL_STIPEND` is never reached, regardless of the actual gas limit supplied. This is exactly backwards from the code's own stated intent: the comment claims the heuristic targets "solc transfer/send" calls, but Solidity's `.transfer(v)`/`.send(v)` are defined precisely as *value-transferring* calls with the fixed `2300` gas stipend — i.e., `value != 0 && gas_limit == 2300`. That is the primary real-world case the heuristic is supposed to catch, and it is the one case guaranteed to fall into `(false, _)` and get `AllowReentry` instead of `AllowNext`.

An attacker (any unprivileged contract deployer) can trivially construct `target.call{value: v, gas: 2300}(...)` with `v > 0` (or simply use Solidity's `.transfer()`/`.send()`, which the compiler already emits this way) and the runtime will apply `ReentrancyProtection::AllowReentry` to a call the developer/protocol intended to be gas-stipend-restricted. No signature, origin, fee, or weight check inspects this classification — it is purely an internal interpreter heuristic used to select the reentrancy-guard mode passed to `Ext::call`/`Ext::delegate_call`.

### Impact Explanation
Any contract relying on the 2300-gas stipend pattern (the same pattern Ethereum's `.transfer()`/`.send()` traditionally use to prevent reentrant state changes in the callee) receives `AllowReentry` instead of `AllowNext` from pallet-revive's EVM-compat layer. A malicious callee contract that would otherwise be constrained to “not enough gas to do meaningful reentrant work” gets classified without additional reentrancy restriction, letting the runtime permit a call path a caller may be structurally relying on to be non-reentrant. This is scoped strictly to the reentrancy-classification logic in `run_call`, matching the described impact.

### Likelihood Explanation
Highly likely to trigger unintentionally, not merely as a crafted edge case: it is hit by the standard/idiomatic Solidity `.transfer()` and `.send()` calls (both send non-zero `value` with `gas_limit == 2300`), so essentially every contract compiled with solc that uses these built-ins on pallet-revive's EVM interpreter is affected. An attacker does not need any privileged access — deploying and invoking an ordinary contract using `.transfer()`/`.send()` or manually specifying `call{value: v, gas: 2300}` is sufficient and fully reproducible.

### Recommendation
Reorder the match so that the `gas_limit == CALL_STIPEND` check takes priority over the `value.is_zero()` check, e.g.:
```
(_, true) => (true, ReentrancyProtection::AllowNext),
(false, false) => (true, ReentrancyProtection::AllowReentry),
(true, false) => (false, ReentrancyProtection::AllowReentry),
```
so that any call with `gas_limit == CALL_STIPEND` always receives `AllowNext` regardless of `value`, restoring the intended stipend-based reentrancy restriction for both zero- and non-zero-value transfers.

### Proof of Concept
- Unit/fuzz test in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` (or `exec/tests.rs` using `mock_ext.rs`): fuzz `(value: U256, gas_limit: U256)` pairs feeding the same tuple-match logic as `run_call`; assert that for every input where `gas_limit == CALL_STIPEND` (2300), the resulting `ReentrancyProtection` is `AllowNext`, regardless of `value.is_zero()`. The current implementation fails this assertion for `value != 0, gas_limit == 2300`.
- Integration test: deploy a caller contract that invokes `callee.call{value: 1, gas: 2300}(reentrantSelector)` where `callee` attempts to call back into the caller; assert that with `AllowNext`/`Strict` semantics the reentrant call is rejected, then show that with current code the reentrant call succeeds because `AllowReentry` is selected.
