### Title
No cryptographic/logical enforcement that eye_left and eye_right iris codes are distinct before signing - ([File: src/plans/enroll_user.rs])

### Summary
`make_signature` in `src/plans/enroll_user.rs` hashes `pipeline.v2.eye_left` and `pipeline.v2.eye_right` fields independently and signs the digest without ever comparing `iris_code`/`mask_code` for equality between the two eyes. The only defenses against a duplicate-eye capture live upstream in `biometric_capture` (an IR-Net ML classifier `perceived_side` check plus a fixed `DEFAULT_DELAY_BETWEEN_EYE_CAPTURES` timing heuristic), which are best-effort, not deterministic guarantees.

### Finding Description
`make_signature` builds a SHA-256 context from `ORB_ID`, the user id, model versions, and then `eye_left.iris_code`/`mask_code`/`iris_code_version` followed by the same fields for `eye_right`, then signs it via `secure_element::sign` [1](#0-0) . There is no equality check anywhere between `eye_left` and `eye_right` before signing, and the caller `Plan::run` simply passes through pipeline output to this function without extra validation [2](#0-1) .

Upstream, the only mechanism that tries to ensure the two captures correspond to different physical eyes is in `src/plans/biometric_capture/mod.rs`: an IR-Net ML output field `perceived_side` is compared against the capture's `target_left_eye`, and frames are skipped if they mismatch or if `valid_capture_after` (gated by `DEFAULT_DELAY_BETWEEN_EYE_CAPTURES`) hasn't elapsed [3](#0-2) . The codebase itself documents that this is a known-imperfect mitigation: `DEFAULT_DELAY_BETWEEN_EYE_CAPTURES` exists explicitly "to defend against inaccuracies in IR-Net, which lead to accepting the same eye as the second capture" [4](#0-3) . This is a probabilistic/ML-based defense (classifier confidence + timing), not a hard invariant, and it operates before/during capture — it is not re-validated once `Pipeline` reaches `biometric_pipeline::Plan::run` or `enroll_user::make_signature`. Both of those construct/consume `PipelineV2 { eye_left, eye_right, .. }` and `EyePipeline { iris_code, mask_code, .. }` without any code that checks `eye_left.iris_code != eye_right.iris_code` [5](#0-4) [6](#0-5) .

Because `make_signature` treats `eye_left` and `eye_right` as independent inputs and only asserts their presence, not their distinctness, a presentation that fools the IR-Net perceived-side classifier (or that occurs faster/slower than expected around the timing heuristic) and yields identical `iris_code`/`mask_code` for both eye slots will still pass through the pipeline and produce a validly signed signature.

### Impact Explanation
This corresponds to a liveness/fraud-bypass class impact: a single-eye (or photographic/mirror) presentation could be accepted by the orb as if it were a genuine two-distinct-eye live capture, producing a cryptographically valid signature and an enrollment package that the backend would treat as a normal dual-eye signup. This weakens the two-iris uniqueness guarantee that anti-Sybil/anti-fraud policy depends on, without requiring any privileged access — only a specific physical presentation to the camera during signup.

### Likelihood Explanation
Feasibility depends entirely on how strong the upstream IR-Net `perceived_side` classifier and RGB-Net-derived bbox/landmark checks are at distinguishing left vs. right eye images; the project's own comment ("inaccuracies in IR-Net, which lead to accepting the same eye as the second capture") indicates this is a real, acknowledged failure mode. However, `Objective.target_left_eye`, `perceived_side` gating, RGB-Net bbox/landmark checks in `face_identifier`, and occlusion checks add real friction, so exploitability is conditional on defeating (or the model naturally failing) these classifiers — not trivial, but not something ruled out by the code, and specifically not caught at all by `make_signature` or `biometric_pipeline::Plan::run` even if the upstream checks are defeated.

### Recommendation
Add an explicit, deterministic invariant check in `biometric_pipeline::Plan::run` (or as a guard in `enroll_user::make_signature`) that rejects the pipeline if `iris_left.iris_code == iris_right.iris_code` (and/or mask codes, and/or Hamming-distance-based near-duplicate detection) before signing, rather than relying solely on the IR-Net perceived-side ML classifier and the fixed inter-capture delay.

### Proof of Concept
Unit test in `src/plans/enroll_user.rs` (or a new test module):

    pipeline.v2.eye_right.mask_code = pipeline.v2.eye_left.mask_code.clone();

    assert!(result.is_err(), "make_signature must reject duplicate-eye pipelines");

Current behavior: `result` is `Ok(signature)` because `make_signature` has no equality check, demonstrating the gap described above.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
