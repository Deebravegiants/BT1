### Title
Blocked/blacklisted original sender permanently bricks POST/GET timeout handling and destination-chain fee refund - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchTimeOut` (both the `PostRequestTimeout` and `GetRequestTimeout` overloads) refunds the protocol fee to `meta.sender` — the address that originally dispatched the request — via a hardcoded `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)`. If `feeToken()` is a blocklist-capable ERC20 (e.g. USDC, as the protocol explicitly supports arbitrary ERC20 fee tokens) and `meta.sender` becomes blocked after dispatch but before timeout, this transfer reverts unconditionally, and there is no alternate-recipient parameter to work around it.

### Finding Description
`dispatchTimeOut` for both `PostRequestTimeout` and `GetRequestTimeout` deletes the request commitment for replay protection, invokes the module's timeout callback, and then unconditionally refunds the fee to the fixed `meta.sender` address recorded when the request was originally dispatched: [1](#0-0) 

Because the whole function is a single external call from `restrict(_hostParams.handler)` (i.e. `HandlerV2`), if `safeTransfer` reverts, the entire transaction — including the module timeout callback and the replay-protection deletion of `_requestCommitments[commitment]` — reverts. Unlike the `onAccept`/`onGetResponse` success-check pattern (`if (!success) { delete ...; return; }`), the fee-refund step has no failure isolation: it runs after the callback succeeds and is not wrapped so a revert here rolls back everything, including any state a downstream module already committed to during the (reverted) callback.

Since `meta.sender` is fixed at dispatch time and never redirectable by the relayer or the sender, once that address is blocklisted by the fee token issuer, no relayer — honest or otherwise — can ever complete a timeout for that specific commitment. This differs from the `dispatchIncoming(GetResponse, relayer)` fee-reward path (`evm/src/core/EvmHost.sol:841-845`), where the recipient (`relayer`) is chosen per-submission by whichever relayer calls the handler, so a blocked relayer can simply be bypassed by another relayer retrying with a different address. `meta.sender` has no such flexibility — it is baked into `FeeMetadata` at original dispatch time.

The Rust side of the protocol (`modules/pallets/relayer/src/accumulate.rs`) explicitly supports a signed "beneficiary redirect" to work around exactly this problem for relayer fee accumulation: [2](#0-1) 

No equivalent redirect exists for the EVM-side timeout refund to the original request sender, confirming this is a genuine gap rather than an intentional design choice.

### Impact Explanation
A blocked `meta.sender` permanently prevents `dispatchTimeOut` from succeeding for that request:
- The module's `onGetTimeout`/`onPostRequestTimeout` callback can never fire, so any escrow-refund or state cleanup logic gated on the timeout callback (e.g. `HyperFungibleToken.onPostRequestTimeout` re-minting burned tokens, or intents/escrow refund logic keyed on request timeouts) is permanently frozen — the burned/escrowed value is unrecoverable.
- The commitment can never be cleared via the timeout path, and the fee itself is permanently stuck in the host contract (unbacked/frozen funds), satisfying "permanent freezing of funds."
- This is triggerable by anyone: any account that dispatches a cross-chain request and later gets blocklisted by the fee-token issuer (a routine, permissionless-from-the-protocol's-perspective event for tokens like USDC) bricks its own timeout refund and the downstream module's timeout logic with no recovery path.

### Likelihood Explanation
The protocol explicitly permits governance to configure the `feeToken` to any ERC20 (as documented and exercised broadly with USDC/DAI throughout the fee-token and Intent Gateway flows), and blocklist-capable stablecoins are the primary real-world fee tokens in this ecosystem. Any user whose dispatched request later times out while their address is blocklisted triggers this deterministically — no attacker collusion or privileged access is required.

### Recommendation
Isolate the fee-refund transfer from the callback/replay-protection logic (e.g. wrap the `safeTransfer` in a try/catch or low-level `call`, and on failure escrow the fee under the sender's address for later claim via an alternate address) so a single blocklisted `meta.sender` cannot revert the entire timeout dispatch. Additionally, allow the original sender to register/prove an alternate payout address (mirroring the `beneficiary_details` redirect pattern already used in `modules/pallets/relayer/src/accumulate.rs`) so a blocked address does not permanently forfeit both the fee refund and the timeout callback execution.

### Proof of Concept
1. Alice dispatches a `PostRequest` via `EvmHost.dispatch`, paying `fee` in the configured `feeToken` (e.g. USDC). `FeeMetadata{ sender: Alice, fee }` is recorded in `_requestCommitments[commitment]`.
2. USDC's issuer blocklists Alice's address for an unrelated reason before the request times out.
3. The request times out on the destination; a relayer submits a valid timeout proof to `HandlerV2`, which calls `EvmHost.dispatchTimeOut(timeout, meta, commitment)`.
4. `_requestCommitments[commitment]` is deleted, the module's `onPostRequestTimeout` callback executes successfully, then `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` reverts because Alice is blocklisted.
5. The entire transaction reverts, restoring `_requestCommitments[commitment]` — but every subsequent timeout submission hits the identical revert. The request timeout, its module callback (e.g. token re-mint/refund), and the fee are permanently stuck, with no parameter or mechanism to redirect the refund to an unblocked address. [3](#0-2)

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
