### Title
Webhook `shop-domain` (and `topic`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook signature over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values come from unauthenticated HTTP headers. `Registry.process` verifies the HMAC and then unconditionally forwards those unauthenticated header values to the app's webhook handler as if they were verified tenant identity, breaking the invariant that `shop` used for tenant attribution == `shop` actually covered by the HMAC.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, etc., which were never part of the signed material: [3](#0-2) 

`HmacValidator.validate` only ever checks the `hmac`/`to_signable_string` pair, i.e. the raw body vs. the header-supplied HMAC — it never touches `shop`: [4](#0-3) 

Since `api_secret_key` is a single app-level (client) secret shared by every merchant installation of the app, any unprivileged user can install the app on their own (e.g. free/trial) shop, trigger a genuine webhook delivery, and capture a legitimately-signed `(raw_body, hmac)` pair. Because the signature covers only the body, the attacker can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`) header for a victim shop's domain. `Registry.process` will pass HMAC validation (body is unchanged) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop: [5](#0-4) 

This is the same bug class as the report's `maxStrategistFee` issue: a value used to gate/attribute a privileged action (`shop` used for tenant attribution) is not actually bound by the check that is supposed to authenticate it (the HMAC only covers `raw_body`). The equality that should hold — `shop used by handler == shop covered by HMAC` — does not hold; instead `shop used by handler == shop read from unauthenticated header`.

### Impact Explanation
This breaks the tenant boundary the host application relies on this gem to enforce: an attacker with a valid (self-obtained) app installation can inject attacker-controlled webhook payloads attributed to any other shop domain, since `shop` is not part of the authenticated data. This is a cross-tenant integrity/confusion issue in the webhook trust boundary this gem exposes to host apps (e.g. an app that keys per-shop state or triggers per-shop side effects directly off `WebhookMetadata#shop` without independent verification would misattribute the data).

### Likelihood Explanation
Any actor who can install the app on any shop (including free development/trial shops, which requires no privileged credentials) can obtain a validly-signed webhook body under the shared `api_secret_key`, then freely modify the `shop-domain` header before sending it to the app's public webhook endpoint. No secrets, tokens, or privileged access are required beyond a normal, unprivileged app installation — matching an "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and topic) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop`/`topic` to the signed body before trusting them in `WebhookMetadata`. At minimum, `Registry.process` should not treat `request.shop`/`request.topic` as authenticated unless they are covered by (or independently cross-checked against) the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker resends the exact same request to the app's webhook endpoint, keeping `B` and `H` unchanged but replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (unchanged) and succeeds: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)`, even though `victim.myshopify.com` never sent or authorized this webhook.
