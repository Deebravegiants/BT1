### Title
Unmetered `GetRequest` processing lets attackers force expensive relayer/consensus work at near-zero cost - ([File: tesseract/messaging/messaging/src/get_requests.rs])

### Summary
Hyperbridge's GET-request relaying pipeline unconditionally processes every dispatched `GetRequest` — including requests dispatched with `fee: 0` — by fetching state proofs from both the source and destination chains and submitting them through the full challenge-period + proof-verification pipeline. The fee-profitability check that would have filtered out unprofitable/free requests is present in the code but entirely commented out, so there is no economic gate before the expensive work is performed.

### Finding Description
On EVM, `DispatchGet.fee` is explicitly documented as optional and settable to zero for self-relay: [1](#0-0) . `EvmHost.dispatch(DispatchGet)` accepts and commits such zero-fee requests without imposing any minimum: [2](#0-1) .

Once dispatched, the tesseract messaging relayer's `process_get_request_events` picks up *all* `GetRequest`s for a destination/height group and immediately begins the expensive off-chain work — querying the source chain's state proof and the destination chain's storage proof via RPC — with no fee or profitability check gating this work: [3](#0-2) 

The code explicitly shows that a profitability filter (checking `query_request_fee_metadata` and skipping requests where `fee.is_zero()`) once existed but has been commented out, meaning it is dead code and not enforced: [4](#0-3) 

After the proofs are fetched (the expensive step — RPC calls, merkle/storage-proof construction), the relayer waits out challenge periods on both source and destination and submits the batched `GetRequestsWithProof` message to Hyperbridge as an unsigned extrinsic via `pallet-state-coprocessor::handle_unsigned`: [5](#0-4) 

`handle_get_requests` then performs full on-chain state-proof verification (membership + state proofs) before finally metering bandwidth via `BandwidthGate::try_consume` — i.e., the bandwidth/economic gate is applied only *after* the costly membership and state proof verification has already run: [6](#0-5) 

This mirrors the reported bug class precisely: a cheap, permissionless, unprivileged action (dispatching a `GetRequest` with `fee: 0`, costing only source-chain gas) triggers a chain of expensive backend operations (RPC-based proof generation by the relayer, on-chain state/membership proof verification by the coprocessor) that are performed unconditionally, before any fee/bandwidth economic check can reject the request. There is no per-request minimum fee enforced at dispatch (`EvmHost.dispatch`), and no per-request fee check in the relayer pipeline (which is commented out), and the on-chain `BandwidthGate` check happens too late to prevent the costly proof-fetching/verification work from being performed for every dispatched GET.

### Impact Explanation
An attacker can dispatch a large volume of `fee: 0` `GetRequest`s (or requests just under whatever allowance the `BandwidthGate` grants) targeting arbitrary destination chains/heights. Each such request forces:
1. The tesseract relayer to make external RPC calls and construct storage/membership proofs for both the source and destination chain (real, non-trivial off-chain compute/IO cost per request, borne by relayer operators for free).
2. The relayer to wait out challenge periods and submit an unsigned extrinsic that runs full on-chain state proof verification in `pallet-state-coprocessor`, consuming block space and validator computation, before the bandwidth gate can reject/charge it.

This can delay or starve processing of legitimate, fee-paying GET requests and consensus/messaging traffic sharing the same relayer and block resources — directly analogous to the reported DOS where a market-closed oracle round-trip is triggered cheaply and repeatedly to saturate a shared, costly backend service. Impact is Medium: it does not steal funds directly but can degrade availability/timeliness of legitimate cross-chain message delivery.

### Likelihood Explanation
Likelihood is High: dispatching a zero-fee `GetRequest` is a normal, permissionless, documented operation (self-relay is explicitly supported), requires no privileged role, and the relayer-side code that would have filtered out unprofitable/free requests is dead (commented out) in the current codebase. An attacker only needs to pay ordinary source-chain gas to dispatch many such requests, similar in cost profile to the original report's "$1.5 collateral, 1000x leverage" cheap trigger.

### Recommendation
- Re-enable (or reintroduce) a fee/profitability filter in `process_get_request_events` before performing any RPC-based proof fetching, so relayers do not spend resources servicing unprofitable/zero-fee requests unless they choose to (self-relay path should remain available to the *dispatcher themselves*, not to arbitrary third parties triggering relayer work).
- Move (or duplicate) the `BandwidthGate::try_consume` check in `pallet-state-coprocessor::handle_get_requests` to run *before* membership/state proof verification, so unauthorized/unallotted apps are rejected cheaply rather than after expensive cryptographic verification.
- Consider enforcing a minimum non-zero fee (or a bandwidth reservation deposit) at `EvmHost.dispatch(DispatchGet)` to raise the cost of spamming free GET requests, mirroring the report's suggestion of increasing minimum position size / fixed minimum fee.

### Proof of Concept
1. Deploy/target an `EvmHost` where `feeToken` and `uniswapV2` are configured normally.
2. From an attacker-controlled contract, call `IDispatcher(host).dispatch(DispatchGet)` repeatedly with `fee: 0`, varying `keys`/`height`/`dest` to avoid dedup, paying only gas.
3. Observe the tesseract relayer's `process_get_request_events` unconditionally group and process these requests: it calls `source.query_state_proof(...)` and `client.query_state_proof(...)` for every batch regardless of the (zero) fee attached — the profitability-filter code path that would skip them is commented out in `tesseract/messaging/messaging/src/get_requests.rs:67-83`.
4. Each iteration consumes relayer RPC/compute resources and, once submitted, on-chain state/membership proof verification cycles in `pallet-state-coprocessor::handle_get_requests`, before the bandwidth gate is even checked — repeating this at scale (many pairs/heights) can saturate relayer and coprocessor throughput for a negligible per-request cost, delaying legitimate paid GET/POST traffic.
