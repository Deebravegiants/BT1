Based on my research, I found a legitimate analog vulnerability. The original report's bug class is "an equality check that compares the wrong two things, letting an attacker-controlled value substitute for a value that should be independently verified." In this codebase, the closest structural analog is in `OmniBridge.describeWithdrawal`, which reports the on-chain withdrawal status/txHash purely by positional index into an externally-supplied, admittedly-unordered API response, without validating that the item actually corresponds to the withdrawal being described.

### Title
Withdrawal status/txHash misreported by positional index instead of matching the actual transfer - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal` picks the transfer to report on solely via `args.index` from the Omni Bridge indexer's `getTransfer` response, without verifying that the picked transfer's destination chain, recipient, or amount corresponds to the withdrawal it is being asked to describe. The exact same class of bug ("respond list is unsorted... match by X instead of index") was identified and fixed for the PoA bridge in the same package, but the fix was not applied to the Omni bridge or Hot bridge equivalents.

### Finding Description
`describeWithdrawal` fetches all transfers for a NEAR transaction hash and indexes into them: [1](#0-0) 

It then derives `destinationChain` from `transfer.recipient` and reports `status: "completed"` with the resolved `txHash`, but never checks that `transfer.recipient` or the asset matches `args.withdrawalParams.destinationAddress` / `assetId`: [2](#0-1) 

By contrast, the PoA bridge implementation explicitly documents and fixes this exact issue by matching on `assetId`/`near_token_id` instead of trusting index/order, both in `intents-sdk` and `internal-utils`: [3](#0-2) [4](#0-3) [5](#0-4) 

The changelog confirms this was a known, previously-fixed defect in the PoA path: `8bbd5c6: Fix POA bridge withdrawal matching to use assetId instead of index`. The Omni bridge's `describeWithdrawal` (and `HotBridge`'s API-fallback branch, which also returns `withdrawals[...]` by nonce/hash lookup rather than validating recipient/amount) never received the analogous fix.

### Impact Explanation
If a single NEAR transaction produces multiple Omni Bridge transfers (e.g., a batched/atomic multi-withdrawal, which this SDK explicitly supports via `signedIntents`/atomic composition), and the indexer returns them in an order that does not match `args.index` (the same "list is unsorted" problem the PoA fix addresses), the SDK will report the wrong transfer's `txHash` and `status: "completed"` for a withdrawal that is unrelated to (or not yet finalized for) the caller's actual withdrawal. An integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` to credit or reconcile a withdrawal could credit/report completion using another withdrawal's destination and hash — a status misreport that doesn't reflect the actual on-chain outcome for the queried withdrawal, matching the "status or hash misreport making an integrator credit twice" impact category.

### Likelihood Explanation
This requires an integrator to batch multiple withdrawals of assets landing via `OmniBridge` in one NEAR transaction and rely on `index`-based `describeWithdrawal`, and for the indexer's `getTransfer` array ordering not to match submission order for that tx — a condition the PoA bridge's own inline comment acknowledges is a real, previously-observed API behavior ("Response list is unsorted"). No malicious actor input is required; it can occur under legitimate concurrent/batched usage, but is not guaranteed to trigger on every call.

### Recommendation
Match the transfer for `describeWithdrawal` by validating destination chain/recipient/amount against `args.withdrawalParams` rather than trusting `args.index` alone, mirroring the `findMatchingWithdrawal` approach already used for the PoA bridge in `poa-bridge.ts` and `waitForWithdrawalCompletion.ts`.

### Proof of Concept
1. Submit a single NEAR transaction containing two atomically-composed Omni Bridge withdrawals: withdrawal A (index 0, recipient X) and withdrawal B (index 1, recipient Y), using the SDK's `signedIntents` atomic composition support in `IntentExecuter.signAndSendIntent`.
2. Call `bridge.describeWithdrawal({ index: 0, withdrawalParams: <A's params>, tx })`.
3. If the Omni Bridge indexer's `getTransfer` response array order differs from submission order (as already documented as a real possibility for the sibling PoA API), `transfer` at position `0` is actually withdrawal B's transfer.
4. The function returns `{ status: "completed", txHash: <B's tx hash> }` for a query about withdrawal A, with no validation that recipient/amount match A's `withdrawalParams`.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
