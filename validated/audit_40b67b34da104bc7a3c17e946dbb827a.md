### Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used downstream to identify which tenant a webhook belongs to are taken from unauthenticated HTTP headers. This mirrors the PoolTogether bug class of "the value that's trusted/acted upon differs from the value that was actually cryptographically verified" — here the `shop` field acted on by `Registry.process` is not covered by the HMAC that `HmacValidator` checks.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, then unconditionally trusts `request.shop` (from the header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only recomputes and compares the signature against `verifiable_query.to_signable_string`, i.e., the body — it never factors in the `shop` header: [4](#0-3) 

Because the `client_secret`/`api_secret_key` used to compute the webhook HMAC is shared across every shop that installs a given app (it is not per-shop), any merchant who has installed the app can legitimately receive one authentic `(body, hmac)` pair for their own shop. Since the HMAC never binds `shop`, that same `(body, hmac)` pair remains valid no matter what `shop-domain` header is sent. This breaks the identity binding: `shop authenticated by HMAC` == `shop trusted by Registry.process` no longer holds — the header is fully attacker-controlled while the body+hmac pair is merely replayed from a legitimately-owned webhook.

### Impact Explanation
An attacker who operates their own (attacker-owned) shop with the app installed can capture a real, validly-signed webhook payload delivered to their own endpoint, then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will report success because it only checks the body against the shared secret, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's shop. If the host application uses this `shop` field (as documented/intended) to scope data writes, cache invalidation, notification dispatch, or session lookups, the attacker can inject data or trigger actions attributed to a shop they do not own — a cross-tenant confusion/access vulnerability entirely enabled by this gem's failure to bind `shop` into the HMAC-verified surface.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant deployment of this gem: exploitation only requires the attacker to install the target app on a shop they control (a normal, unprivileged install — no leaked secrets, no privileged access, no TLS interception needed) and to send a single crafted HTTP POST to the app's already-public webhook endpoint with a header substituted. The HMAC secret itself is never exposed to the attacker; they only reuse a signature that was validly issued to them for a different tenant context.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or otherwise cryptographically tie the header-derived identity to the signed payload, instead of trusting the `shop-domain` header independently of the signature check. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain so `HmacValidator.validate` fails when the header is altered relative to the originally signed request.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and also on `victim-shop.myshopify.com`, using the same app `client_secret`.
2. Shopify sends a legitimate webhook to the attacker: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `B`.
3. Attacker resends the identical body `B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  — this passes because the check only covers `raw_body`.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's tenant context.
