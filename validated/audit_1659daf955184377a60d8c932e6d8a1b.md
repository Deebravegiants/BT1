### Title
Unauthenticated `CallDispatcher.dispatch()` allows theft of ether/tokens held mid-transaction by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single shared helper contract used by `IntentGatewayV2` (predispatch/output execution) and other apps to temporarily route native ETH and ERC20 tokens through arbitrary `Call[]` sequences before sweeping the resulting balance back to the caller. Its `dispatch()` function has **no access control and no reentrancy guard**, so any address can invoke it directly at any point mid-transaction and drain whatever balance the dispatcher happens to be holding at that instant.

### Finding Description
`CallDispatcher.dispatch()` is fully public and unauthenticated: [1](#0-0) 

It simply executes whatever `Call[]` is handed to it, forwarding any `call.value` requested, with no check on `msg.sender` and no reentrancy lock.

`IntentGatewayV2.placeOrder` routes native ETH/ERC20 through this shared dispatcher before sweeping it back based purely on the dispatcher's live balance, not a tracked/committed amount: [2](#0-1) [3](#0-2) 

Between the moment assets are sent to the dispatcher (line 248 `_sendValue(dispatcher, amount)`) and the moment they are swept back (line 289), `order.predispatch.call` — fully attacker-supplied calldata — is executed by the dispatcher (line 258). Because `dispatch()` on the shared `CallDispatcher` is callable by anyone from anywhere (not just from within that same call stack), a token used in `predispatch.assets` with a transfer hook (e.g., ERC-777 `tokensReceived`) can call back out during the `safeTransferFrom` into an attacker-controlled contract, which then calls `CallDispatcher.dispatch()` directly with a `Call{to: attacker, value: dispatcher.balance, data:""}` to sweep out the ETH that is currently sitting in the dispatcher awaiting the legitimate sweep. The same unprotected sweep-by-balance pattern (rather than sweep-by-tracked-amount) also exists in `_execute()` for post-dispatch (fill) calldata: [4](#0-3) 

`IntentGatewayV2`'s own `nonReentrant` modifiers on `placeOrder`/`fillOrder`/`cancelOrder` only protect re-entry into the gateway itself; they do nothing to protect the separately-deployed, shared `CallDispatcher`, which any contract in the ecosystem (IntentGatewayV2, HyperFungibleToken, WrappedHyperFungibleToken — see the documented "dispatcher holds tokens temporarily during execution" pattern) can call into concurrently. This is structurally identical to the reported 0x issue: (1) the balance swept back is measured from `address(this).balance`/`token.balanceOf(dispatcher)` with no strict, pre-committed accounting of exactly what should remain, (2) reentrancy into the shared dispatcher is possible via attacker-controlled calldata executed inside `dispatch()` itself (tokens with transfer hooks, or any external call that can call back), and (3) `dispatch()` is precisely the "mechanism to spend ether/tokens held by" the contract, reachable by anyone.

### Impact Explanation
Any native ETH or ERC20 balance the shared `CallDispatcher` is holding mid-transaction (from a predispatch swap, a postdispatch settlement, or any other app's in-flight `Call[]` execution using the same dispatcher instance) can be stolen outright by an unprivileged attacker, since `dispatch()` performs no ownership or origin check before moving value to an attacker-supplied address. This is direct theft of funds in transit through core Intent Gateway flows reachable from a single `placeOrder`/`fillOrder` transaction.

### Likelihood Explanation
The precondition is only that `order.predispatch.assets`/`order.output.assets` include a token capable of an external callback during transfer (ERC-777-style hooks, or any token/contract the order references that can execute code), which the order creator or a colluding party fully controls when constructing the order. No special privilege, governance, or off-chain trust is required — it is directly reachable by any unprivileged user submitting an order through the public `placeOrder`/`fillOrder` entry points.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by trusted, registered callers (e.g., `onlyGateway`/`onlyRegisteredApp` access control), add a reentrancy guard on `dispatch()` itself, and change the sweep logic in `IntentGatewayV2`/`IntentsBase` to track and enforce an exact expected balance delta (rather than trusting whatever balance is observed on the dispatcher) so any unaccounted-for value causes a revert instead of silently being swept out or in.

### Proof of Concept
1. Attacker crafts an `Order` with `predispatch.assets` containing a native-ETH leg (amount `X`) followed by an ERC-777-style token leg whose `tokensReceived`/`tokensToSend` hook is attacker-controlled.
2. Attacker calls `placeOrder{value: X}(order, graffiti)`. The gateway sends `X` ETH to the shared `CallDispatcher` (`IntentGatewayV2.sol:248`), then calls `safeTransferFrom` for the callback token, which invokes the attacker's hook.
3. Inside the hook, the attacker directly calls `CallDispatcher.dispatch(abi.encode([Call({to: attackerAddress, value: X, data: ""})]))` on the same shared dispatcher instance — this succeeds because `dispatch()` has no access control (`CallDispatcher.sol:44-62`).
4. The dispatcher's ETH balance is drained to the attacker before the gateway's own sweep step (`IntentGatewayV2.sol:289-306`) runs, which then either reverts (denial of the victim's own order) or, if other value is present from a different concurrent operation sharing the dispatcher, silently steals that value.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
