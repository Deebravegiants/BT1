### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` entirely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator.validate` checks is computed only over the raw request body. This breaks the equality that should hold between "the tenant whose credentials produced a valid HMAC" and "the tenant the application attributes the webhook payload to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers that are never included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body) and, once that check passes, dispatches the handler using the unauthenticated `request.shop` and `request.topic` values: [3](#0-2) 

The app's HMAC secret (`Context.api_secret_key`) is a single, global secret shared across every shop that has the app installed — it is not shop-specific. Consequently, `Utils::HmacValidator.validate` computed over `raw_body` alone will succeed for **any** shop's genuinely-Shopify-signed body, regardless of which `shop-domain` header accompanies it: [4](#0-3) 

This is the exact bug class described in the reference report — "a field acted on but not covered by the HMAC." Here, the identity binding that should hold is:
`shop_bound_by_HMAC == shop_used_by_handler`

but because `shop` (and `topic`/`webhook_id`) are outside the signed content, an attacker who controls or has legitimately installed the app on **their own shop** (Shop A) can capture one authentic webhook delivery (valid body + valid HMAC for Shop A), then replay the identical body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain (Shop B). `HmacValidator.validate` still returns `true` (it never looked at the shop header), and `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the attacker-chosen Shop B, causing the host application to process/store attacker-controlled data under another tenant's identity.

### Impact Explanation
This is a cross-tenant integrity/confusion vulnerability: data that is only guaranteed to be signed by the app's secret (proving it came from *some* Shopify shop running the app) is attributed to an arbitrary shop the attacker selects via an unauthenticated header. Any host application that trusts `WebhookMetadata#shop` (e.g., to select a merchant's database record, session, or Admin API session for reacting to `shop/redact`, `orders/create`, `app/uninstalled`, etc.) can be induced to apply attacker-supplied data/state to a victim tenant it does not control. This matches the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free/trial) merchant with the app installed on their own shop, so they can capture one real webhook delivery signed by the app's shared secret. No access to `api_secret_key`, access tokens, or privileged accounts is needed — this is fully achievable by an unprivileged internet user who installs the app on a shop they control. This is a realistic and repeatable attack, not merely theoretical.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) to the signature verification, e.g., include the shop-domain header (and other trust-sensitive headers) in `to_signable_string`, or independently verify that the `shop` header value matches an expected/allow-listed shop for the session/tenant context before dispatching the handler. At minimum, document and enforce that consumers of `WebhookMetadata#shop` cannot rely on it as an authenticated value unless it is cryptographically bound to the request the same way `raw_body` is.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture one legitimate Shopify webhook delivery for it — raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Replay a request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(client_secret, B) == H`, per: [5](#0-4) 
4. `Registry.process` proceeds and calls the registered handler with `shop: "victim.myshopify.com"` (attacker-controlled) and `body` from `B`, per: [6](#0-5) 
5. The host application processes attacker-supplied webhook content believing it originated from `victim.myshopify.com`.
