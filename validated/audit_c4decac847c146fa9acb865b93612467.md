## Title
Permissionless `handleConsensus` silently drops the first state-machine commitment when `latestStateMachineHeight == 0`, permanently blocking message delivery for that route - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handleConsensus` is a fully permissionless entry point that any relayer can call to advance an `EvmHost`'s consensus state and record new `StateCommitment`s for tracked state machines. When applying the `IntermediateState[]` returned by the consensus client, the handler gates every commitment write with `latestHeight != 0`, which conflates "no commitment has ever been recorded" (Solidity's default `uint256` value) with "the state machine is at height 0." [1](#0-0) 

### Finding Description
`handleConsensus` iterates the intermediate states produced by `IConsensusV2.verify` and only calls `host.storeStateMachineCommitment` when:
```solidity
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ...
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
```
`_latestStateMachineHeight[stateMachineId]` in `EvmHost.sol` is only ever set by `storeStateMachineCommitment` (called from this same gated path) or by the admin's one-shot `setConsensusState` for the initial state machine at genesis. [2](#0-1) [3](#0-2) 

For any state machine that is added to a host's tracked set *after* genesis (i.e., its `_latestStateMachineHeight` mapping entry has never been written and therefore defaults to `0`), the very first `IntermediateState` a relayer submits for it will have `latestHeight == 0`, causing the `if` to evaluate false. The commitment is silently discarded — no revert, no event, no state change — and `_latestStateMachineHeight` remains `0`. Because the gate depends solely on this same storage variable, every subsequent relay attempt for that state machine hits the identical `latestHeight == 0` condition and is dropped again, indefinitely. There is no way for a relayer, admin, or fisherman to break out of this loop through this code path; the only recovery route is an admin `setConsensusState` re-initialization, an out-of-band privileged action not reachable by an ordinary relayer/message dispatcher.

This is analogous to CVE-2015-1853's root cause: an unprivileged party (any relayer) drives updates into a state machine whose internal state variable (`_latestStateMachineHeight`) is not properly initialized/protected before being used as the sole gating condition, resulting in a persistent failure to advance state ("inability to synchronize").

### Impact Explanation
Any EVM-hosted route to a newly tracked destination or counterparty state machine (added post-genesis, e.g. new parachains onboarded to Hyperbridge, new Evm/L2 chains added to a `BeefyConsensusClient`/`SP1Beefy`/sync-committee tracked set) can never have its first state commitment recorded through the normal `handleConsensus` path. Since `pallet-ismp`/`HandlerV2` state proof verification for POST requests, GET responses, and timeouts all require an existing `StateCommitment` at the target height, this permanently freezes message delivery on that route — a "route unable to deliver messages" condition, which the validation rules explicitly call out as an acceptable Medium+ impact. No funds are directly stolen, but any tokens/messages routed to that state machine become permanently undeliverable/stranded, which can also freeze funds in escrow/intents contracts awaiting proof-of-delivery on that route.

### Likelihood Explanation
Reachable by any unprivileged relayer calling the permissionless `handleConsensus` function with a valid consensus proof for a state machine that has not yet had a commitment stored — a very ordinary and expected event whenever Hyperbridge onboards a new destination chain (which happens routinely as the protocol expands to new networks). No malicious intent or special privilege is required; it will occur naturally the first time consensus for a newly configured state machine is submitted.

### Recommendation
Replace the `latestHeight != 0` sentinel check with an explicit existence flag (e.g., a `mapping(uint256 => bool) hasCommitment`) or use `height.height > 0` semantics correctly by tracking "initialized" state separately from height `0`, so the very first commitment for a state machine is always accepted regardless of whether `_latestStateMachineHeight` defaults to zero.

### Proof of Concept
1. Configure an `EvmHost` with a new tracked `stateMachineId` (e.g., `3001`) that was never passed through `setConsensusState` (post-genesis onboarding), so `latestStateMachineHeight(3001) == 0`.
2. A relayer calls `HandlerV2.handleConsensus(host, proof)` where the consensus client's `verify` returns an `IntermediateState{ stateMachineId: 3001, height: 100, commitment: ... }`.
3. In `handleConsensus`, `latestHeight = host.latestStateMachineHeight(3001)` returns `0`; the condition `latestHeight != 0 && intermediate.height > latestHeight` is `false`, so `storeStateMachineCommitment` is never called — confirmed by `HandlerV2Test.testHandleConsensusV2StoresState`/similar tests only exercising cases where `latestStateMachineHeight` is already non-zero (e.g., pre-seeded via `_makeConsensusProof`), never the "first ever" case with a genuinely-zero prior height. [4](#0-3) 

4. Any later relayer resubmitting proofs for `stateMachineId 3001` — even at higher heights — hits the same `latestHeight == 0` check and is dropped again. Messages destined to/from `3001` can never be relayed because `stateMachineCommitment(request.proof.height)` will never resolve, causing `handlePostRequests`/`handleGetResponses` to revert with `StateCommitmentNotFound`. [5](#0-4)

    function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
        external
        restrict(_hostParams.handler)
    {
        _stateCommitments[height.stateMachineId][height.height] = commitment;
        _stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
        _latestStateMachineHeight[height.stateMachineId] = height.height;

        emit StateMachineUpdated({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId), 
            height: height.height
        });
    }
