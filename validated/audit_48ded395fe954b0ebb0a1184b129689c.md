### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant-spoofed webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `request.shop` is read verbatim from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body only, then trusts the header value as the tenant identity passed to the app's handler. Because the webhook HMAC secret (`Context.api_secret_key`) is shared across all shops installed on the app (it is not shop-specific), any body+HMAC pair that is valid for one shop's webhook is also a valid HMAC for a request claiming to originate from a different shop.

### Finding Description
`Request#to_signable_string` binds only `@raw_body` into the signature: [1](#0-0) 

`Request#shop` is derived from the `shop-domain` header, which is not part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, and then forwards `request.shop` directly into `WebhookMetadata` used by the app's handler, without any cross-check that the claimed shop is bound to the signed payload: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body, in the webhook case) and `Context.api_secret_key`/`Context.old_api_secret_key`, which is a single app-level secret shared by every installed shop, not a per-shop secret: [4](#0-3) 

The binding that is broken, expressed as an equality that should hold but doesn't:
`shop_bound_by_hmac == shop_trusted_by_handler`
In this code, the left side is always empty (the signature covers no shop identifier at all), while the right side is `request.shop`, taken unauthenticated from an HTTP header. Consequently `shop_bound_by_hmac != shop_trusted_by_handler` is provable for any request where an attacker controls the header independent of the signed body.

### Impact Explanation
This is a cross-tenant identity-binding failure matching the "field acted on but not covered by the HMAC" and "shop authenticated versus shop used as identity key" pattern called out in scope. An attacker who is an ordinary merchant with a legitimate (even free/trial) install of the app receives real webhook deliveries signed by the app's single shared `api_secret_key` for their own shop. Because the signature never incorporates the shop identity, the attacker can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` still returns `true` (the body and secret are unchanged), and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as the source, with attacker-chosen body content. Any handler logic that keys tenant-scoped actions or storage off `WebhookMetadata#shop` (the pattern this gem's own webhook docs and the `Http`/`PubSub` registrations expect) can be corrupted with attacker data attributed to a different tenant — i.e., cross-tenant access/data injection, without requiring the app's `client_secret`, TLS interception, or a privileged account.

### Likelihood Explanation
Requires only an ordinary, unprivileged app install (any merchant can install an app that supports installs, or a trial/dev store) — no leaked credentials or elevated access. The attacker does not need to know `api_secret_key`; they only need one legitimately signed webhook delivery for their own shop plus the ability to POST an HTTP request with a forged `shop-domain` header to the app's webhook endpoint. This is a straightforward capture-and-replay with header substitution, well within the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the shop identity into the signed material used for webhook verification, or otherwise cryptographically tie the claimed `shop-domain` header to the payload before trusting it. Concretely:
- Extend `Request#to_signable_string` (or add a companion check in `Registry.process`) to require that the shop the caller claims matches a shop value that is itself verifiable — e.g., cross-checking against session/shop records the app already trusts for that installation, not solely the raw header.
- At minimum, document/enforce that `WebhookMetadata#shop` must not be used as the sole tenant key without corroborating it against a known, previously-authenticated shop record (e.g., an existing installed-shop lookup), since the HMAC in this gem only proves "this body was signed by an app secret," not "this body came from shop X."

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (ordinary merchant flow, no special privilege).
2. The app is configured with mandatory/topic webhooks; Shopify delivers a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-for-body>`, `x-shopify-topic: orders/create`
   - Body: attacker fully controls their own store's order content (e.g., `{"id":1,"note":"PAYLOAD"}`).
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker resends an HTTP POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only — it matches, so validation passes: [5](#0-4) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, believing it is a genuine webhook for the victim tenant: [6](#0-5)
