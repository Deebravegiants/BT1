## Analog Found: Webhook shop/topic identity fields are not covered by the HMAC signature [1](#0-0) [2](#0-1) 

### Title
Webhook `shop`, `topic`, and `webhook_id` headers are excluded from HMAC verification, allowing signature replay under a forged shop/topic identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` authenticates the JSON payload bytes but never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that `Registry.process` subsequently trusts and dispatches on.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [3](#0-2) 

but `to_signable_string`, which is what `HmacValidator` signs/verifies against, only returns the raw request body: [4](#0-3) 

`Registry.process` validates the HMAC over the request object and then unconditionally trusts the header-derived `topic` and `shop` to select a handler and construct `WebhookMetadata`: [2](#0-1) 

The equality the code implicitly assumes is: `bytes verified by HMAC == identity (shop, topic) acted upon`. In reality, only the body bytes are covered; the `shop`/`topic`/`webhook_id` headers are unauthenticated inputs that ride alongside a validly-signed body.

### Impact Explanation
Any party who has received one legitimately HMAC-signed webhook body (e.g., a merchant receiving webhooks for their own shop) can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers. `Utils::HmacValidator.validate` will still pass (it only checks the body against the secret), and `Registry.process` will hand the forged shop/topic to the registered handler via `WebhookMetadata`. If the host application uses `data.shop` to select which tenant's records to update (the documented and expected usage pattern shown in the gem's own webhook handler examples), this allows one merchant to inject data attributed to a different shop — a cross-tenant integrity violation - purely through the interface this gem exposes to handler code.

### Likelihood Explanation
Exploitation only requires standing up a normal webhook subscription for a shop the attacker legitimately controls, capturing one delivered payload, and re-POSTing it to the app's public webhook URL with modified Shopify headers. No access token, secret, or privileged account is needed — only network access to the app's already-public webhook receiver.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the signable string (or otherwise cryptographically bind them, e.g. by having `Registry.process` re-derive/validate `shop` against an independently trusted source such as the session store for that shop) so that the HMAC check actually authenticates the identity fields the registry dispatches on, not just the payload bytes.

### Proof of Concept
1. Attacker legitimately owns `shop-a.myshopify.com` and receives a real webhook for topic `orders/create` with body `B` and a valid `X-Shopify-Hmac-SHA256` header `H` (computed over `B` only, per `to_signable_string`).
2. Attacker POSTs the same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim shop) and/or a different `X-Shopify-Topic`.
3. `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` succeeds because it only checks `B` against `H`.
4. `Registry.process` looks up the handler for the (possibly forged) topic and calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body, ...))`, causing the app to process attacker-supplied data as if it came from `shop-b`.
