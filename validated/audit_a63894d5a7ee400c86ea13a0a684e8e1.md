Based on the evidence gathered, I found a valid analog in `EvmHost.sol`.

### Title
Single global `challengePeriod` applied uniformly to all whitelisted state machines with heterogeneous finality/security assumptions - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.sol`'s `HostParams` struct defines exactly one `challengePeriod` value that governs how long a relayer must wait after a state commitment is recorded before it can be used to process incoming requests, responses, or timeouts — for *every* counterparty state machine the host has whitelisted, regardless of how many distinct state machines with different consensus/finality characteristics are configured.

### Finding Description
`HostParams` stores a single `uint256 challengePeriod` field alongside a `uint256[] stateMachines` array of whitelisted counterparties: [1](#0-0) 

`updateHostParamsInternal` writes this single value into storage for the whole host, applying it uniformly to however many state machines are whitelisted in `params.stateMachines`: [2](#0-1) 

`HandlerV2.sol` then enforces this one global `challengePeriod` against the recorded update time of *any* proof height, irrespective of which state machine produced it, in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`: [3](#0-2) [4](#0-3) 

This is the same bug class as the reported `ChainLinkOraclePivot` issue: one freshness/delay threshold is used to gate two (or more) sources that legitimately need different values. On the Substrate/pallet-ismp side, the protocol explicitly avoids this by keying the challenge period per `StateMachineId` (state machine + consensus state), letting each counterparty state machine have its own delay: [5](#0-4) [6](#0-5) 

`CreateConsensusState` even carries a `BTreeMap<StateMachine, u64>` of `challenge_periods` for exactly this reason — different state machines under the same consensus client can require different delay periods: [7](#0-6) 

`EvmHost.sol`, however, collapses this into one governance-settable scalar applied to every whitelisted `stateMachines[]` entry, which can have very different underlying consensus/finality security assumptions (e.g. a fast BEEFY-attested parachain vs. a slower OP-Stack L2 relying on `finalizationPeriodSeconds`/fault-proof windows as seen in the op-host tooling).

### Impact Explanation
If the single `challengePeriod` is tuned short enough to be workable for a fast-finalizing counterparty, it may be insufficient for a slower/weaker-security counterparty whitelisted on the same `EvmHost`, allowing state commitments to be trusted (and requests/responses/timeouts dispatched) before that chain's actual fraud-proof/challenge window has elapsed — undermining the "wait for fishermen to veto byzantine commitments" security model and permitting a forged/premature state commitment to be acted upon. Conversely, if tuned long enough for the slower counterparty, message delivery for the faster one is needlessly delayed, which can manifest as a route effectively unable to deliver messages in a timely manner (stale-state style denial of service) for that state machine.

### Likelihood Explanation
This triggers whenever host governance whitelists more than one state machine of differing finality profiles on the same `EvmHost` instance (a supported, unprivileged, ordinary configuration reachable through the existing message-dispatch/relayer path) — no admin misbehavior is required, only the normal operation of `HandlerV2.handlePostRequests`/`handleGetResponses`/timeout handlers being invoked by any relayer once a commitment for the weaker-security chain is stored.

### Recommendation
Key the challenge period per counterparty `StateMachine`/`StateMachineId` in `EvmHost.sol`, mirroring the substrate/pallet-ismp design (`ChallengePeriod` storage keyed by `StateMachineId`, and `CreateConsensusState.challenge_periods: BTreeMap<StateMachine, u64>`), instead of a single scalar in `HostParams`, and have `HandlerV2` look up the challenge period for the specific state machine referenced by `request.proof.height.stateMachineId`.

### Proof of Concept
1. Governance whitelists two state machines on the same `EvmHost` — one fast-finality chain (e.g. a sync-committee based L2) and one that legitimately needs a much longer economic-security/fraud-proof window — via `updateHostParamsInternal`, both bound by the single `_hostParams.challengePeriod`.
2. A consensus proof updates `stateMachineCommitmentUpdateTime` for the weaker-security chain.
3. Because `challengePeriod` was tuned to suit the fast chain, `handlePostRequests`/`handleGetResponses` in `HandlerV2.sol` (lines 181-186, 217-221) allow requests referencing the weaker chain's commitment to be dispatched once the (too-short) global delay elapses, before that chain's real fraud-proof window has passed — i.e., before a fisherman could realistically veto a byzantine commitment.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
