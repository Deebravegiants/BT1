### Title
Webhook Shop, Topic, and Webhook ID Fields Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-validated signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are taken directly from unauthenticated HTTP headers and passed on to application webhook handlers as if they were verified. This breaks the intended equality `shop authenticated by HMAC == shop delivered to the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop`/`#topic`/`#webhook_id`/`#api_version` are read straight from request headers with no cryptographic binding to the body: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string`, i.e., the raw body: [2](#0-1) 

`Webhooks::Registry.process` treats a successful HMAC check as sufficient authorization to dispatch the (unauthenticated) `request.shop` and `request.topic` values straight to the application's handler: [3](#0-2) 

Because the shop-domain, topic, and webhook-id headers are never mixed into the HMAC-signed material, any actor who can obtain one legitimately-signed `(raw_body, hmac)` pair (trivially done by installing the app on a shop they control and capturing a real webhook delivery) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting arbitrary values for `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id`. The HMAC check still passes because it only validates the body bytes, yet the handler receives attacker-chosen `shop`/`topic`/`webhook_id` values bound to attacker-chosen body content.

### Impact Explanation
This is a cross-tenant identity-binding break: the library hands the webhook handler a `shop` value that looks authenticated (it arrived alongside a passing HMAC check) but is not actually covered by that HMAC. Applications commonly key their tenant logic and data writes off `WebhookMetadata#shop`. An attacker can therefore impersonate any other merchant's shop domain while controlling the payload content, causing the host app to process attacker-controlled data under a victim tenant's identity — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Any actor able to install the target app on a shop they control (a normal, unprivileged onboarding flow for public apps) can capture one legitimately HMAC-signed webhook body from Shopify, then freely replay it to the app's public webhook endpoint with forged `shop`/`topic`/`webhook_id` headers — no access token, `client_secret`, or privileged access is required, only network access to the app's webhook route.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (at minimum `shop`) in the HMAC-verified signable material, or independently authenticate/bind the shop-domain header before it is passed to `WebhookMetadata`, e.g., by requiring the caller to confirm the header against a known/registered shop for that specific webhook subscription/body combination, rather than trusting header values whenever body-only HMAC validation succeeds.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (an attacker-controlled store) and trigger a webhook event (e.g., `customers/create`) so Shopify sends a legitimately HMAC-signed request to the app's webhook endpoint; capture the raw body `B` and its valid `X-Shopify-Hmac-Sha256` value `H`.
2. Replay a new HTTP POST to the same app webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: <topic of attacker's choosing>`
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H` (see `Request#to_signable_string` / `HmacValidator#validate_signature`).
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: <forged topic>, shop: "victim-shop.myshopify.com", body: <attacker body>, ...)`, causing the host application to act on attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
