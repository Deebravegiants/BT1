### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop-domain` header — which is *not* covered by that signature — as the tenant identity passed to the app's handler. This breaks the intended equality `hmac_verified_bytes == bytes_the_handler_trusts_for_tenant_identity`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and then forwards `request.shop` (the unverified header) directly to the handler as the tenant identifier: [3](#0-2) 

Because the `hmac-sha256` value only proves the integrity of the JSON body, not of the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, any request whose body+hmac pair is valid (e.g. a real webhook the attacker legitimately received for their own shop, since the same app `client_secret`/HMAC key is shared across all shops that install the app) can be replayed to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. `HmacValidator.validate` will report success because it only checks the body, and `Registry.process` will pass the attacker-chosen `shop` value into `WebhookMetadata`/the handler as if it were authenticated.

### Impact Explanation
This crosses a tenant boundary: a multi-tenant app process trusts `shop` (obtained from an unauthenticated header) to route webhook data to per-shop records, uninstall flows, GDPR/compliance actions, or business logic keyed by shop. Since the app's own client_secret is the shared HMAC key across all its installed shops, any shop installing the app can, with a validly-signed webhook body for its own shop, present that same body/hmac while claiming to be a different (victim) shop — resulting in cross-tenant data confusion/injection into another merchant's context. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires: (1) the app is installed on more than one shop (multi-tenant, the common case), (2) the attacker installs the app on their own shop or otherwise obtains any validly-HMAC'd webhook body/HMAC pair (readily available — they simply receive their own shop's webhooks), and (3) they can hit the app's public webhook endpoint with custom headers, which is trivial since these endpoints are public HTTP callback URLs. No access token, credentials, or privileged account is required — only an attacker-controlled shop that can install the target app, which is an unprivileged internet-facing action against a public endpoint.

### Recommendation
Bind the shop identity (and other trust-relevant metadata such as topic/webhook-id) into the HMAC-verified data, or otherwise validate `shop-domain` out of band. Concretely:
- Include the shop domain (and other headers required for routing/authorization decisions) in `to_signable_string` so any tampering invalidates the HMAC, or
- Cross-check the `shop-domain` header against records of shops that are actually installed for this app (e.g., verify a session exists for that shop) before trusting it for tenant-scoped operations, and reject if unknown/mismatched.
- Document explicitly that only the body is HMAC-protected and headers are unauthenticated, so downstream apps do not conflate "HMAC valid" with "all headers/shop trusted."

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on victim `victim-shop.myshopify.com`, both sharing the same app `client_secret`.
2. Attacker's own shop triggers a webhook (e.g. `orders/create`); attacker captures the raw body and the resulting `x-shopify-hmac-sha256` value — both are legitimately signed with the app's secret.
3. Attacker POSTs to the app's public webhook endpoint with the same raw body/HMAC but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks the body against the HMAC): [4](#0-3) 
5. `Registry.process` invokes the handler with `shop: request.shop` = `"victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [5](#0-4) 
6. Any app logic keyed off `data.shop` (e.g. updating per-shop records, triggering shop-specific side effects) is now executed under the victim shop's identity using attacker-supplied data — a cross-tenant confusion/injection.
