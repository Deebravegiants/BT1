### Title
Unseparated cache key collision in `getCachedStorageDepositValue` can return a stale zero-fee storage-deposit result for the wrong `(contractId, accountId)` pair - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key as `` `${contractId}${accountId}` `` with no separator, so two distinct `(contractId, accountId)` pairs that concatenate to the same string collide. Because the cache only ever stores the "no top-up needed" case (`result[1] >= result[0]`), a collision can cause `estimateWithdrawalFee` to silently return `feeAmount = 0` for a destination that actually lacks sufficient NEP-141 storage balance.

### Finding Description
The broken equality: the fee computed for `(tokenAccountId, destinationAddress)` must equal `getNearNep141MinStorageBalance(tokenAccountId) - getNearNep141StorageBalance(tokenAccountId, destinationAddress)` for that exact pair. With the collision, `estimateWithdrawalFee` instead returns the cached result for a *different* `(contractId', accountId')` pair whose concatenation matches.

Code path: [1](#0-0) 

`estimateWithdrawalFee` calls this helper with `tokenAccountId` (derived from the caller-supplied `assetId` via `utils.parseDefuseAssetId`) and `args.withdrawalParams.destinationAddress` (fully caller-supplied): [2](#0-1) 

Root cause: NEAR account IDs allow `.` as a valid character in both the token contract ID and the destination account ID, so `contractId + accountId` is not injective — e.g. `contractId="usdc.near"`, `accountId="alice.near"` produces the same key string as `contractId="usdc.nearalice"`, `accountId="near"`. Since the cache is only populated when `result[1] >= result[0]` (i.e., only "sufficient storage / zero fee" results are cached), a collision can only ever inject a false *zero-fee* result into a victim's lookup, never the reverse. This means an attacker who can get some `(contractId', accountId')` pair with a real zero-fee outcome cached under a colliding key can cause a later legitimate `estimateWithdrawalFee(tokenAccountId, destinationAddress)` call — for a destination account that actually needs a storage top-up — to be served that stale zero-fee entry.

Downstream, `estimateWithdrawalFee`'s `feeAmount`/`underlyingFees.storageDepositFee` feed `createWithdrawalIntents`, which passes `storageDeposit: 0` into `createWithdrawIntentPrimitive`. If the real destination is not registered with the token contract (or has insufficient storage balance), the resulting on-chain `ft_transfer_call` can fail, leaving the withdrawal unable to complete without manual intervention.

None of the existing guards catch this: `validateWithdrawal` only checks address format/existence and token/destination collision (`validateAddress`, `compareAddresses`, `getCachedAccountExistenceCheck`) and does not touch the storage-deposit cache; `supports()` only checks route/asset format; `FeeExceedsAmountError` and `getUnderlyingFee` operate on the (already-wrong) fee value and cannot detect that it was computed for a different account.

### Impact Explanation
The attacker (or an unrelated actor sharing the same long-lived `DirectBridge` instance in an integrator's backend) can cause `feeEstimation.underlyingFees[NearWithdrawal].storageDepositFee` and `feeEstimation.amount` to be `0` for a withdrawal whose real destination requires a nonzero NEP-141 storage top-up. The withdrawal intent is then built with `storageDeposit: 0`, and the subsequent `ft_transfer_call` to the real destination can fail on-chain, stranding the withdrawal until manual intervention — a misreported fee for the wrong account, breaking the intended one-to-one binding between `destinationAddress` and its computed storage fee. This is repeatable for any pair of strings the attacker can arrange to collide.

### Likelihood Explanation
Requires: (1) a long-lived `DirectBridge`/cache instance shared across calls (typical integrator backend pattern), (2) the attacker being able to trigger a first `estimateWithdrawalFee` call with a crafted `(contractId', accountId')` pair that is a real NEP-141 contract/account with sufficient balance (attacker can deploy or use their own NEP-141 token contract with a permissionless NEAR account name chosen to produce the collision string), and (3) a victim/legitimate call later using the colliding `(tokenAccountId, destinationAddress)` pair. NEAR account-name permissionlessness makes constructing the colliding contract name feasible. This is a real cache-key design flaw, though it requires deliberate string engineering and a shared bridge instance, keeping likelihood moderate rather than trivial.

### Recommendation
Use a collision-free cache key, e.g. include a fixed separator and length-prefix or JSON-encode the tuple: `` `${contractId.length}:${contractId}:${accountId}` `` or `` `${contractId}\u0000${accountId}` ``, ensuring no valid NEAR account ID can produce ambiguous concatenation.

// vitest, mocking only getNearNep141MinStorageBalance / getNearNep141StorageBalance (HTTP/RPC layer)
it("does not return a colliding cached storage-deposit result for a different account", async () => {
  const bridge = new DirectBridge({ envConfig, nearProvider, solverRelayApiKey });

  // Pair A: contractId="usdc.nearalice", accountId="near" -> key "usdc.nearalicenear"
  // Pair B: contractId="usdc.near", accountId="alicenear" -> key "usdc.nearalicenear" (collision)
  mockStorageBalance({ contractId: "usdc.nearalice", accountId: "near", min: 100n, user: 200n }); // sufficient -> cached as 0-fee
  mockStorageBalance({ contractId: "usdc.near", accountId: "alicenear", min: 100n, user: 0n });    // insufficient -> should require fee 100n

  const feeA = await bridge.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:usdc.nearalice", destinationAddress: "near", routeConfig: undefined },
  });
  expect(feeA.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(0n);

  const feeB = await bridge.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:usdc.near", destinationAddress: "alicenear", routeConfig: undefined },
  });

  // Correct behavior: feeB should be recomputed against (usdc.near, alicenear) = 100n
  expect(feeB.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(100n);
  // Bug: with the unseparated key, feeB incorrectly equals feeA's cached 0n
});

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
