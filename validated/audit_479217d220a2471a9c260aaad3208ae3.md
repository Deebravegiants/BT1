### Title
Webhook Shop-Domain Tenant Identifier Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking an app's webhook handler with the shop identifier that the host application is expected to use as its tenant key. In reality, the HMAC signature only ever covers the raw request body — never the `shop-domain` header that identifies *which* shop/tenant the webhook belongs to. Because the app's `client_secret` (`api_secret_key`) used to sign webhooks is shared across every shop that has installed the app, any legitimate (even a free-trial, self-service) shop can capture a genuinely-signed webhook delivered to its own endpoint and replay that same body/HMAC pair while substituting a victim shop's domain in the `shop-domain` header. `Registry.process` will accept it as authentic and hand the victim's shop identifier plus attacker-controlled body to the app's handler.

### Finding Description
The signable material for a webhook request is defined as just the raw body: [1](#0-0) 

The `shop` accessor, sourced straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature only from `to_signable_string` (the body) and compares it with `secure_compare`, so it never involves the shop field at all: [3](#0-2) 

`Registry.process` uses this validator as its sole authenticity check, then immediately trusts `request.shop` (and `request.parsed_body`) to build the `WebhookMetadata` passed to the app-provided handler: [4](#0-3) 

The documented equality the caller is led to believe holds is:
`hmac_valid(body, api_secret_key) == true` implies `shop header == authentic origin of body`.

The actual equality enforced is only:
`hmac_valid(body, api_secret_key) == true` implies `body was signed once by Shopify for this app`, with **no binding whatsoever to which shop** the signature was originally issued for.

Since `api_secret_key` is the app's single shared `client_secret` (identical for every merchant that installs the app), a request signed for Shop A's body is equally "valid" no matter what shop-domain header accompanies it. This is confirmed by the library's own documentation, which explicitly tells implementers that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` can be used directly as the tenant key (e.g., `shop_domain: data.shop`) when enqueueing further work: [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the tenant-isolation guarantee the gem's `process` API implicitly promises: "an HMAC-valid webhook can be attributed to the shop named in its headers." Any shop that installs the app (an unprivileged, self-service action requiring no special credentials) can obtain genuinely-signed webhook deliveries for its own tenant, then replay the identical body/HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The app, following the gem's documented contract, will treat the forged delivery as authentic and process/store attacker-controlled data under the victim tenant's identity — a cross-tenant data-integrity/access violation.

### Likelihood Explanation
The attacker only needs to install the target app on a shop they control (no elevated privileges, no access to `api_secret_key`, no TLS interception) and can then freely replay a captured, validly-signed body while swapping the shop header. This is a straightforward HTTP replay with header modification, well within reach of an "unprivileged internet user" who can self-provision a shop.

### Recommendation
Bind the shop identifier into the material that is actually verified, e.g., have `HmacValidator`/`Request#to_signable_string` incorporate the shop domain (or otherwise require the host application to independently confirm, from its own session store, that the shop named in the webhook is a shop that has actually installed the app and matches a per-shop secret/token) before trusting `request.shop`. At minimum, update the documentation to make explicit that `Registry.process` verifies only the body's authenticity, not the `shop-domain` header, so implementers do not treat `data.shop` as cryptographically authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker registers/receives a legitimate webhook (e.g., `orders/create`) delivered by Shopify to the app's webhook endpoint, capturing the raw body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify as `HMAC-SHA256(client_secret, B)`).
3. Attacker resends the exact same POST to the app's webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged, but replacing the header `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request` parses this into a request whose `to_signable_string` is still `B`; `HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and it matches `H`, so validation succeeds.
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body — the app now processes attacker-controlled data as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
