### Title
Precision/decimals desync between `pallet-hyper-fungible-token` send-time encoding and receive-time conversion can mint wrong amounts - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`pallet-hyper-fungible-token`'s EVM→Substrate leg converts the raw ERC20 `amount` embedded in an ISMP `PostRequest` into the local balance using the `Precisions` storage value read *at delivery time* in `on_accept`. The EVM-side `HyperFungibleToken.send()` contract does not embed the decimals/precision it assumed when the user submitted the transaction — it only sends the raw `params.amount`. If `Precisions` is updated (via `update_token`/`register_token`, a `CreateOrigin`-gated but ordinary maintenance call) between the moment a user's EVM `send()` transaction is broadcast and the moment the corresponding ISMP message is delivered and processed by `on_accept`, the amount minted/unlocked to the beneficiary on Substrate is computed against a different scaling factor than the one the sender/receiver expected — exactly the same "rebase desync" root cause as the ECO L1/L2 report.

### Finding Description
In `send()` on the substrate side, `erc_decimals` is read once via `Precisions::<T>::get(...)` and used to scale the outgoing amount into `erc20_amount`, which is then baked as a literal `uint256` into the cross-chain `Message.amount`: [1](#0-0) [2](#0-1) 

For the reverse direction, `on_accept` re-derives `erc_decimals` from the *current* `Precisions` storage at the time the message is processed, not from any value carried in the message itself, and uses it to scale the raw incoming ERC20 amount down to the local balance: [3](#0-2) 

The scaling helper divides by `10^(erc_decimals - local_decimals)`, so any change to the configured `erc_decimals` for that `(asset, chain)` pair changes the amount actually minted for a message whose `amount` field was fixed at dispatch time on the EVM side: [4](#0-3) 

`Precisions` can legitimately be mutated at any time by `update_token`/`register_token` (gated by `CreateOrigin`, not by a malicious actor, but as an ordinary/authorized maintenance call, e.g. correcting a misconfigured decimals value): [5](#0-4) 

The `HyperFungibleToken.sol` EVM contract that originates these messages does not embed any precision/decimals value into the `Message` body — it burns/locks and dispatches only `{from, to, amount, data}` with no synchronization mechanism (no epoch/version tag tying the message to the precision in effect at send time): [6](#0-5) [7](#0-6) 

This is the same class of bug as the ECO `notifyGenerationIncrease`/`rebase()` desync: a scaling factor is applied independently and asynchronously on each side of a cross-chain bridge, with no guarantee the two applications see the same factor for the same logical transfer.

### Impact Explanation
If `Precisions` for an `(asset, chain)` pair is decreased between send and delivery, in-flight transfers get under-minted on Substrate (user fund loss). If it is increased, in-flight transfers get over-minted (attacker/user profit funded by the pallet's escrow/asset supply, i.e. unbacked mint relative to what was actually locked/burned on the EVM side). Because `Precisions` changes are ordinary configuration updates (not exploits themselves), any user with a transfer in flight during such an update is exposed, and an attacker could time a `send()` immediately before a known precision update to profit, repeating the attack for each update window. This can lead to concrete theft of funds or unbacked minting on the destination chain.

### Likelihood Explanation
Requires: (1) a `Precisions` update via `update_token`/`register_token` for a token that already has active in-flight transfers, and (2) a user (attacker or victim) with a `send()` already dispatched from the EVM `HyperFungibleToken` contract but not yet processed by `on_accept`. Decimal/precision corrections are a real, documented operational action ("Incorrect precision values would lead to failed transfers" is explicitly called out for the related deprecated Token Gateway), so this window is realistic, especially for chains with longer finality/ISMP delivery times, and an attacker can actively race the update rather than wait for an accidental collision.

### Recommendation
Embed the precision/decimals (or a full fixed-point amount already normalized to a chain-agnostic denomination) used at send-time directly in the cross-chain `Message` body instead of re-deriving it from mutable storage at delivery time. Alternatively, version the `Precisions` entries and require `on_accept` to use the precision value that was active at the block height/timestamp the request was dispatched (carried in the message or looked up via a historical/checkpointed map), so that updates to `Precisions` never retroactively change the scaling applied to already-dispatched messages.

### Proof of Concept
1. Register/configure asset `X` for chain `EVM-C` with `erc_decimals = 18` via `register_token`.
2. User submits `HyperFungibleToken.send()` on `EVM-C` for `amount = 100e18`, burning 100 tokens; the ISMP `Message.amount` field literally carries `100e18`.
3. Before the ISMP request is delivered, governance/admin calls `update_token` to change `Precisions` for `(X, EVM-C)` from `18` to `6` (e.g., to correct a misconfiguration).
4. `on_accept` on the Substrate pallet now computes `convert_to_balance(100e18, erc_decimals=6, local_decimals=...)`, dividing by `10^(6-local_decimals)` instead of `10^(18-local_decimals)`, minting/unlocking a drastically different (much larger) amount than the 100 tokens actually burned on `EVM-C` — see `convert_to_balance` at [4](#0-3)  and its use in `on_accept` at [8](#0-7) .
5. Symmetrically, an increase in `erc_decimals` during the in-flight window causes under-minting and permanent user fund loss.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
