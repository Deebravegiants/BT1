### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw request body, while `shop-domain`, `topic`, `webhook-id`, and `api-version` are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` treats HMAC success as proof the whole webhook (including `shop`) is authentic and hands `request.shop` straight to the app's handler as `WebhookMetadata#shop`. Because `shop` is never bound into the signed material, an attacker who can produce (or capture) any one valid `body`/`hmac` pair — trivially available to them for their own shop, since anyone can create a Shopify store and install an app to receive real webhooks — can replay that exact body+hmac to the target app's public webhook endpoint with an arbitrary `shop-domain` header. The signature will still validate, and the app will process the payload as if it belongs to the victim shop.

### Finding Description
The identity binding that should hold is:
`shop asserted by Shopify in the signed webhook == shop the app attributes the payload to`

In this gem that binding is broken:

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` (and `topic`, `api_version`, `webhook_id`) come from raw HTTP headers with no cryptographic tie to the body or the HMAC: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` only recomputes and compares the HMAC over `to_signable_string` (i.e., the raw body), never touching `shop`, `topic`, etc.: [3](#0-2) 
- `Registry.process` gates entirely on this body-only HMAC check and then trusts `request.shop` as the tenant identity passed to the handler: [4](#0-3) 

Because `shop` is excluded from the signed bytes, "bytes verified" (the raw body) and "bytes/identity acted on" (the `shop` header used by the handler) diverge. Any request whose body+hmac pair is valid for *some* shop will also validate for *any* `shop-domain` header value the attacker chooses to send, since the header plays no role in the HMAC computation.

### Impact Explanation
Webhook endpoints are public, unauthenticated HTTP endpoints reachable by any internet user. An attacker does not need the app's `client_secret` or an access token to obtain a valid body+HMAC pair — they only need one legitimate webhook delivery, which they can trivially generate by installing the app on a shop they control (a normal, unprivileged action) and capturing the resulting webhook. They can then replay that exact request to the same endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain (a public, guessable value like `victim.myshopify.com`). The HMAC still validates because it never covered those headers.

Depending on how the app's registered `WebhookHandler` uses `WebhookMetadata#shop` (e.g., to select which tenant's data to update, mark a shop uninstalled, process GDPR redaction, or ingest order/customer data), this allows an attacker to inject or misattribute events into a different tenant's context — a cross-tenant identity confusion driven purely by unauthenticated header manipulation, which qualifies as cross-tenant access.

### Likelihood Explanation
High likelihood: the webhook endpoint is by design internet-facing and unauthenticated except for the HMAC check; obtaining a valid body+HMAC pair requires nothing more than the attacker installing the target app on their own (or any) test store, which is normal unprivileged app-installation behavior, not privileged access to Shopify or the victim's credentials. No secret leakage, TLS interception, or social engineering is required.

### Recommendation
Bind the tenant/topic identity into the material that is actually verified, e.g.:
- Include `shop-domain`, `topic`, and `webhook-id` in the string that is HMAC-verified (this would require a protocol change on Shopify's side and isn't fully under the gem's control), **or**
- At minimum, document/enforce in `Webhooks::Registry.process` that `request.shop` is *not* cryptographically authenticated by `HmacValidator.validate`, and require/encourage callers to independently confirm the `shop` value against their own known set of installed shop domains (e.g., via `ShopValidator` and/or a lookup against stored sessions) before acting on `WebhookMetadata#shop`, rather than implying it is trusted purely because HMAC validation passed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free/unprivileged action) and lets Shopify deliver a real webhook, e.g. `orders/create`, to the app's public webhook endpoint. Attacker captures the exact `raw_body` and the `x-shopify-hmac-sha256` header from this legitimate delivery.
2. Attacker resends an HTTP POST to the same public webhook endpoint with:
   - The identical `raw_body` and `x-shopify-hmac-sha256` value captured in step 1.
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any target shop domain).
   - Optionally a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `raw_body` — this passes because the body is unchanged. [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, causing the app to process attacker-supplied data under the victim shop's identity, despite Shopify never having sent this webhook for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
