### Title
Unconditional Uniswap V2 swap inside `EvmHost.dispatch()` can revert and block order cancellation / escrow-refund messages - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` unconditionally route any native-value payment through a hard‑coded, unguardable `swapETHForExactTokens` call on the local Uniswap V2 router whenever `msg.value > 0`. This swap has no fallback and no way for the caller to opt out once native value is attached, so a transient liquidity/price problem in that swap reverts the entire dispatch — including the cross-chain cancellation/refund messages that `ExtrinsicIntents._cancelFromSource` / `_cancelFromDest` (and the Tron `IntentGatewayV2`) rely on to release a user's escrowed funds. This mirrors the M-18 pattern: an oracle/price-dependent check that is unrelated to the actual user intent (exiting/cancelling a position, not swapping) gates the ability to stop a loss or recover funds.

### Finding Description
`EvmHost.dispatch()` for both POST and GET requests contains identical logic: [1](#0-0) [2](#0-1) 

Whenever `msg.value > 0`, the function performs `swapETHForExactTokens(post.fee/get.fee, path, address(this), block.timestamp)` against the configured Uniswap V2 router, with `amountInMaximum` implicitly capped at `msg.value`. There is no user-configurable slippage parameter and no branch to skip the swap while still using native value — the only way to avoid the swap entirely is to send `msg.value == 0` and pre-approve/transfer the fee token via `dispatchWithFeeToken`: [3](#0-2) 

This `dispatch()` entrypoint is exactly what `ExtrinsicIntents._cancelFromSource` uses to send the GET request that verifies non-fill and triggers the escrow refund, and what `_cancelFromDest` uses to send the `RefundEscrow` POST back to the source chain: [4](#0-3) 

Both call sites branch purely on `msg.value > 0`:

```solidity
if (msg.value > 0) {
    IDispatcher(hostAddr).dispatch{value: msg.value}(request);
} else {
    dispatchWithFeeToken(request);
}
```

The documented/SDK-driven UX for cancellation pays with native value quoted ahead of time and passes it straight through: [5](#0-4) [6](#0-5) 

Because the swap's exact input amount is fixed at quote time (`quote()` in `HyperApp.sol` calls `getAmountsIn` once) but is only executed later on-chain with `amountInMaximum = msg.value`, any adverse price movement, thin liquidity, or MEV sandwich against the feeToken/WETH pair between quoting and execution causes `swapETHForExactTokens` to revert with `EXCESSIVE_INPUT_AMOUNT` (or run out of liquidity entirely). Unlike the AutoRange/AutoExit case, there isn't even a caller-level knob (like `amountIn = 0`) to bypass the swap once native value is attached — the entire dispatch, and therefore the cancellation/refund message, fails.

### Impact Explanation
This blocks the exact recovery path a user needs when they want to exit: cancelling an unfilled cross-chain intent order and recovering escrowed input tokens (`_cancelFromSource`/`_cancelFromDest` in `ExtrinsicIntents.sol`, and the equivalent Tron `cancelOrder`). If the router-level swap reverts — which is more likely precisely during volatile markets, the same conditions under which a user is most motivated to cancel and pull out funds — the cancellation message cannot be dispatched at all. Funds remain locked in escrow until (a) conditions change enough for the swap to succeed, or (b) the caller manually reconstructs the transaction to instead pay in feeToken via `dispatchWithFeeToken`, which is not what the SDK or documented flow does by default. This is a route/message that becomes undeliverable for reasons unrelated to the actual protocol action, directly analogous to the confirmed Medium-severity M-18 finding.

### Likelihood Explanation
Any unprivileged actor dispatching a POST/GET request with native value — including a user or relayer executing a documented `cancelOrder` flow — can hit this. The failure condition (thin feeToken/WETH liquidity, price drift, or a sandwich attack against the swap) is realistic on lower-liquidity EVM chains where Hyperbridge's Uniswap V2 fee-token pools are typically shallow, and is more likely to occur during exactly the volatile conditions that prompt users to cancel orders.

### Recommendation
Do not force a swap-and-revert coupling onto message dispatch used for escrow refunds/cancellations:
- Allow the caller to supply a slippage bound and/or refund path so a swap failure degrades gracefully (e.g., retry with feeToken, or refund native value) instead of reverting the whole dispatch.
- For cancellation-critical dispatch paths (`_cancelFromSource`, `_cancelFromDest`), prefer or default to `dispatchWithFeeToken` when it is available, or add a fallback: if the native-value swap fails, fall back to pulling the fee token directly from the payer rather than aborting the message.
- More generally, decouple fee-payment mechanics from the deliverability of a message whose purpose is recovering user funds, matching the fix pattern applied to `_validateSwap` in the referenced disclosure (skip/bypass unrelated validation when the caller's intent does not require it).

### Proof of Concept
1. User places a cross-chain intent order via `IntentGatewayV2.placeOrder`, escrowing input tokens.
2. Market conditions turn adverse; user wants to cancel. They call the documented SDK flow (`OrderCanceller`), which quotes `nativeValue` and constructs a `cancelOrder` transaction that dispatches a GET (source-side) or RefundEscrow POST (destination-side) with that native value attached, per `_cancelFromSource`/`_cancelFromDest` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`.
3. Between the SDK's `quote()` call (`getAmountsIn`) and on-chain execution, the feeToken/WETH pool price moves (normal volatility or a sandwich), so the required native input to buy `request.fee` feeToken now exceeds the attached `msg.value`.
4. `EvmHost.dispatch()`'s `swapETHForExactTokens` call reverts with `UniswapV2Router: EXCESSIVE_INPUT_AMOUNT`, reverting the entire `cancelOrder` transaction (`evm/src/core/EvmHost.sol:921-932` / `974-985`).
5. The user cannot dispatch the cancellation/refund message and remains stuck in the order, unable to recover escrowed funds, until liquidity/price conditions recover or they manually build a feeToken-paid transaction outside the standard SDK flow.

    function dispatchWithFeeToken(DispatchPost memory request) internal returns (bytes32) {
        address hostAddr = host();
        address feeToken = IDispatcher(hostAddr).feeToken();
        if (request.payer != address(this)) IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee);
        IERC20(feeToken).forceApprove(hostAddr, request.fee);
        return IDispatcher(hostAddr).dispatch(request);
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
