## Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) attributes purely from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body. `Webhooks::Registry.process` treats a passing HMAC check as proof the entire webhook (including which shop it is for) came from Shopify, and hands `request.shop` straight to the app's handler. This breaks the identity binding `hmac_verified_bytes == data_acted_on`, allowing any holder of one valid `(body, hmac)` pair to replay it with a forged `shop-domain` header pointing at a different, victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` only returns the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read from headers that are entirely outside of `to_signable_string`, so they are never part of the HMAC-verified bytes: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the signature over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` treats this body-only check as sufficient authentication for the whole request, then forwards the unauthenticated `request.shop` to the handler as trusted tenant data: [4](#0-3) 

The gem's own documentation reinforces the false assumption that this check authenticates the entire request, not just the body: "This will verify the request did indeed come from Shopify and then call the specified handler" (`docs/usage/webhooks.md:125`). Host apps are explicitly told to key off `data.shop` for tenant-specific work: `docs/usage/webhooks.md:14, 25-26`.

Because the same `api_secret_key` is used to sign webhook bodies for every shop that installs the app, a valid `(body, hmac)` pair captured from any one installed shop (including one the attacker installs on their own free/dev store) remains cryptographically valid for that exact body regardless of which shop header accompanies it. The equality that should hold — "shop the HMAC authenticates" == "shop the handler acts on" — does not hold, because the shop is never part of the signed bytes at all.

### Impact Explanation
An unprivileged internet user who has installed the app on their own store (a normal, unprivileged action) can capture one legitimate webhook `(raw_body, X-Shopify-Hmac-Sha256)` pair and POST it directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. `Registry.process` will accept it (HMAC over body is valid) and invoke the app's handler with `data.shop` set to the victim shop. Any host app that follows the documented pattern and uses `data.shop` to select which tenant's session/data to act on will process attacker-controlled webhook content under a victim tenant's identity — cross-tenant data injection/confusion, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is High for apps that follow the library's documented usage: no secrets, tokens, or privileged access are required — only a copy of one's own legitimately-received webhook body+HMAC and the ability to send an HTTP POST to the app's public webhook endpoint with a different `shop-domain` header. Shop domains (`*.myshopify.com`) are often guessable or publicly known (app store listings, storefront URLs), making target selection easy.

### Recommendation
Bind the shop (and other acted-upon metadata) into the HMAC-verified surface, or otherwise cryptographically tie the header-derived shop to the verified body:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` if Shopify's webhook signing ever covers them, or
- At minimum, require the caller to independently confirm the `shop` belongs to a shop with a known, previously-issued access token/session before trusting `request.shop`, rather than treating the body-only HMAC pass as authenticating the shop attribution.
- Update `docs/usage/webhooks.md` to stop stating the HMAC check "verif[ies] the request did indeed come from Shopify" for the shop field specifically, and warn integrators that `data.shop` is not covered by the signature.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (`attacker-shop.myshopify.com`) — a normal, unprivileged action.
2. Shopify sends a real webhook to the app's public endpoint; attacker captures the raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`, and `api_secret_key` is the same for every installed shop).
3. Attacker sends a new POST to the same public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid per `lib/shopify_api/utils/hmac_validator.rb:26-31`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) validates the HMAC (passes, since it only checks `B`/`H`), finds the handler, and calls it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198`).
5. Any host app handler that uses `data.shop` to select the victim's session/access token (as documented in `docs/usage/webhooks.md:25-26`) processes attacker-controlled data under the victim tenant's identity.
