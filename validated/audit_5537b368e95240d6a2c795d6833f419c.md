### Title
Tron `IntentGatewayV2.placeOrder()` omits duplicate input/output token rejection, allowing shared escrow buckets to be under/over-released - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
This is the same bug class as the reported GMX issue: a value that should be tracked per distinct leg is instead collapsed into one shared key when two legs reference the same underlying identifier, corrupting the amount the contract later validates/uses. In GMX, `getPoolAmount` collapses long/short pool accounting into one storage slot when `market.longToken == market.shortToken`, so `validatePoolAmount()` reads half the true amount. In Hyperbridge's Tron port of the Intent Gateway, escrow accounting is keyed by `_orders[commitment][token]`, and when an order contains two input (or output) legs with the same token address, the amounts collapse into a single shared bucket, while the per-leg fill/release logic still treats each leg independently.

### Finding Description
The canonical EVM `IntentGatewayV2.sol` explicitly guards against this by rejecting duplicate input tokens (`if (_orders[commitment][token] != 0) revert InvalidInput();`) [1](#0-0)  and duplicate output tokens via transient-storage tracking [2](#0-1) . A regression test confirms this was added specifically to fix an "over-release" bug: `testRevert_PlaceOrder_DuplicateInputTokens` — "Regression test for: same-chain partial fills over-release repeated input escrow" [3](#0-2) .

The Tron port (`evm/tron/contracts/apps/IntentGatewayV2.sol`) has no equivalent duplicate-token check on `placeOrder()`. Its input escrow loop credits `_orders[commitment][token]` using `+=` for every input leg without ever checking for a pre-existing non-zero value [4](#0-3) [5](#0-4) . This means two order inputs with the same token address are merged into one escrow bucket that equals the sum of both legs, while the order's own `inputs[]` array (used elsewhere for per-leg redemption math, e.g. proportional fill accounting in `IntrinsicIntents.sol`'s `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired`) still treats each leg's `amount` as independent [6](#0-5) . Withdrawal then decrements the merged bucket per redemption request token-by-token via `_orders[body.commitment][token] -= amount` [7](#0-6) , which does not by itself protect against a caller supplying a withdrawal amount computed from only one leg's `amount` while the bucket actually contains the sum of two legs (or vice versa) — the invariant that "one escrow key == one order leg" that the mainline EVM contract's duplicate-rejection restores is missing here.

### Impact Explanation
Because the escrow mapping key (`token` address) does not uniquely identify an order leg when two legs share a token, partial-fill or multi-leg redemption paths that compute per-leg amounts from `order.inputs[i].amount` independently, but check/release against the single merged `_orders[commitment][token]` value, can be driven into an inconsistent state — enabling either a legitimate leg's escrow to be released more than once (theft of protocol/user funds) or a revert/lockup of the remaining legitimate escrow (permanent freezing of funds), depending on redemption ordering. This is a fund-safety defect matching the "concrete theft or permanent freezing of funds" bar, directly analogous to the GMX pool-amount miscalculation causing wrong validation.

### Likelihood Explanation
Any unprivileged user submitting a `placeOrder()` transaction on the Tron-deployed Intent Gateway can construct an order with duplicate input (or output) token entries — nothing in `placeOrder()` on this contract rejects it, unlike the EVM version. This makes the root cause directly reachable from a single submitted transaction with no privileged role required.

### Recommendation
Port the same duplicate-token rejection that `evm/src/apps/IntentGatewayV2.sol` already implements (reverting `InvalidInput` on any repeated input token address in `order.inputs[]`, and repeated output token address in `order.output.assets[]`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder()`, ensuring the `_orders[commitment][token]` key remains a 1:1 mapping to a single order leg.

### Proof of Concept
1. User calls `placeOrder()` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: 600}, {token: USDC, amount: 400} ]`.
2. The loop at [5](#0-4)  executes `_orders[commitment][USDC] += 600` then `+= 400`, leaving `_orders[commitment][USDC] == 1000`, with no rejection.
3. Downstream partial-fill/redemption logic that computes amounts from `order.inputs[i].amount` per leg (as in `IntrinsicIntents.sol`'s proportional-release formula) can be exploited to redeem against the same merged bucket using each leg's individual amount, releasing more (or less) than the actual per-leg entitlement, since the bucket no longer corresponds 1:1 to a single leg's escrowed value.
