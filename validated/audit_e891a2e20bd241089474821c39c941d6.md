### Title
Position NFT transfer to an incapable contract permanently freezes the lending account - (File: `contracts/position-nft/src/contract.rs`)

### Summary
The position NFT is the sole ownership record for a controller account, so transferring it moves control of all collateral and debt. [1](#0-0)  The contract exposes the stock OpenZeppelin `transfer` and `transfer_from` methods and does not verify that a contract recipient can later authorize or initiate NFT/controller calls. [2](#0-1)  An owner can therefore send the NFT to an inert Wasm contract, permanently losing control of the underlying lending position. [3](#0-2) 

### Finding Description
`PositionNft` implements `NonFungibleToken` with `ContractType = Enumerable`; `token_uri` is the only overridden token behavior. [2](#0-1)  The inherited `transfer(from, to, token_id)` accepts the supplied `to` address after sender authorization, with no compatibility check for a contract recipient. [3](#0-2) 

The controller resolves authority through the current NFT owner rather than maintaining a separate owner field. [4](#0-3)  Owner-gated flows such as `withdraw` require `caller.require_auth()` and then require that caller to be the owner or an active delegate. [5](#0-4) 

If `to` is a contract with no code path that can transfer the NFT or invoke owner-gated controller methods, the account has no usable owner. [1](#0-0)  The NFT remains well-formed and can still be read through `owner_of`, but neither the old holder nor an arbitrary third party can recover control. [6](#0-5) 

### Impact Explanation
For a solvent account, all collateral and claimable yield controlled by the NFT are permanently frozen because no capable owner can authorize withdrawal, repayment followed by withdrawal, delegation, or NFT recovery. [1](#0-0)  For an indebted account, the debt also remains attached to the inaccessible account and may be liquidated by third parties, while the NFT owner still cannot recover or manage the position. [6](#0-5) 

This is not limited to direct `transfer`; an approved spender can reach the same state through `transfer_from(spender, from, inert_contract, token_id)`. [7](#0-6) 

### Likelihood Explanation
Any position holder can trigger the issue by passing a Wasm contract address as `to`; the endpoint is intentionally exposed to holders and approved operators. [8](#0-7)  Wallet, marketplace, integration, or manual-address errors can select a contract that can receive the NFT in ledger state but cannot subsequently invoke the NFT or controller. [3](#0-2) 

The controller rejects only the pool and controller as payout recipients in `borrow`/`withdraw`, which demonstrates the protocol recognizes inaccessible protocol recipients but does not extend equivalent protection to the more dangerous NFT ownership transfer. [9](#0-8) 

### Recommendation
Do not allow an unrestricted NFT transfer to an arbitrary Wasm contract recipient without proving that the recipient can manage the position. [2](#0-1) 

Prefer a receiver-initiated claim flow: the current owner marks the token as claimable by a specific recipient, and the recipient contract must itself invoke a `claim` method that updates ownership. [1](#0-0)  Alternatively, reject Wasm recipients in `transfer`/`transfer_from` unless the recipient is explicitly recognized by the protocol as capable of managing accounts. [7](#0-6) 

### Proof of Concept
1. Alice supplies collateral through `controller::supply(caller=alice, account_id=0, spoke_id=S, assets=[(hub_asset, amount)])`; this creates account/token id `N` and mints its NFT to Alice. [10](#0-9) 
2. Alice calls `position_nft::transfer(from=alice, to=dead_contract, token_id=N)`, where `dead_contract` is a Wasm contract containing no method capable of transferring the NFT or calling controller position methods. [11](#0-10) 
3. `owner_of(N)` now returns `dead_contract`, and Alice’s subsequent `withdraw` call fails the owner/delegate check. [12](#0-11) 
4. Because `dead_contract` cannot authorize or initiate a further NFT/controller call, no unprivileged path can restore a capable owner or withdraw the collateral. [13](#0-12) 

A minimal sequence is:

```text
controller.supply(alice, 0, spoke_id, [(hub_asset, amount)])
    -> account_id = N

position_nft.transfer(
    from = alice,
    to = dead_contract,
    token_id = N,
)

controller.withdraw(
    caller = alice,
    account_id = N,
    withdrawals = [(hub_asset, 0)],
    to = None,
)
    -> reverts NotAuthorized
``` [14](#0-13)

/// Rejects pool and controller recipients with `InvalidFlashloanReceiver`.
/// Pool self-transfers debit cash without moving tokens; controller receipts
/// would remain unclaimed by balance-delta accounting.
pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
