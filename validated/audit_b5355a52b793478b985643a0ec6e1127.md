### Title
Missing sender allowlist enforcement in gateway's legacy Web API capability handler allows any signer to trigger DON-wide workflow requests - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The external report describes a Convex `VoterProxy.deposit` function that accepts calls "from anyone with any `_token` and `_gauge`" because the contract never whitelists/validates the caller-supplied inputs before acting on them. The closest analog in this chainlink repository is the gateway's `capabilities` handler, which forwards a `web_api_trigger` message to every node in a DON without ever checking that the message's cryptographically-recovered sender is an allowlisted/authorized caller — the allowlist check is explicitly marked "TODO" and never implemented.

### Finding Description
Incoming gateway messages are validated for structural correctness in `Message.Validate()`, which recovers the signer address from the signature via `ExtractSigner()` and stores it in `m.Body.Sender`, but performs no check that this signer is a known/authorized entity [1](#0-0) . Any actor can generate an arbitrary ECDSA keypair, sign a well-formed message, and produce a request that passes `Validate()` — this is analogous to how anyone could craft calldata to call `VoterProxy.deposit` with arbitrary `_token`/`_gauge` values.

The `gateway.ProcessRequest` dispatch path calls `msg.Validate()` for legacy DON-ID requests and then routes to the handler's `HandleLegacyUserMessage` with no additional sender authorization [2](#0-1) .

Inside `HandleLegacyUserMessage`, after checking payload decoding, timestamp freshness, and the method name, the code contains an explicit unimplemented allowlist/rate-limit check before forwarding the request to every DON member node: [3](#0-2) 

The comment `// TODO: apply allowlist and rate-limiting here` directly precedes the method whitelist check (`if msg.Body.Method != MethodWebAPITrigger`) and the subsequent `don.SendToNode` fan-out to all DON members. There is no verification that `msg.Body.Sender` (the recovered signer) belongs to any authorized workflow owner or is otherwise entitled to trigger this DON's web API capability.

### Impact Explanation
Because the sender allowlist is never enforced, any unprivileged party who can reach the gateway's `ProcessRequest` endpoint can submit a validly-signed (but attacker-controlled key) `web_api_trigger` message that gets forwarded to every node in the target DON. This is a direct request-impersonation / authorization-bypass analog to the report's core complaint ("anyone can perform any arbitrary calls on behalf of" the privileged component) — here, "on behalf of" any workflow/DON's web API trigger capability, since the identity check that should gate this action is missing.

### Likelihood Explanation
High: exploitation requires no privileged credentials — an attacker only needs to generate a keypair, sign a message body per `GetRawMessageBody`, and satisfy the length/format checks in `Validate()`, all of which are public logic reproducible by anyone. The `TODO` comment itself is direct, uncontestable evidence that this control is not yet implemented in this code path.

### Recommendation
Implement the sender allowlist check before forwarding `web_api_trigger` (and any other legacy) messages to DON nodes in `HandleLegacyUserMessage`, verifying `msg.Body.Sender` against a configured/authorized list of allowed signers (e.g., workflow owners registered for that DON), mirroring the allowlist-based authorization already implemented for the vault capability (`core/capabilities/vault/allow_list_based_auth.go`). Reject unauthorized senders before any `don.SendToNode` fan-out occurs.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair not registered with any DON/workflow.
2. Construct a `Message` with `Body.Method = "web_api_trigger"`, a valid `Body.DonID`, and a fresh `Body.Timestamp`-bearing payload.
3. Sign it with the arbitrary key via `Message.Sign()`.
4. Submit the message to the gateway's legacy `ProcessRequest` endpoint targeting the DON ID.
5. Observe that `msg.Validate()` succeeds (signature format is valid) and `HandleLegacyUserMessage` forwards the request to every DON node via `don.SendToNode`, despite the sender never having been allowlisted — confirmed by the absent implementation at the `// TODO: apply allowlist and rate-limiting here` marker.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
