### Title
`update_token` re-pointing or removing a chain's contract mapping permanently strands in-flight escrowed/burned funds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`pallet_hyper_fungible_token::update_token` lets `CreateOrigin` overwrite or remove the `(StateMachine, AssetId) -> contract` mapping (`TokenContracts`) and its reverse lookup (`ContractToAsset`) used to authenticate/attribute inbound and timed-out cross-chain messages. Any `send` request that was dispatched (and locked/burned the user's local asset) against the *old* contract mapping, but is still in-flight when governance updates or removes that mapping, becomes permanently unredeemable: both the success path (`on_accept`) and the failure/refund path (`on_timeout`) key off the current `ContractToAsset`/`TokenContracts` state, which no longer references the old contract address.

### Finding Description
- `send` locks (native) or burns (non-native) the caller's asset and dispatches a `DispatchPost` to the `to` contract address resolved from `TokenContracts` at call time: [1](#0-0) 
- `update_token` can be called by `CreateOrigin` at any time to change a chain's registered contract address (`add_chains`) or remove it (`remove_chains`). Both paths delete the old `ContractToAsset` entry for that chain/contract pair before continuing: [2](#0-1) 
- `on_timeout`, which is the only refund mechanism for a `send` that fails to be delivered, looks up the asset via `ContractToAsset::get(dest, &to)` using the request's original `to` (the contract address that was current when `send` was dispatched). If that entry has since been removed or repointed by `update_token`, this lookup fails with `UnknownContractOnTimeout` and the refund is never executed, leaving the escrowed/burned funds permanently stuck in the pallet's custody account (native case) or permanently destroyed (non-native/burn case): [3](#0-2) 
- Symmetrically, `on_accept` authenticates inbound messages via `ContractToAsset::get(source, &from)`. If a legitimate counterpart EVM contract (the "old" one) sends a message after `update_token` has removed its mapping, delivery fails and the user who already locked/burned tokens on the EVM side never receives the corresponding release/mint on the substrate side: [4](#0-3) 

This mirrors the referenced Juicebox `changeTokenOf` finding: a routine, authorized administrative action (token/contract migration) silently orphans state tied to the previous mapping, with no mechanism to convert or redeem funds tied to the old mapping and no delay/dual-mapping to let in-flight operations settle.

### Impact Explanation
Any `send` transaction whose corresponding `TokenContracts`/`ContractToAsset` entry is changed or removed via `update_token` before that request is delivered or times out results in funds that are neither delivered to the beneficiary on the destination chain nor refundable on the source chain. For native assets these funds remain permanently locked in the pallet's escrow account (`Pallet::<T>::pallet_account()`); for non-native assets the tokens were already burned, so the loss is unrecoverable. This is a permanent freezing/loss of user funds, not merely a griefing or DoS condition, and can affect every pending cross-chain transfer at the moment of a legitimate token/contract update.

### Likelihood Explanation
`update_token` is a normal, documented maintenance operation (e.g., migrating to a new/patched EVM contract, or decommissioning support for a chain), so it will be exercised in the ordinary lifecycle of the pallet, not merely in adversarial scenarios. Given cross-chain message delivery/timeout windows are non-trivial (relayer-dependent, timeout-based), there is a realistic window during which in-flight `send` requests exist when such an update occurs, making this reachable without any malicious behavior — simply an ordinary administrative migration executed while transfers are in flight.

### Recommendation
- Preserve the old `(chain, contract) -> asset` mapping in `ContractToAsset` for a grace period after `update_token`, or maintain multiple valid contract mappings per `(chain, asset)` so that in-flight `on_accept`/`on_timeout` messages referencing older contracts can still resolve correctly.
- Alternatively, disallow `update_token` from mutating a chain's mapping while any outstanding (undelivered/untimed-out) requests reference the old contract for that chain/asset, or provide an explicit migration extrinsic that lets users convert/redeem balances tied to the old mapping before it is removed.

### Proof of Concept
1. Governance registers asset `X` with `TokenContracts[Evm(1), X] = OldContract` via `register_token`.
2. Alice calls `send` for asset `X` to `Evm(1)`; her tokens are burned/escrowed and a `DispatchPost` with `to = OldContract` commitment is created: `modules/pallets/hyper-fungible-token/src/lib.rs` lines 251-315.
3. Before the request is delivered or times out, governance calls `update_token` with `add_chains = { Evm(1): NewContract }` (a legitimate contract migration). This removes `ContractToAsset[Evm(1), OldContract]` and inserts `ContractToAsset[Evm(1), NewContract]`: `modules/pallets/hyper-fungible-token/src/lib.rs` lines 407-419.
4. If Alice's request later times out, `on_timeout` calls `ContractToAsset::get(Evm(1), OldContract)`, which now returns `None`, causing `HftError::UnknownContractOnTimeout` and no refund: `modules/pallets/hyper-fungible-token/src/module.rs` lines 236-247. Alice's burned/escrowed tokens are permanently lost/stuck.

					sender_bytes.copy_from_slice(from_bytes);
