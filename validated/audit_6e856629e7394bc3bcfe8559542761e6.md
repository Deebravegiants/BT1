### Title
Solver funds theft via spot-price manipulation of a thin Uniswap V4 pool used as Simplex's venue price oracle - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
Simplex's `FXFiller` strategy can price "exotic" (non-stable) token legs directly off a live Uniswap V4 pool's spot price (`sqrtPriceX96`/tick) instead of a static curve, and uses that spot price both to size the fill amount and to value the solver's cost basis. Like the Mango Markets exploit — where an attacker cheaply spiked the price of a thin, low-liquidity market (MNGO-PERP) to inflate the value of collateral and drain lending pools — an attacker who can move a thin V4 pool's spot price can force a Simplex solver to pay out real stablecoins (USDC/USDT) against an inflated valuation of the exotic token, extracting funds from the solver's vault in a single atomic sequence (manipulate pool → place/fill intent order at inflated rate → restore pool).

### Finding Description
`resolveLegRates` in `sdk/packages/simplex/src/strategies/fx.ts` (lines 1436-1480) prices a curveless, USD-stable/exotic pair leg from the live venue quote: [1](#0-0) 

`getVenueUsdPrice` / `UniswapV4FundingPlanner.getExoticTokenPrice` reads the pool's current spot price directly from `sqrtPriceX96` via `computeDirectPoolPriceUsd`: [2](#0-1) 

As the project's own internal flow doc states, this is a **raw pool mid** with no size/impact term and no TWAP: [3](#0-2) 

The only defense is an **optional** `checkPriceGuard`, which merely bounds the quote to `maxDeviationBps` of a static, manually-configured `referencePrice`: [4](#0-3) 

Per the docs, this guard "must be set together" but is entirely optional — a pair can be venue-priced with **no guard at all**: [5](#0-4) 

Even when configured, the guard only rejects quotes that deviate from a stale static reference by more than a fixed bps band — it does not account for real swap/impact cost, and does not prevent an attacker from moving the price anywhere within that (possibly wide) band, which is enough to be profitable against a large or important fill. This mirrors the Mango root cause exactly: a price used to size/value a payout is read directly from a low-liquidity spot market that a single well-funded actor can move, with only a coarse, static bound (if any) as protection.

### Impact Explanation
An attacker who identifies a Simplex-configured chain/pair that either (a) has no `referencePrice`/`maxDeviationBps` guard configured, or (b) has a wide/stale guard band, can:
1. Swap into the thin V4 pool backing the exotic token to spike its spot price.
2. Immediately place (or have pre-placed) an IntentGateway order that this Simplex solver evaluates and fills using `resolveLegRates`/`referenceRate`, which price and size the fill off the manipulated spot price.
3. Receive an output amount valued at the inflated price, draining real stablecoin/exotic-token inventory from the solver's vault, while the attacker's manipulation cost is only the temporary price impact plus fees on the thin pool (potentially reversible after the fill, similar to Mango's post-attack unwind).

This is a direct, unprivileged loss of solver funds — the same bug class (thin-market spot-price manipulation feeding a payout/collateral calculation) as the $115M Mango Markets exploit, scoped here to whatever capital a Simplex operator has provisioned for that pair/vault.

### Likelihood Explanation
Likelihood is Medium-High for any deployment that configures Uniswap V4 pool-based pricing on a genuinely thin/exotic pair (the docs explicitly target "exotic" low-liquidity tokens like cNGN) without the optional price guard, or with a loosely-set guard. The guard's opt-in nature and the explicit acknowledgment in the codebase's own documentation ("leaves the solver exposed to a manipulated, stale, or thin pool") show the team is aware pool-based pricing is inherently manipulable; the mitigation is a manual, static reference band rather than a manipulation-resistant price source (e.g., TWAP, multiple independent venues, or a max fill size tied to real pool depth).

### Recommendation
- Make the price guard mandatory whenever a pair is configured for pool-based (venue) pricing rather than optional.
- Replace or supplement the raw spot price (`sqrtPriceX96`) read with a time-weighted average price (TWAP) over a manipulation-resistant window, or require corroboration from a second independent venue/oracle before sizing a fill.
- Bound the guard's effective deviation window relative to fill size / pool depth (impact-aware), not just a static bps band against a manually maintained reference price.
- Consider capping `maxOrderSize` for venue-priced pairs based on live pool depth rather than a fixed static config value, so a manipulated price cannot be used to justify an outsized payout.

### Proof of Concept
Conceptual sequence (no on-chain PoC executed, derived from code paths cited above):
1. Attacker identifies a Simplex deployment with `[vault.uniswapV4]` positions configured for pair `USDC/EXOTIC` with either no `referencePrice`/`maxDeviationBps`, or a wide band (per `sdk/packages/simplex/src/config/filler-toml.ts` validation, which allows omitting the guard entirely).
2. Attacker swaps a modest amount into the thin `EXOTIC/USDC` V4 pool, moving `sqrtPriceX96` so `computeDirectPoolPriceUsd` reports an inflated USD price for `EXOTIC`.
3. Attacker (or an accomplice) places an IntentGateway order requesting `EXOTIC` output for `USDC` input, sized so that `FXFiller.calculateProfitability` → `resolveLegRates`/`referenceRate` prices the fill using the manipulated pool quote (passing `checkPriceGuard` because it is absent or too wide).
4. Simplex solver fills the order at the inflated rate, transferring real `EXOTIC`/`USDC` value out of its vault based on the manipulated spot price — analogous to Mango's attacker draining lending-pool liquidity against an inflated MNGO collateral value.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
