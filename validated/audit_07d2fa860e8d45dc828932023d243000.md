## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on validly-signed webhook deliveries - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature only to the raw request body via `to_signable_string`, which returns `@raw_body` [1](#0-0) . The `shop` value used by `Webhooks::Registry.process` to attribute the webhook to a tenant is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is completely outside the signed payload [2](#0-1) . `Registry.process` validates the HMAC and then forwards `request.shop` straight into the `WebhookMetadata` passed to the app's handler [3](#0-2) , without ever checking that the header-derived shop matches anything cryptographically bound to the signed body.

### Finding Description
The identity binding that should hold is:

`shop_used_for_tenant_attribution == shop_that_the_HMAC_signature_actually_authenticates`

For OAuth callbacks this binding is correctly enforced: `AuthQuery#to_signable_string` includes `shop` in the signed parameter set [4](#0-3) , so `HmacValidator.validate` cryptographically ties the `shop` value to the signature [5](#0-4) .

For webhooks, this binding is broken. `HmacValidator.validate` calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` is exactly `@raw_body` [1](#0-0) , i.e. the signature authenticates the body bytes only. The `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers [6](#0-5)  and are never fed into `to_signable_string`, so none of them are covered by the HMAC.

`Registry.process` validates only the body-bound HMAC (`Utils::HmacValidator.validate(request)`), then immediately trusts `request.shop` from the header to build `WebhookMetadata` for the app-level handler [3](#0-2) . Because two independent Shopify shops (e.g. a shop the app is installed on, and any other shop that shares the same webhook subscription/body shape, such as a `shop/redact` or generic customer/order webhook with identical JSON payload) can produce byte-identical bodies, a genuinely-signed webhook delivery's headers can be re-sent with the `shop-domain` header swapped to a different tenant while the HMAC over the (unchanged) body remains valid. `HmacValidator.validate` still returns `true` because it never inspects headers, and the mismatched shop is handed to the handler as though it were authenticated.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to provide to host applications: the one signal the library gives call sites to trust ("`Utils::HmacValidator.validate(request)` passed, so this shop's webhook is authentic") does not actually bind `request.shop`. Any host app that keys per-tenant side effects (data stores, redaction, deduplication, order/customer processing) off `WebhookMetadata#shop` as returned by this gem can be made to act on/for the wrong shop using a replayed, still-validly-signed payload with a substituted `shop-domain` header — a cross-tenant confusion condition, consistent with the High/Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires an unprivileged actor to be able to intercept or replay a legitimately delivered webhook body (e.g., via a network position that lets them resend HTTP requests with modified headers, or via any environment where webhook bodies/headers are logged and replayable) — they never need `api_secret_key`. Because HMAC coverage is a documented design property of this gem's `VerifiableQuery`/`HmacValidator` mechanism, and here it silently degrades to "body-only" for webhooks while `shop` is presented by `Registry.process` as if validated, this is a real gap in the gem's own logic rather than a host-app misuse issue.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them, e.g. via a canonical signed string similar to `AuthQuery#to_signable_string`) into `Webhooks::Request#to_signable_string`, or otherwise have `HmacValidator`/`Registry.process` verify these header values against a signed representation before exposing them through `WebhookMetadata`, matching the pattern already used correctly for `Auth::Oauth::AuthQuery`.

### Proof of Concept
1. Capture a legitimately delivered webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(secret, B)` as computed in `compute_signature` [7](#0-6) .
2. Resend the same body `B` and the same `H` to the app's webhook endpoint, but with `x-shopify-shop-domain` changed to `shop-b.myshopify.com`.
3. `Webhooks::Request.new` accepts it (all three required headers present) [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature only from `@raw_body` and matches `H` — validation succeeds [9](#0-8) .
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the signature never authenticated that shop value [10](#0-9) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
