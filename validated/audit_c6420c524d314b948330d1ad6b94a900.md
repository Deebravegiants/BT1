### Title
Receipt size validation is checked before `output_data_receivers`/return values are attached, letting oversized receipts bypass `max_receipt_size` - ([File: runtime/runtime/src/verifier.rs])

### Summary
The reported CVE describes `pallet-ethereum` including transactions without validating input data size, so oversized/invalid data ends up recorded in chain state even though it has no further effect. Nearcore has a directly analogous, already-acknowledged defect in its receipt-size enforcement: `validate_receipt` is only invoked in `ValidateReceiptMode::NewReceipt` mode at receipt-creation time, before later processing (attaching `output_data_receivers`, or resolving a `ReturnData::Value`) can grow the receipt beyond `max_receipt_size`. The result is that an unprivileged account can, via ordinary `FunctionCall` actions, cause the runtime to record and propagate receipts whose serialized size exceeds the configured `max_receipt_size` hard limit.

### Finding Description
`validate_receipt` enforces the size cap only for `NewReceipt` mode: [1](#0-0) 

A second, explicitly weaker mode, `ExistingReceipt`, exists specifically to tolerate this known gap: [2](#0-1) 

The size check happens when the receipt is first constructed by contract execution, but subsequent runtime logic (attaching `output_data_receivers` for a receipt whose result will be delivered as callback data, or writing a large `ReturnData::Value`) can enlarge the already-validated receipt past `max_receipt_size` without re-validating it. This is corroborated by two other locations in the runtime that explicitly work around the same defect rather than fixing it:

- `try_forward` in congestion control clamps an oversized receipt's size down to `max_receipt_size` purely to keep bandwidth accounting from getting stuck, with an explicit comment citing the bug: [3](#0-2) 

- `generate_bandwidth_request` does the same clamping for bandwidth-scheduler requests: [4](#0-3) 

The nearcore test suite explicitly reproduces and documents the bug (referencing `https://github.com/near/nearcore/issues/12606`) rather than treating it as fixed: [5](#0-4) [6](#0-5) 

Both `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` build a receipt that is exactly at `max_receipt_size` (which passes the `NewReceipt` validation), then mutate/grow it (adding `output_data_receivers`, or returning a value as large as `max_receipt_size` which gets wrapped into a `DataReceipt`), and assert (via `assert_oversized_receipt_occurred`) that an oversized receipt is actually observed on-chain afterward: [7](#0-6) [8](#0-7) [9](#0-8) 

This directly parallels the `pallet-ethereum` CVE class (CWE: Improper Validation of Specified Quantity in Input): the size gate exists, but it is checked at the wrong point in the pipeline, so data that should have been rejected for exceeding a hard size limit is nonetheless admitted into chain state (incoming receipts / receipt proofs on subsequent blocks).

### Impact Explanation
`max_receipt_size` (4 MiB, see `LimitConfig`/`RuntimeConfig`) exists specifically to bound the size of `ChunkStateWitness` and keep per-receipt storage-proof/processing costs predictable (see `docs/misc/state_witness_size_limits.md`). An unprivileged account can, through ordinary contract calls (no special permissions), force receipts larger than this bound onto chains, which:
- undermines the state-witness size guarantees the whole limit system was designed to provide,
- causes downstream code (congestion control / bandwidth scheduler) to have to special-case and silently clamp the oversized value rather than reject it, which is itself an indication that assumptions elsewhere in the runtime (`main_storage_proof_size_soft_limit`, bandwidth grants, outgoing size limits) can be violated by attacker-controlled receipts,
- does not directly cause fund theft or unauthorized balance transfer, matching the "no observable effect on internal state beyond the record itself" characterization used for the low/medium `pallet-ethereum` advisory, but does constitute unbounded resource use / a violated hard input-size invariant reachable from a normal transaction.

Given that the maintainers have already opened and are tracking issue #12606 for this exact behavior, this is a real, currently-open defect in the shipped code, not a hypothetical.

### Likelihood Explanation
High reachability: no validator, node-operator, or protocol-level privilege is required. Any account can deploy a WASM contract (as done in `runtime/near-test-contracts/test-contract-rs`) that returns a large value or creates a promise whose result is directed to `output_data_receivers`, both of which are ordinary supported contract patterns. The existing regression tests demonstrate the exploit path end-to-end using only standard `SignedTransaction::call` and `SignedTransaction::deploy_contract` calls from a funded test account.

### Recommendation
- Re-run `validate_receipt` (or an equivalent size check) after all fields of a receipt are finalized - specifically after `output_data_receivers` is populated and after `ReturnData::Value`/promise-return processing - rather than only immediately after the receipt is initially constructed.
- Alternatively, restructure the receipt-construction pipeline so that `output_data_receivers` and return-value wrapping happen before the `NewReceipt` size check runs, guaranteeing the check observes the final, fully-populated receipt.
- Once fixed, tighten `ValidateReceiptMode::ExistingReceipt` back to the same strictness as `NewReceipt` (currently intentionally weakened to tolerate this bug) and remove the compensating clamps in `try_forward` and `generate_bandwidth_request`, since those workarounds mask the root cause rather than enforce the invariant.
- Resolve this in coordination with the already-tracked `near/nearcore` issue #12606.

### Proof of Concept
The existing repository tests are a working PoC for this defect:
1. `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs:130-208`): deploys the standard test contract, computes `args_size` so a generated receipt is exactly `max_receipt_size`, and calls `max_receipt_size_promise_return_method1`. The contract's promise chain later attaches `output_data_receivers` to that already-validated receipt, growing it past the limit. `assert_oversized_receipt_occurred` confirms an oversized receipt is present on-chain.
2. `test_max_receipt_size_value_return` (`test-loop-tests/src/tests/max_receipt_size.rs:216-267`): calls `max_receipt_size_value_return_method` with `value_size = max_receipt_size`; the returned value is wrapped into a `DataReceipt` that ends up larger than `max_receipt_size`, again confirmed oversized via `assert_oversized_receipt_occurred`.

Both tests are pre-existing in the codebase and their comments explicitly state the receipt "should be rejected, but currently isn't because of a bug," referencing `https://github.com/near/nearcore/issues/12606`. [5](#0-4) [6](#0-5)

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
