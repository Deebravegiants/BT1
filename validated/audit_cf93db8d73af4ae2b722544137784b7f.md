### Title
CPU exhaustion via unbounded `handle_unsigned` batch/proof processing during transaction-pool `validate_unsigned` - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is declared `#[pallet::weight(weight())]`, where `weight()` returns a fixed constant regardless of how many messages, requests, or proof items the caller submits. This same unbounded execution path (`Self::execute(messages.clone())`) is invoked in full, off-chain, inside `ValidateUnsigned::validate_unsigned`, which every full node runs on every gossiped unsigned transaction *before* any block-inclusion weight limit is ever applied. An attacker can submit a single unsigned transaction containing a very large `Vec<Message>` (each containing large `Vec<PostRequest>`/`Vec<GetResponse>` and large membership/non-membership proofs) that every peer node must fully verify and execute (hashing, MMR/state-proof verification, router dispatch to `on_accept`/`on_response` callbacks) at mempool-validation time, with no weight metering or per-iteration cancellation check, monopolizing node CPU across the network.

### Finding Description
`handle_unsigned` is dispatched with `ensure_none(origin)`, meaning anyone can submit it as an unsigned extrinsic: [1](#0-0) 

Its declared weight is a hardcoded constant, not derived from `messages.len()` or the size of any inner request/proof vectors: [2](#0-1) 

Crucially, `ValidateUnsigned::validate_unsigned` for this call fully executes the batch — `Self::execute(messages.clone())` — as part of transaction-pool validation, which runs on every node that receives the gossiped transaction, independent of and prior to any block-weight accounting: [3](#0-2) 

`execute()` maps `handle_incoming_message` over the entire `Vec<Message>` with no early bail-out or per-message budget: [4](#0-3) 

Inside message handling, `handlers::request::handle` and `handlers::response::handle` iterate the caller-supplied `requests`/`responses` vectors, performing hashing, membership-proof verification, and module callback dispatch for each entry with no cap on batch size: [5](#0-4) [6](#0-5) 

The MMR/merkle multi-proof verification these handlers invoke is itself proportional to the number of leaves and proof items supplied by the caller, which are also unbounded at this layer: [7](#0-6) 

This is structurally the same bug class as the SurrealDB advisory: a nominally cheap, "free" (unsigned, fee-less) entry point whose declared cost bookkeeping (static weight here; the SurrealQL for-loop iteration cap there) does not reflect the actual unbounded work the caller can request, and that work runs to completion with no cancellation/interrupt check — except here the unbounded work runs during P2P mempool validation on every full node in the network, not merely during block execution.

### Impact Explanation
An attacker submits a single unsigned `handle_unsigned` extrinsic with an oversized `messages: Vec<Message>` (bounded only by the node's configured max extrinsic/transaction-pool byte size, not by declared weight). Every full node that receives this transaction via gossip runs `validate_unsigned`, which fully executes the batch — hashing every request, verifying every membership/non-membership proof, and invoking router callbacks — before the transaction is ever included in a block (and it need not ever be includable; it can even be relayed with invalid signer/be otherwise doomed to fail final application, since the CPU cost is already paid by every validating node). Because this happens outside block-weight accounting, there is no `CheckWeight`-style ceiling stopping the attacker from constructing arbitrarily expensive batches within the extrinsic size limit, and because it happens on every peer independently, the effect compounds across the whole validator/full-node set — a network-wide CPU-exhaustion condition that can stall block production and honest relayer message delivery, i.e. a route rendered unable to deliver messages. This matches the "resource exhaustion in an unprivileged message dispatcher" class explicitly in scope.

### Likelihood Explanation
`handle_unsigned` is reachable by any unauthenticated party since it uses `ensure_none` origin and requires no fee or prior registration — it is Hyperbridge's normal, permissionless relayer message-delivery path, described in the docs as executing "for free" for anyone with valid-looking proofs. Constructing a large batch of syntactically valid `Message`/`PostRequest`/proof structures (they need not ultimately verify) that is expensive to hash/verify does not require any privileged access, consensus client control, or economic stake — only knowledge of the SCALE-encodable message formats. Both `handlers::request::handle` and `handlers::response::handle` are additionally invoked from `validate_unsigned` before duplicate/timeout screening completes.

### Recommendation
- Scale the declared weight of `handle_unsigned` with the actual size of `messages` (number of messages, number of inner requests/responses, and proof length) so `CheckWeight` can reject oversized batches pre-dispatch, analogous to how `pallet-call-decompressor` gates `encoded_call_size` before doing any expensive work.
- Cap the number of requests/responses/proof items permitted per `handle_unsigned` call (e.g., a `MaxMessagesPerBatch`/`MaxRequestsPerBatch` bound enforced in `validate_unsigned` itself, before `Self::execute` runs), so mempool-validation cost is bounded independent of block inclusion.
- Consider computing a cheap upper-bound cost estimate (e.g., total encoded length or item count) and rejecting the transaction in `validate_unsigned` before invoking `execute`, mirroring the `CallSizeOutOfBound` early-exit pattern already used in `pallet-call-decompressor`.

### Proof of Concept
1. Construct an unsigned `Call::handle_unsigned { messages }` where `messages` is a single `Message::Request(RequestMessage { requests, proof, .. })` (or `Message::Response`) with `requests` populated with tens of thousands of syntactically valid `PostRequest`/`GetResponse` entries and a correspondingly large but not-necessarily-valid multiproof, sized just under the node's max-extrinsic-size limit.
2. Submit this as an unsigned transaction to a Hyperbridge parachain RPC node.
3. Observe that every peer node receiving the gossiped transaction invokes `ValidateUnsigned::validate_unsigned` → `Pallet::execute` → `handlers::request::handle`/`response::handle`, which hashes and attempts proof verification over every entry in `requests`, consuming CPU proportional to the attacker-chosen batch size — while the extrinsic's declared weight (`Weight::from_parts(300_000_000, 0)`, a fixed ~0.3ms-equivalent) is completely disconnected from that cost and provides no protection at the mempool-validation stage.
4. Repeating/parallelizing submissions from multiple peers amplifies the effect network-wide before any transaction is included in a block.
