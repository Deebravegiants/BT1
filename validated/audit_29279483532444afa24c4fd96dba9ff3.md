### Title
Missing allowlist/rate-limit authorization on legacy WebAPI gateway trigger requests - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `FootiumAcademy#mintPlayers()` report is about a state-changing function that is reachable by any caller because a required authorization check (`onlyOwner`) was never implemented, despite the code's own NatSpec documenting that only the owner should be permitted. The closest unprivileged-actor analog in the chainlink internet-facing gateway path is `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, which processes `web_api_trigger` requests coming from external, unauthenticated gateway clients and forwards them to every DON node — with an explicit `// TODO: apply allowlist and rate-limiting here` marking the exact place where an authorization/allowlist check is supposed to exist but does not.

### Finding Description
`HandleLegacyUserMessage` [1](#0-0)  parses the incoming gateway message payload, validates its timestamp for staleness, and then reaches this comment and check: [2](#0-1) 

Immediately after the `// TODO: apply allowlist and rate-limiting here` comment, the method only validates that `msg.Body.Method == MethodWebAPITrigger` — there is no check of the message sender against any per-workflow allowlist, no authentication of the caller's identity, and no rate limiting applied to this specific entry point. The request is then converted and broadcast to every member of the DON: [3](#0-2) 

This mirrors the FootiumAcademy pattern precisely: the code comment (like the Solidity NatSpec `@dev Only the owner can mint players to their club.`) documents the intended access-control requirement, but the actual enforcement was never added before the privileged action (forwarding a trigger request to the entire DON, which will execute node-side outgoing HTTP/webapi actions) is performed.

Corroborating evidence that this gap is a known, unresolved issue (not a design decision) comes from a companion test file for a related handler in the same package family, which explicitly notes the same missing control: [4](#0-3) 

By contrast, other handlers in the same gateway subsystem (e.g., the Vault gateway handler) enforce authorization before processing any privileged request via a dedicated `Authorizer`/allowlist pipeline (`AuthorizeRequest`, `allowListBasedAuth`) [5](#0-4) [6](#0-5) , and the webapi trigger capability (a related, but distinct, code path) does check sender authorization via `unauthorized Sender` errors [7](#0-6) . This confirms that allowlist-based sender authorization is the expected pattern for gateway-facing entry points, and its absence in `HandleLegacyUserMessage` for `MethodWebAPITrigger` is a genuine gap rather than an intentional simplification, exactly as the TODO comment states.

### Impact Explanation
Because `HandleLegacyUserMessage` is the entry point invoked for user-submitted legacy gateway messages routed to the `capabilities` handler (registered for `MethodWebAPITrigger`, `MethodWebAPITarget`, `MethodComputeAction`, `MethodWorkflowSyncer` via `Methods()` [8](#0-7) ), any external, unauthenticated party able to reach the gateway's HTTP/WS-facing message-handling surface can submit a well-formed `web_api_trigger` message and have it broadcast to every DON node member without being checked against an allowlist of authorized senders/workflows, and without a rate limit specific to this trigger path. This is analogous to "unexpected situation that anyone can call ... and mint players freely" — here, anyone can cause the DON to process/trigger webapi trigger requests that were meant to be restricted, potentially enabling unauthorized job/workflow triggering and resource exhaustion of the DON via unthrottled message flooding.

### Likelihood Explanation
High, in the sense that no additional privilege, secret, or session is required to reach the vulnerable code path beyond forming a syntactically valid, non-stale `web_api_trigger` message — the check that's missing is exactly the one the TODO comment says should exist. The only mitigating factors are whatever authentication/allowlisting is enforced at earlier layers of the gateway connection (e.g., DON handshake/connection-level authorization), which were not fully verifiable within the scope of this investigation; I could not confirm from the index alone whether an outer layer (e.g., `gateway.go`, `connectionmanager.go`) already restricts which senders can reach `HandleLegacyUserMessage` for this handler, which affects whether this gap is fully exploitable by a fully unprivileged client or only by an already-connected-but-untrusted sender.

### Recommendation
Implement the allowlist and rate-limiting check explicitly called out by the TODO in `HandleLegacyUserMessage`, before forwarding the request to DON members: verify `msg.Body.Sender` (or equivalent workflow/owner identity extracted from the payload) against a maintained allowlist (mirroring the pattern already used in `core/capabilities/vault/allow_list_based_auth.go`), and apply a rate limiter scoped to the sender/workflow for `MethodWebAPITrigger`, rejecting and responding with an authorization error for any sender not present in the allowlist, consistent with how `webapi/trigger` already returns `"unauthorized Sender ..."` errors for its own dispatch path.

### Proof of Concept
Not independently executable from static review alone; the code-level proof is the literal absence of any sender/allowlist check between message parsing/staleness validation and the `don.SendToNode` broadcast loop in `HandleLegacyUserMessage` [9](#0-8) , combined with the explicit `// TODO: apply allowlist and rate-limiting here` acknowledging the missing control, and the test-file comment confirming senders/rate limits are "pending" and unvalidated for this handler [10](#0-9) .

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}

// AuthorizeRequest authorizes a request using AllowListBasedAuth.
// It does NOT check if the request method is allowed.
func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}
