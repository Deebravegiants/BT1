### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are excluded from the HMAC computation. `Utils::HmacValidator.validate` only proves that the body bytes match the signature; it says nothing about the `shop-domain` header that `Registry.process` later trusts and forwards to the app's webhook handler as the tenant identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 
Only `@raw_body` is signed. `shop`, `topic`, `webhook_id`, `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC/body pair and then unconditionally trusts `request.shop` as the tenant identity forwarded to the handler: [3](#0-2) 

This reproduces the report's bug class ("a field acted on but not covered by the HMAC") almost exactly: the report's fix set aside collateral tied to the *position that was actually opened*; the analog here is that the *shop the payload is attributed to* is not tied to the bytes that were actually authenticated. The equality that should hold is:
`shop_bound_by_signature == shop_used_for_tenant_attribution`
but in this code the left side doesn't exist — only `body_bound_by_signature == shop_header_used_for_tenant_attribution` is false in general, since the header is outside the signed string.

Because Shopify signs webhooks with the app's single shared `client_secret` (`Context.api_secret_key`) across every shop that has the app installed, any merchant who has installed the app (an unprivileged internet user with respect to other tenants of the same app) can capture a legitimate `(raw_body, hmac)` pair delivered to their own endpoint, then replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` will hand the attacker-supplied body to the handler tagged as coming from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an app that keys any per-shop side effects (feature flags, cached settings, inventory sync, order/customer records, uninstall/reinstall handling, etc.) off `WebhookMetadata#shop` can have that state corrupted or overwritten using attacker-controlled body content while attributed to a shop the attacker doesn't own — cross-tenant data confusion using only the requester's own legitimate webhook credentials/subscription. This fits the "cross-tenant access" Critical-impact category defined in scope.

### Likelihood Explanation
Requires only: (1) installing the app on an attacker-controlled shop (an ordinary merchant action, not privileged), (2) triggering any webhook topic to capture a valid `(body, hmac)` pair, and (3) sending that pair to the app's public webhook endpoint with a forged `shop-domain` (and optionally `topic`/`webhook-id`/`api-version`) header. No access token, `client_secret`, or leaked credential is needed — the attacker only needs their own valid webhook delivery, which Shopify sends them automatically. The webhook endpoint is, by design, a public unauthenticated HTTP endpoint reachable by anyone who can guess/derive its URL, which is documented and standard for Shopify apps.

### Recommendation
Bind the shop (and topic/webhook id) into the signed material, or otherwise cryptographically tie the header values to the verified payload, e.g.:
- Extend `to_signable_string` to include `shop`, `topic`, and `webhook_id` in addition to the raw body, and update the validator/documentation accordingly (this is a breaking change to the signing scheme, so it may instead need to be enforced at the `Registry.process` layer).
- At minimum, document and/or enforce in `Registry.process` that the `shop` extracted from headers must match a shop known to be currently installed/authorized for the app (i.e., cross-check against the app's own session/shop store) before invoking the handler, rather than trusting the header as-is once the body HMAC passes.

### Proof of Concept
1. Install the app on `attacker.myshopify.com` (attacker's own shop) and let Shopify deliver a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint. Capture the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `HMAC-SHA256(client_secret, B) == H`).
2. Replay the captured request to the same public webhook endpoint, keeping `B` and `H` unchanged, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares it to `H` via `Request#to_signable_string` (body only) — validation passes: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)`, so any per-shop side effects the app performs are executed against `victim-shop.myshopify.com` using attacker-supplied body content, despite the attacker never having installed the app on, or obtained any credential for, that shop.
