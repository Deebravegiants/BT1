### Title
Unauthenticated Runtime-Call Origin Derivation in `pallet-hyper-fungible-token`'s Cross-Chain Calldata Execution - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler lets an incoming cross-chain token transfer carry an optional `data` payload (`SubstrateCalldata`) that is dispatched as an arbitrary `T::RuntimeCall` on the destination chain. When the payload has **no signature**, the dispatch `origin` is derived directly from the unauthenticated `message.from` field taken from the ABI-decoded message body, rather than from any cryptographically-verified identity, and the call is executed as `RawOrigin::Signed(origin)`.

### Finding Description
In `on_accept`, after crediting `beneficiary` with bridged tokens, the module optionally executes calldata: [1](#0-0) 

If `substrate_data.signature` is `None`, the code silently derives the dispatch origin from `message.from` (an EVM address or 32-byte account embedded in the attacker/caller-controlled ABI message body) with no signature verification at all: [2](#0-1) 

That derived `origin` is then used to dispatch a fully attacker-supplied `T::RuntimeCall`, gated only by the runtime's generic `BaseCallFilter` (which is a blanket allow/deny list, not an authorization check tied to the specific caller or call): [3](#0-2) 

The only authentication performed on the whole `PostRequest` is that the *source contract address* (`from` field of the ISMP `PostRequest`, i.e., the registered `HyperFungibleToken`/`WrappedHyperFungibleToken` contract) is a known bridge contract for that chain, via `ContractToAsset`: [4](#0-3) 

This check only proves the message came from *a* legitimate bridge deployment — it says nothing about who supplied the inner `message.from` bytes, which is application-layer data set when the source-chain call to `send()`/bridge transfer was made. The pallet's documentation itself confirms this design: "If no signature is provided, the origin is derived from the sender address in the cross-chain message," treating the presence of a signature as optional rather than mandatory for privileged dispatch: [5](#0-4) 

This is the same bug class as the reference Kibana Fleet CVE: a configuration/identity field embedded in a message that is not adequately validated is used downstream to grant elevated capability (there: elevated Elasticsearch API-key privileges; here: dispatch rights as an arbitrary account) — an "improper input validation leading to privilege escalation."

Because the unsigned path exists specifically to let a bridge transfer's *sender* on the source chain (i.e., whoever pays/initiates the transfer) act as themselves on the destination chain without a second signature, the security of the whole mechanism depends entirely on the EVM/Substrate source-side contract strictly binding `message.from` to the actual transaction signer for that specific transfer, with no way for a third party (e.g., an ERC-20 `approve`/`transferFrom`-style relayer, or any code path that lets one account move another's tokens) to set `from` to someone else's address. I could not fully verify from the indexed contents of `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` whether `from` is strictly hardcoded to `msg.sender` in every code path (including any allowance-based or relayed send flow); the pallet-side code provides no independent verification of this invariant and simply trusts the embedded `from` bytes.

### Impact Explanation
If any code path on the source chain (EVM `HyperFungibleToken`/`WrappedHyperFungibleToken`, or another integrating chain) allows the `Message.from` field to diverge from the actual transaction signer — e.g. an approved spender bridging tokens "on behalf of" a token owner, a misconfigured relayer, or any future contract update — an attacker can cause an arbitrary `RuntimeCall` to be dispatched as `RawOrigin::Signed(<victim account>)` on the destination chain. Since `BaseCallFilter` is a coarse global filter and not a per-account authorization mechanism, this can reach any allowed extrinsic (governance voting, staking, asset transfers of unrelated balances, proxy/identity operations, etc.), constituting privilege escalation and unauthorized app action against victim accounts without their consent.

### Likelihood Explanation
The vulnerable code path is reachable by any account that can dispatch a cross-chain token send with non-empty `call_data` and omit the signature field — this requires no elevated privilege, only the ability to initiate a bridge transfer, matching the "unprivileged... token bridger" reachability bar. The likelihood of full exploitation depends on whether the paired EVM/Substrate sending contracts ever allow `from` to be set independently of the actual signer (e.g., via approvals or relaying); this could not be conclusively confirmed from the available EVM contract source in this pass, so the finding should be validated against `HyperFungibleToken.sol`'s exact `send`/bridge-initiation logic during triage.

### Recommendation
- Require a valid signature (`SubstrateCalldata.signature`) for every calldata execution, removing the unsigned/`message.from`-derived origin branch entirely, or
- If the unsigned convenience path must remain, cryptographically bind `message.from` to the actual source-chain transaction signer at the protocol level (e.g., only allow it when the bridge transfer itself was authenticated as being initiated directly by that same address, with no allowance/relay indirection), and add an explicit runtime check/documentation invariant enforcing this on both EVM and Substrate sender implementations.
- Consider scoping the unsigned dispatch to a restricted allow-list of calls (rather than relying solely on `BaseCallFilter`) to limit blast radius even if origin derivation is later found to be spoofable.

### Proof of Concept
1. Attacker locates (or waits for) a source-chain flow where `Message.from` can be set to an address other than the actual initiator of the bridge transaction — e.g., an approval-based "send on behalf of" flow, or a contract that lets a caller supply `from` as calldata.
2. Attacker bridges a minimal amount of tokens to `pallet-hyper-fungible-token`, setting `Message.from = <victim address>` and `Message.data` to a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary victim-authorized call, e.g. Balances::transfer_allow_death to attacker> }`.
3. On `on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:176-202`), since no signature is present, the pallet derives `origin` purely from `message.from`, converts it to the victim's substrate account via `EvmToSubstrate`, and dispatches the attacker-chosen `runtime_call` as `RawOrigin::Signed(victim)` — executing a privileged action as the victim without their authorization, bounded only by the runtime's `BaseCallFilter`.

## Calldata Execution

The `call_data` field in `SendParams` allows executing arbitrary runtime calls on the destination substrate chain after the tokens are transferred. The calldata is SCALE-encoded as:

```rust lineNumbers
pub struct SubstrateCalldata {
    /// Optional SCALE-encoded MultiSignature of (account_nonce, runtime_call)
    pub signature: Option<Vec<u8>>,
    /// SCALE-encoded runtime call to execute
    pub runtime_call: Vec<u8>,
}
```

If a signature is provided, it is verified against the beneficiary's account nonce and the runtime call before dispatch. Supported signature types: Ed25519, Sr25519, ECDSA. The account nonce is incremented after dispatch to prevent replay.

If no signature is provided, the origin is derived from the sender address in the cross-chain message.
```
