### Title
Unvested yield can be permanently diverted/frozen when a `StreamingYieldVault`'s share supply drops to zero mid-tranche - ([File: sdk/packages/core/contracts/vaults/StreamingYieldVault.sol])

### Summary
`StreamingYieldVault` streams owner-supplied yield linearly over a fixed `VEST` window and masks the not-yet-vested portion out of `totalAssets()` via `_lockedYield()`. This mirrors the reported `Reward.sol` bug class: value is escrowed against a pool of depositors/shareholders that is assumed to be non-empty, but there is no accounting for the case where that pool empties out entirely while value is still pending recognition. If every shareholder redeems while a tranche is vesting (`totalSupply()` reaches `0`), the still-locked portion of the tranche is left in the contract balance but is not backing any share. It is orphaned from the ERC-4626 exchange-rate mechanism until the next depositor arrives.

### Finding Description
- `totalAssets()` deliberately excludes `_lockedYield()`, the not-yet-recognized part of the current tranche [1](#0-0) .
- `_lockedYield()` computes the remaining locked amount purely as a function of `block.timestamp`, `_vestingStart`, and `_vestingAmount` — it has no dependency on `totalSupply()` at all [2](#0-1) .
- Withdrawals/redemptions (inherited from OpenZeppelin `ERC4626`) are always available, even mid-vest — the contract only gates `maxDeposit`/`maxMint` to zero during vesting, never gates exits [3](#0-2) .
- Because a redeeming holder receives assets proportional to `totalAssets()` (which already nets out locked yield), a holder who fully exits mid-vest takes only their share of the *unlocked* assets. If they were the last/only holder, `totalSupply()` becomes `0` while the contract still physically holds the locked (unvested) balance of the tranche — this balance is now orphaned: it backs no shares, and it is masked out of `totalAssets()` until `elapsed >= VEST`.
- New deposits are blocked while `_isVesting()` is true (`maxDeposit` returns `0`), so nobody can enter and claim/absorb this orphaned balance until the tranche fully vests [4](#0-3) .
- Once the tranche fully vests, `totalAssets()` becomes the *entire* leftover balance (now unmasked), while `totalSupply()` is still `0`. ERC4626's virtual-share formula (`_decimalsOffset()` = 6) then mints shares to the *next* depositor against `totalSupply() + 10**offset` vs `totalAssets() + 1`; since that depositor is the sole shareholder the instant they deposit, they end up owning 100% of the pool's assets, including all of the previously orphaned/leftover yield that was meant to accrue to the shareholders who were present when the tranche started. If no one ever deposits again, the leftover yield sits in the contract permanently, unclaimable by anyone, because ERC4626 exit functions operate on shares and there are none outstanding to redeem it.

This is structurally analogous to the `Reward.sol` finding: a reward/yield pool is escrowed against a "supply" checkpoint (share supply here, staked-weight there); if that supply is zero for the relevant accounting window, the value is either permanently stranded or captured by an unrelated later party rather than by the intended participants, and there is no mechanism in either contract to redistribute/reclaim it.

### Impact Explanation
**High.** Depending on subsequent activity, the not-yet-vested tranche remainder is either:
1. Permanently frozen in the contract (unclaimable — no shares outstanding, and no owner-only rescue path exists for locked yield), or
2. Fully captured by whichever address happens to make the next deposit after `totalSupply()` returns to a nonzero state, at the expense of the depositors who were present when the yield tranche was funded and who should have accrued it.

Both outcomes represent a genuine loss of funds to the intended beneficiaries — either destroyed value or value misdirected to an unrelated party — with no code path in the contract to detect or correct it.

### Likelihood Explanation
**Low/Medium.** This requires a full share-supply drain (`totalSupply() == 0`) while a yield tranche is actively vesting. `StreamingYieldVault` is designed/documented (per `docs/content/developers/evm/streaming-yield-vault.mdx`) for use as a Simplex solver treasury vault, typically funded by a small number of LPs. A single dominant depositor withdrawing everything mid-tranche (a normal, permitted operation since withdrawals are never gated) is a realistic scenario, especially since the vault's own docs recommend seeding-and-burning a tiny initial deposit specifically to avoid "empty vault" edge cases — but that seed/burn only guards against the first-depositor inflation attack on an *empty* vault, not against the supply later returning to zero while a tranche is mid-flight with real locked yield still pending.

### Recommendation
Track whether locked yield is still economically "owned" by a live share supply, and prevent orphaning:
- Snapshot/cancel the remainder of a tranche if `totalSupply()` drops to `0` while vesting is in progress (e.g., roll the still-locked remainder back to the owner, or auto-forfeit it into the next tranche only after being explicitly reclaimed), rather than silently leaving it to be swept up by whoever deposits next.
- Alternatively, disallow full exits that would bring `totalSupply()` to `0` while `_isVesting()` is true, or provide an owner-only `reclaimOrphanedYield()` function (analogous to the suggested `renotifyRewardAmount` in the referenced report) that lets governance recover/redistribute a tranche's unvested remainder once it detects `totalSupply() == 0`, instead of allowing it to be either stranded or windfall-captured by an unrelated future depositor.

### Proof of Concept
Conceptual trace based on the contract logic (not an executed test, since tool access ended before a Foundry run could be performed):
1. Owner deploys `StreamingYieldVault`, seeds it with a small deposit and burns the shares per the documented pattern.
2. Solver LP deposits `1000` assets and mints shares; owner calls `addYield(500)`, starting a 22h vest.
3. Midway through the vest (11h in, `_lockedYield()` ≈ 250 remaining locked), the LP calls `redeem()` for their entire share balance. `totalAssets()` at that point nets out the ~250 locked yield, so the LP receives only their pro-rata share of the ~1250 unlocked assets. After this redemption `totalSupply() == 0` (only the tiny burned seed shares remain permanently at `address(0xdead)`, but assume LP was effectively the sole active holder — or in a vault without a burned seed, `totalSupply()` truly reaches `0`).
4. The vault's balance still holds the ~250 unvested remainder, which is invisible to `totalAssets()` per `_lockedYield()` — line 165-170 [5](#0-4) .
5. No one can deposit until `block.timestamp >= _vestingStart + VEST` (`maxDeposit` returns 0 while `_isVesting()`).
6. After the vest window elapses, `_lockedYield()` returns `0`, so `totalAssets()` jumps to include the full leftover ~250. `totalSupply()` is still `0`.
7. The next depositor (anyone, permissionlessly) calls `deposit()`. Since `totalSupply() == 0`, they become sole shareholder and, on any subsequent `redeem()`, extract the entire pool balance — including the ~250 that was never theirs — while the original LP who funded/earned it has already exited with less than the full yield they were owed.

I could not execute this against the actual Foundry test suite (`sdk/packages/core/test/StreamingYieldVault.t.sol`) within the available tool budget to confirm exact numeric outcomes; the mechanism described is derived directly from the contract's `totalAssets()`/`_lockedYield()`/`maxDeposit()` logic and OpenZeppelin's ERC4626 zero-supply virtual-share deposit formula.

```text
    /// @dev True while the current tranche is still vesting, i.e. deposits are locked. Returns
    ///      false before the first tranche has ever been added (`_vestingStart == 0`).
    function _isVesting() internal view returns (bool) {
        uint256 start = _vestingStart;
        return start != 0 && block.timestamp < start + VEST;
    }

    /// @inheritdoc ERC4626
    /// @dev Zero while a tranche is vesting so deposits are closed (and integrators can detect it);
    ///      unbounded otherwise. This is the single lock that keeps new capital from joining
    ///      mid-tranche: `deposit` reverts at its `maxDeposit` check with `ERC4626ExceededMaxDeposit`.
    function maxDeposit(address) public view override returns (uint256) {
        return _isVesting() ? 0 : type(uint256).max;
    }

    /// @inheritdoc ERC4626
    /// @dev Zero while a tranche is vesting so integrators see mints are closed; unbounded otherwise.
    function maxMint(address) public view override returns (uint256) {
        return _isVesting() ? 0 : type(uint256).max;
    }
```

```text
    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }
```
