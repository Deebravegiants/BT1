### Title
Webhook tenant identity (`shop-domain`/`topic` headers) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC validation, while the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers — which are used to route and attribute the webhook to a tenant — are never part of the signed bytes. This breaks the intended identity binding `hmac == HMAC(secret, everything the handler trusts)` and lets an attacker who possesses one valid `(raw_body, hmac)` pair for the app's secret replay it with a forged `shop-domain`/`topic` header, and have `Registry.process` accept it as coming from an arbitrary shop.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it (constant-time) to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., only the body integrity/provenance), then immediately trusts the header-derived `request.topic` and `request.shop` to route the payload and construct `WebhookMetadata`, which host applications use as the tenant key to update per-shop state: [3](#0-2) 

The equality the code implicitly assumes is:
`shop_header == shop_that_actually_produced(raw_body, hmac)`

But because `shop` (and `topic`) are excluded from `to_signable_string`, this equality is never checked. Any request with a raw body/HMAC pair that is valid for the app's `client_secret` will pass validation regardless of which `shop-domain` header accompanies it. An attacker who can obtain one genuine `(raw_body, hmac)` pair signed with the app's secret (e.g., from a webhook delivered to their own installed instance of the app, or intercepted/logged by any component in the delivery path) can resend that exact body with the `X-Shopify-Shop-Domain` header changed to any target shop domain, and `HmacValidator.validate` will still return `true` because the raw body — the only signed material — is unchanged.

### Impact Explanation
This is a tenant-identity-binding bypass: the gem authenticates *bytes* (the body) but the application-facing API (`WebhookMetadata#shop`) exposes an *unauthenticated* value as if it had been verified. Host applications built on this gem's documented `Registry.process` contract reasonably assume `data.shop` is trustworthy once `HmacValidator.validate` succeeds. An attacker exploiting this can inject spoofed webhook events attributed to an arbitrary victim shop (e.g., fake `orders/create`, `app/uninstalled`, GDPR, or fulfillment events), causing the host app to mutate per-tenant state, trigger notifications, or make decisions for a shop the attacker does not control — a cross-tenant access/data-integrity violation.

### Likelihood Explanation
The attacker does not need `api_secret_key`, an access token, TLS interception of the victim's traffic, or any privileged account — they only need one valid `(raw_body, hmac)` pair produced under the app's secret, which is achievable by installing the app on their own store and capturing a legitimately delivered webhook for their own shop (or via any weaker exposure such as a debug/log endpoint that reflects webhook payloads). Once obtained, the replay against the app's public webhook endpoint with a modified `shop-domain` header is trivial and requires no further secrets.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically verify it out-of-band:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (this requires coordinating with Shopify's signing scheme, since Shopify currently signs only the body) or,
- After looking up the registered `webhook_id`/subscription for the topic, verify the delivered `shop-domain` header matches the shop that owns that specific `webhook_id`/subscription (an authenticated lookup) rather than trusting the header directly, and reject mismatches before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g., updates an order) to receive a genuine webhook delivery, capturing the raw body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (both are valid for the app's secret).
2. Attacker sends a POST request directly to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `raw_body` (`B`), matching `H`: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the host application processes the event as if it genuinely originated from the victim shop.
