## Analysis Result

### Title
`DestinationAddressMatchesTokenAddressError` Guard Bypassed via Bitcoin Bech32 Case Variance, Causing Funds to Be Misdelivered to the Bridge's Own Token Address - (File: `packages/intents-sdk/src/lib/compareAddresses.ts`)

### Summary
The Omni Bridge withdrawal path validates a destination address for format-acceptance using a BIP-173-compliant, case-tolerant `validateAddress()`, but blocks self-sends (destination == token's own custody address) using a strictly case-sensitive `compareAddresses()`. A later normalization step lowercases Bitcoin `bc1...` addresses before they are embedded in the actual on-chain withdrawal message. This means an attacker/user can submit an all-uppercase variant of the bridge's own BTC token address, pass the anti-self-send equality check (because the comparison is case-sensitive and doesn't match), and have the address silently lowercased afterward into the exact address the check was supposed to block — resulting in funds being sent to the token's own bridge-custody address.

### Finding Description
`validateAddress()` accepts bech32 addresses per BIP-173, which explicitly permits an address encoded in *either* all-lowercase or all-uppercase form (mixed case is invalid, but pure uppercase is spec-valid): [1](#0-0) 

The equality check used to block "withdraw to the token's own address" is `compareAddresses()`, which for Bitcoin (and several other chains) does a raw, case-sensitive string comparison with no canonicalization: [2](#0-1) 

This is invoked in `OmniBridge.validateWithdrawal()`: [3](#0-2) 

Separately, `deriveOmniWithdrawIntentParams()` explicitly documents and performs a lowercase-normalization step for `bc1` addresses right before constructing the actual on-chain recipient, because "the Omni contract only accepts lowercase bech32 addresses": [4](#0-3) 

The break in the equality: the check `compareAddresses(destTokenAddress, args.destinationAddress, Bitcoin)` is evaluated on the *original, case-preserved* input, while the value actually written into the withdrawal `recipient` field is the *lowercased* value computed afterward in `deriveOmniWithdrawIntentParams`. If a caller submits the bridge's own BTC token custody address in all-uppercase form:
- `validateAddress()` accepts it as a syntactically valid bech32 address.
- `compareAddresses()` (case-sensitive `a === b`) does **not** match it against the lowercase canonical `destTokenAddress`, so `DestinationAddressMatchesTokenAddressError` is never thrown.
- Later, `deriveOmniWithdrawIntentParams` lowercases the address (since it matches `/^bc1/i`), producing exactly the token's own custody address as the on-chain `recipient`.

The validated value and the delivered value diverge only in case, but resolve to the identical destination once normalized — defeating the purpose of the self-send guard.

### Impact Explanation
Withdrawals sent to the bridge's own token custody address are the exact scenario `DestinationAddressMatchesTokenAddressError` exists to prevent elsewhere in the codebase (see analogous comments/tests for other chains in `omni-bridge.ts`/`omni-bridge.test.ts`). Funds delivered to the token's own bridge address are not deliverable to any real user and require manual intervention or are permanently unrecoverable, matching the "funds delivered to a wrong address/chain/contract with no recovery" / "withdrawal stuck until manual intervention" impact classes.

### Likelihood Explanation
Any caller of the public SDK (`IntentsSDK.createWithdrawalIntents` / `estimateWithdrawalFee`) controls `destinationAddress` directly; no privileged or on-chain access is required. The only additional pre-condition beyond attacker knowledge is knowing the bridge's canonical Bitcoin bech32 custody address for the given token (which is derivable via `getBridgedToken`/public bridge queries) and submitting an uppercase variant of it.

### Recommendation
Normalize case before comparison in `compareAddresses()` for bech32-based chains (Bitcoin, and any other chain where the address encoding permits an alternate valid case form), or perform the self-send equality check *after* all chain-specific normalization (including the `bc1` lowercasing done in `omni-withdraw-params.ts`) rather than before it. In general, ensure any equality/safety check operates on the same canonical form that is ultimately written to the chain.

### Proof of Concept
1. Determine the bridge's BTC custody address for a token, e.g. `bc1q5deh93tj8lcwuh4c34nxtcydtdnfpvmdfzwdml` (used throughout `omni-bridge.test.ts` as the token's destination address).
2. Call withdrawal with `destinationAddress: "BC1Q5DEH93TJ8LCWUH4C34NXTCYDTDNFPVMDFZWDML"` (all-uppercase form of the same address).
3. `validateAddress()` accepts it (valid bech32 format).
4. `compareAddresses(destTokenAddress /* lowercase */, "BC1Q5DEH93TJ8LCWUH4C34NXTCYDTDNFPVMDFZWDML", Bitcoin)` returns `false` (case-sensitive `a === b`), so `DestinationAddressMatchesTokenAddressError` is not thrown.
5. `createWithdrawalIntents` proceeds to `deriveOmniWithdrawIntentParams`, which matches `/^bc1/i` and lowercases the address to `bc1q5deh93tj8lcwuh4c34nxtcydtdnfpvmdfzwdml` before embedding it as `recipient` in the `ft_withdraw` intent — identical to the token's own custody address that the check was meant to reject.
