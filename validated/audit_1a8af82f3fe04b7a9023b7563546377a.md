### Title
Same-`assetId` batched withdrawals cause `PoaBridge.describeWithdrawal` to misreport status/txHash across `WithdrawalIdentifier.index` values - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal status record using only `assetId` via `findMatchingWithdrawal`, ignoring `index`. When a single NEAR Intents transaction contains two PoA withdrawal legs with the same `assetId` (e.g., two `nep141:btc.omft.near` legs to different `destinationAddress` values), both `WithdrawalIdentifier{index:0}` and `WithdrawalIdentifier{index:1}` resolve to the same (first) matching record returned by `array.find`, so both legs report the same `status`/`transfer_tx_hash` even though only one leg's on-chain payout actually corresponds to it.

### Finding Description
The broken equality: `describeWithdrawal({index:0}).txHash` should equal the destination-chain tx hash of withdrawal leg 0 only, and `describeWithdrawal({index:1}).txHash` should equal leg 1's own tx hash; they must never be equal to each other's true underlying record when the two legs' payouts are in different states.

Code path:
- `createWithdrawalIdentifiers` in [1](#0-0)  assigns a per-route incrementing `index` to each withdrawal leg without any check that `assetId` is unique within that route; two `nep141:btc.omft.near` legs both routed to `PoaBridge` get `index:0` and `index:1`.
- `PoaBridge.describeWithdrawal` at [2](#0-1)  calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely on `assetId`, and the comment at the definition explicitly states this limitation: [3](#0-2) .
- `findMatchingWithdrawal` uses `Array.prototype.find`, so when the PoA bridge API returns two withdrawal records with the same `near_token_id` (one `COMPLETED` with a real `transfer_tx_hash`, one still `PENDING`), both `index:0` and `index:1` calls receive the *first* matching record — identical `status`/`txHash` — regardless of which leg it actually belongs to.
- `watchWithdrawal` in [4](#0-3)  polls `describeWithdrawal` per `WithdrawalIdentifier` and returns `{hash: status.txHash}` once `status === "completed"` — an integrator awaiting both legs' promises will see both resolve to "completed" with the same `txHash`, even though only one leg has actually settled.

No existing guard prevents this: `supports()` only validates that the asset belongs to the PoA token factory, not asset uniqueness across legs; `validateAddress`/`compareAddresses` validate a single leg's destination format, not cross-leg disambiguation; there is no index-aware or amount-based tie-breaking in `findMatchingWithdrawal`.

### Impact Explanation
An integrator that treats `watchWithdrawal` output as authoritative per-leg settlement proof will credit/release the downstream action (e.g., mark a destination-chain payout as confirmed, or release custody) for the leg whose real transfer is still `PENDING` (or has a different `transfer_tx_hash`/amount), based on the other leg's completed record. This is a status/hash misreport that can cause an integrator to act on funds twice or route confirmation to the wrong leg — matching the High-severity category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Preconditions: an ordinary user (or a solver constructing withdrawal params echoed by an integrator) submits one intent transaction with two PoA-routed withdrawal legs for the identical `assetId` but distinct `destinationAddress`. This requires no privileged access — `WithdrawalParams` are attacker-supplied strings per the threat model, and nothing in `createWithdrawalIdentifiers` or `PoaBridge.supports` rejects duplicate `assetId` within a batch. The scenario is reachable purely through the SDK's public API and standard PoA response shapes (mocked via HTTP in tests), so it is feasible and repeatable for every batch withdrawal with a repeated PoA asset.

### Recommendation
Make `findMatchingWithdrawal` index-aware: sort the batch's own `withdrawalParams` and the API's `withdrawals` array deterministically (e.g., by `amount`, since fees are equal per token so relative order is preserved, as the existing code comment already suggests) and select the `index`-th matching entry for a given `assetId`, rather than the first match. Alternatively, until the PoA API supports disambiguating multiple same-asset withdrawals in one batch, explicitly detect and reject (throw) when a batch contains more than one leg with the same `assetId` routed to `PoaBridge`, rather than silently returning ambiguous statuses.

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
