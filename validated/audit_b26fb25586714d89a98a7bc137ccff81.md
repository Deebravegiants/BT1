### Title
`describeWithdrawal` reports NEAR-bound Omni Bridge withdrawals as `completed` without checking any finalisation marker - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
`OmniBridge.describeWithdrawal` branches on the destination chain derived from `transfer.recipient`. For any chain that is neither EVM/Sol/Fogo/Strk/Aptos nor a UTXO chain (in particular `ChainKind.Near`, i.e. a withdrawal that lands back on a NEAR account), it unconditionally returns `{ status: "completed", txHash: null }` as soon as `getTransfer` returns a record with a non-null `recipient`, regardless of `transfer.finalised`, `transfer.finalised_on_near`, `transfer.claimed`, `transfer.verified`, or `transfer.status`.

### Finding Description
The broken equality is: reported `status` (`'completed'`) should equal the actual on-chain/ledger finalisation state of the transfer as recorded by the bridge indexer (`transfer.finalised_on_near` / `transfer.claimed` / `transfer.status === "Finalised"`, etc.).

In [1](#0-0)  the flow is:

1. `transfer = (await this.omniBridgeAPI.getTransfer({ transactionHash: args.tx.hash }))[args.index]`.
2. If `transfer == null || transfer.recipient == null` → `pending` (correct).
3. `destinationChain = getChain(transfer.recipient)`.
4. If `destinationChain` is EVM/Sol/Fogo/Strk/Aptos → txHash comes from `transfer.finalised?.transaction_hash` (checked, correct).
5. Else if UTXO chain → txHash comes from `utxo_meta.pending_sign_id` or `transfer.finalised?.transaction_hash` (checked, correct).
6. **Else (any other `ChainKind`, e.g. `ChainKind.Near`) → `return { status: "completed", txHash: null };` with no check of any finalisation field at all.**

This last branch is reached the moment `getTransfer` returns any record whose `recipient` decodes to an address prefix that isn't handled by the two explicit branches (e.g. `near:<account>`), even if the transfer object has `status: "Initialised"`, `finalised: null`, `finalised_on_near: null`, `claimed: null`, `verified: null` — i.e. no evidence the transfer has actually landed. The attacker's exact input is simply the counterparty-controlled destination address string used to build the withdrawal (`destinationAddress` routed into `withdrawalParams`, ultimately encoded as a NEAR-style Omni recipient), which is exactly the kind of string an integrator forwards into the SDK per the threat model.

None of the existing guards (`validateWithdrawal`, `supports()`, `FeeExceedsAmountError`, `matchesRequest`, the intents contract's signature/nonce checks) touch this post-submission status-polling code path — they only govern intent construction, not the after-the-fact `describeWithdrawal` status query. `watchWithdrawal` in [2](#0-1)  trusts `describeWithdrawal`'s `status === "completed"` verbatim and stops polling, returning a finished `TxInfo` to the caller.

### Impact Explanation
An integrator polling withdrawal status via `watchWithdrawal`/`describeWithdrawal` for a NEAR-destination Omni Bridge withdrawal is told the withdrawal is `completed` (with `txHash: null`) the instant the bridge indexer records *any* transfer entry with that recipient, not once it is actually finalised/claimed on NEAR. This can cause an integrator to release downstream funds, credits, or unlock dependent actions before the withdrawal is truly settled, and if the transfer later fails, stalls, or is reorganized on the indexer side, there is no re-check because polling has already stopped believing it "completed". This matches the High/Critical category of "a status or hash misreport making an integrator credit or refund twice" / "withdrawal stuck until manual intervention" since the caller has no `txHash` to independently verify and no further status transition will be observed.

### Likelihood Explanation
Preconditions: the withdrawal's destination must resolve (via `getChain`) to a `ChainKind` not covered by the EVM/Sol/Fogo/Strk/Aptos or UTXO branches — this is the case for NEAR-bound Omni withdrawals, which are a normal, permissionless, and reachable route (any ordinary user can request a withdrawal whose destination is a NEAR account through the Omni Bridge route). No special privilege or malicious relayer is required; this triggers on every such withdrawal by design of the code, and the divergence is repeatable on every call to `describeWithdrawal` for this chain class until the underlying `@omni-bridge/core` `getChain`/branch coverage is updated.

### Recommendation
In the `else` branch of `describeWithdrawal` (packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts, around lines 722-724), do not unconditionally return `completed`. Instead check an actual finalisation signal for the NEAR-side leg, e.g. `transfer.finalised_on_near` / `transfer.claimed` / `transfer.status === "Finalised"` (or the correct equivalent field for NEAR-bound transfers), returning `pending` when it is absent, consistent with how the EVM/Sol/UTXO branches gate on `transfer.finalised`.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
