### Title
`process_withdraw` skips `calc_take_pnl` in `WithdrawOnly` status, letting LPs withdraw the AMM owner's unrealized fee PnL - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` conditionally calls `Self::calc_take_pnl` only `if amm.status != AmmStatus::WithdrawOnly.into_u64()`. This mirrors the reported bug class: an accounting/ratio update ("carve out owner fee PnL from reserves before computing the LP share") is skipped based on an unrelated condition (pool status), even though the state that should trigger the update (accrued but un-swept `k`-growth from trading fees) is independent of that condition.

### Finding Description
`calc_take_pnl` is the function that reconciles the constant-product invariant growth (from swap fees) since the last snapshot (`target_orders.calc_pnl_x` / `calc_pnl_y`) and carves the AMM owner's fee share out of `total_pc_without_take_pnl` / `total_coin_without_take_pnl` before any deposit/withdraw math runs: [1](#0-0) 

In every other reachable state-changing path (`process_deposit`, `process_withdrawpnl`), `calc_take_pnl` is invoked unconditionally before computing the LP/owner shares: [2](#0-1) [3](#0-2) 

But `process_withdraw` explicitly skips this step when the pool is in `WithdrawOnly` status: [4](#0-3) 

When skipped, `delta_x`/`delta_y` remain `0`, `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` are **not** incremented, and `total_pc_without_take_pnl`/`total_coin_without_take_pnl` are **not** reduced by the owner's already-accrued (unswept) fee revenue. The withdrawing LP's `coin_amount`/`pc_amount` are then computed as a pro-rata share of the *full* un-carved reserve (including the owner's unclaimed PnL), via: [5](#0-4) 

and `target_orders.calc_pnl_x`/`calc_pnl_y` (the running invariant snapshot) is still decremented by the withdrawn amount as if the PnL had been swept (using `delta_x = delta_y = 0`): [6](#0-5) 

This breaks the accounting invariant that `vault_balance ≈ total_without_take_pnl + need_take_pnl_{pc,coin}` — exactly analogous to the referenced Ajna bug where a derived accounting value is updated conditionally on the wrong trigger, causing it to drift from the true state. Here the trigger is `amm.status`, unrelated to whether unrealized owner PnL actually exists in the pool.

### Impact Explanation
Whenever the pool is transitioned into `WithdrawOnly` status while there is still unswept trading-fee PnL sitting in the vaults (i.e., `total_pc_without_take_pnl`/`total_coin_without_take_pnl` computed from vault balances still contains the owner's un-carved fee share), every LP withdrawal during that status silently distributes part of the AMM owner's accrued fee revenue to withdrawing LPs. This is a real fund-misallocation/insolvency bug: the pool's owner-designated PnL (`need_take_pnl_pc`/`need_take_pnl_coin`) becomes under-collateralized relative to the true residual vault balance, so a subsequent `process_withdrawpnl` call by the legitimate `pnl_owner` can fail (`AmmError::TakePnlError`) or leave the pool insolvent for the last withdrawers, since `withdrawpnl` requires `need_take_pnl_coin <= amm_coin_vault.amount && need_take_pnl_pc <= amm_pc_vault.amount`. This directly qualifies as "insolvent pool accounting" / unauthorized value transfer between the owner's PnL and LPs.

### Likelihood Explanation
Reachability requires only a single `Withdraw` transaction by any LP holding LP tokens while `amm.status == WithdrawOnly`. `WithdrawOnly` is a legitimate, reachable operational status (set via `SetParams`/admin action, not attacker-controlled, but the withdrawal itself is triggerable by any unprivileged LP once that status is active) — no privileged signer or off-chain condition is needed to trigger the flawed accounting path itself. The bug is deterministic whenever there is any nonzero unswept PnL at the time of withdrawal, which is the normal/expected condition after any prior swap activity.

### Recommendation
Remove the `amm.status != AmmStatus::WithdrawOnly` condition around the `calc_take_pnl` call in `process_withdraw`, or equivalently always call `calc_take_pnl` (mirroring `process_deposit`/`process_withdrawpnl`) so that owner PnL is always carved out of reserves before computing the LP's proportional withdrawal amount, regardless of pool status.

### Proof of Concept
1. Initialize a pool and perform swaps so that trading fees accrue, i.e. `x1*y1 > calc_pnl_x*calc_pnl_y` (real invariant growth exists) without any deposit/withdraw/withdrawpnl call in between to sweep it.
2. Admin sets pool status to `WithdrawOnly`.
3. An LP calls `Withdraw`. In `process_withdraw`, because `amm.status == WithdrawOnly`, `calc_take_pnl` is skipped (`program/src/processor.rs:1740-1749`), so `total_pc_without_take_pnl`/`total_coin_without_take_pnl` still include the owner's unswept PnL and `need_take_pnl_pc`/`need_take_pnl_coin` are not incremented.
4. The LP's `coin_amount`/`pc_amount` (computed at `program/src/processor.rs:1756-1761`) are inflated by their pro-rata share of the owner's unswept PnL, which is transferred out of the vaults.
5. Later, `process_withdrawpnl` is called by the legitimate `pnl_owner`; because the vault balances have already been depleted by the inflated withdrawals in step 4, `need_take_pnl_coin <= amm_coin_vault.amount && need_take_pnl_pc <= amm_pc_vault.amount` may fail, reverting with `AmmError::TakePnlError` (`program/src/processor.rs:1505-1536`), or if it barely passes, the owner receives less than the fees actually earned — the difference having been extracted by the LP(s) who withdrew during `WithdrawOnly` status.

                    .unwrap();
