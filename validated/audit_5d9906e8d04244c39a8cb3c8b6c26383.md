## Analysis Result

### Title
Newly whitelisted parachains always get a hardcoded zero challenge period, silently diverging from governance-configured values - (File: `modules/ismp/clients/parachain/client/src/lib.rs`)

### Summary
The `pallet-ismp-parachain` client hardcodes the challenge period to `0` whenever a new parachain is added to the relay-chain consensus client, instead of reading/propagating whatever challenge period governance has configured as the current standard for that consensus state. This mirrors the referenced M-04 pattern (`setPeriodSize` updates existing pairs but `createPair` still uses the stale/default value): here, `update_consensus_state` can raise the challenge period for already-whitelisted state machines under a consensus state, but any parachain added afterwards via `add_parachain` bypasses that governance decision and is unconditionally set to `0`.

### Finding Description
`add_parachain` calls `store_challenge_period` with a literal `0` for every newly whitelisted parachain, regardless of any challenge period previously/subsequently configured by `T::AdminOrigin` for other state machines sharing the same `consensus_state_id`: [1](#0-0) 

The same hardcoded `0` is used at genesis for the initial parachain set: [2](#0-1) 

Separately, `pallet-ismp`'s `update_consensus_state` extrinsic is the governance path meant to change challenge periods for state machines (analogous to `setPeriodSize` in the referenced report): [3](#0-2) 

Critically, a challenge period of `0` is treated specially in the delay-verification logic — it means **no delay is enforced at all**, not merely "very fast": [4](#0-3) 

So while governance may have raised the challenge period for all currently-tracked parachains (e.g., in response to observed relayer/validator misbehavior, or simply as the chain's standard security parameter), any parachain added to the whitelist afterwards via `add_parachain` receives `challenge_period = 0` — meaning state commitments relayed for that parachain can be consumed by `validate_state_machine` immediately, with zero dispute/fisherman window, the moment they're stored: [5](#0-4) 

This is the exact bug class from the report: a creation/whitelisting function (`add_parachain`, analogous to `createPair`) does not read the "current" governance-configured value (analogous to the updated `periodSize`), instead using a stale/hardcoded default.

### Impact Explanation
A zero challenge period removes the fisherman dispute window that other properly-configured parachains benefit from. Any newly whitelisted parachain becomes immediately exploitable: a relayer submitting a fraudulent/premature state commitment for that parachain (e.g., before finality, or from an equivocating validator set) can have it consumed instantly by requests/responses/`GetRequest` verification, since `verify_delay_passed` short-circuits to `true` when the configured period is `0`. This is a concrete "unsound state commitment"/"forged message delivery" risk for the newly added chain — an application that trusts requests routed through Hyperbridge from that state machine can be tricked into acting on unfinalized or forged state before it should be trustable, undermining the security intent of governance's higher challenge period standard.

### Likelihood Explanation
`add_parachain` runs under `RootOrigin`, so it requires a privileged call — but it is not a malicious-admin scenario: this is the normal, expected operational flow (onboarding new parachains over time), just like `createPair` in the referenced report is a normal, benign admin action. Any time governance has previously raised the challenge period standard (via `update_consensus_state`) and later legitimately onboards a new parachain, the new parachain silently gets zero delay — this will happen on every single onboarding after the initial governance tuning, making it a systematic (not edge-case) inconsistency.

### Recommendation
Instead of hardcoding `0`, `add_parachain` (and the genesis builder) should read the challenge period currently configured for the shared `consensus_state_id` (e.g., via `host.challenge_period(...)` for an existing sibling state machine, or from a pallet-level "current default challenge period" storage item kept in sync by `update_consensus_state`) and apply that same value to the newly added parachain, or accept the desired challenge period as part of `ParachainData` so governance can set it explicitly per parachain.

### Proof of Concept
1. Governance calls `update_consensus_state` (`modules/pallets/ismp/src/lib.rs:416-437`) to raise the challenge period for `StateMachineId { state_id: Polkadot(1000), consensus_state_id: POLKADOT_CONSENSUS_ID }` to, say, 600 seconds, as the chain's new security standard.
2. Later, governance calls `add_parachain` with `ParachainData { id: 2000 }` to onboard a new parachain under the same relay-chain consensus client.
3. `add_parachain` calls `host.store_challenge_period(StateMachineId { state_id: Polkadot(2000), consensus_state_id: POLKADOT_CONSENSUS_ID }, 0)` (`modules/ismp/clients/parachain/client/src/lib.rs:173-179`), overwriting/ignoring the governance-intended 600s standard.
4. A relayer submits a state commitment for `Polkadot(2000)` and immediately submits a request/response proof against it. `verify_delay_passed` (`modules/ismp/core/src/handlers.rs:104-114`) sees `delay_period.as_secs() == 0` and returns `true` unconditionally, so `validate_state_machine` accepts the proof with zero elapsed time — no dispute window was ever available for parachain 2000, unlike parachain 1000.

		/// - `message`: `UpdateConsensusState` struct.
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().writes(2))]
		#[pallet::call_index(3)]
		pub fn update_consensus_state(
			origin: OriginFor<T>,
			message: UpdateConsensusState,
		) -> DispatchResult {
			T::AdminOrigin::ensure_origin(origin)?;

			let host = Pallet::<T>::default();

			if let Some(unbonding_period) = message.unbonding_period {
				host.store_unbonding_period(message.consensus_state_id, unbonding_period)
					.map_err(|_| Error::<T>::UnbondingPeriodUpdateFailed)?;
			}

			for (state_id, period) in message.challenge_periods {
				let id =
					StateMachineId { state_id, consensus_state_id: message.consensus_state_id };
				host.store_challenge_period(id, period)
					.map_err(|_| Error::<T>::UnbondingPeriodUpdateFailed)?;
			}

			Ok(())
		}

/// for the state machine has elasped.
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

/// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
