### Title
Webhook `shop`, `topic`, and `webhook-id` values are trusted from unauthenticated HTTP headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` by reading them directly from HTTP headers, but its `to_signable_string` (the data the HMAC actually protects) is only the raw request body. This breaks the identity binding `hmac == HMAC(shop || topic || body)` that a consumer of this gem would reasonably assume holds; in reality `hmac == HMAC(body)` only, so the `shop`/`topic`/`webhook_id` fields are "acted on but not covered by the HMAC," matching the bug class in the external report (a value used for a security decision that isn't bound by the value that's supposed to authenticate it).

### Finding Description
`Webhooks::Request#hmac` decodes the `X-Shopify-Hmac-Sha256` header, and `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers, which are never included in the signed string: [3](#0-2) 

`Utils::HmacValidator.validate` (used elsewhere for OAuth) computes `HMAC(secret, to_signable_string)` and compares it to the supplied `hmac`; the same interface (`Utils::VerifiableQuery`) is implemented here, but for webhooks nothing in the library calls `HmacValidator.validate` against the body — a host application is expected to verify `request.hmac` against the raw body itself. Even when that verification is done correctly, it only proves the body's integrity, not that `shop`/`topic`/`webhook_id` are the values Shopify actually associated with that body.

This mirrors the reported bug class: just as `IsolatedMarginTrading` uses `liquidationThresholdPercent` in a security check without it being properly bound/initialized, here the `shop` value used to route/dispatch a webhook (in `Webhooks::Registry`, which reads `request.shop`) is used in a security-relevant decision without being cryptographically bound to the payload that was actually signed.

### Impact Explanation
If a background job or handler keys any tenant-scoped action (e.g., which shop's data to delete/update, or which session/store to invalidate) off `request.shop` while only validating `request.hmac` against the body, an attacker who has ever received one legitimately-signed webhook body for *some* shop of the same app (e.g., their own store) can replay that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a *different* shop. The HMAC will still validate because the header isn't part of the signed content, enabling cross-tenant action confusion. This matches the "cross-tenant access" Critical impact category, since it lets an unprivileged user manipulate which tenant a signed payload is attributed to.

### Likelihood Explanation
Exploitability depends entirely on the host application's use of `request.shop` for authorization/routing decisions after HMAC verification, which the gem's own webhook docs/flow encourage (`Registry` reads `request.shop`). Since the gem provides no binding between the signed body and the header-derived `shop`, any consumer following the documented pattern of "verify HMAC, then trust `request.shop`" is exposed. Likelihood is moderate — it requires the app to have already received one valid webhook (easy, since merchants can trigger events on their own store) and to trust `shop` for a security-relevant decision.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the signable content that is cryptographically verified, or explicitly document that `Webhooks::Request#shop` is unauthenticated and must never be used for tenant-scoping decisions independent of a separately verified value (e.g., the shop encoded via OAuth session lookup). Alternatively, have `Registry` re-derive/cross-check the shop from a value that is part of the HMAC-covered payload (many webhook bodies include shop-identifying fields) rather than solely from the header.

### Proof of Concept
1. App has multiple shops installed (`shop-a.myshopify.com`, `shop-b.myshopify.com`) using the same `client_secret`.
2. Attacker (a user of `shop-a`) triggers a legitimate webhook event on `shop-a`, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H = HMAC(secret, B)`.
3. Attacker replays a request to the app's webhook endpoint with body `B`, the same header `H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-hmac-sha256" => H, "x-shopify-shop-domain" => "shop-b.myshopify.com", ...})`.
5. `request.hmac` still equals `H` and `to_signable_string` still equals `B`, so any HMAC check against the body passes, while `request.shop` returns `"shop-b.myshopify.com"` — a value never covered by the HMAC — causing the handler to act on `shop-b`'s tenant context using data intended only for `shop-a`. # typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
