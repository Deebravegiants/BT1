### Title
Webhook shop/topic identity not bound to HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the shop domain, topic, and webhook id are read from separate, unsigned HTTP headers and then trusted downstream to route and label the delivered data. This breaks the binding between "bytes verified" and "shop/topic acted on."

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by computing an HMAC over `to_signable_string` and comparing it to the supplied `hmac` [1](#0-0) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from separate HTTP headers that are not part of the signed content [3](#0-2) .

`Registry.process` validates only the HMAC over the body, then uses the unauthenticated `request.topic` to look up a handler and passes the unauthenticated `request.shop` straight into the delivered `WebhookMetadata` that the host application's handler code consumes: [4](#0-3) .

Because `shop`, `topic`, and `webhook_id` are never covered by the signature, any request whose raw body carries a valid HMAC for the app's `client_secret` will pass validation regardless of which shop-domain/topic headers are attached to it. Since the same `api_secret_key` is shared across all shops that install the app, a party who controls a legitimate install of the app (an ordinary merchant/tenant, not a privileged actor) receives real, validly-signed webhook deliveries for their own shop's events, and can replay that exact `raw_body`+`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) headers for another tenant's shop. `Registry.process` will accept it as valid and hand the host application a `WebhookMetadata` claiming to originate from the victim shop, breaking the equality that should hold: `shop bound by HMAC == shop acted upon by the handler`.

### Impact Explanation
This is a cross-tenant identity confusion: data purportedly belonging to shop A can be injected and processed by the host app as if it belonged to shop B, using nothing but a single legitimately-received webhook from the attacker's own (or any) install of the app. Depending on what the host app's webhook handlers do with `WebhookMetadata#shop` (e.g., look up records, provision resources, or gate access per tenant), this can lead to cross-tenant data corruption or unauthorized cross-tenant actions — matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Moderate. The attacker needs at least one genuine webhook delivery from Shopify for any shop that has installed the target app (trivial to obtain by installing a test/dev store of the target app, or observing/replaying a delivery for their own store), and needs to be able to POST to the app's public webhook endpoint with modified headers — no possession of `api_secret_key`, access tokens, or any privileged credential is required.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content used by `HmacValidator`, or otherwise cryptographically bind them (e.g., require the host application to independently verify `request.shop` against a known/authorized tenant before dispatching to a handler), so that a validly-signed body cannot be replayed under a different shop or topic.

### Proof of Concept
1. Attacker installs (or otherwise gets deployed as) the target app on `attacker-shop.myshopify.com`; Shopify sends a real webhook: body `B`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: H` (valid HMAC over `B` using the app's `client_secret`).
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, client_secret) == H` [5](#0-4)  — this passes because `B` and `H` are unchanged.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim tenant's identity.
