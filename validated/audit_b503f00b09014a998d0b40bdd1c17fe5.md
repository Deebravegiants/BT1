### Title
Uncontrolled Resource Consumption via Unbounded `votes_ancestries` in GRANDPA Justification Verification - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The reported Apache Tika CVE is a classic "attacker supplies unbounded/crafted structure → verifier does unbounded work" bug class. The closest reachable analog in Hyperbridge is `GrandpaJustification::verify_with_voter_set`, which builds an `AncestryChain` from the relayer-controlled `votes_ancestries: Vec<H>` field of a submitted consensus proof, with no length or size bound enforced before the expensive header-graph construction and per-precommit ancestry walk are performed.

### Finding Description
`GrandpaConsensusClient::verify_consensus` (`modules/ismp/clients/grandpa/src/consensus.rs`) SCALE-decodes an attacker/relayer-submitted `proof: Vec<u8>` into a `ConsensusMessage`, which for the GRANDPA/relay-chain path eventually reaches `verify_grandpa_finality_proof` → `GrandpaJustification::<H>::decode_all` (`modules/consensus/grandpa/verifier/src/lib.rs:66-68`). Neither the outer extrinsic/message envelope nor the `GrandpaJustification` decode path enforces any cap on the number of headers in `votes_ancestries: Vec<H>` (`modules/consensus/grandpa/primitives/src/justification.rs:41-48`).

`verify_with_voter_set` then does: [1](#0-0) 

For every precommit, it walks `AncestryChain::ancestry(base_hash, target_hash)`: [2](#0-1) 

`AncestryChain::new` first clones the entire `votes_ancestries` vector into a `BTreeMap<Hash, Header>`: [3](#0-2) 

Because `votes_ancestries` is fully attacker-controlled (a relayer constructs the justification bytes that are submitted as `proof`), and each `Header` itself can carry an arbitrarily large digest/log payload, an attacker can submit a justification with an extremely large `votes_ancestries` vector (many large headers) to force:
- A large SCALE decode allocation for the whole header list,
- A large `BTreeMap` clone/build in `AncestryChain::new`,
- Repeated linear ancestry walks per precommit (`self.commit.precommits.iter()` × ancestry chain length),
- A final `BTreeSet` diff over `visited_hashes` vs `ancestry_hashes` covering the whole set.

This is directly analogous to the Tika PSD parser bug class: a crafted/oversized input structure drives unbounded memory allocation and CPU work in a verifier that is expected to process untrusted, externally supplied data before any cryptographic check can reject it (the ancestry construction and walk happen *before/alongside* the ed25519 signature checks and are not short-circuited by a fast-fail size check).

### Impact Explanation
This is reachable by any relayer submitting a GRANDPA consensus proof through the public `verify_consensus`/`verify_fraud_proof` entry points — no special privileges are required. A crafted oversized `votes_ancestries` list can drive excessive memory allocation and CPU consumption in the runtime processing the consensus update, potentially exhausting node resources or causing execution to exceed block-processing budgets, denying or degrading the ability of the chain to process legitimate consensus updates (a route unable to deliver/verify consensus messages, satisfying the "unable to deliver messages" impact bucket). This matches CWE-400 Uncontrolled Resource Consumption at Medium severity — it does not itself forge state or steal funds, but it can stall the finality pipeline that gates all downstream message delivery for GRANDPA-secured state machines.

### Likelihood Explanation
Likelihood is bounded by the practical cost to the attacker: since the proof is included in extrinsic/call data, some outer size limits (block size / weight, or `BoundedVec` on some pallets' calls) may partially throttle the worst case, but I could not confirm any explicit `BoundedVec`/length cap specifically on `votes_ancestries` or the GRANDPA proof payload analogous to `BoundedVec<u8, MaxProofSize>` used by `pallet-beefy-consensus-proofs`. Absent such a bound, an attacker only needs to construct a valid-looking (not necessarily cryptographically valid) large header list to trigger the expensive `BTreeMap`/`BTreeSet` construction and ancestry walk before verification fails, since these operations run prior to the point where the justification is ultimately rejected.

### Recommendation
- Enforce an explicit, conservative upper bound on `votes_ancestries.len()` (and on `unknown_headers.len()` in `FinalityProof`) before constructing `AncestryChain`, similar to the `BoundedVec<u8, MaxProofSize>` pattern already used in `pallet-beefy-consensus-proofs`.
- Consider bounding the total decoded size of the GRANDPA proof/justification payload at the pallet/extrinsic boundary (e.g., a `MaxJustificationSize` config constant) so oversized payloads are rejected during SCALE decode rather than after allocation.
- Add a regression test analogous to the existing MMR/Pharos `MAX_PROOF_DEPTH`/oversized-proof tests, asserting that a justification with a pathologically large `votes_ancestries` is rejected cheaply (e.g., `Error::TooManyAncestryHeaders`) before `AncestryChain::new`/`ancestry()` run.

### Proof of Concept
1. Construct a `GrandpaJustification<H>` with a valid `Commit` (or one that will fail late) but populate `votes_ancestries` with N (e.g., 10⁵–10⁶) synthetic `Header` values, each padded with large digest logs to maximize decoded size.
2. SCALE-encode this as the `justification` field inside a `FinalityProof`, wrap it as the `proof` bytes for `GrandpaConsensusClient::verify_consensus` (or `verify_fraud_proof`, which also calls `GrandpaJustification::decode` and `AncestryChain::new` on `unknown_headers`, `modules/ismp/clients/grandpa/src/consensus.rs:286-320`).
3. Submit via the public message-handling extrinsic that dispatches to `verify_consensus`.
4. Observe that decoding + `AncestryChain::new` (BTreeMap of N headers) + the per-precommit `ancestry()` walk are all executed — consuming memory and CPU proportional to N — before the function can reject the proof, regardless of whether the signatures ultimately verify.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
}
