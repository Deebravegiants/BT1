### Title
Non-unique `assetId`-based withdrawal matching causes wrong destination tx hash to be reported for batch withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` and the equivalent `waitForWithdrawalCompletion` helper in `internal-utils` identify which of possibly several withdrawals in a single NEAR transaction corresponds to a given `WithdrawalIdentifier` by matching on `assetId` alone, not by amount, destination address, or index. When a batch withdrawal contains two or more withdrawals of the same token (e.g., two USDC withdrawals to different destination addresses in one `processWithdrawal` batch call), `findMatchingWithdrawal` returns the *first* array entry whose `near_token_id` matches — which may belong to a different withdrawal in the batch than the one being queried.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  looks up a completed withdrawal purely by `nep141:${w.data.near_token_id}} === assetId`, with an explicit code comment acknowledging: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." The same limitation and matching logic is duplicated in [2](#0-1) , where `WithdrawalCriteria` is defined as `{ assetId: string }` only [3](#0-2) .

`describeWithdrawal` is called once per index in a batch via `createWithdrawalCompletionPromises`, each with its own `WithdrawalIdentifier` (`landingChain`, `index`, `withdrawalParams`, `tx`) [4](#0-3) . Because the underlying POA bridge status API returns an unsorted list of withdrawals for the shared NEAR tx hash, and the SDK's matching key (`assetId`) is not unique when the batch has two withdrawals of the same token, `Array.find` will return the same entry for both queries — specifically the first matching entry in the list — regardless of which index/destination address was actually requested. This breaks the equality "the tx hash reported for withdrawal N is the tx hash of withdrawal N," analogous to the LineaRollup report's core issue: a non-unique key used to index into stored/validated data structures, causing wrong data to be attributed to a caller's query.

### Impact Explanation
If an integrator submits a batch withdrawal with two entries of the same asset (e.g., USDC to address A and USDC to address B) via `sdk.processWithdrawal`/`createWithdrawalCompletionPromises`, both `promises[0]` and `promises[1]` could resolve to the same `{ hash }`, or promise for withdrawal-to-A could resolve with the destination tx hash that actually belongs to withdrawal-to-B (and vice versa). An integrator that persists `{ index, withdrawalParams, destinationTxHash }` for reconciliation/crediting purposes (a common pattern shown in the SDK's own README, e.g. `saveSuccess(index, tx)`) could then attribute the wrong on-chain transaction to the wrong destination/customer, potentially causing a double-credit (crediting customer A's withdrawal as completed using B's transaction, while B's ledger entry is left unresolved or credited with A's hash) — this falls under the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Requires an unprivileged caller/integrator to construct a batch withdrawal (`WithdrawalParams[]`) containing two or more entries with the identical `assetId` but different destination addresses/amounts — a valid, normal usage pattern of the public `processWithdrawal`/`signAndSendWithdrawalIntent`/`createWithdrawalCompletionPromises` batch API, requiring no malicious or privileged action. The bug is explicitly acknowledged in code comments as an unhandled limitation, confirming it is a real, currently-unmitigated gap rather than a false-positive assumption.

### Recommendation
Do not rely on `assetId` alone as the matching key when multiple withdrawals of the same asset can exist in one batch/transaction. Either:
- Require the POA bridge status API to return a per-withdrawal unique identifier (e.g., an index or leg id correlated with the NEAR intent's withdrawal ordering) and match on that, or
- As suggested in the existing code comment, sort both the API results and the local `withdrawalParams` by amount (and destination) to establish a stable correspondence when `assetId` collides, and fail closed (throw, rather than silently pick the first match) when ambiguity cannot be resolved.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `signAndSendWithdrawalIntent` + `createWithdrawalCompletionPromises`) with `withdrawalParams = [{ assetId: "nep141:usdc.token.near", amount: 100n, destinationAddress: "addrA" }, { assetId: "nep141:usdc.token.near", amount: 200n, destinationAddress: "addrB" }]`.
2. After the NEAR intent tx settles, the POA bridge processes both withdrawals in the same `tx.hash`, producing two entries in `getWithdrawalStatus({ withdrawal_hash: tx.hash })` result, both with `near_token_id: "usdc.token.near"` but different `transfer_tx_hash` values.
3. `describeWithdrawal` is invoked independently for index 0 and index 1 (see `createWithdrawalCompletionPromises` in [5](#0-4) ), each calling `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.token.near")`.
4. `Array.prototype.find` returns the same (first) matching element for both calls, so `promises[0]` and `promises[1]` can both resolve with the same `transfer_tx_hash`, or resolve with a hash that belongs to the other withdrawal — even though `amount`/`destinationAddress` differ between the two withdrawal legs.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
