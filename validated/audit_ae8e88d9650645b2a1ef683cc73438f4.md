### Title
Webhook shop-domain identity is not covered by HMAC, allowing cross-tenant spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop-domain` header — the value that downstream tenant-scoped logic keys on — is never included in the signed material, so it can be swapped freely without invalidating a legitimately-obtained signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC purely from that signable string with the app's shared `api_secret_key`: [2](#0-1) 

`Registry.process` accepts the request as authentic once this body-only HMAC checks out, and then forwards `request.shop` — taken directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — to the app's handler as the tenant identifier: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body || shop_header || topic_header)`

but what is actually enforced is:
`hmac == HMAC(secret, raw_body)`

Because the `shop-domain` header is a field acted upon (`request.shop`, passed into `WebhookMetadata`) but excluded from the signed bytes, the header can be modified independently of the signature that gates acceptance.

### Impact Explanation
Since the app's `api_secret_key` is shared across all shops using the app (it is not per-tenant), any entity that can obtain one valid `(raw_body, hmac)` pair for their own shop's webhook delivery — e.g. an unprivileged merchant who installs the app and receives an ordinary webhook for a generic/predictable topic — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will accept it as authentic and hand a `WebhookMetadata` with the attacker-chosen `shop` to the host handler. Any host logic that follows the gem's documented contract of trusting `WebhookMetadata#shop` (e.g., to write/update per-tenant records, revoke sessions, or trigger tenant-scoped side effects) can then be made to act against a shop the attacker doesn't operate — a cross-tenant identity confusion.

### Likelihood Explanation
Exploitability requires the attacker to already be able to trigger delivery of at least one webhook with a body they can reproduce byte-for-byte (trivial for topics with static or attacker-influenced bodies, e.g. `app/uninstalled`-style or empty-body events, or events whose payload the attacker's own shop controls). No access token, `client_secret`, or privileged account is needed — only ordinary merchant-level interaction with the app, which is the "unprivileged internet user" tier for a multi-tenant SaaS app.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material verified by `Utils::HmacValidator`, or otherwise cryptographically tie the accepted `shop-domain` header to the signed body (e.g., have `Request#to_signable_string` incorporate the shop/topic headers, matching what Shopify actually signs, or independently verify shop identity via a separate authenticated channel) before it is handed to the webhook handler.

### Proof of Concept
1. Register a webhook handler that scopes state by `data.shop` (per the gem's documented `WebhookMetadata` contract).
2. As an app-installing merchant ("shop-a"), receive a legitimate webhook delivery with raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(secret, B)`.
3. Replay a POST to the app's webhook endpoint with the same raw body `B` and same `H`, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks `B` against `H`; the handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"`, causing the app to perform the webhook's side effects against "shop-b" instead of "shop-a".
