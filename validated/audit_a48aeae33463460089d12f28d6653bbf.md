### Title
Orb-relay client resends its last message to any sender matching `RequestState`, bypassing the source-identity check enforced for all other messages - (File: `orb-relay-client/src/client.rs`)

### Summary
The `PollerAgent::main_loop` in the Orb-relay client blindly re-transmits its cached `last_message` whenever an incoming payload matches `self_serve::app::v1::RequestState`, and it does so *before* the `src.id != self.config.dst_id` identity check that every other inbound message type is subject to. This mirrors the `StakingManager.receive()` bug class: an unauthenticated/unbound trigger (a message "shape" rather than a validated sender) causes an automatic, state-revealing action, sidestepping the trust boundary the rest of the code enforces.

### Finding Description
In the relay poll loop: [1](#0-0) 

the flow is:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...   // <-- no src check
} else if src.id != self.config.dst_id {
    // reject unexpected source
} else {
    self.handle_message(...)                              // normal path is source-checked
}
```
Every other payload type reaching this loop is validated against `self.config.dst_id` (the expected counterpart entity id, i.e. the specific session/orb pairing) before being processed. The `RequestState` branch is carved out ahead of that check, so it executes for a payload from *any* `src`, as long as it matches the `RequestState` protobuf shape. The comment directly above `main_loop` even flags the underlying design gap: [2](#0-1) 

"We need to split auth and subscription... that will avoid multiplexing messages from different sources" — i.e., the authors themselves acknowledge that messages from sessions other than the one this client instance is bound to can arrive on the same stream, yet the `RequestState` fast-path does not re-validate which session it came from before echoing potentially session-specific state (`self.last_message`, which is whatever the Orb most recently sent to its counterpart — see `self.last_message = relay_message.clone().into();` at line 499) back onto the wire.

This is the orb-core analog to the external report's `receive()` calling `stake()` for any `HYPE` regardless of sender: a message payload's *shape* is treated as sufficient authorization to trigger a privileged/stateful action (resending the last message), instead of validating identity/binding first, exactly as the recommended fix in the report inserts a `msg.sender != systemAddress` check before allowing the state-changing effect.

### Impact Explanation
Because `RequestState` bypasses the `src.id` check, an entity that is not the bound counterpart for this relay session can cause the Orb/App client to re-emit its last message. In the self-serve signup flow this channel carries session state such as `CaptureStarted`, `CaptureTriggerTimeout`, `SignupEnded`, and `AnnounceOrbId` (mode/hardware info) — see usages in `src/plans/mod.rs`'s `proceed_with_biometric_capture` and `orb_relay_announce_orb_id`. If message multiplexing across sessions is possible on the shared relay stream (as the TODO comment implies), a party belonging to a different self-serve session could trigger disclosure of another session's last relay message/state, i.e., cross-session state bleed in the self-serve signup binding between App and Orb.

### Likelihood Explanation
Exploitability depends on whether the underlying relay transport can deliver a `RequestState`-shaped payload with an arbitrary/foreign `src` to this client (e.g., via the shared/multiplexed stream the authors' own TODO warns about, or a compromised/malicious relay). Given the code explicitly special-cases this message type ahead of the standard sender check, the likelihood is directly tied to relay-level message routing behavior rather than any additional application logic protecting this path client-side.

### Recommendation
Move the `src.id != self.config.dst_id` validation ahead of the `RequestState::matches` branch so that the "resend last message" behavior only executes for the bound counterpart entity, consistent with every other payload type:
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. Establish an Orb-relay client session A (`orb_id`, `session_id_A`).
2. From a separate, unrelated entity (or a relay path capable of delivering cross-session payloads, per the code's own TODO about multiplexing), send a payload matching `self_serve::app::v1::RequestState` to the response stream consumed by client A, with `src` not equal to `self.config.dst_id`.
3. Because the `RequestState::matches` check in `orb-relay-client/src/client.rs` lines 436-440 executes before the `src.id != self.config.dst_id` check, client A resends `self.last_message` regardless of the untrusted `src`, unlike every other message type which is rejected at line 441-445 for a mismatched source.
