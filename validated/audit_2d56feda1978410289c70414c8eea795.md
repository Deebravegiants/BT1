## Analysis

The Zivoe bug is a classic **reward-accumulator time-skip**: the contract advances its "last updated" timestamp even during periods when `totalSupply == 0`, silently discarding the rewards that should have accrued to nobody, and (worse) making already-deposited tokens permanently stuck because deposits require simultaneous `safeTransferFrom`.

The Polkadot SDK's `pallet-asset-rewards` (`substrate/frame/asset-rewards`) implements the exact same Synthetix-style "reward-per-token" streaming model, and has the same defect. [1](#0-0) 

```rust
pub(super) fn reward_per_token(pool_info: &PoolInfoFor<T>) -> Result<T::Balance, DispatchError> {
    if pool_info.total_tokens_staked.is_zero() {
        return Ok(pool_info.reward_per_token_stored);
    }
    ...
}
```

When `total_tokens_staked == 0`, `reward_per_token` correctly skips accumulating rate into `reward_per_token_stored`, but `update_pool_rewards` — called immediately afterward — unconditionally sets `last_update_block` to the current block regardless of whether any reward was actually accrued: [2](#0-1) 

```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
```

This pair is invoked from `stake`/`unstake`/`harvest_rewards` via `update_pool_and_staker_rewards`: [3](#0-2) 

Because the pallet's reward pot is pre-funded (via `deposit_reward_tokens` or a direct transfer) up front to cover `reward_rate_per_block * duration`, any block-range during which `total_tokens_staked == 0` causes the corresponding slice of reward tokens to be silently skipped — `last_update_block` jumps forward with no compensating increase to `reward_per_token_stored` — so those tokens are never credited to any staker. They remain stranded in the pool's `account` (`pool_account_id`) with no future accounting path to redistribute them, since emission going forward is computed strictly from the (rate × elapsed blocks) model, not from the actual pot balance.

Reachability requires no privileged role: any single staker can trigger the zero-stake window simply by fully unstaking (`unstake`), which is a normal unprivileged call: [4](#0-3) 

The only recovery path, `cleanup_pool`, is admin-gated and requires the pool to have **zero stakers at cleanup time**: [5](#0-4) 

If the pool has active stakers again (the normal expected state for an active incentive program), `cleanup_pool` fails with `NonEmptyPool`, so the admin cannot reclaim the stranded tokens either — they are stuck for the life of the pool.

### Title
Reward tokens are permanently stranded when a pool transitions through a zero-stakers window - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` advances `PoolInfo::last_update_block` to the current block every time `update_pool_rewards` runs, even when `total_tokens_staked == 0`. Because `reward_per_token` deliberately skips accruing the emission rate during zero-stake periods, the block range with no stakers is silently "consumed" without crediting anyone, permanently stranding the pre-funded reward tokens corresponding to that period.

### Finding Description
`reward_per_token` (lib.rs:787-810) returns the unchanged `reward_per_token_stored` whenever `total_tokens_staked.is_zero()`, which is correct in isolation (no divisor, no owner to credit). However `update_pool_rewards` (lib.rs:775-784), called right after via `update_pool_and_staker_rewards` (lib.rs:754-765), always overwrites `last_update_block` with `current_block_number()`. This means the elapsed blocks during the zero-stake window are treated as "already accounted for" going forward, even though no reward was actually distributed for them. The pool's reward pot (`pool_info.account`), which was pre-funded to cover the full `reward_rate_per_block * duration`, retains the balance meant for that skipped window, but the accounting model has no future mechanism to redistribute it — emission is computed purely as `reward_rate_per_block * elapsed_blocks / total_tokens_staked`, not from residual pot balance.

Any unprivileged staker can trigger the zero-stake window unilaterally by fully unstaking (`unstake`, lib.rs:513-560), then re-staking or waiting for another user to stake later (`stake`, lib.rs:472-502). This directly mirrors the Zivoe root cause: the timestamp/"last update" clock keeps ticking during a zero-total-supply period while the corresponding reward-per-token accrual is skipped, so already-deposited reward funds for that interval are lost to future accounting.

### Impact Explanation
Reward tokens funded into the pool's account for a zero-staker interval become permanently unclaimable by any staker. Recovery via `cleanup_pool` requires the pool to have zero stakers at cleanup time (lib.rs:697-704); if the pool subsequently regains stakers (the expected steady-state for an active incentive pool), even the pool admin cannot reclaim the stranded balance, since `cleanup_pool` errors with `NonEmptyPool`. This is a loss-of-funds / permanent-lock bug matching the classification of the original Zivoe finding (Sherlock Medium).

### Likelihood Explanation
Fully unprivileged and easily reachable: a pool with a single staker who calls `unstake` for their full amount creates a zero-stake window with no special conditions. This is a normal, expected lifecycle event (e.g., the sole staker leaving before a new one joins), not an edge case requiring adversarial setup, matching the "low probability but real and repeatable" likelihood noted by the Sherlock judges for the original issue.

### Recommendation
When `total_tokens_staked.is_zero()`, do not advance `last_update_block` in `update_pool_rewards` (mirror the early-return behavior already applied to `reward_per_token_stored`), so that the elapsed zero-stake window remains "pending" and its rewards are properly attributed once staking resumes. Alternatively, track undistributed rewards from zero-stake windows explicitly and roll them back into the pot's future emission schedule or allow admin recovery irrespective of current staker count.

### Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R`, funds `pool_info.account` up front with `R * expected_duration` reward tokens (via `deposit_reward_tokens`, lib.rs:672-688).
2. Staker A calls `stake(pool_id, X)` at block `N`.
3. At block `N+10`, staker A calls `unstake(pool_id, X, None)` for their full balance → `total_tokens_staked` becomes `0`; `reward_per_token_stored` and `last_update_block = N+10` are recorded (lib.rs:544, 780-781).
4. No one stakes for 40 blocks (block `N+50`).
5. Staker B calls `stake(pool_id, Y)` at block `N+50`. Inside `update_pool_and_staker_rewards`, `reward_per_token` is evaluated with `total_tokens_staked == 0` (staker B's stake hasn't been added to `pool_info.total_tokens_staked` yet) → returns the stored value unchanged; `update_pool_rewards` then sets `last_update_block = N+50` (lib.rs:780).
6. The `R * 40` reward tokens sitting in the pot corresponding to blocks `N+10..N+50` are never reflected in `reward_per_token_stored` and are never emitted going forward — they remain stuck in `pool_info.account` indefinitely, unclaimable by staker B or any future staker, and unrecoverable by the admin unless the pool later returns to a fully-empty state to permit `cleanup_pool`.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
