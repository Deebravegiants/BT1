### Title
Same-`assetId` batch withdrawals cause `PoaBridge.describeWithdrawal` to report identical status/txHash for two distinct withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When a single intent contains two POA-bridge withdrawals of the same `assetId` (e.g. two `nep141:usdc.omft.near` withdrawals to different destinations), `findMatchingWithdrawal` matches only by `assetId` and returns the same withdrawal record for both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` calls. This causes the SDK to report the same `(status, txHash)` for two on-chain-distinct withdrawals.

### Finding Description
The broken equality: `describeWithdrawal({index:1}).txHash` should equal the on-chain outcome of the second signed withdrawal, but instead equals `describeWithdrawal({index:0}).txHash` (the first match found in the array).

Code path:
- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns sequential `index` values per bridge route (`RouteEnum.PoaBridge`), regardless of `assetId`. Two same-token withdrawals in one intent thus become `WithdrawalIdentifier`s with `index:0` and `index:1`, both carrying the same `assetId` but different `withdrawalParams.destinationAddress`.
- `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` — it ignores `args.index` entirely.
- `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`, returning the **first** array element whose token matches, with no disambiguation by destination address, amount, or index.
- The docstring above `findMatchingWithdrawal` (`poa-bridge.ts:409-417`) explicitly acknowledges this: "matching by assetId instead of index... multiple withdrawals of the same token in a single transaction are not supported."

Attacker input: an ordinary user (or counterparty whose withdrawal params an integrator forwards) constructs/executes an intent with two POA withdrawal legs sharing the same `assetId` but different `destinationAddress`. No signature, nonce, or contract-level check on the intents contract prevents two same-token withdrawal legs in a batch; `validateWithdrawal`, `compareAddresses`, and `supports()` operate per-leg and do not check for duplicate `assetId` across legs in the batch. Nothing in `createWithdrawalIdentifiers` deduplicates or rejects same-`assetId` legs — it only tracks a per-route counter.

Exploit flow: once both withdrawals execute on-chain (two separate POA relayer transfers with two different `transfer_tx_hash` values), the integrator's watcher (`watchWithdrawal` in `withdrawal-watcher.ts:20-78`) calls `describeWithdrawal` for each `WithdrawalIdentifier`. Both calls hit the same underlying `getWithdrawalStatus` response array and `findMatchingWithdrawal` returns the same entry (typically the first) for both index 0 and index 1. The integrator then observes identical `(status:"completed", txHash)` for both legs even though the two on-chain payouts have distinct `transfer_tx_hash` values and went to different destinations.

No existing guard catches this: `assert` checks in `validateWithdrawal`/`createWithdrawalIdentifier` only validate asset support and address format per-leg; `supports()` ordering only picks the bridge, not disambiguates duplicates; the intents contract's own signature/nonce verification authorizes the batch of intents but has no concept of "distinguishing withdrawal status lookups" — that's purely an SDK-side indexing bug.

### Impact Explanation
This causes an integrator to mis-report withdrawal completion: crediting the destination of withdrawal index 1 as "completed" using withdrawal index 0's `txHash` (or vice-versa), while the true outcome of the other withdrawal is masked/duplicated. This matches the "status or hash misreport making an integrator credit or refund twice" category — a integrator watching per-leg status could, e.g., release a corresponding off-chain credit for both legs based on one on-chain confirmation, or fail to detect that one leg actually failed while reporting it as completed via the other leg's success. This is repeatable for every batch containing duplicate `assetId` POA withdrawals, and it is triggerable by an ordinary unprivileged user simply by constructing such a batch (no privileged actor needed).

### Likelihood Explanation
Precondition: a single intent/transaction must contain two (or more) POA-bridge withdrawal legs with the same `assetId`. This is easily attacker-controlled — the attacker (or a counterparty whose params the integrator forwards) only needs to include two same-token withdrawal legs with different destination addresses in one intent; nothing in `supports()`, `validateWithdrawal()`, or the batching logic in `withdrawal-watcher.ts` rejects or deduplicates this. Attacker cost is minimal (normal transaction fees), and it is fully repeatable per batch. The bug is also self-acknowledged in the code comments as an unhandled case, confirming it is not defended against elsewhere.

### Recommendation
Disambiguate withdrawals sharing an `assetId` within `findMatchingWithdrawal`/`describeWithdrawal`, e.g. by sorting both the POA API's returned withdrawals list and the batch's withdrawal params (for the same `assetId`) by amount (as the existing comment suggests) and pairing them positionally, or by tracking already-matched withdrawal records within the same `describeWithdrawal` invocation set so distinct `index`es never resolve to the same record. Until the POA API supports returning a client-supplied correlation id per withdrawal, either implement this amount-based positional matching, or explicitly reject/serialize batches containing duplicate `assetId` POA legs so the ambiguity cannot occur.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
