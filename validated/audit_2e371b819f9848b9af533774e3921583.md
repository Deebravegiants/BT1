### Title
Webhook HMAC does not bind the `shop-domain` (or `topic`) header, enabling cross-tenant webhook shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and event `topic` from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` checks only covers the raw request body. This breaks the binding *"HMAC-verified bytes == bytes acted on"*: the signature proves Shopify produced *some* body, but not that the accompanying `shop-domain`/`topic` headers are the ones Shopify actually sent with that body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then dispatches to the handler using the header-derived `shop`: [3](#0-2) 

Compare this with `Auth::Oauth::AuthQuery`, where the analogous "shop" field *is* included in the signed string: [4](#0-3) 

That asymmetry shows the intended invariant elsewhere in the gem (identity fields must be inside the HMAC-signed payload) is not honored for `Webhooks::Request`. An unprivileged internet user who has access to any single valid `(raw_body, hmac)` pair for their own shop (e.g., by owning a test store and triggering a real webhook to their own endpoint, or capturing one over network) can replay that exact body+hmac to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain: [5](#0-4) 

### Impact Explanation
Any host application relying on `WebhookMetadata#shop`/`#topic` to select which tenant's data to create/update/delete (the documented purpose of this metadata) can be tricked into applying attacker-controlled webhook payload content under a different shop's identity — i.e., cross-tenant data injection/corruption without ever possessing that shop's credentials. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High: obtaining one legitimate `(body, hmac)` pair only requires operating any Shopify dev/test store capable of receiving webhooks (no privileged access to the victim or to `api_secret_key` is needed), and header spoofing on an inbound HTTP request to the merchant app is trivial for a network-adjacent or scripted client.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`) in the signable string used for HMAC verification, not just the raw body, e.g.:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}|#{topic}|#{@raw_body}"
end
```
and verify these headers are present and match before dispatch, mirroring the pattern already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. Register a webhook handler in a host app using this gem, keyed off `WebhookMetadata#shop`.
2. As an attacker who owns `attacker.myshopify.com`, trigger any webhook event on that store; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
3. Replay the identical body and HMAC to the same app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `raw_body` is checked (`lib/shopify_api/utils/hmac_validator.rb:12-22`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler executes with `data.shop == "victim.myshopify.com"`, causing the app to process attacker-controlled payload content as if it belonged to the victim tenant.
