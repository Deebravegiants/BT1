### Title
Unbacked shielded UTXO minting via self-reported `balanceOf` on attacker-controlled ERC20 tokens - (File: `contracts/Hinkal.sol`)

### Summary
Hinkal accepts an arbitrary, unvetted `erc20TokenAddresses[i]` on every `transact()` call and verifies deposit custody solely by diffing `token.balanceOf(address(this))` before/after the transfer. Since the attacker fully controls the token contract's `balanceOf`/`transferFrom` logic, they can make the on-chain balance check report a deposit of `amountChanges[i]` tokens while transferring zero real value, producing a fully backed-looking but economically worthless shielded UTXO.

### Finding Description
The broken equality is: **real ERC20 value received by Hinkal == `amountChanges[i]`**.

In `Hinkal.transact()`, balances are snapshotted via `getBalancesForArray`, which calls `getERC20OrETHBalance(token)` → `token.balanceOf(address(this))`: [1](#0-0) 

`_internalTransact` requires the depositor to be `msg.sender` and pulls funds with `transferERC20TokenFromOrCheckETH`, which for ERC20 simply calls `safeTransferFrom`: [2](#0-1) [3](#0-2) 

Back in `transact()`, the post-transfer balance diff is compared against `amountChanges[i] + utxoAmount`: [4](#0-3) 

Nowhere in `performHinkalChecks`, `dimensionsCheck`, or `checkOnchainCreation` (all in `contracts/HinkalHelper.sol`) is `circomData.erc20TokenAddresses[i]` validated against any registry/whitelist: [5](#0-4) 

The circuit-side check (`MainEVMCircuit.circom`) only constrains the internal UTXO arithmetic (`inTotal + amountChanges === outTotal`); it has no way to attest to real-world ERC20 custody, since ZK circuits cannot observe external contract state: [6](#0-5) 

Because `balanceOf` is queried on the attacker's own deployed contract, the attacker writes `balanceOf(address(this))` to unconditionally return `oldBalance + amountChanges[i]` (independent of any `transferFrom` outcome), and writes `transferFrom`/`transfer` to return `true` without moving real value (or without even holding real value, since none is needed). The `balanceDif == amountChanges[i] + utxoAmount` check then passes trivially, and `insertCommitments` writes a valid Merkle leaf/UTXO commitment for `amountChanges[i]` units of the fake token that were never custodied by Hinkal.

None of the existing guards catch this: `performHinkalChecks` validates structure/dimensions/hashes, not token legitimacy; `verifyProof` only proves knowledge of a valid private-input arithmetic transcript, not real transfers; the on-chain slippage/balance-diff `require` is the sole custody check and is exactly the value being spoofed.

### Impact Explanation
This mints shielded value (a UTXO commitment) with zero real backing for an attacker-controlled ERC20 address — matching the Critical category "minting shielded value without backing." The attacker can repeat this for any amount and any number of "tokens" they deploy, at will, at negligible gas cost. The scenario is fully self-contained and reachable by any unprivileged EOA that can deploy a contract and call `transact()`.

The further claim that this fake UTXO can be redeemed for a *different, real* token's pooled balance requires an internal cross-token swap path. Hinkal enforces per-token balance accounting (`balanceDif` is computed and checked independently for each `erc20TokenAddresses[i]`), and cross-token value movement only happens through `_externalTransact`, which requires `externalActionMap[externalActionId]` to be a contract registered by `DEFAULT_ADMIN_ROLE` via `registerExternalAction` — an unprivileged attacker cannot register their own swap contract: [7](#0-6) [8](#0-7) 
So the "drain real funds via internal swap" extension of the exploit is not directly reachable without a pre-existing, legitimately-registered swap action and real router liquidity for the fake token (which does not exist). The confirmed, in-scope impact is the unbacked-UTXO minting itself.

### Likelihood Explanation
Trivial to execute: deploy a minimal ERC20-like contract with a `balanceOf` that ignores real transfers and a `transferFrom`/`transfer` that returns `true` unconditionally. No preconditions on protocol state, no privileged role needed, fully repeatable across arbitrary token addresses and amounts.

### Recommendation
Do not trust the deposited token's self-reported `balanceOf` as the sole proof of custody for arbitrary, unvetted ERC20 addresses. Introduce an ERC20 allowlist/registry (the `erc20TokenRegistryAddress` referenced in `IHinkal.ConstructorArgs` but apparently unused in the checked transact path) and enforce it in `performHinkalChecks`/`dimensionsCheck` so only vetted tokens can be used to mint shielded UTXOs, or otherwise cryptographically/economically bind minted UTXO value to a verified, standard-compliant token implementation.

### Proof of Concept
Foundry test plan:
1. Deploy `FakeToken` implementing `IERC20` where `balanceOf(address)` returns a value tracked by an attacker-settable state var (e.g., incremented directly by the attacker in the same tx, not by `transferFrom`), and `transferFrom`/`transfer` always return `true` without moving real balances.
2. Call `Hinkal.transact()` with `circomData.erc20TokenAddresses[0] = address(FakeToken)`, `amountChanges[0] = X`, `onChainCreation[0] = false`, a validly-generated proof for the corresponding circuit constraints (which only constrain internal arithmetic, not real custody), and `externalActionData.externalAddress = attacker`.
3. Before the call, record `oldBalance = FakeToken.balanceOf(address(Hinkal))`; have `FakeToken` set `balanceOf` to report `oldBalance + X` after `transferFrom` is invoked (regardless of actual attacker balance/allowance).
4. Assert `transact()` succeeds, `balanceDif == amountChanges[0]` inside `Hinkal.sol` passes, and a new commitment is inserted into the Merkle tree via `insertCommitments`.
5. Assert that no real ERC20 value ever left the attacker's EOA (attacker's real token holdings, e.g. actual `IERC20` balance on any real token, are unchanged; `FakeToken` never required real backing).
6. This demonstrates the equality "real ERC20 value received by Hinkal == `amountChanges[0]`" is false (0 ≠ X) while Hinkal's internal state treats it as true and mints a corresponding shielded UTXO.
