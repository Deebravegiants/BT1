### Title
Attacker-controlled Aquarius LP withdrawal bricks all valuation-dependent operations on their account, permanently shielding bad debt from liquidation and cleanup - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
A borrower who is also a liquidity provider in an Aquarius pool backing a listed LP collateral token can make their own account unliquidatable on demand: by withdrawing liquidity until the pool's value drops below the oracle's configured `min_pool_value_wad`, every strict price read for that asset fails with `InsufficientAquariusLiquidity`. Because the controller builds health factor, `min_borrow_collateral_usd`, liquidation plans, and bad-debt eligibility from strictly-resolved prices, all valuation-dependent entrypoints (`liquidate`, `clean_bad_debt`, `withdraw`, `borrow`, `repay_debt_with_collateral`, `update_account_threshold`) revert for any account holding that asset as a supply leg, while interest keeps accruing on the debt.

### Finding Description
The Aquarius LP oracle source is fail-closed on pool value. In `read`, after computing the fair LP share price, the provider computes `pool_value_wad = price_wad * total_shares / share_unit` and rejects the price entirely when it is below the configured floor: [1](#0-0) 

Pool value depends only on live reserves and total shares read fresh from the pool contract each call (`aquarius_pool_reserves_call`, `aquarius_total_shares_call`), so any LP can change the outcome between blocks by removing liquidity — the check re-validates on every read, per the design note that "a pool can be re-pointed or drained after it was attested." [2](#0-1) 

On the controller side, collateral/debt valuation is strict: an invalid required price aborts the whole operation rather than skipping the leg, so a single broken LP leg poisons the account context. [3](#0-2) 

The deployed mainnet configuration makes this reachable: `AQUAUSDC_LP` (hub 3) is priced solely from Aquarius pool `CA6GAFO…` with `min_pool_value_wad = 200_000 USD` and a single source (`independence: RequireDisjoint`, zero tolerance), so there is no fallback source when the floor is breached. [4](#0-3) 

Supply requires no price at all, so the attacker can even attach the LP leg after going underwater (subject to the position/decimal rules), choosing the feed outage as a shield: [5](#0-4) 

### Impact Explanation
While the pool stays under the floor:
- `liquidate` reverts for the account → the position cannot be unwound and interest compounds into bad debt (protocol insolvency accrues).
- `clean_bad_debt` reverts → the dust-threshold cleanup path is blocked for the same leg.
- Other suppliers of the same LP asset are also frozen: `withdraw`, `borrow`, `swap_collateral`, `repay_debt_with_collateral`, `update_account_threshold` all need the strict price and revert — a temporary freezing of their funds for the duration of the outage.

The attacker alone controls the duration (they can re-add liquidity to unbrick at will), and the cost is bounded by their existing LP share — they only need to push total pool value below 200k USD-equivalent, not own the whole pool, if other LPs' exit or market moves cooperate.

### Likelihood Explanation
Requires the attacker to be a dominant or sufficiently large LP in a listed Aquarius pool — a real capital commitment, but a normal unprivileged action (own trades on Aquarius are in-scope) with no protocol gate. No privileged role, no leaked key, no oracle dishonesty: the price is *accurately* reflecting a drained pool, and the fail-closed design converts that into an availability failure. The repo itself documents this residual risk (threat-model DoS.1) and ships a near-floor monitoring alert, confirming it is a live, reachable condition rather than a hypothetical.

### Recommendation
- For LP-sourced oracles, add a second independent source so a single drained pool cannot zero the price, or fall back to a last-known-good LP price within a bounded staleness window for liquidation/cleanup paths (risk checks for new borrows can stay strict).
- Reduce `min_pool_value_wad` so the floor can only be hit by near-total drainage, and/or price against a time-weighted reserve rather than the spot reserve.
- Allow liquidation and `clean_bad_debt` to skip an unpriceable *supply* leg (seize nothing for it) rather than aborting the entire plan, so a poisoned collateral leg cannot shield debt.

### Proof of Concept
1. Attacker supplies `AQUAUSDC_LP` as collateral on a spoke and borrows a liquid asset to max LTV (or becomes underwater via price movement).
2. Attacker calls `withdraw_liquidity` on Aquarius pool `CA6GAFOJCW4MGQQBUCQUSA3CLIH25G4SNKB2JHYKZCVWZTNW5VXMSC4O`, removing reserves until `fair_price * total_shares / 1e7 < 200_000e18`.
3. Any subsequent `liquidate(liquidator, attacker, debt_asset, amount)`, `clean_bad_debt(attacker)`, or victim `withdraw` touching the LP leg resolves the oracle → `aquarius::read` returns `Err(InsufficientAquariusLiquidity)` → the strict price context fails → the transaction reverts.
4. Debt keeps accruing via `update_indexes` (index sync needs no price); the account remains unliquidatable until the attacker (or arbitrageurs) restore pool value. Confirmed by the unit test showing a pool one wei under the floor is refused: `test_a_stable_pool_one_wei_under_its_liquidity_floor_is_refused`. [6](#0-5)

#[test]
fn test_a_stable_pool_one_wei_under_its_liquidity_floor_is_refused() {
    let env = Env::default();
    env.ledger().set_timestamp(1_000_000);
    with_contract(&env, || {
        let (key, mut lp, pool_value_wad) = priced_stable_lp(&env);
        lp.min_pool_value_wad = pool_value_wad + 1;

        let mut session = Session::new(&env);
        assert_eq!(
            crate::providers::aquarius::read(&mut session, &key, &lp, 7, 0, true).err(),
            Some(OracleError::InsufficientAquariusLiquidity)
        );
    });
}
