### Title
Attacker-controlled octal wavelength parameter in QR-code signup extensions causes `assert_eq!` panic, crashing the orb-core process and blocking all signups - (File: `src/plans/biometric_capture/focus_sweep.rs`, `src/plans/biometric_capture/mirror_sweep.rs`, `src/plans/biometric_capture/overcapture.rs`)

### Summary
An unauthenticated person presenting a QR code during a signup session (the "user QR-code" scanning step, which happens before identity verification is complete) can supply a signup-extension parameter that is parsed as an octal `u8` without validating its numeric range. Downstream code formats that value as a fixed-width 3-bit binary string and asserts the resulting string length is exactly 3 characters. Because the octal string is not restricted to values ≤ 7 (only to individual octal digits), a value such as `77` (octal) = 63 (decimal) produces a 6-character binary string, causing the `assert_eq!` to fail and the process to panic. This mirrors the reported ERC20.sol bug class: a controller-supplied parameter that passes creation-time validation but causes a later, unconditional revert/panic that blocks the entire subsequent workflow (here, bond distribution; in orb-core, the signup/biometric-capture pipeline for the current and any subsequent user).

### Finding Description
User QR-codes are parsed by `qr_scan::user::Data::try_parse`, which — when built with the `internal-data-acquisition` feature — matches the `QR_CODE_SIGNUP_EXTENSION` regex. This regex allows an almost unconstrained `parameters` capture group: `[a-z0-9:]+`, with no bound on numeric magnitude [1](#0-0) . This captured string is stored as `SignupExtensionConfig.parameters` [2](#0-1)  and flows unchanged into the biometric-capture extension plans that are selected based on `mode` (`FocusSweepExtension`, `MirrorSweepExtension`, `Overcapture`) [3](#0-2) .

In `focus_sweep.rs` and `mirror_sweep.rs`, the parameter is parsed with `u8::from_str_radix(parameter, 8).ok().unwrap_or(1)` — i.e., interpreted as an octal *numeral*, not restricted to 3-bit values — and passed to `SweepConfiguration::new`: [4](#0-3) 

`parse_configuration_value` then formats the u8 with a minimum width of 3 binary digits and asserts the resulting string is exactly 3 characters long: [5](#0-4) 

The identical pattern exists in `mirror_sweep.rs`: [6](#0-5) [7](#0-6) 

And in `overcapture.rs`, where the wavelength sub-field of the `wavelength:duration` parameter string is parsed the same way via `parse_u8_octal`: [8](#0-7) [9](#0-8) 

`format!("{value:0>3b}")` only guarantees a *minimum* width of 3; for any value ≥ 8 (e.g., decimal 63, i.e. octal string `"77"`), the binary representation is longer than 3 characters (`"111111"`), so `binary_repr.chars().count() == 3` is false and the `assert_eq!` panics. Because `u8::from_str_radix(_, 8)` only rejects strings containing non-octal digits (8, 9, or other characters) — it happily accepts multi-digit octal strings whose *value* exceeds 7 — the QR-code regex's permissive `[a-z0-9:]+` capture lets an attacker supply exactly such a string (e.g., `"77"`, `"17"`, `"27"`, etc.).

This is directly analogous to the reported bug class: a value accepted at "creation time" (QR-code scan/parse, which succeeds) later causes an unconditional panic/revert in a downstream, unvalidated arithmetic/formatting step (`faceValueRemaining` in the original report vs. `parse_configuration_value`/`parse_wavelength_configuration` here), which then blocks the entire subsequent pipeline (`distributeBonds` in the original report vs. the biometric-capture/signup flow and — because Rust panics unwind and, depending on panic-handling configuration, can abort the whole orb-core process — potentially the entire orb).

### Impact Explanation
A panic triggered during the biometric-capture phase of a signup, driven entirely by data presented by the *unauthenticated* person currently in front of the orb (via a crafted QR code), can crash or abort the running signup task/process before biometric data is properly captured, disrupted, or before liveness/fraud checks complete for that session. If the panic propagates and terminates the orb-core process (a realistic outcome for an unhandled `assert_eq!` panic in an async task depending on the panic hook/unwind behavior configured for the binary), this blocks signup capability for all subsequent users of that orb until the process is restarted — a denial-of-service on identity signup, the same "trapped" impact pattern described in the original report (all future `distributeBonds` calls always reverting).

### Likelihood Explanation
This requires the `internal-data-acquisition` Cargo feature to be enabled (gating the entire signup-extension QR-code parsing path) and, per code comments, the extension features appear intended for controlled data-acquisition sessions rather than general public signup flow, so likelihood depends on whether that feature is compiled into production orb-core builds. If it is enabled, exploitation only requires presenting a single crafted QR code string, with no special privileges, so likelihood is otherwise high given the very permissive parameter regex.

### Recommendation
Validate the parsed octal wavelength parameter (and any other user-controlled numeric extension parameter) at parse time so that only values in the valid 3-bit range (0–7) are accepted; reject or clamp out-of-range values instead of relying on an `assert_eq!` that can panic on attacker-controlled input. Replace the `assert_eq!` panics in `parse_configuration_value` (`focus_sweep.rs`, `mirror_sweep.rs`) and `parse_wavelength_configuration` (`overcapture.rs`) with graceful error handling (e.g., return a `Result`/fall back to a safe default) so malformed QR-code parameters cannot crash the signup pipeline. Long term, add fuzz/property tests (as recommended in the original report for Echidna/Manticore) covering all `SignupExtensionConfig.parameters` parsing paths reachable from QR-code input.

### Proof of Concept
1. Build orb-core with the `internal-data-acquisition` feature enabled.
2. Present a QR code matching `QR_CODE_SIGNUP_EXTENSION` with a mode of `focus_sweep`/`mirror_sweep`/`overcapture` and a parameters field containing an octal string whose decimal value exceeds 7, e.g.:
   `userid:12345678-1234-1234-1234-123456789012:1::data_acquisition_mode_focus_sweep:77::`
3. `Data::from_signup_extension` accepts this and stores `parameters = Some("77")` [10](#0-9) .
4. When the focus-sweep extension plan is constructed, `u8::from_str_radix("77", 8)` succeeds, yielding `63u8` [11](#0-10) .
5. `SweepConfiguration::new(63)` calls `parse_configuration_value(63)`, producing `format!("{63:0>3b}")` = `"111111"` (6 chars), and `assert_eq!(6, 3, ...)` panics [5](#0-4) , crashing the task/process during signup.

impl From<biometric_capture::Plan> for Plan {
    fn from(biometric_capture: biometric_capture::Plan) -> Self {
        let config = biometric_capture
            .signup_extension_config
            .as_ref()
            .and_then(|config| config.parameters.as_ref());
        let (wavelength_parameter, duration_parameter) =
            config.map_or((1, Duration::from_millis(DEFAULT_OVERCAPTURE_DURATION)), |parameters| {
                parameters.split_once(':').map_or(
                    (
                        parse_u8_octal(parameters, 1),
                        Duration::from_millis(DEFAULT_OVERCAPTURE_DURATION),
                    ),
                    |(wavelength, duration)| {
                        (
                            parse_u8_octal(wavelength, 1),
                            parse_duration(duration, DEFAULT_OVERCAPTURE_DURATION),
                        )
                    },
                )
            });

    fn parse_wavelength_configuration(configuration_value: u8) -> VecDeque<IrLed> {
        let binary_repr = format!("{configuration_value:0>3b}");
        assert_eq!(
            binary_repr.chars().count(),
            3,
            "Overcapture wavelength parameter needs to be octal (<=3 bit)!"

        let mut wavelength_vec = VecDeque::new();
        for (n, c) in binary_repr.char_indices() {
            if c == '1' {
                wavelength_vec.push_front(WAVELENGTH_LUT[n]);
            }
        }
        wavelength_vec
    }
}

fn parse_u8_octal(src: &str, default: u8) -> u8 {
    u8::from_str_radix(src, 8).unwrap_or(default)
