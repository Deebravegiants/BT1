Unbounded-precision Uniswap V4 spot-price venue pricing lets an unprivileged intent submitter extract solver funds via reserve/price manipulation, with the only defense (`checkPriceGuard`) optional and operator-configurable - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
`FXFiller`, Hyperbridge's Simplex intent solver, prices "curveless" cross-asset order legs directly off the live spot price of a Uniswap V4 pool (`sqrtPriceX96`/tick) rather than a curve, and uses that single manipulable number to compute how many output tokens to hand a counterparty for a submitted intent order. This is structurally the same bug class as the reported TGAI reserve-manipulation attack: a spot AMM price is read and trusted as ground truth for a value calculation that pays out real funds, and the only sanity check on that price (`checkPriceGuard`/`maxDeviationBps`) is optional per pair/chain and can be left unconfigured ("guard is optional").

### Finding Description
`resolveLegRates` prices a curveless leg by calling `venueUsdPrice(chain, token1)`, which resolves through `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which returns the raw pool mid derived from `sdkPool.token0Price`/`token1Price` (i.e., directly from `sqrtPriceX96`) with no TWAP, no size/impact adjustment, and no fee-tier correction: [1](#0-0) [2](#0-1) 

`UniswapV4LiquidityState.refresh()` reads `getSlot0`/`getLiquidity` live via `StateView` immediately before pricing/withdrawal, so the price used is whatever the pool's current tick is at read time: [3](#0-2) 

The only mitigation is `checkPriceGuard`/`referenceRate`, which compares the venue quote to a static `referencePrice` within `maxDeviationBps`. This guard is explicitly optional per-position: if the operator does not set `referencePrice`/`maxDeviationBps`, the pool quote is used unguarded, as confirmed by the test "sizes unguarded when no reference is configured (guard is optional)": [4](#0-3) [5](#0-4) 

The venue-pricing docs themselves acknowledge the price is a raw mid with no execution-cost or impact term applied: "`computeDirectPoolPriceUsd` returns the raw pool mid derived from `sqrtPriceX96`... there is no size or impact term... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost": [6](#0-5) 

This pricing feeds directly into `calculateProfitability`/`computeLegPolicyOutput`, which determines the real token amount the solver pays out for the order's fill, i.e. an unprivileged order submitter's intent is priced from a value an attacker (using the exact reserve-manipulation technique in the report: large swap or flash-loan-funded swap against the referenced Uniswap V4 pool) can move within the same evaluation window.

### Impact Explanation
If an attacker manipulates the referenced Uniswap V4 pool's spot price (analogous to the TGAI attack's `sync()`-based reserve injection/flash-loan swap) immediately before or during a solver's pricing evaluation of an unguarded pair, the solver will size and pay out an order at the manipulated rate. Because `resolveLegRates` computes `rate = 1 / venueUsd` and passes it straight into `computeLegPolicyOutput`, a favorably-skewed quote directly overpays the attacker in real tokens the solver holds/funds via LP withdrawal — concrete theft of solver funds, matching the report's "reserve manipulation attack" bug class and its "unauthorized value extraction from a DEX-integrated protocol" outcome.

### Likelihood Explanation
Reachable by a fully unprivileged intent submitter: any order routed to a curveless pair backed only by `[vault.uniswapV4]` triggers this pricing path with no special permission. Exploitability is conditioned on an operator configuration gap — pairs with no `referencePrice`/`maxDeviationBps` guard are exposed unconditionally, and pairs that do configure a guard are only bounded by a static deviation band, not an execution-cost-aware check, so a manipulation within the configured band still succeeds. Given that the guard is explicitly documented and tested as "optional," at least some deployed fillers can reasonably be expected to run pairs without it.

### Recommendation
- Make `referencePrice`/`maxDeviationBps` mandatory for any Uniswap-V4-venue-priced pair rather than optional, or require a TWAP/observation-window price instead of the instantaneous `sqrtPriceX96` mid.
- Apply the pool's own fee tier and a size/impact term when deriving the price used for `computeLegPolicyOutput`, not just a static-deviation check.
- Consider requiring same-block/flash-loan resistance (e.g., minimum block-age of the price sample, or cross-referencing multiple independent pools/oracles) before trusting a single V4 pool's spot price for payout sizing.

### Proof of Concept
1. Operator configures a curveless pair (e.g., USDC/EXOTIC) priced solely via `[vault.uniswapV4]` with no `referencePrice`/`maxDeviationBps` set (an explicitly supported, tested configuration per `fx.price-guard.test.ts` "sizes unguarded when no reference is configured").
2. Attacker performs a large swap (optionally flash-loan funded, as in the TGAI report) against the referenced Uniswap V4 pool to shift `sqrtPriceX96`/tick so that `computeDirectPoolPriceUsd` returns a price favorable to the attacker's upcoming order.
3. Attacker submits an intent order matching that pair; `FXFiller.calculateProfitability` → `resolveLegRates` reads the manipulated live pool state via `UniswapV4LiquidityState.refresh()` and computes `venueRate` from it, unguarded.
4. `computeLegPolicyOutput` sizes the solver's payout from this manipulated rate; the fill executes and pays the attacker more than the fair-value amount.
5. Attacker reverses the pool manipulation (closing the swap/repaying the flash loan), keeping the excess extracted from the solver — the same profit mechanic as the reported PancakeSwap V2 reserve-manipulation attack, transplanted onto Hyperbridge's Simplex venue-pricing path.

```typescript
	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
