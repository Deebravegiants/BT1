### Title
Inconsistent mid-signup freezing of `ignore_user_centric_signups` causes backend deduplication (`enroll_user`) to be bypassed - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::do_signup` snapshots most `Config` fields once at the start of a signup session, but the decision of whether to invoke the backend enrollment/dedup call is instead determined by re-reading the live, mutable `orb.config` at the moment of the decision, well after biometric capture and pipeline processing have completed. If the backend pushes a `Config` update (via the periodic `Config::download_and_store`) while a signup is in flight, the orb evaluates the enrollment-skip decision against a value that never applied at the start of that signup, producing an inconsistent state for a single signup session.

### Finding Description
At the top of `do_signup`, the config used for network/version/self-serve behavior is destructured and pinned once for the duration of the signup: [2](#0-1) 

Later in the very same function, after biometric capture, the biometric pipeline, and fraud checks have already run, the code decides whether to call the real backend enrollment (`enroll_user`, which performs `signup_post`/`signup_poll` and is the only place where backend-side "Backend duplicates" / "Backend inflight matches" checks occur) by re-locking the config and reading a fresh, live value instead of reusing the value pinned at the top of the function: [3](#0-2) 

```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    // trust local pipeline result; enroll_user() is never called
} else {
    // calls enroll_user(), which is the only backend enrollment/dedup entry point
};
```

`orb.config` is a shared `Arc<Mutex<Config>>` that is asynchronously overwritten by the backend config-refresh task via `Config::download_and_store`: [4](#0-3) 

Because the biometric capture, biometric pipeline and (stripped) fraud checks between the two config reads can take on the order of tens of seconds, a config update landing in that window changes the effective value of `ignore_user_centric_signups` mid-signup, even though every other timing-sensitive config value (`self_serve`, `pcp_v3`, relay timeouts, `operator_qr_expiration_time`) was deliberately frozen at the start of the same function. This is exactly the "drawing parameter isolation" violation described in the reference report: some session parameters are frozen for the transaction/session, one is not, creating an inconsistent state within a single signup.

### Impact Explanation
If a signup starts while `ignore_user_centric_signups` is `false` and the config is updated mid-signup to keep it `false` (or toggles favorably from the attacker's perspective), a `user_centric_signup=true` request skips the call to `enroll_user` entirely. `enroll_user` is the only code path that talks to `signup_post`/`signup_poll`, which is where backend-side duplicate/inflight-match detection happens (see the explicit "Backend duplicates" / "Backend inflight matches" comment in `enroll_user.rs`). Skipping it means the orb locally reports `success = true` based solely on the on-device pipeline result and the (FOSS-stripped) fraud-check outcome, without the backend ever getting a chance to reject the signup as a duplicate/misattributed registration. This is a concrete cross-session state-bleed/dedup-bypass risk: the same biometric identity could be locally accepted as a successful, distinct signup multiple times without backend-side registration/dedup ever executing, because the enrollment-skip decision is not pinned to the config that was authoritative when the signup (and its `user_centric_signup` flag from the QR scan) began.

### Likelihood Explanation
Exploitability depends on the config value changing during the specific window between `do_signup`'s initial config snapshot and the later `orb.config.lock().await.ignore_user_centric_signups` read — a window that spans biometric capture and the full pipeline (non-trivial duration). This is a timing-dependent race rather than a directly attacker-triggerable primitive, so likelihood is moderate: it requires a config refresh to land during an in-progress signup, which happens routinely given the periodic background config-download task, but the resulting condition (skipping `enroll_user`) also depends on the `user_centric_signup` flag reported by the user's own QR/app data.

### Recommendation
Read `ignore_user_centric_signups` once, together with the other signup-session parameters already destructured at the top of `do_signup` (lines 497-506), and use that single pinned snapshot for the later enrollment-skip decision at line 639, instead of re-locking `orb.config` at the point of use. This ensures every parameter that affects the outcome of a given signup session is frozen consistently for that session's entire lifetime, matching the isolation already applied to `self_serve`, `pcp_v3`, and `operator_qr_expiration_time`.

### Proof of Concept
1. Start a signup where `qr_codes.user_data.user_centric_signup == true` and the orb's current in-memory `Config.ignore_user_centric_signups == true` (so the initial semantics expect a full backend `enroll_user` call).
2. During the multi-second window between the `do_signup` config snapshot (`src/plans/mod.rs:497-506`) and reaching the branch at `src/plans/mod.rs:639` — i.e., while biometric capture/pipeline is running — trigger (or wait for) a backend config refresh via `Config::download_and_store` (`src/config.rs:357-368`) that sets `ignore_user_centric_signups = false`.
3. Observe that `do_signup` now takes the branch that skips `enroll_user` entirely (`src/plans/mod.rs:639-645`), so no `signup_post`/`signup_poll` call is ever made, and `result.success` is set to `true` purely from the local `signup_reason`, with no backend duplicate/inflight-match check performed for that signup.
