## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop spoofing / cross-tenant webhook attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by verifying an HMAC computed only over the raw request body, but the `shop` identifier that the rest of the library treats as the authenticated tenant for that webhook is taken from an HTTP header that is never included in the signed material. This breaks the equality `shop bound by HMAC == shop trusted by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string` (the body) against the secret, and nothing else: [3](#0-2) 

`Registry.process` only checks that this body-only HMAC validates, then forwards `request.shop` straight into `WebhookMetadata` and on to the app's handler as the authoritative tenant identifier for the webhook: [4](#0-3) 

Because `shop` is never part of the signed string, any request whose body carries a valid HMAC for the app's secret will pass validation regardless of what `shop` header accompanies it. An attacker who can obtain one valid `(raw_body, hmac)` pair signed by the app's own secret — e.g., by installing the app on their own shop and receiving one legitimate webhook delivery from Shopify — can resend that exact body to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because it never inspects the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) shop, even though the payload actually originated from the attacker's own store.

### Impact Explanation
Apps that use this gem's documented webhook flow use `WebhookMetadata#shop` as the tenant key for looking up sessions, writing records, or authorizing per-shop actions in response to a webhook. Because the shop value is unauthenticated relative to the HMAC, an attacker-controlled body can be attributed to an arbitrary victim shop, causing cross-tenant data confusion/corruption in the host app — this matches the "cross-tenant access" critical-impact category, since a party who only has legitimate access to their own tenant can cause the library to assert a different, victim tenant's identity for attacker-supplied webhook data.

### Likelihood Explanation
Likelihood is high for any merchant/attacker who can install the app (a normal, low-privilege action) and receive at least one real webhook for their own shop (webhooks fire automatically on ordinary store events such as `app/uninstalled`, `orders/create`, etc.). No access to the app's `client_secret`, no TLS interception, and no privileged account are required — only the ability to replay an HTTP request with a modified header, which is standard "unprivileged internet user" capability once a valid signed body is captured.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the claimed shop to the verified payload, so that `Utils::HmacValidator.validate` fails whenever the `shop` header does not match the shop the signature was actually generated for. At minimum, `Registry.process` should not trust `request.shop` for tenant attribution unless it has been verified as part of the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, causing Shopify to deliver a legitimately signed webhook `POST` to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)`.
3. Attacker sends a new request to the same webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only [3](#0-2)  and it matches `H`, so validation succeeds.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [5](#0-4)  and invokes the app's handler as if the (attacker-controlled) payload came from the victim shop.
