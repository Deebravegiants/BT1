Found the analog. `Webhooks::Request` binds the HMAC (`hmac`) only to `@raw_body` via `to_signable_string`, while the `shop` attribute that the gem hands to application handlers as the tenant identifier is read straight from the unauthenticated `x-shopify-shop-domain` header and is never covered by that HMAC.

### Title
Webhook `shop` identity is taken from an HMAC-unverified header, breaking the tenant binding for webhook handlers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by HMAC-checking the request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the trusted tenant identity.

### Finding Description
`Webhooks::Registry.process` validates authenticity with `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is derived only from the `hmac-sha256`/`x-shopify-hmac-sha256` header [3](#0-2) . The `shop` attribute, however, is read directly from the `shop-domain`/`x-shopify-shop-domain` header and is never included in the signable string nor otherwise validated against `ShopValidator` [4](#0-3) . `Registry.process` then passes this unverified `request.shop` straight into the `WebhookMetadata` object delivered to the app's handler as the authoritative tenant identifier [1](#0-0) .

This breaks the intended binding: `bytes verified (raw_body via HMAC) != bytes/headers acted on (shop-domain header)`. Since the HMAC only proves the request body wasn't tampered with by someone lacking `api_secret_key`, it does **not** prove which shop the body actually belongs to — the `shop-domain` header can be set to any value independent of the HMAC-signed payload.

### Impact Explanation
Any client capable of producing (or replaying) a validly-HMAC'd webhook body for shop A (e.g., a merchant of a shop they legitimately control, who can generate real webhook traffic for their own store and capture the raw body + HMAC) can resend that exact request to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different tenant shop B. The HMAC check still passes (it only checks the body), and the gem reports `WebhookMetadata#shop == "shop-b.myshopify.com"` to the app's handler. If the host application trusts this `shop` field to key data writes, look up per-tenant credentials, or attribute the event (a common and directly encouraged usage per the gem's own `WebhookMetadata` contract), this results in cross-tenant data confusion/write using another merchant's identity — a cross-tenant access primitive, driven entirely by this gem's contract that `request.shop` is the verified tenant for a body that passed `HmacValidator.validate`.

### Likelihood Explanation
Reaching this requires only an unprivileged actor able to send an HTTP POST to the app's public webhook endpoint with a captured/legitimate HMAC+body pair (trivially available to any merchant using the app, since Shopify signs every webhook it sends to that merchant's own shop) and a forged `shop-domain` header — no `api_secret_key`, access token, or privileged account is needed. The only prerequisite is possession of one genuine (raw_body, hmac) pair for any shop, which any installed merchant naturally receives.

### Recommendation
Include the shop domain in the HMAC-covered signable content (or otherwise independently verify `shop-domain` came from Shopify, e.g., by validating it against the topic/webhook registration state and requiring TLS client verification), and/or sanitize `request.shop` with `Utils::ShopValidator` and cross-check it against the shop associated with the session/registration the webhook was registered under, rather than trusting an unauthenticated header value name-for-name as the tenant identity handed to `WebhookMetadata`.

### Proof of Concept
1. App receives a legitimate Shopify webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`, computed and sent by Shopify itself).
2. Attacker (a user of `shop-a`, or anyone who can observe/capture this traffic) replays the exact same `B`/`H` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {... "x-shopify-hmac-sha256" => H, "x-shopify-shop-domain" => "shop-b.myshopify.com" ...})` is constructed; `hmac` and `to_signable_string` are unaffected by the spoofed shop header [3](#0-2) .
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against `H` [2](#0-1) .
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: parsed_body, ...)` [5](#0-4) , causing the app to process shop A's webhook payload under shop B's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
