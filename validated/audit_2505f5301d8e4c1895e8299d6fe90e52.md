### Title
`VerifyRequestJWT` does not enforce `IssuedAt` (`iat`) being before `ExpiresAt` (`exp`) - ([File: core/utils/jwt.go])

### Summary
`utils.VerifyRequestJWT` validates several relationships between the `iat` and `exp` claims of a request-signing JWT, but never checks that `iat` actually precedes `exp`. This mirrors the `RCFactory.createMarket()` bug class: a sequence of timestamps that must be monotonically ordered for the function to behave correctly is only partially checked, allowing out-of-order values to slip through.

### Finding Description
`VerifyRequestJWT` performs these checks on the verified claims:
- `jti`, `exp`, and `iat` must be present. [1](#0-0) 
- `iat` must not be further in the future than `now + issuedAtTolerance` (default 5 minutes). [2](#0-1) 
- The lifetime `duration := exp - iat` must not exceed `maxExpiryDuration` (default 5 minutes). [3](#0-2) 

There is no check that `duration >= 0`, i.e. that `iat` occurs before `exp`. If a caller supplies `iat` after `exp` (e.g. `iat = now+4m`, `exp = now+1m`), `duration` is negative and the guard `duration > maxExpiryDuration` is trivially false, so the "lifetime exceeds max" branch is skipped even though the claims are logically inverted. The underlying `golang-jwt/jwt/v5` library (invoked via `jwt.ParseWithClaims`) does validate `exp` against wall-clock time, and by default does **not** validate `iat` against `exp` at all, so nothing else in the call chain catches this ordering violation. [4](#0-3) 

This function is used to authenticate unprivileged, internet-facing requests — e.g. the CRE gateway's workflow/HTTP-trigger handlers call `VerifyRequestJWT` to authenticate externally supplied JSON-RPC requests before dispatching them to workflow capabilities. [5](#0-4) 

The project's own test suite documents exactly the two checks that exist (future `iat` tolerance, and max lifetime) but has no test asserting rejection of `iat > exp`, confirming the gap is unintentional/unnoticed. [6](#0-5) 

### Impact Explanation
The comparable bug in `RCFactory.createMarket()` allowed a market's `OPEN` → `LOCKED` → `WITHDRAW` state machine to be created out of order, breaking invariants the rest of the system relied on. Here, the analogous invariant is "a token's validity window (`iat`→`exp`) must be non-negative," which the intended `maxJWTExpiryDuration` control silently fails to enforce for inverted claims. In practice, exploitability is constrained because `exp` is still independently checked against the current time by the JWT library, so a token can't be replayed once `exp` has actually passed — bounding the effective damage. However, this is a genuine logic defect in a security-relevant validation function: the "reduce the gap between `iat` and `exp`" invariant that other code may rely on (e.g. any future logic that trusts `duration` as a non-negative freshness/TTL value, or logs/audits based on `iat`/`exp` ordering) can be silently bypassed with malformed but signature-valid claims.

### Likelihood Explanation
Low-to-moderate. The JWT is attacker/client-supplied and only requires a valid signature over attacker-chosen claims (the attacker controls `iat`/`exp` in the payload before signing), so producing an inverted-claims token requires no special privilege — just a valid signing key for the request (which the token issuer already possesses per protocol). The actual security impact is limited today because expiry-vs-now is independently enforced, but this is a fragile situation created only by that side effect rather than explicit validation.

### Recommendation
Add an explicit ordering check in `VerifyRequestJWT`, immediately alongside the existing `iat`/`exp` presence and tolerance checks:
```go
if verifiedClaims.ExpiresAt.Before(verifiedClaims.IssuedAt.Time) {
    return nil, gethcommon.Address{}, errors.New("expiresAt (exp) must not be before issuedAt (iat)")
}
```
This closes the gap and makes the `maxExpiryDuration` check meaningful for all claim combinations, consistent with the ordering enforcement recommended (and implemented) for the original `RCFactory.createMarket()` finding.

### Proof of Concept
1. Craft `JWTClaims` with `IssuedAt = now + 4m` (within the default 5-minute `issuedAtTolerance`) and `ExpiresAt = now + 1m` (still in the future, so not "expired").
2. Sign with `SigningMethodEth` using a valid private key, as in the existing test harness. [7](#0-6) 
3. Call `VerifyRequestJWT(tokenString, req)`.
4. Observe: `verifiedClaims.IssuedAt.After(now.Add(tolerance))` is false (passes), `duration := ExpiresAt - IssuedAt` is negative so `duration > maxExpiryDuration` is false (passes), and the underlying library does not reject `exp > now`. The token is accepted despite `iat > exp`, an ordering the max-lifetime control was implicitly assumed to prevent. [8](#0-7)
