**Analysis:**

The premise that `expect_write_op_iter()` "matching purely on `StateKey`" causes a decomposition error for resource-group writes doesn't hold up against how resource groups are modeled throughout the Aptos VM/BlockSTM stack, not just in the sharded executor.

Key facts:

1. Resource groups are addressed by a single group-level `StateKey` everywhere in the system — reads, writes, dependency analysis (`StorageLocation::Specific(StateKey)`), and the final committed write set all operate at group granularity, not per-tag/per-field granularity. [1](#0-0)  This is consistent even for non-sharded execution.

2. By the time `CrossShardCommitSender::send_remote_update_for_success` runs (in the `on_transaction_committed` hook), the `TransactionOutput` has already gone through materialization, where `resource_group_write_set` entries are finalized and fully serialized into a single blob per group `StateKey` via `serialize_groups`/`materialize_output`. [2](#0-1) [3](#0-2)  So the `WriteOp` iterated by `expect_write_op_iter()` for a group key is the complete, correctly up-to-date serialized group contents (including the owner field), not a stale/partial bundled snapshot. [4](#0-3) 

3. `CrossShardCommitSender::send_remote_update_for_success` forwards this WriteOp verbatim, keyed by the same `StateKey`, to shards whose dependency edges reference that exact key — dependency edges themselves are also derived from `StorageLocation`/`StateKey`-based read/write hints, so the granularity of dependency tracking matches the granularity of the forwarded write. [5](#0-4) 

4. Because the whole group blob is forwarded atomically as one `WriteOp` for one `StateKey`, there is no mechanism by which an individual sub-field (e.g., an Object's owner field within the group) could be split off, partially applied, or replaced with a stale value independent of the rest of the group — the receiving shard's `CrossShardStateView::set_value` stores exactly the same fully-materialized value a non-sharded execution would have produced for that state key. [6](#0-5) 

There is no code path here that decomposes group writes "per dependent edge" incorrectly, and no unprivileged input can make this code treat a resource-group state key differently from how the rest of the VM (including non-sharded execution) treats it. The finding's premise is not supported by the actual data flow.
