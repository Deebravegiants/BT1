### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `topic`, `shop`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` — the value that `HmacValidator` actually verifies — only returns the raw request body. Any unprivileged internet user who can obtain one genuine `(body, hmac)` pair (e.g. by installing the app on their own trial/dev shop and receiving a real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `Utils::HmacValidator.validate` will still report success because it never inspects those headers, and `Webhooks::Registry.process` will pass the attacker-chosen `shop`/`topic` straight to the registered handler.

### Finding Description
The HMAC binding that the rest of the gem relies on (`Utils::HmacValidator.validate`) is computed purely over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` then trusts these header-derived fields to authenticate/route the event: [3](#0-2) 

The broken identity binding, expressed as an equality that the library should enforce but does not:
`hmac(secret, raw_body) == received_hmac` is verified, but there is no check that `shop_header == shop_that_the_(body, hmac)_pair_was_actually_issued_for`. Because `shop` (and `topic`) are outside the signed material, they can be freely rewritten by anyone who can present any valid `(body, hmac)` pair for the same shared `api_secret_key` — including a pair legitimately issued to the attacker's own shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), one of the accepted High-severity impacts: an attacker who is a legitimate, unprivileged merchant/installer of the app can forge webhook deliveries that the app will process as if they originated from a different shop or a different topic than the one actually authenticated by Shopify. Depending on the handler logic, this can lead to injecting attacker-controlled data into another merchant's account state, triggering privileged handler logic for a shop the attacker does not own, or corrupting per-shop data isolation — all without ever needing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
The prerequisite is low-effort for any developer building on the Shopify platform: create/own a shop that installs the target app (or observe one legitimately delivered webhook via any means available to the app's own infrastructure/logs the attacker can influence), capture one valid `(raw_body, X-Shopify-Hmac-Sha256)` pair, then replay it against the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header. No knowledge of `api_secret_key` or any merchant's access token is required.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the raw body before verification), or at minimum document explicitly that host applications must independently corroborate `request.shop`/`request.topic` (e.g., against the session/shop that separately received the webhook subscription) before trusting them, since `HmacValidator.validate` does not protect these header values today.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; Shopify sends a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
2. Attacker resends the identical request to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or changes `X-Shopify-Topic` to a more sensitive topic that shares the same body shape, e.g. `{}`).
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and compares it to `H` — this still matches because `to_signable_string` never looked at the headers.
4. `Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: <attacker-chosen>, ...)`, and the handler acts on behalf of `victim.myshopify.com` even though Shopify never issued this webhook for that shop.
