Audit Report

## Title
`ValidateGetSecretsRequest` wrongfully rejects a `GetSecrets` batch that is exactly at `MaxBatchSize` - (File: `core/capabilities/vault/validator.go`)

## Summary
`RequestValidator.ValidateGetSecretsRequest` in `core/capabilities/vault/validator.go` uses `len(request.Requests) >= vaulttypes.MaxBatchSize` instead of `>`, causing a legitimate batch of exactly `MaxBatchSize` (10) `GetSecrets` requests to be rejected with `"request batch size exceeds maximum of %d"`. This is an off-by-one boundary bug inconsistent with the rest of the codebase's limiters.

## Finding Description
`vaulttypes.MaxBatchSize` is defined as "the maximum number of secrets that can be created/updated/deleted in a single request" [1](#0-0) , which by definition means a batch equal to this value should be allowed. However, `ValidateGetSecretsRequest` checks `if len(request.Requests) >= vaulttypes.MaxBatchSize` and rejects the request in that case [2](#0-1) , meaning a batch containing exactly `MaxBatchSize` items is wrongly rejected as exceeding the maximum.

This is inconsistent with every other bound-based limiter in the same package, which use `limits.BoundLimiter.Check`-style semantics that reject only when the value is strictly greater than the bound (`n > bound`), confirmed by the pattern in `ownerOverrideLimiter.Check` and by write-request validators such as `MaxIdentifierOwnerLengthLimiter.Check`/`MaxIdentifierKeyLengthLimiter.Check` used elsewhere in the same file [3](#0-2) [4](#0-3) . `ValidateGetSecretsRequest` is the sole outlier that hand-rolls the length comparison instead of delegating to a `Check`-style limiter, introducing the off-by-one.

The existing test suite documents this incorrect behavior as expected rather than catching it as a bug, explicitly building a batch of exactly `vaulttypes.MaxBatchSize` items and asserting it is rejected.

## Impact Explanation
This is a functional/availability defect reachable by any unprivileged workflow or gateway caller invoking the vault capability's `GetSecrets` method via `Capability.Execute`. A caller submitting exactly `MaxBatchSize` secret-get requests — an in-bound, legitimate size per the documented maximum — is deterministically denied service. This does not enable authentication bypass, secret exfiltration, or fund movement; it is purely a correctness/availability bug causing legitimate maximum-size requests to fail. It does not clearly map to a high-severity in-scope Chainlink bounty impact category (e.g., auth bypass, key/secret exfiltration, unauthorized fund movement, gateway impersonation, allowlist bypass, cross-user corruption) — it is a minor off-by-one validation inconvenience, not a security bypass or data exposure issue.

## Likelihood Explanation
The bug is 100% reproducible: any caller submitting a batch of exactly `MaxBatchSize` items always triggers the rejection, with no special access needed. However, likelihood of security relevance is low since the "impact" is merely inconvenience/DoS-of-self for legitimate max-size batches, not disclosure or bypass of any protection.

## Recommendation
Change the comparison to `if len(request.Requests) > vaulttypes.MaxBatchSize` to match the inclusive semantics of `MaxBatchSize` and the behavior of other limiters in the file, or refactor to reuse a `Check`-style bound limiter for consistency.

## Proof of Concept
1. Construct a `vaultcommon.GetSecretsRequest` with exactly `vaulttypes.MaxBatchSize` (10) `SecretRequest` entries with valid, unique identifiers.
2. Call `Capability.Execute` with `Method: vault.MethodGetSecrets`.
3. Observe the request is rejected with `"request batch size exceeds maximum of %d"` even though the batch size does not exceed the documented maximum, as demonstrated by the existing test `TestCapability_Execute_GetSecretsRequestValidationFailed` in `core/capabilities/vault/capability_test.go` (lines 255-285), which builds `reqs := make([]*vault.SecretRequest, vaulttypes.MaxBatchSize)` and asserts an error is returned.
