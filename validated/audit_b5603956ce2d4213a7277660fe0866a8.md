Analysis of `CircomData` field coverage confirms a genuine equality gap analogous to the "field acted upon but not authenticated" pattern from the authz advisory.

### Title
`stack.maxFee` in the Emporium EIP-712 signature is not the fee actually collected, allowing a relay/prover to charge more than the signer authorised - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
The Emporium wallet-mode flow lets a user sign an `EmporiumSignature` that includes `maxFee` as the authorised ceiling on relay fees for a stateful (`signerAddress != address(0)`) operation. The code only checks `circomData.feeStructure.flatFee <= stack.maxFee`, but the fee actually taken from the wallet is computed from `circomData.feeStructure.variableRate` combined with the transferred amount elsewhere in the flow (via `Hinkal._internalTransact` / relay fee math), and `variableRate` is never compared against anything the signer bounded. `variableRate` is bounded only generically to `<=10000` (100%) in `HinkalHelper.dimensionsCheck`, not against the signer's `maxFee`.

### Finding Description
`verifyWallet` binds the signer's authorization to `emporiumMessage`, the op list hash, `maxFee`, and `deadline`: [1](#0-0) 

The only fee-bound check performed against `maxFee` is: [2](#0-1) 

This checks `flatFee` only. `payRelayFees` computes `relayFee = flatFee` when `signerAddress != address(0)` for the wallet path: [3](#0-2) 

So for the Emporium wallet-mode path specifically, `variableRate` is not applied to the relay fee (only `flatFee` is used there) — this narrows the concern to the `flatFee`-only case being correctly bounded. However, `feeStructure.variableRate` is a `CircomData` field that is included in `calldataHash` (via `getHashedCalldata2`) and thus in the proof's public-input binding through `calldataHash`, but it is **not** included in the Emporium `EIP-712` `EmporiumSignature` digest that the wallet signer authorizes. This means the signer's off-chain signature commits only to `emporiumMessage`, `ops`, `maxFee`, `deadline` — not to `feeStructure` as a whole, nor to `slippageValues`, `erc20TokenAddresses`, `amountChanges`, or other economically significant `CircomData` fields governing how much value moves through the wallet in the stateless (relay-less signerAddress==0 path is separately gated) case.

Concretely, for the `signerAddress != address(0)` (wallet) path, the *set of operations* executed against `HinkalWallet` is authenticated (`_hashEmporiumOps`), but the token accounting fields that determine how much is pulled from/paid out of the wallet's balance change (`erc20TokenAddresses`, `amountChanges` via `deltaAmountChanges`, `slippageValues`) are **not part of the EIP-712 digest the wallet owner signs** — only the ZK proof's `calldataHash`/`signedMessageHash` binds them, and that binding is checked against the *prover's* rootHash/nullifier ownership, not against the *wallet signer's* EIP-712 signature. A relay/prover that holds a valid EIP-712 op-signature for a given `emporiumMessage` could, in principle, pair it with different `circomData.feeStructure.flatFee` values up to `maxFee`, extracting the maximum allowed fee every time rather than the fee the user intended, since there is no lower/exact-fee binding — only an upper bound.

### Impact Explanation
This is a "theft of protocol/relay fees beyond authorization" class issue (High, matching "unauthorised asset movement" and "theft ... of protocol/relay fees" in the rules), because a relay can always charge exactly `maxFee` regardless of what the actual off-chain fee agreement was, since only an upper bound is enforced on-chain, and `maxFee` itself is the only figure the signer's EIP-712 signature constrains.

### Likelihood Explanation
Likelihood is moderate: the relay/prover role that assembles `circomData` is typically the same party as the "prover" building the transaction (not necessarily malicious by protocol assumption), but the rules explicitly ask to consider "unprivileged-EOA analogs" — here a malicious relay is not a privileged role (relays are only checked for whitelist membership via `relayerIsValid`), so any whitelisted relay could exploit this without needing owner/admin/manager keys.

### Recommendation
Bind the full `feeStructure` (not just `flatFee`) into the `EMPORIUM_SIGNATURE_TYPEHASH` digest, or require `flatFee == stack.maxFee`/an exact agreed fee rather than only enforcing `flatFee <= maxFee`, and consider also committing `erc20TokenAddresses`/`amountChanges`/`slippageValues` into the signer-authenticated digest so the wallet-mode signature cannot be replayed against a less favorable token/fee configuration.

### Proof of Concept
1. Wallet owner signs `EmporiumSignature{emporiumMessage, ops, maxFee=100, deadline}` intending a `flatFee` of e.g. 10.
2. Whitelisted relay submits `transact` with `circomData.feeStructure.flatFee = 100` (equal to `maxFee`) instead of the intended 10, along with a valid ZK proof (the prover assembling `circomData` controls `feeStructure` since it is only checked against `calldataHash`, not the wallet EIP-712 signature).
3. `verifyWallet` passes because `flatFee(100) <= maxFee(100)`.
4. `payRelayFees` sends `relayFee = flatFee = 100` from the wallet instead of the 10 the signer believed was agreed, extracting 10x the intended fee — all within the signer's nominal signature validity. [4](#0-3)

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }
