## Title
`WrappedHyperFungibleToken.send`/`onAccept` uses `safeTransferFrom`/`safeTransfer` with a payload-committed `amount` that is not re-derived from actual balance delta, breaking for rebasing/fee-on-transfer underlying tokens - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

## Summary
`WrappedHyperFungibleToken` (and its upgradeable variant) locks an underlying ERC20 on the home chain via `safeTransferFrom` and later releases the same fixed `amount` on the destination chain (or refunds it on timeout) via `safeTransfer`, using the caller-specified `params.amount` verbatim rather than the amount actually received by the contract. This is the same architectural pattern flagged in the Axelar ITS report: a lock/unlock token manager whose committed cross-chain `amount` diverges from the token's real balance behavior between lock time and unlock time.

## Finding Description
In `send()`: [1](#0-0) 
tokens are pulled with `safeTransferFrom(msg.sender, address(this), params.amount)`, and the *same* `params.amount` (not the delta of `balanceOf(address(this))` before/after) is what gets ABI-encoded into the cross-chain `Message.amount` field via `_buildDispatchPost`: [2](#0-1) 

On the receiving side (`onAccept`) and on timeout (`onPostRequestTimeout`), the contract unconditionally transfers out `message.amount` of the underlying token from its own custody: [3](#0-2) [4](#0-3) 

Nowhere does the contract snapshot `balanceOf(address(this))` before and after the `safeTransferFrom` in `send()` to determine the *actual* amount received (unlike, e.g., the fee-on-transfer-aware `IntentGatewayV2` logic elsewhere in this repo, which explicitly measures pre/post balances and mutates `order.inputs[i].amount` to match reality — see `evm/src/apps/IntentGatewayV2.sol` lines 260-300 and the accompanying `FeeOnTransferToken` tests). Because the committed `amount` is the caller-specified value rather than the measured delta:

- If the underlying token is fee-on-transfer, `send()` locks less than `params.amount`, but the destination `onAccept` (or the source `onPostRequestTimeout`) still attempts to pay out the full `params.amount`, over-drawing the contract's custody balance and potentially reverting or draining funds meant for other users' locked balances.
- If the underlying token rebases (balance changes outside of transfers, which is explicitly the bug class this analog targets), the amount locked at `send()` time and the amount available at `onAccept`/timeout time can diverge — a positive rebase lets the contract pay out more than any single depositor actually contributed (leaking value to whichever transfer happens to be processed, at the expense of other users' escrowed balance), while a negative rebase can make `safeTransfer(beneficiary, message.amount)` revert or under-collateralize the shared custody pool, since there is no per-asset balance/share accounting — the contract is a shared custody pool for one underlying token across all outstanding cross-chain transfers, so any single rebase or fee-skim affects the fungible pool backing every other pending transfer of that asset.
- Because `WrappedHyperFungibleToken` is documented to "supports any possible ERC20" (no allowlist of "safe" token behaviors is enforced in the contract itself, mirroring Axelar's `Any (all possible ERC20s)` scope statement), this reachable code path is not merely theoretical from an integrator's perspective.

## Impact Explanation
This is a shared-custody pool for potentially many concurrent cross-chain transfers of the same underlying asset (unlike the burn/mint `HyperFungibleToken` counterpart, which has no such shared pool since it mints/burns its own supply). Any deployment configured with a fee-on-transfer or rebasing ERC20 as `underlying` risks:
- Insolvency of the custody pool (some users unable to redeem locked tokens because the pool balance is short of the sum of outstanding committed `amount`s), or
- Value leakage to whichever transfer is processed during a positive-rebase window, stealing from other users' escrowed balance in the same pool.

This matches the "concrete theft or permanent freezing of funds" bar, since it is the custody pool itself (not a single user's own funds) that is the affected balance, and the attack/failure is reachable by any unprivileged token bridger who deploys/uses a `WrappedHyperFungibleToken` for a non-standard ERC20 — a permissionless action requiring no special role.

## Likelihood Explanation
Likelihood is Medium: it requires the pool operator/integrator to configure `WrappedHyperFungibleToken` with a rebasing or fee-on-transfer underlying token (both `configure()` calls are `onlyOwner`, but nothing in the contract itself restricts or warns against such tokens, and the docs advertise wrapping "existing ERC20 tokens" generically). Given the docs and design explicitly aim for broad ERC20 compatibility (paralleling Axelar ITS's "Any (all possible ERC20s)" scope claim that the C4 judge held the protocol to), this is a foreseeable integration path rather than a contrived edge case.

## Recommendation
- In `send()`, snapshot `balanceOf(address(this))` before and after `safeTransferFrom`, and encode the measured delta (not `params.amount`) into `Message.amount`, mirroring the pattern already used in `IntentGatewayV2.placeOrder` for fee-on-transfer tokens.
- In `onAccept`/`onPostRequestTimeout`, either cap the payout at the contract's real balance for that underlying asset, or explicitly document/enforce (e.g. via a `configure()`-time check or an allowlist) that rebasing and fee-on-transfer tokens are unsupported as `underlying` for `WrappedHyperFungibleToken`.
- Consider per-transfer share accounting (rather than raw token amount) if rebasing tokens are meant to be supported, so a single asset's rebase cannot dilute/inflate other users' pending transfers in the shared custody pool.

## Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `underlying` set to a rebasing ERC20 (e.g., a Lido-stETH-like token) — no on-chain check prevents this.
2. User A calls `send(SendParams{amount: 1000, dest: chainB, ...})`; the contract's `safeTransferFrom` pulls tokens from A, and `_buildDispatchPost` encodes `amount: 1000` into the ISMP `Message` verbatim regardless of what the contract actually holds afterward — see [5](#0-4) .
3. Before the ISMP request is relayed/finalized, the underlying token undergoes a positive rebase, increasing the wrapper contract's `balanceOf` beyond the sum of all committed `amount`s.
4. A second user B's earlier transfer times out; `onPostRequestTimeout` unconditionally calls `IERC20(_underlying).safeTransfer(refundee, message.amount)` for B's original committed amount — see [6](#0-5) . Depending on rebase direction/timing and processing order, either the pool pays out more than the true sum of contributions (leaking rebase upside to whichever transfer clears first) or a negative rebase makes a legitimate `safeTransfer` for a later user revert because the pool's actual balance is now less than the sum of outstanding committed `amount`s — freezing that user's transfer.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    /**
     * @notice Handles incoming cross-chain token transfer messages
     * @dev Called by the ISMP host when a POST request is received. Verifies the source
     * address matches the configured contract for that chain, then transfers the underlying
     * ERC20 to the recipient. If calldata is present, executes it via the CallDispatcher.
     * @param incoming The incoming POST request containing the token transfer message
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Attempts to unwrap WETH and refund native tokens.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
