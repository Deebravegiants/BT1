## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body. The `shop`, `topic`, and `webhook_id` values, which are taken from unauthenticated HTTP headers, are never included in the signed content, so they are not bound to the HMAC that "proves" the request came from Shopify for that specific shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC purely against `to_signable_string` (i.e. the raw body), independent of the shop header: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate, then dispatches the handler using the unauthenticated `request.shop` value: [4](#0-3) 

The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_tenant_identity`. Here it does not: `hmac` is only bound to `raw_body`, while `shop` (the tenant identifier acted upon by the handler) is taken from an independent, unsigned header.

### Impact Explanation
An app's `client_secret`/webhook secret is shared across every merchant that installs the app. Any unprivileged attacker who installs the app on their own (even free/dev) store can trigger a legitimate webhook delivery for their own shop, capturing a valid `(raw_body, hmac)` pair signed with the app's shared secret. Because the `shop-domain` header is not part of the signed content, the attacker can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim merchant's domain). `HmacValidator.validate` will accept it, and `Registry.process` will invoke the app's handler with `shop: <victim-shop>` and attacker-controlled `body` content, causing the host application to process/apply data under the wrong tenant identity — a cross-tenant confusion/injection primitive using only a publicly known secret-independent replay.

### Likelihood Explanation
Likelihood is meaningful: the attacker only needs to be a legitimate installer of the target app on their own store (no elevated privileges, no access to `api_secret_key` needed) and the ability to send arbitrary HTTP requests to the app's known-public webhook endpoint, both of which are available to any unprivileged internet user/merchant.

### Recommendation
Bind the shop identity (and ideally topic) into the verified material — e.g., include `shopify-shop-domain` in the signable string, or require the caller to independently confirm the shop header value corresponds to a shop with an active, previously-established session/installation before trusting it, rather than relying on an HMAC that only covers the raw body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) on their store, capturing the raw POST body and the valid `X-Shopify-Hmac-SHA256` header sent by Shopify (signed with the app's shared secret).
3. Attacker sends a new HTTP request directly to the app's public webhook endpoint, reusing the captured `raw_body` and `hmac` header unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `hmac` against `raw_body` — validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled data>, ...)`, causing the app to act on forged data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
