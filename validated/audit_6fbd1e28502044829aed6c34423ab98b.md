### Title
Hardcoded ledger-time TTL constants assume mainnet `max_entry_ttl` and ~5s ledger speed; on a network with a lower max entry TTL every user entrypoint reverts once the instance threshold is crossed - (File: common/src/constants/shared.rs)

### Summary
The protocol bakes two environment-specific assumptions into compile-time constants: that one day equals 17,280 ledgers (~5-second ledger close) and that the network's `max_entry_ttl` is at least `TTL_BUMP_INSTANCE = 180 * 17_280` ledgers. `renew_instance` unconditionally calls `env.storage().instance().extend_ttl(TTL_THRESHOLD_INSTANCE, TTL_BUMP_INSTANCE)` at the top of every controller/pool user entrypoint. On a Stellar network where `max_entry_ttl` is lower than the requested bump (or is later reduced by a protocol upgrade, as has happened historically — max_entry_ttl was lowered on mainnet), `extend_ttl` to a value above the network maximum fails at the host level, every call reverts, and all user funds are frozen until redeployment and migration. There is no governance parameter to adjust these values; they are constants compiled into the Wasm.

### Finding Description
`common/src/constants/shared.rs` derives all TTL windows from `ONE_DAY_LEDGERS: u32 = 17_280`, which assumes mainnet's ~5-second ledger close time, and sets `TTL_BUMP_INSTANCE_DAYS = 180` explicitly documented as "the mainnet `max_entry_ttl`". This produces `TTL_BUMP_INSTANCE = 3,110,400` ledgers and `TTL_BUMP_SHARED = 3,110,400` ledgers, all hardcoded `pub const` values. `common::ttl::renew_instance` calls `extend_ttl(TTL_THRESHOLD_INSTANCE, TTL_BUMP_INSTANCE)` with no configuration override, and `contracts/controller/src/storage/protocol.rs` applies the same hardcoded bumps to every shared (`TTL_BUMP_SHARED`) and per-user (`TTL_BUMP_USER = 120 days`) persistent entry via `renew_persistent_key`. Because the bump targets were sized to sit exactly at mainnet's current `max_entry_ttl` rather than a configurable or safely-clamped value, the contract has zero margin: any deployment environment or future network-state reduction with `max_entry_ttl < 3,110,400` makes every entry that hits its renewal threshold unextendable.

This is the same bug class as the source report: a chain-specific deployment parameter (there a hardcoded 500,000 VRF callback gas limit and PUSH0-era compiler version; here `ONE_DAY_LEDGERS` and bump targets pinned to mainnet's `max_entry_ttl`) compiled in with no per-deployment override, so the contract cannot operate correctly outside the assumed environment and must be redeployed with user migration.

### Impact Explanation
Once instance TTL drops below `TTL_THRESHOLD_INSTANCE` (30 days of ledgers), `renew_instance` attempts to extend to a value the host rejects on a lower-`max_entry_ttl` network, so `extend_ttl` traps and every controller/pool/position-nft entrypoint — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `flash_loan`, NFT `transfer` — reverts. User-supplied collateral and debt positions become inaccessible: a temporary freezing of funds (recoverable only by contract redeploy + migration of persistent state, which cannot migrate expired/unextendable entries cheaply) that becomes permanent for any entries that archive before a patched contract is deployed. Identical exposure exists for shared and user persistent entries under `TTL_BUMP_SHARED`/`TTL_BUMP_USER`.

### Likelihood Explanation
The trigger requires only that the contracts be deployed on (or the network migrate to) a config where `max_entry_ttl < 3,110,400` or ledger cadence deviates from ~5s — both are realistic: Soroban testnet/standalone networks and past protocol upgrades have used different TTL bounds, and the constants are also baked into `position-nft`, `governance`, and `price-aggregator` with no runtime override. Every unprivileged user action drives the renewal path, so the failure surfaces through normal usage rather than an adversary; any user calling `supply`/`borrow` after the threshold crossing hits it. Rated Medium: funds are not stolen and recovery is possible via redeployment, but the deployed contract cannot operate as-is in the off-mainnet environment, matching the source finding's severity reasoning.

### Recommendation
Make TTL thresholds and bump targets constructor/config parameters per contract (stored in instance storage and validated against a minimum), or clamp the requested `extend_ttl` target to the network's reported `max_entry_ttl` (e.g., `min(bump, env.ledger().max_live_until_ledger() - current)` / `env.storage().max_ttl()` where exposed) instead of hardcoding `180 * ONE_DAY_LEDGERS`. At minimum, size `TTL_BUMP_*` to a conservative fraction of the smallest `max_entry_ttl` across targeted networks rather than exactly the mainnet maximum.

### Proof of Concept
Constants and the unconditional renewal call:

```rust
// common/src/constants/shared.rs
pub(crate) const ONE_DAY_LEDGERS: u32 = 17_280;          // assumes ~5s ledgers
const TTL_BUMP_INSTANCE_DAYS: u32 = 180;                 // "the mainnet max_entry_ttl"
const TTL_BUMP_SHARED_DAYS: u32 = 180;
const TTL_BUMP_USER_DAYS: u32 = 120;
pub const TTL_BUMP_INSTANCE: u32 = ONE_DAY_LEDGERS * TTL_BUMP_INSTANCE_DAYS; // 3,110,400
```

```rust
// common/src/ttl.rs
pub fn renew_instance(env: &Env) {
    env.storage()
        .instance()
        .extend_ttl(TTL_THRESHOLD_INSTANCE, TTL_BUMP_INSTANCE); // traps if bump > network max_entry_ttl
}
```

```rust
// contracts/controller/src/storage/protocol.rs
fn renew_persistent_key(env: &Env, key: &ControllerKey, threshold: u32, bump: u32) {
    env.storage().persistent().extend_ttl(key, threshold, bump); // same hardcoded bump for shared/user keys
}
```

Scenario: deploy to a Stellar network whose `max_entry_ttl` is below 3,110,400 ledgers. Users deposit via `controller::supply`. After ~30 days of ledgers the instance TTL falls under `TTL_THRESHOLD_INSTANCE`; the next user's `supply` calls `renew_instance`, the host rejects the `extend_to = 3,110,400` request, the call reverts, and every subsequent entrypoint reverts identically — deposits are frozen until a rebuild with corrected constants and state migration. Note: this assessment relies on the host rejecting `extend_ttl` requests above `max_entry_ttl`; if the host instead clamps, the residual risk is shortened effective TTLs and premature archival from the fixed 5s-ledger assumption, which is weaker.
