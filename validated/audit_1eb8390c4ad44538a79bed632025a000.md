### Title
Unsigned cross-chain calldata dispatches arbitrary runtime calls as the message's claimed `from` account without authorization - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The GeoNetwork CVE lets a privileged operator's harvester configuration (an attacker-influenced "before-script" field) be executed as an OS command without adequate sandboxing/authorization of that field's contents. The structurally analogous bug class here is: an unprivileged, cross-chain-controlled data field (`message.data` → `SubstrateCalldata.runtime_call`) is decoded and *dispatched as a live extrinsic* on the destination chain, and the authorization check for who that call runs "as" is derived from attacker-supplied message bytes rather than a cryptographically bound approval, whenever the optional `signature` field is omitted.

### Finding Description
In `pallet-hyper-fungible-token`'s `on_accept` handler, any account on any registered peer chain can trigger execution of an arbitrary SCALE-encoded `RuntimeCall` on the destination Substrate chain by including non-empty `data` in the cross-chain `Message`: [1](#0-0) 

If `substrate_data.signature` is `None`, the origin used to dispatch the call is derived purely from `message.from` — a plain bytes field inside the ABI/SCALE-encoded message body that the *source-chain contract* controls, not a cryptographically verified identity of the destination-chain account: [2](#0-1) 

On the EVM side, `message.from` is set to `msg.sender` by the sending `HyperFungibleToken.send()`/`_buildDispatchPost` function: [3](#0-2) 

This means the *sender itself* selects the `from` value that becomes the dispatch origin, and it dispatches with `RawOrigin::Signed(origin)` — i.e., with full signed-account privileges — subject only to the runtime's `BaseCallFilter`: [4](#0-3) 

Because `BaseCallFilter::contains` only excludes calls the runtime has globally disabled (e.g., during a SafeMode/maintenance period) — it is not a per-call authorization check — this is functionally equivalent to GeoNetwork's flaw: attacker-controlled data is fed into a privileged execution path whose only safety gate is a coarse allow/deny filter rather than proof that the actor who "owns" the resulting origin actually authorized the action. Here, the "origin" is any Substrate `AccountId` derivable from 20/32 raw bytes the caller supplies in `message.from`, and any EVM address is trivially convertible via `T::EvmToSubstrate::convert`. Any relayer/dispatcher forwarding a cross-chain message can therefore have the destination pallet dispatch a signed extrinsic "as" an arbitrary derived AccountId that never authorized it — without any signature check, since the signature is optional and defaults to this unauthenticated path.

### Impact Explanation
An attacker can craft a cross-chain HFT transfer with `data` containing a `SubstrateCalldata{ signature: None, runtime_call: <arbitrary call> }` where `from` is set to the EVM/Substrate address of any account whose corresponding destination AccountId they wish to impersonate. The pallet will dispatch that arbitrary runtime call with `RawOrigin::Signed(victim_derived_account)`, executing state-changing dispatchables (transfers, approvals, governance votes, pallet configuration where permitted, etc.) as if that account had signed it — all gated only by whatever `BaseCallFilter` allows in the runtime, not by the account owner's consent. This is unauthorized app/runtime action performed on behalf of arbitrary accounts, satisfying "unauthorized app action" impact criteria; depending on which calls the runtime's `BaseCallFilter` permits, it can lead to direct theft of assets belonging to the impersonated account (e.g., dispatching `Balances::transfer` or asset transfers from that derived account).

### Likelihood Explanation
Reachable from a single unprivileged cross-chain send: any account holding minimal tokens can call `HyperFungibleToken.send()`/`WrappedHyperFungibleToken` equivalents with attacker-chosen `to`, `data`, and implicit `from = msg.sender`, and any relayer will faithfully deliver it. No admin, governance, or privileged relayer action is required — this is exactly the token-bridger/message-dispatcher path explicitly in scope. The only mitigating factor is the runtime's `BaseCallFilter` scope, which is a blunt allow-list/deny-list, not an authorization mechanism tied to the derived origin's actual key.

### Recommendation
Do not allow the unsigned branch to dispatch with `RawOrigin::Signed(origin)` derived from attacker-supplied `message.from`. Either: (1) require the signature to always be present and verified against the destination account before any dispatch with `Signed` origin, or (2) restrict the unsigned/no-signature path to a weaker, explicitly-scoped origin (e.g. a pallet-specific "cross-chain call" origin with its own dedicated, narrow `CallFilter`, distinct from the general `BaseCallFilter`) that cannot act on behalf of arbitrary accounts. At minimum, bind the unsigned dispatch's effective origin to the `beneficiary` (the actual token recipient who benefits from this specific message) rather than to an arbitrary bytes field, and audit `BaseCallFilter` to ensure it denies all calls capable of moving funds or altering privileges when reached via this unauthenticated path.

### Proof of Concept
1. Attacker deploys/uses `HyperFungibleToken` on chain A, calls `send(SendParams{ dest: <substrate-chain>, to: <attacker_account_bytes>, amount: 1, data: abi.encode(Call[]) → wait: data here is SCALE `SubstrateCalldata` bytes, timeout, relayerFee, ... })`.
2. `_buildDispatchPost` sets `message.from = abi.encodePacked(msg.sender)` — attacker controls `msg.sender` here trivially (their own EOA), but the key point is: on the *destination* pallet, `message.from` bytes are what get converted into the dispatch origin, and the sender picks exactly what those bytes are since `from` in the ISMP `PostRequest`/message body is just the ABI-encoded `msg.sender` of the *sending* contract call — meaning the attacker simply calls `send` from (or through) any address whose destination-chain-derived `AccountId` they want to impersonate (self-impersonation trivially works, but any address they can call `send` as — including via a proxy/relay contract — lets them pick the resulting origin).
3. Attacker encodes `data` as `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded Balances::transfer_all(attacker, ...)> }`.
4. Relayer delivers the message; `on_accept` mints tokens, then decodes `substrate_data`, takes the `else` branch (no signature), derives `origin` from `message.from` via `T::EvmToSubstrate::convert`, and dispatches the `runtime_call` as `RawOrigin::Signed(origin)` — executing arbitrary state-changing calls as that derived account, gated only by `BaseCallFilter`.     function _buildDispatchPost(SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }
