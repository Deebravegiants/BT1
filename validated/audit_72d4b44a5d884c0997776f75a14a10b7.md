### Title
Missing allowlist/rate-limiting enforcement on gateway `HandleLegacyUserMessage` for `web_api_trigger` allows unauthenticated fan-out to all DON nodes - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Sherlock report describes a class of bug where a partially-honored, gas-limited cross-domain message is accepted into a "pending/undone" state and later completed (replayed) by an unprivileged party to force stale/unauthorized state changes, because a critical guard (proper completion / re-validation) is missing on the message-processing path. The closest concrete analog in this chainlink codebase is the WebAPI capabilities gateway handler's `HandleLegacyUserMessage`, which forwards every accepted external user request to **all DON members** without ever performing the allowlist or rate-limiting check that the code explicitly documents as required, an unprivileged-caller check that never actually executes.

### Finding Description
`handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` processes an inbound user message from the internet-facing gateway. It performs payload decoding, timestamp/staleness checks, and a method whitelist check, but the allowlist/rate-limit enforcement is left as a bare `TODO` comment with no code behind it: [1](#0-0) 

Specifically:
```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
    ...
}
```
Right after that no-op comment, the request is registered as a saved callback and sent to **every** DON member: [2](#0-1) 

The call chain confirms this handler is reachable directly from the gateway's public message dispatch path with no intervening allowlist gate — `multiHandler.HandleLegacyUserMessage` simply looks up the method-registered handler and forwards the call verbatim: [3](#0-2) 

There is a `nodeRateLimiter` field on the handler, but it is only invoked in `handleWebAPIOutgoingMessage` (the node→client egress path), not in `HandleLegacyUserMessage` (the client→node ingress path): [4](#0-3) 

Contrast this with the Vault gateway path, which explicitly enforces `AuthorizeRequest` (allowlist/JWT-based authorization) before any request is processed or forwarded to nodes: [5](#0-4) 
and the HTTP Trigger v2 handler which enforces JWT-based authorization plus a replay cache before dispatch: [6](#0-5) 

The legacy WebAPI capabilities handler has no equivalent authorization/allowlist gate at all — the only checks are payload well-formedness, timestamp freshness, and method name, none of which restrict *who* may call the endpoint.

### Impact Explanation
Any unauthenticated/unprivileged party reaching the gateway's legacy user-message endpoint for the `web_api_trigger` method can trigger fan-out of arbitrary, attacker-controlled `TriggerRequestPayload` messages to every member of the DON, consuming DON node resources and invoking downstream capability/workflow trigger logic without any allowlist restriction. This is a direct analog of the report's core issue — a message-processing path that is meant to be gated (there, by proper OOG-safe completion; here, by an allowlist) but the gate is absent, letting an unprivileged actor drive privileged-looking effects (broadcasting requests to the entire DON, consuming node resources, potentially triggering workflows) that the system's own comments and sibling implementations (Vault, HTTP Trigger v2) indicate should require authorization.

### Likelihood Explanation
High: the missing check is unconditional (not dependent on configuration or feature flags) and sits directly on the reachable, documented method (`MethodWebAPITrigger`) of an internet-facing gateway handler. No special conditions, timing, or gas-crafting are required — any caller of the legacy user message path with a well-formed, non-stale payload triggers the fan-out.

### Recommendation
Implement and enforce the allowlist/rate-limit check called out by the `TODO` comment in `HandleLegacyUserMessage` before saving the callback and forwarding the request to DON members — mirroring the `AuthorizeRequest`/JWT-based authorization pattern already used by the Vault and HTTP Trigger v2 gateway handlers in this same codebase.

### Proof of Concept
1. Send an inbound legacy gateway message with `Body.Method = "web_api_trigger"` and a well-formed `webapicap.TriggerRequestPayload` (non-zero `Timestamp` within `MaxAllowedMessageAgeSec`) to the gateway's public ingress for the WebAPI capabilities handler, with no prior registration/allowlisting of the caller.
2. Observe that `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) passes all checks (decode, timestamp, method) — since none of them validate caller identity — and forwards the message to every member in `h.donConfig.Members` via `don.SendToNode`.
3. Repeat with arbitrarily many distinct unauthenticated senders/messages to demonstrate unrestricted fan-out to the DON, confirming the absence of any allowlist or per-caller rate limiting on this ingress path.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
