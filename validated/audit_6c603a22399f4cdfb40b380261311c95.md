### Title
Unbacked shielded-value minting via untraced Emporium balance deltas, compounded with real withdrawal laundering in the same call - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` credits an ERC20/ETH "deposit" index purely from the raw before/after balance delta of the Emporium contract itself, with no check that the increase was actually funded by an incoming transfer tied to the attacker's `msg.sender`. Because `handleOut` and the `runAction` accounting loop process each `erc20TokenAddresses[i]` independently, an attacker can combine a genuine `tokenB` withdrawal (backed by a real UTXO) with a fabricated `tokenA` "deposit" backed only by unattributed residual balance already sitting on the Emporium contract, in a single `transact` call.

### Finding Description
The equality that should hold is: for every index `i` where `deltaAmountChanges[i] >= 0` (a claimed deposit), the resulting `balanceChange` credited as `amountChanges[i]`/UTXO value must originate from tokens the attacker actually moved into Emporium during that call — not from pre-existing, unattributed balance.

Trace:
- `EmporiumUpgradeable.runAction` snapshots `balancesBefore` for all tokens, executes attacker-crafted `stack.ops` (unprivileged endpoints/calldata), then snapshots `balancesAfter`. [1](#0-0) 
- For each index, `balanceChange = balancesAfter[i] - balancesBefore[i]`; only when `deltaAmountChanges[i] < 0` (a withdrawal already funded from Hinkal via `_externalTransact`) is `balanceChange` adjusted by subtracting `deltaAmountChanges[i]` to avoid double counting. For a deposit index (`deltaAmountChanges[i] >= 0`), the raw balance delta is trusted as-is, with no verification that it came from an attacker-authorized transfer during the ops loop. [2](#0-1) 
- `handleOut` then forwards the full `balanceChange` back to `msg.sender` (the Hinkal contract) and mints a `UTXO` of that amount for that token, with no source-of-funds check. [3](#0-2) 
- Back in `Hinkal.sol`, the balance equation only checks that Hinkal's own balance delta equals `amountChanges[i] + utxoAmount`, which is satisfied numerically once Emporium forwards the dust-derived amount as a UTXO — it never verifies the dust's provenance. [4](#0-3) 
- `_externalTransact` only handles the negative-delta (withdrawal) legs by transferring funds out of Hinkal to Emporium before calling `runAction`; positive-delta (deposit) legs are left entirely to the ops to fund, with no enforcement mechanism tying the resulting Emporium balance increase to an authenticated inbound transfer. [5](#0-4) 

Crucially, the per-index loops in both `runAction`'s accounting section and `Hinkal.sol`'s balance-difference section operate strictly independently per token index — `tokenA`'s processing never reads or is affected by `tokenB`'s `deltaAmountChanges`/`balanceChange`, and vice versa. This independence is exactly what allows an attacker to pair a legitimate `tokenB` withdrawal with the fabricated `tokenA` deposit in the same `erc20TokenAddresses` array without either leg interfering with or blocking the other, since none of `performHinkalChecks`, `verifyProof`, `rootHashExists`, the slippage requires, `insertNullifiers`, or `onlyAllowedRecipient` inspect provenance of an Emporium balance increase — they only check that the numeric equation `balanceDif == amountChanges[i] + utxoAmount` holds, which it trivially does regardless of whether the underlying tokens were freshly deposited or pre-existing dust.

### Impact Explanation
An unprivileged attacker can mint a shielded UTXO backed by no real deposit (unbacked shielded value creation) for `tokenA`, while simultaneously legitimately withdrawing real funds for `tokenB` from their own genuine shielded note — both in one `transact` call. This is Critical: it constitutes minting shielded value without backing, and doing so alongside a real withdrawal doubles the attacker's exfiltration efficiency per transaction. The underlying root cause (untraced balance-delta trust for "deposit" legs) is repeatable for every distinct token where reachable unattributed dust exists on the Emporium contract, and the multi-token combination adds no additional safeguard that would prevent co-mingling it with a real withdrawal.

### Likelihood Explanation
This finding depends entirely on the same precondition as the referenced prior scenarios: that Emporium holds unattributed `tokenA` dust reachable via an unprivileged, attacker-crafted `EmporiumOperation`. That precondition itself is not independently re-verified within this trace (it is asserted as already established in "scenario 1/2," whose contents were not available for re-verification here). Given that precondition, the multi-token combination is straightforward: the attacker only needs to craft `stack.ops` with one harmless op that surfaces the dust as a `tokenA` balance increase, and separately fund the `tokenB` withdrawal leg from a genuine owned UTXO — both are fully within attacker capability (crafting `CircomData`, `EmporiumStack.ops`, proof generation for their own UTXO). No additional privilege or a new distinct code interaction is required beyond what the base dust-sweep finding already requires.

### Recommendation
For every index where `deltaAmountChanges[i] >= 0` (a "deposit" leg), require that the Emporium balance increase be attributable to a transfer explicitly authorized by/from `circomData.externalActionData.externalAddress` (or `msg.sender`/attacker) during the ops execution — e.g., by requiring the relevant op(s) to emit/prove a matching `Transfer` event from the depositor, or by having `_externalTransact` itself pull the deposit funds via `transferERC20TokenFromOrCheckETH` from the attacker before invoking `runAction`, rather than trusting Emporium's raw balance delta. Additionally, sweep/zero any unattributed residual token balance on Emporium at the start of each `runAction` (or track attributable balances explicitly) so that stale dust can never be credited as a fresh deposit.

### Proof of Concept
Foundry test plan:
1. Seed Emporium with unattributed `tokenA` dust (e.g., via a prior failed/rounding op or direct `deal`).
2. Have attacker deposit and later generate a real shielded UTXO for `tokenB` (genuine funds).
3. Craft `CircomData` with `erc20TokenAddresses = [tokenA, tokenB]`, `amountChanges = [X, -Y]`, and `EmporiumStack.ops` containing a no-op-style call that merely surfaces the pre-existing `tokenA` balance (no real transfer-in for `tokenA`), plus whatever call funds the real `tokenB` withdrawal path.
4. Call `Hinkal.transact` with a proof attesting to input nullifier consumption for the real `tokenB` UTXO and `amountChanges[0] = X` for `tokenA` with no corresponding external payer.
5. Assert: (a) attacker's wallet receives `Y` of `tokenB` from their genuine UTXO withdrawal, (b) a new shielded UTXO/commitment for `tokenA` amount `X` is created and spendable by the attacker, and (c) no `ERC20.transferFrom` or equivalent inbound transfer of `X` `tokenA` from the attacker ever occurred — i.e., `balanceDif[tokenA] == amountChanges[0] == X` in `Hinkal.sol` line 137-146 holds with zero real depositor, confirming value creation without backing.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)

            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
