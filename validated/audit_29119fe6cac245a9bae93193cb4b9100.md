### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant shop spoofing on an otherwise validly-signed webhook - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, while its HMAC signable content (`to_signable_string`) is only the raw request body. `Registry.process` trusts `request.shop` to build the `WebhookMetadata` passed to the host app's handler after confirming only that the *body* HMAC is valid, never that the `shop-domain` header matches the shop the body actually came from.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from headers, none of which participate in the signature: [2](#0-1) 

`Registry.process` validates only the HMAC of `request` (i.e., the body) and then builds the metadata handed to the host app's handler using the unauthenticated `request.shop`: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string` (the body, for webhooks) with the app's `api_secret_key`: [4](#0-3) 

This breaks the intended identity binding: `shop-domain header == shop that produced/authorized this signed body`. In practice, the app's `client_secret`/`api_secret_key` is the *same* HMAC key Shopify uses for every shop that installs the app (that's the whole point of app-wide webhook signing). Therefore any merchant who has installed the app on their own store (tenant A) receives Shopify-signed webhook bodies whose HMAC they can observe. Because the header set (`shop-domain`, `topic`, `webhook-id`, `api-version`) is not part of the signed content, that same attacker can replay the identical `raw_body` + valid `hmac-sha256` header to the app's webhook endpoint while substituting a different `shop-domain` header value (tenant B's domain, or any arbitrary domain). `HmacValidator.validate` will still pass because it only checks the body signature, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the payload belongs to tenant B: [5](#0-4) 

Any host application logic that looks up the target shop's session/access token by `data.shop` (the gem's own documented usage pattern for webhook handlers, since `WebhookMetadata#shop` is the only shop identifier the gem exposes) will then act on tenant B's store using data controlled by tenant A — a direct violation of the equality "shop authenticated by HMAC == shop the request claims to be for," since the HMAC never authenticates the `shop` field at all.

### Impact Explanation
This is a cross-tenant authentication/identity confusion: the gem's own webhook signature-verification API certifies a body's authenticity but silently omits the shop-domain claim from that certification, while the API's only exposed way to attribute the webhook to a tenant (`WebhookMetadata#shop`) is that unauthenticated field. Any host app that follows the gem's documented pattern (verify via `Registry.process`, then trust `data.shop` for tenant dispatch) is exposed to cross-tenant webhook injection — meeting the Critical bar ("cross-tenant access") since data attributed to one merchant can be forced onto another merchant's account context using only a validly-signed body the attacker legitimately received for their own store.

### Likelihood Explanation
Any user able to install the app on their own Shopify store (a normal, unprivileged flow available to any merchant) automatically receives genuinely HMAC-signed webhook payloads for their own shop from Shopify. They then only need to resend that intercepted request with a modified `shop-domain` header to the app's public webhook endpoint — no secret key, access token, or privileged access is required. This is a low-effort, unauthenticated-relative-to-the-target-tenant attack.

### Recommendation
Include the shop identity (and ideally topic/webhook id) in the HMAC-signed content, or otherwise cryptographically bind the `shop-domain` header to the signed body (e.g., verify the shop against the session/store looked up independently of the header, or require the host app to cross-check `request.shop` against an out-of-band trusted mapping) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant dispatch without additional verification.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`; the app registers a webhook (e.g., `orders/create`).
2. Shopify sends a webhook to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
3. Attacker captures this request (e.g., via a proxy they control, since it's their own endpoint) and resends it to the app's webhook endpoint with the header changed to `x-shopify-shop-domain: victim.myshopify.com`, leaving `raw_body` and `x-shopify-hmac-sha256` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `raw_body`: [3](#0-2) 
5. The host app's `handler.handle` receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)` and, following the gem's documented pattern, looks up `victim.myshopify.com`'s stored access token to act on the payload — resulting in attacker-controlled data being processed under the victim tenant's identity.
