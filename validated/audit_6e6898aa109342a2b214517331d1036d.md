This confirms the finding: the docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" using the HMAC, but the HMAC verification (`Utils::HmacValidator.validate` over `Webhooks::Request#to_signable_string`) only covers the raw request body — it never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that `Registry.process` and `WebhookMetadata` rely on for tenant identification and dispatch.

### Title
Webhook HMAC only authenticates the raw body, letting a replayed payload be relabeled to a different shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (used by `Registry.process`) proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Those header values are trusted downstream and handed to the app's handler as authenticated fields, even though they were never covered by the signature.

### Finding Description
`Registry.process` gates all webhook handling on a single check: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

And `Webhooks::Request#to_signable_string` is defined as just the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated headers: [3](#0-2) 

The identity binding the docs claim to provide is broken:
`hmac_verified(secret, raw_body) == true` is treated as equivalent to `shop_header == authenticated_originating_shop`, but the equality only actually holds for `raw_body`; `shop`, `topic`, `webhook_id`, and `api_version` are never part of the signed bytes.

Because a single app uses one shared `api_secret_key` across every shop that installs it, any valid `(raw_body, hmac)` pair generated for one tenant (e.g. captured from the attacker's own shop, which legitimately receives correctly signed webhooks) remains a valid pair for `HmacValidator.validate` no matter what `shop-domain` header accompanies it. An attacker who operates or has installed the app on their own shop can:
1. Capture a legitimate webhook `(raw_body, hmac)` delivered to their own installation (this is trivial — they own that tenant and can trigger events, e.g. `orders/create`, at will and read their own webhook traffic).
2. Replay that exact `raw_body` and `hmac` header to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop that also has the app installed.
3. `HmacValidator.validate` re-derives the same HMAC over the same `raw_body` with the same shared secret and returns `true`, since the shop header was never part of the signed input.
4. `Registry.process` then dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` — `request.shop` is the attacker-supplied header, not anything cryptographically tied to the payload. [1](#0-0) 

The gem's own documentation states this `process` call "will verify the request did indeed come from Shopify," which is only true for the bytes of the body, not for which shop the app should attribute that body to: [4](#0-3) 

Every downstream consumer, per the documented handler contract, is expected to key persistence/business logic off `data.shop`: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity confusion: the app will accept and process an attacker's own webhook data (order, customer, product, etc.) as if it belonged to any other shop that has installed the same app, since `shop` is not bound by the HMAC that is supposed to authenticate the whole request. Depending on how the host application uses `data.shop` (as essentially all documented usage does — to select which tenant's record to create/update, e.g. `perform_later(shop_domain: data.shop, ...)`), this allows a low-privileged attacker who merely installs the app on their own store to inject or corrupt data belonging to an arbitrary victim shop, i.e. cross-tenant access/write, matching the Critical impact category for cross-tenant access.

### Likelihood Explanation
The prerequisite is only that the attacker installs the app on their own shop (available to anyone) or otherwise observes one valid `(body, hmac)` pair for the shared app secret, and that they can send arbitrary HTTP requests with arbitrary headers to the app's webhook endpoint (a normal capability of any internet client, since nothing in `Request` validates headers beyond presence, and nothing in the gem restricts the source IP). No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Bind the identity fields the app relies on into the signed/verified surface, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the specific delivery instead of trusting bare headers:
- Have `Webhooks::Request#to_signable_string` incorporate `shop`, `topic`, and `webhook_id` (e.g., by canonicalizing headers + body into the signable string, mirroring what `Auth::Oauth::AuthQuery#to_signable_string` does for OAuth params) so `HmacValidator.validate` actually authenticates the tuple the handler will act on, not just the body bytes.
- At minimum, document/require host apps to cross-check `shop` against an app-side allowlist of shops with active installations before trusting `data.shop`, and consider adding built-in `webhook_id` replay-de-duplication guidance to reduce the blast radius of a captured-and-replayed payload.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real event (e.g. creates an order) so Shopify sends a legitimately signed webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (computed with the app's shared `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `B` and `H` to the app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and, if desired, `x-shopify-webhook-id` to a fresh value to bypass any dedup).
3. Server calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers))`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and compares to `H` — matches, returns `true`, per [2](#0-1) .
5. `Registry.process` dispatches the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, per [6](#0-5) , causing the host app to act on attacker-controlled `B` as though it were victim-shop's legitimate webhook data.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
