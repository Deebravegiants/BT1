## Analysis

The reported bug pattern is a **fee-bypass via an alternate order-matching function**: `RecipeOrderbook`'s `createIPOrder`/`fillIPOrder` path charges `protocolFee`, but the `createLPOrder`/`fillLPOrder` path reaches the same economic outcome without the fee ever being applied — the recommendation was to synchronize fee logic between the two paths.

Searching the in-scope Hinkal contracts for the same bug class — two independent entry points that reach the *same* resulting on-chain state, but only one of them applies the protocol fee — surfaces a direct analog between `HinkalWrapper.prooflessDeposit` and `Hinkal.prooflessDeposit`.

`HinkalWrapper.sol`'s own doc comment states its purpose explicitly: *"Settles the protocol fee for a proofless deposit, then forwards the deposit itself to Hinkal (which has no fee-taking logic of its own)"* [1](#0-0) . Its `prooflessDeposit` calls `_settleFee` to pull `feeStructure.feeAmount` in ETH or ERC20 to `feeStructure.feeRecipient` before forwarding the deposit call to `Hinkal.prooflessDeposit` [2](#0-1) .

However, `Hinkal.prooflessDeposit` itself is a `public payable` function with no access-control restricting the caller to `HinkalWrapper` and no fee logic of its own — it only runs `performProoflessDepositChecks`, pulls tokens from `msg.sender`, and creates the on-chain shielded commitments [3](#0-2) .

### Title
Protocol fee on proofless deposits can be bypassed by calling `Hinkal.prooflessDeposit` directly instead of through `HinkalWrapper` - (`contracts/Hinkal.sol`, `contracts/HinkalWrapper.sol`)

### Summary
`Hinkal.prooflessDeposit` (contracts/Hinkal.sol:263-295) is a public entry point that performs the exact same deposit + on-chain commitment creation as `HinkalWrapper.prooflessDeposit` (contracts/HinkalWrapper.sol:28-47), but without the fee-settlement step. `HinkalWrapper` is only a convenience wrapper that additionally deducts a protocol fee before forwarding to `Hinkal`; nothing in `Hinkal.sol` or its checks (`performProoflessDepositChecks`) enforces that the deposit must originate from `HinkalWrapper` or that a fee has been paid.

### Finding Description
`HinkalWrapper.prooflessDeposit` calls `_settleFee(feeStructure)` to transfer the protocol fee to `feeStructure.feeRecipient` in either ETH or an ERC20 token, then forwards the remaining ETH value and pulls/approves the deposit tokens to `Hinkal.prooflessDeposit` [4](#0-3) . The `feeStructure` parameter (fee amount/recipient) is supplied entirely by the caller and is never mirrored or enforced inside `Hinkal.sol`.

`Hinkal.prooflessDeposit` itself has no caller restriction (no `onlyRole`, no check that `msg.sender == hinkalWrapperAddress`), and it independently performs the full deposit flow: validation via `hinkalHelper.performProoflessDepositChecks`, token pull via `_handleTransfersFromProoflessDeposit`, and shielded commitment creation via `_createProoflessDepositCommitments` [3](#0-2) . Any EOA can call this function directly with the same `erc20Addresses`/`amounts`/`stealthAddressStructures` arguments used by the wrapper and obtain an identical resulting shielded UTXO state, with identical funds pulled from the user, but without ever invoking `_settleFee`.

This breaks the intended equality that the protocol wants to hold: *fee paid == deposit accepted*. Since `Hinkal.sol` doesn't gate on fee payment, a user reaches the same "deposit accepted, commitment inserted" state as through `HinkalWrapper`, but with `fee paid == 0`.

### Impact Explanation
This is a permanent loss of protocol fee revenue for every proofless deposit performed this way — it matches the "High" impact class of *permanent freezing/loss of protocol fees*, since the wrapper's fee-recipient never receives what it is designed to collect, and there is no on-chain mechanism to recover it retroactively.

### Likelihood Explanation
Likelihood is high: `Hinkal.prooflessDeposit` is a `public` function on the main entry contract, requires no proof, no special role, and no knowledge beyond the ABI, which is trivially discoverable from the verified contract. Any user who would otherwise use `HinkalWrapper` can instead call `Hinkal` directly with the same parameters and save the fee.

### Recommendation
Restrict `Hinkal.prooflessDeposit` (and any other deposit/withdraw entry points intended to be fee-gated by a wrapper) so it can only be called by the designated wrapper/fee-collecting contract, or move the fee-settlement logic into `Hinkal.sol` itself (e.g., as part of `performProoflessDepositChecks`) so that it cannot be bypassed by calling the base contract directly.

### Proof of Concept
1. Attacker identifies `hinkal` address stored in `HinkalWrapper` (public/inspectable) or from deployment records.
2. Attacker calls `Hinkal.prooflessDeposit(erc20Addresses, amounts, stealthAddressStructures, onChainEncryptedOutputs, createBlockedUtxos, orderId)` directly with `msg.sender` = attacker, supplying the same parameters that would otherwise be passed through `HinkalWrapper.prooflessDeposit`.
3. `Hinkal.sol` pulls exactly `amounts` from attacker, creates the shielded on-chain commitments, and completes successfully — identical end state to using the wrapper — but `feeStructure.feeRecipient` never receives any fee, because `_settleFee` in `HinkalWrapper.sol:49-70` was never executed.

            onChainEncryptedOutputs,
            createBlockedUtxos,
            orderId
        );
    }

    function _settleFee(
        ProoflessFeeStructure calldata feeStructure
    ) internal returns (uint256 ethForHinkal) {
        ethForHinkal = msg.value;
        if (feeStructure.feeToken == address(0)) {
            require(
                msg.value >= feeStructure.feeAmount,
                "insufficient ETH for fee"
            );
            ethForHinkal = msg.value - feeStructure.feeAmount;
            if (feeStructure.feeAmount > 0) {
                transferETH(feeStructure.feeRecipient, feeStructure.feeAmount);
            }
        } else if (feeStructure.feeAmount > 0) {
            transferERC20TokenFrom(
                feeStructure.feeToken,
                msg.sender,
                feeStructure.feeRecipient,
                feeStructure.feeAmount
            );
        }
    }
