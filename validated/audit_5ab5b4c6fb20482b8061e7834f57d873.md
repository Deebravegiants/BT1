### Title
Unbounded `messages: Vec<Message>` batch in `pallet-ismp::handle_unsigned` combined with a static declared weight enables a weight/DoS mismatch on message delivery - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is a permissionless, unsigned, fee-free extrinsic that accepts an arbitrary-length `Vec<Message>` and fully executes (verifies proofs + dispatches to every destination module) every message in the batch, yet its declared weight is a single hard-coded constant that does not scale with the number or complexity of messages supplied.

### Finding Description
`handle_unsigned` is declared with a static weight and dispatches the full batch: [1](#0-0) 

The weight used for that call is a constant, independent of `messages.len()` or the cost of what those messages contain (consensus proofs, MMR multiproofs, trie non-membership proofs, etc.): [2](#0-1) 

`validate_unsigned` itself calls `Self::execute(messages.clone())` — i.e., it runs the *entire* verification+dispatch pipeline (membership proof checks, per-request loops, module callbacks) just to admit the extrinsic into the pool, before any block-level weight accounting is even relevant: [3](#0-2) 

The actual per-message work is unbounded and grows linearly (or worse, given nested proof verification) with the size of the batch — every request in the batch is walked twice (validation pass + dispatch pass) in the request/response handlers: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

There is no on-chain bound (`BoundedVec`, `MaxMessages`, per-batch length cap) found on `messages: Vec<Message>` in `handle_unsigned`, and the pallet's own testsuite constructs and processes a 1000-request batch through this exact call path, confirming large batches are accepted as valid input shapes: [8](#0-7) 

This is directly analogous to the reported bug class: a caller-supplied, unbounded list is iterated by a dispatch/handler function whose gas/weight cost is not properly bounded relative to the declared cost, risking execution beyond the intended per-call budget.

### Impact Explanation
On the EVM side (`HandlerV2.handlePostRequests`/`handleGetResponses`/timeouts), the relayer pays their own gas for their own chosen batch size, so an oversized batch only wastes the caller's own gas — this mirrors the original low/self-inflicted-DoS report and is not independently impactful.

On the Substrate/pallet-ismp side, however, the situation is qualitatively different: `handle_unsigned` is fee-free (Substrate `Pays::No`-style unsigned extrinsic path) and its weight is a fixed constant rather than one computed from `messages.len()`/message contents. If the true execution cost of processing a large or proof-heavy batch of ISMP messages substantially exceeds the declared static weight, a block author that includes such an extrinsic (validated successfully by `validate_unsigned`, which itself executes the whole batch) can produce a block whose actual execution time is far larger than the weight budget assumed by the runtime's block-weight accounting. This can degrade block production/import performance for the parachain that processes ISMP messages, i.e., stalling the very extrinsic path (`handle_unsigned`) responsible for delivering all incoming ISMP messages (requests, responses, timeouts, consensus updates) to the chain — matching the "route unable to deliver messages" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high given: (1) the call is permissionless and free (no signer, no fee) so an attacker can submit these batches repeatedly at no cost beyond crafting valid proofs; (2) the testsuite already demonstrates 1000-entry batches are a normal accepted shape for this call, showing no practical/enforced cap; (3) the weight constant `300_000_000` is small relative to the cost of verifying hundreds of proofs and running the corresponding module `on_accept`/`on_response` callbacks. I was unable to fully verify whether `modules/pallets/ismp/src/fee_handler.rs` post-dispatch overrides `actual_weight` based on the real batch size (a tool-call budget limit prevented reading that file in this pass); if it does dynamically recompute and charge `actual_weight` after execution, the severity of this specific weight-mismatch concern would be reduced (though the fee-free/unsigned nature and lack of any max-batch-length bound would remain).

### Recommendation
- Enforce an explicit maximum length/weight budget on `messages: Vec<Message>` accepted by `handle_unsigned` (e.g., a `BoundedVec` with a `MaxMessages` config constant, or reject batches whose aggregate estimated verification cost exceeds a threshold before calling `Self::execute`).
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` a function of `messages.len()`/message kind so the runtime's weight accounting reflects the true worst-case cost, and confirm/enforce that `actual_weight` returned in `PostDispatchInfo` matches real consumption (verify `fee_handler.rs` behavior explicitly).
- Consider capping the number of leaves/messages per `PostRequestMessage`/`GetResponseMessage`/timeout message that can be included in a single `handle_unsigned` call, mirroring the same cap that should be applied to the EVM `HandlerV2` batch functions.

### Proof of Concept
1. Craft a `Vec<Message>` containing many (e.g., hundreds to a thousand, as already exercised in `pallet_call_decompressor.rs`'s test) `PostRequest`/`GetResponse` entries with valid consensus/membership proofs targeting real registered destination modules.
2. Submit as an unsigned `pallet_ismp::Call::handle_unsigned { messages }` extrinsic.
3. `validate_unsigned` executes the entire batch via `Self::execute` at pool-validation time (`modules/pallets/ismp/src/lib.rs:625`), and if included, dispatch executes it again with only the static `weight()` constant (`modules/pallets/ismp/src/lib.rs:730`) attributed to the call, regardless of the batch's true cost — demonstrating the weight/cost mismatch that a caller can amplify by increasing batch size or proof complexity.
