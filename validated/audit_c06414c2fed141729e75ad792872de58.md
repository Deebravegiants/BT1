### Title
CallDispatcher.dispatch() has no caller restriction, permitting anyone to drain any transient ETH/token balance held by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is an unrestricted `external` function with no `onlyOwner`, `onlyHost`, or caller allow-list of any kind. It decodes an arbitrary `Call[]` array and executes each entry as a low-level `.call{value: call.value}(call.data)` from the `CallDispatcher`'s own address, using the `CallDispatcher`'s own native-ETH and token balances. Because this is a single, shared, long-lived contract that multiple protocol apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`) route funds through as an intermediate execution sandbox, any balance transiently or accidentally left in the contract is fully and permissionlessly stealable by any address, exactly the "lack of strict access control" class described in the referenced SlowMist MEV bot incident.

### Finding Description
`CallDispatcher.dispatch` has no access-control modifier at all: [1](#0-0) 

This contract is intentionally used as a shared execution sandbox that temporarily custodies funds:
- `HyperFungibleToken.onAccept`/`onPostRequestTimeout` mint tokens to a `beneficiary` and then forward `message.data` to `ICallDispatcher(_dispatcher).dispatch(message.data)`. Integrators are explicitly instructed to set `to: CALL_DISPATCHER` so the minted tokens land in the dispatcher before further calls spend them: [2](#0-1) 
- `IntentGatewayV2`/`ExtrinsicIntents`/`IntentsBase._execute` transfer predispatch/output assets to the same `dispatcher` address, call `dispatch()` on attacker/user-supplied `Call[]` payloads, and then sweep any residual balance back: [3](#0-2) 
- The `CallDispatcher` also has a bare `receive()` that accepts ETH from anyone, and the docs acknowledge it "can hold and forward native tokens" (e.g. Uniswap refunds), i.e. residual/dust ETH or tokens are an expected, documented occurrence during execution: [4](#0-3) 

Because `dispatch()` is callable by anyone, any ETH or ERC-20 balance sitting in the `CallDispatcher` at any point between transactions — whether from an incomplete sweep, a misconfigured `to: CALL_DISPATCHER` message with empty `data` (tokens minted to the dispatcher and never forwarded), or leftover native-token refunds from an external DEX call inside an app's `Call[]` batch — is directly and permissionlessly withdrawable by constructing a `Call[]` that transfers the balance to an attacker-controlled address and submitting it straight to `CallDispatcher.dispatch()`. No proof, no relayer, and no relationship to the apps that use the dispatcher is required; a single unprivileged transaction from any account is sufficient.

### Impact Explanation
Any funds that are temporarily or mistakenly left in the `CallDispatcher` — a contract multiple production apps (bridging and intents) are documented to route escrowed/minted assets through — are unconditionally stealable by any address at any time, satisfying the "concrete theft of funds" bar. This mirrors the reported MEV bot incident where a lack of strict access control on a privileged/fund-holding entry point allowed direct theft (~$210k / 116.7 ETH) rather than requiring any privileged role or forged proof.

### Likelihood Explanation
The likelihood of a triggering window (residual balance in `CallDispatcher`) is not guaranteed on every transaction, since well-formed app flows sweep balances back atomically in the same transaction. However, the docs themselves acknowledge dust/residual native-token scenarios are expected (Uniswap refunds, dust events), and any integrator or user misconfiguration (e.g., setting `to: CALL_DISPATCHER` with empty `data`, or an app upgrade/new integration that omits the sweep step) creates an immediately and permanently exploitable balance, since `dispatch()` itself enforces zero restriction on who may call it or what it may do with the contract's held assets.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., an `onlyAuthorizedCaller` modifier keyed to the specific app/proxy addresses that are meant to use the dispatcher within the same transaction), or redesign the pattern so the dispatcher never custodies value across calls it did not itself initiate — for example by requiring the caller to pre-register itself as the expected `msg.sender` for a given batch, or by moving to a per-call ephemeral dispatcher (e.g., a minimal proxy deployed and destroyed within the same transaction) so no shared, permanently-deployed contract ever holds a balance reachable by an arbitrary transaction.

### Proof of Concept
1. Any ETH or ERC-20 balance ends up held by the deployed `CallDispatcher` singleton (e.g., via a `HyperFungibleToken` message with `to: CALL_DISPATCHER` and empty `data` so the mint never gets forwarded/swept, or via dust left after an external DEX call inside an `IntentGatewayV2` order's `Call[]` batch).
2. An attacker (or MEV bot) observes the nonzero balance on `CallDispatcher` (or its `receive()` balance) via a public RPC call.
3. The attacker constructs `Call[] calls = [{ to: attackerControlledOrTokenContract, value: <balance>, data: <transfer(attacker, balance) or empty for ETH> }]` and calls `CallDispatcher.dispatch(abi.encode(calls))` directly from any EOA.
4. Since `dispatch()` performs no caller check, the low-level call executes with `CallDispatcher`'s own ETH/token balance and the funds are transferred to the attacker, with no ISMP proof, relayer authorization, or app-specific check required.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
