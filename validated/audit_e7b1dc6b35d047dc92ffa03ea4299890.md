Session cookie value is a predictable, unsigned identifier, enabling session fixation/hijack across tenants - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/oauth/session_cookie.rb`)

### Summary
The report describes a bug class where an identity check is missing: `redeem()` trusted the bytes of a valid signed voucher regardless of who submitted them, rather than binding the reward recipient to the voucher's rightful owner. The same class of bug appears in this gem's non-embedded session-cookie flow: the session identifier that is stored in the browser cookie and later used to look up a merchant's stored `Session` (containing the access token) is a fully deterministic, unsigned string derived only from public information (the shop domain), with no cryptographic binding tying the cookie's bytes to the specific OAuth-authenticated session that created them.

### Finding Description
When OAuth completes for a non-embedded app, `Session.from` computes the session `id` as: [1](#0-0) 

- offline: `"offline_#{shop}"`
- online: `"#{shop}_#{associated_user.id}"`

This deterministic `id` becomes the *entire* value of the `SessionCookie`, which is a plain, unsigned struct with no MAC/signature over its `value`: [2](#0-1) 

`validate_auth_callback` sets this cookie value directly to `session.id` for non-embedded apps: [3](#0-2) 

Later, on every subsequent request, `SessionUtils.current_session_id` (the gem's documented API for retrieving the "current" session, per `docs/getting_started.md`) simply reads the raw cookie value back out and returns it as the session id — with no signature/HMAC check that the value was actually issued by this gem's own OAuth completion for an authenticated shop: [4](#0-3) [5](#0-4) 

The broken identity binding, stated as an equality: the host app trusts `cookie_session_id(cookies) == <session id legitimately issued after this browser completed OAuth for that shop>`. Because the ID is `"offline_#{shop}"` — a pure function of the shop domain, which is public/guessable — and the cookie carries no signature, an attacker can compute the exact session id for any target shop without ever completing OAuth, and simply present it as their own cookie value. The gem provides no mechanism to detect that the bytes were not the product of its own signed OAuth flow.

### Impact Explanation
This maps to the "session fixation or forced OAuth completion" High-impact category. Since `SessionUtils.current_session_id` is the gem's documented, recommended way for host apps to resolve "the current session" from cookies (see `docs/getting_started.md` lines 47-52), any host app that follows this documented pattern and uses the returned ID to fetch a persisted `Session` (containing the merchant's real access token) is vulnerable: an attacker who merely knows/guesses a target shop's domain (e.g. `victim-shop.myshopify.com`, which is typically public) can set a cookie `shopify_app_session=offline_victim-shop.myshopify.com` on their own browser and have the host app resolve and use the victim shop's stored access token on their behalf — a cross-tenant access without ever authenticating as that shop.

### Likelihood Explanation
Exploitation requires the attacker to place an arbitrary value into the session cookie for the target app's origin (e.g. via any cookie-setting primitive scoped to that origin, or if the host app ever accepts the session id from a non-HttpOnly source, e.g. a query/header fallback as documented for embedded apps). The core weakness — a fully predictable, unsigned identifier standing in for an authenticated session — is present in the gem regardless of how the cookie is transported, and directly mirrors the reported bug class: no check binds the presented identifier to its rightful, authenticated owner.

### Recommendation
Do not use a deterministic, guessable string (`"offline_#{shop}"` / `"#{shop}_#{user_id}"`) as the opaque, bearer-token-like value stored in the session cookie. Either:
- Generate a cryptographically random, unpredictable session cookie value that is only used as an opaque lookup key server-side and stored separately from the deterministic internal session `id`, or
- Sign/HMAC the cookie value with the app's secret so that `SessionUtils.cookie_session_id` can verify authenticity before returning it, rejecting any cookie value that wasn't produced by this gem's own OAuth completion.

### Proof of Concept
1. Target app uses non-embedded OAuth via `ShopifyAPI::Auth::Oauth.begin_auth`/`validate_auth_callback` and follows the documented pattern of storing the resulting cookie and later resolving sessions with `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` as shown in `docs/getting_started.md`.
2. Victim shop `victim-shop.myshopify.com` has previously installed the app (offline token), so the host app's session store contains a `Session` keyed by `offline_victim-shop.myshopify.com`.
3. Attacker, without ever completing OAuth, sends a request to the app with cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
4. `cookie_session_id` returns this attacker-supplied value verbatim [5](#0-4) ; the host app looks up and uses the victim's stored `Session`/access token to serve the attacker's request, granting cross-tenant access without any authentication of that shop.
