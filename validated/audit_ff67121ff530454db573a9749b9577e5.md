### Title
Webhook shop-domain spoofing due to `shop` field excluded from HMAC signature verification - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC over the raw body only, while the `shop` (and `topic`) values passed to the webhook handler come from unauthenticated HTTP headers. Since Shopify webhook HMACs are generated with the app's single shared `api_secret_key` (not a per-shop secret), a malicious merchant who has legitimately installed the app can capture a genuine webhook payload/HMAC pair delivered to their own shop and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header, causing the gem to report a different, arbitrary shop as the source.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the handler: [1](#0-0) 

The verification is delegated to `Utils::HmacValidator.validate(request)`, which signs/verifies only `request.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns solely the raw body — `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are never part of the signed material: [3](#0-2) 

Despite this, `Registry.process` forwards `request.shop` — the unauthenticated header value — straight to the app's handler as the authoritative tenant identifier once HMAC validation of the body passes: [4](#0-3) 

The identity binding broken is:
`shop domain authenticated by HMAC` ≠ `shop domain delivered to the handler as data.shop`.

Because Shopify webhook HMACs for a given app are computed with the app's single `api_secret_key`, shared across all shops that install the app, a valid `(raw_body, hmac)` pair obtained from a webhook genuinely sent to *shop A* remains a valid `(raw_body, hmac)` pair when replayed with the `x-shopify-shop-domain` header changed to *shop B*. `HmacValidator.validate` will still return `true`, because the header is not covered by the signature at all.

### Impact Explanation
This is a cross-tenant identity confusion: any merchant who installs the app can obtain a legitimately-signed webhook body from their own store and re-deliver it to the app's webhook endpoint while claiming it came from another merchant's shop. Any app logic that uses `data.shop` (as instructed in the gem's own documentation example, `docs/usage/webhooks.md`) to look up sessions, apply mutations, or make trust decisions per-tenant would act on the wrong tenant's identity — e.g. attributing another shop's order/customer/GDPR data-request payload to shop B, or triggering shop-specific side effects (billing, redact/uninstall flows) against an arbitrary victim shop. This falls under cross-tenant access.

### Likelihood Explanation
Any account holder who can install the app on a shop (a routine unprivileged step, not requiring any secret) can capture their own genuine webhook traffic and replay it with a modified header value — no access to `api_secret_key`, tokens, or TLS interception is needed.

### Recommendation
Bind `shop` (and other headers used downstream, e.g. `topic`, `webhook_id`) into the signed material, or otherwise cross-check that the `shop` value corresponds to a shop with an active app installation/session known to the app before trusting it, rather than passing the raw unauthenticated header through `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g., `orders/create`) on their own shop, capturing the resulting webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker resends the same body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header; `HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation succeeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled content under the victim's tenant identity.
