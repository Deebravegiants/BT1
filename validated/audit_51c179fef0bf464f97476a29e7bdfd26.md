### Title
Webhook `shop` domain is trusted from an unauthenticated header while the HMAC only signs the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by checking an HMAC over the raw request body, but the `shop` value that is handed to the app's handler (and thus becomes the tenant identity the host application acts on) is read from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed bytes. This breaks the intended binding `HMAC-verified bytes == bytes the shop identity is derived from`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body: [2](#0-1) [3](#0-2) 

`Registry.process` validates HMAC via `Utils::HmacValidator.validate(request)`, which computes the signature over `to_signable_string` (i.e., only the body) and compares it to the `hmac` header: [4](#0-3) [5](#0-4) 

After this check passes, `request.shop` (the unauthenticated header value) is forwarded directly into `WebhookMetadata`, which the host application's handler uses as the tenant/shop identifier: [6](#0-5) 

Critically, Shopify computes the webhook HMAC using the app's single `api_secret_key`/`client_secret` — the same secret is shared across **every** shop that has installed the app. That means a genuine webhook delivered to Shop A (which the app operator controls or can install the app on as an ordinary merchant) has a body+HMAC pair that is valid under the *same* key as a webhook for Shop B. Since the HMAC never covers the `shop-domain` header, an entity capable of delivering an HTTP request to the app's webhook endpoint (e.g., replaying/relaying a previously received, validly-signed webhook payload while substituting the `X-Shopify-Shop-Domain` header) can cause `Registry.process` to accept the HMAC and dispatch the handler with an attacker-chosen `shop` value, while the actual authenticated bytes (the body) says nothing about which shop it belongs to.

This is the exact bug class from the report generalized to identity binding: "a field acted on (`shop`) but not covered by the HMAC (only the body is signed)."

### Impact Explanation
Handlers are documented to key off `data.shop` to persist/act on data for "the shop domain of the webhook" (see `docs/usage/webhooks.md`), and typical host-application patterns (e.g., `perform_later(shop_domain: data.shop, ...)`) will process/store data under whatever shop string arrives in the header — independent of what was actually verified. This allows cross-tenant data injection/confusion: an attacker who can get one authentic, HMAC-valid webhook body (from any shop that installed the app, including their own store) can relabel it as belonging to a different, victim shop by only changing an unauthenticated header, since the gem provides no mechanism or requirement to check the header's shop against the body or against a known/authorized shop list. This matches the "cross-tenant access" Critical impact category, because the gem's own verification API gives host applications false confidence that `request.shop`/`data.shop` is authenticated when it is not.

### Likelihood Explanation
Exploitation requires only the ability to deliver an HTTP POST to the app's webhook endpoint with a previously-observed (or otherwise obtained) valid `(body, hmac)` pair and an arbitrary `shop-domain` header — no access token, client secret, or privileged account is needed; the attacker can be an ordinary merchant/install of the same app, i.e., an "unprivileged internet user" relative to any other tenant of the app. The library performs no additional cross-check between the authenticated field (body) and the identity field (`shop` header), so the vulnerable code path is reached on every call to `Registry.process`, which is the gem's documented, canonical way to process webhooks.

### Recommendation
Bind the shop identity to the HMAC-authenticated material, or explicitly document/require validating `request.shop` against a store of shops known to have installed the app before trusting it. At minimum:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) as part of the bytes verified by `to_signable_string`, mirroring how the OAuth `AuthQuery#to_signable_string` signs all identity-relevant fields together with `code`/`state`.
- Alternatively, have `Registry.process`/`WebhookMetadata` require the caller to supply the currently-authenticated shop (from session storage) and assert equality with the header-derived `shop` before dispatching to the handler, raising `Errors::InvalidWebhookError` on mismatch.

### Proof of Concept
1. App has webhooks registered; two shops, `victim.myshopify.com` and `attacker.myshopify.com`, both have the app installed (both share the same `api_secret_key` for HMAC purposes, since it's app-level, not per-shop).
2. Attacker triggers/receives a legitimate webhook for `attacker.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`, both unchanged and valid.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...))` — the handler now processes attacker-supplied content attributed to the victim shop.

Note: I could not find any code path in this gem (outside `test/**`/`docs/**`, which are out of scope) that cross-checks `request.shop` against the HMAC-verified body or against any authorized-shop allowlist, confirming the header is the sole, unauthenticated source of the `shop` field passed to handlers.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
