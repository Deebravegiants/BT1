### Title
Unauthorized arbitrary external call and full drain of `EmporiumUpgradeable` token/ETH balance via zero-token Emporium action - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction()` only verifies balance changes (and only enforces the EIP-712 wallet signature) for the tokens listed in `circomData.erc20TokenAddresses`. When that array is empty — a path explicitly supported by `CircomDataBuilder.formInputForCircom()` via `HINKAL_EMPORIUM_ACTION_ID` — both the pre/post-balance accounting loop and the signature check are skipped entirely, letting any unprivileged EOA execute an arbitrary low-level call from the Emporium contract and drain any token/ETH it holds.

### Finding Description
`CircomDataBuilder.formInputForCircom()` routes to a minimal circuit (`formInputEmporiumMin`, backed by `MainEVMCircuitMin.circom`) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && circomData.erc20TokenAddresses.length == 0`: [1](#0-0) 
`MainEVMCircuitMin.circom` only requires the prover to know a self-chosen `messageSeed` whose Poseidon hash matches the committed `message` — it enforces no ownership of funds, no nullifier spend, nothing tied to real value: [2](#0-1) 

`circomData.externalActionData` (which contains `externalActionMetadata`, the ABI-encoded `EmporiumStack`) is bound only via `calldataHash`, which the caller freely constructs and matches themselves — there's no additional restriction on the content of the `EmporiumStack`: [3](#0-2) [4](#0-3) 

Inside `EmporiumUpgradeable.runAction()`, `verifyWallet()` completely skips signature verification when the attacker sets `stack.signerAddress == address(0)`: [5](#0-4) 

With `signerAddress == address(0)`, each op falls into "CASE 2: Stateless Interaction", which performs an arbitrary low-level call **from the Emporium contract's own address**, with the only restriction being that the selector can't be `callHinkalWallet`/`doSendToRelay`: [6](#0-5) 

Finally, the only guard against misuse of this arbitrary call is the balance-diff loop that iterates over `circomData.erc20TokenAddresses`: [7](#0-6) 
When `circomData.erc20TokenAddresses.length == 0` (the exact path selected above), this loop runs zero times, so **no balance check of any kind is performed** — the arbitrary call in CASE 2 is completely unconstrained.

This is the same root-cause class as the reported LiFi bug ("initial balance of tokens is not protected/checked"), but strictly worse: instead of merely failing to protect *dust/intermediate* balances during a swap, this path removes the balance-protection mechanism altogether, while also disabling the signer-authorization check that would otherwise gate the arbitrary call.

### Impact Explanation
Any unprivileged EOA can, with a self-generated trivial proof (no real UTXOs or deposits required), call `Hinkal.transact()` routed to Emporium with `erc20TokenAddresses = []` and an `EmporiumStack` containing `signerAddress = address(0)` and one or more stateless ops such as `IERC20(dustToken).transfer(attacker, balance)` or a call draining the contract's native ETH. This directly steals any token or ETH balance held by `EmporiumUpgradeable` — including relay fees in transit, dust from other users' incomplete swap-style actions, or any funds otherwise resting in the contract — with no authorization or balance check. This is direct theft of protocol/relay/user funds resting in an unprivileged, permissionlessly reachable contract, qualifying as Critical/High impact (unauthorized asset movement / direct theft).

### Likelihood Explanation
High. No special privileges, relayer cooperation, or victim action are required. The attacker only needs to call `Hinkal.transact()` once with a self-satisfiable minimal-circuit proof and craft `externalActionMetadata` accordingly; the emptied `erc20TokenAddresses` path is a first-class, explicitly coded branch (`formInputEmporiumMin`), not an edge case requiring unusual manipulation.

### Recommendation
- Do not allow `verifyWallet()` to bypass signature verification purely based on `signerAddress == address(0)`; stateless ops that act on the Emporium contract's own balance must always be constrained by the post-call balance-diff check.
- Ensure the balance-diff / authorization logic in `EmporiumUpgradeable.runAction()` cannot be skipped by supplying an empty `erc20TokenAddresses` array — either reject `erc20TokenAddresses.length == 0` when stateless (`invokeWallet == false`) ops are present, or require a non-bypassable signature (or restrict CASE 2 endpoints/selectors more narrowly) whenever `erc20TokenAddresses` is empty.
- Reassess whether the `HINKAL_EMPORIUM_ACTION_ID` + empty-token-array minimal-circuit path should permit arbitrary `EmporiumStack` payloads at all, since it currently allows execution of arbitrary external calls from the Emporium contract without any economic/balance constraint.

### Proof of Concept
1. Attacker (any EOA) observes `EmporiumUpgradeable` holds some ERC20 `X` balance (dust from prior operations, unclaimed relay fees, or accidental transfers).
2. Attacker picks a random `messageSeed`, computes `message = Poseidon(messageSeed)`, and builds a valid proof for `MainEVMCircuitMin` (trivially satisfiable, no fund ownership required).
3. Attacker builds `circomData` with:
   - `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []` (consistent with `formInputEmporiumMin`).
   - `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = <Emporium address>`.
   - `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [ EmporiumOperation{ endpoint: X, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, X.balanceOf(Emporium)) } ] }`.
   - `calldataHash` computed to match per `CircomDataBuilder.getHashedCalldata`.
4. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. `performHinkalChecks` passes (calldata hash matches, trivial minimal proof verifies); `_externalTransact` calls `EmporiumUpgradeable.runAction`.
6. `verifyWallet` returns immediately (signerAddress == address(0)); the stateless op executes `X.transfer(attacker, balance)` directly from the Emporium contract.
7. The post-loop balance check runs zero iterations (`erc20TokenAddresses.length == 0`), so nothing reverts — the attacker has drained `X` from `EmporiumUpgradeable`.
