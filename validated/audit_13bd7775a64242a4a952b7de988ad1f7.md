## Analysis: DoS via unbounded, underpriced `handle_unsigned` ISMP batches

The CVE describes DoS from an unbounded count of "parts" causing disproportionate resource consumption relative to what the request "costs" the server. `pallet-ismp`'s `handle_unsigned` extrinsic has the same shape: it accepts an **unbounded `Vec<Message>`** (each message itself wrapping unbounded `Vec<PostRequest>`/`Vec<GetRequest>`, and each `GetRequest` carrying an unbounded `Vec<Vec<u8>>` of storage keys), is dispatched **for free** as an unsigned transaction, and is charged a **fixed, size-independent weight**.

### Title
Unbounded, free, statically-weighted `handle_unsigned` batches enable resource-exhaustion DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Call::handle_unsigned` executes an attacker-supplied `Vec<Message>` where nested collections (`requests: Vec<PostRequest>`/`Vec<GetRequest>`, `GetRequest.keys: Vec<Vec<u8>>`) are unbounded, yet the extrinsic is billed a constant weight via `fn weight()`, and — critically — the same expensive execution path (`Self::execute`) also runs unconditionally inside `validate_unsigned`, which every full node runs on every gossiped transaction, for free, before any block inclusion decision is made.

### Finding Description
`handle_unsigned` is declared with a static weight: [1](#0-0) [2](#0-1) 

That weight (`300_000_000` ref-time units, i.e. ~0.3ms) is **not scaled** to the size of `messages`. There is no bound in the pallet on `Vec<Message>` length, nor on the number of `PostRequest`/`GetRequest` entries per message, nor on `GetRequest.keys` length — the test suite itself demonstrates 100 `GetRequest`s each carrying 256 keys with no rejection for size: [3](#0-2) 

Every element in the batch triggers real cryptographic and storage work — state-machine validation, membership-proof verification (Merkle/MMR/storage-proof verification, potentially ECDSA/BEEFY signature recovery for consensus messages), hashing, and duplicate/timeout checks — inside `handle`: [4](#0-3) 

The docs confirm this call is deliberately "free" and unsigned: [5](#0-4) 

Worse, this expensive execution is not gated behind block inclusion at all: `validate_unsigned` fully executes the batch (`Self::execute(messages.clone())`) as part of transaction-pool validation, which fires on every peer that receives the gossiped extrinsic: [6](#0-5) 

The `execute` function itself iterates the whole batch unconditionally before any fee is ever charged: [7](#0-6) 

Because the declared weight used for block-space accounting and mempool priority is a constant unrelated to the actual size of the attacker-controlled `Vec<Message>`/`Vec<Request>`/`Vec<Vec<u8>>`, an attacker can construct one extrinsic near the max extrinsic/block length limit that is packed with the maximum number of small nested requests/keys, forcing full computational proof verification for potentially thousands of items while the runtime's weight accounting only reserves space for ~0.3ms of computation. Submitting many such transactions (each free, unsigned, and independently gossip-validated by every node) multiplies the effect across the whole network.

This is directly analogous to the reachable-analog rule set: it hits `pallet-ismp handle_unsigned`, a route where unauthenticated/unprivileged relayers, dispatchers, or any network peer can submit data that the protocol must process.

### Impact Explanation
An attacker with no signed account and no funds can repeatedly submit maximally-sized `handle_unsigned` batches. Because:
1. execution is free (unsigned, no fee payer),
2. `validate_unsigned` runs the full computational path on every node during mempool gossip (not just on the block author), and
3. the weight declared for block-inclusion accounting does not scale with the actual number of nested items processed,

the actual CPU/verification cost incurred by the network per submitted transaction can vastly exceed what the protocol's weight system assumes it should cost. This can starve node resources (CPU, block production time) network-wide, causing missed block production, degraded relayer/validator performance, or an outright denial of service for the parachain's ISMP message pipeline — a High-severity availability impact on a state-machine handler that every relayer and message-dispatcher path depends on.

### Likelihood Explanation
High. No signed account, deposit, or bonded relayer status is required — `handle_unsigned` explicitly permits `ensure_none(origin)` execution for anyone with proof material (which can be self-manufactured against a `Mock`/misconfigured consensus client, or crafted with a large number of trivially-valid GetRequest/PostRequest leaves against a real, already-finalized state commitment). Constructing an oversized-but-within-extrinsic-limits `Vec<Message>` requires only public information about existing finalized heights and no special privileges, making this trivially reachable by any unprivileged party running a relayer-like script.

### Recommendation
- Bound the number of messages per `handle_unsigned` call and the number of nested requests/keys per message (e.g., a `MaxMessagesPerBatch`, `MaxRequestsPerMessage`, `MaxKeysPerGetRequest` config constant), rejecting oversized batches in `validate_unsigned` before any expensive proof verification runs.
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` proportional to `messages.len()` (and ideally to the nested request/key counts) rather than a fixed constant, so block-weight accounting reflects real cost.
- Consider cheap, size-derived pre-checks (e.g., total encoded length or item count thresholds) executed before `Self::execute` inside `validate_unsigned`, so gossip-time validation cannot be used to force full cryptographic verification of unbounded, unpriced input on every peer.

### Proof of Concept
1. Craft a single `pallet_ismp::Call::handle_unsigned { messages }` where `messages` is one `Message::Response(ResponseMessage)` (or `Message::Request`) whose `requests: Vec<GetRequest>` contains the maximum number of entries that fit under the runtime's max extrinsic/block length, each `GetRequest.keys` also maximized (as already demonstrated feasible with 100×256 in the existing test fixture, at path `modules/pallets/testsuite/src/tests/pallet_call_decompressor.rs:33-96`, scaled up toward the byte-length ceiling).
2. Submit this as an unsigned transaction; `validate_unsigned` (`modules/pallets/ismp/src/lib.rs:614-626`) will call `Self::execute` and perform full membership/consensus verification across every nested item, for free, on every peer that receives the gossiped transaction — while the pallet's declared weight (`fn weight()`, `modules/pallets/ismp/src/lib.rs:728-730`) reserves only a fixed, size-independent budget.
3. Repeat submission from multiple sources; observe CPU time consumed by nodes validating/gossiping/executing these batches grows with attacker-chosen batch size while no fee is charged and no weight limit scales to match, demonstrating the resource-exhaustion DoS.

```rust
pub fn handle<H>(host: &H, msg: RequestMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	if msg.requests.is_empty() {
		Err(Error::EmptyBatch)?
	}

	let state_machine = validate_state_machine(host, msg.proof.height)?;
	let consensus_clients = host.consensus_clients();
	let check_state_machine_client = |state_machine: StateMachine| {
		consensus_clients
			.iter()
			.find_map(|client| client.state_machine(state_machine).ok())
			.is_none()
	};

	let router = host.ismp_router();

	// Reject duplicate requests within the batch. Wire format is `Vec`,
	// so this is the line of defence against an attacker padding a
	// batch with identical requests.
	let wrapped: Vec<Request> = msg.requests.iter().cloned().map(Request::Post).collect();
	dedup_requests::<H>(&wrapped)?;

	for req in msg.requests.iter() {
		let req = Request::Post(req.clone());
		// If a receipt exists for any request then it's a duplicate and it is not dispatched
		if host.request_receipt(&req).is_some() {
			Err(Error::DuplicateRequest { meta: req.clone().into() })?
		}

		// can't dispatch timed out requests
		if req.timed_out(host.timestamp()) {
			Err(Error::RequestTimeout { meta: req.clone().into() })?
		}

		// either the host is a router and can accept requests on behalf of any chain
		// or the request must be intended for this chain
		if req.dest_chain() != host.host_state_machine() && !host.is_router() {
			Err(Error::InvalidRequestDestination { meta: req.clone().into() })?
		}

		let source_chain = req.source_chain();

		// in order to allow proxies, the host must configure the given state machine
		// as it's proxy and must not have a state machine client for the source chain
		let allow_proxy = host.is_allowed_proxy(&msg.proof.height.id.state_id) &&
			check_state_machine_client(source_chain);

		// check if the request is allowed to be proxied
		if source_chain != msg.proof.height.id.state_id && !allow_proxy {
			Err(Error::RequestProxyProhibited { meta: req.clone().into() })?
		}
	}

	// Verify membership proof
	let state = host.state_machine_commitment(msg.proof.height)?;
	let commitments = msg
		.requests
		.iter()
		.map(|post| hash_request::<H>(&Request::Post(post.clone())))
		.collect();
	state_machine.verify_membership(host, commitments, state, &msg.proof)?;
```

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
