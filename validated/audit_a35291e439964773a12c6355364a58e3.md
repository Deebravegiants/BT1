### Title
Permissionless `finalizeGraduation` seeds HyperSwap LP via `addLiquidity` with `amountMin = 1`, letting anyone pre-seed the pair and lock LP away from the curve close price - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The C4 report on Backd's `TopUpAction` flags that a keeper-executable action which swaps assets with a wide (or attacker-influenced) slippage tolerance lets an unprivileged actor sandwich the trade for profit at the expense of the position owner. `Bonding.finalizeGraduation` is the direct analog in alt.fun: it is explicitly **permissionless** ("anyone can call to rescue a stuck token") and it performs an on-chain deposit into an external AMM (`HyperSwap V2`) using `addLiquidity` with `amountMin = 1`, i.e. essentially no slippage protection, executed against whatever reserves the `TOKEN/LT` pair holds at call time.

### Finding Description
Per `packages/contracts/AGENTS.md` (lines 79-93), graduation is split into two phases:
- **Phase 1 (`_enterGraduating`)**: fired inline by the threshold-crossing buy. Caches `tokensForLP` and the curve-derived LT amount in `pendingGraduation[token]`, computed from the pair's reserves *at that moment* so the LP would open at exactly the last curve price.
- **Phase 2 (`finalizeGraduation`)**: a **permissionless** call, invoked later (normally by a keeper, but callable by anyone) that creates the HyperSwap pair if needed and seeds liquidity. For the "hostile mint-pre-seed" regime, `Bonding` calls `pair.swap` directly for rebalancing plus the canonical HyperSwap `addLiquidity(...)` for the deposit leg via `_routerDepositAndDispose` (referenced in `AGENTS.md` lines 93, 112).

Because `finalizeGraduation` is not restricted to run atomically with phase 1, and the pending cached `tokensForLP` value is fixed while the *actual* HyperSwap pool reserves at execution time are not, an unprivileged address can:
1. Directly transfer `TOKEN` and/or `LT` into the not-yet-finalized HyperSwap `TOKEN/LT` pair (a direct ERC20 transfer into an externally reachable pair address, explicitly listed as an in-scope analog surface), skewing its reserve ratio away from the cached curve-close price.
2. Call the permissionless `finalizeGraduation` itself (or wait for the keeper to call it, since the keeper has no way to detect or reject a manipulated ratio before submitting).
3. The deposit executes through `addLiquidity` with `amountMin = 1`, so the transaction cannot revert on an unfavorable ratio — it silently accepts whatever split the manipulated reserves dictate, and the router's own `quote()`-based optimal-split logic computes the deposited amounts from the *live, attacker-chosen* ratio rather than the cached, phase-1 curve price.

This directly breaks the "zero price gap" invariant the protocol relies on (`docs/contracts-scope.md` lines 79-90: "compute the exact `tokensForLP` at graduation time so the LP opens at precisely the last curve price… Naively seeding the LP with the full 250M reserve would create a large price gap that arbitrage bots would immediately close, transferring value out of the protocol"). An attacker who pre-seeds the pool before the permissionless finalize call effectively recreates exactly the price-gap scenario the design is meant to prevent, and — unlike the TopUp keeper case, where the position owner at least suffers only slippage on their own swap — here the loser is the **protocol treasury/LP** (`ltFromPair`, `tokensForLP`, and the 250M `lpReserve` held by `Bonding`), which gets permanently locked into `LPLock` (a one-shot, non-skippable lock per `LPLock.recordLock`) at the manipulated ratio. ### Impact Explanation
Value seeded into the HyperSwap LP (curve-raised LT plus up to 250M reserved tokens) is priced at an attacker-chosen ratio instead of the true last curve price, and is then locked forever in `LPLock` (no withdraw path in v1). This is a permanent, protocol-level loss/misallocation of LP funds and mispriced LP, benefiting whoever pre-seeded the pool (who can immediately arbitrage the mispriced pool once it goes live), directly matching the "LP seeded away from the curve close price" impact class called out as in-scope. This is Medium/High severity because it results in concrete, unrecoverable value transfer out of the protocol treasury/LP into an attacker's hands, without requiring any privileged access.

### Likelihood Explanation
`finalizeGraduation` is explicitly documented as permissionless and callable by any address, and pre-seeding a not-yet-created (or freshly created) `TOKEN/LT` pair via a direct ERC20 transfer is one of the explicitly allowed unprivileged attack surfaces. The `amountMin = 1` slippage setting on `addLiquidity` means there is no on-chain guard preventing the deposit from executing at a bad ratio — the transaction will simply succeed regardless of how skewed the pool is at call time. Any account with enough capital to move the pair's reserves and enough visibility of a graduating token (public on-chain state) can execute this without any special permission, making likelihood high once a token is in the `Graduating` state and before `finalizeGraduation` lands.

### Recommendation
Bound the `addLiquidity` deposit leg with a real slippage tolerance derived from the phase-1-cached `tokensForLP` / curve price (e.g., `amountAMin`/`amountBMin` computed as a bounded percentage of the cached target ratio, not `1`), and/or verify the live pool ratio against the cached `pendingGraduation` price before depositing, reverting (or retrying with a corrected split) if it has drifted beyond an acceptable tolerance. Alternatively, restrict who can trigger `finalizeGraduation` at the moment of deposit (e.g., require a caller-supplied minimum-out that is checked against the pending graduation snapshot) so a manipulated pre-seed cannot silently pass through.

### Proof of Concept
1. Token `T` reaches the graduation threshold; `Bonding._enterGraduating` fires, caching `pendingGraduation[T] = {tokensForLP, ltFromPair}` computed from the curve's last price.
2. Before anyone calls `finalizeGraduation(T)`, an attacker creates (or finds already-created) the `HyperSwap V2` `T/LT` pair and directly transfers a skewed ratio of `T` and/or `LT` into it via plain ERC20 `transfer`.
3. Attacker (or an unaware keeper) calls the permissionless `Bonding.finalizeGraduation(T)`.
4. Inside, the hostile-pre-seed path performs `pair.swap` rebalancing plus `_routerDepositAndDispose`'s `addLiquidity(..., amountAMin=1, amountBMin=1, ...)` against the now-skewed live reserves rather than the phase-1 cached curve price.
5. LP tokens are minted at the attacker's chosen ratio and locked via `LPLock.recordLock` (one-shot, non-skippable), permanently fixing the mispriced position; the attacker immediately arbitrages the newly-live pool at the correct market price to extract the difference. [4](#0-3)

Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
```markdown
- **Parabola invariant.** With `V_t_init = totalSupply` and `curveSupply = 75%`, the function `tokensForLP(sold) = sold·(S−sold)/S` peaks at `S/4 = LP_RESERVE`. The cap in `_prepareGraduationLiquidity` is defensive — it can never bind in normal operation.
```

```markdown
### Dynamic LP Seeding (zero price gap)

The problem: the reserve asset (LT) has a varying USD price, so the exact number of LP tokens needed to make the DEX pool open at the last curve price is not known ahead of time. Naively seeding the LP with the full 250M reserve would create a large price gap that arbitrage bots would immediately close, transferring value out of the protocol.

Our approach: compute the exact `tokensForLP` at graduation time so the LP opens at **precisely** the last curve price. Burn whatever is left of the 250M reserve.

`_graduate()` performs, in order:

1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).
```
