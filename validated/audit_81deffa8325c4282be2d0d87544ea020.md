This confirms the finding: `CallDispatcher.dispatch(bytes memory encoded)` at [1](#0-0)  has **no access-control modifier whatsoever** — it is `external` and callable by any address, not restricted to the HFT/WrappedHFT/IntentGatewayV2/ExtrinsicIntents contracts that are documented as its intended callers. The same singleton `CallDispatcher` instance is shared across every app on a chain (HFT, WrappedHFT, IntentGatewayV2, ExtrinsicIntents, BridgeToken) as shown by the deployment scripts [2](#0-1) [3](#0-2) , and it also accepts native ETH from anyone via `receive()` [4](#0-3) .

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain any token/ETH balance the shared dispatcher happens to hold - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` executes an attacker-supplied `Call[]` (arbitrary `to`, `value`, `data`) with no caller restriction. Because a single `CallDispatcher` instance is shared as a stateful intermediary by `HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2` and `ExtrinsicIntents` on every chain, any token or native balance that lands on it and is not fully consumed/swept before the enclosing transaction ends is permanently reachable by any external account — mirroring Transit Swap's "unchecked input data" root cause (an unrestricted arbitrary-call executor operating in the context of a contract that transiently custodies value).

### Finding Description
`dispatch()` decodes an ABI-encoded `Call[]` and loops over it, checking only that `to` has code (`extcodesize`), then performs `to.call{value: call.value}(call.data)` [5](#0-4) . There is no `onlyOwner`, `onlyHost`, or allow-list of callers — literally anyone can invoke `dispatch()` directly against the deployed `CallDispatcher` address.

This is safe only under the assumption that the dispatcher never holds a balance except during the exact instant its owning app (HFT/WrappedHFT/IntentGatewayV2/ExtrinsicIntents) is executing its own atomic sequence of `dispatch()` calls. All observed call sites route tokens into the dispatcher, call `dispatch()` for user-supplied `predispatch`/`postdispatch`/`output.call` calldata, then call `dispatch()` a second time to sweep the resulting balance back out [6](#0-5) [7](#0-6) . The sweep, however, only iterates over the tokens explicitly declared in `order.inputs`/`order.output.assets` [8](#0-7) ; any token the attacker-or-order-controlled `Call[]` interacts with that is *not* in that declared list is left on the dispatcher indefinitely, as is any native ETH sent via `receive()` outside of a tracked flow, or an unlimited/residual ERC20 approval left by a `Call[]` (the docs explicitly acknowledge this risk: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution" [9](#0-8) ).

Because `dispatch()` has zero access control, once any value is orphaned on the shared `CallDispatcher` (untracked dust token, unswept ETH, or spendable via a stale approval the dispatcher granted to a router), *any* unrelated third party — not the order's user, not a solver, not a relayer — can call `CallDispatcher.dispatch()` directly with a `Call[]` such as `{to: token, value: 0, data: transfer(attacker, dispatcher.balanceOf(dispatcher))}` or `{to: attacker, value: dispatcher.balance, data: ""}` and take it. This is the same class of bug as Transit Swap: an externally-reachable, insufficiently-restricted call executor operating with custody of value it does not own.

### Impact Explanation
Impact scales with whatever value transiently sits on the shared dispatcher: leftover dust tokens not enumerated in an order's `inputs`/`output.assets`, native ETH sent to it outside a tracked flow, or funds reachable through a stale allowance a `Call[]` left behind to a router. Since the same `CallDispatcher` is reused by every HFT/WrappedHFT deployment and every `IntentGatewayV2`/`ExtrinsicIntents` order on the chain, the aggregate surface across concurrent unrelated flows is not bounded to a single order — theft is a permanent, unrecoverable loss of protocol/user/solver funds, satisfying the "concrete theft ... of funds" bar.

### Likelihood Explanation
Likelihood is opportunistic rather than guaranteed on every transaction — the sweep logic correctly recovers declared-asset dust in the tested paths [10](#0-9) . But it only takes one order/solver/integrator using a `Call[]` that touches an undeclared token, sends value the enclosing flow doesn't fully consume, or sets an unlimited/unreset approval (a pattern the project's own docs warn integrators against), for value to become permanently exposed. Any bot watching for a non-zero `CallDispatcher` balance can then call `dispatch()` immediately, with no privileged access required.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (the registered HFT/WrappedHFT/IntentGatewayV2/ExtrinsicIntents instances), or make the dispatcher a one-time/ephemeral per-call contract (e.g., deployed via CREATE2 and self-destructed, or using a transient-storage session guard) so no balance can outlive the transaction that created it. At minimum, add a caller check (`msg.sender == registered app`) and consider a reentrancy guard, since the current design relies entirely on every calling app perfectly enumerating and sweeping every asset a `Call[]` could touch, which is not enforced by the dispatcher itself.

### Proof of Concept
1. An order's `postdispatch`/`output.call` (or an HFT bridging message's `data`) includes a swap that produces a small amount of a token not listed in `order.output.assets` (e.g., a reward token, a wrong-decimals dust remainder, or an intermediate hop token), or leaves a non-zero allowance from the dispatcher to a router.
2. `IntentsBase._execute` / `IntentGatewayV2.placeOrder` only sweeps the tokens in `order.output.assets`/`order.inputs`; the untracked token balance remains on `CallDispatcher` after the transaction completes [8](#0-7) .
3. Any external account (not the order's user, solver, or app) submits a new transaction calling `CallDispatcher.dispatch(abi.encode([Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, leftoverToken.balanceOf(dispatcher))})]))` directly against the publicly known, unguarded `CallDispatcher` address [5](#0-4) .
4. The call succeeds because `dispatch()` performs no caller check — the attacker walks away with the balance, and any dust-collection accounting in the app that expected to sweep it (`DustCollected` event) never fires for that amount.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
