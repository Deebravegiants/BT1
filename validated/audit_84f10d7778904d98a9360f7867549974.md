### Title
CREATE2 address collision via unseparated concatenation of `code` and `input_data` - (File: `substrate/frame/revive/src/address.rs`)

### Summary
`pallet_revive`'s `create2` address-derivation function hashes the raw concatenation of the (attacker/deployer-controlled) `code` and `input_data` byte arrays without any length prefix or separator. Because both are independently-sized, attacker-controlled dynamic byte strings, this is the same collision class as `abi.encodePacked(a, b)` with two dynamic arguments: shifting bytes from the tail of `code` to the head of `input_data` (or vice versa) produces an identical concatenated byte string and therefore an identical `init_code_hash`/predicted contract address, while the two deployments actually execute *different* bytecode and *different* constructor calldata.

### Finding Description
`create2` is defined as: [1](#0-0) 

```rust
pub fn create2(deployer: &H160, code: &[u8], input_data: &[u8], salt: &[u8; 32]) -> H160 {
	let init_code_hash = {
		let init_code: Vec<u8> = code.into_iter().chain(input_data).cloned().collect();
		keccak_256(init_code.as_ref())
	};
	...
}
```

`code` and `input_data` are concatenated with `.chain()` — a raw byte concatenation with no length prefix, no separator, and no domain tag distinguishing where `code` ends and `input_data` begins. This is exactly the pattern the Solidity documentation warns against for `abi.encodePacked` with more than one dynamic argument, and it is the same root cause as the reported API3 `StorageUtils.sol#storeSubscription` issue: two semantically distinct dynamic-length inputs are concatenated before hashing, so different `(code, input_data)` pairs whose concatenations happen to be byte-identical produce the identical hash.

Critically, unlike real EVM `CREATE2` — where there is no separate "code" and "constructor args" at the protocol level (the entire `init_code` blob is executed as one program, so any byte-identical `init_code` always produces byte-identical execution) — `pallet_revive` treats `code` and `input_data` as semantically distinct at execution time: `code` is compiled/loaded and becomes the contract's actual stored bytecode, while `input_data` is passed separately as constructor calldata. This is visible in the instantiation path: [2](#0-1) 

Here `address::create2(&deployer, executable.code(), input_data, salt)` is used to derive the address, but `executable` (compiled from `code`) is what is actually executed as the contract's bytecode, and `input_data` is passed separately as the constructor's calldata. Because the address is derived from `keccak256(code || input_data)` rather than binding each field independently (e.g. `keccak256(code) || keccak256(input_data)` or length-prefixed encoding), two different `(code, input_data)` splits that produce the same concatenated bytes will yield the same predicted address, yet result in genuinely different deployed bytecode and different constructor calldata.

### Impact Explanation
`CREATE2`'s entire security value (as used across the ecosystem for counterfactual deployment, deterministic factories, state channels, escrow-before-deploy patterns, etc.) rests on the guarantee that a given address is cryptographically bound to one specific bytecode + constructor input. This implementation breaks that guarantee: a deployer can advertise/predict an address using `(code, input_data, salt)`, have a counterparty rely on that address always running `code`, and later actually instantiate with a different split `(code', input_data')` that hashes to the identical address but installs different bytecode (e.g. `code'` missing trailing bytes/opcodes) with different constructor calldata. This is a "bait-and-switch" primitive that defeats deterministic-address trust assumptions used by higher-level protocols/tooling built on `pallet_revive`.

### Likelihood Explanation
Exploitation requires the party who submits the instantiate call to also control the choice of `(code, input_data)` splitting — which they always do, since both are user-supplied arguments to `instantiate`/`instantiate_with_code`. No privileged role or trusted party compromise is needed; any account instantiating a contract can deliberately choose a split that collides with a previously-advertised address. The barrier to exploitation is only that the attacker must want to present two different byte-splits of the same total content, which is trivial. The realistic victim is any protocol/tooling that relies on the deterministic `code ⇒ address` binding when the same account (or a account it colludes with) is expected to eventually deploy.

### Recommendation
Bind each dynamic field independently before hashing, e.g. compute `init_code_hash = keccak256(code) || length_prefix || keccak256(input_data)`, or otherwise ensure at most one dynamic-length value is used raw in the concatenation (mirroring the `abi.encode`-style recommendation from the original report). At minimum, separate `code` and `input_data` with a fixed-length domain separator or explicit length fields before hashing, consistent with the pattern already used elsewhere in the codebase (e.g. `bridges/primitives/messages/src/lane.rs`'s `VALUES_SEPARATOR` for `HashedLaneId`, or `DefaultAddressGenerator::contract_address` in `substrate/frame/contracts/src/address.rs`, which relies on SCALE's self-describing encoding rather than raw concatenation).

### Proof of Concept
Let `code = [0x60, 0x00, 0x60, 0x00, 0x55]` (5 bytes) and `input_data = [0x01, 0x02]`.
- Deployment A: `create2(deployer, code, input_data, salt)` hashes `keccak256([0x60,0x00,0x60,0x00,0x55,0x01,0x02])`, deploying bytecode `code` (5 bytes) with constructor calldata `[0x01,0x02]`.
- Deployment B: `code' = [0x60,0x00,0x60,0x00]` (4 bytes, last byte moved), `input_data' = [0x55,0x01,0x02]`. `create2(deployer, code', input_data', salt)` hashes the identical byte string `keccak256([0x60,0x00,0x60,0x00,0x55,0x01,0x02])`, producing the **same address** as Deployment A, but deploys a **different, 4-byte bytecode** `code'` with constructor calldata `[0x55,0x01,0x02]` instead.

Both are valid, unprivileged calls to `instantiate`/`instantiate_with_code`, and the collision is visible directly from the `create2` implementation cited above without requiring any trusted role or mocked path. Full end-to-end runtime confirmation (deploying both and checking resulting `AccountInfoOf`/bytecode) was not performed within available tool budget, so exact interpreter behavior on the truncated `code'` (e.g., whether it fails validation for other reasons such as minimum-bytecode-length checks) is not verified — this should be confirmed by a background agent before filing.

/// Determine the address of a contract using the CREATE2 semantics.
pub fn create2(deployer: &H160, code: &[u8], input_data: &[u8], salt: &[u8; 32]) -> H160 {
	let init_code_hash = {
		let init_code: Vec<u8> = code.into_iter().chain(input_data).cloned().collect();
		keccak_256(init_code.as_ref())
	};
	let mut bytes = [0; 85];
	bytes[0] = 0xff;
	bytes[1..21].copy_from_slice(deployer.as_bytes());
	bytes[21..53].copy_from_slice(salt);
	bytes[53..85].copy_from_slice(&init_code_hash);
	let hash = keccak_256(&bytes);
	H160::from_slice(&hash[12..])
}
