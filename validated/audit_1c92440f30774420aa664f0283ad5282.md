### Title
Unspent native TRX not refunded after fee-swap in `placeOrder` causes permanent user fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` swaps leftover native value for the protocol fee token via `swapETHForExactTokens`, but unlike the canonical EVM implementation, it never captures the actual amount spent by the swap nor refunds the unspent remainder to the caller. Any native-token overpayment supplied to cover `order.fees` is silently absorbed by the router's exact-output refund mechanism into the contract itself and never returned to the user, permanently trapping user funds in the contract with no accounting record.

### Finding Description
In `placeOrder`, when `order.fees > 0` and the caller has leftover native `msgValue` after input escrow, the contract swaps that value for the fee token: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = IDispatcher(hostAddr).feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

`swapETHForExactTokens` is an exact-output swap: it only consumes as much ETH/native value as needed to buy `order.fees` worth of the fee token, and refunds any unspent value back to `msg.sender` of the call — which here is the `IntentGatewayV2` contract itself, not the original order-placing user. The function has no subsequent step to (a) capture the actual amount spent (`amounts[0]` from the router's return value) or (b) forward any remaining `msgValue`/refunded value back to the depositor. Execution then falls straight through to `emit OrderPlaced(...)` and returns.

This is exactly the bug class from the external report: an external, unprivileged-reachable method (`placeOrder`) that performs multiple token/value movements but omits a final "check remaining balance and transfer it back" step. The canonical (non-Tron) implementation in `evm/src/apps/IntentGatewayV2.sol` correctly handles this by capturing `amounts[0]` and refunding the true remainder: [2](#0-1) 

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```

The Tron variant lacks both the `amounts[0]` deduction and the terminal refund entirely, so any native-token overpayment intended to cover `order.fees` becomes stranded, un-escrowed native balance inside the `IntentGatewayV2` contract with no corresponding accounting entry (`_orders[commitment][...]` is never credited for it) and no `DustCollected` event, unlike other dust paths in the same contract.

### Impact Explanation
Users placing orders with `order.fees > 0` and paying via native value on the Tron deployment lose any overpayment beyond the exact amount the router needs to acquire the fee token. Because the excess is never recorded against the order's commitment nor refunded, it is not retrievable by the user through any normal contract flow (cancel/withdraw only release amounts tracked in `_orders`). This constitutes a concrete, permanent loss of user funds for every over-funded native-fee order — a direct violation of the "funds must not be permanently frozen or lost" invariant for the Intent Gateway's escrow/fee accounting.

### Likelihood Explanation
This triggers on every ordinary `placeOrder` call on the Tron deployment where the user pays the order fee in native token and supplies `msg.value` that isn't exactly equal to the router's required input (which is the common case, since callers cannot predict the router's exact required input for an exact-output swap ahead of time, and the reference off-chain SDK/UI logic naturally overestimates to be safe). No malicious actor, governance, or admin action is required — it is a self-inflicted but protocol-caused loss on normal usage.

### Recommendation
Mirror the canonical `evm/src/apps/IntentGatewayV2.sol` pattern: capture the `amounts[0]` returned by `swapETHForExactTokens`, subtract it from `msgValue`, and refund any remaining `msgValue` to `msg.sender` at the end of `placeOrder` in the Tron contract, exactly as recommended by the external report — check and transfer back all remaining token/native balances after the external function completes.

### Proof of Concept
1. On the Tron chain deployment, call `placeOrder(order, graffiti)` with `order.fees = F > 0`, no ERC-20 input requiring native value, and `msg.value = M` where `M` comfortably exceeds the native amount needed to buy `F` fee tokens from `uniswapV2Router`.
2. `swapETHForExactTokens{value: M}(F, path, address(this), deadline)` executes, spending only `amountIn < M` and refunding `M - amountIn` back to `address(this)` (the `IntentGatewayV2` contract), per standard UniswapV2Router02 semantics.
3. `placeOrder` returns without ever inspecting or forwarding the refunded `M - amountIn` to `msg.sender`; `_orders[commitment][...]` was never credited with this amount either.
4. The user has permanently lost `M - amountIn` of native value with no way to reclaim it through `cancelOrder`, `fillOrder`, or any other contract function, since it is untracked native balance sitting in the contract.
