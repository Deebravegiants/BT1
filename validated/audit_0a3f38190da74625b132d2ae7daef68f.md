Confirmed: `SimplexPaymaster` is deployed on Arbitrum (`EVM-42161`) and Base (`EVM-8453`), both Optimistic-Rollup-style L2s that rely on a Chainlink L2 Sequencer Uptime feed for safe oracle consumption. The contract's `_getOraclePrice` function does not check any sequencer feed.### Title
Missing L2 sequencer-uptime check in `SimplexPaymaster._getOraclePrice` allows stale/mispriced gas charges during sequencer downtime - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` consumes Chainlink `AggregatorV3Interface.latestRoundData()` for both the native/USD oracle and each token/USD oracle via `_getOraclePrice`, validating only `answer > 0` and freshness against `maxOracleAge`. It never checks an L2 Sequencer Uptime Feed. The contract is deployed on Arbitrum (`EVM-42161`) and Base (`EVM-8453`), both of which are Optimistic-Rollup L2s where Chainlink's own integration guidance requires checking `SequencerUptimeFeed` before trusting price data, because during a sequencer outage the "last observed" round can remain within the staleness window while being stale relative to real market conditions, and once the sequencer restarts, Chainlink enforces a grace period before feeds are considered trustworthy again. [1](#0-0) 

### Finding Description
`_getOraclePrice` is the sole gate used to price gas in ERC-20 tokens for every sponsored `UserOperation`:

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
``` [2](#0-1) 

This function is called from `_tokenPrice`, which is used both in the ERC-4337 validation path (`_fetchDetails`, invoked per sponsored op) and in the treasury-only `swapAndDeposit` fee-recycling flow: [3](#0-2) [4](#0-3) [5](#0-4) 

On Arbitrum and Base — both confirmed live deployment targets of `SimplexPaymaster` per the contract-address docs — Chainlink price feeds are backed by an off-chain sequencer that batches and forwards L2 transactions/updates. If the sequencer goes down, oracle updates can freeze while `updatedAt` stays inside `maxOracleAge`, or a malicious/compromised sequencer operator situation can allow a backlog of stale price reports to be pushed through once service resumes, before the traditional Chainlink grace period would otherwise reject them. `_getOraclePrice` has no way to detect either condition because it never queries a sequencer uptime feed. This exactly mirrors the reported analog (`BLVaultManagerLido#_validatePrice`), where Chainlink `answeredInRound`/`updatedAt` checks are present but the sequencer liveness check that Chainlink's documentation mandates for L2 deployments is absent. [6](#0-5) [7](#0-6) 

### Impact Explanation
Any unprivileged UserOp sender (a "message dispatcher"/gas-payment sender reachable without any privilege) triggers `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` on every sponsored transaction. During a sequencer outage or sequencer-restart grace window on Arbitrum/Base, the price returned can be stale/wrong in either direction:
- If the native-asset price is understated relative to the true market price (or the token price overstated), users are overcharged in ERC-20 tokens relative to the true gas cost, directly benefiting the paymaster treasury at users' expense but breaking the pricing invariant `SimplexPaymaster` promises.
- If the native-asset price is overstated (or token price understated), users underpay for gas, draining `SimplexPaymaster`'s EntryPoint deposit and eating the difference from treasury-owned funds — a direct theft-of-funds vector against the paymaster's treasury/EntryPoint balance, since the ERC-20 collected is worth less than the native gas the paymaster fronts.
This is a concrete freezing/mispricing-of-funds condition reachable by a single unprivileged UserOp, satisfying the Medium bar (funds mis-transfer via unsound price data), analogous in root cause to the original Chainlink sequencer-check omission.

### Likelihood Explanation
L2 sequencer downtime is an observed, recurring event on rollups (Arbitrum and Base have both experienced sequencer outages in the past), and no special conditions are required to trigger the vulnerable code path — every sponsored `UserOperation` routes through `_getOraclePrice` with no additional gating. The `maxOracleAge` bound (configurable up to `MAX_ORACLE_AGE = 7 days`) is far larger than typical sequencer outage windows, so an outage well within that window would pass the existing staleness check undetected. [8](#0-7) 

### Recommendation
Add an `AggregatorV3Interface sequencerUptimeFeed` per L2 deployment (configurable via governance `UpdateParams`, similar to `nativeOracle`), and in `_getOraclePrice` (or a wrapper called before it) check `latestRoundData()` on the sequencer feed: revert if `answer != 0` (sequencer down) and additionally enforce a grace period (e.g. Chainlink's recommended pattern requiring `block.timestamp - startedAt > GRACE_PERIOD_TIME` after the sequencer comes back up) before trusting price data again. On chains without an L2 sequencer (e.g. Ethereum mainnet, BSC, Polygon, Gnosis), this check should be a no-op/disabled via configuration.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum/Base as done in production (`0x7281Bccb...` on Arbitrum, `0x15b3B03C...` on Base).
2. Simulate/observe an Arbitrum or Base sequencer outage (as has occurred historically) where the sequencer stops posting new L2 blocks/transactions for a period shorter than `maxOracleAge` (up to 7 days per `MAX_ORACLE_AGE`).
3. During the outage, market price of the native asset or a registered ERC-20 moves significantly (e.g., a native asset crash or spike) while the last Chainlink round on that L2 remains "fresh" per `updatedAt` (or a backlogged stale update is pushed once the sequencer resumes, inside the same block that user transactions land).
4. A UserOp is submitted paying gas via `SimplexPaymaster` (mode `0x00` or `0x02`); `_fetchDetails` calls `_tokenPrice` → `_getOraclePrice`, which returns the stale price without any sequencer check, computing `tokenPrice` from out-of-date market data.
5. The prefund/charge computed in `_erc20Cost` using this stale `tokenPrice` is mismatched with the real-time cost of the native gas the paymaster fronts through the EntryPoint, either overcharging the user or underpricing gas and draining paymaster-held EntryPoint deposit/treasury value — with no check (`_getOraclePrice`, lines 662-668) able to detect or block this condition.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
