## Title
Blocklisted `payer`/relayer address on `feeToken` permanently bricks POST/GET timeout refunds in `EvmHost.dispatchTimeOut` / `dispatchIncoming` - (File: `evm/src/core/EvmHost.sol`)

## Summary
`EvmHost.dispatchTimeOut` (for both POST and GET requests) and `EvmHost.dispatchIncoming` (for GET responses) execute the destination application's callback and then unconditionally attempt an `IERC20(feeToken()).safeTransfer(...)` to a caller-supplied address, all within a single atomic external call from `HandlerV2`. If `feeToken()` is a blocklist-capable stablecoin (e.g. USDC/USDT — explicitly named as typical fee tokens in the docs) and the recipient of that transfer is blocklisted, the `safeTransfer` reverts and rolls back the entire transaction, including the application-level state changes (e.g. re-minting burned tokens) that the callback had already performed. Because the blocklisted status never changes, the request can never be successfully processed again, permanently freezing both the relayer fee and any application-level refund/unlock logic tied to that delivery.

## Finding Description
`dispatchTimeOut` for POST requests refunds the relayer fee to `meta.sender` (the `payer` recorded at dispatch time) only after successfully invoking the app's `onPostRequestTimeout` callback: [1](#0-0) 

The same pattern exists for GET timeouts: [2](#0-1) 

and for GET responses, where the relayer fee is paid to the delivering relayer after `onGetResponse` succeeds: [3](#0-2) 

`post.payer` is a caller-supplied field on `DispatchPost`, stored verbatim as `FeeMetadata.sender` at dispatch time: [4](#0-3) 

`HandlerV2.handlePostRequestTimeouts` and `handleGetRequestTimeouts` call `host.dispatchTimeOut(...)` directly in a loop with no try/catch — any revert from the fee transfer bubbles up and reverts the whole call: [5](#0-4) [6](#0-5) 

Crucially, unlike `dispatchIncoming` for POST requests (which wraps the app's `onAccept` call in a low-level `.call()` with a `success` check and swallows failures so the message stays retryable): [7](#0-6) 

the fee-transfer step in `dispatchTimeOut`/`dispatchIncoming` is a direct `safeTransfer` with no failure isolation. If the app callback (e.g. `HyperFungibleToken.onPostRequestTimeout`, which re-mints burned tokens to the refund address) succeeds but the subsequent fee refund to the blocklisted `payer` reverts, the *entire* transaction — including the token re-mint that had already logically completed — is rolled back: [8](#0-7) 

Since `payer` is an arbitrary caller-controlled field on `DispatchPost` (set when dispatching the original message, independent of the `message.from` refund-recipient parsed from the body), an attacker who controls the dispatch of a message (as a self-relaying user, or via any app that lets the caller freely choose the fee `payer`) can set `payer` to an address blocklisted on the fee token. Because the deletion of `_requestCommitments[commitment]` also happens inside the same atomic call that reverts, the state is never advanced — every future retry hits the identical revert, permanently:
1. freezing the relayer fee held by the host for that commitment, and
2. preventing the destination/source application from ever completing its timeout-triggered refund/unlock logic for that specific message, since that logic is atomically coupled to the failing fee transfer.

This mirrors the referenced UMA/KPIRewarder bug class: a message-flow completion step is gated on an unconditional ERC20 transfer to an attacker-chosen, potentially blocklisted address, with no isolation between the "core" state transition and the "reward" transfer.

## Impact Explanation
This is a permanent freezing-of-funds bug reachable by a single unprivileged dispatch: any relayer fee (in a blocklist-capable `feeToken`) attached to a POST/GET request whose `payer` becomes blocklisted is permanently stuck in `EvmHost`, and the associated application-level timeout logic (e.g. token refunds in `HyperFungibleToken`/`WrappedHyperFungibleToken`, escrow releases in intents apps that rely on `onPostRequestTimeout`) can never execute successfully for that commitment. This satisfies the "permanent freezing of funds" bar. Additionally, because `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` process multiple leaves per call with no isolation, a relayer who unknowingly batches a poisoned commitment together with legitimate ones will have the entire batch revert, degrading delivery of unrelated timeouts until the poisoned one is manually excluded.

## Likelihood Explanation
Reaching this requires only dispatching an ordinary POST/GET request (via `IDispatcher.dispatch`) with `payer` set to an address already blocklisted (or blocklistable in the future) on the configured `feeToken`, then allowing/forcing the request to time out. Since `payer` is a plain user-supplied parameter with no validation, and USDC/USDT (both blocklist-capable) are explicitly cited as typical `feeToken` choices in the project's own documentation, the precondition is realistic and requires no special privilege — a single unprivileged dispatch transaction is sufficient to set up the freeze.

## Recommendation
Isolate the fee-refund transfer from the core state transition: wrap `IERC20(feeToken()).safeTransfer(...)` in `dispatchTimeOut`/`dispatchIncoming` in a try/catch (or low-level `call`) so that a reverting transfer does not roll back the already-executed application callback or the receipt/commitment bookkeeping. On transfer failure, credit the fee to an internal, pull-based balance mapping keyed by recipient (allowing the blocklisted party, or a designated recovery address, to withdraw later once/if unblocked) rather than pushing funds unconditionally and atomically with unrelated state changes.

## Proof of Concept
1. Deploy `EvmHost` with `feeToken()` set to a blocklist-capable ERC20 (e.g. mock USDC).
2. Call `HyperFungibleToken.send(...)` (or any `IDispatcher.dispatch(DispatchPost)` caller) with `payer` set to address `X`, and a non-zero `relayerFee`, targeting a chain/timeout that will not be delivered.
3. Have the token issuer blocklist `X` on the fee token (or use an address already blocklisted).
4. Wait for timeout, submit a valid non-membership proof via `HandlerV2.handlePostRequestTimeouts`.
5. Observe: `host.dispatchTimeOut` calls the app's `onPostRequestTimeout` (which would re-mint tokens to the refund address), then attempts `safeTransfer(X, fee)`, which reverts due to the blocklist; the whole transaction reverts, so no re-mint occurs and `_requestCommitments[commitment]` is unchanged.
6. Repeat step 4 indefinitely — the transaction always reverts identically, proving the fee and the associated app-level refund are permanently stuck.

     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.

        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
