### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate`, then trusts the `shop` value taken from an **unauthenticated HTTP header** (`x-shopify-shop-domain` / `shopify-shop-domain`) when constructing the `WebhookMetadata` passed to the app's handler. The binding the gem claims to guarantee — "the shop this webhook came from" equals "the shop the HMAC was computed for" — does not actually hold, because the HMAC signable string is only the raw body.

### Finding Description
`Registry.process` gates all webhook handling on a single check: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the Shopify headers are included in the signed material: [3](#0-2) 

Yet `request.shop` (read straight from the `shop-domain` header) is passed on, unauthenticated, as the tenant identifier to the app's handler: [4](#0-3) 

The documented contract tells app developers that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "the shop domain of the webhook," implying that the shop is trustworthy once the call succeeds: [5](#0-4) [6](#0-5) 

Because a single app in this gem's model shares one `api_secret_key` across every installed shop (`Context.api_secret_key`, used identically for all tenants in `HmacValidator.validate`), any shop that has legitimately installed the app can capture a genuine webhook it received from Shopify (valid raw body + valid HMAC, both computed with the app's one shared secret) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `shop-domain` header. `HmacValidator.validate` still succeeds, because it never inspects the header, only the body. The equality the gem is supposed to enforce — `shop authenticated by HMAC == shop acted upon` — is broken: the HMAC authenticates "this body came from an app-secret holder," while `request.shop` supplies an attacker-chosen tenant label that the handler is told to trust.

### Impact Explanation
This crosses the tenant boundary the gem is meant to enforce for multi-tenant apps: a shop that is not the origin of an event can cause the app to process a spoofed event under another shop's identity (cross-tenant access), since `data.shop` is the only tenant-scoping value handlers are given by this API. Any app that keys persistence, authorization, or side effects on `data.shop` (as the gem's own example in `docs/usage/webhooks.md` does — `shop_domain: data.shop`) is exposed to cross-tenant data injection/confusion.

### Likelihood Explanation
Any merchant/developer who has legitimately installed the app (an "unprivileged internet user" relative to other tenants) automatically receives real webhooks with valid signatures for their own shop and can freely re-POST that captured payload with a modified header to the same public webhook endpoint — no access to `api_secret_key` or any other tenant's credentials is required.

### Recommendation
Include the relevant Shopify identity headers (at minimum `shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signable string for webhook requests, or otherwise cryptographically bind them to the verified body, so `Utils::HmacValidator.validate` fails whenever any of these header values has been altered relative to what Shopify actually sent.

### Proof of Concept
1. App `myapp` has two installs: `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both sharing the same `api_secret_key`.
2. Attacker's own shop triggers a real event (e.g. `orders/create`); Shopify posts to the app with a valid `x-shopify-hmac-sha256` computed over the raw body using the shared secret, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures that raw body + HMAC header (both visible to them, since it's their own webhook) and re-issues an HTTP POST to the same endpoint, keeping raw body and HMAC identical but changing the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — this passes.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and the app processes it as if it were a genuine event from `victim-shop`, per [4](#0-3) .
