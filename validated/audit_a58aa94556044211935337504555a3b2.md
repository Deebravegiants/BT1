Confirmed. I have enough evidence to write the finding.### Title
Unchecked ERC20 return value in Tron `IntentGatewayV2.withdraw()`/`onAccept(SweepDust)` permits silent transfer failures to permanently freeze escrowed user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` uses raw low-level `.call()` invocations of `IERC20.transfer` and only checks that the *call itself did not revert*, never decoding/validating the returned boolean. Non-compliant tokens (TRC-20/ERC-20 analogues of ZRX/HT/BNB/USDT-style tokens) that return `false` on failure instead of reverting will make `success == true` while the actual token balance is never moved. Escrow accounting is nonetheless decremented and the order is marked filled/refunded, permanently losing the user's or solver's funds with no possibility of recovery.

### Finding Description
`withdraw()` in the Tron contract settles escrowed inputs and transaction fees using: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

`success` here reflects only whether the external call reverted — it does **not** inspect `returndata` to confirm the token itself reported a successful transfer (`true`). Many ERC20/TRC20 tokens (the exact bug class cited in the referenced report — ZRX, HT, WOO-style tokens) return `false` on a failed transfer rather than reverting. With this pattern, such a failure is silently accepted as success.

Immediately after, regardless of whether tokens actually moved, escrow state is unconditionally mutated: [2](#0-1) 
```solidity
_orders[body.commitment][token] -= amount;
```
and the order is already marked filled at the top of the function: [3](#0-2) 

The same unchecked-call pattern also handles the transaction-fee payout and the `SweepDust` admin sweep in `onAccept`: [4](#0-3) [5](#0-4) 

This is entered from `onAccept()`, which is invoked by the ISMP host whenever any relayer delivers a `RedeemEscrow`/`RefundEscrow` message from the counterpart chain — an unprivileged, permissionless path triggered by relayed proofs: [6](#0-5) 

It also matches the report's core complaint precisely: the sibling implementation of the same contract on standard EVM chains (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly uses `SafeERC20.safeTransfer`, which reverts on a `false` return, and this same file even imports `SafeERC20`: [7](#0-6) [8](#0-7) 
yet `withdraw()` deliberately bypasses `safeTransfer` in favor of a manual low-level call that fails to check returndata — the exact regression class flagged in the audit report.

### Impact Explanation
For any escrowed token that follows the non-reverting "return false on failure" ERC20 convention (an established, common real-world token class), a filler/solver or a refunded user can be told their withdrawal succeeded (order marked filled/refunded, escrow debited, event emitted) while never receiving the tokens. The escrowed balance is irrecoverably lost — the escrow accounting is already decremented and the commitment already marked filled/refunded, so there is no retry path. This is a permanent freezing/loss of escrowed user funds, satisfying the Medium/High bar for concrete fund loss.

### Likelihood Explanation
Likelihood is moderate-to-high in practice for deployments on Tron/TRC20 ecosystems, where non-standard token semantics (including tokens that return `false` instead of reverting, akin to the ZRX/HT class cited in the report, and TRC20 tokens with quirky compliance) are common. Any order whose input/output token is configured as one of these tokens is reachable by a normal user placing an order and any relayer delivering the settlement message — no privileged role is required.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`, `IntentGatewayV2.sol` on EVM). This ensures both call failure and a `false` boolean return are treated as failures and revert the state mutation, preventing escrow debits/`_filled` marks from being committed when a transfer did not actually succeed.

### Proof of Concept
1. Configure an order whose input/output token behaves like ZRX/HT (i.e., its `transfer()` function returns `false` on failure conditions instead of reverting — e.g., a paused/blacklisted state, or insufficient allowance edge cases specific to the token's custom logic).
2. Attacker (or any user) triggers a scenario in which the token's `transfer` call to the `beneficiary` fails internally and returns `false` (e.g., beneficiary is blacklisted by the token, or a token-specific guard rejects the transfer) but the low-level `.call` does not revert.
3. `RedeemEscrow`/`RefundEscrow` is delivered via `onAccept()` → `withdraw()`. `success` is `true` (the call didn't revert), so `TransferFailed` is not raised.
4. `_orders[body.commitment][token] -= amount` executes, and `_filled[body.commitment] = beneficiary` is already set — the order is permanently marked complete.
5. The beneficiary's on-chain token balance never increased; the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to reclaim them (escrow already zeroed and order already filled/refunded).
