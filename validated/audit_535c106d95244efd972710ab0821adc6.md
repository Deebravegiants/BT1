### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is swapped back to the Host itself and permanently stuck with no recovery path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and swap it into the fee token using `swapETHForExactTokens`. Unlike the `IntentGatewayV2`/`IntentsBase` flows in this same codebase, which explicitly refund unspent `msg.value` back to the original caller via `_sendValue`, these `EvmHost` functions never refund the caller. Instead, any unspent ETH from the Uniswap swap is returned by the router to `msg.sender` of the swap call, which is `EvmHost` itself, not the original dispatcher. That leftover native ETH balance sits in the `EvmHost` contract permanently, and there is no native-ETH withdrawal path exposed to anyone (only `feeToken` revenue is withdrawable via the governance-only `IHostManager.withdrawFees` path).

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and `dispatch(DispatchGet)`: [2](#0-1) 

and `fundRequest`: [3](#0-2) 

all follow the same pattern: when `msg.value > 0`, the entire `msg.value` is forwarded to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. UniswapV2Router02's `swapETHForExactTokens` implementation only spends exactly the amount needed to buy `post.fee`/`get.fee`/`amount` output tokens and refunds any unused ETH back to `msg.sender` of that call — which here is the `EvmHost` contract address (not the end user who called `dispatch`/`fundRequest`).

Contrast this with the sibling `IntentGatewayV2`/`ExtrinsicIntents` contracts in the same repo, which explicitly track `msgValue` and call `_sendValue(msg.sender, msgValue)` to refund any leftover native token to the original caller after a fee swap: [4](#0-3) 

`EvmHost.dispatch()`/`fundRequest()` has no equivalent refund step, and no `receive()`/`withdraw` function was found that lets any party — including governance — sweep native ETH out of the host (the only withdrawal interface, `IHostManager.updateHostParams`/fee withdrawal, operates on the ERC20 `feeToken`, not native ETH): [5](#0-4) 

Any user who slightly overestimates the required `fee`/`amount` and sends excess `msg.value` to `dispatch()` or `fundRequest()` has that excess permanently locked in `EvmHost`, exactly analogous to the Pyth `updatePythPrice` report where leftover fee ETH becomes non-refundable and stuck in the contract — except here there isn't even a failed-refund-attempt revert path; the excess silently accumulates in the contract with no owner-level sweep function at all.

### Impact Explanation
Any unprivileged caller dispatching a POST/GET request or funding a pending request with native ETH can lose the difference between `msg.value` and the actual fee token cost. Because `getUpdateFee`-equivalent pricing (Uniswap swap output) is variable and callers must send a superficially-generous `msg.value` to guard against slippage/price movement between quote and execution, overpayment is a normal, expected occurrence, not an edge case. Since there is no mechanism anywhere in `EvmHost` to reclaim this stuck native ETH, funds are permanently frozen in the contract — a direct loss of user funds with no recovery path, matching the "Medium" severity class of the reference report (non-refundable, permanently locked funds, not attacker-profitable but definite value loss for legitimate users).

### Likelihood Explanation
High likelihood in practice: every call to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` that pays with native ETH and doesn't send the *exact* wei amount consumed by the Uniswap swap will strand the difference. Since off-chain callers estimate fees before submitting a transaction (fee/price can drift due to AMM slippage or multi-block delay), overpayment by any nonzero amount is the common case, not a crafted attack.

### Recommendation
Track the actual amount spent by the Uniswap swap (e.g., `amounts[0]` returned by `swapETHForExactTokens`) and refund `msg.value - amounts[0]` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, mirroring the `_sendValue(msg.sender, msgValue)` pattern already used in `ExtrinsicIntents.sol`/`IntentGatewayV2.sol`. Alternatively (or additionally), expose a governance-restricted native-ETH sweep function so any residual balance is not permanently unrecoverable.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `post.fee = 100` (fee-token units) and sends `msg.value = 1 ETH` to comfortably cover the swap, per: [1](#0-0) 
2. `swapETHForExactTokens{value: 1 ETH}(100, path, address(this), block.timestamp)` only spends, say, `0.01 ETH` to acquire the 100 fee-token units, and the router refunds the remaining `0.99 ETH` to `msg.sender` of the swap call — which is `EvmHost`, not the user.
3. `EvmHost.dispatch` returns normally; the user's transaction succeeds but their `0.99 ETH` is now held by `EvmHost`.
4. No function in `EvmHost` (checked: only `feeToken`-based `IHostManager.withdrawFees`-style governance action exists) lets anyone withdraw this native ETH balance, so it is permanently locked in the contract.
