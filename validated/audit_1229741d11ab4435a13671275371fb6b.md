### Title
Escrow accounting in the Tron `IntentGatewayV2.placeOrder` ignores fee-on-transfer token deductions, causing over-committed escrow and stuck/insolvent refunds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrow commitment and credited `_orders[commitment][token]` balances from the user-supplied `order.inputs[i].amount` (minus protocol fee), and then separately calls `IERC20(token).safeTransferFrom(msg.sender, ..., amount)` for that same nominal amount, without ever checking how many tokens the contract (or the predispatch `dispatcher`) actually received. If the input token deducts a transfer fee, the contract ends up crediting more in escrow than it actually holds, unlike the EVM-mainline `IntentGatewayV2.sol`, which was hardened against exactly this class of bug.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` (lines 338-506):
- `reducedInputs[i].amount` is derived purely by subtracting the protocol fee from `order.inputs[i].amount` (lines 359-385), with no reference to actual token balances.
- Tokens are then moved with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (line 459, no-predispatch path) or `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` followed by a `dispatcher.transfer` sweep sized to `requiredAmount` (lines 405-446, predispatch path) — but the code never re-measures `balanceOf(address(this))` before vs. after the transfer.
- `_orders[commitment][token] += reducedInputs[i].amount` (lines 441, 463) is credited using the nominal (pre-fee) amount.

This is exactly the class of bug in the original report: the code assumes `amountSent == amountReceived`, which breaks for fee-on-transfer/deflationary ERC20s. [1](#0-0) 

By contrast, the primary EVM `IntentGatewayV2.sol` explicitly guards against this: it snapshots `balanceOf` before and after `safeTransferFrom` / sweep calls and mutates `order.inputs[i].amount` to the *actual received* amount before computing the commitment and crediting escrow. [2](#0-1) [3](#0-2)  This is confirmed by dedicated tests (`testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) that assert escrow equals *actual received* amount, not the nominal input. [4](#0-3) 

The Tron fork lacks this protection entirely for both the direct-transfer and predispatch paths. [5](#0-4) 

### Impact Explanation
When a fee-on-transfer token is listed as an order input, `placeOrder` will credit `_orders[commitment][token]` for more tokens than the contract physically received. Downstream, `withdraw()` (used by `cancelOrder`, `onAccept` for `RedeemEscrow`/`RefundEscrow`, and `onGetResponse`) pushes out `body.tokens[i].amount` — the full nominal amount recorded in the order — via a raw low-level `token.call(transfer.selector, ...)` (`evm/tron/contracts/apps/IntentGatewayV2.sol` lines 691-714). Because the contract's real token balance is short by the transfer fee, this transfer either:
- reverts, permanently freezing the escrowed funds for that order (since `_filled[commitment]` is already set to the beneficiary before the transfer attempt, a failed transfer leaves the order marked filled/refunded with no clean retry path), or
- succeeds by draining balance that belongs to other orders' escrow (since all tokens of that type sit in one shared contract balance), causing an accounting shortfall that can strand or steal other users' escrowed funds once enough orders exhaust the buffer.

This satisfies the required impact bar: freezing of user funds and/or unbacked escrow accounting leading to insolvency across orders that share the same input token. [6](#0-5) 

### Likelihood Explanation
`placeOrder` is a fully permissionless, unprivileged entry point reachable by any user submitting a single transaction with a fee-on-transfer/deflationary token as an input asset — no special role or governance action is required. [7](#0-6)  While the currently deployed input tokens may not charge transfer fees today, the report class (as in the original finding) applies: any token added to the accepted set, or an existing standard proxy token that later enables a fee switch (e.g. USDT-style tokens), triggers the bug automatically without any code change on the gateway's side. The Tron contract is a maintained fork of the hardened EVM `IntentGatewayV2.sol`, so the omission looks like a fork-drift regression rather than a deliberate design choice, increasing the likelihood it goes unnoticed until exploited.

### Recommendation
Port the balance-before/balance-after pattern already implemented in `evm/src/apps/IntentGatewayV2.sol` (and its own tron fork's fee-handling for `order.fees`, which is untouched here) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`:
- For the direct-transfer path, measure `balanceOf(address(this))` before and after each `safeTransferFrom` and use the delta as `order.inputs[i].amount` before computing `reducedInputs`/`commitment`.
- For the predispatch path, measure balances on the `dispatcher` and on `address(this)` before and after each transfer/sweep, exactly as done in the mainline EVM contract, and use actual received amounts for both the commitment and the `_orders[commitment][token]` credit.
- Ensure `commitment` is computed only after all actual-received amounts are known, matching the mainline contract's ordering, so cross-chain proofs and escrow bookkeeping stay consistent with real token custody.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g. 1% fee) as an accepted input token on the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. Contract executes `IERC20(FOT).safeTransferFrom(msg.sender, address(this), 1000e18)` (line 459), but only 990e18 actually lands in the contract due to the 1% fee.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits (≈) 1000e18 (minus only the protocol fee, not the transfer fee) (line 463), while the contract's real `FOT` balance increased by only 990e18.
5. When `withdraw()` is later invoked (via `cancelOrder`, `RedeemEscrow`, or `RefundEscrow`) for this commitment with `body.tokens[0].amount = reducedInputs[0].amount`, the raw `token.call(transfer.selector, beneficiary, amount)` at line 706 either reverts (insufficient balance) or pays out using balance belonging to other users' unrelated escrowed `FOT` orders, demonstrating the freeze/insolvency impact.

    /// @notice Fee-on-transfer with protocol fees: both deductions applied correctly.
    function testPlaceOrder_FeeOnTransferToken_WithProtocolFee() public {
        IntentGatewayV2 gatewayWithFees = _deployGatewayProxy();
        Params memory intentParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: SURPLUS_SHARE_BPS,
            protocolFeeBps: PROTOCOL_FEE_BPS, // 30 bps
            priceOracle: address(0)
        });
        gatewayWithFees.initialize(intentParams, new bytes[](0), address(0));

        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 receivedAfterTransferFee = inputAmount - (inputAmount * 100) / 10000; // 990
        uint256 protocolFee = (receivedAfterTransferFee * PROTOCOL_FEE_BPS) / 10000;
        uint256 expectedEscrow = receivedAfterTransferFee - protocolFee;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(gatewayWithFees), inputAmount);
        gatewayWithFees.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Reconstruct commitment: inputs mutated to received, then reduced by protocol fee
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedEscrow; // commitment is hashed with reduced amount
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            gatewayWithFees._orders(commitment, address(fot)),
            expectedEscrow,
            "Escrow should equal received minus protocol fee"
        );
    }
