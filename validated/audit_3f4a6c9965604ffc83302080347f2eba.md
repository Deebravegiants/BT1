`VWAPOracle.recordSpread` lets a self-filling solver mint arbitrary, permanently-recorded volume-weighted "spread" using an unbounded, uncapped input amount - ([File: evm/src/utils/VWAPOracle.sol])

### Summary
`VWAPOracle` is called from `IntentGatewayV2`'s `fillOrder` path with the **filler-declared** `order.inputs` and `options.outputs` for same-token cross-chain swaps [1](#0-0) . It folds these attacker-influenceable numbers directly into a permanent, monotonically-growing, volume-weighted cumulative average (`weightedSpreadSum` / `totalVolume`) that `spread()` exposes as a trusted price/quality oracle for that (source chain, token) pair [2](#0-1) [3](#0-2) . This is structurally the same defect as the `SynthVault` finding: a value an unprivileged party can cheaply manufacture at transaction time (here, the solver simply chooses `inputs`/`outputs` amounts on a same-chain order it fills itself) is folded into an aggregate that other logic treats as reflecting real, costly market activity, with the weight of each observation (`inputAmountNormalized`, i.e. "volume") unbounded and unrelated to real economic cost.

### Finding Description
`recordSpread` is restricted only to `_intentGateway` [4](#0-3) , i.e. any account can trigger it indirectly by calling `IntentGatewayV2.fillOrder` with an order whose `inputs`/`outputs` amounts are entirely of the caller's choosing (same-token swap orders can be created and filled by the same actor, since `placeOrder`/`fillOrder` are both permissionless entry points reachable by a single dispatched transaction). The oracle computes, per token:

- `spreadBps = (outputAmountNormalized - inputAmountNormalized) * 10000 / inputAmountNormalized`
- `weightedSpread = spreadBps * inputAmountNormalized`
- accumulates into `weightedSpreadSum += weightedSpread` and `totalVolume += inputAmountNormalized` forever [5](#0-4) [6](#0-5) .

There is no minimum real-cost requirement tying the "volume" weight to anything the attacker actually paid or risked (this is not an executed AMM trade with real slippage — it's simply the numbers written into an order the same actor fills), no cap on `spreadBps` magnitude, and no rate limiting or staleness/decay on the aggregate. An actor can therefore submit orders with a very large `inputs[i].amount` (used as the weight) and a manipulated `outputs[i].amount` to swing `weightedSpreadSum`/`totalVolume` arbitrarily and permanently, or dilute/inflate an honest historical spread with a single outsized synthetic fill. Because `fillOrder` fully controls both `inputs` and `outputs` values passed into `recordSpread` (the escrow/settlement logic operates on the same attacker-chosen numbers), the manipulation cost to the attacker is just gas plus round-tripping the same tokens back to themselves on a same-chain order — not the cost of moving a real market.

The project's own changelog documents that `recordSpread` was later removed from the call path specifically because it operated on values "not validated against anything that costs the caller money" [7](#0-6) , confirming the root cause independently.

### Impact Explanation
Any downstream consumer of `IIntentPriceOracle.spread()` (e.g. a solver's pricing/venue-guard logic, a fee/quality gate, or any future protocol logic that trusts this VWAP as a market signal) can be fed a manipulated value at near-zero real cost. If `spread()` is used to gate pricing decisions, set fee discounts, or influence solver selection/reward logic, an attacker can bias it in either direction: understate the spread to make their own future fills look more favorable, or corrupt the aggregate to degrade service/pricing for others. Because the corruption is permanent (cumulative sum, no decay/expiry), a single well-timed manipulation persists indefinitely and compounds with `fillCount`/`totalVolume`, requiring an administrative/governance intervention to correct — this is the freezing/mis-pricing analog of the `SynthVault` reward-weight inflation, applied to a shared on-chain price oracle rather than a staking-weight ledger.

### Likelihood Explanation
High reachability, low cost: `recordSpread` is invoked purely as a side effect of calling `fillOrder` on `IntentGatewayV2` with attacker-chosen `inputs`/`outputs` for a same-token order the attacker can both place and fill themselves (same-chain same-token round trip), requiring no special privilege, no real liquidity pool to move, and no oracle staleness bypass — unlike the original `SynthVault` case, there isn't even a cost proportional to pool depth, since the "market" here is simply the numbers written into the order itself. The main mitigating factor is that this code path was reportedly de-wired from `fillOrder` in a later commit per the changelog note found; however, this repository snapshot's `VWAPOracle.sol` and `IIntentPriceOracle` interface remain in the deployable `evm/src/utils/` tree and continue to expose `recordSpread` restricted only by `msg.sender == _intentGateway`, so any gateway version/deployment that still wires this call (or a future feature that re-adds/relies on it) inherits the vulnerability.

### Recommendation
- Do not derive `spreadBps`/volume weight from self-declared order `inputs`/`outputs` of a same-chain, same-actor-fillable order; if this oracle is reinstated, weight observations only by fills that involve independent counterparties and real settlement risk (e.g. cross-chain fills with a genuine relayer/consensus-verified settlement, not a same-chain round trip).
- Cap `spreadBps` per observation (e.g. reject/clamp fills reporting spreads outside a sane band) and cap or diminish the weight any single fill can contribute relative to trailing total volume, to bound single-transaction influence on the cumulative average.
- Add decay/windowing (true TWAP/VWAP over a bounded recent window) instead of an all-time unbounded cumulative sum, so a corrupted observation ages out rather than persisting indefinitely.
- If the oracle's output is ever consumed for any economically consequential decision, require it to reconcile against an independent, harder-to-manipulate reference and reject when they diverge beyond a threshold (mirroring the `maxDeviationBps` guard already used elsewhere in the codebase for Uniswap V4 pool pricing).

### Proof of Concept
1. Attacker deploys/uses an address that both places and fills a same-chain, same-token `Order` via `IntentGatewayV2` (input token == output token, e.g. DAI→DAI), setting `inputs[0].amount = X` (large) and `outputs[0].amount = X * 1.10` (or any desired ratio) as the filled `options.outputs`.
2. `fillOrder` calls `IIntentPriceOracle.recordSpread(commitment, sourceChain, order.inputs, options.outputs)` on `VWAPOracle`, which is gated only by `msg.sender == _intentGateway` [8](#0-7) [9](#0-8) .
3. `recordSpread` normalizes both amounts to 18 decimals and computes `spreadBps = +1000` (10%), weighting it by the attacker-chosen `inputAmountNormalized = X` — an amount fully controlled by the attacker and unconstrained by any real capital cost beyond briefly holding `X` tokens for a same-chain round trip.
4. `_updateCumulativeSpread` permanently adds `weightedSpread = 1000 * X` to `weightedSpreadSum` and `X` to `totalVolume` [10](#0-9) .
5. Because `X` can dwarf all prior genuine volume for that token, a single transaction can move `spread()`'s reported value arbitrarily close to the attacker's chosen `spreadBps`, and this distortion never expires (no decay/window), corrupting the oracle for all future readers until governance intervenes.

    /**
     * @inheritdoc IIntentPriceOracle
     */
    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }

    /**
     * @notice Updates cumulative spread data
     * @param data Storage reference to the cumulative spread data
     * @param weightedSpread The weighted spread (spread * volume)

     */
    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
        data.weightedSpreadSum += weightedSpread;
        data.totalVolume += volume;
        data.fillCount += 1;
        data.lastUpdate = block.timestamp;
