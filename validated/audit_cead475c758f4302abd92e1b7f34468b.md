### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unsigned HTTP headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers (`shopify_header`) that are never covered by the HMAC. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` to dispatch the payload to a handler as authoritative tenant/topic identity.

### Finding Description
The identity binding that should hold is: `HMAC-signed bytes == bytes that determine tenant identity (shop) and event routing (topic)`. In this gem, that equality is broken:

- `hmac` is computed by the caller over the `hmac-sha256` header value [1](#0-0)  and validated against `to_signable_string`, which returns only `@raw_body` [2](#0-1) .
- `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers via `shopify_header`, none of which are part of the signed bytes [3](#0-2) .
- `HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., only the body — and returns `true`/`false` with no reference to headers [4](#0-3) .
- `Registry.process` gates only on this body-only HMAC check, then forwards the header-derived, unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` to the app's registered handler as if they were verified [5](#0-4) .

Because a JSON body signed by Shopify for shop A's webhook produces the exact same valid HMAC regardless of which `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` header values accompany it, an attacker who obtains one legitimately-delivered webhook request (e.g., from network logs, a compromised intermediary, a misconfigured proxy, or a webhook the attacker's own store received) can replay that exact body with different header values — most importantly a different `shop-domain` — and the request still passes `Utils::HmacValidator.validate`. The library then hands the host application data attributed to a shop that never actually produced it.

### Impact Explanation
This breaks the shop identity binding relied on by any host application: `Registry.process` -> `WebhookMetadata` construction attributes body content to `request.shop`, a value entirely outside the cryptographic guarantee. Any app that uses `request.shop` to select which tenant's records to update (a standard, gem-endorsed pattern, since `shop` is exposed specifically for that purpose) can be made to write, and in redact/GDPR topics like `shop/redact` or `customers/redact`, delete or redact data for a shop that is not the one whose signature was actually validated. This is a cross-tenant data integrity/authentication issue: the gem asserts "HMAC valid" implies "this shop truly sent this body," but the two are unbound.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(body, hmac)` pair for the app's `client_secret`-derived signature (e.g., their own store's genuine webhook, or one obtained via any interception outside the app's own trust boundary) and to be able to deliver a crafted HTTP request with altered headers but identical body/hmac to the app's webhook endpoint. No `api_secret_key` or access token needs to be known — only replay of a previously observed, validly signed body under attacker-chosen header metadata. Because `shop`/`topic`/`webhook_id` are advertised gem APIs (`WebhookMetadata`) specifically meant to let apps route per-tenant, this path is realistically reachable by any app that follows the gem's documented webhook flow.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (e.g., by having `to_signable_string` incorporate a canonical, delimiter-safe concatenation of these header values with the body, matching whatever Shopify's actual signing scheme supports), or require the host application to independently confirm `request.shop` against a shop already known/authorized via an existing session before trusting the payload for tenant-scoped operations.

### Proof of Concept
1. App receives a legitimate webhook for `victim-real-shop.myshopify.com` with body `B` and valid header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker (having obtained `B` and `H` from any source outside the gem's control, e.g. their own shop's webhook if body content is attacker-influenced, or via interception) sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: attacker-or-other-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body without complaint [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [7](#0-6) .
5. The handler receives `WebhookMetadata` with `shop: "attacker-or-other-shop.myshopify.com"` and the victim's body content, despite the signature never covering that shop value [8](#0-7) .
