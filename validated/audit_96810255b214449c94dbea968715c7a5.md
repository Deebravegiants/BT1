### Title
Webhook Shop/Topic/Webhook-ID Attribution Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, while `Utils::HmacValidator` (invoked by `Registry.process`) only authenticates the raw request body against the app's shared `api_secret_key`. Because the HMAC signature never binds these header values to the signed body, an attacker who can obtain one validly-signed webhook delivery (e.g., by installing the app on their own store) can replay that exact body to the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and other) headers to attribute the payload to a different, victim tenant. `Registry.process` passes this unverified `shop` value straight to the app's handler as trusted tenant identity.

### Finding Description
The Shopify webhook signature is computed once per app using the app's `client_secret`/`api_secret_key`, shared across every shop that has the app installed — it is not shop-specific. `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read verbatim from HTTP headers that are excluded from that signable string: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` confirms the check is scoped to `verifiable_query.to_signable_string`, i.e. the body only: [4](#0-3) 

The identity-binding equality that should hold is: `HMAC-authenticated bytes ⊇ {shop, topic, webhook_id}`. In reality: `HMAC-authenticated bytes = {raw_body}` only, so `shop` (the tenant key used by the handler) is completely outside the authenticated boundary.

The gem's own documentation reinforces this false trust: it states `Registry.process` "will verify the request did indeed come from Shopify" and instructs developers to use `data.shop` directly as the shop domain for follow-on actions (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), with no mention that `shop` is unauthenticated relative to the signed content. [5](#0-4) [6](#0-5) 

### Impact Explanation
Because the `api_secret_key` used to sign webhooks is per-app (not per-shop), any merchant who installs the app on their own store legitimately receives HMAC-valid webhook deliveries. That merchant can capture one such delivery and replay the identical `(raw_body, hmac)` pair to the app's shared webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. `HmacValidator.validate` still passes (only the body is checked), so `Registry.process` dispatches the handler with `shop` set to the victim's domain and body content controlled by the attacker. Any host app that follows the documented pattern of using `data.shop` to select the tenant/session for persisting or acting on webhook data will process attacker-controlled data under a victim tenant's identity — a cross-tenant data injection / spoofing primitive that crosses the tenant isolation boundary this gem is trusted to enforce.

### Likelihood Explanation
Obtaining one's own valid webhook delivery requires nothing beyond installing the app on an attacker-controlled store — a capability freely available to any unprivileged internet user for apps with public installation flows, no leaked credentials or privileged access is required. Forging arbitrary HTTP headers on a request to a public webhook endpoint is trivial. The only constraint is that the replayed body must be one the attacker already possesses a valid signature for (from their own installation), which still allows attribution/data-injection attacks (e.g., replaying "app/uninstalled", "customers/redact", or content-bearing topics) against a chosen victim shop.

### Recommendation
Do not treat header-derived `shop`, `topic`, or `webhook_id` as authenticated. At minimum, `Registry.process` (or `Request`) should require the caller to supply the expected shop (resolved from an already-authenticated session/install record) and assert it equals `request.shop` before invoking the handler, and/or incorporate the shop/topic/webhook_id into the value that is HMAC-verified when the host application has an independent way to bind them (e.g., cross-check against Shopify's registered webhook subscription for that shop/topic). Document explicitly that `Webhooks::Request#shop`/`WebhookMetadata#shop` is not covered by the HMAC and must be independently verified before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, to the app's public webhook endpoint. The attacker captures the raw POST: `raw_body` and header `X-Shopify-Hmac-Sha256: <valid_hmac>`.
2. Attacker resends the exact same `raw_body` (with the identical valid `X-Shopify-Hmac-Sha256`) to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. Server constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the shared `api_secret_key` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-supplied order data as if it belonged to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
