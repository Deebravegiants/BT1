### Title
Panic-inducing out-of-bounds `copy_from_slice` in BEEFY vote signature conversion enables relayer-triggered DoS of consensus updates - (File: evm/rust/src/conversions.rs)

### Summary
The BEEFY consensus proof ABI→SCALE conversion path performs an unchecked `copy_from_slice` from an attacker-controlled, variable-length Solidity `bytes` field into a fixed 65-byte array. A relayer submitting a malformed BEEFY consensus proof through the permissionless `pallet-beefy-consensus-proofs::verify_and_apply` path can supply a `Vote.signature` of any length other than 65 bytes and trigger a Rust length-mismatch panic before any cryptographic or structural validation of the vote occurs.

### Finding Description
`impl From<Vote> for SignatureWithAuthorityIndex` unconditionally copies the raw signature bytes into a fixed-size buffer without validating length first: [1](#0-0) 

`Vote.signature` originates from the Solidity ABI type `bytes` (an arbitrary-length dynamic byte array), not a fixed `bytes65`, so nothing at the ABI-decoding boundary enforces a 65-byte length. This conversion is reached from the permissionless proof-submission path: `pallet-beefy-consensus-proofs::verify_and_apply` ABI-decodes attacker-supplied proof bytes for `PROOF_TYPE_NAIVE`, then converts straight into the SCALE-encoded consensus message via chained `Into` calls that eventually invoke `Vote::into()` for every submitted vote: [2](#0-1) 

The conversion chain is: `BeefyConsensusProof -> ConsensusMessage` (via `From<BeefyConsensusProof> for ConsensusMessage`), which converts `relay: RelayChainProof -> MmrProof`, which maps every vote through `Into::into()`: [3](#0-2) 

None of these intermediate conversions validate `Vote.signature.len() == 65` before `Vote::into()` performs the fixed-size `copy_from_slice`. Unlike the CVE's Qt `QOutlineMapper::convertPath`, which corrupts memory via a raw C++ write, Rust's `copy_from_slice` will not corrupt memory on a length mismatch — it panics deterministically. However, this panic occurs deep inside runtime dispatch logic that is normally expected to return a typed `Result`/`Error`, not unwind. This is analogous in bug class (unchecked length assumption feeding a fixed-size buffer write) even though Rust's safety guarantees downgrade the OOB write to a panic.

### Impact Explanation
A panic thrown from within pallet dispatch logic that executes as part of block-building/state-transition (rather than being caught and converted to a dispatch error) is a denial-of-service vector for the whole runtime executing that extrinsic. Because `verify_and_apply` sits in the sole update path for the BEEFY consensus client used to admit new relay-chain/parachain state commitments, an attacker-triggered panic here can halt processing of that extrinsic and, by extension, the pipeline that updates consensus state needed to deliver cross-chain messages — matching the "route unable to deliver messages" impact class. Any single unprivileged account able to submit a `submit_proof`/`verify_and_apply` call can attempt this at negligible cost.

### Likelihood Explanation
High: the vulnerable conversion sits directly on the parsing path for permissionless proof submission, requires no valid signatures, MMR proof, or authority-set matching to be reached (the panic fires before verification-heavy checks even run over the offending vote), and only requires the submitter to craft a `Vote.signature` field of a length other than 65 bytes in the ABI-encoded proof blob.

### Recommendation
Validate `value.signature.len() == 65` in `impl From<Vote> for SignatureWithAuthorityIndex` (and any other ABI→SCALE conversions using `copy_from_slice` on attacker-controlled `bytes` fields) and return an error/`Result` instead of panicking, or migrate the fallible conversion into a `TryFrom` so `verify_and_apply` can surface it as `Error::<T>::AbiDecodeFailed` rather than unwinding.

### Proof of Concept
1. Construct a `BeefyConsensusProof` (Solidity ABI `PROOF_TYPE_NAIVE` payload) where `signedCommitment.votes[i].signature` is set to a `bytes` value of length ≠ 65 (e.g., 64 or 66 bytes) — valid to construct/encode since `bytes` is variable length.
2. Prefix the encoded payload with `types::PROOF_TYPE_NAIVE` and submit it via the pallet's `submit_proof` extrinsic call (any account can invoke this permissionlessly).
3. Execution reaches `verify_and_apply` → `abi_decode_params::<BeefyConsensusProof>` (succeeds, since ABI does not enforce fixed length) → `.into()` → `RelayChainProof -> MmrProof` → `Vote::into()` → `signature.copy_from_slice(&sig_bytes)` panics with a length-mismatch panic before signature verification or authority-set checks occur.
