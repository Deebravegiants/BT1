## Finding

The webhook signature verification in this gem covers only the raw request body, while the `shop-domain` and `topic` header fields used to route/attribute events are left completely outside the signed data.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, never the headers: [1](#0-0) 

`shop` and `topic` are read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` (shared by both OAuth callback and webhook flows) computes the signature only over whatever `to_signable_string` returns for the given object: [3](#0-2) 

`Registry.process` accepts the request purely on the strength of that body HMAC, then hands the caller-supplied (unauthenticated) `shop` and `topic` straight to the app's handler: [4](#0-3) 

### Equality that should hold but doesn't

`shop-header-claimed-by-request == shop-that-actually-produced-the-signed-body`

Because the same `api_secret_key` is shared by an app across every merchant install, a valid `(raw_body, hmac)` pair only proves "some installation of this app produced this body" — it proves nothing about which shop. Since `shop-domain`/`topic` aren't part of the signed bytes, an attacker who controls one legitimate installation (their own store, or a dev store) can capture a validly-signed `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Registry.process` will accept it as authentic and dispatch `WebhookMetadata` with the attacker-chosen `shop`, letting the attacker inject events attributed to any tenant. Contrast this with the OAuth callback path, where `shop` *is* included in the signed string, so it is properly bound: [5](#0-4) 

This asymmetry is the exploitable gap — it is the webhook path, not the OAuth path, where the `shop` field is validated (via `HmacValidator.validate`) but not actually bound to the HMAC input.

### Caveat / uncertainty

Whether this is exploitable in a *given host application* depends entirely on whether that app's webhook handlers key data storage/lookups by the `shop` field of `WebhookMetadata` (a very common pattern, e.g. resolving a per-shop session/access token to react to the event). This gem's own code offers no additional binding (e.g., checking the header shop against a known/expected value), so the trust boundary crossing (spoofing another tenant's webhook shop) is fully reachable through this gem's public API surface alone; I could not find any place in `lib/shopify_api/webhooks/**` that cross-checks `request.shop` against anything else. This is a structural characteristic of Shopify's real webhook signing scheme (body-only HMAC) rather than a mistake unique to this gem's implementation, so I flag it with that caveat rather than certainty that it's a novel defect.

### Title
Webhook `shop-domain`/`topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` and `topic` from HTTP headers that are excluded from the HMAC-signed payload (`to_signable_string` returns only the raw body). `Registry.process` validates only the body HMAC and then forwards the unauthenticated `shop`/`topic` values to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only [6](#0-5) , while `shop` and `topic` are pulled from `shopify-shop-domain`/`shopify-topic` headers [2](#0-1) . `HmacValidator.validate` signs/verifies exactly the string returned by `to_signable_string` [7](#0-6) . `Registry.process` gates entirely on this HMAC check before dispatching the unauthenticated `shop`/`topic` fields to the handler [4](#0-3) . Since one `api_secret_key` is shared across all shops that install the app, a valid signature over a given body can be obtained by an attacker who controls (or trials on) their own installation, and then replayed against the app's webhook endpoint with a forged `shop-domain` header naming a different (victim) shop.

### Impact Explanation
Any handler logic that trusts `WebhookMetadata#shop` (typically used to resolve the tenant/session the event belongs to) can be made to process attacker-crafted body content under a victim shop's identity — a cross-tenant confusion/injection primitive reachable purely through this gem's documented webhook-processing API.

### Likelihood Explanation
Requires the attacker to have at least one shop installation of the target app (to obtain a validly-signed body/HMAC pair) and network access to the app's webhook endpoint — no `api_secret_key`, access token, or privileged account needed.

### Recommendation
Include the routing-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind the claimed `shop` to the HMAC verification step in `HmacValidator`/`Webhooks::Request`, so a body signed for one shop cannot be relabeled as originating from another.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/records a legitimate webhook delivery, capturing `raw_body` and its `x-shopify-hmac-sha256` value (valid under the shared `api_secret_key`).
2. Attacker POSTs the same `raw_body`/HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `victim.myshopify.com`, despite the payload actually originating from the attacker's own shop [9](#0-8) .
