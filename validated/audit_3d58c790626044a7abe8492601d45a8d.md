### Title
Position NFT approval binds only `token_id` — approved account contents can be drained/rebound between `approve` and `transfer_from` (File: contracts/position-nft/src/contract.rs)

### Summary
The OpenClaw class — an approval that pins an opaque token but not the resolved identity of what will actually execute — maps onto the position NFT: `approve`/`approve_for_all` commit a spender to `token_id` only, while the underlying controller account (collateral, debt, HF) bound to that same id remains fully mutable by the still-owner. Between approval and pull, the owner can borrow to the LTV limit and withdraw spendable proceeds, then let the approved spender execute `transfer_from`, delivering a hollowed-out account the buyer priced on pre-rebind state.

### Finding Description
`contracts/position-nft/src/contract.rs` is the stock OpenZeppelin `NonFungibleToken` + `Enumerable` implementation (`contract.rs:131-173`); `approve`, `approve_for_all`, `transfer`, and `transfer_from` are inherited unmodified. The token id *is* the account id (`contract.rs:1-5`), and the controller derives account ownership from the NFT owner (`try_account_owner` in `contracts/controller/src/risk/params.rs:165`; `require_owner_or_delegate` in `contracts/controller/src/strategies/swap_collateral.rs:47`). No approval or transfer path notifies the controller, snapshots account state, or freezes the account. So the "approved object" — the leveraged account — can be re-resolved by the seller after approval:

1. Seller supplies collateral, creating account/NFT `N`.
2. Seller calls `approve(marketplace_or_buyer, N, live_until_ledger)`.
3. Before the buyer's `transfer_from` lands, seller calls controller `borrow`/`multiply`/`withdraw` to extract value up to the borrow limit (LTV-stamped params in `refresh_supply_risk_params`, `params.rs:35`), leaving `N` at HF just above 1.05 or minimally solvent.
4. Approved spender pulls `N`; received collateral-backing is now largely debt.

The timelock's analogous surface is already hardened — `RelaxSpokeAssetFlags` pins `expected_epoch` at propose and re-checks at execute (`docs/reference/endpoints.md:230`), and governance `execute` rehashes `target+function+args+salt` (`lifecycle.rs`/`hash_operation`, `api.rs:94-103`). The NFT approval has no equivalent binding.

### Impact Explanation
Theft of user funds: the buyer pays for collateral value that no longer backs the account. Loss is bounded by the borrowable fraction of the position's collateral, but covers essentially the full advertised account value minus residual equity. Unlike the threat-model's router exposure note, no signed-auth-tree misuse is needed — this is native contract semantics reachable by any unprivileged address via `position-nft.approve` plus normal `borrow`/`withdraw`.

### Likelihood Explanation
Requires a secondary-market sale of a position NFT (or OTC escrow) and a victim that prices the NFT without re-reading account state at execution. A defensive buyer could compose `transfer_from` atomically with a state check, but nothing in-protocol forces that — the approval primitive itself carries the TOCTOU gap. Medium likelihood, Medium severity.

### Recommendation
Bind approvals to account state, e.g.: revoke/clear approvals when the account's debt or supply positions change (controller hook on position mutation), store an account-state epoch on the NFT that `transfer_from` verifies against an `expected_epoch` argument (mirroring `RelaxSpokeAssetFlags`' epoch check), or gate `borrow`/`withdraw`/`multiply`/`swap_*` for accounts with a live approval.

### Proof of Concept
1. Attacker `supply(USDC)` → account `id`, NFT minted.
2. `position-nft.approve(attacker, buyer_contract, id, ledger+N)`.
3. `controller.borrow(caller=attacker, account_id=id, ...)` to max LTV, then `withdraw` residual equity; proceeds go to attacker's wallet.
4. Buyer executes `transfer_from(spender, attacker, buyer, id)` — receives account at HF ≈ 1.0 whose debt ≈ collateral.

Caveat: I could not fully verify whether the controller stores a copied `owner` field that diverges from NFT ownership or whether any approval-aware freeze exists elsewhere in `contracts/controller/src/account.rs`; `account_from_parts(owner, ...)` in `params.rs:178` and `require_owner_or_delegate` indicate ownership is NFT-derived at call time, and no freeze hook was found in the indexed code, but a confirmatory read of `account.rs` would close that gap.
