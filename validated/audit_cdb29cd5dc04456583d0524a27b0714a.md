No analog vulnerability found for this question.

**Reasoning:** The reported issue concerns a hardcoded Chainlink `FAST_GAS_HEARTBEAT` staleness threshold used to validate an external price/gas oracle feed. Raydium AMM's swap instructions (`process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`) derive prices exclusively from on-chain SPL token vault balances via `Calculator::calc_total_without_take_pnl_no_orderbook`, not from any Chainlink or external oracle feed with a heartbeat/staleness window. [1](#0-0) 

The only time-based checks in the swap paths gate `WaitingTrade → SwapOnly` transitions against `amm.state_data.pool_open_time` using `Clock::get()?.unix_timestamp`, which is an on-chain sysvar comparison, not a staleness check against a hardcoded heartbeat constant for a price feed. [2](#0-1) 

The `recent_epoch` field on `AmmInfo` is simply bookkeeping updated after state-mutating operations and is unrelated to any staleness/freshness validation of a price input. [3](#0-2) 

There is no hardcoded heartbeat/staleness constant governing an external price or gas feed reachable by an unprivileged swapper, LP, or pool creator in this program, so the bug class from the report does not map to an in-scope, reachable defect here.
