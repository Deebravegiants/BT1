### Title
Sandwichable AMM price used for exact-fee swaps in `EvmHost.dispatch`/`fundRequest` and `IntentGatewayV2.placeOrder` enables griefing and forced overpayment of dispatch fees - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` — the primary unprivileged, ISMP message-dispatch entry points — convert a caller's native token into `feeToken()` on-chain via `IUniswapV2Router02.swapETHForExactTokens`, using the live pool reserves at execution time and `block.timestamp` as the swap "deadline" (i.e., no real deadline protection). `IntentGatewayV2.placeOrder()` performs the identical pattern to escrow `order.fees`. Because the swapped amount is priced against the current pool state with no caller-supplied slippage/maximum-input bound beyond `msg.value`, any unprivileged attacker can sandwich a dispatching transaction to move the pool price and either revert the victim's dispatch (`EXCESSIVE_INPUT_AMOUNT`, a message-delivery DoS) or force the victim to consume more of their supplied native value than fair market price, capturing the difference as MEV. This is the same underlying bug class as the referenced zBanc report — a privileged/consequential state-changing action gated or priced by a manipulable on-chain quantity computed at call time, exploitable by sandwiching — except here the manipulable quantity (AMM spot price) directly prices a value transfer paid by an unprivileged user on the core dispatch path, rather than just gating an admin call.

### Finding Description
`EvmHost.dispatch(DispatchPost memory post)`: [1](#0-0) 

and the `DispatchGet` and `fundRequest` variants use the identical construct: [2](#0-1) [3](#0-2) 

All three call `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The Uniswap V2 router computes the required WETH input from the pool's *current* reserves and reverts with `EXCESSIVE_INPUT_AMOUNT` if that exceeds `msg.value`; `deadline = block.timestamp` provides no protection since it is always satisfied within the same block that includes the transaction. Nothing else bounds the swap's price impact.

The same pattern is repeated in `IntentGatewayV2.placeOrder()` when escrowing `order.fees`: [4](#0-3) 

and in the Tron port: [5](#0-4) 

The protocol's own documentation acknowledges that the equivalent read-only `quote()` path (which uses `getAmountsIn` against the same reserves) is sandwich-vulnerable and warns integrators to only use it off-chain: [6](#0-5) 

However, that warning covers only the off-chain estimation helper. The actual on-chain state-changing swap embedded in `dispatch`/`fundRequest`/`placeOrder` carries exactly the same reserve-dependent pricing risk, with no slippage cap, and it is not just a griefing surface but an active value-transfer path (native ETH → fee token) paid for by any unprivileged user dispatching a cross-chain message or placing an intent order.

### Impact Explanation
An attacker (no privileges required) can watch the mempool for `dispatch()`/`fundRequest()`/`placeOrder()` calls that pay via native token and sandwich them:
1. Front-run: buy `feeToken()` from the pool to push its price up relative to WETH.
2. Victim's exact-output swap now needs more WETH input for the same `fee`/`order.fees` output:
   - If the required input exceeds `msg.value`, the entire dispatch/order-placement reverts — denying message delivery/order placement (griefing on the core EvmHost dispatch and IntentGateway escrow paths).
   - If `msg.value` still covers the inflated input, the victim pays materially more ETH than fair value for the same fee token amount, and the attacker captures the difference by back-running (selling back into the pool) — direct value extraction from the dispatching user.
This affects the primary path by which apps and users pay to dispatch ISMP messages and place intent orders, making it a systemic, always-reachable griefing/theft vector on core dispatch and intents functionality, not a one-off admin function.

### Likelihood Explanation
High. `dispatch()` (POST/GET), `fundRequest()`, and `placeOrder()` are all public, unprivileged, frequently-called entry points on every chain with an `EvmHost`/`IntentGatewayV2` deployment, and pools used for `feeToken()` conversion (especially on lower-liquidity chains) can be materially moved with a small amount of capital. No special conditions are required beyond mempool visibility, which is standard for MEV searchers.

### Recommendation
- Do not perform on-chain reserve-priced swaps with no caller-specified maximum input in critical dispatch paths. Require callers to supply an explicit `amountInMax`/slippage tolerance for the native→feeToken swap and enforce it (rather than implicitly using the entire `msg.value` as the cap and a same-block deadline).
- Consider routing native-fee dispatches through a TWAP or bounded-deviation price source (as already used elsewhere, e.g. `referencePrice`/`maxDeviationBps` guards in the Simplex solver) rather than raw spot AMM reserves for pricing.
- Alternatively, restrict the affected code paths to pre-quoted, fee-token-denominated payments and push native-to-fee-token conversion off-chain (as `evm.ts`'s `quote`/`quoteNative` already do for estimation), removing the on-chain swap from the atomic dispatch transaction entirely.

### Proof of Concept
1. Attacker observes a pending `EvmHost.dispatch(DispatchPost)` (or `fundRequest`/`IntentGatewayV2.placeOrder`) transaction paying via `msg.value` for `feeToken()`.
2. Attacker front-runs with a large buy of `feeToken()` against WETH on the pool referenced by `_hostParams.uniswapV2`, increasing the WETH cost of the fixed `post.fee` output.
3. Victim's `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` either:
   - reverts with `UniswapV2Router: EXCESSIVE_INPUT_AMOUNT` if the new input requirement exceeds `msg.value` (dispatch fails, message never sent, gas wasted), or
   - succeeds while consuming close to the victim's full `msg.value`, well above the pre-attack fair price.
4. Attacker back-runs by selling the `feeToken()` back into the pool, realizing profit from the price impact paid for by the victim's exact-output swap.
