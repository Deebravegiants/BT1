### Title
Non-embedded app session lookup trusts an unsigned, predictable cookie value as the session identifier - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`SessionUtils.current_session_id` for non-embedded apps only checks that a cookie named `shopify_app_session` is present; it never verifies that the cookie's value was produced/signed by the app under `Context.api_secret_key`. Because the cookie's value is simply `session.id`, and offline session ids are deterministically constructed as `"offline_#{shop}"` from a public, guessable shop domain, an attacker can set that cookie value directly in a raw HTTP request and have it accepted as an authenticated session identifier.

### Finding Description
The broken binding: `RETURNED_SESSION_ID == cookies["shopify_app_session"]` is treated as equivalent to `RETURNED_SESSION_ID == session_id_authenticated_by(Context.api_secret_key)`, but no code anywhere in this path enforces the right-hand side.

Code path:
- `SessionUtils.current_session_id` (non-embedded branch) does:
```ruby
raise Errors::CookieNotFoundError, ... unless cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]
cookie_session_id(cookies)
``` [1](#0-0) 
- `cookie_session_id` just returns the raw cookie value verbatim: [2](#0-1) 
- `SessionCookie` is a plain struct with `name`, `value`, `expires` and no signature/HMAC field at all: [3](#0-2) 
- The cookie is originally set by `Oauth.validate_auth_callback` to the literal `session.id` for non-embedded apps: [4](#0-3) 
- Offline session ids are deterministic and derived only from the public shop domain: `"offline_#{shop}"` [5](#0-4) 

Contrast with the OAuth callback flow, which does cryptographically validate untrusted input via `Utils::HmacValidator.validate(auth_query)` before trusting `auth_query` [6](#0-5) . No equivalent HMAC/secret-based check exists in `current_session_id`'s cookie branch for either the embedded-fallback or non-embedded case.

Attacker request: for a non-embedded app, the attacker sends any HTTP request to the app with header `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` (or the exact `session.id` value if online-session ids/format are known/guessable). Since `shop` domains are public (they appear in install URLs, webhooks, App Store listings, etc.), the attacker can construct this value for any victim merchant without ever touching `Context.api_secret_key`.

`current_session_id` returns this attacker-chosen string unmodified. If the host app then uses this string as the lookup key into its session storage (as documented usage in `docs/getting_started.md` implies), and a session was previously persisted for the victim shop (e.g., because the victim installed the app), the app will load and act using the victim's `Session`, including its `access_token`, on behalf of the attacker's request.

Why existing guards don't catch this: `HmacValidator.validate` is only invoked in the OAuth callback path (`validate_auth_callback`) against `AuthQuery`, never against the session cookie. `Context.setup?`/`private?`/`embedded?` only gate whether OAuth is allowed or which JWT/cookie branch is taken — they don't validate cookie authenticity. `JwtPayload`'s `aud` check only applies to the JWT/embedded App Bridge path, not the raw cookie path used for non-embedded apps.

### Impact Explanation
An attacker can obtain the return value of `current_session_id` equal to any string they choose, including the deterministic offline session id of an arbitrary victim merchant that has installed the target app. If the calling application uses this id to fetch the persisted `Session` (containing the merchant's `access_token`), the attacker gains cross-tenant access to that merchant's Shopify Admin API credentials without ever authenticating — a full authentication bypass and access-token theft, repeatable against any merchant whose shop domain is known and who has previously completed OAuth with the app. This matches Critical severity: cross-tenant access / theft of a merchant access token via authentication bypass.

### Likelihood Explanation
Preconditions: the app is configured as non-embedded (or embedded with a missing JWT, falling back to the cookie branch); the attacker knows the victim's shop domain (public information) and the victim has previously installed the app so a session exists in storage. The attacker never needs `api_secret_key`, an access token, or any secret — only the ability to set an arbitrary `Cookie` header, which is trivial for any HTTP client. Cost is a single crafted HTTP request; the exploit is fully repeatable against any known victim shop.

### Recommendation
Do not trust the raw cookie value as an authenticated session identifier. Either (a) sign the cookie value with an HMAC keyed by `Context.api_secret_key` when it is set in `Oauth.validate_auth_callback`, and verify that signature (via `OpenSSL.secure_compare`, mirroring `HmacValidator`) inside `SessionUtils.current_session_id`/`cookie_session_id` before returning it, or (b) use a cryptographically random, unpredictable session cookie value (e.g., a signed/encrypted Rails-style session id) instead of the literal deterministic `session.id`, and validate it server-side against the stored session before use.

### Proof of Concept
Add to `test/utils/session_utils_test.rb`:
```ruby
def test_non_embedded_cookie_branch_never_validates_hmac_and_accepts_arbitrary_value
  ShopifyAPI::Context.setup(..., is_embedded: false, ...)

  forged_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => "offline_victim-shop.myshopify.com" }

  ShopifyAPI::Utils::HmacValidator.expects(:validate).never

  session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, forged_cookies, false)

  assert_equal "offline_victim-shop.myshopify.com", session_id
end
```
This demonstrates that `current_session_id` returns the attacker-supplied cookie value unchanged with no HMAC/secret validation on either side of the binding, confirming the divergence between "cookie present" and "cookie authentic."
