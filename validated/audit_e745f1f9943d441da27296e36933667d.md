Confirmed: `signature_verify_strict_t` automatically wraps the signed struct with `type_info::type_of<T>()` (module address, module name, struct name) via the `SignedMessage<T>` wrapper [1](#0-0) . This means every one of the account-capability proof-challenge structs is automatically domain-separated by module/struct type — the "signature reuse across functions" and "signature reuse across projects with different struct semantics" attack classes from the Rigor report are already closed at the framework level. What is **not** automatically covered is chain ID, since `type_info::type_of` has no concept of chain identity.

### Title
Missing chain-ID domain separation in `SignerCapabilityOfferProofChallengeV2` enables cross-chain signer-capability-offer replay - (File: aptos-move/framework/aptos-framework/sources/account/account.move)

### Summary
`offer_signer_capability` builds and verifies a `SignerCapabilityOfferProofChallengeV2` proof challenge that contains only `sequence_number`, `source_address`, and `recipient_address` [2](#0-1) . Unlike its sibling `RotationCapabilityOfferProofChallengeV2`, which explicitly adds a `chain_id` field specifically "to prevent replaying the challenge message" [3](#0-2) , the signer-capability variant never received this fix.

### Finding Description
`offer_signer_capability` constructs the challenge purely from on-chain state (`get_sequence_number(source_address)`, `source_address`, `recipient_address`) and verifies it via `verify_signed_message`, which itself just calls `signature_verify_strict_t` [4](#0-3) . `signature_verify_strict_t` domain-separates by `TypeInfo` (address/module/struct of `SignerCapabilityOfferProofChallengeV2`) but has no chain awareness [1](#0-0) . Because `sequence_number` is the *account's* current sequence number rather than a global nonce, and because addresses (and, on a chain fork/testnet/mirrored chain with identical genesis-derived addresses) can be identical across chain IDs, a signature Alice creates authorizing `offer_signer_capability` for a given `recipient_address` at sequence number `n` on chain A remains valid for the identically-addressed account on chain B at the same sequence number. This directly reproduces attack #2 from the Rigor report (signature reuse across different chains) for one specific, live custody-relevant capability: full signer capability delegation (equivalent to handing over unrestricted control of the account, since `create_authorized_signer` returns a full `signer` for the offerer's account) [5](#0-4) .

Compare this with `create_resource_account`, which explicitly documents the necessity of domain separation to prevent exactly this class of cross-context collision (`DERIVE_RESOURCE_ACCOUNT_SCHEME`) [6](#0-5) , and with `MultisigAccountCreationMessage`/`RotationCapabilityOfferProofChallengeV2`, which both explicitly include `chain_id::get()` [7](#0-6) [8](#0-7) . `SignerCapabilityOfferProofChallengeV2` is the one outlier that never got the chain-ID hardening applied to its sibling struct.

### Impact Explanation
If an Aptos-derived chain (testnet, devnet, a fork, or any chain sharing the same genesis/account-derivation scheme) exists where an account with the same address and same sequence-number history is present, an attacker can replay a previously-observed, legitimately-signed `offer_signer_capability` transaction/signature from one chain onto the other. Successful replay grants the recipient a full authorized `signer` for the victim's account via `create_authorized_signer`, i.e. complete custody takeover (transfer/burn/mint any coin or object owned by that account, rotate keys via any capability the account holds, etc.). This meets the custody-grade bar (unauthorized takeover of account/resource control).

### Likelihood Explanation
Likelihood is **low-to-moderate** in practice: it requires (a) a second Aptos-compatible chain/environment where the victim address and sequence number line up, and (b) an attacker who has observed a previously broadcast `offer_signer_capability` signature (these are normally submitted directly on-chain as part of the same transaction, so the "signed message" is public once used). This is a narrower, lower-severity variant than a true unbounded cross-chain replay, and is mitigated somewhat by the requirement that sequence numbers and addresses must coincide across chains. It is nonetheless a genuine, demonstrable violation of the project's own established domain-separation policy (the sibling rotation-capability struct fixes exactly this).

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`) and populate it with `chain_id::get()` in `offer_signer_capability`, bumping to a `V3` struct name so `TypeInfo` domain separation also changes. Audit all other proof-challenge structs used with `signature_verify_strict_t`/`verify_signed_message` framework-wide for the same omission.

### Proof of Concept
Not independently constructible from this index alone — a full working reproduction would require simulating two chains with `chain_id::initialize_for_test` at different IDs but identical account state (as is done in the existing test `test_valid_offer_rotation_capability`, which sets `chain_id::initialize_for_test(&framework, 4)` [9](#0-8) ). Analogous test scaffolding exists in `test_valid_check_signer_capability_and_create_authorized_signer` [10](#0-9) , which would need to be modified to sign under chain ID X and verify successfully under chain ID Y, demonstrating no `chain_id` check exists.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
