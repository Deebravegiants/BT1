### Title
Race condition in `Auth#mergeIntoAtom` allows stale keystore reads from `load()` to clobber concurrent `enableBioAuth()`/`disableBioAuth()` writes to `#authAtom` - (File: `features/auth-mobile/module/auth.js`)

### Summary
`Auth.load()` performs several sequential `await`s against the keystore/biometry (`hasPin`, `#hasBioAuth`, `#hasDeviceAuth`, `biometry.get()`) *before* calling `#mergeIntoAtom`, capturing a point-in-time snapshot of auth flags into a plain `params` object. If `enableBioAuth()`/`disableBioAuth()` runs concurrently and completes its own keystore write + `#mergeIntoAtom` call in between `load()`'s reads and its eventual `#mergeIntoAtom` call, `load()`'s stale `params` will unconditionally overwrite the freshly-written flags in `#authAtom`, since `#mergeIntoAtom` spreads `params` over `current` (`{...current, ...params}`) rather than re-reading the keystore at commit time.

### Finding Description
`load()` is defined as:
```js
load = async () => {
  const hasPin = await this.hasPin()
  const hasBioAuth = await this.#hasBioAuth()
  const hasDeviceAuth = await this.#hasDeviceAuth()
  const biometry = await this.#biometry.get()

  await this.#mergeIntoAtom({ hasPin, biometry, hasBioAuth, hasDeviceAuth })
}
``` [1](#0-0) 

and `#mergeIntoAtom` merges the given `params` on top of whatever is `current` in the atom at commit time:
```js
#mergeIntoAtom = async (params) => {
  await this.#authAtom.set((current) => {
    const data = { ...current, ...params }
    ...
  })
}
``` [2](#0-1) 

The functional `#authAtom.set(current => ...)` form only protects against a stale *`current`* snapshot — it re-reads the atom's own latest state at commit time. It does **not** protect against a stale *`params`* object, which is computed from multiple independent, non-atomic keystore reads taken well before the `set()` call executes. `disableBioAuth()`/`enableBioAuth()` each perform their own `#setBioAuth` keystore write followed by their own `#mergeIntoAtom` call:
```js
enableBioAuth = async ({ fallbackToDevicePin = false } = {}) => {
  await this.#setBioAuth(true, { useDeviceAuth: fallbackToDevicePin })
  await this.#mergeIntoAtom(fallbackToDevicePin ? { hasDeviceAuth: true } : { hasBioAuth: true })
}
...
disableBioAuth = async () => {
  await this.#setBioAuth(false)
  await this.#mergeIntoAtom({ hasDeviceAuth: false, hasBioAuth: false })
}
``` [3](#0-2) 

Given `Promise.all([auth.load(), auth.disableBioAuth()])`, if `load()`'s `#hasBioAuth()` read occurs before `disableBioAuth()`'s keystore deletion, but `disableBioAuth()`'s `#mergeIntoAtom({hasBioAuth:false,...})` commits *before* `load()`'s own `#mergeIntoAtom({..., hasBioAuth:true})` commits, the atom ends up reflecting `hasBioAuth: true` (and a correspondingly stale `shouldAuthenticate`) even though the keystore secret was just deleted. The reverse ordering (load reading `false` before an in-flight `enableBioAuth` commits `true`) can also resurrect a stale `false`, transiently flipping `shouldAuthenticate` to `false` when a bio-auth/device-auth secret is in fact freshly set. `removePin`/`clear()` are similarly susceptible since they also call `#mergeIntoAtom` after multiple awaits.

### Impact Explanation
The only state affected is the derived `#authAtom` (`hasBioAuth`/`hasDeviceAuth`/`hasPin`/`shouldAuthenticate`), which is a cache/derived-state atom, not the keystore itself — the keystore secrets (`AUTH_KEYSTORE_BIO_AUTH_KEY`, etc.) are written/deleted correctly and independently of this race. Any consumer that re-validates against the keystore directly (e.g. `isCorrectPin`, `hasPin`, `getBioAuthTrigger`) is unaffected. The exploitable impact is limited to transient/persisted inconsistency of the UI-facing `shouldAuthenticate`/`hasBioAuth` flags in `#authAtom`, which could cause protect-worthy UI gating (e.g., a lock screen or bio-auth prompt driven purely by the atom) to be skipped or shown incorrectly until the next `load()` call self-corrects. This is a real-state-consistency bug but its severity depends entirely on whether any security-critical gate trusts `#authAtom.shouldAuthenticate`/`hasBioAuth` without re-verifying against the keystore — this could not be confirmed from the files reviewed.

### Likelihood Explanation
No privilege is required beyond the ability to trigger overlapping RPC calls to `auth.load()`/`auth.enableBioAuth()`/`auth.disableBioAuth()` in quick succession, which the question states is reachable via ordinary concurrent RPC invocation. The race window depends on the relative timing of multiple `await` boundaries in `load()` versus a single `#setBioAuth` + `#mergeIntoAtom` pair in `enableBioAuth`/`disableBioAuth`, making it timing-dependent but reproducible under fuzzing/stress with artificial delays in the keystore mock.

### Recommendation
Make `#mergeIntoAtom` re-derive stale, externally-sourced fields from the source of truth at commit time rather than merging pre-computed snapshots, e.g. have `load()` pass a function/selector to `#mergeIntoAtom` that re-reads `hasPin`/`hasBioAuth`/`hasDeviceAuth`/`biometry` inside the atom's updater callback (or serialize/queue all `Auth` mutating calls so that `load()`, `enableBioAuth()`, and `disableBioAuth()` cannot interleave against the same keystore keys).

### Proof of Concept
Integration/fuzz test plan (extending `features/auth-mobile/module/__tests__/auth.test.js`):
1. Build a fake keystore where `getSecret`/`setSecret`/`deleteSecret` have configurable async delays.
2. Enable bio auth first (`hasBioAuth` keystore secret set).
3. Fire `Promise.all([auth.load(), auth.disableBioAuth()])`, delaying `load()`'s `#hasBioAuth()` read to resolve with the pre-disable value (`true`) while `disableBioAuth()`'s keystore delete + `#mergeIntoAtom` commit resolve first.
4. Assert that after both promises resolve, `authAtom.get()` matches the keystore ground truth (`hasBioAuth: false`, `shouldAuthenticate` derived from actual keystore state) — expected failure: atom incorrectly shows `hasBioAuth: true`.
5. Repeat symmetric case with `enableBioAuth()` racing `load()` to show a false negative (`shouldAuthenticate: false` resurrected despite a freshly-enabled bio auth secret).

  #mergeIntoAtom = async (params) => {
    await this.#authAtom.set((current) => {
      const data = {
        ...current,
        ...params,
      }

      const { hasBioAuth, biometry, hasPin, hasDeviceAuth } = data

      data.hasBioAuth = hasBioAuth && !!biometry
      data.shouldAuthenticate = hasDeviceAuth || hasBioAuth || hasPin

      if (isEqual(current, data)) return current

      this.#logger.info('Updated auth data', data)
      return data
    })
```
