### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted as tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, and `webhook_id` values that are handed to the application's webhook handler entirely from unauthenticated HTTP headers, while the HMAC signature that `Registry.process` validates only covers the raw request body. An unprivileged internet user who is able to replay or forge a request with a previously-observed valid `(body, hmac)` pair can freely substitute the `shop-domain` header, and the signature will still validate, causing the handler to process the webhook under the wrong tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read straight from headers that are not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately treats `request.shop` as the authenticated tenant identity, passing it straight into the handler: [3](#0-2) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes the handler uses to decide "which shop this event is about"`

Here that equality is broken: the HMAC only proves the *body* came from Shopify (assuming body-secret knowledge), it says nothing about which shop the header claims to be. Since `hmac`, `shop`, `topic`, and `webhook_id` are independent, unauthenticated header values layered on top of a body whose signature never mixes them in, any request carrying a previously valid `(body, hmac)` pair — for example one legitimately delivered to the attacker's own shop endpoint — can have its `shop-domain` header rewritten to name a different, victim shop, and `Utils::HmacValidator.validate(request)` will still return `true` because it only recomputes the HMAC over `@raw_body`.

### Impact Explanation
If the host application uses the `shop` field passed to its `WebhookHandler#handle` implementation to select which tenant's data/record to update (a common and encouraged pattern, since `WebhookMetadata#shop` is presented by this gem as the trustworthy shop identity once HMAC validation has passed), an attacker can cause an event legitimately generated for shop A to be attributed to and acted upon for shop B, i.e. cross-tenant data corruption/access. This matches the Critical "cross-tenant access" impact category in scope.

### Likelihood Explanation
Exploitation requires no credentials, tokens, or privileged access: it only requires that the attacker at some point can observe/control one syntactically valid `(raw_body, hmac)` pair delivered to the app's public webhook endpoint (e.g. their own store's webhook, or any topic whose body content is attacker-influenced/predictable) and can then replay it with a different `shop-domain` header value to the same endpoint. Because the gem's `Registry.process`/`Request` API gives applications no signal that `shop`/`topic`/`webhook_id` are unauthenticated, this is not a case of ignoring documented guidance — the gem's own `WebhookMetadata` construction implicitly presents these fields as validated once `HmacValidator.validate` succeeds.

### Recommendation
Bind the tenant-identifying headers into the value that is HMAC-verified, or explicitly document/enforce that `shop`, `topic`, and `webhook_id` must be independently cross-checked (e.g., against the shop that the app expects for a given endpoint/session) before being trusted. At minimum, `Registry.process` should not hand an unauthenticated `shop` value to handlers as if it were validated; the gem should compute/verify a combined signature over body + these header values, or require callers to supply the expected shop and assert equality before invoking the handler.

### Proof of Concept
1. Register an HTTP webhook handler that trusts `WebhookMetadata#shop` as the tenant identity, per the documented pattern in `lib/shopify_api/webhooks/registry.rb`.
2. Obtain any single valid `(raw_body, x-shopify-hmac-sha256)` pair delivered to the app's public webhook endpoint (e.g., from the attacker's own store, where the attacker legitimately receives Shopify webhooks and thus a genuine signature over a body they control/observe).
3. Send a new HTTP request to the same endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but with `x-shopify-shop-domain` changed to the victim shop's domain (and `x-shopify-topic`/`x-shopify-webhook-id` changed if desired).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` (`to_signable_string`) — validation succeeds despite the forged `shop-domain` header.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs its tenant-scoped action against the victim shop, even though the actual signed payload never originated from Shopify for that shop.
