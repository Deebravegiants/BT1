### Title
Volume-level `mountableSecrets` check bypassed via Projected Secret sources - (File: plugin/pkg/admission/serviceaccount/admission.go)

### Summary
`Plugin.limitSecretReferences` only inspects `volume.VolumeSource.Secret` when validating pod secret mounts against a ServiceAccount's `Secrets` allow-list, but it never inspects `volume.VolumeSource.Projected.Sources[].Secret`. A pod whose ServiceAccount has `EnforceMountableSecretsAnnotation=true` (or `LimitSecretReferences` globally enabled) can therefore mount an arbitrary Secret in the namespace by wrapping the `SecretProjection` inside a `Projected` volume instead of using a bare `VolumeSource.Secret`.

### Finding Description
`limitSecretReferences` builds a `mountableSecrets` set from `serviceAccount.Secrets` and enforces it only across a fixed enumeration of pod fields: [1](#0-0) [2](#0-1) 

The enumerated vectors are: `Volumes[].VolumeSource.Secret`, `InitContainers`/`Containers` `Env[].ValueFrom.SecretKeyRef`, `Env­From[].SecretRef`, and `ImagePullSecrets`. There is no handling of `Volumes[].VolumeSource.Projected.Sources[].Secret` (`api.SecretProjection`) anywhere in this function — contrast with the mirror-pod path a few lines above in `Validate`, which explicitly walks `Projected.Sources` to reject `ServiceAccountToken` projections, showing the code is aware `Projected` sources exist but simply doesn't cover `Secret` projections in `limitSecretReferences`. [3](#0-2) 

An attacker who can create Pods in a namespace (an ordinary namespaced user with `create pods` RBAC, using their own restricted ServiceAccount) can submit:
```yaml
spec:
  serviceAccountName: restricted-sa
  volumes:
  - name: v
    projected:
      sources:
      - secret:
          name: arbitrary-secret-not-in-sa-list
```
Because `limitSecretReferences` never looks at `Projected.Sources[].Secret`, the `mountableSecrets.Has()` check is never invoked for this reference, and the pod is admitted, mounting a Secret the ServiceAccount was never granted.

### Impact Explanation
This bypasses the intended containment control (`EnforceMountableSecretsAnnotation` / `LimitSecretReferences`) whose entire purpose is to prevent a ServiceAccount from mounting Secrets outside its allow-list. This maps to the "admission bypass leading to unauthorized cross-tenant/cross-identity secret read" class: a workload can read the contents of any Secret in its namespace (credentials, tokens, TLS keys) that it was not authorized to mount, via only pod-create privileges.

### Likelihood Explanation
Requires only: (1) a ServiceAccount configured with `kubernetes.io/enforce-mountable-secrets: "true"` (or the plugin configured with `LimitSecretReferences=true`), (2) attacker RBAC limited to creating Pods bound to that ServiceAccount in the namespace. No special privileges, no admin, no webhook bypass — a single-field substitution (`projected.sources[].secret` instead of `secret`) in the pod spec fully evades the check. This is trivially repeatable and deterministic.

### Recommendation
Extend `limitSecretReferences` to also walk `volume.VolumeSource.Projected.Sources` and validate `projSource.Secret.Name` against `mountableSecrets`, mirroring the pattern already used for `ServiceAccountToken` projections in the mirror-pod branch of `Validate`. Consider reusing/adapting `podutil.VisitPodSecretNames` (which already appears to enumerate projected secret sources) as the single source of truth for both admission enforcement and mirror-pod restriction, to avoid this kind of divergence.

### Proof of Concept
Table test to add to `plugin/pkg/admission/serviceaccount/admission_test.go`:
1. Build a ServiceAccount `sa` in namespace `ns` with `Secrets: [{Name: "allowed"}]` and annotation `kubernetes.io/enforce-mountable-secrets: "true"`.
2. Case A (existing, should fail): Pod with `Spec.Volumes[0].VolumeSource.Secret.SecretName = "forbidden"` → expect `Validate` to return a `Forbidden` error (already covered).
3. Case B (new, exploit): Pod with
   ```go
   Volumes: []api.Volume{{
       Name: "v",
       VolumeSource: api.VolumeSource{
           Projected: &api.ProjectedVolumeSource{
               Sources: []api.VolumeProjection{{
                   Secret: &api.SecretProjection{LocalObjectReference: api.LocalObjectReference{Name: "forbidden"}},
               }},
           },
       },
   }}
   ```
   Call `plugin.Validate(ctx, admission.NewAttributesRecord(pod, ...), o)`.
   - Expected (fixed): returns `admission.NewForbidden` error referencing `"forbidden"`.
   - Actual (current bug): returns `nil` (admitted), proving the bypass.
4. Repeat for `EphemeralContainers`/other unenumerated vectors as regression coverage if desired, but the Projected-Secret case alone is sufficient to demonstrate the exploitable gap.

```go
func (s *Plugin) limitSecretReferences(serviceAccount *corev1.ServiceAccount, pod *api.Pod) error {
	// Ensure all secrets the pod references are allowed by the service account
	mountableSecrets := sets.NewString()
	for _, s := range serviceAccount.Secrets {
		mountableSecrets.Insert(s.Name)
	}
	for _, volume := range pod.Spec.Volumes {
		source := volume.VolumeSource
		if source.Secret == nil {
			continue
		}
		secretName := source.Secret.SecretName
		if !mountableSecrets.Has(secretName) {
			return fmt.Errorf("volume with secret.secretName=\"%s\" is not allowed because service account %s does not reference that secret", secretName, serviceAccount.Name)
		}
	}
```
