### Title
Webhook `shop-domain` tenant identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `x-shopify-shop-domain` HTTP header, but `to_signable_string` — the data actually protected by the HMAC check in `Utils::HmacValidator.validate` — only covers the raw request body. `Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler. This breaks the identity binding: `shop (verified by HMAC) != shop (used to route/attribute the webhook)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently from the `shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e. the raw body) using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and, if it passes, trusts `request.shop` (the unauthenticated header) as the tenant identity handed to the app's handler: [4](#0-3) 

Because the `api_secret_key` is shared across all shops that have the same app installed (it's per-app, not per-shop), any merchant who installs the app on their own store can obtain a body+HMAC pair that is valid under the app's shared secret (e.g., by triggering `orders/create` on their own shop). Since the shop-domain header is not part of the signed content, that same valid `(body, hmac)` pair can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop that also has the app installed. `Registry.process` will accept the HMAC (body unchanged) and dispatch to the handler claiming the event is `shop: victim-shop.myshopify.com`, even though the payload content actually belongs to the attacker's own shop.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` (as returned by `Registry.process`) to select per-tenant session/storage context — the documented and expected usage pattern — can be made to process attacker-supplied body content under another tenant's identity. This is a cross-tenant data-integrity/access issue: an attacker can inject fabricated order/customer/product event data attributed to a victim shop, or trigger tenant-scoped side effects (e.g. cache invalidation, inventory sync, customer record updates) for a shop they do not own, without ever needing that victim's or the app's real credentials — only their own legitimate app installation. This matches the "field acted on but not covered by the HMAC" analog explicitly called out in scope.

### Likelihood Explanation
Medium-High. The attacker only needs their own (attacker-controlled) shop with the app installed to obtain valid `(body, hmac)` pairs, and the webhook endpoint is by design a public, unauthenticated HTTP endpoint reachable from the internet. No access token, `client_secret`, or privileged account is required — only participation as a normal, unprivileged merchant/installer of the target app, which is the baseline threat model for this scan.

### Recommendation
Bind the tenant identity into the verified signal. At minimum, `Webhooks::Request#to_signable_string` (or the validation flow in `Registry.process`) should incorporate the `shop-domain` header (and/or require the host app to independently confirm the reported `shop` is one it has an active session/install record for) before trusting `WebhookMetadata#shop`. Document explicitly that `request.shop` is unauthenticated and must be cross-checked against a known/installed-shop list by the integrating application before being used for tenant routing.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, obtaining a valid `api_secret_key`-signed webhook delivery for `orders/create`, e.g.:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: `{"id": 123, ...}` (attacker fully controls order content on their own store)
2. Attacker replays this exact body and HMAC to the app's public webhook endpoint, but rewrites the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)` — this only re-hashes `request.to_signable_string` (the untouched raw body) against `Context.api_secret_key`, so it succeeds. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host app to process attacker-controlled content as if it originated from the victim tenant.
