## Analog Found

### Title
Post-deadline permissionless order cancellation races a solver's in-flight `RedeemEscrow` message, letting anyone seize the solver's delivered collateral - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The Beedle report describes a lender who exploits a razor-thin timing window (a 1-second `auctionLength`) to seize a borrower's collateral after the borrower has already performed their side of the deal. The Hyperbridge Intent Gateway's cross-chain order-fill/cancel flow has an analogous timing window at `order.deadline`: a solver can legitimately fill an order in the very last valid block, delivering output tokens to the beneficiary and dispatching a `RedeemEscrow` message back to the source chain — but in the immediately following block, `cancelOrder()` becomes permissionless (callable by *anyone*, not just the order owner), and it races a competing `RefundEscrow` message to the same source-chain escrow with no check that the order was already filled.

### Finding Description
`_cancelFromDest` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (lines 297-307) implements the destination-side cancellation path: [1](#0-0) 

Once `order.deadline < block.number`, the `order.user == msg.sender` check is skipped entirely — the function is permissionless for anyone. It then unconditionally overwrites `_filled[commitment]` and dispatches a `RefundEscrow` message to the source chain, with **no check that `_filled[commitment]` is already non-zero** (i.e., no check that a solver already filled the order on this very chain).

Compare with `_fillCrossChain` (lines 164-220), which is only reachable while `order.deadline >= block.number` (per the documented fill-flow check "`order.deadline >= block.number`"), and which also unconditionally sets `_filled[commitment] = msg.sender` before dispatching a `RedeemEscrow` message back to the source chain: [2](#0-1) 

Both `RedeemEscrow` and `RefundEscrow` are independent, permissionless-relayed ISMP messages that travel back to the source chain and are processed via `onAccept` → `_withdraw`: [3](#0-2) 

Because message delivery order on the source chain is controlled purely by whichever relayer submits the proof first (permissionless, and biddable via `options.relayerFee`/`nativeDispatchFee` on both dispatches), an attacker can:
1. Wait for a solver to fill the order in the final valid block (`fillOrder` succeeds because `order.deadline >= block.number` still holds at fill time on the destination chain), delivering output tokens to the beneficiary and dispatching `RedeemEscrow`.
2. In the very next block, `order.deadline < block.number` is now true, so **anyone** calls `cancelOrder()` → `_cancelFromDest`, dispatching a competing `RefundEscrow` for the same commitment, paying a higher relayer fee to have it delivered to the source chain ahead of the solver's `RedeemEscrow`.
3. If `RefundEscrow` lands first, `_withdraw` drains the escrowed input tokens back to `order.user`, consuming the escrow. When `RedeemEscrow` is later delivered for the same commitment, the escrow is already gone, so the solver receives nothing.

The solver has already irreversibly delivered output tokens to the beneficiary on the destination chain (in `_fillCrossChain`), so this is a direct loss of solver funds analogous to the borrower's seized collateral in the original report — the same razor-thin boundary condition (`order.deadline`) is exploited by racing message delivery instead of an admin-set `auctionLength`.

### Impact Explanation
A solver who correctly fills a cross-chain order right at its deadline can have their entire delivered output — potentially far exceeding the escrowed input value once surplus is accounted for — stolen by any third party (or the order owner) who simply outbids the solver's relayer fee for the competing `RefundEscrow` message. This is concrete theft of solver funds, reachable by any unprivileged intent solver and any unprivileged relayer/attacker, matching a High-severity, direct loss-of-funds analog.

### Likelihood Explanation
The window is narrow (bounded by `order.deadline`), but it is deterministic and cheaply exploitable: an attacker only needs to monitor fills near expiry and outbid the solver's dispatch fee to win the delivery race — no special privilege, governance action, or admin control is required, only normal permissionless relayer/dispatch mechanics that Hyperbridge explicitly supports (`fundRequest`/relayer-fee prioritization).

### Recommendation
`_cancelFromDest` should check `_filled[commitment] == address(0)` before allowing cancellation (mirroring the fill-side check), so that an order already filled by a solver cannot be subsequently "cancelled" and its escrow redirected. Additionally, consider requiring the destination-side fill deadline check and the source-side cancellation-eligibility check to be strictly consistent (e.g., requiring the GET-proof height for `_cancelFromSource`/permissionless `_cancelFromDest` eligibility to be provably *after* the destination chain has finalized past the deadline, not merely `block.number > order.deadline` on the destination chain itself, which can be reorg/race-sensitive), and/or requiring cancellation messages to include proof that no fill occurred, resolved atomically rather than via racing independent message deliveries.

### Proof of Concept
1. Solver monitors an order approaching `order.deadline` and calls `fillOrder()` in the block where `order.deadline == block.number`, satisfying the destination-side expiry check; this delivers output tokens to `beneficiary` and sets `_filled[commitment] = solver`, dispatching `RedeemEscrow(commitment, order.inputs, solver)` to `order.source`.
2. In the next block, `order.deadline < block.number` on the destination chain. Attacker calls `cancelOrder()` → `_cancelFromDest`, which is now permissionless, setting `_filled[commitment] = order.user` and dispatching `RefundEscrow(commitment, order.inputs, order.user)` to `order.source`, paying a higher relayer fee (`options.relayerFee`) than the solver's fill dispatch.
3. A relayer delivers the attacker's `RefundEscrow` message to `order.source` first; `onAccept` → `_withdraw` releases the escrowed input tokens to `order.user`, zeroing the escrow.
4. The solver's `RedeemEscrow` message is later delivered but the escrow is already consumed — the solver receives nothing for the output tokens already delivered on the destination chain.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
