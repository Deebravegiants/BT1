### Title
Unfunded `recapitalize` refunds real custody out of the pool, leaving the cash book overstated and unrelated suppliers' withdrawals failing in the SAC transfer - ([File: contracts/pool/src/ops/recapitalize.rs])

### Summary
Mirroring CVE-2020-13962 — where one TLS session's leftover error state silently corrupts and disconnects unrelated sessions — the pool's `recapitalize` path lets a single unprivileged call corrupt shared market state so that unrelated users' later exits fail. `recapitalize::apply` computes a "refund" as `amount - applied` and pays it out of the pool's own token balance via `cache.transfer_out(&payer, outcome.refund)`, while `accounting` only credits `min(amount, backing_shortfall)` to the cash book. Because `apply` performs no inbound transfer and does not verify custody before refunding, calling it with no real shortfall makes `applied = 0` and `refund = amount`, sending existing suppliers' custody to an arbitrary `payer` while the cash book still records the funds. Every later `withdraw` passes the pool's book-based liquidity guards (`require_reserves` reads the book, not the balance) and then aborts inside the token transfer, freezing unrelated suppliers' funds and hiding the insolvency from every state view.

### Finding Description
- `contracts/pool/src/ops/recapitalize.rs:26-38` — `apply` calls `accounting`, then unconditionally transfers the refund to `payer`. `accounting` (lines 44-67) sets `applied = amount.min(guards::backing_shortfall(&cache))` and `refund = amount - applied`; when there is no shortfall, `applied = 0` and the entire `amount` becomes a "refund" drawn from pool custody that was never funded. Only the `applied` part is credited via `cache.credit_cash`, so the cash book is untouched while custody drains.
- The doc comment at `contracts/pool/src/ops/recapitalize.rs:4` states "The controller transfers `amount` into the pool before this call," but nothing in the pool entrypoint enforces that invariant — the pool function itself is reachable and pays out regardless of whether any inbound transfer occurred.
- Consequence: the cash book continues to report the drained funds. Withdrawals therefore clear the pool's own liquidity/solvency guards (which read the book, not the token balance) and only fail inside the SAC transfer — exactly the cross-session contamination of the CVE: one session's bad state silently surfaces as a failure in unrelated sessions.
- `contracts/pool/tests/flows.rs:3408-3483` demonstrates the mechanism end-to-end: an unfunded `recapitalize` of the full balance drains custody to zero, `cash` still reports at least the supplier's deposit, and the subsequent `withdraw` fails with the SAC `BalanceError = 10` rather than any pool guard.

### Impact Explanation
An unprivileged address can call the pool's `recapitalize` entrypoint directly (or via `controller.recapitalize` before the controller performs its measured inbound transfer, per the documented contract split) with `amount` equal to the pool's token balance and a `payer` it controls. With no backing shortfall, the entire balance is transferred out as "refund" while the cash book still credits it. This is (a) theft of user funds — custody is paid to an arbitrary `payer` — and (b) permanent/temporary freezing of remaining suppliers' funds plus hidden insolvency, since all book-based views still report the market solvent and exits revert in the token layer rather than at a pool guard.

### Likelihood Explanation
The trigger requires only a direct `recapitalize(hub_asset, payer, amount)` invocation — no collateral position, no oracle condition, no timing window. Any unprivileged caller can submit it at any time, and the repo's own regression test reproduces it with a three-call sequence (mint to pool, recapitalize, withdraw). The only mitigating factor is whether the deployed pool contract's `recapitalize` restricts its caller to the controller; the `apply`/`accounting` implementation itself performs no authorization and no custody check, and the code path documented — "the controller transfers `amount` into the pool before this call" — is an unenforced convention rather than a guard.

### Recommendation
- Require the caller in `pool::recapitalize` to be the authorized controller address, or move custody settlement entirely inside `accounting`.
- Make the refund measured, not arithmetic: record the pool's token balance before crediting and only refund the *measured* inbound delta (`transfer_amount_measured`-style), capping `refund` at actually-received funds.
- Refuse (or charge back) any refund when the book-to-custody invariant `token.balance(pool) >= cash` would be violated by the outgoing transfer.
- Consider reconciling `require_reserves`/solvency guards against actual custody, or emitting a book-vs-balance check on exits, so hidden shortfalls surface at the protocol layer instead of inside unrelated users' SAC transfers.

### Proof of Concept
```
// contracts/pool/tests/flows.rs:3408-3483 (existing regression test)
// 1. Supplier deposits 10_000_000_000 via controller.supply; book == custody.
token_admin.mint(&t.pool, &deposit);
let supplied = t.client().supply(&t.sup(0, deposit)).get_unchecked(0)
    .position.scaled_amount;

// 2. Attacker calls pool.recapitalize with payer=attacker and amount=custody.
//    backing_shortfall == 0 => applied = 0, refund = custody;
//    transfer_out pays the entire balance to attacker. Book unchanged.
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);                 // custody drained
assert!(t.state_snapshot().cash >= deposit);           // book still claims funds

// 3. Unrelated supplier withdraws. Book-based guards pass;
//    the call aborts inside the SAC transfer with BalanceError = 10.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());                             // exit frozen, book rolled back
```

The failing leg matches the CVE's shape exactly: the attacker's single action plants corrupt shared state (book > custody), and an unrelated user's session is the one that "disconnects" — its withdrawal reverts deep in the token transfer even though every protocol-level check reported the market healthy.
