### Title
Webhook `shop-domain`/`topic` header spoofing via HMAC that only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` proves the *body* bytes were signed with the app's secret, but the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never part of the signed material. `Registry.process` uses `request.topic` to pick a handler and passes `request.shop` straight through to the app's handler as the tenant identifier.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` by defining: [1](#0-0) 
Only the raw body is included in the signable string. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled directly from HTTP headers: [2](#0-1) 

`HmacValidator.validate` computes an HMAC-SHA256 over `to_signable_string` (i.e., the raw body only) and compares it to the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Webhooks::Registry.process` then trusts the header-derived `topic` to select the handler and forwards the header-derived `shop` (and `webhook_id`/`api_version`) into the handler payload without any additional check that they are consistent with the signed body: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that produced/owns the signed body`. Because the HMAC only covers the body, this equality is never checked — an attacker who possesses one legitimately-signed webhook body/HMAC pair (trivially obtainable by owning/operating any Shopify dev store that installs the target app, since Shopify sends real webhooks to any registered app for any shop) can resend that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers. The HMAC check still passes (body is byte-identical), but `Registry.process` will dispatch to whatever handler the attacker chose via the spoofed `topic`, and will hand that handler a `WebhookMetadata` claiming an arbitrary `shop` — i.e., attacker-controlled shop attribution despite a "verified" HMAC.

### Impact Explanation
This breaks the identity binding `shop authenticated == shop the body actually belongs to`, letting an unprivileged internet user (anyone who can install the app on their own store and capture one webhook delivery) forge the *tenant* and *topic* of a request that the host application will treat as HMAC-verified/authentic. Any app logic keyed on `WebhookMetadata#shop` (e.g., "update shop X's local record", GDPR/mandatory webhook routing, per-tenant data writes) can be tricked into acting on the wrong tenant, and topic spoofing can route data meant for one webhook type into a different handler. This is a cross-tenant identity confusion delivered through the gem's own "verified" webhook API, matching the High-severity class (scope/binding check bypass) called out in scope.

### Likelihood Explanation
Requires the attacker to obtain at least one legitimately HMAC-signed `raw_body` for the target app (trivial: install the app on an attacker-owned/controlled shop, which triggers real Shopify webhooks with valid signatures), then replay it with rewritten headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is needed — only network access to the app's public webhook URL, which is exactly the threat model in scope.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the material that is authenticated, or otherwise cryptographically/contextually bind them, e.g.:
- Validate that `request.shop` corresponds to a shop with an active/known session/installation for this app before dispatching, rather than trusting the header verbatim.
- Consider incorporating `shop-domain` into the value passed to HMAC comparison logic (or require callers to independently confirm the shop against their session store) before calling into `handler.handle`.
- Document explicitly that `Registry.process`'s HMAC check only authenticates the body, not the shop/topic headers, so integrators are not misled into treating `WebhookMetadata#shop` as verified.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's real `client_secret`.
3. Attacker captures this exact `raw_body` and `hmac` header value.
4. Attacker POSTs the same `raw_body` and `hmac` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or `x-shopify-topic` to a different registered topic).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body`: [5](#0-4) 
6. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"` even though the signed body never originated from that shop: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
