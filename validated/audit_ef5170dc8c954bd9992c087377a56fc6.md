## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the **raw body**, then hands the handler a `shop` value that is read from the `x-shopify-shop-domain` header — a field that was never part of the signed payload. This is the same class of bug as the DeBridge issue: the identity/authority value that downstream logic acts on (`shop`) is different from, and not bound to, the value that was actually cryptographically verified (the raw body bytes).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string`, i.e. over the body only: [2](#0-1) 

`shop` is defined as a completely separate header accessor, outside the signed string: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed to the app's handler, with no cross-check that this shop is the one whose secret/body actually produced the signature: [4](#0-3) 

The binding that should hold is:
`shop_that_produced(valid_hmac_over(raw_body)) == shop_value_acted_on_by_handler`

But the gem only proves `valid_hmac_over(raw_body)` using the app's shared secret; it never proves anything about which shop header accompanies that body. Any request with a body+HMAC pair that is valid for the app's secret (i.e., a body Shopify has legitimately signed for *some* shop that installed the app) can be replayed with an arbitrary `x-shopify-shop-domain` header, and `WebhookMetadata#shop` will carry that attacker-chosen value into the handler: [5](#0-4) 

### Impact Explanation
An unprivileged party who owns/controls a shop that has installed the target app receives legitimately-signed webhook traffic (valid body + HMAC) for *their own* shop. Because the shop header is outside the signed payload, that same body/HMAC pair can be replayed toward the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a *different, victim* shop. Handlers that use `data.shop` as the tenant key (e.g., to select which merchant's records to update/delete, especially for the mandatory `customers/redact`, `customers/data_request`, `shop/redact` topics) will act on the victim tenant using attacker-supplied body content, producing cross-tenant data corruption/exfiltration — the same "wrong identity is trusted for the acted-upon field" pattern as the DeBridge chain-ID mismatch.

### Likelihood Explanation
Moderate: it requires the attacker to control a shop that has installed the app (a normal, unprivileged step — no `api_secret_key`, tokens, or leaked credentials are needed) and the ability to intercept/replay their own outbound webhook HTTP request while modifying only the shop-domain header, which is entirely feasible since that header is not authenticated in any way.

### Recommendation
Bind `shop` to the same authenticated material as the body, e.g. include the shop domain in the HMAC signable string (mirroring Shopify's `X-Shopify-Shop-Domain` inclusion recommendations) or otherwise verify the shop header against an app-side record (e.g., that the shop currently holds an installed/active session before trusting the header) before invoking the handler, instead of passing the raw unauthenticated header value straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, body `B`.
3. Attacker intercepts this outbound request (e.g. via a local proxy they control since it's their own traffic) and resends it to the app's public webhook endpoint with the header changed to `x-shopify-shop-domain: victim.myshopify.com`, keeping body `B` and the HMAC unchanged.
4. `HmacValidator.validate` succeeds (it only checks `B` against the HMAC using the app's secret) — see: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"`, and the app's handler executes body `B`'s logic against the victim tenant.
