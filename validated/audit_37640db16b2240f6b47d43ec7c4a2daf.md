Based on my investigation, I found the strongest analog for this bug class in orb-core.

### Title
User-centric signup path locally marks enrollment as successful and irrevocably uploads Personal Custody Package data before ever consulting the backend's authoritative fraud/duplicate check, with no revocation mechanism if fraud is later confirmed - ([File: src/plans/mod.rs])

### Summary
The `issueDomainName()` report describes an action (domain registration) that is granted immediately based on an unverified, revocable payment method (credit card/Stripe), bypassing the authoritative on-chain commitment check, and relying only on a time lock with no way to reverse the grant if the payment is later reversed. The `do_signup` flow in `orb-core` has the same structural weakness: when `user_centric_signup` is set (from data the user's own app reported to the backend), the Orb uploads the user's Personal Custody Package (biometric-derived credential data) to the backend and marks the signup as enrolled *locally*, without ever calling the backend's authoritative `enroll_user` endpoint that performs server-side fraud/duplicate detection, and there is no mechanism to walk back the already-uploaded PCP data if the app-reported flag was wrong or abused.

### Finding Description
In `do_signup`, after the Orb completes biometric capture and its own (locally-run) fraud check, it unconditionally builds and uploads the Personal Custody Package (PCP) — the cryptographic credential/iris-code material tied to the user's identity — to the backend, regardless of what happens next: [1](#0-0) 

Immediately after that upload, the code branches on `user_centric_signup`, a boolean that originates from data the **user's own app** supplied to the backend (not verified by any orb-side authoritative process): [2](#0-1) 

When `user_centric_signup` is true (and the orb's `ignore_user_centric_signups` config flag is false), the enrollment `success`/status is derived **purely from the local `signup_reason`** computed on-device by `detect_fraud`, and the authoritative `enroll_user` call — which posts to the backend's `signup_post`/`signup_poll` endpoints that perform server-side duplicate detection, fraud checks, and legacy/inflight-match checks — is skipped entirely: [3](#0-2) 

The local `detect_fraud` function that gates this decision is a stub that always returns `false` in this build: [4](#0-3) 

This mirrors the reported bug's structure precisely: an authoritative, reversible verification path (`enroll_user`/backend fraud check, analogous to the on-chain commitment) is bypassed based on an untrusted, self-reported signal (`user_centric_signup`, analogous to a credit-card/Stripe payment claim), the credential data is already durably committed/uploaded (PCP tier 0-2 upload, analogous to the domain being registered) before that decision is even made, and there is no code path anywhere in `plans/mod.rs` or `enroll_user.rs` to revoke, invalidate, or re-verify a signup after the fact if the `user_centric_signup` claim later turns out to be false or fraudulent.

### Impact Explanation
If the `user_centric_signup` flag can be set/spoofed by a malicious app-side actor (or is simply wrong for an out-of-date/misbehaving app), an attacker can obtain what the Orb reports and treats as a "successful" biometric enrollment — and the backend never runs its authoritative duplicate/fraud detection (`signup_post`/`signup_poll`) for that signup, since `enroll_user::Plan::run` is never invoked. Because the PCP has already been uploaded to the backend before this branch is evaluated, there is no way to retroactively undo the credential issuance once the local, unauthoritative path is taken and the backend accepts the "already enrolled" state implied by the orb's report — a direct cross-signup/attestation-forgery style analog to the "domain issued for free, then unrevokable" scenario in the report.

### Likelihood Explanation
Exploitability depends on whether the backend fully trusts the Orb-reported outcome for `user_centric_signup` flows and whether `user_centric_signup`/`ignore_user_centric_signups` are reliably set correctly in field deployments; the code shows this is an intentional app-centric signup optimization path, not a rare edge case — it's a first-class branch in the main signup flow guarded only by a boolean sourced from user-QR-linked app data.

### Recommendation
Do not treat `user_centric_signup` as sufficient grounds to skip the authoritative backend `enroll_user` call. At minimum: (1) always call the backend enrollment/fraud-check endpoint (`signup_post`/`signup_poll`) even for user-centric signups so the backend's authoritative duplicate/fraud detection runs before the PCP upload is considered final; or (2) if PCP upload must precede confirmation, add a backend-side mechanism to invalidate/revoke a PCP upload tied to a `signup_id` if the deferred/local enrollment determination is later found incorrect, similar to the "burn flagged/locked domains" recommendation in the report.

### Proof of Concept
1. Complete a signup on an Orb where the scanned user QR-code's associated `UserData.user_centric_signup` is `true` (as returned by `backend::user_status::request`, see `src/backend/user_status.rs:163-246`).
2. Ensure `orb.config.ignore_user_centric_signups` is `false` (the default per `src/config.rs:383-446`).
3. Complete biometric capture and pipeline successfully so `detect_fraud` (which always returns `false`, `src/plans/mod.rs:1390-1406`) yields `SignupReason::Normal`.
4. Observe that `do_signup` uploads PCP tiers 0-2 to the backend and then sets `enrollment_status` to `Success` locally without ever calling `enroll_user`/`signup_post` (`src/plans/mod.rs:639-656`), meaning the backend's authoritative fraud/duplicate verification never executes for this signup, yet the PCP/credential data is already persisted server-side with no revocation path.
