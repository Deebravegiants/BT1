### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are then handed to the application's handler as authoritative, trusted identity fields are read directly from HTTP headers that are excluded from the signed payload [3](#0-2) .

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning only `@raw_body` [4](#0-3) . `Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it against the `hmac` header value [5](#0-4) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from `shopify-*` / `x-shopify-*` headers with no cryptographic binding to the body or to each other [6](#0-5) .

`Registry.process` calls `Utils::HmacValidator.validate(request)` (body-only check) and then, without any further consistency check, builds `WebhookMetadata` from these unauthenticated header fields and dispatches it to the app-supplied handler [7](#0-6) . The documented contract for this API explicitly promises that `process` "will verify the request did indeed come from Shopify" before exposing `data.shop` and `data.topic` to the handler [1](#0-0) , but the implementation only proves the *body* came from Shopify — it never proves that the *shop* or *topic* attached to that body did.

This breaks the intended identity binding: `hmac == HMAC(body)` should imply `shop == the shop that produced this body`, but the code only checks the former and silently trusts the latter as read off an ordinary, attacker-modifiable HTTP header.

### Impact Explanation
Any unprivileged actor who can operate a normal Shopify store and install the target app (a completely unprivileged, self-service action) will cause Shopify to deliver a legitimately HMAC-signed webhook to the app's public webhook endpoint for their own shop. Because the signature covers only the body, that same `(raw_body, hmac)` pair remains valid for *any* combination of `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. The attacker can replay the captured request to the same public endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) for another tenant of the app. The application's webhook handler — following this gem's documented API — will process attacker-controlled body content as if it originated from a victim shop, and dispatch it to per-shop business logic (e.g., app/uninstall handling, order/customer sync, GDPR/mandatory topics) keyed by the spoofed `shop` value. This is a cross-tenant data/identity confusion vulnerability reachable without any credentials belonging to the app or the victim shop.

### Likelihood Explanation
High. No secret, access token, or privileged access is required — only the ability to install the app on any shop (including a free Shopify developer/trial store) and the ability to send an arbitrary HTTP POST to the app's known, public webhook URL, which is by definition internet-reachable. Capturing one's own valid `(body, hmac)` pair and replaying it with different headers requires no cryptography knowledge or brute force.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload used by `Utils::HmacValidator`, e.g., by making `Request#to_signable_string` incorporate a canonical representation of these header values alongside the raw body, or by having `Registry.process` independently verify that the `shop` header is consistent with a previously established, trusted binding (e.g., matching a webhook registration/subscription record keyed by `webhook_id` for that shop) before constructing `WebhookMetadata`. At minimum, the documentation and API should not represent `data.shop`/`data.topic` as verified when only the body is authenticated.

### Proof of Concept
1. Attacker creates a free development store `attacker-shop.myshopify.com` and installs the target public app, triggering a legitimate Shopify webhook delivery to the app's registered endpoint, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: abc-123
   Body: {"id": 1, "note": "malicious content"}
   ```
2. Attacker captures this exact `(body, hmac)` pair (e.g., by proxying their own store's traffic or running their own receiver as a MITM front for the request before it's forwarded).
3. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the same public webhook endpoint, but rewrites:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-topic: app/uninstalled
   ```
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the HMAC — it never inspects the headers.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, `topic: "app/uninstalled"` and dispatches it to the app's handler, which acts on victim-shop's tenant data/state based entirely on attacker-supplied, unauthenticated headers.
