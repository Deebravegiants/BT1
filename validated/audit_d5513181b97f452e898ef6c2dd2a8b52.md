### Title
Missing keyType↔derivationAlgorithm binding in `#getPrivateHDKey` allows a `cardanoByron`-scoped signer to pull key material from the unrelated SLIP10 (nacl) derivation tree - ([File: features/keychain/module/keychain.js])

### Summary
`KeyIdentifier` only forbids the `SLIP10` + `secp256k1` combination, but does not forbid `SLIP10` + `cardanoByron`, so a `KeyIdentifier({ keyType: 'cardanoByron', derivationAlgorithm: 'SLIP10', derivationPath })` is valid and passes `throwIfInvalidKeyIdentifier`. For non-external (regular HD) seeds, `Keychain#getPrivateHDKey` selects the master purely by `derivationAlgorithm` (`this.#masters[seedId][derivationAlgorithm]`) with no check that this matches the expected tree for `keyType`, unlike the check that exists only for external seeds. This lets `cardano.js`'s `signBuffer` derive and sign using key material from the SLIP10/nacl tree instead of the intended BIP32 tree.

### Finding Description
`libraries/key-identifier/src/key-identifier.js` constructor only asserts: [1](#0-0) 
It never restricts `cardanoByron` to `BIP32`. Meanwhile `Keychain#addSeed` populates `this.#masters[seedId]` with **both** `BIP32` and `SLIP10` roots derived from the same underlying 64-byte seed: [2](#0-1) [3](#0-2) 

`#getPrivateHDKey` picks the master strictly by `derivationAlgorithm` from `keyId`, and only validates `keyType` against the master's own `keyId.keyType` when `isExternalSeedId(seedId)` is true — for ordinary (non-external) seeds this check is skipped entirely: [4](#0-3) 

`cardano.js`'s `signBuffer` only asserts `keyId.keyType === 'cardanoByron'` and blindly forwards whatever `getPrivateHDKey` returns into `seedToCardanoV1Seed`: [5](#0-4) 

Thus, an attacker who constructs (or is permitted to submit) a `KeyIdentifier` with `keyType: 'cardanoByron'` and `derivationAlgorithm: 'SLIP10'` bypasses the intended BIP32-only binding for Cardano and instead derives from `this.#masters[seedId]['SLIP10']` — the same tree used for `nacl` keys (e.g. Solana/other ed25519 assets) — at an attacker-chosen `derivationPath`. That derived seed (which is entropy belonging to a different asset's key tree/path) is then fed into `seedToCardanoV1Seed()` and signed as a Cardano key.

### Impact Explanation
This breaks the intended invariant that `keyType` strictly determines which derivation tree (`BIP32` vs `SLIP10`) is used, allowing cross-tree/cross-asset key-material confusion: entropy from another asset's SLIP10/nacl derivation path is silently consumed to produce a "Cardano" signature. This violates account/key segregation guarantees that dapp-origin authorization for `cardanoByron` signing is expected to enforce (an origin scoped to Cardano should never be able to cause derivation from another asset's key tree/path). While `seedToCardanoV1Seed`'s HMAC transform prevents direct raw secp/ed25519 private-key disclosure of the other asset, the check that is supposed to bind `keyType` to the correct KDF (present for external seeds) is missing for ordinary seeds, which is the root design flaw enabling this class of confusion.

### Likelihood Explanation
Any code path that lets a caller (dapp/message-signer plumbing) supply or influence a `KeyIdentifier`'s `derivationAlgorithm` independently of its `keyType`—while nominally restricting the caller to `keyType: 'cardanoByron'`—triggers this immediately; it requires no lock bypass, no leaked keys, and works with an ordinary unlocked seed already present in the keychain. The bug is deterministic and 100% reproducible given such a `KeyIdentifier`.

### Recommendation
Enforce the `keyType`↔`derivationAlgorithm` pairing centrally, not only for external seeds. In `Keychain#getPrivateHDKey`, add an explicit assertion (mirroring the external-seed check) that `cardanoByron`/`secp256k1` require `derivationAlgorithm === 'BIP32'` and `nacl` requires the algorithm matching the seed's intended tree, before calling `master.derive(derivationPath)`. Alternatively, tighten `KeyIdentifier`'s constructor to also forbid `SLIP10` + `cardanoByron` (and any other non-`nacl` keyType) so invalid identifiers can never be constructed in the first place.

### Proof of Concept
```js
// features/keychain/module/__tests__/cardano-slip10-confusion.test.js
import keychainDefinition from '..'
import KeyIdentifier from '@exodus/key-identifier'
import { mnemonicToSeed } from '@exodus/bip39'

test('cardanoByron keyId with SLIP10 derivationAlgorithm derives from the wrong tree', async () => {
  const keychain = keychainDefinition.factory({})
  const seed = await mnemonicToSeed({ mnemonic: 'menu memory fury language physical wonder dog valid smart edge decrease worth' })
  const seedId = await keychain.addSeed(seed)

  const bip32KeyId = new KeyIdentifier({
    keyType: 'cardanoByron',
    derivationAlgorithm: 'BIP32',
    derivationPath: "m/44'/1815'/0'/0/0",
  })

  const slip10KeyId = new KeyIdentifier({
    keyType: 'cardanoByron',           // still scoped/authorized only for cardanoByron
    derivationAlgorithm: 'SLIP10',     // attacker-chosen algorithm
    derivationPath: "m/44'/1815'/0'/0/0",
  })

  const sigBip32 = await keychain.signBuffer({
    seedId, keyId: bip32KeyId, signatureType: 'ed25519', data: Buffer.from('hello'),
  })
  const sigSlip10 = await keychain.signBuffer({
    seedId, keyId: slip10KeyId, signatureType: 'ed25519', data: Buffer.from('hello'),
  })

  // EXPECTED (secure): this should throw, because SLIP10 is not a valid
  // derivationAlgorithm for keyType 'cardanoByron'.
  // ACTUAL (vulnerable): both calls succeed and produce DIFFERENT signatures,
  // proving #getPrivateHDKey derived from the SLIP10 tree instead of enforcing BIP32.
  expect(sigBip32.equals(sigSlip10)).toBe(false)
})
```
Expected secure behavior: `signBuffer`/`#getPrivateHDKey` should reject `keyId.derivationAlgorithm === 'SLIP10'` when `keyId.keyType === 'cardanoByron'` (or any keyType/algorithm mismatch) with an assertion error, instead of silently deriving from and signing with SLIP10-tree key material.
