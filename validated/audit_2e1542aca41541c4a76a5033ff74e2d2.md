### Title
Webhook shop-domain, topic, and webhook-id headers are trusted without HMAC coverage, enabling cross-tenant event spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies only the body's HMAC and then dispatches the handler using these unsigned header values, so the identity binding `signed_bytes == (body, shop, topic)` never actually holds — only `signed_bytes == body` does.

### Finding Description
`Request#to_signable_string` returns `@raw_body` alone: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, `#webhook_id` are all pulled straight from headers, none of which are part of the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. body-only), and then immediately builds `WebhookMetadata` from the same unauthenticated `request.topic` / `request.shop` / `request.api_version` / `request.webhook_id` before invoking the registered handler: [3](#0-2) 

`HmacValidator.validate` confirms this — it signs/compares `verifiable_query.to_signable_string`, which for `Request` is body-only: [4](#0-3) 

Before the request: `hmac == HMAC(secret, body_A)` was generated by Shopify for a genuine webhook addressed to shop A (e.g. delivered because the reporter installed the app on their own store). After the attacker's replayed request: the same `body_A`/`hmac` pair is resubmitted with `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) changed to shop B. `HmacValidator.validate` still returns `true` because it only checks `body_A` against the secret — it never checks that the signature was produced for shop B or for the claimed topic. The gem then hands `WebhookMetadata(shop: "B", topic: attacker_topic, body: body_A, ...)` to the host application's handler, which will act on it as an authentic event for shop B.

The identity binding that should hold is:
`HMAC(secret, request) → (shop, topic, body)` all authenticated together

but what actually holds is:
`HMAC(secret, body) → body only`, with `shop`/`topic`/`webhook_id` supplied unauthenticated by the caller.

### Impact Explanation
Any user who is themselves a merchant that has installed the app (an "unprivileged" party relative to other tenants) receives genuine, correctly-signed webhooks for their own store. By intercepting/replaying that request to the app's public webhook endpoint with modified `shop-domain`/`topic` headers, they can make the host application process attacker-supplied event data as if it originated from a different, victim shop — a cross-tenant data-injection/spoofing primitive that lives entirely in this gem's webhook processing path (`Registry.process`, `Request`), since the gem provides no protection against header tampering and documents `WebhookMetadata.shop`/`.topic` as trustworthy outputs of `process`.

### Likelihood Explanation
Moderate-to-high: the attacker needs no secret, token, or privileged access — only a single legitimate webhook delivery to their own store (trivial to obtain by installing/using any app built on this gem) and the ability to POST arbitrary headers to the app's own webhook endpoint, both of which are available to an ordinary internet/merchant user.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (e.g., include them in the signable string alongside the body, or require the host application to independently authenticate the delivery, such as verifying the topic/shop against Shopify's webhook delivery metadata or mTLS/allow-listed source). At minimum, document and enforce that `shop`/`topic` headers must not be trusted unless verified out-of-band, and consider deriving the shop from a value that participates in the signature (as Shopify's newer webhook payloads do via `X-Shopify-Hmac-Sha256` computed with topic-bound secrets, or by including these fields in `to_signable_string`).

### Proof of Concept
1. Install the target app on shop A (attacker-controlled) and let it register an HTTP webhook. Shopify delivers a request:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body over shop A's app secret>
   x-shopify-shop-domain: shop-a.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"id": 1, ...}
   ```
2. Capture this exact `body` + `x-shopify-hmac-sha256` value.
3. Replay the same body and HMAC header to the same endpoint, but change:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only re-computes the HMAC over `raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` builds `WebhookMetadata` using `request.shop` == `"victim-shop.myshopify.com"` (attacker-controlled header) and dispatches to the app's handler, which will process/store the attacker's data as belonging to the victim shop — a cross-tenant spoofing/injection outcome, confirmed by inspecting `lib/shopify_api/webhooks/registry.rb:188-200`.

          received_signature = verifiable_query.hmac
