### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only that the raw request body matches the HMAC computed with the app's `client_secret`, but the `shop` value handed to the application's webhook handler is read straight from an unauthenticated HTTP header, never covered by that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` validates the HMAC, then immediately forwards `request.shop` to the handler as trusted tenant-identifying metadata: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) . Passing HMAC validation is treated as proof that the entire request — including the `shop` value — originates from Shopify for that specific shop, but the signature only proves the body's integrity/origin; it says nothing about which shop sent it.

The equality this breaks: `shop authenticated (HMAC-signed bytes) == shop acted upon (header value passed to the handler)`. Before the attack: a legitimate webhook for shop A has `shop-domain: A` and a valid HMAC over its body. After the attack: an attacker who controls (or has captured) any body+HMAC pair signed with the app's single `client_secret` — e.g., from a real webhook delivered to their own installed test shop, since HMAC is computed with the app's shared `client_secret`, not a per-shop key — replays that same body/HMAC pair with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (only the body is checked), and `Registry.process` calls the handler with `shop: <victim-shop>` [5](#0-4) , letting the attacker inject events attributed to a shop they do not control.

### Impact Explanation
Because the app's single `client_secret` is used to sign webhooks for every installed shop (not a per-shop secret), any unprivileged party who has installed the app on their own store (or otherwise obtained one valid signed body) can forge webhook deliveries "from" any other tenant simply by changing the `shop-domain` header, since that header is outside the HMAC's protection. Downstream applications that key session/data lookups off `WebhookMetadata#shop` (the documented, expected use of this field) will act on data for the wrong tenant — a cross-tenant access condition.

### Likelihood Explanation
Exploitation requires only: (1) obtaining any single legitimately signed webhook body+HMAC pair for the app (trivially available to any developer who installs the app on a store they control), and (2) the ability to POST arbitrary headers to the app's webhook endpoint, which is standard for any internet-reachable webhook receiver. No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the signed payload used for HMAC verification — e.g., include them in `to_signable_string` — or otherwise cryptographically tie the header-derived `shop` to the specific delivery (as Shopify's `X-Shopify-Webhook-Id` combined with an authenticated API lookup would allow) before exposing it to handlers as trusted tenant identity.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook delivery, e.g. `orders/create`, noting its raw JSON body `B` and its valid header `x-shopify-hmac-sha256: H` (computed as `HMAC-SHA256(client_secret, B)`).
2. Replay a POST to the app's webhook endpoint with the exact same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: orders/create`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [7](#0-6) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process attacker-supplied order data as if it belonged to `victim.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
