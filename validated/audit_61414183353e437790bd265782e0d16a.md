### Title
Webhook `shop-domain` and `topic` headers are trusted by the handler but excluded from HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the raw body bytes against `Context.api_secret_key` [2](#0-1) . However, `Registry.process` uses `request.shop` and `request.topic` — both parsed straight from HTTP headers, not from the signed body — to dispatch to a handler and populate `WebhookMetadata` [3](#0-2) [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook by the handler == shop whose secret produced the HMAC over the delivered content`. In reality the HMAC only covers `@raw_body` [1](#0-0) ; the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read independently via `shopify_header` and never included in `to_signable_string` [5](#0-4) [6](#0-5) .

Because the app's `api_secret_key` is shared across all shops that install the app (it is not per-shop), any legitimate webhook delivery to the app — for any shop that installed it, including a shop controlled by the attacker — yields a `(raw_body, hmac)` pair that is valid proof of "signed by this app's secret," but it is not proof of *which shop* or *which topic* the body belongs to. An attacker who has captured one such valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store and receiving a webhook) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header to a victim shop's domain and/or the `x-shopify-topic` header to a different topic. `HmacValidator.validate` still succeeds because it never inspects those headers [7](#0-6) , and `Registry.process` will happily route the forged `shop`/`topic` values into the registered handler [8](#0-7) .

The shipped documentation shows host applications are expected to use `data.shop` as the tenant key for enqueued work (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [9](#0-8) , i.e., the gem's own guidance directs consuming apps to trust `data.shop` as an authenticated tenant identifier — which it is not.

### Impact Explanation
This allows cross-tenant data injection: an attacker can make the host application process arbitrary (but attacker-controlled, previously-legitimate) webhook payloads under the identity of a victim shop, or dispatch payloads to unintended topic handlers. Depending on what the host app does with `data.shop`/`data.body` (e.g., updating shop-scoped records, enqueuing background jobs keyed by shop domain), this can corrupt or leak data across tenants — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one valid `(raw_body, hmac)` pair signed by the target app's `api_secret_key`. This is achievable without any credential leak: any user/merchant who installs the app on their own (attacker-controlled) shop legitimately receives such webhooks. No `api_secret_key`, access token, or privileged access is required — only ordinary use of the app as an unprivileged merchant, which then lets them forge the shop/topic attribution for replayed deliveries.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the HMAC-signed content check (or otherwise cryptographically bind them, e.g. by validating them against Shopify's per-request signature scheme or against a session already associated with the currently processing shop) rather than trusting headers verbatim once only the body HMAC is validated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker replays the same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` and/or a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [10](#0-9) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the secret [11](#0-10) .
4. The registered handler executes with `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim.myshopify.com", body: <attacker's own webhook body>, ...)` [12](#0-11) , causing the host app to process attacker data under the victim shop's identity.

        end
