### Title
Webhook `shop` (and topic/webhook-id) fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature only to the raw request body, while `Registry.process` trusts the unauthenticated `shop`, `topic`, and `webhook-id` headers to route the payload to a merchant-specific handler. Because a single app-wide `api_secret_key` is used to validate every shop's webhooks, a valid `(raw_body, hmac)` pair obtained for one shop can be replayed with a different `shop-domain` header to impersonate another tenant.

### Finding Description
The identity binding that should hold is:
`shop_domain_covered_by_hmac == shop_domain_delivered_to_handler`

In `lib/shopify_api/webhooks/request.rb`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

only `@raw_body` is signed. The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to the body:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` then only checks that `HMAC(raw_body, api_secret_key)` matches the supplied `hmac`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` uses this validation gate and then forwards the unauthenticated `shop` header to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

`api_secret_key` is a single, app-wide secret (not per-shop), so the same secret validates webhooks for every merchant that installs the app. This means the gem's own HMAC check does not prove which shop a given `(raw_body, hmac)` pair actually belongs to — it only proves the pair was produced by Shopify for *some* shop of this app. Contrast this with the OAuth callback path, `Auth::Oauth::AuthQuery#to_signable_string`, which correctly includes `shop` inside the signed parameters:
```ruby
def to_signable_string
  params = { code: code, host: host, shop: shop, state: state, timestamp: timestamp }
  URI.encode_www_form(params)
end
``` [5](#0-4) 

The webhook path lacks this equivalent binding.

### Impact Explanation
An attacker who installs the app on their own shop can capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair that Shopify sends for their own tenant. Because the HMAC only covers `raw_body` and is validated with the app-wide secret, the attacker can replay this exact body/HMAC directly to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming the data originated from the victim shop, causing the application to process attacker-controlled data under another tenant's identity — a cross-tenant confusion/injection that crosses the tenant isolation boundary this gem is supposed to enforce.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged action for any merchant/dev store) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind the `shop-domain` header to the signed body (e.g., verify the HMAC over `raw_body + shop_domain`, or cross-check the shop domain reported by the webhook against the shop associated with the specific subscription that was registered) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and lets it register for topic `orders/create`.
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)` where `secret` is the app's single `api_secret_key`.
3. Attacker captures `B` and the HMAC value, then sends their own POST to the same webhook endpoint with:
   - `x-shopify-hmac-sha256: HMAC(B, secret)` (unchanged, still valid because it only signs `B`)
   - `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - `x-shopify-topic: orders/create`
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(raw_body, secret)`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the app to associate attacker-controlled data with the victim's tenant.
