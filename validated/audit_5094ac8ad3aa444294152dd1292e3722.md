### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using a `shop` value taken from an HTTP header that was never part of the signed payload. This breaks the binding "bytes verified == identity acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC generically via `Utils::HmacValidator.validate(request)` (which only calls `request.to_signable_string` and `request.hmac`), and then immediately trusts `request.shop` to build the data passed to the merchant's webhook handler: [3](#0-2) 

`Utils::HmacValidator#validate_signature` confirms only that `to_signable_string` (i.e., the raw body) matches the computed HMAC — it says nothing about which shop sent it: [4](#0-3) 

Because `api_secret_key` (the app's client secret) is shared across every shop that has the app installed, any merchant that has installed the app can receive a webhook body with a **valid** HMAC signed with the same shared secret. That merchant can then replay the same raw body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body bytes against the secret), yet `request.shop` — and therefore `WebhookMetadata#shop` handed to the host application's handler — now falsely claims to originate from the victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the equality that should hold is `shop the HMAC guarantees == shop the handler acts on`, but in this gem's webhook layer it is actually `shop covered by HMAC (none) != shop acted on (attacker-controlled header)`. Any Shopify app built on this gem that uses `WebhookMetadata#shop` to select the tenant/session context for persisting or acting on webhook data is exposed to cross-tenant data injection/corruption by a malicious but legitimately-installed merchant, satisfying the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Any user who installs the app (an "unprivileged" merchant relative to other tenants of the same app) automatically receives real webhooks with valid HMACs computed over bodies of their choosing (by triggering the corresponding shop events). Replaying that body with a forged shop-domain header requires no secret knowledge beyond what a normal merchant already possesses, and the HMAC check in `HmacValidator` and `Registry.process` does nothing to prevent it.

### Recommendation
Include the shop domain (and ideally webhook id / topic) inside the material that is verified — e.g., derive `request.shop` only after confirming a source that Shopify itself binds to the HMAC (Shopify does not sign headers, so the safer fix is for the gem to require host applications to cross-check `request.shop` against the shop associated with the specific webhook subscription/session they expect, and to document/enforce this at `Registry.process`, rather than passing an unauthenticated header value straight into `WebhookMetadata`).

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and `victim.myshopify.com` (same `client_secret`/`api_secret_key` for the app).
2. Attacker triggers a real webhook event on their own store, capturing `raw_body` and the genuine `X-Shopify-Hmac-Sha256` header Shopify computed for that body.
3. Attacker POSTs this same `raw_body` + valid HMAC header to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds (body+secret match), and `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)`.
5. Any host application logic keyed on `data.shop` to select the merchant/session context now operates on the victim's tenant using attacker-supplied data. [1](#0-0) [3](#0-2)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
