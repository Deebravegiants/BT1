### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and identify the tenant are taken from HTTP headers that are excluded from the signature. An attacker who can obtain one legitimate, validly-signed webhook body (e.g., from their own Shopify store) can replay it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header, and the HMAC check will still pass.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` attribute: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `#topic`, and `#webhook_id` are all derived from HTTP headers that are never part of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC, then dispatches the handler using the unauthenticated `request.shop` (and `request.topic`) as the tenant/routing identity: [4](#0-3) 

The binding the code assumes is:
`hmac-verified bytes == bytes used to establish tenant identity`

In reality:
`hmac-verified bytes (raw_body only) != bytes used to establish tenant identity (shop-domain header, topic header)`

Because the header values are not part of `to_signable_string`, any request with a body+HMAC pair the attacker can legitimately obtain (from a webhook fired to their own store) remains valid after swapping the `shopify-shop-domain` (and/or `shopify-topic`) header to point at a different shop or a different topic's handler. The signature check in `HmacValidator.validate` gives no signal that the header-derived identity has been tampered with.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem's webhook processing will treat attacker-controlled header values as if they were verified, cryptographically-bound data about the target shop. A merchant/attacker who controls one shop and can capture (or simply reuse) a valid webhook delivery can forge deliveries that `Registry.process` accepts as authentic for a different `shop` value, since `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built directly from the unauthenticated headers: [5](#0-4) 

Depending on how the host application keys per-shop data/access-token lookups off `WebhookMetadata#shop`, this enables cross-tenant data confusion or actions being attributed to the wrong shop — matching the "cross-tenant access" impact class.

### Likelihood Explanation
The attacker only needs to be an unprivileged Shopify merchant who has installed the app (or otherwise gets one legitimate webhook body+HMAC delivered to the endpoint). No access to `api_secret_key`, access tokens, or `client_secret` is required — they simply replay the same body/HMAC with a modified `shop-domain` header. This is straightforward to exploit and requires no privileged access.

### Recommendation
Include the shop-domain (and topic, api-version, webhook-id) header values in the signed/verified content, or otherwise cryptographically bind them to the raw body before trusting them for tenant routing — e.g., verify the HMAC over a canonical string of `raw_body + shop + topic` rather than `raw_body` alone, or require the host application to separately re-validate the shop domain against a known/allow-listed value tied to the session that originally installed the app.

### Proof of Concept
1. App developer installs the gem's webhook handling and registers a handler for topic `orders/create` using `ShopifyAPI::Webhooks::Registry`.
2. Attacker (who has their own store, `attacker-shop.myshopify.com`, with the app installed) triggers an `orders/create` webhook on their own store, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
3. Attacker replays this exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC only from `raw_body` [2](#0-1)  — validation succeeds despite the shop header being forged.
5. `Registry.process` invokes the handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled order data as if it belonged to the victim shop.
