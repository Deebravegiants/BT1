### Title
Webhook shop-domain (and topic/webhook-id) not covered by HMAC signature, enabling cross-tenant impersonation via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the shop identity (`shop-domain`), `topic`, and `webhook_id` are read directly from HTTP headers that are never part of the signed material. `Utils::HmacValidator.validate` only proves that `@raw_body` was signed with the app's secret; it says nothing about which shop, topic, or webhook that body belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are pulled straight from headers with no cryptographic binding to the body or to the HMAC [2](#0-1) . `Webhooks::Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body signature) and then trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . `HmacValidator.validate_signature` verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac` using `OpenSSL.secure_compare`, but for `Request` that signable string never includes `shop`, `topic`, or `webhook_id` [4](#0-3) .

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the app's handler`

In this implementation, the left side is undefined (the HMAC binds nothing about shop), while the right side is an attacker-controllable header value. Documentation confirms host apps are expected to trust `data.shop` directly as the tenant identifier without any additional verification, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) .

### Impact Explanation
Any unprivileged user who has installed the app on their own shop (a legitimate, low-privilege scenario) will receive genuine webhooks whose bodies are correctly HMAC-signed with the app's `client_secret` for their own tenant. Because the signature covers only the raw body — not the shop, topic, or webhook id — that same body+HMAC pair can be replayed to the app's public webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to claim it belongs to a different, victim shop. `HmacValidator.validate` still returns `true` (the body signature is untouched), and `Registry.process` will hand the forged `shop` value to the app's handler as if it were an authenticated fact [3](#0-2) . Downstream apps that key their persistence, session lookup, or job dispatch by `data.shop` (exactly as shown in the gem's own documentation) can be made to process or store attacker-supplied content under a victim shop's identity — a cross-tenant impact.

### Likelihood Explanation
Reaching this requires only: (1) the ability to install the app on one's own shop (any merchant can do this — no special privilege), (2) capturing one genuine webhook body/HMAC pair addressed to that shop, and (3) sending a normal HTTP POST to the app's webhook endpoint with a modified shop-domain header. No access to `api_secret_key`, no TLS interception, and no privileged account are required — this fits squarely in the "unprivileged internet user" threat model. The likelihood is bounded only by whether a given host app actually keys sensitive logic off `data.shop` without independent verification, which the gem's own documented usage pattern encourages.

### Recommendation
Bind the shop domain (and ideally topic/webhook_id) into the value that is HMAC-verified, or independently verify that `request.shop` matches an expected/allow-listed value for the session/tenant context before trusting it, rather than deriving tenant identity purely from an unauthenticated header while only the body bytes are covered by the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook, e.g.:
```
POST /callback/orders/create
shopify-topic: orders/create
shopify-hmac-sha256: <valid HMAC of BODY signed with app's client_secret>
shopify-shop-domain: attacker-shop.myshopify.com
shopify-webhook-id: abc-123

BODY = {"id": 1, "note": "hello"}
```
2. Attacker resends the identical `BODY` and `shopify-hmac-sha256` value, but changes the header:
```
shopify-shop-domain: victim-shop.myshopify.com
```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: BODY, headers: ...)` builds `to_signable_string` = `BODY` only [1](#0-0) ; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `BODY` and it matches, so validation passes [6](#0-5) .
4. `Registry.process` proceeds and calls the app handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [7](#0-6) , even though this webhook was never sent by Shopify for `victim-shop.myshopify.com`.
