### Title
Attacker-crafted route payload executes arbitrary pool code inside the victim's authorization tree, enabling theft of unrelated wallet funds via controller swap strategies - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
CVE-2020-1931 is a crafted-configuration-to-command-execution bug: attacker-supplied input is interpreted as executable instructions inside a trusted context. XOXNO Lending has the same shape. The controller swap strategies (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `flash_position` swap legs) accept an opaque, fully attacker-controllable `swap`/`StrategySwap` XDR payload and forward it to the configured router via `swap_tokens` in `contracts/controller/src/strategies/swap.rs:36-38`. The router treats the payload as a program: it invokes whatever "pool" address each hop names, with no allowlist of pools, tokens, or venues (`docs/explanation/threat-model.md:154-165`). A malicious "pool" contract executed on this call stack can emit `token.transfer(victim, attacker, amount)` for any token, and Soroban records that invocation as a child of the victim's own `swap_collateral` authorization entry. If the victim signs the simulated authorization tree — which standard signing flows do — the wallet-draining transfer executes. The controller's measured-output and `RouterOverspend` checks bound only the routed amount; they do not bound transfers from the victim's wallet for unrelated tokens.

### Finding Description
`swap_tokens` (`contracts/controller/src/strategies/swap.rs:13-55`) grants the router exactly one `token_in.transfer(controller, router, amount_in)` authorization and calls `router.execute_strategy(controller, amount_in, swap)`, where `swap` is raw XDR supplied by the caller. Inside `execute_strategy` (`contracts/swap-aggregator/src/lib.rs` → `execute::run`), the decoded `StrategyPayload` is a program whose instruction records select pool addresses from the caller-controlled `assets` registry, and `dispatch_hop` / venue adapters `invoke_contract` those addresses (`contracts/swap-aggregator/src/venues/phoenix.rs:23-25` shows the pattern). No allowlist constrains which contracts get invoked.

Because the controller call runs under the end-user's `require_auth`, any contract on the hop call stack can require the victim's auth and have its invocations attached beneath the victim's root authorization. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates this end-to-end: a `RogueHopPool` whose `swap` does `token::transfer(alice, attacker, WALLET_BALANCE)` on a token the protocol never listed gets its transfer recorded as a child of Alice's `swap_collateral` entry in recording mode (lines 194-227), and it executes in enforcing mode once Alice signs that tree (lines 166-183). The swap itself settles fairly — `min_out` is honored, controller balances check out — so all post-swap gates (`verify_router_output`, `RouterOverspend`, final health checks) pass while the wallet is drained.

### Impact Explanation
Theft of user funds beyond the swapped amount. The victim loses arbitrary balances of arbitrary tokens held in their wallet (in the test, `WALLET_BALANCE` of an unlisted token is fully drained, lines 224-225), because the malicious transfer carries the victim's own signature authority. The stolen amount is unbounded by `total_in`, `min_out`, slippage checks, or the controller's risk gates — the threat model itself states "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:158-161`). The same exposure exists on the direct `execute_strategy` path for every swap user.

### Likelihood Explanation
Any unprivileged address can reach this path: `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` all take a caller-supplied `swap` bytes argument, and an attacker can deploy a `RogueHopPool`-style contract freely and embed its address in the payload's `assets` registry. The exploit does require the victim to sign a route whose authorization tree contains the extra child transfer — i.e., it is a phishing/frontend-supply vector (a malicious or compromised quote/route delivered to a user who signs the simulated tree without decoding it), analogous to the original CVE requiring a crafted `.cf` file to be loaded. The threat model notes a client "must decode the route it signs," which is a mitigation expectation, not an on-chain control; nothing in the contracts prevents the poisoned tree from being produced and signed. Severity is reduced to Medium by that user-action precondition.

### Recommendation
- Enforce a governance-managed allowlist of permitted hop pool/venue addresses in the router, so payloads cannot direct execution into arbitrary contracts.
- Alternatively, have the router verify that each invoked `pool` address corresponds to a contract whose code hash is on an approved-venue list.
- At the controller level, document and enforce that strategy `swap` payloads must come from the trusted quote service, and have frontends reject any authorization tree containing children beyond the single expected input `transfer`.

### Proof of Concept
The repository already contains a working PoC: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

- `RogueHopPool.swap` (lines 62-71) reads a stored `(victim, wallet_token, to, amount)` plan and calls `token::transfer(victim, to, amount)`.
- `route_through_pool_stealing` (lines 111-125) builds a `swap` payload naming the rogue pool as `hop_pool`.
- Alice calls `controller.swap_collateral(alice, account_id, USDC, 50_000e7, ETH, route)` (lines 147-164).
- In recording mode, the recorded auth tree shows the stolen `transfer(alice → attacker, WALLET_BALANCE)` nested under Alice's `swap_collateral` invocation (lines 206-222); after signing, `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` while the swap itself pays out fairly (lines 224-226).
