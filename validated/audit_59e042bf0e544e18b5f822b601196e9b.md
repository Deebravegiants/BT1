The premise of the question is factually incorrect. `payload.recipient` in the NEP-413 signing flow is **not** derived from an integrator-supplied `routeConfig`/destination string — it is always the `verifying_contract` value, i.e., the NEAR intents contract ID (e.g. `"intents.near"`), set via `this.envConfig.contractID` in `IntentPayloadBuilder` and `IntentExecuter.signAndSendIntent`. [1](#0-0) [2](#0-1) [3](#0-2) 

The withdrawal destination address (`receiver_id`, `destinationAddress`, etc.) is embedded as an *intent* inside `payload.message` (the JSON-serialized intents array), never as `payload.recipient`. `payload.recipient` only ever gets user-controlled data through the explicit escape hatch `setVerifyingContract()`, which is documented as "Use with caution — normally this is automatically set based on environment" — that's a deliberate override, not something an unprivileged attacker/counterparty can inject through normal flows. [4](#0-3) 

Additionally, `computeSignedNep413Hash` reconstructs the hash purely from the already-signed `MultiPayload.payload` fields (`message`, `recipient`, `nonce`, `callbackUrl`) that are recorded as part of the signed payload itself, not from some separately-tracked `routeConfig`/destination variable. Since `signRaw()` in `IntentSignerNEP413` computes `nep413Hash` from the exact same `nep413Payload` object it returns in `signed.payload`, and passes that pre-computed hash directly to the signing function, there is no independent re-derivation step by "the wallet" inside this SDK that could normalize/trim the recipient differently from what's stored in `signed.payload.recipient`. [5](#0-4) [6](#0-5) 

For a NEAR keypair signer, the hash bytes are signed directly (`signer.sign(nep413Hash)`), with no re-serialization by "the wallet" at all. [7](#0-6) 

The theoretical concern about a browser wallet extension internally normalizing/trimming the recipient string before it computes its own hash (differing from the SDK's pre-computed hash) would be a defect in a third-party wallet/relayer outside this repo, which is explicitly out of scope per the rules ("trust assumptions about external RPCs, the relayer, bridge APIs... defects inside intents.near, bridge contracts or third-party SDKs with no path through this repo").

export async function computeSignedNep413Hash(
	signed: Extract<MultiPayload, { standard: "nep413" }>,
): Promise<Uint8Array> {
	// For NEP-413, we need to reconstruct the original message that was hashed
	const payload = signed.payload;

	return hashNEP413Message({
		message: payload.message,
		recipient: payload.recipient,
		nonce: Array.from(base64.decode(payload.nonce)),
		callback_url: payload.callbackUrl,
	});
}
