### Title
Permissionless, front-runnable pool `Initialize2` allows attacker to set an arbitrary initial price and mint themselves the initial LP supply - (File: `program/src/processor.rs`)

### Summary
`AmmInstruction::Initialize2`, handled by `Processor::process_initialize2`, is the sole supported way to create a new Raydium AMM pool. It performs no check restricting who may call it or verifying that the caller is the party who originally intended to create the pool for a given `market` seed. All of a pool's core accounts (`amm_info`, `target_orders`, `lp_mint`, `coin_vault`, `pc_vault`) are deterministically derived solely from `program_id` and the caller-supplied `market_info.key`, and the initial exchange ratio is set directly from attacker-controlled `init_coin_amount`/`init_pc_amount` instruction arguments. This is the same class of bug as the referenced Algebra `initialize()` front-running finding: whoever's `Initialize2` transaction lands first for a given `market` seed permanently fixes the pool's price and captures virtually all of the initial LP mint.

### Finding Description
`process_initialize2` derives every pool-related account from the `market_info` account key via `generate_amm_associated_account` / `generate_amm_associated_spl_mint` / `generate_amm_associated_spl_token`, all of which call `get_associated_address_and_bump_seed(program_id, market_account.key, associated_seed, program_id)`. [1](#0-0) 
Because `market_info` is explicitly documented as "Just a seed for AMM account. Can be any account", nothing ties this seed to a real, pre-existing on-chain market — the address of the entire pool (AMM state, LP mint, coin/pc vaults, target orders) is fully predictable from any pending `Initialize2` transaction visible in the mempool. [2](#0-1) 

The instruction accepts `init_pc_amount`/`init_coin_amount` directly from the caller with no relationship to any external oracle or existing liquidity, and these values alone determine the pool's starting price and the amount of LP token minted to the caller: [3](#0-2) [4](#0-3) 

Since `generate_amm_associated_account` only succeeds the first time an address is uninitialized (`RepeatCreateAmm` otherwise), whichever transaction lands first for a given `market` key wins irrevocably: [5](#0-4) 

An attacker monitoring the mempool for a pending `Initialize2` call (instruction tag `1`, decoded by `AmmInstruction::unpack`) can read the target `market`, `coin_mint`, and `pc_mint` accounts directly from the transaction, then submit their own `Initialize2` with the same accounts but with a heavily skewed `init_pc_amount`/`init_coin_amount` ratio and higher priority fee/compute price to land first. [6](#0-5) 

### Impact Explanation
The attacker becomes the pool's first and (given `lp_mint.supply != 0` check) only pre-existing LP, minting themselves `sqrt(coin*pc) - 10^decimals` LP tokens for whatever quantities of the two tokens they choose: [7](#0-6) 
By choosing a heavily imbalanced ratio (e.g., depositing a negligible amount of one side and a large amount of the other, or vice versa), the attacker fixes an arbitrary starting exchange price for the pool at essentially no cost. Any legitimate depositor or trader who subsequently interacts with the pool (via `Deposit`, `SwapBaseIn`/`SwapBaseOut`) does so against this attacker-chosen price, allowing the attacker to extract value by withdrawing/swapping against depositors who trade at the manipulated ratio before it is arbitraged back to fair value — the classic "pool front-running" attack. The legitimate creator's own `Initialize2` transaction reverts atomically with `RepeatCreateAmm`/`AlreadyInUse`, so their funds are not directly lost, but their capital and their intended price for the pool are wasted and they must recreate the pool under a different `market` seed, and any user who trusts the on-chain reported reserve ratio before the pool is arbitraged is exposed to loss.

### Likelihood Explanation
The prerequisites are low: the attacker only needs mempool visibility (public on Solana) and the ability to hold and transfer both of the mint's tokens in whatever ratio they choose (or use worthless/attacker-created balances if unrelated mints are used, since nothing enforces `market_info` corresponds to an actual OpenBook market or that `coin_mint`/`pc_mint` correspond to any real trading venue). Front-running via higher priority fees is a standard, well-understood technique on Solana. This mirrors exactly the mitigation gap identified in the referenced Algebra report and was judged Medium severity there due to the fact that on-chain price of a freshly initialized, low-liquidity pool should not be trusted; the same caveat and severity apply here.

### Recommendation
- Require the pool creator to be a pre-authorized/expected signer (e.g., store an expected creator pubkey tied to the `market`/config account and check it in `process_initialize2`), or
- Bind pool addresses/initial price to data that cannot be freely chosen by an unrelated third party (e.g., require `market_info` to genuinely reference an on-chain market/order book whose creation is itself permissioned or rate-limited), and/or
- Add a commit-reveal or minimum-liquidity-lock step so that the entity submitting the `Initialize2` transaction cannot unilaterally and atomically fix the price and receive nearly all the initial LP supply in the same transaction observed via mempool front-running.
- At minimum, document prominently (as the Algebra judge did) that pricing from newly initialized/low-liquidity Raydium pools must not be trusted.

### Proof of Concept
1. Alice constructs and broadcasts an `Initialize2` transaction for a new coin/pc pair with `market = M`, `coin_mint = C`, `pc_mint = P`, `init_coin_amount = 1_000`, `init_pc_amount = 1_000`.
2. Mallory monitors the mempool, decodes the instruction via `AmmInstruction::unpack` (tag `1`) and extracts `M`, `C`, `P` from the account list.
3. Mallory computes the same derived `amm_info`/`lp_mint`/`coin_vault`/`pc_vault` addresses (deterministic function of `program_id` and `M`) and submits her own `Initialize2` for the same `M`, `C`, `P` but with `init_coin_amount = 1`, `init_pc_amount = 1_000_000`, with a higher priority fee.
4. Mallory's transaction lands first: `generate_amm_associated_account`/`generate_amm_associated_spl_*` succeed (accounts previously uninitialized), vaults are funded from Mallory's own token accounts, and she is minted almost all of the initial LP supply at her chosen 1:1,000,000 price.
5. Alice's transaction, arriving second, fails at the account-creation step with `RepeatCreateAmm` (or later with `AlreadyInUse`) and reverts entirely — her intended price and pool ownership are gone; anyone trading against the pool before arbitrage corrects the price interacts with Mallory's manipulated ratio.         program_id: &Pubkey,
        assign_to: &Pubkey,
        market_account: &'a AccountInfo<'b>,
        associated_token_account: &'a AccountInfo<'b>,
        user_wallet_account: &'a AccountInfo<'b>,
        system_program_account: &'a AccountInfo<'b>,
        _rent_sysvar_account: &'a AccountInfo<'b>,
        associated_seed: &[u8],
        data_size: usize,
    ) -> ProgramResult {
        let (associated_token_address, bump_seed) = get_associated_address_and_bump_seed(
            &program_id,
            &market_account.key,
            associated_seed,
            program_id,
        );
        if associated_token_address != *associated_token_account.key {
            msg!("Error: Associated token address does not match seed derivation");
            return Err(AmmError::ExpectedAccount.into());
        }
        if associated_token_account.owner == system_program_account.key {
            let associated_account_signer_seeds: &[&[_]] = &[
                &program_id.to_bytes(),
                &market_account.key.to_bytes(),
                associated_seed,
                &[bump_seed],
            ];
            let rent = Rent::get()?;
            let required_lamports = rent
                .minimum_balance(data_size)
                .max(1)
                .saturating_sub(associated_token_account.lamports());
            if required_lamports > 0 {
                invoke(
                    &system_instruction::transfer(
                        user_wallet_account.key,
                        associated_token_account.key,
                        required_lamports,
                    ),
                    &[
                        user_wallet_account.clone(),
                        associated_token_account.clone(),
                        system_program_account.clone(),
                    ],
                )?;
            }
            invoke_signed(
                &system_instruction::allocate(associated_token_account.key, data_size as u64),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
            invoke_signed(
                &system_instruction::assign(associated_token_account.key, assign_to),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
        } else {
            associated_token_address.log();
            return Err(AmmError::RepeatCreateAmm.into());
        }
