## Analysis

The relevant analog in Hyperbridge is `pallet-messaging-incentives`, which mints a `ReputationAsset` to whoever relays an ISMP message, scaled by the message body's byte size, and that reputation balance is the sole criterion `pallet-collator-manager` uses to select the paid Collator set each session. Both roles (dispatcher and relayer) are explicitly permissionless.

### Title
Byte-Inflated Self-Relay Lets Any Unprivileged Relayer Mint Unbacked Reputation and Buy Collator Seats - (File: modules/pallets/messaging-incentives/src/lib.rs)

### Summary
`pallet-messaging-incentives::on_executed` mints `ReputationAsset` to the relayer proportional to `body.len()` of every delivered `Request`, based only on the relayer's own signature over the message and no economic cost tied to body size beyond a fixed-size state/membership proof. Because relaying (and dispatching) is fully permissionless, an attacker can self-dispatch a request with an arbitrarily padded body between endpoints they control, self-relay it to themselves, and mint reputation nearly for free — exactly mirroring the donation-voting exploit where a recipient funnels self-controlled "donations" to itself to unfairly capture a larger share of a shared allocation pool. Here the "matching pool" is the Collator seat allocation, which is ranked purely by `ReputationAsset` balance.

### Finding Description
`Pallet::message_bytes` sums `max(body.len(), 32)` across the requests in a delivered message [1](#0-0) , and `on_executed` mints `rate * bytes` of `ReputationAsset` to the account recovered from the message's `signer` field, with no other gating on the content, source, or purpose of the message [2](#0-1) .

The cost of getting a request accepted as "delivered" does not scale with `body.len()`. The request handler verifies membership using only the request's commitment hash (`hash_request`), not the body content — the Merkle/state proof size is bounded and effectively independent of the actual payload size [3](#0-2) . The `StateMachineClient::verify_membership`/`verify_state_proof` abstraction likewise operates only on commitment hashes and small storage keys, never on raw body bytes [4](#0-3) .

Both roles required to trigger this are explicitly permissionless: "This model is inherently permissionless — no staking or whitelisting is required to participate. Any operator can run a prover and begin competing to submit proofs and earn rewards" applies to the analogous prover role, and the collator docs confirm messaging relayers earn reputation identically: "Messaging Relayers deliver cross-chain messages between connected chains and earn $BRIDGE rewards through pallet-messaging-incentives... All three roles earn reputation on equal footing" [5](#0-4) . That `ReputationAsset` balance is the exclusive ranking signal `pallet-collator-manager::new_session` uses to select the paid Collator set for the next session [6](#0-5) .

This is structurally the same bug class as the donation-voting report: a participant who fully controls both ends of the interaction (donor+recipient there; dispatcher+relayer here) can generate self-referential "activity" that the protocol treats as legitimate contribution to a shared reward pool, at a cost far below the reward, and thereby seize a disproportionate share of that pool (matching funds there; collator seats/block-production rewards here) at the expense of honest participants.

### Impact Explanation
An attacker can dispatch a trivial ISMP `PostRequest` with a maximally padded `body` between a source chain and destination they control (or between accounts on the same appchain), sign the delivery message themselves, and mint reputation proportional to the padding — with real cost limited to one dispatch + one bounded-size state proof, not to the reputation earned. Accumulating enough padded self-relayed messages lets the attacker outrank honest relayers/provers in `ReputationAsset` balance and get selected into the Collator set purely through fabricated "activity," which is an unauthorized/unearned elevation into a privileged block-producing role that legitimate operators are supposed to earn through real service (real message delivery, real consensus proofs). This is a real, protocol-level "unauthorized app action" (buying a collator seat with unbacked/self-generated reputation) that can be used to seed censorship, MEV extraction, or bypass the fisherman-veto liveness protections tied to legitimate collators.

### Likelihood Explanation
High. No privileged role, staking, or whitelist is required — any account can dispatch a self-addressed request and act as its own relayer, satisfying the "unprivileged message dispatcher/relayer" reachability requirement directly. The only friction is gas/dispatch fees on chains the attacker controls, which is far cheaper than the honest cost of running real infrastructure to earn equivalent reputation.

### Recommendation
Decouple `ReputationAsset` minting from raw byte counts of self-controlled messages: require the relayed message's source and destination to be distinct, economically-external state machines (not both attacker-controlled), cap per-account reputation accrual per session independent of message size, or tie the mint rate to real, non-self-referential fee payment rather than to `body.len()` alone.

### Proof of Concept
1. Attacker deploys/controls a source-chain "app" (or reuses a demo module) able to call `IsmpDispatcher::dispatch_request` with an arbitrary `body`.
2. Attacker dispatches a `PostRequest` from `source = A` to `dest = B`, with `body` padded to the maximum allowed message size, `fee = 0`.
3. Attacker (or a colluding account) relays the message to Hyperbridge, signing it as `msg.signer`, satisfying `verify_membership` with a fixed-size state proof against `RequestCommitments` regardless of `body.len()` [3](#0-2) .
4. `pallet_ismp` executes the message and calls `pallet_messaging_incentives::on_executed`, which computes `bytes = max(body.len(), 32)` and mints `rate * bytes` of `ReputationAsset` to the attacker's `signer` account [2](#0-1) .
5. Repeat cheaply across many self-dispatched/self-relayed padded messages to accumulate a `ReputationAsset` balance exceeding all honest operators.
6. At the next session boundary, `pallet_collator_manager::new_session` ranks candidates purely by this balance and selects the attacker's controller account into the Collator set [6](#0-5) .

	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}

/// A state machine client. An abstraction for the mechanism of state proof verification for state
/// machines.
///
/// All trie-key derivation methods take `Vec<H256>` request commitment hashes rather than the
/// full request/response objects. Callers compute the commitment via `hash_request` at the
/// boundary so the trait stays agnostic to ISMP message types and just maps commitment hashes
/// onto the per-chain storage layout.

    /// Verify the overlay membership proof of a batch of request commitments against `root`.
    fn verify_membership(
        &self,
        host: &dyn IsmpHost,
        commitments: Vec<H256>,
        root: StateCommitment,
        proof: &Proof,
    ) -> Result<(), Error>;

    /// Used by the timeout handler to prove non-delivery.
    fn receipts_state_trie_key(&self, commitments: Vec<H256>) -> Vec<Vec<u8>>;
