Malicious deflationary/rug-pull ERC20 order input can permanently freeze cross-chain solver repayment in IntentGatewayV2 - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`/`IntentsBase._withdraw` releases escrowed order-input tokens to a solver by trusting the recorded `_orders[commitment][token]` accounting and calling `safeTransfer(beneficiary, amount)` without re-checking the gateway's actual token balance at redemption time. An order creator who supplies a malicious ERC20 as the order's input asset — one with an attacker-controlled/privileged burn or rebase function (the same bug class as the 3913 token's `burnPairs()` used to desynchronize real balances from cached accounting) — can zero out the gateway's real holdings of that token *after* a solver has already irrevocably delivered real value on the destination chain, causing the solver's `RedeemEscrow` settlement to permanently revert.

### Finding Description
`placeOrder` correctly measures actual received balances for fee-on-transfer tokens (see `evm/src/apps/IntentGatewayV2.sol:291-306, 312-323`), but this only defends against value lost *at deposit time*. It does not defend against value being removed from the contract's balance *after* deposit and before withdrawal by any mechanism external to a `transfer`/`transferFrom` call — e.g., a privileged burn function on a malicious token contract that the order's `input` token address points to, analogous to `I3913(vulnerable).burnPairs()` in the reference exploit, which lets a controlling party destroy balances at arbitrary addresses independent of a transfer.

`_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`) does:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
```
It never checks `IERC20(token).balanceOf(address(this))` against `amount` before transferring. If the recorded escrow no longer corresponds to real token balance (because the order's malicious input token burned the gateway's balance out-of-band), `safeTransfer` simply reverts.

For a cross-chain order:
1. The order creator (attacker) places an order on the source chain with a malicious, attacker-controlled ERC20 as `inputs[0]`, and a real valuable asset (e.g., DAI/USDC/ETH) as the requested `output`.
2. A solver, observing the order, calls `fillOrder` on the destination chain and immediately delivers the real output tokens to the beneficiary (`evm/src/apps/intentsv2/IntrinsicIntents.sol` cross-chain fill path / `IntentGatewayV2._fillCrossChain`), then a `RedeemEscrow` POST request is dispatched back to the source chain to release the escrowed malicious input token to the solver.
3. Before that message is delivered/processed on the source chain, the attacker calls a privileged function on their own malicious token contract to burn/zero the balance held by the `IntentGatewayV2` contract.
4. When Hyperbridge delivers the `RedeemEscrow` request and `onAccept` invokes `withdraw()` → `_withdraw()`, `IERC20(token).safeTransfer(solver, amount)` reverts because the gateway's real balance is now below `amount`. Since the underlying token balance can never be restored, every future relayer attempt to deliver this request reverts identically — the message becomes permanently undeliverable, and the solver's expected repayment is permanently frozen while the attacker has already received real value on the destination chain for a worthless/rugged input.

### Impact Explanation
This lets an intent-order creator steal from any solver who fills a cross-chain order: the solver's genuine payout (real assets delivered on the destination chain) is uncollateralized because the corresponding escrowed input can be destroyed post-fill, and the ISMP settlement message that should compensate the solver can never succeed. This is concrete permanent loss of solver funds and a permanently undeliverable message — no privileged role is required, only the ability to deploy an arbitrary ERC20 and act as an ordinary order creator, which is fully within the unprivileged "intent solver" attack surface named in scope.

### Likelihood Explanation
Likelihood is moderate-to-high: nothing prevents an order creator from choosing any ERC20 contract address as `inputs[i].token`; the gateway performs no allowlisting of input tokens, and solvers must inspect and trust arbitrary tokens named in orders (the same trust assumption abused in numerous documented deflationary/rug-token exploits, including the referenced 3913 case). A financially motivated attacker only needs to deploy one malicious token and wait for a solver to fill their order.

### Recommendation
In `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol`), verify `IERC20(token).balanceOf(address(this)) >= amount` (or measure actual balance delivered) before decrementing `_orders` and transferring, and consider allowlisting/registering permitted input tokens for cross-chain orders (or requiring solvers to escrow real collateral independent of the order's own input token) so that a malicious/rug-pullable ERC20 cannot desynchronize accounted escrow from real balance after a solver has already delivered value.
