### Title
`describeWithdrawal` misreports txHash/status for batched same-`assetId` withdrawals due to `findMatchingWithdrawal` matching by `assetId` only - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves a withdrawal's status/txHash by calling `findMatchingWithdrawal`, which selects the first entry in the bridge's response list whose `near_token_id` maps to the requested `assetId` — it never checks `index` or `destinationAddress`. When a batch contains two withdrawals of the same token to different destinations, both `WithdrawalIdentifier`s (index 0 and index 1) resolve to the *same* underlying record, so the caller polling index 0 can receive the `COMPLETED` status and `transfer_tx_hash` that actually belong to the withdrawal sent to index 1's destination address.

### Finding Description
The equality that should hold is: for every `i`, `describeWithdrawal({index: i, withdrawalParams: withdrawalParams[i]}) == outcome of withdrawal actually executed for withdrawalParams[i]` (in particular, its `txHash` must correspond to the transfer sent to `withdrawalParams[i].destinationAddress`).

The code path:
- `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) fetches the full withdrawal list for the batch transaction via `getWithdrawalStatusWithRetry`, then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`, i.e. it returns the **first** array element whose token matches — it ignores `args.index` and `args.withdrawalParams.destinationAddress` entirely. The comment at line 318 explicitly documents this as unsorted-by-index matching, and lines 410-416 document the known gap ("multiple withdrawals of the same token in a single transaction are not supported").
- `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107` assigns `index` per-bridge-route sequentially but does **not** deduplicate or group by `assetId`+`destinationAddress`; it happily creates two `WithdrawalIdentifier`s with the same `assetId` (index 0 and index 1) if the caller supplies two `WithdrawalParams` for the same token to different addresses.
- `watchWithdrawal` in the same file (`:20-78`) then polls `bridge.describeWithdrawal({...wid})` independently for each identifier. Since the PoA API response is a flat unsorted list and `findMatchingWithdrawal` keys only on `assetId`, both polling loops (for index 0 and index 1) converge on identical bridge lookups and can both find the same list entry (usually whichever completes/appears first), reporting its `txHash`/status for both indices even though the entries have different `destination_address`/`transfer_tx_hash`.

None of the existing guards prevent this: `validateAddress`, `compareAddresses`, and `validateWithdrawal` only validate a single withdrawal's destination address format at creation time — they never cross-check that a status response's destination matches the specific `WithdrawalIdentifier.index` being polled. `supports()` ordering and `FeeExceedsAmountError` are unrelated to status matching. The identical logic and identical gap also exist in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153`.

### Impact Explanation
An integrator/watcher polling `describeWithdrawal` for withdrawal index 0 can receive `{status: "completed", txHash: <hash of the tx that paid withdrawal index 1's destination>}`. If the integrator uses this `txHash` to confirm/credit delivery to `withdrawalParams[0].destinationAddress`, it will incorrectly believe funds were delivered to that address (or reconcile against the wrong on-chain transaction), while the actual recipient was a different address from `withdrawalParams[1]`. This is a status/hash misreport that can cause an integrator to credit or reconcile the wrong recipient — matching the High/Critical category "a status or hash misreport making an integrator credit or refund twice" / "funds delivered to a wrong address ... with no recovery" from the caller's accounting perspective. It is repeatable for every batch containing ≥2 withdrawals of the same `assetId` on the PoA bridge route.

### Likelihood Explanation
Preconditions: the caller (an ordinary SDK user constructing a batched withdrawal, or an integrator forwarding user-supplied `withdrawalParams`) must submit two or more withdrawals in the same intent transaction using the same POA-bridge `assetId` but different `destinationAddress` values. This is a normal, unprivileged usage pattern (e.g., paying out the same token to two different users in one intent) requiring no special permissions, RPC compromise, or malicious relayer — only ordinary batch construction through the public SDK API (`createWithdrawalIdentifiers` / multi-withdrawal flows). The bug is deterministic once the bridge returns both withdrawal records in its unsorted list, and is explicitly acknowledged as unhandled by the code's own comments, making it highly likely to manifest whenever such batches occur.

### Recommendation
Match withdrawal status records using a discriminator that uniquely identifies each withdrawal within the batch — e.g., correlate by `destinationAddress` (and `destinationMemo`/amount) in addition to `assetId`, or track per-`(assetId, destinationAddress)` occurrence counts so that the k-th matching record is bound to the k-th `WithdrawalIdentifier` for that `assetId`. Until the POA Bridge API supports a stable per-withdrawal correlation id, the SDK should either reject/serialize batches containing duplicate `assetId` values for the same route, or explicitly document and guard against it by throwing (as `PoaWithdrawalInvariantError` already does for "not found") rather than silently returning a mismatched result.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
