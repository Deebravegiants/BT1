### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC validation only binds the raw request body. The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values are all read from unauthenticated HTTP headers and passed straight to the handler as if they were verified, exactly matching the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all derived from headers that are never fed into the signature computation: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` to build the `WebhookMetadata` handed to the app's handler, with no additional binding of these fields to the verified body: [4](#0-3) 

The identity equality this code is supposed to guarantee is:

`hmac_verified_bytes == (shop, topic, webhook_id, api_version, body)`

but what is actually verified is only:

`hmac_verified_bytes == body`

The gem's own documentation reinforces the false sense of authentication: it states that `Registry.process` "will verify the request did indeed come from Shopify" and then shows the recommended handler implementation directly consuming `data.shop` to route/attribute the webhook to a tenant, without any suggestion that `shop` needs independent verification: [5](#0-4) [6](#0-5) 

Because all shops installed on a given app share the same `api_secret_key`, any party who can obtain one legitimately-signed `(body, hmac)` pair for their own store (e.g., by installing the app on their own development/test shop and observing a real Shopify webhook delivery) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version`) headers to name a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will dispatch the forged tenant identity straight to the app-defined handler.

### Impact Explanation
This breaks the tenant/shop identity binding that `Registry.process` and its documentation claim to guarantee, enabling an unprivileged party (any user able to install the target app on their own store, which is normal for public/embedded Shopify apps) to make the host application believe a webhook — and the `shop` it is attributed to — originated from a shop they do not own. Per the documented usage pattern, this is used directly to route/store data keyed by shop (`shop_domain: data.shop`), so this is a cross-tenant data-integrity/confusion vector reachable purely over the internet with no access token, no `api_secret_key`, and no privileged account, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for a determined attacker with any legitimate install of the target app (a normal, unprivileged action for a public Shopify app): they can trivially capture one valid `(raw_body, X-Shopify-Hmac-Sha256)` pair for a topic supported by the app, then POST it to the app's public webhook route with forged shop/topic/webhook-id headers. No secret material beyond what is already exposed to any installer is required.

### Recommendation
Bind the identity headers into the HMAC-verified material (or otherwise cryptographically/authoritatively confirm `shop` independently, e.g. by cross-checking against a known/registered shop list or re-fetching webhook metadata from Shopify) before trusting `request.shop`/`request.topic`/`request.webhook_id` in `Registry.process`. At minimum, update `to_signable_string` in `ShopifyAPI::Webhooks::Request` to incorporate the shop/topic/webhook-id headers used downstream, and correct the documentation so it does not claim full request authenticity is verified when only the body is checked.

### Proof of Concept
1. Install the target app on an attacker-controlled test shop `attacker.myshopify.com`; wait for Shopify to deliver a legitimate webhook (e.g., `orders/create`) to the app's public webhook endpoint. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header value.
2. Replay an HTTP POST to the same public webhook endpoint using the identical captured body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally alter `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC only over the raw body (`request.rb#to_signable_string`) — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` value and invokes the app's handler, which (per the documented pattern) treats the webhook as authentically belonging to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
