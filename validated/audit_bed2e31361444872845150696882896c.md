Audit Report

## Title
OIDC Token Exchange Grants Authenticated Session Despite Missing Identity Claim, Bypassing Intended Rejection - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, when the OIDC ID token's `email` claim is missing or not a string, the handler logs the error and writes an HTTP 500 response via `c.String(...)`, but is missing the `return` statement that every other failure branch in this function has. Execution falls through and continues to compute the user's RBAC role from the `groups`/ID claims, insert a row into `oidc_sessions` with `user_email = ""`, and set the session cookie, completing a valid, cookie-backed authenticated session with an assigned role but no identity.

## Finding Description
`handleTokenExchange` performs a sequence of validation steps (state check, token exchange, ID token verification, claim extraction), each of which correctly aborts with `return` on failure — except the email-claim check at line 226-230, which logs an error and writes a 500 response but does not `return`: [1](#0-0) 

Because `return` is omitted, execution continues to map claims to a role via `IDClaimsToUserRole` (unaffected by the missing email): [2](#0-1) , insert a row into `oidc_sessions` with `user_email = ''` (lowercased empty string) and the resolved role: [3](#0-2) , log the audit event with an empty email: [4](#0-3) , and finally set/save the session cookie: [5](#0-4) .

Downstream, `AuthorizedUserWithSession` reconstructs the `clsessions.User{Email, Role}` directly from the `oidc_sessions` row with no validation that `Email` is non-empty: [6](#0-5) . This `User` is used by `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole`, all of which gate solely on `user.Role`, never on `user.Email`: [7](#0-6) .

## Impact Explanation
Any user who completes a valid OIDC login flow against a misconfigured provider (one whose token lacks an `email` claim or returns it in a non-string form, while still supplying a `groups`/ID claim mapping to a privileged role) is granted a persisted, cookie-backed session with `Role` derived from the group claims. Since RBAC enforcement checks only `Role`, this session functions with full permissions of that role (potentially Admin), and the audit log records the login with an empty email, undermining audit attribution. This is a real code-level authentication/authorization defect, not a hypothetical one — the missing `return` is directly verifiable in the source.

## Likelihood Explanation
Exploitation requires the operator's OIDC provider to be configured such that an authenticated user's ID token lacks an `email` claim (or has it as non-string) while still supplying a `groups` claim that resolves to a privileged role. This is a provider/claims configuration scenario rather than something an unprivileged external attacker can force purely by sending crafted requests to the node API — the trigger depends on how the identity provider issues tokens, which is outside the node operator's own request path and requires either operator misconfiguration or a compromised/permissive external IdP. Per the validation rules, issues that require a misconfiguration (here, a provider issuing tokens without expected claims) to be exploitable, rather than being triggerable by an unprivileged actor via normal request flows, fall into the excluded "misconfiguration" category. There is no other reachable path to exercise this bug (a normal login flow always includes an `email` claim from a correctly configured OIDC provider), so likelihood for an unprivileged, non-misconfiguration-dependent attacker is not established.

## Recommendation
Add `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call at `core/sessions/oidcauth/oidc.go:229` so the handler aborts when the `email` claim is missing or invalid, consistent with every other validation branch. Additionally, reject empty-string `email` before persisting the `oidc_sessions` row, and add a defense-in-depth check in `AuthorizedUserWithSession` to reject sessions with an empty `UserEmail`.

## Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'oidc'` with a provider whose ID tokens include a `groups` claim (e.g., `NodeAdmins`) but omit the `email` claim.
2. Complete the OIDC flow to `POST /oidc-exchange` with a valid `code`/`state`.
3. `claims["email"].(string)` fails at `core/sessions/oidcauth/oidc.go:226-230`; missing `return` allows execution to continue.
4. `IDClaimsToUserRole` resolves role to `UserRoleAdmin` (lines 233-245); a row is inserted into `oidc_sessions` with `user_email = ''` (lines 247-260), and the session cookie is set (lines 264-271).
5. Subsequent requests with that cookie pass `AuthenticateBySession` → `AuthorizedUserWithSession` → `RequiresAdminRole`, granting admin API access despite an empty identity — but only achievable given the provider misconfiguration precondition described above.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

	}
