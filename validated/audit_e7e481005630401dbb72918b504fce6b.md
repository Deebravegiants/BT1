This confirms the analog. ### Title
Webhook shop/topic/webhook_id headers are not covered by HMAC, allowing cross-tenant webhook forgery via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [5](#0-4) . The `shop`, `topic`, and `webhook_id` values that are handed to the handler as the trusted identity of the webhook are read directly from HTTP headers [2](#0-1) , but `to_signable_string` — the string the HMAC is actually computed over — is defined as just `@raw_body` [1](#0-0) . None of these headers are part of the signed payload.

### Finding Description
The intended binding is: `shop header == shop bound to this HMAC-authenticated body`. In reality, the gem only checks `hmac == HMAC(secret, raw_body)` and never binds `shop`/`topic`/`webhook_id` to that computation:

- `HmacValidator.validate` computes `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header [6](#0-5) .
- For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are pulled from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers, which are never mixed into the signed string [2](#0-1) .
- `Registry.process` accepts the request once the body-only HMAC passes, then constructs `WebhookMetadata` using the unauthenticated `request.shop` value and dispatches it to the handler as the trusted tenant identifier [3](#0-2) .

Because the signature only proves the body wasn't tampered with, an attacker who has ever received one genuine webhook delivery for a shop they control (a routine, unprivileged action — installing the app on their own store and triggering any webhook topic) can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) for a different tenant. `HmacValidator.validate` still succeeds because it only recomputes over `raw_body`, so `Registry.process` will dispatch the handler with `shop:` set to the attacker-chosen value while the signature was never actually computed for that shop.

### Impact Explanation
This breaks the equality the app relies on for tenant isolation: `HMAC-verified request == request belonging to the shop named in its headers`. Any app handler that trusts `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) as an authenticated identifier — which is the documented usage pattern for this API [7](#0-6)  — can be made to act on shop B's identity using data/timing from shop A's genuine webhook, or have the same event replayed as a forged event for an arbitrary topic/shop pair, entirely without needing `api_secret_key` or any credential of the target shop. This is a cross-tenant identity-binding failure reachable by an unprivileged party who only needs to receive one legitimate webhook for a shop they control.

### Likelihood Explanation
Likelihood is high for any app that relies on `Registry.process`/`WebhookMetadata` as the documented integration point: any user can freely install a Shopify app trial/dev store, receive at least one legitimate webhook with a valid HMAC over the body, and then replay that exact `raw_body`/`hmac` pair against the app's public webhook endpoint with arbitrary `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers. No secret, token, or privileged access is required — only observation of one's own legitimate webhook traffic and the ability to send an HTTP request to the app's public endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or minimally `shop`) in the signable string used for HMAC validation of webhook requests, or otherwise cryptographically bind these header values to the signed body (e.g., verify that the same values were present when the signature was originally issued by Shopify, by including them in the canonical string HMAC'd in `Webhooks::Request#to_signable_string`). At minimum, document that host applications must independently re-verify the `shop`/`topic` against a known list of registered shops/topics before trusting `WebhookMetadata`, since the current HMAC check provides no such guarantee.

### Proof of Concept
1. Install the target app (as any unprivileged user) on `attacker-shop.myshopify.com` and trigger any webhook topic the app registers for (e.g., `orders/create`). Capture the resulting HTTP request: `raw_body` and the `shopify-hmac-sha256` header — this pair is a valid signature per `HmacValidator.validate` [4](#0-3) .
2. Craft a new request to the app's webhook endpoint using the exact same `raw_body` and `shopify-hmac-sha256` value, but set `shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally change `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts these headers since only presence, not correspondence to the signed body, is checked [8](#0-7) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` and matches the (attacker-supplied but genuinely-signed) `hmac`, so validation succeeds [9](#0-8) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [10](#0-9) , causing the app to process attacker-controlled body/topic data under the identity of a shop the attacker does not control — a cross-tenant identity-binding bypass.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`.     )
    render json: {success: true}.to_json
  end
