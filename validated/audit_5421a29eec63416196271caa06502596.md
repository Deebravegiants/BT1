### Title
Webhook shop/topic/id/api_version identity fields are unauthenticated (not covered by HMAC) - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only the raw request body against the `X-Shopify-Hmac-Sha256` signature, then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` values taken from plain, unsigned HTTP headers to build the `WebhookMetadata` handed to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `HmacValidator.validate` computes/compares the HMAC solely over that string [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled directly from HTTP headers with no cryptographic binding to the signature at all [3](#0-2) . `Registry.process` validates only the HMAC and then constructs `WebhookMetadata` from those unauthenticated header fields, handing them to the host app's handler as trusted identity: [4](#0-3) .

Critically, the webhook signing secret is the app's `api_secret_key`/client secret — the same value for *every* merchant that has installed the app, not a per-shop secret. This is confirmed by the OAuth/webhook code sharing the single `Context.api_secret_key` across all merchants [5](#0-4) . Consequently, any merchant who installs the app can capture a validly-HMAC-signed webhook body/signature pair delivered for their own store, then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) with a victim shop's identity. Because `shop` is not part of `to_signable_string`, the forged header sails through `HmacValidator.validate` untouched, and the handler receives `WebhookMetadata#shop` claiming to be the victim store while `body` is attacker-chosen (bounded to whatever body/HMAC pairs the attacker can legitimately obtain from their own shop's webhook deliveries).

This breaks the identity binding: `shop authenticated by HMAC` != `shop stored/used as the tenant key` in `WebhookMetadata`.

### Impact Explanation
This is a cross-tenant data injection / spoofing primitive reachable by any unprivileged internet user who can install the app on their own store (a normal, unprivileged action for any Shopify merchant) and hit the app's public webhook callback URL. Any host application that uses `WebhookMetadata#shop` to route webhook data to a specific merchant's records (exactly as documented in `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to write/process attacker-controlled body content under a victim shop's identity — a cross-tenant boundary break.

### Likelihood Explanation
Likelihood is high for any app that processes more than one merchant: obtaining a valid `(body, hmac)` pair only requires installing the app on an attacker-controlled shop (no special privilege) and capturing one webhook delivery, then replaying it with a modified `shop-domain` header to the same public endpoint.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) as part of the HMAC-covered signable string, or otherwise cryptographically bind the header-derived identity fields to the signed payload (e.g., derive/validate `shop` from a per-shop stored secret/session rather than trusting the header verbatim). At minimum, document and enforce that `WebhookMetadata#shop` must not be treated as authenticated unless the header is cross-checked against a known, already-authenticated shop for that specific `webhook_id`/subscription.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, e.g. `orders/create` with body `{"id":1}` and header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` (signed with the app's single, shared `api_secret_key`).
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because the body/HMAC pair is untouched and unsigned headers were never part of the signature.
4. The host app's handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {"id"=>1}, ...)` and, following the documented pattern, processes/persists the attacker's data under the victim shop's identity. [4](#0-3) [7](#0-6) [8](#0-7)

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
