### Title
Unchecked ERC20 `transfer()` return value in `IntentGatewayV2.placeOrder` predispatch settlement leads to escrow/balance desync - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch branch manually encodes a raw `IERC20.transfer(address,uint256)` call instead of using the `SafeERC20` library that the rest of the contract relies on (`using SafeERC20 for IERC20;`). The encoded call is executed through `CallDispatcher.dispatch`, which only verifies that the low-level `.call` did not revert — it never inspects the ABI-decoded boolean return value of the ERC20 `transfer`. For a non-standard ERC20/TRC20 token that returns `false` on failure instead of reverting, this lets a failed (or partial/no-op) transfer be silently treated as successful, while the contract still credits the full `reducedInputs[i].amount` to escrow accounting.

### Finding Description
In `placeOrder`'s predispatch path, the gateway builds a batch of `Call`s to move funds from the `CallDispatcher` back to itself: [1](#0-0) 

These calls are executed via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`: [2](#0-1) 

`CallDispatcher.dispatch` only checks that the raw external call succeeded (did not revert); it never decodes/validates the `bool` return value that a compliant ERC20 `transfer()` is supposed to return: [3](#0-2) 

Regardless of whether that low-level call actually moved tokens, the gateway unconditionally increments escrow bookkeeping: [4](#0-3) 

This is the same bug class as the referenced `D3MMLiquidationRouter.D3Callee` finding: using the raw `IERC20` interface's `transfer`/`approve` instead of `SafeERC20`, which breaks silently on tokens that don't strictly follow the ERC20 standard (return `false` instead of reverting, or otherwise misbehave). Notably, elsewhere in the very same function and contract, the developers correctly use `safeTransferFrom` for all other token movements, e.g.: [5](#0-4) [6](#0-5) 

The `transferCalls[i]` construction is the sole inconsistent spot that bypasses `SafeERC20`.

### Impact Explanation
An unprivileged order-placer who chooses a predispatch call path (e.g. unwrapping LP tokens before escrow, a normal supported flow) can place an order with a non-standard input token. If that token's `transfer()` returns `false` on failure rather than reverting, the gateway will still record the funds as escrowed (`_orders[commitment][token] += reducedInputs[i].amount`) even though the actual balance held by the gateway did not increase by that amount. This creates a permanent desync between the contract's internal escrow accounting and its real token balance. Because solvers later withdraw exactly the escrowed amount recorded in `_orders` upon fill/settlement, this can result in insolvency of the shared escrow pool — other users' legitimately escrowed funds being drained to cover the shortfall, i.e., permanent freezing/loss of funds for unrelated order placers.

### Likelihood Explanation
Requires a specific class of ERC20/TRC20 token used as a predispatch/input asset whose `transfer()` does not revert on failure (return-`false`-style tokens are common on Tron/TRC20 and among older ERC20 implementations). This is not the default path (`placeOrder` without predispatch calldata correctly uses `safeTransferFrom`), so exploitability depends on the input token's behavior and on the order using the predispatch calldata feature — a supported, user-reachable configuration, not an edge case requiring special privilege.

### Recommendation
Use `SafeERC20.safeTransfer` (the contract already has `using SafeERC20 for IERC20;`) for the dispatcher-to-gateway transfer instead of manually encoding `IERC20.transfer.selector`, e.g. build the call using `abi.encodeCall(IERC20.transfer, (address(this), balance))` is still insufficient by itself — the actual fix is to route this token movement through a call path that validates the boolean return (or decode/check the `Call` `result` bytes in `CallDispatcher.dispatch` for ERC20-transfer-shaped calls), or simply avoid the indirect `CallDispatcher` round-trip and call `IERC20(token).safeTransferFrom` directly where possible, consistent with the rest of the function.

### Proof of Concept
1. Deploy (or use) a token whose `transfer()` returns `false` instead of reverting on insufficient balance/blacklist/paused conditions (representative of common non-compliant tokens).
2. Configure the `CallDispatcher` to hold zero or insufficient balance of that token after the predispatch call executes (e.g. the predispatch call fails to deliver the expected amount, or the token owner blacklists the dispatcher).
3. Call `placeOrder` with `predispatch.call` populated so execution reaches the `transferCalls` construction at `evm/tron/contracts/apps/IntentGatewayV2.sol:427-435`.
4. The encoded `IERC20.transfer(address(this), balance)` call executes via `CallDispatcher.dispatch`; since the token returns `false` rather than reverting, `success` in `CallDispatcher.dispatch` (`evm/src/utils/CallDispatcher.sol:59`) is `true`, so no revert occurs.
5. `_orders[commitment][token]` is incremented by `reducedInputs[i].amount` (`evm/tron/contracts/apps/IntentGatewayV2.sol:441`) even though the gateway's actual token balance did not increase by that amount, creating an escrow/balance mismatch that a solver can later exploit during fill/withdrawal.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
