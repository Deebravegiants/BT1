## Analog Found

### Title
Webhook `shop` (tenant) identity is read from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (and `topic`) values used to dispatch the webhook to a handler are read directly from HTTP headers that are never included in the signed content. This breaks the binding `shop_verified_by_hmac == shop_used_by_handler`, allowing a valid `(body, hmac)` pair obtained from one tenant to be replayed against the app's webhook endpoint with a forged `shop-domain` header claiming to belong to a different tenant.

### Finding Description
`Utils::HmacValidator.validate` authenticates a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the supplied `hmac`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers supplied by the caller of the webhook endpoint, and are not part of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler using `request.shop` and `request.topic` taken from these unauthenticated headers: [4](#0-3) 

Because `shop` is excluded from the signable string, the equality the gem is implicitly supposed to guarantee — `shop authenticated by HMAC == shop the handler acts on` — does not hold. Any unprivileged internet user who can obtain one genuine `(body, hmac-sha256)` pair signed with the app's `client_secret` (e.g., by legitimately installing the app on their own store and capturing a webhook delivered to a server they control) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will accept it because only the body bytes are checked, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming the forged shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass at the SDK level: the value the gem hands to the host app as "the shop this event is for" is not authenticated. Any host application that trusts `WebhookMetadata#shop` (as the SDK's own docs and `Registry.process` intend it to be trusted, since it is derived from a request the SDK has just declared "HMAC valid") to select a session, tenant record, or perform tenant-scoped side effects can be tricked into applying attacker-supplied webhook data to a victim shop's tenant context. This satisfies the Critical bar of cross-tenant access, since the binding broken (shop identity) is exactly the tenant boundary this SDK is responsible for asserting after signature validation.

### Likelihood Explanation
Any internet user who signs up for a normal (even free) trial/install of the app being protected can generate a legitimately-HMAC-signed webhook body under the app's real `client_secret` without ever learning the secret — Shopify computes and delivers that HMAC to them from their own store. They can then trivially replay the captured `(body, hmac-sha256)` bytes to the target app's public webhook endpoint with a different `shop-domain` header value, since no additional secret, token, or privileged access is required to reach the endpoint or to construct the forged headers.

### Recommendation
Include the tenant-identifying and dispatch-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body before dispatch — e.g., by validating that `shop-domain` matches a shop that is independently confirmed to have a matching, currently-installed access token/session, or by having `to_signable_string` incorporate the header values so a replay against a different `shop-domain` invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid under the real app `client_secret` since it was genuinely computed by Shopify.
2. Attacker replays that captured body verbatim to the same app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and any topic header desired) instead of their own shop domain.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not correctness of `shop-domain`/`topic` is checked), and `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks the (unchanged) raw body: [4](#0-3) 
4. `Registry.process` invokes the app's registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though nothing about `victim-shop` was ever authenticated.
