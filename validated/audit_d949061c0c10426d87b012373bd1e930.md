### Title
Single `maxOracleAge` staleness bound shared across heterogeneous Chainlink feeds in `SimplexPaymaster` - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using two independent Chainlink feeds — `nativeOracle` (native/USD) and each token's `tokenOracle` (token/USD) — but validates both against one shared `maxOracleAge` threshold. This mirrors the reported `ChainLinkDataConsumer` finding: different feeds have materially different heartbeats, so a single staleness bound is either too loose for the fast feed or bricks the slow one.

### Finding Description
`_getOraclePrice` enforces freshness using the single storage variable `maxOracleAge` for whichever oracle is passed in: [1](#0-0) 

This function is invoked identically for both the native/USD feed and the token/USD feed in `_tokenPrice`, which is the pricing routine used on every UserOp validation path (`_fetchDetails` → `_tokenPrice`) and in `swapAndDeposit`: [2](#0-1) [3](#0-2) [4](#0-3) 

`maxOracleAge` is a single global governance parameter, and the contract's own documentation acknowledges heartbeats differ across the two feed types it consumes ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h"), yet no per-oracle heartbeat is stored or checked: [5](#0-4) [6](#0-5) 

Because `_setParams` only bounds `maxOracleAge` between `0` and `MAX_ORACLE_AGE` (7 days) with no per-oracle differentiation, governance is forced to pick one value: either loose enough for the slowest configured feed (e.g., a 24h stablecoin heartbeat), which lets the other, faster-updating feed (e.g., native/USD) be consumed up to that same stale bound, or tight enough for the fast feed, which will spuriously revert (DoS) once a slower feed's natural heartbeat exceeds it. [7](#0-6) 

### Impact Explanation
`_tokenPrice`/`_getOraclePrice` drive the exact exchange rate the ERC-4337 paymaster charges a solver's stablecoin for sponsoring gas, and this path is triggered by any unprivileged UserOp sender (an ERC-4337 "bandwidth purchaser") during `_fetchDetails`, which is called on every validated UserOp. If governance widens `maxOracleAge` to accommodate a slow stablecoin feed's heartbeat, the fast-moving native/USD price can be consumed while stale for up to that same window. A sender who submits a UserOp while the native asset price has diverged materially from the stale on-chain answer (e.g., after a sharp native-asset price move within the stale window) can force the paymaster to price gas at the old rate — draining paymaster-held native funds/EntryPoint deposit relative to what it collects in stablecoin, a direct value-extraction/theft-of-funds condition. Alternatively, tightening the bound to protect the fast feed makes the contract non-functional (reverts) once the slower feed's legitimate heartbeat naturally exceeds the shared threshold, denying all users this permissionless gas-payment path.

### Likelihood Explanation
Any user can submit a UserOp at any time; no privileged action is required to trigger `_fetchDetails`/`_tokenPrice`. The condition depends on Chainlink feed staleness/divergence occurring within the shared window, which is a normal, expected operating condition given the acknowledged heartbeat mismatch documented directly in the contract's own comments (27s vs 24h). This makes the unsafe window reachable under ordinary market conditions, not an edge case requiring compromise of any privileged role.

### Recommendation
Store and enforce a per-oracle maximum age (e.g., add a `maxAge` field to both the native-oracle configuration and each `TokenConfig`) instead of one shared `maxOracleAge`, and check `_getOraclePrice` against the specific oracle's configured heartbeat rather than a single global bound.

### Proof of Concept
1. Governance registers a token whose Chainlink feed has a 24h heartbeat (e.g., a stablecoin) alongside `nativeOracle`, a fast feed with a 1h heartbeat, and sets `maxOracleAge` to a value tolerant of the 24h feed (e.g., close to 24h) via `UpdateParams`/`_setParams`.
2. `nativeOracle`'s `latestRoundData().updatedAt` ages past its natural 1h heartbeat but remains within the 24h `maxOracleAge` window while the true native/USD price has moved significantly.
3. An attacker submits a UserOp using mode `0x00`/`0x02` paymasterData; `_fetchDetails` calls `_tokenPrice` → `_getOraclePrice(nativeOracle, ...)`, which passes the staleness check (`block.timestamp - updatedAt <= maxOracleAge`) despite the stale, favorable price.
4. The paymaster charges the stablecoin amount computed from the stale native price, letting the attacker underpay relative to actual gas cost, extracting value from the paymaster's native balance/EntryPoint deposit over repeated operations.

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
