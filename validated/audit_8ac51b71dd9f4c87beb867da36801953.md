### Title
Webhook shop domain header is not covered by the HMAC signature, enabling shop spoofing via `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The report's bug class is "a paid/charged/consumed value that is not bound to the value that was actually verified" — in `Gateway.query()`, `msg.value` is checked (`>=`) but never reconciled against the fee that was actually charged, so excess value is silently accepted without being tied to what was verified. The analogous defect in this Ruby gem is in `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process`: the HMAC signature only signs the raw webhook body, but the gem lets a caller-controlled header (`shop-domain`) flow into the trusted `WebhookMetadata.shop` field without that field ever being part of the signed material — i.e. the identity binding "the shop that is cryptographically verified == the shop the handler acts on" is broken.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body — none of the Shopify headers, including `shop-domain`, are part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (parsed straight from the unauthenticated header) to build the `WebhookMetadata` object handed to the app's handler: [3](#0-2) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it's not a per-shop secret), any unprivileged user who installs the app on their own (attacker-controlled) shop will legitimately receive real webhooks — with a valid HMAC computed over the body using the same shared secret that protects every other tenant's webhooks. That attacker can then replay the exact same body/HMAC pair while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with any other victim shop's domain. `Registry.process` will still call `Utils::HmacValidator.validate(request)` successfully (since HMAC only covers the body, which is unchanged) and will pass the attacker-chosen `shop` value straight into the handler as `WebhookMetadata#shop`: [4](#0-3) 

The documented usage pattern instructs handler authors to trust `data.shop` directly for tenant-scoped work (e.g. looking up the shop's session/store record and enqueuing per-shop jobs) without any additional binding step performed by the gem itself: [5](#0-4) 

This is the same root-cause shape as the Solidity report: a field that is *acted upon* (`shop` used to route/attribute the webhook to a tenant) is not part of the data that is *cryptographically verified* (only the body is HMAC-signed). The equality that should hold — `shop bound by HMAC == shop delivered to handler` — does not hold; the gem lets these two diverge.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an attacker who is a legitimate (if malicious) installer of the app on their own shop can forge webhook deliveries that appear to originate from any other shop, without needing the app's `api_secret_key`, an access token, or any privileged credential — they only need a body/HMAC pair legitimately issued to their own tenant. Downstream, if the host application uses `data.shop` (as documented) to attribute state changes, enqueue background jobs, or update per-shop records, this results in cross-tenant data corruption/spoofing — one tenant able to inject fabricated webhook payloads attributed to another tenant.

### Likelihood Explanation
High for any app that installs on more than one shop (the normal SaaS model) and follows the gem's own documented pattern of trusting `data.shop`. The only prerequisite is installing the app once as an ordinary merchant (a routine, unprivileged, self-service action), which is far short of the "privileged account / leaked credentials / TLS interception" exclusions in scope. No modification to `api_secret_key`, tokens, or TLS is required — this is purely a self-contained defect in `Request`/`Registry` within the gem.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-verified material, or otherwise independently authenticate the `shop-domain` header against a trusted, per-tenant identifier (e.g., verify it matches the shop associated with the stored access token/session before invoking the handler) instead of passing the raw header value through unauthenticated. At minimum, `Registry.process` should not present `request.shop` to handlers as if it were verified — the gem should document/enforce that shop must be cross-checked against a known/authorized shop for the app before being trusted for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own dev shop `attacker.myshopify.com`, completing OAuth normally (no elevated privileges required).
2. Shopify delivers a legitimate webhook to the app for `attacker.myshopify.com`; attacker captures the raw body and the `x-shopify-hmac-sha256` header value.
3. Attacker replays an HTTP POST to the app's webhook endpoint with the identical body/HMAC but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unmodified) body against the HMAC: [6](#0-5) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)`, and the host app performs tenant-scoped actions (per the documented pattern) attributing them to `victim.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
