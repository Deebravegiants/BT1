### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unsigned HTTP headers to dispatch the handler and identify the tenant. Because the signature never covers these header fields, any caller who can replay a body/HMAC pair Shopify generated for one webhook can attach a different `shop-domain`/`topic` header and have the app process it as if it belonged to another shop or topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and the accessors for `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` (the raw body): [3](#0-2) 

`Registry.process` accepts the request once the HMAC over the body checks out, then builds `WebhookMetadata` using `request.topic` and `request.shop` — both unsigned header values — and dispatches to the handler registered for that (unsigned) topic: [4](#0-3) 

The identity binding that should hold is: `shop/topic bound by the HMAC == shop/topic acted upon by the handler`. Here the HMAC binds only the body bytes, so this equality fails — the header-derived `shop`/`topic` used to identify the tenant and route to a handler is never actually authenticated. Any party capable of sending an HTTP POST to the app's webhook endpoint with a body that happens to match one for which they can obtain (or predict) a genuine Shopify-issued `(body, hmac)` pair (e.g., a body that is identical across shops/topics, such as `"{}"` or another minimal/templated payload obtained from webhooks delivered to the attacker's own installed shop) can substitute the `shopify-shop-domain` and `shopify-topic` headers to impersonate a different tenant or topic. The consuming application (per the documented usage pattern in `docs/usage/webhooks.md`) is expected to trust `data.shop` and `data.topic` as the source of truth for which merchant/event the webhook is about, so this directly enables cross-tenant confusion of webhook-driven business logic (e.g., `shop/redact`, `customers/data_request`, order/product mutation handlers) without ever possessing the app's `client_secret` or an access token.

### Impact Explanation
This qualifies as Critical/cross-tenant access: an unprivileged caller who merely has one legitimately-issued webhook (from their own, unprivileged shop install) can forge the shop identity attached to that payload and cause the host application to attribute/process the event as belonging to an arbitrary different `shop-domain`, breaking tenant isolation of a security-relevant control path in the gem's webhook subsystem.

### Likelihood Explanation
Exploitability depends on finding or engineering a body whose HMAC the attacker already possesses for a webhook they legitimately received (e.g., a webhook whose payload is fixed/templated or doesn't embed the shop domain, such as some `app/uninstalled`-style or filtered/fields-limited payloads configured via `add_registration(fields: ...)`), which is realistic given apps can register field-filtered subscriptions that reduce body variability. No possession of `api_secret_key` or an access token is required — only the ability to POST to the public webhook endpoint with attacker-controlled headers and a previously-observed valid `(body, hmac)` pair.

### Recommendation
Extend the webhook `to_signable_string`/signature verification (or a secondary binding step in `Registry.process`) to include the `shop-domain`, `topic`, `webhook_id`, and `api_version` header values, or otherwise cryptographically bind them to the payload before trusting them for dispatch and tenant identification — mirroring the pattern already used for `AuthQuery`, where `shop`/`host` are explicitly part of `to_signable_string`.

### Proof of Concept
1. Register the app for a topic with a small/templated body (e.g., register `add_registration` with `fields: [...]` producing a minimal, shop-agnostic JSON body), for tenant shop A which the attacker owns/controls a normal (unprivileged) install of.
2. Capture a genuine Shopify-delivered webhook: raw body `B` and header `x-shopify-hmac-sha256: H` (valid since Shopify signed `B` with the app's real secret).
3. Replay a POST to the app's webhook endpoint with the same body `B` and same `hmac` header `H`, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com` and/or `x-shopify-topic` to a different registered topic.
4. `Utils::HmacValidator.validate` succeeds because it only verifies `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), and `Registry.process` dispatches the handler using the attacker-supplied `shop`/`topic` headers (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process the event as if it came from `victim-shop.myshopify.com`.
