## Title
Malicious/blacklistable input token can permanently block RedeemEscrow settlement in the Intent Gateway - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
A user who places a cross-chain intent order can include a malicious (e.g. blacklistable, pausable, or hook-reverting) ERC-20 as one of several `order.inputs` alongside legitimate high-value tokens. Once a solver fills the order on the destination chain (delivering real output value to the user's beneficiary), settlement on the source chain requires releasing **all** escrowed input tokens to the solver in a single atomic loop. If any one of those tokens is engineered to always revert on transfer to the solver, the entire `onAccept`/`withdraw` call reverts, and — because delivery failures are silently swallowed and made retryable rather than causing partial settlement — the escrow (including the legitimate, valuable tokens bundled with the malicious one) can never be released to the solver. This is directly analogous to the ERC777-callback issue in the external report, where a hostile token embedded in a batch operation blocks an otherwise-legitimate settlement for every other party.

### Finding Description
`_withdraw` in `IntentsBase.sol` iterates over every escrowed token for an order commitment and performs a `safeTransfer` to the beneficiary for each one, all within a single function call: [1](#0-0) 

This is invoked from `ExtrinsicIntents`'s `onAccept` when a `RedeemEscrow`/`RefundEscrow` message is delivered, and from the equivalent Tron variant: [2](#0-1) 

There is no per-token isolation or try/catch around each `safeTransfer` — a single reverting token aborts the whole withdrawal, including transfers of otherwise-healthy tokens in the same order.

`_fillCrossChain` in `ExtrinsicIntents.sol` places no restriction on which ERC-20 the user may specify as an input asset; any address can be used as `order.inputs[i].token` when the order is placed via `placeOrder`/escrow accrual: [3](#0-2) 

Because `EvmHost.dispatchIncoming` uses a low-level `.call()` to invoke `onAccept` and, on failure, simply deletes the request receipt and returns without reverting the batch, the failed `RedeemEscrow` delivery is not lost — it becomes indefinitely retryable, but will deterministically fail forever if the malicious token always reverts on transfer: [4](#0-3) 

This "retryable forever, but never succeeds" behavior is exactly the effect of the ERC777 `tokensToSend`/callback-based DoS in the reference report: the malicious token can be made to revert deterministically for a specific target address (the solver) or under specific conditions, permanently blocking a settlement action that legitimately belongs to a third party (the filler), not the token holder causing the block.

### Impact Explanation
The solver/filler has already delivered real output value to the user's beneficiary on the destination chain in good faith (the fill is atomic and irreversible there). If the source-chain escrow release for that same order is blocked by one poisoned input token, the solver permanently loses the compensating escrowed assets — including any legitimate, valuable tokens (e.g. USDC) bundled in the same order alongside the malicious token — and the accumulated protocol/transaction fees tied to that commitment are frozen as well, since `finalize` fee payout occurs in the same `_withdraw` call. This is a permanent freezing of funds belonging to a party other than the one who chose the malicious token, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is high for a determined attacker: placing an order costs only the ordinary escrow amount and gas, and the attacker fully controls the malicious token's transfer logic (e.g. an address-conditional revert or a self-blacklisting token that blocks transfers to the specific solver address once triggered). No privileged role or governance action is required — any unprivileged order-placer can attempt this, and it only requires a solver to be willing to fill an order that includes an unfamiliar token, which is an ordinary occurrence in an open solver market.

### Recommendation
- Process each escrowed token transfer in `_withdraw` independently (e.g., low-level call plus try/catch or a per-token retry queue), so a single malformed/malicious token cannot block release of the other escrowed tokens or fees in the same order.
- Consider allow-listing or additional validation of input tokens accepted by `placeOrder`, or requiring solvers/relayers to pre-simulate fills against the exact input token set before committing.
- Add an owner/governance-gated recovery path (e.g. a `SweepDust`-style mechanism scoped to a specific order) that can force-release the non-malicious tokens of a stuck commitment without requiring the poisoned token's transfer to succeed.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer`/`transferFrom` always reverts when the recipient equals a solver address it will target (or reverts unconditionally after a delay/trigger the attacker controls).
2. Attacker calls `placeOrder` on the source chain with `order.inputs = [ {token: USDC, amount: 1000e6}, {token: EvilToken, amount: 1} ]`, escrowing both into the gateway per `evm/src/apps/IntentGatewayV2.sol` (lines 361-373 above).
3. A solver, unaware of `EvilToken`'s conditional revert, calls `_fillCrossChain` on the destination chain, delivering the required output tokens to the attacker's beneficiary, and dispatches the `RedeemEscrow` message (`evm/src/apps/intentsv2/ExtrinsicIntents.sol` lines 164-220).
4. When the `RedeemEscrow` POST request is delivered on the source chain, `onAccept` calls `_withdraw`, which attempts `safeTransfer(solver, 1000e6 USDC)` then `safeTransfer(solver, 1 EvilToken)`; the `EvilToken` transfer reverts, causing the whole `_withdraw` — and thus the whole `onAccept` — to revert.
5. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and leaves the message retryable; every retry hits the same deterministic revert, so the solver never receives the escrowed USDC or fees, despite having already paid out on the destination chain.

Note: I could not fully verify whether any governance/administrative recovery function exists elsewhere in the codebase specifically to rescue a stuck order commitment (my search for `SweepDust`/rescue-style functions in `IntentsBase.sol`/`ExtrinsicIntents.sol` found matches but I was unable to read their full implementation before the tool budget ran out); if such a per-order rescue path exists and can bypass the poisoned token, it would reduce — but not eliminate — the severity of this finding.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
