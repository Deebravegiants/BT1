### Title
Overpaid native-token fees in `EvmHost.dispatch()`/`fundRequest()` get stranded in the Host contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()` and `EvmHost.fundRequest()` forward the entire `msg.value` to `swapETHForExactTokens`, requesting only an exact output of `post.fee`/`amount` in `feeToken`. Neither function captures or refunds the ETH change that a standard `UniswapV2Router02.swapETHForExactTokens` sends back when `msg.value` exceeds the ETH actually required for the exact-output swap. This is the same "mismatch between `msg.value` and the required amount causes stuck funds" bug class described in the reference report, but here it lives in `EvmHost`, which every `IApp` (including `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) calls into for dispatch fee payment.

### Finding Description
`dispatch(DispatchPost)` unconditionally swaps the full `msg.value`: [1](#0-0) 

and `fundRequest()` does the same pattern: [2](#0-1) 

`swapETHForExactTokens(amountOut, path, to, deadline)` on a canonical UniswapV2Router02 only consumes as much ETH as needed to produce exactly `amountOut` of `feeToken`, and refunds any leftover ETH back to `msg.sender` of the swap call — which here is `EvmHost` itself, not the original caller of `dispatch()`/`fundRequest()`. `EvmHost` has a `receive()` function (confirmed present) so this refund does not revert; it simply accumulates as native-token balance on `EvmHost`. Neither `dispatch()` nor `fundRequest()` captures the swap's return value or contains any logic to forward the change back to `_msgSender()`/`post.payer`. Compare this to `IntentGatewayV2.placeOrder()`, which explicitly tracks `msgValue` and refunds any unspent native token at the end: [3](#0-2) 

`EvmHost` has no equivalent refund step. Any caller who overestimates the native-token amount needed to cover `post.fee` (e.g. due to slippage buffers, stale quotes, or simple over-payment) will have the excess silently retained by `EvmHost`.

Note: the `GnosisUniswapV2Wrapper` variant of the router (used in the Gnosis Chain deployment) behaves even more aggressively — it wraps the *entire* `msg.value` into WETH and forwards *all* of it to `msg.sender` (i.e., `EvmHost`) regardless of `amountOut`, meaning 100% of any overpayment (not just the swap-computed change) ends up custodied by `EvmHost` as `feeToken`/WETH balance: [4](#0-3) 

### Impact Explanation
Excess native-token funds sent by any user dispatching a cross-chain request (directly or via an `IApp` such as `IntentGatewayV2`/`HyperFungibleToken`) become commingled with `EvmHost`'s own balance with no per-payer accounting. There is no mechanism in `dispatch()`/`fundRequest()` to attribute or later reclaim this specific overpayment to the paying account; recovery, if any, would require a privileged host-manager/governance action that acts on the whole balance rather than restoring funds to the specific depositor — the same "all-or-nothing, no fund identification" problem flagged in the source report. This constitutes a permanent freezing of user funds under normal usage (no malicious actor required — any legitimate overestimate of the native fee amount triggers it).

### Likelihood Explanation
Because `feeToken()` amounts and ETH/feeToken exchange rates fluctuate, and dApps/SDKs must estimate `msg.value` client-side ahead of execution (with slippage buffers commonly added to avoid `dispatch` reverting due to price movement), overpayment is a realistic and even routine occurrence for any caller using the native-token payment path documented for `dispatch()`/`fundRequest()`.

### Recommendation
- Capture the return value of `swapETHForExactTokens` (the array of amounts, where `amounts[0]` is the actual ETH consumed) and refund `msg.value - amounts[0]` back to `_msgSender()` (or `post.payer`) in both `dispatch()` and `fundRequest()`, mirroring the refund pattern already implemented in `IntentGatewayV2.placeOrder()`.
- For router adapters like `GnosisUniswapV2Wrapper` that wrap the full `msg.value`, adjust the wrapper to only consume `amountOut` worth of native token and refund the remainder as native ETH to the caller, rather than forwarding the entire `msg.value` as WETH.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: X}(post)` where `post.fee` requires only `Y < X` ETH-equivalent via the configured Uniswap V2 router to obtain `post.fee` `feeToken`.
2. `swapETHForExactTokens{value: X}(post.fee, path, address(this), deadline)` executes; the router consumes `Y` ETH, mints `post.fee` `feeToken` to `EvmHost`, and refunds `X - Y` ETH to `msg.sender`, i.e., `EvmHost`.
3. `EvmHost.dispatch()` does not read the swap's return value nor forward any ETH back to the original caller; the `X - Y` ETH remains part of `EvmHost`'s balance permanently, with no record tying it back to the original caller.
4. Repeating this from any `IApp` (e.g. `IntentGatewayV2._post`, `HyperFungibleToken.send`) that forwards leftover `msg.value` into `EvmHost.dispatch{value: msgValue}` compounds the stuck balance across many unrelated senders with no accounting distinguishing whose funds are trapped.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
    }
