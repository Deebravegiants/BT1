### Title
`fund_message` relies on caller discipline instead of an enforced check to prevent permanently lost relayer-fee top-ups - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::fund_message` is a signed, permissionless extrinsic that lets any user top up the relayer fee for an in-flight ISMP request or response. Its NatSpec explicitly warns "Should not be called on a message that has been completed (delivered or timed-out) as those funds will be lost forever," but the function only guards against a *missing* storage entry — it never distinguishes "still pending" from "completed but not yet purged," or from a race where completion and funding land in the same block. This mirrors the `InvestmentPoolCore::setInflowOutflowPool` pattern in the external report: a critical ordering/state invariant is documented in a comment rather than enforced in code. [1](#0-0) 

### Finding Description
`fund_message` looks up the commitment's metadata, and only reverts with `MessageNotFound` if the entry is entirely absent from `RequestCommitments`/`ResponseCommitments`: [2](#0-1) 

If the entry still exists in storage — which is possible whenever the pallet's cleanup of a completed message (via `delete_request_commitment`/`delete_response_receipt` in `modules/pallets/ismp/src/host.rs`) has not yet run relative to the block a user submits `fund_message`, or whenever a response has been processed without a corresponding removal of the funded commitment — the call proceeds to transfer the caller's tokens into the protocol's relayer-fee account and simply bumps `metadata.fee.fee`: [3](#0-2) [4](#0-3) 

Because there is no relayer left to claim the fee (the message is already delivered/timed-out) and no automatic refund path back to the caller for this scenario, the additional funds are permanently stranded, exactly as the NatSpec predicts. The invariant "never fund an already-completed message" exists only as documentation, not as an enforced state flag (e.g., a `Delivered`/`Completed` marker checked explicitly, independent of whether the commitment happens to still be present in storage).

This is directly analogous to the reported bug class: a security-critical sequencing requirement ("call X before Y, or funds are lost") is captured only in a comment, with no code-level guard ensuring the precondition actually holds at call time.

### Impact Explanation
Any ordinary signed account (not an admin) that submits `fund_message` at the "wrong" moment — e.g., against a message that is being delivered/timed-out in the same or an earlier untracked state — permanently loses the tokens it transfers into `RELAYER_FEE_ACCOUNT`. This is an unrecoverable freeze of user funds triggered from a single ordinary extrinsic, which meets the required "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is higher than the original admin-only report because `fund_message` is callable by any signed account without special privileges — it doesn't require a malicious or compromised admin, only unfortunate/adversarial timing (e.g., a user or bot racing a relayer's delivery, or being front-run). The report's own reasoning ("easily forgotten," "error-prone flow relying on caller discipline") applies with equal or greater force here since the caller is an untrusted, permissionless party rather than a trusted operator.

### Recommendation
Enforce the "not completed" precondition explicitly rather than relying on storage-entry presence as a proxy: introduce and check a dedicated completion flag (e.g., `Responded`/timed-out marker) atomically with the fund transfer, or make cleanup and the fund-eligibility check happen in a way that guarantees no window exists where a stale-but-present commitment can still be funded after completion. Alternatively, mirror `EvmHost::fundRequest`'s explicit design choice (treat late funding as an intentional "donation to protocol") but state and enforce this consistently, or add a refund path for extra fees deposited against a message that turns out to be already completed.

### Proof of Concept
1. A relayer submits `handle_unsigned` delivering (or timing out) a request/response whose commitment metadata removal (`delete_request_commitment`) has not yet executed relative to a pending `fund_message` extrinsic from another user in the transaction pool for the same block/mempool window.
2. The user's `fund_message(FundMessageParams { commitment, amount })` executes: `RequestCommitments::<T>::get(commitment)` (or `ResponseCommitments`) still returns `Some(metadata)` because the entry has not yet been purged.
3. `T::Currency::transfer` moves `amount` from the user to `RELAYER_FEE_ACCOUNT`, and `metadata.fee.fee` is bumped and re-inserted.
4. Because the message is already completed, no relayer will ever claim this incremented fee, and there is no code path to refund it to the user — the funds are permanently lost, as the NatSpec itself predicts but does not prevent.

*Note: full certainty on every code path that deletes `RequestCommitments`/`ResponseCommitments` (particularly for GET responses and post-response POST request cleanup) could not be exhaustively traced within the available tool budget; the core issue — that the "don't fund a completed message" invariant is documented but not affirmatively enforced by a completion flag — is confirmed directly from `fund_message`'s implementation.*

		/// Add more funds to a message (request or response) to be used for delivery and execution.
		///
		/// Should not be called on a message that has been completed (delivered or timed-out) as
		/// those funds will be lost forever.
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().writes(5))]
		#[pallet::call_index(4)]
		pub fn fund_message(
			origin: OriginFor<T>,
			message: FundMessageParams<T::Balance>,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;

			let metadata = match message.commitment {
				MessageCommitment::Request(commitment) => RequestCommitments::<T>::get(commitment),
				MessageCommitment::Response(commitment) =>
					ResponseCommitments::<T>::get(commitment),
			};

			let Some(mut metadata) = metadata else {
				return Err(Error::<T>::MessageNotFound.into());
			};

			T::Currency::transfer(
				&account,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				message.amount,
				Preservation::Expendable,
			)?;

			match message.commitment {
				MessageCommitment::Request(commiment) => {
					metadata.fee.fee += message.amount;
					RequestCommitments::<T>::insert(commiment, metadata);
				},
				MessageCommitment::Response(commiment) => {
					metadata.fee.fee += message.amount;
					ResponseCommitments::<T>::insert(commiment, metadata);
				},
			};

			Ok(())
		}
