### Title
Cross-Tenant Webhook Confusion — Shop Identity Not Bound by HMAC in `Webhooks::Request` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature over the raw request body only, while the `shop` value it exposes to the webhook handler is read from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header. This breaks the identity binding `hmac-authenticated-bytes == bytes-that-determine-tenant`, letting an attacker replay a validly-signed webhook body under a different, attacker-chosen `shop` value.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `hmac` reader likewise verifies only the body via `HmacValidator.validate`, which calls `verifiable_query.to_signable_string`: [2](#0-1) [3](#0-2) 

Meanwhile `shop` (the tenant identifier) is parsed straight from the request headers, which are never included in the signed payload: [4](#0-3) 

`Registry.process` validates the HMAC (which only covers the body) and then forwards `request.shop` to the handler as the trusted tenant identifier, without any additional cross-check that this shop is the one the payload actually originated from: [5](#0-4) 

Because the header carrying the shop identity is not part of the signable string, `hmac_of(body) == hmac_of(body)` holds true regardless of which `shop-domain` header value accompanies it. An attacker who intercepts, or otherwise obtains, one legitimately-signed webhook delivery (body B, valid hmac H, originally for shop A) can resend the exact same `(B, H)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with shop B's domain. `HmacValidator.validate` still succeeds (it never inspected the shop header), and `Registry.process` dispatches `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed_body_of_B, ...)` to the app's handler — i.e., data legitimately generated for tenant A is now attributed to and processed under tenant B's identity.

This is the same unit/identity-mismatch bug class as the reference report: a verification check (HMAC) is computed over one set of bytes while a security-relevant decision (which tenant owns this data) is made from a different, unverified set of bytes.

### Impact Explanation
This enables cross-tenant data confusion for any host application that trusts `WebhookMetadata#shop` from this gem as the source of truth for which merchant a webhook payload belongs to — e.g. writing order/customer data into the wrong tenant's database row, or triggering shop-B-scoped side effects using shop-A's data. This matches the "Cross-tenant access" Critical impact category, since the gem itself supplies no binding between the authenticated payload and the claimed tenant.

### Likelihood Explanation
Requires the attacker to obtain one legitimate `(body, hmac)` pair for any shop (e.g., via network capture, a compromised intermediary, or logging leakage of webhook deliveries) and the ability to POST to the app's webhook endpoint with a modified `shopify-shop-domain` header — no `api_secret_key`, access token, or privileged account is needed. This is a realistic unprivileged-attacker path once one webhook delivery has been observed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`/`api_version`) header values in the signed data compared against the HMAC, or independently verify that `request.shop` matches a shop this app has an active session/installation for before trusting it as the tenant key. At minimum, `to_signable_string` should incorporate the shop-domain header so a body/hmac pair cannot be replayed under a different tenant identity.

### Proof of Concept
1. Capture a legitimate webhook delivery to the app: body `B`, header `shopify-hmac-sha256: H` (valid for secret `S` and body `B`), header `shopify-shop-domain: shop-a.myshopify.com`.
2. Resend a POST to the app's webhook endpoint with the identical body `B` and identical `shopify-hmac-sha256: H`, but change `shopify-shop-domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= @raw_body = B`) and succeeds, since the header change did not alter `B`. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed_body_of_B, ...)`, so shop A's payload is processed under shop B's identity. [7](#0-6)
