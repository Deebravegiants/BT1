# Custody Analog Found

## Title
Bonding-curve `graduate()` permanently strands 10% of pooled APT and FA reserves in the `LiquidityPair` object with no reclaim path - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move`)

## Summary
The external report identifies a class of bug where an amount calculated by truncating/deriving a portion of a paired-asset balance does not match the actual custodied balance, leaving value effectively stuck. The Aptos-native analog is in `bonding_curve_launchpad::liquidity_pairs::graduate()`, which hardcodes a 90%/10% split when migrating a bonding-curve pool's real APT and FA reserves to an external DEX pool. Only 90% of each asset is ever withdrawn from the `LiquidityPair` object's custody (`fa_store` and the object's own APT coin balance); the remaining 10% of both assets is left behind. Because `graduate()` unconditionally sets `is_enabled = false` and no other function in the module can ever regenerate access to that residual value (the only entry points into the object's `extend_ref`/`fa_store` are gated by `is_enabled`), that 10% of both assets is permanently and irrecoverably locked on every single graduation event.

## Finding Description
`swap_apt_to_fa()` triggers `graduate()` once `apt_updated_reserves > APT_LIQUIDITY_THRESHOLD`: [1](#0-0) 

`graduate()` disables the pair (`is_enabled = false`) and then migrates liquidity to the external DEX by withdrawing only 90% of the tracked reserves: [2](#0-1) 

`add_liquidity_coin_entry_transfer_ref` then withdraws exactly `optimal_amount_1`/`optimal_amount_2` — i.e., the 90% figures — from the liquidity pair's real custody (the object's own APT coin balance via `coin::withdraw`, and the object-owned `fa_store` via `fungible_asset::withdraw_with_ref`), and deposits them into the new DEX pool: [3](#0-2) 

The remaining 10% of both real APT (sitting as a coin balance on the `liquidity_pair` object's address, since only `optimal_amount_1` is withdrawn via `coin::withdraw`) and real FA (sitting in `liquidity_pair.fa_store`, since only `optimal_amount_2` is withdrawn via `withdraw_with_ref`) is never moved anywhere. The only two functions capable of generating a signer for the `LiquidityPair` object or withdrawing from `fa_store` — `swap_fa_to_apt` and `swap_apt_to_fa` — both begin with: [4](#0-3) 
and abort with `ELIQUIDITY_PAIR_DISABLED` once `is_enabled` is false, which `graduate()` sets unconditionally and irreversibly (no "un-graduate"/reactivate function exists anywhere in the module). There is also no admin/sweep function anywhere in `liquidity_pairs.move` that can access `liquidity_pair.extend_ref` or `liquidity_pair.fa_store` outside of the swap/graduate paths.

The custody invariant broken here is: value held in an object-owned store (fungible-asset store and object-owned coin balance) must remain recoverable through some authorized path; a withdrawal/migration function must not architecturally partition custody such that a fraction of the balance becomes permanently unreachable once the object's operational flag is toggled off.

## Impact Explanation
This meets the "Permanent lock or non-recoverable loss of object-held...value" custody-impact criterion. Every single bonding-curve token that reaches the graduation threshold (`APT_LIQUIDITY_THRESHOLD = 600_000_000_000` octas, i.e. 6,000 APT) permanently strands roughly 10% of the real APT (at least ~550-600 APT scale, growing with reserve size at the moment of the triggering swap) and 10% of the real FA reserves inside the now-inert `LiquidityPair` object. This is a systemic, no-privilege-required, deterministic loss of custodied assets on the mainnet-relevant migration path (bonding-curve-to-DEX graduation), not a one-off edge case. Given that this is the core migration mechanism of the launchpad (every graduation loses funds), the aggregate value lost across all launches could be substantial.

## Likelihood Explanation
This triggers automatically and deterministically on every graduation — there is no attacker action, race condition, or adversarial state required. Any legitimate swap that pushes `apt_updated_reserves` above the threshold invokes `graduate()`, which always leaves the 10% remainder unreachable. Likelihood is effectively certain (100%) for any bonding-curve pair that reaches graduation.

## Recommendation
- In `graduate()`, withdraw the **full** real APT and FA balances held by the `LiquidityPair` object (not a hardcoded 90% cut) before disabling the pair, or explicitly compute and transfer the residual (`10%`) to a recoverable destination (e.g., the DEX pool, the FA creator, or a withdrawal address), mirroring how `vesting::distribute` explicitly forwards leftover dust rather than abandoning it.
- Alternatively, add an admin/creator-gated `sweep_after_graduation` function that can generate the object's signer (via the still-existing `extend_ref`) after `is_enabled == false` and drain any residual APT/FA balances to a designated recipient.
- Add an invariant/test asserting that after `graduate()` completes, both the object's native APT balance and `fa_store` balance are zero (no dust left behind), which would have caught this issue.

## Proof of Concept
1. A bonding-curve `LiquidityPair` accrues real APT and FA via `swap_apt_to_fa` / `swap_fa_to_apt` until `apt_updated_reserves` exceeds `APT_LIQUIDITY_THRESHOLD` (`liquidity_pairs.move:322`).
2. `graduate()` is invoked automatically, computing `amount_1_desired = apt_updated_reserves - apt_updated_reserves/10` and `amount_2_desired = fa_updated_reserves - fa_updated_reserves/10` (`liquidity_pairs.move:351-352`), then calling `add_liquidity_coin_entry_transfer_ref`, which withdraws exactly those 90% amounts via `coin::withdraw` and `fungible_asset::withdraw_with_ref` (`liquidity_pairs.move:404-409`) and deposits them into the new DEX pool.
3. `liquidity_pair.is_enabled` is set to `false` at the top of `graduate()` (`liquidity_pairs.move:340`), permanently disabling `swap_apt_to_fa`/`swap_fa_to_apt` (`liquidity_pairs.move:223`, `281`) — the only functions that can generate the object's signer or touch `fa_store`.
4. The remaining 10% real APT (held as a coin balance at the `LiquidityPair` object's address) and 10% real FA (held in `liquidity_pair.fa_store`) are never withdrawn or transferred anywhere, and no other function in the module (or any caller module such as `bonding_curve_launchpad`) can access them going forward — the value is permanently locked.

    fun add_liquidity_coin_entry_transfer_ref<CoinType>(
        transfer_ref: &TransferRef,
        lp: &signer,
        fa_store: Object<FungibleStore>,
        token_2: Object<Metadata>,
        is_stable: bool,
        amount_1_desired: u64,
        amount_2_desired: u64,
        amount_1_min: u64,
        amount_2_min: u64,
    ) {
        // Wrap APT into a FA. Then, determine the optimal amounts for providing liquidity to the given FA - APT pair.
        let token_1 = coin_wrapper::get_wrapper<CoinType>();
        let (optimal_amount_1, optimal_amount_2, _) = router::optimal_liquidity_amounts(
            token_1,
            token_2,
            is_stable,
            amount_1_desired,
            amount_2_desired,
            amount_1_min,
            amount_2_min,
        );
        // Retrieve the APT and FA from the liquidity provider.
        // `transfer_ref` is used to avoid circular dependency during graduation. A normal transfer would require
        // visiting `bonding_curve_launchpad` to execute the custom withdraw logic. `transfer_ref` bypasses the need to
        // return to `bonding_curve_launchpad` by not executing the custom withdraw logic.
        let optimal_1 = coin::withdraw<CoinType>(lp, optimal_amount_1);
        let optimal_2 = fungible_asset::withdraw_with_ref(
            transfer_ref,
            fa_store,
            optimal_amount_2
        );
        // Place the APT and FA into the liquidity pair.
        router::add_liquidity_coin<CoinType>(lp, optimal_1, optimal_2, is_stable);
    }
