### Title
Creator fee claims permanently frozen if creator address is blacklisted by USDC - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` pays a creator's accrued USDC balance directly to `msg.sender` via `safeTransfer`. If USDC ever puts that specific creator address on its blacklist (e.g. via Circle's `notBlacklisted` modifier), every call to `claim()` reverts, and there is no other function in `FeeVault` or `Bonding` that can redirect or rescue that creator's already-accrued balance. This mirrors the reported `Stream.cancel()` issue: a hard-coded USDC recipient that can become non-transferable, permanently freezing funds with no fallback path.

### Finding Description
`FeeVault.claim()` reads and zeroes `creatorBalance[msg.sender]`, then unconditionally calls `$.usdc.safeTransfer(msg.sender, amount)`: [1](#0-0) 

Because `safeTransfer` reverts the entire transaction on failure (per `SafeERC20`), a USDC blacklist hit on `msg.sender` reverts `claim()` — including the state writes that zeroed the balance — so the accrued `creatorBalance[msg.sender]` is left intact but permanently unclaimable through this path.

Critically, the recipient in `claim()` is hard-wired to `msg.sender`; there is no parameter to specify an alternate payout address. `Bonding.transferCreator(tokenAddress, newCreator)` only updates `TokenInfo.creator` for *future* fee attribution on that specific token going forward: [2](#0-1) 

It does **not** touch `FeeVault`'s `creatorBalance` mapping, which is keyed globally by creator address across every token that creator has launched, and is only mutated by `accrue` (on deposit) and `claim` (on payout): [3](#0-2) 

So even after a creator calls `transferCreator` to move future attribution to a fresh address, any USDC already sitting in `creatorBalance[oldCreator]` from prior trading remains keyed to the blacklisted address and stays stuck there. `FeeVault` has no owner-controlled rescue or force-redirect function for creator balances — the only owner hooks are `addDepositor`, `removeDepositor`, and `setFeeTo`, none of which touch `creatorBalance`.

### Impact Explanation
Funds legitimately earned by a token creator become permanently locked in `FeeVault` with no code path to retrieve them — the exact "permanent freezing of funds" class called out in scope. This is entirely plausible for real-world USDC: Circle blacklists many addresses (sanctions, compromised addresses, mixer-tainted addresses), and a token creator address is fully attacker/environment-controlled (any EOA or contract can be a creator via `Bonding.launch`/`Zap.createToken`), so this is reachable without any privileged action.

### Likelihood Explanation
Any unprivileged address can become a `creator` simply by calling `Zap.createToken`. Fees accrue automatically on every buy/sell of that creator's token via `Zap` → `FeeVault.accrue`. The only external trigger needed is the USDC issuer blacklisting that specific address — an event outside the protocol's control but well precedented for USDC, and once it occurs there is no recovery mechanism in the contracts themselves.

### Recommendation
Add a pull-based or redirectable claim path, e.g.:
- Let a blacklisted creator (or, as a fallback, `Bonding.transferCreator`) migrate/merge their `creatorBalance` to a new, non-blacklisted address in `FeeVault`, or
- Wrap the `claim()` transfer in a non-reverting pattern (`trySafeTransfer`) so a failed transfer doesn't block the accrual bookkeeping, combined with an admin- or self-service "claim-to(address)" function that lets the creator designate an alternate payout address.

### Proof of Concept
1. Attacker/creator `C` calls `Zap.createToken` to launch a token and becomes `TokenInfo.creator`.
2. Trading occurs; `Zap` calls `FeeVault.accrue(token, C, creatorAmount, protocolAmount, isBuy)` repeatedly, growing `creatorBalance[C]`.
3. USDC's issuer blacklists address `C` (independent real-world event).
4. `C` calls `FeeVault.claim()`; `$.usdc.safeTransfer(C, amount)` reverts because USDC's `transfer` enforces `notBlacklisted(to)`, so the whole `claim()` transaction reverts.
5. `C` calls `Bonding.transferCreator(token, newAddress)` to redirect future fees — this only updates `TokenInfo.creator`, leaving `creatorBalance[C]` in `FeeVault` untouched and still only claimable by the blacklisted `C`.
6. `creatorBalance[C]`'s USDC is now permanently unclaimable through any function in the contracts.

        address token,

        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
