I have enough evidence to confirm the vulnerability. The `Registry.process` flow validates HMAC only over `raw_body` (`Request#to_signable_string` returns `@raw_body` only) while `Registry.process` passes `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all pulled from unauthenticated HTTP headers via `shopify_header` — into the `WebhookMetadata` object delivered to the app's handler.### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, but then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values pulled from unauthenticated HTTP headers when constructing the `WebhookMetadata` handed to the host app's handler. The HMAC binding covers only the body bytes; the shop-identity field the handler acts on is never part of what was verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from raw HTTP headers via `shopify_header`, none of which participate in the HMAC computation: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, i.e. only the raw body is authenticated: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated header-derived `shop` (and other fields) into `WebhookMetadata`, which is delivered to the app's handler as the trusted webhook identity: [5](#0-4) [6](#0-5) 

The binding that should hold is: `bytes_verified_by_HMAC == bytes_acted_on_by_handler(shop, topic, webhook_id)`. In this implementation that equality is broken — `bytes_verified_by_HMAC = raw_body` while `bytes_acted_on = raw_body ∪ {shop-domain header, topic header, webhook-id header, api-version header}`.

Because Shopify signs webhook requests using the app's single `client_secret` (shared across every merchant shop that installs the app), any shop that has installed the app can capture one of its own genuinely-signed webhook deliveries (valid `raw_body` + valid HMAC) and replay that identical body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header with a different, victim shop's domain. `HmacValidator.validate` still returns `true` because the body/HMAC pair it checks is untouched, and `Registry.process` will happily invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem cannot distinguish "webhook genuinely sent by Shopify for shop X" from "attacker-supplied header claiming shop X, backed only by a signature that was actually computed for a different shop's payload." Any downstream logic in the host app that trusts `WebhookMetadata#shop` (e.g., updating shop-scoped records, redact/compliance flows, order/customer sync) can be misattributed to or triggered against a shop the requester does not control, i.e., cross-tenant access driven entirely by data this gem asserts is authenticated. This matches the Critical "cross-tenant access" impact category, since the compromise is achieved purely with a merchant-controlled shop's own credentials (no access token, `client_secret`, or admin access to the victim is required).

### Likelihood Explanation
Requires only: (1) the attacker's own shop having the app installed (an ordinary, unprivileged action any merchant can take), (2) triggering any webhook topic on their own shop to obtain one valid raw-body+HMAC pair, and (3) sending an HTTP POST to the app's webhook endpoint with the captured body/HMAC and a substituted `shop-domain` (or other) header. No secrets, TLS interception, or privileged access are needed — the attacker only ever uses material legitimately available to them as an app installer. This is fully within an attacker's control and does not depend on the host app violating this gem's documented contract; it results directly from `Registry.process`/`Request` trusting header fields that `HmacValidator` never authenticates.

### Recommendation
Bind the shop identity (and other security-relevant metadata such as topic/webhook_id) into the HMAC-verified surface, or otherwise cryptographically tie them to the verified body — for example by including the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values in `to_signable_string`, or by requiring the caller to separately confirm that the deserialized body's shop-scoped payload/context matches the header-derived `shop` before dispatch. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be trusted as tenant identifiers without additional application-level verification (e.g., cross-checking against a known/expected shop for the installation, or validating that the `body`'s own shop-scoped identifiers match the header).

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":123,"foo":"bar"}'

# 1. Attacker's own shop ("attacker-shop.myshopify.com") legitimately receives
#    this webhook from Shopify, with a correctly computed HMAC over `body`.
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
hmac_b64 = Base64.encode64(hmac_digest)

# 2. Attacker replays the SAME body/HMAC pair to the app's webhook endpoint,
#    but swaps the shop-domain header to the victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# HmacValidator only checks `body`, which is untouched and valid -> passes.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will now invoke the handler with shop: "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
```
The handler receives `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the HMAC was only ever computed for the attacker's own shop's payload, confirming the shop field is not bound to the HMAC-verified bytes.
