### Title
Cross-Tenant Webhook Spoofing via Unauthenticated `shop-domain`/`topic` Headers Not Bound by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook HMAC validation in this gem only covers the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values—used downstream to attribute and route the webhook to a specific merchant—are read directly from unauthenticated HTTP headers. This breaks the identity binding: `shop` (the tenant identifier the handler trusts) ≠ `shop` (the tenant actually bound by the cryptographic signature).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `#shop`, `#topic`, and `#webhook_id` are all pulled straight from HTTP headers, none of which participate in the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e., the raw body) using the app's single, shop-independent `api_secret_key`: [3](#0-2) 

`Registry.process` gates handling on this HMAC check, then immediately trusts `request.shop` and `request.topic` as the identity/routing fields passed into the handler: [4](#0-3) 

This is structurally the same bug class as the reference report: a critical decision (there, the deposit-limit check; here, the tenant/topic attribution) is made using data that is not covered by the guarding check (there, `totalDifferentDeposit` bypassed by early return; here, `shop`/`topic` bypassed by the HMAC only covering the body). Because `api_secret_key` is shared by the app across **all** installed shops (it is not per-shop), a party who is an ordinary, unprivileged merchant of the same app can:
1. Trigger a genuine webhook to their own shop (fully within their privileges, e.g., placing an order in their own store), capturing a valid `(raw_body, hmac)` pair.
2. Replay that exact body and HMAC to the app's public webhook endpoint, but with the `shopify-shop-domain` (and optionally `shopify-topic`) header changed to a victim shop's domain.
3. `HmacValidator.validate` still returns `true` because the body and secret are unchanged — the header-derived `shop` was never part of the signed material.
4. The registered handler executes with `WebhookMetadata` claiming attribution to the victim shop, causing the host application to act on (store, process, or trigger side effects for) data misattributed to a different tenant.

### Impact Explanation
This crosses a tenant boundary using only an unprivileged merchant's own legitimate webhook traffic and no possession of `api_secret_key`, access tokens, or any privileged credential — matching the "Critical: cross-tenant access" impact category. The consequence depends on how the host app's handler uses `shop`/`topic` (e.g., persisting orders/customers keyed by the spoofed shop, invoking `shop/redact` or `customers/data_request` mandatory handlers against a victim shop, or corrupting per-shop caches/state), but the gem itself provides no binding to prevent it.

### Likelihood Explanation
Likelihood is high for any app using this gem's `Webhooks::Registry`/`Request` as documented: the webhook endpoint must be internet-reachable (that's the entire point of receiving Shopify webhooks), header spoofing on an HTTP POST requires no special access, and the attacker only needs to be a legitimate merchant of the same multi-tenant app to obtain one valid `(body, hmac)` pair from their own store's activity.

### Recommendation
Bind the identity fields into the HMAC-verified material, or otherwise independently verify `shop` before trusting it: e.g., include `shop-domain`/`topic`/`webhook-id` headers in the signed string (`to_signable_string`), or require that the resolved `shop` correspond to a session/shop already known to the host app for this app installation, rejecting requests where the header-derived shop cannot be corroborated.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (both under the same app, sharing one `api_secret_key`).
2. As the (unprivileged) owner of `shop-a`, trigger any subscribed webhook topic (e.g. `orders/create`) by placing an order in your own store; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent to your endpoint.
3. Replay that exact body + HMAC header to the same webhook endpoint, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (the victim).
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the (unmodified) body against the (shared) secret.
5. The topic handler runs with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ...)`, causing the host app to process attacker-supplied data as if it originated from `shop-b`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
