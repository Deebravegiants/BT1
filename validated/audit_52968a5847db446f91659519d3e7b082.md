### Title
Missing pre/post balance check on token escrow allows fee-on-transfer tokens to under-collateralize order accounting - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` credits the internal `_orders` escrow ledger with the user-*stated* input amount (minus protocol fee) instead of the amount actually received by the contract, unlike the canonical EVM `IntentGatewayV2.sol`, which explicitly measures the balance delta around each `safeTransferFrom` to protect against fee-on-transfer tokens.

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract pulls tokens with `safeTransferFrom` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from the caller-supplied `order.inputs[i].amount` (minus the protocol fee), never from an observed balance change: [1](#0-0) 

This contrasts with the fixed logic in the canonical `evm/src/apps/IntentGatewayV2.sol`, which snapshots `balanceOf` before and after the transfer and mutates `order.inputs[i].amount` to the actual received amount before computing the commitment and crediting escrow: [2](#0-1) 

and this behavior is explicitly asserted by the project's own fee-on-transfer regression test: [3](#0-2) 

Even the predispatch branch of the Tron contract at least checks `balance < requiredAmount` against the dispatcher's actual token balance before sweeping: [4](#0-3) 

but the plain (non-predispatch) branch — the common path most callers use — has no such check at all. Any ERC20 with a transfer fee, rebasing behavior, or other transfer-time deduction will cause `_orders[commitment][token]` to record more tokens than the contract actually holds for that order.

This ledger value is later relied upon during cancellation and cross-chain settlement: `cancelOrder` reads `_orders[commitment][token]` to validate order existence and constructs a `WithdrawalRequest` carrying `order.inputs` (the full, unreduced amounts) which is passed to `withdraw()` on `onAccept`/local cancel paths: [5](#0-4) [6](#0-5) 

Since the escrow bookkeeping is inflated relative to the contract's real token balance for the affected token, a refund/redeem/settlement attempt for that order (or a subsequent order sharing the same token) can end up short of funds — the contract's accounting promises more of a given token than it physically custodies.

### Impact Explanation
Using a fee-on-transfer (or otherwise transfer-deducting) token as an order input causes the escrow ledger to overstate the gateway's real balance for that token. This is a direct accounting/solvency defect: subsequent withdrawals, refunds, or fills relying on `_orders[commitment][token]` can attempt to pay out more than the contract holds, which can either (a) cause reverts that permanently strand a legitimate user's order/funds, or (b) drain real balances belonging to other unrelated orders denominated in the same token once several such shortfalls accumulate. This matches "permanent freezing of funds" / unbacked accounting criteria for a valid analog.

### Likelihood Explanation
Likelihood is limited by the requirement that a solver, user, or attacker chooses to submit an order using a fee-on-transfer/deflationary ERC20 as the input token — a config any unprivileged caller of `placeOrder` fully controls, since `order.inputs[i].token` is caller-supplied. No special privilege is needed; only the token itself must have transfer-time deductions, which is common in the wild (e.g., certain reflection or tax tokens).

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: in the non-predispatch branch, snapshot `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom`, use the actual delta to compute `order.inputs[i].amount` (and thus `reducedInputs[i].amount`) before computing the commitment hash and crediting `_orders`, ensuring escrow accounting always reflects tokens the contract actually holds.

### Proof of Concept
1. Attacker deploys/uses an ERC20 with e.g. a 5% transfer fee (`FeeOnTransferToken`, as already used in the project's own EVM test suite).
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000}` and no predispatch.
3. `safeTransferFrom(msg.sender, address(this), 1000)` actually delivers only 950 tokens to the contract due to the fee.
4. The contract nonetheless sets `_orders[commitment][FOT] += reducedInputs[0].amount` based on the full 1000 (minus protocol fee), not the 950 actually received.
5. On cancellation/timeout/redemption, `withdraw()` is invoked with `order.inputs` (still stating 1000), attempting to release/settle 1000 FOT tokens for this commitment even though only 950 were ever escrowed — either reverting (freezing the order) or, once multiple such orders exist, being paid out of other users' FOT balances held by the same contract, corrupting the shared token accounting.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
        } else if (currentChain == orderSource) {
            // source chain: fetch storage proof from destination
            // only owner can cancel order
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // order has not yet expired
            if (options.height <= order.deadline) revert NotExpired();

            // Cross-chain: fetch storage proof
            uint256 inputsLen = order.inputs.length;
            for (uint256 i; i < inputsLen;) {
                // check for order existence
                if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

                unchecked {
                    ++i;
                }
            }

            bytes memory context =
                abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(
                // contract address
                abi.encodePacked(instance(order.destination)),
                // storage slot hash
                calculateCommitmentSlotHash(commitment)
            );
            DispatchGet memory request = DispatchGet({
                dest: order.destination,
                keys: keys,
                timeout: 0,
                height: uint64(options.height),
                fee: options.relayerFee,
                context: context,
                payer: msg.sender
            });

            // dispatch storage query request
            if (msg.value > 0) {
                // there's some native tokens left to pay for request dispatch
                IDispatcher(hostAddr).dispatch{value: msg.value}(request);
            } else {
                // try to pay for dispatch with fee token
                dispatchWithFeeToken(request);
            }
        } else if (currentChain == orderDest) {
            // destination chain: dispatch RefundEscrow request to source chain
            // If order hasn't expired, only owner can cancel
            if (order.deadline >= block.number) {
                if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
            }

            // Mark as cancelled locally to prevent fills
            _filled[commitment] = address(uint160(uint256(order.user)));

            bytes memory body = bytes.concat(
                bytes1(uint8(RequestKind.RefundEscrow)),
                abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
            );
