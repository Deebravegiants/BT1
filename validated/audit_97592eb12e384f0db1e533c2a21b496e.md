### Title
`finalizeGraduation` is brick-resistant against hostile LP seeding but not against an owner blacklisted by the LT asset, permanently freezing curve-raised LT and the token's graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` is a permissionless phase-2 call that any address can trigger for a token stuck in `Lifecycle.Graduating` [1](#0-0) . At the end of that call it unconditionally invokes `_sweepLTToOwner(lt, protectedLT)`, which performs a hard `safeTransfer` of any LT residue to `owner()` with no fallback recipient [2](#0-1) . If the protocol `owner()` address is ever blacklisted by the BounceTech LT (or the LT's underlying transfer path reverts for that address for any reason), this transfer reverts, and since `finalizeGraduation` has no code path around it, the entire phase-2 call reverts — the token is permanently stuck in `Lifecycle.Graduating`, with all curve-raised LT and the 250M reserved LP tokens parked on `Bonding` with no rescue path.

### Finding Description
The protocol's own documentation states that "Phase 2 must never revert under any pre-seed shape" and that `finalizeGraduation` exists specifically so that "anyone can call to rescue a stuck token" [3](#0-2) . This brick-resistance guarantee is built for hostile pre-seed griefing of the HyperSwap pair, but it is not built to survive a hard revert in the mandatory closing sweep to `owner()`.

`_sweepLTToOwner` is called unconditionally at the tail of `finalizeGraduation`, after LP seeding and before `LPLock.recordLock` [4](#0-3) . It computes `amount = bal - keep` and calls `IERC20(lt).safeTransfer(recipient, amount)` where `recipient = owner()` — a fixed, hardcoded address with no override or beneficiary parameter [5](#0-4) . This exactly mirrors the reported bug class: a recoverable-asset transfer hardcoded to a single, non-parameterizable recipient (`owner()`), with no alternate address to redirect to if that recipient becomes untransferable on the asset contract.

The class of assets involved (`lt`) is the BounceTech Leveraged Token used as the bonding-curve reserve asset throughout the protocol [6](#0-5) . Whether or not the currently deployed BounceTech LT implementation supports blacklisting today, the protocol's own risk model explicitly acknowledges that LT behavior/registration can change externally and that Bonding must remain functional even so (see the "Retired LTs" discussion in `docs/contracts-scope.md` acknowledging exchange-rate freezes and other external-LT-state risks) [7](#0-6) . A transfer-reverting condition against `owner()` (blacklist, code-based receive-guard, or any other asset-level restriction) breaks the "Phase 2 must never revert" invariant the codebase asserts it upholds, unlike the hostile-pre-seed defenses which were deliberately engineered to have no escape-hatch/brick risk [8](#0-7) .

This is a stronger instance of the reported bug class than the original report: instead of freezing only the recoverable dust belonging to the caller/owner, a revert here freezes the entire graduation — all curve-raised LT (`p.ltFromPair`) and the 250M reserved tokens (`LP_RESERVE`) that are parked on `Bonding` between phase 1 and phase 2, as documented in the two-phase graduation design [9](#0-8) .

### Impact Explanation
If `owner()` cannot receive the LT (blacklist or any other asset-level transfer restriction), `finalizeGraduation` reverts every time it's called for that token, for any caller, forever — there is no parameter to redirect the sweep and no owner-only override function to bypass `_sweepLTToOwner`. The token stays permanently in `Lifecycle.Graduating`: trading is frozen (curve trading stopped at phase 1), the token never reaches HyperSwap, and all the curve-raised LT plus the 250M LP-reserved tokens sit locked on `Bonding` with no withdrawal path. This affects every trader who bought into that token's curve, not just the owner — a clear case of permanent freezing of funds belonging to third parties (traders), which is more severe than the single-recipient freeze in the original report.

### Likelihood Explanation
Reaching `finalizeGraduation` requires no privilege — it is explicitly permissionless and callable by anyone once a token enters `Graduating` [10](#0-9) . The only precondition for the freeze is that `owner()`'s address is untransferable on the LT asset (e.g., blacklisted). This is plausible over the protocol's lifetime given `owner()` is a long-lived, publicly known multisig address and the reserve asset is an externally controlled leveraged token whose registration/behavior the protocol itself flags as subject to external change (BounceTech `redeployLt`/`ltExists` rotations) [7](#0-6) . Probability is comparable to the original report's assessment ("not high" but nonzero), while consequence is materially worse since it freezes third-party trader funds rather than only the owner's own recoverable dust.

### Recommendation
Do not hard-fail `finalizeGraduation` on the owner sweep. Either:
1. Wrap the `_sweepLTToOwner` transfer in a try/catch (or use `trySafeTransfer`) so a failed sweep does not block LP seeding, lock recording, and the `Lifecycle.Graduated` transition — emit a distinct event/leave the residue on `Bonding` for later manual recovery via an owner-settable beneficiary; or
2. Decouple the sweep from `finalizeGraduation` entirely: record the residue amount and let `owner()` (or a parameterized beneficiary) claim it separately via a standalone, owner-gated function that accepts an explicit `to` address, so a blacklisted `owner()` can redirect to any other address without affecting graduation of any token.

### Proof of Concept
1. Assume `owner()` of `Bonding` becomes untransferable on the LT contract (e.g., a future/alternate BounceTech LT deployment implements a transfer-restriction/blacklist, or the currently trusted LT is swapped for one that does via a normal LT rotation as documented for `ltExists`).
2. A trader buys enough of a freshly launched token to cross the graduation threshold; `_enterGraduating` fires inline, caching `pendingGraduation[token]` and flipping `Lifecycle: Curve → Graduating` [11](#0-10) .
3. Any address (keeper, trader, or attacker) calls `Bonding.finalizeGraduation(token)`.
4. LP seeding succeeds and produces `protectedLT` residue > 0; `_sweepLTToOwner(lt, protectedLT)` computes `amount = bal - keep` and calls `safeTransfer(owner(), amount)` [5](#0-4) .
5. Because `owner()` is blacklisted by the LT, the LT's `transfer`/`transferFrom` call reverts inside `safeTransfer`, which reverts the whole `finalizeGraduation` transaction.
6. Every subsequent call to `finalizeGraduation(token)` by anyone reverts identically; `token` never reaches `Lifecycle.Graduated`, and all curve-raised LT plus the 250M reserved tokens remain permanently locked on `Bonding`.

```markdown
- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).
- **Virtual token reserve.** At launch, `Pair.reserve0 = totalSupply (1B)` while only `curveSupply = 75%` (750M) of real tokens are transferred to the pair. The other 250M (`LP_RESERVE`) sit in `Bonding` for graduation. This extends the curve beyond the sellable supply, which is what makes dynamic LP seeding work cleanly.
- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
- **Parabola invariant.** With `V_t_init = totalSupply` and `curveSupply = 75%`, the function `tokensForLP(sold) = sold·(S−sold)/S` peaks at `S/4 = LP_RESERVE`. The cap in `_prepareGraduationLiquidity` is defensive — it can never bind in normal operation.
```

```markdown
### Options we considered (and rejected)

The obvious fixes were either ineffective or worse than the disease:

1. **Pre-create the pair atomically inside `_deployAndSeed` at launch time.** Doesn't work. A V2 pair is just an empty contract until someone calls `mint()`; pre-creating prevents `factory.createPair` from being callable by an attacker, but the attacker can still `transfer + mint` against the empty pair we created. ~80k extra gas per launch for zero security.
2. **Detect skewed pre-existing reserves in `_seedUniswapV2Direct` and revert if the ratio diverges by more than N bps.** Re-introduces brick risk: an attacker can grief every graduation with $1 of dust per token. Forces ops to either (a) widen the bound enough that the attack survives, or (b) keep it tight and ship an admin escape hatch. We previously had `_requirePairEmpty` which had this exact problem and we removed it for that reason — `test_brick_resistance_frontRun_dust_seed` exists to prevent regression.
3. **Custom V2 pair with launchpad-specific `mint()` semantics.** Means forking the AMM. Breaks the "post-grad venue is HyperSwap" property in the root [`AGENTS.md`](../../AGENTS.md) — our pairs would no longer be real HyperSwap pairs, aggregators wouldn't pick them up. Architecturally unacceptable.
4. **Defensive bot only.** Off-chain race against the attacker to call `finalizeGraduation` first. Probabilistic, fails on bad gas estimation, and doesn't address the case where the attacker pre-seeded BEFORE the threshold-crossing buy lands. Insufficient.
```

```markdown
**Retired LTs.** The reserve asset is an external BounceTech LT. If BounceTech de-registers it (it redeploys a fresh LT at a new address and flips the old address's `ltExists` to `false`), bonding curves already pointing at the old LT keep trading — `mint` / `redeem` / `exchangeRate` still work — but its `exchangeRate` stops tracking the underlying, so leverage is effectively frozen. The USD trigger above then can't ripen further; the supply trigger still graduates the token, and holders can always exit via `redeem`, so no funds are stranded. `Bonding.launch` rejects new bonding curves against a retired LT (its `ltExists` gate), so only pre-existing bonding curves are affected. See root `AGENTS.md` for the full note.
```
