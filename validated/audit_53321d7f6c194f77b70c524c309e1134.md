### Title
Unchecked division-by-zero panic in `calc_take_pnl` can permanently freeze deposits when pool reserves normalize to zero - ([File: program/src/processor.rs])

### Summary
The CVE describes an InnoDB bug where a high-privilege but otherwise ordinary client operation causes the MySQL server to hang or crash (an availability/DoS impact) via a reachable arithmetic/internal-state fault. The closest reachable analog in this codebase is the unconditional, unguarded division in `Processor::calc_take_pnl`, which is invoked on every `Deposit` (and non-`WithdrawOnly` `Withdraw`) instruction and can divide by an attacker-influenced value that becomes zero, panicking the transaction and — because the call is unconditional in `process_deposit` — permanently blocking deposits into the pool once that state is reached.

### Finding Description
`Processor::calc_take_pnl` computes a new "post-pnl" reserve split using: [1](#0-0) 

```
let x2_power = Calculator::calc_x_power(target.calc_pnl_x.into(), target.calc_pnl_y.into(), x1, y1);
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
```

`x1` is `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, amm.pc_decimals, amm.sys_decimal_value)` [2](#0-1) , which performs integer division: `val * sys_decimal_value / 10^native_decimal` [3](#0-2) . Because this is floor/integer division, if the pool's remaining native PC reserve (`total_pc_without_take_pnl`) is small relative to `10^pc_decimals / sys_decimal_value`, `x1` can normalize to `0` even though the raw token balance is non-zero.

`calc_take_pnl` is called unconditionally at the top of `process_deposit` regardless of AMM status [4](#0-3) , and in `process_withdraw` whenever `amm.status != AmmStatus::WithdrawOnly` [5](#0-4) . When `x1 == 0`, `checked_div(x1)` returns `None`, and the immediately-following `.unwrap()` panics the transaction, exactly mirroring the CVE's "hang or frequently repeatable crash" bug class, but at the smart-contract level.

Reaching this state requires the pool's normalized PC (or, symmetrically, coin) reserve to reach zero while the raw token account balance is still non-zero — attainable by an unprivileged trader repeatedly executing `SwapBaseIn`/`SwapBaseOut` to drain one side of the pool down to a residual amount below the normalization granularity (`10^pc_decimals / amm.sys_decimal_value`), a threshold that is entirely a function of public, attacker-visible AMM configuration (`pc_decimals`, `sys_decimal_value`).

### Impact Explanation
Once the pool state satisfies `x1 == 0` (or symmetrically `y1 == 0` via `coin_decimals`), any subsequent `Deposit` instruction unconditionally panics inside `calc_take_pnl`, because `process_deposit` has no status-based bypass for this call. This means legitimate liquidity providers can no longer add liquidity to the pool — a permanent freezing of the deposit path for that pool — until/unless the reserve ratio is restored by external means, which an adversary who has already drained the pool has no incentive to do. This satisfies the "permanent freezing of user or LP funds" impact bar (deposits, not just an isolated swap, become permanently unusable for that pool instance).

### Likelihood Explanation
Reachable purely via the public `SwapBaseIn`/`SwapBaseOut` instructions and the public `Deposit` instruction, using attacker-chosen instruction data (`amount_in`/`amount_out`) and standard swapper/LP account roles — no privileged signer or off-chain component required. The precondition (driving one side's normalized reserve to zero) depends on the specific `pc_decimals`/`coin_decimals`/`sys_decimal_value` configuration of a given pool, so exploitability is pool-specific rather than universal, which is why this is assessed as Medium rather than High/Critical.

### Recommendation
Replace the raw `.unwrap()` calls in `calc_x_power`/`calc_take_pnl` with `checked_div(...).ok_or(AmmError::CalcPnlError)?` (or equivalent), and add an explicit guard in `calc_take_pnl` (and its callers) to short-circuit/return a clean error when `x1 == 0` or `y1 == 0`, so a zero-normalized reserve cannot brick the deposit path.

### Proof of Concept
Conceptually:
1. Attacker (any user) repeatedly calls `SwapBaseIn`/`SwapBaseOut` to drain the PC side of a pool whose `pc_decimals` is large relative to `amm.sys_decimal_value`, until `total_pc_without_take_pnl` is small enough that `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, amm.pc_decimals, amm.sys_decimal_value)` floors to `0`.
2. Any subsequent `Deposit` instruction calls `Self::calc_take_pnl(...)` unconditionally [4](#0-3) , which computes `x1 = 0` and then executes `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` [6](#0-5) , panicking the transaction for every future deposit attempt.

Note: I was unable to fully verify how `amm.sys_decimal_value` is initialized/constrained across all pool configurations (the `AmmInfo::initialize` function body in `state.rs` was not fully retrievable via the index), so the exact numeric conditions under which `x1`/`y1` can reach zero for typical mainnet pool configurations (e.g., default `sys_decimal_value` and common token decimal combinations) could not be conclusively confirmed. A Devin session with full repository access would be needed to inspect `program/src/state.rs::AmmInfo::initialize` and confirm concrete decimal/`sys_decimal_value` combinations that make this reachable in practice.
