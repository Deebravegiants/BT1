Based on my analysis of `Webhooks::Request` and `Webhooks::Registry`, this is a genuine finding, though the specific "access token theft" impact framing in the question overstates what the code path directly demonstrates. The concrete, provable impact is forged topic/shop dispatch, which is a form of authentication bypass (forged webhook accepted as a different event/tenant).

### Title
Webhook HMAC binds only `@raw_body`, allowing `topic`/`shop-domain` header forgery under a replayed valid signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` authenticates the body bytes but never binds `topic`, `shop-domain`, `webhook-id`, or `api-version` to that signature [2](#0-1) . An attacker who owns a real development shop can capture one genuine Shopify-signed webhook body+HMAC pair delivered to their own endpoint, then POST that same body/HMAC directly to the app's public webhook route with arbitrary `x-shopify-topic` and `x-shopify-shop-domain` headers; `Registry.process` will accept the HMAC and dispatch the handler keyed to the forged topic with the forged shop identity [3](#0-2) .

### Finding Description
The invariant the question describes should hold is:
`hmac_valid(request) == true` **iff** `(request.topic, request.shop, request.webhook_id, request.raw_body)` were all produced together by Shopify for a single authenticated delivery.

In this codebase that binding does not exist. `to_signable_string` is defined as simply:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it with `verifiable_query.hmac`, which is decoded straight from the `x-shopify-hmac-sha256` header via `Base64.decode64` [4](#0-3) [5](#0-4) . None of `topic`, `shop`, `webhook_id`, or `api_version` — all read from separate, unauthenticated HTTP headers via `shopify_header` [6](#0-5) [7](#0-6)  — enter the signed material.

`Registry.process` trusts these header-derived values directly to select the handler and to construct `WebhookMetadata`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [8](#0-7) 

**Attacker's exact request:** the attacker registers their own development shop, receives one genuine Shopify webhook delivery to their own endpoint (raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-topic: T1`, `x-shopify-shop-domain: attacker.myshopify.com`). Since `H = HMAC(secret, B)` does not depend on the topic/shop headers, the attacker can then send a direct POST to the app's public webhook endpoint with the same `B` and `H`, but `x-shopify-topic: T2` (any registered topic) and `x-shopify-shop-domain: victim.myshopify.com` (any shop string). `HmacValidator.validate` still returns `true` because it only recomputes HMAC over `B`. `Registry.process` then dispatches the handler registered for `T2`, and hands it `WebhookMetadata` claiming shop `victim.myshopify.com`, even though the body content and HMAC were only ever authenticated for the attacker's own shop and original topic `T1`.

**Why existing guards don't stop this:** `HmacValidator.validate` and `ShopValidator` are not invoked together here — `ShopValidator.sanitize!` is used only in OAuth flows, not in the webhook pipeline; `Registry.process` performs no comparison between `request.shop`/`request.topic` and any value embedded inside `request.parsed_body`. There is no Sorbet check that could catch this, since types (`String`) don't constrain provenance.

### Impact Explanation
This lets the handler registered for an arbitrary topic (including sensitive ones like `shop/redact`-style app-defined handlers, or any handler the app author registered) be invoked with an attacker-chosen `shop` value and a body that was never actually validated for that topic/shop pair. This is a **forged-webhook-accepted** condition: `Registry.process` treats an HMAC that only authenticates *bytes* as if it authenticates *(shop, topic)* identity too, letting a single-tenant attacker's own signed traffic be replayed to impersonate arbitrary other shops/topics against the app's webhook handlers. Whether this reaches token theft or other Critical outcomes depends entirely on what the *host app's* handler code does with the (forged) `shop`/`topic`/`body` combination — the gem itself does not expose or transmit `X-Shopify-Access-Token` anywhere in this webhook path [9](#0-8) , so the "Admin API access token theft" impact claimed in the question is not directly substantiated by this file; the directly demonstrable impact is topic/shop confusion enabling forged webhook acceptance, which still fits the Critical "authentication bypass (forged webhook ... accepted)" category, but only cross-tenant/token-theft consequences that a specific host app's handler logic might add are speculative and outside this gem's code.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's control: create/own a development shop, install the target app, receive one legitimate webhook, then directly POST to the app's known webhook endpoint URL with forged headers and the captured body/HMAC pair. No secrets, no TLS interception, and no elevated privileges are needed — only that the app's webhook endpoint is reachable directly over HTTP (true for any typical Rack/Rails route), matching the "attacker can send arbitrary HTTP requests" threat model. This is fully repeatable for any topic registered in `Registry` and any shop-domain string.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise cryptographically or structurally verify that `topic`/`shop-domain`/`webhook-id` match the authenticated delivery (e.g., compare against a `shop`/`topic` value embedded in the JSON payload itself, or require the app to independently confirm the shop exists in its own session store and only invoke handlers for topics that shop is actually subscribed to) rather than trusting `x-shopify-topic`/`x-shopify-shop-domain` headers as implicitly authenticated once the raw-body HMAC passes.

### Proof of Concept
Minitest outline (extends the existing pattern in `test/webhooks/registry_test.rb`):
```ruby
def test_hmac_does_not_bind_topic_or_shop_to_body
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  hmac_header = Base64.encode64(hmac)

  handler_a = mock; handler_a.expects(:handle).never
  handler_b = mock; handler_b.expects(:handle).once
  ShopifyAPI::Webhooks::Registry.add_registration(topic: "topicA", delivery_method: :http, path: "x", handler: handler_a)
  ShopifyAPI::Webhooks::Registry.add_registration(topic: "topicB", delivery_method: :http, path: "x", handler: handler_b)

  # Forged request: same body+hmac originally issued for "topicA"/attacker shop,
  # replayed under "topicB" and a different shop-domain
  forged = ShopifyAPI::Webhooks::Request.new(
    raw_body: body,
    headers: {
      "x-shopify-topic" => "topicB",
      "x-shopify-hmac-sha256" => hmac_header,
      "x-shopify-shop-domain" => "victim.myshopify.com",
    },
  )

  ShopifyAPI::Webhooks::Registry.process(forged) # does not raise InvalidWebhookError
  # assertion: handler_b was invoked despite the HMAC never being computed with knowledge of "topicB" or "victim.myshopify.com"
end
```
This demonstrates that swapping `topic`/`shop-domain` headers on an otherwise-unmodified, validly-signed body still passes `HmacValidator.validate` and dispatches the (forged) handler, confirming the header/body identity is not bound to the authenticated signature.
