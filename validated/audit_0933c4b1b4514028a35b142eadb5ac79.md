This confirms the claim precisely. The documentation itself is misleading/inaccurate: `core.toml` states "This check is already performed during login/logout actions" for `UpstreamSyncInterval = '0s'`, but no code path invokes `Work()` on login or logout — grep for `Work(` calls shows it is only referenced within `sync.go` itself (`Start()` calling it once at boot, and `run()`'s ticker calling it only when the interval is non-zero) [1](#0-0) . With the shipped default `UpstreamSyncInterval = '0s'` [2](#0-1) , `Start()` executes `Work()` a single time at startup and never schedules a ticker, so no ongoing reconciliation occurs.

`AuthorizedUserWithSession` for both LDAP and OIDC providers trusts the locally cached `user_role` column exclusively, validating only session expiry via elapsed time, with no per-request upstream check [3](#0-2) [4](#0-3) . This cached role is what `RequiresAdminRole` and related middleware trust on every subsequent request [5](#0-4) . In contrast, `localauth.orm.UpdateRole` immediately purges the user's sessions on role change, forcing re-authentication — a pattern absent from the LDAP/OIDC provider's role-sync logic, which only updates the role column in place without invalidating in-flight cached sessions [6](#0-5) .

Given the code review confirms every specific technical claim (stale role caching, default `'0s'` disabling periodic sync, no login/logout-triggered resync despite documentation claiming otherwise, and no per-request revalidation against upstream), this is a legitimate finding rather than a speculative one. It requires the operator to have configured LDAP or OIDC authentication (an in-scope, supported node feature, not a "misconfiguration" exclusion since `'0s'` is the documented shipped default), and the exploit trigger — a demoted user continuing to send authenticated requests with an existing valid session cookie — is exactly the "unprivileged (post-demotion) client request" pattern that is in-scope per the rules, not requiring host, database, or additional admin access.

Audit Report

## Title
Stale Cached Role in LDAP/OIDC Session Table Enables Post-Demotion Privileged Access - ([File: core/sessions/ldapauth/ldap.go])

## Summary
When `WebServer.AuthenticationMethod` is `ldap` or `oidc`, a user's role is cached in `ldap_sessions`/`oidc_sessions` at login and is never re-validated against the upstream LDAP/OIDC source on a per-request basis. The only reconciliation mechanism, `LDAPServerStateSyncer.Work`, is gated behind `UpstreamSyncInterval`, whose documented default is `'0s'`, causing it to run exactly once at node startup and never again — despite the config documentation incorrectly claiming the sync "is already performed during login/logout actions."

## Finding Description
`AuthorizedUserWithSession` for LDAP queries only the local `ldap_sessions` table and returns the cached `user_role`, checking solely elapsed time for expiry [3](#0-2) ; the OIDC equivalent behaves identically against `oidc_sessions` [4](#0-3) . This cached role is trusted by `RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` on every subsequent request [5](#0-4) . `LDAPServerStateSyncer.Start` only schedules a recurring `Work()` ticker if `UpstreamSyncInterval` is non-zero; with the default `'0s'`, `Work()` runs once at boot and is never re-invoked on a timer [1](#0-0) , and `Work()` is not called from any login/logout code path in `ldap.go`'s `CreateSession`/`DeleteUserSession` — contradicting the config doc's claim [2](#0-1) . This is structurally different from `localauth.orm.UpdateRole`, which purges all of a demoted user's sessions in the same transaction as the role update, forcing re-authentication [7](#0-6) ; the LDAP/OIDC sync path only updates the role value in place without invalidating already-cached sessions [6](#0-5) .

## Impact Explanation
A user demoted from admin (or removed from the upstream LDAP admin group / OIDC claim) while authenticated via LDAP or OIDC retains their cached `admin` role for every `RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole`-gated HTTP/GraphQL API call until their session naturally expires per `SessionTimeout` (default `15m0s`, operator-configurable much higher) [8](#0-7) , because the default `UpstreamSyncInterval='0s'` disables periodic reconciliation entirely. This is a concrete node API role-bypass impact affecting administrative actions across the node's authenticated surface.

## Likelihood Explanation
The trigger requires no special access beyond continuing to use an already-issued, valid session cookie after demotion — an unprivileged-relative-to-the-new-state client action. The only precondition is running with LDAP/OIDC auth and the shipped default `UpstreamSyncInterval='0s'`, which is the out-of-the-box default rather than an unusual hardening choice, making this a realistic default-configuration exposure.

## Recommendation
- Change the default `UpstreamSyncInterval` to a bounded non-zero value, and correct the misleading documentation claiming login/logout-triggered sync exists.
- Trigger an upstream role re-check (or session invalidation) in `AuthorizedUserWithSession` for privileged roles, or at minimum on a short request-scoped cadence.
- Have `Work()` purge/invalidate `ldap_sessions`/`oidc_sessions`/`*_user_api_tokens` rows on detected role changes rather than only updating the role column in place, mirroring `localauth.orm.UpdateRole`'s session-purge behavior.

## Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'ldap'` with default `UpstreamSyncInterval = '0s'` and a long `SessionTimeout`.
2. User logs in as a member of the LDAP `NodeAdmins` group; `CreateSession` inserts an `ldap_sessions` row with `user_role='admin'`.
3. Operator removes the user from `NodeAdmins` upstream.
4. Because `Work()` only ran once at boot, `ldap_sessions.user_role` remains `'admin'`.
5. The demoted user continues sending requests with their existing session cookie against a `RequiresAdminRole`-gated endpoint (e.g., `PATCH /v2/users`); `AuthorizedUserWithSession` returns the stale `admin` role and the request is permitted until session expiry.

		Role:  foundSession.UserRole,

	})
