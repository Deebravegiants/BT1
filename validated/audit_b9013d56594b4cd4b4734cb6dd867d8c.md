### Title
Fee-only failed transactions with `define_ltds_fee_only_semantics` charge only the declared `set_loaded_accounts_data_size_limit`, not the real bytes read before the limit check aborted the load - ([File: svm/src/account_loader.rs])

### Summary
An unprivileged attacker can craft a transaction that declares an artificially tiny `loaded_accounts_data_size_limit` via `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit` while referencing one very large account (up to `MAX_ACCOUNT_DATA_LEN` = 10 MiB). The account is fully fetched/deserialized from accounts-db (real IO/CPU work) before the size check fails, but `LoadedTransactionDataSize::from` caps the reported `loaded_accounts_data_size` down to the tiny declared limit, so the fees-only transaction's cost-model charge reflects only the declared limit instead of the actual bytes touched.

### Finding Description
`load_transaction_accounts` in [1](#0-0)  loads each referenced account (real accounts-db read/clone/deserialize) via `load_transaction_account` and only afterwards calls `collect_loaded_account`, which invokes `increase_calculated_data_size` in [2](#0-1) . That function adds the account's real size to the running total and only *then* checks it against `requested_loaded_accounts_data_size_limit`, returning `Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)` when exceeded - after the expensive read has already occurred.

When the load fails, `load_transaction` in [3](#0-2)  builds a `FeesOnlyTransaction` and, when `define_ltds_fee_only_semantics` is active, sets `loaded_accounts_data_size` from `loaded_transaction_data_size.into()`. The `From<LoadedTransactionDataSize> for u32` conversion in [4](#0-3)  explicitly does `.min(requested_loaded_accounts_data_size_limit)`, so any raw size that exceeded the limit is truncated down to exactly the declared (attacker-chosen) limit - confirmed by the code comment/test "data size helper reports the limit only" in [5](#0-4)  and by the dedicated integration test `fee_only_loaded_transaction_data_size` in [6](#0-5) , which asserts the reported size equals `size_limit` (not the true accumulated size) when the limit is exceeded.

This capped value then flows directly into real cost accounting: `ProcessedTransaction::loaded_accounts_data_size` returns `details.loaded_accounts_data_size` for the `FeesOnly` branch ( [7](#0-6) ), and banking-stage's `calculate_processed_transaction_costs` feeds it into `CostModel::calculate_cost_for_executed_transaction` ( [8](#0-7) ), which is what actually gets added to `cost_tracker` via `try_add` ( [9](#0-8) ). No lower bound is enforced on `set_loaded_accounts_data_size_limit`, and account sizes up to `MAX_ACCOUNT_DATA_LEN` (10 MiB) are permitted ( [10](#0-9) ), so the attacker fully controls both the huge real read size and the tiny reported/charged size.

### Impact Explanation
This is a cost-model/fee-accounting underpricing bug: an unprivileged attacker can force the validator to perform a full accounts-db fetch/deserialize of an up-to-10 MiB account for a fee-only (failed) transaction while only being charged the cost of a single page (as low as 1 byte, rounding to `ACCOUNT_DATA_COST_PAGE_SIZE`) via `CostModel::calculate_loaded_accounts_data_size_cost` ( [11](#0-10) ). Because this cost feeds the block-level `cost_tracker`, many such transactions can be packed into a block far beyond what the declared cost-tracker limits should allow for the real IO/CPU work performed, degrading leader throughput/replay time relative to the nominal per-block cost budget - matching the "cost-model ... charge materially less than the real CPU, memory, or account-load work performed, exhausting block capacity or node resources below true cost" category.

### Likelihood Explanation
Fully attacker-controlled and repeatable with a single unsigned transaction template: (1) reference one pre-existing large account (attacker can create/fund such an account themselves beforehand), (2) add `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit(1)` (or any tiny value), (3) reference a nonexistent/failing program so the load path fails via `MaxLoadedAccountsDataSizeExceeded`. This requires only normal RPC/TPU access, no special privileges, and can be repeated across many transactions/blocks.

### Recommendation
Do not cap the reported/charged `loaded_accounts_data_size` to the declared limit for cost-tracking purposes when the failure is `MaxLoadedAccountsDataSizeExceeded`; instead charge based on the actual raw accumulated `loaded_accounts_data_size` (the real bytes measured before the abort), or charge a fixed worst-case penalty (e.g., the size of the account that caused the overflow) so the cost tracker reflects real work performed rather than the attacker-chosen limit.

### Proof of Concept
Extend `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs`:
1. Create one initial account of size close to `MAX_ACCOUNT_DATA_LEN` (10 MiB).
2. Build a transaction with `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit(1)` referencing that account and a valid program, so account loading reads the full 10 MiB account before the size check trips.
3. Assert `output.processing_results[i].loaded_accounts_data_size() == 1` (the declared limit) while the actual account read was ~10 MiB.
4. Compute `CostModel::calculate_loaded_accounts_data_size_cost(1, feature_set)` vs. `CostModel::calculate_loaded_accounts_data_size_cost(10 * 1024 * 1024, feature_set)` and show a multi-order-of-magnitude discrepancy, demonstrating the cost tracker undercharges for the real work performed.
