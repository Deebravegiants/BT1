### Title

Accidental token transfers to the controller are permanently stranded - (contracts/controller/src/payments.rs)

### Summary

The controller can custody tokens, but it has no user-facing recovery or sweep mechanism for pre-existing balances. Its refund helper intentionally returns only the positive balance delta created during a specific operation and leaves any earlier balance in the contract. An unprivileged user who transfers a token directly to the controller—or delivers an undeclared token during a `flash_position` callback—cannot recover it.

### Finding Description

`refund_controller_balance_delta` snapshots a prior controller balance and refunds only `current_balance - balance_before`; a pre-existing controller balance is explicitly preserved. [1](#0-0) 

`flash_position` accepts a caller-selected `refund_assets` list, but refunds are based on positive callback deltas. Tokens already held by the controller before the callback, or tokens returned without being declared for refund, remain uncredited in the controller. [2](#0-1) 

The public controller surface contains user operations such as supply, borrow, repayment, liquidation, flash operations, and strategy calls, but no endpoint that lets the original sender withdraw an unrelated or stranded controller balance. [3](#0-2) 

The pool has the same accounting separation: cash is a book balance rather than the token contract balance, while `transfer_out` moves the listed asset without sweeping an excess balance. [4](#0-3) [5](#0-4) 

### Impact Explanation

A mistaken direct token transfer to the controller is permanently frozen. The same applies to callback-delivered assets that are not covered by `refund_assets`: they remain under controller custody without becoming account collateral, repaying debt, or being returnable through a recovery path. For pool donations, the token balance rises but the donor receives no shares or bookkeeping claim.

This is permanent freezing of user funds, reachable by an unprivileged address through a direct SAC token transfer or an authorized flash-position callback.

### Likelihood Explanation

The condition requires user or integration error rather than an attacker forcing the loss. That lowers likelihood, but the controller is an active settlement contract and routinely receives temporary balances during strategy callbacks, making accidental delivery plausible. Once delivered outside the measured delta/refund scope, recovery is impossible through the exposed interface.

### Recommendation

Add an explicit recovery mechanism for non-accounting controller balances, or extend the relevant operations to refund positive balances attributable to the current payer/callback even when they predate the balance snapshot.

For the pool, either expose a controlled donation-recovery path for balances above all market books and obligations, or document and enforce that incidental balances can be recapitalized by governance. Any recovery implementation must distinguish prior donations from balances reserved for cash books, revenue, refunds, and in-flight callbacks.

### Proof of Concept

1. Let `C` be the deployed controller address and `T` a token contract accepted by, or even unrelated to, a listed market.
2. An unprivileged user calls `T.transfer(user, C, amount)`. The token transfer itself only requires the user's authorization.
3. The controller now holds `amount` of `T`, but no account position is created and `T` is not associated with a refundable payment leg.
4. The user calls `flash_position` with `T` included in `refund_assets`. The callback performs no additional `T` transfer to the controller.
5. `refund_controller_balance_delta` computes `balance_after - balance_before`. Because the transfer occurred before the callback, the delta is zero and no refund is issued. [1](#0-0) 
6. Repeating the call or declaring the asset again cannot recover the pre-existing balance; only a positive delta is eligible. The transferred `amount` remains stranded in the controller.

/// Refunds only the controller balance increase since `balance_before`,
/// preserving the pre-existing balance; no-op for a nonpositive delta.
pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
