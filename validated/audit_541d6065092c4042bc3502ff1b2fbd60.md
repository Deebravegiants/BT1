Webhook shop-tenant identity (`x-shopify-shop-domain` header) is not covered by the HMAC signature, allowing shop-spoofing in `ShopifyAPI::Webhooks::Request` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. The header carrying the tenant identity is never part of the signed material, so `Registry.process` accepts any shop value the caller supplies in that header as long as the body bytes match a valid HMAC for *some* registered app secret.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` field [1](#0-0) .

For webhooks, `ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` with:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`to_signable_string` returns only `@raw_body` — the `shop` (and `topic`, `webhook_id`, `api_version`) headers are excluded from the signable string entirely. Genuine Shopify webhooks always sign body bytes only (this matches Shopify's actual webhook HMAC scheme, so this is a legitimate constraint of the protocol, not a bug in isolation). However, `Registry.process` treats the header-derived `request.shop` as trusted tenant identity once the body HMAC passes:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` **and** `shop ∈ signed_bytes`. Instead the gem only guarantees `HMAC(secret, raw_body) == received_hmac`, with `shop` supplied out-of-band and unauthenticated. Since the raw body itself is attacker-controlled JSON (an app cannot reject arbitrary JSON payloads sent to its webhook endpoint before HMAC validation — the HMAC is the *only* gate), an attacker who can obtain one valid `(body, hmac)` pair for their own shop (trivial — they can trigger a real webhook for their own installed/development store) can replay that exact body+hmac pair while substituting an arbitrary `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will pass the HMAC check (it never looks at the header) and will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding purely within library code that host applications are documented to rely on directly (`docs/usage/webhooks.md` shows using `ShopifyAPI::Webhooks::Registry.process` as the sole verification step before trusting `data.shop`) [4](#0-3) . Any app that uses `WebhookMetadata#shop` to look up/scope data (a documented, expected usage pattern) can be tricked into acting on data intended for shop A while `shop` claims to be shop B, constituting cross-tenant confusion delivered entirely through this gem's own verification API, without needing the app's `client_secret`, an access token, or any other elevated credential — the attacker only needs a valid HMAC over a body they control (achievable using their own shop's genuine webhook delivery).

### Likelihood Explanation
Moderate-to-high: exploitation requires the attacker to have at least one valid `(body, hmac)` pair, which is trivially obtainable if the app is installed on any shop the attacker controls (a free/dev store), since Shopify will deliver real webhooks with real HMACs for that shop, and the attacker fully controls the header set when replaying the request to the app's webhook endpoint (headers are not covered by TLS-based origin identity for this gem's own verification, which only checks the HMAC).

### Recommendation
Do not trust `request.shop` from `ShopifyAPI::Webhooks::Request` as an authenticated tenant identifier based solely on the body HMAC. Either:
- Cross-check `request.shop` against the shop encoded within the parsed body/topic-specific payload when available, or
- Require callers to independently confirm the shop domain against a shop they have a stored offline session/access token for before trusting `WebhookMetadata#shop`, and document this requirement explicitly since the current implementation and docs imply `Registry.process` alone is sufficient to authenticate the shop.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app has registered. Capture the raw body `B` and the `x-shopify-hmac-sha256` value `H` that Shopify sends (valid because `H = HMAC(secret, B)`, which does not depend on the shop header at all per `to_signable_string`) [5](#0-4) .
2. Replay a request to the app's webhook endpoint with the same body `B` and hmac header `H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` and `H` [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop == "victim.myshopify.com"` [7](#0-6) , even though the payload body actually belongs to `attacker.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
