### Title
Unbounded QR-code `user_id` accepted from the internal-data-acquisition regex and embedded directly into signup HTTP requests without a length/charset cap - (File: src/plans/qr_scan/user.rs)

### Summary
The user-facing QR scanning schema that identifies a signup session validates the standard user QR code against a strict, length-bounded UUID pattern, but the alternate "signup extension" QR code path accepts an effectively unbounded `user_id` string. That attacker-controlled string is later concatenated verbatim into backend request URLs and multipart form fields with no size or character-set enforcement.

### Finding Description
`Data::try_parse` in `src/plans/qr_scan/user.rs` first tries `decode_qr`, then the strict `QR_CODE_V2` regex (which constrains `user_id` to fixed-length hex/UUID groups), and finally — when the `internal-data-acquisition` feature is compiled in — the `QR_CODE_SIGNUP_EXTENSION` regex: [1](#0-0) 

Unlike `QR_CODE_V2`, this regex captures `user_id` with the unbounded quantifier `[a-z0-9_-]+`, and also captures `mode`/`parameters` with unbounded quantifiers (`[a-z0-9]+`, `[a-z0-9:]+`), imposing no maximum length on the input a scanned QR code can contribute: [1](#0-0) 

`Data::from_signup_extension` copies this unvalidated `user_id` straight into the `Data` struct with no additional length check: [2](#0-1) 

This `user_id` (`qr_code.user_id`) is then interpolated directly into backend request URLs as a path segment in `src/backend/user_status.rs`: [3](#0-2) 

and into a multipart form field (`userId`/`distributorId`) sent to the signup endpoint in `src/backend/signup_post.rs`: [4](#0-3) 

Because the value originates from a QR code shown to the Orb's camera — content fully controlled by any unprivileged party physically presenting a QR code during the signup flow — an attacker can encode an arbitrarily long `user_id` (limited only by QR-code physical data capacity, which can still reach several KB) that flows unchecked into a URL path and HTTP form body constructed on the Orb.

### Impact Explanation
This matches the reported bug class precisely: no application-side limit is enforced on a value that ends up in a URL parameter/path segment and a form field. Concretely reachable impacts:
- Malformed/oversized `GET {SIGNUP_BACKEND_URL}/api/v2/session/{user_id}/status` and `POST {SIGNUP_BACKEND_URL}/api/v2/signups/{signup_id}` requests could be rejected unpredictably by the backend or its edge/proxy layers (URL length limits), causing the Orb signup/validation flow to fail or behave inconsistently (denial of legitimate signup attempts) — a fraud/identity-binding-flow reliability issue rather than a simple crash.
- Because `distributorId`/`userId` are trusted verbatim for the signup request without a sanity length check, this could contribute to cross-signup state confusion if a downstream service mishandles overlong or malformed identifiers differently than shorter validated UUIDs (the fixed-format `QR_CODE_V2` path is safe; only the extension path lacks the bound).
- This is a client-side input validation gap in a security-relevant identity binding value (`user_id` used to correlate a signup session), reachable by any unprivileged user scanning a crafted QR code, consistent with the "Unrestricted Input Size" bug class.

### Likelihood Explanation
The `QR_CODE_SIGNUP_EXTENSION` path is only compiled when the `internal-data-acquisition` feature is enabled (used for data-acquisition/research builds), and requires the operator/user QR-scan flow to reach `from_signup_extension`. When that feature is active, no operator authorization or special privilege is required to trigger this — any QR code shown to the camera during the standard QR-scan plan step is parsed through `Data::try_parse`, and reaching this path only requires crafting a QR code matching the extension format, which is a low-privilege, physically-reachable action.

### Recommendation
- Bound the `user_id`, `mode`, and `parameters` capture groups in `QR_CODE_SIGNUP_EXTENSION` in `src/plans/qr_scan/user.rs` to explicit maximum lengths (mirroring the fixed-length groups already used in `QR_CODE_V2`).
- Add an explicit length/charset validation step in `Data::from_signup_extension` before accepting the parsed `user_id`, rejecting values that exceed the expected UUID-like size.
- Enforce a maximum length check on `qr_code.user_id` immediately before it is used to build request URLs/form fields in `src/backend/user_status.rs` and `src/backend/signup_post.rs`, and reject processing early if exceeded.

### Proof of Concept
1. Build/run the Orb software with the `internal-data-acquisition` feature enabled.
2. Present a QR code encoding a string matching the `QR_CODE_SIGNUP_EXTENSION` pattern but with a `user_id` field of many thousands of characters, e.g. `userid:` + `"a" * 4000` + `:1::`.
3. Observe `Data::try_parse` (src/plans/qr_scan/user.rs) accept this value via `from_signup_extension` with no length rejection.
4. Continue the signup flow: `qr_code.user_id` is embedded verbatim into the URL built in `src/backend/user_status.rs` (`.../session/{user_id}/status`) and into the multipart form (`userId`) posted in `src/backend/signup_post.rs`, producing an oversized request that the backend or its infrastructure may reject or mishandle inconsistently compared to the length-bounded `QR_CODE_V2` path.

    #[must_use]
    fn from_signup_extension(captures: &Captures) -> Self {
        let v2_data = Self::from_v2(captures);
        let mode = SignupMode::parse(captures.name("mode").map(|mode_group| mode_group.as_str()));
        let parameters = captures
            .name("parameters")
            .map(|parameters_group| parameters_group.as_str().to_string());

        Self {
            user_id: v2_data.user_id,
            signup_extension: true,
            signup_extension_config: mode.map(|mode| SignupExtensionConfig { mode, parameters }),
            user_data_hash: None,
        }
    }
