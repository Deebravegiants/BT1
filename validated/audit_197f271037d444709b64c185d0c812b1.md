### Title
Webhook shop/topic identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` never covers the `shop-domain`, `topic`, or `webhook-id` headers. `Webhooks::Registry.process` nonetheless trusts these unauthenticated headers to determine which shop/tenant and topic a payload belongs to and dispatches it to the app's handler under that shop's identity.

### Finding Description
`Webhooks::Request` extracts `shop`, `topic`, and `webhook_id` purely from HTTP headers: [1](#0-0) 

Its `to_signable_string` — the data the HMAC is computed and verified over — is only the raw body: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` and `request.topic` (unauthenticated header values) to build the metadata handed to the app's handler: [3](#0-2) 

The identity binding this breaks (as an equality that should hold but doesn't): `HMAC-verified bytes == bytes the handler treats as authoritative for tenant attribution`. In reality `HMAC-verified bytes (raw_body only) != bytes used to determine shop (shop-domain header)`. Since Shopify apps share a single `api_secret_key`/`client_secret` across every shop that installs the app (webhook HMACs are not shop-specific secrets), anyone who can obtain one valid `(raw_body, hmac)` pair for their own shop's webhook delivery (e.g., a developer/attacker installing the app on a test store and observing the webhook body/HMAC sent to the app's endpoint) can replay that same body and HMAC to the app's endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` still succeeds because it only checks the raw body against the shared secret, and `Registry.process` will dispatch the payload to the handler as if it came from the spoofed victim shop/topic.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an app's webhook handler (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or any custom handler that keys persistence/business logic off `WebhookMetadata#shop`) can be made to act on behalf of, or attribute data to, a shop the attacker does not control. Depending on how a host application uses `shop`/`topic` from `WebhookMetadata`, this can lead to deletion or mutation of another merchant's stored data, corrupted session/token bookkeeping, or triggering compliance workflows (GDPR redact) against the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Requires the attacker to have legitimately received at least one webhook delivery for a shop they control from the same app (trivial for anyone who can install a free/dev version of the app), plus network access to POST to the app's public webhook endpoint with modified headers. No possession of `api_secret_key`, access tokens, or the target shop's credentials is required — only observation of one's own webhook traffic, which is routine for any developer testing an app. This is a realistic, low-effort attack path.

### Recommendation
Bind the identity fields into the signed payload before verifying: include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in `to_signable_string`, or otherwise verify these header values against a source Shopify signs (e.g., cross-check `shop-domain` against a shop known to be associated with the delivered `webhook_id`/subscription, or require the host app to validate `shop` independently before trusting `WebhookMetadata`). At minimum, document/require that `shop` and `topic` not be treated as authenticated unless additionally covered by the signature.

### Proof of Concept
1. App developer installs the target app on their own dev store `attacker.myshopify.com` and registers a webhook (e.g. `app/uninstalled`).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <hmac(raw_body, secret)>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `hmac` value.
4. Attacker POSTs the same `raw_body` to the app's webhook endpoint again, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`, keeping the same `hmac` header (still valid since `to_signable_string` only depends on `raw_body`):
```ruby
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => captured_hmac,   # unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request) # HMAC still validates; handler runs believing shop == "victim-shop.myshopify.com"
```
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `captured_raw_body` against the secret, and the handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, an identity the attacker never proved control over.
