## Title
Missing permission check on `CallDispatcher.dispatch` allows any unprivileged caller to drain funds left in the dispatcher - (`evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with **no caller restriction whatsoever** — it will execute an arbitrary attacker-supplied `Call[]` (arbitrary `to`, arbitrary `value`, arbitrary `data`) on behalf of the `CallDispatcher` contract for *any* `msg.sender`. This mirrors the Jenkins Blue Ocean class of bug (CWE‑862, GHSA‑5m4q‑x28v‑q6wp): an HTTP/RPC endpoint that should only be reachable by a trusted, privileged caller (there: Blue Ocean's own controller code; here: `IntentGatewayV2`/`IntentsBase`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleTokenUpgradeable`) is left open to any unauthenticated/unprivileged party, letting them force the contract to act against attacker-chosen targets. [1](#0-0) 

### Finding Description
`CallDispatcher` is a shared periphery contract, one instance deployed per app (see `evm/script/DeployWrappedHFT.s.sol`, `evm/tron/migrations/2_deploy_ismp.js`), that legitimate callers use as a temporary custodian while composing swaps/calldata during cross-chain flows:

- `IntentGatewayV2`/`IntentsBase._execute` and `placeOrder` transfer input/output tokens to the dispatcher, call `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` / `dispatch(order.output.call)`, then sweep only the *declared* `order.inputs`/`order.output.assets` tokens back out. [2](#0-1) [3](#0-2) 
- `WrappedHyperFungibleTokenUpgradeable.onAccept` unlocks tokens directly to the `CallDispatcher` address (when `to == CALL_DISPATCHER`) and then calls `dispatch(message.data)`. [4](#0-3) 

The docs explicitly acknowledge that the sweep is *not exhaustive*: only tokens named in `order.output.assets`/`order.inputs` are collected back; anything else the predispatch/postdispatch call produces (slippage residue, a token the swap incidentally touched, direct ETH sent to the dispatcher's `receive()`) is left sitting in the dispatcher's balance ("After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust ..."). [5](#0-4) 

Because `CallDispatcher.dispatch()` has **no `onlyOwner`/`onlyGateway`/`onlyHost` modifier and no caller allow-list**, any address — not just the app contracts that are supposed to own that residual dust — can call it directly with a crafted `Call[]` (e.g., `IERC20.transfer(attacker, balanceOf(dispatcher))` or a plain native-value transfer) and steal any balance currently held by the dispatcher, including protocol/user dust, or funds sent to it by mistake via its open `receive()`. [6](#0-5) 

### Impact Explanation
Any solver, relayer, or unrelated third party watching chain state can permissionlessly sweep any ERC-20/native balance that legitimately accumulates in a `CallDispatcher` instance as part of normal intent-gateway/HFT operation (unswept dust, slippage residue, stray transfers). This is concrete theft of funds that otherwise belong to users/the protocol (per the documented dust-collection accounting), satisfying the "concrete theft ... of funds" bar. The severity is Medium because the amounts at risk are bounded to whatever dust/residual balance accumulates in a given `CallDispatcher` instance rather than the full escrowed principal, but it is a genuine, unauthenticated drain path with no caller restriction at all — the exact CWE-862 pattern in the reference advisory.

### Likelihood Explanation
High reachability, low complexity: `dispatch()` takes no special preconditions, needs no proof, no relayer role, and no privileged key — it is a single unauthenticated call. Any intent solver, bandwidth purchaser, or arbitrary EOA that notices a nonzero balance at a known `CallDispatcher` address (addresses are published in deployment docs, e.g. `docs/content/developers/evm/contract-addresses/*.mdx`) can drain it instantly with a single transaction.

### Recommendation
Add an explicit caller check to `CallDispatcher.dispatch` restricting it to the contract(s) that are meant to own/orchestrate it (e.g., an immutable `owner`/`gateway` address set at construction, checked with a `restrict`/`onlyOwner`-style modifier), analogous to the `restrict`/`onlyHost` patterns already used elsewhere in the codebase (`EvmHost.restrict`, `HyperApp.onlyHost`). Alternatively, make `CallDispatcher` non-custodial across transactions by sweeping the dispatcher's *entire* balance of any token touched (not just the declared input/output token set) back to the caller at the end of every `dispatch()` invocation, so no residual balance can ever persist between transactions. [7](#0-6) [8](#0-7) 

### Proof of Concept
1. A user places an order on `IntentGatewayV2` whose `predispatch.call` performs a DEX swap that (due to slippage or an intermediate hop token) leaves 5 USDT sitting on the `CallDispatcher` instance after the declared `order.inputs` tokens are swept back to the gateway in `placeOrder`. [9](#0-8) 
2. That 5 USDT is never referenced by `order.inputs`/`order.output.assets`, so no later transaction ever sweeps it — it simply sits at `CallDispatcher`'s address.
3. Any external account calls `CallDispatcher.dispatch(abi.encode([Call({to: USDT, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 5e6)})]))` directly. Since `dispatch()` has no caller restriction, the call succeeds and the 5 USDT is transferred to the attacker, even though the attacker had no relationship to the order that generated the dust. [1](#0-0)

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

```text
### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
```
