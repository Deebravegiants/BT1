### Title
Swap-route-controlled contracts can add unrelated token thefts to the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategies accept caller-supplied swap routes and execute them through the configured router without constraining which venue contract the route names. [1](#0-0) [2](#0-1)  A malicious route venue can therefore run while the account owner's authorization context is active and request an unrelated `token.transfer(owner, attacker, amount)`; Soroban records that transfer as a child invocation and executes it if the wallet signs the simulated authorization tree. [3](#0-2) [4](#0-3) 

### Finding Description
`swap_collateral` authorizes the caller, verifies account ownership, withdraws the selected collateral, and forwards the caller-controlled `swap` bytes into `withdraw_and_swap_from_supply`. [5](#0-4) [1](#0-0)  `swap_tokens` grants only one exact controller-to-router input transfer, but then invokes `router.execute_strategy` with that opaque payload. [6](#0-5) 

The router decodes caller-provided operations and dispatches each hop to the pool address embedded in the payload. [7](#0-6) [8](#0-7)  The venue adapters invoke that route-selected contract; for example, the Aquarius adapter calls `hop.pool.swap`. [9](#0-8) 

The controller’s `RouterOverspend` and `NoSwapOutput` checks only measure the controller’s input and output balances; they do not prevent a nested venue from asking the account owner for unrelated authorization. [10](#0-9)  The focused test demonstrates that a route-selected contract can call `transfer(victim, attacker, amount)` on a token that is not part of the lending market. [11](#0-10) 

In recording mode, that unrelated transfer is attached beneath the caller’s `swap_collateral` authorization, and the transaction succeeds with the unrelated-token balance moved to the attacker. [12](#0-11)  In enforcing mode, the honest authorization tree rejects the theft, while signing the poisoned child permits it. [13](#0-12) 

### Impact Explanation
An attacker can drain an arbitrary unrelated token held by the account owner, in addition to receiving a valid swap output that lets the lending operation complete normally. [14](#0-13) [15](#0-14)  The stolen amount is bounded by the victim’s balance and willingness to sign the returned authorization tree, not by `amount_in`, `min_out`, health factor, or any controller balance check. [16](#0-15) 

### Likelihood Explanation
Any unprivileged user can supply route bytes to `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral`, and the attacker only needs to get the victim to submit a transaction containing the malicious route. [17](#0-16) [18](#0-17)  Exploitation requires the victim’s wallet or client to sign the simulated tree containing the extra transfer, so it is not a silent authorization bypass. [19](#0-18)  Because the resulting loss can include assets unrelated to the protocol and the signed tree may be difficult for users to audit, this is a High-impact user-fund theft path. [20](#0-19) 

### Recommendation
Do not let caller-controlled routes name arbitrary executable venue contracts. [21](#0-20)  Constrain every hop to protocol-approved venue implementations or immutable pool addresses, and reject any route that can introduce an authorization child beyond the expected token transfer. [22](#0-21) [23](#0-22)  Until that is enforced on-chain, clients must decode route bytes and refuse any authorization tree containing unexpected children. [24](#0-23) 

### Proof of Concept
The repository contains a regression test for this path. [25](#0-24) 

1. Alice owns a lending account with USDC collateral and also holds an unrelated `wallet_token`. [26](#0-25) 
2. The attacker deploys `RogueHopPool`, storing `(victim, wallet_token, attacker, amount)`. [27](#0-26) 
3. The attacker crafts route bytes naming that pool and gives them to Alice as the `swap` argument for `swap_collateral`. [28](#0-27) 
4. During the swap, the rogue pool invokes `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`. [4](#0-3) 
5. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization. [29](#0-28) 
6. If Alice signs the poisoned tree, her entire unrelated-token balance moves to the attacker while her collateral swap still succeeds. [30](#0-29)

```rust
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
```

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
