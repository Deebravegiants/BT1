### Title
Unrestricted outbound HTTP fetch of user-registered workflow artifact URLs enables SSRF - (File: core/services/workflows/syncer/v2/fetcher.go)

### Summary
Workflows in the Workflow Registry are registered on-chain by workflow owners/authorized addresses via `UpsertWorkflow`, supplying arbitrary `binaryURL`/`configURL` strings [1](#0-0) . When a `WorkflowRegistered`/`WorkflowActivated` event is processed, the node calls `createWorkflowSpec`, which passes these attacker/user-supplied URLs straight into `FetchWorkflowArtifacts` without validating that they point to a public/safe host [2](#0-1) [3](#0-2) . Depending on node configuration, these URLs are fetched by `newHTTPFetcher`, a plain `http.Client` with no restriction on private/internal IP ranges, unlike the pipeline `HTTPTask`, which explicitly wraps its client with `clhttp.NewRestrictedClient`/`safeurl` to block "local/private and multicast networks" [4](#0-3) [5](#0-4) .

### Finding Description
This is the same bug class as CVE-2024-39687 (Fedify SSRF): resource identifiers embedded in remotely-supplied objects (there, ActivityPub `@id`/media URLs; here, on-chain `BinaryURL`/`ConfigURL`) are fetched by the node without first validating that the resolved address is a public, non-internal IP.

The relevant flow:
1. Any address authorized to call `UpsertWorkflow` on the `WorkflowRegistry` contract supplies `binaryURL`/`configURL` as free-form strings; the contract performs no validation on these values [6](#0-5) .
2. The syncer/event handler decodes the on-chain event into a `WorkflowRegisteredEvent` and calls `createWorkflowSpec`, forwarding `payload.BinaryURL`/`payload.ConfigURL` unchanged to `FetchWorkflowArtifacts` [7](#0-6) .
3. `FetchWorkflowArtifacts` only special-cases URLs matching the configured `ArtifactStorageHost` (using a signed-URL retrieval flow); any other host is passed directly to `h.fetchFn` as the `ghcapabilities.Request.URL` [8](#0-7) .
4. If the fetcher is configured via `NewFetcherFunc` with an `http`/`https` base URL (bypassing the gateway), the resulting `newHTTPFetcher` builds a request by joining the base URL path with a user-controlled path fragment and performs a GET using a bare `http.Client{Timeout: 30 * time.Second}` — with no IP/host allowlisting, no scheme restriction beyond http/https, and no blocking of internal/private/loopback/link-local addresses (e.g. cloud metadata `169.254.169.254`) [9](#0-8) .

By contrast, the gateway-mediated path (`FetcherService.Fetch` → `OutgoingConnectorHandler.HandleSingleNodeRequest` → gateway's `network/httpclient.go`) does apply `AllowedPorts`/`AllowedSchemes`/`safeurl`-based internal-IP blocking [10](#0-9) , and the node's classic HTTP pipeline task (`task.http.go`) also defaults to a restricted client that blocks local/private networks unless `allowUnrestrictedNetworkAccess=true` is explicitly set [11](#0-10) . The `newHTTPFetcher` path used by the workflow syncer has no equivalent safeguard.

### Impact Explanation
If a node is configured to fetch workflow artifacts via the direct HTTP fetcher path (bypassing the gateway), a workflow owner (an unprivileged, non-operator on-chain actor once authorized to register workflows) can register a workflow whose `BinaryURL`/`ConfigURL` points at an internal service, localhost, or a cloud metadata endpoint. The node will issue an outbound GET request to that address and treat the response body as workflow binary/config data, which is then base64-decoded and stored/executed. This can leak information about internal-only services (via response content/errors), probe internal network topology, or under certain conditions have the internal response misinterpreted as valid workflow content. This maps to a concrete SSRF/request-forgery pattern per the report's bug class, matching CWE-918.

### Likelihood Explanation
Exploitability depends on deployment: it requires (a) the node operator to configure `NewFetcherFunc` with a direct `http`/`https` base URL instead of routing through the gateway's `FetcherService.Fetch` (the code explicitly supports and tests both paths), and (b) an actor able to register/activate a workflow with an attacker-chosen `BinaryURL`/`ConfigURL` (workflow registration is gated by on-chain authorization/allowlisting in `WorkflowRegistry`, not by node-operator trust). Given the fetcher function offers no internal-IP protection regardless of configuration, and workflow URLs are fully attacker/owner-controlled strings validated only against a single storage host, likelihood is moderate.

### Recommendation
Apply the same SSRF protections used elsewhere in the codebase (`clhttp.NewRestrictedClient` / `safeurl`) to `newHTTPFetcher` in `core/services/workflows/syncer/v2/fetcher.go`, blocking requests to private, loopback, link-local, and other non-public IP ranges by default, and enforce scheme/port allowlists consistent with `core/services/gateway/network/httpclient.go`. Ensure `FetchWorkflowArtifacts` validates `binaryURL`/`configURL` hosts (not just matching `ArtifactStorageHost`) before dispatching to any fetcher implementation.

### Proof of Concept
1. Configure a node's workflow syncer with `NewFetcherFunc("http://<base>", lggr)` (non-gateway direct HTTP fetch path).
2. As an authorized workflow owner, call `UpsertWorkflow` on the `WorkflowRegistry` contract with `BinaryURL` set to an internal address, e.g. `http://169.254.169.254/latest/meta-data/` or `http://localhost:6060/debug/pprof`, and an arbitrary `ConfigURL`.
3. Once the syncer processes the `WorkflowRegistered`/`WorkflowActivated` event, `createWorkflowSpec` → `FetchWorkflowArtifacts` → `newHTTPFetcher` issues an unrestricted GET to the attacker-chosen internal URL, as shown by the lack of IP-safety checks in [9](#0-8) , contrasted with the explicit internal-network blocking present in the pipeline HTTP task test [12](#0-11) .

func newHTTPFetcher(baseURL string, lggr logger.Logger) types.FetcherFunc {
	client := &http.Client{
		Timeout: 30 * time.Second,
	}

	return func(ctx context.Context, messageID string, req ghcapabilities.Request) ([]byte, error) {
		// Clean the path to prevent directory traversal
		cleanPath := strings.TrimPrefix(filepath.Clean(req.URL), "/")

		// Join base URL with path
		u, err := url.Parse(baseURL)
		if err != nil {
			return nil, fmt.Errorf("failed to parse base URL: %w", err)
		}

		u.Path = filepath.Join(u.Path, cleanPath)
		fetchURL := u.String()

		lggr.Debugw("Fetching HTTP resource", "url", fetchURL, "workflowID", req.WorkflowID)

		req2, err := http.NewRequestWithContext(ctx, http.MethodGet, fetchURL, nil)
		if err != nil {
			return nil, fmt.Errorf("failed to create request: %w", err)
		}

		resp, err := client.Do(req2)
		if err != nil {
			return nil, fmt.Errorf("HTTP request failed: %w", err)
		}
