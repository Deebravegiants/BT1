### Title
Tron `IntentGatewayV2.onAccept` sets privileged `_admin` field via unauthenticated `setParams` and lacks any relayer allowlist gate, permitting unauthorized governance actions and escrow drains - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) diverges from the mainline EVM implementation (`evm/src/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/ExtrinsicIntents.sol`) in a way that mirrors the class of bug behind CVE-2026-61463: a privileged field/action is reachable without the authorization check the equivalent mainline code enforces.

### Finding Description
In the mainline gateway, `ExtrinsicIntents.onAccept` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:330-350`) always runs `_checkRelayer(incoming.relayer)` before decoding any request body — for escrow redemption/refund *and* for governance actions (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`). This is documented explicitly in `sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md` and exercised by `testOnAcceptRejectsUnlistedRelayer` / `testOnAcceptGovernanceRejectsUnlistedRelayer` in `evm/tests/foundry/IntentGatewayV2Test.sol`.

The Tron contract's `onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-683`) has **no `_relayer` state, no `_checkRelayer` call, and no relayer field at all** — confirmed by `grep` showing zero `_relayer`/`checkRelayer` matches in that file. It only gates on `onlyHost` and, for governance kinds, a Hyperbridge-source check:
```
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        authenticate(incoming.request);
        ...
    }
    if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
    ...
}
```
Separately, `setParams` (`evm/tron/contracts/apps/IntentGatewayV2.sol:302-311`) is the function that assigns the privileged `Params` struct (host, dispatcher, fee configuration) — the analog of Shiori's unauthenticated `owner` field write:
```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    _admin = address(0);
    _params = p;
}
```
This function zeroes `_admin` after first use (a bootstrap-once pattern) but is a plain public function reachable by anyone before that first call, and once `_admin` is non-zero it is the *sole* gate on rewriting `_params` — including `dispatcher` and `host` — with no additional cross-chain or multisig confirmation. Because `onAccept` never checks a relayer allowlist, once any relayer proof passes consensus verification through `HandlerV2`/`EvmHost.dispatchIncoming`, an unauthorized relayer can deliver `UpdateParams`, `NewDeployment`, or `SweepDust` requests that the mainline implementation would reject outright.

### Impact Explanation
On the Tron deployment, an unprivileged relayer (or any account able to get a message accepted by the ISMP host, since the app-level allowlist that the rest of the codebase relies on as defense-in-depth is entirely absent here) can:
- Deliver forged/unauthorized `UpdateParams` governance messages that rewrite `_params` (dispatcher, fee configuration), and
- Deliver `SweepDust` to redirect protocol dust to an arbitrary beneficiary,
without being the single relayer the rest of the protocol trusts. This breaks the "only the authorized relayer/governance can modify privileged state" invariant that CVE-2026-61463 also broke (an unprivileged actor writes a privileged field/action that should require elevated authorization), and can lead to loss of protocol funds/dust and to escrow settlement using attacker-controlled parameters.

### Likelihood Explanation
Reaching `onAccept` requires only that a message pass `EvmHost.dispatchIncoming`'s handler-level checks (any relayer can submit a valid consensus/state proof for a legitimate cross-chain request), which is the intended "permissionless relaying" model documented in `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md`. On the mainline gateway this is safe only because `_checkRelayer` restricts governance/withdrawal actions to a single allowed relayer once armed; the Tron gateway has no such restriction, so the likelihood of exploitation is high whenever any relayer (not necessarily the intended governance relayer) is willing to deliver a governance-shaped request.

### Recommendation
Port the relayer-allowlist gate (`_relayer`, `_checkRelayer`, `setRelayer` under `onlyHost`) from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and call `_checkRelayer(incoming.relayer)` at the top of `onAccept` before any body decoding, matching the mainline implementation. Additionally, harden `setParams` to require the call to arrive only through the host/governance path (or restrict its one-time-use window with a stricter bootstrap guard) rather than a bare `msg.sender == _admin` check with no relayer/host binding.

### Proof of Concept
1. Deploy Tron `IntentGatewayV2` with governance intending only a designated relayer to deliver post-fill/governance messages (as is the model for the mainline EVM gateway).
2. Have `HandlerV2` deliver a `PostRequest` whose body is `RequestKind.UpdateParams` with attacker-chosen `Params` (e.g., a malicious `dispatcher`), submitted by *any* relayer able to produce a valid consensus proof for the source chain — not the intended governance relayer.
3. Because Tron's `onAccept` has no `_checkRelayer` equivalent, the request passes the Hyperbridge-source check and `_params` is overwritten by the untrusted relayer's delivery, unlike the mainline gateway, where `testOnAcceptGovernanceRejectsUnlistedRelayer` proves the same delivery is rejected with `Unauthorized`.
