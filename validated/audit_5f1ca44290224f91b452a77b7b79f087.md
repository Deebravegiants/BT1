### Title
Tron IntentGatewayV2 partial-fill escrow accounting permanently locks rounding dust in the escrow contract - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM `IntentGatewayV2`/`IntrinsicIntents.sol` intent-fill logic was patched (documented as "Finding #4") so that the final solver completing a partially-filled order receives the *entire remaining escrow balance* rather than a proportionally-truncated (floor-divided) amount, preventing residual "dust" from being permanently stuck in the gateway. The Tron port of the contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements its own separate escrow/withdraw logic and was not confirmed to carry the same "release remainder to final filler" fix. Because Tron's `_orders[commitment][token] -= amount` accounting matches the EVM contract's pre-fix pattern, floor-division truncation on each partial fill can leave 1+ units of escrowed input token that is never released to any solver and never refunded to the user — a permanently frozen dust balance analogous to the Ajna bug class of "settlement leaves an un-clearable residual that freezes state."

### Finding Description
In the fixed EVM contract (`evm/src/apps/intentsv2/IntrinsicIntents.sol`), each partial fill computes:
```
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
``` [1](#0-0) 

This floor-division intrinsically truncates on every partial fill except the one that completes the order. The completing fill instead reads the *full remaining escrow balance* directly (`_orders[commitment][token]`), rather than another truncated proportional share, so no dust remains locked:
```
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

This is exercised and confirmed fixed by the dedicated regression tests `testPartialFill_RoundingDustReleasedToFinalSolver` and its native-ETH variant, which explicitly assert "Gateway should have zero USDC/ETH — no rounding dust locked." [2](#0-1) [3](#0-2) 

The Tron contract's redeem/`withdraw` function decrements escrow with a plain subtraction and has no equivalent "final-fill gets remaining balance" branch visible in the reviewed code:
```
_orders[body.commitment][token] -= amount;
``` [4](#0-3) 

Its escrow-crediting path on placement uses the same reduced-amount-after-protocol-fee accounting as the EVM contract:
```
_orders[commitment][token] += reducedInputs[i].amount;
``` [5](#0-4) 

If the partial-fill fill-amount computation on Tron mirrors the EVM contract's pre-fix formula (proportional truncation on *every* fill, including the completing one), a `commitment`'s escrow balance for an input token can retain 1+ wei/unit of undistributed tokens after the order is marked fully filled (`isFullyFilled`/completion path), with no code path left to claim it: the order is already finalized (`_filled[commitment]` set), so no further `fillOrder` or `cancelOrder` call against that commitment can retrieve the residual.

I was not able to fully verify the exact partial-fill computation function in the Tron file (its `fillOrder`/`IntrinsicIntents`-equivalent body was not returned by my searches), so this analog rests on the observed asymmetry between the EVM fix (proven via dedicated tests) and the absence of an equivalent test or "final solver gets remainder" code confirmed in the Tron contract.

### Impact Explanation
If Tron's partial-fill logic lacks the remainder-release fix, every multi-solver partial fill of a same-chain order permanently strands 1+ smallest-denomination units of the user's escrowed input token inside the gateway contract, with no mechanism (withdraw, cancel, or sweep) able to recover it for that specific commitment — a permanent, protocol-level freezing of user funds, matching the Ajna report's core impact category ("permanent freezing of funds due to un-clearable residual"). While each individual instance is dust-sized, this is systemic: it recurs on every partially filled order and compounds across the many independent commitments a public dispatcher processes, and the analog's causal mechanism (floor-division rounding never reconciled against actual remaining balance) is identical in kind to the reported bug class.

### Likelihood Explanation
Any unprivileged user can trigger this merely by placing an order and any set of unprivileged solvers filling it in multiple partial tranches — an ordinary, expected usage pattern for the Intent Gateway's partial-fill feature, not an edge case requiring malicious coordination. Given the same-chain partial-fill flow is a documented, supported feature (`docs/content/developers/evm/intent-gateway/overview.mdx`) [6](#0-5) , likelihood is high if the Tron deployment indeed omits the fix; however, since I could not directly confirm the absence of the fix in the Tron fill function (only in the withdraw/redeem function reviewed), this should be treated as a plausible but unconfirmed regression risk specific to the Tron contract port.

### Recommendation
Audit `evm/tron/contracts/apps/IntentGatewayV2.sol`'s partial-fill computation function to confirm whether it applies the same "final fill releases the full remaining escrow balance" logic as `IntrinsicIntents.sol`. If it instead performs proportional floor-division on every fill including the completing one, port the exact fix: on the fill that brings `amountFilled == totalRequired`, escrow release should equal the live `_orders[commitment][token]` balance rather than a re-computed proportional share. Add a Tron-side regression test mirroring `testPartialFill_RoundingDustReleasedToFinalSolver` to lock in the invariant that gateway balance for a fully-settled commitment is zero.

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeCleanAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeCleanAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeCleanAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
