### Title
IR-Net capture accepts single physical eye into both left_ir/right_ir slots with only a timing heuristic as defense - ([File: src/plans/biometric_capture/mod.rs])

### Finding Description
`Plan::handle_ir_net` gates frame acceptance solely on `estimate.perceived_side` matching `self.target_left_eye`, then stores the frame into `self.left_ir` or `self.right_ir` accordingly: [1](#0-0) [2](#0-1) 

`perceived_side` is a model-derived classification of which eye is presented, not a geometric or cryptographic proof of iris identity/distinctness — there is no comparison of iris texture, gaze geometry, or any embedding distance between what lands in `left_ir` and `right_ir`. The only temporal control is `self.valid_capture_after`, gated by `delay_between_eye_captures` (default `DEFAULT_DELAY_BETWEEN_EYE_CAPTURES` from `src/consts.rs`), which enforces a minimum time delay before a new valid capture is accepted, and `self.target_left_eye`, which is toggled between objectives by the orchestrating plan logic (`Plan::objectives` / `set_next_objective` flow). Neither of these mechanisms establishes that the frames placed in `left_ir` and `right_ir` correspond to two distinct physical eyes — they only ensure temporal spacing and that the IR-Net model's own left/right side classification differs between the two accepted frames.

Because `perceived_side` is a perception output on attacker-controlled visual input (the scene presented to the camera), an attacker who can reposition a single eye (or a printed/replayed image) between the two "sides" within the objective loop, while satisfying the timing delay and the `IRIS_SCORE_MIN`/brightness/sharpness thresholds, can cause the same physical eye's IR frame data to be independently classified as "left" in one objective and "right" in the other, populating both slots without any cross-check for distinctness.

### Impact Explanation
If exploitable, this would allow a single iris to be captured and stored/processed as if two independent eyes had been presented, feeding into downstream iris-code generation and signature. This maps to a liveness/fraud bypass finding, since the "two distinct eyes" assumption is a fraud/liveness-adjacent invariant. However, this is a heuristic weakness in the model-perception layer, not a hard authorization break — it does not directly forge a signature, bind a wrong identity to another user's account, or achieve unauthorized signup on its own, since the actual anti-fraud/liveness enforcement (if present) may exist further downstream in the pipeline (e.g., backend-side iris uniqueness checks, `biometric_pipeline`, or signature/backend validation) which was not confirmed to be absent in this file and was not fully traceable within the current investigation.

### Likelihood Explanation
Feasibility is plausible in principle: an attacker with physical/visual control over the presented scene (a single eye or a photo moved between positions) is within the unprivileged threat model described. Repeatability depends on: (1) the IR-Net model's `perceived_side` classifier being fooled or genuinely alternating for the same physical eye under repositioning, and (2) satisfying `IRIS_SCORE_MIN`, brightness range, and sharpness gates for both "sides" using the same eye. This has non-trivial preconditions (model behavior under adversarial repositioning is not verified here) and was not confirmed against any downstream distinctness check that might exist in `biometric_pipeline` or backend iris-uniqueness logic, which limits certainty about full exploitability.

### Recommendation
Add an explicit distinctness check between `left_ir` and `right_ir` captures beyond the `perceived_side` heuristic and timing delay — e.g., compare iris embeddings/codes for the two captured frames and reject the capture (or require re-capture) if they are found to represent the same iris, or incorporate simultaneous/paired stereo geometric verification (relative gaze/eye position consistency with the Orb's mirror/optics state) rather than relying solely on a per-frame ML classification of side.

### Proof of Concept
Integration test in `src/plans/biometric_capture/mod.rs` test module:
1. Construct `Plan` with `target_left_eye = true`, call `handle_ir_net` with a synthetic `ir_net::Output::Estimate` whose `perceived_side` corresponds to "left", a `camera::ir::Frame` `F`, and score/brightness passing thresholds; advance clock past `delay_between_eye_captures`.
2. Toggle `target_left_eye = false`, call `handle_ir_net` again with the same frame `F` and an estimate whose `perceived_side` corresponds to "right" (simulating the same physical eye being reclassified), after again satisfying `valid_capture_after`.
3. Assert `plan.left_ir.unwrap().frame == plan.right_ir.unwrap().frame` (or equivalent content equality), demonstrating both slots were populated from identical frame data with no distinctness check rejecting it.

Note: full confirmation of end-to-end exploit impact (i.e., whether downstream code such as `biometric_pipeline` or backend enforces iris uniqueness before finalizing a signup) could not be completed within this investigation and should be verified separately before treating this as a critical, fully realized vulnerability.
