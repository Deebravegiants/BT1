### Title
Unbacked cross-chain mint due to fee-on-transfer token accounting mismatch in `WrappedHyperFungibleToken.send()` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin) locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but dispatches the cross-chain message with the caller-specified `params.amount`, not the amount actually received by the contract. If the underlying token charges a transfer fee (fee-on-transfer/FOT), the wrapper receives less than `params.amount`, yet the destination `HyperFungibleToken` mints the full `params.amount` to the recipient, creating unbacked supply.

### Finding Description
In `send()`, the underlying token is pulled with `safeTransferFrom`, and the dispatched `Message.amount` is built directly from `params.amount` in `_buildDispatchPost`, independent of the actual token balance change: [2](#0-1) [3](#0-2) 

On the destination chain, `HyperFungibleToken.onAccept` mints exactly `message.amount` to the beneficiary, with no cross-check against any locked collateral: [4](#0-3) 

For a FOT underlying token, this means every `send()` call locks `params.amount - fee` in the wrapper but mints the full `params.amount` on the remote chain — a permanent shortfall between the wrapper's actual token balance and the total cross-chain-circulating claim on it. This is the same bug class as the Sherlock report (`BufferBinaryPool` using nominal transfer amount instead of balance delta for accounting), and the codebase's own `IntentGatewayV2.placeOrder` demonstrates the correct fix pattern (measure `balanceOf` before/after and use the delta), which was applied there but not to `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`.

The identical pattern exists in `send()` of the upgradeable variant: [5](#0-4) 

### Impact Explanation
Each FOT `send()` call inflates the total cross-chain-minted supply beyond what's actually locked in the home-chain wrapper. Over repeated transfers, the deficit accumulates. When holders eventually redeem minted tokens back through the wrapper (`onAccept` on the wrapper side calling `safeTransfer(beneficiary, message.amount)`), later redemptions will fail once the wrapper's actual underlying balance is exhausted below the cumulative claims, since `safeTransfer` will revert on insufficient balance: [6](#0-5) 
This causes permanent freezing of funds for the affected users (their tokens already burned on the remote chain, with no valid underlying to unlock), and effectively an unbacked mint condition on the remote-chain token, both explicitly in-scope high-impact outcomes.

### Likelihood Explanation
Reachable by any unprivileged user via a single call to the public `send()` function, requiring only that the deployer/owner has configured the wrapper's `_underlying` to a fee-on-transfer ERC20 (a real and increasingly common token category, exactly the concern raised in the source report). No privileged action or governance compromise is needed to trigger the accounting drift — only a normal `send()` transaction on an FOT-underlying deployment.

### Recommendation
Mirror the fix already used in `IntentGatewayV2.placeOrder`: measure the wrapper's `balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual received delta as `params.amount` (or as the value encoded into the dispatched `Message`), rather than trusting the caller-supplied `params.amount` directly.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to an ERC20 that takes, e.g., a 1% fee on transfer.
2. User calls `send({..., amount: 1000e18, ...})`. `safeTransferFrom` pulls 1000e18 nominally, but the wrapper's balance only increases by 990e18 (1% fee retained by the token).
3. `_buildDispatchPost` still encodes `amount: 1000e18` into the `Message`, and this is what gets dispatched via ISMP.
4. On the destination chain, `HyperFungibleToken.onAccept` mints 1000e18 to the beneficiary — 10e18 more than what is actually backed by the wrapper's locked balance.
5. Repeating this pattern accumulates an unbacked supply gap; when enough remote-minted tokens are sent back for redemption, `WrappedHyperFungibleToken.onAccept`'s `safeTransfer` calls will begin reverting for lack of sufficient underlying balance, permanently freezing the corresponding cross-chain transfers.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
