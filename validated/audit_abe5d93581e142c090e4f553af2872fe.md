### Title
Creator fee payouts in FeeVault permanently freeze if `creator` is a smart contract that cannot call `claim()` - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` only ever pays out `creatorBalance[msg.sender]` to `msg.sender` itself — there is no way for anyone else to trigger a payout to a specific `creator` address. `Bonding.transferCreator()` lets the current creator (any unprivileged wallet) set the fee-attribution address for a launched token to **any** non-zero address, including a smart contract, with no check that the new address can actually initiate a call. If `creator` ends up being a contract with no function that forwards an arbitrary call to `FeeVault.claim()` (e.g. a vanity/counterfactual contract, a minimal proxy, or simply any contract deployed without a generic "execute" method), every future 0.25% creator fee accrued for that token becomes permanently unclaimable, exactly mirroring the M-18 pattern where `InfernalRiftAbove::claimRoyalties()` is gated to `msg.sender == receiver`.

### Finding Description
Fee accrual attributes creator fees by address, keyed off `Bonding.tokenInfo(token).creator`: [1](#0-0) 

`transferCreator` is fully permissionless from the current creator's perspective — it accepts any non-zero `newCreator` with no check that the address is an EOA or a contract capable of calling back into `FeeVault`: [2](#0-1) 

`FeeVault.claim()` is the *only* path to withdraw a creator's pooled balance, and it is hard-wired to pay `msg.sender`, not an explicit `creator` argument: [3](#0-2) 

Unlike `claimProtocol()` (permissionless, always pays the admin-set `feeTo` regardless of caller) and `sweepDonations()`, there is no permissionless variant of `claim()` that lets a third party push the creator's balance to the `creator` address on their behalf: [4](#0-3) 

If `creator` is set (either at launch, via `Bonding.launch(params, creator_)` called from `Zap.createToken` with `msg.sender`, or later via `transferCreator`) to a smart contract that has no mechanism to originate a call to `FeeVault.claim()` — e.g. a Safe/module not yet deployed, a vanity CREATE2 address squatted before deployment, a minimal contract with no fallback/execute function, or even `Bonding`/`Pair`/`Token`/`Zap` themselves — the accrued `creatorBalance[creator]` in `FeeVault` can never be withdrawn, since only that exact address calling `claim()` directly can trigger the transfer: [5](#0-4) [6](#0-5) 

### Impact Explanation
Every buy and sell against the token accrues 0.25% of the 0.75% protocol fee to `creatorBalance[creator]`, per the documented split: [7](#0-6) 

If `creator` is a smart contract that cannot call `claim()`, this balance grows indefinitely and is permanently frozen inside `FeeVault` — real USDC funds are locked with no recovery path, since `claim()` is the sole withdrawal route and there is no owner/admin override to redirect a stuck creator balance. This is a direct freezing-of-funds impact scaled by the token's full trading lifetime (both pre- and post-graduation, since the fee applies on both venues).

### Likelihood Explanation
Any unprivileged token creator can trigger this unintentionally or maliciously:
- Launching a token with `Zap.createToken` where `msg.sender` is itself a smart contract (e.g. a multisig, a vault, a not-yet-deployed CREATE2 address) that lacks a generic call-forwarding function.
- Calling `Bonding.transferCreator(tokenAddress, newCreator)` — callable by the current creator with zero validation on `newCreator` beyond non-zero — to move attribution to any contract address, including one deliberately chosen to be unable to call back (e.g. a burn-style address, a simple ERC20/Token clone, or the `Pair`/`Bonding`/`Zap` contract addresses themselves, none of which have any function that calls `FeeVault.claim()`).

No special privileges, timing, or external state are required — this is reachable by any user in a single transaction.

### Recommendation
Add a permissionless payout path analogous to `claimProtocol()`/`sweepDonations()` that lets anybody push a specific `creator`'s balance to that `creator` address (e.g. `claimFor(address creator)` that transfers `creatorBalance[creator]` to `creator` regardless of `msg.sender`), so a smart-contract creator without call-forwarding capability can still receive its accrued fees.

### Proof of Concept
1. Attacker (or any user) deploys a minimal contract `StuckCreator` with no fallback and no function that calls `FeeVault.claim()`.
2. Attacker calls `Zap.createToken(params, seedUsdcAmount)` from `StuckCreator` (or, for an existing token, the current creator calls `Bonding.transferCreator(tokenAddress, address(StuckCreator))`), setting `tokenInfo[tokenAddr].creator = address(StuckCreator)`.
3. Normal trading proceeds: every `Zap.buy`/`Zap.sell` call accrues 0.25% of the fee to `feeVault.creatorBalance(address(StuckCreator))` via `_accrueFee`.
4. `address(StuckCreator)` never calls `FeeVault.claim()` (it has no way to), so the balance is permanently stuck — no other address, including the protocol owner, can withdraw it via `FeeVault.claim()`, since it strictly requires `msg.sender == creator`.

```text
        address tokenAddress,
```

```text
    function claimProtocol() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.protocolBalance;
        if (amount == 0) revert NothingToClaim();
        $.protocolBalance = 0;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit ProtocolFeesClaimed(feeTo_, amount);
    }

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
```

```markdown
## Fees & FeeVault

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
```
