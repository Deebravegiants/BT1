### Title
Non-atomic two-step write in `withFilesystemFallback().set` can leave a placeholder pointing to no backing file on filesystem write failure - (File: adapters/storage-mobile/src/helpers/with-filesystem-fallback.ts)

### Summary
When a value's stringified payload exceeds `threshold`, `set()` first writes a placeholder (`'~'`) to the primary `storage`, then writes the real payload to the filesystem via `filesystemStorage.setString`. These two writes are not atomic and there is no rollback or retry: if the filesystem write fails after the placeholder write succeeds, `get()` will thereafter believe data exists (placeholder present) but resolve to `undefined` because the backing file was never created.

### Finding Description
In `set` [1](#0-0) , when `stringifiedPayload.length > threshold`, the code does:
1. `await storage.set(key, placeholder as never)` — commits the placeholder to the primary (e.g. AsyncStorage-backed) store.
2. `await filesystemStorage.setString(key, stringifiedPayload)` — writes the real payload to disk via `filesystem.writeUtf8`.

If step 2 throws (e.g. transient filesystem error, disk full, permission failure, forced kill between the two awaits), the function rejects, but step 1's effect is already durably persisted. There is no try/catch, no rollback of the placeholder, and no retry logic.

On the next `get(key)` call [2](#0-1) , `storage.get(key)` returns the placeholder, so the code delegates to `filesystemStorage.get(key)`. Since the file was never written, `filesystem.readUtf8` throws, which is caught internally in `FilesystemStorage.get` [3](#0-2)  and swallowed, silently returning `undefined`. There is no signal to the caller that this represents a lost/corrupted write versus a legitimately absent key — both look identical (`undefined`).

This is reachable whenever a large value (e.g. a multi-seed backup blob or large imported/restored payload) is persisted through this adapter (used for `androidFallback` in `createStorageMobile`, see [4](#0-3) ) and the filesystem write fails after the placeholder commit.

### Impact Explanation
The scoped impact is silent loss of a large persisted value with no error surfaced to the caller — `get(key)` returns `undefined` indistinguishably from "key never set." If this storage path backs sensitive data such as wallet seed/backup material that exceeds the size threshold, an application built atop this storage could interpret the `undefined` result as "seed not found," which per the question's framing could trigger unintended downstream behavior (e.g. re-import/re-creation flows) in code that consumes this storage layer. Note: within this repository/package itself, there is no evidence of such downstream "seed not found → recreate" logic; that consequence depends on how a higher-level consumer interprets `undefined`, which is outside this file's scope.

### Likelihood Explanation
Preconditions are plausible: `threshold` (default ~1.9MB in `index.android.ts` [5](#0-4) ) can be crossed by sufficiently large imported data, and `filesystem.writeUtf8` (backed by `@exodus/react-native-fs`) can transiently fail for ordinary reasons (low disk space, OS-level I/O errors, app killed mid-write, permission issues) without any attacker privilege needed. The bug is deterministic given the described failure injection and is reproducible in a unit test with a mocked filesystem.

### Recommendation
Make the two-step write atomic/consistent: e.g. write the file to the filesystem first and only commit the placeholder to `storage` after `filesystemStorage.setString` succeeds; or wrap both writes in a try/catch that rolls back the placeholder write (or the prior value) if the filesystem write fails, and propagate/log the error rather than allowing a partially-committed state. Additionally, `FilesystemStorage.get`'s catch-and-return-`undefined` behavior should be reconsidered so that a "placeholder present but file missing" state can be distinguished from "key absent," e.g. by re-throwing on read errors rather than silently masking them for keys known to be flagged via the placeholder.

### Proof of Concept
Integration test in `adapters/storage-mobile/test/`:
1. Construct `withFilesystemFallback` with a real/spy `storage` and a `filesystem` mock whose `writeUtf8` resolves normally the first N calls but rejects on the call corresponding to the fallback body write (or simply always rejects for `setString`).
2. Call `set('key', largeValueExceedingThreshold)` and expect it to reject (current behavior).
3. Call `get('key')` afterward and assert: currently returns `undefined` (masking the failure) even though `storage.get('key')` reports the placeholder `'~'`.
4. Expected fix behavior: either `get('key')` should never return `undefined` for a key whose primary store holds the placeholder without a valid file (should surface an error/inconsistent state), or `set` should ensure that if `filesystemStorage.setString` fails, `storage`'s value is rolled back to its pre-write state (so `get` correctly reflects "not set" / previous value) — assert whichever consistent contract is chosen.
