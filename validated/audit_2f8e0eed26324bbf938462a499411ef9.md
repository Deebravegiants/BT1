### Title
Unwrap-panic DoS in `calc_take_pnl` from decimal-normalization rounding mismatch permanently freezes pool funds - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` is called by every unprivileged `Deposit`, `Withdraw`, and `WithdrawPnl` instruction to rebalance the AMM's tracked PnL baseline (`TargetOrders.calc_pnl_x` / `calc_pnl_y`) against the pool's live token-vault balances [1](#0-0) . The function performs an invariant guard using **un-normalized native-unit amounts**, but then performs the actual x2/y2 recomputation using **sys_decimal-normalized** amounts, and unconditionally `unwrap()`s the resulting subtraction [2](#0-1) . A scale/rounding mismatch between these two representations can make the computed `x2` exceed `x1` (or `y2` exceed `y1`) even though the native-unit guard passed, causing `x1.checked_sub(x2).unwrap()` to panic and abort the transaction.

### Finding Description
The guard at `program/src/processor.rs:190-192` compares `pool_pc_amount * pool_coin_amount` against `calc_pc_amount * calc_coin_amount`, both expressed in native token-vault units (post `restore_decimal`) [3](#0-2) . Immediately after, `calc_x_power` and the subsequent `integer_sqrt()`/subtraction are performed with `x1`/`y1`, which are the **sys_decimal-normalized** pool amounts computed via `Calculator::normalize_decimal_v2` in the callers, not the native amounts used in the guard [4](#0-3) . `normalize_decimal_v2`/`restore_decimal` perform integer (floor) division when coin/pc decimals differ from `sys_decimal_value`, so native-unit comparisons and normalized-unit comparisons are not guaranteed to preserve the same ordering across every rounding boundary [5](#0-4) . When the invariant guard passes on the native scale but rounding makes `x2 = sqrt(x_power)` exceed `x1` on the normalized scale, the line `let diff_x = U128::from(x1.checked_sub(x2).unwrap().as_u128());` panics [6](#0-5) . Because `TargetOrders.calc_pnl_x`/`calc_pnl_y` are persisted on-chain state that isn't mutated on a failed/reverted transaction, once the pool's live ratio drifts (through ordinary swap/deposit/withdraw activity, which any unprivileged trader/LP can drive) into the triggering region, **every subsequent** `Deposit`, `Withdraw`, and `WithdrawPnl` call for that pool will hit the same panic path and revert, since none of them can make progress to correct the stored baseline.

### Impact Explanation
This is a permanent denial-of-service of a specific AMM pool: LPs can no longer withdraw or deposit, and the privileged PnL owner can no longer call `process_withdrawpnl`, effectively freezing both LP and PnL-owner funds in that pool with no recovery path through the on-chain instructions. This matches the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Reaching the exact rounding-boundary condition requires a specific relationship between the pool's decimal configuration (`pc_decimals`, `coin_decimals`, `sys_decimal_value`) and the drift between the live vault ratio and the stored `calc_pnl_x`/`calc_pnl_y` baseline. This drift accumulates naturally from ordinary swap activity (no privileged access needed), but pinpointing the precise trigger requires numeric analysis specific to a pool's decimals/liquidity; it is not trivially forced in a single crafted transaction the way a direct overflow would be. Likelihood is therefore moderate rather than trivial.

### Recommendation
Replace the `unwrap()` calls in `calc_take_pnl` around the `x1.checked_sub(x2)` / `y1.checked_sub(y2)` computations with saturating or checked operations that fall back to a safe no-op (skip PnL taking) instead of panicking, and ensure the invariant guard at lines 190-192 uses the **same unit scale** (either both native or both normalized) as the subsequent `calc_x_power`/sqrt computation so the guard actually prevents `x2 > x1` before the subtraction is attempted.

### Proof of Concept
Conceptual trigger (cannot be fully deterministic without live decimal/liquidity parameters, but the code path is directly reachable):
1. Create a pool with `pc_decimals` and `coin_decimals` values that differ non-trivially from `sys_decimal_value`'s scale (e.g., 6 vs 9), so `normalize_decimal_v2`/`restore_decimal` floor-round differently depending on direction.
2. Perform ordinary swaps to drift the live vault ratio relative to the stored `calc_pnl_x`/`calc_pnl_y` baseline near a rounding boundary where native-scale `pool_pc*pool_coin >= calc_pc*calc_coin` holds but normalized-scale `x2 = sqrt(calc_pnl_x*calc_pnl_y*x1/y1) > x1`.
3. Call `Deposit` or `Withdraw`; `calc_take_pnl` is invoked (`program/src/processor.rs:1166` / `1741`), hits `x1.checked_sub(x2).unwrap()` at line 213, and panics, aborting the transaction.
4. Because state is unchanged on abort, every future `Deposit`/`Withdraw`/`WithdrawPnl` call against this pool reproduces the same panic, permanently freezing the pool.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
