### Title
Emporium `runAction` lets `erc20TokenAddresses` omit `address(0)` (or be empty), so `EmporiumOperation.value` (native ETH) leaves the contract with zero balance accounting and no offsetting UTXO — ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` computes `balancesBefore`/`balancesAfter` and the final `BalanceChangeShouldBePositive`/UTXO-minting loop strictly over `circomData.erc20TokenAddresses`. Nothing in `dimensionsCheck`, the circuit's `distinctErc20AddressChecks`, or `runAction` forces `address(0)` to be a member of that array, so an attacker can submit a proof whose `erc20TokenAddresses` excludes (or is entirely empty of) `address(0)` while still including a stateless `EmporiumOperation` that sends real ETH (`op.value`) to an attacker-controlled endpoint.

### Finding Description
The equality the contract is supposed to preserve is:
`sum over i in erc20TokenAddresses of (balancesAfter[i]-balancesBefore[i] adjusted by deltaAmountChanges[i]) == total real balance change of EmporiumUpgradeable`.

This equality only holds if every asset that can leave the contract (including native ETH moved via `op.value`) has a slot `i` in `erc20TokenAddresses`. Nothing enforces this:

- `dimensionsCheck` (`contracts/HinkalHelper.sol`) only checks that `erc20TokenAddresses.length == dimensions.tokenNumber` and other array-length agreements; it never requires `address(0)` to be present, and `tokenNumber` can legally be `0`. [1](#0-0) 
- The circuit's only cross-token constraint (`distinctErc20AddressChecks`) enforces that listed token addresses are pairwise distinct — it never requires `address(0)` to be one of them. [2](#0-1) 
- `CircomDataBuilder.formInputForCircom` explicitly special-cases `erc20TokenAddresses.length == 0` for the Emporium action, using `formInputEmporiumMin`, which builds a public-input vector containing only `emporiumMessage`, `timeStamp`, and `calldataHash` — i.e., a fully valid, legitimately-provable "no token" mode exists. [3](#0-2) 
- In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` and the `BalanceChangeShouldBePositive` / UTXO-minting loop iterate only over `circomData.erc20TokenAddresses`. [4](#0-3) [5](#0-4) 
- The stateless-call branch performs `op.endpoint.call{value: op.value}(op.callData)` with attacker-controlled `endpoint`, `value`, and `callData`, gated only by a selector blacklist (`callHinkalWallet`/`doSendToRelay`) — nothing ties `op.value` to any tracked balance slot. [6](#0-5) 
- `verifyWallet` performs no signature check at all when `stack.signerAddress == address(0)` (only nonce/`usedMessages` tracking), so an attacker can fully self-author the `EmporiumStack` (including malicious `ops`) without needing anyone else's signature. [7](#0-6) 
- Upstream in `Hinkal.transact`, the top-level per-token `balanceDif`/slippage/UTXO-sum checks (the only other place ETH is normally reconciled, including the special `address(0)` `msg.value` adjustment) are also indexed by `circomData.erc20TokenAddresses` and thus are `0` iterations if that array excludes/omits ETH. [8](#0-7) 

Attacker's exact call: submit `Hinkal.transact(a,b,c,dimensions,circomData)` where `dimensions.tokenNumber` is `0` (or `>0` but never includes `address(0)`), `circomData.externalActionData.externalActionId` = Emporium's action id, and `externalActionMetadata` encodes an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{endpoint: attackerContract, invokeWallet: false, value: X, callData: anything not colliding with the two blacklisted selectors}`. Because `erc20TokenAddresses` is empty/omits `address(0)`, none of `dimensionsCheck`, the circuit's distinctness check, `Hinkal.transact`'s balance loop, or `EmporiumUpgradeable.runAction`'s balance loop ever observe or gate the ETH leaving Emporium's balance to `attackerContract`. The call succeeds, `X` wei leaves the contract, and no UTXO/commitment is ever created to represent it.

### Impact Explanation
Any real ETH resident in (or transiently routed through) `EmporiumUpgradeable` — e.g., left over from prior swap/unwrap operations, refunds from routers, or accidental direct sends via the contract's `receive()` — can be permanently diverted to an attacker-chosen contract with zero balance accounting and no nullifier/UTXO created to represent the loss. This is direct theft of protocol/in-flight ETH with no on-chain trace tying it to any spent leaf, matching the Critical category (direct theft of in-flight funds, and an action executed that the accounting model never constrained). The attack is repeatable for as long as Emporium holds exploitable ETH and the attacker can mint a fresh `emporiumMessage` nonce each time.

### Likelihood Explanation
The attacker needs only: (1) the ability to call `Hinkal.transact` as an unprivileged relay-less sender (`circomData.originalSender == msg.sender`, `relay == address(0)`), (2) the ability to generate a valid SNARK proof for the trivial `tokenNumber == 0` (or non-ETH) dimension — which is an intentionally supported, documented code path (`formInputEmporiumMin`), not a forged/edge circuit, and (3) EmporiumUpgradeable actually holding spendable ETH at the time of the call. Precondition (3) is the main variable — the vulnerability is fully "live" whenever the contract has a nonzero ETH balance, which can arise from normal multi-hop Emporium operations (e.g., WETH-unwrap-then-forward flows) leaving transient ETH, or from any direct ETH transfer to the contract via its permissive `receive()`. No signature, admin role, or relay is required since `verifyWallet` skips signature verification entirely when `signerAddress == address(0)`.

### Recommendation
Enforce that `address(0)` is always present in `circomData.erc20TokenAddresses` whenever any `EmporiumOperation.value > 0` is used (or, simpler, always require `address(0)` be included as one of the tracked slots for any Emporium action, with `dimensions.tokenNumber >= 1`). Additionally, in `EmporiumUpgradeable.runAction`, independently record `address(this).balance` before/after the ops loop and require that native ETH change is fully accounted for by a corresponding entry in `erc20TokenAddresses`/`deltaAmountChanges`/UTXO output, regardless of whether the caller chose to list `address(0)`. Reject `runAction` if `sum(op.value) > 0` for any op while `address(0)` is absent from `erc20TokenAddresses`.

### Proof of Concept
Foundry test outline:
1. Deploy `EmporiumUpgradeable`, `Hinkal`, `HinkalHelper`, verifiers as in existing test harness; register a "malicious endpoint" contract that just accepts ETH (`receive() payable {}`).
2. Fund `EmporiumUpgradeable` with `X` ETH directly (simulating resident/in-flight ETH, e.g. via `vm.deal` or a legitimate prior op leaving change).
3. Build `circomData` with `erc20TokenAddresses` either empty (`tokenNumber = 0`, using the `formInputEmporiumMin` path) or non-empty but excluding `address(0)`; set `externalActionData.externalActionId` to Emporium's id and `externalActionMetadata` to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{endpoint: maliciousEndpoint, invokeWallet: false, value: X, callData: ""}`.
4. Generate a valid proof for this minimal circuit input locally (per `formInputEmporiumMin`/circuit for `tokenNumber = 0`), or otherwise satisfy `verifyProof`.
5. Call `Hinkal.transact(...)` with this `circomData` from an unprivileged EOA.
6. Assert: `address(EmporiumUpgradeable).balance` decreased by `X`, `maliciousEndpoint.balance == X`, `deltaAmountChanges` (empty or excluding index for ETH) never reflected `X`, and no `UTXO`/on-chain commitment for `X` was created (`utxoSet.length == 0` or no matching `erc20Address == address(0)` entry) — proving the equality "total ETH change in EmporiumUpgradeable == sum of tracked balanceChange across circomData.erc20TokenAddresses" is broken.
