### Title
Relayer Loses All Delivery Fee When `onAccept` Reverts, Since `dispatchIncoming` Deletes the Relayer Attribution Needed for Fee Claims - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address relayer)` records the delivering relayer's address in `_requestReceipts[commitment]` *before* calling the destination module's `onAccept`, but deletes that record if the callback reverts. Since `_requestReceipts[commitment]` is the exact slot that Hyperbridge proves against to attribute and pay out the relayer fee for a delivered POST request, a relayer that pays gas to verify the merkle proof and invoke `onAccept` — but whose call reverts for any reason on the receiving application — gets no attribution and therefore no fee, while a later relayer can retry the same request and collect the entire reward instead.

### Finding Description
`dispatchIncoming` for POST requests is: [1](#0-0) 

The relayer is optimistically written to `_requestReceipts[commitment] = relayer` before the external call to the destination module's `onAccept`. If that call fails (`success == false`), the receipt is deleted "so it can be retried" and the function returns without reverting the whole batch, but also without crediting this relayer.

This receipt is the sole on-chain attribution of "who delivered this request," and it is exactly what the fee/reward machinery reads to determine who gets paid. This is demonstrated by the parallel outbound-reward claim pipeline, which explicitly derives the reward-recipient address from `RequestReceipts[commitment]`: [2](#0-1) 

and by the general relayer fee model, which states the fee is "paid out to the relayer that delivers the message": [3](#0-2) 

Because a destination application's `onAccept` can revert for reasons entirely outside the relayer's control (out-of-gas on a complex handler, application-level require/revert, reentrancy guard trip, temporary paused state, insufficient allowance/liquidity in the receiving app, etc.), a relayer who correctly verified the state proof and paid gas for the call receives zero reward if that call reverts — the receipt they would have been paid against is deleted. Any other relayer (or the same one, again at their own gas cost) can then resubmit the identical request and claim the entire fee, since `_requestReceipts[commitment]` is empty again and the duplicate check in `HandlerV2.handlePostRequests` only rejects requests whose receipt is *non-zero*: [4](#0-3) 

This is structurally the same root cause as the referenced Connext finding: the code path that sets the relayer-of-record for fee purposes is inside the same execution that can fail due to downstream application logic, so a revert in that downstream call permanently forfeits the first relayer's compensation for an otherwise correctly-performed delivery.

### Impact Explanation
Any unprivileged relayer participating in Hyperbridge's permissionless delivery network can lose the entire fee for a delivery attempt whenever the destination `IApp.onAccept` implementation reverts, despite having correctly paid gas to verify the MMR/consensus proof and execute the call. This is a direct loss of funds for relayers and undermines the "relayer fee and reward accounting" invariant that the protocol depends on to keep relayers economically incentivized to deliver messages reliably. It also creates a race condition where competing/opportunistic actors can "snipe" retried deliveries for messages whose first delivery attempt failed, extracting the fee that the first relayer effectively paid for (in gas) but never received.

### Likelihood Explanation
Any application built on Hyperbridge (`IApp.onAccept`) can revert under conditions unrelated to proof validity — reentrancy checks, paused states, insufficient balances/allowances in receiving contracts, custom validation logic, or plain out-of-gas due to underestimated gas limits by the relayer. Given the permissionless and decentralized nature of the relayer network and the diversity of third-party `IApp` implementations dispatched to, this is a realistic and recurring condition, not a rare edge case.

### Recommendation
Do not gate relayer fee attribution/payment on the success of the downstream `onAccept` call, or provide a fallback compensation mechanism for relayers whose delivery attempt reverts only due to receiver-side logic (while still allowing the message to be retried). At minimum, distinguish between "message not deliverable" (should not compensate) and "receiver reverted after successful, gas-metered delivery attempt" (should still credit or partially reward the relayer), mirroring the design tension already acknowledged for this bug class in Connext's own triage.

### Proof of Concept
1. A relayer submits `handlePostRequests` with a valid MMR proof for a `PostRequest` whose destination module intentionally or incidentally reverts in `onAccept` (e.g., a paused contract, a reentrancy guard, or a `require` that depends on mutable application state).
2. `EvmHost.dispatchIncoming` sets `_requestReceipts[commitment] = relayer`, calls `onAccept`, observes `success == false`, and executes `delete _requestReceipts[commitment]` before returning.
3. The relayer's transaction does not revert, but no `PostRequestHandled` event is emitted and `_requestReceipts[commitment]` is empty again — the fee-claim/accumulation flow described in `docs/outbound-request-incentivization.md` (steps referencing `RequestReceipts[commitment]`) has nothing to prove delivery against for this relayer.
4. A second relayer resubmits the identical `PostRequestLeaf` (now that the destination app's blocking condition has cleared, or simply because the same call now succeeds for any reason), and this second relayer's address is what gets written and proven for the fee payout, per the receipt-based attribution described in `docs/outbound-request-incentivization.md:130-138`.
5. The first relayer has paid gas for proof verification and the failed call, and receives no fee for that attempt.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

## Relayer Fees

The relayer fee is an optional incentive provided by applications initiating cross-chain transactions. It compensates Hyperbridge's decentralized relayers for delivering messages to the destination chain. Apps that prefer to self-relay can leave the fee at zero.

The fee is collected by `pallet-ismp`'s `IsmpDispatcher` from the configured `Currency` (typically a stablecoin). It's escrowed into the `RELAYER_FEE_ACCOUNT` and paid out to the relayer that delivers the message (or refunded to the payer on timeout).
