### Title
Race condition between unawaited `PassphraseCache#set()` in `Application#unlock` and `PassphraseCache#clear()` in `Application#lock` can leave a cached passphrase after locking - (File: `features/application/src/modules/application.ts`)

### Summary
`Application#unlock` fires `void this.#passphraseCache.set(opts.passphrase)` without awaiting it, so the `unlock()` promise resolves and returns to the RPC caller before the passphrase write to storage completes. If `lock()` is invoked immediately after (as a normal follow-up RPC call, no special access needed), its awaited `this.#passphraseCache.clear()` can complete before the still-in-flight `set()` write lands, leaving a residual passphrase in storage while `lockedAtom` reports `true`.

### Finding Description
In `features/application/src/modules/application.ts`, `unlock()` is defined as: [1](#0-0) 
The passphrase cache write is dispatched with `void`, meaning `unlock()`'s own promise resolves as soon as the `if` block schedules the microtask, without waiting for `PassphraseCache#set()` to finish its internal work (`#getTtl()` await followed by `this.#storage.batchSet(...)`), as seen in `passphrase-cache.ts`: [2](#0-1) 

Meanwhile, `lock()` fully awaits `this.#passphraseCache.clear()`, which calls `this.#storage.clear()` directly with no preceding async work: [3](#0-2) [4](#0-3) 

There is no mutex, queue, or serialization mechanism guarding calls into `Application` methods exposed over RPC — the RPC layer (`libraries/json-rpc`, `libraries/sdk-rpc`) dispatches each incoming request to its handler independently as it arrives, with no per-module call queue found in `features/application/**`. Consequently, an unprivileged caller with normal RPC access to `application.unlock` and `application.lock` (exposed via `features/application/src/api/index.ts`) can issue `unlock({ passphrase })` and then immediately `lock()` without waiting for the first call's underlying passphrase persistence to finish. Because `set()`'s write path has an extra await (`#getTtl()`) before `batchSet`, and `clear()`'s write path has none, `clear()` is likely to resolve first in many storage backends, after which the pending `set()`'s `batchSet` can still land and repopulate the passphrase keys — leaving a live passphrase in storage despite `lockedAtom` being `true` and the UI reporting "locked".

### Impact Explanation
This breaks the "locked means locked" invariant: even though the application state and UI indicate the wallet is locked, the passphrase cache in `sessionStorage`-backed storage still contains a valid passphrase. On subsequent app restart or reload, `#autoUnlock()` reads this residual passphrase and can automatically unlock the wallet with attacker-observable/controlled material still cached, undermining the security boundary a user or automation expects from calling `lock()`. This matches the "privilege/secret persistence past a security boundary" class of impact (AUTH_BOUNDARY / SECRET_ISOLATION invariant violation).

### Likelihood Explanation
Preconditions are minimal: an unprivileged caller only needs ordinary RPC access to `application.unlock` and `application.lock` (both are plain, unauthenticated module methods with no rate limiting or call serialization). The race window depends on storage timing — `set()` has one extra `await` (`#getTtl()`) before its write versus `clear()`'s direct write — making the unfavorable ordering (write lands after clear) plausible on real async storage backends (e.g., IndexedDB/chrome.storage with variable latency), especially under load or with a genuinely slower storage implementation. This is a timing-dependent but realistically reproducible race, not requiring any privileged access.

### Recommendation
Await the passphrase cache write in `unlock()` before the method resolves (or at minimum before firing `Hook.Unlock`/returning), i.e. replace `void this.#passphraseCache.set(opts.passphrase)` with `await this.#passphraseCache.set(opts.passphrase)`. Additionally, consider serializing/queueing calls to `Application#lock` and `Application#unlock` (e.g. via a per-instance async mutex) so that an unlock's in-flight cache write cannot race with a subsequent lock's clear.

### Proof of Concept
Integration test plan:
1. Construct an `Application` instance with a real `PassphraseCache` backed by an injectable `storage` mock whose `batchSet` resolves after a controllable delay (e.g., `storage.batchSet = () => new Promise(resolve => setTimeout(resolve, 50))`), while `storage.clear` resolves immediately.
2. Call `await application.unlock({ passphrase: 'secret' })` — note it resolves before `batchSet` completes because of the `void` call.
3. Immediately call `await application.lock()`.
4. Assert `await passphraseCache.get()` returns `undefined` immediately after `lock()` resolves.
5. Wait for the delayed `batchSet` to flush, then assert again that `await passphraseCache.get()` is still `undefined` (it will fail, returning the passphrase, demonstrating the residual-cache bug) — expected failing assertion confirms the vulnerability; fix is verified once `unlock()` awaits `set()`.
