### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop` header value to the app as the trusted tenant identifier. The `shop` field is never included in the signed material, so the binding "shop trusted by the handler" == "shop cryptographically committed to by the HMAC" does not hold — exactly the same class of bug as the report's mismatch between the price used for settlement (`_fillOrder`'s `ctx.fillPrice`) and the price used for margin validation (`getIndexPrice()`): one code path authenticates on one piece of data, a second, security-relevant path acts on a *different*, unauthenticated piece of data that is assumed to correspond to the first.

### Finding Description
`Webhooks::Request` extracts `shop` straight from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header: [1](#0-0) 

But the value that is actually HMAC-verified (`to_signable_string`) is only the raw body — the header is never part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only over that signable string: [3](#0-2) 

`Registry.process` performs exactly one check — HMAC over the body — and then forwards the *unauthenticated* `request.shop` value to the app's handler as the tenant identity for the webhook, alongside the (now-verified) body: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any user who can get one valid `(body, hmac)` pair for their **own** shop (e.g., by installing the app on a shop they control and triggering any webhook, or by using the mandatory `customers/redact`-style test payloads) can replay that exact body/HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `shop` header. `HmacValidator.validate` still succeeds (it never looks at `shop`), and the handler receives `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, with `body`/`topic` fully attacker-controlled. Any app logic that uses `data.shop` (the field this gem is designed to hand off as the tenant key) to select which merchant's data/session to update is thereby confusable across tenants.

### Impact Explanation
This breaks the identity binding "shop authenticated" == "shop the payload actually pertains to," which is one of the explicitly listed analog patterns. An app that keys off `WebhookMetadata#shop` (the documented, intended use of this field) to write/update per-merchant state can be made to attribute attacker-controlled webhook data to a different, victim tenant — a cross-tenant data integrity/access issue, achieved without needing the app's `client_secret`, an access token, or any token authentication step, only a legitimate (even free) install of the app on an attacker-controlled shop.

### Likelihood Explanation
Any developer/user can install a Shopify app on a store they control, which is sufficient to obtain a validly HMAC-signed `(body, hmac)` pair for an arbitrary webhook topic and body content the attacker can influence (e.g., product/order fields). Because the webhook endpoint is a public HTTP endpoint and the HMAC secret is shared across all shops using the app, no privileged credentials or TLS interception are required to replay the pair with a forged `shop` header.

### Recommendation
Cover the `shop` (and ideally `topic`/`api_version`) values in the HMAC-verified material, or independently verify that the shop asserted in the header corresponds to a shop the app actually has an active, matching installation/session for before trusting `WebhookMetadata#shop` in `Registry.process`.

### Proof of Concept
1. Install the target app (any app using this gem's webhook registry) on an attacker-controlled development shop `attacker.myshopify.com`.
2. Trigger any registered webhook topic (e.g. `products/create`) on the attacker's shop; capture the raw request body and the `X-Shopify-Hmac-Sha256` value delivered to the attacker's own endpoint — this is a valid `(body, hmac)` pair under the app's shared `api_secret_key`.
3. Send a POST directly to the target app's public webhook URL with the same body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and the desired `X-Shopify-Topic`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-190`) validates the HMAC successfully (it only checks the body) and invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to process attacker-controlled data attributed to the victim tenant.

          received_signature = verifiable_query.hmac

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
