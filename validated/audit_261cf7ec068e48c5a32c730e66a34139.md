Audit Report

## Title
Bridge OutgoingToken (external adapter credential) exposed in plain text to view-only users via `/v2/bridge_types` REST and GraphQL `bridge`/`bridges` queries - (File: core/web/presenters/bridges.go)

## Summary
The `BridgeType.OutgoingToken`, a static credential the Chainlink node uses to authenticate to an external adapter, is returned unredacted in plaintext by both the REST `GET /v2/bridge_types`/`GET /v2/bridge_types/:BridgeName` endpoints and the GraphQL `bridge`/`bridges` queries. These read routes carry no `auth.RequiresEditRole`/`RequiresAdminRole` restriction, so any authenticated user with the lowest-privilege `UserRoleView` role can retrieve it.

## Finding Description
`BridgeType.OutgoingToken` is persisted in the DB [1](#0-0) . `BridgeResource`, used by `BridgeTypesController.Index`/`Show`, marshals `OutgoingToken` as a required field with no `omitempty` or redaction, unlike `IncomingToken` which is explicitly documented and tagged as one-time-only [2](#0-1) . The handlers build this resource directly from the ORM record [3](#0-2) .

The route registration confirms `GET /bridge_types` and `GET /bridge_types/:BridgeName` are wired without any role wrapper, while `Create`, `Update`, and `Destroy` require `auth.RequiresEditRole` [4](#0-3) . The RBAC test table documents these GET routes as reachable in the view-only role case [5](#0-4) .

The GraphQL schema exposes the same field as non-nullable `outgoingToken: String!` [6](#0-5) , resolved directly from the stored value [7](#0-6) , and the resolver test confirms the plaintext token appears in the query result [8](#0-7) .

By contrast, the sibling `ExternalInitiator` credential model treats `OutgoingToken` as sensitive: `ExternalInitiatorAuthentication` (returned only on create) tags it `omitempty` [9](#0-8) , though notably the separate `ExternalInitiatorResource` (used for listing, per `ExternalInitiatorsController.Index`) also exposes `OutgoingToken` without `omitempty` [10](#0-9)  — a parallel exposure, but not part of this specific claim about bridges.

No existing role check, redaction, or omission logic protects `OutgoingToken` on the bridge read paths; the only asymmetric protection applied is to `IncomingToken`, which explicitly is not shown after creation. This is a genuine gap between the documented intent (only expose secrets at creation) and the actual behavior (OutgoingToken is always exposed on every read, to any role, including view-only).

## Impact Explanation
This maps to the in-scope "key/secret exfiltration" impact class. Any user holding the `UserRoleView` role — the lowest privilege tier, intended for read-only dashboard access — can retrieve the plaintext outgoing bridge credential for every configured external adapter via a normal, supported API call. If the external adapter uses this token for authorization (a common bridge pattern), a view-only user gains an unintended capability to act as the node against the adapter, which is a concrete escalation beyond the intended read-only boundary.

## Likelihood Explanation
High. No race conditions, timing windows, or special preconditions are needed beyond having a `view`-role session or API token, which is a normal, documented, supported credential tier in the RBAC model. A single `GET /v2/bridge_types` or GraphQL `bridges` query suffices, and it is repeatable at will.

## Recommendation
Apply the same `omitempty`/one-time-disclosure pattern currently used for `IncomingToken` to `OutgoingToken` in `BridgeResource` (core/web/presenters/bridges.go) and in the GraphQL `Bridge` type/resolver (core/web/schema/type/bridge.graphql, core/web/resolver/bridge.go), redacting it on `Index`/`Show`/`bridge`/`bridges` reads. If the token must remain visible for operational reasons, restrict these read routes to `edit`/`admin` roles instead of allowing `view`. Consider auditing `ExternalInitiatorResource` for the same pattern.

## Proof of Concept
1. Provision a user with `sessions.UserRoleView` and authenticate a session, as done in `TestRBAC_Routemap_ViewOnly` [11](#0-10) .
2. Send `GET /v2/bridge_types` with that session; the route registration shows no role wrapper is applied [12](#0-11) .
3. Observe the JSON response includes `attributes.outgoingToken` in plaintext, matching the presenter test fixture [13](#0-12) .
4. Equivalently, issue `{ bridges { results { outgoingToken } } }` via GraphQL as a view-role user; the resolver test confirms the plaintext token is returned in the response [14](#0-13) .

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
