Audit Report

## Title
HTTP Response Cache Key Omits WorkflowID, Causing Cross-Workflow Response Cache Poisoning/Confusion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The `responseCache` used by the gateway's HTTP capability v2 stores and retrieves cached HTTP responses keyed solely by `req.Hash()`, and unit tests confirm this hash omits `WorkflowID` while including `WorkflowOwner`. The `gatewayHandler` maintains a single shared `responseCache` instance (`h.responseCache`) across all workflow requests handled by that gateway node, so two distinct workflows owned by the same owner that issue identically-shaped requests (method, URL, headers, body) collide onto the same cache entry — contradicting the component's documented "Workflow Isolation" guarantee.

## Finding Description
`isExpiredOrNotCached`, `Fetch`, and `Set` all key the cache map exclusively by `req.Hash()` [1](#0-0) [2](#0-1) [3](#0-2) . The cache itself is instantiated once and referenced as `h.responseCache` on the `gatewayHandler`, invoked directly from `makeOutgoingRequest` for every node's outbound HTTP request regardless of which workflow issued it [4](#0-3) . Unit tests explicitly demonstrate `req.Hash()` is identical for two requests differing only in `WorkflowID`, while it differs when `WorkflowOwner` differs [5](#0-4) [6](#0-5) . The README's "3.2 Caching Behavior" section explicitly documents the intended invariant: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [7](#0-6) . The actual implementation contradicts this documented isolation model — there is no code path that scopes the cache map by workflow ID; the map key is a single flat hash.

## Impact Explanation
Because the shared cache is keyed without `WorkflowID`, two different workflows belonging to the same `WorkflowOwner` that happen to issue outbound HTTP requests with identical method/URL/headers/body will read/write the same cache entry. This causes cross-workflow response confusion: a response cached for one workflow execution context can be served to a different workflow execution under the same owner, violating the explicitly documented "Workflow Isolation" invariant of this component. This maps to the "cross-user response corruption" impact category referenced in the validation rules, since responses (which may embed workflow-specific data via headers/body) can leak or be served across distinct workflow contexts that share an owner.

## Likelihood Explanation
Both `WorkflowID` and `WorkflowOwner` are attacker/workflow-author controlled inputs — no operator, admin, or elevated privilege is required. Any owner running two workflows (e.g., staging and production instances of the same workflow template, or two workflows that call the same external API with the same shape) that both set `CacheSettings.Store = true` or non-zero `CacheSettings.MaxAgeMs` will deterministically hit this collision, as proven by the passing unit test at `TestRequestHash / "having different workflowID results in same Hash"`. This is a concrete, reproducible cross-workflow behavior for a shared owner, not merely theoretical, though it requires the two workflows to be owned by the same `WorkflowOwner` and to issue identically-shaped requests (method, URL, headers, body) — it does not directly bypass owner-to-owner isolation (which is enforced) but does break the additionally documented per-workflow isolation.

## Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in `OutboundHTTPRequest.Hash()`'s hashed fields, so cache entries are scoped per-workflow as documented, e.g., hash `(WorkflowID, WorkflowOwner, Method, URL, MultiHeaders, Body)` instead of omitting `WorkflowID`.

## Proof of Concept
1. Construct two `gateway.OutboundHTTPRequest` values with identical `Method`, `URL`, `MultiHeaders`, and `Body`, but different `WorkflowID` values ("workflow-123" vs "workflow-456"), both with the same `WorkflowOwner`.
2. Call `req1.Hash()` and `req2.Hash()` — per `TestRequestHash` ("having different workflowID results in same Hash") in `response_cache_test.go` lines 139-149, both hashes are equal.
3. Store a response for `req1` via `responseCache.Set(req1, resp)` (or via `Fetch` with `storeOnFetch=true`), then call `responseCache.Fetch(ctx, req2, fetchFn2, ...)` with a max age set — `req2` will retrieve `req1`'s cached response from the shared `rc.cache` map instead of invoking `fetchFn2`, confirming cross-workflow cache confusion.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}
```

```go
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```

```markdown
### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage
```
