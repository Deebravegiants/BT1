### Title
`register_token` allows re-registering an already-active asset's custody model (`native`) while transfers are in flight, causing unbacked mint or permanent escrow lock - (File: modules/pallets/hyper-fungible-token/src/lib.rs)

### Summary
`register_token` in `pallet-hyper-fungible-token` is a privileged (`CreateOrigin`) call that is meant to be used once per asset to set up its custody model before the asset is used for cross-chain transfers, analogous to `updateFounders` being meant to run only "before handing off control to the DAO". Like `updateFounders`, `register_token` has no guard preventing it from being called again on an asset that already has in-flight `send()` transfers, and it unconditionally overwrites `NativeAssets` (the custody-model flag consulted by both `on_accept` and `on_timeout`).

### Finding Description
`register_token` (`modules/pallets/hyper-fungible-token/src/lib.rs:330-376`) is callable at any time by `T::CreateOrigin` and unconditionally does: [1](#0-0) 
`NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);`

There is no check that the asset is unregistered, no check for existing `TokenContracts`/`Precisions` entries, and critically no check for outstanding escrowed balance in the pallet's custodial account (`pallet_account()`) or in-flight (not-yet-timed-out/not-yet-accepted) ISMP requests for that asset — unlike `setReservedUntilTokenId` in the referenced nounsbuilder report, which explicitly checks `settings.mintCount > 0` before allowing a state change that would corrupt in-progress allocations.

`send()` locks (native=true) or burns (native=false) tokens based on the *current* `NativeAssets` flag at call time: [2](#0-1) 

The corresponding settlement paths, `on_accept` (destination mint/release) and `on_timeout` (source-side refund), independently re-read `NativeAssets` at settlement time rather than snapshotting it at dispatch time: [3](#0-2) [4](#0-3) 

If governance calls `register_token` again for the same `local_id` between the time a user calls `send()` (escrowing tokens because `native=true` at that time) and the time the request times out or is refunded, and the new call flips `native` to `false`, then `on_timeout`'s refund path takes the `mint_into` branch instead of releasing the escrowed tokens from `pallet_account()`. This mints new tokens to the user while the originally escrowed tokens remain permanently stuck in `pallet_account()` — an unbacked mint plus a permanent freeze of the previously locked funds. The same divergence applies in reverse (native=false→true): a `burn_from` on `send()` followed by a flag flip to `native=true` on `on_timeout`/`on_accept` results in an attempted `transfer` from `pallet_account()` of tokens that were never actually escrowed there, which will fail or, if the account happens to hold other reserves, silently drain unrelated custody funds to the wrong beneficiary.

### Impact Explanation
This breaks the fundamental custody invariant of the bridge for the affected asset: either tokens are minted without backing (inflation / theft-equivalent for other holders of the same wrapped asset) or the user's transferred funds become permanently unrecoverable in `pallet_account()`. This qualifies as "unbacked mint" and "permanent freezing of funds" per the validation criteria, reachable through a single unprivileged user's `send()` extrinsic combined with a subsequent config change and a timeout/accept delivery — the funds-at-risk transaction (`send`) is itself unprivileged.

### Likelihood Explanation
The trigger requires a `CreateOrigin` call to `register_token` while a `send()` is in flight for the same asset — this is a legitimate, foreseeable governance action (e.g., correcting a misconfiguration, or a routine re-registration after adding new chains, as documented in `update_token`'s sibling call) rather than malicious governance intent. Because there is no invariant check, an honest operator with no awareness of pending transfers can trigger it, exactly mirroring the `updateFounders` root cause (a state-mutating admin function usable at any time, without knowledge that a preceding action already fixed part of the state).

### Recommendation
Add the same class of guard the nounsbuilder fix suggests: before allowing `register_token` to change `NativeAssets` for an already-registered `local_id`, verify there are no outstanding escrowed balances for that asset in `pallet_account()` (e.g., reject if `pallet_account()`'s balance for that asset is nonzero) or reject re-registration outright if the asset ID already exists in `NativeAssets`/`TokenContracts`, forcing a distinct explicit migration path that first drains/settles all in-flight transfers. Additionally, consider snapshotting the custody-model flag into the dispatched `Message`/request state at `send()` time so `on_accept`/`on_timeout` settle against the flag that was true when the transfer was initiated, rather than the possibly-changed current value.

### Proof of Concept
1. Governance calls `register_token` for `asset_id = X` with `native = true`, mapping it to an EVM `HyperFungibleToken` contract on chain `C`.
2. A user calls `send(asset_id=X, destination=C, amount=100)`. Per `modules/pallets/hyper-fungible-token/src/lib.rs:268-276`, since `NativeAssets::get(X) == true`, 100 units of `X` are transferred (escrowed) into `pallet_account()`, and a `DispatchPost` is sent via ISMP.
3. Before the message is delivered/times out, governance calls `register_token` again for `asset_id = X` with `native = false` (e.g., intending only to add a new chain but supplying the wrong `native` flag, or as part of an unrelated re-registration). `NativeAssets::<T>::insert(X, false)` overwrites the flag with no check for the pending transfer.
4. The ISMP request times out. `on_timeout` (`modules/pallets/hyper-fungible-token/src/module.rs:266-284`) reads `NativeAssets::get(X)`, now `false`, and executes `Assets::mint_into(X, beneficiary, 100)` — minting 100 new units of `X` to the user.
5. Result: the user now holds 100 newly minted `X` tokens plus the original 100 `X` tokens remain locked forever in `pallet_account()`, doubling the effective circulating supply of `X` without backing.
