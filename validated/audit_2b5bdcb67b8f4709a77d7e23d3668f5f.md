### Title
Webhook Shop Identity Spoofing via Unauthenticated `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by validating the HMAC of the raw request body, but it dispatches the webhook handler using a `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed payload. The binding "the shop attributed to the event" == "the shop whose secret authenticated the event" is broken: the HMAC signs only `@raw_body`, while the `shop` field acted upon by the handler is parsed unauthenticated from headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the body only) and compares it against the received HMAC: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request — including the shop identity — is authentic, then immediately hands the unauthenticated `request.shop` to the app's handler as the tenant identity for the event: [4](#0-3) 

The library's own documentation reinforces the false assumption that this call "will verify the request did indeed come from Shopify," without qualifying that only the body — not the shop/topic headers — is verified: [5](#0-4) 

Because the HMAC is computed with the app's single shared `client_secret` across *all* shops that have the app installed (there is no per-shop signing key), any actor who controls a shop with the app installed can trigger a legitimate webhook, capture the valid `(raw_body, hmac)` pair Shopify sends to the app's endpoint, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (body is byte-for-byte unchanged), and `Registry.process` calls the handler with `shop: <attacker-chosen shop>` and the attacker-controlled body content, exactly mirroring the reported bug pattern: a value ("shop") that is *acted on* by downstream logic but not *covered* by the authentication primitive that gates access.

### Impact Explanation
This breaks the tenant boundary: the app's webhook handler will process attacker-supplied data (which was only ever legitimately signed for the attacker's own shop) as if it belongs to a victim shop. Depending on how the host app consumes `WebhookMetadata#shop` (e.g., looking up the victim's stored session, updating the victim's local records, keyed by `data.shop` as the docs recommend: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data injection/corruption — data destined for shop A gets attributed to and processed under shop B's tenant context. This qualifies as Critical (cross-tenant access) per the impact criteria.

### Likelihood Explanation
Exploitation requires only: (1) the attacker controls, or can install the app on, any single shop (trivial for a public app — anyone can install a public Shopify app on their own dev/test store), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a spoofed header, which is standard for any internet-reachable webhook receiver. No access to `api_secret_key`, tokens, or the target shop is needed. Likelihood is therefore High for any app that keys tenant-sensitive logic off the webhook's `shop` field, which the gem's own documentation encourages.

### Recommendation
Include the shop domain (and other identity-bearing headers such as topic/webhook id, or at minimum shop) in the HMAC-signed material used for validation, or otherwise cryptographically bind the `shop` header to the signed body (e.g., by requiring the caller to reconcile the header shop against a shop already tied to an authenticated session/webhook subscription id, and rejecting mismatches). At minimum, update the documentation to clarify that only the body is authenticated, and explicitly warn integrators not to trust the `shop`/`topic` headers as authenticated tenant identifiers without additional server-side reconciliation (e.g., against the registered webhook ID's associated shop).

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` (a shop they control) and subscribes the app to a webhook topic (e.g., `orders/create`).
2. Attacker triggers the event in `attacker-shop` (e.g., creates an order), causing Shopify to POST a legitimately-signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, body: `<raw_body>`.
3. Attacker captures `<raw_body>` and `<valid HMAC>` (e.g., by running their own receiving endpoint, or a proxy/logging endpoint they control for the attacker-owned shop's install).
4. Attacker replays a POST to the app's webhook endpoint with the same `<raw_body>` and same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` (unchanged) — see `Request#to_signable_string` and `HmacValidator#validate_signature`.
6. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, causing the app to process attacker-controlled data under the victim shop's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
