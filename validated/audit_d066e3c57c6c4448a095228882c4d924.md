### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` identity that the host application relies on to route/attribute the webhook (`request.shop`, sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is read directly from an unauthenticated HTTP header and never included in the signed material. `ShopifyAPI::Utils::HmacValidator.validate` only proves that the *body* was signed by the app's shared secret; it says nothing about which shop the body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an HTTP header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body) and then unconditionally forwards `request.shop` to the app's handler as authoritative tenant context: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely over `to_signable_string` (the body), which never includes shop, topic, api-version, or webhook-id: [4](#0-3) 

The identity binding that should hold is: `shop attributed to the webhook (request.shop, used by WebhookMetadata/handler) == shop that the HMAC-secret holder actually signed for`. Because the header is not part of the signed bytes, this equality is never enforced by the gem — only `body == HMAC(body, secret)` is checked. Any request with a *body* that was legitimately HMAC-signed by Shopify for the app's client secret (e.g., a webhook payload the attacker's own store received, since the secret is shared across all shops installing the app) can be replayed to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header value, and it will pass `Registry.process`'s HMAC check unchanged, while `WebhookMetadata#shop` (and therefore whatever host-app logic keys off of it — session/tenant lookup, data writes, redaction actions, etc.) reflects the attacker-supplied header rather than the shop that actually produced/signed the body. [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide via `Registry.process`/`WebhookHandler`: host applications are told the `shop` field on `WebhookMetadata` identifies "the shop domain of the webhook" and is safe to use for routing (per `docs/usage/webhooks.md`), when in fact it is unauthenticated attacker-controlled input. A merchant/attacker who controls one shop with the app installed can capture a legitimately-signed webhook body/HMAC pair from their own store and replay it against the app's endpoint while spoofing a different shop's domain in the header, causing the host app to process/attribute that webhook body to a victim tenant. Depending on how the host app uses `data.shop` (e.g., looking up the victim's session/access token to act on the victim's store, or triggering `customers/redact`/`shop/redact` handling for the wrong shop), this can lead to cross-tenant data confusion or actions being taken against another merchant's shop context — a cross-tenant boundary violation.

### Likelihood Explanation
Likelihood is moderate-to-high for any app built directly on this gem's documented API: it requires only (a) that the attacker's own shop have the app installed and receive real Shopify webhooks (trivial, since the app's `api_secret_key` is shared across all install), and (b) that the attacker be able to influence the body content they want replayed (many webhook topics, e.g. `orders/create`/`products/update`, are attacker/merchant-controlled data on their own store) or simply replay a captured payload verbatim while only changing the shop header, since nothing about the body ties it to a particular shop. No secrets need to be stolen — the attacker uses their own valid webhook deliveries.

### Recommendation
Bind the shop identity into what is verified: either include the `shop-domain` (and ideally `topic`/`api-version`/`webhook-id`) header values in the HMAC-signable string that `HmacValidator` checks, or independently authenticate/expect the `x-shopify-shop-domain` header against a claim carried inside the signed body (Shopify's webhook payloads generally include shop-identifying fields that can be cross-checked against the header before trusting `request.shop`). At minimum, `Registry.process`/`WebhookHandler` documentation should not present `data.shop` as trustworthy for cross-tenant authorization decisions unless the header is verified against signed content.

### Proof of Concept
1. App has `api_secret_key` `S` (shared across all shop installs).
2. Attacker's own shop `attacker.myshopify.com` has the app installed and receives a legitimate webhook for topic `orders/create` with raw body `B` and header `x-shopify-hmac-sha256: HMAC(S, B)` (a real, valid Shopify delivery — attacker fully observes both body and header from their own inbox).
3. Attacker replays to the app's webhook endpoint:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256`: unchanged, still valid
   - header `x-shopify-shop-domain`: changed to `victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...spoofed shop...})` builds fine (`shop-domain` header presence is the only requirement, not its value: [6](#0-5) ).
5. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(S, B)` and compares to the (still-valid, unchanged) header — validation **succeeds** because shop is not part of `to_signable_string`.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, so the host app processes body `B` (attacker/self-originated data) under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
