### Title
`Pallet::execute`'s post-hoc `FeeHandler::on_executed` charge can revert an entire batch of validly-processed ISMP messages - (File: `modules/pallets/ismp/src/impls.rs`)

### Summary
`pallet-ismp`'s `Pallet::<T>::execute` mirrors the exact bug class in the Canto `PostTxProcessing` report: state-changing message handling completes first, and only *after* all requests/responses/timeouts/consensus updates have been validly processed does the code run a side-effect (fee charging) whose failure aborts the whole call and rolls back all the otherwise-valid message processing, penalizing unrelated messages in the same batch.

### Finding Description
`Pallet::<T>::execute` first runs `handle_incoming_message` for every message in the batch, collects events, and only afterward invokes the fee hook: [1](#0-0) 

The critical line is: [2](#0-1) 

`T::FeeHandler::on_executed(...)` maps *any* error to `Error::<T>::ErrorChargingFee` and propagates it out of `execute`, which is a `DispatchResult`-returning function invoked from an extrinsic; a returned `Err` causes Substrate's transactional storage layer to roll back **all** storage writes performed during that call — including the legitimate, already-validated `RequestCommitments`/`ResponseCommitments` inserts, state-machine commitment updates, and consensus-client updates for every other message in the batch that had nothing to do with the failing fee transfer.

The default `FeeHandler` implementation, `WeightFeeHandler::on_executed`, is exactly the kind of fragile side-effect that can fail for reasons unrelated to message validity: [3](#0-2) 

It calls `C::transfer(&account, &treasury_account, fee, ExistenceRequirement::KeepAlive)` for the message signer of every non-zero-fee `Request`/`Response` message in the batch. `ExistenceRequirement::KeepAlive` means the transfer fails with an `Err` (turned into `DispatchError::Other`) whenever the originator's balance would drop below the Existential Deposit after paying the computed weight-fee — a condition entirely independent of whether the ISMP messages themselves (proofs, requests, responses, consensus updates) are valid. Any signer with a low/borderline balance, or a fee-to-balance-conversion rounding edge case, can trigger this failure.

Because `execute()` bundles multiple, unrelated `Message`s (requests, responses, timeouts, and consensus updates from potentially different senders/relayers) into a single call and the fee charge is evaluated over the *whole* `messages_with_weights` vector in one loop, a single message's fee-payer having an insufficient balance reverts delivery of every other message in the same call — this is functionally identical to the Canto report where the Turnstile CSR-fee distribution failing for one interaction reverted an entire, otherwise-successful transaction.

The tuple `FeeHandler` composition (`impl_for_tuples`) also short-circuits with `?` on the first failing handler in the tuple, so any pluggable fee-handler chain suffers the same all-or-nothing failure mode: [4](#0-3) 

### Impact Explanation
This is a Medium/High-severity availability/griefing issue against message delivery, the core reachable dispatch path of Hyperbridge (`pallet-ismp`'s handler for incoming `Message`s — POST requests, responses, timeouts, and consensus updates). Any relayer or user who batches multiple unrelated messages in one `execute` call (or whose runtime's default weight-based fee handler is active) can have legitimately verified, cryptographically-proven cross-chain messages fail to be committed on-chain purely because of an unrelated fee-payer's balance shortfall. This blocks message delivery (a listed unsound/undeliverable-route impact) for messages that should have succeeded, and can be weaponized by an attacker who deliberately includes/piggybacks a message whose signer's account is drained to the existential-deposit boundary, causing repeated failed submissions and denial of service for the batch's other legitimate messages (including third parties' funds-critical POST requests, e.g. token bridge mint/burn or intent fills relying on message delivery).

### Likelihood Explanation
Likelihood is Medium-to-High: the code path is reachable by any unsigned/permissionless submission that goes through `Pallet::execute` with a batch of messages, requires no privileged access, and the triggering condition (a signer balance at or near the Existential Deposit after fee deduction) is a naturally occurring state, not an exotic exploit precondition. The runtime's choice of `WeightFeeHandler` (the pallet's canonical/example fee handler) with `KeepAlive` semantics makes this the default behavior unless a runtime opts out via `POLICY = false` or overrides with a custom, more resilient `FeeHandler`.

### Recommendation
Decouple fee charging from message-delivery success, following the same remediation Canto adopted for `PostTxProcessing`:
- In `WeightFeeHandler::on_executed` (and any custom `FeeHandler`), do not propagate a transfer failure as a hard error that reverts `execute`. Instead, log/emit an event for the failed fee charge (e.g. `Event::Errors`) and continue processing the remaining messages, returning `Ok(..)` from `on_executed`.
- In `Pallet::<T>::execute` (`modules/pallets/ismp/src/impls.rs`), avoid using `T::FeeHandler::on_executed(...).map_err(|_| Error::<T>::ErrorChargingFee)?` as a batch-wide short-circuit; instead call the fee handler per-message (or tolerate partial failure) so a single fee-charge failure cannot roll back the entirely-valid `handle_incoming_message` results for unrelated messages.
- Consider using `ExistenceRequirement::AllowDeath` or capping/skip-if-insufficient logic, and separately tracking uncharged fees for later recovery instead of blocking delivery.

### Proof of Concept
1. Runtime configures `pallet-ismp` with the default `WeightFeeHandler<AccountId, Balances, IsmpWeightToFee, TreasuryPalletId, true>` (POLICY = true), per the documented pattern in `fee_handler.rs`.
2. Submit an ISMP `handle` extrinsic with a batch of `Message`s containing:
   - Message A: a valid POST request from Signer A whose account balance is exactly at/near the Existential Deposit.
   - Message B: a valid, unrelated POST response/consensus message from Signer B with ample balance, verifiably legitimate and independently deliverable.
3. `handle_incoming_message` succeeds for both A and B (`modules/pallets/ismp/src/impls.rs:43-51`), producing valid `RequestCommitments`/`ResponseCommitments` writes and events.
4. `T::FeeHandler::on_executed` iterates the batch (`fee_handler.rs:178-209`); for Message A, `C::transfer(.... ExistenceRequirement::KeepAlive)` fails because deducting the fee would kill Signer A's account.
5. The `?` inside `on_executed` (`fee_handler.rs:206`) propagates the error; `execute()` maps it to `Error::<T>::ErrorChargingFee` (`impls.rs:78-79`) and returns `Err`.
6. Substrate's transactional dispatch rolls back all storage changes made during the call, so Message B's otherwise-valid, unrelated request/response commitment is also reverted and never delivered, even though Message B had nothing to do with Signer A's balance.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<Event>,
	) -> DispatchResultWithPostInfo {
		if !POLICY {
			return Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
		}
		let mut total_weight = Weight::zero();
		let treasury_account: AccountId = T::get().into_account_truncating();

		for message in &messages {
			let weight = message.weight;
			total_weight.saturating_accrue(weight);
			let fee = W::weight_to_fee(&weight);

			if fee.is_zero() {
				continue
			}

			let originator = match message.message.clone() {
				Message::Request(msg) => {
					let data = sp_io::hashing::keccak_256(&msg.requests.encode());
					Signature::decode(&mut &msg.signer[..])
						.ok()
						.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
				},
				Message::Response(msg) => {
					let data = sp_io::hashing::keccak_256(&msg.requests.encode());
					Signature::decode(&mut &msg.signer[..])
						.ok()
						.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
				},
				_ => None,
			};

			if let Some(originator_bytes) = originator {
				if let Ok(account) = AccountId::decode(&mut &originator_bytes[..]) {
					C::transfer(&account, &treasury_account, fee, ExistenceRequirement::KeepAlive)
						.map_err(|_| DispatchError::Other("Failed to transfer fee to treasury"))?;
				}
			}
		}

		Ok(PostDispatchInfo { actual_weight: Some(total_weight), pays_fee: Pays::Yes })
	}
