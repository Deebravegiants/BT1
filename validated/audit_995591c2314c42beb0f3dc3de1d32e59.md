Based on my investigation, I found a valid analog in the gateway's HTTP trigger handler.

### Title
Global `requestID` collision map lets an unauthenticated attacker DoS a victim's HTTP trigger request via "already been used" conflict - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler.setupCallback` rejects any incoming request whose `requestID` is already present in the shared `h.callbacks` map, exactly mirroring the reported pattern where `CrabNetting.checkOrder` lets anyone invalidate a nonce before its "real" consumer uses it. Because `requestID` is fully attacker-chosen and the collision check is keyed only by that string (not by caller identity), an attacker who knows or predicts a victim's intended `requestID` can pre-register it first, causing the victim's legitimate request to be rejected with `ErrConflict`.

### Finding Description
`HandleUserTriggerRequest` processes requests in this order: parse/validate → resolve workflow → `authorizeRequest` (JWT check) → `checkRateLimit` → `setupCallback`. [1](#0-0) 

`setupCallback` is the step analogous to `_useNonce`/`_checkOrder` in the audit report: it checks `h.callbacks[requestID]` and, if occupied, immediately fails the *new* request with "has already been used", rather than failing the older one: [2](#0-1) 

The `requestID` is the JSON-RPC request `ID`, which is fully user/client-supplied and only validated for non-emptiness and absence of `/`: [3](#0-2) . There is no requirement that it be a UUID, be unpredictable, or be scoped per-caller/per-workflow — the map is a single global `map[string]savedCallback` shared across all users and workflows: [4](#0-3) .

Crucially, `authorizeRequest` (JWT signature validation against the workflow's authorized keys) happens *before* `setupCallback` for the incoming request itself, but that only proves the attacker's own request is authorized for whatever workflow the attacker chooses — it does nothing to prevent the attacker from picking a `requestID` string that collides with a value the victim is about to use for a *different* workflow. Since the JSON-RPC `id`/`requestID` is typically something a client (e.g. deterministic client library, replay-prone script, or predictable sequence) chooses, and is visible to anyone who can observe or guess the pattern (e.g. via a public integration, shared client library defaults, or a previous response that echoes back the ID), an attacker with no privileges beyond submitting HTTP trigger requests to the gateway can win the race to reserve a given `requestID` for any workflow.

### Impact Explanation
This is a request-level denial of service against a specific caller: the legitimate request, upon losing the race, receives `jsonrpc.ErrConflict` and never triggers workflow execution: [5](#0-4) . Repeated or targeted use of this technique could selectively block specific workflow executions (e.g. for a competitor's automation or a time-sensitive trigger), analogous to how the crab-netting bug lets an attacker block a specific privileged auction call by pre-consuming its nonce. Severity is bounded to denial-of-service of individual requests; it does not directly enable fund theft, key disclosure, or execution as another identity, since `authorizeRequest`'s JWT check still gates whether the attacker's own colliding request can actually reach `setupCallback` for a workflow it isn't authorized for — but it does not gate whether the attacker can occupy a `requestID` slot for a *victim's* workflow, since the colliding request is for the attacker's own (or any) workflow/JWT, and the requestID namespace is global rather than partitioned by workflow or caller.

### Likelihood Explanation
Exploitability requires only: (1) ability to submit HTTP trigger requests to the gateway (the front-facing HTTP endpoint, no privileged credentials needed for the attacker's own request), and (2) knowledge or prediction of the victim's `requestID` before the victim's request is processed. Because `requestID`s are often generated by client tooling in a predictable manner (e.g. incrementing counters, timestamps, deterministic UUIDs derived from public inputs) and there's no per-caller/per-workflow namespacing, this is plausible in real-world usage patterns, though it does require some information advantage or timing to guess/observe the victim's exact ID, similar to the original report's requirement to observe the mempool for the specific order.

### Recommendation
Scope the in-flight-request map key by `(workflowID, requestID)` or `(authorizedOwner, requestID)` instead of a bare global `requestID`, so an unrelated caller cannot pre-empt another caller's/workflow's request ID. Alternatively, perform authorization (`authorizeRequest`) binding to the specific workflow/owner before the collision check, and make the collision check reject only requests from the same authorized owner, so cross-tenant ID squatting is impossible.

### Proof of Concept
1. Victim's client is known/predicted to send a `workflows.execute` HTTP trigger request with `id = "X"` for `workflowID = W_victim`.
2. Attacker (an unprivileged but authenticated user of *any* workflow, e.g. their own `W_attacker`) sends a request with the same `id = "X"` for `W_attacker` slightly before the victim's request arrives.
3. Attacker's request passes `validatedTriggerRequest`, `resolveWorkflowID`, and `authorizeRequest` (using attacker's own valid JWT for `W_attacker`), then reaches `setupCallback` and inserts `h.callbacks["X"]`: [6](#0-5) .
4. Victim's request for `W_victim` with `id = "X"` arrives and hits the collision check in `setupCallback`, receiving `ErrConflict` ("requestID: X has already been used...") and never being dispatched to the workflow DON: [5](#0-4) .

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
