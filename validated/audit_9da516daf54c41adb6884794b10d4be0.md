### Title
Unbounded token minting via repeated triggering of the `one_yocto_on_promise` zero-balance subsidy - (File: `runtime/near-vm-runner/src/logic/logic.rs`)

### Summary
The `one_yocto_on_promise` protocol feature lets a contract with an exactly-zero balance attach 1 yoctoNEAR to a promise `FunctionCall` action without actually deducting that balance from the account — the deduction is skipped and the amount is instead recorded as `subsidized_amount`, which is effectively minted into existence. Because the skip condition only checks that `current_account_balance` is currently zero, and successfully skipping the deduction leaves the balance at zero, the same contract execution can re-trigger this exemption an unbounded number of times, each time minting 1 yoctoNEAR with no limit tied to a shared/subsidy budget (unlike the Drips `commonFunds`, which is at least a bounded pool). This is directly analogous to the reported bug class: an unprivileged caller can freely and repeatedly invoke a subsidized code path with no rate limiting or budget cap.

### Finding Description
`promise_batch_action_function_call_weight` (and its mirror in `promise_yield_create_with_id`) contains: [1](#0-0) 

The exemption fires whenever `amount == 1 yoctoNEAR`, the config flag `one_yocto_on_promise` is enabled, and `current_account_balance.is_zero()`. When it fires, `deduct_balance` is *not* called, so `current_account_balance` remains exactly zero — the same precondition that allowed the exemption in the first place. The comment in `ExecutionResultState` explicitly documents this as effectively minting funds: [2](#0-1) 

and the stats struct confirms it must be treated as new supply that offsets `total_balance_burnt`: [3](#0-2) 

Because the balance never moves away from zero after the exemption is applied, nothing in this host function itself prevents a single WASM execution from calling `promise_batch_action_function_call_weight` (or `promise_yield_create_with_id`) many times over many promise indices in a single receipt — each such call adds another yoctoNEAR to `subsidized_amount`. There is no cap on the number of times this exemption can be exercised by a given account, no decreasing shared budget, and no restriction limiting it to a privileged/whitelisted caller — any contract deployed by any account can reach this path once its own balance is drained to zero (trivial to arrange, and explicitly demonstrated to be supported for Zero Balance Accounts under NEP-448, which are exempt from the storage-stake balance floor). The only throttle is gas/action-count limits per receipt and per chunk, which bound the amount minted per chunk but do not eliminate the ability to repeatedly and cheaply mint yoctoNEAR-scale amounts across many chunks/receipts over time, entirely from an unprivileged account.

### Impact Explanation
This is a concrete token-supply integrity issue: value is created (`subsidized_amount`) without a corresponding deduction from any account or shared pool, and it is explicitly meant to be subtracted from `total_balance_burnt` to "keep total supply correct" — meaning it directly increases net circulating supply. While bounded per unit of gas (each action still costs gas), an attacker with modest resources could repeatedly issue receipts that mint 1 yoctoNEAR per action indefinitely, and unlike the original Drips report's `commonFunds` (a finite pool that eventually empties, stopping the drain), here the "subsidy" is not backed by any pool at all — it is unconditionally created balance, so there's no natural limit other than gas cost.

### Likelihood Explanation
Reaching a zero-balance state is fully supported and intended (ZBA support, `check_storage_stake` exemption for accounts under 770 bytes storage usage), and the exemption condition is checked independently on each call with no persistent counter, cooldown, or authorization check beyond "attached amount == 1 and balance == 0". Any account can deploy a minimal contract that loops issuing many `FunctionCall` promise actions with 1 yoctoNEAR attached each, from an account kept at zero balance, requiring no special privileges.

### Recommendation
Cap the total `subsidized_amount` that a single account (or a single receipt/chunk) may accrue, or restrict the number of times the exemption can be exercised per account per time window, so the subsidy cannot be turned into unbounded, unauthorized token minting. Alternatively, tie the subsidy to an explicit funded budget (mirroring how a real "common funds" pool would work) rather than allowing it to be created unconditionally whenever balance is zero.

### Proof of Concept
1. Deploy a contract to an account and drain its balance to exactly zero (a Zero Balance Account is exempt from the storage-stake floor, so this is achievable and already demonstrated in the test suite): [4](#0-3) 
2. From that zero-balance contract, repeatedly call `promise_batch_action_function_call_weight` across many promise indices within the same or across successive receipts, each time attaching exactly 1 yoctoNEAR.
3. Each call satisfies `skip_deduct` since `current_account_balance` never leaves zero, causing `subsidized_amount` to accumulate without bound across calls/receipts/chunks, as already unit-tested for the single-call case: [5](#0-4) 
4. Repeating this process indefinitely mints net-new yoctoNEAR-denominated balance into the system with no offsetting burn, other than gas fees, from a fully unprivileged account.

        // when the contract has zero balance. This lets deterministic accounts

#[test]
fn test_one_yocto_on_promise_enabled() {
    let mut logic_builder = VMLogicBuilder::default();
    logic_builder.config.one_yocto_on_promise = true;
    logic_builder.context.account_balance = Balance::ZERO;
    logic_builder.context.attached_deposit = Balance::ZERO;
    let mut logic = logic_builder.build();

    let index = promise_create(&mut logic, b"rick.test", 0, 0).expect("should create a promise");

    // 1 yoctoNEAR should succeed even with zero balance
    promise_batch_action_function_call_weight(&mut logic, index, 1, Gas::ZERO, 0)
        .expect("1 yoctoNEAR should succeed with feature enabled");

    // 2 yoctoNEAR should still fail
    promise_batch_action_function_call_weight(&mut logic, index, 2, Gas::ZERO, 0)
        .expect_err("2 yoctoNEAR should fail with zero balance");

    // Transfer with 1 yoctoNEAR should still fail (feature only applies to function calls)
    let num_1u128 = logic.internal_mem_write(&1u128.to_le_bytes());
    logic
        .promise_batch_action_transfer(index, num_1u128.ptr)
        .expect_err("transfer should still fail with zero balance");

    assert_eq!(
        logic.result_state().subsidized_amount,
        Balance::from_yoctonear(1),
        "subsidized_amount should track the skipped deduction"
    );
}
