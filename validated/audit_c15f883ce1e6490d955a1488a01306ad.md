### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers — only that the body bytes were HMAC-signed with the app's `client_secret`. `Registry.process` nonetheless trusts the unauthenticated `shop-domain` header to route the payload to a tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns `@raw_body` only — the `shop`, `topic`, `api_version`, and `webhook_id` accessors are all derived from headers that are excluded from the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then dispatches using the unverified `request.shop` and `request.topic`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string`: [4](#0-3) 

This breaks the identity binding: **shop authenticated by HMAC (over body only) ≠ shop used to route/attribute the webhook (header value, unauthenticated)**. Because the body content — not the headers — is what's covered by the signature, any webhook payload whose body happens to validate against the app's secret (e.g., a webhook the attacker's own shop legitimately received, since Shopify signs with the single app-wide `client_secret` for every installed shop) can be re-submitted to the app's webhook endpoint with an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass because the header isn't part of the signed string, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a different (victim) shop while the shop-domain header is not authenticated by the same secret-derived signature that authenticated the body.

### Impact Explanation
Host applications rely on `WebhookMetadata#shop` (built directly from `request.shop`) to determine which tenant's data to update from webhook payloads. Since the HMAC only proves "signed with this app's secret," not "this payload is legitimately associated with this specific shop," an attacker who controls their own legitimately-installed shop (an unprivileged, non-privileged Shopify merchant — no special access to the victim) can produce validly-signed bodies and replay them with a forged `shop-domain` header, causing the app to attribute/act on that data as if it came from a different, victim tenant. This is a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Requires the attacker to control at least one shop that has the target app installed (to legitimately receive Shopify-signed webhook bodies), then to be able to POST to the app's public webhook endpoint with modified headers — which is trivial for any internet-reachable webhook handler built with this gem, since headers are entirely attacker-controlled in the HTTP request the host framework passes into `Webhooks::Request.new(raw_body:, headers:)`.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC validation, or otherwise cryptographically bind them to the body (e.g., concatenate headers + body before computing/verifying the signature), so that the HMAC check enforces the same identity that `Registry.process` uses for tenant routing.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook event; Shopify sends a request with body `B` and header `shopify-hmac-sha256: HMAC(B, client_secret)`.
2. Attacker replays this exact body `B` and HMAC header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(request.to_signable_string, secret) == request.hmac`; since `to_signable_string` is `@raw_body` (unchanged), validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and the host app processes/persists data as if it belongs to `victim-shop.myshopify.com`. [3](#0-2)
