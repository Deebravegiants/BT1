### Title
Vetoing the latest state machine height in `EvmHost` resets `_latestStateMachineHeight` to a hardcoded `1` instead of the true previous verified height, re-opening lower heights for resubmission - (File: evm/src/core/EvmHost.sol)

### Summary
The external report's root cause is a state-reset bug: a critical tracking variable (`unredeemedEpoch`) is reset to a value that discards legitimate prior state because the code fails to correctly restore what the "correct" prior value should be, only guarding on an insufficient condition. The Hyperbridge analog is `EvmHost::deleteStateMachineCommitmentInternal`, which, when vetoing the *latest* height for a state machine, resets `_latestStateMachineHeight` unconditionally to the literal `1` rather than restoring the actual last-known-good height, unlike the equivalent Substrate/pallet-ismp implementation which correctly tracks and restores `PreviousStateMachineHeight`.

### Finding Description
In `evm/src/core/EvmHost.sol`, `deleteStateMachineCommitmentInternal` handles fisherman vetoes of a state commitment: [1](#0-0) 

When the vetoed height equals the currently recorded latest height, the code resets `_latestStateMachineHeight[height.stateMachineId]` to the constant `1`, discarding any knowledge of the actual previously-verified height (e.g., height 1000, 5000, etc.). Compare this to the Substrate implementation in `modules/pallets/ismp/src/host.rs::delete_state_commitment`, which correctly restores the height to `PreviousStateMachineHeight` (the actual last good height) rather than an arbitrary constant: [2](#0-1) 

The EVM host has no equivalent `_previousStateMachineHeight` tracking at all — the reset is a bare literal `1`. This means that after any veto of the current latest height (whether by a fisherman correctly disputing bad data, or triggered against a legitimately-verified height), `latestStateMachineHeight` collapses to `1` for that state machine, regardless of how far consensus had actually progressed.

This directly affects `HandlerV2::handleConsensus`, which gates acceptance of new intermediate states purely on `intermediate.height > latestHeight`: [3](#0-2) 

Once `latestStateMachineHeight` has been reset to `1`, *any* relayer can resubmit *any* height greater than `1` — including a height far below the actual, previously-verified progress of that state machine — and have `storeStateMachineCommitment` overwrite/store a commitment for it. This breaks the intended monotonic non-decreasing height invariant the rest of the protocol (request/response membership proofs, timeouts, incentive accounting) relies on.

### Impact Explanation
Because `_latestStateMachineHeight` is the sole state gating which heights `HandlerV2` will accept as valid consensus updates, resetting it to `1` after a single veto of the current tip:
- Allows replay/resubmission of stale, already-superseded state commitments at lower heights than the chain had truly reached, since the check `intermediate.height > latestHeight` becomes trivially satisfiable for almost any height.
- Can be leveraged to reintroduce previously-vetoed or stale state roots into `_stateCommitments`, which are subsequently used to verify request/response membership proofs (`HandlerV2::handlePostRequests` and others), and by consensus-incentive/reward accounting on the parachain side.
- This is a permanent-freezing/route-disruption and forged-state-commitment class issue: legitimate cross-chain messages relying on the correct latest height can be blocked or, worse, an old/incorrect state commitment can be substituted for the current one, undermining the security guarantee that only monotonically advancing, verified state is trusted.

This matches the report's core theme — a state variable ("unredeemedEpoch" there, "_latestStateMachineHeight" here) is reset without correctly restoring the true prior value, and only an insufficient equality check (`== currentEpoch` / `== height.height`) gates the reset, leading to corrupted state that downstream logic depends on for correctness.

### Likelihood Explanation
`deleteStateMachineCommitmentInternal` is only callable by `restrict(_hostParams.handler)`, i.e., triggered through the handler's veto/fisherman flow (not directly by an arbitrary external actor), so it requires a veto event to occur against the current tip height. However, any single veto of the latest height — including a legitimate one, initiated as designed — will trigger this incorrect reset every time, since the bug is in the core logic rather than a rare edge case; there is no special crafting needed beyond causing (or waiting for) a veto of the currently-latest height, which is the primary intended vetoing use case (disputing the most recent/tip commitment). Given the veto mechanism is a normal part of protocol operation, this bug is very likely to manifest in production once any veto of the tip height occurs.

### Recommendation
Track a `_previousStateMachineHeight` mapping alongside `_latestStateMachineHeight` (analogous to `PreviousStateMachineHeight` in pallet-ismp), updated every time `storeStateMachineCommitment`/`storeLatestCommitmentHeight` advances the latest height. In `deleteStateMachineCommitmentInternal`, restore `_latestStateMachineHeight[height.stateMachineId]` to this tracked previous height instead of the hardcoded `1`, mirroring the correct Rust implementation.

### Proof of Concept
1. Host verifies consensus updates progressing `latestStateMachineHeight` for state machine `X` to height `5000` via `HandlerV2::handleConsensus` → `EvmHost::storeStateMachineCommitment`. [4](#0-3) 
2. A veto is issued against height `5000` (the current tip) via `deleteStateMachineCommitment`, which calls `deleteStateMachineCommitmentInternal`. [5](#0-4) 
3. `_latestStateMachineHeight[X]` becomes `1` (not `4999` or whatever the true previous verified height was).
4. Any relayer now submits a new consensus proof containing an `IntermediateState` for state machine `X` at, say, height `100` (far below the chain's actual progress). Since `100 > 1`, `HandlerV2::handleConsensus`'s gate passes and `storeStateMachineCommitment` accepts and stores this stale/incorrect commitment as if it were valid new progress. [3](#0-2) 
5. Downstream consumers (request/response proof verification, timeout handling) may now operate against this reintroduced stale state commitment, in violation of the intended monotonic-height invariant.

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }
