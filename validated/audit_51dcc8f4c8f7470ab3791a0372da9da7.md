## Finding: Manipulable Uniswap V4 spot-price quote can shrink Simplex's reorg-confirmation depth for cross-chain intent fills

The InuSaitama report describes a classic AMM spot-price manipulation/arbitrage attack. The closest reachable analog in this repo is in the **Simplex intent solver's FX strategy**, where an unprivileged order-placer can influence the price Simplex reads off a public Uniswap V4 pool, and that price feeds directly into the number of source-chain confirmations required before Simplex commits capital cross-chain.

### Finding Description
For curve-less ("venue-priced") pairs, `FXFiller` derives the exotic token's USD price directly from the **live spot price** of a Uniswap V4 pool (`sqrtPriceX96`/current tick), with no TWAP and no swap-size/impact term: [1](#0-0) [2](#0-1) 

This same quote is reused by `referenceRate`, which explicitly says it "sizes the order's USD notional for confirmation depth": [3](#0-2) 

The only defense is `checkPriceGuard`, comparing the live quote to a **static, optional** `referencePrice`/`maxDeviationBps` pair — which is off by default ("omit both to leave the chain unguarded"): [4](#0-3) [5](#0-4) 

The resulting USD value flows into `requiredConfirmations` via `ConfirmationPolicy.getConfirmationBlocks`, which scales block confirmations with the order's USD value (small orders wait fewer blocks, large orders wait more, guarding against chain reorgs): [6](#0-5) [7](#0-6) 

Because a Uniswap V4 pool is a public AMM, any unprivileged actor can move its spot tick with an ordinary (even flash-loan-funded) swap in the same or a preceding block — exactly the InuSaitama-style arbitrage-swap pattern — to **understate** the USD value the pool reports for the order's leg.

### Impact Explanation
An attacker who also controls (or colludes with) the order-placer can:
1. Manipulate the exotic-token/USD Uniswap V4 pool's spot price downward on the source chain right before placing a large cross-chain order.
2. Because `referenceRate`/`getOrderUsdValue` reads the depressed spot price, `inputUsdValue` is understated, so `ConfirmationPolicy.getConfirmationBlocks` returns far fewer required confirmations than the order's true value warrants — the comment in the fx.ts code itself calls this out: *"a manipulated pool understating the value would otherwise shrink the reorg protection — the exact attack the guard exists to stop."*
3. Simplex commits destination-chain capital to fill the order after only a shallow confirmation wait.
4. The attacker then reverses the source-chain price manipulation and reorgs/invalidates the original order-placing transaction (feasible specifically because confirmation depth was too shallow for the order's real value), keeping the destination-chain payout while the source-chain escrow never materializes — a direct theft of solver funds.

This is only mitigated when the operator explicitly configures `referencePrice`/`maxDeviationBps` per chain; it is unguarded by default.

### Likelihood Explanation
Exploitability depends on: (a) the FXFiller operator running venue-priced (curve-less) pairs, (b) not configuring the optional price guard, and (c) the manipulated pool having low enough liquidity/depth to be moved cheaply relative to the order size. These are realistic operator configurations documented as supported and even demonstrated in the shipped example config (`filler-config-example.toml`) with the guard commented out by default. The attack requires no privileged access — any address can place an order and swap against a public pool.

### Recommendation
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory rather than optional for any venue-priced pair, or derive a manipulation-resistant reference (e.g., TWAP over multiple blocks, or a cross-checked external oracle) instead of trusting a single spot read.
- When no guard is configured, refuse to use the venue quote for confirmation-depth sizing (fail closed to the most conservative default rather than silently trusting the raw pool mid).
- Consider applying a floor/ceiling based on the pool's fee tier and available liquidity so the guard reacts to swap-cost-implied manipulation cost, not just price deviation from a static reference.

### Proof of Concept
1. Operator runs Simplex with a curve-less pair (`token0` = USDC, `token1` = EXOTIC) funded/priced via `[vault.uniswapV4]`, no `referencePrice`/`maxDeviationBps` set (default, unguarded — matches `filler-config-example.toml` lines 281–292).
2. Attacker swaps a large amount into/out of the EXOTIC/USDC Uniswap V4 pool on the source chain to move `sqrtPriceX96` and depress the EXOTIC-per-USD spot price.
3. Attacker (or colluding order-placer) places a large cross-chain order in `IntentGatewayV2` using EXOTIC as input.
4. `handleNewOrder` → `getOrderUsdValue`/`referenceRate` reads the manipulated spot price, understating `inputUsdValue`; `ConfirmationPolicy.getConfirmationBlocks(chainId, inputUsdValue)` returns a low confirmation count.
5. Simplex fills the destination leg after the short wait.
6. Attacker reverses the pool manipulation and causes the source-chain order transaction to be reorged out before the (too-short) confirmation window would have caught it, retaining the destination payout with no matching source-side escrow.

```typescript
	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
