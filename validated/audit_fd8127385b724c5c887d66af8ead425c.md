Multi-token order refunds can be permanently frozen by a single blacklisted input token, since the beneficiary is immutably `order.user` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The `IntentGatewayV2`'s escrow refund path mirrors the reported Maia bug class exactly: a single atomic loop transfers *all* of a multi-token order's escrowed inputs to one hard-coded recipient address, with no ability for the recipient to redirect the payout. If any one of the escrowed input tokens is a blacklist-capable ERC20 (e.g. USDC/USDT-style) and the order's `user` address becomes blacklisted on that specific token, the entire refund transaction reverts — permanently freezing every other (non-blacklisted) token escrowed for that same order, since no retry-with-different-address path exists.

### Finding Description
`IntentsBase._withdraw` [1](#0-0)  iterates over `body.tokens` and sends each one to a single `beneficiary` computed from `body.beneficiary`. For refunds, `beneficiary` always equals `order.user`, set unconditionally in both cancellation paths:

- `_cancelFromSource` builds the withdrawal context with `beneficiary: order.user` [2](#0-1) .
- `_cancelFromDest` dispatches the `RefundEscrow` request with `order.user` as the fixed beneficiary [3](#0-2) .

Neither the order creator nor anyone else can specify an alternate recipient for the refund — `order.user` is baked into the order at creation time and is not settable at cancel/redeem time. When the refund is finally executed via `onAccept`/`onGetResponse`, `_withdraw` loops through every escrowed input token in a single transaction and calls `safeTransfer(beneficiary, amount)` for each [4](#0-3) . If the order escrowed multiple input tokens (e.g., USDC + USDT + DAI) and `order.user` is later blacklisted on just one of them, that single `safeTransfer` reverts, unwinding the entire transaction — including the transfers of the other, non-blacklisted tokens that would otherwise have succeeded. `_orders[commitment][token]` accounting is also rolled back, so the order is never marked filled and there is no partial-refund fallback.

This is structurally identical to the reported `redeemDeposit` bug: atomic all-or-nothing redemption across N tokens, sent to one address that cannot be substituted, so a blacklist on any single token locks out redemption of the rest.

### Impact Explanation
Once `order.user` is blacklisted on any one escrowed token, the order can never be refunded or finalized through the current code path — every attempt to call `_withdraw` for that commitment reverts identically. This is a permanent freezing-of-funds condition for potentially the full value of a multi-asset order, not just the blacklisted token, since the loop is atomic and all input tokens for that commitment are locked in the same escrow entry. There is no admin sweep/override function visible for stuck per-order escrow balances (as distinct from `SweepDust`, which only handles protocol fee dust, not user escrow) [5](#0-4) . This satisfies "permanent freezing of funds" and is reachable by any unprivileged user simply placing a multi-token order and later being blacklisted on one input asset (or being blacklisted before cancellation, e.g., via a compliance action against a common stablecoin).

### Likelihood Explanation
Likelihood is realistic but conditional: it requires (a) an order with multiple escrowed input tokens, at least one of which implements an allow/deny-list (USDC, USDT, and similar centrally-administered stablecoins all have this capability), and (b) `order.user` being blacklisted on that token by the token issuer. This is outside attacker control directly, but it is a foreseeable real-world event (regulatory/compliance blacklisting) rather than a hypothetical edge case, and once triggered it is trivially and permanently reproducible — every subsequent call to the refund flow for that commitment fails the same way.

### Recommendation
Decouple per-token transfer failures so one blacklisted token cannot block redemption of the others, and/or allow the beneficiary to redirect failed transfers:
- In `_withdraw`, wrap each `safeTransfer`/`_sendValue` call in a try/catch (or use a pull-based claim pattern) so a revert on one token does not roll back the others; track any token that failed to transfer in a per-user "stuck balance" mapping that can be claimed later to an address the depositor specifies.
- Alternatively, add a governance/permissionless sweep function allowing the order's `user` (or, after a timeout, anyone) to redirect undeliverable escrowed tokens to an alternate address they control, similar to the recommended fix in the referenced Maia report (`redeemDeposit(_depositNonce, _receiver)`).
- At minimum, split `_withdraw` into per-token idempotent calls (e.g., a `withdrawToken(commitment, tokenIndex)` external entrypoint) so a failing token doesn't gate the others, while preserving `_filled`/fee finalization logic once all deliverable tokens have been claimed.

### Proof of Concept
Conceptual reproduction (mirrors the original PoC's structure):
1. User places a cross-chain order via `IntentGatewayV2`/`ExtrinsicIntents` with `order.inputs` = [USDC, USDT, DAI], escrowing all three, with `order.user = attackerOrVictim`.
2. Order expires unfilled; user calls `cancelOrder()` → `_cancelFromDest` dispatches `RefundEscrow` with `beneficiary = order.user` fixed [3](#0-2) .
3. Before the refund message is relayed and accepted on the source chain, USDT (or USDC) issuer blacklists `order.user`'s address.
4. Hyperbridge delivers the `RefundEscrow` message; `onAccept` calls `_withdraw(body, true, true)` [6](#0-5) .
5. The loop in `_withdraw` reaches the blacklisted token's `safeTransfer(beneficiary, amount)` [4](#0-3)  which reverts ("blacklisted").
6. The entire `onAccept` call reverts; `_orders[commitment][*]` is never decremented, `_filled` is never set, and USDC/DAI (non-blacklisted tokens) remain escrowed and unreachable alongside the blacklisted USDT, with no way to redirect the refund to a different address.

    /**
     * @dev Handles incoming cross-chain post requests dispatched via Hyperbridge.
     * The first byte of the request body encodes the `RequestKind`, which determines
     * the action to take:
     *
     * - RedeemEscrow: Releases escrowed tokens to the solver who filled the order
     *   on the destination chain. Authenticated against the registered gateway instance.
     * - RefundEscrow: Refunds escrowed tokens to the original user after a successful
     *   cancellation from the destination chain. Authenticated against the registered gateway.
     * - NewDeployment: Registers a new gateway instance for a state machine. Only
     *   Hyperbridge itself may dispatch this request.
     * - UpdateParams: Updates the gateway's configuration parameters and per-destination
     *   protocol fees. Only Hyperbridge may dispatch this request.
     * - SweepDust: Transfers accumulated protocol dust to a specified beneficiary.
     *   Only Hyperbridge may dispatch this request.
     * - Execute: Delegatecalls the current implementation with the rest of the body, the host
     *   still `msg.sender`, so the host-only functions (`upgradeToAndCall`, `setRelayer`) are
     *   reachable. Reverts bubble up unchanged. Only Hyperbridge may dispatch this request.
     *
     * @param incoming The incoming post request from Hyperbridge.
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }
