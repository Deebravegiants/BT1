### Title
Arbitrary token exfiltration via `EmporiumOperation` chaining when `erc20TokenAddresses=[]` bypasses all balance accounting - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` and `Hinkal.transact` only ever check balance changes for tokens listed in `circomData.erc20TokenAddresses`; every accounting loop is bounded by `erc20TokenAddresses.length`. When that array is empty (a valid input on the Min circuit path, since `MainEVMCircuitMin.circom` places no constraint on token balances at all), an attacker can chain arbitrary `EmporiumOperation` calls that move any ERC20 balance held by the shared `Emporium` contract straight to themselves with zero on-chain accounting.

### Finding Description
The claimed equality is: **tokens leaving Emporium for a given ERC20 == `-deltaAmountChanges[token]`** (i.e., every outflow from Emporium must be reflected in the signed `amountChanges`/`deltaAmountChanges` for that token). This equality is only enforced inside a loop bounded by `circomData.erc20TokenAddresses.length`: [1](#0-0) 

and again at the outer `Hinkal.transact` level: [2](#0-1) 

If `circomData.erc20TokenAddresses = []`, both loops execute zero iterations, so **no equality is ever evaluated** for any token — it is not "false", it is simply never checked. `getBalancesForArray` also returns an empty array in that case [3](#0-2) , so `balancesBefore`/`balancesAfter` in `runAction` carry no information about the reward token either.

Meanwhile, `runAction` executes attacker-supplied `EmporiumOperation[] ops` with essentially no restriction on `endpoint`/`callData`/`value` for "stateless" calls (Case 2), which are executed directly from the `Emporium` contract's own address (`op.endpoint.call{value: op.value}(op.callData)`), only blocking the `callHinkalWallet`/`doSendToRelay` selectors: [4](#0-3) 

Crucially, when `stack.signerAddress == address(0)`, `verifyWallet` skips the EIP-712 signature check entirely and only marks the (attacker-chosen) `emporiumMessage` as used: [5](#0-4) 

This means the entire `ops` array (endpoint, callData, value) is fully attacker-controlled with no third-party authorization required, as long as the attacker is the one producing a valid ZK proof for their own `transact()` call (they are an ordinary unprivileged EOA who can always do this for their own UTXOs/deposits).

The circuit that authorizes this Min-path call, `MainEVMCircuitMin.circom`, only computes `message <== Poseidon([messageSeed])`; the public inputs `calldataHash` and `outTimeStamp` are declared but never used in any constraint: [6](#0-5) 

So no circuit-level constraint ties the actually-executed `ops` (or the token movements they cause) back to `erc20TokenAddresses`/`amountChanges`. All accounting responsibility is delegated to the Solidity loops described above, and those loops are empty when `erc20TokenAddresses=[]`.

**Exploit flow:**
1. An earlier, legitimate transact (by any user) uses a "stateless" `EmporiumOperation` to interact with a staking/lending contract, whose calls are made with `msg.sender = Emporium` (the shared contract address, not a per-user wallet). This creates a position/reward accrual keyed to `Emporium`'s address, a global shared identity across all Hinkal users.
2. Attacker (any unprivileged EOA) crafts a Min-path `transact()` with `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and:
   - `ops[0]`: `endpoint = stakingContract, callData = claim()` → rewards land on `Emporium`'s balance.
   - `ops[1]`: `endpoint = rewardToken, callData = transfer(attacker, amount)` → tokens sent directly from `Emporium` to the attacker.
3. `verifyWallet` skips signature verification (`signerAddress == 0`), both ops succeed, `payRelayFees`/balance loops iterate zero times because `erc20TokenAddresses.length == 0`, and `runAction` returns an empty `utxoSet`.
4. `Hinkal.transact`'s own balance/slippage loop also iterates zero times over the same empty array, so nothing catches the stolen tokens.

Existing guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`, `nonReentrant`) all pass normally for this call because the attacker only needs a valid proof for their own UTXOs/no-deposit transact — none of them constrain the *content* of `ops` or tie it to `erc20TokenAddresses`.

### Impact Explanation
This allows theft of any ERC20 (or ETH) balance held by the `Emporium` contract that is not listed in `erc20TokenAddresses` for that call — including protocol-held reward/fee tokens, dust, or funds/positions accrued to the shared `Emporium` identity by other users' prior legitimate interactions. This is direct theft of protocol/other-user-attributable value with no proof or nullifier constraint preventing it, matching Critical/High impact (theft of protocol/relay-held funds, unauthorized calls/asset movement never constrained by the proof). It is repeatable for every token balance the attacker can get `Emporium` to accumulate and then drain.

### Likelihood Explanation
Preconditions: (1) `Emporium` must hold or be made to hold a drainable balance of some ERC20 token (via a prior legitimate "stateless" op interaction, e.g., staking rewards, or simply stray/fee tokens sent to `Emporium`), and (2) the attacker must be able to submit a Min-path `transact()` with `erc20TokenAddresses=[]` and a crafted `EmporiumOperation[]`. Both are achievable by any unprivileged EOA who can deposit their own funds and generate their own proof — no privileged role or victim key is required. The attack cost is just gas plus proof generation; it is fully repeatable and requires no special timing beyond the prior deposit/accrual existing on-chain.

### Recommendation
Do not gate the balance/accounting checks by `circomData.erc20TokenAddresses.length` when arbitrary external calls (`EmporiumOperation.endpoint.call`) are permitted. Either (a) require that `erc20TokenAddresses` includes every token address touched by any `op.endpoint`/token transferred during `ops` execution (enforced by decoding calldata or maintaining an explicit allow-list per op), or (b) remove the ability to skip signature verification when `signerAddress == address(0)` for stateless ops that can call arbitrary token/staking contracts, or (c) snapshot and diff the full set of tokens Emporium could plausibly hold (not just the caller-declared subset) before returning control, reverting if any token balance decreased without being declared.

### Proof of Concept
Hardhat test plan:
1. Deploy `Emporium` (`EmporiumUpgradeable`), a mock staking contract that accrues reward tokens to `msg.sender` on `stake()`/`claim()`, and a mock reward `ERC20`.
2. User A performs a legit Min-path `transact()` with a stateless `EmporiumOperation` calling `stakingMock.stake(amount)` from `Emporium`'s context, moving tokens into the staking contract as `Emporium`.
3. Advance time so rewards accrue to `Emporium`'s address in the mock staking contract.
4. Attacker (unrelated EOA, own deposit/UTXO) submits a Min-path `transact()` with `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [ {stakingMock, false, 0, claim()}, {rewardToken, false, 0, transfer(attacker, rewardAmount)} ]}`.
5. Assert: `rewardToken.balanceOf(attacker)` increases by `rewardAmount`, and `rewardToken.balanceOf(emporium)` returns to (or below) its pre-claim value — while `circomData.amountChanges`/`deltaAmountChanges` for `rewardToken` is undefined (token absent from `erc20TokenAddresses`), i.e. tokens-leaving-Emporium ≠ `-deltaAmountChanges` (no such entry exists), and both the `Hinkal.transact` balance loop and `EmporiumUpgradeable.runAction` balance loop execute zero iterations (assert via event/trace count or by instrumenting a mock erc20 with a counter incremented only inside `getERC20OrETHBalance`).
