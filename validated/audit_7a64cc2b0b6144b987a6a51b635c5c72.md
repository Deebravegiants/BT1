## Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` verifies solely that the *body* was signed with the app's `api_secret_key`. The `shop` (shop-domain header) that `Webhooks::Registry.process` passes on to application handlers as the tenant identifier is never part of the signed material, so its authenticity is never actually checked.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read straight from an attacker-controllable HTTP header with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, i.e. only over the raw body: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the host application's handler: [4](#0-3) 

This breaks the identity binding: `shop authenticated by the app's secret` should equal `shop attributed to the webhook payload`, but here `shop` is parsed from headers that are outside the HMAC's coverage. Since `api_secret_key` is a single, app-wide secret shared across *all* shops that install the app (not a per-shop secret), any merchant who has installed the app can:

1. Install the app on their own (attacker-controlled) shop and receive a legitimately Shopify-signed webhook (`body`, valid `X-Shopify-Hmac-Sha256`).
2. Replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds, because it only checks the body bytes against the shared secret — the header substitution is invisible to the check.
4. `Registry.process` calls the host app's handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `shop` is now the victim's domain, causing the host application to store/act on data under the wrong tenant.

### Impact Explanation
This allows a low-privilege, unprivileged internet user (any merchant capable of installing the app on their own store) to make the library-provided `HmacValidator`/`Registry.process` pipeline report a validly-signed webhook as belonging to an arbitrary victim `shop`. Any host application relying on `request.shop` / `WebhookMetadata#shop` from this gem to select the tenant record to write into is exposed to cross-tenant data corruption/confusion — satisfying the "cross-tenant access" Critical impact category, since the binding "shop cryptographically authenticated" vs "shop attributed to the webhook data" does not hold.

### Likelihood Explanation
Any actor who can install the target app on a shop they control (a normal, unprivileged onboarding flow, not requiring the app's `api_secret_key`, an access token, or social engineering) can capture a genuine `(body, hmac)` pair from their own webhook deliveries and replay it with a forged shop-domain header against the app's public webhook endpoint. No secret material or elevated access is needed — likelihood is high wherever the host application trusts `request.shop`/`WebhookMetadata#shop` for tenant selection without additional verification.

### Recommendation
Bind the shop identity into the signed content that `HmacValidator` checks, or otherwise cryptographically tie `shop` to the verified payload before it is handed to `Registry.process`/handlers — e.g., include the `shop-domain` header value in `Webhooks::Request#to_signable_string`, or cross-check `request.shop` against session/installation records keyed by an independently-verified identifier before trusting it as the tenant for the webhook.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers `orders/create`. Shopify sends a webhook to the app's registered endpoint with a body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)` (they control the receiving server or a proxy in front of it) and resends the identical `(B, H)` pair to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request#hmac` and `#to_signable_string` derive the same `H` and `B` as before — see: [5](#0-4) 
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and it matches `H`, so validation passes: [6](#0-5) 
5. `Registry.process` invokes the host handler with `shop: request.shop` set to `"victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com`: [7](#0-6)
