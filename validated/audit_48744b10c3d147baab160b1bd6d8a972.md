### Title
Escrowed intent funds cannot be recovered when `EvmHost` is frozen, since both delivery and timeout/GET-response recovery paths require `notFrozen` - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
`ExtrinsicIntents`/`IntentsBase` escrows user input tokens on the source chain when an order is created, and only releases them via one of three ISMP-mediated paths: a `RedeemEscrow`/`RefundEscrow` post request delivered through `onAccept`, or a GET-response delivered through `onGetResponse` after `_cancelFromSource`. All three recovery paths depend on `HandlerV2` processing incoming ISMP datagrams (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`), and every one of those entrypoints is gated by the `notFrozen(host)` modifier, which reverts whenever `EvmHost.frozen()` is `FrozenStatus.Incoming` or `FrozenStatus.All`. There is no alternate, permissionless emergency-withdrawal function on the gateway that lets a user reclaim escrowed input tokens while the host is frozen.

### Finding Description
Escrow is created and stored per-order in `_orders[commitment][token]` (referenced in `_cancelFromSource`, [1](#0-0) ) when a user submits a cross-chain intent. Releasing those funds back to the user or to the solver only happens through `_withdraw`, invoked from:
- `onAccept` for `RedeemEscrow`/`RefundEscrow` kinds, gated `onlyHost`: [2](#0-1) 
- `onGetResponse` after a GET query verifying the order wasn't filled: [3](#0-2) 

Both of these callbacks are only ever invoked by `EvmHost.dispatchIncoming`, which in turn is only reachable from `HandlerV2`'s message-processing functions. Every one of those functions — `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`, and `handleConsensus` — carries the `notFrozen(host)` modifier: [4](#0-3) 

This modifier reverts with `HostFrozen()` whenever `host.frozen()` returns `FrozenStatus.Incoming` or `FrozenStatus.All`: [5](#0-4) [6](#0-5) [7](#0-6) 

`EvmHost.setFrozenState` can be called by the host `admin` (or the handler) at any time, e.g. during an emergency response to a compromised consensus client or exploited bridge module: [8](#0-7) 

Once the host is frozen with `Incoming` or `All`, `handlePostRequestTimeouts`/`handleGetRequestTimeouts` — the very functions that would normally let a user reclaim funds for an undelivered or expired request — are themselves blocked. This means a user who has already escrowed funds in `IntentGatewayV2`/`ExtrinsicIntents` (or analogously, tokens locked in `HyperFungibleToken`/`WrappedHyperFungibleToken` pending an in-flight `send()`) has no way to recover them for as long as the freeze persists, since:
1. Delivery of `RedeemEscrow`/`RefundEscrow` requests is blocked.
2. Delivery of the GET response needed to trigger a cancellation refund is blocked.
3. Timeout processing that would otherwise let `onPostRequestTimeout`/`onGetTimeout` refund the user is also blocked (both `handlePostRequestTimeouts` and `handleGetRequestTimeouts` require `notFrozen`).
4. There is no separate, unprivileged "emergency withdraw" function on the gateway/token contracts that bypasses the ISMP handler pipeline.

The contract's `Pausable` modifiers on the app level (`whenNotPaused` on `HyperFungibleToken`/`WrappedHyperFungibleToken`) are a related, narrower instance of the same class: pausing the app prevents outbound `send()` and inbound `onAccept()`, but a *host-level freeze* (needed to actually stop an active consensus/verification exploit) additionally suspends the timeout path that these apps rely on to eventually unwind stuck funds.

### Impact Explanation
If the host must remain frozen for an extended period (e.g., while a compromised consensus client or exploited proof-verification path is fixed and redeployed, which can require governance action across multiple chains), any user funds already escrowed in `IntentGatewayV2`-style intents, or tokens already burned/locked pending an in-flight `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer, are frozen along with the protocol — with no way for the affected user to reclaim them even though the freeze was meant only to stop *new* malicious activity, not to hold existing legitimate deposits hostage. This is a permanent-freezing-of-funds condition for as long as governance takes to resolve the incident and unfreeze the host, which can be an unbounded/lengthy multi-chain governance process.

### Likelihood Explanation
Freezing the host is an intentional emergency control exercised by the `admin` (and, per `tesseract/consensus/admin-relayer`, automated relayer tooling routinely wraps consensus submission with freeze/unfreeze around `handleConsensus`), so the frozen state is a realistic and expected operational condition, not a contrived edge case. Any user who has escrowed funds in-flight at the moment of (or during) a freeze is affected; likelihood scales with how often freezes occur and how long they persist, both of which are outside a user's control.

### Recommendation
Provide a bypass in the escrow-recovery path that does not depend on `HandlerV2`'s `notFrozen` gate — for example, allow `handlePostRequestTimeouts`/`handleGetRequestTimeouts` (or a dedicated emergency-timeout function) to proceed even when the host is frozen for *incoming* delivery only, since timeouts are refund/rollback operations rather than new state-changing deliveries, and blocking them serves no security purpose while actively harming users. Alternatively, add an explicit, permissionless emergency-withdrawal function to `IntentsBase`/`ExtrinsicIntents` (and the `HyperFungibleToken`/`WrappedHyperFungibleToken` apps) that allows a user to reclaim their own escrowed/locked funds after their order's `deadline` or a message's `timeoutTimestamp` has passed, independent of the host's frozen status.

### Proof of Concept
1. User calls the source-chain intent-creation flow, escrowing `order.inputs` tokens into `IntentGatewayV2`/`ExtrinsicIntents`, recorded in `_orders[commitment][token]`.
2. Before the order is filled, the admin calls `EvmHost.setFrozenState(FrozenStatus.All)` in response to an unrelated security incident: [8](#0-7) .
3. The order's `deadline` passes without a fill. The user (or anyone) attempts `_cancelFromSource`, dispatching a GET request whose response must arrive via `HandlerV2.handleGetResponses`, which reverts with `HostFrozen()`: [5](#0-4) .
4. Alternatively, if the order was already filled on the destination and a `RedeemEscrow` post request was dispatched, its delivery via `handlePostRequests` is likewise blocked while frozen, and its eventual timeout recovery via `handlePostRequestTimeouts` is blocked too: [6](#0-5) .
5. The user's escrowed tokens sit in the contract with no code path to reach `_withdraw` until the host is unfrozen, which may take an indeterminate amount of time.
