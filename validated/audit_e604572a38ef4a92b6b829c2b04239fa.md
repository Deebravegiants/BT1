Audit Report

## Title
Attacker can front-run a `dest` account with a small vesting claim to permanently block the victim's legitimate vested claim - ([File: polkadot/runtime/common/src/claims/mod.rs])

## Summary
`claim`/`claim_attest` are unsigned extrinsics where `dest: T::AccountId` is fully caller-controlled and cryptographically bound only to the Ethereum signature over `dest`'s own bytes, not to any real ownership relationship between the signer and `dest`. `process_claim` gates vesting claims solely on `T::VestingSchedule::vesting_balance(&dest).is_some()`, a check on the destination account's *current* state rather than on whether the pending claim is the one that legitimately owns that destination, allowing any holder of an unrelated Ethereum claim with a vesting component to pre-empt and permanently block a different claimant's vested claim to the same `dest`.

## Finding Description
`claim` recovers the Ethereum signer from a signature over `dest` and forwards to `process_claim` without any binding of `dest` to a specific claim beyond the signature itself: [1](#0-0) 

`process_claim` then checks `T::VestingSchedule::vesting_balance(&dest).is_some()` to decide whether to reject the vesting branch, and calls `T::VestingSchedule::add_vesting_schedule(&dest, ...)` to install a schedule, with the `Claims`/`Vesting`/`Signing` storage for the *signer* only cleared afterward via `Claims::<T>::remove(&signer)`: [2](#0-1) 

Because `Claims`/`Vesting` are keyed by `EthereumAddress` and consumed per-signer on success, while `dest` is an unrelated, caller-supplied parameter checked only against the destination account's aggregate vesting state, any account already holding a valid (even root-minted, dust-value) Ethereum claim with a `vesting_schedule` can call `claim(dest = X, sig)` to install a vesting lock on arbitrary account `X` first. `claim_attest` has the identical `dest`-driven flow: [3](#0-2) 

A subsequent, unrelated legitimate claimant targeting the same `dest = X` will then hit `Error::VestedBalanceExists` and be permanently unable to complete their vested claim into that destination, since the check only inspects `dest`'s current vesting state, never whether the *pending claim* is the one entitled to install it. The only preconditions on being able to mint such an attacker claim are via genesis config or root-only `mint_claim`: [4](#0-3) 

## Impact Explanation
The impact is a targeted, permanent denial-of-claim: a victim's `claim`/`claim_attest` call to a specific `dest` account will always revert with `VestedBalanceExists` as long as the attacker's earlier-installed vesting schedule remains active on that account. This is a genuine account-state griefing vector rooted in the mismatch between the per-signer claim identity and the per-account vesting-collision check, though it does not destroy the victim's underlying claim balance (still recorded under the victim's own Ethereum address) and is mitigable by the victim choosing a different destination account.

## Likelihood Explanation
Exploitability requires the attacker to already control a pre-existing Ethereum claim (from genesis distribution or root-issued `mint_claim`) that carries a vesting schedule — `Claims`/`Vesting` entries are not something an arbitrary unprivileged actor can create for themselves, and each such claim is single-use since `Claims::<T>::remove(&signer)` consumes it on success. This makes the "attacker" pool a closed, historical set of original DOT-sale claim holders rather than any arbitrary user, and the attacker must additionally front-run the victim's specific choice of `dest`. This is a legitimate but narrow-surface, low-severity griefing bug rather than a broadly and repeatably exploitable vulnerability by generic unprivileged users.

## Recommendation
Bind the vesting-collision check to claim provenance rather than solely to `dest`'s current account state — e.g., track which claim/signer installed an existing vesting schedule on a given `dest` and only reject collisions from *unrelated* claims, or require an opt-in/ownership proof from `dest` before an unrelated claim can install a vesting lock on it, or adopt `merge_schedules`-style semantics instead of hard-failing on any pre-existing schedule.

## Proof of Concept
In `polkadot/runtime/common/src/claims/tests.rs`: register two Ethereum claims via genesis/`mint_claim` — a small attacker claim (key `six`) with a vesting schedule, and a separate, unrelated legitimate vesting claim (Alice's key). Call `Claims::claim(RuntimeOrigin::none(), 42, sig_from_six(42))`, confirm success and that `<Test as Config>::VestingSchedule::vesting_balance(&42)` is now `Some`. Then call `Claims::claim(RuntimeOrigin::none(), 42, sig_from_alice(42))` and confirm it returns `Error::<Test>::VestedBalanceExists`, while Alice's original `Claims`/`Vesting` entries remain untouched, demonstrating the permanent block on `dest = 42` for her unrelated legitimate claim.

	fn process_claim(signer: EthereumAddress, dest: T::AccountId) -> sp_runtime::DispatchResult {
		let balance_due = Claims::<T>::get(&signer).ok_or(Error::<T>::SignerHasNoClaim)?;

		let new_total =
			Total::<T>::get().checked_sub(&balance_due).ok_or(Error::<T>::PotUnderflow)?;

		let vesting = Vesting::<T>::get(&signer);
		if let Some(_) = vesting {
			if T::VestingSchedule::vesting_balance(&dest).is_some() {
				return Err(Error::<T>::VestedBalanceExists.into());
			}

			// A vesting schedule installs a balance lock, which requires the account to stay alive,
			// otherwise it is dusted and the lock placed on a non-existent account. The `dest` may
			// already hold funds, so a small claim that tops an existing account over the ED is
			// valid.
			let free_after = CurrencyOf::<T>::free_balance(&dest).saturating_add(balance_due);
			ensure!(
				free_after >= CurrencyOf::<T>::minimum_balance(),
				Error::<T>::ClaimBelowExistentialDeposit,
			);
		}

		// We first need to deposit the balance to ensure that the account exists.
		let _ = CurrencyOf::<T>::deposit_creating(&dest, balance_due);

		// Check if this claim should have a vesting schedule.
		if let Some(vs) = vesting {
			// This can only fail if the account already has a vesting schedule or its balance is
			// below the existential deposit, both of which are checked above.
			T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)
				.map_err(|_| Error::<T>::VestedBalanceExists)?;
		}

		Total::<T>::put(new_total);
		Claims::<T>::remove(&signer);
		Vesting::<T>::remove(&signer);
		Signing::<T>::remove(&signer);
