#### Title
Overcapture extension self-reports "configured" even when zero wavelengths are captured, allowing a QR-controlled bypass of anti-spoof frame capture - (File: src/plans/biometric_capture/overcapture.rs)

#### Summary
The overcapture extension derives `overcapture_wavelengths` from a QR-supplied `wavelength_parameter` string parsed via `parse_u8_octal`, which silently falls back to a default on unparseable input but does not reject `0` explicitly. If the parameter is `0` (or parses to `0`), `Configuration::parse_wavelength_configuration` returns an empty `VecDeque`, so `extension_finished` returns `true` immediately without ever invoking `perform_overcapture`, yet `Plan::run` still unconditionally attaches `ExtensionReport::Overcapture(self.report)` to the pipeline output.

#### Finding Description
`Plan::from<biometric_capture::Plan>` reads `signup_extension_config.parameters` (sourced from QR-scan configuration, see `src/plans/qr_scan/user.rs`) and computes `wavelength_parameter` via `parse_u8_octal(wavelength, 1)` [1](#0-0) . `parse_u8_octal` uses `u8::from_str_radix(src, 8).unwrap_or(default)` [2](#0-1) , so a literal `"0"` parses successfully to `0` rather than falling back to the default of `1`. `Configuration::parse_wavelength_configuration(0)` formats `0` as binary `"000"`, finds no `'1'` bits, and returns an empty `VecDeque<IrLed>` [3](#0-2) .

In `Plan::run`, the loop `while !self.extension_finished(orb).await? { self.perform_overcapture(orb).await?; }` relies on `extension_finished` to pop from `overcapture_wavelengths`; when it's empty, `extension_finished` immediately calls `self.reset_extension()` and returns `true` on the very first check, so the loop body (and therefore `perform_overcapture`, which is the only place extra anti-spoof frames are actually captured) never executes [4](#0-3) [5](#0-4) . Despite this, `self.report` (built at construction time solely from the `Configuration`, independent of whether any overcapture actually ran) is unconditionally passed to `run_post` as `ExtensionReport::Overcapture(self.report)` [6](#0-5) [7](#0-6) . There is no code path in `overcapture.rs` that conditions the report, or omits `ExtensionReport::Overcapture`, based on whether `overcapture_wavelengths` was empty. Downstream consumers of `ExtensionReport::Overcapture` (fraud/enroll pipeline, per `debug_report.rs`) thus receive a report entry indicating the overcapture extension was configured/present without any indication that zero frames were captured, unless those downstream consumers separately inspect `overcapture_configuration.overcapture_wavelengths` for emptiness — which was not verified to exist in the explored code.

#### Impact Explanation
If the fraud/anti-spoof pipeline treats presence of `ExtensionReport::Overcapture` as evidence that additional multi-wavelength anti-spoof frames were captured (as the question's proof idea implies), an attacker who controls the QR extension parameter could present `"0"` to disable actual overcapture capture while the report still reflects a "configured" extension. This could weaken the anti-spoof/liveness signal used during enrollment, matching a liveness/fraud-bypass class of impact under the Orb bounty scope, contingent on how the fraud pipeline consumes `overcapture_configuration.overcapture_wavelengths`/`Report`.

#### Likelihood Explanation
Reachability requires only presenting a QR code (or otherwise supplying the biometric-capture extension configuration string) with an overcapture wavelength parameter of `"0"` — no special privileges, keys, or hardware tampering. The parsing path (`parse_u8_octal`, `parse_wavelength_configuration`) confirmed empty-wavelength behavior deterministically and repeatably. However, whether this is actually exploitable end-to-end depends entirely on unverified downstream logic (in `debug_report.rs` or the fraud pipeline) that consumes `ExtensionReport::Overcapture` — I was unable to fully trace how `Report`/`Configuration` are consumed by the fraud/enroll pipeline within the available tool budget, so I cannot confirm whether existing checks there already treat an empty `overcapture_wavelengths` as fail-closed (not-performed).

#### Recommendation
Make the report conditional: only emit `ExtensionReport::Overcapture` (or mark it explicitly as "not performed") when `overcapture_wavelengths` was non-empty at construction time, and/or have `extension_finished`/`Plan::run` track whether `perform_overcapture` actually executed at least once, embedding that boolean in `Report` so downstream fraud logic can fail-closed on self-reported-but-unperformed overcapture.

#### Proof of Concept
Unit test in `overcapture.rs` (or an integration test against `biometric_capture`):
1. Construct `Configuration::new(0, Duration::from_millis(1000))`.
2. Assert `configuration.overcapture_wavelengths.is_empty()`.
3. Simulate `Plan::run`'s loop logic: call `extension_finished` and assert it returns `true` on the very first invocation (before any `perform_overcapture` call), i.e., assert a counter/flag tracking `perform_overcapture` invocations remains `0`.
4. Assert that despite step 3, the `Report`/`ExtensionReport::Overcapture(report)` value produced is identical in shape/presence to a run where `overcapture_wavelengths` was non-empty and frames were captured — demonstrating downstream code cannot currently distinguish "configured but never executed" from "executed" purely from the `ExtensionReport::Overcapture` variant, unless it also inspects `overcapture_configuration.overcapture_wavelengths` was empty at report-build time (pre-consumption), which the current code does not guarantee since `reset_extension`/`reset()` recomputes `overcapture_wavelengths` from `wavelength_parameter` again after each eye rather than reporting actual captured counts.

            3,
