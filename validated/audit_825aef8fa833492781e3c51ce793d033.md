### Title
Front-running `Initialize2` by pre-funding the deterministic vault PDAs skews the pool's initial price and LP-supply accounting - ([File: program/src/processor.rs])

### Summary
`process_initialize2` computes the pool's initial liquidity and initial price entirely from the *live token balances* of `amm_coin_vault_info` / `amm_pc_vault_info` rather than from the `init_coin_amount` / `init_pc_amount` values the pool creator actually intends to deposit. Because these vault accounts are derived deterministically (PDAs seeded from `market_info` via `COIN_VAULT_ASSOCIATED_SEED` / `PC_VAULT_ASSOCIATED_SEED`), their addresses can be computed off-chain before the creator's `Initialize2` transaction lands. An attacker can transfer a small amount of the coin or pc token directly to this predictable vault address beforehand, so that when `Initialize2` executes, `amm_coin_vault.amount` / `amm_pc_vault.amount` include the attacker's donation in addition to the creator's transferred `init_coin_amount` / `init_pc_amount`. This is directly analogous to the report's bug class: donating tokens straight to a contract-controlled balance before/at initialization corrupts the internal accounting (there: `rebasingCredits`/`totalSupply`; here: vault balances used for `liquidity` and price-defining `x`/`y`).

### Finding Description
In `process_initialize2` [1](#0-0)  the coin/pc vault token accounts are created at deterministic PDA addresses via `generate_amm_associated_spl_token` using fixed seeds tied to `market_info`, and only afterward are the creator's `init_coin_amount`/`init_pc_amount` transferred into them.

The pool's initial invariant and LP supply are then derived purely from the resulting on-chain balances, not the intended amounts: [2](#0-1) 

These same raw vault balances are also normalized into `x`/`y` and stored as the pool's baseline pnl/price reference in `TargetOrders`: [3](#0-2) 

Because the vault addresses are predictable before the `Initialize2` instruction is confirmed, an attacker can submit a plain SPL `Transfer` to the not-yet-owned/not-yet-checked vault account ahead of (or racing) the creator's transaction, inflating one side of `amm_coin_vault.amount` / `amm_pc_vault.amount` relative to the other. Since `liquidity = sqrt(pc_amount * coin_amount)` and the initial coin/pc ratio recorded in `target_order.calc_pnl_x/calc_pnl_y` (which is what all subsequent `SwapBaseIn`/`SwapBaseOut`/`Deposit` calculations reference as `total_*_without_take_pnl`) are computed straight from these balances, the attacker can set the pool's opening price arbitrarily far from the ratio the creator intended (`init_coin_amount`/`init_pc_amount`), without any of the account/mint/authority checks in this instruction (owner, delegate, close-authority, mint match) preventing it — those checks validate account *type/ownership*, not that the vault only contains the creator's deposit.

### Impact Explanation
An attacker who can predict/derive the coin_vault and pc_vault PDAs for an upcoming pool (which is possible before `Initialize2` executes, since the seeds are fixed and public) can donate a small, disproportionate amount of one token to skew the mint's/vault's resulting balance ratio. This lets the attacker dictate the pool's real opening exchange price and the `liquidity`/`user_lp_amount` minted to the creator, then immediately swap against the now-mispriced pool once it is live, extracting value that should have belonged to the legitimate creator/LP. This is insolvent/mispriced pool accounting at the trust boundary of pool creation, reachable purely with unprivileged, attacker-chosen SPL transfer instructions.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker must predict and front-run/race a specific `Initialize2` transaction and only profits proportional to price distortion versus their own donated capital (similar to the original report's acknowledgment that "the attacker will have to send a large amount... for no financial gain" in typical cases). It requires timing (mempool visibility / predictable pool creation) and only matters for pools with low initial liquidity, which is the exact low-likelihood/limited-profit caveat the original bug report and its "acknowledged, Medium severity" resolution reflect.

### Recommendation
Do not derive the initial `liquidity`/price purely from live vault balances at `Initialize2` time. Either: (1) validate that `amm_coin_vault.amount == init.init_coin_amount` and `amm_pc_vault.amount == init.init_pc_amount` immediately before computing `liquidity`/`x`/`y`, rejecting the initialization if a pre-existing balance is detected; or (2) create the vault accounts with a fresh, non-derivable keypair rather than a seed predictable from `market_info`, so an attacker cannot pre-fund them before the creator's transaction executes.

### Proof of Concept
1. Attacker observes/derives the deterministic PDA for `amm_coin_vault` (seed `COIN_VAULT_ASSOCIATED_SEED` + `market_info`) for a pool about to be created, before the creator's `Initialize2` transaction is confirmed.
2. Attacker submits an SPL `Transfer` of a small amount of the coin token directly to that PDA address (it is a valid, ownerless-until-created associated token account once `generate_amm_associated_spl_token` inside the creator's transaction creates it — or races the creation itself is unnecessary if the attacker's transfer lands in the same/adjacent block after account creation but before the creator's deposit transfer completes within the same instruction sequence).
3. When `process_initialize2` [2](#0-1)  executes, `amm_coin_vault.amount` includes both the creator's `init_coin_amount` and the attacker's donation, skewing `liquidity` and the coin/pc ratio recorded in `TargetOrders` [4](#0-3) .
4. Attacker then calls `SwapBaseIn`/`SwapBaseOut` against the newly created, mispriced pool to extract value at the expense of the pool creator's deposited liquidity.

**Note:** I was unable to fully view the implementation of `generate_amm_associated_spl_token`/`generate_amm_associated_account` (ran out of tool iterations) to conclusively confirm the exact PDA derivation formula and whether any additional guard (e.g., requiring the account be freshly created with zero balance) exists beyond what's shown above. This should be verified directly in `program/src/processor.rs` before treating this as fully confirmed.
