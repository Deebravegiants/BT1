### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` (tenant identity) that is handed to the app's webhook handler is read from an unauthenticated header that is never included in the signed material. This mirrors the reported bug class: a field is acted upon by the system without being covered by the cryptographic binding that is supposed to guarantee its integrity.

### Finding Description
`Webhooks::Registry.process` verifies webhook authenticity with: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body: [3](#0-2) 

However, `shop` (the tenant identifier) is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the signed payload: [4](#0-3) 

`Registry.process` then forwards this unauthenticated `shop` value directly to the application's webhook handler as the tenant identity for the event, alongside the (authenticated) body: [5](#0-4) 

Because every installation of a given app shares the same `api_secret_key`, a valid `(raw_body, hmac)` pair obtained from a genuine webhook delivered to one shop (e.g., the attacker's own store) remains cryptographically valid for that same body regardless of which shop domain header accompanies it. The equality the code should enforce — `authenticated_shop == shop_used_for_tenant_routing` — is never checked; instead the code only enforces `hmac(body) == hmac(body)`, leaving `shop` completely unauthenticated.

### Impact Explanation
An unprivileged internet user who controls one shop where the app is installed can capture a legitimately-signed webhook body (with its valid HMAC) and replay it against the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Registry.process` will accept the request as valid (HMAC check passes because only the body is verified) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. If the host application uses this `shop` field to route data updates, look up the right merchant record, or otherwise scope tenant data (the documented and expected usage), the attacker can inject fabricated webhook events attributed to another merchant's shop — a cross-tenant access/data-integrity break using only the attacker's own legitimate app installation, no stolen credentials required.

### Likelihood Explanation
Exploitation requires only that the attacker install the app on their own shop (a normal, unprivileged action) and capture one legitimate webhook delivery (many webhooks fire automatically, e.g. `app/uninstalled`, `orders/create` triggered by attacker's own actions). No access to `api_secret_key`, tokens, or other shops' data is needed. Likelihood is high for apps that trust `WebhookMetadata#shop` for tenant routing, which is the primary documented purpose of that field.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting an out-of-band header:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signable string, or
- Cross-check the header-provided `shop` against an independently verified source (e.g., a shop already recorded for a session/install lookup) before dispatching to the handler, and reject mismatches.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any webhook (e.g. uninstall) to capture a valid `{raw_body, x-shopify-hmac-sha256}` pair signed with the app's shared `api_secret_key`.
2. Send a new POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds (only body is checked, per `Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the request has nothing to do with that shop.
