### Title
CatFee API credentials logged in cleartext at `info` level, exposing bandwidth-purchasing account to log-file readers - (File: `tesseract/messaging/tron/src/lib.rs`)

### Summary
`TronClient::new` initializes the CatFee bandwidth-purchase integration and logs the entire `CatFeeConfig` — including `api_key` and `api_secret` — with `log::info!(target: LOG_TARGET, "CatFee integration enabled: {:#?}", catfee_config)`. Because `CatFeeConfig` derives plain `Debug` with no redaction, the raw HMAC signing secret and API key are written to the relayer's log output at the default `info` level (no elevated log level needed), matching the same bug class as CVE-2023-29471 (component logs its own auth config, leaking credentials into log files).

### Finding Description
`CatFeeConfig` is a plain struct with `#[derive(Debug, Clone)]` and fields `api_key: String`, `api_secret: String` with no masking `Debug` implementation: [1](#0-0) 

When a TRON chain is configured with CatFee credentials, `TronClient::new` constructs this config and logs it verbatim with the `{:#?}` (pretty Debug) formatter at `info` level — the default, always-on log level, unlike the original CVE which required `debug`: [2](#0-1) 

The source fields feeding this struct are `TronConfig::catfee_api_key` / `catfee_api_secret`, themselves also `Debug`-derived on the outer `TronConfig`: [3](#0-2) 

The `api_secret` is the HMAC-SHA256 signing key used to authenticate every CatFee order request (energy/bandwidth purchase for TRON transaction submission): [4](#0-3) 

Any party with read access to the relayer's log stream/file (log aggregation pipelines, shared hosts, container log drivers, support/monitoring tooling with log access but not config access) recovers the full `api_key`/`api_secret` pair in plaintext, since it is emitted unconditionally at `info` level on every relayer startup with CatFee configured.

### Impact Explanation
With the leaked `api_key`/`api_secret`, an attacker can forge valid `CF-ACCESS-SIGN` HMAC signatures for arbitrary CatFee API requests and place unauthorized energy/bandwidth purchase orders billed to the operator's CatFee account, draining the operator's CatFee balance/funds without their consent — this is a real-token/funds-loss primitive tied directly to the relayer's bandwidth-purchasing role, not merely an operational nuisance. This is worse than the upstream Alpakka Kafka issue because the leak occurs at `info` (default, always emitted) rather than requiring `debug` verbosity to be explicitly enabled.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where log output is centralized, shipped to third-party aggregators, or accessible to operators/support staff with lesser privilege than the config file itself (a very common operational split — config files are typically access-controlled tighter than log streams). No attacker action is required to trigger the leak; it happens automatically on every relayer start whenever CatFee integration is enabled, which is the intended/normal configuration path for TRON relaying.

### Recommendation
Implement a manual `Debug` (or a wrapper masking type, as already used elsewhere in the codebase, e.g. `maskSecret`/`maskToml` patterns in `sdk/packages/simplex/src/services/server/setup-api.ts`) for `CatFeeConfig` that redacts `api_key` and `api_secret`, and change the log call in `tesseract/messaging/tron/src/lib.rs` to log only non-sensitive fields (e.g., `api_base`, `timeout`) or a masked summary instead of the full `{:#?}` dump.

### Proof of Concept
1. Configure a TRON chain block with `catfee_api_key = "AKID..."` and `catfee_api_secret = "SuperSecretHmacKey"`.
2. Start `tesseract` (the relayer binary) with default log level (`info`, per `tesseract/relayer/src/config.rs` `setup_logging`, which defaults `EnvFilter::new("info")`): [5](#0-4) 
3. `TronClient::new` executes and logs the full `CatFeeConfig` including `api_secret` to stdout/journal at `info` level: [6](#0-5) 
4. Any reader of the resulting log stream (log aggregator, shared host, support engineer) now possesses `api_key`/`api_secret` and can compute valid `Base64(HMAC-SHA256(secret, timestamp+method+path))` signatures to submit arbitrary CatFee energy-purchase orders against the operator's account, per the documented signature scheme: [7](#0-6)

	/// Generate HMAC signature for API request
	///
	/// Signature format: Base64(HMAC-SHA256(secret, timestamp + method + requestPath))
	/// where requestPath includes query parameters
	fn generate_signature(&self, timestamp: &str, method: &str, request_path: &str) -> String {
		let message = format!("{}{}{}", timestamp, method, request_path);

		let mut mac = HmacSha256::new_from_slice(self.config.api_secret.as_bytes())
			.expect("HMAC can take key of any size");
		mac.update(message.as_bytes());

		BASE64.encode(mac.finalize().into_bytes())
	}

pub fn setup_logging() -> Result<(), anyhow::Error> {
	use tracing_subscriber::{fmt, prelude::*, EnvFilter};

	let filter = EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"));
	// `fmt::layer` defaults to auto-detect: ANSI on only if stdout is a
	// TTY. That breaks under systemd / `nohup` / docker where stdout is
	// piped to journald or a file and colors get silently dropped. Force
	// ANSI on; the standard `NO_COLOR=1` opt-out (https://no-color.org)
	// disables it for users who pipe through non-rendering tools. The
	// raw bytes survive into the journal, and `journalctl` pages through
	// `less -R` by default so colors render on read-out.
	let use_ansi = std::env::var_os("NO_COLOR").is_none();
	tracing_subscriber::registry()
		.with(fmt::layer().with_ansi(use_ansi))
		.with(filter)
		.init();
