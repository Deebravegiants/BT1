### Title
Excess native token sent to `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host contract instead of the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. The Uniswap V2 router refunds any leftover ETH (`msg.value - amounts[0]`) to its immediate caller via `TransferHelper.safeTransferETH(msg.sender, ...)`. Since `EvmHost` itself calls the router, `msg.sender` from the router's perspective is `EvmHost`, not the original end user, so the dust refund is sent back into the `EvmHost` contract's own balance rather than to the user who overpaid.

### Finding Description [1](#0-0) 
In `dispatch(DispatchPost memory post)`, when `msg.value > 0`, the function calls:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```
The `to` argument (`address(this)`) only controls where the purchased `feeToken` is sent — it has no bearing on the router's dust-ETH refund, which the router always sends to its direct caller (`msg.sender` inside the router call), i.e., `EvmHost`. The same pattern is repeated in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

Because a user calling any of these entry points is expected to estimate `msg.value` off-chain via `quote()` (documented as imprecise/sandwichable, see `docs/content/developers/evm/messaging/post-requests.mdx:236-238`), any slippage between the estimate and the actual on-chain swap price results in a nonzero `msg.value - amounts[0]` dust amount. That dust ends up not with the user, but stuck inside the `EvmHost` contract, since none of these dispatch functions ever forward or track a refund back to `_msgSender()`.

### Impact Explanation
This is a direct, permanent loss of user-supplied native tokens for every route that pays dispatch/relayer fees in native currency (POST dispatch, GET dispatch, and `fundRequest`). Given the frontend explicitly warns that `quote()` results are approximate and vulnerable to sandwich attacks, users routinely over-supply `msg.value` as a safety margin, guaranteeing repeated dust loss across the bridge's normal, unprivileged usage by any relayer, app, or end user dispatching a message with native-token payment. There is no code path in `EvmHost.sol` that returns or accounts for this trapped ETH to affected users (no `_requestCommitments`/`FeeMetadata` tracking of leftover native value, and no admin sweep function was found scoped for this purpose), so the funds are permanently frozen from the perspective of the user who sent them, matching a "permanent freezing of funds" impact class.

### Likelihood Explanation
High likelihood: this triggers on every single native-token dispatch call whenever the actual Uniswap swap price differs even slightly from what was estimated off-chain (the common case, since `quote()` is explicitly documented as an approximation not to be relied upon on-chain). No attacker action or special conditions are needed — it is a systemic side effect of normal usage by any unprivileged caller of `dispatch()`/`fundRequest()`.

### Recommendation
After calling `swapETHForExactTokens`, check the router's actual leftover ETH balance change (or capture `amounts[0]` return value) and explicitly refund the true dust `msg.value - amounts[0]` to `_msgSender()` via a low-level call, in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`). Alternatively, require `_msgSender()`, not `EvmHost`, to be the caller context the router refunds to — e.g., by having the calling app forward `msg.value` directly to the router with `to`/refund target set to the original sender, or by having `EvmHost` immediately forward any post-swap leftover balance increase to `_msgSender()`.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `msg.value` computed via off-chain `quote()`, e.g., intending to pay `post.fee` = 100 feeTokens.
2. Between quote time and execution, the Uniswap V2 pool price shifts (or the quote simply included a safety buffer), so `amounts[0] < msg.value`.
3. `swapETHForExactTokens` executes: swaps `amounts[0]` ETH for exactly `100` feeToken sent to `address(this)` (the `EvmHost`), then calls `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])` where `msg.sender` (from the router's perspective) is the `EvmHost` contract address.
4. The dust ETH (`msg.value - amounts[0]`) is added to `EvmHost`'s own balance (accepted because `EvmHost` implements `receive() external payable`), not returned to the user.
5. The user's transaction succeeds, the `PostRequestEvent` is emitted, but the user has permanently lost the dust ETH difference with no function in `EvmHost.sol` to reclaim it. Repeating this at scale (many dispatch calls) accumulates value that is effectively locked/donated involuntarily to the Host contract.

*Note: I was unable to fully verify from the index the exact body of `EvmHost`'s `receive()` function (only its existence was located via `grep_search`, confirmed by 2 matches in `evm/src/core/EvmHost.sol`) or whether any downstream admin-only sweep mechanism exists elsewhere in the codebase to redistribute this trapped balance back to users. If such a mechanism exists, it would only mitigate — not eliminate — the finding, since it does not return funds to the specific overpaying user.*
