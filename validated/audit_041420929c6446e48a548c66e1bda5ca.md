### Title
MultiKey / MultiEd25519 threshold accounts do not reject duplicate public keys, allowing a single signer to satisfy a k-of-n custody threshold - (File: `types/src/transaction/authenticator.rs`, `crates/aptos-crypto/src/multi_ed25519.rs`)

### Summary
The Sherlock finding is a single custody invariant: *"a k-of-n approval count must be backed by k distinct signers, not k signatures from fewer distinct keys."* `Consensus.checkSignatures` violated it by never checking for duplicate `signer` addresses in the submitted signature array. Aptos's native threshold-signature account-control primitives — `MultiKey` (used by `AuthenticationKey::multi_key`) and `MultiEd25519PublicKey` (the `MULTI_ED25519_SCHEME` used by account auth-key rotation and resource accounts) — have the analogous gap: neither constructor rejects duplicate public keys in the key list.

### Finding Description
`MultiKey::new` only validates count and threshold bounds, never checking that `public_keys` are pairwise distinct: [1](#0-0) 

`MultiKeyAuthenticator::new` deduplicates by **bitmap index**, not by underlying key identity — it only guards against reusing the same *slot* twice: [2](#0-1) 

The existing unit test `verify_multi_key_auth` builds a 2-of-3 `MultiKey` where index 1 and index 2 are the *same* public key (`sender1_pub` is duplicated), then satisfies the threshold using two signatures produced from the same private key (`sender1`) placed at indices 1 and 2 (`mk_auth_12`), and `signed_txn.verify_signature()` succeeds: [3](#0-2) [4](#0-3) 

The legacy `MultiEd25519PublicKey::new` has the identical gap — it checks only `threshold`, key count and `MAX_NUM_OF_KEYS`, never key uniqueness: [5](#0-4) 

`MultiEd25519Signature::verify_arbitrary_msg` only checks that `num_ones_in_bitmap >= threshold` (i.e., that enough bitmap *positions* are set), and never checks whether those positions map to distinct underlying keys: [6](#0-5) 

Because these primitives govern account authentication keys — including resource accounts and any account/object owner rotated to a `MultiEd25519`/`MultiKey` scheme — this identity/holder set is the ultimate root of custody control for all assets (APT, fungible-asset stores, object ownership) held by that account. `account::rotate_authentication_key` accepts a `MULTI_ED25519_SCHEME` byte blob and only checks that the *current* key matches, never that the *new* multi-key key set is free of duplicate members: [7](#0-6) 

`resource_account::create_resource_account` and friends rotate a resource account's authentication key to an arbitrary caller-supplied `optional_auth_key`/origin key with no dedup validation either: [8](#0-7) 

### Impact Explanation
A "k-of-n" `MultiEd25519`/`MultiKey` account — the Aptos-native analog of a Solidity multisig/custody policy — is intended to guarantee that k *distinct* parties must cooperate to control the account (and therefore all APT/fungible assets/object ownership rooted at that address, including resource-account and code-object controllers rotated to such a scheme). Because duplicate public keys are never rejected at key-set construction (`MultiKey::new`, `MultiEd25519PublicKey::new`) nor at authentication-key rotation time in the framework (`account::rotate_authentication_key`), a party that controls only one private key that has been listed twice (or more) in the key set can single-handedly produce the k required signatures (one per duplicated slot) and pass verification — silently degrading a "k distinct signers" custody guarantee to "1 signer," while the on-chain, auditable `owners`/key list still visually implies k independent approvers. This mirrors exactly the Sherlock root cause (threshold counted duplicated signers) but manifests in Aptos's core account-authentication layer rather than an app-level `Consensus` contract, i.e. it can silently weaken the actual security of any account, resource account, or object-owning account whose custody model relies on `MultiEd25519`/`MultiKey` k-of-n control.

Note the framework's own `multisig_account.move` module is *not* vulnerable to this class: its `MultisigTransaction.votes` is a `SimpleMap<address, bool>` keyed by owner address, so a duplicate vote from the same owner cannot double-count, and `validate_owners` explicitly rejects duplicate owners: [9](#0-8) 

### Likelihood Explanation
This requires the account/resource-account owner (or whoever controls the transaction that sets up or rotates the authentication key) to construct the duplicated key set — it is not a remote unprivileged attacker directly draining an arbitrary victim's funds without any cooperation from the account-controlling party. This weakens the "custody-grade, unprivileged-root-cause" bar somewhat: exploitation requires either (a) the account owner unknowingly/maliciously including a duplicate key at setup/rotation time (e.g., a rogue custodian on a governance/treasury account slipping in their own key twice to defeat a "3 distinct guardians required" policy), or (b) tooling/UX failing to flag duplicate keys during multisig setup, which is plausible since neither the Rust nor the Move layer validates it and existing test code (`verify_multi_key_auth`) demonstrates it as accepted, non-error behavior.

### Recommendation
- Add a uniqueness check on the public-key list in `MultiKey::new` and `MultiEd25519PublicKey::new` (and their Move-exposed constructors in `aptos-stdlib/sources/cryptography/multi_ed25519.move` and `multi_key.move`), rejecting duplicate keys at construction.
- Enforce the same check in `account::rotate_authentication_key`/`rotate_authentication_key_internal` before accepting a new `MULTI_ED25519_SCHEME`/multi-key authentication key, so accounts (including resource accounts) cannot be rotated into a degraded threshold scheme.
- Consider treating this as a documented invariant check surfaced to wallets/SDKs (e.g., `aptos-cli-common` key-generation helpers) so multisig setup tooling proactively rejects duplicate members.

### Proof of Concept
The existing repository test already demonstrates the bypass (single key, two bitmap slots, threshold satisfied): [3](#0-2) [4](#0-3) 
Steps: (1) Build `MultiKey::new(vec![pkA, pkB, pkB], 2)` — a "2-of-3" account where `pkB` occupies two slots. (2) An attacker/insider holding only `skB` signs the transaction/rotation payload twice, submitting `(1, sig_B)` and `(2, sig_B)` via `MultiKeyAuthenticator::new`. (3) `to_single_key_authenticators`/`verify` succeeds because the bitmap has 2 bits set and the signature count matches — despite only one distinct private key ever being used, defeating the intended "2 distinct approvers" custody guarantee for whatever account/resource-account/object this key controls.
