### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) are not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields consumed by `ShopifyAPI::Webhooks::Registry.process` are parsed straight from unauthenticated HTTP headers. `HmacValidator.validate` verifies only the body bytes against the app's shared `client_secret`, never binding the header-derived shop identity into the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
returning `@raw_body` only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates the request using this signable string, then dispatches the handler using the *unauthenticated* header fields: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(client_secret, to_signable_string)` and compares it to the `hmac` header value: [4](#0-3) 

The invariant that should hold is: `shop authenticated by HMAC == shop delivered to the app's handler`. In this implementation, the HMAC only proves "this body was signed with the app's `client_secret`" — it says nothing about which shop the body belongs to, because `client_secret` is shared across every shop that installed the app. An attacker who legitimately owns any shop with the app installed can capture a real, validly-signed webhook delivered to them (body + valid `hmac-sha256` header, computed with the same app secret used for all merchants), then replay the identical raw body to the app's webhook endpoint while substituting the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header to name a different, victim shop. Since `to_signable_string` never includes `shop`, the HMAC signature computed over the (unchanged) body remains valid, and `Registry.process` will pass HMAC validation and invoke the host app's handler with `WebhookMetadata.new(shop: <victim shop>, ...)` — a cross-tenant identity spoof.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to route/attribute webhook data per tenant. A single unprivileged merchant installing the app can forge webhook deliveries "from" any other merchant's shop (since only the app-wide `client_secret` — not a per-shop secret — signs the payload, and the shop field is outside the signed material). Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., looking up per-shop records, triggering per-shop side effects, updating billing/subscription state, or writing into another tenant's data), this can cause cross-tenant data corruption or unauthorized actions attributed to a shop that never sent the webhook — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is Medium-High for apps with many installs: any merchant that has installed the app can capture one of their own valid webhook deliveries (trivial — they receive it directly) and replay it against the app's public webhook endpoint with a spoofed `shop-domain` header. No access to the `client_secret`, a token, or TLS interception is required — only a normal, unprivileged install of the app, which matches the target threat model.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the bytes that are actually verified, or otherwise cryptographically bind the header-derived shop to the signed payload before trusting it — e.g., recompute/validate using a canonical string that incorporates the shop domain, not solely `@raw_body`, in `ShopifyAPI::Webhooks::Request#to_signable_string`/`HmacValidator`. Shopify's own delivered signature is computed over the body only by design, so at minimum the gem (or documentation) should make explicit that consumers must independently verify `data.shop` against a known/expected set of installed shops before acting on it, since the HMAC check alone does not authenticate the shop field.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing the same `client_secret`.
2. Shopify delivers a real webhook to the attacker's shop with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw_body>`, and some `raw_body`.
3. Attacker resends an HTTP request to the app's webhook endpoint with the identical `raw_body` and identical `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` reads the (unchanged, still-valid) HMAC header; `to_signable_string` returns the unchanged `raw_body`: [5](#0-4) 
5. `HmacValidator.validate` succeeds because the signature was computed over `raw_body` with the shared `client_secret`, unaffected by the header change: [6](#0-5) 
6. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` using the attacker-spoofed `victim-shop.myshopify.com`: [7](#0-6) 
7. The host app's handler processes attacker-controlled data believing it originated from `victim-shop.myshopify.com`.
