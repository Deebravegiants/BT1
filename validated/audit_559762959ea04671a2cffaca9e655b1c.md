### Title
`EmporiumUpgradeable.runAction`'s "Min" path (`erc20TokenAddresses.length == 0`) skips the balance-diff invariant entirely, letting an attacker drain any pre-existing Emporium balance via an unsigned, unauthenticated `EmporiumOperation` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `CircomDataBuilder.formInputForCircom` routes a Hinkal-Emporium call to `formInputEmporiumMin` (triggered simply by submitting `erc20TokenAddresses = []`), every loop in `Hinkal.transact` and `EmporiumUpgradeable.runAction` that is keyed off `circomData.erc20TokenAddresses.length` executes zero times, so `BalanceChangeShouldBePositive()` can never revert and no balance-conservation check ever runs. Combined with the fact that `verifyWallet` performs **no signature check at all** when `stack.signerAddress == address(0)`, and `EmporiumOperation.endpoint`/`callData` are fully attacker-controlled, an unprivileged caller can force Emporium to execute an arbitrary external call (e.g. `ERC20.transfer(attacker, balance)`) that drains any pre-existing balance Emporium is holding, with zero on-chain check that anything was accounted for.

### Finding Description
The claimed equality is: `Δ(Emporium's real token/ETH balance) == Σ(deltaAmountChanges) + Σ(UTXOs paid out)`. On the Min path both sides are forced to zero-length/empty, so the equality is checked over an empty set and can never fail regardless of what actually happened to Emporium's balance.

Trace:
- `Hinkal.transact` loops `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` to enforce `balanceDif == amountChanges[i] + utxoAmount` [1](#0-0) . With `erc20TokenAddresses = []` this loop body never runs, so this top-level invariant is entirely skipped.
- `Hinkal._externalTransact` builds `deltaAmountChanges` with the same zero length and forwards it to `IExternalActionV2.runAction` [2](#0-1) .
- Inside `EmporiumUpgradeable.runAction`, the post-op balance-diff loop containing `BalanceChangeShouldBePositive()` also iterates `circomData.erc20TokenAddresses.length` times, i.e. zero times on the Min path [3](#0-2) . The code comment itself acknowledges Emporium can hold pre-existing funds before a call ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call", line 141), confirming standing balances are an expected state this check exists to protect — yet it is bypassed here.
- Routing to this path is entirely attacker-controlled: `formInputForCircom` selects `formInputEmporiumMin` purely based on `circomData.erc20TokenAddresses.length == 0` [4](#0-3) , and the resulting Min public-input vector only contains `emporiumMessage`, `timeStamp`, `calldataHash` [5](#0-4)  — no root hash, no nullifiers, no amount changes are bound into the proof, so the attacker needs no shielded funds or ownership proof, just a self-generated, self-consistent proof for their own submitted calldata.
- Separately, and critically, `verifyWallet` performs the EIP-712 signature check **only if** `stack.signerAddress != address(0)`; if it's zero, it just marks the message used and returns [6](#0-5) . When `signerAddress == 0`, the op-execution branch condition `op.invokeWallet && stack.signerAddress != address(0)` is always false, so every operation goes through CASE 2 (`op.endpoint.call{value: op.value}(op.callData)`), executed directly by Emporium with `msg.sender == Emporium`, with `endpoint`/`callData` fully chosen by the attacker (only `callHinkalWallet`/`doSendToRelay` selectors are blocked) [7](#0-6) .
- `EmporiumUpgradeable.runAction` is gated by `onlyAllowedRecipient`, restricting direct callers to addresses on Emporium's allow-list (i.e. the Hinkal contract itself) [8](#0-7) ; this does not block the attack because the entry point is `Hinkal.transact`, callable by any EOA.

Exploit flow: attacker calls `Hinkal.transact` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `inputNullifiers = []`, `onChainCreation = []`, and `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: <token Emporium holds>, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, emporiumBalance))}]}`. They generate their own valid Min-circuit proof (no ownership of shielded funds required) and any historically-valid `rootHashHinkal` (existence-only check, not tied to the Min public signals). `runAction` executes the transfer, calling `handleOut`/the post-loop nowhere, since the loop bound is zero — no revert, no accounting, `utxoSet` returned empty.

### Impact Explanation
Any ERC20/ETH balance sitting in the Emporium contract (whether leftover dust from partial "Normal" ops, in-flight funds for a multi-step campaign, or accumulated relay-fee tokens) can be fully drained by an unprivileged attacker to their own address, with no signature, no owner check, and no balance invariant enforced. This is theft of protocol/user funds held in escrow by Emporium — Critical, since these balances are conceptually still backing users' shielded/in-flight positions (per the code's own comment). It is repeatable every time Emporium holds a nonzero balance of any token, at zero cost to the attacker beyond gas and proof generation.

### Likelihood Explanation
Preconditions: Emporium must hold a nonzero balance of some token/ETH (explicitly anticipated by the contract's own comment at line 141). No privileged role, victim cooperation, or valid UTXO ownership is required — only the ability to call `Hinkal.transact` (open to any EOA) and to generate a proof for the Min circuit for one's own chosen `emporiumMessage`/`timeStamp`/`calldataHash`, which the Min circuit's public-input scheme does not tie to fund ownership. This makes the attack highly feasible whenever Emporium is nonzero-balance, and trivially repeatable.

### Recommendation
Do not let `erc20TokenAddresses.length == 0` bypass balance accounting for arbitrary external calls. Either (a) forbid `invokeWallet == false && stack.signerAddress == address(0)` stateless ops from targeting endpoints other than a fixed allow-list, (b) always run a balance-diff/invariant check over the full set of tokens actually touched/held by Emporium (not restricted to the caller-chosen `erc20TokenAddresses` array), or (c) require `verifyWallet` to authenticate ops (e.g., via `msg.sender`-bound authorization) even when `signerAddress == address(0)`, so unsigned stateless calls cannot move Emporium's standing balance without being reconciled by the post-call balance check.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as external action, Hinkal added as allowed recipient), a mock ERC20.
2. Fund Emporium directly with e.g. 1000 mock tokens (simulating leftover/escrowed balance) and confirm `balanceOf(emporium) == 1000`.
3. As an unprivileged attacker EOA, construct `CircomData` with `erc20TokenAddresses = []`, `inputNullifiers = []`, `onChainCreation = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` encoding `EmporiumStack{signerAddress: address(0), ops:[{endpoint: address(token), invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker,1000))}]}`, and a `rootHashHinkal` equal to any existing root.
4. Generate a valid Min-circuit proof locally for the resulting public signals (`emporiumMessage`, `timeStamp`, `calldataHash`).
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
6. Assert: call succeeds (no revert), `token.balanceOf(attacker) == 1000`, `token.balanceOf(emporium) == 0`, and the returned/emitted UTXO set is empty — demonstrating value left Emporium with no `deltaAmountChanges`/UTXO accounting for it and no `BalanceChangeShouldBePositive()` revert.
