### Title
Webhook `shop`/`topic`/`webhook_id` identity headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the handler actually acts on are read from HTTP headers that are excluded from the HMAC computation entirely, so any request whose body happens to match a previously-observed (validly signed) body can be replayed with arbitrary attacker-chosen identity headers, including a victim shop domain.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies the signature purely against `to_signable_string`, i.e. the body bytes, using the app's secret: [4](#0-3) 

`Registry.process` trusts the header-derived `shop`/`topic` fields directly once the (body-only) HMAC passes, and hands them to the app's webhook handler as authenticated data: [5](#0-4) 

The documented contract for `Registry.process` explicitly claims this "will verify the request did indeed come from Shopify," and instructs handlers to trust `data.shop` as "The shop domain of the webhook": [6](#0-5) [7](#0-6) 

**Broken binding:** `HMAC-verified(raw_body)` ≠ `identity used by handler (shop, topic, webhook_id)`. The signature authenticates the body bytes only; it says nothing about which shop or topic those bytes belong to. Any attacker capable of obtaining one legitimately-signed webhook for their own installation (e.g. by installing the app on a free/dev store — no victim credentials needed) can capture a `(raw_body, hmac)` pair for a topic with a fixed/predictable body (many topics, e.g. `app/uninstalled`, ship with body `{}`), then replay that exact byte-identical body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`) headers with a victim shop and any topic. Because the HMAC only signs the body, it still validates, and the handler is invoked believing it received an authentic webhook for the victim shop/topic.

### Impact Explanation
This crosses a tenant boundary purely via HTTP requests to the app's own public endpoint, with no access token, API secret, or victim credentials required — matching the Critical "cross-tenant access" bucket. Depending on which topic is forged, impact ranges from corrupting/injecting data attributed to a victim shop, to firing sensitive lifecycle topics (`app/uninstalled`, `shop/redact`, `customers/redact`, billing/subscription topics) against a victim tenant, causing the host app (following this gem's documented API exactly) to take shop-scoped action (e.g. purging the victim's stored access token/session, deleting victim data) on the attacker's behalf.

### Likelihood Explanation
Likelihood is High: any actor can install the target app on a shop they control (or observe another installer's fixed-body webhook, such as `app/uninstalled`'s `{}` body) to obtain a valid `(body, hmac)` pair, then freely re-issue the HTTP POST to the app's public webhook route with forged `shop`/`topic` headers. No secret material or elevated privilege is needed beyond the ability to send HTTP requests.

### Recommendation
Bind the identity headers into the signed material, or independently verify them:
- Compute/verify the HMAC over a canonical string that includes `shop`, `topic`, and other headers relied upon by handlers, not just the raw body, OR
- Cross-check `request.shop` against the set of shops that currently have this exact webhook/topic registered (and that installed the app) before dispatching to the handler, rejecting shop/topic combinations that were not registered for that installation.
- Update `docs/usage/webhooks.md` to stop asserting that `process` fully authenticates the shop/topic identity if this is not fixed, so host apps do not blindly trust `data.shop`/`data.topic`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store (`attacker-shop.myshopify.com`) and subscribe to a topic whose body is fixed/empty, e.g. `app/uninstalled` (body `{}`).
2. Capture the resulting webhook POST sent by Shopify to the app's registered webhook endpoint, noting the raw body (`{}`) and the `x-shopify-hmac-sha256` value — this HMAC is valid for body `{}` under the app's `api_secret_key`, and is reusable for any request whose body is `{}`.
3. Replay a POST to the app's public webhook endpoint with:
   - Body: `{}` (unchanged)
   - Header `x-shopify-hmac-sha256`: unchanged (still valid, since only the body is signed — see `lib/shopify_api/webhooks/request.rb#L35-38` and `lib/shopify_api/utils/hmac_validator.rb#L26-31`)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - Header `x-shopify-topic`: `app/uninstalled` (or any topic registered by the app)
4. `ShopifyAPI::Webhooks::Registry.process` at `lib/shopify_api/webhooks/registry.rb#L188-199` validates the HMAC (passes, since body is unchanged) and invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the app to act on the victim shop's tenant data/session as though Shopify itself sent this event for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
