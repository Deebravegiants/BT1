### Title
Octal QR extension parameter can trigger unrecoverable `assert_eq!` panic in `SweepConfiguration::parse_configuration_value` - (File: `src/plans/biometric_capture/focus_sweep.rs`)

### Summary
The `From<biometric_capture::Plan> for Plan` impl parses the QR's `signup_extension_config.parameters` string with `u8::from_str_radix(parameter, 8)`, which happily accepts any octal digit string producing values from `0` to `255` (e.g. `"10"` → 8, `"377"` → 255). `parse_configuration_value` then formats the value as a zero-padded 3-bit binary string and asserts its length is exactly 3, which is false for any `configuration_value > 7`, causing an unconditional panic that is fully attacker-reachable from an unprivileged, crafted QR code.

### Finding Description
`Plan::from` at `src/plans/biometric_capture/focus_sweep.rs:160-167` builds a `SweepConfiguration` directly from octal parsing of an attacker-supplied QR `parameters` string: [1](#0-0) 

`SweepConfiguration::new` calls `parse_configuration_value`, which formats `configuration_value` as `{:0>3b}` and asserts the resulting string is exactly 3 characters: [2](#0-1) 

`u8::from_str_radix(parameter, 8)` only rejects strings with non-octal digits or overflow past `u8::MAX`; it does not restrict the *value* to the 0–7 range the code comment assumes ("octal value whose binary representation symbolizes the three different wavelengths", `focus_sweep.rs:91-94`). Any octal string decoding to 8–255 (e.g. `"10"`, `"77"`, `"377"`) passes the `.ok()` parse and is passed into `SweepConfiguration::new`, producing a binary representation longer than 3 characters and triggering the `assert_eq!` panic at construction time, i.e. inside `Plan::from`, before `Plan::run` or any MCU/camera commands are issued.

Because there is no `catch_unwind` anywhere in the plan/broker code (the only occurrences in the repo are in `agentwire/src/testing_rt.rs`, a test harness), this panic is not caught and will unwind through whatever task drives the signup plan.

### Impact Explanation
This is a reachable, unprivileged panic that aborts a signup mid-flow, purely from a value embedded in the presented QR code's extension parameters — a legitimate availability/DoS impact against the signup pipeline. However, I could not confirm the specific "cross-signup state bleed" claim in the question: the panic occurs inside `Plan::from`, before `biometric_capture.run_pre`/`reset_extension`/any MCU command is sent (`focus_sweep.rs:188-203`), so no focus-sweep-specific extension state has been mutated yet when the panic fires. Whether the outer signup supervisor recovers per-signup (leaving stale global/fraud/QR state) or the whole orb process crashes and is restarted by its supervisor (which would fully reset state) could not be determined from the files inspected; no code path resetting fraud/QR state after a panic (nor evidence of its absence) was found.

### Likelihood Explanation
High feasibility and full attacker control: any unprivileged user can encode a QR with an extension `parameters` string like `"10"`, `"77"`, or any octal string decoding above 7, requiring no operator access, keys, or hardware tampering.

### Recommendation
Validate `configuration_value` is within `0..=7` before constructing `SweepConfiguration` (e.g., return a `Result`/fallback to default instead of panicking), and replace the `assert_eq!` in `parse_configuration_value` with a graceful bounds check/clamp so malformed QR extension parameters cannot crash the signup task.

### Proof of Concept
Unit test in `focus_sweep.rs`:
```rust
#[test]
fn octal_parameter_above_seven_panics() {
    // "10" in octal = 8 decimal -> binary "1000" (4 chars) fails the 3-char assert
    let value = u8::from_str_radix("10", 8).unwrap();
    let _ = SweepConfiguration::new(value); // panics
}
```
Fuzz target: feed arbitrary strings through `u8::from_str_radix(s, 8).ok()` into `SweepConfiguration::new`/`parse_configuration_value` and assert no panic occurs for any successfully-parsed `u8`; currently any value `8..=255` panics. A follow-up integration test would need to drive an actual signup task through `Plan::from` with such a QR parameter and observe whether the process/task recovers and whether fraud/QR state is reset before the next signup — this part requires runtime verification I could not complete from static inspection alone.
