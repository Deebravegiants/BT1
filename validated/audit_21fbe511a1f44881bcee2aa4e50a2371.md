Found the analog. The Tron variant of `IntentGatewayV2.sol` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reproduces exactly the "re-parameterization without sanity checks" bug class from the report — its `onAccept` handler for `RequestKind.UpdateParams` applies attacker/governance-controlled `feeBps`, `Params`, and destination-fee values to storage with **no bounds validation**, unlike the mainline EVM `IntentGatewayV2.sol`, which validates the same fields via `IntentsBase._validateParams`/`_updateParams`.

### Title
Missing bounds validation on `UpdateParams`/destination fee bps in Tron `IntentGatewayV2.onAccept` allows invalid re-parameterization of protocol economics - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2` validates every field of an incoming `UpdateParams` governance message before applying it, via `IntentsBase._validateParams` (bounding `surplusShareBps <= 10_000`, `protocolFeeBps < 10_000`, and per-destination `feeBps < 10_000`) [1](#0-0) . The Tron port of the same contract implements the identical `RequestKind.UpdateParams` branch but skips this validation entirely, directly overwriting `_params` and `_destinationProtocolFees[stateMachineId]` with attacker/relayer-controlled values [2](#0-1) .

### Finding Description
`onAccept` dispatches on the first byte of the incoming `PostRequest` body. For `RequestKind.UpdateParams`, it ABI-decodes a `ParamsUpdate` struct and unconditionally assigns it:
```solidity
} else if (kind == RequestKind.UpdateParams) {
    ParamsUpdate memory update = abi.decode(incoming.request.body[1:], (ParamsUpdate));
    emit ParamsUpdated({previous: _params, current: update.params});
    _params = update.params;
    for (uint256 i; i < update.destinationFees.length;) {
        ...
        _destinationProtocolFees[stateMachineId] = feeBps;
        ...
    }
``` [3](#0-2) 

There is no analog of `_validateParams`/the `feeBps >= 10_000` check that the mainline contract enforces in `_updateParams` [4](#0-3) , and the mainline test suite confirms this invariant is treated as security-critical, explicitly testing that `protocolFeeBps >= 10000` and `destinationFeeBps >= 10000` must revert [5](#0-4) . The Tron variant has no such guard, so `protocolFeeBps`/`surplusShareBps`/`destinationFeeBps` can be set to values ≥ 10,000 (≥100%), or `host`/`dispatcher` set to zero/EOA addresses, none of which the Tron contract checks before or after the write.

`placeOrder` in the same Tron contract computes escrow amounts directly from these unbounded values:
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
``` [6](#0-5) 
If `protocolFeeBps` (or the per-destination override) is set ≥ 10,000, `reducedAmount` underflows/reverts or (for values in [10000, 2^256) depending on arithmetic path) can make every subsequent order for that destination revert or have escrow computed incorrectly, mirroring "Scenario 1" in the report (invalid parameter breaks all downstream interactions). This is the direct root-cause analog of the report's `resolveReparam`: a governance/relayer-delivered message updates critical economic parameters with zero sanity checks, and downstream contract logic (fee math, escrow accounting) assumes the invariant holds.

### Impact Explanation
Because `onAccept` is only reachable from messages whose `source` equals Hyperbridge (`keccak256(incoming.request.source) != keccak256(hyperbridge())` reverts otherwise) [7](#0-6) , exploitation requires a message genuinely originating from Hyperbridge governance/coprocessor — but that message itself carries no on-chain bounds check at the destination. A single malformed or maliciously-crafted governance payload (e.g. produced by a buggy or compromised upstream `pallet-intents-coprocessor`/relayer path, which itself uses unchecked `U256` fee fields [8](#0-7) ) permanently corrupts destination-chain economics: `placeOrder` can be made to always revert (denial of service / permanent freeze of new orders to that destination) or fee math can silently misprice every order, causing funds mispricing/loss for users placing orders against that destination. This matches "concrete... permanent freezing of funds" / "unsound state" impact bar, since the Tron gateway has no independent defense-in-depth check that the mainline contract explicitly added as a security fix.

### Likelihood Explanation
Medium: this requires a single incoming governance-tagged `PostRequest` reaching `onAccept` with an out-of-range `ParamsUpdate`/`DestinationFee`. Because the mainline `IntentGatewayV2.sol` was hardened with exactly this check (and dedicated regression tests), it demonstrates the project itself recognizes an unbounded value here as reachable and dangerous; the Tron port simply never received the same fix, making it a straightforward regression/inconsistency rather than a theoretical concern.

### Recommendation
Port `IntentsBase._validateParams` (or an equivalent check) into the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch: reject `update.params.surplusShareBps > 10_000`, `update.params.protocolFeeBps >= 10_000`, zero/non-contract `host`/`dispatcher`, and any `destinationFeeBps >= 10_000` before writing to storage, exactly mirroring the mainline EVM contract's enforced invariants and regression tests.

### Proof of Concept
1. Hyperbridge (or a message crafted to appear to originate from it, per the `source` check) delivers a `PostRequest` to the Tron `IntentGatewayV2` with body `[RequestKind.UpdateParams] || abi.encode(ParamsUpdate)` where `update.params.protocolFeeBps = 10_000` (100%) or `update.destinationFees[i].destinationFeeBps = 10_000`.
2. `onAccept` decodes and directly writes `_params = update.params;` and `_destinationProtocolFees[stateMachineId] = feeBps;` with no validation [3](#0-2) .
3. Any subsequent `placeOrder` call computes `protocolFee = (originalAmount * protocolFeeBps) / 10_000` and `reducedAmount = originalAmount - protocolFee` [6](#0-5) ; at 100% fee, `reducedAmount == 0`, and escrow/commitment accounting for every future order on that destination is corrupted or the flow reverts entirely, freezing intent placement for that route — reproducing the report's "any contract that requires the [parameter] will always fail" scenario, but for the Tron deployment specifically since the mainline contract's `_validateParams` prevents it there.

    /**
     * @dev Validates gateway configuration parameters. Reverts with InvalidInput if any
     * value would brick the gateway or cause arithmetic errors in fee calculations.
     *
     * @param p The parameters to validate.
     */
    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
