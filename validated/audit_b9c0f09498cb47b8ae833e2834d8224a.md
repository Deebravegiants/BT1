Confirmed: `WebhookMetadata.shop` is the tenant identity field passed directly to the app's `handle` method, and it's sourced solely from the unauthenticated `shop-domain` header, never included in the HMAC-signed bytes.

### Title
Webhook `shop-domain` identity field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value taken from an HTTP header that is never part of the signed bytes. This breaks the identity binding `shop_verified == shop_acted_on`: the gem verifies the body's authenticity but attributes it to whatever `shop-domain` (or `x-shopify-shop-domain`) header value the caller supplies.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` only: [2](#0-1) 

For webhook `Request`, `to_signable_string` returns only `@raw_body`; `shop`, `topic`, `api_version` and `webhook_id` are all pulled from headers, entirely outside the signed material: [3](#0-2) 

The `shop` value produced here is passed verbatim as the tenant identifier into `WebhookMetadata`, which is the struct the host application's `WebhookHandler#handle` implementation is expected to trust for per-shop attribution (e.g. looking up a session/store record, writing shop-scoped data): [4](#0-3) 

Because the HMAC only proves "this body was signed with the app's secret at some point for some shop," and not "this body belongs to this specific shop," an attacker who owns a legitimate installed instance of the app on their own store can capture one genuine `(raw_body, hmac)` pair from their own webhook deliveries and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header pointing at a victim shop. `Utils::HmacValidator.validate` still passes because the body bytes are unchanged, and the handler receives `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break: the field the application logic acts on (`shop`) is not the field the cryptographic check actually authenticates (`raw_body`). Any host application that uses `WebhookMetadata#shop` to key writes, cache invalidation, order/customer processing, or session lookups can be made to apply an attacker-controlled payload under a victim shop's identity, without needing the app's `client_secret`. This matches the Critical "cross-tenant access" impact category, since the attacker only needs their own legitimate app installation to harvest a signed body and can redirect its effect to any other shop.

### Likelihood Explanation
Likelihood is high for any app that relies on `Registry`/`Request`/`WebhookMetadata` as documented, since no additional binding of `shop` to the signed bytes is performed anywhere in the gem, and obtaining one valid `(body, hmac)` pair only requires installing/using the app on an attacker-owned store, which is normal, unprivileged access.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value as part of the string that is HMAC-verified, or otherwise cryptographically bind the `shop` claim to the signed payload before constructing `WebhookMetadata`, so that a captured `(body, hmac)` pair cannot be replayed under a different shop domain.

### Proof of Concept
1. Attacker installs the target app on their own controlled shop `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because Shopify signed `B` with the app's real secret).
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com` and any topic already registered by the app.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not correlation, is checked) at [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `@raw_body`, matching `H` [6](#0-5) .
5. The handler is invoked with `WebhookMetadata#shop == "victim.myshopify.com"`, so the host app processes attacker-supplied body `B` as if it originated from the victim's store.
