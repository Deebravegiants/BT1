### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed by `Utils::HmacValidator.validate` proves nothing about the `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. The `shop` accessor used to attribute the webhook to a tenant is read straight from that unauthenticated header. [1](#0-0) 

### Finding Description
`Registry.process` validates the incoming webhook by calling `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` and compares it against `request.hmac`. [2](#0-1)  `to_signable_string` is hard-coded to the raw body only, never the headers. [3](#0-2)  Yet immediately after the HMAC check passes, `Registry.process` builds the `WebhookMetadata` handed to the app's handler using `request.shop`, which is parsed verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header. [4](#0-3) [5](#0-4) 

This is the exact binding break the report describes: a field ("shop") that is acted upon (used as the tenant key by every downstream handler) is not covered by the cryptographic authenticity check (HMAC over body bytes only). The equality that should hold but doesn't is:
`shop_bound_by_hmac == shop_used_for_tenant_routing`
Before the attacker's action: for a genuine Shopify delivery, both sides are the true originating shop. After an attacker intercepts/replays a valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on a shop the attacker controls and capturing its own legitimate webhook — and resends it to the same shared webhook endpoint with a different `shopify-shop-domain` header, `HmacValidator.validate` still returns `true` (body+hmac unchanged) while `request.shop` now names an arbitrary victim shop.

### Impact Explanation
Since `Registry.process` passes `request.shop` unauthenticated into `WebhookMetadata`, any app relying on this gem to route/process webhooks per-tenant will process the attacker-supplied body under the identity of a shop it never came from. This is a cross-tenant confusion: the webhook handler will act as if the (attacker-controlled) payload belongs to a victim's store, e.g. writing data, revoking access, or triggering compliance actions (`shop/redact`, `customers/redact`, `customers/data_request` topics are explicitly mandatory and processed the same way). This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite — obtaining one valid `(raw_body, hmac)` pair — is trivial for any attacker: they only need to install the target app on a shop they control (or capture any webhook delivered to it) to get a signature that remains valid for that same body forever, since the signature never binds the shop. They then only need to alter the `shop-domain` header on replay, which requires no secret knowledge. The main constraint is that the app must expose a single shared webhook endpoint distinguishing tenants purely via this header (a common SaaS pattern), and the attacker needs network path to POST to that endpoint, which is normal internet-reachable behavior, not a privileged capability.

### Recommendation
Bind the shop identity into the value verified by the HMAC check rather than trusting an unauthenticated header for tenant attribution. Practically:
- Do not rely on `shopify-shop-domain` alone as the tenant key for webhook processing; require the app to independently confirm the shop has an active session/install record before trusting webhook content for that shop, or
- If the API supports it, incorporate header values that need to be trusted (`shop-domain`, `webhook-id`, `topic`) into `to_signable_string`, or otherwise cryptographically bind them, so tampering an authenticated field invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook: headers include `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `raw_body`.
2. Attacker captures `raw_body` and `valid_hmac` (both are visible to them since it's their own store's webhook).
3. Attacker sends a new HTTP POST to the app's shared webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256: <valid_hmac>`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` → `true`, since verification only checks `raw_body` against `valid_hmac`. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload originated from the attacker's own shop. [4](#0-3)
