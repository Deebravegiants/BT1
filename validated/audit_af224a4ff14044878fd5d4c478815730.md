### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all of which are read from HTTP headers and passed on to the handler as trusted `WebhookMetadata` — are excluded from the signed data. `ShopifyAPI::Utils::HmacValidator` verifies only that the signature matches the raw body; it has no way to bind the header-derived identity fields to that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But the same object exposes `shop`, `topic`, `webhook_id`, and `api_version`, all parsed straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (i.e., the raw body) against the `hmac` header: [3](#0-2) 

`Registry.process` uses this validation result as the sole authenticity gate, then dispatches the handler using the unverified `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The binding that should hold is:
`HMAC(client_secret, signed_bytes) == received_hmac` where `signed_bytes` must include everything the app trusts and acts on (`shop`, `topic`, body). Instead the gem only enforces `HMAC(client_secret, raw_body) == received_hmac`, while `shop`/`topic`/`webhook_id`/`api_version` are accepted from unauthenticated headers and forwarded to the handler as if they were verified.

Since `Context.api_secret_key` is a single per-app secret shared across every merchant that installs the app (not a per-shop secret), any user who installs the app on their own store can trigger a genuine webhook delivery and capture a valid `(raw_body, hmac)` pair signed with the app's own secret. That attacker-obtained, validly-signed pair can then be replayed directly against the app's public webhook endpoint with the `shop-domain` (and/or `topic`/`webhook_id`) header swapped to any other merchant's shop domain. `Utils::HmacValidator.validate` will still return `true` because it only checks the untouched raw body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged `shop`/`topic`, which downstream app logic uses to select the merchant/tenant record to act on.

### Impact Explanation
This breaks the identity binding between "bytes verified by HMAC" and "bytes the host application trusts as message metadata," specifically the shop identity. A host application built on this gem's documented `Registry.process` API has no way to know that `data.shop` was not authenticated by the signature, so it will process webhook payloads attributed to the wrong tenant. This is a cross-tenant data-injection primitive: an attacker-controlled (but validly-HMAC'd) payload can be attributed to an arbitrary victim shop, satisfying the High/Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any user who can install the target app on their own store (an unprivileged, ordinary Shopify merchant/internet user relative to the app) can obtain a validly-signed `(body, hmac)` pair for free, since the HMAC secret is shared across all installs rather than per-tenant. Replaying that pair to the app's webhook endpoint with a different `shop-domain`/`topic` header requires only a normal HTTP client — no leaked secrets, no privileged access, and no interception of Shopify's traffic is needed.

### Recommendation
Include the identity-critical header fields (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signable string in `Request#to_signable_string`, or otherwise cryptographically bind them before `Registry.process` trusts them, so that `HmacValidator.validate` fails if any of these fields are altered independently of the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`; the app's single shared `api_secret_key` is used for HMAC signing on every install.
2. Attacker triggers a real webhook (e.g. `orders/create`) on their own store, capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify computed with the app's secret.
3. Attacker sends a new POST directly to the app's public webhook endpoint, reusing the same `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged; `Utils::HmacValidator.validate(request)` returns `true` because it only checks the (unmodified) raw body against the hmac.
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, i.e. `shop: "victim.myshopify.com"`, even though the payload actually originated from the attacker's own store — a cross-tenant identity binding failure the app has no way to detect using this library's API.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
