### Title
IntentGatewayV2 (Tron) Authenticates Cross-Chain Messages Using an Unsafe Zero-Default `instance()` Fallback - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` authenticates incoming ISMP `PostRequest`s by comparing the sender address (`request.from`) against `instance(request.source)`. When a source chain is *not* registered in `_instances`, `instance()` silently falls back to `address(this)` instead of reverting. This mirrors the InfinityPool bug class exactly: an unset/default identifier (an unregistered `_instances[hash] == address(0)`) is coerced into a *valid, matchable* identity (`address(this)`) rather than a sentinel nobody can forge, letting an attacker who can source a message from *any* chain Hyperbridge can verify consensus for (but that is not on the gateway's registered-peer allowlist) satisfy the authorization check.

### Finding Description
`instance()` and `authenticate()` in the Tron `IntentGatewayV2`: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

For any `request.source` that has never been registered via `NewDeployment` (i.e., `_instances[keccak256(source)] == address(0)`), `instance()` returns `address(this)` rather than reverting. `authenticate()` then only requires that the message's `from` field equal `address(this)`. Since `IntentGatewayV2` is deployed deterministically via CREATE2 with fixed bytecode/salt so the same address exists on every EVM-compatible chain (a design goal documented elsewhere in this codebase, e.g. `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`/`BridgeToken.sol` comments on CREATE2 determinism), an attacker who can get *any* address matching `address(this)` on a chain that is not registered as a peer (but whose consensus/state Hyperbridge otherwise supports verifying, or whose ISMP dispatch/`from` field the attacker otherwise controls) can produce a `PostRequest` that passes `authenticate()` while `request.source` is a chain the gateway operator never trusted.

This is structurally identical to the reported InfinityPool flaw: `GetRoute.agentFactory(router).agents(msg.sender)` defaults to `0` for any non-agent caller, and the fix was to disallow `vc.subject == 0` from matching. Here, `_instances[...]` defaults to `address(0)` for any unregistered chain, and instead of rejecting that default (as the newer, already-hardened `IntentsBase._instance()` does — see below), the Tron contract maps the default into a value (`address(this)`) that an attacker can realistically match, reopening the exact class of bug the InfinityPool fix closed.

Contrast with the corrected pattern already adopted elsewhere in this same codebase for the same purpose: [2](#0-1) 

```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```

The current (non-Tron) `IntentGatewayV2`/`ExtrinsicIntents` implementation reverts on an unregistered chain, closing the bypass. The Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` still contains the vulnerable fallback-to-`address(this)` pattern.

### Impact Explanation
`authenticate()` gates the `onAccept` dispatch for privileged `RequestKind`s including `RedeemEscrow` (releases escrowed solver funds), `NewDeployment` (registers a peer gateway address — which could then be used to forge further "trusted" instances), `RefundEscrow`, `SweepDust`, and `UpdateParams`. Passing this check with a forged/unregistered source lets an attacker drive these governance/settlement actions on the gateway's own escrow, up to draining escrowed order funds (`RedeemEscrow`) or rewriting the trusted peer table (`NewDeployment`), which are the "concrete theft" and "unauthorized app action" outcomes required by the validation rubric.

### Likelihood Explanation
Exploitability depends on the attacker's ability to produce a `PostRequest` whose `source` is an unregistered/unrecognized chain and whose `from` bytes equal `address(this)` (or otherwise pass HandlerV2/EvmHost's proof verification for that state machine). Because `IntentGatewayV2` is deployed via deterministic CREATE2 across EVM chains specifically so `address(this)` is identical everywhere, an attacker deploying to the same address on any chain Hyperbridge is configured to accept consensus proofs from — but which the gateway operator has not yet added to `_instances` — meets both conditions without needing any privileged key. This is a realistic, single-message attack path (one relayed proof) rather than a theoretical one, matching the "reachable from a single relayed proof" bar in the validation rubric. Likelihood is Medium-to-High depending on how many unregistered-but-consensus-supported chains exist for a given gateway deployment; it requires deliberate misconfiguration state (chain not yet added to `_instances`) that is common during rollout/expansion to new chains.

### Recommendation
Change `instance()` (and `authenticate()`'s reliance on it) in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert on an unregistered chain instead of returning `address(this)`, matching the fixed pattern already used in `IntentsBase._instance()` (`evm/src/apps/intentsv2/IntentsBase.sol`). Concretely:

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```

Audit all other call sites of `instance()` in the Tron contract that may currently rely on the `address(this)` self-fallback behavior (e.g., dispatch-side logic that intentionally treats "no known deployment" as "same-chain / self"), and separate that same-chain convenience logic from the security-critical `authenticate()` path so authentication never silently trusts an unregistered chain.

### Proof of Concept
1. Identify a state machine ID `S` for which the Tron `IntentGatewayV2._instances[keccak256(S)]` is still `address(0)` (never registered via a `NewDeployment` request) but for which Hyperbridge's consensus module can still verify state/proofs (e.g., a newly supported EVM chain awaiting peer registration).
2. On chain `S`, obtain code at the same address as the Tron `IntentGatewayV2` deployment (deterministic CREATE2 address, same across EVM chains), or otherwise arrange for the dispatch to record `request.from = abi.encodePacked(address(intentGatewayTron))`.
3. Dispatch (or have a relayer submit) a `PostRequest` with `source = S`, `from = address(intentGatewayTron)` (20 bytes), and `body` starting with `RequestKind.RedeemEscrow` (or `NewDeployment`) followed by an attacker-chosen `WithdrawalRequest`/`Deployment` payload.
4. `HandlerV2`/`EvmHost` verifies the (legitimately-issued) consensus/state proof for chain `S` and calls `IntentGatewayV2.onAccept`.
5. `authenticate(request)` computes `module = address(intentGatewayTron)` and `instance(S) == address(this) == address(intentGatewayTron)` (since `S` is unregistered), so the check passes even though `S` was never an approved peer.
6. The attacker's `RedeemEscrow`/`NewDeployment` payload executes, releasing escrowed tokens to an attacker-controlled beneficiary or installing an attacker-controlled peer gateway for further abuse.
