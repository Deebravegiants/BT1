### Title
Emporium `runAction` CASE 2 lets any unprivileged caller drive Emporium-owned assets, so anything Emporium ends up owning (e.g. an ERC721 minted with recipient=Emporium) can be stolen by a later unrelated `transact()` call - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose public-input vector contains only `emporiumMessage`, `timeStamp`, `calldataHash` [1](#0-0) . Because `erc20TokenAddresses` is empty, `EmporiumUpgradeable.runAction`'s per-token balance/UTXO accounting loop is a no-op [2](#0-1) , and if `stack.signerAddress == address(0)` the EIP-712 authorization check is completely skipped [3](#0-2) , so CASE 2 (`op.invokeWallet == false`) executes an arbitrary `op.endpoint.call(op.callData)` directly from `Emporium` with no binding to any specific depositor or asset.

### Finding Description
Broken equality: `owner_of_asset_created_by_op(after full flow) == depositing_user's_wallet/stealth_address`. Actual: `owner_of_asset_created_by_op == address(Emporium)`, and control over any asset Emporium happens to hold is not restricted to the depositor at all.

Path:
1. `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [4](#0-3) . `dimensionsCheck` permits `tokenNumber == 0`, `nullifierAmount == 0`, `outputAmount == 0` [5](#0-4) , so no UTXO ownership/spend is required to build a valid witness for this circuit — the attacker fully controls `emporiumMessage`, `timeStamp`, and the `externalActionMetadata` (the `EmporiumStack`), and only needs `getHashedCalldata(circomData) == circomData.calldataHash` [6](#0-5) , which they can freely satisfy since they choose every field.
2. `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction`, gated only by `onlyAllowedRecipient`, which checks `msg.sender == Hinkal` (the caller contract), not the original EOA [7](#0-6) .
3. Inside `runAction`, `verifyWallet` marks `emporiumMessage` used and, since `stack.signerAddress == address(0)`, returns immediately without checking any signature [3](#0-2) .
4. CASE 2 then executes `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == address(Emporium)` [8](#0-7) . Any position/asset previously created with `recipient/owner = address(Emporium)` (e.g., an NFT minted via a prior CASE 2 call) is therefore owned by the shared `Emporium` contract, not by any specific user's stealth address, and nothing in `runAction` ties that asset back to the original depositor.
5. Because `erc20TokenAddresses.length == 0` for this Min path, the balance-diff/`handleOut` accounting that normally forwards received tokens to `msg.sender` (line 172-176) never runs for whatever the op touches, so the asset is simply left sitting under Emporium's control with zero on-chain bookkeeping tying it to anyone.
6. A second, completely unrelated caller can then submit their own `Hinkal.transact` with a fresh Min-circuit proof, a fresh `emporiumMessage`, `signerAddress = address(0)`, and CASE 2 `op.callData = safeTransferFrom(emporium, attacker, tokenId)`. Since `Emporium` is the actual on-chain owner of `tokenId`, this call succeeds trivially (`msg.sender == owner`), and none of `verifyProof`, `verifyWallet`, or `onlyAllowedRecipient` distinguish this attacker from the legitimate depositor.

Existing guards do not prevent this: `verifyProof`/`rootHashExists` only check a trivial statement with no fund-ownership binding for the Min path; `onlyAllowedRecipient` authorizes the Hinkal contract, not the calling EOA; `verifyWallet` is fully bypassed when `signerAddress == address(0)`; and the balance-diff loop that would otherwise return assets to `msg.sender` is empty because `erc20TokenAddresses.length == 0` is a precondition of reaching this code path at all.

### Impact Explanation
Any asset (ERC721/ERC1155 positions, stray ERC20/ETH not represented in `erc20TokenAddresses` for that call) that ends up owned/held by `address(Emporium)` — whether from a legitimate user's CASE 2 op (e.g., a swap/mint whose output recipient is the calling contract itself) — can be seized by any unprivileged third party via a subsequent CASE 2 call authorized only by a self-generated, ownership-free Min-circuit proof and `signerAddress = address(0)`. This is direct theft of a victim-funded asset/position, matching the Critical category (direct theft of shielded/in-flight user funds / executing calls or moving assets a wallet owner never authorized). It is repeatable against every asset that transiently lands on Emporium's own balance across any user's interaction.

### Likelihood Explanation
Preconditions: (a) some prior interaction (by any user) results in an asset owned by `address(Emporium)` itself rather than a `HinkalWallet`/stealth address — plausible whenever a CASE 2 op's callback (e.g., NFT mint `recipient`) is set to the calling context, or op logic mistakenly/naturally returns the asset to `msg.sender == Emporium`; (b) the attacker can construct a valid Min-circuit proof and a fresh unused `emporiumMessage`. Given that the Min circuit requires no proof of note ownership (`tokenNumber`/`nullifierAmount`/`outputAmount` can all be 0), any unprivileged attacker can generate this proof for their own chosen `callData` at negligible cost, and can monitor Emporium's on-chain balances (public) for extractable assets, making this front-runnable and cheap to execute repeatedly.

### Recommendation
Do not allow `stack.signerAddress == address(0)` to bypass authorization for CASE 2 stateless calls whose target/callData can create or move assets on behalf of a specific depositor; require every runAction invocation to bind to a specific depositor identity (e.g., via a Hinkal-generated commitment/H0/H1 stealth key or a mandatory signature), and never allow assets to be left owned by `address(Emporium)` itself — force all created positions to be recipient-checked against the caller's `HinkalWallet`/stealth address, or add an owner-tracking mapping in Emporium so only the original depositor (or their signed delegate) can later move an asset out via CASE 2.

### Proof of Concept
Hardhat fork test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, a `HinkalWallet`, and a Uniswap V3 `NonfungiblePositionManager` fork instance.
2. As "victim," call `Hinkal.transact` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, generating a Min-circuit proof for a `CircomData` whose `externalActionMetadata` encodes an `EmporiumStack` with `signerAddress = address(0)` and one CASE 2 op calling `mint(...)` with `recipient = address(emporium)`.
3. Assert `IERC721(nftManager).ownerOf(tokenId) == address(emporium)` (broken-equality left side would be victim's stealth address; actual right side is `emporium`).
4. As "attacker" (unrelated EOA), submit a second `Hinkal.transact` call with a freshly generated Min-circuit proof, a new unused `emporiumMessage`, `signerAddress = address(0)`, CASE 2 `op.callData = safeTransferFrom(emporium, attacker, tokenId)`.
5. Assert the call succeeds and `IERC721(nftManager).ownerOf(tokenId) == attacker`, proving theft with no privileged role, no signature, and no prior relationship to the victim's UTXO.

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
