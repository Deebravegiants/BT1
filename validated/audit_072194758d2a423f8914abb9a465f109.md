Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as the raw JSON body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and handed to app webhook handlers as trusted, tenant-identifying data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `to_signable_string` (the body) using the app's shared `api_secret_key` [2](#0-1) . After that single check, `Registry.process` builds `WebhookMetadata` directly from the request's `shop`, `topic`, `webhook_id`, and `api_version` accessors, all of which are simple header reads with no cryptographic binding to the HMAC [3](#0-2) [4](#0-3) .

This breaks the identity binding the report's bug class targets: `data.shop` (acted on by the app, e.g. to look up the tenant/session) is not the same value the HMAC "authenticates". Since `api_secret_key` is the same for every shop that has installed a given app, any tenant of that app can capture one of their own genuine webhook deliveries (valid body + valid HMAC over that body), then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a different (victim) shop's domain. `Utils::HmacValidator.validate` still passes because it only checks the body against the shared secret, and `Registry.process` forwards the attacker-chosen `shop` value straight into the handler as `WebhookMetadata#shop` [5](#0-4) , which per the gem's own documented usage pattern is used by host apps to select/act on tenant data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) .

### Impact Explanation
This is a cross-tenant access primitive: a malicious merchant/tenant of a multi-tenant app can forge a webhook that is accepted as valid (HMAC passes) yet claims to originate from any other shop domain of their choosing, causing the host application to process/act on attacker-supplied body content while attributing it to a victim tenant.

### Likelihood Explanation
Any user who has installed the app on at least one shop can trivially capture a legitimate webhook (body + HMAC header) delivered to their own endpoint and replay it with a modified shop-domain header. No access to `api_secret_key`, tokens, or the victim's infrastructure is required.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-verified content, or otherwise cryptographically tie them to the signed body (e.g., include them in `to_signable_string`, or cross-check `shop`/`topic` against values embedded in the signed payload) before trusting them in `WebhookMetadata`.

### Proof of Concept
1. App has two shops installed: attacker's `attacker.myshopify.com` and victim's `victim.myshopify.com`, both under the same Shopify app / `api_secret_key`.
2. Attacker's shop receives a genuine webhook: body `{"id":1}}`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over body>`.
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only verifies the body against the shared secret and passes [7](#0-6) .
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` and forwarded to the app's handler [8](#0-7) , letting the attacker inject data attributed to the victim tenant.
