## Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`) values that `ShopifyAPI::Webhooks::Registry.process` passes on to the application handler are read from unauthenticated HTTP headers. The equality the library implicitly claims to the app (`hmac valid` ⇒ `shop == the shop that produced this event`) does not hold, because the signed bytes and the acted-upon `shop` field are disjoint.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic`, however, are read straight from the (attacker-controllable, when hitting the endpoint directly) HTTP headers, with no binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, i.e. it only authenticates the raw body: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate` passes, and then forwards the *unauthenticated* `request.shop`/`request.topic` values straight to the app-defined handler as trusted metadata: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop_bound_by_hmac == shop_delivered_to_handler`

Because the api_secret_key (and therefore the HMAC) is shared across every shop that has installed a given app, a body+HMAC pair that is legitimately produced for one shop (e.g. an attacker's own store, on which they can trigger arbitrary webhook-eligible events such as `orders/create`) remains a *valid* signature no matter which `shop-domain`/`topic` headers accompany it. An attacker who operates their own shop (fully installed, unprivileged with respect to the target) can:
1. Trigger a real webhook delivery to capture a legitimate `(raw_body, hmac)` pair signed with the app's `api_secret_key`.
2. Replay that exact body+HMAC directly to the app's public webhook endpoint, substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain.
3. `Registry.process` will pass HMAC validation (body unchanged) and hand the handler a `WebhookMetadata` claiming to be from the victim shop.

This is the same bug class as the report's `VestedStaking` finding: an operation trusts a value (there, `usdtAmount`/balance delta; here, `shop`) that is not actually the value protected by the integrity check that gates the operation.

### Impact Explanation
Any application logic that uses the delivered `shop` value from `WebhookMetadata` to decide which merchant's data/session/order to mutate (the documented, expected usage pattern for this gem, per `docs/usage/webhooks.md`) can be tricked into acting on behalf of, or against, a different tenant using data supplied by the attacker's own shop but attributed to a shop they don't own — a cross-tenant access primitive gated only by the ability to install the app once as an ordinary merchant.

### Likelihood Explanation
Requires only that the attacker be an app-installing internet user capable of triggering ordinary store events (e.g., placing their own order to generate an `orders/create` webhook) — no access to `api_secret_key`, tokens, or any privileged account is needed. The webhook HTTP endpoint is by design internet-reachable and unauthenticated apart from the HMAC check.

### Recommendation
Bind `shop` (and `topic`) into the signed material that `HmacValidator` verifies, or independently authenticate `request.shop` (e.g., require it be included in the signable string alongside the raw body, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `host`, `code`, `state`, and `timestamp` together in `lib/shopify_api/auth/oauth/auth_query.rb#L34-L43`). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted for tenant selection without additional verification (e.g., cross-checking against a known/installed shop list is not itself sufficient, since the attacker's own shop is legitimately installed).

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" with the target app installed.
# Step 1: trigger any webhook-eligible event on their own shop to obtain a
# legitimately-signed (raw_body, hmac) pair, e.g. by placing an order.
captured_raw_body = '{"id": 1, ...}'          # captured from attacker's own delivery
captured_hmac     = "shopify-hmac-sha256-header-value" # captured from same delivery

# Step 2: replay directly to the app's public webhook endpoint with a
# forged shop-domain header pointing at the victim.
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => captured_hmac,          # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (it only checks captured_raw_body),
# and the registered handler receives WebhookMetadata#shop == "victim-shop.myshopify.com",
# even though that shop never produced this event or its HMAC.
```
