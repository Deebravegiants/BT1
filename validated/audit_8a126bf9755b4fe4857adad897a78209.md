### Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator` never covers the `shop`, `topic`, `webhook_id`, or `api_version` header values, even though `Webhooks::Registry.process` trusts those unauthenticated header fields (in particular `request.shop`) to identify which merchant tenant the payload belongs to.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` and compares it to the `hmac` field with `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to be only the raw HTTP body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated request headers with no cryptographic binding: [3](#0-2) 

`Webhooks::Registry.process` only checks that the body-only HMAC is valid, then hands `request.shop` (and `request.topic`) straight to the application's webhook handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(shop || topic || body, secret)`, but the actual check is `hmac == HMAC(body, secret)` while `shop` is trusted independently and unauthenticated. Because a single app's webhook secret (`Context.api_secret_key`) is shared across every shop that has the app installed, an attacker who controls one legitimate installation (e.g., their own test store) can capture a genuinely-signed webhook (valid `body` + `hmac`) generated for their own shop, then replay that exact `body`/`hmac` pair against the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. The HMAC check still passes because it never covers those headers, so `Registry.process` dispatches the forged event to the handler labelled as coming from the victim shop.

### Impact Explanation
This crosses the tenant boundary the gem is responsible for enforcing during webhook ingestion: an unprivileged holder of any single valid app installation can inject attacker-chosen webhook payloads that the host application will process as if they originated from a different, victim merchant. Depending on how the host app's webhook handlers use `shop`/`topic` (order sync, fulfillment, data deletion, GDPR webhooks, etc.), this enables cross-tenant data corruption or forged business events — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires the attacker to control (or install the app on) any single shop to obtain a validly-signed webhook body/HMAC pair, and the ability to send an HTTP POST with custom headers to the app's public webhook endpoint — both are trivially available to an unprivileged internet user with no access to `api_secret_key` or any victim credentials.

### Recommendation
Include the identity-binding fields in the signed payload verification path, e.g. have `Webhooks::Request#to_signable_string` incorporate `shop`, `topic`, and `webhook_id` (or otherwise verify these fields out-of-band against a trusted source, such as a per-shop record established during OAuth) rather than trusting the raw headers once the body-only HMAC passes.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic (e.g. `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)`).
2. Replay the captured request to the app's webhook endpoint, keeping `body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because `Request#to_signable_string` only checks `B` against `H`. [5](#0-4) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, so the host application processes attacker-controlled data under the victim shop's identity.
