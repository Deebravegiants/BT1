## Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while the shop that the webhook is attributed to is read directly from an HTTP header with no cryptographic binding to that signature [2](#0-1) . `Registry.process` validates only the body's HMAC and then trusts `request.shop` to build the `WebhookMetadata` handed to the host app's handler [3](#0-2) . This breaks the identity binding `HMAC(body) == HMAC(body)` **but** `shop_claimed_by_header != shop_actually_bound_by_signature`, exactly the "field acted on but not covered by the HMAC" class described in the report's bug pattern (an unbound value being trusted after a signature check that doesn't cover it).

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the caller-supplied `hmac` [4](#0-3) . For webhook requests, `to_signable_string` is defined to be just `@raw_body` [1](#0-0) , meaning the signature authenticates *only the body bytes*, not the `shopify-shop-domain` / `x-shopify-shop-domain` header that `Registry.process` and every registered handler use to attribute the event to a tenant [2](#0-1) .

Because the shop-domain header sits entirely outside the signed content, any actor who can obtain one genuinely-signed `(body, hmac)` pair — trivially available to any unprivileged internet user by installing the app on their own store and triggering a real webhook event for it — can replay that same `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `HmacValidator.validate` will still return `true`, since it never inspects the header. `Registry.process` will accept the forged request and invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen shop [5](#0-4) , exactly as it does for a legitimate webhook from that other shop.

The equality that must hold and is violated:
`shop_the_signature_was_issued_for == shop_the_handler_believes_it_received_the_event_from`

Before the attacker's request: body+hmac are valid *only* for the attacker's own shop's event. After: the same pair is replayed with a different shop-domain header, and the check still passes, so the host app processes an event "from" a shop the attacker does not control.

### Impact Explanation
Any app built on this gem that keys per-tenant state (order/customer records, entitlements, idempotency, billing state, etc.) off `WebhookMetadata#shop` can have that state corrupted or manipulated using data supplied by an attacker who only controls their own shop, without ever needing that victim shop's access token or `client_secret`. This is a cross-tenant access vulnerability: the boundary between shops is enforced only by an unauthenticated header, not by the HMAC that is supposed to be the trust anchor for the whole webhook pipeline.

### Likelihood Explanation
High likelihood of exploitability: the only prerequisite is control of any shop with the target app installed (something any unprivileged internet user can obtain by installing a public app on a free development store), the ability to trigger one qualifying webhook event, and the ability to send an HTTP POST with a modified header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required.

### Recommendation
Bind the shop identity into the signed content, or otherwise cryptographically tie the header to the payload, rather than trusting it unconditionally after only the body is verified. Concretely, `Webhooks::Request#to_signable_string` should not be the sole trust boundary for shop attribution — the gem (or its documentation) should require host applications to cross-check `request.shop` against a shop for which they already hold an established, independently-authenticated session before acting on the payload, and/or the library should expose a stricter validation path that fails closed when the shop cannot be independently corroborated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the real request Shopify sends, including body `B` and header `x-shopify-hmac-sha256: H`.
2. Attacker replays the captured request to the app's public webhook endpoint, keeping body `B` and header `H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body without complaint [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds despite the spoofed shop [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, causing the host application to process attacker-controlled data as if it originated from the victim shop [5](#0-4) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
