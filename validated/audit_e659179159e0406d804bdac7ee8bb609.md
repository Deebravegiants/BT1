### Title
Same-`assetId` batch withdrawals resolve to identical `txHash` due to `findMatchingWithdrawal`'s assetId-only match - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves each withdrawal in a batch by looking up the POA bridge's status list with `findMatchingWithdrawal`, which matches purely by `assetId` via `Array.prototype.find`, ignoring `WithdrawalIdentifier.index` entirely. When an intent contains N>1 withdrawals of the identical `assetId`, every index resolves to the same (first) matching record, so `watchWithdrawal`/`createWithdrawalCompletionPromises` report the same `status`/`txHash` for all N withdrawals even though only one has actually completed on-chain.

### Finding Description
Broken equality: for indices `i` and `j` (`i != j`) with identical `assetId`, `describeWithdrawal({index: i, ...}).txHash` must equal the on-chain outcome of withdrawal `i` specifically, but instead it equals `findMatchingWithdrawal(response.withdrawals, assetId)` — the first array element whose `nep141:${w.data.near_token_id} === assetId`, independent of `i`. Both calls read the exact same `response.withdrawals` list (from `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash })`) and the same `assetId`, and the `.find()` call always returns the same element regardless of `args.index`, so `describeWithdrawal` at index 0 and index 1 return identical results: [1](#0-0) [2](#0-1) 

The code comment explicitly documents this as an unsolved limitation: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) .

Attacker input: an ordinary user submits an intent with two (or more) `WithdrawalParams` entries sharing the same POA `assetId` (e.g., two `usdc.omft.near` withdrawals to different destination addresses/amounts within the same intent transaction). `createWithdrawalIdentifiers` assigns each a distinct per-route `index` [4](#0-3) , and `watchWithdrawal` calls `bridge.describeWithdrawal({...wid, logger})` per index independently and in parallel [5](#0-4) . Because `describeWithdrawal` never consults `args.index`, both promises converge on the first matching withdrawal record returned by the bridge API — if that first record is `COMPLETED`, both promises resolve with the same `txHash`, even though the second withdrawal is still `PENDING` on-chain.

No existing guard prevents this: `validateWithdrawal` and `supports()` only validate `assetId`/`destinationAddress` individually per withdrawal and never check for duplicate `assetId`s across the batch [6](#0-5) ; `createWithdrawalIntents` builds one intent primitive per withdrawal param independently [7](#0-6) ; nothing in the batching path (`createWithdrawalIdentifiers`) rejects duplicate assetIds in one intent.

### Impact Explanation
An integrator relying on `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` per-index results to credit off-chain accounting (e.g., mark withdrawal #1 for user A and withdrawal #2 for user B as paid) will see both promises resolve with the identical destination `txHash`, causing the integrator to record two payouts against a single actual transfer. This is a status/hash misreport that causes an integrator to credit twice — matching the High/Critical "status or hash misreport making an integrator credit or refund twice" category. It is fully repeatable any time a user (or the integrator on the user's behalf) submits a multi-withdrawal intent with duplicate `assetId`s, and it self-triggers purely from an ordinary user's own withdrawal request — no privileged action or third-party compromise is required.

### Likelihood Explanation
Preconditions: an intent with ≥2 withdrawals routed through `PoaBridge` sharing the same POA `assetId` (same token, same origin chain) but distinct destination addresses/amounts. This is a normal usage pattern (e.g., splitting a payout across two recipients in one intent) and requires no special privileges — any unprivileged intents.near user can construct such a batch. Attacker cost is nil (just constructing a normal multi-leg withdrawal). The misreport is deterministic once one of the duplicate-assetId withdrawals completes before the others, which is the common case for sequential POA settlement.

### Recommendation
Update `findMatchingWithdrawal`/`describeWithdrawal` to disambiguate same-`assetId` withdrawals within a batch, e.g., by tracking already-consumed withdrawal records per `(tx.hash, assetId)` and matching the Nth occurrence to the Nth `index` (after sorting deterministically, e.g., by amount as the existing comment suggests), or by requesting/using an API that returns a per-withdrawal-request identifier from the POA bridge instead of relying solely on `assetId` matching. At minimum, until fixed, reject or explicitly warn on intents containing duplicate `assetId`s within a `PoaBridge` batch so integrators aren't silently given incorrect per-index status.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
