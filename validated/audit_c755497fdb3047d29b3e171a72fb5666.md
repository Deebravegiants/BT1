This confirms the vulnerability. The `shop` field in `WebhookMetadata` (documented as "The shop domain of the webhook", used by host apps for tenant routing per `docs/usage/webhooks.md` line 26 example `shop_domain: data.shop`) is derived purely from the `x-shopify-shop-domain` header and is never included in the HMAC-signed bytes.

### Title
Webhook tenant identity (`shop` field) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over `@raw_body` only [1](#0-0) , while the `shop` attribute used downstream for tenant identification is read directly from the unauthenticated `x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the body's HMAC and then forwards the header-derived `shop` value straight into `WebhookMetadata`, which the host app's handler is expected to trust for shop/tenant routing [3](#0-2) .

### Finding Description
The equality the library is supposed to enforce is: `bytes verified by HMAC == bytes/fields the handler acts on`. Here that equality is broken: the HMAC only covers `raw_body` (`to_signable_string` returns `@raw_body`) [1](#0-0) , but `topic`, `shop`, `api_version`, and `webhook_id` are all parsed from headers that are completely outside the signature [4](#0-3) . `HmacValidator.validate` only checks `verifiable_query.hmac` against a signature computed from `to_signable_string`, i.e. the body [5](#0-4) .

Because the app's `api_secret_key` is the same secret used to sign webhooks for every shop that has installed the app (not a per-shop secret), any merchant/attacker who has installed the app on their own store can capture a genuinely Shopify-signed webhook `(raw_body, hmac)` pair for their own shop, then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. The HMAC still validates (it only checks `raw_body`), and `Registry.process` passes the attacker-controlled `shop` value into `WebhookMetadata.shop` and calls the app's handler with it [3](#0-2) . Documentation explicitly instructs handlers to key persistence/business logic off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) , so this gem hands the host application spoofed tenant identity alongside a "verified" signature, i.e. it breaks the binding `verified-HMAC-shop == acted-upon-shop`.

### Impact Explanation
This is a cross-tenant confusion vector: an attacker-controlled shop can cause the app to process webhook payloads (attributed to a spoofed body/topic they choose) under a victim shop's identity, since the gem itself asserts "did indeed come from Shopify" (per its own documentation) purely on the basis of an HMAC that never covers the `shop` field it hands to the handler.

### Likelihood Explanation
Any developer/merchant who can install the target app on a shop they control can trivially capture a real signed webhook and replay it with a modified `shop-domain` header — no access to `api_secret_key`, access tokens, or TLS interception is required, since the header is not part of the signed material by design of this class.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (or at minimum `shop`) in the signable string used for HMAC validation, or otherwise cryptographically bind the shop-domain header to the payload signature before constructing `WebhookMetadata`, so that `HmacValidator.validate` fails whenever any of these header-derived fields are altered independently of the signed body.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a real webhook (e.g. `orders/create`) and capture the raw POST including headers `x-shopify-hmac-sha256: <sig>` and `x-shopify-shop-domain: attacker.myshopify.com`, with `raw_body` = signed body.
2. Replay the identical request to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim.myshopify.com` (leave `raw_body` and `x-shopify-hmac-sha256` unchanged).
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`, which only re-hashes `raw_body` [1](#0-0)  — validation succeeds.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop: "victim.myshopify.com"` [7](#0-6)  and delivered to the app's handler, which (per the gem's own documented usage pattern) performs shop-scoped work using this spoofed value.
