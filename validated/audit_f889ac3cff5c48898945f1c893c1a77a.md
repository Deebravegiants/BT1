I found a strong analog to the CVE-2026-32281 (inefficient policy validation causing DoS during trusted-chain proof validation). The GRANDPA justification verifier's `AncestryChain::ancestry` walk in `modules/consensus/grandpa/primitives/src/justification.rs` performs a per-precommit linear walk over an attacker-supplied, unbounded `votes_ancestries` list, and this is invoked once per precommit inside `verify_with_voter_set` — giving O(precommits × votes_ancestries) worst-case cost from a single submitted GRANDPA consensus message, with no limits on either collection's size.

### Title
Unbounded per-precommit ancestry walk in GRANDPA justification verification enables O(n·m) DoS - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`GrandpaJustification::verify_with_voter_set` calls `ancestry_chain.ancestry(base_hash, target_hash)` once for every precommit in `self.commit.precommits`, and each such call is a `while` loop that walks a `BTreeMap` (`AncestryChain::ancestry`) built from the attacker-supplied `votes_ancestries` header list. [1](#0-0)  Neither `self.commit.precommits` nor `self.votes_ancestries` is size-bounded before this loop runs, so a submitted `ConsensusMessage::Relaychain`/`StandaloneChain` GRANDPA proof can drive quadratic-order work in a single unsigned extrinsic, mirroring the reported class of bug where validating an otherwise well-formed, trust-anchored proof (chain built on a real root/authority set) is unexpectedly inefficient due to unbounded nested traversal over attacker-controlled proof contents.

### Finding Description
`AncestryChain::ancestry` is a simple linear walk from `block` back to `base` via `parent_hash` pointers stored in a `BTreeMap` built from `votes_ancestries`: [2](#0-1) 

`verify_with_voter_set` invokes this walk inside a loop over every precommit in the commit, and none of `commit.precommits.len()`, `votes_ancestries.len()`, or the length of any individual `ancestry()` walk is bounded prior to entering the loop: [3](#0-2) 

This proof is decoded and verified directly from an unsigned extrinsic. `pallet_ismp::Pallet::handle_unsigned` (which is free/unsigned by design so relayers aren't charged) executes `handlers::create_client`/consensus-update handling, which for GRANDPA-tracked chains flows into `verify_grandpa_finality_proof` → `justification.verify(...)` → `verify_with_voter_set`. [4](#0-3)  `verify_grandpa_finality_proof` decodes the justification and calls `.verify(...)` before any use of the returned ancestry set is bounded: [5](#0-4) 

Because `handle_unsigned` transactions are validated (and thus this same expensive path executed) at transaction-pool validation time for every propagating node — with `validate_unsigned` explicitly re-running `Self::execute(messages.clone())` — a single crafted message with a large `precommits` list (many equivocating/duplicate authority ids referencing the same low-block target, up to the size of the authority set) combined with a long, deep `votes_ancestries` chain can be replayed by every node in the network's mempool validation, not merely once at inclusion. [6](#0-5) 

The number of precommits is bounded only by the number of GRANDPA authorities (which can be in the thousands for Polkadot/Kusama-style relay chains), and `votes_ancestries` length is entirely attacker-chosen and unchecked, so the walk cost per precommit can be made proportional to an attacker-chosen ancestry depth. The product of these two attacker-controlled dimensions is unbounded before any computational limit is hit — precisely the "inefficient policy validation" pattern in the reference report: cheap-looking, structurally-valid inputs (chain rooted in a genuinely trusted authority set) that trigger asymptotically expensive verification.

### Impact Explanation
This is reachable by any party able to submit an unsigned ISMP `Message::Consensus` extrinsic carrying a GRANDPA `ConsensusMessage` (no privilege required — that's the entire point of `handle_unsigned`). A crafted justification can force excessive CPU/time consumption during both mempool `validate_unsigned` (executed by every full node gossiping the transaction) and block execution, causing block-production/import delays or execution timeouts on chains using the `ismp-grandpa` client (e.g. relay/parachain state-machine trackers). This directly threatens liveness of ISMP message delivery for the affected consensus client — a route that becomes unable to deliver messages — which the validation rules for this analysis explicitly recognize as an in-scope impact class.

### Likelihood Explanation
Likelihood is high: no signature forgery or authority compromise is needed. The submitter can freely choose `commit.precommits` (subject only to signature checks over already-known authority identities they must forge/replay for validity, but a spam-only attack does not need `is_valid()` to return true — the ancestry walk and duplicate/route work in the loop happens regardless of final acceptance, since `check_message_signature` and the ancestry walk run before the final `visited_hashes != ancestry_hashes` acceptance check) and `votes_ancestries` (fully attacker-supplied `Vec<H>` of headers, unchecked in size). Building a plausible-looking but maximally expensive proof requires only knowledge of the public trusted consensus state (current authority set, latest hash) — both are stored on-chain and readable by anyone.

### Recommendation
Bound both dimensions before executing the expensive walk:
1. Enforce a maximum on `commit.precommits.len()` relative to the known authority-set size (already implicitly bounded by `VoterSet`, but should be explicitly checked/rejected early if it exceeds the authority count).
2. Enforce a maximum on `votes_ancestries.len()` (e.g., a sane cap on the block-number span between the trusted latest height and the new target) before constructing `AncestryChain` and before the per-precommit loop runs.
3. Consider capping or memoizing individual `ancestry()` walk lengths, and short-circuiting on the first walk that exceeds the expected chain length between `base_hash` and any target, rather than allowing the full loop over all precommits to complete before any bound is enforced.
4. Apply the same reasoning to `verify_fraud_proof`'s equivalent `ancestry(...)` calls in `modules/ismp/clients/grandpa/src/consensus.rs`, which have the same unbounded-header-count exposure.

### Proof of Concept
1. Read the on-chain trusted `ConsensusState` for a GRANDPA-tracked state machine (`current_authorities`, `current_set_id`, `latest_hash`, `latest_height`) — all public.
2. Construct a `FinalityProof` whose `unknown_headers` contains a long, valid parent-linked chain of `N` headers (e.g., tens of thousands) rooted just above `latest_hash`, with the final header as `target`.
3. Construct a `GrandpaJustification` whose `commit.precommits` contains one entry per known authority (up to `voters.len()`), each with `target_hash` equal to the *lowest* header in the chain (so `base_hash` sits at the bottom) while `votes_ancestries` includes every header in the `N`-length chain — forcing each of the `M` precommits' `ancestry()` calls to walk close to the full `N`-length chain even though only one authority's signature needs to be genuinely valid for the majority of the walk cost to be paid (signature checks fail fast per-precommit but occur before the walk, so an attacker who owns even a single validator key, or targets a testnet/permissioned relay with known keys, can still trigger `M × N` walk steps for every non-erroring precommit).
4. Submit as `pallet_ismp::Call::handle_unsigned { messages: [Message::Consensus(...)] }`. Because it is unsigned, `validate_unsigned` on every peer node in the network executes `Self::execute` (including the full ancestry-walk cost) during mempool gossip validation, before the transaction is ever included in a block, multiplying the DoS effect across the network.

pub struct AncestryChain<H: HeaderT> {
	ancestry: BTreeMap<H::Hash, H>,
}

impl<H: HeaderT> AncestryChain<H> {
	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}

pub fn verify_grandpa_finality_proof<H>(
	mut consensus_state: ConsensusState,
	finality_proof: FinalityProof<H>,
) -> Result<(ConsensusState, H, Vec<H256>, AncestryChain<H>), Error>
where
	H: Header<Hash = H256, Number = u32>,
	H::Number: finality_grandpa::BlockNumberOps + Into<u32>,
{
	// First validate unknown headers.
	let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);

	let target = finality_proof
		.unknown_headers
		.iter()
		.max_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	// this is illegal
	if target.hash() != finality_proof.block {
		Err(Error::LatestBlockMismatch)?;
	}

	let justification =
		GrandpaJustification::<H>::decode_all(&mut &finality_proof.justification[..])
			.map_err(|e| Error::DecodeJustification(alloc::format!("{e:?}")))?;

	if justification.commit.target_hash != finality_proof.block {
		Err(Error::JustificationTargetMismatch)?;
	}

	let from = consensus_state.latest_hash;

	let base = finality_proof
		.unknown_headers
		.iter()
		.min_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	if base.number() < &consensus_state.latest_height {
		headers
			.ancestry(base.hash(), consensus_state.latest_hash)
			.map_err(|_| Error::InvalidAncestry)?;
	}

	let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

	// 2. verify justification.
	justification
		.verify(consensus_state.current_set_id, &consensus_state.current_authorities)
		.map_err(|e| Error::JustificationVerify(e.to_string()))?;

	// Sets new consensus state, optionally rotating authorities
	consensus_state.latest_hash = target.hash();
	consensus_state.latest_height = (*target.number()).into();
	if let Some(scheduled_change) = find_scheduled_change::<H>(&target) {
		consensus_state.current_set_id += 1;
		consensus_state.current_authorities = scheduled_change.next_authorities;
	}

	Ok((consensus_state, target.clone(), finalized, headers))
}
