### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Finding Description
The identity binding that must hold is: `hmac_signature == HMAC(api_secret_key, bytes_the_app_acts_on)`. In this gem, the "bytes acted on" for a webhook include the `shop` (tenant identity) that gets attached to the dispatched event, but the HMAC only covers the raw request body.

`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop`, the unauthenticated header value, as the tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, so for webhooks it only ever checks the body bytes against the computed HMAC — it never authenticates which shop the payload is attributed to: [4](#0-3) 

Because the header carrying the tenant identity (`shop-domain`) sits entirely outside the HMAC's signed input, `verify(bytes) == true` says nothing about which shop the request is really for. Any party capable of obtaining one valid `(raw_body, hmac)` pair for their own shop (trivially available to any merchant who installs the app and receives real webhooks) can resend that exact body/HMAC pair with an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` still returns `true` because it only recomputes the signature over `raw_body`, and `Registry.process` forwards the attacker-chosen `shop` value straight to the handler via `WebhookMetadata`.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to scope side effects (e.g., "look up shop X's session/access token and act on its data", write to shop X's tenant records, or trigger per-shop business logic) can be made to process a *validly-signed* payload under a spoofed tenant identity. This is a cross-tenant access primitive: data or actions intended for shop A get attributed to shop B purely because the shop header is unauthenticated, satisfying the Critical "cross-tenant access" impact bar defined in scope.

### Likelihood Explanation
The prerequisite is low: the attacker only needs to be an ordinary merchant/installer of the target app (an "unprivileged internet user" relative to other tenants) capable of receiving one legitimate webhook for their own shop, or otherwise obtaining any one valid `(body, hmac)` pair (webhook bodies/HMACs are not treated as secret and are commonly visible in logs, proxies, or webhook-inspection tools). No knowledge of `api_secret_key` is required to perform the replay — only to have received one legitimate webhook.

### Recommendation
Bind the shop identity into the verified bytes instead of trusting an unauthenticated header. Options:
- Include the `shop-domain` (and `topic`/`webhook_id` if they are also relied upon) in the signable string used for HMAC verification, or
- Cross-check `request.shop` against an independently authenticated source (e.g., the shop associated with the delivered `webhook_id` via Shopify's Admin API), rejecting mismatches, before dispatching to handlers.

### Proof of Concept
1. Install the app on shop `attacker-shop.myshopify.com`; capture one legitimate webhook delivery: raw body `B` and its valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the shared `api_secret_key`).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` even though the payload was never issued for that shop, allowing the attacker-controlled body to be processed under the victim's tenant identity.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end
