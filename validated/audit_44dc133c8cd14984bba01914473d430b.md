## Title
Blacklisting a beneficiary for a single escrowed token permanently freezes the entire multi-token order escrow in `IntentsBase._withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` escrows orders that can hold multiple different ERC20 tokens as inputs (`order.inputs`). Settlement (`RedeemEscrow`/`RefundEscrow`) and cancellation paths all funnel into `IntentsBase._withdraw()`, which loops over every token in the withdrawal request and transfers each one to a single `beneficiary` in the same atomic call. If any one of those tokens implements a blacklist (e.g. USDC) and the beneficiary is blacklisted for it, `safeTransfer` reverts, the whole `_withdraw` call reverts, and — because it's invoked from `onAccept`/`onGetResponse`, which are themselves atomic — none of the other, non-blacklisted tokens in the same order can be released either. Since the beneficiary address is fixed by the order/commitment, every retry fails identically, permanently freezing the full escrowed basket.

### Finding Description
`_withdraw` iterates `body.tokens` and unconditionally transfers each to the same `beneficiary`: [1](#0-0) 

This function is reachable from the unprivileged, relayer-driven message-delivery path:
- `onAccept` on `RedeemEscrow`/`RefundEscrow` calls `_withdraw(..., finalize=true)` after only authenticating the message source, with no way to select or skip individual tokens: [2](#0-1) 
- `onGetResponse` (source-chain cancellation) calls the same `_withdraw` unconditionally: [3](#0-2) 
- Same-chain fills and cancellations reach `_withdraw` too: [4](#0-3) 

Crucially, when the top-level module call reverts, `EvmHost.dispatchIncoming` simply deletes the request receipt "so it can be retried" and returns without reverting the relayer's batch: [5](#0-4) 

This "retry" mechanism assumes the failure is transient (e.g., temporary gas issue or a bug that gets patched). A blacklist status is not transient — the beneficiary address baked into the already-signed/committed order or the already-delivered fill is fixed, so every future retry of the identical message hits the identical `safeTransfer` revert on the blacklisted token. The message can never be delivered, and because `_withdraw` treats the full `body.tokens` array as one atomic unit, **all** other (non-blacklisted) tokens in that same order/commitment are frozen along with the blacklisted one — there is no per-token release, no partial settlement, and no alternate sweep path for escrowed (non-dust) funds. The `SweepDust`/`_sweepDust` path only recovers protocol dust, not amounts still tracked in `_orders[commitment][token]`: [6](#0-5) 

The same unconditional-loop pattern (and thus the same weakness) exists in the Tron variant of the gateway: [7](#0-6) 

### Impact Explanation
This is a permanent freezing-of-funds bug reachable from ordinary protocol usage, not privileged action:
- A solver (filler) that fills a cross-chain order and delivers output tokens to the user on the destination chain can be permanently denied their entire input-token payout on the source chain if they are blacklisted for just one of the several input tokens in that order (e.g. mixed USDC+DAI escrow) — even though the solver already performed the fill in good faith.
- A user cancelling a multi-token order (destination-side `RefundEscrow` or source-side GET-response cancellation) can have their entire refund basket permanently stuck if they are blacklisted on just one input token.
- An attacker can deliberately weaponize this: place (or induce) an order with a mix of a blacklist-capable token and other valuable tokens, get blacklisted on the cheap/blacklist-prone token, and permanently lock the more valuable co-escrowed tokens belonging to a counterparty (solver) in the contract with no recovery path in the current protocol logic.

This matches "permanent freezing of funds" — Medium/High severity, consistent with the referenced report's classification.

### Likelihood Explanation
Likelihood is realistic: USDC (and similar tokens) actively blacklist addresses (e.g., addresses that interacted with sanctioned mixers), and the `IntentsBase`/`IntentGatewayV2` order model explicitly supports arbitrary multi-token `inputs`/`outputs` per order, so mixing a blacklistable stablecoin with other assets in one order is an ordinary, expected usage pattern, not a contrived edge case. No special privileges are required to trigger it — only that a legitimate participant's address ends up blacklisted for one of the tokens involved, which can happen at any time and outside the protocol's control.

### Recommendation
Do not perform per-token transfers as a single all-or-nothing atomic loop over a caller-uncontrollable beneficiary. Options:
- Make each token transfer failure isolated (e.g., wrap each `safeTransfer` in a try/catch or low-level call and, on failure, hold that specific token's amount in a per-account, per-token "claimable" escrow instead of reverting the whole withdrawal), while allowing the rest of the tokens to settle.
- Alternatively, support a "claim specific tokens" mechanism (as suggested in the source report) so a beneficiary/relayer can withdraw non-blacklisted tokens individually rather than requiring the full basket in a single transaction.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder` with `order.inputs = [USDC: 1000, DAI: 1000e18]`, destined to be filled by `solver`.
2. `solver` fills the order on the destination chain (delivers DAI/USDC-equivalent output to the user) via `fillOrder`, triggering a `RedeemEscrow` dispatch back to the source chain with `beneficiary = solver`.
3. Before the settlement message is delivered, `solver`'s address is blacklisted by USDC's issuer (e.g., via an external event unrelated to this protocol).
4. A relayer delivers the `RedeemEscrow` PostRequest to the source chain. `EvmHost.dispatchIncoming` → `IntentGatewayV2.onAccept` → `_withdraw` iterates `[USDC, DAI]`; the `IERC20(USDC).safeTransfer(solver, 1000)` call reverts due to the blacklist.
5. The entire `_withdraw` call reverts, `onAccept` reverts, `EvmHost.dispatchIncoming` (evm/src/core/EvmHost.sol:812-816) deletes the receipt and returns silently — the message is "retryable" but any subsequent delivery attempt hits the identical revert.
6. Result: both the 1000 USDC and 1000e18 DAI escrowed for this order remain permanently locked in `IntentGatewayV2`; the solver, despite having honestly filled the order, can never claim any portion of the payout, and there is no other function in the contract that can release funds tracked under `_orders[commitment][token]`.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
