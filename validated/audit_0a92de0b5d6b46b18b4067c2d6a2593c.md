### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`/`webhook_id`/`api_version`) from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the raw request body via `to_signable_string`. The `shop` value that the registry hands to the app's webhook handler is therefore never bound to the HMAC that proves message authenticity.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook solely with: [1](#0-0) 
`Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [2](#0-1) 
For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 
Meanwhile `request.shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material, yet it is forwarded as the tenant identity to the app's handler: [1](#0-0) 
This breaks the intended identity binding `HMAC-verified-bytes == tenant-identity-bytes`: the gem verifies the body's integrity/authenticity but not the shop that the body is attributed to. The documented app pattern treats `data.shop` as trustworthy for routing/attributing webhook data per tenant: [4](#0-3) 

### Impact Explanation
If an attacker can obtain any single valid `(raw_body, hmac)` pair produced under the app's shared `api_secret_key` (the same secret is used for every shop the app serves), they can resend that exact body/HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still pass (it only checks body bytes), so the registry will invoke the app handler with `shop: <victim>` and attacker-controlled `body`, causing the app to process/store data attributed to the wrong tenant — a cross-tenant data confusion issue.

### Likelihood Explanation
Exploitation requires the attacker to already possess a legitimately-signed `(body, hmac)` pair. Since the HMAC secret is per-app (not per-shop) and not derivable from the endpoint itself, an attacker without knowledge of `api_secret_key` and without ever having observed a genuine delivery (e.g., through their own installed instance of the app or by capturing traffic) cannot forge a new valid pair. This limits practical exploitation mostly to scenarios involving predictable/constant body payloads (e.g., topics whose body is always `{}` or otherwise shop-independent, as shown in the gem's own test fixtures) reused across shops; likelihood is low but the header/HMAC scope mismatch is a genuine, provable root-cause gap rather than a theoretical concern.

### Recommendation
Either include the `shop-domain` (and ideally `topic`) header in the HMAC-signable material, or explicitly document/require that consuming applications independently verify `request.shop` against their own list of installed shops before trusting it for tenant routing, since the gem's HMAC check does not cover header-derived identity fields.

### Proof of Concept
1. Attacker installs the app on shop `attacker.myshopify.com` (or otherwise obtains a genuine webhook delivery) for a topic whose body is constant/empty, e.g. as used in the gem's tests: `raw_body = "{}"`, `hmac = OpenSSL::HMAC.digest(sha256, api_secret_key, "{}")` — this HMAC is valid for *any* shop, not just the attacker's, because the signable string never includes the shop.
2. Attacker POSTs to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256: <same valid Base64 HMAC>`
   - `x-shopify-topic: <same topic>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body: `{}`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body bytes. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the request never actually originated from Shopify for that shop, and the app processes it as legitimate victim-shop data. [6](#0-5)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook.
