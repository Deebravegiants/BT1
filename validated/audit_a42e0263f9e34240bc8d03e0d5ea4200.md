### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream to route and attribute the webhook are read directly from unauthenticated HTTP headers that are never included in the HMAC computation.

### Finding Description
`Webhooks::Registry.process` accepts a request as valid whenever `Utils::HmacValidator.validate(request)` succeeds: [1](#0-0) 

`HmacValidator.validate_signature` computes the expected signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the identifying headers are part of the signed material: [3](#0-2) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` — all read straight from attacker-controllable HTTP headers — are what the registry uses to dispatch the handler and to build the trusted `WebhookMetadata` object passed to app code: [4](#0-3) [5](#0-4) 

This breaks the identity binding: `bytes verified by HMAC == bytes acted on as the tenant/topic identity` does not hold. The equality that should be enforced is `HMAC(secret, signed_material) == received_signature` where `signed_material` must include the `shop` (and ideally `topic`) that the application will treat as authoritative. Instead, only `raw_body` is bound, while `shop` (`request.shop`, from `x-shopify-shop-domain`) is trusted unconditionally by the handler.

An unprivileged actor who can obtain one validly-HMAC-signed webhook body for their *own* development/test shop (installing the app themselves is sufficient, and this is unprivileged relative to any other tenant) can replay that exact body to the app's webhook endpoint while substituting the `shop-domain`/`topic`/`webhook-id` headers with values for a different, victim shop. Because the signature check only validates `raw_body`, the forged headers pass validation, and the handler executes with `WebhookMetadata.shop` set to the victim's shop even though the payload was never actually generated or authorized for that shop.

### Impact Explanation
This qualifies as cross-tenant data attribution: an attacker with no access to any other merchant's credentials can cause the app to process attacker-supplied payload data as if it originated from a different (victim) shop, using a legitimately-signed body they generated for their own tenant. Depending on how the host application keys writes/business logic off `WebhookMetadata#shop`, this can corrupt or inject data into another tenant's records purely by manipulating unauthenticated headers, which meets the "cross-tenant access" bar since the tenant boundary (`shop`) is not cryptographically bound to the signed payload.

### Likelihood Explanation
Likelihood is moderate-to-high for any developer who can install the app on their own store (a normal, unprivileged onboarding action) and craft raw HTTP requests to the app's public webhook endpoint — no secrets, tokens, or privileged access are required, only knowledge of one's own validly-signed webhook body and the ability to swap headers on replay.

### Recommendation
Include the identity fields the handler trusts (`shop`, and ideally `topic`) in the HMAC-signable string, or otherwise cryptographically bind them to the payload (e.g., derive/verify `shop` from a value embedded in the signed body or from a separately-authenticated channel) before constructing `WebhookMetadata`, so `to_signable_string` in `lib/shopify_api/webhooks/request.rb` cannot be satisfied while headers are altered.

### Proof of Concept
1. Install the app on an attacker-controlled shop (`attacker.myshopify.com`) and capture a legitimate webhook delivery: raw body `B` and its valid `x-shopify-hmac-sha256` header `H`, computed as `HMAC-SHA256(secret, B) == H`.
2. Replay a request to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)`, which still equals `H`, so `Registry.process` (lib/shopify_api/webhooks/registry.rb:190) accepts the request.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ..., body: parsed(B))` (lib/shopify_api/webhooks/registry.rb:198-199), processing attacker-chosen content under the victim's tenant identity.
