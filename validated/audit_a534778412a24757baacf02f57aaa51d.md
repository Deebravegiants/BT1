### Title
Single shared `maxOracleAge` staleness bound applied to price feeds with heterogeneous heartbeats in `SimplexPaymaster` - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payment against two independent Chainlink feeds — the native asset feed and the registered token's feed — but validates both with a single, contract-wide `maxOracleAge` staleness bound, exactly the bug class described in the external report (one constant threshold applied to feeds with different real heartbeats). Because different feeds referenced by the same paymaster instance have very different actual heartbeats (the contract's own comments cite BSC stablecoins ~27s vs. Base/Ethereum stablecoins up to 24h), a `maxOracleAge` sized to tolerate the slowest feed silently accepts a badly stale reading from a much faster-updating feed.

### Finding Description
`_getOraclePrice` checks staleness against one shared state variable for every oracle call: [1](#0-0) 

`_tokenPrice` calls `_getOraclePrice` twice — once for `nativeOracle` and once for the registered token's `cfg.tokenOracle` — using the same `maxOracleAge` for both, even though the `Params` struct documentation explicitly acknowledges the feeds' heartbeats differ per chain and per token: [2](#0-1) [3](#0-2) 

The deployment tooling confirms this is a real operational hazard, not a hypothetical: the default `maxOracleAge` is deliberately set to ~25 hours to avoid reverts on the slowest (24h-heartbeat) stablecoin feeds, while the native asset oracle it is also applied to can have a far shorter heartbeat (e.g. ~27s on BSC): [4](#0-3) 

This mirrors the root cause of M-6 precisely: the protocol uses one constant/shared threshold (`STALE_PRICE_THRESHOLD` there, `maxOracleAge` here) to gate multiple price feeds whose true staleness windows differ by orders of magnitude, so a threshold sized for the least-frequently-updated feed lets a much-more-stale reading of the fast feed pass as "fresh."

The mispriced result feeds directly into the ERC-20 amount charged to the UserOperation sender in both supported flows: [5](#0-4) [6](#0-5) 

Any unprivileged party submitting a UserOperation through this paymaster (including intent solvers using it to sponsor bid-submission gas, per `docs/content/developers/evm/simplex/pricing.mdx`) is the party whose `prefundAmount`/`erc20Cost` is computed from these two oracle reads.

### Impact Explanation
Because `nativeUsd` and `tokenUsd` are each individually checked against the same, loosely-sized `maxOracleAge`, a fast-heartbeat feed (e.g., the native asset feed) can return an answer that is many hours out of date and still be accepted as "fresh" as long as it is within the bound sized for the slowest registered token feed. `_tokenPrice` (`tokenPrice = (nativeUsd * 10**tokenDecimals * (10000+markupBps)) / (tokenUsd*10000)`) then computes the ERC-20-per-gas rate directly off that stale reading. If the true native asset price has since risen relative to the stale cached price, `_erc20Cost`/`prefundAmount` undercharges the sender in ERC-20 terms for the actual native gas cost the paymaster must reimburse via `entryPoint()`, draining the paymaster's/treasury's economic value with every UserOperation submitted while the fast feed is stale but within the shared bound. This is a direct fund-loss vector reachable by any address that can submit a UserOperation through the paymaster's PERMIT or PERMIT2 modes — no privileged role required.

### Likelihood Explanation
The condition is not a rare edge case: the contract's own deploy script sets `maxOracleAge` to ~25 hours specifically to tolerate the *slowest* feed heartbeat it expects to register, while simultaneously using that same bound to gate the native asset feed, whose heartbeat is documented in the same file as being far shorter (seconds, not hours) on some chains. Any period where the native feed genuinely stalls or is delayed (congestion, deviation-threshold-only updates, oracle node downtime) for longer than its real heartbeat but shorter than the shared `maxOracleAge` window will be silently accepted.

### Recommendation
Track and enforce a per-oracle staleness bound (e.g., a `maxOracleAge` per `nativeOracle` and per registered `TokenConfig.tokenOracle`) instead of one contract-wide value, mirroring the standard per-feed heartbeat configuration rather than reusing a single constant/parameter across feeds with different update cadences.

### Proof of Concept
1. Governance deploys/updates `SimplexPaymaster` with `maxOracleAge = 90_000` (≈25h) to accommodate a registered stablecoin feed with a 24h heartbeat, per `evm/script/DeploySimplexPaymaster.s.sol` lines 18-20.
2. The same instance's `nativeOracle` (e.g., BNB/USD, real heartbeat ~1 min per the external report's analog) stalls or is delayed for several hours — well past its real heartbeat but under 25h.
3. A user or intent solver submits a UserOperation through PERMIT2 mode; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(nativeOracle, ...)` (`evm/src/utils/SimplexPaymaster.sol:662-668`) accepts the stale native price because `block.timestamp - updatedAt <= maxOracleAge`.
4. `prefundAmount` in `_prefund` (`evm/src/utils/SimplexPaymaster.sol:582`) is computed from this stale, mispriced rate, systematically under- or over-charging the ERC-20 amount relative to the paymaster's actual native-gas expenditure, extracting value from (or unfairly overcharging) the paymaster treasury on every such operation until the native feed updates.

        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    )
        internal
        view
        override
        returns (uint256 validationData, IERC20 token, uint256 tokenPrice)
    {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode != 0x00 && mode != 0x02) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction

            (,,, uint256 deadline,,,) = _parsePermit2Data(data);
            // Surfacing the permit deadline as validUntil lets bundlers drop
            // expiring ops instead of discovering it through a Permit2 revert.

            validationData = ERC4337Utils.packValidationData(true, 0, validUntil);

    function _prefund(
        PackedUserOperation calldata userOp,
        bytes32 userOpHash,
        IERC20 token,
        uint256 tokenPrice,
        address prefunder_,
        uint256 maxCost
    )
        internal
        override
        returns (bool prefunded, uint256 prefundAmount, address prefunder, bytes memory prefundContext)
    {
        bytes calldata data = userOp.paymasterData();
        if (uint8(data[0]) != 0x02) {
            return super._prefund(userOp, userOpHash, token, tokenPrice, prefunder_, maxCost);
        }

        (, uint256 permitAmount, uint256 nonce, uint256 deadline, uint8 v, bytes32 r, bytes32 s) =
            _parsePermit2Data(data);
        prefundAmount = _erc20Cost(maxCost, userOp.maxFeePerGas(), tokenPrice);
        if (prefundAmount > permitAmount) revert InsufficientPermitAmount(permitAmount, prefundAmount);
        // Solidity's own extcodesize revert on a code-less target is not caught by try/catch.
        if (address(PERMIT2).code.length == 0) revert Permit2NotDeployed();

        // Charge the token _fetchDetails already validated as registered and active, rather
        // than re-trusting the mode byte's token field, so the external call never depends
        // on the caller-ordering of the base contract.
        address tokenAddr = address(token);
        // `prefunder_` is who the base says funds the op (userOp.sender today); use it so this
        // branch stays aligned with the mode-0 branch that forwards it to super._prefund.
        address owner = prefunder_;
        try PERMIT2.permitTransferFrom(
            ISignatureTransfer.PermitTransferFrom({
                permitted: ISignatureTransfer.TokenPermissions({token: tokenAddr, amount: permitAmount}),
                nonce: nonce,
                deadline: deadline
            }),
            ISignatureTransfer.SignatureTransferDetails({to: address(this), requestedAmount: prefundAmount}),
            owner,
            abi.encodePacked(r, s, v)
        ) {
            emit Permit2Executed(tokenAddr, owner, prefundAmount, nonce);
        } catch (bytes memory reason) {
            revert Permit2Failed(tokenAddr, reason);
        }

        return (true, prefundAmount, owner, "");
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
