### Title
Webhook HMAC covers only the raw body, not the shop/topic identity — enabling cross-tenant webhook forgery (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload as the raw request body only, while the shop and topic that the registry uses to dispatch and attribute the event come from separate, unsigned HTTP headers. Because a single app-level `api_secret_key` is shared across every shop that installs the app, a merchant who installs the app on their own store can obtain a validly-HMAC'd body and replay it against the same endpoint while swapping the shop-identifying header to impersonate a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The shop, topic and webhook id are read from HTTP headers that are never mixed into the signed bytes: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e. the raw body) against the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` trusts the HMAC check and then dispatches to the handler using `request.shop` (an unauthenticated header) as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is: `bytes verified by HMAC == bytes (including shop/topic) acted upon by the handler`. Here that equality is broken — the HMAC only binds the JSON body, not the `shop-domain`/`topic`/`webhook-id` headers used to route and attribute the event to a specific tenant. Since the same `api_secret_key` signs webhooks for every shop on the app, a body+HMAC pair produced for shop A remains cryptographically valid when replayed with shop B's domain in the header.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who installs the target app on their own (attacker-controlled) shop can trigger a webhook with attacker-chosen JSON content, capture the resulting valid `(raw_body, hmac)` pair, then replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `WebhookMetadata` is built with the attacker-controlled `shop` value, causing the app's webhook handler to process attacker-supplied data as if it originated from the victim's store — a cross-tenant access/spoofing condition.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a store they control (a normal, unprivileged step for any Shopify app that supports installation), craft a webhook payload of their choosing by performing an action on their own store, and send a forged HTTP POST to the app's public webhook endpoint with modified headers. No access token, `client_secret`, or session compromise of the victim is needed.

### Recommendation
Bind the tenant/topic identity into the verified bytes, analogous to an `eip-712`-style domain separator: include `shop-domain`, `topic`, and `webhook-id` (or otherwise cryptographically bind them, e.g., by hashing them together with the body before HMAC comparison) in `to_signable_string`, or independently verify that the shop/topic values in the headers match values embedded in the signed payload before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `products/create`) with an attacker-crafted JSON body; capture the raw request body and its `shopify-hmac-sha256` header sent by Shopify (valid because it's signed with the app's shared `api_secret_key`).
3. Replay an HTTP request to the app's webhook endpoint with the identical raw body and `shopify-hmac-sha256`, but set `shopify-shop-domain: victim-shop.myshopify.com` (and desired `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, per `lib/shopify_api/webhooks/registry.rb:188-199`, causing the app to act on forged data attributed to the victim tenant.
