## Finding: Webhook HMAC Validation Does Not Cover the `shop-domain` Header, Allowing Cross-Tenant Webhook Spoofing

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` attribute used to attribute the webhook to a tenant is read from an HTTP header that is **not included** in the signed payload. Any user who can obtain one valid `(body, hmac)` pair — e.g., by installing the app on their own store and receiving a legitimate webhook — can replay that same body/HMAC pair while changing the `X-Shopify-Shop-Domain` header to a victim shop, and the HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns **only the raw body** — the `shop` value (read from the `x-shopify-shop-domain` / `shopify-shop-domain` header) is never part of the signed material: [3](#0-2) 

The unauthenticated `shop` value is then propagated directly into the tenant-scoping metadata passed to the app's webhook handler: [4](#0-3) 

This breaks the identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == authentic_shop_for(body)`, but the two are never cryptographically tied together. Since Shopify signs webhooks per-app (using the app's single `client_secret`) rather than per-shop, any shop that has installed the app can produce a fully valid `(body, hmac)` pair for its own events. That same pair remains valid if replayed with a different `shop-domain` header value, letting the attacker make the app process (and dispatch to handlers as) a webhook "from" an arbitrary victim shop.

### Impact Explanation
This allows cross-tenant confusion: the receiving application will call the registered webhook handler with `WebhookMetadata#shop` set to an attacker-chosen shop domain while the `body` content actually originated from the attacker's own shop. Any app logic that uses `request.shop` to select or update per-tenant records (the intended and documented purpose of this field) can be tricked into associating attacker-supplied data with another merchant's tenant, without needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Any unprivileged user who installs the target app on their own development/test store can obtain a valid `(body, hmac)` pair for free by triggering a normal Shopify event. Replaying that request to the app's public webhook endpoint with a forged `shop-domain` header requires only standard HTTP tooling — no secret material, TLS interception, or social engineering is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered payload, or otherwise cryptographically tie the header value to the signed body (e.g., include it in `to_signable_string`, or cross-check it against a known/registered shop for the receiving app installation) before trusting `request.shop` for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own store; Shopify sends a POST to the app's webhook endpoint with a body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` re-computes `HMAC(secret, B)` — identical to before, since the signable string is body-only — and the check passes. [5](#0-4) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the payload actually came from the attacker's own shop. [6](#0-5)

        end
