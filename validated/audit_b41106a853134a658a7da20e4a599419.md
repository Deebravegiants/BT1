### Title
`Webhooks::Request#to_signable_string` excludes `shop`, `topic`, `webhook_id`, `api_version` header fields trusted by `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Utils::VerifiableQuery` requires only that `to_signable_string` return "a" string and `hmac` return an optional string; it does not require that string to cover every field a consumer relies on. `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `Webhooks::Registry.process` trusts header-derived `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` as authenticated tenant-identifying data after `Utils::HmacValidator.validate` succeeds.

### Finding Description
The claimed binding is: `HmacValidator.validate(request) == true` should imply `request.shop == the tenant Shopify actually sent this webhook for`. In fact `validate` only checks `HMAC-SHA256(secret, request.to_signable_string) == request.hmac`, and `to_signable_string` for `Webhooks::Request` is defined as `@raw_body` alone [3](#0-2) . The `hmac` itself is derived from the `hmac-sha256` header [4](#0-3) , but `shop`, `topic`, `webhook_id`, `api_version` are derived from separate, unsigned headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) [5](#0-4) . `Registry.process` validates only the body/HMAC pairing and then trusts these header fields to route the handler and construct `WebhookMetadata` [1](#0-0) .

An attacker who can register their own development shop and receive their own validly-signed webhook (body + matching HMAC) can replay that exact body/HMAC pair to the victim app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) to name a different, victim shop. Because the signature covers only the body, `HmacValidator.validate` still succeeds, and `Registry.process` will invoke the handler with `WebhookMetadata.new(topic: ..., shop: <attacker-forged shop>, ...)`. If the app's handler logic keys off `shop` (as is standard for merchant-scoped side effects, e.g. finding a session/access token by shop domain and taking action on behalf of it), the attacker causes the app to process attacker-controlled webhook body content under the identity of a shop domain the attacker does not own.

This is a genuine gap between what the `VerifiableQuery` interface promises (`hmac` exists, `to_signable_string` exists) and what callers assume (that all fields they read off the implementing object were covered by the signature). `AuthQuery#to_signable_string` by contrast composes `code`, `host`, `shop`, `state`, `timestamp` into the signed string, covering everything a caller of `AuthQuery` reads [6](#0-5) , so the AuthQuery side has full coverage. The gap is specific to `Webhooks::Request`.

No existing guard closes this: `HmacValidator.validate` never inspects header consistency; `Registry.process` never re-derives `shop` from the signed payload; Sorbet typing only enforces the interface signature, not semantic coverage.

### Impact Explanation
An attacker who owns a legitimate development shop can forge the tenant-identifying metadata (`shop`, possibly `topic`/`webhook_id`) of a webhook delivered to a third-party app while keeping a validly-signed body, causing the app to act on attacker-chosen webhook payload content attributed to an arbitrary victim shop domain of the attacker's choosing. This matches the "authentication bypass" / cross-tenant class: an unauthenticated (header-forged) value (`shop`) is trusted as if it were authenticated by the HMAC, and one tenant's forged request can touch data logically scoped to another shop identifier. The severity depends heavily on what the specific app's `WebhookHandler#handle` implementation does with `shop`/`topic`; this gem provides the primitive gap, but actual account/data compromise requires an app that trusts `WebhookMetadata#shop` for authorization decisions.

### Likelihood Explanation
Preconditions: the attacker needs a real (self-owned) development shop able to register a webhook subscription and receive one legitimately-signed webhook delivery to capture a valid `(raw_body, hmac)` pair; they then send a forged HTTP request directly to the victim app's public webhook endpoint with modified `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers but the captured body and HMAC. This requires no secrets, is repeatable against any number of victim shops sharing the same app, and costs only the ability to create a free development store and send arbitrary HTTP requests — both explicitly within the attacker's allowed capabilities.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, and ideally `api_version`) inside `Webhooks::Request#to_signable_string`, or have `HmacValidator`/`Registry.process` independently verify that the header-derived `shop` matches an expected value bound to the signature (Shopify's real HMAC only covers the body by design upstream, so the fix must be either to canonicalize headers into the signed string within this gem before HMAC comparison, or to require/validate `shop` via a separate authenticated channel before dispatching `handler.handle`).

### Proof of Concept
```ruby
# test/webhooks/registry_forged_shop_test.rb
require "test_helper"

class RegistryForgedShopTest < Test::Unit::TestCase
  def test_hmac_validation_does_not_bind_shop_header
    body = '{"id":1}'
    secret = ShopifyAPI::Context.api_secret_key
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
    ).strip

    legit = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "shopify-topic" => "orders/create",
        "shopify-hmac-sha256" => hmac,
        "shopify-shop-domain" => "attacker-owned-shop.myshopify.com",
      },
    )
    assert ShopifyAPI::Utils::HmacValidator.validate(legit)

    forged = ShopifyAPI::Webhooks::Request.new(
      raw_body: body, # same body, same hmac
      headers: {
        "shopify-topic" => "orders/create",
        "shopify-hmac-sha256" => hmac,
        "shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant
      },
    )

    # Signature still validates even though "shop" was substituted -
    # proving to_signable_string does not cover the shop field the caller trusts.
    assert ShopifyAPI::Utils::HmacValidator.validate(forged)
    assert_equal "victim-shop.myshopify.com", forged.shop
  end
end
```
This demonstrates the equality `HmacValidator.validate(request) == true` holds identically for both the legitimate and the shop-forged request, proving `to_signable_string` does not cover `shop`, which `Registry.process` treats as authenticated tenant data.
