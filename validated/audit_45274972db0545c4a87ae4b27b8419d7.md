### Title
`shop-domain` webhook header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC that `Registry.process` validates is computed only over the raw request body, never over this header. This breaks the intended identity binding `hmac ==_verified== (secret, shop, body)`, since in reality only `hmac ==_verified== (secret, body)` holds while `shop` flows unauthenticated into the webhook handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the values fed into `HmacValidator.validate`, and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, in contrast, is read straight from the (attacker-controllable) HTTP header, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and then forwards `request.shop` directly to the app's webhook handler as the tenant identifier, without any additional check that ties the shop header to the signed payload: [3](#0-2) 

`HmacValidator.validate_signature` confirms the digest is computed purely from `verifiable_query.to_signable_string` (the body) and the secret — the shop header never enters the HMAC computation: [4](#0-3) 

Because the shop header is outside the HMAC's scope, any request body that was legitimately HMAC-signed by Shopify for one shop (tenant A) — e.g., a webhook payload the attacker's own store received, or any other authentic body/HMAC pair the attacker can obtain — can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a different shop domain (tenant B). `HmacValidator.validate` still returns `true` because it only re-derives and compares the digest of the body, and `Registry.process` will then invoke the handler with `shop: "tenant-B"` even though the signed body actually originated for tenant A. This is exactly the identity-binding class described in the report: a field (`shop`) that is acted upon by the application logic but is not covered by the value that was cryptographically verified (the HMAC).

### Impact Explanation
Any host application that follows the documented pattern of using `WebhookMetadata#shop` (built from `request.shop`) to select which merchant/tenant record to update — the exact intended usage of this API — can be made to apply an attacker-supplied, correctly-HMAC'd body to the wrong shop's tenant context. This is a cross-tenant integrity issue: data legitimately signed for shop A gets attributed and acted on as if it belongs to shop B purely because the HMAC does not bind the `shop-domain` header. This satisfies the "cross-tenant access" high/critical impact bucket, since the trust boundary between merchants is broken by the gem's own webhook-verification design.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimate `(body, hmac)` pair signed with the app's `api_secret_key` — most straightforwardly by installing the app on their own store and capturing (or simply reusing) the webhooks Shopify sends them, since a merchant installing an app is otherwise an unprivileged party with respect to other merchants' data. No access to `api_secret_key`, access tokens, or the target's session is needed; the attacker only replays a request they legitimately received to the app's own public webhook endpoint with a modified header. This is a realistic, credential-free replay achievable purely with knowledge of this gem's own verification code path.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signable string, or otherwise cryptographically bind the shop claim to the verified payload, so that `HmacValidator.validate` fails whenever the shop header has been altered relative to what was actually signed by Shopify. At minimum, document that `request.shop` must never be trusted without further out-of-band verification (e.g., against Shopify's known list of shops for the app), and consider adding a first-class check in `Registry.process` that verifies the shop is consistent with the registered session for the topic.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and configures a webhook endpoint they control (or otherwise captures) to receive a legitimate webhook, obtaining a genuine `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's `api_secret_key`.
2. Attacker sends this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but replaces the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the request; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [5](#0-4)  and it matches, since the body/HMAC pair is authentic.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` [6](#0-5) , causing the host application to process attacker-controlled data under the victim shop's tenant context, despite the HMAC never having verified that binding.
