### Title
Unauthenticated exposure of raw private key material and arbitrary message signing once wallet is unlocked - (File: features/key-viewer/module/key-viewer.ts)

### Summary
The `@exodus/key-viewer` module's `getEncodedPrivateKeys` and the `@exodus/message-signer` module's `signMessage` both perform sensitive private-key operations (raw key export, arbitrary data signing) gated solely on the wallet's global "unlocked" state, with no per-action password/biometric re-authentication. Any caller with access to these module APIs while the wallet session is unlocked can retrieve the raw encoded private key or sign arbitrary data without further confirmation, exactly mirroring the reported "Sign & Verify"/"Account Keys" issue.

### Finding Description
`KeyViewer.getEncodedPrivateKeys` fetches the wallet account, derives the key identifier, and calls `keychain.exportKey({ seedId, keyId, exportPrivate: true })` to obtain the raw private key material, which it then encodes and returns directly: [1](#0-0) .

The only gate inside `keychain.exportKey` is `#assertPrivateKeysUnlocked([seedId])`, which merely checks the seed's lock flag (`#seedLockStatus`) — a boolean set once when the wallet session is unlocked and cleared only on `lockPrivateKeys()`: [2](#0-1) [3](#0-2) .

Similarly, `SeedBasedMessageSigner.signMessage` derives the key identifier and asks the keychain's signer to sign arbitrary caller-supplied `message` data with no additional authentication step: [4](#0-3) . The public `MessageSigner.signMessage` entry point forwards the request straight through to the underlying signer: [5](#0-4) .

There is no password prompt, timeout, or biometric check anywhere in these code paths — the private key/signing capability is available to any caller for as long as the wallet remains unlocked, which is the exact vulnerability class described in the report ("Anyone with access to an unlocked wallet ... can perform those two actions").

### Impact Explanation
Once a wallet session is unlocked, any code path with access to the `keyViewer` or `messageSigner` module/API (e.g., a compromised or malicious dApp/provider integration, or a UI surface built on top of these headless SDK modules) can extract the raw private key in cleartext or sign arbitrary data with the user's key, without any secondary confirmation. This directly leads to full wallet compromise (funds theft) if an attacker gains any access to an unlocked session, matching the report's "high difficulty, high impact" characterization.

### Likelihood Explanation
Exploitation requires access to an already-unlocked wallet session (physical access, malware with UI/API access, or a compromised integration calling these headless SDK APIs) — the same precondition described in the original report. No additional secrets or bypass of encryption are required since the gating check is a simple boolean unlocked/locked flag rather than a re-authentication step.

### Recommendation
Require a fresh password (or biometric-backed passphrase re-entry) immediately before `keyViewer.getEncodedPrivateKeys` and `messageSigner.signMessage` execute, rather than relying solely on the session-wide unlocked flag checked by `#assertPrivateKeysUnlocked`. Store private key material only as ciphertext by default, decrypt only transiently for the specific operation, and zero it immediately after use. Add a UI-level timeout that clears any displayed secret key and forces re-authentication for subsequent reveal/sign actions.

### Proof of Concept
1. Unlock the wallet (`wallet.unlock({ passphrase })`) once, establishing the session.
2. Without any further authentication, call `exodus.keyViewer.getEncodedPrivateKeys({ baseAssetName: 'bitcoin', walletAccount: 'exodus_0' })` — the raw private key is returned in plaintext, matching the flow exercised in the test `sdks/headless/__tests__/key-viewer.test.js`. [6](#0-5) 
3. Likewise call `messageSigner.signMessage({ baseAssetName, walletAccount, message: { rawMessage } })` to sign arbitrary attacker-chosen data with the account's key, with no additional password/biometric prompt, as shown in the message-signer test flow. [7](#0-6)

  async exportKey({ seedId, keyId, exportPrivate, exportPublic = true }) {
    assert(typeof seedId === 'string', 'seedId must be a string')

    if (exportPrivate) {
      this.#assertPrivateKeysUnlocked([seedId])
    }

    keyId = new KeyIdentifier(keyId)

    const hdkey = this.#getPrivateHDKey({
      seedId,
      keyId,
      getPrivateHDKeySymbol: this.#getPrivateHDKeySymbol,
    })
    const privateKey = hdkey.privateKey
    let publicKey = null

    if (exportPublic) {
      publicKey = await this.#getPublicKeyFromHDKey({ hdkey, keyId })
    }

    const { xpriv, xpub } = hdkey.toJSON()
    return {
      xpub: exportPublic ? xpub : null,
      xpriv: exportPrivate ? xpriv : null,
      publicKey,
      privateKey: exportPrivate ? privateKey : null,
    }
  }
