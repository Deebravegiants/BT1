### Title
Signup-time config values are re-fetched from an unlocked, backend-mutable `Mutex` mid-flight, letting the backend change fraud/age/self-serve parameters after a signup has already started - (File: `src/plans/mod.rs`, `src/config.rs`)

### Summary
The Slurp report describes a value (`clerk()` fee) that is read fresh at the moment of a privileged call, allowing the privileged party to change that value between the time a user commits to an action and the time it is executed, to the user's detriment. The orb-core analog is `orb.config` (`Arc<Mutex<Config>>`), which is downloaded from the management backend on a periodic interval and can be updated *while a signup is in progress*. `MasterPlan::do_signup` and its sub-steps each independently call `orb.config.lock().await` to read out fields such as `self_serve`, `pcp_v3`, `child_threshold`, and `fraud_check_engine_config` at different points in the same signup, rather than taking one consistent snapshot for the whole flow.

### Finding Description
`do_signup` destructures a snapshot of `Config` (`self_serve`, `pcp_v3`, `orb_relay_*`, `operator_qr_expiration_time`, etc.) at the very start of the function via `*orb.config.lock().await`. [1](#0-0) . Later phases of the very same signup (biometric capture, fraud detection, pipeline evaluation) independently re-acquire the config lock in separate functions (`src/plans/biometric_capture/mod.rs`, `src/plans/biometric_pipeline/mod.rs`, `src/plans/qr_scan/mod.rs`) rather than reusing the snapshot taken at signup start.

Meanwhile, `Config::download_and_store` overwrites the shared `Arc<Mutex<Config>>` in place whenever a new config is fetched from the management backend endpoint [2](#0-1) , and this config includes fraud-sensitive fields such as `child_threshold` (under-age classifier threshold) and `fraud_check_engine_config` [3](#0-2) . The download is triggered on a periodic interval by the observer/master-plan loop, independent of whether a signup is currently underway.

Because no single, immutable configuration snapshot is threaded through the entire signup pipeline, the backend (an entity analogous to the "clerk" in the Turbo report, i.e., a privileged-but-not-root actor whose config changes are not directly authorized by the end user) can alter thresholds such as `child_threshold` or fraud-check toggles in the middle of an in-progress, unprivileged user's signup. This is architecturally identical to the Slurp bug: a value fetched "live" at multiple points of a single logical operation, changeable by a privileged party in between those reads, with no snapshot/lock held for the duration of the operation.

### Impact Explanation
If the backend config used for age/fraud enforcement is changed between the start of biometric capture and the later fraud/age evaluation of the same signup, a single signup could be evaluated with a mix of old and new thresholds. This could allow a signup that should have been blocked as fraud or as underage (under old config) to complete with the new, more permissive config, or vice versa, causing an unintended fraud-check outcome for that specific in-flight signup. It is a misattribution/inconsistent-enforcement risk on the fraud/liveness enforcement path rather than a direct biometric-disclosure bug.

### Likelihood Explanation
This requires the config polling/download to race with an in-progress signup's phases, which is plausible given `CONFIG_UPDATE_INTERVAL`-driven background refresh runs concurrently with the multi-step signup flow (QR scan → capture → pipeline → fraud check → enrollment), each step independently reading `orb.config`. It does not require an on-orb attacker; it only requires the normal backend config refresh to coincide with a signup, which will happen occasionally by construction over time, not needing an active adversary — making this closer to a design/timing correctness issue than an actively exploitable single-user attack in the same way as the Turbo fee-frontrun (which required a deliberate governance action to time the change).

### Recommendation
Take a single `Config` snapshot at the very start of a signup (already partially done for a few fields) and thread that entire snapshot through all subsequent phases (`biometric_capture`, `biometric_pipeline`, `detect_fraud`, `enroll_user`) instead of re-locking `orb.config` at each phase. This guarantees a signup is fully evaluated against one consistent configuration, closing the "config change mid-flight" TOCTOU window analogous to the reported fee-frontrun issue.

### Proof of Concept
1. Attacker/backend operator (or normal automated config rollout) triggers a config update setting `child_threshold` or `fraud_check_engine_config` to more permissive values while orb is mid-signup for a specific user (after QR scan/config snapshot at `src/plans/mod.rs:497-506`, before `detect_fraud`/pipeline evaluation independently re-reads config).
2. Because `detect_fraud`/`biometric_pipeline` re-fetch `orb.config.lock().await` fresh rather than using the initial snapshot, the same signup gets evaluated with the new, weaker thresholds even though it started under the old, stricter ones.
3. Signup completes and is enrolled/tagged `SignupReason::Normal` under thresholds that were not in effect when the signup was initiated, demonstrating the config-timing inconsistency within a single logical operation. [4](#0-3)

    pub async fn download_and_store(config: Arc<Mutex<Config>>) -> Result<()> {
        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }
