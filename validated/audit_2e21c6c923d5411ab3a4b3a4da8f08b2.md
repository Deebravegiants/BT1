## Analog Found

### Title
Unchecked zero-address beneficiary in Intent Gateway order fill/escrow release permanently burns solver and user funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The Intent Gateway's `Order.output.beneficiary` field (a user-supplied `bytes32` recipient address for the swap payout) and the cross-chain `WithdrawalRequest.beneficiary` field used to release/refund escrow are never checked against the zero address before funds are transferred to them, mirroring the `transferPosition` bug in the reference report.

### Finding Description
When an order creator calls `placeOrder`, the `PaymentInfo.beneficiary` of `order.output` is fully user-controlled and stored as part of the order commitment; nothing in the codebase validates it is non-zero. When a solver later fills the order, the fill logic decodes this value into a real `address` and sends the solver's payment tokens/ETH directly to it with no zero-address guard: [1](#0-0) 

Similarly, on the escrow-release side, `_withdraw` (called from both `RedeemEscrow` and `RefundEscrow` handling) decodes `body.beneficiary` and transfers/refunds the escrowed tokens to it without ever checking for `address(0)`: [2](#0-1) 

The same unchecked pattern exists in the standalone `IntentGatewayV2.sol` (Tron variant) `withdraw` function, invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse`: [3](#0-2) 

In all three code paths, the value being moved (native ETH via `_sendValue`/`.call{value:}`, or ERC20 via `safeTransfer`/`transfer`) is sent to `address(0)` if that is what the beneficiary field encodes, with no revert and no recovery path — exactly the same missing check as the referenced `BvbProtocol.transferPosition` bug, but here reachable by an ordinary intent creator against an ordinary solver/filler, and by any beneficiary field carried inside a legitimate cross-chain redeem/refund message.

### Impact Explanation
- A malicious (or simply buggy) order creator can craft an order with `output.beneficiary = bytes32(0)`. Any unprivileged solver who fills that order permanently loses the payment tokens/ETH they send, since it is burned to `address(0)` instead of reverting.
- If a beneficiary bytes32 of zero ever reaches the escrow-release path (`_withdraw`/`withdraw`), the escrowed input tokens or refunded tokens are permanently burned rather than delivered, causing irrecoverable protocol/user fund loss.
- This satisfies "permanent freezing/loss of funds" for an unprivileged intent solver — a directly in-scope actor per the validation rules.

### Likelihood Explanation
High-likelihood/no-privilege-required: placing an order with a zero beneficiary requires no special permission, and solvers select/fill orders based on economic incentives without necessarily validating every field before submitting a fill transaction. The only defense today is off-chain solver diligence, not an on-chain invariant.

### Recommendation
Add an explicit non-zero check on `order.output.beneficiary` in `placeOrder` (or `_execute`/fill logic before dispatch) and on `body.beneficiary` in `_withdraw` / `withdraw` in `IntentsBase.sol` and `IntentGatewayV2.sol`, reverting (e.g., `InvalidBeneficiary`) if the decoded address is `address(0)`.

### Proof of Concept
1. User calls `placeOrder` with `order.output.beneficiary = bytes32(0)` for an output amount of, say, 1000 DAI, with source/destination on the same chain (same-chain fill path).
2. A solver calls the fill entrypoint; `ExtrinsicIntents.sol`/`IntrinsicIntents.sol` decode `beneficiary = address(0)` and execute `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` or `_sendValue(beneficiary, beneficiaryTotal)` (see `evm/src/apps/intentsv2/ExtrinsicIntents.sol:186-196`), sending the solver's 1000 DAI/ETH to `address(0)` — no revert occurs, funds are burned.
3. Equivalently, an escrow release message (`RedeemEscrow`/`RefundEscrow`) with `WithdrawalRequest.beneficiary = bytes32(0)` reaching `_withdraw` (`IntentsBase.sol:451-469`) burns the escrowed tokens instead of returning them to the solver/user. [4](#0-3)
