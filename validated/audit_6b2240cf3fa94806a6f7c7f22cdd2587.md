This confirms the vulnerability path. The gem's docs at `docs/usage/webhooks.md` lines 12-14 and 125 explicitly tell app developers that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook" — i.e., it is documented as a trusted, verified identity field that apps are expected to use for tenant scoping (as shown in the example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). But the HMAC signature computed in `Request#to_signable_string` only covers the raw body, not the `shop` header, so the shop identity is never actually authenticated.

### Title
Webhook shop-domain identity is trusted but not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` only proves the *body* bytes were signed by Shopify with `Context.api_secret_key`. The `shop` (and `topic`, `webhook_id`, `api_version`) values come from separate, unauthenticated HTTP headers that are never included in the HMAC-signed content, yet `Registry.process` forwards `request.shop` into `WebhookMetadata` and hands it to the app's handler as a trusted tenant identifier.

### Finding Description
`Registry.process` only gate-checks `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

The HMAC validator computes/verifies the signature strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

But `Request#to_signable_string` is defined to return `@raw_body` only — none of the shop/topic/webhook-id/api-version headers are part of the signable content: [3](#0-2) 

`request.shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cross-check against the HMAC: [4](#0-3) 

That unauthenticated value is then packaged into `WebhookMetadata.shop` and delivered to the app's handler as if it were an authenticated fact: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs app authors to treat `data.shop` as the verified tenant identifier once `process` has been called ("This will verify the request did indeed come from Shopify" / "`shop`, `String` - The shop domain of the webhook"), and shows it being used directly for tenant-scoped dispatch (`shop_domain: data.shop`): [7](#0-6) [8](#0-7) 

The binding that should hold is: `hmac_signed_bytes == bytes_containing(shop, topic, webhook_id, api_version, body)`. In this implementation it instead holds only `hmac_signed_bytes == body`, so the equality the app relies on for tenant identity (`verified_shop == request.shop`) does not actually hold — `request.shop` is attacker-controlled header content, not something the signature attests to.

### Impact Explanation
A merchant/attacker who has legitimately installed the app on their own shop (an unprivileged relative to any other tenant of the same app) receives genuinely-signed webhooks for their own shop. Since the signature only certifies the body, they can capture one such signed body and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop). `HmacValidator.validate` will still pass (the body/HMAC pair is valid), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain. Any app that uses `data.shop` to select which tenant's stored data/session to update — exactly as the gem's own documentation example does — can be made to write or act on another merchant's tenant context, which is a cross-tenant access impact.

### Likelihood Explanation
Reaching this requires no secrets, tokens, or privileged access beyond installing the app on any shop (something any unprivileged internet user offering a Shopify store can do) to obtain one legitimately-signed webhook body/HMAC pair, then replaying it with a forged shop header to the app's public webhook endpoint. This is a straightforward HTTP replay with a modified header; the gem performs no additional cross-check between the HMAC-covered content and the shop header before trusting it.

### Recommendation
Bind the shop (and ideally topic/webhook-id/api-version) into the HMAC-signed content, or otherwise cryptographically tie the `shop` header to the verified payload, before exposing it via `WebhookMetadata`. At minimum, `Utils::HmacValidator.validate` should be changed so `Request#to_signable_string` incorporates the shop-domain header (and other trusted headers) rather than the body alone, so that verifying the HMAC also verifies which shop the webhook claims to be from.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid HMAC of body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical body and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate(request)` succeeds because it only checks the HMAC against `raw_body`, per [9](#0-8)  and [2](#0-1) .
4. `Registry.process` calls the app handler with `WebhookMetadata.new(... shop: request.shop ...)` where `shop` is `"victim-shop.myshopify.com"`, per [5](#0-4) , causing any tenant-scoped logic in the handler to run against the wrong shop's context.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
