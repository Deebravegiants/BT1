### Title
Webhook shop/topic identity not bound to HMAC signature, enabling cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` treats the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers as trusted identity fields for a webhook, while `Utils::HmacValidator` only verifies the HMAC over the raw request body. The `shop` value that the host application uses to attribute the webhook to a tenant is never covered by the signature check, so it can be swapped for an arbitrary value while still passing validation, as long as the attacker can produce one valid `(raw_body, hmac)` pair signed with the app's real secret (e.g., from their own legitimately installed test shop).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other identity fields — `shop`, `topic`, `webhook_id`, `api_version` — are pulled straight from HTTP headers without being part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` then dispatches to the handler using `request.shop` and `request.topic` as trusted tenant/topic identifiers, having only checked the HMAC: [4](#0-3) 

The binding that should hold is:
`shop header value == shop that produced/signed this exact HMAC`

But the actual check only enforces:
`HMAC(raw_body, api_secret_key) == received_hmac`

Since `shop` (and `topic`/`webhook_id`) are outside the signed content, any request carrying a *body* that was legitimately signed by the app's secret — for *any* shop, at *any* time — can be replayed to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header, and `HmacValidator.validate` will still return `true`. There is no timestamp/webhook-id freshness check anywhere in `Request` or `Registry`, so replay is unbounded in time and reusable indefinitely.

An unprivileged internet user can obtain a valid `(raw_body, hmac)` pair without any privileged credentials simply by installing the app on a shop they control (a normal, unprivileged action) and capturing the genuine webhook Shopify sends to the app's public callback URL. They can then replay that exact body+signature to the same public endpoint while substituting the `shop-domain` header for a victim shop's domain.

### Impact Explanation
Because `WebhookMetadata.shop` (built directly from the unverified `shop` header) is what host applications use to determine which tenant's data store to write to, an attacker can inject data that is falsely attributed to a shop they do not own into the app's tenant-scoped storage/business logic — a cross-tenant access/data-integrity breach. Depending on the webhook topic (e.g., `app/uninstalled`, `customers/data_request`, `orders/create`), this can trigger tenant-scoped side effects (data deletion, incorrect order/customer records, GDPR-flow disruption) attributed to a shop the attacker never controls.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any shop (an unprivileged, normal merchant action, e.g. a free development store), (2) network access to the app's public webhook endpoint (which is always internet-reachable by design), and (3) capturing one legitimate webhook body/HMAC pair sent to that endpoint. No access token, `api_secret_key`, or privileged account is required — only observation of one's own legitimately received webhook traffic. This is straightforward to reproduce given the current code base.

### Recommendation
Bind the tenant identity to the signed payload rather than trusting unauthenticated headers:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them), similar to how `AuthQuery#to_signable_string` includes `shop`, `host`, `code`, `state`, and `timestamp` in its signable content: [5](#0-4) 
- Alternatively/additionally, enforce webhook_id-based replay protection (reject already-seen `webhook_id`s) and reject requests whose timestamp is stale, since no freshness check currently exists in `Webhooks::Request`/`Webhooks::Registry`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Capture a genuine incoming webhook POST to the app's webhook endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-webhook-id: <id>`
   - Body: `<raw_body>` (arbitrary JSON payload Shopify sent for the attacker's own resource)
3. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but change the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still returns `true` because it only checks `raw_body` against the HMAC — it never checks `shop`.
5. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act as if this data legitimately originated from `victim-shop.myshopify.com`.
