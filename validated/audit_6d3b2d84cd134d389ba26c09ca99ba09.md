### Title
Webhook shop-domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body [1](#0-0) . The shop identity attached to the webhook (`shop-domain` header) is read directly from an unauthenticated HTTP header and handed to the app's handler, without ever being bound to the HMAC-verified content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and the app's single, shared `api_secret_key` — the same secret is used for *every* shop that installs the app, not a per-shop secret: [4](#0-3) 

This breaks the intended identity binding:
`hmac_valid_for(body) == true` should imply `shop_header == originating_shop`, but the code only proves `hmac_valid_for(body) == true`, with `shop_header` completely unconstrained.

Because the HMAC key (`api_secret_key`) is shared across all shops that install a given app, an attacker who controls any shop that has the app installed (e.g. their own free/dev store) can capture a genuine webhook delivery — a valid `(raw_body, hmac)` pair signed with the app's secret — and then replay that exact body and signature to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped to point at a victim shop that also uses the same app. `HmacValidator.validate` will still pass because the signed content (raw body) is unchanged, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled body content.

### Impact Explanation
Any host application that uses `data.shop` (as `docs/usage/webhooks.md` explicitly instructs: `data.shop` is "The shop domain of the webhook") to key data writes, look up the shop's session/access token, or make authorization decisions will process attacker-supplied payloads under the identity of a shop the attacker does not own. This is a cross-tenant integrity/authentication issue: an attacker can inject or associate fabricated webhook events (orders, product updates, app-uninstall, GDPR topics, etc.) with an arbitrary victim tenant that shares the same app, without needing that victim's credentials, access token, or client secret — only requiring their own legitimate install of the app to obtain one valid `(body, hmac)` pair for a given topic. This matches the "Cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for apps that trust `data.shop` from `WebhookMetadata` without independently cross-checking it (e.g., against a list of shops actually registered for that specific webhook topic, or the shop stored in the session for the given webhook `webhook_id`). No special access is required beyond installing the same third-party app on an attacker-controlled shop, which is the normal, unprivileged flow for any Shopify merchant/developer. The library ships no built-in check that ties the header-derived shop to the signed body, and the docs actively encourage developers to trust `data.shop` directly.

### Recommendation
- Do not treat the `shop-domain` header as authenticated. Either:
  - Include the shop domain (and ideally topic/webhook id) in the signable string used for `HmacValidator`, so the signature binds shop identity to body content, or
  - Require callers to independently verify that `request.shop` corresponds to a shop that is registered for the webhook (e.g., cross-check against known/installed shops before dispatching to the handler), or
  - Document explicitly and prominently that `shop`, `topic`, and `webhook_id` are unauthenticated header values that must not be used for authorization decisions without additional verification.
- Consider mitigating shared-secret replay by validating uniqueness of `webhook_id` per shop to prevent cross-shop replay of the same delivery.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. The app sends attacker a legitimate webhook, e.g. `orders/create`, with headers:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of raw_body computed with the app's shared client_secret>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: <id>
   ```
   and raw body `{"id": 1, "note": "malicious payload"}`.
3. Attacker replays the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) raw body and succeeds [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id": 1, "note": "malicious payload"}, ...)` [6](#0-5) , and the host application processes attacker-controlled data under the victim's tenant identity.
