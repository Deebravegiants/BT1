### Title
Webhook shop identity is trusted from an unauthenticated header while the HMAC signature only covers the request body - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC signature that is computed **only** over the raw JSON body, yet the shop identity used to dispatch and act on the webhook is read from the `shopify-shop-domain` header, which is never included in the signed data. This breaks the intended binding `authenticated_bytes == acted_upon_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies this signable string against the received `hmac` header: [2](#0-1) 

`Registry.process` treats this as full request authentication, then immediately reads `request.shop` — sourced from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header — and passes it straight into the webhook handler: [3](#0-2) [4](#0-3) 

The equality the gem is supposed to guarantee before handing data to the app is:
`hmac_verified_bytes == (body, shop)`

What it actually guarantees is:
`hmac_verified_bytes == body` while `shop` is taken from unauthenticated header bytes and forwarded to the handler as if it were verified.

### Impact Explanation
Because the `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that has installed the app (it is not shop-specific), any unprivileged internet user who installs the target app on their own store legitimately receives genuine `(body, hmac)` pairs signed by Shopify with that shared secret. Such an attacker can:

1. Capture a valid `(raw_body, hmac)` pair from a webhook delivered to their own shop.
2. Replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

Depending on the handler implementation (which the gem's documented API explicitly instructs apps to key off `data.shop`), this enables cross-tenant data confusion/corruption — e.g., an attacker-controlled `orders/create` or `app/uninstalled` payload can be attributed to a victim shop, causing the app to write attacker-supplied data into, or trigger de-provisioning actions against, another merchant's account.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must be able to install the app on some shop they control (readily available to any internet user for public/free apps) and must know or predict a webhook topic whose body content they want reflected under the victim's identity. No access token, secret, or privileged account is required — only participation as a normal merchant of the app, which satisfies the "unprivileged internet user" bar.

### Recommendation
Include the shop domain (and other header-derived identity fields such as `topic`/`webhook-id`, if they are acted upon) in the HMAC-signed material, or independently bind `request.shop` to a value derived from a source Shopify actually signs (e.g., cross-check against a shop already known/authorized for the app installation) before dispatching to handlers. At minimum, document and enforce that `WebhookMetadata#shop` must not be trusted as authenticated unless it is verified against an independent, signed source.

### Proof of Concept
1. App installs webhook handler that uses `data.shop` to select which shop record to update (per documented usage in `docs/usage/webhooks.md`).
2. Attacker installs the app on `attacker-shop.myshopify.com`, and Shopify delivers a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)`.
3. Attacker sends `POST /webhooks` to the app with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), and header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H`.
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to act on attacker-controlled data under the victim shop's identity.
