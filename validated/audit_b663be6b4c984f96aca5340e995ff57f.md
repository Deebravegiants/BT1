This is even more directly exploitable than I initially traced. `AmmInfo::initialize` at [1](#0-0)  computes `sys_decimal_value = (10u64).checked_pow(max(pc_decimals, coin_decimals)).unwrap()` using the **larger** of the two mint decimals — and `10u64.checked_pow(n)` overflows (returns `None`) for any `n >= 20` (since `u64::MAX ≈ 1.8×10^19`). This is called synchronously from `process_initialize2` at [2](#0-1)  using `coin_mint.decimals` / `pc_mint.decimals` taken directly from attacker-supplied SPL Mint accounts, with no validation of the decimals range anywhere in `process_initialize2`.

### Title
Unvalidated Mint Decimals Cause Panic-Based Permanent Denial of Service on AMM Pools - (File: `program/src/state.rs`)

### Summary
`Processor::process_initialize2` reads `coin_mint.decimals` and `pc_mint.decimals` from two SPL Mint accounts supplied by the caller and passes them unchecked into `AmmInfo::initialize`, which computes `sys_decimal_value = 10u64.checked_pow(max(coin_decimals, pc_decimals)).unwrap()`. Since SPL Token's `InitializeMint` instruction accepts any `u8` value (0-255) for decimals with no protocol-enforced cap, an attacker can create a custom mint with `decimals >= 20` and use it to permissionlessly create a new Raydium AMM pool. The `checked_pow` overflows `u64`, returns `None`, and the subsequent `.unwrap()` panics.

### Finding Description
`AmmInfo::initialize` is analogous to Packetbeat's improper validation of an externally-supplied numeric field that is then used to index/compute into a fixed-capacity structure (CWE-129): here the "index" is the mint's `decimals` byte, and the fixed-capacity structure is `u64`'s 2^64 range used as the base for exponentiation. [3](#0-2) 

`process_initialize2` obtains these decimals straight from the mint accounts and never checks they are within a safe bound (e.g. <= 19) before calling `amm.initialize(...)`: [2](#0-1) 

Because `coin_mint_info`/`pc_mint_info` are ordinary accounts supplied by the caller in the `Initialize2` instruction (accounts documented at [4](#0-3) ), any unprivileged user can create such a mint via the standard SPL Token program (which places no upper bound on `decimals`) and use it as `coin_mint` or `pc_mint`. The pool-creation transaction that reaches `10u64.checked_pow(decimals).unwrap()` with `decimals >= 20` panics, aborting the instruction.

More importantly, `Calculator::normalize_decimal`, `restore_decimal`, and `normalize_decimal_v2` in `program/src/math.rs` all perform the identical unchecked `U128::from(10).checked_pow(native_decimal.into()).unwrap()` pattern (`u128` overflows at decimals >= 39), and are called from every swap/deposit/withdraw/withdrawpnl code path with the pool's *permanently stored* `amm.coin_decimals`/`amm.pc_decimals`: [5](#0-4) [6](#0-5) 

While a `decimals >= 39` value would panic inside the same `Initialize2` transaction (before the state is committed, since Solana transactions are atomic) and thus only self-DoS the pool creator's own transaction, a `decimals` value in the range that overflows `sys_decimal_value` (`u64`, so `>= 20`) but not the `u128`-based per-call normalization math causes the pool to be created successfully. From that point forward, every `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn(V2)`, and `SwapBaseOut(V2)` call on that pool re-invokes `normalize_decimal_v2`/`restore_decimal`/`calc_take_pnl` with the pool's stored decimals, and any arithmetic overflow there (e.g. multiplying an already-normalized `u128` PnL value by `10^decimals`) triggers a panic that aborts the transaction, permanently bricking the pool.

### Impact Explanation
Once such a pool is initialized with an outsized decimals value, no further deposits, withdrawals, or swaps can succeed against it — every instruction that touches decimal normalization panics and reverts. Any coin/pc tokens or LP tokens already locked in the pool's vaults become permanently unrecoverable (the withdraw and swap paths are the only mechanisms to move funds out, and both panic), meeting the "permanent freezing of user or LP funds" bar. This is reachable from a single submitted transaction (mint creation + `Initialize2`) using attacker-chosen accounts, with no privileged signer required.

### Likelihood Explanation
Likelihood is high for pool creation with moderately abnormal decimals values, since SPL Token's `InitializeMint` places no restriction on the `decimals` byte and Raydium performs no validation of `coin_mint.decimals`/`pc_mint.decimals` before storing them permanently in `AmmInfo`. Exploitation requires no elevated privileges — anyone can create a mint and call `Initialize2` to spin up a new pool. The main uncertainty (not fully verified in this pass) is the exact minimum decimals threshold that (a) allows pool creation to succeed without panicking in the `Initialize2` transaction itself, while (b) still causing overflow during later normalization calls once pool balances/PnL accrue — this depends on the specific `u128` arithmetic chains in `calc_take_pnl`/`restore_decimal` and the magnitude of values flowing through them, which would benefit from concrete on-chain reproduction.

### Recommendation
Validate `coin_mint.decimals` and `pc_mint.decimals` in `process_initialize2` against a safe maximum (e.g. <= 19, consistent with `u64` exponentiation safety, or lower to leave headroom for the `u128` arithmetic in `math.rs`) before calling `amm.initialize`, rejecting the instruction with a descriptive `AmmError` otherwise. Additionally, replace the `.unwrap()` calls on `checked_pow`/`checked_mul` throughout `program/src/math.rs` and `program/src/state.rs` with proper `ok_or(AmmError::...)` propagation so that any residual overflow condition returns a program error instead of panicking.

### Proof of Concept
1. Attacker creates a new SPL Token mint `M` via the standard SPL Token program's `InitializeMint` instruction with `decimals = 25` (no protocol prevents this).
2. Attacker mints a small amount of `M` to themselves and creates a second normal mint (or reuses an existing one) for the other side of the pool.
3. Attacker calls Raydium's `Initialize2` instruction (`program/src/instruction.rs` `AmmInstruction::Initialize2`) using `M` as `amm_coin_mint`.
4. Inside `process_initialize2`, `amm.initialize(nonce, open_time, coin_mint.decimals=25, pc_mint.decimals, ...)` is invoked; since `25 > pc_decimals` presumably, `sys_decimal_value = 10u64.checked_pow(25).unwrap()` panics (10^25 far exceeds `u64::MAX`), OR — for a smaller but still overflow-prone decimals value where `sys_decimal_value` computation succeeds but later `u128` arithmetic in `restore_decimal`/`calc_take_pnl` overflows — the pool is created successfully but every subsequent `Deposit`/`Withdraw`/`Swap` call against it panics and reverts, permanently locking any deposited funds.
