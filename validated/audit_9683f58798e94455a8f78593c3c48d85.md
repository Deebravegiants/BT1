Audit Report

## Title
Unbounded loop over all registered workflow triggers on every Gateway-forwarded WebAPI trigger message causes DoS - (File: `core/capabilities/webapi/trigger/trigger.go`)

## Summary
`processTrigger` in `core/capabilities/webapi/trigger/trigger.go` iterates over the entire in-memory `registeredWorkflows` map (and nested, every topic in the caller-supplied payload) on every inbound `MethodWebAPITrigger` Gateway message, with `RegisterTrigger` enforcing no cap on the number of entries. This is confirmed to be reachable from an unprivileged client: `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` explicitly notes `// TODO: apply allowlist and rate-limiting here` and forwards any signed `web_api_trigger` message to all DON nodes without checking sender authorization against any workflow.

## Finding Description
The registration path has no bound: [1](#0-0) . `processTrigger` snapshots and fully scans all registered triggers for every message, doing per-topic map lookups, rate-limit checks and channel writes before returning: [2](#0-1) . This is dispatched from `HandleGatewayMessage` for every `MethodWebAPITrigger` message: [3](#0-2) .

Critically, the gateway-side ingress `handler.HandleLegacyUserMessage` accepts any signed message with method `web_api_trigger`, checks only payload structure and staleness, and explicitly documents the missing allowlist/rate-limit check before broadcasting to all DON members: [4](#0-3) . The sender/topic authorization checks (`allowedSenders`, `allowedTopics`) happen only inside the per-workflow loop in `processTrigger`, i.e., after the full-list traversal cost has already been paid, confirming that cost is incurred by any caller regardless of authorization for any registered workflow.

However, the per-entry work inside the loop is a simple in-memory map lookup (`trigger.allowedTopics[topic]`), not an expensive network/external call as in the NFTX `distribute()` analogy (external token transfers per receiver). The cost model is O(registered-workflows × topics) map probes — cheap individually, but genuinely unbounded and reachable pre-authorization by any actor who can produce a validly-signed Gateway message (the signing key can be any self-generated ECDSA key; `body.Sender` is derived from the signer and does not require any special allowlisted role, as shown in `handler_test.go`'s `triggerRequest` helper which signs with an arbitrary test key).

## Impact Explanation
This is a legitimate, if modest, computational-amplification concern: as the registered-workflow count for the WebAPI trigger capability grows, each inbound `web_api_trigger` message costs proportionally more CPU to process, and there's no cap in `RegisterTrigger`, no indexing by topic, and no allowlist/rate-limit at the Gateway ingress layer (explicitly called out as a TODO). This does map to a real availability concern for the Gateway/node message-handling path, consistent with a DoS-class finding, though the per-entry cost is low (hash-map lookups) rather than the heavier per-receiver operations in the referenced NFTX bug, so the severity is more moderate than the report implies.

## Likelihood Explanation
Likelihood is real but bounded by practical constraints: an attacker needs only an ECDSA keypair to sign a `web_api_trigger` message (no DON membership or workflow registration required) and can repeatedly send messages with non-matching topics to force full traversals, as the `TODO` comment in `handler.go` confirms no allowlist/rate-limiting currently gates this path before broadcast to all DON nodes. The magnitude of the DoS scales with the number of registered workflows on a given node, which in most deployments is not attacker-controlled and grows slowly, limiting the practical severity compared to the NFTX scenario where the vulnerable list is unboundedly attacker-influenced.

## Recommendation
- Cap the number of concurrently registered triggers per node/DON in `RegisterTrigger`.
- Replace the full scan in `processTrigger` with a topic-indexed map (`map[topic][]*webapiTrigger`) built incrementally in `RegisterTrigger`/`UnregisterTrigger` so lookup cost is proportional to matches, not total registrations.
- Implement the `TODO: apply allowlist and rate-limiting here` in `core/services/gateway/handlers/capabilities/handler.go` `HandleLegacyUserMessage` so unauthenticated/unauthorized senders cannot force full-list traversals repeatedly.
- Bound the `topics` length per request in `processTrigger`.

## Proof of Concept
1. Register N WebAPI trigger workflows via `RegisterTrigger` (no cap enforced): `core/capabilities/webapi/trigger/trigger.go` L212-232.
2. Sign a `web_api_trigger` JSON-RPC message with any arbitrary ECDSA keypair (per `handler_test.go`'s `triggerRequest` helper pattern) containing a non-matching `Topics` list, and submit it to the Gateway.
3. Observe that `HandleLegacyUserMessage` forwards it to all DON nodes without allowlist checks (per the TODO comment), and each node's `processTrigger` performs a full O(N×topics) scan before returning `"no Matching Workflow Topics"`.
4. Repeat at volume to measure CPU/latency scaling with N; compare processing time for small vs. large registered-workflow counts to quantify the amplification.

```go
func (h *triggerConnectorHandler) RegisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) (<-chan capabilities.TriggerResponse, error) {
	cfg := req.Config
	if cfg == nil {
		return nil, errors.New("config is required to register a web api trigger")
	}

	reqConfig, err := h.ValidateConfig(cfg)
	if err != nil {
		return nil, err
	}

	if len(reqConfig.AllowedSenders) == 0 {
		return nil, errors.New("allowedSenders must have at least 1 entry")
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	_, errBool := h.registeredWorkflows[req.TriggerID]
	if errBool {
		return nil, fmt.Errorf("triggerId %s already registered", req.TriggerID)
	}
```
