### Title
Low-utilization rounding of `calc-liquidity-rate` to zero permanently pins `lindex` while `index` keeps growing, freezing supplier yield - ([File: local-testing/contracts/vault/vault-stx.clar])

### Summary
`next-index` and `next-liquidity-index` derive their compounding multipliers from two structurally different rate values computed by `calc-multiplier-delta`: the borrower side uses the raw `interest-rate` (round-up), while the supplier side uses `calc-liquidity-rate`, which pre-scales that same rate by `utilization` and `(1-reserve-factor)` in integer BPS *before* any time/precision scaling is applied. At low utilization this pre-scaling floors to exactly `0`, so the supplier-side multiplier is deterministically `INDEX-PRECISION` (no change) on every single `accrue` call, forever, while the borrower-side multiplier is always `> INDEX-PRECISION` because it is computed from the un-scaled rate with much larger precision headroom (`* INDEX-PRECISION` before dividing). The result is `index` growing every block while `lindex` never advances, even though `fee-reserve < BPS` (i.e., LPs are entitled to a nonzero share of interest).

### Finding Description
Identity claimed to hold: whenever `index_after - index_before > u0` and `fee-reserve < BPS`, then `lindex_after - lindex_before` should also be `> u0` (suppliers should accrue *some* nonzero share of borrower-paid interest, proportional to `(BPS - fee-reserve)`). The code breaks this identity under low utilization.

Root cause, in `local-testing/contracts/vault/vault-stx.clar`:

```
(define-private (calc-multiplier-delta (rate uint) (time-delta uint) (round-up bool))
  (+ INDEX-PRECISION
    (if round-up
      (mul-div-up rate (* time-delta INDEX-PRECISION) SECONDS-PER-YEAR-BPS)
      (mul-div-down rate (* time-delta INDEX-PRECISION) SECONDS-PER-YEAR-BPS))))
``` [1](#0-0) 

```
(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
  (let ((util-applied (mul-bps-down var-borrow-rate util-pct))
        (one-minus-rf (- BPS reserve-factor-bps)))
    (mul-bps-down util-applied one-minus-rf)))
``` [2](#0-1) 

```
(define-private (next-index)
  ...
  (multiplier (calc-multiplier-delta rate time-delta true))
  (calc-index-next idx multiplier))

(define-private (next-liquidity-index)
  ...
  (liquidity-rate (calc-liquidity-rate rate (utilization) (var-get fee-reserve)))
  (multiplier (calc-multiplier-delta liquidity-rate time-delta false))
  (calc-index-next lidx multiplier))
``` [3](#0-2) 

`calc-liquidity-rate` performs `floor(rate * util-pct / BPS)` and then `floor(util-applied * one-minus-rf / BPS)`, both in integer BPS units (`BPS = 10000`). When utilization is very low (e.g., a large supply pool with a small active borrow, `util-pct` on the order of a few bps or less), `rate * util-pct / BPS` truncates to exactly `0` before any time-scaling or `INDEX-PRECISION` multiplication ever occurs. Once `liquidity-rate = 0`, `calc-multiplier-delta(0, time-delta, false)` returns exactly `INDEX-PRECISION` for *any* `time-delta`, so `calc-index-next(lidx, INDEX-PRECISION) = lidx` — `lindex` is bit-for-bit unchanged, no matter how many seconds elapse or how many times `accrue` is called.

By contrast, `next-index` uses the raw, un-scaled `rate` and multiplies by `INDEX-PRECISION` (typically `1e18`) *before* dividing by `SECONDS-PER-YEAR-BPS`, giving it far more precision headroom; combined with `mul-div-up` rounding, the borrower-side multiplier is essentially always `> INDEX-PRECISION` for any nonzero `rate` and `time-delta`, so `index` (and therefore borrower `total-debt`, via `calc-cumulative-debt`) keeps growing every accrual, unboundedly, in perpetuity.

Reachable path in `accrue` (shown for `vault-usdc.clar`, structurally identical across all vaults):
```
(let ((next (next-index)) (nliq (next-liquidity-index)) ...)
  (if (not (is-eq idx next)) (var-set index next) false)
  (if (not (is-eq lidx nliq)) (var-set lindex nliq) false)
  ...)
``` [4](#0-3) 

`reserve-inc` (the DAO treasury's cut) is computed purely from `index`'s growth (`debt-delta`) and `fee-reserve`, independent of `lindex`:
```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
``` [5](#0-4) 

So even the treasury only captures the `fee-reserve` fraction of `debt-delta`. The remaining `(BPS - fee-reserve)` fraction of the same `debt-delta` — the part that is supposed to compound into `lindex` for suppliers — is never captured anywhere once `liquidity-rate` rounds to `0`. No `min-out`, pause flag, or auth check in `accrue` guards against this: the `(get accrue states)` pause path only freezes *both* indexes together, and there is no assertion that `lindex` growth tracks `index` growth.

Any unprivileged principal can reach this state without needing special call ordering: simply supply a large amount of liquidity (permissionless deposit) and issue/keep a small borrow open (permissionless borrow) to hold utilization in the sub-threshold range, then let normal block cadence (or repeatedly call any public function that triggers `accrue`, e.g. `system-borrow`/`system-repay`) drive repeated `accrue` calls with `time-delta > 0`.

### Impact Explanation
Per accrual call in the affected regime: `index` delta `> u0` (borrower debt grows), `lindex` delta `== u0` (supplier index frozen) — a full, permanent divergence for every such call, not a bounded one-time rounding error, because `calc-liquidity-rate` recomputes from scratch each time and produces exactly `0` again as long as utilization stays low. This is repeatable indefinitely (every block/every `accrue` call) and the loss compounds with `total-debt`. The party bearing the loss is every liquidity provider holding `zft` in the pool — their claim on `total-assets` never grows to reflect the interest their capital is backing, i.e., permanent freezing/loss of unclaimed yield (matches the "High" severity category: permanent freezing of unclaimed yield). It does not constitute direct theft of principal or insolvency of principal balances, since scaled principal itself is untouched — only the yield accrual mechanism is starved.

### Likelihood Explanation
Preconditions are cheap and realistic: an attacker (or even an organic market condition) simply needs a supply pool large relative to a small active borrow, which is trivially achievable by depositing capital (no privileged role required) and opening/maintaining a modest borrow. No flashloan, oracle manipulation, or DAO/privileged access is required. The bug is deterministic given the arithmetic (integer BPS double-flooring before scaling by `INDEX-PRECISION`), so it is 100% reproducible under the stated utilization regime and persists across arbitrarily many blocks/calls until utilization rises enough to make `floor(rate*util/BPS) >= 1`.

### Recommendation
Compute `calc-liquidity-rate` with the same high-precision ordering used for the borrower rate: fold the `util-pct` and `(BPS - reserve-factor-bps)` scaling into the `INDEX-PRECISION`/`time-delta` multiplication in `calc-multiplier-delta` (i.e., multiply by `rate * util-pct * one-minus-rf * INDEX-PRECISION` once and divide once by `BPS * BPS * SECONDS-PER-YEAR-BPS`) instead of truncating to integer BPS twice before any time-scaling. This preserves sub-bps precision so `lindex`'s multiplier is `> INDEX-PRECISION` whenever `index`'s is, for any positive `rate`, `util-pct`, and `time-delta`.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy `vault-stx` (or any vault), set `fee-reserve` to e.g. `1000` (10%, `< BPS`) and interest-rate curve with a nonzero base rate at low utilization.
2. Have LP A deposit a large amount (e.g. `1_000_000_000000` micro-units) to establish a large supply base.
3. Have borrower B borrow a small amount so that `utilization()` (in BPS) is `< 1` bps relative to `rate` such that `mul-bps-down(rate, util-pct)` floors to `0` (compute concretely from the deployed IR curve/util value to pick amounts).
4. Loop N times (e.g. N=500): advance the simnet chain by 1 second, call any public function that triggers `accrue` (e.g. `system-repay 0` or a dedicated accrual trampoline), and log `(var-get index)` and `(var-get lindex)` before/after.
5. Assert: `index_after - index_before > u0` on every iteration, and `lindex_after - lindex_before == u0` on every iteration, for all N iterations.
6. Assert cumulative `index` growth over N iterations `> u0` while cumulative `lindex` growth `== u0`.
7. Assert no `treasury-lp`/`zft` was minted to `.dao-treasury` beyond the `fee-reserve`-scaled `reserve-inc` amount (i.e., verify `(BPS - fee-reserve)` fraction of `debt-delta` is unaccounted for in both `lindex` and `treasury-lp`).
