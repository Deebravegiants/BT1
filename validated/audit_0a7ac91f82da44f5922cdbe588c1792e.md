## Title
Escrow release relies on unconditional push-transfers with no pull-fallback, allowing a blacklisted/reverting beneficiary to permanently freeze escrowed order funds - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The Intent Gateway v2's escrow release path (`_withdraw`) unconditionally pushes tokens (`IERC20.safeTransfer`/native `call`) to the `beneficiary` address baked into the order/commitment at fill or cancel time. There is no pull-based claim mechanism and no way to redirect the payout to a different address if the transfer keeps reverting. This is the exact bug class from the external report: push-only token transfers without a pull-pattern fallback that permanently strand user funds whenever the destination cannot receive them.

### Finding Description
`IntentsBase._withdraw()` iterates the escrowed tokens for a commitment and does an unconditional push transfer to `beneficiary`: [1](#0-0) 

For native assets, `_sendValue` reverts if the low-level call fails: [2](#0-1) 

This `_withdraw` is invoked from three places, none of which provide an alternative pull path if the push fails:

1. Same-chain refund/cancel (`_cancelSameChain`) — the beneficiary is `order.user`, hardcoded at order-placement time, and `_withdraw` runs synchronously inside the user's own `cancelOrder()` transaction: [3](#0-2) 

2. Cross-chain settlement via ISMP `onAccept` (`RedeemEscrow`/`RefundEscrow`), where the beneficiary is either the solver (`msg.sender` at fill-time on the destination chain) or `order.user`: [4](#0-3) 

3. Cross-chain cancellation confirmed via GET response (`onGetResponse`), which also calls `_withdraw` with `order.user` as beneficiary.

If the token used is a compliance-gated stablecoin (e.g. USDC/USDT) and the `beneficiary` address becomes blacklisted by the issuer *after* the order was placed/filled — or if the beneficiary is a contract without a working `receive()`/`fallback()` for native assets — every call to `safeTransfer`/`_sendValue` reverts.

- In the same-chain path, this makes `cancelOrder()` permanently unexecutable: the user can never reclaim their escrowed `_orders[commitment][token]` balance, since there is no other function that reads that mapping and no alternative recipient can be substituted.
- In the cross-chain path, the revert propagates up through `onAccept`, and `EvmHost.dispatchIncoming` treats it as a retryable delivery failure by deleting the request receipt: [5](#0-4) 
Because the root cause (a persistently blacklisted/reverting beneficiary) does not change between retries, the message can never be successfully delivered. The escrowed funds sit in `_orders[commitment][token]` indefinitely with no admin sweep, no alternate-address claim, and no expiry — `SweepDust` only handles residual "dust", not full order escrow.

This mirrors the reported Moloch issue precisely: a push-pattern token transfer embedded in the "release/refund" code path, with no fallback (pull) mechanism, converts a token-transfer failure (whether from compliance blacklisting or a non-accepting contract) into a permanent loss/freeze of the escrowed principal rather than a retryable/recoverable state.

### Impact Explanation
This is a fund-freezing bug reachable by any ordinary user of the Intent Gateway: place an order, escrow tokens, and if the beneficiary address is ever blacklisted by the token issuer (a routine, expected occurrence for USDC/USDT compliance) or is a smart-contract wallet that cannot accept native value, the full escrowed principal for that order becomes permanently unrecoverable. There is no admin or governance override to force-redirect the beneficiary or sweep the trapped order-level escrow (only the unrelated dust-sweep flow exists). This qualifies as concrete permanent freezing of user funds.

### Likelihood Explanation
Compliance blacklisting of USDC/USDT addresses is an externally-triggered, non-attacker-controlled but realistic event; it does not require any malicious action from Hyperbridge operators, governance, or peers — it is a routine occurrence for centralized stablecoins used as intent-gateway input/output/fee tokens. Similarly, using a smart-contract beneficiary without a payable fallback for a native-asset order is a normal integration mistake. Given the Intent Gateway explicitly supports USDC-class tokens (per the fee/escrow design and tests using `usdc`), the likelihood of this occurring in production is Medium-to-High.

### Recommendation
Replace the unconditional push transfer in `_withdraw`/`_sendValue`/`_cancelSameChain` with a pull-based claim pattern: on transfer failure, credit the beneficiary's balance in an internal ledger (per address, per token) rather than reverting the whole settlement, and expose a separate `claim(token)` function the beneficiary (or a redirect-capable owner) can call once the transfer is possible again, or that allows specifying an alternate receiving address. This decouples ISMP message delivery / order finalization from the beneficiary's ability to physically receive the specific token at that specific address, consistent with the "pull pattern" recommendation in the original report.

### Proof of Concept
1. Attacker/ordinary user places a cross-chain order on the source chain via `placeOrder`, escrowing `USDC` with `order.user = U`.
2. Address `U` is later added to the USDC blacklist by Circle (external, but common/expected event) — or, for the same-chain path, the user simply uses a contract address as `order.user` whose `receive()` reverts for a native-token order.
3. User calls `cancelOrder()` before a solver fills (same-chain) or the destination triggers `RefundEscrow` after expiry (cross-chain).
4. `_withdraw` attempts `IERC20(token).safeTransfer(U, amount)` (or `_sendValue`), which reverts because `U` is blacklisted/non-accepting.
   - Same-chain: `cancelOrder()` itself reverts every time it is called — the escrow is permanently stuck in `_orders[commitment][token]`.
   - Cross-chain: `onAccept` reverts, `EvmHost.dispatchIncoming` deletes the request receipt so it can be retried, but every retry hits the exact same revert, so the `RefundEscrow`/`RedeemEscrow` message can never be delivered and the escrow is permanently stuck with no other recovery path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
