### Title
Silent u128→u64 truncation in `SwapBaseOut` fee-adjusted input calculation allows near-total pool drain for negligible payment - ([File: program/src/processor.rs])

### Summary
`process_swap_base_out` and `process_swap_base_out_v2` compute the amount a swapper must pay by calling `Calculator::swap_token_amount_base_out` (which returns a 128-bit `U128`), scaling it by the fee denominator, and finally calling `.as_u64()` to store it as the on-chain transfer amount [1](#0-0) . The `uint::construct_uint!`-generated `U128` type's `.as_u64()` does not perform a range check — it silently returns the low 64 bits of the 128-bit value. When `swap.amount_out` is chosen close to the pool's opposite-side reserve, the required input amount computed by `swap_token_amount_base_out` legitimately exceeds `u64::MAX`, and the truncation yields an arbitrary, attacker-influenced small value rather than aborting, letting an attacker pay almost nothing while draining almost the entire reserve.

### Finding Description
`Calculator::swap_token_amount_base_out` computes `amount_in = coin * amount_out / (pc - amount_out)` (or the symmetric PC2Coin case) entirely in `U128` arithmetic using `checked_mul`/`checked_ceil_div` [2](#0-1) . Because `denominator = total_pc_without_take_pnl.checked_sub(amount_out)` can be driven arbitrarily close to `1` by an attacker who freely chooses `swap.amount_out` in the `SwapBaseOut` instruction, the numerator/denominator ratio can legitimately be much larger than `u64::MAX` while still fitting comfortably inside `U128` (max ≈ 3.4×10^38).

Both `process_swap_base_out` and `process_swap_base_out_v2` then do:
```rust
let swap_in_after_add_fee = swap_in_before_add_fee
    .checked_mul(amm.fees.swap_fee_denominator.into())
    .unwrap()
    .checked_ceil_div(...)
    .unwrap()
    .as_u64();
``` [3](#0-2) [4](#0-3) 

`.as_u64()` on the `U128` type produced by `construct_uint!` truncates to the low 64 bits rather than returning `None`/panicking on overflow — unlike the `checked_*` operators used everywhere else in this codebase (`Calculator::to_u64` explicitly uses `try_into` and returns `AmmError::ConversionFailure` on overflow, but that safer path is not used here) [5](#0-4) .

The truncated (small, effectively attacker-steerable) value `swap_in_after_add_fee` is then used for every subsequent safety check:
- `if user_source.amount < swap_in_after_add_fee` (insufficient funds check) [6](#0-5) 
- `if swap.max_amount_in < swap_in_after_add_fee` (slippage check) [7](#0-6) 
- it is the exact amount transferred from the user into the vault via `Invokers::token_transfer` [8](#0-7) 

Meanwhile, `swap.amount_out` — the full attacker-chosen output — is transferred out of the vault unmodified, gated only by `if swap.amount_out >= total_pc_without_take_pnl { return Err(InsufficientFunds) }`, i.e. any value strictly less than the entire reserve is accepted [9](#0-8) .

Because the truncated payment amount is computed *after* the overflow occurs, the checks that are supposed to enforce "pay enough" and "respect slippage" are checking against a corrupted number, not the true economic cost.

### Impact Explanation
An attacker can call `SwapBaseOut` (or its v2 variant) with `amount_out` set just below the pool's total opposite-side reserve, driving the required input into overflow territory. The resulting truncated `swap_in_after_add_fee` can be far smaller than the true amount needed to preserve the pool invariant. The attacker pays only the truncated (small/near-zero) amount while receiving almost the entire reserve of the other token, directly draining LP/user funds from the pool — a concrete theft of pool funds and insolvent pool accounting. This is reachable directly on-chain from a single transaction by any unprivileged swapper with attacker-chosen instruction data (`amount_out`, `max_amount_in`) and no special privileges.

### Likelihood Explanation
Reachable by any user who can submit a `SwapBaseOut`/`SwapBaseOutV2` instruction — no privileged signer, off-chain component, or non-default build is required. The only precondition is that pool reserves and the chosen `amount_out` create a denominator small enough that the mathematically correct `amount_in` exceeds `u64::MAX`, which is achievable by simply picking `amount_out` extremely close to the reserve (a single value the attacker fully controls), making this practically triggerable on any live pool.

### Recommendation
Replace the unchecked `.as_u64()` truncation on the final fee-adjusted amount with a checked conversion that fails the instruction (e.g. via `Calculator::to_u64` returning `AmmError::ConversionFailure`, mirroring how the rest of the codebase already treats overflow) whenever the computed `U128` value does not fit in `u64`. Apply this fix to both `process_swap_base_out` and `process_swap_base_out_v2`, and consider bounding `amount_out` well below the raw reserve (not just strictly less than it) to keep the denominator in `swap_token_amount_base_out` from approaching zero.

### Proof of Concept
1. Attacker observes pool reserves `total_pc_without_take_pnl = P`, `total_coin_without_take_pnl = C` (e.g., both on the order of 10^12–10^15, typical for live pools).
2. Attacker submits `SwapBaseOut` with `swap.amount_out = P - 1` (Coin2PC direction) and `swap.max_amount_in = u64::MAX` (to pass slippage since the truncated amount will be small anyway).
3. Inside `process_swap_base_out`, `denominator = P - amount_out = 1`, so `swap_in_before_add_fee = C * (P-1) / 1 ≈ C*P`, generally ≫ `u64::MAX` for realistic reserves.
4. `swap_in_after_add_fee = (swap_in_before_add_fee * fee_denominator / (fee_denominator - fee_numerator)).as_u64()` truncates the huge `U128` to its low 64 bits, producing an arbitrary/small value instead of erroring.
5. The insufficient-funds and slippage checks pass against the truncated value; `Invokers::token_transfer` moves only that small truncated amount from the attacker into the vault.
6. `Invokers::token_transfer_with_authority` then sends `swap.amount_out = P - 1` (almost the entire PC reserve) to the attacker, draining the pool while paying far less than the true cost.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
