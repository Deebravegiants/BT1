### Title
Webhook Tenant Identity (`shop`) Header Not Covered by HMAC Signature Verification - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (tenant identifier) that is handed to the application's webhook handler is read from an HTTP header that is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC exclusively against that signable string (the body): [2](#0-1) 

`Registry.process` gates on this body-only HMAC check, and then constructs `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which are parsed straight from unauthenticated headers (`shopify-shop-domain`, `shopify-topic`, etc.) rather than from the signed body: [3](#0-2) [4](#0-3) 

The binding the library implicitly relies on is:
`hmac_valid(raw_body) == true` therefore `shop header == authentic tenant for this event`

But the actual guarantee provided is only:
`hmac_valid(raw_body) == true` (the header `shop`/`topic`/`webhook_id` are never part of the signed input)

This is precisely the "field acted on but not covered by the HMAC" pattern: `shop` is used by `Registry.process` to build `WebhookMetadata` that host applications use as the tenant key for storing/acting on data, yet it is not bound to the HMAC-verified payload.

### Impact Explanation
A merchant who has installed the app (an "unprivileged internet user" from the app's perspective — no access to `api_secret_key`) legitimately receives a genuinely-signed webhook from Shopify for their own shop (valid body + valid HMAC computed by Shopify using the app's secret). Because the HMAC signs only the body, that same valid `(body, hmac)` pair remains valid for the body no matter what `shop-domain` header is attached to the replayed request. The merchant can therefore resend the same request to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a *different* shop's domain. `Registry.process` will accept it (HMAC of the body still validates) and dispatch it to the handler tagged with the attacker-chosen `shop`, causing the host application to update/act on data under another tenant's identity — a cross-tenant access/data-integrity breach in any app that trusts `WebhookMetadata#shop` as the authoritative tenant key (which is the documented usage pattern, see `docs/usage/webhooks.md`).

### Likelihood Explanation
Exploitation requires only owning/installing the app for one shop and manipulating one HTTP header on a replayed request — no possession of `api_secret_key`, no TLS interception, and no other privileged access is needed.

### Recommendation
Bind the identity headers (`shop-domain`, `topic`, `webhook-id`) to the HMAC-verified request, e.g. by including them in the signable string or requiring the caller to independently verify `request.shop` against a known/installed shop list before trusting it as a tenant key in `Registry.process` / `WebhookMetadata`.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body, computed by Shopify with the app's secret>
x-shopify-shop-domain: shop-a.myshopify.com
Body: {"id": 123, ...}
```
2. The merchant who owns `shop-a` intercepts/replays this exact request but changes only the header:
```
x-shopify-shop-domain: shop-b.myshopify.com
```
3. `Utils::HmacValidator.validate` (which hashes only the body) still returns `true`: [5](#0-4) 
4. `Registry.process` dispatches the handler with `shop: "shop-b.myshopify.com"`, `body` belonging to `shop-a`, and the app processes/stores this cross-tenant, mismatched data under `shop-b`'s identity: [6](#0-5)
