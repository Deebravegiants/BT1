### Title
Unauthenticated RPC-reachable auth reset strips PIN/biometric/device-auth protections via `exodus.auth.clear`/`removePin` - ([File: features/auth-mobile/module/auth.js])

### Summary
The `Auth.clear()` and `Auth.removePin()` methods in `features/auth-mobile/module/auth.js` delete the PIN and bio/device-auth secrets from the keystore and reset the `authAtom` state without verifying that the caller has already authenticated (no `isCorrectPin` check, no lock-state check). These methods are exposed unguarded over the RPC surface via `authApiDefinition`, which simply spreads all `auth` module methods onto `exodus.auth.*`.

### Finding Description
`Auth.clear` calls `this.removePin()` then records `all_auth_removed`; `removePin` calls `this.disableBioAuth()`, deletes `AUTH_KEYSTORE_PIN_KEY`, merges `{hasPin: false}` into the atom, and records `pin_auth_removed` [1](#0-0) . None of `clear`, `removePin`, or `disableBioAuth` take any authentication token/current-PIN/unlock-state parameter, nor do they consult `#authAtom`'s existing `shouldAuthenticate`/lock condition before mutating protected state — they unconditionally call `#keystore.deleteSecret` on the PIN, bio-auth, and device-auth keys [2](#0-1) .

`authApiDefinition` exposes the entire `auth` module surface (including `clear`, `removePin`, `disableBioAuth`) directly onto the RPC-facing API object with a plain spread, adding no gating logic: `auth: { ...auth, ... }` [3](#0-2) . This is unlike other feature APIs in the same codebase that explicitly gate sensitive calls behind lock state — e.g. `addressProviderApi` wraps methods with `withWalletAccountInstance`, which throws `'address-provider: wallet should be unlocked'` if `lockedAtom.get()` is true before proceeding [4](#0-3) . No equivalent `lockedAtom`/authenticated-state check exists anywhere in `authApiDefinition` or in `Auth` itself. The RPC layer (`@exodus/sdk-rpc`'s `flattenObject`/`exposeMethods`) is a generic method-dispatch bridge with no per-method auth middleware [5](#0-4) , so any caller with RPC access to the exposed SDK can invoke `exodus.auth.clear()` or `exodus.auth.removePin()` regardless of whether the wallet/device is currently locked or the user has ever supplied a correct PIN or biometric.

The existing unit tests confirm the call succeeds with no precondition other than a PIN having been previously set — no simulated `isCorrectPin`/`bioAuth.authenticate` success is required before `auth.clear()`/`auth.removePin()` run and delete all keystore secrets [6](#0-5) [7](#0-6) .

### Impact Explanation
An unprivileged party with RPC reach to `exodus.auth.*` (e.g. a compromised UI-thread, malicious in-app content, or any RPC client that shares the transport channel) can silently strip all local lock protections — PIN, biometric, and device-auth keys — turning `hasPin`/`hasBioAuth`/`hasDeviceAuth` to `false` and `shouldAuthenticate` to `false` in `authAtom`, all without ever proving knowledge of the current PIN or passing biometric/device authentication. While this does not directly decrypt the wallet seed (PIN/bio-auth appear to be a device-level UI gate rather than the storage-encryption key itself, based on `features/wallet/module/wallet.js`'s separate `unlock`/passphrase-based decryption flow), it does eliminate the lock-screen protection that guards subsequent app-level flows (viewing mnemonic, signing, sending) from a person who has physical/local access to the device but not the correct PIN — a persistent, silent downgrade of wallet security state triggerable at any time.

### Likelihood Explanation
Feasible and repeatable given only ordinary RPC access to the exposed SDK API surface — no privileged state, keys, or social engineering required. Exploitability depends on the deployment's RPC transport exposure (e.g., whether a compromised or malicious webview/dapp/content process can reach the `exodus.auth` namespace); within this codebase's own architecture, no code path prevents the call once RPC access exists, as confirmed by the absence of any `lockedAtom`/current-PIN check in `authApiDefinition` or `Auth`.

### Recommendation
Gate `removePin`/`clear`/`disableBioAuth` (and any other destructive auth-state mutation) behind a proof of current authentication — e.g., require and verify `isCorrectPin(currentPin)` or a recent successful bio/device-auth trigger before permitting the keystore deletions, mirroring the `lockedAtom`-gating pattern already used in `features/address-provider/api/index.js`. At minimum, wrap these methods in `authApiDefinition` with a check against `authAtom`/`lockedAtom` state (reject if `shouldAuthenticate` is true and no fresh-auth proof was supplied) before delegating to the underlying `auth` module methods.

### Proof of Concept
Integration test against `authDefinition.factory(...)` wired the same way as `authApiDefinition`:
1. Set up `auth` with a PIN and bio-auth enabled (`auth.setPin('123456')`, `auth.enableBioAuth()`), matching `features/auth-mobile/module/__tests__/auth.test.js` setup.
2. Do NOT call `auth.isCorrectPin` with the correct value, and do NOT simulate `bioAuth.authenticate` success.
3. Call `auth.clear()` (or `auth.removePin()`) directly, as would happen via `exodus.auth.clear()` RPC dispatch.
4. Expected (fixed) behavior: the call rejects with an authentication-required error and `keystore.deleteSecret` is never invoked, `authAtom` remains unchanged (`hasPin: true`, `hasBioAuth: true`).
5. Current (vulnerable) behavior: the call succeeds, `keystore.deleteSecret` is called for `AUTH_KEYSTORE_PIN_KEY`, `AUTH_KEYSTORE_BIO_AUTH_KEY`, `AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY`, `AUTH_KEYSTORE_DEVICE_AUTH_KEY`, `AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY`, and `authAtom` is updated to `{hasPin: false, hasBioAuth: false, hasDeviceAuth: false}` — as already demonstrated by the existing (non-adversarial) test at `features/auth-mobile/module/__tests__/auth.test.js:68-89`.

export const flattenObject = <T>(obj: T, path: string[] = []): { [name: string]: Fn } => {
  if (typeof obj === 'function') {
    return { [serializePath(path)]: obj as Fn }
  }

  if (typeof obj !== 'object' || !obj) return {}

  return Object.keys(obj).reduce((acc, key) => {
    return { ...acc, ...flattenObject(obj[key as keyof T], [...path, key]) }
  }, {})
}
