Audit Report

## Title
Dry-run vs. real-transaction `CREATE1` address mismatch in `pallet-revive` — (File: substrate/frame/revive/src/exec.rs)

## Summary
In `Storage::new_frame`'s `FrameArgs::Instantiate` branch (`substrate/frame/revive/src/exec.rs`, lines 1141-1158), the `CREATE1` contract address is derived by subtracting 1 from the current account nonce whenever `origin_is_caller` is true, regardless of whether execution is a real dispatched transaction or an RPC/dry-run simulation. The repository's own `prdoc/stable2506/pr_8504.prdoc` documents that this exact code is buggy and that the fix requires gating the subtraction on an `ExecContext::Transaction` check, but no `ExecContext` identifier, parameter, or equivalent gating exists anywhere in `exec.rs` or the rest of the crate — the documented fix was not applied to this code snapshot.

## Finding Description
`Storage::new` always calls `Self::new_frame(... , origin_is_caller = true, ...)` for the first frame [1](#0-0) , and this same `new` entry point is used both for dry-run/RPC queries and for real extrinsic dispatch. Inside `new_frame`, the `FrameArgs::Instantiate` branch derives the `CREATE1` address by subtracting 1 from `account_nonce` whenever `origin_is_caller` is true, with no distinction between a simulated call (where `frame_system`'s nonce has not yet been incremented) and a real dispatched transaction (where the nonce has already been incremented pre-dispatch) [2](#0-1) . A repository-wide search confirms `ExecContext` — the enum the prdoc says was added to gate this subtraction — appears only in `prdoc/stable2506/pr_8504.prdoc` and is absent from `exec.rs`, `new`/`new_frame`, and every other source file in the crate. The `nonce_not_incremented_in_dry_run` regression test referenced in the prdoc likewise does not exist anywhere in the codebase. This confirms the code in this snapshot is the "before fix" version described in the prdoc, and the address-derivation logic does not correctly differentiate dry-run vs. real-transaction execution contexts.

## Impact Explanation
Any consumer relying on `pallet-revive`'s dry-run/RPC contract-creation preview (the same path Ethereum-JSON-RPC-style `eth_estimateGas`/`eth_call` tooling uses for `CREATE1` address prediction) to determine the address a to-be-deployed contract will occupy can be given an incorrect address, because the dry-run path computes `create1(deployer, N-1)` while the subsequent real transaction computes `create1(deployer, N)` for the same nonce state. This can break wallets/tooling that pre-display, fund, or reference the predicted deployment address before the real transaction lands, causing funds/approvals to be sent to an address that will never host the deployed contract. This is a functional correctness/tooling-safety bug in the exposed RPC-facing address-derivation logic rather than a direct on-chain fund-drain or consensus-safety issue.

## Likelihood Explanation
The mismatch is deterministic and requires no privileged access: any unprivileged user calling the standard dry-run/RPC instantiate path followed by the real signed instantiate extrinsic for the same account will observe two different addresses whenever `origin_is_caller` is true, since the code unconditionally applies the "nonce already incremented pre-dispatch" assumption to both contexts.

## Recommendation
Reintroduce the `ExecContext` (or equivalent, e.g. `exec_config.is_dry_run`) distinction in the `CREATE1` branch of `Storage::new_frame` so the nonce subtraction is applied only when executing inside a real dispatched transaction, not during RPC/dry-run simulation:
```rust
if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
    account_nonce.saturating_sub(1u32.into()).saturated_into()
} else {
    account_nonce.saturated_into()
}
```
Restore/add the `nonce_not_incremented_in_dry_run` regression test referenced in `prdoc/stable2506/pr_8504.prdoc` to lock in the fix.

## Proof of Concept
1. For account `A` at nonce `N`, call the dry-run/bare-instantiate RPC path with `salt = None`. Since it's simulated, `frame_system`'s nonce for `A` is still `N`, but `new_frame` (via `origin_is_caller == true`) computes `create1(deployer, N-1)`.
2. Submit the real signed `instantiate`/`instantiate_with_code` extrinsic for the same account `A`. By the time execution reaches `new_frame`, `frame_system` has incremented the nonce pre-dispatch to `N+1`, and the same subtraction computes `create1(deployer, N)`.
3. Compare the two addresses: `create1(deployer, N-1)` (dry-run) vs. `create1(deployer, N)` (actual deployment) — they differ, confirming the mismatch. This matches lines 1141-1158 of `substrate/frame/revive/src/exec.rs` as currently written, and the absence of the `ExecContext` gate described in `prdoc/stable2506/pr_8504.prdoc` lines 26-41.
