### Title
Users can permanently lose escrowed order funds if a destination `IntentGateway` instance is never registered (or is later overwritten to zero) - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._instance()` hard-reverts with `UnknownInstance` whenever the destination/source chain has no registered gateway deployment in `_instances`. The source-side cross-chain cancellation path, `_cancelFromSource` in `ExtrinsicIntents.sol`, calls this exact function to build the storage-proof key needed to dispatch the recovery GET request. Because this call is made unconditionally, before any escrow is released, an order whose destination chain instance is unset or removed can never be cancelled from the source chain, permanently trapping the user's escrowed input tokens — the same failure mode as the referenced `GaugeController` finding, where a required-nonzero check on a registry entry blocked a user's own recovery/cleanup action after that entry was removed.

### Finding Description
`_instance()` is the sole lookup used to resolve a counterpart gateway address for a given state machine: [1](#0-0) 

It reverts unconditionally if `_instances[keccak256(stateMachineId)] == address(0)` — this happens both when a deployment was never registered for that state machine and, since `NewDeployment` (see `onAccept`) can be re-dispatched by Hyperbridge governance to overwrite `_instances[...]`, whenever a later `NewDeployment` message clears or points the instance elsewhere.

The order owner's own cancellation entrypoint, `_cancelFromSource`, depends on this lookup to build the GET-request key that proves the order was not filled on the destination: [2](#0-1) 

Line 258 (`_instance(order.destination)`) is called after the deadline/height checks but before any state is written or refund dispatched. Because `_instance` reverts, the entire cancellation transaction reverts — there is no way for `_cancelFromSource` to proceed and refund the user's already-escrowed tokens if the destination instance mapping is unset for `order.destination` at the time of cancellation.

This mirrors the GaugeController pattern precisely: a mapping that flags "this entity is registered" is checked with a hard revert inside the *cleanup/removal* code path (vote-removal in the original finding, order-cancellation/refund here), instead of being restricted only to the *creation/entry* path (vote-casting in the original, order-placement here). Once the registry entry disappears (gauge removed / instance never set or cleared by a later `NewDeployment`), the user has no way to reclaim already-committed value through that path.

### Impact Explanation
Any user whose cross-chain order names a `destination` for which `_instances[keccak256(order.destination)]` is zero (never configured, or reset by a subsequent `NewDeployment` message) cannot cancel that order from the source chain: `cancelOrder` → `_cancelFromSource` → `_instance(order.destination)` reverts every time. Since input tokens were already escrowed in `_orders` at `placeOrder` time, this results in permanently frozen user funds with no recovery via the source-side cancellation route — a fund-freezing bug reachable by any ordinary user simply by placing then trying to cancel an order, no privileged actor required. This satisfies the "permanent freezing of funds" / "route unable to deliver messages" criteria for a valid analog.

### Likelihood Explanation
The precondition (a destination gateway instance being unset or later cleared) is realistic in production: instances are populated by cross-chain `NewDeployment` governance messages that can, in principle, be re-issued for redeployments/rotations, and any transient period where an instance is not yet registered (e.g., new chain onboarding, or a solver/user mistakenly/legitimately targeting a `destination` value that was never deployed) exposes this path. The order placement side (`placeOrder`) does not appear to validate `order.destination` against `_instances` before escrowing funds, so nothing prevents a user from creating an order for a destination lacking a registered instance in the first place, after which the only cross-chain cancellation route that depends on `_instance` becomes permanently blocked.

### Recommendation
Do not let the cancellation/recovery path hard-fail on a missing registry entry the way `_cancelFromSource` currently does via `_instance()`. Specifically:
- Validate `order.destination` has a registered instance at `placeOrder` time so that orders can never be escrowed against an unregistered destination.
- For the cancellation path, avoid gating the refund on `_instance()` succeeding, or provide an alternative recovery mechanism (e.g., a timeout-based direct refund with no cross-chain proof requirement) when the destination instance is unset/cleared, mirroring the fix recommended in the referenced report: remove the hard dependency on a currently-valid registry lookup from the user's own fund-recovery code path.

### Proof of Concept
1. A user calls `placeOrder` for a cross-chain order with `order.destination = D`, escrowing input tokens in `_orders[commitment]`. No check ensures `_instances[keccak256(D)]` is set.
2. Suppose `D`'s gateway instance was never registered, or Hyperbridge later re-dispatches `NewDeployment` and effectively updates/omits `D`'s entry (`onAccept` → `_addDeployment`, referenced in `ExtrinsicIntents.sol` lines 318-319, 341-342).
3. After the order's deadline passes, the user calls `cancelOrder`, routing to `_cancelFromSource` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:240-275`).
4. Execution reaches `_instance(order.destination)` at line 258, which reverts with `UnknownInstance` (`evm/src/apps/intentsv2/IntentsBase.sol:401-405`) because `_instances[keccak256(D)] == address(0)`.
5. The entire cancellation transaction reverts; the user's escrowed tokens in `_orders[commitment]` remain locked in the contract with no other route to reclaim them via `_cancelFromSource`.

Note: I was unable to fully inspect `_addDeployment`'s exact overwrite semantics (whether re-registration can zero out an existing instance) or confirm whether `_cancelFromDest`'s underlying `_post`/`_body` helper also depends on `_instance(order.source)` in the same unconditional way, due to tool-call limits in this session. Those code paths in `IntentsBase.sol`/`ExtrinsicIntents.sol` should be reviewed directly to confirm the full extent of exposure (i.e., whether the destination-side cancellation route offers a working fallback or is similarly blocked).

        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
