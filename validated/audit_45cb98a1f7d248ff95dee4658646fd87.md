### Title
Webhook shop identity spoofing — the `shop-domain` header is trusted but not covered by the webhook HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's tenant identity from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator.validate` is computed only over the raw request body, not over that header. This breaks the intended binding `shop header == HMAC-authenticated field`, allowing anyone who can produce a body+HMAC pair that is valid for the app's shared webhook secret (e.g. by replaying/observing one legitimately delivered webhook, or triggering a delivery for a shop they control) to relabel it as coming from a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC against `to_signable_string`, i.e. body-only, using the app's shared secret key (`Context.api_secret_key`, the same secret for every installed shop): [3](#0-2) 

Since Shopify signs webhooks with the app's single `client_secret` (not per-shop), and that secret is not bound to the shop header in this gem's verification, the equality the app relies on —
`request.shop (used as tenant key) == shop that produced the HMAC-covered bytes`
— does not hold. The `hmac` only proves "this body was signed with our app secret", not "this body came from shop X". Any webhook body+HMAC pair valid for the app's secret can be paired with an arbitrary `shop-domain` header and will still pass `Registry.process` → `HmacValidator.validate`, per the documented flow: [4](#0-3) 

The `shop` value is then handed to the app's registered handler as the trusted tenant identifier (`data.shop`) per the documented `WebhookHandler` contract: [5](#0-4) 

This is the direct analog of the reported bug class: a field the code *acts on* (here, tenant/shop attribution) is not covered by the cryptographic check (here, the HMAC) that is supposed to make it trustworthy — analogous to a session key trusted separately from the authenticated payload.

### Impact Explanation
An attacker who installs the vulnerable app on their own shop (or otherwise obtains one valid `(raw_body, hmac)` pair signed with the app's secret) can resend that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will accept it as HMAC-valid, and the app's handler will process attacker-controlled webhook data under the victim's tenant identity — a cross-tenant data confusion/injection primitive. Depending on how the host app trusts `data.shop` (e.g. to look up which merchant's data to update/delete, or to know which session to use for subsequent API calls), this can lead to cross-tenant data corruption or actions being taken against the wrong merchant's account.

### Likelihood Explanation
Requires the attacker to be able to generate at least one HMAC-valid body for the target app's shared secret — trivially achievable by installing the app on any shop they control and triggering a real webhook (topics like `app/uninstalled` or any subscribed topic), since the secret is shared across all shops using the app, not shop-specific. No access to the app's `client_secret` or any merchant's access token is needed. The only extra step is replaying the captured request with a modified `shop-domain` header, which is fully controllable by the client since it's an HTTP header.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the signable string that is HMAC-verified, or independently verify that the `shop-domain` header corresponds to a shop for which this specific webhook was actually registered/expected (e.g. cross-check against stored subscription state) before trusting `Request#shop`/`data.shop`. At minimum, document that `Request#shop` is not itself authenticated by the HMAC and must not be used as a sole tenant-identity source without additional verification.

### Proof of Concept
1. App installs on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a real webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)` — valid per: [6](#0-5) 
(see `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker resends the same body `B` and hmac `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"victim.myshopify.com"` per `Request#shop`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only and it matches `H`, so validation succeeds even though `victim.myshopify.com` never produced this webhook.
5. The registered `WebhookHandler#handle` is invoked with `data.shop == "victim.myshopify.com"`, `data.body == B` (attacker-chosen), demonstrating cross-tenant spoofing of the webhook's shop identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
