### Title
Colliding `ImageId` generated for two distinct biometric image variants of the same frame - (File: `src/agents/image_notary.rs`)

### Summary
The Aragon report describes a fixed identifier (`PRESALE_ID` apmNamehash) being reused to reference two conceptually different contracts, creating ambiguity about which entity a given ID actually points to. The closest reachable analog in orb-core is in `save_identification_images_impl`, where the identifier used to reference a saved biometric image (`ImageId`) is derived purely from frame content/timestamp/dimensions, and is computed twice from the *same* source frame object to label two different output artifacts (a privacy-reduced identification copy and the full-resolution capture), producing identical IDs for what are treated as distinct downstream objects.

### Finding Description
`Frame::image_id` computes the ID deterministically from frame bytes, timestamp, width and height only [1](#0-0) . In `save_identification_images_impl`, the RGB image is saved twice — once at reduced resolution into `identification/rgb/left` and once at full resolution into `rgb_camera` — by calling `left.rgb_frame.image_id(signup_id)` twice on the very same `left.rgb_frame` value: [2](#0-1) 
Because `image_id()` only hashes the frame's bytes/timestamp/width/height (not the target resolution or directory), the two calls always yield the exact same `ImageId`, even though they are recorded as two distinct fields (`left_rgb` and `left_rgb_fullres`) in `IdentificationImages` [3](#0-2) . The same pattern repeats for the right eye [4](#0-3) . This mirrors the reported bug class: a single identifier is made to stand in for two semantically different objects (here, a redacted/medium-resolution identification image vs. the full-resolution raw capture), with no mechanism ensuring the IDs diverge according to the different resolution/purpose.

### Impact Explanation
Downstream consumers (backend presigned-URL requests, upload paths keyed by `ImageId`, and personal-custody package metadata in `make_info_json`, which records `left_ir_image_id`/`right_ir_image_id`/`thumbnail_image_id` by string value [5](#0-4) ) rely on `ImageId` as a unique, purpose-specific reference. Because the medium-resolution "identification" RGB image and the full-resolution raw RGB image share the same ID, any system that indexes or deduplicates by `ImageId` cannot distinguish which resolution/variant of the image a given ID actually refers to. This creates the same category of risk as the reported issue: ambiguity over "which application/data is actually deployed/referenced" under one identifier, which could result in the wrong image variant (potentially a higher-resolution biometric capture than intended for a given use case) being associated with, retrieved as, or substituted for the other under upload/retention flows that assume `ImageId` uniquely identifies a specific image artifact.

### Likelihood Explanation
This is deterministic, not probabilistic — it happens on every signup whenever `save_identification_images_impl` runs, because it is a direct consequence of calling `image_id()` twice on the same frame value rather than a hash collision. It requires no attacker action; it is a structural defect reachable on the standard signup path for every identification-image capture. However, whether it causes an actual data-disclosure or misattribution issue depends on backend-side handling of `ImageId` (out of scope of this repo), which could not be fully verified.

### Recommendation
Derive distinct `ImageId`s for distinct output variants of the same source frame — e.g., by mixing in a variant/resolution/purpose tag (similar to how `data_id` is already used to disambiguate images within a signup) before hashing, so that `left_rgb` (medium-res identification copy) and `left_rgb_fullres` (full-resolution capture) never collide. Apply the same fix to the corresponding right-eye computation.

### Proof of Concept
1. During a signup, `save_identification_images_impl` is invoked with a given `left.rgb_frame`.
2. `let left_rgb = left.rgb_frame.image_id(signup_id);` is computed and used to save the medium-resolution copy under `identification/rgb/left`.
3. `let left_rgb_fullres = left.rgb_frame.image_id(signup_id);` is computed immediately after, from the identical `left.rgb_frame` value (same bytes, timestamp, width, height) and the same `signup_id`.
4. Since `image_id()` is a pure function of those inputs, `left_rgb == left_rgb_fullres` for every signup — verifiable by inspecting `IdentificationImages` in the generated debug report / personal custody metadata, where both fields will contain the identical `ImageId` string despite referring to different image files/resolutions.     /// Returns a image id for the frame.
    fn image_id(&self, signup_id: &SignupId) -> ImageId {
        let mut hasher = crc32fast::Hasher::new();
        hasher.update(self.as_bytes());
        hasher.update(&self.timestamp().as_nanos().to_le_bytes());
        hasher.update(&self.width().to_le_bytes());
        hasher.update(&self.height().to_le_bytes());
        ImageId::new(signup_id, hasher.finalize())
    }
