### Title
Webhook shop/topic headers are not covered by the HMAC, so `Registry.process` trusts an unauthenticated `shop` into `WebhookMetadata` - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` validates only that the raw HTTP body was signed with the app's `api_secret_key` via `Utils::HmacValidator.validate`, but `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and passed unchecked into `WebhookMetadata` given to the app's handler [2](#0-1) . Since `api_secret_key` is shared across all shops that install a given app, any attacker with one legitimately-signed webhook body (e.g., from their own dev-store install) can replay that exact body to the app's public webhook endpoint with a forged `shop-domain` header naming a victim merchant, and the signature still validates.

### Finding Description
The binding the question asks about is:
`shop authenticated by signature == shop passed to WebhookMetadata`

Trace:
- `HmacValidator.validate(request)` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `request.hmac` [3](#0-2) .
- `Webhooks::Request#to_signable_string` returns `@raw_body` only — no header, including `shop-domain` or `topic`, is part of the signed material [1](#0-0) .
- `Registry.process` uses the validated-body result to authorize dispatch, then reads `request.topic` and `request.shop` straight from headers (`shopify-shop-domain`/`x-shopify-shop-domain`) with no cross-check against the signature or against any known-installed-shop list [2](#0-1) , path="lib/shopify_api/webhooks/request.rb" start="20" end="23" />.
- The resulting `WebhookMetadata#shop` is handed to the app's `WebhookHandler#handle` as if it were an authenticated shop identity [4](#0-3) .

So the two sides of the equality diverge: the HMAC only proves "this body was produced by someone possessing this app's `api_secret_key`" (which, for multi-tenant apps, is Shopify itself signing on behalf of *any* installed shop), while the `shop` value the handler receives is taken from a header entirely outside that signature. An attacker who owns their own dev/test shop and app install will legitimately receive real, validly-HMAC-signed webhook deliveries for their own shop. Because the signature covers only the body, that captured `(body, hmac)` pair remains valid under any header combination. The attacker replays it to the app's public webhook route with `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`, `x-shopify-webhook-id`), and `Registry.process` will invoke the app's handler with `data.shop == "victim-shop.myshopify.com"` even though nothing about the victim was ever verified.

None of the existing guards catch this: `HmacValidator.validate` only checks the body signature, not header binding; there is no `ShopValidator.sanitize!`, `state` comparison, `JwtPayload`, `HttpRequest#verify`, or `Context.setup?/private?/embedded?` check anywhere in `Registry.process`. The `@registry` class-level hash mutation via `add_registration`/`clear` described in the prompt is not itself attacker-reachable over HTTP (it requires calling Ruby methods in the host app's own process, not something an unprivileged internet attacker can trigger), so that specific vector is not a real path — but the underlying "shop header is unauthenticated" claim is independently true and exploitable via the replay described above.

### Impact Explanation
An app that keys any data lookup, deletion, or business logic in its `WebhookHandler#handle` off `data.shop` (as is standard/expected usage, and as documented via `WebhookMetadata#shop`) will act on the attacker-chosen shop string rather than an authenticated tenant. Depending on handler logic this can mean triggering another merchant's mandatory-webhook side effects (e.g., simulating `shop/redact` or `customers/redact` for a shop the attacker doesn't control), causing log/state pollution keyed to a victim's shop domain, or confusing per-shop caches/queues — a cross-tenant data-integrity issue. This is repeatable indefinitely and against any shop domain string the attacker chooses (real or fabricated), since nothing about `shop` is validated against installed shops or the signature.

### Likelihood Explanation
Preconditions: the attacker needs (a) a target app built on this gem that exposes a webhook endpoint calling `Registry.process`, and (b) at least one legitimately-delivered webhook body+HMAC pair, obtainable trivially by installing the app on their own free development store and triggering any webhook topic. Cost is a single HTTP replay with modified headers; no secrets, no TLS interception, and no privileged access are required. This is straightforward and fully repeatable.

### Recommendation
Do not treat header-derived `shop`/`topic`/`webhook_id` as authenticated. Cross-check `request.shop` against the app's own record of installed/authenticated shops (session storage) before dispatching, and/or include the shop and topic in the material verified against Shopify (Shopify does provide these in headers only, so the gem should require host apps to independently verify shop existence via their session store rather than implicitly trusting it as authenticated in `WebhookMetadata`). At minimum, document explicitly in `WebhookMetadata`/`Registry.process` that `shop` is unauthenticated header data and must be revalidated by the handler before any tenant-scoped action.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryShopSpoofTest < Test::Unit::TestCase
      def test_shop_header_not_bound_to_hmac
        body = "{}"
        hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          body,
        )
        encoded_hmac = Base64.encode64(hmac)

        # Attacker's own legitimately-signed webhook (their own shop)
        attacker_headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => encoded_hmac,
          "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        }
        attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: attacker_headers)
        assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))

        # Same body+HMAC replayed with victim's shop domain -- still validates
        forged_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
        forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
        assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))

        received_shop = nil
        handler = TestHelpers::FakeWebhookHandler.new(->(data) { received_shop = data.shop })
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
        )

        ShopifyAPI::Webhooks::Registry.process(forged_request)

        # Handler received an unauthenticated, attacker-chosen shop identity
        assert_equal("victim-shop.myshopify.com", received_shop)
        refute_equal("attacker-shop.myshopify.com", received_shop)
      end
    end
  end
end
```
This demonstrates that `Utils::HmacValidator.validate` accepts the same body+signature under an arbitrary `shop-domain` header, and `Registry.process` forwards that unverified shop straight into `WebhookMetadata#shop` delivered to the handler — confirming the SHOP BINDING invariant is broken.
