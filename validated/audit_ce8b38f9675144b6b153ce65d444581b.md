## Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw HTTP body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never part of the signed payload — to identify the tenant the webhook belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , and `HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string [2](#0-1) . The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` validates only the HMAC and then unconditionally forwards `request.shop` (the unauthenticated header value) into `WebhookMetadata`, which is delivered to the app's webhook handler as the tenant identity for the event: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" bug class from the report, translated to this gem: the equality that should hold — `shop-used-for-authorization == shop-covered-by-hmac` — never holds, because `shop` is outside the signed byte range entirely.

### Impact Explanation
Because the shop identity is never part of the signed content, an attacker who legitimately installs the app on their own store (an "unprivileged internet user" from the app's perspective) can:
1. Trigger any webhook topic/body they choose on their own shop, obtaining a genuinely-signed `(raw_body, hmac)` pair from Shopify's real signing.
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still passes (it never looks at the header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the event came from the victim shop.

Any host application logic that uses `WebhookMetadata#shop` to look up/update per-tenant records (session storage, billing state, mandatory GDPR redaction flows, etc.) can be made to act on the wrong tenant, i.e., cross-tenant access/data corruption using only the attacker's own valid webhook credentials — no access token, `api_secret_key`, or victim credentials are required.

### Likelihood Explanation
Any merchant with the app installed can generate valid signed webhook payloads for their own shop and replay them with a forged shop header; this requires no special access beyond a routine app installation, satisfying the "unprivileged internet user" bar.

### Recommendation
Include the shop domain (and ideally the webhook id / topic) inside the value that is HMAC-verified, or otherwise cryptographically bind the `shop` header to the signature before it is trusted — e.g., derive the shop from a separately authenticated source, or reject/re-verify when the header-provided shop does not match a shop independently known to be tied to this signature. At minimum, document and enforce that `WebhookMetadata#shop` must not be used as a sole tenant key without additional server-side verification (such as confirming the shop has a matching, previously-registered webhook or session).

### Proof of Concept
1. Install the app on attacker-controlled shop A; have Shopify deliver any real webhook to the app endpoint, capturing `raw_body` and the resulting `X-Shopify-Hmac-Sha256` header (valid HMAC signed by the app's real `api_secret_key`).
2. Resend the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` (called in `Registry.process`) succeeds because it only checks `raw_body` against the HMAC [5](#0-4) .
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [6](#0-5)  and processes attacker-supplied content as if it originated from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
