### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant/shop identity from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, but `to_signable_string` — the value that is actually HMAC-verified — is only the raw request body. The shop-domain header is never included in the signed payload, so the identity that `Registry.process` hands to app webhook handlers is not cryptographically bound to the HMAC that "authenticates" the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain` header without any relation to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac` field, but never touches `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop` as the authoritative merchant identity for the event, without any additional check tying `shop` to the signed body: [4](#0-3) 

The identity binding that should hold is:
`shop_used_by_handler == shop_that_the_HMAC_signature_actually_authenticates`

But because `to_signable_string` excludes the `shop-domain` header, the equality collapses to:
`HMAC(raw_body, client_secret) == received_hmac` (independent of `shop` header value)

This means any request whose `raw_body` + `hmac` pair is valid (i.e., was genuinely generated and signed by Shopify for *some* shop/topic using this app's `client_secret`) will pass `HmacValidator.validate` regardless of what value is placed in the `shopify-shop-domain` header. An attacker who controls the delivery of the HTTP request to the app's webhook endpoint (e.g. a party who intercepts/replays a legitimate webhook delivery, or a proxy/CDN misconfiguration that lets an attacker resubmit a captured webhook payload with a modified shop-domain header) can cause the app to process a legitimately-signed webhook body under an attacker-chosen shop identity, since `shop` is passed unauthenticated into `WebhookMetadata` and used by the app's handler to select the tenant context.

### Impact Explanation
This breaks the tenant-identity binding at the point the app trusts a webhook as belonging to a specific merchant. Because `shop` is not covered by the same cryptographic guarantee as the body, an attacker who can influence the header (replay, HTTP request smuggling in front of the app, or a shared endpoint receiving webhooks for multiple apps/tenants) can attribute a validly-signed payload to a different tenant than the one Shopify actually generated it for — a cross-tenant confusion at the trust boundary the gem is responsible for enforcing (`Registry.process` is the exact place this trust decision is made). This matches the "cross-tenant access" Critical impact category, since the gem's stated guarantee ("HMAC validated webhook") is what host applications rely on to trust `data.shop`.

### Likelihood Explanation
Exploitation requires the ability to influence which raw HTTP request/headers actually reach the app's webhook endpoint with an otherwise-genuine (already-signed) body — e.g. via a shared reverse proxy, an intermediary that can replay a previously captured webhook to reuse its signature, or multiple apps/environments sharing a single client_secret and endpoint. This is a real but non-trivial threat model (it does not require possession of `api_secret_key`), which the analysis rules explicitly permit as it targets a documented identity-binding assumption of the gem, not a host-app misuse.

### Recommendation
Include the shop-domain (and ideally topic/webhook id) in the value that is HMAC-verified, or explicitly validate that the `shopify-shop-domain` header corresponds to session/tenant context the app expects before trusting `WebhookMetadata#shop` in `Registry.process`. At minimum, document that `Request#shop`/`shopify-shop-domain` is not covered by the HMAC and must not be used as a sole tenant-authentication signal by host applications; better, extend `to_signable_string` (or introduce a second explicit check) to bind the header value into the verified digest.

### Proof of Concept
1. Attacker obtains a validly Shopify-signed webhook delivery for shop A (raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`), for example via a legitimate webhook subscription in a shop they control, or by intercepting/replaying a delivery through a shared intermediary.
2. Attacker resends the exact same body `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B, client_secret)` and compares to `H` — this succeeds since `B` and `H` are unchanged. [4](#0-3) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)` and the host app processes/stores data under the victim shop's tenant context, despite the payload never having been signed for that shop.

Note: I could not locate `webhook_metadata.rb` in the indexed portion of the repo to confirm the exact `WebhookMetadata` struct fields beyond what's passed at the call site above; this is a minor gap that does not affect the core finding, which is fully supported by `request.rb`, `hmac_validator.rb`, and `registry.rb`.
