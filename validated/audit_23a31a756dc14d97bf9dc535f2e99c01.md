### Title
Webhook Shop-Domain Spoofing via HMAC That Only Covers the Request Body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `ShopifyAPI::Utils::HmacValidator.validate` verifies solely the payload bytes against the app's shared `api_secret_key`. The `x-shopify-shop-domain` header is never part of the signed material, yet `ShopifyAPI::Webhooks::Registry.process` passes it straight through as the trusted tenant identifier to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `HmacValidator.validate_signature` computes/verifies the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` accepts any request whose body/HMAC pair verifies, then forwards `request.shop` (parsed straight from the unauthenticated `x-shopify-shop-domain` header) into `WebhookMetadata`, which the app handler uses to identify which tenant the event belongs to: [3](#0-2) 

The identity binding the fix should enforce is: `shop_header == shop_bound_in_hmac`. Instead, the code enforces only `hmac == HMAC(secret, raw_body)`, with no cryptographic tie between the signature and the `shop` (or `topic`/`webhook-id`) header. Critically, `api_secret_key` is the app's single `client_secret`, shared across **every** shop that installs the app — it is not shop-specific. Consequently, any actor who can obtain one valid `(raw_body, hmac)` pair for a topic (e.g., by installing the app on their own store, an action available to any unprivileged internet user) can replay that exact body/HMAC combination to the app's webhook endpoint while substituting an arbitrary victim's `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the forged `shop` value to the handler as if the event genuinely originated from the victim's store.

This is exactly the documented, intended usage pattern (`docs/usage/webhooks.md`) — apps are told to trust `data.shop` from the handler once `Registry.process` succeeds — so the vulnerability is not caused by an application deviating from the gem's documented API; the gem's verification itself fails to bind the header to the signature.

### Impact Explanation
An attacker who legitimately installs the app on a shop they control gains a valid `api_secret_key`-signed body for any topic they can trigger on their own store (including mandatory GDPR topics like `customers/redact` or `shop/redact`, and ordinary topics like `orders/create`). By replaying that body/HMAC pair with a forged `x-shopify-shop-domain` header, the attacker can inject fabricated webhook events attributed to any other merchant using the same app — a cross-tenant data-integrity/access violation. Depending on how the host app's handler acts on `data.shop` (e.g., deleting data on `shop/redact`, creating records on `orders/create`), this can be leveraged to corrupt, delete, or fabricate another tenant's data without any credential belonging to that tenant.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on a shop they own (a normal, unprivileged onboarding action) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint — both trivially available to any internet user, with no access token, TLS interception, or social engineering required.

### Recommendation
Include the tenant-identifying headers (`shop`, and ideally `topic`/`webhook-id`) in the signable string used for HMAC validation, or otherwise cryptographically bind the header values to the verified payload, so the signature check enforces `shop_header == shop_covered_by_hmac` rather than validating body bytes alone.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com` and trigger a webhook topic of interest (e.g., `orders/create`); capture the raw POST body and its `x-shopify-hmac-sha256` value — both are valid because they were signed with the app's shared `api_secret_key`.
2. Replay this exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` (via `Registry.process`) accepts the request because it only checks `HMAC(secret, raw_body)`, ignoring the shop header: [3](#0-2) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, causing the app to process attacker-controlled data as if it originated from the victim tenant.
