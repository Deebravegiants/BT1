This confirms the asymmetry: in the OAuth flow, `AuthQuery#to_signable_string` explicitly includes `shop` in the signed payload, so the HMAC binds the shop identity to the signature [1](#0-0) . But in the webhook flow, `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop` is read from a separate, unsigned header (`shop-domain`) [2](#0-1) . `Registry.process` validates only this HMAC-over-body and then trusts `request.shop` as the tenant identifier passed to the handler [3](#0-2) .

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable string solely from the raw request body, while the `shop` (tenant identifier) is read from an entirely separate, unauthenticated header. `Registry.process` validates the HMAC over the body only, then hands the unverified `shop` value to the app's webhook handler as the tenant/shop context.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively [4](#0-3) . The `shop` accessor instead reads the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content [5](#0-4) . `Utils::HmacValidator.validate` computes and compares an HMAC over `to_signable_string` only [6](#0-5) . `Registry.process` calls this validator and then, once it passes, builds `WebhookMetadata` using `request.shop` as the trusted tenant identity for the handler, with no additional binding check [3](#0-2) .

This breaks the equality that should hold: `shop authenticated == shop used by the handler as tenant key`. The HMAC only proves "the app's secret key produced this exact body," not "the app's secret key vouches for this shop." Because the same `client_secret`/api secret is shared across every shop that installs a given public app, and Shopify signs webhooks with that shared secret for every installed shop (including a shop an attacker controls, e.g. a free development store), an attacker who installs the app on their own shop receives a genuinely HMAC-valid webhook request whose body/HMAC pair they fully control. They can then replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and `x-shopify-webhook-id`/`topic` as needed) with a victim shop's domain. The signature still validates because it never covered the shop header, so `Registry.process` will accept the request and invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

By contrast, the OAuth callback path does this correctly: `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameter string alongside `code`, `host`, `state`, and `timestamp` [1](#0-0) , so an attacker cannot swap the shop without invalidating the HMAC. The webhook path lacks this binding.

### Impact Explanation
Any app built on this gem that uses `request.shop` / `WebhookMetadata#shop` (or the `data.shop` field passed to handlers, as shown in the test suite's `FakeWebhookHandler` usage) to key per-tenant state — installing data for the wrong store, triggering compliance actions (`shop/redact`, `customers/redact`, `customers/data_request` are the very topics enumerated in `Registry::MANDATORY_TOPICS`), or dispatching shop-scoped business logic — can be made to process attacker-supplied data under an arbitrary victim shop's identity. This is a cross-tenant identity confusion: the handler believes the event genuinely originated from and pertains to the victim shop, when it did not. This matches the "cross-tenant access" impact class since the gem itself misattributes shop identity despite valid-looking signature verification.

### Likelihood Explanation
Any unprivileged internet user can trigger this: they need no access to the app's `client_secret`, access tokens, or any privileged account — only the ability to install the target public app onto a shop they control (trivial via a free Shopify development/partner store) to obtain one genuinely signed webhook body+HMAC pair, then replay it against the same endpoint with a forged `shop-domain` header.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the signed payload the HMAC covers, or otherwise cryptographically bind the shop header to the signature before trusting `request.shop` — mirroring how `Auth::Oauth::AuthQuery#to_signable_string` folds `shop` into its signable string. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop header value so `Utils::HmacValidator.validate` implicitly authenticates it.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` (a store they control), obtaining valid OAuth access and triggering a real webhook, e.g. `orders/create`, signed by Shopify with the app's real `client_secret`.
2. Attacker captures the raw POST body `B` and header `x-shopify-hmac-sha256: H` from that legitimate webhook delivery — `H` is a valid HMAC of `B` under the app's secret, matching what `Utils::HmacValidator.validate` will accept [7](#0-6) .
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and adjusts `x-shopify-webhook-id`/`x-shopify-topic` as desired.
4. `Webhooks::Request.new` parses these headers [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H` [9](#0-8) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [10](#0-9) , causing the app to act on the victim shop's tenant context using attacker-controlled body content, despite the victim never having sent this webhook.
