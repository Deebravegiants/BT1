### Title
Webhook `shop` (and `topic`/`webhook_id`) Identity Fields Not Covered by HMAC Verification, Enabling Cross-Tenant Confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and computes the HMAC over `@raw_body` only [1](#0-0) . `Request#to_signable_string` returns exclusively `@raw_body` [2](#0-1) , while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers that are never included in the signable string and therefore never covered by the HMAC signature [3](#0-2) .

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values — including `shop: request.shop` — and hands it to the registered `WebhookHandler#handle` [1](#0-0) . `WebhookMetadata.shop` is a plain `String` field with no further validation [4](#0-3) .

The broken identity binding is: **`shop` value cryptographically authenticated by the HMAC ≠ `shop` value the host application's handler actually acts on**. The HMAC only proves "this exact body was signed with the api secret at some point," it does not prove "this body originated for shop X." Any party who can obtain one valid `(raw_body, hmac)` pair — trivially, any merchant who installs the app and receives one legitimate webhook to their own endpoint, since HMAC uses only the app's static `api_secret_key`, not anything shop-specific — can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will construct a `WebhookMetadata` claiming the attacker-chosen shop, dispatching it to the handler as if it were an authentic event for that shop.

### Impact Explanation
Host applications built on this gem are expected to use `WebhookMetadata#shop` to look up the corresponding merchant session/tenant record and act accordingly (e.g., update per-shop data, revoke access, process GDPR redaction for `shop/redact`, `customers/redact`, `customers/data_request` mandatory topics). Because `shop` is not bound to the HMAC, an attacker who has captured/obtained one valid signed payload can cause the handler to process it under a different tenant's identity, resulting in cross-tenant data manipulation without ever needing the target's access token or credentials — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker needs only a single valid `(body, hmac)` pair, which is not secret-dependent per shop — any developer/merchant test account, or any captured request to a public webhook endpoint (headers are typically logged/visible to reverse proxies, WAFs, APM tools, etc., separately from the body), suffices. The endpoint accepting webhooks is by design internet-reachable and unauthenticated aside from the HMAC, so no privileged access is required to attempt the replay with a forged `shop-domain` header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload verification (or otherwise cryptographically bind them to the body, e.g. by validating that `shop` in the header matches a shop the app expects/has a stored session for) before constructing `WebhookMetadata`, rather than trusting header values as-is once only the body's HMAC is verified.

### Proof of Concept
```ruby
# Attacker has one legitimate webhook delivery for their own shop:
real_body    = '{"id":123}'
real_hmac    = OpenSSL::HMAC.digest("sha256", app_secret, real_body) # legitimately received once

# Replay with a forged tenant identity header:
forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary, attacker-chosen
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (HMAC only covers raw_body)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
``` [1](#0-0) [5](#0-4)
