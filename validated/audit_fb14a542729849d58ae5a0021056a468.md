### Title
Webhook Cross-Tenant Spoofing via Unsigned `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The gem's webhook signature verification computes the HMAC only over the raw request body, while the `shop` (tenant identity) is read from an unsigned HTTP header. Because the Shopify app secret (`api_secret_key`) used to sign webhooks is shared across *all* shops that install a given app, any merchant that installs the app can capture one of their own legitimately-signed webhooks and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim tenant. The signature still validates, but the handler receives the attacker's payload attributed to the victim's shop — a cross-tenant identity binding break.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the (unsigned) header, entirely independent of the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks the `hmac` field against `to_signable_string` (the raw body), never incorporating `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed into the application's webhook handler: [4](#0-3) 

Because `api_secret_key` is the same app-wide secret for every installed shop (not a per-shop secret), an HMAC computed over a given raw body is valid for that body regardless of which shop's header accompanies it. This breaks the intended identity equality:
`shop_that_signed_the_payload == shop_the_handler_believes_sent_it`

An attacker (any merchant who has installed the app — an "unprivileged" party with respect to other tenants of the same app) can:
1. Receive a legitimate webhook from Shopify for their own store (valid `hmac-sha256` over the body).
2. Replay the exact same raw body + hmac to the app's public webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` passes (body unchanged), and `Registry.process` invokes the handler with `shop: <victim-shop>` and the attacker's body content.

### Impact Explanation
This allows cross-tenant data/state confusion: an attacker can inject arbitrary (but self-authored) webhook payloads under a chosen victim tenant's identity for any topic the app has registered (e.g. `app/uninstalled`, `customers/data_request`, `orders/create`, etc.), causing the host application to execute tenant-scoped business logic (data writes, deletions, GDPR flows, session/token invalidation) against the wrong tenant. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any user who can install the app on at least one shop (a normal, unprivileged onboarding flow) can obtain arbitrarily many validly-signed webhook bodies of their choosing (by triggering events on their own store) and freely pair them with any `shop-domain` header value when POSTing to the app's public webhook endpoint, since that endpoint is by design reachable from the internet and the header is not authenticated at all.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signable content, or otherwise cryptographically tie the shop domain to the signature — e.g., include the `X-Shopify-Shop-Domain` header value in `to_signable_string`, or require the caller to independently confirm that `request.shop` corresponds to a shop with a stored, valid session/access token before processing, rejecting the webhook if the shop is not one the app is currently installed on. At minimum, document that `request.shop` must not be trusted for authorization decisions unless independently cross-checked against installed-shop state.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`.
2. Trigger any webhook topic (e.g. `orders/create`) on that store; capture the raw POST body and its `X-Shopify-Hmac-Sha256` header from Shopify.
3. Replay this exact HTTP request to the app's public webhook endpoint, keeping body and HMAC header identical, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because it only checks the (unmodified) raw body against the HMAC.
5. The registered handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, processing attacker-controlled data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
