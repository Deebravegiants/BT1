Audit Report

## Title
Fee withdrawn from caller before queue capacity is verified, causing fund loss on `QueueFull` in `Pallet::do_place_order` - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)

## Summary
In `do_place_order`, the caller's balance is debited via `T::Currency::withdraw` and the payment is recorded into `Revenue::<T>` inside a `try_mutate`/similar closure on the order-status storage item, but the actual enqueue via `queue.try_push(..)` — which is the only capacity check — happens afterward inside the same closure. Because `StorageValue::try_mutate` (or `try_mutate_exists`) only conditionally commits the storage item being mutated (e.g. `OrderStatus`/`QueueStatus`) and provides no rollback guarantee for other storage side effects performed within the closure (such as `Currency::withdraw` writing to `Balances::Account`, or `Revenue::<T>::mutate`), a late `QueueFull` failure from `try_push` leaves the withdrawal and revenue bookkeeping permanently committed while no order is enqueued.

## Finding Description
The sequence inside `do_place_order` computes the spot price from the current traffic factor, immediately calls `T::Currency::withdraw(&sender, spot_price, WithdrawReasons::FEE, existence_requirement)`, records the amount into `Revenue::<T>`, and only then attempts `order_status.queue.try_push(..)`. `try_push` on a `BoundedVec` can return `Err`, mapped to `Error::<T>::QueueFull`, when the queue is already at `on_demand_queue_max_size`. The critical flaw is architectural: FRAME's `StorageValue::try_mutate` semantics only guard the storage value passed into the closure — they do not create a generic all-or-nothing transaction over every storage write performed inside the closure. `Currency::withdraw` and `Revenue::<T>::mutate` are independent storage mutations that commit as soon as they execute, regardless of whether the enclosing closure ultimately returns `Ok` or `Err`. This is precisely the reason Substrate exposes the opt-in `#[transactional]` attribute / `with_storage_layer` helper — without it, a dispatchable returning `Err` does not automatically undo storage writes made earlier in its execution. ## Impact Explanation
An unprivileged signed caller loses real funds with no order recorded and no parachain block scheduled: the withdrawal into `Revenue::<T>` is not offset by a corresponding queue entry, producing a permanent accounting desync and direct fund loss for the caller. This is a concrete, in-scope impact matching a fee-charged-but-service-not-rendered bug class, not a theoretical or cosmetic issue.

## Likelihood Explanation
The bug is triggerable by any ordinary user with sufficient balance and no special privileges. The only precondition is that the on-demand queue is one slot away from `on_demand_queue_max_size` when the extrinsic executes — a state that occurs naturally under contention, or that an attacker can engineer themselves by submitting `max_size - 1` prior orders before making the final call that is expected to fail with `QueueFull`. No signature forgery, governance action, or origin confusion is required, and the scenario is reproducible deterministically via a unit test that fills the bounded queue to capacity and then calls `place_order_allow_death` once more, observing that the caller's balance and `Revenue::<T>` change despite the extrinsic returning `Err(Error::<T>::QueueFull)`.

## Recommendation
Validate queue capacity (`order_status.queue.len() < on_demand_queue_max_size`, or perform the `try_push` first against a scratch copy) before invoking `T::Currency::withdraw` or mutating `Revenue::<T>`. Alternatively, wrap the entire withdraw-then-enqueue sequence in `#[transactional]` or `frame_support::storage::with_storage_layer` so any `Err` returned mid-sequence atomically reverts all nested storage writes, including the Balances withdrawal and `Revenue::<T>` update.

## Proof of Concept
In `polkadot/runtime/parachains/src/on_demand/tests.rs`:
1. Configure the mock runtime with a small `on_demand_queue_max_size` and fund an account `ALICE`.
2. Fill the on-demand queue to full capacity via successful `place_order_allow_death` calls from other funded accounts.
3. Record `ALICE`'s balance and `Revenue::<T>` totals before the final call.
4. Call `OnDemand::place_order_allow_death(RuntimeOrigin::signed(ALICE), max_amount, para_id)`.
5. Assert the call returns `Err(Error::<T>::QueueFull.into())`, yet `Balances::free_balance(ALICE)` is reduced by `spot_price` and `Revenue::<T>::get()` is increased, while `OrderStatus::<T>::get().queue.len()` remains unchanged and no `OnDemandOrderPlaced` event is emitted — demonstrating the fund-loss/accounting desync.
