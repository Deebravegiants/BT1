## Analysis

This is a direct analog of the reported bug class: the reported issue is about code that hardcodes an assumption about decimal relationships (assumes 18 decimals) which breaks scaling arithmetic when a token doesn't match that assumption. `pallet-hyper-fungible-token`'s decimal-conversion helpers make the same class of mistake — they assume the EVM-side token always has *at least as many* decimals as the local substrate asset, and silently degrade to a no-op scale factor when that assumption is false. [1](#0-0) 

The helper functions are:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
	let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both use `erc_decimals.saturating_sub(local_decimals)`. This only produces a correct scale factor when `erc_decimals >= local_decimals`. When `erc_decimals < local_decimals` (a token registered with fewer EVM decimals than local decimals — e.g., local asset registered at 18 decimals while the corresponding EVM token uses 6 decimals), `saturating_sub` returns `0`, so the "scale factor" becomes `10^0 = 1` — i.e., no scaling is applied at all, even though scaling is required.

`convert_to_erc20` is called from the `send` extrinsic, which any signed user can call, and its output is dispatched as the `Message.amount` that the peer `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract mints on `onAccept`: [2](#0-1) 

Concretely, with `local_decimals = 18` and `erc_decimals = 6` (a perfectly plausible registration, the reverse of the documented BRIDGE example which is 18 EVM / 12 local), a user escrows/burns `1 * 10^18` raw local units (1 token) but `convert_to_erc20` returns `erc20_amount = 10^18` unscaled instead of the correct `10^6`. The EVM `HyperFungibleToken` contract then mints `_mint(beneficiary, message.amount)` verbatim: [3](#0-2) 

Since the EVM contract's token has only 6 decimals, minting `10^18` raw units is `10^12` whole tokens instead of `1` — an unbacked mint of the destination asset by a factor of `10^(local_decimals - erc_decimals)`, fully reachable by any user calling `send` on a token pair configured with `erc_decimals < local_decimals`.

The mirrored `convert_to_balance` bug (used in both `on_accept` and `on_timeout`) causes the opposite failure in the same configuration: an inbound ERC20-denominated amount is credited to the beneficiary without being scaled up to local precision, permanently under-crediting (effectively burning) user funds instead of releasing/minting the correct amount: [4](#0-3) [5](#0-4) 

This contrasts with the `VWAPOracle._normalizeAmount` helper elsewhere in the codebase, which correctly branches on both directions (`decimals < 18` vs `decimals > 18`), showing the project is otherwise aware of this class of bug — the hyper-fungible-token pallet's helpers are the outlier that got it wrong in one direction only. [6](#0-5) 

### Title
Hyper Fungible Token pallet's decimal scaling helpers silently skip scaling and cause unbacked minting or fund loss when the EVM token has fewer decimals than the local asset - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_erc20` and `convert_to_balance` in `pallet-hyper-fungible-token` compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`, which silently becomes `0` (no scaling) whenever `erc_decimals < local_decimals`, instead of correctly dividing down. This is the same root-cause class as "Protocol assumes debt token has 18 decimals" — an implicit, unchecked assumption about a fixed decimal relationship baked into arithmetic.

### Finding Description
`convert_to_erc20(value, erc_decimals, local_decimals)` multiplies by `10^(erc_decimals.saturating_sub(local_decimals))` to convert a locally-denominated `u128` balance into the ERC20 `U256` amount dispatched to the paired EVM contract. This formula is only correct when `erc_decimals >= local_decimals`. When a token pair is registered with `erc_decimals < local_decimals` (a fully supported, non-adversarial configuration per the pallet's own documentation, which states decimals "may differ" between chains), `saturating_sub` clamps to `0`, and the function returns the raw local-unit value unscaled — i.e. `10^(local_decimals - erc_decimals)` times larger than it should be.

This value flows directly into the `Message.amount` field of the `DispatchPost` sent to the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken`/`BridgeToken` contract, which mints (or releases escrowed) `message.amount` verbatim to the beneficiary with no additional scaling on the EVM side. The symmetric `convert_to_balance` function has the same defect in the opposite direction, causing incoming EVM→substrate transfers to be credited at `10^-(local_decimals - erc_decimals)` of the correct amount when the same decimal relationship holds.

### Impact Explanation
This is a High/Critical-severity unbacked-mint / fund-loss bug:
- Outbound direction (`convert_to_erc20`): a user who escrows/burns `N` local-denomination tokens can cause the destination EVM contract to mint `N * 10^(local_decimals - erc_decimals)` tokens — an unbacked mint that can be redeemed/transferred/sold on the destination chain, draining value from the bridge with no corresponding backing.
- Inbound direction (`convert_to_balance`): legitimate inbound transfers (or the refund path on timeout) get credited at a small fraction of their true value, causing silent, permanent loss of user funds.

Both paths are triggered through the ordinary, unprivileged `send` extrinsic and the standard ISMP `on_accept`/`on_timeout` delivery flow — no malicious admin or governance action is required, only a token pair configuration where the EVM-side decimals are fewer than the local asset's decimals (a common and reasonable configuration, e.g., a 6-decimal EVM stablecoin paired with an 18-decimal local asset representation).

### Likelihood Explanation
Likelihood is high for any deployment that registers a token pair with `erc_decimals < local_decimals`. This is not a contrived edge case: many real tokens (e.g., 6-decimal USDC/USDT) would naturally be registered this way if the local asset uses 18 or another higher decimal count for internal precision. The bug requires no attacker privilege beyond calling the public `send` extrinsic on such a pair.

### Recommendation
Rewrite both helpers to handle both scaling directions explicitly, analogous to `VWAPOracle._normalizeAmount`:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the mirror image for `convert_to_balance`. Add test coverage for the `erc_decimals < local_decimals` case (the current test suite only exercises `erc_decimals: 18, local_decimals: 10`, i.e. the direction that happens to work).

### Proof of Concept
1. Governance registers a token via `register_token` with `native = false`, `local_decimals = 18` (e.g. a pallet-assets asset created with 18 decimal places), and `ChainConfig { decimals: 6 }` for an EVM destination (a 6-decimal stablecoin representation) — a valid, non-malicious configuration.
2. Any user with `1 * 10^18` of the local asset calls `send` with `amount = 10^18` (representing "1 token").
3. In `send`, `erc_decimals = 6`, `decimals = 18`; `convert_to_erc20(10^18, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18u8) as u32) = 10u128.pow(0) = 1`, so `erc20_amount = 10^18` (unscaled).
4. The dispatched `Message.amount = 10^18` is delivered to the EVM contract's `onAccept`, which calls `_mint(beneficiary, 10^18)`. Since the EVM token has 6 decimals, this mints `10^12` whole tokens instead of the intended `1` — the beneficiary receives a mint inflated by `10^12`, unbacked by the single token burned/escrowed on the source chain.     function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
