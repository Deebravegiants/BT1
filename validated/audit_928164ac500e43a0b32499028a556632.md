### Title
Unauthenticated arbitrary `RuntimeCall` deserialization and dispatch in `hyper-fungible-token::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` in the hyper-fungible-token pallet SCALE-decodes attacker-supplied bytes (`message.data`) directly into `SubstrateCalldata` and then into `T::RuntimeCall` — the runtime's entire dispatchable call enum — and immediately `.dispatch()`s it. When the embedded `signature` field is `None`, no cryptographic check is performed at all: the dispatch `origin` is derived purely from the attacker-controlled `message.from` bytes via a keyless, deterministic conversion. This mirrors the YamlBeans class of bug: untrusted bytes are deserialized straight into an executable "class" (a `RuntimeCall` variant) whose type and contents are entirely controlled by whoever authored the cross-chain message, and execution proceeds without proof that the invoker owns the identity/origin being impersonated.

### Finding Description
In `on_accept`, after minting/transferring the bridged asset, optional calldata is processed: [1](#0-0) 

If `substrate_data.signature` is `Some`, the code verifies an `MultiSignature` over `(nonce, runtime_call)` against a key tied to `beneficiary`: [2](#0-1) 

But if `signature` is `None`, the origin is derived purely from `message.from` with **no signature check whatsoever**: [3](#0-2) 

The runtime call is then SCALE-decoded and dispatched as that unverified origin: [4](#0-3) 

`message.from` and `message.data` are both fields of the ABI-decoded `Message` struct taken from `PostRequest.body` — fully attacker-controlled application payload, distinct from the ISMP-level `from`/`source` pair that is only used to authenticate which token contract sent the request via `ContractToAsset::<T>::get(source, &from)`: [5](#0-4) 

The EVM→Substrate account mapping used to build the dispatch origin is a trivial, keyless zero-pad with no proof-of-possession requirement: [6](#0-5) 

Because `BaseCallFilter` only filters call *types* that are globally disabled, not the relationship between the deserialized call and its origin, any dispatchable that a `Signed` origin is permitted to call (transfers, asset operations, governance voting weight, staking, proxy management, etc.) can be triggered against whichever account the pallet derives from `message.from`.

### Impact Explanation
This allows an unprivileged party who can get a `PostRequest` delivered to this module (any relayer/sender able to construct a valid ISMP request from a registered source contract) to encode an arbitrary `RuntimeCall` and have it dispatched as `RawOrigin::Signed` for an account they select via `message.from`, without proving control of that account's key. If the destination-chain application layer (e.g. a custom integrator, gateway, or future source-chain contract change) ever allows `message.from` to diverge from the true transaction signer, this becomes full account impersonation: draining a victim account's balance/assets, transferring away a victim's asset holdings, or performing any other `Signed`-gated action as that victim — i.e., theft of funds / unauthorized app action, matching CWE-502's "attacker controls both class and data" pattern.

### Likelihood Explanation
The path is reachable directly from a single relayed cross-chain PostRequest with non-empty `data` and no `signature`, which is the pallet's documented "unsigned" execution mode (intended for the sender acting as themselves). The residual risk is contingent on whether the source-chain contract that constructs `message.from` strictly and immutably binds it to `msg.sender` for every currently and future registered source contract in `ContractToAsset`; the destination pallet itself performs no independent verification, so any weakening of that off-chain/contract-side invariant (multi-hop relaying, alternate integrations, future contract upgrades) directly translates into arbitrary-account call dispatch with no additional safeguard on the receiving pallet.

### Recommendation
Require a valid `signature` (verified against the actual account being impersonated, with nonce-based replay protection) for every non-empty `data` payload; remove the unsigned/`None`-signature dispatch branch, or at minimum restrict it to a `RuntimeOrigin` that carries no ambient authority beyond what the bridged transfer itself grants (e.g., a dedicated sandboxed pallet-account per bridge instead of `RawOrigin::Signed(origin)` mapped onto arbitrary user AccountIds).

### Proof of Concept
1. Attacker controls (or triggers) a `PostRequest` from a registered `ContractToAsset` source with `body` ABI-encoding a `Message` where `to` = victim (for the token portion, irrelevant to this path) and `from` = the 20/32-byte identifier of a victim account whose destination-chain `AccountId` the attacker wants to impersonate.
2. `data` is set to a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary Signed-callable call, e.g. Balances::transfer_all(attacker, false)> }`.
3. `on_accept` mints/transfers the bridged token normally, then reaches the unsigned branch, computing `origin = EvmToSubstrate::convert(H160::from(message.from))` (or a direct 32-byte copy for substrate sources) with zero signature verification.
4. `T::RuntimeCall::decode` succeeds, passes `BaseCallFilter`, and `runtime_call.dispatch(RawOrigin::Signed(origin))` executes the attacker-chosen call as the victim's derived account, e.g. transferring all of the victim's balance to the attacker. [7](#0-6)

/// Converts an EVM address to a substrate AccountId
pub trait EvmToSubstrate<T: frame_system::Config> {
	fn convert(addr: H160) -> T::AccountId;
}

/// Default implementation: zero-pads the 20-byte address into a 32-byte AccountId
impl<T: frame_system::Config> EvmToSubstrate<T> for ()
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn convert(addr: H160) -> <T as frame_system::Config>::AccountId {
		let mut account = [0u8; 32];
		account[12..].copy_from_slice(&addr.0);
		account.into()
	}
}
