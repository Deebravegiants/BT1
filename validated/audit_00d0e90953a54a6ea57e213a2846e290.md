Based on my review, I found a legitimate analog to the reported bug class in this gem's webhook verification code.

### Title
Webhook shop-domain identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an unauthenticated HTTP header, while the HMAC that `ShopifyAPI::Webhooks::Registry.process` verifies covers only the raw request body. This breaks the intended binding `hmac_verified_bytes == identity_bytes`, allowing an attacker who controls one shop where the app is installed to replay a genuinely-signed webhook body while relabeling it as belonging to a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are read straight from attacker-controllable HTTP headers, with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates only the body-bound HMAC via `HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`/`request.webhook_id`) to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` recomputes the HMAC solely over `to_signable_string` (the body) using `Context.api_secret_key`: [4](#0-3) 

Because Shopify apps use a single `client_secret` (`api_secret_key`) shared across every shop that installs the app, an attacker who installs the app on their own shop can:
1. Trigger a webhook delivery to their own endpoint (or replicate `raw_body`/`hmac` from a delivery they legitimately received) with an attacker-influenced body (e.g. an `orders/create` payload containing attacker-chosen note/metadata fields).
2. Replay that exact `(raw_body, hmac)` pair to the merchant app's webhook endpoint, only changing the `X-Shopify-Shop-Domain` header to a victim shop's domain.
3. `HmacValidator.validate` still succeeds because the signature check never looks at the shop-domain header — it only re-hashes `raw_body` — so `Registry.process` dispatches the handler believing the event originated from the victim shop.

The identity equality the gem should enforce is `hmac_signed_bytes ⊇ shop_identity_bytes`, but here `hmac_signed_bytes = raw_body` while `shop_identity_bytes` comes from an unsigned header, i.e. exactly the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" mismatch class.

### Impact Explanation
This crosses a tenant boundary: an attacker with a legitimate install on Shop A can make the consuming application process attacker-controlled webhook content while attributing it to Shop B (any shop domain, not necessarily one the attacker has access to). Depending on how the host app's `handler.handle` uses `WebhookMetadata#shop` (e.g., to select which merchant's DB record to write/update, or to enqueue store-specific side effects), this can lead to cross-tenant data injection/corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant/installer of the target app (a standard, low-privilege position for any public or unlisted Shopify app) — no access to the app's `client_secret`, no privileged account, and no host application misuse beyond consuming the gem's documented `shop`/`WebhookMetadata` API as intended. This is a realistic, low-effort scenario for any app that keys business logic off `WebhookMetadata#shop`.

### Recommendation
Do not treat `request.shop` (or `topic`/`webhook_id`) as trusted merely because `HmacValidator.validate` succeeded. Either:
- Extend `to_signable_string` (or add a secondary check) so the shop-domain header is cryptographically bound to the verified payload, or
- Require/encourage callers to independently confirm `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it, and document this explicitly as a caller responsibility in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimately delivered webhook `raw_body` + `X-Shopify-Hmac-Sha256` for a topic the attacker can influence (e.g. `orders/create` with attacker-controlled order note/attributes).
2. Send an HTTP request to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared `api_secret_key`.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to act on attacker data as if it came from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
