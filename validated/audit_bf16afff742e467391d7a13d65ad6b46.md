This confirms the vulnerability. The gem's documentation explicitly instructs handlers to use `data.shop` (from `Registry.process`) as the tenant identifier, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [1](#0-0) , while `Registry.process` derives that value directly from `request.shop`, an unauthenticated HTTP header [2](#0-1) .

### Title
Webhook `shop` field used for tenant identification is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies the HMAC of an incoming webhook and then passes the request's `shop` value on to the app's handler as the tenant identifier. However, the HMAC only signs the raw request body, not the `shop` (or `topic`/`webhook-id`) header, so an attacker who can produce one valid `(raw_body, hmac)` pair can reuse it with an arbitrary `shopify-shop-domain` header to make the gem report an attacker-chosen shop to the handler.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)` and, on success, immediately trusts `request.shop`: [2](#0-1) 

`Webhooks::Request#shop` returns the raw `shopify-shop-domain`/`x-shopify-shop-domain` header value verbatim, with no cross-check against the HMAC: [3](#0-2) 

Crucially, `Webhooks::Request#to_signable_string` — the data that is actually HMAC-verified — is only the raw body: [4](#0-3) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., just `@raw_body`) and compares it to the `hmac` header; it never considers `shop`, `topic`, or `webhook-id`: [5](#0-4) 

The binding the gem should enforce is:
`hmac == HMAC(secret, raw_body ‖ shop ‖ topic ‖ webhook_id)`
but what it actually enforces is:
`hmac == HMAC(secret, raw_body)`

Because `shop` sits outside the signed scope, `request.shop == <attacker-chosen value>` can diverge from `request.shop == <the shop Shopify actually generated this payload for>` while `HmacValidator.validate` still returns `true`. Any unprivileged actor who can obtain one legitimate `(raw_body, hmac)` pair — trivially available to them by simply installing the app on their own store and capturing the webhook Shopify sends them — can replay that exact body and HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `Registry.process` will treat the HMAC as valid and hand the handler `shop: "<victim-shop>.myshopify.com"` alongside the attacker's own webhook body/topic.

### Impact Explanation
This breaks the shop/tenant identity binding that the entire webhook processing model relies on, and the gem's own documented usage pattern (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) directly channels this untrusted value into tenant-scoped application logic. Depending on how the host app persists or attributes webhook data (a documented, intended use of `data.shop`), this enables cross-tenant data confusion/corruption — an attacker-controlled shop value being associated with attacker-controlled body content, injected into another merchant's tenant scope.

### Likelihood Explanation
Likelihood is high: no privileged credentials, access tokens, or `client_secret` access are required. An attacker only needs their own (unprivileged) shop with the app installed to receive one legitimate webhook body+HMAC pair, which they can then replay against the same public webhook endpoint with a forged `shop` header, since nothing in the gem re-derives or binds `shop` to the signed payload.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed scope, or independently verify the `shop` header against a value obtained through an authenticated channel (e.g., cross-check against the shop associated with the webhook subscription/registration) before passing it to the handler. At minimum, document that `data.shop` from `WebhookMetadata` is not cryptographically bound to the signed body and must not be trusted for authorization/tenant-attribution decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `client_secret`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the *same* body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation passes because `shop` is never part of `to_signable_string`.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, so the app's handler processes attacker-controlled content under the victim shop's identity, exactly matching the documented usage `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`.
