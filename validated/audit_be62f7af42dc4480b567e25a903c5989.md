## Analysis

The reentrancy bug in the external report describes accounting/state that is mutated based on an untrusted external call before the internal invariant is fully enforced — i.e., a check is satisfied against stale/partial state instead of the true, complete state. The closest analog in this gem's in-scope code (`lib/shopify_api/**`, excluding generated REST resources) is an identity-binding break in webhook verification: the field used to authenticate/attribute a webhook (`shop`) is **not** covered by the HMAC signature that is actually verified.

### Root cause

`ShopifyAPI::Webhooks::Request` derives the tenant identity from an HTTP header, while `to_signable_string` (the only material that is HMAC-verified) is limited to the raw body: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature strictly over `verifiable_query.to_signable_string`: [3](#0-2) 

For `Request`, `to_signable_string` returns `@raw_body` only — the `shopify-shop-domain` header is never part of the signed material. This is exactly the identity-binding break named in the rules: *"a field acted on but not covered by the HMAC"*. The equality that should hold is:

`shop_attributed_to_payload == shop_that_cryptographically_produced_the_payload`

but the gem instead enforces only:

`hmac_over(body) == hmac_over(body)` while `shop = header["shop-domain"]` (unauthenticated)

### Exploit path (unprivileged actor)

1. An attacker who is merely a regular merchant installing the public app receives legitimate webhook deliveries for their **own** shop. These are correctly signed (the app's shared `client_secret`/HMAC secret authenticates *any* shop's webhook body, since Shopify signs with the app's secret regardless of which shop the webhook is for).
2. The attacker captures one such delivery (body + `X-Shopify-Hmac-Sha256` header) — no TLS interception or credential theft needed; it's their own webhook traffic to their own endpoint.
3. The attacker replays that exact body/HMAC pair to the app's public webhook endpoint, but swaps only the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to a victim shop's domain.
4. `HmacValidator.validate` still succeeds, because the shop-domain header was never covered by the signature. `Request#shop` then reports the victim's domain to the host application's webhook handler/dispatcher.

This lets an unprivileged actor cause the host application to process attacker-supplied webhook data under a victim tenant's identity — a cross-tenant confusion driven purely by this gem's failure to bind `shop` to the signed payload.

## Answer

### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook delivery by validating an HMAC over the raw body only, while the shop identity used by the host application (`Request#shop`) is read from the `shop-domain` HTTP header, which is not covered by that HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `Utils::HmacValidator.validate` verifies the signature strictly against that signable string [3](#0-2) . Meanwhile `Request#shop` is populated directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic tie to the body or the HMAC [4](#0-3) . Consequently, the gem's own verification primitive lets any valid `(body, hmac)` pair be paired with an arbitrary, attacker-chosen `shop` value and still pass `validate`.

### Impact Explanation
This is a cross-tenant identity confusion: a valid signature for shop A's webhook body can be relabeled as belonging to shop B purely by changing an unauthenticated header, since the binding between "the bytes that were verified" and "the shop attributed to those bytes" does not exist in this gem. Any host application that trusts `Request#shop` after a passing `HmacValidator.validate` call inherits this tenant-confusion, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitability only requires an unprivileged actor who has installed the public app (or otherwise obtained one legitimately-signed webhook body+HMAC pair for any shop) and can send an HTTP request to the app's public webhook endpoint with a modified shop-domain header — no `api_secret_key`, access token, or privileged access is required. The attack is a straightforward header substitution replay.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before exposing `Request#shop` to consumers, so that verification failure occurs if the attributed shop does not match the shop that produced the signed body.

### Proof of Concept
1. Install the target app as Merchant A; capture a legitimate webhook POST to the app's webhook endpoint, noting `raw_body` and the `X-Shopify-Hmac-Sha256` header value.
2. Resend the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the same endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Observe that `ShopifyAPI::Utils::HmacValidator.validate` (invoked via `Request#hmac`/`to_signable_string`) still returns `true` [5](#0-4) , and `Request#shop` reports `victim-shop.myshopify.com` [4](#0-3) , causing the host application to process Merchant A's payload as if it belongs to the victim shop.
