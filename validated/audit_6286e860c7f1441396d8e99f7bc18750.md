Confirmed: the JWT replay-guard for HTTP-trigger requests in `WorkflowMetadataHandler.Authorize` has a TOCTOU (check-then-act) race that lets the same one-time JWT authorize multiple concurrent workflow trigger requests — the same "quota/one-time-use state not updated atomically" bug class as the QVBaseStrategy report (there `voiceCreditsCastToRecipient` is checked but never decremented; here `jti` "already used" is checked but not recorded atomically with the check).

### Title
JWT replay protection race condition allows a single one-time trigger token to authorize multiple concurrent workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` is supposed to guarantee that each signed HTTP-trigger JWT (`jti`) can authorize exactly one workflow execution request. The "used" check and the "mark used" write are two separate, non-atomic operations guarded by different locks, so concurrent requests carrying the same JWT can both pass the check before either records usage.

### Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` to check whether the JWT was used, and only after passing all other checks calls `h.jwtCache.recordUsage(claims.ID)`: [1](#0-0) 

`isReplay` takes an `RLock` and only reads the map; `recordUsage` takes a separate `Lock` later: [2](#0-1) 

Because the check (`isReplay`) and the write (`recordUsage`) are not performed under a single critical section, two goroutines handling two concurrent `HandleUserTriggerRequest` calls with the identical `req.Auth` JWT can both call `isReplay` and both get `false` (not yet recorded) before either calls `recordUsage`. Both then pass authorization and proceed to trigger workflow execution. This is the same root-cause pattern as the reported Solidity bug: a "one-shot" resource (voice credits / a one-time JWT) is checked for availability but the consumption/decrement step happens too late and is not atomic with the check, so the guard can be bypassed by repeating the action before the state update lands.

`HandleUserTriggerRequest` calls `authorizeRequest` → `workflowMetadataHandler.Authorize` before setting up the per-request-ID callback dedupe (`setupCallback`), and request-ID deduplication uses a *different* key (`req.ID`) than the JWT `jti`, so an attacker/client sending the same signed JWT with two different request IDs concurrently is not blocked by the request-ID dedupe check: [3](#0-2) [4](#0-3) 

The existing tests only validate the sequential (non-concurrent) replay case (`t.Run("duplicate JWT token and request ID", ...)`), which succeeds because the two `Authorize` calls happen one after another, not concurrently: [5](#0-4) [6](#0-5) 
No test exercises truly concurrent `Authorize` calls with the same `jti`, so the race is untested and unguarded.

### Impact Explanation
A single signed trigger JWT is intended to authorize one workflow execution. Exploiting the race lets an unprivileged client (any holder of a valid signer key for a workflow, which is the normal caller of this endpoint) trigger the *same* workflow execution twice (or more) concurrently from one token — duplicate job runs, duplicate downstream side effects (e.g., duplicate on-chain/off-chain actions performed by the workflow), and resource/cost amplification, while bypassing the intended "one-time-use" security control. This matches the "unauthorized job run" / "quota bypass" impact classes called out for this bug class.

### Likelihood Explanation
Requires the attacker to send the same valid signed JWT in two (or more) requests essentially simultaneously — trivially achievable by any client since HTTP requests are naturally concurrent and the caller controls timing/parallelism of its own requests. No special privilege beyond already holding a workflow-authorized signer key is needed (the same access level normally required to trigger the workflow once), so likelihood is high for a caller motivated to double-trigger.

### Recommendation
Make the check-and-record atomic: combine `isReplay` + `recordUsage` into a single method (e.g. `checkAndRecord(jti)`) that holds the write lock for the full check-then-insert sequence, analogous to the pattern already used correctly in `core/capabilities/vault/request_replay_guard.go`'s `CheckAndRecord`, which performs the existence check and the map write under one `mu.Lock()`: [7](#0-6) 
Apply the same atomic pattern to `jwtReplayCache` in `workflow_metadata_handler.go` so `isReplay`/`recordUsage` cannot be split by concurrent goroutines.

### Proof of Concept
1. Register a workflow and authorized signer key as in `TestWorkflowMetadataHandler_Authorize`.
2. Create one signed JWT (`tokenString`) for a given request digest.
3. Spawn two goroutines that both call `handler.Authorize(workflowID, tokenString, req)` at the same time (e.g., synchronized with a `sync.WaitGroup` and a barrier channel to maximize the chance both goroutines execute `isReplay` before either executes `recordUsage`).
4. Observe that both goroutines can return `nil` error (both succeed), each yielding an `AuthorizedKey` and letting `HandleUserTriggerRequest`/`sendWithRetries` fan out and trigger the workflow twice with distinct request IDs but the same, supposedly one-time, JWT — instead of the second call returning `"JWT token has already been used"` as intended.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
