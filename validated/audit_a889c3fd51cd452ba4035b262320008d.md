## Analog Finding Confirmed

### Title
Missing validation of `VestingSchedule` timestamps in `LockupContract::new` allows bypassing the vesting lock via integer underflow - (File: `lockup/src/lib.rs`, `lockup/src/types.rs`, `lockup-factory/src/lib.rs`)

### Summary
The external report flags missing timestamp bounds-checking in an auction's `createAuction`. The same root-cause class (unvalidated, attacker-controlled start/cliff/end timestamps at a public creation entrypoint) exists in the NEAR `lockup` contract's vesting-schedule initialization. A validation helper `VestingSchedule::assert_valid()` exists in the codebase, but it is never invoked anywhere in the production `lockup/src/lib.rs`, so a caller-supplied `VestingSchedule` with out-of-order timestamps is accepted unchecked.

### Finding Description
`VestingSchedule::assert_valid()` enforces `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp`: [1](#0-0) 

However, `LockupContract::new` builds `VestingInformation::VestingSchedule(vs)` directly from the caller-supplied `vesting_schedule` argument without ever calling `assert_valid()`: [2](#0-1) 

A grep across the production crate confirms `assert_valid()` is defined only in `lockup/src/types.rs` and is not referenced anywhere else in `lockup/src/*.rs` (it is unrelated calls in `staking-pool`/`staking-pool-factory` that use their own `assert_valid`, not this one). This makes the check effectively dead code — the invariant it documents is never enforced at the only entrypoint (`new`) where the schedule is set.

This `vesting_schedule` argument is attacker-controlled: it is forwarded verbatim from the public, unauthenticated `LockupFactory::create` method, which has no owner/foundation gate and is callable by any account that attaches the minimum deposit: [3](#0-2) 

The factory's own test suite shows the future contract owner itself is the caller of `create`, i.e. the party whose funds are meant to be constrained by the vesting schedule controls the schedule's parameters: [4](#0-3) 

Because no ordering is enforced, an owner can submit a `VestingSchedule` where `start_timestamp > end_timestamp` (while still satisfying `cliff_timestamp` falling between the reported cliff bound and end). `get_unvested_amount` then computes:
```
total_time = end_timestamp - start_timestamp
```
using unsigned 64-bit subtraction: [5](#0-4) 

If `end_timestamp < start_timestamp`, this subtraction underflows. NEAR contracts are compiled in `--release` mode for the `wasm32` target, where Rust integer overflow/underflow silently wraps instead of panicking, producing an astronomically large `total_time`. The resulting `unvested_amount = lockup_amount * time_left / total_time` collapses toward zero, meaning `get_locked_amount()` — which every owner-facing balance/transfer/staking check relies on — reports the account as essentially fully vested immediately, regardless of the schedule the Foundation believed it had agreed to.

### Impact Explanation
This lets an unprivileged owner of a to-be-created lockup contract choose a malformed vesting schedule at contract creation and immediately (or far earlier than intended) unlock funds that are supposed to vest gradually, defeating the entire purpose of the vesting/clawback mechanism relied upon by the Foundation for early-termination refunds. This matches the in-scope impact: "Share, reward, vesting, refund... accounting divergence that lets an unprivileged user over-credit value... withdraw more than fair entitlement."

### Likelihood Explanation
Low-to-medium: it requires the party calling `LockupFactory::create` (which, per the factory's own tests, can be the future owner) to deliberately submit an inverted `VestingSchedule`. There is no on-chain check preventing it, so it is fully reachable through the public entrypoint without any privileged role — the same "requires misconfiguration/misuse of unchecked input" likelihood profile the original report describes for `createAuction`.

### Recommendation
Call `vesting_schedule.assert_valid()` inside `LockupContract::new` (and anywhere else a raw `VestingSchedule` is accepted, e.g. `VestingScheduleOrHash::VestingSchedule` branch) before storing it as `VestingInformation::VestingSchedule`. Additionally, consider bounding `end_timestamp - start_timestamp` to a sane minimum/maximum duration and rejecting degenerate schedules, mirroring the recommendation in the original report.

### Proof of Concept
1. Attacker (future lockup owner) calls `LockupFactory::create` with `vesting_schedule = Some(VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T+100, cliff_timestamp: T+50, end_timestamp: T+80 }))` and sufficient attached deposit.
2. The factory forwards this unchanged to the deployed lockup contract's `new` function: [6](#0-5) 
3. `LockupContract::new` stores it without validation: [7](#0-6) 
4. Once `block_timestamp` falls between `cliff_timestamp` and `end_timestamp` (a narrow, attacker-chosen window), `get_unvested_amount` computes `total_time = end_timestamp - start_timestamp` which underflows (u64 wraps in release mode), causing the division to yield ~0 unvested tokens, i.e. the owner's balance is treated as immediately liquid: [8](#0-7)

#[derive(BorshDeserialize, BorshSerialize, Deserialize, Serialize, Clone, PartialEq, Debug)]
#[serde(crate = "near_sdk::serde")]
pub struct VestingSchedule {
    /// The timestamp in nanosecond when the vesting starts. E.g. the start date of employment.
    pub start_timestamp: WrappedTimestamp,
    /// The timestamp in nanosecond when the first part of lockup tokens becomes vested.
    /// The remaining tokens will vest continuously until they are fully vested.
    /// Example: a 1 year of employment at which moment the 1/4 of tokens become vested.
    pub cliff_timestamp: WrappedTimestamp,
    /// The timestamp in nanosecond when the vesting ends.
    pub end_timestamp: WrappedTimestamp,
}

impl VestingSchedule {
    pub fn assert_valid(&self) {
        assert!(
            self.start_timestamp.0 <= self.cliff_timestamp.0,
            "Cliff timestamp can't be earlier than vesting start timestamp"
        );
        assert!(
            self.cliff_timestamp.0 <= self.end_timestamp.0,
            "Cliff timestamp can't be later than vesting end timestamp"
        );
        assert!(
            self.start_timestamp.0 < self.end_timestamp.0,
            "The total vesting time should be positive"
        );
    }
}

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
