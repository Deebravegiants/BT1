Audit Report

## Title
Per-sender rate limit keyed on unnormalized address string allows quota bypass - (File: core/capabilities/webapi/trigger/trigger.go)

## Summary
In `triggerConnectorHandler.processTrigger`, the allowlist check normalizes the sender via `sender.String()` (a canonical `common.Address` derived from `ethCommon.HexToAddress(body.Sender)`), but the immediately following rate-limit check uses the raw, attacker-controlled `body.Sender` string instead of the normalized value. Since hex addresses are case-insensitive, a caller can vary the casing of the same address across requests to obtain a fresh rate-limiter bucket each time, defeating the configured `PerSenderRPS`/`PerSenderBurst` quota.

## Finding Description
`HandleGatewayMessage` normalizes the sender once: `sender := ethCommon.HexToAddress(body.Sender)` [1](#0-0) . This normalized value is correctly used for the allowlist check: `trigger.allowedSenders[sender.String()]` [2](#0-1) . Immediately after, the rate limiter is called with the unnormalized field instead: `trigger.rateLimiter.Allow(body.Sender)` [3](#0-2) . `body.Sender` is a plain string field taken from the inbound gateway message body, and `msg.Validate()` invoked in `hc.ValidatedMessageFromReq` [4](#0-3)  performs only structural/format validation, not case normalization of the sender address. The rate limiter (`ratelimit.RateLimiter.Allow`) keys its buckets by the exact string passed in, so distinct casings of the same address produce distinct buckets, each with its own fresh quota.

## Impact Explanation
This allows a caller who is already on the trigger's allowlist to bypass the `PerSenderRPS`/`PerSenderBurst` quota configured at `RegisterTrigger` [5](#0-4)  by simply varying the letter-case of their own address string across requests, since each casing maps to a different rate-limiter bucket while all pass the allowlist check identically. This maps to excessive/unthrottled workflow trigger execution — a quota/rate-limit bypass — which can cause resource exhaustion and unbounded downstream workflow execution.

However, this is not a purely unprivileged bypass: the attacker must already be an allowlisted sender for the trigger (the allowlist check must pass to reach the rate limiter at all), and I was unable to fully verify within available time whether the gateway performs a case-sensitive signature-based authentication step upstream (prior to `HandleGatewayMessage`) that ties the accepted `body.Sender` string to a specific casing recovered from the message signature. If such an upstream check exists and enforces that `body.Sender` matches the signer's canonical address exactly, the attacker's ability to freely vary casing while still passing authentication would be constrained or eliminated. I could not confirm this within the available investigation.

## Likelihood Explanation
Given the confirmed code path, exploitation only requires trivial string-casing manipulation by a sender who is already allowlisted for the trigger — no additional privilege beyond being a legitimate registered caller of the endpoint. Repeatability is high assuming the gateway's authentication does not tie the exact `body.Sender` string casing to the verified signer address (unverified, see above).

## Recommendation
Use the normalized `sender.String()` consistently for both the allowlist check and the rate-limiter key, e.g., change `trigger.rateLimiter.Allow(body.Sender)` to `trigger.rateLimiter.Allow(sender.String())` in `processTrigger`, so both security-relevant checks operate on the same canonical identity representation.

## Proof of Concept
1. Register a trigger with `AllowedSenders: ["0xAbCd...ef"]` and a low `PerSenderRPS`/`PerSenderBurst`.
2. As an allowlisted sender, send repeated `web_api_trigger` gateway messages where `body.Sender` is a case-permutation of the allowlisted address each time (`0xabcd...ef`, `0xABCD...EF`, etc.).
3. Confirm each request passes the allowlist check in `processTrigger` (`trigger.allowedSenders[sender.String()]`) since `sender.String()` normalizes to the same checksummed value regardless of input casing.
4. Confirm `trigger.rateLimiter.Allow(body.Sender)` treats each casing variant as a distinct key, allowing requests beyond the configured `PerSenderRPS`/`PerSenderBurst` to be accepted.
5. This should be validated as a Go unit test on `triggerConnectorHandler.processTrigger` with a mock `ratelimit.RateLimiter`, and separately confirmed against the actual gateway message authentication path to determine whether upstream signature verification constrains achievable `body.Sender` casing values in practice.
