### Title
Webhook `shop` identifier is not covered by the HMAC signature, allowing cross-tenant shop-header spoofing via webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `X-Shopify-Shop-Domain` header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body, never the shop header. An unprivileged merchant who legitimately receives one valid signed webhook for their own shop can capture that `(body, hmac)` pair and replay it to the app's webhook endpoint with the `shop` header changed to a victim shop, and it will still pass HMAC validation while `handler.handle` is invoked with the attacker-chosen `shop` value.

### Finding Description
`Request#hmac` is computed from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `verifiable_query.to_signable_string`, i.e. the body bytes, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` trusts `request.shop` (parsed from the unauthenticated header) once the body HMAC passes, and forwards it directly to the app's webhook handler as the tenant identifier: [4](#0-3) 

The bug-class equality that should hold is: `shop bound by HMAC == shop acted upon by the handler`. Here, the field acted upon (`request.shop`, used to route/attribute the webhook event to a tenant) is disjoint from what the HMAC actually authenticates (only `@raw_body`). Because the shop header sits outside the signed payload, any valid `(body, hmac)` pair — including one an attacker legitimately received for their own shop — can be replayed with an arbitrary `shop` header value and will still validate successfully.

### Impact Explanation
This breaks the tenant/shop identity binding at the point the gem hands data to the host application: `Registry.process` and `WebhookMetadata` present `request.shop` as an authenticated fact once `HmacValidator.validate` succeeds, but that value was never actually part of what was cryptographically verified. Any host application that uses `WebhookMetadata#shop` to look up a merchant's session/access token, or to attribute the webhook body's contents (order data, product data, GDPR data, etc.) to that shop, can be made to process data for shop A under the identity of shop B — a cross-tenant data confusion within the boundary this gem is responsible for asserting (the "is this event genuinely for this shop" guarantee).

### Likelihood Explanation
Any user who can install the app on their own store (a normal, unprivileged merchant) automatically receives real webhook deliveries containing a body correctly signed with the app's shared secret. Capturing one such valid `(body, hmac)` pair requires no elevated access — it's simply the webhook the app receives for the attacker's own shop. Replaying it against the app's public webhook endpoint with a modified `shopify-shop-domain` header is a trivial HTTP replay, no secrets required.

### Recommendation
Include the shop domain (and other routing-critical headers such as topic/api-version if they affect business logic) inside the value that is HMAC-verified, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted, e.g.:
```diff
 def to_signable_string
-  @raw_body
+  "#{shop}\n#{topic}\n#{@raw_body}"
 end
```
along with computing/verifying against that same canonical string on the Shopify-issued side, or documenting explicitly that host applications must independently verify the `shop` value (e.g. against their own record of installed shops) before trusting webhook payload data for a given tenant.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`. Shopify sends a legitimately signed webhook (body `B`, header `X-Shopify-Hmac-Sha256: H`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`) to the app's webhook endpoint. Attacker can observe this traffic since it targets infrastructure they control/operate (their own webhook receiver, proxy, or logs).
2. Attacker resends the exact same body `B` and hmac `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the spoofed header into `request.shop`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, api_secret_key) == H` — this still passes because `B` and `H` are unchanged. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, i.e. the host app processes attacker-controlled data as if it belongs to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
