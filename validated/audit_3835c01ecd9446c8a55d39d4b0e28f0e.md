### Title
Webhook HMAC does not bind the `shop` field, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, excluding the `shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates only that signature and then passes the unauthenticated `shop` value straight to the handler. Any party who possesses one genuine `(raw_body, hmac)` pair delivered to their own shop's endpoint can resend it to the same endpoint with a forged `shop-domain` header, and the HMAC check will still pass because the shop identity was never part of what was signed.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the (attacker-controllable) `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signature: [2](#0-1) 

`HmacValidator.validate_signature` signs/verifies only `verifiable_query.to_signable_string`, i.e. the body — the shop identity is never included in the signed material: [3](#0-2) 

`Registry.process` raises `InvalidWebhookError` only if the HMAC (body signature) is invalid, and otherwise forwards the raw, unverified `request.shop` value to the app's handler as the tenant identifier: [4](#0-3) 

This breaks the identity binding: `shop authenticated == shop the handler attributes the data to`. Because the HMAC only covers `raw_body`, and every shop installed on the same app shares the same `api_secret_key` (the value used to compute/verify the HMAC), a payload's `(body, hmac)` pair is valid for the app in general — not scoped to any specific shop. An attacker who is a legitimate merchant with the app installed on their own shop will receive genuine `(raw_body, hmac)` deliveries from Shopify for their own shop. They can replay that exact `(raw_body, hmac)` pair to the app's webhook controller while substituting a different `shop-domain` header value naming a victim shop. `HmacValidator.validate` still returns `true` (it only checks the body signature), so `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `shop` is the attacker-chosen value.

### Impact Explanation
Any app that keys persistence, side effects, or authorization decisions in its webhook handler off `WebhookMetadata#shop` (the documented and expected pattern, per `docs/usage/webhooks.md`) can be made to attribute another tenant's fabricated event to a shop the attacker does not control, or to attribute a real event under a spoofed shop identity. This is a cross-tenant integrity break: data intended for/about shop A can be injected/mislabeled as belonging to shop B purely by manipulating a header that sits outside the HMAC-signed content — satisfying the "cross-tenant access" impact class.

### Likelihood Explanation
Medium: the attacker needs at least one genuine `(raw_body, hmac)` pair, which any merchant with the app installed on their own store legitimately receives from Shopify on every webhook delivery. No secret material, token theft, or privileged access is required — only the ability to send an HTTP request to the app's already-public webhook endpoint with modified headers.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the material that is cryptographically verified, or otherwise cross-check the header-derived `shop` against a value independently known to the app (e.g., validate that `request.shop` matches an actively registered/expected shop domain, or include the shop domain in the HMAC computation as Shopify's webhook payloads already embed `shop_id`/`shop_domain` inside the JSON body for some topics — verify that body-embedded shop identity matches the header before trusting it). At minimum, document that `WebhookMetadata#shop` from the header is not authenticated and must not be trusted as a tenant key without additional verification against the signed body contents.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook delivery, e.g. `orders/create`, with:
   - `raw_body`: `{"id":123,...}`
   - `x-shopify-hmac-sha256`: valid HMAC over `raw_body` computed with the app's `api_secret_key` (shared across all installs of the app)
   - `x-shopify-shop-domain`: `attacker.myshopify.com`
2. Attacker resends this exact request to the app's webhook controller endpoint, replacing only the header:
   - `x-shopify-shop-domain`: `victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (`request.rb` `to_signable_string`) — this still matches because the body/HMAC pair is unmodified, per `hmac_validator.rb` lines 26-31.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` (`registry.rb` lines 198-199), causing the app to process attacker-controlled data under the victim shop's identity.
