### Title
Webhook `shop`/`topic` fields are trusted downstream without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates an HMAC over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's webhook handler as trusted metadata come from unauthenticated HTTP headers. Because the app's `client_secret` (`Context.api_secret_key`) used to sign webhooks is the same across every shop that has installed the app, any merchant who can capture one legitimately-signed webhook can replay it with a forged `X-Shopify-Shop-Domain` header, and the signature will still validate — causing the handler to process attacker-supplied data as if it belonged to a different tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only ever checks `to_signable_string` (the body) against the HMAC: [3](#0-2) 

`Registry.process` validates only that HMAC and then forwards the unauthenticated `shop`/`topic`/`webhook_id` straight to the app's handler as trusted identifying metadata: [4](#0-3) 

This reproduces the same bug *class* as the external report: a value the code *acts on* (here, the tenant identity `shop`, used by the calling application to route/attribute the webhook) is not covered by the integrity check that is supposed to authenticate the message (the HMAC), while an unrelated value (the body) is. The equality that should hold — `hmac_covers(shop) == shop_trusted_by_handler` — is broken: `hmac_covers(shop) = false` but `shop_trusted_by_handler = true`.

Because `api_secret_key` is a single per-app secret shared by all installed shops (it is not shop-specific), any unprivileged user who can install the app on their own shop (or who can otherwise obtain one valid `(body, hmac)` pair, e.g. from a public/mandatory webhook such as `customers/data_request`) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. The HMAC still validates because the shop header is not part of the signed content.

### Impact Explanation
This crosses a tenant boundary: `Registry.process` hands the forged `shop` value to the app's registered handler as authenticated fact, with no gem-level mechanism to detect the mismatch. Depending on how the host application keys its logic off `WebhookMetadata#shop`/`topic` (e.g., looking up sessions, updating per-merchant records, or acting on mandatory compliance topics like `shop/redact`/`customers/redact`), an attacker can cause the app to attribute attacker-controlled webhook content to a victim merchant, producing cross-tenant data corruption or improper deletion/redaction actions performed against a shop the attacker doesn't own. This matches the "Critical — cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high for an attacker who is simply a normal, unprivileged installer of the target app: installing a public app on their own store is unprivileged and gives them a legitimate channel to receive at least one real `(body, hmac)` pair signed with the app's shared secret. No access token, refresh token, or `client_secret` leak is required — only observation of one webhook delivery to their own shop and the ability to replay an HTTP POST with a modified header, both of which are entirely within reach of an "unprivileged internet user" relative to other tenants of the same app.

### Recommendation
Bind the identity fields to the signature, not just the body. Options:
1. Extend `to_signable_string` (or introduce a second, header-aware verification step) to require the `shop` domain to match a known/allow-listed shop for that installation before dispatching to the handler.
2. At minimum, document/require host applications to independently verify `X-Shopify-Shop-Domain` against a session/shop the app has actually installed for, rather than trusting the header at face value; consider exposing a helper in `Registry.process` that rejects webhooks whose `shop` header does not correspond to a shop with an active, known installation.
3. Where feasible, additionally validate the `X-Shopify-Webhook-Id` for idempotency/replay protection so a captured `(body, hmac)` pair cannot be reused indefinitely, mitigating the cross-shop replay vector.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, which is a fully unprivileged action.
2. Shopify delivers a real webhook (e.g., `app/uninstalled` or `customers/data_request`) to the app's endpoint, signed with the app's single, shared `client_secret`:
   ```
   X-Shopify-Topic: customers/data_request
   X-Shopify-Hmac-Sha256: <valid HMAC over body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {...}
   ```
3. Attacker captures this raw body and its valid `X-Shopify-Hmac-Sha256` value.
4. Attacker replays the identical body and HMAC to the same app endpoint but swaps the shop header:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
5. `Utils::HmacValidator.validate` in `hmac_validator.rb` recomputes the HMAC over the body only and it matches, so `Registry.process` in `registry.rb` accepts the request and dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` to the app's handler [5](#0-4) , causing the app to process attacker-controlled webhook content as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
