### Title
Webhook `shop` and `topic` identity headers are not covered by the HMAC signature, enabling spoofed/cross-tenant webhook events - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using `Utils::HmacValidator.validate`, but the HMAC is computed only over the raw request body. The `shop-domain` and `topic` headers—used to identify which tenant and event the webhook belongs to—are read directly from unauthenticated HTTP headers and passed straight through to the handler. This breaks the identity binding `HMAC-verified bytes == data used to authorize/attribute the event`, analogous to the reported bug class where an unvalidated field (`signatures_required`) let an attacker bypass an authorization check that should have been tied to the verified data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` and `topic` accessors are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then dispatches based on the unauthenticated `topic`, forwarding the unauthenticated `shop` value straight to the app's handler: [3](#0-2) 

Crucially, `HmacValidator.validate` computes the signature using the app's single shared `Context.api_secret_key`—the *same* secret is used for every shop/tenant installed on the app, not a per-shop secret: [4](#0-3) 

Because the secret is shared across all tenants of the app, a real, validly-signed webhook body+HMAC pair captured from one shop (e.g., an attacker's own store installing the same app) remains a *valid* body+HMAC pair when replayed to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header. `Registry.process` will pass HMAC validation and route the (attacker-controlled shop identity, potentially attacker-chosen topic) straight to the registered handler, which the app's documentation explicitly claims has already been confirmed to "come from Shopify": [5](#0-4) 

The equality that should hold but doesn't: `shop header used by handler == shop cryptographically bound to the HMAC-verified payload`. Instead: `shop header used by handler == arbitrary attacker-supplied header value`.

### Impact Explanation
This crosses a tenant boundary using only credentials/capabilities available to any merchant who can install the app on their own store (an "unprivileged" actor relative to other tenants). By replaying a self-signed webhook body with a forged `shop-domain` header, the attacker can make the host application process fabricated webhook events attributed to a victim shop (e.g. triggering `orders/create`, `app/uninstalled`, or GDPR mandatory topics for a shop they do not own), and/or spoof the `topic` header to invoke a different registered handler than what Shopify actually intended for that payload. This is cross-tenant data/event injection into the app's business logic, matching the "cross-tenant access" impact bucket.

### Likelihood Explanation
Any developer/attacker can install the target app on their own trial/dev store, causing Shopify to send them genuinely-signed webhooks (same shared `api_secret_key`). They can then freely replay that body+HMAC pair to the app's public webhook endpoint with modified `shop-domain`/`topic` headers, since the library performs no validation of these fields. No access token, `client_secret`, or privileged access is required — only the ability to install the target app on any store, which is standard unprivileged internet-user capability for a public app.

### Recommendation
Bind the `shop-domain` and `topic` headers into the HMAC-verified signable string used by `Request#to_signable_string` where feasible, or, at minimum, have `Registry.process` cross-check the `shop` header against an independently-verified source (e.g., a session/shop record established via OAuth) before dispatching to the handler. At the very least, update the documentation to clarify that `Registry.process` only authenticates the payload bytes and does not authenticate the `shop` or `topic` headers, so host applications know they must independently verify shop identity before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for `orders/create` webhooks.
2. Shopify sends a legitimately HMAC-signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - Body: `{"id": 1, ...}` (attacker fully controls the order content in their own store)
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but rewrites the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `Registry.process` calls `HmacValidator.validate(request)`, which only checks the body against the shared `api_secret_key` — validation succeeds because the body/HMAC pair is genuinely valid for this app. [6](#0-5) 
5. The registered handler is invoked with `data.shop == "victim-shop.myshopify.com"`, `data.topic == "orders/create"`, even though Shopify never sent this event for `victim-shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
