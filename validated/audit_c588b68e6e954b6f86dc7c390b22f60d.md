### Title
Overflow in borrow-index accrual permanently freezes an oversized high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large market can make `borrowed * borrow_index` exceed `i128::MAX` before `borrow_index` reaches its configured ceiling. Every pool mutation runs `global_sync` before applying the operation, so the first accrual that crosses this product bound panics with `MathOverflow`, and all subsequent supply, borrow, repay, withdraw, liquidation, strategy, and revenue operations on that market panic at the same point. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` first converts scaled debt to its original RAY-scaled value and then calculates accrued interest by multiplying the unchanged `borrowed` share total by both the old and new borrow indexes. [3](#0-2) 

Those products are represented as RAY-scaled `i128` values, so a market with approximately `1e9` whole 18-decimal tokens has a scaled debt around `1e36`, and reaches the `i128::MAX ≈ 1.7e38` value ceiling at a borrow index of only about `170 * RAY`. [4](#0-3) [5](#0-4) 

`update_borrow_index` multiplies before clamping and only bounds the index at `1e9 * RAY`; it does not bound `borrowed * index`. [6](#0-5) [7](#0-6) 

The fixed-point helper protects intermediate multiplication with `I256`, but intentionally panics when the final quotient cannot fit in `i128`; therefore this is not merely a rejected oversized transaction, but a persistent state-dependent panic. [8](#0-7) [9](#0-8) 

Because `last_timestamp` is only updated after every accrued chunk succeeds, the overflowing accrual is retried on every later invocation and can never advance past the unsafe state. [10](#0-9) [11](#0-10) 

### Impact Explanation
All supplier funds and unclaimed protocol revenue in the affected market become permanently inaccessible once the product ceiling is crossed. [1](#0-0) 

`supply`, `borrow`, `withdraw`, `repay`, `update_indexes`, `flash_loan`, `create_strategy`, `seize_positions`, `recapitalize`, and `claim_revenue` all load or synchronize the same market state before mutation, so the unchecked representability failure blocks normal exit, repayment, liquidation, and bad-debt cleanup. [12](#0-11) [13](#0-12) 

Even an owner-driven rate-model replacement first accrues under the old model, so governance cannot reduce the rate to zero as an in-contract recovery path once the accrual itself panics. [14](#0-13) 

The repository already contains a regression demonstrating this outcome: a one-billion-token 18-decimal market at 98% utilization reaches `MathOverflow` before the index ceiling, after which both withdrawal and repayment fail. [15](#0-14) 

### Likelihood Explanation
The attacker does not need privileged storage access: they can reach the state by calling controller `supply` with a large asset leg, posting sufficient collateral in another market, calling controller `borrow` for enough debt to keep utilization in the curve’s high-growth segment, and later calling public `update_indexes` for the affected `HubAssetKey`. [16](#0-15) 

The required position size is within the protocol’s admitted cap domain: for 18 decimals, `max_cap_for_decimals` permits about 170 billion whole tokens before the asset-to-RAY conversion itself overflows, while the demonstrated value ceiling is crossed with only one billion tokens after index growth. [17](#0-16) [18](#0-17) 

Likelihood is constrained by the need for a very large token supply, enough collateral to sustain the borrow, and a listed rate model whose utilization cap and steep segment permit prolonged high utilization. [19](#0-18) [20](#0-19) 

Once those market conditions exist, however, any unprivileged address can trigger the freeze by invoking `update_indexes`; the condition is deterministic and cannot be avoided by subsequent callers. [21](#0-20) [22](#0-21) 

### Recommendation
Bound the resulting debt value, not just the borrow index. [6](#0-5) 

Before applying `new_borrow_index`, compute `borrowed * new_borrow_index` through a non-panicking path and clamp the index to the largest value that keeps the resulting RAY-scaled debt within `i128::MAX`. [2](#0-1) 

Apply the same explicit value-domain guard to `supplied * supply_index`, since `update_supply_index` also multiplies total shares by an index before distributing rewards. [23](#0-22) 

Add a market-level regression that reaches the value ceiling and verifies that accrual clamps instead of freezing withdrawals, repayments, liquidations, bad-debt cleanup, and revenue claims. [15](#0-14) 

### Proof of Concept
1. In a listed 18-decimal market `H = HubAssetKey { hub_id, asset }` whose caps and rate model permit the position, a whale calls controller `supply(caller, account_id, spoke_id, [(H, 1_000_000_000 * 10^18)])`.
2. A borrower with sufficient collateral calls controller `borrow(caller, account_id, [(H, 980_000_000 * 10^18)], None)`, leaving the market at approximately 98% utilization.
3. Interest compounds under the market’s high-utilization rate segment until `borrowed * borrow_index > i128::MAX` while `borrow_index < MAX_BORROW_INDEX_RAY`. [24](#0-23) [7](#0-6) 
4. Anyone calls controller `update_indexes([H])`; the pool loads the market and invokes `interest::global_sync`. [21](#0-20) 
5. `accrue_step` calls `scaled_to_original` or `calculate_supplier_rewards`, causing the RAY-scaled product’s final `i128` conversion to panic with `MathOverflow`. [25](#0-24) [8](#0-7) 
6. The transaction rolls back before `last_timestamp` is updated, so subsequent `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, flash, or strategy paths invoke the same accrual and fail identically. [10](#0-9) [22](#0-21)

        return old_index;

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

pub fn calculate_annual_borrow_rate(env: &Env, utilization: Ray, params: &MarketParams) -> Ray {
    let utilization = if utilization > Ray::ONE {
        Ray::ONE
    } else {
        utilization
    };

    let annual_rate = if utilization < params.mid_utilization {
        let contribution = utilization
            .mul(env, params.slope1)
            .div(env, params.mid_utilization);
        params.base_borrow_rate.checked_add(env, contribution)
    } else if utilization < params.optimal_utilization {
        let excess = utilization.checked_sub(env, params.mid_utilization);
        let range = params
            .optimal_utilization
            .checked_sub(env, params.mid_utilization);
        let contribution = excess.mul(env, params.slope2).div(env, range);
        params
            .base_borrow_rate
            .checked_add(env, params.slope1)
            .checked_add(env, contribution)
    } else {
        let base_rate = params
            .base_borrow_rate
            .checked_add(env, params.slope1)
            .checked_add(env, params.slope2);
        let excess = utilization.checked_sub(env, params.optimal_utilization);
        let range = Ray::ONE.checked_sub(env, params.optimal_utilization);
        let contribution = excess.mul(env, params.slope3).div(env, range);
        base_rate.checked_add(env, contribution)
    };

    if annual_rate > params.max_borrow_rate {
        params.max_borrow_rate
    } else {
        annual_rate
    }
