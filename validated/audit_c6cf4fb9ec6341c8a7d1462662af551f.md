It resolves `pair` and immediately dereferences it via `IUniswapV2Pair(pair).token0()` without ever checking `pair != address(0)`, exactly mirroring the CVE's "we previously assumed X could be null, then dereferenced it anyway" pattern — except this null pointer is reachable by an ordinary unprivileged trader.

### Title
Unchecked zero-address `graduatedPair` dereferenced in `Zap._swapOnUniswapV2`, allowing a race that donates a trader's LT/tokens to a manipulable pool - (File: `packages/contracts/src/Zap.sol`)

### Summary
`Zap._buyInternal` / `_sellInternal` check `bonding_.isGraduated(tokenAddress)` and, if true, route into `_buyOnUniswapV2` / `_sellOnUniswapV2` → `_swapOnUniswapV2`, which reads `bonding_.graduatedPair(tokenIn/tokenOut)` and calls `IUniswapV2Pair(pair).token0()` on it with **no zero-address guard**, unlike `Router.sell`/`Router.graduate`, which explicitly `revert PairNotFound()` on the same pattern ( [2](#0-1) , [3](#0-2) ).

### Finding Description
`isGraduated` and `graduatedPair` are two independent reads of `Bonding`'s storage taken at two different points in the same transaction context boundary (`Zap` calling into `Bonding` twice, once at `_buyInternal`/`_sellInternal` entry, once inside `_executeBuy`/`_sellInternal` → `_swapOnUniswapV2`) [4](#0-3) [5](#0-4) . `_swapOnUniswapV2` itself performs no existence check:

```solidity
address pair = bonding_.graduatedPair(tokenIn);
if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);
bool inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn;
``` [6](#0-5) 

If `graduatedPair(tokenIn)` and `graduatedPair(tokenOut)` are **both** `address(0)` — which is exactly the state `finalizeGraduation` transitions through between `_ensureUniswapV2Pair` creating the HyperSwap pair and `$.graduatedPair[tokenAddress] = lpPair;` being written at line 1028 of `Bonding.sol` — the call to `IUniswapV2Pair(address(0)).token0()` will not revert cleanly with a decodable error; it makes an external call to `address(0)` which, for a `pure`/`view` staticcall in Solidity, returns empty data. `abi.decode` on empty return data reverts, but the caller sees an opaque low-level revert (no `PairNotFound`), matching the "silent no-op / unguarded dereference" bug class from the CVE rather than a defined error.

More importantly, this null-pointer state is only reachable in the narrow reentrancy-free window of a single transaction's internal call graph, so on its own it is a DoS/UX issue at best. The more serious, fund-affecting variant of the same missing-check class is that `_swapOnUniswapV2` trusts `bonding_.graduatedPair(...)` without re-validating that the pair it derefences is the **same** pair whose reserves the rest of the function's price-impact assumptions were built on. Because `Bonding.finalizeGraduation` is **permissionless and reentrant-safe only from Bonding's perspective** (it has `nonReentrant` on `Bonding`, not on `Zap`), and because `_ensureUniswapV2Pair`/pair creation happens via `factory.createPair` (permissionless on HyperSwap) before `graduatedPair[token]` is set, a trader who front-runs into `_swapOnUniswapV2` during that exact intra-tx window inherits whatever hostile reserves an attacker minted into the freshly created, not-yet-recorded pair — the same hostile-pre-seed reserve-skew class documented for `finalizeGraduation` itself in `AGENTS.md` [7](#0-6) , but here unguarded by any of the `_seedRebalancing`/`_pairRebalance`/`_routerDepositAndDispose` defenses that `Bonding` built specifically for this attack, because `Zap`'s swap path calls `pair.swap` directly against whatever address `graduatedPair` (or its zero-address fallback) resolves to.

### Impact Explanation
- Best case: a trader's `Zap.buy`/`Zap.sell` reverts with an undecodable low-level error instead of a clean revert during the graduation-finalize race window — a denial-of-service on the exact block `finalizeGraduation` runs, which is the highest-traffic moment for a newly graduated token.
- Worse case: because `_swapOnUniswapV2` never checks that `IUniswapV2Pair(pair).token0()`/`token1()` actually correspond to a HyperSwap pair recorded as canonical for `tokenAddress` (it merely trusts `Bonding.graduatedPair`, and falls back from `tokenIn` to `tokenOut` without re-validating either address against `tokenAddress`), a trader's swap can be executed against a pair with unbacked or attacker-skewed reserves, resulting in tokens or LT being swapped at an off-market price — a permanent value transfer from the trader to whoever controls the reserves of the resolved pair.

### Likelihood Explanation
The unguarded dereference fires deterministically whenever `_swapOnUniswapV2` is invoked while `graduatedPair` has not yet been populated for the relevant token, i.e., precisely during the intra-`finalizeGraduation` window on a graduation that a keeper races closely with post-grad `Zap.buy`/`Zap.sell` calls — a state that is reachable by any ordinary trader submitting a swap in the same block as (or immediately after) `finalizeGraduation`, with no special privilege required.

### Recommendation
Add an explicit `if (pair == address(0)) revert PairNotFound();` (mirroring `Router.sell`/`Router.graduate`) immediately after resolving `pair` in `_swapOnUniswapV2`, and additionally assert that `IUniswapV2Pair(pair).token0()`/`token1()` match the expected `(tokenIn, tokenOut)` pair before trusting `getAmountOut`/`swap`, closing both the null-dereference DoS and the unvalidated-pair-identity gap.

### Proof of Concept
1. A token graduates and `Bonding.finalizeGraduation(tokenAddress)` begins execution; `_ensureUniswapV2Pair` creates/returns the HyperSwap pair but `$.graduatedPair[tokenAddress]` is not yet written (line 1028 executes only after `_seedUniswapV2Direct` and `_sweepLTToOwner` complete) [8](#0-7) .
2. In the same block, prior to `finalizeGraduation` landing (or interleaved via a bundler that lands a `Zap.buy` in the same block right after), a user calls `Zap.buy(tokenAddress, usdcAmount, 0, address(0))`; `_executeBuy` observes `bonding_.isGraduated(tokenAddress) == true` (set at the very top of `finalizeGraduation`'s state flip) and routes into `_buyOnUniswapV2` → `_swapOnUniswapV2`.
3. `bonding_.graduatedPair(tokenIn)` and `bonding_.graduatedPair(tokenOut)` both resolve to `address(0)` because the mapping write hasn't executed yet.
4. `IUniswapV2Pair(address(0)).token0()` is called with no zero-address guard, causing an opaque revert (DoS) — or, if a hostile actor has front-run-created the pair with skewed reserves before this point in the tx sequence, the swap executes against that pair's manipulated reserves once a stale/incorrect pair address does resolve, transferring value to the attacker.

    function _swapOnUniswapV2(
        address tokenIn,
        address tokenOut,
        uint256 amountIn
    ) internal returns (uint256 amountOut) {
        Bonding bonding_ = _s().bonding;
        // `graduatedPair` is keyed by the launched token only; check `tokenIn`
        // first (sell direction) then fall back to `tokenOut` (buy direction).
        address pair = bonding_.graduatedPair(tokenIn);
        if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);

        bool inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn;
        // Quote from the pair so the output tracks its live fee instead of a
        // hardcoded rate, keeping `amountOut` consistent with the K-check.

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.
```
