### Title
Webhook `shop-domain` (and `topic`) header is trusted for tenant dispatch but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop-identifying header (`shopify-shop-domain`) is read separately and passed unauthenticated into the handler dispatch path in `Registry.process`. The shop value that downstream handler code uses to decide "which tenant does this event belong to" is never bound by the HMAC that `Utils::HmacValidator.validate` checks.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns `@raw_body` only. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (and `request.topic`) to route the event to a handler and construct the metadata object the host application acts on: [3](#0-2) 

The equality this breaks is: **shop authenticated (bytes covered by HMAC = body) ≠ shop acted on (header value used for tenant dispatch)**. Since the app's `client_secret`/`api_secret_key` is shared across every shop that has installed the app, any two tenants of the same app share the same HMAC key. This means a byte-for-byte valid `(body, hmac)` pair generated by Shopify for tenant A's webhook remains a **valid** signature no matter what value is placed in the `shopify-shop-domain` header, because that header is never part of the signed material.

### Impact Explanation
This breaks the tenant isolation boundary the report's bug-class describes (identity binding failure — a field acted upon, here `shop`, is not covered by the authentication mechanism protecting the request). A user of one shop that has legitimately installed the app receives real, validly-signed webhooks for their own tenant. That user can capture such a `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`) header swapped to point at a different, victim tenant of the same app. `Utils::HmacValidator.validate` will pass because it only checks the body against the shared secret, and `Registry.process` will hand the forged shop identity straight to the app's webhook handler via `WebhookMetadata.new(topic:, shop:, body:, ...)`. Depending on how the host application uses `data.shop` (e.g., to select which merchant's database row to update, uninstall, redact, or create records for), this enables **cross-tenant data injection/corruption** — one merchant forging Shopify-attributed events against another merchant's data using only their own, legitimately-obtained webhook secret material (no `api_secret_key` leak, no privileged access required — only being a normal, unprivileged installed user of the app).

### Likelihood Explanation
Medium-High. Exploitation requires only: (1) install the app as any shop (or otherwise receive at least one real webhook), (2) capture one valid `(raw_body, X-Shopify-Hmac-Sha256)` pair, and (3) resend it to the same publicly reachable webhook endpoint with a different `shop-domain`/`topic` header. No secrets need to be extracted or brute-forced; the HMAC stays valid because it was never bound to the header. The main constraint is that the forged payload's `raw_body` must be one the attacker already possesses (they can't forge arbitrary bodies without the secret), so the attack is most powerful for topics with predictable/re-usable bodies (e.g., replaying a `customers/redact` or `shop/update` payload against a different shop identifier) rather than fully arbitrary content.

### Recommendation
Bind the shop and topic (and any other header fields the application will act on) into the signed material verified by `HmacValidator`, or independently verify that the shop in the header matches an actively known/authorized session/shop for this app before dispatching to handlers, e.g. by cross-checking `request.shop` against the app's installed-shop registry rather than trusting it implicitly during dispatch. At minimum, document that host applications must treat `shop`/`topic` headers as untrusted for authorization decisions and must always re-verify shop identity via their own session/install store before acting on webhook payloads.

### Proof of Concept
1. App is installed on shop `attacker-shop.myshopify.com` and shop `victim-shop.myshopify.com`, both sharing the same `api_secret_key`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
3. Attacker (who only controls their own shop/webhook receiver, e.g. via a temporary proxy or logging) captures `(B, H)`.
4. Attacker POSTs to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) computes `HMAC-SHA256(secret, B)` and compares to `H` — it matches, since the shop header is not part of the signed string.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds to call the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data as if it originated from the victim shop.
