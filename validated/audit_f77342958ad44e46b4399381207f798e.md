## Title
Webhook shop/topic identity fields are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed by `Utils::HmacValidator.validate` cryptographically authenticates the request body only. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read straight from HTTP headers, are never part of the signed material yet are trusted downstream and handed to the app's handler as the tenant/topic identity.

## Finding Description
`Registry.process` verifies the HMAC and then immediately builds `WebhookMetadata` from unauthenticated header fields: [1](#0-0) 

The `Request` class computes the signable string from the raw body alone, while `shop`, `topic`, `webhook_id`, and `api_version` come from `shopify_header`, which just reads whatever value is present in the HTTP headers of the incoming request: [2](#0-1) [3](#0-2) 

The equality that should hold but does not is: `shop header value used for handler dispatch == shop whose identity the HMAC actually attests to`. Since the HMAC key (`Context.api_secret_key`) is the app's single client secret shared by every installed shop, and the signed bytes are only the body, any two requests with identical bodies but different `shop-domain` / `topic` headers will both validate successfully: [4](#0-3) 

This does mirror Shopify's real-world documented webhook signing scheme (HMAC over raw body only, using the app secret), so this is inherent to the protocol this gem implements rather than an implementation defect introduced by the gem — but it does mean the gem itself performs no binding between the identity fields consumed by `Registry.process` (`shop`, `topic`) and the cryptographic check, and the docs do not instruct integrators to cross-check `request.shop` against a known/installed shop before trusting the payload.

## Impact Explanation
Because the shop and topic are not bound to the signature, and because the app's client secret is shared across every shop that has installed the app, any tenant who can obtain one genuine signed webhook body (by triggering an event in their own store, which any Shopify merchant can do) can replay the same bytes with `x-shopify-shop-domain` and `x-shopify-topic` headers swapped to name a different, victim shop. `Registry.process` will accept the HMAC (it only checks the body) and dispatch the handler with `WebhookMetadata` claiming the data belongs to the victim shop/topic. If the host app's handler uses `data.shop`/`data.topic` to select which tenant's session/record to mutate (a common pattern, e.g. `shop/redact`, `app/uninstalled`), this enables cross-tenant data operations without needing the target's access token, `client_secret`, or any credential belonging to the victim.

## Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even trial) installer of the target app on their own store — not an admin of the target app, and no access token/`client_secret`/leaked credential is required, which keeps it within an "unprivileged internet user" model. However, note this is the same header/body split Shopify's own official webhook verification uses; the gem does not deviate from the documented contract, and mitigating this ultimately depends on the host application additionally checking that the reported `shop` is a shop it has an active session for before acting on webhook content — a check the gem's docs do not currently emphasize.

## Recommendation
- Document explicitly (and consider providing a helper) that host applications must verify `WebhookMetadata#shop` against a shop with a known/active session (or otherwise a shop that is expected to receive that specific `topic`) before trusting webhook body content for tenant-scoped operations.
- Consider exposing the verified body separately from unauthenticated headers so integrators are not tempted to treat `request.shop`/`request.topic` as authenticated.

## Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook event (e.g. `orders/create`) to receive a body `B` and a valid `x-shopify-hmac-sha256` header `H` (computed over `B` using the shared app secret).
2. Replay an HTTP POST to the app's webhook endpoint with the same raw body `B` and header `H`, but set `x-shopify-shop-domain: victim.myshopify.com` and (optionally) a different `x-shopify-topic`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`; `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, causing the host app to act on data attributed to a shop the attacker does not control. [1](#0-0) [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
