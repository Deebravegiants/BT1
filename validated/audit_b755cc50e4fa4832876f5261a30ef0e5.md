## Finding

### Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the **raw body**, then blindly trusts the unauthenticated `shop-domain` header to identify which merchant the payload belongs to. Because the HMAC signature never covers the shop-domain (or topic/webhook-id) header, and the signing secret (`Context.api_secret_key`) is the same app-wide `client_secret` shared across every installed shop, any merchant who has installed the app can capture a legitimately-signed webhook for their own shop and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a different (victim) shop. The gem reports the request as fully valid and hands the handler a `WebhookMetadata` object whose `shop` field is attacker-controlled, even though the HMAC only proves the body's integrity, not its shop attribution.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then forwards `request.shop` unchecked to the registered handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature using `Context.api_secret_key` — the single shared `client_secret` for the whole app, identical for every shop that installed it: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`HMAC-verified(body) == HMAC-verified(body, shop)` is assumed true by the caller, but in reality only the former holds — the `shop` field that the handler acts on is disjoint from the bytes actually covered by the signature. This is the same class of bug as the report's "field acted on but not covered by the verified state" — the value trusted for downstream logic differs from the value cryptographically checked.

### Impact Explanation
Because the secret is shared across tenants, a malicious/curious merchant (an "unprivileged internet user" relative to any other tenant of the same app) can:
1. Install the app on their own shop and trigger any webhook topic (e.g. by editing an order/customer/product), fully controlling the JSON body content.
2. Capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair — a validly signed payload for their own shop.
3. Replay that exact body + HMAC to the app's public webhook endpoint, substituting `x-shopify-shop-domain` with the domain of any other shop that uses the app.
4. `HmacValidator.validate` succeeds (body signature is untouched), so `Registry.process` invokes the handler with `WebhookMetadata(shop: <victim-shop>, body: <attacker-controlled JSON>)`.

Any host application that uses `data.shop` to key its per-tenant persistence (the documented and expected pattern) will write or act on attacker-supplied data under the victim shop's tenant record — i.e., cross-tenant data injection/corruption using this gem's own trusted API surface, without needing the victim's credentials, access token, or `client_secret`.

### Likelihood Explanation
Any actor who can install the target app on their own store (typically anyone, for public apps) can produce an arbitrary number of validly-HMAC'd bodies at will and replay them with a forged shop header against the app's public-facing webhook URL. No special access, leaked secrets, or race conditions are required — only the ability to author webhook bodies for one's own shop and knowledge of another shop's domain (public information).

### Recommendation
Bind the shop identity into the value that is actually verified: include the `shop-domain` (and ideally `topic`/`webhook-id`) header in `to_signable_string`, or otherwise cryptographically bind the claimed shop to the signed payload before exposing `request.shop` to consumers, so a signature valid for shop A's body cannot be replayed with shop B's identity.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com`, both webhooks signed with the same `Context.api_secret_key`.
2. Attacker triggers a webhook on their own shop (e.g. `orders/create`) and captures:
   - `raw_body = '{"id":1,"malicious":"payload"}'`
   - `x-shopify-hmac-sha256 = HMAC(api_secret_key, raw_body)` (valid, since it was really signed by Shopify for this app).
3. Attacker POSTs to the app's webhook endpoint with headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <captured hmac>
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   and body = the captured `raw_body`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the hmac (see `to_signable_string`), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body — despite the payload never having come from, nor being validated against, `victim-shop.myshopify.com`.
