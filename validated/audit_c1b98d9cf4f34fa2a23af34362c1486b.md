Audit Report

## Title
Sensitive `AuditLogger.Headers` credentials exposed to any authenticated (including view-only) user via `GET /v2/config` - (File: core/web/config_controller.go)

## Summary
`ConfigController.Show`, registered at `authv2.GET("/config", cc.Show)` and `authv2.GET("/config/v2", cc.Show)` with no role wrapper, returns the node's full effective TOML configuration, including `AuditLogger.Headers` — a field explicitly documented to carry `Authorization` credentials for the audit-forwarding webhook. Because the TOML redaction mechanism only masks fields typed as `config.SecretString`/`config.SecretURL`, and `Headers` is typed as `models.ServiceHeaders` (a plain string-slice-derived type), any authenticated user regardless of role — including the lowest "view" role — can retrieve this credential in cleartext.

## Finding Description
`ConfigController.Show` at [1](#0-0)  serves `cfg.ConfigTOML()` (built from `inputTOML`/`effectiveTOML`) as JSON to any caller who reaches the handler. This route is registered under the generic `authv2` group with no `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper, unlike most other mutating/sensitive routes registered immediately around it in the same file, e.g. `authv2.POST("/transfers", auth.RequiresAdminRole(ets.Create))`: [2](#0-1) .

The project's own auth route-permission test table confirms `/v2/config` and `/v2/config/v2` are reachable by all three tested roles (`true, true, true` — admin, edit, view all pass): [3](#0-2) .

The `AuditLogger.Headers()` accessor returns `models.ServiceHeaders`, a plain (non-secret) type, not `config.SecretString`: [4](#0-3) . Because it is not one of the secret types (`config.SecretString`/`config.SecretURL`) that the TOML marshaler redacts as `xxxxx` — the mechanism that protects fields like `Database.URL`/`Password.Keystore` — the `Headers` value, which the project's own documentation instructs operators to set to values like `AUDIT_LOGGER_HEADERS="Authorization||{{token}}"`, is rendered verbatim in the config dump, as shown in the effective-config test fixture (`Headers = ['Authorization: token', ...]`).

This confirms the claim: the route lacks role gating, the exact underlying field is a documented location for bearer/API-key credentials, and it is excluded from the type-based redaction logic.

## Impact Explanation
Any authenticated user, including one with only the `view` role — the lowest privilege tier in Chainlink's multi-user node RBAC — can call `GET /v2/config` and obtain the plaintext contents of `AuditLogger.Headers`. If an operator has configured this per the documented example with an `Authorization` header, this leaks a live credential used to authenticate the node's audit-log forwarding webhook to a party who should have only read-only, non-administrative visibility. This is a legitimate secret/credential disclosure to an under-privileged authenticated actor, analogous to CVE-2023-46288-class config-exposure bugs, and maps to the in-scope "key/secret exfiltration" impact category.

## Likelihood Explanation
Exploitation requires only a valid low-privilege (`view`-role) session or API token — a normal, unprivileged authenticated capability that is readily obtainable in any multi-user Chainlink deployment. The precondition is that the operator has enabled the audit-logger feature and used a header value containing a real credential (as the project's own docs instruct), which is a realistic, foreseeable configuration rather than a contrived edge case. No admin/operator/host access is needed to trigger the disclosure itself.

## Recommendation
Wrap `AuditLogger.Headers` (and audit other general-config fields capable of holding credentials, e.g., webhook URLs with embedded basic-auth) in the existing `config.SecretString`/`config.SecretURL` types so they are redacted by the TOML marshaler the same way `Database.URL`/`Password.Keystore` are. As a complementary/alternative mitigation, restrict `GET /v2/config` and `/v2/config/v2` to `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`), consistent with how comparably sensitive endpoints elsewhere in `router.go` are gated.

## Proof of Concept
1. Configure a node with `[AuditLogger] Enabled = true` and `Headers = ['Authorization: Bearer supersecrettoken']`.
2. Create a session or API token for a user with `Role = view`.
3. Call `GET /v2/config` (or `/v2/config/v2?userOnly=true`) using that low-privilege credential.
4. Inspect the returned `ConfigV2Resource.Config` TOML string — it contains `Headers = ['Authorization: Bearer supersecrettoken']` in cleartext, confirming disclosure to a view-only user.
5. As a regression test: add a case to `core/web/config_controller_test.go` asserting that a `view`-role-authenticated request to `/v2/config` either (a) is rejected with 403, or (b) has `AuditLogger.Headers` redacted in the response body, once the fix is applied.

```go
func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}
```
