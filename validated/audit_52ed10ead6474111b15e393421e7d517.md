Audit Report

## Title
Unauthenticated nil-pointer dereference DoS via `vault_publicKeyGet` gateway request with null params - (File: core/capabilities/vault/gw_handler.go)

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet`, completely bypassing `h.requestProcessor.ProcessRequest` [1](#0-0) , unlike the `MethodSecretsCreate`, `MethodSecretsUpdate`, `MethodSecretsDelete`, and `MethodSecretsList` paths which are validated by `GatewayVaultRequestProcessor` with explicit `if req.Params == nil` guards [2](#0-1) . `handlePublicKeyGet` unconditionally dereferences `*req.Params` before any nil check [3](#0-2) , so a request with `params` omitted or `null` panics on dereference of a nil `*json.RawMessage`.

## Finding Description
The gateway connector's `readLoop` unmarshals arbitrary attacker-forwarded JSON-RPC requests into `jsonrpc.Request[json.RawMessage]` and invokes `handler.HandleGatewayMessage` synchronously for whatever method string is present, with no panic recovery wrapper [4](#0-3) . Inside `HandleGatewayMessage`, all other vault RPC methods go through `p.processRequest`, whose per-method handlers (`processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) each explicitly check `req.Params == nil` before unmarshalling [5](#0-4) . `MethodPublicKeyGet`, however, is special-cased to call `h.handlePublicKeyGet` directly with no validation pipeline at all [1](#0-0) , and that function dereferences `*req.Params` unconditionally: `json.Unmarshal(*req.Params, r)` [3](#0-2) . If `req.Params` is `nil` (i.e., the JSON `params` field is omitted or explicitly `null`), this line panics with a nil-pointer dereference before `json.Unmarshal` is even reached. Confirmed by reading the actual repository source, no `recover()` call exists anywhere in `core/services/gateway/connector`, so this panic is unrecovered and propagates up through `readLoop`'s goroutine.

## Impact Explanation
`MethodPublicKeyGet` requires no prior authorization step (it never reaches `Authorizer.AuthorizeRequest`), so any actor able to route a message through the gateway to this handler can trigger the panic with no credentials, allowlist membership, or JWT. The panic occurs inside the per-gateway `readLoop` goroutine that is core to the node's gateway connectivity; an unrecovered panic in that goroutine crashes it (or the process, depending on the Go runtime's panic propagation, which does crash the whole process unless recovered), denying vault service — and potentially other services depending on process health — to all legitimate tenants. This is a genuine availability-impacting denial-of-service bug reachable by an unprivileged caller.

## Likelihood Explanation
High. The trigger requires a single JSON-RPC message with `"method":"vault_publicKeyGet"` and `"params":null` (or omitted), which is trivial to construct and requires no authentication, no valid workflow owner, and no prior state.

## Recommendation
Add an explicit nil/empty check for `req.Params` in `handlePublicKeyGet` before dereferencing it (mirroring the pattern in `GatewayVaultRequestProcessor`'s per-method validators), returning an `api.UserMessageParseError` or `api.InvalidParamsError` response instead of panicking. More broadly, consider wrapping `handler.HandleGatewayMessage` calls in `connector.go`'s `readLoop` with a `recover()` to prevent any single malformed/malicious message from crashing the read loop or process.

## Proof of Concept
Send the following through the gateway to a vault-capable node:
```json
{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet","params":null}
```
This is parsed by `readLoop` into `jsonrpc.Request[json.RawMessage]{Method: "vault_publicKeyGet", Params: nil}` and dispatched to `GatewayHandler.HandleGatewayMessage`, which routes to `handlePublicKeyGet`, which panics at `json.Unmarshal(*req.Params, r)` since `req.Params` is `nil`. A Go unit test constructing a `*jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and calling `GatewayHandler.HandleGatewayMessage` directly would reproduce the panic deterministically.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
