### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` verifies solely the request body bytes against `X-Shopify-Hmac-Sha256` [2](#0-1) . The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) with no cryptographic binding to the signed body [3](#0-2) . `Registry.process` passes this unauthenticated `shop` value directly into `WebhookMetadata`, which is delivered to the host application's handler as if it were verified [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop header used to attribute a webhook's data == shop that produced the HMAC-verified body`. In this gem, the HMAC only signs `@raw_body`; the `shop-domain` header is parsed but never included in `to_signable_string`. Consequently, `HmacValidator.validate(request)` returning `true` proves only that *some* request body was produced with the app's shared `api_secret_key` — it proves nothing about which shop header accompanies that body. The documentation itself claims `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4) , but that verification does not extend to the `shop` field that the doc's own example handler uses to attribute data (`data.shop`) [6](#0-5) .

Since the `api_secret_key`/HMAC secret is shared across all shops installing the same app (it is not per-shop), any existing, unprivileged merchant who has installed the app receives genuine webhook deliveries — real `(raw_body, hmac)` pairs — for their own shop. That merchant can replay the exact same `raw_body` and `hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will happily build `WebhookMetadata` claiming the payload belongs to the victim shop [7](#0-6) .

### Impact Explanation
Any app that uses `data.shop` from `WebhookMetadata` to key data storage, trigger per-tenant side effects, or make decisions (which the gem's own documented usage pattern encourages, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into associating attacker-controlled webhook content with an arbitrary victim shop domain. This is a cross-tenant data-integrity/confidentiality break driven purely by a gem-level verification gap (the identity field is not bound to the authenticated bytes), reachable by any shop that has installed the app — no `api_secret_key`, access token, or TLS interception required.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant app: attacker only needs to be a legitimate (even low-privilege) installer of the app to receive at least one genuine webhook delivery, then can replay `(raw_body, hmac)` against the same publicly reachable webhook endpoint with a forged `shop-domain` header. No secret material needs to be known or guessed.

### Recommendation
Bind the identity fields into the HMAC-verified surface, or otherwise cryptographically/authoritatively tie the `shop` used for attribution to the verified request. Options:
- Cross-check the `shop-domain` header against a value embedded in the signed payload (e.g. cross-reference against a stored/expected shop derived from the webhook subscription id rather than trusting the header outright), and/or
- Document and enforce that `Registry.process` callers must independently confirm `request.shop` corresponds to a shop with an active app installation/session before trusting `WebhookMetadata#shop`, and
- Consider incorporating shop domain into an application-level replay/idempotency check keyed by `webhook_id` scoped per originating shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures a webhook (e.g. `orders/create`).
2. Shopify delivers a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical `B` and `H` to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only [8](#0-7)  — it matches `H`, so validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: B ...)` [7](#0-6)  and dispatches it to the host app's handler, which (per the gem's documented pattern) attributes `B`'s content to `victim-shop.myshopify.com`.
