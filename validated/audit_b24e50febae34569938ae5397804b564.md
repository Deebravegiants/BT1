### Title
Unchecked ERC20 `transfer` return value allows theft/loss of escrowed funds in Tron `IntentGatewayV2.withdraw` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens using a raw low-level `.call()` to the token's `transfer` function and only checks that the *call itself* did not revert (`success`), never inspecting the ABI-decoded boolean return value. For any ERC20 that follows the "return false on failure" pattern instead of reverting, `withdraw` will mark the escrow as spent and emit `EscrowReleased`/`EscrowRefunded` even though the beneficiary received nothing.

### Finding Description
`withdraw` (called from both `RedeemEscrow`/`RefundEscrow` request handling and from `onGetResponse` for cancellations) settles escrow for non-native tokens like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here is `true` whenever the external call does not revert — it does not verify the ABI-encoded `bool` return data. Many ERC20 tokens (e.g. tokens following the classic non-reverting ERC20 pattern such as certain legacy/old tokens, or any token that simply returns `false` on insufficient allowance/paused/blacklist conditions instead of reverting) will make this call succeed while returning `false`, meaning no tokens are actually transferred to `beneficiary`. Despite this, the code unconditionally decrements `_orders[commitment][token]` and (in the caller) marks the order `_filled` and emits the release/refund event, permanently destroying the escrow record for the intended recipient. This is the same root-cause pattern as the referenced Cooler.sol issue — a transfer's return value is not properly checked, letting the contract believe funds moved when they did not.

The same low-level `.call` pattern without return-value inspection is also used for the transaction-fee payout and for `SweepDust`: [2](#0-1) [3](#0-2) 

By contrast, the canonical EVM `IntentGatewayV2`/`IntentsBase` implementation consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which reverts on a `false` return: [4](#0-3) 

This confirms the Tron contract's manual, unchecked low-level call is the deviation/regression that introduces the bug.

### Impact Explanation
This is reachable by any unprivileged user placing and filling cross-chain intents through the Tron `IntentGatewayV2` (the entry point reachable from a relayed `RedeemEscrow`/`RefundEscrow` POST request or a `GET` response for cancellation). If the escrowed input token is one that can return `false` instead of reverting under some condition (paused, blacklisted address, insufficient balance edge case in a non-standard implementation), the protocol will silently "release" funds it never actually sent, permanently freezing the beneficiary's rightful claim (their escrow accounting is deleted/decremented with nothing received) — a permanent loss/freezing of funds for the affected user. This matches the "concrete theft or permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Likelihood depends on the specific ERC20 token configured for intents on Tron/TRC20 tokens (many TRC20 tokens historically do not strictly follow revert-on-failure semantics, making this more plausible on Tron than on mainnet EVM). Given IntentGatewayV2 is explicitly designed to support arbitrary tokens supplied by users in `order.inputs`/`output.assets`, and the Tron deployment is the only place in the codebase that reverted to unchecked low-level calls instead of `SafeERC20`, this is a realistic, not purely theoretical, risk for that specific chain deployment.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw` (and the fee payout and `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used consistently in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures transfers that return `false` instead of reverting are treated as failures and the escrow state is not mutated / events are not emitted for a transfer that never happened.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an escrowed input token `T` that implements `transfer` to return `false` (rather than revert) when, e.g., the recipient is blacklisted or a balance/allowance check silently fails — a legitimate pattern for several TRC20 tokens.
2. User places an order escrowing `T`; solver fills it cross-chain, triggering `RedeemEscrow` back on the source chain, which calls `withdraw`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` — `success` is `true` because the call did not revert.
4. `withdraw` proceeds: decrements `_orders[commitment][token]`, marks `_filled`, and emits `EscrowReleased`, even though `beneficiary`'s `T` balance is unchanged.
5. The beneficiary has permanently lost their escrowed tokens with no on-chain record left to reclaim them (root cause identical to `Cooler.sol`'s unchecked `transferFrom`/`transfer` calls in the original report).
