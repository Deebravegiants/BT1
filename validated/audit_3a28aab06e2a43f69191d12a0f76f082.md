### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-spoofing via replay of a legitimately signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, then trusts the unauthenticated `shop-domain` header to populate `WebhookMetadata#shop`, which host apps use as the tenant key to route/update data. The HMAC never binds the `shop` value, so the tenant identity attached to a webhook payload is not actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is **not** part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC of the request (i.e., of the body only) and, once that check passes, forwards `request.shop` straight into `WebhookMetadata` without any additional binding to the signature: [3](#0-2) 

`WebhookMetadata#shop` is a plain, unauthenticated `String` field: [4](#0-3) 

And the gem's own documentation instructs host apps to trust `data.shop` as the tenant identifier for routing work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), confirming this field is meant to be the authoritative per-tenant binding: the doc explicitly presents `shop` as "The shop domain of the webhook" and shows it being forwarded directly into job/tenant routing.

**Root cause / broken identity binding**: the equality that should hold is
`shop authenticated by HMAC == shop stored/used as tenant key`.
Here, the HMAC only authenticates `raw_body` bytes; the `shop` header is bytes verified (none) versus bytes parsed (yes) — the header is parsed and trusted, but never covered by the signature. Any entity capable of capturing one legitimately-signed webhook delivery for a shop it controls (which is trivial — every merchant who installs the app receives real, correctly-HMAC'd webhooks for their own store, since the app's `client_secret`/HMAC key is shared across all tenants of a given app) can replay the identical body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and the handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own body>)`.

### Impact Explanation
Because the app's HMAC secret is identical for every installed tenant, this is a cross-tenant boundary break: an unprivileged user who is simply a merchant using the app (no special privileges, no leaked credentials, no access token) can produce webhook requests that the gem will affirmatively certify as authentic ("did indeed come from Shopify", per the docs) for a **different** shop of their choosing. Any host application that follows the documented pattern of keying persistence/business logic off `data.shop` (exactly as shown in the gem's own usage example) will attribute attacker-controlled data to another merchant's tenant record — i.e., cross-tenant data injection/corruption through this gem's own trusted API surface, meeting the "cross-tenant access" impact bar.

### Likelihood Explanation
High. No secrets, tokens, or elevated access are required — only the ability to install the app on any shop (which any Shopify merchant/attacker can do for a public app) and observe one webhook body/HMAC pair, which is then replayed with a substituted header. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler) is the sole, exactly-documented way this gem processes inbound webhooks, so every consumer following the docs is exposed.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable string that is HMAC-verified, or otherwise cryptographically bind the `shop` value to the signed payload before exposing it via `WebhookMetadata`. At minimum, document prominently that `data.shop` is not itself authenticated and must be independently cross-checked against the caller's known/registered shop before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: HMAC(client_secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the identical body `B` and HMAC header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", ...})` is constructed; `to_signable_string` returns `B` only: [1](#0-0) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC was computed correctly over `B` with the shared `client_secret`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the host app (per the documented pattern) processes/attributes `B`'s contents to `victim-shop.myshopify.com`.
