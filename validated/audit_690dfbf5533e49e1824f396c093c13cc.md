This confirms the finding. The documentation at `docs/usage/webhooks.md` line 125 explicitly states: "This will verify the request did indeed come from Shopify" — and `WebhookHandler.handle` receives `data.shop` (line 8 of `webhook_handler.rb`) which app authors are told to trust as the shop identity (`docs/usage/webhooks.md` lines 12-26), even though `shop` is never covered by the HMAC computation.

### Title
Webhook HMAC verification does not bind the `shop` (or `topic`/`webhook_id`/`api_version`) header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body [1](#0-0) . The `shop` value that is subsequently handed to the app's handler as the trusted tenant identifier is taken from the `shop-domain` header, which is never included in the signed material [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the HMAC using exactly that signable string [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from HTTP headers [5](#0-4)  and are not part of that signable string.

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and the other header-derived fields) to construct the `WebhookMetadata` passed to the app-provided handler: [6](#0-5) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break called out in the rules: the equality the gem implicitly promises is `HMAC-verified data == (shop, topic, webhook_id, api_version, body)`, but what is actually verified is only `HMAC-verified data == body`. The `shop` field — the only tenant discriminator supplied to the handler — is fully attacker-controlled while the HMAC still validates successfully, because `api_secret_key` is per-app, not per-shop, and the signature never mixes in the shop value.

The gem's own documentation instructs developers to trust exactly this unverified binding: it says webhook processing "will verify the request did indeed come from Shopify" [7](#0-6)  and that `data.shop` is "The shop domain of the webhook" [8](#0-7) , to be used directly for tenant-scoped work such as `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [9](#0-8) .

### Impact Explanation
Any actor who can install the target app on their own Shopify store (a normal, unprivileged action) receives real webhooks for that store, each with a valid `(body, hmac)` pair signed with the app's shared `api_secret_key`. Because the shop identity is not bound into the signature, that same `(body, hmac)` pair can be replayed to the app's webhook endpoint with an arbitrary `shop-domain` header value naming a victim store. `HmacValidator.validate` will still return `true` since it only checks the body against the secret, and `Registry.process` will invoke the app's handler with `data.shop` set to the attacker-chosen victim shop and `data.body` set to attacker-controlled content. If the host app does what the gem's own documentation recommends — key persistence/state changes/job dispatch off `data.shop` — this results in cross-tenant data injection/corruption (e.g., writing attacker-controlled order/product data into a victim shop's records, or triggering shop-scoped side effects under a victim's identity).

### Likelihood Explanation
Exploitation requires no privileged access, no leaked credentials and no `api_secret_key` — only the ability to install the app on any shop (including the attacker's own store to legitimately obtain a valid `(body, hmac)` pair) and the ability to POST to the app's public webhook endpoint with a forged `shop-domain` header, both of which are standard unprivileged-internet-user capabilities.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the signed/verified material, or otherwise cryptographically bind them to the body before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated and must not be used as a tenant key without independent verification (e.g., cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker.myshopify.com`, completing OAuth normally.
2. Attacker registers for a webhook topic (e.g. `orders/create`) and lets Shopify deliver a real webhook to the app's endpoint; attacker captures the raw request body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` — both are legitimate values signed by the app's real `api_secret_key`, because the attacker is a legitimate (if unprivileged) app installer.
3. Attacker crafts a new HTTP POST to the same app webhook endpoint using the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any topic header still matched to a registered handler.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)` builds a request whose `hmac` is `H` and whose `to_signable_string` is `B` — identical to the legitimate signed value [10](#0-9) .
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` with the same `api_secret_key` and succeeds [1](#0-0) .
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [11](#0-10) , causing the app to process attacker-supplied data under the victim shop's identity.
