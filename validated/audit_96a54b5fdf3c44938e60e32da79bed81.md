This is the exact analog of the diamond-storage bug: an eviction queue (array-like ring buffer) whose entries are deliberately **not kept in sync** with an out-of-band deletion, causing the queue's stale index to later evict/mismatch the wrong live entry — the same root cause as `LibDiamond.replaceFunctions` not updating the `selectors` array while `facetAddressAndSelectorPosition` moves on, so a stale index later deletes the wrong element.

### Title
Vetoing the latest state-machine height creates a stale commitment-queue entry that evicts the wrong (live) state commitment - ([File: modules/pallets/ismp/src/host.rs])

### Summary
`IsmpHost::delete_state_commitment` in pallet-ismp intentionally leaves the vetoed height's entry in the bounded, ring-buffer-style state-commitment eviction queue instead of removing/relocating it, exactly the class of bug described in the report: an index/queue structure that is updated out of sync with the data it indexes, so a stale index later acts on the wrong live element.

### Finding Description
`delete_state_commitment` removes `BoundedStateCommitments` and `BoundedStateMachineUpdateTime` for a vetoed height and, if that height was the latest, rolls `LatestStateMachineHeight` back to `PreviousStateMachineHeight`, re-opening the height for honest resubmission [1](#0-0) . The comment explicitly documents that the height's slot in `StateCommitmentQueue`/`CommitmentQueueState` (the FIFO eviction queue that enforces `StateMachineCommitmentCap`) is deliberately left behind rather than located and removed, because that would require scanning the queue [2](#0-1) .

When the vetoed height is later honestly resubmitted via `store_state_machine_commitment`, it gets a *second* queue entry appended behind the stale one — analogous to `replaceFunctions` writing new selectors into `facetAddressAndSelectorPosition` without updating the corresponding slot in the `selectors` array, so the array element at that position becomes stale and later operations (here, FIFO eviction; there, `removeFunctions`) act on the wrong logical element. Because the stale entry reaches the queue head first, it triggers eviction of the just-resubmitted (live) commitment for that same height one insertion earlier than intended, and the test suite directly demonstrates this: two queue slots end up pointing at the same height, and eviction of the stale one deletes the live commitment prematurely, permanently burning a queue slot and reducing effective retention below the configured cap [3](#0-2) .

### Impact Explanation
This causes premature, silent deletion of a legitimately re-submitted state machine commitment that BEEFY/consensus verification just accepted, before its retention window elapses. Downstream ISMP request/response proof verification against that height (via `state_machine_commitment`) will then fail with `StateCommitmentNotFound` even though the height is within the nominal retention cap, potentially blocking legitimate message delivery/proof verification for that state machine height and permanently wasting one slot of the bounded queue capacity per veto-then-resubmit cycle. The test file frames this as a known, accepted "wart," but it is a genuine, reachable route-availability degradation (a route temporarily/permanently unable to deliver messages for the affected height) triggered by governance vetoing + honest relayer resubmission, which any relayer's message flow can hit.

### Likelihood Explanation
This requires the `AdminOrigin`/governance to veto (`delete_state_commitment`) a state machine height that happens to be the current latest height, followed by an honest resubmission of that same height — a plausible, foreseeable operational sequence (veto of a bad/malicious commitment followed by legitimate re-consensus), not a purely malicious-admin scenario since the resulting harm falls on the protocol's message-delivery guarantees rather than requiring admin malice.

### Recommendation
Maintain a height→queue-index mapping (or equivalent) so `delete_state_commitment` can also remove/rewrite the corresponding queue entry, mirroring the diamond-storage fix of keeping the `selectors` array and the `facetAddressAndSelectorPosition.selectorPosition` mapping consistent on every mutation, so stale queue entries can never evict a differently-tracked live commitment.

### Proof of Concept
The existing regression test demonstrates the flaw end-to-end: `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early` stores height 10 then 11, vetoes 11 (the latest), resubmits 11, and shows two queue slots (`index 1` and `index 2`) both pointing at height 11; the next insertion evicts the stale `index 1` entry and deletes the live commitment for height 11 one insertion earlier than the configured cap allows [3](#0-2) .

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())

fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {

			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(

			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));
	})
