The finding centers on `ShopifyAPI::Webhooks::Request`, whose HMAC signature covers only the raw body, while the shop, topic, and webhook-id fields — trusted by `Registry.process` — come from unauthenticated headers.

### Title
Webhook `shop`, `topic`, and `webhook_id` are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the request body bytes alone. The `shop`, `topic`, and `webhook_id` values, read straight from HTTP headers, are never part of the signed material, yet `Registry.process` trusts them unconditionally once the body HMAC checks out.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which only returns the raw body. Meanwhile `shop`, `topic`, and `webhook_id` are pulled from headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived fields to build the metadata handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the signature purely from `to_signable_string`: [4](#0-3) 

This breaks the intended binding `shop (authenticated by HMAC) == shop (acted on by handler)`. In reality, the HMAC only proves "this body was signed by Shopify for *some* topic/shop combination Shopify chose to deliver to this app's endpoint" — it proves nothing about which shop or topic the body is for, because those fields are outside the signed string.

An unprivileged attacker can install the target app on a shop they control (no special credentials needed, ordinary OAuth install flow) and receive genuine webhook deliveries with valid `X-Shopify-Hmac-Sha256` values. Because the signature depends only on the raw body bytes, the attacker can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while freely rewriting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers. `Registry.process` still validates the HMAC successfully (since the body is unchanged) and dispatches the handler with attacker-chosen `shop`/`topic`/`webhook_id` values via `WebhookMetadata`.

### Impact Explanation
This is a cross-tenant identity-binding break: the shop identifier acted upon by the host application's webhook handler is not the shop actually authenticated by Shopify's signature. Depending on how a host app's handler keys its per-tenant state (a common and Shopify-documented pattern, since `WebhookMetadata#shop` is the canonical tenant identifier the gem hands applications), an attacker can:
- Attribute their own captured payload to a victim shop, injecting attacker-controlled data (e.g., `orders/create`, `customers/update` content) into a victim tenant's data pipeline.
- Spoof `topic` on a captured payload to route the same bytes into a different handler than Shopify intended (e.g., turning a benign topic into `shop/redact` or `app/uninstalled` handling for a victim shop), potentially triggering data deletion or session revocation for a shop the attacker doesn't own.
- Manipulate `webhook_id` to defeat idempotency/dedup logic keyed on that header.

This matches the Critical bucket of cross-tenant access, since the gem's own webhook-authentication primitive fails to bind the tenant identity to the cryptographic proof, and no access token, `client_secret`, or privileged access is required — only a normal, self-serve app install.

### Likelihood Explanation
Likelihood is high for any host application that trusts `WebhookMetadata#shop`/`#topic`/`#webhook_id` as delivered by this gem (the documented, expected usage). No credentials beyond a standard app install are needed; the attacker only needs to observe one legitimate webhook delivery to their own shop and can then replay/rewrite headers freely, since header tampering does not invalidate the HMAC.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header fields the handler relies on) in the HMAC-signed material, or otherwise cryptographically bind them to the body — e.g., verify shop/topic against Shopify's out-of-band webhook subscription metadata rather than trusting client-supplied headers, or require handlers to independently confirm that `data.shop` corresponds to a shop with an active session/installation matching the expected topic before acting.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) — Shopify delivers a POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's secret), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally alters `X-Shopify-Topic` / `X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`), matching `H` — validation passes.
4. The handler executes with `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-controlled data as if it originated from, or pertains to, `victim-shop.myshopify.com`.
