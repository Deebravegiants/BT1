### Title
POA bridge withdrawal status/tx-hash misreport for co-mingled same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal (identified by `landingChain` + `index` + `tx`) by calling `findMatchingWithdrawal`, which selects an entry from the POA relayer's response purely by matching `assetId` (`nep141:${near_token_id}`), ignoring the `index` and the actual `destinationAddress`/`amount` that the caller is polling for.

### Finding Description
When a single NEAR intents transaction contains more than one POA-bridge withdrawal of the *same asset* (e.g., two withdrawals of `nep141:usdc.omft.near` to two different destination addresses within one `IntentsSDK.createWithdrawalIntents`/execution call), `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns each withdrawal an `index` (0, 1, ...) per bridge route [1](#0-0) , but `PoaBridge.describeWithdrawal` never uses that `index` to disambiguate: it only calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` and returns the *first* array entry with a matching asset, since "Response list is unsorted" [2](#0-1) [3](#0-2) .

This breaks the equality "status/txHash returned for withdrawal at index N" == "on-chain outcome of the withdrawal actually created at index N (to destinationAddress_N)". If two same-asset withdrawals exist in the tx, both index 0 and index 1 polling calls can resolve to the *same* underlying relayer record (whichever one `Array.find` hits first), so the withdrawal to `destinationAddress_1` can be reported "completed" with a `transfer_tx_hash` that actually belongs to the payout made to `destinationAddress_0` (or vice versa), even though the other withdrawal is still pending or failed.

### Impact Explanation
`watchWithdrawal` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` treats a `"completed"` status with a `txHash` as terminal proof of completion and resolves the poll immediately [4](#0-3) . An integrator relying on `IntentsSDK`'s withdrawal-completion promises to release funds, mark an order as fulfilled, or refund a user could therefore credit/confirm the wrong leg of a batched withdrawal, or report a legitimate withdrawal to a low-value/attacker-influenced address as completed while the actual user-facing withdrawal is unresolved. This matches "a status or hash misreport making an integrator credit or refund twice" (High impact per the rubric).

### Likelihood Explanation
The code comment itself acknowledges the gap explicitly: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [5](#0-4) , and there is no guard anywhere in `IntentsSDK.createWithdrawalIntents` / `withdrawal-watcher.ts` that prevents a caller from constructing a batch of withdrawal params containing two same-`assetId` POA-bridge withdrawals — `createWithdrawalIdentifiers` happily assigns them index 0 and 1 without validating uniqueness [6](#0-5) . So the vulnerable state is reachable purely by normal SDK usage (any integrator issuing >1 POA withdrawal of the same token in one call), not requiring a malicious relayer or admin action. Likelihood is elevated by the fact that it is a known, documented, unresolved limitation rather than a purely theoretical edge case.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` using more than `assetId` — incorporate `destinationAddress` and `amount` from `args.withdrawalParams`, or otherwise correlate relayer records to the specific intended output (e.g., by sorting both lists deterministically and pairing by position, as the code comment itself suggests) so that `describeWithdrawal` never returns a status/txHash for a withdrawal other than the one identified by `index`. Until fixed, `IntentsSDK` should either reject/serialize withdrawal batches that contain duplicate `assetId` values on the POA route, or surface a clear error rather than silently mis-attributing statuses.

### Proof of Concept
1. Caller submits one NEAR intents transaction with two `ft_withdraw` (POA bridge) intents for the same `assetId` (e.g., `nep141:usdc.omft.near`): withdrawal A to `addressA` (amount 100) at index 0, withdrawal B to `addressB` (amount 900) at index 1.
2. `createWithdrawalIdentifiers` assigns `wid.index = 0` for A and `wid.index = 1` for B, both with `landingChain` equal to the same chain [7](#0-6) .
3. The relayer completes withdrawal B first; `getWithdrawalStatus` returns an unsorted array whose first `usdc.omft.near` entry is B's completed record (`transfer_tx_hash = txB`).
4. Both `watchWithdrawal` calls (for wid index 0 and index 1) invoke `describeWithdrawal`, which calls `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")` — both calls get the *same* first match (B's record), so the poller for withdrawal A also resolves as `{status: "completed", txHash: txB}`, even though A (to `addressA`) has not actually completed.
5. Any integrator logic waiting on A's completion promise will treat A as finished and act on `txB`, which is unrelated to `addressA`'s actual payout.

**Uncertainty**: I could not verify from the indexed code whether higher-level integrator flows (outside `packages/intents-sdk`) already deduplicate same-asset withdrawals before calling the SDK, which would reduce real-world exploitability. This should be confirmed with a full checkout of the repo (a Devin session) since the index may not include all downstream integrator usage of `describeWithdrawal`/`watchWithdrawal`.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
