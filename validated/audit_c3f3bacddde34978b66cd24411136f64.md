### Title
Sandwich-attack value extraction on native-token fee swaps in `EvmHost.dispatch()`/`fundRequest()` due to unprotected on-chain Uniswap V2 conversion - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all convert native token sent as `msg.value` into the protocol `feeToken` via `IUniswapV2Router02.swapETHForExactTokens` on a single, locally-configured Uniswap V2 pool, with no caller-supplied slippage/price-limit protection and no way to recover the "buffer" ETH a caller must send to survive normal price movement between quoting and inclusion. This mirrors the FeeBuyback sandwich pattern: any submitter of a `dispatch`/`fundRequest` transaction that pays in native token can be sandwiched by an MEV searcher who manipulates the pool price immediately before the call and reverses it immediately after, extracting the caller's slippage buffer as profit.

In every case, `post.fee` / `get.fee` / `amount` is the **exact output** requested from a single Uniswap V2 pool (`_hostParams.uniswapV2`), and `msg.value` is the caller's implicit maximum input. There is no `amountInMax` parameter under the caller's control that is validated against an oracle or committed at dispatch time — the only "slippage protection" is however much extra native token the caller happens to send as `msg.value`. Callers determine that buffer by calling `HyperApp.quote()` beforehand: [4](#0-3) 

which reads the pool's instantaneous price via `getAmountsIn`. Because Uniswap V2 pools have no oracle-based, TWAP, or external slippage bound here (unlike `SimplexPaymaster.swapAndDeposit`, which derives `amountOutMin` from Chainlink oracles rather than trusting the caller/pool spot price — see `evm/src/utils/SimplexPaymaster.sol:454-480`), the quote-then-submit window is exploitable exactly like the reported `FeeBuyback.submit()` case: an attacker can front-run the dispatch/fundRequest transaction, buy `feeToken` to inflate its ETH price, force the Host's `swapETHForExactTokens` to consume a larger share of (or exceed) `msg.value`, then back-run by selling `feeToken` back into the now-depressed pool for profit — extracting value that would otherwise have been left over as the caller's slippage cushion or refunded.

Additionally, any ETH `swapETHForExactTokens` refunds for unused input is sent to `msg.sender`, which is the `EvmHost` contract itself (not the original dispatcher), meaning any leftover buffer ETH from a successful swap is not recoverable by the caller — it stays trapped/donated at the Host, compounding the incentive for callers to size buffers tightly and the profitability of sandwiching them precisely.

### Impact Explanation
Every app (HyperFungibleToken sends, IntentGatewayV2 cross-chain dispatch/relayer-fee payments, IsmpHost consumers generally) that pays dispatch/relayer fees in native token routes through this exact code path. A sandwich bot monitoring the mempool for `dispatch`/`fundRequest` calls with `msg.value > 0` can systematically extract value from ordinary users' cross-chain message fees on any EVM deployment where the configured Uniswap V2 pool has shallow liquidity — a very likely condition since this is described as "the local uniswap router," not a deep, canonical pool. This is a protocol-wide funds-loss vector affecting the base dispatch mechanism used across all Hyperbridge EVM apps, not an isolated app bug, satisfying High severity.

### Likelihood Explanation
The functions are `external payable` and callable by anyone dispatching a request or funding one with native token — no privilege required. MEV sandwich bots are already generically deployed against all AMM interactions; a fixed target contract with a fixed swap direction and no minimum-output validation is a straightforward, low-cost target requiring only mempool visibility and pool liquidity thin enough to move (well within reach for most EVM deployments beyond Ethereum mainnet, which is common for the "local uniswap router" pattern the Host explicitly documents).

### Recommendation
Do not derive the executed swap's acceptable price purely from `msg.value`/spot pool state:
- Require callers to pass an explicit `amountInMax`/`minFeeTokenOut`-style bound distinct from `msg.value`, and validate it against a TWAP or independent oracle (mirroring `SimplexPaymaster.swapAndDeposit`'s Chainlink-derived slippage bound) rather than trusting the same pool being traded against.
- Refund any unused `msg.value` (swap input surplus) to `_msgSender()`/`post.payer` instead of leaving it in the Host contract.
- Consider using a TWAP-based Uniswap V2 oracle or routing fee-token pricing through a Chainlink feed entirely, consistent with the mitigation already applied in `SimplexPaymaster`.

### Proof of Concept
1. Attacker watches mempool for a `dispatch(DispatchPost)` call with `msg.value > 0` targeting `EvmHost`.
2. Attacker front-runs with a large ETH→feeToken swap on the same `_hostParams.uniswapV2` pool, inflating feeToken's ETH price.
3. Victim's `dispatch` executes `swapETHForExactTokens(post.fee, [WETH, feeToken], address(this), block.timestamp)` at `evm/src/core/EvmHost.sol:927-929`; because output is fixed and price is inflated, it consumes a larger share of `msg.value` than quoted (or reverts if `msg.value` is insufficient, a DoS variant).
4. Attacker back-runs, selling feeToken back into the now-depressed pool, capturing the price-impact profit that came from the victim's forced trade — the classic sandwich extraction, directly analogous to the referenced `FeeBuyback.submit()` report.
