### Title
Caller-controlled swap route can execute a malicious token transfer under the swapper’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A route-driven controller strategy forwards an attacker-controlled `StrategySwap` payload to the configured router after establishing the account owner’s top-level authorization. [1](#0-0)  Because the controller validates only its own token-balance deltas and does not constrain external calls made while processing that payload, malicious route code can request an unrelated `token.transfer` from the swapping address and have it included as a child of the signed authorization tree. [2](#0-1) 

### Finding Description
`swap_tokens` accepts a nonempty caller-supplied `StrategySwap`, resolves the configured router, grants that router one exact controller-token transfer, and invokes `execute_strategy` with the opaque route payload. [3](#0-2)  Afterward it verifies only that the controller did not overspend the declared input, refunds unused input held by the controller, and requires a positive controller-side output delta. [2](#0-1)  Those checks do not bound authorization effects outside the controller’s token balances, so a malicious contract reached by the route can place a transfer from the caller to the attacker beneath the caller’s `swap_collateral`, `swap_debt`, `multiply`, or similar strategy authorization. [4](#0-3) 

### Impact Explanation
A victim who submits a malicious route and signs the authorization tree returned by simulation can lose arbitrary wallet tokens unrelated to the supplied collateral or routed amount. [5](#0-4)  The controller-side minimum output and solvency checks can still pass because the theft occurs against the caller’s wallet rather than the controller’s measured input or output balances. [2](#0-1)  This is theft of user funds, with the loss bounded only by the malicious child invocations the victim signs. [4](#0-3) 

### Likelihood Explanation
Exploitation requires the victim to select or accept a malicious route and then sign the complete authorization tree containing the malicious token-transfer child. [3](#0-2)  That makes the attack phishing-dependent rather than callable by an attacker against an arbitrary account without that account’s signature, but an unprivileged attacker can deploy the malicious venue, construct the route, and present it through a swap interface or payload. [2](#0-1) 

### Recommendation
Constrain route execution to governance-approved venue contracts and reject route data that can name an arbitrary external contract address. [6](#0-5)  Until venue allowlisting is enforced, clients must decode the route and reject any signed invocation tree containing children beyond the expected input transfer and legitimate venue calls. [2](#0-1) 

### Proof of Concept
1. Attacker deploys a contract whose route callback invokes `token.transfer(victim, attacker, amount)` for a token held by the victim but not otherwise involved in the lending strategy. [5](#0-4) 
2. Attacker constructs a `StrategySwap` payload that causes the configured router to invoke that contract while still returning enough `token_out` for `verify_router_output` to succeed. [2](#0-1) 
3. Victim calls a route-driven controller strategy such as `swap_collateral` with that payload. [7](#0-6) 
4. Transaction simulation records the malicious wallet-token transfer as a child authorization under the victim’s strategy invocation. [5](#0-4) 
5. If the victim signs that returned tree, the malicious venue transfers the victim’s unrelated token to the attacker, while the controller observes a bounded input spend and positive output receipt and accepts the strategy. [2](#0-1)

pub(crate) fn swap_tokens(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    require_positive_amount(env, amount_in);
    assert_with_error!(env, !swap.is_empty(), GenericError::InvalidPayments);

    let controller = env.current_contract_address();
    let router_addr = storage::get_swap_aggregator(env);
    let router = SwapAggregatorClient::new(env, &router_addr);
    let token_in_client = token::Client::new(env, token_in);

    // Snapshot before router execution to measure its spend and output.
    let in_before = token_in_client.balance(&controller);
    let out_before = token::Client::new(env, token_out).balance(&controller);

    // Authorize only this token transfer to this router for this exact amount.
    authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in);

    storage::with_flash_guard(env, || {
        let _ = router.execute_strategy(&controller, &amount_in, swap);
    });
