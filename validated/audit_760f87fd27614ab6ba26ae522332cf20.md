### Title
Cross-Tenant Webhook Impersonation via Shop-Domain Header Not Bound to HMAC Signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop-domain` header from the HMAC-signed material [1](#0-0) . `Registry.process` validates the HMAC over that signable string and, if valid, dispatches the handler using `request.shop` as the trusted tenant identity, with no additional check binding the shop header to the signature [2](#0-1) . This breaks the identity binding `bytes_verified_by_hmac == bytes_used_to_attribute_tenant`.

### Finding Description
The webhook verification flow is:
1. `Request#hmac` reads the `hmac-sha256` header, and `Request#shop` reads the `shop-domain` header — both are just headers on the incoming HTTP request, not cryptographically tied to each other [3](#0-2) .
2. `Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3) , which computes an HMAC over `verifiable_query.to_signable_string` and compares it to the header value [5](#0-4) .
3. `Request#to_signable_string` returns only the raw HTTP body [1](#0-0)  — the `shop`, `topic`, `webhook_id`, and `api_version` fields are **not** part of the signed bytes.
4. On successful HMAC validation, `Registry.process` builds `WebhookMetadata` using `request.shop` verbatim and passes it to the app's handler as the authoritative tenant identity [6](#0-5) .

Because the shop header sits outside the HMAC's protected scope, any two webhook deliveries that happen to carry the same raw body (which is common for empty-body or fixed-payload topics, e.g. compliance topics with `{}` payloads, or any topic where the JSON body is small/predictable) will produce the identical valid HMAC digest regardless of which shop header is attached. This is exactly the "field acted on but not covered by the HMAC" identity-binding gap: `verified_bytes(raw_body) != attributed_identity(shop header)`.

### Impact Explanation
An unprivileged internet user who operates their own legitimate Shopify shop (Shop A) receives real, validly-signed webhook deliveries at their own configured endpoint. If that endpoint is reachable/observable, the attacker can capture a genuine `(raw_body, hmac)` pair for a topic whose body is static, empty, or predictable across shops. The attacker then replays that exact `(raw_body, hmac)` pair to the target app's webhook endpoint while substituting the `shop-domain` header with Shop B's domain (or `x-shopify-shop-domain`). `HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret-derived digest, and `Registry.process` will invoke the app's handler with `WebhookMetadata(shop: "shop-b.myshopify.com", ...)`, causing the app to process attacker-controlled/replayed webhook data under a different tenant's identity — a cross-tenant integrity violation with no requirement to know `api_secret_key`.

### Likelihood Explanation
Exploitability requires: (a) the attacker legitimately controls at least one Shopify shop that receives real webhooks (trivial — free/dev store), and (b) a target topic/body combination that is invariant or attacker-influenceable enough to collide across shops (e.g., empty-body compliance webhooks, or topics whose payload the attacker can force to match by taking an equivalent action in their own store, such as creating an object with identical field content). This does not require possession of `api_secret_key`, an access token, or any privileged access — only ordinary use of the gem-consuming app's public webhook endpoint, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise explicitly bind the verified digest to the claimed shop before trusting `request.shop` downstream. At minimum, `Request#to_signable_string` should incorporate the shop domain so that a valid signature for one shop's payload cannot be replayed with a different shop header and still validate.

### Proof of Concept
1. Attacker owns Shop A and has app installed; Shopify sends a real webhook for a topic with a static/empty JSON body, e.g. `raw_body = "{}"`, with headers:
   `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of "{}">`.
2. Attacker captures this HMAC value (it is delivered to their own endpoint, so no secret is needed).
3. Attacker sends a POST to the target app's webhook endpoint with the same `raw_body = "{}"` and the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `"{}"` only [1](#0-0)  and it matches, so validation passes [5](#0-4) .
5. `Registry.process` dispatches the handler with `shop: "shop-b.myshopify.com"` [6](#0-5) , causing the app to act on behalf of Shop B based on data that was never authenticated for Shop B.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
