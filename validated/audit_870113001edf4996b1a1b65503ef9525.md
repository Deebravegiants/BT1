Based on my investigation, I found a compelling analog. The `weightedMedian` price-aggregation mechanism in `aggregatePhantomBids` weights each solver's quote by their **live, self-reported token balance** on the destination chain, which is exactly the kind of "deposit briefly to inflate a ratio, then withdraw" surface the report describes — except here the manipulated ratio is the weight used to select the published price/rate that downstream consumers (indexer pool rates, `quoteIntent`) trust as a tradeable quote.

### Title
Phantom bid price can be manipulated by a solver flash-inflating its balance to win the weighted-median price - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights each solver's quote for a phantom-order leg by a single point-in-time read of the solver's ERC-20/vault balance of the leg's output token, taken while the bid window is open. A solver (an unprivileged, ordinary EVM account — anyone can run a solver) can borrow/flash-acquire a large balance of the output token immediately before the window closes, submit a quote that low-balls or highballs the leg amount, and let its inflated weight dominate `weightedMedian`, then move the tokens away right after. This is structurally the same "deposit, get advantage from the ratio, withdraw" pattern the external report describes for pool-ratio manipulation, but the manipulated ratio here is solver-weight rather than pool-reserve ratio.

### Finding Description
`runAggregation` reads each bidding solver's balance via `getBalance(destUrl, chain, outputToken, solver)` [1](#0-0)  and uses that raw balance directly as the weight passed into `weightedMedian`: "A solver holding over half the leg's weight sets the published price verbatim" [2](#0-1) . The balance is a single live read with no minimum holding duration, no vesting, and no cooldown — unlike `StreamingYieldVault`, which explicitly defends the analogous "flash deposit/withdraw" pattern by keying yield recognition to `block.timestamp` so "a deposit and withdrawal in the same block observe an identical share price and capture nothing" [3](#0-2) . No equivalent time-lock exists on the phantom-bid balance weighting.

Because the weight is "the solver's balance of that leg's output token on the destination chain — so a solver holding over half the leg's weight sets the published price verbatim" [4](#0-3) , a solver can flash-borrow the output token (via a DEX flash loan, or simply parking funds from another wallet), submit a bid inside the same bidding window, and move the weight above 50%, forcing `weightedMedian` to select its own quote as the leg's price, verbatim: "lowestPrice and highestPrice are deliberately overwritten with the median so consumers cannot read an outlier bid as a tradeable bound" — but the median itself is exactly the value the manipulated bidder submitted [5](#0-4) . The test suite even documents the boundary case: "when every quote for a leg carries zero weight there is nothing to weight the median by... so on an even-sized set the highest quote wins and any solver holding nothing sets the published rate for free" [6](#0-5) , confirming that weight, not fill-capability, controls the published rate, and there is no mechanism confirming the balance is durable/committed capital rather than a transient flash position.

This published price flows directly into consumer-facing rate data: `updateLiquidityPools` turns it into `PoolChainLiquidity`/`LiquidityPool.sellRate`/`buyRate` rows [7](#0-6) , which `quoteIntent` serves to end users placing real orders: "Quotes an intent from the latest aggregate pool buy or sell rate published by the indexer" [8](#0-7) .

### Impact Explanation
A manipulated median price causes users calling `quoteIntent` to construct real `IntentGatewayV2` orders (`inputs`/`output.assets`) against a false rate. A user who places an order sized off a manipulated favorable quote either escrows too little for the true market rate (order goes unfilled/expires, tokens locked until cancellation) or too much (overpays, since the escrow amount is fixed by the order and not revisited). This is a real-money mispricing of an on-chain escrow reachable from a single manipulated read taken by an unprivileged solver account — no admin, governance, or node compromise required.

### Likelihood Explanation
Running a solver only requires delegating an EIP-7702 SolverAccount and submitting signed bids to the coprocessor — an ordinary, unprivileged capability documented throughout the intent-gateway docs. Flash-acquiring ERC-20 balance for a single block/transaction window is a routine and cheap DeFi primitive. The balance read has no lock-up check, so the barrier to executing this is low, though it requires timing a bid within an active phantom bid window and holding over 50% of that leg's total quoted weight, which limits it to less-liquid legs/pairs.

### Recommendation
Do not weight `weightedMedian` by a raw, single-block balance read. Require the solver's inventory to be sourced from a position with enforced dwell time (mirroring `StreamingYieldVault`'s block-timestamp-gated recognition), or average/attest the balance over multiple blocks within the bid window, or cap any single solver's weight contribution to a fraction of total leg weight so no one bidder can force the median to their own quote.

### Proof of Concept
1. Attacker runs (or controls) a delegated `SolverAccount` for chain `EVM-X`.
2. During an open phantom bid window for order commitment `C`, attacker flash-borrows a large balance of the leg's output token on chain `EVM-X` (e.g., via a DEX flash loan), moving their balance above 50% of all bidders' combined weight for that leg.
3. Attacker submits a signed bid quoting a favorable (mispriced) `outputs[i].amount` for that leg through the normal bid submission flow (`BidManager`/coprocessor).
4. `runAggregation` reads attacker's balance via `getBalance`, computes `weight`, and because attacker's weight exceeds 50% of the leg total, `weightedMedian` (in `phantomAggregation.test.ts`'s own documented boundary behavior) resolves to the attacker's submitted price [9](#0-8) .
5. Attacker returns the flash-borrowed tokens; the manipulated price is already committed to `PhantomOrderPriceSnapshotV2`/`LiquidityPool.sellRate`/`buyRate`.
6. A victim calling `quoteIntent` receives the manipulated rate and places a real `IntentGatewayV2.placeOrder` escrowing tokens against it.
