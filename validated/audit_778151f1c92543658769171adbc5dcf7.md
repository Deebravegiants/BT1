### Title
Emporium's balance check is scoped only to attacker-declared `erc20TokenAddresses`, letting any token balance held by the shared Emporium contract be swept without limit - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only verifies balance conservation for tokens the caller chooses to list in `circomData.erc20TokenAddresses`. Because the `EmporiumStack.ops` are opaque, attacker-supplied calls executed with Emporium itself as `msg.sender`, any token that Emporium happens to hold or receive during those calls but that is *not* included in the declared token list is never checked at all, and can be transferred out to the attacker's own EOA in the same call with zero revert.

### Finding Description
The claimed equality is: for every token actually moved during the Emporium call, `balancesAfter[token] - balancesBefore[token] + (-deltaAmountChanges[i])` must be `>= 0`, enforced by: [1](#0-0) 

This loop is bounded by `circomData.erc20TokenAddresses.length`, and `circomData.erc20TokenAddresses` is a field the attacker fully controls when constructing their own proof/`CircomData`. The ops themselves are arbitrary, attacker-chosen `(endpoint, callData, value)` triples executed by Emporium acting as `msg.sender`: [2](#0-1) 

Nothing in the circuit or in `HinkalHelper`/`Hinkal.sol` decodes or constrains the contents of `op.callData`, so there is no on-chain mechanism forcing `erc20TokenAddresses` to include every token an op actually moves. If an attacker crafts a stack whose ops are `[victim-vault.harvest()]` (which, because Emporium is the caller, sends the harvested reward token to Emporium's own address) followed by `[rewardToken.transfer(attackerEOA, harvestedAmount)]`, and simply omits the reward token from `circomData.erc20TokenAddresses`, the `for` loop at lines 132-151 never iterates over that token at all — the check is not merely satisfied, it is never evaluated. The identical gap exists in the top-level accounting in `Hinkal.sol`, which also iterates only over `circomData.erc20TokenAddresses`: [3](#0-2) 

Because Emporium is a single shared contract used by every Hinkal user for arbitrary DeFi interactions (staking, claiming, swapping), any residual/undeclared token balance it ends up holding — whether from a third-party reward pool paid out to caller `msg.sender` (Emporium's own address), or from another legitimate user's operation that left dust/rewards behind before being swept via `handleOut` — becomes a de-facto public pool that any subsequent, unprivileged attacker can drain with a single `EmporiumUpgradeable.runAction` call, simply by excluding that token from their own declared `erc20TokenAddresses`.

### Impact Explanation
An attacker can steal any token balance sitting on the shared `EmporiumUpgradeable` contract that is not part of their own declared token list — this includes protocol/third-party reward funds routed to Emporium's identity, and any other user's undeclared/residual funds temporarily held by Emporium before being converted into a UTXO. This is theft of in-flight/protocol-side funds via a call path available to any unprivileged EOA that can call `Hinkal.transactExternal` targeting the Emporium external action, matching the Critical category ("direct theft of shielded or in-flight user funds"). The exploit is repeatable for every token Emporium ever accumulates outside a caller's declared set.

### Likelihood Explanation
No special privilege is required — any EOA can call the whitelisted `Emporium` external action via `Hinkal.sol`, construct their own `CircomData` (including choosing which tokens to declare in `erc20TokenAddresses`), and supply an arbitrary `EmporiumStack` of ops. The only precondition is that Emporium holds (or can be made to receive, e.g. via a public/permissionless `harvest()`-style call) a balance of some token the attacker chooses not to declare. Given Emporium's role as a shared, general-purpose call forwarder for many independent user actions, such undeclared residual balances are a realistic and recurring occurrence.

### Recommendation
Do not let the caller choose which tokens are checked. Either (a) require `circomData.erc20TokenAddresses` to enumerate a fixed/allow-listed superset of tokens relevant to the specific ops being executed and enforce this on-chain, or (b) snapshot and diff Emporium's balance for every token actually touched (e.g., every ERC20 address referenced in `op.endpoint`/`op.callData`, or a strictly enumerated allow-list per integration), rejecting any op whose target/token is not covered by the balance-conservation check, so that no token balance can leave Emporium unaccounted for.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `RewardVault` with a permissionless `harvest()` that sends `rewardToken` to `msg.sender`, and `rewardToken` as a mock ERC20.
2. Have some balance of `rewardToken` be sent to `RewardVault` so `harvest()` pays out to whoever calls it (or alternatively, pre-fund Emporium directly with `rewardToken` to simulate residual balance from a prior legitimate op).
3. As attacker, build `CircomData` where `erc20TokenAddresses` excludes `rewardToken` (e.g., only lists an unrelated dummy token or is empty for this token), `amountChanges`/`deltaAmountChanges` contain nothing for `rewardToken`.
4. Build `EmporiumStack.ops = [ {endpoint: RewardVault, callData: harvest()}, {endpoint: rewardToken, callData: transfer(attackerEOA, harvestedAmount)} ]`, with `invokeWallet = false`, `signerAddress = address(0)`.
5. Call `Hinkal.transactExternal(...)` (or equivalent) targeting the Emporium action id with a validly generated proof for the declared token set only.
6. Assert `rewardToken.balanceOf(attackerEOA)` increased by `harvestedAmount` while `circomData.erc20TokenAddresses`/`amountChanges` never referenced `rewardToken`, and that `EmporiumUpgradeable.runAction` did not revert with `BalanceChangeShouldBePositive`.
