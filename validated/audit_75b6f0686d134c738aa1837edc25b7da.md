### Title
Shared, stateful `CallDispatcher` lets order calldata leave standing ERC-20 approvals that persist beyond a single fill/order and can later drain any token that transits it - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, permanent, address-fixed contract shared by every order placed through `IntentGatewayV2` (and by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment configured with it). Its `dispatch()` executes attacker-supplied `Call[]` with no restriction on target or calldata [1](#0-0) . Any user's `order.predispatch.call` or `order.output.call` can therefore instruct the dispatcher to `approve()` an arbitrary spender for an arbitrary token, and that approval is a permanent state change on the ERC-20 contract that outlives the transaction that created it. This is analogous to the RigoBlock incident, where a generic, insufficiently constrained call/exchange mechanism inside a shared custody contract let an attacker manipulate approvals/allowances and put assets other than the "safe" ones at risk.

### Finding Description
`IntentGatewayV2.placeOrder` and `IntentsBase._execute` route escrowed assets through `_params.dispatcher` (the `CallDispatcher`) whenever an order carries `predispatch.call` or `output.call`:

- Assets are pushed to the dispatcher, `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` runs the user-supplied calls, and only afterward are the *declared* input tokens swept back with a plain `transfer` [2](#0-1) .
- On fill, `_execute` dispatches `order.output.call` and then sweeps only the balances of the tokens listed in `order.output.assets` (bounded by `outputsLen`) [3](#0-2) .

Nothing in `CallDispatcher.dispatch` or in the callers validates *what* the calls do — a call is free to be `IERC20(anyToken).approve(attacker, type(uint256).max)`. Because `CallDispatcher` is one fixed, reused contract (not a disposable per-call proxy), that approval is not scoped to the current transaction: it is a durable allowance from the dispatcher to the attacker for `anyToken`, on top of whatever the dispatcher happens to hold at any later time.

The protocol's own documentation acknowledges the mechanism is dangerous but only advises callers to be careful, it does not enforce anything on-chain: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution" [4](#0-3) . This is advisory only; the contract enforces no cap, no revocation, and no allowlist of callable targets/selectors.

Compounding this, the sweep after `_execute` only clears balances for tokens explicitly listed in `order.output.assets` — any other token balance the calldata causes to land on the dispatcher (e.g., an intermediate swap-path token, or dust from a router) is never zeroed and remains on the dispatcher indefinitely [5](#0-4) . Likewise the predispatch sweep only iterates `order.inputs` [6](#0-5) .

### Impact Explanation
An attacker places one low-cost order whose `predispatch.call` or `output.call` grants the dispatcher's unlimited approval of some token `T` to an attacker-controlled address, with no requirement that `T` even be one of that order's declared inputs/outputs. From that point forward, the `CallDispatcher` carries a standing `T.allowance(dispatcher, attacker) = type(uint256).max`. Any subsequent balance of `T` that ever sits on the dispatcher — whether from another user's `predispatch`/`output` flow involving `T` as an intermediate hop, or from any dust the sweep logic fails to capture because `T` was not declared in that order's asset list — is transferable to the attacker via a plain `transferFrom`, independent of the intended order flow. This is theft of funds routed through a shared protocol contract, not limited to the attacker's own escrow, matching the RigoBlock bug class (a shared exchange contract's generic call surface being used to plant an exploitable approval that threatens assets besides the ones the developers considered "safe").

### Likelihood Explanation
Reachable from a single, unprivileged `placeOrder`/`fillOrder` transaction — no privileged role, governance, or off-chain trust is required. The `Call[]` executed by `CallDispatcher` is fully attacker-controlled calldata inside an order any address can submit, and `dispatch()` performs no target/selector allowlisting [1](#0-0) . The only mitigation currently is a documentation recommendation to callers to use exact approval amounts, which does not stop a malicious order from doing otherwise.

### Recommendation
- Have `CallDispatcher` (or the caller before/after `dispatch`) explicitly revoke any non-zero allowance it granted during the call before returning, or restrict `dispatch` to disallow `approve` calls entirely and require pre-approved fixed-amount transfers instead.
- Sweep the *entire* token balance for every token touched by a dispatched call, not only the tokens declared in `order.inputs`/`order.output.assets`, so stray balances cannot accumulate.
- Consider deploying an ephemeral, single-use dispatcher (e.g., minimal proxy per order) instead of one shared, stateful contract, so any approval or balance is scoped to that one call's lifetime.

### Proof of Concept
1. Attacker calls `placeOrder` with `predispatch.assets = []`, `predispatch.call = abi.encode([Call({to: T, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})])`, where `T` is any ERC-20 the attacker wants to target; `order.inputs`/`order.output.assets` need not reference `T` at all.
2. `IntentGatewayV2.placeOrder` forwards this call to `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [7](#0-6) ; `CallDispatcher` executes it verbatim, setting `T.allowance(dispatcher, attacker) = max`.
3. At any later time, whenever `T` balance appears on the dispatcher (via another order's predispatch/postdispatch flow involving `T`, or as unswept dust from a swap path), the attacker calls `T.transferFrom(dispatcher, attacker, balance)` directly, draining it — independent of and unauthorized by the order that put it there.

        if (order.output.call.length == 0) return;

        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);

                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)

                ++i;
            }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
