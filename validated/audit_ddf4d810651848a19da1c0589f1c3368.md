### Title
Spot-price-based valuation of declared Uniswap V4 positions lets a solver forge phantom-bid weight and single-handedly set the published FX price - (File: `sdk/packages/sdk/src/protocols/intents/uniswap-v4-position.ts`, `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`positionAmountOfToken`/`getAmountsForLiquidity` value a solver's declared Uniswap V4 LP position purely off the pool's *instantaneous* `sqrtPriceX96` read at RPC-query time, with no comparison against any independent/TWAP reference price. This is fed directly into the weight used by `weightedMedian` in `runAggregation`, and the aggregation docs establish that the median is a **selection, not a blend** — a bidder holding over half a leg's weight sets the published price verbatim.

### Finding Description
`getAmountsForLiquidity` mirrors Uniswap's `LiquidityAmounts.getAmountsForLiquidity`: below a position's tick range it is entirely `token0`, above it entirely `token1`, and the boundary is exactly the current pool tick. [1](#0-0) 

`positionAmountOfToken` applies this to a declared position using `state.sqrtPriceX96`, which is read live from the pool. [2](#0-1) 

In `runAggregation`, this valuation is added straight into the per-leg `weight` used by the liquidity-weighted median that decides the leg's published price, after confirming only that the solver *owns* the declared position — never that the pool's spot price is not being manipulated: [3](#0-2) 

The median's own semantics make this dangerous: it "returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted." [4](#0-3) 

This is the same bug class as the referenced UniswapV3AM report: a narrow-range (even single-tick) LP position's reported composition flips entirely to one token depending on which side of the tick the spot price currently sits, and the contract/pipeline trusts that spot reading unconditionally rather than reconciling it against an oracle or historical price. A solver can (a) open a minimal-capital, narrow-range V4 position that straddles the current tick for the exact output token of a leg it wants to dominate, and (b) briefly move the pool's spot price (e.g. via a same-block swap) so that, at the moment the indexer's RPC read lands, the position appears to be composed entirely of the leg's output token — inflating `positionAmountOfToken` and hence its bid `weight` far beyond what its real capital could ever deliver. Because `weightedMedian` is a selection over weights, a large enough forged weight lets the attacker's own (possibly worthless or predatory) quote become the leg's `medianPrice`/`lowestPrice`/`highestPrice` verbatim.

### Impact Explanation
The published `medianPrice` feeds `PhantomOrderPriceSnapshotV2` and then `updateLiquidityPools`, which renormalizes it into the `LiquidityPool.sellRate`/`buyRate` rows. [5](#0-4) 

Those pool rates are consumed by `getFxPriceFromPools` to price non-stable tokens in USD for downstream consumers, including `BidManager`'s mixed-output USD valuation that ranks/selects real fills. [6](#0-5) [7](#0-6) 

A solver able to forge disproportionate weight can therefore publish an arbitrary FX rate for a pair with minimal real backing capital, which corrupts the price other solvers/consumers rely on to rank bids and to size fills — a route to systematically mispriced or manipulated fills (value extraction from users or from the protocol's own bid-selection logic), i.e. a concrete route to fund misallocation via a forged/manipulated intent price, reachable by any unprivileged solver submitting a phantom bid.

### Likelihood Explanation
Reachability is straightforward: any address willing to become a delegated solver can submit a phantom bid that declares an owned Uniswap V4 position — no privileged role is required. Executing the price-shift itself requires a swap sized to move the pool's tick and land within the window the indexer's RPC read is taken, which is a routine MEV-style, single-transaction manipulation, especially against thinner pools (the very pools the phantom pricing pipeline is designed to source liquidity from). The absence of any TWAP check, reference-price guard (unlike the analogous `referencePrice`/`maxDeviationBps` guard that exists in Simplex's own venue-pricing path), or slippage/staleness bound on `sqrtPriceX96` in this valuation path makes the manipulation low-effort relative to its ability to hijack a "selection" median.

### Recommendation
- Do not value a declared V4 position off a single live `sqrtPriceX96` read. Use a TWAP (time-weighted average tick) over a meaningful window, or cross-check the spot tick against an independent price source and reject/clamp the declaration if it deviates beyond a bounded threshold — mirroring the `referencePrice`/`maxDeviationBps` guard already implemented for Simplex's own venue pricing (`docs/content/developers/evm/simplex/pricing.mdx`).
- Cap a single declared position's contribution to a leg's weight (e.g., as a fraction of the pool's total liquidity or of the leg's aggregate weight) so no single narrow-range position can dominate the weighted median.
- Consider requiring a minimum tick-range width for a declared position to count toward weight, since positions near a single tick are the ones most trivially flippable between all-token0/all-token1.

### Proof of Concept
1. Solver deploys `SolverAccount` and delegates per the phantom-bid protocol (`delegateToSolverAccount` pattern used in tests).
2. Solver opens a Uniswap V4 position with minimal liquidity but a very narrow tick range straddling the current tick of the pool for `token X` (the leg's output token), and declares this `tokenId` in `paymasterAndData` per `decodePhantomBidPaymasterAndData`.
3. When a phantom order opens a bid window for a leg outputting `token X`, the solver front-runs the aggregation RPC read with a swap that pushes the pool's spot tick to the side of its range that is 100% `token X` (per `getAmountsForLiquidity`'s below/above-range branches), then reverts the swap (or lets arbitrage restore it) once the read is captured.
4. `runAggregation` computes `positionAmountOfToken(...)` for this position using the manipulated `sqrtPriceX96`, adding a large `weight` to the solver's quote for that leg. [8](#0-7) 
5. If this weight exceeds half the leg's total weight, `weightedMedian` selects the manipulating solver's quoted price verbatim as `medianPrice`, which is then persisted to `PhantomOrderPriceSnapshotV2` and propagated into `LiquidityPool.sellRate`/`buyRate`, corrupting the FX price other consumers (e.g. `BidManager.sortMixedOutputs`) rely on.

export function getAmountsForLiquidity(params: {
	sqrtPriceX96: bigint
	sqrtRatioAX96: bigint
	sqrtRatioBX96: bigint
	liquidity: bigint
}): { amount0: bigint; amount1: bigint } {
	let { sqrtRatioAX96, sqrtRatioBX96 } = params
	const { sqrtPriceX96, liquidity } = params
	if (sqrtRatioAX96 > sqrtRatioBX96) [sqrtRatioAX96, sqrtRatioBX96] = [sqrtRatioBX96, sqrtRatioAX96]

	const amount0For = (from: bigint, to: bigint) => (liquidity * Q96 * (to - from)) / to / from
	const amount1For = (from: bigint, to: bigint) => (liquidity * (to - from)) / Q96

	if (sqrtPriceX96 <= sqrtRatioAX96) {
		return { amount0: amount0For(sqrtRatioAX96, sqrtRatioBX96), amount1: 0n }
	}
	if (sqrtPriceX96 < sqrtRatioBX96) {
		return {
			amount0: amount0For(sqrtPriceX96, sqrtRatioBX96),
			amount1: amount1For(sqrtRatioAX96, sqrtPriceX96),
		}
	}
	return { amount0: 0n, amount1: amount1For(sqrtRatioAX96, sqrtRatioBX96) }
}

export function positionAmountOfToken(params: {
	info: PoolAndPositionInfo
	liquidity: bigint
	sqrtPriceX96: bigint
	outputToken: string
}): bigint {
	const { info, liquidity, sqrtPriceX96 } = params
	const outputToken = params.outputToken.toLowerCase()
	if (outputToken !== info.currency0 && outputToken !== info.currency1) return 0n
	if (liquidity <= 0n || sqrtPriceX96 <= 0n) return 0n

	const { amount0, amount1 } = getAmountsForLiquidity({
		sqrtPriceX96,
		sqrtRatioAX96: getSqrtRatioAtTick(info.tickLower),
		sqrtRatioBX96: getSqrtRatioAtTick(info.tickUpper),
		liquidity,
	})
	return outputToken === info.currency0 ? amount0 : amount1
}

"""
A cross-chain liquidity pool for one token pair, identified by the canonical slug of the two
symbols sorted case-insensitively (e.g. cNGN-USDC). Upserted by the phantom price handler: each
chain's phantom order samples the same market price (solvers arbitrage away per-chain drift), so
the pool's single price per direction is the depth-weighted merge of the chains' latest samples,
while depth is what actually varies per chain.

Rates are output token units per 1 whole input token, scaled 1e18. Depths are 18-decimal
normalized. A pair registered in only one direction in the pallet leaves the other side null.
"""
type LiquidityPool @entity {
	"""
	Canonical pair slug: {token0Symbol}-{token1Symbol}, symbols sorted case-insensitively.
	"""
	id: ID!

	"""
	First symbol in the sort order, in the registry's canonical casing.
	"""
	token0Symbol: String! @index

	"""
	Second symbol in the sort order; equals token0Symbol for a same-asset pool.
	"""
	token1Symbol: String! @index

	"""
	SELL price: token1 units received per 1 whole token0, scaled 1e18, depth-weighted across the
	chains' latest samples. Null until the token0 -> token1 direction is first priced. A same-asset
	pool's legs always resolve to SELL, so its baseline-margin measurement lands here and buyRate
	stays null.
	"""
	sellRate: BigInt @index

	"""
	BUY price: token0 units received per 1 whole token1, scaled 1e18. The inverse quote of
	sellRate's, not its reciprocal — it is measured from the token1 -> token0 legs. Null until
	that direction is first priced.
	"""
	buyRate: BigInt @index

	 * Price an FX token in USD from its liquidity pool against a $1 stable. Pool rates are
	 * decimals-free (output per 1 whole input, 1e18-scaled) and already merged across chains, so
	 * no address or decimals context is needed — any chain's representation prices identically.
	 * Prefers the direct FX -> stable side; falls back to the reciprocal of the stable -> FX side
	 * when only that direction is registered. Null when no pool has priced the symbol yet.
	 */
	private static async getFxPriceFromPools(symbol: string): Promise<Decimal | null> {
		const canonical = canonicalPoolSymbol(symbol)
		if (!canonical) return null

		for (const quote of STABLE_SYMBOLS) {

			if (!pool) continue

			const { direct, inverse } = orientedPoolRates(pool, canonical)

				return new Decimal(direct.toString()).div(POOL_RATE_SCALE)
			}
			if (inverse && inverse > 0n) {
				return POOL_RATE_SCALE.div(new Decimal(inverse.toString()))
			}
		}
		return null
