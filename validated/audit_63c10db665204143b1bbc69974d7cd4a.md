### Title
Governance can permanently freeze in-flight escrow releases by rotating the registered `IntentGateway` instance address - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` authenticate incoming `RedeemEscrow`/`RefundEscrow` messages by checking that `request.from` equals the single currently-registered gateway address for the source chain, stored in `_instances`. This mapping is a single-slot overwrite with no history: when Hyperbridge governance dispatches a `NewDeployment` message to rotate/replace the counterpart gateway address for a chain, any `RedeemEscrow`/`RefundEscrow` message that was already dispatched (with `from` fixed to the old, now-deregistered address) but not yet delivered/relayed will permanently fail authentication once it lands, since the `from` field baked into an already-dispatched ISMP message cannot be changed to match the new instance. This mirrors the Homora "governor can prevent user repaying debt" bug class: a routine, non-malicious governance action (rotating a whitelisted counterpart address) can permanently strand already-escrowed user/solver funds with no recovery path for those specific in-flight messages.

### Finding Description
`_instances` maps `keccak256(stateMachineId) => gateway address` and is resolved via `_instance()`/`instance()`: [1](#0-0) 

Incoming `RedeemEscrow`/`RefundEscrow` requests are authenticated against this single stored address: [2](#0-1) 

`onAccept` routes based on `RequestKind`, calling `_authenticate` before releasing escrow, and processes `NewDeployment` (governance-only, via Hyperbridge) which unconditionally **overwrites** `_instances` for that chain: [3](#0-2) 

The Tron/EVM sibling implementation has the identical pattern — `authenticate()` checks `instance(request.source) != module`, and `NewDeployment` replaces `_instances[...]` with no versioning or grace window: [4](#0-3) [5](#0-4) 

Because ISMP messages are immutable once dispatched (the `from` field is fixed at dispatch time on the remote chain and cannot be re-signed by a new address), any `RedeemEscrow`/`RefundEscrow` message dispatched from the old gateway instance before a `NewDeployment` update propagates, but delivered/relayed after it, will hit `revert Unauthorized()` in `_authenticate`/`authenticate` forever. There is no fallback authorizing "the previously valid instance for messages already in flight." Unlike the standard order-cancellation path (`onGetResponse`, which validates via storage proof rather than the instance whitelist and is therefore unaffected), the fill-confirmation path (`RedeemEscrow`, used to pay the filler/solver after a successful cross-chain fill) has no equivalent bypass — once blocked, the solver's escrowed collateral is permanently unrecoverable through the normal flow.

### Impact Explanation
This is a permanent freezing-of-funds vulnerability. A solver who fills an order and dispatches `RedeemEscrow` from the (soon to be rotated) old gateway instance will find their claim on the source-chain escrow permanently rejected if governance updates the registered instance for that chain before the message is relayed — a realistic timing given typical multi-day ISMP finality/challenge periods for consensus proofs. Escrowed source-chain tokens (`_orders[commitment][token]`) remain locked in the contract indefinitely for that commitment, since `_filled[commitment]` was already set optimistically on the destination side during the fill, leaving no way to re-trigger a valid redemption. This is not caused by a compromised or malicious relayer/attacker; it results from a normal governance maintenance operation (gateway migration/rotation), which is exactly the pattern flagged in the referenced Homora report — governance changing a whitelist state can strip legitimate users/solvers of funds already committed under the old, valid rule set.

### Likelihood Explanation
Medium. `NewDeployment` is a routine, expected governance operation (e.g. re-deploying/upgrading the counterpart `IntentGatewayV2` on a chain, or migrating instances), and Hyperbridge's own cross-chain consensus/challenge periods mean there is a non-trivial window during which in-flight `RedeemEscrow`/`RefundEscrow` messages dispatched under the old instance can still be delivered after the mapping has already been rotated. No malicious actor is required; this can happen during ordinary maintenance.

### Recommendation
Do not treat `_instances` as a single-slot pointer that is unconditionally overwritten. Either (a) retain a bounded history/allowlist of previously valid gateway addresses per chain for a configurable grace period covering the maximum in-flight message lifetime, so `_authenticate` accepts messages from a recently-deprecated instance during migration, or (b) require that a `NewDeployment` rotation only take effect after all in-flight messages referencing the old instance have settled (e.g. via a two-phase/queued rotation), or (c) add a governance-gated recovery path (analogous to `SweepDust`) allowing stuck `_orders[commitment][...]` balances tied to unauthenticatable in-flight messages to be manually released to the intended beneficiary.

### Proof of Concept
1. User places an order on chain A via `IntentGatewayV2`/`ExtrinsicIntents` with `_instances[keccak256(chainB)] = GatewayB_v1`.
2. Solver fills the order on chain B (`GatewayB_v1`), which dispatches a `RedeemEscrow` POST request back to chain A with `request.from = GatewayB_v1`.
3. Before this message is relayed/delivered on chain A, Hyperbridge governance dispatches a legitimate `NewDeployment` message rotating the registered instance: `_instances[keccak256(chainB)] = GatewayB_v2` (e.g. migrating to an upgraded gateway on chain B) — analogous to the flow exercised in `testOnAcceptGovernanceRejectsUnlistedRelayer`/`_newDeploymentRequest` in the test suite: [6](#0-5) 
4. The relayer subsequently delivers the earlier `RedeemEscrow` message. `onAccept` calls `_authenticate`, which now compares `request.from == GatewayB_v1` against `_instance(chainB) == GatewayB_v2`, reverting with `Unauthorized`.
5. The message can never be successfully retried under a different `from` address (it was already dispatched and committed on chain B with `GatewayB_v1` as sender), so the solver's escrowed collateral for that commitment remains locked in `_orders[commitment][token]` on chain A indefinitely, with no available recovery mechanism apart from a manual governance-level fix outside the protocol's designed flows.

    /**
     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }

    /**
     * @dev Authenticates an incoming cross-chain post request by verifying that the
     * sender module matches the registered gateway instance for the source chain.
     * Reverts with InvalidInput if the sender address is malformed, or Unauthorized
     * if the sender is not the expected gateway.
     * @param request The incoming post request to authenticate.
     */
    function _authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }

        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);

            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
