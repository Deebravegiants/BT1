### Title
Outbound consensus/request delivery rewards read the live reward-config storage at claim time, letting a governance reward update strand already-earned relayer rewards - ([File: modules/pallets/relayer/src/outbound_consensus.rs], [File: modules/pallets/relayer/src/outbound_request.rs])

### Summary
`pallet-ismp-relayer`'s outbound consensus and outbound request delivery-reward claim paths look up the *current* value of `OutboundConsensusDeliveryReward` / `OutboundRequestDeliveryReward` at the moment the claim extrinsic is processed, rather than a value captured or locked in at the time the relayer actually performed the (irreversible, on-chain, gas-costing) delivery. If governance lowers or zeroes the reward for a chain/module between delivery and claim, a relayer who already delivered the mandatory consensus rotation or the hyperbridge-originated request loses part or all of the reward they legitimately earned, with no path to recover it. This mirrors the reported Sherlock issue where removing a reward token from a list after the qualifying action makes an already-earned reward unclaimable.

### Finding Description
For outbound consensus delivery rewards, `process_outbound_consensus_delivery_claim` reads the reward amount live: [1](#0-0) 

For outbound request delivery rewards, `process_outbound_request_delivery_claim` does the same: [2](#0-1) 

Both amounts are governance-configurable and can be changed (including down to zero) at any time via unsigned/governance-origin calls: [3](#0-2) 

The delivery itself (the mandatory BEEFY authority-set rotation to `EvmHost._epochs[set_id]`, or the hyperbridge-originated request to `RequestReceipts[commitment]`) is a one-time, already-completed, irreversible on-chain event recorded on the *destination* chain — the relayer has already paid gas and won the "relay race" per the docs' description of the flow: [4](#0-3) 

The pallet never snapshots the reward amount that was in effect when the delivery happened; it only records the delivery via the commitment/`(destination,set_id)` idempotency keys (`OutboundRequestsClaimed`, `OutboundConsensusRotationsClaimed`) and the currently configured reward is applied whenever the claim extrinsic is finally submitted and verified. Because verifying a claim requires waiting for Hyperbridge to see a state-proof of the destination past the delivery height (`wait_for_state_machine_update`, consensus proof forwarding, etc.), there is an inherent delay between "delivery happened" and "claim is submitted", during which the relayer has no ability to influence or predict a reward change. If the reward is reduced or set to zero during that window, `ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured)` (or `OutboundNoRewardConfigured` for consensus) rejects the claim outright, or, if merely lowered, silently underpays the relayer relative to what was promised for the actual delivery.

This is the exact bug class from the referenced report: a token/param-list (here, the per-module/per-chain reward config) can be removed/updated at any time, and users (relayers) who already performed the qualifying, reward-earning action lose access to a reward they already earned, because the claim path re-derives the payout from live configuration instead of the configuration in effect when the action occurred.

### Impact Explanation
Any relayer that delivers a mandatory consensus rotation or a hyperbridge-originated request can have their earned reward permanently reduced to zero (or partially reduced) by a subsequent, entirely ordinary reward-configuration update, since:
- The claim requires `reward > 0` at claim time, so if it's zeroed, `OutboundRequestNoRewardConfigured` / `OutboundNoRewardConfigured` permanently blocks the claim for that commitment/`(destination,set_id)` — the delivery event itself is one-time (idempotency key), so there is no way to "redeliver" and re-earn once the config changes back.
- If merely lowered rather than zeroed, the relayer is underpaid for work that was priced (implicitly, by the relayer's decision to spend gas competing for the reward) under the old reward level.

This is a real loss of funds for relayers — the entities the protocol is specifically designed to economically incentivize — and can also degrade the security assumption that mandatory consensus rotations and hyperbridge-originated governance requests are reliably relayed, since relayers cannot trust that pending rewards for work already done are safe from a later parameter update.

### Likelihood Explanation
Reward parameters (`OutboundConsensusDeliveryReward`, `OutboundRequestDeliveryReward`) are explicitly designed to be adjustable via governance/`RelayerOrigin` at any time with no cooldown, timelock, or grandfathering for in-flight claims: [3](#0-2) 
Given that claim submission is inherently delayed behind state-proof/consensus availability on Hyperbridge, and reward tuning is an expected, routine governance operation (not an attack), the window in which a relayer's already-completed delivery can be devalued or nullified by a legitimate config change is realistically and repeatably reachable, not a contrived edge case.

### Recommendation
Snapshot the applicable reward amount at delivery time rather than at claim time — e.g., have the destination-side delivery event (or an intermediate on-chain record keyed by commitment/`(destination,set_id)`) capture the reward value in effect at delivery, and have `process_outbound_consensus_delivery_claim` / `process_outbound_request_delivery_claim` pay out that captured value instead of re-reading `OutboundConsensusDeliveryReward` / `OutboundRequestDeliveryReward` live. Alternatively, apply a grace/vesting mechanism so reward reductions only take effect for deliveries that occur after the change is finalized, and never zero out rewards for deliveries that already completed under the previous configuration.

### Proof of Concept
1. Governance sets `OutboundRequestDeliveryReward[module_id] = R` via `set_outbound_request_delivery_reward` (call_index visible in `modules/pallets/relayer/src/lib.rs`).
2. A relayer observes the allowlist, delivers a hyperbridge-originated `PostRequest` for `module_id` to its destination chain (per `docs/outbound-request-incentivization.md` steps 3–5), writing the delivery receipt into `RequestReceipts[commitment]` on the destination.
3. Before the relayer's claim task can submit `claim_outbound_request_delivery_reward` (it must first wait for Hyperbridge's state-machine height for the destination to advance past the delivery height), governance calls `set_outbound_request_delivery_reward(module_id, 0)` (a routine, non-malicious adjustment, e.g. because the module no longer needs the incentive).
4. When the relayer submits `OutboundRequestDeliveryClaim`, `process_outbound_request_delivery_claim` reads `OutboundRequestDeliveryReward::<T>::get(&module_id)` as `0` and reverts with `Error::<T>::OutboundRequestNoRewardConfigured`, per: [5](#0-4) 
5. Because `OutboundRequestsClaimed`/commitment tracking is one-shot (the delivery already happened and cannot be "redone"), the relayer permanently forfeits the reward for work it already completed.

### Why testnet delivery is a race

The reward goes to whichever relayer lands the delivery transaction on the destination chain first. That relayer's address is what the destination's ISMP host writes into `RequestReceipts[commitment]`, and `process_outbound_request_delivery_claim` only pays the address proven in that slot. A relayer that delivers second just no-ops, and its claim fails `OutboundRequestSignerMismatch`. The on-chain reward is registered globally, so every relayer watching gargantua sees the module in its allowlist snapshot and competes. Running locally sidesteps this: your relayer is the only one delivering.
