### Title
Missing Signup-Session Binding in Secure-Element Iris-Code Signature Enables Cross-Signup Replay - (File: `src/plans/enroll_user.rs`)

### Summary
The Orb's `make_signature` function computes the digest that is signed by the Secure Element to attest that the iris codes attached to a signup were produced by this Orb for this user. The digest binds `ORB_ID`, the user's QR `user_id`, and the iris/mask codes, but it does **not** bind the `signup_id` (the value that uniquely identifies this specific signup attempt/session). This is structurally identical to the reported bug class: a signature/attestation that omits the domain-separating identifier (there: `chainId`; here: `signup_id`) can be replayed outside the context it was meant to authorize.

### Finding Description
`make_signature` in [1](#0-0)  builds a SHA-256 context over `ORB_ID`, `user_qr_code.user_id`, and the iris/mask codes and versions for both eyes, then signs it via `secure_element::sign`:
```
ctx.update(ORB_ID.as_str().as_bytes());
ctx.update(user_qr_code.user_id.as_bytes());
ctx.update(pipeline.v2.ir_net_version.as_bytes());
...
let signed = secure_element::sign(ctx.finish())?;
```
None of the fields hashed here are unique per signup attempt — the same physical iris naturally yields the same iris/mask codes across repeated captures, so the resulting Secure-Element signature is deterministic for a given user on a given Orb regardless of *when* or under what `signup_id` it was produced.

The signature is then submitted together with an out-of-band `signup_id` at [2](#0-1) , and the HTTP request itself places `signup_id` only in the URL path while the `signature` field travels in the multipart form, unbound to that path parameter, as seen in `signup_post::request`: [3](#0-2) . Because `signup_id` (the session/domain identifier) is never part of what the Secure Element actually signs, a previously captured `(signature, codes, orbId, userId)` tuple is valid input for a *different* `signup_id` endpoint call, exactly mirroring the missing-`chainId` class of bug: the signed payload lacks the context-binding value that should prevent reuse outside its original transaction/session.

### Impact Explanation
This allows attestation replay across signup sessions: an attacker who can capture or retain one legitimate signup's multipart payload (signature + iris codes + orbId + userId) can resubmit it against a new `signup_id`, producing a new signup request that still carries a "valid" Secure-Element attestation despite no fresh biometric capture having occurred for that attempt. This undermines the attestation's intended guarantee (fresh iris capture from real hardware for *this* signup) and enables cross-signup state bleed / attestation forgery — an old attestation is misattributed to a new signup context.

### Likelihood Explanation
Exploitability depends on an attacker having network/data access to a prior signup's multipart payload (e.g., via a compromised or malicious client-side component submitting requests, or a captured/replayed backend request), which is a realistic no-privilege-escalation scenario for a party that already interacts with the signup HTTP flow. The root cause — missing domain separation in the signed digest — is unconditionally present in `make_signature` and requires no additional preconditions beyond obtaining one prior valid signature/codes tuple.

### Recommendation
Include the `signup_id` (and ideally a fresh per-attempt nonce/timestamp) in the data hashed and signed by the Secure Element in `make_signature`, so the resulting signature is cryptographically bound to the specific signup session it was generated for, analogous to adding `chainId`/`address(this)` to the EIP-4337 `getHash` computation.

### Proof of Concept
1. Orb performs a legitimate signup for `user_id = U`, producing iris codes `C` and Secure-Element signature `S = sign(ORB_ID || U || C)` (see [1](#0-0) ).
2. An attacker with access to that request's multipart body captures `(orbId, userId=U, codes=C, signature=S)`.
3. Attacker (or a compromised client) later submits a new signup request to `POST /api/v2/signups/{new_signup_id}` (per [4](#0-3) ) reusing `orbId`, `userId=U`, `codes=C`, and `signature=S`.
4. Because `S` never incorporated `new_signup_id`, the signature verifies successfully as if it were freshly generated for this new signup attempt, even though no new biometric capture occurred for it.

```rust
fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
```
