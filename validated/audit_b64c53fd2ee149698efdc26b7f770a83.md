### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated HTTP headers while `Registry.process` only HMAC-verifies the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler a `shop`, `topic`, `webhook_id`, and `api_version` that are read straight from HTTP headers, none of which are covered by the HMAC signature computed over the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validator computes and compares the signature purely against this signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never included in the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` when constructing the metadata passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop that is cryptographically bound to this payload == shop the handler is told the payload came from`. In this gem, the left side is undefined (no field ties `shop` to the signature) while the right side is an attacker-controlled header. Because the same `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant who has legitimately installed the app can:
1. Receive one authentic webhook for their own shop (valid `x-shopify-hmac-sha256` over a known raw body).
2. Replay that exact raw body to the app's webhook endpoint, but with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header changed to a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the (unchanged) raw body against the shared secret; `Registry.process` then calls the handler with `WebhookMetadata` claiming the payload is for the victim shop.

Any application logic that trusts `data.shop` to select which tenant's records to look up, update, or key by (a common documented pattern - see `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will act on attacker-supplied, forged content under the identity of another tenant. This is inherent to the gem's own verification API, not a misuse of it by a host application, since the gem provides no signal at all that `shop`/`topic`/`webhook_id` were unauthenticated.

### Impact Explanation
This breaks the cross-tenant boundary: an authenticated (but unprivileged with respect to other tenants) app installer can forge webhook events attributed to any other shop using the app, using data they control (their own valid webhook body) combined with headers the gem does not verify. Depending on how the host application uses `data.shop`/`data.body`, this can enable cross-tenant data corruption, spoofed business events, or confusion attacks against another merchant's data - matching the "High: cross-tenant access" / identity-binding-break class described in the report.

### Likelihood Explanation
Any external attacker who is themselves a legitimate (even free-tier) installer of the app can obtain a validly-signed webhook body for their own shop and replay it with modified headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged access is required - only a normal, unprivileged merchant installation, which matches the "unprivileged internet user" threat model.

### Recommendation
Include the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the raw body (e.g., derive/verify `shop` against a per-shop secret or session record looked up independently, and reject requests where header values do not correspond to an installed shop with a matching webhook subscription) before invoking the handler in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. App installer for `attacker-shop.myshopify.com` legitimately receives an `orders/create` webhook: raw body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the shared `api_secret_key`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same raw body `B` and same `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (only `B` and `H` are checked).
4. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under `victim-shop.myshopify.com`'s identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
