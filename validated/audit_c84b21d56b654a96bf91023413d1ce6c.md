### Title
Rounding-to-zero sell on the bonding curve burns tokens with no LT returned - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeSell` / `Router.sell` and `Bonding.sell` never guard against the constant-product output rounding down to zero, mirroring Sherlock H-8's `_convertStrategyTokensToBPTClaim` / `_redeem` bug class: a trader can burn (irrecoverably transfer into the pair) launched-token supply while receiving `0` LT back.

### Finding Description
`Router.sell` unconditionally pulls the trader's tokens into the pair before computing the payout: [1](#0-0) 

```solidity
function sell(uint256 amountIn, address token, address to) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
    if (amountIn == 0) revert ZeroAmount();
    ...
    IERC20(token).safeTransferFrom(to, pairAddr, amountIn);   // tokens moved FIRST
    assetOut = _computeSell(pairAddr, amountIn);               // may compute to 0
    IPair(pairAddr).transferAsset(to, assetOut);                // no-op if 0
    IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
}

function _computeSell(address pairAddr, uint256 amountIn) internal view returns (uint256 assetOut) {
    (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
    uint256 k = pair.k();
    uint256 newReserveToken = reserveToken + amountIn;
    assetOut = reserveAsset - (k / newReserveToken);
}
```

Because integer division truncates, for a small enough `amountIn` (relative to the reserves) `k / newReserveToken` can equal `k / reserveToken` exactly (i.e. `reserveAsset`), making `assetOut = 0`. Neither `_computeSell` nor `Router.sell` reverts on this — exactly the pattern flagged in H-8 for `StrategyUtils._convertStrategyTokensToBPTClaim` returning `bptClaim = 0` and `Boosted3TokenPoolUtils._redeem` silently accepting it.

`Bonding.sell` (`onlyRouter`, reachable from any allowlisted router such as `Zap` or `curveRouter` in tests) only enforces a slippage floor, which a caller can trivially set to `0`, allowing the zero-output sell to succeed silently: [2](#0-1) 

```solidity
function sell(uint256 amountIn, address tokenAddress, uint256 amountOutMin, address trader)
    external onlyRouter nonReentrant returns (uint256)
{
    ...
    (, uint256 assetOut) = $.router.sell(amountIn, tokenAddress, msg.sender);
    if (assetOut < amountOutMin) revert SlippageExceeded();   // 0 < 0 is false — passes
    ...
    return assetOut;
}
```

Once `Router.sell` executes, the trader's tokens are already inside the `Pair` contract (`safeTransferFrom(to, pairAddr, amountIn)`), and `Pair.swap` permanently commits the new reserves: [3](#0-2) 

There is no path back for the trader to reclaim those tokens — they are now indistinguishable from real curve liquidity, and the trader received `0` LT.

### Impact Explanation
Direct, permanent loss of the trader's launched-token holdings for zero compensation, matching the "Loss of assets for the users as they burn their strategy tokens, but receive no assets in return" impact called out in the H-8 report. This is Medium/High severity: unbacked/uncompensated token burn is a concrete fund-loss condition reachable by any unprivileged trader who calls `sell`/`Bonding.sell` (via any allowlisted router) with a small enough `amountIn` and `amountOutMin = 0`.

### Likelihood Explanation
Reachable purely by choosing `amountIn` small relative to the pair's reserves and `amountOutMin = 0`; both are attacker/user-controlled inputs to a permissionless entry point (`Bonding.sell`, exposed to end users through any allowlisted router). No privileged role, special timing, or external price manipulation is required — only picking a sufficiently small sell size, which is trivial given 18-decimal token amounts against large virtual reserves.

Note: I was only able to confirm that `Zap._sellInternal` happens to catch some (not all) of these cases indirectly via its post-hoc `minUsdcAmount` check on `grossUsdcEstimate` (computed from `ltReceived`), which would revert the whole transaction if the curve sell returned 0 LT — but that check runs **after** `_sellOnCurve`/`bonding.sell` already executed, so it only prevents state persistence via revert, not the underlying rounding defect. It is unverified whether every possible dust-sell amount is caught this way, and other allowlisted routers (e.g., a raw `curveRouter`, present in the test harness) may call `Bonding.sell` without any such downstream check at all, in which case the zero-payout burn commits with no revert.

### Recommendation
In `Router._computeSell` (and/or `Router.sell`), revert when the computed `assetOut` is zero, before transferring the trader's tokens into the pair — mirroring the H-8 recommendation:
```solidity
function _computeSell(...) internal view returns (uint256 assetOut) {
    ...
    assetOut = reserveAsset - (k / newReserveToken);
    require(assetOut > 0, "ZeroAssetOut");
}
```
Alternatively, add the same check in `Bonding.sell` immediately after calling `$.router.sell(...)`, before any state is finalized, and ensure it fires regardless of the caller-supplied `amountOutMin`.

### Proof of Concept
1. Seed a curve pair via `Bonding` launch with large virtual reserves (production seeding, e.g. `virtualReserveToken = 1e9 * 1e18`, `reserveAsset` on the order of the virtual LT liquidity).
2. Buy a modest amount of tokens as `trader` so `trader` holds a token balance.
3. Compute (or brute-force via `Router.getAmountOut(token, false, amountIn)`/`previewSell`-style call) the smallest `amountIn` where `reserveAsset - (k / (reserveToken + amountIn)) == 0` — for large reserves this can be satisfied by a very small `amountIn` (down to `1` wei of the 18-decimal token).
4. As `trader`, call `Bonding.sell(amountIn, tokenAddress, 0, trader)` (via any allowlisted router).
5. Observe: `Router.sell` transfers `amountIn` tokens from `trader` into the `Pair`, `_computeSell` returns `assetOut = 0`, `Bonding.sell`'s check `0 < 0` passes, and the transaction succeeds — `trader` permanently loses `amountIn` tokens for `0` LT.

    /// @notice Sell tokens on the curve. Router-only.
    function sell(
        uint256 amountIn,
        address tokenAddress,
        uint256 amountOutMin,
        address trader
    ) external onlyRouter nonReentrant returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.creator == address(0)) revert TokenNotTrading();
        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();
        // A graduatable curve token must graduate, not sell back below the
        // threshold. The user-facing router triggers graduation up front via
        // `triggerGraduation`; rejecting here stops any router that skipped
        // that step from un-ripening a ready graduation.
        if (canGraduate(tokenAddress)) revert TokenIsGraduating();

        (, uint256 assetOut) = $.router.sell(amountIn, tokenAddress, msg.sender);
        if (assetOut < amountOutMin) revert SlippageExceeded();

        (uint256 newCurveSupply, uint256 newLtReserve) = _getCurveState(tokenAddress);
        emit Trade(tokenAddress, trader, false, assetOut, amountIn, newCurveSupply, newLtReserve);
        return assetOut;
    }

        uint256 tokenIn,

        uint256 assetIn,

    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
