### Title
Webhook Shop/Topic Identity Confusion — HMAC Covers Only the Raw Body, Not the Shop/Topic Headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values read from HTTP headers to build the `WebhookMetadata` passed to the app's handler. Those header values are never covered by the HMAC signature, so the "authenticated" identity (which tenant/shop the event belongs to, and what topic it is) is not actually bound to the cryptographic proof of authenticity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight out of request headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header/method: [3](#0-2) 

Because `to_signable_string` for a webhook request is just `@raw_body`, the HMAC check only proves "this body was signed by someone holding `api_secret_key`" — it proves nothing about which shop or topic header accompanied that body. `Registry.process` nonetheless uses the raw, unauthenticated `request.shop` and `request.topic` to route and to construct the metadata object handed to app-provided handlers: [4](#0-3) 

The implicit identity binding the gem is supposed to enforce is:
`hmac_valid_for(raw_body) == (shop_header_is_authentic AND topic_header_is_authentic)`

But the actual code only proves `hmac_valid_for(raw_body)`; `shop_header` and `topic_header` are independent, attacker-controllable fields once an attacker can reach the app's webhook endpoint with any *body* for which they can produce a valid HMAC (e.g., a body previously delivered to their own, legitimately-owned/installed shop). This is the same bug class as the reported issue — trusting untyped/unchecked auxiliary data (there, the account discriminator; here, the shop/topic headers) that sits outside the verified boundary (there, the Borsh size-only check; here, the HMAC-of-body-only check).

### Impact Explanation
A multi-tenant app built on this gem uses `WebhookMetadata#shop` to determine which merchant's records to read or mutate (e.g. update an order, delete customer data for `customers/redact`, or provision/deprovision resources for `app/uninstalled`). Because `shop` is taken from an unauthenticated header rather than from data actually covered by the HMAC, an attacker who can obtain one valid `(raw_body, hmac)` pair — trivially available to anyone who installs the app on their own store and receives one genuine webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim shop. `Registry.process` will accept it (HMAC validates) and hand the handler a `WebhookMetadata` claiming the event is for the victim shop, leading to cross-tenant data confusion (e.g., triggering `app/uninstalled` cleanup or `customers/redact` deletion against a shop the attacker does not control). This falls under the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) an attacker-controlled/installed shop to legitimately receive one webhook delivery with a valid HMAC for a given body, and (2) the ability to POST directly to the app's public webhook endpoint with custom headers — both are available to any unprivileged internet user/app installer, with no access token, `api_secret_key`, or privileged account required.

### Recommendation
Do not treat the `shop`/`topic`/`webhook_id`/`api_version` headers as authenticated. Either:
- Include the shop domain and topic as part of the signable string covered by the HMAC (matching what Shopify actually signs), or
- Cross-check the header-derived `shop` against an independently-verified source of truth (e.g. the session/shop record the app expects for that webhook subscription) before dispatching to the handler, rather than trusting the header value verbatim.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook delivery, e.g. body `{}` with headers `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>`, `X-Shopify-Topic: customers/redact`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, raw_body)` — see `to_signable_string` returning `@raw_body` at `lib/shopify_api/webhooks/request.rb:35-38`.
4. The handler receives `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and performs the redact/uninstall/whatever action against `victim-shop`, despite the request never being authenticated as coming from Shopify on behalf of `victim-shop`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
