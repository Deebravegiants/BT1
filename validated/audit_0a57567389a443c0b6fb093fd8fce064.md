## Analysis

The confirmed bug pattern here is exactly the CVE-2018-25004 shape: an unprivileged caller can trigger expensive proof-verification work (trie rebuilding / trie walking over an arbitrary number of storage keys) *before* any cost accounting or bandwidth gate is enforced, and the entire path is reachable via a **free, unsigned extrinsic**.

`pallet_state_coprocessor::handle_get_requests` iterates every `GetRequest` in the batch and, per request, calls `dest_state_machine.verify_state_proof(&host, req.keys.clone(), state_root.state_root, &response)` — which does full Merkle/Patricia trie verification for every key in `req.keys` — and only *after* that expensive verification does it call `BandwidthGate::try_consume(...)` to check whether the caller (identified by `req.source`/`req.from`) had any allowance at all: [1](#0-0) 

The doc comment on `BandwidthGate` even states the intended design was the opposite — charge *before* any state-proof work "fails fast for apps without allowance" — but the implementation charges only *after* verification completes: [2](#0-1) 

Critically, `handle_get_requests` is invoked from `ValidateUnsigned::validate_unsigned`, meaning **every node in the network runs this full verification on every submitted transaction during mempool validation**, for free (no signer, no fee, `Pays::No` semantics), and repeatedly for every peer that receives the gossiped extrinsic: [3](#0-2) 

I found no cap on `requests.len()` or on `req.keys.len()` anywhere in `handle_get_requests`, `GetRequest`, or the various `verify_state_proof` implementations (EVM, Substrate, Pharos) I inspected — the loops over `keys` in `verify_state_proof` (EVM/Substrate/Pharos) run once per key with no upper bound: [4](#0-3) [5](#0-4) 

By contrast, I noted the codebase has clearly hardened *other* proof paths against exactly this class of issue: EVM `verify_state_proof` rejects duplicate keys before doing trie work, and Pharos's `spv` module enforces `MAX_PROOF_DEPTH` to bound trie-walk cost: [6](#0-5) [7](#0-6) 

That hardening does not address the ordering issue in `handle_get_requests`: even if each individual key's proof verification is now bounded/duplicate-free, an attacker can still submit a batch with a very large number of distinct legitimate-looking keys/requests (each triggering a full trie rebuild and walk) whose bandwidth-gate rejection only fires per-request *after* that request's proof has already been fully verified — and since this validation runs unauthenticated and for free on every node's `validate_unsigned`, the cost is imposed network-wide with no economic disincentive to the caller.

I could not verify from the index alone whether `dedup_requests` or any extrinsic-size / `BoundedVec` limit indirectly caps `requests.len()` or `keys.len()` at the SCALE-decode layer (e.g., in the runtime's `RuntimeCall` decode limits) — that would need to be checked in a full Devin session, since the index only shows `GetRequestsWithProof.requests: Vec<GetRequest>` and `GetRequest.keys: Vec<Vec<u8>>` with no `#[pallet::compact]`/`BoundedVec` annotations visible.

### Title
Denial of Service via Unbounded, Unmetered State-Proof Verification in `pallet_state_coprocessor::handle_get_requests` - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`pallet_state_coprocessor::handle_get_requests`, reachable via the free/unsigned `handle_unsigned` extrinsic and executed by every node during `validate_unsigned`, performs full state-proof (trie) verification for every `GetRequest` and every key in `req.keys` before checking the `BandwidthGate` allowance for that request. This mirrors CVE-2018-25004's pattern (a cheap/unprivileged operation — `explain` on a `find` — triggering unbounded, expensive query execution before any resource check), except here the "unprivileged operation" is a signature-less transaction that is validated by every node in the network for free.

### Finding Description
`handle_get_requests` loops over `requests: Vec<GetRequest>` and, per request, calls `dest_state_machine.verify_state_proof(...)`, which rebuilds an in-memory trie from the supplied proof and walks it once per key in `req.keys`. Only after this full verification completes does it charge `BandwidthGate::try_consume` for that specific request: [1](#0-0) 

Because `handle_unsigned` is dispatched with `ensure_none(origin)` and the pallet implements `ValidateUnsigned::validate_unsigned` by calling `Self::handle_get_requests(message.clone())` directly, the *entire* expensive verification runs during transaction-pool validation — before the transaction is even included in a block, and on every node that receives it via gossip: [8](#0-7) 

There is no visible upper bound on `requests.len()` or on `GetRequest.keys.len()` in the router types, and the per-key trie-walk loops in the EVM/Substrate/Pharos `verify_state_proof` implementations execute unconditionally for every supplied key: [9](#0-8) 

### Impact Explanation
Because the entire batch's proof verification runs before the per-request bandwidth check, and the whole call is free and unsigned, an attacker can craft `GetRequestsWithProof` batches with a large number of requests/keys pointing at apps that will ultimately be denied bandwidth, and force every node on the network to repeatedly perform expensive trie reconstruction and walks during mempool validation, at zero cost to the attacker. This is a network-wide denial-of-service/resource-exhaustion vector against Hyperbridge nodes, degrading consensus/relayer message-processing availability — the same bug class (cheap operation → unbounded expensive execution before resource checks) as CVE-2018-25004.

### Likelihood Explanation
High: the path is reachable by anyone able to submit an unsigned extrinsic (no fee, no signature, no prior state required beyond a syntactically valid `GetRequestsWithProof` and any accepted consensus state/height), and the vulnerable ordering (verify-then-charge, not charge-then-verify) is unconditional in the current code with no size caps observed on the batch or key count.

### Recommendation
Move (or duplicate) the `BandwidthGate::try_consume` check to run before `verify_state_proof` is invoked for each request — i.e., charge/gate on the request's declared key-count/context size (as the `BandwidthGate` doc comment already intends) prior to doing any trie verification — and additionally enforce hard upper bounds on `requests.len()` and `GetRequest.keys.len()` in `handle_get_requests`/`validate_unsigned` so a single batch cannot force unbounded trie work regardless of bandwidth-gate state.

### Proof of Concept
1. Attacker crafts a `GetRequestsWithProof` with `requests` containing many `GetRequest`s (or few requests each with many `keys`) targeting a `(source, from)` app pair known to have zero/low bandwidth allowance.
2. Attacker submits this as an unsigned `pallet_state_coprocessor::Call::handle_unsigned` extrinsic to the network (no fee required).
3. Every node's `validate_unsigned` calls `handle_get_requests`, which runs `dest_state_machine.verify_state_proof` (full trie rebuild + walk) for every request/key in the batch before reaching the `BandwidthGate::try_consume` check that ultimately rejects it.
4. Repeating this with many such batches (each costing the attacker nothing) forces continuous, unbounded proof-verification CPU work network-wide — the resource-exhaustion pattern analogous to CVE-2018-25004's unmetered `explain` execution.

pub fn verify_state_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: &Proof,
	ismp_address: H160,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
	// Reject repeats before doing any work at all. They are already an error — repeats collapse
	// in the map returned below, so the caller's key-count check fails — but reaching that
	// check means every repeat has been verified first, and for account queries that is a
	// clone of the whole contract proof each time.
	let mut seen_keys = BTreeSet::new();
	for key in &keys {
		if !seen_keys.insert(key.as_slice()) {
			return Err(EvmStateMachineError::DuplicateKey.into());
		}
	}

	let evm_state_proof = decode_evm_state_proof(proof)?;
	let mut map = BTreeMap::new();
	let mut contract_to_keys = BTreeMap::new();
	let mut contract_account_queries = Vec::new();

	// Group keys by the contract address they belong to
	for key in keys {
		// For keys that are 52 bytes we expect the first 20 bytes to be the contract address and
		// the last 32 bytes the slot hash.
		// For keys that are 20 bytes we expect that to the
		// contract or account address.
		// For keys that are 32 bytes we expect that to be a slothash in
		// the Ismp EVM host
		let contract_address = if key.len() == 52 {
			H160::from_slice(&key[..20])
		} else if key.len() == 32 {
			ismp_address
		} else if key.len() == 20 {
			contract_account_queries.push(H160::from_slice(&key));
			continue;
		} else {
			return Err(EvmStateMachineError::UnsupportedKeyLength.into());
		};
		let entry = contract_to_keys.entry(contract_address.0.to_vec()).or_insert(vec![]);

		let slot_hash = if key.len() == 52 {
			H::keccak256(&key[20..]).0.to_vec()
		} else {
			H::keccak256(&key).0.to_vec()
		};

		entry.push((key, slot_hash));
	}

	// The storage proof must correspond exactly to the contracts a key was requested from:
	// every one covered, and nothing else. Both directions are settled here, before a single
	// entry is resolved — resolving one clones the whole contract proof and rebuilds its trie,
	// so checking as we go would let a proof padded with unrequested accounts do that work
	// before being rejected, and would make which error surfaces depend on map ordering.
	// The honest prover already emits exactly this set, deriving its map from the requested
	// keys, so nothing legitimate is turned away.
	let result = contract_to_keys
		.clone()
		.into_keys()
		.all(|contract| evm_state_proof.storage_proof.contains_key(&contract));
	if !result {
		return Err(EvmStateMachineError::IncompleteStorageProof.into());
	}

	if evm_state_proof
		.storage_proof
		.keys()
		.any(|contract| !contract_to_keys.contains_key(contract))
	{
		return Err(EvmStateMachineError::UnrequestedContractProof.into());
	}

	for (contract_address, storage_proof) in evm_state_proof.storage_proof {
		// Unreachable: the correspondence check above already rejected any entry without a
		// requested key. Kept as a hard error rather than a skip so the invariant survives if
		// that check is ever moved or relaxed.
		let Some(keys) = contract_to_keys.remove(&contract_address) else {
			return Err(EvmStateMachineError::UnrequestedContractProof.into());
		};

		let contract_root = get_contract_account::<H>(
			evm_state_proof.contract_proof.clone(),
			&contract_address,
			root,
		)?
		.storage_root
		.0
		.into();

		let slot_hashes = keys.iter().map(|(_, slot_hash)| slot_hash.clone()).collect();
		let values = get_values_from_proof::<H>(slot_hashes, contract_root, storage_proof)?;
		keys.into_iter().zip(values).for_each(|((key, _), value)| {
			map.insert(key, value);
		});
	}

	fn verify_state_proof(
		&self,
		_host: &dyn IsmpHost,
		keys: Vec<Vec<u8>>,
		root: H256,
		proof: &Proof,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
		// The trie root is supplied by the caller, bound to the calling context, so a relayer
		// cannot steer verification at the wrong trie.
		let StateMachineProof { hasher, storage_proof } =
			codec::Decode::decode(&mut &*proof.proof)
				.map_err(SubstrateStateMachineError::ProofDecodeError)?;
		let data = match hasher {
			HashAlgorithm::Keccak => {
				let db = StorageProof::new(storage_proof).into_memory_db::<Keccak256>();
				let trie = TrieDBBuilder::<LayoutV0<Keccak256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?
			},
			HashAlgorithm::Blake2 => {
				let db = StorageProof::new(storage_proof).into_memory_db::<BlakeTwo256>();
				let trie = TrieDBBuilder::<LayoutV0<BlakeTwo256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?
			},
		};

		Ok(data)
	}
