### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then trusts the unauthenticated `shopify-shop-domain` and `shopify-topic` headers to decide which merchant/topic the payload belongs to. Because the signature never covers those headers, any party who can obtain one validly-signed `(raw_body, hmac)` pair (e.g. by having their own shop install the app and capturing a webhook Shopify sends them) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` value. The signature still validates, and the handler receives attacker-controlled `shop` data as if it came from Shopify for that shop — a tenant-identity spoof.

### Finding Description
`Registry.process` performs the only authentication check on inbound webhooks: [1](#0-0) [1](#0-0) 

That check calls `Utils::HmacValidator.validate(request)`, which computes an HMAC over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only the raw body — never the headers: [3](#0-2) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` — the fields used to route and label the webhook — are read directly from headers with no cryptographic binding to the signed body at all: [4](#0-3) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` straight from these unauthenticated header values and hands it to the app's handler as the trusted tenant identity for the event: [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_that_produced_the_HMAC-signed_body == shop_delivered_to_the_handler_as_data.shop`

Before the attack: Shopify signs `(raw_body_A, hmac_A)` for shop A's genuine webhook, and the header `shopify-shop-domain: shop-a.myshopify.com` matches.
After the attacker's replay: the same `(raw_body_A, hmac_A)` is resent with header `shopify-shop-domain: shop-b.myshopify.com`. `HmacValidator.validate` still returns `true` (it never looked at the header), so `Registry.process` calls the handler with `data.shop == "shop-b.myshopify.com"` even though the signed content actually originated for shop A. The app's webhook secret (`Context.api_secret_key`) is shared across all shops using the app, so any merchant who legitimately installs the app can obtain a valid `(body, hmac)` pair and then relabel it for any other tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged party (any merchant capable of installing the target app) can cause the host application to process a webhook under an arbitrary shop's identity while the payload content and HMAC were only ever valid for their own shop. Any host application that uses `WebhookMetadata#shop` (as documented/intended by this gem) to select the tenant's session/access-token or data store will act on/write to the wrong merchant's records, i.e., cross-tenant access consistent with the Critical impact category in scope.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker only needs their own (free) app installation to receive a legitimately-signed webhook, then can replay it with a modified `shopify-shop-domain` header to the shared endpoint. No access token, `api_secret_key`, or privileged account is required — just the ability to install the app as a normal merchant and issue an HTTP request with attacker-chosen headers.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed payload used for verification, or otherwise cryptographically bind them to the signature — e.g., have `VerifiableQuery`/`Request#to_signable_string` incorporate the header values, or independently verify that the shop domain in the payload/body matches the header before trusting `request.shop`. At minimum, document that `WebhookMetadata#shop` is not itself authenticated by the HMAC and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and registers/receives a legitimate webhook, capturing the exact raw body `B` and the `shopify-hmac-sha256` header value `H` Shopify sent for that shop.
2. Attacker sends a new HTTP request to the app's webhook endpoint with body `B`, header `shopify-hmac-sha256: H` unchanged, but `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and compares it to `H` — validation succeeds because headers are never part of the signed string. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)`, causing the host application to process/store the event under the victim's tenant identity despite it never being signed for that shop.
