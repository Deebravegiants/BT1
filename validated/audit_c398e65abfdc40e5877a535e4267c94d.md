## Title
Webhook HMAC validates only the request body while `shop`, `topic`, and other identity headers used by the handler are unauthenticated - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw body. The `shop`, `topic`, `api_version`, and `webhook_id` values that are actually dispatched to the host app's handler are read straight from HTTP headers that are never included in the signed material, so the field an app uses to identify the tenant (`shop`) is not the field the HMAC actually covers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC and, once it passes, forwards these header-derived, unauthenticated values straight to the app's handler as the tenant/topic identity: [3](#0-2) 

The equality that should hold is:

`bytes verified by HmacValidator.validate` == `bytes the handler uses to identify shop/topic`

but in this implementation:

`bytes verified` = `raw_body` only
`bytes acted upon` = `raw_body` (parsed as `data.body`) **plus** `shop`, `topic`, `webhook_id`, `api_version` from headers

Because the `shop-domain` and `topic` headers sit outside the HMAC-covered signable string, any party who can produce one genuine `(raw_body, hmac)` pair from Shopify for their own store (which every merchant legitimately receives once they install the app) can resend that exact body/HMAC pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` and/or `x-shopify-topic` headers to name a different tenant or topic. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) still succeeds because it only recomputes the signature over `to_signable_string`, i.e. the body, and never inspects the headers. The app then processes attacker-controlled body content under the identity of an arbitrary victim shop, breaking the tenant isolation the HMAC is meant to guarantee.

### Impact Explanation
This directly breaks the binding between the cryptographically authenticated bytes and the tenant-identifying bytes the app relies on. If the host application uses `WebhookMetadata#shop` (as documented/tested, see `handler.handle(data: WebhookMetadata.new(topic:, shop:, body:, ...))`) to look up which merchant's session/access token to act on, an attacker who is a legitimate but unprivileged merchant can cause the app to attribute forged-topic/forged-shop webhook data to a different tenant — a cross-tenant data-confusion primitive reachable with only a normal merchant account and no access token, `client_secret`, or privileged role.

### Likelihood Explanation
Any merchant who installs the app receives real webhooks with a valid HMAC over the body they control the timing of. Replaying that exact body with edited `shop`/`topic` headers requires no additional secret knowledge, only the ability to send an arbitrary HTTP request to the app's public webhook endpoint — something any internet-reachable webhook endpoint accepts by design.

### Recommendation
Include the header fields the app relies on for tenant/topic identification (`shop-domain`, `topic`, `webhook-id`, `api-version`) inside `to_signable_string`, or otherwise cryptographically bind them to the payload the way Shopify does for OAuth's `AuthQuery` (compare `lib/shopify_api/auth/oauth/auth_query.rb:33-43`, which includes `shop` and other fields in the signed string). At minimum, document that `shop`/`topic` must not be trusted independently of body content, or have the library return only the HMAC-verified fields to callers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and captures a legitimate webhook Shopify sends them, e.g. `orders/create` with headers `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`.
2. Attacker resends the exact same body `B` and `hmac` to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and/or changes `x-shopify-topic` to a different registered topic).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`) — validation succeeds unchanged.
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's data>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-supplied data under the victim tenant's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
