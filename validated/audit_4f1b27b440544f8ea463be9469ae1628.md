## Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` only computes its HMAC-signable string from the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. Because the app's `api_secret_key` is shared across every shop that installs the app (it is not shop-specific), a valid HMAC only proves "this body was signed by an app secret holder," not "this body belongs to the shop named in the `shop-domain` header." An attacker who controls their own shop installation can capture a legitimately-signed webhook and replay it with a forged `shop-domain` header pointing at a victim shop, and `ShopifyAPI::Utils::HmacValidator.validate` will still accept it.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards the unauthenticated `request.shop` value straight to the registered handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the received signature: [4](#0-3) 

The identity binding that the code implicitly assumes is:
`hmac_valid(body, secret) == true` implies `shop_header == shop_that_produced_body`.

That equality does not hold, because:
1. `secret` (`Context.api_secret_key`) is the same value for every shop that has installed the app — it is an app-level secret, not a per-shop secret.
2. The signable string never includes `shop`, `topic`, or `webhook_id`.

So any party that owns a legitimate installation of the app (i.e., any merchant who installs the app, which is available to any unprivileged internet user) can capture one of their own valid webhook deliveries (body + valid `X-Shopify-Hmac-Sha256`) and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which tenant's session/data store to write to (a very common pattern, since this is exactly what the field is for), an attacker can inject or overwrite data under a victim shop's tenant using content they fully control, which is a cross-tenant integrity/isolation break attributable to a broken identity binding in this gem's webhook verification.

### Likelihood Explanation
Any internet user can sign up for a development/trial store and install the target app, giving them a stream of legitimately-HMAC-signed webhook bodies signed with the app's single shared secret. Replaying one of these with a modified `shop-domain` header requires no privileged credentials, tokens, or access to the victim — only knowledge of the target app's webhook endpoint and a victim shop domain, both routinely public/discoverable.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is verified, or otherwise cryptographically tie the header to the signed payload — e.g., include the `shop-domain` header in the signable string used by `HmacValidator`, or require the caller to independently confirm that `request.shop` corresponds to a shop for which the app has an active session/webhook subscription (e.g., verifying against `webhook_id` looked up via API) before trusting it for tenant routing. At minimum, documentation should clearly warn integrators that `WebhookMetadata#shop` is not authenticated by the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify sends a webhook to the app with body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, and `X-Shopify-Hmac-Sha256: HMAC(api_secret_key, B)`.
3. Attacker captures this request, then re-sends it to the app's webhook endpoint but rewrites the header to `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and the same HMAC value unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` — unchanged since `B` is untouched — and the check passes (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler executes with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though `victim.myshopify.com` never sent this webhook.
