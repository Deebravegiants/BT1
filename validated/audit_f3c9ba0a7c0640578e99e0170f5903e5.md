### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing tenant-spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is subsequently handed to the application's handler is read from an HTTP header that is never included in the signed payload. Anyone in possession of one valid `(body, hmac)` pair — for example a merchant/attacker who owns a store with the app installed and can trivially observe its own legitimate webhook deliveries — can resend that identical body/HMAC pair with a different `x-shopify-shop-domain` header and have the library accept it as authentic, attributing the payload to an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validator computes/compares the HMAC exclusively against this signable string: [2](#0-1) 

Meanwhile, `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches to the handler using the unverified `request.shop`: [4](#0-3) 

This breaks the identity binding: `shop authenticated by HMAC == shop consumed by WebhookMetadata`. In reality, the binding enforced is only `hmac == HMAC(body)`, independent of `shop`. Any request carrying a body/HMAC pair the attacker has previously observed — combined with a forged `shop-domain` header — passes `HmacValidator.validate` unchanged, because `shop` never enters `to_signable_string`.

### Impact Explanation
This is a High-severity, cross-tenant issue: an application that uses `request.shop` (via `WebhookMetadata#shop`) to scope database writes, cache invalidation, billing state, or redaction handling (e.g. GDPR `customers/redact`, `shop/redact` mandatory webhooks) can be tricked into applying another merchant's legitimate webhook payload to a different tenant's records, since the gem provides no signal that `shop` was forged. Because the payload body itself is valid and HMAC-correct, host applications that trust the gem's `process` return (no exception raised) will treat the spoofed shop attribution as authentic — a cross-tenant data integrity/confidentiality violation.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimate `(body, hmac)` pair. This is trivially available to any merchant that installs the app themselves (an unprivileged internet user), since webhook payload content is often not treated as secret and every registered topic will eventually fire against their own store, or via other lower-privilege data-exposure channels (logs, network capture on their own webhook endpoint testing). Any handler that keys business logic off `data.shop` rather than the raw body is exposed. Likelihood is Medium-High given how commonly webhook handlers dispatch/scope purely on the `shop` value.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification, or otherwise cryptographically bind them (e.g., verify that the shop domain matches a shop known to have an active session/webhook subscription with that `webhook_id` before trusting `request.shop`). At minimum, document that `request.shop` is unauthenticated header data and must not be trusted for tenant-scoping without additional verification (e.g., cross-checking against `webhook_id` via the Admin API).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers (or captures) a legitimate webhook delivery, e.g. `orders/create`, recording the exact raw JSON body `B` and the resulting `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's secret).
2. Attacker sends a POST to the host application's webhook endpoint with:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256` = `H` (unchanged, still valid because `to_signable_string` only hashes the body)
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`, `x-shopify-webhook-id` set arbitrarily.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `OpenSSL.secure_compare(computed_signature, hmac)` over `@raw_body`, per [1](#0-0)  and [5](#0-4) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, per [6](#0-5) , causing the host application to process attacker-supplied data under the victim shop's identity.
