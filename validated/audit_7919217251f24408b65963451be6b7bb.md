This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over the request (which only covers the body) and then trusts `request.shop`/`request.topic` to build `WebhookMetadata` and dispatch to the topic-specific handler [3](#0-2) . The gem's own documentation confirms that host apps are expected to key their tenant logic directly off `data.shop` [4](#0-3) .

### Title
Webhook tenant/topic identity (shop-domain, topic headers) not bound to HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable content for HMAC verification using only the raw request body, while the `shop-domain` and `topic` headers — both of which are trusted downstream to identify which merchant/tenant and which handler an event belongs to — are read straight from unauthenticated HTTP headers and never covered by the signature.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) . `Request#shop` and `Request#topic` are derived purely from the `x-shopify-shop-domain` / `x-shopify-topic` (or `shopify-shop-domain` / `shopify-topic`) headers [5](#0-4) , which are never included in `to_signable_string` and are therefore not authenticated by `HmacValidator.validate` [6](#0-5) .

`Registry.process` only checks the HMAC of the body, then immediately trusts `request.shop` and `request.topic` to route the event to a handler and to populate `WebhookMetadata.shop`, which is the value app developers are told to use to identify which merchant the event is for [3](#0-2) [7](#0-6) .

This breaks the intended binding: `shop authenticated == shop the merchant-scoped data is stored/acted under`. Because only the body bytes are covered by the HMAC, an attacker who can obtain one validly HMAC-signed webhook body for *any* shop that has installed the app (e.g., their own store, or by triggering any webhook-emitting action on their own shop) can replay that exact body to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain (and/or the `topic` header changed to route to a different, more sensitive handler). The signature still validates because it was computed with the shared `api_secret_key` over body bytes that are unmodified; the header claiming which shop/topic the event pertains to is not part of what was signed.

This is directly analogous to the referenced report's root cause pattern: a downstream-trusted identity field (`FillInstruction.destinationSettler` there, `shop`/`topic` header here) is not covered by the binding mechanism (contract encoding there, HMAC here) that is supposed to guarantee its authenticity.

### Impact Explanation
**High** — cross-tenant access/data confusion. Any app that follows the gem's own documented pattern of using `data.shop` to decide which merchant's records to create/update/delete (as shown in the gem's own `docs/usage/webhooks.md` example) can be made to process a validly-signed webhook body under an attacker-chosen `shop` value, and/or have it dispatched to an attacker-chosen registered `topic` handler. This crosses the tenant boundary the HMAC is meant to enforce.

### Likelihood Explanation
**Medium-High** for an attacker who already controls one shop that has installed the target app: real webhook traffic for their own shop is signed with the same `api_secret_key` used for all shops, so they can capture a legitimately-signed body/HMAC pair and resend it with forged `shop-domain`/`topic` headers, since nothing in `Request` or `Registry.process` binds those headers to the signature.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values (in addition to the raw body) in the string/bytes that are HMAC-verified in `Request#to_signable_string`, or otherwise cryptographically bind them (e.g., by having `HmacValidator` verify a canonical representation of headers + body together rather than only the body) so that the identity fields consumed by `Registry.process` and exposed via `WebhookMetadata` cannot be altered independently of the signature.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers any subscribed webhook topic (e.g. `orders/create`) on their own shop and captures the raw POST body plus the `x-shopify-hmac-sha256` header sent by Shopify (both signed with the app's shared `api_secret_key`).
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unmodified) body against the (unmodified) HMAC header, so validation succeeds [8](#0-7) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with the forged `shop`/`topic` values and passed to the app's handler [9](#0-8) , causing the app to process/store data as if it originated from `victim-shop.myshopify.com` (or dispatch to an unintended handler), even though `victim-shop` never sent this event.
