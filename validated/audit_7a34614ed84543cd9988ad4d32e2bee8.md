This confirms the vulnerable design: session IDs are fully deterministic, non-secret strings derived from public data (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{associated_user.id}"` for online ones — see `Auth::Session.from` in `lib/shopify_api/auth/session.rb`), and for non-embedded apps this exact deterministic string is what gets placed into the session cookie and later trusted verbatim as the session lookup key by `SessionUtils.current_session_id`/`cookie_session_id`, with no signature binding the cookie bytes to the browser/session that was actually issued a token.### Title
Non-embedded session lookup trusts an unsigned, fully predictable cookie value as the session identity - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` is the gem's documented mechanism for resolving "who is calling" on every request for non-embedded apps (and as a fallback for embedded apps without a Bearer/`id_token`). For that path it returns whatever raw bytes are present in the `shopify_app_session` cookie, with zero cryptographic verification that those bytes were ever actually issued by the gem to that browser.

### Finding Description
The identity binding that should hold is:

`session id trusted by the host app's session store == session id cryptographically bound to a specific OAuth-authenticated browser`

What actually happens:

1. `ShopifyAPI::Auth::Session.from` builds session ids as fully deterministic, non-secret strings derived only from public data: `"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions [1](#0-0) .
2. `Auth::Oauth.validate_auth_callback` puts that exact deterministic string into the `SessionCookie` value for non-embedded apps: `SessionCookie.new(value: session.id, expires: ...)` [2](#0-1) . The `SessionCookie` struct itself carries no signature/HMAC field, just `name`, `value`, `expires` [3](#0-2) .
3. On every subsequent request, `SessionUtils.current_session_id` (non-embedded, or embedded-without-id-token) calls `cookie_session_id(cookies)`, which does nothing but read the raw cookie value back out and return it as the authoritative session id — no signature check, no comparison against a server-side nonce, no binding to the browser that completed OAuth: [4](#0-3) [5](#0-4) .

Because the id is `"offline_#{shop}"` or `"#{shop}_#{associated_user_id}"`, and `shop` (a `myshopify.com` domain) and numeric admin user ids are not secret, any unauthenticated internet user who knows or guesses a target merchant's shop domain can construct this string themselves and set it directly as their own `shopify_app_session` cookie value. If the host application follows the gem's own API contract literally — i.e., stores sessions keyed by `Session#id` and calls `SessionUtils.current_session_id` to resolve "the current session" for a request, exactly as the gem's `docs/getting_started.md`/`session_utils_test.rb` usage pattern implies — the attacker's forged cookie resolves to the victim shop's stored `Auth::Session`, including its offline/online access token, with no OAuth ever performed by the attacker.

This is the "session id derived from unauthenticated bytes" class of bug: the gem defines the session-id format (predictable, public-derivable) and defines the only verification step for cookie-based lookups (`cookie_session_id`), and that verification step performs no authentication of the bytes at all.

### Impact Explanation
If exploited, an attacker gains a session id that a host app's session store resolves to a real merchant's `Auth::Session`, including that merchant's access token — this is credential/session theft enabling cross-tenant access to the victim's Shopify store data via the Admin API, which maps to the Critical/High categories of authentication bypass and cross-tenant access.

### Likelihood Explanation
Requires the host application to use `SessionUtils.current_session_id` and a plain (unsigned) cookie exactly as the gem's own `SessionCookie`/`current_session_id` contract implies for non-embedded apps, and requires knowledge of the target `shop` domain (public) and, for online sessions, the numeric associated-user id (often guessable/small integers, sometimes leaked in webhooks or URLs). No access token, `client_secret`, TLS interception, or privileged account is needed — only an unprivileged internet user setting a cookie value.

### Recommendation
Do not use the raw, predictable `Session#id` as the cookie's trust anchor. `SessionCookie`/`cookie_session_id` should carry and verify a cryptographically random, unguessable session identifier (or an HMAC/signature over the session id, keyed with `Context.api_secret_key`) instead of the deterministic `shop`/`shop_user_id` string, and `cookie_session_id` must verify that signature before returning a value.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` installs the app (offline, non-embedded flow). The gem issues a `Session` with `id = "offline_victim-shop.myshopify.com"` and sets that exact string as the `shopify_app_session` cookie value [6](#0-5) [7](#0-6) . The host app, following the gem's contract, persists this `Session` (with the merchant's access token) keyed by that same id string.
2. An unrelated attacker, who never installed the app, sends a request to the app with a cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim with no verification [8](#0-7) [5](#0-4) .
4. The host app loads the stored `Session` for that id (the victim's real session/access token) and treats the attacker's request as coming from `victim-shop.myshopify.com`.
