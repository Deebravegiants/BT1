### Title
Webhook shop-tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The tenant-identifying `shop-domain` header (along with `topic`, `webhook-id`, `api-version`) is read directly from unauthenticated HTTP headers and is never included in the signed payload [2](#0-1) . Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app rather than being per-shop, any party that can obtain one genuinely-signed `(body, hmac)` pair (e.g., by installing the app on a shop they control and capturing a real webhook delivery) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header. The gem will accept it as authentic and hand the handler a `WebhookMetadata` object whose `shop` field is attacker-chosen [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop_the_hmac_was_computed_for == shop_the_handler_acts_on`

`Request#to_signable_string` returns only `@raw_body`: [4](#0-3) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from headers that are never fed into `to_signable_string` and therefore never covered by `HmacValidator.validate`: [5](#0-4) 

`HmacValidator.validate`/`validate_signature` only checks `verifiable_query.to_signable_string` against the HMAC, so it can only ever attest to the integrity of the body, never to which shop or topic it belongs to: [6](#0-5) 

`Registry.process` uses this unauthenticated `request.shop` value directly to build the metadata passed to the app's handler, with no secondary check that the shop is the one that actually owns/sent this payload: [3](#0-2) 

Since Shopify signs webhooks using the app's `api_secret_key`, which is identical for every shop that has installed the app (there is no per-shop signing secret in this flow), a valid `(body, hmac)` pair from *any* shop's webhook delivery is cryptographically indistinguishable from one belonging to any other shop. The only thing that ties a delivery to a specific shop is the `X-Shopify-Shop-Domain` header — which this gem treats as trusted input despite it carrying no cryptographic binding to the signed body.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers. An attacker who legitimately installs the target app on their own store (an "unprivileged" action available to anyone) can capture one authentic `(body, hmac)` pair from their own webhook deliveries, then replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop. Because `Registry.process` only checks the HMAC (which validates), the handler executes with `data.shop` set to the victim's domain and `data.topic`/`data.body` fully attacker-chosen (topic and webhook-id are likewise unauthenticated). Any host application logic keyed off `WebhookMetadata#shop` (e.g., looking up the victim's stored session/access token, updating the victim's local records, triggering `app/uninstalled`-style cleanup, or GDPR `shop/redact` handling) can be invoked against the wrong tenant using attacker-controlled body content. This is a cross-tenant access issue reachable without any credential belonging to the victim.

### Likelihood Explanation
Reaching this requires only: (1) installing the target app on an attacker-owned shop to obtain a valid, freshly-signed `(body, hmac)` pair for some topic, and (2) sending a raw POST to the app's public webhook endpoint with that body/HMAC and a modified `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header. No access token, `api_secret_key`, or victim credentials are needed — both steps are available to any internet user who can create a Shopify development/partner store, which is the normal way this class of app is tested. The `HmacValidator`/`Request` code path enforces no additional binding, so likelihood of a successful bypass, given the attacker has one valid pair, is high.

### Recommendation
Include the tenant/topic identity in the signed material, or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the HMAC before trusting them:
- If Shopify's real signature genuinely only covers the raw body (which matches Shopify's documented behavior), the gem should not expose these header-derived fields as if they were authenticated. At minimum, `Webhooks::Registry`/`WebhookMetadata` documentation and API should make clear that `shop`, `topic`, and `webhook_id` are unauthenticated, and host applications must independently confirm that `data.shop` corresponds to a shop that is expected to send the topic/body combination (e.g., by validating shop-specific invariants in the payload itself, or maintaining a shop allowlist per delivery).
- Where feasible, require host apps to additionally verify the `shop` against session/install records before acting, and clearly flag in the webhook API surface that `Registry.process`'s HMAC check does not authenticate the shop or topic — only the body bytes.

### Proof of Concept
1. As an attacker, install the target Shopify app on an attacker-controlled development store (`attacker-shop.myshopify.com`).
2. Trigger any subscribed webhook topic (e.g., `orders/create`) on that store; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it is computed the same way as in `HmacValidator.compute_signature`, over the raw body, using the app's shared `api_secret_key`: [7](#0-6) 
3. Replay this exact body and `X-Shopify-Hmac-Sha256` value to the same app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally change `X-Shopify-Topic`).
4. `Request.new` accepts the forged headers (only checks presence, not authenticity) [8](#0-7) ; `HmacValidator.validate` succeeds because it only recomputes the HMAC over `@raw_body`, which is unchanged [1](#0-0) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"` even though the payload originated from the attacker's own store [9](#0-8) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
