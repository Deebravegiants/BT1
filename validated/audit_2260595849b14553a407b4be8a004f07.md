### Title
Fee-on-transfer tokens cause escrow over-crediting and insolvency in the Tron `IntentGatewayV2.placeOrder()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2.placeOrder()` pulls input tokens via `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits the escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount`, a value derived purely from the user-*requested* `order.inputs[i].amount` minus the protocol fee — never from the amount the contract actually received. The mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against exactly this class of bug by measuring `balanceOf` before/after the transfer and mutating `order.inputs[i].amount` to the actual received amount before computing fees/commitment/escrow, but that fix was never ported to the Tron variant.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the no-predispatch branch of `placeOrder()`: [1](#0-0) 

performs `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and immediately credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` was computed earlier from the raw `order.inputs[i].amount` requested by the user: [2](#0-1) 

No balance delta is measured. If the input token charges a transfer fee (fee-on-transfer, deflationary/rebasing token), the contract actually receives strictly less than `order.inputs[i].amount`, yet the escrow accounting records the full (fee-adjusted-for-protocol-fee-only) requested amount as a claimable liability against `_orders[commitment][token]`. The predispatch branch has a similar issue: dust is only computed relative to `requiredAmount = order.inputs[i].amount`, and the escrow credit again uses `reducedInputs[i].amount`, not the amount actually swept into the contract: [3](#0-2) 

By contrast, the EVM mainline contract explicitly measures `balBefore`/`balAfter` and rewrites `order.inputs[i].amount` to the delta before any fee/commitment/escrow math is performed, precisely to prevent this discrepancy: [4](#0-3) 

This is the same root cause identified in the external report: code assumes the transferred/received amount equals the requested amount when interacting with an arbitrary ERC20 that can silently deduct a fee on transfer, and this assumption is baked into a critical accounting value (here, escrow liability tracking rather than a `require` check).

### Impact Explanation
The escrow mapping `_orders[commitment][token]` is the sole source of truth for how many tokens a filler/solver can withdraw against a given order commitment during `withdraw()`/settlement. If it is credited with more tokens than the contract actually holds for that specific fee-on-transfer token, the sum of all outstanding escrow liabilities across commitments can exceed the contract's actual token balance. Because balances are fungible (not partitioned per-order), this manifests as either:
- Permanent freezing of funds: some legitimate order withdrawals fail once the shared token balance runs out, leaving later users unable to redeem their entitled input tokens, or
- Fund misallocation/theft-by-shortfall: an earlier withdrawer can drain tokens that were actually funded by a different user's order, at the expense of that other user, since escrow bookkeeping no longer matches actual custody.

Either outcome satisfies "concrete theft or permanent freezing of funds" from actual on-chain custody managed by an unprivileged, reachable entry point (`placeOrder`).

### Likelihood Explanation
Any unprivileged user can call `placeOrder()` with any ERC20 address as an input token; there is no allow-list enforcement visible in the reviewed contract for the input token type. Fee-on-transfer tokens are a well-documented and common ERC20 variant (see the referenced weird-erc20 doc). A single `placeOrder()` call using such a token is sufficient to introduce a shortfall between real balance and recorded escrow liability — no special privileges or multi-step setup required.

### Recommendation
Port the same fix already applied to `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` call (and after the predispatch sweep), mutate the effective input amount to the measured delta, and only then compute protocol fees, the commitment hash, and the `_orders[commitment][token]` escrow credit from that actual-received amount — never from the user-requested `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and mint balance to `user`.
2. `user` calls `placeOrder()` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no predispatch, no protocol fee (`protocolFeeBps == 0`).
3. `safeTransferFrom(user, gateway, 1000e18)` executes; gateway's actual FOT balance increases by only `990e18` (1% fee burned/redirected).
4. `_orders[commitment][FOT]` is nonetheless credited `reducedInputs[0].amount == 1000e18` (since `reducedInputs = order.inputs` when no protocol fee), i.e., 10e18 more than the gateway actually holds for this order.
5. Repeat with additional orders using the same token; the aggregate `_orders[*][FOT]` liabilities exceed the gateway's actual FOT balance by the cumulative transfer-fee shortfall.
6. When solvers later fill orders and the settlement path (`withdraw()`) attempts to pay out the full escrowed amount, the last such payout(s) for that token will fail due to insufficient contract balance (permanent freeze) — or, since token accounting is not per-order-segregated, an early withdrawal can consume balance funded by a later order, causing a shortfall/loss for that later order's beneficiary.

This mirrors the mechanics validated in the existing Foundry fee-on-transfer regression tests for the mainline EVM contract (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) which specifically assert the mainline contract's escrow equals *actual received* — behavior the Tron contract does not replicate: [5](#0-4)

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
