## Title
Replayable off-chain `transfer_from` approval in USDK stablecoin due to a static, self-referential nonce - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
The USDK stablecoin example implements a gasless "permit"-style transfer, `transfer_from`, where the token owner signs an off-chain `Approval` message and a `spender` submits it on-chain. The nonce used inside that signed message is `account::get_sequence_number(from)` — the on-chain sequence number of the **owner's own account**, not a nonce tracked by the `usdk` module itself. This is the exact bug class from the Krystal DeFi report: a signed authorization with no dedicated, module-owned replay-protection counter.

### Finding Description
`transfer_from` builds the challenge and verifies it as follows: [1](#0-0) 

The `nonce` field is populated with `account::get_sequence_number(from)` at line 178. Critically, `from` is not the transaction signer here — `spender` is — so nothing in `transfer_from` increments `from`'s account sequence number. On Aptos, `account::get_sequence_number` (`aptos-move/framework/aptos-framework/sources/account/account.move`) is only incremented by `transaction_validation::check_for_replay_protection_regular_txn` when `from` itself submits a transaction as sender: [2](#0-1) 

Because `usdk::transfer_from` never touches `from`'s sequence number and never records any (owner, nonce) pair itself (no `Table`/`SimpleMap` tracking used-nonces, unlike `multisig_account.move`'s sequence-number-gated flow or the framework's dedicated `nonce_validation.move`), a single valid `Approval` signature remains valid for `from`'s **entire idle period on-chain**. If the owner does not submit any of their own sequenced transactions in between, the identical `(proof, from, to, amount)` tuple can be replayed an unlimited number of times by anyone holding the signature (typically the `spender`, or anyone the spender/backend leaks it to), each replay executing another `primary_fungible_store::transfer_with_ref` from the owner's primary store: [3](#0-2) 

This mirrors the Krystal `V3Automation` flaw precisely: the signed authorization lacks a self-contained, monotonically-advancing nonce controlled by the verifying module, so the same signature can be reused to move value repeatedly. Compare with the framework's actual dedicated nonce/hash constructs that were built for exactly this purpose (`nonce_validation::check_and_insert_nonce`, `multisig_account`'s sequence-number-based `last_resolved_sequence_number`), which USDK's `transfer_from` does not use.

### Impact Explanation
This breaks the custody invariant that a single signed authorization corresponds to exactly one balance-moving transfer. An attacker who has captured one valid `Approval` proof (e.g., a spender relaying it, a leaked mempool/backend artifact, or a compromised/malicious `spender` role) can drain the owner's entire USDK balance in repeated `amount`-sized withdrawals as long as the owner's account sequence number does not advance in between — a realistic condition for accounts that only interact via this permit mechanism and never submit their own sequenced transactions. This is a direct custody/fund-loss impact: unauthorized, repeated withdrawal from a fungible-asset primary store via replayed signature, moving supply to an unintended holder.

### Likelihood Explanation
Likelihood is bounded by two factors: (1) `transfer_from` is a `public fun`, not `entry`, in this `move-examples` package, so it must be composed into a real deployment by an integrator (the code is illustrative/example code, which lowers direct mainnet applicability), and (2) exploitation requires either possession of the valid signature+proof by someone other than the intended one-time use, or the "spender" replaying its own captured proof multiple times before the owner's sequence number changes — plausible for permit/gasless flows where owners rarely submit direct transactions. Because this lives under `aptos-move/move-examples/`, it should be treated as a reference-implementation defect rather than a live mainnet vulnerability unless a real deployment reuses this exact pattern verbatim.

### Recommendation
Replace `account::get_sequence_number(from)` with a dedicated, module-owned nonce/replay-protection table (as done in `aptos_framework::nonce_validation` or by tracking a per-owner monotonic counter incremented atomically inside `transfer_from` itself upon successful verification), and additionally record consumed proof hashes to prevent any replay regardless of sequence-number drift.

### Proof of Concept
1. Owner `A` signs one `Approval{owner: A, to: B, nonce: seq(A), chain_id, spender: S, amount: 100}` and gives the signature/proof to spender `S` for a legitimate one-time transfer.
2. `S` calls `usdk::transfer_from(S, proof, A, scheme, pk, B, 100)`. It succeeds: `account::verify_signed_message` passes because `nonce == account::get_sequence_number(A)` still matches, and 100 USDK moves from `A` to `B`.
3. `A` has not submitted any of its own sequenced transactions, so `account::get_sequence_number(A)` is unchanged.
4. `S` calls `usdk::transfer_from` again with the identical `proof`, `A`, `B`, `100` — verification passes again since the recomputed `nonce` is still equal, and another 100 USDK is drained from `A`'s primary store.
5. Repeat until `A`'s balance is exhausted or `A` finally submits a sequenced transaction (unpredictable timing, not guaranteed to happen). [4](#0-3)

```text
    /// Allow a spender to transfer tokens from the owner's account given their signed approval.
    /// Caller needs to provide the from account's scheme and public key which can be gotten via the Aptos SDK.
    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,
    ) acquires Management, State {
        assert_not_paused();
        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }
```

```text
    fun check_for_replay_protection_regular_txn(
        sender_address: address,
        gas_payer_address: address,
        txn_sequence_number: u64,
    ) {
        if (
            sender_address == gas_payer_address
                || account::exists_at(sender_address)
                || !features::sponsored_automatic_account_creation_enabled()
                || txn_sequence_number > 0
        ) {
            assert!(account::exists_at(sender_address), error::invalid_argument(PROLOGUE_EACCOUNT_DOES_NOT_EXIST));
            let account_sequence_number = account::get_sequence_number(sender_address);
            assert!(
                txn_sequence_number < (1u64 << 63),
                error::out_of_range(PROLOGUE_ESEQUENCE_NUMBER_TOO_BIG)
            );

            assert!(
                txn_sequence_number >= account_sequence_number,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_OLD)
            );

            assert!(
                txn_sequence_number == account_sequence_number,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_NEW)
            );
        } else {
            // In this case, the transaction is sponsored and the account does not exist, so ensure
            // the default values match.
            assert!(
                txn_sequence_number == 0,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_NEW)
            );
        };
    }
```
