### Title
`TokenExchange.exchange_token` sends `client_secret` to a `dest`-derived host that is never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination shop host solely from the JWT `dest` claim and uses it, unvalidated, as the base path for a request that carries the app's `client_id`/`client_secret` to `https://<dest_shop>/admin/oauth/access_token`. Every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) runs the caller-supplied `shop` through `Utils::ShopValidator.sanitize!` before building the request host, but `exchange_token` does not apply that same check to `dest_shop`.

### Finding Description
The gem's own security invariant, enforced consistently elsewhere, is: *host that receives `client_secret` == a host validated by `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`*.

- `lib/shopify_api/auth/client_credentials.rb:25` calls `Utils::ShopValidator.sanitize!(shop)` and uses `validated_shop` to build the session/host before sending `client_secret`. [1](#0-0) 
- `lib/shopify_api/auth/refresh_token.rb:24` does the same for `refresh_access_token`. [2](#0-1) 
- `lib/shopify_api/auth/token_exchange.rb:103` (`migrate_to_expiring_token`) also calls `Utils::ShopValidator.sanitize!(shop)`. [3](#0-2) 

But `exchange_token` (the primary, "recommended" OAuth path per the docs) breaks this invariant: it takes `dest_shop = jwt_payload.shop` straight from `JwtPayload#shop`, which is just `@dest.gsub("https://", "")` with no domain allow-listing, and immediately builds the outbound session/host from it: [4](#0-3) [5](#0-4) 

`JwtPayload.new` only verifies the JWT signature (`aud`) and that `aud == Context.api_key`; it never checks that `dest`/`iss` is a `myshopify.com`/trusted-domain host: [6](#0-5) 

`Clients::HttpClient` builds request URLs directly from `session.shop`/`Context.host` for the given session, so an attacker-controlled `dest` value flows straight into the outbound HTTPS request host that receives `client_id`/`client_secret` in the POST body.

The binding that should hold, expressed as an equality, is:
`host_receiving(client_secret) == ShopValidator.sanitize!(shop)`
For `exchange_token` this instead reduces to:
`host_receiving(client_secret) == jwt_payload.dest` (unchecked)

### Impact Explanation
If an app relies on `exchange_token` as documented (this is the gem's explicitly recommended flow for embedded apps, ahead of the Authorization Code Grant) and an attacker can influence or forge the session token passed to `exchange_token` (e.g., a malicious/compromised embedded surface, a proxied/relayed session token, or any host application that forwards a token without itself re-validating `dest`), the gem will POST the app's `client_id` and `client_secret` to a host taken from that token's `dest` claim without confirming it is a genuine Shopify domain. This is a credential-leakage/SSRF-with-credentials primitive: the app's `client_secret` — the same class of secret guarded everywhere else in this file — is sent to an unauthenticated-boundary-controlled host.

### Likelihood Explanation
Medium. Exploitation requires a way to get an attacker-influenced `dest` value into a session token that reaches `exchange_token` — this could occur through a host application that trusts a client-supplied `id_token` param without server-side shop binding (the gem's own docs describe `id_token` arriving via URL param), or through any deployment that does not independently re-validate `dest` before calling this API. Because the gem does not enforce the check itself (unlike its sibling methods), the safety of this flow depends entirely on the caller doing what the gem itself does for every other similar method — which is exactly the class of gap the other three functions were hardened against.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) before constructing `shop_session`/building the request, and raise `Errors::InvalidShopError` if the `dest` claim is not a trusted Shopify domain.

### Proof of Concept
1. Construct/obtain a session token whose `dest` claim is set to an attacker-controlled host (e.g., `attacker.example.com`), signed with the app's known `api_secret_key` (or forwarded verbatim by a vulnerable host integration that doesn't itself pin `dest`).
2. Call:
   ```ruby
   ShopifyAPI::Auth::TokenExchange.exchange_token(
     session_token: crafted_token,
     requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
   )
   ```
3. Trace execution: `jwt_payload.shop` returns `"attacker.example.com"` unchecked [7](#0-6) ; `shop_session = Session.new(shop: dest_shop)` and `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` build a request whose target host is `attacker.example.com`, and the POST body containing `client_id`/`client_secret` is sent there [8](#0-7) .
4. Compare with `client_credentials.rb`/`refresh_token.rb`, where the equivalent step is preceded by `Utils::ShopValidator.sanitize!(shop)`, which would reject `attacker.example.com` and raise `Errors::InvalidShopError`.
