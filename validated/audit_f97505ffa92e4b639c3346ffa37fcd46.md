### Title
Permissionless `CallDispatcher.dispatch()` lets anyone drain any native ETH left in the shared dispatcher, permanently robbing prior HFT users of unspent bridged ETH - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, un-owned contract used by every `WrappedHyperFungibleToken` / `HyperFungibleToken` deployment on a chain to execute post-bridge calldata. It has an empty `receive()` to accept ETH and a completely unauthenticated `dispatch(bytes)` function that forwards `to.call{value: call.value}(call.data)` using the contract's own balance, based solely on a `Call[]` array supplied by the caller. Any account that leaves the WETH-unwrap path unconsumed (fully or partially) in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` deposits real ETH into this shared pot, which any unrelated, unprivileged caller can subsequently withdraw to an address of their choosing.

### Finding Description
`CallDispatcher.dispatch` has no access control and no restriction tying the forwarded value to the caller's own funds: [1](#0-0) 

It also accepts arbitrary native ETH via an empty `receive()`: [2](#0-1) 

This contract is the designated recipient for cross-chain calldata execution in the HFT token bridge. When `WrappedHyperFungibleToken.onAccept` (or `onPostRequestTimeout`) processes a WETH-mode message with a non-empty `data` field, it unwraps WETH to native ETH and pushes it to `beneficiary` (which the documented pattern sets to the `CallDispatcher` address so the dispatcher can spend it), then immediately calls `ICallDispatcher(_dispatcher).dispatch(message.data)`: [3](#0-2) 

The documented "transfer-and-swap" flow explicitly relies on this: the unwrapped native ETH lands in `CallDispatcher`, and the encoded `Call[]` forwards it onward via `Call.value`: [4](#0-3) 

The security model documented for `CallDispatcher` only discusses storage-safety (no `delegatecall`) and atomic revert-on-failure, but never addresses value custody or dust: [5](#0-4) 

Because `dispatch()` is `external` with zero access control, and because it spends the contract's own balance rather than `msg.value` supplied in the same call, any of the following situations leaves ETH in `CallDispatcher` that becomes a target for theft by an unrelated third party:
- The encoded `Call[]` sums to less than the ETH actually delivered to the dispatcher (e.g. slippage-tolerant swap encodes a lower `Call.value` than what was unwrapped, or the bridging amount and the calldata's embedded value diverge due to a bug, mis-encoding, or fee/rounding mismatch upstream).
- A user sends ETH directly to `CallDispatcher` (its `receive()` accepts unconditionally from anyone).
- Multiple concurrent cross-chain fills leave small residual balances that accumulate over time since the contract is shared by all HFT deployments referencing it.

Once ETH sits in `CallDispatcher`'s balance, ANY external account — not just the depositor, not just a Hyperbridge relayer, not just the HFT contract — can call `dispatch()` with a `Call[]` naming an attacker-controlled contract (the only check is `extcodesize(to) > 0`) and `value` set to the dispatcher's balance, immediately draining it. This is the same class of bug as the referenced DODO report: value can enter a contract through an unrestricted `receive()`/inbound path but there is no mechanism binding a caller to only their own contribution, so the funds are either permanently stuck (if nobody ever calls a withdrawal path) or — worse here — stolen outright by any opportunistic caller who monitors the contract's balance and calls `dispatch()` first.

### Impact Explanation
This is a concrete theft/permanent-loss-of-funds vector reachable from a single, unprivileged, submitted cross-chain message: a user (or relayer delivering their proof) triggers `onAccept`/`onPostRequestTimeout` on `WrappedHyperFungibleToken`, which unwraps and forwards real ETH into the shared `CallDispatcher`. If the encoded `Call[]` doesn't fully consume that value (a realistic scenario for swap-with-slippage or any calldata that intentionally reserves change), the leftover ETH becomes forever unrecoverable by the rightful user and stealable by any bystander who calls the dispatcher's public `dispatch()` function. Because `CallDispatcher` is a shared, un-owned singleton referenced by potentially many HFT deployments across a chain, the blast radius extends to all users of all wrappers pointing at that dispatcher instance, not just one app.

### Likelihood Explanation
Likelihood is high in practice: the officially documented calldata-execution pattern for HFT (transfer-and-swap via UniswapV2) inherently transfers native ETH into `CallDispatcher` before executing calls that spend it, and any swap that specifies `amountOutMin`/slippage tolerance or otherwise doesn't consume the full forwarded value leaves dust behind by design. No special privileges, timing races, or governance compromise are needed to exploit it — any address can watch the dispatcher's balance and call `dispatch()` to steal it.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only forward the caller's own `msg.value` (i.e., require `msg.value == sum(call.value)` and use `msg.value` rather than the contract's standing balance), removing incentive/ability to spend residual balance belonging to others.
- Alternatively/additionally, remove the unconditional `receive()` or add `assert(msg.sender == WETH)`-style sender checks so the dispatcher never silently custodies un-attributed ETH, mirroring the reported fix pattern.
- Add a per-call bookkeeping/refund mechanism so any leftover value after executing the `Call[]` is returned to the original caller (e.g., `WrappedHyperFungibleToken`/beneficiary) atomically within `dispatch()`, rather than sitting in the dispatcher's balance for anyone to claim.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` in WETH mode (`isWeth = true`) pointed at a `CallDispatcher`, per the documented deployment flow (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`).
2. A legitimate cross-chain transfer arrives with `to = CallDispatcher` and `data` encoding a `Call[]` that swaps `amount` ETH for USDC via `swapETHForExactTokens` with `amountOutMin` set below `amount` worth (i.e., the swap intentionally specifies a `Call.value` less than the full unwrapped `message.amount`, or the swap under-uses the value due to slippage protection logic in a more complex multi-call payload).
3. `onAccept` executes: unwraps WETH, sends the full `message.amount` in native ETH to `CallDispatcher` via `beneficiary.call{value: message.amount}("")`, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`, which only spends part of the balance on the encoded `Call[]`.
4. Residual ETH now sits in `CallDispatcher`'s balance, un-attributed to any account.
5. Any unrelated address (attacker) calls `CallDispatcher.dispatch(encoded)` directly with a `Call[]` = `[{to: attackerContract, value: <dispatcher balance>, data: ""}]`, where `attackerContract` is any trivial contract with a `receive()` (satisfying the `extcodesize(to) > 0` check). This call succeeds because `dispatch()` has no access control and no ownership check on the forwarded balance.
6. The attacker's contract receives the residual ETH that rightfully belonged to the original bridging user, who has no recourse to recover it.

     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

### Calldata Execution

Pass a non-empty `data` field to execute arbitrary calls on the destination chain after tokens are unlocked. The `data` must be an ABI-encoded `Call[]` array (see [overview](/developers/evm/hyper-fungible-token/overview#calldata-execution) for the full `Call` struct and security details).

When `isWeth = true`, the WrappedHFT unwraps WETH to native ETH on receive. This example bridges WETH back to the home chain, where it's unwrapped to native ETH and swapped for an exact amount of USDC via UniswapV2. The `Call.value` field forwards the native ETH to the router — demonstrating that the `CallDispatcher` can hold and forward native tokens:

```solidity lineNumbers
import {IUniswapV2Router02} from "@uniswap/v2-periphery/contracts/interfaces/IUniswapV2Router02.sol";

address[] memory path = new address[](2);
path[0] = WETH;
path[1] = USDC;

Call[] memory calls = new Call[](1);

// Swap native ETH → exact USDC via UniswapV2
// The CallDispatcher holds the unwrapped ETH and forwards it via Call.value
calls[0] = Call({
    to: UNISWAP_V2_ROUTER,
    // forward the native ETH to the router
    value: amount,
    data: abi.encodeWithSelector(
        IUniswapV2Router02.swapETHForExactTokens.selector,
        usdcAmountOut,
        path,
        recipientAddress,
        block.timestamp
    )
});

IHyperFungibleToken(address(wrapper)).send{value: nativeFee}(
    IHyperFungibleToken.SendParams({
        dest: StateMachine.evm(1),
        // unlock to the CallDispatcher so it receives the unwrapped ETH
        to: abi.encodePacked(CALL_DISPATCHER),
        amount: amount,
        timeout: 3600,
        relayerFee: relayerFee,
        data: abi.encode(calls)
    })
);
```

Tokens are unlocked (or unwrapped for WETH) to `to` first, then the `CallDispatcher` executes each call in sequence. Setting `to` to the `CallDispatcher` address ensures the dispatcher holds the tokens (or native ETH) so subsequent calls can spend them via `Call.value` or ERC20 transfers.
```

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
