### Title
`feeStructure.feeToken` and `circomData.erc20TokenAddresses`/`deltaAmountChanges` are excluded from the EIP-712 `EmporiumSignature` payload, letting the tx submitter redirect the signed `flatFee` to an unrelated token via `payRelayFees` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
The victim's `EmporiumStack` signature only binds `emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `maxFee`, and `deadline`; it never binds `circomData.erc20TokenAddresses`, `deltaAmountChanges`, or `circomData.feeStructure.feeToken`. Because `payRelayFees` selects which token gets charged purely from these unsigned, caller-supplied fields, whoever submits the transaction (who need not be the signer) can point the relay fee at a token that never appears in any `op.callData` the victim authorized.

### Finding Description
The claimed equality — "(token charged as relay fee) == (token in `ops` the signer authorized)" — is not enforced anywhere in the signed data. `verifyWallet` recovers the signer from: [1](#0-0) 
which hashes only `emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline`. `_hashEmporiumOps` hashes `endpoint`, `invokeWallet`, `value`, and `callData` per op: [2](#0-1) 
— it does not include `circomData.erc20TokenAddresses`, `deltaAmountChanges`, or `circomData.feeStructure.feeToken`. The only fee-related check tied to the signature is a numeric cap: [3](#0-2) 

`payRelayFees` then iterates the attacker-supplied `circomData.erc20TokenAddresses`/`deltaAmountChanges` and, for any index with `deltaAmountChanges[i] < 0`, treats it as "sent to emporium" and pays a fee for whatever `erc20TokenAddress` sits at that index, matching it only against `feeStructure.feeToken` (also attacker-supplied): [4](#0-3) 
When `signerAddress != address(0)` (the delegated-wallet path), `relayFee = flatFee` — a fixed number bounded by the signed `maxFee` — with no scaling to a specific token's decimals or value: [5](#0-4) 
This flows into `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, erc20TokenAddress)`, which unconditionally transfers `erc20TokenAddress` from the wallet to `relay`: [6](#0-5) [7](#0-6) 

Since `feeStructure.feeToken` and `erc20TokenAddresses`/`deltaAmountChanges` are not part of the signed hash, an attacker holding a leaked `EmporiumStack` can build a fresh `circomData` that sets `feeStructure.feeToken` and one `erc20TokenAddresses[i]` to a token the victim's `ops` never reference, with `deltaAmountChanges[i] < 0`. `verifyWallet` still validates because the signature only covers `ops`/`maxFee`/`deadline`; `payRelayFees` then invokes `doSendToRelay` for that unrelated token, transferring `flatFee` from the wallet to `circomData.relay` (also attacker-supplied), which the attacker controls.

### Impact Explanation
This lets the transaction submitter move up to `flatFee` (bounded by the signed `maxFee`, a plain `uint256` with no token/decimals binding) of an arbitrary ERC20 held by the delegated `HinkalWallet` to an attacker-controlled `relay`, for a token never referenced in any op the wallet owner signed. Because `maxFee` is a unitless numeric cap not bound to a specific token's decimals, the attacker can pick a high-value/high-decimal token so that the same signed numeric cap authorizes a disproportionately large drain relative to what the signer likely intended for the actual fee token. This is "moving assets a wallet owner ... never authorised," matching the High severity bucket (rather than an unbounded/critical drain of the entire unrelated-token balance, since the amount transferred per matching array index is capped at `flatFee`).

### Likelihood Explanation
Preconditions: the attacker must obtain a validly signed, not-yet-used `EmporiumStack` (e.g., harvested from a dropped mempool tx, as stated) and the wallet must hold a nonzero balance of some other ERC20 token. The attacker fully controls `circomData` (it is calldata to `runAction`), including `erc20TokenAddresses`, `deltaAmountChanges`, `feeStructure.feeToken`, and `relay`; no privileged role is needed since `runAction` is reached via `onlyAllowedRecipient` (a Hinkal-controlled proof-verified entry path, not gated on signer identity). `usedMessages[circomData.emporiumMessage]` is marked used after the first successful `verifyWallet` call, so each harvested signature can only be exploited once, limiting repeatability to one exploit per captured signature.

### Recommendation
Include `erc20TokenAddresses`, `deltaAmountChanges` (or at minimum `feeStructure.feeToken` and `feeStructure.flatFee`/`variableRate`) in the EIP-712 `EmporiumSignature` typed-data hash so the signer explicitly authorizes which token(s) may be debited as relay fees, and reject any `payRelayFees` charge on a token not present in the signed `ops`/fee-token set.

### Proof of Concept
Hardhat test outline:
1. Deploy `HinkalWallet` for a victim signer; fund it with Token A and Token B.
2. Victim signs an `EmporiumStack` whose `ops` reference only Token A (e.g., an `approve`/`transfer` call on Token A's contract), with `maxFee = M`.
3. Attacker intercepts this signature (simulating mempool harvesting) and calls the Hinkal entry point with a `circomData` where `erc20TokenAddresses = [TokenB]`, `deltaAmountChanges = [-1]`, `feeStructure = {feeToken: TokenB, flatFee: M, variableRate: 0}`, `relay = attackerRelay`.
4. Assert `verifyWallet` succeeds (signature check only covers `ops`/`maxFee`/`deadline`, both satisfied) — i.e., confirm `_hashEmporiumOps(stack.ops)` never mentions Token B.
5. Assert `payRelayFees` invokes `doSendToRelay(attackerRelay, M, TokenB)` and Token B balance of the wallet decreases by `M` while Token B was never in `_hashEmporiumOps`, and Token A balance is untouched.
6. Compare both sides of the equality "(token charged as relay fee) == (token referenced in signed ops)" — before: undefined/no fee token signed; after: TokenB charged despite being absent from `stack.ops`, confirming the break.

```text
    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }
```

```text
    function _hashEmporiumOps(
        EmporiumOperation[] memory ops
    ) private pure returns (bytes32) {
        bytes32[] memory opHashes = new bytes32[](ops.length);
        for (uint256 i = 0; i < ops.length; i++) {
            opHashes[i] = keccak256(
                abi.encode(
                    EMPORIUM_OPERATION_TYPEHASH,
                    ops[i].endpoint,
                    ops[i].invokeWallet,
                    ops[i].value,
                    keccak256(ops[i].callData)
                )
            );
        }
        return keccak256(abi.encodePacked(opHashes));
    }
```
