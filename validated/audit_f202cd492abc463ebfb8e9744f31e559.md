### Title
Remote config JSON is trusted with no integrity/signature verification before being persisted as authoritative security state - ([File: features/remote-config/module/index.ts])

### Summary
`RemoteConfig#fetchConfig` fetches `${remoteConfigUrl}?cacheBump=0`, checks `response.ok`, parses `response.json()`, and validates only `typeof data === 'object'` before returning it as `config`, which `update()` then freezes and persists into `this.#current` and `remoteConfigAtom`. No cryptographic signature, checksum, or content-integrity check is ever applied to the fetched payload — the code relies solely on transport-level TLS to the fixed `https://remote-config.exodus.io/...` URL.

### Finding Description
In `#fetchConfig` [1](#0-0) , the response is accepted based purely on HTTP status (`response.ok`) and successful JSON parsing, then the entire `data` object is validated with a single weak check `if (!data || typeof data !== 'object')`. There is no signature field, no HMAC, no allow-listed schema enforcement, and no pinned key material checked anywhere in this module or in `generate-remote-config-url.ts` [2](#0-1) .

The accepted `config` then flows unchanged into `update()`, which freezes it and sets it as `this.#current` (the value returned by `get`/`getAll`) and persists it into `remoteConfigAtom` [3](#0-2) . Downstream consumers — e.g. `feeDelegationService` (`infrastructure.feeDelegationService.servers`), `ethereumProvider.defaultChainIds`, and `web3Browser.dapps` allow-list — read directly from this trusted config via `remoteConfig.get`/`getAll` or `remote-config-atoms` selectors [4](#0-3) , with no additional verification at the consumption layer either.

If an attacker can serve an arbitrary well-formed JSON object for this URL (compromised CDN edge, cache poisoning, DNS-adjacent redirect), the only gate is `typeof data === 'object'`, which any attacker-controlled payload trivially satisfies. There is no application-layer trust anchor independent of the transport channel.

### Impact Explanation
A successful response substitution lets an attacker fully replace security-relevant remote-config values: `feeDelegationService.servers` (redirect fee-delegation/broadcast infrastructure), `ethereumProvider.defaultChainIds` (alter default chain binding presented to dapps/origins), and `web3Browser.dapps` allow/deny lists (change which origins are treated as trusted dapps). Because there is no signature check, the wallet cannot distinguish a legitimate config from an attacker-forged one once the transport channel is compromised.

### Likelihood Explanation
Exploitation strictly requires the attacker to already control what is served at the fixed `remote-config.exodus.io` URL (CDN compromise, cache poisoning, or a TLS/DNS-adjacent MITM) — this is a real precondition and not something reachable from an ordinary dapp/origin request without such transport-level compromise. Given that precondition, exploitation is trivial and fully repeatable: any well-formed JSON object is accepted regardless of provenance.

### Recommendation
Add an application-layer integrity check independent of TLS: sign the remote-config payload server-side and verify the signature client-side with a pinned public key before accepting `data`, reject unsigned/invalid-signature payloads, and consider schema validation for security-relevant fields (`feeDelegationService`, `ethereumProvider.defaultChainIds`, `web3Browser.dapps`) in addition to the raw `typeof` check in `#fetchConfig` (`features/remote-config/module/index.ts:230`).

### Proof of Concept
Unit test plan for `features/remote-config/module/index.ts`:
1. Mock `fetch` to return `{ ok: true, headers: { get: () => <timestamp> }, json: () => ({ data: { infrastructure: { feeDelegationService: { servers: ['https://attacker.example'] } } } }) }` with no signature field.
2. Call `remoteConfig.update()` and assert it succeeds (`{ success: true }`) and `remoteConfig.get('infrastructure.feeDelegationService')` returns the attacker-controlled value — confirming no rejection occurs.
3. Repeat with a payload that omits `data` entirely or sets `data` to a non-object, confirming rejection (`invalid body data`), to show validation is limited strictly to shape, not provenance/signature.
4. (Differential) Add a hypothetical `signature` field requirement in a patched version and show the same attacker payload is now rejected — demonstrating the current implementation has no equivalent check.

export default async function generateRemoteConfigUrl(
  getBuildMetadata: GetBuildMetadata
): Promise<string> {
  const { build } = await getBuildMetadata()
  return `https://remote-config.exodus.io/v1/${encodeURIComponent(build)}.json`
}
