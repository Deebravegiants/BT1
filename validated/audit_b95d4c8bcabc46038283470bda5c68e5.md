### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` and `topic` values that are handed to the application's handler as the trusted tenant/routing identifiers are taken from separate, unsigned HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . However, `Request#shop` and `Request#topic` are read straight from the `x-shopify-shop-domain` / `x-shopify-topic` headers, which are never included in the signed bytes [3](#0-2) .

`Registry.process` validates the HMAC and then, without any additional check that `request.shop`/`request.topic` are consistent with the signed body, dispatches to the handler using those unverified values as the tenant/routing identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

Because `api_secret_key` is a single shared secret used to sign webhooks for *every* shop that installs the app, any webhook payload the attacker's own shop legitimately receives (or a payload whose HMAC they can otherwise obtain) is valid proof only that "some body came from Shopify" — it says nothing about which shop or topic it belongs to. An attacker who controls one installation can replay the exact `raw_body` + `x-shopify-hmac-sha256` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`) for a victim shop/topic. `HmacValidator.validate` still succeeds because it never inspects those headers, and the handler receives `WebhookMetadata` claiming the victim shop as the source of the data.

This breaks the intended identity binding: `authenticated_body == HMAC(body)` while `shop_used_by_handler != shop_that_actually_produced_the_signed_body`. The library's own documentation explicitly promises this call "will verify the request did indeed come from Shopify" for the whole request [5](#0-4) , but the `shop`/`topic` identity fields that host applications are told to trust (`data.shop`, `data.topic`) are not part of that verification [6](#0-5) .

### Impact Explanation
This is a "field acted on but not covered by the HMAC" identity-binding failure. Applications built on top of this gem are expected (per the gem's own docs and `WebhookMetadata` API) to use `data.shop` as the tenant key to look up sessions/records and `data.topic` to route processing — both un-authenticated. An attacker able to obtain any one valid `(raw_body, hmac)` pair (e.g., from a webhook delivered to their own shop) can forge the shop/topic headers to impersonate a different merchant, causing cross-tenant data confusion in the host application (e.g., a benign update for the attacker's own store being applied/attributed to a victim shop's tenant record).

### Likelihood Explanation
Exploitation requires only that the attacker possess or trigger one legitimate webhook (trivial for an app's own installed shop, which any unprivileged user can create with a Shopify dev/trial store) and be able to POST to the app's public webhook endpoint with custom headers — no access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`/`api_version`) in the HMAC-signed material, or otherwise validate that the shop/topic values are cryptographically bound to the payload before constructing `WebhookMetadata`, so that `Registry.process` cannot be tricked into attributing a signed body to an arbitrary shop/topic.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256: H` header from the delivered request.
2. Attacker POSTs to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`), but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` and matches `H` — validation succeeds [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.
