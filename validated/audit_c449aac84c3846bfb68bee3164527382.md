### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header spoofing due to HMAC covering only the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from an HTTP header that is **not** included in the value signed by the webhook HMAC. The HMAC only ever covers the raw request body, so an attacker who possesses one *valid, signed* webhook delivery (trivially obtainable by installing the target app on their own shop) can replay it while swapping the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, and `Registry.process` will still accept it as authentic.

### Finding Description
`Registry.process` authenticates a webhook purely by calling `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` - none of the Shopify headers are part of the signed material: [3](#0-2) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` — all read straight from unauthenticated headers — are exactly the fields handed to the application's webhook handler as the identity/context of the event: [1](#0-0) 

The binding that should hold is:
```
HMAC(raw_body ∥ shop, client_secret) == received_hmac
```
but the gem only verifies:
```
HMAC(raw_body, client_secret) == received_hmac
```
i.e. `shop` (the tenant key that downstream code relies on) is a field **acted on but not covered by the HMAC**.

Because Shopify webhooks for a given app are all signed with the same `client_secret` regardless of which shop triggered them, any shop that has installed the app can obtain a legitimately-signed webhook delivery for its own store, then resend that exact body+HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header changed to a different, victim shop. The HMAC check still passes because it never touched those headers, so `WebhookMetadata.shop` will report the victim's domain even though the payload actually originated from the attacker's own shop.

### Impact Explanation
This breaks the `session.shop == request.shop` (or equivalent tenant lookup) binding that host applications rely on when processing webhooks: `WebhookMetadata#shop` is treated as an authenticated fact but is actually attacker-controlled. Depending on how the handler uses `data.shop` (e.g., to look up/update per-shop state, feature flags, billing, or to route `shop/redact` / `customers/redact` GDPR webhooks), this enables cross-tenant data confusion — an attacker-controlled shop can inject events that appear to originate from a victim shop, and vice versa, without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Any unprivileged user who can install the target Shopify app on a store they control automatically receives correctly-signed webhook deliveries. Crafting a replay with a modified `shop-domain`/`topic`/`webhook-id` header requires only basic HTTP tooling — no secret material, TLS interception, or social engineering is needed. Exploitability depends only on whether the host application trusts `WebhookMetadata#shop`/`#topic` for tenant-sensitive logic, which is the documented and expected usage pattern shown in `docs/usage/webhooks.md`.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the HMAC (e.g., by signing `raw_body + shop-domain` or validating that `shop` matches an application-provided expected shop before dispatch). At minimum, document loudly that `request.shop`/`request.topic` are **not** authenticated by the HMAC check and must be independently validated by the caller (e.g., against the shop that owns the referenced `webhook_id` via a follow-up Admin API call, or against a known/expected shop for the current install).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering event `X` (e.g., `orders/create`).
2. Shopify delivers a webhook POST to the app's endpoint with body `B`, and headers including:
   - `X-Shopify-Hmac-Sha256: HMAC(client_secret, B)`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
3. Attacker captures this request, then re-sends the identical body `B` and identical `X-Shopify-Hmac-Sha256` value, but changes:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, B)` — this still matches, since `B` is unchanged.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the application to process attacker-controlled data as if it belongs to `victim-shop.myshopify.com`. [4](#0-3) [1](#0-0)

          received_signature = verifiable_query.hmac
