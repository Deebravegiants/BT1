### Title
Webhook `shop-domain` header is trusted for tenant routing but is excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards `request.shop` to the app's handler as the tenant identity, so the value that binds a webhook to a merchant is never covered by the cryptographic check that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived from the `hmac-sha256` header: [1](#0-0) 

`shop` is read from the `shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`; it never touches `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed into the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop-that-produced-this-signed-body == shop-domain-header-trusted-by-the-handler`

Because the HMAC only covers `@raw_body`, this equality is never checked. An unprivileged internet user who obtains any one legitimately-signed webhook body+HMAC pair (e.g., from their own store's webhook logs, a captured request, or a debugging proxy — no `api_secret_key` needed) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a *different* merchant. `HmacValidator.validate` will still return `true` because the signature check is body-only, and `Registry.process` will hand the forged `shop` value straight to the handler via `WebhookMetadata`.

### Impact Explanation
This breaks the tenant/session boundary that the gem is expected to enforce for webhook processing: an attacker-controlled `shop` value flows into the application logic as if it were authenticated, enabling data to be attributed to (or acted upon for) a shop other than the one that actually generated the webhook. This is a cross-tenant confusion vulnerability reachable purely by replaying previously-observed, otherwise-legitimate webhook traffic — no access token, `client_secret`, or privileged access is required.

### Likelihood Explanation
High. The prerequisite is only possession of one prior legitimate webhook body+signature pair for any shop (easily obtainable by any merchant using the app, since apps commonly log inbound webhook payloads, or via basic request interception on the attacker's own store's webhook deliveries). No secret material is required to forge the `shop-domain` header, since it sits entirely outside the HMAC's scope.

### Recommendation
Include the trusted identity fields (`shop-domain` at minimum, ideally `topic`/`webhook-id`) in the HMAC-covered signable string, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is exposed via `Request#shop` / passed to `WebhookMetadata`. At minimum, document clearly that `shop` is unauthenticated and require host applications to cross-check it against a known/registered shop for the resource in question before trusting it.

### Proof of Concept
```ruby
# Attacker has captured one legitimate webhook delivery for shop-a.myshopify.com
raw_body = '{"id": 123, "...": "..."}'
hmac_b64 = "captured-valid-base64-hmac-for-raw_body-and-secret"

# Replay with a different tenant header — signature still validates because
# the HMAC only ever covered raw_body, never the shop-domain header.
forged_headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unsigned
  "x-shopify-webhook-id" => "attacker-chosen",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/HMAC pair is genuinely valid)
# => handler.handle receives shop: "victim-shop.myshopify.com" with attacker-controlled body,
#    even though that body was never produced for victim-shop.
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
