### Title
EmporiumUpgradeable.payRelayFees fallback branch charges an unsigned, arbitrary `feeStructure.feeToken` from the EIP-7702 wallet - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.verifyWallet` only checks the numeric value `circomData.feeStructure.flatFee <= stack.maxFee`, while `EMPORIUM_SIGNATURE_TYPEHASH` never includes `feeStructure` (or any token identifier) in the signed payload. Because `feeStructure.feeToken` is unsigned, `payRelayFees`'s fallback branch (`!foundToken && feeStructure.flatFee != 0`) will call `payRelay`/`sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay` for whatever `feeStructure.feeToken` the transaction submitter chooses, pulling that token straight out of the delegated wallet's balance without the signer ever having authorized that specific token as a fee source.

### Finding Description
The claimed equality is: `feeStructure.feeToken` charged by `payRelay` should be a token contained in the signer's `EMPORIUM_SIGNATURE_TYPEHASH`-covered authorization. Tracing the code shows this equality never holds:

- The EIP-712 typehash only covers `message`, `ops`, `maxFee`, `deadline`: [1](#0-0) 
- `verifyWallet` recovers the signer over exactly those fields and only bounds the fee amount, never the fee token: [2](#0-1) 
- `payRelayFees` loops `erc20TokenAddresses` looking for a match to `feeStructure.feeToken`; if none of the tokens actually debited in this call match it, `foundToken` stays `false`, and the fallback branch still fires as long as `signerAddress != address(0)` and `flatFee != 0`, charging `feeStructure.feeToken` directly regardless of whether it was ever referenced anywhere else in the transaction: [3](#0-2) 
- That fallback ultimately calls `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`: [4](#0-3) 
- `HinkalWallet.doSendToRelay` is only gated by `onlyEmporium` and blindly forwards whatever `erc20TokenAddress` and `actualAmount` Emporium passes, with no check tying it to anything the wallet owner signed: [5](#0-4) 

Root cause: the wallet owner's EIP-712 signature authorizes a numeric fee cap (`maxFee`) but not the token that fee will be denominated in. `circomData.feeStructure` (including `feeToken`) is not part of the signed struct; it is only checked for internal self-consistency via `calldataHash` (`CircomDataBuilder.getHashedCalldata`/`performHinkalChecks`), which merely verifies that the submitted `feeStructure` matches the hash baked into the proof's public input — it does not constrain `feeToken` to any token the signer actually agreed to. Since the raw `(v, r, s)` signature and all `EmporiumStack` fields are visible calldata once a legitimately-signed stack is produced (e.g., handed to a relay for submission), any party holding that signature can resubmit it with a substituted `feeStructure.feeToken`, as long as `flatFee <= stack.maxFee`, and drain that arbitrary token from the delegated wallet.

Existing guards do not prevent this: `performHinkalChecks`'s `calldataHash` check only enforces internal consistency of the submitted struct, not that `feeToken` was ever intended by the signer; the circuit's public inputs (`formBasicInput`) never include `feeStructure` fields at all, so the ZK proof places no constraint on it either; and `usedMessages` only prevents nonce replay, not substitution of `feeToken` on first use.

### Impact Explanation
An attacker able to obtain (front-run, intercept, or otherwise acquire) a validly-signed `EmporiumStack` intended for legitimate relaying can substitute `feeStructure.feeToken` with any ERC20 the delegated wallet holds and drain up to the signed `maxFee` amount of that token to `circomData.relay`, regardless of whether that token was ever part of `erc20TokenAddresses` or the signed message. This is theft of wallet funds via a call the signer never authorized for that token, matching the "High" severity category (executing calls/moving assets a wallet owner never authorized). It is repeatable once per distinct `emporiumMessage` nonce, and an attacker can obtain many such signatures if they operate/control a relay-facing frontend that collects signed stacks from users for submission.

### Likelihood Explanation
Preconditions: attacker needs access to a signed `EmporiumStack` (v, r, s, signerAddress, ops, maxFee, deadline) before/at the time it is submitted — plausible in the intended relay model where signed payloads are handed off for third-party submission, or observable in a public mempool. Attacker also needs to construct a valid `circomData`/proof for the Emporium action (feasible with `erc20TokenAddresses` unrelated to the target token, or empty, using `formInputEmporiumMin`), and the wallet must hold a non-zero balance of the chosen token. No privileged role is required. Cost is limited to gas and running the existing proving pipeline for a self-authored transaction.

### Recommendation
Include `feeStructure.feeToken` (and ideally `flatFee`/`variableRate`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` so the signer explicitly authorizes which token(s) may be charged as relay fees, or restrict the fallback branch in `payRelayFees` to only ever charge tokens that also appear in `circomData.erc20TokenAddresses` (rejecting the transaction instead of falling back to an unconstrained `feeStructure.feeToken`).

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, `HinkalWallet` delegated to a test EOA (`signerAddress`), fund the wallet with DAI and USDC.
2. Have `signerAddress` sign an `EmporiumStack` (ops referencing only USDC-related calls, `maxFee = X`, `deadline`) per `EMPORIUM_SIGNATURE_TYPEHASH`.
3. Craft `circomData` with `erc20TokenAddresses = [USDC]` (or empty) and `feeStructure.feeToken = DAI`, `flatFee = X`, computing `calldataHash` to match via `CircomDataBuilder`.
4. Call `runAction` (via the allowed-recipient path/`Hinkal.transact`) using the legitimately-obtained signature but the substituted `feeStructure`.
5. Assert: `verifyWallet` passes (`flatFee <= maxFee`), `foundToken` remains `false` in `payRelayFees`, `doSendToRelay` is invoked with `feeToken = DAI`, and the wallet's DAI balance decreases by `flatFee` despite DAI never appearing in `erc20TokenAddresses`, `ops`, or any signed field of `EMPORIUM_SIGNATURE_TYPEHASH`.
