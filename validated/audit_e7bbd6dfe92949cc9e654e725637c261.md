I found the key finding: in `features/tx-signer/src/api/index.ts` and `features/message-signer/src/module/message-signer.ts`, the `walletAccount` passed to signing is resolved from `walletAccountsAtom`/`walletAccountsAtom` by name, but the lookup only checks *existence*, not whether the account is still `enabled` — this is structurally analogous to the reNFT bug where a stale/deactivated policy is still trusted by downstream consumers because they only check "does it exist" rather than "is it currently active."

### Title
Disabled wallet account can still be used to sign transactions/messages because signer APIs only check existence, not `enabled` status - ([File: features/tx-signer/src/api/index.ts])

### Summary
The `transactionSignerApi` and `messageSigner` modules resolve a `WalletAccount` by name from `walletAccountsAtom` and only assert that the record exists, never checking the account's `enabled` flag before using it to sign. This mirrors the reNFT Guard-policy bug class: a "deactivated" authority object (there, an old Guard; here, a disabled wallet account) continues to be usable by downstream consumers because those consumers only validate against a local/stale reference instead of re-checking the canonical "is this still active" status at the time of the privileged operation (signing).

### Finding Description
`walletAccounts.disable()` in `features/wallet-accounts/src/module/wallet-accounts.ts` marks a wallet account as `enabled: false` (or deletes it for hardware accounts) via `#disableWalletAccount` [1](#0-0) , and the UI-facing "enabled accounts" selectors correctly filter out disabled accounts, e.g. `active.ts` only treats an account as active `if` it's in the `enabled` list [2](#0-1) .

However, the transaction-signing API path does not perform this same check. `createTransactionSignerApi` resolves a wallet account purely by presence in `walletAccountsAtom`:
```
const getWalletAccount = async (name) => {
  const walletAccounts = await walletAccountsAtom.get()
  const walletAccount = walletAccounts[name]
  assert(walletAccount, `Unknown wallet account: ${name}`)
  return walletAccount
}
``` [3](#0-2) 

This resolved account is passed straight into `transactionSigner.signTransaction`, which dispatches to `seedBasedTransactionSigner`/hardware signer without any `enabled` check [4](#0-3) , and ultimately into `SeedBasedTransactionSigner.signTransaction`, which derives keys and signs unconditionally based on the account's `seedId`/`index` [5](#0-4) .

The same pattern exists in message signing: `MessageSigner#normalizeWalletAccount` looks up the account by name from `walletAccountsAtom` and only asserts it exists, never that it's `enabled`:
```
const walletAccounts = await this.#walletAccountsAtom.get()
const instance = walletAccounts[walletAccount]
assert(instance, `wallet account ${walletAccount} not found`)
return instance
``` [6](#0-5) 

Because `walletAccounts.disable()` for non-hardware accounts keeps the record in `walletAccountsAtom` (just flips `enabled: false`) rather than removing it [7](#0-6) , any caller that still holds/knows the account name (e.g. a connected dApp, extension UI, or SDK consumer) can continue requesting signatures for that "disabled" account. This is analogous to the reNFT report: the canonical registry (Kernel/`walletAccountsAtom`) has an authoritative "active" flag, but the privileged operation's enforcement path (`checkTransaction`/`signTransaction`) checks a different, weaker condition (existence rather than active-status), letting stale/deactivated entities keep operating with full privileges.

### Impact Explanation
If an origin, UI surface, or SDK integration is expected to only be able to sign for currently enabled accounts (e.g., after a user disables an account to stop using it, expecting it to no longer sign or expose addresses), this gap allows continued unauthorized signing under a disabled account. This is a direct wallet-compromise-adjacent impact: unauthorized signing capability persists after a user believes the account access has been revoked, undermining the intended access-control boundary between "enabled" and "disabled" accounts.

### Likelihood Explanation
Likelihood depends on whether any caller path (dApp connection via `connectedOrigins`, UI, or third-party SDK integration) retains a reference to a wallet-account name after disabling and can still invoke `transactionSigner.signTransaction`/`messageSigner.signMessage` with that name. Given `disable()` doesn't purge the record and the signer paths never re-validate `enabled`, exploitation only requires that some caller has (or can guess/store) the account name — a plausible scenario in a multi-account wallet where account names are predictable (e.g., `exodus_1`).

### Recommendation
In `features/tx-signer/src/api/index.ts`'s `getWalletAccount` and `features/message-signer/src/module/message-signer.ts`'s `#normalizeWalletAccount`, assert `walletAccount.enabled` (in addition to existence) before returning the account for use in signing, mirroring the checks already present in the `active` selector [8](#0-7) .

### Proof of Concept
1. Create two wallet accounts (`exodus_0`, `exodus_1`) via `walletAccounts.create()`.
2. Call `exodus.walletAccounts.disable('exodus_1')` — confirm `getEnabled()` no longer returns `exodus_1` [9](#0-8) .
3. Directly call `exodus.transactionSigner.signTransaction({ walletAccount: 'exodus_1', ... })` (or the equivalent `messageSigner.signMessage`) with the disabled account's name.
4. Observe that `getWalletAccount`/`#normalizeWalletAccount` still resolves the record from `walletAccountsAtom` (since it's merely flagged `enabled: false`, not removed) and passes it through to `SeedBasedTransactionSigner`, which signs the transaction successfully despite the account being disabled.

  disable = async (name: string) => {
    await this.disableMany([name])

  disableMany = async (walletAccountNames: string[]) => {
    const currentWalletAccounts = await this.#getInternalWalletAccountsWithFallback()
    walletAccountNames = walletAccountNames.filter(
      (walletAccount) => currentWalletAccounts[walletAccount]
    )

    if (walletAccountNames.length === 0) return

    const walletAccounts = { ...currentWalletAccounts }

    await this.setActive((oldValue) =>
      walletAccountNames.includes(oldValue) ? WalletAccount.DEFAULT_NAME : oldValue
    )

    for (const walletAccount of walletAccountNames) {
      if (walletAccounts[walletAccount].isHardware) {
        delete walletAccounts[walletAccount]
        delete this.#hardwareWalletPublicKeys[walletAccount]
      } else {
        walletAccounts[walletAccount] = this.#disableWalletAccount(walletAccounts, walletAccount)
      }
    }

    if (equalWalletAccounts(currentWalletAccounts, walletAccounts)) return

    await this.#walletAccountsInternalAtom.set(walletAccounts)
    await this.#savePublicKeys()
    await this.#updateFusion()
  }
