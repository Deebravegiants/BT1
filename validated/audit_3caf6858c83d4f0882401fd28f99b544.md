### Title
Unprotected on-chain AMM spot-price used to swap native token for fee token during `EvmHost.dispatch()`, enabling flash-loan price manipulation - (File: `sdk/packages/core/contracts/apps/HyperApp.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`HyperApp.quote()` and the `EvmHost` dispatch path both derive the native-token cost of a cross-chain message from `IUniswapV2Router02.getAmountsIn`/the configured `uniswapV2` router (or `UniV3UniswapV2Wrapper`), a live AMM spot price with no staleness check, TWAP, or bounded deviation guard. [1](#0-0)  The host's own params document this router as "used for swapping the native token to the feeToken" during dispatch. [2](#0-1)  The docs themselves flag that `quote()` "uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks," but only warn against calling it from *another contract's transaction* — they do not address that the host's own dispatch-time swap is exposed to the identical unguarded price. [3](#0-2) 

### Finding Description
Any unprivileged caller can invoke `dispatch()`/`quote()` in the same transaction as a flash loan that skews the reserves of the configured `uniswapV2` pool (or the V3 pool the `UniV3UniswapV2Wrapper` queries) between `feeToken` and the native asset. Because `getAmountsIn`/`getAmountsOut` reads the pool's instantaneous reserves with no oracle staleness bound, no TWAP, and no deviation cap against a trusted reference (unlike, for example, `SimplexPaymaster._getOraclePrice`, which enforces `maxOracleAge` and reverts on non-positive answers [4](#0-3) ), the fee computed for dispatching a cross-chain message can be pushed arbitrarily low or high within one atomic transaction. The V3 wrapper variant is explicitly noted to *write state* via the quoter, meaning it must be reached through a `CALL`, further confirming the pricing call executes live, manipulable AMM logic rather than a cached/oracle-protected value. [5](#0-4)  The Rust relayer/gas-oracle mirrors this same unguarded on-chain quote when computing gas costs. [6](#0-5) 

### Impact Explanation
An attacker who flash-loan-manipulates the native/feeToken pool immediately before calling `dispatch()` can pay a drastically reduced native-token fee for message dispatch (or, conversely, force other users' `quote()`-based fee estimates to be wrong), starving relayers of adequate compensation or under-collateralizing the fee actually swapped into `feeToken` by the host. Since dispatch fees fund relayer delivery and Hyperbridge's own revenue accounting, systematic underpayment via price manipulation degrades protocol economics and relayer incentives — a Medium/High-severity issue depending on deployed pool liquidity, matching the flash-loan oracle-manipulation bug class from the Deus Finance report.

### Likelihood Explanation
Likelihood is bounded by how much liquidity backs the specific `uniswapV2`/V3 pool configured for a given `EvmHost` deployment — thin pools (as often exist for a bridge's native/feeToken pair on smaller EVM chains) are cheaply manipulable via flash loan, while deep pools (e.g., mainnet ETH/DAI) are not economically attackable. The vulnerability is reachable by any single unprivileged transaction/extrinsic (`dispatch()`), requires no privileged role, and the code contains no on-chain mitigation (no slippage bound, no oracle freshness check) — only documentation warning developers not to call `quote()` from another contract, which does not address host-side manipulation during dispatch itself.

### Recommendation
Add a maximum-input / minimum-output slippage bound (or TWAP-based pricing with staleness checks, mirroring `SimplexPaymaster._getOraclePrice`'s `maxOracleAge` and non-positive-answer reverts) to the native↔feeToken swap path in `EvmHost` and to `HyperApp.quote()`, and consider requiring callers to pass an acceptable slippage/maxAmountIn parameter that the swap enforces atomically, reverting if the live pool price has moved beyond the caller's tolerance.

### Proof of Concept
Not independently reproduced in this pass — the finding is derived from static analysis of `HyperApp.quote()`, `EvmHost`'s `uniswapV2` router usage, and the `UniV3UniswapV2Wrapper`'s state-writing quoter call, all of which lack slippage/staleness protection; verifying exploitability would require forking a chain with a specific, sufficiently thin `uniswapV2` pool configured on a live `EvmHost` and confirming a flash loan reduces the swap output/increases favorable pricing within one transaction. I was not able to view the exact `dispatch()` swap-execution code (e.g., `swapETHForExactTokens` call site with `amountInMax`) before running out of tool calls, so I cannot confirm whether any refund/slippage-limit parameter is already enforced at the swap-execution step itself (as opposed to the `quote()`/`getAmountsIn` estimation step) — this should be verified by a Devin session with full file access.

    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
