Based on my investigation, the "sanctioned users can transfer tickets without check" bug class maps to a **missing relayer-authorization gate** on the Tron fork's `IntentGatewayV2.onAccept`.

### Title
Tron `IntentGatewayV2.onAccept` omits the relayer authorization gate, allowing any relayer to forge escrow releases and governance actions - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `ExtrinsicIntents.onAccept` gates every incoming delivery with `_checkRelayer(incoming.relayer)` before decoding the request body [1](#0-0) , mirroring the documented design that "once a relayer is set, rejects deliveries from anyone else before the body is read" [2](#0-1) . The Tron fork's `IntentGatewayV2.onAccept` is only gated by `onlyHost` and never calls any relayer check at all before dispatching `RedeemEscrow`/`RefundEscrow` withdrawals or governance actions [3](#0-2) .

### Finding Description
`ExtrinsicIntents._checkRelayer` and the accompanying flow doc establish that the intended security model is: "a delivery from anyone but the authorised relayer never decodes the body, never runs `_authenticate`, and leaves no receipt" [4](#0-3) . This gate exists specifically because `EvmHost.dispatchIncoming` forwards the real relayer address into `IApp.onAccept`, and the app is expected to reject anyone but the one authorized relayer once armed [5](#0-4) .

The Tron deployment of the same gateway logic (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reimplements `onAccept` but drops this check entirely — the function goes straight from the `onlyHost` modifier to reading `RequestKind` from the body [3](#0-2) . `onlyHost` only proves the call came from the local host contract (any relayer who successfully submits a valid consensus/state proof reaches the host), it does not restrict *which* relayer's delivery is honored. Since the Tron contract has no `_relayer`/`_checkRelayer` mechanism at all, there is no way to close this gate even by governance/owner action, unlike the EVM version where `setRelayer` exists specifically to arm this check [6](#0-5) .

This is structurally the same bug class as the reported issue: a permission check ("not sanctioned"/"authorized relayer") exists and is enforced on one code path (the canonical `ExtrinsicIntents.onAccept`) but is missing on the analogous path in a sibling deployment (`tron/.../IntentGatewayV2.onAccept`), letting an unprivileged/unauthorized party carry out the sensitive action (escrow release, refund, governance upgrade) that the check was designed to block.

### Impact Explanation
Any relayer capable of getting a message past the ISMP handler/host on the Tron deployment — not just the intended authorized relayer — can trigger `RedeemEscrow`/`RefundEscrow` withdrawals and privileged governance actions (`NewDeployment`, `UpdateParams`, `SweepDust`) [7](#0-6) . Because the EVM sibling explicitly treats this as a security-critical control (protecting escrow redemption/refund and governance actions from a malicious or compromised relayer), its absence on Tron removes protection against a malicious/rogue relayer forging or front-running settlement messages, directly risking theft of escrowed user/solver funds and unauthorized governance state changes (new instance registration, parameter updates, dust sweeps) on that chain.

### Likelihood Explanation
High reachability: any party that can act as a relayer for the Hyperbridge message-passing pipeline into this Tron gateway can exploit this immediately, with no special privilege beyond being an unauthorized/otherwise-untrusted relayer — exactly the "unprivileged relayer" actor class in scope. No additional preconditions (governance misconfiguration, admin compromise) are required, unlike the EVM gateway's "open until armed" window, since the Tron contract has no arming mechanism to close the gate at all.

### Recommendation
Port the `_relayer` / `_checkRelayer` / `setRelayer` allowlist mechanism from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and call `_checkRelayer(incoming.relayer)` (and the equivalent in `onGetResponse`) at the top of `onAccept`, before any request-kind branching or body decoding, mirroring the EVM implementation.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with an order escrowed via `placeOrder` on the source chain [8](#0-7) .
2. Any relayer (not the operator's intended/trusted relayer) submits a `RedeemEscrow` or `RefundEscrow` `PostRequest` through the host to `onAccept`.
3. Because `onAccept` only checks `onlyHost` and never inspects `incoming.relayer`, the withdrawal proceeds and funds are released to the attacker-chosen beneficiary in the request body [9](#0-8) [10](#0-9) . This contrasts with the EVM test suite, which explicitly demonstrates the intended-blocked case (`testOnAcceptRejectsUnlistedRelayer`) that has no Tron counterpart [11](#0-10) .

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
            _instances[keccak256(body.stateMachineId)] = body.gateway;

            emit NewDeploymentAdded({stateMachineId: body.stateMachineId, gateway: body.gateway});
        } else if (kind == RequestKind.UpdateParams) {
            // Decode the body which includes optional destination-specific protocol fee updates
            ParamsUpdate memory update = abi.decode(incoming.request.body[1:], (ParamsUpdate));
            emit ParamsUpdated({previous: _params, current: update.params});
            _params = update.params;

            // Update destination-specific protocol fees if provided
            for (uint256 i; i < update.destinationFees.length;) {
                bytes32 stateMachineId = update.destinationFees[i].stateMachineId;
                uint256 feeBps = update.destinationFees[i].destinationFeeBps;
                _destinationProtocolFees[stateMachineId] = feeBps;

                unchecked {
                    ++i;
                }
                emit DestinationProtocolFeeUpdated(stateMachineId, feeBps);
            }

            SweepDust memory req = abi.decode(incoming.request.body[1:], (SweepDust));

                unchecked {
                    ++i;
                }

1. A relayer calls `HandlerV2.handlePostRequests` (or `handleGetResponses`). After proof

   plain `msg.sender`; the handler has no trusted forwarder.
2. `EvmHost.dispatchIncoming` (restricted to the handler) writes a receipt for the request
   commitment, then low-level calls the module with `IApp.onAccept(IncomingPostRequest(request,
   relayer))`. If that call fails the host deletes the receipt and returns without reverting, so the
   rest of the batch proceeds and the message stays deliverable.
3. `ExtrinsicIntents.onAccept` runs `onlyHost`, then `_checkRelayer(incoming.relayer)`, which reverts
   with `Unauthorized` when a relayer is set and the delivery is from anyone else. Only then is the
   first body byte read as a `RequestKind`. `onGetResponse` has the same two steps before touching
   the response.
