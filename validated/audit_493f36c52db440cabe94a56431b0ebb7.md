### Title
Webhook `shop` identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity passed to the host application's handler. Because the HMAC signature covers only the body bytes and never binds the `shop` header, an attacker who legitimately receives one valid webhook (e.g. by installing the app on their own store and triggering an event) can replay that exact `body + hmac` pair to the app's shared webhook endpoint while substituting a different `x-shopify-shop-domain`/`shopify-shop-domain` header value. The HMAC check still passes, and the host app processes attacker-controlled data under a victim shop's identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`, which for webhooks is defined as `@raw_body` and nothing else: [1](#0-0) [2](#0-1) 

The `shop` accessor, however, is read straight from the (unsigned) HTTP header: [3](#0-2) 

`Registry.process` validates the HMAC, then hands the handler a `WebhookMetadata` whose `shop` field comes directly from that unauthenticated header, with no cross-check between the shop that "should" have signed the body and the shop claimed in the header: [4](#0-3) 

This breaks the identity binding: `hmac(body) valid` is treated as equivalent to `shop header == true tenant of body`, but the header is never part of the signed material, so the two are independent. Any party that can present *some* valid `(body, hmac)` pair signed with the app's shared secret — trivially obtainable by installing the app on their own store and capturing one real webhook delivery — can resend that same pair to the app's public webhook endpoint with an arbitrary `shop-domain` header, and `Utils::HmacValidator.validate` will accept it.

### Impact Explanation
This is a cross-tenant identity confusion: a webhook payload genuinely originating from shop A's account can be replayed and attributed to shop B, and the host application's `WebhookHandler#handle` will act on it as if shop B had produced that data (e.g. writing into shop B's tenant records, triggering shop-B-scoped business logic, or corrupting per-tenant state) even though the content and any embedded identifiers are controlled by the attacker's own shop A. This qualifies as cross-tenant access under an unprivileged-internet-user threat model, since no access token, `client_secret`, or privileged credential is required — only a normal app installation on the attacker's own store and the ability to reach the app's public webhook URL.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where the webhook endpoint is reachable over the public internet (the normal deployment model, since Shopify itself delivers webhooks over plain HTTPS POST with no client-certificate or IP-based authentication enforced by this library). The only prerequisites are: (1) the attacker can install the app on a store they control (self-service, unprivileged) to obtain one legitimately signed `(body, hmac)` pair, and (2) the app's webhook path is a single shared endpoint across tenants, which is the standard multi-tenant pattern this library's `Registry` is built for.

### Recommendation
Bind the claimed shop to the signed material, e.g. by including the `shop-domain` (and ideally `topic`/`webhook-id`) header value as part of `to_signable_string`, or by requiring host applications to independently verify that `request.shop` corresponds to a shop with a valid, currently-installed session/access token before dispatching to the handler. At minimum, document prominently that `request.shop` is not authenticated by the HMAC and must be re-validated by the consuming application against known installed shops.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers/receives one webhook (e.g. `orders/create`) at the app's shared callback URL, capturing the raw body and its `x-shopify-hmac-sha256` header — a legitimately signed `(body, hmac)` pair.
2. Attacker sends a new HTTP POST to the same public webhook endpoint with the identical `body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(body, secret) == received_hmac` — this passes because `body`/`hmac` are unchanged. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker-supplied body as if it belonged to the victim tenant.
