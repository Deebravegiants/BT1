## Analysis: PoA Bridge status matching ignores withdrawal index — misattributes destination tx hash across withdrawals of the same asset

### Title
Withdrawal status/tx-hash misreport for batched same-asset PoA Bridge withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status of a withdrawal by looking up the POA Bridge API response and matching **only by `assetId`**, ignoring the `index` that uniquely identifies which withdrawal in a batch is being queried. When a caller submits multiple withdrawals of the same token (same `assetId`, e.g. two different destination addresses) in one intent, every one of those withdrawals resolves to the *same* API record — the status/txHash of whichever entry the API happens to return first for that asset.

`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is implemented as: [1](#0-0) 

This is explicitly acknowledged in the code comment as unsupported: "multiple withdrawals of the same token in a single transaction are not supported." Despite that, nothing upstream prevents such a batch from being constructed and monitored — `createWithdrawalIdentifiers` assigns per-route index counters without any per-asset disambiguation, so two `withdrawalParams` with identical `assetId` but different `destinationAddress` both get indices under the same `PoaBridge` route: [2](#0-1) 

Each of those withdrawal identifiers is subsequently polled independently by `watchWithdrawal`, which trusts whatever `status`/`txHash` `describeWithdrawal` returns as the on-chain outcome: [3](#0-2) 

Because `findMatchingWithdrawal` only keys on `assetId` and not `index`/destination, both withdrawal-index queries return the *first* matching entry from the API's (unsorted) withdrawal list — i.e., the same `transfer_tx_hash` and `status` gets reported for withdrawal A and withdrawal B, even if B is still pending, failed, or resolved to a completely different destination/transaction on-chain.

The exact same bug pattern (matching by `assetId` alone) also exists in the sibling implementation used by `waitForWithdrawalCompletion` in `internal-utils`: [4](#0-3) 

### Impact Explanation
This breaks the equality "status/hash reported == the actual on-chain outcome for *that specific* withdrawal." An integrator batching multiple same-token withdrawals (e.g., paying out several users the same NEP-141 asset in one intent) and using `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` per-index would receive a `completed` status and `txHash` for withdrawal B that actually belongs to withdrawal A's on-chain transfer. This can cause an integrator to:
- Mark withdrawal B as completed (and release/credit downstream) while B is still pending or has failed.
- Record the wrong destination transaction hash for reconciliation, causing a double-credit or a missed failure detection for the withdrawal that never actually completed.

This matches the "High" bucket in the rules: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
No malicious actor is required — any legitimate integrator submitting a batch of same-asset withdrawals (a supported/likely usage pattern per the SDK's own "Batch Processing" feature described in the README) triggers this. The bug is deterministic whenever ≥2 withdrawals share an `assetId` under the PoA route, not a rare edge case.

### Recommendation
`findMatchingWithdrawal` must disambiguate withdrawals sharing the same `assetId` within a batch — e.g., by also matching on destination address/amount, or by requiring/using an API-provided identifier tied to the specific withdrawal request, rather than falling back to "first entry matching this token." Until the POA API supports precise per-withdrawal correlation, the SDK should refuse to track (throw) rather than silently misreport status/txHash for batches containing duplicate `assetId` entries.

### Proof of Concept
1. Submit an intent with `withdrawalParams = [{assetId: "nep141:usdc.omft.near", amount: X, destinationAddress: A}, {assetId: "nep141:usdc.omft.near", amount: Y, destinationAddress: B}]` via the PoA route.
2. `createWithdrawalIdentifiers` assigns index 0 and index 1 under `RouteEnum.PoaBridge` (see `withdrawal-watcher.ts:80-107`).
3. Call `sdk.createWithdrawalCompletionPromises` for both.
4. Suppose the POA Bridge processes the withdrawal to A first, completing with `transfer_tx_hash = "0xA"`, while withdrawal to B is still pending.
5. `PoaBridge.describeWithdrawal` for **both** indices calls `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")`, which returns the single completed entry (`0xA`) regardless of index, per `poa-bridge.ts:409-427`.
6. Both promises resolve `{status: "completed", txHash: "0xA"}` — the integrator believes B's withdrawal to address B has landed at `0xA`, when in reality that hash corresponds only to A's payout.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
