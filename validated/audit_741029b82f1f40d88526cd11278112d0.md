### Title
Withdrawal status falsely reported as "completed" on corrupt/unparseable HOT bridge contract response - (File: `packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts`)

### Summary
`HotBridge.describeWithdrawal` treats an invalid, non-hex `status` value returned by the HOT contract's `getGaslessWithdrawStatus` call as a **completed** withdrawal (with `txHash: null`), instead of leaving it `pending` or surfacing an error. This breaks the equality that the reported `WithdrawalStatus` must reflect the real on-chain outcome.

### Finding Description
`describeWithdrawal` queries `this.hotSdk.getGaslessWithdrawStatus(nonce)` and expects either the sentinel `HotWithdrawStatus.Completed`/`Canceled` string or a hex-encoded destination transaction hash [1](#0-0) .

For non-EVM/Stellar/TON chains, when the returned `status` is a string but fails the `isHex` check — an explicitly unexpected/corrupt value per the inline warning "HOT Bridge incorrect destination tx hash detected" — the code still returns `{ status: "completed", txHash: null }` instead of treating this as pending or failed: [2](#0-1) 

This is the exact analog of the `applyCover` bug class: a status/outcome is reported to callers that does not correspond to the verified on-chain state (the code itself acknowledges the value is "incorrect"/unexpected, yet still emits a positive "completed" signal).

### Impact Explanation
`describeWithdrawal`'s result feeds directly into `watchWithdrawal`, which stops polling and resolves successfully as soon as `status === "completed"` [3](#0-2) . That resolved value is what `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` return to the integrator [4](#0-3) . An integrator relying on this SDK-reported completion (e.g., to credit a user, release an off-chain balance, or mark a batch withdrawal as fully done) would do so based on a "completed" status that the SDK itself detected as anomalous/corrupt, with no verified destination transaction hash (`txHash: null`). This matches the High-severity impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This path is reached only when the HOT contract's non-EVM status view returns a string that is not a recognized sentinel and not valid hex — an edge case (contract/indexer inconsistency or unexpected raw bytes) rather than routine operation, and only for non-EVM/Stellar/TON destination chains going through the primary contract-view branch (bridge indexer/API fallback is bypassed in this branch). This makes it a low-to-moderate likelihood but concrete, code-confirmed defect (the developers' own comment flags the value as "incorrect") rather than a purely theoretical one.

### Recommendation
When `status` is a string that fails `isHex(status)`, do not report `completed`. Instead:
- Fall back to the API indexer lookup (`fetchWithdrawalHashFromApi`) the same way the `else` failure branches do, or
- Return `{ status: "pending" }` (or a dedicated error/failed status) until a verifiable destination hash can be obtained, mirroring the more conservative TON handling a few lines above that keeps status `pending` on indexer failure [5](#0-4) .

### Proof of Concept
1. Withdraw an asset on a non-EVM/non-Stellar/non-TON chain via `HotBridge` (e.g., Solana/TON-adjacent flow taking the `else` branch).
2. Mock/observe `hotSdk.getGaslessWithdrawStatus(nonce)` returning an arbitrary non-hex string (contract bug, indexer glitch, or malformed raw bytes) instead of `HotWithdrawStatus.Completed` or a valid hex hash.
3. `describeWithdrawal` logs "HOT Bridge incorrect destination tx hash detected" but still returns `{ status: "completed", txHash: null }` (lines 471-481).
4. `watchWithdrawal` immediately resolves with `{ hash: null }`, and any caller of `sdk.waitForWithdrawalCompletion` treats the withdrawal as finished, even though no destination transaction was ever verified.

**Note:** This analog was found by inspecting `describeWithdrawal` implementations across all bridge adapters (`hot-bridge.ts`, `omni-bridge.ts`, `poa-bridge.ts`); only the HOT bridge branch exhibits this "known-bad value reported as success" pattern. The other bridges (`omni-bridge.ts`, `poa-bridge.ts`) correctly return `pending` or `failed` when data is missing/ambiguous.
