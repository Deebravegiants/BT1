### Title
Webhook shop/topic identity spoofing via headers not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unsigned HTTP headers to build the `WebhookMetadata` handed to the app's handler. Because those identity fields are never included in the HMAC-signed material, an attacker who has legitimately received one valid `(body, hmac)` webhook pair for their own shop can replay that exact body/HMAC while relabeling the `shopify-shop-domain` (and/or `shopify-topic`) header to a different, victim tenant. The signature check still passes, and the handler executes with the attacker-chosen shop identity — breaking the equality `signed_origin_shop == asserted_shop`.

### Finding Description
`HmacValidator.validate` is the only authentication performed on inbound webhooks: [1](#0-0) 

The value it signs comes exclusively from `Request#to_signable_string`, which returns the raw body — nothing else: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body: [3](#0-2) 

`Registry.process` validates only the HMAC, then unconditionally trusts `request.shop`/`request.topic` to build the metadata passed to the app's handler: [4](#0-3) 

The identity binding this gem is supposed to guarantee is: *the shop that cryptographically produced this webhook body equals the shop attributed to the event delivered to the handler.* Before the attack, that equality holds because Shopify computes `HMAC(secret, body)` and sets `shop-domain` together, atomically, for the shop the event actually belongs to. After the attack, an attacker who is a legitimate merchant of the app (or who otherwise obtains one valid `(body, hmac)` pair, e.g., by triggering a webhook to their own shop) can resend the identical body and HMAC, but with the `shopify-shop-domain` header changed to any other shop string of their choosing (a different real merchant of the same app). `HmacValidator.validate` only re-derives `HMAC(secret, body)` and compares it to the supplied HMAC — it has no dependency on the header values — so the check still succeeds, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive scoped to the app built on this gem: the app's webhook handler receives an authenticated-looking event that is attributed to the wrong shop. Depending on what the handler does with `WebhookMetadata#shop` (e.g. looking up/mutating per-shop records, billing, GDPR/data-request processing, uninstall handling), this can let one tenant's traffic masquerade as another tenant's event, which is a cross-tenant access class issue rooted entirely in this gem's verification logic (`HmacValidator`/`Webhooks::Request`/`Registry.process`), not in host-application misuse.

### Likelihood Explanation
Exploitation only requires network access to the app's webhook endpoint plus one previously-observed valid `(raw_body, hmac)` pair — something any merchant/installer of the app can obtain for their own shop by triggering an event (e.g., placing/cancelling an order) and capturing the delivered webhook. No access token, `client_secret`, or privileged credential is required; the gem's own verification surface is what fails to bind the header identity to the signed bytes.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-verified material, or otherwise cryptographically bind them to the body (e.g., verify them against a value looked up via the session/shop store rather than trusting the header verbatim). At minimum, `Registry.process` should treat `request.shop`/`request.topic` as unauthenticated hints and require the host application to cross-check them against the shop the app actually expects, rather than the gem implicitly certifying them via `HmacValidator.validate`.

### Proof of Concept
1. Attacker is (or becomes) a real merchant of the target app and legitimately triggers a webhook, capturing `raw_body` and the `shopify-hmac-sha256` header from the delivery to the app's callback endpoint.
2. Attacker resends an HTTP request to the same webhook endpoint with the identical `raw_body` and `shopify-hmac-sha256`, but sets:
   ```
   shopify-shop-domain: victim-shop.myshopify.com
   ```
3. Server-side, the app calls:
   ```ruby
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
   )
   ```
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes `HMAC(secret, raw_body)` (`lib/shopify_api/utils/hmac_validator.rb:12-22`, `lib/shopify_api/webhooks/request.rb:35-38`), independent of the `shop-domain` header.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), so the app processes an attacker-supplied body as an authenticated event for `victim-shop.myshopify.com`.
