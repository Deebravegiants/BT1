Based on my review of `DepositOnChainUtxosExternalAction.sol`, I found a genuine unauthorized-fund-movement issue that is the closest reachable analog to the referenced bug class ("value moved by Hinkal ... not authorised by the prover or signer").

### Title
Unauthorized ERC20 `transferFrom` using unauthenticated `circomData.originalSender` in `DepositOnChainUtxosExternalAction` - (File: contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
`DepositOnChainUtxosExternalAction.runAction` pulls ERC20 tokens from an address taken directly from `circomData.originalSender`, a prover-supplied field, and credits the resulting on-chain UTXOs to `circomData.stealthAddressStructure`, another prover-supplied field, with no check that these two values correspond to the same, consenting party.

### Finding Description
`runAction` decodes `utxoAmounts` and, for every non-ETH token, executes: [1](#0-0) 
pulling `tokenTotal` from `userAddress = circomData.originalSender` via `transferERC20TokenFrom`, which is `IERC20.safeTransferFrom(userAddress, msg.sender, tokenTotal)` [2](#0-1) . The only checks present in the function are that `originalSender != address(0)` and that `deltaAmounts[i] == 0` [3](#0-2) ; there is no requirement that `originalSender == msg.sender` of the outer `Hinkal.transact()` call, unlike the analogous internal-deposit path which explicitly enforces `circomData.externalActionData.externalAddress == msg.sender` [4](#0-3) .

The resulting UTXOs are created with `stealthAddressStructure: circomData.stealthAddressStructure` — also a free prover-supplied field — and are inserted into the tree as valid, spendable shielded notes via `insertCommitments` [5](#0-4) . Because on-chain UTXO creation in this path requires no nullifier / spend-authorization proof over the `originalSender` address (it only needs `originalSender` and the deposited amount to be internally consistent for the balance equation in `Hinkal.transact()`), any caller who can construct any valid proof for `circomData` can set `originalSender` to any address that has previously granted ERC20 allowance to this contract (a realistic scenario, since infinite/one-time approvals to a known, whitelisted external-action contract are a normal UX pattern), and set `stealthAddressStructure` to their own key. The victim's tokens are then pulled into Hinkal and minted as a shielded UTXO owned by the attacker.

### Impact Explanation
This breaks the intended equality that only the token owner (or an entity they explicitly authorized via signature/allowance intended for this specific deposit) can direct value into a shielded UTXO — i.e., "a transferFrom ... not authorised by the prover or signer." Any victim with a standing ERC20 allowance to this contract can have their tokens stolen and converted into an attacker-controlled shielded balance, matching the Critical impact category (direct theft of user funds / minting shielded value not backed by the victim's consent).

### Likelihood Explanation
Likelihood is contingent on victims having granted an ERC20 allowance to this specific external-action contract address, which is a normal and expected setup step for using this deposit flow repeatedly (avoiding per-tx approvals). Once such an allowance exists, exploitation requires only submitting a `transact()` call with attacker-chosen `originalSender`/`stealthAddressStructure` and a self-consistent (but otherwise trivial) proof — no special privilege is needed.

### Recommendation
Add an explicit check in `DepositOnChainUtxosExternalAction.runAction` (or in `Hinkal._externalTransact`) requiring `circomData.originalSender == msg.sender` of the top-level `transact()` call (mirroring the check already used in `_internalTransact` at `contracts/Hinkal.sol:177-187`), or otherwise cryptographically bind `originalSender` to a signature that can only be produced by the token owner.

### Proof of Concept
1. Victim approves `DepositOnChainUtxosExternalAction` for `tokenX` (e.g., unlimited allowance) as part of normal onboarding to this deposit flow.
2. Attacker calls `Hinkal.transact(...)` with `circomData.externalActionData.externalActionId` pointing to `DepositOnChainUtxosExternalAction`, `circomData.originalSender = victim`, `circomData.stealthAddressStructure = attacker's key`, and `utxoAmounts` metadata equal to the victim's allowance/balance.
3. `runAction` executes `transferERC20TokenFrom(tokenX, victim, Hinkal, tokenTotal)`, pulling the victim's tokens into Hinkal.
4. The resulting UTXO is inserted into the tree with the attacker's `stealthAddressStructure`, giving the attacker a spendable shielded note backed by the victim's stolen tokens.

Note: I could not fully verify within the available iterations whether `originalSender` is separately constrained inside `HinkalHelper.performSideEffects` or `CircomDataBuilder.sol` (both reference `originalSender`) in a way that might mitigate this; a full review of those files is recommended to confirm whether any binding to the proof's public inputs or a signature check exists there.
