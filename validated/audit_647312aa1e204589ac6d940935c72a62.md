### Title
Webhook `shop`, `topic`, and `webhook_id` are unauthenticated headers not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that are used to build the `WebhookMetadata` passed to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that `to_signable_string` value and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates handling on this validation, then constructs `WebhookMetadata` directly from the request's `shop`, `topic`, `webhook_id`, and `api_version` accessors, all of which are read straight from unauthenticated headers: [3](#0-2) [4](#0-3) 

The equality the code implicitly relies on but does not enforce is: `bytes verified by HMAC == bytes parsed and acted upon`. In reality, `bytes verified` = `raw_body` only, while `bytes parsed and acted upon` = `raw_body + shop-domain + topic + webhook-id + api-version` headers. Any header outside the raw body can be altered by a request sender without invalidating the HMAC, since the secret-keyed signature never covers them.

The published gem documentation reinforces the false assumption that the whole request is authenticated: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook." [5](#0-4) 

### Impact Explanation
An actor who can obtain one genuine `(raw_body, hmac)` pair signed with the app's `api_secret_key` — e.g. by installing the app on their own shop and receiving a real webhook delivery for it — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `topic`/`webhook_id`) header for a victim shop. `Registry.process` will pass HMAC validation (since only the body is checked) and dispatch a `WebhookMetadata` claiming to be from the victim shop, with attacker-influenced topic/body content, to the app's handler. Because host apps are told the "request" itself was verified as coming from Shopify, they generally trust `data.shop` for tenant routing (e.g., looking up/refreshing shop records, updating tenant-scoped data) — allowing cross-tenant data injection/confusion without any credential of the victim shop.

### Likelihood Explanation
The likelihood is moderate: it requires the attacker to have legitimately received at least one signed webhook (trivial for any developer/free-tier merchant who installs the app), and it does not require possession of `api_secret_key`, a leaked token, or any privileged access — fitting the "unprivileged internet user" threat model. It does depend on the host application trusting `data.shop`/`data.topic` for tenant-scoped actions, which is exactly the pattern the gem's own documentation and example handler encourage (`shop_domain: data.shop`).

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC signable string (or otherwise cryptographically bind them to the verified payload), or clearly document that `Registry.process` only authenticates the raw body and that consuming applications must independently validate `data.shop` against a known/expected shop before trusting it for tenant-scoped operations.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a real webhook with a valid `x-shopify-hmac-sha256` for some `raw_body` (e.g. `orders/create` payload).
2. Capture `(raw_body, hmac)`.
3. POST to the app's webhook endpoint with the same `raw_body`/`hmac`, but set `x-shopify-shop-domain: victim.myshopify.com` and optionally a different `x-shopify-topic`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the secret-derived HMAC: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never actually originated from that shop, letting the attacker inject data attributed to a tenant they do not control.
