This confirms the vulnerability chain. The `WebhookMetadata.shop` field is populated directly from `request.shop` [1](#0-0)  and passed unmodified to the host app's `handle(data:)` implementation as an authenticated-looking tenant identifier [2](#0-1) , while the HMAC that `Registry.process` actually verifies only covers the raw JSON body, never the shop-domain header.

### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature computed by `HmacValidator` only signs the raw request body via `to_signable_string`. The `shop` value is never part of the signed material, so it can be freely substituted by anyone who can produce a request with a valid body/HMAC pair, allowing cross-tenant webhook impersonation.

### Finding Description
`Registry.process` treats a request as authentic solely based on `Utils::HmacValidator.validate(request)` succeeding, then immediately trusts `request.shop` when building `WebhookMetadata` for the app's handler: [3](#0-2) 

The HMAC check itself only validates the raw body: [4](#0-3) [5](#0-4) 

`to_signable_string` returns `@raw_body` only — the `shop`, `topic`, `webhook-id`, and `api-version` headers are excluded from the signed string. This breaks the intended identity binding: **`shop` field trusted by the handler == `shop` field covered by the HMAC**. In reality, `shop` is read straight from an unauthenticated header while only the JSON body bytes are authenticated.

Because a single app's `api_secret_key` is shared across every merchant shop that installs the app, an unprivileged attacker can:
1. Install the target app on their own (attacker-controlled) development/free store, which is a normal, unprivileged action.
2. Trigger any webhook topic the app subscribes to (e.g., `orders/create`) by performing an action in their own store, causing Shopify to deliver a webhook to the app's callback URL with a body and `X-Shopify-Hmac-Sha256` value computed using the app's real (shared) secret.
3. Capture that body + HMAC pair (trivial since it is delivered to infrastructure the attacker controls, or simply observed via the attacker's own store's outbound webhook logs).
4. Replay the exact same body and HMAC header to the app's public webhook endpoint, but swap `X-Shopify-Shop-Domain` to the victim shop's domain.
5. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` forwards `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` to the app's handler.

If the host application uses `data.shop` from `WebhookMetadata` (as the library's own `WebhookHandler` interface encourages, and as shown in the library's tests) to look up per-tenant data, credentials, or perform per-tenant side effects, the attacker can inject data or actions attributed to a shop they do not own — a cross-tenant confusion analogous to the Solidity report's core flaw (a value acted upon that is not actually covered by the verification mechanism protecting it).

### Impact Explanation
This is a cross-tenant identity-binding break: the field consumed as the authoritative tenant identifier (`shop`) is disjoint from the field actually verified by the cryptographic check (raw body only). Depending on host app logic keyed on `WebhookMetadata#shop`, this can lead to cross-tenant data injection/corruption, or attribution of attacker-controlled webhook content to a victim shop, satisfying the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Exploitation requires only: (a) the ability to install the target app on an attacker-owned store — a standard, unprivileged operation available to any internet user for any public app, and (b) capturing a body+HMAC pair from a webhook delivered to that attacker-owned store. No access to `api_secret_key` value itself is needed by the attacker; they only need to replay an existing valid signature computed by Shopify using the shared secret. This is straightforward and repeatable.

### Recommendation
Include the identity-defining headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material — i.e., extend `Request#to_signable_string` to canonicalize and include these header values, not just `@raw_body` — so that the verified bytes and the trusted `shop` value are provably the same. Alternatively/additionally, cross-check `request.shop` against an expected/authorized shop list (e.g., sessions already known to the host app) before dispatching to `WebhookHandler#handle`.
