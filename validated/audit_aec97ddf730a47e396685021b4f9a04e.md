### Title
Unguarded underflow in `Router._computeBuy`'s overflow-cap branch after a token-donation attack inflates `realBalance` above `reserveToken` - ([File: packages/contracts/src/Router.sol])

### Summary
The external report describes a NULL pointer dereference in Open Babel's CACAO parser: a malformed/attacker-crafted input reaches a code path that dereferences a pointer without checking it was set, crashing the process (CWE-404/CWE-476). The alt.fun analog is an arithmetic-underflow panic (Solidity's equivalent unchecked-precondition class) in `Router._computeBuy`'s overflow-cap branch, reachable by any unprivileged address that donates the launched `Token` directly to its `Pair` before a subsequent buy hits the cap.

### Finding Description
`Router._computeBuy` computes the standard curve output, then caps it against the pair's live token balance: [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

`cappedReserveToken = reserveToken - tokensOut` only guards the `== 0` case; it does **not** guard the case where `tokensOut` (set to `realBalance`) exceeds `reserveToken`, which underflows and panics.

This preconditon violation is not hypothetical: the codebase's own regression tests prove `realBalance > reserveToken` is directly reachable by an unprivileged wallet via a plain ERC20 `transfer` of the launched token into its own `Pair` (no `mint`/`sync`, just a donation): [2](#0-1) 

That test file's own comment states the historical bug plainly: *"A TOKEN donation that drives `realBalance > reserveToken` previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg, cascading into a `Zap.buy` DoS. Guard added; tests pin the fix."* The fix that was applied lives only in `Bonding.previewLtUntilGraduation`: [3](#0-2) 

```
// Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
if (realBalance >= reserveToken) return ltUntilThreshold;

uint256 cappedReserveToken = reserveToken - realBalance;
```

The identical subtraction pattern in `Router._computeBuy` (`reserveToken - tokensOut` where `tokensOut == realBalance`) was **not** given the equivalent `>=` guard — only the degenerate `== 0` outcome is checked. Once the donation attack (already proven reachable, see `test_donation_realBalanceExceedsReserveToken`) inflates `realBalance` above `reserveToken`, any buy whose uncapped `tokensOut` computation exceeds the inflated `realBalance` triggers the cap branch and underflows `cappedReserveToken`, reverting with an unhandled arithmetic panic instead of `OverflowCapDegenerate()` or a graceful cap.

### Impact Explanation
Any buyer attempting to route through the overflow-cap branch after the donation (e.g. a large buy sized to approach curve exhaustion, or the exact size needed to trigger graduation via the supply/overflow path documented in `docs/contracts-scope.md`'s "Overflow buy protection") reverts unexpectedly. This breaks `Zap.buy`/`Bonding.buy`'s overflow-buy-cap invariant (documented and tested elsewhere as invariant #6, "Overflow refund") for any token whose pair has received a donation, denying legitimate traders access to the capped-buy/graduation-triggering path and effectively freezing that specific trade flow until the token graduates and `_prepareGraduationLiquidity` burns the donated tokens. This matches the "permanent freezing of trader funds / broken invariant" bar via CWE-404/CWE-476-class denial of service.

### Likelihood Explanation
Medium-to-high. The precondition (`realBalance > reserveToken`) is a proven, cheap, unprivileged donation (`IERC20.transfer(pair, amount)` of the launched Token — no role, no approval needed) and is already exercised by the project's own test harness (`_stageDonationAttack`). No additional privilege beyond being able to hold/acquire some of the launched token (obtainable via a normal buy) and re-transfer it to the pair is required.

### Recommendation
Mirror the `Bonding.previewLtUntilGraduation` guard inside `Router._computeBuy`: before computing `cappedReserveToken = reserveToken - tokensOut`, check `if (tokensOut >= reserveToken) revert OverflowCapDegenerate();` (or equivalent saturating logic) so a donation-inflated `realBalance` degrades gracefully instead of panicking. Add a fuzz/unit test analogous to `test_donation_realBalanceExceedsReserveToken` that stages the donation and then executes a buy sized to hit the overflow-cap branch, asserting it reverts with the intended custom error (or succeeds gracefully) rather than an unchecked arithmetic panic.

### Proof of Concept
1. Launch a token via `Zap.createToken` (any unprivileged wallet).
2. Execute `_stageDonationAttack`-style sequence: buy enough tokens off the curve to receive > 250M tokens, then `Token.transfer(pair, donatedTokens)` directly to the `Pair` — this is proven in `test_donation_realBalanceExceedsReserveToken` to leave `IPair(pair).tokenBalance() > reserveToken`.
3. Submit a further buy via `Zap.buy`/`Bonding.buy` sized so that `Router._computeBuy`'s uncapped `tokensOut` computation exceeds the now-inflated `realBalance`, forcing entry into the `if (tokensOut > realBalance)` branch.
4. `cappedReserveToken = reserveToken - tokensOut` underflows (`tokensOut == realBalance > reserveToken`), causing an unhandled Solidity panic revert instead of the intended `OverflowCapDegenerate()` guard or a graceful cap — denying the buyer's transaction.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
