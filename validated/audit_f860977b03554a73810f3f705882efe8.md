### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC is computed only over the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values come from HTTP headers that are never included in the signed content, yet `shop` is passed straight through into `WebhookMetadata` and handed to the app's `WebhookHandler#handle` as the authoritative tenant identifier.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` uses this same body-only check to accept the request, then trusts `request.shop` (an unauthenticated header) as the tenant identity forwarded to the handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed by the host app's handler to decide which merchant/session the event belongs to: [5](#0-4) 

The identity binding broken is: `hmac == HMAC(secret, body)` is verified, but the trusted tenant value is `request.shop (header)`, not any value bound into the signed bytes. So `HMAC-verified bytes == body` while `attributed tenant == header`, an inequality that lets an attacker who possesses one valid `(body, hmac)` pair swap the `shop-domain` header to any other shop domain string and still pass verification, because the signature check never inspects the header.

### Impact Explanation
This breaks the "bytes verified vs. bytes parsed" identity binding: the field acted upon (`shop`, used to route/attribute the event to a merchant) is not covered by the HMAC that is supposed to authenticate the webhook. If an app architecture relies on `WebhookMetadata.shop` from this gem to determine which tenant's data/session to touch (a documented, expected usage pattern shown in `docs/usage/webhooks.md` and exercised in `test/webhooks/registry_test.rb`), a request with a re-used/valid body+hmac pair but a forged `shop-domain` header will pass `checksWithdraw`-equivalent validation in this gem (`Registry.process` / `HmacValidator.validate`) and be delivered to the handler labeled as coming from a different shop. This is a cross-tenant attribution issue rooted in this gem's own webhook verification code, not merely "the host app ignoring documented behavior" — the gem's own `to_signable_string` implementation excludes the very field it later treats as trusted output.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one legitimately-signed `(body, hmac)` pair (e.g., their own shop's webhook delivery, which any merchant installing the app can obtain), then replay it to the app's webhook endpoint with a modified `shopify-shop-domain` / `x-shopify-shop-domain` header. No `api_secret_key` or access token is needed to mount the header swap itself — only knowledge of a previously delivered valid body/HMAC pair, which is realistic for any unprivileged merchant who installed the app. This is a plausible but not certain High-impact issue since actual exploitability depends on how strongly the host app relies on `WebhookMetadata.shop` versus independently verifying shop identity via other means (e.g., an active session lookup) — this gem does not enforce or hint at that dependency.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body, before trusting them in `WebhookMetadata`. At minimum, document/enforce that `WebhookMetadata.shop` must be cross-checked against an independently established session/tenant before being used for any state-changing or data-returning operation, and consider validating that the delivered `shop` matches the shop associated with the registered webhook subscription.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and its valid `x-shopify-hmac-sha256` header `H = HMAC(secret, B)`.
2. Attacker resends `B` and `H` to the app's webhook endpoint but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unmodified: [6](#0-5) 
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, so the app processes the event as if it originated from `victim-shop.myshopify.com` even though nothing about the header was verified: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
