### Title
`handle_unsigned` executes ISMP message batches for free and validates them twice, allowing unbounded resource-consumption DOS - (File: modules/pallets/ismp/src/lib.rs)

### Summary
The reported op-geth bug is a "Node Resource Consumption DOS": tracking/processing overhead (redundant hashing, extra storage writes) is incurred by every node processing a transaction, but the gas/fee model does not force the attacker to pay for that overhead, so a bounded fee lets an attacker impose unbounded processing time on validators/sequencers. Hyperbridge's `pallet-ismp` has a structurally identical gap: its `handle_unsigned` extrinsic is explicitly fee-less ("permits anyone execute ISMP messages for free") and executes an attacker-supplied `Vec<Message>` batch through full consensus/state-proof verification twice per submission — once during `validate_unsigned` (which every node in the network runs for every transaction that enters the pool) and again during actual dispatch — with no compile-time bound on batch size or proof complexity.

### Finding Description
`Pallet::handle_unsigned` is declared as callable via `ensure_none(origin)` — i.e. unsigned, no fee payer, no deposit: [1](#0-0) 

Its `ValidateUnsigned::validate_unsigned` implementation runs `Self::execute(messages.clone())` — the *same* full proof-verification/dispatch pipeline used by the real extrinsic — purely to compute transaction-pool priority/tags: [2](#0-1) 

Then, if the transaction is included, `handle_unsigned` calls `Self::execute(messages.clone())` again: [3](#0-2) 

`execute()` iterates the entire submitted `Vec<Message>`, invoking `handle_incoming_message` per message, which performs consensus-client checks, Merkle/MMR multi-proof verification, and (for state-machine messages) child-trie / patricia-trie walks over attacker-chosen key sets and proof node lists — all before any fee is charged: [4](#0-3) 

Because `validate_unsigned` is invoked by every node during gossip/pool validation (not just the block author), this doubles (at minimum) the CPU cost per submitted batch, and because the call is unsigned and free, there is no economic gate on submitting arbitrarily large `messages` vectors or arbitrarily large/pathological proofs (long trie proof node lists, huge child-trie key sets, or many `RequestMessage`/`ResponseMessage` entries each carrying its own Merkle multi-proof, as seen in `modules/ismp/core/src/handlers/request.rs` and `response.rs`) to force expensive proof verification on every full/validating node in the network. `#[pallet::weight(weight())]` assigns a `Weight` to the extrinsic for block-inclusion accounting, but this only bounds the weight *charged inside a block* — it does not prevent the same unbounded computation from being triggered for free, repeatedly, during `validate_unsigned` in the transaction pool (which runs even for batches that will ultimately be rejected/never included), nor does it cap the number of messages or bytes an attacker can pack into one submission before weight is known.

This is a direct analog of the op-geth report's core claim: uncosted/under-costed per-call work (there: gas-tracker hashing and state writes; here: proof verification and trie traversal triggered by a free, doubly-validated unsigned call) lets an attacker trade a cheap, repeatable submission for outsized validator/node processing time, threatening block-time budgets — exactly the "resource consumption" DOS class the report flags, and it is reachable by any unprivileged party submitting a single unsigned extrinsic (a relayed proof/message batch), matching the required reachable-path list (pallet-ismp `handle_unsigned`).

### Impact Explanation
An attacker can gossip large, and even ultimately-invalid, `handle_unsigned` batches (large `Vec<Message>`, each carrying oversized proofs/trie node lists) at zero cost. Every node in the network that receives the transaction runs `validate_unsigned` → `execute()` → full proof verification before the transaction is even included in a block, and the block producer that does include it pays the cost again. Because delivery is free and unsigned, this can be repeated continuously, degrading node responsiveness/block production capacity network-wide — a liveness/DOS risk to the relayer/consensus-update path that underlies all cross-chain message delivery. This matches "High Risk" severity classification analogous to the source report (resource-consumption DOS on the sequencer/validator, not fund loss directly, but capable of halting/degrading message delivery for the whole bridge).

### Likelihood Explanation
Likelihood is high: the call is intentionally permissionless and free by design (comment: "This allows users execute ISMP datagrams for free. Use with caution."), requires no signature, no deposit, and no special privilege — any relayer-capable actor can submit it, and the double-execution (validate + dispatch) plus lack of an explicit cap on batch size/proof size makes the attack straightforward to construct using pathologically large but syntactically valid `Message` batches.

### Recommendation
- Bound the number of messages and/or total proof-node/key count accepted per `handle_unsigned` call (a `MaxMessages`/`MaxProofSize`-style constant enforced before any expensive verification work runs).
- Avoid running the full `execute()` verification pipeline inside `validate_unsigned`; perform only cheap, bounded pre-checks (format/size limits, and where feasible, signature/consensus-freshness checks) there, deferring expensive multi-proof/trie verification to actual dispatch.
- Consider a lightweight anti-spam gate for unsigned submissions that are ultimately proven invalid (e.g., rate limiting per proof/consensus height, or requiring a bond that is only refunded on valid submissions) so invalid batches cannot be replayed cheaply to keep re-triggering expensive validation.
- Audit `handle_incoming_message` and trie/MMR verification code paths for computational complexity relative to attacker-controlled proof size, ensuring costs are pre-charged via weight *before* expensive traversal begins rather than only being reflected in post-hoc weight accounting.

### Proof of Concept
1. Construct a `Vec<Message>` containing many `RequestMessage`/`GetResponseMessage`/`ConsensusMessage` entries, each with maximally sized (but syntactically valid) Merkle multi-proofs / trie storage proofs (large `storage_proof: Vec<Vec<u8>>` and large key sets), per `modules/ismp/core/src/handlers/request.rs` (`RequestMessage`) and `modules/ismp/state-machines/substrate/src/lib.rs` (`StateMachineProof`).
2. Submit this batch as `Call::handle_unsigned { messages }` via `ensure_none` origin (unsigned, no fee) to the network.
3. Every full node validates the transaction via `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())` — running full consensus-client and trie/MMR proof verification over the entire attacker-supplied batch — before the transaction is even accepted into a block: `modules/pallets/ismp/src/lib.rs:604-626`.
4. If included, `handle_unsigned` invoke `Self::execute` a second time: `modules/pallets/ismp/src/lib.rs:373-382`.
5. Repeat cheaply (cost is only network bandwidth to gossip the extrinsic, since it is free and unsigned) to sustain elevated CPU load across the network's validating/sequencing nodes, analogous to the nested-contract-call resource-exhaustion scenario described in the source op-geth report.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;
