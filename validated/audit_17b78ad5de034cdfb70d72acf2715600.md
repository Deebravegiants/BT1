Confirmed: `WebhookMetadata.shop` is a plain `String` field populated directly from `request.shop` (the unauthenticated `x-shopify-shop-domain` header), and every app's `WebhookHandler#handle` implementation relies on this field to determine which tenant the event belongs to.

### Title
Webhook `shop` identity is taken from an unauthenticated header and is not bound by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` attribute that is handed to application webhook handlers is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. Any actor able to obtain one valid `(raw_body, hmac)` pair for the shared app secret (e.g., a merchant who has the app installed and thus legitimately receives HMAC-signed webhooks for their own shop) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still succeed because it only checks the body, but `Registry.process` will dispatch the payload to the app's handler tagged with the attacker-chosen shop, breaking the tenant identity binding.

### Finding Description
The identity binding that should hold is:

`shop authenticated by the signature == shop the handler acts on`

But in this gem:

- `ShopifyAPI::Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [1](#0-0) .
- For webhooks, `to_signable_string` is defined as just the raw body, excluding all headers [2](#0-1) .
- The `shop` value used downstream, however, is pulled from the `x-shopify-shop-domain` header, a value that is entirely outside the HMAC-covered content [3](#0-2) .
- `Registry.process` validates only the body's HMAC and then immediately trusts `request.shop` (the header) to build the `WebhookMetadata` passed to the app's handler [4](#0-3) .
- `WebhookMetadata#shop` is a plain, unauthenticated `String` field that the app handler is expected to use to identify which tenant/store the event pertains to [5](#0-4) .

Because the app's `client_secret`/`api_secret_key` is the same for every shop that installs a given app (it is a per-app secret, not per-shop), any tenant that legitimately receives a webhook (for example a mandatory `customers/redact`, `shop/redact`, or `customers/data_request` payload, or any ordinary topic they've subscribed to) possesses a body+HMAC pair that is valid against the shared secret. Nothing in `to_signable_string` or in `HmacValidator` binds that HMAC to the specific shop that originated the event. Replaying the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but with a modified `X-Shopify-Shop-Domain` header pointed at a victim shop, passes `HmacValidator.validate` unchanged and causes `Registry.process` to invoke the handler with `WebhookMetadata.shop` set to the victim's domain [4](#0-3) .

This is the exact bug class from the report: a field that business logic acts on (`shop`, used for tenant dispatch) is not covered by the MAC that is supposed to prove authenticity of the whole message, so the linear/implicit assumption ("if the HMAC validates, every field on the request — including `shop` — can be trusted") does not hold.

### Impact Explanation
Any handler implementation that uses `data.shop` from `WebhookMetadata` to decide which merchant's records to create/update/delete (which is the documented and expected usage pattern for this field) can be made to act on a victim shop's identity using a payload/signature pair the attacker legitimately obtained for a different shop. This crosses the tenant boundary the app is supposed to enforce (Critical — cross-tenant access) purely through this gem's own webhook verification logic, without needing the app's `api_secret_key`, an access token, or any privileged account.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop (or otherwise being a valid recipient of a webhook from the app), (2) capturing one raw webhook body and its `X-Shopify-Hmac-Sha256` value sent to the app's endpoint, and (3) resending it to the same endpoint with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. No cryptographic secret needs to be recovered because the header is simply not part of what's being verified.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the authenticated body before constructing `WebhookMetadata`. At minimum, `Registry.process` should refuse to trust `request.shop` unless it can be correlated with data inside the verified body, or the gem should document/require that consuming apps cross-check `data.shop` against an out-of-band expected value (e.g., the session store) rather than treating it as authenticated on its own.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shared_app_secret", # same secret for every installed shop
  host: "example.com",
  scope: [],
  is_embedded: false,
  api_version: "2024-01",
  is_private: false,
)

# 1. Attacker's own shop legitimately triggers/receives a real webhook,
#    e.g. a "customers/redact" mandatory webhook, with a body they can
#    fully predict/control the shape of.
raw_body = '{"customer":{"id":123},"orders_to_redact":[]}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_app_secret", raw_body)

# 2. Attacker replays the exact same body + hmac to the app's webhook
#    endpoint, but swaps the shop-domain header to the victim's shop.
forged_headers = {
  "x-shopify-topic" => "customers/redact",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation succeeds because it only checks raw_body, not shop.
ShopifyAPI::Utils::HmacValidator.validate(request) #=> true

# 4. Registry.process dispatches to the handler tagged with the victim's shop.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the event body/signature actually originated from the attacker's own shop.
```
