### Title
Attached NEAR deposit is permanently swallowed by `WalletContract::rlp_execute` on malformed/invalid Ethereum-transaction input instead of being refunded - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is a `#[payable]` entry point that accepts a relayer-supplied, base64/RLP-encoded Ethereum-style transaction and an attached NEAR deposit, then decodes it into a NEAR `Action` via `inner_rlp_execute` → `internal::parse_rlp_tx_to_action`. When the decoded/ABI-encoded transaction data is malformed in a way classified as `Error::User(...)` (e.g. `InvalidAbiEncodedData`, `UnknownFunctionSelector`, `UnsupportedAction`, `UnknownPublicKeyKind`, `InvalidEd25519Key/InvalidSecp256k1Key`, `InvalidAccessKeyAccountId`, `ExcessYoctoNear`), the function does not panic and does not create any refund promise for the caller's `attached_deposit`. It simply returns `PromiseOrValue::Value(e.into())`, i.e. a *successful* NEAR function call outcome with an `ExecuteResponse{success:false,...}` body. Because the call succeeds at the protocol level, NEAR's automatic deposit-refund mechanism (which only triggers when a receipt *fails*) never fires, and the deposit that was already credited to the wallet-contract's account balance is retained by the contract forever, with no code path to return or claim it.

### Finding Description
`rlp_execute` is invoked with `#[payable]`, meaning `env::attached_deposit()` is credited to the wallet-contract account balance as soon as the `FunctionCall` action executes, per protocol. [1](#0-0) 

The core decode/dispatch logic lives in `inner_rlp_execute`. Two categories of pre-existing error handling exist:
- `Error::User(_)`: nonce is incremented (to block replay) and the error is returned directly — **no refund promise is created**.
- `Error::Relayer(_)` / `Error::AccountId(_)`: also returned directly with no refund. [2](#0-1) 

Back in `rlp_execute`, any `Err(e)` (other than the ban-relayer special case) is converted straight into a value response:
```rust
Err(e) => PromiseOrValue::Value(e.into()),
``` [3](#0-2) 

`From<Error> for ExecuteResponse` explicitly documents that this method is designed to never panic so that state changes (e.g. nonce increment / relayer ban) persist even on error: [4](#0-3) 

By contrast, the contract *does* implement a `CallerDeposit` refund mechanism, but only for the case where a cross-contract promise is created and later fails (`rlp_execute_callback`): [5](#0-4) [6](#0-5) 

This confirms the developers' intent was that a caller who attaches a deposit should get it back whenever their intended action does not execute — this is explicitly tested for the "cross-contract call fails" case: [7](#0-6) 

However, `CallerDeposit` is only constructed and refunded inside the async/promise path (`inner_rlp_execute`'s success branch and `rlp_execute_callback`'s `PromiseResult::Failed` arm). For the synchronous parse-error paths (`Err(Error::User(_))`, `Err(Error::Relayer(_))`, `Err(Error::AccountId(_))` returned directly from `rlp_execute`), no `CallerDeposit` is ever created or refunded — the function returns a `Value` (success) response, so the general Near protocol deposit-refund-on-failure rule documented in `docs/RuntimeSpec/Components/BindingsSpec/EconomicsAPI.md` ("If contract execution fails ... `attached_deposit` is refunded back to `predecessor_account_id`") does not apply, because the call did not fail from the protocol's perspective. [8](#0-7) 

This is structurally analogous to the reported `onERC721Received()` bug: a callback/entry point that accepts value (an NFT / a NEAR deposit) together with attacker/relayer-controlled data, where certain malformed data values fall through all recognized branches, the value is retained by the contract, and nothing forces a revert/refund for those specific unhandled cases.

### Impact Explanation
Any external caller (not just a relayer using an access key) who calls `rlp_execute` directly with an attached deposit and a transaction payload that fails to parse into a recognized ABI-encoded action (`UnknownFunctionSelector`, `InvalidAbiEncodedData`, unsupported public-key encoding, unsupported action types, etc.) permanently loses their attached NEAR deposit to the wallet-contract account, with no way to reclaim it — this is an unauthorized/irreversible balance loss for an unprivileged user interacting with an in-scope production contract shipped as part of nearcore's eth-implicit-account infrastructure. Funds accumulate in the wallet-contract account instead of being returned, which is a direct token/asset loss for the depositor.

### Likelihood Explanation
Triggering this requires only a single unprivileged call to `rlp_execute` with a `tx_bytes_b64` argument that base64/RLP-decodes into a valid Ethereum transaction shell but whose inner ABI-encoded `data` field is malformed in one of the ways mapped to `Error::User` (or is a `Relayer`/`AccountId` error) — no special privileges, validator status, or race condition are needed. Malformed calldata can easily arise from front-end bugs, hand-crafted requests, or third-party tooling errors (as acknowledged in the code comments: "A careful power-user should never see these errors ... If a user does see these errors then there is likely a bug in the front-end code"), making accidental triggering plausible, and deliberate triggering by any attacker trivial.

### Recommendation
For every `Err` path returned synchronously from `inner_rlp_execute` in `rlp_execute` (i.e., not routed through a cross-contract promise), construct a `CallerDeposit`-equivalent refund transfer of `env::attached_deposit()` back to `env::predecessor_account_id()` before returning `PromiseOrValue::Value(e.into())`, mirroring the refund logic already implemented in `rlp_execute_callback`'s `PromiseResult::Failed` arm. Alternatively, only credit/keep the deposit once an action has actually been dispatched, and issue a `promise_batch_action_transfer` refund whenever `inner_rlp_execute` returns any `Error` variant.

### Proof of Concept
1. Deploy `WalletContract` (or use the existing eth-implicit-account deployment) and fund an externally owned test account with several NEAR.
2. Craft a valid RLP-encoded Ethereum transaction (correct nonce, signature, `to` matching a `target` account) whose `data` field is a 4-byte function selector that does not match any of `FUNCTION_CALL_SELECTOR`, `TRANSFER_SELECTOR`, `ADD_KEY_SELECTOR`, `DELETE_KEY_SELECTOR`, or matches a selector but has an invalid ABI-encoded body — this yields `Error::User(UserError::UnknownFunctionSelector)` or `Error::User(UserError::InvalidAbiEncodedData)` from `internal::parse_rlp_tx_to_action`.
3. Call `rlp_execute(target, tx_bytes_b64)` from an account other than the wallet contract itself, attaching a non-trivial NEAR deposit (e.g. 1 NEAR) — analogous to the existing test harness in `test_caller_refunds` at [9](#0-8) , but using an invalid-selector payload instead of a failing cross-contract call.
4. Observe the transaction succeeds at the protocol level (`ExecuteResponse{success:false, error: Some("Error: unknown function selector")}`), and verify (as the existing test framework does with `view_account().balance`) that the caller's account balance decreased by (approximately) the full attached deposit, while the wallet-contract's account balance increased by the same amount, with no follow-up refund receipt ever generated — unlike the `fake.near` receiver-id scenario in `test_caller_refunds`, which does get refunded because it goes through the promise/`CallerDeposit` path.

Note: I was unable to directly execute this contract or trace `internal::parse_rlp_tx_to_action` and `ethabi_utils` byte-for-byte to enumerate every malformed-input case that maps to `Error::User`/`Error::Relayer` due to tool/time limits; the finding is based on the confirmed absence of any refund logic in the `Err` branches of `rlp_execute`/`inner_rlp_execute`, contrasted with the refund logic that does exist for the promise-failure path. A Devin session with full repository access would be needed to enumerate and test every malformed-input branch exhaustively.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

/// Response given from the `rlp_execute` entry point to the contract.
/// The error information is needed because that method is not meant to panic,
/// therefore success/failure must be communicated via the return value.
/// The reason that method should never panic is to ensure the contract's state
/// can be changed even in error cases. For example, banning a dishonest relayer.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct ExecuteResponse {
    pub success: bool,
    pub success_value: Option<Vec<u8>>,
    pub error: Option<String>,
}

impl From<Error> for ExecuteResponse {
    fn from(value: Error) -> Self {
        Self { success: false, success_value: None, error: Some(format!("{value}")) }
    }
}

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}

# Economics API

Accounts own certain balance; and each transaction and each receipt have certain amount of balance and prepaid gas
attached to them.
During the contract execution, the contract has access to the following `u128` values:

- `account_balance` -- the balance attached to the given account. This includes the `attached_deposit` that was attached
  to the transaction;
- `attached_deposit` -- the balance that was attached to the call that will be immediately deposited before
  the contract execution starts;
- `prepaid_gas` -- the tokens attached to the call that can be used to pay for the gas;
- `used_gas` -- the gas that was already burnt during the contract execution and attached to promises (cannot exceed `prepaid_gas`);

If contract execution fails `prepaid_gas - used_gas` is refunded back to `signer_account_id` and `attached_deposit`
is refunded back to `predecessor_account_id`.
