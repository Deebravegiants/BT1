Confirmed: the webhook `Request#to_signable_string` returns only `@raw_body`, meaning the HMAC computed by `HmacValidator.validate` binds exclusively to the request body — not to the `shop` (i.e. `x-shopify-shop-domain` header). Yet `Registry.process` trusts `request.shop` directly (an unauthenticated header) to attribute the webhook to a tenant.

### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw JSON body via HMAC-SHA256, while the `shop` identity (`x-shopify-shop-domain` / `shopify-shop-domain` header) that is handed to the app's webhook handler as the tenant identifier is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely with `Utils::HmacValidator.validate(request)` and then immediately hands the header-derived `request.shop` value to the handler as the trusted tenant identity: [1](#0-0) 

The HMAC that is verified, however, is computed only over `@raw_body`: [2](#0-1) 

and `shop` is read straight from an HTTP header with no cryptographic binding to the signature at all: [3](#0-2) 

`HmacValidator.validate` confirms the `hmac` field matches `to_signable_string` (the raw body) — it never touches `shop`: [4](#0-3) 

This breaks the intended identity binding `hmac == HMAC(secret, body ∥ shop)`. In reality the binding actually enforced is only `hmac == HMAC(secret, body)`, i.e. `shop` is a field acted on (passed into `WebhookMetadata.new(shop: request.shop, ...)` and used by the app to select tenant data/state) but not covered by the HMAC.

An attacker who can obtain any one HMAC-valid `(body, hmac)` pair signed with the app's `api_secret_key` — for example by installing the app on their own store and receiving a legitimate webhook for that store — can replay that exact body/hmac pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim merchant's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will dispatch the handler with `shop` set to the victim's domain, alongside body content of the attacker's choosing (from their own store's webhook).

### Impact Explanation
This crosses a tenant boundary: it allows an unprivileged attacker (any merchant who can install the target app once) to make the host application process attacker-controlled webhook data under a spoofed victim `shop` identity. Depending on how the host app is built (as documented/intended by this gem — `WebhookMetadata#shop` is the documented tenant key), this enables cross-tenant data confusion/injection — e.g., an attacker triggering `orders/create` or `app/uninstalled` logic that the host app scopes by `shop`, corrupting or exfiltrating another merchant's state. This matches the Critical "cross-tenant access" impact category, since the gem's own webhook-verification primitive is what fails to bind the identity field it delivers to the host app.

### Likelihood Explanation
Likelihood is significant for any developer relying on the gem's built-in webhook verification and metadata as authoritative: an attacker needs only to (1) install the target app on a store they control to receive one legitimately signed webhook, and (2) resend that exact body with an altered `shop` header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required — only the ability to receive a webhook for one's own installation, which is available to any unprivileged internet user who installs the app.

### Recommendation
Include the trusted `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed payload before they are exposed via `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the shop domain (e.g., signable string = header `shop` + raw body, matching what is verified), so `HmacValidator.validate` fails whenever the `shop` header has been tampered with independently of the body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook: Shopify sends `POST /webhooks` with headers `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some JSON body `B`.
2. Attacker captures `(B, valid-hmac)`.
3. Attacker replays `POST /webhooks` to the same app endpoint with body `B` unchanged, `x-shopify-hmac-sha256: valid-hmac` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `valid-hmac` — validation passes: [5](#0-4) 
5. The handler executes with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the host app processes attacker-controlled data attributed to the victim tenant: [6](#0-5)
