## Finding

### Title
Native-token intent outputs sent to a zero-address beneficiary are permanently burned in `_withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (and its sibling `IntentGatewayV2.withdraw` in the Tron variant) releases escrowed/filled order outputs to `body.beneficiary` with no check that the decoded address is non-zero. For native-token (`token == address(0)`) payouts this is done via a raw low-level `call`, which succeeds even when the target is the zero address, silently burning funds instead of reverting.

### Finding Description
`_withdraw` decodes the beneficiary directly from the withdrawal request and dispatches funds to it without validation: [1](#0-0) 

The native-token transfer helper never checks the recipient address: [2](#0-1) 

`beneficiary` is derived purely from a `bytes32` field supplied in the order/withdrawal body (`address(uint160(uint256(body.beneficiary)))`), with no non-zero check anywhere in the call chain: [3](#0-2) 

For ERC20 outputs the OpenZeppelin `ERC20` implementation itself reverts transfers to `address(0)`, which incidentally protects that path. But a native-value call to `address(0)` via `.call{value: amount}("")` succeeds unconditionally (it behaves like sending ETH to any EOA), so no revert occurs and the value is irrecoverably lost. The identical pattern exists in the Tron port of the same contract: [4](#0-3) 

### Impact Explanation
Whenever an order's `output.beneficiary` (or a withdrawal/refund `WithdrawalRequest.beneficiary`) resolves to `address(0)` — whether via a user/integrator mistake, a malformed cross-chain relay of the order data, or corrupted encoding — the solver-provided native-token output that has already been paid into escrow is permanently and irrecoverably destroyed on `_withdraw`/`withdraw` finalization. This is a permanent freezing/loss of funds with no path to recovery, satisfying the "concrete... permanent freezing of funds" bar. It specifically differs from the ERC20 leg of the same function, which is safe only because the token contract itself enforces the check — the protocol logic provides no equivalent guard for native value.

### Likelihood Explanation
The escrow/withdraw path is reachable from a single order placement and normal `fillOrder`/`onGetResponse`/refund flow — no privileged role is required. The only precondition is that `beneficiary` decodes to the zero address, which can happen from a buggy caller, SDK, or off-chain integration constructing the order, or truncation/corruption of the 32-byte beneficiary field. Given native-asset orders are an explicitly supported path (`token == address(0)` is checked directly in `_withdraw`), the class of order that triggers this is fully within normal, unprivileged protocol usage.

### Recommendation
Add an explicit `beneficiary != address(0)` check (revert if zero) at order-placement time in `IntentsBase`/`IntentGatewayV2`, and/or guard it defensively inside `_withdraw`/`withdraw` before dispatching either the native or ERC20 leg, so malformed/zero beneficiaries fail loudly instead of silently burning escrowed funds.

### Proof of Concept
1. Place an order via `IntentGatewayV2.placeOrder` with `order.output.beneficiary = bytes32(0)` and `order.output.assets[0].token = address(0)` (native output), escrowing input tokens normally.
2. A solver fills the order via `fillOrder`, providing native value as the output.
3. `_withdraw` is invoked with `body.beneficiary = bytes32(0)`; `beneficiary` resolves to `address(0)`.
4. `_sendValue(address(0), amount)` executes `address(0).call{value: amount}("")`, which returns `sent = true` (a call with empty calldata and no code at the destination always "succeeds").
5. The native value is now held at `address(0)` — permanently unspendable — while the order is marked filled/finalized, with no error and no way to recover the funds.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
