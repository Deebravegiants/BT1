Confirmed: the webhook HMAC signature in this gem only covers the raw request body, not the `shop-domain` or `topic` headers, and the docs explicitly instruct host apps to trust `data.shop` for tenant-scoped work (queuing jobs, looking up records, etc.).

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `hmac` from the `X-Shopify-Hmac-Sha256` header and exposes `to_signable_string` as **only the raw body**, while `shop` and `topic` are read straight from unauthenticated HTTP headers. `Utils::HmacValidator.validate` recomputes the signature over `to_signable_string` (the body) and compares it to the received `hmac`. Because the signature never covers the `shop-domain` header, `Webhooks::Registry.process` accepts any request whose body/HMAC pair is valid regardless of which shop the `shop-domain` header claims to be, and forwards that unauthenticated `shop` value straight to the app's handler as `WebhookMetadata#shop`.

### Finding Description
- `Request#hmac` reads the signature header, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0)  and [2](#0-1) .
- `shop` and `topic` are pulled directly from headers with no cryptographic binding: [3](#0-2) .
- `HmacValidator.validate_signature` only ever signs `verifiable_query.to_signable_string` (the raw body) with the app's `api_secret_key`: [4](#0-3) .
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` passed to the app's handler: [5](#0-4) .
- The documented usage pattern explicitly tells host apps to key business logic (e.g. background job enqueue, per-shop data writes) off `data.shop`: [6](#0-5) .

Because the app's `api_secret_key` is a single shared secret for the app across **all** installed shops (not shop-specific), any unprivileged internet user who legitimately installs the app on their own shop can obtain a genuine `(raw_body, hmac)` pair for their own tenant (e.g. by triggering a real webhook, or simply computing the HMAC themselves offline since `api_secret_key` is a static app-level secret, not merchant-specific — though in this analysis we only need the attacker to replay a body/HMAC pair they can obtain from Shopify for their own shop). The attacker then POSTs directly to the app's public webhook endpoint with the genuine body and HMAC, but with the `X-Shopify-Shop-Domain` header changed to the victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at that header), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain while the `body` is attacker-controlled content. This breaks the identity binding: **shop authenticated (via HMAC) ≠ shop attributed to the request (`shop-domain` header)**.

### Impact Explanation
This directly enables cross-tenant confusion in the host application: any handler that uses `data.shop` to select which merchant's session/data to act on (exactly as instructed in the gem's own documentation) can be tricked into writing attacker-controlled webhook payload content under a victim shop's identity, or triggering side effects (order/product/fulfillment processing, cache invalidation, job enqueueing) attributed to a shop the attacker doesn't own. This matches the "cross-tenant access" high/critical impact category since the shop-identity binding that gates per-tenant processing is not authenticated.

### Likelihood Explanation
Any internet user who can install the app on a shop they control (a normal, unprivileged flow) can capture a valid webhook body+HMAC for their own tenant, then directly POST to the app's public webhook callback URL (which is, by design, an unauthenticated public HTTP endpoint) with a forged `shop-domain` header. No access token, `client_secret`, or privileged access is required — only network access to the app's public webhook route, which is required functionality for Shopify to deliver webhooks in the first place.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-validated, or otherwise cryptographically/authoritatively confirm the shop identity before trusting `request.shop`:
- Extend `VerifiableQuery#to_signable_string` for webhook `Request` to include the `shop-domain` (and `topic`) header value concatenated with the body, and validate that combined value, OR
- After HMAC validation, cross-check `request.shop` against an authoritative source (e.g., confirm the shop has an active, previously-registered webhook subscription/session for that specific `webhook_id`/topic pair) before dispatching to handlers.
- Document prominently that `data.shop` in `WebhookMetadata` is not covered by the HMAC today, so host apps are not misled into treating it as verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker sends a raw HTTP POST directly to the app's public webhook route (e.g. `/callback/orders/create`) with:
   - `raw_body` = the captured body (or any body producing whatever payload the attacker wants, since only the HMAC of the body must match, and the attacker fully controls the body of their own shop's webhook)
   - `X-Shopify-Hmac-Sha256` = the captured/matching HMAC for that body
   - `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic` = `orders/create`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates `raw_body` against the HMAC — see [7](#0-6) .
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and processes it as if Shopify itself confirmed this data belongs to `victim-shop.myshopify.com`.
