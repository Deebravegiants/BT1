### Title
Duplicate `address(0)` legs in `Hinkal.transact` let a single `msg.value` back multiple UTXO-minting balance equations - (File: contracts/Hinkal.sol)

### Summary
The framing proposed in the question (`address(0)` + WETH with a mid-call unwrap) does **not** break the accounting: unwrapping WETH to ETH mid-transaction correctly shows up as a WETH balance decrease and an ETH balance increase, and both legs' `balanceDif` equations remain individually true, so no double count occurs there. However, the *actual* mechanism the question is describing — the same `msg.value` backing two separate accounting terms — is achievable through a different, simpler vector: `circomData.erc20TokenAddresses` is never checked for duplicates, and the `address(0)` branch of the balance-diff formula in `Hinkal.transact` re-adds the *entire* `msg.value` for every array slot equal to `address(0)`, not just once.

### Finding Description
The broken equality is:
`Σ over i where erc20TokenAddresses[i]==address(0) of (creditedETH_i) == msg.value` (exactly one occurrence should consume the ETH actually deposited).

In `Hinkal.transact`, `oldBalances`/`newBalances` are captured via `getBalancesForArray(circomData.erc20TokenAddresses)` [1](#0-0) , and for every index `i` where the token is `address(0)`, the balance-diff formula compensates for `msg.value` already being included in the contract's balance at the time of the snapshot: [2](#0-1) 

If `erc20TokenAddresses` contains `address(0)` at two indices `i` and `i'` (nothing in `dimensionsCheck` or `performHinkalChecks` rejects duplicate token addresses — see `contracts/HinkalHelper.sol:64-171`), then `oldBalances[i] == oldBalances[i']` and `newBalances[i] == newBalances[i']` (same underlying contract ETH balance), so `balanceDif` is computed as `0 + msg.value` **independently for both slots**. Each slot's `balanceDif` is then checked against `amountChanges[i] + utxoAmount` separately, so the attacker can set `amountChanges[i] = amountChanges[i'] = msg.value` and satisfy both equalities with only one real ETH transfer.

On the input side, `_internalTransact`'s per-slot deposit check also does not prevent this: for a positive `deltaAmountChange`, it calls `transferERC20TokenFromOrCheckETH`, which for `address(0)` only asserts `msg.value == _value` [3](#0-2)  — a stateless, non-cumulative check performed independently per slot, so it passes for both duplicate slots using the same `msg.value`.

Nothing else blocks this: the circuit only enforces per-slot conservation (`inTotal[i] + amountChanges[i] === outTotal[i]`) using the attacker's own nullifiers/commitments for that slot; it has no notion that slot `i` and slot `i'` refer to the same physical token, and `getHashedCalldata`/`formInputForCircom` encode `erc20TokenAddresses` verbatim without deduplication [4](#0-3) . Since the attacker is depositing into UTXOs they own, they can freely generate a valid proof for two independent virtual deposits of `msg.value` each.

### Impact Explanation
An attacker can send `X` ETH once and mint two (or more, bounded only by whichever verifier circuit dimension is registered) independent shielded ETH UTXOs, each valued at `X`, from a single physical ETH transfer of `X`. This mints unbacked shielded ETH and creates protocol insolvency the moment the attacker withdraws the extra UTXO — matching Critical severity ("minting shielded value without backing"). The attack is fully repeatable by any unprivileged EOA for every transaction, limited only by gas and the availability of a deployed verifier for a `tokenNumber ≥ 2` dimension with two `address(0)` slots.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (1) a proof for a circuit dimension where `tokenNumber ≥ 2`, (2) `erc20TokenAddresses` with `address(0)` repeated at two indices, (3) `amountChanges` at both indices equal to `msg.value`, and self-generated UTXO commitments/nullifiers for their own new leaves (fully within an unprivileged attacker's capability per the rules). No relay, admin, or victim funds are required. This is directly reachable through the public `Hinkal.transact` entrypoint and does not depend on `HinkalWrapper.prooflessDeposit` (which has its own separate, correctly-implemented `balanceBefore -= msg.value` / `balanceAfter - balanceBefore == amount` check per unique token and is not vulnerable to this issue) [5](#0-4) .

### Recommendation
- Reject duplicate entries in `circomData.erc20TokenAddresses` in `dimensionsCheck`/`performHinkalChecks` (e.g., require strictly ascending token addresses or an explicit uniqueness check).
- Alternatively, compute the `address(0)` `msg.value` compensation exactly once for the whole transaction rather than per-slot (e.g., track a `bool ethAccountedFor` flag and only add `msg.value` on the first `address(0)` occurrence, or precompute `oldBalances`/`newBalances` per unique token and map slots to unique-token indices).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with a verifier registered for `tokenNumber = 2, nullifierAmount = 0 (deposit), outputAmount = 1` (or whatever minimal dimension supports two output UTXOs and zero input nullifiers), and any generated proof toolchain (attacker generates their own proof for their own new UTXOs).
2. Craft `circomData.erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, and `outCommitments`/nullifiers such that slot 0 and slot 1 each produce one out-UTXO of value `X` for `address(0)`, matching the circuit constraint `inTotal[i] + amountChanges[i] === outTotal[i]` independently for each slot.
3. Call `Hinkal.transact{value: X}(...)`.
4. Assert: `address(this).balance` (Hinkal contract) increased by exactly `X` (`newBalances[i] - oldBalances_true == X` once), while the sum of newly created shielded UTXO amounts for `address(0)` equals `2 * X`.
5. Assert this passes the existing `require(balanceDif == amountChanges[i] + utxoAmount, ...)` checks at both `i=0` and `i=1` despite only one real ETH transfer, demonstrating `mintedShieldedETH (2X) > realETHReceived (X)`.
