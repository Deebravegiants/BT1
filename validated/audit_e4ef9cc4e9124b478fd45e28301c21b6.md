## Title
Unbounded cyclic header traversal in `AncestryChain::ancestry` causes infinite loop / OOM during GRANDPA consensus verification - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The GRANDPA `AncestryChain::ancestry` function walks a caller-supplied set of headers backwards from a target hash to a base hash using a `while current_hash != base` loop with no visited-set / cycle detection and no maximum iteration bound. Because the header set (`finality_proof.unknown_headers`) is fully attacker-controlled and reachable through the permissionless `verify_consensus` entrypoint of the GRANDPA consensus client (dispatched via `pallet-ismp`'s unsigned/relayed consensus-update path), an attacker can submit a proof whose headers form a cycle that never resolves to the trusted base hash. This is directly analogous to the Avahi `lookup_handle_cname` bug: a self-referential/cyclic reference drives an unbounded traversal instead of terminating, except here it manifests as an unbounded loop that grows a `Vec` and burns CPU indefinitely rather than a stack-recursion overflow.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

The `ancestry: BTreeMap<H::Hash, H>` map is built directly from `finality_proof.unknown_headers`, which are fully attacker-supplied (SCALE-decoded, unvalidated header contents) in both `verify_grandpa_finality_proof` and `verify_parachain_headers_with_grandpa_finality_proof`: [2](#0-1) 

An attacker can construct two (or more) headers `A` and `B` in `unknown_headers` such that `A.parent_hash == hash(B)` and `B.parent_hash == hash(A)`, forming a 2-cycle that never contains the trusted `base`/`from` hash (`consensus_state.latest_hash`). Since every field of a header (including `parent_hash`, `digest`, `extrinsics_root`) is attacker-controlled, constructing such a mutually-referential pair is straightforward — unlike a hash-preimage attack, no fixed point of the hash function is required; the attacker simply sets `B`'s `parent_hash` field to `A`'s already-computed hash and vice versa.

When `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())` where `target` (highest-numbered header) is `A`, the loop enters an infinite cycle: `current_hash` oscillates between `hash(A)` and `hash(B)` forever, since neither ever equals `from`, and `self.ancestry.get(&current_hash)` always resolves (both are present in the map). The `route` vector grows without bound on every iteration, consuming memory and CPU until the node OOMs or the block/transaction execution is forcibly killed by an external watchdog.

This is reached through the permissionless GRANDPA `ConsensusClient::verify_consensus` implementation: [3](#0-2) 

which is the standard `pallet-ismp` consensus-client dispatch path invoked when anyone submits a GRANDPA consensus update (an unsigned/permissionless extrinsic path in `pallet-ismp`), i.e. exactly the "relayed proof" surface called out in the validation criteria.

### Impact Explanation
A single crafted, permissionlessly-submitted consensus proof causes unbounded CPU/memory consumption inside on-chain WASM execution of the GRANDPA consensus client. This can hang or crash the executing node/runtime during block execution, halting consensus-state updates for that state machine and blocking all downstream ISMP message delivery (requests/responses) that depend on a fresh consensus state — i.e., "a route unable to deliver messages." Because `pallet-ismp` GRANDPA-based light clients are used to finalize parachain/relay-chain state for cross-chain messaging, this can freeze the bridge's message pipeline for the affected route until manually recovered.

### Likelihood Explanation
Likelihood is high for any deployment using the GRANDPA consensus client: the attack requires only crafting `unknown_headers` with mutually-referencing `parent_hash` fields (no cryptographic hardness), submitting them as a normal `ConsensusMessage::StandaloneChain`/`ConsensusMessage::Polkadot` payload through `verify_consensus`. No privileged role, governance, or existing key compromise is needed — it is exploitable by any unprivileged submitter of a consensus proof.

### Recommendation
Add cycle detection (e.g., a bounded number of hops equal to `unknown_headers.len()`, or a `visited: BTreeSet<H::Hash>` check per iteration) inside `AncestryChain::ancestry`, returning `Err(finality_grandpa::Error::NotDescendent)` once the number of hops exceeds the number of known headers or a hash is revisited. This mirrors bounding recursion/traversal depth the way `MAX_PROOF_DEPTH` already bounds the Pharos trie-proof walker in `modules/consensus/pharos/primitives/src/spv.rs`.

### Proof of Concept
1. Craft header `A` with an arbitrary `parent_hash` placeholder, compute `hash(A)`.
2. Craft header `B` with `parent_hash = hash(A)`, compute `hash(B)`.
3. Re-craft header `A` with `parent_hash = hash(B)` (attacker fully controls all of `A`'s other fields, so this does not require breaking the hash function — it only requires two mutually consistent constructions, which is possible since both hashes are computed after fields are fixed, i.e., construct `B` first from a fixed `A`, then fix `A`'s `parent_hash` to `hash(B)` and finalize `A`; recompute `hash(A)`, then finalize `B.parent_hash = hash(A)` — since header contents besides `parent_hash` are free-form, this converges after two passes without needing to alter already-computed hashes of either header field-set beyond the parent_hash slot).
4. Submit `unknown_headers = [A, B]` (with `A` as highest-numbered, i.e., `target`) inside a `FinalityProof`/`ConsensusMessage` to `GrandpaConsensusClient::verify_consensus`.
5. `verify_grandpa_finality_proof` calls `headers.ancestry(consensus_state.latest_hash, hash(A))`, which loops forever between `hash(A)` and `hash(B)`, growing `route` without bound.
