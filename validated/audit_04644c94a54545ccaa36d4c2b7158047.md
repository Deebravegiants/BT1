### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC of the raw request body, then passes header-derived values — most importantly `shop` — into the merchant-facing `WebhookMetadata` struct that app-defined `WebhookHandler` implementations use to decide which tenant's data to act on. The HMAC signature never covers these header fields, so the "identity" (`shop`) that handlers act on is not bound to the signature that authenticates the request.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body` — none of `topic`, `shop`, `api_version`, or `webhook_id` (all read from separate, unsigned headers via `shopify_header`) are included in the signed content: [2](#0-1) 

`Registry.process` validates only this body HMAC and then forwards `request.shop` (and other header values) straight into the handler payload with no further check that the shop matches the signed content: [3](#0-2) 

Because the webhook signing secret is the app's single `api_secret_key`/`client_secret`, shared across every shop that installs the app, a valid HMAC only proves "some webhook genuinely originated from Shopify for some installation of this app" — it does not prove which shop it belongs to. The `shop-domain` header is attacker-controllable data that is authenticated by nothing. The equality that should hold — `shop bound by the signature == shop the handler acts on` — does not hold; instead `shop the handler acts on == unauthenticated header value`.

### Impact Explanation
An attacker who controls one legitimate installation of the app (Shop A) can capture a validly-signed webhook delivery (correct `hmac-sha256` over the body) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop (Shop B). `HmacValidator.validate` will still pass because it only checks the body against the shared secret. `Registry.process` then calls the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the app to attribute Shopify-originated, cryptographically "valid" webhook data to the wrong tenant. Depending on how the host application's handlers use `data.shop` (e.g., `MANDATORY_TOPICS` like `shop/redact`, `customers/redact`, `customers/data_request`, or `app/uninstalled`-style handlers that revoke tokens, delete data, or update per-shop state), this enables cross-tenant data corruption or unauthorized state changes keyed off a spoofed shop identity — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires the attacker to operate at least one real installation of the target app (a fairly low bar — installing a public/free app on a development store is trivial) and to capture one genuine, validly-signed webhook delivery for a topic whose body content is attacker-influenceable or generic enough to be replayed against another shop. The library itself provides no mechanism to bind the `shop` header to the signature, so every app built on this gem's webhook processing inherits this gap; the likelihood of exploitation depends on how much a given handler trusts `data.shop`, but the underlying gap in the gem is present unconditionally.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header values in the signable content verified by `HmacValidator`, or independently verify that the `shop` on the webhook belongs to a session/installation the app already trusts before acting on it. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted for authorization decisions without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; attacker controls this shop and triggers a webhook (e.g. `orders/create`) so Shopify delivers it to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of raw body, using the app's api_secret_key>`
   - `x-shopify-shop-domain: shop-a.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker captures the raw body and the valid `x-shopify-hmac-sha256` value.
3. Attacker resends the exact same body/HMAC to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `to_signable_string` (`@raw_body`), which is unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, so the handler executes tenant-scoped logic under the attacker-chosen shop identity despite the HMAC never having verified that identity.
