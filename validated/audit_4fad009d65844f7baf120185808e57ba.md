### Title
Front-running manual staking-pool deployment's `new` (init) call allows attacker to seize pool ownership - (File: staking-pool/src/lib.rs, staking-pool/README.md)

### Summary
The staking pool contract's `new` constructor has no access control beyond the one-time `state_exists` guard, and the documented manual deployment procedure performs account creation, code deployment, and initialization as three independent transactions rather than one atomic batch. [2](#0-1) 

### Finding Description
The `new` function of the staking pool contract sets `owner_id`, `stake_public_key`, and `reward_fee_fraction` and is guarded only by the near-sdk `#[init]` macro's implicit `!env::state_exists()` check (i.e., it can be called by anyone, exactly once, as long as no state exists yet). The documented usage flow explicitly separates deployment from initialization into three distinct transactions: `near create_account`, `near deploy`, and `near call my_validator new ...` [1](#0-0) . Because the contract code (including the public, permissionless `new` method) is live on-chain immediately after the `deploy` step, and before the intended owner's `new` transaction is confirmed, any unprivileged party who observes the pending deployment (e.g., via mempool/pending-transaction monitoring, similar to the described MEV/front-run vector) can submit their own `new` call with `owner_id` set to themselves. Since `state_exists()` becomes true after the first successful call, the legitimate owner's subsequent `new` transaction will then simply fail/panic on the guard, permanently locking the attacker in as the pool owner. This mirrors the root cause of the reported Uniswap V3 issue: a state-setting initializer with no caller restriction, invoked in a transaction window separate from contract creation/deployment, letting an unprivileged actor front-run the intended initializer and seize control of a fresh, empty contract.

This differs materially from the factory-based contract creation paths (`staking-pool-factory`, `lockup-factory`), which bundle `create_account`, `transfer`, `deploy_contract`, and `function_call("new", ...)` into a single atomic Promise chain within one receipt [3](#0-2) [4](#0-3) , which structurally prevents any front-run window — no separate mempool transaction can be interleaved between deployment and initialization there.

### Impact Explanation
If an attacker wins the race to call `new` on a newly deployed but not-yet-initialized staking-pool account, they become the permanent `owner_id` of that pool. Since the staking pool contract is meant to hold delegator funds and pooled NEAR, ownership grants control over the reward fee, the staking key, pause/resume staking, and governance voting on behalf of the pool. Any legitimate depositors who later delegate funds to what they believe is `owner`'s validated pool would in fact be delegating to an attacker-controlled pool, matching the Allowed Impact Scope categories for unauthorized state-transition/ownership bypass and potential loss of delegator funds through an owner-controlled reward fee or malicious staking key.

### Likelihood Explanation
Likelihood depends entirely on operators following the documented manual `create_account` → `deploy` → `call new` sequence instead of a single atomic multi-action transaction. Since this exact three-step sequence is the one explicitly documented in `staking-pool/README.md`, it represents a real, sanctioned operational path, not a hypothetical misuse. However, exploitation requires (1) real-time mempool/transaction observation to detect the `deploy` step before the follow-up `new` call lands, and (2) the attacker's transaction being included with priority ahead of the legitimate `new` call, which is feasible but requires active monitoring and is not always guaranteed on NEAR's transaction-inclusion model.

### Recommendation
- Update `staking-pool/README.md` to instruct operators to combine `create_account`, `deploy`, and `call new` into a single batched/atomic transaction (as already done programmatically in `staking-pool-factory`), removing the multi-transaction window entirely.
- Alternatively/additionally, add an explicit access check in `new` restricting the caller to `env::predecessor_account_id() == env::current_account_id()` (i.e., only the contract's own account, via a full-access key, can initialize it), closing off any third-party call regardless of deployment sequencing.
- Apply the same review to any other documented manual deployment flows (e.g., `lockup/README.md` "Initialization" section) to ensure account creation/deployment and constructor calls are always atomic.

### Proof of Concept
1. Owner runs `near create_account my_validator --masterAccount=owner` and `near deploy --accountId=my_validator --wasmFile=res/staking_pool.wasm`, exactly as documented [5](#0-4) .
2. Before the owner's subsequent `near call my_validator new '{"owner_id": "owner", ...}'` transaction is included, an attacker observes the deployed-but-uninitialized `my_validator` account (state doesn't exist yet) and submits their own `near call my_validator new '{"owner_id": "attacker", ...}'`.
3. Because `#[init]` only checks `!env::state_exists()` [6](#0-5) , the attacker's transaction succeeds first, setting `owner_id = attacker`.
4. The legitimate owner's `new` call then reverts, because state now exists, leaving the pool permanently owned by the attacker.
