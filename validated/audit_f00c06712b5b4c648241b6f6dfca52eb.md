### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then forwards the `shop-domain` header — which is *not* part of the signed data — directly to the app's handler as the identity of the shop the payload belongs to. Because a single `api_secret_key` is shared across every shop that installs the app, any shop that has received one legitimate webhook (i.e., any merchant who has installed the app) can replay that same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header of a different, victim shop. The HMAC check still passes because it only verifies the body, so the handler processes the attacker's data under the victim's identity.

### Finding Description
The identity binding that should hold is:
`shop that cryptographically authorizes the payload == shop delivered to the handler`

Instead, the code creates:
`shop attribute delivered to handler = unauthenticated header value`
`HMAC-verified content = raw_body only`

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from a header with no verification tie to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC of the request (i.e. of `raw_body`), and — on success — immediately builds `WebhookMetadata` using `request.shop`, which was never part of what the HMAC covers: [3](#0-2) 

`HmacValidator.validate` confirms this: it signs/compares only `verifiable_query.to_signable_string`, which for `Request` is the raw body: [4](#0-3) 

Since `api_secret_key` is one value per app (not per shop), any merchant who has installed the app is able to observe a genuine `(raw_body, hmac)` pair from their own store's webhook traffic. That merchant can then POST that same body/HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to another tenant's domain. `Registry.process` will accept it as valid (the body's HMAC still matches) and hand the handler a `WebhookMetadata` claiming the payload is for the victim shop.

### Impact Explanation
This breaks the multi-tenant boundary the gem is expected to enforce for webhook consumers: an app built on top of `ShopifyAPI::Webhooks::Registry` cannot trust `WebhookMetadata#shop` to correctly identify which tenant a webhook actually originated from, since that value is attacker-controllable independent of the cryptographic signature. Any app that keys tenant-scoped side effects (e.g., updating shop-specific inventory/order records, billing, or authorization decisions) off `data.shop` from the webhook handler is exposed to cross-tenant data injection/confusion — one tenant can cause the app to process forged data attributed to a different tenant.

### Likelihood Explanation
Any shop that installs the app is inherently untrusted relative to other tenants of the same app, and needs no special privilege beyond having received one legitimate webhook of their own (a normal, unavoidable occurrence for any installed app). Crafting and sending the replayed request requires no access to `api_secret_key`, no interception of TLS, and no social engineering — only observing one's own webhook traffic and issuing a normal HTTP POST to the app's public webhook endpoint with a different header value.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the value that is HMAC-verified, or otherwise cryptographically tie the claimed shop to the signed payload, before handing it to the consumer's handler. At minimum, document clearly that `WebhookMetadata#shop` is not authenticated by the HMAC and must be cross-checked by the host application against a shop it already trusts/has a session for, rather than treated as verified request provenance.

### Proof of Concept
1. App AppX shares one `api_secret_key` for all installs.
2. Shop A (attacker, a legitimate installer of AppX) receives a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with `api_secret_key`), and `x-shopify-shop-domain: a.myshopify.com`.
3. Attacker POSTs to AppX's webhook endpoint with the same body `B` and same `hmac` header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` — see `lib/shopify_api/webhooks/registry.rb` line 190 and `lib/shopify_api/webhooks/request.rb` lines 35-38.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` and processes it as if it were victim's data — see `lib/shopify_api/webhooks/registry.rb` lines 198-199.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
