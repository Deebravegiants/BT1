### Title
Webhook shop-domain spoofing via unauthenticated header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity solely by checking the HMAC of the raw request body, but the `shop` field that is handed to application webhook handlers is read from the `shopify-shop-domain` HTTP header, which is never included in the signed content. An attacker who can obtain any genuinely-signed webhook body (e.g., by triggering webhook delivery on a store they control that uses the same app, since the HMAC secret is the app's single, shared `client_secret`) can replay that body with an arbitrary `shopify-shop-domain` header and the signature check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` is decoded from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Registry.process` validates only this body-based HMAC before dispatching to the registered handler with `request.shop` taken straight from the unauthenticated header: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature over `verifiable_query.to_signable_string` (i.e., the raw body) only — it never binds the `shop` header into the signed material: [4](#0-3) 

This breaks the intended identity binding: `signed_shop == shop_acted_on`. In reality, the equality that holds is only `hmac(secret, raw_body) == received_hmac`; the `shop` value delivered to the handler (`request.shop`) is completely independent of what was actually signed. Because the HMAC secret (`api_secret_key`) is shared across every shop installation of a given app, any tenant of the app can generate a validly-signed body (by causing any webhook event on their own store) and then replay that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. The signature still validates, and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` to the host application's handler as though the event genuinely originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the gem asserts a signed webhook is authentic, but the tenant (`shop`) attribute of that "authentic" event is attacker-controlled and never covered by the same authenticity proof. Any host application that keys its side effects (data mutations, uninstall/GDPR processing, entitlement changes, etc.) off `WebhookMetadata#shop` as delivered by this gem can be made to apply attacker-supplied data under a victim shop's identity — a cross-tenant confusion made possible purely by this gem's verification logic.

### Likelihood Explanation
Exploitation requires only that the attacker be able to trigger any webhook delivery for their own shop using the same app installation (a normal, low-privilege action available to any merchant/tenant that installs a public app), then replay the resulting HTTP request to the app's webhook endpoint with a modified `shopify-shop-domain` header. No access token, `client_secret`, or elevated privilege is required — the app's `client_secret`/HMAC key is shared across all shops using the app, and only the header (not the signed payload) determines which shop the event is attributed to.

### Recommendation
Bind the shop identity into the verified signable content, or otherwise cryptographically tie `shop` to the payload before trusting it. Options include:
- Including `topic`, `shop`, and `webhook_id` in the HMAC-covered signable string (this would require a corresponding change in what Shopify signs, so at minimum document/require host apps to independently verify `shop` against known/authorized installations before trusting `WebhookMetadata#shop`).
- At minimum, have `Registry.process` cross-check `request.shop` against a set of shops the app has active sessions/installations for, rejecting webhooks for shops the app is not currently expecting, rather than passing the header value through unchecked.

### Proof of Concept
1. App `App1` is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the same `api_secret_key`.
2. Attacker triggers any webhook event on their own store (e.g. `orders/create`), and Shopify delivers a request to the app's webhook endpoint with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of body>`
   - body: attacker-controlled order JSON
3. Attacker resends the exact same body/HMAC to the app's webhook endpoint but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body's HMAC.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the app's handler with `shop: "victim-shop.myshopify.com"`, `body: <attacker-controlled JSON>`, letting the attacker inject data attributed to the victim tenant.

          received_signature = verifiable_query.hmac
