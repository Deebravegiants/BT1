Confirmed: the `shop` value delivered to the app's webhook handler is read directly from the `x-shopify-shop-domain` HTTP header and is never included in the HMAC-signed payload, which is only the raw body.### Title
Webhook `shop` identity is taken from an unsigned HTTP header, not covered by the HMAC, allowing tenant spoofing in the delivered `WebhookMetadata` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor and an `hmac`/`to_signable_string` pair used by `Utils::HmacValidator.validate` to authenticate incoming webhook requests. The HMAC is computed and verified only over the raw request body, while the `shop` value that later gets bound to `WebhookMetadata#shop` and handed to the app's `WebhookHandler` is read straight from the `x-shopify-shop-domain` header, which is completely outside the signed payload.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Request#shop` is read from the `shop-domain` header via `shopify_header` [2](#0-1) . `HmacValidator.validate` computes the signature exclusively from `to_signable_string`, i.e., from the body bytes, and never incorporates `shop`, `topic`, `api_version`, or `webhook_id` [3](#0-2) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, then constructs `WebhookMetadata` using `request.shop` verbatim and passes it to the registered handler [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field with no additional validation [5](#0-4) .

This breaks the identity binding: `hmac_valid(raw_body) == true` should imply `metadata.shop == the shop that actually produced raw_body`, but the gem only proves `hmac_valid(raw_body) == true` while `metadata.shop` is copied from an attacker-controllable header that carries no cryptographic binding to `raw_body`.

An unprivileged internet user who legitimately operates their own Shopify store receives real webhooks from Shopify with a valid `x-shopify-hmac-sha256` for their own store's payloads. Because the signature only covers the body, that same `(raw_body, hmac)` pair remains valid for any `shop-domain` header value. The attacker can resend the identical body+HMAC pair to the app's webhook endpoint while substituting a victim's `x-shopify-shop-domain` value; `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process`/`WebhookMetadata` will attribute the payload to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem that uses `WebhookMetadata#shop` to key data or trigger store-scoped side effects (a very common pattern, since `shop` is the multi-tenant identifier throughout the gem, e.g. in `Session#shop`) can be made to process attacker-supplied, self-generated webhook content under another merchant's identity, without the attacker ever possessing that merchant's credentials, `client_secret`, or access token. This matches the "cross-tenant access" Critical bucket, since the gem itself performs the shop binding and hands it to the app as trusted, validated metadata.

### Likelihood Explanation
Reachable by any unprivileged internet user who owns (or can install) a Shopify dev/trial store to obtain genuine `(body, hmac)` pairs, then replays them at the target app's public webhook endpoint with a forged `shop-domain` header — no secrets, tokens, or privileged access required. The only prerequisites are knowledge of the target app's webhook URL and normal internet access to it.

### Recommendation
Include `shop`, `topic`, and `api_version`/`webhook_id` in the signable payload (or otherwise cryptographically bind the shop domain to the signature, e.g., HMAC over `shop-domain + raw_body`), and reject if the header value used for `WebhookMetadata#shop` is not part of what was verified. At minimum, document/enforce that `shop` must be treated as verified only after being cross-checked against an out-of-band trusted source (e.g., server-to-server confirmation with Shopify), since this gem cannot currently vouch for header-derived `shop` values in `Registry.process`.

### Proof of Concept
1. Attacker registers a Shopify store `attacker-shop.myshopify.com` and configures a webhook subscription pointing at the target app's public webhook endpoint.
2. Shopify delivers a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends an HTTP POST to the same endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this still passes [6](#0-5) .
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` sets `shop` to `"victim-shop.myshopify.com"` [7](#0-6) , and the app's handler processes attacker-controlled body content as if it originated from the victim shop.
