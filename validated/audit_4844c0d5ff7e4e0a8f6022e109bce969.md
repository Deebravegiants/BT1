### Title
Unbounded numeric fields in attacker-supplied BEEFY proofs panic the runtime via unchecked `.expect()` conversions - ([File: evm/rust/src/conversions.rs])

### Summary
The Solidity-ABI → SCALE conversion layer used to decode BEEFY/SP1 consensus proofs uses `.try_into().expect("... out of bounds")` on attacker-controlled `uint256` fields (`blockNumber`, `validatorSetId`, `authorityIndex`, `leafIndex`) instead of returning an error. These proofs are submitted by any signed account through `pallet-beefy-consensus-proofs::submit_proof`, so a value that doesn't fit the narrower Rust integer type (`u32`/`u64`) causes a deterministic panic inside runtime (STF) execution rather than a graceful `Err`.

### Finding Description
`evm/rust/src/conversions.rs` implements the conversions from ABI-decoded Solidity structs (produced by `alloy_sol_types::SolType::abi_decode_params`) into the SCALE primitives consumed on-chain: [1](#0-0) 

and similarly for the ECDSA/NAIVE path: [2](#0-1) 

Every one of `blockNumber`, `validatorSetId`, each vote's `authorityIndex`, and `leafIndex` is a Solidity `uint256`/large integer that a submitter fully controls, but each is force-converted with `.try_into().expect(...)` into a narrower type (`u32`, `u64`). None of these conversions return an error the caller can propagate — they abort execution with a Rust panic.

This is reachable from the pallet extrinsic entry point without any privilege beyond `ensure_signed`: [3](#0-2) 

`do_submit_proof` ABI-decodes the attacker-supplied bytes and immediately invokes the vulnerable `From` conversion while extracting the nonce for the SP1 path: [4](#0-3) 

It is reached again on the "uncle" settlement path: [5](#0-4) 

and on the first-proof path via `verify_and_apply`: [6](#0-5) 

In each case the ABI decode step (`abi_decode_params`) only validates that the bytes are well-formed ABI — it places no constraint on the numeric ranges of `commitment.blockNumber`, `commitment.validatorSetId`, `latestMmrLeaf.leafIndex`, or each `Vote.authorityIndex`, all of which a submitter fully controls in the calldata/extrinsic payload they construct.

### Impact Explanation
This mirrors the CVE-2019-17498 bug class: a bounds/range check on a length-like or numeric field derived from untrusted protocol input is not enforced safely, and the failure path corrupts execution rather than gracefully rejecting the message. Here, instead of an out-of-bounds memory read, the failure mode is a Rust panic during `apply_extrinsic`/STF execution. Because `submit_proof` is a normal signed extrinsic with `BoundedVec<u8, MaxProofSize>` (bounding only total *byte length*, not the numeric *value* of ABI fields), any account can trigger this deterministically on every node that executes the block containing the malicious extrinsic — collators/validators panicking on the same transaction is a chain-halting denial-of-service, which is the "route unable to deliver messages" / consensus-liveness class explicitly in scope.

### Likelihood Explanation
High. No special permissions, prior authority-set state, or cryptographic forgery are required — only a syntactically valid ABI encoding with an out-of-range integer in one of the flagged fields (e.g., `commitment.blockNumber = type(uint256).max`, or a `Vote.authorityIndex` greater than `u32::MAX`). The transaction fee spam-deterrent described in the pallet's comments assumes failures are graceful `Err`s that "pay the fee"; a panic bypasses that economic assumption entirely because the extrinsic never returns.

### Recommendation
Replace every `.try_into().expect(...)` in `evm/rust/src/conversions.rs` (and any equivalent conversions in `ismp-abi`) with fallible conversions that propagate an error (e.g., `TryFrom` returning `Result`, mapped to a proper `ismp`/pallet error) instead of panicking. Add explicit upper-bound validation on `blockNumber`, `validatorSetId`, `authorityIndex`, and `leafIndex` immediately after `abi_decode_params`, before any use, and reject the proof (paying the submission fee) rather than aborting the runtime.

### Proof of Concept
1. Construct a valid ABI encoding of `SP1BeefyProof` where `commitment.blockNumber` (a `uint256`) is set to a value `> u32::MAX` (e.g., `2^32`), all other fields well-formed enough to pass ABI decoding.
2. Prefix the byte `PROOF_TYPE_SP1` and submit via `pallet_beefy_consensus_proofs::submit_proof` as any signed account (per [3](#0-2) ).
3. Execution reaches `do_submit_proof` → `verify_and_apply`/`settle_uncle_proof`, both of which call `<... SP1BeefyProof as SolType>::abi_decode_params` then `.into()` on the result, invoking `impl From<crate::sp1_beefy::SP1Beefy::SP1BeefyProof> for Sp1BeefyProof` ( [1](#0-0) ), where `value.commitment.blockNumber.try_into().expect("block number out of bounds")` panics.
4. The panic aborts extrinsic execution deterministically for every node applying the block, rather than returning a rejected/failed extrinsic.

Note: I could not fully verify within this session whether every parachain runtime's block-execution panic-handling wraps this into a recoverable trap versus a full node crash/consensus stall — that determination would require examining the Substrate executor/panic-hook configuration in each runtime, which is outside what I was able to confirm from the indexed code. I recommend a Devin session with full repo access to confirm the exact operational blast radius (block invalidation vs. process abort) and to implement the fix.
