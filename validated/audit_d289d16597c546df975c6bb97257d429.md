### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant payload replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, then trusts `request.shop` (taken directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identity forwarded to the app's `WebhookHandler`. The `shop` header is never included in the signed material, so the binding "authenticated request == authenticated shop" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only this body-based HMAC and then dispatches using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate_signature` compares `compute_signature(verifiable_query.to_signable_string, secret)` against the `hmac` header — again, only the body is covered: [4](#0-3) 

This is provably a deliberate design choice elsewhere in the gem that was not applied here: `ShopifyAPI::Auth::Oauth::AuthQuery`, used for the OAuth callback (also a `VerifiableQuery`), explicitly folds `shop` into the HMAC-signed parameter set: [5](#0-4) 

So the gem's own pattern for binding tenant identity to an HMAC (OAuth callback) is not mirrored for webhooks. The `WebhookMetadata` struct that is handed to the merchant's `WebhookHandler.handle` carries this unauthenticated `shop` value verbatim: [6](#0-5) [7](#0-6) 

The identity binding that should hold is:
`HMAC(secret, signed_bytes) valid` ⇒ `signed_bytes` fully determines `(shop, topic, body)` used by the handler.
In this implementation, `signed_bytes == raw_body` only, so the equality that actually holds is:
`HMAC(secret, raw_body) valid` ⇒ `body` is authentic, but `shop`/`topic`/`webhook_id` are **not** authenticated.

### Impact Explanation
An attacker who owns (or controls) any shop running the same app can receive genuinely-signed webhook deliveries from Shopify for their own store (the app's `client_secret`/`api_secret_key` is shared across all installs of the app, and the attacker's own store's webhook traffic is legitimately HMAC-signed with it). The attacker can capture such a request (body + valid `hmac` header) and replay it to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain, while keeping the body and HMAC unchanged (or crafting any body content they choose to send from their own shop and simply relabeling the tenant). Because `HmacValidator` never inspects the shop header, this modified request still validates successfully, and `Registry.process` calls the host app's handler with `data.shop` set to the victim's domain and an attacker-controlled `data.body`.

If the host application uses `data.shop` from `WebhookMetadata` to select which merchant's session/tenant data to update (a common integration pattern explicitly enabled by this API, e.g. GDPR `customers/data_request`, `app/uninstalled`, `orders/create`, etc.), the attacker can inject or forge events attributed to a victim shop they do not control — a cross-tenant identity confusion that breaks the tenant boundary this gem is supposed to enforce for webhook consumers. This satisfies the "cross-tenant access" Critical impact category, since the vulnerability lets an unprivileged tenant impersonate another tenant purely through data the app itself is documented to trust (`WebhookMetadata#shop`).

### Likelihood Explanation
Likelihood is moderate-to-high for any app that: (1) is installed on at least one attacker-controlled/free-trial store, letting the attacker legitimately receive HMAC-valid webhook deliveries for arbitrary topics/bodies from Shopify, and (2) exposes its webhook endpoint on the public internet (mandatory, since Shopify itself must reach it). No access to `api_secret_key`, access tokens, or leaked credentials is required — only ordinary use of a free/attacker-owned store and the ability to send one HTTP request with modified headers to the app's own endpoint, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the tenant/topic identity fields into the signed material, mirroring `AuthQuery#to_signable_string`. Since Shopify signs only the body by design, the gem cannot retroactively add server-side header signing, but it can and should:
- Require host apps to cross-check `request.shop` against an app-maintained record of shops that have `app/uninstalled` not yet fired, or against known installed shops, before trusting `data.shop`.
- At minimum, document prominently (and ideally enforce via an API) that `WebhookMetadata#shop`, `#topic`, and `#webhook_id` are **not** covered by the HMAC and must not be used as the sole tenant-authorization key without additional verification (e.g., correlating `webhook_id` via a GraphQL lookup against the claimed shop's registered subscriptions before processing).
- Consider validating that the `shop` header matches an expected/allow-listed format and, where feasible, confirming webhook origin via Shopify's published source IP ranges as a defense-in-depth measure, since header-level binding cannot be added to the HMAC itself.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers any webhook topic the app subscribes to (e.g. `orders/create`) on their own store, capturing the real request Shopify sends to the app's public webhook endpoint — this includes a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
3. Attacker resends this exact HTTP request to the same endpoint, but changes only the `x-shopify-shop-domain` header value to `victim-shop.myshopify.com` (leaving body and HMAC untouched, or crafting the body freely).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`: [8](#0-7) 
   This succeeds because `to_signable_string` never includes the shop header.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and any application logic keyed on `data.shop` (e.g., updating `victim-shop`'s stored order/customer/uninstall state) is executed under the attacker's control despite the attacker having no access to `victim-shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
