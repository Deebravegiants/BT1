### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, allowing cross-tenant event forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body of an inbound webhook request, while `shop`, `topic`, `webhook_id`, and `api_version` are extracted from separate HTTP headers that play no part in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts those header-derived fields to construct `WebhookMetadata` for the registered handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors all read from `@headers`, independent of the signed body: [2](#0-1) .

`Utils::HmacValidator.validate` verifies the received HMAC by recomputing the signature over `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) .

`Registry.process` calls this validator and, once it passes, builds `WebhookMetadata` directly from `request.topic` and `request.shop` — both header-derived and not bound to the HMAC: [4](#0-3) .

The equality this breaks: `shop authenticated-by-HMAC` (which is really just "body-with-valid-HMAC") is treated as equal to `shop delivered-in-header-and-acted-upon`, but the gem never enforces that binding. An unprivileged internet user who has legitimate access to any single shop that has the app installed (e.g., a free Shopify development store) can capture one genuine webhook (valid body + HMAC signed with the app's shared `api_secret_key`) and then replay it to the app's webhook endpoint with the `shopify-shop-domain` and/or `shopify-topic` headers swapped to a different (victim) shop/topic combination. Because the HMAC only covers the body, the swapped headers do not invalidate `Utils::HmacValidator.validate`, so `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop/topic while carrying attacker-chosen body content that was never actually sent by Shopify for that shop.

### Impact Explanation
This maps to the High severity bucket — a scope/authentication boundary check ("this webhook truly originated from shop X and topic Y") answers permissively because that boundary is never actually checked by the HMAC, only the raw body is. A host application built on top of the documented API (as shown in `docs/usage/webhooks.md`, which explicitly instructs apps to trust `data.shop`, `data.topic`, and `data.body` after calling `Registry.process`) will process attacker-controlled cross-tenant events, potentially causing it to write attacker-supplied body content into another merchant's tenant record, trigger cross-tenant side effects (e.g., GDPR "customers/redact" mishandling, order/product state corruption for a shop the attacker doesn't control), or otherwise blur tenant isolation — all without needing the app's `api_secret_key` or an access token, since the attacker reuses a real signature obtained from their own shop's genuine webhook delivery.

### Likelihood Explanation
Any developer/merchant who installs the target app on their own store receives real webhook deliveries with valid HMACs for arbitrary bodies they control (by triggering resource changes in their own store). Replaying that exact body+HMAC pair to the app's public webhook endpoint with modified `shop-domain`/`topic` headers requires no secret and no privileged access — only the ability to send an HTTP POST, which matches the "unprivileged internet user" threat model. The likelihood is high given the low complexity of the attack and the fact that the app's documented usage pattern trusts `data.shop`/`data.topic` unconditionally after `Registry.process` succeeds.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them to the request, e.g., by having `to_signable_string` concatenate the header values with the body) so that any mutation of those header fields invalidates the signature. Alternatively/additionally, `Registry.process` should cross-check `request.shop` against a set of shops known to have received the specific `webhook_id`, or require callers to supply an expected shop context.

### Proof of Concept
1. Install the target app on an attacker-controlled development store `attacker.myshopify.com`; trigger a webhook event (e.g., `products/update`) to obtain a genuine request with `raw_body` = `B` and header `shopify-hmac-sha256` = `H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Send a POST to the app's webhook endpoint with the same body `B` and the same `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim.myshopify.com` and/or `shopify-topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers and body, exposing `shop` → `victim.myshopify.com` [5](#0-4) .
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only, matches `H`, and returns `true` [6](#0-5) .
5. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(topic: "customers/redact", shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)` [7](#0-6) , causing the host application to act on forged, cross-tenant webhook data that Shopify never actually sent for `victim.myshopify.com`.
