### Title
Unverified `repay` overpayment refunds are paid out of real token custody without any inbound transfer - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's `repay` flow computes a refund as `declared_amount - net_repay` derived purely from the caller-supplied declared amount, not from a measured balance delta of tokens actually received. When `repay` is invoked against a `(hub, token)` market that carries no debt, `current_debt_ceil` resolves to zero, the full-close branch yields `net_repay == 0`, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the entire declared amount is transferred back to the caller out of the pool's real custody. This is the same bug class as CVE-2016-1000030 (unchecked/improperly used return value): the settlement result of the repay leg is never reconciled against an actual inbound token transfer before funds leave the contract.

### Finding Description
`ops::repay::apply` resolves the repay through `resolve_repay`/`current_debt_ceil` and then refunds `declared - net_repay` to the payer. The refund leg neither debits `cash` nor passes `require_reserves`, and no step verifies that the payer actually transferred `declared` tokens in. The in-repo regression test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` executes exactly this path: with `before.borrowed == 0` and zero tokens sent, `client().repay(&payer, &ract(0, custody_before))` credits `actual_amount == 0` yet drains `custody_before` from the pool's token balance, leaving the book untouched. [1](#0-0) 

The same unfunded-refund gap is documented in `ops::recapitalize::apply`, which refunds the excess over the shortfall from a declared inbound amount rather than measured receipts. [2](#0-1) 

### Impact Explanation
An unprivileged address can call `repay` on any no-debt spoke market with `amount` equal to the pool's full token balance and receive the entire custody balance as a "refund" without paying anything. Since pool custody backs all suppliers' RAY-denominated supply shares, this is direct theft of user funds and, on repeat across markets, protocol insolvency. Because the book (`cash`, `borrowed`, `supplied`) is untouched, the loss is not reflected in indexes — suppliers' claims remain nominally intact while the underlying tokens are gone, which is worse than a priced bad-debt event.

### Likelihood Explanation
The attack requires only: (a) a registered `(hub, token)` market with `borrowed == 0` for the caller (trivially satisfied by any market the attacker has never borrowed from, and in the limiting case a market with zero outstanding debt pool-wide, where the refund is unbounded by any debt), and (b) a single `repay` call with a crafted `RepayAction`/`amount`. No collateral, no position, no auth beyond the caller's own address, and no oracle dependence is needed. The cost is one transaction; the gain is up to the market's full liquid balance.

### Recommendation
Make repay settlement receipt-measured, matching the flash-loan pattern already used in `ops::flash::apply`/`require_balance`: snapshot `token::Client::balance(&pool)` before the flow, require `balance_after >= balance_before + net_repay`, and compute the refundable excess as `min(declared, actual_received) - net_repay` rather than `declared - net_repay`. Apply the same fix to `ops::recapitalize::apply`. [3](#0-2) 

### Proof of Concept
The repository itself contains the executable proof: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs` creates a fresh payer with no debt, calls `repay` with `amount == custody_before`, sends nothing, and asserts (via `assert_unfunded_refund_drained_custody`) that the payer receives `custody_before` while `cash`/book state is unchanged. [4](#0-3) 

Note on certainty: I verified the behavior through the test's own assertions and doc comments, which describe `ops::repay::apply`, `resolve_repay`, `current_debt_ceil`, and `ops::recapitalize::apply` internals; I did not read `contracts/pool/src/ops/repay.rs` directly, so the exact line where the refund transfer is issued should be confirmed there.

```rust
/// The refund gap is not specific to `recapitalize`. Two pool legs refund an
/// excess derived from a declared inbound amount, not from the cash book:
/// `ops::recapitalize::apply` (the excess over the shortfall) and
/// `ops::repay::apply` (the excess over the debt). Neither refund debits `cash`
/// or passes `require_reserves`.
///
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
```
