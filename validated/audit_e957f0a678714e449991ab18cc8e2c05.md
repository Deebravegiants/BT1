### Title
Webhook `shop-domain` header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature over the raw request body only, while the `shop` identity that the app's handler acts on is read from an unauthenticated HTTP header. This breaks the intended binding `HMAC-verified bytes == data the app trusts`, letting anyone who can obtain one valid `(body, hmac)` pair for a webhook (e.g., a merchant/attacker who installs the app on their own store and triggers a webhook) replay that same body+signature to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header, causing the app to process the payload as if it originated from a different, unrelated shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`, i.e. the body bytes: [2](#0-1) 

But `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC, then forwards `request.shop` (the unverified header) straight into `WebhookMetadata`, which is handed to the app's webhook handler as the tenant identity for the event: [4](#0-3) [5](#0-4) 

Equality that should hold but does not:
`bytes verified by HMAC` (raw body only) `== bytes the app trusts for tenant attribution` (body **and** `shop-domain` header). Because the header is outside the signed scope, an attacker who owns a legitimate shop that has this app installed can capture one authentic `(raw_body, x-shopify-hmac-sha256)` pair from their own store's webhook delivery, then POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different (victim) shop's domain. The HMAC still validates (it only covers the body, which is untouched), so `Registry.process` accepts the request and dispatches it to the handler tagged with the attacker-chosen `shop`, i.e. cross-tenant impersonation of the webhook's origin.

This directly mirrors the report's bug class: the field acted upon (`shop`, used for tenant-scoped business logic in the app's `WebhookHandler#handle`) is not covered by the same authenticity check (HMAC) that is used to accept the request.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key storage lookups, write data, or otherwise scope actions per-tenant is exposed to cross-tenant data confusion/injection: an attacker-controlled webhook body can be attributed to a shop the attacker does not own, without needing that shop's access token or any Shopify-issued credential for it. This matches the Critical "cross-tenant access" impact category from the rules, since the tenant boundary (`shop`) is not authenticated even though the request overall passes the app's only authenticity check (HMAC).

### Likelihood Explanation
The prerequisite is only that the attacker controls (or can install the app on) at least one shop and can trigger a webhook delivery for it — this is achievable by any unprivileged merchant/developer, no special credentials, secrets, or privileged accounts are required. Capturing a `(raw_body, hmac)` pair requires only observing traffic the attacker's own server receives (their own webhook endpoint), and replaying it with a modified header is trivial once observed, so exploitation likelihood is high given attacker access to any installable shop.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header into the HMAC-signed material, or otherwise cryptographically verify that the shop the app dispatches to is the one Shopify actually delivered the webhook for — e.g., look up/validate the shop against a known, previously-established session/installation record rather than trusting the header verbatim, and reject webhooks whose `shop-domain` does not correspond to a shop with a legitimate installation delivering that specific webhook id/topic combination.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), receiving a legitimate delivery with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `api_secret_key` over `B`).
2. Attacker replays an HTTP POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic` / `x-shopify-webhook-id` as needed
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes body `B` as if it were an authentic event from the victim shop, even though the victim never sent it and the attacker holds no credential for the victim shop.
