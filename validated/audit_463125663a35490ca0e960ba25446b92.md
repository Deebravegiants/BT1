### Title
Webhook `shop-domain` (and `topic`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`) values that the gem hands to the app's `WebhookHandler` are read from unauthenticated HTTP headers. This breaks the intended identity binding: `hmac-verified bytes == raw_body` but `shop attributed to the webhook == unauthenticated header value`.

### Finding Description
`Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Request#shop` and `Request#topic`, however, are read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` and `x-shopify-topic` / `shopify-topic` headers, with no HMAC coverage at all: [3](#0-2) 

These unauthenticated values are then propagated directly into `WebhookMetadata`, which the host application's `WebhookHandler#handle` uses as the tenant identifier for the webhook: [1](#0-0) [4](#0-3) 

Equality that should hold but doesn't: `shop value cryptographically bound by HMAC == shop value delivered to the app's handler`. In fact `HMAC(raw_body)` says nothing about which shop or topic header accompanied it, so any `(raw_body, hmac)` pair that is valid for one webhook delivery remains valid if replayed with a different `x-shopify-shop-domain` (or `x-shopify-topic`) header.

### Impact Explanation
This is a cross-tenant identity-binding failure. An attacker who is able to obtain any one legitimately-signed `(raw_body, hmac)` pair — e.g., a webhook their own store received, or one intercepted/replayed in a multi-tenant test/proxy setup — can resubmit it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain (and/or the `topic` header changed to a different registered topic). `Registry.process` will still consider the HMAC valid (it only checks the body) and will dispatch to the handler with `WebhookMetadata.shop` set to the attacker-chosen value. Any host application that keys per-tenant state, authorization, or side effects off `data.shop`/`data.topic` (which is exactly the documented and expected use of `WebhookHandler`) can be tricked into acting on behalf of, or against, a shop it never actually received a signed webhook for — satisfying the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
Requires the attacker to possess at least one valid signed webhook body/HMAC pair (e.g., from their own shop's webhook deliveries, which any merchant using the app can obtain without any special privilege), and to control raw HTTP headers sent to the app's webhook endpoint. No access to `api_secret_key` or any merchant's access token is required — only a previously delivered, legitimately-signed webhook payload, which is standard, low-friction information for anyone who installs the app on a shop they control.

### Recommendation
Include the shop domain and topic (and any other header claiming to identify the message) in the signed payload verification path, or otherwise cryptographically bind them to the HMAC (e.g., verify against Shopify's per-request signature scheme that covers headers, or require the caller to independently confirm the `shop-domain` against a previously known/authenticated tenant registration before trusting it). At minimum, document/enforce that `Request#shop` and `Request#topic` must not be treated as authenticated unless verified against out-of-band, tenant-specific state (e.g., cross-check against the shop for which the webhook topic was registered).

### Proof of Concept
1. App installs on `attacker.myshopify.com` and receives a legitimate webhook, e.g., for topic `orders/create`, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and raw JSON body `B`.
2. Attacker resends the same body `B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only [5](#0-4)  and it matches, since the shop header was never part of the signed input.
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it legitimately originated from `victim.myshopify.com`.
