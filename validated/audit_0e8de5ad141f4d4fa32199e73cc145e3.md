This confirms the root cause: the gem's own documentation (`docs/usage/webhooks.md:125`) states that `Registry.process` "will verify the request did indeed come from Shopify," and instructs the handler to trust `data.shop` for tenant identification (line 14, 26), yet the HMAC computed in `Utils::HmacValidator.validate` only signs `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers [2](#0-1) .

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely that the body bytes were signed with the app's shared secret. It never binds the `shop-domain` header to that signature. `Registry.process` accepts any request whose body/HMAC pair validates, then constructs `WebhookMetadata` using the unauthenticated `shop` header value and hands it to the app's handler as the trusted tenant identifier.

### Finding Description
The equality that should hold is: `shop_header == shop_that_produced(hmac)`. In reality the HMAC only proves `raw_body == body_that_produced(hmac)`; the `shop` field is read independently via `shopify_header("shop-domain")` [3](#0-2)  and is never included in `to_signable_string` [1](#0-0) .

`HmacValidator.validate`/`validate_signature` computes the HMAC purely from `to_signable_string` and the app's `api_secret_key` [4](#0-3) . Because a single app's `api_secret_key` is shared across every shop that installs the app, any two webhook deliveries with identical raw bodies (e.g., the same JSON payload shape, or a body an attacker can freely reproduce/predict, such as `customers/redact` or `shop/redact` boilerplate payloads, or any webhook whose body content is attacker-influenced, e.g., `orders/create` from an order the attacker places in their own shop) produce mathematically valid HMACs regardless of which shop the header claims.

`Registry.process` trusts the header value directly: it validates only the HMAC of the body, then forwards `request.shop` unchanged into `WebhookMetadata` for the handler [5](#0-4) . The gem's own documentation instructs consuming apps to treat `data.shop` as the authoritative tenant/shop identity (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) , explicitly claiming that `process` "will verify the request did indeed come from Shopify" [7](#0-6) . That claim is only true for the body; it is false for the shop attribution, which is the field host apps rely on to segregate tenants.

An attacker who is a legitimate merchant with the target app installed on their own store can generate a real, validly-HMAC'd webhook delivery from Shopify for their own shop (by triggering the underlying event, e.g. creating an order or triggering `customers/data_request`), capture the raw body and its `X-Shopify-Hmac-Sha256` value, then replay that exact `raw_body`/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different shop the app is also installed on (shop domains for other merchants are frequently guessable/public, e.g. `othershop.myshopify.com`). `Request.new` and `Registry.process` accept it as fully authentic for the spoofed shop, since only the body is checked [8](#0-7) .

### Impact Explanation
This is a cross-tenant identity-binding break: data or actions the host app attributes to shop B are actually attacker-controlled content the attacker sourced from shop A, delivered with a forged shop header that passes signature validation. Depending on the handler, this can pollute another merchant's data store, trigger the mandatory GDPR handlers (`customers/redact`, `shop/redact`, `customers/data_request`) against the wrong tenant, or otherwise let one merchant inject events into another merchant's account context, meeting the "cross-tenant access" bar.

### Likelihood Explanation
Exploitation only requires being (or briefly becoming) a legitimate merchant of the target app — no access to `api_secret_key`, access tokens, or the target shop's credentials is needed. The attacker fully controls the raw HTTP request to the app's own webhook endpoint (headers and body), so forging the `shop-domain` header while replaying a validly-signed body is straightforward and requires no privileged access.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered `to_signable_string`, or otherwise cryptographically bind the shop header to the signed payload before trusting it. At minimum, `Registry.process` should cross-check `request.shop` against the app's own session/installation store for that shop before invoking the handler, rather than passing through an unauthenticated header value as ground truth.

raw_body = captured_raw_body        # legitimately signed by Shopify using the app's shared secret
hmac_header = captured_hmac_header  # valid for raw_body

# 2. Attacker replays the exact same body/HMAC to the app's webhook endpoint,
#    but rewrites the shop header to a victim shop where the app is also installed.

  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,     # unchanged, still validates raw_body

}

ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body against the HMAC.
# The handler receives WebhookMetadata with shop: "victim-shop.myshopify.com",
# even though the payload/content actually originated from the attacker's own shop.
