Audit Report

## Title
CORS wildcard origin matching in the Gateway HTTP server is too lax, permitting subdomain/prefix spoofing bypass - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function implements wildcard CORS origin matching (e.g. `*.remix.com`) using a raw `strings.HasSuffix` comparison on the hostname, without enforcing a `.` label boundary. This allows any attacker-controlled domain that merely ends with the configured suffix string (e.g. `evilremix.com`, `attacker-remix.com`) to be treated as a legitimate subdomain and granted cross-origin access via a reflected `Access-Control-Allow-Origin` header.

## Finding Description
In `isAllowedOrigin`, when an allowed entry starts with `*.`, the code strips the prefix and checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 
This is a pure string-suffix check, not a domain-label-boundary check, so `evilremix.com` satisfies `HasSuffix("evilremix.com", "remix.com")` even though it is not a subdomain of `remix.com`. The origin used in this check comes directly from the attacker-controlled `Origin` header, and if the check passes, that same untrusted value is reflected verbatim into the `Access-Control-Allow-Origin` response header: [2](#0-1) 
No other validation (scheme/port matching aside) narrows this down to a true subdomain relationship, so the exact-match and scheme/port checks preceding it do not mitigate the flaw.

## Impact Explanation
When an operator configures a wildcard CORS entry (a supported, documented pattern, as seen in `core/scripts/gateway/sample_config.toml` and `sample_config_tls.toml`), an attacker who registers a domain sharing the suffix string can obtain CORS access to the gateway's HTTP endpoint that was never intended to be trusted. This enables cross-origin reads of gateway responses in victims' browsers, matching the cross-user response confusion / CORS bypass impact class.

## Likelihood Explanation
Exploitation requires no special privileges — any unprivileged client can set an arbitrary `Origin` header in a cross-origin request. The only precondition is that the operator has enabled a wildcard `CORSAllowedOrigins` entry, which is an intentional supported feature, not a misuse of the system. Domain suffix-squatting (e.g. registering `evilremix.com`) is cheap and trivial for an attacker, making this moderately-to-highly likely wherever wildcard CORS is used.

## Recommendation
Enforce a proper label boundary in the wildcard match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```

## Proof of Concept
1. Configure `CORSAllowedOrigins = ["https://*.remix.com"]` in the gateway config.
2. Send an HTTP request to the gateway with header `Origin: https://evilremix.com`.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilremix.com", "remix.com")` is `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirming the bypass. This can be directly verified via a Go unit test calling `isAllowedOrigin("https://evilremix.com")` against a server configured with `*.remix.com`.
