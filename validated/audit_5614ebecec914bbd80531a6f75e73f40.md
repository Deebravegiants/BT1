### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then dispatches the handler using the shop identity taken from the unauthenticated `X-Shopify-Shop-Domain` header. Because the signing secret (`api_secret_key`) is a single, app-wide secret shared across every shop that installs the app, a valid `(body, hmac)` pair captured from one tenant remains valid when replayed with a different `shop-domain` header, letting an attacker who controls one installation of the app make the library process forged webhook data under another shop's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies only that the HMAC matches the *signable string*: [1](#0-0) 

For webhook requests, the signable string is defined as the raw body only: [2](#0-1) 

`shop` (and `topic`) are read straight from HTTP headers that are not part of the signed material at all: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` when constructing the metadata passed to the handler: [4](#0-3) 

The equality the code implicitly assumes is:
`hmac_valid(body) == true` ⟺ `shop_header == shop_that_produced(body, hmac)`

This equality does not hold: `hmac_valid(body)` only proves the request was signed with *the app's* `api_secret_key` — it says nothing about which shop the header claims to be from, because the same `api_secret_key` is shared by every shop that has the app installed. `shop` is exactly the kind of "field acted on but not covered by the HMAC" that breaks the identity binding.

### Impact Explanation
An attacker who has installed the app on any shop they control (which is normal, unprivileged access for a public/embedded app) can:
1. Trigger a legitimate webhook delivery to their own endpoint (or simply POST a body of their choosing to their own webhook URL, since they control the raw body content that gets HMAC-signed by Shopify using the shared `api_secret_key`).
2. Capture the resulting `(raw_body, hmac-sha256)` pair, which will validate successfully via `HmacValidator.validate` for *any* shop, because that check never touches `shop-domain`.
3. Replay the exact same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop that also has the app installed.
4. `Registry.process` passes `request.shop` (the attacker-controlled victim shop string) together with `request.parsed_body` (attacker-controlled content) straight to the registered handler as `WebhookMetadata`.

Any application logic that uses this shop value to look up per-tenant state, write data, or make authenticated decisions (a common pattern for webhook consumers) will act on attacker-controlled data attributed to the wrong tenant — a cross-tenant access/injection primitive, which is explicitly a Critical-impact category.

### Likelihood Explanation
This requires no privileged credentials, no access token, and no interception — only a working webhook endpoint on the app (already public by design) and the ability to install/operate the app on one shop, which is the baseline capability of any unprivileged user of a public Shopify app. The library provides no built-in mitigation (e.g., binding shop to a shop-scoped secret, or validating the shop domain format/membership against the signed payload), so any consumer of this gem inherits the exposure unless they implement extra checks themselves.

### Recommendation
Bind the `shop` identity to the signed payload rather than trusting the unauthenticated header alone. Options include:
- Cryptographically confirming the delivered `shop` against a per-shop record (e.g., cross-checking against the shop stored for a matching install/session) before trusting `request.shop` in `WebhookMetadata`.
- Where feasible, incorporate the shop domain into the value that is verified (e.g., verify that `shop` corresponds to a shop known to have a currently valid session/access token for this app) rather than only checking the raw-body HMAC.
- At minimum, clearly document in `Registry.process`/`Webhooks::Request` that `shop` is unauthenticated and must not be trusted for authorization decisions without independent verification by the consuming application.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on victim `victim-shop.myshopify.com`, both sharing the same `api_secret_key`.
2. Attacker POSTs `{"malicious":"payload"}` to their own webhook consumer endpoint, which is processed by Shopify's webhook infra and delivered with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of the body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker intercepts/replays this request to the same app endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body and HMAC identical.
4. `HmacValidator.validate(request)` returns `true` because it only validates `Digest.hexencode(...)` against `@raw_body`: [5](#0-4) 
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's forged body, as shown in the `handler.handle` call above.
