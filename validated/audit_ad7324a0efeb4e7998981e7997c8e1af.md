### Title
Reentrant escrow drain in `IntentGatewayV2.withdraw` (Tron) via external transfer before escrow accounting update - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.sol` implements `withdraw()` with the external token/native transfer performed **before** the escrow ledger (`_orders[commitment][token]`) is decremented, and without a `nonReentrant` guard on the function or its callers (`onAccept`, `onGetResponse`). This violates the checks-effects-interactions (CEI) pattern that the canonical EVM implementation enforces (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`), where the escrow balance is decremented *before* the transfer is made.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

The check on the escrow slot is only `== 0` (existence), not a sufficiency check (`>= amount`), and the state decrement (`_orders[body.commitment][token] -= amount`) happens **after** the external call. This is the classic use-after-free-analogous pattern the CVE hints at: a resource (`_orders[...][token]`, the escrowed balance record) is used to authorize a payout, but the record that should "consume"/invalidate that resource is not updated until after control has been yielded to an untrusted external contract (the `beneficiary`, which is directly attacker-controlled — it is the solver address supplied in `fillOrder`/`WithdrawalRequest`). During that external call the balance record still reflects the pre-payout state — a stale, not-yet-"freed" value that remains reachable and reusable.

By contrast the maintained EVM implementation applies CEI correctly: [2](#0-1) 

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    ...
    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();
    _orders[body.commitment][token] = escrowed - amount;
    if (token == address(0)) {
        _sendValue(beneficiary, amount);
    } else {
        IERC20(token).safeTransfer(beneficiary, amount);
    }
}
```

Here the decrement happens strictly before the transfer, closing the reentrancy window. The existence of `IntrinsicIntentsReentrancyTest.sol` (documenting a fixed pre-CEI reentrancy bug in `_fillSameChain`/`_fillCrossChain`) confirms the project is already aware of and has fixed this exact bug class elsewhere — but the Tron variant of `IntentGatewayV2.withdraw` was not updated to match.

Reachability: `withdraw()` is invoked from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` messages authenticated only against the registered peer gateway, not against arbitrary parties) and from `onGetResponse()` on a cancellation proof: [3](#0-2) [4](#0-3) 

Both are reachable by any relayer submitting a valid ISMP message/proof — an unprivileged path that matches the required threat model (relayer/message dispatcher reachable, single relayed proof).

### Impact Explanation
An attacker who places (or fills) an order can name themselves (or a contract they control) as `beneficiary`. When native TRX/ETH is escrowed, the low-level `.call{value: amount}("")` to the beneficiary yields control before `_orders[...][token]` is decremented. A malicious beneficiary contract's fallback can attempt to re-enter reachable public functions of the gateway while the stale (undecremented) escrow accounting is still in place, or — if the token being paid out is itself attacker-supplied/malicious (arbitrary ERC20 registered as an order's input, permitted by the design) — the token's `transfer` hook can re-enter before the corresponding decrement. Because the sufficiency check is only `== 0` rather than a bounds check against `amount`, any reentrant path that reaches `withdraw`/the transfer loop again for the same commitment/token before the decrement executes can extract more value than was actually escrowed, i.e. concrete theft of escrowed funds / unbacked payout from the gateway's balance. This directly matches the "concrete theft or permanent freezing of funds" bar in the validation rules.

### Likelihood Explanation
High. The path from a relayed ISMP message (attacker-controlled `beneficiary`/token choice, since the order creator and fill beneficiary are both otherwise-unprivileged actors) into `withdraw()` requires no admin/governance/validator collusion — only a normal relayer delivering a message with a valid Hyperbridge proof, which is the standard, permissionless intent-fill/redeem flow. The absence of `nonReentrant` on `onAccept`/`onGetResponse`/`withdraw` in this file (confirmed by grep — no `nonReentrant`/`ReentrancyGuard` matches in the Tron contract) removes the only other mitigating control.

### Recommendation
Apply the same CEI fix already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` by `amount` (with an explicit `amount <= escrowed` check, not just `== 0`) *before* performing the native/token transfer. Additionally, add a `nonReentrant` guard on `withdraw`/its entry points as defense in depth, consistent with `IntentGatewayV2.sol` (main) which guards `cancelOrder` with `nonReentrant`.

### Proof of Concept
1. Attacker (as `user`) places a same-chain or cross-chain order with `output.beneficiary` = an attacker-deployed contract `Evil`, and includes at least one native-token (`token == address(0)`) leg in the escrow/withdrawal.
2. A relayer delivers the valid `RedeemEscrow`/`RefundEscrow` ISMP message; `onAccept` → `withdraw(body, ...)` executes.
3. `withdraw` sets `_filled[commitment] = beneficiary` (fine), reads `_orders[commitment][token] != 0` (passes), and calls `beneficiary.call{value: amount}("")` — this yields control to `Evil` **before** `_orders[commitment][token] -= amount` runs.
4. `Evil`'s `receive()`/fallback attempts to re-enter a path that reaches `withdraw` again (or, for the ERC20 branch, a malicious `token.transfer` implementation calls back into the gateway) while `_orders[commitment][token]` still shows the pre-decrement (stale) balance, allowing a second payout to be authorized against the same, not-yet-consumed escrow record before the first call's decrement is applied — draining more than was actually escrowed for that commitment.
5. Exact exploitability of the specific re-entry target (which public function, given `onlyHost` gating on `onAccept`/`onGetResponse`) depends on further verification of Tron's host call semantics per-batch, which was not fully traced in this pass; the root-cause CEI violation and missing sufficiency check are confirmed directly in the source and are sufficient on their own to warrant remediation regardless of the precise re-entry vector, since any future code path (own or via composable calldata `_execute`) that reaches `withdraw` a second time for the same commitment before the decrement lands will realize the drain.
