### Title
Webhook HMAC only signs the request body, not the `shop`/`topic`/`webhook_id` headers, allowing cross-tenant webhook spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature Shopify sends never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` accepts any request whose body+HMAC pair is valid and then dispatches the handler using the unauthenticated `shop`/`topic` header values, breaking the binding between "the HMAC-verified sender" and "the shop/topic the app believes the event is about."

### Finding Description
`Request#to_signable_string` is defined as: [2](#0-1) 

This is the only material `HmacValidator` checks via `validate_signature`: [3](#0-2) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

`Registry.process` checks HMAC validity, then immediately trusts these unauthenticated header-derived fields to build the `WebhookMetadata` passed to the app's own handler: [1](#0-0) 

The `api_secret_key` (the app's OAuth `client_secret`) used for the HMAC is a single value shared by the app across **all** installing shops — it is not per-tenant. Any user who can install the public app on a shop they control (a free/dev store is sufficient, and no privileged credentials are needed) will legitimately receive real, correctly-signed webhook deliveries containing arbitrary body content (e.g. `customers/data_request`, `orders/create`, `app/uninstalled`). Because the signature covers only the body, that attacker can capture one `(raw_body, x-shopify-hmac-sha256)` pair from their own shop, then replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds because the body bytes are unchanged, so `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled `body`/`topic`, even though nothing about the victim shop was ever verified.

The equality that should hold but doesn't: `verified_bytes (raw_body signed by HMAC) == bytes_the_app_keys_its_tenant_decision_on (headers: shop, topic, webhook_id)`. Here the HMAC only certifies the body; the shop/topic identity fields are asserted, not proven.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who has no relationship with a victim shop can cause the host application to process a fully-HMAC-"valid" webhook that the app attributes to that victim shop, with attacker-chosen topic and body content. Depending on how the host app's registered handlers use `WebhookMetadata#shop`/`#topic`/`#body` (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`, `customers/data_request`, or any custom topic wiring business logic such as disabling access, deleting data, or altering settings keyed by `shop`), this can lead to cross-tenant data manipulation or deletion for shops the attacker does not own — this matches the Critical "cross-tenant access" impact category, since it defeats the sole tenant-identity check (HMAC) that `Registry.process` relies on.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker must (1) install the public app on any shop they control (no special privilege — this is the normal, unauthenticated app-install flow available to any merchant), (2) receive at least one real webhook delivery for a topic of interest, and (3) replay the captured `(body, hmac)` pair with a forged `shop-domain`/`topic` header to the app's public webhook endpoint. No knowledge of `api_secret_key` or any access token is required, satisfying the "unprivileged internet user" bar. The main constraint is that the replayed body content is fixed to whatever was captured (not free-form attacker JSON), which limits — but does not eliminate — impact depending on handler logic.

### Recommendation
Do not trust `request.shop`, `request.topic`, or `request.webhook_id` as authenticated values based solely on the body HMAC. At minimum:
- Include the `shop-domain` (and ideally `topic`) header bytes in the HMAC-signed string (`to_signable_string`) so a body/signature pair cannot be replayed under a different shop or topic, or
- Require callers of `Registry.process` to cross-check `request.shop` against a shop they already have an authenticated session/webhook-registration record for before invoking the handler, and document this requirement prominently since the gem currently implies the HMAC check alone is sufficient (`raise ... unless Utils::HmacValidator.validate(request)`).

### Proof of Concept
1. Install the target app (which uses this gem) on an attacker-controlled dev/test shop `attacker-shop.myshopify.com`; trigger a real webhook (e.g. `customers/data_request`) so Shopify sends a legitimately HMAC-signed request to the app's webhook endpoint. Capture the raw body `B` and header `x-shopify-hmac-sha256: H`.
2. Send a new HTTP POST to the same app webhook endpoint with:
   - `x-shopify-hmac-sha256: H` (unchanged)
   - body: `B` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: any registered topic of choice (forged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   This succeeds because validation only recomputes the HMAC over `B`, per `to_signable_string`: [2](#0-1) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: "victim's forged topic", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act as if the victim shop sent this webhook — despite the victim never being involved.
