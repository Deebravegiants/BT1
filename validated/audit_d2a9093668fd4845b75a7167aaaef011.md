## Title
`CallDispatcher.dispatch()` has no access control, letting anyone drain assets temporarily held by the shared dispatcher - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is an unrestricted `external` function that decodes an attacker-supplied `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry, in the `CallDispatcher`'s own context [1](#0-0) . It has no `msg.sender` restriction, no reentrancy guard, and no allow-list on `to` — the only check is that `to` has code. This mirrors the Rabby Swap incident pattern: an externally-callable function that forwards arbitrary, unchecked `to`/`data`/`value` parameters supplied by whoever calls it, letting anyone impersonate the intended caller and reach any target with the contract's own privileges/balance.

### Finding Description
`CallDispatcher` is deployed once and shared as a long-lived singleton across every app that composes with it — `IntentGatewayV2` (predispatch/output execution) [2](#0-1) [3](#0-2) , `HyperFungibleToken.onAccept` [4](#0-3) , and `WrappedHyperFungibleToken.onAccept` [5](#0-4) . Its documented address is published on the contract-addresses page and is meant to be reused by all integrators [6](#0-5) .

The documented usage pattern explicitly instructs users to set the bridge recipient (`to`) to the `CallDispatcher` address so that minted/unlocked tokens land there before the attached `Call[]` spends them (e.g. approve+swap) [7](#0-6) [8](#0-7) . The security notes even acknowledge the dispatcher "holds tokens temporarily during execution" and recommend exact-amount approvals rather than unlimited ones [6](#0-5)  — but this only mitigates lingering ERC20 *allowances*, not lingering ERC20/native *balances*.

Because `dispatch()` is callable by anyone (no `onlyHost`, no `onlySelf`, no caller allow-list), any address whose bridged/attached `Call[]` does not perfectly consume 100% of the amount delivered to the dispatcher (rounding, partial-fill swap output, a call intentionally crafted to leave a remainder, or a race where a user's calldata array is simply incomplete) leaves a residual balance sitting in the shared `CallDispatcher`. Unlike `IntentGatewayV2`, which explicitly builds and executes sweep-back `Call[]`s for every known input/output token after dispatching [9](#0-8) , the `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` paths perform no such sweep — they simply forward `message.data` to `dispatch()` and return [4](#0-3) . Any tokens or ETH left in the dispatcher after that call remains there, unprotected, until the next unrelated caller sweeps it away via their own `dispatch()` call.

### Impact Explanation
Since `CallDispatcher.dispatch()` performs no caller authentication, any address can submit a `Call[]` that targets an ERC20 token (`transfer(attacker, dispatcher.balanceOf)`) or forwards native ETH out of the dispatcher, stealing any balance currently or residually held by the shared dispatcher — funds that legitimately belong to whichever bridging user's tokens were minted/unlocked to that address and not fully consumed by their own calldata. This is a direct, permissionless external-call vector into a balance-holding contract, the same bug class as the Rabby incident (unchecked `functionCallWithValue`/low-level `call` reachable by any external transaction, draining funds the caller never should have controlled).

### Likelihood Explanation
Reachable from a single external transaction with no privileged role required — any account can call `CallDispatcher.dispatch(bytes)` directly at any time the dispatcher holds a nonzero balance. The documented `to = CALL_DISPATCHER` bridging pattern actively encourages routing bridged assets through this contract, and any imperfect/partial calldata (slippage, rounding, a swap that yields less than expected, or a user simply omitting a full sweep in their `Call[]`) creates a window where funds sit exposed.

### Recommendation
Restrict `CallDispatcher.dispatch()` to authorized callers only (e.g. an allow-list of registered app contracts such as `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, or an `onlyRegisteredCaller` modifier), and/or ensure every integration sweeps 100% of any asset delivered to the dispatcher back to a safe owner within the same atomic call (as `IntentsBase._execute` already does), so no exploitable residual balance can ever persist in the shared, permissionless dispatcher.

### Proof of Concept
1. A user bridges tokens via `HyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` encoding a swap `Call[]` that (due to slippage/rounding or an incomplete call array) does not spend the full minted amount.
2. `onAccept()` mints the full amount to the `CallDispatcher`, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` [4](#0-3) , leaving a residual token balance sitting in the dispatcher after the swap completes.
3. Any third party (attacker) calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)})]))` directly — `dispatch()` has no caller check [1](#0-0)  — and transfers the residual balance to themselves.

```text
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```

```text
### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
