### Title
`calc_take_pnl` computes protocol PnL using manipulable instantaneous vault reserves, allowing accounting distortion via same-transaction swap-then-deposit/withdraw - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` derives the current "price" purely from the AMM's live vault token balances (`total_pc_without_take_pnl`/`total_coin_without_take_pnl`, i.e. `x1`/`y1`), and this function is invoked unconditionally inside `process_deposit` and `process_withdraw` — both instructions reachable by any unprivileged user in a single transaction that can also contain the four swap instructions beforehand. Because a single attacker-controlled transaction can move the spot reserves with a swap, then immediately call `Deposit`/`Withdraw` (which recomputes and commits new `calc_pnl_x`/`calc_pnl_y` baselines and `need_take_pnl_pc`/`need_take_pnl_coin`), and then reverse the swap, the pool's permanent PnL bookkeeping can be skewed at will, exactly analogous to the Zivoe `fetchBasis`/`forwardYield` issue where a manipulable spot-reserve read is used to update a persisted baseline that gates future value transfers.

### Finding Description
`calc_take_pnl` uses the AMM's real-time vault balances as `x1`/`y1` to represent "current price/reserves" and compares them against the previously stored invariant (`target.calc_pnl_x`, `target.calc_pnl_y`) to decide how much of the pool's growth should be skimmed as PnL: [1](#0-0) 

The `x1`/`y1` inputs come straight from `Calculator::calc_total_without_take_pnl_no_orderbook`, which is just `vault.amount - need_take_pnl`, i.e. the live SPL token vault balances with no TWAP, oracle, or manipulation-resistance mechanism: [2](#0-1) 

Both `process_deposit` and `process_withdraw` unpack the live vault balances and feed them directly into `calc_take_pnl` on every single call: [3](#0-2) [4](#0-3) 

The result of `calc_take_pnl` is used to permanently update `target_orders.calc_pnl_x`/`calc_pnl_y` (the invariant baseline for all future PnL comparisons) and `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin`: [5](#0-4) 

Since Solana transactions can atomically combine multiple instructions with attacker-chosen accounts and data, an unprivileged actor can: (1) execute a large `SwapBaseIn`/`SwapBaseOut` to push the coin/pc vault ratio far from the true market price, (2) call `Deposit` or `Withdraw` in the same transaction so `calc_take_pnl` computes `x1`/`y1` from the distorted reserves, and (3) reverse the swap in the same transaction. Step 2 permanently commits a new `calc_pnl_x`/`calc_pnl_y` baseline and a `need_take_pnl_pc`/`need_take_pnl_coin` increment/decrement derived entirely from the manipulated instantaneous price, exactly as `fetchBasis` was exploited to set an artificially low `basis` in the referenced report.

### Impact Explanation
Because the recorded PnL baseline (`target_orders.calc_pnl_x`/`calc_pnl_y`) and the `need_take_pnl_pc`/`need_take_pnl_coin` reserved amounts feed `Calculator::calc_total_without_take_pnl_no_orderbook`, which in turn determines the coin/pc amounts every subsequent LP receives on deposit/withdraw, a single manipulated call causes durable, incorrect pool accounting: LP share calculations become insolvent relative to actual deposited value, either siphoning value into the "need_take_pnl" bucket (effectively removed from LPs) or under-recording PnL so a future benign action distributes an inflated share. This is the same accounting-corruption class as the referenced Medium finding — a manipulable spot-reserve read used to update a persisted state variable that gates future fund distribution.

### Likelihood Explanation
The attack requires only a single attacker-funded/flash-loaned transaction containing standard, permissionless instructions (`SwapBaseIn`/`SwapBaseOut` + `Deposit`/`Withdraw` + a reversing swap) with attacker-chosen accounts — no privileged signer, off-chain component, or validator collusion is needed. `Deposit` and `Withdraw` are always reachable in normal pool states (`deposit_permission()`/`withdraw_permission()`), so `calc_take_pnl` runs on essentially every LP interaction with attacker-controllable reserve inputs.

### Recommendation
Do not derive the PnL baseline/price directly from the instantaneous vault token balances read at the top of `process_deposit`/`process_withdraw`. Consider using a time-weighted or otherwise manipulation-resistant reference price (or bounding the allowed deviation of `x1`/`y1` per transaction/slot) before it is used in `calc_take_pnl`, and/or reject deposit/withdraw processing when the observed reserve ratio has moved beyond a sane threshold within the same transaction as a swap.

### Proof of Concept
1. Attacker submits a single transaction containing: (a) a large `SwapBaseIn` (or `SwapBaseOut`) instruction against the target pool skewing `amm_coin_vault`/`amm_pc_vault` balances far from fair value; (b) a `Deposit` (or `Withdraw`) instruction on the same pool.
2. Inside `process_deposit`/`process_withdraw`, `Calculator::calc_total_without_take_pnl_no_orderbook` reads the just-manipulated `amm_pc_vault.amount`/`amm_coin_vault.amount` [6](#0-5) , producing skewed `x1`/`y1`.
3. `Self::calc_take_pnl` is invoked with these skewed values [7](#0-6) , computing a `delta_x`/`delta_y` and `need_take_pnl_pc`/`need_take_pnl_coin` far from the correct value.
4. `target_orders.calc_pnl_x`/`calc_pnl_y` are permanently overwritten using the manipulated `x1`/`y1` [5](#0-4) .
5. Attacker adds a final instruction in the same transaction to reverse the initial swap, restoring the true market price while leaving the corrupted PnL baseline and `need_take_pnl_*` state committed on-chain, degrading pool solvency/accounting for all future depositors and withdrawers.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
