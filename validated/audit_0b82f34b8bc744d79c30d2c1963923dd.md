## Title
`CallDispatcher.dispatch()` has no access control, letting any attacker drain leftover token/ETH balances held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The reported bug class is an unauthenticated function (`PeripheryPayments.approve()`) that lets any caller instruct a shared contract to move out tokens it holds. The direct analog in Hyperbridge is `CallDispatcher.dispatch()`, a public, unauthenticated entrypoint that executes arbitrary attacker-supplied calls *from the dispatcher's own context*. Because `CallDispatcher` is a single, shared contract reused across `IntentGatewayV2`, `HyperFungibleToken`/`WrappedHyperFungibleToken`, and any other app that routes calldata through it, any ERC20/ETH balance it transiently or permanently holds can be swept by an unprivileged third party.

### Finding Description
`CallDispatcher.dispatch` has no modifier restricting the caller: [1](#0-0) 

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
```

There is no `onlyGateway`, `onlyHost`, or `msg.sender` check whatsoever — the interface itself is documented as dispatching "untrusted call(s)": [2](#0-1) 

This contract is deployed once and shared across apps (per the docs, "Existing `CallDispatcher` deployments are listed on the contract addresses page"), and is invoked by `IntentGatewayV2`/`IntentsBase` for `predispatch`/`output.call` execution and by `HyperFungibleToken`/`WrappedHyperFungibleToken` for calldata execution on `onAccept`: [3](#0-2) [4](#0-3) 

The docs explicitly acknowledge the dispatcher only transiently holds tokens and that any residual balance is swept back per-order, enumerated only over the order's known `inputs`/`outputs` asset list: [5](#0-4) [6](#0-5) 

Because the sweep only covers tokens explicitly listed in `order.inputs`/`order.output.assets`, any token balance or ETH left on the dispatcher outside that enumerated set (e.g. produced by a predispatch/postdispatch swap route that yields an unlisted token, a partially-consumed swap remainder, or accidental direct transfers exploiting the dispatcher's public `receive()`) is never swept by the gateway and remains sitting on the shared, permanently-deployed `CallDispatcher` contract. Since `dispatch()` performs zero authentication, any external address can call it directly, at any time, with a crafted `Call[]` whose target is the residual token's `transfer`/`transferFrom` selector, moving that balance to themselves — exactly the "call `approve()`/steal via `transferFrom`" pattern from the reported bug, generalized to arbitrary calldata execution from a shared, always-accessible contract.

### Impact Explanation
Any unprivileged attacker can directly call the publicly-reachable, unauthenticated `CallDispatcher.dispatch()` to exfiltrate any ERC20 token balance or native ETH that the shared dispatcher is holding at the time of the call — including dust accumulated across many historical orders from every app that reuses this single dispatcher deployment. This is a concrete theft-of-funds vector reachable from a single unprivileged transaction, matching the "concrete theft of funds" acceptance bar.

### Likelihood Explanation
`CallDispatcher` is intentionally a long-lived, shared, singleton contract reused by multiple gateways/apps on a chain, and its `receive()` function accepts arbitrary incoming ETH. Any residual balance — whether from an unenumerated dust token produced by a predispatch/postdispatch swap, or from ETH/tokens sent to it outside a gateway's atomic flow — is a standing, permanently-drainable target for any attacker monitoring the contract's balance, since no caller restriction exists on `dispatch()`.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by an authorized/registered caller (e.g. an allow-listed set of gateway/app addresses configured at deployment, or an `onlyOwner`/`onlyAuthorized` modifier), or redesign the pattern so the dispatcher never retains any balance beyond a single atomic call sequence (e.g. by requiring the caller to pre-fund via `transferFrom` inside the same `dispatch()` invocation rather than relying on prior transfers, and sweeping any unenumerated residual balance back to a protocol-controlled address rather than leaving it dispatcher-resident).

### Proof of Concept
1. Observe (via on-chain state or events) that the shared `CallDispatcher` contract at a known address holds a nonzero balance of some ERC20 token or native ETH — e.g. dust left from a prior order's predispatch/postdispatch swap that was not enumerated in that order's `inputs`/`output.assets`, or a stray ETH transfer to its `receive()`.
2. Attacker calls `CallDispatcher.dispatch(encoded)` directly (no permission required) with `encoded` decoding to a `Call[]` such as:
   ```solidity
   Call[] memory calls = new Call[](1);
   calls[0] = Call({
       to: address(residualToken),
       value: 0,
       data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)
   });
   callDispatcher.dispatch(abi.encode(calls));
   ```
3. Since `dispatch()` executes the call from the dispatcher's own context (`to.call{value: call.value}(call.data)`) with no caller check, `token.transfer(attacker, residualBalance)` succeeds, transferring the dispatcher's held balance to the attacker.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
