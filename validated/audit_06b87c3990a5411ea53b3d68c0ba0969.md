## Finding: Replay-able `transfer_from` Approval in USDK Stablecoin Example Allows Repeated Draining of Approved Funds

### Title
Non-incrementing nonce in `usdk::transfer_from` allows signature replay to drain approved balances - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
The external report describes `addGasFee` stealing tokens because the pull-payment authority relied on caller-supplied parameters instead of an unforgeable, single-use authorization. The Aptos-native analog is `stablecoin::usdk::transfer_from`, an EIP-2612-style "permit" pull-transfer that authorizes a `spender` to move tokens out of `from`'s primary fungible store based on a signed `Approval` message. The custody invariant it must uphold — "a single signed approval authorizes exactly one transfer of `amount`" — is broken because the nonce embedded in the signed message is the account's global transaction `sequence_number`, which `transfer_from` never consumes or increments.

### Finding Description
`transfer_from` builds the message to verify as: [1](#0-0) 

```
let expected_message = Approval {
    owner: from,
    to: to,
    nonce: account::get_sequence_number(from),
    chain_id: chain_id::get(),
    spender: signer::address_of(spender),
    amount,
};
account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);
...
primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
```

`account::get_sequence_number(from)` reads the account's normal on-chain transaction sequence number, which is only advanced by the Aptos transaction prologue/epilogue when `from` itself submits a transaction as sender (`transaction_validation`/`account::increment_sequence_number` friend-only paths). `transfer_from` itself never bumps this counter, and there is no separate per-approval nonce, expiry, or one-time-use marker recorded anywhere in `usdk.move`.

Consequently, once `from` signs one `Approval` message for a given `sequence_number`, that exact `proof` bytes remain valid for every subsequent call to `transfer_from` with the same `owner`/`to`/`spender`/`amount`/`chain_id` until `from`'s sequence number changes for an unrelated reason (i.e., `from` sends its own transaction). Any account that is a passive holder — for example a resource account, an object-owned account, a custody wallet that never itself originates transactions, or simply a user who has not transacted since signing — will have a static sequence number, so the `spender` (or anyone who obtains the `proof`) can call `transfer_from` repeatedly, draining `amount` out of `from`'s primary store on each call instead of the single authorized transfer.

The `assert_not_paused` / `assert_not_denylisted` checks in [2](#0-1)  do not address this: they only gate global pause/denylist state, not per-approval replay. The `TransferRef`-based transfer bypasses the frozen flag by design and moves real balance via `primary_fungible_store::transfer_with_ref`, exactly mirroring the unrestricted `safeTransferFrom` pull in the Solidity report.

### Impact Explanation
This corrupts the custody accounting of the fungible-asset primary store: the corrupted value is the balance field of `from`'s `FungibleStore` (via `ConcurrentFungibleBalance`), which is decremented multiple times beyond the single `amount` the owner authorized, moving funds to `to`/`spender` without further owner consent. Because `usdk` is a stablecoin template with mint/burn/freeze authority intended for production reuse, any deployment based on this pattern permits unauthorized, repeated draining of user funds — a direct custody-grade theft impact identical in class to the reported `addGasFee` issue (unauthorized `transferFrom`-style pull of approved tokens).

### Likelihood Explanation
Exploitation requires only that the attacker (the `spender`, or anyone who intercepts/receives the signed `proof`, e.g., off-chain via a dApp or relayer flow typical of permit-style transfers) resubmits the same `transfer_from` call multiple times. No signer key, admin role, or race condition is needed — only that `from`'s sequence number has not changed since signing, which is the common case for object/resource accounts and inactive wallets. This is a straightforward, deterministic replay, not a probabilistic race, so likelihood is high for any account that is not simultaneously actively transacting.

### Recommendation
Do not reuse the transaction `sequence_number` as an approval nonce. Introduce a dedicated, monotonically increasing (or single-use) nonce/allowance resource stored under the `Management`/`State` object per `(owner, spender)`, explicitly incremented or consumed inside `transfer_from` before or after the transfer succeeds, and include an expiration timestamp in the signed `Approval` message. Reject any `proof` whose nonce does not match the currently stored expected nonce for that owner/spender pair.

### Proof of Concept
1. Owner `A` (e.g., a resource account or dormant wallet with `sequence_number = 5`) signs an `Approval{owner: A, to: B, nonce: 5, chain_id, spender: S, amount: 1000}` intending to authorize a single transfer of 1000 USDK to `B` via relayer `S`.
2. `S` calls `usdk::transfer_from(S, proof, A, scheme, pubkey, B, 1000)`. It succeeds: `account::verify_signed_message` matches because `A`'s sequence number is still `5`; 1000 USDK moves from `A` to `B`.
3. Because `A` never itself submits a transaction, `A`'s sequence number remains `5`.
4. `S` calls `usdk::transfer_from` again with the identical `proof`, `from = A`, `to = B`, `amount = 1000`. The `Approval` message reconstructed inside the function is byte-identical to the one originally signed (nonce is still `5`), so `verify_signed_message` succeeds again, and another 1000 USDK is drained from `A`.
5. Step 4 can be repeated until `A`'s store is empty, with no additional signature from `A`.
