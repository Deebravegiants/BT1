## Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook purely by validating an HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that the handler uses to attribute the payload to a specific merchant are read from HTTP headers that are **not included** in the signed content. Anyone who can obtain one valid `(raw_body, hmac)` pair — trivially, by installing the app on their own store and receiving a real webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The request still passes HMAC validation, and the handler receives attacker-controlled data labeled as belonging to the victim shop.

### Finding Description
The `Registry.process` method treats a webhook as authentic solely based on HMAC validity: [1](#0-0) 

`HmacValidator.validate` computes/verifies the signature only over `to_signable_string`, which for `Webhooks::Request` is defined to be the raw body alone: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` — the values used to route and attribute the payload — are pulled straight from HTTP headers that are not part of the signable string at all: [3](#0-2) 

These unauthenticated header values are then handed directly to the app's webhook handler as the tenant identity: [4](#0-3) 

This breaks the identity binding: `shop asserted by HMAC-verified sender` should equal `shop the handler acts on`, but here `hmac covers body only` ≠ `shop used for tenant attribution`. Because the HMAC secret (`api_secret_key`) is shared across all shops installing the same app, a valid `(body, hmac)` pair generated for one tenant (the attacker's own store) is cryptographically indistinguishable, at the `process` layer, from a pair meant for any other tenant — the header claiming *which* tenant it belongs to is never checked against the signature.

### Impact Explanation
An unprivileged user who installs the vulnerable app on their own (attacker-controlled) Shopify store can:
1. Trigger a real webhook delivery to capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared secret.
2. Replay that exact body/HMAC pair to the app's public webhook endpoint, changing only the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header to point at a victim merchant's shop domain.
3. `HmacValidator.validate` still succeeds (it never inspects the shop header), so `Registry.process` invokes the app's handler with `WebhookMetadata` claiming the payload originated from the victim shop.

Depending on how the host application's handler uses `data.shop` (e.g., to look up the victim's session/access token and act on their behalf, update local per-shop state, or trigger `app/uninstalled`-style side effects), this allows a cross-tenant data injection / cross-tenant state corruption primitive purely from the gem's own webhook-processing API — meeting the "cross-tenant access" bar for a Critical finding.

### Likelihood Explanation
Likelihood is high for any app that: (a) uses `ShopifyAPI::Webhooks::Registry.process` as documented, and (b) is installable by arbitrary merchants (including the attacker's own test store), which is the normal operating model for public/embedded Shopify apps. No access token, secret, or privileged account is required — only a normal, self-service app install and the ability to POST to the app's own public webhook route.

### Recommendation
Bind the `shop` (and ideally `topic`) into the HMAC-covered content, or otherwise cryptographically tie the header-derived shop domain to the signed payload before it is trusted — e.g., by validating the header shop domain against the shop already recorded for a previously-verified session/webhook registration rather than trusting it as an assertion. At minimum, document (and, better, enforce) that `Registry.process`/`Webhooks::Request` provides message integrity but not a signed shop identity, and require host apps to cross-check `data.shop` against an independently established per-shop registration before acting on it.

### Proof of Concept
1. Install the app on attacker-owned store `attacker.myshopify.com`; trigger any registered webhook topic (e.g. `orders/create`) to capture the real request body `B` and header `X-Shopify-Hmac-Sha256: H`.
2. Send a forged HTTP POST to the app's public webhook route:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim.myshopify.com
   x-shopify-webhook-id: <any>
   x-shopify-api-version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because `H` correctly signs `B` (see `to_signable_string` returning only `@raw_body`), and then invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)` — data attacker fully controls, attributed to a shop the attacker does not own.
