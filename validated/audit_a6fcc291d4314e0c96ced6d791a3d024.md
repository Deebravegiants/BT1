## Title
Front-running griefing of `LockupFactory::create` permanently blocks legitimate lockup creation for a target owner - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` in `lockup-factory/src/lib.rs` derives the deterministic sub-account name for the new lockup contract solely from the caller-supplied `owner_account_id`, via `sha256(owner_account_id)`, and never binds it to `env::predecessor_account_id()` or any creator-specific value. [1](#0-0) 
Because this function is `#[payable]` and callable by any unprivileged account, an attacker can pre-compute the target lockup account name for any known/expected `owner_account_id` and submit their own `create` call (front-running, or simply racing, the legitimate funder) to occupy that NEAR sub-account first.

### Finding Description
The lockup account ID is computed as:
```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [1](#0-0) 
This mirrors the reported `BatonLaunchpad.create`/`LibClone.cloneDeterministically` issue: a deterministic deployment address/account is derived only from attacker-controllable/public input (here, `owner_account_id`) with no binding to `msg.sender`/predecessor. Any account can call `create` for an arbitrary `owner_account_id` with the minimum attached deposit, causing `Promise::new(lockup_account_id).create_account()` to succeed first for that name. [2](#0-1) 
Since NEAR account names are globally unique and cannot be recreated once they exist, any subsequent legitimate `create` call for the same `owner_account_id` (e.g., by the NEAR Foundation or a funding account) will have its `create_account()` action fail, and the callback `on_lockup_create` simply refunds the deposit and returns `false`. [3](#0-2) 
Because the account slot is permanently occupied (it cannot be deleted/recreated for the same `owner_account_id`, as the name depends only on that ID), this is not a one-time revert but a **permanent** denial of the ability to create the canonical lockup contract for that owner via this factory. An attacker could also front-run with a hostile/minimal `vesting_schedule`, `lockup_duration`, or `release_duration` to occupy the slot with a deceptive, mis-configured lockup contract nominally "owned" by the victim (since `owner_account_id` is attacker-chosen to be the victim's account), while paying only their own attached deposit.

### Impact Explanation
This is a permanent, unrecoverable griefing of the lockup creation flow for a specific owner: the intended owner/funder can never deploy their real lockup contract at the expected deterministic address through this factory once griefed, since NEAR account names cannot be reclaimed. This matches the account-binding/front-running failure class in the deterministic-address creation flow.

### Likelihood Explanation
`create` is a public, unprivileged, payable method requiring only the `MIN_ATTACHED_BALANCE` (3.5 NEAR) deposit. [4](#0-3) 
Any address that can guess or observe a target `owner_account_id` (e.g., known token-recipient accounts, or by watching the mempool for a pending `create` transaction) can front-run it cheaply, with the only cost being the attacker's own attached deposit sent to the occupied account.

### Recommendation
Bind the deterministic lockup account name to the funding party's identity or to a fresh, contract-controlled nonce (e.g., incorporate `env::predecessor_account_id()` and/or an incrementing counter into the hash input), so that an unrelated account cannot preemptively occupy the sub-account intended for a specific owner/funder pair. Alternatively, allow multiple lockup accounts per `owner_account_id` (e.g., suffix with an index), or require that only a specifically authorized funder (matching `owner_account_id` or a foundation-approved list) can create the lockup for that owner.

### Proof of Concept
1. Attacker observes (or predicts) that `owner_account_id = "victim.near"` will have a lockup created via `lockup-factory`.
2. Attacker computes `lockup_account_id = hex(sha256("victim.near")[..20]) + "." + <factory_account>`.
3. Attacker calls `create({owner_account_id: "victim.near", lockup_duration: <arbitrary>}, attached_deposit: 3.5 NEAR)` before the legitimate funder's transaction lands. The account gets created at `lockup_account_id`. [5](#0-4) 
4. When the legitimate funder later calls `create` with the same `owner_account_id`, `create_account()` fails because the account already exists; `on_lockup_create` refunds their deposit and the call returns `false`. The legitimate lockup for `"victim.near"` can never be created at the canonical address through this factory again. [3](#0-2)

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
