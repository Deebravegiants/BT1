### Title
Webhook shop-domain, topic and webhook-id are trusted by handlers without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the raw request body only, then dispatches the handler using the `topic`, `shop`, `webhook_id`, and `api_version` values taken verbatim from HTTP headers that are never covered by that HMAC. This breaks the intended binding: `HMAC-verified bytes (raw_body) == identity bytes used for dispatch/attribution (shop-domain, topic, webhook-id headers)`. Anyone who can obtain one genuine `(raw_body, hmac)` pair from the app (trivially available to any unprivileged attacker who installs the app on their own store) can replay that exact body with **attacker-chosen** `shop-domain`, `topic`, and `webhook-id` headers and still pass validation.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives all identity fields from headers that are excluded from the signed content: [1](#0-0) 

Only `@raw_body` is returned by `to_signable_string`, so `topic`, `shop`, `webhook_id`, and `api_version` are not part of what is HMAC-verified.

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., it verifies the body bytes only: [2](#0-1) 

`Registry.process` then uses the unauthenticated header-derived `request.topic` and `request.shop` to select the handler and construct the metadata object that the handler acts on: [3](#0-2) 

That metadata (including `shop`) is exactly what host application handlers rely on for tenant attribution: [4](#0-3) 

Since `api_secret_key` is shared across all shops that install the same app (it is not per-shop), an attacker only needs to be an unprivileged merchant who installs the app on their own store to receive a genuine `(raw_body, hmac)` pair signed with the app's real secret. They can then replay that exact body to the app's public webhook endpoint while freely setting `x-shopify-shop-domain` to a victim shop, `x-shopify-topic` to any registered topic, and `x-shopify-webhook-id` to any value. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret, and `Registry.process` will happily route this attacker-controlled event, with attacker-controlled `shop`/`topic`/`webhook_id` metadata, to the handler as if it were a genuine Shopify-originated event for the victim tenant.

This matches the report's underlying bug class precisely: the value used to select/attribute the event (`shop`, analogous to the TSS public key) is not included in the data covered by the integrity check (the HMAC, analogous to the vote hash), so the last-mile identity used for dispatch can be substituted freely by anyone who can produce one valid `(body, hmac)` pair.

### Impact Explanation
This crosses the tenant boundary that `ShopifyAPI::Webhooks::Registry` is meant to enforce: any handler implementation that trusts `WebhookMetadata#shop` for tenant/session lookup (the documented and expected usage pattern per `docs/usage/webhooks.md`) can be made to attribute attacker-supplied webhook data to an arbitrary victim shop, or to invoke a handler for a topic the body was never actually generated for (e.g., replaying an `orders/create` body against a `customers/redact` or `app/uninstalled` handler), producing type-confused/forged business data injected under another tenant's identity. This falls under cross-tenant access, one of the defined Critical impacts.

### Likelihood Explanation
Requires no privileged credentials, tokens, or `api_secret_key` knowledge—only the ability to install the app once (any developer/merchant can do this for free) to harvest a single legitimate `(body, hmac)` pair, then freely replay it with forged headers to the app's own public webhook URL. This is directly reachable through the gem's documented `Registry.process` / `Request.new` API exactly as instructed in `docs/usage/webhooks.md`, not through any misuse of the gem by the host app.

### Recommendation
Bind the identity headers into the signed/verified content, e.g., include `shop-domain`, `topic`, and `webhook_id` in the signable string computed by `Request#to_signable_string`, or otherwise cryptographically bind them to the raw body before `Registry.process` uses them for handler dispatch and metadata construction.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (no privileges required) and triggers any subscribed webhook topic, capturing the raw POST body and its `x-shopify-hmac-sha256` header — both are valid because they were genuinely signed by the app's `api_secret_key`.
2. Attacker POSTs the exact same `raw_body` to the app's webhook endpoint again, but this time sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <any topic the app registered a handler for>`
   - `x-shopify-webhook-id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request.new` accepts these headers, and `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (unchanged) with the shared secret:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
4. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and `topic` set to the attacker's chosen value, even though neither was ever part of what Shopify (or the attacker, replaying it) actually had a valid signature for.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
