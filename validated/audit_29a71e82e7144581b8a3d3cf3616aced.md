### Title
Missing length validation on `Message.from` causes runtime panic during cross-chain mint dispatch - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` in the `hyper-fungible-token` module ISMP handler decodes an attacker-controlled cross-chain payload (`Message::abi_decode(&body)`) and later slices/copies `message.from` into a fixed-size buffer without validating its length first, unlike the sibling `message.to` field which is explicitly length-checked. A crafted request whose `from` field is shorter than expected drives an unguarded subtraction/slice/`copy_from_slice` that panics, mirroring the out-of-bounds-read/DoS pattern behind CVE-2016-9264 (buffer overflow in an unvalidated-length header field of a parser).

### Finding Description
`on_accept` is the `IsmpModule::on_accept` handler invoked whenever a `PostRequest` destined for this pallet is delivered through pallet-ismp's dispatch/handler path — i.e., reachable by any relayer delivering a message that originated from a registered source contract [1](#0-0) .

For the `to` recipient bytes, the code explicitly validates the length is either 32 or 20 bytes and returns a typed error otherwise: [2](#0-1) 

But for the `from` bytes used to derive the calldata-dispatch origin (used only when `message.data` is non-empty and no `substrate_data.signature` was supplied), there is no equivalent length check:
```
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [3](#0-2) 

- If `source.is_evm()` and `from_bytes.len() < 20`, the expression `from_bytes.len() - 20` underflows a `usize`. In debug builds this panics with "attempt to subtract with overflow"; in release builds it wraps to a huge index which is then used to slice `from_bytes`, causing a slice-index-out-of-bounds panic.
- In the substrate branch, `account.copy_from_slice(from_bytes)` panics outright if `from_bytes.len() != 32` (the standard `copy_from_slice` length-mismatch panic).

`message.from` is decoded from `body`, which is the fully attacker/relayer-controlled ABI-encoded payload of the ISMP `PostRequest` — the same body a user dispatching a token-bridge transfer from the source chain controls, since it is used elsewhere in this same struct as ABI `bytes` (evidenced by the explicit variable-length handling done for the sibling `to` field). Nothing else in this function validates `message.from`'s length before this arithmetic/copy occurs.

### Impact Explanation
A crafted `body` (an out-of-bounds/underflow-triggering `from` length) causes the runtime to panic while executing `on_accept`, which is invoked from pallet-ismp's message handling path during normal request delivery. A panic during extrinsic execution inside a FRAME pallet call is a chain-halting/DoS condition (or at minimum causes that transaction's whole block execution logic to fail unexpectedly), a permanent denial-of-service risk analogous to the CVE's "out-of-bounds read" DoS impact, and reachable without any privileged role — any token bridger/relayer delivering a message with a malformed `from` field can trigger it.

### Likelihood Explanation
High for any state machine using this module: the malformed `from` field is entirely attacker-controlled inside the cross-chain payload, requires no privileged access, and is delivered via the standard, permissionless relaying flow (submit proof → pallet-ismp handles unsigned request → `on_accept` dispatch). No signature or authorization gate protects the vulnerable branch — it is on the default "no-signature, calldata-present" path.

### Recommendation
Validate `message.from`'s length (must be exactly 20 for EVM or exactly 32 for substrate, matching the pattern already used for `message.to`) and return a typed `HftError` instead of performing raw arithmetic/`copy_from_slice`/`H160::from_slice` on unchecked length input.

### Proof of Concept
1. On the source EVM chain, dispatch an ISMP `PostRequest` to the hyper-fungible-token module whose ABI-encoded `body` decodes to a `Message` with: `data` non-empty, `substrate_data.signature = None`, and `from` set to a byte string shorter than 20 bytes (e.g., 1 byte) when the local state machine handling is EVM-sourced, or any length ≠ 32 when substrate-sourced.
2. Relay/deliver this request through the normal permissionless relaying flow so pallet-ismp calls `Pallet::on_accept`.
3. Execution reaches `let from_bytes = message.from.as_ref(); ... &from_bytes[from_bytes.len() - 20..]` (or the substrate `copy_from_slice`), triggering an arithmetic-underflow/slice-index panic and aborting execution — no error is returned, unlike the length-checked `to` field.
