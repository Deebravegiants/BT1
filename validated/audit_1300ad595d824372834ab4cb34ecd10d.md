### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives both the HMAC signature and the `shop` tenant identifier from the incoming HTTP request, but only the raw body is included in the signed payload. The `shop-domain` header used to attribute the webhook to a specific merchant is never part of the HMAC computation, so its authenticity is never verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the request purely against that signable string via `Utils::HmacValidator.validate(request)` [2](#0-1) . `HmacValidator` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `Context.api_secret_key` [3](#0-2) . Because `api_secret_key` is the app's single client secret shared across every installed shop, any HMAC value that is valid for one shop's webhook body is equally valid for the same body sent under a different `shop-domain` header — the signature carries no binding to `shop`.

Despite this, immediately after HMAC validation, `Registry.process` reads `request.shop` (sourced solely from the `x-shopify-shop-domain`/`shopify-shop-domain` header, see `Request#shop` [4](#0-3) ) and passes it straight into `WebhookMetadata` as the trusted tenant identifier for the handler: [5](#0-4) . `WebhookMetadata.shop` is a plain `String` field with no additional validation [6](#0-5) .

The broken identity binding, as an equality: `shop (header, attacker-controlled)` ≠ `shop (bound by the HMAC that was actually verified)` — the HMAC only proves "signed by an app-secret holder," not "signed for this particular shop."

### Impact Explanation
Any merchant who has installed the app can capture one legitimate HMAC+body pair delivered to their own webhook endpoint (they are the intended, unprivileged recipient of their own webhooks). By replaying that exact body and HMAC while substituting the `x-shopify-shop-domain` header with a different merchant's `myshopify.com` domain, they produce a request that passes `HmacValidator.validate` yet is attributed by `Registry.process`/`WebhookMetadata` to the victim shop. Any host application that trusts `data.shop` from the webhook handler (as the gem's own documentation instructs: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-supplied webhook content as if it originated from another tenant — a cross-tenant data-integrity/access issue reachable by an unprivileged internet user (any app-installing merchant) without ever needing the app's `client_secret` or another merchant's access token.

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged user of the multi-tenant app (i.e., install it on their own store to receive at least one real webhook), which is trivial for any public app. No credentials beyond normal merchant access are required, and the header substitution is a simple HTTP replay.

### Recommendation
Bind the shop identity into the value that is actually verified. At minimum:
- Do not treat `request.shop` as trusted unless it can be cross-checked against a shop known to be associated with the specific webhook subscription/access token (e.g. via a per-shop webhook secret, or by validating the `shop` against a shop record retrieved independently, not the header echoed back by the sender).
- Where feasible, include the shop domain in the signed payload used for `to_signable_string`, or require the host application to independently confirm shop ownership before trusting `WebhookMetadata#shop`.
- Document clearly (and enforce in code where possible) that `data.shop` is HMAC-unverified and must not be used as a sole tenant boundary.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook handler, receiving a real webhook: body `B`, header `x-shopify-hmac-sha256: H`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — this still matches because `to_signable_string` never includes the shop header [7](#0-6) [8](#0-7) .
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and invokes the registered handler, which the host app trusts as if Shopify itself had confirmed the webhook came from `victim-shop.myshopify.com` [5](#0-4) .
