## Title
Decimal-scaling functions in `pallet-hyper-fungible-token` silently skip conversion when local decimals exceed EVM decimals, enabling unbacked minting on the receiving chain - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers (`convert_to_erc20` / `convert_to_balance`) only implement scaling for the case `erc_decimals >= local_decimals`. When a registered asset has more decimals on the Substrate side than on the EVM side, `saturating_sub` silently produces a scale factor of `10^0 = 1`, so the raw balance is passed through unscaled in the wrong direction. This is the same decimal-normalization root cause as the referenced Wormhole/Olas finding: an amount is transformed between two different-precision domains, and the code assumes the transform is always "scale up," never validating or handling the opposite case, causing state on one chain to diverge from the value actually locked/burned on the other.

### Finding Description
The conversion helpers are defined in [1](#0-0) :

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions use `erc_decimals.saturating_sub(local_decimals)` as the exponent. This is correct only when `erc_decimals >= local_decimals` (e.g. the documented `BridgeToken` case: nexus 12 decimals → EVM 18 decimals, `HyperFungibleToken` README notes `_decimals` are configured per `(AssetId, StateMachine)` via `Precisions` [2](#0-1) ). If instead `local_decimals > erc_decimals` for a registered asset/chain pair, `saturating_sub` returns `0`, so both functions degrade to a no-op multiplier of `1` — the raw numeric value crosses the chain boundary completely unscaled instead of being divided down.

This is directly reachable by any signed account through the public `send` extrinsic, which computes the outgoing ERC20 amount via `convert_to_erc20(amount, erc_decimals, decimals)` after escrowing/burning the local asset at `decimals` precision [3](#0-2) . On the receiving side, `on_accept` performs the inverse conversion via `convert_to_balance(..., erc_decimals, decimals)` before minting/releasing to the beneficiary [4](#0-3) , and `on_timeout` uses the same helper to compute refunds [5](#0-4) .

`local_decimals` here is not a fixed constant — for non-native assets it is read straight from `fungibles::metadata::Inspect::decimals(local_asset_id)` [6](#0-5) , while `erc_decimals` is an independently configured `Precisions` value set at `register_token`/`update_token` time [7](#0-6) . There is no invariant enforced anywhere that `erc_decimals >= local_decimals`; a normal (non-malicious) registration of an asset whose Substrate-side decimals are higher than the paired EVM contract's decimals is a legitimate, expected configuration for many real tokens.

### Impact Explanation
When `local_decimals > erc_decimals` for a registered asset:
- On `send()`, the user's locally-denominated `amount` (say, `100 * 10^local_decimals` raw units) is passed to the destination chain unscaled instead of being divided by `10^(local_decimals - erc_decimals)`. The EVM-side `HyperFungibleToken`/`WrappedHyperFungibleToken` contract mints/unlocks `amount` interpreted at `erc_decimals` precision — inflating the credited value by a factor of `10^(local_decimals - erc_decimals)`.
- Symmetrically, on `on_accept`/`on_timeout`, an ERC20-denominated amount coming from the EVM side is divided by `1` instead of being multiplied up, under-crediting the beneficiary/refund recipient by the same factor.

The mint-side direction (`send()` from Substrate to EVM) results in tokens being minted or released on the destination chain vastly exceeding what was escrowed or burned on the source chain — an unbacked-mint condition that lets an attacker drain the destination-side custody/liquidity by escrowing a negligible amount locally and redeeming an inflated amount remotely. This satisfies the "unbacked mint" / concrete theft criterion.

### Likelihood Explanation
This requires only a single ordinary `send` extrinsic call by any account holding (or able to acquire) the affected asset — no malicious governance action is required to trigger the bug; the misconfiguration condition (`local_decimals > erc_decimals`) is a plausible, non-adversarial registration outcome for tokens whose Substrate-side precision is higher than their EVM counterpart's, and nothing in `register_token`/`update_token` validates or rejects this ordering. Once such an asset exists, every subsequent `send()` call to that chain silently mis-scales, so the bug is deterministic and repeatable, not a one-off edge case.

### Recommendation
Make both `convert_to_balance` and `convert_to_erc20` handle both directions explicitly instead of relying on `saturating_sub` collapsing to zero:
```rust
if erc_decimals >= local_decimals {
    value * 10^(erc_decimals - local_decimals)   // or / for convert_to_balance
} else {
    value / 10^(local_decimals - erc_decimals)   // or * for convert_to_balance
}
```
Additionally, consider validating at `register_token`/`update_token` time that the configured `erc_decimals` is sane relative to the local asset's decimals, and add symmetric round-trip tests (`convert_to_erc20` followed by `convert_to_balance`, and vice versa) covering `local_decimals > erc_decimals`.

### Proof of Concept
1. Governance (or any `CreateOrigin`) registers a non-native asset `X` with local (Substrate) decimals `18` (typical for `pallet-assets` EVM-style tokens) and `Precisions[X][EVM-chain] = 6` (the paired ERC20 contract genuinely uses 6 decimals).
2. A user calls `send(params)` with `params.amount = 1 * 10^18` (i.e., "1 X" in local units).
3. In `lib.rs::send`, `decimals = 18`, `erc_decimals = 6`. `convert_to_erc20(1e18, 6, 18)` computes `10^(6.saturating_sub(18)) = 10^0 = 1`, so `erc20_amount = 1e18` is sent as-is [8](#0-7) .
4. On the EVM chain, the destination `HyperFungibleToken` contract interprets `1e18` at its native 6-decimal precision — i.e., `1,000,000,000,000 X` tokens (a 10^12 inflation) — and mints/unlocks that amount to the recipient, while only `1 X` (in 18-decimal local units) was actually escrowed/burned on the Substrate side.
