### Title
Bounded state-machine commitment cap evicts commitments needed by in-flight relayed messages before they can be verified - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s `insert_bounded_state_commitment` stores each newly finalized `StateCommitment` in a fixed-size, per-`StateMachineId` FIFO ring buffer (`BoundedStateCommitments`/`StateCommitmentQueue`) and evicts the oldest entries purely by insertion count once a configurable cap is exceeded [1](#0-0) . Eviction is triggered solely by the number of consensus updates recorded, with no check on whether the challenge period for a given height has elapsed, or whether any pending relayed request/response/timeout message still needs a membership/non-membership proof against that specific height. This is the same bug class as the Gondi finding: a fixed bound (`_LOAN_BUFFER_TIME`/`getMinTimeBetweenWithdrawalQueues`) that assumes a bounded rate of external events, but does not actually bound the rate at which those events (auction bids / consensus updates) can occur, so state needed later gets overwritten/evicted prematurely.

### Finding Description
`update_client`/`handleConsensus` consensus message submission is permissionless — any relayer can submit valid consensus proofs advancing a counterparty state machine's height [2](#0-1) . Each successful update calls `insert_bounded_state_commitment`, which pushes the new height onto `StateCommitmentQueue` and evicts the oldest entries (up to `MAX_COMMITMENT_EVICTIONS_PER_INSERT` per call) once `tail - head` exceeds the state machine's configured cap (`state_machine_commitment_cap`, default `MAX_STATE_MACHINE_COMMITMENTS` unless overridden by `StateCommitmentCap`) [3](#0-2) .

Crucially, the eviction condition is purely count-based — it does not consult `challenge_period`, `verify_delay_passed`, or whether any outstanding `Request`/`Response`/`Timeout` message batch still targets that height for a membership or non-membership proof. `handlers::validate_state_machine`/`verify_delay_passed` (and the EVM `HandlerV2` equivalent) require the challenge period to have elapsed before a proof at a given height can be processed [4](#0-3) , meaning proofs against a given height are *expected* to be submitted and processed only after that delay — a window during which more consensus updates (and therefore more evictions) can and will occur. If a relayer (malicious or otherwise) drives a burst of consensus updates — or simply, in a period of higher block/finality throughput on the counterparty chain than the operator anticipated when picking the commitment cap — more than `cap` heights are recorded within the challenge-period window, older `StateCommitment`/`update_time` entries for heights still awaited by legitimate, already-signed-and-in-flight request/response/timeout proofs are deleted (`BoundedStateCommitments::remove`, `BoundedStateMachineUpdateTime::remove`) before those proofs are submitted.

This mirrors the Gondi root cause exactly: a static assumption about "how much time/how many events fit inside a fixed slot" (`_LOAN_BUFFER_TIME` vs. actual auction-extension rate) is violated by an entity (bidder / relayer) that is not bound by that assumption, causing the on-chain record the later step depends on (`pendingQueues` / `StateCommitment`) to be destroyed prematurely.

### Impact Explanation
Once a height's `StateCommitment`/update-time is evicted, `state_machine_commitment(height)` returns `Err`/`StateCommitmentNotFound`, and any relayed `RequestMessage`/`ResponseMessage`/`TimeoutMessage` proof built against that height can never be verified — it is not merely delayed but permanently undeliverable, since the specific overlay/state root it needs no longer exists anywhere in the pallet's storage (the height was never re-finalized with the same root). This is a "route unable to deliver messages" outcome per the validation rules: outgoing/incoming cross-chain messages relying on that evicted height are permanently stuck, and any relayer fee escrowed for their delivery becomes permanently unclaimable, i.e., a fund-freezing condition. Because the eviction is FIFO-by-count with no floor tied to challenge period or pending-proof awareness, an attacker who can push consensus updates faster than the configured cap tolerates (or simply exploit an operator-misconfigured low cap) can deterministically engineer this outcome against a target request/response.

### Likelihood Explanation
Consensus-message submission is permissionless (any relayer can submit a valid consensus proof once available), so triggering many rapid updates costs only the relayer's own submission cost and does not require any protocol-side approval. The cap (`MAX_STATE_MACHINE_COMMITMENTS` / per-chain override via `StateCommitmentCap`) is a fixed operator-chosen constant, unrelated to the counterparty chain's actual block/finality rate or to the configured `challenge_period`; nothing in the code enforces `cap ≥ (challenge_period / block_time) + safety_margin`. On fast-finalizing counterparties (e.g., short block times or bursts of finality catch-up messages after downtime, which the codebase's own `next_consensus_update`/BSC epoch-rotation code shows can enqueue several updates per batch), the number of heights recorded within one challenge period can plausibly exceed a conservatively-sized cap, especially for a determined attacker deliberately spamming update submissions to grief specific pending messages.

### Recommendation
- Size the eviction floor dynamically: do not evict a queued height until `current_timestamp - update_time(height) > challenge_period(state_machine)` for that height (mirroring `verify_delay_passed`), regardless of the FIFO count, or alternatively refuse to evict heights that have not yet cleared the challenge period even if the numeric cap is exceeded (allow the queue to temporarily grow past `cap` instead).
- Cross-check outstanding pending request/response commitments' `proof.height` against the eviction candidate list before removing a `BoundedStateCommitments` entry, or expose an explicit "pinned height" mechanism relayers can use to protect in-flight proofs.
- Alternatively/additionally, derive `MAX_STATE_MACHINE_COMMITMENTS` per counterparty from its configured `challenge_period` and expected block time with an explicit safety margin, and validate at `update_commitment_caps` call time that the configured cap is not obviously undersized relative to `challenge_period`.

### Proof of Concept
1. Configure (or use default) `MAX_STATE_MACHINE_COMMITMENTS = N` for state machine `S`, with `challenge_period(S) = T` seconds.
2. A user dispatches a `PostRequest` targeting `S`; a relayer begins constructing a membership/non-membership proof for a specific finalized height `H` of `S` (must wait until `T` has elapsed per `verify_delay_passed` before submitting).
3. During the `T`-second window, an attacker (any permissionless relayer) submits `> N` valid consensus updates for `S` (e.g. replaying consecutive finalized headers/epoch rotations in quick succession), each calling `insert_bounded_state_commitment` and advancing `StateCommitmentQueue`'s tail.
4. Once the queue's `tail - head` exceeds `N`, `insert_bounded_state_commitment` evicts the oldest entries including height `H`, removing `BoundedStateCommitments::<T>::remove(id, H)` and `BoundedStateMachineUpdateTime::<T>::remove(id, H)` [5](#0-4) .
5. The legitimate relayer submits the previously-prepared proof for height `H`; `state_machine_commitment(H)` now returns `StateCommitmentNotFound`, so `validate_state_machine`/proof verification fails permanently — the request can never be delivered nor timed out through this height, and any escrowed relayer fee for it is stuck.

	impl<T: Config> Pallet<T> {
		/// Number of state commitments retained for `id`: the
		/// [`StateMachineCommitmentCap`] override if set, otherwise
		/// [`MAX_STATE_MACHINE_COMMITMENTS`].
		pub fn state_machine_commitment_cap(id: StateMachineId) -> u32 {
			StateMachineCommitmentCap::<T>::get(id).unwrap_or(MAX_STATE_MACHINE_COMMITMENTS)
		}

		/// Insert a state commitment into the bounded map. ISMP does not allow
		/// duplicate state updates so we don't have an overwrite path.
		///
		/// Appends the height to the per-chain [`StateCommitmentQueue`] and, once
		/// the chain's cap is exceeded, evicts oldest-first from the queue head.
		/// Evictions are limited to [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per
		/// call so a lowered cap drains over many insertions rather than in one.
		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}

The `update_client` method is responsible for advancing the state of the consensus client. This performs the consensus verification of new `StateCommitment`s that have been finalized by a `StateMachine`'s consensus system. The `IsmpHost` must return the concrete implementation of the associated `ConsensusClient` and a previously stored `ConsensusState`. The procedure for updating the consensus client is as follows.

- First the handler must assert that the consensus client is not frozen or expired. Consensus clients can expire if the last time the consensus client was updated has exceeded the chain's unbonding period. This effectively mitigates any potential long fork attacks that may arise due to a loss of liveness of consensus clients.
- Finally the handler may perform consensus proof verification using the concrete implementation for the consensus client using `ConsensusClient::verify_consensus`. If verifications pass, the udpated `ConsensusState` and `IntermediateState`s are persisted to storage and enter a new challenge period.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
