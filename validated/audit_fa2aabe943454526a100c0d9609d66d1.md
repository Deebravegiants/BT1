### Title
Webhook `shop` (and `topic`) attribution is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return **only the raw HTTP body**: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers, not from the signed payload: [2](#0-1) 

`Webhooks::Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (body only) and compares against `request.hmac`: [3](#0-2) [4](#0-3) 

Once the body-HMAC check passes, `request.shop` (the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) is trusted as the tenant identity and forwarded straight into `WebhookMetadata`, which the host application uses to route/act on data per-shop: [5](#0-4) 

This is exactly the bug class described in the report: the binding that should hold is `hmac_signed(shop) == shop_acted_on`, but the gem's HMAC only covers the raw body — `to_signable_string == raw_body`, while `shop == header("shop-domain")`, a field never included in the signed bytes. The two are logically independent, so the signature validity says nothing about which shop the payload belongs to.

Contrast this with the OAuth callback signature, where `shop` **is** part of the signed query and is verified as such (`AuthQuery#to_signable_string` includes `shop`), confirming that binding the tenant identifier into the signature is the intended pattern elsewhere in this gem, but it is missing for webhooks.

### Impact Explanation
Any actor capable of triggering a legitimately-signed webhook for *some* shop that has installed the app (e.g., an ordinary merchant installing the app on their own store and generating a webhook event through normal usage) obtains a `(raw_body, valid-hmac)` pair signed with the app's shared `client_secret`. Because the signature never covers the `shop` header, that same body+HMAC pair can be replayed directly to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` will report success (body bytes unchanged), and `Registry.process` will dispatch to the app's handler with `WebhookMetadata#shop` set to the victim shop. Any per-tenant action the host application performs based on that `shop` value (e.g., data updates, uninstall/redact handling, order processing keyed by shop) is now executed against the wrong tenant using attacker-supplied body content — a cross-tenant confusion/injection primitive rooted entirely in this gem's signature-verification/identity-binding design.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install (or use) the target app on any shop to obtain one valid signed webhook body, and who can send arbitrary HTTP requests to the app's public webhook receiver endpoint (which by design accepts external POSTs from "Shopify"). No access token, `api_secret_key`, or privileged account is required — only the ability to receive one real webhook and forge headers on a replayed request, both attacker-controlled steps external to this gem.

### Recommendation
Bind the tenant identity into the verified bytes: include `shop` (and ideally `topic`) in `to_signable_string`, or otherwise cryptographically bind the header-derived `shop`/`topic` values to the signed payload before they are trusted by `Registry.process`/`WebhookMetadata`, mirroring how `AuthQuery` binds `shop` into its OAuth HMAC signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (attacker-controlled) shop `attacker-shop.myshopify.com`, a normal unprivileged action.
2. Attacker triggers any subscribed webhook topic (e.g. `orders/create`) on their shop, and captures the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends to the app's webhook endpoint. This HMAC is valid because it is signed with the app-wide `client_secret`, shared across all shops using the app — see `to_signable_string` only covering `@raw_body`: [1](#0-0) .
3. Attacker POSTs the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because the signature only depends on the unchanged body: [6](#0-5) .
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`: [5](#0-4) , causing the host app to process attacker-controlled data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

        end
