### Title
Backend-issued biometric-encryption public keys (`backend_keys`) are not cryptographically bound to the QR-authenticated user session - (File: src/backend/user_status.rs)

### Summary
`backend::user_status::request` fetches a signup-backend response containing two logically separate pieces of data: an `authenticated_app_data` object (`orb_qr_link::UserData`) that *is* verified against a hash embedded in the scanned QR code, and a sibling `backend_keys` object (per-tier `public_key` + `encrypted_private_key` for iris, normalized-iris, face and tier2) that is *not* covered by that verification at all. The Orb then uses these unverified public keys to encrypt the user's raw biometric captures for the Personal Custody Package (PCP). This is the same root cause described in the external report: ciphertext/key material is not bound to the context (identity/session) it is supposed to belong to, so it can be silently substituted without detection.

### Finding Description
`backend::user_status::request` deserializes the backend response into two independent structs: [1](#0-0) 

Only the `authenticated_app_data` (`user_data`) is checked against the `user_data_hash` carried in the scanned QR code: [2](#0-1) 

The `backend_keys` field (containing `iris`, `normalized_iris`, `face`, and optional `tier2` public keys and their `encrypted_private_key` blobs) is destructured and decoded immediately afterward, with no cryptographic linkage to `identity_commitment`, `self_custody_public_key`, or the verified hash: [3](#0-2) 

These unauthenticated public keys are subsequently used, unmodified, to seal the user's actual iris/face/normalized-iris biometric captures and self-custody tiers when building the Personal Custody Package: [4](#0-3) [5](#0-4) 

The `Credentials` struct that carries these keys through the signup plan is populated straight from `UserData` with no additional binding check: [6](#0-5) [7](#0-6) 

Because `verify()` operates only on the `orb_qr_link::UserData` fields (identity_commitment, self_custody_public_key, data_policy, pcp_version, user_centric_signup, orb_relay_app_id) — a type defined in the external `orb-qr-link` crate, whose implementation is outside this repo and could not be inspected further — there is no mechanism in `orb-core` itself that ties `backend_keys.iris.public_key`, `.normalized_iris.public_key`, `.face.public_key`, or `.tier2.public_key` to the same signup/identity context that was authenticated by the QR-code hash. This mirrors exactly the audited bug class: the ciphertext-producing key material is not bound to the context it is presented alongside, so if the backend (due to a bug, race condition, cache confusion, or session mix-up under load) ever returns `backend_keys` from a different session than the one whose `authenticated_app_data`/QR hash was verified, `orb-core` has no way to detect the mismatch.

### Impact Explanation
If `backend_keys` for one signup session are ever returned/substituted for another (e.g. a backend-side session/cache bug, load-balancer routing anomaly, or a compromised/rogue backend replaying stale key material), `orb-core` will:
- Encrypt Signup A's iris, normalized-iris, and face biometric captures under Signup B's `backend_iris_public_key` / `backend_face_public_key` / etc., without any check that these keys were meant for Signup A.
- Encrypt the same PCP tiers with `self_custody_user_public_key` values that likewise are not bound to the verified identity commitment.

This can result in unauthorized biometric data disclosure to whoever controls the mismatched private key, and cross-signup state bleed (one user's biometric package becoming decryptable/attributable to another user's key material), matching the accepted impact categories (biometric data disclosure, cross-signup state bleed).

### Likelihood Explanation
Exploitation does not require a malicious peer or hardware access — it only requires the trusted signup backend to (even inadvertently) return `backend_keys` inconsistent with the verified `authenticated_app_data` for the same HTTP response (e.g., a backend-side bug, cache poisoning, or response reordering). Because `orb-core` performs no cross-check between the two structures, such a mismatch would go completely undetected and would silently propagate into the encrypted PCP artifacts. The likelihood depends on backend-side correctness/attacker capability outside this repo, which limits confidence to "reachable but conditional on an upstream data-integrity failure."

### Recommendation
- Short term: Extend the QR-code-bound hash/signature (or a new backend-provided signature) to cover the entire `backend_keys` structure (all `public_key` fields for iris/normalized_iris/face/tier2), and reject the response in `backend::user_status::request` if this verification fails — mirroring the existing `user_data.verify(user_data_hash)` check at `src/backend/user_status.rs:175`.
- Alternatively, have the backend include the `identity_commitment` (or another session-binding value) as authenticated additional data during PCP encryption, and validate it inside `personal_custody_package::Package::build` before calling `encrypt(...)` at `src/plans/personal_custody_package.rs:300-327`.
- Long term: Never assume implicit binding between independently-transmitted key material and an authenticated context; require explicit authenticated binding (AAD, signature, or MAC) whenever encryption keys and their associated identity/session data travel as separate, individually-parsed fields.

### Proof of Concept
Conceptual (network/backend-response-level) PoC, since exploitation depends on backend-side behavior outside this repo's control:
1. Backend responds to `/api/v2/session/{id}/status` (or `/api/v1/user/{id}/status`) with a JSON body where `authenticated_app_data` correctly corresponds to Signup Session A's `identity_commitment`/`self_custody_public_key` (and thus passes `user_data.verify(user_data_hash)` at `src/backend/user_status.rs:175`), but the sibling `backend_keys.iris/normalized_iris/face/tier2.public_key` values actually belong to Session B (e.g., due to a backend cache bug or concurrent-session confusion).
2. `backend::user_status::request` accepts the response because only `user_data` is hash-verified; `backend_keys` sails through unchecked (`src/backend/user_status.rs:181-244`).
3. `personal_custody_package::Package::build` seals Session A's actual iris/face/normalized-iris tar archives with Session B's public keys (`src/plans/personal_custody_package.rs:300-327`), producing a PCP whose Tier 1 biometric ciphertext can only be opened by whoever holds Session B's private key — with no error, log, or detection anywhere in `orb-core`.

fn encrypt<T: AsRef<[u8]>>(data: T, public_key: &PublicKey) -> Vec<u8> {
    let encrypted = sodiumoxide::crypto::sealedbox::seal(data.as_ref(), public_key);
    assert_ne!(data.as_ref(), encrypted);
    encrypted
}
