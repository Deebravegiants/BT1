### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` proves nothing about the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Registry.process` nevertheless treats `request.shop`, derived solely from that unverified header, as the authoritative tenant identifier passed to the app's webhook handler. This mirrors the reported `take_offer.rs` bug class: a value that is *used* in a security-relevant decision but is not the value that was actually *authenticated*.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Registry.process` validates the request purely against this body-only signable string, then immediately forwards `request.shop` (read straight from the unauthenticated header) to the merchant's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [2](#0-1) 

`Request#shop` is defined as:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it against the `hmac-sha256` header value:
```ruby
def validate(verifiable_query)
  return false unless verifiable_query.hmac
  result = validate_signature(verifiable_query, Context.api_secret_key)
  ...
end
``` [4](#0-3) 

The equality this bug class expects to be enforced is:
```
shop authenticated by HMAC == shop acted upon by the handler
```
In reality the code enforces only:
```
raw_body authenticated by HMAC != shop header acted upon by the handler
```
Because the signature is computed exclusively over `@raw_body`, the `shop-domain` header can be swapped for any value without invalidating the HMAC, as long as the body and its HMAC pair were legitimately produced (e.g., from a webhook the attacker legitimately received for their own shop/installation). The gem passes this unauthenticated `shop` value straight through as the tenant identity in `WebhookMetadata`, which is exactly the kind of "field acted on but not covered by the HMAC" identity-binding break called out by the rules.

### Impact Explanation
Any app whose webhook handler uses `WebhookMetadata#shop` to select the tenant/session/database row to act on (the officially documented and expected usage pattern, since `shop` is provided specifically for that purpose) can be made to act on the wrong tenant's data. An attacker who controls one legitimate app installation (their own shop) can capture a valid `(raw_body, hmac)` pair from a real webhook delivery to their own shop, then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. The HMAC still validates (it only covers the body), and the handler executes with `shop == victim_shop`, i.e., cross-tenant access/attribution using data intended for a different merchant. This matches the Critical "cross-tenant access" impact category defined in scope.

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged user of the app on their own store (no `api_secret_key`, no stolen tokens, no TLS interception) to obtain a valid `(body, hmac)` pair via any real webhook delivered to their own installation. Delivering the crafted request to the merchant app's public webhook endpoint with a modified header is trivial once that pair is captured. The only prerequisite is that the host application relies on `WebhookMetadata#shop` for tenant selection, which is the gem's own documented contract for this field, not a misuse of an undocumented API.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header value in the signed content used for verification, or otherwise cryptographically bind the reported shop to the payload before trusting it (e.g., verify the header-derived shop against a shop value embedded/signed inside the body, or require the caller to cross-check the resolved shop against a session lookup keyed by an independently authenticated value). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as the sole tenant selector without additional verification.

### Proof of Concept
1. Install the app on `attacker.myshopify.com` (or otherwise become a normal merchant user of the app).
2. Trigger a real webhook delivery to the app (e.g., `orders/create`), capturing the raw request body `B` and its `x-shopify-hmac-sha256` header value `H` — a legitimately signed `(B, H)` pair for `attacker.myshopify.com`.
3. Send a new HTTP request to the same app webhook endpoint with:
   - Body = `B` (unchanged)
   - `x-shopify-hmac-sha256` = `H` (unchanged)
   - `x-shopify-shop-domain` = `victim.myshopify.com` (changed)
   - `x-shopify-topic`/`x-shopify-webhook-id` as needed
4. `HmacValidator.validate` succeeds because `Request#to_signable_string` returns only `B`, which is unchanged.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...))`, causing the app's handler to act on/for `victim.myshopify.com` using data the attacker fully controls in `B`, despite the request never being authenticated for that shop. module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
