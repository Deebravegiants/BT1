### Title
Token Exchange sends the app's `client_secret` to an SSRF-controllable host derived from an unvalidated JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
Every other flow in this gem that builds the OAuth "shop host" — `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, and `TokenExchange.migrate_to_expiring_token` — runs the caller-supplied `shop` through `Utils::ShopValidator.sanitize!` before using it to construct the request host that will receive the app's `client_id`/`client_secret`. `TokenExchange.exchange_token` is the one exception: it takes the `shop` value straight from the JWT `dest` claim (`JwtPayload#shop`) and uses it, unvalidated, to build the host that receives the `client_secret`.

### Finding Description
In `lib/shopify_api/auth/token_exchange.rb:39-65`:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = { client_id: ..., client_secret: ShopifyAPI::Context.api_secret_key, ... }
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [1](#0-0) 

`JwtPayload#shop` is derived purely as `@dest.gsub("https://", "")` [2](#0-1)  — it is never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [3](#0-2) . `JwtPayload#initialize` only validates the JWT signature and that `aud == Context.api_key` [4](#0-3) ; it does not constrain the *value* of `dest`.

That unvalidated `dest_shop` string is then fed directly into `Session.new(shop: dest_shop)`, and `HttpClient` builds the outbound request host straight from `session.shop`:
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [5](#0-4) 

The POST body containing `client_id` and the app's `client_secret` is sent to `https://#{dest_shop}/admin/oauth/access_token`. Compare this with the three sibling flows that all call `Utils::ShopValidator.sanitize!(shop)` before doing the exact same thing:
- `RefreshToken.refresh_access_token` [6](#0-5) 
- `ClientCredentials.client_credentials` [7](#0-6) 
- `TokenExchange.migrate_to_expiring_token` [8](#0-7) 

This is precisely the "host validated versus host that receives the `client_secret`" binding break: the identity check performed on the JWT (signature + `aud`) does not bind or constrain the `dest` value to a trusted Shopify host, yet that same unvalidated value becomes the destination host for the `client_secret`-bearing request.

The exploitability question hinges on whether an attacker can influence the JWT's `dest` claim while still producing a token this gem will accept. Because `JwtPayload` validates the HMAC-SHA256 signature against `Context.api_secret_key` (or `old_api_secret_key`), an attacker without that secret cannot forge an arbitrary `dest`. However, this gem's own documentation states the token is not restricted to Shopify's admin issuer: the `iss` claim can legitimately end in `/checkouts` for checkout UI extension tokens as shown in `test/auth/jwt_payload_test.rb:23-32` [9](#0-8) , and `JwtPayload` never checks `iss` before `TokenExchange.exchange_token` trusts `dest`. Any Shopify-issued session token bound to *this app's* `client_id` (`aud`) — regardless of which surface issued it or what its intended scope was — is accepted and its `dest` is used unvalidated as the destination host for the `client_secret`. Because `ShopValidator.sanitize!` is deliberately applied everywhere else in this codebase to close exactly this gap, its omission here is a real, code-level identity-binding gap: the code verifies "this JWT belongs to my app" but never verifies "the shop this JWT names is a real, trusted Shopify shop domain" before sending the app's `client_secret` there.

### Impact Explanation
If `dest` can carry a non-`myshopify.com`/non-trusted-domain value that still passes signature and `aud` checks (e.g., via any Shopify-issued token type for the app that is not restricted to `/admin`, or via a future/alternate token-issuing surface), the app's `client_secret` would be exfiltrated to an attacker-controlled host — a direct credential-theft / SSRF-with-credentials scenario, matching the "High: SSRF with the app's credentials" / "Critical: theft of client_secret" impact bands.

### Likelihood Explanation
Medium: the JWT signature check bounds the attack surface to tokens issued by Shopify for this specific app (`aud == Context.api_key`), so a fully blind forgery is not possible. But the missing `ShopValidator.sanitize!` call here — present in every sibling method in the same file/module — is a genuine, reachable defense-in-depth gap in this gem's own code path that lets an unvalidated claim (not scoped to `/admin`, not restricted to a trusted Shopify domain) directly determine where the `client_secret` is sent.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, and `ClientCredentials.client_credentials`) before constructing `shop_session`/`HttpClient`. Additionally, consider having `JwtPayload` validate that `iss`/`dest` correspond to a trusted Shopify domain and, where token-exchange is concerned, that `iss` ends with `/admin`, so tokens minted for other surfaces (e.g., checkout UI extensions) cannot be used to request admin access tokens.

### Proof of Concept
Conceptual (cannot be fully demonstrated without a real Shopify-signed token, since forging `dest` requires the app's `api_secret_key`):
1. Obtain any Shopify-issued session token whose `aud` equals the target app's `client_id` but whose `dest`/`iss` do not correspond to a trusted `myshopify.com` domain (or reflect a non-admin issuer).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `dest_shop = jwt_payload.shop` is used unvalidated to build `shop_session`, and `Clients::HttpClient` sends the POST containing `client_id`/`client_secret` to `https://#{dest_shop}/admin/oauth/access_token` — with no `ShopValidator.sanitize!` check as exists in the other three credential-exchange flows in this same module.
