This confirms the finding: the gem's documented API explicitly tells the host app to trust `data.shop` from `WebhookMetadata` (per `docs/usage/webhooks.md` lines 12-17, "shop, String - The shop domain of the webhook") as the authoritative tenant identifier returned by `ShopifyAPI::Webhooks::Registry.process`, while `ShopifyAPI::Utils::HmacValidator.validate` only authenticates the raw body.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then forwards `request.shop` straight into `WebhookMetadata` as the trusted tenant identifier for the host application's handler. This is the same bug class as the reported "arbitrary proposer" issue: a field that is acted upon (`shop`) is not bound by the same cryptographic check (HMAC) that authenticates the rest of the message.

### Finding Description
`lib/shopify_api/webhooks/request.rb`: [1](#0-0) [2](#0-1) 

`hmac` is derived from the `hmac-sha256` header, and `shop`, `topic`, `webhook_id`, `api_version` are derived from separate, unsigned headers. Crucially, `to_signable_string` returns `@raw_body` only — none of those header-derived fields are part of the signed content.

`lib/shopify_api/utils/hmac_validator.rb` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`lib/shopify_api/webhooks/registry.rb#process` validates only this body-bound HMAC, then trusts `request.shop` (and `request.topic`) as authoritative when constructing the metadata handed to the app's webhook handler: [4](#0-3) 

The gem's own documentation instructs app developers to treat `data.shop` as "The shop domain of the webhook" and use it directly to key merchant-specific side effects (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

The identity binding that should hold is: `HMAC(shared_secret, message) == received_hmac` should imply `message` (including the shop it is attributed to) is unforgeable. Instead, the equality actually enforced is `HMAC(shared_secret, raw_body) == received_hmac`, which is independent of the `shop` value carried in `x-shopify-shop-domain`. Because the `client_secret`/`api_secret_key` used to sign webhooks is the same for every shop that installs a given app, any merchant that has legitimately installed the app can capture one of their own genuine webhook deliveries (valid body + valid HMAC signed with the app's real secret) and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a different, victim shop that also uses the same app. `HmacValidator.validate` still returns `true` (the body and HMAC are genuinely valid for that secret), and `Registry.process` passes the attacker-supplied `shop` value through unmodified to the handler.

### Impact Explanation
This lets any shop that has installed a multi-tenant app impersonate another tenant of the same app to the app's webhook processing pipeline — a cross-tenant boundary crossing achieved purely by resending an otherwise-legitimate, correctly-HMAC-signed webhook with a modified shop header, requiring no access to the `api_secret_key`, no TLS interception, and no privileged account beyond ordinary app installation. Depending on how the host handler keys its persisted data or triggers actions off `data.shop` (exactly as the gem's own example code does), this can inject attacker-controlled data (`data.body`) into another merchant's records, trigger unauthorized side effects under another shop's identity, or corrupt per-tenant state — i.e., cross-tenant access/data confusion.

### Likelihood Explanation
Likelihood is realistic but conditioned on the attacker already being able to trigger genuine webhook deliveries for their own shop (which any merchant using the app can do) and on the host app's HTTP layer allowing the client to set/override the shop-domain header value sent to the processing endpoint (or an intermediary forwarding it verbatim). No secret material or credential theft is required — only manipulation of a header field that the gem itself never binds cryptographically.

### Recommendation
- Include `shop`, `topic`, and `webhook_id` (all header-derived fields the handler is told to trust) in the signable content, or otherwise re-verify `shop` against the API that actually delivered the specific `webhook_id`, before invoking the handler.
- At minimum, document loudly that `data.shop` in `WebhookMetadata` is NOT authenticated by the returned HMAC validity, and that host apps must independently correlate the webhook to a session/shop they expect (e.g., only accept webhooks for shops they still have an active install/session for), rather than trusting the header value implicitly as the current documentation implies.
- Consider having `Request#to_signable_string` incorporate the full header set that downstream code treats as trusted, not just the raw body.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both using the same Shopify app (same `api_secret_key`).
2. Attacker triggers a webhook event on their own store (e.g., `orders/create`), and Shopify delivers a POST with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and the raw body `B`.
3. Attacker captures this request and resends it to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping `raw_body = B` and `hmac-sha256` unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` builds a request whose `hmac` and `to_signable_string` (`= B`) are unchanged from the genuine request.
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` — matches the (unchanged) received HMAC, returns `true`.
6. `process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, i.e., the host app's handler is invoked believing the data in `B` (attacker-controlled/attacker-shop's data) belongs to `victim-shop.myshopify.com`.
