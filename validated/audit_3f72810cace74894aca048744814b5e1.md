Audit Report

## Title
Missing `return` after failed email-claim extraction allows OIDC session/cookie creation with an empty-email identity - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `handleTokenExchange`, the type assertion `email, ok := claims["email"].(string)` fails to `return` when `ok` is `false`, unlike every other error branch in the same function. Execution continues into role mapping, `oidc_sessions` row insertion, and session cookie creation, resulting in an authenticated session being issued for an identity with an empty email.

## Finding Description
The code at [1](#0-0)  shows the vulnerable branch: when the `email` claim is missing or not a string, `oi.lggr.Errorf` and `c.String(http.StatusInternalServerError, ...)` are called, but there is no `return` statement. This is inconsistent with the surrounding error handling in the same function — the ID token verification at [2](#0-1)  and claim extraction at [3](#0-2)  both correctly `return` on error.

As a result, execution falls through to role mapping, session row insertion with `strings.ToLower(email)` (which will be `""`), and finally to setting/saving the gin session cookie and returning HTTP 200 success JSON, as seen at [4](#0-3) . Gin's `c.String` in the earlier branch does not stop execution or panic; it merely writes to the response body/sets headers once, but the handler function keeps running and unconditionally performs the state-changing session creation and cookie-setting logic.

## Impact Explanation
This results in a persisted `oidc_sessions` row with `user_email = ''` and a valid `user_role` derived from group claims, plus a saved session cookie (`webauth.SessionIDKey`) returned to the caller — despite the handler detecting and logging a fatal condition. This is a genuine authentication-state integrity bug: an empty-email but role-bearing session is issued and usable via `AuthorizedUserWithSession` for subsequent authenticated API calls, matching the "node API authentication bypass" impact class.

## Likelihood Explanation
This is not attacker-controlled in the traditional unprivileged sense: it depends on the configured OIDC identity provider (a trusted, node-operator-configured backend) returning an ID token that passes signature verification and includes valid group/role claims but omits or malforms the `email` claim. This requires either a misconfigured/misbehaving IdP or control over the IdP response by the party operating it. It is not exploitable by a normal unprivileged client sending arbitrary requests to the node API — the trigger point is entirely within the OIDC provider trust boundary that the node operator configures and controls. Given that IdP behavior/configuration is an operator-controlled trust boundary rather than something an unprivileged external attacker can manipulate, this significantly reduces real-world attacker reachability, though the code-level bug itself is real and reproducible with a controlled/test IdP.

## Recommendation
Add a `return` immediately after the failed email-claim assertion, matching the pattern used elsewhere in the function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Also add a `return` after the `oidc_sessions` insert failure at [5](#0-4) , which has the identical missing-return defect.

## Proof of Concept
1. Stand up a test/mock OIDC provider (fully within the node operator's control) that returns a signed, verifiable ID token containing a valid group/role claim matching the node's configured `ClaimName`/role claims, but with the `email` claim absent or a non-string type.
2. Configure the node's OIDC settings to point at this provider and complete the `/oidc-login` → callback flow with a valid `code`/`state` against `handleTokenExchange`.
3. Observe: despite the logged "Failed to get email from claims" error, the response sets the session cookie and `oidc_sessions` gains a row with `user_email=''` and the mapped role.
4. Use the session cookie against an authenticated endpoint and confirm `AuthorizedUserWithSession` returns a valid `User{Email: "", Role: <role>}`.
