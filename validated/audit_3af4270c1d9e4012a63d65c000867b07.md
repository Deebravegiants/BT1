### Title
Webhook HMAC only signs the request body, allowing the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers to be forged for cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery#to_signable_string` by returning only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` are read straight from unauthenticated HTTP headers. Since the HMAC never covers these headers, any actor who can obtain one valid `(raw_body, hmac)` pair from the shared `api_secret_key` (e.g., by installing the app on their own shop and capturing/replaying one of their own legitimate webhooks) can resend that same signed body to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. The HMAC still validates, so the app processes attacker-controlled data as if it originated from a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are never part of the signed string: [2](#0-1) 

`HmacValidator.validate` only calls `validate_signature`, which HMACs `verifiable_query.to_signable_string` (the body) against the app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` passed to the host app's handler, gating solely on the body's HMAC: [4](#0-3) 

Because `api_secret_key` is a single per-app secret (not per-shop), any user who can install the app onto their own store (an unprivileged internet actor with respect to *other* merchants' data) can legitimately trigger a webhook to their own endpoint, capture the `(raw_body, hmac)` pair, and then replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `topic`/`webhook-id`) with a victim shop's domain. `Registry.process` will accept it as authentic and hand the host application a `WebhookMetadata` whose `shop` field does not match the entity that actually authenticated the payload — breaking the invariant `hmac-authenticated body == data attributed to shop`. Any host application that uses `WebhookMetadata#shop` to look up the target shop's session, update shop-scoped records, or otherwise key its "tenant" boundary (which is the intended and documented use of the field, per `test/webhooks/registry_test.rb`) will act on the wrong tenant's behalf using attacker-controlled body content.

### Impact Explanation
This crosses the tenant boundary of the library's core authentication primitive: the webhook HMAC is meant to prove "this payload really came from Shopify for shop X," but the `shop` identity is not part of what is proven. This matches the Critical category of cross-tenant access: an attacker (their own legitimately-installed shop) can make the host application process data under another merchant's identity.

### Likelihood Explanation
Any user can install a public app to obtain their own valid webhook deliveries and secret-signed bodies for their own shop, then replay the body with a forged `shop-domain` header to the same publicly-reachable webhook endpoint. No access token, `api_secret_key`, or privileged account is required — only ordinary app installation, which is the normal, unprivileged use case for a merchant.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api_version`, `webhook_id`) header values in the signable string used by `Webhooks::Request#to_signable_string`, or otherwise bind them cryptographically to the HMAC, so that `HmacValidator.validate` fails if any of these fields are altered independently of the body.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; the app registers webhooks as usual.
2. Shopify delivers a legitimate webhook to the attacker's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — attacker records `(B, H)`.
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, an interesting `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` builds `to_signable_string` from `B` only; `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so validation passes at `lib/shopify_api/webhooks/registry.rb:190`.
5. `Registry.process` invokes the host handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data attributed to the victim shop.
