### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC-validated signal (`hmac`) that is verified solely against the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (and `topic`, `webhook_id`, `api_version`) values consumed downstream come from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) that are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC is valid and forwards the unauthenticated `shop` header straight to the application's webhook handler as trusted tenant identity.

### Finding Description
The binding that should hold is: `shop value trusted by the handler == shop value cryptographically bound by the HMAC`. In this gem that binding is broken:

- `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header [5](#0-4) .
- For `Webhooks::Request`, `to_signable_string` is just the raw JSON body [1](#0-0) ; `shop`, `topic`, `api_version`, and `webhook_id` are read from headers that are entirely outside the signed string [2](#0-1) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` (body HMAC) before dispatching `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the handler [3](#0-2) .
- The documented integration pattern instructs apps to use `data.shop` directly for tenant-scoped work (e.g., enqueueing jobs keyed by `shop_domain`) [6](#0-5) .

Because the header is unauthenticated, anyone capable of sending an HTTP POST to the app's public webhook endpoint with a body whose HMAC they can compute — which is trivially true for any merchant who owns a shop with the app installed, since Shopify will deliver them a legitimately signed webhook for their own shop, and the raw body/HMAC pair can be replayed with a different `shop-domain` header — can make the endpoint accept content as if it came from a different, victim shop. The gem itself never binds `shop` to the signature, so this is a root-cause gap in the library's webhook-verification API, not merely a misuse by the host app following the documented contract.

### Impact Explanation
This breaks the shop/tenant identity binding relied upon by host applications integrating per the gem's own documented API (`data.shop`), enabling cross-tenant confusion: a request that is valid Shopify traffic for shop A can be replayed/forged with shop B's domain in the header while keeping shop A's legitimately-HMAC'd body, causing the host app to process/attribute the payload to the wrong tenant. This matches the Critical impact category of cross-tenant access, since the gem's verification primitive fails to bind the identity field applications are told to trust.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own Shopify shop with the target app installed (to legitimately receive one HMAC'd webhook body), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a modified `shopify-shop-domain` header — both are available to any unprivileged internet user/merchant, with no access token, `client_secret`, or privileged access needed.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the HMAC-signed material, or otherwise cryptographically bind them (e.g., derive/validate the shop domain independently, such as cross-checking against a session already associated with the webhook subscription) instead of trusting the unauthenticated header verbatim in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST from Shopify with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Attacker replays this exact request to the app's public webhook callback URL, but changes the header `x-shopify-shop-domain` to `victim-shop.myshopify.com` while leaving body `B` and `x-shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) and successfully matches `H`, since headers are not part of the signed string [7](#0-6) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [8](#0-7) , causing the host application to process attacker-controlled content under the victim shop's tenant identity.
