## Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates nothing but the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` extracts and hands to the host application's handler come exclusively from HTTP headers that are never included in the signed material. Any party capable of obtaining one validly-signed `(body, hmac)` pair for the app's shared `client_secret` — e.g., an attacker who installs the app on their own store and receives/triggers one real webhook — can replay that body+HMAC to the app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain`/`x-shopify-topic`/`x-shopify-webhook-id` headers, and the gem will report it as authentic.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — none of `shop`, `topic`, `webhook_id`, or `api_version` (all parsed from headers via `shopify_header`) participate in the signable string: [3](#0-2) 

`HmacValidator.validate` computes/compares the HMAC solely over `verifiable_query.to_signable_string`: [4](#0-3) 

`Registry.process` validates the HMAC and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the `WebhookMetadata` object delivered to the app's handler — the exact tenant-identifying data the host app uses to route/store per-merchant data: [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`bytes_verified_by_HMAC` (raw body) `≠` `bytes_that_determine_the_tenant/topic` (`shop`, `topic`, `webhook_id`, `api_version` headers).

Because the webhook signing secret is the **app's** `client_secret` (identical for every merchant using the app, not per-shop), any unprivileged user who installs the app on their own store can obtain a genuinely Shopify-signed `(raw_body, x-shopify-hmac-sha256)` pair from a real webhook delivery to their own store. That pair validates successfully via `HmacValidator.validate` regardless of which `shop`, `topic`, or `webhook_id` header accompanies it, because those headers are outside the signed payload.

### Impact Explanation
An attacker who is a legitimate (but unprivileged relative to other merchants) installer of the app can capture one validly-HMAC-signed webhook body/signature pair from their own store, then send that same body+signature to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim merchant's shop (and/or a forged `x-shopify-topic`/`x-shopify-webhook-id`). `ShopifyAPI::Webhooks::Registry.process` will treat this as an authentic webhook for the victim shop/topic and invoke the app's handler with attacker-chosen `shop`/`topic`/`body` combination, since `Registry.process` only calls `Utils::HmacValidator.validate(request)` before dispatch and that validator never inspects the header fields. Depending on how the host app's handler uses `WebhookMetadata#shop` (commonly used as the tenant/session key to load merchant records), this enables cross-tenant data injection or corruption — writing attacker-controlled body content into a victim shop's records, or triggering topic-specific business logic (e.g., `app/uninstalled`, `customers/redact`) against a shop the attacker doesn't own. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite (becoming an installer of a target merchant's same app to obtain one valid signed webhook) is realistic for any public/embedded Shopify app, since installation itself does not require special privilege beyond having a Shopify store — a capability available to any unprivileged internet user. Capturing a webhook body/HMAC pair requires only observing traffic to an endpoint the attacker controls (their own app installation's webhook receiver), not TLS interception of anyone else's traffic. The forgeable headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`) are plain HTTP headers on a POST request the attacker sends directly to the target app's public webhook URL.

### Recommendation
Bind the tenant-identifying header values into the material that is HMAC-verified, or otherwise cryptographically authenticate them, before trusting `request.shop`/`request.topic`/`request.webhook_id` in `Registry.process`. At minimum, `Request#to_signable_string` should not be the sole gate for header-derived identity fields consumed downstream — the header values relied upon for tenant routing must be verified against the actual originating request context (e.g., confirm the request truly originated from Shopify's IP ranges/mTLS, or require the shop to be cross-checked against a shop already known/authorized for the given `client_secret`/session store) rather than trusted purely because *some* valid HMAC/body pair was presented.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store, receiving `api_secret_key`-signed webhooks like any merchant (the secret is shared across all installs of the app).
2. Attacker captures one webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — verified in `Request#to_signable_string`/`HmacValidator.validate_signature`.
3. Attacker sends a POST to the victim app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still verifies since only `B` is signed)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: orders/create` (forged to any registered topic)
   - `x-shopify-webhook-id: <arbitrary>`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`, only `B` is checked), then dispatches to the registered handler with `shop: "victim-shop.myshopify.com"` (per `lib/shopify_api/webhooks/registry.rb:188-200`), even though that shop never sent this webhook.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
