### Title
Pod Security Admission fails to validate pod-security labels mutated via namespace `status`/`finalize` subresources - ([File: staging/src/k8s.io/pod-security-admission/admission/admission.go])

### Summary
`Admission.ValidateNamespace` unconditionally allows any request with a non-empty subresource before ever inspecting the namespace's pod-security labels, while `ValidatePod` only ignores a fixed, hardcoded set of pod subresources. Combined with the fact that the namespace `status` and `finalize` registry strategies only reset `.status` or `.spec` (not `ObjectMeta.Labels`), a caller with narrow RBAC on `namespaces/status` or `namespaces/finalize` can mutate `pod-security.kubernetes.io/*` labels on a namespace without ever going through `newPolicy`/`oldPolicy` validation or the existing-pod dry-run check.

### Finding Description
`Admission.Validate` dispatches namespace requests to `ValidateNamespace`: [1](#0-0) 

`ValidateNamespace` short-circuits on *any* non-empty subresource before decoding the object or computing `PolicyToEvaluate`: [2](#0-1) 

This is in contrast to `ValidatePod`, which only ignores a fixed allowlist (`exec`, `attach`, `binding`, `eviction`, `log`, `portforward`, `proxy`, `status`) and evaluates any other subresource as a full pod object: [3](#0-2) 

Looking at the actual REST strategy for namespace subresources, `namespaceStatusStrategy.PrepareForUpdate` only resets `.Spec`, leaving `ObjectMeta` (including `Labels`) as submitted by the caller, and `namespaceFinalizeStrategy.PrepareForUpdate` only resets `.Status`: [4](#0-3) [5](#0-4) 

Because neither subresource strategy resets `ObjectMeta.Labels`, a caller with only `update` permission on `namespaces/status` or `namespaces/finalize` can submit a namespace object whose `metadata.labels` include arbitrary `pod-security.kubernetes.io/enforce`, `.../audit`, `.../warn` labels (and version labels). The registry-level `ValidateNamespaceStatusUpdate` / `ValidateNamespaceFinalizeUpdate` validation functions only check status/finalizer semantics, not pod-security label well-formedness. Since `Admission.ValidateNamespace` bails out immediately for any non-empty subresource, this admission plugin never runs `PolicyToEvaluate`, never rejects malformed/downgraded labels, and never triggers `EvaluatePodsInNamespace` to warn about/dry-run existing pods against a new enforce level — the entire pod-security label admission-completeness guarantee is bypassed for this write path.

### Impact Explanation
An attacker who can update `namespaces/status` or `namespaces/finalize` (without `namespaces` update rights) can set or change the effective Pod Security Standard enforced on a namespace — e.g. relax `enforce=restricted` to `enforce=privileged`, or set invalid labels that would normally be rejected — with no PSA validation and no warning about existing non-compliant pods. This corresponds to a Pod Security Admission bypass / policy-tampering impact, since the labels that gate PSA enforcement for the whole namespace are the security control being subverted, potentially enabling subsequently created pods in that namespace to run privileged workloads that should have been blocked.

### Likelihood Explanation
Exploitability depends entirely on whether the attacker's principal (a normal user or a serviceaccount) actually holds `update` on `namespaces/status` or `namespaces/finalize` without holding `update` on `namespaces` itself. This is an unusual RBAC grant in stock Kubernetes (the default `system:controller:namespace-controller` typically gets `finalize`, and most `edit`/`admin` ClusterRoles grant `namespaces` fully), so the precondition is a non-default, narrowly-scoped RBAC binding rather than something present out of the box. Given such a binding exists, the exploit is deterministic and repeatable (a single PATCH/PUT to the subresource endpoint), and label mutation via `ObjectMeta` on a status/finalize subresource update is a general possibility across the codebase, not specific to a bug elsewhere — the gap is specifically that `ValidateNamespace`'s subresource short-circuit does not account for it.

### Recommendation
Restrict `ValidateNamespace`'s short-circuit so it does not blindly skip all namespace subresources; specifically, when the incoming object's `metadata.labels` differ from the stored object's pod-security labels via `status`/`finalize` subresource requests, run the same `PolicyToEvaluate`/dry-run validation as for the main resource (mirroring `ValidatePod`'s allowlist approach instead of allow-by-default), or alternatively have the namespace `status`/`finalize` registry strategies also reset `ObjectMeta.Labels` (or at least the pod-security label keys) to the old object's values, consistent with how `.Spec`/`.Status` are already reset.

### Proof of Concept
Integration test plan:
1. Create a namespace `ns1` with `pod-security.kubernetes.io/enforce: restricted` and a pod that only satisfies "restricted" (no privileged fields).
2. As an authenticated user/serviceaccount granted RBAC solely for `update` on `namespaces/finalize` (or `namespaces/status`) in a ClusterRole/ClusterRoleBinding — explicitly NOT granting `update`/`patch` on `namespaces` — issue a `PUT` to `/api/v1/namespaces/ns1/finalize` (or `/status`) with the namespace body containing `metadata.labels["pod-security.kubernetes.io/enforce"] = "privileged"`.
3. Assert: the request succeeds (200), confirming the label mutation was persisted without going through `PolicyToEvaluate`/`EvaluatePodsInNamespace`.
4. Fetch `ns1` and assert the `enforce` label is now `privileged`, and that no warnings about the existing "restricted"-only pod being newly-permitted were ever generated (since `ValidateNamespace` never ran for the subresource path), demonstrating the admission-completeness bypass.
5. As a control, repeat the same label change via the main `namespaces` update endpoint (with proper RBAC) and confirm `ValidateNamespace` executes label validation/dry-run as expected, showing the discrepancy is isolated to the subresource path.
