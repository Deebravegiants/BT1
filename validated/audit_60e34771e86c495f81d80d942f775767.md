### Title
Webhook `shop-domain` (tenant identifier) header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the `shop-domain` HTTP header as the authoritative tenant identifier for an inbound webhook and hands it to the app's handler, but `ShopifyAPI::Utils::HmacValidator` only verifies the raw request body against the HMAC. The header carrying the tenant binding is never part of the signed content, so it can be swapped independently of the body/HMAC pair that passes verification.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` that is passed to the app's `handler.handle`: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [4](#0-3) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [5](#0-4) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived purely from HTTP headers, with no cryptographic tie to the HMAC: [6](#0-5) 

This reproduces the analog of the reported bug class: an identity-binding field (`shop`, the tenant) is *acted on* (used to route/attribute the webhook payload to a specific merchant in the handler) but is *not covered* by the cryptographic check (`HMAC` over body only). The equality the code implicitly assumes but never enforces is:

`hmac_verified(raw_body) == true` should imply `shop_header == shop_that_produced(raw_body)`

but no such binding exists — `hmac_verified(raw_body)` is independent of `shop_header`, `topic`, or `webhook_id`. Any HTTP client that can reach the app's public webhook endpoint (the "unprivileged internet user") and that possesses one valid `(raw_body, hmac)` pair — trivially available since the merchant's own shop legitimately receives such deliveries, or any publicly documented example payload signed against a known test secret — can resubmit that exact body/hmac pair while freely substituting the `shop-domain` (and `topic`/`webhook_id`) headers to any value, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the tenant boundary at the point the app is expected to trust it most: the very value (`shop`) that many apps use to select which merchant's account/data record the webhook payload should be written to. An attacker who controls (or has captured) any one legitimately signed `(body, hmac)` pair can present it to the app claiming it belongs to an arbitrary other shop, causing the app to attribute/process that payload under a different tenant's identity — i.e., cross-tenant data injection/confusion, which maps to the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint by design (Shopify delivers webhooks over the internet), so no privileged access, TLS interception, or credential theft is required — only the ability to send an HTTP POST with attacker-controlled headers and a body/hmac pair the attacker already possesses (from their own shop's traffic or any leaked/published sample). No secret (`api_secret_key`) needs to be known by the attacker, since the hmac is being replayed unmodified, not recomputed.

### Recommendation
Bind the tenant/shop identifier (and ideally `topic`/`webhook_id`) into the HMAC-signed content, or otherwise cryptographically tie the header set to the signature (e.g., include them in `to_signable_string`, or require the caller to independently confirm the `shop-domain` header matches a shop known to have an active app installation/session before trusting `WebhookMetadata#shop`). At minimum, document that `request.shop` from `ShopifyAPI::Webhooks::Request` is *not* authenticated by the HMAC and must not be used as a sole tenant-routing key without an independent installation/session check.

### Proof of Concept
1. Capture (or construct with a known/public test `api_secret_key`) one valid webhook delivery: `raw_body = "{}"`, `headers["x-shopify-shop-domain"] = "victim-shop.myshopify.com"`, `headers["x-shopify-hmac-sha256"] = Base64.encode64(OpenSSL::HMAC.digest("sha256", api_secret_key, raw_body))`.
2. Build a forged request reusing the same `raw_body`/`hmac` but with `headers["x-shopify-shop-domain"]` changed to `"attacker-shop.myshopify.com"`:
```ruby
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: raw_body,
  headers: headers.merge("x-shopify-shop-domain" => "attacker-shop.myshopify.com"),
)
ShopifyAPI::Webhooks::Registry.process(request) # HMAC still validates; handler receives shop: "attacker-shop.myshopify.com"
```
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the `hmac`, and `Registry.process` passes the attacker-chosen `shop` straight to `handler.handle`, confirming the header can be freely substituted without invalidating the signature. [3](#0-2)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
