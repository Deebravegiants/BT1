## Finding: Webhook shop identity not bound to the Shopify HMAC signature

### Title
Webhook `shop-domain` header is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The bug report describes a caching mechanism that returns stale/incorrect approval information because the cached value doesn't actually reflect what was verified. The structural analog here is a verification/binding mismatch: `ShopifyAPI::Webhooks::Registry.process` treats a webhook's `shop` field as trustworthy identity information, but that field is never included in the data that the HMAC signature actually covers, so "the HMAC that was verified" and "the shop that gets acted upon" are two different, unbound things.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is a completely separate field from the body: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC only over `to_signable_string` (the body), using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` calls `HmacValidator.validate(request)` and, once it passes, unconditionally trusts `request.shop` to route the payload to the app's handler as the acting tenant: [4](#0-3) 

The identity-binding equality that should hold is:
`shop bound inside HMAC-signed bytes == shop used to attribute/process the webhook`

But what actually holds is:
`HMAC(body, client_secret) == received_hmac` AND `shop = header value (unauthenticated, unbound to body/HMAC)`

Since the app's `client_secret` (and therefore its HMAC key) is shared across every shop that installs the app, a valid `(body, hmac)` pair generated for one shop's webhook delivery remains valid for *any* `shop-domain` header value — the signature check can't detect the substitution because the shop was never part of the signed material.

### Impact Explanation
This breaks the tenant/shop-authentication boundary the gem's webhook processing model is supposed to enforce: `Registry.process` hands `WebhookMetadata` (with attacker-controlled `shop` and attacker-influenced `body`) straight to the host app's registered handler, believing it originated from that shop. Any content a shop owner can cause to appear verbatim in one of their own webhook bodies (e.g., a product/customer/order field they control) can be replayed with a spoofed `shop-domain` header, causing the host application to process and store attacker-supplied data under a different, victim shop's identity — cross-tenant data injection.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(raw_body, hmac)` pair. This is realistically achievable by an unprivileged user who runs their own store with the target app installed: they trigger a real webhook delivery containing content they chose (e.g., a product title), capture the resulting HTTP request (their own webhook endpoint, or any place they can observe raw deliveries), then resend the same body/HMAC to the app's public webhook endpoint with only the `shop-domain` header altered. No access to `api_secret_key`, tokens, or the app's infrastructure is required — only visibility into a webhook delivery the attacker legitimately caused.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed/verified material, or independently verify that the `shop-domain` header corresponds to a shop session/registration the caller is authorized to represent, rather than trusting it purely because the body-only HMAC validated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker sets an order/product/customer field to a value they want injected (this becomes part of `raw_body` for a real webhook, e.g. `orders/create`).
3. Shopify delivers the webhook to the app with a valid `x-shopify-hmac-sha256` computed over that `raw_body` using the shared `client_secret`.
4. Attacker (having visibility into that delivery, e.g. via the app's own debug/logging surface or a webhook relay they control) replays the exact same `raw_body` + `x-shopify-hmac-sha256` to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only checks `raw_body` against the secret; `Registry.process` in `lib/shopify_api/webhooks/registry.rb` then dispatches the handler with `shop: "victim.myshopify.com"`, causing the host application to attribute attacker-controlled data to the victim shop.
