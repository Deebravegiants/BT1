### Title
Attacker-controlled venue/pool addresses in strategy `swap` payloads execute arbitrary contract code inside the victim's authorization tree, enabling wallet theft beyond the routed amount - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller's swap-based strategy verbs (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) accept a fully attacker-controlled `swap` XDR payload whose `assets` registry names the pool/token contracts the router invokes. The router keeps no allowlist of pools, so a crafted route can place a malicious contract on the call stack beneath the caller's `require_auth`. That contract can attach a `token.transfer(victim → attacker)` sub-invocation, which simulation faithfully records as a child of the caller's auth entry and which executes once the caller signs the tree — an exact analog of the CVE-2024-10524 class (attacker-controlled destination inside a seemingly constrained request). [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` forwards the caller-supplied `StrategySwap` bytes verbatim to `router.execute_strategy` after authorizing only one input transfer (`authorize_transfer_as_current`). [3](#0-2)  The payload format gives the route builder complete control of destination addresses: each 5-byte instruction record's `idx_a` is a `pool` index into the attacker-supplied `assets` registry, and `idx_b`/`idx_c` are token indices. [4](#0-3)  `dispatch_hop` then calls whatever address the payload names, with no venue-address allowlist. [5](#0-4) 

While the controller's own grant is bounded to the single measured input transfer (`RouterOverspend`, `NoSwapOutput`), that bound does not extend to the human caller: a rogue "pool" invoked mid-route runs while the caller's top-level authorization is active, and any `require_auth`-bearing call it makes against the caller (e.g., `token.transfer(victim, attacker, N)`) is recorded by simulation as a child of the caller's auth tree and succeeds if the wallet signs that simulated tree. [6](#0-5)  The test harness pins exactly this shape with `RogueHopPool`, which performs a token transfer from a stored victim during the hop. [7](#0-6) 

### Impact Explanation
Theft of user funds: the loss is the caller's wallet balance of any token the rogue contract names, not merely the routed `amount_in`. Neither the router's `total_min_out` check nor the controller's measured-output/final-risk gates bound this loss, because the theft rides the authorization tree rather than the swap accounting. [8](#0-7) 

### Likelihood Explanation
An unprivileged attacker can craft a `swap` payload embedding their own contract as a hop pool and deliver it wherever route bytes are sourced (a malicious or compromised quote/frontend, or a phishing `routeXdr`). Exploitation requires the victim to sign a transaction containing the crafted payload, and Soroban simulation will include the malicious child entry in the auth tree — so wallets that surface full auth trees mitigate it, but users routinely sign simulated trees without decoding them. This matches the documented exposure the threat model assigns to client verification rather than on-chain enforcement. [9](#0-8) 

### Recommendation
Enforce on-chain rather than relying on clients to decode routes: maintain a governance-managed allowlist of venue pool/share-token contracts (or venue-immutable adapter registries) and reject hops whose `idx_a`/`idx_b`/`idx_c` resolve outside it, so no route can place arbitrary contract code under the caller's authorization. At minimum, validate that every `assets` entry used as a pool or token belongs to a registered market/venue before `dispatch_hop`. [10](#0-9) 

### Proof of Concept
1. Attacker deploys `RogueHopPool` (as in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`), whose `swap()` calls `token::Client::transfer(&victim, &attacker, &amount)` for a token the victim holds.
2. Attacker builds a `StrategyPayload` whose `assets` contains `[legit_token_in, legit_token_out, rogue_pool]` plus the victim's valuable token, and an instruction naming `rogue_pool` as the hop pool; encodes it as `routeXdr`.
3. Victim is induced to submit a controller `swap_collateral`/`multiply` (or direct `execute_strategy`) carrying that payload. Simulation records the rogue pool's `transfer(victim → attacker)` as a child of the victim's auth entry.
4. Victim signs the simulated tree; the transaction executes the hop, the rogue transfer runs under the victim's authorization, and attacker receives tokens unrelated to the swap. The swap itself can still satisfy `min_out` and all controller risk gates. [11](#0-10)

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
