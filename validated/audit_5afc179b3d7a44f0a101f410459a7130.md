Confirmed: `WebhookMetadata` carries `shop: request.shop` straight from the unauthenticated header into the app's handler, with no further validation layer.

### Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` identity that the gem hands to the app's webhook handler is read from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, which is **not** part of the HMAC-covered bytes. Because the app's `api_secret_key` is shared across every shop that has installed the app, any tenant that can trigger a legitimately signed webhook can replay that exact body/HMAC pair to the app's single webhook endpoint while substituting an arbitrary victim shop's domain in the header, and the gem will report it as authentic data for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is parsed independently, straight out of request headers, with no cryptographic tie to the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the metadata passed to the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`, i.e., the body, using the app-wide `Context.api_secret_key`: [4](#0-3) 

The equality this breaks is: `shop authenticated by HMAC` ≠ `shop consumed by the handler`. The HMAC only proves "this body was produced with our app's secret" — it does not prove "this body/shop pairing was produced by Shopify for this shop." Since the same `api_secret_key` is used for every shop the app is installed on, an attacker who controls one legitimately-installed shop (e.g., a merchant using the same third-party app) can:
1. Trigger a real webhook from their own shop A (e.g., `orders/create`), capturing the raw body and the valid `X-Shopify-Hmac-Sha256` signature Shopify computed for it.
2. Replay that exact `raw_body` + HMAC to the app's single shared webhook endpoint, but override `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to name shop B, a victim tenant they have no access to.
3. `HmacValidator.validate` succeeds because it never inspected the shop header, and `Registry.process` dispatches the handler with `shop: "shop-b.myshopify.com"` and shop A's body content.

### Impact Explanation
This crosses a tenant boundary: data or events belonging to shop A can be injected into the app's processing pipeline under shop B's identity with a cryptographically "valid" webhook. Depending on what the host application's webhook handler does with `data.shop` (e.g., look up the shop's session/access token, update per-shop billing/usage records, write to a per-shop database keyed by `shop`, trigger fulfillment or inventory changes scoped to that shop), this enables cross-tenant data corruption/injection using another merchant's identity, without needing that merchant's access token or any Shopify credentials — satisfying the cross-tenant access criterion.

### Likelihood Explanation
Any user who can install the app on at least one shop (a normal, unprivileged installation flow) can generate a validly-signed webhook body at will (e.g., by creating an order) and replay it with a modified header using an ordinary HTTP client — no access token, secret, or privileged account is required, only network access to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated material before trusting it: e.g., verify that the `shop` header matches a shop that the app actually issued/holds a session for `AND` require that Shopify-side webhook delivery configuration is per-shop verifiable (Shopify's newer webhook payloads include the shop id in the JSON body — validate that body-embedded shop/id against the header before dispatch), or maintain a mapping from webhook `id`/idempotency and known active shops, rejecting shop headers that don't correspond to a shop with an active, previously-established session in host-application storage. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host app against installed-shop state before being trusted for any authorization decision.

### Proof of Concept
```ruby
# 1. Attacker (has legitimate access to shop-a.myshopify.com, e.g. installed the app)
#    triggers a real webhook and captures the raw POST Shopify sends to the app,
#    e.g. body = '{"id":1,"note":"hello"}' with a valid
#    X-Shopify-Hmac-Sha256 signature computed by Shopify using the app's shared secret.

raw_body = '{"id":1,"note":"hello"}'
valid_hmac = "<captured from Shopify's real request to shop-a's webhook>"

# 2. Attacker resends the identical body+HMAC, but swaps the shop-domain header
#    to a victim shop they don't control.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,      # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "shop-b-victim.myshopify.com",
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. This succeeds because HmacValidator only checks raw_body, not the shop header
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "shop-b-victim.myshopify.com", body: {...}, ...))
```
The webhook handler now processes attacker-supplied data as if it originated from `shop-b-victim.myshopify.com`, despite the attacker never having any credential or session for that shop.
