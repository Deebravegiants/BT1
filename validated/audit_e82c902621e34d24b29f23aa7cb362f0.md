### Title
`Oauth.begin_auth` embeds unsanitized `shop` into the OAuth `authorize` redirect host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds `auth_route` by concatenating `auth_base_uri(shop)` (which is `"https://#{shop}/admin"`) with the query string, but unlike `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, it never calls `Utils::ShopValidator.sanitize!` on `shop` first. Any caller that forwards a raw, attacker-supplied `shop` value (as the gem's own docs instruct: `shop = request.headers["Shop"]`) will produce a redirect to an arbitrary attacker-controlled host, embedding the app's real `client_id` in the URL.

### Finding Description
Binding claimed: `host_of_authorize_redirect == ShopValidator.TRUSTED_SHOPIFY_DOMAINS-accepted_host`.

Code path:
- [1](#0-0) .
- `auth_base_uri` performs no validation against `ShopValidator.TRUSTED_SHOPIFY_DOMAINS`: [2](#0-1) .
- Compare with the two other OAuth entry points in the same gem, which both validate the shop before using it in any host-affecting context: [3](#0-2)  and [4](#0-3) .
- `ShopValidator.sanitize!`/`sanitize_shop_domain` exist precisely to confine a shop's host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or a configured `myshopify_domain`: [5](#0-4) , [6](#0-5) . `begin_auth` never invokes either.

Attacker request: A caller of an app built per the gem's documented example — [7](#0-6)  — supplies `Shop: attacker.example` (or a `shop=` query param depending on host app's own extraction logic, which the gem does not itself dictate/sanitize). `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=<real client_id>&scope=...&redirect_uri=<legit Context.host + redirect_path>&state=<nonce>&grant_options[]=..."`. The browser is then 307-redirected to `attacker.example`, exposing `client_id`, `scope`, `state` nonce and the legitimate `redirect_uri` to the attacker's own server, and can be used to build a phishing/consent-capture page.

Why existing guards don't catch this: `HmacValidator.validate`, the `state` cookie comparison, and `JwtPayload`'s `aud` check are all invoked only in `validate_auth_callback`, which runs after the redirect — they cannot protect the initial `begin_auth` redirect target. `Context.setup?`/`private?` checks only gate whether OAuth can run at all, not the destination host. Sorbet typing on `shop: String` does not constrain the value's content. `ShopValidator.sanitize!`, the one mechanism designed for this, is simply never called from `begin_auth`/`auth_base_uri`.

### Impact Explanation
This matches the "High - SSRF driving an authenticated request to an unintended host" / credential-adjacent leakage category: the browser is driven to an attacker-chosen host carrying the app's `client_id`, `scope`, and the legitimate `redirect_uri`/`state`. This alone is not full token theft (the merchant/browser, not the server, makes the request, and the attacker doesn't yet have `code` unless they can further trick the merchant into completing consent on their own fake authorize-lookalike page or if the attacker's host reflects back to the real Shopify authorize flow). It is repeatable against any shop value the calling app forwards from user input, for every app built on this gem that follows the documented pattern of taking `shop` from request parameters/headers without independently confining it to `*.myshopify.com`.

### Likelihood Explanation
Requires that the host application pass a `shop` value into `begin_auth` that it did not already sanitize against trusted Shopify domains — which is exactly the flow shown in this gem's own `docs/usage/oauth.md` example (`shop = request.headers["Shop"]`, no independent validation). No secrets, tokens, or special access are needed; the attacker only needs to control the `shop`/`Shop` value on a request to the app's login route, which is by design attacker-controllable (any visitor of the app's install/login endpoint). This is not theoretical: the sanitize step exists and is used in the two sibling flows (`client_credentials`, `refresh_token`) in the very same codebase, showing the pattern is known but omitted for `begin_auth`.

### Recommendation
In `ShopifyAPI::Auth::Oauth.begin_auth`, validate `shop` the same way the other flows do before using it to build `auth_base_uri`:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
...
auth_route = auth_base_uri(validated_shop) + "/oauth/authorize?#{query_string}"
```
This ensures `auth_route`'s host is always confined to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (or the configured `myshopify_domain`), matching the invariant already enforced in `client_credentials.rb` and `refresh_token.rb`.

```ruby
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```

```ruby
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
```

```markdown
class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
```
