## Title
Webhook cross-tenant spoofing — HMAC signs only the raw body, not the `shop-domain`/`topic` headers ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then trusts those header-derived fields as the identity of the originating shop, letting any app-installing user forge webhooks that are processed as if they came from a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate_signature` verifies exactly (and only) `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` checks that HMAC, then immediately forwards the unauthenticated `request.shop` and `request.topic` to the app's handler as trusted metadata: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any unprivileged user can install the app on their own (e.g. free/dev) store and trigger a real Shopify event, receiving a legitimately HMAC-signed `(body, hmac)` pair. Since the signature covers only the body, that same pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (and `x-shopify-topic`) headers swapped to name an arbitrary victim shop. `HmacValidator.validate` still returns `true` because it only re-derives the HMAC from the body, and `Registry.process` hands the forged `shop`/`topic`/`body` combination straight to the handler as if Shopify itself attested to that shop.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the binding that should hold is `hmac-authenticated body == hmac-authenticated shop`, but the actual binding enforced is `hmac-authenticated body != authenticated shop (attacker-supplied header)`.

### Impact Explanation
An attacker who can install the target app on any shop they control (a normal, unprivileged onboarding action) can forge webhook events attributed to any other shop's domain, with body content of their choosing (by controlling what event/data they trigger on their own store). Depending on how the host app keys business logic on `WebhookMetadata#shop` (session/token lookup, data sync, uninstall handling, GDPR webhooks, etc.), this enables cross-tenant data injection or corruption — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: creating/installing a Shopify app on a low-cost or free development store is trivial for any internet user, and replaying an intercepted-by-design (self-received) webhook with altered headers requires no special access, no leaked secrets, and no privileged account — only standard HTTP tooling.

### Recommendation
Bind the shop (and ideally topic) identity into the verified material — e.g., include `shop-domain` and `topic` in the signable string, or independently verify that the header-derived `shop` corresponds to a shop with an active, previously-established session/installation record before dispatching to handlers. At minimum, document and enforce that host apps must authorize `request.shop` against their own installation store rather than trusting it purely because `Registry.process` didn't raise.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Attacker triggers the event on their own store, capturing the genuine `X-Shopify-Hmac-Sha256` header and raw body Shopify sends — this HMAC is valid because it's computed with the app's shared `api_secret_key`.
3. Attacker POSTs that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only checks the body's signature.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though Shopify never sent this event for that shop.
