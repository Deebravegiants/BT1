### Title
Fee-on-transfer / rebasing input tokens over-credit escrow beyond actual balance received in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow with the user-specified nominal input amount instead of the amount actually received by the contract, unlike the mainline EVM `IntentGatewayV2.sol` which measures actual balance deltas. For any ERC20 input token whose `balanceOf()` does not increase by the full transferred amount (fee-on-transfer tokens, deflationary/rebasing tokens), the contract's recorded escrow liability (`_orders[commitment][token]`) exceeds the tokens it actually holds, reproducing the "variable balance token" fund-lock/loss bug class from the referenced report.

### Finding Description
In the no-predispatch branch of `placeOrder`, the contract does: [1](#0-0) 
```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        unchecked { ++i; }
    }
}
```
`safeTransferFrom` is invoked for the nominal `order.inputs[i].amount`, but no post-transfer `balanceOf` check is performed to determine the amount actually received. `reducedInputs[i].amount` (derived from the caller-specified `order.inputs[i].amount` minus protocol fee) is then unconditionally added to the on-chain escrow ledger `_orders[commitment][token]`.

This contrasts directly with the mainline EVM contract, which explicitly measures the actual received amount to defend against exactly this class of token: [2](#0-1) 
```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            uint256 balBefore = IERC20(token).balanceOf(address(this));
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
            order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
        }
        unchecked { ++i; }
    }
}
```
The EVM repo's own test suite confirms this is the intended defensive pattern and that fee-on-transfer tokens are an anticipated input type for this gateway: [3](#0-2) 

Because the Tron deployment omits this balance-delta check in the no-predispatch path, any fee-on-transfer or negative-rebasing ERC20 registered as an intent input token will cause `_orders[commitment][token]` to record more tokens than the gateway actually holds. This is directly analogous to `VTVLVesting._createClaimUnchecked`/`withdraw` recording a promised balance that drifts from the actual `balanceOf()` value — the token bridge/intents equivalent of the original finding.

### Impact Explanation
The escrow ledger becomes under-collateralized relative to the contract's actual token balance. When solvers/relayers later redeem escrow (fill/cancel/refund flows that pay out of `_orders[commitment][token]`), the aggregate promised payouts across orders using the same fee-on-transfer token can exceed the gateway's real balance. Whichever redemption is processed last will revert with insufficient balance, permanently locking that user's fill/refund (DoS) unless external tokens are donated to the contract to cover the shortfall — an unbacked liability that causes fund loss/freezing for the protocol or for order participants, matching the Medium-severity impact accepted in the original report (permanent freezing of funds / unbacked accounting).

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer or deflationary/rebasing ERC20 as an input token — no privileged role required. The Tron token ecosystem includes such tokens, and the contract itself already anticipates fee-on-transfer tokens in intents (as shown by dedicated tests on the mainline EVM version), yet the Tron port fails to replicate the mitigation in its non-predispatch escrow path.

### Recommendation
Mirror the mainline EVM `IntentGatewayV2.sol` pattern in the Tron contract's `placeOrder` no-predispatch branch: snapshot `balanceOf(address(this))` before `safeTransferFrom` and compute the actually-received amount after the transfer, then use that measured amount (rather than the nominal `order.inputs[i].amount`/`reducedInputs[i].amount`) both for the commitment hash and for crediting `_orders[commitment][token]`. Apply the same fix to the predispatch dust-accounting used to compute `_orders[commitment][token] += reducedInputs[i].amount` at line 441, ensuring reduced amounts are derived from measured balances rather than caller-declared amounts.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee on transfer, as modeled by `FeeOnTransferToken` in the test suite) on the Tron deployment.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` with no predispatch call.
3. `safeTransferFrom(user, gateway, 1000e18)` executes; gateway actually receives `990e18` due to the 1% fee.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits `1000e18` (minus any protocol fee) instead of `990e18`.
5. Repeat with additional orders using the same FOT token; the sum of all `_orders[...][FOT]` entries exceeds `FOT.balanceOf(address(gateway))`.
6. When solvers attempt to redeem escrow for later orders (via fill/cancel/refund paths that transfer out `_orders[commitment][token]`), the `safeTransfer` reverts due to insufficient contract balance, permanently locking those users' funds.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
