This confirms the finding. The `ShopifyAPI::Webhooks::Request#shop` field (parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is passed directly into `WebhookMetadata.shop`, which apps use as the tenant identifier for processing, but that field is entirely absent from `to_signable_string`, which only returns `@raw_body`. The HMAC therefore authenticates "this body came from someone who knows the app's shared `api_secret_key`" but says nothing about which shop the request claims to be from.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which signs/verifies only `request.to_signable_string` (the raw body). The `shop` attribute exposed to the app's handler comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content, breaking the identity binding `shop-header == HMAC-covered-shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , while `shop` is read from an HTTP header that is not part of that signed string [2](#0-1) . `Registry.process` gates only on `Utils::HmacValidator.validate(request)` and then forwards `request.shop` straight into `WebhookMetadata`, which is handed to the app's handler as the tenant identity [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` using the app's `api_secret_key` [4](#0-3) . Since the `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop key), any tenant of the app can capture a genuine `(raw_body, hmac)` pair from their own store's webhook traffic and replay it to the app's webhook endpoint with a forged `shopify-shop-domain` header naming a different (victim) shop. The HMAC will still validate because it only covers the body, so `Registry.process` will accept the request and hand the handler a `WebhookMetadata` claiming to be from the victim shop while carrying the attacker's chosen body content.

### Impact Explanation
This breaks the binding `shop asserted in WebhookMetadata == shop actually covered by HMAC verification`, letting one tenant inject or replay events under another shop's identity into any app logic that trusts `data.shop` from the webhook payload (queueing jobs, updating per-shop records, triggering redact/mandatory compliance topics, etc.) — a cross-tenant confusion at the trust boundary this gem is responsible for enforcing. This does not require the target's credentials, only the attacker's own legitimate installation of the app.

### Likelihood Explanation
Medium: exploitation requires the attacker to already be a legitimate app user (installs the app on their own shop) to capture a valid `(body, hmac)` pair, then send a crafted HTTP request to the app's public webhook endpoint with a modified `shop-domain` header and the captured hmac/body — no secrets need to be recovered since the attack replays already-authentic bytes and merely swaps an unauthenticated header.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the value covered by the HMAC computation, or require the app to independently validate `request.shop` against a known/allow-listed shop (e.g., a shop for which the app has an active session) before trusting it, rather than passing the raw header value straight through to `WebhookMetadata`.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target Shopify app, causing Shopify to send a legitimate webhook: raw body `B`, header `shopify-shop-domain: attacker.myshopify.com`, and `shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)` from their own traffic to the app's webhook controller.
3. Attacker sends a new POST to the same webhook endpoint with the same body `B` and same `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header [2](#0-1) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` since the header is not part of the signed string [5](#0-4) .
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes attacker-controlled content as though it came from the victim shop.
