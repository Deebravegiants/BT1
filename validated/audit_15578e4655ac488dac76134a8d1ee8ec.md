### Title
Missing zero-address check in `authorize_nonce_account` permanently bricks and locks lamports in durable-nonce accounts - (File: `programs/system/src/system_instruction.rs`)

### Summary
The system program's `authorize_nonce_account` function accepts any `Pubkey` as the new nonce authority — including `Pubkey::default()` (the all-zero address, which is not a keypair-controlled address but the System Program ID) — with no validation that the new authority is non-default/reachable. This mirrors the InstaRegistry `setAddress` bug class: a caller who omits or mis-supplies the `new_authority` argument (e.g., a front-end/wallet/CLI defaulting a missing parameter to the zero address) will have their nonce account's authority permanently set to an address nobody controls, "burning" their authority over the account.

### Finding Description
`authorize_nonce_account` in `programs/system/src/system_instruction.rs` directly writes whatever `nonce_authority: &Pubkey` is supplied into the nonce account's state, without checking it against `Pubkey::default()`: [1](#0-0) 

The unit test `authorize_inx_ok` explicitly demonstrates that `Pubkey::default()` is accepted as a perfectly valid new authority and results in a successful state transition: [2](#0-1) 

Once the authority field is set to `Pubkey::default()`, all subsequent privileged operations on the nonce account require a signer matching `data.authority`:
- `advance_nonce_account` requires `signers.contains(&data.authority)`: [3](#0-2) 
- `withdraw_nonce_account` requires `check_signer(&data.authority)` before any partial or full withdrawal: [4](#0-3) 
- `authorize_nonce_account` itself requires a signature matching the current `data.authority` before it can be re-authorized: [5](#0-4) 

`Pubkey::default()` (all-zero, `11111111111111111111111111111111`) is the System Program's ID, not an address with a corresponding private key, so no transaction can ever produce a valid signature for it. Once the authority is set to this value, the account can never again be advanced, withdrawn from, or re-authorized — the lamports held by the nonce account (as well as its usefulness as a durable nonce) become permanently inaccessible.

This is directly analogous to the InstaRegistry `setAddress` issue: a missing/blank `_userAddress`/`new_authority` input that a client interprets as the zero address results in unrecoverable loss of control, and no `require`-style check exists in the agave instruction handler to reject it.

### Impact Explanation
This causes concrete, permanent value loss: lamports held in the nonce account (which must retain rent-exempt minimum balance while `Initialized`, and any additional funded balance) become irrecoverably locked, since no key can ever sign as the zero-address authority to withdraw, advance, or re-authorize the account. This is a legitimate unprivileged-user-reachable SVM/nonce path (any user creates and authorizes their own nonce accounts via the System Program), not a validator/operator-role issue, and it falls squarely within the explicitly in-scope "nonce/blockhash replay" category.

### Likelihood Explanation
Likelihood is driven entirely by user/tooling error rather than a deliberate attacker, mirroring the original report's framing: a wallet, CLI, or dApp that fails to strictly validate/require the `new_authority` argument (e.g., a blank form field, an unset variable, or a client library defaulting an optional missing pubkey argument to `Pubkey::default()`) can silently construct a valid, successfully-executing `AuthorizeNonceAccount` instruction that bricks the account. Because the agave program layer performs no defensive check, the mistake is irreversible once committed on-chain.

### Recommendation
Add an explicit check in `authorize_nonce_account` (and ideally in the client-side `system_instruction::authorize_nonce_account` builder) that rejects `Pubkey::default()` as the `nonce_authority`, returning `InstructionError::InvalidArgument` (or a dedicated `SystemError`) similar to protections recommended in the original InstaRegistry report — i.e., disallow the zero address for authority-transfer instructions unless a deliberate "renounce" pathway is explicitly desired.

### Proof of Concept
1. Create and initialize a nonce account normally, with an authority the caller controls.
2. Submit a `System::AuthorizeNonceAccount` instruction (via `system_instruction::authorize_nonce_account`) with `new_authority = Pubkey::default()`, signed by the current authority — the same pattern already exercised (and asserted to succeed) in the existing test `authorize_inx_ok`: [6](#0-5) 
3. Attempt to call `AdvanceNonceAccount`, `WithdrawNonceAccount`, or `AuthorizeNonceAccount` again on the account — all three now require a signature from `Pubkey::default()`, which no private key can produce, so all subsequent calls fail with `MissingRequiredSignature` and the account (and its lamports) is permanently inaccessible.

```rust
pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
```
