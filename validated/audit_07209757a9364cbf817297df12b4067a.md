### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but the `shop` and `topic` values used to route and attribute the webhook to a merchant are read from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` verifies the HMAC strictly against that signable string using `Context.api_secret_key` [2](#0-1) . However, `Request#shop` and `Request#topic` are read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` and `shopify-topic`/`x-shopify-topic` headers, which are never included in `to_signable_string` [3](#0-2) .

`Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values: [4](#0-3) 

The identity binding that should hold is:
`shop_that_Shopify_actually_generated_this_webhook_for == shop_value_the_handler_receives`

Because `shop` (and `topic`) are outside the HMAC's coverage, this equality is not enforced by the gem. Any party capable of producing an HTTP POST with a body/HMAC pair that once validly passed through the app (e.g., a merchant who has this app installed and can observe HMAC values, or any actor who can capture one valid `(body, hmac)` pair for a given topic) can resend that same body+hmac to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates (it only checks the body), and `WebhookMetadata` will be constructed with the attacker-chosen `shop` [5](#0-4) , causing the host application to process/attribute data as belonging to a shop it was not actually sent for — a cross-tenant identity confusion.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: an app relying on `request.shop` (as returned by this gem) to select which merchant's data/session to act on can be made to apply another shop's business logic under a forged shop identity, matching the "cross-tenant access" critical-impact category, since the shop attribution is derived from bytes the HMAC never covers.

### Likelihood Explanation
Medium — exploitation does not require the `api_secret_key`, only a genuinely-issued `(body, hmac)` pair for the same api-secret-keyed app (which any shop that has installed the app will legitimately receive many of, e.g. for low-sensitivity topics such as `app/uninstalled` on their own store), combined with the ability to POST directly to the app's public webhook endpoint with a modified `shop-domain` header — something entirely under the requester's control since headers are attacker-supplied on the HTTP request.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in `Request#to_signable_string`, or otherwise require the host application to independently corroborate the header-derived `shop` against a value that is cryptographically bound to the signed body, before dispatching to a handler keyed by that shop.

### Proof of Concept
1. App installs `MyApp` on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same `client_secret`/`api_secret_key` for both, as is standard for public Shopify apps).
2. Shopify sends a legitimate webhook to the app for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
3. Attacker (operator of `shop-a`, or anyone who intercepts this webhook call) resends the exact same body `B` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` [6](#0-5) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "shop-b.myshopify.com", body: ..., ...)`, so the app processes shop-a's webhook payload as if it belonged to shop-b [5](#0-4) .
