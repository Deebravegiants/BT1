### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header to attribute the payload to a tenant. Because the HMAC signing key (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant who receives (or can trigger) one genuinely-signed webhook can replay that exact body+HMAC pair while swapping in a victim shop's domain in the header, causing the app to process attacker-controlled data as if it belongs to another merchant.

### Finding Description
`Registry.process` gates all processing on a single check: [1](#0-0) 

The HMAC that is validated is computed only over the raw body, per `Request#to_signable_string`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the HMAC value at all: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body, using `Context.api_secret_key` (the single shared app secret used for every installed shop, as shown in the test fixtures using the same `ShopifyAPI::Context.api_secret_key` for shop-specific hmacs): [4](#0-3) 

This is the exact bug class from the referenced report: a field that is acted upon (`request.shop`, used by `Registry.process` to construct `WebhookMetadata` and dispatched to the app's handler) is not covered by the authentication mechanism (`to_signable_string` / HMAC). The equality that should hold — `shop asserted by the request == shop that the HMAC actually authenticates` — is broken, because the HMAC authenticates nothing about `shop`, `topic`, or `webhook_id` at all: [5](#0-4) 

**Before the attacker's request**: a malicious but otherwise unprivileged merchant (call them "shop A") who has legitimately installed the app receives a correctly HMAC-signed webhook for their own shop, with `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: HMAC(body, secret)`, for body content they fully control (they can trigger `orders/create`, `products/update`, etc. with attacker-chosen field values).

**Attacker's action**: they replay this identical `raw_body` + `hmac` header to the app's public webhook endpoint, only substituting `x-shopify-shop-domain: victim-shop.myshopify.com`.

**After**: `HmacValidator.validate` recomputes `HMAC(raw_body, secret)` — which is unchanged since the body wasn't altered — and returns `true`. `Registry.process` proceeds and calls the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, which the host application will treat as authentic data belonging to the victim's tenant.

### Impact Explanation
This breaks tenant isolation: an unprivileged app user can inject arbitrary webhook payloads under another merchant's shop identity with no need for the victim's credentials, the app's `client_secret`, or any access token — only the ability to receive one genuine webhook for their own (attacker's) shop. Depending on how the host application's webhook handler uses `data.shop` (e.g., to look up/mutate per-tenant records, trigger emails, update billing state, or write to a datastore keyed by shop), this enables cross-tenant data corruption or confusion, matching the "cross-tenant access" Critical impact category in scope.

### Likelihood Explanation
High. The only precondition is that the attacker is a legitimate (even free-tier) installer of the target app — which is the normal, unprivileged path for any internet user to interact with a public Shopify app. No secret material beyond what Shopify already delivers to every installed shop is required; the attack is a straightforward header substitution on a replayed HTTP request.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or otherwise cryptographically/authoritatively verify that the shop asserted in the header matches the shop that installed/owns the webhook subscription (e.g., cross-check against the app's own session/shop store using `webhook_id`, or require per-shop webhook secrets where the platform supports them). At minimum, document prominently that `request.shop` must never be trusted for authorization decisions without an independent shop-ownership check by the host application, and consider having `Registry.process` accept an expected/known shop list to validate against.

### Proof of Concept
1. Install the target app on attacker-controlled shop `shop-a.myshopify.com`; register a webhook (e.g. `orders/create`).
2. Trigger an event so Shopify sends a real webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H = HMAC-SHA256(B, api_secret_key)` and `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Capture `B` and `H` (attacker fully controls webhook content, e.g. custom order fields).
4. Re-POST to the same app endpoint with identical body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only verifies `HMAC(B, secret) == H`, unaffected by the header change.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-199` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen `body`, which the host application processes as if it originated from the victim shop.
