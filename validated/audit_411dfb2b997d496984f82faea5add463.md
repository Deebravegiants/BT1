### Title
Direct-Transfer Donation to AMM Vaults Inflates the Coin/PC-to-LP Exchange Ratio, Enabling DOS of Subsequent `Deposit` Calls - (File: `program/src/processor.rs`)

### Summary
Raydium's `Deposit`/`Withdraw` accounting reads live SPL vault balances directly (`amm_coin_vault.amount`, `amm_pc_vault.amount`) rather than an internally tracked reserve, and uses those balances together with the *unchanged* `amm.lp_amount` to compute the LP tokens to mint. Because any account can transfer tokens directly into the AMM's coin/pc vaults (a plain, permissionless SPL Token transfer, no AMM instruction required), an attacker can inflate the coin/pc balance relative to `amm.lp_amount` at any point after pool initialization, driving the per-share price up and causing `mint_lp_amount` for subsequent, smaller `Deposit` calls to round down to zero, reverting with `InvalidInput`. This is the same bug class as the referenced DODO GSP finding (share-price inflation via balance manipulation causing DOS of subsequent LP mints), adapted to Raydium's on-chain accounting model.

### Finding Description
`process_deposit` computes the pool's current reserves via `Calculator::calc_total_without_take_pnl_no_orderbook`, which is fed the raw, live vault balances obtained from `Self::unpack_token_account` [1](#0-0) . It then computes the LP tokens to mint proportionally to `amm.lp_amount` (the pool's internal supply counter, not the live token-mint `supply`):

```
mint_lp_amount = invariant_coin.exchange_token_to_pool(amm.lp_amount, RoundDirection::Floor)
``` [2](#0-1) 

`amm.lp_amount` is only updated by `Deposit`/`Withdraw` flows (`amm.lp_amount = amm.lp_amount.checked_add(mint_lp_amount)` on deposit, `checked_sub` on withdraw) [3](#0-2) [4](#0-3) . Because it does not react to a plain token transfer, while `total_coin_without_take_pnl`/`total_pc_without_take_pnl` are derived from the *live* vault balances, an attacker can send a large "donation" of coin/pc tokens directly to `amm.coin_vault`/`amm.pc_vault` using the standard SPL Token program (bypassing the `Deposit` instruction entirely — no AMM-side check prevents third parties from crediting these vault accounts). This instantly and artificially raises `total_coin_without_take_pnl`/`total_pc_without_take_pnl` without a corresponding increase in `amm.lp_amount`, inflating the effective coin/pc-per-LP-share price.

A subsequent legitimate depositor computing:
```
mint_lp_amount = floor(deduct_coin_amount / total_coin_without_take_pnl * amm.lp_amount)
```
will get `mint_lp_amount == 0` if their deposit is small relative to the donation, and the instruction explicitly reverts:
```
if mint_lp_amount == 0 || deduct_coin_amount == 0 || deduct_pc_amount == 0 {
    return Err(AmmError::InvalidInput.into());
}
``` [5](#0-4) 

This directly mirrors the root cause identified in the referenced DODO GSP report: LP-share accounting derived from spot/live token balances that a third party can manipulate via a bare token transfer ("donation"), causing subsequent proportional-share computations to round to zero and DOS legitimate LP operations.

Note: unlike the DODO GSP pool (which allowed the *first* depositor to set `totalSupply` down to `1 wei`), Raydium's `process_initialize2` permanently withholds a `10^lp_decimals` amount from ever being minted while still counting it in `amm.lp_amount` (`user_lp_amount = liquidity - 10^decimals`, but `amm.lp_amount = liquidity`) [6](#0-5) [7](#0-6) , and the `Withdraw` path forbids `withdraw.amount >= amm.lp_amount`, so `amm.lp_amount` can never collapse to a value near 1 [8](#0-7) . This blocks the exact 1001x-style first-LP-er manipulation described in the DODO report. However, it does **not** prevent the donation-based DOS vector above, since that vector never needs to shrink `amm.lp_amount`; it only needs to inflate the live vault balance relative to a fixed `amm.lp_amount`, which remains fully reachable at any time post-initialization by a single, permissionless SPL token transfer.

### Impact Explanation
An attacker can, with a single transaction transferring tokens directly to the AMM's coin/pc vault (no signer privilege beyond owning the tokens), inflate the coin/pc reserves relative to the internally tracked `amm.lp_amount`. This can cause any subsequent `Deposit` whose deposit size is small relative to the donation to revert with `InvalidInput`, denying legitimate LPs the ability to add liquidity until they deposit proportionally large amounts (which may be economically infeasible). This impairs a core, reachable operation of the protocol (`Deposit`) without requiring any privileged role, matching the Medium-severity DOS classification given to the analogous DODO GSP finding.

### Likelihood Explanation
The precondition is trivial to satisfy: it requires only an SPL Token transfer into the already-known, publicly-readable `amm.coin_vault`/`amm.pc_vault` public token accounts, which is entirely permissionless and requires no interaction with the Raydium AMM program itself. The capital cost scales with how large a DOS window the attacker wants to create (bounded by the ratio `donation / amm.lp_amount`), similar in spirit to the DODO report's costed-attack model, though the specific 1001x "first-LP-er" magnification from that report is blocked here by the locked-minimum-liquidity mechanism in `process_initialize2`.

### Recommendation
Do not rely on live/spot token account balances for LP-share-minting math. Either:
1. Maintain and use an internally tracked reserve (updated only by `Deposit`/`Withdraw`/`Swap` accounting) rather than reading `amm_coin_vault.amount`/`amm_pc_vault.amount` directly for the mint-ratio calculation, or
2. Detect and reconcile "excess" balances (i.e., balances beyond what internal accounting expects) before they can affect share-minting math, similar to a `skim`/`sync` pattern that is access-controlled or accounted for separately from LP issuance.

### Proof of Concept
1. Pool `P` is initialized via `Initialize2` with reserves `C0` (coin) and `Q0` (pc), yielding `amm.lp_amount = L0 = sqrt(C0 * Q0)` [9](#0-8) .
2. Attacker issues a plain SPL Token `Transfer` instruction (not via the AMM program) sending a large amount `D` of the coin token directly into `amm.coin_vault`, and a corresponding proportional amount of pc token into `amm.pc_vault`. `amm.lp_amount` is unaffected (`L0` unchanged) because this bypasses `process_deposit`.
3. A victim now calls `Deposit` with `max_coin_amount = X` where `X` is a normal-sized deposit but small relative to `D`. The pool computes:
   ```
   deduct_coin_amount = X
   mint_lp_amount = floor(X / (C0 + D) * L0)
   ```
   using `total_coin_without_take_pnl` inflated by the donation [10](#0-9) .
4. If `X / (C0 + D) * L0 < 1`, `mint_lp_amount` rounds to `0`, and the instruction reverts at:
   ```
   if mint_lp_amount == 0 || deduct_coin_amount == 0 || deduct_pc_amount == 0 {
       return Err(AmmError::InvalidInput.into());
   }
   ``` [5](#0-4) 
5. Any deposit below the threshold `(C0 + D) / L0` will continue to revert, denying normal-sized LP deposits until the attacker's donation is diluted by comparably large legitimate deposits (or the attacker withdraws nothing back, since the donation was a bare transfer with no LP tokens minted to reclaim).
