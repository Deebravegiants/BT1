### Title
Webhook HMAC only covers the request body, not the `shop`/`topic`/`webhook_id` headers, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all of which are read straight from HTTP headers and are then trusted by `Registry.process` to route the webhook and identify the tenant — are never included in the HMAC-signed material. Since the app's `api_secret_key` is shared across every shop that installs the app, any attacker who has one legitimate, low-privilege installation can capture a real, validly-signed webhook body and replay it with forged `shop-domain`/`topic` headers, producing a request that still passes `HmacValidator.validate` while impersonating a different shop or a different (more sensitive) topic.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated HTTP headers, not from the signed payload: [3](#0-2) 

`Registry.process` then trusts these unverified fields to both route the webhook to a handler and to identify the tenant it belongs to: [4](#0-3) 

The documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" (implying full authenticity of the whole webhook, including which shop/topic it is for) — but the identity binding actually only proves "some entity that knows this app's `api_secret_key`" produced *this exact body byte-for-byte*; it does **not** bind that body to the `shop` or `topic` headers used for dispatch and tenant attribution: [5](#0-4) 

Because `api_secret_key` is a single, app-wide secret (not per-shop), any merchant who installs the app on their own store receives genuinely-signed webhooks. They can capture the `(raw_body, hmac)` pair from one of their own legitimate webhooks and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop and/or the `X-Shopify-Topic` header for a more sensitive topic (e.g. `shop/redact`, `customers/redact`, `customers/data_request`, `app/uninstalled`). The forged request still passes HMAC validation because the signature never covered those headers, breaking the identity equality: `shop authenticated by HMAC` ≠ `shop attributed to the resulting handler call`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged attacker who only controls their own store/installation can make the host application believe a webhook — with attacker-chosen body content — originated from a different merchant's shop and/or for an arbitrary topic. Depending on how the host application's handler uses `data.shop`/`data.topic` (e.g., updating per-shop records, triggering GDPR redaction flows, deactivating the app, importing order/customer data under someone else's shop), this can lead to cross-tenant data corruption, spoofed compliance/redaction actions against a shop the attacker doesn't own, or forged application lifecycle events — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the ability to install the app on one's own store (a normal, unprivileged action any Shopify developer/merchant can perform) plus the ability to send an arbitrary HTTP request to the app's public webhook endpoint — both trivially available to any internet user. No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include `shop`, `topic`, and any other header-derived fields used for routing/tenant attribution in the HMAC-signed material (or otherwise cryptographically bind them to the body), and/or require the host application to independently verify the `shop-domain` header against a known/registered shop before trusting `WebhookMetadata#shop` for tenant-scoped operations. At minimum, update `Request#to_signable_string` so the fields relied upon by `Registry.process` for dispatch and identity cannot be altered without invalidating the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, raw body `B`, and valid `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(api_secret_key, B)`).
2. Attacker resends the exact same body `B` and signature `H` to the app's webhook endpoint, but changes the headers to `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: shop/redact` (or any topic registered by the app).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `HmacValidator.validate` succeeds because it only recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H`, both unchanged: [6](#0-5) 
4. `Registry.process` dispatches to the handler registered for `shop/redact` and calls it with `data.shop == "victim-shop.myshopify.com"`, even though the request never actually originated from or was authorized by that shop: [4](#0-3)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

**File:** docs/usage/webhooks.md (L125-135)
```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
