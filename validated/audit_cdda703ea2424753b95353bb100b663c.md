### Title
Webhook Shop-Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `ShopifyAPI::Webhooks::Registry.process` proves the *body* came from Shopify using the app's shared `api_secret_key`, but does **not** bind that signature to the `shop` (tenant) attributed to the request. Any unprivileged merchant who installs the app can capture a legitimately-signed webhook (body + HMAC) generated from their own store, replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header pointing at a different, victim shop, and the signature check will still pass — because the header is never part of the signed content.

### Finding Description
`Webhooks::Request` extracts `shop` directly from an unauthenticated header: [1](#0-0) 

The value that actually gets HMAC-verified is only the raw body: [2](#0-1) 

`Registry.process` treats a passing `HmacValidator.validate` check as full proof of authenticity for the whole request, and forwards the unauthenticated `request.shop` straight to the handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever signs `verifiable_query.to_signable_string`, which for webhooks is the raw body — the `shop` header is never included in the signable string: [4](#0-3) 

Because `api_secret_key` is a single app-level secret shared across every shop that installs the app (not per-shop), a valid `(body, hmac)` pair produced from *any* installed shop's real webhook traffic is valid for *any* shop-domain header value — the signature carries no tenant identity. The gem's own documented usage pattern demonstrates the shop is trusted at face value for tenant-scoped processing: [5](#0-4) 

The identity binding that is broken:
`shop_header_used_for_tenant_attribution` should equal `shop_that_produced_the_signed(body, hmac)_pair`, but the HMAC only guarantees `body` integrity/authenticity, not the `shop` binding.

### Impact Explanation
This is a cross-tenant vulnerability: an attacker who is nothing more than a normal merchant that installed the app can inject attacker-controlled webhook data (body content of their own choosing, since it's their own shop's resource, e.g. order note/customer fields) and have the gem attribute it to an arbitrary victim shop domain that also installed the app. Any host application following the documented handler pattern (`shop_domain: data.shop`) will process/store this forged data as if it originated from the victim tenant — a cross-tenant data injection/spoofing vector, meeting the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high for any app that: (1) is installable by multiple untrusted merchants (typical for a public/multi-tenant app), and (2) uses the gem's documented `ShopifyAPI::Webhooks::Request`/`Registry.process` flow as-is. The attacker only needs to be an ordinary merchant capable of installing the app and triggering one webhook on their own store (e.g., placing an order) — no privileged credentials, no access token, and no knowledge of `api_secret_key` are required.

### Recommendation
Bind the tenant identity into the verified content, or otherwise cryptographically tie the `shop` value to the signature. Options: reject/flag webhooks where the `shop` header doesn't match an app-known/installed shop with an active session *before* trusting `data.shop` for tenant-scoped writes, and/or include the shop domain header in the signable string alongside the body so the HMAC binds shop-to-body, and/or require per-shop secrets/session correlation before acting on webhook data.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and subscribes to `orders/create`.
2. Attacker creates an order on their own store; Shopify sends a webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and attacker-controlled JSON body.
3. Attacker intercepts/replays this exact `(raw_body, hmac header)` pair to the same webhook endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` against the header value — this still matches since `raw_body` and the HMAC value are unchanged.
5. The registered handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, and any host app following the documented pattern (`shop_domain: data.shop`) stores/processes attacker data under the victim's tenant.
