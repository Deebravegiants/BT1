## Title
Beneficiary can DOS a hyperbridge-attached cross-chain call by front-running their own account nonce - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` executes an optional signed runtime call on behalf of the message's beneficiary. The signature that authorizes this call is bound to the beneficiary's **live** `frame_system` account nonce, read at execution time rather than at signing time. Because the beneficiary fully controls that nonce (any ordinary transaction increments it), they can invalidate the pending cross-chain call's signature simply by transacting on the destination chain before the ISMP message is delivered — the exact same "bump my own nonce to break a pending signature check" pattern described in the reference report, just applied to a token-transfer-plus-call message instead of a liquidation call.

### Finding Description
`Pallet::<T>::on_accept` decodes an optional `SubstrateCalldata { signature, runtime_call }` from the incoming message body and, when a signature is present, verifies it against `(current_account_nonce_of(beneficiary), runtime_call)`: [1](#0-0) 

The nonce used is fetched live from `frame_system::Pallet::<T>::account_nonce(beneficiary)` at the moment the message is processed on the destination chain — not a value fixed when the beneficiary originally signed the payload off-chain: [2](#0-1) 

Because this is the beneficiary's ordinary `frame_system` nonce (incremented by literally any signed extrinsic they submit), they can watch for the pending hyperbridge message (or simply always keep their nonce moving) and submit an unrelated transaction before the relayer's `handle_unsigned` message lands. Once their nonce advances, the previously-signed `(nonce, runtime_call)` hash can never match again — `frame_system` nonces are monotonically increasing and compared for exact equality, so there is no way to "re-sign" against the same nonce value after the fact without the original signer minting a brand new signature.

`handle_unsigned` is `#[frame_support::transactional]`, and `handlers::request::handle` deletes the module's request receipt whenever `on_accept` returns an error, explicitly to allow retries: [3](#0-2) [4](#0-3) [5](#0-4) 

So every relay attempt for that request will re-run the whole `on_accept` (mint/transfer included, then rolled back by the `transactional` wrapper), fail again on the now-permanently-stale nonce check, and be retried again — an unbounded, unpriced retry loop for that specific message until it eventually times out on the source chain (or forever, if no timeout was configured).

### Impact Explanation
This is a message-delivery-denial vector reachable by an unprivileged actor (the beneficiary of an inbound `pallet-hyper-fungible-token` message) with only a single ordinary transaction:
- The composed cross-chain instruction (transfer + authorized call) can never be delivered as intended — the signature can never again satisfy the exact-nonce check once the beneficiary transacts, satisfying the "route unable to deliver messages" criterion for this specific commitment.
- Every relayer that attempts to deliver/retry this request wastes gas and effort on a request that is now guaranteed to fail, until the source-side timeout eventually reclaims the escrowed/burned funds back to the *original sender* — not the beneficiary that blocked it, meaning any counterparty relying on the beneficiary-authorized call being executed (e.g., a downstream contract expecting balance movement plus a specific follow-up call) is left in limbo for the full timeout window, and forever if `timeout == 0`.
- Because `on_accept` is `transactional`, this doesn't cause fund loss (the token mint/transfer is rolled back on each failed attempt), but it is a straightforward, cost-asymmetric DOS on a specific class of hyperbridge cross-chain messages, directly analogous to the referenced liquidation-signature-nonce race.

### Likelihood Explanation
Likelihood is high for any message that includes signed `call_data`: the beneficiary needs no privileged role, no coordination with a relayer, and no mempool front-running skill beyond submitting any ordinary transaction on the destination chain before the ISMP message is delivered (which typically takes multiple blocks/consensus-proof latency, giving ample time).

### Recommendation
Do not bind the authorization to the beneficiary's live `frame_system` nonce. Instead:
- Use a dedicated, message-scoped nonce/replay-protection value (e.g., derived from the source request's own commitment/nonce) that is fixed at message-creation time and stored/consumed by the pallet itself, independent of the beneficiary's unrelated on-chain activity, or
- Have the beneficiary sign the request's `PostRequest` commitment (or another value fixed at dispatch time) instead of a mutable account nonce, so nothing the beneficiary does afterward on the destination chain can invalidate a signature that was valid when created.

### Proof of Concept
1. Alice sends an HFT message from chain A to chain B with `call_data = SubstrateCalldata { signature: Some(sig over (nonce_0, call)), runtime_call: call }`, where `nonce_0` is Bob's (the beneficiary's) `frame_system` nonce on chain B at signing time.
2. Before the relayer submits `handle_unsigned` with this request, Bob submits any ordinary extrinsic on chain B, bumping his nonce from `nonce_0` to `nonce_0 + 1`.
3. The relayer delivers the message; `on_accept` reads `account_nonce(Bob) == nonce_0 + 1`, recomputes the hash over `(nonce_0 + 1, call)`, which no longer matches the signature computed over `(nonce_0, call)`. Verification fails with `HftError::SignatureVerificationFailed`.
4. Because `handle_unsigned` is transactional and the failed callback causes the receipt to be deleted, the mint/transfer is rolled back and the request remains re-deliverable, but the signature check will fail identically on every future attempt (Bob's nonce is now permanently ahead of `nonce_0`), so the calldata can never execute; the request cycles until timeout, at which point funds return to Alice (the original sender), not Bob.
