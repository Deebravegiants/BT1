### Title
Order placer can set `output.beneficiary` to the zero address, permanently burning their own destination-chain output funds - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntentGatewayV2.placeOrder` accepts an `Order.output.beneficiary` (a raw `bytes32`, cast to `address`) supplied entirely by the order creator, with no validation that it is non-zero. When a solver later fills the order, the gateway sends the destination-chain output tokens directly to this attacker/user-controlled beneficiary address without ever checking for `address(0)`. This mirrors the reported `TokenFactory` bug where a user-controlled recipient field (`creatorFeeRecipient`) can be set to `address(0)`, causing funds destined for that party to be silently and irrecoverably burned instead of reverting or being redirected.

### Finding Description
`Order.output.beneficiary` is a user-supplied `bytes32` field set when the order is placed via `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`). Neither `placeOrder` nor any of the fill paths validate that the decoded address is non-zero.

In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:59`):
```solidity
address beneficiary = address(uint160(uint256(order.output.beneficiary)));
```
this value is used directly as the transfer target for both native ETH transfers (`beneficiary.call{value: beneficiaryTotal}("")` at line 99) and ERC-20 transfers (`IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` at line 102).

The same unchecked pattern exists in the cross-chain fill path `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:170`) and in the general escrow-release helper `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:452-469`), which similarly casts `body.beneficiary` without a zero check before calling `_sendValue(beneficiary, amount)` or `IERC20.safeTransfer(beneficiary, amount)`.

Because a plain ETH transfer to `address(0)` via a low-level `.call` succeeds (it is not a contract call that reverts), and because the destination output tokens are pushed to `beneficiary` unconditionally, an order whose `output.beneficiary` is `bytes32(0)` will have its promised output permanently burned the moment a solver fills it — exactly analogous to the referenced `TokenFactory._sendFees` bug where `creatorFeeRecipient == address(0)` burns the creator's fee share instead of reverting.

### Impact Explanation
Any order placed with `output.beneficiary == bytes32(0)` results in permanent loss of the order's entire destination-side value once filled — the solver still delivers the output tokens (to the burn address) and the corresponding escrowed input is released to the solver as normal, so the transaction completes successfully while the user's intended proceeds are irrecoverably destroyed. This is a permanent freezing/loss-of-funds condition triggerable by a single unprivileged `placeOrder` call, matching the "Medium" impact class of the referenced report (self-inflicted misconfiguration that the protocol should defensively reject rather than silently execute).

### Likelihood Explanation
`placeOrder` is a fully permissionless, single-transaction entry point open to any user; no special conditions are required beyond supplying a zero `beneficiary`, which can happen from wallet/integration bugs, encoding mistakes (e.g., `abi.encode`/padding errors when constructing the 32-byte beneficiary), or malicious front-end tooling. The lack of a guard makes this trivially reachable, and once a solver fills the order the loss is final and cannot be reversed via cancellation (the order is marked `_filled`).

### Recommendation
Add a validation check in `placeOrder` (and in `_withdraw`/`_fillSameChain`/`_fillCrossChain` as defense-in-depth) that reverts with `InvalidInput()` if `order.output.beneficiary == bytes32(0)`, mirroring the existing zero-address checks already present elsewhere in `IntentsBase._validateParams` (e.g. `evm/src/apps/intentsv2/IntentsBase.sol:592-598`). Alternatively, if a zero beneficiary is not rejected outright, route the funds to a recoverable protocol-owned address instead of burning them.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder` with `order.output.beneficiary = bytes32(0)` and valid `inputs`/`output.assets`, escrowing input tokens. [1](#0-0) 
2. A solver calls `fillOrder`, which for a same-chain order invokes `_fillSameChain`.
3. Inside `_fillSameChain`, `beneficiary` is derived from `order.output.beneficiary` with no zero check, and the solver's output tokens (native ETH via `.call` or ERC-20 via `safeTransferFrom`) are sent to `address(0)`, permanently burning the funds meant for the order placer. [2](#0-1) 
4. The fill still succeeds, the order is finalized (`_filled[commitment] = msg.sender`), and the solver receives the escrowed input tokens as normal — the user's destination-side funds are unrecoverable. [3](#0-2)
