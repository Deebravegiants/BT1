Based on the code I found, there's a concrete identity-binding flaw in the webhook processing path where the HMAC signature covers only the request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used by the application are taken from unauthenticated HTTP headers.### Title
Webhook shop/topic/id identity spoofing due to HMAC covering only the raw body, not the Shopify headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` treats as verified/trusted are all pulled from HTTP headers that are never included in that signable string. This breaks the equality "shop the HMAC authenticates == shop the handler acts on," analogous to the referenced report's pattern of a field acted on but not covered by the HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other identity-bearing attributes are read directly from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.shop` and `request.topic` to build the metadata handed to the app's webhook handler: [3](#0-2) 

`HmacValidator.validate` simply recomputes the HMAC over `to_signable_string` (the body) using the app's shared `api_secret_key` and compares it to the received signature — it has no knowledge of, or binding to, the shop/topic/webhook_id headers: [4](#0-3) 

Because the `client_secret`/`api_secret_key` used to sign webhooks is the same for every shop that has the app installed (it's an app-level secret, not a per-shop secret), any merchant who installs the app receives real, validly-signed webhook deliveries whose HMAC depends solely on the body bytes. An attacker who is a legitimate (if malicious) merchant of the app can capture one such delivery and replay it to the app's webhook endpoint after altering only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` still returns `true` because the raw body/HMAC pair is untouched, yet `Registry.process` passes the attacker-controlled `shop` value into `WebhookMetadata`, which is exactly the value host applications are documented to rely on for tenant identification.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: the library asserts (via a passing `Utils::HmacValidator.validate` check) that a webhook is an authentic, Shopify-originated event, and it exposes `data.shop` in `WebhookMetadata` as the "verified" shop, but that shop value carries no cryptographic binding to the signature. Any app that keys tenant lookups, data writes, or entitlement decisions off `WebhookMetadata#shop` (the officially documented handler contract) can be made to apply attacker-supplied webhook bodies to a victim shop's record, enabling cross-tenant access/write — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation only requires being able to install the app on one's own store (a normal, unprivileged action for any Shopify merchant) and the ability to send an arbitrary HTTP request with modified headers to the app's public webhook endpoint — no access token, `api_secret_key`, or privileged account is needed. The attacker never needs to forge an HMAC; they merely relabel an HMAC-body pair they legitimately received.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable payload (or otherwise cryptographically bind them, e.g., by having `to_signable_string` combine header values with the body before hashing), so that `HmacValidator.validate` fails if any of these identity fields are altered independently of the body.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; the app registers a webhook (e.g., `orders/create`) delivered to `https://victim-app.example.com/webhooks`.
2. Shopify sends a real webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker replays the exact same body `B` and HMAC header `H` to the same endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds because `B`/`H` are unchanged. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-chosen data as if it originated from the victim's shop.
