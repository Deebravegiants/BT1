### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (tenant identity) is taken from the unauthenticated `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` HTTP header. `Utils::HmacValidator.validate` only proves that the *body* was signed with the app's `api_secret_key`; it says nothing about which shop that body belongs to. `Webhooks::Registry.process` nonetheless treats the header value as authoritative and passes it straight into the handler as the tenant identifier.

### Finding Description
The identity binding that should hold is:

`verified_shop` (the shop tied to the cryptographically-verified payload) `==` `attributed_shop` (the shop value the handler acts on)

In this code path that equality does not hold:

- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC binds nothing but the JSON body.
- `Request#shop` simply reads the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no cryptographic linkage to the body or to the HMAC [2](#0-1) .
- `Registry.process` validates the HMAC over the request, then forwards `request.shop` unchanged into the handler as the tenant for the delivered event [3](#0-2) .

Because the api's `api_secret_key` is shared across every shop that has the app installed (it's a per-app secret, not a per-shop secret), any party who can obtain one genuinely-signed `(raw_body, hmac)` pair for *any* shop — e.g., by installing the target app on their own free/dev store and capturing a real webhook delivery — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass, because it only checks that the body was signed with the correct secret, not who the body is "from." `Registry.process` then hands the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain [4](#0-3) , even though the payload was never associated with that shop by Shopify.

This differs from `AuthQuery` in `lib/shopify_api/auth/oauth/auth_query.rb`, where `shop` is explicitly included inside `to_signable_string` and thus IS bound by the HMAC [5](#0-4) . The webhook `Request` class has no equivalent binding for `shop`, `topic`, or `webhook_id` — none of the identifying headers are part of the signed content.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook delivery: an unprivileged actor who can obtain any one valid signed webhook body for the shared app secret (trivially available to anyone who installs the app on a store they control, including via a free development store) can cause the host application to process that event as if it originated from an arbitrary other merchant. Depending on which webhook topic is replayed (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, `customers/data_request`), this can trigger cross-tenant state changes — deactivating another shop's integration, deleting or "redacting" another shop's data, or falsely triggering GDPR data-request/erasure flows for a shop that never made such a request. This is cross-tenant access/action caused entirely by a gap in this gem's verification logic, not by anything the host application does incorrectly (the gem tells the host "this HMAC is valid" without ever validating the shop it is being attributed to).

### Likelihood Explanation
Likelihood is moderate to high in practice for any developer who has installed the target app on a store they control: they routinely receive real, validly-signed webhook deliveries from Shopify for their own shop, satisfying the "possession of one legitimate (body, hmac) pair" precondition without needing to break cryptography or obtain the app's secret. The only additional step is resending that captured request to the app's public webhook endpoint with a modified `shop-domain` header, which requires no authentication and no knowledge of the `api_secret_key`.

### Recommendation
- Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed content, or otherwise cryptographically bind the shop domain to the signed body, so `HmacValidator.validate` cannot pass for a body/shop combination that Shopify never actually produced together.
- At minimum, document prominently that `Webhooks::Request#shop` is derived from an unauthenticated header and must not be used as a trust boundary; recommend that consuming applications independently correlate the delivered shop against their own installation record (e.g., an existing offline session for that shop) before acting on the payload.
- Consider validating that the webhook's declared `shop` matches an actively installed shop for this app before dispatching to a handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (free/dev) store `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook, e.g. `app/uninstalled`, to the app's endpoint, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — captured by the attacker (e.g., via a proxy they control, or by simply being the receiving app's operator for a short-lived test install).
3. Attacker resends the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. In `ShopifyAPI::Webhooks::Registry.process`:
   ```ruby
   raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
   # passes -- HMAC only checked over @raw_body, unaffected by header change
   handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
   # shop == "victim-shop.myshopify.com", attacker-controlled
   ``` [3](#0-2) 
5. The registered handler executes its `app/uninstalled` logic (e.g., deleting stored tokens/data) attributing the event to `victim-shop.myshopify.com`, even though Shopify never sent that shop this event.
