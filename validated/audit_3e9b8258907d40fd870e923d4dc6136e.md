### Title
Unbounded ERC-20 pull by router via `approveUnlimited` lets attacker drain stranded `inputToken` balance beyond proof-constrained amount - (File: contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
In `LifiExternalAction.callRouter`, `approveUnlimited(inputToken, router)` grants the router a `type(uint256).max` allowance before invoking `router.call(externalActionMetadata)`. The `inputAmount` parameter, derived from the Groth16-proof-constrained `deltaAmounts[0]`, is never used to bound the ERC-20 branch's router call - the router's own calldata decides how much `inputToken` it pulls via `transferFrom`. If any `inputToken` balance already sits in the contract (e.g., stranded from a prior transaction), an attacker can craft `externalActionMetadata` that pulls that leftover balance too, so the tokens actually removed from the action exceed what the proof's public input vector says Hinkal transferred in for this transaction.

### Finding Description
The equality that should hold is: `uint256(-deltaAmounts[0])` (the amount Hinkal sent into the action for this proof, constrained by the circuit's public inputs via `formBasicInput`) `==` the amount of `inputToken` actually pulled from the action's balance by `router` in the same call.

Trace:
- `ExternalActionSwap.swap` (contracts/external-actions/swaps/ExternalActionSwap.sol:40-68) computes `inputAmount = uint256(-deltaAmounts[0])` and passes it to `callRouter`.
- `LifiExternalAction.callRouter` (contracts/external-actions/swaps/LifiExternalAction.sol:16-36), for the ERC-20 branch, calls `approveUnlimited(inputToken, router)` then `router.call(externalActionMetadata)`. `inputAmount` is not passed to, or checked against, the router call at all in this branch (unlike the native-coin branch, where `inputAmount` at least bounds `msg.value`).
- `approveUnlimited` (contracts/TransfererBase.sol:32-43) sets the allowance to `type(uint256).max` whenever the current allowance is below half of max, and leaves it there indefinitely (it is never reset to zero after the swap, and is reused across transactions/actions).
- The router's calldata (`externalActionMetadata`), fully attacker-controlled, decides exactly how much `inputToken` is pulled from `address(this)` (the action) via `transferFrom`. Nothing in `swap()` or `callRouter` measures or enforces that the pulled amount equals `inputAmount`; only the resulting `outputToken` balance diff (`swappedAmount`) is measured, and `swappedAmount` is checked only against slippage (`circomData.slippageValues[1]`), not against the `inputToken` consumed.
- Because the allowance is unlimited and persists across calls, any `inputToken` balance that ends up sitting in the action contract (e.g., left behind by a previous user's partially-filled/stranded swap that didn't send an output back for the entire input, or dust from rounding) is available for the router to pull on a subsequent, unrelated transaction, as long as the attacker's `externalActionMetadata` requests it.
- None of the existing guards close this gap: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the circuit's `inTotal + amountChanges === outTotal` constraint only bind what Hinkal transfers *into* the action (`amountChanges[0]`); they say nothing about what the router is allowed to pull back *out* of the action's balance once `approveUnlimited` has been granted. The slippage checks only bound the output side.

Attacker's exact call: attacker calls Hinkal's transact flow with `deltaAmounts[0]` set small (minimizing the proof-constrained amount actually sent to the action), while `circomData.externalActionData.externalActionMetadata` encodes a router call whose `transferFrom` pulls `smallAmount + leftoverStrandedBalance` from the action.

### Impact Explanation
Tokens stranded/left in the `LifiExternalAction` contract belonging to a different flow (or simply protocol dust) can be siphoned out through the router by an attacker who only proves a small `amountChanges[0]`, using an unlimited allowance that was never scoped to the current transaction's proof-constrained amount. This is a proof-coverage bypass: the amount leaving the action contract via the router exceeds the amount the public input vector attested to. Depending on where the stranded balance originates (unclaimed victim input, protocol dust, rounding remainder), this can constitute direct theft of another party's in-flight funds, matching the Critical category ("direct theft of shielded or in-flight user funds" / "proof or nullifier verification bypass" on the input side).

### Likelihood Explanation
Exploitability depends entirely on the action contract actually holding a non-zero `inputToken` balance beyond what the current transaction sends it. The `swap()`/`callRouter()` design does not zero out or track per-call input consumption, and `approveUnlimited` deliberately keeps a standing max allowance across calls for gas efficiency, which is the root enabler. Whether a "leftover balance" precondition is realistically reachable (via partial fills, a previous failed/aborted flow, or simple token dust from a prior swap round) is implementation/router-behavior dependent and could not be fully confirmed from the available files alone - the LI.FI router's fill/partial-fill semantics and how `runAction` is invoked from `Hinkal._externalTransact` (whether it sends exactly `inputAmount` or could leave residue) were not fully traceable within the indexed context. The theft amount is capped at the accumulated leftover balance and cost to the attacker is just one transaction with a proof for their own small UTXO, so it would be repeatable each time leftover balance accrues.

### Recommendation
Bound the router's pull to exactly `inputAmount` for the current call: use `approveERC20Token(inputToken, router, inputAmount)` (exact, per-call approval reset to 0 before and after) instead of `approveUnlimited`, or explicitly measure the `inputToken` balance before/after the router call and `require(balanceBefore - balanceAfter <= inputAmount)` (or `== inputAmount`), reverting/refunding any excess. Additionally revoke the router's allowance back to zero at the end of `callRouter` so no standing allowance persists across unrelated transactions.

### Proof of Concept
Foundry test outline:
1. Deploy `LifiExternalAction` with a mock router and a mock ERC20 `inputToken`/`outputToken`.
2. Simulate a "first victim" leftover state: mint/transfer some `inputToken` directly to the `LifiExternalAction` contract address (representing stranded balance) without going through a full accounted swap.
3. Craft attacker's `CircomData`/`deltaAmounts` with `deltaAmounts[0] = -smallAmount` (small proof-constrained input).
4. Craft `externalActionMetadata` for the mock router such that its `transferFrom(action, router, smallAmount + leftoverAmount)` call succeeds because of the unlimited allowance from `approveUnlimited`.
5. Call `swap`/`runAction` with the crafted proof/circomData.
6. Assert: `inputToken.balanceOf(router) - routerBalanceBefore != smallAmount` (i.e., `!= uint256(-deltaAmounts[0])`), proving the router pulled more than the proof-constrained amount, draining the previously stranded leftover balance.
