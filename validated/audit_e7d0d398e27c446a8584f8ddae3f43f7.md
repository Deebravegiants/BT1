### Title
Donation attack causes an unrecoverable arithmetic-underflow revert (Panic) in `Router._computeBuy`'s overflow-cap branch, DoS'ing large buys and the curve's supply-exhaustion graduation trigger - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at `pair.tokenBalance()` and back-calculates `amountInUsed` from `reserveToken - tokensOut` whenever the curve-implied output exceeds the pair's real token balance [1](#0-0) . This subtraction assumes `reserveToken ≥ realBalance` always holds. An unprivileged attacker can break that assumption by buying a large chunk of the curve and donating the tokens straight back to the `Pair` via a plain `IERC20.transfer`, which increases `pair.tokenBalance()` (`realBalance`) without touching the stored `reserveToken` [2](#0-1) . Once `realBalance > reserveToken`, any subsequent buy whose curve-implied `tokensOut` exceeds `realBalance` enters the cap branch and computes `cappedReserveToken = reserveToken - tokensOut` (`= reserveToken - realBalance`), which underflows and reverts with Solidity's arithmetic Panic (0x11) under 0.8.24's default checked-math semantics.

### Finding Description
The protocol's own analogous view function, `Bonding.previewLtUntilGraduation`, was patched against exactly this scenario with an explicit guard: `if (realBalance >= reserveToken) return ltUntilThreshold;` [3](#0-2) . The accompanying test comment confirms the bug class was real and reachable: *"A TOKEN donation that drives `realBalance > reserveToken` previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg, cascading into a `Zap.buy` DoS."* [4](#0-3) 

However, `Router._computeBuy` — the function that actually executes every curve buy through `Router.buy` — has **no equivalent guard**:
```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // underflows if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [1](#0-0) 

The invariant that would normally prevent this ("virtual reserve always exceeds real balance") is explicitly documented as holding only under *honest* buy/sell flow — the test suite calls it out as the property that makes `cappedReserveToken == 0` "unreachable... if it ever ceased to hold" [5](#0-4) . A direct-to-pair token donation is exactly the kind of state mutation the invariant test never exercises against `_computeBuy`, because it's driven purely by `IERC20.transfer`, which is outside `Router`'s and `Pair`'s control (`Pair` has no `onTransfer` hook and `_computeBuy` never reads `reserveToken` against `realBalance` before subtracting).

Reachability: any unprivileged trader can (1) buy a large fraction of the curve supply through `Zap.buy` (no privilege required — normal user flow), and (2) `transfer` the purchased `Token` directly to the `Pair` address (a plain ERC20 transfer, explicitly listed as in-scope in the rules). This is the identical staging sequence the protocol's own regression test (`_stageDonationAttack`) uses to reproduce `realBalance > reserveToken` [2](#0-1) . Once staged, any later buy — by the attacker or any other trader — whose curve-implied `tokensOut` would exceed the (now donation-inflated) `realBalance` trips the cap branch and reverts with an unrecoverable Panic instead of a graceful revert or a correct cap.

### Impact Explanation
This is a repeatable-crash / denial-of-service class matching CVE-2018-2775's bug class (a crafted, low-privilege-reachable input causing the engine to hang/crash rather than serve the request):
- Any buy sized to sell out the remaining real token balance on a donation-poisoned curve permanently reverts with a raw arithmetic Panic instead of executing or cleanly capping — bricking the curve's "supply exhaustion" graduation trigger (`tokenBalance() == 0`) for any buy large enough to attempt it.
- Because `Router.buy` (and therefore `Bonding.buy`/`Zap.buy`) reverts deep inside the AMM math rather than with a named, catchable error, integrations (frontend previews, keeper bots, other traders) see an opaque low-level failure with no recovery path short of the USD-leg trigger firing via LT exchange-rate appreciation — which may never happen for a flat-priced LT.
- No admin or protocol-level function can un-donate tokens from the `Pair` while `Lifecycle.Curve` is active (there is no skim/rescue path pre-graduation), so the DoS persists until conditions outside anyone's control (LT rate movement) resolve it, or forever if they don't.

This satisfies "concrete... permanent freezing of trader ... funds" in spirit: legitimate large buyers are locked out of completing purchases on the poisoned curve, and the curve can become permanently stuck unable to reach the supply-exhaustion graduation trigger.

### Likelihood Explanation
High. The attack requires only: (1) a normal-sized `Zap.buy` call to acquire tokens (standard user action, no special timing or privilege), and (2) a single unprivileged `Token.transfer(pair, amount)` call. Both are explicitly in the rules' allowed reachable-action list ("direct ERC20 transfers of a launched Token... into Pair"). The exact staging sequence is already implemented and exercised by the protocol's own test helper `_stageDonationAttack`, confirming it's cheap and mechanically straightforward — the only cost is the LT spent on the initial buy, most of which is recoverable by selling the surplus token supply back before or after donating a portion.

### Recommendation
Add the same guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy`: before computing `cappedReserveToken = reserveToken - tokensOut`, check `if (realBalance >= reserveToken) { ... }` and take a safe fallback path (e.g., treat the cap as fully consuming `amountIn` while denying `tokensOut` beyond the actual transferable balance, or explicitly revert with a named error) rather than let the subtraction underflow into an unstructured Panic. This should be covered by a new invariant test mirroring `test_donation_realBalanceExceedsReserveToken` but driving `Router.buy`/`Bonding.buy` directly at cap-triggering size, to confirm the buy no longer reverts with an arithmetic Panic once the guard is added.

### Proof of Concept
1. Launch a token normally through `Bonding.launch` / `Zap.createToken`.
2. Attacker (any unprivileged trader) calls `Zap.buy(tokenAddr, usdcAmount, 0, referrer)` sized so the curve mints `tokensOut > LP_RESERVE` (250M) — mirrors `_stageDonationAttack`'s sizing rationale, spending roughly one-third of the virtual LT reserve [6](#0-5) .
3. Attacker calls `Token(tokenAddr).transfer(pairAddr, donatedTokens)` with the tokens just purchased, pushing `pair.tokenBalance() > reserveToken` [7](#0-6) , confirmed by the existing test `test_donation_realBalanceExceedsReserveToken` [8](#0-7) .
4. Any subsequent trader calls `Zap.buy` with an amount large enough that the curve-implied `tokensOut` (pre-cap) exceeds the now-inflated `realBalance` — this trips the `if (tokensOut > realBalance)` branch in `Router._computeBuy` and reverts with Panic(0x11) instead of executing, because `cappedReserveToken = reserveToken - tokensOut` underflows (`tokensOut` was just set to `realBalance > reserveToken`) [1](#0-0) .
5. This buy fails deterministically for every subsequent trader attempting a cap-triggering purchase size, and the curve cannot reach `tokenBalance() == 0` via this path — the supply-exhaustion graduation trigger is effectively DoS'd unless the LT exchange rate independently pushes the USD-leg trigger.
