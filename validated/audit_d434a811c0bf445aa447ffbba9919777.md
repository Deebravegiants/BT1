### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from the JWT `dest` claim without validating it against the trusted Shopify domain allow-list - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange POST (which carries `client_id` and `client_secret`) directly from the `dest` claim of the caller-supplied session token, with no call to `Utils::ShopValidator.sanitize!`. Every sibling method that builds the same kind of request (`client_credentials`, `refresh_token.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly runs the `shop` value through `Utils::ShopValidator.sanitize!` before using it to construct the HTTP client. `exchange_token` skips this step, breaking the intended equality "host that receives the `client_secret`" == "host validated as a trusted Shopify domain."

### Finding Description
`exchange_token` decodes the session token and takes the shop straight from `JwtPayload#shop`, which is simply `dest.gsub("https://", "")` with no domain-format validation: [1](#0-0) 

`JwtPayload#initialize` only checks that `aud == Context.api_key`; it never checks that `dest`/`iss` matches a trusted Shopify domain shape.

That unvalidated value is then used to build the `Session` and the `HttpClient`, and is passed to the endpoint that sends the app's `client_secret`: [2](#0-1) 

`Clients::HttpClient#initialize` builds the outbound URL directly from `session.shop` when no `Context.api_host` override is set: [3](#0-2) 

Compare this to the three sibling flows in the same file/module that perform the identical "send client_secret to `{shop}/admin/oauth/access_token`" operation, but first pass `shop` through `Utils::ShopValidator.sanitize!`, which only accepts hosts on `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) and explicitly rejects userinfo/`@`-based host confusion and non-Shopify suffixes: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The identity binding that should hold is: `host contacted with client_id/client_secret == host verified by ShopValidator as a genuine Shopify domain`. In `exchange_token` this becomes `host contacted with client_id/client_secret == raw dest claim from the JWT`, which is a strictly weaker (and inconsistent) check compared to every other code path in the same module that performs an equivalent credential-bearing POST. This mirrors the report's bug class: a check that should be strict/exact (bind the recipient host to a validated allow-list) is instead permissive (accept whatever value flows through, unchecked against the same allow-list applied elsewhere).

### Impact Explanation
If the `dest` claim value can ever diverge from a genuine, well-formed Shopify domain (e.g., through host/embedding edge cases, proxy/CDN domain confusion, or any code path that constructs a session token with attacker-influenced `dest`), the app's `client_id` and `client_secret` would be transmitted via an HTTPS POST to that host. This is SSRF carrying the app's OAuth credentials — a High-severity issue per the rubric, since it leaks the `client_secret` to a non-Shopify endpoint and could enable credential capture/replay.

### Likelihood Explanation
`JWT.decode` in `JwtPayload` does cryptographically verify the token against `Context.api_secret_key` (or `old_api_secret_key`), which limits who can produce a token with an arbitrary `dest`. However, this is exactly the class of "checked signature but unchecked domain-shape" gap the analog targets: the code performs a weaker, inconsistent check (no `ShopValidator` call) compared to the pattern used everywhere else this exact operation occurs in the codebase, indicating the omission is a genuine defect in the identity-binding logic rather than intentional design (there is no explanation why `exchange_token` should be exempt while `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token` all sanitize).

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (as is already done in `migrate_to_expiring_token`, `client_credentials`, and `refresh_token.refresh_access_token`) before constructing `shop_session` and issuing the `HttpClient` request that carries `client_id`/`client_secret`. Additionally, consider validating the `dest`/`iss` claim shape inside `JwtPayload` itself so all consumers of `JwtPayload#shop` get this guarantee for free.

### Proof of Concept
Not independently reproducible from this gem's code alone without a JWT signed with the app's `api_secret_key` containing an attacker-controlled `dest` claim; conceptually:
1. Obtain/produce a session token whose `dest` claim is not a genuine Shopify domain (the exact mechanism by which such a token could reach `exchange_token` is outside this gem's code and not verifiable from the indexed files).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` is instantiated with `session.shop` equal to the unsanitized `dest` value [8](#0-7)  and the POST containing `client_id`/`client_secret` is sent to `https://#{dest}/admin/oauth/access_token` [3](#0-2) , unlike the sibling flows which would have rejected an untrusted `dest`/`shop` via `Utils::ShopValidator.sanitize!` [9](#0-8) .
