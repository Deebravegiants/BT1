Based on my research, I found a genuine analog to the reported bug class in the `VWAPOracle` contract, which serves as Hyperbridge's `IIntentPriceOracle` for the Intents system.

### Title
Unbounded, never-expiring cumulative spread in `VWAPOracle.spread()` allows manipulation of the price guardrail used to validate solver fills - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle` implements `IIntentPriceOracle`, tracking a running weighted-average "spread" per `(sourceChain, token)` pair that solvers' fills are compared against. Like the reported `getPrice` bug — where a cached price is returned as valid with no check on how stale the underlying update actually is — `VWAPOracle.spread()` returns a value derived from `CumulativeSpreadData` that is never invalidated, decayed, or bounded by time, even though the struct tracks a `lastUpdate` timestamp.

### Finding Description
`recordSpread` accumulates every fill's weighted spread into `weightedSpreadSum`/`totalVolume` forever, and stamps `lastUpdate = block.timestamp` [1](#0-0) , but `lastUpdate` is written and never read anywhere in the contract. The public view `spread()` simply divides `weightedSpreadSum` by `totalVolume` with no staleness check, no decay, and no consideration of how old or how few the contributing fills are: [2](#0-1) .

This mirrors the analog class in the report: a "last known" value is treated as current/valid without verifying its freshness. Here the flaw is stronger — there is no freshness check mechanism at all (not even a superficial timestamp-equality check), so a value influenced by fills from any point in the contract's history — including a single manipulative fill long ago — is returned with full weight indefinitely.

### Impact Explanation
Because `IIntentPriceOracle.spread()` is the mechanism the Intents system relies on to price/validate same-token cross-chain swaps, an unbounded historical average can be poisoned once and then relied upon by the protocol indefinitely (or until diluted by enough offsetting volume, which an attacker controls the pace of). A solver/filler that funds a series of low-cost fills to skew `weightedSpreadSum`/`totalVolume` can shift the reported "expected" spread in their favor, and — since staleness is never checked — that skewed baseline remains authoritative for any future order validated against `spread()`, regardless of how much time has passed since the fills that produced it. This can misprice legitimate order flow and enable a filler to extract more favorable terms on subsequent large fills than the true current market spread would allow, causing an economic loss to depositors/protocol relying on the oracle for correctness of the intents settlement price.

### Likelihood Explanation
`recordSpread` is only callable by `_intentGateway` per the `restrict` modifier [3](#0-2) , so an attacker's path is indirect: they must be a solver/filler who completes intents through the IntentGateway to influence recorded spreads, which is a standard unprivileged path (fill orders is exactly the "intent solver" attack surface named as in-scope). No special privileges beyond being a solver are required, and the number of fills needed to swing a small-volume pair's average is bounded only by the attacker's own capital/gas, making this practically exploitable over time.

### Recommendation
Introduce a bounded/decaying window for the spread computation — e.g., only accumulate fills within a configurable `maxSpreadAge`, reset or exponentially decay `weightedSpreadSum`/`totalVolume` based on `lastUpdate`, or cap the total volume window (a true VWAP over a rolling period rather than an all-time cumulative average). At minimum, expose and let consumers check `lastUpdate` and revert or fall back if the data is older than an acceptable threshold, analogous to adding the `stalePriceDuration` check recommended in the original report.

### Proof of Concept
1. A filler executes several same-token intents through the `IntentGateway` for a low-volume `(sourceChain, token)` pair, deliberately supplying outputs slightly smaller than inputs across each fill so `recordSpread` accumulates a favorable (attacker-beneficial) `spreadBps` into `_tokenSpreads[chainHash][token]` [4](#0-3) .
2. Because `totalVolume` for that pair is small (or the pair is otherwise thinly used), a modest series of fills materially shifts the weighted average toward the attacker's favor.
3. Time passes — potentially long enough that market conditions have reverted — but `spread()` still returns the skewed historical average unconditionally, since no code path checks `lastUpdate` against `block.timestamp` [2](#0-1) .
4. Any protocol logic (in the Intents pipeline) that consults `spread()` to validate or price a new, larger fill for the same pair is misled by the stale/manipulated baseline, letting the filler capture value beyond what the true current spread should allow.

**Caveat:** I was not able to fully trace, within this session, the exact guardrail logic in `evm/src/apps/intentsv2/IntentsBase.sol` that consumes `IIntentPriceOracle`/`spread()` (only its import references were found before the tool budget was exhausted) [5](#0-4) , so the precise downstream effect (e.g., whether it reverts a fill outside tolerance, or only informs an off-chain solver-selection decision) is not fully confirmed from the code I reviewed. If `spread()` is purely informational/off-chain and not used to gate an authorized on-chain action or fund movement, the severity should be reassessed downward.

        bytes32 chainHash = keccak256(sourceChain);
        CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];
        if (data.totalVolume == 0) return 0;

        return data.weightedSpreadSum / int256(data.totalVolume);
    }

    /**
     * @notice Updates cumulative spread data
     * @param data Storage reference to the cumulative spread data
     * @param weightedSpread The weighted spread (spread * volume)
     * @param volume The volume for this fill
     */
    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
        data.weightedSpreadSum += weightedSpread;
        data.totalVolume += volume;
        data.fillCount += 1;
        data.lastUpdate = block.timestamp;
    }
