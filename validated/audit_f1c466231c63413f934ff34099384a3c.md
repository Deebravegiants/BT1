### Title
`migrate_from_blend` sends a hardcoded `BLEND_WITHDRAW_ALL_AMOUNT` to Blend that reverts on overflow once Blend's b_rate drops, blocking user migrations - (File: contracts/controller/src/constants.rs)

### Summary

`migrate_from_blend` fully withdraws a user's Blend collateral and supply by submitting `BlendRequest`s whose `amount` is the hardcoded constant `BLEND_WITHDRAW_ALL_AMOUNT = 1e30` (`contracts/controller/src/constants.rs:24`, `contracts/controller/src/external/blend.rs:58,65`). Blend internally converts that amount to b-tokens as `ceil(amount * 1e12 / b_rate)` and traps on overflow before clamping to the position. The 1e30 sentinel is safe only while every reserve's `b_rate` stays above roughly `5.9e-9`; below that bound the submitted `submit` call traps, `blend_sweep_all` reverts, and the whole `migrate_from_blend` transaction fails (`contracts/controller/src/strategies/migrate_blend.rs:103`). Like the GMX `MAX_CALLBACK_GAS_LIMIT` finding, a hardcoded value baked into calls to an external protocol can be invalidated by an external state change the protocol does not control, turning a reachable user entrypoint into a permanent revert.

### Finding Description

`b_rate` on a Blend reserve is not fixed: it drifts down when the reserve takes bad debt / the b-token exchange rate is impaired. The `constants.rs` comment itself documents that `i128::MAX` traps "once bad debt pushes a reserve's b_rate below 1.0" and that 1e30 was chosen because it converts without overflow only "while b_rate stays above 5.9e-9" [1](#0-0) . Nothing in the controller reads the reserve's current `b_rate` or sizes the request from the user's actual position; `blend_sweep_all` emits one `REQ_WITHDRAW_COLLATERAL`/`REQ_WITHDRAW` per asset unconditionally at 1e30 [2](#0-1) , and `guarded_submit` propagates Blend's trap [3](#0-2) . A second, independent consequence of the same hardcoding: positions larger than `1e12` whole tokens at `MAX_ASSET_DECIMALS` are only partially swept — "the rest stays in Blend" per the comment — with no follow-up sweep, so the remainder is stranded in Blend rather than migrated [4](#0-3) .

### Impact Explanation

Once any target Blend reserve's `b_rate` falls below ~5.9e-9, every `migrate_from_blend` call that lists that reserve's asset in `collateral_assets`/`supply_assets` reverts in `submit` [5](#0-4) . Any unprivileged user holding a Blend position in such a reserve cannot migrate it through the protocol's designated path — temporary (potentially permanent, absent a Blend recovery or controller upgrade) freezing of the funds they intended to migrate. For oversized positions the tail of the position is simply left in Blend.

### Likelihood Explanation

Medium, mirroring the report's reasoning: a precondition must occur in the external protocol first (Blend b-rate impairment via bad debt, or a whale-scale position). It does not require any privileged or malicious actor — an unprivileged user merely calls `migrate_from_blend` after the external state changes, exactly as in the GMX case where lowering `MAX_CALLBACK_GAS_LIMIT` silently breaks a hardcoded constant.

### Recommendation

Size the withdraw request from live state instead of a constant: read the user's Blend position (or the reserve's `b_rate`) and submit `min(position, overflow_safe_cap)`, or issue repeated bounded sweeps and sum the measured deltas, so that no Blend-side conversion can overflow regardless of `b_rate`. This parallels the report's "make `callbackGasLimit` configurable" recommendation — the value sent to an external protocol must derive from that protocol's current bounds.

### Proof of Concept

1. A user holds supply/collateral in an approved Blend pool listing asset X.
2. Blend reserve X accrues bad debt and its `b_rate` falls below `5.9e-9` (or the user's position exceeds `1e12` whole-token units).
3. User calls `migrate_from_blend` with `collateral_assets = [X]` on an active hub.
4. `blend_sweep_all` submits `BlendRequest { request_type: REQ_WITHDRAW_COLLATERAL, amount: BLEND_WITHDRAW_ALL_AMOUNT }` [6](#0-5) .
5. Blend computes `ceil(1e30 * 1e12 / b_rate)`, overflows, traps; `guarded_submit` propagates and the entire migration reverts — the user's migration path is blocked indefinitely while `b_rate` remains low, with no alternative in-protocol entrypoint to sweep the position [3](#0-2) .
