### Title
Tier-2 biometric package (thermal/face-IR audit data) becomes permanently unrecoverable when `pcp_version >= 3` but `backend_tier2_public_key` is `None` - (File: src/plans/personal_custody_package.rs)

### Summary
`Package::build` decides whether to populate the "tier 2" PCP archive based solely on `pcp_version >= 3`, while the encryption key used to protect that archive for the backend, `backend_tier2_public_key`, is an independent `Option<PublicKey>` that can legitimately be `None`. When both of these states occur simultaneously (a config/version flag says "produce tier 2 data" while the corresponding key is absent), the tier-2 payload is built and committed to in the signed hash manifest, but it is never encrypted with a key the backend can use to decrypt it - functionally freezing that biometric data forever, exactly mirroring the `escrowPool == address(0)` / `escrowPortion > 0` bug class where the "enable" flag and the "destination" are decoupled and never validated together.

### Finding Description
`Credentials::pcp_version` (u16) and `Credentials::backend_tier2_public_key` (`Option<PublicKey>`) are independently supplied by the backend/QR flow and stitched together in `TryInto<personal_custody_package::Credentials>` without any consistency check [1](#0-0) .

In `Package::build`, whether the tier-2 archive (`face_ir.png`, `thermal.png` - captured via `make_tier2`) is populated is gated purely on `*pcp_version >= 3`: [2](#0-1) 

The encryption of that tier-2 archive for the backend, however, is gated purely on whether `backend_tier2_public_key` is `Some`, completely independent of `pcp_version`: [3](#0-2) 

If `backend_tier2_public_key` is `None` while `pcp_version >= 3`, `tier2_single_encrypted` becomes an empty `Vec` (`unwrap_or_default()`), and the value ultimately shipped as "tier2" is just the self-custody-key-wrapped encryption of an empty payload - i.e., the thermal/face-IR biometric data captured for that signup is discarded rather than delivered to the backend. Despite this, the code proceeds to compute and sign a hash commitment for this now-empty tier-2 blob as if it were valid data: [4](#0-3) [5](#0-4) 

No check anywhere in `Package::build`, `Plan::run`, or the caller (`do_signup` in `src/plans/mod.rs`) verifies that `backend_tier2_public_key.is_some()` when `pcp_version >= 3` before proceeding, and the signup is reported as fully successful regardless [6](#0-5) .

### Impact Explanation
The tier-2 archive is the only carrier in the PCP for `face_ir.png` and `thermal.png`, which are part of the biometric/anti-spoofing evidentiary record retained for fraud review. When the misconfiguration occurs, this data is silently and permanently lost with no error surfaced to the operator, backend, or logs (the pipeline reports success and uploads a hash-committed but empty tier-2 blob). This breaks the completeness/integrity guarantee of the biometric audit trail used for later fraud/liveness review, analogous to the referenced report where funds meant to be routed to an escrow become permanently stuck due to an unchecked combination of an "enabled" flag and an absent destination.

### Likelihood Explanation
This requires only a backend-side configuration mismatch (returning `pcp_version >= 3` without a `tier2` key in `BackendKeys`) or a client bug that fails to populate one of the two independent fields - no on-orb attacker action is needed, and there is no local validation to prevent or even detect it. Because `backend_tier2_public_key` is derived from an `Option` field returned by the backend response and mapped through several layers without a cross-field check, a single backend misconfiguration silently affects the record for every signup processed until it's fixed.

### Recommendation
Add a consistency check where `Credentials` is constructed (or at the top of `Package::build`) that fails/aborts PCP construction if `pcp_version >= 3 && backend_tier2_public_key.is_none()` (and correspondingly `backend_tier2_encrypted_private_key.is_none()`), rather than silently emitting an empty, hash-committed tier-2 archive. This mirrors the sherlock-audit fix pattern of validating the "portion enabled" and "destination present" invariants together instead of independently.

### Proof of Concept
1. Backend returns `authenticated_app_data.pcp_version = 3` but `backend_keys.tier2 = None` in the `/user_status`-style response consumed by `src/backend/user_status.rs` (lines 163-246), which is a legal/allowed shape of the `Response`/`BackendKeys` struct.
2. This flows unchanged into `Credentials { pcp_version: 3, backend_tier2_public_key: None, backend_tier2_encrypted_private_key: None, .. }` via the `TryInto` impl (`src/plans/mod.rs:1898-1938`), which only requires the *other* six keys/fields to be `Some`.
3. `do_signup` proceeds normally through `build_pcp` → `Plan::run` → `Package::build`.
4. Because `pcp_version >= 3`, `make_tier2` runs and tier2 tar containing `face_ir.png`/`thermal.png` is built (`src/plans/personal_custody_package.rs:310-314`).
5. `backend_tier2_public_key` is `None`, so `tier2_single_encrypted` defaults to an empty vector (`src/plans/personal_custody_package.rs:324-326`); the final `tier2_encrypted` is just an empty payload wrapped in the user's self-custody key.
6. `hashes.json` still commits `tier_2` to the hash of this empty-payload blob (`src/plans/personal_custody_package.rs:682-688`), and the resulting PCP is uploaded and the signup marked successful, with the thermal/face-IR biometric evidence permanently unrecoverable by the backend.
