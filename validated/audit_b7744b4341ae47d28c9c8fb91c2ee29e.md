### Title
Emporium `runAction` lets an unprivileged caller drain Emporium's on-chain balance via unsigned, unaccounted operations when `signerAddress == 0` and `erc20TokenAddresses.length == 0` (Min-proof path) - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` / `contracts/CircomDataBuilder.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves knowledge of a `messageSeed` (`message == Poseidon(messageSeed)`) and binds nothing about the `EmporiumStack` ops. In `EmporiumUpgradeable.runAction`, when the attacker sets `stack.signerAddress == address(0)`, `verifyWallet` skips all signature verification and every `EmporiumOperation` is executed as a raw, unauthenticated `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own address. Because the balance-accounting loops in both `EmporiumUpgradeable.runAction` and `Hinkal.transact` iterate only over `circomData.erc20TokenAddresses` (which is forced to length 0 to use the Min path), any assets moved by these arbitrary calls are completely unaccounted for.

### Finding Description
The invariant that should hold is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. This equality is broken by design of the Min proof path.

- `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `erc20TokenAddresses.length == 0` and the action is Emporium: [1](#0-0) 
- `formInputEmporiumMin` produces only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`) — no root hash, no amountChanges, no token bindings are part of the proof at all: [2](#0-1) 
- `dimensionsCheck` only requires `erc20TokenAddresses.length == dimensions.tokenNumber`, so `tokenNumber == 0` is self-consistent and passes: [3](#0-2) 
- `Hinkal.transact`'s balance-diff/slippage loop only iterates `circomData.erc20TokenAddresses`, i.e., zero iterations when the array is empty — no check applies to any token actually touched by the action: [4](#0-3) 
- Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are likewise computed only over `circomData.erc20TokenAddresses` (empty in this path), so the entire per-token accounting and `BalanceChangeShouldBePositive` guard is a no-op: [5](#0-4) [6](#0-5) 
- `verifyWallet` performs NO signature check at all when `stack.signerAddress == address(0)` — it only marks the message as used and returns: [7](#0-6) 
- With `signerAddress == 0`, every op in the loop takes the "stateless" branch (`op.invokeWallet && stack.signerAddress != address(0)` is false), performing an arbitrary low-level call `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own identity, blocked only from directly hitting `callHinkalWallet`/`doSendToRelay` selectors: [8](#0-7) 

**Attacker's exact call**: craft `circomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, and `externalActionMetadata` encoding an `EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: <token or arbitrary contract Emporium holds balance in>, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, EmporiumBalance)) }] , maxFee: 0, deadline: anything }`; pick any known `messageSeed`, set `emporiumMessage = Poseidon(messageSeed)`, compute `calldataHash` consistently via `getHashedCalldata`, generate a valid Min-circuit proof (trivial — attacker knows the private witness), pick any historically valid `rootHashHinkal`/index, and call `Hinkal.transact`.

**Why existing guards fail**: `performHinkalChecks` only checks `calldataHash` integrity, relay validity, `dimensionsCheck`, and `checkOnchainCreation` — none constrain the content of `ops` or require signer authorization. `rootHashExists` is satisfied trivially with any historical root because the Min path doesn't bind `rootHashHinkal` into the proof at all. `verifyProof` succeeds because the Min circuit only proves `Poseidon(messageSeed) == message`, an unrelated nonce. `insertNullifiers`/`insertCommitments` operate over empty arrays and do nothing. There is no invariant anywhere that ties the `EmporiumOperation.endpoint`/`callData`/`value` to `circomData.erc20TokenAddresses`, `amountChanges`, or any signed authorization when `signerAddress == 0`.

### Impact Explanation
Any unprivileged attacker can drain the entire on-chain balance (any ERC20 held via prior Emporium interactions, or native ETH sent to Emporium's `receive()`) of the `EmporiumUpgradeable` contract to themselves in a single transaction, with zero economic accounting or authorization check. This is direct theft of protocol/shielded funds held by Emporium — matching the **Critical** severity category (direct theft of shielded or in-flight user funds). The attack is fully repeatable as long as Emporium holds any balance and each attempt only needs a fresh unused `emporiumMessage`.

### Likelihood Explanation
Preconditions are minimal and entirely attacker-controlled: no special role, no signature from any legitimate signer, no prior interaction with the target funds is required — only that Emporium currently holds some token/ETH balance (which happens naturally as users route funds through Emporium for multi-step ops). The attacker's cost is just generating one cheap Min-circuit proof (3 public signals) and gas. This makes the attack highly feasible and low-cost, and repeatable per available Emporium balance.

### Recommendation
- Remove or gate the "no signature required" branch (`stack.signerAddress == address(0)`) in `verifyWallet` so that `EmporiumOperation`s always require either a valid recovered signature over the ops, or restrict the stateless path so it cannot target arbitrary endpoints/calldata that move assets outside of `circomData.erc20TokenAddresses` accounting.
- Do not allow `formInputEmporiumMin` (empty `erc20TokenAddresses`) to be paired with non-empty/arbitrary `ops` that call arbitrary endpoints; require that any op capable of moving value declares its token in `erc20TokenAddresses` so the `balancesBefore`/`balancesAfter` checks in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` actually cover it.
- Alternatively, bind the full `EmporiumStack` (ops, signer, endpoints) into the circuit's public/private inputs for the Min path so a ZK proof cannot be generated for arbitrary attacker-chosen ops without appropriate authorization.

6. Assert: `testERC20.balanceOf(attacker)` increased by 1000e18 and `testERC20.balanceOf(emporium)` == 0, while `circomData.erc20TokenAddresses.length == 0` means neither `Hinkal.transact`'s balance-diff loop nor `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loop ever executed (assert both arrays have length 0), proving the equality "assets moved == assets accounted" is violated (1000e18 moved vs. 0 accounted).
