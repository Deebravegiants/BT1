### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The Kinetiq finding is a case of an identity/authorization binding being enforced over the wrong data: `receive()` treats *any* incoming HYPE the same as a user's `stake()` deposit, because the contract never checks *who* the sender is (whether it's the trusted system address or an ordinary depositor) before running privileged accounting logic. The analog in this gem is `ShopifyAPI::Webhooks::Request`: the HMAC signature that authenticates a webhook as coming from Shopify is computed only over the raw body, while the `shop-domain` header — the field the app actually uses to attribute the webhook to a tenant — is never bound into that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop` accessor, by contrast, is read directly from the attacker-controllable `shopify-shop-domain` header with no cryptographic tie to the HMAC: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the HMAC exclusively from `to_signable_string` (i.e., the body) and compares it to the received `hmac`: [4](#0-3) 

`Registry.process` gates only on this HMAC check, then forwards the untrusted `request.shop` straight into the dispatched `WebhookMetadata` that the app's handler acts on: [5](#0-4) [6](#0-5) 

**Binding that should hold, expressed as an equality:**
`shop_attributed_to_webhook == shop_that_the_HMAC_actually_authenticates`

Because `to_signable_string` only contains the body, this equality is never enforced: `hmac` authenticates *"this body was produced with the app's `client_secret`"*, not *"this body belongs to shop X"*. Since a single app's `client_secret` (and therefore its webhook signing key) is shared across every merchant that installs it, any party who has legitimately installed the app on their own store receives real, validly-signed webhooks. That merchant can capture one such `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it never looked at the shop header, and `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain.

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's own webhook-authentication primitive: an unprivileged internet user who is a legitimate merchant on their own shop can forge a webhook that the app will process *as if it came from a different, victim shop*. Any host application that trusts `WebhookMetadata#shop` (e.g., to look up/mutate per-shop settings, revoke access on `app/uninstalled`, or write shop-scoped data) can be made to act on the wrong tenant's data purely because the gem's HMAC check does not bind the `shop` field it hands to the handler. This matches the "Critical — cross-tenant access" bucket: the attacker crosses a tenant boundary using only their own legitimately-issued webhook traffic, no access token, secret, or privileged account required.

### Likelihood Explanation
Likelihood is realistic but conditioned on the attacker being an actual (even if low-privilege) installer of the app — which is trivial to obtain for any public Shopify app, and matches the "unprivileged internet user" threat model. Capturing a real `(body, hmac)` pair from one's own store and replaying it against the app's public webhook endpoint with a modified header requires no cryptographic secret. The severity of what happens next depends on how much the host app trusts the `shop` field without cross-checking it against its own installed-shop/session store, but the gem itself provides no protection at the point where this binding should exist.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise fold the shop identity into `to_signable_string` before verification, e.g.:
```ruby
def to_signable_string
  "#{shop}\n#{@raw_body}"
end
```
so that an HMAC computed for one shop cannot be replayed with a different `shop-domain` header. At minimum, document prominently that `request.shop` from `ShopifyAPI::Webhooks::Request` is not authenticated by the HMAC and that consuming applications must independently verify the shop is one they have on record before acting on the payload.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (a normal, unprivileged merchant action).
2. Shopify sends a real webhook (e.g. `products/create`) to the app, signed with the app's `client_secret`:
   - headers: `x-shopify-topic: products/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `{...attacker-controlled product payload...}`
3. Attacker captures the raw body and the `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST to the same webhook endpoint, keeping the identical body and `x-shopify-hmac-sha256` header, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only [7](#0-6)  — it matches, since the body is unchanged.
6. `ShopifyAPI::Webhooks::Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to process attacker-supplied content under the victim's tenant identity.
