### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook data spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop` is read straight from the `shop-domain` header without ever being part of the HMAC-verified material [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body HMAC) and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . This breaks the identity binding `HMAC-verified bytes == bytes the shop identity is derived from`: the body is verified, but the shop header used for tenant attribution is not.

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against the `hmac` field of the query object [4](#0-3) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , and the `hmac` value itself is taken from the `hmac-sha256` header [5](#0-4) . The `shop`, `topic`, `api_version`, and `webhook_id` fields are all read from separate headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) that are never included in the signed material [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and, if it passes, immediately builds `WebhookMetadata` using `request.shop` verbatim and dispatches it to the registered handler [3](#0-2) . `WebhookMetadata#shop` is a plain `String` field with no further validation [7](#0-6) .

Concretely, if an attacker (e.g., a developer running their own store/app installation, who legitimately receives real webhook deliveries — body + valid HMAC — for their own shop) captures one such `(raw_body, hmac-sha256 header)` pair, they can replay it to the app's public webhook endpoint while substituting an arbitrary value for the `X-Shopify-Shop-Domain` header. Because the HMAC only covers `raw_body`, `HmacValidator.validate` still succeeds, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop domain, together with the body data that actually belongs to the attacker's own shop. Any host application that uses `data.shop` to select which tenant's records to update (a documented, expected usage pattern of this SDK, per `docs/usage/webhooks.md`) will write/react to attacker-supplied data under a different tenant's identity — an identity binding violation ("shop verified" ≠ "shop the HMAC covers").

### Impact Explanation
This breaks the tenant boundary the SDK's webhook API is meant to enforce: the only cryptographic check (`HmacValidator.validate`) authenticates the payload bytes, not the shop the payload is attributed to. An attacker can therefore make an app process attacker-controlled webhook content while asserting it originates from an arbitrary target shop, resulting in cross-tenant data corruption/injection — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own real Shopify store already configured with the target app (an unprivileged/ordinary merchant relationship, not a leaked secret or privileged account), which naturally yields legitimate `(body, hmac)` pairs for webhooks addressed to their own shop, and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — both are within reach of an ordinary internet user/merchant and require no `api_secret_key`, no access token, and no TLS interception.

### Recommendation
- Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values in the HMAC-signed material for webhook requests, or otherwise cryptographically bind the shop identity to the signature so that changing the `shop-domain` header invalidates the HMAC.
- Alternatively/additionally, document prominently that `request.shop` is unauthenticated header data and must be cross-checked by the host application against a known, previously-registered shop/session before being trusted for any tenant-scoped operation.

### Proof of Concept
```ruby
# Attacker has a legitimately received webhook for their OWN shop:
raw_body = '{"id":1,"note":"legit payload for attacker-shop.myshopify.com"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
# (attacker obtained hmac because it was delivered to their own store's webhook log)

# Attacker replays it to the same app endpoint, but swaps the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),        # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => Utils::HmacValidator.validate(req) succeeds (only raw_body is checked),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
# The app now processes attacker-supplied data as if it belongs to victim-shop.myshopify.com.
```
