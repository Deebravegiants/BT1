## Title
Boolean-Return Assumption in `ERC20Transactor` Breaks Cross-Chain Transfers for Void-Return ERC20 Tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke a target contract's `transfer(address,uint256)` via `pallet_revive::Pallet::<T>::bare_call`, then strictly ABI-decode the return data as a `bool` via `IERC20::transferCall::abi_decode_returns_validate`. A Solidity ERC20 contract that returns `void` on success (as real-world USDT does) will fail this decode step, and the code treats a decode failure identically to a failed transfer, aborting the XCM instruction with `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")` even though the underlying transfer succeeded on-chain.

## Finding Description
In `withdraw_asset_with_surplus`, after a successful (non-reverted) `bare_call` to `transfer`, the code unconditionally decodes the return data as a `bool`: [1](#0-0) 

The same pattern exists in `deposit_asset_with_surplus`: [2](#0-1) 

Neither function special-cases an empty `return_value.data` (which is what a `void`-return `transfer` produces on success). Both simply pass the raw bytes to `abi_decode_returns_validate`, which fails to decode a `bool` from empty data, and that failure is mapped to a fatal `XcmError`, not treated as success.

There is no restriction on which contracts can be used as ERC20 assets in this transactor — `ERC20Matcher` matches any `AccountKey20` location via `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, confirming any unprivileged user-deployed contract on `pallet_revive` is eligible. [3](#0-2) 

The maintainers' own test suite, `smart_contract_does_not_return_bool_fails`, confirms that any non-standard return value (in that test, a `uint256` instead of `bool`) is treated as an unrecoverable failure via `XcmError::FailedToTransactAsset`, and there is no equivalent test or handling path for the `void`-return case, which behaves identically (empty decode failure) but represents a much more common real-world ERC20 pattern (USDT-style tokens). [4](#0-3) 

## Impact Explanation
Both `WithdrawAsset` and `DepositAsset` XCM instructions in the executor are wrapped in `Config::TransactionalProcessor::process`, which rolls back all storage changes (including internal `pallet_revive` contract state such as the underlying successful token transfer) whenever the closure returns `Err`. [5](#0-4) 

The concrete impact is denial of service for a specific class of ERC20 token: any void-return ERC20 contract (matching real-world USDT's ABI) deployed via `pallet_revive` cannot be bridged through `ERC20Transactor` at all — every `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call against it deterministically fails, wasting the weight/fees paid for the XCM message, though the rollback prevents actual fund loss. This is a functional-correctness/availability bug rather than a fund-loss or accounting-break vulnerability; it denies legitimate use of the feature for an entire class of common tokens rather than causing insolvency, unauthorized transfer, or privilege escalation.

## Likelihood Explanation
High for triggering the failure: no privileged role is required — `ERC20Matcher` accepts any `AccountKey20` location, so any user can deploy a void-return ERC20 contract on `pallet_revive` and immediately encounter this failure deterministically on both the withdraw and deposit paths, as verified directly in the code and corroborated by the closely analogous `smart_contract_does_not_return_bool_fails` test in the repository.

## Recommendation
Do not assume a strict ABI-encoded `bool` return from `transfer`/`transferFrom`. Follow the "safe transfer" pattern (as in OpenZeppelin's `SafeERC20`): treat an empty `return_value.data` as success, only attempt to ABI-decode a `bool` when return data is non-empty, and only treat an explicit `false` or an undecodable-but-non-empty result as failure.

## Proof of Concept
1. Deploy via `pallet_revive` a minimal ERC20 contract whose `transfer(address,uint256)` mutates balances correctly but is declared with no return value (`void`), matching real USDT's ABI.
2. Reference this contract's `H160` address as an XCM asset; no special permission is required since `ERC20Matcher` (`IsLocalAccountKey20`) accepts any `AccountKey20` location, as shown in `lib.rs`.
3. Execute an XCM program performing `WithdrawAsset`/`DepositAsset` for this asset, following the pattern of the existing `smart_contract_does_not_return_bool_fails` test in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`.
4. Observe `bare_call` succeeds and the token balances actually change inside the contract, but `abi_decode_returns_validate(&return_value.data)` fails on the empty return, producing `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")`, and the outer `TransactionalProcessor` rolls back the transfer, causing `PolkadotXcm::execute` to return `Err`/`Outcome::Incomplete`.
