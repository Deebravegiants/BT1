### Title
`verifying_contract` override in `signAndSendIntent` lets a caller bind the signed intent to a contract different from `envConfig.contractID` - (File: packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts)

### Summary
`IntentExecuter.signAndSendIntent` builds the default intent payload by first setting the trusted `verifying_contract` from `this.envConfig.contractID` and then spreading the caller-supplied `intentParams` object over it. Because `intentParams` is typed as `Partial<Parameters<IntentPayloadFactory>[0]>` (i.e. `Partial<IntentPayload>`), it can legally contain its own `verifying_contract` field, which silently overwrites the trusted value before the payload is signed.

### Finding Description
In `signAndSendIntent`:
```ts
let intentPayload = defaultIntentPayloadFactory(salt, {
    verifying_contract: verifyingContract,   // trusted, derived from envConfig.contractID
    ...intentParams,                          // caller-controlled, spread AFTER, can override it
});
``` [1](#0-0) 

`intentParams` is captured via destructuring from the full method argument object (`{ relayParams, salt, signedIntents, ...intentParams }`), and its type allows any field of `IntentPayload`, including `verifying_contract`: [2](#0-1) 

The equality that should hold is: `intentPayload.verifying_contract === this.envConfig.contractID` for every signed intent produced by this executer, because `envConfig.contractID` is the value the rest of the SDK/relayer trusts as "the correct verifying contract" for this environment. Because the spread order places `...intentParams` after the trusted assignment, a caller that supplies its own `verifying_contract` key breaks this equality — the signer (`this.intentSigner.signIntent(intentPayload)`) will then produce a `MultiPayload` cryptographically bound to whatever contract the caller specified, not the one derived from `envConfig`.

This same payload subsequently flows unchanged through `mergeIntentPayloads` (which again spreads `customPayload` over `basePayload`, further preserving whatever `verifying_contract` was set) and into `computeIntentHash` / `intentRelayer.publishIntent`, so the wrong-contract binding propagates all the way to relaying without any re-validation against `envConfig.contractID`. [3](#0-2) 

### Impact Explanation
This matches the "signature bound to the wrong contract" High-impact category: the signed `MultiPayload` can end up verifying against a contract other than the one the SDK/integrator configured and trusts (`envConfig.contractID`). Depending on how the resulting signature/hash is consumed downstream, this can misdirect fund-moving intents to an unintended contract instance, since the cryptographic commitment (`verifying_contract`) no longer matches the environment's validated contract ID.

### Likelihood Explanation
Exploitability depends entirely on whether any caller of `signAndSendIntent` (either an integrator's own code path or code that forwards partially external input into the `intentParams` bag) can influence a `verifying_contract` value. I was not able to fully trace every call site (e.g., `sdk.ts`, `sdk.signAndSendIntent.test.ts`) within the available tool budget to confirm whether `verifying_contract` is ever forwarded from less-trusted input in practice — this should be verified further. The structural flaw (trusted value being overridable via spread order) is nonetheless concrete and present in the code as written.

### Recommendation
Do not allow `intentParams` to override `verifying_contract`. Either omit `verifying_contract` from the caller-facing type entirely, or explicitly strip it before merging, e.g.:
```ts
const { verifying_contract: _ignored, ...safeIntentParams } = intentParams;
let intentPayload = defaultIntentPayloadFactory(salt, {
    ...safeIntentParams,
    verifying_contract: verifyingContract,   // trusted value always wins, spread last
});
```
Apply the same fix in `mergeIntentPayloads` so `customPayload.verifying_contract` cannot override the value already fixed by `envConfig.contractID`.

### Proof of Concept
```ts
// Assume envConfig.contractID = "trusted.contract.near"
await intentExecuter.signAndSendIntent({
  salt,
  verifying_contract: "attacker-controlled.contract.near", // part of Partial<IntentPayload>
  intents: [...],
});
// intentPayload.verifying_contract ends up as "attacker-controlled.contract.near"
// instead of envConfig.contractID, and this is what gets signed via intentSigner.signIntent(intentPayload).
``` [4](#0-3)

async function mergeIntentPayloads(
	defaultPayload: IntentPayload,
	intentPayloadFactory: IntentPayloadFactory,
	salt: Salt,
): Promise<IntentPayload> {
	const customPayload = await intentPayloadFactory(defaultPayload);
	const customPayloadIntents = customPayload.intents ?? [];

	const { nonce: _nonce, ...basePayload } = defaultPayload;

	return defaultIntentPayloadFactory(salt, {
		...basePayload,
		...customPayload,
		intents: Array.from(
			new Set([...customPayloadIntents, ...basePayload.intents]),
		),
	});
}
