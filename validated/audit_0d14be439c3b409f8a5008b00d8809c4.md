### Title
Webhook `shop-domain`, `topic`, and other identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — which are used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant and dispatch the webhook — come from unauthenticated HTTP headers that are never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from request headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) via `Utils::HmacValidator.validate`, then unconditionally trusts `request.shop` and `request.topic` to build `WebhookMetadata` and dispatch it to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever hash `verifiable_query.to_signable_string`, i.e. the raw body for webhooks, with the shared `api_secret_key`: [4](#0-3) 

Because a single app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, the HMAC over the body alone does not prove which shop the request came from — it only proves the request was signed by *some* holder of that shared secret (i.e., Shopify, on behalf of any installed shop). This breaks the identity binding: `hmac(body)` should equal `verify(shop, body)`, but the implementation only enforces `hmac(body) == valid`, leaving `shop` (and `topic`/`webhook_id`/`api_version`) completely unauthenticated and attacker-controllable in the delivered HTTP request.

The docs confirm apps are expected to trust `data.shop` as the tenant identity coming out of `Registry.process`: [5](#0-4) 

### Impact Explanation
This falls under the "cross-tenant access" impact category. An attacker who is a legitimate merchant of Shop A (or who otherwise captures/replays one authentic, correctly-HMAC'd webhook body originally intended for Shop A) can resend that same raw body to the app's webhook endpoint with headers claiming `shop-domain: shop-b.myshopify.com`. Since the signature covers only the body, and the same `api_secret_key` is valid across all shops of the app, the HMAC check still passes. The application's handler then receives `WebhookMetadata` attributing Shop A's data to Shop B, potentially causing the app to write/update/act on Shop B's tenant data using attacker-supplied content, or to trigger business logic (e.g., order creation side effects, `app/uninstalled` handling) under a victim shop's identity — a violation of the tenant isolation boundary that `shop_id`/`shop` normally guarantees.

### Likelihood Explanation
Any unprivileged internet user who can install the app on their own store (common for public apps) gains the ability to receive genuinely-signed webhook bodies for their own shop, then can freely replay them with a forged `shop-domain` (and `topic`/`webhook_id`) header against the app's public webhook endpoint. No access token, `api_secret_key`, or privileged access is required — only knowledge of the endpoint URL and one legitimate webhook delivery, both of which are trivially available to any app installer.

### Recommendation
Bind the identity headers into the signed content, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` (matching Shopify's documented webhook verification, which signs the full raw request), or independently verify that the `shop-domain` header matches a shop associated with an actively registered/expected webhook subscription before dispatching to handlers. At minimum, document clearly that `data.shop` from `WebhookMetadata` is not authenticated by the HMAC and must not be trusted as a tenant boundary without additional server-side verification (e.g., cross-checking against a known list of installed shops).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256` computed over `B` using the app's shared `api_secret_key`.
2. Attacker captures this exact HTTP request (body `B` and its valid HMAC header).
3. Attacker crafts a new POST to the app's webhook endpoint using the same raw body `B` and the same valid HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(body, api_secret_key)`.
5. The app's registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
