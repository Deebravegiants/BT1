### Title
Escrow accounting in the Tron `IntentGatewayV2.placeOrder` credits the nominal amount instead of the actually-received balance, enabling a phantom-deposit drain of other users' escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` is a hand-duplicated reimplementation of `evm/src/apps/IntentGatewayV2.sol`'s `placeOrder` escrow logic. The two copies have drifted: the canonical EVM version measures the *actual* token balance received before crediting the escrow ledger (to defend against fee-on-transfer/deflationary tokens), while the Tron duplicate credits the ledger with the *requested* input amount regardless of what the gateway actually received. Because all orders' escrow is tracked only via a shared internal mapping against one pooled token balance, this lets an attacker inflate their own order's ledger entry beyond what they deposited, and later redeem more tokens than they escrowed — draining tokens that belong to other users' orders from the shared pool.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol::placeOrder`, input transfers are always followed by a balance-diff measurement so `order.inputs[i].amount` reflects what the contract actually received: [1](#0-0) 
This value (`order.inputs[i].amount`, hence `reducedInputs[i].amount`) is what gets written into the escrow ledger: [2](#0-1) 

The Tron duplicate performs the transfer but never re-measures the balance — it simply trusts the caller-supplied `order.inputs[i].amount` (minus the protocol fee) and credits it to the ledger with `+=`: [3](#0-2) 
The predispatch branch has the same gap — it computes `dust` from the dispatcher's balance but still stores `reducedInputs[i].amount` (the nominal figure) into `_orders`, not what was actually swept back into the gateway: [4](#0-3) 

Both `IntentGatewayV2` contracts hold every order's escrowed tokens in one pooled contract balance; `_orders[commitment][token]` is purely bookkeeping, not a segregated custody account: [5](#0-4) 
Redemption pays out of that shared pool by `token.call(transfer, ...)` for whatever amount the ledger says is owed, with no check that the pool actually holds that order's fair share: [6](#0-5) 

Consequently, a user placing an order with a fee-on-transfer (or otherwise balance-skimming) TRC20 as an input token can have the gateway receive less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is still credited with the full (fee-reduced) nominal amount. When that order is later filled and redeemed cross-chain (`RedeemEscrow`) or refunded, the beneficiary is paid the inflated ledger amount out of the shared pool — i.e., out of tokens that in fact belong to other users' still-outstanding orders. This is exactly the "confusing semantics" duplication bug class described in the external report: the escrow-crediting logic was copied instead of shared, and the copy silently lost the safety fix (balance-diff measurement) present in the original.

### Impact Explanation
This allows an attacker to place a single `placeOrder` transaction (an unprivileged, directly reachable entry point of the intents escrow) using a fee-on-transfer token, then redeem more tokens than were ever deposited for that order. Because escrow for all orders in a given token is pooled in one contract balance, this constitutes direct theft of other users' escrowed funds and can eventually cause legitimate redemptions to revert (insufficient balance) — a freezing/loss of funds condition. This satisfies concrete theft/freezing of funds via the intents escrow path.

### Likelihood Explanation
Reachable directly by any unprivileged caller of `placeOrder` on the Tron deployment with any TRC20 input token that has a transfer fee/rebasing/deflationary behavior (a well-known token category on most EVM/TVM-compatible chains). No special privileges, governance, or malicious insiders are required — only the attacker's own order placement and redemption.

### Recommendation
Remove the duplicated `placeOrder`/escrow logic in `evm/tron/contracts/apps/IntentGatewayV2.sol` and share the canonical implementation (e.g., via the same `IntentsBase`/`IntrinsicIntents` inheritance used by `evm/src/apps/IntentGatewayV2.sol`), or, if a standalone Tron file must be kept, port the balance-diff measurement (`balBefore`/`balAfter`, and the predispatch dust/balance snapshot logic) so `_orders[commitment][token]` is always credited with the amount actually received by the contract, never the caller-supplied nominal amount.

### Proof of Concept
1. Deploy/select a fee-on-transfer TRC20 token `T` that skims e.g. 10% on every transfer.
2. Attacker calls `placeOrder` with `order.inputs = [{token: T, amount: 1000}]`, no protocol fee. The `safeTransferFrom` moves 1000 nominal but the gateway actually receives only 900 T (100 skimmed by the token). `_orders[commitment][T] += reducedInputs[0].amount` (i.e., `+= 1000`), even though the gateway only holds 900 T from this order.
3. When the order is filled and redeemed (`withdraw`), the beneficiary is paid `1000` T out of the shared pool, i.e., `100` T more than this order ever deposited — drawn from other users' escrowed `T` balances sitting in the same contract.
4. Repeating this (or scaling amounts) drains the shared escrow pool and causes other legitimate orders' `withdraw` calls to revert once the pool is insufficient, freezing their funds.
