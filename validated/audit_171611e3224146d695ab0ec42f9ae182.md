### Title
Missing relayer-authorization check in Tron `IntentGatewayV2.onAccept` allows any relayer to deliver privileged escrow/governance actions - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Sakai advisory (SAK-50571) describes a case where a restricted user "type" (`roleview`) was not properly distinguished from a normal privileged type during authentication, letting an unprivileged principal act with normal-user rights. The reachable analog in Hyperbridge is a class-confusion/missing-authorization check on the `onAccept` entry point of the Tron `IntentGatewayV2` contract: the function authenticates the message's *source module* for escrow actions but never authenticates *who delivered it* (the relayer), even though the sibling EVM implementation enforces exactly this second check as a security-critical gate.

### Finding Description
`IntentGatewayV2.onAccept` in the Tron contracts guards only with `onlyHost` [3](#0-2) . For `RedeemEscrow`/`RefundEscrow` it calls `authenticate(incoming.request)`, which (per the analogous `_authenticate` in `IntentsBase`) only checks that `request.from` matches the registered gateway instance for `request.source` — i.e., it authenticates the *cross-chain module*, not the relayer that physically submitted the proof to this chain's host [4](#0-3) .

By contrast, the current EVM `ExtrinsicIntents.onAccept`/`onGetResponse` path was hardened specifically to add a **second, independent check**: `_checkRelayer(incoming.relayer)`, which reverts unless the delivering relayer matches the gateway's configured `_relayer` (once armed) [2](#0-1) . The project's own documentation states this check "runs before the message body is decoded, so escrow redemptions, refunds and every governance action ... are covered" [1](#0-0)  and the flow doc for `HandlerV2`→`EvmHost`→`onAccept` explicitly documents `_checkRelayer` as the gate that determines whether an escrow/governance action is processed at all [5](#0-4) .

The Tron `IntentGatewayV2` implements the same `RequestKind` set (`RedeemEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`, `RefundEscrow`) and the same escrow-withdrawal logic [6](#0-5) , but has no `_relayer` state, no `setRelayer`, and no relayer check anywhere in `onAccept`. This is the same class of bug as SAK-50571: a security boundary that is supposed to distinguish "who is delivering this" (privileged relayer vs. arbitrary account) is silently absent for one code path (Tron) while present for the structurally-identical path (EVM `ExtrinsicIntents`), letting any account submit a valid proof through `HandlerV2`/host dispatch and have it accepted as though from the authorized relayer.

### Impact Explanation
On the EVM side, the relayer allowlist was added deliberately to cover "escrow redemptions, refunds and every governance action, upgrades included" [1](#0-0) . Its absence in the Tron contract means:
- Any relayer (not just the authorized one) can trigger `RedeemEscrow`/`RefundEscrow` withdrawals as soon as a valid state/consensus proof exists for the message, i.e. front-run or race the intended relayer for fee/ordering advantage, or bypass any invariant the authorized-relayer restriction was meant to enforce.
- Governance-tagged actions (`NewDeployment`, `UpdateParams`, `SweepDust`) are only gated by `source == hyperbridge`, with no relayer check — weaker than the equivalent EVM path, which layers the relayer gate underneath the same source check.

This maps to "unauthorized app action" per the validation criteria: privileged escrow/governance state transitions become reachable from any relayer instead of the designated one.

### Likelihood Explanation
Reaching this requires only a normal relayer delivering an already-valid ISMP message (proof-verified through the standard `HandlerV2`/host dispatch path) — no admin, governance, or node compromise needed, matching the "single relayed proof" reachability bar. Given that the EVM sibling contract was patched specifically because this exact absence was judged security-critical (per the changelog's stated rationale), the missing check in the Tron variant is a concrete, currently-live gap in a production-intended contract.

### Recommendation
Port the relayer-allowlist mechanism (`_relayer`, `_checkRelayer`, `setRelayer`, and armed-via-`initialize`/`migrate` semantics) from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and call `_checkRelayer(incoming.relayer)` at the top of `onAccept` (and any `onGetResponse` equivalent) before the `RequestKind` byte is read, mirroring the EVM path exactly.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with an order filled cross-chain, generating a legitimate `RedeemEscrow` (or `RefundEscrow`) request.
2. Any relayer (not a designated/authorized one) submits the corresponding proof through the standard handler/host dispatch path so that `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept(IncomingPostRequest(request, relayer))` with an arbitrary `relayer` address.
3. `onAccept` at [7](#0-6)  only checks `onlyHost` and `authenticate(request)` (source-module check); it never inspects `incoming.relayer`, so the withdrawal proceeds regardless of which relayer submitted it — unlike the EVM `ExtrinsicIntents.onAccept`, which would revert with `Unauthorized` here once a `_relayer` is armed.
