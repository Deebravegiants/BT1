Based on my investigation, I did not find a confirmed, reachable analog of this vulnerability class in this codebase's in-scope Polkadot SDK code. Here's my analysis:

## Why the direct analog mostly doesn't apply

The Olympus bug hinges on two things: (1) balance-before/after diff accounting around an external token transfer, and (2) a token contract that can execute attacker logic mid-transfer (ERC777-style hook) to reenter a *different* trusted contract that shares the same balance.

Native FRAME `Currency`/`fungible`/`fungibles` transfers (`pallet-balances`, `pallet-assets`) are plain storage mutations with no callback to arbitrary code — there is no equivalent of an ERC777 "tokens-to-send" hook, so the core precondition of the original bug is absent for ordinary FRAME asset transfers. [1](#0-0) 

## The closest candidate I found

`pallet-psm` (Peg Stability Module) has a mint/redeem flow structurally similar to Olympus's mint/repay: it computes amounts, calls a generic `T::Fungibles::transfer` (an "external interaction" from the pallet's point of view since `Fungibles` is a trait object that could be backed by many implementations), and only afterwards commits the debt-accounting effects (`PsmDebt::<T>::insert`) — a check→interact→effect ordering rather than check→effect→interact: [2](#0-1) 

If `T::Fungibles` for some external asset were ever backed by an ERC20 contract routed through `pallet-revive` (as seen in the XCM ERC20 transactor, which calls `pallet_revive::Pallet::<T>::bare_call` to invoke a Solidity `transfer`), the transferred token *could* in principle contain hook-like reentrant logic: [3](#0-2) 

However, `pallet-revive` explicitly guards against exactly this cross-pallet reentry pattern: a contract invoked mid-transaction cannot dispatch back into the runtime/another pallet call while already executing, since the runtime-call precompile enforces a reentrancy guard and returns `ReenteredPallet`: [4](#0-3) [5](#0-4) 

This means even if `pallet-psm` (or any other pallet with this ordering) were configured with an ERC20-backed `Fungibles` instance, an attacker's contract could not re-dispatch `Psm::mint`/`Psm::redeem` from within the transfer callback to exploit the stale debt-ceiling check — the exact mechanism that made the Olympus bug work (calling back into `Operator::swap`, a separate contract-level entry point) is blocked at the pallet-revive boundary for calls back into FRAME dispatchables.

## What I could not fully verify

I ran out of tool-call budget before confirming the exact `Fungibles` type wired into `pallet_psm::Config` in the production `asset-hub-westend` runtime (i.e., whether any of its approved external assets could actually be an ERC20-backed asset routed through `pallet-revive`, or whether it's restricted to natively-implemented `pallet-assets`/foreign assets with no callback surface at all). Without that confirmation, I cannot assert reachability, and per the disqualification criteria ("No reachable attacker-controlled entry path" and "Theoretical-only issue with no protocol impact"), this does not meet the bar for a valid finding.

## Conclusion

I did not find a valid, reachable analog of the Olympus `repayLoan`/`Operator::swap` reentrancy in this codebase. FRAME's native asset-transfer primitives lack the hook mechanism the original bug depends on, and the one plausible path through `pallet-revive`-backed ERC20 assets is independently blocked by `pallet-revive`'s explicit `ReenteredPallet` guard against contracts re-dispatching into the runtime mid-call.
