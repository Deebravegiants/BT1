### Title
Webhook `shop` (and `topic`/`webhook-id`) Not Covered by HMAC — Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the value later trusted as the tenant identity (`shop`) from an HTTP header, but the HMAC signature that the gem validates is computed **only over the raw request body**, never over that header. Any actor who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared secret — trivially achievable by installing the app on their own (attacker-controlled) shop and capturing a legitimate webhook delivery — can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds, and `Registry.process` hands the handler a `WebhookMetadata` claiming the forged shop, breaking the equality that host applications rely on: `shop authenticated by HMAC == shop delivered to handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an unauthenticated header, independent of that signed string: [2](#0-1) 

`HmacValidator.validate_signature` computes the digest exclusively over `verifiable_query.to_signable_string` (i.e. the body), so the `shop-domain` header plays no role whatsoever in the cryptographic check: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` — the unauthenticated field — directly to the app's handler as the tenant identifier: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is a single value shared across every shop that installs the app, an attacker does not need any special privilege to obtain a valid signed body: they simply install the app on a shop they control, trigger any webhook-eligible event, and capture Shopify's genuine delivery (`raw_body`, `x-shopify-hmac-sha256`). They can then POST that identical body/HMAC pair to the app's public webhook endpoint with `x-shopify-shop-domain` rewritten to the victim merchant's domain. `HmacValidator.validate` returns `true` (body and HMAC still match), and `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, which the host app's handler will treat as authentic data belonging to the victim.

The equality the gem implicitly promises to the host application — "if `HmacValidator.validate` passes, `request.shop`/`request.topic`/`request.webhook_id` are the values Shopify actually sent for that authenticated payload" — does not hold, because none of those header-derived fields are part of the signed material.

### Impact Explanation
This is a cross-tenant confusion primitive: a party with only unprivileged access to the platform (their own free/dev shop and app install) can cause the app to process attacker-supplied, HMAC-"verified" webhook data under a victim shop's identity. Any host application logic keyed off `WebhookMetadata#shop` (e.g., updating per-merchant records, triggering merchant-specific side effects, writing audit logs, invalidating/replacing merchant data) can be manipulated cross-tenant. This matches the Critical bar of "cross-tenant access" since the shop-scoping guarantee the gem is expected to provide is broken.

### Likelihood Explanation
High from a mechanics standpoint: webhook endpoints are public, unauthenticated HTTP endpoints by design; forging headers on a replayed HTTP request requires no special tooling; and obtaining a legitimate `(body, hmac)` pair only requires a free/dev shop install of the target app (no privileged credentials, no access token, no leaked secret). The only constraint is that the attacker can't control body *content* arbitrarily — the practical impact depends on which webhook topics/bodies are useful to replay against another shop within a host app's business logic (e.g., generic bodies, or bodies whose content becomes ambiguous cross-tenant).

### Recommendation
Bind the header-derived identity fields into the HMAC-verified material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the signature so they cannot be swapped independently of the signed body. At minimum, `to_signable_string` (or an additional check in `Registry.process`) should incorporate the shop domain, topic, and webhook id so that mutating any of those headers invalidates the HMAC.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`).
2. Shopify delivers `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H` (H = HMAC-SHA256(secret, B)); attacker captures `B` and `H`.
3. Attacker sends `POST /webhooks` to the same app endpoint with body `B` unchanged, `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) — validation succeeds: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never touched Shopify's systems for that shop.
