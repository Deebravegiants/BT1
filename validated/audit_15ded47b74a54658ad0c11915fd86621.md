Audit Report

## Title
Proxy `NonTransfer`-style restrictions on parachains do not cover `PolkadotXcm::execute`, letting a proxy move `real`'s local assets via a crafted XCM program - (File: `polkadot/xcm/pallet-xcm/src/lib.rs`, cross-module with `substrate/frame/proxy/src/lib.rs` and parachain `ProxyType::filter` impls, e.g. `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`)

## Summary
`ProxyType::NonTransfer` on Asset Hub (Westend/Rococo), Coretime-Westend, Collectives-Westend, and the staking-async parachain runtime is implemented as a negation/deny-list that excludes `Balances`, `Assets`, `Nfts`, `Uniques`, `NftFractionalization`, but does not exclude `RuntimeCall::PolkadotXcm(..)`. A delegate holding a `NonTransfer` proxy can therefore dispatch `PolkadotXcm::execute` with a `WithdrawAsset`+`DepositAsset` program signed as `real`, effectively performing an unauthorized asset transfer that the proxy type was meant to forbid.

## Finding Description
`Proxy::proxy` checks `def.proxy_type.filter(&call)` against the outer `RuntimeCall` variant shape only, so it cannot see the semantic effect of an embedded XCM program inside `PolkadotXcm::execute`. On Asset Hub Rococo/Westend, Coretime-Westend, Collectives-Westend, and the staking-async parachain runtime, `ProxyType::NonTransfer` is implemented via `!matches!(c, RuntimeCall::Balances{..} | RuntimeCall::Assets{..} | RuntimeCall::NftFractionalization{..} | RuntimeCall::Nfts{..} | RuntimeCall::Uniques{..})`, confirmed at [1](#0-0)  and [2](#0-1) , none of which list `RuntimeCall::PolkadotXcm(..)`, so `filter()` returns `true` for `PolkadotXcm::execute`.

This is in stark contrast to the relay-chain implementations, which use an allow-list approach and explicitly comment that they are "Specifically omitting the entire XCM Pallet," confirmed at [4](#0-3)  and [5](#0-4) . This design contrast strongly indicates the relay-chain authors deliberately treated the XCM pallet as transfer-capable and excluded it from `NonTransfer`, while the parachain deny-lists were not updated to do the same.

Once the proxy filter passes, `Proxy::do_proxy` dispatches the call with `RawOrigin::Signed(real)`. `pallet_xcm::Pallet::execute` converts that signed origin into an XCM `Location` via `ExecuteXcmOrigin`/`LocalOriginToLocation` (typically `SignedToAccountId32`), checks `XcmExecuteFilter` (commonly `Everything` on these runtimes), and runs the program through the XCM executor with that origin. A `WithdrawAsset` instruction withdraws directly from `real`'s local balance via the `AssetTransactor`, and a subsequent `DepositAsset` can send funds to an attacker-controlled beneficiary — reproducing the exact effect of `Balances::transfer`, which the proxy type was intended to forbid.

## Impact Explanation
Any account holder who grants a `NonTransfer` proxy — a proxy type specifically intended to prevent asset movement — is exposed to full theft of their local native/asset balances by that delegate on Asset Hub Westend/Rococo, Coretime-Westend, Collectives-Westend, and the staking-async parachain runtime. This breaks the proxy-scope invariant that a `NonTransfer` grant fully bounds the delegate's asset-moving capability.

## Likelihood Explanation
Exploitation requires only an existing `NonTransfer` proxy grant (a common, low-trust delegation pattern) and a single `Proxy::proxy` extrinsic wrapping `PolkadotXcm::execute` with a `WithdrawAsset`+`DepositAsset` program. No governance, special timing, or privileged origin is needed — this is fully reproducible by an ordinary signed account through documented extrinsic paths.

## Recommendation
Add `RuntimeCall::PolkadotXcm(..)` (or at minimum `execute`, `send`, `teleport_assets`, `reserve_transfer_assets`, `limited_teleport_assets`, `limited_reserve_transfer_assets`) to the `NonTransfer` deny-list on Asset Hub, Coretime, Collectives, and the staking-async parachain runtimes, matching the relay-chain pattern. Additionally, consider hardening `pallet_xcm::Config::XcmExecuteFilter` so that locally-executed messages reachable via proxied/delegated signed origins cannot trivially perform withdraw+deposit sequences equivalent to a transfer, and/or having `pallet-proxy` treat `pallet_xcm::execute`/`send` as inherently transfer-capable regardless of proxy type deny-list gaps.

## Proof of Concept
1. Fund `real` with native balance `N`; have `real` call `Proxy::add_proxy(attacker, ProxyType::NonTransfer, 0)`.
2. Construct `message = Xcm(vec![WithdrawAsset((Here, N).into()), BuyExecution{fees: (Here, fee).into(), weight_limit: Unlimited}, DepositAsset{assets: Wild(All), beneficiary: attacker_location}])`.
3. `attacker` calls `Proxy::proxy(real, Some(ProxyType::NonTransfer), Box::new(RuntimeCall::PolkadotXcm(pallet_xcm::Call::execute{message: Box::new(VersionedXcm::V4(message)), max_weight})))`.
4. Observe the call succeeds (proxy filter does not reject it), `Balances::free_balance(real)` decreases by `N`, and the attacker's account increases — proving the `NonTransfer` scope is bypassed. A correct fix should cause this dispatch to fail with `Error::CallFiltered`.
