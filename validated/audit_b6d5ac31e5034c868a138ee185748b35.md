### Title
Fraud detection enforcement is unconditionally disabled, allowing every signup to bypass anti-fraud checks - (File: `src/plans/mod.rs`)

### Summary
The external report describes a missing *minimum* enforcement bound (`minFeeRate`) that lets an off-chain-computed value bypass a mandatory protocol safeguard. The closest reachable analog in `orb-core` is the `detect_fraud` enforcement path in the signup pipeline, which does not merely lack a lower bound — it contains **no enforcement at all**. The function that is supposed to gate a signup on fraud/liveness results is hardcoded to always report "no fraud detected," regardless of the biometric pipeline output.

### Finding Description
`Plan::detect_fraud` in `src/plans/mod.rs` is the enforcement point invoked during every signup to decide whether the just-captured biometric pipeline output should be treated as fraudulent: [1](#0-0) 

The function takes the pipeline output, but instead of running any check against it, it is stubbed to unconditionally return `Ok(false)` with the comment `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`. This means the boolean that downstream code uses to decide `SignupReason::Fraud` vs. `SignupReason::Normal` can never be `true`, no matter what score, threshold, or fraud signal the underlying models produce.

This is corroborated by `src/plans/fraud_check.rs`, where the `Report` struct and its helper methods (`fraud_checks`, `enabled_checks_from_config`, `feedback_messages`) all return empty arrays, so `fraud_detected()` and `fraud_detected_with_config()` are structurally incapable of returning any actionable result: [2](#0-1) 

The caller in the signup flow uses this result to pick the `signup_reason` that is submitted to the backend for enrollment: [3](#0-2) 

Just as the external report's contract enforces an upper bound on `feeRate` but omits the lower bound — letting a value that should have been floored at a minimum instead be set arbitrarily low and bypass the fee requirement — `detect_fraud` here omits the enforcement entirely, so any signup, regardless of how fraudulent the underlying biometric signals are, always satisfies the "not fraud" condition and proceeds to enrollment.

### Impact Explanation
Because `detect_fraud` always resolves to `false`, `SignupReason::Fraud` can never be assigned by the orb-side pipeline; every biometric capture that produces a `Some(pipeline)` is treated as `SignupReason::Normal`. This removes the local backstop against fraudulent or spoofed signups (e.g., presentation attacks, duplicate/underage signups that the fraud pipeline was meant to catch) before the data is submitted to the backend for enrollment, enabling misattributed or unauthorized signups to proceed as if verified, undermining the integrity guarantee the fraud/liveness enforcement is supposed to provide.

### Likelihood Explanation
This is not conditional on attacker sophistication — the bypass is unconditional and hit on every single signup that reaches the fraud-check phase, since the function body performs no comparison against pipeline data at all. Any user (unprivileged, no special access) benefits from this bypass automatically.

### Recommendation
Reinstate an enforced minimum/floor condition analogous to `require(order.feeRate >= minFeeRate, ...)`: restore real threshold comparisons in `Report::fraud_checks` / `enabled_checks_from_config` and wire `detect_fraud` to evaluate the actual biometric pipeline signals (occlusion, face-identifier fraud checks, liveness scores) against configured thresholds rather than returning a hardcoded `false`.

### Proof of Concept
1. Complete a signup so that `biometric_pipeline` returns `Some(pipeline)` (any capture, regardless of quality/fraud signals).
2. Observe that `self.detect_fraud(orb, debug_report, pipeline.as_ref())` at `src/plans/mod.rs:564` always evaluates to `false` because the function body at `src/plans/mod.rs:1392-1406` never inspects `pipeline` and returns `Ok(false)` unconditionally.
3. `signup_reason` is therefore always `SignupReason::Normal` (or `Failure` only if `pipeline.is_none()`), never `SignupReason::Fraud`, and enrollment proceeds via `enroll_user` with no fraud gating having occurred locally.
