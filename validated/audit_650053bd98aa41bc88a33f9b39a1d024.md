## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are trusted from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC signature only covers the raw request body. The `shop` domain (along with `topic`, `webhook_id`, and `api_version`) is read straight from HTTP headers that are never included in the signed payload. Any party who can obtain one genuine `(body, HMAC)` pair — e.g. by installing the target app on their own store and receiving a real webhook for it — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature still validates, and the forged shop identity is handed to the app's handler as trusted data.

### Finding Description
`Registry.process` performs exactly one authenticity check: [1](#0-0) 

The HMAC check is `Utils::HmacValidator.validate(request)`, which computes and compares a signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For a `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — none of the identity headers: [3](#0-2) 

So the equality the code implicitly assumes is:
`hmac_verified(body) == identity_of(shop, topic, webhook_id, api_version)`

but the actual binding enforced is only `hmac_verified(body)`, while `shop` (and the other identity headers) are read unauthenticated from `@headers["shopify-shop-domain"]` and passed straight into the handler payload without any cross-check against the signed body: [1](#0-0) 

The gem's own documentation reinforces the false guarantee, stating that `process` "will verify the request did indeed come from Shopify," and documents `shop` as a trustworthy field of `WebhookMetadata` ("The shop domain of the webhook"): [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who has any store where the target public app is installed can capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair for a webhook they control the content of (e.g. `orders/create` on their own shop, with attacker-chosen order/customer fields). They can then POST that same body+HMAC to the app's webhook endpoint with the `shopify-shop-domain` header (and optionally `shopify-topic`/`shopify-webhook-id`) rewritten to name a victim shop. `HmacValidator.validate` passes because it only checks the body against the secret. The app's handler then processes attacker-controlled data as if it originated from the victim shop — a cross-tenant data-integrity breach (data attributed to/merged into the wrong tenant, potentially triggering victim-shop side effects such as order/inventory updates, fulfillment actions, or record creation keyed by the spoofed shop domain).

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or `client_secret` — only that the attacker can install the target public app on any store (including a free Shopify dev/partner store) to legitimately receive one signed webhook, then replay it with a modified `shop-domain` header to the app's public webhook callback URL. This is fully reachable by an unprivileged internet user.

### Recommendation
Bind the shop/topic/webhook identity to the signed payload instead of trusting headers independently:
- Include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or
- Have the host application independently verify that `request.shop` corresponds to a shop with an active, registered webhook subscription for that `webhook_id`/topic before trusting the value, and update the documentation/`WebhookMetadata` contract to state clearly that `shop` is not itself HMAC-protected.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker-shop.myshopify.com` and registers/receives a real webhook, e.g. `orders/create`, capturing the exact `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker crafts an HTTP POST to the app's webhook endpoint using the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`.
4. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` and processes it as authentic data for the victim shop. [6](#0-5) [7](#0-6)
