### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` verifies that the **body** was signed by the app's `client_secret`, but never verifies that the **`shop-domain` header** is bound to that same signature. Because `client_secret` is shared across every shop that installs the app, any shop that can trigger one legitimate webhook can replay its `(raw_body, hmac)` pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing `ShopifyAPI::Webhooks::Registry.process` to hand the handler an attacker-chosen tenant identity for genuinely-signed data.

### Finding Description
`Webhooks::Request` extracts the tenant identity from an unauthenticated header: [1](#0-0) 

but the value that is actually HMAC-verified is only the raw body: [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(client_secret, request.to_signable_string)` and compares it against the `hmac-sha256` header — it never mixes in `request.shop`: [3](#0-2) [4](#0-3) 

The verified-but-unbound `shop` value is then handed directly to the app's handler as the tenant identifier via `WebhookMetadata`, exactly as the gem's own documentation instructs consumers to use it for tenant routing/lookup: [5](#0-4) [6](#0-5) 

This is the same class of bug as the reference report: an equality the code is *supposed* to enforce — `hmac == HMAC(secret, shop || body)` — is instead only enforced over a subset (`hmac == HMAC(secret, body)`), silently dropping the `shop` binding. Since `client_secret` is per-app (not per-shop), any shop that has installed the app can capture one valid `(raw_body, hmac)` pair from its own legitimate webhook traffic and replay it against the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to any other installed shop. The signature will still validate because the header is not part of the signed content, and the handler will process attacker-supplied data under the impersonated shop's identity.

### Impact Explanation
This breaks the tenant-identity boundary the gem is supposed to provide via webhook HMAC verification: `Registry.process` asserts "this request/body came from Shopify for `request.shop`," but the code only proves "this body came from Shopify for *some* shop using this app's secret." Any app that follows the gem's documented pattern of trusting `data.shop` (as shown in `docs/usage/webhooks.md`) is exposed to cross-tenant data injection — an attacker-controlled shop can inject fabricated webhook events (order data, product changes, GDPR events, etc.) attributed to a victim shop, corrupting per-tenant state or triggering tenant-scoped side effects (e.g., fulfillment, notifications) without ever touching the victim's data directly. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability only requires being any unprivileged merchant/attacker who has installed the target app on their own store (a normal, unprivileged way to interact with a public app) — no access to `api_secret_key`, tokens, or victim credentials is needed. Triggering one webhook to capture a valid `(raw_body, hmac)` pair is trivial (e.g. update a product), and replaying it with a modified `shop-domain` header requires only a basic HTTP client. This is entirely within the gem's own webhook-processing code path (`Webhooks::Request` + `Webhooks::Registry.process` + `Utils::HmacValidator`), with no dependence on the host app violating documented behavior — the host app is doing exactly what the gem's docs instruct.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed content that `Utils::HmacValidator` verifies, or otherwise cryptographically tie the verified body to the specific shop/topic before constructing `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not allow an attacker to freely vary `shop-domain` while keeping a previously-valid `(body, hmac)` pair valid — e.g., reject/re-verify using a canonicalized string that includes `shop` and `topic`, matching Shopify's actual webhook verification guarantee per-shop rather than per-app-secret only.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. updates a product), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` sent to the app's webhook endpoint.
2. Attacker replays the exact same HTTP request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds `request.shop == "victim-shop.myshopify.com"` while `request.to_signable_string == B`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` — identical to `H` — so validation passes:
`lib/shopify_api/webhooks/registry.rb:190` `raise Errors::InvalidWebhookError ... unless Utils::HmacValidator.validate(request)`.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed B, ...)` and processes attacker-controlled data as if it originated from the victim shop.
