### Title
Fee-on-transfer tokens create phantom escrow credit in Tron `IntentGatewayV2.placeOrder`, allowing token-pool drainage / stuck escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` escrows the *requested* input amount rather than the amount actually received from `safeTransferFrom`/`transferFrom`, unlike the mainline EVM implementation which was explicitly hardened against this exact issue.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder`'s non-predispatch branch does:
```
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) 

`reducedInputs[i].amount` is derived from `order.inputs[i].amount` (the user-requested amount, optionally minus a protocol fee), not from the contract's actual token balance delta. If `token` is a fee-on-transfer ERC20, the contract receives less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is credited with the full requested (pre-fee) figure. This is the direct analog of the `Queue.deposit()` issue in the external report: the internal escrow accounting drifts above the real on-chain balance for that token by exactly the transfer fee, for every `placeOrder` call using such a token.

The predispatch branch has the same flaw: it sweeps the dispatcher's actual `balance` into transfer calls, but still books `_orders[commitment][token] += reducedInputs[i].amount` using the pre-fee requested amount rather than the swept `balance`/`dust`-adjusted figure:
```
uint256 dust = balance - requiredAmount;
if (dust > 0) emit DustCollected(token, dust);
_orders[commitment][token] += reducedInputs[i].amount;
``` [2](#0-1) 

By contrast, the audited/patched mainline `evm/src/apps/IntentGatewayV2.sol` explicitly measures the actual balance delta and mutates `order.inputs[i].amount` to the real received amount before computing the commitment/escrow, with an inline comment acknowledging the fee-on-transfer risk:
```
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [3](#0-2) 

The Tron variant was never given this fix, and `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` / `IntentGatewayV2Test.sol` only validate the fee-on-transfer correction against the mainline `IntentGatewayV2`, not the Tron contract.

### Impact Explanation
`_orders[commitment][token]` accounting on the Tron gateway is a shared pool per token across all outstanding orders using that token. When escrow bookkeeping is inflated beyond the real balance held, redemption (`withdraw`) and refund/cancel paths that pay out `body.tokens[i].amount` via `token.call(...transfer...)` will eventually be unable to pay all legitimately-recorded escrow amounts, because the contract's real balance is short by the accumulated transfer fees. This is a fund-freezing/fund-drainage condition: whichever order is redeemed/cancelled later will fail to receive its full recorded escrow (funds effectively become unbacked liabilities), or in a worse ordering, an attacker exploiting this drift across repeated `placeOrder`/`cancelOrder` (same-chain, immediate) cycles with a fee-on-transfer token can extract more tokens from the shared pool than they contributed, draining collateral belonging to other users' orders of the same token — mirroring the reported `Queue` drain exactly, just at the intent-escrow layer instead of the vault-queue layer.

### Likelihood Explanation
Any ERC20 configured as an order input on the Tron gateway that charges a transfer fee (or one that currently has a zero fee but can be changed, e.g. USDT-style tokens) triggers this on every `placeOrder` call — no special privileges or timing are required, only a normal user submitting a standard order with such a token as input. Given USDT is exactly this class of token and Tron is a common deployment target for USDT-denominated activity, the likelihood of this token class being used with the Tron gateway is realistic.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: capture `balanceOf(address(this))` before and after each `transferFrom` (and after the predispatch sweep), and use the measured delta — not the caller-specified `amount` — both for the `_orders[commitment][token]` credit and for the commitment hash computed over `order.inputs`. Apply the same correction to the predispatch-asset sweep step in the Tron contract.

### Proof of Concept
1. Deploy a 1%-fee ERC20 (`FeeOnTransferToken`) and use it as `order.inputs[0].token` with `amount = 1000e18` in a same-chain order on the Tron `IntentGatewayV2`.
2. `placeOrder` calls `safeTransferFrom(user, gateway, 1000e18)`; the gateway actually receives `990e18` (fee-on-transfer), but `_orders[commitment][token]` is incremented by the full (or fee-reduced-by-protocol-fee, but not by the transfer fee) `1000e18`-derived figure.
3. Immediately `cancelOrder` (same-chain route) is called, which invokes `withdraw(body, true)` and transfers `body.tokens[i].amount` (recorded escrow, `1000e18`-based) back to the user — but the contract only holds `990e18` of that token, so either the transfer reverts (locking the order) or, if other orders' escrow of the same token exists in the pool, the payout is satisfied out of other users' escrowed balance, silently under-collateralizing them.
4. Repeating step 1–3 (deposit+cancel) across many orders accumulates a growing shortfall between recorded `_orders` totals and the real token balance held by the gateway, exactly as described for `Queue` in the source report.
