### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw body only, while the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) are read from HTTP headers that are **not** included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` and `request.topic` to dispatch to the correct handler and to build the `WebhookMetadata` object passed to the app's handler, without ever checking that the claimed `shop` actually corresponds to the HMAC-authenticated payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `to_signable_string`: [3](#0-2) 

`Registry.process` calls this validator and then unconditionally uses `request.topic` for handler lookup and `request.shop` to populate the `WebhookMetadata` delivered to the app: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:

`shop authenticated by HMAC == shop used by handler.handle for tenant scoping`

but the actual binding is:

`shop authenticated by HMAC (raw_body only) != shop header value used for dispatch/metadata`

Since the HMAC is computed with the app's single shared `api_secret_key` across **all** shops installing the app (not a per-shop secret), any party that legitimately receives one valid webhook for their own shop (e.g., by installing the app on a store they control, or replaying a legitimately captured webhook) possesses a `(raw_body, hmac)` pair that is valid for that body under the app's secret **regardless of which `shop-domain`/`topic`/`webhook-id` header accompanies it**. That party can resend the identical `raw_body` + valid `hmac` bytes but substitute the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with a different (victim) shop's domain and topic. `HmacValidator.validate` will report the signature as valid (it never looks at the headers), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the spoofed victim shop, causing the host application to act on data for the wrong tenant — a cross-tenant identity confusion rooted entirely in this gem's webhook-verification logic.

### Impact Explanation
This crosses the "cross-tenant access" bar in the Critical impact bucket: an unprivileged actor who merely receives one authentic webhook delivery (for their own tenant/topic) can forge the tenant-identifying metadata (`shop`, `topic`, `webhook_id`) that the gem hands to the host application as "verified," without needing the app's `client_secret`, an access token, or any other privileged credential. The vulnerability lives entirely inside `lib/shopify_api/webhooks/request.rb` and `registry.rb` — the gem's own claim of "HMAC-validated webhook" implicitly covers only the body, not the routing/tenant metadata it exposes through `WebhookMetadata`, which is the exact "field acted on but not covered by the HMAC" bug class described in the report (there, the redeem fee was deducted from a value not covered by an equivalent invariant check; here, `shop`/`topic` are consumed by `process` without being covered by the same HMAC that is supposed to authenticate the whole webhook).

### Likelihood Explanation
Likelihood is moderate to high: it requires only (a) obtaining one legitimate webhook delivery — trivially available to anyone who can install the app on any shop and trigger a webhook topic they're allowed to subscribe to — and (b) being able to POST arbitrary headers/body to the app's public webhook endpoint, which is inherent to any internet-reachable webhook receiver built on this gem. No secret material, TLS interception, or social engineering is needed.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., have `Request#to_signable_string` concatenate a canonical form of these header values with the raw body) so that `HmacValidator.validate` fails whenever any of these fields are altered relative to what was actually signed by Shopify for that specific shop/topic delivery.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and subscribes to webhook topic `orders/create`.
2. Shopify sends a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-raw_body>`, and some `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair (it is delivered to their own endpoint, so they own it).
4. Attacker resends the exact same `raw_body` and `hmac` header to the app's endpoint, but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present), and `Utils::HmacValidator.validate(request)` returns `true` because it only checks `hmac` against `raw_body` — see `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
6. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` — see `lib/shopify_api/webhooks/registry.rb:188-200` — delivering attacker-controlled `shop`/`topic` values that the host application believes are HMAC-verified and tied to `victim-shop.myshopify.com`.
