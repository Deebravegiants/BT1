### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Registry.process` trusts the unauthenticated `shop-domain` header (`request.shop`) to determine which tenant the webhook event belongs to. The HMAC therefore authenticates *that some body was signed with the app's shared secret*, but not *which shop* the event is attributed to, breaking the binding `authenticated_signature_scope == shop_the_handler_acts_on`.

### Finding Description
`Request#hmac` is computed over `shopify_header("hmac-sha256")` and validated by `Utils::HmacValidator.validate` against `to_signable_string`, which is defined as just `@raw_body`: [1](#0-0) [2](#0-1) 

None of `topic`, `shop`, `api_version`, or `webhook_id` — all pulled unauthenticated from HTTP headers via `shopify_header` — are included in the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally dispatches to the app handler using the unauthenticated `request.shop` value as the tenant identity: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` used to sign webhook bodies is shared across *every* shop that has the app installed (it is not a per-shop secret), an attacker who installs the app on their own shop can trigger events that produce a genuine, correctly-signed webhook body (e.g. an order/customer payload they fully control), capture the `hmac-sha256` header Shopify computed for it, and then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `Utils::HmacValidator.validate` will pass because it only checks the body bytes against the signature, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop: [5](#0-4) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold — `hmac_signed_scope == (shop, topic, body)` — instead only holds for `body`.

### Impact Explanation
Handlers registered via `Registry.add_registration` typically use `data.shop` to look up the shop's session/offline access token and perform actions (data sync, order fulfillment, GDPR redaction flows, etc.) attributed to that shop. Since `shop` is attacker-controlled and unauthenticated, an attacker can cause the host application to process an attacker-fabricated payload (crafted through their own shop's actions) as if it originated from an arbitrary victim shop, resulting in cross-tenant data corruption or the triggering of privileged, shop-scoped side effects (e.g. mandatory `customers/redact`, `shop/redact`, `customers/data_request` handling) under a false tenant identity. This meets the Critical bar of cross-tenant access.

### Likelihood Explanation
Exploitation requires only that the attacker have the app installed on a shop they control (a normal, unprivileged install) — no access token, API secret, or victim credentials are needed. The attacker only needs to know a valid victim shop domain (public information) and craft a request to the app's public webhook endpoint with modified headers. This is reachable by any unprivileged internet user who can install the target app.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the value that is cryptographically bound to the signature check, or independently verify `request.shop` against a shop known to have installed the app (e.g. cross-check against a stored session for that shop) before dispatching to the handler. At minimum, document and enforce that `Registry.process` must not trust `request.shop` for authorization decisions unless corroborated by a stored, previously-authenticated session for that shop.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body they fully control.
2. Shopify computes and delivers a legitimate `X-Shopify-Hmac-Sha256` header for that body signed with the app's shared `client_secret`.
3. Attacker replays the request to the app's webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and desired `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the signature. [6](#0-5) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing the host app to act as though the event genuinely originated from the victim shop.
