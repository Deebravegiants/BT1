## Finding

### Title
Unbounded weight in `pallet-ismp::handle_unsigned` allows a permissionless proof-heavy extrinsic to consume far more execution time than its declared, fixed weight — ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`Pallet::handle_unsigned` is dispatched as an unsigned extrinsic (`ensure_none`), so any network peer can submit it for free, and its declared weight is a hard-coded constant regardless of the size or content of the `messages: Vec<Message>` payload:

```rust
#[pallet::weight(weight())]
#[pallet::call_index(0)]
#[frame_support::transactional]
pub fn handle_unsigned(origin: OriginFor<T>, messages: Vec<Message>) -> DispatchResultWithPostInfo {
    ensure_none(origin)?;
    Self::execute(messages.clone())?;
    Ok(().into())
}
``` [1](#0-0) 

```rust
fn weight() -> Weight {
    Weight::from_parts(300_000_000, 0)
}
``` [2](#0-1) 

`Vec<Message>` has no `BoundedVec` cap on element count, and the individual `Message` variants (GRANDPA finality proofs with `unknown_headers`, BEEFY/SP1 consensus updates with large authority sets or MMR multi-proofs, sync-committee multi-proofs, Pharos SPV proofs up to `MAX_PROOF_DEPTH`, etc.) can each carry substantial cryptographic verification work bounded only by the runtime's max extrinsic/block length, not by weight. `Self::execute` is also invoked a second time inside `validate_unsigned`, which runs on every node during transaction-pool validation, doubling the unmetered cost per submission:

```rust

    let messages = match call {
        Call::handle_unsigned { messages } => messages,
        _ => Err(TransactionValidityError::Invalid(InvalidTransaction::Call))?,
    };
    let events = Self::execute(messages.clone()).map_err(|_| InvalidTransaction::BadProof)?;
    ...
``` [3](#0-2) 

### Finding Description
Substrate's weight system is the mechanism that bounds how much CPU time a block author/importer will spend per extrinsic and per block. When an extrinsic's declared weight does not reflect its true computational cost, an attacker can craft an unsigned `handle_unsigned` transaction containing many messages (or a small number of messages with maximally large but individually-valid consensus/state proofs — e.g. many GRANDPA `unknown_headers`, large BEEFY authority-set merkle multiproofs, deep Pharos SPV proofs up to `MAX_PROOF_DEPTH`, or large sync-committee multi-proofs) whose real verification cost vastly exceeds the fixed `300_000_000` weight units charged. Because the call is unsigned and free (`Self::Currency` is never touched for `handle_unsigned`), and it is validated twice (once in `validate_unsigned` in the pool, once again at dispatch), a single well-formed, cryptographically valid submission can force every collator/validator/full node to perform far more verification work than the block's weight accounting assumes, repeatedly, for the cost of assembling one syntactically valid message.

This mirrors CVE-2023-22056's bug class: a low-cost, permission-light input (there, a crafted SQL optimizer query; here, a crafted but valid ISMP message batch) drives disproportionate CPU consumption inside a core dispatch path, producing a hang or repeatable resource-exhaustion condition rather than a memory-safety violation.

### Impact Explanation
If actual per-message verification cost is not tightly bounded relative to the fixed weight, this allows a route/consensus-update DoS: nodes spend excessive, unbudgeted time validating and executing `handle_unsigned` transactions, degrading block production/import throughput on the affected parachain and stalling processing of legitimate incoming ISMP messages — i.e., "a route unable to deliver messages," which is one of the explicitly accepted impact categories. Because the extrinsic is unsigned and processed for free, the attack has near-zero cost to mount repeatedly.

### Likelihood Explanation
Medium: exploitation requires no privileges beyond network access to submit an unsigned extrinsic (permissionless by design), and valid consensus/state proofs of near-maximal size for a supported client (GRANDPA, BEEFY, sync-committee, Pharos) are obtainable by any relayer/observer of the source chain, since proof structure/size is a function of protocol parameters rather than secret data. The severity of the resulting slowdown depends on how far real verification cost diverges from the fixed 300M weight budget across the various consensus client implementations, which is not derivable purely from static review and would need on-chain benchmarking to confirm the magnitude.

### Recommendation
- Replace the fixed `weight()` constant on `handle_unsigned` with a weight function that scales with the actual content of `messages` (number of messages, number of headers/leaves in nested proofs, proof depth), similar to the `IsmpModuleWeight`/`FeeHandler` benchmarking pattern already used for `on_accept`/`on_response`/`on_timeout`.
- Enforce hard upper bounds (`BoundedVec`, or explicit length checks in `validate_unsigned`/`pre_dispatch`) on `messages.len()` and on nested proof structures (e.g., `unknown_headers`, MMR/authority multiproof leaf counts) so no single unsigned extrinsic can exceed a safe, benchmarked worst-case weight.
- Consider skipping the duplicate `Self::execute` call between `validate_unsigned` and `handle_unsigned`, or caching/reusing verification results, to avoid doubling the unmetered cost of processing the same payload.

### Proof of Concept
Not independently executable from static review alone; would require on-chain weight benchmarking across each `ConsensusClient` (GRANDPA/BEEFY/sync-committee/Pharos) to demonstrate that a maximally-sized-but-valid `Message` (e.g., a GRANDPA `FinalityProof` with the largest permitted `unknown_headers` vector, or a BEEFY proof with the largest supported authority set) consumes execution time substantially exceeding the fixed 300,000,000-weight budget declared for `handle_unsigned`.
