### Title
AMM pool creation can be front-run via the deterministic, publicly-known `market_info` PDA seed, permanently blocking honest pool creation for that market - (File: `program/src/processor.rs`)

### Summary
`Initialize2` derives every account of a new pool (AMM state, target orders, LP mint, coin/pc vaults) as a PDA seeded solely by the (public, attacker-visible) OpenBook `market_info` pubkey and the program id. Because the seed is not chosen or committed to by the creator in any front-running-resistant way, and because any signer can supply arbitrary `user_wallet`/`user_token_coin`/`user_token_pc` accounts, an attacker can observe (or simply predict, since the market account itself is public) an honest user's pending `Initialize2` transaction and submit an equivalent instruction first, consuming the deterministic pool address for that market with only dust liquidity.

### Finding Description
The pool's core accounts are derived with `get_associated_address_and_bump_seed`, which uses only `market_account.key` and a fixed seed suffix: [1](#0-0) 

`generate_amm_associated_account` / `generate_amm_associated_spl_token` allocate and assign these PDAs, but explicitly bail out with `RepeatCreateAmm` once the account is no longer owned by the system program, i.e. once *anyone* has already claimed the PDA for that market: [2](#0-1) [3](#0-2) 

`process_initialize2` never requires that `user_wallet_info` (the signer), `user_token_coin_info`, or `user_token_pc_info` belong to any specific, pre-committed party — any signer holding a positive balance of the coin/pc mints can call it for a given `market_info`: [4](#0-3) 

The only floor on how little liquidity is required to successfully claim the pool is `InitLpAmountTooLess`, which just requires `liquidity > 10^lp_decimals` — trivially satisfiable with a dust deposit for most token decimal configurations: [5](#0-4) 

Because the market account is public (an OpenBook/Serum market that anyone can read on-chain, and whose creation is itself a public transaction), an attacker monitoring the mempool for `Initialize2` calls targeting a market can front-run the honest creator's transaction with the identical `market_info`, their own token accounts, and a minimal `init_coin_amount`/`init_pc_amount`. Their transaction lands first, the AMM/LP mint/vault PDAs for that market become permanently owned by the program, and the legitimate creator's transaction subsequently fails with `AmmError::RepeatCreateAmm` because `associated_token_account.owner` is no longer the system program.

### Impact Explanation
Since the pool address space for a given market is a single deterministic PDA, once an attacker front-runs pool creation for that market with dust liquidity, no other party can ever create a proper, well-funded pool for that trading pair through this program instance — the PDA is permanently occupied. This is a genuine griefing/DoS: the intended liquidity provider's transaction reverts and the market is left with a functionally worthless (or attacker-controlled economics) pool with negligible liquidity, which also leaves it exposed to sandwich/price-manipulation on the very first real swaps, and prevents the legitimate creator from ever "correctly" seeding a fresh pool for that mint pair. It matches the "griefing" impact category: no profit is required for the attacker, but users/protocol suffer a permanent loss of ability to properly bootstrap that pool.

### Likelihood Explanation
The attack requires no privileges: it is a single, unprivileged transaction using `Initialize2` with attacker-chosen accounts (their own `user_wallet`, `user_token_coin`, `user_token_pc`) and attacker-chosen data (`init_coin_amount`, `init_pc_amount`, `open_time`), reachable purely from watching either the mempool for the target `Initialize2` transaction or simply the public creation of the underlying OpenBook market (which must exist before a pool can reference it). On any chain with a public mempool this is trivially executable by any bot, making likelihood high whenever a new, high-value market's pool is about to be created.

### Recommendation
- Require the creator to commit to a pool creation in a front-running-resistant way, e.g., derive the AMM PDA using a seed that includes the creator's own pubkey (or a creator-chosen nonce bound to their pubkey) rather than only the `market_info` pubkey, so the same market cannot be pre-claimed by an unrelated third party at negligible cost.
- Alternatively/additionally, raise the minimum initial liquidity requirement well above `10^lp_decimals` so dust-value front-running is economically infeasible, and/or restrict who may call `Initialize2` for a not-yet-initialized market (e.g., only the account that created/owns the OpenBook market, or a permissioned allow-list), removing the fully-permissionless race condition on pool creation.

### Proof of Concept
1. Alice creates (or is about to reference) OpenBook market `M` and prepares an `Initialize2` transaction seeding pool `PDA(M)` with substantial coin/pc liquidity via `program/src/instruction.rs::initialize2`.
2. Attacker Bob observes Alice's pending transaction in the mempool (or simply observes that market `M` now exists on-chain, since `market_info` is a public, non-secret account) and submits his own `Initialize2` call for the same `market_info = M`, using his own `user_wallet`, `user_token_coin`, `user_token_pc` accounts and the smallest `init_coin_amount`/`init_pc_amount` that satisfies `liquidity > 10^lp_decimals` (see `program/src/processor.rs:908-917`).
3. Bob's transaction lands first: `generate_amm_associated_account`/`generate_amm_associated_spl_token` succeed because the PDAs for `PDA(M)` are still system-owned, and the pool for market `M` becomes permanently initialized with dust liquidity under Bob's control.
4. Alice's transaction is then processed and reverts with `AmmError::RepeatCreateAmm` at `program/src/processor.rs:541-544` (or `313-317`), because the associated accounts for `market_info = M` are no longer owned by the system program — Alice can never create a properly-funded pool for market `M`.
