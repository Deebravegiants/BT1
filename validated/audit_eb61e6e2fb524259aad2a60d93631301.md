## Title
Webhook shop/topic identity spoofing via headers not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the application are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards these unverified header values straight to the app's webhook handler as trusted identity data. This breaks the equality `shop_header == shop_that_produced(hmac)`: the signature never binds the header-derived `shop`/`topic` to the signed bytes, so any holder of a valid `(body, hmac)` pair for a webhook signed with the app's `api_secret_key` can relabel the shop and topic and have the app process it as belonging to a different tenant.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from the (attacker-controllable) HTTP headers with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.topic` and `request.shop` (both header-derived) as the tenant identity for the handler call: [3](#0-2) 

Shopify signs every webhook for an app with the app's single shared `api_secret_key` — the same key is used regardless of which merchant/shop triggered the webhook (confirmed by `HmacValidator.validate` using `Context.api_secret_key`/`Context.old_api_secret_key`, with no shop-specific key material): [4](#0-3) 

Because the signature covers only the body bytes, an unprivileged internet user who legitimately receives (or otherwise obtains) a valid `(body, hmac)` pair for any topic on any shop connected to the app can resend that exact body/hmac pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` and `shopify-topic` headers to point at a victim shop and a different (potentially more sensitive) topic. `Registry.process` will accept the forged headers as-is because `Utils::HmacValidator.validate` only checks the body against the shared secret — it never checks that the claimed `shop`/`topic` match what was actually signed, since they weren't part of the signed data at all.

### Impact Explanation
This breaks the binding `authenticated_bytes == identity_metadata_acted_on`, letting an attacker cause the host application to process webhook data attributed to an arbitrary shop/topic pair with a validly-signed body they control (e.g., from their own installed store). Depending on the handler logic (data deletion, compliance topics like `customers/redact`/`shop/redact`, uninstall cleanup, order/inventory sync, etc.), this can result in cross-tenant data corruption or actions being taken against a shop that never sent the webhook — a cross-tenant access violation.

### Likelihood Explanation
Exploitability requires the attacker to obtain at least one valid `(body, hmac)` pair signed with the app's `api_secret_key` — trivially achievable by any merchant who installs the app and triggers any webhook on their own store, since Shopify signs all app webhooks with the same shared secret. No access to `api_secret_key` itself, TLS interception, or privileged accounts is needed; only the ability to install the app as any shop and then POST to the public webhook endpoint with forged headers.

### Recommendation
Bind the `shop` and `topic` (and any other fields the handler relies on for identity/routing) into the signed material, or otherwise cryptographically tie them to the verified body — e.g., require the handler-facing metadata to be re-derived from the verified JSON body rather than raw headers, or have `Registry.process` cross-check header-derived `shop`/`topic` against values embedded in the (now-verified) payload before dispatching to a handler. At minimum, document that header values are unauthenticated and must not be trusted as tenant identity without additional verification.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify sent (both signed with the app's shared `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/redact` (or any other topic/shop the attacker wants processed).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC over `B` using the shared secret — see [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: ...)`, causing the app to perform handler logic against `victim-shop` despite the request never originating from that shop — see [6](#0-5) .
