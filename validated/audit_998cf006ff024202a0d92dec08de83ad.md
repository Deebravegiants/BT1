Found a direct analog. The `convert_to_balance` / `convert_to_erc20` decimal-scaling helpers in `pallet-hyper-fungible-token` compute the scale factor with `erc_decimals.saturating_sub(local_decimals)`, which silently clamps to `0` whenever `erc_decimals < local_decimals` instead of performing the inverse scaling — exactly the same class of unguarded decimals-based division/scaling bug as the reported `LibUbiquityPool.getDollarInCollateral` issue, and it is reachable by any signed account via the `send` extrinsic.

### Title
Reversed-decimals `saturating_sub` in `convert_to_erc20`/`convert_to_balance` allows unbacked mint on the destination `HyperFungibleToken` contract - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s cross-chain amount conversion helpers only correctly scale amounts when the EVM-side ERC20 decimals (`erc_decimals`) are greater than or equal to the local asset's decimals (`local_decimals`). When `erc_decimals < local_decimals`, `saturating_sub` clamps the exponent to `0`, so the function performs **no scaling at all** instead of the required inverse conversion. In `send()`, this means the escrowed/burned amount on the substrate side is forwarded to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract unscaled, and that contract mints `message.amount` directly to the beneficiary — resulting in a mint that is `10^(local_decimals - erc_decimals)` times larger than what the sender actually locked/burned.

### Finding Description
The two conversion helpers are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

`convert_to_erc20` is called from `send()` to compute the outgoing `Message.amount` that will be dispatched to the peer EVM contract: [2](#0-1) 

```rust
let sender: [u8; 32] = who.clone().into();
let amount: u128 = params.amount.into();
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);

let token_message = Message {
    from: sender.to_vec().into(),
    to: params.recipient.to_vec().into(),
    amount: alloy_primitives::U256::from_be_bytes(erc20_amount.to_big_endian()),
    data: params.call_data.unwrap_or_default().into(),
};
```

`erc_decimals` here is `Precisions::<T>::get(asset_id, destination)` (the decimal precision governance recorded for the asset on the destination EVM chain), while `decimals` is the local asset's own decimals (the local currency/asset's precision, which can legitimately be higher than 6, 8, or even 12/18 depending on the asset). Correct scaling requires:
- multiply by `10^(erc_decimals - local_decimals)` when `erc_decimals >= local_decimals` (handled correctly), or
- **divide** by `10^(local_decimals - erc_decimals)` when `erc_decimals < local_decimals` (NOT handled — `saturating_sub` returns `0`, so the function multiplies by `10^0 = 1`, i.e. no conversion happens).

The destination `HyperFungibleToken.onAccept` mints `message.amount` verbatim to the beneficiary: [3](#0-2) 

Since the `Message.amount` was never scaled down for the `erc_decimals < local_decimals` case, the beneficiary receives `10^(local_decimals - erc_decimals)` times more tokens on the destination chain than the amount actually escrowed/burned on the source chain. The reverse function `convert_to_balance` (used by `on_accept`/`on_timeout` on the substrate side) has the mirror-image flaw and under-credits in that direction, but the `send()` path is the one that produces unbacked/inflated minting on the EVM destination — the same "no check on the resulting minted amount vs. what was actually paid in" root cause as the audit report's `mintDollar`/`getDollarInCollateral` issue, just triggered via a decimals-scaling helper instead of a price-based division.

### Impact Explanation
Any signed account can call `send()` for an asset whose registered EVM-side `Precisions` value is lower than the local asset's own decimals (a realistic configuration — e.g. a locally 18-decimal `pallet-assets` representation of a token whose canonical EVM form uses 6 decimals, such as USDC-style stablecoins). Every `send()` call in that configuration burns/escrows the correct (small) local amount but instructs the destination contract to mint an amount inflated by `10^(local_decimals - erc_decimals)`, i.e. unbacked minting of the bridged asset on the EVM side, draining the peg/backing between the two representations and letting an attacker repeatedly mint value with no economic cost.

### Likelihood Explanation
The path is reachable via a single unprivileged `send` extrinsic and requires no special conditions beyond a registered asset/chain pair where `erc_decimals < local_decimals` — a configuration governance may set up entirely legitimately (the docs only say EVM decimals are "typically 18", not that they must exceed local decimals). Once such an asset exists, exploitation is immediate and repeatable by any holder of the asset with no need for governance or admin compromise.

### Recommendation
Fix both `convert_to_balance` and `convert_to_erc20` to handle both scaling directions explicitly:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and symmetrically for `convert_to_balance`, with the division direction reversed. Additionally, consider explicitly rejecting `send()`/`on_accept` conversions that round to zero, to avoid the equivalent zero-value silent-mint edge case highlighted in the referenced report.

### Proof of Concept
1. Governance registers an asset via `register_token` where the local `pallet-assets` decimals for the asset is `18`, and `Precisions` for the destination EVM chain is set to `6` (a plausible real-world mapping, e.g. bridging a 6-decimal stablecoin whose local wrapped representation uses 18 decimals).
2. A user calls `send(asset_id, destination, recipient, amount = 1_000_000000000000000 /* 1 unit at 18 decimals */, ...)`. The pallet burns/escrows `1e18` raw units locally (correct).
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `exponent = 6.saturating_sub(18) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18`.
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken` contract, which calls `_mint(beneficiary, 1e18)` — minting `1e18` raw ERC20 units (i.e., `1e12` "dollars" worth at 6-decimal precision) even though only `1` unit's worth (`1e18` at 18 decimals ≈ 1 token) was actually escrowed. The beneficiary receives `10^12` times the correct amount, an unbacked mint.
