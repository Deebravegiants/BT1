## Analysis

CVE-2021-25742's bug class is: **a shared, privileged execution context accepts attacker-controlled input from an unprivileged actor and executes it with no isolation between tenants**, letting that actor reach resources belonging to others.

The closest reachable analog in Hyperbridge is `CallDispatcher.dispatch()` — a single shared contract instance used by every ISMP application (`IntentGatewayV2`, `ExtrinsicIntents`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and their Tron counterparts) to execute arbitrary attacker-supplied calldata, but the function has **no access control whatsoever**.

### Title
Unauthenticated `CallDispatcher.dispatch()` lets any unprivileged actor drain funds transiently held by the shared cross-app call executor - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is deployed once and shared across `IntentGatewayV2`, `ExtrinsicIntents`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` (and their Tron equivalents) as the execution point for order predispatch/postdispatch calldata and HFT/WHFT cross-chain calldata. Its `dispatch(bytes memory encoded)` function is `external` with **no caller restriction** — not `onlyGateway`, not `onlyHost`, nothing. [1](#0-0) 

### Finding Description
Every app that uses `CallDispatcher` briefly moves real user/escrowed funds through it before calling `dispatch()` on attacker-supplied `Call[]` data, then sweeps the residual balance back:

- `IntentGatewayV2.placeOrder` transfers `predispatch.assets` into the dispatcher, then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` with calldata fully controlled by the order placer. [2](#0-1) 
- `IntentsBase._execute` (fill path) dispatches `order.output.call`, then sweeps whatever ERC20/native balance remains on the dispatcher back to the gateway as "dust." [3](#0-2) 
- `WrappedHyperFungibleToken.onAccept` unlocks tokens to the beneficiary and then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` with attacker/sender-controlled calldata from the source chain message. [4](#0-3) 

The protocol's own documentation acknowledges the dispatcher "holds tokens temporarily during execution" and explicitly warns against unlimited approvals in the `Call[]` array because of this — i.e., the design already assumes value can transiently sit on this address: [5](#0-4) 

Because `dispatch()` carries no `msg.sender` check, any unprivileged party — a solver, a token bridger, or any address at all, not just the gateway/host contracts that are supposed to be the only legitimate callers — can invoke it directly at any time with their own arbitrary `Call[]`. This breaks the isolation the interface's own comment claims to provide ("dispatch untrusted call(s)" implies the *calls* are untrusted but the *caller* was assumed to be a trusted app contract): [6](#0-5) 

This mirrors the CVE's structure exactly: a component meant to run only inputs vetted/introduced by a privileged caller (ingress-controller admin ⇔ the gateway/HFT contracts) instead accepts input from anyone, and the shared execution context has access to state (secrets ⇔ transiently held escrow/dust funds, and any native ETH sent via the dispatcher's payable `receive()`) that does not belong to the caller.

### Impact Explanation
Any residual ERC20 balance or native ETH sitting on `CallDispatcher` — whether from imperfect dust-sweeping (fee-on-transfer tokens, rounding, a reverted sweep leaving assets behind), or ETH sent directly via its unguarded `receive()` — is stealable by an arbitrary unprivileged caller who crafts a `Call[]` transferring that balance to themselves. Because the same dispatcher instance backs multiple independent apps, funds belonging to any of `IntentGatewayV2`, `ExtrinsicIntents`, `HyperFungibleToken`, or `WrappedHyperFungibleToken` users are exposed through this single unauthenticated entry point, rather than being isolated per-app.

### Likelihood Explanation
Reachability is trivial and requires no special privilege: `dispatch()` is a public external function with zero preconditions, callable by any EOA or contract with a single transaction. The likelihood of exploitation is bounded only by whether/how often a non-zero balance is left on the dispatcher between transactions, which the project's own documentation admits can happen ("dust," temporary holding, non-exact approvals).

### Recommendation
Restrict `CallDispatcher.dispatch()` to a set of authorized caller contracts (the registered gateway/HFT instances), e.g. via an `onlyAuthorizedCaller` modifier backed by an allowlist set at deployment/configuration time, mirroring the `onlyHost` pattern already used on `onAccept` handlers. Additionally, ensure sweep logic in `_execute`/predispatch flows leaves zero residual balance (or add a permissionless "sweep to caller-specified beneficiary that only the depositing app can trigger") so no value can persist on the shared dispatcher between transactions.

### Proof of Concept
1. Observe (via events or direct `balanceOf`/`address(dispatcher).balance` queries) that `CallDispatcher` holds a non-zero balance of some token or native ETH after a legitimate order fill/predispatch flow (dust left by fee-on-transfer token, rounding, or a stray `receive()` deposit).
2. As an arbitrary unprivileged address (no relationship to the order/message that left the balance), call:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({
    to: TOKEN,
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)
});
CallDispatcher(dispatcher).dispatch(abi.encode(calls));
```
3. The transfer succeeds because `dispatch()` performs no caller check — the attacker walks away with funds that belonged to another party's cross-chain order/message. [7](#0-6)

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
