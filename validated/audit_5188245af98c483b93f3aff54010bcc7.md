## Finding

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. Since the app's `api_secret_key` is a single value shared across every shop that installs the app, any shop can obtain a valid `(raw_body, hmac)` pair for its own webhook traffic and replay that exact body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. The signature still validates (it only checks the body), but the tenant identity handed to the app's handler is now attacker-controlled.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from a header that is not part of the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) using the app's single `api_secret_key`: [3](#0-2) 

`Registry.process` only checks that the HMAC of the body is valid, then trusts `request.shop` as the tenant for the handler: [4](#0-3) 

The identity binding this breaks: **bytes verified (raw body under HMAC) ≠ bytes/field acted on (`shop-domain` header)**. Because `api_secret_key` is shared by all shops that install the app (it is the app's client secret, not a per-shop secret), any installed shop can generate a body+HMAC pair that Shopify itself would have sent for that shop's webhook, and that same pair remains valid for *any* `shop-domain` value, since the header is never part of the signed content.

### Impact Explanation
An attacker who installs the target app on their own (attacker-controlled) shop can:
1. Trigger any webhook topic they've subscribed to (e.g. `orders/create`) and capture the resulting `raw_body` and `hmac-sha256` header Shopify sent to the app's registered endpoint.
2. Replay that exact body and HMAC to the app's webhook endpoint, but set `shopify-shop-domain` to a victim shop's domain.
3. `Utils::HmacValidator.validate` passes (same body, same shared secret), and `Registry.process` calls the app's `WebhookHandler#handle` with `shop: <victim-shop>` and the attacker-crafted body/topic.

Since the app's business logic trusts `WebhookMetadata#shop` as the source of truth for which tenant to act on (e.g., updating orders, redacting customer data, revoking access for `shop/redact`), this allows an attacker to make the host application perform actions against, or ingest attacker-controlled data into, a completely different merchant's tenant — a cross-tenant access issue.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on any shop they control (which is normal, unprivileged app installation, not a privileged account) and to be able to send HTTP requests to the app's public webhook endpoint, which by design must be reachable from the internet. No access token, `api_secret_key`, or other secret is required — the attacker only reuses a `(body, hmac)` pair that Shopify itself legitimately produced for the attacker's own shop.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header into the value that's HMAC-verified, or otherwise cryptographically bind the claimed shop to the request, e.g. by including the header value in `to_signable_string`, or by validating that `request.shop` matches an already-known/authorized shop record before invoking the handler. At minimum, document/enforce that `WebhookMetadata#shop` must not be trusted unless it is corroborated by data outside the header set that isn't covered by the signature.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives/triggers a legitimate webhook, capturing:
raw_body = '{"id": 1, "note": "hello"}'
hmac_b64 = "<value Shopify sent in shopify-hmac-sha256 for attacker's own shop>"

# Attacker replays the SAME body+hmac to the app's public webhook endpoint,
# but spoofs the shop-domain header to target a victim shop:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  "shopify-webhook-id" => "spoofed-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation passes because it only checks `raw_body` against the app's
# single shared api_secret_key; the handler executes with shop: "victim-shop.myshopify.com"
``` [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
