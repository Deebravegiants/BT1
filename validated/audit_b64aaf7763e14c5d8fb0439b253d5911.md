### Title
Under-metered compute cost for regular access-key and contract-data removal during `DeleteAccount` - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` calls `remove_account`, which iterates and removes every access key and every contract-data record belonging to an account one trie entry at a time. The only removal work that is billed against the chunk's `compute_usage` budget is the removal of **gas-key nonces**; the (potentially much larger) set of ordinary access keys and contract-data keys removed in the same loop is never added to `result.compute_usage`. This mirrors the reported bug class: real per-item O(n) trie work is performed without a matching, linear compute charge, so the accounting that is supposed to bound a chunk's wall-clock cost can be bypassed.

### Finding Description
`remove_account` walks the account's access-key/gas-key prefix and its contract-data prefix, collecting every matching trie key and then calling `state_update.remove()` on each one individually: [1](#0-0) [2](#0-1) 

The function returns only `gas_key_nonce_count` / `gas_key_nonce_total_key_bytes`, i.e. counts of gas-key nonce rows removed. It reports nothing about how many regular access keys or contract-data keys were removed.

In `action_delete_account`, the compute-cost accounting only converts `gas_key_nonce_count` into a `storage_removes_compute` charge added to `result.compute_usage`: [3](#0-2) 

There is no equivalent `storage_removes_compute` call for the access keys and contract-data entries removed by the same `remove_account` invocation — those removals cost real trie-mutation work (`storage_removes_compute` is defined specifically to model this cost, see `runtime/runtime/src/config.rs:54-60`) but are charged $0 compute.

The only safeguard against an account accumulating an unbounded number of these entries is a byte-based ceiling on the account's total `storage_usage`: [4](#0-3) 

This bound (`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`, defined in `core/primitives-core/src/account.rs`) limits the total *storage bytes* an account may hold before it can be deleted, not the *number* of individually-removed trie entries. Because access keys and contract-data records can each be made very small (a few bytes for a short key name / empty or minimal value), an attacker can, within that byte budget, create a large number of tiny access keys or `Data` entries on a single account they own, paying only the fixed per-entry storage staking cost, then issue a single `DeleteAccount` action. `remove_account` will loop over all of them and perform an individual trie `remove()` for each, while `action_delete_account` bills compute only for the (in this attack, empty) set of gas-key nonces.

By contrast, for `DeleteKey` on a regular (non-gas) key, `delete_regular_key` likewise never adds to `result.compute_usage`: [5](#0-4) 
confirming that this whole class of trie-removal (regular access keys, contract data) is systematically excluded from the `compute_usage` metering that was specifically introduced (for gas keys) to bound the real cost of bulk removals within `max_gas_burnt`/`compute_limit` per chunk.

### Impact Explanation
This is analogous to the reported order-book DoS: real, disproportionate per-item work (trie removal) is not reflected in the resource metric (`compute_usage`) that is checked against the chunk's `compute_limit` (`runtime/runtime/src/lib.rs` `process_receipts`). A single `DeleteAccount` receipt can therefore make a validator perform many more trie mutations than its reported/charged compute would suggest, understating the actual chunk-processing cost. If repeated across multiple accounts/receipts in a chunk, this results in underpriced/free execution work relative to the protocol's compute accounting, which is the mechanism meant to prevent a chunk from taking longer than its allotted budget to apply — risking slower block production or an inconsistency between the gas/compute economically charged and the wall-clock cost actually imposed on all validators.

### Likelihood Explanation
The path is reachable by any account owner via ordinary, unprivileged transactions: create many small access keys and/or write many small contract-data entries (each within normal fee/storage-staking rules) up to the byte ceiling `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, then submit one `DeleteAccountAction`. No special privileges are required. The severity depends on how large `MAX_ACCOUNT_DELETION_STORAGE_USAGE` is relative to the minimum per-entry byte footprint (this exact numeric ceiling could not be retrieved in this session — it is declared in `core/primitives-core/src/account.rs`), which determines the maximum achievable entry count and therefore how far the uncharged compute work can scale.

### Recommendation
Extend `remove_account`'s result to also track the count and total key/value bytes of regular access-key and contract-data removals (in addition to the existing gas-key-nonce counters), and have `action_delete_account` add a corresponding `storage_removes_compute` charge to `result.compute_usage` for those removals as well, consistent with how gas-key nonce removal is already billed.

### Proof of Concept
1. Create an account and, using ordinary `AddKey`/`FunctionCall` (or a helper contract writing many small `storage_write` entries) transactions, populate it with the maximum number of minimal-size access keys and/or contract-data records permitted while keeping total `storage_usage` under `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`.
2. Submit a single `DeleteAccountAction` transaction for that account.
3. Observe that `remove_account` (`core/store/src/utils/mod.rs:505-575`) performs one `state_update.remove()` per access key/data entry, but `action_delete_account` (`runtime/runtime/src/actions.rs:371-386`) adds `compute_usage` only for `gas_key_nonce_count` (zero in this scenario), so the reported `compute_usage` for the receipt does not reflect the actual number of trie removals performed.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }
