### Title
Non-embedded session lookup trusts an unsigned, predictable session-id cookie, enabling cross-tenant session hijacking - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
The M-5 report's root cause is a broken identity binding: code pulls/acts on a value (`stake`) that was never covered/authorized by the matching approval, instead of the value (`quote.sellToken`/`quote.amount`) that was actually verified. The analogous class of bug in this gem is checking/deriving an identity from bytes that were never authenticated, then using that identity to grant access. `ShopifyAPI::Utils::SessionUtils` exhibits exactly this pattern: for non-embedded apps, the "authenticated session id" that the host app uses to fetch a merchant's stored `Session` (containing the real Admin API `access_token`) is taken verbatim from an unsigned browser cookie, and that id is a deterministic, guessable function of the shop domain.

### Finding Description
`ShopifyAPI::Utils::SessionUtils.current_session_id` is the gem's documented mechanism (`docs/getting_started.md` lines 41-52) for non-embedded apps to resolve "the session id" from the request: [1](#0-0) 

For non-embedded apps (`else` branch) — and also as the fallback path for embedded apps without a JWT — it calls `cookie_session_id`, which returns the raw, attacker-controllable cookie value with no cryptographic verification whatsoever: [2](#0-1) 

The session ids that this cookie is expected to carry are deterministic, predictable strings derived only from the shop domain (and user id for online sessions) — not secrets: [3](#0-2) 

This same predictable id (e.g. `"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`) is what gets written into the cookie by `ShopifyAPI::Auth::Oauth.validate_auth_callback` after a real OAuth completion, with no HMAC/signature over the cookie value itself: [4](#0-3) [5](#0-4) 

The binding that should hold is:

`session_id_used_to_fetch(access_token) == session_id_bound_to_the_browser_that_completed_the_shop's_OAuth_flow`

What actually holds is:

`session_id_used_to_fetch(access_token) == raw_unauthenticated_bytes_of_a_client-supplied_cookie`

Because the cookie value is never signed and its content is a deterministic function of public information (the shop's `myshopify.com` domain, which is routinely discoverable — e.g. via the storefront's public HTML/JSON, `X-ShopId` headers, sitemaps, or simply guessed for a known merchant name), any unauthenticated internet user can forge the `SESSION_COOKIE_NAME` cookie value to be `"offline_#{victim_shop}"` (or `"#{victim_shop}_#{user_id}"` for a guessed/leaked online user id) and submit it to the app. The app calls `SessionUtils.current_session_id`/`cookie_session_id` exactly as documented, gets back the victim's real session id, and its session store (e.g. `shopify_app`'s reference implementation shown in this gem's own docs) returns the victim shop's `Session` object — including the live Admin API `access_token`. Compare to the analogous class explicitly called out: "a session id derived from unauthenticated bytes."

This is not a case of the host app "ignoring documented API" — it is the gem's own documented, recommended flow (`docs/getting_started.md`) that this vulnerability lives in.

### Impact Explanation
An unauthenticated user who can forge/set a cookie value (trivial from any browser, or via a related web vulnerability such as cookie injection on a shared parent domain) can obtain another merchant's stored `Session`, and thus perform Admin API calls under that merchant's `access_token` through the app. This is cross-tenant access and effectively theft/misuse of another merchant's access token — squarely within the "Critical" impact bucket (cross-tenant access, theft of merchant access token).

### Likelihood Explanation
Likelihood is elevated because:
- No cryptographic secret protects the cookie value; it is compared/used as-is.
- The session-id format is fully deterministic and documented in this very gem (`offline_#{shop}`, `#{shop}_#{user_id}`), so an attacker does not need to brute-force anything beyond the shop domain (public) and, for online sessions, the target's numeric Shopify user id (often obtainable/guessable, e.g. sequential IDs, or leaked via other channels).
- The vulnerable helper is the gem's officially recommended integration point for non-embedded apps, so most conforming integrations are exposed by construction, not by misuse.

### Recommendation
Do not trust the raw cookie value as a bare identity. Either (a) sign/HMAC the session-id cookie value with the app's `api_secret_key` (parallel to how `HmacValidator`/`JwtPayload` already protect OAuth callback and JWT session tokens elsewhere in this gem) and verify that signature in `cookie_session_id`/`current_session_id` before using it to look up a session, or (b) store an unguessable random session identifier (not derived from `shop`/`user_id`) at OAuth completion time and require that opaque value in the cookie, so that knowledge of a shop's domain or user id is insufficient to derive a valid session id.

### Proof of Concept
1. App A is a non-embedded Shopify app built with `shopify_api` following `docs/getting_started.md`'s documented cookie flow (`SessionUtils.current_session_id(nil, cookies, false)`).
2. Victim shop `victim-shop.myshopify.com` installs App A; OAuth completes and `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser cookie `SESSION_COOKIE_NAME` = `"offline_victim-shop.myshopify.com"` (see `oauth.rb` lines 100-112, `session_utils.rb` `offline_session_id`).
3. Attacker, an unauthenticated user, learns `victim-shop.myshopify.com` (public storefront domain) and, in their own browser/HTTP client, sets a cookie named identically to `SessionCookie::SESSION_COOKIE_NAME` with value `"offline_victim-shop.myshopify.com"`.
4. Attacker sends a request to App A's server. App A calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, attacker_cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim (`session_utils.rb` lines 19-37, 68-71) — no signature check occurs anywhere in this gem's code.
5. App A's session repository (per the gem's own documented pattern in `docs/usage/oauth.md` and `BREAKING_CHANGES_FOR_V16.md`) looks up the stored `Session` for that id and returns victim shop's `access_token`.
6. App A now performs Admin API calls (e.g., via `ShopifyAPI::Clients::Graphql::Admin`) using victim shop's session/`access_token` on behalf of the attacker's request — cross-tenant access and access-token misuse achieved with zero credentials from the attacker.
