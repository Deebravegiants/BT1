## Analysis

I traced the bug-class ("a field is trusted/acted on without being covered by the same integrity check that vouches for the rest of the payload — i.e., a slot/identity confusion between what's cryptographically bound and what's actually read") to the webhook processing pipeline. [1](#0-0) [2](#0-1) 

`Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` signs/verifies exclusively the body bytes. `Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never mixed into `to_signable_string`. [3](#0-2) 

`HmacValidator.validate` calls `compute_signature(verifiable_query.to_signable_string, secret)` — for webhooks that's HMAC(body) only. [4](#0-3) 

`Registry.process` gates on the HMAC check, then immediately trusts `request.shop` (the unauthenticated header) to build `WebhookMetadata` and dispatch it to the app's handler as the tenant identity for this event.

The identity binding broken here is:
`HMAC(secret, body) valid` ⇏ `shop header == shop that produced body`

Since the HMAC secret (`api_secret_key`) is one shared per-app secret across every merchant that installs the app (not per-tenant), any unprivileged user who installs the app on their own shop receives genuine `(body, hmac)` pairs for their own shop's events. Nothing in the library binds that hmac to the shop header, so a captured `(body, hmac)` pair can be replayed with an arbitrary `x-shopify-shop-domain` header, and `Registry.process` will accept it and route the attacker-controlled body into the target shop's tenant context.

### Title
Webhook HMAC only signs the request body, not the shop-domain header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC verified by `Registry.process` never covers the `shop-domain` header that is later trusted as the tenant identity for the webhook.

### Finding Description
`Registry.process` validates authenticity solely via `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` and compares it against the `hmac-sha256` header. `to_signable_string` returns `@raw_body` exclusively: [2](#0-1) 

Meanwhile `request.shop`, which is passed downstream as the authoritative merchant/tenant identity in `WebhookMetadata`, comes straight from a header that plays no role in the signature computation: [5](#0-4) [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs it, any unprivileged merchant who installs the app can trigger events on their own store, capture the resulting genuine `(raw_body, hmac)` pair, and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will still succeed because it only checks the body against the shared secret, and `Registry.process` will dispatch the attacker-controlled body to the app's handler tagged with the victim's shop identity — crossing the tenant boundary without ever needing the victim's credentials.

### Impact Explanation
This breaks tenant isolation for any application built on this gem's webhook registry: an attacker-controlled payload (e.g., a spoofed `orders/create`/`app/uninstalled` body) can be injected and processed as if it originated from a different, victim merchant, since the library does not bind the trusted shop identity to the cryptographic proof of authenticity. This falls under the Critical "cross-tenant access" category, since the identity used to route/attribute the webhook data is not part of the verified integrity check.

### Likelihood Explanation
Any unprivileged internet user who can install the app on their own store (a normal, low-privilege action) can capture a valid `(body, hmac)` pair from their own legitimate webhook traffic and replay it with a forged shop header — no access token, `client_secret`, or victim credentials are required.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signable string bound to the HMAC, or otherwise cryptographically bind `request.shop` to the verified payload before it is trusted as tenant identity in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g. `orders/create`) they control the body of.
2. Attacker captures the genuine request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and hmac `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds (body unchanged), `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` to the app's handler, causing attacker-controlled data to be processed under the victim's tenant identity.
