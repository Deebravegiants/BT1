## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook payloads - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`api_version`/`webhook_id`) values are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then trusts `request.shop` as the tenant identity handed to the app's handler, without any cross-check that the header-derived shop is bound to the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over `raw_body` only, per `HmacValidator.validate` calling `verifiable_query.to_signable_string`), and then unconditionally forwards `request.shop` to the app's webhook handler as the authoritative tenant identity: [3](#0-2) [4](#0-3) 

The equality that should hold is: `shop-domain header == shop bound inside the HMAC-signed bytes`. Instead, the code only proves `HMAC(raw_body, secret) == received_hmac`; it never proves that `shop-domain` is the shop the secret-holder (Shopify) actually associated with that body. Any entity capable of obtaining one genuine `(raw_body, hmac)` pair signed with the app's `api_secret_key`/`old_api_secret_key` — for example a merchant who has installed the app on their own store and thus legitimately receives real, correctly-signed webhook deliveries for that store — can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `WebhookMetadata` is built with the attacker-chosen `shop` value: [5](#0-4) 

This breaks the binding between "bytes verified" (raw body signed by Shopify) and "identity parsed" (shop header taken at face value), letting one tenant's legitimately-signed payload be relabeled and processed by the app under a different, arbitrary shop's identity.

### Impact Explanation
This is a cross-tenant identity-confusion vector inside the gem's own webhook processing path: the app-level handler receives `shop: <attacker-controlled>` alongside genuinely-signed body content, with no code path forcing correlation between the two. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up or update per-shop records), this can lead the app to associate/write attacker-supplied webhook data against a victim shop's records — a cross-tenant access impact, achievable by any party who can obtain one valid signed webhook (an unprivileged app-installer, not a privileged account).

### Likelihood Explanation
Obtaining one valid `(body, hmac)` pair only requires installing the app on any shop (the normal onboarding flow for a public app) and receiving one real webhook delivery — no access to `api_secret_key` or a merchant's access token is needed, only observation of network traffic to the app's own webhook endpoint (which is by design internet-reachable). Replaying it with a modified header is a simple HTTP request.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the HMAC-signed content, or otherwise cross-verify the `shop-domain` header against a value obtained through an authenticated channel (e.g., compare against the shop associated with the session/subscription that registered the webhook) before dispatching to handlers, rather than trusting the raw header value from `Request#shop`.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; capture a genuine webhook delivery — headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
2. Resend the identical body `B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`B`) and succeeds, since the header substitution never touches the signed bytes.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)`, i.e., attacker-controlled data processed under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
