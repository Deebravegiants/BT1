### Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain` header to identify the tenant that the webhook belongs to. Because the HMAC never binds the `shop` value, any holder of one validly-signed webhook body/HMAC pair (e.g. a merchant who legitimately installed the app on their own store and received a real webhook) can replay that exact body with the `shop-domain` header changed to a different merchant's shop domain, and the gem will accept it as authentic and dispatch it to the app's handler tagged with the attacker-chosen shop.

### Finding Description
`Registry.process` performs the authentication check like this: [1](#0-0) 

The only integrity check is `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

`to_signable_string` returns only `@raw_body` — the `shop-domain` header used to fill `request.shop` (and subsequently `WebhookMetadata#shop` passed to the app's handler) is never part of the signed material: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`HMAC-covered-bytes == bytes that determine which tenant (shop) the payload is attributed to`

Here that equality is broken: the HMAC covers `raw_body` only, while `request.shop` (derived from an unauthenticated header) is what the library hands to `handler.handle` for tenant attribution. `test/webhooks/registry_test.rb` confirms `data.shop` is populated straight from the `x-shopify-shop-domain` header with no cross-check against the signed payload: [5](#0-4) 

### Impact Explanation
An unprivileged actor who can obtain any single legitimately-signed webhook (trivial for anyone who installs the app on their own store, since Shopify sends real webhooks to the app for every shop that installs it, and the HMAC secret is the same app-wide `client_secret` shared across all tenants) can take that body+HMAC pair and resubmit it with an arbitrary victim `shop-domain` header. `Registry.process` will validate the HMAC (it only checks the body) and invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain. Any app that uses `shop` from `WebhookMetadata` to look up/update per-tenant records (the intended and documented usage pattern) will process/store data under the wrong tenant — a cross-tenant data integrity/confusion issue reachable without any credentials belonging to the victim.

### Likelihood Explanation
Likelihood is high for apps that accept webhooks from any shop that can install them (public app listings): obtaining one genuine signed webhook body requires only installing the app on an attacker-controlled/dev store, which is available to any internet user, not a privileged action. Swapping the header and replaying is trivial HTTP manipulation.

### Recommendation
Bind the tenant identity into the signed material actually verified by the gem, or explicitly document/enforce that callers must independently authenticate the `shop` value (e.g., verify it against a known-installed shop list) before trusting `WebhookMetadata#shop`. At minimum, `HmacValidator`/`Request#to_signable_string` should incorporate the `shop-domain` header into the signable string so the HMAC cryptographically binds body-to-shop, preventing header substitution replay across tenants.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (permitted — any Shopify Partner/dev store).
2. Attacker triggers a real event and receives a legitimately signed webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical `B`/`H` to the app's webhook endpoint but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload content actually originated from `attacker-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`).

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
