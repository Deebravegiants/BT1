### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant spoofing during `Registry.process` - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook only by checking `Utils::HmacValidator.validate(request)`, which HMAC-signs solely the raw request body [1](#0-0) . The `shop` value that is handed to the application's webhook handler as the tenant identifier is read directly from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material [2](#0-1) . Because the app's `api_secret_key` (used to compute the HMAC) is a single secret shared across *all* shops that install the app, the HMAC only proves "this body was signed with our app secret" — it proves nothing about which shop the event belongs to.

### Finding Description
`Registry.process` performs exactly one check before dispatching to the handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field via `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is decoded from the `hmac-sha256` header [5](#0-4) .

Crucially, `shop` is read straight from the `shop-domain` header, entirely outside the signed data [2](#0-1) , and the constructor only checks that the header is *present*, not that it is consistent with anything cryptographically bound to the payload [6](#0-5) .

**Equality that should hold but doesn't:** `shop (used for tenant routing/business logic) == shop (bound by the HMAC signature)`. In this gem, the left side is attacker-controlled header data and the right side doesn't exist at all — the HMAC binds only the body bytes, never the shop identity.

Because the app's secret is shared across every merchant installation of the app (it is not a per-shop secret), any party who can obtain one valid `(body, hmac)` pair signed with the app's secret — for example by installing the app on their own free/dev store and capturing the webhook their own store legitimately receives — can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and `x-shopify-topic`/`x-shopify-webhook-id` headers, also unsigned) to name a victim shop. `HmacValidator.validate` still returns `true` because the body and secret are unchanged; `Registry.process` then calls the handler with `shop: <victim-shop>` and attacker-chosen `body`.

### Impact Explanation
This breaks the tenant/identity boundary that host applications rely on `ShopifyAPI::Webhooks::Registry.process` to enforce. Any host application that uses `data.shop` (from `WebhookMetadata`) to select which merchant's records to create/update/delete — which is the documented and expected usage pattern — can be made to apply attacker-supplied webhook payloads (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, etc.) against a shop the attacker does not control, using only a webhook capture from a shop the attacker *does* control (their own trial/dev store, requiring no privileged credentials, no access token, and no knowledge of `api_secret_key`). This is a cross-tenant access primitive per the accepted-impact criteria (data can be attributed to/injected into another merchant's tenant scope).

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on any store the attacker controls (a free/dev store, which is trivial and requires no special privilege), (2) capturing one legitimately delivered webhook `(raw_body, hmac header)` pair for that store, and (3) replaying it to the app's public webhook HTTP endpoint with a rewritten `shop-domain` (and desired `topic`) header. No secrets, tokens, or elevated access are required, making this reachable by any unprivileged internet user who can install the target app once.

### Recommendation
Do not trust `request.shop` (or `topic`/`webhook_id`) as authenticated data derived purely from HMAC validation of the body. At minimum:
- Require host applications to independently verify that the `shop` domain in the webhook matches a shop for which they hold an active session/installation record before acting on the payload (document this requirement prominently), and/or
- Extend `Webhooks::Request#to_signable_string` (or add a secondary check) to bind the `shop-domain`, `topic`, and `webhook-id` headers into the value being verified, so a replayed body cannot be reattributed to a different shop, and/or
- Track/require idempotency using `webhook_id` scoped per-shop combined with a nonce/replay cache, since HMAC alone provides no freshness or shop-binding guarantee given the secret is shared across all installations of the app.

### Proof of Concept
```ruby
# Step 1: Attacker installs the target app on their own store "attacker.myshopify.com"
# and captures one legitimately delivered webhook, e.g. for "orders/create":
raw_body = '{"id":1,"note":"legit content from attacker store"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Step 2: Attacker replays the SAME body+hmac to the app's public webhook endpoint,
# but rewrites the shop-domain header to a victim shop they do not control.
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac,          # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Step 3: The library accepts it because HmacValidator only checks raw_body vs secret.
ShopifyAPI::Webhooks::Registry.process(forged_request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...attacker content...}, ...))
```
`Registry.process` raises `Errors::InvalidWebhookError` only if the HMAC over the body is wrong [7](#0-6) ; it never checks that `shop` is consistent with anything cryptographically verified, so the forged request above passes and the handler is invoked with the victim shop's identity attached to attacker-controlled content.
