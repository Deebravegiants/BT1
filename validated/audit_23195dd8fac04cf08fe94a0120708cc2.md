Audit Report

## Title
Sender's HRMP channel deposit is never unreserved when the counterpart para is offboarded before `process_hrmp_open_channel_requests` runs - (File: polkadot/runtime/parachains/src/hrmp.rs)

## Summary
`Pallet::process_hrmp_open_channel_requests` removes a confirmed `HrmpOpenChannelRequest` and its bookkeeping entries unconditionally, but only creates the actual `HrmpChannels` entry if `paras::Pallet::<T>::is_valid_para` returns `true` for both the sender and recipient. If either para is offboarded (lifecycle flips immediately, ahead of actual purge at the following session boundary) between confirmation and processing, the request is deleted with no channel created and no unreserve of the `sender_deposit` (or recipient deposit), permanently locking the reserved funds.

## Finding Description
`hrmp_init_open_channel` reserves `config.hrmp_sender_deposit` from the sender para's sovereign account and stores it as `sender_deposit` in a new `HrmpOpenChannelRequest`, pushing the channel id into `HrmpOpenChannelRequestsList`. `hrmp_accept_open_channel` marks the request confirmed and reserves the recipient's deposit. These are ordinary unprivileged parachain-origin extrinsics reachable via `ensure_parachain`. At the next session boundary, `process_hrmp_open_channel_requests` iterates confirmed requests and only inserts into `HrmpChannels` when `is_valid_para` holds for both sides; if not, the surrounding request-removal and counter-decrement logic still executes, but no compensating `T::Currency::unreserve` call exists for the skipped branch — the deposit becomes stuck against a sovereign account with no remaining on-chain record connecting it to a live channel or a cancellable request.

## Impact Explanation
This results in a permanent, silent lock of the sender parachain's reserved balance: the funds remain reserved indefinitely, are not usable, and are not backed by a channel or a request that could otherwise be cancelled to trigger a refund. This breaks the invariant that HRMP deposits are always either applied to a live channel or returned to their owner, representing a concrete fund-loss condition for the affected parachain's sovereign account.

## Likelihood Explanation
Triggering this requires two paras to open and confirm a channel and then one of them to be scheduled for offboarding (a normal, unprivileged lifecycle event such as lease expiry or manager-initiated deregistration) before the next session-change hook processes the pending queue. Both preconditions are ordinary protocol operations, not admin-only or attacker-privileged actions, and the timing window is deterministic and reproducible in a controlled test by sequencing the offboarding call before the session-change hook.

## Recommendation
In the `is_valid_para` failure branch of `process_hrmp_open_channel_requests`, explicitly unreserve `request.sender_deposit` from the sender's sovereign account (and the recipient's deposit if reserved) before removing the `HrmpOpenChannelRequests` entry, mirroring the refund logic already used in `hrmp_close_channel`/`hrmp_cancel_open_request`.

## Proof of Concept
1. Onboard two paras `SENDER` and `RECIPIENT`; call `Hrmp::hrmp_init_open_channel` and `Hrmp::hrmp_accept_open_channel` to create and confirm a channel request, reserving `sender_deposit` from `SENDER`'s sovereign account.
2. Before the next session-change hook runs, schedule `RECIPIENT` (or `SENDER`) for offboarding via the normal deregistration path so `paras::Pallet::<Test>::is_valid_para` returns `false` for it.
3. Run the initializer session-change logic that invokes `Hrmp::process_hrmp_open_channel_requests`.
4. Assert `HrmpChannels::<Test>::get(&channel_id).is_none()`, `HrmpOpenChannelRequests::<Test>::get(&channel_id).is_none()`, and `Balances::reserved_balance(sender_sovereign_account)` is unchanged (still equal to `sender_deposit`) instead of returning to `0`, demonstrating the deposit is permanently stuck rather than unreserved.
