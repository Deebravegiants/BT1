## Title
Batched message delivery reverts entirely when one message becomes stale (already-delivered/duplicate/expired), delaying all other valid messages in the batch - ([File: modules/pallets/ismp/src/impls.rs], [File: evm/src/core/HandlerV2.sol])

### Summary
Both the Substrate pallet-ismp path (`handle_unsigned` → `Pallet::execute`) and the EVM `HandlerV2.batchCall` path deliver multiple ISMP messages atomically in a single transaction/extrinsic. If any single message in the batch fails a per-message precondition check (e.g. it was already delivered by a competing relayer, has since timed out, or a duplicate receipt now exists), the entire batch reverts, causing every other still-valid message bundled with it to be delayed rather than delivered.

### Finding Description
On Substrate, `handle_unsigned` is marked `#[frame_support::transactional]` and calls `Self::execute(messages.clone())`, which maps `handle_incoming_message` over every message and immediately short-circuits with `.collect::<Result<Vec<_>, _>>()?` the moment any one message errors: [1](#0-0) [2](#0-1) 

Because the whole call is `transactional`, a single stale item (e.g. `Error::DuplicateRequest`/`DuplicateResponse` because another relayer already delivered that particular request/response between when this relayer built its batch off-chain and when its extrinsic landed on-chain) causes the entire extrinsic — and therefore delivery of every other, still-timely and still-valid message batched alongside it — to revert. This mirrors the Notional pattern precisely: state used to build the payload (`checkRebalance`'s view of unhealthy currencies` / the relayer's view of undelivered messages) can change by the time the transaction executes, and the on-chain code enforces an all-or-nothing check instead of skipping the now-invalid item.

On the EVM side, `IHandlerV2.batchCall` has the identical atomicity property by design: [3](#0-2) 

and the relayer explicitly batches consensus updates together with POST requests / GET responses into a single `batchCall` transaction for gas efficiency: [4](#0-3) 

If a competing relayer delivers one of the bundled requests first (`DuplicateMessage`), or a bundled request's `timeout()` elapses by the time the transaction is mined (`MessageTimedOut`), `handlePostRequests`/`handleGetResponses` reverts: [5](#0-4) 

and via `batchCall`'s delegatecall-and-revert-on-failure semantics, the whole transaction — including any still-valid consensus update and any other still-deliverable requests/responses in the same batch — reverts.

### Impact Explanation
A single stale/racing item forces the reverting relayer to detect the failure, rebuild the batch excluding the stale message, and resubmit. Every legitimate message that happened to be bundled with the stale one is delayed until the next successful attempt. Because Hyperbridge relies on timely delivery for cross-chain intents, token bridging, and consensus-dependent state proofs, repeated occurrences of this race (multiple relayers racing to deliver the same request/response, or timeouts elapsing mid-flight) systematically delays message delivery across all applications sharing that batch, which can cascade into missed timeouts for otherwise-deliverable requests and stalled cross-chain settlement — a direct parallel to the "route unable to deliver messages" impact class.

### Likelihood Explanation
Multiple independent relayers competing to deliver the same proven message set is an expected, permissionless, and routine occurrence in Hyperbridge's design (any actor can call `handleConsensus`/`handlePostRequests`/`handleGetResponses`/`handle_unsigned`), and message timeouts are a normal part of protocol operation. Given typical mempool latency and multi-relayer competition, hitting this race is a matter of when, not if, whenever more than one message is intentionally batched together — which the relayer code does by default to save gas.

### Recommendation
Do not let a single stale/racing message abort the whole batch. On the Substrate side, process each message independently inside `Pallet::execute` (collect per-message success/failure rather than short-circuiting on the first error) so still-valid messages are delivered and only the stale one is skipped/reported. On the EVM side, consider making `batchCall` (or a variant of it) tolerant of individual call failures — e.g., catching and logging failures for known "already delivered"/"timed out" conditions per call instead of reverting the entire batch — or have the relayer defensively re-check each message's still-valid status immediately before submission and drop any that raced, rather than relying solely on atomic all-or-nothing execution.

### Proof of Concept
1. Relayer A and Relayer B both observe requests `[R1, R2, R3]` as deliverable and independently build batches `handle_unsigned([Consensus, R1, R2, R3])` (or `batchCall([handleConsensus, handlePostRequests{R1,R2,R3}])`).
2. Relayer A's transaction lands first, delivering `R1, R2, R3`.
3. Relayer B's transaction executes next; `handle_incoming_message`/`handlePostRequests` hits `DuplicateRequest`/`DuplicateMessage` on `R1` (already delivered) inside the loop.
4. Because `execute` short-circuits via `.collect::<Result<_,_>>()?` under `#[transactional]` (Substrate), or `batchCall`'s delegatecall-revert-on-failure (EVM), the entire transaction reverts — even though `R2` and `R3` alone would have been redundant no-ops but any other *not-yet-delivered, still valid* message bundled by Relayer B alongside `R1` (e.g., a fresh consensus update or an unrelated request) is also discarded and must be resubmitted, delaying its delivery.

		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))

    /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }
