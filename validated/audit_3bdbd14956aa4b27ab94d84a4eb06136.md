Audit Report

## Title
`ERC20Transactor` credits full nominal amount to XCM holding without verifying actual balance change on the checking/beneficiary account, enabling fee-on-transfer / deflationary ERC20 tokens to mint phantom XCM asset credit - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke an arbitrary ERC20 contract's `transfer()` and treat the operation as fully successful based solely on the boolean return value, without checking the actual balance delta on the receiving account. [1](#0-0)  A fee-on-transfer/deflationary ERC20 contract that still returns `true` but delivers less than the nominal `value` causes the transactor to credit the full nominal `amount` into `AssetsInHolding` while the checking account (or beneficiary) actually received less.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` to move `amount` from the user to the `TransfersCheckingAccount`, and upon `abi_decode_returns_validate` returning `true`, unconditionally constructs `Erc20Credit(amount)` — the full requested nominal amount — into the XCM holding register: [2](#0-1)  No pre/post balance check on `TransfersCheckingAccount` is performed. The symmetric `deposit_asset_with_surplus` has the same structure for the checking-account-to-beneficiary transfer, also relying only on the boolean return value. [3](#0-2) 

Critically, the asset identifier used by this transactor is matched via `ERC20Matcher`, which is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, where `IsLocalAccountKey20` matches *any* local location containing an `AccountKey20` junction — there is no allowlist, registry, or governance check restricting which contract addresses can be used as ERC20 asset kinds. [4](#0-3)  Since `pallet-revive` allows permissionless contract deployment, an unprivileged user can deploy a custom fee-on-transfer ERC20 and use its address directly as the XCM `AssetId` in a withdraw/deposit sequence, with no privileged registration step required to trigger the vulnerable code path.

The transactor is wired live into Asset Hub Westend's `AssetTransactors` tuple. [5](#0-4) 

The only existing checks are `did_revert()` and the ABI-decoded boolean return value — both insufficient against a compliant-looking ERC20 that returns `true` while transferring less than `value` (a legal and common real-world ERC20 pattern).

## Impact Explanation
Each `withdraw_asset` call against a fee-on-transfer/deflationary ERC20 asset kind causes the XCM holding register to be credited with more value than is actually received by `TransfersCheckingAccount`. This phantom credit is fully fungible within the XCM executor (depositable to any beneficiary, usable in reserve transfers), while the checking account's real ERC20 balance under-accrues relative to the aggregate outstanding claims against it. Repeated exploitation can eventually cause the checking account to be unable to cover legitimate `deposit_asset` calls for that asset kind, causing transfer failures for other holders of the same asset. Because the asset kind itself is attacker-deployed and attacker-controlled, the "victims" are limited to other users who choose to hold/use that same malicious asset kind — the checking account's shortfall is scoped per-ERC20-contract, not a chain-wide fund-draining bug against unrelated assets.

## Likelihood Explanation
Likelihood is realistic: no privileged role or governance action is required. An attacker can deploy an arbitrary `pallet-revive` contract implementing a superficially-compliant `IERC20` interface with fee-on-transfer logic, and immediately reference its address as an `AccountKey20` XCM asset via `ERC20Matcher`, which imposes no allowlisting. [6](#0-5)  The exploit is repeatable and requires only crafting the malicious token and submitting ordinary `WithdrawAsset`/`DepositAsset` XCM instructions.

## Recommendation
Do not rely solely on the ERC20 `transfer()` boolean return value. In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the receiving account's ERC20 balance immediately before and after the `bare_call`, and credit/rely on the actually observed balance delta rather than the requested nominal `amount`; if the delta is less than requested, fail the operation (safest) or credit only the actually-received amount into `AssetsInHolding`.

## Proof of Concept
1. Deploy a fee-on-transfer `IERC20`-compliant contract via `pallet-revive` where `transfer()` deducts a percentage but still returns `true`.
2. Reference the deployed contract's address as an `AccountKey20` XCM asset location (no registration needed since `ERC20Matcher`/`IsLocalAccountKey20` accepts any such location).
3. Submit an XCM program: `WithdrawAsset { <malicious-erc20>, amount: 1000 }` from the attacker's account, followed by `DepositAsset` to a second attacker-controlled account.
4. Observe `withdraw_asset_with_surplus` credits `Erc20Credit(1000)` into holding at [7](#0-6)  even though `TransfersCheckingAccount`'s real balance increased by less than 1000.
5. Repeat to demonstrate the checking account's real balance falling behind the aggregate XCM-registered claims for that asset kind, eventually causing `deposit_asset_with_surplus` to fail with `"ERC20 contract transfer failed"` for other holders of the same asset kind.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
