Duplicate same-asset withdrawals in a single batch cause the POA bridge's `describeWithdrawal` to misreport an unrelated withdrawal's status/hash to the caller. This is analogous to the `AuctionParticipant` bug in that a client-controlled input (repeated identical entries in a batch) collides with an internal index-free lookup, producing wrong results attributed to the wrong logical item.

### Title
POA Bridge `describeWithdrawal` misattributes status/txHash for duplicate-asset batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` matches the POA bridge API's withdrawal list to a specific `WithdrawalIdentifier` using **only `assetId`**, ignoring the `index` field that is supposed to disambiguate multiple withdrawals in the same transaction. [1](#0-0) [2](#0-1) 

### Finding Description
`createWithdrawalIdentifiers` assigns a per-bridge `index` to each withdrawal in a batch, intended to let each bridge's `describeWithdrawal` pick out the correct entry when multiple withdrawals of the same route are packed into one NEAR transaction. [3](#0-2) 

However, `PoaBridge.describeWithdrawal` never uses `args.index`. It calls `findMatchingWithdrawal`, which just does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — the **first** entry in the (explicitly documented as unsorted) API response list whose token matches, regardless of which logical withdrawal (index) is being queried. [4](#0-3) 

`signAndSendWithdrawalIntent` performs no validation preventing two withdrawals of the same `assetId` (e.g., to two different destination addresses) within a single batch/tx — it simply builds intents for each entry in the array. [5](#0-4) 

So, if a caller submits a batch withdrawal with two entries for the same asset (different destination addresses/amounts), both resulting `WithdrawalIdentifier`s (`index: 0` and `index: 1`) share the same `assetId`. When both are watched via `watchWithdrawal`, `describeWithdrawal` for **both** indices resolves to the **same** first-matching API record. The equality that should hold — "the status/txHash returned for withdrawal `i` reflects the on-chain outcome of withdrawal `i`" — is broken: the second withdrawal's watcher will report the first withdrawal's `COMPLETED` status and `transfer_tx_hash` even though the second withdrawal may still be pending, failed, or landed with a different hash/destination. [6](#0-5) 

The code comment acknowledges the limitation but frames it only as "not supported," not as a security-relevant misreport that a caller can trigger unprivileged. [7](#0-6) 

### Impact Explanation
An integrator (exchange, custodian, or any system using `sdk.createWithdrawalCompletionPromises`/`watchWithdrawal` to decide when to mark a withdrawal complete and release corresponding internal credit) can be made to believe a second, distinct withdrawal completed with a specific destination/tx hash when in fact only the first did. This matches the High-severity criterion "a status or hash misreport making an integrator credit or refund twice": the integrator could credit/settle the second withdrawal based on the first withdrawal's completion, while the second withdrawal's actual funds movement is untracked, misreported, or still pending — with no way for the SDK to later correct the mismatch since `findMatchingWithdrawal` has no index awareness at all.

### Likelihood Explanation
This requires no privileged access — any user of the SDK can construct a batch withdrawal (`signAndSendWithdrawalIntent` with `WithdrawalParams[]`) containing two POA-routed withdrawals of the same `assetId` in one NEAR transaction, which the SDK does not reject. Batch withdrawals are a first-class, documented feature; nothing prevents duplicate assets from being combined.

### Recommendation
Make `PoaBridge.describeWithdrawal` disambiguate using more than `assetId` — e.g., match by `(assetId, destinationAddress, amount)` tuple, or by relative ordering/index once the POA API supports positional correlation (as the existing comment suggests). Until the API supports strict per-index correlation, the SDK should either reject/warn on batches with duplicate `assetId` for the POA route, or explicitly document and surface an error/ambiguous status instead of silently returning a matched-but-wrong withdrawal's status.

### Proof of Concept
1. Caller invokes `sdk.signAndSendWithdrawalIntent` with a batch `withdrawalParams` array containing two entries for the same POA-bridged `assetId` (e.g., `nep141:usdc.omft.near`) but different `destinationAddress`/`amount`, both routed via `RouteEnum.PoaBridge`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals of the same bridge route. [8](#0-7) 
3. Caller watches both via `watchWithdrawal`, each calling `PoaBridge.describeWithdrawal` with its own `WithdrawalIdentifier`.
4. The POA bridge API returns the withdrawals list for the tx hash (unsorted); `findMatchingWithdrawal` picks the first entry whose token matches `assetId` for **both** calls. [9](#0-8) 
5. Once the first withdrawal's API record reaches `COMPLETED`, both watchers resolve `{ status: "completed", txHash: <first withdrawal's hash> }`, even if the second withdrawal is still `PENDING` or failed — an integrator relying on this resolved promise would incorrectly treat the second withdrawal as settled to that hash.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
