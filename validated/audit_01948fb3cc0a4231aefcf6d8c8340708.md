### Title
Unswept residual balances in the shared `CallDispatcher` can be credited as attacker escrow via balance-diff accounting in `placeOrder` - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
The Swapos exploit succeeded because the AMM's `swap()` function trusted a balance figure that could be inflated by means unrelated to the caller's actual contribution, and used that balance directly to satisfy its invariant check, letting the attacker withdraw far more value than deposited. `IntentGatewayV2.placeOrder`'s predispatch/escrow path in Hyperbridge has the same root-cause shape: it credits escrow based on the *entire* observed balance swept from a shared, address-known helper contract (`CallDispatcher`) rather than an amount cryptographically or contextually tied to the placing user's own deposit in that transaction.

### Finding Description
When an order carries `predispatch.call`, `placeOrder` executes the following balance-diff pattern: [1](#0-0) 

- The attacker-controlled `order.predispatch.call` is dispatched through `ICallDispatcher(dispatcher).dispatch(...)` [2](#0-1) , executed with the `CallDispatcher` itself as `msg.sender`, per `CallDispatcher.dispatch` which simply loops over attacker-decoded `Call[]` and executes each with no allowlist or per-order isolation: [3](#0-2) .
- The sweep step then reads `balance = IERC20(token).balanceOf(dispatcher)` — the dispatcher's **total** balance, not a per-order tracked amount — and only requires `balance >= requiredAmount` before sweeping the *whole* balance to the gateway: [4](#0-3) .
- `received` is then computed purely from the gateway's own balance delta and, when `received <= requiredAmount`, is credited verbatim as the order's escrowed input: [5](#0-4) .

Because `CallDispatcher` is a single, publicly documented, shared contract used by *every* `placeOrder` predispatch flow and every order's postdispatch `_execute` flow across the whole gateway (and across `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain calldata as well), any token balance that lands on it and is not fully accounted for by the caller who caused it becomes available to the *next* caller who declares an order with a matching input token. The postdispatch sweep in `_execute` only iterates over the order's own declared `output.assets`, so any token balance an attacker-crafted `output.call` routes into an *undeclared* token is left stranded on the dispatcher, uncollected as dust: [6](#0-5) 

A user placing a later order can then supply a no-op `predispatch.call` (satisfying only the "target must be a contract" check in `CallDispatcher.dispatch`) and declare `order.inputs[i]` for that stranded token; the balance-diff logic will treat the dispatcher's pre-existing balance as "received" for their own order and escrow it, without contributing an equivalent real transfer of their own for that leg.

The exact same escrow-from-shared-balance pattern also exists, with the same lack of provenance checks, in the Tron variant of the contract: [7](#0-6) .

### Impact Explanation
An attacker able to engineer or observe a token balance left on the `CallDispatcher` (via a crafted `output.call`/`predispatch.call` from any order, including their own prior transaction, or a direct token donation to the well-known dispatcher address) can have that value credited into a fresh order's escrow for free. Escrowed balances are later paid out to solvers on fill or refunded to the order creator on cancellation, so this converts unaccounted dispatcher balance into a claim redeemable for real, backed tokens — a form of unbacked mint/theft of funds that belong to the protocol (dust) or to other users whose predispatch/postdispatch flows left stray balances.

### Likelihood Explanation
Reaching this path only requires an unprivileged user calling `placeOrder` with an attacker-chosen `predispatch.call`/`output.call`, which is the intended, permissionless "swap-then-escrow" and "fill-then-act" composability feature of the gateway — no special privileges or governance action are needed. The harder part to fully verify without further code tracing is guaranteeing a *concrete, repeatable* source of stranded dispatcher balance (e.g., a specific fee-on-transfer/multi-hop DEX interaction, or a token whose `output.assets` declaration an attacker can under-declare relative to what their own `output.call` actually receives) — this requires deeper tracing of realistic `output.call`/`predispatch.call` payloads than I could complete in this pass.

### Recommendation
Track and verify amounts per-order rather than trusting the dispatcher's raw balance: transfer exactly the amount the predispatch/postdispatch call is expected to produce (or snapshot the dispatcher's balance for that token *before* the user's own deposit and only sweep the incremental delta caused by the current call), and sweep *all* tokens the dispatcher could plausibly hold after arbitrary calldata execution — not just the order's declared output/input tokens — back to a protocol-owned dust account immediately, so no balance can persist on the shared dispatcher between transactions for a later caller to claim.

### Proof of Concept
Not independently reproduced on a fork; the report is based on static analysis of `evm/src/apps/IntentGatewayV2.sol` (lines 258–311), `evm/src/apps/intentsv2/IntentsBase.sol` (`_execute`, lines 498–533), and `evm/src/utils/CallDispatcher.sol`. A full PoC would need to (1) place an order whose `output.call` routes solver funds into a token not listed in `order.output.assets`, leaving it stranded on `CallDispatcher`, then (2) place a second order declaring that stranded token as an input with a no-op `predispatch.call`, and observe escrow credited without an equivalent fresh deposit for that leg.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
