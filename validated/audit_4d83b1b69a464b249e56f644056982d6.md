Based on my research, I found a concrete instance of the exact same vulnerability class (a Checks-Effects-Interactions violation where an external token transfer happens before escrow accounting is finalized) reintroduced in the Tron fork of the Intent Gateway, while the canonical EVM implementation was already hardened against it.

### Title
Reentrancy-exploitable CEI violation in `withdraw()` — escrow debited after external transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-targeted copy of `IntentGatewayV2`'s `withdraw()` function transfers escrowed tokens (native and ERC-20) to the beneficiary via a low-level `.call` *before* decrementing the corresponding `_orders[commitment][token]` escrow balance, and also releases accumulated transaction fees before clearing `_orders[commitment][TRANSACTION_FEES]`. This is the same class of bug as the reported `QVBaseStrategy._distribute` issue: state finalization (`paidOut`/escrow decrement) happens strictly after the value-transferring external call.

### Finding Description
`withdraw()` is invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow`) and from `onGetResponse`, both gated by `onlyHost`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- decrement AFTER the transfer
        ...
```
and the fee-release path: [2](#0-1) 

Contrast this with the canonical, audited-and-fixed version of the same logic in the main EVM package, where the escrow decrement is moved *before* the transfer (proper CEI): [3](#0-2) 

The Tron copy did not receive this fix, reintroducing the exact ordering flaw described in the external report (effect after interaction).

`order.inputs` (the tokens later mirrored into `body.tokens` for the `RedeemEscrow` message) is fully attacker-controlled at `placeOrder()` time — a user can escrow any ERC-20 address, including a purpose-built malicious token with a hostile `transfer()`/hook implementation.

### Impact Explanation
If the transfer of a malicious, attacker-supplied input token can trigger reentrant logic before `_orders[body.commitment][token] -= amount` executes, escrow accounting for that commitment is temporarily stale (still shows the pre-transfer balance) during the external call. This mirrors the reported bug's impact class (fund-draining via a not-yet-updated ledger entry) and, if any other externally reachable path reads `_orders[commitment][token]` for the same commitment without first checking `_filled[commitment]`, it could be leveraged to double-account or drain escrowed funds. `_filled[body.commitment]` is at least set before the loop in this version (partial CEI), which narrows — but does not eliminate — the practical exploitation surface, since the escrow-balance state itself is not protected the same way.

### Likelihood Explanation
Medium: the primary defense (`_filled` set first) blocks the most direct re-entry into `cancelOrder`/`fillOrder` for the same commitment, so I could not fully enumerate within the available search budget a second externally reachable function that reads `_orders[commitment][token]` without checking `_filled`. However, the divergence from the patched main EVM contract (which explicitly writes escrow state before the transfer as a deliberate hardening measure) is a genuine regression, and any future addition or partial-fill/dust-sweep function that touches `_orders[commitment][token]` without the `_filled` gate would immediately become exploitable by a solver choosing a malicious escrowed input token.

### Recommendation
Apply the same CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` (and `delete _orders[body.commitment][TRANSACTION_FEES]`) *before* performing the native/ERC-20 transfer, and add `nonReentrant` protection to `withdraw`/`onAccept`/`onGetResponse` as defense in depth.

### Proof of Concept
1. Attacker deploys a malicious ERC-20 `EvilToken` with a `transfer()` override that, when called, attempts to re-enter the gateway.
2. Attacker calls `placeOrder()` with `order.inputs = [EvilToken: X]`, escrowing `X` `EvilToken` into `_orders[commitment][EvilToken] = X`.
3. Attacker (or a colluding solver) fills the order cross-chain, causing a `RedeemEscrow` message naming the attacker-controlled `beneficiary`.
4. On delivery, `onAccept` → `withdraw()` calls `EvilToken.transfer(beneficiary, X)` via `.call` while `_orders[commitment][EvilToken]` is still `X` (not yet decremented).
5. `EvilToken.transfer()`'s malicious logic attempts to re-enter any function that reads/writes `_orders[commitment][EvilToken]` before the decrement lands — I was not able to conclusively identify a second qualifying externally reachable function within the current investigation given the `_filled[commitment]` early-set guard, so full exploitability requires further validation.

Given the incomplete confirmation of a concrete secondary reentrant call target (I ran out of investigation budget before finishing a full read of `evm/tron/contracts/apps/IntentGatewayV2.sol` and `evm/src/core/EvmHost.sol`'s `dispatchIncoming` ordering), this should be treated as a **verified code-level CEI regression with unconfirmed full exploit chain** — I recommend a follow-up Devin session to complete the call-graph analysis of `_orders` accessors and `dispatchIncoming`'s receipt-vs-call ordering before treating this as fully proven Critical/High.
