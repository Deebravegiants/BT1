### Title
PoA Bridge withdrawal-status matching keyed only on `assetId` misattributes completion hash/status across batched same-asset withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
Both `PoaBridge.describeWithdrawal()` and `waitForWithdrawalCompletion()` resolve a withdrawal's on-chain outcome by matching the bridge's response array to the caller's withdrawal solely by `nep141:${near_token_id} === assetId`. The SDK explicitly supports submitting multiple withdrawals (potentially of the same asset, to different `destinationAddress`es) in a single batched intent/transaction via `processWithdrawal({ withdrawalParams: WithdrawalParams[] })`. When two or more withdrawals in the same NEAR transaction share an `assetId`, the matching function returns whichever entry the bridge API lists first, regardless of destination, amount, or index — breaking the equality between "the withdrawal record I'm querying" and "the withdrawal record I actually own."

### Finding Description
`findMatchingWithdrawal` in both:
- `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` lines 418-427
- `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` lines 144-153

uses `.find((w) => nep141:${w.data.near_token_id} === assetId)`. Neither `index` (batch position), `destinationAddress`, nor `amount` are part of the matching criteria, even though `WithdrawalIdentifier` carries `index` and `withdrawalParams` (which includes `destinationAddress`/`amount`) [1](#0-0) , and `createWithdrawalIdentifier` explicitly comments "Response list is unsorted, so we match by assetId instead of index" [2](#0-1) .

The code's own comment acknowledges the gap: "Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) , and the identical caveat appears in the internal-utils copy [4](#0-3) .

However, the SDK's public API actively encourages exactly this unsupported scenario: `processWithdrawal` and `sdk.ts`'s batch machinery accept `WithdrawalParams[]` and create one `ft_withdraw` intent per entry in a single NEAR transaction [5](#0-4) , and the README documents "Batch Withdrawals" as a first-class feature without warning against same-asset batches [6](#0-5) . Nothing in `createWithdrawalIntents`/`processWithdrawal` validates or rejects batches containing duplicate `assetId`s routed through the PoA bridge.

This is directly analogous to the referenced Teller `getLoanLender` bug: a stored/looked-up value (`bid.lender` / here, "the withdrawal entry for my txHash+assetId") is resolved via an incomplete equality check (`== lenderManager` / here, `assetId` only) that silently returns another party's record when more than one entity satisfies that partial key.

### Impact Explanation
When a batch contains ≥2 withdrawals with the same PoA-bridge `assetId` (e.g., two USDT withdrawals to different destination addresses in one intent), `describeWithdrawal`/`waitForWithdrawalCompletion` can report the **wrong `txHash`** for a given index — i.e., report withdrawal #0 as completed using withdrawal #1's destination transaction hash, or vice versa. An integrator relying on this status to confirm settlement, release custody, or credit a user's off-chain ledger could:
- Credit/confirm the wrong destination transaction to the wrong batch leg (double credit / wrong receipt attribution), matching the rubric's "status or hash misreport making an integrator credit or refund twice."
- In the worst case, treat a still-pending leg as completed (using the sibling's hash), or treat a genuinely completed leg as unmatched/pending.

This does not misroute on-chain funds directly (the bridge itself still sends tokens to the correct destination address), but it corrupts the SDK's authoritative status/hash reporting for downstream consumers who trust `describeWithdrawal`/`waitForWithdrawalCompletion` as the source of truth for "which destination tx corresponds to which withdrawal leg."

### Likelihood Explanation
Likelihood is moderate: it requires (a) using the PoA bridge route, and (b) batching two or more withdrawals of the identical `assetId` in one `processWithdrawal`/`signAndSendWithdrawalIntent` call — a pattern the SDK's own README promotes as "Batch Withdrawals" without restriction. No malicious actor is needed; a normal integrator following the documented batch API (e.g., withdrawing the same token to two different user addresses in one settlement) triggers the mismatch deterministically since the PoA API response order is explicitly "unsorted."

### Recommendation
Extend the matching key beyond `assetId` to disambiguate same-asset batch entries — e.g., match on `(near_token_id, address, amount)` tuple (destination + amount, which the bridge response already carries in `data.address`/`data.amount`), or reject/queue withdrawals so that same-asset batches through PoA bridge are executed sequentially rather than combined. At minimum, `PoaBridge.validateWithdrawal`/`createWithdrawalIntents` (or the SDK's batch orchestration in `sdk.ts`) should detect and reject batches with duplicate `assetId`s routed to the PoA bridge until proper disambiguation is implemented, consistent with the code's own acknowledged limitation.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdt.omft.near", amount: 100n, destinationAddress: "0xAAA...", feeInclusive:false}, {assetId: "nep141:usdt.omft.near", amount: 200n, destinationAddress: "0xBBB...", feeInclusive:false} ] })`.
2. Both legs route via PoA bridge and settle in one NEAR tx with `tx.hash = H`.
3. PoA bridge's `getWithdrawalStatus({withdrawal_hash: H})` returns an unsorted `withdrawals` array containing both USDT legs (to 0xAAA and 0xBBB) with different `transfer_tx_hash`.
4. `waitForWithdrawalCompletion`/`describeWithdrawal` is invoked once per index (0 and 1), but `findMatchingWithdrawal` uses only `assetId`, so both index-0 and index-1 lookups resolve to the *same* array entry (the first one satisfying `nep141:usdt.omft.near === assetId`) — reporting the same `txHash` for both legs, or attributing 0xBBB's completion hash to the 0xAAA leg's promise, depending on array order [7](#0-6) .

**Uncertainty note:** I was not able to fully verify from the index whether `sdk.ts`'s `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` orchestration layer performs any additional per-index disambiguation before calling the bridge-level `describeWithdrawal`/`findMatchingWithdrawal` (the index only shows the bridge-level function lacking this). If such disambiguation exists elsewhere in `sdk.ts`, it would mitigate this finding; I recommend a Devin session with full repo access to confirm the call chain from `sdk.ts`'s batch completion methods down to `PoaBridge.describeWithdrawal`.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	async processWithdrawal(
		args: ProcessWithdrawalArgs<WithdrawalParams | WithdrawalParams[]>,
	): Promise<WithdrawalResult | BatchWithdrawalResult> {
		const withdrawalParams = Array.isArray(args.withdrawalParams)
			? args.withdrawalParams
			: [args.withdrawalParams];

		// Step 1: Estimate fee
		const feeEstimation = await (() => {
			if (args.feeEstimation != null) {
				return Array.isArray(args.feeEstimation)
					? args.feeEstimation
					: [args.feeEstimation];
			}

			return this.estimateWithdrawalFee({
				withdrawalParams,
				logger: args.logger,
			});
		})();

		// Step 2: Sign and send intent
		const { intentHash } = await this.signAndSendWithdrawalIntent({
			withdrawalParams,
			feeEstimation,
			referral: args.referral,
			intent: args.intent,
			logger: args.logger,
		});

		args.logger?.info("Intent published", { intentHash });

		// Step 3: Wait for intent settlement
		const intentTx = await this.waitForIntentSettlement({
			intentHash: intentHash,
			logger: args.logger,
		});

		args.logger?.info("Intent settled", { txHash: intentTx.hash });

		// Step 4: Wait for withdrawal completion
		const destinationTx = await this.waitForWithdrawalCompletion({
			withdrawalParams,
			intentTx,
			logger: args.logger,
		});

		if (!Array.isArray(args.withdrawalParams)) {
			return {
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				feeEstimation: feeEstimation[0]!,
				intentHash,
				intentTx,
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				destinationTx: destinationTx[0]!,
			};
		}

		return {
			feeEstimation,
			intentHash,
			intentTx,
			destinationTx,
		};
	}
