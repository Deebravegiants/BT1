### Title
POA Bridge Withdrawal Status Matched Only by `assetId`, Causing Wrong Destination Tx Hash to Be Reported for Batched Same-Asset Withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
The PoA bridge's `describeWithdrawal()` resolves the on-chain completion status of a specific withdrawal in a batch by scanning all withdrawals returned for a NEAR transaction and picking the first one whose token matches the requested `assetId` — it does not disambiguate by index, amount, or destination address. When a batch contains two or more withdrawals of the *same* asset (to different destination addresses/amounts), every `describeWithdrawal` call for that asset resolves to the *same* underlying withdrawal record, so a status/tx hash is reported for a withdrawal item that does not correspond to that item's actual on-chain outcome.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` matches purely by asset identity: [1](#0-0) 

This is called from `describeWithdrawal`, which reports `completed` with `transfer_tx_hash` taken from whichever record matched: [2](#0-1) 

The equality this breaks is: *the withdrawal identifier (index within the batch, tied to a specific destination address/amount) the caller is asking about* vs. *the withdrawal record actually returned as "matching."* Because matching ignores `index`, both withdrawal items in a batch with the same `assetId` map to the identical record, and later batched watchers (`createWithdrawalIdentifiers` / `watchWithdrawal` in `packages/intents-sdk/src/core/withdrawal-watcher.ts`) will report the same `txHash` for both, even though on-chain there are two distinct destination transactions to two distinct addresses. [3](#0-2) 

The comment in the source acknowledges the assetId-only matching, explicitly stating multiple same-token withdrawals within one transaction are "not supported," but the SDK exposes no guard, assertion, or validation error preventing an integrator from constructing exactly this batch via `processWithdrawal`/`createWithdrawalIntents` with `withdrawalParams: WithdrawalParams[]` containing repeated `assetId`s. Nothing in `sdk.ts`'s batch-processing path (`createWithdrawalIntents`, `_estimateWithdrawalFee`, `processWithdrawal`) rejects duplicate-asset batches before they reach the PoA bridge.

### Impact Explanation
An integrator that batches two withdrawals of the same token to two different recipients through the PoA bridge would receive a `completed` status/`txHash` for withdrawal index 1 that is actually the destination transaction hash belonging to withdrawal index 0 (or vice versa, depending on API ordering, which is explicitly documented as unsorted). If the integrator uses this reported hash to mark a specific recipient's payout as fulfilled (e.g. for reconciliation, refund suppression, or user notification), it can credit or confirm the wrong recipient's transaction, or report the same hash as complete for both withdrawals — a "status/hash misreport" that can cause an integrator to credit or refund incorrectly, matching the accepted High-impact class of the rules.

### Likelihood Explanation
This requires no privileged or malicious actor — it is triggered purely by an ordinary integrator use case: batching multiple withdrawals of the same token (e.g., paying out the same asset to several users) in a single `processWithdrawal`/`createWithdrawalIntents` call through the PoA bridge route. The SDK's public batch API accepts arrays of `WithdrawalParams` without asset-uniqueness validation, so this is reachable in normal integration usage, not a contrived edge case.

### Recommendation
- Disambiguate `findMatchingWithdrawal` using more than `assetId` — e.g., match by destination address/amount pairing, or track consumed indices so each withdrawal in the batch is matched to a distinct record (sort withdrawals and withdrawal params by amount as the existing comment suggests).
- Alternatively, validate at the SDK batch entry points (`processWithdrawal`, `createWithdrawalIntents`, `_estimateWithdrawalFee`) and reject/flag batches containing duplicate `assetId`s routed through PoA bridge, or route such duplicates through distinct correlation identifiers.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "addrA", feeInclusive: false}, {assetId: "nep141:btc.omft.near", amount: 200000n, destinationAddress: "addrB", feeInclusive: false} ] })` where both route through the PoA bridge.
2. On NEAR, this generates one transaction with two separate PoA withdrawal records with the same `near_token_id`/`assetId` but different destination addresses/amounts/tx hashes.
3. When `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` calls `describeWithdrawal` for index 0 and index 1, both calls invoke `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the *same* first match — as verified in `poa-bridge.ts:409-427` and confirmed by the existing test `"matches withdrawal by assetId, not by index"` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1111`, which demonstrates matching disregards `index` entirely (it only differentiates by distinct `assetId` in that test, not by two same-asset entries — no test covers the duplicate-asset-in-batch case, confirming it is unhandled).
4. Both destination-tx results reported to the integrator will show the same `txHash`, even though addrA and addrB received different on-chain transactions.

Note: I could not fully verify whether any duplicate-asset-in-batch guard exists elsewhere in `sdk.ts` due to running out of search iterations before completing a full read of `sdk.ts`; based on all sections reviewed (`createWithdrawalIntents`, `_estimateWithdrawalFee`, `processWithdrawal`), no such validation was found.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
