### Title
Unsafe raw `token.call` transfers in Tron `IntentGatewayV2.withdraw`/`onAccept` accept non-reverting `false` returns as success, permanently freezing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-targeted `IntentGatewayV2.sol` contract deviates from the rest of the intents codebase (which uses `SafeERC20.safeTransfer`/`safeTransferFrom` throughout `evm/src/apps/intentsv2/IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`) and instead performs raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls, checking only the low-level `success` boolean and never validating the ABI-decoded return value.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, escrow release (`withdraw`), dust sweeping (`onAccept`/`SweepDust`), and predispatch sweeps (`placeOrder`) all use the unsafe pattern:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

and

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same pattern is used for `feeToken` disbursement of accumulated transaction fees:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [3](#0-2) 

This is precisely the "unsafe ERC20 methods" bug class described in the report: `success` from a low-level `.call` only reflects whether the callee reverted, not whether the ERC20 transfer actually succeeded. Some tokens (e.g., TRC20/ERC20 tokens that do not conform to the standard, or intentionally return `false` on failure instead of reverting — a known "weird token" pattern) will cause `success == true` while the transfer silently failed, since the returned `bool` payload is never decoded/checked (compare to the correct pattern in `withdraw()`/`_withdraw()` used elsewhere in the codebase, e.g., `evm/src/apps/intentsv2/IntentsBase.sol` which uses `IERC20(token).safeTransfer(beneficiary, amount)` — `SafeERC20` decodes and reverts on a `false` return) [4](#0-3) .

Crucially, in `withdraw()`, the escrow accounting is decremented/finalized regardless of whether the underlying token transfer logically succeeded:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    _orders[body.commitment][token] -= amount;
``` [5](#0-4) 

Because `_filled[body.commitment]` is marked and the escrow ledger is decremented unconditionally after a "successful" (non-reverting) `.call`, a token that returns `false` on transfer failure (rather than reverting) will result in the escrow bookkeeping being finalized as if funds were paid out, while the beneficiary never actually receives the tokens. Since `_filled[commitment]` is now non-zero, the order can never be filled or refunded again (`Filled()` guard on `cancelOrder`/`fillOrder`), permanently freezing the beneficiary's owed tokens inside the contract with no recovery path.

### Impact Explanation
This is reachable directly from the settlement path of every cross-chain intent order: `onAccept()` → `withdraw()` is invoked automatically by the ISMP host whenever a `RedeemEscrow`/`RefundEscrow` message is delivered from a solver fill or a cancellation, with `token` fully attacker/user-controlled at order-placement time (any TRC20/ERC20 address can be specified as an input asset). Using a token whose `transfer()` returns `false` on failure without reverting (or any non-standard implementation), an order can be settled such that escrow accounting is finalized (order marked filled/refunded) but the actual token transfer to the beneficiary silently fails — this is a permanent freezing of the beneficiary's funds with no way to reclaim them, since `_filled[commitment]` blocks any future settlement/cancellation attempt for that order. The same defect affects fee-token payouts and `SweepDust` dust distribution.

### Likelihood Explanation
Medium-to-High: it requires only a single order using a non-standard-return-value ERC20/TRC20 token as an input asset — the token itself is fully user-selected at `placeOrder` time and does not need to be "malicious" in a governance sense, merely one of the well-documented class of non-conforming tokens that return `false` instead of reverting on failure (a known real-world occurrence on both EVM and TRC20 ecosystems). No privileged role is needed; a normal user placing an order with such a token, combined with any transient balance/allowance issue on the paying side causing the token's internal transfer to fail, triggers the bug through the normal message-delivery/dispatch flow.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` (and any analogous `transferFrom`) patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `SafeERC20.safeTransfer`/`safeTransferFrom`, consistent with the rest of the codebase (`IntentsBase.sol`, `ExtrinsicIntents.sol`, `IntentGatewayV2.sol` non-Tron variant), so that a `false` return value causes an explicit revert instead of being silently treated as success. This ensures escrow state is only finalized when the token transfer genuinely succeeded.

### Proof of Concept
1. Deploy or use a TRC20/ERC20 token whose `transfer(address,uint256)` returns `false` on failure instead of reverting (e.g., due to insufficient contract-held balance from a prior fee-on-transfer deduction, or a deliberately non-conforming implementation).
2. User places an order via `placeOrder` on the Tron `IntentGatewayV2` with this token as an input asset; escrow accounting records the token amount in `_orders[commitment][token]`.
3. Solver fills the order on the destination chain; a `RedeemEscrow` POST request is dispatched back to the source (Tron) chain.
4. `onAccept()` decodes the request and calls `withdraw(body, false)` [6](#0-5) .
5. Inside `withdraw`, `token.call(...IERC20.transfer.selector...)` is invoked; the token's internal logic returns `false` (e.g., because the contract balance was insufficient for that transfer, without reverting). The low-level `.call` reports `success = true` because no revert occurred.
6. The `if (!success) revert TransferFailed();` check passes (success is true), `_orders[body.commitment][token] -= amount;` executes, and `_filled[body.commitment] = beneficiary;` is set — finalizing the order as settled even though the beneficiary received zero tokens.
7. Because `_filled[commitment]` is now set, any subsequent `cancelOrder` or refund attempt reverts with `Filled()`, permanently freezing the beneficiary's owed tokens.
