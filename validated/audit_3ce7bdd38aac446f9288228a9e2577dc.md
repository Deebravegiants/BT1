This confirms the vulnerability. The webhook's `shop` (and `topic`, `webhook_id`) fields are delivered as HTTP headers that are entirely excluded from the HMAC computation — only the raw request body is signed.

### Title
Webhook shop-domain (and topic) attribution is not covered by the HMAC signature, allowing cross-tenant spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers via `shopify_header`. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then trusts `request.shop` and `request.topic` to build the `WebhookMetadata` object passed to the host app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, that signable string is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` verifies only the body/HMAC pair, then forwards the (unauthenticated) `shop` and `topic` header values straight into the handler: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`, i.e., the shop/topic the app acts on should be the same shop/topic Shopify actually signed for. Instead the gem only enforces `hmac == HMAC(secret, body)`, with `shop`/`topic` supplied out-of-band and unauthenticated. Any entity capable of obtaining one genuine `(body, hmac)` pair for a topic they legitimately receive (e.g., a merchant who installs the app on their own shop and receives real webhooks for their own store) can replay that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true` because the signature check never inspected the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to a victim shop, as documented for consuming apps: [5](#0-4) 

Since host apps are explicitly told they can trust `data.shop` after `Registry.process` succeeds (the gem's stated purpose is "verify the request did indeed come from Shopify"), this breaks the identity binding shop_verified == shop_acted_upon, and any host app that uses `data.shop` to look up per-tenant credentials, write per-tenant records, or make API calls scoped to that shop is exposed to cross-tenant data corruption/exfiltration using data attributed to the wrong merchant.

### Impact Explanation
This qualifies as Critical (cross-tenant access): an unprivileged holder of one legitimate webhook payload for their own shop can forge webhook events attributed to a different shop id, since the gem's `Registry.process`/`HmacValidator.validate` never authenticates the shop-domain (or topic) header, only the body bytes.

### Likelihood Explanation
Likelihood is high for any app that relies on the documented `Registry.process` + `WebhookMetadata#shop` flow (as recommended in `docs/usage/webhooks.md`) without independently re-verifying `shop` against a known/registered value. The attacker needs no secrets beyond a webhook body+HMAC pair they can legitimately obtain for their own store (trivial for anyone who installs the app), and headers are fully attacker-controlled when replaying the request directly to the app endpoint.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g. include them in a MAC computed independent of the raw body but validated per-request), so that `HmacValidator.validate` fails if any of these attribution fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same body `B` and header `H` to the app's webhook endpoint again, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over body `B` only and matches `H`, returning `true`.
4. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)` and performs shop-scoped work (e.g., updating victim-shop's stored data or associating attacker-controlled content with the victim tenant), even though Shopify never sent this event for `victim-shop`.
