## Analysis

The Moonwell finding is a *"malicious recipient reverts on token receipt to block a critical, must-complete state transition"* bug class. The Hyperbridge analog exists in `IntentGatewayV2`'s escrow-settlement path.

### Root cause

`IntentsBase._withdraw()` — called from `onAccept` for both `RedeemEscrow` (successful cross-chain fill) and `RefundEscrow` (cancellation) — transfers every escrowed token to a single `beneficiary` in one loop, using `SafeERC20.safeTransfer`, which reverts the entire call if any transfer fails: [1](#0-0) 

The Tron variant is functionally identical but even more exposed, since it performs a raw low-level `.call` and explicitly reverts with `TransferFailed()` if any single token in the loop fails: [2](#0-1) 

The `beneficiary` for `RedeemEscrow` is the solver address captured at fill time (`msg.sender`), and for `RefundEscrow` it is `order.user`: [3](#0-2) 

Because an order can escrow multiple distinct `TokenInfo` entries (`order.inputs`), and the beneficiary receives *all* of them in a single atomic loop, if any one of those tokens has a receiver-side hook (ERC777-style `tokensReceived`, or any token whose `transfer`/hook logic can be made to revert conditionally for a specific recipient) the beneficiary contract can force the whole settlement transaction to revert.

### How this reaches the host and becomes a "silent freeze"

`EvmHost.dispatchIncoming` performs the callback via a low-level `.call` and, on failure, simply **deletes the receipt so the message becomes retryable** rather than reverting the whole relay batch: [4](#0-3) 

This "fail gracefully, retry later" behavior is intentional and documented for genuinely transient failures, but it means a **permanently** reverting beneficiary (a malicious/hook-bearing token controlled contract) causes `RedeemEscrow`/`RefundEscrow` for that commitment to never succeed — no relayer resubmission can ever get past the malicious transfer. This locks the escrowed input tokens for that order commitment in the contract indefinitely, i.e., a concrete permanent freezing of funds, the same underlying primitive as the Moonwell ERC777 bug (an attacker-controlled recipient weaponizes a transfer hook to indefinitely block a state transition that the protocol needs to complete).

### Title
Malicious escrow beneficiary can permanently block `IntentGatewayV2` settlement via a transfer-hook token, freezing escrowed order funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase._withdraw()` (and its Tron equivalent `withdraw()`) atomically transfers every escrowed `TokenInfo` for an order to a single `beneficiary` and reverts the entire call if any one transfer fails. Because the beneficiary is attacker-influenced (the solver address for `RedeemEscrow`, or `order.user` for `RefundEscrow`), and because at least one of the multiple escrowed tokens can carry receiver-side transfer hooks (ERC777-style `tokensReceived` or similar), an attacker can make one transfer permanently revert, which reverts the whole settlement call for that commitment on every retry.

### Finding Description
`_withdraw` loops over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each, with no per-token failure isolation: [5](#0-4) 

`EvmHost.dispatchIncoming` invokes `onAccept` (which reaches `_withdraw`) via a swallowed low-level `.call`; on failure it deletes the request receipt so the message stays "deliverable" and can be retried by any relayer: [6](#0-5) 

If the beneficiary is a contract the attacker controls and implements a hook on one of the multi-token escrow's assets that always reverts (e.g., an ERC777 `tokensReceived` hook, or any hook-bearing/callback token used as one of `order.inputs`), then no matter how many times a relayer resubmits the `RedeemEscrow`/`RefundEscrow` message, `_withdraw` will always revert at that specific token transfer, and the whole settlement — including the unrelated, otherwise-fine transfers and the `_filled` bookkeeping and transaction-fee payout — never completes.

### Impact Explanation
This permanently locks the escrowed input tokens for the affected order commitment inside the `IntentGatewayV2`/`IntentsBase` contract: they can never be released to the solver (on fill) nor refunded to the user (on cancel), because the on-chain state transition that would release them can never successfully execute. This is a concrete, permanent freezing of user/solver funds, matching the accepted impact class for this scan.

### Likelihood Explanation
The attacker only needs to (a) act as, or control, the `msg.sender`/solver that fills a cross-chain order (setting themselves as the `RedeemEscrow` beneficiary), or (b) be the order's `user` for a `RefundEscrow` beneficiary, and (c) ensure one of the multiple escrowed input/output tokens is a receiver-hook-bearing token (which is possible whenever the order's asset list includes an attacker-chosen or otherwise hook-capable token). No special privileges are required — this is reachable from a single order placement/fill by any unprivileged user or solver.

### Recommendation
Isolate per-token transfer failures in `_withdraw`/`withdraw` so a single malicious/hook-reverting token cannot block the settlement of the other escrowed assets — e.g., use a try/catch or pull-based (claim) pattern per token instead of a single atomic loop that reverts entirely on any one failure, and consider disallowing/flagging hook-bearing (ERC777-class) tokens as escrowable assets.

### Proof of Concept
1. User places a cross-chain order whose `order.inputs` includes two tokens: a normal ERC20 (e.g., USDC) and a hook-bearing token `H` that the attacker fully controls (custom ERC20 with a transfer hook, or a real ERC777).
2. A malicious solver (attacker-controlled contract `Evil`) fills the order via `fillOrder`, honestly delivering the required outputs to the user's beneficiary on the destination chain, and is recorded as `msg.sender` (i.e. `RedeemEscrow` beneficiary) in `_fillCrossChain`: [7](#0-6) 
3. The `RedeemEscrow` POST request is relayed back to the source chain and delivered via `EvmHost.dispatchIncoming` → `onAccept` → `_withdraw`.
4. `_withdraw` transfers USDC to `Evil` successfully, then attempts `safeTransfer` of `H` to `Evil`; `Evil`'s hook/receive logic for token `H` unconditionally reverts.
5. The whole `_withdraw` call reverts; `EvmHost.dispatchIncoming` deletes the receipt so the message is retryable, but every future retry hits the same revert.
6. The escrowed USDC and `H` for this order commitment remain locked in the contract indefinitely — no legitimate path exists to release them, since the `beneficiary` recorded in the message body is immutable for that commitment.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
