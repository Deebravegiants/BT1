## Analysis: Missing slippage protection on EvmHost's native-fee-to-feeToken swaps

The C4 report is about `TopUpAction.sol` performing swaps on a user's behalf with a fixed/default slippage tolerance that the position owner cannot configure, letting keepers or the owner sandwich the swap. The closest reachable analog in Hyperbridge is `EvmHost`'s automatic native→feeToken swap performed inside the core, permissionless `dispatch()` / `fundRequest()` entry points — any unprivileged caller who pays with native token triggers this swap, and neither the caller nor the protocol enforces a real slippage bound or a meaningful deadline.

### Title
Unprotected exact-output native→feeToken swap in `EvmHost.dispatch`/`fundRequest` enables sandwich attacks on unprivileged dispatchers - (File: `evm/src/core/EvmHost.sol`)

### Summary
Every `IDispatcher.dispatch()` call paid with native token (and `fundRequest`) routes through `IUniswapV2Router02.swapETHForExactTokens`, requesting an exact `feeToken` output equal to the caller-specified `fee`/`amount`. The call sets `deadline = block.timestamp` (a no-op deadline that never actually expires before the swap can execute) and provides no caller-configurable maximum-input / slippage parameter beyond the raw `msg.value` sent. This mirrors the M-11 bug class: a swap is executed automatically on behalf of an unprivileged party with no meaningful, user-chosen slippage tolerance, making it profitable to sandwich.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all contain the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case:
- `deadline` is hard-coded to `block.timestamp`, which offers no real transaction-staleness protection — the deadline check trivially passes for any transaction mined in the current block, including one deliberately sandwiched by a searcher/validator.
- The only economic bound on the swap's price is `msg.value` itself; there is no independent, caller-supplied `amountInMax`/slippage-bps parameter distinct from the value attached to the call. Callers (via `IDispatcher`) have no documented way to say "I will accept at most X% price impact" — they can only guess a generous `msg.value` to avoid reverts, which is exactly the "default 5%"-style problem the C4 report flags, except here there is no slippage bound at all, just whatever `msg.value` the caller happens to send.
- The same pattern repeats in `IntentGatewayV2.placeOrder`'s native-fee escrow path, which performs the identical `swapETHForExactTokens{value: msgValue}(order.fees, ...)` call with `block.timestamp` as deadline: [4](#0-3) 

The `IDispatcher` interface itself documents this as expected behavior without warning integrators about the missing slippage control: [5](#0-4) 

The docs explicitly acknowledge the resulting slippage exposure but do not describe any on-chain mitigation, only an off-chain warning to avoid calling `quote()` on-chain: [6](#0-5) 

Because `uniswapV2` is a low-liquidity local AMM used purely for fee-token acquisition (not a deep, arbitrage-resistant market), and because the transaction path is fully permissionless (any address can call `dispatch{value: ...}`), a searcher/relayer can:
1. Detect a pending `dispatch()`/`fundRequest()` call with native value in the mempool.
2. Front-run it with a trade that moves the WETH/feeToken pool price against the victim.
3. Let the victim's `swapETHForExactTokens` execute at the worse price, consuming more of the attached native value than a fair-market swap would require.
4. Back-run to restore the pool price and capture the price impact as profit.

### Impact Explanation
Any unprivileged user or application dispatching a cross-chain message and paying with native token can have their transaction sandwiched, causing them to pay materially more native token than fair value for the same `feeToken` fee amount — a direct value extraction from users who never opted into or configured any slippage tolerance. Because this path is on the core message-dispatch flow (`EvmHost.dispatch`) used broadly across integrating `HyperApp`s and `IntentGatewayV2` order placement, the blast radius covers most native-token-funded interactions with the protocol, not a niche feature.

### Likelihood Explanation
Likelihood is Medium-to-High: the swap is triggered on every native-funded `dispatch()`/`fundRequest()`/`placeOrder()` call, it is fully permissionless and predictable from mempool inspection, MEV searchers already generically front-run/sandwich AMM swaps, and the `deadline = block.timestamp` pattern provides no defense against being included in an attacker-controlled block ordering.

### Recommendation
Add an explicit, caller-supplied slippage/maximum-input parameter (e.g., `amountInMax` or `maxSlippageBps`) to `DispatchPost`/`DispatchGet`/`fundRequest`/`placeOrder`'s native-payment path instead of implicitly trusting `msg.value` as the only bound, and replace `deadline = block.timestamp` with a genuine caller-specified deadline so transactions cannot be held and replayed favorably by a searcher. Consider routing the fee-acquisition swap through a TWAP-resistant or higher-liquidity venue, or allow direct feeToken payment to be the strongly preferred path (as the docs already recommend) while hardening the native-token fallback.

### Proof of Concept
1. Attacker monitors the mempool for a `dispatch(DispatchPost)` (or `fundRequest`/`placeOrder`) call with `msg.value > 0`.
2. Attacker front-runs with a large swap on the `uniswapV2` WETH/feeToken pool used by `_hostParams.uniswapV2`, shifting the price.
3. Victim's `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes at the manipulated price, consuming a larger share of `msg.value` than fair value for the same `post.fee` output.
4. Attacker back-runs to restore the pool price, pocketing the spread — with the victim's dispatch transaction never reverting because the `deadline` check (`block.timestamp`) trivially passes and `msg.value` was over-provisioned to avoid `INSUFFICIENT_INPUT_AMOUNT` reverts. ### Payment Method Comparison

```text
| Feature | Native Token | FeeToken (Recommended) |
|---------|-------------|------------------------|
| **Gas Cost** | Higher (includes swap) | Lower (no swap) |
| **Slippage** | Yes (Uniswap swap) | No |
| **Fee Calculation** | Approximate (subject to slippage) | Exact |
| **Token Approval** | Not required | Required  |
| **User Convenience** | High (users have native tokens) | Low (users need feeToken) |
| **Best For** | One-off transactions, user-facing apps | Frequent dispatches, cost optimization |
```
