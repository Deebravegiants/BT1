### Title
Leftover input tokens from LI.FI swaps are permanently stranded in `LifiExternalAction`/`ExternalActionSwap` and never returned to the shielded balance - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap()` debits the user's shielded balance for the *full* `inputAmount`, forwards that amount to an external router via `callRouter`, and then mints a new shielded UTXO only for the resulting `outputToken` amount. `LifiExternalAction.callRouter` approves the router for the whole `inputAmount` and executes an arbitrary, prover-supplied router call, but never checks or reclaims any unspent `inputToken` left over from that call. Any leftover input token balance is simply left sitting in the `ExternalActionSwap`/`LifiExternalAction` contract's own balance with no UTXO, no sweep, and no return path — the shielded value corresponding to that leftover is permanently lost to the user who paid for it, analogous to the BakerFi "leftover collateral locked in Strategy" bug (H-03), where leftover collateral after an inexact swap was left unswept in the strategy contract.

### Finding Description
`ExternalActionSwap.swap()` computes: [1](#0-0) 

`inputAmount` is derived from `deltaAmounts[0]`, i.e., the exact value the circuit/prover committed to debiting from the user's shielded notes for this swap (checked later in `Hinkal.transact` against `circomData.amountChanges`/`utxoAmount`). This full `inputAmount` is handed to `callRouter`.

`LifiExternalAction.callRouter` only measures the *output* token balance delta; it does not verify that `inputAmount` of the input token was fully consumed by the router call: [2](#0-1) 

Because the router call's `externalActionMetadata` is arbitrary calldata (constructed off-chain, ultimately trusted to execute a swap of roughly `inputAmount`), any real-world execution that consumes less than the approved/transferred `inputAmount` (slippage-limited exact-output swaps, partial fills, rate changes between quote and execution, etc. — the exact scenario described in the referenced report where an exact-output swap consumes less than the withdrawn/transferred amount) leaves a residual balance of `inputToken` sitting in the `LifiExternalAction` contract.

Back in `swap()`, only the `outputToken` amount is turned into a new UTXO and transferred onward: [3](#0-2) 

There is no code path that inspects the post-call `inputToken` balance of `ExternalActionSwap`/`LifiExternalAction`, refunds it to `msg.sender` (the Hinkal contract, and by extension the user), or re-mints it as a UTXO. The leftover token is not part of the `Hinkal.transact` balance-equation check either, because that check operates on `Hinkal.sol`'s own balance before/after `_externalTransact`, not on the internal balance of the external-action contract: [4](#0-3) 

From `Hinkal.sol`'s perspective the equality `balanceDif == amountChanges[i] + utxoAmount` still holds (the full `inputAmount` left the Hinkal contract as expected), so the bug is invisible at that layer — but the value is silently lost one hop downstream, inside the swap action contract, with no owner-only rescue function present in this contract to recover it.

### Impact Explanation
This breaks the fundamental invariant that every unit of shielded value debited from a user via `deltaAmounts`/`amountChanges` must be accounted for by either an on-chain transfer to the external recipient or a newly minted UTXO. Any leftover input-token residue from an inexact/partial swap execution is permanently unspendable and unrecoverable by the user — a permanent freezing (loss) of a portion of the user's own funds, matching the report's confirmed Medium-severity impact class ("permanent freezing of user funds"/value leakage over time), which maps to this scan's in-scope "Critical/High" impact category of permanent freezing of user funds.

### Likelihood Explanation
Any swap whose actual execution consumes less than the fully-approved `inputAmount` — a normal, expected occurrence for exact-output or partially-filled swaps, or simply favorable price movement between quote generation and execution — triggers this loss on every affected transaction. No malicious actor is even required; it happens under ordinary swap-execution variance, making likelihood high whenever LI.FI/aggregator routes do not consume the full approved amount.

### Recommendation
After `callRouter` returns in `ExternalActionSwap.swap()`, measure the input token's residual balance held by the contract (`getERC20OrETHBalance(inputToken)` compared to a pre-call snapshot) and either (a) revert if any unspent input remains, requiring the metadata to consume the full amount, or (b) mint an additional UTXO of the input token type for the leftover amount so it is credited back to the user's shielded balance instead of being stranded in the contract.

### Proof of Concept
1. A user submits a `transact` call with `externalActionData.externalActionId` pointing to `LifiExternalAction`, with `deltaAmounts[0] = -100` (debit 100 units of `inputToken`) and `externalActionMetadata` encoding a LI.FI router call quoted to swap 100 `inputToken` for some `outputToken`.
2. `Hinkal.transact` verifies the proof and transfers 100 `inputToken` into `LifiExternalAction` before invoking `runAction` → `swap()`.
3. `swap()` calls `callRouter(inputToken, 100, outputToken, metadata)`; `LifiExternalAction.callRouter` approves the router for 100 and executes `router.call(metadata)`.
4. Due to slippage/rate change between quote time and execution time (or the router only partially filling), the router only pulls 90 `inputToken`, leaving 10 `inputToken` sitting in `LifiExternalAction`'s balance.
5. `callRouter` returns `swappedAmount` based solely on the `outputToken` balance delta; `swap()` mints a UTXO only for `outputToken`. The 10 leftover `inputToken` units are never transferred, refunded, or represented by any UTXO — they remain permanently stuck in `LifiExternalAction`, unrecoverable by the user or the protocol, even though `Hinkal.sol`'s own balance-equation check at lines 134-146 passes because the full 100 units correctly left `Hinkal.sol`.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
