This matches exactly the report's bug class: a field that is *acted upon* but not covered by the HMAC — here, the webhook `shop-domain` used to route/attribute a webhook to a merchant tenant is never included in `to_signable_string`, so it is verified for *integrity of the body only*, not for its *binding to the shop that produced the HMAC*.

### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` (from the `X-Shopify-Shop-Domain` header) as the tenant identity that a host application uses to route a webhook to the correct merchant/session, while the HMAC signature covers only `@raw_body`.

### Finding Description
`Request#to_signable_string` returns just the raw body: [1](#0-0) . The `shop` accessor used by consumers to identify which merchant the webhook belongs to is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) . `HmacValidator.validate` only compares `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)` [3](#0-2) ; since `to_signable_string` is the raw body alone, the `shop` header is never part of the signed material. The identity binding that should hold is: `shop_attributed_to_webhook == shop_that_the_HMAC_actually_authenticates`. Because the header is outside the HMAC, an attacker who can forward/replay a validly-signed webhook payload (e.g. from their own shop, or from any shop for which they can obtain one signed webhook body against the shared `client_secret`-derived signature scheme) can pair that valid signature with an arbitrary `shop-domain` header to make the host application process it as if it came from a different merchant. This is the same root cause as the ENS report: "the only check is a partial one; anything outside of it is uncontrolled," here the equivalent of the untrusted `functionCall` bytes is the tenant-identifying header sitting outside the authenticated envelope.

### Impact Explanation
If a host application (as documented/intended for this gem) uses `Request#shop` to decide which merchant's session/access token/state to act on after `HmacValidator.validate` succeeds, spoofing that header while reusing a validly-signed body allows cross-tenant confusion — actions or data intended for shop A can be attributed to shop B. This matches the "cross-tenant access" Critical impact category since the binding between authenticated bytes and the tenant identifier is broken by design of `to_signable_string`.

### Likelihood Explanation
Requires only unauthenticated network access to the app's webhook endpoint plus the ability to supply arbitrary HTTP headers alongside a body/HMAC pair — no access token, secret, or privileged account is required, satisfying the unprivileged-internet-user constraint. The main uncertainty is how strictly a specific host app couples `shop` to `hmac` validation before trusting it, since this gem only supplies the primitive; I could not fully verify downstream usage patterns beyond the gem's own code, which was correctly out of scope per the rules.

### Recommendation
Bind the tenant-identifying fields into the signed payload, not just the body. At minimum, verify that `shop`, `topic`, and `webhook_id` headers are consistent with a signature computed over a canonical string that includes them (similar to how `Oauth::AuthQuery#to_signable_string` includes `shop`, `host`, `code`, etc.), or document/enforce that callers must independently authenticate `shop-domain` against a known, registered store (e.g., cross-check with a previously established session or with Shopify's mandatory webhook API version metadata) rather than trusting the header at face value once `hmac-sha256` validates only the body.

### Proof of Concept
```ruby
# Attacker captures/derives a validly-signed webhook payload for shop-a.myshopify.com
# (raw_body + hmac-sha256 pass HmacValidator.validate).
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_for_raw_body, # unchanged, still verifies
  "x-shopify-shop-domain" => "shop-b.myshopify.com",  # swapped tenant, NOT covered by HMAC
  "x-shopify-webhook-id" => "1",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because signable string is just raw_body
request.shop # => "shop-b.myshopify.com" -- attacker-controlled, unauthenticated
```
`HmacValidator.validate` returns `true` regardless of the injected `shop-domain`, because `to_signable_string` never includes it [1](#0-0) [4](#0-3) .
