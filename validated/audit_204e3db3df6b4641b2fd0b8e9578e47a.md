### Title
Rounding-biased buy/sell round trips can push `Pair.assetReserve` below the recovered `virtualLtReserve`, permanently bricking a curve via an unguarded underflow in `canGraduate` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` computes `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no check that `assetReserve` is still at least the recovered virtual seed. `Router._computeBuy` / `_computeSell` round every trade in the trader's favor (floor-division always benefits the trader side), and `Pair.swap`'s K-invariant only enforces a `(reserve+1)*(reserve+1) >= k` floor, not per-reserve monotonicity. Enough round-trip buy/sell activity can therefore drift the stored `assetReserve` down to exactly `virtualLtReserve` or one wei below it. Once that happens, `canGraduate` underflows and reverts — and since `canGraduate` is invoked at the end of every buy (`_executeBuy`) and at the start of every sell (`Zap._sellInternal`), every subsequent trade on that token reverts, permanently freezing the curve and any LT already raised inside `Pair`.

### Finding Description
`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT seed from the immutable `Pair.k()`: [1](#0-0) 

`canGraduate` uses that recovered value to compute `realLtRaised` by direct subtraction, with **no guard** that `assetReserve >= virtualLtReserve`: [2](#0-1) 

This is structurally the same class of bug as the dm-era report: a value that is only valid "target-relative" (i.e. `assetReserve` measured relative to the launch-time virtual floor) is used in a subtraction without first confirming it hasn't dropped below that floor — analogous to dm-era computing the writeset block before applying the target offset and indexing past the bitset's bounds. Here the "index" is `assetReserve - virtualLtReserve`, and an out-of-range value (an `assetReserve` that has drifted at or below the floor) causes an unchecked-arithmetic revert instead of a memory-safety violation, but the reachable trigger and the permanent-freeze consequence are equivalent in class and severity.

The drift is possible because both AMM legs round in the trader's favor:
- Buy: `tokensOut = reserveToken - (k / newReserveAsset)` — floor division on `k / newReserveAsset` rounds `tokensOut` up.
- Sell: `assetOut = reserveAsset - (k / newReserveToken)` — same floor division rounds `assetOut` up. [3](#0-2) 

`Pair.swap`'s only safety check is a loose `(newTokenReserve+1)*(newAssetReserve+1) >= k` floor — it does not prevent `assetReserve` from creeping toward (or at) the launch-time virtual seed over many trades, it only bounds the product: [4](#0-3) 

Because `tokenReserve` is capped at `totalSupply` (the virtual seed value baked in at `Pair.mint`), a sequence of round-trip buys/sells that pushes `tokenReserve` toward that ceiling repeatedly forces `k / newReserveToken` (and thus `k / newReserveAsset` on the buy side) through the same rounding-favorable floor divisions, letting `assetReserve` settle at or one wei below `virtualLtReserve` after enough iterations — a low-cost, purely on-curve grinding attack requiring no privileged role, since `Bonding.buy` / `Bonding.sell` (reached through `Zap.buy` / `Zap.sell`) are open to any address.

Once `assetReserve < virtualLtReserve`, `canGraduate` underflows on any call. This is fatal because:
- `_executeBuy` checks `canGraduate` at the end of every buy (per the documented flow), so even a "healthy" buy that would restore `assetReserve` above the floor reverts entirely once it hits the trailing `canGraduate` check, rolling back the whole transaction: [5](#0-4) 
- `Zap._sellInternal` calls `bonding_.canGraduate(tokenAddress)` up front on every sell, so sells revert too: [6](#0-5) 

With both entry points permanently reverting, the token can never trade, never graduate, and all real LT already locked in `Pair` (plus any tokens still on the curve) becomes permanently unreachable — no recovery path exists since `Router.graduate` (the only way to drain `Pair`'s LT) is itself only reachable from the now-unreachable `_prepareGraduationLiquidity`/`_enterGraduating` path, which is gated behind the same `canGraduate`-adjacent lifecycle logic.

### Impact Explanation
This is a permanent freeze of trader, creator, and protocol funds tied to the affected token: the bonding curve becomes permanently untradeable (no buy, no sell), the token can never graduate to HyperSwap, and the real LT raised on the curve is stuck inside `Pair` with no code path to extract it (`Router.graduate` is only invocable from the bricked graduation flow). This matches the "permanent freezing of trader, creator or LP funds" impact bar required by the prompt, and is systemic to any single token whose curve accumulates enough round-trip rounding drift — reachable purely through the public `Zap.buy`/`Zap.sell` interfaces available to any unprivileged wallet.

### Likelihood Explanation
The attack requires no special privilege, only repeated small buy+sell round trips on a single token's curve through `Zap.buy`/`Zap.sell` or `Bonding.buy`/`Bonding.sell` directly (an attacker can self-route as their own trader). Each round trip only needs to nudge `tokenReserve` toward its ceiling and rely on the built-in favorable-rounding bias; the number of iterations needed depends on the wei-scale of the drift versus `virtualLtReserve`'s magnitude, which can be pushed lower by targeting freshly launched/thinly-capitalized tokens (small `virtualLtReserve` due to a high LT `exchangeRate`) to shrink the number of round trips required. Gas cost is the only real barrier, and it is bounded and automatable.

### Recommendation
- Guard `canGraduate` (and any other site subtracting `_launchTimeVirtualLtReserve` from `assetReserve`, e.g. `previewLtUntilGraduation` at line 722 and `_prepareGraduationLiquidity` at line 1084) with an explicit `assetReserve <= virtualLtReserve` early-return / clamp-to-zero, mirroring the donation-inflation guard already applied to the supply leg in `previewLtUntilGraduation` (`if (realBalance >= reserveToken) return ltUntilThreshold;`).
- Alternatively, tighten `Pair.swap`'s K-invariant so it also enforces a floor on `assetReserve` relative to `k / totalSupply` (the launch-time virtual value), preventing the reserve from ever drifting to or below the virtual seed regardless of rounding accumulation.
- Re-run `test/GraduationInvariants.t.sol` and add a fuzz/regression test that performs many small round-trip buy/sell cycles and asserts `canGraduate` never reverts due to underflow.

### Proof of Concept
1. Launch a token via `Zap.createToken` with an LT whose `exchangeRate` is high enough to make `virtualLtReserve` small (a few wei-scale units after `1e18` normalization is not achievable directly, but relative drift becomes proportionally easier to reach with a smaller `virtualLtReserve`).
2. As an unprivileged trader, repeatedly call `Bonding.buy` with a small `amountIn` of LT, then immediately `Bonding.sell` back the exact `tokensOut` received, driving `tokenReserve` upward across iterations (each cycle's rounding favors the trader per `Router._computeBuy`/`_computeSell`'s floor-division as cited above).
3. After enough iterations, `Pair`'s stored `assetReserve` settles at exactly `virtualLtReserve` or one wei below it.
4. Any further call to `Bonding.buy` (which triggers `canGraduate` at the end via `_executeBuy`) or `Zap.sell` (which calls `canGraduate` up front) now reverts due to the unchecked `assetReserve - _launchTimeVirtualLtReserve(...)` underflow in `canGraduate` — bricking the token's curve permanently, with any real LT raised on the curve now unreachable.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
