Based on my research, I found a clear analog in `pallet-messaging-incentives`. This pallet mints `ReputationAsset` to whichever account's signature recovers from a delivered message's `signer` field, scaled purely by payload byte-size — with no check that the "relayer" actually performed real, valuable relaying work, and no check that a single relayer can't submit unlimited distinct self-authored messages to farm this reward for free, mirroring the original bug's pattern of cheaply minting many free "objects" (there: NFTs from free account creation; here: self-signed request/response messages) and converting them into disproportionate backing (there: loan collateral; here: Reputation Asset, which is the sole input to Collator selection and is the reward this exclusion list explicitly keeps in scope as "relayer fee and reward accounting").### Title
Self-relaying inflates free, unbacked Reputation Asset used for Collator selection - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
`pallet-messaging-incentives::on_executed` mints `ReputationAsset` to whoever's sr25519 signature recovers from a delivered `Message`'s `signer` field, scaled only by payload byte-size, with no requirement that the relaying involved any real cross-chain value delivery, competition, or third-party benefit. This mirrors the referenced Arcadia bug class: an unprivileged actor can cheaply/for-free mint many low-value "objects" (there: NFTs from free `Factory::createAccount()`; here: self-authored, self-signed ISMP request messages) and consolidate them to obtain a disproportionate amount of a value asset used as collateral/trust elsewhere (there: margin collateral; here: Reputation Asset, the sole determinant of Collator selection per `pallet-collator-manager`).

### Finding Description
`Pallet::on_executed` iterates every executed `Message`, computes `bytes = message_bytes(message)` (a simple `max(body_len, 32)` floor, no cost or economic backing check), recovers the signer via `relayer_for`, and unconditionally mints `rate * bytes` of `ReputationAsset` to that account: [1](#0-0) 

The only "cost" a relayer pays to trigger a mint is submitting a signed `Message::Request`/`Message::Response` for ISMP execution — there is no check that:
- The relayer is not also the request originator (self-dispatch),
- The message carries any real fee payment or destination-side value,
- The same account hasn't already minted for functionally duplicate/self-generated traffic.

Because `pallet-hyperbridge` allows zero-fee dispatch (`fee: Default::default()`, as documented for host-originated system messages) and because dispatching+delivering a POST request from a source chain to itself is a normal, permissionless operation any user can perform end-to-end, a single actor can:
1. Deploy/control a trivial `IApp` module (or use an existing self-dispatchable path) on a source chain.
2. Dispatch cheap POST requests with maximal-allowed body size, from itself, to itself or another chain, with `fee = 0`.
3. Run their own relayer instance (or self-sign the delivery) to have `on_executed` process the message and recover their own account as `relayer`.
4. Repeat across many (source, dest) pairs / many blocks, at essentially the gas cost of dispatch only, to mint unlimited `ReputationAsset` without ever performing genuine third-party relaying work.

This is directly analogous to the referenced report: the "cost" of creating the value-bearing object (an Arcadia margin Account NFT / here, a Reputation-minting message) is negligible relative to the value it can later be redeemed for (margin collateral / Collator selection), and nothing stops one actor from doing this many times over and consolidating the result.

### Impact Explanation
`ReputationAsset` accrued this way is the *only* input `pallet-collator-manager::new_session` uses to rank and select the next Collator set: [2](#0-1) 

An attacker who can mint Reputation for free (rather than through genuine cross-chain message delivery competition) can outrank legitimate operators and get elected as a Collator — a block-producing, treasury-rewarded (`0.7 $BRIDGE`/block) and fraud-detection role (the "fisherman" veto duty) — without contributing genuine relaying value to the network. This is a real, unbacked-mint-style economic distortion of a reward/selection mechanism explicitly in scope ("relayer fee and reward accounting"), not merely a griefing/DoS concern.

### Likelihood Explanation
High reachability: dispatching a POST request is a single unprivileged transaction any user can send, and delivering/executing it (triggering `on_executed`) is likewise something any relayer-capable account can do, including the message's own originator. The pallet performs no anti-self-dealing check and no proportional real-value requirement — only a byte-size floor meant to stop trivial-payload gaming, not self-dispatch gaming. The mechanism is only "profitable" while `MintPerByte` is non-zero (governance-controlled), but whenever it is active this path is directly and cheaply reachable.

### Recommendation
- Require that the account credited by `relayer_for` differ from the message's originating account/module (`request.from`), rejecting or discounting self-relayed messages.
- Tie reputation minting to genuine economic signal already present in the protocol — e.g., only mint proportional to `RequestPayments`/non-zero relayer fees actually collected at origin (mirroring how `pallet-relayer`'s existing `accumulate_fees` flow works), rather than raw byte count alone.
- Consider per-account rate limiting or diminishing returns on reputation minted from a single relayer/source-module pair within a session, to blunt any residual Sybil pattern even after the self-dealing check.

### Proof of Concept
1. Governance (or an already-active) `MintPerByte` rate is non-zero (a normal operating state for the pallet).
2. Attacker deploys a trivial `IApp` on an EVM (or Substrate) chain and dispatches a POST request to any destination with `fee = 0`, `body` sized near governance-configured limits, from an account they control.
3. Attacker runs (or is) the relayer that picks up and delivers this message to Hyperbridge for execution, signing the `Message::Request`/`Message::Response` envelope with their own sr25519 key.
4. `pallet_ismp` calls `FeeHandler::on_executed`, which calls `message_bytes` → `relayer_for` → mints `rate * bytes` of `ReputationAsset` to the attacker's account, as shown in `on_executed_mints_reputation_proportional_to_bytes`: [3](#0-2) 

5. Attacker repeats steps 2–4 across many self-controlled chains/accounts/blocks at minimal gas cost, accumulating Reputation Asset far beyond what genuine third-party relaying would have earned, then uses that Controller account to register as a Collator candidate and be selected ahead of legitimate operators per the ranking in `pallet-collator-manager::new_session`.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
