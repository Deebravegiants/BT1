## Analog Vulnerability Found

### Title
Webhook shop/topic identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook purely by verifying the raw HTTP body against the app's shared `api_secret_key`, while the `shop`, `topic`, and `webhook_id` values that determine *which tenant and which handler* the payload is dispatched to are read straight from unauthenticated HTTP headers. Because the same `api_secret_key`/HMAC is valid for every shop that has installed the app, a merchant who legitimately receives their own signed webhook can replay the identical body with a forged `X-Shopify-Shop-Domain` header naming a different (victim) shop, and the signature check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop`, `#topic`, and `#webhook_id` are pulled from headers with no cryptographic binding: [1](#0-0) 

```
def topic ... shopify_header("topic") end
def shop  ... shopify_header("shop-domain") end
def to_signable_string; @raw_body; end
```

`to_signable_string` — the only thing actually covered by the HMAC — returns just `@raw_body`; the shop/topic/webhook-id headers are excluded, as confirmed by: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`, i.e. only the raw body: [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop`/`request.topic` immediately after this body-only check succeeds, and forwards them unchanged to the handler as the tenant identity for the event: [4](#0-3) 

The identity binding the app relies on is: `shop reported to handler == shop that produced/owns the signed body`. In reality the gem only proves `HMAC(secret, body) == received_hmac`; it never proves `shop_header == the shop the secret's owner intended`. Since `api_secret_key` is the same for all shops that installed the app (it's the app's client secret, not a per-shop secret), any shop owner who can trigger a webhook to themselves possesses a `(body, valid_hmac)` pair that remains valid when replayed with an arbitrary `shop-domain` header.

### Impact Explanation
This breaks the cross-tenant boundary the whole `Webhooks::Registry`/`Request` API is meant to enforce: host applications built on this gem are expected to trust `WebhookMetadata#shop` (built directly from `request.shop`, see `Registry.process` line 198) to select the tenant record to update. An attacker who is a normal (unprivileged, non-victim) merchant on the same multi-tenant app can obtain a validly-signed webhook for their own shop and then relay a spoofed request naming a different merchant's shop domain, causing the host app to apply that legitimate payload against the victim tenant's data — a cross-tenant access/write primitive achieved without any credential, token, or secret belonging to the victim.

### Likelihood Explanation
Any user of the app who can install it on their own store (the normal, unprivileged install flow of any public Shopify app) can legitimately receive a webhook whose body+HMAC pair is valid under the shared `api_secret_key`. Forging the `shop-domain`/`topic` header on the replayed HTTP POST requires no secret material at all, only network access to the app's public webhook endpoint. This is a low-effort, no-privilege exploit path.

### Recommendation
- Bind `shop`, `topic`, and `webhook_id` into the signed content used for HMAC verification (e.g., include them in `to_signable_string`), or
- Require the gem to independently verify the reporting shop against an expected/allow-listed set (e.g., cross-check `shop-domain` header against a shop derived from a per-shop secret or from the session/access-token record associated with that webhook subscription id) before constructing `WebhookMetadata`.
- At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant selection without additional verification, and provide a built-in mechanism (e.g., per-shop webhook secrets) to close the gap.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged action).
2. The app registers a webhook (e.g., `orders/create`) and Shopify delivers a body `B` with header `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: HMAC(api_secret_key, B)`.
3. Attacker captures this legitimate `(B, hmac)` pair.
4. Attacker POSTs the same `B` and `hmac` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `hmac`.
6. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host application to process attacker-controlled data under the victim's tenant context.
