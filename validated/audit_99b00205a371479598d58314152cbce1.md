### Title
Webhook tenant identity (`shop`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, then dispatches to the app's handler using `request.shop` as the tenant identifier. The HMAC, however, is computed only over the raw request body, never over the `shop` (or `topic`) fields. This breaks the equality the app relies on: `shop_authenticated_by_hmac == shop_delivered_to_handler`.

### Finding Description
`Webhooks::Request#hmac` decodes the `X-Shopify-Hmac-Sha256` header, and `#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, to_signable_string)` and compares it against the received value using `OpenSSL.secure_compare`: [4](#0-3) 

Since `to_signable_string` for a webhook `Request` is exactly `@raw_body`, the signature only binds the body bytes — it says nothing about which shop the header claims to be from. `Registry.process` nonetheless uses the unauthenticated header value as the merchant/tenant identity forwarded to the app's business logic: [5](#0-4) 

`WebhookMetadata` exposes this unauthenticated `shop` field directly to the handler as if it were verified: [6](#0-5) 

Because a legitimate merchant of a multi-tenant app receives real, correctly-HMAC-signed webhook deliveries for their own shop (same body, same secret), that merchant can capture one such valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`) header with a different shop/topic value that also uses the app. `HmacValidator.validate` still succeeds because the body bytes are unchanged, so the gem reports the webhook as authentic and hands the handler a `WebhookMetadata` claiming to be for the victim tenant.

### Impact Explanation
This is a cross-tenant boundary break: the app's webhook handler (built on the trust that `Registry.process` only invokes it after fully authenticating the request) receives attacker-controlled `shop`/`topic`/`webhook_id` values under the cover of a passing HMAC check. Depending on how the host app uses these fields (e.g., looking up the tenant's stored session/access token by `shop`, writing data keyed by `shop`, or triggering GDPR redaction/data-request flows for the wrong shop), this enables cross-tenant data corruption, incorrect authorization decisions, or processing actions against another merchant's data — satisfying the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker (a merchant who has legitimately installed the app) can observe one webhook delivery it receives (trivial — apps commonly log or expose webhook payloads, and the merchant controls their own store activity to trigger deliveries) and can send an HTTP POST to the app's public webhook endpoint with modified headers, which is unauthenticated inbound traffic by design. No access to `api_secret_key` or any token is needed.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signable string, or otherwise cryptographically bind them before trusting them, so `to_signable_string` covers everything `Registry.process`/`WebhookMetadata` subsequently rely on — not just the JSON body. At minimum, document that consumers of `WebhookMetadata#shop` must independently verify the shop against a known/registered tenant list rather than trusting it as authenticated by `HmacValidator.validate`.

### Proof of Concept
1. App receives a real webhook for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Merchant of `shop-a` (attacker) captures `B` and `H`.
3. Attacker POSTs to the app's webhook endpoint with the same body `B`, same header `H`, but `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a different tenant of the same app).
4. `Utils::HmacValidator.validate(request)` at [7](#0-6)  passes because it only checks `B` against `H`.
5. `Registry.process` calls `handler.handle` with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, and the app processes the payload as belonging to `shop-b`, even though it never came from Shopify for that shop.
