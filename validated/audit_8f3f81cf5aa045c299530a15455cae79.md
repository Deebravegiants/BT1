### Title
Fixed weight `{1_000_000}` on `accumulate_fees`/`withdraw_fees` decouples declared cost from unbounded per-commitment proof verification, enabling weight-based DoS - (File: `modules/pallets/relayer/src/lib.rs`)

### Summary
The Sherlock report describes `getPositionIdsByOwner` performing an unbounded loop over `nextPositionId` whose cost scales with attacker-influenced state, making the function unusably (or dangerously) expensive relative to what callers/integrators expect. The equivalent bug class in Hyperbridge is `pallet_ismp_relayer`'s unsigned extrinsic `accumulate_fees`, which processes an attacker/relayer-supplied, unbounded `withdrawal_proof.commitments: Vec<H256>` through multiple linear-cost loops and full Merkle/state-proof verification, yet is declared with a fixed weight of `{1_000_000}` regardless of the batch size.

### Finding Description
`accumulate_fees` is an unsigned extrinsic reachable by any relayer (no origin check beyond `ensure_none`): [1](#0-0) 

It is declared with a constant weight independent of input size: [2](#0-1) 

`Self::accumulate` deduplicates commitments in a `BTreeSet`, filters the (unbounded) `Vec<H256>`, derives storage keys per commitment, and calls into `verify_state_proof` (full Merkle/RLP or trie proof verification per key) for both the source and destination chains — cost scaling linearly (or worse) with `withdrawal_proof.commitments.len()`: [3](#0-2) 

It then iterates the same commitments again to mark them claimed: [4](#0-3) 

`WithdrawalProof.commitments` is a plain `Vec<H256>` (not a `BoundedVec`), so nothing at the type/codec level caps how many commitments — and therefore how many storage-proof leaves and trie-verification operations — a single unsigned submission can carry. Because the `#[pallet::weight]` annotation is a hardcoded constant (`{1_000_000}`) rather than a function of `commitments.len()` or the proof size, the runtime's weight accounting has no relationship to the actual computation/PoV consumed by `validate_unsigned`/dispatch. This mirrors the `BlueBerryBank.getPositionIdsByOwner` bug class: the caller-facing/consensus-facing cost model assumes bounded, cheap execution, but the actual execution cost is unbounded and attacker-influenced.

`validate_unsigned` itself invokes `Self::accumulate` (i.e., runs the full proof-verification/looping logic) during transaction-pool validation, before the fixed dispatch weight is even charged: [5](#0-4) 

This means the expensive, size-dependent verification work happens both at txpool-validation time and at dispatch time, for a fee/weight cost fixed at `1_000_000`. `withdraw_fees` (`Self::withdraw`) shares the same `{1_000_000}` weight pattern and `ensure_none` unsigned origin.

### Impact Explanation
An unbounded, size-independent weight declaration on a computationally unbounded, unsigned, attacker-reachable extrinsic breaks the block-weight accounting model that Substrate relies on to bound block execution time. A relayer can submit `accumulate_fees` calls with very large `commitments` vectors (each requiring a full state/storage proof verification, hashing, and set operations), while the runtime believes each call costs only `1_000_000` weight. This can be used to pack a block with calls whose declared weight fits well within the block weight limit but whose actual execution time vastly exceeds it, causing block production/import slowdowns, denial-of-service risk to collators/validators processing the block, and validate_unsigned-time slowdowns in the transaction pool (since `validate_unsigned` itself calls `Self::accumulate`, duplicating the expensive path before dispatch). This can degrade or halt honest relayer fee processing and broader chain liveness — a Medium severity availability/DoS issue analogous to the original unbounded-loop gas-exhaustion report, but manifesting through weight-accounting mismatch rather than a literal out-of-gas revert.

### Likelihood Explanation
Likelihood is moderate-to-high: `accumulate_fees` is unsigned and callable by anyone acting as a relayer (any account can construct a valid-looking `WithdrawalProof` referencing real delivered commitments, or an adversarial relayer can pad the batch up to whatever proof size is practically constructible). No explicit maximum length is enforced on `commitments` before the expensive verification path runs, so the only natural limits are transaction/extrinsic size limits and block PoV limits — not the intentional weight-based limits that were the actual point of Substrate's declared-weight mechanism.

### Recommendation
Make the declared weight of `accumulate_fees` (and `withdraw_fees`, if similarly affected) a function of `withdrawal_proof.commitments.len()` (and/or proof byte length), using a `WeightInfo` benchmark that charges per-commitment/per-proof-leaf cost, matching Substrate's standard "linear weight from a bounded/benchmarked input" pattern. Additionally, bound `WithdrawalProof.commitments` with an explicit `BoundedVec<H256, MaxCommitmentsPerWithdrawal>` (and similarly bound the accompanying storage proofs) so both the type system and the weight function agree on a hard cap, and so `validate_unsigned`'s pre-dispatch verification cost is capped as well.

### Proof of Concept
Not directly exploitable via a runnable PoC from the indexed context alone (no benchmarking harness or weight file was found in-scope to confirm the exact numeric mismatch). Conceptually:
1. A relayer collects (or synthesizes, if it can produce valid deliveries) a very large number of distinct request commitments plus their corresponding source/destination storage proofs.
2. It submits `accumulate_fees(withdrawal_proof)` as an unsigned extrinsic with `commitments.len()` as large as the extrinsic/PoV size limits allow.
3. Both `validate_unsigned` and dispatch execute `Self::accumulate`, which runs `BTreeSet` dedup, filtering, and `verify_state_proof` over every commitment — actual computation scaling with `commitments.len()` — while the runtime only reserves `1_000_000` weight for the call.
4. Repeating this across multiple transactions in a block allows the sum of *actual* execution cost to exceed the block's real weight/time budget while the *declared* weight sum stays within limits, degrading block-production time for collators/validators.

I was unable to verify the presence or absence of an upstream `BoundedVec` size cap or `WeightInfo` benchmark file for this pallet within the indexed context, so confirm this by inspecting `modules/pallets/relayer/src/withdrawal.rs` (full definition of `WithdrawalProof`) and any `weights.rs`/benchmarking module for `pallet-ismp-relayer` before finalizing severity.

	pub fn accumulate(mut withdrawal_proof: WithdrawalProof) -> DispatchResult {
		// Reject duplicate commitments within the batch. The wire format is a
		// `Vec` and this extrinsic is unsigned, so this is the line of defence
		// against an attacker padding the batch with identical commitments to
		// double-claim fees.
		let mut seen = alloc::collections::BTreeSet::new();
		for key in withdrawal_proof.commitments.iter() {
			ensure!(seen.insert(key.encode()), Error::<T>::DuplicateCommitment);
		}

		// Filter out already-claimed / missing commitments
		withdrawal_proof.commitments = withdrawal_proof
			.commitments
			.into_iter()
			.filter(|req| match RequestCommitments::<T>::get(*req) {
				Some(leaf_meta) => !leaf_meta.claimed,
				// If request commitment does not exist in storage which should not be
				// possible, we skip it
				None => false,
			})
			.collect();
		ensure!(!withdrawal_proof.commitments.is_empty(), Error::<T>::MissingCommitments);
		let host = <T as Config>::IsmpHost::default();
		let source_sm = validate_state_machine(&host, withdrawal_proof.source_proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		let dest_sm = validate_state_machine(&host, withdrawal_proof.dest_proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		let state_machine = withdrawal_proof.source_proof.height.id.state_id;
		let source_keys = Self::source_fee_commitment_keys(
			state_machine,
			&*source_sm,
			&withdrawal_proof.commitments,
		);
		let dest_keys = dest_sm.receipts_state_trie_key(withdrawal_proof.commitments.clone());
