I now have everything needed to write up the finding.### Title
Webhook Shop-Domain and Topic Headers Are Trusted for Tenant Routing Without HMAC Coverage - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, then dispatches to the app's handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from unauthenticated HTTP headers. Because these header fields are never included in the HMAC-signed content, the identity binding "shop that the HMAC-authenticated payload actually belongs to" == "shop the handler is told it belongs to" does not hold.

### Finding Description
`Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

Its `to_signable_string`, which is the only input fed into HMAC verification, is just the raw body: [2](#0-1) 

`HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this single check as the entire authenticity gate, then immediately trusts `request.shop` and `request.topic` (unauthenticated headers) to build the metadata passed to the app's handler: [4](#0-3) 

The documented contract tells host apps that `data.shop` is "The shop domain of the webhook" and shows apps using it directly as the tenant identifier for follow-up work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) 

The identity binding that should hold is:

`shop_that_signed(raw_body, hmac)` == `request.shop` (the value the handler is told)

But since `shop` is not part of the signable string, the gem only proves *"a request body was HMAC'd with `Context.api_secret_key`,"* not *"this body belongs to shop X."* Because the `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not shop-specific), any tenant of the app that receives a legitimate webhook (body + valid HMAC) for their own shop can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. `Utils::HmacValidator.validate` will still pass (it never looked at the header), and `Registry.process` will dispatch to the handler with `WebhookMetadata.new(shop: <victim_shop>, topic: ..., body: <attacker's own webhook body>, ...)` — a cross-tenant confusion where data attributable to one tenant is processed under another tenant's identity.

### Impact Explanation
This breaks the shop-identity binding that host applications are documented to rely on for tenant isolation (`data.shop` is used to select/act on a shop's session, records, or queued jobs). An attacker who is merely an unprivileged existing merchant/tenant of the app (no special privilege, no access token, no leaked secret) can cause the host app to attribute forged or replayed webhook data to a different shop, i.e., cross-tenant access/confusion — matching the Critical "cross-tenant access" impact category, since the shop binding that the gem is documented to guarantee is not actually enforced by its own verification code.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that follows the documented pattern (`docs/usage/webhooks.md`) of trusting `data.shop` without independently re-validating it against a known/registered shop for that specific webhook. The attacker needs only: (1) to be an installed merchant of the target app (to legitimately receive one authentic webhook, i.e., a valid `(raw_body, hmac)` pair), and (2) the ability to POST arbitrary headers to the app's public webhook callback URL, which is unauthenticated by design (that's the whole point of the HMAC check). No access token, no `client_secret`, and no privileged account are required — only participation as any tenant.

### Recommendation
- Include the intended shop domain (and ideally topic) inside the HMAC-signed material, or independently verify `request.shop` against the shop that the webhook was registered for/expected from before dispatching to the handler.
- At minimum, document and/or enforce that `Registry.process` callers must cross-check `request.shop` against a shop known to have an active registration/session for that specific `topic`/`webhook_id`, rather than treating the header as trusted metadata once HMAC-over-body succeeds.

### Proof of Concept
1. App merchant "Attacker Shop" installs the app and legitimately receives an authentic webhook: `raw_body = B`, headers include `x-shopify-hmac-sha256 = HMAC(secret, B)` and `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker captures this `(B, HMAC(secret, B))` pair (e.g., by simply logging their own inbound webhook, or standing up a normal endpoint to receive it).
3. Attacker POSTs to the same app's webhook callback URL with the identical body `B` and identical `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-31` succeeds because it only checks `B` against the HMAC — it never inspects the shop header.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. - `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
