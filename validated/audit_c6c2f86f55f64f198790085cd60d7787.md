### Title
Webhook shop-domain spoofing via header not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` object that includes `shop`, described as "The shop domain of the webhook." In reality, only the raw request body is covered by the HMAC check; the `shop` (and `topic`, `webhook-id`, `api-version`) values are read straight from HTTP headers that are never included in the signed bytes. Any party capable of obtaining one genuine, validly-signed webhook body (e.g., a merchant who has installed the app on their own store) can replay that exact body with a forged `shopify-shop-domain` header to the app's webhook endpoint, and it will pass verification while being attributed to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

`Request#shop` is populated directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing `HmacValidator.validate` result as sufficient proof of authenticity and forwards `request.shop` unchecked to the handler: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," and that the resulting `data.shop` is "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

This is the same identity-binding break described in the analog report: a field that is acted upon (`shop`, used to attribute/route the webhook payload to a tenant) is not covered by the cryptographic proof (HMAC) that the library presents as validating "the request." The equality that should hold — `shop_header == shop_bound_by_hmac` — never holds, because the HMAC signable string contains no shop identifier at all.

### Impact Explanation
Because the HMAC secret (`client_secret`) is shared by the app across all of its shop installations, any shop that has installed the app can capture one of its own legitimate webhook deliveries (body + valid HMAC) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `Registry.process` will accept it as authentic and hand `WebhookMetadata` with the attacker-chosen `shop` to the app's handler. Any app that uses `data.shop` to select which tenant's records to update, look up sessions/tokens for, or otherwise route the payload — exactly as the docs advise doing — will process attacker-controlled data under a spoofed tenant identity, which is a cross-tenant data-integrity/confidentiality issue.

### Likelihood Explanation
Exploitation only requires becoming a merchant of the target app (which for most public apps is open to any internet user) to obtain one legitimately-signed webhook body, then replaying it with a modified header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or privileged accounts is required beyond the trivial act of installing the app on a shop the attacker controls.

### Recommendation
Bind the tenant identity into the verified material, or explicitly document/enforce that `shop` from a webhook is unauthenticated and must be cross-checked against a known, previously-established relationship (e.g., verify that `webhook_id`/topic-derived resource actually belongs to a shop with an active session/subscription, or use Shopify's provided `X-Shopify-Shop-Domain` only after confirming that shop has a webhook currently registered for that specific `webhook_id`). At minimum, `HmacValidator`/`Registry.process` should not be documented as proof the request "did indeed come from Shopify" for the shop attribution — only for the body content.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and triggers an `orders/create` event, capturing the legitimate webhook HTTP request: headers (including `shopify-hmac-sha256` and `shopify-shop-domain: attacker.myshopify.com`) and raw body.
2. Attacker resends the identical raw body and `shopify-hmac-sha256` value to the same app webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `HmacValidator.validate` recomputes the HMAC over `raw_body` only, which still matches, so `Registry.process` proceeds.
4. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` and performs its normal shop-scoped logic (e.g., "update order for victim.myshopify.com") using attacker-supplied body content, even though the payload never originated from or concerned `victim.myshopify.com`.
