### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs (and later validates) only the raw request body, while the `shop`, `topic`, and `webhook_id` attributes that the registry uses to route and identify the webhook are pulled unverified from HTTP headers. An attacker who can obtain one genuine, HMAC-valid webhook body/signature pair for the app (e.g., from their own store where the app is installed) can replay that exact body with a forged `x-shopify-shop-domain` header claiming to be a different, victim shop, and the HMAC check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, and `webhook_id` — the identity/tenant fields the rest of the library relies on — are read directly from request headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates only that the body's HMAC matches, then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the metadata that is dispatched to the app's handler: [3](#0-2) 

The `HmacValidator` itself only ever computes/compares a signature against whatever `to_signable_string` returns for the given `VerifiableQuery` implementation: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop the app is installed on (not a per-shop secret), a body signed for one shop's event is cryptographically indistinguishable from a body meant for another shop. The binding that should hold is:
```
verified(bytes) == bytes actually used to determine "shop" for tenant-scoped handling
```
but here `verified(bytes) == raw_body only`, while `shop_used_for_dispatch == header value (unverified)`. This is exactly a "field acted on but not covered by the HMAC" break of an identity binding.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (populated straight from the unverified header) to select which tenant's session/access token to act on, or to write/attribute data per-shop, can be made to process an attacker's own legitimate webhook payload under a victim shop's identity. This is a cross-tenant confusion vulnerability: the "shop" field the app trusts for tenant routing is not the shop that the cryptographic signature actually vouches for.

### Likelihood Explanation
Medium: it requires the attacker to (a) have the target app installed on at least one shop they control (a very low bar — many apps are freely installable), (b) capture one genuine webhook body/HMAC pair from their own shop (trivial, since they receive it directly), and (c) resend it to the app's public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or elevated privileges are needed beyond normal app installation.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed/verified payload, or otherwise cryptographically bind them to the HMAC-covered body before trusting them for tenant-scoped dispatch in `Registry.process`. At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used alone to select per-shop credentials.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., updates a product) and captures the resulting POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`).
3. Attacker resends body `B` with header `H` unchanged but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-31` only checks `H` against `B`, which still matches — request passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the app's handler, which now believes this attacker-supplied payload originated from the victim shop.

          received_signature = verifiable_query.hmac
