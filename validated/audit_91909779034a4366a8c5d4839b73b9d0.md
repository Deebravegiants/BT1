### Title
Fee-token migration in `EvmHost.updateHostParamsInternal` can be permanently blocked by a griefer donating dust of the old fee token - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` refuses to change `feeToken` whenever the host contract still holds a non-zero balance of the *old* fee token. Because any address can transfer an arbitrary ERC-20 (including 1 wei) directly to the `EvmHost` contract at any time, without any permission check, an attacker can perpetually keep this balance non-zero and permanently block governance from ever migrating the fee token, mirroring the root cause of M-29 (an unprivileged actor pre-loading a balance that a reset/migration code path unconditionally checks/acts on, causing the migration transaction to revert forever).

### Finding Description
`updateHostParamsInternal` contains this guard: [1](#0-0) 

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
```

This function is reachable only via `updateHostParams`, restricted to `_hostParams.hostManager`: [2](#0-1)  and this in turn is only reachable through the cross-chain `HostManager`/`pallet-ismp-host-executive` governance flow, which is itself a slow, multi-step, non-atomic process (the governance action is dispatched as an ISMP message and later delivered by a relayer) [3](#0-2) .

Just like M-29 - where anyone could pre-load a balance at a supposedly-empty address (`address(0)`) so that a later unconditional balance-based branch in `setFlywheelRewards` would always be non-zero and force a revert - here **anyone** holding any amount of the old fee token can call `IERC20(oldFeeToken).transfer(address(evmHost), 1)` at any time, since the check on the balance is a plain `balanceOf(address(this))` with no gating on who deposited it or when. The only "reset" mechanism available is `withdraw`, which is also cross-chain-governance-gated and non-atomic with `updateHostParams` [4](#0-3) , so there is always a window between "governance withdraws the residual balance" and "governance's fee-token-change message is delivered" during which the attacker can re-donate dust and force the change to revert again — indefinitely, at negligible cost (dust amounts, no approval needed).

### Impact Explanation
If Hyperbridge's operators ever need to migrate the protocol `feeToken` (e.g., the token is deprecated, compromised, depegged, or a regulatory/technical reason forces a swap), a single unprivileged actor holding a tiny amount of the current `feeToken` can permanently deny this governance action from ever succeeding on a given `EvmHost`, since:
1. Withdraw and update are two separate, non-atomic cross-chain governance deliveries.
2. The attacker only needs to observe the withdrawal (a public on-chain event) and front-run/immediately follow it with a 1-wei transfer before the subsequent `updateHostParams` delivery lands.
3. There is no upper bound on how many times the attacker can repeat this, and the cost is negligible.

This is a governance/config DoS on a critical dispatch-fee parameter of the `IsmpHost`, permanently freezing the protocol's ability to correct or rotate its fee token — a core economic parameter that gates every fee-bearing dispatch on that chain.

### Likelihood Explanation
High likelihood in the specific (but realistic) scenario that governance ever needs to change the fee token: the attack requires no special privileges, no approval, and costs only the price of a dust ERC-20 transfer and gas. It's a standing griefing vector any time a fee-token migration is attempted, and the attacker doesn't even need to be the current fee-token holder in large amounts — 1 wei suffices to make `balance != 0` true.

### Recommendation
Do not gate the fee-token change on the *current* balance being zero. Instead:
- Either automatically sweep/transfer out any residual `oldFeeToken` balance to the beneficiary/treasury as part of `updateHostParamsInternal` itself (atomically, in the same transaction as the parameter update), removing the two-step non-atomic race entirely, or
- Remove the hard revert and instead just emit a warning/event if residual balance exists, letting governance decide, or
- If the safety property (not silently losing stuck old-fee-token balance) must be preserved, make the check resistant to griefing, e.g., by not enforcing it based on balance but based on an explicit governance flag/acknowledgement, or by using a threshold/dust-ignoring comparison and providing an atomic sweep-and-migrate path in the same call.

### Proof of Concept
1. `EvmHost.hostParams().feeToken == TokenA`.
2. Governance decides to migrate to `TokenB` due to some issue with `TokenA` and dispatches a `Withdraw` request through `HostManager` to drain `TokenA` from the host, then dispatches an `updateHostParams` request with `feeToken = TokenB`.
3. After the `Withdraw` message is delivered and the host's `TokenA` balance is zero, an attacker (anyone holding `TokenA`, including a fresh acquisition of dust from a DEX) calls `TokenA.transfer(address(evmHost), 1)`.
4. When the `updateHostParams` governance message is later delivered (relayed cross-chain, not atomic with step 2/3), `updateHostParamsInternal` computes `balance = IERC20(TokenA).balanceOf(address(this)) == 1`, and reverts with `CannotChangeFeeToken` [1](#0-0) .
5. The attacker repeats step 3 after every subsequent withdrawal attempt, indefinitely blocking the fee-token migration at negligible cost.
