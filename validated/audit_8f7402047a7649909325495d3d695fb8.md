## Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while only the raw body is HMAC-verified — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the merchant identity (`shop-domain`), the event type (`topic`), and the delivery id (`webhook_id`) are read directly from unauthenticated HTTP headers and are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only the body-HMAC and then dispatches to the app's handler using these unsigned header values, breaking the binding "the shop/topic the HMAC vouches for == the shop/topic the app acts on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic linkage to the signature: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which, per `to_signable_string`, checks only the body), looks up the handler by the unsigned `topic` header, and forwards the unsigned `shop` header straight into the dispatched metadata: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this: the comparison is solely against `verifiable_query.to_signable_string`, which for webhooks is the raw body: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared with every shop that installs the app, any merchant that has installed the app can receive genuine, validly-signed webhooks for **their own shop** (body + `hmac-sha256` pair). Since the signature never covers `shop-domain`, `topic`, or `webhook-id`, that same (body, hmac) pair remains cryptographically valid no matter what values are placed in those headers. An attacker who controls one legitimately-installed shop can therefore replay a genuine webhook to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain, and/or the `topic` header rewritten to a different registered topic (e.g. a compliance topic like `customers/redact` or `shop/redact`), and the request will still pass `HmacValidator.validate` and be dispatched to the corresponding handler as if it genuinely originated from, and concerns, the victim shop.

The identity binding that should hold is:
`shop/topic authenticated by HMAC == shop/topic acted upon by the handler`
but the actual code enforces only:
`body authenticated by HMAC` while `shop/topic == unauthenticated header value`.

### Impact Explanation
This breaks tenant isolation for any app whose webhook handlers key persistence, side effects, or trust decisions off `WebhookMetadata#shop` or `#topic` (e.g., updating a shop's local record based on `shop/update`, deleting data for `customers/redact`/`shop/redact`, disabling access on `app/uninstalled`) — an attacker with just one paid or free install of the target app can inject events that the app will process as belonging to an arbitrary other shop, producing cross-tenant data corruption or unauthorized state changes. This meets the Critical "cross-tenant access" bar defined in scope.

### Likelihood Explanation
Exploitation requires only that the attacker install the app once on any shop (a normal, unprivileged action) and capture one legitimately delivered webhook (body + hmac) from Shopify — no access to `api_secret_key`, tokens, or other shops' credentials is needed. Likelihood is high for apps that trust `WebhookMetadata#shop`/`#topic` for tenant-scoped or compliance-sensitive logic, which is the documented intended use of `Registry`/`WebhookMetadata`.

### Recommendation
Extend `Utils::VerifiableQuery`/`HmacValidator` usage for webhooks so that `shop`, `topic`, and `webhook_id` are bound to the verified request — e.g., include them in the signable string (would require Shopify to sign them, not solely a gem-side fix) or, at minimum, have `Registry.process` cross-check `request.shop` against the shop associated with the session/subscription that registered the webhook for that specific `topic`/`webhook_id` before dispatching, instead of trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Shopify sends the attacker a legitimate webhook, e.g. topic `customers/redact`, body `{"shop_id":123,"shop_domain":"attacker.myshopify.com", ...}`, with header `X-Shopify-Hmac-Sha256: <valid hmac of body>`.
3. Attacker replays the exact same body and `hmac-sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks the body against the hmac (`lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/request.rb`).
5. `Registry.process` dispatches `WebhookMetadata.new(topic: "customers/redact", shop: "victim.myshopify.com", ...)` to the app's handler, which performs redaction/side effects attributed to `victim.myshopify.com` even though the payload never came from Shopify concerning that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
