### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-covered "signable string" from the raw body only, while the `shop` (and `topic`, `webhook_id`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then dispatches the handler using the unauthenticated `request.shop`, breaking the binding between "the payload Shopify actually signed" and "the shop the library asserts the payload belongs to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or HMAC: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC using only `verifiable_query.to_signable_string` (i.e., the raw body for webhooks), never touching the shop header: [3](#0-2) 

`Registry.process` checks only this body HMAC, then immediately forwards the caller-supplied, unauthenticated `request.shop` to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is:
```
shop bound by HMAC == shop used by handler to attribute/act on the event
```
Here, the left side does not exist at all — the HMAC binds only the body bytes, not the shop. Consequently the equality is vacuously false: any `shop-domain` header value can be paired with any HMAC-valid body.

Because the app's `api_secret_key` used to compute the webhook HMAC is a single shared secret across all shops that have installed the app (it is not per-shop), any merchant who installs the app receives genuine webhook deliveries — real `(raw_body, hmac)` pairs signed by Shopify with that shared secret. Since the shop header is excluded from the signed content, that same valid `(raw_body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to name a different (victim) tenant. `Utils::HmacValidator.validate` will still return `true`, and `Registry.process` will invoke the handler with `WebhookMetadata` carrying the attacker-chosen `shop`.

### Impact Explanation
Any app installer (an ordinary, unprivileged merchant with no special access, access token, or knowledge of `client_secret`) can obtain a legitimately HMAC-signed webhook body/HMAC pair from their own shop's webhook deliveries and replay it against the app's public webhook endpoint while spoofing the `shop-domain` header to name a victim shop. Host applications that key merchant-scoped side effects (data writes, cache invalidation, order/inventory updates, session/webhook bookkeeping) off `WebhookMetadata#shop` as returned by this gem will attribute the attacker's forged event to the victim tenant, i.e., cross-tenant action under a false tenant identity — meeting the Critical "cross-tenant access" bar, since the shop identity is the trust boundary here and this gem provides no protection against it.

### Likelihood Explanation
High likelihood for any deployment that relies on this gem's `Webhooks::Registry`/`Request` as the sole verification mechanism (which is exactly how the gem's own documentation and tests demonstrate its use): the attacker only needs (a) to install the target app on their own shop (a normal, permissionless action for any Shopify merchant), (b) to capture one webhook delivery's raw body and HMAC header, and (c) to send a normal HTTP POST to the app's public webhook URL with a forged shop header. No secret material, tokens, or privileged access is required.

### Recommendation
Bind the shop identity into the value that is cryptographically verified before it is trusted:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signable string (`to_signable_string`) so that spoofing the header invalidates the signature, or
- Independently verify that `request.shop` matches an expected/registered shop domain (e.g., an existing session record) before dispatching the handler, rather than trusting the unauthenticated header outright.

### Proof of Concept
1. App is installed by attacker's own shop `attacker.myshopify.com`; Shopify sends a real webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures `B` and the HMAC header value.
3. Attacker sends a new POST to the same public webhook endpoint with identical body `B` and identical HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb#L12-L31`) validates successfully because it only checks `B` against the HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-L200`) invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the event body actually originated from and was signed for `attacker.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
