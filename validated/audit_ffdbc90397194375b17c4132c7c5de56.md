### Title
`isAutoApprove` grants blanket per-origin trust that ignores wallet-account and asset scope, letting scope silently widen after approval - ([File: features/connected-origins/module/connections.js])

### Summary
`isAutoApprove` in `features/connected-origins/module/connections.js` only keys off the literal `origin` string and returns a single boolean stored on the connection record, without checking which wallet account or which asset scope the user originally consented to when enabling auto-approve. Combined with `add()`, which silently unions any newly requested `assetNames`/`connectedAssetName` into the existing connection's `assetNames` array without re-confirming `trusted`/`autoApprove`, a connected origin that has been granted auto-approve for a narrow scope (one account, one asset) can have its trust reused for a broader asset scope or a different active wallet account with no new user interaction.

### Finding Description
`isAutoApprove` is defined as: [1](#0-0) 
It looks up the origin exactly by string via `#getOrigin` [2](#0-1) 
and returns only `value.autoApprove`, with no parameter for `assetName`/`assetNames` or the currently active `walletAccount`.

`setAutoApprove` sets this single flag with no asset or account scoping: [3](#0-2) 

Meanwhile `add()` merges any new `assetNames`/`connectedAssetName` passed for an *existing* origin into the union of previously stored `assetNames`, and preserves `trusted`/`autoApprove` from the prior record if not explicitly overridden: [4](#0-3) 

Because `isAutoApprove` is asset- and account-agnostic, once a website origin obtains `autoApprove: true` for some initial narrow scope (e.g., one asset on one wallet account, as a result of explicit user approval), any later `add()` call from the same origin that widens `assetNames` (an attacker/dapp-controlled parameter) is accepted and merged into the connection record without requiring the auto-approve flag to be re-confirmed for the new scope. Any subsequent request that calls `isAutoApprove({ origin })` will return `true` and skip the approval prompt for the newly expanded asset set, and — since `walletAccount` is never checked inside `isAutoApprove` — the same holds if the user switches the active wallet account (`activeWalletAccountAtom`) while remaining on the same connected origin. The stored `walletAccount` field on the connection is written by `add()`/`#addNewItem` but is never consulted by `isAutoApprove`: [5](#0-4) 

The exact cross-*origin* reuse described in the prompt is not possible, since `#getOrigin` performs a strict `value.origin === origin` equality check, so a different origin string always returns `undefined`/`false`. The real, code-confirmed weakness is: (1) auto-approve trust is not scoped to the asset set that was approved when the flag was turned on, and (2) auto-approve trust is not scoped to the wallet account that was active/approved at grant time.

### Impact Explanation
A malicious or compromised dapp origin that has already earned `autoApprove: true` (typically after a user opts in for convenience on a narrow scope) can incrementally call `add()` with additional `assetNames` to expand what gets silently approved, and/or continue to benefit from auto-approve after the user switches to a different wallet account, resulting in state-modifying authenticated actions (e.g., signing/connecting for assets or accounts) being approved without the specific interactive consent the user believes they gave for that narrower scope. This matches "Taking state-modifying authenticated actions on behalf of other users [accounts] without any interaction by that user" for the account-reuse portion of the flow.

### Likelihood Explanation
Preconditions: the user must have previously enabled `autoApprove` for the origin (an intentional, if narrow, opt-in) and either (a) later interact with the same dapp again requesting different/more assets, or (b) switch active wallet accounts while the dapp session persists. Both are ordinary, low-friction user behaviors that a dapp can trigger simply by requesting additional connections; no privileged access or key leakage is required, matching the "unprivileged attacker via connected website" threat model.

### Recommendation
Scope `autoApprove` (and its lookup in `isAutoApprove`) to the specific `assetName`(s)/`connectedAssetName` and `walletAccount` that were active when the user granted it, e.g., store and check `autoApprove` per `{origin, walletAccount, assetName}` tuple, or invalidate/require re-confirmation of `autoApprove` whenever `add()` widens `assetNames` for an origin, and require `isAutoApprove` to take and validate the currently active `walletAccount` against the one recorded at grant time.

### Proof of Concept
Unit test to add to `features/connected-origins/module/__tests__/connections.test.js`:
```js
test('autoApprove silently covers expanded asset scope without re-approval', async () => {
  await connectedOrigins.add({
    origin: 'evil.com',
    connectedAssetName: 'solana',
    assetNames: ['solana'],
    trusted: true,
  })
  await connectedOrigins.setAutoApprove({ origin: 'evil.com', value: true })

  // Dapp later requests a broader scope via add(), simulating attacker-controlled assetNames
  await connectedOrigins.add({ origin: 'evil.com', assetNames: ['solana', 'ethereum', 'bitcoin'] })

  // Expectation for a correct implementation: auto-approve should NOT silently cover the new scope
  const result = await connectedOrigins.isAutoApprove({ origin: 'evil.com' })
  expect(result).toBe(false) // FAILS currently: returns true, proving scope creep
})

test('autoApprove is reused across different active wallet accounts', async () => {
  await connectedOrigins.add({
    origin: 'evil.com',
    connectedAssetName: 'solana',
    assetNames: ['solana'],
    trusted: true,
    walletAccount: 'exodus_0',
  })
  await connectedOrigins.setAutoApprove({ origin: 'evil.com', value: true })

  await activeWalletAccountAtom.set('exodus_1')

  // Expectation for a correct implementation: auto-approve granted for exodus_0 should not apply to exodus_1
  const result = await connectedOrigins.isAutoApprove({ origin: 'evil.com' })
  expect(result).toBe(false) // FAILS currently: returns true regardless of active account
})
```
Both assertions currently fail against the implementation shown at `features/connected-origins/module/connections.js:209-216` and `140-185`, confirming the scope-widening/account-reuse behavior.

  add = async ({
    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,
    favorite,
    walletAccount,
  }) => {
    const value = await this.#getOrigin({ origin })

    const allConnectedAssetNames = new Set([
      connectedAssetName,
      ...assetNames,
      ...(value?.assetNames ?? []),
    ])

    if (value) {
      await this.#setAttributes({
        origin,
        attributes: {
          icon: icon ?? value.icon,
          name: name ?? value.name,
          connectedAssetName: connectedAssetName ?? value.connectedAssetName,
          trusted: trusted ?? value.trusted,
          favorite: favorite ?? value.favorite,
          assetNames: [...allConnectedAssetNames],
          walletAccount: walletAccount ?? value.walletAccount,
        },
      })

      return
    }

    await this.#addNewItem({
      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,
      assetNames: [...allConnectedAssetNames],
      walletAccount,
    })
  }
