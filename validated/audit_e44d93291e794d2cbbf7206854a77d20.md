### Title
XRPL X-address with embedded destination tag combined with separate `destinationMemo` produces conflicting tags in `WITHDRAW_TO` memo - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts])

### Summary
`validateXrpAddress` accepts XRPL X-addresses, which embed their own destination tag, without converting them to classic form or checking whether the caller also supplied a `destinationMemo`. `createWithdrawMemo` then naively concatenates the raw address and the memo into `WITHDRAW_TO:<address>:<memo>`, producing a payload with two independent, potentially conflicting tag encodings for the same withdrawal.

### Finding Description
The claimed invariant is: the destination tag encoded in the address the user validated equals the destination tag ultimately paid by the bridge. This breaks because:

- `validateXrpAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` (lines 333-335) accepts an address if `xrp_isValidClassicAddress(address) || xrp_isValidXAddress(address)`, with no branch that rejects X-addresses or requires converting them to classic form. [1](#0-0) 
- `createWithdrawIntentPrimitive` / `createWithdrawMemo` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts` build the on-chain memo by simply joining `["WITHDRAW_TO", normalizedAddress]` and, if `xrpMemo` is non-empty, appending it as a third segment — with no XRPL-specific handling that decodes an X-address, extracts its embedded tag, or rejects the combination of an X-address plus a separate memo. [2](#0-1) 

An attacker (an ordinary user withdrawing their own funds, or a counterparty whose strings an integrator forwards) supplies:
- `destinationAddress` = a valid XRPL X-address encoding tag `999`
- `destinationMemo` = `"42"`

`validateAddress` passes (X-address accepted). `createWithdrawMemo` then produces `WITHDRAW_TO:<xAddress-with-tag-999>:42` — a memo string containing two different tag sources for the same payment. Whatever downstream component (bridge/off-chain relayer/rippled submission logic) decides which of the two tags to honor, the *other* one is silently dropped, and there's no code in this path that detects the conflict, converts the X-address to a classic address to extract/reconcile the "true" tag, or throws an error.

No other guard in the reachable path (`validateAddress`, `compareAddresses`, `validateWithdrawal`, etc., none of which reference `destinationMemo` per repository search) checks for this XRPL-specific conflict.

### Impact Explanation
The intent that gets signed/submitted embeds an ambiguous/conflicting destination tag in `memo`. For XRPL destinations at custodial exchanges that key incoming deposits purely by destination tag, whichever tag is actually honored by the bridge (the X-address-embedded one or the free-form memo one) may not be the one the user intended, misdirecting the deposit credit with no on-chain recovery mechanism (this is a memo/tag misrouting, not a wrong on-ledger account, but for tag-keyed custodial accounts it is equivalent to funds being irrecoverably lost to the depositor). This matches "funds delivered to a wrong address/chain/contract with no recovery" — Critical severity for the affected user, and is repeatable on every such withdrawal.

### Likelihood Explanation
Preconditions: a withdrawal to an XRPL destination through the POA bridge where the caller supplies both an X-address-format `destinationAddress` and a non-empty `destinationMemo`. This requires no privilege — any caller invoking `createWithdrawIntentPrimitive` (or any public SDK withdrawal method that forwards user-supplied `destinationAddress`/`destinationMemo` down to it) can trigger it, at zero attacker cost, and it is fully repeatable per call. Whether it manifests as an actual fund loss depends on how the downstream bridge/rippled submission logic parses the composite memo string — this part of the resolution is outside this repo, but the repo-level flaw is that no validation or normalization occurs before the ambiguous memo is constructed and signed into the intent.

### Recommendation
In `createWithdrawMemo` (or `createWithdrawIntentPrimitive`), for XRPL destinations: detect X-address format, decode it (e.g., via `ripple-address-codec`'s `xAddressToClassicAddress`) to extract its embedded tag and the classic address; if `destinationMemo` is also provided and non-empty, reject the request (throw a validation error) instead of silently emitting both; otherwise use the extracted tag as the memo and always emit the classic address in `WITHDRAW_TO`.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { createWithdrawIntentPrimitive } from "../src/bridges/poa-bridge/poa-bridge-utils";
import { classicAddressToXAddress } from "ripple-address-codec";

describe("XRPL X-address + destinationMemo conflict", () => {
  it("embeds both the X-address (with tag=999) and a separate memo=42 without reconciliation", () => {
    const classicAddress = "rEXAMPLE00000000000000000000000000"; // valid classic address
    const xAddress = classicAddressToXAddress(classicAddress, 999, false);

    const primitive = createWithdrawIntentPrimitive({
      assetId: "xrp.omft.near", // XRPL-mapped assetId
      destinationAddress: xAddress,
      destinationMemo: "42",
      amount: 1000n,
    });

    // BROKEN EQUALITY: memo should encode exactly one tag source, but it embeds two
    expect(primitive.memo).toBe(`WITHDRAW_TO:${xAddress}:42`);
    expect(primitive.memo).toContain(xAddress); // raw X-address, unconverted, tag=999 still embedded
    expect(primitive.memo).toContain(":42");    // separate conflicting tag=42
    // No error is thrown despite the conflicting tag sources
  });
});
```

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
