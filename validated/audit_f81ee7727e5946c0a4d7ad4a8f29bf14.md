### Title
Permanent Graduation Brick via `Math.mulDiv` Overflow in `Bonding._noFeeSwapInput` from Attacker-Inflated HyperSwap Pre-Seed Reserves - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._noFeeSwapInput`, the closed-form rebalance-swap-size calculator used by the hostile-pre-seed defense, computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` where `reserveIn`/`reserveOut` come straight from the attacker-front-runnable HyperSwap V2 pair's `(uint112 r0, uint112 r1)` reserves [1](#0-0) . The function's own natspec admits the invariant "`reserveIn*reserveOut*targetN/targetD ≤ 2^256`" is only true "in practice," is unenforced by any code-level clamp, and that "constructed adversarial inputs that violate this would revert rather than silently truncate" [2](#0-1) . Since the reserves are attacker-seeded up to `uint112` max and `targetD` (whichever of `tokensForLP`/`ltFromPair` is used as denominator) can be small relative to the numerator, this lets an unprivileged attacker force a revert deep inside the graduation path that the protocol's own documentation says "MUST never" happen.

### Finding Description
`finalizeGraduation`'s hostile-pre-seed defense is designed around the guarantee that `_seedUniswapV2Direct` (and its helpers `_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose` / `_noFeeSwapInput`) "MUST never revert under any pre-seed shape," calling this "the load-bearing security property... because a brick locks every holder in `Graduating` forever" [3](#0-2) .

The attack path an unprivileged address can take (all steps are the exact "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation" primitive):
1. Front-run `Bonding._enterGraduating`/`finalizeGraduation` by permissionlessly calling `factory.createPair(token, lt)`.
2. Transfer TOKEN and LT to the pair at extreme, attacker-chosen magnitudes (bounded only by the attacker's holdings and V2's `uint112` reserve cap, i.e. up to `type(uint112).max ≈ 5.19e33` per side) and call `pair.mint(attacker)` — exactly the "Regime 3" mint pre-seed the codebase already documents as reachable and expected [4](#0-3) .
3. When `finalizeGraduation` runs, `_seedRebalancing` reads these inflated `(r0, r1)` reserves as `reserveToken`/`reserveLT` and, since they dwarf the `DIRECT_MINT_PRESEED_BPS` dust band, routes into the rebalance branch, calling `_pairRebalance` with `reserveIn`/`reserveOut` set to the attacker-inflated values and `targetN`/`targetD` set to the protocol's own `ltFromPair`/`tokensForLP` [5](#0-4) .
4. `_noFeeSwapInput` computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` [6](#0-5) . With `reserveIn`, `reserveOut` near `2^112` each, the raw product approaches `2^224`; multiplied by `targetN` (up to `~2^88` for `tokensForLP`, bounded by `LP_RESERVE = 250M·1e18`) the 512-bit intermediate can reach `~2^312`. When the *denominator* `targetD` (the other of `tokensForLP`/`ltFromPair`) is small relative to that product — which happens naturally whenever the graduating LT has appreciated sharply, so only a tiny amount of real LT (`ltFromPair`) was needed to cross the fixed `graduationThresholdUsd` — the final quotient no longer fits in `uint256`, and OZ's `Math.mulDiv` reverts rather than truncating.
5. That revert propagates unguarded through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`, which has no try/catch or fallback for this case, breaking the documented "must never revert" contract.

Once this fires, the token is permanently stuck in `Lifecycle.Graduating`: all curve-raised LT and the 250M reserved `lpReserve` tokens parked on `Bonding` during the two-phase split [7](#0-6)  can never be released, because `finalizeGraduation` is the only permissionless path out of `Graduating` and it will revert on every retry (the hostile reserves persist in the pair).

### Impact Explanation
This is a permanent freeze of funds for every trader/holder of the affected token, the creator's future fee stream, and the LP that would have been seeded — the exact "permanent freezing of trader, creator or LP funds" class the analog rules call out. The trigger costs the attacker only gas plus whatever TOKEN/LT they choose to donate into the pre-seed (which they retain claim on, or can even recover economically since the pair never finalizes); it is a griefing/DoS vector reachable by any address with no special privilege, matching the CVE's "unauthorized ability to cause a hang or frequently repeatable crash (complete DoS)" bug class mapped onto alt.fun's graduation state machine instead of MySQL's DML engine.

### Likelihood Explanation
The `_noFeeSwapInput` natspec itself flags the overflow precondition as unenforced by code ("Call sites must keep that invariant... Constructed adversarial inputs that violate this would revert") [2](#0-1) , and the test suite's own overflow-safety tests only assert safety within a *bounded, non-adversarial* input space (`uint64` reserves, or a specific realistic ceiling), explicitly not the full `uint112` V2 reserve range combined with a small `targetD` [8](#0-7) . Reaching the precise numeric threshold requires the attacker to combine (a) maximal V2 reserve inflation and (b) a graduation where `ltFromPair` (or `tokensForLP`) is unusually small — both of which are attacker/market-influenceable but not fully attacker-controlled in one transaction, so likelihood is real but conditional rather than trivially guaranteed on every graduation.

### Recommendation
Clamp `reserveIn`/`reserveOut` (or the intermediate product) inside `_noFeeSwapInput` to a safe bound before calling `Math.mulDiv`, and/or wrap the rebalance computation in a try/catch inside `_pairRebalance` that falls back to `_seedDirectMint` on any revert (mirroring the existing `s == 0` / `expectedOut == 0` fallback), so a pathological pre-seed degrades to the safe direct-mint path instead of permanently bricking `finalizeGraduation`.

### Proof of Concept
1. Launch a token normally via `Zap.createToken`.
2. Buy on the curve until it becomes graduatable via the USD trigger at a moment where `exchangeRate()` is very large (or wait for such a moment on an appreciating LT), so that `ltFromPair` computed by `_enterGraduating` is a very small wei amount while `tokensForLP` is comparatively large.
3. Before `finalizeGraduation` is called, front-run: call `factory.createPair(token, lt)`, then `transfer` TOKEN and LT to the pair near `type(uint112).max` each (funded via cheap curve purchases / minted LT), and call `pair.mint(attacker)`.
4. Call `Bonding.finalizeGraduation(token)` — it reverts inside `_noFeeSwapInput`'s `Math.mulDiv` call due to a >`uint256` quotient, and every subsequent call reverts identically, leaving the token permanently stuck in `Lifecycle.Graduating`.

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

#### Regime 3 — mint pre-seed (the actual exploit)

Attacker called `pair.mint(attacker)` against a self-funded dust seed. Reserves are non-zero at a hostile ratio. We:

1. **Compute the swap input** that would drive the pool ratio back to the curve-close ratio under the no-fee constant-product model: `s = sqrt(reserveIn · reserveOut · targetN / targetD) − reserveIn`, capped at our per-side budget. Implementation in `_noFeeSwapInput`. Closed-form via OZ `Math.sqrt + Math.mulDiv`; no binary search, no convergence loop.
2. **Execute the swap directly on the pair** via `pair.swap(amount0Out, amount1Out, address(this), "")`. We read the output from the pair's own fee-aware `getAmountOut` quote and pass it as the output. **Bypasses the router** — HyperSwap's V2 router has no canonical `swapExactTokensForTokens` (see "HyperSwap Router non-standard ABI" above). Same direct-to-pair pattern Zap uses for post-grad user swaps. Implementation in `_pairRebalance`.
3. **Deposit the remaining inventory** via `router.addLiquidity(rest, 1, 1, lpLock, ...)`. The router's `quote()`-based optimal split deposits only the matched-ratio subset; neither side becomes a `min()` donation. Off-ratio remainder stays in `Bonding`. The router's `addLiquidity` IS canonical V2 on HyperSwap (verified selector `0xe8e33700`), so this leg is safe to keep on the router and gets the `quote()` math for free.
4. **Dispose the off-ratio remainder.** TOKEN side burned (`Bonding` is the Token owner). LT side auto-swept to the protocol owner by `finalizeGraduation`'s post-sweep — emits `LTRescued(lt, owner, amount)` for observability. See "Per-graduation LT isolation" below.
