### Title
Non-Atomic Withdrawal of Paired Assets Causes Total Freezing of LP Funds When Either Side's Token Transfer Fails - (File: program/src/processor.rs)

### Summary
`process_withdraw` burns a user's LP tokens and transfers *both* the coin-side and pc-side vault balances to the user in a single atomic instruction. If either one of the two `Invokers::token_transfer_with_authority` calls fails for any reason tied to the recipient's token account or the underlying mint (e.g. a frozen/closed destination ATA, a mint with a freeze authority that has frozen the user's account, or any other non-standard/misbehaving SPL token behavior on one side of the pair), the entire withdraw instruction reverts, and the user's LP position — including the healthy side of the pair — becomes permanently unrecoverable.

### Finding Description
`Processor::process_withdraw` performs the following sequence unconditionally as one all-or-nothing transaction: [1](#0-0) 

Both transfers (`amm_coin_vault` → `user_dest_coin`, and `amm_pc_vault` → `user_dest_pc`) must succeed, then the LP is burned via `Invokers::token_burn` and `amm.lp_amount` is decremented. There is no mechanism to withdraw only the coin side or only the pc side independently, nor any fallback accounting path if one transfer CPI fails.

The underlying `Invokers::token_transfer_with_authority` is a thin CPI wrapper with no error handling/fallback — any failure from the SPL Token program (e.g. `AccountFrozen`, closed account, or other transfer-blocking condition on the destination token account) propagates as an instruction failure via `invoke_signed`: [2](#0-1) 

Unlike Initialize2, which validates the vault's own delegate/close-authority state at pool creation time, there is no check at withdraw time (or pool-creation time) that guarantees the user's *destination* token accounts for both coin and pc mints will remain transferable indefinitely. A user's own destination ATA could later be frozen by a mint's freeze authority (for either the coin or pc mint), or otherwise rendered non-transferable, independent of the AMM's control. Because `process_withdraw` couples the two transfers atomically with the LP burn, a problem affecting only one side of the pair (e.g., a frozen pc-token destination account) makes it impossible to redeem the healthy coin-side value too — the whole instruction reverts and the LP tokens remain stuck, permanently freezing the user's claim on both assets.

This mirrors the reported bug class: an operation that loops/couples multiple token transfers into one all-or-nothing action, where the misbehavior of a single token/account blocks recovery of value from the others.

### Impact Explanation
This can produce permanent freezing of LP-holder funds: a user's entire LP position (spanning both coin and pc assets) becomes unwithdrawable if either single leg of the pair transfer cannot complete, even though the value of the other leg's assets sitting in the vault would otherwise be fully redeemable. Since `SetParams`/pool status also gate whether withdrawals are permitted at all (`AmmStatus::from_u64(amm.status).withdraw_permission()`), there is no path within the withdraw instruction itself to partially settle in this scenario — the user's stake is stuck as long as the impaired leg remains impaired, which for a frozen token account can be indefinite.

### Likelihood Explanation
Likelihood is contingent on token behavior outside the AMM's control (e.g., mint freeze authority freezing a user's own token account, or other similar failure conditions), and is not directly triggerable by an attacker against a victim's account without a cooperating freeze authority. This lowers likelihood relative to a fully attacker-controlled trigger, but the condition is realistic given many SPL mints retain freeze authorities and pools are permissionlessly created against arbitrary mints, so this is a reachable Medium-severity design flaw rather than requiring any privileged action within the raydium-amm program itself.

### Recommendation
Decouple the two legs of `process_withdraw` so a user can specify (or the program can automatically fall back to) burning LP tokens and redeeming only the currently-transferable side, crediting/accounting for the un-transferable side separately (e.g., via an internal claim/accounting balance that can be withdrawn later once the destination account becomes transferable again), rather than reverting the entire operation when one `token_transfer_with_authority` call fails.

### Proof of Concept
1. A pool is created for `coin_mint`/`pc_mint` where `pc_mint` has (or later gains) a freeze authority.
2. User deposits and receives LP tokens normally via `Deposit`.
3. Freeze authority freezes the user's `user_dest_pc` (or any pc-side) token account after the fact.
4. User calls `Withdraw`; `process_withdraw` performs `token_transfer_with_authority` for the coin leg successfully, then attempts the pc leg, which fails because the destination account is frozen.
5. The whole instruction reverts (per Solana atomicity); the LP burn (`Invokers::token_burn` at `program/src/processor.rs:1805-1811`) never occurs, so the user's LP tokens — and thus their entire claim on both the coin and pc vault balances — remain permanently locked, even though the coin-side transfer alone would have succeeded.

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
