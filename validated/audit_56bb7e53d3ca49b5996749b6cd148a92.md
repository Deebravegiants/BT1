I have enough to finalize the analysis. The webhook `shop` field is read from the `X-Shopify-Shop-Domain` header but is not included in the HMAC-signed payload (`to_signable_string` returns only `@raw_body`), so `Registry.process` only proves the body was signed by the app's shared secret — it proves nothing about which shop the header claims to be from.

### Title
Webhook shop-domain header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed content [2](#0-1) . `Registry.process` validates only the HMAC over the body and then hands the unauthenticated `shop` header straight to the app's handler as trusted tenant identity.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just the raw JSON body — the shop domain header is never included in the signable string [4](#0-3) , [5](#0-4) .

This breaks the intended identity binding: `hmac_valid(body, api_secret_key) == true` is treated as proof of `shop == request.shop`, but the equality that is actually verified is only `hmac_valid(body, api_secret_key) == true`; `request.shop` is an independent, attacker-controlled header value not covered by that proof. Because the app's `api_secret_key` is the same across every shop that installs the app, any attacker who installs the app on their own store receives a genuinely-signed webhook (valid body + HMAC pair). They can replay that exact HTTP request to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim's shop domain). `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` forwards the forged `shop` value to `WebhookMetadata`, which the gem's own documentation describes as the trusted "shop domain of the webhook" for handlers to key their tenant-scoped logic on [6](#0-5) .

### Impact Explanation
Any handler that uses `data.shop` to scope database writes, session lookups, background jobs, or other tenant-specific side effects (exactly as the gem's own documented example does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`, [7](#0-6) ) can be made to process attacker-supplied body content under an arbitrary victim shop's identity. This is a cross-tenant confusion vulnerability rooted entirely in this gem: the gem asserts that a validated `Request` carries an authenticated `shop`, but its own `HmacValidator`/`to_signable_string` design never binds that field to the signature.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (an ordinary, unprivileged action for any Shopify merchant/developer) and be able to POST to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged account is required. This is a realistic, low-effort attack path for any internet user willing to install the app once.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the HMAC-verified content, or otherwise cryptographically tie the accepted shop to the specific webhook subscription/shop known to have registered that topic (e.g., cross-check `request.shop` against the shop associated with the stored session/subscription before invoking the handler), rather than passing the raw unauthenticated header through as trusted identity in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   ```
   POST /webhooks
   X-Shopify-Hmac-Sha256: <valid HMAC of body using the app's api_secret_key>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   X-Shopify-Topic: orders/create
   Body: {"id": 1, ...attacker-controlled order data...}
   ```
3. Attacker captures this request and replays it to the same endpoint, changing only the header:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this still returns `true` because it only re-hashes the (unchanged) body with the app's secret [8](#0-7) .
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's order data>, ...)` and performs tenant-scoped actions as though `victim.myshopify.com` sent this data.
