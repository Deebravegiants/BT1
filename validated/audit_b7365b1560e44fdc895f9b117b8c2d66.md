### Title
Webhook shop identity spoofing via HMAC verification that only covers the raw body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used to attribute and dispatch the webhook are taken from unauthenticated HTTP headers that are never included in the HMAC-signed material. This breaks the intended identity binding: `hmac == HMAC(secret, body)` should imply `shop == the shop that owns this body`, but the code only enforces the former.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` is read straight from the `hmac-sha256`/`x-shopify-hmac-sha256` header, and `shop`, `topic`, `webhook_id`, `api_version` are all read from separate headers with no cryptographic linkage to each other or to the body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)` — i.e., against the raw body only: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` after only checking the body HMAC: [4](#0-3) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the field host apps use to attribute/store the incoming data per-tenant: [5](#0-4) 

Because `shop-domain` is not part of the signed payload, any party that has captured one legitimately-signed `(raw_body, hmac)` pair for shop A's webhook (e.g., by controlling an endpoint that legitimately receives a webhook, or via a network vantage point that can see the plaintext request before it reaches the app's TLS-terminated listener/log/proxy) can resubmit the same `raw_body` + `hmac` with an altered `shopify-shop-domain` header claiming to be shop B. `HmacValidator.validate` still passes because it never examines the header, so the app processes and attributes shop A's data to shop B — a tenant-identity binding failure (`shop_claimed == shop_verified` is not enforced; only `hmac_verified == true` is).

### Impact Explanation
This is a cross-tenant data-integrity/attribution failure: an attacker can make a multi-tenant app process/store a legitimately-signed webhook body under an arbitrary target shop's identity, since `WebhookMetadata.shop` (used by host apps to key which merchant record to update, per the gem's own documented usage pattern) is not covered by the HMAC that supposedly authenticates the whole webhook. Depending on how the host app uses `data.shop` (e.g., to look up which merchant's DB row/session to mutate), this can lead to cross-tenant data corruption or information disclosure, satisfying the "cross-tenant access" criticality bar.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(raw_body, hmac)` pair — this is realistically obtainable by an entity that operates as (or has intercepted traffic to) a legitimate webhook receiver for any shop, since Shopify webhook payloads and HMACs are not shop-specific-secret-bound beyond the app's single `client_secret`. The barrier is capturing one genuine webhook delivery, not possessing `api_secret_key` or an access token, so this remains within the "unprivileged internet party" threat model requested.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) headers in the HMAC-signed material, or otherwise cryptographically bind them to the body before verification, so that `HmacValidator.validate` fails if any of these identity-critical fields are altered independently of the signed body.

### Proof of Concept
1. App owns a legitimate webhook endpoint and receives (or otherwise captures) a real Shopify webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
2. Attacker replays a POST to the app's webhook route with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this succeeds regardless of the `shop-domain` header value: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop-a's data>, ...)`, causing shop A's webhook content to be processed/stored under shop B's identity.
