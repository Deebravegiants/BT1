### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the signature exclusively against that body. The `shop` value that the registry hands to application webhook handlers is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the HMAC computation. Any party that can obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret` — e.g. by triggering a webhook on their own, legitimately-installed shop — can replay that exact body/HMAC pair while substituting an arbitrary victim shop domain in the header, and the gem will treat the request as authentic and hand the attacker-chosen shop to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read independently from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate_signature` computes the digest solely from `verifiable_query.to_signable_string` (the raw body) and compares it with `secure_compare`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authentication for the entire request, then forwards `request.shop` unchanged into the handler payload: [4](#0-3) 

The equality the gem implicitly claims to enforce is: `shop header value == shop that originated the signed body`. In reality only `hmac == HMAC(secret, raw_body)` is checked; the `shop` field is disjoint from the signed material, so the equality does not hold — any shop domain string can be attached to a validly-signed body from a different shop.

The library's own documentation instructs applications to treat `data.shop` as the trusted tenant identifier for dispatching downstream work: [5](#0-4) 
and `WebhookMetadata#shop` is the documented, typed field handed to every handler: [6](#0-5) 

Because the app's `client_secret` (and therefore the HMAC key) is shared across every merchant that installs the app, an attacker who installs the app on their own store obtains a source of validly-signed bodies. Since the body content for many topics is attacker-influenced (e.g., an `orders/create` webhook whose body is derived from an order the attacker placed in their own shop) and the shop binding is not cryptographically enforced, the attacker can forge events that `Registry.process` will accept as originating from any victim shop domain.

### Impact Explanation
This breaks the tenant/shop identity binding that downstream applications rely on `data.shop` for (as the gem's own documentation recommends). An attacker can cause the app to process webhook events under an arbitrary victim shop domain, leading to cross-tenant data confusion/injection — e.g., queuing background jobs, updating per-shop caches, or triggering shop-scoped business logic keyed on `data.shop` for a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be a legitimate (even trial) installer of the target app on their own shop, which for most public Shopify apps is trivial (self-service app installs are the norm). No leaked credentials, TLS interception, or privileged access are required — only a normal, unprivileged merchant account able to install the app and trigger a webhook-generating action.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the material covered by the HMAC verification, or otherwise cryptographically bind the `shop` header to the signed body (e.g., verify the header's shop matches the shop associated with the specific `webhook_id`/subscription via a server-side, authenticated lookup rather than trusting the header value at face value).

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and obtains a valid session/access token like any normal merchant.
2. Attacker performs an action that triggers a subscribed webhook topic (e.g., `orders/create`) on their own shop. Shopify sends:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw_body using the shared client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   body: <raw_body>
   ```
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` from step 2.
4. Attacker replays the same request to the app's public webhook endpoint but rewrites the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   keeping `raw_body` and `x-shopify-hmac-sha256` identical.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (`request.rb:35-38`, `hmac_validator.rb:26-31`) — validation passes.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` (`registry.rb:198-199`), even though this body/event never originated from `victim-shop.myshopify.com`.
