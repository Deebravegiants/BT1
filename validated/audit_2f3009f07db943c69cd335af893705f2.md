## Title
Webhook HMAC only covers the raw body; `shop`, `topic`, and `webhook_id` are taken from unauthenticated headers and used unbound - cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC of the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that determine *which tenant* and *which handler* the webhook is dispatched to are read straight from HTTP headers that are never included in the signed bytes. Because the HMAC secret (`Context.api_secret_key`) is the app's single, shared secret across every shop that installs the app (not a per-shop secret), any unprivileged user who installs the app on their own store can obtain a genuinely-signed `(body, hmac)` pair and replay it with attacker-chosen `shop-domain`/`topic` headers, causing the app to process a forged webhook as if it originated from a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body, not any header: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from headers, none of which are part of the signed material: [3](#0-2) 

`Registry.process` verifies only the HMAC and then dispatches the handler using these unbound header values, including `shop`, which is the tenant identifier for the app: [4](#0-3) 

The equality the code implicitly assumes is:
`hmac_valid(raw_body) == true` implies `(shop, topic, webhook_id) are authentic for this raw_body`

but the actual guarantee is only:
`hmac_valid(raw_body)` proves the *bytes of the body* were produced with the app's `api_secret_key` — it says nothing about which shop or topic they were originally sent for, since those fields never entered the HMAC computation.

Because `Context.api_secret_key` is a single value shared by the app across all installations (it is the app's `client_secret`, not a per-shop secret), any unprivileged user can:
1. Install the app on their own (attacker-controlled) development/trial shop.
2. Receive a genuine webhook from Shopify for their own shop with a body `B` and a valid `hmac(B)`.
3. Replay `(B, hmac(B))` to the app's webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain and/or the `x-shopify-topic` header with a different registered topic (as long as a topic exists whose handler tolerates body `B`, e.g. an empty-body `{}` payload).
4. The app calls `Utils::HmacValidator.validate` (line 190 in `registry.rb`), which passes because the body signature is genuinely valid, and then invokes the handler with the attacker-chosen `shop` and `topic`.

This lets the attacker inject cross-tenant webhook events for a shop they do not control and do not have credentials for, and/or trigger a different topic's handler than the one Shopify actually signed for that body — a credential/tenant boundary crossed entirely with self-obtained, unprivileged data.

### Impact Explanation
This is a cross-tenant authentication bypass at the webhook boundary: an attacker with no privileged access to a victim's shop or account can cause the host application to execute business logic (e.g. GDPR redact handlers, order/customer sync, uninstall handling — whatever the app registers) attributing it to a shop domain the attacker chooses, purely by controlling the header values, which is not something Shopify's own webhook delivery would allow. This matches the "Critical - cross-tenant access" category since the tenant boundary (`shop`) is not cryptographically bound to the authenticated payload.

### Likelihood Explanation
Likelihood is realistic for a determined but unprivileged attacker: creating a Shopify development store and installing any app that supports it is free and requires no special access; from there the attacker fully controls the raw HTTP request sent to the app's public webhook endpoint, since HTTP headers are entirely attacker-controlled at the transport layer while only the body is protected.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and `api_version` if relevant to business logic) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them (e.g., verify the values against Shopify's `X-Shopify-*` set only over an authenticated channel/mTLS, or require the app to independently validate the shop is currently installed via a signed offline session before trusting header-provided tenant identity in `Registry.process`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook (e.g., `topic=carts/update`, body `{}`), signed as `hmac = HMAC-SHA256(api_secret_key, "{}")`.
3. Attacker captures `(body="{}", hmac)` and crafts:
```
POST /webhooks
x-shopify-topic: customers/redact
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-hmac-sha256: <captured hmac>
x-shopify-webhook-id: any-value

{}
```
4. `ShopifyAPI::Webhooks::Request.new` parses these headers as-is (`lib/shopify_api/webhooks/request.rb:46-63`); `Utils::HmacValidator.validate` passes because it only checks `hmac` against the raw body `"{}"` (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the `customers/redact` handler with `shop: "victim-shop.myshopify.com"`, even though Shopify never signed this shop/topic combination.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
