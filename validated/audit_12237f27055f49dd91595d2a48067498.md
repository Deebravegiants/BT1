### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, never the `shop-domain`/`x-shopify-shop-domain` header value, yet `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity handed to the app's webhook handler after HMAC validation passes.

### Finding Description
`Request#to_signable_string` is defined as simply the raw body: [1](#0-0) 

`HmacValidator.validate` computes and compares the HMAC purely over `to_signable_string`: [2](#0-1) 

`Registry.process` gates on `Utils::HmacValidator.validate(request)` and, once it passes, forwards `request.shop` — sourced directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — to the app's handler as the tenant identifier, with no separate check that this header matches anything cryptographically bound to the body: [3](#0-2) [4](#0-3) 

The equality that is supposed to hold is: `shop authenticated by HMAC == shop delivered to the handler`. In this code, the HMAC only authenticates that the *body bytes* were produced by an entity holding `api_secret_key` — every merchant installation of a multi-tenant app shares the same `api_secret_key`, so any tenant of the app can compute a valid HMAC over an arbitrary body they choose (e.g., their own store's `orders/create` payload) and then deliver that request with the `shop-domain` header set to a *different* victim tenant's domain. Because the header is never part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` hands the handler a `WebhookMetadata` claiming the body originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding for webhook processing: a merchant who has legitimately installed the app (and therefore knows how to produce a validly-HMAC'd body using the shared `api_secret_key`, or can simply replay/observe any correctly signed webhook payload sent to their own endpoint from Shopify) can spoof events as coming from a completely different shop. Any app logic keyed off `WebhookMetadata#shop` (e.g. updating per-shop data, triggering `shop/redact`/`customers/redact`-style workflows, or writing into a shop-scoped data store) can be attributed to, or executed against, the wrong tenant — a cross-tenant confusion consistent with the "Critical - cross-tenant access" category, since it lets one tenant inject and misattribute events into another tenant's data path without ever needing that tenant's credentials.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even trial) app-installing merchant who can capture one real, validly-signed webhook delivery for their own store (webhooks are delivered to app-controlled endpoints in cleartext HTTP bodies with headers, so the attacker fully controls what they log) and then replay it with a modified `shop-domain` header. No access to `api_secret_key`, tokens, or Shopify infrastructure is needed — only observation of traffic the attacker's own store legitimately generates. This fits the "unprivileged internet user" threat model since it needs no elevated credentials.

### Recommendation
Include the shop/tenant identity (and ideally other webhook headers like `topic`, `webhook_id`) inside the HMAC-signed payload verification, or otherwise cryptographically bind the `shop-domain` header to the request before trusting it — e.g., verify that the resolved session/shop for the signed body matches an app-known installation record, or require the host application to independently confirm the shop belongs to an active installation before acting on `WebhookMetadata#shop`. At minimum, document/enforce that `shop-domain` must not be treated as authenticated purely because `HmacValidator.validate` succeeded.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and configures a webhook endpoint they control (or use ngrok to inspect traffic to a real endpoint).
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the attacker's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
   and body `raw_body`.
3. Attacker captures `raw_body` and the valid `x-shopify-hmac-sha256` value (the HMAC only covers `raw_body`, per `to_signable_string`).
4. Attacker crafts a new request to the app's webhook processing endpoint using the *same* `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it never checks the shop header. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's order payload>, ...)`, causing the app to process attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.
