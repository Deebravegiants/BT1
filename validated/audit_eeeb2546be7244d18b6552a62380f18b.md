Confirmed root-cause path: `Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) without being part of the signed payload. `Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:188-190`) and then forwards `request.shop` unchanged into `WebhookMetadata` (`lib/shopify_api/webhooks/registry.rb:198-199`), which the host app uses to attribute the webhook to a tenant.

### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook signature verification only authenticates the raw request body. The `shop` (tenant identifier) is read from an unauthenticated header and passed through to the host application as trusted data, allowing a merchant who possesses one genuinely-signed webhook (from their own store) to relabel it as belonging to a different shop and have it pass verification.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining `to_signable_string` to return only `@raw_body`: [1](#0-0) 
Meanwhile `shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string: [2](#0-1) 
`Registry.process` validates the HMAC (which only covers the body) and, once it passes, unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by the signature — to build the data handed to the app's webhook handler: [3](#0-2) 
`Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`, so it never binds the header-derived `shop` field into the signed value: [4](#0-3) 

The identity equality that should hold is: `shop attributed by handler == shop that actually generated/authorized the signed body`. Because `shop` is not part of `to_signable_string`, this equality is never enforced — the HMAC only proves "some install of this app produced this body with the shared `api_secret_key`", not "shop X produced this body." Since all shops installing the same app share the same `Context.api_secret_key`, a webhook body legitimately signed for the attacker's own shop is equally "valid" if replayed with a different `shop-domain` header claiming another tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to help the host application enforce: an attacker who is a legitimate but unprivileged merchant of the app (i.e., has the app installed on their own store, entitling them to receive genuine signed webhooks) can capture a valid `(body, hmac)` pair from their own shop's webhook delivery and re-POST it to the host application's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Registry.process` will accept it as valid because HMAC validation succeeds (the body/hmac pair is genuinely valid for the shared secret), and the handler will receive `WebhookMetadata` claiming the victim shop, causing the host application to write, delete, or act on data under the wrong tenant identity — a cross-tenant confusion/access condition rooted entirely in this gem's verification logic.

### Likelihood Explanation
Likelihood is high for any application that relies on this gem's webhook verification as the sole authentication for `shop` attribution (as the gem's own docs and `WebhookMetadata` usage pattern encourage): any merchant who installs the app can generate a legitimately-signed webhook body/hmac pair for their own shop, then directly call the app's public webhook endpoint with a forged `shop-domain` header — no MITM, leaked secrets, or privileged access required.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable representation validated against the HMAC, or otherwise cryptographically bind the shop-domain header to the signed payload before trusting `request.shop` for tenant attribution — mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed string.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook event, capturing the raw body `B` and the genuine `X-Shopify-Hmac-Sha256` header value `H` (valid because `HMAC(api_secret_key, B) == H`).
2. Attacker POSTs to the app's public webhook receiver endpoint with:
   - `X-Shopify-Hmac-Sha256: H`
   - `X-Shopify-Topic: <same topic>`
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it equal to `H`, so validation passes.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and performs tenant-scoped operations (e.g., data deletion/sync) against `victim-shop.myshopify.com`, even though the payload was never actually sent by or for that shop.
