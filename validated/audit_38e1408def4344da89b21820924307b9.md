Based on my research, I found a legitimate analog to the Django session-store DoS (CWE-770) in `pallet-ismp`'s request/response commitment storage.

### Title
Unbounded, unprunable growth of ISMP request/response commitment storage via zero-fee, non-expiring dispatches - (File: modules/pallets/ismp/src/impls.rs)

### Summary
`pallet_ismp::Pallet::<T>::dispatch_request` permanently inserts an entry into the `RequestCommitments` child-trie storage (and pushes a leaf into the offchain MMR/`OffchainDB`) for every outgoing request, with no cap or eviction mechanism, unlike `BoundedStateCommitments` elsewhere in the same pallet which the developers explicitly bounded and made self-evicting.

### Finding Description
`IsmpDispatcher::dispatch_request` only withdraws a relayer fee "if fee.fee != Zero::zero()" [1](#0-0) , meaning a `fee = 0` dispatch is an explicitly supported, documented path ("Optional relayer fees ... can also be set to zero if the application developers prefer to self-relay") [2](#0-1) . Every such dispatch still calls `Pallet::<T>::dispatch_request`, which computes the commitment, pushes the request into the offchain DB/MMR, and unconditionally inserts a `RequestMetadata` entry into `RequestCommitments` [3](#0-2) , backed by the `RequestCommitments` child-trie map defined in `modules/pallets/ismp/src/child_trie.rs` [4](#0-3) , which has no size cap or eviction logic.

The only way these entries are ever removed is `delete_request_commitment`, invoked when a relayer submits a proof-based timeout message for a request whose `timeout_timestamp` has passed. However, `DispatchPost`/`DispatchGet` accept `timeout = 0`, which is documented to mean the message "will never expire" [5](#0-4) , so such requests can never enter the timeout/prune path at all. Combined with `fee = 0`, no relayer has an economic incentive to ever submit a timeout proof for these entries even if a nonzero timeout were used.

This is in stark contrast to how the same pallet already treats state-machine commitments: `insert_bounded_state_commitment` explicitly caps entries per state machine (`state_machine_commitment_cap`) and evicts the oldest entries via a `StateCommitmentQueue` once the cap is exceeded [6](#0-5)  — demonstrating the team is aware unbounded state growth is a risk to guard against, yet `RequestCommitments`/`ResponseCommitments`/`RequestReceipts`/`ResponseReceipts` have no analogous protection.

### Impact Explanation
Any unprivileged application pallet built on `IsmpDispatcher` (e.g. `pallet-demo`'s message-sending call, or any real app pallet) can repeatedly dispatch `fee=0`, `timeout=0` POST/GET requests. Each call permanently grows the ISMP child-trie storage and the offchain MMR that all cross-chain messages (from every application on Hyperbridge) are proven against. Because this storage is never pruned, it grows monotonically with each dispatch, directly analogous to the Django session-store-filling DoS where each unique, low-cost request permanently consumes shared store capacity. Over time this degrades state-proof size/verification cost, full-node storage/sync requirements, and block execution overhead for the entire `pallet-ismp` message-dispatch pipeline — potentially impairing all state machines' ability to reliably process and prove ISMP messages ("a route unable to deliver messages" per the shared dispatch/commitment path).

### Likelihood Explanation
The only friction is the base transaction weight fee for submitting the dispatch extrinsic — there is no protocol-level fee, deposit, or rate limit tied to the number of outstanding `fee=0`/`timeout=0` commitments a single account (or many free/low-cost accounts) can create. This is a meaningfully weaker deterrent than a full economic fee, and any actor able to submit transactions (which is any unprivileged user/application) can trigger it repeatedly. I could not verify the exact base-weight fee schedule for `dispatch_request`-invoking extrinsics in this pass, which affects how cheap the attack is in absolute terms — this is a limitation of my review.

### Recommendation
Apply the same bounding/eviction pattern already used for `BoundedStateCommitments` to `RequestCommitments`/`ResponseCommitments`/request and response receipts (e.g., a per-account or global cap with FIFO eviction, or a mandatory minimum non-zero fee/deposit scaled to storage cost), and/or enforce a maximum permitted `timeout` value (reject `timeout = 0` "never expires" requests, or apply a protocol-wide default maximum lifetime) so every commitment is guaranteed to eventually become eligible for `delete_request_commitment` via the timeout path.

### Proof of Concept
1. Deploy/target any application pallet exposing `IsmpDispatcher::dispatch_request` (e.g. the pattern in `docs/content/developers/polkadot/dispatching.mdx`'s `send_message` example) [7](#0-6) .
2. Repeatedly submit `DispatchRequest::Post`/`Get` with `fee = 0` and `timeout = 0`.
3. Each call inserts a new, never-pruneable entry into `RequestCommitments` via `Pallet::<T>::dispatch_request` [3](#0-2)  and a leaf into the offchain MMR.
4. Repeat at scale (many accounts / low-value transactions) to grow the child-trie and offchain MMR without bound, since no timeout ever fires and no cap exists to evict old entries, unlike the explicit `MAX_STATE_MACHINE_COMMITMENTS` cap/eviction used for `BoundedStateCommitments` [8](#0-7) .

	pub fn dispatch_request(request: Request, meta: FeeMetadata<T>) -> Result<H256, ismp::Error> {
		let commitment = hash_request::<Pallet<T>>(&request);

		if RequestCommitments::<T>::contains_key(commitment) {
			Err(ismp::Error::Custom("Duplicate request".to_string()))?
		}

		let (dest_chain, source_chain, nonce) =
			(request.dest_chain(), request.source_chain(), request.nonce());
		let leaf_index_and_pos = T::OffchainDB::push(Leaf::Request(request));
		// Deposit Event
		Pallet::<T>::deposit_event(Event::Request {
			request_nonce: nonce,
			source_chain,
			dest_chain,
			commitment,
		});

		RequestCommitments::<T>::insert(
			commitment,
			RequestMetadata {
				offchain: LeafIndexAndPos {
					leaf_index: leaf_index_and_pos.index,
					pos: leaf_index_and_pos.position,
				},
				fee: meta,
				claimed: false,
			},
		);

		Ok(commitment)
	}

		/// Number of state commitments retained for `id`: the
		/// [`StateMachineCommitmentCap`] override if set, otherwise
		/// [`MAX_STATE_MACHINE_COMMITMENTS`].
		pub fn state_machine_commitment_cap(id: StateMachineId) -> u32 {
			StateMachineCommitmentCap::<T>::get(id).unwrap_or(MAX_STATE_MACHINE_COMMITMENTS)
		}

		/// Insert a state commitment into the bounded map. ISMP does not allow
		/// duplicate state updates so we don't have an overwrite path.
		///
		/// Appends the height to the per-chain [`StateCommitmentQueue`] and, once
		/// the chain's cap is exceeded, evicts oldest-first from the queue head.
		/// Evictions are limited to [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per
		/// call so a lowered cap drains over many insertions rather than in one.
		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}
