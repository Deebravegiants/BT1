Based on my investigation, the specific "donation inflates realBalance past reserveToken" bug class has already been identified and patched at the `Bonding.previewLtUntilGraduation` level (regression tests `test_donation_realBalanceExceedsReserveToken`, `test_donation_zapBuyStillSucceeds`, `test_donation_sellsStillWork` all pass). However, `Router._computeBuy` itself — the function that actually executes the capped buy — still contains the exact same unguarded subtraction that was the root cause of that regression, and it is **not** covered by an equivalent guard.

### Title
Donation-forced `reserveToken < realBalance` causes `Router._computeBuy`'s overflow-cap branch to underflow-revert, permanently freezing a curve that cannot reach its USD graduation threshold - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` computes the overflow-cap branch as `cappedReserveToken = reserveToken - tokensOut` (with `tokensOut` set to `realBalance` once the uncapped quote exceeds it). This subtraction assumes the protocol invariant `realBalance < reserveToken` always holds. That invariant is provably breakable by an unprivileged actor: `Bonding.previewLtUntilGraduation` already documents and guards against the *identical* condition (`realBalance >= reserveToken` after a Token donation to the pair) in its own math (`packages/contracts/src/Bonding.sol:728-729`), but `Router._computeBuy` — the function that runs on every actual capped buy, both via `Router.buy` and `Router.getAmountOut`/`previewBuy` — has no such guard.

### Finding Description
Any unprivileged holder of a launched `Token` can call `IERC20(token).transfer(pair, X)` directly (explicitly in-scope per the rules). This increases `Pair.tokenBalance()` (`realBalance`, a live `balanceOf` read) without touching the stored `_pool.tokenReserve` (`reserveToken`), which is only mutated by `Pair.swap` through `Router`. [1](#0-0) 

`Router._computeBuy`:
```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // <-- underflows if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

If a large enough donation drives `realBalance` above `reserveToken` (the test-suite's own `_stageDonationAttack` helper demonstrates draining enough curve supply that `donatedTokens > 250M`, i.e., `donated > LP_RESERVE`, is enough to flip `realBalance > reserveToken` — see [2](#0-1) ), then **any subsequent buy whose uncapped AMM quote (`tokensOut`) exceeds the (now-huge) `realBalance` is fine**, but the far more important case is the opposite: any buy that would otherwise legitimately trip the overflow cap (i.e., `tokensOut > realBalance` under the *uncapped* math) sets `tokensOut = realBalance`, and then `reserveToken - tokensOut` underflows because `tokensOut (=realBalance) > reserveToken`. Solidity 0.8's checked arithmetic reverts the entire transaction with a raw `Panic(0x11)` instead of the intended `OverflowCapDegenerate()` custom error.

Critically, `Bonding.canGraduate`'s supply trigger (`IPair.tokenBalance() == 0`) can never fire once tokens are donated into the pair (the balance only grows), so the *only* remaining path to graduation is the USD trigger. If the LT's `exchangeRate()` never appreciates enough to cross `graduationThresholdUsd`, the curve is permanently stuck in `Lifecycle.Curve` with buys reverting whenever the cap would otherwise bind. This is the exact scenario the protocol's own comment in `previewLtUntilGraduation` calls out ("Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg") — but that comment only protects the *preview* function, not the *execution* function (`Router._computeBuy`) that Zap actually calls through `Bonding.buy`. [3](#0-2) 

This is a direct analog of the CVE-2022-31081 bug class: two different code paths (`previewLtUntilGraduation`'s advisory quote vs. `Router._computeBuy`'s authoritative execution) interpret the *same* underlying condition (`realBalance` vs `reserveToken` ordering) inconsistently — one path was hardened, the other was not — producing a desynchronized outcome between what callers are told will happen and what actually happens on-chain.

### Impact Explanation
Once triggered, every buy that would need the overflow cap to bind reverts with an unhandled Panic instead of gracefully capping. Combined with the supply trigger being permanently unreachable after the donation, a curve whose LT price never appreciates past the USD threshold becomes permanently unable to complete its final capped buy and thus unable to graduate — freezing the remaining curve-raised LT and the 250M `lpReserve` tokens inside `Bonding`/`Pair` with no recovery path (no `triggerGraduation` success either, since `canGraduate` also depends on the same USD leg). This is a permanent freezing of trader and creator funds reachable by a single unprivileged token holder for the cost of the tokens they donate.

### Likelihood Explanation
Reachable by any address holding the launched `Token` (obtainable via a normal curve buy) with a single `IERC20.transfer(pair, amount)` call — no privileged role, no timing dependency beyond having bought enough supply from the curve to exceed the `LP_RESERVE` gap (250M tokens, i.e., depleting more than 25% of the virtual curve). The regression tests already prove this state is easily reachable in practice (`_stageDonationAttack`), confirming the preconditions are realistic, not theoretical.

### Recommendation
Apply the same guard used in `previewLtUntilGraduation` to `Router._computeBuy`: before computing `cappedReserveToken = reserveToken - tokensOut`, check `if (tokensOut >= reserveToken) { ... handle donation-inflated realBalance gracefully (e.g., treat cap as unreachable / skip to non-cap branch) ... }` instead of letting the subtraction underflow. Add a regression test analogous to `test_donation_realBalanceExceedsReserveToken` that specifically drives a *cap-binding* buy (not just a below-cap buy) after the donation and asserts it does not revert with a raw Panic.

### Proof of Concept
1. Launch a token via `Zap.createToken` (attacker or any trader).
2. As `drainer`, buy enough LT-denominated volume through `Zap.buy`/`Bonding.buy` to receive `> 250,000,000e18` tokens (mirrors `_stageDonationAttack` in `packages/contracts/test/Zap.t.sol:944-965`).
3. `Token(tokenAddr).transfer(pair, donatedTokens)` — a plain unprivileged ERC20 transfer. Now `IPair(pair).tokenBalance() > reserveToken` (confirmed directly by the existing `test_donation_realBalanceExceedsReserveToken`).
4. Ensure the LT `exchangeRate()` never crosses `graduationThresholdUsd` (attacker does nothing further; this is the default/flat-market state).
5. Any subsequent `Zap.buy` sized so that the *uncapped* AMM quote would exceed the current (donation-inflated) `realBalance` triggers the `if (tokensOut > realBalance)` branch in `Router._computeBuy`, and `reserveToken - tokensOut` underflows, reverting the entire buy with an unhandled Panic rather than `OverflowCapDegenerate`. Since the supply trigger is now permanently unreachable (`tokenBalance()` can never hit `0`) and the USD trigger never fires, the curve cannot progress to graduation, freezing curve-raised LT and the 250M `lpReserve` indefinitely.

*Note: I was unable to run this scenario against the test suite to confirm whether an existing test happens to catch this exact cap-binding-after-donation case; the located regression tests (`test_donation_zapBuyStillSucceeds`, `test_donation_sellsStillWork`) only exercise *non-cap-binding* buys/sells after the donation, not a cap-binding closing buy. A Devin session with repository access would be needed to execute Foundry tests and confirm the exact revert behavior end-to-end.*

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```
