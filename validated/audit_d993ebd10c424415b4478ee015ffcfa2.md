### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the `X-Shopify-Hmac-SHA256` header against the raw request body, using the app's `client_secret`. The `shop-domain` header — which is the value the gem hands to the application's webhook handler as the tenant identifier — is never included in the signed payload, so its authenticity is not verified. This breaks the identity binding `HMAC-verified(body) == body originated from claimed shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers with no cryptographic tie to the HMAC: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which is passed straight to the app's handler: [3](#0-2) 

Because the app-wide `client_secret` (not a per-shop secret) is used to sign every webhook body for every shop that installed the app, a valid `(raw_body, hmac)` pair generated for one shop remains a valid HMAC for that same body regardless of which `shop-domain` header accompanies it. The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" — implying shop-level authenticity — but the code only proves the body was signed by *some* installation of the app, not that it came from the shop named in the header: [4](#0-3) 

**Equality that should hold but doesn't:** `hmac_valid(body) == true` should imply `shop_header == shop_that_Shopify_actually_sent_this_for`. Since `shop` is excluded from `to_signable_string`, `hmac_valid(body)` is true for *any* forged `shop-domain` value as long as the attacker can produce (or replay) a body/HMAC pair signed with the app's shared secret (e.g., from webhooks delivered to their own store using the same app, or from a captured legitimate webhook payload with an unchanged body).

### Impact Explanation
An attacker who has (or can obtain) one valid `(raw_body, hmac)` pair for the target app — e.g., by installing the app on their own store and triggering a webhook, or capturing/replaying a previously delivered webhook — can resend that exact body to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will accept it as authentic and dispatch `WebhookMetadata` with `shop` set to the attacker-chosen victim tenant. Any handler logic that keys behavior (data writes, uninstall/GDPR handling, order processing, cache invalidation, etc.) off `data.shop` operates under an attacker-controlled tenant identity, meeting the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only unauthenticated HTTP access to the app's public webhook endpoint plus one legitimately-signed payload for the same app (trivially obtainable by installing the app on any store, including the attacker's own, since the signing secret is the app's `client_secret`, shared across all installs). No access token, leaked credential, or privileged account is needed.

### Recommendation
Include `shop`, `topic`, and ideally `webhook_id`/`api_version` in the signed string verified by `HmacValidator`, or at minimum have `Registry.process` cross-check `request.shop` against an expected/registered shop for the delivery before invoking the handler, and document that consuming apps must not trust `data.shop` without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-SHA256: H` (computed by Shopify using the app's `client_secret` over `B`).
2. Attacker POSTs to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged, still valid since only body is signed)
   - header `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - header `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H`.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, causing the app to process attacker-supplied order data as if it belonged to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
