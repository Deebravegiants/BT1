### Title
Under-reported `loaded_accounts_data_size` in the legacy `FeesOnlyTransaction` path materially underprices load-cost accounting when `define_ltds_fee_only_semantics` is inactive - ([File: svm/src/account_loader.rs])

### Finding Description
`load_transaction` in `svm/src/account_loader.rs` builds a `FeesOnlyTransaction` when `load_transaction_accounts` fails after validation succeeds. When `account_loader.feature_set.define_ltds_fee_only_semantics` is inactive, `loaded_accounts_data_size` is populated from `tx_details.rollback_accounts.data_size()` instead of the actual `LoadedTransactionDataSize` accumulator that was being tracked during `load_transaction_accounts`: [1](#0-0) 

`RollbackAccounts::data_size()` only sums the data length of the fee payer (and nonce, if present) — the two accounts that are rolled back on failure — explicitly ignoring every other account touched/loaded while walking the transaction's account keys (e.g., ALT-resolved accounts, program accounts, or other static accounts) before the load ultimately failed: [2](#0-1) 

This value flows unmodified into `ProcessedTransaction::loaded_accounts_data_size()` for the `FeesOnly` variant: [3](#0-2) 

and from there into `CommittedTransaction.loaded_account_stats.loaded_accounts_data_size`: [4](#0-3) 

which is subsequently used by `get_transaction_costs` to build the *actual* `TransactionCost` fed to `check_block_cost_limits`/the cost tracker: [5](#0-4) [6](#0-5) 

The `CostModel::calculate_loaded_accounts_data_size_cost` converts this byte count into a page-based cost that directly composes the block cost budget: [7](#0-6) 

An attacker (unprivileged, just broadcasting transactions) can construct a transaction whose fee payer/nonce accounts are tiny, but whose message references many large (e.g., multi-KB) accounts (directly or via address lookup tables) that are read/inspected by `load_transaction_account`/`load_account` during `load_transaction_accounts`, and craft it so that the load ultimately fails (e.g., referencing a missing/invalid program account, so `TransactionError::InvalidProgramForExecution`/`ProgramAccountNotFound` is returned) *after* those large accounts were already fetched. The real bytes fetched (and CPU/I/O work performed by the validator to fetch and inspect them) are not reflected at all in the reported `loaded_accounts_data_size` — only the (tiny) fee payer/nonce size is counted. This directly violates the stated invariant that loaded-accounts-data-size must upper-bound real work performed, and is confirmed by the existing repo test which documents this exact behavior: [8](#0-7) 

No existing guard (sanitization, lock, signature, nonce, status-cache, budget, or rent check) restores accuracy here — the discrepancy is a direct, deterministic function of the feature-gate state and the attacker's account-list construction, and is applied identically by every validator running with the same feature-set state (the flag is a cluster-wide feature, not a per-node config), so this does not cause cross-node divergence, but it does cause every validator to systematically under-cost these specific failed-load transactions relative to real I/O performed.

### Impact Explanation
This falls into "materially underpriced execution" / cost-model manipulation: an attacker can build failed-load transactions that force the validator to fetch/inspect large account data (real I/O and CPU work) while contributing only a few dozen/hundred bytes toward the block's loaded-accounts-data-size cost budget, whenever `define_ltds_fee_only_semantics` is inactive. This lets such transactions be packed far more densely into a block than the cost model's page-based cost intends, allowing a class of relatively cheap-to-broadcast, likely-to-fail transactions to consume disproportionate leader/validator load-time resources without a matching cost-tracker charge, which is a resource-metering underpricing issue rather than a straightforward double-spend or consensus split (since the feature-gate value is uniformly applied cluster-wide, all validators are equally underpriced, not divergent).

### Likelihood Explanation
The precondition is that `define_ltds_fee_only_semantics` is inactive on the target cluster (this is a feature-gated legacy code path explicitly slated for removal by "the fee-payer data size amendment to SIMD-186" per the comment on `RollbackAccounts::data_size()`). Given that comment and the test matrix explicitly exercising both `old_fee_only` and `simd186_fee_only` cases, this path is real, reachable, and requires no special privilege — only a well-formed transaction (achievable with ALTs or plain static account lists) that references large accounts and fails during load (trivial: reference a nonexistent/invalid program). No signature, nonce, or budget check blocks the account fetch from happening before the failure is detected, so the discrepancy is fully attacker-controlled and repeatable for as long as the feature remains inactive on a given cluster.

### Recommendation
Remove (or accelerate deprecation of) the legacy `tx_details.rollback_accounts.data_size()` fallback in `load_transaction` (`svm/src/account_loader.rs`), and always report the actual measured `LoadedTransactionDataSize` accumulated during `load_transaction_accounts` for `FeesOnlyTransaction`, regardless of `define_ltds_fee_only_semantics`. If backward-compatible activation sequencing is required, ensure the feature is activated across all clusters/tests using this SVM version before decommissioning the flag, and add an invariant test asserting `loaded_accounts_data_size >= rollback_accounts.data_size()` unconditionally.

### Proof of Concept
Extend the existing test `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs` (lines 3624-3770) with an explicit differential assertion:
```rust
// With define_ltds_fee_only_semantics = false, construct a transaction that:
// 1. references several large (e.g. 8192-byte) accounts in its static account list,
// 2. targets a missing/invalid program id so load_transaction_accounts fails
//    with TransactionError::ProgramAccountNotFound / InvalidProgramForExecution
//    only AFTER those large accounts were fetched via load_transaction_account.
// Then assert:
let processed = &output.processing_results[fail_program_id_index].as_ref().unwrap();
let reported_size = processed.loaded_accounts_data_size();
let real_bytes_touched: u32 = loaded_account_sizes.iter().map(|(_, sz)| *sz as u32).sum::<u32>()
    + loaded_fee_payer_size;
// Invariant expected: reported_size >= real_bytes_touched
// Actual (bug) with define_ltds_fee_only_semantics = false:
assert_eq!(reported_size, 0); // only rollback_accounts.data_size(), i.e., fee payer alone with 0 data
assert!(reported_size < real_bytes_touched); // demonstrates under-reporting
```
This differential test (toggling the `test_case(false)`/`test_case(true)` matrix already present) shows that with the feature off, `loaded_accounts_data_size` reports far less than the bytes actually fetched during the failed load, while with the feature on it correctly reports the full `LoadedTransactionDataSize`, confirming the invariant violation is feature-gate-specific and attacker-triggerable.

            total_size = total_size.saturating_add(account.data().len());

fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {

            .map_err(TransactionError::from)?;
    }

    Ok(())

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
