### Title
Unsanitized `shop` param lets `Oauth.begin_auth`/`auth_base_uri` redirect victims to an attacker-controlled host, leaking the anti-CSRF `state` nonce and enabling forced OAuth completion - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorize URL by calling `auth_base_uri(shop)` on the raw, caller-supplied `shop` string without ever invoking `Utils::ShopValidator.sanitize!`. Because `auth_base_uri` just does `"https://#{shop}/admin"` for any string that doesn't match the internal dev-server suffix, an attacker who controls the `shop` value passed to a host app's install-start endpoint can make the generated authorize URL (and the `state` nonce embedded in it) point at a host they control instead of a real Shopify domain.

### Finding Description
The expected binding is: `auth_base_uri(shop)` should only ever resolve to a host in `ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (i.e. `sanitize!(shop) == host_used_in_auth_route`). In the actual code: [1](#0-0) 

`begin_auth` never calls `ShopValidator.sanitize!` on `shop` before passing it to `auth_base_uri`: [2](#0-1) 

so for any `shop` not containing `.my.shop.dev`, the method returns `"https://#{shop}/admin"` verbatim, i.e. `host_used_in_auth_route == shop` (attacker-controlled), breaking the binding.

Attack flow:
1. Host app exposes `/install?shop=<value>` which forwards `shop` straight into `begin_auth` (per README's documented usage, no independent sanitize call is required by the doc since the gem is expected to validate).
2. Attacker crafts `shop=attacker.evil.com` and lures/redirects the victim's browser to the install endpoint.
3. `begin_auth` generates `state` (`SecureRandom.alphanumeric(15)`), sets a `SessionCookie` with that value in the victim's browser, and returns `auth_route = "https://attacker.evil.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=STATE&grant_options[]=..."`.
4. The victim's browser is redirected to the attacker's server, which now directly observes `state` (and `redirect_uri`, `client_id` — non-secret, but sufficient) because it, not Shopify, received the request.
5. The attacker independently completes a real installation on their own development shop, obtaining a genuine `code`, `hmac`, and `shop` signed by Shopify's real secret for their own tenant.
6. The attacker's fake authorize page then redirects the victim's browser to the app's real callback URL with `code=<attacker's own code>&shop=<attacker's own shop>&state=STATE&hmac=<valid>`.
7. In `validate_auth_callback`, `Utils::HmacValidator.validate(auth_query)` passes (HMAC is valid for the attacker's own shop/code — it was never intended to bind to who initiated the flow), and the `state == auth_query.state` check also passes because the victim's cookie still holds `STATE`, the same value the attacker captured in step 4. [3](#0-2) 

The result: the victim's browser session completes an OAuth flow that resolves to the attacker's tenant/session rather than failing or belonging to the shop the victim intended — a forced/attacker-steered OAuth completion enabled purely by the missing shop sanitization in `begin_auth`/`auth_base_uri`. None of the existing guards (`Context.setup?`, `Context.private?`, `HmacValidator.validate`, the `state` equality check) block this, because they only validate the callback's internal consistency, not that the authorize redirect itself went to a genuine Shopify domain.

### Impact Explanation
This matches the High-severity category "session fixation or forced OAuth completion." The attacker forces a victim's browser/session flow to be hijacked toward a tenant the attacker controls, without ever needing `api_secret_key` or any credential. It does not directly hand over another merchant's access token (the HMAC/secret still gates the token exchange itself), so it stops short of the Critical "forged callback accepted for arbitrary shop" bar, but it does break the intended one-time, single-shop binding of the `state` nonce and is repeatable against any victim who can be lured to the install link.

### Likelihood Explanation
Preconditions are minimal and match how the gem is documented to be used: a host app with `Context.setup` completed, non-private mode, and an install-start endpoint that forwards a `shop` query parameter into `begin_auth` (standard integration pattern shown in the README). The attacker needs no secrets — only the ability to (a) send an HTTP link to a victim and (b) run their own server and complete their own legitimate install on a shop they control. This is fully repeatable per victim.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `begin_auth` before constructing `auth_base_uri`, raising `Errors::InvalidShopError` for any `shop` that doesn't resolve to a trusted Shopify domain, exactly as is already done elsewhere for domain validation in `lib/shopify_api/utils/shop_validator.rb`.

```ruby
def test_begin_auth_rejects_untrusted_shop

  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.evil.com", redirect_path: "/callback")
  end

def test_begin_auth_currently_returns_untrusted_host  # demonstrates the bug pre-fix
  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.evil.com", redirect_path: "/callback")
  uri = URI(result[:auth_route])
  assert_equal "attacker.evil.com", uri.host   # should have raised instead
  # assert `state` param is present in the query, proving it is disclosed to a non-Shopify host
  assert_includes URI.decode_www_form(uri.query).to_h.keys, "state"
end
```
Both sides of the binding to assert: expected `URI(auth_route).host` ∈ `ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` vs. actual `URI(auth_route).host == "attacker.evil.com"` (the unsanitized input), demonstrating the divergence exploited above.

```ruby
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
