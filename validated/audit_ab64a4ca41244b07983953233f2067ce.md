### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop` (`x-shopify-shop-domain`) header that identifies which merchant/tenant the webhook belongs to is read independently and is never included in the signed material. Because the app-shared `api_secret_key` is common to every shop that installs the app, any merchant that legitimately installs the app can obtain validly-signed webhook bodies and then present the same body with a different `shop-domain` header to the app's webhook endpoint, passing HMAC validation while impersonating an unrelated tenant.

### Finding Description
The webhook signature check compares the received `hmac-sha256` header against a signature computed over `to_signable_string`, which returns only the raw body: [1](#0-0) 

The `shop` field is parsed from a separate, unauthenticated header and is not part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string`, so it can never detect a mismatched `shop` header: [3](#0-2) 

`Registry.process` raises only if the HMAC check fails, then forwards `request.shop` directly to the handler as the tenant identifier for the webhook payload, without any additional binding to the signed body: [4](#0-3) 

The identity binding that should hold is:
`shop header used by handler == shop bound inside the HMAC-signed payload`

but in this implementation:
`shop header used by handler != anything covered by the HMAC signature`

Since `api_secret_key` is one shared secret across all shops that install the app (it is not a per-shop secret), any shop that installs the app can generate a body+HMAC pair that is valid under that same secret. An unprivileged attacker who installs the app on their own store receives real, validly-signed webhook deliveries. They can then replay that exact body/HMAC pair to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` will still return `true` because it never inspects the `shop` header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the tenant identity binding that webhook consumers rely on: apps built on this gem generally trust `WebhookMetadata#shop` (backed by the "HMAC-validated" request) as the authoritative tenant for the payload, since the surrounding code explicitly validates the HMAC before dispatch (`registry.rb` line 190). An attacker-controlled merchant install can therefore inject data, trigger side effects, or overwrite state attributed to an arbitrary victim shop inside the host application, i.e. cross-tenant access/write despite passing signature verification. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires installing the app on an attacker-owned development/trial store (a normal, unprivileged action available to any internet user for public apps) to obtain a validly-signed webhook, and then sending an HTTP request to the app's own public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only the ability to receive one legitimate webhook delivery from the target app, which is inherent to installing it.

### Recommendation
Bind the tenant/shop identity into the material that is actually verified:
- Include `shop` (and ideally `topic`/`webhook_id`) in `to_signable_string`, or
- Have `Registry.process`/the handler cross-check that the `shop` header matches an expected/allow-listed shop for the given installation context (e.g., compare against the shop the app currently has an active session/access token for) before trusting `request.shop`, rather than relying solely on the raw-body HMAC to authenticate the header-derived tenant.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`; the app is configured with a single shared `api_secret_key`.
2. Shopify sends the attacker a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical request to the app's webhook endpoint, but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are unchanged (they never read `shop`), so `Utils::HmacValidator.validate` still returns `true`.
5. `ShopifyAPI::Webhooks::Registry.process` proceeds and invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host application to act as though the payload originated from `victim.myshopify.com`.
