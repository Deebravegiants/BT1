Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body [1](#0-0) , while the `shop` value that is later trusted and passed to the app's handler is read straight from an HTTP header that is never included in that signature [2](#0-1) .

### Finding Description
`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the raw body) and `request.hmac` (derived from the `hmac-sha256` header) [3](#0-2) [4](#0-3) . The signable string used for verification is `@raw_body` only [1](#0-0) . After the HMAC check passes, `Registry.process` builds `WebhookMetadata` using `request.shop`, which is taken verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) [5](#0-4) . `WebhookMetadata.shop` is then handed to the host app's `WebhookHandler#handle` as the authoritative tenant identifier [6](#0-5) .

This breaks the binding `authenticated(bytes) == identity(shop)`: the HMAC authenticates the body bytes but not the `shop-domain` header. Any party in possession of one valid `(body, hmac)` pair signed with the app's secret for shop A (e.g., because they legitimately operate shop A and captured/replayed their own genuine webhook) can resend the identical body and HMAC while substituting an arbitrary value in the `shop-domain` header. `HmacValidator.validate` will still succeed because it never inspects the header, and the app-level handler will process the payload under the attacker-chosen `shop`, not the shop that actually produced the signed body.

### Impact Explanation
This is a cross-tenant integrity violation: an app that keys per-tenant business logic or data writes off `WebhookMetadata#shop` (e.g., "look up shop by this shop domain, then apply the order/customer data in `body`") can be made to apply data captured from shop A's webhook into shop B's tenant context, since the gem provides no protection against a mismatched header/body pairing. This matches the "Critical - cross-tenant access" impact category, because the shop identity used for data attribution is decoupled from the cryptographically verified content.

### Likelihood Explanation
The attacker needs a valid `(raw_body, hmac)` pair signed by the app's real `client_secret` for at least one shop — trivially obtainable by any unprivileged merchant who installs the target app on their own store and captures one of their own legitimate webhook deliveries. No access to the app's `client_secret`, access tokens, or any other shop's credentials is required; only the ability to replay an HTTP POST with a modified header. Likelihood is Medium-to-High since it only requires being a legitimate (even trial) install of the app.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values inside the signed payload used by `to_signable_string`, or otherwise cryptographically bind the shop domain to the signature (e.g., verify the header's shop against a shop known to be associated with the webhook subscription/registration, or require the HMAC to cover a canonical string that includes the header values). At minimum, document that host applications must independently correlate `WebhookMetadata#shop` with a shop they have on record before trusting it for tenant-scoped writes.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker controls this shop and can trigger a webhook (e.g., `orders/create`) to their own endpoint, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header value.
2. Attacker sends a POST request directly to the app's webhook endpoint with:
   - `raw_body` unchanged (still validly signed for that body),
   - `X-Shopify-Hmac-Sha256` header unchanged,
   - `X-Shopify-Shop-Domain` header changed to `shop-b.myshopify.com` (a different tenant).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` → passes, because validation only hashes `@raw_body` [1](#0-0) .
4. `WebhookMetadata.shop` is set to `shop-b.myshopify.com` [5](#0-4) , and the host app's handler processes shop A's payload under shop B's identity.
