### Title
Duplicate `erc20TokenAddresses` entries allow one real balance change to back two independent value-creation paths, minting unbacked shielded/on-chain value - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact()` enforces a per-token-index balance equation intended to guarantee that any change in the contract's actual token holdings is fully and exactly accounted for by shielded (off-chain) or on-chain UTXO value created in that same call. Because the equation is applied independently *per array index* of `circomData.erc20TokenAddresses` rather than per unique token, and nothing in `contracts/HinkalHelper.sol` or `contracts/CircomDataBuilder.sol` enforces uniqueness of that array, an attacker/relayer can list the same ERC-20 address twice. The single real balance delta for that token is then reused to satisfy the balance equation at both indices, letting the caller mint a second, unbacked chunk of shielded value.

### Finding Description
In `contracts/Hinkal.sol:96-146`, for each index `i` in `circomData.erc20TokenAddresses`:
```solidity
balanceDif = newBalances[i] - oldBalances[i] (+ msg.value for native)
require(balanceDif >= slippageValues[i]);
...
require(balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount);
``` [1](#0-0) 

`oldBalances`/`newBalances` come from `getBalancesForArray(circomData.erc20TokenAddresses)`, which is queried once before and once after the internal/external action [2](#0-1) . If the same token address appears at two different indices `i` and `i'`, `oldBalances[i] == oldBalances[i']` and `newBalances[i] == newBalances[i']`, so `balanceDif` is identical at both indices — it reflects only **one** real change in the contract's token balance.

Neither `dimensionsCheck` nor any other validation in `contracts/HinkalHelper.sol:64-171` requires `circomData.erc20TokenAddresses` to contain distinct addresses; it only checks array lengths match `dimensions.tokenNumber` [3](#0-2) . The token addresses are simply re-encoded as public circuit inputs in `formBasicInput` with no distinctness constraint applied on the Solidity side [4](#0-3) .

With a duplicate entry for token `T` at indices `i` (with `onChainCreation[i] = false`) and `i'` (with `onChainCreation[i'] = true`, only allowed for external-action transactions per `checkOnchainCreation` in `contracts/HinkalHelper.sol:173-202`), a single real balance increase `D` for `T` can independently satisfy:
- index `i`: `D == amountChanges[i] + 0` → proves `D` worth of new off-chain shielded UTXOs (whose conservation across inputs/outputs is separately enforced by the ZK circuit, tied to `amountChanges[i]`), and
- index `i'`: `D == 0 + utxoAmount(T)` → creates an *additional* on-chain UTXO commitment worth `D` for the same token, inserted via `insertCommitments` with no nullifiers required (since `onChainCreation` is set, `checkOnchainCreation` explicitly zeroes out the nullifier requirement) [5](#0-4) .

The net effect is `2D` of claimed shielded/on-chain value created in the tree from only `D` of tokens actually held by the contract — breaking the intended invariant "change in on-chain token balance == change in off-chain UTXOs + change in on-chain UTXOs" stated explicitly in the code comment at `contracts/Hinkal.sol:134-146`.

### Impact Explanation
This is unbacked minting of shielded/on-chain value inside the protocol's UTXO accounting, directly analogous to the Zetachain `MintCoins()` bug: value is created without any corresponding decrease elsewhere, breaking the core solvency invariant of the mixer. Once minted, the unbacked UTXO(s) can later be spent/withdrawn by the attacker, draining real backing funds deposited by other users. This maps to Critical impact: minting shielded value without backing, enabling eventual theft of pooled funds.

### Likelihood Explanation
The attack requires only an unprivileged EOA (or relayer) calling `transact()` with a crafted `circomData` containing a duplicated token address and a valid ZK proof for the chosen `amountChanges`/output-commitment values (the circuit only enforces conservation of the off-chain UTXO leg, not cross-index token uniqueness). It also requires the transaction to go through the external-action path (`externalActionId != 0`) so `onChainCreation` can be set to `true`, which is a normal, permissionless code path (e.g., swap/emporium external actions), not an admin-only function. No special privileges are needed, making this practically exploitable by any user able to construct a matching proof.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck` (or in `transact`), rejecting any transaction where the array contains duplicate token addresses, before the per-index balance equation is evaluated. Alternatively, aggregate `balanceDif`, `amountChanges`, and `utxoAmount` per unique token address (deduplicating indices) rather than trusting a one-to-one mapping between array index and independent balance evidence.

### Proof of Concept
Conceptual reproduction (would need to be executed against the deployed contracts with a matching Circom proof for the chosen public inputs):
1. Register/use an external action that performs a real swap or transfer bringing exactly `D` extra units of token `T` into the `Hinkal` contract.
2. Construct `circomData` with:
   - `erc20TokenAddresses = [T, T]`
   - `onChainCreation = [false, true]`
   - `amountChanges = [D, 0]` (with a valid off-chain proof making the off-chain UTXO outputs sum to `D` more than inputs)
   - `outCommitments`/on-chain UTXO data at index `i'` describing a new UTXO of amount `D` for token `T`, with `inputNullifiers[i'] = [0,...]`
   - `slippageValues` satisfied for both indices given `balanceDif = D` at both.
3. Call `Hinkal.transact(a, b, c, dimensions, circomData)`.
4. Observe: the transaction succeeds, both the off-chain shielded value (`D`) and the on-chain UTXO commitment (`D`) are inserted (`insertCommitments`), while the contract's real token balance only increased by `D` once — total newly claimable shielded value is `2D` against `D` of real backing.

Note: I was not able to fully inspect the Circom circuit (`circuits/MainEVMCircuit.circom`) side within the available iterations to confirm there is no implicit uniqueness/ordering constraint on `erc20TokenAddresses` baked into the circuit logic; this should be verified against the actual circuit template before treating this as fully confirmed, though the Solidity-side check (`dimensionsCheck`/`checkOnchainCreation`) shows no such constraint exists at the contract layer.
