### Title
Path traversal in `newHTTPFetcher` allows escaping the configured `WorkflowFetcher` base path - (File: core/services/workflows/syncer/v2/fetcher.go)

### Summary
The HTTP variant of the workflow-artifact fetcher (`newHTTPFetcher`) cleans the caller-supplied request URL but never verifies that the final resolved path still lives under the configured base path, unlike its sibling `newFileFetcher`, which performs an explicit prefix check. This mirrors the LoLLMs `open_personality_folder` bug class: a "sanitize" step (`filepath.Clean`) is applied, but the code omits the actual containment check, so a crafted relative path with enough `../` segments escapes the intended base directory/base URL path.

### Finding Description
`NewFetcherFunc` builds one of two fetchers based on the configured `CRE.WorkflowFetcher.URL` scheme [1](#0-0) .

For `file://` URLs, `newFileFetcher` cleans the incoming `req.URL`, joins it to `basePath`, and then explicitly rejects any resolved path that is not prefixed by `basePath + separator`: [2](#0-1) 

For `http://`/`https://` URLs, `newHTTPFetcher` only cleans the path and joins it into the base URL's path with no containment check afterward: [3](#0-2) 

`filepath.Clean` followed by `filepath.Join(u.Path, cleanPath)` does not prevent traversal beyond `u.Path` when `cleanPath` contains more `..` segments than there are path components in `u.Path`. For example, with base URL path `/workflows` and `req.URL = "../../secret"`, `filepath.Join("/workflows", "../../secret")` resolves to `/secret` — completely outside the intended `/workflows` prefix on the target host. The comment "Clean the path to prevent directory traversal" is misleading: cleaning alone does not enforce containment, exactly as in the LoLLMs `sanitize_path`-but-no-boundary-check bug.

`req.URL` here is the artifact locator carried in `ghcapabilities.Request`, which is populated per-workflow when the syncer fetches an artifact (e.g., workflow binary/config) identified by a URL that is workflow-owner-supplied data, not something the node operator controls at request time — making this reachable by an unprivileged workflow owner rather than requiring operator/admin access.

### Impact Explanation
An attacker who controls the artifact URL for their own workflow can cause the node to issue GET requests to arbitrary paths on the configured `WorkflowFetcher` host, escaping the intended artifact directory. Depending on what else is exposed on that host (e.g., internal path-based access controls, other tenants' artifacts, or an internal admin path on the same server), this can result in disclosure of data the requester should not be able to read — a direct analog to the CVE-2024-6985 personality-folder disclosure. Confidentiality impact is Medium; there is no code execution or write capability created by this alone.

### Likelihood Explanation
Exploitation only requires the CRE workflow syncer to be configured with an `http`/`https` `WorkflowFetcher.URL` (a supported, documented configuration) and for an attacker to control/register a workflow whose artifact URL is passed through to the fetcher. No special node privileges are required beyond being able to register/own a workflow that gets synced.

### Recommendation
Apply the same containment check used in `newFileFetcher` to `newHTTPFetcher`: after computing `u.Path = filepath.Join(u.Path, cleanPath)`, verify that the resulting path is still prefixed by the original base path (with a separator boundary) before issuing the HTTP request, rejecting the request otherwise.

### Proof of Concept
1. Configure `[CRE.WorkflowFetcher] URL = "https://workflow-server.example.com/workflows"`.
2. Trigger a fetch with `ghcapabilities.Request{URL: "../../secret-path"}` (as would occur if a workflow's registered artifact URL contains such a value).
3. `newHTTPFetcher` computes `cleanPath = "../../secret-path"`, then `u.Path = filepath.Join("/workflows", "../../secret-path")` = `/secret-path`, and issues `GET https://workflow-server.example.com/secret-path` — outside the intended `/workflows` scope, with no error raised (contrast with the `file://` fetcher test at `fetcher_test.go:443-448`, which explicitly asserts traversal is rejected for the file scheme but no equivalent test/guard exists for the HTTP scheme).

// NewFetcher creates a new FetcherFunc based on the provided URL configuration
// The implementation supports both file and HTTP(S) URLs and bypasses the gateway
func NewFetcherFunc(baseURL string, lggr logger.Logger) (types.FetcherFunc, error) {
	if baseURL == "" {
		return nil, errors.New("baseURL cannot be empty")
	}

	u, err := url.Parse(baseURL)
	if err != nil {
		return nil, fmt.Errorf("invalid URL: %w", err)
	}

	switch u.Scheme {
	case "file":
		// Ensure the basePath is absolute
		if !filepath.IsAbs(u.Path) {
			return nil, fmt.Errorf("basePath must be an absolute path, got: %s", u.Path)
		}
		return newFileFetcher(u.Path, lggr), nil
	case "http", "https":
		return newHTTPFetcher(baseURL, lggr), nil
	default:
		return nil, fmt.Errorf("unsupported URL scheme: %s", u.Scheme)
	}
}
