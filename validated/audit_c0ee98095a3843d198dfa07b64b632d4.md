### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over the body only, then trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . This breaks the intended binding `hmac_signed_bytes == tenant_identity_bytes`: the HMAC only authenticates the payload bytes, not the shop that the payload is attributed to.

### Finding Description
The core equality this gem is supposed to enforce for tenant isolation is:

`HMAC-covered bytes == bytes used to determine which shop/tenant the webhook belongs to`

Instead, the gem enforces:

`HMAC-covered bytes == @raw_body only`, while `shop` (and topic/webhook_id/api_version) are taken from `shopify-shop-domain` / `x-shopify-shop-domain` headers that are never fed into `to_signable_string`.

Because Shopify webhook HMACs are computed with the **app's `client_secret`**, which is shared across every shop that has the app installed, any merchant who installs the app on their own store legitimately receives real webhooks (e.g. `app/uninstalled`, `orders/create`) whose body+HMAC pair is valid under that same shared secret. That attacker-merchant can then replay the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop). `Utils::HmacValidator.validate` in `Registry.process` will succeed because it only checks the body against the shared secret [4](#0-3) , and the forged `shop` value flows straight into the app's webhook handler via `WebhookMetadata` [5](#0-4) .

Any host application built on this gem that uses `data.shop` from the handler callback to identify which tenant's session/data to act on (a normal, expected usage pattern this gem's own docs and tests demonstrate, e.g. `assert_equal(@shop, data.shop)` in `test/webhooks/registry_test.rb` [6](#0-5) ) will process a request as belonging to the wrong shop, since the gem provides no cryptographic binding between the authenticated payload and the claimed shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker with a valid (self-owned) shop installation of the target app can forge webhook deliveries that the app's own gem-provided verification accepts as authentic for a shop of the attacker's choosing. Depending on the handler's logic, this can drive state changes (e.g., simulating `app/uninstalled` for a victim shop, corrupting order/customer data attribution, or triggering side effects keyed off `data.shop`) attributed to a tenant the attacker does not control. This matches the Critical bucket of "cross-tenant access" since the gem's identity binding for the webhook's tenant is not covered by any cryptographic guarantee.

### Likelihood Explanation
Moderate-to-high: the attacker only needs their own real, currently-installed instance of the target app (any developer/merchant can install most public apps or build a personal store) to receive at least one legitimately signed webhook, then replay it with a substituted `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only normal use of the app as any customer.

### Recommendation
Bind the shop (and other routing-relevant fields) into the HMAC-signed material, or otherwise cryptographically bind them to the verified session:
- Require the host application to independently verify that `request.shop` corresponds to a shop with the app installed (e.g., cross-check against a stored, previously-provisioned session for that shop) before trusting the payload's shop attribution — but the gem should also warn callers via docs/API that `shop`, `topic`, `webhook_id`, `api_version` are not integrity-protected by the HMAC.
- Preferably, include the shop-domain and other identifying headers in `to_signable_string` if Shopify's downstream verification model allows it, or expose an API that requires callers to separately authenticate the shop before processing, since currently `Registry.process` implicitly treats `Utils::HmacValidator.validate(request)` as sufficient authorization for all fields read off `request`, including `shop`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receives a real webhook delivery, e.g.:
   - Body: `{"id":123,...}`
   - Header `x-shopify-hmac-sha256`: valid HMAC-SHA256(body, app's `client_secret`)
   - Header `x-shopify-shop-domain`: `attacker.myshopify.com`
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [4](#0-3) [1](#0-0) .
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the app's handler, which treats the event as belonging to the victim tenant [8](#0-7) .

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
