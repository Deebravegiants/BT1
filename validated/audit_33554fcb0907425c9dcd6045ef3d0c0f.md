This confirms the claim in full detail. The HTTP server layer (`httpserver.go`) enforces only a request-size limit and optional JWT extraction — there is no generic incoming rate limiter or authentication gate at that layer; JWT enforcement is delegated entirely to individual handlers (as seen in the HTTP capabilities v2's `httpTriggerHandler.authorizeRequest`). The Confidential Relay handler implements no such check.

Tracing `gateway.ProcessRequest`: for non-legacy (JSON-RPC) requests, the handler is resolved purely by `jsonRequest.ServiceName()` with no call to `msg.Validate()` (that only happens in the `else` branch for legacy DON-ID requests) [1](#0-0) . The resolved handler's `HandleJSONRPCUserMessage` is invoked directly [2](#0-1) .

The Confidential Relay handler's `HandleJSONRPCUserMessage` performs only ID-length checks before creating an `activeRequest` and fanning out to the DON — no auth, no per-caller quota [3](#0-2) . `newActiveRequest` inserts unconditionally into the unbounded `map[string]*activeRequest` keyed by caller-supplied `req.ID` [4](#0-3) . The only rate limiters in the struct (`globalNodeRateLimiter`, `perNodeRateLimiters`) are consumed exclusively in `HandleNodeMessage`, gating DON *node* responses, not incoming user requests [5](#0-4) . This is architecturally identical to what the report describes, and I verified there's no other gate (HTTP-server-level rate limiting, generic auth middleware) that would prevent an unauthenticated caller from reaching this code path repeatedly with unique IDs. The comparison points (bounded `RequestCache` elsewhere, JWT+rate-limited HTTP trigger handler) are also accurate as cited in the original report.

Audit Report

## Title
Unauthenticated caller can cause unbounded per-request memory growth in the Confidential Relay gateway handler - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

## Summary
The gateway's Confidential Relay handler accepts JSON-RPC user requests over the internet-facing `/user` gateway endpoint without any authentication, authorization, or per-caller quota, and stores state for every accepted request in an unbounded in-memory map (`activeRequests`) until a fixed 30-second timeout elapses. An unauthenticated client can flood the endpoint with unique request IDs to grow this map without bound, exhausting gateway process memory.

## Finding Description
`gateway.ProcessRequest` routes JSON-RPC (non-legacy) requests to a handler by service name alone; the `msg.Validate()`/signature check only runs for legacy DON-ID requests (`msg.Body.DonID != ""`), so JSON-RPC requests routed to the Confidential Relay handler bypass that check entirely [8](#0-7) . `HandleJSONRPCUserMessage` in the Confidential Relay handler performs only trivial ID-length validation (empty / >200 chars) before creating a tracked `activeRequest` and fanning it out to all DON members [3](#0-2) . `newActiveRequest` inserts unconditionally into `h.activeRequests`, a `map[string]*activeRequest` with no size cap, keyed solely by attacker-controlled `req.ID` [4](#0-3) . The handler's only rate limiters, `globalNodeRateLimiter` and `perNodeRateLimiters`, throttle DON node *responses* in `HandleNodeMessage`, not incoming user requests [5](#0-4) . Entries are removed only by a once-per-second sweep once they exceed `requestTimeout` (default 30s) [7](#0-6) [9](#0-8) . The HTTP server layer only enforces request-size limits and optionally extracts a JWT (never validated at that layer) [10](#0-9) , so nothing upstream of the handler blocks unauthenticated, high-rate traffic. This contrasts with the bounded `common.RequestCache` (`maxCacheSize`, rejects when full) and the JWT-authenticated, dual-rate-limited HTTP capabilities v2 trigger handler used elsewhere in the same gateway codebase, confirming this is a gap specific to the Confidential Relay handler rather than an inherent design constraint.

## Impact Explanation
This is a genuine, code-confirmed Denial-of-Service vector: any network client that can reach the gateway's public `/user` endpoint and knows the public method constants `MethodSecretsGet`/`MethodCapabilityExec` can create unbounded `activeRequest` entries (each holding a request, labels, and responses map, plus triggering a fan-out RPC to every DON member) without any credential. Sustained flooding at a rate exceeding the 1-second cleanup sweep's ability to expire 30-second-old entries grows memory usage without bound, potentially exhausting gateway process memory and disrupting confidential-relay service availability for legitimate workflow executions. This maps to an in-scope availability/DoS impact against the gateway's request-handling path.

## Likelihood Explanation
Likelihood is high: no signature, JWT, or DON membership is required to reach `HandleJSONRPCUserMessage`; only network reachability to the gateway's user port and knowledge of public method name constants. The attacker's per-request cost (a small HTTP POST) is far below the server's cumulative cost (map entry + fan-out RPC to every DON member per request), making the attack cheap and easily repeatable.

## Recommendation
Bound `activeRequests` with a maximum concurrent-entry cap that rejects new requests once full (mirroring `common.RequestCache.maxCacheSize`'s "request cache is full" behavior), and/or add per-sender and global incoming rate limiting to `HandleJSONRPCUserMessage` before `newActiveRequest` and `fanOutToNodes` are invoked, consistent with the JWT authentication and dual rate limiting already implemented in the HTTP capabilities v2 trigger handler.

## Proof of Concept
1. Identify the gateway's public `/user` HTTP endpoint and a configured Confidential Relay DON service name.
2. Loop sending JSON-RPC POSTs with a unique `id` each time and no `Authorization` header, e.g. `{"jsonrpc":"2.0","id":"<uuid>","method":"confidentialrelay_secretsGet","params":{}}`.
3. Each request passes the ID-length checks in `HandleJSONRPCUserMessage`, is inserted into `h.activeRequests` via `newActiveRequest`, and triggers `fanOutToNodes` to every DON member — with no auth or per-sender throttling anywhere on this path.
4. Send at a rate exceeding the once-per-second `removeExpiredRequests` sweep's throughput to make `h.activeRequests` grow unboundedly across the 30-second `requestTimeout` window, exhausting gateway memory over sustained load.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {

	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
