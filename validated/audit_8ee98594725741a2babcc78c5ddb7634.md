### Title
Unchecked ERC20 return value in IntentGatewayV2 `withdraw`/`SweepDust` escrow release lets silent-failing tokens drain escrow accounting - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2` releases escrowed tokens using a raw low-level `.call()` to the ERC20 `transfer` selector and only checks that the **external call succeeded**, never decoding the ABI-encoded boolean that `IERC20.transfer` returns. For any ERC20 that returns `false` on failure instead of reverting, `success` will be `true` even though no tokens moved, yet the contract still decrements escrow accounting and marks the order as filled/refunded.

### Finding Description
In `withdraw()`, the escrow-release loop and the transaction-fee release both do: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

`success` here only reflects whether the low-level call reverted, not whether the token's `transfer` returned `true`. Standard-conforming tokens that signal failure by returning `false` (a legal ERC20 pattern) will make this `call` return `success = true` with `returndata` decoding to `false`, so the check silently passes. Immediately after, the code unconditionally does: [2](#0-1) 

`_orders[body.commitment][token] -= amount;` — decrementing escrow and (via `_filled[body.commitment] = beneficiary` at the top of `withdraw`) marking the order permanently settled, even though the beneficiary received nothing.

The identical unchecked pattern also appears in the `SweepDust` handler: [3](#0-2) 

and for transaction-fee redemption: [4](#0-3) 

Notably, this contract already imports and uses `SafeERC20` elsewhere (`safeTransferFrom` in `placeOrder`/`fillOrder`, `using SafeERC20 for IERC20;`) — [5](#0-4)  — but `withdraw()` and `SweepDust` bypass it, making the raw-call pattern an inconsistency rather than an intentional design choice, and reproducing exactly the bug class from the referenced Footium report (unchecked boolean return of `transfer`).

`withdraw()` is reached through the normal cross-chain message flow: `onAccept` is called by the host after a relayer delivers a proven `RedeemEscrow`/`RefundEscrow` POST request from the counterpart gateway, and `onGetResponse` calls it after a GET response for order cancellation — both are ordinary, permissionless (from the perspective of the calling relayer/filler/user) paths of the intents protocol, not privileged-admin actions: [6](#0-5) 

### Impact Explanation
If the input, output, or fee token used in an order is one whose `transfer` returns `false` instead of reverting on failure (e.g., due to insufficient balance in an edge case, a paused/blacklisted state, or any conforming-but-non-reverting ERC20 implementation), the escrow accounting (`_orders[...]`) is decremented and the order is marked filled/refunded while the beneficiary/filler/user receives zero tokens. This is a permanent loss of the escrowed funds — the tokens remain stuck in the `IntentGatewayV2` contract (untracked, since the accounting says they were paid out) while the intended recipient never receives them, and there is no recovery path since `_filled`/`_orders` state has already been finalized.

### Likelihood Explanation
The likelihood depends on the intents gateway supporting ERC20s that can return `false` rather than revert. This is a legitimate, non-exotic ERC20 behavior (the base `IERC20.transfer` spec explicitly allows returning `false`), so any token integrated into the gateway that follows this pattern (rather than always reverting) triggers the bug on every failed transfer attempt caused by that token's business logic (e.g., blacklist, pause, insufficient allowance edge cases relevant to fee-on-transfer or rebasing tokens). Because `IntentGatewayV2` is a generic multi-token intents/escrow gateway (any `token` address can be encoded in `TokenInfo`), this is reachable without any privileged role — any relayer delivering a valid, correctly-proven `RedeemEscrow`/`RefundEscrow`/`SweepDust` message triggers the flawed release path.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, exactly as already used elsewhere in this same contract (`safeTransferFrom` in `placeOrder`), so that both the low-level call success and any returned boolean (or lack of `returndata` in older standards) are correctly validated and non-conforming/failed transfers cause a revert instead of silently succeeding.

### Proof of Concept
1. Register an ERC20 token whose `transfer(address,uint256)` returns `false` on failure rather than reverting (fully spec-compliant behavior) as an order's input token.
2. Place and fill a cross-chain order using this token; the source-chain `IntentGatewayV2` escrows `amount` of the token.
3. Craft (or have the destination gateway naturally produce) conditions under which the token's `transfer` internally fails and returns `false` (e.g., the token later becomes paused, or the gateway's balance is manipulated to be insufficient at withdrawal time, e.g. due to a prior partial sweep/dust event on the same token).
4. When the `RedeemEscrow`/`RefundEscrow` message is delivered, `onAccept` → `withdraw()` executes `token.call(...transfer...)`; the call itself does not revert (`success = true`) even though `returndata` decodes to `false`.
5. `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment] = beneficiary` is set, finalizing the order as settled — but the beneficiary's token balance is unchanged, and the tokens remain permanently stuck in the gateway contract with no path to reclaim them.
