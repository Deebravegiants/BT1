### Title
Permanent front-running/griefing of AMM pool creation via deterministic market-derived PDAs - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every account needed for a new pool (`amm_info`, `amm_target_orders_info`, `amm_lp_mint_info`, `amm_coin_vault_info`, `amm_pc_vault_info`) solely from the public `market_info.key` and fixed seed constants, with no binding to the caller's identity. Any unprivileged signer can submit an `Initialize2` instruction for a market they do not control, permanently claiming the canonical pool address for that market before the legitimate creator's transaction lands.

### Finding Description
The pool's associated accounts are computed with `get_associated_address_and_bump_seed`, whose inputs are only `program_id`, `market_account.key`, and a fixed seed (`AMM_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`): [1](#0-0) 

`process_initialize2` never validates that `user_wallet_info` is an authorized deployer for the given `market_info`; any signer can pass any market and any token mints/amounts: [2](#0-1) 

Account creation for each of these PDAs is guarded only by `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint`, which check whether the target address is still owned by the System Program; if it has already been allocated (by a previous successful `Initialize2` call, from anyone), the call fails with `AmmError::RepeatCreateAmm` and can never succeed again for that market: [3](#0-2) [4](#0-3) 

This mirrors the reported bug class exactly: the "account ID" in the cross-chain report (an attacker-observable, user-chosen identifier that a griefer can pre-claim) is analogous to `market_info.key` here — a public, deterministic input that any observer of a pending `Initialize2` transaction (visible in the mempool/gossip before confirmation) can extract and resubmit first with their own `user_wallet`, mints and amounts, permanently occupying the deterministic PDA slot for that market. Once an attacker's `Initialize2` lands first, the legitimate project can never initialize the "real" pool for that market again, because the target PDAs are irreversibly assigned/owned by the program (`AmmError::RepeatCreateAmm`).

### Impact Explanation
This is a Griefing/Denial-of-Service impact matching the report's accepted "Griefing" category: the legitimate market operator is permanently prevented from creating the canonical AMM pool for their OpenBook market, since pool/vault/LP-mint addresses are deterministically pinned to the market key with no per-creator uniqueness or reservation mechanism. The attacker can grief with minimal cost — an arbitrary signer, an arbitrary tiny `init_coin_amount`/`init_pc_amount` (as long as non-zero), and no requirement of relationship to the project — and squats the market's only valid pool slot, degrading trust and forcing the legitimate team to abandon that specific market entirely.

### Likelihood Explanation
Likelihood is significant wherever pool creation is publicly observable (e.g., via RPC mempool/pending transaction monitoring, or simply monitoring newly registered OpenBook markets and racing to be first). Since `Initialize2` has no signer-authorization tie to the market and no reservation/commit-scheme, any party can watch for markets about to get a Raydium pool and preemptively submit their own `Initialize2` for the same market, and whichever transaction lands first on-chain wins permanently.

### Recommendation
Bind pool/PDA derivation (or an explicit authorization check inside `process_initialize2`) to an authorized creator/allowlist for a given market, or otherwise require a permissioned/whitelisted step before the deterministic PDA is claimed, so an arbitrary third party cannot permanently occupy a market's canonical pool address. At minimum, provide an admin-controlled recovery path (e.g., ability to invalidate/reclaim a griefed, effectively "abandoned" pool with negligible liquidity) so the DoS is not irreversible.

### Proof of Concept
1. A legitimate market operator prepares and broadcasts an `Initialize2` transaction (built via `initialize2` in `program/src/instruction.rs`) for their OpenBook `market`, with mints, real `init_coin_amount`/`init_pc_amount`, and their `user_wallet` as signer.
2. An attacker observes this pending transaction (or simply monitors for newly created OpenBook markets that don't yet have a Raydium pool) and computes the deterministic PDAs via the same `get_associated_address_and_bump_seed` derivation using the public `market` key.
3. The attacker submits their own `Initialize2` instruction for the same `market`, using their own wallet, arbitrary token accounts they control for the mints, and a minimal non-zero `init_coin_amount`/`init_pc_amount`, and gets it confirmed first.
4. `process_initialize2` for the attacker succeeds: `generate_amm_associated_account`/`generate_amm_associated_spl_token` allocate and assign the PDAs (lines 477-546), and `amm.status` is set (lines 960-983).
5. The legitimate operator's original transaction now fails at the same account-creation checks with `AmmError::RepeatCreateAmm` (lines 317-381, 470-473, 541-544), permanently, since the market-derived PDA addresses can never be reused for a different pool state once claimed.

    #[allow(clippy::too_many_arguments)]
    fn generate_amm_associated_account<'a, 'b: 'a>(
        program_id: &Pubkey,
        assign_to: &Pubkey,
        market_account: &'a AccountInfo<'b>,
        associated_token_account: &'a AccountInfo<'b>,
        user_wallet_account: &'a AccountInfo<'b>,
        system_program_account: &'a AccountInfo<'b>,
        _rent_sysvar_account: &'a AccountInfo<'b>,
        associated_seed: &[u8],
        data_size: usize,
    ) -> ProgramResult {
        let (associated_token_address, bump_seed) = get_associated_address_and_bump_seed(
            &program_id,
            &market_account.key,
            associated_seed,
            program_id,
        );
        if associated_token_address != *associated_token_account.key {
            msg!("Error: Associated token address does not match seed derivation");
            return Err(AmmError::ExpectedAccount.into());
        }
        if associated_token_account.owner == system_program_account.key {
            let associated_account_signer_seeds: &[&[_]] = &[
                &program_id.to_bytes(),
                &market_account.key.to_bytes(),
                associated_seed,
                &[bump_seed],
            ];
            let rent = Rent::get()?;
            let required_lamports = rent
                .minimum_balance(data_size)
                .max(1)
                .saturating_sub(associated_token_account.lamports());
            if required_lamports > 0 {
                invoke(
                    &system_instruction::transfer(
                        user_wallet_account.key,
                        associated_token_account.key,
                        required_lamports,
                    ),
                    &[
                        user_wallet_account.clone(),
                        associated_token_account.clone(),
                        system_program_account.clone(),
                    ],
                )?;
            }
            invoke_signed(
                &system_instruction::allocate(associated_token_account.key, data_size as u64),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
            invoke_signed(
                &system_instruction::assign(associated_token_account.key, assign_to),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
        } else {
            associated_token_address.log();
            return Err(AmmError::RepeatCreateAmm.into());
        }
        Ok(())
    }
