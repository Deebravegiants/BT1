### Title
Attestation signature omits `signup_id`/timestamp binding, enabling cross-signup replay of Orb-signed biometric attestation - ([File: src/plans/enroll_user.rs])

### Finding Description
`make_signature` builds the SHA-256 digest that is passed to `secure_element::sign` from only `ORB_ID`, `user_qr_code.user_id`, and the iris/mask code fields of the `Pipeline` — it never mixes in `signup_id` or a timestamp: [1](#0-0) 

`Plan::run` calls `make_signature(&user_qr_code, &p)` without threading `self.signup_id` into the digest at all, even though `signup_id` is available in the same scope and is used immediately afterward to build the multipart upload: [2](#0-1) 

The resulting base64 signature is then sent as an independent `"signature"` form field, separate from the URL path's `signup_id`, in `signup_post::request`: [3](#0-2) 

Because the signed payload is a pure function of `(ORB_ID, user_id, iris_code, mask_code, iris_code_version)`, any two signups for the same `user_id` that reproduce identical iris/mask code outputs (e.g., by presenting the same static iris artifact twice, which is plausible since the biometric pipeline is deterministic for identical input imagery) will hash to the *identical digest*. Signing the same digest twice does not cryptographically bind the resulting signature to a particular `signup_id` or point in time — the digest itself carries no session-uniqueness. This means a signature (and the userId/codes it was computed over) captured from one signup session can be resubmitted as the `"signature"`/`"userId"`/`"codes"` fields of a different `signup_id`'s POST to `/api/v2/signups/{signup_id}`, and would validate identically at the digest/message level, since the client never asks the secure element to attest to *which* signup it belongs to.

Whether the raw signature bytes are bit-identical across the two calls depends on whether the signing primitive uses a deterministic nonce (e.g., RFC 6979) or a random one; the `#[cfg(test)]` stub in `src/secure_element.rs` uses standard `EcdsaSig::sign`, which typically uses a randomized nonce, so byte-identical outputs are not guaranteed in that mock: [4](#0-3) 
That detail is secondary to the core issue: the *message being signed* — not just the final signature bytes — lacks any binding to `signup_id` or time, so the signed attestation for signup A is semantically valid and replayable as an attestation for signup B for the same user.

### Impact Explanation
This breaks session-unique attestation: the secure-element signature is meant to prove "the Orb captured this iris code for this specific signup," but because `signup_id`/timestamp are excluded from the signed data, the attestation cannot cryptographically distinguish between two different signup attempts for the same user. An attacker who can trigger two signup sessions with the same QR code and force identical pipeline outputs can reuse attestation material across sessions, undermining the backend's ability to treat the signature as fresh, per-signup proof. This matches an "attestation forgery / replay" class finding under Worldcoin/Orb bounty scope (forging or replaying Orb-signed attestation material).

### Likelihood Explanation
Feasibility requires: (1) attacker-controlled ability to initiate two signups with the same user QR code (unprivileged attacker input, no special access needed), and (2) reproducing identical iris/mask code outputs across both attempts, which is plausible with a static high-quality iris print/photo presented twice, since the pipeline computation is deterministic given identical captured imagery. No operator, key, or hardware access is required — only repeated presentation of the same QR code and iris artifact to the camera during two separate signup flows.

### Recommendation
Include `signup_id` (and ideally a monotonic timestamp or freshness nonce issued by the backend) in the digest that `make_signature` signs, e.g.:
```rust
ctx.update(signup_id.as_bytes());
ctx.update(timestamp.to_string().as_bytes());
```
so that the secure-element signature is cryptographically bound to the specific signup session, preventing reuse of a valid signature/digest pair across different `signup_id`s even when biometric inputs are identical.

### Proof of Concept
Unit test in `src/plans/enroll_user.rs` (or a new test module):
```rust
#[test]
fn make_signature_does_not_bind_signup_id() {
    let user_qr_code = qr_scan::user::Data { user_id: "same-user".into(), ..Default::default() };
    let pipeline = build_fixed_pipeline(); // deterministic iris/mask codes

    // Signup A and Signup B both use the same user QR code and reproduce
    // identical iris/mask codes, but represent different signup_ids.
    let digest_a = build_digest(&user_qr_code, &pipeline);
    let digest_b = build_digest(&user_qr_code, &pipeline);

    // The signed message (digest) is identical regardless of signup_id,
    // proving no session binding exists in make_signature's input.
    assert_eq!(digest_a.as_ref(), digest_b.as_ref());
}
```
Expected assertion: the SHA-256 digest fed into `secure_element::sign` is identical for both "signups" because `make_signature` never consumes `signup_id` or a timestamp, demonstrating the missing session binding described above.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
