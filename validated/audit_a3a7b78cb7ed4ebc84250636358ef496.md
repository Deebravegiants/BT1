### Title
Webhook shop-domain identity spoofing due to HMAC covering only the raw body, not the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload as only the raw request body (`to_signable_string` returns `@raw_body`), while the tenant-identifying `shop` (and `topic`/`webhook_id`/`api_version`) values are read straight from HTTP headers that are never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` to build `WebhookMetadata` passed to the app's handler, breaking the equality "bytes verified == bytes acted upon."

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC [4](#0-3) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [3](#0-2) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are outside the HMAC-signed content [5](#0-4) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before invoking the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [1](#0-0) . Because the shop header is never part of the signed content, any request that carries a body+HMAC pair valid for *some* shop (e.g., one the attacker legitimately owns/installed the app on) will pass HMAC validation regardless of what value is placed in the `shop-domain` header. An attacker can therefore swap in an arbitrary victim shop domain while reusing a body/HMAC pair they legitimately obtained, and the gem will hand the host application a `WebhookMetadata` object asserting that the (attacker-controlled) body came from the victim shop.

This exactly matches the identity-binding class called out in the prompt: "a field acted on but not covered by the HMAC" / "the shop authenticated versus the shop stored as a session key" — here the HMAC authenticates the body, but the shop value used by the application to key per-tenant storage/business logic is not authenticated at all.

### Impact Explanation
This is a cross-tenant identity spoofing vector: because `shop` is not bound to the HMAC, an attacker who can produce or capture any single valid (body, HMAC) pair for a topic they control (e.g., by installing the app on a store they own and observing a real webhook delivery, or from any other body they can get signed) can replay it against the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. Any host application that uses `WebhookMetadata#shop` to select a merchant record (common practice, especially for `app/uninstalled`, GDPR redact topics, or order-processing webhooks) would apply the attacker's payload to the victim's account — this crosses the tenant boundary and satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls into the app without any session/access-token requirement). Obtaining one valid (body, HMAC) pair is trivial for anyone who can install the app on a shop they control (installing a free/dev app is not a privileged action) — after that, the header they control for `X-Shopify-Shop-Domain` is unauthenticated and freely modifiable, since the requirement in the code (`missing_headers` check) is only presence, not any binding to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) header values in the signable string used for the HMAC digest verification, or otherwise cryptographically bind these header fields to the payload before trusting them (e.g., verify shop matches an already-registered/known shop record rather than blindly trusting the header). At minimum, document clearly that `request.shop`/`request.topic` are NOT covered by HMAC verification and must not be used as a sole tenant key without additional binding by the consuming application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they control) and configures a webhook subscription (or observes a real webhook fired by their own store).
2. Attacker captures the raw webhook body and the legitimately-computed `X-Shopify-Hmac-Sha256` header Shopify sent for that request — this HMAC is valid because it is signed only over the raw JSON body, not over the shop header:
   ```ruby
   # lib/shopify_api/webhooks/request.rb
   def to_signable_string
     @raw_body   # only the body, no shop/topic binding
   end
   ```
3. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the digest matches the unchanged body [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: attacker_controlled_body, ...)` [7](#0-6) , causing the host app to process attacker-controlled data under the victim's tenant identity.
