### Title
`ShopValidator.sanitize_shop_domain` treats any `admin.<trusted_domain>` host as the unified-admin URL, letting an attacker-supplied path segment become the returned shop domain - ([File: lib/shopify_api/utils/shop_validator.rb])

### Summary
`sanitize_shop_domain` evaluates `unified_admin?(uri) && from_trusted_domain` before checking `no_shop_name_in_subdomain`, and `unified_admin?` only checks that the first host label is `"admin"` without restricting which trusted domain it is paired with. Because `from_trusted_domain` is computed from `uri.domain` (the registrable/public-suffix domain, e.g. `"myshopify.com"`), a URL like `https://admin.myshopify.com/<anything>` satisfies both conditions even though `admin.myshopify.com` is not Shopify's real unified-admin host (`admin.shopify.com`), causing the function to return `"<anything>.myshopify.com"` instead of rejecting the URL or returning the literal host.

### Finding Description
The intended binding is: `sanitize_shop_domain(url)` returns the *host actually presented in the URL* (or `nil`/raises for anything not a genuine Shopify host), i.e. `returned_shop == uri.host` (or the shop derived only from Shopify's real unified-admin host `admin.shopify.com`). What the code actually computes for `https://admin.myshopify.com/any-attacker-string` is:

```ruby
uri.host   # "admin.myshopify.com"
uri.domain # "myshopify.com" (registrable domain)
no_shop_name_in_subdomain = host == trusted_domain   # "admin.myshopify.com" == "myshopify.com" -> false
from_trusted_domain       = trusted_domain == uri_domain # "myshopify.com" == "myshopify.com" -> true
unified_admin?(uri)       # host.split(".").first == "admin" -> true
``` [1](#0-0) 

Since `unified_admin? && from_trusted_domain` is `true`, the function short-circuits into `myshopify_domain_from_unified_admin(uri)`, which takes the *last path segment* and appends `.myshopify.com`: [2](#0-1) 

This branch was clearly designed only for the real Shopify "New Admin" host `admin.shopify.com` (see the passing test `test_unified_admin_store_url_maps_to_myshopify_host` using `https://admin.shopify.com/store/cool-shop`) [3](#0-2) , but `unified_admin?` never restricts the check to `trusted_domain == "shopify.com"`; it fires for *any* trusted domain whose registrable domain equals the current label-1 "admin" host, including `myshopify.com`, `myshopify.io`, `spin.dev`, and `shop.dev` [4](#0-3) . As a result, `sanitize_shop_domain('https://admin.myshopify.com/any-attacker-string')` returns `"any-attacker-string.myshopify.com"` — a value derived entirely from an unauthenticated URL path — instead of being rejected by the `no_shop_name_in_subdomain` guard that exists precisely to reject bare/attacker-shaped trusted-domain hosts.

`Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` is the gem's documented guard for validating an untrusted `shop` value (see tests like `test_rejects_attacker_controlled_domain`, `test_rejects_similar_looking_domain`) [5](#0-4) , intended to be called by host apps on request-supplied `shop`/URL values before starting OAuth. Within this gem's own reachable call sites (`Auth::TokenExchange.migrate_to_expiring_token`, `Auth::ClientCredentials`, `Auth::RefreshToken`), the `shop` argument comes from the calling application, not directly from an unauthenticated wire value with a scheme/path; `TokenExchange.exchange_token` (the OAuth/session-token path) uses `JwtPayload#shop` directly rather than `ShopValidator`, so that specific flow is unaffected by this bug [6](#0-5) .

### Impact Explanation
This is a genuine logic bug in `ShopValidator.sanitize_shop_domain`: it returns an attacker-controlled, path-derived string for `admin.<any trusted domain>` hosts instead of rejecting them, violating the function's own domain-name invariant. I could not confirm, within this gem's own code, a concrete reachable call site where this specific bad input (a full URL with `admin.myshopify.com` host and attacker path) is fed into the function as part of an unauthenticated request and the result is then used to bind a session or access token — the confirmed callers pass an app-controlled `shop:` string, and the token-exchange flow (which does handle raw session tokens from requests) derives shop from the JWT `dest` claim, not from `ShopValidator`. So full cross-tenant token theft/session hijack cannot be demonstrated purely from this gem's code; the confirmed, reproducible impact is limited to the sanitizer itself producing a wrong/attacker-influenced shop string for this class of input, which is a real defect but its severity depends on how a host application uses the return value.

### Likelihood Explanation
Triggering the flaw itself requires no privileges — any caller of the public API method `ShopValidator.sanitize_shop_domain`/`sanitize!` with a URL of the form `https://admin.<trusted_domain>/<attacker-string>` (where `trusted_domain` is `myshopify.com`, `myshopify.io`, `spin.dev`, or `shop.dev`) reproduces it deterministically. Whether it becomes an authentication/session-binding bypass depends on whether a host application passes an unauthenticated, attacker-supplied full URL (not just a bare `shop.myshopify.com` string) into this sanitizer and then trusts the returned value as the authenticated shop — a usage pattern I could not confirm inside this gem's own reachable code paths.

### Recommendation
Restrict `unified_admin?`'s path-extraction branch to the real Shopify unified-admin host only, e.g. require `uri.host == "admin.shopify.com"` (or `trusted_domain == "shopify.com"` specifically) rather than matching any trusted domain whose first label is `"admin"`. Additionally, reorder the checks so `no_shop_name_in_subdomain` (host literally equals the trusted domain) is evaluated before the unified-admin branch, and validate that the extracted path segment itself is a syntactically valid shop handle before trusting it.

```ruby

require_relative "../test_helper"

module ShopifyAPITest
  module Utils
    class ShopValidatorAdminMyshopifyTest < Test::Unit::TestCase
      def test_admin_myshopify_host_is_not_hijacked_by_path
        result = ShopifyAPI::Utils::ShopValidator.sanitize_shop_domain(
          "https://admin.myshopify.com/any-attacker-string",
        )
        # Binding under test: returned shop must equal the actual host presented,
        # or the call must be rejected -- NOT an attacker-chosen path value.
        refute_equal("any-attacker-string.myshopify.com", result)
      end
    end
  end
end
```
Running this against current `lib/shopify_api/utils/shop_validator.rb` fails: `sanitize_shop_domain` returns `"any-attacker-string.myshopify.com"`, confirming the `unified_admin?`/`from_trusted_domain` ordering bug described above.
