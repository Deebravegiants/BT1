### Title
Cross-chain amount conversion in `pallet-hyper-fungible-token` silently skips decimal scale-down, over-inflating minted amounts - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_erc20` and `convert_to_balance`, the helpers `pallet-hyper-fungible-token` uses to translate amounts between this chain's asset precision and a remote EVM chain's ERC20 precision, use `erc_decimals.saturating_sub(local_decimals)` (or the inverse) as the *only* scaling exponent and always apply it as a multiplication (or division). When the two precisions are in the direction the `saturating_sub` clamps to zero, the required scale factor silently becomes `10^0 = 1` instead of the correct divisor/multiplier, producing an amount that is off by `10^|decimals_diff|` — exactly the "value is over-inflated by re-applying a scaling factor that was already accounted for / omitting a required inverse scaling factor" bug class from the referenced report.

### Finding Description
`convert_to_erc20` is called from the pallet's `send` extrinsic to build the `Message.amount` that gets ABI-encoded and dispatched via ISMP to the destination chain's `HyperFungibleToken`/`WrappedHyperFungibleToken` contract: [1](#0-0) 

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

and used at the call site: [2](#0-1) 

The correct conversion from a local balance (precision `local_decimals`) to an ERC20 amount (precision `erc_decimals`) is:
- multiply by `10^(erc_decimals - local_decimals)` when `erc_decimals > local_decimals`
- divide by `10^(local_decimals - erc_decimals)` when `local_decimals > erc_decimals`

`saturating_sub` only ever returns a non-zero value in the *first* case. When `local_decimals > erc_decimals` (i.e. the locally-registered asset carries more decimal places than the destination chain's registered ERC20 token — a completely ordinary and expected configuration, e.g. an 18-decimal Substrate asset bridging to a 6-decimal ERC20 token address on some EVM chain, both configured via the admin-only `register_token`/`update_token` calls and stored per-chain in `Precisions`), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the multiplier collapses to `1` — the function performs **no scaling at all**, when it should be *dividing* by `10^(local_decimals - erc_decimals)`.

Concretely: burning/escrowing `amount` local units (say, `1` whole token = `10^18` raw units at 18 decimals) and calling `convert_to_erc20(amount, erc_decimals=6, local_decimals=18)` returns `10^18` unchanged, instead of the correct `10^6`. That raw value is ABI-encoded into `Message.amount` and dispatched cross-chain; the destination `HyperFungibleToken` contract mints/releases based on that field at its own 6-decimal precision, so it credits `10^18` raw units — `10^12` (one trillion) times more tokens than one whole token — against collateral that only backs one whole token on the source chain.

The counterpart function has the symmetric, opposite-direction bug: [3](#0-2) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```
used in `on_accept`/`on_timeout` when an inbound message is credited/minted locally: [4](#0-3) 

Here, when `erc_decimals < local_decimals` (the destination has more local decimals than the source's ERC20 token), the divisor clamps to `1`, so the incoming ERC20 amount is credited without the required scale-*up*, under-crediting the beneficiary — the mirror-image consequence of the same missing branch.

None of the existing tests exercise the `local_decimals > erc_decimals` (send) or `erc_decimals < local_decimals` (receive) branches; the only test asserting `convert_to_erc20` uses `erc_decimals=18, local_decimals=10`, i.e. the one direction that happens to work: [5](#0-4) 

### Impact Explanation
This directly matches the "route unable to deliver messages"/"unauthorized app action"/"unbacked mint" categories: an ordinary, signed `send` extrinsic call from any user against a token pair configured (by the token's admin, via ordinary `register_token`/`update_token`, not a malicious action) with the local asset decimals greater than the destination chain's registered ERC20 decimals results in a cross-chain message that instructs the destination `HyperFungibleToken` contract to mint/release an amount inflated by `10^(local_decimals - erc_decimals)`. This is an unbacked mint on the destination chain relative to the collateral escrowed/burned on the source — a direct and severe fund-drain/insolvency vector for any deployment where such a decimal mismatch exists (which is a normal, expected configuration for cross-chain assets of differing standard decimals, e.g. 18-decimal Substrate assets vs 6-decimal EVM stablecoins).

### Likelihood Explanation
Likelihood is high for any deployment bridging an asset whose local decimals exceed the destination chain's registered ERC20 decimals for that asset — a routine, non-malicious configuration explicitly anticipated by the pallet's design (`Precisions` exists precisely to record differing decimals per chain). Triggering it requires nothing more than an ordinary signed `send` call once such a pair is registered; no privileged or malicious actor is needed beyond the normal token registration that legitimate deployments perform.

### Recommendation
Fix both helpers to scale in the correct direction depending on which side has more decimals, rather than relying on `saturating_sub` collapsing to zero:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}

pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if local_decimals >= erc_decimals {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    } else {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
Add tests covering both directions (`local_decimals > erc_decimals` and `local_decimals < erc_decimals`) for both `send`/`convert_to_erc20` and `on_accept`/`convert_to_balance`.

### Proof of Concept
1. Register a token via `register_token` with `local_decimals = 18` (e.g. a standard 18-decimal Substrate asset) and, for some destination `StateMachine`, `Precisions::<T>::insert(asset_id, chain, 6)` (a 6-decimal ERC20 token address on that EVM chain) — an entirely normal registration.
2. Any signed user calls `send` with `amount = 10^18` (one whole token), escrowing/burning `10^18` local raw units.
3. `convert_to_erc20(10^18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, returning `10^18 * 10^0 = 10^18` instead of the correct `10^6`.
4. The dispatched `Message.amount = 10^18` is ABI-encoded and delivered to the destination `HyperFungibleToken` contract, which mints/releases `10^18` raw units at its own 6-decimal precision — i.e. `10^12` whole tokens — against collateral that only backs one whole token, demonstrating the over-inflated, unbacked mint.
