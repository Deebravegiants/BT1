### Title
Cross-tenant webhook spoofing via `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, while the `shop` (tenant) identifier that the handler receives comes from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. This breaks the equality "shop authenticated by HMAC == shop delivered to the handler," letting a merchant who legitimately installed the app on their own store relabel a validly-signed webhook payload as belonging to a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  and `Request#shop` is read directly from an unsigned header: [2](#0-1) .

`Registry.process` verifies only that the HMAC matches the body, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) .

The HMAC is computed with `OpenSSL::HMAC.hexdigest(sha256, secret, signable_string)` where `signable_string` is exactly the raw body — no shop, topic, or webhook-id header is part of the signed material: [4](#0-3) .

Because the app's `client_secret`/HMAC key is identical across every merchant install of the app, a merchant who installs the app on their own store legitimately receives real webhook deliveries signed with that same key for their own shop. Nothing in `Request`/`HmacValidator`/`Registry` binds the shop identity into the signature, so that attacker can replay the exact same raw body and HMAC to the app's webhook endpoint while substituting `shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` will still return `true` (it only checks the body bytes), and the handler will process the payload as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged but legitimate app installer (attacker on their own shop) can make the app process attacker-controlled webhook content under an arbitrary victim shop's identity. Any app logic that keys off `WebhookMetadata#shop` (e.g., updating per-shop billing state, GDPR data flags, inventory, or triggering shop-scoped side effects) can be manipulated cross-tenant without ever needing the victim's credentials — satisfying the "cross-tenant access" Critical impact class since the gem itself provides no protection against this and documents `shop` as the trusted identity of the payload.

### Likelihood Explanation
Medium-High: any developer who installs (or has installed) the target app on a shop they control can capture real, validly-HMAC'd webhook deliveries (body + hmac header) at will, since Shopify sends these automatically on ordinary events (e.g., `orders/create`), and can then trivially replay them with a forged shop header to the same public webhook endpoint — no secret material or elevated privilege is required beyond being an app installer.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the authenticated identity: either include `shopify-shop-domain` in the signable string used for HMAC validation, or cross-check the delivered `shop` against a shop that is independently known to be associated with the specific webhook subscription (e.g., validate against the webhook ID or an app-side registration record) before trusting it. At minimum, document that consumers must not rely on `WebhookMetadata#shop` as an authenticated field unless it is also cryptographically bound.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g., creates an order), causing Shopify to POST a real webhook: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures `B` and the HMAC value.
3. Attacker POSTs the same `B` and HMAC to the app's public webhook endpoint again, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and matches — validation passes: [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, so the app processes attacker-controlled content as belonging to the victim tenant: [6](#0-5) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
