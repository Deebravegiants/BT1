Audit Report

## Title
Missing role-based authorization on `/v2/debug/pprof/*` allows any authenticated user (including View role) to read runtime memory dumps, goroutine stacks and command-line data - ([File: core/web/router.go])

## Summary
The `metricRoutes` function mounts Go's `net/http/pprof` handlers (`heap`, `goroutine`, `cmdline`, `profile`, `trace`, `allocs`, etc.) directly onto the `authv2` router group, which only enforces base authentication (token or session) and no minimum role. Every other operationally sensitive route registered in the same `v2Routes` function is explicitly wrapped with `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole`, but the pprof routes are not, allowing a low-privilege `UserRoleView` account (or a `view`-scoped API token) to pull raw process memory/goroutine dumps.

## Finding Description
`v2Routes` defines `authv2` with only base authentication middleware (`auth.AuthenticateByToken`/`auth.AuthenticateBySession`) at [2](#0-1) . Within that group, sensitive endpoints consistently add a second-layer role check, e.g. `auth.RequiresAdminRole(uc.Index)` for `/v2/users` at [4](#0-3) , `auth.RequiresAdminRole(ets.Create)` for `/v2/transfers` at [6](#0-5) , and `auth.RequiresEditRole` for the newly added vault DKG endpoints at [5](#0-4) . However, `metricRoutes(authv2)` — called at [1](#0-0)  — registers the pprof group with no role wrapper at all, as shown in the function definition at [3](#0-2) . The role-check helpers themselves (`RequiresAdminRole`, and by extension `RequiresEditRole`/`RequiresRunRole`) perform the intended second gate of checking `user.Role` after authentication succeeds, but this gate is entirely absent for pprof, meaning any authenticated principal — including one provisioned only with `UserRoleView` — can reach these endpoints.

## Impact Explanation
`pprof` endpoints such as `/v2/debug/pprof/heap`, `/goroutine`, `/cmdline`, `/profile`, and `/trace` can leak full heap memory dumps, goroutine stack traces, and process command-line arguments. In a Chainlink node process, heap contents may include decrypted private keys, session tokens, DKG shares, or database credentials resident in memory during signing/transaction operations, and `cmdline` can reveal secrets passed as CLI flags. This maps to an in-scope key/secret exfiltration and improper authorization impact class (CWE-285 / CWE-732), since exploitation requires only a low-privilege authenticated credential rather than admin/operator access.

## Likelihood Explanation
Any deployment that provisions non-admin API users or tokens (e.g., for read-only dashboards or monitoring integrations) is exposed. No special conditions are required beyond a valid low-privilege session/token, and the pprof route naming is standard and easily guessed/documented, making exploitation straightforward and repeatable.

## Recommendation
Wrap the `pprofGroup` routes in `metricRoutes` with an explicit role check consistent with other operationally sensitive endpoints — at minimum `auth.RequiresAdminRole` — rather than relying solely on `authv2`'s base authentication. Add corresponding entries for `/v2/debug/pprof/*` to `routesRolesMap` in `core/web/auth/auth_test.go` so future regressions are caught automatically.

## Proof of Concept
1. Provision a Chainlink node and create a non-admin API user (e.g., `chainlink admin users create --role=view`), obtaining a session cookie or `X-API-KEY`/`X-API-SECRET` pair.
2. Authenticate as that view-role user against `/sessions` or via API key headers.
3. Issue `GET /v2/debug/pprof/heap` (or `/goroutine`, `/cmdline`) using the low-privilege credentials.
4. Observe a `200 OK` response with the full profile/dump data returned, despite the account never having been granted `edit`/`run`/`admin` privileges — confirming the missing role check at `core/web/router.go:185-199,445-446`.
