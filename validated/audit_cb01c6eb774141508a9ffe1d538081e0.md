### Title
Webhook topic/shop headers are excluded from the HMAC signature, allowing signed-body replay with an attacker-chosen topic to hijack the handler dispatch - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the `x-shopify-topic` and `x-shopify-shop-domain` headers are never covered by the HMAC. `Registry.process` validates the HMAC and then dispatches strictly on `request.topic` and passes `request.shop` into the handler, meaning any body/HMAC pair genuinely issued by Shopify to any shop the attacker controls can be replayed to the same app's webhook endpoint with a forged topic and shop header, causing the wrong handler to run against forged shop/body pairing.

### Finding Description
The broken binding is: **topic bytes verified by HMAC == topic header used for dispatch**. In reality, `to_signable_string` equals `@raw_body` only [1](#0-0) , while `#topic` and `#shop` are read straight from headers with no cryptographic binding to the body [4](#0-3) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [2](#0-1) , so it is topic/shop-agnostic by construction.

Exploit flow: the app's `api_secret_key` is shared across every shop that installs the app. An attacker installs the app on their own development shop, registers a webhook for any topic the app subscribes to, and receives one genuine `raw_body` + `x-shopify-hmac-sha256` pair from Shopify signed with the app's secret. The attacker then replays that exact body and HMAC header to the same app's webhook endpoint, but swaps `x-shopify-topic` to a sensitive topic present in the app's `Registry` (e.g., `shop/redact`, `app/uninstalled`) and sets `x-shopify-shop-domain` to an arbitrary victim shop domain. `HmacValidator.validate` still returns true because it re-derives the same signature over the same `raw_body`. `Registry.process` then looks up `@registry[request.topic]` (the attacker-forged topic) and invokes that handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` — all attacker-controlled except the ultimate content of `raw_body` [3](#0-2) . No guard in the gem cross-checks that the topic or shop claimed in the headers corresponds to what was actually signed, because nothing besides `raw_body` is signed.

### Impact Explanation
An attacker can trigger any topic-specific handler registered in the host app (e.g., mandatory `shop/redact`/`customers/redact`/`app/uninstalled` handlers, or any custom handler) using a spoofed `shop` value and a body that doesn't semantically correspond to that topic, since the gem never checks correlation between signed content and the headers used for routing/shop attribution. Depending on what the host app's handler does with `data.shop` and `data.body` (very common: locate a `Session`/tenant record by `shop` and act on it, e.g. delete data, revoke access, mark uninstalled), this can produce cross-tenant impact against a shop the attacker does not own, purely from headers with no HMAC binding. This matches "cross-tenant access" / handler-confusion category, and is repeatable indefinitely against arbitrary victim shop domains using a single valid signed body captured from the attacker's own store.

### Likelihood Explanation
Preconditions: the host app must be built with this gem's `Webhooks::Registry`/`Request` as documented (default usage), and register at least one webhook handler. Attacker cost is low: install the app on any development shop they control (a normal, low-privilege action), capture one legitimately delivered webhook body+HMAC, and POST it to the app's known webhook endpoint with modified `x-shopify-topic`/`x-shopify-shop-domain` headers. No secrets, tokens, or victim credentials are required. This is fully repeatable.

### Recommendation
Include `topic` and `shop` (and ideally `webhook_id`) in the signable string alongside `raw_body`, or otherwise have `Registry.process` reject any inconsistency by verifying topic/shop against a value cryptographically tied to the signed payload. At minimum, document/enforce that handlers must not trust `WebhookMetadata#shop`/`#topic` without additional verification, but the correct gem-level fix is to make the HMAC cover the headers used for dispatch and tenant attribution, matching Shopify's actual webhook verification guidance which only signs the raw body — meaning the real mitigating control has to be that topic/shop values used for routing come from an out-of-band trusted registration path rather than attacker-suppliable headers on the same request that's merely proven "some valid `raw_body` for this secret was produced."

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryTopicConfusionTest < Test::Unit::TestCase
      def setup
        super
        ShopifyAPI::Webhooks::Registry.clear
        @raw_body = '{"id":123,"note":"legit order body signed for orders/create"}'
        @hmac = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, @raw_body)
        )
      end

      def test_replayed_body_with_forged_topic_dispatches_wrong_handler
        redact_called_with = nil
        redact_handler = ShopifyAPI::Webhooks::Http.new(
          handle_proc: proc { |data:| redact_called_with = data }
        )
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "shop/redact", path: "path", delivery_method: :http, handler: redact_handler,
        )

        forged_headers = {
          "x-shopify-topic" => "shop/redact",              # attacker-chosen, not covered by HMAC
          "x-shopify-hmac-sha256" => @hmac,                 # HMAC only over raw_body
          "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen
        }

        request = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: forged_headers)

        # Binding check BEFORE: hmac covers raw_body only, topic/shop unauthenticated
        assert_equal(@raw_body, request.to_signable_string)
        assert(ShopifyAPI::Utils::HmacValidator.validate(request))

        ShopifyAPI::Webhooks::Registry.process(request)

        # Binding check AFTER: shop/redact handler ran with attacker-chosen shop and
        # body never intended for that topic -- dispatch trusted the unauthenticated header
        refute_nil(redact_called_with)
        assert_equal("shop/redact", redact_called_with.topic)
        assert_equal("victim-shop.myshopify.com", redact_called_with.shop)
      end
    end
  end
end
```
