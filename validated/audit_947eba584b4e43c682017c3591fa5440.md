### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The external report's bug class ("code that is used but not covered by testing/verification, weakening a security binding") maps to a concrete gap in this gem: `ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (tenant identity) field is read from an unauthenticated HTTP header and passed downstream as trusted. The binding that should hold — `hmac_verified(body) == hmac_verified(shop)` — does not; only the body is bound to the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request` includes `Utils::VerifiableQuery` and defines: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, i.e., the HMAC in `x-shopify-hmac-sha256`/`shopify-hmac-sha256` is computed exclusively over the body, using the app's shared `client_secret`. But `shop` is read straight from `shopify-shop-domain` / `x-shopify-shop-domain`, a header entirely outside the signed payload: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC — it never touches `shop`: [4](#0-3) 

`Registry.process` accepts the request once `HmacValidator.validate(request)` passes, then forwards `request.shop` to the app's handler as trusted tenant identity, without any additional binding of `shop` to the signed content: [5](#0-4) [6](#0-5) 

Because every shop installed on the same app shares the same `client_secret`, a valid `(raw_body, hmac)` pair generated for one tenant (e.g. attacker's own store, which legitimately receives real, correctly-signed webhooks from Shopify) remains cryptographically valid regardless of which `shop-domain` header value accompanies it. The equality the gem should enforce — "the shop identity trusted by the app equals the shop identity that produced the HMAC-signed bytes" — is broken: HMAC covers `body` only, but `shop` is what downstream code treats as the tenant boundary.

### Impact Explanation
An attacker who operates or controls any shop installed on the target app can capture a legitimate, correctly HMAC-signed webhook delivery for their own store (or forge one via any accessible webhook trigger), then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` passes (it never inspected `shop`), and `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop` set to the victim's domain and `body` set to attacker-controlled data. Any app that uses `data.shop` to key a per-tenant record and `data.body` to update/create tenant data (a standard usage pattern shown in this gem's own webhook docs) can be tricked into writing attacker-controlled data into another merchant's tenant context — a cross-tenant data-integrity/confusion issue reachable purely with knowledge of the app's public webhook URL and possession of one's own legitimately signed webhook payload, no access token or `api_secret_key` required.

### Likelihood Explanation
Any merchant who installs the app (a normal, low-privilege action, not requiring `api_secret_key` or an access token) automatically becomes a source of validly-signed webhook payloads, since Shopify signs webhooks per-app (not per-shop) with the app's `client_secret`. The webhook endpoint is public by design. No cryptographic secret needs to be obtained; only replay of an already-received, legitimately-signed body with a different header is required.

### Recommendation
Bind `shop` into the signed payload construction or otherwise cryptographically verify it as part of `to_signable_string`/`HmacValidator.validate`, or require host applications to independently confirm that `shop` matches an expected/installed shop associated with the webhook subscription before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a tenant boundary without additional verification (e.g., cross-checking against the shop that owns the specific `webhook_id`/registration).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify delivers a real webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, "note": "malicious payload"}`
2. Attacker intercepts/replays this exact request but rewrites only the shop header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (HMAC and body left untouched)
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into `hmac`, `shop = "victim-shop.myshopify.com"`, `to_signable_string == raw_body`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `raw_body`, matching the header value copied verbatim from the original legitimate delivery.
5. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: {"id" => 1, "note" => "malicious payload"}, ...)` and, if it persists/reacts to `data.body` keyed by `data.shop`, applies attacker-controlled content under the victim tenant's identity. module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
