### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used by `Registry.process` and passed to the app's `WebhookHandler` from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Because the `shop` header is never part of the signed payload, and the webhook signing secret (`Context.api_secret_key`) is shared across every shop that has the app installed (it is not shop-specific), any party who can obtain one validly-signed webhook body/HMAC pair (trivially available by installing the app on their own free/dev store) can replay that pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, spoofing the identity of a victim shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show that only the raw body is fed into the HMAC computation: [1](#0-0) 

`Request#shop` reads directly from the (unsigned) header with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the computed signature — it never validates the shop header: [3](#0-2) 

`Registry.process` treats a successful HMAC check as proof the entire request (including `request.shop`) came from Shopify for that shop, and forwards `request.shop` unchanged into `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" before calling the handler, and explicitly documents `data.shop` as a trusted field apps are meant to key their business logic on (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

The broken identity binding as an equality:
`shop_cryptographically_bound_to_signature == None` while `shop_used_by_handler == header("shop-domain")`, i.e. the shop identity the app acts on is never the shop the HMAC actually authenticates (the HMAC only authenticates the body bytes + the fact the sender knows the app's shared secret).

Because Shopify signs webhooks with the single per-app `client_secret`, not a per-shop secret, this signature does not bind a specific body to a specific shop. Any entity that has installed the target app on any store they control (trivial for an unprivileged internet user — anyone can create a free development/trial store and install a public app) receives legitimately signed webhook deliveries. That party can then POST the exact same raw body and HMAC to the app's public webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled webhook payload (topic/body they fully control, since they own the source shop and can trigger the corresponding action e.g. `app/uninstalled`, `shop/update`, `customers/data_request`, etc.) is processed by the host application as if it originated from a shop the attacker does not control. Depending on how the host app's `WebhookHandler` uses `data.shop` (session lookup, data deletion, entitlement changes, GDPR compliance actions), this can lead to unauthorized state changes, data deletion, or disclosure scoped to a victim tenant — i.e. cross-tenant access driven entirely by this gem's own trust boundary, since the gem's documented contract explicitly claims the shop is verified after `process()` succeeds.

### Likelihood Explanation
Obtaining a validly-signed webhook body/HMAC pair requires only installing the target app on any shop, which is available to any unprivileged internet user for public apps (free/dev stores). Forging the `shop-domain` header on a replayed HTTP POST requires no secret at all. No access token, `api_secret_key`, or privileged account is needed — only the ability to trigger a webhook topic on your own installed instance and replay it with a different header value.

### Recommendation
Do not treat `request.shop` as authenticated by the HMAC check alone. Either:
- Include the shop/domain (and other identity-relevant headers such as topic and webhook-id) inside the HMAC-signed payload/signable string so they cannot be altered without invalidating the signature, or
- Require host applications to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation for this app before acting on the webhook, and document this requirement clearly, or
- Bind webhook delivery to a per-shop verification (e.g. cross-check `webhook_id`/shop pair against Shopify via API) rather than trusting the header value implied by a body-only signature.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a free/dev store), triggering a legitimate webhook, e.g. `app/uninstalled`, delivered to the app's webhook endpoint with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw body under the app's shared client_secret>`
   - body: `{}` (or whatever Shopify sends for that topic)
2. Attacker captures this raw body and valid HMAC (e.g. via a proxy they control, since it's their own store/webhook delivery).
3. Attacker crafts a new POST to the same app webhook endpoint, keeping the raw body and `x-shopify-hmac-sha256` identical, but changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `victim-shop.myshopify.com`; `Utils::HmacValidator.validate` succeeds because it only re-derives the HMAC from `raw_body`, which is unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app's `WebhookHandler#handle` with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the host application to perform the corresponding action (e.g., mark victim's installation as uninstalled, purge victim shop data, etc.) attributed to `victim-shop.myshopify.com`, despite the event never having actually occurred for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
```
