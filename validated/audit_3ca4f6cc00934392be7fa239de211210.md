### Title
Secret-reference limiting bypass via projected volume secret sources - (File: plugin/pkg/admission/serviceaccount/admission.go)

### Finding Description
`Plugin.Validate` calls `s.limitSecretReferences(serviceAccount, pod)` (`plugin/pkg/admission/serviceaccount/admission.go:231-235`) whenever `LimitSecretReferences` is enabled (via `enforceMountableSecrets`, lines 271-282). `limitSecretReferences` (lines 317-379) is intended to reject any pod whose spec references a `Secret` object that is not listed in the pod's `ServiceAccount.Secrets`. However, its volume-checking logic only inspects the direct `VolumeSource.Secret` field:

```go
for _, volume := range pod.Spec.Volumes {
    source := volume.VolumeSource
    if source.Secret == nil {
        continue
    }
    secretName := source.Secret.SecretName
    if !mountableSecrets.Has(secretName) { ... }
}
``` [1](#0-0) 

It never inspects `VolumeSource.Projected.Sources[].Secret`, nor any of the other secret-carrying volume sources (`AzureFile`, `CephFS`, `Cinder`, `FlexVolume`, `RBD`, `ScaleIO`, `ISCSI`, `StorageOS`, `CSI.NodePublishSecretRef`). By contrast, the canonical enumerator used elsewhere in the codebase, `VisitPodSecretNames` in `pkg/api/pod/util.go`, explicitly walks all of these, including the projected-volume case:

```go
case source.Projected != nil:
    for j := range source.Projected.Sources {
        if source.Projected.Sources[j].Secret != nil {
            if !visitor(source.Projected.Sources[j].Secret.Name) { ... }
        }
    }
``` [2](#0-1) 

This confirms `limitSecretReferences` is an incomplete, hand-rolled subset of the fields that actually reference secrets, and diverges from the "single source of truth" enumerator. Env/envFrom secretKeyRef paths for `InitContainers` and `Containers` are checked (lines 334-366) and `ImagePullSecrets` are checked (lines 368-377), but projected-volume secrets are never checked in `limitSecretReferences`, and there is no other admission check that closes this gap on pod create.

Exploit flow: an attacker with only namespace-scoped `create pods` RBAC (and no `get secrets` RBAC) creates a pod bound to a ServiceAccount whose `.secrets` list does not include the target Secret. Instead of a plain `volume.secret.secretName` (which would be blocked), the attacker adds a `projected` volume with a `sources[].secret.name` pointing at the target Secret in the same namespace. `Plugin.Validate` → `limitSecretReferences` iterates `pod.Spec.Volumes`, sees `source.Secret == nil` (because it's a `Projected` source, not a raw `Secret` source), and `continue`s without ever checking the projected sources. The pod is admitted, and the kubelet — which does not perform this authorization check and relies purely on admission having already enforced it — mounts the projected secret into the pod's filesystem, letting the attacker's container read its contents directly.

### Impact Explanation
This allows an authenticated but low-privileged tenant (able only to create pods under a service account) to read the contents of any Secret in the same namespace regardless of RBAC on the Secret itself and regardless of the ServiceAccount's declared `.secrets` list, by mounting it via a projected volume. This is a cross-tenant/namespace-scoped secret disclosure via bypass of a control-plane authorization invariant (`LimitSecretReferences`), matching a Kubernetes security bounty "authorization bypass leading to unauthorized secret disclosure" impact class.

### Likelihood Explanation
- Precondition: cluster/namespace admin has enabled `LimitSecretReferences=true` (or the ServiceAccount carries `EnforceMountableSecretsAnnotation=true`) with the intent of restricting which secrets pods under a given ServiceAccount may reference.
- Attacker only needs standard `create` RBAC on `pods` in the target namespace, using any ServiceAccount whose `.secrets` list is limited/does not include the target secret.
- No RBAC `get` on the Secret is required — the kubelet mounts it once the pod is admitted.
- Trivially repeatable: a single pod spec with a `projected` volume referencing the target secret name is sufficient; no timing or race conditions involved.

### Recommendation
Rewrite `limitSecretReferences` (and `limitEphemeralContainerSecretReferences`) to reuse the same enumeration logic as `podutil.VisitPodSecretNames` (or explicitly add a case for `volume.VolumeSource.Projected.Sources[].Secret`, plus the other secret-referencing volume source types: `AzureFile`, `CephFS`, `Cinder`, `FlexVolume`, `RBD`, `ScaleIO`, `ISCSI`, `StorageOS`, `CSI.NodePublishSecretRef`) so that every secret reference recognized elsewhere in the codebase is also checked against the ServiceAccount's mountable secrets set.

### Proof of Concept
Add a table-driven test to `plugin/pkg/admission/serviceaccount/admission_test.go` that:
1. Creates a `ServiceAccount` with `LimitSecretReferences=true`/`EnforceMountableSecretsAnnotation=true` and `Secrets: []corev1.ObjectReference{}` (no secrets referenced).
2. Constructs a Pod with `Spec.Volumes = []api.Volume{{Name: "v", VolumeSource: api.VolumeSource{Projected: &api.ProjectedVolumeSource{Sources: []api.VolumeProjection{{Secret: &api.SecretProjection{LocalObjectReference: api.LocalObjectReference{Name: "target-secret"}}}}}}}}`.
3. Calls `Plugin.Validate` (or `Admit` then `Validate`) with this pod/SA combination.
4. Asserts the call currently returns `nil` (admitted) — demonstrating the bypass — whereas an equivalent pod using `VolumeSource.Secret.SecretName = "target-secret"` directly is correctly rejected with a forbidden error referencing `"volume with secret.secretName=... is not allowed"`.
5. After the fix, assert both cases return a forbidden error referencing `target-secret`.
