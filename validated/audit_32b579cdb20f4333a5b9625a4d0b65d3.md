### Title
Native ETH sent to `Hinkal.transact` is permanently locked when `address(0)` is omitted from `erc20TokenAddresses` - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact()` is `payable` and accepts arbitrary `msg.value`, but the balance-equation check that reconciles native ETH received against the shielded/on-chain amounts is only executed for token slots that the caller chooses to list in `circomData.erc20TokenAddresses`. Nothing in `HinkalHelper.performHinkalChecks` / `dimensionsCheck` enforces that `address(0)` (the sentinel for native ETH) must be present in that array whenever `msg.value > 0`. If it is omitted, the ETH increases the contract's balance but is never validated, never turned into a UTXO/commitment, and never forwarded anywhere — it is stranded in the `Hinkal` contract with no admin/rescue/withdraw function to recover it.

### Finding Description
`transact()` is declared `payable`: [1](#0-0) 

The balance-equation loop that is supposed to tie every unit of value moved into/out of the contract to a UTXO or an external transfer only iterates over `circomData.erc20TokenAddresses`, and only applies the `msg.value` correction when it encounters an entry equal to `address(0)`: [2](#0-1) 

`performHinkalChecks` calls `dimensionsCheck` and `checkOnchainCreation`, but neither of these — nor any other check in `HinkalHelper.sol` — requires `address(0)` to appear in `erc20TokenAddresses` as a function of `msg.value`: [3](#0-2) [4](#0-3) 

Consequently, a caller (a user's own client, a relayer submitting on behalf of a user, or any EOA) can invoke `transact()` with `msg.value > 0` while supplying a `circomData.erc20TokenAddresses` array that does not contain `address(0)`. In that case:
- The proof/circuit checks still pass, since `msg.value` is not part of `calldataHash`/the public-input vector at all — it is only referenced directly in Solidity via `msg.value` inside the `Hinkal.transact` loop.
- The balance-equation loop never inspects `address(0)`, so the ETH increment is never checked against `circomData.slippageValues`, `circomData.amountChanges`, or any created UTXO.
- No commitment, no on-chain commitment, and no external transfer accounts for the received ETH.
- There is no rescue/sweep/withdraw function anywhere in the contracts checked (`Hinkal.sol`, `HinkalBase.sol`, `Transferer.sol`, `HinkalHelper.sol`) that would allow later recovery of stray ETH sitting on the `Hinkal` contract's balance (only `receive() external payable {}` exists in `HinkalBase.sol`, which accepts ETH with no bookkeeping).

This is the same bug class as the referenced report: a `payable` entry point accepts ETH that the rest of the code path has no mechanism to account for or retrieve, so the ETH becomes permanently locked in the contract.

### Impact Explanation
Any ETH included in a `transact()` call whose `erc20TokenAddresses` array does not include `address(0)` is permanently frozen inside the `Hinkal` contract, with no code path to withdraw or credit it to any UTXO, relay, or external recipient. This matches the "permanent freezing of user funds" Critical-tier impact category, and it also breaks the contract's core balance equation (`newBalances[i] + msg.value - oldBalances[i]` must equal the sum of on/off-chain UTXO changes for every tracked token) — ETH excluded from the array is fully invisible to that invariant.

### Likelihood Explanation
This does not require any privileged role, admin key, or malicious relayer collusion — a normal EOA (or a relayer wallet acting under `tx.origin == relay`) simply needs to attach `msg.value` to a `transact()` call whose `erc20TokenAddresses` list happens not to include `address(0)` (e.g. an ERC20-only swap/transfer where the caller's wallet or a buggy/compromised front-end mistakenly forwards leftover `msg.value`, or the relay attaches its own fee balance to the transaction). Since neither `dimensionsCheck` nor `performHinkalChecks` enforces any relationship between `msg.value` and the presence of `address(0)` in the token list, nothing in the contract prevents this.

### Recommendation
Add an explicit invariant in `Hinkal.transact` (or in `HinkalHelper.performHinkalChecks`) requiring that if `msg.value > 0`, `address(0)` must be present in `circomData.erc20TokenAddresses`; otherwise revert the transaction. Alternatively, remove `payable` from `transact()` entirely and require any ETH-denominated flows to go exclusively through `prooflessDeposit`, mirroring the fix applied for the analogous `sendZkSafeTransaction` issue (removing `payable` where the function offers no accounting/retrieval path for attached ETH).

### Proof of Concept
1. Caller (EOA or relayer) constructs a valid `circomData` for a pure ERC20-to-ERC20 shielded operation (e.g., an internal transfer/withdrawal) where `erc20TokenAddresses` contains only ERC20 token addresses, never `address(0)`.
2. Caller submits `transact(a, b, c, dimensions, circomData)` with `msg.value = X` (X > 0) attached to the call.
3. `performHinkalChecks` and `verifyProof` succeed, because none of the checks reference `msg.value` or require `address(0)` to be listed.
4. Inside `transact`, the `for` loop over `circomData.erc20TokenAddresses` (contracts/Hinkal.sol:97-146) never encounters `address(0)`, so the `X` wei received via `msg.value` is never validated, never assigned to a UTXO, and never transferred out.
5. The transaction completes successfully; the `Hinkal` contract's ETH balance has permanently increased by `X`, with no function in the contract capable of withdrawing or crediting that value back to anyone.
