Based on my research, I found a strong analog in `EvmHost.sol`'s native-token fee payment path, which performs unprotected AMM swaps on every dispatch — directly matching the report's bug class of "unprotected/insufficiently-protected AMM interaction on a reachable core path, exploitable via price manipulation."

### Title
Unprotected Uniswap V2 exact-output swap in `EvmHost` dispatch/fundRequest paths enables sandwich-attack value extraction from every native-fee dispatch - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` — the core, unprivileged, permissionless entry points any app or user calls to send a cross-chain message and pay in native token — swap `msg.value` for the exact `feeToken` amount required via `IUniswapV2Router02.swapETHForExactTokens`, with no minimum-price guard, no TWAP/oracle check, and no protection beyond the caller's own `msg.value` acting as an implicit (and mutable) upper bound on input.

### Finding Description
In `EvmHost.sol`, every dispatch that pays with native token executes: [1](#0-0) 

and identically in the GET-dispatch and fee-top-up paths: [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` computes the current spot price on the configured Uniswap V2 pool at execution time and pulls however much ETH is required to deliver the exact `post.fee`/`get.fee`/`amount` of `feeToken`, with the caller's `msg.value` as the only cap. There is no `amountInMax`-style parameter derived from a trusted price source, and no slippage/price-deviation check against a fair value. The project's own documentation acknowledges the pool's `getAmountsIn` "quote" is "vulnerable to sandwich attacks" and should only ever be used off-chain — yet the identical unguarded on-chain swap is what actually executes the payment: [4](#0-3) 

The identical unguarded pattern is duplicated in `IntentGatewayV2.sol`'s fee-collection logic, which also performs a `swapETHForExactTokens` against the host's Uniswap V2 router with no min-input/slippage bound: [5](#0-4) 

This mirrors the root cause pattern in the external Lido report: an on-chain AMM interaction that determines how much value a contract pays out, executed without any protection against the AMM's spot price being manipulated in the same transaction context (classic sandwich). In the Lido case a hardcoded 2.5% tolerance was too loose; here there is effectively *no* tolerance at all — the swap will consume as much ETH as the manipulated pool demands, up to whatever `msg.value` the caller supplied, and any dApp/wallet that pads `msg.value` with margin (as the docs explicitly instruct users/integrators to do, since exact fee is only knowable via an off-chain, sandwich-vulnerable quote) hands an attacker room to extract that margin via a front-run/back-run pair around the dispatch transaction.

### Impact Explanation
Every unprivileged call to `dispatch()`, `dispatch(DispatchGet)`, `fundRequest()`, and `IntentGatewayV2.placeOrder`/fee handling that pays in native token is exposed. An attacker monitoring the mempool can front-run the dispatch transaction to spike the WETH→feeToken price on the host's configured Uniswap V2 pool, causing the `swapETHForExactTokens` call to consume abnormally large amounts of the dispatcher's supplied `msg.value` margin to obtain the same fixed `feeToken` output, then back-run to restore the price and capture the difference as MEV profit. This is a protocol-wide, continuously-reachable value-leak on the primary message-dispatch surface (`EvmHost` — explicitly in scope per "EvmHost and HandlerV2 dispatch and delivery"), not a one-off app bug, and losses accrue on every native-paid dispatch across all EVM chains running this host.

### Likelihood Explanation
High. No privilege is required — any account can dispatch a POST/GET request or fund one with native token, and the vulnerable swap executes unconditionally whenever `msg.value > 0`. The docs already flag `getAmountsIn` pool pricing as sandwich-vulnerable for off-chain quoting, confirming the underlying pool/price-manipulation surface is known and reachable; the on-chain payment swap that actually executes value transfer carries the same exposure with zero mitigation.

### Recommendation
Do not let the AMM spot price at execution time be the sole determinant of how much native value is spent. Either: (1) require callers to pass an `amountInMax` bound derived from a recent trusted quote and revert if the actual required input exceeds it (rather than only being capped by whatever `msg.value` was sent), (2) use a TWAP or oracle-derived fair price to bound acceptable slippage on the swap, or (3) route native-fee payments through a more manipulation-resistant mechanism (e.g., require `feeToken` payment for programmatic dispatch, reserving the native-swap path for manually-reviewed, off-chain-quoted transactions with a tight, explicit slippage bound). Apply the same fix to `IntentGatewayV2.sol`'s fee-swap logic.

### Proof of Concept
1. Attacker observes a pending `dispatch(DispatchPost)` / `fillOrder`/`placeOrder` transaction paying native token, with the caller's `msg.value` padded above the expected fee to tolerate normal slippage (as recommended practice, since exact costs can only be estimated off-chain).
2. Attacker front-runs with a large swap on the host's configured Uniswap V2 WETH/feeToken pool, moving the spot price against the dispatcher.
3. The victim's `dispatch()`/`placeOrder()` call executes `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`; the router now requires far more ETH than fair value to deliver the fixed `fee` output, consuming most or all of the padded `msg.value`.
4. Attacker back-runs to restore the pool price, capturing the spread as profit extracted directly from the dispatching contract/user's supplied native value, repeatable on every subsequent native-paid dispatch.
