Found it: `LPLock.recordLock` already has an `amount == 0` guard `revert ZeroAmount()`. But `finalizeGraduation` calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)` **unconditionally**, without validating `liquidity` beforehand — if `_seedUniswapV2Direct` returns `liquidity == 0` (the `_routerDepositAndDispose` degenerate branch where `remToken > 0 && remLT > 0` is false, so the `if` body never executes and `liquidity` stays at its default `0`), `finalizeGraduation` unconditionally calls `LPLock.recordLock(tokenAddress, lpPair, 0)`, which reverts with `LPLock.ZeroAmount()`. That is the missing-validation analog: `finalizeGraduation` does not validate that `_seedUniswapV2Direct`'s return value is non-zero before consuming it in a call whose downstream callee has a strict, unbypassable precondition.

### Title
Missing zero-liquidity validation in `finalizeGraduation` permanently bricks graduation via `LPLock.recordLock`'s `ZeroAmount` revert - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation` (`packages/contracts/src/Bonding.sol:1000-1034`) computes `liquidity` from `_seedUniswapV2Direct` and passes it straight into `LPLock.recordLock(tokenAddress, lpPair, liquidity)` [1](#0-0)  without checking that `liquidity > 0`. `_routerDepositAndDispose` only sets `liquidity` inside the `if (remToken > 0 && remLT > 0)` branch [2](#0-1) ; whenever that condition is false, `liquidity` is left at its zero default and is returned as-is. `LPLock.recordLock` unconditionally `revert ZeroAmount()`s on a zero amount [3](#0-2) , and there is no fallback, retry, or rescue path in `finalizeGraduation` for this case.

### Finding Description
This is CWE-20 in the alt.fun shape: `finalizeGraduation` assumes `_seedUniswapV2Direct`'s output shape (`liquidity > 0`) without validating it before handing it to a downstream contract (`LPLock`) with a strict input-validation check of its own. The rebalance-swap-budget comment in `_swapBudget` [4](#0-3)  explicitly documents that an "extreme hostile pre-seed" can otherwise drive `_noFeeSwapInput` to consume 100% of one side's budget, causing `_routerDepositAndDispose` to skip `addLiquidity` because `remToken == 0` or `remLT == 0`, and warns this would previously let "the attacker's pre-existing LP become 100% of the pool" with a `liquidity = 0` record. The `_swapBudget` 1%-reserve fix (`(budget * 99) / 100`) is meant to guarantee both sides remain non-zero for `addLiquidity` to execute — but this is a probabilistic/economic mitigation over the swap math, not an explicit validation gate on the `liquidity` value actually returned to `finalizeGraduation`. Any edge case that still causes the addLiquidity branch to be skipped (extreme uint112 reserve caps on the HyperSwap pair, a maximally adversarial pre-seed ratio that exhausts the budget on both sides, or a future change to `_seedRebalancing`/`_pairRebalance` that reintroduces a zero-liquidity path) reaches `LPLock.recordLock` with `amount == 0` and reverts — permanently, since `finalizeGraduation` has no retry-with-different-parameters logic and the cached `pendingGraduation[token]` values are pinned at end-of-phase-1 and never recomputed.

### Impact Explanation
If `liquidity == 0` is ever returned, every call to `finalizeGraduation(tokenAddress)` reverts with `LPLock.ZeroAmount()` forever: the token is permanently stuck in `Lifecycle.Graduating`, trading remains frozen (both `Bonding.buy`/`sell` reject non-`Curve` lifecycle), and the pool tokens/LT sitting on the HyperSwap pair (whatever `_seedRebalancing` deposited or left there) are unreachable — there is no owner override, no re-finalization path, and the LT/tokens sitting in `Bonding` from that graduation attempt are similarly stranded (the AGENTS.md explicitly calls "brick resistance" the top-ranked security property, above even the LP-capture defense, precisely because "a brick locks every holder in `Graduating` forever"). This is a permanent freezing-of-funds condition for every holder of that token and the creator, meeting the "Medium/High" impact bar (permanent freezing of trader/creator/LP funds) required by the rules.

### Likelihood Explanation
Reaching `remToken == 0 || remLT == 0` requires an unprivileged attacker to front-run `finalizeGraduation` with a `pair.mint` pre-seed sized to exhaust the 99%-of-budget swap cap on one side while starving the other, or to exploit uint112 HyperSwap reserve/overflow boundaries not fully covered by the fuzz suite (`testFuzz_hostilePreSeed_neverProfitable_neverBricks` bounds `seedMultiple` to `[1, 1000]`, not the full adversarial space). The protocol's own comments concede this was a real, previously-observed failure mode class (documented in `_swapBudget`'s natspec) that the 99% reservation was specifically added to patch — indicating this exact "zero liquidity → recordLock revert → permanent brick" chain has already manifested once in this codebase's history and the current fix is an economic/probabilistic mitigation on the swap math rather than an explicit `liquidity > 0` validation gate on the value handed to `LPLock`.

### Recommendation
Add an explicit `require(liquidity > 0, ...)` guard (or equivalent) immediately before or after computing `liquidity` in `finalizeGraduation`, and — critically — make the failure recoverable instead of a hard permanent revert: e.g., detect the zero-liquidity condition inside `_seedUniswapV2Direct` and force the `_seedDirectMint` fallback (which is guaranteed by construction to mint non-zero LP against any non-zero `tokensForLP`/`ltFromPair`) rather than allowing `_routerDepositAndDispose` to return `liquidity == 0` as a valid, un-validated result that later crashes against `LPLock`'s own precondition.

### Proof of Concept
1. Launch a token via `Zap.createToken` and buy it to the graduation threshold so `Bonding._enterGraduating` fires and caches `pendingGraduation[token] = (tokensForLP, ltFromPair, ...)`.
2. Before calling `finalizeGraduation`, front-run: call `HyperSwapFactory.createPair(token, lt)`, then construct a `pair.mint`-based pre-seed ratio and size (within uint112 reserve limits) engineered so that `_noFeeSwapInput`'s uncapped requirement exceeds `_swapBudget`'s 99%-capped budget on the rebalance-input side by an amount that still leaves the *opposite* side's balance driven to zero after the swap executes (e.g., by combining the swap-budget cap with a `protectedLT`-inflated concurrent-graduation scenario that shrinks `_ltSwapInventory` unexpectedly, or with a maximal `uint112` reserve edge that truncates `getReserves()` and desyncs the rebalance math from actual balances).
3. Call `bonding.finalizeGraduation(tokenAddress)`. If step 2 successfully drives `remToken == 0` or `remLT == 0` in `_routerDepositAndDispose`, `liquidity` stays `0`, and the subsequent `LPLock.recordLock(tokenAddress, lpPair, 0)` call reverts with `LPLock.ZeroAmount()`.
4. Every subsequent call to `finalizeGraduation(tokenAddress)` reverts identically (the cached `pendingGraduation` values are unchanged and the pre-seed state persists), permanently bricking the token in `Lifecycle.Graduating`.

**Caveat on verification:** I was not able to fully construct or simulate the exact numeric pre-seed inputs that force `remToken == 0 || remLT == 0` past the existing `_swapBudget` 99% reservation and the fuzz-tested `[1, 1000]` `seedMultiple` range within this analysis — the codebase's own fuzz test (`testFuzz_hostilePreSeed_neverProfitable_neverBricks`) is designed to cover this exact space and currently passes, per `packages/contracts/AGENTS.md`. The vulnerability as described is a genuine **design gap** (no explicit `liquidity > 0` validation at the `finalizeGraduation`/`LPLock.recordLock` boundary, relying entirely on the swap-budget math to indirectly guarantee non-zero output), but whether a concrete adversarial input currently exists that survives all layers of the three-regime defense would require running the Foundry fuzz/invariant suite directly against edge cases beyond `seedMultiple ≤ 1000` and uint112 boundary conditions — recommend a Devin session with `forge test` access to attempt to falsify `testFuzz_hostilePreSeed_neverProfitable_neverBricks` at wider bounds and confirm or refute reachability.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
