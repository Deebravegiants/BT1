This confirms the reachability path: on the EVM side, the `data` field in `HyperFungibleToken.send()`/`WrappedHyperFungibleToken.send()` is fully attacker-controlled bytes forwarded verbatim in the cross-chain `Message.data` field [1](#0-0) , and once relayed and proven via ISMP, the substrate-side `pallet-hyper-fungible-token`'s `on_accept` decodes it into a `SubstrateCalldata` struct containing a raw `runtime_call: Vec<u8>` and calls `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` with **no depth limit** [2](#0-1) , unlike the sibling `pallet-call-decompressor`, which explicitly uses `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)` for the exact same purpose of decoding an attacker-supplied `RuntimeCall` [3](#0-2) .

### Title
Unbounded SCALE-decode of attacker-controlled `RuntimeCall` in `pallet-hyper-fungible-token::on_accept` enables stack-overflow DoS on message delivery - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s ISMP module decodes an unbounded, fully attacker-controlled byte blob into the runtime's top-level `RuntimeCall` enum using plain `Decode::decode` with no recursion-depth limit, while the codebase's own `pallet-call-decompressor` treats the identical operation (decoding an untrusted `RuntimeCall`) as dangerous enough to require `decode_all_with_depth_limit`.

### Finding Description
`on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` processes any incoming ISMP `PostRequest` from a registered peer contract [4](#0-3) . The message body's `data` field — populated by anyone calling `HyperFungibleToken.send()`/`WrappedHyperFungibleToken.send()` on the source EVM chain with an arbitrary `bytes data` payload [5](#0-4)  — is SCALE-decoded into `SubstrateCalldata` and then its inner `runtime_call: Vec<u8>` field is decoded straight into `T::RuntimeCall`:

```rust
let runtime_call = T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)
    .map_err(HftError::RuntimeCallDecodeError)?;
``` [2](#0-1) 

`RuntimeCall` is a deeply recursive enum on any FRAME runtime that includes pallets like `pallet_utility` (`batch`, `batch_all`, `as_derivative`) or `pallet_proxy`, so an attacker can encode a payload representing thousands of nested `Utility::batch(vec![Utility::batch(vec![...])])` calls. The SCALE `Decode` implementation for such nested enums recurses on the call stack proportional to nesting depth with no built-in bound. This is the exact same class of hazard the codebase already documents and defends against elsewhere: `pallet-call-decompressor` calls out the recursion-depth attack surface explicitly and enforces `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` via `decode_all_with_depth_limit` [6](#0-5) [7](#0-6) . The hyper-fungible-token module has no equivalent guard, and no size cap is enforced on `substrate_data.runtime_call` before decode either.

Unlike the IoTDB Java-deserialization gadget-chain scenario, this Rust analog cannot be leveraged for arbitrary code execution; the concrete impact is a crash/stack-overflow denial of service triggered inside `on_accept`, which executes during ISMP message handling in `pallet_ismp::Pallet::execute` (invoked from `handle_unsigned`/`handle`). A stack overflow inside block execution aborts the node process handling that block, which is a much more severe outcome than an ordinary panic-caught error, because Substrate's `Decode` recursion is not caught by `catch_unwind` the way ordinary logic errors are.

### Impact Explanation
Because `on_accept` runs during block-import/execution of any relayer-submitted ISMP message batch, a successful stack-overflow abort here crashes the node executing that block. Since the malicious message must be included in a block to be executed, an attacker (any token bridger, needing only a small bridged amount) can craft a `send()` call with a "call bomb" `data` payload; once relayed and delivered, every full node/validator that imports the block executing this message crashes, halting production and freezing the parachain's ability to deliver ISMP messages (and by extension the HFT token route and all pallets sharing that runtime) until node operators patch and resync — a "route unable to deliver messages" condition.

### Likelihood Explanation
Likelihood is high for chains that run `pallet-hyper-fungible-token` together with any pallet contributing recursive/nesting `RuntimeCall` variants (e.g. `pallet_utility`), since triggering it only requires: (1) registering/using any already-configured HFT peer contract and (2) a single cross-chain `send()` with a crafted `data` payload plus normal message relay — both fully within reach of an unprivileged token bridger/relayer, with no special permissions needed.

### Recommendation
Mirror the pattern already used in `pallet-call-decompressor`: decode `substrate_data.runtime_call` with `T::RuntimeCall::decode_all_with_depth_limit(MAX_DEPTH, &mut &*substrate_data.runtime_call)` (or an equivalent bounded-recursion decode) instead of plain `Decode::decode`, and additionally bound `substrate_data.runtime_call.len()` before attempting to decode it.

### Proof of Concept
1. On the source EVM chain, call `HyperFungibleToken.send(SendParams{..., data: <ABI-encoded Message.data>})` where the ABI-decoded `data` (interpreted on the destination as `SubstrateCalldata`) SCALE-encodes a `runtime_call` blob representing `N` nested `Utility::batch(vec![Utility::batch(vec![... ])])` calls, with `N` large enough to exceed the default thread stack size during recursive `Decode::decode`.
2. Relay the resulting ISMP `PostRequest` with a valid state/consensus proof to the destination parachain as normal.
3. When `pallet_ismp` executes the request and dispatches into `pallet-hyper-fungible-token::on_accept`, `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` at `modules/pallets/hyper-fungible-token/src/module.rs:189` recurses `N` times, overflowing the executor's stack and aborting the process handling that block — compare against `modules/pallets/call-decompressor/src/lib.rs:264-268`, which guards the same decode with a depth limit specifically to prevent this.
