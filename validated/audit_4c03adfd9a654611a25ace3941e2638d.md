### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates incoming webhooks by HMAC-validating only the raw request body, while the `shop` (and `topic`, `api_version`, `webhook_id`) values used to route and process the webhook are read directly from unauthenticated HTTP headers. This breaks the identity binding between "bytes verified by HMAC" and "shop the webhook is attributed to," allowing a multi-tenant app installer to forge a webhook for a *different* shop.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. The HMAC is computed over `to_signable_string`, which for `Webhooks::Request` is defined as just the raw body: [2](#0-1) 

However, the `shop` attribute — which is passed to the handler and used to determine which tenant/store the webhook data belongs to — is pulled straight from the unauthenticated `x-shopify-shop-domain` HTTP header, with no cryptographic binding to the signed payload: [3](#0-2) 

The constructor only checks for the *presence* of the `shop-domain` header, not that it is bound to the HMAC: [4](#0-3) 

The identity binding the gem should enforce is: `hmac == HMAC(raw_body || shop)`, but the actual code computes `hmac == HMAC(raw_body)` and independently trusts `header["shop-domain"]` for tenant attribution. Because the same `client_secret` is used to sign webhooks for every shop that installs the app, an attacker who controls their own shop installation can:
1. Trigger a webhook with an attacker-chosen body on their own store (Shopify signs it validly with the app's shared secret).
2. Capture the `(raw_body, hmac)` pair.
3. Replay the exact same body/HMAC to the app's webhook endpoint, but substitute `x-shopify-shop-domain` with a victim shop's domain.

`Utils::HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the forged shop identity to the handler: [1](#0-0) 

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged app-installer (someone who owns a store using the app, thus not privileged w.r.t. the app's other merchants) can make the app process data under a spoofed victim `shop` value with a body they fully control. Because mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) and any custom webhook handler trust `request.shop` for tenant-scoped side effects (data deletion, session lookups, cache keys, etc.), this can be leveraged to trigger cross-tenant actions against another merchant's data using only the attacker's own (validly signed) webhook traffic.

### Likelihood Explanation
Requires the attacker to be an app installer (a legitimate but unprivileged user of the multi-tenant app) capable of triggering at least one real webhook delivery from their own shop and capturing the request. No access to the app's `client_secret`, access tokens, or victim credentials is required — only observation/replay of their own valid webhook traffic with a header rewrite, which is fully within an unprivileged internet user's reach if they can reach the app's public webhook endpoint directly (bypassing Shopify's proxy, e.g., since apps often expose these endpoints publicly).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signable string used for HMAC verification, or otherwise cryptographically tie the header-derived shop to the signed payload (e.g., require the host application to cross-check `request.shop` against a shop already known/authorized in session storage before trusting it, and document this requirement clearly). At minimum, `to_signable_string` should not omit fields that downstream handler logic depends on for tenant attribution.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com` and register a webhook (e.g. `orders/create`).
2. Trigger an event in the attacker's shop; Shopify sends a POST to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and the raw JSON body.
3. Capture `raw_body` and `x-shopify-hmac-sha256`.
4. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` bytes; `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`) then invokes the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body, despite the request never having been signed for that shop.

        missing_headers = []
