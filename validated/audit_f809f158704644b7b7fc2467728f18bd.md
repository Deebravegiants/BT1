### Title
Webhook Shop/Topic Spoofing via HMAC Coverage Gap - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::HmacValidator` only authenticates the raw HTTP body of an incoming webhook. The `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` trusts and hands to the host application's handler are read from HTTP headers that are never included in the HMAC computation, so they can be freely rewritten without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` verifies exactly this signable string (the body) against the `hmac` header, and nothing else: [3](#0-2) 

`Registry.process` performs only this HMAC check, then dispatches directly using the unauthenticated header-derived `shop`/`topic`/`webhook_id`/`api_version` values: [4](#0-3) 

This is exactly the bug class described in the analog report: a field (`shop`) is acted upon by the finalize step (`Registry.process` → handler dispatch) without being covered by the same authentication check (`HmacValidator.validate`) used to justify trusting the record. The equality that is supposed to hold — "the shop that produced a valid HMAC" == "the shop passed to the handler as `WebhookMetadata#shop`" — does not actually hold, because the HMAC only proves the body came from a Shopify server holding this app's single, app-wide `client_secret`; it says nothing about which specific shop's header values accompanied that body.

Because a Shopify app's `client_secret` is shared across every shop that installs it, an unprivileged internet user can install the target app on their own store (a normal, permission-less onboarding action). Their own store will receive genuine, correctly-signed webhook deliveries to the app's endpoint. If the attacker points the webhook (or captures/forwards it through infrastructure they control, e.g. by using their own tunnel as the temporary delivery target during a "resend" or debugging flow) at the app's live endpoint while rewriting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to a victim shop's domain, the raw body and its HMAC remain untouched and therefore still validate. `Registry.process` will accept it and invoke the handler believing the event originated from the victim shop.

### Impact Explanation
Per this gem's own documented usage pattern, host apps key their persistence/business logic off `WebhookMetadata#shop` and `#topic` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), and mandatory topics like `customers/redact`, `customers/data_request`, and `shop/redact` are dispatched the same way: [5](#0-4) [6](#0-5) 

An attacker can forge which tenant a genuinely-signed webhook is attributed to, causing the host app to act on another merchant's behalf — a cross-tenant confusion condition (e.g., triggering data-redaction logic, cache/session invalidation, or business workflows for a shop the attacker does not control).

### Likelihood Explanation
Any user can install the target app on a free development store to obtain genuinely HMAC-signed webhook traffic, and no secret material or privileged account on the victim's side is required — only header manipulation of values that this gem never binds to the signature.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop` and `topic`) in the signable string used by `HmacValidator`, or otherwise cryptographically bind them to the HMAC (e.g., verify `shop` against a value embedded in the signed body, or require the caller to separately confirm the shop is one for which a session/webhook registration is known) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store; Shopify begins delivering real, validly-signed webhooks (e.g., `orders/create`) to the app's public webhook endpoint using the app's shared `client_secret`.
2. Capture one such delivery's exact `raw_body` and `X-Shopify-Hmac-Sha256` value (e.g., via a debugging proxy the attacker controls in front of their own endpoint, or Shopify's "resend webhook" tooling).
3. Replay the identical `raw_body` + `hmac` header to the app's live webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`).
4. `HmacValidator.validate` succeeds because it only checks `raw_body`/`hmac`, per `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-38`; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) then calls the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process attacker-supplied data as if it originated from the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
