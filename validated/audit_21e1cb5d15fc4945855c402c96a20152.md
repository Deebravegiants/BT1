## Finding: Webhook `shop` (and `topic`/`webhook_id`) Attribution Is Not Covered by the HMAC Signature

### Title
Webhook Shop/Topic Attribution Bypasses HMAC Binding, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are taken directly from unauthenticated HTTP headers. This breaks the identity binding `hmac-covers(shop) == shop-acted-on`, mirroring the reported analog class ("a field acted on but not covered by the HMAC").

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers that are never included in that signable string: [2](#0-1) 

`Registry.process` validates the HMAC purely over this body-only string and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

`HmacValidator.validate` simply calls `verifiable_query.to_signable_string` and compares against the computed HMAC — it has no notion that `shop`/`topic`/`webhook_id` even exist for this object: [4](#0-3) 

Because the raw body and the HMAC are valid together for *any* combination of headers, an unprivileged holder of one legitimately-signed `(body, hmac)` pair (obtainable by simply installing the app on their own, attacker-controlled shop and receiving a real webhook, or by capturing/replaying any webhook delivery they can trigger for their own tenant) can resubmit that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain or a different topic. `Utils::HmacValidator.validate(request)` still returns `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with the attacker's payload/topic of choice.

This is precisely the "identity binding" break called out in the rules: the field acted upon (`shop`) is not the field cryptographically covered by the HMAC.

### Impact Explanation
Any host application built on this gem that trusts `WebhookMetadata#shop` for tenant attribution (which is the documented and only intended use, per `docs/usage/webhooks.md` and `Registry.process`) can be tricked into applying an attacker-controlled payload to a victim shop's tenant context — e.g. treating a forged `app/uninstalled` or GDPR redact webhook, with attacker-chosen body content, as originating from a shop the attacker does not own. This is cross-tenant action attribution entirely enabled by this gem's own `Request`/`Registry` implementation, not a host-app misuse of an undocumented API.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to first obtain one valid `(raw_body, hmac)` pair, which any unprivileged party can do by installing the app on their own store (no special credential, no `api_secret_key`, no privileged account required) and capturing the webhook Shopify sends them, then replaying that exact pair to the endpoint with a forged `shop`/`topic` header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the request, e.g. via a nonce/signature per header set), so that `Utils::HmacValidator.validate` fails if any of these identity-bearing headers are altered independently of the body. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` unless they are covered by the same signature that gates `Errors::InvalidWebhookError`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. `orders/create`, with `raw_body = B` and header `x-shopify-hmac-sha256 = H` (valid for `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally changes `x-shopify-topic` to `app/uninstalled` if `B` matches a registered handler's expected shape, or simply reuses `orders/create`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The handler registered for that topic is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the host application processes the action as if it came from `victim-shop.myshopify.com`.
