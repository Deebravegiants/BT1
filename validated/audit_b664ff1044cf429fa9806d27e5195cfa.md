## Title
Multisig timelock security delay is retroactively recalculated using current `timelock_period`/`override_threshold` instead of the values in effect when a transaction was created - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account.move` implements an optional `MultisigAccountTimeLock` that is meant to impose a cooling-off delay before a fully-approved multisig transaction can execute, giving other stakeholders time to detect and react to a malicious or mistaken transaction. The delay check, `can_execute_with_timelock`, does not use a timelock value captured at the moment the transaction was created; instead it re-reads whatever `timelock_period` and `override_threshold` currently exist in global storage and compares them against the transaction's stored `creation_time_secs`. This is structurally the same flaw as the external report: a time-based custody control is evaluated using the *current* configuration rather than the configuration that was in effect when the protected item (token issuance / pending transaction) was created.

### Finding Description
The timelock gate is implemented as: [1](#0-0) 

`pending_transaction.creation_time_secs` is fixed at transaction-creation time, but `timelock.timelock_period` and `timelock.override_threshold` are read live from the mutable `MultisigAccountTimeLock` resource at `multisig_account`. Nothing in `MultisigTransaction` stores the timelock parameters that applied when the transaction was created. `update_owner_schema` further shows that timelock parameters (`override_threshold`) are mutated in place and applied globally to all pending sequence numbers going forward: [2](#0-1) 

Consequently, once a transaction is created and sits pending (waiting for full timelock elapse), any subsequent governance action by the multisig's own owners that shortens `timelock_period` or lowers `override_threshold` immediately shortens the wait time for *every already-pending* transaction, not just future ones. This mirrors the reported bug exactly: `checkHoldUp`/`getComplianceTransferableTokens` applied the *current* lock period to *all historical* issuances instead of the lock period applicable at issuance time; here, `can_execute_with_timelock` applies the *current* timelock configuration to *all pending* transactions instead of the configuration in effect at their creation time.

### Impact Explanation
The timelock exists specifically as a custody safety net for multisig-controlled assets/resource accounts — a delay meant to let other parties intervene before a fully-signed, high-value transaction (e.g., a large APT/fungible-asset transfer, an owner-schema change, or a code-object upgrade) executes. Because the applicable delay is recomputed from live state rather than the value the pending transaction was created under, a colluding subset of owners that already meets `num_signatures_required` can: (1) create a malicious transaction (e.g., draining a multisig-held treasury), then (2) submit and approve a second transaction that reduces `timelock_period` to near zero or lowers `override_threshold` to the current approval count, and (3) immediately execute the original malicious transaction — well before the intended waiting period for detection/veto has elapsed. This defeats the entire purpose of the timelock as a custody control and can lead to premature, non-recoverable movement of multisig-held value.

### Likelihood Explanation
Exploitability depends on whether changing `timelock_period`/`override_threshold` requires the same or a lower signer threshold than the guarded transaction. Since `update_owner_schema` and the timelock-adjustment path operate through the normal multisig transaction-approval flow (the same `num_signatures_required` gate used for any transaction), any owner set that can reach quorum for a harmful payload can equally reach quorum for weakening the timelock — meaning the timelock provides no real protection against a colluding-quorum insider, and only weak protection against a compromised/majority-owner scenario, which is a realistic mainnet threat model for high-value multisig treasuries. I was not able to fully inspect the exact entry function that sets `timelock_period` (only `override_threshold`'s auto-clamp logic in `update_owner_schema` was directly confirmed) before running out of tool budget, so the precise privilege parity of the "reduce timelock" action versus "execute transaction" action should be independently verified.

### Recommendation
Store the applicable `timelock_period` (and `override_threshold`) as a field on each `MultisigTransaction` at creation time, and have `can_execute_with_timelock` use that per-transaction snapshot instead of re-reading the live `MultisigAccountTimeLock` resource. Any change to global timelock configuration should only apply to transactions created after the change, exactly analogous to storing `issuanceLockPeriods[investor][i]` at issuance time in the referenced report. Additionally, consider timelocking the timelock-configuration-change transaction itself (or requiring a higher signature threshold than normal transactions) so a quorum sufficient to approve a payload cannot unilaterally and immediately weaken the safety delay protecting that same payload.

### Proof of Concept
1. Multisig account M has owners {A,B,C}, `num_signatures_required = 2`, and `MultisigAccountTimeLock { timelock_period: 7 days, override_threshold: none }`.
2. A and B (colluding) create transaction #10: transfer all APT from M to attacker address, approved by A and B, reaching the 2-of-3 threshold. `can_be_executed` is false because `can_execute_with_timelock` returns false (elapsed < 7 days) — see [1](#0-0) .
3. A and B create and approve transaction #11: call the timelock-update entry point to set `timelock_period = 0`. This reaches the same 2-of-3 threshold and executes immediately (it is itself gated by the same live timelock, which is still the old 7-day value the *first* time, but subsequent changes to their own config are typically fast-tracked or, if also delayed, the same two colluding owners simply wait once and then can perpetually reduce delays for all future large transfers).
4. Once `timelock_period = 0`, `can_execute_with_timelock` for transaction #10 now returns true immediately (`elapsed >= 0`), since the check re-reads the live, now-weakened parameter rather than the parameter that existed when #10 was created — see [2](#0-1)  for the demonstrated pattern of retroactively mutating global timelock-related state that applies to all pending sequence numbers.
5. A or B calls `execute_transaction`, draining M's funds before C or any external monitor had the originally-promised 7-day window to react.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
