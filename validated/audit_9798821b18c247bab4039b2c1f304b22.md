### Title
Webhook shop/topic/metadata attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The Celo report's root cause is a security-critical value (the implementation address) being taken from an untrusted, unauthenticated source (attacker-supplied calldata) rather than being cryptographically bound to the authorized action. The same class of bug exists in this gem's webhook processing: the tenant identity (`shop`) and other metadata delivered with a webhook are trusted from HTTP headers that are never covered by the HMAC signature check, breaking the required binding between "bytes verified" and "bytes acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

Yet `Registry.process` uses `request.shop`, `request.topic`, and `request.webhook_id` — all read directly from HTTP headers, not from the signed body — to build the `WebhookMetadata` passed to the application's handler: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`shop asserted in the "shopify-shop-domain" header == shop cryptographically bound to the delivered payload`

In this implementation, that equality is never checked — the HMAC only proves the request body was produced with the app's `client_secret`; it says nothing about which shop the header claims to be from. Because the `client_secret` is shared by the app across **all** installed shops (it is not a per-shop key), any two payloads signed with the same secret produce a valid HMAC regardless of which shop's header accompanies them.

### Impact Explanation
This breaks the tenant boundary the report's bug class targets: cross-tenant access. An attacker who is a legitimate installer of the app on their own shop can capture a valid `(raw_body, hmac)` pair from a real webhook delivered by Shopify to the app's webhook endpoint (e.g. by triggering an event on their own store while running a proxy/logger in front of their server, or simply reusing an identical minimal payload such as `{}` used by several topics/mandatory webhooks — see `test/webhooks/registry_test.rb` where `hmac` is computed purely over `"{}"`). They can then replay that exact `raw_body`/`hmac` pair to the shared webhook endpoint with a forged `shopify-shop-domain` header naming a *different* merchant. `HmacValidator.validate` will succeed (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the spoofed shop, causing the host application to process/store data attributed to a shop the attacker does not control — a cross-tenant data-integrity/confidentiality breach for apps that key any per-shop logic (session lookup, redaction requests, order processing, etc.) off `WebhookMetadata#shop`.

### Likelihood Explanation
Exploitability requires only: (1) being an installed merchant of the target app (no special privilege beyond ordinary app installation), and (2) obtaining one valid `(body, hmac)` pair, which is trivial for empty/near-empty payload topics (e.g. mandatory GDPR webhooks, or any topic whose payload can be made to match a previously captured body). No access to `api_secret_key`, access tokens, or TLS interception of the victim's traffic is required — the attacker signs nothing themselves; they reuse a signature that Shopify itself generated for their own legitimate webhook.

### Recommendation
Bind the identity fields to the signed content: include `shop`, `topic`, and `webhook_id` (or a canonical concatenation of the relevant headers) inside `to_signable_string`, or otherwise validate that the shop/topic in the headers match values embedded in and covered by the payload before constructing `WebhookMetadata`. At minimum, document and enforce that `request.shop` must not be trusted as a tenant key unless it is cross-checked against session/shop records established independently of the webhook headers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook with an empty/predictable body, e.g. the `customers/data_request` mandatory webhook, and captures the resulting `X-Shopify-Hmac-Sha256` header and raw body (`{}`), as shown to be sufficient for a valid signature in [5](#0-4) .
3. Attacker sends a POST to the app's webhook endpoint with the same raw body and HMAC header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` validates via `Utils::HmacValidator.validate(request)` (body-only) which passes, then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload was never actually generated for that shop [3](#0-2) .
