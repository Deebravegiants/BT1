This confirms the finding: the docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" via HMAC, and `data.shop` is documented as trusted, host-app-facing tenant identity — yet only the raw body is actually covered by the HMAC.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted for tenant identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `Registry.process` uses the unauthenticated `x-shopify-shop-domain` header value (`request.shop`) as the tenant identity passed to the host application's webhook handler. Because the shop identity is not bound to the HMAC signature, any actor who can produce one valid `(raw_body, hmac)` pair signed with the app's shared secret — most simply, an attacker's own free/dev store that has the same app installed and thus receives genuinely-signed webhooks — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares HMAC only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then forwards the caller-supplied `request.shop` straight to the handler as the trusted tenant identifier: [4](#0-3) 

The documented contract explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "the shop domain of the webhook", implying host apps can trust it as an authenticated tenant boundary: [5](#0-4) [6](#0-5) 

This is the same bug class as the report's core lesson: a field that is *acted upon* (here, the tenant-identifying `shop` used to route/attribute webhook data) is not covered by the cryptographic check that is supposed to authenticate the whole message (`hmac == HMAC(body)`, but tenant routing uses `shop != HMAC-bound`). The broken identity binding, stated as an equality: the app should require `shop_used_for_dispatch == shop_bound_by_signature`, but the gem instead enforces only `hmac == HMAC(body)` and separately trusts `shop_used_for_dispatch = header("x-shopify-shop-domain")`, which are independent, unlinked values.

Since a single Shopify app's `api_secret_key` is shared across every shop that installs it, any unprivileged individual can install a public app (or any app they can reach) on their own store, receive a genuinely HMAC-signed webhook for their own shop, and then replay that exact `(raw_body, hmac)` to the app's webhook endpoint while forging the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to any victim shop domain. `Registry.process` accepts it as valid and calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce (shop identity should only be trustable after HMAC validation). A host application that (as documented/intended) uses `data.shop` to key its data store, look up/scope records, or attribute the incoming body to a specific merchant, can be tricked into writing or acting on attacker-supplied data under another (victim) tenant's identity — i.e., cross-tenant data injection/corruption through this gem's own webhook verification API, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for an unprivileged actor: no access token, `client_secret`, or privileged account is required. Obtaining one authentic `(raw_body, hmac)` pair only requires installing any target app (many apps in the Shopify App Store can be freely installed) on the attacker's own development store and capturing one real webhook delivery, or simply reusing any legitimately-received webhook whose body content is attacker-influenceable/predictable (e.g., attacker updates their own store's data to control the body). The replay itself is a single unauthenticated HTTP POST with forged headers.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) to the HMAC-verified content, or independently authenticate the shop domain (e.g., cross-check `request.shop` against the session/shop that legitimately registered the specific `webhook_id`, or require the host app to verify `shop` is one of its installed, known shops before trusting it) before passing it to `WebhookMetadata`. At minimum, update `to_signable_string` and the verification flow so that the shop domain cannot be varied independently of the signed payload, and document clearly that `data.shop` is not currently cryptographically bound so host apps must not rely on it as an authenticated tenant identifier without additional checks.

### Proof of Concept
1. Attacker creates/uses their own Shopify development store (`attacker-shop.myshopify.com`) and installs the target app, which shares one `api_secret_key` across all installs.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`, e.g., `orders/create` with body `{"id":1,...}`, including a valid `x-shopify-hmac-sha256` header computed as `HMAC-SHA256(api_secret_key, raw_body)`.
3. Attacker captures this `(raw_body, hmac)` pair (they receive it directly since it's their own store, or trigger it themselves) and replays it to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body)` — this passes because `raw_body`/`hmac` are unchanged from the genuine delivery. [7](#0-6) 
5. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and processes/persists it as if it were an authentic webhook from the victim shop.
