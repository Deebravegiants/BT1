## Title
Outbound relayer reward claims (`claim_outbound_consensus_delivery_reward` / `claim_outbound_request_delivery_reward`) permanently revert once the treasury balance falls below the configured reward - (File: `modules/pallets/relayer/src/outbound_consensus.rs`, `modules/pallets/relayer/src/outbound_request.rs`)

### Summary
Both outbound-reward claim paths on `pallet-relayer` pay a fixed, governance-configured reward out of a single `TreasuryPalletId` account. Neither path checks treasury solvency before allowing the claim, and neither has any mechanism to reduce/redirect the payout if the treasury cannot cover it. Exactly like the referenced `distributor_contract#spend()`'s hardcoded `spend_limit` reverting `claim_rewards` once rewards exceed it, here the hardcoded reward amount reverts the claim once it exceeds the treasury's actual balance - and there is no way for the caller to request a partial/lesser amount.

### Finding Description
`process_outbound_consensus_delivery_claim` and `process_outbound_request_delivery_claim` are both reachable via unsigned, unprivileged extrinsics (`ensure_none(origin)`) that any relayer can submit after proving delivery: [1](#0-0) 

Both functions look up a flat, governance-set reward and unconditionally attempt to move it out of the treasury account: [2](#0-1) [3](#0-2) 

If `TreasuryPalletId`'s balance is below `reward` (drained by prior payouts, a misconfigured `set_outbound_consensus_delivery_reward`/`set_outbound_request_delivery_reward`, or simply never topped up enough), `Currency::transfer`/`Mutate::transfer` fails and the call returns `Error::<T>::OutboundRewardTransferFailed` / `Error::<T>::OutboundRequestRewardTransferFailed` — the whole extrinsic reverts. Crucially, the idempotency markers (`OutboundConsensusRotationsClaimed`, `OutboundRequestsClaimed`) are only inserted *after* the transfer succeeds, so the relayer that legitimately delivered the message/proof has no way to ever collect a reduced or partial reward — every resubmission of the exact same claim fails identically until governance/an operator manually tops up the treasury.

The codebase itself documents this as a deliberate, known hazard for a structurally identical reward path (`pay_position_reward` in `pallet-beefy-consensus-proofs`), explicitly contrasting the two behaviors: the position/rotation reward soft-fails to avoid blocking core consensus, but the "messaging proofs deliberately keep the hard error": [4](#0-3) 

This is the same bug class as the referenced money-market report: a hardcoded payout ceiling (there, `spend_limit`; here, treasury balance vs. a fixed `reward`) that a legitimate claimant cannot influence, causing their `claim_*` call to revert instead of degrading gracefully (e.g. paying out the available balance, queuing the shortfall, or reducing the reward).

### Impact Explanation
Relayers who correctly deliver hyperbridge-originated consensus proofs or requests earn no reward once the treasury cannot cover the configured amount — this is explicitly the relayer/reward accounting surface called out in scope. Because the failure is a hard revert with no partial payment and no persisted record of the pending obligation, the reward is effectively locked/unclaimable for that specific delivery until governance intervenes, discouraging relayers from continuing to service the given module/destination and creating a route (`outbound_consensus`/`outbound_request` delivery) that stops being reliably incentivized. Given the docs explicitly track `docs/outbound-request-incentivization.md`'s warning that `OutboundRequestRewardTransferFailed` requires the treasury to "hold enough balance," this is a real, currently-live operational risk rather than a hypothetical one.

### Likelihood Explanation
The treasury is a single shared pot funded manually by governance/operators (`Sudo::sudo(Balances::force_set_balance(...))` in the docs' own runbook) and drained by every successful claim across every configured module/destination and every consensus rotation. Any period of high relayer activity, a misconfigured (too-high) `set_outbound_consensus_delivery_reward`/`set_outbound_request_delivery_reward`, or simply insufficient top-ups will drain it below the fixed reward, and the very next legitimate claim will hit this revert. No malicious actor is required — this triggers under normal operational load, matching the "practicality" caveat used to downgrade the original finding to Medium.

### Recommendation
- Cap the payout to `min(reward, treasury_balance)` and pay out the available amount rather than reverting entirely, or
- Persist the claim (mark it claimed / record the shortfall) even when the transfer partially fails, so the relayer can be paid via a follow-up "top-up" mechanism instead of resubmitting an unbounded number of times, or
- Alert/gate new reward registrations (`set_outbound_consensus_delivery_reward`, `set_outbound_request_delivery_reward`) against the current treasury balance so operators can't configure an unpayable reward in the first place.

### Proof of Concept
1. Governance calls `set_outbound_consensus_delivery_reward(destination, REWARD)` (or `set_outbound_request_delivery_reward(module_id, REWARD)`) with `REWARD` larger than, or later draining, the `TreasuryPalletId` balance.
2. A relayer legitimately delivers the consensus rotation / hyperbridge-originated request to `destination` and is correctly recorded in `EvmHost._epochs[set_id]` / `RequestReceipts[commitment]`.
3. The relayer submits `claim_outbound_consensus_delivery_reward` / `claim_outbound_request_delivery_reward` with a valid state proof and signature.
4. `Currency::transfer`/`Mutate::transfer` from the treasury fails because its balance < `reward`; the call returns `Error::<T>::OutboundRewardTransferFailed` / `OutboundRequestRewardTransferFailed`, and no idempotency marker is written.
5. Every subsequent resubmission of the identical claim fails the same way — the relayer can never collect this reward until an operator manually funds the treasury, exactly mirroring the `spend_limit`-blocked `claim_rewards` behavior in the referenced report.

/// Same hazard, different source: an unpayable reward. `pay_position_reward` runs after the
/// caller has applied the rotation, so propagating `RewardTransferFailed` rolls it back — and
/// since the mandatory justification is the only one obtainable for that session, every retry
/// fails identically until the treasury is topped up, leaving consensus on the old set. The
/// reward is the cheaper thing to drop. Messaging proofs deliberately keep the hard error.
#[test]
fn an_unpayable_reward_cannot_block_a_rotation() {
	let mut ext = new_test_ext();
	let height = 800u64;

	ext.execute_with(|| {
		// The BEEFY proofs treasury holds nothing in genesis, so any non-zero reward makes the
		// transfer fail with `RewardTransferFailed`.
		ProofReward::<Test>::put(1_000_000u128);

		pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
			submitter(11),
			vec![PROOF_TYPE_SP1, 0xab],
			Some(H256::repeat_byte(11)),
			PROOF_TYPE_SP1,
			Vec::new(),
			rotation_outcome(height, 30),
		)
		.expect("an unpayable reward must not reject the rotation");

		assert_eq!(
			RotationProofs::<Test>::get().get(&30).copied(),
			Some(height),
			"the rotation must be recorded even though the reward could not be paid",
		);

		// The asymmetry is deliberate: reverting a messaging proof is recoverable, because the
		// next proof re-attempts the same work once the treasury can pay.
		assert!(
			pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
				submitter(12),
				vec![PROOF_TYPE_SP1, 0xac],
				Some(H256::repeat_byte(12)),
				PROOF_TYPE_SP1,
				Vec::new(),
				messaging_outcome(height + 1, 30),
			)
			.is_err(),
			"a messaging proof must still fail hard when the reward cannot be paid",
		);
