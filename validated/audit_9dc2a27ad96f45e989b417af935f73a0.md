### Title
Fee-on-Transfer Tokens Break Escrow Accounting in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrowed amount from the user-declared `order.inputs[i].amount` instead of the tokens actually received by the contract. This is the exact bug class described in the external report (fee-on-transfer tokens cause deposited/escrowed accounting to diverge from actual contract balance). The main EVM `IntentGatewayV2.sol` was hardened against this (it snapshots balances before/after the transfer and mutates `order.inputs[i].amount` to the actual received amount before computing fees/commitment/escrow), but the Tron copy of the same contract was not updated with this fix.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` computes `reducedInputs` (input minus protocol fee) and the order `commitment` directly from `order.inputs[i].amount` — the amount the user requested — before any token transfer occurs: [1](#0-0) 

It then transfers tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and credits the escrow mapping with the previously computed `reducedInputs[i].amount` — without checking what the contract's balance actually increased by: [2](#0-1) 

For any ERC20 with a transfer fee/burn/rebase-on-transfer mechanic, the contract receives strictly less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is credited with the full (fee-reduced-only-by-protocol-fee) nominal amount. This mirrors the reported bug in `TimeLockPool.deposit`, where the struct records the nominal amount while the contract's real balance is smaller.

By contrast, the primary EVM contract `evm/src/apps/IntentGatewayV2.sol` explicitly fixes this by snapshotting `balBefore`/`balanceOf` and setting `order.inputs[i].amount` to the actual delta received before fee computation and escrow crediting: [3](#0-2) [4](#0-3) 

The Tron deployment of the identical `IntentGatewayV2` app was not updated with this hardening, leaving it with the vulnerable pre-fix pattern.

### Impact Explanation
`_orders[commitment][token]` is the ledger used to pay solvers via `fillOrder`/`withdraw` and to refund users on `cancelOrder`/`RefundEscrow`, both of which transfer out the recorded escrow amount: [5](#0-4) [6](#0-5) 

If a fee-on-transfer token is used as an order input, the gateway's actual token balance will be less than the sum of all outstanding escrow entries for that token. The contract will still attempt to pay out the over-stated escrowed amount to solvers or refund the full nominal amount to cancelling users, drawing down other users' legitimately escrowed balances of the same token. Eventually, some user or solver will be unable to withdraw/redeem their entitled funds because the contract's real balance is insufficient — a permanent freezing/loss of funds for at least one party, and effectively insolvency of the escrow ledger for that token.

### Likelihood Explanation
This is directly reachable by any unprivileged user calling `placeOrder` on the Tron `IntentGatewayV2` with a fee-on-transfer/deflationary/rebasing ERC20 as an input asset — no special privileges are required. Whether this is exploited depends on whether such tokens are permitted as escrow inputs on the Tron deployment (the contract itself performs no allowlist check preventing fee-on-transfer tokens), so the vulnerability is live for any token meeting that description.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure the contract's token balance immediately before and after `safeTransferFrom`, and use the actual received delta (not the nominal `order.inputs[i].amount`) as the basis for the protocol fee calculation, the commitment hash, and the `_orders` escrow credit. This must also be applied consistently to the `predispatch`/`ICallDispatcher` sweep path within the same function, mirroring the balance-snapshot-and-diff pattern already implemented on the EVM `src` version.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., burns 1% on every `transfer`/`transferFrom`) and use it as `order.inputs[0].token` with `amount = 1000e18` when calling `placeOrder` on the Tron `IntentGatewayV2`.
2. `placeOrder` computes `reducedInputs[0].amount` from the full `1000e18` (minus only the protocol fee), and credits `_orders[commitment][token] = reducedInputs[0].amount` (~999.7e18 with a 30bps protocol fee).
3. The actual `safeTransferFrom` call at line 459 only delivers `990e18` (1% transfer fee) to the gateway; the contract's real token balance is `990e18`, but the escrow ledger says `~999.7e18` is owed.
4. When this order (and others sharing the same token) are filled/cancelled, the ~9.7e18 shortfall is drawn from other users' escrowed balances of the same token; the last withdrawer(s) will find `safeTransfer` reverting due to insufficient contract balance, permanently freezing their funds — reproducing the accounting break described in the original Merit Circle report, now analogous to `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 359-469.
