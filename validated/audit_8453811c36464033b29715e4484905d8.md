### Title
`WebhookMetadata#shop` is set from an unauthenticated header, not from anything covered by the webhook HMAC signature - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only signs and checks `request.to_signable_string` (the raw body). It never covers `request.shop`, `request.topic`, or `request.webhook_id`, which are read straight from attacker-suppliable HTTP headers. Once an unprivileged attacker owns a single valid `(raw_body, hmac)` pair for a topic they legitimately received on their own development shop, they can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value, and `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` whose `shop` field is the attacker's chosen victim domain.

### Finding Description
The binding under test is: *shop authenticated by the signature == shop used for dispatch*. Tracing the code shows this equality never holds because the signature side of the equation excludes `shop` entirely.

- `lib/shopify_api/webhooks/request.rb` `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [2](#0-1) 
- `Utils::HmacValidator.validate` recomputes the HMAC only from `verifiable_query.to_signable_string` (the body) and compares it to the received `hmac` header, never touching `shop` or `topic`: [3](#0-2) 
- `Registry.process` gates on that body-only HMAC check, then builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler: [4](#0-3) 

Exploit flow: the attacker creates their own development shop, installs the app, and lets it register a webhook (e.g. `orders/create`). Shopify delivers a legitimately signed callback: body `B`, headers including `x-shopify-shop-domain: attacker-shop.myshopify.com` and `x-shopify-hmac-sha256: HMAC(B, api_secret_key)`. The attacker now POSTs directly to the app's public webhook route (not through Shopify) with the identical body `B` and identical `x-shopify-hmac-sha256` value, but with `x-shopify-shop-domain` rewritten to `victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because it only recomputes over `B`. `Registry.process` then calls the registered handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though nothing about the signature was ever computed for, or tied to, that shop. The documented usage pattern forwards this trusted-looking value straight into shop-scoped work: [5](#0-4) .

None of the existing guards catch this: `HmacValidator.validate` only checks body integrity, not header/shop authenticity; there is no `ShopValidator.sanitize!`, `state` comparison, `JwtPayload aud` check, or session/host correlation anywhere in this call path, because `Registry.process` never constructs or consults a `Session`, JWT, or request host at all — it is a pure header/body pipeline. The Sorbet `sig`s only enforce that `shop` is a `String`; they do not enforce it originates from an authenticated source.

### Impact Explanation
An attacker who controls only their own shop and their own public webhook endpoint can force any app built on this gem to invoke a webhook handler with an attacker-chosen `data.shop` value and attacker-chosen `data.body` (their own legitimate event payload) attributed to an arbitrary victim shop domain of their choosing. Depending on the handler's logic (loading a session for `data.shop`, writing/deleting records keyed by `data.shop`, or triggering shop-lifecycle actions such as uninstall/redact handling), this is a genuine cross-tenant impact: one shop's (attacker's) traffic can cause reads or mutations scoped to another merchant's identity. This matches the Critical "cross-tenant access" category. The attack is fully repeatable: the attacker can replay the same captured body/HMAC pair against any victim domain string of their choosing, for every topic they can get a signed callback for.

### Likelihood Explanation
Preconditions are cheap and entirely within the "unprivileged attacker" capability set defined by the rules: create a dev shop, install the app, register at least one topic, capture one legitimate signed webhook delivery, then send a direct HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. No secrets, no TLS interception, and no privileged access are required. The only dependency is that the host app's handler actually uses `data.shop` for shop-scoped effects without independently re-verifying the shop (e.g. against an existing installed-shop record) — which the gem's own documented example encourages by passing `data.shop` straight through. This is highly feasible and repeatable against arbitrary victim domain strings.

### Recommendation
`Registry.process` (or `Request`) should not treat `shop`, `topic`, or `webhook_id` header values as trustworthy metadata equivalent to a signed claim. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be revalidated by the host app (e.g., checked against a shop that has an active, previously-established session/installation) before being used for any tenant-scoped read or write. Ideally, the gem should provide or require an explicit shop-existence/session check inside `process` before dispatching to the handler, rather than leaving cross-tenant validation entirely to downstream app code with no warning in the type signature.

### Proof of Concept
Minitest + WebMock plan (no live shop, no secrets beyond the test's own `ShopifyAPI::Context.api_secret_key`):

```ruby
def test_shop_header_is_not_covered_by_hmac_and_can_be_forged
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

  # "legitimate" delivery for attacker's own shop
  legit_headers = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    "x-shopify-webhook-id" => "id-1",
    "x-shopify-api-version" => "2024-01",
  }
  legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: legit_headers)
  assert(ShopifyAPI::Utils::HmacValidator.validate(legit_request))
  assert_equal("attacker-shop.myshopify.com", legit_request.shop)

  # replayed request: identical body + identical hmac, forged shop-domain header
  forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

  # Binding under test: shop authenticated by signature == shop used for dispatch
  # LHS: no shop is actually authenticated by the signature (signature is body-only)
  # RHS: dispatch uses request.shop == "victim-shop.myshopify.com"
  assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request)) # HMAC still passes

  handler_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| handler_shop = data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
  )

  ShopifyAPI::Webhooks::Registry.process(forged_request)

  # Fails the invariant: handler received a shop never tied to the signature
  assert_equal("victim-shop.myshopify.com", handler_shop)
  refute_equal(legit_request.shop, handler_shop)
end
```

This demonstrates that `WebhookMetadata#shop` (the RHS of the binding) can diverge from any shop actually authenticated by the request signature (the LHS, which does not exist for `shop` at all), confirming the cross-tenant risk originates in `lib/shopify_api/webhooks/registry.rb` and `lib/shopify_api/webhooks/request.rb`.
