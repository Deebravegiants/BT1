## Title
Webhook shop/topic/webhook-id headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the tenant-identifying `shop`, `topic`, `webhook_id` and `api_version` values are read verbatim from HTTP headers and never enter the signed payload. `ShopifyAPI::Webhooks::Registry.process` then hands these unauthenticated header values straight to the app's webhook handler as the trusted tenant identifier, breaking the intended binding between "the HMAC that proves this event is genuine" and "the shop the event is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled directly from HTTP headers with no cryptographic tie to the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e. the raw body) against the secret: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC passes, then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to the app's handler as authoritative identity fields: [4](#0-3) 

The intended identity binding should be:
`HMAC_valid(raw_body) ∧ shop == the shop that produced raw_body`

The actual binding enforced by the gem is only:
`HMAC_valid(raw_body)`

with `shop` (and `topic`/`webhook_id`) taken from an entirely separate, unauthenticated channel (headers). This is the same bug class as the report's `CyclicBoundedVec` issue — a structure is reconstructed/trusted using some fields (headers) that are not covered by the integrity check (HMAC) that is supposed to authenticate the whole record.

Critically, Shopify computes the webhook HMAC using the app's single `client_secret`, which is identical across **every merchant/tenant** that has installed the app. This means a valid `(raw_body, hmac)` pair generated for one shop is cryptographically indistinguishable from one for any other shop — the HMAC never encodes which shop it came from. The `shop` header is the only piece of data that ties a webhook delivery to a specific tenant, and it is exactly the field this gem fails to authenticate.

### Impact Explanation
Any unprivileged Shopify merchant who can install the target app on their own store (a normal, unprivileged action for any public/multi-tenant app) can capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from a webhook delivered to their own shop, then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header naming a victim tenant. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the event to the app's handler tagged with the attacker-chosen victim shop. This is a cross-tenant identity-binding break: the app cannot distinguish "an event that really happened on shop X" from "an event that happened on my own shop, relabeled as shop X." Depending on how the host app's webhook handler uses `data.shop` (which the gem's own documented `WebhookMetadata` API explicitly instructs handlers to trust as the tenant key), this enables cross-tenant data injection/corruption or triggering of shop-scoped business logic under a victim's identity.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (or otherwise arrange for one legitimate webhook delivery to reach them) and can send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. This is realistic for any publicly listed or multi-merchant Shopify app.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable content, or otherwise cryptographically bind them to the verified payload before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, the gem should document and/or enforce that consumers cross-check `request.shop` against a shop that is independently known to have a valid session/installation, rather than presenting it as a value implicitly validated by `HmacValidator.validate`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g. `orders/create`) so Shopify POSTs to the app's webhook endpoint with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body using the app's shared client_secret>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - body: attacker-controlled order JSON.
3. Capture `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, then send a new POST directly to the same webhook endpoint with:
   - Same body and same `X-Shopify-Hmac-Sha256`.
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` returns `true` (body/HMAC pair unchanged), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` even though the event never touched the victim's store, confirming the identity-binding gap in `lib/shopify_api/webhooks/request.rb` / `lib/shopify_api/webhooks/registry.rb`.
