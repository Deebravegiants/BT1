### Title
Webhook `shop` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` passes, then immediately builds `WebhookMetadata` using `request.shop` and `request.topic`, both of which are read straight from HTTP headers that are never included in the HMAC-signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled from headers that are excluded from the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` gates on this validation and then forwards the unauthenticated `request.shop`/`request.topic` values to the handler as if they were verified: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop installation (it is not a per-tenant secret), the HMAC over a given raw body is identical no matter which shop or topic it is delivered for. An unprivileged internet user who has legitimately received (or can otherwise obtain) one valid `(body, hmac)` pair for their own shop — for example a webhook with an empty/well-known body like `orders/create` with `{}` — can replay that exact body and hmac to the app's public webhook endpoint while substituting arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header values. `HmacValidator.validate` will still return `true`, because it never checks those headers, so `WebhookMetadata.shop`/`.topic` presented to the host application's handler is attacker-controlled even though the call site treats it as "verified by HMAC." This breaks the identity binding: shop authenticated (bytes actually verified = raw body only) ≠ shop acted upon (`request.shop` header, unauthenticated).

### Impact Explanation
This allows cross-tenant confusion: a handler that uses `WebhookMetadata#shop` to look up/act on a specific merchant's stored session or data can be tricked into processing data intended for shop A under the identity of shop B, since the library asserts the webhook was verified. This matches the "Critical - cross-tenant access" impact category, as it lets one tenant of a multi-tenant app forge events attributed to another tenant purely by controlling headers on an otherwise-valid signed body.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair — trivially available to any merchant who has installed the app (they receive real webhooks for their own shop) or to anyone who can observe a delivered webhook body (bodies for many topics, e.g. `app/uninstalled`, are near-static/predictable). No possession of `api_secret_key` or access token is required, satisfying the "unprivileged internet user" constraint. The main friction is that the raw body must match for the desired topic, which is easy for topics with minimal/no meaningful body content.

### Recommendation
Include `shop`, `topic`, `webhook-id`, and `api-version` (or at minimum `shop` and `topic`) in the signable string used for webhook HMAC verification, or independently cross-check the `shop-domain` header against the session/shop context the handler expects before dispatching. At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are not integrity-protected by `HmacValidator.validate` so consuming apps do not conflate "HMAC valid" with "headers authentic."

### Proof of Concept
1. Attacker installs app on `attacker-shop.myshopify.com`, triggers a webhook with a fixed/empty body (e.g., `{}`), and captures the delivered `X-Shopify-Hmac-Sha256` value `H` computed over that body using the app's shared `api_secret_key`.
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - body: `{}`
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or any registered topic whose real payload for some legitimate event is also `{}`/matches)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since only body bytes are checked at `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though `victim-shop` never sent this request, as shown by the field wiring in `lib/shopify_api/webhooks/registry.rb:198-199`.
