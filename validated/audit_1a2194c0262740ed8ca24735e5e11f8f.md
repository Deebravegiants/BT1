### Title
Non-standard ERC-20 tokens in `IntentGatewayV2.withdraw()` can silently fail while escrow accounting is marked spent, permanently freezing user/solver funds — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed order tokens with a raw low-level `.call()` to the token's `transfer` selector and only checks that the *call itself* did not revert — it never inspects the ERC-20 return value, and it decrements the escrow accounting **after** making that external call rather than before it. This is the exact bug class from the referenced report (a fund-release function that trusts an external, potentially non-conforming/`hook`-bearing token contract and updates its own bookkeeping only after the external interaction), reachable by any user through the fully permissionless `cancelOrder()`/`placeOrder()` flow with an arbitrary, attacker-chosen "token" address.

### Finding Description
`withdraw()` is the single internal function that releases escrow for both same-chain cancellation and cross-chain redemption/refund: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    for (uint256 i; i < len;) {
        ...
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }
        _orders[body.commitment][token] -= amount;   // accounting mutated only AFTER the external call
        ...
    }
```

Two defects compound here:

1. **Unchecked ERC-20 return value.** `token.call(...)` only reverts on failure to execute the low-level call; it does not decode the `bool` result. A large class of real-world and non-standard tokens (old USDT-style tokens, fee-on-transfer tokens, deflationary/rebasing tokens, or a token deliberately crafted by the order-placer since `order.inputs[i].token` is fully attacker-supplied at `placeOrder()`) can return `false` on failure without reverting. Because the code treats a merely-successful `.call` as a successful transfer, `_orders[body.commitment][token] -= amount` still executes and `_filled[body.commitment]` is already set — permanently marking the order as settled even though the beneficiary never received the tokens, which are now unrecoverable (no retry path exists once `_filled` is non-zero).

2. **Missing checks-effects-interactions / reentrancy guard.** The external transfer is performed *before* `_orders[body.commitment][token] -= amount`, and `cancelOrder()` (the sole user-reachable entry to `withdraw()`) has no `nonReentrant` modifier, unlike the audited mainline contract: [2](#0-1) 

Compare with the hardened mainline version, which explicitly decrements escrow *before* the transfer and guards `cancelOrder` with `nonReentrant`: [3](#0-2) [4](#0-3) 

and which has dedicated regression tests proving reentrancy must be blocked structurally: [5](#0-4) 

The Tron contract regressed both protections (raw `.call` instead of `SafeERC20.safeTransfer`, and post-interaction state update) relative to the mainline fix, for the identical fund-release code path.

### Impact Explanation
Any order placer can choose an arbitrary token contract as an order input (`order.inputs[i].token`, no allowlist enforced in `placeOrder()`), escrow it, and later cancel/redeem it. If that token (deliberately or incidentally) returns `false` on a failed `transfer` instead of reverting, the beneficiary receives nothing while the contract marks the order `_filled` and zeroes out `_orders[commitment][token]`. The tokens remain trapped in the `IntentGatewayV2` contract with no code path to recover them — a permanent freeze of funds, matching the "borrower can never get back the collateral" impact class from the referenced report. The missing CEI ordering additionally removes a defense-in-depth layer against reentrancy for any future code paths that call `withdraw()`.

### Likelihood Explanation
`placeOrder()` and `cancelOrder()` are both plain, permissionless, single-transaction entry points with no token allowlist, so any user can trigger this with a token they fully control. No relayer, governance, or consensus verification is required — the whole flow is reachable from one submitted transaction, satisfying the "single submitted transaction... token transfer" bar for this analog scan.

### Recommendation
- Replace raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with OpenZeppelin's `SafeERC20.safeTransfer`, as already used in the mainline `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`.
- Reorder `withdraw()` to decrement `_orders[body.commitment][token]` (and delete `TRANSACTION_FEES`) **before** performing the external transfer (checks-effects-interactions).
- Add a `nonReentrant` modifier to `cancelOrder()` (and any other externally reachable function that can reach `withdraw()`), matching the mainline `evm/src/apps/IntentGatewayV2.sol::cancelOrder`.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20-like contract whose `transfer(to, amount)` returns `false` (or reverts under a chosen condition) instead of moving balance, without ever throwing.
2. Attacker calls `placeOrder()` on `evm/tron/contracts/apps/IntentGatewayV2.sol` with `order.inputs = [{token: EvilToken, amount: X}]`, using `safeTransferFrom` to genuinely fund the escrow with `EvilToken` balance (attacker controls `EvilToken`'s `transferFrom` to succeed here).
3. Attacker (as `order.user`) calls `cancelOrder(order, options)` on the same chain. This reaches `withdraw()`.
4. Inside `withdraw()`, `token.call(...transfer(beneficiary, X)...)` returns `success = true` (low-level call executed) even though `EvilToken.transfer` internally returns `false`/no-ops.
5. `_orders[commitment][EvilToken] -= X` executes, `_filled[commitment]` is set, `EscrowRefunded` is emitted — the order is permanently marked settled, but the beneficiary's `EvilToken` balance never increased and the underlying value backing `X` (if `EvilToken` wraps or represents real value) is now unrecoverable by any user-facing function.
