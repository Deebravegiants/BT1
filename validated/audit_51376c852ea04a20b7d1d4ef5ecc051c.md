## Analysis

The reachable analog of the `_releaseIntervalSecs` bug class — "a field acted on but not covered by the HMAC" — exists in the webhook processing path.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop` (and `topic`) are read from HTTP headers that are never included in the HMAC-signed content: [1](#0-0) 

`Registry.process` validates the HMAC over that same `to_signable_string` (body only), then immediately trusts the *unauthenticated* `request.shop` header value to build the `WebhookMetadata` handed to the host app's handler: [2](#0-1) 

The documentation explicitly promises full authentication of the request, not just the body: [3](#0-2) 

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`HmacValidator.validate` authenticates only the raw request body (`request.to_signable_string`), but `Registry.process` uses the separate, HMAC-uncovered `shop-domain` (and `topic`) header to attribute the webhook to a tenant when invoking the handler.

### Finding Description
The identity binding that should hold is: `hmac_verified_bytes == bytes_used_for_tenant_attribution`. Here, `hmac_verified_bytes = @raw_body` only [4](#0-3) , while `bytes_used_for_tenant_attribution = headers["shopify-shop-domain"]` [5](#0-4) . `Registry.process` never checks that the `shop-domain` header is consistent with anything covered by the signature: it validates the HMAC and then blindly forwards `request.shop` into `WebhookMetadata` for the app handler [6](#0-5) .

Since Shopify's HMAC covers only the JSON body and never binds it to a particular shop, any `(raw_body, hmac)` pair obtained from a genuine webhook delivery to *any* shop that has the app installed (including a shop the attacker owns/controls) remains a valid `(raw_body, hmac)` pair for *every* other shop's domain, because the shared `client_secret` is the same across all merchants/tenants of a given app. An attacker who operates their own store with the app installed can trigger a real webhook (e.g., `customers/create`, `orders/create`) with attacker-chosen body content, capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair, and replay it directly to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim merchant's domain. `Utils::HmacValidator.validate` will report success because it only checks the body signature [7](#0-6) , and the handler will process attacker-controlled data as if it originated from the victim tenant.

### Impact Explanation
This crosses a tenant boundary: the gem hands the host application attacker-controlled payload content bound to a victim shop's identity, despite documentation stating the request is verified to have "indeed come from Shopify" for that shop [3](#0-2) . Depending on the handler registered by the host app (e.g., `app/uninstalled`, `customers/data_request`, `shop/redact`, order/customer sync handlers), this can lead to unauthorized cross-tenant state changes (fake data injected under another merchant's identity, forced app-uninstall cleanup logic, GDPR redaction triggered for the wrong shop, etc.), which matches the "cross-tenant access" High-impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/dev) merchant with the vulnerable app installed on their own store — no access to the app's `client_secret`, no privileged account, and no host-application misuse is needed. The `shop`/`topic` header spoofing is purely a client-side HTTP replay against the app's public webhook endpoint.

### Recommendation
Bind the tenant identity into the material that is HMAC-verified, or otherwise enforce the header/body match cryptographically — e.g., include the `shop-domain` (and `topic`) values in `to_signable_string`, or require the host application to independently confirm that `request.shop` corresponds to a shop with a currently valid, previously-stored session/webhook registration before trusting the payload. At minimum, update the documentation to clarify that only body integrity/authenticity is verified, not the shop attribution.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g. creates a customer) causing Shopify to POST a body `B` with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and a valid `X-Shopify-Hmac-Sha256: H` (computed with the app's shared `client_secret`) to the app's webhook endpoint.
3. Attacker intercepts/records `(B, H)` (e.g. via a proxy they control in front of their own endpoint, or by triggering the delivery to a URL they own first).
4. Attacker replays `POST /webhooks` directly to the target app instance with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body = B` [4](#0-3) .
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, believing it is authentic data for the victim tenant [8](#0-7) .

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
