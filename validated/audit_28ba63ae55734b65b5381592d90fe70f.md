### Title
Ceiling-rounded prioritization fee causes deterministic sub-unit overcharge - (File: compute-budget/src/compute_budget_limits.rs)

### Summary
`ComputeBudgetLimits::get_prioritization_fee` converts a transaction's `compute_unit_price` (denominated in micro-lamports per CU) into a lamport fee by multiplying by the compute unit limit and then rounding the result **up** to the nearest whole lamport, exactly mirroring the reported bug class: a fixed-granularity truncation/rounding step applied to a linear per-unit rate causes users to pay more than the mathematically exact amount they agreed to.

### Finding Description
The prioritization fee is computed as: [1](#0-0) 

`micro_lamport_fee = compute_unit_price * compute_unit_limit` is computed in micro-lamports, then `(micro_lamport_fee + (MICRO_LAMPORTS_PER_LAMPORT - 1)) / MICRO_LAMPORTS_PER_LAMPORT` performs a ceiling division back to lamports. This is confirmed by the unit tests, which explicitly assert the round-up behavior for fractional lamport amounts: [2](#0-1) 

This value becomes the transaction's actual `priority_fee_lamports`, which is charged from the fee payer and fed directly into `solana_fee::calculate_fee_details`/`calculate_fee` for signature+priority fee totals, and into reward/burn accounting: [3](#0-2) [4](#0-3) 

This is structurally the same class of bug as the reported `LoanManager` issue: a continuous, linear per-unit rate (interest-per-day vs. compute-unit-price-per-micro-lamport) is discretized via a coarse rounding step (ceiling to whole lamports vs. truncation to whole days) applied *after* multiplying by a variable quantity (days late vs. compute units), so the granularity of the rounding step, not the actual rate agreed upon, determines a nonzero portion of what is actually charged.

### Impact Explanation
Every transaction that sets a `compute_unit_price` whose product with `compute_unit_limit` is not an exact multiple of `1_000_000` micro-lamports is charged up to 1 lamport more than the value implied by its stated price. This is a real, deterministic value transfer from the fee payer to the fee/reward/burn pool on essentially all prioritized transactions network-wide, which is exactly the "unnecessary loss of funds" pattern the original report flags — though, like the original, the absolute magnitude per transaction is capped at under 1 lamport, making it a low-severity systemic rounding bias rather than an exploitable drain.

### Likelihood Explanation
This code path executes unconditionally for any transaction using `ComputeBudgetInstruction::set_compute_unit_price`/`set_compute_unit_limit` (the common priority-fee mechanism used on every cluster today), so the rounding is triggered with very high frequency, though each individual instance is capped to sub-lamport magnitude.

### Recommendation
None — the rounding is a deliberate design choice (ceiling ensures the protocol never under-collects due to integer truncation) rather than an accidental defect, and the per-transaction magnitude is bounded to under 1 lamport, so it carries materially lower and different risk profile than the original per-day late-interest issue. This is reported strictly as a structurally analogous rounding pattern per the task's bug-class mapping request, not as a newly discovered high-impact vulnerability.

### Proof of Concept
Using the existing test values: with `compute_unit_price = MICRO_LAMPORTS_PER_LAMPORT - 1` and `compute_unit_limit = 1`, `get_prioritization_fee` returns `1` lamport instead of `0`, i.e., a fee payer whose intended price implies `0.999999` lamports is charged a full `1` lamport — a ~0.0001% overcharge that scales (in aggregate, not per-tx) across all mainnet transactions using compute-unit pricing. fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}
