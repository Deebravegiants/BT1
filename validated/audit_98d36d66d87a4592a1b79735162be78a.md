### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop` field taken from an unsigned HTTP header as the tenant identity passed to the app's handler. Because the shared `client_secret` used to compute the HMAC is common to *every* shop that installs a given app, and the shop-domain header is not part of the signed material, any shop that has installed the app can capture one of its own genuine webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The gem accepts it as authentic and dispatches it to the app's handler as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC only over `verifiable_query.to_signable_string`, which for webhooks is the raw request body: [1](#0-0) [2](#0-1) 

The shop identity, however, is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the HMAC input: [3](#0-2) 

`Registry.process` only checks the HMAC, then forwards `request.shop` (the unsigned header value) straight to the app's handler as the tenant identifier: [4](#0-3) 

The `client_secret`/`api_secret_key` used to compute this HMAC is a single, app-wide secret (set once via `Context.setup`), not a per-shop secret — it is identical across all merchants who install the app. The documented usage pattern instructs developers to trust `data.shop` from the callback as the tenant/shop identifier without any additional binding check: [5](#0-4) 

The broken identity binding is:
`HMAC_valid(api_secret_key, raw_body) == true` should imply `shop_header == originating_shop`, but because `shop_header` is excluded from the signed bytes and `api_secret_key` is shared across all tenants of the app, `HMAC_valid` is true for *any* shop header paired with a previously-observed valid `(raw_body, hmac)` pair — regardless of which shop actually sent it.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), which the rules classify as Critical impact. A merchant who legitimately installs the app (an unprivileged actor with respect to other merchants' data) can capture one of the genuine webhook deliveries Shopify sends to their own endpoint (body + valid `x-shopify-hmac-sha256`), then resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop's domain. The gem's `Registry.process` will validate it as authentic and invoke the app's handler with `data.shop` set to the victim's domain, `data.topic`, and the replayed body — allowing the attacker to inject spoofed events (e.g., fake `orders/create`, `app/uninstalled`, `shop/redact`) attributed to a shop they do not control, which can poison the app's per-tenant data store, trigger unauthorized side effects (e.g., data deletion via `shop/redact`/`customers/redact` handling), or corrupt cross-tenant business logic keyed on `shop`.

### Likelihood Explanation
Likelihood is realistic: obtaining a genuine `(raw_body, hmac)` pair requires nothing more than installing the target app on any shop (a normal, low-privilege action any internet user can perform for public apps), then observing the webhook their own shop naturally receives. No knowledge of `api_secret_key` is required to exploit it — only the ability to replay previously observed valid bytes with a different header value, since the header is unauthenticated. The only extra requirement is that the replayed body needs to be plausible for the target topic/handler logic (many payload shapes, like `shop/redact`, are simple and generic enough to be shop-agnostic).

### Recommendation
Bind the shop identity to the authenticated material instead of trusting the unsigned header alone:
- Cross-check `request.shop` against a shop that is actually known to have this webhook registered/installed for this app (e.g., look up the webhook by `webhook_id`/topic registration state or an app-side installation record) before dispatching to the handler.
- Where feasible, incorporate the shop domain into the value being HMAC-verified, or require verification that the `shop-domain` header corresponds to a shop with a valid, still-installed session/access token, rejecting webhooks for shops with no active install.
- Document clearly that `data.shop` from `WebhookMetadata` is not cryptographically bound to the payload and must not be treated as an authenticated tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any user can do this for a public app).
2. Shopify sends a legitimate webhook to the app's endpoint:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, "note": "hello"}
   ```
3. Attacker captures this exact `Body` and `x-shopify-hmac-sha256` value (HMAC over `raw_body` only, per `lib/shopify_api/webhooks/request.rb#to_signable_string`).
4. Attacker replays the identical request to the app's webhook endpoint, only changing the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (HMAC only covers the unchanged body), and `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {...})`, even though `victim-shop` never sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
