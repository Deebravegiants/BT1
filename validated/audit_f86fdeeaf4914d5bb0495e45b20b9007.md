### Title
`CallDispatcher.dispatch()` is fully permissionless, allowing any attacker to drain tokens/ETH left in the shared dispatcher — (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no access control (no `onlyOwner`/`onlyGateway`/`onlyHost` modifier). It decodes an attacker-supplied `Call[]` array and executes `to.call{value: call.value}(call.data)` against any contract, with the only check being that `to` has code. This mirrors the Unibot root cause — a router/dispatcher entry point that performs a raw, attacker-controlled low-level call without validating the caller or the call target/selector — which let the Unibot attacker insert a `transferFrom()` to drain approved tokens. Here, since `dispatch()` is callable by anyone, any value the `CallDispatcher` instance is holding (tokens or native ETH), or any lingering ERC20 approval it has been granted, is reachable by an unrelated third party via a single unprivileged call. [1](#0-0) 

### Finding Description
`CallDispatcher` is the shared, generic call executor used by `IntentGatewayV2`/`IntentsBase` (for `predispatch.call` and `output.call`) and by `HyperFungibleToken`/`WrappedHyperFungibleToken` (`onAccept` executing `message.data` after mint/unlock). In every one of these call sites, the pattern is: push funds into the dispatcher, then call `ICallDispatcher(dispatcher).dispatch(calls)`, then sweep the dispatcher's resulting balance back out. [2](#0-1) [3](#0-2) 

Critically, `dispatch()` itself is `external` with **no caller restriction whatsoever**: [4](#0-3) [5](#0-4) 

The only validation performed is that the call target has bytecode (`extcodesize(to) != 0`); there is no restriction on `to`, `data`, `value`, or `msg.sender`. This is functionally identical to the Unibot root cause described in the report — an unvalidated function that lets an attacker insert an arbitrary call (including `transferFrom`) — except here the vulnerability is explicit: the dispatch function is public by design with zero gatekeeping, relying entirely on callers (IntentGatewayV2, HyperFungibleToken) always fully draining the dispatcher within the same transaction so nothing of value is ever left behind for an outsider to seize.

That invariant is fragile:
- In the intents flow, only the token addresses explicitly listed in `order.inputs`/`order.outputs` are swept after a `predispatch.call`/`output.call`; any other token type or excess native ETH produced as an unlisted byproduct of the attacker/solver-supplied call is left in the dispatcher (`evm/src/apps/intentsv2/IntentsBase.sol:498-533`, `evm/src/apps/IntentGatewayV2.sol:260-311`).
- The Uniswap/DeFi composability examples in the docs show calls that route through the dispatcher and can leave residual approvals or token balances on it (e.g., `approve(uniswapRouter, type(uint256).max)` issued as one of the dispatcher's own calls, or native ETH forwarded via `Call.value` — "demonstrating that the `CallDispatcher` can hold and forward native tokens"). [6](#0-5) 

Any of this residual value (dust tokens, native ETH, or a standing approval the dispatcher was granted as part of some other contract's swap route) becomes stealable by literally anyone, at any time after the original transaction, by directly calling `CallDispatcher.dispatch()` with a `Call{to: token, data: transfer(attacker, balance)}` or `Call{to: token, data: transferFrom(approver, attacker, amount)}` if the dispatcher holds an outstanding allowance.

### Impact Explanation
Since `dispatch()` is unprivileged and reachable by a single transaction from any address, it constitutes exactly the "unprivileged message dispatcher... reachable" class called out in scope. Concrete impact: theft of any tokens/ETH parked in (or approved to) the shared `CallDispatcher`, which is used by both the Intents system and the Hyper Fungible Token apps — a cross-cutting utility whose value is meant to only ever be transient within a single transaction but has no on-chain guarantee of that. This is a Medium-severity fund-theft vector matching the Unibot bug class (unvalidated arbitrary-call entry point draining value the contract was never supposed to expose to third parties).

### Likelihood Explanation
Likelihood is moderate: exploitation requires the dispatcher to actually be holding exploitable value at some point (e.g., an unswept dust token from a composable swap route, an ETH remainder, or a standing approval left by one of the example integration patterns shown in the docs). Given the intents/HFT sweep logic only accounts for explicitly enumerated tokens and the docs actively encourage patterns that grant approvals via dispatcher-executed calls, such residues are plausible in production usage, and once they exist, exploitation is trivial (single call, no proof, no timing constraints) for any address that notices the dispatcher's balance/allowance state.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a whitelisted set of authorized callers (e.g., the specific `IntentGatewayV2`/`HyperFungibleToken` instances that own it), or make the dispatcher single-use/ephemeral (deployed fresh per call via `CREATE2`/factory pattern) so no caller-independent contract instance persists with reachable value. At minimum, add an `onlyAuthorizedCaller` modifier and ensure every integration explicitly enumerates and sweeps *all* token types/ETH a predispatch/output call could produce, not just the declared input/output assets.

### Proof of Concept
1. A user places an intents order (or the HFT bridge delivers a message) whose `predispatch.call`/`output.call`/`message.data` routes through `CallDispatcher.dispatch()` and, as part of a multi-hop swap, causes the dispatcher to end up holding a small amount of an unlisted ERC20 token or leftover native ETH (only the declared `order.inputs`/`order.outputs` token types are swept — see `evm/src/apps/intentsv2/IntentsBase.sol:498-533`).
2. An unrelated attacker observes the dispatcher's balance (e.g., via `balanceOf`).
3. The attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, leftoverBalance)})]))` directly — no permission check prevents this per `evm/src/utils/CallDispatcher.sol:44-60`.
4. The call succeeds and the attacker receives the dispatcher's residual balance, funds that belonged to the protocol/users, not the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}
