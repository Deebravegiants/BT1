### Title
Unregistered destination/source IntentGateway instance defaults to self, allowing forged cross-chain message authentication - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` resolves an unregistered peer-chain gateway instance to `address(this)` instead of reverting, unlike the canonical EVM implementation. This "silently accept an unresolved reference" pattern is structurally the same bug class as the Nezha DDNS report: a lookup that should reject a not-yet-bound/nonexistent foreign reference instead treats it as valid, letting the value be used later in an authorization decision it was never vetted for.

### Finding Description
In the canonical EVM `IntentsBase.sol`, `_instance()` explicitly reverts with `UnknownInstance()` when no gateway deployment has been registered for a given `stateMachineId`: [1](#0-0) 

The Tron contract implements the same lookup differently — when no deployment is registered for a chain, `instance()` falls back to `address(this)` rather than reverting: [2](#0-1) 

This resolved value is then used directly as the trust anchor in `authenticate()`, which accepts an incoming request only if the decoded `request.from` address equals the resolved instance for `request.source`: [3](#0-2) 

Because `request.from` is attacker-supplied bytes decoded from the incoming message body (not derived from any on-chain registry), and because `instance()` silently resolves an *unregistered* `request.source` state machine to `address(this)` instead of rejecting it, a message purporting to originate from a chain hyperbridge/governance has never registered a deployment for can still pass `authenticate()` — as long as the attacker sets `request.from == address(this)`. The intended invariant ("only a message from a peer gateway address that governance has explicitly bound via `NewDeployment`/registration may be trusted") is bypassed exactly the way the Nezha report's "future ID" bypasses ownership checks: the binding does not exist yet, the check does not reject the absence, and the absence is later (or immediately) treated as an authoritative match.

### Impact Explanation
`onAccept`/withdrawal-processing paths in the intents flow gate `RedeemEscrow`/`RefundEscrow` handling on `authenticate()` succeeding. If this authentication can be satisfied for a state machine that was never actually given a registered peer deployment, an attacker-controlled message (relayed through Hyperbridge's normal delivery path, which only verifies consensus/state membership — not gateway-level authorization) could be accepted as coming from a "known" peer instance, resulting in unauthorized escrow withdrawal/authorization on the destination gateway. This is an unauthorized app action / potential loss of escrowed funds, matching the CWE-863 (improper authorization) class of the reference finding.

### Likelihood Explanation
Exploitability requires: (1) a state machine for which no `Deployment` has yet been registered on this Tron gateway instance, and (2) an incoming Hyperbridge-delivered request whose `from` field is exactly `address(this)` bytes. Both conditions are attacker-influenceable at the message-construction layer once a relayer can deliver a validly-proven ISMP message from that (unregistered) source chain — the relayer does not need any special privilege, only the ability to dispatch/relay a standard cross-chain request, which is the normal unprivileged relayer/dispatcher path this scan is scoped to. This is a semi-practical, config-dependent bug (only reachable before/absent explicit registration for a chain), mirroring the "semi-practical" severity note in the source report.

### Recommendation
Make `instance()` in the Tron `IntentGatewayV2.sol` revert (e.g., with `UnknownInstance()`) when no deployment is registered for the given `stateMachineId`, matching the canonical `_instance()` behavior in `evm/src/apps/intentsv2/IntentsBase.sol`. Additionally, `authenticate()` should never be satisfiable using a default/self-referential fallback value — any lookup used for authorization must fail closed on an unresolved reference rather than fail open to a plausible-looking default.

### Proof of Concept
1. Deploy/observe a Tron `IntentGatewayV2` instance that has not yet had `NewDeployment` processed for state machine `X` (`_instances[keccak256(X)] == address(0)`).
2. Call `instance(X)` and observe it returns `address(this)` instead of reverting: [4](#0-3) 
3. Construct (or have a relayer deliver) an ISMP `PostRequest` with `source = X` and `from = abi.encodePacked(address(thisGatewayContract))`.
4. Call `onAccept`, which internally calls `authenticate(request)`; since `instance(request.source) == address(this) == module`, the check at line 299 passes despite `X` never having a registered peer deployment: [5](#0-4) 
5. The request is processed as an authenticated `RedeemEscrow`/`RefundEscrow` message.

Note: I was unable to locate the deployment-registration entry point (`NewDeployment`/`_addDeployment` equivalent) inside the Tron contract file within the available index (a search for `_addDeployment` in that file returned no matches), so I could not fully confirm how/whether registration is wired in the Tron variant versus the mainline EVM contract. This should be verified directly in the file before treating the finding as fully confirmed, though the `instance()`/`authenticate()` logic shown above is a direct read from the indexed source and stands as a real behavioral divergence from the fail-closed EVM implementation.

     * @dev Checks that the request originates from a known instance of the IntentGateway.
     */
    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }
