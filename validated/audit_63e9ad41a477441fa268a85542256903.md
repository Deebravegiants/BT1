Audit Report

## Title
Value-transfer `CALL`s always get `ReentrancyProtection::AllowReentry`, defeating the stipend-based anti-reentrancy heuristic - (File: substrate/frame/revive/src/vm/evm/instructions/contract.rs)

## Summary
In `run_call`, the tuple match that selects `add_stipend`/`ReentrancyProtection` places `(false, _) => (true, ReentrancyProtection::AllowReentry)` before `(_, true) => (true, ReentrancyProtection::AllowNext)`. Since Rust evaluates match arms top-to-bottom, any call with nonzero `value` matches the first arm regardless of `gas_limit`, so the `AllowNext` stipend heuristic can never be reached when `value != 0`, even when `gas_limit == CALL_STIPEND` (2300) — exactly the pattern produced by Solidity's `.transfer()`/`.send()`.

## Finding Description
`run_call` computes the protection mode as:
```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
``` [1](#0-0) 

`value.is_zero()` returns `false` whenever value is transferred, so `(false, true)` (nonzero value + stipend gas) is caught by the first arm before the second arm's `(_, true)` guard can match. This makes the `AllowNext` heuristic arm dead code for any nonzero-value call. The resulting `reentracy` value is passed directly into `interpreter.ext.call(...)`. [2](#0-1) 

The pallet's own documentation for `ReentrancyProtection::AllowNext` explicitly describes its purpose as protecting exactly this case: "This is used for calls that transfer value but restrict gas so that the callee only has a stipend gas amount... we enforce it explicitly here." [3](#0-2) 

Downstream, `Stack::call` in `exec.rs` only clears `top_frame_mut().allows_reentry` (blocking further reentrancy into the same contract) when `allows_reentry == ReentrancyProtection::AllowNext`; for `AllowReentry` no such restriction is applied. [4](#0-3)  This confirms the branch ordering bug has a real behavioral effect: the intended stipend-based reentrancy guard is bypassed for value-carrying calls.

## Impact Explanation
Any contract relying on the classic Solidity `.transfer()`/`.send()` gas-stipend idiom for reentrancy safety will not get the `AllowNext` protection that the engine's own heuristic is designed to grant for that exact call shape. Because `AllowReentry` imposes no restriction on `top_frame.allows_reentry`, a malicious receiving contract's fallback can reenter the calling ("victim") contract during a value transfer, enabling the classic reentrancy attack pattern (double-spend/fund draining) that the stipend convention is meant to prevent.

## Likelihood Explanation
This is reachable by any unprivileged user through ordinary contract deployment and execution: deploy a victim contract using `.transfer()`/`.send()` and an attacker contract with a reentrant fallback, then invoke the victim via a normal extrinsic. No privileged origin or governance action is required, and the triggering condition (`value != 0`, `gas_limit == CALL_STIPEND`) is the default compiler output for the idiomatic Solidity pattern, not a contrived edge case.

## Recommendation
Reorder the match arms so the stipend check is evaluated before the blanket nonzero-value case:
```rust
let (add_stipend, reentracy) = match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND)) {
    (_, true) => (true, ReentrancyProtection::AllowNext),
    (false, _) => (true, ReentrancyProtection::AllowReentry),
    (_, _) => (false, ReentrancyProtection::AllowReentry),
};
```
This ensures any call with `gas_limit == CALL_STIPEND` (value zero or nonzero) receives `AllowNext`, matching the documented intent in `ReentrancyProtection::AllowNext`'s doc comment, and only unrestricted-gas value transfers receive `AllowReentry`.

## Proof of Concept
1. Unit-test `run_call`'s match logic directly: for `value != 0 && gas_limit == CALL_STIPEND` assert the returned `reentracy` is `ReentrancyProtection::AllowNext`; this assertion fails against the current code, which returns `AllowReentry`.
2. Integration test (in `substrate/frame/revive/src/exec/tests.rs` style, using `MockLoader`/`MockStack`): deploy a `Victim` contract with a withdraw function that performs balance transfer via `CALL` with `value != 0` and `gas_limit == 2300` before finalizing its internal ledger, and an `Attacker` contract whose fallback calls back into `Victim.withdraw`. Fund `Victim`, invoke `withdraw` from `Attacker` via a normal extrinsic, and observe multiple nested withdrawals succeed (proving the reentrancy gate did not activate) because `interpreter.ext.call` was invoked with `ReentrancyProtection::AllowReentry` instead of `AllowNext`.
