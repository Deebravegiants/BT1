### Title
`createWithdrawalIntents` skips the `FeeExceedsAmountError` guard, letting `signAndSendWithdrawalIntent` sign a zero-output withdrawal that fully consumes `amount` as fee - ([File: packages/intents-sdk/src/sdk.ts])

### Summary
`IntentsSDK._estimateWithdrawalFee` throws `FeeExceedsAmountError` when `feeInclusive: true` and `amount <= fee.amount`, but the actual execution path used by `signAndSendWithdrawalIntent` — `IntentsSDK.createWithdrawalIntents` — recomputes `actualAmount = amount - feeEstimation.amount` without that guard and hands it straight to the bridge. For `DirectBridge` (`nep141:...` / `NearWithdrawal`), neither `validateWithdrawal` nor `createWithdrawIntentPrimitive` reject a zero (or negative) amount, so a withdrawal where `amount === feeEstimation.amount` is signed and published: the `token_diff` intent still debits the user for the full storage-deposit fee, while the final `ft_withdraw`/`native_withdraw` transfers `0` to the destination.

### Finding Description
The invariant that should hold is: `sum(debits in produced intents) == amount` (feeInclusive case) and `destination receives amount - fee > 0`, with a hard failure before signing otherwise.

- `IntentsSDK._estimateWithdrawalFee` enforces this only when the SDK itself computes the fee: [1](#0-0) 
- `IntentsSDK.createWithdrawalIntents`, which is the method actually invoked by `signAndSendWithdrawalIntent`, recomputes `actualAmount` the same way but has **no** equivalent check: [2](#0-1) 
- `signAndSendWithdrawalIntent` calls `this.createWithdrawalIntents` directly with a caller-supplied `feeEstimation`, never routing through `_estimateWithdrawalFee`: [3](#0-2) 
- `DirectBridge.validateWithdrawal` only checks the destination address (validity, not-equal-to-token, existence) — it never inspects `amount` at all, ignoring `skipMinAmountValidation`/`feeEstimation` entirely: [4](#0-3) 
- `DirectBridge.createWithdrawalIntents` still pushes the `token_diff` swap for the storage-deposit fee, then builds the `ft_withdraw`/`native_withdraw` intent with whatever `amount` it was given, with no positivity check: [5](#0-4) 
- `createWithdrawIntentPrimitive` simply serializes `amount.toString()` — `"0"` is a perfectly valid, on-chain-acceptable value: [6](#0-5) 

Reachable, non-malicious flow: an integrator calls `estimateWithdrawalFee` once (e.g. with a placeholder `amount`, or reuses a previously fetched fee for `wrap.near`'s storage-deposit gap that is quoted via `token_diff` for non-`wrap.near` assets), then later calls `signAndSendWithdrawalIntent({ withdrawalParams: { amount, feeInclusive: true, ... }, feeEstimation })` where the user's chosen `amount` happens to equal (or, if not filtered upstream, be less than) `feeEstimation.amount`. Because this path bypasses `_estimateWithdrawalFee`'s `FeeExceedsAmountError` check and `DirectBridge.validateWithdrawal` has no amount check of its own, `actualAmount` is `0` (or negative), and the SDK signs and publishes:
1. a `token_diff` intent debiting the user the full `feeEstimation.quote.amount_in` of the withdrawal asset (or the raw NEAR fee amount if asset is `wrap.near`), and
2. an `ft_withdraw`/`native_withdraw` intent moving `0` to the destination.

The whole `amount` requested is consumed as fee while the destination receives nothing.

### Impact Explanation
The user's `intents.near` balance is debited by the entire requested `amount` (via the fee-swap `token_diff`), while the withdrawal that reaches the destination chain is `0`. This is a complete fee overcharge for the affected withdrawal — the invariant "destination receives `amount - fee`, non-negative, or throw" is violated for the exact-equal case, matching "a fee error draining a material share of the amount" / "fee overcharge" from the listed impact categories. The loss is scoped to whichever withdrawal call hits this boundary condition and is repeatable per call.

### Likelihood Explanation
Requires: (a) a `DirectBridge` (nep141 NEAR) withdrawal, (b) `feeInclusive: true`, (c) a `feeEstimation` supplied directly to `signAndSendWithdrawalIntent` (rather than obtained fresh via the SDK's `estimateWithdrawalFee` immediately before signing with the same `amount`), and (d) `amount` equal to (or below) `feeEstimation.amount`. This is plausible in normal integrator flows that separate fee estimation from amount selection (e.g., "estimate first, let user decide/sweep balance, then submit"), and requires no crafted malicious input — an ordinary user withdrawing a small remaining balance close to the storage-deposit fee can trigger it unintentionally. No special privileges are needed.

### Recommendation
Add the same `amount <= feeEstimation.amount` (feeInclusive) guard to `IntentsSDK.createWithdrawalIntents` before computing `actualAmount`, and additionally have `DirectBridge.validateWithdrawal` reject non-positive `amount` regardless of `skipMinAmountValidation`.

### Proof of Concept
Vitest plan (mock only HTTP for storage-balance/quote lookups used inside `DirectBridge.estimateWithdrawalFee`, not the assertions):
1. Construct a `DirectBridge`-supported `withdrawalParams` for a non-`wrap.near` nep141 asset with `feeInclusive: true` and `amount = F` (a bigint).
2. Construct a `feeEstimation` object with `amount = F`, `quote: { defuse_asset_identifier_in, defuse_asset_identifier_out, amount_in: "<F converted>", amount_out: "<near amount>", quote_hash }`, `underlyingFees: { [RouteEnum.NearWithdrawal]: { storageDepositFee: F } }`.
3. Call `sdk.signAndSendWithdrawalIntent({ withdrawalParams, feeEstimation })` with a stub `IIntentSigner`/`IIntentRelayer` that captures the produced `intents` array instead of hitting the network.
4. Parse the produced intents: find the `token_diff` intent and the `ft_withdraw`/`native_withdraw` intent.
5. Assert `BigInt(ft_withdraw.amount) === 0n` while `token_diff.diff[assetId] === "-" + feeEstimation.quote.amount_in` — showing the full `amount` was consumed as fee for a `0`-value withdrawal, i.e. `sum(debits) === amount` but `destination_received === 0`, which per the stated invariant should have thrown `FeeExceedsAmountError` before signing but did not.

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	destinationAddress: string;
	amount: bigint;
	storageDeposit: bigint;
	msg: string | undefined;
	logger?: ILogger;
}): IntentFtWithdraw | IntentNativeWithdraw {
	if (
		params.assetId === NEAR_NATIVE_ASSET_ID &&
		// Ensure `msg` is not passed, because `native_withdraw` intent doesn't support `msg`
		params.msg === undefined
	) {
		return {
			intent: "native_withdraw",
			receiver_id: params.destinationAddress,
			amount: params.amount.toString(),
		};
	}

	const { contractId: tokenAccountId, standard } = utils.parseDefuseAssetId(
		params.assetId,
	);
	assert(standard === "nep141", "Only NEP-141 is supported");
	if (params.msg !== undefined) {
		params.logger?.warn(
			"min_gas is not set for direct-bridge withdrawal with msg, gas consumption is unpredictable",
		);
	}

	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: params.destinationAddress,
		amount: params.amount.toString(),
		storage_deposit:
			params.storageDeposit > 0n ? params.storageDeposit.toString() : undefined,
		msg: params.msg,
		// Only set min_gas when msg is not provided (simple ft_transfer).
		// When msg is present, ft_transfer_call is used and gas consumption is unpredictable.
		min_gas: params.msg == null ? MIN_GAS_AMOUNT : undefined,
	};
}
