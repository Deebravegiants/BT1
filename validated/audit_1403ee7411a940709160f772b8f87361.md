### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body. However, the `shop`, `topic`, `api_version`, and `webhook_id` values — which are taken from unauthenticated HTTP headers — are never included in the signed payload. Any party who possesses one legitimately-signed webhook (e.g., an attacker who owns their own Shopify development store and receives webhooks for it) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different shop, and the signature check will still pass.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" bug class: the equality the code implicitly assumes is `shop_the_signature_was_computed_for == shop_the_handler_acts_on`, but only the body is signed, so this equality does not hold. An unprivileged attacker who operates their own Shopify store receives a validly-signed webhook (body + HMAC) for their own shop. They can then POST that identical body/HMAC to the target app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a victim shop's domain (and/or forging `X-Shopify-Topic`, `X-Shopify-Webhook-Id`). `HmacValidator.validate` still succeeds because it only checks the body, and the app's handler receives `WebhookMetadata` claiming the victim shop sent this data.

### Impact Explanation
This breaks the shop-identity binding a webhook consumer relies on to determine which merchant/tenant the payload belongs to. Any app that keys its side effects (data updates, entitlement changes, redaction processing for GDPR topics, order/inventory sync, etc.) off `data.shop` is exposed to cross-tenant data confusion: attacker-controlled (replayed) content can be attributed to, and processed under, a different tenant's identity. Since app authors are directed by this library's own documentation to trust `Registry.process`/`WebhookMetadata` as the authentication boundary for webhooks, this qualifies as a cross-tenant access issue originating in the gem's verification logic.

### Likelihood Explanation
Requires no privileged credentials: any actor with a Shopify store (even a free development store) can register a webhook for their own shop, capture a legitimately-signed request, and replay it against a target app's public webhook endpoint with modified headers. The `api_secret_key` is never needed by the attacker because the signature check ignores the header fields being spoofed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) into the signable payload used for HMAC verification, or otherwise cryptographically tie the header-derived shop to the verified body (e.g., require the caller to additionally verify the shop against a per-shop webhook secret or an out-of-band registered webhook ID/shop mapping) before dispatching to `handler.handle`.

### Proof of Concept
1. Attacker registers a webhook for `attacker-shop.myshopify.com` and receives a real webhook from Shopify:
   - Body: `{"id":123}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid-for-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
2. Attacker resends the exact same raw body and `X-Shopify-Hmac-Sha256` value to the victim app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — identical to step 1 — so validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...)`, causing the app to process attacker-supplied content as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
