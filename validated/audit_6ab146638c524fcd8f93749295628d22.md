### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant routing directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. This breaks the identity binding `hmac_signed_bytes == authenticated_shop`, allowing the `shop` field passed into the app's webhook handler to be forged independently of the value the HMAC actually authenticates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from a header that is never included in that signable string: [2](#0-1) 

`Registry.process` validates the HMAC against `request` (i.e., only the body), and then unconditionally forwards `request.shop` into `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature purely over `to_signable_string`: [4](#0-3) 

Because the `shop-domain` header sits entirely outside the HMAC-signed bytes, an attacker who can obtain any single valid `(body, hmac)` pair signed with the app's `api_secret_key` for one merchant/shop (e.g., from their own store's legitimately delivered webhook, which they fully control) can resend the exact same body and HMAC while substituting an arbitrary value in the `shop-domain` header. `Registry.process` will accept the HMAC as valid (since it only checks the body) and will pass the attacker-chosen `shop` through to the handler as `WebhookMetadata#shop`. This is the analog to the reported bug class: a value that is *acted on* (the shop used for tenant routing) is not *covered by* the same authentication check (HMAC) that gates acceptance of the request — i.e., "bytes verified" (raw body) ≠ "identity used downstream" (shop header).

### Impact Explanation
Any app that uses `WebhookMetadata#shop` (as intended/documented by this gem) to decide which merchant's session/data record to update is exposed to cross-tenant data corruption or disclosure: an attacker with a legitimate low-privilege shop install can cause their own webhook deliveries to be attributed to a different (victim) shop identifier inside the host app, since the gem itself performs no binding between the authenticated bytes and the shop identity it hands out. This matches the Critical category of "cross-tenant access" since it lets an unprivileged, authenticated user of the app manipulate data attributed to another tenant purely through this gem's webhook-processing API.

### Likelihood Explanation
Exploitation only requires the attacker to control a shop where the app is installed (an ordinary unprivileged merchant/tenant, not a privileged account) and to be able to send an HTTP request to the app's webhook endpoint with a captured `(body, hmac)` pair and a modified `shop-domain` header — no `api_secret_key`, access token, or other secret is needed, since the header is not part of what's verified. The likelihood is bounded only by whether the app's webhook endpoint accepts headers set by the request sender (true for any standard reverse-proxy setup where these are passed through) and whether it relies on `request.shop`/`WebhookMetadata#shop` for tenant-scoped actions, which is exactly the documented use of this API.

### Recommendation
Include the shop domain (and other tenant-identifying headers such as topic/api-version if used for routing decisions) inside the HMAC-signed material, or independently verify `request.shop` against a value obtained through an authenticated channel (e.g., cross-check against the webhook_id via the Admin API, or bind the shop to the endpoint URL/path per tenant rather than trusting the header). At minimum, document prominently that `request.shop` is unauthenticated and must not be used for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `{"id":1}"` with header `x-shopify-hmac-sha256: <valid HMAC over body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body and HMAC to the app's webhook endpoint but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only checks the HMAC over `@raw_body`, so validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` even though the request body/HMAC were never associated with `victim.myshopify.com`: [6](#0-5) 
5. Any app logic keyed off `data.shop` (e.g., "update order record for this shop") now operates on the wrong tenant's data using attacker-supplied content.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
