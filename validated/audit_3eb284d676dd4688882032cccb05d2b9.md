This confirms the root cause: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` only checks the HMAC against `to_signable_string` (the body) [3](#0-2) , and `Registry.process` dispatches the handler using `request.shop` taken straight from the header without any binding to the HMAC-verified content [4](#0-3) . The HMAC secret used is the single, app-wide `Context.api_secret_key` (or `old_api_secret_key`), not a per-shop secret [5](#0-4) .

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body against the app's shared `api_secret_key`. The `shopify-shop-domain` (and `topic`/`webhook-id`) headers, which the host application uses to decide *which tenant* the webhook payload belongs to, are never included in the signed content, so they carry no cryptographic binding to the verified body.

### Finding Description
`Request#hmac`/`#to_signable_string` build the digest exclusively from `@raw_body`: [6](#0-5) . `Request#shop`, `#topic`, and `#webhook_id` read directly from HTTP headers with no cryptographic tie to the body or its signature [2](#0-1) .

`Utils::HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` (the body only) and compares it with the received `hmac` value [3](#0-2) . It never factors in `shop`, `topic`, or `webhook_id`.

`Registry.process` treats a passing `HmacValidator.validate(request)` as proof the *entire request* (including the tenant-identifying `shop` header) is authentic, then constructs `WebhookMetadata` using `request.shop` straight from the header and dispatches it to the registered handler: [4](#0-3) .

Because the signing secret (`Context.api_secret_key`) is the app's single client secret shared across every installed shop — not a per-shop secret — an attacker who legitimately controls one shop that has the app installed can:
1. Trigger a webhook event on their own shop and capture the genuine `(raw_body, hmac)` pair delivered to the app's webhook endpoint.
2. Replay that exact body and HMAC to the same endpoint, but with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain.
3. `HmacValidator.validate` still succeeds, because it only checks the body against the shared secret — it has no knowledge of, and does not bind to, the `shop` header.
4. The host application's webhook handler receives `WebhookMetadata` claiming the payload originated from the victim shop and processes/persists it under that tenant's identity.

This is the "field acted on but not covered by the HMAC" identity-binding failure: the equality the library implicitly assumes — `shop header == shop that produced this signed body` — is never enforced; only `hmac == HMAC(secret, body)` is checked.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a party with access to only their own shop's legitimate webhook traffic can inject attacker-controlled, HMAC-"valid" payloads attributed to a different, unrelated shop, because the shop identity is never part of the signed material. Any host application that trusts `WebhookMetadata#shop` (as documented/intended usage of this gem — see `Registry.process` building `WebhookMetadata.new(... shop: request.shop ...)`) to key persistence or business logic can have another tenant's data corrupted or spoofed. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to have their own account/shop with the app installed (a normal unprivileged merchant, not a privileged Shopify/app-owner credential), and to control the webhook endpoint delivery path only in the sense of replaying a previously-received, legitimate webhook call with a modified header — no `api_secret_key`, access token, or TLS interception is needed. The victim shop domain is typically guessable/public (`*.myshopify.com`).

### Recommendation
Bind the tenant identity into the verified material, e.g., include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload used for verification (or otherwise cryptographically bind headers to the body before trusting `request.shop`), or validate that the `shop` header corresponds to a shop session/installation state that is otherwise authenticated (e.g., cross-checked against Shopify's originating IP ranges and a per-shop-bound secret) rather than trusting the header verbatim once only the body's HMAC checks out.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) to receive a legitimately-signed `(raw_body, X-Shopify-Hmac-Sha256)` pair from Shopify.
2. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses successfully (all required headers present) [7](#0-6) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because the body/HMAC pair is genuinely valid for the shared `api_secret_key` [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
