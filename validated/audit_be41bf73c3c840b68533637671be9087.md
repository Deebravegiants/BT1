### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by HMAC-checking the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the gem hands to the app's handler as trusted, authenticated identity fields come from HTTP headers that are never part of the HMAC-signed message. An unprivileged attacker who obtains one legitimately-signed `(raw_body, hmac)` pair (e.g., by installing the app on their own store and triggering any webhook) can replay that exact body/hmac while substituting arbitrary `shop-domain` and `topic` headers, and the library will report it as a validated webhook for a shop and topic the attacker does not own.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the signature only over `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are completely outside that signed string: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields when constructing the metadata passed to the app's handler: [4](#0-3) 

The equality the library implicitly claims to guarantee is:
`hmac_verified(raw_body) == authenticated(shop, topic)`

but the actual binding is only:
`hmac_verified(raw_body) == raw_body`

`shop` and `topic` are attacker-controllable headers with no cryptographic tie to the signed body. The gem's own documentation reinforces the false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 

and that the handler's `data.shop` / `data.topic` are simply "The shop domain of the webhook" / "The topic of the webhook", implying they are authenticated along with the body: [6](#0-5) 

### Impact Explanation
An attacker who can install the target app on any shop they control (e.g., a free/dev store, if the app is public) receives real, validly HMAC-signed webhook deliveries for that shop, signed with the app's shared `api_secret_key`. Because the signature only covers the body, the attacker can capture one `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with the `shop-domain` header changed to any victim shop and the `topic` header changed to any topic string (e.g., a sensitive/mandatory topic such as `shop/redact` or `customers/data_request`). `Registry.process` will accept it as authentic and invoke the registered handler with `WebhookMetadata` attributing the (attacker-chosen) body to the victim shop and the (attacker-chosen) topic. If the host app's handler acts on `data.shop`/`data.topic` (e.g., purging stored data for `shop/redact`, deactivating a session, or triggering shop-scoped business logic) without further correlating body content to the claimed shop/topic — which the library's documented contract explicitly encourages, since it advertises the request as pre-verified — this results in cross-tenant impersonation and unauthorized actions against a shop the attacker doesn't control.

### Likelihood Explanation
Exploitation only requires the ability to install the app on any shop (common for public apps with free trials/dev stores) and access to the app's public webhook endpoint, both available to any unprivileged internet user. No access token, secret, or privileged access is required — the attacker reuses a signature that Shopify itself generated for their own shop.

### Recommendation
Bind the shop and topic identity to the HMAC-protected message, e.g., include `shop-domain`, `topic`, and `webhook_id` header values (or their SHA256 digests) as part of `to_signable_string`, or independently re-validate that the shop/topic in the headers match values embedded in the (verified) body/session context before invoking the handler. At minimum, document clearly that `shop`/`topic`/`webhook_id` headers are NOT authenticated by `HmacValidator`, so host apps cannot mistakenly treat them as trusted.

### Proof of Concept
1. Attacker installs the target (public) app on their own shop `attacker.myshopify.com`.
2. Attacker triggers any registered webhook topic (e.g., `carts/update`) on their own shop, capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's endpoint. This HMAC is valid because `HmacValidator.validate_signature` only checks `OpenSSL::HMAC.hexdigest(secret, raw_body)` against the header — see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
3. Attacker POSTs the same `raw_body` and the same `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint again, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or any other registered topic)
4. `ShopifyAPI::Webhooks::Request.new` parses these headers (`lib/shopify_api/webhooks/request.rb` lines 15-33); `Registry.process` calls `HmacValidator.validate(request)`, which passes because only `raw_body` is checked (`lib/shopify_api/webhooks/registry.rb` line 190).
5. The handler registered for that topic is invoked with `WebhookMetadata.new(topic: "shop/redact", shop: "victim.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host app to perform shop-scoped logic against `victim.myshopify.com` that it believes was authenticated by Shopify.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
