### Title
Incorrect TON Connect domain length encoding causes wrong intent hash to be computed for non‑ASCII domains - (File: `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`)

### Summary
`computeTonConnectHash` encodes the `domain_len` field using the JavaScript string's `.length` (UTF‑16 code‑unit count) instead of the byte length of the UTF‑8 encoded domain that is actually appended to the hashed message. This is the same class of bug as the referenced report: a boundary/length field is derived from character count instead of byte count of a variable‑length, potentially multi‑byte string, causing the serialized artifact to not match what was actually produced.

### Finding Description
`computeTonConnectHash` builds the SHA‑256 preimage for a TON Connect signed payload as a sequence of length‑prefixed fields: [1](#0-0) 

The `domain_len` field is computed as `numberToBigEndian(domain.length, 4)`, i.e. the number of UTF‑16 code units in the JS string, while the bytes actually inserted right after it are `new TextEncoder().encode(domain)` — the UTF‑8 byte encoding of the same string: [2](#0-1) 

For any `domain` value containing non‑ASCII characters (e.g. Cyrillic/CJK/IDN‑style domains, or any character above U+007F), `domain.length` (UTF‑16 units) is smaller than the number of UTF‑8 bytes actually appended. The declared length field therefore does not match the number of bytes that follow it in the hashed message — exactly analogous to the referenced Bio contract bug, where a byte offset was computed from character semantics instead of raw byte length, corrupting the resulting artifact.

Note that `payloadData.length` at line 74 is computed correctly (from the `Uint8Array` produced by `TextEncoder`), so only the `domain` field suffers from this inconsistency — this asymmetry within the same function underscores that the `domain.length` usage is a bug rather than an intentional deviation from spec.

### Impact Explanation
`computeTonConnectHash` (via `computeSignedTonConnectHash`) feeds `computeIntentHashHashBytes`/`computeIntentHash`, which is used across the SDK to derive the canonical intent hash locally without publishing: [3](#0-2) 

This locally-derived hash is relied upon elsewhere in the SDK (e.g. `intent-executer.ts`, withdrawal completion tracking) to correlate a signed payload with its on-chain/relayer-side representation. If the reference implementation (and any verifier that recomputes this hash to authorize/verify a signature, per the "TON Connect" spec referenced in the docstring) uses the byte-length of the domain — the standard convention for length-prefixed serialization — then any TON Connect payload with a non‑ASCII `domain` will produce a **different hash** in this SDK than the hash actually signed/verified on-chain. This breaks the equality between "hash the SDK computes and tracks" and "the actual on-chain/verified intent hash," which can leave a legitimately submitted and executed withdrawal permanently unmatched by the SDK's tracking/polling logic — i.e., a withdrawal that is stuck from the integrator's perspective until manual intervention, matching the High-impact category for "a status or hash misreport" / "a withdrawal stuck until manual intervention."

### Likelihood Explanation
This triggers deterministically whenever the `domain` field of a `ton_connect` `MultiPayload` contains any character outside the ASCII range (which is common for internationalized domains or dApp names). No malicious actor is required — this is a plain correctness bug that will surface for any legitimate non-ASCII domain, though the current test suite only exercises ASCII domains (`"near.com"`) so the bug is not caught: [4](#0-3) 

### Recommendation
Compute `domain_len` from the UTF‑8 byte length of the encoded domain, not the JS string length, mirroring how `payloadData.length` is already handled correctly:

```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```

### Proof of Concept
```ts
import { computeTonConnectHash } from "./ton-connect";

const base = {
  standard: "ton_connect",
  address: "0:64c41584e067fd81ddac35b9b5489eb35d69db03acb0a01be9014421057258fd",
  timestamp: 1778685374,
  payload: { type: "text", text: "hello world" },
  public_key: "ed25519:99q8mY2bNRik43niUSKrXWsHGgmp9S6iG6VKmyta2Znj",
  signature: "ed25519:not-checked-by-hash-fn",
} as const;

// "über.com" -> JS .length = 8, UTF-8 byte length = 9 (ü is 2 bytes)
const payload = { ...base, domain: "über.com" };

// domain_len field encodes 8, but 9 bytes of UTF-8 domain are appended,
// so the length-prefixed message does not correctly delimit the domain
// field from the following `timestamp` bytes, producing a hash that
// diverges from any spec-conformant implementation that uses byte length.
console.log(computeTonConnectHash(payload));
```
