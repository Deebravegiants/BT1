This is the confirmed root cause candidate: `findMatchingWithdrawal` matches withdrawals by `assetId` alone, not by index, in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (`describeWithdrawal`, lines 313-343) and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (lines 144-153). The docstring itself acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" [1](#0-0) . However, `sdk.createWithdrawalCompletionPromises` and `createWithdrawalIdentifiers` allow batches of `WithdrawalParams[]` and explicitly assign separate `index` values per bridge route without any restriction preventing two withdrawals of the same `assetId` in one batch [2](#0-1) .

### Title
Cross-withdrawal status/hash misreport when batching same-asset PoA withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` and the shared `findMatchingWithdrawal` helper identify which on-chain withdrawal record corresponds to a given `WithdrawalIdentifier` by looking up **only the `assetId`** in the array of withdrawals returned by the PoA indexer, ignoring the withdrawal's `index`. When a caller submits an intent batch containing two or more withdrawals of the *same* token to *different* destination addresses/amounts, both `WithdrawalIdentifier`s resolve to the *same* matched record, so the `txHash`/`status` reported for withdrawal #2 is actually the outcome of withdrawal #1 (or vice versa).

### Finding Description
`describeWithdrawal` fetches all withdrawals for a NEAR tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find(w => nep141:${w.data.near_token_id} === criteria.assetId)` [3](#0-2) . This `.find()` always returns the *first* array element whose token matches, regardless of which of possibly several same-asset withdrawals in that transaction it actually corresponds to. The equality that should hold — "the withdrawal identifier (tx hash + index + assetId) maps 1:1 to the on-chain outcome record" — is broken because `index` is discarded entirely in the lookup, and the API response order is explicitly called out as "unsorted" in the surrounding comment: "Response list is unsorted, so we match by assetId instead of index" [4](#0-3) .

The batch entry point `sdk.createWithdrawalCompletionPromises` creates one polling promise per withdrawal param via `createWithdrawalIdentifiers`, which assigns sequential `index` values per bridge route but places no constraint preventing two same-`assetId` withdrawals from being routed to the same `PoaBridge` instance in a single call [5](#0-4) [2](#0-1) . Each of those promises independently calls `watchWithdrawal` → `bridge.describeWithdrawal`, and because the matcher can't disambiguate, both polling loops converge on the same withdrawal record — meaning one destination's real completion (with the correct `transfer_tx_hash`) gets reported as the completion for the *other* destination's withdrawal as well.

`waitForWithdrawalCompletion` in `internal-utils` has the identical flaw and is used independently to await a single withdrawal's destination hash, so the same corruption applies to any integrator using it directly for batched same-token withdrawals.

### Impact Explanation
This breaks the "status/hash reported must equal the actual on-chain outcome for that specific withdrawal" equality named in the rules. An integrator that credits or marks a withdrawal complete based on the SDK's `describeWithdrawal`/`watchWithdrawal` result could:
- Report withdrawal B as "completed" with withdrawal A's `transfer_tx_hash`, even though B's actual funds went to a different destination address, causing wrong bookkeeping/double-crediting logic on the integrator side.
- Prematurely resolve two watcher promises with the same hash when only one destination actually received funds, since `.find()` returns the same element for both indices.

This matches the High-impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious actor — it triggers whenever a normal (unprivileged) caller batches ≥2 withdrawals of the same `assetId` to the PoA bridge in one `signAndSendWithdrawalArgs`/`processWithdrawal` call, which is an explicitly supported feature (`WithdrawalParams[]`, `isBatchMode`). The bug is acknowledged in the code comments as a known limitation but is not enforced/guarded against anywhere in `sdk.ts` or `withdrawal-watcher.ts` — no assertion rejects duplicate-asset PoA batches, so the misreport happens silently under ordinary use.

### Recommendation
Either (a) reject/validate batches containing more than one PoA-bridge withdrawal with the same `assetId` at `createWithdrawalIdentifiers`/`sdk.ts` time, forcing callers to split them into separate submissions, or (b) extend the POA API/response and `findMatchingWithdrawal` matching key to disambiguate by amount+destination (as the code comment itself suggests: sort both API results and params by amount) or by a per-withdrawal correlation id, so `index` is honored rather than discarded.

### Proof of Concept
1. Call `sdk.signAndSendWithdrawalArgs` (or directly `createWithdrawalIntents`) with `withdrawalParams: [{assetId: "nep141:usdc.omft.near", amount: 100n, destinationAddress: "addrA", feeInclusive:false}, {assetId: "nep141:usdc.omft.near", amount: 200n, destinationAddress: "addrB", feeInclusive:false}]` routed to `PoaBridge`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` for the two entries, both under `RouteEnum.PoaBridge` [6](#0-5) .
3. After the NEAR tx lands, PoA indexer returns two `withdrawals` entries, both with `near_token_id: "usdc.omft.near"`, in indexer/return order (unsorted) — e.g. `[{...addrB, transfer_tx_hash:"0xB"}, {...addrA, transfer_tx_hash:"0xA"}]`.
4. `watchWithdrawal` for index 0 (intended for addrA) calls `describeWithdrawal` → `findMatchingWithdrawal` returns the first match, `0xB`'s record, and reports `{status:"completed", txHash:"0xB"}` for what was actually the addrA withdrawal.
5. The second poll for index 1 (intended for addrB) also matches the same first record and also reports `txHash:"0xB"`, i.e., both polling promises resolve to the identical hash despite being different destinations/amounts, corrupting any integrator crediting logic keyed on completion hash per withdrawal index. This mirrors the report's core bug class of "a status reported that is not the on-chain outcome" for the specific unit of work being tracked.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
