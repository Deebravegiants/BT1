This confirms the vulnerability. Confirmed exact code paths: `Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `Webhooks::Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) — that header is never included in the HMAC-signed string. `Registry.process` validates HMAC via `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`) then immediately trusts `request.shop` to build `WebhookMetadata` passed to the host app's handler (`lib/shopify_api/webhooks/registry.rb:198-199`), without any cross-check binding the shop header to the signed body.

### Title
Webhook `shop` identity is not bound to the HMAC-verified payload, enabling cross-tenant data misattribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, but the `shop` field used downstream to attribute the webhook to a tenant is read from an unauthenticated HTTP header that plays no part in the signature. This breaks the intended binding `shop_verified == shop_used`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` is the single trust boundary for inbound webhooks: it calls `Utils::HmacValidator.validate(request)` and, if that passes, forwards `request.shop` (together with the parsed body) to the host application's registered handler as the shop identity for the event: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw request body — it does not include the shop domain, topic, webhook id, or api version: [3](#0-2) 

Meanwhile `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC computation: [4](#0-3) 

Because every shop that installs the same app shares the same `client_secret`/`api_secret_key`, a genuine, validly-HMAC-signed webhook body originating from the attacker's own (legitimately installed) shop can be replayed to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. `HmacValidator.validate` will still succeed, because it only checks the raw body bytes against the shared secret — it never checks that the signed bytes are bound to the shop asserted in the header. `Registry.process` then hands the handler a `WebhookMetadata` claiming the victim shop, while the body content is really the attacker's own shop's data: [5](#0-4) 

This is the same "field acted on but not covered by the HMAC" pattern as the referenced report, where a value used for authorization/accounting decisions is not part of what was actually verified.

### Impact Explanation
Host applications built on this gem key their per-shop data storage, access-token lookups, and business logic off `WebhookMetadata#shop`/`request.shop`, trusting it as an authenticated tenant identifier because it arrives alongside an HMAC that "passed." Since the header is unauthenticated, an unprivileged holder of any single shop installation can cause the host app to process/store attacker-controlled webhook payloads under an arbitrary victim shop's identity — a cross-tenant data integrity/confusion issue reachable purely through this gem's public `Registry.process` / `Webhooks::Request` API, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker legitimately installs the same target app on their own shop (a normal, unprivileged action), (2) they capture one real webhook delivery (body + valid HMAC) from Shopify to their own shop, and (3) they replay that exact body/HMAC pair to the app's public webhook endpoint with a different `shop-domain` header. No access token, no `api_secret_key` knowledge, and no privileged account on the victim shop are needed, matching the in-scope threat model.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is actually HMAC-verified, or otherwise cross-validate the header-derived `shop` against a value obtained through an authenticated channel (e.g., re-deriving/confirming the shop from a signed claim) before constructing `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not be the sole source of truth for authorization decisions when other unsigned headers (`shop`, `topic`, `webhook_id`) are trusted for those decisions.

### Proof of Concept
1. App is installed on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` with the same `api_secret_key`.
2. Attacker triggers a real event (e.g., `orders/create`) on their own shop, capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify computed over `B` with the shared `api_secret_key`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — matches `H`, validation passes.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)` and invokes the host app's handler, which now processes attacker-supplied data under the victim shop's identity.
