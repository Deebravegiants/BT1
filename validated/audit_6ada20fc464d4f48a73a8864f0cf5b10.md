Confirmed: `Registry.process` at [1](#0-0)  passes `request.shop` straight to the app's `WebhookHandler` as the tenant identifier, while `Utils::HmacValidator.validate` only checks the HMAC against `request.to_signable_string`, which returns solely the raw body.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC integrity check only signs the raw request body. Any party capable of producing a body+HMAC pair that validates for one shop can attach an arbitrary `shop-domain` header and have `Registry.process` dispatch it to the app's handler as if it originated from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body only) and compares it with `verifiable_query.hmac`: [4](#0-3) 

`Registry.process` accepts the request once this body-only HMAC check passes, and forwards `request.shop` unchanged to the registered handler as the authoritative tenant identity: [5](#0-4) 

The security property broken is the equality: `shop asserted by HmacValidator.validate(request) == true` should imply `shop header == the shop that produced this exact signed body`. Because `shop` is outside the signed content, that equality does not hold — the HMAC only proves "Shopify (or holder of `api_secret_key`) produced this body at some point," not "this body belongs to the shop named in this header."

Any merchant/tester with the app installed on their own store is an unprivileged, credential-less party with respect to *other* tenants of the app, yet they can legitimately trigger Shopify to send them a validly-signed webhook (e.g., updating a product fires `products/update`). Capturing that body+HMAC pair, they can replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (same body, same secret), and `Registry.process` will hand the handler `WebhookMetadata` claiming to be from the victim shop with the attacker-chosen body content, breaking the shop-identity binding and enabling cross-tenant data confusion/injection in the host application's per-shop data store.

### Impact Explanation
This breaks the identity binding between the cryptographically verified payload and the tenant the payload is attributed to, letting one tenant's legitimately-obtained signed webhook be replayed and misattributed to another tenant — a cross-tenant access impact under a Critical-severity bucket, and it requires no possession of `api_secret_key`, access tokens, or any other credential beyond having the app installed on any single shop (which is the normal, unprivileged onboarding flow for any merchant).

### Likelihood Explanation
Likelihood is moderate to high in any application built on this gem's documented webhook pattern: the gem's own registry design (`Registry.process` → `WebhookMetadata.new(shop: request.shop, ...)`) actively encourages host apps to treat `request.shop` as trustworthy once `HmacValidator.validate` passes, without documenting that the shop header is outside the signed envelope. No secret material is required — only the ability to receive one legitimate webhook for a shop where the app is installed (trivial for any test/developer/attacker store) and to POST an HTTP request with modified headers to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/api_version) inside the HMAC-covered signable content, or otherwise cryptographically bind them to the signed body (e.g., require the app to independently verify `request.shop` against session/install records keyed by a value derived from the signed payload, not from an unauthenticated header). At minimum, document prominently that `request.shop`, `request.topic`, and `request.api_version` are unauthenticated and must not be trusted as tenant-binding without additional verification.

### Proof of Concept
1. App installs the library and registers a webhook handler for topic `products/update` that uses `data.shop` to look up/update the corresponding shop record in the host app's database (the pattern documented in `docs/usage/webhooks.md` and exercised in `Registry.process`, `WebhookMetadata.new(shop: request.shop, ...)` at [6](#0-5) ).
2. Attacker installs the app on their own store (`attacker.myshopify.com`) and triggers a `products/update` event, capturing the legitimate `raw_body` and `x-shopify-hmac-sha256` header Shopify sent.
3. Attacker POSTs to the app's webhook endpoint with the *same* raw body and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body` ( [2](#0-1) ), which is unchanged and correctly signed.
5. `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and the attacker-originated body content, causing the host application to process attacker-controlled data under the victim shop's identity.
