### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates that body against the `x-shopify-hmac-sha256` header. The `shop` value used downstream to attribute the webhook to a tenant is read from the `x-shopify-shop-domain` header, which plays no part in the HMAC computation. This breaks the identity binding `hmac_signed_bytes == bytes_the_gem_acts_on_for_tenant_attribution`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the caller-supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But the `shop` accessor used for tenant attribution is taken from the `shop-domain` header, entirely outside the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC-over-body, then forwards `request.shop` (the unauthenticated header) straight to the app's handler as the trusted tenant identifier: [4](#0-3) 

Because the shop header is not part of the signed string, a valid `(raw_body, hmac)` pair for shop A remains a *valid* signature no matter what `x-shopify-shop-domain` value is attached to it. Any party who can obtain one legitimately-signed webhook body+HMAC pair (e.g., a merchant who owns shop A and can see/replay their own app's webhook deliveries, or anyone able to capture one over the wire before TLS termination at the app) can resend the exact same body and HMAC while substituting a different shop's domain in the header, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks cross-tenant isolation: the host application, trusting the gem's "verified" `WebhookMetadata.shop`, will process/attribute the replayed event (order data, `app/uninstalled`, `shop/redact`, etc.) as belonging to a shop the attacker does not control. Depending on how the host app uses `data.shop` (e.g., to look up/revoke a stored access token, to write records keyed by shop, or to trigger data-deletion flows), this can result in cross-tenant data corruption, spoofed uninstall/redact events for a victim shop, or confusion of per-shop state — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires possession of at least one validly-signed `(body, hmac)` pair, which an attacker cannot forge without the `api_secret_key`. However, unlike stealing the secret itself, this does not require credential theft — an attacker only needs to capture/replay a legitimate webhook delivery they have visibility into (e.g., their own shop's webhook payloads, which every merchant using the app naturally receives), and repurpose it with a forged `shop-domain` header. This is a lower bar than compromising the API secret, but it does require an intermediary or a malicious/curious merchant capable of intercepting or replaying HTTP traffic to the app's webhook endpoint — hence "low probability, meaningful impact," consistent with the analog bug class in the reference report (a mutable/critical field not bound by the protecting mechanism).

### Recommendation
Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-verified signable material, or independently verify that the `shop-domain` header matches a shop for which the specific `webhook_id`/subscription was registered before dispatching to the handler. At minimum, document to consumers that `data.shop` is not itself authenticated by the HMAC and must not be trusted for authorization decisions without additional verification (e.g., cross-checking against the app's known/installed shop list).

### Proof of Concept
1. App has webhooks registered for shop A (`shop-a.myshopify.com`) and shop B (`shop-b.myshopify.com`), both installed by different merchants.
2. Shopify delivers a legitimate webhook to the app for shop A with body `BODY` and header `x-shopify-hmac-sha256: HMAC(secret, BODY)`.
3. The merchant who owns shop A (or anyone able to observe/replay this HTTP request, e.g. via their own webhook debugging tools) resends the identical request to the app's webhook endpoint, changing only the header:
   `x-shopify-shop-domain: shop-b.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `BODY`, unchanged) and successfully validates, because the shop header was never part of the signed string: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the body originally intended for shop A, and the host app processes/attributes the event as belonging to shop B.
