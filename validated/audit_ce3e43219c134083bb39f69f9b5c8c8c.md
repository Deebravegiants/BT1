### Title
Orb-Relay-Client does not verify message source before replaying signup state (`RequestState` handling) - (File: `orb-relay-client/src/client.rs`)

### Summary
`PollerAgent::main_loop` in `orb-relay-client` receives relayed messages and, before acting on them, is supposed to verify that the message's `src.id` matches the expected paired peer (`self.config.dst_id`) — this is the same "verify sender before acting" pattern described in the external report for the Amarok `Receiver`. However, for one specific inbound message type, `self_serve::app::v1::RequestState`, this verification is skipped entirely, so the client replays its `last_message` to whoever sent the `RequestState` payload regardless of source.

### Finding Description
The receive loop explicitly checks the source identity for every payload *except* `RequestState`: [1](#0-0) 

```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx
        .send(self.last_message.clone())
        .await
        .wrap_err("Failed to send outgoing message")?;
} else if src.id != self.config.dst_id {
    tracing::error!(
        "Skipping received message from unexpected source: {:?}: {payload:?}",
        src.id
    );
} else {
    self.handle_message(...).await?;
}
```

The comment directly above `main_loop` acknowledges the underlying risk explicitly: the relay connection may deliver "messages from different sources," and the client needs to "split auth and subscription" to "avoid multiplexing messages from different sources" [2](#0-1) . Despite this known risk, the `src.id` equality check — the client's only defense against acting on messages from an unverified originator — is bypassed specifically for `RequestState`, so the agent will unconditionally resend `self.last_message` (the last state payload it sent, e.g. `AnnounceOrbId` or `SignupEnded{success: ...}`) to any entity able to inject a `RequestState` payload on the shared response stream, without confirming that entity is the legitimate paired peer (`self.config.dst_id`).

This is structurally identical to the reported bug class: a receiver trusts an inbound cross-channel message and acts on it (replays privileged state) without verifying that the message actually originated from the authorized counterpart, exactly as `Receiver.xReceive` in the report acts on `_callData` without verifying `_sender`.

### Impact Explanation
`last_message` can carry signup-lifecycle state such as `SignupEnded { success, failure_feedback }` or `AnnounceOrbId`. If any entity able to reach this multiplexed stream (a scenario the code's own TODO says is possible) sends a `RequestState` message, it will receive a replay of state data intended for a specific orb/app session pairing without being validated as that pairing's counterpart. This creates a cross-signup state bleed / information disclosure of signup outcome data to an unauthorized entity, and — depending on how downstream consumers react to a replayed `SignupEnded` — creates the potential for misattributed signup-state confusion between sessions.

### Likelihood Explanation
Exploitation depends on an attacker being able to inject a `RequestState` payload into the shared relay stream that this client instance is listening on (the multiplexing scenario the code comment itself calls out as a known concern). This is a Medium-likelihood issue: it requires a specific pre-condition (message multiplexing / an unauthorized peer landing on the same stream) rather than being trivially triggerable by any unauthenticated party, but the code contains no defense-in-depth check for this one message type even though such a check exists for every other message type.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special-case, so that `RequestState` messages are also validated against the expected paired peer before `last_message` is replayed. Do not special-case any inbound message type as exempt from source verification.

### Proof of Concept
1. Establish a relay client pairing with `session_id`/`orb_id` (as in `orb-relay-client/src/bin/manual-test.rs`) and let the orb send a `SignupEnded { success: true, .. }` state message, which becomes `last_message` on the orb-side `PollerAgent`.
2. From an entity that can deliver a `RequestState` payload on the same underlying response stream (the multiplexing scenario called out in the code's own comment) but that is not the legitimate `dst_id` peer, send `self_serve::app::v1::RequestState {}`.
3. Observe that `main_loop` skips the `src.id != self.config.dst_id` check for this payload type and replays `last_message` (the `SignupEnded`/`AnnounceOrbId` state) directly to the sender, regardless of identity verification. [3](#0-2)
