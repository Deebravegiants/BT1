The external report's root cause—an unprivileged caller supplying an identifier that becomes a unique on-chain key without proof of ownership/relation, letting them permanently squat that key before the legitimate party—has a direct analog in `lockup-factory/src/lib.rs`.

### Title
Front-running/account-squatting of deterministic lockup accounts via unvalidated `owner_account_id` in `LockupFactory::create` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the to-be-created lockup contract's account ID deterministically from the caller-supplied `owner_account_id` parameter, with no check that the caller (predecessor) is actually that owner or otherwise authorized to create a lockup on their behalf, and no check that the lockup parameters were approved by anyone associated with `owner_account_id`.

### Finding Description
In `create`, the lockup account name is computed purely from `owner_account_id`: [1](#0-0) 
and immediately used to `create_account()` at that deterministic address with attacker-chosen `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, and `release_duration`: [2](#0-1) [3](#0-2) 

There is no assertion that `env::predecessor_account_id()` matches `owner_account_id`, nor any signature/authorization check tying the request to the intended owner. Because a NEAR account name can only be created once, any unprivileged user can pay the minimum deposit and call `create` with a victim's account ID as `owner_account_id`, thereby permanently claiming the deterministic lockup account name `sha256(owner_account_id).<factory>` with parameters of the attacker's own choosing (e.g., `lockup_duration = 0`, no vesting schedule, or a bogus `vesting_schedule`). This is structurally the same class of bug as the external report: a public, unvalidated, user-supplied value (transaction hash there, `owner_account_id` here) is used as a unique key that the legitimate party (Alice / the real funder) will later also need to use, and the attacker's premature/incorrect claim on that key blocks the legitimate operation.

### Impact Explanation
When the legitimate funder (e.g., an employer/foundation) later calls `create` with the correct `owner_account_id`, `create_account()` on the already-existing account fails, the promise fails, and `on_lockup_create` refunds the attached deposit: [4](#0-3) 
The refund prevents direct fund loss to the legitimate funder, but the deterministic address for that specific `owner_account_id` is permanently squatted with attacker-chosen (potentially adversarial/incorrect) lockup or vesting terms, and the correct lockup contract for that employee/owner can never be deployed via the factory at that address. This is a High-severity account-binding/front-running failure in the lockup creation flow that breaks the intended single-execution/rightful-creation guarantee for a given owner.

### Likelihood Explanation
Any unprivileged account can call `create` and only needs to know the intended victim's `owner_account_id` (typically public, e.g., an employee's known NEAR account) and attach the minimum deposit, making this readily executable by any observer who anticipates a lockup being created for a given account (e.g., during onboarding of a new employee whose account name is public knowledge in advance).

### Recommendation
Require that `env::predecessor_account_id() == owner_account_id.as_ref()` (or require an explicit authorization/allow-list from a trusted party such as the foundation) before allowing `create` to proceed, so that only the owner themselves (or an authorized party acting on their explicit request) can cause the deterministic lockup account for that `owner_account_id` to be created.

### Proof of Concept
1. Employer publicly announces intent to create a lockup for `alice.near` (owner_account_id = "alice.near").
2. Attacker Eve calls `create({"owner_account_id": "alice.near", "lockup_duration": "0", ...})` from her own account, attaching `MIN_ATTACHED_BALANCE`.
3. `lockup_account_id = hex(sha256("alice.near"))[..20] + "." + factory_account` gets created with Eve's chosen (unfavorable) parameters.
4. Employer later calls `create` with the same `owner_account_id = "alice.near"` and correct parameters; `create_account()` fails because the account already exists, the promise fails, and the employer's deposit is refunded via `on_lockup_create` — the intended, correctly-configured lockup for Alice can never be created at that address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
