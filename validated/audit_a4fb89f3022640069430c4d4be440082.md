Confirms `VerifiableQuery` is a generic interface requiring only `hmac` and `to_signable_string`; for `Webhooks::Request` the latter returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), so `shop`, `topic`, `api_version`, and `webhook_id` headers are never part of the HMAC-signed material.

### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature, enabling cross-tenant data injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then trusts the `shop-domain` header — which is never part of the signed material — to decide which tenant the webhook payload belongs to. An attacker who can obtain one legitimately-signed webhook body (e.g., by installing the host app on their own store) can replay that exact body/signature pair while substituting a victim shop's domain in the `shopify-shop-domain` header, causing the host application to process attacker-controlled data as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns **only** the raw HTTP body: [1](#0-0) 

Yet the class exposes `shop`, `topic`, `api_version`, and `webhook_id`, all parsed directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` verifies only this HMAC-over-body and then immediately forwards the unauthenticated `shop` header to the application's handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and constant-time-compares it to the supplied `hmac`: [4](#0-3) 

The identity binding the gem implicitly relies on is:
`shop header used by the handler == shop that actually produced/owns the signed body`

Because `to_signable_string` never incorporates the `shop-domain` header, this equality is never enforced. An unprivileged actor who has legitimately installed the host application on their own store receives real Shopify webhooks — bodies with genuine, valid HMAC signatures computed with the app's shared `api_secret_key` — addressed to their own shop. Since verification checks only `raw_body`, that attacker can resend the identical `raw_body`/`hmac-sha256` pair to the same webhook endpoint (which is shared across all tenants of the SaaS app) while changing only the `shopify-shop-domain` header to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because the body and signature are unmodified and match; `Registry.process` then calls `handler.handle` with `WebhookMetadata.shop` set to the victim's domain while `body` contains attacker-controlled content from their own store's webhook.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: a merchant/attacker with no privileges over another tenant can get their own arbitrary webhook payload attributed to a victim shop. Any host application that uses `WebhookMetadata#shop` to select which merchant's records, cache, or database row to update with `WebhookMetadata#body` is exposed to cross-tenant data injection/corruption — e.g., writing attacker-controlled order/product/customer data into the victim shop's stored records, or triggering business logic (fulfillment, notifications, billing hooks) against the wrong tenant. This matches the Critical category of cross-tenant access, achieved without ever obtaining the victim's access token, refresh token, or the app's `client_secret`.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be able to install the target app on any shop they control — a normal, unprivileged action supported by the app's own onboarding flow, and (2) the ability to send an arbitrary HTTP request (with attacker-chosen headers) to the app's public webhook endpoint, which by design must be internet-reachable to receive Shopify webhooks. No secret material, TLS interception, or social engineering is needed, making this practically reachable for any host application that relies on the gem's `Webhooks::Registry`/`Request` machinery to authenticate and route webhooks by shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified material, or otherwise cross-check it out of band before trusting it for tenant routing:
- Extend `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) to incorporate the `shop-domain` header into the value that is HMAC-validated, so a mismatch between header and body invalidates the request; or
- Require callers of `Registry.process` to supply the expected shop (resolved independently, e.g. from an authenticated route/subdomain) and assert it equals `request.shop` before invoking the handler, rejecting on mismatch.

### Proof of Concept
1. Attacker installs the host application (built on this gem) on their own store `attacker-shop.myshopify.com`; the app registers webhooks via `ShopifyAPI::Webhooks::Registry.register_all`.
2. Shopify sends a legitimate webhook to the shared endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then re-issues it directly to the same public webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header set; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only (`request.rb:35-38`, `hmac_validator.rb:26-31`) and it matches `H`, so validation succeeds.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...))` (`registry.rb:188-200`), and the host application processes attacker-supplied data `B` as belonging to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
