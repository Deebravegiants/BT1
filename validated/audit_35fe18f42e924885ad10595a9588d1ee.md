### Title
Front-runnable AMM pool creation via arbitrary, attacker-controlled `market` seed permanently squats the pool PDA, blocking honest liquidity providers from creating the correct pool - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every account of a new pool (the `AmmInfo`, `TargetOrders`, `lp_mint`, `coin_vault`, `pc_vault`) from a PDA whose only variable seed is the caller-supplied `market_info` account key, which the code explicitly documents as "Just a seed for AMM account. Can be any account." Because this seed does not have to correspond to a real, validated market and the resulting addresses are fully deterministic and publicly computable, an attacker can observe a pending `Initialize2` transaction (or simply predict the conventional market pubkey a project intends to use) and front-run it with their own `Initialize2` call using the same `market_info` key but attacker-chosen mints/ratios and minimal capital.

### Finding Description
The AMM pool address space is keyed uniquely by the `market_info` pubkey via `get_associated_address_and_bump_seed`: [1](#0-0) 
and this same account is used verbatim (only as a bump/derivation seed, never validated against an actual serum/openbook market) to derive the `AmmInfo`, `TargetOrders`, lp mint, and both vault accounts in `process_initialize2`: [2](#0-1) 
The instruction docs and inline comments confirm this account is unconstrained ("Can be any account"): [3](#0-2) 
Once any of these PDAs is created and assigned to the program, every subsequent `generate_amm_associated_*` call for the same `market_info` seed fails with `RepeatCreateAmm`/`AlreadyInUse`, since the helper checks that the target account is still system-owned before initializing it: [4](#0-3) [5](#0-4) 
This mirrors the reported bug class exactly: correctness of the on-chain state depends on a first-come-first-served unique identifier (there, dispute-game UUID; here, the AMM PDA keyed by `market_info`), and an attacker able to submit a transaction ahead of the honest party for that identifier can permanently claim it with invalid/malicious data, so the honest party's legitimate transaction referencing the same identifier can never succeed afterward.

### Impact Explanation
A project (or any user) intending to launch the canonical pool for a given market can be front-run: the attacker submits `Initialize2` for the same `market_info` key first, using tokens/ratios of their choosing and the minimum viable liquidity (`InitLpAmountTooLess` only requires liquidity above `10^lp_decimals`), permanently occupying the `AmmInfo`/vault/lp-mint PDAs tied to that market. The honest party can never create their intended pool at that address again (`AlreadyInUse`), and any user or integrator who trusts the deterministic address-derivation convention and deposits into or swaps against the squatted pool is exposed to an attacker-controlled initial price and can have funds extracted via the attacker's own subsequent swaps. This is a permanent denial of the correct pool state and a fund-loss vector for anyone who interacts with the squatted pool believing it is the legitimate one.

### Likelihood Explanation
Solana transactions are visible before confirmation, and the `market_info` account a project intends to use is typically public/predictable ahead of time (it's the OpenBook/Serum market for the token pair). The attack requires only a single `Initialize2` transaction with trivial capital (minimum liquidity threshold) and no privileged role, making it reachable by any unprivileged actor from a single transaction with attacker-chosen accounts/data, consistent with the reachable-path constraints of this scan.

### Recommendation
Do not rely solely on an arbitrary, unvalidated `market_info` account as the sole uniqueness seed for pool PDAs. Bind the derivation additionally to validated, immutable data (e.g., the actual coin/pc mint pair, or a real, on-chain-verified serum/openbook market whose base/quote mints are checked against `amm_coin_mint_info`/`amm_pc_mint_info`) so that squatting the seed account does not let an attacker preempt the canonical pool for a legitimate mint pair.

### Proof of Concept
1. Attacker monitors for (or predicts) the `market_info` pubkey a legitimate project plans to use in an upcoming `Initialize2` call.
2. Attacker submits their own `Initialize2` transaction first, passing the same `market_info` account, arbitrary `amm_coin_mint`/`amm_pc_mint` accounts they control, and the minimal `init_coin_amount`/`init_pc_amount` needed to pass `InitLpAmountTooLess` (`program/src/processor.rs:908-917`).
3. `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` succeed for the attacker since the PDAs are still system-owned, creating `AmmInfo`, `lp_mint`, `target_orders`, `coin_vault`, `pc_vault` all keyed to `market_info` (`program/src/processor.rs:747-814`).
4. When the honest party's original `Initialize2` transaction (using the same `market_info`) lands afterward, every associated-account helper hits the `else` branch and returns `AmmError::RepeatCreateAmm`, and even if somehow bypassed, the `amm.status != Uninitialized` check returns `AmmError::AlreadyInUse` (`program/src/processor.rs:843-847`), permanently preventing creation of the correct pool for that market.
