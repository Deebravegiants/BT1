### Title
Webhook `shop` identity field is not covered by the HMAC signature, allowing a valid webhook body to be replayed under a forged tenant identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Request#to_signable_string` used for that HMAC computation returns only `@raw_body`, while `Request#shop` is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [2](#0-1) . The `shop` value that identifies which merchant/tenant the webhook belongs to is passed straight into the handler's `WebhookMetadata` without ever being checked against the bytes that were HMAC-verified [3](#0-2) .

### Finding Description
The identity binding that should hold is:

`shop bound by HMAC == shop used by handler for tenant routing/session lookup`

In this gem's implementation, that equality is broken:
- `HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for `Webhooks::Request` returns only the raw body bytes [4](#0-3) [5](#0-4) .
- `Request#shop` is parsed from a header that is entirely attacker-controlled and never enters the HMAC computation [6](#0-5) [7](#0-6) .
- `Registry.process` verifies the HMAC once, then unconditionally forwards `request.shop` (the header value) into `WebhookMetadata` for the handler to act on [1](#0-0) .

Because Shopify signs the webhook HMAC only over the JSON body (this is the actual, documented Shopify webhook design — the same secret is shared by every store the app is installed on, and the body's HMAC is not scoped to a particular shop), any party who has previously received one valid webhook body/HMAC pair for topic X (e.g., by installing the app on their own test/free shop, or by observing a webhook delivery) can replay that exact body+HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `shop:` set to the attacker-chosen domain. Any host application that trusts `WebhookMetadata#shop` (as returned by this library) to select which merchant's session/access token to use, or to route the payload to a specific tenant's data, will process attacker-controlled data under an incorrect tenant identity — a cross-tenant confusion caused entirely by this gem's failure to bind the `shop` field into the value it HMAC-verifies.

This matches the report's underlying bug class (an action taken on a field, here `shop`, that is not covered by the same authentication check used to validate the request) even though the original ComplexRewarder report was about a DoS/exception-handling issue in a different domain — the structurally analogous flaw here is an identity-binding gap rather than a revert-based DoS.

### Impact Explanation
This is a **High** severity issue: it is a scope/binding check that fails permissively — the HMAC check passes while the tenant-identifying field it should be tied to can be forged, enabling cross-tenant webhook processing in any host application that relies on `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Request`/`Registry.process` without independently re-validating the shop domain against its own session store keyed off the same trusted binding.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately-signed webhook body/HMAC pair for the topic they want to forge (obtainable cheaply by installing the target app on a shop the attacker controls, since app secrets are shared across all installs) and the ability to POST to the app's public webhook endpoint with a modified `shopify-shop-domain` header. No access token, `client_secret`, or privileged credential is required — only a normal, unprivileged interaction with a public webhook endpoint that this gem exposes for verification.

### Recommendation
Bind the shop domain into the value that is cryptographically checked, or at minimum instruct/require host applications to cross-check `request.shop` against a value that is verifiably tied to the specific webhook subscription (e.g., the `webhook_id`, which is unique per subscription/shop, rather than the raw header). At the gem level, `Registry.process` should not pass an unauthenticated header value onward as if it were verified; documentation and/or an explicit secondary check tying `topic`+`webhook_id` to an expected shop would close the gap.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development shop `attacker-shop.myshopify.com`; trigger any webhook of interest (e.g. `orders/create`) and capture the raw JSON body and the `X-Shopify-Hmac-Sha256` header Shopify sends — these are valid because the app's single shared `api_secret_key` signs webhooks for every install.
2. Replay a POST to the victim app's webhook endpoint using the captured `raw_body` and `hmac` unchanged, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because `Request#to_signable_string` only hashes `raw_body` [4](#0-3) .
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` [3](#0-2) , even though the payload actually originated from the attacker's own shop — any host logic that uses this `shop` value to select the merchant session/access token will act as though `victim-shop` sent this data.

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
