### Title
`block.timestamp` used as swap deadline in fee-payment swaps allows MEV sandwich extraction of user funds - (File: `evm/src/core/EvmHost.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert user-supplied native token into `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`, passing `block.timestamp` as the swap `deadline`. [1](#0-0) [2](#0-1) [3](#0-2)  The same pattern exists in `IntentGatewayV2._placeOrder`'s fee-collection path. [4](#0-3)  Because `block.timestamp` always resolves to the timestamp of whichever block ultimately includes the transaction, this "deadline" imposes no real expiration and offers no protection against the transaction being delayed and executed at a manipulated price.

### Finding Description
`dispatch()`, the GET-variant `dispatch()`, and `fundRequest()` are all `external payable` entry points on `EvmHost`, reachable by any unprivileged caller who wants to submit a cross-chain POST/GET request or top up a pending request's relayer fee with native token. [1](#0-0) [3](#0-2)  When `msg.value > 0`, the host performs an on-chain swap of native token for the exact `feeToken()` amount needed, using the local Uniswap V2 router:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

`swapETHForExactTokens` bounds the input by `msg.value` (functioning as `amountInMax`) and requires the swap to complete "before" `deadline == block.timestamp`. Since this deadline is set to the timestamp of the very transaction performing the swap, it can never actually expire prior to inclusion — a validator/searcher can hold, reorder, or sandwich the transaction and it will still satisfy the deadline check no matter how the price has moved by the time it lands. This is the same root-cause pattern flagged in the referenced Beefy report for `UniV3Utils::swap`, `StrategyPassiveManagerUniswap::_chargeFees`, and `BeefyQIVault::_swapRewardsToNative`, all of which use `deadline: block.timestamp`.

### Impact Explanation
Any address dispatching a POST/GET request or funding a request with native token is forced through this swap. A searcher observing the pending transaction can front-run it by buying `feeToken()` (pushing its price up) and back-run by selling it after, extracting value from the dispatcher: the exact-output swap will consume more of the caller's supplied ETH (up to the full `msg.value`) to obtain the same `post.fee`/`get.fee` amount of `feeToken()`, with the excess captured by the attacker's sandwich rather than refunded to the caller. This is a repeatable, permissionless value-extraction path against every fee-paying dispatch/fund call and the `IntentGatewayV2` fee-collection path, i.e., concrete loss of user funds on the most commonly used entry points of the protocol (dispatching ISMP requests).

### Likelihood Explanation
High: `dispatch()` and `fundRequest()` are core, frequently invoked, permissionless entry points for anyone using Hyperbridge with native-token fee payment, and equivalent MEV infrastructure (public mempools, private order flow, validator-searcher relationships) is standard on the EVM chains Hyperbridge deploys to. No special privilege or race condition beyond ordinary MEV capability is required.

### Recommendation
Add a caller-supplied `deadline` parameter (or a bounded relative timeout, e.g., `block.timestamp + maxSwapWindow`) to `DispatchPost`/`DispatchGet`/`fundRequest`/`IntentGatewayV2` order-fee structs, and pass that value to `swapETHForExactTokens` instead of `block.timestamp`, so that a stale/delayed transaction genuinely reverts rather than always satisfying the deadline check. Combine this with an explicit `amountInMax` slippage parameter distinct from `msg.value` where feasible, so users can bound their acceptable price impact independently of the full amount sent.

### Proof of Concept
1. User calls `EvmHost.dispatch(post)` with `msg.value = X` ETH to pay `post.fee` in `feeToken()`.
2. A searcher observes the pending transaction in the mempool and front-runs it with a large buy of `feeToken()` on the same Uniswap V2 pair, raising its price.
3. The victim's `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes; since `deadline == block.timestamp` of the block it lands in, it is never actually stale and succeeds, but now consumes a larger portion of `X` (up to all of it) to acquire `post.fee` tokens, versus the pre-manipulation price.
4. The searcher back-runs by selling `feeToken()`, realizing profit equal to the price impact it created, extracted directly from the victim's `msg.value`.
5. Repeat for `fundRequest()`, GET `dispatch()`, and `IntentGatewayV2` order placement with native fee payment — all share the identical `block.timestamp` deadline pattern.
