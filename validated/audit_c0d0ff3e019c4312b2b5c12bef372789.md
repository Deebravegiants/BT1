### Title
Unvalidated `message.from` length causes panic on unsigned calldata execution - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` (the `IsmpModule::on_accept` implementation for the `hyper-fungible-token` pallet) validates the length of `message.to` (must be 20 or 32 bytes) before converting it into a Substrate `AccountId`, but it never validates the length of `message.from` before using it in the same way when calldata is attached without a signature. A crafted cross-chain `Message` with a short `from` field drives this code into a slice underflow / `copy_from_slice` length-mismatch panic.

### Finding Description
`on_accept` decodes the ABI-encoded `Message` from an incoming `PostRequest.body`: [1](#0-0) 

For `message.to`, the code explicitly checks the byte length is 20 or 32 and rejects anything else with `HftError::InvalidRecipientLength`. No equivalent check exists for `message.from`.

When `message.data` is non-empty and it decodes to `SubstrateCalldata` with no `signature`, the pallet falls back to deriving the dispatch origin directly from `message.from`: [2](#0-1) 

- If `source.is_evm()` is true, it computes `&from_bytes[from_bytes.len() - 20..]`. If `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize` (panics with an arithmetic overflow check in debug builds, or wraps to a huge value causing an out-of-bounds slice/index panic in release builds — either way, unreachable/undefined behavior triggering a runtime panic).
- If the source is not EVM, `account.copy_from_slice(from_bytes)` requires `from_bytes.len() == 32` exactly; `copy_from_slice` panics on any length mismatch.

`message.from` is fully attacker-controlled: it is part of the ABI-encoded `Message` body carried inside the ISMP `PostRequest`, which any relayer can submit (after proof verification) to the ISMP handler, which then dispatches to this pallet's `on_accept`. The bounds established for `message.to` were clearly intended to also apply to `message.from`, since both are addresses of the same shape, but the check was only applied to one of the two fields.

### Impact Explanation
A panic inside `on_accept`, invoked from `pallet_ismp`'s message-dispatch path (`handle_unsigned`/`execute`), aborts execution of that call. Depending on how panics propagate through the runtime's dispatch machinery, this can deny service for that specific message and, more importantly, blocks any relayer from ever successfully delivering that request (since resubmission with the same malformed body will always panic), leaving the corresponding cross-chain token transfer permanently undeliverable/stuck — a message the source chain believes was dispatched but that can never be completed on the destination pallet, which matches the "route unable to deliver messages" acceptance criterion. This mirrors the underlying bug class in CVE-2016-2317: insufficiently validated length fields from an untrusted, structured input triggering an out-of-bounds memory access/crash during parsing.

### Likelihood Explanation
Likelihood is high for triggering the crash: any account that can get a proof of a PostRequest accepted by the ISMP handler for this app (i.e., any relayer submitting a message from a configured source contract with `ContractToAsset` mapping already set up) can construct the `Message.data` field to embed `SubstrateCalldata` with no signature and craft `Message.from` to be a length other than 20/32 bytes while `Message.data` remains non-empty. Because ABI decoding of `bytes` fields permits arbitrary lengths, this is trivial to construct once the app/asset mapping exists.

### Recommendation
Validate `message.from`'s length the same way `message.to` is validated — reject any length other than 20 (EVM) or 32 (Substrate) bytes with a proper error (e.g., extend `HftError::InvalidRecipientLength`/add `InvalidSenderLength`) before it is used in the `H160::from_slice`/`copy_from_slice` calls, instead of relying on `Message.to`'s guard to cover both fields.

### Proof of Concept
1. Configure `ContractToAsset` for a source EVM chain/contract as in normal setup.
2. Craft an ISMP `PostRequest` with body = ABI-encoded `Message` where:
   - `to` = 20-byte valid address (passes existing check).
   - `from` = e.g. a 3-byte value (or any length not in {20, 32}).
   - `data` = ABI/SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any> }`, non-empty.
3. Get this PostRequest delivered with a valid consensus/state proof through the normal relaying path to `pallet_ismp`, which calls `Pallet::on_accept`.
4. Execution reaches `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() == 3`, causing `3usize - 20` to underflow, panicking the call (or panicking on the out-of-bounds slice if the underflow wraps), instead of returning a decode/validation error. [3](#0-2) [2](#0-1)
