### Title
Shared, reusable `CallDispatcher` allows theft of leftover ERC20 allowances via unrestricted arbitrary calls - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` executes attacker-supplied `Call[]` data to arbitrary target contracts with no restriction on the target address or function selector [1](#0-0) . Because the same `CallDispatcher` instance is a single, shared, long-lived contract address reused across every user's `predispatch`/`postdispatch`/calldata-execution flow in `IntentGatewayV2` and the `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` paths [2](#0-1) [3](#0-2) , any ERC20 allowance left outstanding on `CallDispatcher` from a previous order/message (e.g. an `approve` for an exact amount that isn't fully consumed by the swap it was intended for) remains callable by any later, unrelated attacker-controlled order. This mirrors the root cause of the Bancor incident: a contract that legitimately holds standing approvals performs an unverified/unscoped `transferFrom`-style call reachable by an unprivileged caller, letting that caller redirect funds approved by someone else.

### Finding Description
`CallDispatcher.dispatch` is documented and designed to "dispatch untrusted call(s)" [4](#0-3) . Its implementation only checks that the target has code before performing `to.call{value: call.value}(call.data)` — it does not restrict which function selectors may be invoked, nor does it verify that the calldata pertains only to tokens the current order/message legitimately owns [5](#0-4) .

`IntentGatewayV2.placeOrder` (and its Tron variant) routes the user's `predispatch.assets` to this shared dispatcher and then lets the user's own attacker-controlled `order.predispatch.call` execute inside it, e.g. `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` followed by `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [6](#0-5) . The same dispatcher address is also used for `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution on `onAccept` [7](#0-6) .

The official documentation acknowledges the resulting standing-allowance risk explicitly: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution" [8](#0-7) . This confirms the dispatcher's storage/allowance state is *shared and persistent* across otherwise-unrelated users' orders — any residual allowance a user's own predispatch/postdispatch calldata grants to `CallDispatcher` (deliberately, or due to an approve-then-partial-consume swap pattern, or a revert-safe approve pattern that doesn't reset to zero) remains spendable by a subsequent, completely unrelated attacker who crafts a malicious `order.predispatch.call` or `order.output.call` containing `token.transferFrom(victim, attacker, allowance)`. Because `CallDispatcher.dispatch` performs no scoping of `to`/`data` to the legitimate flow, this is directly reachable by any unprivileged user placing an order through `IntentGatewayV2.placeOrder` or triggering `fillOrder`'s postdispatch execution.

### Impact Explanation
An attacker who identifies any account with an outstanding ERC20 allowance to the `CallDispatcher` address can construct an order whose `predispatch.call` or `output.call` invokes `transferFrom(victim, attacker, amount)` on that token, executed in `CallDispatcher`'s own context (`msg.sender == CallDispatcher`), draining the victim's approved balance to the attacker. This is a concrete theft-of-funds vector reachable from a single submitted order, matching the Bancor incident's root cause of an unscoped/unverified transfer-pulling call exploiting standing approvals.

### Likelihood Explanation
Likelihood depends on users/integrators leaving non-zero allowances on the dispatcher (e.g. via approve-exact-amount patterns that under-consume due to fee-on-transfer tokens, partial fills, or reverted follow-up calls that don't reset allowance to zero). The docs' explicit warning against unlimited allowances indicates the maintainers are aware unconsumed/standing allowances on this shared contract are dangerous, which is itself evidence the condition is anticipated to occur in practice.

### Recommendation
Make `CallDispatcher` non-reusable/ephemeral per order (e.g., deploy a fresh minimal-proxy instance per `placeOrder`/`fillOrder`/`onAccept` invocation), or have it revoke/reset any allowances it granted immediately after each `dispatch` call, or restrict `dispatch` to disallow calls whose selector is `transferFrom`/`transfer`-like from arbitrary token contracts unless explicitly whitelisted for the current order's own tokens.

### Proof of Concept
1. Victim places a legitimate order whose `predispatch.call` approves `CallDispatcher` for `token.approve(CallDispatcher, X)` and swaps only part of `X` (e.g., due to slippage protection or a fee-on-transfer token), leaving a residual allowance `R > 0` on `CallDispatcher` for `token`.
2. Attacker calls `IntentGatewayV2.placeOrder` (or triggers a `fillOrder` postdispatch path) with `predispatch.call`/`output.call` = `[Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transferFrom.selector, victim, attacker, R)})]`.
3. `ICallDispatcher(dispatcher).dispatch(...)` executes `token.call(transferFrom(victim, attacker, R))` from `CallDispatcher`'s context, since `CallDispatcher.dispatch` performs no selector/target validation [5](#0-4) , succeeding because `msg.sender` (the dispatcher) still holds allowance `R` from the victim.
4. Victim's tokens are transferred to the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
