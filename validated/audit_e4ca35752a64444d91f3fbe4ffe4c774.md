### Title
Webhook `shop` field is trusted by the app but excluded from HMAC verification, enabling cross-tenant webhook shop-spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity using `Utils::HmacValidator.validate(request)`, but the HMAC signature it checks only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all read straight from unauthenticated HTTP headers — are never bound to that signature, yet `shop` is handed directly to the app's handler as the authoritative tenant identifier.

### Finding Description
`HmacValidator.validate` computes/compares the signature against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

while `shop` (and `topic`/`webhook_id`/`api_version`) are parsed straight from HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the body-bound HMAC, then immediately trusts `request.shop` as the tenant identity passed to the handler: [4](#0-3) 

The resulting `WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the field apps are expected to use to route/attribute the webhook to a specific merchant: [5](#0-4) [6](#0-5) 

**The broken identity binding, stated as an equality that fails:**
`HMAC-verified bytes (raw_body)` ≠ `shop value trusted by the handler (header "x-shopify-shop-domain")`.

Because the signature never covers the shop header, an attacker who can obtain any single valid `(raw_body, hmac)` pair — e.g., by installing the target app on their own store and legitimately receiving a real webhook from Shopify for their own shop — can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still passes because it only checks the (unchanged) body against the (unchanged) HMAC; `request.shop`, however, now returns the attacker-chosen victim domain, and this value is forwarded unmodified to the app's handler via `WebhookMetadata.new(... shop: request.shop ...)`.

### Impact Explanation
This crosses the "cross-tenant access" boundary called out as Critical impact: an unprivileged attacker (any merchant who can install the app and thus legitimately receive one signed webhook) can cause the gem to hand the host application a webhook body attributed to a shop domain of the attacker's choosing, without needing the app's `client_secret`, an access token, or any credential leak. Any host application that uses `data.shop` from `WebhookMetadata` (exactly as the gem's own documentation instructs) to look up per-tenant state, invalidate/refresh data, or dispatch tenant-scoped background jobs is exposed to processing forged data under another merchant's identity.

### Likelihood Explanation
Medium: exploitation requires the attacker to first obtain one legitimate `(body, hmac)` pair, which is trivial to do by installing the target app on their own (attacker-controlled) shop and triggering any subscribed webhook topic (e.g. `orders/create`), then replaying that captured request to the app's fixed webhook endpoint with a modified `shop-domain` header. No secret material, TLS interception, or privileged access is required — only the ability to be a normal app installer, which is available to any internet user for a public app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material that `HmacValidator` checks, or otherwise cross-verify that `request.shop` matches a shop already known to be legitimately associated with the webhook (e.g., compare against a shop recorded when the webhook subscription was registered, in addition to computing the HMAC over `shop + raw_body` rather than `raw_body` alone). Absent a change to Shopify's own signing scheme, host applications should be documented and expected to re-validate `data.shop` against session/tenant records before trusting it, but the gem should at minimum not present `shop` as a value implicitly covered by "Invalid webhook HMAC" validation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers `orders/create`. Shopify sends a real webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker sends a new HTTP request to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`raw_body` only) — this still matches, so validation succeeds.
5. `request.shop` now returns `"victim-shop.myshopify.com"`, and `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, which is passed to the app's registered handler as if Shopify itself sent this webhook for `victim-shop.myshopify.com`.
