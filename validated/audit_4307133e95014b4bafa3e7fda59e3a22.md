### Title
`calc_take_pnl` reverts with `CalcPnlError` when current pool value dips below the stored PnL snapshot, permanently blocking Deposit and Withdraw - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` requires `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` before it will proceed; if this comparison fails it unconditionally returns `AmmError::CalcPnlError`, aborting the whole instruction. `process_deposit` calls `calc_take_pnl` unconditionally, and `process_deposit` / `process_withdraw` (for any AMM status other than `WithdrawOnly`) both depend on it succeeding before any funds move. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`calc_pnl_x`/`calc_pnl_y` in `TargetOrders` are a snapshot of the pool's normalized reserves (`x`,`y`) at the time PnL was last taken; they are only updated inside the success branch of `calc_take_pnl` (and after `withdrawpnl`/`withdraw`/`deposit`) using `checked_sub`. On every subsequent `deposit`, `withdraw` (unless status is `WithdrawOnly`), and `withdrawpnl`, the current pool value (`pool_pc_amount * pool_coin_amount`) is compared against this snapshot (`calc_pc_amount * calc_coin_amount`) and if it is smaller for any reason, the function hard-fails with `CalcPnlError` instead of just skipping the PnL-taking step for that call. [5](#0-4) 

Because all decimal conversions in this path (`normalize_decimal_v2`, `restore_decimal`) are integer arithmetic that truncates/rounds, and because the target snapshot is updated using `checked_sub` against `x1`/`y1` minus the withdrawn/deposited amount and `delta_x`/`delta_y` (see the post-processing at the end of `process_deposit`/`process_withdraw`), rounding in this bookkeeping can leave `calc_pnl_x * calc_pnl_y` slightly larger than the actual current reserve product on a subsequent call. Any state where the true reserve product ends up smaller than the stored snapshot — whether from accumulated rounding in the snapshot update, or because reserves genuinely shrank in that exact epoch (e.g., a large withdrawal reduces `total_pc_without_take_pnl`/`total_coin_without_take_pnl` and thus `x1*y1` immediately below the previous snapshot before the snapshot itself is corrected) — causes every future `deposit`/`withdraw`/`withdrawpnl` call on that pool to revert with `CalcPnlError`, since the snapshot (`calc_pnl_x`,`calc_pnl_y`) is never updated to reflect the lower value (the update code only executes if the check passes). [6](#0-5) [7](#0-6) 

This mirrors the reported analog: an overly strict guard condition (`sharesOwed == 0` blocking `rebalance` in the external report vs. `pool_value < snapshot_value` blocking `calc_take_pnl` here) causes the legitimate operation to permanently revert instead of degrading gracefully (e.g., skipping the PnL step, as is already done conditionally for `WithdrawOnly` status in `process_withdraw`). [8](#0-7) 

### Impact Explanation
If the pool enters this reverting state, **all deposits and all non-`WithdrawOnly`-status withdrawals become permanently unavailable** — LPs cannot add liquidity and, more critically, cannot redeem their LP tokens for underlying coin/pc through the normal `process_withdraw` path, freezing user funds in the pool (the only bypass is if `amm.status == AmmStatus::WithdrawOnly`, which is a privileged/admin-controlled status change, not something a normal user can trigger). This is a permanent freezing-of-funds condition reachable purely by normal swap/deposit/withdraw usage over time, not by any privileged action.

### Likelihood Explanation
Reachable from unprivileged deposit/withdraw instructions; no special account permissions are required. Likelihood depends on precision-loss accumulation and reserve movement patterns in `calc_pnl_x`/`calc_pnl_y` tracking over the pool's life (rounding always occurs in `normalize_decimal_v2`/`restore_decimal`, and larger single-sided withdrawals or many small deposit/withdraw operations increase the chance the recorded snapshot ends up above the true instantaneous reserve product for at least one subsequent call). [9](#0-8) 

### Recommendation
Do not hard-fail the entire deposit/withdraw/withdrawpnl instruction when `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount`. Instead, treat this as "no PnL to take this round" (analogous to the `WithdrawOnly` branch already present in `process_withdraw`) — return `(0, 0)` for `delta_x`/`delta_y` and allow the deposit/withdraw to proceed, rather than reverting via `AmmError::CalcPnlError`. [8](#0-7) 

### Proof of Concept
1. Pool is initialized and operates normally; `target_orders.calc_pnl_x`/`calc_pnl_y` are periodically updated by successful `deposit`/`withdraw`/`withdrawpnl` calls to reflect `x1`/`y1` at that time.
2. Due to integer truncation in `restore_decimal`/`normalize_decimal_v2` (called in `calc_take_pnl` and in the post-update of `target_orders.calc_pnl_x`/`calc_pnl_y`), or due to a large withdrawal that reduces vault balances right before the snapshot correction executes, the recorded `calc_pnl_x * calc_pnl_y` ends up marginally greater than the true current `pool_pc_amount * pool_coin_amount`.
3. Any subsequent call to `process_deposit`, `process_withdraw` (status != `WithdrawOnly`), or `process_withdrawpnl` invokes `calc_take_pnl`, hits the `else` branch at `program/src/processor.rs:267-278`, and returns `Err(AmmError::CalcPnlError)`.
4. Because the snapshot values are never corrected on this failing path, every future call to these three instructions reverts identically, permanently freezing further deposits and (for non-`WithdrawOnly` pools) LP withdrawals — matching the reported bug class of a legitimate operation becoming permanently unreachable due to an overly strict pre-condition. [10](#0-9)
