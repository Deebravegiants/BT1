### Title
`CallDispatcher.dispatch` return-bomb griefing on untrusted call targets executed from cross-chain message delivery and intent order execution - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch` executes arbitrary attacker/order-creator supplied `Call[]` entries via `to.call{value: call.value}(call.data)` and unconditionally captures the full returned bytes into memory (`bytes memory result`), without any bound on the returned data size and without limiting forwarded gas. This is the exact anti-pattern the external report flags for `GovPool::execute`: an untrusted callee can return/revert a large bytes array, forcing the caller to pay for a large, unbounded `returndatacopy`, exhausting gas in that call frame.

### Finding Description
`CallDispatcher.dispatch` is the shared utility used to execute untrusted, attacker-controlled calldata reachable from at least two unprivileged, single-transaction paths:

1. Cross-chain token delivery with calldata: `WrappedHyperFungibleToken.onAccept` / `HyperFungibleToken.onAccept` (and the upgradeable variant) decode `message.data` from an incoming `PostRequest` body — fully controlled by the sender on the source chain — and forward it verbatim to `ICallDispatcher(_dispatcher).dispatch(message.data)`. [1](#0-0) [2](#0-1) 

2. Intent order execution: `IntentGatewayV2.placeOrder`/fill flow dispatches `order.predispatch.call` — attacker/order-creator supplied bytes decoded into `Call[]` with an arbitrary `to` — through the same `CallDispatcher`. [3](#0-2) 

The dispatcher itself does the unsafe unconditional copy:
```solidity
(bool success, bytes memory result) = to.call{value: call.value}(call.data);
if (!success) revert CallFailed(to, result);
``` [4](#0-3) 

Because `result` is bound to a `bytes memory` variable regardless of `success`, Solidity emits a `returndatacopy` of the entire return buffer for every call, whether it succeeds or reverts. A malicious `to` contract can return (or revert with) a huge byte array — the exact POC pattern in the report (`assembly { revert(0, 1_000_000) }`) — forcing the frame executing `dispatch` to pay quadratic memory-expansion gas, exhausting the gas forwarded to that call frame and reverting it with an out-of-gas exception.

This contrasts with the core host's own low-level call sites, which already avoid the pattern by discarding return data (`(bool success,) = destination.call(...)`), e.g. `EvmHost.dispatchIncoming`. [5](#0-4) 
That defensive discard pattern is absent in `CallDispatcher.dispatch`.

### Impact Explanation
An attacker who controls (or can nominate) the `to` target inside a `Call[]` — either as the sender of a cross-chain token message with `data`, or as the creator of an intent `Order` with `predispatch.call` — can make delivery/fill of that specific message or order arbitrarily gas-expensive or practically un-fillable within reasonable gas limits, griefing the relayer or solver who must call `onAccept`/fill the order to unlock escrowed funds. Because `onAccept`'s failure causes `EvmHost.dispatchIncoming` to delete the request receipt and return (allowing retry), and orders eventually time out and refund, this does not appear to cause *permanent* fund loss on its own — the damage is gas-griefing/DoS against relayers and solvers attempting delivery/fill, and repeated forced retries at ever-increasing gas cost. This is a Medium-severity griefing/DoS vector, not a fund-theft or permanent-freeze primitive, since recovery paths (retry, timeout refund) exist elsewhere in the protocol.

### Likelihood Explanation
Reachable with a single crafted cross-chain message body or a single crafted `Order.predispatch.call`/order fill, requiring only that the attacker deploy a contract with a malicious fallback/return, matching the report's proof-of-concept pattern closely. No privileged role is required — any sender of a `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer with `data`, or any order creator, can trigger it against the relayer/solver that processes the message.

### Recommendation
In `CallDispatcher.dispatch`, bound the copied return data size (e.g. via an `ExcessivelySafeCall`-style call that specifies a maximum `returndatacopy` size, such as `to.call{value: call.value, gas: gasleft()}(call.data)` combined with manual assembly limiting the copied bytes to a small fixed cap for the revert reason), or drop the captured return value entirely when it is not required for the revert message (mirroring the `(bool success,)` discard pattern already used in `EvmHost.dispatchIncoming`).

### Proof of Concept
Deploy a malicious contract:
```solidity
contract ReturnBomb {
    fallback() external payable {
        assembly { revert(0, 1_000_000) }
    }
}
```
Encode a `Call[]` with `to = address(returnBomb)`, `data = ""`, and either:
- embed it as `message.data` of a `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain transfer so that on delivery, `onAccept` calls `ICallDispatcher(_dispatcher).dispatch(message.data)`, or
- embed it as `order.predispatch.call` in an `IntentGatewayV2` order.

When the relayer/solver processes the delivery/fill, `CallDispatcher.dispatch`'s `to.call{...}(call.data)` triggers the 1,000,000-byte revert, and the enclosing call frame that captured `result` runs out of gas from the `returndatacopy`, causing the delivery/fill attempt to fail and requiring the relayer/solver to retry with a much larger gas allowance.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
