### Title
Unbounded Length-Prefixed Allocation in Livestream Upstream TCP Listener Enables Remote Resource-Exhaustion DoS - (File: src/agents/livestream/upstream.rs)

### Summary
The livestream agent binds an unauthenticated TCP listener on `0.0.0.0:9201` and parses incoming messages using a 4-byte big-endian length prefix followed by an `rkyv`-serialized payload. The length value read from the network is used directly to allocate a buffer with no upper-bound validation, allowing any network peer able to reach the port to force multi-gigabyte allocations per connection with a single 4-byte write.

### Finding Description
`Upstream::new` binds a `TcpListener` to all interfaces on a fixed port: [1](#0-0) 

Once a client connects, `EventReader::poll_stream` reads exactly 4 bytes as a `u32` length and immediately allocates a `Vec<u8>` of that size before reading any further payload bytes: [2](#0-1) 

There is no maximum-size check, no correlation with an expected/legitimate livestream event size, and no authentication on the TCP connection prior to processing this length prefix — the connection is accepted unconditionally in `Upstream::poll_next` and handed straight to the length-prefixed reader: [3](#0-2) 

This matches the reported bug class ("lack of data sanitization and validation of limits" leading to large-payload/resource-exhaustion attacks): an attacker sends a 4-byte length header claiming e.g. `0xFFFFFFFF` (~4 GiB) and the process attempts to allocate that buffer, then continues attempting to read that many bytes from the socket, before deserialization is ever attempted with `rkyv::from_bytes`: [4](#0-3) 

### Impact Explanation
Repeated connections with malicious length prefixes can force the orb-core process (or the dedicated livestream agent thread) to allocate large buffers, exhausting available memory and potentially crashing the process or degrading device availability. Because only one connection/stream is tracked at a time (`self.stream`), an attacker only needs a single TCP connection to hold the allocation, and can reconnect repeatedly to compound the effect. This is an availability/DoS impact on the orb device rather than a data-disclosure or signup-integrity impact.

### Likelihood Explanation
The listener binds to `0.0.0.0`, meaning it is reachable from any host that can route to the orb on the local network (this is the livestream feature used to visualize the biometric-capture UI over the network, paired with the `Downstream` UDP/RTP push on port 9200). No authentication, TLS, or peer allow-listing is performed at this layer before the length prefix is parsed, so any unprivileged network peer that can reach the port can trigger the issue with a trivial 4-byte payload.

### Recommendation
- Enforce a strict maximum message size (e.g., matching the largest legitimate `livestream_event::Event` serialization) before allocating the buffer in `EventReader::poll_stream`, rejecting/closing the connection if the declared length exceeds that bound.
- Avoid eagerly allocating the full declared size up front; consider incremental/capped allocation or reading in bounded chunks.
- Restrict the listener to trusted interfaces/loopback or add authentication/mutual trust verification for livestream connections instead of binding to `0.0.0.0`.
- Log and rate-limit connections that send invalid/oversized length prefixes.

### Proof of Concept
1. From any host on the same network as the orb, open a TCP connection to `<orb-ip>:9201`.
2. Send 4 bytes representing a large big-endian `u32`, e.g. `0xFFFFFFFF`.
3. Observe that `EventReader::poll_stream` executes `self.buf = vec![0; u32::from_be_bytes(self.len) as usize];` [5](#0-4) , immediately attempting a ~4 GiB allocation in the orb-core/livestream process, and then blocks waiting to read that many bytes — repeatable across reconnections to exhaust memory/availability.
