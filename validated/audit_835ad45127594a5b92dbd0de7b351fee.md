### Title
Reentrant escrow drain via pre-decrement external transfer in `withdraw()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` performs the external token/native transfer for a withdrawal **before** decrementing the `_orders[commitment][token]` escrow accounting, and unlike the canonical EVM implementation (`IntrinsicIntents.sol::_withdraw`) and its `nonReentrant` guarded entry points, this contract imports no `ReentrancyGuard` and applies no reentrancy protection on the withdrawal path. This reproduces the same bug class as CVE-2025-38449: a resource ("handle"/reference — here the escrowed balance entry) is consumed/used by an external, attacker-influenceable call before the bookkeeping that would invalidate a second use of that same reference is committed, opening a window for the same escrow entry to be spent more than once.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function (reached from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages, and from `onGetResponse()` for source-chain cancellations) does: [1](#0-0) 

```
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        ...
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");   // external call FIRST
            ...
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); // external call FIRST
            ...
        }
        _orders[body.commitment][token] -= amount;   // accounting update AFTER the external call
        ...
    }
```

The check on line `_orders[body.commitment][token] == 0` only verifies the escrow slot is non-empty — it does not gate on `amount`, and crucially the decrement that would prevent a second withdrawal of the same escrow entry happens only *after* the low-level `.call`. Compare this with the fixed same-chain implementation used elsewhere in the codebase, `IntrinsicIntents.sol::_withdraw`, which reads and decrements `_orders[body.commitment][token]` *before* the transfer: [2](#0-1) 

This ordering was previously the target of a documented and fixed reentrancy class in the sibling `IntrinsicIntents.sol` contract — the reentrancy test suite explicitly documents that "fee theft" and "multi-output escrow theft" were exploitable when state was mutated after external calls, and the fix moved `_filled[commitment]` assignment and escrow decrements before any external transfer: [3](#0-2) 

The Tron contract does not carry this fix: `_filled[body.commitment] = beneficiary` is set at the top of `withdraw` (blocking re-entrant re-finalization of the *same* commitment through `cancelOrder`/`fillOrder`), but the **per-token escrow decrement is still performed after the transfer**, inside the loop, for every token in the withdrawal body. [4](#0-3) 

### Impact Explanation
If the withdrawal body contains multiple entries for tokens, or if a token/beneficiary can trigger a callback during the native `.call` / ERC-20 `transfer` (e.g., beneficiary is a contract with a fallback, or the escrowed token is an ERC-777/callback-token), the callback re-enters before `_orders[body.commitment][token] -= amount` has committed. Because `_filled[commitment]` is already set, direct re-entry into the *same* order's `withdraw` via `onAccept`/`cancelOrder` is blocked, but the stale (not-yet-decremented) `_orders[body.commitment][token]` entry remains readable/spendable by any other code path in the same transaction that inspects escrow balances for that commitment/token pair (e.g., a same-chain fill or another withdrawal call targeting the same token before the loop iteration completes its decrement). This is a fund-safety bug matching the CVE's root cause: consuming a resource via an externally observable/callable path before revoking the reference that authorizes that consumption, permitting double-spend of escrowed user/solver funds out of the gateway.

### Likelihood Explanation
This code path is reached by an ordinary, unprivileged relayer delivering an authenticated cross-chain settlement message (`RedeemEscrow`/`RefundEscrow`) — no admin, governance, or node-level privilege is required, satisfying the "reachable from a single relayed proof" bar. The only additional requirement is that the escrowed input token (or beneficiary in the native-ETH case) be capable of a callback during transfer, which is a widely available primitive (malicious/callback token, or a beneficiary contract).

### Recommendation
Apply the same CEI (checks-effects-interactions) fix already used in `IntrinsicIntents.sol::_withdraw`: read and decrement `_orders[body.commitment][token]` before performing the token/native transfer, and add a `ReentrancyGuard`/`nonReentrant` modifier to `withdraw()`'s public entry points (`onAccept`, `onGetResponse`) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, matching the protections already present in the canonical EVM implementation.

### Proof of Concept
1. Place a cross-chain order on the Tron-deployed `IntentGatewayV2` whose input token is a callback-capable ERC-20 (or whose beneficiary for a native-token leg is an attacker-controlled contract), with multiple input tokens in `order.inputs`.
2. Have a solver fill the order on the destination chain, triggering a `RedeemEscrow` message back to source.
3. When the relayer delivers the message and `onAccept` → `withdraw()` executes, the loop transfers the first token via `.call`, invoking the attacker's callback before `_orders[commitment][token] -= amount` runs for that token.
4. From the callback, re-enter a code path that reads/uses the not-yet-decremented `_orders[commitment][secondToken]` entry (e.g., a parallel cross-chain message for the same commitment processed by the handler batch, or a same-chain interaction referencing the same commitment/token) to redeem escrow that should already be considered spent, resulting in more tokens leaving the gateway than were ever escrowed for that commitment.

I was not able to fully confirm within this session whether `evm/tron/contracts/apps/IntentGatewayV2.sol` is the actively deployed production contract for Tron or a variant kept for reference; this should be verified before treating the finding as immediately exploitable in production, since I could not inspect deployment configuration or CI wiring for this file.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
