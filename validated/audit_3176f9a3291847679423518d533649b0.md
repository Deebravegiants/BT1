### Title
Webhook shop-domain header is trusted for tenant attribution despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. `Registry.process` validates the HMAC and then hands the handler a `shop` value taken from that unsigned header, so the "shop the signature was actually generated for" and "the shop the handler acts on" are never proven to be the same value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `verifiable_query.to_signable_string` (i.e. the raw body), it never touches `shop`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the metadata passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_bound_by_signature == shop_used_by_handler`

But because `shop` is outside `to_signable_string`, the actual binding enforced is only:
`body_bound_by_signature == body`

An HMAC that is valid for a given body/secret pair remains valid for that exact body regardless of what the `shop-domain` header says. Since the app's `api_secret_key` is shared across every merchant that installs the app (this is a multi-tenant secret, not a per-shop secret), any unprivileged merchant who has installed the app receives genuinely-signed webhooks for their own shop. That merchant can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the untouched body, and `Registry.process` passes the forged `shop` value straight into `WebhookMetadata`, which is what host applications use to select the tenant/session/data to act on.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: an attacker-controlled shop identity flows into the app's business logic as if it were a signature-verified fact. Any handler logic that keys merchant data mutation, notifications, or session/store lookups off `WebhookMetadata#shop` (as documented and demonstrated in this gem's own webhook usage, e.g. `data.shop` in the registry tests) can be made to act against a different merchant's tenant using data belonging to the attacker's own shop, or vice versa — a cross-tenant confused-deputy condition. Given the impact criteria for this scan (cross-tenant access), this qualifies as Critical.

### Likelihood Explanation
Exploitation only requires being any merchant who has installed the app (an unprivileged, non-privileged-account condition since app installation is normally open to any Shopify merchant) and the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a captured valid `(body, hmac)` pair and a modified shop-domain header — no access to `api_secret_key` or any credential leak is required, and no host-application misconfiguration is needed since the gem's own `Request`/`Registry` code is what omits `shop` from the signed data.

### Recommendation
Include `shop` (and ideally `topic`) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived shop to the signed body before it is passed to `WebhookMetadata`/handlers — e.g. require handlers to also validate `shop` against an independent, per-shop registered webhook subscription/state (such as a stored webhook id or a known installed-shop list) rather than trusting the header value implicitly once HMAC-over-body succeeds.

### Proof of Concept
1. App merchant M installs the multi-tenant app and receives a legitimate webhook for `m-shop.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. M replays a POST to the same webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — this still matches because `B` is unchanged (per `Request#to_signable_string` returning only `@raw_body`, `lib/shopify_api/webhooks/request.rb:35-38`, and `HmacValidator#validate_signature`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the forged `victim-shop.myshopify.com` value (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler with it, causing the app to act on M's payload as if it originated from the victim shop.
