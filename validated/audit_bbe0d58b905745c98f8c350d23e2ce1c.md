### Title
Silent ERC20 transfer failure in IntentGatewayV2 predispatch sweep can zero out escrowed input amount - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder`'s predispatch "swap-then-escrow" flow sweeps swapped tokens from the `CallDispatcher` back to the gateway by encoding a raw `IERC20.transfer.selector` call and executing it through `ICallDispatcher.dispatch`. `CallDispatcher.dispatch` only checks that the low-level call did not revert; it never inspects the ABI-decoded boolean return value of `transfer()`. This reproduces exactly the "unsafe transfer() return value" bug class from the referenced Sherlock report, but here it sits in the intents escrow accounting path rather than a simple faucet.

### Finding Description
In the predispatch branch of `placeOrder`, after executing arbitrary swap calldata on the `CallDispatcher`, the gateway builds sweep calls with: [1](#0-0) 
which is dispatched via: [2](#0-1) 

`CallDispatcher.dispatch` executes each call with a bare low-level `call` and only reverts on `!success` (i.e., an actual EVM revert); it does not decode/verify the returned `bool`: [3](#0-2) 

For an ERC20 whose `transfer()` returns `false` on failure instead of reverting (a known "weird-ERC20" pattern, explicitly acknowledged as in-scope by protocols that support arbitrary tokens routed through predispatch swaps), the sweep call succeeds at the EVM level even though no tokens actually moved from the `CallDispatcher` to `IntentGatewayV2`. The gateway then measures the delta and, since no funds arrived, sets the escrowed input amount to zero: [4](#0-3) 

That zeroed amount then becomes the value credited into the escrow map that the destination-chain settlement/redemption relies on: [5](#0-4) 

The same unchecked-`transfer()`-via-`CallDispatcher` sweep pattern exists in the Tron variant of the contract as well: [6](#0-5) 

By contrast, every other token movement in the intents/gateway/host code paths correctly uses OpenZeppelin `SafeERC20`'s `safeTransfer`/`safeTransferFrom` (e.g. `EvmHost.sol`, `IntentsBase.sol`, `ExtrinsicIntents.sol`, `HyperFungibleToken*.sol`), confirming the sweep path is the outlier that bypasses the project's own safe-transfer convention.

### Impact Explanation
An order using the predispatch/swap path with an output token that returns `false` rather than reverting on transfer failure would have its input escrow silently recorded as zero while the actual swapped tokens remain stranded inside the `CallDispatcher` contract. This is a real fund-freezing/loss scenario reachable from a single, unprivileged `placeOrder` transaction: the user's real assets (native ETH/other input token used for predispatch) are consumed by the swap, but the resulting escrow backing the cross-chain order is zero, and the swapped tokens are left orphaned in the shared `CallDispatcher`, recoverable only by whoever can construct a subsequent `dispatch()` call sweeping that balance (and the `CallDispatcher` is shared infra used by many callers, so anyone could potentially claim those stranded funds via a crafted call). This is a concrete freezing/loss-of-funds condition satisfying the "permanent freezing of funds" bar.

### Likelihood Explanation
This requires that one of the swap/output tokens used in an order's predispatch path is a non-standard ERC20 that returns `false` on failed transfer rather than reverting. Since `IntentGatewayV2` and the underlying intents system are explicitly designed to be permissionless / open to arbitrary tokens and arbitrary predispatch calldata (users choose the swap and output assets), and the protocol elsewhere explicitly guards against similarly "weird" token behavior via `SafeERC20`, the likelihood that such a token is eventually used is non-trivial, and no additional privileges are needed to trigger it — any user placing an order with such a token hits the bug.

### Recommendation
Replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` sweep call with a `safeTransfer` semantics check, either by:
1. Having `CallDispatcher.dispatch` decode and validate the return data for calls targeting known ERC20 `transfer`/`transferFrom` selectors, or
2. Avoiding routing token sweeps through raw calldata entirely — instead call `IERC20(token).safeTransfer(...)` directly from a trusted execution context (not via arbitrary `Call[]` dispatch), and
3. Regardless, after the sweep, add an explicit balance-based assertion that the swept amount is at least equal to `order.inputs[i].amount` before crediting/reducing the input amount, reverting the whole order placement instead of silently proceeding with a zeroed escrow.

### Proof of Concept
1. Attacker/user deploys or uses an existing non-standard ERC20 `T` whose `transfer()` returns `false` on failure conditions (e.g., a blacklist/pausable token) instead of reverting.
2. User calls `IntentGatewayV2.placeOrder` with `order.predispatch.call` set to swap native ETH/DAI into `T` via a DEX router, and `order.inputs[0].token = T`.
3. Predispatch assets are transferred to the `CallDispatcher`, and the swap executes successfully, leaving `T` balance on the `CallDispatcher`.
4. The gateway builds a sweep `Call` with `data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` targeting `T`, dispatched via `CallDispatcher.dispatch`.
5. If `T.transfer()` returns `false` for this particular transfer (e.g., dispatcher happens to be blacklisted, or any protocol-specific failure condition that returns false instead of reverting), the low-level `call` still reports `success = true` to `CallDispatcher`, so `dispatch()` does not revert.
6. Back in `placeOrder`, `received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]` evaluates to `0`, so `order.inputs[i].amount` is set to `0` and the escrow for `T` is credited as `0` while the actual `T` balance remains stuck in the `CallDispatcher`.
7. The order is placed and dispatched cross-chain with zero real backing for that input, while the corresponding tokens are frozen in the shared `CallDispatcher` contract.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
