### Title
Coalescing of storage-deposit charges by contract address in `execute_postponed_deposits` wrongly discards legitimate deposits of a contract re-instantiated at the same address within a transaction - (File: `substrate/frame/revive/src/metering/storage.rs`)

### Summary
The scoped code lives in `TransactionMeter::execute_postponed_deposits` (`substrate/frame/revive/src/metering/storage.rs:385-444`), not in `substrate/frame/contracts/src/storage/meter.rs` as stated in the prompt (that file has no `sort_by`/coalescing logic at all — it uses a simple flat charge list, see lines 401-406 in that file). The `execute_postponed_deposits` function sorts `self.charges` by contract account and coalesces adjacent entries for the same account; any `Alive`/`Terminated` pair (in either order) causes the `Alive` charge's amount to be subtracted from `total_deposit` and the entry marked `Terminated` [1](#0-0) . Because the address is derived deterministically (CREATE2-style salt) and can be reused for a fresh contract instance created after a same-tx `SELFDESTRUCT`, a legitimate post-termination charge for the *new* incarnation of the contract can be misattributed to the dead one and silently voided.

### Finding Description
`execute_postponed_deposits` sorts charges by `contract` account id and coalesces same-account entries with this logic [2](#0-1) :
- `Alive + Alive` → sums the amounts.
- `Alive + Terminated` or `Terminated + Alive` (in either order) → subtracts the `Alive` amount from `total_deposit` and sets the merged state to `Terminated`.

`sort_by` on `Vec` is a stable sort, so charges for the same contract account retain their original call-stack order. The intended purpose (per the comment "undo all deposits made by a terminated contract") is to null out charges that occurred *before* a contract terminated in the same top-level transaction, since `terminate()` already added the full `refunded` amount to `total_deposit` directly and pushed a `Charge{contract, Terminated}` marker [3](#0-2) .

However, the coalescing rule is symmetric: it also matches `Terminated` followed by a *later* `Alive` charge for the same account. If a contract is deployed at address `X` (CREATE2 with deterministic salt), self-destructs (`SELFDESTRUCT`/`terminate_if_same_tx`), and — within the same transaction — a *new* contract is instantiated at the same address `X` (address reuse after termination is explicitly supported: `instantiate_unique_trie_id` test in `substrate/frame/revive/src/tests/pvm.rs:448-484` shows re-instantiation at the same address is possible, though that specific test drains `on_idle` between calls rather than doing it strictly within one tx), any subsequent storage `Charge` recorded for that reused account (e.g., via `charge_deposit`, `Diff` charges finalized through `absorb`/`finalize_own_contributions`) gets merged into the preceding `Terminated` marker and its deposit amount is subtracted from `total_deposit`, i.e., discarded.

This means: the origin's `total_deposit`/holds computed by `execute_postponed_deposits` would undercount the actual deposit owed for the storage now occupied by the *newly* instantiated (alive) contract at that address, because the new contract's charge is erroneously voided as if it belonged to the dead one.

Whether this is currently reachable end-to-end within a single transaction depends on two preconditions that I could not fully confirm from the available code:
1. Whether `only_if_same_tx` termination (via `contracts_to_be_destroyed`/`do_terminate` in `exec.rs`) actually frees the account/`AccountInfoOf` entry early enough in the *same* transaction to permit a subsequent `instantiate` at the identical address before the transaction concludes (the `do_terminate` cleanup does `AccountInfoOf::<T>::remove(contract_address)` at line 1841 of `exec.rs`, which happens at end-of-callstack processing, i.e., after the terminating frame is fully unwound — this occurs on `drop_frame` at the top level per `substrate/frame/revive/src/exec.rs:1692-1707`, so a subsequent instantiate call issued later at the top level within the same transaction could see the account already removed).
2. Whether the `DuplicateContract` collision guard (`substrate/frame/revive/src/exec.rs`, referenced by the `reentrant_instantiate_at_same_address_is_rejected` test and pr_12645.prdoc) only guards re-entrant/in-construction collisions and not fully-terminated-then-recreated addresses in the same transaction — the existing tests (`instantiate_unique_trie_id`, `root_call_can_create_and_destroy_in_same_tx`) suggest recreation is a supported flow, at least across `on_idle` drains or root-privileged nested calls, but I could not verify a signed, unprivileged, single-transaction instantiate→terminate→instantiate sequence targeting the identical address succeeds without hitting `DuplicateContract`.

### Impact Explanation
If reachable, the concrete impact is: the storage deposit `total_deposit` returned by `execute_postponed_deposits` (and consequently the amount reserved/held from the origin's account via `E::charge`) would be lower than the actual net storage bytes/items persisted by the reincarnated contract at the reused address by the end of the transaction. This breaks the stated invariant that "total storage deposit charged to origin equals net storage bytes actually persisted at end of transaction," letting the origin under-pay for consumed storage.

### Likelihood Explanation
This requires: (a) deterministic address reuse (CREATE2 with identical salt+code), (b) a `SELFDESTRUCT`/termination and a subsequent instantiate at the exact same address within one transaction, and (c) that the collision/duplicate-contract guard does not block the second instantiate once the first contract has fully terminated. I was unable to conclusively verify precondition (c) with the tools available — the existing tests strongly suggest address reuse after termination is a supported and tested pattern (`instantiate_unique_trie_id`), but none of the retrieved tests exercise the exact terminate→re-instantiate→charge sequence *strictly within a single transaction* for a non-root, signed origin to confirm whether `execute_postponed_deposits`'s coalescing produces an incorrect (under-charged) result versus simply never being reached because of an intervening `DuplicateContract` rejection or because `terminate()`'s `only_if_same_tx` deferral prevents the account from being freed before the transaction ends.

### Recommendation
The coalescing rule should not be symmetric with respect to ordering. Only `Alive` charges that occur *before* the `Terminated` marker for a given contract account (in original push order) should be voided; any charge that is pushed *after* a `Terminated` entry for the same account should be treated as belonging to a distinct (re-instantiated) contract incarnation and coalesced/charged normally, not merged into the terminated entry's discard logic. Concretely, in `execute_postponed_deposits`, replace the symmetric match arm `(Alive, Terminated) | (Terminated, Alive)` with an asymmetric rule: `(Alive, Terminated)` discards the accumulated `Alive` amount (contract died with pending charges), but `(Terminated, Alive)` should start a *new* coalescing group instead of merging, e.g. by pushing `ch` as a new entry rather than continuing the same `last` entry.

### Proof of Concept
Rust integration test plan (`substrate/frame/revive/src/tests/pvm.rs` or `sol/terminate.rs`):
1. Deploy contract `A` at deterministic address `X` via CREATE2 with salt `S`, writing storage (e.g., 100 bytes).
2. Within the same top-level extrinsic/call, have `A` (or a caller contract) `SELFDESTRUCT` `A`.
3. In a later nested call within the *same* transaction, instantiate a new contract at the same salt `S` (same address `X`), and have it write fresh storage (e.g., 50 bytes).
4. Assert:
   - `AccountInfo::<Test>::load_contract(&X)` shows the new contract's `storage_bytes`/`storage_byte_deposit` reflecting the 50 bytes written.
   - The origin's held balance under `HoldReason::StorageDepositReserve` (`get_balance_on_hold`) equals the deposit for the 50 bytes actually persisted, not zero/under-charged.
   - Compare against a directly-computed expected deposit (`bytes * DepositPerByte + items * DepositPerItem`) for the final persisted state, and assert `execute_postponed_deposits`'s returned `total_deposit`/actual holds match this expected value rather than being reduced by the discarded post-termination charge.

Note: this PoC cannot be fully validated without running the code; the two open preconditions above (same-tx address reuse being permitted past collision guards, and termination freeing the account slot before the second instantiate in the same tx) must be confirmed by executing the test, since the available tests only demonstrate cross-block or root-privileged variants of create+destroy+recreate.
