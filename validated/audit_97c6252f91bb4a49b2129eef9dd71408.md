### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw request body, and `HmacValidator` only authenticates that body. The `shop-domain` header, which the registry treats as the authoritative tenant identifier passed to every webhook handler, is never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [2](#0-1) . `HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header value: [4](#0-3) . Meanwhile `Webhooks::Request#shop` is parsed straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no cryptographic binding to the body or the HMAC: [3](#0-2) .

`Registry.process` uses this unauthenticated `request.shop` value directly to build the `WebhookMetadata` passed to the application's handler, which is the mechanism apps use to route the event to the correct tenant/session: [1](#0-0) .

The broken binding, stated as an equality that should hold but doesn't:
`bytes covered by HMAC (raw_body)` ≠ `bytes acted upon as tenant identity (shop-domain header)`.

Because the header is completely outside the signed payload, anyone who possesses one validly-signed webhook delivery (body + HMAC + topic/webhook-id headers) for their *own* shop can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will invoke the handler with `shop:` set to the attacker-chosen domain, tricking the app into applying that shop's own webhook event to a different tenant's data/session context, entirely from the perspective of an unprivileged actor who never needed the app's `client_secret` or `api_secret_key` — only a webhook payload that was legitimately delivered to them for their own store.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: the gem asserts "this payload is authentically from Shopify for shop X" but shop X is attacker-controlled and unverified. Any host application that trusts `WebhookMetadata#shop` (as documented/intended usage of this library) to select which merchant's session/data to update can be made to attribute one shop's webhook event to another shop, i.e. cross-tenant access/write, which satisfies the Critical cross-tenant impact bar.

### Likelihood Explanation
Requires no privileged credentials — only that the attacker's own shop (which they legitimately control as an app installer) receives at least one real webhook delivery, which is trivial to obtain (e.g. install the app, trigger any subscribed event). Replaying that captured request with a modified `shop-domain` header against the app's public webhook endpoint is a standard HTTP replay, well within reach of an "unprivileged internet user."

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed body (e.g., verify `shop` against a value embedded in — and covered by — the signed payload) before it is passed to `WebhookMetadata` and handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and its valid `x-shopify-hmac-sha256` header value `H` (computed by Shopify over `B` using the app's real secret).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header value: [3](#0-2) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H`, so validation passes: [5](#0-4) .
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` — the app now processes attacker-controlled data under the victim shop's tenant identity: [6](#0-5) .
