### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which merchant/tenant the event belongs to. This mirrors the reported Solidity bug class: a value that gates/identifies a resource (`category.enabled` in the report, `shop` here) is read and acted upon by downstream logic, but is not covered by the check that is supposed to bind the whole operation together (the `enabled` flag check in the report, the HMAC signature here).

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw JSON body: [1](#0-0) 

But `shop` is read straight from an HTTP header, entirely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler — the handler has no way to know the `shop` value was never bound to the signature: [3](#0-2) 

`Utils::HmacValidator.validate` only compares `verifiable_query.to_signable_string` (the raw body) against the HMAC — it never incorporates the `shop` header: [4](#0-3) 

The identity binding that should hold is:
`shop_that_receives_the_event == shop_whose_key_signed_the_event`

But what is actually checked is:
`hmac_of(raw_body) == hmac_of(raw_body)` — independent of `shop`.

Because the app's `client_secret`/`api_secret_key` is shared across all tenants/shops of a given app (it is not per-shop), any legitimate merchant who has installed the app can receive a genuinely Shopify-signed webhook for their *own* shop (e.g. `orders/create`), and that HMAC is valid for the same JSON body regardless of which shop it is claimed to be from — since `shop` isn't part of the signed content. That merchant can then replay the exact same body+HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Utils::HmacValidator.validate` will still return `true` (correct signature over correct body), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field claims to be a different tenant than the one that actually produced/owns the payload.

If the host application's webhook handler uses `data.shop` (as documented/intended usage, see `WebhookMetadata` construction) to look up which tenant's session/access token to act on, or to write data attributed to that tenant, this results in cross-tenant confusion: an attacker-controlled shop can inject events that a handler will process as if they came from a victim shop.

### Impact Explanation
This crosses the "cross-tenant access" bar in the Critical impact bucket: an unprivileged (but app-installed) shop can cause the receiving application to attribute a webhook payload — and any state changes/side effects the handler performs, keyed by `data.shop` — to a different, victim tenant, without needing the victim's or the app's credentials. The vulnerability is rooted entirely in this gem's own `Request`/`Registry`/`HmacValidator` code, not in host-application misuse, since the gem's public API (`WebhookMetadata.shop`) is exactly what host apps are expected to trust for tenant identification.

### Likelihood Explanation
Requires only that the attacker themselves have installed the app on a shop they control (an "unprivileged internet user" relative to any other tenant) and can trigger at least one webhook to capture a valid body+HMAC pair, then replay it with a forged `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the app owner's infrastructure is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value that is verified, not just the raw body. Concretely, `Webhooks::Request#to_signable_string` (or `HmacValidator`) should not be the sole basis for trusting `request.shop`; at minimum, `Registry.process` should independently confirm the request's `shop` header corresponds to a session/shop that is expected to receive this specific signed payload (e.g., by having callers supply the expected shop and comparing it, or by only trusting `shop` after correlating it with `webhook_id` via a Shopify API lookup) rather than exposing it as an implicitly-trusted field of `WebhookMetadata` on the strength of a body-only HMAC check.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and lets Shopify deliver a genuine webhook (e.g. `orders/create`) to the app's endpoint. They capture the raw body `B` and the valid header `x-shopify-hmac-sha256: H` (a real Shopify-computed HMAC over `B` using the app's shared `api_secret_key`).
2. Attacker resends a POST to the same webhook endpoint with body `B`, `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` matches (verified via `Utils::HmacValidator.validate`, which only checks `@raw_body`) and whose `shop` returns `"victim.myshopify.com"` [5](#0-4) .
4. `Registry.process` passes HMAC validation and invokes the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: B, ...)` [3](#0-2) , causing the handler to process attacker-supplied data under the victim shop's identity.
