### Title
Withdraw instruction cannot burn the pool's final unit of LP supply, permanently dust-locking a share of pool reserves - (File: program/src/processor.rs)

### Summary
`process_withdraw` in `program/src/processor.rs` rejects any withdrawal request where `withdraw.amount >= amm.lp_amount`, mirroring the reported `InvestorDistribution.claim()` pattern where a `require` blocks the legitimate "claim everything remaining" case. In both cases, a strict inequality/equality check that is meant to guard against a degenerate zero state instead prevents the last holder of the resource (claimable tokens / LP supply) from redeeming their full, legitimately owed balance in a single call.

### Finding Description
In `process_withdraw`, after all account and mint checks: [1](#0-0) 

```rust
if withdraw.amount > user_source_lp.amount {
    return Err(AmmError::InsufficientFunds.into());
}
if withdraw.amount > lp_mint.supply || withdraw.amount >= amm.lp_amount {
    return Err(AmmError::NotAllowZeroLP.into());
}
```

The second check uses `>=` against `amm.lp_amount`, not `>`. This means a caller can never submit `withdraw.amount == amm.lp_amount`, even when their own `user_source_lp.amount` legitimately equals `amm.lp_amount` (i.e., they hold 100% of the pool's outstanding LP supply, such as the sole remaining liquidity provider after all others have exited). The instruction is only reachable via the unprivileged `Withdraw` account-binding path (`amm_program/instruction.rs` `AmmInstruction::Withdraw`), so any LP holder can hit this condition with attacker-chosen `withdraw.amount` data.

This is directly analogous to the reported bug: `InvestorDistribution.claim()` reverted whenever `investors[msg.sender].amount - claimable == 0`, preventing a user from claiming their exact final/full balance in one call, forcing use of an alternate function (`claimExact()`). Here, there is no `claimExact()`-equivalent bypass — `withdraw.amount` is a raw instruction parameter and the `>=` check applies uniformly, so there is no alternate on-chain path within `process_withdraw` to redeem the exact full `amm.lp_amount`.

### Impact Explanation
For the LP who owns the entirety of `amm.lp_amount` (the final withdrawer, e.g., the last provider after all others withdrew), a single call with `withdraw.amount == amm.lp_amount` always fails with `AmmError::NotAllowZeroLP`. To withdraw, they must instead submit `withdraw.amount < amm.lp_amount` (e.g., `amm.lp_amount - 1`), which via `InvariantPool::exchange_pool_to_token` floors the pro-rata coin/pc amounts: [2](#0-1) 

This leaves at least 1 unit of LP supply (and its floor-rounded corresponding share of `total_coin_without_take_pnl`/`total_pc_without_take_pnl`) permanently un-redeemable by that LP, since after the withdrawal `amm.lp_amount` becomes `1`, and the same `>=` check will forever block redeeming that residual unit (and there's no other LP holder left to burn it). This constitutes a permanent, protocol-enforced freezing of a small amount of LP-owned reserves — the exact class of impact ("availability of funds compromised, though not stolen") that the original report was downgraded to Medium for.

### Likelihood Explanation
This is deterministically triggered any time the last LP attempts to fully exit a pool by submitting `withdraw.amount == amm.lp_amount` — a natural, expected user action (fully unwinding a position), requiring no privileged access, special timing, or additional preconditions beyond holding the full remaining LP supply.

### Recommendation
Change the boundary check from `withdraw.amount >= amm.lp_amount` to `withdraw.amount > amm.lp_amount`, matching the pattern used for `lp_mint.supply` (`withdraw.amount > lp_mint.supply`), so that redeeming the entire remaining LP supply is a valid, exact operation. If leaving `amm.lp_amount == 0` risks downstream division-by-zero elsewhere (e.g., in future `Deposit`/`Withdraw` invariant math), that should instead be guarded explicitly at those specific call sites rather than by unconditionally rejecting full withdrawal here.

### Proof of Concept
1. Pool starts with `amm.lp_amount = N`, all held by LP A.
2. All other LPs exit (not required if A is sole provider from `Initialize2`).
3. LP A calls `Withdraw` with `withdraw.amount = N` (equal to `user_source_lp.amount` and `amm.lp_amount`).
4. `process_withdraw` reaches `withdraw.amount >= amm.lp_amount` → `true` → returns `AmmError::NotAllowZeroLP`, aborting the transaction. See [3](#0-2) .
5. LP A must instead call with `withdraw.amount = N - 1`; the burn reduces `amm.lp_amount` to `1`, and the corresponding floor-rounded reserve share tied to that last unit is now permanently unreachable, since no future call can ever submit `withdraw.amount == amm.lp_amount` again.
