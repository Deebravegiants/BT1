## Title
Zest zToken `transfer` accepts `tx-sender`-based authorization, letting any intermediary contract move a victim's vault shares — (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Every Zest vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) implements the SIP-010 `transfer` function for its zToken share, authorizing the move if **either** `tx-sender` **or** `contract-caller` equals the `from` account: [1](#0-0) 

This is the exact analog of the reported `TradeCallee` bug class: `tx-sender` in Clarity is preserved unchanged across the entire call chain regardless of intermediate contract calls, exactly like `tx.origin` in Solidity, while `contract-caller` is the immediate caller (Solidity `msg.sender`). Zest's own audit remediation notes elsewhere in the codebase explicitly recognize this hazard and require *strict equality* (`contract-caller == tx-sender`) to prevent exactly this kind of proxy exploitation for `repay`/`liquidate` in the market contract: [2](#0-1) [3](#0-2) 

But the vault `transfer` function does not apply that same strict check — it uses `or`, so satisfying `tx-sender == from` alone is sufficient, even when `contract-caller` is an arbitrary, unrelated proxy contract.

### Finding Description
The identity that should hold is: *a zToken share balance can only be moved by the account that owns it, or an entity that account has explicitly authorized for that specific transfer* — i.e. `moved_by(from) == from` at the immediate-call level, analogous to requiring `_sender == trader` rather than `tx.origin == trader` in the reported bug.

Because the vault's `transfer` accepts `(is-eq tx-sender from)` as sufficient, any contract that the victim happens to call *for any purpose* within the same transaction can, as a nested call, invoke the vault's `transfer` on the victim's behalf and redirect their zToken balance to an attacker-controlled address, without the victim ever intending or approving that specific transfer. The victim's `tx-sender` is preserved through arbitrary levels of contract-to-contract calls in Clarity, so the check `(is-eq tx-sender from)` is satisfied purely because the top-level transaction was originated by the victim — not because the victim's immediate action was consenting to this transfer.

This directly breaks the custody identity: the zToken balance held by a user is supposed to represent their exclusive redeemable claim on the underlying asset in the vault (`balanceOf(user)` == underlying entitlement of `user`), but this authorization gap lets a malicious contract silently reassign that claim to another principal.

### Impact Explanation
zTokens are the vaults' share representation of deposited principal (STX, sBTC, USDC, USDH, stSTX, stSTXbtc). An attacker who lures a victim into any transaction that calls an attacker-controlled contract can drain the victim's zToken balance directly to themselves via a nested call to `transfer`, with `from` set to the victim and `to` set to the attacker. This is direct theft of user principal at rest, matching the Critical impact bar (direct theft of user funds).

### Likelihood Explanation
Exploitation requires the victim to interact with an attacker-influenced contract in the same transaction (e.g., a malicious "helper"/router/aggregator contract the victim calls, believing it does something unrelated). This is a realistic social-engineering vector common in DeFi (fake yield aggregators, "helper" contracts, batchers) and requires no privileged access — it is reachable by any unprivileged principal that can get a victim to invoke a contract they control.

### Recommendation
Change the authorization check in `transfer` (and any other vault/zToken function relying on `tx-sender` as authorization for moving another account's balance) to require `contract-caller == from` (i.e., only the immediate/direct caller, matching the pattern already used correctly for `repay`/`liquidate` with `(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)`), or drop the `tx-sender` branch of the `or` entirely so that only the direct owner-initiated call (or explicitly whitelisted authorized contract) can move zToken balances.

### Proof of Concept
1. Attacker deploys `MaliciousHelper.clar`, which internally calls `(contract-call? .v0-vault-stx transfer amount victim attacker none)`.
2. Attacker convinces victim to call some innocuous-looking public function on `MaliciousHelper` (e.g., "claim rewards", "compound", "swap") — victim's wallet only sees a call to `MaliciousHelper`, and any post-conditions the wallet sets are typically scoped to what the victim believes they're doing, not to third-party vault contracts.
3. Inside that call, `MaliciousHelper` invokes `v0-vault-stx`'s `transfer`, passing `from = victim` (the current `tx-sender`), `to = attacker`.
4. In `transfer`, `(is-eq tx-sender from)` evaluates true because `tx-sender` is still the victim throughout the nested calls, even though `contract-caller` is `MaliciousHelper`, not the victim.
5. `(try! (ft-transfer? zft amount from to))` succeeds, moving the victim's zSTX shares (and thus their redeemable underlying STX) to the attacker. [1](#0-0)
