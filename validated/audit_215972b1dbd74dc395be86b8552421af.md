### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and label the webhook are taken from unauthenticated HTTP headers that are never included in the signed bytes. Any unprivileged user who can obtain one genuinely-signed webhook body (e.g., by installing the public app on their own free/dev store) can replay that exact body with the HMAC header unchanged but with the `shop-domain` (and/or `topic`) headers swapped to claim the event belongs to a different, victim shop.

### Finding Description
The signable string for a webhook request is defined as just the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only ever calls `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it hashes the body only: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC checks out, then dispatches to the handler using the unauthenticated `shop` and `topic` values straight from the request: [4](#0-3) 

The identity binding that should hold is: `shop header used to attribute/process the event == shop whose data actually produced the signed body`. Because the HMAC covers only `@raw_body` and not the `shop-domain`/`topic` headers, this binding is not enforced by the gem. A public app shares one `api_secret_key` (the app's `client_secret`) across all installing shops, so it is not a per-tenant secret — any shop that installs the app receives webhooks signed with that same key. An attacker who installs the app on their own (attacker-controlled, unprivileged) shop can capture a real `(raw_body, hmac)` pair from a genuine webhook delivery, then POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain (and optionally the `x-shopify-topic` header rewritten too). `HmacValidator.validate` still succeeds because it never looks at those headers, and `Registry.process` will invoke the app's handler with `WebhookMetadata.new(topic: ..., shop: victim_shop, body: attacker_body, ...)`, causing the host application to act on attacker-supplied data while believing it originates from the victim tenant.

### Impact Explanation
This breaks the shop-identity binding across tenants: an unprivileged attacker (someone who can merely install the app on their own store) can forge events that are processed by the app as belonging to an arbitrary victim shop, and can additionally relabel the event topic since that too is unauthenticated. Any host application logic that trusts `WebhookMetadata#shop`/`#topic` to select which tenant's data to update (a documented and expected usage pattern of this gem's webhook API) can be manipulated into writing/mutating data under, or reacting on behalf of, a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop installed: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app on a shop the attacker controls (free to do, no special privileges) and capturing one webhook delivery, after which the header rewrite and replay is trivial.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable string that is HMAC-verified, or otherwise cryptographically bind them to the body before use, so that `HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. App is public and installed by both an attacker-controlled shop `attacker.myshopify.com` and a victim shop `victim.myshopify.com`.
2. Attacker triggers a webhook on their own shop (e.g., `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`), per `lib/shopify_api/webhooks/request.rb`.
3. Attacker replays the exact same `B`/`H` to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim.myshopify.com` (and optionally the `x-shopify-topic` header).
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, matches `H`, and passes.
5. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) invokes the registered handler with `shop: "victim.myshopify.com"` and the attacker's body content, causing the host app to process attacker-controlled data as an authentic event for the victim tenant.
