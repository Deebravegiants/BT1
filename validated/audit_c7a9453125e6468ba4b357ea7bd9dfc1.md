## Title
Blacklisted creator address permanently freezes their accrued fee balance in `FeeVault` - (`packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` pays out `creatorBalance[msg.sender]` directly to `msg.sender` in USDC. Because USDC (and similar tokens) can blacklist addresses, a creator whose wallet becomes blacklisted can never call `claim()` successfully again, and there is no mechanism in `FeeVault` or `Bonding` to redirect or rescue an already-accrued balance tied to that address.

### Finding Description
`claim()` reads the caller's own balance and unconditionally `safeTransfer`s it to `msg.sender`: [1](#0-0) 

If `msg.sender` (the creator address originally recorded via `Bonding.launch`/`transferCreator`) is blacklisted by the USDC contract, `usdc.safeTransfer(msg.sender, amount)` reverts every time, and since the withdrawal condition is baked directly into the payout call there is no alternate path to retrieve `creatorBalance[msg.sender]`.

`Bonding.transferCreator` only reassigns *future* fee attribution — it never touches the already-accrued `creatorBalance` mapping in `FeeVault`, which is keyed by the old (now-blacklisted) address: [2](#0-1) 

So even if the creator proactively calls `transferCreator(tokenAddress, newAddress)` before or after being blacklisted, the USDC that already accrued under `creatorBalance[oldCreator]` in `FeeVault` remains permanently claimable only by `oldCreator`, whose transfer will forever revert. `FeeVault` has no owner-level rescue, no per-creator-balance reassignment, and no "push to holding address" fallback — unlike `claimProtocol`/`sweepDonations`, which are permissionless and pay a rotatable `feeTo`: [3](#0-2) 

This is the same root cause described in the external report: a hard-coded `safeTransfer`/`safeTransferFrom` to a potentially-blacklisted address embedded inside the only code path that can release the funds, with no alternate settlement route.

### Impact Explanation
Any creator whose address is later blacklisted by USDC's issuer (compliance action, sanction, or accidental blacklist) permanently loses access to their entire accrued `creatorBalance`. Since fees continuously accrue to `creatorBalance[creator]` on every buy/sell via `accrue()`, the frozen amount can grow indefinitely for as long as the token keeps trading, because `FeeAccrued` keeps crediting the same (unreachable) balance slot. This is a permanent freeze of creator funds with no owner or user-side recovery mechanism in the contract as written — a concrete, unprivileged-triggerable freezing of funds matching Medium severity.

### Likelihood Explanation
Requires only that a creator's own wallet later become blacklisted by the USDC issuer — a real-world, externally-triggered event outside the creator's or protocol's control, and one the original report treats as a legitimate threat model for USDC-denominated protocols. No attacker action against the protocol is needed; it is a design gap (no rescue path), not an active exploit, so likelihood is low-to-moderate but the resulting freeze is total and permanent for the affected creator's balance.

### Recommendation
Decouple the balance check from the transfer, e.g.:
- Allow the owner (or the creator via a designated backup address) to redirect `creatorBalance[oldCreator]` to a new recipient after proving control or after a timelock, similar to how `setFeeTo` lets `feeTo` be rotated independent of pending balance.
- Alternatively, wrap `claim()`'s transfer in a try/catch that, on failure, moves the amount to an owner-controlled holding/escrow balance claimable by the creator through an alternate address, rather than leaving it stuck against the original blacklisted address.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`, trades accrue fees to `FeeVault.creatorBalance[C]` via `accrue()` on every buy/sell.
2. USDC issuer blacklists `C` (external event, e.g. `USDCLike.isBlacklisted(C) == true`, as modeled in the repo's own test mocks: [4](#0-3)  ).
3. `C` calls `FeeVault.claim()` — `usdc.safeTransfer(C, amount)` reverts because `C` is blacklisted; `claim()` permanently reverts for `C`.
4. `C` calls `Bonding.transferCreator(tokenAddress, newAddress)` to redirect future attribution — this does not move the existing `creatorBalance[C]` in `FeeVault`, which stays locked forever with no way for `newAddress` to claim it.

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```text
    function claimProtocol() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.protocolBalance;
        if (amount == 0) revert NothingToClaim();
        $.protocolBalance = 0;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit ProtocolFeesClaimed(feeTo_, amount);
    }

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
```

```text
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```
