### Title
Blacklisted/self-blacklisting solver or user permanently freezes escrowed IntentGateway funds via reverting push transfer in `_withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` releases escrowed order tokens by pushing them directly to the `beneficiary` address via `IERC20.safeTransfer`. This function is the sole settlement path for both cross-chain fills (`RedeemEscrow`) and refunds/cancellations (`RefundEscrow`), invoked from `onAccept` when Hyperbridge delivers the settlement message. If the beneficiary address is blacklisted on the underlying ERC20 (e.g. USDC/USDT-style tokens with `isBlacklisted`), the transfer reverts, `onAccept` reverts, and the message can never be successfully delivered — permanently freezing the escrowed user funds with no pull-based recovery path.

### Finding Description
`_withdraw` in [1](#0-0)  iterates over the withdrawal request's tokens and does:

```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```

directly to `beneficiary`, which is taken verbatim from the cross-chain `WithdrawalRequest.beneficiary` field (i.e., the solver's address in the `RedeemEscrow` case, or the original `order.user` in the `RefundEscrow` case). This is called from `onAccept` in the cross-chain flow: [2](#0-1) , and from `onGetResponse` for the cancel-from-source path: [3](#0-2) .

The same unconditional push pattern also exists in the Tron/legacy contract's `withdraw`: [4](#0-3) .

There is no try/catch around the transfer, no alternative "credit and let the beneficiary pull later" fallback, and no way to redirect the beneficiary once the order commitment (which is signed/hashed with the beneficiary baked in via `msg.sender` at fill time, or `order.user`) has been fixed. A solver that fills a cross-chain order and then gets itself blacklisted on the input token before the `RedeemEscrow` settlement message is delivered (self-inflicted, permissionless — any solver can request/trigger blacklisting of its own address on tokens like USDC/USDT) causes every future delivery attempt of that specific ISMP POST request to revert inside `onAccept`. Because ISMP request delivery is idempotent/replay-based on the exact request body (which encodes the fixed beneficiary), retries by any relayer hit the identical revert. The user's escrowed input tokens on the source chain are then locked forever — the solver has already been paid out the destination output tokens (or the user already got refunded, in the cancel path also using the same address baked into the order), but the source-chain escrow can never be released.

Additionally, for the `RefundEscrow`/cancel path, if `order.user` itself is blacklisted (or becomes blacklisted, e.g., a compliance action against a wallet) between order placement and refund, the same permanent freeze occurs on cancellation — the user's own escrowed principal becomes permanently unrecoverable.

### Impact Explanation
This causes permanent freezing of user funds (escrowed order inputs) with no recovery mechanism, satisfying the "permanent freezing of funds" bar for High severity. Because IntentGateway escrows can be arbitrarily large token amounts per order, and there is no owner/governance sweep or pull-based reclaim path once `_withdraw` starts reverting, the loss is unbounded and irreversible for any affected order.

### Likelihood Explanation
The trigger requires only that a beneficiary address (solver or user) be blacklisted on a common blacklistable ERC20 such as USDC or USDT — a known, well-documented capability of those token issuers. A solver can trivially arrange this against itself after having already extracted the destination-side output tokens, deliberately griefing/DoS-ing the specific order's escrow release, or an already-blacklisted address could simply place/fill orders and immediately encounter this stuck state. No special privileges beyond being a normal order participant (user placing an order, or solver filling one) are needed, matching the "intent solver" and "token bridger/escrow" unprivileged actor classes explicitly in scope.

### Recommendation
Do not perform unconditional pushes to attacker/beneficiary-controlled addresses inside the ISMP delivery path. Wrap the token transfer in a try/catch (or use a low-level call and check success) and, on failure, credit the amount to an internal `pendingWithdrawals[beneficiary][token]` balance that the beneficiary (or anyone, on their behalf, to a different address they control) can later claim via a separate `claim()` function — mirroring the recommended pattern from the referenced Cooler audit finding. This ensures `onAccept`/`onGetResponse` never revert due to third-party token behavior, so ISMP message delivery always succeeds and escrow release/refund cannot be blocked indefinitely by one recipient's token-level status.

### Proof of Concept
1. User places a cross-chain order on chain A escrowing `amount` of USDC via `placeOrder`, with output required on chain B.
2. Solver calls `fillOrder` on chain B, providing the required output tokens to the user; `_fillCrossChain` records `_filled[commitment] = solver` and dispatches a `RedeemEscrow` POST request back to chain A naming `beneficiary = solver` (see `evm/src/apps/intentsv2/ExtrinsicIntents.sol` lines 164-220).
3. Before a relayer delivers this POST request to chain A, the solver arranges (or already has) a USDC blacklist entry for its own address (e.g., via a sanctioned-address flag, or simply using an address Circle has already blacklisted).
4. A relayer submits the proof and Hyperbridge calls `onAccept` on chain A's IntentGateway, which calls `_withdraw(body, false, true)`.
5. Inside `_withdraw`, `IERC20(usdc).safeTransfer(solver, amount)` reverts because `solver` is blacklisted by USDC.
6. `onAccept` reverts, so the ISMP message delivery transaction reverts as a whole. Any subsequent relayer attempt to deliver the same request hits the identical revert — the escrowed USDC on chain A is now permanently stuck with no other recovery function available in `IntentsBase`/`ExtrinsicIntents`.
