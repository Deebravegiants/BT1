### Title
Missing `FeeExceedsAmountError` / non-negativity guard in `IntentsSDK.createWithdrawalIntents` lets a negative/attacker-controlled `actualAmount` reach HotBridge's signed intent, decoupled from `feeEstimation.underlyingFees.relayerFee` - (File: `packages/intents-sdk/src/sdk.ts`, `packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents` (`sdk.ts:334-372`) recomputes `actualAmount = amount - feeEstimation.amount` when `feeInclusive: true`, but unlike `_estimateWithdrawalFee` (`sdk.ts:421-425`) it never checks `amount <= feeEstimation.amount` and never throws `FeeExceedsAmountError`. `HotBridge.validateWithdrawal` (`hot-bridge.ts:259-301`) also performs no amount/positivity validation, so a negative `actualAmount` flows unchecked into `HotBridge.createWithdrawalIntents` (`hot-bridge.ts:177-252`), where the final on-chain `mt_withdraw` amount is computed as `actualAmount + (isNative ? feeAmount : 0n)` using `feeAmount` taken from `feeEstimation.underlyingFees[RouteEnum.HotBridge].relayerFee` — a value that is never cross-checked against `feeEstimation.amount`.

### Finding Description
The invariant the question poses is: `sum(debits in produced intents) == amount + (feeInclusive ? 0 : fee)` and destination receives `amount - (feeInclusive ? fee : 0)`, both non-negative, else throw before signing.

Trace:
1. `_estimateWithdrawalFee` (`sdk.ts:408-453`) is the only place that guards `feeInclusive` underflow: `if (args.withdrawalParams.amount <= fee.amount) throw new FeeExceedsAmountError(...)` (`sdk.ts:421-425`).
2. The public `IntentsSDK.createWithdrawalIntents` (`sdk.ts:334-372`), which is what `signAndSendWithdrawalIntent` actually calls (`sdk.ts:704-713`), duplicates the subtraction `actualAmount = amount - feeEstimation.amount` (`sdk.ts:342-344`) **without** this guard.
3. `processWithdrawal` (`sdk.ts:793-857`) lets a caller pass `args.feeEstimation` directly, in which case `_estimateWithdrawalFee` (and its guard) is skipped entirely (`sdk.ts:801-812`), and the unguarded path in `createWithdrawalIntents` is the only computation of `actualAmount` that executes.
4. `actualAmount` (now possibly negative, since BigInt subtraction never throws/underflows) is forwarded to `bridge.validateWithdrawal` (`sdk.ts:346-354`). `HotBridge.validateWithdrawal` (`hot-bridge.ts:259-301`) checks address validity, token/destination collision, and Stellar trustlines, but never checks `args.amount > 0` or any minimum.
5. `HotBridge.createWithdrawalIntents` (`hot-bridge.ts:177-252`) computes `feeAmount = getUnderlyingFee(args.feeEstimation, RouteEnum.HotBridge, "relayerFee")` (`hot-bridge.ts:197-201`) — read from `feeEstimation.underlyingFees`, a field independent of `feeEstimation.amount` used upstream — then `amount = args.withdrawalParams.amount + (isNative ? feeAmount : 0n)` (`hot-bridge.ts:222`), and signs an `mt_withdraw` intent with that `amount` (`hot-bridge.ts:224-249`).

Because `feeEstimation.amount` (used to compute `actualAmount`) and `feeEstimation.underlyingFees[...].relayerFee` (used to compute the final on-chain `amount`) are two independent fields of the same attacker-supplied `feeEstimation` object, a caller that constructs/forwards a `feeEstimation` with `amount` large relative to `withdrawalParams.amount` (driving `actualAmount` negative) and a mismatched `relayerFee`, produces an on-chain `mt_withdraw` amount equal to `actualAmount + relayerFee`, which no longer equals `amount - (feeInclusive ? fee : 0)`. The client-side `assert(intent.amounts[0] === amount.toString(), ...)` (`hot-bridge.ts:235`) only checks internal SDK/omni-sdk consistency, not correctness against the user's original request, and does not throw on negative values.

### Impact Explanation
The signed `mt_withdraw`/`token_diff` intent's `amount` field can diverge from the value implied by `amount - fee`, because the missing guard allows the two independent fee-derived quantities (`feeEstimation.amount` and `feeEstimation.underlyingFees.relayerFee`) to be set inconsistently by whoever supplies `feeEstimation` (an unprivileged caller of `processWithdrawal`/`signAndSendWithdrawalIntent`, or an integrator blindly forwarding a solver-provided estimate). This can either (a) produce a negative gross amount, likely rejected on-chain (wasted signed nonce/deadline, stuck withdrawal), or (b) produce a final debited/withdrawn amount larger or smaller than the user's authorized `amount - fee`, i.e. fee overcharge or a debit not matching the displayed fee — matching the "fee overcharge" / "solver overpaid" High-impact category, repeatable on every call where such a `feeEstimation` is supplied.

### Likelihood Explanation
Requires: `assetId` on HotBridge with `feeInclusive: true`, a small `amount`, and control over the `feeEstimation` object passed to `signAndSendWithdrawalIntent`/`processWithdrawal` (either directly by an unprivileged SDK caller, or via an integrator that forwards a counterparty/solver-provided fee estimate without re-validating it against `withdrawalParams.amount`). No RPC/relayer compromise is needed — only the missing local guard in `sdk.ts` and the absent cross-validation in `hot-bridge.ts`. Feasible and repeatable per withdrawal call.

### Recommendation
Add the same `FeeExceedsAmountError` (or equivalent non-negativity) check inside `IntentsSDK.createWithdrawalIntents` (`sdk.ts:342-344`) that already exists in `_estimateWithdrawalFee`, and add a cross-check in `HotBridge.createWithdrawalIntents`/`validateWithdrawal` that `feeEstimation.amount` is consistent with `getUnderlyingFee(..., "relayerFee")` (e.g., re-derive one from the other, or assert their relationship) before signing, rejecting any withdrawal whose computed on-chain amount is negative or inconsistent with `amount - fee`.

### Proof of Concept
Vitest plan (mock HTTP only):
1. Mock `HotBridge.estimateWithdrawalFee`/HOT SDK HTTP calls to be bypassed by supplying `args.feeEstimation` directly to `processWithdrawal` with `{ amount: 999_999n, underlyingFees: { [RouteEnum.HotBridge]: { relayerFee: 1n, blockNumber: 1n } }, quote: null }`.
2. Call `sdk.processWithdrawal({ withdrawalParams: { assetId: "nep245:v2_1.omni.hot.tg:137_...", amount: 1n, feeInclusive: true, destinationAddress: <valid EVM address> }, feeEstimation })`.
3. Assert that `createWithdrawalIntents` does NOT throw `FeeExceedsAmountError` (bug present) even though `1n <= 999_999n`.
4. Parse the produced `mt_withdraw` intent and assert `BigInt(intent.amount) !== amount - (feeInclusive ? feeEstimation.amount : 0n)` (i.e. `1n - 999_999n + 1n = -999_997n`, a negative amount reaching the signed intent), proving the equality `sum(debits) == amount + (feeInclusive?0:fee)` is broken before signing.
