### Title
Webhook `shop` identity is taken from an unauthenticated header and is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity solely via `Utils::HmacValidator.validate(request)`, whose signable content is `@raw_body` only [1](#0-0) . The `shop` identity that the gem hands to the application's webhook handler, however, is read directly and unverified from the `x-shopify-shop-domain` HTTP header [2](#0-1) . Because the header is not part of the HMAC-signed bytes, the binding `hmac_signed_body == shop_the_body_belongs_to` never actually holds — the gem only proves "the body was signed with the app's client secret," not "this body originated from the shop named in the header."

### Finding Description
This mirrors the report's bug class: a value that drives security-relevant logic (`_minutesPassedSinceLastFeeOp`/`lastFeeOperationTime`, un-synchronized with the decay computation) is derived from data that is not itself validated end-to-end, causing the effective binding to diverge from the intended one. Here, the analogous identity binding is:

`request.shop` (used to attribute a webhook event to a tenant) **should equal** the shop that produced/authorized `request.to_signable_string` (the raw body actually covered by the HMAC).

In `Registry.process`, the flow is:
1. `Utils::HmacValidator.validate(request)` is checked — this only verifies that `raw_body` was signed with `Context.api_secret_key` (or `old_api_secret_key`) [3](#0-2) .
2. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [4](#0-3) .

`request.shop` comes straight from `shopify_header("shop-domain")` [2](#0-1) , and `to_signable_string` never includes any header, only `@raw_body` [1](#0-0) . Since a single app-wide `api_secret_key` is used for HMAC validation across **all** installed shops (there is no per-shop signing key in `HmacValidator`) [5](#0-4) , any tenant that has legitimately received one authentic, HMAC-valid webhook payload for their own shop can resubmit that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds (it never looks at the header), and the gem hands the application a `WebhookMetadata` claiming the victim shop's identity while carrying the attacker's chosen body content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: the "authenticated" shop identity handed to the host application's handler is not actually bound to the signed payload. Any application logic that trusts `WebhookMetadata#shop` (e.g., to select which shop's session/access token/database record to update, per the intended usage pattern in `docs/usage/webhooks.md`) can be tricked into associating attacker-controlled webhook body content with an arbitrary other shop, i.e. cross-tenant data injection/confusion — one of the explicitly in-scope Critical categories ("cross-tenant access").

### Likelihood Explanation
Exploitation requires only the capability of an unprivileged internet user who can install the app on their own shop (or otherwise trigger any webhook topic for their own shop) — no access token, `client_secret`, or privileged access is required. They capture one legitimate raw body + `X-Shopify-Hmac-Sha256` pair for their own shop and replay it with a forged `X-Shopify-Shop-Domain` header value. Because the HMAC secret is shared across all merchants and the signable content excludes headers entirely, this bypass is deterministic, not probabilistic — unlike the original rounding bug, there's no timing race needed here.

### Recommendation
Do not treat `x-shopify-shop-domain` as trusted metadata independent of the signed payload. Either:
- Include the shop domain (and topic) in the HMAC-signed material, or
- Cross-check `request.shop` against a shop identity embedded in `parsed_body` (if Shopify includes one) or against the webhook subscription's expected shop, or
- At minimum, clearly document in `WebhookMetadata`/`Request` that `shop` is unauthenticated header data and must be independently verified/looked up by the host app before being trusted for tenant attribution, and provide a validated alternative.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), receiving a real Shopify-delivered request with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body using the app's single `client_secret`.
2. Attacker replays this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — unaffected by the header change — and passes [3](#0-2) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's body content [4](#0-3) , causing the application to process/store attacker-controlled data under the victim shop's identity.
