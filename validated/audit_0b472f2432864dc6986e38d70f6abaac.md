### Title
Webhook `shop-domain` (and `topic`) headers are trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value taken from an unauthenticated header. The binding "HMAC-verified bytes == the shop the payload is attributed to" does not hold, allowing a payload legitimately signed for one shop to be replayed and attributed to a different shop.

### Finding Description
`Webhooks::Registry.process` verifies authenticity with: [1](#0-0) 

The only value covered by the HMAC is the raw request body, as defined by `Request#to_signable_string`: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers via `shopify_header`, none of which are included in `to_signable_string`, and thus none are covered by `HmacValidator.validate`: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) using the app's single, shop-independent `api_secret_key`: [5](#0-4) 

After validation succeeds, `Registry.process` forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which is the tenant-identifying value the host application uses to route/act on the payload: [6](#0-5) [7](#0-6) 

Because the same `api_secret_key` is used to sign webhooks for *every* shop installed on a given app, an unprivileged user who installs the app on their own (attacker-controlled) shop `A` can capture a genuine, validly-signed webhook `(raw_body, hmac)` pair that Shopify sent for shop `A`. The attacker then replays that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but substitutes the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a victim shop `B`'s domain. `HmacValidator.validate` still succeeds (the body and secret are unchanged), so `Registry.process` calls the handler with `WebhookMetadata.shop == "B"` even though the payload content was never produced for, or authorized by, shop `B`. Equality that should hold: `hmac_covers(shop) == true`; in reality `hmac_covers(shop) == false`, so `authenticated(body) != authenticated(shop, body)`.

### Impact Explanation
This breaks the tenant boundary the whole webhook system relies on: the host application trusts `data.shop` from `WebhookMetadata` to decide which merchant record to update, which access token/session to use, or which tenant's data to mutate. An attacker who is merely an install of the app (no special privilege, no access to the victim's credentials) can inject forged/misattributed webhook events into another tenant's processing path, i.e., cross-tenant access/confusion driven entirely by a header value the gem never authenticates. This is a Critical-class cross-tenant issue per the given impact bar.

### Likelihood Explanation
Likelihood is High: the attacker only needs to install the app on their own shop (a normal, unprivileged action), capture one webhook delivery for a topic they intend to spoof, and replay it with a modified header value to the app's public webhook endpoint. No secret, token, or privileged access is required — the `api_secret_key` never needs to be known to the attacker since Shopify itself signs the captured payload.

### Recommendation
Bind the `shop` (and other identifying headers) into the HMAC-covered material — e.g., include the `shop-domain` header in the value that `to_signable_string` returns, or otherwise cryptographically bind it to the payload — so a payload/signature pair legitimately produced for shop `A` cannot be replayed and attributed to shop `B`.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; register a webhook handler for topic `orders/create`.
2. Shopify sends a webhook: body `raw_body`, header `X-Shopify-Hmac-Sha256: hmac(raw_body, api_secret_key)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(raw_body, hmac)` and POSTs it again to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged header; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the (unchanged) HMAC.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: raw_body, ...)`, and the host application acts on `victim`'s tenant using attacker-supplied body content.
