Based on the investigation, I found a genuine analog vulnerability in the Tron deployment of the IntentGateway contract, which diverges from the safer pattern used in the canonical EVM contracts.

### Title
Unsafe low-level `.call()` for ERC20 transfers in `withdraw()`/`onAccept()` permanently freezes escrowed order and dust funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` finalizes escrow accounting (`_orders[...] -= amount`, `_filled[commitment] = beneficiary`) and emits success events based solely on the boolean *call-success* of a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, rather than using `SafeERC20.safeTransfer` as the canonical EVM contract does [1](#0-0) . Unlike a revert-based failure, a legacy/non-standard ERC20 that returns `false` on failure (instead of reverting) will make `success == true` even though no tokens were moved, causing the gateway to treat the withdrawal as complete while the beneficiary receives nothing.

### Finding Description
`withdraw()` handles both cross-chain `RedeemEscrow`/`RefundEscrow` settlement and same-chain `cancelOrder` refunds. For each escrowed token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

This only checks that the low-level call itself did not revert — it never inspects the ABI-decoded boolean return value from `transfer()`. Many legacy/non-compliant ERC20 tokens (and any malicious or non-standard token an order-placer chooses as an input) return `false` on failed transfers rather than reverting, and a call to a token that doesn't implement the function at all can also return `success == true` with empty returndata. The same unchecked pattern is repeated for the transaction-fee payout [2](#0-1)  and for `SweepDust` payouts in `onAccept()` [3](#0-2) .

Contrast this with the canonical EVM `IntentsBase.sol`, whose `_withdraw()` correctly uses `SafeERC20.safeTransfer`, which reverts on a `false` return: [4](#0-3) . The Tron contract imports `SafeERC20` (`using SafeERC20 for IERC20;`) but never applies it to these transfers, indicating the safe-transfer fix present upstream was not carried over to this port.

Additionally, `_filled[body.commitment]` is set unconditionally at the top of `withdraw()` before the token loop [5](#0-4) , so once `withdraw()` runs to completion (which it does even when a transfer silently fails), the order is irreversibly marked filled/cancelled and its escrow decremented — with no remaining code path to retry or reclaim the funds.

### Impact Explanation
Because `_orders[commitment][token]` is decremented and `_filled[commitment]` is set even when the underlying `transfer()` silently failed, the escrowed input tokens (and/or transaction fees) become permanently locked in the contract: they are no longer withdrawable through `withdraw()` (the order is already marked filled/refunded and its accounted balance is now zero), and the intended beneficiary/solver never receives them. This is a permanent freezing-of-funds condition reachable by any user simply escrowing a non-standard ERC20 token as an order input and calling `cancelOrder`, or by a solver being paid out through a settlement message referencing such a token.

### Likelihood Explanation
Any order participant chooses the input token when placing an order (`placeOrder`), so a user (or an attacker crafting an order for another party) can supply a non-reverting-on-failure ERC20 as an input, then trigger `cancelOrder` (same-chain) or wait for the cross-chain settlement `RedeemEscrow`/`RefundEscrow` message to hit `withdraw()`. No privileged access is required; the flow is reachable from ordinary `placeOrder`/`cancelOrder` calls, which are exactly the analog dispatch/relay paths in scope.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` transfers in `withdraw()`, the transaction-fee payout, and the `SweepDust` handler in `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)` using the already-imported `SafeERC20` library, matching the canonical `IntentsBase.sol` implementation. This ensures a `false` return value causes a revert rather than being misinterpreted as success, preventing the accounting state from advancing past a failed transfer.

### Proof of Concept
1. Deploy a non-standard ERC20 token whose `transfer()` returns `false` on failure instead of reverting (or simply always returns `false` while emitting no state change).
2. Call `placeOrder` on the Tron `IntentGatewayV2`, escrowing this token as `order.inputs[0]`, with `order.destination == order.source` (same-chain).
3. Call `cancelOrder(order, options)` as the order owner. Internally this invokes `withdraw(body, true)`:
   - `_filled[commitment] = beneficiary` is set.
   - `token.call(transfer(beneficiary, amount))` returns `success = true` with `false` payload (transfer silently failed).
   - `_orders[commitment][token] -= amount` proceeds, zeroing the escrow record.
   - `EscrowRefunded` is emitted.
4. The beneficiary's token balance is unchanged (no tokens received), yet the order is now permanently marked filled/cancelled with zero remaining escrow — the tokens are stuck in the contract with no code path to recover them.
