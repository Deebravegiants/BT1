### Title
Webhook `shop` tenant identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw request body only, while the `shop` (tenant) identity that `Registry.process` hands to the app's webhook handler is read from an unauthenticated HTTP header. The HMAC check therefore proves only that *some* payload was signed with the app's secret; it proves nothing about which shop that payload belongs to. This is the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" identity-binding break analogous to the Predy `slot0`-vs-action mismatch: one data source is checked (the body bytes), while a different, unchecked data source (the `shop-domain` header) is what the code actually acts on to attribute the webhook to a tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers with no cryptographic binding to the body or to the HMAC at all: [2](#0-1) 

`Registry.process` validates the HMAC purely over `request` (i.e., over `raw_body`), and then immediately trusts `request.shop` — the unauthenticated header value — as the tenant identity passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — the `shop` header plays no role in the signature computation or verification: [4](#0-3) 

The binding that should hold is:
`shop_used_for_tenant_attribution == shop_that_the_HMAC_actually_authenticates`

But in reality:
`shop_used_for_tenant_attribution (header, unauthenticated) ≠ shop_covered_by_HMAC (none — HMAC covers only raw_body)`

Because the `api_secret_key` used to compute the webhook HMAC is a single shared secret for the whole app (not shop-specific), any legitimate but unprivileged merchant using a multi-tenant app can trigger a real, validly-signed webhook for their *own* shop (e.g., by creating an order), capture that `(raw_body, hmac)` pair, and then replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `Registry.process` will accept it as valid (the HMAC still matches the unmodified body) and will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, causing the webhook body to be attributed and acted upon under the wrong tenant.

### Impact Explanation
This breaks the tenant-isolation boundary between shops installed on the same multi-tenant app: an attacker-controlled `shop` value can be smuggled past HMAC verification and delivered to app code as if it were an authenticated fact, leading to cross-tenant data confusion/injection (e.g., an app that upserts records keyed by `data.shop` could write attacker-supplied order/product data into a victim shop's records). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, unprivileged tenant of the same multi-tenant app (able to trigger events on their own store to obtain a validly-signed webhook body) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a modified header — no access to `api_secret_key`, access tokens, or any privileged credential is needed, satisfying the "unprivileged internet user" constraint.

### Recommendation
Bind the tenant identity into the signed payload verification path rather than trusting the header in isolation:
- Cross-check `request.shop` against the shop associated with the registered webhook/session that the app expects for that endpoint/topic before acting on the payload, or
- Require the host application to independently verify that `data.shop` in `WebhookMetadata` corresponds to a shop actually known/authorized for the app instance, documenting this explicitly since the gem cannot itself bind the header into Shopify's HMAC scheme (Shopify signs only the body).

### Proof of Concept
1. App "SaaSApp" is installed by both Merchant A (attacker) and Merchant B (victim), sharing one `api_secret_key`.
2. Merchant A triggers an event (e.g. creates an order) in their own shop, causing Shopify to POST a webhook to `SaaSApp`'s public endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the shared secret.
3. Attacker intercepts/replicates this `(raw_body, hmac)` pair (e.g. via a proxy they control on their own infra path, or by re-registering their own webhook to a URL they own to capture it) and re-POSTs it directly to `SaaSApp`'s webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified) hmac: [3](#0-2) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's order payload, and processes/stores it as if it belonged to the victim shop.
