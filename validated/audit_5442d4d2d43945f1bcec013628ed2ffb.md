### Title
Webhook `shop` identity is not covered by the HMAC signature, letting an attacker relabel a validly-signed webhook to a victim shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, but the gem's HMAC validation only signs the raw request body, never the headers. The gem itself trusts and forwards this unauthenticated `shop` value to the app's webhook handler as the tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only ever operate on `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `Request#shop` is read directly from a header that participates in no cryptographic verification at all: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and constant-time compares it to `verifiable_query.hmac` — again, only the body bytes are covered: [4](#0-3) 

`Registry.process` treats a passing HMAC check as proof of full request authenticity, then hands the caller-supplied, unauthenticated `request.shop` straight to the handler as the tenant identity for that payload: [5](#0-4) 

The identity binding that should hold is:
`HMAC-verified(raw_body)` == `shop that raw_body actually originated from`

But the code only proves `HMAC-verified(raw_body)`; it never proves that `shop` (header) corresponds to the shop whose data is in `raw_body`. Because `shop` is a bare header value with no signature coverage, any party capable of replaying a validly-signed body (e.g., a merchant who legitimately installed the app and receives genuine, correctly-signed webhooks for their own shop) can resend the exact same `raw_body` + `hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a different (victim) shop. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` passes the attacker-chosen `shop` on to `WebhookHandler#handle` inside `WebhookMetadata`: [6](#0-5) 

Any host application that relies on this gem's guarantee ("if `Registry.process` doesn't raise, this data came from `shop`") to key sessions, storage rows, or subsequent Admin API calls by `data.shop` will process/store attacker-controlled data under an arbitrary victim shop's tenant identity — a cross-tenant confusion introduced entirely within this gem's own verification and dispatch logic, not by an ignored API contract.

### Impact Explanation
This breaks the tenant/shop identity binding that the gem is supposed to provide via HMAC verification before invoking `WebhookHandler#handle`. A successful exploitation lets an attacker inject data attributed to (or trigger processing keyed on) a shop they do not control, i.e., cross-tenant access — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
The attacker only needs their own genuine, correctly-signed webhook deliveries (trivially obtainable by installing the app on any shop they control) and the ability to POST to the app's public webhook endpoint with modified headers — no access token, `client_secret`, or privileged account is required. This is a realistic, low-effort replay requiring only unprivileged internet access to the webhook endpoint.

### Recommendation
Bind the `shop` identity into the value that is actually verified: either include the shop domain in the HMAC-signed material (not possible unilaterally since Shopify controls the outbound signature), or — within the gem — require callers to supply the expected shop out-of-band (e.g., match `request.shop` against the shop of the `Auth::Session` used to register the webhook) rather than trusting the header value alone as an authenticated fact. At minimum, `Registry.process`/`WebhookMetadata` documentation and API should make explicit that `shop` is unauthenticated and must be independently corroborated by the caller before being used as a tenant/session key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, and a valid `shopify-hmac-sha256` computed over `B` with the app's real secret (attacker never sees the secret, only the resulting signature).
2. Attacker resends the identical body `B` and identical `hmac` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `hmac`, `shop = "victim-shop.myshopify.com"`, `to_signable_string = B`. [7](#0-6) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares against the supplied `hmac` — it matches because `B` and `hmac` are the genuine unmodified pair.
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, so the app processes attacker's payload `B` under the victim's tenant identity, with no error raised anywhere in the gem.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
