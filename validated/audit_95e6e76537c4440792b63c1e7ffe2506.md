This confirms the vulnerability. The docs explicitly state that `Registry.process` "will verify the request did indeed come from Shopify" — implying the `shop` field is trustworthy — but the HMAC only covers the raw body.

### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop-domain` header from the HMAC-signed data. `Registry.process` validates the HMAC over the body alone and then passes the unauthenticated `shop` header value straight to the app's webhook handler. Since the HMAC secret (`api_secret_key`) is shared across all shops that install the same app, any unprivileged user who installs the app on their own store can capture a validly-signed webhook and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, producing a request that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`Request#to_signable_string` only returns the raw body: `@raw_body`, so `shop` (from `shop-domain`) is never part of the bytes verified by `Utils::HmacValidator`. [1](#0-0) 

`Registry.process` verifies only the HMAC of the request and then forwards `request.shop` (an unauthenticated header) into `WebhookMetadata`, which app code uses to attribute the event to a shop/session: [2](#0-1) 

`HmacValidator.validate` compares `verifiable_query.hmac` against a signature computed only over `verifiable_query.to_signable_string`: [3](#0-2) 

The identity binding that should hold is: `shop_header == shop_bound_by_hmac`. In this gem, the HMAC binds only the body bytes, so `shop_header` is never bound to the signature at all — it is a completely attacker-controllable field even on a genuinely-signed request. Because `api_secret_key` is identical for every shop that installs a given app (it is the app's own secret, not per-shop), an attacker who installs the app on their own shop legitimately receives real webhooks with valid HMACs computed under that same secret. Capturing one such `(raw_body, hmac)` pair, the attacker can send that same body/HMAC pair to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with an arbitrary victim `myshopify.com` domain. `Registry.process` will accept it, because HMAC validation only checks the body, and will invoke the app's handler with `WebhookMetadata#shop` set to the forged victim domain.

### Impact Explanation
Downstream apps rely on `WebhookMetadata#shop` (as documented in `docs/usage/webhooks.md`, "The shop domain of the webhook") to key their session/store lookups, exactly the "shop authenticated versus shop stored as a session key" pattern called out as in scope. Since the gem provides no other authenticated binding of the request to a shop, an app that follows the gem's documented usage will process attacker-supplied data/side effects under a victim shop's identity — i.e., cross-tenant access/confusion, without needing the victim's credentials, TLS interception, or leaked secrets. This qualifies as Critical (cross-tenant access) per the given impact categories.

### Likelihood Explanation
Any internet user can become an "attacker" here simply by installing the target Shopify app on their own free/dev store — no special privilege beyond normal app installation is required. Capturing their own valid webhook (from their own inbox — nothing secret about it once delivered to them) and replaying it with a modified shop header is a low-effort, purely network-level manipulation. The only limiting factor is that the forged webhook's body content will be whatever data the attacker's own shop naturally generates (attacker doesn't control victim's product/order data), but for many webhook topics (e.g., `app/uninstalled`, `shop/update`, `customers/data_request`) even attacker-originated but victim-attributed data is high-impact (e.g., forged uninstall/GDPR-erasure events, or state confusion) for apps that trust `data.shop`.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the HMAC-verified material, or otherwise cryptographically tie the header-derived `shop` to the signed body — e.g., by having `to_signable_string` include the normalized `shop-domain`, `topic`, and `webhook-id` headers alongside the raw body, and documenting that hosts must not trust `data.shop` unless it is part of the verified signature. At minimum, update documentation to make clear that `shop` in `WebhookMetadata` is not covered by the HMAC and must be independently corroborated (e.g., checked against a known/installed shop list) before being used as a session/tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`. The app's Shopify Partner-configured `api_secret_key` is shared across all shop installations.
2. Trigger any webhook topic the app subscribes to (e.g. update a product) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Resend the same `POST {body: B}` to the app's webhook endpoint, keeping `X-Shopify-Hmac-Sha256: H` and `X-Shopify-Topic` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` returns only `B` (see `lib/shopify_api/webhooks/request.rb:36-38`), and the shop-domain header was never part of what was hashed.
5. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, causing the host app to process attacker data (or trigger side effects) attributed to the victim tenant.
