## Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then dispatches to the app's handler using these unauthenticated header values, so the "shop that is cryptographically bound to this payload" and "the shop the app acts on" are not the same value.

### Finding Description
`Request#hmac`/`to_signable_string` compute the signable content solely from `@raw_body`: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates only that signable string (the body) against the HMAC, then immediately trusts the unauthenticated `request.topic` and `request.shop` to route and populate the data handed to the app's business logic: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`Utils::HmacValidator.validate` confirms `Digest.hexencode(HMAC-SHA256(secret, raw_body))` matches the `X-Shopify-Hmac-Sha256` header value, but it never touches `shop`, `topic`, or `webhook_id`: [4](#0-3) 

This is the exact analog of the report's "weight vs. deposited synth" mismatch: the value that is checked (the body signature) is disjoint from the value that is acted upon (`shop`, `topic`). Equality that should hold — `shop bound by HMAC == shop the handler acts on` — is broken: the gem only guarantees `hmac_valid(body) == true`, not `hmac_signed_for(shop_header) == shop_header`.

### Impact Explanation
Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — e.g. by installing the app on their own shop and receiving a legitimately delivered webhook — can replay that exact body to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a different, victim shop. `Registry.process` will accept it (the body HMAC still validates) and hand the app's handler a `WebhookMetadata` claiming the payload originated from the victim shop/topic. Any app logic that keys per-tenant side effects (order/customer records, inventory updates, uninstall/GDPR handling, billing state, etc.) off `WebhookMetadata#shop` can be tricked into acting on/against a shop the attacker does not control — a cross-tenant integrity break rooted entirely in this gem's `Webhooks::Request`/`Registry` design.

### Likelihood Explanation
Moderate: it requires the attacker to possess at least one genuine `(body, hmac)` pair for the target app (trivially obtainable by installing the app on the attacker's own store and triggering any webhook, e.g. `app/uninstalled` or `orders/create`), plus network access to POST directly to the app's public webhook route with custom headers — both are unprivileged-internet-user actions with no need for `api_secret_key`, tokens, or TLS interception.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable content, or otherwise cryptographically bind them (e.g., re-derive/verify `shop` from a store lookup keyed by an authenticated identifier, not from a bare header) before passing them into `WebhookMetadata`. At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be trusted for authorization decisions without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimately delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid since `H = HMAC-SHA256(secret, B)`).
2. Attacker POSTs to the app's public webhook endpoint with the same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to execute tenant-scoped logic under the victim's identity despite the payload never having been authenticated for that shop.
