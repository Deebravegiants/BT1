### Title
Malicious beneficiary can permanently block escrow settlement/refund delivery via atomic `withdraw()` revert - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.onAccept` routes both `RedeemEscrow` and `RefundEscrow` cross-chain messages into a single internal `withdraw()` function that atomically transfers every escrowed token to a `beneficiary` address decoded from the message body [1](#0-0) . If the beneficiary is a contract that rejects the native-token transfer (or if any single ERC-20 in the token list reverts/returns false, e.g. a blacklist-capable token), the whole `withdraw()` call reverts and none of the escrowed tokens or accumulated fees are released [2](#0-1) . This mirrors the KimNFTMarketplace pattern: an unprivileged counterparty can weaponize a mandatory callback/transfer inside an atomic settlement step to grief the other party, and here there is no escrow-and-later-claim fallback, so the message can never be successfully delivered.

### Finding Description
`withdraw()` is the only path that finalizes settlement for both the happy-path (`RedeemEscrow`, releasing escrow to a solver/beneficiary) and the cancellation path (`RefundEscrow`, refunding the original user). It sets `_filled[body.commitment] = beneficiary` and then, in a loop, performs either a raw ETH `.call` or an ERC-20 `transfer` to that same fixed `beneficiary` for every token in the request, reverting the entire transaction with `InsufficientNativeToken()` or `TransferFailed()` on the first failure [3](#0-2) . Because the whole call — including the state write to `_filled` — is rolled back on any single failing leg, there is no partial success and no alternate "claim later" function exposed to let the funds be retrieved once the transfer fails, exactly the gap flagged in the KimNFTMarketplace report before its fix. The `beneficiary` value comes from message fields that are attacker-influenced in practice (e.g. `msg.sender` at fill time, or the order's declared beneficiary/output recipient), so a party who controls that address — a native-ETH-rejecting contract, or a token with blacklist/pausable transfer hooks — can deterministically make every future delivery attempt for that commitment fail.

### Impact Explanation
Since the ISMP relayer delivers the `RedeemEscrow`/`RefundEscrow` message by invoking `onAccept`, and every invocation for the same commitment hits the identical failing transfer, the message becomes permanently undeliverable — the escrowed input tokens for that order commitment can never be released to anyone, either as a fill payout or as a cancellation refund. This is a permanent freezing of escrowed funds and a message route that cannot deliver, satisfying the "route unable to deliver messages" / "permanent freezing of funds" impact classes.

### Likelihood Explanation
Any user who can become the `beneficiary` of a `WithdrawalRequest` (by filling their own order, or by controlling the destination beneficiary address of an order) can deploy a trivial contract that reverts on `receive()`, or select/interact with an ERC-20 that can later blacklist that address — no special privilege beyond normal protocol usage (placing/filling an order) is required, making this reachable from a single unprivileged transaction/relayed message.

### Recommendation
Decouple the atomicity of multi-token/native settlement from success of any individual transfer: on a failed transfer to `beneficiary`, keep the token escrowed (do not revert the whole `withdraw()`), mark that specific leg as pending, and finalize the other legs; expose a separate public "claim" function that the beneficiary (or, after a timeout, the counterparty) can call later to retry or redirect the stuck leg, analogous to the Cantina-recommended fix of protecting the non-griefing party while leaving a claimable escrow for the griefing party's leg.

### Proof of Concept
1. Attacker deploys `EvilBeneficiary` with no `receive()`/`fallback()` (or one that always reverts).
2. Attacker places/fills an order such that `WithdrawalRequest.beneficiary` resolves to `EvilBeneficiary` (e.g., as `msg.sender` filling a cross-chain order, or as the destination beneficiary in the order they crafted).
3. Relayer submits the proof and the host calls `IntentGatewayV2.onAccept` with `RequestKind.RedeemEscrow`/`RefundEscrow`, which calls `withdraw()`.
4. The native-token `.call{value: amount}("")` to `EvilBeneficiary` returns `false`; `withdraw()` reverts with `InsufficientNativeToken()`, rolling back `_filled[commitment]` as well.
5. Every subsequent relayer attempt to deliver the same message hits the identical revert — the escrowed inputs for that commitment are permanently stuck with no available recovery function.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {

            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }
