### Title
`findMatchingWithdrawal` matches by `assetId` only, causing status/txHash cross-contamination between two same-asset withdrawals batched in one intent - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` queries the POA bridge status API by `tx.hash` (shared by every withdrawal in a batch intent) and then picks a match with `findMatchingWithdrawal`, which selects the first withdrawal whose `near_token_id` equals the requested `assetId`, ignoring `destinationAddress` and the `WithdrawalIdentifier.index`. When an integrator batches two withdrawals of the same token but to different `destinationAddress`es into a single signed intent, both `describeWithdrawal` calls resolve to the same underlying record, so one attacker-controlled, already-completed withdrawal's `transfer_tx_hash` can be reported as the completion of a different (victim) withdrawal.

### Finding Description
The broken equality: `describeWithdrawal(widᵢ).status/txHash` should equal the on-chain outcome for `widᵢ.withdrawalParams.destinationAddress`, for each `i` in a batch. It does not, because:

- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns each withdrawal a `WithdrawalIdentifier` with the same `tx` (the shared settled `NearTxInfo` of the whole intent) and a per-route `index`, but `index` is never used for matching against the API response.
- `describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) queries `getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` — identical for every withdrawal in the batch — then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`, matching solely on `assetId`. The code's own comment explicitly acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" — but this is a code-comment acknowledgment, not a runtime guard; nothing in `supports()`, `validateWithdrawal()`, `createWithdrawalIntents()`, or `createWithdrawalIdentifiers()` prevents an integrator from batching two same-asset withdrawals with different `destinationAddress`.
- Batch withdrawals of multiple tokens in one intent are a documented, first-class SDK feature (`packages/intents-sdk/README.md`, "Batch Withdrawals" section; `sdk.processWithdrawal`/`sdk.signAndSendWithdrawalIntent` accept `WithdrawalParams[]`). An integrator that batches requests from two different end-users happening to withdraw the same `assetId` (attacker + victim) in one intent hits this gap. The attacker only needs to supply `assetId` and `destinationAddress`, both ordinary user-controlled inputs forwarded by the integrator.

Exploit flow: integrator batches `[attackerParams(assetId=X, dest=attacker), victimParams(assetId=X, dest=victim)]` into one signed intent/tx. Once the bridge processes both withdrawals, `getWithdrawalStatus` returns a list containing (at least) the attacker's COMPLETED withdrawal for `assetId=X`. Calling `describeWithdrawal` for the victim's `WithdrawalIdentifier` (same `tx.hash`, same `assetId`) returns `{status: "completed", txHash: attacker's transfer_tx_hash}` — identical to what is returned for the attacker's own identifier — even though the victim's real payout may still be pending or has gone to `destinationAddress` victim on a different transaction.

### Impact Explanation
This is a status/txHash misreport: an integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` for per-withdrawal completion tracking (see `docs/design/rfc-batch-withdrawal-granular-control.md`) can mark the victim's withdrawal as completed using a `transfer_tx_hash` that actually paid the attacker, potentially causing the integrator to release credit, mark an obligation settled, or stop retry/alerting for the victim while the victim's real funds are unaccounted for. This matches the "High" category: "a status or hash misreport making an integrator credit or refund twice." It is repeatable any time two same-asset withdrawals with different destinations land in the same settled intent/tx.

### Likelihood Explanation
Preconditions: an integrator must batch multiple withdrawals into a single intent, and among the batch at least two withdrawals must target the same POA-bridge `assetId` with different `destinationAddress`. The attacker's cost is just submitting a normal withdrawal request for a token that a legitimate concurrent user is also withdrawing, relying on the integrator's batching logic to combine them — feasible for any integrator that batches multiple end-users' requests per token/window for gas efficiency, a pattern the SDK explicitly supports and documents. No privileged access, no malicious relayer/RPC, and no misuse of an undocumented escape hatch is required — batching itself is a first-class documented feature; the flaw is the lack of any per-withdrawal disambiguation in the status lookup.

### Recommendation
Disambiguate withdrawals of the same asset within one settled tx before falling back to assetId-only matching, e.g. by also checking `destinationAddress`/`destinationMemo` against `withdrawal.data` fields (if the API exposes recipient info), or by enforcing that `createWithdrawalIdentifiers`/`signAndSendWithdrawalIntent` reject batches containing multiple POA withdrawals of the same `assetId` until the POA bridge API supports disambiguation, or implement the amount-based sorting/matching strategy already suggested in the code's own comment (sort both API results and requested withdrawals by amount, since same-token relayer fees are equal so relative amount ordering is preserved).

### Proof of Concept
```ts
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts (new test)
import { describe, it, expect, vi } from "vitest";
import { poaBridge } from "@defuse-protocol/internal-utils";
import { PoaBridge } from "./poa-bridge";

describe("PoaBridge.describeWithdrawal - assetId-only matching cross-contamination", () => {
  it("returns attacker's completed txHash for victim's still-pending withdrawal of the same assetId", async () => {
    const sharedTx = { hash: "shared-intent-tx-hash", accountId: "relayer.near" };
    const assetId = "nep141:btc.omft.near";

    vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
      withdrawals: [
        {
          status: "COMPLETED",
          data: {
            near_token_id: "btc.omft.near",
            transfer_tx_hash: "ATTACKER_TX_HASH",
            // recipient/destination not checked by findMatchingWithdrawal
          },
        },
      ],
    } as any);

    const bridge = new PoaBridge({ envConfig: /* ... */ {} as any, xrplRpcUrls: [] });

    const attackerWid = {
      landingChain: "bitcoin",
      index: 0,
      withdrawalParams: { assetId, amount: 1n, destinationAddress: "attackerBtcAddr" } as any,
      tx: sharedTx,
    };
    const victimWid = {
      landingChain: "bitcoin",
      index: 1,
      withdrawalParams: { assetId, amount: 1n, destinationAddress: "victimBtcAddr" } as any,
      tx: sharedTx,
    };

    const attackerResult = await bridge.describeWithdrawal(attackerWid as any);
    const victimResult = await bridge.describeWithdrawal(victimWid as any);

    // BROKEN EQUALITY: victim's outcome should differ from attacker's,
    // but both resolve to the SAME completed txHash.
    expect(attackerResult).toEqual({ status: "completed", txHash: "ATTACKER_TX_HASH" });
    expect(victimResult).toEqual({ status: "completed", txHash: "ATTACKER_TX_HASH" }); // demonstrates the bug
  });
});
```
This mocks only the HTTP layer (`poaBridge.httpClient.getWithdrawalStatus`) and demonstrates that `describeWithdrawal` cannot distinguish the two `WithdrawalIdentifier`s (different `destinationAddress`, same `assetId`, same `tx.hash`), returning identical completed status/txHash for both.
