The claim is fully verified against the actual code. `Authorize` performs the JWT verification, then `h.jwtCache.isReplay(claims.ID)` check, then workflow/key lookup, and only calls `h.jwtCache.recordUsage(claims.ID)` at the very end — right before returning success [1](#0-0) . The `jwtReplayCache` itself implements `isReplay` and `recordUsage` as two separately-locked operations (`RLock`/`RUnlock` for the read, then a distinct `Lock`/`Unlock` for the write), rather than a single atomic check-and-set [2](#0-1) . This creates a genuine TOCTOU race: two concurrent calls to `Authorize` with the same `jti` can both pass `isReplay` before either reaches `recordUsage`.

This function is directly reachable from `httpTriggerHandler.authorizeRequest`, which is invoked when an unprivileged external caller sends an HTTP-trigger workflow-execute request to the gateway [3](#0-2) . No additional check elsewhere (rate limiting, org resolution, etc.) closes this race — `checkRateLimit` is a separate, independent limiter unrelated to JWT single-use enforcement [4](#0-3) .

The report's cited correct pattern also checks out: `RequestReplayGuard.CheckAndRecord` in the Vault package holds a single mutex across both the "check" and "record" steps, demonstrating the atomic pattern that `jwtReplayCache` fails to implement [5](#0-4) .

This satisfies all validation checks: precise in-scope code references, a clear root cause (non-atomic check-then-act instead of atomic check-and-set), a reachable exploit path from an unprivileged HTTP-trigger caller, and a concrete in-scope impact (unauthorized duplicate workflow execution from a single-use credential, i.e., an authentication/replay bypass leading to unauthorized job runs).

Audit Report

## Title
JWT Replay-Protection Race Condition Allows Reuse of a Single-Use Workflow-Trigger Token - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` checks `jwtCache.isReplay(jti)` and only calls `jwtCache.recordUsage(jti)` at the very end of the function, well after JWT verification and authorization lookups complete. Because `isReplay` and `recordUsage` are implemented as two independently-locked operations in `jwtReplayCache` rather than one atomic check-and-set, concurrent requests bearing the identical single-use JWT can both pass the replay check before either records usage, allowing the token to authorize more than one workflow execution.

## Finding Description
`Authorize` verifies the JWT, calls `h.jwtCache.isReplay(claims.ID)` to reject reused tokens, performs workflow/signer lookups, and only afterward calls `h.jwtCache.recordUsage(claims.ID)` right before returning success. The `jwtReplayCache.isReplay` method takes an `RLock`, reads, and releases; `recordUsage` acquires a separate `Lock` later. There is no shared critical section spanning both the check and the write, so two goroutines invoking `Authorize` with the same `jti` concurrently can both observe `isReplay == false` before either calls `recordUsage`, and both will pass authorization. This function is reachable directly from `httpTriggerHandler.authorizeRequest`, which handles unprivileged HTTP-trigger workflow-execute requests at the gateway boundary, so no existing middleware or rate limiter intercepts or serializes this check.

## Impact Explanation
A JWT designed as a single-use credential for triggering one workflow execution can be replayed by sending it twice in parallel, resulting in duplicate/unauthorized workflow executions from a single authorization grant. This falls under unauthorized job run / node API authentication bypass since the single-use guarantee that downstream billing/rate-limiting/deduplication logic relies on is broken.

## Likelihood Explanation
Exploitation only requires an unprivileged caller who already possesses one valid signed JWT to send the same token via two near-simultaneous HTTP requests — no special privilege, node compromise, or other access is required. The race window (spanning JWT verification plus workflow/key lookups) is narrow but real and requires no unusual timing tricks beyond ordinary concurrent HTTP requests, making it a practically exploitable, if not 100%-reliable-on-every-attempt, race condition.

## Recommendation
Make the check-and-record operation atomic by adding a combined method, e.g. `CheckAndRecord(jti string) bool`, that holds a single write lock across both the existence check and the insertion into `cache.cache`, mirroring the already-correct pattern in `RequestReplayGuard.CheckAndRecord` (`core/capabilities/vault/request_replay_guard.go`). Update `Authorize` to call this combined method once instead of separate `isReplay`/`recordUsage` calls, ideally performed immediately after JWT signature verification.

## Proof of Concept
1. Register a workflow and an authorized signer key as in `TestWorkflowMetadataHandler_Authorize`.
2. Create one JWT for an `HTTPTriggerRequest`/`MethodWorkflowExecute` request signed by the authorized key.
3. From two goroutines, concurrently call `handler.Authorize(workflowID, tokenString, req)` with the identical token (or send two concurrent HTTP requests to `httpTriggerHandler.HandleUserTriggerRequest` bearing the same JWT).
4. Observe that both goroutines can return a valid `*gateway.AuthorizedKey` (no `"JWT token has already been used"` error on either), demonstrating that the single-use token was accepted twice.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
