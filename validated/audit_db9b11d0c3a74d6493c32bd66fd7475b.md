Confirmed: `WebhookMetadata.shop` is a plain string passed straight from the unauthenticated header into the handler contract, with no independent verification against anything the HMAC covers.

### Title
Webhook shop identity is unauthenticated and can be spoofed independently of the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw body [1](#0-0) , using `Request#to_signable_string`, which returns only `@raw_body` [2](#0-1) . The `shop` value that is subsequently trusted and forwarded to the app's handler is parsed straight from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, which is never included in the signed material [3](#0-2) .

### Finding Description
The identity binding that should hold is: **shop authenticated by HMAC == shop the app acts on**. Instead:
- The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — not a per-shop secret [4](#0-3) .
- `HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string`, which for webhooks is just the raw JSON body [5](#0-4) .
- `Registry.process` trusts `request.shop` unconditionally once the body-only HMAC passes, and hands it to the handler as `WebhookMetadata.shop` [6](#0-5) .

Because any merchant can freely install a public app on their own (even free/dev) store, they receive genuinely Shopify-signed webhooks whose HMAC is valid for the shared app secret. Since the `shop-domain` header is outside the signed payload, that same attacker can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint after only rewriting the `X-Shopify-Shop-Domain` header to name a victim shop. The HMAC check still passes because it only verifies the body bytes, not the shop claim — exactly the "field acted on but not covered by the HMAC" class of bug described in the report, applied here instead of to the audited vault.teal/vault.js mismatch.

### Impact Explanation
Any app logic keyed off `WebhookMetadata.shop` (e.g., looking up the shop's stored session/settings to apply the webhook body, writing per-tenant state, or triggering shop-scoped side effects) can be made to operate against an arbitrary victim shop using attacker-supplied body content, while Shopify's own HMAC verification is satisfied. This is a cross-tenant identity-binding break: the "authenticated" shop (whichever shop's secret validated the bytes — indistinguishable since the secret is shared) and the "acted-upon" shop (header value) are never proven equal.

### Likelihood Explanation
High-plausibility, low-effort: no access token, `client_secret`, or privileged account is required — only a normal app installation on any shop (including the attacker's own store), which is available to any unprivileged internet user. Capturing/replaying one's own legitimate webhook and editing an HTTP header is trivial.

### Recommendation
- **Short term:** Bind the shop identity into the verified material — e.g., require the webhook registry to only trust `request.shop` after confirming the shop is one the app actually has an active session/install for, or additionally validate that the delivering shop matches per-installation expectations before dispatching to the handler.
- **Long term:** Include the shop domain (and other identity-bearing headers such as `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified payload, so that the same class of "verified bytes vs. parsed identity" mismatch flagged in the vault contract report cannot recur here.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic so Shopify delivers a legitimately HMAC-signed webhook (`X-Shopify-Hmac-Sha256` computed over the raw body with the app's shared `client_secret`).
2. Intercept/replay that HTTP POST to the app's webhook endpoint, keeping the body and `X-Shopify-Hmac-Sha256` header untouched, but changing `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body's HMAC — validation succeeds [1](#0-0) .
4. The registered handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-chosen JSON>, ...)` [7](#0-6)  and performs shop-scoped actions against the victim's tenant using attacker-controlled data, despite the request never actually originating from or about that shop.
