### Title
`OmniBridge.describeWithdrawal` reports "completed" for non-EVM/Sol/UTXO destination chains without checking on-chain finalization - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
`OmniBridge.describeWithdrawal` determines withdrawal status differently depending on destination chain kind. For EVM, Solana, Fogo, Starknet and Aptos chains it requires `transfer.finalised?.transaction_hash` to be present before reporting `"completed"`, and falls back to `"pending"` otherwise. For UTXO chains it similarly requires a real hash. For any other chain kind not covered by these branches, it unconditionally returns `{ status: "completed", txHash: null }` the moment `transfer.recipient` is non-null — i.e., as soon as the Omni Bridge indexer has recorded a recipient for the transfer, regardless of whether the transfer was actually finalized/delivered on the destination chain.

### Finding Description [1](#0-0) 

The function fetches the transfer record and branches on `destinationChain`:
- EVM/Sol/Fogo/Strk/Aptos: `txHash = transfer.finalised?.transaction_hash` then only reports `"completed"` if `txHash` is truthy, otherwise `"pending"`.
- UTXO chains: similarly requires a pending-sign-id or finalized hash before completing.
- **Else branch**: immediately `return { status: "completed", txHash: null }` — with no check of `transfer.finalised` at all.

This "else" branch breaks the equality that `describeWithdrawal`'s reported status should equal the actual on-chain settlement outcome. Every other branch explicitly gates "completed" behind evidence of finalization (a real transaction hash); the fallback branch reports "completed" purely based on the indexer having assigned a `recipient`, which can happen before the transfer is actually delivered/finalized on the destination chain.

This status feeds directly into `watchWithdrawal`, which treats `status === "completed"` as terminal success and resolves the poll immediately: [2](#0-1) 

An integrator calling `sdk.waitForWithdrawalCompletion` (built on `watchWithdrawal`/`describeWithdrawal`) for any chain routed through Omni Bridge that falls into this fallback branch would receive a premature "completed" (with `txHash: null`) before the underlying transfer is verified finalized.

### Impact Explanation
This maps to the allowed impact category "a status or hash misreport making an integrator credit or refund twice" (High). An integrator relying on the SDK's completion status to credit a user's balance, mark an off-chain ledger entry as settled, or release a corresponding asset on another system could act on a false "completed" signal before the withdrawal is actually finalized on the destination chain, leading to premature crediting.

### Likelihood Explanation
The bug is deterministic for any destination chain kind not explicitly enumerated in the EVM/Sol/Fogo/Strk/Aptos and UTXO branches — no attacker action or malicious party is required; the misreport occurs purely from the code's control-flow structure whenever `transfer.recipient` is set before finalization completes for such chains. Whether any currently-supported Omni Bridge chain actually falls into this fallback branch depends on the full `ChainKind` enum and `isEvmChain`/`isUtxoChain` definitions from the external `@omni-bridge/core` package, which is outside this repo's scope; I could not fully enumerate all `ChainKind` values from the in-scope code to confirm which specific chains currently exercise this branch.

### Recommendation
In the fallback branch, require `transfer.finalised` (or an equivalent finalization signal) to be present before reporting `"completed"`, mirroring the EVM/Sol and UTXO branches, and return `"pending"` otherwise — do not treat a non-null `recipient` alone as proof of completion.

### Proof of Concept
1. A withdrawal is routed via `OmniBridge` to a destination chain kind that is not matched by `isEvmChain`, `ChainKind.Sol/Fogo/Strk/Aptos`, or `isUtxoChain`.
2. The Omni Bridge indexer records the transfer with a non-null `recipient` but the transfer is not yet finalized on the destination chain (`transfer.finalised` is absent).
3. `describeWithdrawal` reaches the `else` branch at [3](#0-2)  and returns `{ status: "completed", txHash: null }`.
4. `watchWithdrawal` sees `status.status === "completed"` and immediately resolves with `{ hash: null }`, signaling completion to the caller/integrator before actual on-chain settlement is confirmed.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
