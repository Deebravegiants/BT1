### Title
Webhook shop identity not bound by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies only the body's HMAC and never checks that the `shop` value is bound to the signature, so any request with a valid `(raw_body, hmac)` pair is accepted regardless of which shop the `shop-domain` header claims to be.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes [2](#0-1) . `Registry.process` only calls `Utils::HmacValidator.validate(request)`, which validates the HMAC over `to_signable_string` (i.e. the body), and then immediately forwards `request.shop` to the app's handler as trusted `WebhookMetadata` [3](#0-2) . `HmacValidator.validate` signs with `Context.api_secret_key`, which is the single app-level secret shared across every shop that installed the app — it is not shop-specific [4](#0-3) .

The documented contract states that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4) , but in fact it only proves the body bytes were signed with the app secret — it does not prove which shop that signature was issued for. The binding that should hold is `shop(hmac-signed-payload) == shop(shop-domain header)`; the gem never enforces this equality.

### Impact Explanation
An attacker who controls any shop that has installed the app (an unprivileged actor from the app's perspective — no special role or leaked credential needed) receives real webhook deliveries from Shopify for their own shop, each with a body and a valid `hmac-sha256` signed with the app's shared `api_secret_key`. The attacker can replay that exact `(raw_body, hmac)` pair directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` passes the spoofed `shop` value straight to the app's handler [6](#0-5) . Any host application that trusts `data.shop` from the handler (as instructed by the gem's own documentation example, which calls `perform_later(shop_domain: data.shop, ...)` [7](#0-6) ) will process attacker-controlled webhook content attributed to a shop the attacker does not control — a cross-tenant identity confusion.

### Likelihood Explanation
Reaching this requires only that the attacker operate their own shop with the target app installed (a normal, unprivileged merchant-level capability) and send a crafted HTTP POST with copied body/HMAC and a modified shop header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically verify that the claimed `shop-domain` header corresponds to the shop the HMAC was actually issued for before handing `WebhookMetadata` to the handler. At minimum, document/require callers to independently confirm the `shop` value corresponds to a shop with an active, known session before trusting it, or have `HmacValidator`/`Registry.process` reject requests where the header-derived `shop` cannot be tied to the signature.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it's signed with the app's single shared `api_secret_key` [8](#0-7) .
3. Replay this exact body and HMAC to the app's webhook route, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (unsigned) header [2](#0-1) ; `Registry.process` validates only the body HMAC and dispatches `WebhookMetadata.new(... shop: request.shop ...)` to the handler with `shop == "victim-shop.myshopify.com"` [9](#0-8) , even though the payload originated from the attacker's own shop.
