### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are excluded from the HMAC signature, allowing cross-tenant webhook shop-spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version` and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` verifies only the body's HMAC and then hands the header-derived `shop` value straight to the app's webhook handler, so the identity binding "the shop the HMAC was computed for" == "the shop attributed to the processed webhook" is not enforced.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`. [1](#0-0) 
For webhooks, `to_signable_string` is defined to be exactly the raw request body — no headers are included in the signed material: [2](#0-1) 
Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight out of HTTP headers with no cryptographic binding to the signature: [3](#0-2) 
`Registry.process` validates only this body HMAC, then immediately trusts `request.shop` (and `request.topic`/`request.webhook_id`) when constructing the `WebhookMetadata` passed to the app's registered handler: [4](#0-3) 

Because the signature only covers the body, an unprivileged attacker who owns any shop that has the vulnerable app installed can:
1. Trigger a legitimate webhook delivery for their own shop (e.g., by performing an action in their own store that fires a webhook topic the app subscribes to). This delivery is a genuinely valid, correctly-signed HTTP POST — attacker never needs `api_secret_key`.
2. Capture the raw body and the `X-Shopify-Hmac-Sha256` value from that delivery.
3. Replay the exact same body/HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain.
4. `HmacValidator.validate` still succeeds because it only recomputes the HMAC over the untouched raw body — the forged `shop` header is never checked against the signature.
5. `Registry.process` passes the attacker's chosen `shop` value (now pointing at the victim) to the app's handler as `WebhookMetadata#shop`, alongside the attacker's own body content.

This breaks the binding: **HMAC-verified byte source (body only) == identity attributed to the processed event (shop/topic/webhook_id, taken from unauthenticated headers)**. Any host application that uses `WebhookMetadata#shop` to select which tenant record to update, which tenant's session/access token to use for a follow-up API call, or which tenant's data the payload belongs to, can be made to apply attacker-controlled payload content to a different (victim) tenant's data — a cross-tenant confusion/write primitive that is reachable by any unprivileged internet user who can install a free/dev shop running the target app.

### Impact Explanation
This is a genuine cross-tenant boundary break originating in the gem's own webhook verification code (`Utils::HmacValidator`, `Webhooks::Request`, `Webhooks::Registry`), not a misuse of a documented API by the host app — the gem's `process` method is the documented entry point apps are told to call, and it silently forwards an unauthenticated `shop` value after only checking body authenticity. Any app that keys per-tenant behavior off `WebhookMetadata#shop` (the field this gem explicitly hands to handlers) is exposed to processing attacker-supplied payload content under a victim shop's identity — satisfying the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
Requires no privileged credentials, no `api_secret_key`, and no TLS interception — only an attacker-controlled shop (freely obtainable as a Shopify partner/dev store) that has the target app installed, plus the ability to replay an HTTP POST with a modified header, which is trivial. The only constraint is that the replayed payload's *content* is whatever the attacker's own store produced, but the *shop attribution* is fully attacker-chosen for any target shop's domain string.

### Recommendation
Include the shop-identifying headers (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them the way `AuthQuery#to_signable_string` binds `shop`/`host`/`state` for OAuth callbacks (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`). At minimum, `Webhooks::Request#to_signable_string` should not be limited to the raw body alone if `shop` is going to be trusted downstream without additional verification (e.g., cross-checking `shop` against a value already associated with the specific webhook subscription/session on the app side).

### Proof of Concept
```ruby
# 1. Attacker's own store fires a real webhook; attacker captures body+hmac.
raw_body     = '{"id":123,"note":"legit content from attacker shop"}'
valid_hmac   = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays the identical body+hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac,          # still valid: body unchanged
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, NOT covered by HMAC
  "x-shopify-webhook-id"   => "attacker-chosen-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. Validation succeeds because only raw_body is HMAC-checked
ShopifyAPI::Webhooks::Registry.process(request)
# => app's handler receives WebhookMetadata#shop == "victim-shop.myshopify.com"
#    with attacker-controlled body content.
``` [4](#0-3)
