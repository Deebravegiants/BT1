Confirmed: `WebhookMetadata.shop` is passed directly from `request.shop` and delivered as-is to the host app's `WebhookHandler#handle` for tenant-specific processing, without being cryptographically bound to the payload.

### Title
Webhook `shop` domain is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but exposes and propagates the `shop` field (read from the `shopify-shop-domain` / `x-shopify-shop-domain` header) as trusted tenant identity to the host application's webhook handler. Because the `shop` value is never included in the signed bytes, `Utils::HmacValidator.validate` cannot detect if the `shop` header has been tampered with, breaking the binding `hmac_signed_bytes == bytes_the_app_trusts_for_tenant_identity`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an unauthenticated header, independent of the signed payload: [2](#0-1) 

`Registry.process` verifies only that the HMAC over `to_signable_string` (i.e., the raw body) is valid, then immediately forwards `request.shop` to the registered handler as authoritative tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` performs a byte-exact HMAC check, but the bytes it verifies (`verifiable_query.to_signable_string`) never include the `shop` header: [4](#0-3) 

The resulting `WebhookMetadata.shop` field is a plain, unauthenticated string handed to the host app as if it were verified: [5](#0-4) 

The equality that should hold but doesn't: `bytes_verified_by_HMAC == bytes_the_app_uses_to_identify_the_tenant`. Here, `bytes_verified_by_HMAC = raw_body` while `bytes_the_app_uses_to_identify_the_tenant = shop header`, so the two are disjoint. An attacker who controls any shop with the app installed receives genuinely-signed webhook deliveries from Shopify for their own store (the HMAC is computed by Shopify using the app's `client_secret` over the body only). The attacker can then replay that exact raw body to the app's webhook endpoint while substituting a different, victim shop's domain in the `shopify-shop-domain` header. Because the HMAC never covered the header, `HmacValidator.validate` still reports the request as valid, and `Registry.process` dispatches it to the handler with the attacker-chosen `shop` value, tricking the host application into processing/crediting webhook data under the wrong tenant.

### Impact Explanation
This crosses a tenant boundary: a party with legitimate access to their own shop's webhook traffic can cause the app to process data attributed to a different merchant, since `shop` is the identifier host apps rely on to select the correct merchant session/database record before acting on webhook `body` content. This matches the High-severity criteria (cross-tenant access) since the shop-identity binding used for per-tenant processing is not actually authenticated, despite the HMAC check appearing to validate the whole request.

### Likelihood Explanation
Likelihood is high for any app that receives webhooks for multiple merchants (the common case): the attacker only needs their own shop to have the app installed (an unprivileged action any merchant can take by installing a public app) and the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop` header — no secrets, tokens, or elevated privileges are required.

### Recommendation
Include the `shop` domain (and other identity-relevant headers such as `topic`, `webhook-id`, `api-version`) in the signable string, or otherwise cryptographically bind them to the payload before verification, so that `Utils::HmacValidator.validate` fails if any of these fields are altered independently of the body. At minimum, `Request#to_signable_string` should incorporate the `shop` header value so tampering invalidates the signature.

### Proof of Concept
1. App receives a legitimately Shopify-signed webhook for `attacker-shop.myshopify.com` with headers `x-shopify-hmac-sha256: <valid-hmac-of-raw-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `raw_body` and `hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) and finds it matches — validation passes.
4. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, so the host application processes the attacker's payload as if it belonged to the victim shop.
