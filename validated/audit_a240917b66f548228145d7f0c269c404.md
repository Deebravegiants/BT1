### Title
Unbounded-length `message.from` bytes field causes panic (slice-index/subtract-overflow) in `on_accept`, crashing the node on cross-chain token receipt - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Message.from` is an ABI `bytes` field of arbitrary attacker-controlled length decoded from the `PostRequest` body of an incoming cross-chain token transfer. When calldata is present and unsigned, and the source is an EVM chain, the code computes `from_bytes.len() - 20` and slices into `from_bytes` without validating that `from_bytes.len() >= 20`, unlike the sibling `to`/`from`-length checks used elsewhere in the same file (e.g. `on_timeout`).

### Finding Description
In `on_accept`, once the token mint/transfer has succeeded, the pallet optionally executes calldata attached to the message: [1](#0-0) 

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(
            &from_bytes[from_bytes.len() - 20..],
        ))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
```

`message.from` comes straight from `Message::abi_decode(&body)` [2](#0-1)  where `Message` is the Solidity-ABI-compatible struct `struct Message { bytes from; bytes to; uint256 amount; bytes data; }` [3](#0-2) . Because `bytes` is a dynamic ABI type, its length is entirely attacker-controlled — a malicious sender on the source chain (or anyone forging the cross-chain request that a relayer then delivers) can set `from` to a length shorter than 20 bytes (including zero).

When that happens:
- `from_bytes.len() - 20` underflows a `usize` subtraction. In a Substrate runtime built with overflow checks (the default for debug and often for release via `overflow-checks = true`), this panics immediately with "attempt to subtract with overflow".
- Even without overflow checks, the wrapped huge value is then used as a slice start index into `from_bytes`, which panics with an out-of-bounds slice index.

Either way this is an unconditional Rust panic, not a recoverable `Result::Err`. Contrast this with the *sibling* code path in `on_timeout`, just a few lines later, which correctly validates length before use: [4](#0-3) 

This confirms the length-validation was deliberately implemented elsewhere in the same file but omitted at line 177-181.

This code is reached via `IsmpModule::on_accept`, which is invoked from the permissionless message-dispatch pipeline: any relayer can submit a `handle_unsigned` unsigned extrinsic containing a `RequestMessage` whose `PostRequest.to` targets this pallet's module id, and `pallet_ismp::Pallet::execute` -> `handle_incoming_message` -> router dispatch will call `on_accept` on valid proof, with no privilege required from the caller: [5](#0-4)  and [6](#0-5) .

This is a Rust/Substrate analog of CVE-2021-20297: an unprivileged/attacker-controlled input field (there, `match.path`; here, the ABI `bytes from` field) is processed without bounds validation, causing an unhandled crash instead of a graceful error, taking down node/relayer availability.

### Impact Explanation
A panic inside extrinsic execution triggered by an unsigned, permissionless `handle_unsigned` call will abort transaction execution and, depending on how panics propagate through the runtime's panic handler (`set_panic_hook`/`AbortOnPanic` semantics common in Substrate runtimes compiled for `no_std`/Wasm), can crash the node's block-authoring/import process or halt the collator, denying service to the whole Hyperbridge parachain (availability impact, matching CVSS `A:H` in the CVE). Because `handle_unsigned` is validated via `ValidateUnsigned::validate_unsigned`, which itself calls `Self::execute(messages.clone())` [6](#0-5) , the panic can even be hit during transaction-pool validation, before the transaction is included in a block — meaning it can crash validating nodes just by being gossiped, without ever needing to be finalized in a block.

### Likelihood Explanation
This is trivially reachable: any relayer or malicious actor able to produce (or forge) a `PostRequest` destined for the hyper-fungible-token module id with calldata attached and an unsigned `SubstrateCalldata` (`signature: None`) needs only to control `message.from` to be shorter than 20 bytes when `source.is_evm()`. Since `from` is a dynamic ABI `bytes` field encoded entirely by the request originator on the source chain, no cryptographic proof forgery is needed to control its length — only a valid state/consensus proof for delivering the message is required, which is the normal relaying flow.

### Recommendation
Validate `from_bytes.len() >= 20` (and ideally `== 20`) before slicing, returning a proper `HftError` (e.g. reuse/extend `HftError::InvalidSenderLength`) exactly as already done in the `on_timeout` handler at lines 224-232, instead of performing an unchecked subtraction and slice.

### Proof of Concept
1. On the EVM source chain, dispatch a `PostRequest` to the hyper-fungible-token module whose ABI-encoded body is a `Message { from: bytes::new() /* len 0 */, to: <valid 20 or 32 bytes>, amount: <valid>, data: <SCALE-encoded SubstrateCalldata{ signature: None, runtime_call: <any valid call> }> }`.
2. Relay this request (with a valid state proof) to the destination Hyperbridge parachain via the permissionless `pallet_ismp::Call::handle_unsigned` extrinsic.
3. `handle_incoming_message` routes to `HyperFungibleToken::on_accept`, which successfully mints/transfers, then reaches the calldata branch; since `substrate_data.signature` is `None` and `source.is_evm()` is `true`, it executes `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() == 0`, causing `0usize - 20` to panic (or, without overflow checks, an out-of-bounds slice panic).
4. Observe the node/collator process panicking during either `ValidateUnsigned::validate_unsigned` (transaction-pool validation) or block execution.
