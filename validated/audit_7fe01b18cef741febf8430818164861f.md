Confirmed root cause: `Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, unauthenticated by the HMAC [2](#0-1) . `HmacValidator.validate` only checks the HMAC against `to_signable_string` (the body), never against the headers [3](#0-2) . `Registry.process` accepts any request whose body-HMAC checks out and then trusts `request.shop`/`request.topic`/`request.webhook_id` as tenant-identifying metadata passed to the handler [4](#0-3) .

### Title
Webhook tenant identity (`shop-domain`/`topic`/`webhook-id` headers) is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw JSON body only, but the tenant-identifying `shop`, `topic`, and `webhook_id` values consumed by `ShopifyAPI::Webhooks::Registry.process` are read from HTTP headers that are excluded from the signature. Any request whose body matches a previously-observed, validly-signed webhook payload will pass `Utils::HmacValidator.validate`, regardless of which shop the accompanying headers claim it is for.

### Finding Description
`Request#hmac` reads `shopify-hmac-sha256` from headers, and `Request#to_signable_string` returns `@raw_body` exclusively [5](#0-4) . `HmacValidator.validate_signature` recomputes the HMAC purely from that signable string and the app's secret, then secure-compares it to the received signature [6](#0-5) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors on `Request` are derived from `shopify_header(...)` and never participate in the signature at all [7](#0-6) .

`Registry.process` gates handling on `Utils::HmacValidator.validate(request)` succeeding, then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id` and hands it to the registered handler [4](#0-3) . This breaks the intended binding `HMAC-verified-bytes == identity-fields-acted-on`: the equality that should hold is `signed(raw_body) == (shop, topic, webhook_id)`, but in this code only `signed(raw_body) == raw_body` is enforced — the headers carrying tenant identity are outside the signed byte range.

### Impact Explanation
Any host application built on this gem that dispatches per-tenant logic based on `WebhookMetadata#shop` (the documented and expected usage, per `docs/usage/webhooks.md`) is relying on a value this gem never authenticates. An attacker who can deliver an HTTP POST to the app's webhook endpoint with a previously-seen valid `(raw_body, hmac)` pair (e.g., replaying their own store's legitimate webhook, which they can freely trigger and observe as the store owner) but a substituted `shopify-shop-domain` header will pass `Registry.process`'s HMAC check unmodified, causing the handler to process the payload under a different shop's identity than the one that produced it. This is a cross-tenant identity-binding failure: the gem's own signature verification provides no guarantee that the "shop" driving tenant-scoped logic corresponds to the data whose authenticity was actually checked.

### Likelihood Explanation
Exploitation only requires control of an unprivileged/free Shopify store (to legitimately generate one validly-signed webhook body+HMAC pair) and the ability to POST to the target app's public webhook endpoint with attacker-chosen headers — both routine, no leaked credentials or TLS interception needed. The gem provides no header-vs-body binding check anywhere in `Utils::HmacValidator` or `Webhooks::Registry`, so this is reachable through documented, ordinary use of `Registry.process`.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before `Registry.process` accepts the request, so that a valid HMAC can only correspond to the specific `(shop, topic, webhook_id, body)` tuple it was generated for.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (free/development store) and triggers any webhook topic they've registered (e.g. `orders/create`), capturing the raw POST body and its `shopify-hmac-sha256` header — both are legitimately signed by Shopify with the app's real secret.
2. Attacker resends the identical `raw_body` and `shopify-hmac-sha256` header to the app's webhook endpoint, but replaces `shopify-shop-domain` with `victim-shop.myshopify.com` (and, if desired, `shopify-webhook-id`/`shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC — unaffected by the header substitution [8](#0-7) .
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` even though the body content was generated for `attacker-shop.myshopify.com`, causing the host app to attribute attacker-controlled data to the victim tenant [9](#0-8) .
