### Title
Predictable "randomized" NFT reveal lets users select/steal specific destination tokens via timestamp-modulo index and vector-length manipulation - ([File: aptos-move/move-examples/post_mint_reveal_nft/sources/minting.move])

### Summary
`exchange()` is supposed to assign each user a "randomized" destination NFT from the shared reveal pool. In reality, the index is computed as `timestamp::now_seconds() % length`, not real randomness, and the underlying `BigVector::swap_remove` reshuffles the pool on every claim in a fully deterministic, attacker-observable way. This reproduces the exact same custody-invariant break as the external report (an on-chain "random" index derived from a value the attacker can predict/steer, combined with attacker-controlled queue mutation between observation and use) — except here the target asset is an Aptos token-object-backed NFT rather than an EVM auction NFT.

### Finding Description
In `exchange()`: [1](#0-0) 

```
// Assert there's still some token uris in the vector.
assert!(big_vector::length(&collection_config.tokens) > 0, error::permission_denied(ENO_ENOUGH_TOKENS_LEFT));

// Randomize which token we're assigning to the user.
let index = now % big_vector::length(&collection_config.tokens);
let token = big_vector::swap_remove(&mut collection_config.tokens, index);
```

Two compounding problems break the "fair random assignment" invariant:

1. **No real randomness is used.** `now` is `timestamp::now_seconds()`, the current block timestamp — a value known to every validator/observer *before* the transaction executes, and one the caller can effectively choose by timing their submission (or, on Aptos, by simply waiting for/targeting a specific second, since block timestamps are monotonically increasing and coarse-grained). This is the direct analog of the external bug's `randomNumber % auctionQueue.length` being predictable/stale relative to actual queue state.

2. **The "queue" (`collection_config.tokens`, a `BigVector`) is mutated by `swap_remove` on every single exchange**, using the same swap-to-slot mechanic described in the report: [2](#0-1)  `swap_remove` pops the last element and moves it into slot `i`. Anyone who holds (or can acquire) a source certificate can call `exchange()` to shrink `length(tokens)` by exactly 1 and reposition the last-remaining token into a predictable slot, immediately before submitting their real exchange call in the same block/timing window. Since `add_tokens` performs no reveal-time gating either (it only checks `exists<CollectionConfig>`), and the tokens vector and its contents are readable off-chain (all module state is public), an attacker can:
   - Observe `length(tokens)` and the URIs at each index.
   - Compute exactly which second (`now`) would yield `now % length == target_index` for a desired rare/valuable `token_uri`.
   - If not already aligned, burn one extra cheap certificate via `exchange()` (or simply wait) to shift `length` by 1 and reposition items until the rare token lands on an index reachable at a convenient timestamp, then submit their real `exchange()` call at that timestamp to claim it deterministically.

This mirrors the external report's core invariant break: **the "random" selection mechanism can be steered by controlling either the input to the modulo or the length/contents of the collection being indexed**, so it stops being random and becomes attacker-chosen.

### Impact Explanation
The destination collection tokens represent the actual value/art NFTs (token objects minted via `token::mint_token` and transferred to the claimer) — this is the custody-bearing asset the whole "reveal" mechanism exists to protect against front-running. An attacker who can predict/steer the index can guarantee they receive the rarest/most valuable token in the pool while other legitimate certificate holders are diverted to less valuable/common tokens, i.e., unauthorized reassignment of specific token-object ownership away from fair, unpredictable distribution — a direct custody/ownership integrity violation on value-bearing NFTs. This is high impact for any project relying on this example for a live reveal mechanism, since token rarity commonly maps directly to secondary-market value.

### Likelihood Explanation
Likelihood is high: no privileged role is required, all state needed to compute the target timestamp/index (`collection_config.tokens` contents and length) is publicly readable, `exchange()` is a permissionless entry function open to any certificate holder, and Aptos block timestamps are coarse and effectively attacker-influenceable in terms of choosing when to submit. The only cost to the attacker is holding/burning one or more low-value certificates to adjust `length` if needed.

### Recommendation
Replace `now % length` with Aptos's on-chain randomness API (`aptos_framework::randomness::u64_range`) invoked from a `#[randomness]`-annotated, non-composable entry function (per AIP-41 guidance already used elsewhere in this repo's `raffle` example), and disallow `add_tokens`/pool mutation once claiming/reveal has started so the pool composition cannot be adjusted between a user's certificate purchase and their reveal draw.

### Proof of Concept
1. Admin sets up source/destination collections and calls `add_tokens` with a list of `token_uris`, e.g. `[common1, common2, ..., RARE]` at some index `k` (attacker reads `CollectionConfig.tokens` state via a view/indexer since it's stored plainly on-chain).
2. Attacker acquires two certificates (`mint_source_certificate`, amount = 2).
3. Attacker computes, given current `length = L`, the timestamp `t` such that `t % L == k` (the rare token's current slot). If `t` has already passed or is inconvenient, attacker instead calls `exchange()` with certificate #1 at any time to shrink the pool to `L-1` and (per `swap_remove` semantics) recomputes the new slot of `RARE` after the swap.
4. Attacker repeats step 3 (spending cheap certificates) until `RARE`'s slot aligns with a `now % length` reachable at the next transaction submission, then calls `exchange()` with certificate #2 at that exact time.
5. `index = now % length` equals `RARE`'s slot; `big_vector::swap_remove` returns `RARE`; attacker receives the rare destination NFT deterministically instead of by fair chance, while other legitimate certificate holders are left only with common tokens.

    public fun swap_remove<T>(v: &mut BigVector<T>, i: u64): T {
        assert!(i < length(v), error::invalid_argument(EINDEX_OUT_OF_BOUNDS));
        let last_val = pop_back(v);
        // if the requested value is the last one, return it
        if (v.end_index == i) {
            return last_val
        };
        // because the lack of mem::swap, here we swap remove the requested value from the bucket
        // and append the last_val to the bucket then swap the last bucket val back
        let bucket = table_with_length::borrow_mut(&mut v.buckets, i / v.bucket_size);
        let bucket_len = vector::length(bucket);
        let val = vector::swap_remove(bucket, i % v.bucket_size);
        vector::push_back(bucket, last_val);
        vector::swap(bucket, i % v.bucket_size, bucket_len - 1);
        val
    }
