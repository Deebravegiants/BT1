Based on my research, I found a concrete analog: the block-revenue-sharing reward path for SIMD-0123 (`pending_delegator_rewards`) can silently strand deposited lamports without any credit path back to the depositors.

### Title
Block-revenue-sharing rewards deposited via `DepositDelegatorRewards` are permanently unaccounted for when a vote account has zero delegated stake in the rewarded epoch - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`deposit_delegator_rewards` lets anyone deposit lamports into a vote account's `pending_delegator_rewards` balance to be split among that validator's delegators at the next epoch boundary [1](#0-0) . Distribution of that balance is computed each epoch by `calculate_block_reward`, which divides `pending_delegator_rewards` proportionally by `total_active_stake` for the vote account in the rewarded epoch [2](#0-1) . If `total_active_stake` is `0` for that epoch — e.g., no stake is currently delegated to the vote account, or the vote account cannot be found in `distribution_epoch_vote_accounts` — the function returns `0` for every delegation, meaning nothing is distributed for that epoch. Crucially, `pending_delegator_rewards` itself is never decremented anywhere in this reward computation/distribution flow (`calculate_stake_rewards_and_commissions`, `distribute_reward_commissions`, `store_stake_accounts_in_partition`) — I searched the entire partitioned-rewards module and found no write path that reduces `pending_delegator_rewards` after a payout is calculated.

### Finding Description
This exactly mirrors the Y2K Finance bug class: a reward pool (`pending_delegator_rewards`) is funded by an external actor's deposit, but the reward is only distributed proportionally to *currently active* stake at epoch-turn time. When there is no active stake for that vote account in the rewarded epoch (`total_active_stake == 0` at line 211), `calculate_block_reward` returns `0` for all callers [3](#0-2) . Because `pending_delegator_rewards` is a monotonically-increasing field only ever incremented by `add_pending_delegator_rewards` in the vote program [4](#0-3) , and I could not locate any decrement/consumption path in the reward-distribution code, the deposited lamports for that "no active stake" epoch are neither paid out to any delegator, returned to the depositor, nor rolled forward with an accounting adjustment (e.g., an explicit "amount consumed this epoch" subtraction) — the value calculated in `calculate_block_reward` is discarded, but the balance backing it in `pending_delegator_rewards` is unaffected by that discard, since nothing writes to it during distribution. This can cause a mismatch between "advertised" pending rewards (visible on-chain in `pending_delegator_rewards`) and lamports that are actually reachable by any delegator claim path, similar to the disclosed Y2K "rewards not rolled over" issue, where funds sit in the pool unusable because the accrual logic ties distribution strictly to the concurrent active-stake set instead of tracking/rolling forward an "unused" remainder.

### Impact Explanation
If a validator's vote account temporarily has zero delegated stake in the rewarded epoch (e.g., between full un-delegation and re-delegation, or right after vote-account creation before any stake activates) while `pending_delegator_rewards` is nonzero, the SIMD-0123 mechanism permanently loses the ability to attribute that epoch's share of the deposit to delegators — there is no code path shown that re-attempts distribution for a "skipped" period or corrects the outstanding balance. This is a protocol-level accounting/value-loss issue in the reward path (not a validator/operator misconfiguration), analogous to the disclosed "protocol leaked value" finding in the original report.

### Likelihood Explanation
Likelihood is moderate: it requires (1) `block_revenue_sharing`/SIMD-0123 features enabled, (2) a nonzero `pending_delegator_rewards` balance (achievable by anyone calling `DepositDelegatorRewards`), and (3) a rewarded epoch in which the vote account has zero recorded `total_active_stake` in `RewardEpochDelegatedStakes` — a state reachable through normal stake deactivation/reactivation cycles.

### Recommendation
Verify whether there is an intentional mechanism elsewhere (not found in the search) that decrements `pending_delegator_rewards` by the total amount actually computed as `block_reward` across all delegations for the epoch, or that carries forward unattributed amounts. If no such mechanism exists, `calculate_block_reward`/`calculate_stake_rewards_and_commissions` should track total block-reward lamports distributed per vote account and subtract that from `pending_delegator_rewards` after distribution (in `distribution.rs`'s `store_stake_accounts_in_partition`), and any un-distributable remainder (from `total_active_stake == 0`) should either remain correctly reflected in `pending_delegator_rewards` for future distribution or be explicitly handled (e.g., returned/burned) rather than silently computed-then-dropped.

### Proof of Concept
1. Enable `block_revenue_sharing`, `commission_rate_in_basis_points`, `custom_commission_collector` features and create a VoteState V4 account.
2. Call `DepositDelegatorRewards` to deposit lamports, incrementing `pending_delegator_rewards` (verified in test flow at [5](#0-4) ).
3. Ensure the vote account has zero active delegated stake for the rewarded epoch (e.g., all delegators undelegate before epoch boundary), so `reward_epoch_delegated_stakes.delegated_stakes.get(&vote_pubkey)` resolves to `0` or missing.
4. At epoch boundary, `calculate_block_reward` computes `0` for every stake delegation to that vote pubkey (`total_active_stake == 0` branch) [6](#0-5) .
5. Re-delegate stake in a later epoch and inspect the vote account's `pending_delegator_rewards` value on-chain — confirm it still reflects the full deposited amount (since no decrement occurred), while the "skipped" epoch's share was neither paid to any delegator nor otherwise accounted for as consumed.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
