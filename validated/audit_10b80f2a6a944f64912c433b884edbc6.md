### Title
Webhook processing trusts unauthenticated `shop-domain` header while HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw JSON body, but the `shop` (and `topic`/`webhook_id`) values that are subsequently trusted and forwarded to the app's handler are read from HTTP headers that are **not** covered by that HMAC. This breaks the intended binding `hmac_signed_bytes == identity_bytes_trusted`, allowing a captured, validly-signed webhook body to be replayed with a different `shop-domain` header and be processed as if it belonged to another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from HTTP headers, which are not part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., only the body for webhooks) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which the HMAC covers — to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is precisely the report's bug class: **a field acted upon (the shop identity that scopes/tenants the webhook data) is not covered by the HMAC** that is used to authenticate the request. The signature only proves the body bytes came from a holder of the API secret (Shopify); it proves nothing about which shop, topic, or webhook the body is associated with, because those identity-bearing headers can be freely modified without invalidating the signature.

### Impact Explanation
An attacker who operates or has compromised a Shopify app installed on their own shop legitimately receives real webhooks (valid body + valid HMAC) for their own shop's events. Because the HMAC never binds `shop-domain`, that attacker can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) to reference a victim shop. `Registry.process` will pass HMAC validation (body unchanged) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any app that uses `WebhookMetadata#shop` to select the tenant record/session to update (the documented and expected use, e.g. to look up `SessionRepository` for that shop) will write or act on attacker-controlled data under a different tenant's identity — a cross-tenant data injection, satisfying the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only sending a normal HTTP request to the app's public webhook endpoint with attacker-controlled headers and a body+HMAC pair the attacker legitimately possesses from their own shop's traffic — no `api_secret_key`, access token, or privileged access is needed. This is reachable by any unprivileged internet user/app operator, making likelihood non-trivial, though it depends on the host app trusting `WebhookMetadata#shop` as the sole tenant discriminator (the intended and documented usage pattern of this library).

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the header-derived identity to the verified body:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (requires coordinating with Shopify's signing scheme, since Shopify currently signs body-only — so at minimum the app-facing API should not present these header values as "verified" alongside a body-only HMAC check).
- At minimum, update documentation/API so `WebhookMetadata#shop` is not treated as authenticated by `Registry.process`, and require callers to independently confirm `shop` against a known/expected value (e.g., the shop tied to the resource being modified) before trusting it.
- Consider validating `shop` against `Utils::ShopValidator` and cross-checking it against session storage keyed data before use, rather than passing it through unchecked.

### Proof of Concept
1. Attacker's app is installed on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid signature of `B`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a POST to the victim-hosted app's webhook endpoint with the same body `B` and same `hmac-sha256: H`, but sets `shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — matches `H` — validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though `victim-shop` never sent this event, resulting in cross-tenant data corruption/injection in any app that trusts this field to select the tenant context.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
