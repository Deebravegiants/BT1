### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` entirely from HTTP headers, but its `to_signable_string` (used by `HmacValidator`) only covers the raw request body. This mirrors the report's root cause of "trusting a field that is not covered by the authentication check": the router-signature covered `transferId`/`pathLength` but not `ExecuteArgs.local`, letting an attacker swap the untrusted field while keeping the signature valid. Here, the HMAC covers only `@raw_body`, while `shop`/`topic` headers used downstream for tenant/topic routing are left completely unauthenticated.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`: [2](#0-1) 

Meanwhile, `Registry.process` trusts `request.shop` and `request.topic` — both sourced from headers, not from the signed body — to dispatch the webhook and populate `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers: [4](#0-3) 

The equality that should hold is: `shop_used_by_handler == shop_that_actually_generated_the_signed_body`. Because the HMAC signature is computed only over the JSON body and never binds the `shop-domain` header, an attacker can take a **genuine, validly-signed webhook body** (obtainable by installing the app on their own store — an unprivileged action any merchant can perform) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to name a different (victim) shop. `HmacValidator.validate` will still return `true`, because it only re-derives the HMAC from `@raw_body`, which is unchanged. `Registry.process` will then hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop, even though the payload actually originated from, and describes, the attacker's own store.

This is the direct analog of the Connext finding: the signature (`HMAC`) authenticates a payload, but a field that downstream logic uses for identity/tenant routing (`ExecuteArgs.local` there, the `shop`/`topic` headers here) is excluded from what's signed, letting the attacker splice authenticated bytes with unauthenticated identity claims.

### Impact Explanation
Host applications built on this gem typically use `WebhookMetadata#shop` to key persistence, cache invalidation, or business logic per-tenant (e.g., "update product data for shop X"). Because that field is unauthenticated, an attacker who is a legitimate account holder of the app on their own store can forge webhook deliveries that the host app will process as if they came from an arbitrary victim shop, injecting attacker-controlled data (fake order/product/inventory events, uninstall notifications, etc.) into another tenant's data pipeline. This is a cross-tenant data-integrity/spoofing issue reachable purely with the attacker's own (unprivileged) merchant credentials against the app's public webhook endpoint — no access token, secret, or privileged account for the victim is required.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's `Webhooks::Request`/`Registry.process` without additional binding checks: an attacker only needs (a) to install the target app on their own store to receive one legitimately HMAC-signed webhook, and (b) to POST that captured body to the app's public webhook URL with a modified `shop-domain` header. Both steps require no elevated privilege — only ordinary use of the app as a merchant plus a normal HTTP client capable of setting headers.

### Recommendation
Bind the identity fields to the signature instead of trusting bare headers:
- Include `shop`, `topic`, and `webhook_id`/`api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that tampering with these headers invalidates the HMAC.
- Alternatively/additionally, require host applications to cross-check `request.shop` against the shop associated with the currently registered session/webhook subscription before dispatching to a handler, rather than trusting the header verbatim.
- Document clearly (and enforce in `Registry.process`) that `shop`/`topic` are not authenticated by the HMAC today, so integrators are not misled into treating them as trusted identity claims.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store (`attacker-shop.myshopify.com`) and triggers a webhook event (e.g., `orders/create`). Shopify delivers a POST to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures the raw body and the valid HMAC header value.
3. Attacker replays the same raw body and HMAC to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally changes `x-shopify-topic`/`x-shopify-webhook-id`).
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`, which calls `HmacValidator.validate(request)`: [5](#0-4) 
   Since `to_signable_string` returns only `@raw_body` (unchanged), validation succeeds despite the spoofed shop header.
5. `handler.handle` receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"`, even though the body content and origin were the attacker's own store — demonstrating the cross-tenant spoofing.
