The gem's docs explicitly instruct developers to trust `data.shop` from the webhook handler, `docs/usage/webhooks.md:14` states `shop`, `String` - The shop domain of the webhook and shows a documented usage pattern (`shop_domain: data.shop`) to route work to a merchant's tenant record, while the actual HMAC signature only ever covers the raw JSON body.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` never authenticates the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic` / `X-Shopify-Webhook-Id`) header. An attacker who owns any shop where the merchant's app is installed can capture a legitimate, validly-signed webhook payload sent by Shopify to their own endpoint, then replay that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop's domain. The gem accepts it as valid and hands the forged `shop` value straight to the host application's webhook handler as trusted tenant data.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` purely from HTTP headers: [1](#0-0) 

But the value actually signed and verified is only the raw body: [2](#0-1) 

`Registry.process` validates the HMAC and, once it passes, forwards `request.shop` (the unauthenticated header) into `WebhookMetadata`, which is delivered to the app's registered handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unguarded field: [4](#0-3) 

The gem's own docs instruct developers to use `data.shop` as the authoritative tenant identifier to route webhook processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is the gem's documented, intended usage — not host-app misuse.

The break in identity binding, stated as an equality:
`shop authenticated by HMAC == shop stored in the header trusted by the handler`
does not hold, because the HMAC is computed only over `@raw_body`, never over the `shop-domain`/`topic`/`webhook-id` headers.

### Impact Explanation
This allows cross-tenant confusion: an attacker who legitimately installs the target app on their own shop (or a free Shopify dev/partner store) receives real, correctly-signed webhooks from Shopify for events on their own store. By replaying the identical body and HMAC signature to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim merchant, the attacker can inject fabricated (but validly-"signed") data that the host app associates with the victim's tenant record, since `HmacValidator.validate` returns `true` for the replayed request. Depending on the topic (e.g. `app/uninstalled`, `customers/data_request`, `shop/update`, order/customer webhooks), this can corrupt or exfiltrate cross-tenant data, trigger unauthorized state changes (like faking an uninstall or a customer redaction event) for a shop the attacker does not control — meeting the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high: no secrets, access tokens, or `client_secret` are needed. The attacker only needs a shop where the target app is installed (attainable via a self-serve/free Shopify dev store for many apps) and the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint, which is by design a public, unauthenticated endpoint (Shopify calls it directly).

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the signable payload used for HMAC verification (or otherwise cryptographically bind them, e.g. via the parsed body's own `shop_id`/`myshopify_domain` fields verified against the header), rather than relying on the header value being implicitly trustworthy. At minimum, document, prominently, that `data.shop` is unauthenticated header data and must not be trusted without a separate cross-check (e.g. verifying against an authenticated session/shop already on file), and encourage handlers to check the webhook against a per-shop webhook_id/topic uniqueness map obtained from an authenticated source.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`. Shopify sends a real webhook, e.g. `orders/create`, to the app's callback URL with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker intercepts/replays this exact request to the same endpoint, keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and compares to `H` — this succeeds because `B` and `H` were not modified: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, and the host app (following the gem's documented pattern) processes this as a genuine event for `victim.myshopify.com`.
