### Title
RAY value overflow before index cap permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large market can reach a state where ordinary interest accrual panics while unscaling aggregate debt before the borrow-index cap can engage. Once reached, every subsequent operation that accrues that market repeats the panic, permanently freezing withdrawals, repayments, liquidations, and index updates.

### Finding Description
`accrue_step` computes `borrowed_original = scaled_to_original(borrowed, borrow_index)` before calculating or clamping the next borrow index. [1](#0-0)  `scaled_to_original` delegates to `Ray::mul`, which panics with `MathOverflow` when the resulting RAY value does not fit in `i128`. [2](#0-1) [3](#0-2) [4](#0-3) 

The static `MAX_BORROW_INDEX_RAY` clamp is applied only inside `update_borrow_index`, after the vulnerable unscale has already succeeded. [5](#0-4)  Therefore, a market whose scaled debt is large enough can overflow the debt-value calculation at an index far below the intended index cap.

The controller exposes `update_indexes(caller, assets)` as a permissionless entrypoint, and it forwards the listed markets to pool accrual. [6](#0-5) [7](#0-6)  Pool mutations also load and accrue each touched market before applying the operation, so ordinary `withdraw`, `repay`, liquidation, and related paths hit the same accrual panic. [8](#0-7) 

### Impact Explanation
Once `borrowed * borrow_index / RAY > i128::MAX`, `last_timestamp` is never advanced because `mark_accrued` is unreachable after the panic. [9](#0-8)  Retrying later cannot recover the market: elapsed time remains positive and the same overflowing unscale runs again.

The existing regression test demonstrates that `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`; its comment also records that liquidation cannot proceed. [10](#0-9)  This is permanent freezing of supplier and borrower funds in the affected market.

### Likelihood Explanation
The condition requires an unusually large aggregate market and enough accrued index growth, but it can be reached through ordinary `supply`, `borrow`, and permissionless `update_indexes` calls when configured caps and utilization admit the position size. [11](#0-10) [6](#0-5)  The protocol documentation acknowledges that admitted caps and bounded indexes do not guarantee that accrued market values remain representable. [12](#0-11) 

The likelihood is constrained by the capital and market-cap prerequisites rather than by any privileged authorization requirement, making this a Medium-severity availability failure.

### Recommendation
Enforce a per-market index ceiling derived from the largest representable value:

```text
max_safe_index <= floor(i128::MAX * RAY / max(supplied, borrowed))
```

Before calling `scaled_to_original`, detect that the current scaled total cannot safely grow further and pin the relevant index at a market-specific safe ceiling. Alternatively, use a widened/saturating value representation for utilization and reward calculations, then explicitly preserve an exit path that allows repayments, withdrawals, and liquidations without requiring further value growth.

### Proof of Concept
For an 18-decimal borrowable market `debt_key` whose configured caps admit the amount, a single funded caller can execute:

```text
supply(attacker, 0, spoke_id,
       [(debt_key, 1_000_000_000 * 10^18)])
    -> supply_account_id

supply(attacker, 0, spoke_id,
       [(collateral_key, sufficient_collateral)])
    -> borrower_account_id

borrow(attacker, borrower_account_id,
       [(debt_key, 980_000_000 * 10^18)],
       None)
```

After sufficient ledger-time accrual, any caller triggers the freeze with:

```text
update_indexes(attacker, [debt_key])
```

The checked-in scenario uses 1 billion 18-decimal units supplied and 98% borrowed, advances time until accrual fails, verifies that the borrow index is still below `MAX_BORROW_INDEX_RAY`, and then verifies that both withdrawal and repayment fail with `MathOverflow`. [13](#0-12)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
