### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via header substitution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's HMAC signature exclusively from the raw request body, while the tenant-identifying `shop` value is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` trusts this `shop` value and forwards it directly to the app's handler, breaking the equality that should hold: `bytes verified by HMAC == bytes used to bind the request to a shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` (used by `Registry.process`) only calls `to_signable_string`, so it verifies the body bytes but never the shop header: [3](#0-2) 

`Registry.process` then validates the HMAC and, once it passes, immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the webhook signing secret (`Context.api_secret_key` / the app's `client_secret`) is the same for every shop that installs the app, an attacker who installs the app on their own Shopify store receives genuine, validly-signed webhooks for that store. Since the HMAC covers only the JSON body, the attacker can replay that captured request unmodified except for the `x-shopify-shop-domain` header value — swapping it for a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` because the (unchanged) body still matches the (unchanged) signature; `Registry.process` will then call `handler.handle` with `data.shop` set to the victim's domain.

The equality that is broken: **HMAC-verified bytes (`raw_body`) ≠ bytes trusted for tenant identity (`shop` header)**. Any app handler that uses `data.shop` to decide which merchant's stored session/data to act on (the documented and expected usage pattern, see `docs/usage/webhooks.md`) can be tricked into performing actions attributed to, or against, a shop the attacker does not control.

### Impact Explanation
This is a cross-tenant confusion vector: an unprivileged attacker (merely a merchant installing the same public app on their own store) can forge webhook deliveries that the library reports as authentic for an arbitrary victim shop domain, without needing the app's `client_secret`, an access token, or any privileged access. Downstream logic that keys off `WebhookMetadata#shop` (as recommended in the gem's own documentation) can be corrupted with attacker-chosen shop identity, meeting the cross-tenant access bar.

### Likelihood Explanation
Requires only: (1) attacker installs the app on a shop they control to receive one legitimately-signed webhook payload, (2) attacker resends the same body to the app's webhook endpoint with a modified `shop-domain` header. No secret material or elevated privilege is required, and the whole verification surface is `ShopifyAPI::Utils::HmacValidator` + `ShopifyAPI::Webhooks::Registry.process`, which is exactly the code path this gem exposes to hosting apps.

### Recommendation
Include the shop-domain header (and ideally api-version/topic) in the signable string, or otherwise cryptographically bind the extracted `shop` value to the HMAC-verified content, e.g., append shop/topic to `to_signable_string` or require callers to double-check `shop` against `Session` state already associated with the specific webhook subscription rather than trusting the header value that ships with each request.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; Shopify delivers a real webhook, e.g. `orders/create`, signed with the app's `client_secret`:
   - Headers: `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
2. Capture this request.
3. Resend the exact same body `B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the signature over `B` only (`Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`) — matches, returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app handler with `data.shop == "victim.myshopify.com"`, even though the payload actually originated from, and was signed for, the attacker's own shop.
