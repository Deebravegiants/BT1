### Title
POA bridge `findMatchingWithdrawal` matches by `assetId` only, causing identical-asset withdrawals to report the same completion tx hash - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`createWithdrawalIdentifiers` assigns a per-route `index` to each withdrawal, but `PoaBridge.describeWithdrawal` never uses that index; it resolves the withdrawal record purely via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`. When a caller submits two `withdrawalParams` entries with the same `assetId` routed to PoA bridge in one `intentTx`, both `WithdrawalIdentifier`s (index 0 and 1) resolve to the same matched record, so `watchWithdrawal` returns the identical `{hash}` for both entries in `sdk.createWithdrawalCompletionPromises`.

### Finding Description
Broken equality: `hash(wid_0)` should correspond only to withdrawal 0's actual on-chain payout, and `hash(wid_1)` only to withdrawal 1's — but both resolve to the same POA API record.

Code path:
- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) increments a counter per `bridge.route` and stamps `wid.index`, but this index is purely informational for `PoaBridge`. [1](#0-0) 
- `PoaBridge.createWithdrawalIdentifier` copies the `index` field into the `WithdrawalIdentifier` but never uses it for matching later. [2](#0-1) 
- `PoaBridge.describeWithdrawal` looks up the withdrawal by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` — matching solely on `assetId`, explicitly ignoring `index`. [3](#0-2) 
- `findMatchingWithdrawal` itself documents the limitation: "multiple withdrawals of the same token in a single transaction are not supported." [4](#0-3) 
- `watchWithdrawal` (`withdrawal-watcher.ts:20-78`) returns `{hash: status.txHash}` once `describeWithdrawal` reports `"completed"`, with no awareness that the same underlying record was already consumed by another `wid`. [5](#0-4) 
- `sdk.createWithdrawalCompletionPromises` (`sdk.ts:557-608`) creates one `watchWithdrawal` promise per `withdrawalParams` entry independently, so both promises call `describeWithdrawal` with the same `assetId` and both get the same matched record/hash. [6](#0-5) 

Root cause: the upstream POA bridge status API itself does not disambiguate multiple same-asset withdrawals within one transaction (the response list is "unsorted" and keyed by asset, not index), and the SDK's matching logic inherits this limitation rather than working around it. The same limitation is independently documented in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:135-152`, used by a separate legacy status-check path.

Attacker/caller input: submit `withdrawalParams` (a normal SDK parameter forwarded by an integrator, not a privileged call) containing two entries with identical `assetId` (both PoA-routed), e.g. two withdrawals of the same NEP-141 token to different destination addresses, within the same intent transaction.

Exploit flow: once the transaction executes and the POA bridge processes withdrawal #1 as `COMPLETED` (assigning it a `transfer_tx_hash`), `describeWithdrawal` for *both* wid entries returns that same completed record and hash, even while the second (real) transfer might still be pending or even before it is broadcast at all.

Existing guard failures: `supports()`, `validateWithdrawal`, `compareAddresses`, `FeeExceedsAmountError`, and the nonce/signature checks in the intents contract are all unrelated to this cross-withdrawal matching problem and do not prevent it, since the divergence happens purely in the off-chain status-polling/matching logic, not in the on-chain intent execution or authorization path.

### Impact Explanation
No funds are misrouted and no signature is replayed at the on-chain level — the two distinct withdrawal intents are still correctly signed, sent, and executed with their own destinations/amounts. The vulnerability is a **status/hash misreport**: the SDK's off-chain completion tracking causes an integrator's client code to believe withdrawal #2 landed at the same destination tx hash as withdrawal #1, when in fact withdrawal #2's actual hash was never independently confirmed. This matches the **High** category ("a status or hash misreport making an integrator credit or refund twice"), not Critical — no funds move that weren't authorized, and no signature is executed twice on-chain.

Repeatable: any caller can trigger it every time they batch two or more same-`assetId` PoA-routed withdrawals in a single call to `createWithdrawalCompletionPromises` (via `sdk.ts`).

### Likelihood Explanation
Preconditions: both withdrawals must route through `PoaBridge` (same `assetId`, not migrated to Omni bridge, `RouteEnum.PoaBridge`) and be submitted together in one call. This is a routine feature usage pattern (batch withdrawals of the same token), not an obscure edge case, and costs the caller nothing beyond constructing normal withdrawal params. The code's own comments acknowledge the API limitation, indicating the authors are aware but have not fully mitigated the reporting-side risk to callers of `createWithdrawalCompletionPromises`.

### Recommendation
Either detect and reject/warn on duplicate same-`assetId` PoA-bridge withdrawals batched in a single `withdrawalParams` array before creating completion promises, or extend `findMatchingWithdrawal` to disambiguate by sorting withdrawals and params by amount (as the code comment already suggests) instead of relying purely on `assetId`. At minimum, `watchWithdrawal`/`describeWithdrawal` should track already-consumed API records per intent tx so a second same-asset `wid` cannot resolve to a record already attributed to another `wid`.

### Proof of Concept
Vitest plan (mocking only the POA bridge HTTP client):
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to return a single withdrawal record: `{ data: { near_token_id: "usdc", transfer_tx_hash: "0xHASH" }, status: "COMPLETED" }` for a given `withdrawal_hash`.
2. Construct two `withdrawalParams` entries with identical `assetId: "nep141:usdc.omft.near"`, different `destinationAddress`, both routed to `PoaBridge`.
3. Call `createWithdrawalIdentifiers({ bridges: [poaBridge], withdrawalParams, intentTx })`, assert `wids[0].wid.index === 0` and `wids[1].wid.index === 1` (indexes differ).
4. Call `watchWithdrawal({ bridge: poaBridge, wid: wids[0].wid })` and `watchWithdrawal({ bridge: poaBridge, wid: wids[1].wid })`.
5. Assert both resolve to `{ hash: "0xHASH" }` — i.e. `promise0.hash === promise1.hash` despite `wid.index` differing and `withdrawalParams[0] !== withdrawalParams[1]`, demonstrating the STATUS TRUTH equality (`reported hash for withdrawal i == outcome of withdrawal i, once each`) is broken.

				txHash: withdrawal.data.transfer_tx_hash,

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
