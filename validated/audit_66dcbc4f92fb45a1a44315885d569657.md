### Title
Webhook HMAC only signs the raw body, letting the trusted `shop` (tenant) field be forged across tenants - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header, while `to_signable_string` (the value that is actually HMAC-verified) returns only the raw request body. `ShopifyAPI::Utils::HmacValidator.validate` therefore proves nothing about the `shop` (or `topic`) header — it only proves the body bytes were signed with the app's shared client secret. `ShopifyAPI::Webhooks::Registry.process` nonetheless forwards this unauthenticated `shop` value straight into `WebhookMetadata`, which apps use as the tenant/session key for the webhook. This is the same class of bug as the report: a field that is acted on (the tenant identity `shop`) is not covered by the authentication mechanism (HMAC), so the "verified" and "trusted" identities diverge.

### Finding Description
The webhook verification chain is: [1](#0-0) 

`to_signable_string` — the only value fed into the HMAC check — is just the raw body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` and compares it to the `hmac` header, never touching `shop` or `topic`: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches using the unauthenticated `request.shop` / `request.topic` values as the tenant identity handed to the app's handler: [4](#0-3) 

Because every merchant/app-install shares the same `client_secret` (the app's secret, not a per-shop secret), any tenant that has the app installed can obtain a validly-HMAC'd `(raw_body, hmac)` pair for their own shop, then replay that exact pair to the same webhook endpoint while substituting the `shop-domain` (and/or `topic`) header for a different, victim tenant. `HmacValidator.validate` still returns `true` because the signature only ever covered the body, and `Registry.process` will happily deliver `WebhookMetadata` labeled with the victim's shop and attacker-controlled body content.

This mirrors the report's bug class precisely: the equality that should hold is `authenticated_identity == identity_used_for_dispatch`, i.e. `shop_covered_by_hmac == shop_used_by_registry.process`. Here, `shop` is never part of the signed bytes, so the equality is false — the identity used to key/dispatch the webhook is not the identity the HMAC actually authenticates.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), which is explicitly a Critical-severity impact category. An attacker who is merely an installer of the app on their own (even free/dev) store — an "unprivileged" tenant relative to other merchants — can inject arbitrary attacker-controlled webhook payloads that are attributed to a different, victim shop. Any host application that follows this gem's own `WebhookMetadata#shop` field as the tenant/session key (the documented usage pattern for this library) will process or persist attacker data under the victim's identity.

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem: the only prerequisite is the ability to install the app as any tenant (trivial via a free Shopify partner/dev store) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers — both are unprivileged-internet-user capabilities requiring no leaked credentials, access tokens, or `client_secret`.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed content, or independently verify that the `shop` header corresponds to a shop that is actually registered/installed for this app instance before trusting it as a dispatch key in `ShopifyAPI::Webhooks::Registry.process`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by host applications against their own installed-shop records before being used as a session/tenant key.

### Proof of Concept
1. Attacker installs the target app on their own (e.g. free/dev) store `attacker.myshopify.com`. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `client_secret`, and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this `(raw_body, hmac)` pair (they own the store/data, so this requires no interception of anyone else's traffic).
3. Attacker crafts a new POST to the same webhook endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-store.myshopify.com` (any other merchant using the same app) and, if desired, a different `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `to_signable_string` (the unchanged raw body) and it matches, so validation passes despite the spoofed shop.
5. `ShopifyAPI::Webhooks::Registry.process` looks up the handler for the (attacker-chosen) topic and invokes it with `WebhookMetadata.new(topic: ..., shop: "victim-store.myshopify.com", body: attacker_body, ...)`.
6. The host app's handler processes/stores the attacker-controlled payload under `victim-store.myshopify.com`, achieving cross-tenant data injection despite a "valid" HMAC check.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
