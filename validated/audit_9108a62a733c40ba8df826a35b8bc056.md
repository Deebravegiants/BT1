## Analysis

The eBTC report describes a class of bug: **a signature-based (EIP-2612-style) permit/approval scheme where the owner has no way to proactively invalidate an outstanding signed permit** other than waiting for its `deadline` to pass — revoking the resulting approval doesn't help if the signature is later replayed.

Searching the Polkadot SDK codebase, the closest and directly analogous mechanism is the ERC20Permit-compatible `permit` pallet used by `pallet-assets` precompiles (EVM-facing `permit()` support), which implements the exact same EIP-2612 pattern (owner signs an off-chain message, a nonce is stored per `(verifying_contract, owner)`, and `permit()` consumes it by incrementing the nonce).

### Root cause
`Nonces` storage tracks a nonce per `(verifying_contract, owner)` pair [1](#0-0) , and the only way this nonce advances is inside `use_permit`, which first verifies a submitted signature and only then calls `increment_nonce` [2](#0-1) . `increment_nonce` itself is a plain, non-authenticated helper that merely bumps the counter [3](#0-2) , but it is never exposed as a standalone, owner-invocable operation — it is only reachable indirectly through a valid `permit()` signature check.

This means: if an owner signs a permit with a far-future `deadline` (as EIP-2612/ERC20Permit tooling commonly encourages) and later decides they no longer want that permit to be redeemable (e.g., they mistakenly signed it, or fear it was leaked/intercepted), **there is no self-service function to bump their own nonce and invalidate it**. The signature remains valid and redeemable by anyone holding it until its `deadline` elapses — exactly the vulnerability class flagged in the eBTC report (`increaseNonce()` was the recommended remediation there).

### Comparison to the report
- eBTC: `_nonces[msg.sender]` can only advance via `permit()` itself; recommended fix added a nonce-bump function.
- polkadot-sdk `permit` pallet: `Nonces` can only advance via `use_permit` (i.e. through `permit()`); there is no equivalent nonce-bump entry point exposed to the owner.

I was not able to fully enumerate the precompile's dispatch table (`lib.rs` selector matching for `nonces()`, `DOMAIN_SEPARATOR()`, `permit()`, etc.) within the available search budget, so I cannot confirm with certainty whether any additional "cancel"/"increaseNonce"-style selector has been added elsewhere in the precompile surface that I didn't locate. Given the code I did inspect, no such function exists in `permit.rs`, and `permit_tests.rs`/`permit_precompile_tests.rs` (which extensively test replay protection, deadline handling, and asset-rename invalidation) contain no test for an owner-initiated nonce bump, which suggests this capability was not implemented.

### Title
Owners cannot proactively invalidate an outstanding `ERC20Permit`-style signature before its deadline - (File: `substrate/frame/assets/precompiles/src/permit.rs`)

### Summary
The `permit` pallet backing the pallet-assets EVM precompile's EIP-2612 `permit()` implements the standard "sign off-chain, redeem on-chain" nonce scheme, but exposes no function letting an owner voluntarily advance their own nonce to invalidate a permit signature that has not yet been redeemed.

### Finding Description
`Nonces::<T>` is a double map keyed by `(verifying_contract, owner)` [4](#0-3) . The nonce only advances inside `use_permit`, after signature/deadline verification succeeds [5](#0-4) . `increment_nonce` is a bare, unauthenticated helper called only from that flow [3](#0-2) . There is no owner-gated "revoke"/"increase-nonce" entry point analogous to the eBTC fix's `increaseNonce()`, so a permit signed with a long-dated deadline remains redeemable by any holder of that signature until it either expires or is consumed — the owner cannot cut it off early.

### Impact Explanation
An owner who signs an off-chain permit (common UX pattern to let a dApp/relayer submit an approval on their behalf) and later wants to withdraw that authorization (e.g. suspecting the signed message was intercepted, or simply changing their mind before the relayer submits it) has no way to do so short of waiting for `deadline` to pass. Because permits commonly carry long-dated deadlines for UX convenience, this creates a window where a leaked/mis-issued signature can be submitted at any time regardless of the signer's intent, similar in kind (though the pallet-assets precompile scopes only ERC-20 style allowances, not full "close position" style custody as in the original eBTC/BorrowerOperations report) to the invalidation gap identified in the external report.

### Likelihood Explanation
Reachable by any unprivileged user who has ever signed a permit message: exploitation requires only that (a) the owner signed a permit with a future deadline, and (b) that signature becomes exposed or is no longer wanted, at which point any party who obtains it can still redeem it. No privileged role is required to trigger the underlying gap — it is a missing defensive control rather than a directly attacker-triggerable exploit, so likelihood depends on external leakage of a signed permit message, which is a realistic condition given permits are transmitted off-chain to relayers/dApps.

### Recommendation
Add a public, owner-authenticated function (dispatched via extrinsic or exposed through the precompile ABI) that lets an account explicitly bump its own nonce in `Nonces::<T>` for a given `verifying_contract`, invalidating any outstanding unredeemed permit signed under the old nonce — mirroring the `increaseNonce()` remediation adopted for the eBTC contracts.

### Proof of Concept
1. Owner signs an EIP-712 `Permit(owner, spender, value, nonce=0, deadline=<far future>)` message off-chain and hands it to a relayer/dApp to submit later.
2. Owner has a change of heart / suspects leakage and wants to invalidate the permit before it's submitted.
3. Owner has no available call path to bump `Nonces::<T>` for `(verifying_contract, owner)` — inspecting `permit.rs`, the only nonce mutation path is `use_permit`, gated behind successful verification of an actual signature [2](#0-1) .
4. The relayer submits the original signature at any point before `deadline`; `use_permit` succeeds because the nonce (`0`) still matches, and the approval is granted despite the owner's intent to prevent it.

		H160, // owner ethereum address
		U256, // nonce (EIP-2612 uses uint256)

		/// Increment the nonce for an owner on a specific verifying contract.
		/// Returns the new nonce value, or an error if overflow would occur.
		pub fn increment_nonce(verifying_contract: &H160, owner: &H160) -> Result<U256, Error<T>> {
			Nonces::<T>::try_mutate(verifying_contract, owner, |nonce| {
				*nonce = nonce.checked_add(U256::one()).ok_or(Error::<T>::NonceOverflow)?;
				Ok(*nonce)
			})
		}

			spender: &H160,
			value: &[u8; 32],

			s: &[u8; 32],

				name,
				owner,
				spender,
				value,
				deadline,
				v,
				r,
				s,
			)?;
