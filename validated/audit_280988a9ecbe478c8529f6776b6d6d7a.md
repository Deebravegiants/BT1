### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` covers exclusively the JSON body. The `shop` (and `topic`/`api_version`/`webhook_id`) values are read straight from HTTP headers and are never included in the signed bytes. `Registry.process` still forwards the header-derived `shop` into the app-facing `WebhookMetadata` as the tenant identifier, so the field that downstream code uses to route/attribute a webhook to a merchant is unauthenticated.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` only, while `shop` is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` for constructing the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) using the app's global `client_secret` (`Context.api_secret_key`), which is the same secret for every shop that has this app installed: [4](#0-3) 

Because the secret is shared across all tenants of the app and the shop header is excluded from the signed content, the binding the gem is supposed to enforce is:
`shop value trusted by the handler == shop value cryptographically bound to the signed bytes`

but in reality it is only:
`shop value trusted by the handler == shop value copied verbatim from an unauthenticated header`

An attacker who is simply a merchant running the same app on their own shop (an "unprivileged internet user" from the app's perspective — they hold no special credential, just a legitimate webhook delivery to their own store) can capture one genuine webhook delivery (raw body + valid `x-shopify-hmac-sha256`), then replay the identical body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different shop that also uses the app. `HmacValidator.validate` still returns `true` because the signed bytes (the body) are unchanged and were signed with the same app-wide secret; `Registry.process` then hands the handler a `WebhookMetadata` whose `shop` is the attacker-chosen value, not the shop that actually produced the payload.

### Impact Explanation
This breaks the tenant-isolation boundary that host applications rely on the gem to enforce: any downstream logic that uses `WebhookMetadata#shop` to decide which merchant's records to update, look up an access token for, or attribute an event to, can be made to act on the wrong tenant's identity using otherwise-valid webhook content. This matches the "Critical - cross-tenant access" impact category, since it allows a request that is provably genuine (valid HMAC) to be misattributed to an arbitrary victim shop that also installed the app.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop has the target app installed (a normal, unprivileged position for any merchant/developer to be in) and the ability to send arbitrary HTTP requests to the app's publicly reachable webhook endpoint — no access token, `client_secret`, or session hijacking is needed. The bug is fully within `shopify_api`'s own webhook-processing code path (`Request`/`Registry`), not a misuse of an undocumented API, since the gem itself performs the HMAC check and constructs `WebhookMetadata#shop` from the header.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values into the signed payload, or otherwise cryptographically tie the header claims to the verified body, before exposing them to `WebhookMetadata`/the app handler — e.g., include the shop domain in `to_signable_string`, or require the host application to cross-check `data.shop` against a shop/token record it independently owns before trusting it. Document explicitly (more prominently than the current webhooks doc) that `data.shop` is *not* covered by the HMAC and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — this signature depends only on `B`, not on the shop header, per [1](#0-0) .
3. Attacker captures this raw request and resends it to the same endpoint, keeping `body=B` and `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and succeeds, per [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, per [6](#0-5)  and [7](#0-6) , causing the app to process attacker-controlled content as if it originated from the victim's shop.
