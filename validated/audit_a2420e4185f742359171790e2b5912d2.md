### Title
Silent truncation instead of abort when the "parabola invariant" breaks in `_prepareGraduationLiquidity` mis-prices the graduation LP - (`packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._prepareGraduationLiquidity` computes the exact `tokensForLP`/`ltFromPair` pair that is supposed to make the graduated HyperSwap V2 pool open at precisely the bonding curve's closing price. The code assumes, as a "mathematical" invariant, that `tokensForLP` can never exceed `LP_RESERVE` (250M), so instead of treating a breach as fatal it silently clamps the value and proceeds: [1](#0-0) 

This mirrors the CVE-2025-39800 bug class: an assumption about internal state ("generation must match") is checked, but on violation the code merely tolerates it (`WARN_ON` in btrfs; a silent clamp here) instead of aborting the operation, letting corrupted/inconsistent state persist and be committed.

### Finding Description
`tokensForLP` and `ltFromPair` are meant to satisfy the price-parity identity documented in `packages/contracts/src/Bonding.sol` and `docs/contracts-scope.md`:

`tokensForLP / ltFromPair == tokenReserve / assetReserve` (the curve's closing marginal price). [2](#0-1) 

The code justifies the `if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;` cap as "defensive" because the parabola `tokensForLP(sold) = sold·(S−sold)/S` peaks exactly at `S/4 = LP_RESERVE` when `sold = S/2` — a value that sits inside the reachable `sold` domain `[0, curveSupply]` (`curveSupply = 750M > S/2 = 500M`), so the peak is reachable, not just a theoretical asymptote.

The reserves that feed this formula, however, are not pure continuous math — they are the product of `Router._computeBuy` / `_computeSell`, both of which use floor division when converting between LT-in and tokens-out: [3](#0-2) [4](#0-3) 

Every buy computes `tokensOut = reserveToken - (k / newReserveAsset)`, floor-rounded, so each trade removes strictly fewer real tokens from `reserveToken` than the exact continuous parabola would for the same LT raised. This rounding bias is systematic and one-directional (always leaves `reserveToken` marginally *higher*, i.e. `sold` marginally *lower*, than the ideal curve for the same `assetReserve`). It compounds with trade count — an actor who fragments buys into many small transactions (still cheap on HyperEVM) accumulates this bias far more than a single large buy reaching the same `assetReserve`. Because the parabola's cap at `LP_RESERVE` is achieved exactly at `sold = S/2`, and the rounding bias systematically understates `sold` relative to `assetReserve` raised, a sequence of many small buys that lands the curve's `assetReserve` near the threshold that would ideally correspond to `sold ≈ S/2` can push the *computed* `tokensForLP = ltFromPair·reserveToken/assetReserve` above `LP_RESERVE`, tripping the "impossible" cap.

When that happens, `_prepareGraduationLiquidity` does not abort — it silently rewrites `tokensForLP` down to `LP_RESERVE` while `ltFromPair` (derived independently from the real, donation-immune LT raised, `assetReserve - virtualLtReserve`) is left untouched: [5](#0-4) 

This breaks the price-parity identity the whole "zero price gap" design depends on (`docs/contracts-scope.md` invariant #1, "Zero price gap"). The resulting `PendingGraduation` values are cached and consumed verbatim two transactions later by the permissionless `finalizeGraduation`, which mints the actual HyperSwap V2 LP at the now-mispriced ratio: [6](#0-5) 

Because `finalizeGraduation` is permissionless and has no staleness/re-check gate by design ("no freshness timestamp / staleness gate… re-pricing… would break the invariant"), any attacker who has engineered the rounding drift can call `finalizeGraduation` (or wait for the keeper to) and then immediately swap against the newly seeded, off-curve-price HyperSwap pool to extract the price gap risk-free, at the expense of the locked LP (ultimately the token's buyers/creator whose curve-raised LT/tokens back that LP).

### Impact Explanation
An LP seeded away from the true curve-close price is a direct, permanent value transfer out of protocol-controlled, `LPLock`-locked liquidity (which has no withdraw path in v1) to whichever address arbitrages the freshly created pool first. This satisfies the "LP seeded away from the curve close price" impact class explicitly called out as in-scope, and is realized purely through unprivileged, permissionless calls (`Zap.buy` repeated many times, then `finalizeGraduation`).

### Likelihood Explanation
The precondition — accumulating floor-rounding drift across many small buys until the graduation trigger fires with `sold` near `S/2` — is achievable by a single unprivileged trader who fragments a graduation-crossing buy into many minimal-size buys (bounded below only by the LT's `minTransactionSize`) rather than one large buy. No special role, timing race against other users, or off-chain component is required; `triggerGraduation`/`finalizeGraduation` are both explicitly permissionless. The magnitude of the mispricing per graduation is bounded by rounding dust order-of-fee-unit size, but it is deterministic and repeatable across every token launch, and the cap is meant by the authors to be literally unreachable ("mathematically invariant... not a runtime guess"), meaning there is currently zero test/defense coverage validating behavior once it is hit.

### Recommendation
Replace the silent clamp with an abort: if `tokensForLP > LP_RESERVE` (or more generally if the computed price-parity identity deviates from the cached reserves beyond a tight rounding tolerance), revert the phase-1 transaction (`_enterGraduating`/`triggerGraduation`) instead of truncating and caching a corrupted `PendingGraduation`. This is the direct analog of the upstream fix: turn the "should never happen" assumption into a hard abort (`revert`) rather than a tolerated/soft-patched value, preventing mispriced state from ever reaching `finalizeGraduation`.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken` with a paired LT.
2. Instead of a single buy that would cross the graduation threshold, submit many minimal-size `Zap.buy` calls (each above the LT's `minTransactionSize` floor) so that `Router._computeBuy`'s floor rounding is applied on every trade, accumulating the systematic understatement of `sold` relative to `assetReserve` raised, until the pair's `sold` lands near `S/2` (i.e., `reserveToken` near `totalSupply/2`) right as the USD or supply graduation trigger fires.
3. Observe (via `previewLtUntilGraduation` / direct reserve reads) that the resulting `tokensForLP = ltFromPair * reserveToken / assetReserve` computed in `_prepareGraduationLiquidity` exceeds `LP_RESERVE` and gets silently clamped instead of reverting.
4. Call `finalizeGraduation` (permissionless) to seed the HyperSwap V2 pool at the clamped, mispriced ratio.
5. Immediately swap against the new pool to extract the price gap, profiting at the expense of the locked LP. [5](#0-4) [3](#0-2)

        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it

        // `_routerDepositAndDispose` and `_sweepLTToOwner`.

        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
