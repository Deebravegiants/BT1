### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` fields are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` only validates the HMAC (which covers the body) before dispatching the handler with these header-derived fields [3](#0-2) , so the tenant-identifying `shop` value handed to the app is never bound to the signature that "proves" the request came from Shopify.

### Finding Description
This is the same class of bug as the external report: a value that is acted upon (there, the ERC777 `credit.deposit` accounting; here, the `shop` field used for tenant routing) is not covered by the integrity check that is supposed to authenticate the whole request (there, no reentrancy guard on state mutation; here, no coverage of headers by the HMAC).

The equality that should hold is:
`bytes_verified_by_hmac == bytes_the_handler_treats_as_authenticated`

In `to_signable_string`, only `@raw_body` is signed [1](#0-0) . But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding to that body [4](#0-3) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string` (i.e., the body) [5](#0-4) , so a valid HMAC only proves "this body was signed by Shopify with my secret" — it says nothing about which shop, topic, or webhook id it was for.

`Registry.process` uses `request.shop` unauthenticated to build `WebhookMetadata` passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [6](#0-5) . The gem's own documentation tells host apps to trust `data.shop` as "The shop domain of the webhook" and to key job/data processing off it directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) . `Registry.process` itself documents that it "will verify the request did indeed come from Shopify" [8](#0-7)  — implying the whole request, including the shop, is verified, which is not the case.

Contrast this with the OAuth callback path in the same gem, where `shop` (along with `code`, `state`, `timestamp`, `host`) is explicitly included in the HMAC-signed query string via `AuthQuery#to_signable_string`/`validate_signature` [9](#0-8)  and tested as such [10](#0-9) . This shows the gem's own design intent is for identity-relevant fields to be part of the signed payload — a guarantee that is absent for webhook headers.

### Impact Explanation
An attacker who has ever received (or can capture) one legitimate, validly-signed webhook body+HMAC pair for any shop that has this app installed (including their own shop, if they can install the app or trigger a webhook for their own store) can replay that exact body/HMAC while substituting the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers to any value they choose. `HmacValidator.validate` will still pass because it only checks the body [11](#0-10) . The forged `shop` value then flows unauthenticated into the app's webhook handler, which per the gem's own documented usage pattern is used to key merchant/tenant-scoped data operations [12](#0-11) . This enables cross-tenant data injection/confusion in any host app that follows the gem's documented pattern of trusting `WebhookMetadata#shop` as an authenticated tenant identifier.

### Likelihood Explanation
Exploitation requires possession of one valid signed webhook body (obtainable from the attacker's own shop, a low bar for any developer/merchant that can install a public app) and knowledge of the target's shop domain (public, e.g. `victim.myshopify.com`). No access to `api_secret_key`, access tokens, or any privileged credential is required. This is a realistic, unprivileged-internet-actor scenario matching the analog rules.

### Recommendation
Include the `shop`, `topic`, and `webhook_id`/`api_version` header values as part of the signed payload used by `to_signable_string` (or otherwise cryptographically bind them, e.g., by hashing headers+body together), and document clearly to host apps that only the body is currently verified, not the tenant-identifying headers, so downstream data operations are not accidentally keyed on unauthenticated input.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and registered for `orders/create` webhooks.
2. Attacker controls `shop-a` (e.g., as its merchant/dev) and captures a legitimate webhook delivery: raw body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B`).
3. Attacker (or any party who can reach the app's public webhook endpoint) replays the request to the same endpoint with the same body `B` and same `H`, but sets `shopify-shop-domain: shop-b.myshopify.com` (the victim tenant) instead of `shop-a.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully [13](#0-12) .
5. `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only recomputes the HMAC over `B` [14](#0-13) .
6. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the attacker-controlled body `B`, even though this data never actually originated from Shopify for `shop-b` [6](#0-5) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
