Audit Report

## Title
Missing `return` after failed email-claim extraction in OIDC token exchange creates an authenticated session bound to an empty user identity - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `handleTokenExchange`, when the ID token's `claims["email"]` field is missing or not a string, the handler logs the error and writes an HTTP 500 body via `c.String`, but omits the `return` statement, so execution continues. The function proceeds to derive an RBAC role from a separate claim, insert a new row into `oidc_sessions` with `user_email = ""`, save the session cookie, and finally write an additional `200 OK` JSON body — resulting in a valid, cookie-backed session tied to no real user identity but a real role.

## Finding Description
The code path is exactly as cited: [1](#0-0) 
This type assertion failure (`ok == false`) is not followed by `return`, unlike every other error branch in the same function which does call `return` after writing an error response (see lines 167-171, 177-183, 189-196, 199-204, 207-212, 215-219, 220-225, 241-245, 266-271 for the pattern that is consistently followed elsewhere but broken here).

Because there's no `return`, execution falls through to role derivation (`IDClaimsToUserRole`, based on the separately configured group claim, not `email`) and then to session creation: [2](#0-1) 
The session cookie is then saved and a `200 OK` success response is returned to the client: [3](#0-2) 

This session, once looked up via `AuthorizedUserWithSession`, returns a `User{Email: "", Role: <derived role>}`, which is accepted by `AuthenticateBySession` as a valid authenticated principal: [4](#0-3) [5](#0-4) 

The OAuth2 config requests the `email` scope by default, but requesting the scope does not guarantee the identity provider actually populates the `email` claim in the ID token for every account (e.g., robot/service accounts, or providers that treat `email` as optional even when the scope is granted): [6](#0-5) 
No other validation in this file rejects an empty/absent email before session creation — the only gate that could stop this flow (the `return` after the log/error write) is absent.

## Impact Explanation
This is a genuine authentication-integrity defect within the in-scope OIDC login flow (`POST` route handled by `handleTokenExchange`, reachable without any prior chainlink credential — the OIDC exchange endpoint is the login mechanism itself). An account on the configured IdP that satisfies role-group claims but lacks a string `email` claim obtains a fully functional, role-scoped chainlink session decoupled from any accountable identity, undermining both audit logging (the `Audit(audit.AuthLoginSuccessNo2FA, ...)` call records an empty email) and the assumption that every session maps to a real user. This falls into the "authentication/role bypass" and "cross-user identity confusion" impact categories.

## Likelihood Explanation
The only precondition is deployment with OIDC authentication enabled (a standard, supported chainlink node configuration, not a misconfiguration) and possession of a valid account on that IdP whose token omits/nulls the `email` claim while still matching one of the configured admin/edit/run/read group claims. This is a plausible real-world scenario for IdPs where `email` is attribute-optional or absent for certain account types. The defect itself is an unconditional code-path bug (missing `return`), not dependent on race conditions, network tricks, or operator/host access — it is deterministically triggered by any request whose token lacks the email claim.

## Recommendation
Add a `return` (or otherwise short-circuit) immediately after detecting a missing/invalid `email` claim:
```go
email, ok := claims["email"].(string)
if !ok || email == "" {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, reject empty-email lookups defensively in `AuthorizedUserWithSession` and `FindUser`, and avoid inserting `oidc_sessions` rows with an empty `user_email`.

## Proof of Concept
1. Stand up a local chainlink node with OIDC auth enabled against a test OIDC provider/mock that issues ID tokens containing group claims satisfying one of `AdminClaim`/`EditClaim`/`RunClaim`/`ReadClaim`, but with the `email` claim omitted or `null`.
2. Perform the standard OIDC login flow: `GET` the sign-in redirect handled by `handleSignIn`, complete provider auth, then `POST /sessions/oidc/exchange` with the resulting `code`/`state`, routed to `handleTokenExchange`.
3. Observe server logs show `"Failed to get email from claims"` yet the HTTP response is still `200 OK` with `{"success": true}`, and a `Set-Cookie` session header is present.
4. Inspect the `oidc_sessions` table (or via `AuthorizedUserWithSession`) to confirm a row with `user_email = ''` and a non-empty `user_role`.
5. Reuse the returned session cookie against an authenticated, role-gated endpoint (e.g., a GraphQL mutation gated by the derived role) via `AuthenticateBySession` and confirm it succeeds despite `Email` being empty — demonstrating a session bound to no real identity but usable for role-authorized actions.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil

// AuthenticateBySession authenticates the request by the session cookie.
//
// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
