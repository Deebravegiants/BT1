### Title
Missing EVM memory-expansion gas surcharge in `Memory::resize` allows cheap, disproportionate memory growth via MSTORE/MLOAD/MSTORE8 - (File: substrate/frame/revive/src/vm/evm/memory.rs)

### Summary
`Memory::resize` in the pallet-revive EVM interpreter only enforces a hard byte cap (`EVM_MEMORY_BYTES`) and performs `Vec::resize`, but never charges the standard EVM memory-expansion gas cost (the quadratic+linear `memory_cost(new_words) - memory_cost(old_words)` formula every real EVM implements). `MLOAD`/`MSTORE`/`MSTORE8` in `substrate/frame/revive/src/vm/evm/instructions/memory.rs` charge only the fixed `EVMGas(VERYLOW)`/`EVMGas(BASE)` opcode cost before calling `resize`, so an attacker-controlled contract can grow memory toward the 1 MiB cap for a nearly constant, fixed per-opcode gas cost instead of the economically-modeled increasing cost.

### Finding Description
`Memory::resize` (substrate/frame/revive/src/vm/evm/memory.rs:66-79) computes `target_len` and only performs a bound check against `crate::limits::EVM_MEMORY_BYTES`, returning `Error::OutOfGas` if exceeded, then does `self.data.resize(target_len, 0)`. No gas or weight is deducted here based on the size of memory growth.

`mload`, `mstore`, and `mstore8` in substrate/frame/revive/src/vm/evm/instructions/memory.rs:31-62 each charge only the flat `EVMGas(VERYLOW)` (or `BASE` for `msize`) opcode cost via `interpreter.ext.charge_or_halt(...)` *before* calling `interpreter.memory.resize(offset, len)`. Unlike `mcopy` (memory.rs:75-96), which at least derives a length-dependent `copy_cost_verylow(len)` for the copy itself (still not a true quadratic memory-expansion charge), `mload`/`mstore`/`mstore8` apply zero size-dependent charge for the memory growth they trigger.

This is a real semantic deviation from the canonical EVM gas schedule, where every memory-touching opcode must pay `memory_expansion_cost` proportional to `(new_words² - old_words²)/512 + 3*(new_words - old_words)` in addition to the opcode's fixed cost. Here that surcharge is entirely absent — an attacker can issue a sequence of `MSTORE` instructions at strictly increasing 32-byte-aligned offsets (e.g., offset = 0, 32, 64, ... up to `EVM_MEMORY_BYTES`) and pay only `VERYLOW` (3 gas) per instruction regardless of how large memory has already grown, all the way to the hard cap.

Reachability: this is directly triggerable by any unprivileged contract caller by deploying/calling an EVM-flavored contract on pallet-revive that executes `MSTORE`/`MLOAD`/`MSTORE8` opcodes with attacker-chosen offsets — no privileged origin, governance, or admin path is required.

### Impact Explanation
Because memory-expansion cost is unbudgeted, the EVM gas charged for growing memory to the maximum permitted size (`EVM_MEMORY_BYTES`, capped in `substrate/frame/revive/src/limits.rs`) is far lower than what canonical EVM gas accounting would charge for the same memory footprint. Since gas is the mechanism by which pallet-revive translates EVM execution into Substrate weight/fees, this creates a gap between charged weight and actual `Vec::resize`/copy work performed per call frame. However, the impact is **bounded**, not unbounded: `Memory::resize` enforces a fixed hard cap (`EVM_MEMORY_BYTES`), so the maximum extra unaccounted work per call frame is capped at that constant (on the order of 1 MiB), and Rust's `Vec::resize`/`reserve` uses amortized-growth reallocation, so the total copy/allocation work to reach the cap is linear in the cap size, not quadratic. The exploitable effect is therefore "cheap access to the maximum allowed EVM memory per call frame," not an unbounded blow-up; the practical amplification vector is stacking many such call frames (e.g., repeated/nested calls), each of which still pays the normal per-call/opcode costs (e.g., `CALL` gas, cold-access surcharges) which are charged independently and are not the subject of this question's scope.

### Likelihood Explanation
Trivial to trigger: any contract caller who can deploy and invoke an EVM contract can construct a loop or straight-line sequence of `MSTORE` opcodes at increasing offsets. No signature/nonce/origin/proxy/multisig checks are relevant or would block this, since it is pure contract bytecode execution. It is fully repeatable per call, per block, by any account with enough balance to pay the (deliberately much lower) gas cost.

### Recommendation
Implement the standard EVM memory-expansion gas formula in `Memory::resize` (or in the callers before invoking `resize`), charging `memory_cost(new_words) - memory_cost(old_words)` (quadratic + linear component, as `revm`'s own `gas::memory_gas`/`calc_memory_size` helpers already provide) via `interpreter.ext.charge_or_halt(EVMGas(...))` prior to or as part of resizing memory, for `MLOAD`, `MSTORE`, `MSTORE8`, and any other memory-touching opcode (`MCOPY`, `CALL`-family, `RETURN`, `REVERT`, `LOG*`, `CREATE*`, `SHA3`/`KECCAK256`, etc.), consistent with upstream `revm`/go-ethereum gas accounting.

### Proof of Concept

1. Construct an interpreter with a fresh `Memory<Test>` and a gas meter tracking consumed `EVMGas`.
2. Execute a sequence of `mstore` calls at offsets `0, 32, 64, ..., EVM_MEMORY_BYTES - 32` (~32768 iterations).
3. Assert `interpreter.memory.size() == EVM_MEMORY_BYTES` after the loop.
4. Assert total gas charged equals `32768 * VERYLOW` (fixed, flat total).
5. Compare against the reference EVM memory-expansion formula's expected total gas cost for growing memory linearly to `EVM_MEMORY_BYTES` (which is substantially higher, quadratic in words).
6. Assert `total_charged_gas < reference_formula_gas_cost`, proving the metering gap; optionally measure wall-clock/allocation counts (e.g., via `Vec` capacity tracking) to show work scales with `EVM_MEMORY_BYTES` while gas charged stays flat/minimal. [1](#0-0) [2](#0-1) [3](#0-2)

	pub fn resize(&mut self, offset: usize, len: usize) -> ControlFlow<Halt> {
		let current_len = self.data.len();
		let target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32;
		if target_len > crate::limits::EVM_MEMORY_BYTES as usize {
			log::debug!(target: crate::LOG_TARGET, "check memory bounds failed: offset={offset} target_len={target_len} current_len={current_len}");
			return ControlFlow::Break(Error::<T>::OutOfGas.into());
		}

		if target_len > current_len {
			self.data.resize(target_len, 0);
		}

		ControlFlow::Continue(())
	}

pub fn mload<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let ([], top) = interpreter.stack.popn_top()?;
	let offset = as_usize_or_halt::<E::T>(*top)?;
	interpreter.memory.resize(offset, 32)?;
	*top = U256::from_big_endian(interpreter.memory.slice_len(offset, 32));
	ControlFlow::Continue(())
}

/// Implements the MSTORE instruction.
///
/// Stores a 32-byte word to memory.
pub fn mstore<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let [offset, value] = interpreter.stack.popn()?;
	let offset = as_usize_or_halt::<E::T>(offset)?;
	interpreter.memory.resize(offset, 32)?;
	interpreter.memory.set(offset, &value.to_big_endian());
	ControlFlow::Continue(())
}

	interpreter.memory.resize(offset, 1)?;
	interpreter.memory.set(offset, &[value.byte(0)]);
	ControlFlow::Continue(())
}

pub fn mcopy<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	let [dst, src, len] = interpreter.stack.popn()?;

	// Into usize or fail
	let len = as_usize_or_halt::<E::T>(len)?;
	// Deduce gas
	let Some(gas_cost) = copy_cost_verylow(len) else {
		return ControlFlow::Break(Error::<E::T>::OutOfGas.into());
	};
	interpreter.ext.charge_or_halt(EVMGas(gas_cost))?;
	if len == 0 {
		return ControlFlow::Continue(());
	}

	let dst = as_usize_or_halt::<E::T>(dst)?;
	let src = as_usize_or_halt::<E::T>(src)?;
	// Resize memory
	interpreter.memory.resize(max(dst, src), len)?;
	// Copy memory in place
	interpreter.memory.copy(dst, src, len);
	ControlFlow::Continue(())
}
