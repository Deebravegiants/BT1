## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. Because the app's `api_secret_key` (the HMAC key) is identical for every shop that installs the app, an attacker who obtains one valid `(body, hmac)` pair — e.g. by installing the app on their own store and capturing a real webhook delivery — can replay that same body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for any victim shop. The signature check still passes because the shop is never part of the signed bytes, breaking the equality `hmac_verified_bytes == bytes_the_handler_trusts_as_shop_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the `hmac` field against `to_signable_string`, i.e. the body — it never incorporates the shop header: [3](#0-2) 

`Webhooks::Registry.process` trusts this unverified `request.shop` value directly when dispatching to the app's handler as the tenant identity: [4](#0-3) 

Since `api_secret_key` (the client secret) is shared across all shops that install a given app — not per-shop — any unprivileged attacker can:
1. Install the target app on their own (attacker-controlled) development shop.
2. Trigger any webhook topic and capture the legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends, which is validly signed with the app's shared secret.
3. Replay that exact body/HMAC pair to the app's webhook endpoint, but swap the `X-Shopify-Shop-Domain` (and optionally `topic`/`webhook-id`) header to reference a victim shop.
4. `HmacValidator.validate` still succeeds because it never checks the shop header, so `Registry.process` invokes the handler with `shop: request.shop` set to the victim's domain.

This breaks the intended binding: *the shop identity acted upon by the handler* should equal *the shop identity covered by the HMAC*, but here the shop identity is attacker-controlled while only the body is authenticated.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler is told an event belongs to shop B when it was actually never sent by Shopify for shop B. Depending on how the host application uses `WebhookMetadata#shop` (e.g. keying data writes, triggering deauthorization on `app/uninstalled`, updating billing/subscription state, or gating per-tenant caches), an attacker can forge events attributed to any other tenant, causing cross-tenant data corruption or state changes — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own (attacker-controlled) shop — a normal, unprivileged action available to any merchant — and be able to POST to the app's public webhook endpoint, which is by design internet-reachable. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) as part of the HMAC-signed material, or independently verify that `request.shop` corresponds to a shop with a legitimately provisioned session/installation before trusting it, rather than relying solely on a body-only HMAC check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) and records the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` in [5](#0-4)  recomputes the HMAC over `B` only and it matches `H`, so validation passes.
5. `Registry.process` dispatches to the app's handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , even though Shopify never sent this event for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
