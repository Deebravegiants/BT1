### Title
Webhook shop identity is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by validating the HMAC over the raw request body only, then hands the shop identity taken from an unauthenticated HTTP header directly to the app's `WebhookHandler` as trusted tenant metadata. The shop value is never included in the signed bytes, so the "shop the HMAC proves the payload came from" and "the shop the handler is told to act on" are two different, independently-controlled values.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is part of `@headers`, not `@raw_body`: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, and then builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and passes it straight to the app-supplied handler as the tenant identifier for the event: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body), confirming the header is outside the signed scope: [4](#0-3) 

Because a single app-wide `api_secret_key` is used to compute the webhook HMAC for every shop that installs the app (there is no per-shop secret — see `Utils::HmacValidator.validate`, which only ever uses `Context.api_secret_key`/`old_api_secret_key`), any merchant who installs the app can obtain a webhook whose HMAC validates correctly for that app. That merchant fully controls the HTTP request they relay to the app's webhook endpoint (e.g. by proxying/replaying a genuine webhook delivered to their own shop) and can rewrite the `shopify-shop-domain` header to name a victim shop, while the HMAC — computed only over the untouched body — still validates. `Registry.process` then dispatches to the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop, breaking the equality `shop authenticated by HMAC == shop delivered to handler`.

### Impact Explanation
This is a cross-tenant identity-binding break inside the gem's own dispatch logic: the field the handler relies on to know which merchant/tenant a webhook event belongs to is not part of the cryptographically verified data. Any host application that follows the documented pattern (using `WebhookMetadata.shop` from `Webhooks::Registry.process` to scope data lookups/writes, e.g. resolving the session/access token for that shop) can be made to process or persist data under the wrong tenant, or trigger tenant-scoped side effects (like the mandatory `shop/redact`/`customers/redact` flows) for a shop the attacker doesn't own — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires installing the app (or otherwise obtaining one authentically-signed webhook payload for any shop) and the ability to replay/forward an HTTP request with a modified header, both of which are available to an ordinary, unprivileged app user — no access token, `client_secret`, or privileged account is needed. The `hmac` check in `Registry.process` gives false assurance that the accompanying metadata (including `shop`) is trustworthy, making this straightforward to exploit for a user who already has legitimate access to the app.

### Recommendation
Bind the shop (and other identity-bearing headers such as `topic`, `api-version`, `webhook-id`) into the signed material, or otherwise cross-check the header-derived shop against an independently authenticated source (e.g. only accept the shop domain from Shopify's originating IP/mTLS, or include it in `to_signable_string` and require API consumers to supply the full raw request including headers for signing verification purposes). At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated and must not be used as a sole tenant-scoping key without additional verification (e.g. confirming it matches a shop for which the app already holds a session/access token).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, receiving genuine webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures a delivered webhook HTTP request (raw body + headers, including a valid `x-shopify-hmac-sha256`).
3. Attacker resends the identical body/HMAC to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` in `Registry.process` recomputes the HMAC over `raw_body` only, which still matches, so the request passes as valid. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and performs its shop-scoped action against the victim's tenant data, even though the payload never touched Shopify for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
