### Title
Webhook Shop-Domain Cross-Tenant Spoofing via HMAC Signature Not Covering `X-Shopify-Shop-Domain` Header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`) values used to route and process the webhook are taken from unsigned HTTP headers. This breaks the identity binding `HMAC(secret, raw_body) == signature` versus what is actually trusted downstream, `data.shop == X-Shopify-Shop-Domain header`, allowing any holder of one valid `(body, hmac)` pair for the shared app secret to replay it while spoofing the shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled directly from HTTP headers that are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` checks the HMAC using exactly `to_signable_string` (i.e. only the body) against `Context.api_secret_key`, which is the same secret shared across **every shop** that has installed the app: [3](#0-2) 

`Webhooks::Registry.process` validates that HMAC and then immediately trusts the unsigned `request.shop` header to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The equality the library implicitly promises is:
```
valid_hmac(body, secret) == true  implies  shop header is authentic for that body
```
But in reality only `HMAC(secret, body)` is verified — the `shop-domain` header is never part of the signed input. Any attacker who is a legitimate merchant of the same multi-tenant app (i.e., installs the app on their own store and thus can trigger and capture a genuine webhook delivery with a valid HMAC for arbitrary/attacker-chosen body content) can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with a victim shop's domain. The signature still validates because it depends only on the body and the shared secret, not on the shop header, so `Registry.process` dispatches the handler with a forged `data.shop` identifying the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's own webhook trust boundary: the value host applications are expected to rely on for shop/tenant identification (`data.shop`, per this gem's documented `WebhookMetadata` contract) is not covered by the cryptographic proof that is supposed to authenticate the request as coming from Shopify for that shop. Any app built on this gem that keys any action off `data.shop` (e.g., looking up and reusing the shop's stored session/access token, deleting/updating shop-scoped resources, or GDPR mandatory webhooks like `customers/redact`, `shop/redact`) can be tricked into performing that action against a victim's tenant using body content chosen by the attacker (since the attacker fully controls the body of the webhook they legitimately received for their own shop, up to what Shopify would emit for that topic). This matches the "cross-tenant access" Critical impact category — no access token, TLS interception, or privileged account is needed beyond installing the app on the attacker's own store, which is normal unprivileged merchant/internet-user behavior.

### Likelihood Explanation
Likelihood is high: no secret material beyond a normal app installation is required. An attacker only needs to (1) install the target app on their own Shopify store (unprivileged, self-service), (2) capture one legitimately signed webhook delivery for a topic/body of their choosing, and (3) POST that same raw body and HMAC to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. The library performs no additional binding check between the header and the signed payload, so this path is directly reachable through the gem's documented `Registry.process` API as shown in its own tests and docs: [5](#0-4) 

### Recommendation
Include the `shop-domain` (and ideally `topic`) header values in the HMAC-signed content that `Utils::HmacValidator` verifies, or otherwise cryptographically bind the shop identity to the payload before handing `WebhookMetadata` to handlers, e.g. by validating that the `shop` header matches a shop domain associated with the specific `webhook_id`/subscription on Shopify's side, or documenting/enforcing that host apps must independently verify shop ownership (not just possession of a valid HMAC) before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and configures a webhook subscription (e.g. `orders/create`) that the app registers via `Webhooks::Registry`.
2. Shopify delivers a legitimately signed webhook to the app's endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of BODY with shared api_secret_key>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: BODY (attacker fully controls order content within the topic schema by placing the order in their own store)
   ```
3. Attacker replays the exact same `Body` and `X-Shopify-Hmac-Sha256` value, but changes the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`@raw_body`), so it validates successfully (same body, same shared secret) — see: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, despite the request never actually originating from or being authorized for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
