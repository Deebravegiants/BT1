### Title
Unbounded SCALE Deserialization of Attacker-Controlled Bytes into the Full `RuntimeCall` Type in `pallet-hyper-fungible-token` - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an attacker-supplied byte blob directly into `T::RuntimeCall` — the entire, unbounded call surface of the runtime (every pallet's every dispatchable, including recursively-nesting calls like `Utility::batch`) — using a plain `Decode::decode` with **no recursion/depth limit**, unlike the sibling `pallet-call-decompressor`, which explicitly bounds the same kind of decode with `decode_all_with_depth_limit`.

### Finding Description
CVE-2016-8744 is a case of a deserializer unmarshalling untrusted bytes into an unconstrained universe of types ("any Java type on the classpath"), enabling attacker-chosen objects/behavior at the unmarshalling boundary. The analogous pattern here is `T::RuntimeCall::decode`, which will construct *any* variant of the runtime's `Call` enum — a type that spans every pallet in the chain (balances, assets, XCM, ISMP, staking, etc.) and includes recursively-composable calls such as `Utility::batch`/`as_derivative`.

In `on_accept`: [1](#0-0) 
the pallet decodes `message.data` (fully attacker-controlled ABI bytes carried inside the cross-chain token-transfer body) into `SubstrateCalldata`: [2](#0-1) 
and then decodes the embedded `runtime_call` bytes directly into the full `T::RuntimeCall` type with no depth limiting: [3](#0-2) 

Contrast this with `pallet-call-decompressor`, which performs the *same class* of operation (decoding attacker-supplied bytes into `T::RuntimeCall`) but explicitly guards against unbounded nesting: [4](#0-3) [5](#0-4) 

The `on_accept` path is reached by delivering an ISMP POST request through the permissionless `handle_unsigned` extrinsic, which any relayer can submit for free with a valid proof: [6](#0-5) 

The `BaseCallFilter::contains` check is applied only *after* the unbounded decode has already completed, so it cannot prevent a decode-time stack exhaustion caused by deeply nested call structures: [7](#0-6) 

### Impact Explanation
`handle_unsigned` executes messages inline during block execution/transaction-pool validation (not merely as an isolated sandbox), so a stack overflow triggered while SCALE-decoding a maliciously deep `T::RuntimeCall` inside `on_accept` traps the WASM runtime executing that block/extrinsic. Because `execute` is wrapped `#[frame_support::transactional]`, an in-flight token transfer plus malicious calldata can be crafted by any unprivileged token bridger sending a cross-chain transfer with `call_data` set (per `SendParams::call_data`), and delivered by any permissionless relayer. This can repeatedly crash message processing for the whole HFT route, effectively producing "a route unable to deliver messages" — any future request against the same module/pallet path is blocked until the offending message is worked around, which qualifies as the accepted impact category of message-delivery denial for that ISMP module.

### Likelihood Explanation
Likelihood is high: the trigger requires only (1) an authorized/registered source-chain HyperFungibleToken contract sending a normal cross-chain transfer with a `data` payload containing a crafted `SubstrateCalldata.runtime_call` blob (something already reachable by any ordinary bridge user via `SendParams::call_data`), and (2) any relayer submitting the resulting ISMP message via the permissionless `handle_unsigned` extrinsic — both steps are part of the pallet's normal, documented user flow, requiring no privileged role.

### Recommendation
Replace the unguarded `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` in `on_accept` (module.rs:189) with a depth-bounded decode, mirroring `pallet-call-decompressor`'s use of `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, …)`, and move the `BaseCallFilter` check to occur only on a bounded, successfully-decoded call. Consider also capping `substrate_data.runtime_call`'s byte length before decoding.

### Proof of Concept
1. A source-chain user calls the registered `HyperFungibleToken` contract's send function with a `Message.data` payload whose SCALE encoding is a `SubstrateCalldata { signature: None, runtime_call: <deeply nested Utility::batch/as_derivative call, nested to depth >> typical stack limits> }`.
2. Any relayer observes the resulting POST request/commitment and submits it through `pallet_ismp::Call::handle_unsigned` with a valid membership proof (module.rs:189, ismp/src/lib.rs:373-382).
3. During `on_accept`, `T::RuntimeCall::decode` recurses without a depth cap while parsing the nested call structure, exhausting the WASM call stack before the `BaseCallFilter::contains` check is ever reached, aborting execution of that transaction/block.

Note: I was unable to fully verify from the indexed EVM contract source how strictly `Message.from`/`data` are bound to `msg.sender` on the source chain (the relevant `send`/`dispatchWithFee*` functions in `HyperFungibleToken.sol` were only partially retrievable due to index size limits); this does not affect the deserialization/depth-limit finding above, which depends only on `message.data` being attacker-suppliable by the token sender, but a full assessment of `message.from`-based origin derivation would benefit from a Devin session with complete file access.
