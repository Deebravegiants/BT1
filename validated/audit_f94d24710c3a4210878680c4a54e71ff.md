### Title
Rounding-favorable buy/sell round-trips can push a curve pair's stored LT reserve below its immutable launch-time virtual reserve, causing `Bonding.canGraduate` to permanently revert and brick the entire curve - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The gnutls advisory is a class of bug where an attacker-controlled, unvalidated value (a bogus PSK binder) is fed into an arithmetic/pointer operation that the code implicitly assumes is well-formed, producing an unhandled fault (NULL deref) and a permanent-per-request DoS. The analogous assumption in alt.fun is that a bonding-curve pair's live `assetReserve` (`Pair.getReserves()`'s reserve1) can never fall below the pair's fixed launch-time virtual LT reserve, so `Bonding.canGraduate` unconditionally subtracts one from the other with no floor check.

### Finding Description
`canGraduate` computes the USD graduation trigger as: [1](#0-0) 

`realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` is an unchecked Solidity 0.8 subtraction. It is safe only under the invariant "current stored `assetReserve` is always ≥ the immutable launch-time virtual LT reserve," which the docs assert holds because `Pair.k()` (and hence the recovered virtual reserve `Pair.k()/TOTAL_SUPPLY()`) is fixed at mint and the pair only ever gains real LT via buys and loses it via sells governed by the K-invariant: [2](#0-1) 

`_computeSell` derives `assetOut` from `reserveAsset - (k / newReserveToken)` using integer division, and the same rounding pattern exists in `_computeBuy`'s overflow-cap branch with its explicit ceil-rounding: [3](#0-2) 

Both `AGENTS.md` and `docs/contracts-scope.md` flag this exact surface — the bonding-curve math with "no curve fee," the overflow cap's "ceil-rounded `amountInUsed`," and "Pair.swap's `+1` K slack" — as the place where alt.fun's own math, not gnutls', is fragile. Repeated dust-sized buy/sell round trips that exploit integer-division rounding (favoring the trader by even 1 wei per round trip, which the `+1` K slack in `Pair.swap` is documented to tolerate) can incrementally erode the pair's stored `assetReserve` below the fixed `_launchTimeVirtualLtReserve` baseline. Because `_launchTimeVirtualLtReserve` never changes (it's derived from immutable `Pair.k()`), once enough rounding-favorable round trips have executed, `assetReserve - _launchTimeVirtualLtReserve` underflows and reverts with a Solidity Panic(0x11).

`canGraduate` is not a side-view function — it is called unconditionally at the end of every buy: [4](#0-3) 

So once the underflow condition exists, `canGraduate(tokenAddress)` reverts inside `_executeBuy`, which reverts every subsequent `Zap.buy` / `Zap.buyWithPermit` on that token. `docs/contracts-scope.md` also states the sell path checks graduatability before executing a sell ("If the curve token is already graduatable ... the sell triggers graduation instead"), meaning `Zap.sell` / `sellWithPermit` would hit the same reverting check. The curve becomes permanently untradeable on both sides — a full DoS of the token, exactly mirroring the "malformed input → unhandled fault → permanent service disruption" shape of the gnutls CVE, except the fault here is a Solidity arithmetic Panic rather than a NULL pointer dereference, and it is permanent because `_launchTimeVirtualLtReserve` is immutable and `assetReserve` can only be pushed further away from recovery by more trades, not toward it.

### Impact Explanation
If reachable, this permanently freezes trader/creator funds locked in the affected `Pair` (the real LT raised via buys, and the 750M curve-transferred tokens) — no buy or sell can execute on that curve ever again, and the token can never graduate (both the USD and buy-triggered `_enterGraduating` paths run through `canGraduate`). This matches the accepted impact class: "permanent freezing of trader, creator or LP funds."

### Likelihood Explanation
This requires an unprivileged attacker to execute a large number of dust buy/sell round trips against a single curve, relying on the `+1` K-invariant slack in `Pair.swap` (referenced repeatedly in the repo's own documentation as a rounding surface) accumulating in the attacker's favor over many iterations. I was not able to read `Pair.sol` directly within the available tool budget to confirm the exact mechanics and magnitude of the `+1` slack, or to confirm whether existing rounding-direction guarantees in `_computeBuy`/`_computeSell` (both of which round in the protocol's favor via `k / newReserve` floor division and explicit ceil on the overflow-cap branch) actually prevent net-favorable drift for an attacker over repeated trades. This is the main open uncertainty in this analog — it is plausible on the documented rounding shape, but not verified against `Pair.sol`'s literal implementation.

### Recommendation
Add an explicit invariant check (rather than relying on invariant-by-construction) in `canGraduate` and `previewLtUntilGraduation`: if `assetReserve < _launchTimeVirtualLtReserve(...)`, treat `realLtRaised` as `0` instead of underflowing, e.g. `uint256 realLtRaised = assetReserve > virtualReserve ? assetReserve - virtualReserve : 0;`. Separately, audit `Pair.swap`'s `+1` K-slack tolerance and `Router._computeSell`/`_computeBuy` rounding to confirm no sequence of trades can drift `assetReserve` net-downward relative to the immutable virtual baseline; if such drift is possible, either fix the rounding direction to always favor the pool, or track "real LT raised" as an explicit monotonic accumulator rather than re-deriving it from live reserves each time.

### Proof of Concept
Conceptual PoC (requires confirming `Pair.swap`'s slack magnitude, which I could not verify directly):
1. Launch a token via `Zap.createToken`.
2. An unprivileged attacker repeatedly calls `Zap.buy(tokenAddress, dustUsdc, 0, address(0))` followed by `Zap.sell(tokenAddress, tokensJustBought, 0)` in a loop, each round trip exploiting the `+1` K-invariant slack in `Pair.swap` to extract a small net amount of LT from the pair beyond what the constant-product formula would allow.
3. After enough iterations, the pair's stored `reserve1` (`assetReserve`) drops below the immutable `_launchTimeVirtualLtReserve`.
4. The next call to `Bonding.canGraduate(tokenAddress)` (invoked internally by `_executeBuy` on the next buy) underflows and reverts with Panic(0x11), permanently reverting every subsequent buy (and, per documented sell-side graduatability check, every subsequent sell) on that token's curve.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
