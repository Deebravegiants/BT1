This confirms the vulnerability. `WebhookMetadata#shop` (`lib/shopify_api/webhooks/webhook_handler.rb:6-12`) is populated directly from `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`), which reads the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. But `Request#to_signable_string` — the value the HMAC actually authenticates via `Utils::HmacValidator.validate` in `Registry.process` — is only the raw body (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/webhooks/registry.rb:188-199`). The topic, api_version and webhook_id headers are equally unauthenticated. Since the webhook secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, any tenant that receives a validly-signed webhook for their own shop can replay that exact `(body, hmac)` pair against the app's webhook endpoint while substituting a different `shopify-shop-domain` header, and `Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming it came from the victim shop.

### Title
Webhook shop-domain (and topic/webhook_id) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but dispatches handler logic keyed on the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhook requests `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the body or its signature [2](#0-1) .

`Registry.process` validates only the body's HMAC, then builds `WebhookMetadata` (which the app's handler uses to identify the tenant) directly from these unauthenticated header values: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` [3](#0-2) .

The equality the code should enforce is: `shop-bound-by-HMAC == shop-acted-upon`. Instead, the HMAC only proves `body-bound-by-HMAC == body-acted-upon`; the `shop` (and `topic`/`webhook_id`) fields are trusted without being covered by the signature, which is exactly the "field acted on but not covered by the HMAC" identity-binding break called out in the report analog.

Because the webhook signing secret is the app's `client_secret` (`Context.api_secret_key`), it is identical for every shop that has installed the app — it is not shop-specific. Any tenant of a multi-tenant app therefore possesses at least one genuine, validly-signed `(body, hmac)` pair (from webhooks Shopify sends them for their own shop). That attacker-controlled tenant can POST that same body and HMAC to the app's public webhook endpoint while setting the `shopify-shop-domain` header (and optionally `shopify-topic`) to a victim shop's domain. `Utils::HmacValidator.validate` will pass because it only checks the body signature, and `Registry.process` will hand the handler a `WebhookMetadata` asserting the event came from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an app built on this gem cannot distinguish a genuine webhook about shop A from an attacker-controlled tenant forging a webhook that claims to be about shop B, because the signature never covers the shop identifier. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g., mandatory GDPR topics like `shop/redact`, `customers/redact`, `customers/data_request`, or app-specific webhooks that trigger data deletion, plan changes, resource sync, or cache invalidation keyed by shop), this enables cross-tenant data corruption, spurious data-erasure, or state confusion attributed to a shop the attacker does not control — satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Any actor who can install the target app on their own store (a normal, unprivileged action for any Shopify merchant/developer) automatically receives genuinely-signed webhooks from Shopify and can capture valid `(body, hmac)` pairs without ever needing the app's `client_secret`. Replaying that pair against the app's public webhook endpoint with a modified `shopify-shop-domain` header requires no privileged access, no leaked credentials, and no interaction with Shopify's servers — only network access to the app's webhook callback URL, which is publicly reachable by design.

### Recommendation
Bind the shop (and ideally topic/webhook_id) to the HMAC-verified payload instead of trusting the header value independently, e.g., have `Request#to_signable_string` incorporate the shop-domain header (matching what Shopify actually signs, if supported) or require host applications to cross-check `request.shop` against a shop the app has an active session/install record for before dispatching to `WebhookHandler#handle`. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must be revalidated against known installed shops before being trusted for any tenant-scoped action.

### Proof of Concept
1. App merchant "Attacker" installs the target Shopify app on `attacker.myshopify.com`. Shopify sends a real webhook, e.g. `customers/data_request`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — using `lib/shopify_api/webhooks/request.rb`'s `to_signable_string` semantics (body-only).
2. Attacker captures `(B, H)`.
3. Attacker POSTs to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged/valid), but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [4](#0-3) .
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and invokes the registered handler, which now believes this is a genuine event for `victim.myshopify.com` even though Shopify never sent it about that shop [5](#0-4) .
