### Title
Emporium Min-circuit path lets an unprivileged attacker run unaccounted, unauthenticated ops that drain any token balance held by the Emporium contract - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` selects `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin`) only proves `message == Poseidon(messageSeed)` — no signature, no nullifier, no root-hash, no amount binding. Combined with `EmporiumUpgradeable.runAction`'s `verifyWallet` short-circuit for `signerAddress == address(0)` (no ECDSA check at all) and its `ops` loop making arbitrary `endpoint.call{value: op.value}(op.callData)`, an attacker can run arbitrary calls from the Emporium contract's identity while `balancesBefore`/`balancesAfter` accounting is scoped only to `circomData.erc20TokenAddresses` (empty, or attacker-chosen to exclude the target token), so any token balance Emporium holds can be moved out unaccounted.

### Finding Description
The claimed invariant is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. This breaks because the ops list is never constrained to the tokens the accounting loop tracks.

Path:
1. Attacker calls `Hinkal.transact` with `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`.
2. `dimensionsCheck` forces every token-shaped array (`amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`, `outCommitments`, `encryptedOutputs`) to also be length 0 to match `dimensions.tokenNumber == 0` [1](#0-0) . Consequently `checkOnchainCreation`'s loop never executes, so the `onChainCreation[i] == true` branch referenced in the question cannot co-occur with the empty-array Min path [2](#0-1) ; that specific sub-claim is moot, but it is not needed for the exploit.
3. `formInputForCircom` routes to `formInputEmporiumMin`, which only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` as public inputs — no signature, no root hash, no nullifiers [3](#0-2) . The corresponding circuit `MainEVMCircuitMin` only constrains `message === Poseidon(messageSeed)` [4](#0-3) , something any attacker can trivially prove for a self-chosen `messageSeed`.
4. `Hinkal.transact`'s post-call balance loop iterates `circomData.erc20TokenAddresses` (length 0), so no slippage/accounting checks apply to this call at all [5](#0-4) .
5. `_externalTransact` calls `EmporiumUpgradeable.runAction` with `deltaAmountChanges` of length 0 [6](#0-5) .
6. Inside `runAction`, `verifyWallet` returns immediately without any ECDSA check when `stack.signerAddress == address(0)` [7](#0-6) . The `ops` array — fully attacker-controlled via `externalActionData.externalActionMetadata` — is then executed with the Emporium contract as `msg.sender` for each `op.endpoint.call{value: op.value}(op.callData)` [8](#0-7) .
7. `balancesBefore`/`balancesAfter` and the `balanceChange` accounting loop are scoped exclusively to `circomData.erc20TokenAddresses` (empty in this scenario) [9](#0-8) . An op that calls `someToken.transfer(attacker, someToken.balanceOf(address(this)))` on any token Emporium happens to hold (parked/in-flight balances from other users' multi-step Emporium flows, or leftover dust) sends funds straight to the attacker, completely outside any accounting, slippage, nullifier, or signature check.

Existing guards fail because: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only constrain array shapes, not the semantic content of `ops`; `verifyProof` for the Min circuit constrains nothing about `ops`, `erc20TokenAddresses`, or the eventual token movement; `verifyWallet` is bypassed entirely for `signerAddress == address(0)`; and the balance/slippage checks in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` are indexed only by the attacker-supplied (here empty) `erc20TokenAddresses` array, so they account for nothing.

### Impact Explanation
Any ERC20 (or ETH) balance held by the Emporium contract — including funds temporarily parked there between legitimate multi-op Emporium sessions ("in-flight" user funds) — can be transferred out by an unprivileged attacker with no signature and no meaningful proof. This is direct theft of shielded/in-flight user funds, matching the Critical severity category, and is repeatable every time Emporium accrues a token balance.

### Likelihood Explanation
No special preconditions: the attacker needs no deposit, no valid UTXO, no relay, no privileged role — only the ability to compute `Poseidon(messageSeed)` for a self-chosen seed (a public relation, not a secret) and to craft an `EmporiumStack` with `signerAddress == address(0)`. The only requirement is that Emporium hold a non-zero balance of some token at call time, which naturally occurs whenever other users route funds through Emporium (e.g., mid-multi-op stacks, or callback-based flows crediting Emporium before final settlement). Attack cost is a single transaction's gas.

### Recommendation
- Do not allow `signerAddress == address(0)` to bypass authorization when `ops` can target arbitrary endpoints; require that every token touched by `ops` be present in and accounted by `circomData.erc20TokenAddresses`, or restrict stateless ops (`signerAddress == 0`) to only call into tokens explicitly listed in `erc20TokenAddresses`.
- Reject the Min-circuit path (`erc20TokenAddresses.length == 0`) whenever `ops` reference token-affecting calls, or require the Min path to disallow arbitrary `endpoint.call` execution entirely (e.g., only allow a fixed safe subset of stateless operations).
- Bind `ops` (and the full `externalActionMetadata`) into a value actually constrained by the SNARK (not just `calldataHash`, which provides no authorization, only replay-binding) so that fund movement is cryptographically tied to a real, authorized UTXO spend.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as an allowed recipient), and a mock ERC20.
2. Fund the Emporium contract directly with `mockToken.transfer(address(emporium), 1000e18)` to simulate parked/in-flight balance.
3. As an unprivileged attacker EOA, generate a Min-circuit proof for a self-chosen `messageSeed` (trivial `Poseidon(messageSeed)` witness), and construct `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(mockToken), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))})], ...}))`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. Assert: `mockToken.balanceOf(attacker) == 1000e18` and `mockToken.balanceOf(address(emporium)) == 0`, while no `slippageValues`/balance check reverted and no nullifier/root check was exercised — proving assets moved (1000e18) != assets accounted (0, since `erc20TokenAddresses` is empty on both sides of the equation).

include "../../node_modules/circomlib/circuits/poseidon.circom";

template MainEVMCircuitMin() {
  // Public inputs:
  signal input outTimeStamp;
  signal input calldataHash;

  // Private inputs:
  signal input messageSeed;

  // outputs:
  signal output message;

  message <== Poseidon(1)([messageSeed]);
