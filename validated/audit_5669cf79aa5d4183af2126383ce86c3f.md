### Title
Mutable `operator_qr_expiration_time` config retroactively alters validity window of already-scanned operator sessions - (File: `src/plans/mod.rs`, `src/config.rs`)

### Summary
Orb-core's operator QR-code authorization window is governed by the backend-controlled config field `operator_qr_expiration_time`, but the validity check does not pin the expiration duration that was in effect when the operator QR was originally scanned. Instead, every expiration check re-reads the *current* value of the config, which can change mid-signup because the config is refreshed from the backend independently of the ongoing signup/idle flow. This is the same bug class as the C4 Particle `LOAN_TERM` finding: a mutable global setting is applied retroactively to state (a "session"/"lien") that was created under a different, previously-agreed setting.

### Finding Description
`operator_qr_expiration_time` is a `Duration` field of `Config`, downloaded from the backend and stored in a shared `Arc<Mutex<Config>>`: [1](#0-0) [2](#0-1) 

When an operator QR code is scanned, its authorization is recorded as `OperatorData` with a `timestamp` captured at scan time: [3](#0-2) 

That timestamp is later compared against the *live* value of `operator_qr_expiration_time`, fetched fresh from `orb.config.lock().await` at multiple, separated points in the signup lifecycle — at the top of `MasterPlan::run`, again inside `do_signup`, and used repeatedly in `scan_initial_qr_codes`, `idle_wait_for_signup_request`, `idle_scan_user_qr_code`, and `scan_remaining_qr_codes`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

Nowhere is the expiration duration that was active *when the operator QR was scanned* stored alongside `OperatorData.timestamp`. Instead, every check does `operator_data.timestamp.elapsed() < operator_qr_expiration_time` using whatever value the shared `Config` currently holds. Just as the C4 report's liquidation check used the live `LOAN_TERM` instead of the term value stored at lien creation, this check uses the live `operator_qr_expiration_time` instead of the value captured at operator-QR-scan time.

### Impact Explanation
The self-serve idle loop (`idle_scan_user_qr_code`) can wait for a user QR code for up to the full `operator_qr_expiration_time` (23 hours by default) with only one operator QR scan performed up front. If the backend pushes a config update that *increases* `operator_qr_expiration_time` while this loop (or the equivalent path in `scan_remaining_qr_codes`/`do_signup`) is already running with a previously scanned `OperatorData`, the already-scanned operator authorization — which should have expired and forced a fresh re-scan/re-verification of the operator's QR (and thus re-validation of operator identity and location, per `verify_operator_qr_code`) — remains accepted as valid for a longer time than the operator originally agreed to when their QR was scanned. This effectively extends an operator's authorization window retroactively, letting a stale operator session continue to bind and authorize new user signups (`handle_user_qr_code` / `verify_user_qr_code` receives `operator_data` unconditionally as long as the elapsed check passes). This is a session/authorization-binding integrity issue: the acceptance criteria for an already-existing signup authorization silently changes underneath it, analogous to the unintended liquidation of a position created under a different loan term.

### Likelihood Explanation
Config downloads happen independently of the signup state machine via `Config::download_and_store`, and are applied instantly to the shared `Config` mutex used throughout `plans/mod.rs`. Because self-serve idle loops can legitimately be long-running (`operator_qr_expiration_time` defaults to 23 hours), and signups in general span multiple config-read points, the window for a backend-side config change to land in the middle of an in-flight operator authorization is not narrow — it is a routine operational event (config rollout) rather than an attacker-crafted race condition, making it moderately likely to occur under normal fleet configuration changes.

### Recommendation
Capture the `operator_qr_expiration_time` value at the moment the operator QR is scanned and store it in `OperatorData` (mirroring the report's recommendation to store `loan.loanTerm` at lien creation). All subsequent expiration checks (`scan_initial_qr_codes`, `idle_wait_for_signup_request`, `idle_scan_user_qr_code`, `scan_remaining_qr_codes`) should use this stored, per-session value instead of re-reading the live config, so an already-granted operator authorization window cannot be silently altered by a later config change.

### Proof of Concept
1. Orb is in self-serve mode without button press; operator scans their QR, creating `OperatorData { timestamp: Instant::now(), .. }` with the config's `operator_qr_expiration_time` at, say, 5 minutes (`src/plans/mod.rs:775-781`).
2. The orb enters `idle_scan_user_qr_code`, waiting for the user's QR, using `operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())` as the remaining timeout (`src/plans/mod.rs:456-467`).
3. Before 5 minutes elapse, the backend pushes an updated config that increases `operator_qr_expiration_time` to, e.g., 23 hours; `Config::download_and_store` updates the shared `Arc<Mutex<Config>>` (`src/config.rs:357-368`).
4. The next loop iteration/config read (`src/plans/mod.rs:329-336` or `:497-506`) picks up the new, larger value, so the elapsed-time check against the *stale* `operator_data.timestamp` still evaluates to "not expired," even though the operator's authorization was only ever granted for the original 5-minute window.
5. The stale operator session continues to be accepted to bind and authorize a later user QR scan (`handle_user_qr_code`/`verify_user_qr_code`), despite it having exceeded the originally intended authorization duration.
