### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates the HMAC over that same signable string and, once it passes, forwards `request.shop` unchanged into the handler as the tenant identifier [3](#0-2) . The binding the library implicitly claims to guarantee — "shop header == the shop that produced this signed body" — is never enforced, because the header is parsed but not part of the bytes that are verified.

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(client_secret, to_signable_string)` and compares it to the `hmac` field [4](#0-3) . For webhooks, `to_signable_string` is exactly `@raw_body` [1](#0-0) ; none of `topic`, `shop`, `webhook_id`, or `api_version` participate in the signature — they are read straight from headers with no cryptographic binding to the signed payload [5](#0-4) .

Because the app's `client_secret` (and hence the HMAC key) is shared across every shop that installs the app, any principal who can obtain one genuine `(raw_body, hmac)` pair — for instance an attacker who installs the app on their own store and receives a real webhook for it — possesses a signature that is valid for that exact body under the app's secret regardless of which shop header accompanies it. That attacker can then replay the same body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `Registry.process` accepts the request because `Utils::HmacValidator.validate(request)` only checks the body's HMAC [6](#0-5) , then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the app's handler using the attacker-controlled `shop` value [7](#0-6) .

This is exactly the "field acted on but not covered by the HMAC" pattern: the equality the code needs to hold is `hmac == HMAC(secret, body ‖ shop ‖ topic ‖ webhook_id)`, but what is actually checked is `hmac == HMAC(secret, body)`, silently dropping `shop` (and the other identity fields) from the committed message. The documented usage pattern in `docs/usage/webhooks.md` reinforces the trust placed in `data.shop` as the tenant key passed straight into application logic (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so any consumer following the gem's documented API inherits this cross-tenant confusion.

### Impact Explanation
An attacker who is a legitimate (even free/trial) merchant of the target app can forge webhook deliveries that the app attributes to a different shop of their choosing, since `shop` is not bound to the signed bytes. Depending on how the host app uses `data.shop` (e.g., to look up which merchant's DB row/tokens to update, or to key background jobs), this enables cross-tenant data corruption or confusion — writing attacker-controlled webhook content into another merchant's records, or bypassing per-shop authorization checks that trust `data.shop`. This matches the Critical "cross-tenant access" impact category, since the underlying primitive is an identity/tenant-binding failure in the gem's own verification code, not merely a caller misuse of an undocumented API.

### Likelihood Explanation
Exploitability requires only: (1) attacker access to install the app on at least one shop (or otherwise obtain one valid signed webhook body/HMAC pair for that app), and (2) ability to send an HTTP request to the app's public webhook endpoint with a spoofed `X-Shopify-Shop-Domain` header — both are attacker-reachable actions with no privileged credentials, matching the "unprivileged internet user" threat model. No `api_secret_key`, access token, or social engineering is needed; the attacker never needs to know the app's secret because they reuse a signature Shopify itself generated for their own shop's webhook.

### Recommendation
Include the identity-bearing headers (at minimum `shop`, and ideally `topic`/`webhook_id`) in the signed material that `to_signable_string` returns, or otherwise cryptographically bind them to the verified body (e.g., verify the HMAC over `raw_body` and separately re-derive/validate `shop` from a source that Shopify signs, such as validating it against a known/expected shop list before dispatch). At minimum, document loudly that `data.shop` is not authenticated by `Registry.process` and must be independently verified by the host app against its own shop registry before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a genuine webhook: body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` where `H = Base64(HMAC-SHA256(client_secret, B))`.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses `shop` as `victim-shop.myshopify.com` [2](#0-1) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and finds it equal to `H`, so validation passes [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` [7](#0-6) , causing the host app to process attacker-controlled webhook content as if it originated from the victim's shop.
