### Title
Unauthenticated arbitrary call execution in `CallDispatcher.dispatch` enables theft of tokens escrowed mid-`placeOrder` - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is a fully public, unauthenticated function that ABI-decodes caller-supplied bytes into an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` against any address the caller names [1](#0-0) . This mirrors the ImpressPages `cm_group` eval-injection bug class: a caller-controlled blob is turned directly into executed code/calls with no restriction on who can trigger it or what it targets. `IntentGatewayV2.placeOrder` relies on this same shared `CallDispatcher` instance as a temporary custodian of escrowed input tokens during the "predispatch" phase (e.g. unwrapping LP tokens) before sweeping the resulting balances back into the gateway [2](#0-1) .

### Finding Description
`dispatch()` has no `onlyGateway`/`onlyHost`/`msg.sender` check of any kind — any address can call it directly with a crafted `Call[]` [1](#0-0) . The `ICallDispatcher` interface itself documents that it is meant "to dispatch untrusted call(s)" [3](#0-2) , but the design's safety depends entirely on the invariant that `CallDispatcher` never holds a resting balance outside the atomic window of a single `placeOrder` call.

In `placeOrder`, when `order.predispatch.call` is set, the gateway:
1. Transfers the user's input assets (native value or ERC20 `safeTransferFrom`) into the shared `dispatcher` contract [4](#0-3) .
2. Calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` to run caller-supplied unwrap logic [5](#0-4) .
3. Builds a second `Call[]` (sweep calls) and invokes `dispatcher.dispatch(...)` again to pull the resulting balances back to `address(this)` [6](#0-5) .

Because `dispatch()` is unauthenticated and non-reentrancy-guarded, any external call reachable from step 2's caller-supplied `predispatch.call` (e.g., an ERC-777-style token hook, or any other callback-capable target listed in the predispatch calls) can re-enter `CallDispatcher.dispatch()` before the gateway's own sweep executes in step 3, redirecting the tokens/ETH that are sitting in `CallDispatcher` at that moment to an attacker-chosen address. The vulnerability is the missing access control on `dispatch()` itself: nothing prevents any caller — not just the gateway that legitimately owns the escrow flow — from targeting whatever balance happens to be resting in the shared `CallDispatcher` singleton at any point in time.

### Impact Explanation
If exploited, an attacker can drain escrowed order inputs that are momentarily held by the shared `CallDispatcher` contract during the predispatch phase of `IntentGatewayV2.placeOrder`, resulting in direct theft of user funds mid-transaction. Since `CallDispatcher` is a shared, address-persistent utility contract with no owner or caller restriction, any value it is holding at any instant (from a reentrant callback, a partially-completed predispatch sequence, or accidental direct transfers via its `receive()`) is fully and immediately drainable by anyone. This satisfies the "concrete theft of funds" bar for a High-severity finding.

### Likelihood Explanation
Exploitability depends on the predispatch call graph reaching a contract capable of a callback into `CallDispatcher.dispatch()` before the sweep runs (e.g., a token with transfer/operator hooks, or any other external contract invoked as part of "unwrapping LP tokens"). The `dispatch()` function's total lack of access control makes it trivially callable by anyone once value happens to be held there; the primary uncertainty is how commonly `order.predispatch.call` includes callback-capable targets in practice, which the index does not let me fully verify — a background session with full repo access should audit every caller of `CallDispatcher.dispatch()` and every token/contract type permitted in `predispatch.assets`/`predispatch.call` to confirm real-world reachability of a reentrant window.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the registered gateway/dispatcher owner (e.g., an `onlyGateway` modifier set at construction, or make `CallDispatcher` a non-shared, per-order/per-call ephemeral contract), and add a reentrancy guard so a nested `dispatch()` call cannot execute while a predispatch/sweep sequence is in progress. Alternatively, ensure `CallDispatcher` never persists any balance across calls and reverts if invoked with a nonzero starting balance from an unexpected caller.

### Proof of Concept
1. Deploy a malicious ERC20-like token `Evil` whose `transferFrom` or a nested hook calls back into `CallDispatcher.dispatch()`.
2. Craft an `Order` whose `predispatch.assets` includes `Evil`, and whose `predispatch.call` invokes `Evil`'s transfer, triggering the reentrant hook.
3. Inside the hook, call `CallDispatcher.dispatch()` directly with a `Call[]` that sweeps the legitimate input tokens (already transferred to `dispatcher` in step 1 of `placeOrder`) to an attacker-controlled address, via `to.call{value: call.value}(call.data)` targeting the legitimate token's `transfer` function [1](#0-0) .
4. When the legitimate `placeOrder` sweep call executes afterward, the balance is already gone, and the order accounting proceeds based on a reduced/zero `received` amount while the attacker has captured the escrowed funds [7](#0-6) .

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
