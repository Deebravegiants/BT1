### Title
Unbounded ownership-chain growth in `object.move` lets an attacker permanently brick custody checks (`object::owns`) and creates an unbounded loop in `object::root_owner` - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
The Aptos object model caps ownership nesting at `MAXIMUM_OBJECT_NESTING = 8` [1](#0-0)  and enforces this bound in `verify_ungated_and_descendant`, which is invoked from `transfer_raw` [2](#0-1) . However, the check only walks the **pre-existing** ownership chain of the object being moved, not the chain of the destination it is being attached to, so the resulting combined chain length is unchecked. This lets an attacker legitimately build ownership chains deeper than 8 by repeatedly wrapping a shallow object into progressively-nested targets. Any subsequent `object::owns()` call on such a chain will deterministically abort due to the nesting-depth assertion, and `object::root_owner()` — which has **no depth bound at all** — will loop for the full (attacker-chosen) chain length, mirroring the "unbounded loop causes OOG / bricked processing" pattern from the H-7 report.

### Finding Description
`verify_ungated_and_descendant(owner, destination)` is called as `verify_ungated_and_descendant(owner_address, object)` inside `transfer_raw`, i.e. `destination` is bound to the **object being transferred**, not the target it's being placed into: [3](#0-2) 

The bounded loop in `verify_ungated_and_descendant`/`owns` only checks that the signer reaches the *current* owner of the object being moved within `MAXIMUM_OBJECT_NESTING` hops: [4](#0-3) 

Because a freshly-created object `X` (owned directly by the signer, depth 0) always satisfies this check trivially, an attacker can repeatedly do `transfer(signer, X, Y_address)` where `Y` is itself an already-deeply-nested object (e.g., already at depth 8). The check on `X`'s *old* chain passes, but `X`'s *new* full chain (`X -> Y -> ... -> root`) can now exceed 8. Repeating this with new shallow wrapper objects each iteration produces an ownership chain of unbounded length — the nesting invariant that `owns()`/`transfer` are supposed to enforce is not actually preserved across compositions.

Two downstream functions consume this chain without re-checking it safely:
- `owns()` bounds its own walk to `MAXIMUM_OBJECT_NESTING` and **aborts** (`EMAXIMUM_NESTING`) if the chain is longer [5](#0-4) . `fungible_asset` relies on `object::owns` for withdraw authorization: `withdraw_sanity_check_impl` calls `object::owns(store, owner_address)` and aborts if it's not true [6](#0-5) . If a `FungibleStore` object ends up owned through a chain longer than 8, `owns()` will *always* abort for that store's rightful owner (`EMAXIMUM_NESTING`, not "not owner"), meaning the true owner can never again pass `withdraw_sanity_check`/`upgrade_store_to_concurrent`'s ownership assertion for that store.
- `root_owner()` has **no depth limit whatsoever**: `while (is_object(obj_owner)) { obj_owner = address_to_object<ObjectCore>(obj_owner).owner(); }` [7](#0-6) . A sufficiently long attacker-built chain (thousands of hops, built incrementally across many transactions, each individually valid) makes any single call to `root_owner()` scale linearly with chain length, risking out-of-gas failures for any function that depends on it — the direct structural analog of the H-7 `getLockedFunds()` unbounded loop.

### Impact Explanation
This breaks the custody invariant that "object ownership refs must preserve the intended controller" and that "custody invariants should hold across deposit/withdraw paths." Concretely:
- A `FungibleStore` (or any object) whose ownership chain is driven past depth 8 becomes **permanently unable to pass `object::owns()` checks**, which directly blocks `fungible_asset::withdraw`/`withdraw_sanity_check` and any other logic gated by `object::owns`. This is a non-recoverable, permanent lock of object-held value — matching the "Permanent lock or non-recoverable loss of object-held...value" impact bucket.
- Because `root_owner()` is unbounded, any caller relying on it for ownership resolution can be forced into unbounded gas consumption, denying that operation entirely (OOG), the direct structural analog of the reported bug class.

### Likelihood Explanation
The mechanism requires the attacker/owner to actively construct the deep chain themselves (each `transfer` step needs the current owner's own signature), so this is most exploitable as a **self-inflicted trap set up by a malicious or naive wrapping/composability contract** (e.g., a vault, marketplace escrow, or "bundle" feature that lets users nest objects/stores under attacker- or protocol-controlled wrapper objects without warning). It is not a straightforward "steal any user's assets on demand" attack; it is a way to make custody assertions non-functional for objects that get wrapped past the intended nesting bound, which the code's own bound (`MAXIMUM_OBJECT_NESTING`) was clearly designed to prevent but fails to actually enforce transitively. I was not able to fully verify within available effort whether any current framework/token-object module allows an attacker to nest a **victim's** object without the victim's own transfer signature (this would raise likelihood to Critical); this needs further review of composability/marketplace modules before treating it as fully unprivileged against third parties.

### Recommendation
- Fix `transfer_raw`/`verify_ungated_and_descendant` to validate the **resulting** ownership chain depth (i.e., check depth from the object being moved through its new parent `to` up to a max), not just the object's pre-existing chain.
- Add an explicit, identical `MAXIMUM_OBJECT_NESTING` bound (with a graceful `Option`/bool return rather than an abort) to `root_owner()` so it cannot loop unboundedly.
- Consider re-validating/caching a "depth" field on `ObjectCore` at each transfer so nesting depth is O(1) to check rather than requiring a walk, closing off the compositional bypass entirely.

### Proof of Concept
Conceptual sequence (Move pseudocode, using existing entry functions `object::transfer`):
1. Attacker creates `O1` (owned by self, depth 0).
2. Attacker creates `O2` (owned by self, depth 0), calls `object::transfer(self, O1, O2_address)` → passes check (`O1`'s old chain depth 0 ≤ 8). Chain: `O1 -> O2 -> self`.
3. Attacker creates `O3` (owned by self, depth 0), calls `object::transfer(self, O2, O3_address)` → passes check (`O2`'s old chain depth 0 ≤ 8, since `O2` itself was still directly owned by self at the time of this call). Chain becomes: `O1 -> O2 -> O3 -> self` (depth 3 from O1).
4. Repeat step 3 pattern ~9+ times, each time wrapping the previous "head" object into a new shallow object, to build `O1 -> O2 -> ... -> O10 -> self` (depth > 8).
5. Any call to `object::owns(O1_wrapped_as_store, self_address)` now aborts with `EMAXIMUM_NESTING` regardless of true ownership, and any call to `object::root_owner(O1)` walks the entire >8-hop chain (unbounded as the chain grows further).
6. If `O1` (or any object in the chain) is/contains a `FungibleStore`, `fungible_asset::withdraw` for that store will permanently fail via `withdraw_sanity_check_impl`'s `object::owns` assertion, since it can never return `true` past depth 8 — even though `self` is still the legitimate ultimate owner. This exact PoC was not executed against a live/test node; it is derived purely from static analysis of the cited source and should be validated in the Move unit-test framework (existing tests in `object.move` already demonstrate the 8-hop nesting abort behavior with `test_exceeding_maximum_object_nesting_owns_should_fail`) [8](#0-7) , but that test builds the chain via single-hop-at-a-time transfers where the destination is always shallow — precisely the pattern this report identifies as bypassing the intended bound when repeated with growing "head" chains instead of a static probe chain.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    #[view]
    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
