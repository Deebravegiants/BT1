Confirmed: the `AuthQuery#to_signable_string` includes `shop` in the HMAC-signed payload (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), but `Webhooks::Request#to_signable_string` signs only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop` is read directly from an unauthenticated header (`lib/shopify_api/webhooks/request.rb:20-23`) and then trusted by `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`).

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, excluding the `shop`-domain header. `Registry.process` validates the HMAC and then passes `request.shop` — taken straight from that unauthenticated header — into `WebhookMetadata`, which app handlers use to attribute the webhook event to a tenant. This breaks the intended binding `hmac-authenticated request == request attributed to shop X`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, on success, immediately builds `WebhookMetadata` using `request.shop`, handing this "authenticated" shop value to the registered handler: [3](#0-2) 

`HmacValidator.validate` only calls `verifiable_query.to_signable_string`, so for webhooks it checks nothing but the body bytes against the secret: [4](#0-3) 

By contrast, the OAuth `AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameters, so the same class of value (`shop`) is bound to the signature in one code path but not in the other: [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" bug class: the equality the library implicitly promises to consuming apps — `hmac_valid(raw_body) ⇒ shop_header is authentic` — does not hold. An attacker who can get one genuine webhook delivered to the app's public webhook endpoint for a topic/body they control (e.g. by triggering an event in their own store, which they fully control as an ordinary merchant/customer of that store) obtains a `(raw_body, hmac)` pair that is valid for that exact body regardless of which shop-domain header accompanies it, because the header is never part of the signed material. They can then replay that same body/HMAC to the app's endpoint with the `shop`-domain header rewritten to any victim shop, and `Registry.process` will accept it as authentic and dispatch it to the handler with `shop` set to the victim's domain.

### Impact Explanation
This crosses the tenant/authentication boundary the gem is supposed to enforce for webhook processing: an unprivileged actor (any merchant/customer able to trigger one webhook-eligible event on any shop, including their own) can cause the app to process a validated webhook body while `WebhookMetadata#shop` claims to be an arbitrary other tenant. Any host application that follows the library's documented model — "trust `shop` on a webhook whose HMAC has been validated by this gem" — will attribute attacker-controlled event data to a victim shop, which can pollute victim-tenant state, trigger tenant-scoped side effects (e.g., using the victim's stored session/access token to act on Shopify's API), or otherwise cross the tenant isolation boundary. This matches the "cross-tenant access" class of Critical impact.

### Likelihood Explanation
The prerequisite is only that the attacker can obtain one genuine `(raw_body, hmac)` pair for a webhook topic used by the target app — trivially achievable by installing the app on their own development/trial store (a normal, unprivileged action) and triggering the event, then replaying the captured HTTP request against the same public webhook endpoint with a modified shop-domain header. No access token, `client_secret`, or privileged credential is required, and the HMAC check by design passes.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header value in the HMAC-signable string for `Webhooks::Request`, mirroring what `Auth::Oauth::AuthQuery` does for `shop`. At minimum, `Registry.process` should refuse to trust `request.shop` unless it is cryptographically bound to the same signature that was validated, e.g., by having `HmacValidator` verify a canonical string composed of `shop + topic + raw_body` rather than `raw_body` alone.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook-eligible event (e.g., `orders/create`) so Shopify sends a genuine webhook to the app's public endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's real `api_secret_key`.
2. Capture the raw HTTP request (`raw_body`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`).
3. Replay the same request to the same app endpoint, changing only `X-Shopify-Shop-Domain` from `attacker.myshopify.com` to `victim.myshopify.com`.
4. `Webhooks::Request.new` accepts the headers (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — the value the attacker did not modify — so validation succeeds.
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop event, demonstrating cross-tenant webhook spoofing.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
