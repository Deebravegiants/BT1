### Title
Webhook HMAC signature does not cover the `shop` (or `topic`/`api_version`/`webhook_id`) identity headers, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop identity used to route and process a webhook from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. Because the shop identifier that the host application acts on is never included in the signed material, an attacker who possesses one validly-signed webhook payload (e.g. from their own shop, since all shops share the same app `client_secret`/webhook signature) can replay it against the app's webhook endpoint with a different `shop-domain` header and the check still passes, causing the app to process the event as if it originated from a different (victim) tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` define what is authenticated: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; none of `topic`, `shop`, `api_version`, or `webhook_id` (all parsed from headers via `shopify_header`) are part of the signed string: [2](#0-1) 

`HmacValidator.validate` verifies exactly (and only) `to_signable_string` against the received HMAC: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards the *unauthenticated* `request.shop` value straight to the handler as the tenant identity: [4](#0-3) 

This breaks the intended identity binding:

`HMAC(secret, raw_body) == received_hmac` should imply `shop header == shop that produced raw_body`, but the code only proves `HMAC(secret, raw_body) == received_hmac`; the `shop` (and `topic`/`webhook_id`/`api_version`) fields are attacker-controlled and unauthenticated, so the equality the host application actually relies on (`data.shop == the tenant that generated this payload`) does not hold.

Because Shopify apps typically share a single `api_secret_key` across all installed shops, any merchant with the app installed (including a malicious one, using their own store) can capture a legitimately Shopify-signed webhook for their own shop and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `Registry.process` will validate the HMAC (since the body is untouched) and dispatch the handler with `shop: <victim-shop>`, causing the host app to apply the attacker's payload/body data under the victim's tenant record.

### Impact Explanation
This is a cross-tenant identity confusion: the receiving application is tricked into attributing webhook data to a shop that did not actually generate it. Depending on how the host app's webhook handlers use `data.shop` (e.g., to look up/update per-shop records, toggle subscription/billing state, or trigger app-uninstall/GDPR cleanup logic keyed by shop), this can lead to writes, deletions, or state changes performed against another merchant's tenant data — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger at least one legitimately Shopify-signed webhook delivery to the app (trivial for any merchant who has the app installed on their own store, since they fully control activity that generates webhooks, e.g. product/order updates) and then replay that captured `(body, hmac)` pair to the app's public webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret` or a stolen access token is required — only observation of one's own legitimately delivered webhook.

### Recommendation
Include the shop domain (and ideally the other routing headers used to make trust decisions: `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind the `shop` header value to the signed body before it is used to construct `WebhookMetadata`. At minimum, `Request#to_signable_string` should be changed so that verification fails if the `shop-domain` header is altered relative to what was originally signed by Shopify, e.g. by validating shop-domain format/ownership independently (via `ShopValidator`) is not sufficient by itself — the binding to the specific signed payload is what's missing.

### Proof of Concept
1. App merchant "Attacker" installs the public app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g., updates a product), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`, and `api_secret_key` is shared across all installs of the app) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `hmac_validator.rb` only checks `HMAC(api_secret_key, B) == H`, which still holds, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) accepts the request and invokes the handler with `shop: "victim-shop.myshopify.com"`, `body: <attacker-controlled B>` — despite this event never having been produced for `victim-shop`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
