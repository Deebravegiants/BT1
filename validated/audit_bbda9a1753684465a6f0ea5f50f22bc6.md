### Title
BEEFY consensus threshold check counts raw signature entries instead of unique authority signers, allowing a duplicated single signature to satisfy the supermajority requirement - (File: `modules/consensus/beefy/verifier/src/lib.rs`, `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
The BEEFY consensus verifier (both the Rust `pallet-ismp` client and the Solidity `EcdsaBeefy` contract) determines whether a relay-chain commitment has reached the 2/3+1 supermajority by counting the raw number of `(index, signature)` entries submitted in the proof, not the number of distinct authorities that actually produced a valid, unique signature. There is no check that rejects a proof containing the same `(authority_index, signature)` pair repeated multiple times before that count is compared against the threshold.

### Finding Description
In `verify_mmr_update_proof`, the threshold gate runs before any duplicate detection: [1](#0-0) 

`signatures_length` is simply `mmr.signed_commitment.signatures.len()` — the raw count of entries in the caller-supplied `Vec<SignatureWithAuthorityIndex>`. Nothing here deduplicates by `sig.index` or by the recovered signer address before comparing against `check_participation_threshold`. [2](#0-1) 

The loop that follows recovers a signer address per signature entry and pushes it, along with the caller-supplied `sig.index`, into `authority_leaves` / `authority_indices`, which are then fed into `MerkleProof::verify`. If the same signature is submitted twice under the same `index`, both entries recover to the *same* signer address and hash to the *same* leaf value at the *same* claimed position in the authority-set merkle tree. Nothing in this code path requires `authority_indices` to be a set of distinct positions before calling `verify` — the uniqueness constraint (if any) is delegated entirely to the external merkle-proof library's multi-proof algorithm, which is not designed to enforce signer uniqueness; it is designed to prove that a given set of (index, leaf) pairs are consistent with a root, and a repeated (index, leaf) pair is trivially consistent with itself.

`check_participation_threshold` itself performs no deduplication either: [3](#0-2) 

The identical pattern exists in the Solidity verifier, which is the on-chain analog reachable by any relayer submitting a consensus proof to `IHandlerV2`/`ConsensusRouter`: [4](#0-3) 

`sigLen` is `relayProof.signedCommitment.votes.length` (raw count), used directly in `checkParticipationThreshold(sigLen, authoritySet.len)` before any dedup, and the subsequent `MerkleMultiProof.VerifyProof` call is given `authorities[]` built from possibly-repeated `vote.authorityIndex`/`authority` pairs with no uniqueness enforcement in between.

This is precisely the bug class in the `tough` advisory: the code confirms a *count* of signatures meets a threshold without confirming those signatures come from a *set of unique keys*. Here, an actor who controls (or has obtained, e.g. through a leaked/compromised single validator key or by replaying a captured gossip signature) just one valid BEEFY authority signature over a commitment can pad the `signatures`/`votes` array with repeated copies of that one signature (at the same claimed index, or even at different claimed indices where the merkle library does not itself enforce that a claimed index's leaf hash must correspond to the authority actually occupying that slot beyond the one proof check) to inflate the raw count past the 2/3+1 threshold, without needing 2/3+1 *distinct* validators to have actually signed.

By contrast, the codebase demonstrates elsewhere that the maintainers are aware of and defend against this exact class of bug — the Pharos verifier explicitly rejects duplicate participant keys before applying its stake threshold: [5](#0-4) 

and the Tendermint verifier explicitly rejects duplicate validator addresses in a validator set: [6](#0-5) 

No equivalent "duplicate signer/index" guard exists in the BEEFY verifier (Rust or Solidity) prior to comparing signature count against `check_participation_threshold`/`checkParticipationThreshold`.

### Impact Explanation
BEEFY consensus proofs are the root of trust that Hyperbridge uses to admit finalized relay-chain/parachain state (and, transitively, cross-chain message commitments) into `EvmHost`/`ismp-beefy`. If the supermajority requirement can be satisfied by duplicating a single authority's signature rather than collecting 2/3+1 independent signatures, an attacker who compromises or colludes with far fewer than 2/3+1 authorities (potentially just one) could get a forged/malicious commitment accepted as finalized. That would let forged parachain header state commitments and MMR roots be accepted, enabling forged message delivery and unsound state commitment acceptance across the bridge — a High severity impact matching the CWE-347 (Improper Verification of Cryptographic Signature) class in the referenced advisory.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid signature from a member of the currently trusted authority set over the attacker-chosen (or a legitimately observed) commitment — the same starting requirement as the advisory ("remote authenticated users ... duplicating a valid signature"). Given that BEEFY proofs are submitted by unprivileged, permissionless provers/relayers via ordinary transactions/extrinsics (as described in the docs on provers), the delivery path is reachable by any external submitter; the only additional requirement is possession of one authority signature, which could arise from key compromise, an insider validator acting maliciously (single actor, not "malicious governance"), or replay of an honestly-produced signature from a legitimate but small commitment. This is a plausible, non-trivial-but-realistic attack precondition, consistent with the CVSS `AC:H/PR:L` rating in the source advisory.

### Recommendation
Before comparing signature count to the supermajority threshold in both `verify_mmr_update_proof` (`modules/consensus/beefy/verifier/src/lib.rs`) and `verifyMmrUpdateProof` (`evm/src/consensus/EcdsaBeefy.sol`):
1. Deduplicate by recovered signer address (or by claimed authority index) and reject the proof if any duplicate is found, mirroring the `DuplicateParticipant` check already used in `modules/consensus/pharos/verifier/src/lib.rs` and the `ensure_unique_addresses` check in `modules/consensus/tendermint/verifier/src/verifier.rs`.
2. Use the deduplicated/unique count (not the raw vector length) as the input to `check_participation_threshold` / `checkParticipationThreshold`.

### Proof of Concept
1. Obtain one valid BEEFY authority signature `sig` (index `i`) over a target commitment (e.g., a legitimately observed signature, or one from a single compromised/colluding validator).
2. Construct a `SignedCommitment`/`RelayChainProof` whose `signatures`/`votes` array repeats `(i, sig)` `⌈2/3 * total_authorities⌉ + 1` times (or duplicates a small set of genuinely-held signatures enough times to reach the threshold).
3. Submit this as `ConsensusMessage`/`RelayChainProof` to `verify_consensus`/`EcdsaBeefy.verify`.
4. `signatures_length`/`sigLen` (raw count) passes `check_participation_threshold`/`checkParticipationThreshold` because duplication is not filtered out.
5. Each duplicated entry recovers to the same valid authority address and produces a merkle leaf that is consistent with itself at the claimed index, so `MerkleProof::verify`/`MerkleMultiProof.VerifyProof` does not reject the duplication.
6. The commitment (and any parachain header state commitments/MMR root advance it carries) is accepted as finalized despite lacking genuine 2/3+1 unique-authority participation.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}

/// Rejects a validator set that reuses the same address twice. Each address is a
/// hash of its public key, so a duplicate signals a set that was not built honestly.
fn ensure_unique_addresses(
	validators: &[cometbft::validator::Info],
) -> Result<(), VerificationError> {
	let unique = validators.iter().map(|v| v.address).collect::<BTreeSet<_>>();
	if unique.len() != validators.len() {
		return Err(VerificationError::ValidatorSetError(
			"duplicate validator address in set".to_string(),
		));
	}
	Ok(())
}
