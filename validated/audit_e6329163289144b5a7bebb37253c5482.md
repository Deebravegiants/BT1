### Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The bug class described in the external report is an inverted/incomplete integrity check that lets data outside the verified boundary be trusted as if it were verified. In this gem, the analogous flaw is in `ShopifyAPI::Webhooks::Request` / `ShopifyAPI::Webhooks::Registry.process`: the only integrity check performed is an HMAC over the raw body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values that identify *which tenant* the webhook belongs to are read directly from HTTP headers that are **not covered by the HMAC**. The binding that should hold is:

`hmac_verify(body) == true` should imply `(body, shop) is authentic`,

but the actual binding enforced is only

`hmac_verify(body) == true`, independent of `shop`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for a webhook `Request`, that signable string is defined as just the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are pulled straight from headers with no cryptographic linkage to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` and `request.topic` (unauthenticated headers) as the tenant identity forwarded to the app's handler: [3](#0-2) 

The resulting `WebhookMetadata` struct — the only data surface handed to the host application — carries `shop` as an unauthenticated field: [4](#0-3) 

The documentation explicitly instructs developers to use `data.shop` as the shop identity for routing/attributing webhook data to a tenant, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`: [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant who has installed the app receives genuine webhook deliveries with a valid HMAC over the body content computed with that shared secret. Since the header set (`shop-domain`, `topic`, `webhook-id`, `api_version`) is completely outside the HMAC's scope, a malicious/compromised merchant can capture one of their own legitimately-signed webhook bodies and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a different (victim) shop. `HmacValidator.validate` will still return `true` because the body is unchanged and the signature is still correct for that body, and `Registry.process` will pass the forged `shop` value straight through to the handler as though it were verified.

### Impact Explanation
This breaks the tenant isolation boundary the whole HMAC check exists to enforce, letting an attacker who already has (or previously had) legitimate app access for their own shop inject data attributed to another shop into the host application's webhook processing pipeline — i.e. cross-tenant data injection/impersonation using webhook payloads (e.g., GDPR `customers/redact`, `orders/create`, `app/uninstalled`, etc. processed under a spoofed `shop`). This matches the in-scope "Critical – cross-tenant access" impact category, since the security boundary the gem is documented to enforce (verify the webhook truly originated for a given shop) can be defeated without possessing `api_secret_key` or any privileged credential beyond normal app installation on one's own store.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control (or previously have installed) a shop that receives webhooks from the target app, which is a low bar for a public/embeddable app (any Shopify merchant can install most public apps). No access to `api_secret_key`, TLS interception, or social engineering is required — only capturing one's own legitimate webhook traffic (e.g., via a proxy they control) and replaying it with a modified header to the app's public webhook endpoint.

### Recommendation
Bind the tenant-identifying values into the signed material, or otherwise verify them independently of the header values before trusting them:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (Shopify's own HMAC computation is over the raw body only per their spec, so this may require validating `shop` against a store of legitimately-registered shops/sessions rather than trusting the header blindly), and/or
- Cross-check the header `shop` against the shop for which the specific `webhook_id`/registration was created (e.g., only accept webhooks for shops that have an active, matching session/subscription), and
- Document clearly to consumers of this gem that `data.shop` is not itself covered by the HMAC and must be corroborated against known/authenticated shop records before being trusted for tenant-sensitive operations.

### Proof of Concept
1. App developer registers a webhook handler per `docs/usage/webhooks.md`, using `data.shop` to route/attribute incoming webhook data to a tenant record, as shown in the documented example (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).
2. Attacker installs the app on `attacker-shop.myshopify.com` and captures a legitimate webhook delivery (raw body `B` and its valid `x-shopify-hmac-sha256` header `H`, computed by Shopify using the app's shared `api_secret_key`).
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and same signature `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` only (`Request#to_signable_string`) and it matches `H`, so validation succeeds (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is `"victim-shop.myshopify.com"` — a shop for which the body was never actually generated (`lib/shopify_api/webhooks/registry.rb:188-200`).
6. The host application processes/attributes body `B`'s data as belonging to `victim-shop.myshopify.com`, a cross-tenant integrity violation.
