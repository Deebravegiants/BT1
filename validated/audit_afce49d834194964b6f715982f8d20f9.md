I have enough evidence to confirm the vulnerability. The webhook `Request` class computes its HMAC signable string from the raw body only, while the `shop` (and `topic`) fields used by the handler are taken from HTTP headers that are never included in the HMAC computation.### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`) values consumed by `ShopifyAPI::Webhooks::Registry#process` are taken from HTTP headers that are never included in the HMAC-signed payload. This breaks the intended identity binding: "HMAC-verified bytes" == "bytes that determine which shop the webhook is attributed to."

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

and `Request#shop` simply reads the `shopify-shop-domain` (or `x-shopify-shop-domain`) header without any cryptographic binding to the HMAC:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (the raw body):
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry#process` then trusts the unauthenticated `request.shop` value to build `WebhookMetadata` and dispatch it to the handler as the tenant identity for that webhook:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Shopify computes the webhook HMAC using the app's single, shop-independent `client_secret` (`Context.api_secret_key`) over the raw body only — the same secret is valid for every shop that has installed the app. Consequently, the equality that should hold is:

`shop attributed to webhook by handler` == `shop whose data actually produced the HMAC-signed body`

but the code only enforces:

`HMAC(raw_body, api_secret_key)` == `received_hmac`

with `shop` supplied entirely out-of-band via a header that carries no cryptographic guarantee.

### Impact Explanation
Because the app's webhook secret is shared across all shops (it's the app's `client_secret`, not a per-shop secret), any unprivileged merchant who has installed the app can capture a legitimate, validly-signed webhook delivered to their own store (body + `X-Shopify-Hmac-Sha256` header) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still pass (it never looked at the domain header), and `Registry#process` will hand the attacker-controlled body to the registered handler tagged as `shop: <victim-shop>`. Any application logic that trusts `WebhookMetadata#shop` to select which tenant's data/session to update (e.g. `shop/redact`, `customers/redact`, `orders/*`, inventory or fulfillment updates) can be corrupted with forged data attributed to a different tenant, i.e. cross-tenant data injection/confusion.

### Likelihood Explanation
Any developer/merchant who can install the target app (a normal, unprivileged action) gains a validly HMAC-signed webhook body for their own shop, which is trivial to capture (it is delivered to their own registered endpoint or can be intercepted/logged by their own infrastructure) and replay against the shared endpoint with a modified shop header — no access to the app's `client_secret` or any victim credentials is required.

### Recommendation
Include the shop domain (and ideally the topic, and webhook id) as part of the bytes that are HMAC-verified — i.e., derive `shop`/`topic` only from data that is cryptographically bound to the signed body (or use Shopify's newer verification schemes that incorporate these header values into the digest), rather than trusting the `X-Shopify-Shop-Domain` header independently of the signature check in `Request#to_signable_string` / `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, becoming a legitimate, unprivileged webhook recipient.
2. Shopify sends the attacker a legitimately signed webhook, e.g. for `customers/data_request`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw body under app's client_secret>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - body: `{"customer": {...attacker-controlled fields...}}`
3. Attacker replays the exact same raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — the check passes because the body and HMAC are unchanged. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker body>, ...)` and performs whatever tenant-scoped action (data deletion, record update, notification) as if it genuinely came from the victim shop. [6](#0-5)
