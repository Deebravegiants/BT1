### Title
Unsafe underlying token transfer via unchecked low-level `.call` in `IntentGatewayV2` (Tron) escrow withdrawal and dust sweep - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` replaces the `SafeERC20`-wrapped transfers used in the canonical EVM `IntentGatewayV2` with raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls that only check the outer `success` boolean of the call, never decoding/validating the ERC20's own returned boolean. This is the exact "unsafe underlying token transfer" bug class from the referenced report: tokens that return `false` on failure instead of reverting will cause the contract to believe the transfer succeeded.

### Finding Description
In `withdraw()`, escrowed token releases for `RedeemEscrow`/`RefundEscrow` requests are performed with: [1](#0-0) 
and the accumulated fee redemption: [2](#0-1) 
Both only check that the low-level `call` did not revert (`success`), then unconditionally decrement `_orders[...]`, mark the order as filled (`_filled[body.commitment] = beneficiary`), and emit `EscrowReleased`/`EscrowRefunded`. The same unchecked pattern appears in the `SweepDust` incoming-request handler: [3](#0-2) 
and in the `placeOrder` predispatch sweep-back path: [4](#0-3) 
None of these decode the returned bytes to confirm the ERC20 actually returned `true`; a call to a non-reverting-but-failing token (returns `false`) is treated as a fully successful transfer. This deviates from the canonical (non-Tron) `IntentGatewayV2.sol` and `IntentsBase.sol`, which consistently use `SafeERC20.safeTransfer`/`safeTransferFrom` (e.g. `IntentsBase._withdraw`): [5](#0-4) 

### Impact Explanation
`withdraw()` is reached by any relayer delivering a `RedeemEscrow`/`RefundEscrow` ISMP POST request or a `SweepDust` governance-relayed message — i.e., a normal, unprivileged message-delivery path through the ISMP host (`onAccept`). If the escrowed token (or fee token) is one that returns `false` on failed transfer rather than reverting, the contract will still: (1) decrement the internal escrow accounting `_orders[commitment][token]`, (2) mark the order filled, and (3) emit a success event — while the tokens never actually leave the contract to reach the beneficiary. This causes permanent loss/freezing of the user's escrowed funds: the beneficiary receives nothing, but the order is irreversibly marked as filled/refunded so it can never be redeemed again, and the tokens remain stuck in the contract's balance. This is a concrete permanent freezing/loss-of-funds impact reachable from a single relayed message.

### Likelihood Explanation
Likelihood depends on whether tokens escrowed/bridged via this Tron intents gateway include non-standard ERC20/TRC20 tokens that return `false` instead of reverting on failure (common on Tron, where several TRC20 tokens follow this looser convention). Given the intents gateway is designed to be permissionless for arbitrary `TokenInfo.token` addresses supplied by users in `placeOrder`, and Tron's TRC20 ecosystem has a higher prevalence of non-reverting-on-failure tokens than typical EVM ERC20s, the likelihood of encountering such a token is non-trivial and directly exploitable by any user placing an order with such a token, or by a relayer processing a `RedeemEscrow` for one.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `SafeERC20.safeTransfer`/`safeTransferFrom`, consistent with the canonical `IntentsBase.sol`/`evm/src/apps/IntentGatewayV2.sol` implementations, so that both call-level reverts and false-boolean-return failures cause the transaction to revert rather than being silently treated as success.

### Proof of Concept
1. Deploy a TRC20/ERC20-like token whose `transfer` function returns `false` on failure instead of reverting (e.g., insufficient balance edge case, or a deliberately malicious/non-compliant token registered as an intent input/output asset).
2. A user calls `placeOrder` with this token as an input asset; tokens are escrowed via `IERC20(token).safeTransferFrom(...)` (this path is safe) into `_orders[commitment][token]`.
3. A relayer delivers a `RedeemEscrow` message for the order via `onAccept` → `withdraw(body, false)`.
4. Inside `withdraw`, `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));` — if the token's `transfer` returns `false` without reverting, `success` is `true` (the call itself succeeded), so the check `if (!success) revert TransferFailed();` passes.
5. `_orders[body.commitment][token] -= amount;` executes, `_filled[body.commitment] = beneficiary;` is set, and `EscrowReleased` is emitted — even though the beneficiary never received the tokens.
6. The order can never be redeemed again (already marked filled), and the tokens remain permanently stuck in the `IntentGatewayV2` contract balance: permanent fund freeze/loss for the beneficiary.
