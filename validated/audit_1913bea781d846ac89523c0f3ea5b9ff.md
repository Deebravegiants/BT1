### Title
Unrecoverable escrow freeze when a poisoned/blocked token permanently fails transfer in `IntentGatewayV2.withdraw()` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the IntentGateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements escrow release with raw low-level `.call()` ERC20 transfers that `revert TransferFailed()` on failure, and, unlike the main EVM host's `EvmHost.dispatchIncoming` (`evm/src/core/EvmHost.sol:794-818`), there is no evidence in the reviewed code that failed `onAccept` deliveries on this path are swallowed non-atomically per request instead of failing the whole withdrawal permanently for that commitment, with no fallback recovery function.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol:691-730` iterates over `body.tokens[]` and, for ERC20 tokens, does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

This function is invoked from `onAccept` when handling `RedeemEscrow`/`RefundEscrow` requests delivered via ISMP (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-635`), and from `onGetResponse` for source-chain cancellation refunds (`evm/tron/contracts/apps/IntentGatewayV2.sol:738-743`). If the `beneficiary` is blacklisted by the ERC20 (a well-known real-world condition for tokens like USDC/USDT) or the token is paused, the `token.call` returns `success=false` and the whole `withdraw()` call reverts with `TransferFailed()`. This mirrors exactly the bug class in the external report: a `transfer()` failure inside the settlement/end path reverts the entire transaction, and because `_orders[body.commitment][token]` accounting and `_filled[body.commitment]` are only updated inside this same reverting call, there is no partial progress and no alternate recovery path (no `clearBid()`-equivalent) to release the other tokens in the same `WithdrawalRequest`, or to redirect funds to a non-blacklisted beneficiary.

Whether this reverts the top-level ISMP delivery (and is retried non-atomically per message the way the main EVM host does, per `evm/src/core/EvmHost.sol:794-818` and the flow doc `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md:10-13`) depends on the Tron host's `dispatchIncoming` implementation, which was not found in the indexed `evm/tron/**` contents (no `dispatchIncoming`/`onAccept.selector` matches). This is a gap in what I could verify from the index — it is possible the Tron host mirrors `EvmHost`'s graceful non-reverting dispatch, in which case only that specific commitment's escrow (not the whole batch) is affected but still permanently frozen for as long as the beneficiary/token remains blocked, with no `clearBid()`-style recovery function present anywhere in the reviewed `IntentGatewayV2.sol`/`IntentsBase.sol` code.

### Impact Explanation
If confirmed, escrowed input tokens (`RedeemEscrow`) or refund tokens (`RefundEscrow`) for a specific order commitment become permanently locked in the contract whenever the beneficiary/solver address is blacklisted by the token or the token is paused at settlement time — a realistic scenario for common stablecoins. There is no `clearBid()`/force-release mechanism to redirect or split out the stuck token while releasing the rest, unlike the fix pattern described in the external report (balance/withdraw decoupling). This is a permanent freezing-of-funds condition reachable by a normal, unprivileged flow (placing an order and having it settled/refunded through the standard relayed ISMP message).

### Likelihood Explanation
Requires a token with blacklist/pause functionality being used as an input/output/fee token and the beneficiary being blocked at the time of settlement — a plausible but not universal condition, and outside the attacker's control unless the attacker can get themselves blacklisted or is targeting a token they know is paused. I was not able to fully verify whether the Tron host layer isolates per-message failures the way `EvmHost` does, which affects whether the blast radius is limited to a single commitment or can stall processing of other messages in the same delivery batch.

### Recommendation
Adopt the same balance/withdraw decoupling pattern referenced in the external report: track a per-beneficiary claimable balance in `_withdraw`/`withdraw` instead of pushing tokens via `.call`/`safeTransfer` inline, and expose a separate `claim()`/`withdraw()` entry point beneficiaries can call once their address is no longer blocked. Alternatively, wrap each token transfer in `withdraw()` in a try/catch (or low-level call without `revert`), decrement escrow only for tokens that succeeded, and emit a `PartialWithdrawal`/`StuckToken` event for tokens that failed, allowing them to be retried or swept later — mirroring the non-reverting pattern already used in `EvmHost.dispatchIncoming` (`evm/src/core/EvmHost.sol:809-816`).

### Proof of Concept
1. User places a cross-chain order with `order.inputs` containing a blacklist-capable ERC20 (e.g., a USDC-like token) and `order.output.beneficiary`/solver address `S`.
2. Token issuer blacklists `S` (or the token gets paused) before settlement.
3. Solver fills the order on the destination chain; `RedeemEscrow` is dispatched back to the source chain.
4. On the Tron source chain, `onAccept` → `withdraw(body, false)` executes `token.call(transfer(S, amount))`, which returns `false` because `S` is blacklisted.
5. `withdraw()` reverts with `TransferFailed()` at `evm/tron/contracts/apps/IntentGatewayV2.sol:707` before `_orders[commitment][token]` is decremented or `_filled[commitment]` is set.
6. The escrowed input tokens for this commitment remain locked in the contract indefinitely; every retry of the same message hits the same blacklist condition, and no function in the contract exists to reroute or force-release the stuck tokens. [2](#0-1) [3](#0-2)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
