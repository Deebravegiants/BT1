### Title
Attacker-controlled `assets` registry lets a rogue hop "pool" escape the routed scope and drain the caller's wallet under the caller's own auth tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
CVE-2019-10218 is a path-traversal class bug: a malicious SMB server embeds separators in a pathname, and the trusting client operates outside the intended directory. The direct analog lives in the swap router: the `StrategyPayload.assets` registry is a fully caller/attacker-controlled list of addresses, and `execute_op` invokes `assets[idx_a]` as the hop pool with no allowlist, no code-identity check, and no constraint that the address is a real DEX pool. A malicious route submitted to a victim (or injected via a compromised quote path) names an attacker contract as the pool. That contract executes inside the victim's `require_auth` invocation tree and calls `token.transfer(victim, attacker, amount)` on any token the victim holds — escaping the intended "swap only `token_in` for `token_out`" scope exactly as a `../` escape escapes the intended share. The router's balance-delta measurement and min-out check only bound the routed amount; they do not bound what the rogue pool does with the caller's ambient authority.

### Finding Description
`execute_strategy` decodes `StrategyPayload` and resolves every hop's `pool` straight out of the caller-supplied `assets` vector (`contracts/swap-aggregator/src/execute/mod.rs:152-158`). `dispatch_hop` then calls that address through the venue adapter (`contracts/swap-aggregator/src/venues/mod.rs:34-40`). Because Soroban authorization is tree-based, any `require_auth` performed by the rogue pool — e.g. `token::Client::transfer(victim, attacker, X)` — is recorded by simulation as a child of the victim's signed root invocation and executes when the victim signs the simulated tree. The threat model itself states: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount" (`docs/explanation/threat-model.md:154-160`).

The same exposure reaches the controller strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`), since they forward the caller's `swap_xdr` route bytes to the configured router, and it applies identically to direct `execute_strategy(sender, total_in, swap_xdr)` calls.

The harness proves exploitability end-to-end: `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows a `RogueHopPool` named by the route transferring the victim's entire `wallet_token` balance to the attacker while still delivering a fair swap output (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`), and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` confirms the signed simulated tree authorizes the theft (`:265-268`).

### Impact Explanation
Theft of user funds: the victim loses arbitrary wallet tokens unrelated to the routed swap, bounded only by wallet balances and what the signed auth tree covers. The routed swap itself still succeeds with correct measured output, so on-chain settlement is indistinguishable from a fair trade — the theft is a side effect of the poisoned route escaping its declared scope, the exact shape of the Samba pathname-separator escape.

### Likelihood Explanation
Requires social/delivery of a malicious route the victim signs (e.g., a compromised or fake quote server, phishing dApp), matching the CVSS user-interaction vector of the original CVE. No privilege, upgrade, or key material is needed; the attacker only needs a deployed rogue contract and a route XDR. The defense is entirely off-chain (clients must decode `routeXdr` and reject unexpected auth-tree children per `skills/xoxno-swap-aggregator/payload.md:154-210`), which is thin mitigation for any client that trusts the quote server verbatim — the threat model concedes "The direct `execute_strategy` path has the same exposure for every swap user." Rated Medium/High on impact with the CVE's UI:R likelihood profile.

### Recommendation
Constrain the scope a route can reach, the on-chain analog of rejecting separators in server-supplied names:

- Maintain a governance-managed pool/venue allowlist (or per-venue pool registry) in the router, and reject any `assets[idx_a]` not on it for Swap/Burn/Mint opcodes.
- Alternatively/additionally, have the controller and router bind `token_in`/`token_out` to the markets declared in the calling strategy (the controller already knows the listed hub assets) and reject payload head/tail mismatches — it currently checks only measured deltas and final risk.
- Document as enforced, not advisory: ship the auth-tree verification (`verifyRouteBytes` plus a child-invocation audit of the simulated envelope) inside the official SDK path so unsigned-injection routes fail before signing.

### Proof of Concept
Existing harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Deploy `RogueHopPool` whose `swap()` executes `token::Client::new(&wallet_token).transfer(victim, attacker, WALLET_BALANCE)` (`:62-71`).
2. Register a router conforming to `execute_strategy` that invokes the payload-named pool and pays a fair `min_out` (`:39-47`); production router behaves the same since `dispatch_hop` invokes `assets[idx_a]` unchecked.
3. Alice calls `ctrl.swap_collateral(alice, account_id, USDC, amount, ETH, route)` where `route`'s `assets` contains the rogue pool (`:147-157`).
4. Simulation records `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child of her `swap_collateral` auth entry (`:206-222`); she signs it as an ordinary swap.
5. Result: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the swap still settles (`supply_balance_raw(ALICE, "ETH") == FAIR_OUT_ETH`) (`:224-226`).
