## Finding

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted but not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only ever authenticates the byte content of the body against the app's shared `api_secret_key` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are never part of the signed data [3](#0-2) . `Registry.process` checks only the HMAC validity and then dispatches to the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values [4](#0-3) .

### Finding Description
This is the same bug class as the report's core issue: a value that is *acted upon* (here, the `shop` attribution of a webhook event) is not the value that is *cryptographically verified* (here, only the raw body bytes are HMAC-verified). The binding that is broken is:

`shop authenticated by HMAC` ≠ `shop used by the handler (request.shop from header)`

Since a single Shopify app uses the **same** `api_secret_key`/client secret to sign webhooks for **every** shop that installs it (this is a multi-tenant app, by design), any unprivileged internet user can:
1. Install the target app on a store they themselves control (this requires no special privilege — installing a public/listed app on your own store is an ordinary, unauthenticated-from-the-app's-perspective action).
2. Receive a genuine, correctly-signed webhook delivery for their own shop (valid `raw_body` + valid `x-shopify-hmac-sha256`).
3. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but swap the `x-shopify-shop-domain` header to a victim shop's domain (and/or `x-shopify-topic`/`x-shopify-webhook-id` to a topic/id of their choosing).
4. `HmacValidator.validate` still succeeds, because it only checks the raw body against the shared secret — it never binds the signature to the shop or topic claimed in the headers.
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) , attributing attacker-chosen body content to an arbitrary victim shop.

Any app built on this gem that uses `data.shop` from the webhook handler to look up/update per-tenant records (the documented, expected usage pattern) will process attacker-supplied data as if it originated from the victim shop, without any tenant-boundary check.

### Impact Explanation
This crosses a tenant boundary without any credential of the victim shop: an attacker with a normal, un-elevated installation of the app on their own store can inject webhook events attributed to a different merchant's shop. Depending on how the host app uses `data.shop` (e.g., to find/create/update per-shop records, trigger per-shop side effects, or lookup sessions/access tokens keyed by shop), this enables cross-tenant data corruption/injection — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple, mutually-untrusted shops (the normal SaaS model for Shopify apps): the attacker only needs to install the app on their own store (an ordinary, permitted action) to obtain one valid signed payload, then replay it with a modified `shop-domain` header. No secrets, tokens, or privileged access are required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified data, or otherwise cryptographically tie the header claims to the signed body — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require callers to independently verify that `request.shop` corresponds to a shop with an active installation/session before trusting it in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-topic: orders/create`.
   - Body: attacker-controlled JSON (attacker creates an order in their own shop to control body content).
3. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (using `to_signable_string` = raw body only, per `lib/shopify_api/webhooks/request.rb` lines 35-38) returns `true`.
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, per `lib/shopify_api/webhooks/registry.rb` lines 188-199.
