### Title
Withdraw during `WithdrawOnly` status skips PnL-ratio state update, causing miscalculated LP payouts - ([File: program/src/processor.rs])

### Summary
This is analogous to the Paladin finding where an emergency-path function fails to update ratio state (`userCurrentBonusRatio`/`durationRatio`) before it's used elsewhere, causing subsequent claims to use stale/incorrect ratios. In Raydium's `process_withdraw`, the pnl-ratio bookkeeping fields (`amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin`, and the deltas `delta_x`/`delta_y` derived from `calc_take_pnl`) are conditionally skipped when `amm.status == AmmStatus::WithdrawOnly`, yet `target_orders.calc_pnl_x`/`calc_pnl_y` are unconditionally updated afterward using those (possibly stale/zero) deltas.

### Finding Description
In `process_withdraw` (`program/src/processor.rs`), the code computes `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, then conditionally calls `calc_take_pnl` to compute `delta_x`/`delta_y` and update `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin`: [1](#0-0) 

```
let mut delta_x: u128 = 0;
let mut delta_y: u128 = 0;
if amm.status != AmmStatus::WithdrawOnly.into_u64() {
    (delta_x, delta_y) = Self::calc_take_pnl(...)?;
}
```

When status is `WithdrawOnly`, `calc_take_pnl` is never invoked, so `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` are never updated for the outstanding PnL that should have been reconciled at this withdrawal point, per the same logic exercised in `process_deposit`, `process_withdrawpnl`, and normal-status `process_withdraw` paths: [2](#0-1) 

Despite skipping this update, the code unconditionally proceeds to recompute `target_orders.calc_pnl_x`/`calc_pnl_y` using `x1`/`y1` (which are normalized from the vault-derived `total_pc_without_take_pnl`/`total_coin_without_take_pnl` — the same values that would have been used inside `calc_take_pnl`) and subtracts `delta_x`/`delta_y` (which are `0` in the `WithdrawOnly` case): [3](#0-2) 

This means the pool's baseline pnl accounting (`calc_pnl_x`/`calc_pnl_y`, and by extension `need_take_pnl_pc`/`need_take_pnl_coin`) is left inconsistent with the actual vault balances once the pool is set to `WithdrawOnly`. Every subsequent withdrawal in `WithdrawOnly` mode will use a baseline (`x1`, `y1`) that never had its accrued-but-untaken PnL subtracted out (since `calc_take_pnl` was skipped), so `target_orders.calc_pnl_x/calc_pnl_y` drift from the true "principal" value they are meant to track, while `need_take_pnl_pc/coin` (used later by `process_withdrawpnl`) is never updated to reflect PnL accrued right before the mode switch to `WithdrawOnly`.

### Impact Explanation
Because `calc_pnl_x`/`calc_pnl_y` serve as the reference baseline for computing the pool's "unrealized pnl" for every future withdraw/deposit/withdrawpnl call (via `calc_take_pnl`'s comparison against `pool_pc_amount * pool_coin_amount`), a state divergence here can cause `calc_take_pnl` to later error out (`AmmError::CalcPnlError`) or silently miscompute deltas once the pool exits `WithdrawOnly`, and it under- or over-states the amount attributable to `need_take_pnl_pc/coin` (funds reserved for the pnl owner) versus the LP-share-derived `coin_amount`/`pc_amount` paid to withdrawing LPs. This can result in LPs receiving an incorrect proportion of pool funds relative to true reserves, similar to the referenced report's "user claims funds with the wrong ratio" impact.

### Likelihood Explanation
Reaching this path requires no privileged signer — any LP holding LP tokens can call `Withdraw` while the pool's `amm.status` is `WithdrawOnly` (a status normally reachable via admin operations such as pool shutdown, but the withdraw instruction itself is fully open to any LP holder with `withdraw_permission()` granted, which `WithdrawOnly` explicitly is designed to allow). Every withdrawal made while in this status contributes to the drift, making the likelihood of the accounting getting out of sync moderate-to-high in any pool that transitions through `WithdrawOnly` with multiple withdrawers.

### Recommendation
Ensure that `target_orders.calc_pnl_x`/`calc_pnl_y` updates in `process_withdraw` are only computed using values consistent with whether `calc_take_pnl` ran. Specifically, when `amm.status == AmmStatus::WithdrawOnly` and PnL-taking is intentionally skipped, either: (1) also skip updating `calc_pnl_x`/`calc_pnl_y` relative to `x1`/`y1` baseline math that assumes PnL was taken, or (2) explicitly document/verify that `WithdrawOnly` is meant to be a terminal state where PnL is permanently forfeited and confirm that skipping `need_take_pnl_pc/coin` updates does not create a mismatch for any subsequent state transition back to an active status. Add invariant checks/tests verifying `calc_pnl_x + need_take_pnl_pc` (normalized) tracks total pc reserves consistently across the `WithdrawOnly` transition.

### Proof of Concept
1. Pool is operating normally; multiple deposits/withdraws accrue outstanding PnL tracked via `target_orders.calc_pnl_x/calc_pnl_y` and `amm.state_data.need_take_pnl_pc/coin`.
2. Admin sets `amm.status = AmmStatus::WithdrawOnly` (via `SetParams`, out of scope for this PoC but establishes the precondition).
3. Any LP token holder calls the `Withdraw` instruction (`process_withdraw`) with `withdraw.amount > 0`.
4. Because `amm.status == AmmStatus::WithdrawOnly`, the branch at [4](#0-3)  skips `calc_take_pnl`, leaving `delta_x = delta_y = 0` and `need_take_pnl_pc/coin` un-incremented for any pnl that would have been recognized at this point.
5. `target_orders.calc_pnl_x`/`calc_pnl_y` are still updated at [5](#0-4)  using the unreconciled `x1`/`y1` baseline, producing a baseline that no longer matches what `calc_take_pnl` would expect on the next status transition, causing incorrect pnl/LP-share accounting for subsequent operations.

**Note**: I was unable to fully verify the exact semantics of `AmmStatus::WithdrawOnly` (e.g., whether it is designed as an irreversible terminal state where forfeiting PnL reconciliation is intentional) or confirm via the `state.rs`/status transition code whether the pool can transition back to an active status after `WithdrawOnly`, due to index/tool call limits. This affects confidence in the exploitability/severity of the accounting drift described above.
