### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values that are handed to the app's webhook handler are read directly from unauthenticated HTTP headers. The HMAC never covers these header values, so a caller who possesses *any* validly-signed webhook body (e.g. from their own store, which Shopify will happily sign for them) can re-submit that exact body while substituting the `x-shopify-shop-domain` header for a victim shop. The signature check still passes, and the handler is invoked believing the event originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is derived independently from a header that is never part of the signed content: [2](#0-1) 

`Registry.process` validates only that HMAC: [3](#0-2) 

and then forwards `request.shop` (plus `request.topic`, `request.webhook_id`) straight into `WebhookMetadata` for the handler, with no cross-check that the `shop` header matches any value that was actually part of the signed bytes.

The `HmacValidator.validate` used here only proves “this body was signed with the app's secret”, i.e. it validates:
`HMAC(secret, raw_body) == received_hmac`

It does **not** establish:
`shop_header == shop_that_signed_this_body`

Because Shopify's HMAC only ever covers the JSON body, any shop that legitimately receives signed webhooks for its own events (which is every merchant/dev-store owner who installs the app) can capture a genuine `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. The signature will still validate, breaking the equality that the endpoint implicitly assumes: *the shop claimed in the request equals the shop whose secret-derived signature was checked.*

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged party who can only see webhooks destined for their own tenant can cause the app to process arbitrary attacker-chosen webhook bodies (topic, id, and JSON payload of their choosing, since they control what happens in their own store to generate the signed body) while impersonating any other shop domain to the app's webhook handler logic. Depending on how the app's handler uses `WebhookMetadata#shop` (e.g. to look up/update per-tenant records, trigger `app/uninstalled` cleanup, process GDPR-style customer data requests, etc.), this enables cross-tenant data corruption or disclosure — matching the “cross-tenant access” Critical impact category.

### Likelihood Explanation
Likelihood is significant: any actor can install the app on a store they control (or use any store where the app is installed and they can trigger events), capture a legitimately signed webhook `(body, hmac)` pair via a simple HTTP proxy, and replay it to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only the ability to trigger one webhook event for a store the attacker controls.

### Recommendation
Bind the shop domain into the value that is actually verified. Concretely, include `shop-domain` (and ideally `topic`/`webhook_id`) as part of `to_signable_string`'s verified content is not possible since Shopify itself only signs the body — so this must instead be handled by treating the header-derived `shop`/`topic`/`webhook_id` as unauthenticated within the gem, clearly documenting that consumers must not trust `WebhookMetadata#shop` for authorization decisions without an independent shop-registration/session lookup, or by requiring/encouraging callers to cross-validate the shop domain against a known, previously-established relationship (e.g., an existing offline session for that shop) before acting on the payload. At minimum, update `ShopifyAPI::Webhooks::Registry.process` documentation/behavior to make explicit that HMAC validation only authenticates the body bytes, not the `shop`, `topic`, or `webhook_id` headers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (or any store where they can trigger a webhook, e.g. `orders/create`).
2. Attacker triggers a webhook event in their own store; Shopify sends:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body with app secret>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: ...
   <raw_body JSON>
   ```
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256`, but changes the header to:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — this still succeeds because `raw_body` and `hmac` are unmodified.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker-controlled JSON>, ...)`, causing the app to act on attacker-controlled data as if it came from `victim.myshopify.com`. [3](#0-2) [4](#0-3)
