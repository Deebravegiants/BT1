## Finding

### Title
Cross-chain intent fill hardcodes the `RedeemEscrow` beneficiary to the filler's own `msg.sender`, permanently freezing escrow if that address cannot receive funds on the source chain - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
The reported LiFi/Connext bug hardcodes the `recovery` parameter to `msg.sender` when dispatching a cross-chain call, which can strand funds if that address is a smart contract that either doesn't exist or cannot accept the asset on the destination domain. Hyperbridge's `IntentGatewayV2` cross-chain fill flow has the identical pattern: the address that will later receive the *escrowed input tokens on a different chain* is hardcoded to the filler's own `msg.sender` on the destination chain, with no way for the filler to specify a different, chain-appropriate recipient.

### Finding Description
When a solver fills a cross-chain order, `_fillCrossChain` in `ExtrinsicIntents.sol` builds the `RedeemEscrow` message with the beneficiary hardcoded to the caller's own address on the *destination* chain: [1](#0-0) 

This message is dispatched via Hyperbridge to the *source* chain, where `onAccept` decodes it and calls `_withdraw`, which releases the escrowed input tokens directly to that same address: [2](#0-1) 

For native-token inputs, `_withdraw` uses `_sendValue`, which **reverts the entire withdrawal** if the low-level call to the beneficiary fails: [3](#0-2) 

If the filler's address is a smart contract (e.g. a solver contract, multisig, or the documented `SolverAccount` used for ERC-4337/EIP-7702 batching) that either has no code deployed at that address on the source chain, or has code there that rejects plain native-value transfers (no `receive`/payable fallback, or a fallback that reverts under certain conditions), the `RedeemEscrow` delivery on the source chain will always revert. Per the ISMP handler design, a reverting `on_accept`/`onAccept` does **not** persist a receipt, so the request is retried indefinitely but can never succeed: [4](#0-3) 

Because `_fillCrossChain` already marks the order as filled on the destination chain (`_filled[commitment] = msg.sender`) before this message is ever delivered, the destination-side cancellation path is blocked (`Filled()` on any competing cancel/fill), and the source-side escrow can only ever be released via this one `RedeemEscrow` message to the hardcoded beneficiary. There is no function that lets the filler, the order creator, or governance redirect the beneficiary or otherwise recover the escrowed input tokens once this state is reached.

Additionally, since `_withdraw` iterates over *all* of `order.inputs` in a single call, a revert on the native-token leg reverts the whole function — so even non-native ERC20 inputs in the same order become permanently stuck alongside the native ones.

The equivalent Tron deployment (`evm/tron/contracts/apps/IntentGatewayV2.sol`) has the same pattern (`withdraw()` with `if (!sent) revert InsufficientNativeToken();`), so the issue is not limited to a single implementation.

### Impact Explanation
This results in permanent freezing of user funds (the escrowed order inputs) with no recovery mechanism, triggered entirely by an ordinary, unprivileged actor (a solver/filler) calling `fillOrder` with their own address — no malicious admin, governance, or off-chain component is required. Depending on order size, this can lock arbitrarily large amounts of escrowed tokens per affected order.

### Likelihood Explanation
Any solver operating through a smart-contract wallet on the destination chain that isn't guaranteed to be a plain-ETH-accepting address on the source chain (e.g. a differently configured/undeployed counterpart contract, a paused contract, or a contract without a `receive()`/payable fallback) will trigger this on the very first cross-chain fill it performs for an order containing a native-token input. The docs actively encourage solvers to route fills through smart contract accounts (`SolverAccount`, EIP-7702/ERC-4337 batching), increasing the likelihood that `msg.sender` for a fill is a contract rather than a plain EOA.

### Recommendation
Do not hardcode the `RedeemEscrow` beneficiary to `msg.sender`. Allow the filler to supply an explicit, chain-agnostic recipient address (analogous to taking `recovery` as an argument in the referenced fix), and/or make `_withdraw`'s native-token transfer non-blocking for the rest of the batch (e.g., fall back to a pull-based withdrawal pattern instead of reverting the whole release when a push transfer fails), so a single incompatible beneficiary address cannot permanently freeze the entire order's escrow.

### Proof of Concept
1. Solver deploys/uses a smart-contract address `S` as its filler account on the destination chain (e.g. via the documented `SolverAccount`/EIP-7702 pattern), where `S`'s code either isn't deployed at the same address on the source chain or reverts on receiving plain native value there.
2. Solver calls `fillOrder` on the destination chain for a cross-chain order whose `order.inputs` includes a native-token entry. `_fillCrossChain` sets `_filled[commitment] = S` and dispatches `RedeemEscrow` with `beneficiary = S`. [5](#0-4) 
3. Hyperbridge relays the message; `onAccept` on the source chain calls `_withdraw(body, false, true)`, which attempts `_sendValue(S, amount)`. [2](#0-1) 
4. The call to `S` fails, `_sendValue` reverts, `onAccept` reverts, no receipt is stored (per ISMP semantics), and every relayer resubmission fails identically forever.
5. The order is already `Filled` on the destination, so no alternative cancellation/refund path exists; the escrowed input tokens on the source chain are permanently locked.
