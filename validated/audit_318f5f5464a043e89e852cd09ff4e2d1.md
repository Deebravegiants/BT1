## Title
Webhook shop, topic, and API-version identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery/replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is validated by `Utils::HmacValidator.validate`, which computes and checks the HMAC over `to_signable_string` only. `Request#to_signable_string` returns solely the raw request body [1](#0-0) , while the tenant-identifying fields `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never part of the signed payload [2](#0-1) . `Registry.process` trusts these unauthenticated fields once the body's HMAC checks out and forwards them straight to the app's handler as the webhook's tenant/shop identity [3](#0-2) .

### Finding Description
`HmacValidator.validate_signature` verifies `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` against the received signature [4](#0-3) . For webhooks, `to_signable_string` is exactly `@raw_body` — none of the identity headers are folded into the signed bytes [1](#0-0) .

This breaks the intended identity binding:
`hmac_verified(bytes) == bytes_that_determine_tenant`

In reality:
`hmac_verified(raw_body) != (shop, topic, api_version, webhook_id)` — the latter come from `shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, `shopify-webhook-id` headers that an unprivileged internet client fully controls [5](#0-4) .

Any entity that can obtain one legitimately signed `(body, hmac)` pair for the app — trivially achievable by installing the app on their own free/dev store and letting Shopify deliver one real webhook to the app's public endpoint — can replay that exact body+HMAC to the same endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) to name a different, victim shop. `Registry.process` only checks `Utils::HmacValidator.validate(request)`, which will still pass because the HMAC never covered those headers, and then dispatches to the handler with `shop: request.shop` set to the attacker-chosen value [6](#0-5) .

### Impact Explanation
This is a cross-tenant identity confusion: the app's own webhook-processing pipeline (a security boundary meant to guarantee "this body came from Shopify for shop X") can be tricked into believing forged/replayed data belongs to a shop other than the one that actually generated it. Any handler logic that keys off `WebhookMetadata#shop` (e.g., looking up/updating per-shop records, triggering shop-scoped side effects, or associating `body` content with the named shop) can be manipulated to act on shop B's identity using traffic actually produced under shop A's install, since the gem never binds `shop`, `topic`, `webhook_id`, or `api_version` to the HMAC it verifies.

### Likelihood Explanation
Obtaining a valid `(body, hmac)` pair requires no privileged secret — any unprivileged actor can install the app for free on their own store to receive a genuinely signed webhook, then replay it against the same public webhook endpoint with a modified shop-domain header. No `api_secret_key`, access token, or client secret is needed, only observation of one legitimate delivery to their own tenant.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable payload used for HMAC verification, or otherwise cryptographically bind them to the raw body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document clearly that `Request#shop`/`#topic` are unauthenticated and must not be used as a tenant key without additional verification (e.g., cross-checking against a known/installed shop list) in `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a free/dev store), a fully unprivileged action.
2. Shopify delivers a legitimate webhook to the app's public endpoint with:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body>`
   - body `B`
3. Attacker captures `(B, hmac)` and replays it to the same endpoint, only changing the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `HmacValidator.validate` recomputes the HMAC over `B` only (per `to_signable_string`) [1](#0-0)  and it matches, so `Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , even though `victim-shop` never sent this data.
