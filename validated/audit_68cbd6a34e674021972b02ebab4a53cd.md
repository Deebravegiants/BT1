### Title
Webhook shop-tenant spoofing via HMAC that only covers the raw body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the `shop-domain` header — which is never covered by that HMAC — as the tenant identifier passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly out of unauthenticated HTTP headers and are never included in the bytes that get HMAC-verified. `Registry.process` validates the HMAC and, if it passes, immediately trusts `request.shop` as the tenant for the handler: [3](#0-2) 

`HmacValidator.validate` computes the expected signature purely from `to_signable_string` (i.e., the raw body) and compares it to the `hmac` field extracted from the (also attacker-controlled) `hmac-sha256` header: [4](#0-3) 

The binding that should hold is: `shop_header == shop_that_the_signed_body_actually_originated_from`. Because the signable string is body-only, this equality is never enforced — the HMAC only proves "this body was produced by someone holding `api_secret_key`," not "this body came from shop X." Any unprivileged internet user who operates their own Shopify store with the target app installed will legitimately receive real, correctly-signed webhooks for their own shop (Shopify signs webhooks with the app's shared `client_secret`, not a per-shop secret). That attacker can capture one such `(raw_body, hmac-sha256 header)` pair from their own shop and POST it directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. The HMAC still validates (only the body was checked), so `Registry.process` calls the handler with `WebhookMetadata` claiming `shop:` is the victim, while the actual payload content is attacker-controlled data from the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an app relying on `request.shop`/`data.shop` to scope database writes, cache keys, or side effects per-merchant can be made to attribute attacker-controlled body content to an arbitrary victim shop identifier. Depending on how the host app uses the `shop` field from `WebhookMetadata`, this enables cross-tenant data injection/corruption — matching the Critical "cross-tenant access" impact category, since the attacker (an ordinary merchant with no special privilege over the victim) can inject data attributed to a shop they do not control.

### Likelihood Explanation
Exploitability only requires: (1) installing the target app on any Shopify store (something any internet user can do for a public app, or a plausible insider for private/custom apps), (2) triggering an event that generates a webhook to capture a real `(body, hmac)` pair, and (3) replaying it to the app's public webhook endpoint with a forged `shop-domain` header. No knowledge of `api_secret_key` or any other credential is required — this is exactly the kind of "field acted on but not covered by the HMAC" flaw called out as the target bug class, so likelihood is high wherever a host app trusts `request.shop`/`WebhookMetadata#shop` without independent cross-checking.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content, or otherwise cryptographically tie the header to the verified body — e.g., include the normalized header values in `to_signable_string`, or require the consuming app to cross-check `request.shop` against a shop it already has an active, previously-verified session/webhook registration for before trusting the payload. At minimum, document prominently that `request.shop` is not authenticated by the HMAC and must be independently validated by the host application (e.g., against the set of shops that have completed OAuth) before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., updates a product), receiving a POST from Shopify with:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`
   - `raw_body: <attacker-controlled JSON, since attacker fully controls their own shop's data>`
2. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — unchanged from step 1 — so it matches and validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and the host app processes attacker-controlled content under the victim's tenant identity.
