### Title
Local, unconfirmed enrollment status is used to report signup success/failure in `user_centric_signup` flow, bypassing backend validation - (File: `src/plans/mod.rs`)

### Summary
In the Sui `PostGasPrice()` bug, a value (`gasPrice`) is committed to memory and used for a critical downstream decision (`VoteOutbound`) *before* it is confirmed/validated against the backend consensus (`PostVoteGasPrice`). The analogous pattern in `orb-core` is in `MasterPlan::do_signup`, where for signups flagged `user_centric_signup`, the orb writes a **locally-computed** `enroll_user::Status` into `debug_report` and treats the signup as `Success`/`Error` **without ever calling the backend enrollment/validation endpoint** (`enroll_user` → `signup_post`/`signup_poll`), which is the actual mechanism that lets the backend confirm uniqueness, detect duplicates, or flag fraud server-side.

### Finding Description
`do_signup` computes `signup_reason` purely from local pipeline results and locally-executed fraud checks: [1](#0-0) 

Then, if the user QR data (received earlier from the backend as `user_centric_signup`) is set and the orb is not configured to `ignore_user_centric_signups`, the orb sets its own `enrollment_status` directly from the *local* `signup_reason` and **skips the call to `enroll_user`** (which is the function that actually submits the signup to the backend via `signup_post::request`/`signup_poll::request` for confirmation): [2](#0-1) 

Compare this to the non-user-centric branch, which calls `self.enroll_user(...)`, i.e., the function that posts to `/api/v2/signups/{signup_id}` and polls `/api/v1/signups/{signup_id}` for a backend-confirmed result: [3](#0-2) [4](#0-3) [5](#0-4) 

The backend-confirmed poll response is explicitly documented as the authority for detecting "backend duplicates," "backend legacy signup requests," "backend inflight matches," and "backend detected fraud": [6](#0-5) 

The resulting `result.success` (derived from the locally-set `enrollment_status`) is then used to drive user-visible outcomes: the dbus `signup_finished` signal, `ui_complete_signup`, and — in self-serve mode — a `SignupEnded { success, .. }` message sent to the companion app over `orb_relay`: [7](#0-6) [8](#0-7) 

This is structurally the same root cause as the referenced report: a value that should only be trusted after being validated/confirmed by the authoritative backend (analogous to `PostVoteGasPrice`) is instead committed to local state (`debug_report.enrollment_status`) from a local-only computation, and that local state is used to drive a security-relevant decision (whether the signup is treated as successful, notified to the app, and reflected in dbus events) before any backend confirmation occurs.

It is also worth noting that in this stripped-down (FOSS) build, `detect_fraud`/fraud-check pipeline is a no-op (`N_FRAUD_CHECKS = 0`, always returns `Ok(false)`): [9](#0-8) [10](#0-9) 

which means for `user_centric_signup` sessions in this build, as long as the biometric pipeline produces output, `signup_reason` is always `Normal` and `enrollment_status` is unconditionally reported `Success`, with no backend round-trip at all to catch duplicate/fraudulent signups.

### Impact Explanation
The user-centric-signup branch reports the signup as `Success`/`Error` and forwards that outcome to the app and to internal telemetry (`report_signup_reason`, `dd_incr!("main.count.signup.result.success.successful_signup")`) purely from unconfirmed local state, never invoking the backend enrollment/validation call that would perform duplicate/fraud/inflight-match checks. This allows a signup to be misattributed as successfully-completed/unique without going through the backend confirmation channel that is designed to catch duplicates and fraud — i.e., a cross-signup state bleed / unauthorized-signup class of impact, analogous to acting on unconfirmed gas-price state in the referenced report.

### Likelihood Explanation
`user_centric_signup` is a normal, backend-driven, production configuration flag delivered in the authenticated user QR-code data (`orb_qr_link::UserData::user_centric_signup`), not a test-only or `allow-plan-mods`-gated path: [11](#0-10) 

This means the affected branch is reachable by any user going through the normal self-serve/app-centric signup flow controlled by the `user_centric_signup` flag set by the backend for the app, without requiring any special/privileged access, and is not merely a hypothetical or test-only code path.

### Recommendation
Only set/report `enrollment_status`/signup success for the `user_centric_signup` branch after the orb has received an authoritative confirmation (equivalent to the backend `PostVoteGasPrice`/`signup_post`+`signup_poll` round trip). If the app-centric design intentionally defers this confirmation to the app/backend outside `orb-core`, this should be clearly documented as an accepted architectural trust boundary; otherwise, `do_signup` should call `enroll_user` (or an equivalent backend confirmation call) before marking `debug_report.enrollment_status` and before emitting `SignupEnded`/dbus success notifications, mirroring the fix pattern in the referenced report (validate first, then commit state).

### Proof of Concept
1. A user/app obtains a valid, backend-signed user QR code with `user_centric_signup = true` (a normal, backend-controlled flag, not requiring elevated access).
2. The orb completes biometric capture and pipeline processing; `detect_fraud` (a no-op in this build) returns `false`, so `signup_reason = SignupReason::Normal` regardless of whether the backend would have flagged the signup as a duplicate or fraud.
3. In `do_signup`, because `user_centric_signup` is true and `ignore_user_centric_signups` is false, `debug_report.enrollment_status(enroll_user::Status::Success)` is set directly — `enroll_user`/`signup_post`/`signup_poll` are never called, so no backend-side duplicate/fraud confirmation happens (`src/plans/mod.rs:639-656`).
4. `result.success` is derived from this locally-set status and used to emit `dbus::Signup::signup_finished(true)` and, in self-serve mode, `self_serve::orb::v1::SignupEnded { success: true, .. }` to the app (`src/plans/mod.rs:363-385`, `1481-1495`) — all without backend confirmation, exactly as the referenced report describes acting on an unvalidated value.

pub async fn request(signup_id: &str) -> Result<Response> {
    let request = super::client()?
        .get(format!("{}/api/v1/signups/{signup_id}", *SIGNUP_BACKEND_URL))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    tracing::debug!("Sending request {:#?}", request);
    let response = request.send().await?;
    tracing::debug!("Received response {:#?}", response);
    response.error_for_status_ref()?;

    let response_body = response.text().await?;
    let parsed_response = serde_json::from_str::<Response>(&response_body)
        .inspect_err(|_| {
            tracing::error!("Failed to parse response JSON. Response body: {:#?}", response_body);
        })
        .wrap_err("Failed to parse response JSON")?;

    tracing::debug!("Received response {:#?}", parsed_response);
    Ok(parsed_response)
}
