## Title
Thin-liquidity phantom-order price manipulation can poison the indexer's default `indexed_rates` quote used to size real intents - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The rekt report describes a single well-capitalized actor manipulating a thinly-traded token's price/open-interest on dYdX to force liquidations that drained the insurance fund. The closest reachable analog in Hyperbridge is the phantom-order price-discovery pipeline: any account can permissionlessly become a "delegated solver" (EIP-7702 delegation to the public `SolverAccount` contract is not access-controlled) and then submit phantom bids. Because a leg's published price is a **liquidity-weighted median that is a selection, not a blend**, a single bidder holding over half of a thin leg's output-token inventory sets that leg's published price verbatim. That number becomes `LiquidityPool.sellRate`/`buyRate`, which the SDK's `quoteIntent()` uses **by default** to size real, fund-moving intent orders.

### Finding Description
`aggregatePhantomBids` verifies only that a bid's signer is EIP-7702-delegated to the chain's `SolverAccount` and correctly signed - it does not require any special privilege or protocol-controlled solver identity: [1](#0-0) 

Any EOA can self-delegate to `SolverAccount` via a standard EIP-7702 authorization - this is documented as an open, permissionless action for "solvers": [2](#0-1) 

Each leg's price is chosen by `weightedMedian`, weighted only by the bidder's on-chain balance of that leg's output token on the destination chain - a **selection** of one bidder's exact quote, not an averaged/blended value: [3](#0-2) 

The code and docs explicitly acknowledge this dynamic: "a solver holding over half the leg's weight sets the published price verbatim": [4](#0-3) [5](#0-4) 

That per-leg median is what the indexer turns into `LiquidityPool.sellRate`/`buyRate` via a depth-weighted mean across chains (`mergeChainRowsIntoPool`) - but the underlying per-chain sample is still the possibly-manipulated median: [6](#0-5) 

Crucially, `IntentGateway.quoteIntent()` now defaults to `indexed_rates`, consuming these pool rates directly to size real orders' `amountIn`/`amountOut` with **no fallback and no independent sanity check**: [7](#0-6) [8](#0-7) 

The decision to make this the default explicitly chose *not* to fall back to another source when a rate looks off, on the theory that hiding staleness is worse: [9](#0-8) 

For a thinly-held/illiquid exotic token pair (the exact analog of YFI's thin liquidity on dYdX), an attacker who accumulates enough of the output token on one destination chain, self-delegates to `SolverAccount`, and submits phantom bids at an off-market price for that leg becomes the dominant weight and single-handedly sets the "market" `LiquidityPool` rate that other integrators/users trust as ground truth for constructing real orders.

### Impact Explanation
Once the attacker controls the published `sellRate`/`buyRate` for a thin pair, any caller (integrator, wallet, or automated flow) using the SDK's default `quoteIntent()` will size a real IntentGatewayV2 order's `inputs`/`output.assets` off the poisoned rate. Depending on direction, this either:
- Causes a user to escrow far less input than the market-honest amount for a requested output, letting the attacker (as the filler/solver of that manufactured rate) extract the difference when they fill it — a direct value-extraction/theft vector on user escrow, analogous to the value drained from dYdX's insurance fund by a manipulated price feeding an automatic, trusted downstream mechanism (liquidation fills there; order sizing/fills here).
- Or produces unfillable/mispriced orders that waste escrowed funds and gas, a griefing/DoS variant.

This satisfies the "concrete theft ... via unsound state" bar: the `LiquidityPool` rate is state the protocol's own quoting facade treats as authoritative and un-fallback-able.

### Likelihood Explanation
The barrier to entry is low: delegating an EOA to `SolverAccount` is a normal, permissionless, protocol-supported action (not gated by governance or allowlisting), and phantom bids are public and require no capital commitment beyond holding the leg's output token on one destination chain. Thin pairs (newly listed exotics, low-liquidity corridors) are the most exposed, mirroring how YFI's relatively thin liquidity made it the target on dYdX rather than a deep, liquid market.

### Recommendation
- Require a minimum bidder diversity/quorum (not just one weight-dominant quote) before a leg's median is published, or cap a single bidder's weight contribution to the median (e.g., diminishing marginal influence past some inventory share).
- Add a price-deviation guard on the indexer/pool side analogous to `checkPriceGuard`/`maxDeviationBps` already used elsewhere in Simplex, comparing a new sample against the pool's trailing consensus before accepting it into `sellRate`/`buyRate`.
- Consider making `quoteIntent()`'s `indexed_rates` strategy reject or flag quotes backed by a single bidder/low bid count, surfacing this in `quoteMetadata` so integrators can apply their own sanity thresholds.

### Proof of Concept
1. Identify a thinly-liquid token pair registered for phantom pricing on some destination chain.
2. Fund an EOA with a large balance of that leg's output token on the destination chain (no special access required).
3. Self-delegate the EOA to the chain's public `SolverAccount` via a standard EIP-7702 authorization (permissionless, per `docs/content/developers/evm/intent-gateway/overview.mdx`).
4. Submit a phantom bid quoting an arbitrary off-market price for that leg; because the attacker's balance dominates the leg's weight, `weightedMedian` in `phantom-aggregation.ts` selects the attacker's quoted price verbatim.
5. The indexer's `handlePhantomOrderPrices`/`updateLiquidityPools` writes this into `LiquidityPool.sellRate`/`buyRate`.
6. Any caller invoking `IntentGateway.quoteIntent()` (default `indexed_rates` strategy, no fallback) for that pair receives amounts computed from the poisoned rate and constructs a real order on that basis, which the attacker (or a colluding filler) can then fill to extract value from the mis-sized escrow.

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}
