Webhook `shop`/`topic` metadata used for tenant routing is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentic once `Utils::HmacValidator.validate` succeeds, but that validation only signs the raw request body. The `shop`, `topic`, and `webhook_id` fields — read straight from unauthenticated HTTP headers — are then handed unchanged to the app's `WebhookHandler`, which the docs explicitly tell developers to use as the tenant/shop identifier for routing work (e.g. `shop_domain: data.shop`).

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac`. [1](#0-0) 

For a webhook `Request`, `to_signable_string` returns only the raw body (`@raw_body`), while `shop`, `topic`, `api_version`, and `webhook_id` are parsed directly from HTTP headers and are never part of the signed string: [2](#0-1) 

`Registry.process` only calls `HmacValidator.validate(request)` (i.e. validates the body), then immediately constructs `WebhookMetadata` from the unauthenticated `request.shop` / `request.topic` / `request.webhook_id` and passes it to the app's handler: [3](#0-2) 

`WebhookMetadata` is the exact struct the handler interface is built around: [4](#0-3) 

The library's own documentation instructs developers to trust `data.shop` as the tenant identifier and use it directly for tenant-scoped work, and states that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

This is the same bug class as the reported `_takeFee()` issue: a value that is *used* to make a security decision (there: `collateralOf()`'s balance/interest amounts; here: `shop`/`topic`) does not match the value that was actually *verified* (there: the true post-underflow balance; here: the HMAC-signed bytes, which are the body only). The equality that should hold but does not is:

`shop used for tenant identification (request.shop from header) == shop cryptographically bound by the HMAC (none — the HMAC only binds @raw_body)`

Any internet-connected attacker who has ever legitimately received one webhook delivery from Shopify for *their own* store (trivial to obtain — they just install/use the target app on a shop they control) now possesses a `(raw_body, valid hmac)` pair signed with the app's shared `client_secret`. Because the signature never covers the header fields, the attacker can freely change `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` on a replayed request to the app's public webhook endpoint, and `HmacValidator.validate` will still return `true` since only the (unmodified) body is checked.

### Impact Explanation
This crosses the tenant boundary the gem is expected to enforce: an app receiving webhooks for many merchants relies on `data.shop` to decide which merchant's data/session the webhook body applies to. Since attacker-controlled headers determine `data.shop`/`data.topic` while only the body is authenticated, an attacker can make a legitimately-signed payload appear to originate from a victim shop (or a different topic than what was actually sent), causing the host application to process/store attacker-supplied data under a victim tenant's identity — a cross-tenant integrity/authentication issue. This matches the "cross-tenant access" Critical-impact category defined in scope, since the vulnerability lives entirely in this gem's webhook verification code path (`Request`/`Registry`), not in host-application misuse of an undocumented API — the documented, recommended usage (`data.shop`) is what's unsafe.

### Likelihood Explanation
Requires no privileged credentials: an attacker only needs to be a legitimate (even trial) merchant installing the target app once to capture a valid `(body, hmac)` pair signed with the app's `client_secret`, then can replay it with forged headers against the app's public webhook endpoint at will. The webhook endpoint is by design internet-reachable and unauthenticated apart from this HMAC check.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC before trusting them:
- Extend `VerifiableQuery`/`to_signable_string` for webhook requests to include `shop`, `topic`, and `webhook_id` (Shopify's HMAC header is computed over the body per their spec, so this must be layered as an additional check in this gem, e.g. cross-referencing the registered webhook_id/topic combination via a server-side lookup, or requiring the app to independently verify `shop` against its own session/shop registry before trusting `data.shop`).
- At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop`/`data.topic` are not covered by the HMAC and must be independently validated (e.g., checked against a known/installed shop list) before being used for tenant-scoped operations, and add a public API to make this trust boundary explicit in code rather than only in prose.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (their own store) and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify. This HMAC is computed with the app's shared `client_secret`:
```ruby
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
``` [7](#0-6) 
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets:
```
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-topic: customers/redact
x-shopify-webhook-id: <arbitrary>
```
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes and compares against `@raw_body` — the swapped headers do not affect the check, so validation succeeds. [8](#0-7) 
4. The registered handler receives `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: <attacker's original body>, ...)` and, following the documented pattern (`shop_domain: data.shop`), processes/stores the attacker's data as though it belongs to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
