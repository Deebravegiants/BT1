### Title
POA Bridge withdrawal status matched by asset ID instead of index causes double-credit on batch withdrawals of the same token — (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` looks up the on-chain outcome of a specific withdrawal (identified by `tx.hash` + `index`) by matching against the bridge indexer response using `findMatchingWithdrawal`, which searches by `assetId` only, ignoring the caller-provided `index`. When a batch NEAR intent transaction contains **more than one withdrawal of the same token** (same `assetId`), every `describeWithdrawal` call for that asset in that tx resolves to the **same** underlying withdrawal record, so all of them are reported "completed" as soon as the first one settles.

### Finding Description
`createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107` assigns each withdrawal in a batch a `bridge`-scoped `index` and constructs a `WithdrawalIdentifier` per withdrawal, all sharing the same NEAR `tx.hash` when they originate from the same intent transaction. That identifier is later passed to `Bridge.describeWithdrawal` (`shared-types.ts:429-431`) to obtain the actual on-chain status for that specific withdrawal.

For the POA bridge, `describeWithdrawal` (`poa-bridge.ts:313-343`) fetches all withdrawals for the tx hash and calls:

```
const withdrawal = findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId);
```

`findMatchingWithdrawal` (`poa-bridge.ts:409-427`) explicitly documents the limitation:

```
* NOTE: Currently only matches by assetId. This means multiple withdrawals
* of the same token in a single transaction are not supported.
```
and returns `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — the *first* matching entry regardless of `index`, amount, or destination address.

Nothing upstream enforces "only one withdrawal per asset per transaction." `createWithdrawalIntents`/`sdk.ts` batch withdrawal flow (`sdk.ts:334-372`, `sdk.createWithdrawalCompletionPromises.test.ts`) supports multiple `WithdrawalParams` entries per call, and multiple withdrawals of the same `assetId` (e.g., to two different destination addresses) can legitimately be included in one batch. When that happens, both `describeWithdrawal` calls (index 0 and index 1) hit the exact same `find()` match, so:

- If withdrawal #0 completes and #1 is still pending (or fails), `describeWithdrawal({index: 1, ...})` will *also* report `{status: "completed", txHash: withdrawal.data.transfer_tx_hash}` — the same hash as #0.

This breaks the equality "status reported == on-chain outcome for *that* withdrawal": the caller (integrator, via `waitForWithdrawalCompletion`/`withdrawal-watcher.ts:20-77`) will treat the second withdrawal as finalized and credit/settle it, even though only one of the two on-chain transfers actually occurred.

### Impact Explanation
This matches the High/Critical bug class "a status or hash misreport making an integrator credit or refund twice." An integrator batching two POA-bridge withdrawals of the same token (e.g., splitting a large withdrawal to two different destination addresses, or refunding two users in the same token in one intent) will have the watcher report both as `completed` with the same `txHash` as soon as one settles, potentially causing the integrator to credit/release funds for the second withdrawal that was never actually sent to its destination.

### Likelihood Explanation
Requires only an ordinary user/integrator action — submitting a batch of withdrawals where two entries use the same POA-bridge `assetId` (no malicious relayer, admin, or bridge operator behavior needed). This is a normal use pattern for the SDK's documented batch fee-estimation/withdrawal support, and the code's own comment acknowledges the case is not handled ("multiple withdrawals of the same token in a single transaction are not supported"), confirming reachability but not enforcing rejection of such batches anywhere in `sdk.ts` or `withdrawal-watcher.ts`.

### Recommendation
Match withdrawal indexer records against the specific withdrawal (e.g., using the pair (`assetId`, `destinationAddress`, `amount`) or an ordering system consistent with `index`) instead of `assetId` alone, or explicitly detect and reject/throw when a batch contains multiple POA-bridge withdrawals of the same `assetId` until the POA API can disambiguate by index.

### Proof of Concept
1. Build a batch withdrawal intent with two `WithdrawalParams` entries, both `assetId: "nep141:usdt.omft.near"`, but different `destinationAddress` (A and B), submitted in one NEAR transaction `tx.hash = H`.
2. `createWithdrawalIdentifiers` yields `wid0 = {index:0, tx:{hash:H}, ...}` and `wid1 = {index:1, tx:{hash:H}, ...}`.
3. On-chain, only the transfer to A completes; the transfer to B is still pending in the POA relayer.
4. Call `bridge.describeWithdrawal(wid0)` → correctly returns `{status:"completed", txHash: txA}`.
5. Call `bridge.describeWithdrawal(wid1)` → `findMatchingWithdrawal` finds the **same** record (by `assetId` only) and also returns `{status:"completed", txHash: txA}`, even though the withdrawal to B has not happened.
6. An integrator relying on `waitForWithdrawalCompletion`/`watchWithdrawal` for `wid1` will treat B's withdrawal as settled and may credit/release funds prematurely. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
