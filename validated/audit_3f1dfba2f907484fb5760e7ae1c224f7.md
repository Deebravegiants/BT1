### Title
Unbacked reputation-token mint via attacker-controlled message body size in `pallet-messaging-incentives` - (File: `modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
`pallet-messaging-incentives::on_executed` mints `ReputationAsset` to a relayer using `bytes × MintPerByte`, where `bytes` is simply the length of the request/response body a relayer chose to deliver [1](#0-0) . This mirrors the WatchPug UDT-grant bug class: a token reward is derived from an easily-inflatable proxy metric (there it was `estimatedGasForPurchase * tx.gasprice`, here it is raw payload length) rather than any real, bounded cost incurred by the earner.

### Finding Description
The per-message mint amount is computed purely from `message_bytes()`, which sums `max(body.len(), 32)` across all requests packed into a delivered `Message::Request` [2](#0-1) . There is no cap on request body size within this pallet, no correlation to actual verification/execution gas spent on the destination chain, and no throttling per relayer or per time window — the mint scales linearly and unboundedly with attacker-chosen payload size:

```rust
let bytes = Self::message_bytes(&mw.message);
let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
let amount = rate.saturating_mul(bytes_balance);
...
T::ReputationAsset::mint_into(&relayer, amount)
``` [3](#0-2) 

Any unprivileged dispatcher can drive `body.len()` arbitrarily high from the source chain (e.g. an EVM contract or Substrate pallet dispatching an ISMP POST with a large, cheap-to-produce payload — on EVM chains zero-byte calldata is charged at a steep discount, so padding a body with zero bytes is inexpensive relative to the linear reputation reward it produces). The same relayer who dispatches (or colludes with the dispatcher) can then permissionlessly deliver/relay that message and sign it with the sr25519 key recovered in `relayer_for()` [4](#0-3) , collecting the mint. The identical unbounded pattern is duplicated in `state-coprocessor`'s `impls.rs`, which reuses the same `MintPerByte` rate and reputation asset for a `total_bytes` figure supplied by the coprocessor path [5](#0-4) .

This is structurally the same defect as the Unlock `recordKeyPurchase()` issue: a reward-minting formula keyed to a metric (`estimatedGasForPurchase` there, `body length` here) that the caller/relayer can cheaply manipulate far beyond the real resource cost the protocol intends to compensate, with no daily/global cap on total mint as the WatchPug report recommended.

### Impact Explanation
`ReputationAsset` directly determines eligibility and ranking for `pallet-collator-manager`'s collator selection — per the network documentation, reputation "mirrors your `$BRIDGE` earnings at a 1:1 ratio" and is the basis for becoming a Hyperbridge collator. An attacker who can mint arbitrary reputation by self-dispatching and self-relaying oversized, low-real-cost messages can artificially inflate their standing to gain outsized collator selection weight/rewards without performing proportional genuine relaying work, undermining the "proven economic activity" security model the reputation system is designed to enforce. Because the pallet also feeds `pallet-ismp`'s `FeeHandler` on every successful batch, the drain is systemic and repeatable across all message deliveries, not a one-off.

### Likelihood Explanation
Any account controlling a source-chain application (an unprivileged actor — no special ISMP host permissions are required to dispatch a POST request) can pad a message body, and any account able to construct a signed relayer message (again unprivileged) can deliver it and claim the mint. The 32-byte floor only prevents gaming *small* payloads; it does nothing to bound the *upper* end, which is where the exploit value lies. Exploitation requires no misconfiguration beyond `MintPerByte` being non-zero (a normal operating condition, not an edge case), making this readily reachable whenever the incentive is active.

### Recommendation
- Cap the per-message (and/or per-relayer per-time-window) byte count eligible for minting, independent of the actual dispatched body size, so an attacker cannot linearly scale rewards via payload padding.
- Introduce a global/per-relayer upper bound on total `ReputationAsset` minted per epoch, analogous to the WatchPug recommendation of a daily upper limit on UDT grants.
- Consider tying the reward to a metric harder to game cheaply (e.g., verified destination execution weight/gas actually consumed) rather than raw source-supplied payload length, and apply the same fix to the duplicated logic in `state-coprocessor/src/impls.rs`.

### Proof of Concept
1. Governance sets `MintPerByte` to a non-zero rate (normal production configuration) via `set_mint_per_byte` [6](#0-5) .
2. Attacker deploys/controls a source-chain application and dispatches ISMP POST requests whose bodies are padded to the maximum allowed size with cheap (e.g., zero) bytes.
3. Attacker (or a colluding relayer) delivers these requests to Hyperbridge as `Message::Request`, signing with their own sr25519 key so `relayer_for()` resolves to their account.
4. `on_executed` computes `bytes = sum(max(body.len(), 32))` over the padded requests and mints `bytes × MintPerByte` of `ReputationAsset` to the attacker [3](#0-2) , confirmed by the existing test `on_executed_mints_reputation_proportional_to_bytes`, which shows the mint scales linearly with `body` length with no upper bound [7](#0-6) .
5. Repeating this at scale (batched requests, repeated deliveries) accumulates disproportionate reputation relative to genuine relaying effort, exactly mirroring the gas-token-driven UDT over-minting attack in the referenced report.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
