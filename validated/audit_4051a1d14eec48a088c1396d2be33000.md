Audit Report

## Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` allows sandwiching of XCM fee-swap refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader` swaps a user's XCM-supplied asset into the runtime's `Target` fee asset via `pallet_asset_conversion` to pay execution fees, and on refund swaps unused `Target` back into the original asset using `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`. [1](#0-0)  This disables `pallet_asset_conversion`'s slippage-protection check for the refund leg of the swap, while the `buy_weight` leg is safe because it requests an exact output amount. [2](#0-1) 

## Finding Description
`buy_weight` converts the user's supplied asset into `Target` using `swap_tokens_for_exact_tokens` with `fee` as the exact output — this bounds the output side inherently since the fee amount is fixed. [3](#0-2)  When the XCM executor calls `refund_weight` to return unused weight fees, the excess `Target` credit is swapped back to the asset the user originally paid with via `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)`. [1](#0-0)  `pallet_asset_conversion`'s underlying `do_swap_exact_tokens_for_tokens` only checks `amount_out >= amount_out_min` when `amount_out_min` is `Some`; passing `None` skips this `ProvidedMinimumNotSufficientForSwap` guard entirely, allowing the swap to execute at any resulting AMM price. [4](#0-3)  Since the trait bound `SwapCredit: SwapCreditT<...> + QuotePrice` is already required by `SwapFirstAssetTrader`, a price quote could be obtained to compute a floor, but the current implementation does not use it for the refund. [5](#0-4) 

## Impact Explanation
The impact is real but narrow: the loss is bounded to the size of the *refund* leg only (the difference between weight bought and weight actually consumed), not the full fee amount, and it accrues to the individual XCM sender rather than causing protocol insolvency or fund freezing. The recipient of the refund receives fewer tokens back than a fair-market quote would yield if the pool price is moved against them within the same block. This is a legitimate, in-scope value-extraction bug in `pallet_asset_conversion`-integrated XCM fee handling, but it is a griefing/MEV-style loss affecting individual transactions' refund amounts, not a systemic break of accounting invariants, an unbounded drain, or privilege escalation.

## Likelihood Explanation
`SwapFirstAssetTrader` is genuinely wired into production/testnet runtime configs (Asset Hub Westend, Asset Hub Rococo, Penpal, and the staking-async parachain), confirmed by direct greps of `xcm_config.rs` files in each. [6](#0-5)  Triggering the refund path requires only an ordinary XCM sender to over-provision `BuyExecution` weight relative to actual consumption — a routine occurrence — and does not require any privileged role for the *victim* side. The attacker side, however, requires the capability to control intra-block extrinsic ordering (block authorship) or to race a competing swap into the same block/pool before the refund executes, which is a real but non-trivial MEV/collator-level capability, not available to arbitrary unprivileged users to arbitrarily extract value on demand. The magnitude of extractable value is also constrained per-message by the fee/refund size and by AMM pool depth/manipulation cost, limiting the realistic economic impact.

## Recommendation
Do not pass `None` for `amount_out_min` in `SwapFirstAssetTrader::refund_weight`. Use the already-required `QuotePrice::quote_price_exact_tokens_for_tokens` capability to compute an expected output at refund time, apply a configurable slippage tolerance, and pass `Some(min_amount)` into `swap_exact_tokens_for_tokens`, mirroring the implicit protection already present on the `buy_weight` path. If a safe minimum cannot be computed, prefer holding the excess in `Target` (or another safe fallback) over refunding at an unconstrained price.

## Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader` as in `asset-hub-westend`/`asset-hub-rococo`, backed by a `pallet_asset_conversion` pool for `Target`/`OtherAsset` with limited liquidity.
2. A user sends an XCM message with `BuyExecution` in `OtherAsset`, over-provisioning weight relative to actual consumption.
3. `buy_weight` swaps `OtherAsset` → `Target` for the exact `fee` amount via `swap_tokens_for_exact_tokens`. [2](#0-1) 
4. Before the trailing `refund_weight` executes (via block-author ordering control or a racing extrinsic in the same block), a large swap/liquidity operation shifts the pool price against `Target`→`OtherAsset`.
5. `refund_weight` executes `swap_exact_tokens_for_tokens(vec![Target, OtherAsset], refund, None)`, succeeding at the manipulated price because the `amount_out_min` check is bypassed. [1](#0-0) 
6. The user's received refund in `OtherAsset` is measurably lower than a pre-manipulation quote would predict, demonstrating the unbounded-price refund. A unit test in `pallet_asset_conversion`/`cumulus-primitives-utility` simulating a pool-price shift between `buy_weight` and `refund_weight` calls (using the existing `SwapCreditT`/`QuotePrice` mocks in `cumulus/primitives/utility/src/tests/swap_first.rs`) would concretely reproduce and measure the shortfall.
