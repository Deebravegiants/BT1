## Title
Missing freeze-authority check on coin/pc mints during pool initialization allows a malicious token issuer to permanently freeze all swap, deposit, and withdraw paths - (File: `program/src/processor.rs`)

## Summary
The external report describes an NFT-rental bug class where a "pausable" ERC721/ERC1155 token can permanently block `stopRent`'s asset-return transfer, freezing funds/positions until the token issuer unpauses. The reachable analog in this Solana AMM is the SPL Token **freeze authority**: an account (or mint) with an active freeze authority can be frozen at any time by that authority, causing any subsequent `Transfer` CPI against the frozen account to revert. `Initialize2` explicitly checks that the **LP mint** has no freeze authority, but performs **no equivalent check on the coin or pc mint**, leaving every downstream instruction (`Deposit`, `Withdraw`, `WithdrawPnl`, all four swap instructions) permanently vulnerable to the vault token accounts being frozen.

## Finding Description
During pool creation, `process_initialize2` unpacks and validates the coin vault, pc vault, and LP mint: [1](#0-0) 

Notice that for `amm_coin_vault` and `amm_pc_vault` the code checks `owner`, `amount != 0`, `delegate.is_some()`, and `close_authority.is_some()` — but never checks whether the underlying **coin_vault_mint** or **pc_vault_mint** has a `freeze_authority`. Only the LP mint's `freeze_authority` is validated: [2](#0-1) 

Because the coin/pc mint's freeze authority is never checked or rejected, any SPL mint with an active freeze authority (a common, standard, non-exotic SPL Token feature — analogous to the "pause" feature on ERC721/1155 tokens cited in the report) can be paired with this pool. If that freeze authority ever freezes the `amm_coin_vault`, `amm_pc_vault`, or a user's associated token account involved in a transfer, every subsequent SPL `Transfer` CPI against that account will revert, because the SPL Token program itself rejects transfers to/from frozen accounts.

All value-moving instructions route through the same two CPI helpers: [3](#0-2) [4](#0-3) 

These are called unconditionally in `Deposit` (mint LP + vault transfers), `Withdraw` (vault → user + LP burn), `WithdrawPnl` (vault → pnl owner), and all swap variants (`process_swap_base_in`/`_out`, `_v2`): [5](#0-4) [6](#0-5) [7](#0-6) 

If the coin or pc vault account becomes frozen, **none** of these instructions can complete, since each unconditionally attempts a `token_transfer`/`token_transfer_with_authority` against the vault. There is no pull-based or decoupled recovery mechanism (as the original report recommends as mitigation) — the transfer is inline and atomic with the rest of the instruction logic, so any revert reverts the whole instruction.

## Impact Explanation
This is a permanent-freezing-of-funds issue analogous to M-12: once a pool is created for a mint whose freeze authority is retained (rather than renounced/set to null), the mint's controller can unilaterally and indefinitely freeze the AMM's coin or pc vault account, which:
- Blocks all `Swap` (base-in/base-out, and v2 variants) instructions in both directions.
- Blocks `Deposit`, preventing any new LP additions.
- Blocks `Withdraw`, permanently locking existing LPs' underlying coin/pc funds behind LP tokens that can never be redeemed.
- Blocks `WithdrawPnl`, freezing protocol-owed PnL.

Because pool creation is permissionless (any user can call `Initialize2` with an arbitrary coin/pc mint pair), an attacker can create a pool using a mint they control the freeze authority for, attract liquidity, and then freeze the vault to lock in LPs' deposited funds — a permanent freezing of LP funds.

## Likelihood Explanation
Likelihood is moderate to high in practice: SPL Token mints with an active (non-null) freeze authority are common (many token issuers retain freeze authority for compliance or admin reasons), and `Initialize2` performs no validation to reject such mints for the coin/pc side despite already doing so for the LP mint — showing the project is aware of the general threat model but only applied it to one of the three mints involved.

## Recommendation
Add the same `freeze_authority.is_some()` rejection check used for the LP mint to both the coin mint and pc mint during `process_initialize2`, mirroring the existing LP-mint check: [8](#0-7) 
This should be applied by unpacking `amm_coin_mint_info`/`amm_pc_mint_info` and asserting `freeze_authority.is_none()` before pool creation succeeds, consistent with the existing delegate/close-authority checks on the vaults.

## Proof of Concept
1. Create an SPL mint `M` with a freeze authority retained by attacker-controlled key `F`.
2. Call `Initialize2` to create a Raydium pool with `M` as the coin (or pc) mint. The existing checks (`delegate`, `close_authority`, vault `owner`) all pass; the missing `freeze_authority` check means initialization succeeds. [9](#0-8) 
3. Users deposit liquidity via `Deposit`, minting LP tokens, and the coin vault accumulates real value.
4. Attacker `F` calls SPL Token `FreezeAccount` on the `amm_coin_vault` (or `amm_pc_vault`) token account.
5. Any subsequent `Swap`, `Deposit`, `Withdraw`, or `WithdrawPnl` instruction that calls `Invokers::token_transfer`/`token_transfer_with_authority` against the frozen vault reverts at the SPL Token program level: [3](#0-2) 
LPs can no longer redeem their tokens via `Withdraw`, permanently freezing their funds until (and unless) the attacker chooses to unfreeze.

        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,
    ) -> Result<(), ProgramError> {
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            owner.key,
            &[],
            deposit_amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, owner, token_program],
            &[],
        )
    }

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
