### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to identify *which tenant* the webhook is for are taken from unauthenticated HTTP headers that are never part of the signed bytes.

### Finding Description
`Webhooks::Registry.process` verifies a webhook by calling `Utils::HmacValidator.validate(request)`, which computes an HMAC-SHA256 over `request.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the `hmac` value [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns **only** `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to that signature [3](#0-2) .

After the HMAC check passes, `Registry.process` dispatches to the registered handler using these unauthenticated header values as the trusted tenant identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [4](#0-3) .

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the gem implicitly claims is `verified(bytes) == identity(shop_header)`, but in reality `verified(bytes)` only proves the raw body was signed with the app's secret for *some* legitimate webhook (e.g., one the attacker's own shop received while using the app), it proves nothing about the `shop-domain` header value that accompanies it.

Contrast this with the OAuth callback path, where `Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed query string, so `shop` genuinely is bound to the HMAC there [5](#0-4) . No equivalent binding exists for webhook requests.

### Impact Explanation
Any unprivileged party who can obtain one genuine, HMAC-valid webhook body/signature pair for the app (e.g., by installing the app on their own store and receiving a legitimate webhook for a mandatory or subscribed topic) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still succeeds because it never inspected the header, and the app's handler receives `WebhookMetadata` claiming the payload originated from the victim's shop. Depending on the host app's handler logic (e.g., `shop/redact`, `customers/data_request`, order/inventory sync, uninstall handling), this enables cross-tenant data manipulation or triggering privileged per-shop actions attributed to a shop the attacker does not control — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires no secret material beyond capturing one legitimate webhook delivery that the attacker is authorized to receive (trivial for any merchant/developer using a free/trial store with the app installed), plus the ability to POST arbitrary headers to the app's public webhook endpoint, which is by definition internet-reachable. The only gating factor is whether the host application uses `WebhookMetadata#shop` for privileged, tenant-scoped actions — a very common pattern for GDPR-mandatory topics like `shop/redact` and `customers/data_request` that this gem forces every app to implement.

### Recommendation
Bind the tenant-identifying headers to the HMAC verification. Since Shopify's webhook signature is computed only over the raw body, add a secondary authenticity check inside `Registry.process` — mirroring what token-exchange/JWT paths do, by requiring the app to look up an existing, previously-established session/webhook-id association for the claimed `shop` value before treating it as trusted, or documenting/enforcing that `webhook_id` (opaque, per-delivery) is deduplicated and cross-checked against Shopify's Admin API (`webhookSubscriptions`) for the specific shop rather than trusted from the header alone.

### Proof of Concept
1. Install the app on attacker-controlled store `attacker.myshopify.com`; Shopify sends a legitimate webhook, e.g. `customers/data_request`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers, `HmacValidator.validate` computes HMAC over `B` only [2](#0-1)  and succeeds because `B`/`H` are unchanged.
4. `Registry.process` calls the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)` [4](#0-3) , causing the app to act as if Shopify itself reported this event for the victim's shop.
