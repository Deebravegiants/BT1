### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` directly from HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body (`to_signable_string` returns `@raw_body`). This breaks the intended identity binding `HMAC-verified sender == shop attributed to the webhook payload`. Any party capable of obtaining one genuine, validly-signed webhook body/HMAC pair for their own shop (e.g., by installing the app on their own store, which is a normal unprivileged action) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop domain. `HmacValidator.validate` will report the request as valid, since it never inspects the `shop` header, and `Registry.process` will hand the attacker-controlled body to the app's webhook handler tagged with the victim's shop identity.

### Finding Description
`Webhooks::Request` mixes in `Utils::VerifiableQuery` and implements: [1](#0-0) 

`hmac` is read from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, while `shop`, `topic`, `webhook_id` and `api_version` are read from their respective headers, yet `to_signable_string` — the string that is actually signed/verified — returns only `@raw_body`.

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` and compares it to the `hmac` claim: [2](#0-1) 

Because none of the header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) are part of the signed content, they are **verified bytes only for the body**, while the tenant-identifying `shop` field is **parsed unauthenticated bytes**. `Registry.process` then trusts `request.shop` as the tenant identity for dispatch: [3](#0-2) 

The equality that should hold is:
`shop_that_produced_the_HMAC-signed_body == shop_attributed_to_the_webhook_by_the_handler`

After the attack this equality is broken: the body/HMAC pair genuinely originates from the attacker's own shop, but the `shop` value delivered to `WebhookMetadata`/the app's handler is attacker-chosen and can be any string, including a victim's `myshopify.com` domain.

### Impact Explanation
This is a cross-tenant identity-binding bypass (Critical category: cross-tenant access). Any app that uses `request.shop` (via `WebhookMetadata#shop`) to key persistence, authorization, or business logic — e.g. updating a shop record, marking data-erasure/`customers/redact`, `shop/redact` mandatory compliance webhooks, or altering per-shop feature state — can be made to apply attacker-controlled webhook content to a victim tenant's record, purely because the gem never binds the header-derived `shop` to the HMAC-covered payload. An attacker only needs the ability to trigger any legitimate webhook to their own store (a normal, unprivileged merchant action, e.g. installing a public app or updating their own shop data) and the ability to POST directly to the app's public webhook endpoint with a modified `shop` header — no `api_secret_key`, access token, or privileged account is required.

### Likelihood Explanation
Likelihood is high for any app that relies on `request.shop`/`WebhookMetadata#shop` for tenant-scoped side effects, since:
- Any user can self-install the target app on their own development/free shop and legitimately trigger webhooks against it, obtaining a real `(raw_body, hmac)` pair signed with the app's `client_secret`.
- The webhook receiving endpoint is, by design, unauthenticated/public (Shopify calls it without any session), so nothing else in the request needs to be forged besides the `shop` header.
- The gem performs no correlation whatsoever between the signed body and the shop identity claimed in the headers.

### Recommendation
Include the tenant-identifying fields in the signed/verified content, or otherwise cryptographically bind `shop` (and ideally `topic`/`webhook_id`) to the HMAC check instead of trusting raw headers unconditionally. At minimum, `Utils::HmacValidator`/`Webhooks::Registry.process` should require applications to independently confirm that `request.shop` corresponds to a shop that is expected to be able to produce that specific signed body (e.g., cross-check against the session/shop that installed the app for the given webhook subscription), and `to_signable_string` should not be the only signed content relied upon for identity attribution — document explicitly that `shop`/`topic`/`webhook_id` are NOT authenticated by the HMAC so host apps do not implicitly trust them for tenant scoping.

### Proof of Concept
1. Attacker installs the target app on their own dev shop `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. updates a product to fire `products/update`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this is a **valid** signature since Shopify computed it with the app's real `client_secret` for the attacker's own shop.
2. Attacker replays the exact captured `raw_body` and `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. The app calls:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
)
```
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `to_signable_string` (`@raw_body`) against the (unmodified, still-valid) HMAC — see [4](#0-3) .
5. `Registry.process` dispatches the handler with `shop: request.shop` equal to `"victim-shop.myshopify.com"` — see [5](#0-4) , even though the payload was never produced by or for that shop, demonstrating the cross-tenant identity break.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
