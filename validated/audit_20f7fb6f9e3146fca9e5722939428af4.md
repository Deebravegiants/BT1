### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook's authenticity HMAC only over the raw request body, but the `shop` attribute — which the gem's own `Registry.process` forwards to the app's webhook handler as the tenant identifier — is read directly from the `X-Shopify-Shop-Domain` HTTP header, which is not part of the signed material at all.

### Finding Description
The Shopify webhook HMAC scheme is meant to prove that a request (including all fields the app will act upon) originated from Shopify for a specific shop. In this gem:

- `HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field [5](#0-4) .
- For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [1](#0-0) .
- `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are never included in the signed string [6](#0-5) .
- `Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` taken straight from that unauthenticated header, handing it to the app's handler as the trusted tenant identity [3](#0-2) .

Because the shared secret (`api_secret_key`) is a single app-level secret used across every installed shop (not shop-specific), any body/HMAC pair that is valid for one shop's webhook delivery is also a cryptographically valid body/HMAC pair with respect to the shared secret, independent of which shop it is claimed to be for. This breaks the intended binding: `HMAC-verified(request) == HMAC-verified(request.shop)`. In truth, only the body is authenticated; the shop attribution is attacker-controlled.

An unprivileged attacker who has access to any one genuine, validly-signed webhook delivery (e.g., by installing the target app on their own development store and capturing the resulting webhook POST, which is standard, unprivileged access to their own shop's data) can replay that exact body+HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` will still pass, because it never inspected the header, and `Registry.process` will invoke the app's handler with `data.shop` set to the victim's domain.

### Impact Explanation
This crosses a tenant boundary: an app relying on this gem's HMAC validation as proof of both authenticity and shop attribution (which is what the library's public documentation instructs, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to process attacker-supplied data under a victim shop's identity. Depending on the handler's logic this can cause cross-tenant data injection/corruption (e.g., fake `orders/create`, `app/uninstalled`, or GDPR redact events attributed to a shop that never sent them), which matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate to high: the attacker only needs one legitimately signed webhook payload for any shop (trivially obtainable by installing the app on their own store, which requires no privileged credentials) and a way to POST to the app's public webhook endpoint with a modified header — both of which are within reach of an ordinary internet user interacting with a public app installation.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string used for webhook HMAC validation, or otherwise cryptographically bind the header-derived `shop` value to the signed payload before trusting it in `WebhookMetadata`, so a valid HMAC can only be replayed with the shop it was originally issued for.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a genuine webhook (e.g., `orders/create`) to the app's endpoint; captures the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker sends a new POST to the same public webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `to_signable_string` returns `B`; `HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H` [7](#0-6) .
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the app to act on attacker-controlled data as if it came from the victim shop.
