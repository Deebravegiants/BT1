### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using `Utils::HmacValidator.validate(request)`, but the HMAC signature is computed only over the raw request body. The `shop-domain` header — the value the library hands to app-defined webhook handlers as the tenant identifier — is never part of the signed material. This breaks the intended binding `hmac_valid(body) == authentic(shop)`; in reality `hmac_valid(body)` only proves the *body* is authentic, not which shop it belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against this signable string: [2](#0-1) 

`Registry.process` gates on that same validation and then forwards `request.shop` (parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cross-check against the signed body) to the app's handler as the trusted tenant identity: [3](#0-2) [4](#0-3) 

The `WebhookMetadata` struct passed to `WebhookHandler#handle` carries this unauthenticated `shop` value as the tenant identifier for the handler to act on: [5](#0-4) 

The equality the design is supposed to guarantee is: **shop-domain header used by the handler == shop that the HMAC-signed body actually originated from**. Because the header is excluded from the signable string, that equality is never checked. Any request whose body happens to match a previously-observed, legitimately-signed body (the same JSON payload — which frequently doesn't itself carry the merchant's domain) will pass `HmacValidator.validate` regardless of what `shop-domain` header accompanies it. An attacker who can capture/observe one authentic webhook delivery to their own installed app (or any endpoint reachable by them) can resend that exact body+HMAC pair while substituting an arbitrary `shop-domain`/`x-shopify-shop-domain` header value, and the library will report the webhook as valid and hand the attacker-controlled shop identity to the handler.

### Impact Explanation
This is a cross-tenant identity-binding break: the field the host application relies on to know *which merchant* a webhook body belongs to is not covered by the cryptographic check that is supposed to authenticate the request. An app that keys its data model or authorization decisions on `WebhookMetadata#shop` (the documented and expected usage) can be made to attribute another shop's webhook data/actions to a shop of the attacker's choosing, or vice versa, once the attacker controls or replays a body with a valid signature. This falls under the "Critical – cross-tenant access" category, since the identity used to route/attribute data across tenants is not authenticated.

### Likelihood Explanation
Exploitability requires the attacker to possess a genuinely-signed `(body, hmac)` pair — trivially available to any merchant with the app installed on their own shop, since Shopify sends real webhooks to real merchants that they can observe. Reusing that pair with a forged `shop-domain` header requires only being able to send an HTTP request to the app's public webhook endpoint (no secret key, no privileged access needed). Success additionally depends on the app's webhook body content not itself redundantly identifying the shop and the app trusting `WebhookMetadata#shop` — which is exactly the value this library exposes for that purpose, and is the documented mechanism (`docs/usage/webhooks.md`) for identifying the originating shop. Likelihood is assessed as realistic for any consumer of this gem that follows its documented API.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload before `Registry.process` trusts and forwards it to handlers. At minimum, document that `WebhookMetadata#shop` is not authenticated and must not be used as a sole tenant key, and/or add an explicit verification step (e.g., cross-checking against a body-embedded shop identifier when available) before dispatching to `handle`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and observes one legitimate webhook delivery, capturing `raw_body` and the `x-shopify-hmac-sha256` header (both are otherwise unprotected in transit/observability terms and are the attacker's own data).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint using the **same** `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body without any binding between them; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and calls the app's `handler.handle(data:)`, which will treat the payload as originating from `victim-shop.myshopify.com`, even though it never received or authorized this webhook.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
