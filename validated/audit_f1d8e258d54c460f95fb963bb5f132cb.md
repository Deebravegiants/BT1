## Analysis

The Convex-style bug ("implicit assumption of underlying token decimals" in a price/value conversion) has a direct analog in alt.fun's graduation math.

`Bonding.canGraduate` computes the USD trigger by multiplying the raw LT reserve amount by the LT's `exchangeRate()` and dividing by a hardcoded `1e18`: [1](#0-0) 

The same `realLtRaised × exchangeRate / 1e18` pattern is repeated in the graduation-cap preview: [2](#0-1) 

`IBounceLeveragedToken.exchangeRate()` is documented as "USDC per LT unit, 18-dp": [3](#0-2) 

but the interface never declares or checks `decimals()` on the LT token itself — the `/1e18` divisor is only correct if `realLtRaised` (a raw LT balance) is denominated in an 18-decimal token. The same 18-decimal assumption is baked into the LT-USD conversion helper used across the test suite/launch sizing (`_ltForUsd`), confirming the assumption is systemic rather than local to one function: [4](#0-3) 

The protocol is explicitly designed for **multiple** LTs (`Factory`'s `PairCreated(lt)` / `ltFor` mapping, per `AGENTS.md`), and `Bonding.launch`/the `IBounceLeveragedToken` interface contain no `decimals()` field or sanity check comparing the LT's decimals to the hardcoded `1e18` scale used everywhere reserves are converted to USD.

### Title
Graduation USD trigger and threshold math hardcode `1e18` and implicitly assume the paired LT has 18 decimals - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.canGraduate` and `Bonding.previewLtUntilGraduation` convert the raw LT reserve into a USD value via `realLtRaised * exchangeRate() / 1e18`, silently assuming the paired `IBounceLeveragedToken` has 18 decimals. No such check exists anywhere in `Bonding.sol` or `IBounceLeveragedToken.sol`.

### Finding Description
`canGraduate` reads the pair's stored LT reserve, subtracts the launch-time virtual reserve to get `realLtRaised` (a raw balance in the LT's native decimal units), then computes:
```
valueUsd = (realLtRaised * exchangeRate()) / 1e18
```
This is only correct when one whole LT token = `1e18` raw units, i.e. the LT has 18 decimals. `previewLtUntilGraduation` repeats the identical assumption when deriving `thresholdRealLt` from `graduationThresholdUsd * 1e18 / exchangeRate()`. Nothing in `Bonding.launch`, `Factory`, or `IBounceLeveragedToken` validates or reads the LT's `decimals()`; the interface doesn't even expose a `decimals()` getter. Because the system is explicitly built for multi-LT support (`Factory.ltFor` mapping, per `AGENTS.md`/`docs/contracts-scope.md`), any future BounceTech LT deployed with decimals other than 18 (BounceTech, like Curve's `crvRenWBTC`, could plausibly choose a different decimals value for an underlying-asset-denominated LT) will make this arithmetic wrong by orders of magnitude — exactly the bug class described in the Convex report, mapped onto alt.fun's dual graduation trigger instead of an oracle price.

### Impact Explanation
If a paired LT has fewer than 18 decimals (e.g. 6, mirroring USDC), `realLtRaised` in raw units is up to `1e12`× smaller than the formula expects, so `valueUsd` is understated by the same factor and the USD graduation trigger becomes practically unreachable. The curve then depends solely on the supply trigger (`tokenBalance() == 0`), meaning the entire 750M sellable token supply can be sold and the token forced to graduate while the USD math believes almost no value was raised — an unbacked/mispriced graduation whose LP is seeded off a curve that was never economically validated against the intended `$9K` threshold. Conversely, an LT with more than 18 decimals inflates `valueUsd`, causing premature graduation with a fraction of the intended real value locked, again yielding an underfunded/mispriced LP relative to the protocol's economic design. Both outcomes correspond to the "unbacked token or LT payouts" / "LP seeded away from the intended close price" impact categories.

### Likelihood Explanation
Triggering this requires the protocol operator to onboard a new LT with non-18 decimals via the existing multi-LT `Factory`/`Bonding.launch` path — no attacker privilege is needed once such an LT exists; any trader can then simply buy/sell normally to walk the curve into the mis-scaled graduation logic. Given the codebase explicitly plans for multiple LTs and performs zero decimals validation anywhere in `Bonding.sol` or `IBounceLeveragedToken.sol`, this is a systemic gap rather than a one-off edge case, though it only manifests when a non-18-decimal LT is actually paired.

### Recommendation
Add a `decimals()` accessor to `IBounceLeveragedToken` (or read it via the standard `IERC20Metadata` interface) and normalize all `exchangeRate()`-based conversions in `Bonding.sol` (`canGraduate`, `previewLtUntilGraduation`, and any launch-time virtual-liquidity sizing) using `10 ** ltDecimals` instead of a hardcoded `1e18`. Alternatively, enforce an explicit `decimals() == 18` sanity check in `Bonding.launch` (or wherever a new LT is registered via `Factory`) and revert if a future LT violates that assumption.

### Proof of Concept
1. Deploy a `MockLeveragedToken`-style LT with `decimals() = 6` (mirroring the pattern of `crvRenWBTC` cited in the source report) and register it via `Factory`/`Bonding.launch` for a new token.
2. Buy through `Zap.buy` repeatedly, raising real LT into the pair. Because `realLtRaised` is now denominated in 6-decimal raw units, `canGraduate`'s `realLtRaised * exchangeRate() / 1e18` computes a `valueUsd` roughly `1e12`× smaller than the actual USD value raised.
3. Continue buying until `IPair.tokenBalance() == 0` (the supply trigger fires) while `valueUsd` remains far below `graduationThresholdUsd` — the token graduates via the supply leg alone, with the USD leg never having been satisfied, demonstrating the LP is seeded without the intended economic backing.
