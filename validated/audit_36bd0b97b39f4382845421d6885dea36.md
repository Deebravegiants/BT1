### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook is authentic by calling `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` — for `Webhooks::Request` this is defined as `@raw_body` only [1](#0-0) . The `shop` value handed to the app's handler, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `WebhookMetadata` (built from `request.shop`) to the handler [3](#0-2) .

### Finding Description
`HmacValidator.validate` / `validate_signature` recompute `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compare it to the `hmac` value using `OpenSSL.secure_compare` [4](#0-3) . Because `to_signable_string` for a webhook request is only the raw body, the signature binds *body bytes ↔ app secret*, but the code (and every consuming app, per the gem's own documented pattern) additionally trusts *shop-domain header ↔ tenant identity* without that binding being covered by the HMAC. The identity equality that should hold is:

`shop used for tenant-scoped action == shop cryptographically bound by the HMAC`

but the actual equality enforced is only:

`raw_body == raw_body(signed by app_secret)`

with `shop` supplied independently and unauthenticated. Since a single app's `api_secret_key` is shared across every shop that installs the app, any store owner or partner staff member who can trigger a real webhook to their own store (e.g. by installing the app on a free development store) receives a validly-HMAC-signed request from Shopify. They can then replay that request to the app's webhook endpoint after swapping the `x-shopify-shop-domain` header to a victim shop's domain (and optionally the topic/webhook-id) — the HMAC still validates because it never covered that header, yet `Registry.process` builds `WebhookMetadata` with the attacker-chosen `shop` and dispatches it to the app's handler as if it originated from the victim tenant [5](#0-4) .

### Impact Explanation
Apps built on this gem are documented to key business logic off `data.shop` (e.g., enqueuing shop-scoped jobs: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) . An attacker who owns any shop that has the app installed can forge webhook payloads (of their own choosing, since they control their own store's data/orders/products) and cause the host app to process them under an arbitrary victim shop's identity — this is a cross-tenant boundary break: data or events for shop A get attributed and applied to shop B purely because the gem's HMAC check does not bind the `shop` field it hands to the handler.

### Likelihood Explanation
Any unprivileged internet user can register as a Shopify partner/developer and install a public app on a free development store to legitimately receive real, validly-signed webhooks from Shopify for that store. Because the HMAC only signs the JSON body, and body content for many topics is attacker-controlled (e.g. product/order create on their own store), replaying with a modified `shop-domain` header requires no secret material — only intercepting/replaying their own genuine webhook HTTP request with one header changed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material used for verification, or otherwise cryptographically bind `request.shop` to the HMAC before it is trusted. Concretely, `Webhooks::Request#to_signable_string` should not be limited to `@raw_body`; the validator (or `Registry.process`) should additionally confirm that the shop the payload is attributed to is the one Shopify signed for — e.g., by validating against a known/expected shop for that webhook registration, not just checking `HmacValidator.validate(request)` against the body alone [7](#0-6) .

### Proof of Concept
1. Attacker creates a free development store and installs the vulnerable app; the app registers webhooks via `Registry.register_all` for topics such as `orders/create`.
2. Attacker triggers an event on their own store (e.g., creates an order), causing Shopify to POST a validly HMAC-signed webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid signature over raw body>`.
3. Attacker captures this request and resends it to the same endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com` (leaving body and HMAC header untouched).
4. `HmacValidator.validate` succeeds because it only checks the (unchanged) `raw_body` against the (unchanged) HMAC header [8](#0-7) .
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which now performs shop-scoped logic (data storage, job enqueue, etc.) attributing the attacker-controlled body/event to `victim-shop.myshopify.com` [9](#0-8) .
