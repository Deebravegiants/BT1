## Title
IntentsV2 `fillOrder` sends solver output tokens to an unchecked, order-creator-controlled `beneficiary` address, permitting permanent loss of filler funds to the zero address - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain` read the payment recipient from `order.output.beneficiary`, a `bytes32` field fully controlled by the (unprivileged) user who calls `placeOrder`. Neither function validates that the derived `address beneficiary` is non-zero before sending the solver's ERC20/native output tokens to it, mirroring the `SdtBlackHole.pullSdStakingBrides` bug class where an unchecked destination address parameter allows funds to be transferred (and permanently burned) at the zero address.

### Finding Description
In `IntrinsicIntents.sol`: [1](#0-0) 

the `beneficiary` used for both the native-value `.call{value: ...}` and `IERC20.safeTransferFrom(msg.sender, beneficiary, ...)` calls is derived directly from `order.output.beneficiary` with no zero-address check: [2](#0-1) [3](#0-2) 

The same pattern exists in the cross-chain fill path: [4](#0-3) 

and in the Tron variant of the gateway: [5](#0-4) 

`order.output.beneficiary` is set entirely by the order creator when calling `placeOrder` — the contract only stamps `order.user`, `order.source`, and `order.nonce`, leaving `order.output` (including `beneficiary`) as supplied by the caller: [6](#0-5) 

Any address, including `bytes32(0)`, is accepted. When a solver (an unprivileged filler) calls `fillOrder` on such an order, their own output tokens (`totalRequired + beneficiaryShare`, potentially the full order amount plus surplus) are transferred to `address(0)` and irrecoverably burned, while the solver still releases the order's escrowed input tokens to themselves via `_withdraw`. This is the same root-cause class as the reported `SdtBlackHole` bug: an externally supplied recipient/processor address is used as a token transfer destination without a zero-address guard.

### Impact Explanation
An unprivileged order creator can construct a legitimate-looking order (correct token/amount fields) with `output.beneficiary = 0`. A solver's automated bot that fills orders based on economics without independently re-validating the beneficiary field will send its output tokens to the burn address permanently, while the order creator's escrow still exists to be redeemed normally by that same solver call (the escrow-release side is always keyed off `msg.sender`, so the solver still nominally "completes" the fill and pays gas). Net effect: solver-provided liquidity (ERC20 or native tokens) is destroyed with no recovery path — a permanent loss of funds for the filler role of the protocol, satisfying the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a solver to fill an order without checking `output.beneficiary != address(0)` off-chain first. Because the protocol supports both scripted/automated solvers and the `SolverAccount`/session-key auction flow described in the docs, and because the contract itself performs no on-chain guard, a single malformed or malicious order is sufficient to trigger fund loss for any filler that does not add its own client-side check. This is directly reachable by any address able to call `placeOrder` (no privilege required).

### Recommendation
Add an explicit zero-address check on the decoded `beneficiary` in `_fillSameChain`, `_fillCrossChain` (and the Tron `IntentGatewayV2.withdraw`/fill equivalents) before any transfer occurs, e.g.:
```solidity
address beneficiary = address(uint160(uint256(order.output.beneficiary)));
if (beneficiary == address(0)) revert InvalidBeneficiary();
```
Consider performing this validation once in `placeOrder` as well, rejecting orders whose `output.beneficiary` is the zero address, so malformed/malicious orders can never enter escrow in the first place.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with a normal `inputs` array and `order.output = PaymentInfo({ beneficiary: bytes32(0), assets: [...], call: "" })`.
2. A solver observes the order, deems the economics profitable, and calls `fillOrder` with matching `options.outputs`.
3. Inside `_fillSameChain`/`_fillCrossChain`, `beneficiary = address(uint160(uint256(order.output.beneficiary))) == address(0)`.
4. `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` (or the native `.call{value: ...}`) sends the solver's tokens to `address(0)`, burning them irrecoverably.
5. `_withdraw`/escrow release still pays the solver the order's escrowed input tokens via `_orders`, so the order completes from the protocol's perspective, but the solver's output payment is permanently lost.
