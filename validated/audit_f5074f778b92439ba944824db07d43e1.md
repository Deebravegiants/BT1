### Title
Webhook Shop/Topic Identity Spoofing via Headers Not Covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields consumed by `Registry.process` are taken from unauthenticated HTTP headers. This breaks the identity binding between "bytes verified" (the body) and "bytes acted on" (the shop/topic identity used to route and attribute the webhook), enabling cross-tenant webhook spoofing by anyone who can obtain one validly-signed webhook body from any shop (including their own) under the same app.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies the HMAC exclusively against that signable string: [1](#0-0) [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` only checks the HMAC and then dispatches the handler using these unauthenticated header values, including `shop`: [4](#0-3) 

Since `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), an unprivileged attacker who installs the same public app on their own store can capture one of their own legitimately-signed webhook deliveries (valid `body` + valid `hmac`, both computed with the shared app secret) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to name a different, victim shop. The equality the code relies on is:

`HMAC(body, api_secret_key) valid` ⟹ `shop header == true origin shop`

but the code only proves the left side; the right side (shop attribution) is asserted, not verified, because `shop` is never part of the signed bytes.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem will invoke the merchant's webhook handler with `WebhookMetadata` claiming the data originated from an arbitrary victim shop (`data.shop`), while the actual `body` content is attacker-controlled (from the attacker's own shop). Handlers commonly key persistence, authorization, or session lookups off `data.shop` combined with `data.body`, so this can be leveraged to inject attacker-controlled data attributed to a victim tenant, corrupt per-shop state, or bypass shop-scoped logic — a cross-tenant integrity/data-attribution bypass.

### Likelihood Explanation
Exploitation only requires an "unprivileged internet user" capability: installing the same publicly-installable app on a self-owned/dev store (or otherwise obtaining one legitimate webhook delivery), capturing the raw body + `hmac-sha256` header, and replaying it to the target app's public webhook endpoint with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged account for the victim shop is needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material verified against `hmac`, or otherwise cryptographically tie the header-derived identity to the signed body — e.g., include `shop`/`topic` in `to_signable_string`, or require the host application to independently correlate `request.shop` against a shop known to have triggered the specific `webhook_id`/event via the Admin API before trusting it. At minimum, document that `Request#shop`/`#topic` are unauthenticated and must not be trusted for authorization decisions independent of out-of-band verification.

### Proof of Concept
1. Attacker installs the target public app on shop `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., `orders/create`) and captures the delivered webhook: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a new HTTP request to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since body is unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data as if it belongs to `victim.myshopify.com`.
