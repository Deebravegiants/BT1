### Title
`DirectBridge.describeWithdrawal` reports "completed" without verifying the on-chain outcome of the withdrawal transfer - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge.describeWithdrawal` unconditionally returns `{ status: "completed", txHash: args.tx.hash }` for every NEAR-native withdrawal, without checking whether the underlying `ft_transfer`/`ft_withdraw`/`native_withdraw` cross-contract call to the destination actually succeeded on-chain.

### Finding Description
`DirectBridge` (route `RouteEnum.NearWithdrawal`) builds a `ft_withdraw`/`native_withdraw` intent primitive via `createWithdrawIntentPrimitive` [1](#0-0) , which the verifier contract (`intents.near`) executes asynchronously by issuing a cross-contract `ft_transfer`/`ft_transfer_call` (or native transfer) promise. Whether the intent-signing NEAR transaction (`args.tx`) itself succeeded is orthogonal to whether that resulting outbound transfer promise/receipt succeeded, because NEAR cross-contract calls execute in separate receipts that can fail independently (e.g., missing storage registration for the receiver, receiver contract rejecting `ft_on_transfer`, gas exhaustion in the callback).

Despite this, `describeWithdrawal` in `DirectBridge` returns `completed` immediately, based purely on the existence of the settled intent transaction hash, with no query of the resulting transfer receipt or its execution outcome:

```
async describeWithdrawal(
	args: WithdrawalIdentifier,
): Promise<WithdrawalStatus> {
	return { status: "completed", txHash: args.tx.hash };
}
``` [2](#0-1) 

This is analogous to the C4 finding's "unhandled return value" pattern: instead of an unchecked ERC20 `transfer`/`transferFrom` boolean return, here the SDK unconditionally treats the NEAR withdrawal as "completed" without checking the actual outcome of the transfer receipt that moves funds to the user. Other bridge implementations in the same codebase (`HotBridge`, `OmniBridge`, `PoaBridge`) explicitly query an indexer/contract view method for the transfer's real state before reporting `completed` [3](#0-2) [4](#0-3) [5](#0-4) , while `DirectBridge` (and similarly `IntentsBridge` for internal transfers [6](#0-5) ) skips this verification entirely.

`watchWithdrawal`, which drives all downstream completion signaling (`waitForWithdrawalCompletion`, `processWithdrawal`), trusts `describeWithdrawal`'s reported status verbatim: a `completed` status is converted directly into a resolved `TxInfo`/`TxNoInfo` with no additional on-chain verification [7](#0-6) . The `WithdrawalStatus` type's own documentation states `completed` should mean "I checked, and it succeeded" [8](#0-7) , but `DirectBridge` never performs that check.

### Impact Explanation
If the outbound `ft_transfer`/`ft_withdraw` receipt fails after the intent-signing transaction succeeds (e.g., receiver lacks storage registration on the token contract, or the receiver rejects the transfer), `DirectBridge.describeWithdrawal` still reports `status: "completed"` with a valid `txHash`. Integrators relying on `processWithdrawal`/`waitForWithdrawalCompletion` would incorrectly believe funds were delivered and could credit the user or mark the withdrawal as settled, while the underlying tokens either remain in the verifier contract or are lost, without any mechanism to detect and reconcile the discrepancy. This matches the "status reported that is not the on-chain outcome" class, with impact of an integrator crediting/refunding based on a false completion status.

### Likelihood Explanation
This path is reachable on every `NearWithdrawal`-route withdrawal (the default/direct bridge used for NEP-141 tokens withdrawn to NEAR), so any receiver-side failure of the transfer receipt (unregistered storage, receiver contract logic reverting `ft_on_transfer`) triggers the misreport without any attacker action needed — this is a systemic gap in the bridge's own completion check rather than a required malicious input. However, whether this actually materializes as a loss depends on how often such receiver-side transfer failures occur in practice, which was not independently verified from the available context.

### Recommendation
Before returning `completed`, `DirectBridge.describeWithdrawal` should verify the actual transfer outcome — e.g., by inspecting the receipt/execution outcome of the intent transaction (via `FinalExecutionOutcome.receipts_outcome`) for the specific `ft_transfer`/`native_withdraw` receipt, or by querying token balance/refund events, and return `failed` (or `pending`) when that outcome cannot be confirmed as successful, consistent with the behavior of `HotBridge`, `OmniBridge`, and `PoaBridge`.

### Proof of Concept
1. Call `sdk.processWithdrawal` with `routeConfig: createNearWithdrawalRoute()` for an NEP-141 token, targeting a receiver account that is not registered for storage on that token contract (or whose `ft_on_transfer`/receive logic panics).
2. The intent-signing NEAR transaction (`intents.near` call) settles successfully, so `waitForIntentSettlement` resolves with a valid `tx`.
3. The subsequent cross-contract `ft_transfer` promise fails/reverts in a separate receipt because the receiver account lacks storage registration.
4. `DirectBridge.describeWithdrawal` is invoked with this `tx` and unconditionally returns `{ status: "completed", txHash: args.tx.hash }` [2](#0-1) .
5. `watchWildrawal`/`waitForWithdrawalCompletion` report the withdrawal as completed to the caller, even though the token transfer to the destination never succeeded.

		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Represents the current state of a withdrawal as returned by bridge adapters.
 *
 * Error handling follows AWS SDK "describe" API patterns:
 * - **Thrown errors**: Infrastructure failures (network, auth, service unavailable).
 *   Meaning: "I couldn't check the status."
 * - **`failed` status**: Job-level failure reported by the bridge.
 *   Meaning: "I checked, and the withdrawal failed."
 *
 * @see https://docs.aws.amazon.com/AmazonS3/latest/userguide/batch-ops-job-status.html
 */
export type WithdrawalStatus =
	| { status: "pending" }
	| { status: "completed"; txHash: string | null }
	| { status: "failed"; reason: string };
