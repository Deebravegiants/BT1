### Title
Webhook `topic`, `shop`, and `webhook-id` headers are trusted by `Registry.process` despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against that body alone before dispatching the webhook handler with the unauthenticated `topic` and `shop` header values. The gem's own HMAC check therefore verifies "this body byte-string was produced with our secret," not "this body belongs to this shop/topic," yet `Registry.process` hands the handler a `WebhookMetadata` object built from the unverified header fields as if they were authenticated.

### Finding Description
`Request#to_signable_string` is defined as simply `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (i.e. only the body) and compares it against `request.hmac`: [3](#0-2) [4](#0-3) 

After this check passes, `Registry.process` looks up the handler purely from the unauthenticated `request.topic` and constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, then calls `handler.handle`: [5](#0-4) 

The identity binding that should hold is:
`HMAC-verified(body)` == `HMAC-verified(shop, topic, webhook_id)`

but in this implementation only the body is inside the HMAC's signable string, while `shop`/`topic`/`webhook_id` are read from plain, unauthenticated headers and passed on to the handler as if verified. Any party capable of delivering an HTTP POST to the app's webhook endpoint (this includes the app's own webhook receiver being reachable on the public internet, as it must be for Shopify to call it) can therefore submit a POST with a genuine `hmac-sha256`/body pair that they can legitimately obtain (e.g., from a webhook fired for their own shop) while freely substituting the `shop-domain`, `topic`, and `webhook-id` headers, since none of those are covered by the signature.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to select which tenant's session/record to update (this is the documented/expected usage pattern - the handler receives `shop` precisely so it can look up the corresponding merchant), an attacker who possesses one authentic `(body, hmac)` pair signed with the app's secret (trivially obtainable by installing the app on their own store and capturing a webhook Shopify sends to their own endpoint) can relabel that payload with an arbitrary victim `shop-domain` and `topic` and have it processed by the handler as if it originated from the victim shop. This is a cross-tenant data-confusion primitive: it lets an attacker inject an event under another merchant's identity into the app's authenticated-webhook pipeline, without ever obtaining the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any Shopify store (attacker's own, free dev store), (2) capturing one genuine webhook body+HMAC pair delivered for that store, and (3) sending a crafted POST directly to the app's public webhook endpoint with substituted `shop-domain`/`topic`/`webhook-id` headers. No credentials, tokens, or `client_secret` are needed, and no privileged access to Shopify is required - only the ability to send arbitrary HTTP requests to the app's already-public webhook receiver, which is inherent to how webhook endpoints work.

### Recommendation
Extend `to_signable_string` (or add a companion binding check in `Registry.process`) to bind the `topic`, `shop`, and `webhook_id` header values into the HMAC-verified data, or independently reject/flag any mismatch between the shop asserted in headers and the shop that owns the session/registration the webhook is meant to update. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are **not** part of the signature and must be cross-checked by the host application against known, installed shop sessions before being trusted for tenant-scoped operations.

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own store and captures a
# legitimate webhook POST that Shopify signs and sends to the app's endpoint:
#   headers: {
#     "x-shopify-topic" => "orders/create",
#     "x-shopify-hmac-sha256" => "<valid HMAC of raw_body computed with app secret>",
#     "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
#   }
#   raw_body = '{"id": 123, ...}'  # generic body with no shop info in it

# Step 2: Attacker resends the exact same body + hmac, but swaps only the
# shop-domain (and/or topic) header - HMAC still validates because
# Request#to_signable_string only ever returns @raw_body:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<same valid HMAC as captured above>",
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Step 3: HmacValidator.validate(request) still returns true, because it
# only checks OpenSSL::HMAC over @raw_body - it never inspects `shop`.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The handler now believes this event is authentically from victim-shop.
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
