### Title
Escrow withdrawal treats a `false` boolean return from `IERC20.transfer` as success, permanently freezing solver/user funds for non-compliant tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds using a raw low-level `.call` to the token's `transfer` selector and only checks that the call did not revert (`success`), never decoding/validating the returned boolean. Non-ERC20-compliant tokens that signal failure by returning `false` (instead of reverting) will be treated as a fully successful transfer, while escrow accounting and terminal state (`_filled`, `EscrowReleased`/`EscrowRefunded`) are updated as if the beneficiary was paid.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` performs escrow release/refund like this: [1](#0-0) 

and the fee-token payout right after it: [2](#0-1) 

The same unchecked-return pattern is used in `SweepDust` handling in `onAccept()`: [3](#0-2) 

and in the predispatch-sweep path in `placeOrder`: [4](#0-3) 

In all of these, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only checks `success` (i.e., that the call did not revert). Per the reported bug class (analogous to the Balancer non-compliant-token report), tokens are not guaranteed to revert on failed transfer — some legacy/non-standard ERC20s return `false` on failure. Solidity's low-level `.call` does not automatically bubble that boolean into `success`; the code must decode `returndata` and verify `abi.decode(data, (bool))`. Because that check is absent here, a `transfer` call to such a token that logically fails (returns `false`) is misclassified as a success.

This is a real regression relative to the mainline EVM implementation: `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()` uses OpenZeppelin's `SafeERC20.safeTransfer`, which correctly validates both call success and the boolean return value: [5](#0-4) 

The Tron `IntentGatewayV2.sol` bypasses this safety net.

### Impact Explanation
`withdraw()` is the terminal settlement path for the IntentGateway escrow reachable directly from a relayed cross-chain `RedeemEscrow`/`RefundEscrow` message (via `onAccept`) as well as from `onGetResponse` for source-chain cancellations — both are attacker/relayer-reachable, unprivileged flows once a proof is delivered. If the escrowed input token (chosen by the user when placing the order) is non-ERC20-compliant and its `transfer` silently returns `false` on failure (e.g., due to insufficient allowance-independent internal restrictions, blacklists, or pausability triggered between escrow and withdrawal), the contract will:
1. Mark the order as `_filled` (finalized) and decrement `_orders[commitment][token]`, and
2. Emit `EscrowReleased`/`EscrowRefunded` as if funds were paid,

even though the beneficiary never received the tokens. Because the order state is already finalized, there is no retry path — the escrowed tokens remain permanently stuck in the contract with no way for the beneficiary to reclaim them, and no error is surfaced. This is a permanent freezing/loss-of-funds condition triggerable by any order that escrows a non-compliant token, satisfying the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Triggering requires only that a user creates an order (or the protocol registers) using a token whose `transfer` function can return `false` instead of reverting — a common trait among several widely used but non-fully-compliant ERC20 tokens. No special privileges are needed: any unprivileged user can place an order denominated in such a token, and the withdrawal path executes automatically as part of normal fill/cancel/settlement flows.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()`, the `SweepDust` handler, and the predispatch sweep in `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (as already done in `evm/src/apps/intentsv2/IntentsBase.sol`), which decodes and validates any returned boolean data in addition to checking call success. Additionally, document/whitelist which tokens are supported by the Intent Gateway to exclude non-ERC20-compliant assets, consistent with the recommendation in the referenced report.

### Proof of Concept
1. Deploy a non-compliant ERC20 token whose `transfer(address,uint256)` returns `false` (rather than reverting) when, e.g., the recipient is blacklisted or an internal condition fails, but otherwise behaves like a normal token for `transferFrom`/`balanceOf` used during escrow.
2. A user places an order on the Tron `IntentGatewayV2` escrowing this token as an input (`placeOrder`), which succeeds via `safeTransferFrom` (input side is protected).
3. Before settlement, the condition causing `transfer` to return `false` is triggered (e.g., beneficiary gets blacklisted, or the token pauses transfers to certain addresses).
4. The order is filled/cancelled, and Hyperbridge relays a `RedeemEscrow`/`RefundEscrow` message that reaches `onAccept` → `withdraw()`.
5. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` succeeds at the call level (`success == true`) even though the token's internal logic returned `false` and did not move funds.
6. `_orders[commitment][token]` is decremented to zero and `EscrowReleased`/`EscrowRefunded` is emitted, permanently finalizing the order — the tokens remain locked in the `IntentGatewayV2` contract with no recovery mechanism for the beneficiary.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
