### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Data Injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body only, while the `shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) is read separately and never included in, or checked against, the signature. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the webhook handler as the tenant identifier for the delivered payload. Because the shop identity is not bound to the signed bytes, any party who can produce one *valid* HMAC/body pair (trivially available to any merchant who installs the app on their own store, since Shopify will send them a correctly-signed webhook for their own data) can resubmit that exact signed body to the app's public webhook endpoint with an arbitrary `shop-domain` header, and the app will process/attribute that payload as belonging to a different, victim shop.

### Finding Description
- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` is parsed independently from a header that is not part of the signed payload: [2](#0-1) 
- `HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the received `hmac`; it never touches `shop`: [3](#0-2) 
- `Registry.process` trusts `request.shop` for downstream processing immediately after HMAC validation succeeds: [4](#0-3) 

The equality/binding that should hold is: `shop signed-by-HMAC == shop acted upon by the handler`. In this code, the left side does not exist — the HMAC only binds the body, not the shop — so the binding is broken. Any webhook subscriber (a merchant who has installed the app, an "unprivileged internet user" relative to other tenants of the same app) can obtain a genuinely-signed `(raw_body, hmac)` pair for their own shop's event, then POST it directly to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds because it only checks the body/secret pair, and `Registry.process` will hand the handler `WebhookMetadata` claiming the payload is from the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC is meant to guarantee: an app relying on `ShopifyAPI::Webhooks::Registry` to authenticate the origin shop of webhook payloads can be made to ingest, store, or act on attacker-supplied data (their own legitimately-signed webhook body) under another merchant's identity. Depending on how the host app uses `WebhookMetadata#shop`/`#body` (e.g., syncing orders, updating inventory, triggering per-shop side effects), this enables cross-tenant data injection/corruption without needing any secret, token, or privileged access — only requiring installation of the app on one's own store, which is the baseline unprivileged capability of an internet user interacting with a public app.

### Likelihood Explanation
High likelihood: obtaining a legitimately signed webhook body is trivial for anyone who installs the app on a shop they control (e.g., triggering `orders/create`). Replaying that request to the app's webhook endpoint with a modified `shop-domain` header requires no cryptographic material and no access to `api_secret_key`.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise independently authenticate `request.shop` before trusting it — e.g., include the shop domain in the signable string, or require the delivered shop to be resolved from Shopify-side webhook metadata/session lookup rather than trusting the caller-supplied header. At minimum, cross-check `request.shop` against `ShopifyAPI::Utils::ShopValidator` and reconcile it with a stored, authenticated session/shop mapping for the given `webhook_id` before invoking handlers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers an event that causes Shopify to POST a legitimate webhook to the app's public endpoint, e.g. `orders/create`, capturing:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid HMAC of `B`)
2. Attacker resends the exact same `(B, H)` pair directly to the same app endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic`/`x-shopify-webhook-id` unchanged
3. `ShopifyAPI::Webhooks::Request.new` parses the forged `shop` header; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The registered handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)` and processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
