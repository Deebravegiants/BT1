### Title
Missing relayer authorization on Tron `IntentGatewayV2.onAccept` allows any relayer to forge escrow redemption/refund and governance delivery - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` implements `onAccept` with only `onlyHost` gating — it never checks the delivering relayer. Every other implementation of the same intents-gateway logic in this codebase (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) calls `_checkRelayer(incoming.relayer)` as the very first line of `onAccept`, before the request body is even decoded. The Tron contract has no `_relayer` state, no `_checkRelayer` function, and no `setRelayer`/`relayer()` accessor at all, per the grep against the file returning zero matches for `_relayer|_checkRelayer|relayer\(\)|onGetResponse`.

### Finding Description
`EvmHost.dispatchIncoming` (or the Tron equivalent's host) authenticates only that the *message itself* passed ISMP proof verification and arrived through the configured handler — it forwards whichever `msg.sender` (relayer) actually submitted the delivery transaction as `incoming.relayer`, with no restriction on who that relayer is: `evm/src/core/EvmHost.sol` calls `IApp.onAccept(IncomingPostRequest(request, relayer))` for *any* caller of the handler. The intent-gateway's *own* application-layer check on top of that (`_checkRelayer`) is what restricts which relayer submissions are honored for the sensitive branches — this is documented explicitly in `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md` and enforced in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`:

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    _checkRelayer(incoming.relayer);
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    ...

The Tron variant's `onAccept` omits this line entirely:

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        authenticate(incoming.request);
        WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
        return withdraw(body, kind == RequestKind.RefundEscrow);
    }

    // only hyperbridge is permitted to perfom these actions
    if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
    if (kind == RequestKind.NewDeployment) { ... }
``` [2](#0-1) 

This is structurally the same bug class as the Dokploy CVE: the host-level "session" (that the call came through `onlyHost`, i.e. through a proof-verified ISMP delivery) is validated, but authorization over *who is allowed to exercise that delivery* — the equivalent of Dokploy's per-server access check — is missing. `authenticate(incoming.request)` for `RedeemEscrow`/`RefundEscrow` only checks that `request.from` matches the registered peer gateway instance on the *source* chain (an inter-chain identity check), and the `source == hyperbridge` check for governance actions only checks the *message's origin chain*. Neither check restricts *which relayer* (i.e., `msg.sender` on the handler, forwarded as `incoming.relayer`) is allowed to submit the delivery. Since the ISMP handler on any chain accepts delivery submissions from an unprivileged, permissionless caller once a valid proof exists, and a valid proof for a genuine cross-chain message can be replayed/submitted by *anyone* holding it (proofs and messages are public data on Hyperbridge), any address can call the handler themselves to trigger `onAccept`/`onGetResponse` on the Tron gateway for a message that was intended to require a specific authorized relayer.

### Impact Explanation
On chains where the sibling `ExtrinsicIntents.sol` relayer gate exists, `_checkRelayer` is the boundary that keeps a delivery from being submitted before the message-specific relayer allowlist review runs — it defends against permission-less delivery of governance actions (`Execute`, `UpgradeContract`/upgrade calldata, `SweepDust`, `UpdateParams`, `NewDeployment`) and escrow redemption/refund payouts. On Tron, that gate is entirely absent, so:
- `RedeemEscrow`/`RefundEscrow` deliveries — which release escrowed user funds — can be submitted by any address as soon as a valid proof exists, bypassing whatever relayer-selection/ordering guarantees the rest of the protocol assumes for delivery.
- Governance-class actions (`NewDeployment`, `UpdateParams`, `SweepDust`) — which change registered peer instances, protocol parameters/fees, and sweep dust to an attacker-controlled beneficiary — are reachable by any relayer, not just the one Hyperbridge's off-chain infrastructure intends to authorize, undermining the "governance channel" trust model the rest of the codebase relies on (`SweepDust`'s beneficiary is attacker-supplied ABI data inside the message body).

This is a real, exploitable unauthorized-app-action / potential fund-theft path reachable from a single relayed delivery — meets High/Critical bar under "unauthorized app action" / "route unable to enforce its own access control."

### Likelihood Explanation
High. No special privilege is needed — any account can call the ISMP handler to deliver a message once a valid proof is available (this is the entire point of the permissionless relayer network), and on Tron `IntentGatewayV2` there is no secondary check to stop it. The only barrier to exploitation is possession of a valid proof for the target message, which is public/observable the same way any relayer observes it today.

### Recommendation
Add the same `_relayer`/`_checkRelayer` gate to `evm/tron/contracts/apps/IntentGatewayV2.sol` that exists in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`: introduce a `_relayer` storage slot, a host-only `setRelayer`, and call `_checkRelayer(incoming.relayer)` as the first statement in both `onAccept` and `onGetResponse`, mirroring the fix pattern documented in `sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md`. Audit all other Tron (and any other chain-specific fork) contracts under `evm/tron/contracts/` for the same divergence from the canonical `evm/src/apps/intentsv2/ExtrinsicIntents.sol` implementation, since this indicates the Tron port was not kept in sync with a security-relevant fix applied to the main EVM contracts.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` contract at `evm/tron/contracts/apps/IntentGatewayV2.sol`, with a genuine order placed and a solver having filled it on the destination chain (or a governance message dispatched from Hyperbridge, e.g. `SweepDust`).
2. Wait for the corresponding proof to become available (state commitment landed on the destination/Tron host) — this is public information any observer can retrieve, exactly as a legitimate relayer would.
3. From an arbitrary, non-relayer account, submit the delivery directly to the Tron ISMP handler with the valid proof (calling the handler's post-request delivery function, which then calls `host.dispatchIncoming(request, msg.sender)` → `IntentGatewayV2.onAccept`).
4. Observe that `onAccept` executes successfully for `RedeemEscrow`/`RefundEscrow`/`SweepDust`/`UpdateParams`/`NewDeployment` regardless of `incoming.relayer`, because no `_checkRelayer` call exists — contrast with `evm/tests/foundry/IntentGatewayV2Test.sol::testOnAcceptGovernanceRejectsUnlistedRelayer`, which proves the canonical EVM contract reverts with `Unauthorized` for exactly this scenario when `relayer` is not the authorized one; the Tron contract has no equivalent test or check and would not revert.
