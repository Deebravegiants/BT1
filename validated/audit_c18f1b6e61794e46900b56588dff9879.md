## Finding

### Title
LPs permanently lose access to their funds when the pool `status` is set to `Disabled` - ([File: program/src/state.rs])

### Summary
Similar to the referenced report where a global pause (`whenNotPaused`) blocks `executeClose()` and locks users out of closing positions, Raydium AMM's `AmmStatus::Disabled` state blocks every user-facing capability, including withdrawal, leaving LPs with no way to redeem their LP tokens for the underlying pool assets.

### Finding Description
The pool's permission model is defined by `AmmStatus` in [1](#0-0) . Each status grants a distinct combination of `deposit_permission`, `withdraw_permission`, `swap_permission`, and `orderbook_permission`, implemented in [2](#0-1) .

Critically, while `WithdrawOnly`, `LiquidityOnly`, `OrderBookOnly`, `SwapOnly`, and `WaitingTrade` all preserve `withdraw_permission() == true` (letting LPs always redeem their share), the `Disabled` status sets `withdraw_permission()` to `false` as well as `deposit_permission()` and `swap_permission()`: [3](#0-2) 

`process_withdraw` enforces this permission check directly before allowing any coin/pc to be returned to the LP: [4](#0-3) 

The `status` field can only be updated by the privileged `amm_owner` via `process_set_params`, which validates the new status with `AmmStatus::valid_status` (which permits `Disabled = 2`) and writes it directly to `amm.status` with no other constraints, time-lock, or reversibility guarantee for user funds: [5](#0-4) [6](#0-5) 

Once `Disabled` is set, there is no unprivileged instruction path in `process` that lets an LP redeem their LP tokens: `process_deposit`, `process_withdraw`, `process_swap_base_in/out` (and their v2 variants) all gate on the corresponding `AmmStatus` permission and will return `AmmError::InvalidStatus` for a disabled pool. `process_withdrawpnl` is the only instruction that operates on “all status except Uninitialized”, but it is restricted to the `pnl_owner`/`amm_owner`, not regular LPs: [7](#0-6) 

Unlike the other partially-restricted statuses which were clearly designed to keep an "exit" path open for LPs (e.g., `WithdrawOnly` exists specifically to let users pull liquidity out while other functions are paused), `Disabled` removes withdrawal entirely with no dedicated user-triggered exit mechanism, mirroring the report's core theme: pausing a critical exit function traps user funds.

### Impact Explanation
If the pool is ever placed into `Disabled` status (deliberately, mistakenly, or as a stop-gap emergency measure during an incident), every LP's principal becomes permanently frozen in the vaults with no code path to redeem LP tokens back into `coin`/`pc` tokens, unless/until the owner flips the status again. If the owner key is unavailable, compromised in a way that only allows freezing (not un-freezing), or the protocol is abandoned in the disabled state, LP funds are permanently locked — a full loss-of-funds/availability scenario for liquidity providers, who are the affected unprivileged actors here (same actor class as "traders" in the analog report).

### Likelihood Explanation
Setting `status = Disabled` is an explicit, documented, valid state transition (`AmmStatus::valid_status` accepts `2u64`) reachable via the normal `SetParams` instruction which the project's own owner-key is expected to exercise for pausing during incidents — the exact "emergency pause" scenario the original report is about. The likelihood of the status being set (by design, for legitimate pause purposes) is expected/plausible over the pool's lifetime, and once set the freeze is deterministic and total, with no time-boxing or user-facing override.

### Recommendation
Preserve `withdraw_permission() == true` for the `Disabled` status (as is already done for `WithdrawOnly`, `LiquidityOnly`, `OrderBookOnly`, `SwapOnly`, and `WaitingTrade`) so LPs always retain the ability to redeem their LP tokens even when deposits/swaps/orderbook activity are paused, or add a dedicated emergency-withdraw instruction that bypasses `swap_permission`/`deposit_permission` gating but still allows LP redemption regardless of `status`.

### Proof of Concept
1. Pool is live and LPs hold LP tokens against `amm.coin_vault`/`amm.pc_vault`.
2. `amm_owner` calls `SetParams` with `param = AmmParams::Status`, `value = Some(2)` (i.e., `AmmStatus::Disabled`) — accepted because `AmmStatus::valid_status(2)` returns `true` ( [6](#0-5) ).
3. Any LP now calls `Withdraw` — `process_withdraw` checks `AmmStatus::from_u64(amm.status).withdraw_permission()` which is `false` for `Disabled`, so the call reverts with `AmmError::InvalidStatus` ( [8](#0-7) ).
4. No other unprivileged instruction can move funds out of the vaults on behalf of the LP; `WithdrawPnl` is owner-gated only. LP principal remains locked in the vaults indefinitely.
