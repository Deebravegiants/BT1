### Title
Users can set an order's input/output token to the internal `TRANSACTION_FEES` sentinel address to forge escrowed protocol fees and drain real fee-token balances - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` reserve a magic sentinel address, `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))`, as the dedicated key in the `_orders[commitment][token]` mapping used exclusively to track escrowed Hyperbridge relayer/protocol fees [1](#0-0) . Exactly like the `FALLBACK_ACTIONID` in the external report — a value derived from fixed constants and meant to be reached only through one internal code path — nothing in `placeOrder` prevents a user from directly supplying this same address as a normal `order.inputs[i].token` or `order.output.assets[i].token` value, letting them write into (and later drain) the fee-accounting slot outside of the intended `order.fees` flow.

### Finding Description
`placeOrder` escrows each input token by computing `token = address(uint160(uint256(order.inputs[i].token)))` and, after only checking for *duplicate* tokens, unconditionally sets `_orders[commitment][token] = reducedInputs[i].amount` [2](#0-1) . There is no check that `token != TRANSACTION_FEES`. Separately, real fee payments are escrowed into the very same map slot: `_orders[commitment][TRANSACTION_FEES] = order.fees;` [3](#0-2) .

Because `TRANSACTION_FEES` is a deterministic, non-deployed address (derived from `keccak256("txFees")`), a call such as `IERC20(TRANSACTION_FEES).safeTransferFrom(msg.sender, address(this), amount)` targets an account with no code. EVM `CALL`s to code-less accounts trivially succeed with empty returndata, and OpenZeppelin's `SafeERC20._callOptionalReturn` treats an empty, successful returndata as success. This means an attacker can declare an `order.inputs[]` entry with `token == TRANSACTION_FEES` and an arbitrary large `amount`, and the "transfer" step will silently no-op while the gateway still records `_orders[commitment][TRANSACTION_FEES] = amount` as if real fee tokens were escrowed — as long as `order.fees == 0` so the legitimate fee-escrow write at line 391 doesn't overwrite it.

When the order is later filled/finalized, `_withdraw` reads this forged balance and pays it out using the real, configured protocol fee token, not the sentinel address:
```
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
    ...
}
``` [4](#0-3) 

This transfers real `feeToken` balance — funded by other users' legitimate `order.fees` payments accumulated in the gateway contract — to an attacker-chosen `beneficiary`, without the attacker ever depositing anything of value. The same unguarded pattern (no check that `token != TRANSACTION_FEES`, sentinel reused as a fee-escrow key) exists in the Tron variant of the contract as well [5](#0-4) .

### Impact Explanation
This allows an unprivileged user to mint an arbitrary, unbacked balance in the fee-accounting slot and drain the IntentGatewayV2 contract's real fee-token holdings (accumulated from every user's legitimate `order.fees` payments) to any address they control, via a normal `placeOrder`/`fillOrder` call sequence — a direct theft of pooled relayer/protocol fee funds.

### Likelihood Explanation
The exploit requires only knowledge of the public, deterministic `TRANSACTION_FEES` constant and the ability to call `placeOrder`/`fillOrder`, both permissionless entry points reachable by any address (an unprivileged intent placer/solver). No governance, admin, or privileged role is needed.

### Recommendation
In `placeOrder` (both `evm/src/apps/IntentGatewayV2.sol` and the Tron variant), explicitly reject any `order.inputs[i].token` or `order.output.assets[i].token` that equals `TRANSACTION_FEES`, e.g. `if (token == TRANSACTION_FEES) revert InvalidInput();`, mirroring the recommended `if (target == address(1)) revert();` guard from the reference report. Apply the same check wherever token addresses are derived from user-supplied `bytes32` fields in `IntentsBase.sol`/`IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker calls `placeOrder` with:
   - `order.inputs = [{token: bytes32(uint256(uint160(TRANSACTION_FEES))), amount: 1_000_000e6}]`
   - `order.fees = 0`
   - `order.output` set to a cheap/self-fillable output with `beneficiary = attacker`.
2. `placeOrder`'s transfer step calls `IERC20(TRANSACTION_FEES).safeTransferFrom(...)`, which succeeds as a no-op since `TRANSACTION_FEES` has no code [6](#0-5) .
3. `_orders[commitment][TRANSACTION_FEES]` is now `1_000_000e6` despite no real tokens deposited [2](#0-1) .
4. Attacker (as solver) calls `fillOrder` to finalize the order; `_withdraw(..., finalize=true)` reads the forged `TRANSACTION_FEES` balance and pays out `1_000_000e6` units of the real `feeToken` to `beneficiary` (attacker) from the gateway's pooled fee balance [4](#0-3) .
