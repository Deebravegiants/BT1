### Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from unauthenticated HTTP headers, while the HMAC signature computed by `HmacValidator` only covers the raw request body. This breaks the identity binding `hmac-verified bytes == bytes acted upon`: the signature proves the body's integrity but not the header-derived shop/tenant identity that `Registry.process` hands to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read directly from HTTP headers and are never part of the signed content: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the metadata passed into the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms the HMAC over `verifiable_query.to_signable_string` (the body) using the app's single, shop-agnostic `Context.api_secret_key`: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that has the app installed, any valid `(raw_body, hmac)` pair legitimately delivered to one shop remains cryptographically valid for that same body when replayed with different `shop-domain`, `topic`, or `webhook-id` headers — none of which are covered by the signature. This is exactly the class of bug in the report: an equality the code implicitly relies on (`shop authenticated == shop acted upon`) does not actually hold, because the "authenticated" part (HMAC) and the "acted upon" part (header-derived `shop`) cover disjoint data.

### Impact Explanation
A merchant/attacker who has legitimately installed the app on their own shop receives real webhooks from Shopify, each with a valid HMAC for that body under the shared secret. They can capture such a webhook and resend it to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header rewritten to target another tenant. `HmacValidator.validate` still passes because it only checks the (unchanged) body against the secret. The app's handler then processes attacker-controlled data under a victim shop's identity — a cross-tenant integrity violation matching the Critical "cross-tenant access" category in the rules.

### Likelihood Explanation
Exploitation requires only that the attacker (a) run the target app on any shop (a normal condition for any merchant that installs a public app) to obtain a validly-signed webhook body, and (b) POST a crafted request to the app's public webhook endpoint with altered headers — no access token, `client_secret`, or privileged access is needed. The gem provides no protection against this because header fields are architecturally excluded from the signable content.

### Recommendation
Bind the tenant-identifying headers into the signed content, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified payload before they are trusted (e.g., verify the `shop` against a known/installed-shop allowlist retrieved via an authenticated channel, not solely from the header). At minimum, document to consumers of `ShopifyAPI::Webhooks::Registry.process` that `request.shop`/`request.topic`/`request.webhook_id` are not covered by HMAC integrity and must not be used for authorization decisions without additional verification.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture a legitimate webhook POST (raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`).
2. Resend the exact same body `B` and HMAC `H` to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim.myshopify.com` (and optionally alter `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes HMAC over the (unchanged) body `B` using the shared `Context.api_secret_key`; validation succeeds.
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., webhook_id: request.webhook_id)`, causing the app to process attacker-supplied data under the victim shop's tenant context.
