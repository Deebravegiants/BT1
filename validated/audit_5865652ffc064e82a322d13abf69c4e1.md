### Title
Cookie-derived session id trusted with no MAC/signature, enabling deterministic session-id forgery for offline and online sessions - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.current_session_id` returns the raw, attacker-controllable `shopify_app_session` cookie value as the trusted session id whenever a JWT is absent (non-embedded apps, or the embedded fallback path), with zero MAC, signature, or shop-binding check. Because session ids for both offline (`offline_#{shop}`) and online (`#{shop}_#{user_id}`) sessions are fully deterministic and derivable from public information (shop domain, small integer user ids), an attacker who knows/guesses a victim shop's domain or a staff member's numeric id can set that exact cookie value and have the host app's session store return another tenant's or another staff member's already-established session/access token.

### Finding Description
The binding that should hold is: **shop authenticated by signature/JWT == shop interpolated into the session id used to fetch a stored session**. Tracing the code:

- `current_session_id` (lines 19-37) only calls `session_id_from_shopify_id_token` (JWT-backed, MAC-protected via `Auth::JwtPayload`) when `Context.embedded?` is true **and** a `shopify_id_token` is present. In every other branch — non-embedded apps, or embedded apps that simply omit the JWT header — it falls straight to `cookie_session_id(cookies)` [1](#0-0) .
- `cookie_session_id` does nothing but `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` [2](#0-1) . There is no signature, no HMAC, no re-derivation from a trusted claim — the returned "session id" is exactly whatever bytes the caller placed in the `Cookie` header.
- The values this cookie is ever legitimately set to are fully deterministic: `offline_session_id(shop) = "offline_#{shop}"` and `jwt_session_id(shop, user_id) = "#{shop}_#{user_id}"` [3](#0-2) . Neither includes any random/opaque component, MAC, or expiry — they are simple string concatenations of public/guessable data (shop domain, small integer staff user id).
- `Auth::Oauth.validate_auth_callback` confirms this cookie is literally set to `session.id` for non-embedded apps after OAuth completes [4](#0-3) , i.e. the "secret" that must be presented later is identical to a value any party can compute offline once they know the shop domain (and, for online sessions, the numeric staff id).

None of the guards enumerated in the question (`HmacValidator.validate`, `ShopValidator.sanitize!`, OAuth `state` comparison, `JwtPayload`'s `aud`/`sub` checks, `HttpRequest#verify`, `Context.setup?`/`private?`/`embedded?`) execute anywhere on this cookie path — they only apply to the OAuth callback and to the JWT branch of `current_session_id`. The cookie branch is a bare hash lookup returned as an authenticated identity.

Attack: the attacker sends a normal HTTP request to the app with header `Cookie: shopify_app_session=offline_<victim>.myshopify.com` (or `shopify_app_session=<victim-shop>_<other-staff-id>` for cross-user access). `current_session_id` returns this string verbatim. If the host app's session storage (built on top of this gem, as documented) has a persisted session under that exact key — which it will, once the victim shop/staff member has ever completed OAuth — the app loads and uses that session's access token for the attacker's request, with no re-verification that the caller is actually associated with that shop or user.

### Impact Explanation
This breaks tenant and per-user isolation:
- Offline case: any party who knows a shop's `myshopify.com` domain (public/guessable) can obtain that shop's offline session/access token merely by presenting a synthetic cookie — full cross-tenant access using another merchant's access token, matching "Critical - cross-tenant access" / token theft.
- Online case: within one shop, if staff user ids are small sequential integers (common for Shopify staff), one user can enumerate `#{shop}_#{id}` and get served another staff member's online session — exactly the "Critical - cross-user access inside one shop" scenario in the question.
- Repeatable against arbitrary victims: the forgery cost is a single deterministic string per victim, reusable for as long as the underlying stored session remains valid.

### Likelihood Explanation
Preconditions: the host app must use the non-JWT / cookie-based session flow (true for all non-embedded apps, and for embedded apps' fallback branch, both officially supported configurations of this gem) and must persist sessions keyed by the ids this gem generates (the documented/expected usage). No attacker-held secret, token, or physical/social access is required — only knowledge of a shop domain (or a small integer staff id), both cheap to obtain or brute-force. This is fully within the attacker capabilities described in the rules (crafting arbitrary headers/cookies to their own requests).

### Recommendation
Do not use a bare deterministic string as a bearer session identifier. Either (a) make the cookie value itself an opaque, cryptographically random token that is separately mapped server-side to `offline_#{shop}` / `#{shop}_#{user_id}`, or (b) sign/MAC the cookie value (e.g., HMAC with `Context.api_secret_key`) and verify the MAC inside `cookie_session_id` before trusting it, rejecting any cookie whose signature doesn't match. Additionally, `current_session_id` should never accept a raw, unauthenticated cookie value that decodes to a shop different from the one implied by the request host without an accompanying MAC/JWT proof.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_session_id_accepts_forged_offline_id_with_no_verification
  ShopifyAPI::Context.setup(..., is_embedded: false)
  forged_cookie = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => "offline_victim-shop.myshopify.com" }

  returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, forged_cookie, false)

  assert_equal "offline_victim-shop.myshopify.com", returned_id
  # Demonstrates: no MAC/signature check, no shop binding to request host,
  # attacker-chosen string is trusted verbatim as the session lookup key.
end

def test_jwt_session_id_not_injective_for_underscore_shops
  id_a = ShopifyAPI::Utils::SessionUtils.jwt_session_id("shop_a.myshopify.com", "1_2")
  id_b = ShopifyAPI::Utils::SessionUtils.jwt_session_id("shop_a.myshopify.com_1", "2")
  assert_equal id_a, id_b # collision confirms lack of a structural/MAC-based binding
end
```
Combined with a host app's standard session-storage lookup (`SessionStorage#load_session(returned_id)`), this proves that presenting the forged cookie alone — with no JWT, no HMAC, no OAuth completion by the attacker — is sufficient for `SessionUtils.current_session_id` to hand back another party's session identifier for use in subsequent authenticated requests.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie

            end

          end
        end
