### Title
`onAccept` Paused Gate Can Permanently Block Delivery of Already-Burned Cross-Chain Transfers - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.onAccept` (and the analogous receive paths in `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable`) is gated by the `whenNotPaused` modifier. Tokens are burned on the source chain at `send()` time, and the corresponding mint on the destination chain only happens inside `onAccept`. If the destination token is paused when the relayer delivers the ISMP request, minting reverts, mirroring the reported bug class: a "disabled" flag blocking the completion side of a transfer whose funds have already left the source chain.

### Finding Description
`send()` burns the caller's tokens and dispatches an ISMP `PostRequest` carrying the transfer `Message` (from/to/amount/data) to the destination chain's `HyperFungibleToken` deployment: [1](#0-0) 

The corresponding mint happens only in `onAccept`, which is annotated `onlyHost whenNotPaused`: [2](#0-1) 

The owner can pause/unpause at will via `pause()`/`unpause()`: [3](#0-2) 

If the destination-side token contract is paused after a user's `send()` has already burned their tokens on the source chain but before the relayer delivers the resulting POST request, `onAccept` reverts due to `whenNotPaused`. This is exactly the reported bug pattern — using a single "enabled/paused" switch to gate both new outbound operations (which is reasonable) and the completion of an operation whose funds have already been irreversibly committed elsewhere (which strands the user). The relayer's delivery transaction reverts, so the ISMP request is not marked delivered; the user's funds are minted nowhere and are unusable until an unpause (which is entirely at the owner's discretion and could be withheld indefinitely, or could reasonably be needed for extended emergency response), and if the request's `timeoutTimestamp` passes while paused, the request can time out. On timeout, `onPostRequestTimeout` is the refund path — but it too is gated by `whenNotPaused`: [4](#0-3) 

This means the refund-on-timeout path can be blocked by the exact same pause switch that blocked the original delivery, leaving the user with tokens burned on the source chain, no mint on the destination, and no refund path — until the owner chooses to unpause. There is no way for the user or an unprivileged relayer to force the completion of an already-committed cross-chain transfer while the contract is paused.

The same pattern (`whenNotPaused` on both the completion mint and the timeout refund) is confirmed in the corresponding tests: [5](#0-4) 

### Impact Explanation
Funds already burned on the source chain can become temporarily or (if the owner never unpauses) effectively permanently frozen: neither the destination mint nor the timeout refund can execute while paused. This is a freezing-of-funds condition reachable from a single ordinary user transaction (`send()`), triggered by a legitimate emergency-pause action combined with normal relayer message delivery — no malicious actor is required, only ordinary operational timing (pause coincides with in-flight transfers). Given `HyperFungibleToken`/`WrappedHyperFungibleToken` are production bridge apps for arbitrary token transfers, this qualifies as a High-severity freezing-of-funds risk.

### Likelihood Explanation
This requires no attacker action to trigger, and is highly likely to occur in practice: any owner pausing the contract for maintenance/incident response while transfers are already in flight will strand those users' funds. The likelihood of the pause window overlapping with in-flight (already-burned) transfers scales directly with bridge usage volume and the duration of the pause.

### Recommendation
Do not gate the completion side of an already-committed cross-chain transfer (`onAccept`'s mint, and `onPostRequestTimeout`'s refund) behind the same `whenNotPaused` switch used for initiating new transfers. At minimum, `onPostRequestTimeout` (the refund path) should never be pausable, since it only returns funds already burned by the user. If `onAccept`'s mint must remain pausable for safety reasons (e.g., to stop minting during a compromise), consider queuing/crediting the entitlement so it can be claimed once unpaused, rather than reverting the ISMP delivery outright, and/or add a governance-independent time-boxed pause so funds cannot be frozen indefinitely.

### Proof of Concept
1. User calls `HyperFungibleToken.send(...)` on chain A with `amount = X`; `X` tokens are burned from the user and an ISMP `PostRequest` is dispatched to chain B's `HyperFungibleToken`. [1](#0-0) 
2. Before the relayer delivers the request, the owner of chain B's token calls `pause()`. [6](#0-5) 
3. Relayer delivers the request; `onAccept` reverts because of `whenNotPaused`, so `X` tokens are never minted to the beneficiary on chain B (confirmed by `testOnAcceptRevertsWhenPaused`). [5](#0-4) 
4. If the request's timeout elapses while still paused, `onPostRequestTimeout` — the only refund mechanism — also reverts due to the same `whenNotPaused` modifier, leaving the user's `X` tokens burned with no completion and no refund possible until the owner unpauses. [7](#0-6)

```text
    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
```

```text
    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
```
