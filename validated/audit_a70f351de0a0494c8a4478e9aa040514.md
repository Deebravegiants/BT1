## Title
Reputation minting in `pallet-messaging-incentives` is attributed via a self-signed, front-runnable `signer` field rather than the account that actually delivered the message - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
This is the same bug class as the reported `AccessTokenContract` issue: the contract grants an unauthenticated caller extra benefit (`winChance`) by trusting a caller-supplied identifier (`passportId`) that is public and not bound to who actually performed the qualifying action. In `pallet-messaging-incentives`, the reward-eligible identity (`relayer`) is derived purely from a self-attested signature over public, deterministic message content (`msg.requests`), not from who actually submitted/paid for the consensus proof that got the message executed. Anyone who can read a pending relay transaction can re-sign the same public payload with their own key and front-run it, redirecting the mint to themselves.

### Finding Description
`Pallet::relayer_for` recovers the "relayer" credited with a delivery purely from a signature the message carries in its own `signer` field, over `keccak_256(&msg.requests.encode())`: [1](#0-0) 

Note the crucial detail: `msg.requests` (the `PostRequest`/`Response` payload) is fully public — it appears in the calldata of `pallet_ismp::handle`/`handle_unsigned` submissions before they are included in a block, and the same payload plus its state/consensus proof can be resubmitted by *anyone*, because the signature check binds the signer only to the deterministic, attacker-computable request bytes rather than to any information unique to the entity that actually produced/paid for the delivery (the submitting extrinsic's `origin`, a nonce, or a binding to the proof submitter).

Concretely, this mirrors the report's exact defect shape:
- `paidMint`/`referralMint` both mint, but the caller freely chooses the more generous path and can supply an arbitrary, publicly-known `passportId` because nothing binds that identifier to the caller's real relationship to it.
- Here, `on_executed` mints `ReputationAsset` to whichever account's signature is attached to `msg.signer`, and nothing binds that signature to `msg.sender`/the account that paid the gas and produced the consensus/state proof required for `pallet-ismp` to accept the message in the first place (see `FeeHandler::on_executed` invoked by `pallet-ismp` after message processing): [2](#0-1) 

Because `msg.requests` is identical regardless of who submits it, an attacker observing a legitimate relayer's pending `handle`/`handle_unsigned` transaction in the mempool can:
1. Copy the proof and `requests` verbatim (both public in the pending transaction).
2. Recompute `keccak_256(&msg.requests.encode())` (deterministic, no secret needed).
3. Sign it with their own sr25519 key, replacing `msg.signer`.
4. Resubmit with higher priority/fee so it lands first.

The proof still verifies (it is unmodified and does not depend on the submitter's identity), `pallet-ismp` still processes the request, and `on_executed` mints the full per-byte reputation reward to the attacker's account instead of the relayer who actually did the delivery work.

### Impact Explanation
`ReputationAsset` is soulbound and used for collator/session ranking (per the pallet's own documentation and tests, it's burned each session by `pallet-collator-manager` to reset accumulated rewards). An attacker who can cheaply front-run relayer deliveries can systematically redirect this reward stream to themselves, unfairly inflating their own collator ranking/reputation while starving the legitimate relayers who bear the actual cost and risk of delivering messages. This is an "unbacked mint" attributed to the wrong party — value is minted based on an unauthenticated, spoofable attribution rather than on verified performance of the work being rewarded, which directly undermines the incentive and governance-adjacent ranking mechanism the pallet exists to secure.

### Likelihood Explanation
This requires no privileged access: any account able to submit an unsigned/normal ISMP message extrinsic (the same one relayers use) can execute the front-run. It only needs mempool visibility of a pending relay transaction and a modest gas/priority bid, both of which are trivial for any active participant (including relayers themselves who would have every incentive to game each other, or any other watching bot). The `MintPerByte` rate must be non-zero (governance-controlled) for the incentive to be live, but once enabled the exploit path requires no special timing beyond ordinary mempool front-running.

### Recommendation
Bind reward attribution to something the submitter cannot forge independently of doing the actual work, e.g.:
- Attribute the mint to the extrinsic's signed `origin` (the account that paid for and submitted the `handle`/`handle_unsigned` call) rather than to a self-declared `signer` field inside the message payload, or
- If the self-attested signature model must be kept, bind the signed payload to something unique per submission attempt (e.g. include the submitting account, a nonce, or the block/extrinsic index) so a copied signature cannot be replayed/front-run by a different submitter over the same public request bytes.

### Proof of Concept
1. Legitimate relayer `R` submits `pallet_ismp::handle` (or `handle_unsigned`) with a `RequestMessage { requests, proof, signer: Signature::Sr25519 { public_key: R_pub, signature: sign_R(keccak256(requests.encode())) } }`.
2. Attacker `A` observes this transaction in the mempool before inclusion. `requests` and `proof` are plaintext/public.
3. `A` computes `digest = keccak256(requests.encode())` (identical computation `relayer_for` performs) and signs it with their own key: `sig_A = sign_A(digest)`.
4. `A` constructs an equivalent `handle` call with the same `requests`/`proof` but `signer = Signature::Sr25519 { public_key: A_pub, signature: sig_A }`, and submits it with a higher tip/priority so it is included first.
5. `pallet-ismp` processes the message (the proof is valid and unmodified), calls `FeeHandler::on_executed`, `relayer_for` recovers `A` from the forged-but-validly-signed `signer` field, and `ReputationAsset::mint_into(&A, amount)` credits the attacker instead of `R`, as shown by the mint logic in `on_executed`. 	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}

impl<T: Config> FeeHandler for Pallet<T>
where
	T::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
}
