This confirms the root cause. The webhook HMAC (`Utils::HmacValidator.validate`) only signs `request.to_signable_string`, which returns `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all read from HTTP headers that are never included in the signed bytes [2](#0-1) . `Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` taken straight from those unsigned headers to build `WebhookMetadata`, which is handed to the host app's handler as the tenant identity for the event [3](#0-2) .

### Title
Webhook tenant identity (`shop`, `topic`) is not bound to the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read from unauthenticated HTTP headers. `Registry.process` validates the body HMAC but then dispatches the handler using these unsigned header values as the tenant/topic identity, breaking the binding `hmac_verified_bytes == bytes_the_app_acts_on`.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` [4](#0-3) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) which are not part of the HMAC-covered bytes at all [2](#0-1) .

`Registry.process` raises only if the body HMAC is invalid, then immediately trusts `request.shop` and `request.topic` (header-derived) to build the `WebhookMetadata` passed to the app-defined handler [3](#0-2) . Because an attacker fully controls all HTTP headers of a request they send to the app's webhook endpoint, they can take a webhook body+HMAC pair genuinely issued by Shopify for their own shop (which they legitimately receive, since it's their own store) and re-POST it to the app's webhook callback URL with the `shopify-shop-domain` header changed to a victim shop's domain. Since the HMAC never covers the shop header, `Utils::HmacValidator.validate(request)` still succeeds, and the forged `shop` value flows straight into `WebhookMetadata.shop` that the host application uses as the tenant key (as shown in the documented handler pattern of using `data.shop` to look up/store per-shop data) [5](#0-4) .

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: `verified(bytes) == raw_body`, but `acted_on(shop) == header value`, and `raw_body ⊉ header`.

### Impact Explanation
This allows cross-tenant data confusion/injection: an attacker who controls one legitimate Shopify shop (or who has captured any one genuine webhook body/HMAC pair for a registered topic) can make the app process attacker-supplied body content under an arbitrary victim shop's identity, since the shop attribution is not cryptographically bound. Depending on how the host app uses `data.shop` (e.g., writing order/product data, matching webhook idempotency keys, or looking up the shop's session/access token), this can lead to cross-tenant data corruption in the app's own database — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair, which they trivially can from webhooks delivered to their own store, or any topic body whose exact bytes they can predict/replay (e.g., an app-uninstalled webhook, or any webhook where they control content in their own shop). No secret key or credentials are required — only network access to the app's public webhook endpoint and control over standard HTTP headers on the forged request.

### Recommendation
Include the identity-critical fields (`shop`, `topic`, `api_version`, `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the request (e.g., verify them against Shopify's TLS-terminated request metadata rather than trusting client-supplied headers), so that `to_signable_string` cannot be satisfied by mixing a valid body/HMAC pair with attacker-chosen header values.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and has app installed; app registers webhook for e.g. `orders/create`.
2. Shopify sends attacker a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact body `B` and HMAC `H` to the app's webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop == "victim-shop.myshopify.com"`, `hmac == H`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (`B`) only — passes, since headers are irrelevant to the signature.
6. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` is handed to the app's handler, which now processes attacker-controlled data attributed to the victim shop.
