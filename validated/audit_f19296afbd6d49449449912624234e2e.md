### Title
Reentrancy in `IntentGatewayV2.withdraw` on Tron via unguarded external calls before escrow debit - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.withdraw` transfers escrowed native/ERC20 tokens to an attacker-controlled `beneficiary` *before* decrementing the `_orders[commitment][token]` escrow accounting for that token, violating the checks-effects-interactions pattern that the mainline EVM implementation (`IntentsBase._withdraw`) already follows correctly.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function, reachable from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` requests) and `onGetResponse()` (for source-chain cancellations), performs the token/native payout via low-level `.call` before updating the escrow ledger: [1](#0-0) 

Specifically, for each token in the withdrawal body, the contract calls `beneficiary.call{value: amount}("")` for native token or `token.call(...transfer...)` for ERC20, and only *afterward* executes `_orders[body.commitment][token] -= amount;`. The equality check guarding re-entry, `if (_orders[body.commitment][token] == 0) revert UnknownOrder();`, is a non-zero check rather than a debit-then-check pattern, so it does not prevent a second withdrawal attempt from succeeding while the balance has not yet been zeroed out.

By contrast, the mainline EVM `IntentsBase._withdraw` used by `evm/src/apps/IntentGatewayV2.sol` correctly decrements `_orders` before the external transfer: [2](#0-1) 

This confirms the Tron contract is a regression of the CEI fix already applied elsewhere in the codebase — an analog of the reported `netAtPrice` bug class (state-changing token transfer performed before storage is updated).

### Impact Explanation
If `beneficiary` is a malicious contract (attacker sets the order's beneficiary/`to` address), the native-token `.call{value: amount}("")` or the ERC20 `transfer` (if the token has transfer hooks/callbacks) hands control to attacker code while `_orders[commitment][token]` for that entry is still non-zero. If a re-entrant path exists that reaches `withdraw()` again with the same commitment/token before the first call's debit executes, escrowed funds for that order could be paid out more than once, resulting in direct theft of tokens held in the Intent Gateway's escrow.

### Likelihood Explanation
I was unable to confirm on the Tron side whether the equivalent host/dispatcher marks a request/response "receipt" *before* invoking `onAccept`/`onGetResponse` the way `EvmHost.dispatchIncoming` does on the standard EVM path (`_requestReceipts[commitment] = relayer;` set prior to the app callback, at `evm/src/core/EvmHost.sol` lines 806-810), which is the mechanism that blocks a naive re-delivery based reentry into `withdraw()`. I could not locate a Tron-specific host contract (`dispatchIncoming` or equivalent) in this index to verify the same replay-guard ordering is present there; if the Tron host lacks this guard, or if any other externally reachable function on this contract reads/mutates `_orders[commitment][token]` without an equivalent guard, the reentrancy is directly exploitable within a single external call. Given this gap in verification, I flag the likelihood as **uncertain but plausible** — the vulnerable code pattern is concretely present and reachable from `onlyHost`-gated but attacker-influenced entry points (attacker controls `beneficiary`), but full exploitability depends on Tron-host replay-protection details not available in the indexed code.

### Recommendation
Apply the same CEI ordering used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` (and delete `TRANSACTION_FEES` entries) *before* performing the native/ERC20 transfer in the Tron `IntentGatewayV2.withdraw()` function. Additionally, add an explicit reentrancy guard (`nonReentrant`) on `onAccept`/`onGetResponse` in the Tron contract as defense-in-depth, and confirm the Tron host records request/response receipts prior to invoking the app callback, mirroring `EvmHost.dispatchIncoming`.

### Proof of Concept
Not fully constructible from the indexed code: a complete PoC requires the Tron host's dispatch/replay-protection contract (analogous to `EvmHost.dispatchIncoming`/`HandlerV2.handlePostRequests`), which was not found in the index for the `tron/` tree. The vulnerable ordering itself is directly demonstrated by inspection at `evm/tron/contracts/apps/IntentGatewayV2.sol:702-710`, where the external call precedes the storage debit; a concrete exploit would require a Devin session with full repo access to locate/inspect the Tron host contracts and confirm whether a reentrant call path into `withdraw()` (or another function reading `_orders`) is reachable before the debit completes.
