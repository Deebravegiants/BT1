### Title
Legacy user-QR-code format binds a signup to an arbitrary, unverified user_id - ([File: src/plans/qr_scan/user.rs], [File: src/plans/mod.rs])

### Summary
The WatchPug finding shows `mintFungible()`/`mintSynth()` acting on a caller-supplied `from`/`to` address without verifying the caller is authorized to use that identity. The orb-core analog is the legacy "QR_CODE_V2" user-QR parsing path, which accepts a bare `userid:<uuid>:<data_policy>` string and uses that UUID as the enrolled `user_id` for the entire signup/PCP-upload pipeline without any cryptographic proof that the QR presenter owns that `user_id`.

### Finding Description
`Data::try_parse` in [1](#0-0)  first tries `decode_qr(code)`, which yields a `user_data_hash` used later for cryptographic verification. If that fails, it falls back to the `QR_CODE_V2` regex format, producing a `Data { user_id, user_data_hash: None, .. }` with **no hash and no signature** [2](#0-1) .

Downstream, `backend::user_status::request` branches on whether `backend_keys`/`authenticated_app_data` are present. When they are, and only in that branch, is `user_data.verify(user_data_hash)` cryptographically checked against `qr_code.user_data_hash` [3](#0-2) . But for the legacy/old QR format (`else` branch), the code explicitly takes the path "Using an old QR-code format" and, provided `qr_code.user_data_hash` is `None` (which it always is for `QR_CODE_V2`), it returns `Ok(Some(UserData { .. self_custody_user_public_key: None, id_commitment: None .. }))` **without any signature/hash verification at all** [4](#0-3) . The raw `user_id` string scanned from the QR code is carried forward unauthenticated.

That unauthenticated `user_id` is then used as the enrollment identity for the entire signup: it's sent in `signup_post::request` as `userId` [5](#0-4)  and used directly as the `user_id` field when uploading the Personal Custody Package (biometric data) via `upload_personal_custody_package::request` [6](#0-5)  and in `data_uploader::Agent::upload_pcp` [7](#0-6) .

The only guard applied to the scanned user QR-code before proceeding is a check that it differs from the operator's own QR code [8](#0-7)  — there is no proof-of-possession/ownership check comparable to Solidity's `msg.sender` gate. Anyone who can produce a string matching `userid:<uuid>:<data_policy>` (trivial, no signing key needed) can present it as their own QR code and complete a full biometric signup that gets bound to that arbitrary UUID.

### Impact Explanation
This mirrors the "steal wallet balance via arbitrary `to`" impact class: an attacker with no privileged access (just physical presence at an orb, an unprivileged normal user) can complete a full biometric signup (iris/face capture + PCP upload) while asserting an arbitrary victim's `user_id`, causing biometric data to be misattributed/bound to a `user_id` the attacker does not own. This is a concrete "unauthorized/misattributed signup" and "cross-signup state bleed" impact matching the required validation categories — the attacker's biometric package is uploaded and tagged under a `user_id` string they merely typed/printed into a QR code, not one they cryptographically own.

### Likelihood Explanation
Likelihood is high for any deployment that still accepts the legacy `QR_CODE_V2` format: no cryptographic material, backend key, or signature is required — only knowledge of the target's UUID (which may itself be guessable/leaked) and the ability to render a QR code with that string. The vulnerable code path is production logic (not gated behind a test-only feature such as `skip-user-qr-validation`); it is reached whenever the modern `decode_qr` hashed format fails to parse and the legacy regex format matches.

### Recommendation
Deprecate/reject the legacy `QR_CODE_V2` path in production builds, or require that every accepted user QR-code carry a `user_data_hash`/signature that is verified against backend-issued `authenticated_app_data` before proceeding with signup — i.e., make the check at [9](#0-8)  fail closed (reject) rather than fall back to an unauthenticated `UserData` whenever `user_data_hash` is absent. Ensure `user_id` used for PCP/biometric upload is always sourced from a verified identity binding, never directly from unauthenticated QR text.

### Proof of Concept
1. Attacker generates a QR code encoding the plain-text string `userid:<victim-uuid>:<data_policy>` (matching `QR_CODE_V2` regex, no crypto material needed) [10](#0-9) .
2. Attacker presents this QR code to the orb during a normal signup flow (unprivileged user role). `Data::try_parse` fails `decode_qr` (no valid hashed payload) and falls through to the `QR_CODE_V2` match, producing `Data { user_id: <victim-uuid>, user_data_hash: None, .. }` [1](#0-0) .
3. `backend::user_status::request` takes the "old QR-code format" branch (since `user_data_hash` is `None`) and returns `UserData` without performing any signature check [4](#0-3) .
4. The orb proceeds through biometric capture and calls `upload_personal_custody_package::request(signup_id, &<victim-uuid>, ...)`, uploading the attacker's own iris/face biometric package tagged with the victim's UUID [6](#0-5) .

Note: I was unable to fully inspect `Plan::verify_user_qr_code`'s complete body (only its call site was found within available context) and the `orb_qr_link::UserData::verify` implementation, since these are outside what my search tools surfaced fully; confirming whether any additional non-cryptographic backend-side gate exists for the legacy path would require reviewing `orb_qr_link` crate internals and the full body of `verify_user_qr_code` directly.
