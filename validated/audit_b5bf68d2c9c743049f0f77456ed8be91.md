Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the body HMAC and then dispatches `request.shop` straight into the handler's `WebhookMetadata` [3](#0-2) .

### Title
Webhook shop-domain identity spoofing via unauthenticated header field not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC-SHA256, but the `shop` (tenant identity) is taken from a header that is never part of the signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value to attribute webhook data to a tenant, breaking the binding `HMAC-covered bytes == data acted upon`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` field of the same object [4](#0-3) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#hmac` reads the `hmac-sha256` header [5](#0-4) . The `shop` accessor, however, is populated purely from the `shop-domain` header, which is not included in `to_signable_string` and therefore not covered by the HMAC at all [2](#0-1) .

`Registry.process` validates only that the body HMAC matches (`Utils::HmacValidator.validate(request)`), then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.parsed_body`, and calls the app's handler with it [3](#0-2) . Because `shop` is never part of the signed bytes, any HTTP client that possesses one valid `(raw_body, hmac)` pair — which it legitimately receives whenever it operates its own installed shop, since Shopify sends real webhook deliveries to the app's public endpoint for that shop — can resend the exact same body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a different (victim) shop. The signature still validates because the header is outside the signed scope, so the equality the app relies on — "the shop this data is attributed to" == "the shop that actually produced this signed body" — is broken. The handler then processes attacker-supplied body content as if it were data belonging to the victim shop identified only by the spoofed header.

This matches the reported bug class exactly: a field (the tenant/shop identity) that is acted upon by downstream logic but not covered by the authentication mechanism (HMAC) that is supposed to bind the message to its sender.

### Impact Explanation
Any app built on this gem that keys per-shop state, dispatches per-shop side effects, or trusts `WebhookMetadata#shop` for authorization/business-logic decisions inside its webhook handler can be tricked into cross-tenant data confusion: an unprivileged holder of one valid webhook delivery for their own store can make the app believe that data belongs to a different merchant's store. This is a cross-tenant access issue reachable by any internet user who has installed the app on their own shop (no `api_secret_key`, access token, or other privileged credential is required — they only replay a signature that Shopify itself already computed and delivered to them for their own shop).

### Likelihood Explanation
Exploitation requires only capturing one legitimate webhook delivery (trivial for a merchant who installs the app on their own store) and resending it to the app's public webhook endpoint with a different `shop-domain` header. No secret material needs to be derived or brute-forced; the signature simply doesn't cover the field being spoofed, so likelihood is high for any app that trusts `request.shop`/`WebhookMetadata#shop` for tenant-sensitive logic.

### Recommendation
Include the tenant-identifying value (shop domain) in the signed payload used for HMAC verification, or otherwise cryptographically bind `shop` to the signed body (e.g., require verification that the `shop-domain` header matches a shop value embedded in the signed body/payload, or maintain a mapping validated independently of client-supplied headers). At minimum, document that `request.shop` is unauthenticated and must not be trusted for authorization decisions without independent verification (e.g., cross-checking against the shop associated with the resource IDs in the verified body).

### Proof of Concept
1. App installs webhook endpoint and receives a legitimate Shopify webhook for `shop-a.myshopify.com`: headers include `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `raw_body`.
2. Attacker (who owns/operates `shop-a`) captures this `(raw_body, hmac)` pair.
3. Attacker POSTs the same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop the attacker does not own).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC is computed only over `raw_body` [1](#0-0) .
5. `WebhookMetadata` is built with `shop: request.shop` == `"shop-b.myshopify.com"` and the attacker-originated body [6](#0-5) , and the app's handler runs believing this data is authentic for `shop-b`.

          received_signature = verifiable_query.hmac
