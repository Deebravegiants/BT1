### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` binds *only* the body bytes to the app's `client_secret`. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never included in the signed material, yet they are trusted downstream to attribute the event to a specific merchant (`data.shop` in `WebhookMetadata`).

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` exclusively, while `shop` (`Request#shop`, line 21-23) is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that header's value.

`Registry.process` validates only this body-derived HMAC before dispatching to the app's handler with the header-derived `shop`: [2](#0-1) 

The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_tenant_identity`. Here, `hmac_signed_bytes` (the raw body only) `!= bytes_that_determine_tenant_identity` (body **and** the `shop-domain` header), so the two are not equal — the HMAC "proves" the body came from Shopify using the app's secret, but proves nothing about which shop the header claims to be from.

### Impact Explanation
Because the webhook endpoint is a public HTTP route exposing no authentication other than this HMAC check, any request bearing a *valid body+HMAC pair* is accepted regardless of the `shop-domain` header. A merchant who has installed the app on their own store can capture one legitimate webhook delivery (body + HMAC) sent by Shopify to the app's webhook endpoint, then replay that exact body/HMAC pair while substituting a different, victim shop's domain in the `shopify-shop-domain` header. `Registry.process` will accept it (HMAC only checks body integrity/authenticity, not the header) and invoke the app's `WebhookHandler#handle` with `WebhookMetadata.shop` set to the victim's domain. Any app logic that trusts `data.shop` for authorization, data attribution, or state mutation (e.g., updating settings, deleting data, or triggering the `shop/redact`/`customers/redact` mandatory topics for the wrong tenant) is exposed to cross-tenant data corruption or disclosure — a Critical-impact cross-tenant access issue.

### Likelihood Explanation
Likelihood requires an attacker to already be an installed merchant (able to legitimately receive one webhook from their own shop) and to be able to intercept/replay their own request to the public webhook endpoint with a modified header — no secrets, tokens, or privileged access to the target shop are needed. This is squarely within the "unprivileged internet user" analog class defined by the report: a field (`shop`) acted upon by the handler that is not covered by the HMAC.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-covered signable string, or, at minimum, have `Registry.process`/`WebhookHandler` implementations cross-check the header-derived `shop` against an independently trusted source (e.g., the shop associated with the session/subscription that registered the webhook) before dispatching to the handler. Document clearly that consumers must not trust `WebhookMetadata.shop` without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers an event on their own shop; Shopify POSTs to the app's webhook endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over body B>`, body `B`.
3. Attacker captures this request (they control the network path to their own endpoint/proxy).
4. Attacker resends the identical body `B` and HMAC header, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac` still decodes the same signature, `HmacValidator.validate` recomputes HMAC over `B` and it matches (body untouched), so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though Shopify never sent anything about `victim-shop`.
