### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then dispatches to the per-topic handler using the `shop`, `topic`, and `webhook_id` values taken directly from HTTP headers, none of which are included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body of the request: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`, i.e. the body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` uses this same HMAC check as the sole authentication gate, then reads `request.topic` to select the handler and forwards `request.shop` and `request.webhook_id` — both taken straight from headers — into the handler as trusted tenant/context data: [3](#0-2) 

The `shop`, `topic`, and `webhook_id` accessors simply read attacker-controllable headers with no cryptographic binding to the body they were paired with: [4](#0-3) 

This breaks the intended identity binding: `HMAC(body)` should authenticate `(shop, topic, webhook_id, body)` as one unit, but it only authenticates `body`. Because the same `api_secret_key` is shared across every shop that installs the app, anyone who can install the app on their own store (an unprivileged action) receives genuinely-signed webhook deliveries — i.e., real `(body, hmac)` pairs computed with the app's shared secret. That same person can then replay the exact `body`+`hmac` to the app's webhook endpoint while freely substituting the `shop-domain`, `topic`, and `webhook-id` headers, since none of them affect HMAC validity. The app's registered handler will treat the forged headers as authentic, believing the payload originated from and pertains to a different, victim shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker who legitimately installs the app on a store they control can forge webhook deliveries that the app attributes to another tenant (arbitrary `shop` value) and/or an arbitrary topic. Depending on how the host application's webhook handlers use `shop`/`topic` (e.g., updating per-shop state, triggering `app/uninstalled` cleanup, fulfilling GDPR `customers/redact` requests, or writing data keyed by `shop`), this enables cross-tenant data corruption or state manipulation without ever needing the target's credentials — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is moderate-to-high for any app author using this gem's webhook processing as documented: the attack requires no secret leakage or privileged access — only the ability to install the app on an attacker-owned test/dev store to obtain a validly signed `(body, hmac)` pair (a normal, unprivileged usage flow), followed by a single forged HTTP POST to the target app's webhook endpoint with substituted headers.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` into the signed content (or otherwise cryptographically tie them to the HMAC), for example by including them in `to_signable_string`, or by requiring the caller to independently confirm the `shop` value against a known, previously-established session/tenant record before dispatching to handlers. At minimum, document that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must not be trusted for tenant attribution without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (`attacker.myshopify.com`), a normal unprivileged action.
2. Shopify delivers a genuine webhook to the app, e.g. `orders/create` with `x-shopify-shop-domain: attacker.myshopify.com`, body `B`, and `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures `B` and the HMAC value, then sends a new POST to the app's webhook endpoint with the same body `B` and same HMAC header, but headers changed to `x-shopify-shop-domain: victim.myshopify.com` and/or `x-shopify-topic: app/uninstalled`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B)` against the (unmodified) body.
5. The handler executes using `shop: "victim.myshopify.com"` and/or the spoofed topic, causing the app to act on the wrong tenant's data.
