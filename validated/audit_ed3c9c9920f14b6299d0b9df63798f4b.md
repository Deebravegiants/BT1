Audit Report

## Title
Password change fails to revoke active API tokens, allowing continued unprivileged access after credential rotation - (File: `core/web/user_controller.go`)

## Summary
When a user changes their own password via `PATCH /v2/user/password` (`UserController.updateUserPassword`) or the `updateUserPassword` GraphQL mutation (`Resolver.UpdateUserPassword`), the server clears other browser session cookies but never revokes the user's existing API token (`token_key`/`token_secret`). Any API token issued before the password change continues to authenticate indefinitely.

## Finding Description
`UserController.updateUserPassword` calls `orm.ClearNonCurrentSessions(ctx, sessionID)` followed by `orm.SetPassword(ctx, user, newPassword)`. [1](#0-0)  `ClearNonCurrentSessions` only deletes rows from the `sessions` table scoped by session cookie. [2](#0-1)  `SetPassword` only updates the `hashed_password` column and never touches `token_key`/`token_secret`, nor invokes `DeleteAuthToken`. [3](#0-2)  The GraphQL path `Resolver.UpdateUserPassword` exhibits the identical pattern, calling only `ClearNonCurrentSessions` and `SetPassword`. [4](#0-3)  `FindUserByAPIToken`, used by `AuthenticateByToken`, is a pure lookup on `token_key` independent of password state. [5](#0-4) [6](#0-5)  The `AuthenticationProvider` interface itself defines `SetAuthToken`, `CreateAndSetAuthToken`, `DeleteAuthToken`, and `SetPassword` as entirely independent operations with no cross-invocation in the local ORM implementation. [7](#0-6)  `DeleteAuthToken` is only invoked from the dedicated `DeleteAPIToken` handler. [8](#0-7) 

## Impact Explanation
If an attacker has obtained a valid API token for a user (through prior leak, phishing, or a formerly-authorized shared device), that token continues to grant full role-scoped access (job management, bridge creation, key operations, etc.) even after the legitimate user explicitly rotates their password as a remediation step. This defeats the security purpose of a password-change/remediation action and falls under the node API authentication/role-bypass impact category, since a credential-invalidation action fails to invalidate a co-existing, fully-privileged authentication surface for the same account.

## Likelihood Explanation
Exploitation requires the attacker to already hold a previously-issued valid API token for the victim account — this is not a self-contained escalation from zero access, but it is the exact scenario a password-change is meant to remediate. Given that many operators treat "change password" as sufficient incident response, and the API token remains silently valid indefinitely with no expiry tied to password state, the residual-access window is unbounded, making this concretely reproducible and repeatable via standard authenticated `PATCH /v2/user/password` or GraphQL `updateUserPassword` calls, with no admin/host access required.

## Recommendation
In both `UserController.updateUserPassword` and `Resolver.UpdateUserPassword`, invoke `orm.DeleteAuthToken(ctx, user)` (mirroring the existing call in `DeleteAPIToken`) whenever the password is changed, forcing re-issuance via `CreateAndSetAuthToken` if an API token is still needed.

## Proof of Concept
1. As authenticated user `alice`, call `POST /v2/user/tokens` to create an API token (`CreateAndSetAuthToken`).
2. Confirm the token authenticates successfully against an `AuthenticateByToken`-protected endpoint (e.g., `GET /v2/bridge_types`).
3. As `alice`, call `PATCH /v2/user/password` with a new password.
4. Re-issue the original API token from step 1 against `GET /v2/bridge_types` — the request still succeeds, proving the pre-rotation token remains valid after the password change.

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
