### Title
Webhook shop-domain and topic headers are trusted as tenant identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are taken from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's `WebhookHandler` as the trusted tenant identifier. This breaks the intended identity binding: `HMAC(secret, signed_bytes) == HMAC(secret, raw_body)` while `data.shop == header["shop-domain"]` is never included in `signed_bytes`. Anyone able to replay a genuine, validly-signed webhook body for their own shop can relabel it as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads `shopify-hmac-sha256`/`x-shopify-hmac-sha256`: [1](#0-0) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — again, only the body bytes are covered: [2](#0-1) 

`Registry.process` only checks that HMAC validation passes, then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc. — fields that were never part of the signed material: [3](#0-2) 

`WebhookMetadata#shop` is a plain, unauthenticated `String` that the handler is expected to trust as the tenant/shop the event belongs to: [4](#0-3) 

This is exactly the identity-binding gap called out in the analog rule set: "a field acted on but not covered by the HMAC." The equality that should hold is:

`authenticated_bytes == bytes_that_determine_shop_identity`

but instead:

`authenticated_bytes = raw_body` while `shop_identity_used_by_handler = header["shop-domain"]` (or `header["x-shopify-shop-domain"]`), which is disjoint from `authenticated_bytes`.

### Impact Explanation
Any entity that can obtain one genuine, validly HMAC-signed webhook delivery from the app's own secret (e.g., an unprivileged merchant who has installed the target app on their own store, or anyone who can capture/replay a real webhook POST since the endpoint is a plain public HTTP endpoint) can resend that exact body with the `shop-domain` header rewritten to any other shop the app serves. Because the signature never covered the header, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Any app logic that uses `data.shop` to select which tenant's database row/session/customer record to update, delete, or overwrite (a normal and expected usage pattern per the gem's own webhook documentation) is now attacker-controlled, producing cross-tenant data corruption/exfiltration attributable to a shop the attacker does not control. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that has at least one merchant install (which is required for any real production app): that merchant already receives genuinely-signed webhooks and can freely replay them with modified headers to the same public endpoint, since HMAC validation is the only authentication mechanism and it does not cover the headers. No access token, `api_secret_key`, or privileged credential is needed — only ownership of a shop that has installed the app, which is the normal "unprivileged internet user" scenario for merchant apps.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically bind headers to the body:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (e.g., canonicalize header+body into one string) so any header tampering invalidates the HMAC, or
- Cross-validate `shop` against an independently authenticated source (e.g., look up the expected shop domain from the resolved session/webhook subscription registered with Shopify, not from the request header) before trusting `data.shop`.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key without additional verification, and provide the header-binding fix above as the default-safe behavior.

### Proof of Concept
1. App `X` uses `ShopifyAPI::Webhooks::Registry` to register an `http` webhook handler that uses `data.shop` to update per-tenant state (matching the documented usage pattern in `docs/usage/webhooks.md`).
2. Attacker owns shop `attacker.myshopify.com`, which has installed app `X`. Shopify delivers a genuine webhook to the app's public endpoint with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body with app's api_secret_key>`
   - body: `{}` (or any attacker-influenced body, e.g., an `orders/create` payload for an order the attacker created in their own store)
3. Attacker intercepts/replays this exact POST to the same public endpoint but rewrites only the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - keeps the same raw body and the same (still-valid) `x-shopify-hmac-sha256` value, since the signature was computed over the body only.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and still matches — the tampered header is never checked.
5. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and performs its tenant-scoped action against `victim.myshopify.com`'s data using attacker-supplied body content.
