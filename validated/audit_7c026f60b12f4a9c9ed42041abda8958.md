### Title
Webhook shop-domain identity spoofing due to HMAC only covering the raw body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then trusts a separate, unauthenticated `shop-domain` header to attribute the event to a tenant. Because the app's HMAC secret (`api_secret_key`) is shared across all shops that install the app, any shop that can trigger a legitimately-signed webhook for itself can replay that same valid body+HMAC pair while substituting a different shop's domain in the `shop-domain` header, and the library will process it as if it came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) accessors are read straight from HTTP headers, entirely outside the HMAC's signed data: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then constructs `WebhookMetadata` — the object handed to the app's business logic — using the unauthenticated `request.shop` value: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the signature purely from `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`: [4](#0-3) 

The binding that is broken is: `hmac_valid(body, api_secret_key) == true` is treated as proof that `shop_header == originating_shop`, but the two are independent facts. `api_secret_key` is one shared secret per app (not per shop), so any shop that legitimately installed the app can obtain a valid `(body, hmac)` pair for itself (e.g. by triggering an `orders/create` event) and then replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to another (victim) tenant of the same app. The HMAC check still passes because it never looked at the header, so the app processes the payload as belonging to the victim shop.

### Impact Explanation
This breaks the tenant isolation that `HmacValidator.validate` is nominally providing: an unprivileged shop-owner attacker (who has legitimate install access to the app, but not to other tenants' data) can attribute forged webhook events to a different shop, potentially causing the host application to write attacker-controlled data (`request.parsed_body`) into another tenant's records, trigger tenant-scoped side effects (state changes, notifications, syncs) for the victim shop, or otherwise achieve cross-tenant access/interference — a High severity cross-tenant issue per the given impact classes, since the shop-identity binding used for tenant routing is not authenticated.

### Likelihood Explanation
Likelihood is meaningful: the attacker needs only to be an app-installing merchant (no elevated privilege, no leaked secret, no TLS interception) — they can generate a valid HMAC/body pair through their own store's normal activity and then send a raw HTTP POST directly to the app's public webhook endpoint with a modified `shop-domain` header. This requires no credentials belonging to the victim shop or the app owner.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) identity to the HMAC-authenticated data, e.g., by having `Request#to_signable_string` incorporate the header values that downstream code trusts, or by having `Registry.process`/`WebhookMetadata` cross-check `request.shop` against the shop recorded for the specific installation/webhook subscription (e.g., verify the `webhook_id` was actually registered for that shop) rather than trusting the header value verbatim once the raw-body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify sends a legitimately signed POST: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H` from their own webhook delivery (visible to them as the receiving app owner, or by proxying their own endpoint).
3. Attacker crafts a new POST to the app's webhook endpoint reusing the exact same `B` and `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it still equals `H`, so validation succeeds [5](#0-4) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the app to process attacker-controlled data as an event for the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          received_signature = verifiable_query.hmac
