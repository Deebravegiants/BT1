### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` HTTP header as the tenant identity handed to the app's handler. Any actor who can obtain one valid `(body, hmac)` pair for the shared app `client_secret` (e.g., by installing the app on their own store and receiving genuine webhooks) can replay that exact body/HMAC pair while swapping the `X-Shopify-Shop-Domain` header to an arbitrary victim shop domain, and the gem will accept it as an authentic webhook "from" the victim shop.

### Finding Description
`Utils::HmacValidator.validate` is invoked on the `Request` object in `Registry.process`: [1](#0-0) 

The HMAC is validated using `verifiable_query.to_signable_string`, and for webhook `Request`, `to_signable_string` returns only the raw HTTP body — no header data at all: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are all read directly from unauthenticated HTTP headers: [3](#0-2) 

`Registry.process` then forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata`, which is delivered to the app's `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs developers to use `data.shop` as the tenant key for downstream, per-shop processing (e.g. queuing a job scoped to that shop): [6](#0-5) 

The identity binding that is broken: `hmac-verified bytes == raw_body` but `shop identity used by the app == unauthenticated shop-domain header`. Since the app's `client_secret` (used to compute the HMAC) is shared across every shop that has installed the app, any unprivileged merchant who has installed the app can:
1. Receive a legitimate webhook for their own store (valid `raw_body` + valid `hmac-sha256` header for that body, computed with the app's real `client_secret`).
2. Resend the identical `raw_body` and `hmac-sha256` value to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to an arbitrary victim shop's domain.
3. `HmacValidator.validate` still succeeds (only the body is checked), so `Registry.process` treats the request as an authentic webhook for the victim shop and invokes the handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is meant to enforce: an attacker-controlled shop can cause the app to process events attributed to a different shop it does not own. Depending on how the host application uses `data.shop` (as most Shopify app patterns do — to key which merchant's data/session/state to update, log, or act on), this enables cross-tenant data confusion/corruption without any credential theft, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
High likelihood for any real-world app: installing an app on one's own store to legitimately trigger webhooks is a normal, unprivileged action available to any internet user with a Shopify account, and replaying a captured `(body, hmac)` pair with a modified header requires no special access, no secret key knowledge, and no TLS interception — only a normal HTTP client.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signature verification (or otherwise cryptographically bind them to the signed payload), or at minimum require the app to independently verify that the `shop-domain` header corresponds to a shop for which this app currently holds a stored/active session before trusting it, rather than passing the raw unauthenticated header straight to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for topic `orders/create`.
2. Shopify sends the app a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(client_secret, B)`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` / `lib/shopify_api/webhooks/request.rb#to_signable_string`) validates successfully because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the app to process/act on data as if it originated from the victim shop.
