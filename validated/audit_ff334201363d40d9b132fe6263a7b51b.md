### Title
Unaccounted arbitrary external call in `EmporiumUpgradeable.runAction` stateless ops permits draining Emporium's pooled token balance via `approve` (or direct `transfer`) on tokens outside `erc20TokenAddresses` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`runAction`'s balance-conservation check (`balancesBefore`/`balancesAfter`/`deltaAmountChanges`) is only computed over `circomData.erc20TokenAddresses`, while the "Stateless Interaction" branch executes `op.endpoint.call(op.callData)` for every op in `stack.ops` with no restriction on `endpoint` or on which token is targeted [4](#0-3) . Because `stack` and `deltaAmountChanges`/`erc20TokenAddresses` are independently attacker-supplied (only hash-checked, not content-constrained), an attacker can target a token that is simply absent from `erc20TokenAddresses`, causing zero balance checks to ever apply to that token — allowing both an `approve()` grant and, more directly, an outright `transfer()`/drain of Emporium's holdings of that token with no revert and no UTXO/nullifier accounting.

### Finding Description
The claimed equality is: *every token balance change of Emporium during `runAction` must be matched by `deltaAmountChanges`/UTXO issuance ("value conservation")*. The code only enforces this for `i` in `circomData.erc20TokenAddresses`: [5](#0-4) [6](#0-5) 

The `stack.ops` array that drives the actual external calls is decoded independently from `externalActionMetadata` and is **not** bounded to the tokens listed in `erc20TokenAddresses` [7](#0-6) . Nothing in `dimensionsCheck` (which only checks array *lengths* match `dimensions.tokenNumber`) or `getHashedCalldata`/`calldataHash` (which only checks that the supplied metadata bytes match a hash, not their semantic content against the proof) restricts which endpoint or token an op may touch [8](#0-7) [3](#0-2) . The circuit only constrains `inTotal + amountChanges === outTotal` for the tokens actually listed in the proof's dimension arrays — it has no knowledge of, or constraint on, `stack.ops`. `verifyWallet` in stateless mode (`signerAddress == address(0)`) only marks `emporiumMessage` used and returns, performing no signature check on `ops` content at all [9](#0-8) .

`onlyAllowedRecipient` only restricts *who may call* `runAction` (must be Hinkal) [10](#0-9) ; it does not restrict what `runAction`'s internal loop does. Since Emporium is itself `msg.sender` inside the `op.endpoint.call(...)`, any op — `approve(attacker, max)`, or even `transfer(attacker, balance)` — executed against a token not present in `erc20TokenAddresses` bypasses every balance/slippage check in both `EmporiumUpgradeable.runAction` and the outer `Hinkal.transact` loop (which is likewise only iterated over `circomData.erc20TokenAddresses`) [11](#0-10) .

Exploit flow: attacker deposits their own funds for an unrelated token/action to obtain a valid proof, includes an extra `EmporiumOperation{endpoint: victimToken, invokeWallet:false, callData: transfer(attacker, victimToken.balanceOf(emporium))}` in `stack.ops`, with `victimToken` deliberately excluded from `circomData.erc20TokenAddresses`. `runAction` executes the transfer from Emporium's own balance, returns cleanly with no reverts, and no nullifier/UTXO is ever created or burned for the drained value.

### Impact Explanation
Direct theft of any ERC20 token balance sitting in the `Emporium` contract that is not the specific token(s) declared in the attacker's own transaction's `erc20TokenAddresses` — this includes any float/residual balances from other users' prior Emporium-mediated swaps or transient holdings. This is theft of in-flight/pooled user or protocol funds with zero on-chain accounting (no nullifier, no UTXO), matching the **Critical** category (direct theft of in-flight funds, bypass of the value-conservation invariant). The attack is repeatable for every token balance Emporium accumulates.

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: they need (1) their own valid UTXOs/proof for any unrelated legitimate Emporium-routed transaction, and (2) knowledge that Emporium currently holds a nonzero balance of some token not part of their declared `erc20TokenAddresses`. Both are attacker-controllable/observable; no privileged role, signature, or victim cooperation is required, since `verifyWallet` for stateless mode short-circuits with no signature check [9](#0-8) . Cost is just one legitimate-looking transaction.

### Recommendation
Restrict stateless op endpoints so they cannot target arbitrary tokens/contracts outside the transaction's declared token set, or require that every `op.endpoint` interaction affecting an ERC20 balance/allowance be reconciled against a corresponding entry in `circomData.erc20TokenAddresses` (i.e., enforce that any token whose `balanceOf`/`allowance` for Emporium changes during `runAction` must be present in and accounted for by `erc20TokenAddresses`/`deltaAmountChanges`, not merely the pre-declared subset). Alternatively, disallow direct `approve`/`transfer`-class selectors on arbitrary ERC20s from the stateless branch, or maintain an explicit allowlist of endpoints callable in stateless mode.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, register Emporium as external action, whitelist it as `allowedRecipient`.
2. Seed `Emporium` with a "victim" ERC20 token balance (simulating pooled float from a prior transaction, e.g., leftover from a swap).
3. Attacker constructs a legitimate `CircomData`/proof for an unrelated token X with `erc20TokenAddresses = [X]`, but sets `externalActionData.externalActionMetadata` to an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: victimToken, invokeWallet:false, value:0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, victimToken.balanceOf(address(emporium)))}]`.
4. Call `Hinkal.transact(...)`. Assert: call succeeds, no revert, `utxoSet` contains nothing for `victimToken` (it's not even in `erc20TokenAddresses`).
5. Assert `victimToken.balanceOf(attacker) > 0` and `victimToken.balanceOf(emporium) == 0` afterward, while no nullifier was inserted and no UTXO commitment corresponds to the drained amount — demonstrating the value-conservation equality (`Σ balance changes == Σ deltaAmountChanges`/UTXO issuance) is broken for `victimToken`.
