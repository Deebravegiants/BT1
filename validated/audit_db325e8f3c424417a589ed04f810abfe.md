### Title
Webhook `shop` (and `topic`) identity is taken from unauthenticated HTTP headers while the HMAC only signs the raw body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw body only, but `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shop-domain` (and `topic`) headers as the tenant/handler-selection identity when dispatching the webhook payload to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all read directly from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Registry.process` validates the HMAC against the body/secret only, then immediately trusts `request.shop` and `request.topic` (both header-derived, unauthenticated) to select the handler and build the metadata passed to the app: [3](#0-2) 

This is structurally the same root-cause pattern as the referenced report: a value that is *used* as the trusted identity (`shop`) is not the value that is actually covered by the cryptographic check (the HMAC over `@raw_body` with `Context.api_secret_key`, verified in `HmacValidator.validate_signature`): [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared across all shops installing the same app, any party who legitimately receives one valid `(raw_body, hmac)` pair from their own shop's webhook delivery can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` will still return `true` (it only checks the body signature), and `Registry.process` will hand the forged `shop` value straight to the app's handler via `WebhookMetadata`, since it never cross-checks that the header-provided shop matches anything cryptographically bound to that request.

### Impact Explanation
The identity binding that should hold is:
`shop authenticated by the request signature == shop used as the tenant key for processing the webhook`

Here that equality is broken: the HMAC authenticates "some webhook payload signed with this app's secret," while the `shop` used for tenant attribution comes from an attacker-controllable header. Any app that uses `WebhookMetadata#shop` (as documented/intended) to select or scope per-merchant data will process attacker-forged data under an arbitrary victim shop identity — this is a cross-tenant data-integrity/confidentiality issue reachable purely through HTTP requests to the app's own webhook endpoint, with only knowledge of one legitimately-received `(body, hmac)` pair (no access token, `client_secret`, or privileged account required).

### Likelihood Explanation
Exploitability requires only: (1) the attacker's own shop installs the app and receives at least one legitimate webhook (trivial — install the app, trigger any topic that echoes attacker-controlled content, e.g. product/order webhook body), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers, which is inherent to any exposed webhook receiver. No privileged credentials or secrets are needed.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`) inside the signed payload used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them for handler dispatch/metadata. At minimum, `Registry.process` should not treat header-derived `shop`/`topic` as authenticated identity for tenant-scoped operations unless the app additionally validates that the shop is one it expects for that specific access token/session, since the gem's webhook signature does not vouch for header values.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures one legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a new HTTP request directly to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(api_secret_key, B) == H`, both unchanged. [3](#0-2) 
4. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` to the app's handler, which processes attacker-controlled data under the victim shop's identity.
