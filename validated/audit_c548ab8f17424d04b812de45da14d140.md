## Title
Webhook shop-domain binding not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`) values that the handler subsequently trusts are read from unauthenticated HTTP headers. This breaks the identity binding `hmac_signed_bytes == bytes_the_handler_attributes_to_a_shop`: the signature proves the body came from Shopify for *some* legitimate delivery, but nothing cryptographically ties that body to the `shop-domain` header value used to route/attribute the webhook.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` and `topic` are parsed straight from headers that are not part of the signed content: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

`HmacValidator.validate` and `validate_signature` confirm the check is computed exclusively from `verifiable_query.to_signable_string` (the raw body for webhooks), never from headers: [4](#0-3) 

Because the HMAC never covers `shop-domain`, the equality the library implicitly relies on — "HMAC-authenticated bytes == the shop this webhook is attributed to" — does not hold. A valid `(body, hmac)` pair obtained for shop A can be replayed with the `X-Shopify-Shop-Domain` header swapped to shop B, and `Utils::HmacValidator.validate` still returns `true` because it only recomputes over `@raw_body`.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` (as intended by the API, see `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))`) to select which tenant's session/state to operate on is exposed to cross-tenant data injection: an attacker who legitimately receives real webhook deliveries for their own installed shop (any merchant/unprivileged user can install a public app) can capture a valid `(body, hmac)` pair and resubmit it to the app's webhook endpoint with a different shop's domain in the header. The app then processes attacker-controlled body content while believing it originates from the victim shop, causing cross-tenant state corruption (e.g., fake order/product/customer events attributed to a shop that never sent them). This matches the Critical impact category of cross-tenant access.

### Likelihood Explanation
Likelihood is Medium-to-High for embedded/public apps: exploitation only requires an unprivileged actor who can install the target app on a shop they control (to obtain genuine signed deliveries) and the ability to POST directly to the app's public webhook endpoint with modified headers — no access token, `client_secret`, or leaked credential is needed, satisfying the "unprivileged internet user" bar.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable content, or otherwise cryptographically bind them to the payload before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document/enforce that consuming apps must independently verify `shop` against a known, previously-registered shop for that specific webhook subscription rather than trusting the header value once HMAC-over-body succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a real webhook, e.g. body `{"id":1}` with headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
2. Attacker captures this exact `(body, hmac)` pair.
3. Attacker POSTs the same body/hmac to the app's webhook endpoint, but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC only over the raw body (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:27-31`) — validation still passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-supplied data as belonging to the victim shop.
