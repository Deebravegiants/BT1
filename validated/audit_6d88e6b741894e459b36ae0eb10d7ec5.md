### Title
Stale stored owner retains spending authority after position-NFT transfer — (File: contracts/controller/src/account.rs)

### Summary
The GitLab bug class is a missing authorization-scope check: an action was applied to an entity outside the scope the authority was granted for. The analog here is account spending authority keyed to the stale `owner` field inside the stored `Account` struct rather than the live position-NFT owner. `require_owner_or_delegate` admits `caller == account.owner` from `storage::get_account`, while ownership-sensitive paths like `add_delegate`, `remove_delegate`, and `renew_account` go through `require_account_owner`, which reads `storage::account_owner` (the live NFT owner). If the stored `account.owner` is not resynchronized after a `position-nft::transfer`, the previous holder keeps full borrow/withdraw/strategy authority over an account they no longer own.

### Finding Description
- `is_owner_or_delegate` returns `true` whenever `caller == owner`, where `owner` is `account.owner` loaded by `storage::get_account` (account.rs:121, 98). The delegate list is likewise keyed by that stored owner via `storage::get_delegates(env, account_id, owner)` (account.rs:126).
- Every value-moving entrypoint that must be owner-scoped uses this stale-field check: `process_withdraw` calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` (positions/supply.rs:150), and `borrow`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `migrate_from_blend` reach the same guard per `load_or_create_account`'s `Migrate`/`Multiply` guards (account.rs:101-109).
- By contrast, `require_account_owner` re-reads `storage::account_owner` — the NFT's current owner — and compares it to the caller (account.rs:143-147). That is the correct scope check, used only for delegate management and TTL renewal.
- The declared exception list acknowledges that `position-nft::transfer` moves "the whole account" and only claims "delegate grants from the previous owner go inactive" (scripts/permissionless_entrypoints.txt:111). It does not state that the `owner` field inside `Account` is restamped, and no resync appears in `account.rs`, `supply.rs`, or `finalize_position_flow` paths I inspected.

So a user who sells or transfers their account NFT retains `caller == account.owner` equality under the stored field and can `withdraw` all collateral (with `to` set to any `require_external_recipient`-passing address) or `borrow` against the new owner's collateral.

### Impact Explanation
Theft of user funds: the previous NFT holder drains the account's withdrawable collateral and borrows up to the LTV limit, routing proceeds to an arbitrary `to`/`recipient` address, leaving the buyer with an emptied or maximally leveraged account. This is exactly the GitLab shape: authorization evaluated against the scope the grant was recorded under (stored owner/delegate list), not the entity's current owner.

### Likelihood Explanation
Fully permissionless: `transfer` requires only `from.require_auth` on the NFT side, and `withdraw`/`borrow` require only `caller.require_auth` plus `require_owner_or_delegate`. Any account holder can transfer the NFT (sale, gift, or an attacker who obtains an `approve`/`approve_for_all` grant via `transfer_from`) and immediately exercise the retained authority. No timing, oracle, or liquidity precondition is needed.

### Recommendation
Derive spending authority from a single source of truth. In `is_owner_or_delegate`, replace `account.owner` with `storage::account_owner(env, account_id)` (the NFT owner), or restamp `account.owner` on every load/transfer and rekey the delegate map. Align `require_owner_or_delegate` with `require_account_owner` so the stored `Account.owner` field is never the authority basis, and extend the transfer path to invalidate the old owner's stored-owner equality.

### Proof of Concept
1. Alice owns `account_id` A with supplied collateral; `Account{owner: alice, ..}` is stored via `set_account` at creation (account.rs:64-71).
2. Alice calls `position-nft::transfer(alice → bob, A)`; NFT owner is now Bob.
3. Alice calls `controller::withdraw(caller=alice, account_id=A, withdrawals=[collateral, amount], to=Some(alice))`.
4. `process_withdraw` calls `caller.require_auth()` (passes — Alice signs), loads `account` whose stored `owner` is still Alice, and `require_owner_or_delegate` returns via `caller == owner` (account.rs:121-122).
5. The pool pays Alice; Bob's account keeps the debt and loses the collateral.

Caveat: this finding assumes `storage::get_account` returns the `owner` field as stored at creation and that no path restamps it post-transfer; I could not fully trace `storage/account.rs` and `finalize_position_flow` to confirm there is no owner resync. If a resync exists elsewhere, the vulnerability reduces to the narrower issue that the delegate list is keyed by a field that can diverge from the NFT owner.
