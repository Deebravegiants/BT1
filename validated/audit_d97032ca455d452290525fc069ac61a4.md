Confirmed: `_getOraclePrice` in `SimplexPaymaster.sol` only checks `answer <= 0` and staleness (`block.timestamp - updatedAt > maxOracleAge`), with no bound check against the Chainlink aggregator's `minAnswer`/`maxAnswer` circuit-breaker values. This is used both in `_tokenPrice` (per-UserOp gas pricing) and `swapAndDeposit` (fee-recycling `amountOutMin` derivation), and any unprivileged UserOp sender (a "bandwidth purchaser" of gas via the paymaster) can trigger `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` on every paymaster-sponsored operation.

### Title
Missing Chainlink circuit-breaker (min/max answer) validation in `SimplexPaymaster` oracle pricing lets a de-pegged/crashed feed drain paymaster funds - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` only rejects non-positive and stale answers, never checking the returned `answer` against the aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds. If either the native-asset feed or a registered token's feed crashes past its floor, Chainlink continues returning the frozen `minAnswer` instead of the real price, and every unprivileged UserOp that pays gas through the paymaster is priced off that stale minimum.

No check exists anywhere in the file against a minimum/maximum price bound (confirmed by absence of `minAnswer`/`maxAnswer`/`minPrice`/`maxPrice` identifiers in the codebase), so when an aggregator's circuit breaker is hit — the classic scenario the external report describes (e.g. a token like a stablecoin or the native asset crashing far below the aggregator's configured floor) — `latestRoundData()` keeps returning the frozen floor price instead of reverting or signaling staleness. Because `updatedAt` still advances during circuit-breaker conditions (the round is technically "fresh"), the staleness check does not catch this case either.

### Impact Explanation
`_tokenPrice` computes `tokenPrice = nativeUsd * 10^tokenDecimals * (1+markup) / tokenUsd`. If a registered ERC-20 fee token crashes in real value but its feed is pinned at `minAnswer` (overstating `tokenUsd`), the computed `tokenPrice` is understated, so every subsequent UserOp is charged fewer token units than the true gas cost — directly draining the paymaster's ERC-20/native reserves (a form of protocol fund loss) on each op processed while the feed is pinned. Symmetrically, a native-asset feed pinned at its floor overstates `nativeUsd`, overcharging users on every sponsored UserOp. The same stale price also corrupts `swapAndDeposit`'s `amountOutMin`, allowing an artificially low minimum output when recycling fees, which can be sandwiched for additional loss of treasury funds.

### Likelihood Explanation
Any address can submit a UserOp against a live EntryPoint that routes through this paymaster, so exploitation requires no privileged role — only that one of the registered feeds (native or any onboarded ERC-20) is currently pinned at its circuit-breaker floor, a documented real-world Chainlink failure mode (e.g., the LUNA/UST collapse cited in the source report). Given `_getOraclePrice`'s existing staleness/positivity checks show the team is oracle-safety-conscious but omitted the bound check, this is a plausible oversight rather than a purely theoretical one.

### Recommendation
Extend `_getOraclePrice` to fetch and validate against the aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV2V3Interface.minAnswer()`/`maxAnswer()` or a governance-configured bound per feed), reverting when `answer <= minAnswer` or `answer >= maxAnswer`, consistent with the pattern the external report recommends. Alternatively, cross-check against a secondary price source (e.g. a TWAP) before trusting a Chainlink answer that sits at or near known aggregator bounds.

### Proof of Concept
1. Governance registers a stablecoin fee token via `RegisterToken` with its Chainlink `tokenOracle` (as in `_registerToken`, `evm/src/utils/SimplexPaymaster.sol:392-397`).
2. The stablecoin de-pegs sharply downward in the real market; its Chainlink aggregator hits its configured `minAnswer` floor and freezes there while `updatedAt` keeps refreshing (so `StaleOraclePrice` never triggers).
3. Any user submits a UserOp with `paymasterData` mode `0x00`/`0x02` naming that token. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the frozen floor price without complaint (`answer > 0`, not stale) at `evm/src/utils/SimplexPaymaster.sol:662-668`.
4. The resulting `tokenPrice` is computed from the inflated `tokenUsd`, undercharging the UserOp sender in token terms relative to the real (crashed) value of that token, while the paymaster still pays full native gas cost from its EntryPoint deposit — repeatable across every UserOp routed through the paymaster until governance manually deactivates the token, cumulatively draining paymaster-held funds.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
