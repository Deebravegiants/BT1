### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shopify-shop-domain` (tenant) header verbatim to route/attribute the payload — even though that header is never part of the signed material. This is the exact bug class described in the analog report: two values that are supposed to be the same identity binding (the shop the HMAC authenticates vs. the shop the handler acts on) are computed from different sources, one of which is unauthenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

All tenant-identifying fields — `shop`, `topic`, `api_version`, `webhook_id` — are read straight from HTTP headers and are **not** included in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the request using only this body-scoped HMAC, and then immediately trusts `request.shop` (the raw header) to build the `WebhookMetadata` handed to the application's webhook handler: [3](#0-2) 

`HmacValidator.validate` confirms only that the body matches the signature computed with `Context.api_secret_key`; it says nothing about which shop the body "belongs" to: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler processes data for`. In this code, the HMAC only authenticates *bytes of the body*; the `shop` used for tenant routing is taken from an out-of-band, unauthenticated header. Because the webhook endpoint is a public HTTP endpoint (any client can POST to it, not only Shopify's infrastructure), anyone who can obtain one genuine `(raw_body, hmac)` pair for *any* shop — including a shop they legitimately control, such as their own development store — can replay that exact body and HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` will still succeed (the body/HMAC pair is legitimate and untouched), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to provide: the app cannot actually trust that `WebhookMetadata#shop` reflects the shop that produced the signed body. A host application that uses `data.shop` to select which tenant's database row(s) to update/insert (a normal, expected usage pattern since the gem hands this value straight through as the tenant key) can be made to write attacker-supplied data into a different merchant's tenant context — a cross-tenant data injection. This maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only unprivileged internet access to the app's public webhook endpoint plus a single genuine `(body, hmac)` pair, which is trivial to obtain — e.g., by installing the app on one's own store/dev shop and capturing any webhook delivery it sends, or observing any single benign webhook triggered by an action the attacker controls in their own shop. No `api_secret_key`, access token, or victim credentials are required. The only constraint is that the replayed body content is fixed (attacker controls the *shop* attribution, not arbitrary body content) — still sufficient for spoofing/mis-attribution attacks on any handler that trusts `shop` for row selection or tenant scoping.

### Recommendation
Bind the tenant identity into the material that is HMAC-verified, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signature (e.g., include a canonicalized combination of body + relevant headers in `to_signable_string`, or require applications to independently authenticate the shop via other Shopify-provided verification), so that the shop attributed to a webhook cannot be altered independently of the signed body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it deliver a normal webhook, capturing the raw request body `B` and header `shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's `client_secret`, which the attacker does not know but does not need to know).
2. Attacker replays an HTTP POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `shopify-hmac-sha256: H` (unchanged, still valid because `Request#to_signable_string` == `B`)
   - Header `shopify-shop-domain: victim-shop.myshopify.com` (changed)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `H` against `B`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-originated body `B`, even though `victim-shop` never sent this webhook: [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
