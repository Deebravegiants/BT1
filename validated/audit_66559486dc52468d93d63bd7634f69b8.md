## Analog Found: Reentrancy-Exploitable Fee Payout in `EvmHost.dispatchIncoming(GetResponse)`

### Title
Relayer fee for GET responses is read and paid out **after** an untrusted external call, without clearing the source-of-truth commitment, enabling double-payment via reentrancy - (File: `evm/src/core/EvmHost.sol`)

### Summary
The reported Aloe bug class — "write to memory / run business logic / call out / then finalize storage" without atomic clean-up — has a concrete analog in `EvmHost.dispatchIncoming(GetResponse memory response, address relayer)`. Here the relayer's fee reward is computed from persistent storage (`_requestCommitments[commitment].fee`) and paid out via `safeTransfer` *after* an external, attacker-influenced call (`onGetResponse` on `response.request.from`), and `_requestCommitments[commitment]` is never deleted once the fee is paid. [1](#0-0) 

### Finding Description
```solidity
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    // replay protection
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({relayer: relayer, responseCommitment: response.hash()});

    (bool success,) = _bytesToAddress(response.request.from)
        .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

    if (!success) {
        delete _responseReceipts[commitment];
        return;
    }

    // reward the relayer fee
    uint256 fee = _requestCommitments[commitment].fee;
    if (fee != 0) {
        IERC20(feeToken()).safeTransfer(relayer, fee);
    }
    emit GetRequestHandled({commitment: commitment, relayer: relayer});
}
``` [1](#0-0) 

Two things distinguish this from safe patterns elsewhere in the same contract:
1. `_responseReceipts[commitment]` is unconditionally overwritten, not checked-then-set, so it provides no dedup guard against the same commitment being processed twice in the same or a later handler invocation.
2. Unlike the sibling timeout handlers, which correctly apply CEI by deleting `_requestCommitments[commitment]` **before** making the external call and only restoring it on failure, `dispatchIncoming(GetResponse ...)` reads `_requestCommitments[commitment].fee` and pays it out **after** the external call, and never deletes the entry:

```solidity
function dispatchTimeOut(GetRequestTimeout memory timeout, FeeMetadata memory meta, bytes32 commitment) external restrict(_hostParams.handler) {
    // replay protection
    delete _requestCommitments[commitment];
    (bool success,) = _bytesToAddress(timeout.request.from).call(...);
    if (!success) {
        _requestCommitments[commitment] = meta;
        return;
    }
    if (meta.fee != 0) {
        IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
    }
    ...
}
``` [2](#0-1) 

This shows the codebase is aware of and applies the correct "clear storage before external call" pattern elsewhere, but the GET-response success path does not: the fee's backing storage (`_requestCommitments[commitment]`) is left intact after payment.

### Impact Explanation
`response.request.from` is attacker-controllable (it is whatever address originally dispatched the GET request), so an attacker can deploy a malicious `IApp` contract, dispatch a GET request through it, and have its `onGetResponse` callback attempt to trigger re-processing of the same response commitment (e.g., by causing the relayer/handler to resubmit or by exploiting any batch path in `HandlerV2` that iterates multiple response messages without an upfront duplicate check against `_requestCommitments`). Because `_requestCommitments[commitment].fee` is never zeroed after the reward transfer, each successful (re-)invocation of `dispatchIncoming(GetResponse, ...)` for the same commitment pays out the same fee again, directly draining the host's `feeToken` balance — a concrete unbacked-value transfer that other relayers/protocol revenue ultimately funds. This directly matches "Accept only concrete theft ... or unbacked mint" validation criteria via double relayer-fee payment.

### Likelihood Explanation
This path is reachable by any user who dispatches an ISMP GET request through their own (potentially malicious) `IApp` contract and colludes with (or is) the relayer submitting the response proof — a single relayed proof is sufficient to trigger the vulnerable function. Exploitability depends on whether `HandlerV2` (the sole caller of `dispatchIncoming(GetResponse,...)`, restricted via `restrict(_hostParams.handler)`) prevents delivering/re-delivering the same response commitment more than once before calling into `EvmHost`; I was not able to fully verify `HandlerV2.sol`'s message-processing loop within the available tool budget, so whether duplicate submissions within one batch (or across multiple handler calls before a timeout/settlement) are otherwise blocked is **unconfirmed**. Regardless, the missing "delete `_requestCommitments[commitment]` before paying" step is a real deviation from the CEI pattern used one function below it in the same contract, and is the closest concrete analog to the reported Aloe reentrancy bug class within Hyperbridge's unprivileged-reachable dispatch/delivery surface.

### Recommendation
Apply the same pattern already used in `dispatchTimeOut`: delete (or zero out the `fee` field of) `_requestCommitments[commitment]` **before** invoking the external `onGetResponse` call, and restore it only if the call fails. This closes the reentrancy/double-payment window and makes the success path consistent with the rest of `EvmHost.sol`.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onGetResponse`.
2. Attacker calls `EvmHost.dispatch(DispatchGet{...})` from `EvilApp`, paying a relayer fee `F`, so `_requestCommitments[commitment].fee = F`.
3. A (possibly attacker-controlled or colluding) relayer submits a valid state-proof for the GET response; `HandlerV2` verifies it and calls `EvmHost.dispatchIncoming(response, relayer)`.
4. Inside `EvilApp.onGetResponse`, the attacker arranges for the handler to process the identical response commitment again in the same or a subsequent transaction before any dedup check blocks it (e.g., via a second handler call using the same proof/message before `_requestCommitments` is cleared).
5. Each successful pass re-reads `_requestCommitments[commitment].fee == F` (since it was never deleted) and calls `safeTransfer(relayer, F)` again, paying out `F` multiple times from the host's fee-token balance for a single genuine request.

**Note on verification limits:** I could not fully confirm within tool budget whether `HandlerV2.sol`'s batch-processing loop independently prevents a duplicate `dispatchIncoming(GetResponse,...)` call for the same commitment before this code path executes twice. The core finding — that the fee storage is read/paid post-external-call and never cleared, unlike the adjacent timeout handlers — is confirmed directly from the source.
