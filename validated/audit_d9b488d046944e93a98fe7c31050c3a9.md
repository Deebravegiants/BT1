### Title
Unauthenticated `address` field in `GetRequestsWithProof` lets a front-runner steal relayer fees and reputation rewards for another party's proof work - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
CVE-2018-16860 is a bug class where an unauthenticated identity field in an otherwise cryptographically-verified request is trusted for a security decision, letting a man-in-the-middle substitute the identity while the authenticated part of the request stays valid. The analog here is `pallet-state-coprocessor::handle_unsigned`, which accepts a `GetRequestsWithProof` message containing state proofs (authenticated) plus a plain `address: Vec<u8>` field (unauthenticated) that names who gets paid/credited. Anyone observing the pending unsigned extrinsic can resubmit it verbatim except for a different `address`, and the proof verification will still pass because `address` is not bound into anything cryptographic.

### Finding Description
`GetRequestsWithProof` is defined with an `address` field documented as "Address that should be credited with fees": [1](#0-0) 

`handle_get_requests` verifies the source membership proof and destination state proof, both of which are only over the `requests`/`response` data — `address` is never included in the hashed/proven content: [2](#0-1) 

After verification, `address` is used, unauthenticated, to (a) mint reputation tokens proportional to bytes delivered, and (b) become the "relayer" of record on the response receipt and `GetRequestHandled` event: [3](#0-2) 

This message is dispatched via the pallet's `handle_unsigned` extrinsic, which is `ensure_none`-gated (no signed origin at all) and validated only by re-running `handle_get_requests` and tagging the tx-pool entry with a hash of the *requests*, not of `address`: [4](#0-3) 

Because neither `pre_dispatch` nor `validate_unsigned` binds `address` to a signature or to the submitter, an unsigned transaction sitting in the public mempool can be copied and resubmitted by anyone with a substituted `address`, exactly as CVE-2018-16860 allowed an attacker to substitute the unauthenticated principal field in an otherwise-valid Kerberos exchange. Whoever's copy lands on-chain first collects the reputation mint and is recorded as the delivering relayer, even though they performed none of the off-chain proof-fetching work that the original submitter did.

### Impact Explanation
This directly diverts protocol-level relayer/reward accounting: reputation tokens minted via `pallet_messaging_incentives::ReputationAsset::mint_into` and the recorded "delivering relayer" identity (used for reward/reputation bookkeeping and auditability) go to an attacker who merely observed and resubmitted someone else's transaction, rather than the party who did the off-chain work of fetching and assembling the proofs. This is a concrete "relayer fee and reward accounting" violation explicitly in scope, and requires only observing a public unsigned mempool transaction — reachable by any unprivileged network participant, not an admin/governance/node operator.

### Likelihood Explanation
High for anyone monitoring the unsigned transaction pool of the Hyperbridge chain: `GetRequestsWithProof` messages are broadcast unsigned and openly gossiped, `validate_unsigned` does not tie the payload to any specific submitter, and copying+resubmitting a transaction with one field changed is trivial. The mint is gated by a global `MintPerByte` rate but is otherwise unconditional once a valid proof lands.

### Recommendation
Bind `address` cryptographically to the actual data submitter, e.g., require a signature over `(address, hash of requests, nonce)` similar to how `pallet-relayer`'s `beneficiary_message`/`outbound_request_delivery_message` bind payee to a signed, nonce-protected payload (`modules/pallets/relayer/src/accumulate.rs:303-315`, `modules/pallets/relayer/src/outbound_request.rs:144-154`), or include `address` in the `provides`/priority tag of `validate_unsigned` so only the first-seen `(requests, address)` pair is admitted and simple resubmission with a swapped address cannot win a race against the original submitter's transaction already in the pool.

### Proof of Concept
1. Relayer R constructs a valid `GetRequestsWithProof { requests, source, response, address: R }` and submits it unsigned to `pallet-state-coprocessor::handle_unsigned`.
2. Attacker A observes this pending unsigned extrinsic in the mempool (all fields, including proofs, are visible).
3. A copies the message, replacing only `address` with A's own account, and resubmits it as their own unsigned transaction with the same/higher priority.
4. If A's copy is included first (or instead of R's, since both hash to distinct `provides` tags based only on `requests`, allowing potential double-processing races before R's original is finalized), `handle_get_requests` verifies identically (proofs don't cover `address`), and the reputation mint plus `GetRequestHandled`/response-receipt "relayer" attribution goes to A instead of R.

		fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
			let Call::handle_unsigned { message } = call else {
				return Err(TransactionValidityError::Invalid(InvalidTransaction::Call));
			};

			if let Err(err) = Self::handle_get_requests(message.clone()) {
				log::error!(target: "ismp", "{:?}", err);
				return Err(TransactionValidityError::Invalid(InvalidTransaction::Call));
			}

			let mut messages = message
				.requests
				.iter()
				.map(|get| hash_request::<<T as Config>::IsmpHost>(&Request::Get(get.clone())))
				.collect::<Vec<_>>();
			messages.sort();

			// this is so we can reject duplicate batches at the mempool level
			let msg_hash = sp_io::hashing::keccak_256(&messages.encode()).to_vec();

			Ok(ValidTransaction {
				priority: 100,
				requires: vec![],
				provides: vec![msg_hash],
				longevity: 25,
				propagate: true,
			})
