### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates only the raw JSON body of an incoming webhook via HMAC-SHA256, while the merchant-identifying `shop` header (along with `topic` and `webhook_id`) is read verbatim from HTTP headers and passed unauthenticated to the app's webhook handler. This breaks the binding "tenant identity used by the handler == tenant identity authenticated by the HMAC," allowing an attacker to combine a genuinely-signed body (obtained from their own shop's webhook delivery) with a forged `shop`/`topic` header to make the host application process the payload as if it came from a different, victim merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from HTTP headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, and then immediately dispatches the handler using `request.shop` (and `request.topic`) as trusted tenant/routing identity: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute and compare the signature strictly over `verifiable_query.to_signable_string`, i.e. the raw body, never the headers: [4](#0-3) 

Because the endpoint that receives webhooks is a normal internet-facing HTTP route, nothing in this gem prevents an unprivileged internet user from POSTing directly to it. If that user can obtain any valid `(raw_body, hmac)` pair signed with the app's shared secret — for example by subscribing their own shop to a webhook topic and capturing the delivery Shopify sends them — they can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for an arbitrary victim shop domain. `HmacValidator.validate` will still succeed, because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain: [5](#0-4) 

This is exactly the identity-binding class described in the reference report: a field that is acted upon (`shop`, used by host applications to select which merchant's records to create/update/delete in response to the webhook) is not covered by the cryptographic check (`hmac`, which only covers `raw_body`). The equality that should hold — `shop authenticated by HMAC == shop consumed by handler` — does not hold, since `shop` is never part of the signed content at all.

### Impact Explanation
Any host application that uses `request.shop` / `WebhookMetadata#shop` from this gem to select or scope the merchant/tenant record being mutated (a very common and encouraged usage pattern for multi-tenant Shopify apps) is exposed to cross-tenant data confusion/corruption driven entirely by an unprivileged internet user forging a header on an otherwise-valid signed payload. This matches the Critical "cross-tenant access" impact category, since the gem itself provides no mechanism to bind the claimed tenant to the authenticated bytes.

### Likelihood Explanation
High. The webhook endpoint is by design an internet-facing route that must accept POSTs. Obtaining a legitimate `(body, hmac)` pair only requires the attacker to run their own store and subscribe to any webhook topic supported by the target app (installing the app themselves is a normal, unprivileged action), then capturing the delivered payload and its `X-Shopify-Hmac-Sha256` header. No access token, `client_secret`, or privileged account is required — only the ability to receive a webhook for a shop the attacker legitimately controls and to send a crafted HTTP request to the app's public callback URL.

### Recommendation
Bind the tenant/routing identity into the authenticated material, or otherwise cryptographically tie the header values to the request that this gem validates:
- Compute the HMAC over a canonical string that includes `shop`, `topic`, and `webhook_id` in addition to the raw body, and update `Webhooks::Request#to_signable_string` accordingly (this is a breaking change to the verification contract and must be coordinated with Shopify's webhook delivery format).
- At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` are not authenticated by the HMAC check and must be cross-checked by the host application against a known, previously-established session/shop record before being trusted for tenant-scoped operations.
- Consider exposing a stricter validation mode that rejects requests where the claimed `shop` does not match an expected value supplied by the caller.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and subscribes to webhook topic `orders/create`.
2. Shopify delivers a webhook to the app with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body and headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value.
4. Attacker crafts a direct HTTP POST to the app's webhook endpoint with the identical raw body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unmodified) raw body against the (unmodified) HMAC — validation succeeds.
6. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, and any host application logic keyed on `data.shop` will act on the victim's tenant using attacker-controlled content. [3](#0-2)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
