### Title
Duplicate input‑token entries permanently freeze escrowed order funds via an accounting‑underflow revert - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` explicitly rejects duplicate tokens in `order.output.assets` [1](#0-0)  but performs **no equivalent uniqueness check on `order.inputs`**. Because escrow accounting is keyed only by `(commitment, tokenAddress)` — not by input index — an order whose `order.inputs` array contains the same token at two different indices causes `_withdraw` to release the shared escrow bucket twice in the same call. The second release always finds the bucket already drained and reverts, exactly like the `Pool.repay` `_currentTotalDebt -= amount` underflow in the referenced report, permanently blocking the only code path that can release that escrow.

### Finding Description
Escrow for an order is stored per `(commitment, token)` pair: `mapping(bytes32 => mapping(address => uint256)) public _orders;` [2](#0-1) .

In `_fillSameChain`, each `order.inputs[i]` / `order.output.assets[i]` pair is processed independently, and the escrow amount to release for the *final* leg of any output token is computed by re-reading the **whole remaining balance** of the corresponding input token bucket, not a per-index share:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

If two different indices `i` and `j` of `order.inputs` reference the **same token address**, and both legs complete (`amountFilled == totalRequired`) within the same `fillOrder` call, both `escrowedInputs[i]` and `escrowedInputs[j]` are populated with the *same* full remaining balance of `_orders[commitment][token]` (read before any decrement occurs, since `_fillSameChain` only writes `_partialFills`, not `_orders`).

Both entries are then passed together into a single `_withdraw` call:

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
``` [4](#0-3) 

- Iteration for index `i`: `escrowed` = full balance (e.g. 1000), amount = 1000 → bucket set to `0`, tokens transferred.
- Iteration for index `j` (same token): `escrowed` = `0` → `revert UnknownOrder()`.

Because Solidity ^0.8.24 arithmetic is checked, and because the check `escrowed == 0` also fires deterministically here, the whole transaction reverts. Since the state mutation is atomic, this doesn't corrupt storage, but it means **every attempt to complete the order in a way that finalizes both duplicate-token legs together will always revert**. The identical structural design (shared decrement bucket) recurs in the cross-chain/tron variant of `withdraw`, where the transfer even precedes the decrement before reverting: [5](#0-4) .

This is the same root-cause pattern as the referenced Sherlock report: a shared, single global counter (`_currentTotalDebt` there, `_orders[commitment][token]` here) is depleted by one release path, so a second legitimate release referencing the same counter permanently reverts with an arithmetic/zero-balance guard, and there is no code path that lets the depleted counter be "topped back up" for the other leg. The order's remaining escrowed collateral for that duplicated token then cannot be released through `fillOrder`/`cancelOrder` in the pattern that triggers the collision, because `placeOrder` never rejects the duplicate-input-token construction the way it rejects duplicate outputs.

### Impact Explanation
An order creator (or anyone who can be induced to accept such an order) whose `order.inputs` contains the same ERC‑20/native token at two indices has their escrowed collateral locked: any solver attempt to fully complete both corresponding output legs in one transaction reverts, and repeated attempts fail identically since the underlying storage layout guarantees the collision every time. This is a permanent freezing-of-funds condition matching the "Borrower cannot repay debt / cannot recover collateral" impact class (High), reachable purely through a user-submitted `placeOrder` transaction with no privileged access required.

### Likelihood Explanation
Likelihood is Medium-to-High: nothing in `placeOrder` prevents constructing `order.inputs` with a duplicated token address (unlike `order.output.assets`, which is explicitly checked and rejected at lines 197–221 of `IntentGatewayV2.sol`). Any user or integrator building orders programmatically, or a solver-selection flow that composes multi-leg orders, could trigger this without realizing the two entries alias the same escrow bucket.

### Recommendation
Add the same duplicate-token rejection that already exists for `order.output.assets` to `order.inputs` in `placeOrder`, or key `_orders` by `(commitment, index)` instead of `(commitment, token)` so overlapping input tokens cannot alias a shared bucket, and cap `_withdraw`'s decrement to `min(amount, escrowed)` (or aggregate/allocate distinct sub-balances) rather than relying on a bare equality/underflow guard as the only safety check.

### Proof of Concept
1. Craft `order.inputs = [ {token: USDC, amount: 500}, {token: USDC, amount: 500} ]` and `order.output.assets = [ {token: DAI, amount: 500}, {token: DAI, amount: 500} ]` (two legs, same input token, distinct output legs so the output-dedup check in `placeOrder` doesn't fire).
2. Call `placeOrder` — succeeds; `_orders[commitment][USDC]` accumulates escrow across both legs into the single bucket (no separate accounting per index).
3. A solver calls `fillOrder` supplying `options.outputs` that fully satisfy both DAI legs in the same call, so both `i=0` and `i=1` reach `amountFilled == totalRequired` inside `_fillSameChain`.
4. Both loop iterations compute `escrowedInputs[i].amount = _orders[commitment][USDC]` (same full balance, e.g. 1000 USDC), and both entries are passed to a single `_withdraw` call.
5. `_withdraw`'s first iteration zeroes `_orders[commitment][USDC]`; the second iteration hits `if (escrowed == 0) revert UnknownOrder();`, reverting the entire `fillOrder` transaction.
6. Every subsequent attempt to complete both legs together reproduces the identical revert, leaving the order's USDC escrow permanently unredeemable via that completion path. [6](#0-5)  confirms no equivalent input-token dedup exists, and [7](#0-6)  shows the vulnerable withdrawal accounting.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

            uint256 amount = body.tokens[i].amount;

            _orders[body.commitment][token] = escrowed - amount;

                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
