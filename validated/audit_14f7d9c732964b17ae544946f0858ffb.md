### Title
`placeOrder` in the Tron `IntentGatewayV2` never refunds leftover `msg.value`, permanently locking native tokens sent alongside ERC20 deposits - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` tracks `msgValue` throughout escrow accounting exactly like the mainline EVM contract, but is missing the final "refund unspent native tokens" step that the mainline EVM contract has. Any native token sent by a caller in excess of what is consumed by native inputs/fees (e.g., a caller who mistakenly attaches `msg.value` while funding purely ERC20 inputs, or overestimates the fee-swap cost) is silently retained by the contract with no path to reclaim it — directly analogous to the reported OpenQ issue where protocol tokens sent alongside an ERC20 deposit become permanently stuck because the code path that tracks and refunds them is missing.

### Finding Description
In `placeOrder`, `msgValue` is initialized to `msg.value` and decremented as it's consumed for native inputs (`evm/tron/contracts/apps/IntentGatewayV2.sol:388-469`) and for the fee-token swap (`evm/tron/contracts/apps/IntentGatewayV2.sol:471-488`). After the fee-swap branch, the function immediately emits `OrderPlaced` and returns [1](#0-0)  — there is no `if (msgValue > 0) { ... refund ... }` step.

Compare this to the mainline (non-Tron) `evm/src/apps/IntentGatewayV2.sol`, which performs the identical `msgValue` accumulation but explicitly refunds any leftover native token to the caller before returning: [2](#0-1) . The Tron contract lacks this refund entirely, even though it has the same `msgValue` bookkeeping pattern used elsewhere in the codebase for exactly this purpose (e.g., `IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain` both refund unspent native tokens at the end: [3](#0-2) , [4](#0-3) ).

Concretely, if an order has no native (`address(0)`) inputs but the caller sends `msg.value > 0` (accidentally, or via a wallet/SDK bug/fee overestimate), the whole loop over `order.inputs` in the tron contract skips the native branch entirely (only the `else` ERC20 `safeTransferFrom` branch executes) [5](#0-4) , `msgValue` is never decremented for inputs, and if `order.fees == 0` it is never touched by the fee-swap branch either [6](#0-5) . The full `msg.value` sent is retained in the contract balance with no accounting entry (`_orders[commitment]` is only updated for ERC20/native inputs and `TRANSACTION_FEES`), so it can never be withdrawn by the depositor and is not claimable by anyone through normal contract functions.

### Impact Explanation
This causes concrete permanent loss of user funds (native TRX/ETH on Tron) with no recovery path — the same "protocol tokens sent by error, impossible to refund" class as the reported issue. Since `placeOrder` is a `payable` function callable by any unprivileged order-placer, this is directly and trivially reachable in normal usage (e.g., wallet UI bugs, users copying the EVM flow onto Tron, or minor `msg.value` overestimation for fee swap).

### Likelihood Explanation
High likelihood: `placeOrder` is the primary unprivileged entry point of the intents system, called on every order creation. Any caller who overestimates `msg.value` (common when quoting swap costs via `swapETHForExactTokens`, which can consume less than provided) or submits an order with only ERC20 inputs while still attaching value triggers the stuck-funds condition, with no special conditions required.

### Recommendation
Add the same refund step present in the mainline EVM contract to the Tron `placeOrder`, immediately after the fee-escrow block and before emitting `OrderPlaced`:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```
mirroring `evm/src/apps/IntentGatewayV2.sol:394-397`.

### Proof of Concept
1. Caller invokes `placeOrder(order, graffiti)` on the Tron `IntentGatewayV2` with `order.inputs` containing only ERC20 tokens (no `address(0)` entries) and `order.fees == 0`, but sends `msg.value = 1 TRX`.
2. Execution enters the `else` branch at `evm/tron/contracts/apps/IntentGatewayV2.sol:450-469`; since no input token is `address(0)`, `msgValue` (initialized to `1 TRX` at line 388) is never decremented.
3. Since `order.fees == 0`, the fee block at lines 471-488 is skipped entirely, so `msgValue` is untouched.
4. Function proceeds directly to `emit OrderPlaced(...)` and returns at `evm/tron/contracts/apps/IntentGatewayV2.sol:490-506` without refunding the `1 TRX`.
5. The `1 TRX` remains in the contract's balance permanently; no `_orders[commitment]` entry accounts for it, and no withdraw/cancel/fill path can return it to the caller.
