### Title
Webhook shop identity is derived from an unauthenticated HTTP header, not from the HMAC-covered payload, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but exposes `shop` (the tenant identity used by webhook handlers) from an unsigned HTTP header. Any party who can produce one valid `(body, hmac)` pair for the configured `api_secret_key` — for example by receiving a genuine webhook for their own shop if the app is publicly installable — can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only checks the signed field (`to_signable_string`, i.e., the raw body), and `Webhooks::Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` is the attacker-controlled header value.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from a request header with no cross-check against the HMAC-covered content: [2](#0-1) 

`HmacValidator.validate` verifies exactly and only `verifiable_query.to_signable_string` (the raw body) against the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [4](#0-3) 

The identity binding that should hold is:
```
shop attributed to the event (request.shop, used by the handler to scope tenant data)
==
shop that the HMAC-signed bytes actually originated from
```
That binding is broken: the HMAC signs only `@raw_body`; `shop` is parsed from an entirely separate, unsigned header. Consequently, "bytes verified" (the raw body) and "bytes/fields acted on" (the `shop` header used for tenant scoping) diverge — exactly the rounding/identity-mismatch bug class described in the referenced Surge report, applied here to the shop-header/HMAC-body binding instead of debt-shares/amount.

The test fixtures confirm this design as implemented: the HMAC is computed from the JSON body alone (`"{}"`), while `x-shopify-shop-domain` is a separate, independently-settable header value: [5](#0-4) 

### Impact Explanation
Any unprivileged internet user who can obtain one legitimately-signed `(body, hmac)` pair for the app (e.g., by installing the target app on their own store, if installs are public, and capturing one delivered webhook) can forge the `X-Shopify-Shop-Domain` header to any other tenant's domain and POST the same body+HMAC to the app's public webhook endpoint. Because `Registry.process` only re-validates the HMAC over the body and never checks that the header-derived `shop` corresponds to the shop that actually produced the signed bytes, the host application's webhook handler receives `WebhookMetadata` claiming the event came from the victim shop. If the host app uses `data.shop` to look up/scope the session, access token, or tenant-specific storage (the intended and documented use of `WebhookMetadata#shop`), this results in cross-tenant data injection/corruption under a victim's identity — satisfying the "cross-tenant access" High-impact category.

### Likelihood Explanation
Exploitation requires only:
1. Ability to obtain one authentic signed webhook body for the target app secret (trivial if app installs are open/public, since the attacker installs on their own store and receives a real webhook), and
2. Ability to POST arbitrary headers to the app's public webhook endpoint (webhook endpoints are, by design, internet-reachable and unauthenticated aside from the HMAC check).

No access token, `client_secret`, or privileged access is required — only participation as a normal merchant/installer of the target app, which is the standard multi-tenant SaaS threat model this gem is meant to defend against.

### Recommendation
Bind the `shop` identity into the value that is actually verified, or otherwise cryptographically/authoritatively confirm the header against a value under the server's control (e.g., by requiring apps to check `request.shop` against the shop associated with an already-known session/access-token record before trusting it, or by including the shop domain in the HMAC-signed payload comparison where feasible). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must never be used by itself to select which tenant's stored access token/session to act on without an independent authorization check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (assuming open/public installation, which is common for many third-party apps).
2. Shopify delivers a legitimate webhook to the attacker's own publicly reachable endpoint (or the attacker sets up their own receiving endpoint temporarily), giving them a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's real `api_secret_key`.
3. Attacker crafts a new HTTP POST to the target app's real webhook endpoint using the exact same `raw_body` and `x-shopify-hmac-sha256` header captured above, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` computes HMAC over `raw_body` only and it matches (same secret, same body) — validation succeeds.
5. `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)`, even though the payload never originated from, nor was ever validated against, `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
