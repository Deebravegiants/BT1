### Title
Accrued RAY market value overflows `i128` and permanently freezes a large dormant market - ([File: `common/src/rates/simulate.rs`])

### Summary
A user can create a sufficiently large, borrowing market within protocol-admitted caps, leave it to accrue at high utilization, and eventually make every market operation revert with `MathOverflow`. The root cause is that accrual computes `borrowed_shares * borrow_index` and `supplied_shares * supply_index` as fallible `i128` RAY values before capping utilization or the borrow index. Once either product exceeds `i128::MAX`, `accrue_step` panics, and every pool operation that performs `global_sync` first becomes unusable. [1](#0-0) [2](#0-1) 

### Finding Description
Supply, debt, revenue, and both indexes are stored as RAY-scaled `i128` values. Interest accrual first converts scaled debt and supply to original RAY values through `scaled_to_original`, which calls `Ray::mul`; `Ray::mul` delegates to `mul_div_half_up`, whose `I256` fallback still rejects results that do not fit `i128`. [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The borrow-index cap is applied only after the vulnerable total-value computations, so it cannot prevent this overflow. [7](#0-6)  `update_indexes` and every mutating pool path run `global_sync` before performing the requested operation; consequently, the first call that crosses the arithmetic boundary fails, and all later `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, flash, strategy, and `claim_revenue` calls touching the market fail identically. [2](#0-1) [8](#0-7) 

For an 18-decimal asset, a one-billion-token deposit is `10^36` RAY before index growth. Because `i128::MAX` is approximately `1.70e38`, the scaled debt exceeds the representable range when its borrow index is only about 170 for a 98%-utilized book, far below the configured `10^36` index ceiling. [9](#0-8)  The maximum admitted cap for 18 decimals is approximately 170 billion whole tokens, so this setup does not require an invalid cap. [10](#0-9) 

### Impact Explanation
This permanently freezes all funds and debt in the affected `(hub, token)` market once the boundary is crossed. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize underwater collateral, bad debt cannot be cleaned, and protocol revenue cannot be claimed because all of those flows accrue the market first. [8](#0-7)  The repository’s regression test demonstrates exactly this outcome: `update_indexes` fails with `MathOverflow`, followed by failed withdrawals and repayments. [11](#0-10) 

### Likelihood Explanation
The attack requires a very large deposit and enough collateral-backed debt to keep utilization high while the market remains untouched across multiple accrual chunks. No privileged action is required on a market whose configured caps admit the amounts, and the configured caps may legally reach the protocol’s arithmetic maximum. [12](#0-11)  The required capital and dormancy make the issue less likely on ordinary markets, but the failure is deterministic once the admitted balances and elapsed interest place `scaled * index` above `i128::MAX`. [13](#0-12) 

### Recommendation
Do not compute utilization or accrued totals by first reducing `scaled * index` to a single `i128`. Compute utilization from widened `I256` products or reduce the fraction before multiplication, saturate utilization at `RAY`, and similarly cap accrued debt and reward calculations before converting them back to `i128`. Entry caps should also be enforced against the maximum future representable position value, not merely against the initial token amount. Until indexed arithmetic is widened, provide a bounded recovery/sync path that can clamp indexes without evaluating an overflowing total claim.

### Proof of Concept
1. On an 18-decimal market with admitted caps near `max_cap_for_decimals(18)`, call `Controller::supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18)])`. This stores roughly `10^36` scaled supply RAY. [14](#0-13) [15](#0-14) 
2. Supply sufficient collateral in another market and call `Controller::borrow(caller, account_id, [(BIG18, 980_000_000 * 10^18)], None)` to leave the market at 98% utilization. [16](#0-15) 
3. Leave the market untouched while annual chunks compound. On each subsequent accrual, `global_sync` calls `accrue_step`; `accrue_step` evaluates `scaled_to_original(borrowed, borrow_index)` before applying the index ceiling. [17](#0-16) [18](#0-17) 
4. When `borrowed * borrow_index > i128::MAX`, `mul_div_half_up` returns `None` from its widened conversion and panics with `MathOverflow`. The committed regression test demonstrates that `update_indexes`, `withdraw`, and `repay` all subsequently revert. [6](#0-5) [11](#0-10)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
