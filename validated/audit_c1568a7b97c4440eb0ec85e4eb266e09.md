## Analysis

I traced the CVE's bug class (a missing validation that causes an unhandled crash when an edge-case input is reached) onto alt.fun's real attack surface: the permissionless, two-phase graduation flow in `Bonding.sol` and its interaction with `LPLock.sol`.

### Title
Unvalidated zero-liquidity edge case in `finalizeGraduation` → `LPLock.recordLock` permanently bricks a graduating token — (File: `packages/contracts/src/Bonding.sol`, `packages/contracts/src/LPLock.sol`)

### Summary
`Bonding.finalizeGraduation` seeds the HyperSwap V2 LP via `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`, then unconditionally calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)` with whatever `liquidity` that chain returns [1](#0-0) . `LPLock.recordLock` reverts with `ZeroAmount()` whenever `amount == 0` [2](#0-1) . The contract's own natspec on `_swapBudget` documents that an "extreme hostile pre-seed" can drive the rebalance swap to consume 100% of one side, causing `_routerDepositAndDispose` to skip `addLiquidity` and `finalizeGraduation` to return `liquidity = 0` [3](#0-2) . The 1%-reservation in `_swapBudget` is offered only as an informal mitigation ("Reserving 1% guarantees the deposit leg always lands"), not as a mathematically proven invariant, and `AGENTS.md` explicitly states the dedicated end-to-end test suite that used to pin these hostile-pre-seed properties (`test/HostilePreSeed.t.sol`) "was removed for runtime reasons after deployment... no longer enforced by automated tests" [4](#0-3) .

### Finding Description
- `_enterGraduating` (phase 1) is permissionless-triggerable via `Bonding.triggerGraduation` or inline on a threshold-crossing buy, and flips `Lifecycle.Curve → Graduating`, draining the curve and caching `tokensForLP`/`ltFromPair` [5](#0-4) .
- `finalizeGraduation` (phase 2) is permissionless and is the *only* path back out of `Lifecycle.Graduating` [6](#0-5) . Once `pendingGraduation[token]` is set, no other function can re-derive different `tokensForLP`/`ltFromPair` values — every retry of `finalizeGraduation` replays the identical cached inputs against the identical (attacker-controlled) HyperSwap pair state.
- An attacker who front-runs the HyperSwap pair with an extreme, massively imbalanced mint pre-seed (documented explicitly in the contract's own comments as the scenario the 1% `_swapBudget` reservation exists to prevent) can — if that mitigation does not close every edge case across the `uint112` reserve space and the closed-form `_noFeeSwapInput` math — force `_routerDepositAndDispose` to return `liquidity == 0`.
- `finalizeGraduation` passes that `0` straight into `LPLock.recordLock`, which now reverts on `amount == 0` [7](#0-6) . Because `finalizeGraduation` has no fallback, no parameter to retry with a different liquidity target, and `pendingGraduation` isn't cleared until *after* `recordLock` succeeds, every future call to `finalizeGraduation` for that token hits the exact same revert deterministically.
- The contract's own design philosophy states brick-resistance "ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever" [8](#0-7)  — yet the `ZeroAmount` guard in `LPLock.recordLock` directly contradicts that guarantee for exactly the zero-liquidity edge case the natspec itself describes.

### Impact Explanation
If this edge case is reachable, the token becomes permanently stuck in `Lifecycle.Graduating`: buys and sells on the curve are frozen (`TokenIsGraduating` reverts on both), the drained curve LT (`ltFromPair`) and 250M reserved tokens sit unusable inside `Bonding` with no rescue path, and the LP can never be locked or opened. This is a permanent freeze of trader, creator, and LP funds for that token — the exact class of impact the rules require (concrete permanent freezing), reached entirely through permissionless calls (`triggerGraduation`/a normal buy, then `finalizeGraduation`).

### Likelihood Explanation
Reaching the precise `liquidity == 0` boundary requires an attacker to construct pre-seed reserves at the extreme tail of the `_noFeeSwapInput`/`_pairRebalance`/`_routerDepositAndDispose` math (near `uint112` limits or extreme ratio skew) such that the 99%-capped rebalance swap still consumes an entire side. This is a narrow, gas-/capital-intensive edge case, and the team's own comments suggest the 1% reservation was added specifically to close it. I could not fully trace `_routerDepositAndDispose`'s exact arithmetic in this session to conclusively prove or disprove that the 1% margin is always sufficient across the full input domain — the removed `HostilePreSeed.t.sol` suite means this property is no longer regression-tested, so likelihood should be treated as **uncertain/low-but-unverified** rather than confirmed.

### Recommendation
Add an explicit invariant/require in `_routerDepositAndDispose` (or `_seedUniswapV2Direct`) proving `liquidity > 0` before returning, with a documented fallback (e.g., a minimum-liquidity floor analogous to V2's `MINIMUM_LIQUIDITY`) rather than allowing a `0` to propagate into `LPLock.recordLock`. Alternatively, have `LPLock.recordLock` accept `amount == 0` as a valid (empty) lock rather than reverting, so a defensive zero-liquidity result degrades gracefully instead of permanently bricking `finalizeGraduation`. Restore or replace `test/HostilePreSeed.t.sol` with fuzz coverage that sweeps pre-seed reserves across the full `uint112` domain and asserts `finalizeGraduation` never reverts and always yields `liquidity > 0`.

### Proof of Concept
Conceptual PoC (requires confirming the exact reserve ratio that saturates the 1%-capped rebalance swap, which I was unable to fully derive in this session):
1. Launch a token normally; let it reach `Lifecycle.Curve`.
2. Front-run: attacker calls `factory.createPair(token, lt)`, then transfers an extreme, maximally-skewed `(tokenReserve, ltReserve)` pair to the HyperSwap pair and calls `pair.mint(attacker)`.
3. Trigger phase 1 via a normal buy or `Bonding.triggerGraduation(token)`, caching `tokensForLP`/`ltFromPair`.
4. Call `Bonding.finalizeGraduation(token)`. If the pre-seed ratio is extreme enough that `_pairRebalance`'s 99%-capped swap consumes 100% of one side, `_routerDepositAndDispose` returns `liquidity == 0`, and `LPLock.recordLock` reverts with `ZeroAmount()`.
5. Every subsequent call to `finalizeGraduation(token)` reverts identically — the token is permanently stuck in `Lifecycle.Graduating`.

    /// @notice Permissionless trigger for phase 1 of graduation. Same flow as
    ///         the inline post-buy trigger inside `_executeBuy`, but callable
    ///         without any buy. Closes the case where `canGraduate` is true
    ///         (LT appreciation pushed the curve past the USD threshold) but
    ///         the closing buy on the curve would mint below the BounceTech
    ///         LT mint floor and revert with `BelowMinTransactionSize`,
    ///         making the token un-graduatable via `Zap.buy`.
    /// @dev    `_enterGraduating` reads pair reserves and the launch-time
    ///         virtual reserve only — it does not depend on a buy having
    ///         just landed, so the same logic is safe to expose as a
    ///         standalone entry point. The lifecycle pre-checks mirror
    ///         `Bonding.buy`; the launch trading delay is intentionally
    ///         not enforced because `canGraduate` already requires either
    ///         the USD threshold or full curve sellout, both of which are
    ///         unreachable from a fresh launch within the delay window.
    function triggerGraduation(
        address tokenAddress
    ) external nonReentrant {
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (info.creator == address(0)) revert TokenNotTrading();
        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();
        if (!canGraduate(tokenAddress)) revert NotGraduatable();
        _enterGraduating(tokenAddress);
    }

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. In either case `_pairRebalance` returns `false`, and `_seedRebalancing` overpowers the dust with a direct `transfer + pair.mint` at the cached `tokensForLP / ltFromPair` ratio (`_seedDirectMint`), opening the pool on-ratio. This is safe specifically because the swap only rounds to zero when the reserves are negligible against this graduation's inventory: the V2 `min()` donation to the attacker's pre-existing LP is then bounded by `max(reserveToken/tokensForLP, reserveLT/ltFromPair)`, which vanishe ... (truncated)
- **`_routerDepositAndDispose` uses `min0=1, min1=1`.** Slippage protection on `addLiquidity` exists to defend against a third party moving the pool ratio between quote and execution; here we set the ratio ourselves in `_pairRebalance` in the same atomic tx, so there's no third party to defend against. The `=1` (rather than `=0`) trips V2's degenerate-ratio guard so the call can't silently land at near-zero.
- **No external dependency on the router slot being correct post-deploy.** `uniswapV2Router` is set at `initialize` time alongside `uniswapV2Factory` and is rejected if zero. There's no live setter — rotation requires a UUPS upgrade so the change is visible on-chain ahead of any in-flight graduation.

Tested end-to-end by the brick-resistance regression tests in `test/TwoPhaseGraduation.t.sol` (notably `test_brick_resistance_frontRun_dust_seed`).
