### Title
Webhook `shop` (tenant) is trusted from an HTTP header that is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body, not this header. This breaks the intended equality `shop authenticated == shop bound by HMAC`, allowing the shop attribution of an otherwise-legitimately-signed webhook payload to be forged.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw JSON body — none of the HTTP headers, including the shop domain, are included in the signed string: [2](#0-1) 

Yet the `shop` value that downstream handler code receives and treats as the authenticated tenant identity is read straight from the unauthenticated header: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately hands `request.shop` to the registered handler as the trusted tenant identifier, with no additional check that ties the shop header to the signature: [4](#0-3) 

Because the HMAC only proves "this body byte-string was signed by someone holding `api_secret_key`" and says nothing about which shop the header claims to be from, an entity that has received one legitimately-signed webhook (e.g., from their own store, which any merchant/developer can install the app on) can replay the identical `body` + `hmac` pair while substituting an arbitrary `shopify-shop-domain` header value. The signature will still validate, and the library will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body came from a different shop than it actually did — a `shop authenticated` (header) vs. `shop bound by HMAC` (nothing, since HMAC covers no shop field) mismatch.

### Impact Explanation
Applications built on this gem rely on `request.shop` (exposed via `WebhookMetadata#shop`) as the trusted, per-tenant identity for routing webhook effects (e.g., updating shop-scoped state, triggering uninstall cleanup, fulfilling GDPR/compliance webhooks, etc.), because the library markets HMAC validation as the authenticity guarantee for a webhook. Since the shop header is not bound to that signature, an attacker who legitimately receives webhooks for their own shop can forge the tenant attribution of that payload to any other shop, causing the host application to act on wrong-tenant data — a cross-tenant confusion/injection primitive.

### Likelihood Explanation
Any developer/merchant can install the target app on a shop they control and thus legitimately receive real, validly-signed webhook deliveries (body + HMAC) from Shopify. Replaying that captured body/HMAC pair to the same webhook endpoint with a modified `shopify-shop-domain` header requires no secrets and no privileged access — only the ability to send an HTTP request, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string used by `HmacValidator`, or otherwise cryptographically bind the shop header to the payload before trusting it (e.g., look up the expected shop for the topic/registration and compare, or require the host application to independently verify `request.shop` against a known-installed shop list before using it). At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted as a tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC over `B`).
2. Attacker resends the exact same HTTP POST to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H` — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled webhook content as if it originated from `victim-shop`. [5](#0-4)
