Audit Report

## Title
Unauthenticated `PublicKeyGet` requests can squat owner-prefixed vault request IDs, enabling unprivileged denial-of-service against targeted vault owners - (File: core/services/gateway/handlers/vault/handler.go)

## Summary
The Vault gateway handler stores both unauthenticated `PublicKeyGet` requests and authorized, owner-prefixed secrets requests (`SecretsCreate/Update/Delete/List`) in the same `activeRequests` map keyed by `req.ID`. Because `PublicKeyGet` skips authorization entirely and uses the raw, attacker-controlled `req.ID` as the key, while authorized secrets requests are later assigned the deterministic ID `authorizedOwner + "::" + originalRequestID`, an unauthenticated attacker can pre-register that exact ID and block the legitimate owner's request from ever reaching the vault DON.

## Finding Description
In `HandleJSONRPCUserMessage`, the `MethodPublicKeyGet` branch is handled before any authorization, and when the public-key cache is empty it calls `h.newActiveRequest(req, callback)` directly with the caller-supplied `req.ID`, with no ownership stamping: [1](#0-0) 

All other vault methods go through `h.requestProcessor.ProcessRequest`, which authorizes the caller and rewrites `req.ID` in `authorizeAndStamp` to `authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` before the ID is inserted into the same map via `newActiveRequest`: [2](#0-1) [3](#0-2) 

`RequestIDSeparator` is the fixed, public constant `"::"`: [4](#0-3) 

Both paths write into the identical map, and `newActiveRequest` rejects any request whose ID already exists, returning an error rather than queuing/merging: [5](#0-4) 

The existing test confirms this "duplicate ID" behavior denies the second submitter's request rather than gracefully handling the collision: [6](#0-5) 

Because owner addresses are public and request IDs used by legitimate clients are frequently predictable, an attacker can precompute `owner::guessedID` and submit it as a `PublicKeyGet.ID` ahead of the victim's request, causing `newActiveRequest` to reject the victim's authorized request with `"request ID already exists"` once the processor stamps it to the same key.

This path is real but is gated by a cache guard the developers explicitly added: the `PublicKeyGet` branch only calls `newActiveRequest` with the attacker's raw ID when `h.getCachedPublicKey()` returns nil, i.e., before the public key has been successfully fetched and cached (aggressively, per the inline comment) — otherwise requests are served synchronously from cache without touching `activeRequests` at all: [7](#0-6) . The periodic refresh ticker that populates this cache runs on a 1-minute interval and does not fire immediately on startup, and it uses its own internally generated UUID request ID (not user input) for its own `fetchVaultPublicKey` calls: [8](#0-7) [9](#0-8) . This means the exploitable window is real but bounded — primarily the interval before the first successful public-key fetch after gateway startup, or any period during which fetches from DON nodes are failing — rather than a permanently open window during normal steady-state operation. Additionally, even a successfully squatted entry is cleaned up by `removeExpiredRequests` after the configured request timeout (default 30s), so the attacker must also win a timing race within that window.

## Impact Explanation
This is a genuine, code-confirmed design flaw: two distinct security domains (unauthenticated public-key requests and owner-authorized secrets requests) share one ID keyspace with a fully attacker-controlled key on one side and a deterministic, guessable key on the other. Where exploitable, it allows an unauthenticated actor to deny a specific vault owner's `SecretsCreate/Update/Delete/List` request without any credentials — a legitimate gateway request-impersonation/DoS class of issue. The impact is real but constrained to the (narrower than claimed) window where the gateway's public-key cache is empty, which is not the default steady-state condition for a running gateway.

## Likelihood Explanation
Exploitation requires: (1) no authentication, (2) knowledge of the target's owner address (public) and the exact request ID the victim will use (often predictable/sequential, but not guaranteed), (3) that the gateway's public-key cache is currently empty (startup window or fetch failure, not the normal running state), and (4) winning a race to land the squat within the request's ~30s timeout before the victim's request. This is a plausible but narrower and less "always-on" attack surface than the report implies, since the report's own cited code includes a caching guard specifically intended to limit this exposure.

## Recommendation
Segregate the request-ID namespace by security domain regardless of cache state — e.g., prefix all `PublicKeyGet` request IDs with a reserved marker, use a separate map for unauthenticated requests, or reject any client-supplied ID that contains `vaulttypes.RequestIDSeparator` before insertion into `activeRequests`. This closes the cross-domain collision entirely rather than relying on the incidental protection of the public-key cache.

## Proof of Concept
1. Restart (or otherwise force cache invalidation on) the gateway so `h.cachedPublicKeyGetResponse` is nil, per `getCachedPublicKey` in `core/services/gateway/handlers/vault/handler.go`.
2. Before the periodic 1-minute refresh populates the cache, send an unauthenticated JSON-RPC request `{"method":"vault.publicKey.get","id":"0xVictim::1"}` to the gateway; this inserts `activeRequests["0xVictim::1"]` via `newActiveRequest` without authorization.
3. Have the victim submit `vault.secrets.create` with `id:"1"` and owner `0xVictim`; after authorization, `authorizeAndStamp` rewrites the ID to `"0xVictim::1"`, and `newActiveRequest` returns `"request ID already exists"`, blocking the victim's request from being forwarded to the vault DON — reproducible as a Go unit test extending `handler_test.go`'s existing "duplicate requestId" test to interleave an unauthenticated `PublicKeyGet` call with the cache forced empty.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
