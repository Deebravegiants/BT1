### Title
Locally-Computed Signup Success Bypasses Backend Verification for User-Centric Signups - ([File: src/plans/mod.rs])

### Summary
In `do_signup`, when a signup is flagged as `user_centric_signup`, the Orb decides signup success/failure purely from its own locally-computed `signup_reason` instead of submitting to and polling the backend for the actual enrollment verdict, unlike the standard path which calls `enroll_user` (which performs `signup_post::request` + `signup_poll::request` against the backend). This mirrors the Gravity `sendToCosmos` bug class: a locally claimed/derived value is trusted and propagated as ground truth instead of the value the receiving system (the backend / Cosmos side) actually observed and confirmed.

### Finding Description
The normal signup flow submits credentials to the backend and polls for a confirmed status, letting the backend authoritatively decide success, including checks for duplicates, in-flight matches, legacy signups, and backend-side fraud: [1](#0-0) [2](#0-1) 

However, for `user_centric_signup`, this backend round-trip is skipped entirely, and `success` is derived solely from the Orb-local `signup_reason` (computed from local pipeline/fraud results): [3](#0-2) 

The `signup_reason` itself is computed earlier purely from local state (`pipeline.is_none()` / local `fraud_detected`): [4](#0-3) 

Meanwhile, the personal custody package (biometric data) is still uploaded to the backend regardless of whether `user_centric_signup` is set: [5](#0-4) 

This creates an accounting mismatch between what the Orb locally attributes as a successful/failed signup and what the backend's own signup-processing pipeline (duplicate detection, in-flight-match detection, backend fraud checks — enumerated in the comments of `enroll_user.rs`) would have determined, because that backend pipeline is never invoked or consulted for user-centric signups. [6](#0-5) 

### Impact Explanation
Just as Gravity's `sendToCosmos` let the Ethereum side self-report a locked amount that Cosmos would trust without verifying the true balance delta, here the Orb self-reports "signup success" without ever asking the backend to confirm/reject via its actual verification logic (duplicate/fraud/in-flight detection). This can lead to a signup being recorded/attributed as successful locally (driving UI completion, `debug_report.signup_successful()`, and downstream success metrics/state) that the backend's authoritative signup pipeline would have rejected as a duplicate, fraud, or in-flight match, and vice versa — a misattributed signup outcome/state bleed between the Orb's local view and the backend's system of record. [7](#0-6) 

### Likelihood Explanation
This path is gated by a boolean coming from backend-provided `UserData.user_centric_signup` and an orb-side config flag `ignore_user_centric_signups`, so it is reachable whenever the backend/app enables user-centric signup mode and the Orb config does not override it — an unprivileged-user (app-triggered) code path, not an operator/admin-only path. [8](#0-7) [9](#0-8) 

### Recommendation
For `user_centric_signup` flows, still perform (or require an equivalent) round-trip confirmation with the backend's signup verification pipeline before marking the signup as successful, rather than trusting the Orb-local `signup_reason` alone — analogous to measuring the actual post-transfer balance instead of trusting the pre-transfer requested amount.

### Proof of Concept
Not applicable — this is a logic/trust-boundary analysis based on the code paths in `src/plans/mod.rs` and `src/plans/enroll_user.rs` shown above; no dynamic PoC was executed.
