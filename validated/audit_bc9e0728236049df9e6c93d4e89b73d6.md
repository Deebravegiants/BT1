### Title
Webhook shop identity spoofing — HMAC does not bind `X-Shopify-Shop-Domain` to the signed payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then hands the caller-supplied `shop` header value straight to the app's handler as the tenant identifier. The `shop` field is never covered by the HMAC computation, so the value that determines *which tenant* the webhook is attributed to is not bound to the value that was actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an HTTP header and is never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `request.hmac` against `HMAC(secret, request.to_signable_string)` — i.e. only the body bytes: [3](#0-2) 

`Registry.process` uses this validation result as its only authentication check, then forwards `request.shop` (the unauthenticated header) into `WebhookMetadata`, which is delivered to the app's handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

The equality the design implicitly claims to hold is:
`shop that received the webhook == shop attributed to the verified body`

But the actual invariant enforced is only:
`HMAC(secret, raw_body) == received_hmac`

Since `api_secret_key` is a single **app-level** secret shared across every shop that has installed the app (not per-shop), any merchant who has installed the app can generate a validly-signed webhook body of their own (by triggering a real event in their own store) and then replay that exact `raw_body` + `hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Registry.process` will accept it as valid (HMAC matches) and hand the handler a `WebhookMetadata` claiming the payload belongs to a different, attacker-chosen shop.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to scope tenant data (the officially documented usage pattern, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` shown in the gem's own docs) can be tricked into writing/processing another merchant's data under an attacker-controlled shop identifier, or into impersonating an arbitrary shop domain (including one the attacker does not control) since the header is fully attacker-supplied and carries no cryptographic binding to the signed body. This is a cross-tenant identity-binding failure: an unprivileged actor (any merchant who has installed the app) can attribute an otherwise-legitimate signed payload to a different tenant.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app on their own store (or otherwise triggers/observes one legitimate webhook delivery for any topic), (2) the attacker replays the same raw body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint with a modified `x-shopify-shop-domain` (and optionally `webhook-id`, which is also unauthenticated) header. No access to `api_secret_key`, access tokens, or the target shop is required. The only variable is whether the downstream application relies on `data.shop` for tenant scoping without independent verification — which is exactly the pattern the gem's own documentation recommends.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified material, or perform an out-of-band check that the resolved `shop` from the header corresponds to a shop domain the application has an active, previously-established session/installation for, before trusting it in `WebhookMetadata`. At minimum, update `Utils::VerifiableQuery#to_signable_string` for webhook requests to include the `shop-domain` header (if Shopify's signing algorithm supports it) or explicitly document that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against known installed shops before being used for any tenant-scoped action.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com"
# and receives a legitimately-signed webhook for topic "orders/create":
raw_body = '{"id":1,"note":"hello"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
) # only computable by Shopify, but attacker legitimately receives this via their own install

# Attacker replays the identical body+hmac, but forges the shop-domain header
# claiming it originated from a different, unrelated tenant:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,           # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id"   => "any-value",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (it only checks raw_body),
#    handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
#    is invoked, attributing attacker-controlled data to "victim-shop.myshopify.com".
``` [4](#0-3)
