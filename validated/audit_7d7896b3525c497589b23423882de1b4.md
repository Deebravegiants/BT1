### Title
POA Bridge `describeWithdrawal` misattributes completion status/txHash between distinct same-asset withdrawals in a batch — ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches the withdrawal record returned by the POA indexer using only `assetId`, via `findMatchingWithdrawal`, and ignores the caller-supplied `index`, `destinationAddress`, and `amount`. When a single NEAR transaction contains two or more withdrawals of the same asset (a legitimate batch-withdrawal scenario the SDK itself supports and documents), each `describeWithdrawal({ index, withdrawalParams })` call for that tx will return the *same first-matching* withdrawal record, so the txHash/status reported for withdrawal `index=1` (to destination B) can actually be the outcome of withdrawal `index=0` (to destination A).

### Finding Description

and is called from `describeWithdrawal` without any additional disambiguation by `index`, `destinationAddress`, or `amount`: [2](#0-1) 

The code comment explicitly acknowledges the gap: "Currently only matches by assetId... This means multiple withdrawals of the same token in a single transaction are not supported." [3](#0-2) 

This breaks the equality that the status/txHash reported for a given `WithdrawalIdentifier` (tx hash + index + params) must correspond to the on-chain outcome for *that specific* withdrawal request. Instead, `Array.prototype.find` returns the first record in an unordered API response whose `near_token_id` matches the asset — which, for two same-asset withdrawals to different `destinationAddress`/`amount` in one NEAR tx, is not guaranteed (and is not checked) to be the correct one.

Contrast this with `OmniBridge.describeWithdrawal`, which selects the transfer by `args.index` directly from the array returned by `getTransfer` [4](#0-3)  — i.e., index-based selection is the pattern used elsewhere in this codebase, but POA bridge substitutes an assetId-only match instead, which is not unique when duplicate assets appear in a batch.

### Impact Explanation
If an integrator batches multiple withdrawals of the same asset to different destination addresses/amounts in one NEAR transaction (the SDK's README documents batch fee estimation/withdrawal support), polling `describeWithdrawal` for each `WithdrawalIdentifier` can report "completed" with a txHash that actually belongs to a different withdrawal in the batch. An integrator relying on this status to credit a user or mark a withdrawal as delivered could:
- Prematurely mark withdrawal B as completed using the txHash that actually settled withdrawal A (double-crediting/mis-crediting risk), or
- Report the wrong tx hash for a given destination, misleading reconciliation/support/auditing systems.

This matches the "status or hash misreport making an integrator credit or refund twice" impact category (High).

### Likelihood Explanation
Requires the integrator to submit ≥2 withdrawals of the identical `assetId` within a single NEAR transaction routed through the POA bridge — a normal batch-usage pattern already supported by the SDK's withdrawal APIs, not an attacker-controlled or malicious-actor scenario. No malicious input is needed; ordinary correct usage triggers the misattribution because the matching key is not unique in this case.

### Recommendation
Disambiguate `findMatchingWithdrawal` using more than `assetId`: incorporate `destinationAddress` (`args.withdrawalParams.destinationAddress` vs `withdrawal.data.address`) and/or `amount`, or track per-tx withdrawal ordering/index if the POA API can supply a stable ordering key. At minimum, when multiple candidates match the same `assetId` for a given tx hash, the bridge should refuse to guess (return `pending`/throw) rather than silently returning a possibly-wrong record, until the API provides an unambiguous identifier.

### Proof of Concept
1. Submit a single NEAR transaction containing two withdrawal intents for `nep141:btc.omft.near`: withdrawal A → `destinationAddress: addrA`, withdrawal B → `destinationAddress: addrB`.
2. Both create `WithdrawalIdentifier`s sharing `tx.hash` but with `index: 0` and `index: 1` respectively, via `createWithdrawalIdentifier` (which itself doesn't encode a unique per-index key into `describeWithdrawal`'s lookup).
3. The POA indexer eventually returns `withdrawals: [ { ..., near_token_id: "btc.omft.near", data.address: addrA, transfer_tx_hash: "hashA" }, { ..., near_token_id: "btc.omft.near", data.address: addrB, transfer_tx_hash: "hashB" } ]` (order not guaranteed to match submission order).
4. Calling `describeWithdrawal` for identifier B (`index: 1`, `destinationAddress: addrB`) still runs `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which returns the *first* array element — potentially the record for `addrA`/`hashA` — reporting `{ status: "completed", txHash: "hashA" }` for what is actually withdrawal B, regardless of the true destination or completion state of B.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
