### Title
Webhook shop identity is trusted from an unauthenticated header while only the raw body is HMAC-covered, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw request body only, while the `shop` (merchant) identity is taken straight from an HTTP header that is never included in the signable string. Any party who can obtain one validly-signed webhook (trivially possible by installing the app on their own store) can replay that request to the app's public webhook endpoint while substituting the `shop` header for an arbitrary victim shop domain. The signature still validates because the body — the only thing signed — was untouched, but `ShopifyAPI::Webhooks::Registry.process` and the app's webhook handler will act as if the message came from the victim shop.

### Finding Description
The identity binding that should hold is:
`shop that produced a valid HMAC == shop the handler acts on`

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only ever hashes `verifiable_query.to_signable_string` (i.e., the body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` to build the metadata handed to the app's handler, without any further binding check: [4](#0-3) 

Because `Context.api_secret_key` is the app's single client secret shared across every shop that installs the app (not a per-shop secret), any unprivileged internet user can:
1. Install the target app on a store they control (a free/dev store), which causes Shopify to send them a webhook with a valid HMAC signature computed with the app's real `api_secret_key` over a body the attacker fully controls (e.g. `orders/create`, `app/uninstalled`).
2. Capture that request (valid `hmac-sha256` header + `raw_body`).
3. Replay the identical body/HMAC pair to the app's public webhook endpoint, but change only the `shopify-shop-domain` header to a victim shop's domain.
4. `Utils::HmacValidator.validate` returns `true` (body untouched, signature matches), and `Registry.process` forwards `WebhookMetadata.new(topic:, shop: <victim-shop>, body: <attacker-controlled>, ...)` to the host app's handler.

### Impact Explanation
This breaks the shop authentication vs. shop-acted-upon binding required by the rules. A handler that keys state by `data.shop` (e.g., processing `app/uninstalled` to purge/deactivate a merchant's stored session, or writing order/product data keyed by shop) can be made to act on an arbitrary victim shop using attacker-controlled payload content, resulting in cross-tenant data corruption or forced deactivation without ever needing the victim's credentials or access token — only the ability to install the app on any store. This satisfies the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
High: installing an app on a self-owned/free development store is unauthenticated, unprivileged, and available to any internet user; no leaked secrets, tokens, or social engineering are required. Forging HTTP headers on an HTTP POST to a public webhook URL is trivial once one legitimately-signed body/HMAC pair is obtained.

### Recommendation
Bind the `shop` (and ideally `topic`) into the HMAC-covered payload, or otherwise cryptographically tie the header-derived shop to the authenticated request (e.g., verify the shop against a per-shop registration/webhook-id lookup before dispatch), rather than trusting the unauthenticated `shopify-shop-domain` header directly in `Webhooks::Request#shop`.

### Proof of Concept
```
# 1. Attacker installs the app on attacker-shop.myshopify.com and receives:
POST /webhooks
x-shopify-topic: app/uninstalled
x-shopify-hmac-sha256: <valid HMAC of body, computed with the app's shared api_secret_key>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {}

# 2. Attacker replays the exact same body + hmac header, only changing the shop header:
POST /webhooks
x-shopify-topic: app/uninstalled
x-shopify-hmac-sha256: <same valid HMAC as above>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: {}

# HmacValidator.validate(request) => true (body unchanged)
# Registry.process dispatches WebhookMetadata(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)
# Host app's handler purges/deactivates victim-shop's session/data based on forged "shop".
```
