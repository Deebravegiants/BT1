### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, allowing webhook forgery for arbitrary shops - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook to a tenant are read from unauthenticated HTTP headers. `Registry.process` validates only the body-HMAC and then trusts these header-derived values, breaking the intended binding `hmac == sign(shop, topic, body)` down to `hmac == sign(body)`.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only this body-scoped HMAC, then immediately trusts `request.shop` (and `request.topic`) to construct the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity equality that should hold is: `hmac_valid(body) ⇒ (shop, topic) authentic`. In reality the code only proves `hmac_valid(body)`; the `shop`/`topic` used by the app for tenant attribution are asserted from attacker-controllable transport headers, not from the signed payload. An unprivileged internet user who obtains any single valid `(body, hmac)` pair signed by the app's `api_secret_key` — trivially available by installing the app on their own free/dev shop and capturing one legitimate webhook delivery — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` still succeeds because it only checks the body bytes, so `Registry.process` will invoke the registered handler with attacker-chosen `shop`/`topic` values alongside the attacker's own body content.

### Impact Explanation
This breaks the tenant/shop identity binding that host apps rely on to key persistence, authorization, and mandatory-compliance flows (e.g. `shop/redact`, `customers/redact`, `customers/data_request`, `app/uninstalled`). An attacker with only their own (free) shop installation can forge webhook events "as" any other shop domain string, causing the app to write attacker-supplied data into another tenant's records, trigger uninstall/redaction side effects against a victim shop, or otherwise cross tenant boundaries — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or the app's `client_secret` — only the ability to install the target app on any shop the attacker controls (to harvest one valid HMAC/body pair) and the ability to POST directly to the app's public webhook endpoint with forged headers, both of which are available to any unprivileged internet user/merchant.

### Recommendation
Bind the shop and topic identity into the signed material, or otherwise independently authenticate them: e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (matching the same fields Shopify signs), or require the caller/host app to verify that the header-derived `shop` corresponds to a shop with an active installation/session before trusting it, rather than passing it through unauthenticated to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify send a real webhook; attacker captures the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header value `H` (computed by Shopify over `B` with the app's `api_secret_key`).
2. Attacker sends a POST to the app's registered webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a `Request` whose `hmac` still validates against `B` per `HmacValidator.validate`, per [4](#0-3) .
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, `topic: forged_topic`, causing the app to act on behalf of a shop the attacker never installed on.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
