### Title
Webhook shop/topic identity spoofing due to HMAC binding only the raw body, not the tenant headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw HTTP body, while `topic`, `shop`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only verifies the body against the HMAC and never binds the header values into that signature. `Webhooks::Registry.process` then trusts `request.topic` for handler dispatch and `request.shop` as the tenant identity forwarded to the handler, after HMAC validation has passed.

### Finding Description
The identity binding that should hold is:
`shop header used by the app == shop that produced/owns the HMAC-signed body`

In `to_signable_string`, only `@raw_body` is included: [1](#0-0) 

`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all pulled from headers, none of which participate in the signed content: [2](#0-1) 

`HmacValidator.validate` verifies only `to_signable_string` (the body) against the secret-derived signature — it never checks that the `shop`/`topic` headers correspond to the signer: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` — both header-derived and unverified — to route to a handler and populate `WebhookMetadata`: [4](#0-3) 

Because the signature covers only the body, any two requests with an identical body and a genuinely-computed HMAC for that body will pass validation regardless of what `shop`, `topic`, `webhook_id`, or `api_version` headers accompany it. An attacker who legitimately installs the app on their own shop (an "unprivileged internet user" with no access to the target's credentials or the app's `client_secret`) will receive real webhook deliveries with valid `body` + `hmac` pairs for their own tenant. They can then replay that exact `body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is authentic), and `Registry.process` forwards the forged `shop` value into the handler as if it were authenticated.

### Impact Explanation
This is a cross-tenant identity spoof: the app's webhook handler receives `WebhookMetadata.shop` claiming to be a shop the attacker does not own, backed by a signature that only proves body authenticity, not shop identity. Any handler logic keyed on `request.shop` (e.g., looking up per-shop state, correlating orders/customers, triggering actions using that shop's stored session/access token) can be made to act against the wrong tenant using attacker-supplied body content. This satisfies the Critical impact category of cross-tenant access.

### Likelihood Explanation
High: no secret material, session, or victim credential is required. The only prerequisite is that the attacker can install the app on any shop (including a free/trial shop) to receive a legitimately signed webhook, and can send arbitrary HTTP headers to the app's public webhook endpoint (which this gem does no additional header/shop-authentication for beyond the flawed HMAC check).

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signable content, or otherwise cryptographically bind them to the payload before dispatch, so that `HmacValidator.validate` fails if any of these headers are altered independently of the signed body. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for tenant-sensitive routing unless they are covered by the verified signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the genuine `raw_body` and `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it was computed by Shopify with the app's real secret over that body.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. The registered handler for `orders/create` executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-controlled body content, even though the signature never bound the shop or topic to that value (`lib/shopify_api/webhooks/registry.rb:188-199`).

          received_signature = verifiable_query.hmac
