### Title
Webhook `shop` identity is unauthenticated by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` object that includes `shop`. In reality, the HMAC signature only covers the raw request body — the `shop` value is read directly from an unauthenticated HTTP header. Any party who can obtain one valid `(body, hmac)` pair (trivially, by triggering a webhook on a shop they legitimately control) can replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `Utils::HmacValidator.validate` still passes because it never inspects the shop header, so the app's handler receives forged, cross-tenant data as if it were authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and compares it against the supplied `hmac`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request — including `request.shop` — is legitimate, then forwards `request.shop` straight into `WebhookMetadata` for the app's handler: [4](#0-3) 

The gem's own documentation reinforces this misleading equality — it states that calling `process` "will verify the request did indeed come from Shopify" and shows `data.shop` used directly as the shop identity for enqueuing follow-up work, with no mention that `shop` is unauthenticated: [5](#0-4) [6](#0-5) 

**Broken binding:** the gem implies `HMAC_valid(request) ⇒ shop == request.shop is authentic`, but the actual equality enforced is only `HMAC_valid(request) ⇒ body is authentic`. `shop` is a field acted on (used as the tenant key by every downstream consumer of `WebhookMetadata`) but not covered by the HMAC — exactly the class of binding break this scan targets.

### Impact Explanation
Every app using `shopify_api` for multiple shops (the normal use case) relies on `data.shop` from `Registry.process` to route webhook data to the correct tenant. Since `shop` isn't authenticated, an attacker who controls one shop (e.g., installs the app on their own free/dev store, which is available to any unprivileged internet user) can capture a valid `(body, hmac)` pair from their own webhook traffic and replay it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. The app will process it as authentic data for the victim shop, causing cross-tenant data injection/confusion — e.g., a forged `orders/create` or `app/uninstalled` payload attributed to a shop the attacker does not control. This satisfies the "cross-tenant access" Critical-impact bar, since it lets an unprivileged user cause the app to act on/associate data with a different tenant without that tenant's credentials.

### Likelihood Explanation
High. No secrets are required beyond installing the app on any shop (including the attacker's own), which is a routine, unprivileged action. Capturing a legitimate webhook is trivial (trigger `orders/create` on your own store), and replaying it with a different `Shop-Domain` header requires only a basic HTTP client — the gem performs no additional integrity check tying header claims to the signed body.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the HMAC-covered signable string, or otherwise cryptographically bind them to the verified body, before exposing them via `WebhookMetadata`. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not authenticated by the HMAC and that apps must independently verify the shop against their own installed-shop/session store before trusting it as a tenant identifier.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# triggers a legitimate webhook (e.g. orders/create), capturing:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the SAME body+hmac but spoofs the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,      # still valid: body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds because only raw_body is signed:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process hands the forged shop straight to the app's handler:
ShopifyAPI::Webhooks::Registry.process(request)
# handler receives data.shop == "victim-shop.myshopify.com", fully attacker-controlled
```

```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
