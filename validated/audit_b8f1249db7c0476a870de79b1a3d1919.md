### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` verifies solely that the *body bytes* were signed by the app's `client_secret`. The `shop-domain` header, however, is read unauthenticated and forwarded as the trusted tenant identifier to the app's webhook handler. This mirrors the H-19 pattern: a field that is *acted upon* (used to resolve which tenant a request belongs to) is not *covered* by the integrity check that is supposed to bind it.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

`shop` is pulled straight from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then dispatches to the handler using the unauthenticated `request.shop`: [3](#0-2) [4](#0-3) 

**Broken binding (equality that should hold but doesn't):**
`shop header used by handler == shop that the signature actually authenticates`
In reality the signature only authenticates: `HMAC(client_secret, raw_body) == received hmac`. The `shop-domain` header is disjoint from that computation.

Because Shopify signs webhooks per-app with the single shared `client_secret` (not per-shop), any merchant who installs the app receives HMAC-valid webhook deliveries for their own store. Since that merchant fully controls the HTTP request reaching the app's endpoint (they can intercept/replay/craft it, e.g. by re-sending the exact `raw_body` + `hmac-sha256` header they legitimately received but substituting a different `shop-domain` header value), the resulting `ShopifyAPI::Webhooks::Request` still passes `HmacValidator.validate` (body+hmac unchanged) while `request.shop` now claims to be an arbitrary other tenant known to the app (e.g., a victim shop that also installed the app).

`Registry.process` has no additional check that the claimed `shop` is the one that actually produced the signed body: [5](#0-4) 

The handler receives `WebhookMetadata` built from this unauthenticated `shop`, so any application logic that partitions/writes tenant data keyed by `data.shop` (the intended and documented usage pattern of this API) will attribute attacker-controlled webhook body content to the spoofed victim shop.

### Impact Explanation
This crosses a tenant boundary the gem is supposed to enforce as part of its webhook-verification contract: an attacker (any merchant who has installed the app) can make the library hand off attacker-chosen `topic`/`body` content labeled as belonging to a different shop to the application's webhook handler. This is a cross-tenant identity-binding bypass — the exact bug class targeted (field acted upon but not covered by the authentication check) — and matches the "cross-tenant access" Critical impact category, since it lets one tenant inject data processed under another tenant's identity without needing that tenant's or Shopify's secret.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even trial/free) installer of the target app — no `api_secret_key`, access token, or privileged account is needed, and no TLS interception or social engineering is required. They only need one genuine webhook delivery to their own shop to obtain a valid `(raw_body, hmac)` pair, then can replay it with a substituted `shop-domain` header to any endpoint the app exposes for webhook processing. Likelihood is Medium-High given the low bar to entry (self-installation) and the widely documented reliance on this exact `Registry.process`/`Request` flow.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise require `Registry.process` to cross-check `request.shop` against a shop identity known independently of client-supplied headers (e.g., the session/shop the webhook was registered against) before invoking the handler. At minimum, document prominently that `request.shop` is unauthenticated and must be revalidated by the host application against its own installed-shop records before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app, signed with the app's shared `client_secret`:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - Body: attacker-controlled JSON (attacker crafts the order/customer data they control on their own store).
3. Attacker captures `raw_body` and `hmac-sha256` header value (both intact/untouched — HMAC only signs body).
4. Attacker crafts a new HTTP request to the app's webhook endpoint reusing the same `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts it; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, raw_body)` — passes.
6. `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: attacker_json, ...))` is invoked — the app processes attacker-controlled data as if it came from `victim.myshopify.com`, breaking the tenant isolation the webhook shop field is relied upon to provide.
