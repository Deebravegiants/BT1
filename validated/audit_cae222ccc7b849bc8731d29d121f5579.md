### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `Webhooks::Request` / `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Registry.process` reads the tenant identity (`shop`) from a separate, unsigned HTTP header before invoking the app's handler. The HMAC that `Utils::HmacValidator.validate` checks therefore authenticates the payload bytes, but not the `shop` field that the app acts on to bind the webhook to a tenant.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are read straight from HTTP headers via `shopify_header`: [3](#0-2) 

`Registry.process` validates only this body-derived HMAC, then immediately forwards the header-derived `shop` to the app's handler as the tenant identifier: [4](#0-3) 

`WebhookMetadata.shop` is a plain struct field with no cryptographic binding to the signature: [5](#0-4) 

The equality that should hold is: `shop-domain header value == shop bound by the HMAC signature`. In this implementation that equality is never checked — the HMAC only proves `raw_body` was signed with `api_secret_key`; it says nothing about which shop the header claims to be. Because `api_secret_key` is shared across every shop that installs the app, any shop that installs the app receives its own validly-signed webhook payloads and can capture a valid `(raw_body, hmac)` pair. That party can then replay the same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header for a different, victim shop's domain. `HmacValidator.validate` still passes (it never looks at headers), and the app's handler receives `WebhookMetadata` claiming the payload belongs to the victim shop.

Downstream apps are documented to trust `data.shop` directly for tenant-scoped operations (e.g., enqueuing background jobs keyed by shop, as shown in the gem's own docs), so this header-vs-signature mismatch is a direct cross-tenant identity-binding break, matching the report's "field acted on but not covered by the HMAC" bug class.

### Impact Explanation
This allows a malicious or compromised merchant (who legitimately installed the app and thus can generate real, HMAC-valid webhook bodies for their own shop) to make the app believe an event happened for a different tenant (shop) of their choosing. Any app logic that uses `WebhookMetadata#shop` to scope writes, fulfil orders, update per-shop billing/state, or route the payload to shop-specific storage can be tricked into cross-tenant data corruption or disclosure. This qualifies as Critical (cross-tenant access) per the scope's impact classification, since the trust boundary between tenants is broken purely by manipulating an unauthenticated header.

### Likelihood Explanation
Likelihood is Medium-High for any app that has multiple shop installations (nearly all Shopify apps) and that trusts `data.shop` in the handler, which is exactly the pattern the gem's own documentation recommends (`docs/usage/webhooks.md`, "Create a Webhook Handler" example). The attacker needs only an existing (non-privileged) installation of the same app on any shop and the ability to POST an HTTP request to the app's public webhook callback endpoint with modified headers and a body/HMAC pair replayed from a webhook they legitimately received for their own shop — no access to `api_secret_key`, access tokens, or any other shop's credentials is required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, not just the raw body. At minimum, the gem should:
1. Extend `Webhooks::Request#to_signable_string` (or add an additional check in `Registry.process`) to also validate that the shop the app expects/has a webhook registration record for matches the header-supplied `shop`, cross-checked against server-side state (e.g., only accept webhooks for shops with an active session/subscription), or
2. Document explicitly and prominently that `shop` in `WebhookMetadata` is unauthenticated header data and must not be trusted as a tenant boundary without additional verification (e.g., checking that the shop is a known, currently-installed shop before doing shop-scoped work), since Shopify's HMAC scheme by design only covers the body.

### Proof of Concept
1. App has two shop installations: `attacker.myshopify.com` (attacker-controlled) and `victim.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com`, e.g. `orders/create` with body `B` and header `X-Shopify-Hmac-Sha256: H` (H = HMAC-SHA256(api_secret_key, B)), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `B` and `H` (trivial, since the webhook is delivered to their own endpoint or they control network access to their own shop's webhook flow).
4. Attacker crafts a new HTTP POST to the app's public webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and compares to `H` — this succeeds because only the body is signed.
6. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and performs shop-scoped work under the victim's identity, even though the event actually originated from/was crafted by the attacker. [4](#0-3)
