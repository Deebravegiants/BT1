### Title
Draining an Aquarius pool below `min_pool_value_wad` bricks liquidation and bad-debt cleanup of every account holding its LP token - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
Any account that holds even a dust supply position in an Aquarius LP collateral becomes permanently unliquidatable — and un-cleanable — once the underlying Aquarius pool's measured value falls below `min_pool_value_wad`. An unprivileged actor can trigger this with their own liquidity withdrawal on Aquarius (an in-scope "own trades on Aquarius" action). The borrower can also deliberately add a dust LP leg to their own account, then pull their own liquidity from that pool, shielding their debt from liquidation, permissionless `clean_bad_debt`, and even the owner-gated `force_socialize_bad_debt`, leaving bad debt stuck on the book.

### Finding Description
`aquarius::read` computes the pool's total value in WAD and rejects the price when it falls under the configured floor: `if pool_value_wad < lp.min_pool_value_wad { return Err(OracleError::InsufficientAquariusLiquidity); }` [1](#0-0) . LP price reads are strict: leg resolution errors propagate via `engine::resolve_nested(session, &lp.key_a, depth + 1)?`, so there is no fallback to a cached price [2](#0-1) . On the controller side, `liquidate` builds the plan and risk totals through `Context`-cached strict price reads — `build_liquidation_plan` over every collateral leg and `calculate_account_risk_totals` over all supply/borrow positions — so one unreadable collateral price aborts the whole transaction [3](#0-2) [4](#0-3) . The protocol's own threat model documents this precise chain: "Supply needs no price, so an indebted borrower can add a dust leg of any listed collateral and choose which feed outage shields the account. For an Aquarius LP leg, liquidity providers can cause that outage by withdrawing pool value below `min_pool_value_wad`. The same leg blocks bad-debt cleanup and force-socialization" [5](#0-4) ; INV-LIQ-04 confirms both cleanup paths require "valid required prices" and only `force_socialize` (owner-gated) omits the dust cap — but it still cannot run while a collateral price fails [6](#0-5) . Because `supply` lets anyone top up an existing position and lets a borrower open the dust leg themselves, no privileged action is needed [7](#0-6) .

### Impact Explanation
An insolvent or about-to-be-insolvent account holding the LP collateral cannot be liquidated, cannot be permissionlessly cleaned via `clean_bad_debt`, and cannot be force-socialized — every path reverts on `InsufficientAquariusLiquidity`. The debt accrues interest while its collateral is frozen on the book, producing protocol insolvency: suppliers' claims in that market absorb an ever-growing hole that no keeper or owner action can close while the pool stays thin (and an attacker can keep it thin by re-draining the shallow pool each time it refills). This is attacker-caused unavailability, not a passive oracle outage.

### Likelihood Explanation
The attacker needs only: (a) a listed Aquarius LP collateral whose pool is shallow enough to push below `min_pool_value_wad` — a configured value that exists per-market in the deployed configs (multiple mainnet ops files set it) — and (b) LP shares in that pool, which are freely acquirable. Cost is bounded by the pool's depth at the moment of attack, which for a thin pool is small; alternatively the borrower is themselves a liquidity provider and pays nothing beyond swap fees. The trigger requires no privileged role, no leaked key, and no oracle dishonesty — the aggregator correctly refuses to price a nearly-empty pool.

### Recommendation
- Give `clean_bad_debt`/`force_socialize` a degraded path that prices the LP collateral at zero (or skips unreadable legs) rather than reverting, since cleanup only needs the debt legs valued — the dust collateral is confiscated anyway.
- Alternatively, bound LP-collateral influence: when a pool fails the liquidity floor, treat a below-threshold leg as zero-value collateral in `calculate_account_risk_totals` and `build_liquidation_plan` so a single dust leg cannot veto pro-rata seizure of other collateral.
- Enforce a minimum pool depth/`min_pool_value_wad` relative to the total LP supply admitted as collateral at listing time, and alert when live pool value approaches the floor.

### Proof of Concept
1. Governance has listed Aquarius LP token `LP_AB` (pool `P`, `min_pool_value_wad = M`) as collateral in some spoke; attacker is an LP of `P` holding enough shares that withdrawing drops pool value below `M`.
2. Attacker supplies a dust amount of `LP_AB` to their own account via `controller::supply`, then borrows a different asset via `controller::borrow` up to the threshold.
3. Attacker calls `P.withdraw(...)` on Aquarius directly, pulling reserves until `price_wad * total_shares / share_unit < min_pool_value_wad` [8](#0-7) .
4. The borrowed asset's price rises (or interest accrues) until `HF < 1`. Any liquidator's `controller::liquidate(account_id, payments, SeizeMode::Transfer)` reverts inside `build_liquidation_plan` when the `LP_AB` leg's strict price read returns `InsufficientAquariusLiquidity` [9](#0-8) .
5. `controller::clean_bad_debt(account_id)` and owner `force_socialize_bad_debt(account_id)` also revert — both require valid required prices for every leg [6](#0-5) .
6. Attacker re-drains `P` whenever LPs refill it, keeping the account permanently unclosable while debt accrues — bad debt is stranded and socialization is impossible.
