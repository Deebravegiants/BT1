This confirms the design: `Webhooks::Request#to_signable_string` returns only `@raw_body` (line 37 of `lib/shopify_api/webhooks/request.rb`), while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers via `shopify_header` with no HMAC coverage.### Title
Webhook shop/topic/webhook_id forgery via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` never covers `shop`, `topic`, or `webhook_id`, all of which are read unauthenticated from HTTP headers via `shopify_header`. Since the app's `api_secret_key` is shared across every shop that installs the app, an attacker who legitimately installs the app on their own development store can capture a real, validly-signed webhook body+HMAC pair and replay that exact body to the same public webhook endpoint with a forged `X-Shopify-Shop-Domain` header, causing `Registry.process` to accept the request and invoke the host app's handler with attacker-controlled `shop`/`topic`/`webhook_id` values.

### Finding Description
Binding claimed broken: `shop_signed_by_hmac == shop_acted_upon`, i.e. the value of `shop` that was cryptographically bound into the HMAC signature must equal `Webhooks::Request#shop` used by the host application. Trace:

- `Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controlled headers via `shopify_header`, with no cryptographic linkage: [2](#0-1) 
- `Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., `@raw_body`) and compares it to the received HMAC — `shop` never enters this comparison: [3](#0-2) 
- `Registry.process` gates on `HmacValidator.validate(request)` succeeding, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the host app's handler: [4](#0-3) 
- The gem's own documentation instructs developers to treat `data.shop` as trustworthy shop attribution after this check, calling it verification "the request did indeed come from Shopify": [5](#0-4) 

Root cause: because the app's `api_secret_key` (`Context.api_secret_key`) is identical for every shop that installs the app, any shop — including one the attacker controls — can generate a validly-HMAC-signed `raw_body`. Since the signature covers only the body, that same signed body/HMAC pair remains valid no matter what `shop-domain`, `topic`, or `webhook-id` header is attached to the replayed request. Existing guards do not close this gap: `HmacValidator.validate` only proves the body wasn't tampered with and was signed with a secret the attacker also legitimately possesses (via their own installed instance); it makes no claim about header authenticity, and no other check in `Registry.process` cross-validates `shop` against a known/expected value.

Exploit flow:
1. Attacker installs the target app on their own development shop (`attacker.myshopify.com`) as a normal unprivileged user.
2. Attacker triggers a real webhook event and captures the callback: `raw_body` and its genuine `X-Shopify-Hmac-Sha256` header (validly signed with the app's real `api_secret_key`).
3. Attacker resends the identical `raw_body` (and thus identical HMAC) to the same publicly reachable webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `raw_body` alone, matches, and returns `true`.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the host app's handler, which — per the gem's documented usage — treats this as an authenticated event for the victim shop.

### Impact Explanation
An attacker can inject webhook payloads that the host application attributes to any shop domain of their choosing, including shops they've never installed the app on. Depending on how the host app uses `data.shop`/`data.body`/`data.webhook_id` (e.g., updating shop records, triggering fulfillment or billing side effects, marking data deleted for GDPR-style mandatory webhooks), this can corrupt or leak another tenant's data, or cause actions to be performed under a victim shop's identity — a cross-tenant integrity/confidentiality violation. This is repeatable against arbitrary victim shop domains with a single captured signed payload, since the same HMAC/body pair can be replayed with any forged `shop-domain` header.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's capability: create a free development store, install the target app, receive one legitimate webhook, and know the app's public webhook callback path (documented and typically predictable, e.g., `/callback/orders/create`). No secrets, tokens, or victim cooperation are required. The webhook endpoint must be reachable directly over HTTP without additional shop-binding checks by the host app — which matches the gem's own documented "process a webhook" pattern that relies solely on `Registry.process`/`HmacValidator.validate`.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signable string, or otherwise require the host application to independently verify that `request.shop` corresponds to a shop that is known to have this specific `webhook_id` registered (e.g., by tracking webhook subscription IDs per shop at registration time and rejecting mismatches in `Registry.process`). At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop`/`data.topic`/`data.webhook_id` are not covered by the HMAC and must not be trusted without additional shop-specific validation.

### Proof of Concept
```ruby
# test/webhooks/request_spoofed_shop_test.rb
require "test_helper"

class SpoofedShopWebhookTest < Minitest::Test
  def test_hmac_valid_despite_forged_shop_domain
    body = '{"id":1,"note":"attacker-owned-order"}'
    hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

    # attacker's own genuinely-signed webhook body/hmac pair,
    # replayed with a forged shop-domain header
    headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => Base64.encode64(hmac),
      "x-shopify-shop-domain" => "victim.myshopify.com", # forged, not attacker's real shop
      "x-shopify-webhook-id" => "forged-id",
    }

    request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)

    # binding check: shop_signed_by_hmac (none) != shop_acted_upon
    assert(ShopifyAPI::Utils::HmacValidator.validate(request))
    assert_equal("victim.myshopify.com", request.shop)
  end
end
```
This demonstrates `HmacValidator.validate` returns `true` for a body legitimately signed under the app's secret while `request.shop` reflects an arbitrary, attacker-forged domain — proving the HMAC provides no binding between the signed payload and the shop attribution consumed by `Registry.process`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
