## Analysis

The external report's root cause is that a value the protocol *acts on* (`DISPUTED_L2_BLOCK_NUMBER`) is not itself covered by the binding that is supposed to make the claim trustworthy (the claimed L2 block number), letting one game's inputs be replayed/misinterpreted in a different context. The direct analog in this gem is in the webhook verification path: the `shop` identity that the library hands to application webhook handlers is **not** covered by the HMAC that proves the request came from Shopify. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Webhook `shop` identity is not covered by HMAC, enabling cross-tenant webhook payload replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (from the `x-shopify-shop-domain` header) is read separately and never included in the signed material. `Registry.process` validates the HMAC over the body only, then passes the *unauthenticated* `request.shop` straight to the application's webhook handler as the tenant identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` derive the signature check purely from `@raw_body`: [4](#0-3) 

`Request#shop`, `#topic`, `#api_version`, `#webhook_id` are all pulled from headers that are outside the signed data: [5](#0-4) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it with the provided `hmac`: [6](#0-5) 

`Registry.process` accepts the request once the body HMAC checks out, and then forwards `request.shop` (an unauthenticated header value) to the handler as the tenant identifier: [3](#0-2) 

The equality the code implicitly (and incorrectly) assumes is:
`shop used by handler (header value) == shop that Shopify actually attests to via the HMAC`

But the HMAC only proves `secret` knows `raw_body`; it says nothing about which shop that body belongs to. Since the `client_secret`/HMAC key is shared across every shop that has installed the app (not per-tenant), any actor who can obtain one legitimate `(raw_body, hmac)` pair for a webhook addressed to a shop they control (e.g. their own dev/test store, or a store where they operate the multi-tenant Rails app that embeds this gem) can replay that exact HTTP body and its valid HMAC to the app's live webhook endpoint while substituting a different value in the `shopify-shop-domain` header. The HMAC check still passes (body unchanged), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, while the payload content actually originated from the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook delivery: an unprivileged (with respect to other tenants) but legitimate app-installing merchant can cause the application to process attacker-supplied webhook content under another shop's identity. Depending on the handler logic (e.g., orders/customers/app-uninstalled/GDPR handlers keyed off `shop`), this enables cross-tenant data injection or state corruption — matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be able to observe one valid `(raw_body, hmac)` pair addressed to a shop they control (trivially achievable by installing the app on their own store and capturing the outbound webhook POST at their own infrastructure/proxy in a self-hosted or dev-store scenario) and then send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or TLS interception of third-party traffic is required — only network access to the app's own public webhook URL, which is by design internet-reachable.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, e.g. include the `x-shopify-shop-domain` (and other identifying headers) inside `to_signable_string`/the HMAC context, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before invoking the handler, rather than trusting the header value once only the body HMAC has been checked.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers an `orders/create` webhook (e.g., by placing an order), capturing the exact raw POST body and its `x-shopify-hmac-sha256` value sent to their own hosted instance of the app (or intercepted via a local proxy/dev tunnel they control).
2. Attacker sends that identical `raw_body` and `hmac` to the same production webhook endpoint, but replaces the `x-shopify-shop-domain` header with `victim.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [7](#0-6) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's order data>, ...)`, causing the application to treat attacker-controlled content as belonging to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
