### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only. The `shop-domain` header — which the library uses to attribute the webhook payload to a specific merchant — is never included in the signed bytes, so it is never verified. Since the same `api_secret_key` is shared across every shop that has the app installed, any merchant that legitimately receives genuine webhooks for their own store can replay one with a forged `shop-domain` header and have it processed as if it belonged to a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read straight from the (unsigned) header: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string`, i.e. the body bytes only, with no binding to any header: [3](#0-2) 

`Webhooks::Registry.process` checks only that this body-only HMAC is valid, then trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because `api_secret_key` is one shared secret for the whole app (not per-shop), any shop that installs the app receives real, validly-signed webhook deliveries from Shopify. A malicious merchant can capture one such delivery (body + `x-shopify-hmac-sha256`) and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. The HMAC check still passes — it only validates that the body was signed with the app's secret, not that this particular body is tied to this particular shop — and `Registry.process` will dispatch the handler with `shop: <victim-shop>`, `body: <attacker-controlled-but-signed data>`.

This is the same bug class as the referenced report ("a field acted upon but not covered by the HMAC/signature"): in the analog, the mint amount is used but not signed; here, the tenant identity (`shop`) is used to route/attribute data but not signed.

### Impact Explanation
Any app built on this gem that keys per-shop state, webhook idempotency, or business logic off `WebhookMetadata#shop` (as the library's own documented `handle(data:)` contract encourages) can be made to apply another merchant's genuine event data to a different tenant, or to process attacker-chosen (but genuinely-signed) event bodies under a victim shop's identity. This is a cross-tenant access issue: an app-level merchant can affect the data/state that another tenant's app records show for events like `orders/create`, `app/uninstalled`, `customers/redact`, etc., depending on how the host app consumes `WebhookMetadata`.

### Likelihood Explanation
Exploitation requires only that the attacker has (or can create) their own shop with the target app installed — a normal, unprivileged position for any internet user who installs a public app — plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers. No access to `api_secret_key`, tokens, or the merchant's Shopify admin credentials is required.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) into the signed material, or otherwise cryptographically bind the header to the body before trusting it — e.g. include the shop domain in `to_signable_string`, or independently verify (via a stored, per-shop session/webhook registration) that the signing secret used matches the shop claimed in the header before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a real webhook, e.g.:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id": 1, ...}`
2. Attacker resends this exact body and HMAC to the app's public webhook route, only replacing the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) passes because it only checks the body against the secret, ignoring the header.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the host application to process/attribute the attacker's payload as belonging to the victim shop.
