### Title
Bounded state-commitment eviction lets any relayer purge commitments other pending proofs still need, denying message delivery - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp` keeps only a fixed number of verified state-machine commitments per source chain (`BoundedStateCommitments`, capped by `StateMachineCommitmentCap`/`MAX_STATE_MACHINE_COMMITMENTS`), evicting the oldest heights via a FIFO queue whenever a new consensus update is stored [1](#0-0) . Eviction happens inside `insert_bounded_state_commitment`, which is invoked unconditionally on every consensus update, independent of whether relayers still have in-flight requests/GET-responses whose membership/non-membership proofs are anchored at the heights being evicted [2](#0-1) .

### Finding Description
`handle_unsigned` is a permissionless, unsigned extrinsic: anyone who can produce a valid consensus proof can submit it for free [3](#0-2) . Each accepted consensus message can advance a state machine by many intermediate heights in one call, and `update_client` stores every new height's commitment via `store_state_machine_commitment` → `insert_bounded_state_commitment` [4](#0-3) . That insert path appends to a small FIFO (`StateCommitmentQueue`) and evicts from the head once the per-chain cap is exceeded, removing `BoundedStateCommitments`/`BoundedStateMachineUpdateTime` entries for the oldest heights [5](#0-4) .

Nothing in this eviction path checks whether a height still has outstanding requests/responses that were dispatched against it, or whether the configured challenge period for that height has even elapsed yet. Because any unprivileged party can submit consensus proofs (batched, in quick succession, or after having withheld several valid updates and posting them all at once) they can drive many insertions in a short span and push the queue head past heights that relayer proofs are still targeting. This is analogous to the CVE-2024-45802 Squid bug class: an entity that legitimately controls "cache" state (here, whoever submits consensus proofs) can prematurely release a resource (a state commitment) that other clients (relayers delivering pending requests) still expect to be available for their "effective lifetime" (the delivery/challenge window), and there is no mechanism to release it only after that lifetime ends.

Downstream, `IHandlerV2`/`HandlerV2.sol` and its Substrate analogs reject any proof anchored at a height whose commitment can no longer be found (`StateCommitmentNotFound`), so a relayer holding a fully valid membership/non-membership proof for a pending request or GET-timeout can be permanently unable to deliver it once the source chain's bounded queue evicts that height [6](#0-5) . The pallet's own tests confirm evicted heights become permanently unprovable: `commitment_queue_evicts_oldest_when_cap_is_reached` shows old heights fail both commitment and update-time lookups after eviction [7](#0-6) , and `lowering_the_cap_drains_the_queue_gradually` shows the same effect when governance shrinks the cap [8](#0-7) . Migrations already acknowledge fast-finality chains (BSC, Polygon) need deeper caps precisely because the default cap is too shallow for their block cadence [9](#0-8) , which is exactly the situation an attacker can force artificially by batching/timing consensus submissions on any chain, not just naturally fast ones.

### Impact Explanation
If a state commitment needed to prove an in-flight request, GET-response, or timeout gets evicted before the request is delivered, that message becomes permanently unprovable via the normal membership/non-membership path — the route effectively becomes unable to deliver that message. Escrowed relayer fees (`fund_message` semantics) for that request are then unrecoverable ("lost forever" per the pallet's own documentation of that call) since the message can never be marked delivered or timed out through a state proof [10](#0-9) . This is a Denial-of-Service against message delivery and a form of fund freezing for the relayer/fee-payer, matching the required "permanent freezing of funds" / "route unable to deliver messages" impact bar.

### Likelihood Explanation
Submitting consensus proofs is fully permissionless and unsigned (free), so any actor — not just the source chain itself — can accelerate insertions into the bounded queue simply by batching or timing valid consensus updates. No privileged role is required; this is reachable by an ordinary relayer or bystander with access to publicly available consensus proofs, satisfying the "unprivileged... relayer" reachability requirement. The eviction logic itself is a normal part of every consensus update, so the attack surface is exercised continuously, not merely a theoretical edge case; the existing test suite already demonstrates the exact eviction/loss behavior under a lowered or reached cap.

### Recommendation
Do not evict a height's commitment purely by FIFO age. Track whether a height still has any known outstanding requests/responses/timeouts referencing it (or at minimum, do not evict a height until its type's maximum timeout/challenge period has elapsed since it was stored), and prefer widening/adaptive caps or backpressure (e.g., rejecting/delaying further consensus inserts) over silently destroying still-needed commitments. Alternatively, expose a way for relayers to "pin" or checkpoint proofs against a commitment before it can be evicted.

### Proof of Concept
1. Attacker (any account) accumulates several valid consensus proofs for a target state machine advancing multiple heights, or waits for several natural updates.
2. A relayer submits a message (e.g., a POST request or GET request) that is dispatched against height `H`, whose commitment is stored in `BoundedStateCommitments`.
3. Before the relayer submits its delivery proof, the attacker submits `handle_unsigned` consensus messages that push `CommitmentQueueStates` forward enough that `H` is evicted (see `insert_bounded_state_commitment`, and the eviction demonstrated in `commitment_queue_evicts_oldest_when_cap_is_reached`) [5](#0-4) .
4. The relayer's subsequent `handlePostRequests`/`handleGetResponses` call (or the pallet's `handle_unsigned` for a request/response message) now fails with `StateCommitmentNotFound` because `BoundedStateCommitments::get(H)` returns `None`, and the message can never be delivered through the normal proof path.

		/// Insert a state commitment into the bounded map. ISMP does not allow
		/// duplicate state updates so we don't have an overwrite path.
		///
		/// Appends the height to the per-chain [`StateCommitmentQueue`] and, once
		/// the chain's cap is exceeded, evicts oldest-first from the queue head.
		/// Evictions are limited to [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per
		/// call so a lowered cap drains over many insertions rather than in one.
		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}

#[test]
fn lowering_the_cap_drains_the_queue_gradually() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 8)]),
		)
		.unwrap();
		for height in 1..=8u64 {
			store(height);
		}
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 0, tail: 8 }
		);

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		// 9 live vs cap 2: only MAX_COMMITMENT_EVICTIONS_PER_INSERT entries are
		// evicted per insertion, so the excess drains over several insertions.
		store(9);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 4, tail: 9 }
		);
		store(10);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 8, tail: 10 }
		);
		store(11);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 9, tail: 11 }
		);
		// At the cap: steady state, one eviction per insertion.
		store(12);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 10, tail: 12 }
		);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 10 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
	})
}

	(StateMachine::Evm(137), *b"POLY", RETENTION_WINDOW_SECS * 1_000 / 2_000),
