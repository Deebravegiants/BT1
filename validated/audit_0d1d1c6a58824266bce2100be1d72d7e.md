### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload using only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the host application's handler. Because the identity of the tenant (`shop`) is never part of the signed bytes, any party who can produce one validly-signed `(body, hmac)` pair can replay that pair with a forged `shop-domain` header and have it accepted as coming from a different merchant.

### Finding Description
The equality that should hold is:

`bytes covered by HMAC == bytes the application trusts to identify the tenant (shop)`

In this gem that equality is broken: [1](#0-0) [2](#0-1) 

`hmac` is computed from headers, and `to_signable_string` returns only `@raw_body` — `shop`, `topic`, `webhook_id`, and `api_version` are excluded from the signed content.

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the `hmac`, i.e. it only authenticates the body: [3](#0-2) 

`Registry.process` then validates that HMAC and immediately trusts the unauthenticated `request.shop` header to attribute the payload to a merchant when dispatching to the handler: [4](#0-3) 

Because `shop` is not part of the signed bytes, the "bytes verified" (raw body only) diverge from the "bytes acted on for tenant identity" (`shop` header). Any actor who can obtain one legitimately-signed `(raw_body, hmac)` pair — for example, by installing the app on their own store and capturing a real webhook Shopify sends them, which requires no special privilege — can resend that identical body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. The HMAC still validates because it never covered the header, and the host application (via `WebhookMetadata#shop`) will process the attacker-controlled body as if it originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor (any merchant who has the app installed) can make the receiving application believe attacker-controlled webhook data belongs to a different, victim shop. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., writing merchant data, triggering fulfillment/billing logic, or looking up/mutating the victim's stored session or resources by shop domain), this enables cross-tenant data injection/confusion — matching the "cross-tenant access" Critical impact category, since the merchant/tenant identity binding used by every downstream consumer of the webhook is forgeable without the app's `client_secret`.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker must first obtain a validly-signed `(body, hmac)` pair. The most practical way is becoming a legitimate (even free-tier) merchant installer of the app and capturing one of the real webhooks Shopify sends to their own store — an action available to any unprivileged internet user, requiring no leaked credentials or access tokens. From there, replaying the header-swapped request against the app's public webhook endpoint is trivial.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable content that is authenticated, or independently bind/verify the `shop` header against another trusted source before dispatch (e.g., verify it matches a shop associated with the `webhook_id` via a server-side lookup, or adopt Shopify's recommended approach of treating the HMAC as proof-of-origin only and separately re-deriving/validating the shop via a signed claim). At minimum, document and enforce that `Registry.process` must not treat `request.shop` as authenticated tenant identity unless it is cryptographically bound to the payload.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw HTTP request Shopify sends, including the `X-Shopify-Hmac-Sha256` header and raw body.
2. Resend the exact same raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed with the forged shop header; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `raw_body`, which is unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-supplied data under the victim shop's identity.
