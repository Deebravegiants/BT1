### Title
Cross-signup biometric bundle bleed via time-only fence with no signup_id verification in `Plan::run` - (`src/plans/biometric_pipeline/mod.rs`)

### Summary
`biometric_pipeline::Plan::run` merges agent outputs into the pipeline being assembled purely based on message *type* and a time-based fence (`output.source_ts > fence`), never checking that the `signup_id` embedded in the original `face_identifier::Input::Estimate` request matches `self.signup_id` of the currently running `Plan`. Because `mega_agent_two` (and its underlying Python process) is a long-lived broker shared across signups rather than recreated per-`Plan`, a stale `face_identifier::Output::Estimate{fraud_checks, bundle}` computed for an aborted prior signup can be accepted into a new signup's `Pipeline` as long as its production timestamp is later than the new `Plan`'s fence.

### Finding Description
`Plan::run` builds its fence purely from wall-clock time at `Plan::new`/`run` start: `let fence = Instant::now();` [1](#0-0) . The generated broker code (from the `#[broker]` macro) discards agent outputs only when `output.source_ts <= fence`; anything with a later timestamp is accepted regardless of which request produced it: [2](#0-1) .

Inside the while loop, once a `ModelOutput::FaceIdentifier(face_identifier::Output::Estimate{fraud_checks, bundle})` is received, it is merged unconditionally: [3](#0-2) . Critically, `face_identifier::Output::Estimate` carries no `signup_id` field at all — the enum only round-trips `fraud_checks` and `bundle`: [4](#0-3) . This makes it architecturally impossible for `Plan::run` to verify the response corresponds to `self.signup_id`, even though the request that produced it carried `signup_id: self.signup_id.to_string()`: [5](#0-4) .

The `mega_agent_two` port/agent is a persistent broker field on `Orb`, not something recreated per `Plan`; `run_mega_agent_two` just sends into `orb.mega_agent_two.enabled()`: [6](#0-5) . If a signup is aborted while its `face_identifier::Input::Estimate` request is still being computed by the out-of-process Python agent, dropping the Rust `Plan::run` future cancels only the Rust-side await, not the already-dispatched computation in the separate agent process. When that stale computation later completes and is delivered on the shared port, a subsequent signup's `Plan::run` (with `fence` set after the stale send but before the stale response's `source_ts`) will accept it via `output.source_ts > fence` and merge signup A's `face_identifier_bundle`/`face_identifier_fraud_checks` into signup B's `Pipeline`, since nothing checks `signup_id`.

### Impact Explanation
This results in wrong-identity binding: person A's self-custody face identifier bundle (thumbnail/embeddings) and/or fraud check results get bound into person B's `personal_custody_package`/signup record. This is a genuine cross-signup identity binding and biometric-data-disclosure/contamination issue that could corrupt fraud detection and mis-attribute biometric identity artifacts between unrelated signups.

### Likelihood Explanation
Exploitability requires precise timing: an attacker (or even an ordinary user) triggering rapid signup abort/retry such that the Python agent's response for the aborted signup lags behind the fence set at the very start of the next `Plan::run`, and arrives (`source_ts`) after that new fence. This is plausible under normal load/latency variance for a `MODEL_TIMEOUT` of 90 seconds and any operator/UI-driven abort-and-restart flow, but it is a race condition dependent on process scheduling and channel/timestamp semantics of `agentwire`'s port implementation (`source_ts` assignment logic was not fully inspectable here). The lack of any `signup_id` field in `face_identifier::Output` is a structural gap independent of timing precision, which is the root enabler.

### Recommendation
Add `signup_id` to `face_identifier::Output::Estimate` (and ideally to all `mega_agent_two`/`mega_agent_one` outputs relevant to per-signup state) and have `Plan::run` reject/re-queue any output whose `signup_id` does not equal `self.signup_id`, instead of relying solely on the time-based fence. Alternatively/additionally, ensure that aborting a signup actively cancels or invalidates in-flight agent requests (e.g., via a generation/epoch counter checked on receipt) rather than relying only on `Instant`-based fencing.

### Proof of Concept
Integration test plan (would require access to a mocked `mega_agent_two` port, not available for direct verification in this pass):
1. Construct `Plan A` with `signup_id = A`, call `run_face_identifier` sending `Input::Estimate{signup_id: "A", ...}`, and capture the fence `t0`.
2. Simulate signup A being aborted, dropping `Plan A` before its response is consumed.
3. Construct `Plan B` with `signup_id = B`, set fence `t1 > t0`.
4. Have the mocked agent deliver `Output::Estimate{fraud_checks, bundle}` for the original request A at `source_ts = t2 > t1`.
5. Assert that `Plan B::run` rejects this output because it cannot verify (or, once `signup_id` is added to `Output`, because the embedded `signup_id != "B"`) — currently, the existing code will incorrectly accept it since only `source_ts > fence` is checked, demonstrating `Pipeline.face_identifier_bundle`/`face_identifier_fraud_checks` for `Plan B` ends up populated from data intended for `signup A`.
