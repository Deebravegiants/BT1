### Title
Webhook shop-domain spoofing via unauthenticated header not covered by HMAC — cross-tenant webhook confusion ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant) identifier used to dispatch and process the webhook is read from an HTTP header that is never included in the signed payload. This breaks the identity binding `hmac_verified(body) == authenticated(shop)`: the HMAC proves the *body* was produced with the app's shared secret, but it proves nothing about which shop the webhook is *for*. Anyone who can generate a genuinely-signed webhook for their own shop can relabel it as belonging to a different shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body: [2](#0-1) 

But `shop` — the tenant identity that gets forwarded to the app's webhook handler — is derived from the `x-shopify-shop-domain` header, which is completely outside the HMAC's coverage: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the HMAC and then dispatches using this unauthenticated `shop` value, with no cross-check binding it to the signed body: [5](#0-4) 

Because the HMAC secret (`Context.api_secret_key`) is shared across **every** shop that has the app installed, any unprivileged user can install the public app on their own store (a normal, unprivileged action) and receive genuinely-signed webhook deliveries for their own shop. Since the `shop` header carries no cryptographic binding to the signed body, the attacker can replay that same signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The signature will still validate (it only covers the body), and `Registry.process` will hand the forged event to the handler tagged with the victim's shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the app processes attacker-controlled data as if it originated from another merchant's shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g. `app/uninstalled` triggering deletion of the victim's stored session/access token, or order/customer/GDPR webhooks writing attacker data into the victim's tenant record), this can lead to cross-tenant data corruption or forced session/token invalidation for a shop the attacker does not control — satisfying the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` without independently reconciling it against previously known/installed shops for that specific webhook delivery: the attacker only needs (1) their own installation of the target app (trivial, unprivileged, self-service) to obtain a validly-signed body, and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified header — no access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically/administratively verify that the shop asserted in the header matches a shop that is actually expected to be delivering this specific signed payload (e.g., cross-reference against the app's installed-shop registry before trusting `request.shop`, rather than trusting the header value emitted purely from HMAC-over-body verification).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers/receives a legitimate webhook (e.g. `orders/create`) for their own shop; Shopify signs it with `HMAC-SHA256(api_secret_key, raw_body)` and sends headers including `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `raw_body` (and therefore the same valid `x-shopify-hmac-sha256`) to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks the body signature — this passes — and then calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, per: [6](#0-5) 
5. The host application's webhook handler processes attacker-supplied order/customer/uninstall data as belonging to `victim-shop.myshopify.com`.
