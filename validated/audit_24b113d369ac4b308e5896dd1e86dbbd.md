Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC at all [2](#0-1) . `Registry.process` validates only that the body's HMAC matches, then forwards the unauthenticated header-derived `shop` value straight to the app's handler as the tenant identifier [3](#0-2) .

### Title
Webhook `shop` identity is not covered by the HMAC, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the HMAC over the raw body only, but exposes a separate `shop` accessor sourced from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, which is never included in the signed material. `Registry.process` trusts this header value as the authoritative tenant identity when dispatching to the app's webhook handler.

### Finding Description
The binding that should hold is: `hmac_verified_bytes == identity_bytes_trusted`. Instead:
- `to_signable_string` returns `@raw_body` exclusively [1](#0-0) .
- `HmacValidator.validate` computes/compares the HMAC purely against that signable string [4](#0-3) .
- `shop` is parsed independently from an HTTP header that carries no signature coverage [2](#0-1) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` before handing `request.shop` to the handler as the trusted tenant identity in `WebhookMetadata` [3](#0-2) .

Because the shop header is excluded from the signed bytes, any entity that legitimately receives one genuine webhook (with a valid HMAC for its own body, e.g. a merchant who has the app installed on their own store and can observe/capture webhooks Shopify sends them) can replay the exact same raw body and HMAC value to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it never examines the header, so `Registry.process` will dispatch the (attacker-chosen) body to the handler labeled with the victim's shop.

### Impact Explanation
This breaks the identity binding "HMAC-authenticated bytes == shop identity trusted by the app," letting a low-privilege actor (any shop where the app is installed) inject falsely-attributed webhook events for an arbitrary other tenant. Depending on how the host app keys behavior/storage off `WebhookMetadata#shop` (e.g., updating records, triggering `shop/redact`/`customers/redact` compliance actions, provisioning), this can lead to cross-tenant data corruption or spoofed compliance/administrative actions attributed to a shop the attacker does not control — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Any merchant/developer with the app installed on their own store already receives genuinely-signed webhooks and can replay them with a modified header with a trivial HTTP client; no secrets, tokens, or elevated privileges are required beyond having the app installed somewhere (a normal, low-privilege position for an "unprivileged internet user" relative to other tenants).

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload verification, or independently authenticate `shop` against a known/installed shop list before trusting it, rather than deriving tenant identity solely from an unsigned header.

### Proof of Concept
1. App has webhooks enabled; attacker's own shop (`attacker.myshopify.com`) receives a legitimate webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's secret).
2. Attacker POSTs the same body `B` and same `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#to_signable_string` returns `B`; `HmacValidator.validate` recomputes HMAC over `B` and matches `H` — validation passes despite the header claiming a different shop.
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
