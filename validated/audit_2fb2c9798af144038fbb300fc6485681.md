## Title
Gas griefing via unbounded return-data copy in `EvmHost.dispatchIncoming` low-level module calls - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` (for both `PostRequest` and `GetResponse`) and `dispatchTimeOut` deliver cross-chain messages to destination modules via a raw `.call(...)` whose return value is captured as `(bool success,)`. Discarding the second tuple element does not avoid copying the returned bytes into memory — Solidity still ABI-decodes/copies the full `returndata` before it is dropped. Because `request.to` (the destination module) is attacker-controlled — any account can dispatch a POST request from a source chain addressed to a contract they deployed on the destination chain — an attacker can make that contract's `onAccept`/`onGetResponse`/`onGetTimeout` implementation return an arbitrarily large payload, forcing the relayer who calls `HandlerV2.handlePostRequests`/`handleGetResponses` to pay for copying that huge payload into memory.

### Finding Description

and the GET response / timeout delivery paths follow the identical pattern: [2](#0-1) [3](#0-2) 

The destination (`request.to` / `response.request.from` / `timeout.request.from`) is fully attacker-supplied at the point the original message was dispatched on the source chain — there is no restriction requiring it to be a "well-behaved" `IApp`. The flow is invoked by `HandlerV2.handlePostRequests`/`handleGetResponses`, which any relayer (an unprivileged, permissionless role) submits after proof verification: [4](#0-3) 

`(bool success, )` still requires the EVM to copy all of `returndata` into memory before the tuple is destructured, exactly as described in the reference report. A malicious contract deployed as the destination of a cross-chain message can implement the callback (`onAccept`, `onGetResponse`, or `onGetTimeout`) to `return` many megabytes of ABI-encoded data. Every relayer that attempts to deliver (or batch-deliver) that message pays quadratic-ish memory-expansion gas costs for the copy, even though the result is discarded.

Since `dispatchIncoming` is called once per leaf inside `HandlerV2.handlePostRequests`'s loop, a single crafted message embedded in a batch of otherwise-legitimate requests can dramatically inflate the gas cost of, or outright deny, the entire batch delivery for the submitting relayer.

### Impact Explanation
This is a griefing vector against relayers: an attacker can force excessive, wasted gas expenditure on message delivery, degrading Hyperbridge's reliability and economics. Because message delivery batches multiple requests per transaction (`handlePostRequests`/`handleGetResponses` loop over `request.requests`), an attacker's single malicious destination can inflate/DoS the gas cost for delivering many legitimate, unrelated messages in the same batch, delaying or preventing users' cross-chain messages/token transfers/intents from being delivered — a route-unable-to-deliver-messages condition for the affected batch. This aligns with Medium severity per the report's classification.

### Likelihood Explanation
High likelihood of exploitability: the attacker only needs to dispatch one crafted cross-chain message (permissionless, using any dApp/EvmHost `dispatch`) whose `to` module returns a large payload from its callback. No privileged role or governance access is required — only an ordinary sender able to submit a message and a relayer willing to attempt delivery, both of which are the intended permissionless user classes of the protocol.

### Recommendation
Replace `(bool success, ) = target.call(...)` with a low-level `call` via inline assembly that does not automatically copy return data into memory, e.g.:
```solidity
bool success;
assembly {
    success := call(gas(), destination, 0, add(data, 0x20), mload(data), 0, 0)
}
```
Alternatively, bound the maximum return-data size processed (e.g. via `excessivelySafeCall`-style patterns that only copy the first N bytes) so a malicious module cannot impose unbounded memory-expansion costs on the relayer.

### Proof of Concept
1. Attacker deploys `MaliciousApp` on the destination chain implementing `onAccept(IncomingPostRequest calldata)` that does `return "some huge bytes(1MB+)"` (interpreted as raw returndata from a low-level call, regardless of the ABI-declared external return type since the caller uses a raw `.call`).
2. Attacker dispatches a POST request from the source chain with `to = address(MaliciousApp)`.
3. A relayer submits the corresponding `PostRequestMessage` (containing this and other legitimate requests) via `HandlerV2.handlePostRequests`.
4. Inside `EvmHost.dispatchIncoming`, `(bool success,) = destination.call(abi.encodeWithSelector(IApp.onAccept.selector, ...))` forces the EVM to allocate and copy the multi-megabyte returndata into memory before discarding it, consuming gas disproportionate to the actual logic, potentially exhausting the relayer's supplied gas limit and reverting/failing delivery for the whole batch.

        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
