### Title
Webhook HMAC only covers the request body, allowing shop-domain/topic header spoofing and cross-tenant webhook confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute the webhook come from unauthenticated HTTP headers. This breaks the identity binding: "the tenant whose secret validated this payload" should equal "the tenant the app believes sent it," but the gem only proves the former for the body bytes, not for the header-derived shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers with no cryptographic tie to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC against `to_signable_string` (body only), then immediately trusts `request.shop` and `request.topic` to look up a handler and construct the metadata object dispatched to app code: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirms only that the *body* matches the secret-derived signature — it says nothing about which shop the header claims to be from: [4](#0-3) 

Because the signed content excludes the shop-domain (and topic/webhook-id) headers, any request carrying a **previously-observed valid `(raw_body, hmac)` pair** — for example a genuine webhook the attacker's own shop received, since the attacker fully controls the traffic reaching their own webhook endpoint — can be resubmitted to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop, and/or the `shopify-topic`/`shopify-webhook-id` headers altered, and it will still pass `HmacValidator.validate` because those headers are never part of `to_signable_string`. The equality the code implicitly relies on — *the shop whose secret validated the HMAC* == *the shop attributed by `request.shop`* — does not hold.

### Impact Explanation
This is a cross-tenant identity-binding failure: an app that stores or routes data keyed by `WebhookMetadata#shop` (as populated in `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) can be made to associate attacker-controlled, cryptographically-"valid" webhook payloads with a different merchant's tenant, since `shop` and `topic` ride outside the HMAC boundary. Any host application that trusts `data.shop`/`data.topic` from a successfully-`process`ed request (which is exactly what this gem's documented contract implies — HMAC validation succeeded, therefore the request is authentic for the claimed shop/topic) is exposed to cross-tenant data confusion.

### Likelihood Explanation
Requires the attacker to first obtain at least one genuine `(body, hmac)` pair, which is trivial for any attacker who can install the same public app on their own store (a normal, unprivileged action) and capture the webhook Shopify sends them. No `api_secret_key`, access token, or privileged account is needed to mount the replay — only observation of one's own legitimate webhook traffic and an ordinary HTTP client to resend it with altered headers to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived identity to the signed body, e.g., by including `shop`, `topic`, and `webhook_id` in `to_signable_string`, mirroring how `Oauth::AuthQuery#to_signable_string` incorporates `shop` into its signed payload: [5](#0-4) 

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-SHA256` header `H` that Shopify computed with the app's real `api_secret_key`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present), and `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` via `to_signable_string` (body-only) — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` — see `lib/shopify_api/webhooks/registry.rb:188-200` — even though the payload actually originated from the attacker's shop.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
