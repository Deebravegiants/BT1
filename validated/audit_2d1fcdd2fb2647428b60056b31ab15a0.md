### Title
Escrow refund/redeem always pays a fixed `beneficiary` derived from `order.user`/`msg.sender`, permanently freezing funds if that address is blacklisted by the escrowed ERC-20 - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` (shared by same-chain cancel, cross-chain refund-from-destination, and cross-chain refund-from-source) transfers escrowed ERC-20 tokens with `IERC20(token).safeTransfer(beneficiary, amount)`, where `beneficiary` is hard-coded to `order.user` and cannot be redirected at cancel time. If the escrowed token is a blacklistable stablecoin (e.g., USDC) and `order.user` is later blacklisted, every cancellation/refund path reverts forever, mirroring the `IchiVaultSpell.doRefund` blacklist issue in the report.

### Finding Description
`IntrinsicIntents._cancelSameChain` [1](#0-0) , `ExtrinsicIntents._cancelFromDest` [2](#0-1) , and `ExtrinsicIntents._cancelFromSource` [3](#0-2)  all build a `WithdrawalRequest` whose `beneficiary` is set to `order.user` — an address baked into the order at placement time and part of the commitment hash, so it cannot be changed at cancellation time.

All three paths funnel into `IntentsBase._withdraw`, which performs the actual token payout: [4](#0-3) 

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    ...
    if (token == address(0)) {
        _sendValue(beneficiary, amount);
    } else {
        IERC20(token).safeTransfer(beneficiary, amount);
    }
}
```

`safeTransfer` will revert unconditionally if the collateral token (e.g., USDC) blacklists `order.user` after the order was placed. Since:
- The escrow accounting (`_orders[commitment][token]`) is only decremented inside this same reverting call, there is no partial/alternate withdrawal path.
- `order.user`/`beneficiary` is fixed at order placement and is part of the EIP-712/keccak256 commitment used everywhere (`cancelOrder`, `onAccept`, `onGetResponse`), so the user cannot resubmit with a different recipient.
- There is no override field in `CancelOptions` (`relayerFee`, `height` only) to redirect the refund.

the user's escrowed tokens become permanently unretrievable through any of the three cancel/refund routes. This is the direct analog of the reported bug: a hard-coded recipient transfer in the "close position"/refund flow that can be permanently blocked by an ERC-20 blacklist, with no alternate recipient mechanism.

The `onGetResponse` handler that finalizes the source-side cancel also calls the same `_withdraw`/`withdraw` function with the same fixed beneficiary [5](#0-4) , showing the pattern is consistent across the same-chain, destination-cancel, and source-cancel code paths.

### Impact Explanation
Once a user's escrowed input token blacklists `order.user` (a realistic scenario for USDC/USDT-style tokens with centralized blacklist authority), that user's escrowed collateral is permanently frozen inside the `IntentGatewayV2` contract: 
- Same-chain cancel reverts (`_cancelSameChain` → `_withdraw`).
- Cross-chain cancel-from-destination reverts when the refund message lands on the source chain (`onAccept` → `_withdraw`).
- Cross-chain cancel-from-source reverts when the GET response is processed (`onGetResponse` → `_withdraw`).

There is no admin sweep, no alternate beneficiary parameter, and no way for the affected user to ever reclaim the escrowed tokens through the intended user flow — this is a permanent freezing of user funds, matching the "Medium" bar of the original report (concrete permanent freezing of funds via an unprivileged, single-transaction path: `placeOrder` + `cancelOrder`).

### Likelihood Explanation
Any unprivileged user can place an order using a blacklistable ERC-20 (USDC is explicitly used throughout the gateway's tests as the canonical input token). Being blacklisted is outside the protocol's control but is a foreseeable and previously-audited risk category (as evidenced by the linked Sherlock report on the same bug class). No special privileges or additional preconditions beyond normal order placement and being blacklisted by the token issuer are required to trigger permanent fund lock.

### Recommendation
Decouple failed token transfers from escrow accounting so a blacklist on one recipient cannot brick the whole withdrawal:
- Allow the caller to specify an alternate recipient address in `CancelOptions` (and validate/sign it), falling back to a pull-based claim pattern (e.g., record an internal credit balance for `order.user` that any address they designate, or that they later change, can withdraw) instead of a direct `safeTransfer` inside `_withdraw`.
- Alternatively, wrap `safeTransfer` in a try/catch and, on failure, credit the amount to an internal "stuck funds" ledger keyed by `(commitment, token)` that the user (or a governance-controlled sweep, with proof of ownership) can later redirect to a non-blacklisted address.

### Proof of Concept
1. User places a same-chain order with USDC as an input token via `placeOrder`, escrowing tokens under `_orders[commitment][usdc]` in `IntentGatewayV2`.
2. Before the order is filled, USDC's issuer blacklists the user's address (`order.user`).
3. User calls `cancelOrder(order, options)`. This routes to `_cancelSameChain` → `_withdraw`, which executes `IERC20(usdc).safeTransfer(beneficiary, amount)` with `beneficiary == order.user`.
4. The USDC contract's transfer implementation reverts because the recipient is blacklisted, causing `_withdraw` — and thus the entire `cancelOrder` transaction — to revert.
5. The user has no way to change `beneficiary`/`order.user` for this commitment (it's fixed at order creation and part of the hashed order), so the escrowed USDC in `IntentGatewayV2` remains locked indefinitely. [1](#0-0) [4](#0-3)

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }

        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
