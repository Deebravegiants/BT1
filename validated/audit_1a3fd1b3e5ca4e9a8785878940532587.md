### Title
Missing source-module check in `BandwidthManager.onAccept` lets any Hyperbridge-side module drain the manager's treasury - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.onAccept` gates inbound governance messages (`SetTiers`, `Withdraw`) only on `request.source == hyperbridge`, never on `request.from` (the dispatching module/pallet id on Hyperbridge). Any pallet on Hyperbridge capable of dispatching an ISMP `PostRequest` to an EVM app — including low-privileged, non-`AdminOrigin` code paths — can address a `PostRequest` to this contract with `to = PALLET_BANDWIDTH_MODULE_ID`'s slot... more precisely, can dispatch a message that lands at `BandwidthManager` and is accepted as long as `source == hyperbridge`, without the contract ever verifying it actually came from `pallet-bandwidth`. [1](#0-0) 

### Finding Description
The docs explicitly flag this design: "`BandwidthManager.onAccept` checks `request.source == IDispatcher(_host).hyperbridge()`. Only messages dispatched from Hyperbridge are honored. The `to` field is the manager's address — **no module-id lookup**." [2](#0-1) 

The actual contract code confirms this: `onAccept` decodes `request.body[0]` into `OnAcceptActions.SetTiers` or `OnAcceptActions.Withdraw` and executes it, gated by nothing more than `request.source.equals(hyperbridge())`: [3](#0-2) 

This is architecturally identical to the n8n bug class: a supposed access restriction ("only pallet-bandwidth may issue Withdraw/SetTiers") is not actually enforced at the point where the privileged action (fund transfer to an arbitrary `beneficiary`) executes. The "Allowed HTTP Request Domains" analog here is "allowed module id" — the contract trusts the coarse-grained check (message came from Hyperbridge, the coprocessor) instead of the fine-grained one (message came specifically from `pallet-bandwidth`'s module id, `BWMARKET`). Compare this to `HyperFungibleToken`/`BridgeToken` and `IntentGatewayV2`, which recently added exactly this kind of module/relayer-level check on top of the host/source check (`_checkRelayer`, `authenticate()` comparing `request.from` against a known instance address) — precisely because checking only "came from the host/hyperbridge" is insufficient. [4](#0-3) [5](#0-4) 

For this to be exploitable, some Hyperbridge-side entity other than `pallet-bandwidth` must be able to dispatch an arbitrary `PostRequest` (arbitrary `to`, arbitrary `body`) to an EVM destination — e.g. via `pallet_ismp::dispatcher` directly, another pallet with unrestricted dispatch, or any code path that lets an unprivileged caller construct a raw `DispatchPost`. If any such path exists (which is plausible given `IsmpDispatcher::dispatch_request` is a generic primitive available to any pallet/module in the runtime, and the `ProxyModule` forwards requests whose `dest != HostStateMachine` without restricting who may cause that dispatch), an attacker can forge a `Withdrawal { token, beneficiary: attacker, amount }` payload and have it delivered to `BandwidthManager`, draining its ERC-20/native treasury to their own address — with no `AdminOrigin` or governance approval anywhere in the loop.

I could not fully verify from the index which specific pallet/extrinsic on Hyperbridge would let an unprivileged account construct and dispatch an arbitrary `to`/`body` `PostRequest` destined for an arbitrary EVM contract (this would need confirmation against `modules/pallets/ismp/src/dispatcher.rs` and the full set of pallets wired into the runtime's `IsmpDispatcher`), so likelihood depends on whether such a path is actually reachable by a low-privileged actor versus being gated by `AdminOrigin` everywhere it's used today.

### Impact Explanation
If reachable, this permits complete draining of `BandwidthManager`'s escrowed fee-token/native balance to an attacker-chosen address, bypassing all governance controls (`AdminOrigin`-gated `dispatch_withdraw`) — a direct, unbacked theft of protocol/treasury funds. This matches the "concrete theft ... of funds" bar.

### Likelihood Explanation
Medium: the check is objectively missing and documented as a deliberate simplification ("no module-id lookup"), which is the exact bug class described in the report. However, exploitability hinges on whether any pallet other than `pallet-bandwidth`, reachable by an unprivileged transaction, can dispatch an arbitrary `PostRequest` with attacker-controlled `to`/`body` to an EVM chain. I was not able to conclusively confirm such an unprivileged dispatch path within the available index; if all outbound dispatch paths that could target `BandwidthManager`'s address are themselves privileged (`AdminOrigin`) or fixed-`from`/fixed-body per pallet, the bug is present but not exploitable by a low-privileged actor today.

### Recommendation
Add a `request.from`-based check in `BandwidthManager.onAccept` requiring `request.from == PALLET_BANDWIDTH_MODULE_ID` (mirroring the module-id checks already added to `BridgeToken` and `IntentGatewayV2`), in addition to the existing `request.source == hyperbridge` check, so that only the specific pallet-bandwidth module can trigger `SetTiers`/`Withdraw`.

### Proof of Concept
1. Identify or construct a Hyperbridge-side call path that dispatches an ISMP `PostRequest` with attacker-chosen `to` (the `BandwidthManager` address on the target EVM chain) and attacker-chosen `body`.
2. Craft `body = abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(Withdrawal({token: feeToken, beneficiary: attacker, amount: fullBalance})))`.
3. Dispatch with `source` naturally resolving to Hyperbridge's state-machine id (since the message originates on Hyperbridge itself) and `dest` set to the target EVM chain.
4. Once relayed and delivered, `BandwidthManager.onAccept` passes the `request.source.equals(hyperbridge())` check (true, since it did originate from Hyperbridge) and executes the `Withdraw` branch, transferring `fullBalance` of `feeToken` to `attacker`. [6](#0-5)

    /// @notice Inbound governance from `pallet-bandwidth`. The first
    /// body byte selects `OnAcceptActions`; the remainder is the
    /// action's ABI-encoded payload.
    /// @dev Only the configured host may invoke (`onlyHost`); the
    /// request's `source` must additionally equal hyperbridge.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
