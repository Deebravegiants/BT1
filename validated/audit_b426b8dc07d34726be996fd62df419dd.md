### Title
Attacker-controlled `erc20TokenAddresses` array in `CircomData` lets `EmporiumUpgradeable.runAction` execute arbitrary external calls whose token movements are never accounted for or checked - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`/`handleOut` and `Hinkal.transact`'s slippage/balance-diff loop both iterate strictly over the caller-supplied `circomData.erc20TokenAddresses` array. Since the attacker fully controls this array (and `dimensionsCheck` only requires internal consistency between array lengths, not that it lists every token actually touched), any token that ends up moving through Emporium's shared address but is left out of that array is completely unaccounted for - the degenerate case being the "Min path" of an empty array (`erc20TokenAddresses.length == 0`), where neither `handleOut` nor `Hinkal.transact`'s balance-diff loop execute at all.

### Finding Description
The invariant that should hold is:

`tokens Hinkal/Emporium ends up holding after runAction == sum of UTXO amounts inserted for the caller for every token actually moved by op.callData`

Both sides of this equality are only computed over `circomData.erc20TokenAddresses`:
- In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are taken via `getBalancesForArray(circomData.erc20TokenAddresses)` [1](#0-0) , and `handleOut`/the balance-change revert check only run inside `for (i < circomData.erc20TokenAddresses.length)` [2](#0-1) .
- In `Hinkal.transact`, `oldBalances`/`newBalances` and the slippage/`balanceDif == amountChanges[i] + utxoAmount` check likewise only iterate `circomData.erc20TokenAddresses` [3](#0-2) .

Meanwhile, `stack.ops` (fully attacker-crafted via `externalActionMetadata`) execute arbitrary calls from Emporium's own address with arbitrary `callData` and `value`, for both the stateful (`invokeWallet`) and stateless branches [4](#0-3) . Any token whose balance changes as a side effect of these calls but is not listed in `circomData.erc20TokenAddresses` is invisible to both accounting loops - there is no requirement anywhere (`dimensionsCheck`, `checkOnchainCreation`, `performHinkalChecks`) that the declared token array actually cover every asset touched by `stack.ops`.

The trivial/degenerate form is exactly the "Min path" the question describes: `erc20TokenAddresses.length == 0` forces `inputNullifiers`/`outCommitments`/`amountChanges` to length 0 too (via `dimensionsCheck`), so the whole transaction spends no UTXOs and creates none, yet `stack.ops` still execute fully and unconditionally, with the resulting `0 == 0` balance/slippage checks trivially satisfied on both `EmporiumUpgradeable.runAction` and `Hinkal.transact` sides.

Attacker call: `Hinkal.transact(a,b,c,dimensions,circomData)` where `circomData.erc20TokenAddresses` (and therefore `dimensions.tokenNumber`) excludes the specific token the attacker wants to move, `circomData.externalActionData.externalActionId` points at Emporium, and `externalActionMetadata` encodes an `EmporiumStack` whose `ops[i].callData` is e.g. `token.transfer(attackerEOA, amount)` (or, more generally, an op that produces/receives an out-of-band token, such as swap dust or a reward token, as a side effect). Because the moved token is absent from the declared array, `handleOut` never runs for it and `balancesBefore`/`balancesAfter` never observe it, so nothing prevents Emporium's balance in that token from being drained directly to `attackerEOA`.

### Impact Explanation
Any token balance sitting on the shared `EmporiumUpgradeable` contract (e.g., leftover reward/dust tokens from a DEX call, unswept refunds, or excess ETH from a prior `op.value`) is that token that is untracked by the caller's chosen array and can be siphoned to any address with zero on-chain accounting - no slippage check, no balance/UTXO equality check, no nullifier or commitment created. This satisfies the Critical category "direct theft of shielded or in-flight user funds": funds physically leave the protocol's custody without Hinkal's own balance sheet or the UTXO tree ever recording the movement, and it is fully repeatable per attacker-crafted `runAction` call.

### Likelihood Explanation
The attacker needs no privileged role: they can call `Hinkal.transact` directly (unprivileged EOA), fully control `CircomData`/`Dimensions`/`externalActionMetadata`, and generate a valid proof for a trivial (possibly all-zero) statement since `dimensions.tokenNumber` can be 0 or can simply exclude the target token. The only real-world precondition is that Emporium (a singleton, multi-user shared contract) is holding some non-zero balance of an asset not declared by the attacker at call time - a realistic condition given Emporium routes arbitrary DeFi calls (`op.endpoint.call`) that can produce incidental token balances (rewards, refunds, rounding) that are never guaranteed to be included in every caller's declared array.

### Recommendation
Do not trust the caller-supplied `erc20TokenAddresses` array as the sole basis for Emporium's/Hinkal's accounting. Either (a) restrict `stack.ops` to a strict allow-list of endpoints/selectors so arbitrary token transfers out of Emporium are impossible, or (b) after executing `stack.ops`, sweep and account for *every* token balance change Emporium experiences (not just the declared subset) - e.g., require any token whose balance changed be present in `circomData.erc20TokenAddresses`, or force zero residual balance for all tokens interacted with, rejecting the call otherwise. Additionally, disallow `dimensions.tokenNumber == 0` combined with a non-empty `stack.ops` unless it can be proven no token balance of Emporium can change.

### Proof of Concept
1. Deploy `EmporiumUpgradeable` and seed it with a non-zero balance of `DustToken` outside of any tracked flow (e.g., via a first `runAction` call whose `stack.ops` include a mock DEX call that sends `DustToken` to Emporium as an untracked side-effect of a swap declared only in `WETH`/`USDC`).
2. Craft a second `Hinkal.transact` call (or a single call combining both steps) with `circomData.erc20TokenAddresses` that excludes `DustToken`, `dimensions.tokenNumber` matching that shorter array, and `stack.ops[0].callData = DustToken.transfer(attackerEOA, dustBalance)`.
3. Generate a valid proof for this (trivial, zero-token or dust-excluded) statement.
4. Assert: `Emporium`'s (and `Hinkal`'s) balance of `DustToken` goes from `dustBalance` to `0`, `attackerEOA`'s `DustToken` balance increases by `dustBalance`, and no revert occurs in `handleOut`'s `BalanceChangeShouldBePositive` check or `Hinkal.transact`'s slippage/balance-diff `require`s - proving the movement is fully invisible to both contracts' accounting.
