### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body against `Context.api_secret_key`, but the `shop` domain that identifies which tenant the webhook belongs to is read from an HTTP header that is never included in the signed bytes. Any actor who can obtain one genuine, correctly-signed webhook body/HMAC pair (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact body and HMAC while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header for a different shop, and the request will still pass validation.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhooks `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is pulled straight from a request header, entirely outside the HMAC-covered bytes: [2](#0-1) 

`Registry.process` validates the HMAC and, once it passes, immediately forwards `request.shop` to the app's handler as the tenant identity for that webhook, with no cross-check that the shop matches anything inside the signed body: [3](#0-2) 

Because the gem's `api_secret_key` (the HMAC key) is shared across every shop that installs the app — it is not a per-shop secret — a party who legitimately installs the app on their own store can capture a real, correctly-signed webhook (body + HMAC), then resend the identical body/HMAC pair to the app's webhook endpoint while changing only the `shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` re-verifies successfully because it only checks the body bytes, so `Registry.process` accepts the request and calls the handler with `WebhookMetadata` claiming the victim's `shop`: [4](#0-3) 

This breaks the intended binding: `shop header value == shop the HMAC actually authenticates`. The HMAC authenticates "this body was produced with the app's secret" but says nothing about which tenant it came from, yet the library treats the header value as if it were verified.

### Impact Explanation
Any app built on this gem that dispatches business logic (e.g., updating stored data, deleting sessions on `app/uninstalled`, processing `customers/redact`, syncing orders) keyed off `WebhookMetadata#shop` can be made to apply attacker-controlled webhook content to another merchant's tenant record, since the shop label is spoofable independent of the signed payload. This is a cross-tenant confusion/access primitive: data or actions intended for the attacker's own shop's webhook get attributed to a different shop chosen by the attacker.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate installer of the target app on their own store (an ordinary merchant/customer of the app — not a privileged account, not access to `api_secret_key`), capture one webhook delivery, and replay it with a modified header to the app's public webhook endpoint. No secrets or elevated access are needed beyond normal app usage, making this practically reachable for any multi-tenant app built on this gem's webhook registry.

### Recommendation
Bind the tenant identity into the material that is actually HMAC-verified, or otherwise cryptographically tie the `shop` header to the signed body/topic before trusting it — e.g., include `shop` (and `topic`/`webhook_id`) in `to_signable_string`, or independently confirm the header-derived shop against a shop value embedded in and covered by the signed payload, before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; wait for a legitimate webhook (e.g. `orders/create`) delivery with valid `shopify-hmac-sha256` and body.
2. Capture the raw request: headers `{shopify-topic, shopify-hmac-sha256, shopify-shop-domain: attacker.myshopify.com}` and the raw JSON body.
3. Replay the exact same headers/body to the app's webhook endpoint, changing only `shopify-shop-domain` to `victim.myshopify.com`.
4. `Webhooks::Request.new` parses this into a request whose `hmac` is unchanged and still validates via `HmacValidator.validate` because the check only covers `@raw_body`, per `lib/shopify_api/webhooks/request.rb` (lines 35-43) and `lib/shopify_api/utils/hmac_validator.rb` (lines 26-31).
5. `Registry.process` accepts the forged request and calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` carrying the attacker's body content, per `lib/shopify_api/webhooks/registry.rb` (lines 188-199) — demonstrating the shop/HMAC binding break.
