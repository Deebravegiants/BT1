Based on my research, the closest structural analog to the MasterChef `depositor`-trust bug class in `orb-core--014` is in the signup-authorization flow, where a boolean flag supplied through the backend-authenticated QR payload (`user_centric_signup`) is trusted to bypass the orb's own local enrollment step, without any additional validation "cost."

### Title
Backend-supplied `user_centric_signup` flag lets an authenticated-but-unverified app claim a successful signup, bypassing the orb's local enrollment check - (File: src/plans/mod.rs)

### Summary
`MasterChef.sol`'s core defect was that a `depositor` role, once granted, could unilaterally mint `user.amount` state changes with no further validation or cost, letting it siphon almost all rewards. The structural analog in `orb-core` is in `do_signup()`: the orb reads a `user_centric_signup` boolean out of the backend/app-authenticated QR payload and, if set, treats the signup as `Success`/`Normal` purely from a local `signup_reason` value, skipping the call to `enroll_user::Plan` that would otherwise submit the enrollment attempt to the backend for confirmation.

### Finding Description
During `do_signup`, once the biometric pipeline and fraud check finish, the code branches on `user_centric_signup`: [1](#0-0) 

If `user_centric_signup && !ignore_user_centric_signups`, the enrollment `Status`/success is derived *only* from the locally computed `signup_reason` (itself derived from local pipeline output and local fraud-check result, which — per an inline comment — has had "ALL FRAUD CHECKS" deleted): [2](#0-1) 

In this branch, `enroll_user::Plan` (the code path that actually calls `signup_post::request` / `signup_poll::request` to have the backend confirm the enrollment, detect duplicate irises, etc.) is never invoked. Success is essentially self-attested by the orb, gated entirely by a flag (`user_centric_signup`) that originates from `authenticated_app_data` returned by the backend `user_status` endpoint and is bound to the physical QR code only via a hash comparison: [3](#0-2) [4](#0-3) 

This mirrors the `MasterChef` pattern: a flag/role, once trusted, is allowed to directly set high-value state (`user.amount` in MasterChef; enrollment `Success`/signup completion here) with no secondary validation step that would normally require backend confirmation of the actual event (a deposit transfer in MasterChef; an enrollment record in orb-core).

### Impact Explanation
If the `user_centric_signup` path is taken, the orb never confirms with the backend that the enrollment/signup was actually recorded (no `signup_post`/`signup_poll` round-trip, no duplicate-iris / inflight-match check performed by that specific code path). The success/failure of the signup — and the `SignupReason` reported (`Normal`, `Fraud`, `Failure`) — is decided unilaterally by the orb's local pipeline result, which is then trusted by the app/back-end ecosystem as an authoritative "signup completed" signal. Given `detect_fraud` has been stripped down to a stub (`Ok(false)` unconditionally past pipeline presence), the only remaining server-side backstop for user-centric signups (duplicate detection, inflight match, fraud confirmation) is skipped, leading to potential misattributed/unauthorized signup completions.

### Likelihood Explanation
`user_centric_signup` is populated from `orb_qr_link::UserData`, an app-controlled value transported through the backend response but tied to the QR code only via an HMAC-style hash check (`user_data.verify(user_data_hash)`), not a scheme that ties the flag to a specific enrollment transaction outcome. Since this is the standard (non-debug, non-test-gated) production path for "app-centric signup," it is reachable by any ordinary end-user session, not merely an operator or admin, making the likelihood of exercising this code path itself high; whether it is exploitable to *forge* an unauthorized signup depends on backend-side guarantees not visible in this repository.

### Recommendation
Do not let a client/app-supplied `user_centric_signup` flag fully substitute for the backend-confirmed enrollment round trip. At minimum, `enroll_user::Plan` (or an equivalent backend confirmation call) should be invoked for all signups, with `user_centric_signup` only affecting UX/flow control, not the final success/failure or `SignupReason` recorded for the signup. Reinstate/verify server-side fraud and duplicate checks rather than relying on a stubbed `detect_fraud` that unconditionally returns `Ok(false)`.

### Proof of Concept
Not applicable in the same way as the Solidity finding — no exploit transaction can be constructed from static analysis alone. The control-flow proof is the branch shown above: `user_centric_signup == true` and `ignore_user_centric_signups == false` (the default, per `src/config.rs` `Default for Config`) causes `success = signup_reason == SignupReason::Normal` to be computed without calling `enroll_user::Plan::run`, i.e., without the backend `signup_post`/`signup_poll` confirmation cycle that governs enrollment for all other (operator-centric) signups.

Note on confidence: this analog is weaker than a typical "privileged role with no-cost arbitrary action" bug — the flag is still backend-issued and hash-bound to the QR code, and the exact backend-side guarantees for `authenticated_app_data.user_centric_signup` are not visible in this repository/index, so I could not confirm whether the backend independently re-validates the signup outcome out-of-band. I found no other unprivileged-user-reachable code path (QR/MECARD parsing, secure-element signing, agent-IPC) that more directly mirrors the "role trusted with no-cost arbitrary state change" pattern from the MasterChef report; `MECARD`/WiFi QR parsing (`src/network/mecard.rs`) and the `signup_extension` QR fields are gated behind non-production features or have no signup/fraud/biometric impact, so they were excluded per the rules.
