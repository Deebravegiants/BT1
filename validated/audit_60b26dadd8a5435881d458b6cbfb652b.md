### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then trusts the unsigned `X-Shopify-Shop-Domain` (and topic/webhook-id) header to identify which merchant/tenant the payload belongs to. Because the tenant-identifying field is acted upon without being covered by the HMAC, an attacker who legitimately receives one valid `(body, hmac)` pair for their own shop can replay it with a forged shop-domain header and have the app process it as data belonging to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are never part of the signed content: [2](#0-1) 

`Registry.process` verifies the HMAC and, once it passes, hands `request.shop` (the unsigned header) directly to the host application's handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` confirms the HMAC only against `verifiable_query.to_signable_string`, i.e. the body, using `Context.api_secret_key`: [4](#0-3) 

This breaks the intended binding: `hmac(body) == valid` should imply `shop-header == shop that Shopify actually sent this body for`. In fact the equality that holds is only `hmac(body) == valid`; the `shop` (and `topic`/`webhook-id`) header is completely decoupled from what was cryptographically verified — directly analogous to the `WatcherClient.setWatcherManager` bug, where the update event fired without the underlying state actually being bound/changed.

### Impact Explanation
Any merchant who has the vulnerable app installed on their own shop (an unprivileged party with respect to any other tenant) will naturally receive genuine, validly-HMAC-signed webhook deliveries containing their own shop's data. Because the signature covers only the body, that same `(raw_body, hmac)` pair remains valid no matter what shop-domain header accompanies it. The attacker can resend that exact body/HMAC to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `Registry.process` will accept it (HMAC check passes because the body is unchanged) and dispatch it to the app's handler labeled as belonging to the victim shop, via `WebhookMetadata#shop`. If the host application uses this value to select which tenant's records to create/update (a documented, expected usage pattern of this field), this results in cross-tenant data injection/corruption without ever needing the app's `client_secret` or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchants (the normal case for a Shopify public app): every existing installed merchant is a potential attacker, requires no secret material, no social engineering, and no privileged access — just capturing one of their own legitimate webhook deliveries (trivial, since it's delivered to their own server/proxy) and resending it with a modified header.

### Recommendation
Bind the tenant-identifying and topic-identifying fields into the HMAC-covered content, or otherwise cryptographically tie the shop/topic/webhook-id to the verified body, e.g. include them in `to_signable_string`, or independently validate `request.shop` against the shop associated with the session/subscription that is expected to receive that specific webhook/topic before dispatching to handlers. At minimum, document and enforce that consumers must not treat `WebhookMetadata#shop` as authenticated unless it has been separately corroborated (e.g., against a known list of currently-installed shops that also matches an out-of-band expectation for that specific webhook).

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture a legitimate webhook POST it receives, e.g. `orders/create` with `raw_body = B` and header `X-Shopify-Hmac-Sha256 = H` (valid since `H = HMAC(client_secret, B)`).
2. Replay the exact same request to the app's public webhook endpoint, changing only `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally `X-Shopify-Webhook-Id`), leaving body `B` and `X-Shopify-Hmac-Sha256: H` untouched.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and matches `H`, so validation succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, so any app logic that uses `data.shop` to locate/update tenant records now operates on the victim shop's data despite the payload actually originating from the attacker's own shop.
