### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and validates only the raw request body via HMAC, but the `shop-domain` header — which `Registry.process` trusts and hands to the app's webhook handler as the tenant identifier — is never part of the signed data. Any actor who can obtain one legitimately signed `(body, hmac)` pair from Shopify (i.e., by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The HMAC check still passes, and the forged shop identity is delivered to the app's business logic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e., the body: [2](#0-1) 

`Registry.process` only checks this body-only HMAC before trusting `request.shop` (parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) and forwarding it to the app-supplied handler as the tenant identity: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header == shop that the HMAC attests to`. Because the signed bytes (`raw_body`) are disjoint from the field acted on (`shop-domain` header), this equality can be broken: the HMAC only proves "this body was generated by the app's registered secret for *some* shop," not "this body belongs to *this* shop-domain header." Any tenant of a multi-tenant app that shares one `api_secret_key` across all installs can capture a genuine `(body, hmac)` pair delivered to their own store and re-POST it to the shared public webhook endpoint with the `shop-domain` header changed to a victim shop. `Registry.process` will accept it and dispatch `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` to the app's handler with the attacker-chosen `shop` value, even though the body/HMAC never attested to that shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged actor (a legitimate but malicious merchant of the same app) can inject data that is processed under another tenant's identity — e.g., causing the app to write order/customer/webhook-driven state against a victim shop's records, or trigger shop-scoped side effects (like uninstall/GDPR-style handlers) using their own captured payload but a spoofed shop. This is a cross-tenant access issue reachable without any access token, refresh token, or `client_secret` — only participation as a customer of the same app is required.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even trial) installer of the target app, capture one webhook delivery to their own endpoint/logs, and replay it directly to the app's public webhook URL with a modified header — no credentials, TLS interception, or privileged access needed. Multi-tenant apps sharing a single webhook endpoint/secret across shops are the norm, making this broadly reachable.

### Recommendation
Include the shop identity (and ideally topic/webhook-id) in the signed material used for webhook verification, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., verify the shop against a per-shop registered callback path/secret, or require that the shop header be re-derived/confirmed against Shopify's Admin API using a stored per-shop credential rather than trusted directly from an unauthenticated header). At minimum, document that `request.shop` is not authenticated by the HMAC and must not be used as a sole tenant selector by consuming applications.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets it register a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's shared public endpoint with headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`, where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker captures `B` and `H`, then sends a new POST to the same endpoint with the same body `B` and same `H`, but header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and finds it equal to `H`, so validation passes:
`raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)` — no exception raised.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the attacker's own webhook body is now processed by the app under the victim's tenant identity.
