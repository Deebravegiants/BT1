### Title
Non-embedded session ID is a bare, unsigned, predictable value trusted directly from a client-supplied cookie - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` treats whatever value is present in the `SESSION_COOKIE_NAME` cookie as the authoritative session identifier, with no cryptographic binding between that value and any Shopify-issued credential. Because offline session IDs are computed deterministically as `"offline_#{shop}"` from a publicly-known shop domain, the value an app is expected to trust from this cookie is guessable/forgeable by anyone, unlike the embedded flow where the session ID is derived from a signed JWT.

### Finding Description
The gem exposes two ways to obtain a "trusted" session id in `lib/shopify_api/utils/session_utils.rb`: [1](#0-0) 

For embedded apps, the identifier is derived from `Auth::JwtPayload.new(id_token)`, which cryptographically verifies an HS256 signature against `Context.api_secret_key` before trusting the `shop`/`sub` claims: [2](#0-1) 

For non-embedded apps (and as a fallback for embedded apps without a bearer token), the gem instead returns the raw cookie value verbatim, with no signature or integrity check of any kind: [3](#0-2) 

This cookie value is set once, on successful OAuth completion, directly to `session.id`: [4](#0-3) 

and `session.id` for an offline (store-level) session is computed purely from the public shop domain, with no secret or random component: [5](#0-4) 

The gem's own documentation confirms this is the intended, documented usage pattern for non-embedded apps — passing raw browser cookies straight into `current_session_id` to obtain the value that the host app is expected to use as the session-store lookup key: [6](#0-5) 

The identity binding broken here is: **the value returned by `SessionUtils.current_session_id` (used by a host app to fetch a `Session` and its `access_token` from storage) should equal a value cryptographically tied to a completed, shop-specific OAuth exchange — but instead it equals whatever raw bytes are found in an unsigned, attacker-writable cookie**, and for offline sessions that value is fully computable from public information (`"offline_" + shop_domain`) with no server-side secret involved. There is no HMAC, signature, or nonce over the cookie's contents anywhere in `SessionCookie` or `SessionUtils` — contrast this with `Utils::HmacValidator`/`VerifiableQuery`, which are used everywhere else in the gem (OAuth callback, webhooks) to bind untrusted request data to `Context.api_secret_key`.

### Impact Explanation
If a host application follows the gem's documented pattern (`current_session_id(nil, cookies, ...)` for non-embedded apps) and uses the returned string directly as a session-storage lookup key — the pattern the docs explicitly recommend — an attacker who simply knows or guesses a target merchant's `myshopify.com` domain (public information, often the merchant's own storefront URL) can set their own browser's session cookie to `"offline_target-shop.myshopify.com"` and have the host app retrieve and activate that shop's stored offline `Session`, including its real Admin API `access_token`. This is a cross-tenant session/credential exposure rooted entirely in this gem's cookie-to-session-id contract, not in any host misuse of an undocumented API.

### Likelihood Explanation
Medium: exploitation requires a host application to implement session storage exactly as documented (keying stored sessions by the ID returned from `current_session_id`) and to not layer additional integrity protection (e.g., a signed/encrypted cookie jar) on top of the gem's plain value — which is exactly the flow shown in `docs/getting_started.md` and not called out anywhere as needing extra protection. The shop domain component of the ID is always public, so no secret needs to be leaked for an attacker to construct the value for a known target.

### Recommendation
Do not use a bare, deterministic string as both the session-store key and the client-supplied cookie value. Either (a) sign/HMAC the cookie value with `Context.api_secret_key` (mirroring `Utils::HmacValidator`) and verify it in `cookie_session_id`, or (b) make the cookie store an opaque, unguessable, per-session secret ID that is unrelated to `Session#id`'s public naming scheme, so knowledge of a shop's domain alone is insufficient to construct a valid session cookie for that shop.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` completes non-embedded OAuth; the host app's session repository stores a `Session` under ID `"offline_victim-shop.myshopify.com"` (per `Session.from`, `lib/shopify_api/auth/session.rb:107-118`), as instructed by `docs/getting_started.md`.
2. Attacker, in their own unauthenticated browser session on the same host app, sets the cookie `SessionCookie::SESSION_COOKIE_NAME` to the literal value `"offline_victim-shop.myshopify.com"` (fully derivable from the public shop domain).
3. Attacker requests any authenticated route; the host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns the attacker-forged value unchanged (`lib/shopify_api/utils/session_utils.rb:68-71`).
4. The host app looks up and activates the victim's stored `Session`, using the victim's real `access_token` to serve the attacker's request — a cross-tenant credential exposure with no OAuth ever performed by the attacker.

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
