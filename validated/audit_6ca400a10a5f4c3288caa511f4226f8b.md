### Title
Inflation-attack-style dilution of early LPs due to attacker-controlled LP-mint decimals nullifying the minimum-liquidity lock - ([File: program/src/processor.rs])

### Summary
`process_initialize2` derives the LP mint's decimals from the caller-supplied `coin_mint` and then subtracts `10^lp_mint.decimals` from the initial liquidity to compute the amount minted to the pool creator, intending this as a Uniswap-V2-style "locked liquidity" guard against inflation attacks. Because the `coin_mint` is a completely attacker-controlled SPL token (the pool creator can mint their own token with `decimals = 0`), this protection collapses to burning only `10^0 = 1` unit — functionally equivalent to the insufficient "1 virtual share" design criticized in the referenced StUSR report. Combined with the fact that `process_deposit` derives pool totals from live, directly-donatable vault balances while using the tiny, attacker-set `amm.lp_amount` as the LP-share denominator, a newly created pool can be manipulated so that a follow-on depositor receives a disproportionately small (but non-zero, so not blocked by the zero-share check) LP allocation relative to the value they deposit, transferring value to the pool creator.

### Finding Description
In `process_initialize2`, the LP mint is created by the program itself using decimals copied from the coin mint: [1](#0-0) 

The initial minted LP amount subtracts a "virtual liquidity" term equal to `10^lp_mint.decimals`: [2](#0-1) 

Since the pool creator supplies `amm_coin_mint_info` and this mint is entirely under the creator's control (an attacker can deploy their own SPL mint with `decimals = 0` before calling `Initialize2`, which is common for meme/scam tokens), the "locked liquidity" that is supposed to deter inflation/donation manipulation shrinks to just `1` unit rather than a meaningful buffer, mirroring the insufficient "1 virtual share" flaw described in the external StUSR report.

Subsequently, `process_deposit` computes the pool's total coin/pc holdings directly from the live SPL vault balances (which anyone can inflate via a raw token transfer/donation), not from an internally tracked, donation-resistant total: [3](#0-2) 

The LP shares to mint for a depositor are computed against `amm.lp_amount` (the tiny, attacker-influenced total set at `Initialize2`), using floor rounding: [4](#0-3) [5](#0-4) 

The only anti-zero-share guard is a check that `mint_lp_amount != 0`: [6](#0-5) 

Because `amm.lp_amount` right after `Initialize2` can be as low as `2` (e.g. `liquidity = 2`, `user_lp_amount = liquidity - 1 = 1`), the granularity of the floor-division is extremely coarse. After a donation-based inflation of the vault balance, a victim must deposit an amount close to (or exceeding) half of the manipulated pool balance just to avoid reverting on the zero-share check, and receives disproportionately few LP units relative to fair value — the value gap accrues to the attacker's existing LP holdings, exactly the dynamic described in the StUSR report (steps 3–5), just triggered via a degenerate LP-mint decimals value instead of a hard-coded single virtual share.

### Impact Explanation
An attacker who creates a fresh Raydium pool (a fully permissionless, unprivileged action reachable via `Initialize2`) using a zero/low-decimal token they control can set up a pool whose inflation-attack defense is effectively disabled. If a victim is lured into depositing into that freshly created, low-liquidity pool (plausible for new/scam token listings, a very common pattern on Raydium), the attacker can front-run/donate tokens into the vault and cause the victim's deposit to be minted a disproportionately small number of LP tokens relative to the value contributed, transferring value to the attacker's LP position. This is a concrete loss-of-funds vector for LPs/depositors and an unbacked/skewed LP accounting condition.

### Likelihood Explanation
Exploitation requires the attacker to (1) deploy their own SPL mint with `decimals = 0` (trivial, unprivileged), (2) create the pool via `Initialize2` (unprivileged, single transaction), and (3) get a victim to deposit into the still near-empty pool shortly after creation while front-running/donating to the vault. This is realistic given Raydium's permissionless pool creation and the prevalence of newly launched, low-decimal tokens, but it depends on the attacker successfully timing a donation ahead of a victim's deposit transaction (front-running), which is achievable on Solana but not guaranteed for every pool — rating this Medium likelihood.

### Recommendation
Do not derive the anti-inflation "virtual liquidity" burn from a value the pool creator fully controls (`coin_mint.decimals`). Use a fixed, decimals-independent minimum liquidity lock (à la Uniswap V2's `MINIMUM_LIQUIDITY`), or enforce a floor such as `max(10^lp_mint.decimals, MINIMUM_LIQUIDITY_CONSTANT)` with a sufficiently large constant, and/or reject `Initialize2` calls where `coin_mint`/`pc_mint` decimals fall below a safe minimum (e.g., 6). Additionally, consider decoupling deposit share calculations from raw, donatable vault balances by tracking internal accounted reserves, or require a minimum pool size relative to `amm.lp_amount` before permitting further deposits.

### Proof of Concept
1. Attacker deploys a new SPL mint `M` with `decimals = 0` and mints a small supply to themselves.
2. Attacker calls `Initialize2` pairing `M` (as `coin_mint`) against a real asset (e.g., USDC as `pc_mint`) with `init_coin_amount = 1`, `init_pc_amount = 4`. `liquidity = sqrt(1*4) = 2`; `lp_decimals = coin_mint.decimals = 0`; `user_lp_amount = 2 - 10^0 = 1` [2](#0-1) . `amm.lp_amount` is set to the full `liquidity = 2` [7](#0-6) , while only 1 unit is actually minted to the attacker — effectively no meaningful locked liquidity buffer.
3. Prior to a victim's deposit, attacker directly transfers a large amount of USDC into the `amm_pc_vault` token account (a plain SPL transfer, not gated by the AMM program).
4. Victim submits a `Deposit` with `base_side = 1` (base pc) for some amount D. `process_deposit` recomputes `total_pc_without_take_pnl` from the now-inflated vault balance [8](#0-7)  and computes `mint_lp_amount = floor(D * amm.lp_amount / total_pc_without_take_pnl)` [5](#0-4) .
5. Because `amm.lp_amount` is only `2`, the victim must deposit roughly half of the inflated pool value just to receive `1` new LP unit (else the transaction reverts on the zero-share check at line 1323-1325); receiving 1 of the resulting 3 total LP units for contributing roughly half the pool's inflated value transfers value to the attacker's pre-existing LP position, reproducing the StUSR-style dilution dynamic.
