### Title
Cached operator authorization is reused for the full `operator_qr_expiration_time` window without re-validating against the backend, allowing signups to proceed under a since-revoked/invalid operator - (File: `src/plans/mod.rs`)

### Summary
This is a structural analog of the Nouns DAO "stale decision, sneaked-in update" bug class: a decision (backend validation of the operator's identity/authorization) is made once at time T, cached, and then treated as still binding for subsequent unrelated actions (biometric capture, PCP upload, enrollment) taken minutes later, with no re-check against the authoritative source before those actions execute.

### Finding Description
When an operator QR code is scanned, `scan_initial_qr_codes` calls `verify_operator_qr_code`, which performs a single backend call to `backend::operator_status::request` and caches the result (`valid`, `location_data`) into an `OperatorData { qr_code, location_data, timestamp }` struct. [1](#0-0) 

That cached `OperatorData` is then reused, without any further backend re-validation, as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, in `scan_remaining_qr_codes`: [2](#0-1) 

The same pattern appears in `idle_scan_user_qr_code`, where the previously scanned/validated `operator_data` is passed by reference into the loop that scans and validates a new user QR code (`handle_user_qr_code` -> `verify_user_qr_code`), again purely against the stale `timestamp`, not a fresh backend check of operator status: [3](#0-2) 

The user QR-code validation itself (`backend::user_status::request`) is bound to this stale `operator_data`, i.e., the user's authenticity check is validated in the context of an operator whose authorization was confirmed possibly `operator_qr_expiration_time` (a backend-configured duration, no fixed floor enforced in code) ago: [4](#0-3) 

`operator_qr_expiration_time` is a value supplied entirely by the backend config with no local minimum bound in `src/config.rs`, similar to how `MIN_VOTING_DELAY` in the Nouns report could be set arbitrarily low: [5](#0-4) 

The root cause mirrors the reported bug class: an authorization decision is bound only to a coarse validity window/timestamp rather than being re-confirmed against the live/current backend state immediately before the sensitive action (signup enrollment, PCP key issuance) is executed. If an operator is deactivated, banned, or has their distributor status revoked by the backend after the initial scan but within the expiration window, the orb has no mechanism to detect this before completing one or more subsequent user signups under that operator's identity.

### Impact Explanation
An operator whose authorization is revoked mid-window (e.g., due to fraud detection, distributor account suspension) can still have one or more full user signups attributed to them and processed by the orb until the cached timestamp expires, because no re-validation call occurs between the initial scan and the actual enrollment/PCP upload. This can result in unauthorized signups being attributed to (and monetarily/operationally credited to) an operator identity that the backend no longer considers valid, and/or user data being validated/enrolled using stale operator/location context that no longer reflects the operator's real-time status.

### Likelihood Explanation
Exploitation requires a backend-side state change (revocation) to occur within the `operator_qr_expiration_time` window while the orb continues to rely on the cached operator validation for further signups — a plausible operational race rather than a contrived edge case, especially since `operator_qr_expiration_time` is backend-controlled with no enforced minimum/maximum in the orb code.

### Recommendation
Re-validate the operator's authorization against the backend immediately before starting the sensitive enrollment path (or at minimum before uploading PCP tiers / finalizing the signup), rather than relying solely on a cached timestamp comparison. Alternatively, bind the enrollment request cryptographically/contextually to the specific validated operator session rather than to a reusable time-boxed cache, and enforce a conservative minimum/maximum clamp on `operator_qr_expiration_time` in `src/config.rs`.

### Proof of Concept
1. Operator scans QR code; `verify_operator_qr_code` succeeds and `OperatorData` is cached with `timestamp = now`.
2. Backend revokes/suspends this operator (e.g., fraud flag) shortly after.
3. Within `operator_qr_expiration_time`, the orb's `scan_remaining_qr_codes`/`idle_scan_user_qr_code` paths reuse the cached `OperatorData` (`src/plans/mod.rs:793-820`, `456-488`) without calling `verify_operator_qr_code` again.
4. One or more subsequent users are scanned and enrolled (`verify_user_qr_code`, `do_signup`) under the now-invalid operator context, with no re-check ever occurring before completion.
