### Title
Indexed pool rates used by `quoteIntent` are derived from a manipulable off-chain solver-bid aggregation with no on-chain verification or deviation bound - (File: sdk/packages/sdk/src/protocols/intents/quote/indexedRates.ts)

### Summary
`IntentGateway.quoteIntent`'s default `indexed_rates` strategy prices real user orders directly from `LiquidityPool.buyRate`/`sellRate`, values published by the SubQuery indexer from an off-chain, unaudited-by-design aggregation pipeline (`aggregatePhantomBids` → `weightedMedian` → `updateLiquidityPools`). Nothing in that pipeline is proven on-chain; the SDK trusts whatever the indexer's GraphQL API returns, with only a positivity/format sanity check. This mirrors the Frax `ManualTokenTrackerAMO` finding: a privileged/uncontrolled off-chain process feeds a number straight into an economically consequential on-chain-adjacent decision, without independent verification, increasing attack surface and the likelihood of a mispriced, exploitable value.

### Finding Description
`quoteWithIndexedRate` in [1](#0-0)  computes the user-facing `amountOut`/`amountIn` for a real `IntentGatewayV2` order directly from `selectedRate.scaledRate`, which comes from `LiquidityEngine.getBuyAndSellRates` reading the indexer's `LiquidityPool.buyRate`/`sellRate` fields [2](#0-1) . The only validation performed on the returned rate is that it parses as a positive number (`readIndexedRate`) [3](#0-2) ; there is no on-chain proof, no deviation bound, and no cross-check against a second price source (unlike the Uniswap V4 strategy, which has an explicit `referencePrice`/`maxDeviationBps` guard documented in `docs/content/developers/evm/simplex/pricing.mdx`).

The published `sellRate`/`buyRate` values themselves are the output of an off-chain aggregation script, not a proven on-chain oracle:
- `aggregatePhantomBids` collects solver bids for a phantom order, weights each bid by the solver's own destination-chain balance of the output token (read via RPC, not proven), and reduces this to `weightedMedian` — a **selection**, not a cryptoeconomically bounded computation: "a solver holding over half the leg's weight sets the published price verbatim" [4](#0-3) .
- `weightedMedian` itself documents that with insufficient weighted diversity, "whoever quoted higher" can win, and a solver holding no inventory could set the rate for free if the zero-weight-drop guard were ever bypassed [5](#0-4) .
- `updateLiquidityPools`/`mergeChainRowsIntoPool` then merge these per-chain medians into the pool's single `sellRate`/`buyRate` via a depth-weighted mean with only a soft 5x-divergence *warning* (not a rejection) [6](#0-5) .

This entire pipeline runs off-chain in the indexer (a SubQuery process) and is exposed to any caller of the public GraphQL endpoint (e.g., `https://nexus.indexer.polytope.technology`). A single solver that (a) controls the majority of measured output-token inventory on a destination chain for a given leg, or (b) simply operates against a chain/pool with thin, easily-dominated liquidity, can steer `weightedMedian` and therefore the published `sellRate`/`buyRate` to an arbitrary value. `quoteIntent` then feeds that value, unverified, directly into the `amountIn`/`amountOut` of a real `IntentGatewayV2` order that a user is instructed to submit as-is ("Use `quote.amountIn` and `quote.amountOut` exactly as returned... no further fee or slippage adjustment is required" — [7](#0-6) ).

As with the Frax audit finding, the correctness and liveness of this off-chain script are unreviewed on-chain and unbounded: there is no contract-level check that the priced amount is within any sane range of a second, independently-verifiable price source before the order's assets are escrowed via `IntentGatewayV2.placeOrder`.

### Impact Explanation
A manipulated `sellRate`/`buyRate` directly determines the `inputs`/`output.assets` amounts of a real on-chain order that escrows user funds on the source chain and is filled against by an accepting solver on the destination chain. Because the SDK sets the order's committed amounts verbatim from an unverified off-chain figure, an attacker that controls the aggregation output can cause a user to escrow more input than any honest solver would ever offer for the requested output (colluding-solver counterparty extracts the surplus), or, from the other side, requested output can be set below what the market clears, systematically extracting value from users or providers of the pool. This is a Medium/High-severity mispricing vector that puts user-submitted intent funds at risk without needing a compromised admin, governance, or consensus system — a single unprivileged solver's on-chain balance manipulation and/or a bid-verification/inventory-measurement edge case is sufficient.

### Likelihood Explanation
Likelihood is elevated because: (1) `indexed_rates` is now the *default* `quoteIntent` strategy, so every default-configured integrator/user path is exposed [8](#0-7) ; (2) the weighting mechanism is explicitly documented as giving majority-inventory control of the rate to a single solver; (3) thin-liquidity legs/pairs (e.g., newly-listed tokens, low-volume chains) are the easiest and cheapest to dominate; and (4) no on-chain or SDK-side circuit breaker (deviation bound, TWAP, multi-source cross-check) currently exists for this strategy, unlike the Uniswap V4 path.

### Recommendation
Short term: add a mandatory reference-price/deviation guard to the `indexed_rates` strategy (mirroring the Uniswap V4 `referencePrice`/`maxDeviationBps` pattern) so `quoteIntent` refuses to quote when the indexer's rate diverges materially from an independent source. Consider requiring a minimum diversified `bidCount`/`depth` threshold before a rate is trusted, and reject rather than merely warn on the >5x chain-sample divergence case in `warnOnDivergentSample`.

Long term: document this data path's trust assumptions explicitly for integrators (who is running the indexer, how bids are weighted, what a solver needs to control to move the rate), and consider requiring some cryptoeconomic cost (staking/slashing) tied to a solver's ability to move the published rate, rather than relying purely on an off-chain balance read.

### Proof of Concept
1. A solver deploys minimal inventory of a low-liquidity output token (e.g., a newly listed asset) on a destination chain such that it is the only, or dominant, inventory-backed bidder for that leg during a `PhantomBidWindowExhausted` cycle.
2. The solver submits a single low bid (favorable to itself) for the phantom order leg; because its weight (balance) exceeds half of the total backed weight, `weightedMedian` returns its bid verbatim as `medianPrice` [9](#0-8) .
3. `updateLiquidityPools` writes this as the leg's `PoolChainLiquidity.rate`, which becomes the pool's `sellRate`/`buyRate` (the only sample for that direction/chain) [10](#0-9) .
4. Any user calling `gateway.quoteIntent({ tokenIn, tokenOut, amountIn })` receives `amountOut` computed straight from that manipulated rate [1](#0-0) , with no warning, and is instructed to place the order using `quote.amountIn`/`quote.amountOut` "exactly as returned" [11](#0-10) .
5. The user escrows the mispriced amount on `IntentGatewayV2.placeOrder`; the manipulating solver (or a colluding one) fills the order at the skewed rate, extracting the difference from the user's escrowed funds.

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

// A pair prices identically across chains, so one sample far off the others' consensus almost
// certainly means a wrong registry decimals entry poisoning that chain's normalization — worth an
// alarm, but the sample still merges: this cannot tell a bad entry from a genuinely dislocated
// market, and silently dropping data would hide the bug the alarm exists to surface.
function warnOnDivergentSample(
	poolId: string,
	direction: string,
	rows: { chain: string; rate: bigint; depth: bigint }[],
): void {
	if (rows.length < 2) return
	for (const row of rows) {
		const consensus = weightedRate(rows.filter((other) => other !== row))
		if (consensus === 0n) continue
		if (row.rate > consensus * 5n || row.rate * 5n < consensus) {
			logger.warn(
				{ poolId, direction, chain: row.chain, rate: row.rate.toString(), consensus: consensus.toString() },
				"Pool chain sample diverges >5x from the other chains — check the token registry decimals",
			)
		}
	}
}
