### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity purely from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` validates covers only the raw request body. Because the shop-domain field that downstream code uses to attribute the webhook to a tenant is never part of the signed bytes, an attacker who possesses one validly-signed webhook (trivially obtainable by installing the app on their own store) can replay that exact body+HMAC while substituting an arbitrary victim shop domain in the header. `ShopifyAPI::Webhooks::Registry.process` accepts the forged request as authentic and hands the attacker-chosen shop identity straight to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (unsigned) header: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the body — the shop-domain, topic, webhook-id, and api-version headers are never part of the signed material: [3](#0-2) 

`Registry.process` only checks that the HMAC over the body is valid, then immediately trusts `request.shop` (and other unsigned headers) to build the `WebhookMetadata` object passed to the app's handler: [4](#0-3) 

The gem's own documented usage pattern explicitly instructs apps to key their business logic (job enqueueing, tenant routing, persistence) off `data.shop` without any additional binding check: [5](#0-4) 

Because a single app uses one shared `api_secret_key` for every shop that installs it, and the HMAC is computed only over the body, any unprivileged party who installs the (public/dev) app on a store they control can:
1. Trigger any webhook topic (e.g. `orders/create`, `app/uninstalled`, or the mandatory `shop/redact` topic) for their own shop and capture the raw body plus its valid `X-Shopify-Hmac-Sha256` value.
2. Replay that identical body/HMAC pair to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it never inspects the shop-domain header, so `Registry.process` invokes the handler with `WebhookMetadata#shop` equal to the victim's domain.

The binding broken is: `shop authenticated (HMAC-covered bytes) == shop used for tenant attribution (header value)` — the equality does not hold, since the header is outside the HMAC-signed scope.

### Impact Explanation
This crosses a tenant boundary: an app relying on `data.shop` (as the gem's own docs recommend) to route work, update per-shop records, or act on mandatory compliance topics can be made to process attacker-supplied data under a victim shop's identity, or process spoofed lifecycle events (e.g. forged `shop/redact`/`app/uninstalled`) against a shop the attacker does not control. This is cross-tenant access/data-integrity compromise achievable by any unprivileged internet user who can install the app once on a store they own — no access token, `client_secret`, or privileged account is required.

### Likelihood Explanation
Likelihood is high: installing a Shopify app on a self-owned development/test store is a normal, unprivileged action, and replaying an HTTP request with a modified header while keeping the same body is trivial. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler) is the exact, documented way every app is instructed to process webhooks.

### Recommendation
Bind the shop identity into the material that is cryptographically verified, or independently authenticate it before trusting it for tenant routing: e.g. include the shop-domain (and topic/webhook-id) in the HMAC-signed payload, or require the app to cross-check `request.shop` against the shop of the session/webhook registration that was expected to receive that `webhook_id`/topic before invoking the handler. At minimum, document prominently that `data.shop` is unauthenticated and must be independently verified (e.g. against a known-installed-shops list) before being used for any tenant-sensitive action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and configures a webhook subscription for `orders/create`.
2. Shopify sends a legitimately HMAC-signed webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H`, then sends a new HTTP request to the same app webhook endpoint with identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shop-domain" => "victim-shop.myshopify.com"})` is constructed; `HmacValidator.validate` succeeds because it only recomputes `HMAC(api_secret_key, B)` and compares to `H`, which still matches.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, causing the app to act on data or events attributed to `victim-shop.myshopify.com` even though that shop never sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
