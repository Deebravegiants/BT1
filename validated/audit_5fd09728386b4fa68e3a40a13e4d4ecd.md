### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` only proves the body bytes were signed with the app's `client_secret` — it never binds the signature to the `shop` value taken from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` accepts any request whose body HMAC validates and then trusts the header-derived `shop` as the tenant identity forwarded to the app's handler [3](#0-2) , via `WebhookMetadata` [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, body || shop)` such that a validated HMAC also authenticates the claimed `shop`.

In this gem it is actually:
`hmac == HMAC(secret, body)` — with `shop` read independently from an unsigned header [5](#0-4) .

Because a single app's `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any body+HMAC pair that is valid for one shop's webhook delivery is also a syntactically valid body+HMAC pair for a request that a caller submits directly to the app's webhook endpoint with an arbitrary `shop-domain`/`x-shopify-shop-domain` header. `Registry.process` performs no comparison between the header-derived shop and anything cryptographically bound to the body [3](#0-2) , so `HmacValidator.validate(request)` returns true and the handler is invoked with `WebhookMetadata#shop` set to whatever domain the caller supplied, unrelated to the shop that actually produced the body content.

This is the same bug class as the CLN report: a field that is acted upon by downstream logic (`shop`, analogous to `added_htlc`) is not included in the integrity-checked structure (the TLV/HMAC envelope), so validation success does not guarantee the field's authenticity.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key persistence, authorization, or business logic (e.g., "update order status for shop X", "store customer data-request for shop X") can be made to attribute attacker-influenced body content to a victim shop, because the HMAC only proves the app's secret was used to sign *some* body — not that the body belongs to the shop named in the header. This is a cross-tenant data-integrity break reachable by an unprivileged caller who can obtain any one valid (body, hmac) pair for the app's secret (e.g., from their own shop's legitimately delivered webhook) and replay it to the app's public webhook endpoint with a forged shop-domain header.

### Likelihood Explanation
Exploitation requires only: (1) knowledge that the target app exposes a public webhook receiver built on `ShopifyAPI::Webhooks::Registry.process`, and (2) possession of one legitimate (body, hmac) pair produced by any shop using the same app installation (trivially obtainable by an attacker who installs the app themselves and reads their own webhook deliveries). No access to `api_secret_key`, tokens, or TLS interception is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Bind the shop identity into the verified material: either include the `shop` (and ideally `topic`/`webhook_id`) in the signable string used for HMAC validation, or require the caller to independently authenticate/resolve the shop (e.g., cross-check against a shop that has an active webhook registration/session) rather than trusting the unauthenticated header verbatim once body HMAC succeeds.

### Proof of Concept
1. App A is installed on `attacker.myshopify.com` and on `victim.myshopify.com`, sharing one `client_secret`.
2. Attacker triggers a webhook event on their own shop (e.g., `orders/create`) and captures the raw body `B` and its `X-Shopify-Hmac-Sha256` value `H` from the legitimate delivery to their own endpoint/logging.
3. Attacker POSTs directly to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which recomputes HMAC over `B` only and succeeds because `B`/`H` are a genuinely valid pair for the shared secret.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the app to process attacker-supplied content under the victim shop's identity.
