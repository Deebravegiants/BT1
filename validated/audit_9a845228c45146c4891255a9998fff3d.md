### Title
Governance can change `OutboundConsensusDeliveryReward` / `OutboundRequestDeliveryReward` after a relayer has already delivered, causing overpayment or under-compensation on claim - ([File: modules/pallets/relayer/src/outbound_consensus.rs], [File: modules/pallets/relayer/src/outbound_request.rs])

### Summary
`pallet-relayer`'s outbound-delivery reward mechanism is structurally identical to `FeeCollector.claimFees`: a relayer performs work (delivering a hyperbridge-originated consensus proof or request to a destination chain, paying real gas), and can later submit an unsigned claim to collect a reward. The reward amount is read live from storage (`OutboundConsensusDeliveryReward` / `OutboundRequestDeliveryReward`) at claim-processing time rather than being fixed at the time the relayer committed to delivering. Governance can change these values via `set_outbound_consensus_delivery_reward` / `set_outbound_request_delivery_reward` at any time, including in the window between a relayer's delivery and its claim submission, causing the same overpay/underpay mismatch the report describes for `FeeCollector.payoutAmount`.

### Finding Description
The claim-processing functions `Pallet::process_outbound_consensus_delivery_claim` and `Pallet::process_outbound_request_delivery_claim` fetch the reward amount at the moment the claim extrinsic executes: [1](#0-0) [2](#0-1) 

Both `OutboundConsensusDeliveryReward` and `OutboundRequestDeliveryReward` are plain governance-mutable storage maps updated instantly and unconditionally: [3](#0-2) [4](#0-3) 

The flow mirrors `FeeCollector.claimFees`'s keeper mechanism exactly: an unprivileged relayer sees a profitable opportunity (deliver a consensus rotation or hyperbridge-originated request to earn `reward`), commits gas/capital to the delivery on the destination chain, and only later (after the destination state commitment is verified on Hyperbridge and a state proof is built) submits the claim to collect `reward`. There is no mechanism to lock in the reward value at delivery time, nor any check that prevents governance from changing the reward while deliveries are in flight — the same root cause flagged in the report ("it's important that we don't update the payoutAmount... if there are remaining fee tokens" / outstanding obligations).

### Impact Explanation
- If governance decreases the reward after a relayer has already incurred delivery gas costs (based on the old, higher reward), the relayer collects less than expected on claim, potentially at a net loss for having delivered the message — a direct, unprivileged-actor-reachable loss of expected funds.
- If governance increases the reward after a relayer already delivered under the old low reward, the relayer receives an unexpectedly large payout from the treasury (`TreasuryPalletId` account) — an unintended overpayment/protocol loss, exactly the FeeCollector class of bug ("the value of the payoutAmount decreases... it could suddenly make claimFees highly profitable... causing the system to overpay").
- Because reward changes are visible via chain state/events before the claim lands, and claims are permissionless (`ensure_none` origin, `validate_unsigned`), any relayer/observer can race to submit claims opportunistically once they see a favorable reward change land, extracting value from the treasury disproportionate to the actual delivery cost — a treasury-drain vector reachable from unprivileged submitted extrinsics.

### Likelihood Explanation
Medium. It requires governance to actually change a `OutboundConsensusDeliveryReward`/`OutboundRequestDeliveryReward` entry while deliveries are outstanding (an operational event, not attacker controlled), so it isn't attacker-initiated on demand. However, since delivery and claim are decoupled by an unbounded time window (bounded only by challenge period + relayer discretion — the relayer is not forced to claim immediately), and reward parameters are expected to be tuned periodically as part of normal operations, the window for this race is realistically non-trivial and the loss (protocol overpay or relayer underpay) is a direct, concrete fund-flow impact once triggered.

### Recommendation
Snapshot the reward amount at delivery-attribution time instead of reading it live at claim time. Concretely:
- For `process_outbound_consensus_delivery_claim`/`process_outbound_request_delivery_claim`, persist the reward value that was in effect at the block where delivery attribution became provable (e.g., the reward configured at the destination's recorded delivery height/state commitment used in the proof, or a reward-effective-at snapshot keyed by state_id/module_id + height), rather than `OutboundXDeliveryReward::<T>::get(...)` evaluated at claim submission.
- Alternatively, follow the FeeCollector fix pattern: disallow updating `OutboundConsensusDeliveryReward`/`OutboundRequestDeliveryReward` for a given key while there exist un-claimed, already-delivered commitments/rotations for that key, or apply reward changes only prospectively (new reward applies only to deliveries that occur after the change, tracked via an effective-height cutoff).
- Document/queue this as a governance operational safeguard: require a grace/pending-value delay before a reward change takes effect, mirroring the "set pending values which only get updated at the end of claimFees" recommendation from the referenced report.

### Proof of Concept
1. Governance sets `OutboundConsensusDeliveryReward[EVM destination] = R1` via `set_outbound_consensus_delivery_reward`.
2. A relayer observes the mandatory rotation event, delivers the consensus proof to the EVM destination (paying gas), which writes `EvmHost._epochs[set_id] = relayer` via `HandlerV2.handleConsensus -> EvmHost.recordEpoch`.
3. Before the relayer submits `claim_outbound_consensus_delivery_reward`, governance calls `set_outbound_consensus_delivery_reward` again, changing the value to `R2` (R2 << R1, e.g. reward tuning/incident response).
4. The relayer submits the claim; `process_outbound_consensus_delivery_claim` reads `OutboundConsensusDeliveryReward::<T>::get(destination)` at line 174, which now returns `R2`, and pays only `R2` instead of the `R1` the relayer priced their gas expenditure against — realizing a loss.
5. Symmetrically, if `R2 >> R1` (reward increased after delivery), the relayer collects the inflated `R2` reward for a delivery that was only justified/costed at `R1`, draining the treasury of the difference — this is the "overpay" case from the report. [5](#0-4)
