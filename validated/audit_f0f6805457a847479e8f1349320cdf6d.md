### Title
Webhook shop identity is not covered by the HMAC, allowing shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `hmac` and `to_signable_string` (used by `Utils::HmacValidator.validate`) exclusively from the raw request body, while `shop` is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. The identity binding "shop authenticated == shop passed to the application handler" is broken: HMAC validity proves the body was signed by Shopify for *some* shop, but not for the `shop` value the app receives.

### Finding Description
`Request#hmac` returns the digest from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and compares it to the `hmac` header — the `shop` header is never included in the signed content: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)`, then forwards `request.shop` unchanged to the handler as `WebhookMetadata.shop`: [3](#0-2) 

Because the shop identity is carried in a header that is not part of the signed payload, an attacker who controls a legitimate installed shop (Tenant A) can capture a genuine webhook delivery for Tenant A (valid HMAC, valid body) and replay it to the app's webhook endpoint after substituting the `shopify-shop-domain` header value with Tenant B's shop domain. The HMAC check still passes because it never inspected the header, so `Registry.process` invokes the host application's handler with `data.shop == "tenant-b.myshopify.com"` even though the payload was never generated for Tenant B.

Binding broken (as equality):
`shop authenticated by HMAC` ≠ `shop delivered to the handler / used as tenant key`

### Impact Explanation
Host applications (as documented in `docs/usage/webhooks.md`) use `data.shop` returned from `Registry.process` as the tenant key to look up sessions, dispatch background jobs, or write data (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`). If an attacker can trigger genuine webhooks on their own shop (trivial — install the app, perform normal actions) and replay them with a forged `shop-domain` header, they can cause the host app to process attacker-controlled webhook bodies (payload content controlled to the extent Shopify's payload structure allows, e.g. product/order fields) under a victim shop's identity — a cross-tenant data-integrity/confusion issue. This does not directly leak the victim's access token, but it does cross the tenant boundary that the SDK is trusted to establish via HMAC, so it satisfies the High severity bar for "scope/expiry check" analog (identity check that is permissive because it validates the wrong field).

### Likelihood Explanation
Exploitation only requires being a real (even single, low-trust) merchant of the target app to obtain one genuine webhook delivery with a valid HMAC, and the ability to POST to the app's public webhook endpoint with modified headers (webhook endpoints are unauthenticated public endpoints by design). No secrets are required. Likelihood is Medium-High for any app relying on `data.shop` for tenant routing without an independent shop check.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) values in the HMAC-signed content, or otherwise cryptographically bind the shop domain to the payload before validating it, so `Request#to_signable_string`/`hmac` cannot be satisfied by replaying a body captured for a different shop. At minimum, document and/or enforce that host apps must independently verify `data.shop` corresponds to an app-known/installed shop before trusting it as a tenant key, since the current library-level guarantee only proves body integrity, not shop attribution.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST: body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — matches `H` — validation passes: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, and the host app processes attacker-supplied data under the victim tenant's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
