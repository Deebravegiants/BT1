Confirmed: the HMAC signature validated in `Utils::HmacValidator.validate` only covers `request.to_signable_string`, which for webhooks is the raw request body itself.### Title
Webhook shop-domain identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop-domain` header used downstream to attribute the webhook to a specific tenant is never included in that signature. Any request bearing a body/HMAC pair that is valid for the shared app secret can be replayed with an attacker-chosen `shop-domain` header, and the handler will process it as if it originated from that (potentially victim) shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body — no header, including `shop-domain`, `topic`, or `webhook-id`, is folded into the signed bytes: [2](#0-1) 

`Registry.process` uses this same HMAC check as the sole authentication gate, then immediately trusts `request.shop` (parsed from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

Because Shopify apps use a single `client_secret` (`Context.api_secret_key`) shared across every shop that has installed the app, a valid `(body, hmac)` pair generated for one tenant (e.g., a shop the attacker legitimately controls/installs the app on) remains cryptographically valid for any other tenant's identifier. The `shop` value is act­ed on (used to route data to the handler as the webhook's origin) but is not part of the identity binding — breaking the intended equality `hmac_valid(body) == shop_authenticated(shop_header)`.

### Impact Explanation
This is a cross-tenant confusion at the authentication boundary: an unprivileged user who can install the target app on their own store (a normal, unprivileged action) can capture a genuine `(body, hmac)` pair from their own shop's webhook delivery, then replay that exact payload to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. The app's `WebhookHandler` will process attacker-controlled data under the identity of the victim shop (e.g., triggering `shop/redact`, `customers/redact`, or business-logic side effects keyed by `shop`), since nothing in the signature ties the payload to the shop claimed in the header. This falls under the "Critical – cross-tenant access" category since it lets one tenant inject events attributed to another tenant.

### Likelihood Explanation
Reachable by any unprivileged internet user with a test/dev store: no `api_secret_key`, access token, or privileged account is needed beyond installing the app on their own shop (a standard developer/merchant action), after which they control both the body and a correctly computed HMAC for any payload of their choosing.

### Recommendation
Bind the shop identity into the authenticated request, e.g. include the normalized `shop-domain` (and `topic`) header value in `to_signable_string` before computing/verifying the HMAC, or otherwise cross-check the `shop-domain` header against a value derived from data that is itself covered by the signature (such as a `shop` field embedded in the signed body). This mirrors the general pattern already applied to the JWT-based session flows, where the shop is derived exclusively from the signed `dest` claim rather than an out-of-band value.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook delivery (e.g., `orders/create`) and capture the raw request body `B` and the `X-Shopify-Hmac-Sha256` header `H` — `H` is `HMAC-SHA256(client_secret, B)`, valid because the app secret is the same for every shop.
3. Send a new POST to the app's webhook endpoint with the same body `B` and header `H`, but set `shopify-shop-domain: victim.myshopify.com` (and any `topic`/`webhook-id` desired).
4. `HmacValidator.validate` succeeds (it only checks `B` against `H`), and `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, so the app processes attacker-supplied data as if it came from the victim shop — confirmed by tracing `Request#to_signable_string` → `HmacValidator.validate_signature` → `Registry.process`.
