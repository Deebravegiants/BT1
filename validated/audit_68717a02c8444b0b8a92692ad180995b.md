### Title
Meta-transaction (`DelegateAction`) signatures lack chain/fork binding, enabling cross-fork replay of relayed actions - (File: `core/primitives/src/action/delegate.rs`)

### Summary
Regular NEAR transactions bind their signature to a specific chain history via `Transaction::block_hash`, which is validated for fork-ancestry on every submission [1](#0-0) . Meta-transactions (`SignedDelegateAction`/`VersionedSignedDelegateAction`, NEP-366) sign only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — no block hash or chain-identifying value is part of the signed payload [2](#0-1) . Consequently a validly signed delegate action can be replayed on any chain/fork where the referenced access key still has a lower nonce, exactly analogous to the reported Phi bug where a signature valid on one chain was replayable on another because the chain-binding field was not checked.

### Finding Description
`SignedDelegateAction::verify` and `VersionedSignedDelegateAction::verify` compute the signed hash purely from the `DelegateAction`/`DelegateActionV2` payload fields, with no dependency on any block hash or chain-specific value [3](#0-2) [4](#0-3) . The runtime-side validation of a delegate action in `apply_delegate_action` and `validate_delegate_action_key` only checks the signature itself, `max_block_height` (a plain height number, not a specific block), and the access-key nonce state at the *sender's* current shard/chain — there is no check that the delegate action was produced for, or is being applied to, a specific chain [5](#0-4) [6](#0-5) .

By contrast, plain `SignedTransaction`s are chain-bound: their `block_hash` is checked for validity-period and, crucially, for being an actual ancestor of the current chain via `validity_period_validate_is_ancestor`, which explicitly rejects transactions built on a hash that is not part of the local chain's history (`InvalidTxError::InvalidChain`) [7](#0-6) [8](#0-7) . This is precisely the fork/chain replay defense that is missing from the inner `DelegateAction` signature. The outer wrapping `SignedTransaction` (submitted by the relayer) does get this ancestry check, but that only protects the relayer's own signature/nonce — it does nothing to bind the *inner* `SignedDelegateAction` bytes signed by the end user to one particular chain history. An attacker (or the relayer itself) can take any previously observed, still-unconsumed `SignedDelegateAction` and re-wrap it in a fresh, validly-signed outer transaction on a sibling chain/fork where the sender's access key nonce has not yet advanced past `delegate_action.nonce`.

### Impact Explanation
If a persistent chain split occurs (e.g. a contentious upgrade, a rolled-back/duplicated network built from the same genesis/state snapshot, or any scenario producing two chains that share pre-fork account/access-key state), a meta-transaction signed once by a user can be executed a second time on the sibling chain, moving funds or executing privileged actions (e.g. `AddKey`, `Transfer`, `FunctionCall`) that the user only intended to authorize once. This is an unauthorized/duplicated state and balance change directly reachable by submitting an ordinary transaction (`Action::Delegate`/`Action::DelegateV2`) containing the replayed `SignedDelegateAction`, with no elevated privileges required, matching the same signature-replay root cause as the referenced report (missing chain-binding value in the signed payload).

### Likelihood Explanation
This requires the existence of two chains/forks sharing pre-fork nonce state for the relevant access key — it is not exploitable on a single, healthy chain because the nonce check in `validate_delegate_action_key` prevents same-chain replay (confirmed by `test-loop-tests/src/tests/gas_keys.rs`, "Replaying the same delegate (same gas key nonce) is rejected") [9](#0-8) . However, such splits are a realistic occurrence in NEAR's history (contentious upgrades, testnet resets from mainnet-like state, disaster-recovery forks), and unlike normal transactions, meta-transactions have no defense at all once such a split exists — the gap is entirely due to a missing design element (chain binding) rather than a rare double-fault.

### Recommendation
Include a chain-binding value in the data that `SignedDelegateAction`/`DelegateActionV2` sign — e.g. a recent `block_hash` (mirroring `Transaction::block_hash`) that is checked for validity-period and fork-ancestry the same way ordinary transactions are, or a persistent `genesis_hash`/chain identifier — so that a delegate action signed for one chain cannot be replayed on a sibling/forked chain.

### Proof of Concept
1. Alice signs a `DelegateAction { sender_id: alice, receiver_id: ft, actions: [ft_transfer(bob, 1000)], nonce: N, max_block_height: H }` and hands it to relayer R (see `SignedDelegateAction::sign` in `core/primitives/src/action/delegate.rs`).
2. R wraps it in an outer `SignedTransaction` and submits it on chain A; it executes, and Alice's access key nonce advances past `N` on chain A only, per `validate_delegate_action_key` (`runtime/runtime/src/actions.rs`).
3. A chain split occurs such that chain B still has Alice's access key nonce below `N` (e.g., B is a rolled-back/duplicated state snapshot of the pre-split chain, or a persistent fork).
4. R (or anyone who observed the original `SignedDelegateAction` bytes, which are not secret once broadcast) wraps the identical `SignedDelegateAction` in a new, freshly-signed outer `SignedTransaction` (valid `block_hash`/nonce on chain B) and submits it to chain B.
5. `apply_delegate_action` verifies the (unchanged) inner signature successfully, `validate_delegate_action_key` accepts it because nonce `N` is still greater than chain B's stored nonce, and the `ft_transfer` executes a second time — moving another 1000 tokens on chain B that Alice only authorized once.

/// ahead of the block that has `base_block_hash`.
pub fn check_transaction_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_header.height().saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_header.height() > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is an ancestor of `prev`)
    validity_period_validate_is_ancestor(&base_header, prev_block_header, chain_store)
}

/// Check if base_header is an ancestor of prev_block_header.
/// Used in check_transaction_validity_period.
fn validity_period_validate_is_ancestor(
    base_header: &BlockHeader,
    prev_block_header: &BlockHeader,
    chain_store: &ChainStoreAdapter,
) -> Result<(), InvalidTxError> {
    let base_height = base_header.height();
    let prev_height = prev_block_header.height();
    let base_block_hash = base_header.hash();

    // Base can't be an ancestor of prev if its height is bigger
    if base_height > prev_height {
        return Err(InvalidTxError::InvalidChain);
    }

    // if both are on the canonical chain, comparing height is sufficient
    // we special case this because it is expected that this scenario will happen in most cases.
    if let Ok(base_block_hash_by_height) = chain_store.get_block_hash_by_height(base_height) {
        if &base_block_hash_by_height == base_block_hash {
            if let Ok(prev_hash) = chain_store.get_block_hash_by_height(prev_height) {
                if &prev_hash == prev_block_header.hash() {
                    return Ok(());
                }
            }
        }
    }

    // if the base block height is smaller than `last_final_height` we only need to check
    // whether the base block is the same as the one with that height on the canonical fork.
    // Otherwise we walk back the chain to check whether base block is on the same chain.
    let last_final_height = chain_store
        .get_block_height(prev_block_header.last_final_block())
        .map_err(|_| InvalidTxError::InvalidChain)?;

    if last_final_height >= base_height {
        let base_block_hash_by_height = chain_store
            .get_block_hash_by_height(base_height)
            .map_err(|_| InvalidTxError::InvalidChain)?;
        if &base_block_hash_by_height == base_block_hash {
            Ok(())
        } else {
            Err(InvalidTxError::InvalidChain)
        }
    } else {
        let header =
            get_block_header_on_chain_by_height(chain_store, prev_block_header.hash(), base_height)
                .map_err(|_| InvalidTxError::InvalidChain)?;
        if header.hash() == base_block_hash { Ok(()) } else { Err(InvalidTxError::InvalidChain) }
    }
