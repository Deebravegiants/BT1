Confirmed: for OAuth's `AuthQuery`, `shop` is part of the HMAC-signed content [1](#0-0) , so that flow is not vulnerable. The webhook `Request`, however, signs only the raw body and leaves the `shop`, `topic`, `webhook-id`, and `api-version` headers completely outside the HMAC computation.

### Title
Webhook `shop` (and topic/webhook-id) identity is not covered by the HMAC, allowing shop-spoofed webhook delivery to be accepted as authentic - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` checks the HMAC solely against that raw body [2](#0-1) [3](#0-2) . The `shop` value used as the tenant identity for the webhook (`request.shop`, taken from the `shop-domain` header) is never included in the signed content [4](#0-3) . `Registry.process` validates the HMAC and then forwards `request.shop` unmodified to the app's `WebhookHandler#handle` as the trusted tenant identifier in `WebhookMetadata` [5](#0-4) [6](#0-5) .

### Finding Description
The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_the_shop_used_by_the_handler`

Here this equality is broken: `hmac_signed_bytes = raw_body` only, while `bytes_that_determine_the_shop_used_by_the_handler = shop-domain header`, a value entirely outside the signed payload.

Concretely:
- `Request#hmac` reads `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [7](#0-6) .
- `Request#to_signable_string` returns `@raw_body`, excluding all headers [2](#0-1) .
- `Request#shop` is read straight from the (unsigned) `shop-domain` header [4](#0-3) .
- `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`, so it authenticates the *body* only [8](#0-7) .
- `Registry.process` gates on this HMAC check and then trusts `request.shop` as the tenant identity handed to the app: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [9](#0-8) .

Because the `shop` header is not part of the signed bytes, any request carrying a *valid* `(raw_body, hmac)` pair for the app's secret—which an attacker can obtain by owning any shop that installs the app and triggering a real webhook of their choosing to their own endpoint—can be replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to an arbitrary victim shop. `HmacValidator.validate` will still return `true` because it re-derives the HMAC solely from `raw_body`, which is unchanged. The gem then hands `WebhookMetadata` with the attacker-chosen `shop` value to the host application's webhook handler as if it were an authenticated, Shopify-originated statement about that victim shop.

This is directly analogous to the referenced bug class ("a shop authenticated versus the shop stored as a session key"): the gem validates one thing (body integrity) but the field actually used downstream for tenant identification (`shop`) is a completely different, unauthenticated value.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` from a `Webhooks::Request` to key per-tenant state (e.g., to select which merchant's `access_token`/session to update, invalidate, or act upon in response to a webhook, or to attribute mandatory-webhook actions like `customers/redact` to a shop) can be made to apply attacker-controlled webhook bodies under a victim shop's identity. This is a cross-tenant identity-binding break enabled purely by an unprivileged internet user who is a customer/merchant of the app on their own store — they need no access token, no `client_secret`, and no privileged account of the victim; they only need one authentic sample webhook for their own tenant. This satisfies the Critical/High bar of "cross-tenant access" via a scope/identity-binding bypass in this gem's own webhook-processing code.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker must (a) be a legitimate installer of the target app on some shop so that Shopify sends them at least one real webhook with a known raw body and valid HMAC, and (b) be able to send an arbitrary HTTP request directly to the app's public webhook endpoint with a forged `shop-domain` header (bypassing Shopify's own delivery infrastructure), which is possible because the endpoint is a normal internet-reachable URL and this gem performs no additional binding of the header to the signature. No secret material or privileged access is required beyond normal use of the target app.

### Recommendation
Include the identity-relevant headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed/verified content, or otherwise cryptographically bind them to the HMAC-verified `raw_body` before exposing them via `WebhookMetadata`. At minimum, `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the shop domain (and topic) so that `HmacValidator.validate` fails if these are tampered with independently of the body, restoring the equality between "what Shopify signed" and "what the app treats as the tenant identity."

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`), receiving from Shopify a POST to the app's webhook endpoint with:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw_body B>`
   - body `B`
2. Attacker resends this exact request to the same public endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping `raw_body = B` and `x-shopify-hmac-sha256` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — identical to step 1 — and returns `true` [10](#0-9) .
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app now processes attacker-controlled data under the victim shop's identity [11](#0-10) .
