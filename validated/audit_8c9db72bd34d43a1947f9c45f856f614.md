This is a genuine architectural finding worth documenting. I found strong evidence: the `HyperbridgeLzEndpoint` explicitly implements strict per-channel nonce ordering (rejecting `InvalidNonce` if out of sequence) precisely because ISMP/Hyperbridge itself provides **no ordering guarantee** for message delivery — `HandlerV2.handlePostRequests` and `EvmHost.dispatchIncoming` process each `PostRequestLeaf` independently, in whatever order the relayer includes them in the batch, with no nonce-sequencing check. This confirms the analog exists at the core dispatch layer, and other `IApp` implementations built on `IntentsBase`/`IntentGatewayV2`/`ExtrinsicIntents` that don't implement their own explicit ordering (like the LZ endpoint does) are exposed to the same reordering risk documented in the original report.

### Title
Permissionless relayers can deliver batched POST requests out of order, breaking ordering-dependent application logic - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handlePostRequests` and `EvmHost.dispatchIncoming` process each request in a batch strictly in the order the *relayer* chooses to include leaves in the `PostRequestMessage.requests` array, with no enforcement that requests from the same source/sender are delivered in ascending `nonce` order. Any `IApp` module built on top of ISMP that assumes causal/sequential ordering between consecutive messages from the same source (e.g., "deposit" then "withdraw", "create" then "cancel", or any two-step protocol state machine) can have its invariants violated by a relayer (or even an honest relayer racing multiple pending proofs) submitting requests out of nonce order, since delivery is fully permissionless and unordered by design.

### Finding Description
`EvmHost.dispatch` assigns nonces monotonically at dispatch time via `_nextNonce()` [1](#0-0) , and `pallet_ismp::Pallet::dispatch_request` does the same via `self.next_nonce()` on the Substrate side [2](#0-1) . However, nonce assignment at the source only fixes causal *order*, not delivery order.

On the destination, `HandlerV2.handlePostRequests` iterates over `request.requests[]` — an array fully controlled by whichever relayer assembles the calldata — validating destination, timeout, and duplicate-delivery per leaf, but never checking that `leaf.request.nonce` is the next expected nonce for that `(source, from)` pair before calling `host.dispatchIncoming(leaf.request, _msgSender())`: [3](#0-2) 

`EvmHost.dispatchIncoming` itself likewise has no ordering check — it only guards against duplicate delivery via `_requestReceipts[commitment]` before invoking `IApp.onAccept`: [4](#0-3) 

The permissionless nature of this path (any relayer may submit any proven subset of messages, in any order, at any time up to the timeout) is explicitly documented as a protocol property: [5](#0-4) , and the Rust relayer client itself builds request batches by chunking retriable requests without imposing per-sender ordering constraints: [6](#0-5) 

Notably, the project's own `HyperbridgeLzEndpoint.onAccept` recognizes this gap and defends against it by tracking `_inboundNonce[receiver][srcEid][sender]` and rejecting any delivery whose `nonce` isn't exactly `expectedNonce + 1`: [7](#0-6)  — this is a targeted, app-level mitigation for exactly the ordering hazard described in the report, confirming the underlying ISMP transport provides no such guarantee itself. Other `IApp` implementations (e.g. `IntentGatewayV2`/`ExtrinsicIntents` governance `Execute`/`SetRelayer` sequencing) do not implement equivalent nonce-gating, and are explicitly documented as being vulnerable to reordering when multiple undelivered requests to the same recipient are outstanding: "never dispatch a second `SetRelayer` or `UpgradeContract` while one is undelivered... the relayer picks delivery order" [8](#0-7) .

### Impact Explanation
Any application module built on the ISMP `IApp` interface that dispatches multiple sequential, state-dependent POST requests to the same destination module (deposit-then-withdraw, approve-then-transfer, create-then-cancel, any two-phase protocol) is at risk of having those messages delivered out of order by a relayer, since neither `HandlerV2` nor `EvmHost` enforce sequencing. Depending on the app's logic, this can cause: reverted transactions and stuck relayer fees, permanently inconsistent application state (e.g. a "cancel" applied before the "create" it targets, or a later state-mutating governance/config message landing before an earlier one it was meant to supersede — as explicitly acknowledged for `SimplexPaymaster`/`ExtrinsicIntents.setRelayer` sequencing), or unauthorized/incorrect app action. Since delivery is fully permissionless, a malicious relayer can deliberately choose an adversarial ordering (front-running with only the second-of-two related messages) to grief or manipulate app state without needing any special privilege.

### Likelihood Explanation
High. Delivery ordering is entirely under the control of whichever relayer submits `handlePostRequests`/`batchCall`, requires no special permissions, and no code path in `HandlerV2.sol`, `EvmHost.sol`, or `pallet-ismp`'s `handle_incoming_message`/`request::handle` enforces nonce sequencing for delivery. Any app with implicit ordering assumptions between consecutive same-sender messages is exposed by default; only apps that explicitly implement their own nonce-gating (like `HyperbridgeLzEndpoint`) are protected.

### Recommendation
Add an opt-in ordering-enforcement primitive at the ISMP transport layer (mirroring `HyperbridgeLzEndpoint`'s pattern) so that `IApp` developers can request strict per-(source, from) nonce delivery ordering, rejecting or holding a request until all lower nonces from the same sender have been delivered. Alternatively, document explicitly (and provide a reusable base contract/library) requiring every `IApp` that depends on message causality to implement its own inbound nonce tracking analogous to `HyperbridgeLzEndpoint._inboundNonce`, and audit existing first-party apps (`IntentGatewayV2`, `ExtrinsicIntents`, `SimplexPaymaster`, `HyperFungibleToken`) for any implicit ordering dependency between consecutive dispatches to the same recipient.

### Proof of Concept
1. App `A` on chain `X` dispatches `PostRequest` #1 (nonce `n`) to app `B` on chain `Y`, encoding a state-dependent action (e.g., "open position").
2. App `A` immediately dispatches `PostRequest` #2 (nonce `n+1`) to the same `B`, encoding a dependent action (e.g., "close position").
3. Both requests are proven and become deliverable on Hyperbridge/`Y`. A relayer (or two competing relayers) submits `handlePostRequests` for request #2 first, since `HandlerV2.handlePostRequests` [9](#0-8)  performs no nonce-ordering check across the batch or against previously delivered requests.
4. `EvmHost.dispatchIncoming` [4](#0-3)  calls `B.onAccept` for request #2 before #1 has ever been delivered; if `B`'s logic assumes #1 always precedes #2 (as most naive dApps do, per the report's stake/unstake example), the call either reverts (griefing the relayer fee and stalling delivery, since a fresh nonce-`n` request can still be delivered later or timeout, an inconsistent state) or, worse, silently succeeds against invalid preconditions, corrupting `B`'s state.
5. Request #1 (nonce `n`) is later delivered anyway (no anti-replay or ordering rejection exists for it, only duplicate-commitment protection), executing against state that has already moved past where `A` expected — an outcome the destination app cannot generally recover from without its own explicit nonce-gating, as `HyperbridgeLzEndpoint` implements.

        address destination = _bytesToAddress(request.to);

            return;

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

/// Regroup the requests that made it through into batches the destination can
/// take in one call, each proved once for the whole batch.
async fn batch_requests(
	ctx: &RetryContext,
	profitable: &[(PostRequest, Query)],
	height: StateMachineHeight,
) -> Result<Vec<Message>, anyhow::Error> {
	let dest_state_machine = ctx.dest.state_machine_id().state_id;
	let mut messages = vec![];

	for chunk in profitable.chunks(chunk_size(dest_state_machine)) {
		let (requests, queries): (Vec<_>, Vec<_>) = chunk.iter().cloned().unzip();
		let proof = ctx
			.hyperbridge
			.query_requests_proof(height.height, queries, dest_state_machine)
			.await?;

		messages.push(Message::Request(RequestMessage {
			requests,
			proof: Proof { height, proof },
			signer: ctx.dest.address(),
		}));
	}

	Ok(messages)
}
