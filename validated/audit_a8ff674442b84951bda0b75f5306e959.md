Based on the investigation, I found a solid analog for the Dovecot SASL DoS bug class (invalid input from one session breaking a shared resource for all concurrent sessions).

### Title
Unprofitable/malformed message from any user permanently blocks delivery of unrelated bundled requests via atomic `batchCall` - ([File: tesseract/messaging/evm/src/tx.rs])

### Summary
`IHandlerV2.batchCall` executes multiple independent ISMP messages (a consensus update plus N unrelated `PostRequest`/`GetResponse` deliveries from potentially many different users) atomically in one transaction: any single call reverting reverts the whole batch [1](#0-0) . The tesseract relayer builds these batches by grouping all currently-deliverable events for a destination into one `batchCall`, mixing a mandatory consensus/rotation proof with many independent users' requests [2](#0-1) , and dispatches batches of size ≥2 exclusively through the atomic path with no fallback to per-message submission [3](#0-2) .

### Finding Description
A single deterministically-reverting message inside a batch (e.g., a request whose destination module callback always reverts, or a message that fails `handlePostRequests`/`handleGetResponses` validation for reasons outside the relayer's pre-checks) causes the entire `batchCall` transaction to revert via `BatchCallFailed` [4](#0-3) , confirmed atomic by `testBatchCallRevertsAtomically` [5](#0-4) . This is the same bug class as the Dovecot SASL issue: invalid/malicious input from one "session" (message) causes a shared resource (the batch/login process) serving many unrelated concurrent sessions to fail entirely, denying service to legitimate ones. Because the relayer routes batches of size ≥2 only through this atomic path with "no...fallback...supported for real batches" [6](#0-5) , and because it groups all currently-ready messages for a destination into a single batch every cycle, a message that reliably reverts on-chain but passes the relayer's off-chain profitability/timeout checks will be repeatedly re-batched with fresh unrelated messages and repeatedly fail the whole batch, until it is identified and separated out.

### Impact Explanation
This can cause temporary-to-persistent freezing of unrelated, legitimate message deliveries (funds/state updates) to a destination chain, since one bad actor's message can indefinitely block delivery of many other users' bridged requests bundled in the same relayer batch, degrading the route's ability to deliver messages until relayer operators intervene.

### Likelihood Explanation
Requires an attacker to be able to dispatch (or already have dispatched) a request that the relayer's off-chain checks (timeout, profitability, module allowlist) do not filter but that deterministically reverts on-chain delivery (e.g., a malicious/broken destination module `on_accept`, or a request crafted to fail a check the Handler enforces but the relayer doesn't pre-simulate for). This is plausible for any permissionless-dispatch path to an untrusted/attacker-controlled destination module.

### Recommendation
Consider isolating per-message failures in `batchCall` (e.g., using low-level calls with per-call try/catch and reporting failed indices without reverting the whole batch, similar to the isolation pattern already used in `HyperbridgeLzEndpoint.onAccept`), or have the relayer detect and quarantine a message that fails simulation/repeatedly fails on-chain before rebatching it with unrelated messages.

### Proof of Concept
1. Attacker deploys/controls a destination module that always reverts `on_accept`/`lzReceive`-equivalent for its `PostRequest`.
2. Attacker dispatches a `PostRequest` to that module; it is not filtered out by relayer's off-chain checks (timeout not expired, module not excluded, profitable to relay).
3. Relayer's outbound loop batches this request together with several other unrelated users' deliverable requests into one `batchCall` [7](#0-6) .
4. `batchCall` reverts atomically at the malicious module's call [8](#0-7) , so none of the other bundled users' requests are delivered.
5. Next relayer cycle re-batches the same poison message with newly-ready messages, repeating the failure.

    /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }
