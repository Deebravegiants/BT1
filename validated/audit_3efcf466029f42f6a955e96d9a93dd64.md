### Title
`begin_auth` builds the OAuth redirect URI from an unsanitized `shop` value, enabling forced OAuth redirect to an attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` passes the caller-supplied `shop` string directly into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` with no call to `ShopifyAPI::Utils::ShopValidator.sanitize!` or any other domain validation. The gem's own `docs/usage/oauth.md` documents taking `shop` straight from an inbound request (`request.headers["Shop"]`) and feeding it to `begin_auth`, so any attacker who controls that value can force the app's login endpoint to redirect the victim's browser to an attacker-controlled origin, carrying `client_id`, `redirect_uri`, and `state`.

### Finding Description
The binding that should hold is: `shop_used_in_auth_route == ShopValidator.sanitize!(shop)`. Tracing `lib/shopify_api/auth/oauth.rb`:
- `begin_auth(shop:, redirect_path:, ...)` (lines 22-52) does no validation of `shop` at all - it only checks `Context.setup?` and `Context.private?` (lines 31-34).
- Line 49: `auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"`.
- `auth_base_uri` (lines 117-128) does: `return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")` - i.e., for any shop value that isn't a `.my.shop.dev` dev-server string, it returns `"https://#{shop}/admin"` verbatim.

`ShopifyAPI::Utils::ShopValidator.sanitize!` exists in the codebase specifically to enforce that a shop domain belongs to `TRUSTED_SHOPIFY_DOMAINS` (`lib/shopify_api/utils/shop_validator.rb`, lines 56-64), and it is used by `TokenExchange`, `RefreshToken`, and `ClientCredentials` — but `Oauth.begin_auth`/`auth_base_uri` never calls it. So the equality `shop_used_in_auth_route == sanitize!(shop)` is false: the raw, attacker-suppliable string is used unchanged.

Attack: attacker sends `GET /login?shop=evil.attacker-controlled.example` (or via a header, per the gem's own documented example `shop = request.headers["Shop"]`) to the host app's login route, which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` exactly as shown in `docs/usage/oauth.md`. `auth_base_uri` returns `"https://evil.attacker-controlled.example/admin"`, and `begin_auth` returns `auth_route: "https://evil.attacker-controlled.example/admin/oauth/authorize?client_id=...&redirect_uri=...&state=..."`. The host app 302/307-redirects the victim's browser there, per the documented controller example (lines 195-199 of the doc). No existing guard catches this: `Context.setup?`/`private?` only gate configuration state, not the `shop` value; `HmacValidator`, JWT `aud` checks, and `state` comparison only apply later, in `validate_auth_callback`, and are irrelevant to the redirect construction step.

### Impact Explanation
This is SSRF-style forced redirection: the victim merchant's browser is sent to an attacker-chosen host carrying the app's real `client_id`, `redirect_uri`, and a freshly minted `state` nonce (also set as an httpOnly cookie value on the victim's browser). The attacker's server can capture this and craft a phishing page mimicking the Shopify OAuth consent screen, or use the leaked `state`/cookie value to attempt forced OAuth completion / session fixation against the victim. This matches "High - SSRF driving an authenticated-context redirect to an unintended host, session fixation or forced OAuth completion." It is repeatable against arbitrary victims since each request produces a fresh `state`/cookie pair and no shop is validated.

### Likelihood Explanation
Preconditions: the host app must forward request-controlled data as the `shop:` argument to `begin_auth` without pre-validating it against `ShopValidator` or a known-shop allowlist. This is exactly how the gem's own documentation (`docs/usage/oauth.md`, "Add a route to start OAuth") demonstrates usage: `shop = request.headers["Shop"]` then `Oauth.begin_auth(shop: domain, ...)`. Attacker cost is a single unauthenticated HTTP request with a crafted `shop` parameter/header — no credentials, tokens, or prior access required.

### Recommendation
In `ShopifyAPI::Auth::Oauth.begin_auth`, call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop, myshopify_domain: Context.myshopify_domain)` (or equivalent) before using `shop` in `auth_base_uri`, raising `Errors::InvalidShopError` for any shop that is not a trusted Shopify domain, matching the pattern already used in `TokenExchange`, `RefreshToken`, and `ClientCredentials`.

### Proof of Concept
```ruby
# test/auth/oauth_test.rb (new test)
def test_begin_auth_raises_for_untrusted_shop_host
  ShopifyAPI::Context.setup(
    api_key: "key", api_secret_key: "secret", api_version: "2024-01",
    scope: "read_products", host_name: "app.example.com",
    is_private: false, is_embedded: false,
  )

  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.attacker-controlled.example", redirect_path: "/auth/callback")
  end
end

def test_begin_auth_current_behavior_leaks_attacker_host
  ShopifyAPI::Context.setup(
    api_key: "key", api_secret_key: "secret", api_version: "2024-01",
    scope: "read_products", host_name: "app.example.com",
    is_private: false, is_embedded: false,
  )

  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.attacker-controlled.example", redirect_path: "/auth/callback")
  uri = URI.parse(result[:auth_route])
  assert_equal "evil.attacker-controlled.example", uri.host # demonstrates the unvalidated redirect target
end
```
Before the fix, `test_begin_auth_current_behavior_leaks_attacker_host` passes (demonstrating the vulnerability) and `test_begin_auth_raises_for_untrusted_shop_host` fails (no `InvalidShopError` is raised). After adding `ShopValidator.sanitize!` to `begin_auth`, the first test should raise `InvalidShopError` and the second should pass.
