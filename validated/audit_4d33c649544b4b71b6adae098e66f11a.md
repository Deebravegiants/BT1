### Title
Fee-on-transfer tokens cause escrow over-crediting and insolvency in Tron `IntentGatewayV2.placeOrder()` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits escrow (`_orders[commitment][token]`) with the user-specified `order.inputs[i].amount` (minus protocol fee) rather than the amount actually received by the contract. For fee-on-transfer ERC20 tokens, the contract receives strictly less than `order.inputs[i].amount`, so the escrow ledger overstates the gateway's real token balance for that `token` across all outstanding orders.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived solely from the user-declared `order.inputs[i].amount` reduced only by the protocol fee — it never reflects the actual balance delta on the contract.

This is precisely the bug class from the referenced report: the contract assumes `amount` transferred equals `amount` received, which is false for fee-on-transfer tokens (e.g. STA, PAXG-style fee tokens). Notably, this exact issue was already identified and fixed in the canonical EVM contract, `evm/src/apps/IntentGatewayV2.sol`, which snapshots `balanceOf` before and after the transfer and mutates `order.inputs[i].amount` to the actual received amount: [2](#0-1) 
The Tron fork was not updated with this fix, so it remains vulnerable, as confirmed by the dedicated regression tests added for the EVM contract (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) that would fail against the Tron code path.

The `_orders` mapping is a shared per-token accounting ledger across **all** commitments/orders in the contract; the actual ERC20 balance held by the contract is a single pooled value per token. Any order using a fee-on-transfer input token inflates the ledger beyond the real balance, meaning the contract now claims to hold more tokens (in aggregate, across all `_orders[...][token]` entries) than it physically possesses.

### Impact Explanation
Because escrow accounting is shared across all orders for a given token, over-crediting from one fee-on-transfer order creates a systemic shortfall. When escrow is later released via `withdraw()`: [3](#0-2) 
`withdraw()` uses a raw low-level `token.call(...transfer...)` and does not check the return value beyond `success` (which for most standard ERC20s returns `true` even if balance is insufficient it will revert; but the accounting itself is now wrong). Whichever solver/beneficiary withdraws first drains real token balance disproportionately, and subsequent legitimate withdrawals for other unrelated orders sharing the same token can revert (`TransferFailed`) because the contract's actual balance is depleted before the ledger is exhausted — a permanent freezing of funds for later claimants, or a race where an attacker deliberately places a large fee-on-transfer order to inflate their own credited escrow beyond what they deposited, then fills/cancels to extract more tokens than they actually contributed, at the expense of other users' escrowed balances (fund theft from other orders' pooled balance).

### Likelihood Explanation
Reachable by any single unprivileged user calling `placeOrder()` with a fee-on-transfer ERC20 as an input token — no special privileges required. Fee-on-transfer tokens are a known, common token pattern (e.g., PAXG, STA and various DeFi/rebasing tokens); the Tron deployment does not restrict which ERC20 tokens can be used as order inputs.

### Recommendation
Apply the same balance-snapshot fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: capture `balanceOf(address(this))` before and after `safeTransferFrom`, use the actual delta as the amount used both for the commitment computation and for `_orders[commitment][token]` crediting, instead of trusting the nominal `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token (e.g., 1% fee) and register it as a valid input token.
2. User calls `placeOrder()` on the Tron `IntentGatewayV2` with `inputs[0] = {token: FOT, amount: 1000e18}` and no `protocolFeeBps`.
3. `safeTransferFrom` moves 1000e18 nominal, but the contract actually receives only 990e18 (1% fee retained by the token).
4. `_orders[commitment][FOT] += 1000e18` is credited (per `evm/tron/contracts/apps/IntentGatewayV2.sol:463`), while the contract's real FOT balance increased by only 990e18.
5. Repeat with other orders using the same FOT token, or simply cancel/fill this order and withdraw — the ledger for this token now permanently exceeds the real balance by 10e18 per such order, causing insolvency: some legitimate escrow withdrawals for `FOT` across the contract will revert due to insufficient actual balance, freezing those users' funds.
