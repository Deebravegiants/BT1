### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller a `shop` value that is read from an HTTP header the HMAC never covers. Because the signing secret (`Context.api_secret_key`) is the app's single client secret shared across every installed shop, any tenant that has a legitimately-signed webhook body can relabel it with a different `shop` header and have it accepted as authentic for another tenant.

### Finding Description
The webhook signature check computes the HMAC over `to_signable_string`, which is defined to be only the raw request body: [1](#0-0) 

The `shop` accessor used downstream is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, immediately trusts `request.shop` to build the `WebhookMetadata` object handed to the app's handler: [3](#0-2) 

The HMAC secret used here is `Context.api_secret_key`, the app's single OAuth client secret, not a per-shop key: [4](#0-3) 

The identity binding that should hold is: `shop attributed to the payload == shop whose body/HMAC combination was actually produced by Shopify`. Because the header carrying the shop identity is excluded from the signed bytes, that equality is not enforced by this gem — the HMAC only proves "some webhook body signed with this app's global secret," not "this body was sent for this particular shop."

### Impact Explanation
A user who controls one shop that has this app installed can capture a legitimate webhook delivery for their own shop (valid body + valid HMAC, since the secret is shared across all installs of the app) and replay it to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to a victim shop's domain. `Registry.process` will accept the HMAC as valid (it only checks the body) and pass `shop: <victim-domain>` to the app's `WebhookHandler#handle`, causing the host application to process attacker-controlled data as if it originated from the victim tenant. Depending on what the handler does with `data.shop` (e.g., looking up the victim's session/access token and performing actions, or writing attacker data into the victim's tenant-scoped storage), this results in cross-tenant data corruption/action — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate to high for any multi-tenant public app built on this gem: an attacker only needs their own working installation (any developer/merchant can install a public app) to obtain a validly-HMAC'd webhook body, then simply resend it with a forged shop header — no access to the app's secret or another tenant's credentials is required.

### Recommendation
Bind the shop identity into the signed material, or otherwise verify it out-of-band: either (a) include the `shop-domain` header value in the bytes covered by `to_signable_string` before computing/verifying the HMAC, or (b) require the caller/host app to cross-check `request.shop` against a shop it already has an active session for, and document that `request.shop` from webhook headers must not be trusted as tenant-authenticated on its own. At minimum, the library should not silently offer `request.shop` as if it were verified when only the body is HMAC-protected.

### Proof of Concept
1. App installs on `attacker.myshopify.com`; Shopify sends a webhook with body `B` and header `x-shopify-shop-domain: attacker.myshopify.com`, HMAC `H = HMAC(api_secret_key, B)`.
2. Attacker captures `(B, H)` from their own webhook delivery.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and HMAC header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` using the shared `api_secret_key`. [5](#0-4) 
5. `handler.handle` receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body `B`, which the host app will treat as authentic data for `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
