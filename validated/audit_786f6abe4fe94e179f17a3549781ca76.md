## Title
Webhook shop-domain spoofing due to HMAC covering only the raw body, not the identifying headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while `topic`, `shop`, `api_version`, and `webhook_id` are all taken from unauthenticated HTTP headers that are never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` validates only that the HMAC matches, then passes the header-derived `shop` value straight to the application's webhook handler as an authoritative tenant identifier. Any party who can obtain one validly-signed webhook for their *own* shop (trivial — install/create a dev/test shop and trigger an event) can replay that exact signed body to the app's webhook endpoint while swapping the `shopify-shop-domain` (and `webhook-id`/`topic`) headers, since those are not covered by the signature. The receiving app will process the payload as if it originated from the victim shop.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `topic`, `shop`, `api_version`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`HmacValidator.validate` only proves that `verifiable_query.to_signable_string` (the raw body) was produced with the app's secret — it says nothing about the headers: [4](#0-3) 

`Registry.process` validates the HMAC and then forwards the header-derived `shop` (and `topic`/`webhook_id`) as trusted tenant/routing identity to the app-supplied handler, with no additional check that `shop` corresponds to the body that was actually signed: [5](#0-4) 

This is structurally identical to the reported bug class: a field that is *acted on* (`shop`, used as the tenant-identity boundary for webhook processing) is not covered by the integrity check (`hmac`, which only binds `raw_body`). Because Shopify's HMAC secret (`api_secret_key`/`client_secret`) is shared across all shops that install a given app, a signature valid for shop A's webhook body is equally "valid" when replayed with shop B's identifying headers attached to the same body — the gem provides no mechanism to detect this, and documents `request.shop` as if it were an authenticated value.

### Impact Explanation
An attacker who installs the target app on their own (attacker-controlled) shop — which requires no credentials belonging to the victim, no `api_secret_key`, and no privileged account — can trigger any webhook topic on their own shop to obtain a validly-HMAC-signed body. They can then replay that request to the app's webhook endpoint with the `shopify-shop-domain` header changed to the victim's shop domain. Because `Registry.process` treats `request.shop` as the authenticated tenant identity and passes it into `WebhookMetadata` without any cross-check against the signed content, the app will process/act on data attributed to the victim shop. Depending on what the app does with webhook data (e.g., updating per-shop records, triggering shop-scoped side effects, cache invalidation, billing/inventory sync), this can lead to cross-tenant data corruption or spoofed events for a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any Shopify Partner/developer can create a free development store and install any public or custom app on it, then trigger events (e.g., `app/uninstalled`, `orders/create` with attacker-controlled content) to receive genuinely signed webhook bodies. Replaying the POST with a different `shopify-shop-domain` header requires no interception of TLS and no possession of the app's secret — only a basic HTTP client. This makes the attack straightforward for any unprivileged, self-registered user of the platform.

### Recommendation
Bind the tenant-identifying fields into the HMAC-verified content, or otherwise cryptographically/contextually verify that the `shop` (and `webhook_id`) header actually corresponds to the subscription/shop the app expects, e.g.:
- Cross-check `request.shop` against the shop associated with the stored `webhook_id`/subscription before dispatching to handlers, or
- Require the consuming application to verify shop ownership via a separately authenticated channel (e.g., look up the shop's own webhook secret/subscription registry) rather than trusting the header value.
- At minimum, update the library documentation to make explicit that `WebhookMetadata#shop` is *not* authenticated by the HMAC and must not be used as a sole tenant boundary without additional verification.

### Proof of Concept
1. As an unprivileged Partner, create a free development store `attacker-shop.myshopify.com` and install the target app.
2. Trigger a webhook event (e.g., update a product) so Shopify sends a POST to the app's webhook endpoint with headers:
   ```
   X-Shopify-Topic: products/update
   X-Shopify-Hmac-Sha256: <valid HMAC over raw body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: <id>
   ```
3. Capture the raw body and the `X-Shopify-Hmac-Sha256` value.
4. Re-send the identical raw body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds (it only checks the raw body), and `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, `topic`, and `webhook_id` taken from the attacker-controlled headers — as shown at [6](#0-5) .
