## Finding: Webhook shop/topic identity is not covered by the HMAC signature [1](#0-0) 

### Title
Webhook tenant identity (`shop-domain`, `topic`) is unauthenticated relative to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `hmac`, `shop`, `topic`, `webhook_id`, and `api_version` are all read from separate, unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only, then trusts `request.shop` and `request.topic` — taken straight from headers that are not part of the signed material — to dispatch the payload to the host application's handler as the tenant identifier.

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`. [2](#0-1) 

For webhook requests, `to_signable_string` returns `@raw_body` only: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled from separate headers that are never mixed into the signed string: [4](#0-3) 

`Registry.process` validates only the HMAC over the body, then hands `request.shop` (and `request.topic`) directly to the application's handler as the trusted tenant identity for that payload: [5](#0-4) 

This is exactly the pattern called out in the report's rules: "a field acted on but not covered by the HMAC." The equality that should hold is:

`shop authenticated (bytes covered by HMAC) == shop trusted by the handler (request.shop header)`

but the header is never part of the signed bytes, so this equality does not hold — the gem verifies "the body came from Shopify" but not "this body belongs to this shop/topic."

### Impact Explanation
An unprivileged user who operates their own store with the target app installed receives genuine, correctly-HMAC-signed webhook deliveries from Shopify for their own shop (e.g. `orders/create` with a body they can partly influence, such as by placing an order with a customer-controlled note/name field). They can capture that `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) rewritten to a victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the secret, and `Registry.process` will invoke the handler with `shop: <victim shop>` and the attacker-supplied body. Any host application that uses `shop` from `WebhookMetadata` to route data into per-tenant storage (the intended and documented use) will attribute attacker-controlled data to another tenant — a cross-tenant data-integrity/injection issue and, depending on the topic (e.g. `app/uninstalled`, `shop/redact`, GDPR topics, order/customer data topics), can trigger destructive or data-disclosure side effects against a shop the attacker does not control.

### Likelihood Explanation
The webhook HTTP endpoint is by design public (Shopify must be able to reach it from the internet), and any user can obtain their own genuinely-signed webhook by installing the app on a store they control or by placing an order in a store using the app. No access token, `client_secret`, or privileged access is required — only the ability to receive one legitimate webhook and replay it with modified headers, which is trivial for anyone with a shop or storefront account.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, and ideally `webhook_id`) in the signed material, or otherwise cryptographically bind them to the body before trusting them downstream. Since Shopify's actual HMAC only covers the body by protocol, the gem should treat `request.shop`/`request.topic` as unauthenticated inputs, and clearly document that host applications must independently verify the delivering shop is the one they expect (e.g., cross-checking against a known/installed shop list) rather than presenting `WebhookMetadata#shop` as an authenticated value.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or triggers any webhook topic there) and captures a legitimate delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` with the app's secret).
2. Attacker POSTs to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: <same or different topic>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body: `B`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `B` against `H`. [5](#0-4) 
4. The handler is invoked with `shop: "victim-shop.myshopify.com"` and the attacker's body `B`, even though `B` was never generated for that shop.

          received_signature = verifiable_query.hmac
