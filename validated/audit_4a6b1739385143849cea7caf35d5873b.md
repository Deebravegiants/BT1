### Title
Orb-side fraud/duplicate-signup checks are fully bypassable via app-controlled `user_centric_signup` flag combined with a stubbed-out local fraud detector, allowing unauthorized/duplicate signups - (File: `src/plans/mod.rs`)

### Summary
The reported Perennial bug allows an attacker to skip the value-limiting check that would normally bound their gain, because the protocol never validates that `intent.price` is reasonable relative to `lastVersion.price` before accepting the order. The `orb-core` analog is structurally the same "missing validation/limit" pattern applied to signup approval: the orb accepts a client-supplied boolean (`user_centric_signup`) that, when true, causes the orb to skip the only channel (`enroll_user` → backend `signup_post`/`signup_poll`) that performs backend-side duplicate/fraud checks, and instead locally decides "success" using `detect_fraud`, which in this build is a no-op stub that always returns `false`.

### Finding Description
In `MasterPlan::do_signup`, after biometric capture and pipeline processing, the orb calls `self.detect_fraud(...)` to compute `signup_reason`: [1](#0-0) 

This function is entirely stubbed out in this build ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS") and unconditionally returns `Ok(false)`, meaning `fraud_detected` is always `false` and `signup_reason` is always `SignupReason::Normal` (unless the pipeline itself failed).

Separately, `do_signup` branches on `user_centric_signup`, a value taken from `qr_codes.user_data.user_centric_signup`: [2](#0-1) 

When `user_centric_signup` is `true` and `ignore_user_centric_signups` is not set, the orb **never calls `enroll_user`** — the code path that performs `signup_post::request` and polls `signup_poll::request`, which is the only place the backend's own duplicate-detection / fraud logic (explicitly documented in `enroll_user.rs` comments: "Backend duplicates", "Backend inflight matches", "Backend detected fraud") is invoked: [3](#0-2) 

Instead, `success` is derived purely from the locally computed (and permanently `Normal`) `signup_reason`. The `user_centric_signup` flag itself originates from `orb_qr_link::UserData`, obtained by querying the backend status endpoint using the QR code the *user's own app* generated, and is only checked against a hash (`user_data.verify(user_data_hash)`) that is likewise derived from data the same app produced: [4](#0-3) 

Because the app-supplied flag is not independently authenticated against an orb-independent trust anchor beyond a self-consistent hash check, and because it is capable of steering the orb away from the *only* remaining anti-fraud/anti-duplicate check (the backend `signup_post`/`signup_poll` roundtrip), there is no reachable check left in the local build that can reject a duplicate/fraudulent signup: `detect_fraud` is a stub returning `false`, and the backend call path is skipped entirely.

### Impact Explanation
This mirrors the root cause of the reported bug: a client-controlled value (`intent.price` / here, `user_centric_signup`) that is not bounded or independently verified feeds directly into a security-critical decision (settlement value / here, signup success determination), bypassing the mechanism (collateral checks / here, backend duplicate-fraud detection) that should have limited the outcome. The result is that a person can obtain a "successful" signup outcome on the orb with no fraud or duplicate-enrollment check ever executed by either the orb (`detect_fraud` stub) or the backend (`enroll_user` skipped), enabling unauthorized/duplicate/misattributed signups — a direct identity-integrity compromise analogous to "stealing" an unauthorized successful outcome.

### Likelihood Explanation
The `user_centric_signup` value is populated end-to-end from data that the user's own companion app supplies via a QR code it itself generates and a status hash it itself can compute; it requires no special privilege, hardware access, or operator collusion — an ordinary orb "user" running a modified/malicious version of the app can request `user_centric_signup = true` for their session. Given `detect_fraud` unconditionally returns `false` in this build, the combined condition is deterministically reachable on every signup where the flag is set.

### Recommendation
- Do not allow a client/app-controlled flag to fully bypass the backend duplicate/fraud-check call path (`enroll_user`); at minimum, always perform the backend `signup_post`/`signup_poll` round trip for iris-code duplicate detection regardless of `user_centric_signup`.
- Restore or reinstate real local fraud detection in `detect_fraud` rather than an unconditional `Ok(false)` stub, or explicitly gate any user-centric fast-path behind independent, orb-verifiable authentication of `user_centric_signup`.
- Treat `ignore_user_centric_signups` as the safe default (force backend enrollment) rather than an opt-in override.

### Proof of Concept
1. A user runs a modified/companion app that requests a QR-code session for which the backend's `authenticated_app_data.user_centric_signup` resolves to `true` (this flag is only checked for internal hash-consistency, not for independent backend-side identity binding at the orb level — see `src/backend/user_status.rs:163-179`).
2. The user completes biometric capture normally; `detect_fraud` in `src/plans/mod.rs:1390-1406` always returns `false` regardless of any fraud signal, so `signup_reason == SignupReason::Normal`.
3. In `do_signup` (`src/plans/mod.rs:639-656`), because `user_centric_signup` is `true`, the orb sets `success = (signup_reason == SignupReason::Normal) = true` without ever invoking `enroll_user`/`signup_post`/`signup_poll`.
4. The signup is marked successful on the orb (`debug_report.signup_successful()`), and no backend-side duplicate/fraud check (documented in `src/plans/enroll_user.rs:157-176`) is ever performed for this signup.
