### Title
Webhook `shop` (and `topic`/`webhook-id`) header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from HTTP headers, none of which are included in the signed content. Because the same `api_secret_key` is used for HMAC verification across every shop that has installed the app, a request whose body was legitimately signed for one shop can be replayed with a different `shopify-shop-domain` header value and will still pass validation, letting an attacker choose which shop the payload is attributed to.

`ShopifyAPI::Webhooks::Registry.process` accepts a `Request` object and validates it purely via HMAC: [1](#0-0) 

The HMAC check is: [2](#0-1) 

`Request#to_signable_string`, which is the only thing the HMAC actually signs, returns just the raw body — none of the identifying headers: [3](#0-2) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers: [4](#0-3) 

`Registry.process` uses these unauthenticated header values to build the tenant-identifying `WebhookMetadata` passed to the app's handler: [1](#0-0) 

The equality the gem should be enforcing but doesn't is:
`shop_bound_by_HMAC(body) == shop_used_for_tenant_dispatch(header)`

Instead the gem only enforces `HMAC(body, api_secret_key) == received_hmac`, and separately trusts `shop_header` for tenant dispatch — these are two independent, unlinked values. Since the `api_secret_key` is a single value shared by the app across *all* of its installed shops (it is not per-shop), any user who has legitimately installed the app on their own shop can capture a validly-signed webhook body/HMAC pair addressed to themselves, then replay that exact body (with the same valid HMAC) to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (and/or `shopify-webhook-id`/`shopify-topic`). `Utils::HmacValidator.validate` will report success because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on to know “which merchant does this webhook data belong to.” Depending on how the host app's webhook handler uses `shop`, this enables cross-tenant data confusion/tampering — e.g. spoofing `app/uninstalled` to deprovision a victim shop’s app data, or spoofing `customers/redact`/`shop/redact` GDPR webhooks to trigger deletion of a victim shop's data, or injecting attacker-controlled body content (their own store's data) attributed to a victim shop. This matches the Critical “cross-tenant access” impact category, since the attacker (an ordinary unprivileged app installer, no special access token or secret needed) can make the library assert an incorrect shop identity for a validly-HMAC'd payload.

### Likelihood Explanation
Any user can become "attacker" simply by installing the target app on their own store (public apps allow free/dev store installs), capturing a real webhook delivery (body + `X-Shopify-Hmac-Sha256`), and POSTing it to the app’s known public webhook endpoint with a modified `shopify-shop-domain` header (endpoint paths/URLs are typically discoverable/standard, e.g. `/webhooks`). No credentials, access tokens, or knowledge of `api_secret_key` are required — only the ability to receive one legitimate webhook for their own shop. This is a low-effort, no-privilege attack path fully reachable through this gem's public webhook-processing API (`ShopifyAPI::Webhooks::Registry.process`).

### Recommendation
Do not treat `shop` (and ideally `topic`/`webhook_id`) as trusted metadata derived purely from headers when the HMAC only signs the body. Options:
- Include the `shopify-shop-domain` (and topic) header values in the signed content that `to_signable_string` returns, or otherwise cryptographically bind them to the signature validated by `HmacValidator`.
- Require host applications to cross-check `request.shop` against the shop associated with the currently active/expected session or a shop registry known to have this webhook subscription, rather than trusting the header value implicitly, and document this requirement clearly.
- At minimum, surface a prominent warning in `docs/usage/webhooks.md` and in `Webhooks::Request`/`Registry` documentation that `shop` is not authenticated by the HMAC and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target public app on shop `attacker-shop.myshopify.com` and receives a real webhook, e.g. `app/uninstalled`, with body `{}` and header `X-Shopify-Hmac-Sha256: <valid HMAC of "{}" with the app's shared api_secret_key>`.
2. Attacker sends a forged HTTP POST to the app's public webhook endpoint with:
   - Body: the exact same `{}` (or any other captured, validly-signed body)
   - Headers: `x-shopify-hmac-sha256: <the same valid HMAC>`, `x-shopify-topic: app/uninstalled`, `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body against the secret key.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the host app's handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {}, ...)` — attributing the (spoofable) event to a shop the attacker does not control. [1](#0-0) [5](#0-4)

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
