Confirmed. The vulnerability is that `ShopifyAPI::Webhooks::Request` HMAC verification signs only the raw body, while the `shop` (and `topic`/`webhook_id`/`api_version`) header values are read unauthenticated and passed straight to the app's webhook handler as the tenant identifier.This confirms the root cause: `Registry.process` trusts `request.shop`/`request.topic`/`request.webhook_id` unconditionally after only validating the HMAC over `raw_body`, and hands them to the app handler as `WebhookMetadata.shop` (the tenant identity signal downstream apps rely on for multi-tenant lookups).

### Title
Webhook `shop` (and `topic`/`webhook-id`) header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` authenticates the body bytes only. The `X-Shopify-Shop-Domain` header (exposed as `request.shop`) is never included in the signed material, yet `Registry.process` passes it straight through into `WebhookMetadata.shop`, which is the field host applications use to identify which tenant/shop a webhook belongs to.

### Finding Description
`Registry.process` performs a single check, `Utils::HmacValidator.validate(request)` at [1](#0-0) , before dispatching to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` at [2](#0-1) .

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [3](#0-2) , and for `Webhooks::Request` that method returns only the raw JSON body: [4](#0-3) .

Meanwhile `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` are all read directly from unauthenticated HTTP headers with no cross-check against the signed body: [5](#0-4) .

The equality being broken: **shop bound in the HMAC-signed payload == shop delivered to the application as the tenant identifier**. These are never the same field. The gem authenticates "this body's bytes were produced with the app's `client_secret`" but reports "this event belongs to shop X" using a completely different, unsigned header.

### Impact Explanation
Any actor who can obtain one legitimately-signed `(raw_body, hmac)` pair for a topic the app has a handler for (e.g., by installing the app themselves on their own shop/dev store and capturing one real Shopify-delivered webhook, or by using any topic where the body content is not tenant-specific/sensitive) can resend that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `for shop: <attacker-chosen-value>`. If the host application uses `data.shop` to select which tenant's database row/session/access token to update (the typical, documented pattern, e.g. `shop_session = ...` keyed by `data.shop`), this enables cross-tenant data confusion/injection — writing or triggering victim-shop-scoped side effects (order-processing logic, GDPR redaction handlers like `customers/redact`, `shop/redact`, inventory updates, etc.) using attacker-controlled shop attribution. This satisfies the "cross-tenant access" Critical-impact category since the trust boundary between shops is defined entirely by this unauthenticated header.

### Likelihood Explanation
Moderate-to-high: an attacker needs only one valid signed webhook body for any registered topic (trivially obtained by installing the app on their own store, which any unprivileged merchant can do) and the ability to POST to the app's public webhook endpoint with custom headers — both are within reach of an unprivileged internet actor with no special credentials, TLS interception, or leaked secrets required.

### Recommendation
Do not treat `request.shop`, `request.topic`, or `request.webhook_id` as authenticated data derived purely from HMAC-body validation. Either:
1. Include the shop domain (and ideally topic/webhook id) in the signable string used for HMAC verification, matching what Shopify actually signs if it does so, or
2. Require the host application to independently verify that `request.shop` corresponds to a shop with an active install/session before trusting `WebhookMetadata.shop`, and document this prominently since the gem currently implies the header is trustworthy once `Registry.process` succeeds.
3. At minimum, add explicit documentation/warnings in `Registry.process`/`WebhookMetadata` that `shop` is unauthenticated and must not be used as the sole tenant-selection key without additional verification (e.g., cross-referencing against a known-installed shop list).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and lets it deliver one real webhook, e.g. `orders/create` with body `{"id":1}`, capturing the genuine `X-Shopify-Hmac-Sha256` value Shopify computed over that exact body.
2. Attacker replays the request to the app's public webhook endpoint, keeping `raw_body` and the HMAC header identical, but sets:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <captured-valid-hmac>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches — validation passes at [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` at [2](#0-1) , so any app logic keyed off `data.shop` operates against the victim shop's tenant context using attacker-supplied body content, despite the request never having been signed for that shop.
