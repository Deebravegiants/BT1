### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs `@raw_body`, while `shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) is not part of the signed content. `Registry.process` validates only the HMAC over the body and then hands `request.shop` straight to the app's handler as the tenant identifier, so an attacker who controls the header can decouple "the shop whose secret validated this payload" from "the shop the app believes sent it."

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from an HTTP header that is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (body only) and compares it against `verifiable_query.hmac`: [3](#0-2) 

After validation succeeds, `request.shop` (attacker-controlled header, unauthenticated) is passed directly to the registered handler as the tenant identity, with no cross-check against the body or any other authenticated value: [4](#0-3) 

The identity binding that is broken: `shop asserted to handler == shop that produced the signed bytes`. Because the HMAC is computed by Shopify using the app's shared `client_secret` (the same secret for every shop that has the app installed) over the body only, any entity that legitimately receives a real webhook for a shop it controls (e.g., an attacker who installs the target app on their own store) possesses a validly-signed `(body, hmac)` pair. Since `shop-domain` is outside the signed bytes, that same `(body, hmac)` pair remains valid if replayed with the `shop-domain` header rewritten to name a different, victim shop. `Registry.process` will accept the HMAC (it never inspected the shop header) and forward `shop: <victim-shop>` to the app's handler.

### Impact Explanation
Apps commonly key persisted business data, authorization decisions, or cross-referenced session lookups by the `shop` value returned from `WebhookMetadata` (built directly from `request.shop`). An attacker owning any one shop where the target app is installed can forge webhook deliveries that assert an arbitrary victim shop domain while carrying attacker-chosen body content signed under their own legitimately-issued webhook. This is a cross-tenant authentication/identity confusion: the app's webhook processing pipeline in this gem provides no means to verify that the header-derived `shop` actually matches the tenant whose secret produced the signature, because the header is outside the HMAC's protected scope entirely. This can lead to cross-tenant data corruption/injection in any host application that trusts `shop` from `WebhookMetadata` for tenant-scoped writes.

### Likelihood Explanation
Requires the attacker to be an unprivileged internet user who can install the target Shopify app on a store they control (a normal, unprivileged self-service action) to obtain one legitimately-signed webhook payload/HMAC pair, and to be able to send arbitrary HTTP requests to the app's public webhook endpoint with a modified `shop-domain` header — no access token, `api_secret_key`, or privileged account is needed. The vulnerability is purely a gap in what this gem signs/verifies (`lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`), not a host-application misuse.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the HMAC-protected signable content, or otherwise cryptographically bind the header-derived `shop` to the signed body before exposing it via `WebhookMetadata`, so that `Utils::HmacValidator.validate` fails if the `shop-domain` header is altered relative to what was actually signed.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery: `POST /webhooks` with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)` and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, HMAC(secret,B))`.
3. Attacker replays the exact same request to the app's webhook endpoint but rewrites the header to `shopify-shop-domain: victim-shop.myshopify.com`, keeping `B` and the HMAC unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`B` only) — validation succeeds because the header was never part of what is signed (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: attacker-controlled parsed body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled data under the victim tenant's identity.
