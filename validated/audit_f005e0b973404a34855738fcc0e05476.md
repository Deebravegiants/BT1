### Title
Webhook `shop`/`topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from HTTP headers. Those header values are never included in the signed bytes, so the "shop" identity that is cryptographically authenticated is not the same "shop" identity that the handler acts on.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` method returns only the raw HTTP body: [1](#0-0) 

`Utils::HmacValidator.validate` recomputes the HMAC exclusively over that signable string (the body) using `Context.api_secret_key`: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read directly from request headers and are never part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC (i.e., that the body bytes were produced with the app's secret) and then immediately trusts the header-derived `topic`/`shop`/`webhook_id` to select the handler and build `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is:
```
shop authenticated by HMAC == shop acted upon by the handler
```
Because only the body is signed, this equality is never enforced — `shop` (and `topic`/`webhook_id`) can be swapped for any value while the HMAC still validates, as long as the body bytes are unchanged.

### Impact Explanation
An attacker who can obtain any single legitimate `(raw_body, hmac)` pair — trivially achievable by installing the app on a shop they control themselves (a free Shopify development/trial store) and capturing the webhook Shopify sends them — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with an arbitrary victim shop or topic. `Registry.process` will pass HMAC validation and invoke the registered handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop and the attacker's own body content: [5](#0-4) 

Any host application that uses `WebhookMetadata.shop` to key writes into per-merchant data (order processing, subscription state, GDPR/uninstall handling, entitlement flags, etc.) can be tricked into attributing attacker-controlled data to another tenant — a cross-tenant integrity violation, matching the Critical "cross-tenant access" impact category, and it requires no `api_secret_key`, access token, or TLS interception.

### Likelihood Explanation
Exploitability requires only the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint plus possession of one valid `(body, hmac)` sample, which any unprivileged actor can generate for themselves by installing the target app on a store they control. No secrets need to be extracted or guessed since the header fields simply aren't checked at all. This is a low-effort, repeatable attack path.

### Recommendation
Bind the shop/topic/webhook identifiers into the signed material, or otherwise cross-validate them:
- Prefer verifying webhook authenticity the way Shopify's official model intends — but additionally assert that the `shop` header matches an actively-installed/expected shop for this app (e.g., look up a stored offline session for that shop) before trusting it, rather than accepting any header value once the body HMAC passes.
- Reject/log webhooks where the `shop` header does not correspond to a shop the app currently has installed, closing the gap between "HMAC-authenticated body" and "header-derived tenant identity" used by `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-owned development store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) and capture the raw request body `B` and its `shopify-hmac-sha256` header `H` sent to the app's webhook endpoint.
2. Replay the captured request to the same endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but set:
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: <same or different registered topic>`
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and succeeds (since `B`/`H` are unmodified and the secret matches), per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`.
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, per `lib/shopify_api/webhooks/registry.rb#L188-199`, demonstrating that the shop identity accepted by the handler was never authenticated by the HMAC.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
