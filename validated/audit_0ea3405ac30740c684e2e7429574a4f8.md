### Title
Unrestricted `CallDispatcher.dispatch()` allows any unprivileged caller to execute arbitrary calls from the dispatcher's context, draining any assets it holds - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes)` is a fully public, unauthenticated function that decodes attacker-supplied `Call[]` and executes each one (`to.call{value}(data)`) in the dispatcher's own msg.sender context [1](#0-0) . There is no caller restriction (`onlyHost`, `onlyGateway`, or similar) - `dispatch` can be invoked directly by anyone, not just by the intended integrating app contracts (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, `HyperbridgeLzEndpoint`) that are supposed to be its only legitimate callers.

### Finding Description
`CallDispatcher` is a shared, singleton utility contract deployed once per chain and reused across multiple Hyperbridge apps for "composable" cross-chain calldata execution: `IntentGatewayV2`'s predispatch/postdispatch flows [2](#0-1) [3](#0-2) , and the `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` handlers [4](#0-3)  all forward externally-supplied bytes to `ICallDispatcher(dispatcher).dispatch(...)`.

The dispatcher accepts native ETH unconditionally via `receive()` [5](#0-4) , and legitimate flows deliberately leave it holding assets *temporarily* between the moment tokens/ETH are transferred in and the moment the app-controlled sweep runs (e.g. `IntentGatewayV2.placeOrder`'s predispatch step transfers assets to `dispatcher`, calls `dispatch(order.predispatch.call)`, then issues a second `dispatch()` call to sweep balances back [6](#0-5) ; `IntentsBase._execute` does the same for postdispatch calldata [7](#0-6) ).

Because `dispatch()` has no access control, **any address that observes the dispatcher holding a non-zero balance can call `dispatch()` directly** with a `Call[]` such as `{to: token, data: transfer(attacker, balance)}` or `{to: attacker, value: balance}`, and the call executes with `msg.sender == dispatcher` inside the target - identical privilege to a call issued by the legitimate app. This is structurally the same bug class as the reported `larvitbase-www` "Unintended Require": an unauthenticated endpoint takes an attacker-controlled parameter (here, the `Call[]` array — analogous to the unsanitized file path) and feeds it directly into a powerful, unrestricted execution primitive (`to.call()` — analogous to `require()`), letting the caller reach code/state the endpoint was never meant to expose to them.

Residual balances are not merely theoretical: fee-on-transfer/rebasing tokens, a swap that returns more/less than expected, ETH force-sent via `selfdestruct`/miner payment, or any sweep step that reverts or under-collects, all leave the dispatcher holding value across the boundary between the asset-in step and the sweep-out step within the same or a subsequent block, during which the balance is fully exposed to any external actor able to front-run or simply call `dispatch()` in a following block/transaction.

### Impact Explanation
Any assets sitting in the shared `CallDispatcher` - whether protocol dust, residual escrow tokens/native ETH from an in-flight `placeOrder`/`fillOrder`/`onAccept` execution, or mis-sent funds - can be stolen outright by an unprivileged caller who simply calls `dispatch()` with a call that transfers the balance to themselves. Since the dispatcher is shared across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` on a given chain, this is a direct concrete-theft vector against user/protocol funds reachable from an ordinary, unprivileged transaction (no governance, relayer, or consensus-proof requirement).

### Likelihood Explanation
Exploitability requires only that the dispatcher hold a non-zero balance at a moment an attacker can observe and act on (e.g. between blocks, or via any sweep under-collection due to fee-on-transfer tokens or partial-fill/slippage rounding). Given `dispatch()` has literally zero access control, exploitation is a single unauthenticated call — the barrier is purely opportunistic timing, not technical difficulty, which is a materially lower bar than most theft primitives in this codebase.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a fixed set of trusted, whitelisted caller contracts (e.g. an `onlyAuthorizedApp` modifier checked against a registry set at deployment/governance), or make `CallDispatcher` non-shared/ephemeral per invocation (e.g. deploy a fresh minimal-proxy instance per call, or add per-call access tokens), so no third party can independently trigger arbitrary execution in its context.

### Proof of Concept
1. Observe (via mempool or a prior block) that `CallDispatcher` at address `D` holds a non-zero ERC20/ETH balance — e.g. after a `placeOrder` predispatch swap under-collects due to token fee-on-transfer, or after native ETH is force-sent to `D`.
2. Call `D.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, D.balanceOf(token))})]))` directly, with no relationship to any app contract.
3. `dispatch()` executes the transfer with `msg.sender == D` inside the token contract, succeeding because `D` is a legitimate token holder — the attacker receives the tokens, with no check that the caller of `dispatch()` was `IntentGatewayV2`, `HyperFungibleToken`, or any other authorized app [1](#0-0) .

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
