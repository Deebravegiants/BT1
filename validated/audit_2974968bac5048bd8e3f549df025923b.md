### Title
Webhook shop-domain and topic headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate an incoming webhook solely by validating the raw HTTP body against the `X-Shopify-Hmac-Sha256` header. The `shop` (tenant identity) and `topic` (routing) values are read from separate, unsigned headers and passed straight through to the app's handler once the body-only HMAC check succeeds. Any unprivileged internet user who can obtain one valid `(raw_body, hmac)` pair — trivially available to anyone who has a store on which the app is installed, since Shopify sends real webhooks to that store — can replay that exact body+HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` and/or `topic` header. `HmacValidator.validate` will report success because it only ever inspects `@raw_body`, never the headers.

**Broken identity binding (as an equality):**
`request.shop` (used by the app to select the tenant/session to act on) is expected to equal "the shop that produced this HMAC-authenticated payload," but the gem only proves `hmac == HMAC(api_secret_key, raw_body)`. It never proves `hmac` was computed *for* `request.shop` or `request.topic`. Because a single app-wide `api_secret_key` is used to validate webhooks for *every* merchant, and many legitimate webhook bodies are constant or attacker-fully-controlled regardless of shop (e.g. `app/uninstalled` ships an empty body `{}`, confirmed by the test fixtures using `"{}"` as body for arbitrary topics: [6](#0-5) ), an attacker who installs the app on their own store obtains a `(body="{}", hmac=<valid>)` pair that is valid *for any topic/shop* the gem will accept, since neither is part of the signed content.

### Impact Explanation
This breaks the cross-tenant isolation the HMAC is meant to provide: an unprivileged internet user with no more than "install app on my own shop" access can forge webhook deliveries claiming to originate from a **victim** shop (`x-shopify-shop-domain: victim.myshopify.com`) and for a topic of the attacker's choosing (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`), while passing `HmacValidator.validate` successfully. Any app handler that trusts `WebhookMetadata#shop`/`#topic` to identify which tenant record to update, deauthorize, purge, or reprocess — which is exactly the contract the gem hands to `WebhookHandler#handle` — can be made to act on a shop the attacker does not control. This is a cross-tenant access primitive rooted entirely in this gem's own webhook verification code, not a misuse of a documented API.

### Likelihood Explanation
High for any app that: (1) is installable by the public (standard for Shopify apps), and (2) has at least one webhook topic whose body content is constant, predictable, or attacker-influenced (uninstall/redaction topics, or any topic whose JSON body the attacker can reconstruct exactly, since JSON key order and whitespace must match byte-for-byte for the HMAC to match on replay of a *different* topic/shop). The attacker needs zero privileged credentials — only the ability to install the app on a shop they control and to send a raw HTTP POST to the app's public webhook URL.

### Recommendation
Include the tenant/routing identity in the material that is HMAC-verified, or otherwise cryptographically bind `shop-domain` and `topic` to the signed body before trusting them:
- Have `Request#to_signable_string` incorporate the `shop-domain` and `topic` headers (or their canonical values) alongside the raw body, matching what was actually signed by Shopify's outbound webhook delivery, or
- After HMAC validation, additionally require the caller to supply/compare the expected shop out-of-band (e.g. from the app's own session store keyed by a value that *is* covered by the signature) rather than trusting the header directly, or
- Document loudly (and ideally enforce in `Registry.process`) that `request.shop`/`request.topic` must never be used as the sole tenant selector without corroborating it against Shopify's known registered webhook delivery for that topic.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers a webhook with a body that is constant/predictable, e.g. `app/uninstalled` (empty JSON body `"{}"`), and captures the legitimate `X-Shopify-Hmac-Sha256` header Shopify sent for that delivery, along with the raw body bytes.
3. Attacker POSTs directly to the app's public webhook endpoint with:
   - Body: the exact captured raw bytes (`"{}"`)
   - Header `X-Shopify-Hmac-Sha256`: the exact captured valid HMAC
   - Header `X-Shopify-Shop-Domain`: `victim.myshopify.com`
   - Header `X-Shopify-Topic`: `app/uninstalled` (or any other topic whose body the attacker can reproduce byte-for-byte)
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over the raw body, per [1](#0-0)  and [7](#0-6) .
5. `Registry.process` dispatches to the registered `app/uninstalled` handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to treat the event as pertaining to the victim's tenant, per [4](#0-3) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
