## Finding

### Title
No slippage protection (`amount_out_min`) in `liquidity_pairs::swap_fa_to_apt` / `swap_apt_to_fa` enables guaranteed value extraction from swappers - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move`)

### Summary
The bonding-curve launchpad's AMM swap entry points compute output amounts purely from on-chain reserves at execution time and transfer funds without any caller-supplied minimum-output guard, unlike the sibling `swap` module's router, which correctly enforces `amount_out_min`.

### Finding Description
`swap_fa_to_apt` and `swap_apt_to_fa` in `liquidity_pairs.move` take `amount_in` but no `amount_out_min`/slippage parameter: [1](#0-0) [2](#0-1) 

The output amount is computed from `get_amount_out`, which reads live pool reserves (`fa_reserves`, `apt_reserves`) at the moment of execution: [3](#0-2) 

Once computed, funds are moved unconditionally via `fungible_asset::transfer_with_ref` / `aptos_account::transfer` — there is no assertion comparing the computed `fa_gained`/`apt_gained` against any caller-specified floor: [4](#0-3) [5](#0-4) 

By contrast, this same repository's own `swap` module router demonstrates the intended pattern (accepting and enforcing `amount_out_min`): [6](#0-5) 

This is the exact custody invariant the external `AgentToken::_swapTax` report identifies — a swap that commits to sending funds at a price fixed by the caller's own quote step, with no on-chain enforcement of a minimum acceptable output — reduced to the on-chain AMM analog: **the swapper's expected value at execution is not enforced against manipulated/derived pool state.** Any actor able to influence transaction ordering (e.g., a searcher submitting adjacent transactions in the same block that trade against the same `LiquidityPair` object before the victim's swap executes) can shift `fa_reserves`/`apt_reserves` to their advantage and then reverse the trade afterward, extracting the difference from the victim's `amount_in` with no on-chain check to prevent it.

### Impact Explanation
Every call to `swap_fa_to_apt`/`swap_apt_to_fa` unconditionally transfers the swapper's FA or APT into the `LiquidityPair`'s custody and pays out whatever `get_amount_out` computes at that instant, with no floor. A sandwiching attacker can manipulate `fa_reserves`/`apt_reserves` immediately before the victim's transaction and restore them immediately after, capturing the value gap. Since `apt_reserves`/`fa_reserves` are the *only* custody-accounting fields backing the `fa_store` (an object-held `FungibleStore`), this directly corrupts the value distribution between the pool's rightful holders and the attacker — funds are diverted from the swapper to the attacker without any recovery path.

### Likelihood Explanation
High. Any user calling the bonding-curve swap entry points is exposed on every trade; no privileged access or special conditions are required, only visibility into pending transactions/mempool ordering (or same-block multi-transaction construction, which validators/attackers can control). The lack of a min-out parameter means there is no way for a caller to even opt into protection.

### Recommendation
Add `amount_out_min` (or equivalent slippage-bound) parameters to `swap_fa_to_apt` and `swap_apt_to_fa`, threaded through from the public entry points in `bonding_curve_launchpad.move`, and assert the computed `apt_gained`/`fa_gained` against that minimum before transferring funds — mirroring the pattern already used in `swap::router::swap` (`assert!(fungible_asset::amount(&out) >= amount_out_min, ...)`).

### Proof of Concept
1. Attacker observes a pending `swap_apt_to_fa` transaction (or constructs a same-block sequence) for victim swapping `amount_in` APT.
2. Attacker front-runs with their own `swap_apt_to_fa`/`swap_fa_to_apt` call that shifts `apt_reserves`/`fa_reserves` unfavorably for the victim (increasing effective price).
3. Victim's transaction executes against the now-worse reserves via `get_amount_out`, receiving materially less FA/APT than expected, with no `amount_out_min` check to abort the trade.
4. Attacker back-runs, reversing their initial trade and capturing the extracted value, funded directly by the victim's `amount_in`.

Note: I could not fully verify whether `bonding_curve_launchpad.move`'s public entry wrappers expose any additional protection parameters not visible in `liquidity_pairs.move` alone, since I was unable to read the full contents of `bonding_curve_launchpad.move` before the tool budget ended — a Devin session with full file access should confirm this before treating the finding as final.

    public fun get_amount_out(
        fa_reserves: u128,
        apt_reserves: u128,
        swap_to_apt: bool,
        amount_in: u64
    ): (u64, u64, u128, u128) {
        if (swap_to_apt) {
            let divisor = fa_reserves + (amount_in as u128);
            let apt_gained = (math128::mul_div(apt_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves + (amount_in as u128);
            let apt_updated_reserves = apt_reserves - (apt_gained as u128);
            assert!(apt_gained > 0, ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT);
            (amount_in, apt_gained, fa_updated_reserves, apt_updated_reserves)
        } else {
            let divisor = apt_reserves + (amount_in as u128);
            let fa_gained = (math128::mul_div(fa_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves - (fa_gained as u128);
            let apt_updated_reserves = apt_reserves + (amount_in as u128);
            assert!(fa_gained > 0, ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT);
            (fa_gained, amount_in, fa_updated_reserves, apt_updated_reserves)
        }
    }

    /// Swap an amount of fungible assets for another fungible asset. User can specifies the minimum amount they
    /// expect to receive. If the actual amount received is less than the minimum amount, the transaction will fail.
    public entry fun swap_entry(
        user: &signer,
        amount_in: u64,
        amount_out_min: u64,
        from_token: Object<Metadata>,
        to_token: Object<Metadata>,
        is_stable: bool,
        recipient: address,
    ) {
        let in = primary_fungible_store::withdraw(user, from_token, amount_in);
        let out = swap(in, amount_out_min, to_token, is_stable);
        primary_fungible_store::deposit(recipient, out);
    }

    /// Similar to swap_entry but returns the fungible asset received for composability with other modules.
    public fun swap(
        in: FungibleAsset,
        amount_out_min: u64,
        to_token: Object<Metadata>,
        is_stable: bool,
    ): FungibleAsset {
        let from_token = fungible_asset::asset_metadata(&in);
        let pool = liquidity_pool::liquidity_pool(from_token, to_token, is_stable);
        let out = liquidity_pool::swap(pool, in);
        assert!(fungible_asset::amount(&out) >= amount_out_min, EINSUFFICIENT_OUTPUT_AMOUNT);
        out
    }
