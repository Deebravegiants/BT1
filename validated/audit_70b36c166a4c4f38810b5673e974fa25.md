This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the HMAC-signed content [2](#0-1) . `Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)` and then dispatches to a handler using the unauthenticated `topic` and passes the unauthenticated `shop` value straight into `WebhookMetadata` [3](#0-2) .

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem verifies inbound Shopify webhooks by computing an HMAC over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are used as the tenant/identity binding for dispatching to handlers — are taken from HTTP headers that are excluded from the signed content, breaking the equality `shop verified by HMAC == shop acted upon by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is that `to_signable_string` represents the bytes the HMAC binds. For webhooks, `to_signable_string` is hard-coded to `@raw_body` [1](#0-0) . Meanwhile `shop`, `topic`, and `webhook_id` are pulled from `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers respectively [2](#0-1) , none of which are hashed into `to_signable_string`.

`Utils::HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the received `hmac` header [4](#0-3) . `Registry.process` trusts this check as sufficient proof of authenticity and then uses the unauthenticated `request.shop` and `request.topic` to select a handler and populate `WebhookMetadata` [3](#0-2) .

Because every webhook for a given app is signed with the same app-wide `Context.api_secret_key` regardless of which shop it originates from (the HMAC secret is not shop-specific), any unprivileged merchant who has installed the app receives real, validly-signed webhooks for their own shop. The `(raw_body, hmac)` pair captured from a legitimate webhook delivered to their own shop remains valid for *any* header set, since headers aren't part of the signed bytes. That merchant can replay the same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) with a different shop's identifier. `HmacValidator.validate` still returns `true` because it only checks the untouched body, and `Registry.process` will hand the forged `shop` value to the application's webhook handler as if Shopify had sent it for that other tenant.

### Impact Explanation
This breaks the identity binding "shop authenticated by HMAC" vs. "shop acted upon by the handler," letting a low-privilege actor (any merchant with the app installed) inject attacker-controlled webhook bodies tagged with an arbitrary victim shop domain/topic/webhook id into the host application's webhook processing pipeline — a cross-tenant data-integrity/confusion issue. Depending on how the host application's `WebhookHandler` implementations use `data.shop` (e.g., to look up/update per-merchant records), this can lead to cross-tenant data corruption or unauthorized actions attributed to a victim shop, which falls under the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is Medium-High for any app on this gem that has more than one shop installed (all real-world multi-tenant apps): the attacker only needs to be a normal merchant/user of the app (no special privilege, no token/secret theft) capable of capturing one legitimate webhook delivery to their own endpoint and replaying it with modified headers to the app's webhook endpoint.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed content that `to_signable_string` returns, or otherwise bind them cryptographically to the body before trusting them in `Registry.process`. At minimum, applications should be documented to never trust `WebhookMetadata#shop`/`#topic` unless they are independently corroborated (e.g., cross-checked against a known/registered shop for that specific body), and the gem should consider computing/verifying an HMAC that incorporates these header values directly.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate incoming webhook request, e.g.:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <valid-hmac-for-body>
   shopify-shop-domain: attacker.myshopify.com
   shopify-webhook-id: abc-123
   Body: {"id": 1, "note": "malicious payload"}
   ```
2. Attacker replays the identical body and `shopify-hmac-sha256` value to the same app endpoint, but changes the header:
   ```
   shopify-shop-domain: victim.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` and succeeds [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim.myshopify.com"` even though the body/signature only ever proved authenticity for the attacker's own shop [5](#0-4) .
