## Title
`remove_parachain` deletes the parachain whitelist entry but leaves a stale zero-length `ChallengePeriod` behind, letting a re-whitelisted (or ID-reused) parachain skip the fraud-detection delay - (File: modules/ismp/clients/parachain/client/src/lib.rs)

### Summary
`ismp_parachain::Pallet::add_parachain` whitelists a para ID and, in the same call, unconditionally sets its ISMP `ChallengePeriod` (in `pallet-ismp`'s `ChallengePeriod` storage, keyed by `StateMachineId{state_id, consensus_state_id}`) to `0`. [1](#0-0)  `remove_parachain` only clears `Parachains` and `SlotDurations`, but never clears the `ChallengePeriod` entry that `add_parachain` created. [2](#0-1)  This is the same class of bug as the referenced report: a removal path that flips the "allowed" flag but does not clean up the associated per-entity policy/config, allowing that stale policy to be reused once the entity becomes reachable again.

### Finding Description
When a parachain is added via `add_parachain`, the pallet calls `host.store_challenge_period(StateMachineId { state_id, consensus_state_id }, 0)`, meaning that once a parachain is whitelisted, `verify_delay_passed` treats its delay as instant (`delay_period.as_secs() == 0` short-circuits to `true`) for all state proofs — see `verify_delay_passed`/`validate_state_machine` in `modules/ismp/core/src/handlers.rs`. [3](#0-2) 

`remove_parachain` removes the para ID from `Parachains` (used to gate `state_machine()` lookups and to select which parachain headers get read in `verify_consensus`) and from `SlotDurations`, but it never calls anything to clear the corresponding `ChallengePeriod` entry:
```
pub fn remove_parachain(origin: OriginFor<T>, para_ids: Vec<u32>) -> DispatchResult {
    T::RootOrigin::ensure_origin(origin)?;
    for id in &para_ids {
        Parachains::<T>::remove(id);
        SlotDurations::<T>::remove(id);
    }
    ...
}
``` [2](#0-1) 

Because `ChallengePeriod` is keyed only by `StateMachineId { state_id, consensus_state_id }` and never touched by removal, root governance can:
1. `add_parachain` a para ID (challenge period silently set to 0).
2. `remove_parachain` it (whitelist entry gone, but `ChallengePeriod` for that `StateMachineId` remains `0` in storage).
3. Later `add_parachain` the same ID again (or the para ID is reassigned to a different parachain/team, which is common on Polkadot as para IDs are recycled after lease/slot expiry) — the pallet does not re-set the challenge period on re-add in any way that clears prior state, and since `store_challenge_period` in the ISMP host is an insert (idempotent overwrite to the same value of `0` anyway), the net effect is the same zero-second challenge period applies again immediately, with no protective window during which fishermen can veto a bad state commitment for that parachain.

### Impact Explanation
The challenge period is Hyperbridge's core optimistic-bridging safety mechanism: it exists specifically to give fishermen a window to veto fraudulent state commitments before requests/responses proven against those heights can be processed (see `docs/content/protocol/ismp/consensus.mdx`). [4](#0-3)  A parachain state machine that is added, removed, and re-added (or whose numeric para ID is reused for a different chain/team after the original registration lapses) inherits a stale `ChallengePeriod = 0`, permanently bypassing the veto window for all future state proofs from that state machine ID — undermining the fraud-detection safety net Hyperbridge relies on to prevent processing of forged/invalid state commitments, which can be leveraged to deliver unsound cross-chain messages (mint/settlement) before a fisherman can react.

### Likelihood Explanation
Triggering the stale-state condition requires only the two already-existing root-governed calls `add_parachain` → `remove_parachain` (no new privileged action needed), and reoccurs automatically the moment that para ID is whitelisted again — either intentionally by governance or because Polkadot/Kusama parachain slot IDs are reassigned to new projects over time. Root/governance is a privileged actor, so this is not attacker-controlled in isolation, but it is a genuine cleanup gap directly analogous to the reported `removeContract` bug class: unlike `EvmHost.updateHostParams`, which only ever *adds* to `_latestStateMachineHeight` and never removes state machines (so this specific staleness only exists in the Substrate parachain client's whitelist), this pallet does support full add/remove/re-add cycles, making the stale-policy reuse concretely reachable.

### Recommendation
In `remove_parachain`, also clear the `ChallengePeriod` entry for the corresponding `StateMachineId { state_id, consensus_state_id }` (mirroring the construction used in `add_parachain`), so a subsequent `add_parachain` call is forced to explicitly re-establish (or a safe non-zero default) challenge period rather than silently inheriting a stale `0`. Consider also auditing `ismp-arbitrum`/`ismp-optimism` pallets, which have no removal path at all for their `SupportedStateMachines`/oracle-address mappings, for the same class of issue if a removal extrinsic is ever added.

### Proof of Concept
1. Root calls `ismp_parachain::add_parachain(origin, [ParachainData{ id: 2000 }])` → `Parachains::insert(2000, ())` and `ChallengePeriod` for `StateMachineId{state_id: Polkadot(2000), consensus_state_id: DOT0}` set to `0`.
2. Root calls `ismp_parachain::remove_parachain(origin, [2000])` → `Parachains::remove(2000)`, `SlotDurations::remove(2000)`; `ChallengePeriod` entry for that `StateMachineId` is untouched and remains `0`.
3. Root later calls `add_parachain(origin, [ParachainData{ id: 2000 }])` again (e.g., because the para ID was reassigned to a new project after its original lease expired) — the state machine is whitelisted again with the previously-stale `ChallengePeriod = 0` still in effect.
4. Any submitted state proof for `StateMachine::Polkadot(2000)` immediately passes `verify_delay_passed` (`delay_period.as_secs() == 0`) in `modules/ismp/core/src/handlers.rs`, bypassing the fraud-proof/fisherman veto window entirely, even though governance's intent when re-whitelisting may have been to apply a fresh, non-zero challenge period.

```text
The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs. This may arise from double signing or eclipse attacks. The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state. In this state it can no longer process new consensus messages as well as new requests & responses. Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead.

## Events

The consensus handlers should emit events when a consensus proof is successfully processed or a consensus client is frozen due to consensus fault proofs. This action enables relayers responsible for transmitting requests and responses to either start relaying new eligible requests or stop their relaying tasks.

### `StateMachineUpdated`

```rust showLineNumbers
/// Emitted when a state machine is successfully updated to a new height
struct StateMachineUpdated {
    /// State machine height
    state_machine_id: StateMachineId,
    /// State machine latest height
    latest_height: u64,
}
```

A `StateMachineUpdated` event is emitted to notify network participants (both relayers and fishermen) of some newly available `StateCommitment`s for a given state machine. Relayers will wait for the configured `challenge_period` before attempting to transmit new requests & responses. While fishermen will check if these pending `StateCommitment`s describe valid states on the counterparty network. If the `challenge_period` elapses without any fraud proofs being presented, we can safely conclude that the provided `StateCommitment`s are indeed canonical.
