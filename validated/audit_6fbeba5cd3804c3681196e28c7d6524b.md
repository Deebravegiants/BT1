### Title
Withdrawal status misreported when a batch contains multiple withdrawals of the same token, causing a failed withdrawal to be reported as completed with another withdrawal's transaction hash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal (identified by its `index` inside a batched NEAR transaction) using only `findMatchingWithdrawal`, which matches purely by `assetId`/`near_token_id` and ignores both `index` and `destinationAddress`. When a single NEAR transaction contains two or more withdrawals of the same token (e.g., the same token sent to two different destination addresses), every call to `describeWithdrawal` for that token returns the same matched entry regardless of which of the two withdrawals is actually being queried, so the reported `status`/`txHash` can belong to a different withdrawal than the one the caller asked about.

### Finding Description
`describeWithdrawal` is the function the SDK's polling loop (`watchWithdrawal` in `packages/intents-sdk/src/core/withdrawal-watcher.ts`) uses to decide whether a withdrawal has completed, failed, or is still pending: [1](#0-0) 

It delegates the actual matching to `findMatchingWithdrawal`, which is explicitly documented as matching by `assetId` only, not by `index`: [2](#0-1) 

The equivalent helper in `internal-utils` has the identical limitation: [3](#0-2) 

`createWithdrawalIdentifier`/`createWithdrawalIdentifiers` build one `WithdrawalIdentifier` per withdrawal in a batch, each carrying its own `index` and `withdrawalParams` (including `destinationAddress`): [4](#0-3) 

But because `describeWithdrawal` never uses `index` (or `destinationAddress`) to disambiguate, if the POA API returns two withdrawal records with the same `near_token_id` for the same NEAR `tx_hash` (one `COMPLETED`, one `FAILED`/`REFUNDED`), both `watchWithdrawal` calls — one for each `WithdrawalIdentifier` sharing that `assetId` — resolve to the array's first match. This breaks the equality "status reported == the on-chain outcome for *this* withdrawal": the failed withdrawal's poll can be reported as `completed` with the `transfer_tx_hash` that actually belongs to the other, successful withdrawal.

### Impact Explanation
This falls under the explicitly allowed High-severity class: "a status or hash misreport making an integrator credit or refund twice." An integrator using `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` for a batch containing two same-token withdrawals to different destinations would receive a `completed` result with a transaction hash for a withdrawal that never delivered funds to that destination — it may credit/settle the failed withdrawal as done based on someone else's transaction hash, while the actual failed withdrawal's funds may have been refunded into the intents balance rather than delivered on-chain to the intended destination.

### Likelihood Explanation
Triggering this requires only a normal (non-malicious) user or integrator to submit a batched withdrawal where two of the withdrawals share the same `assetId` (same token, e.g. split across two recipient addresses) in a single NEAR transaction — no privileged or adversarial action is needed, and the code path (`createWithdrawalIntents`/`waitForWithdrawalCompletion`) is a normal SDK usage pattern for batch withdrawals.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` (both in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) using more than `assetId`: incorporate `destinationAddress`/`amount` (and, once the POA API supports it, a stable per-withdrawal identifier) so that each `WithdrawalIdentifier`'s `index` maps deterministically to the correct API response entry, rather than the first entry with a matching token id.

### Proof of Concept
1. Build a withdrawal batch containing two `WithdrawalParams` for the same `assetId` (e.g. `nep141:eth.omft.near`) but different `destinationAddress`es, and submit them in one NEAR transaction via `createWithdrawalIntents`.
2. Suppose withdrawal A (index 0) ultimately fails/is refunded by the POA bridge, and withdrawal B (index 1) completes successfully.
3. The POA bridge status API returns both records for the shared `tx_hash`, e.g. `[{status: "COMPLETED", data: {near_token_id: "eth.omft.near", transfer_tx_hash: "hash-B", ...}}, {status: "REFUNDED", data: {near_token_id: "eth.omft.near", ...}}]` (order per API, documented as "unsorted").
4. Call `watchWithdrawal`/`waitForWithdrawalCompletion` for withdrawal identifier A (index 0). `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`) matches purely on `nep141:${near_token_id} === assetId`, so it returns the first array entry — the `COMPLETED` record for withdrawal B — for the query about withdrawal A.
5. The caller/integrator receives `{status: "completed", txHash: "hash-B"}` for withdrawal A even though withdrawal A actually failed, matching the existing regression test that documents this exact matching behavior: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054` ("matches withdrawal by assetId, not by index").

		args: WithdrawalIdentifier & { logger?: ILogger },

		// Response list is unsorted, so we match by assetId instead of index

			return { status: "pending" };

				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

 * Finds a withdrawal matching the given criteria.

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {

		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
