## Title
Webhook `shop` and `topic` identity fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` fields directly from caller-supplied HTTP headers, but `to_signable_string` — the value that is actually HMAC-verified — returns only the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` and `request.topic` when constructing `WebhookMetadata` passed to the app's handler. This breaks the identity binding: `hmac_verified(body) == true` is treated as equivalent to `hmac_verified(shop, topic, body) == true`, which does not hold.

### Finding Description
`Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` returns `@raw_body` only: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body-based HMAC and then hands `request.shop` and `request.topic` straight to the app's handler as trusted identity metadata: [4](#0-3) 

This is the same bug class described in the external report: a field that is *acted on* (here, `shop`/`topic`, used by the host application to route data to the correct tenant and event handler) is not covered by the integrity check (HMAC), while a different, unrelated field (the raw body) is. An unprivileged internet user who has observed any single legitimate `(body, hmac)` pair for the target app (webhook payloads are not secret — Shopify's webhook payload shapes are public/documented, and can also be observed by the attacker's own shop installing the app) can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` and `shopify-topic` header. The HMAC still validates (it only covers `body`), but the handler now receives attacker-chosen `shop`/`topic` values it treats as authenticated.

### Impact Explanation
This crosses the tenant boundary the gem is documented to enforce: an app relying on `WebhookMetadata#shop` (as constructed by `Registry.process`) to determine which merchant record to update, delete, or act upon can be made to act on behalf of a shop the attacker specifies, using a body the attacker did not need the app's secret to sign (they reused a previously-observed valid signature). Depending on the topic chosen (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`), this can trigger destructive or data-disclosure actions attributed to the wrong tenant — a cross-tenant impact.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and possession of any one valid `(body, hmac)` pair for that app's `api_secret_key`, which is realistically obtainable by an attacker who operates their own shop that installs the target app (a normal, unprivileged path) and captures the webhooks Shopify sends them. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind these header-derived identity fields to the signature before they are surfaced to the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`) and captures a legitimate webhook delivery for some topic, recording the exact `raw_body` and the `x-shopify-hmac-sha256` value Shopify computed for it.
2. Attacker sends a POST to the victim app's webhook endpoint reusing that same `raw_body` and `hmac` header, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or another sensitive topic whose body shape matches the captured one)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `raw_body`, unaffected by the header changes.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with the attacker-chosen `shop` and `topic`, causing the app to process an event as if it authentically originated for `victim-shop.myshopify.com`.
