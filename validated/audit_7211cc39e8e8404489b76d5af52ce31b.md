### Title
Webhook HMAC only signs the request body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used to route and identify the tenant are taken from unsigned HTTP headers. This breaks the identity binding `shop authenticated == shop acted on`, allowing a legitimately-signed webhook payload to be replayed with a forged `shop-domain` header, causing the gem to hand data to the host app's handler under an attacker-chosen tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read from HTTP headers that are never part of the signed material: [2](#0-1) 

`HmacValidator.validate` verifies only that the HMAC matches `verifiable_query.to_signable_string` (i.e., the body) against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` trusts this validation and forwards `request.shop` (an unsigned header value) directly into the handler as the tenant identifier, without any additional check binding it to the HMAC: [4](#0-3) 

Because the signature covers only the JSON body and not the `shop-domain` header, any request with a body/HMAC pair that was legitimately generated for one shop (e.g., a webhook delivered to the attacker's own store where the attacker controls their own install and can capture genuine deliveries) remains valid HMAC-wise even after the `shop-domain` header is swapped to a victim shop's domain. The equality that should hold — `shop bound by HMAC == shop dispatched to handler` — does not hold here, since the header is outside the signable string.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem asserts a webhook is "verified" (`Errors::InvalidWebhookError` is only raised when the body HMAC fails) and then hands the *unauthenticated* `shop` value to the application's webhook handler as if it were verified alongside the body. If the host application (as `ShopifyApp` or custom integrations commonly do) uses `WebhookMetadata#shop` to select the tenant/session/database row to update, an attacker can cause writes, deletes, or notifications to be attributed to or executed against a different, victim shop than the one that actually generated the payload — cross-tenant access, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
The attacker needs no access to the app's `client_secret`/`api_secret_key`. They only need one legitimately delivered webhook (readily obtainable by installing the target app on their own store, a fully unprivileged action) to obtain a valid `(raw_body, hmac)` pair, then can replay it to the app's public webhook endpoint with an arbitrary `shop-domain`/`webhook-id`/`topic` header combination that this gem does not bind to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable material verified by the HMAC, or otherwise cryptographically bind the header-derived `shop` value to the signed body before it is exposed via `WebhookMetadata`. At minimum, document/require that host applications treat the `shop-domain` header as untrusted unless the app independently confirms tenant identity (e.g., cross-checking against a shop that is known to have registered that specific `webhook_id`).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker.myshopify.com`) and triggers an event to receive a real webhook: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, plus a JSON body.
2. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against the (unchanged) raw body — validation succeeds.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` and passed to the handler, even though the HMAC never covered the `shop-domain` header: [5](#0-4) 
5. The host app's handler processes the event as belonging to `victim.myshopify.com`, causing cross-tenant data corruption/leakage depending on the handler's logic.
