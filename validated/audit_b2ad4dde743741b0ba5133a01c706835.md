## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` (or `shopify-shop-domain`) header as the tenant identity passed to the app's handler. The HMAC binding covers only the byte content of the body, not the shop-domain header, so the two can be mixed and matched.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read straight from an HTTP header that is never fed into the HMAC computation: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC and then forwards the header-derived `shop` value, unauthenticated, to the registered handler as tenant identity: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e., the raw body, with no reference to headers such as `shop`: [4](#0-3) 

The identity binding the gem is supposed to enforce is:
`HMAC_valid(raw_body) == authenticated(shop_domain)`

But the actual behavior is:
`HMAC_valid(raw_body)` (over body bytes only) `!=` `shop` (read from an unsigned header)

So an attacker who legitimately receives one authentic webhook (e.g., for their own installed shop) can replay the same raw body and its valid HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The signature still validates (it only checks body bytes against the shared secret), and `Registry.process` passes the attacker-chosen `shop` value straight into `WebhookMetadata`, which downstream application code (as instructed by this gem's own docs) uses to attribute/act on the webhook per-tenant.

The gem's documentation reinforces the false assumption that HMAC verification authenticates the whole request, not just the body: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," with no caveat that the shop attribution is unauthenticated: [5](#0-4) 
and the `data.shop` field is documented as trustworthy metadata for the handler to key off of: [6](#0-5) 

### Impact Explanation
This breaks the shop/tenant binding the HMAC is meant to enforce: an app relying on `WebhookMetadata#shop` (as the gem's own docs instruct) to determine which merchant's data/session a webhook applies to can be tricked into processing another shop's data update, or attributing an attacker-controlled shop's data as belonging to a victim shop — a cross-tenant confusion that meets the Critical "cross-tenant access" bar, since no access token or `api_secret_key` is required by the attacker; only receipt of one legitimately signed webhook body (trivially obtainable by installing the app in the attacker's own dev shop).

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one legitimately signed webhook payload (easy to obtain by simply installing/using the app on a shop they control) and the ability to send an HTTP POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header — both are unprivileged-internet-user actions with no secret material required.

### Recommendation
Include the shop domain (and other trust-relevant headers such as `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise independently bind the header-derived `shop` to a verified source of truth (e.g., cross-check against the webhook subscription registered for that specific shop/session) before dispatching to handlers. At minimum, update `docs/usage/webhooks.md` to explicitly state that `data.shop` is not covered by the Shopify HMAC and must be independently validated by the host application before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with a valid `x-shopify-hmac-sha256` header computed over the raw JSON body.
2. Attacker replays the exact same raw body (and therefore the exact same valid HMAC) to the app's webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed from these attacker-controlled headers/body.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `@raw_body` — see: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` returns `"victim.myshopify.com"` even though the body itself was never intended for that shop: [8](#0-7) 
6. Any host application following this gem's documented pattern of trusting `data.shop` will now act on `victim.myshopify.com`'s behalf using attacker-supplied data.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
