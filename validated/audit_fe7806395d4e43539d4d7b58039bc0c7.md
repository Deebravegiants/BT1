## Custody Invariant Reduction

The external report's core invariant: **a signed authorization for asset movement must be single-use and time-bounded** — it must not remain valid indefinitely and it must not be replayable after its intended execution window. The GluexRouter bug violates "time-bounded"; the Aptos-native analog found below violates both "time-bounded" **and** "single-use."

## Candidate Paths Considered

1. `aptos_framework::multisig_account` timelock (`upsert_timelock`/`can_execute_with_timelock`) — timelock bypass windows are explicitly documented as accepted risk and gated behind multisig quorum re-authorization; no unprivileged root cause found.
2. `aptos_framework::object::transfer_with_ref` / `LinearTransferRef` — owner is snapshotted and re-checked at transfer time; no expiry issue, ref is single-use by design (consumed on call).
3. `primary_fungible_store`/`fungible_asset` `TransferRef`-based flows — all gated by module-held refs, no time or replay dimension exposed to unprivileged callers.
4. `stablecoin::usdk::transfer_from` — a signed off-chain "permit"-style approval for third-party transfers, analogous to the swap `deadline` pattern. **This is the strongest candidate**: it independently reproduces the missing-deadline defect and adds a replay defect on top.

### Title
Off-chain Transfer Approval in `usdk::transfer_from` Has No Expiration and No Dedicated Nonce, Enabling Indefinite Replay of a Single Signature to Drain a Victim's Balance - (File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move)

### Summary
`usdk::transfer_from` lets any `spender` present a signed `Approval` message on behalf of an `owner` account to move fungible assets out of that owner's primary store. The `Approval` struct that is signed contains no deadline/expiry field, and the "nonce" used to make the approval unique is simply the owner's *on-chain account sequence number* — a value the `transfer_from` call itself never consumes or advances. As a result, a single signed approval remains valid forever and can be replayed an unlimited number of times as long as the owner does not submit any transaction of their own that would bump their sequence number, exactly mirroring the GluexRouter `swap()` deadline-omission bug class but with a strictly worse custody impact (unbounded fund drain instead of stale pricing).

### Finding Description
`transfer_from` constructs the message that must be signed by the token owner: [1](#0-0) 

The `Approval` struct itself has no `deadline`/`expiration` field: [2](#0-1) 

The "nonce" field is populated from `account::get_sequence_number(from)` at verification time, not from any counter that `transfer_from` maintains or increments: [3](#0-2) 

Because `spender` (not `from`) submits the transaction, executing `transfer_from` does not change `from`'s account sequence number. Consequently:
- The signed message the owner produced off-chain remains valid for `account::verify_signed_message` on every subsequent call, since the expected message (built from the still-unchanged sequence number) matches the proof every time.
- There is no `deadline`/expiry check anywhere in `transfer_from`, so the approval can be executed at any future block, just like the GluexRouter `swap()` omission.
- The only way the approval stops being valid is if `from` happens to submit an unrelated transaction from their own account (incrementing their real sequence number) — an event entirely outside the owner's control in the context of this permit flow and not something a user would expect to serve as a security boundary for a token-approval scheme.

This breaks the custody invariant that authorization for moving a user's fungible-asset balance must be bounded in both time and reuse. The actual transfer is executed via the privileged `TransferRef` held by the module: [4](#0-3) 

so once a single valid signature is obtained (e.g., leaked from a dApp, a compromised frontend, or simply observed on an intermediate chain/mempool before intended use), any `spender` address can call `transfer_from` repeatedly to drain `from`'s balance in `amount`-sized increments until the store is empty, entirely bypassing the owner's expectation of a single, time-boxed authorization.

### Impact Explanation
This is a high/critical custody-grade impact: unauthorized, repeatable theft of a user's fungible-asset (USDK) balance using a single previously obtained signature, with no time bound and no built-in single-use enforcement. It matches the "Theft ... of ... fungible assets" and "Supply or custody accounting corruption that moves value to the wrong holder" impact categories directly. Because `usdk` is a managed-stablecoin example pattern likely to be copied by real token deployments (the module explicitly documents this as an approval mechanism "via the Aptos SDK"), the pattern risk extends to any downstream token built on this template.

### Likelihood Explanation
Likelihood is high for any deployment that adopts this exact pattern: the vulnerable condition is not an edge case — it is the default behavior of the function as written. Exploitation requires only that a spender obtain one valid signed `Approval` (via phishing, a compromised dApp integration, or the owner's own client persisting/leaking a signature) and that the owner does not submit an unrelated transaction in the interim (a scenario common for wallets that are not actively transacting). No special privileges are required by the attacker.

### Recommendation
- Add an explicit `deadline: u64` field to `Approval` and assert `timestamp::now_seconds() <= deadline` in `transfer_from` before performing the transfer, mirroring the requested Solidity fix.
- Introduce a dedicated, monotonically increasing nonce/counter per `(owner, spender)` or per `owner` that is stored and incremented by `usdk` itself upon successful `transfer_from` execution (not the account's transaction sequence number), so each signed approval can be consumed exactly once.

### Proof of Concept
1. Owner `A` signs an `Approval { owner: A, to: B, nonce: account::get_sequence_number(A), chain_id, spender: S, amount: 100 }` intending a one-time transfer of 100 USDK to `B`, executed by relayer `S`.
2. `S` calls `usdk::transfer_from(S, proof, A, scheme, pubkey_A, B, 100)`. It succeeds; `A`'s FungibleStore balance decreases by 100.
3. `A` has not submitted any transaction of their own, so `account::get_sequence_number(A)` is unchanged.
4. `S` calls `usdk::transfer_from` again with the same `proof`. `verify_signed_message` recomputes the identical `expected_message` (same unchanged nonce) and the signature verifies again — the transfer succeeds a second time, moving another 100 USDK from `A` without any new authorization.
5. Repeat indefinitely until `A`'s balance is exhausted, or until `A` happens to submit an unrelated transaction that bumps their sequence number — a race the owner does not control and has no visibility into. [5](#0-4)

    /// Allow a spender to transfer tokens from the owner's account given their signed approval.
    /// Caller needs to provide the from account's scheme and public key which can be gotten via the Aptos SDK.
    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,
    ) acquires Management, State {
        assert_not_paused();
        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }
