### Title
Native-token overpayment on `EvmHost.dispatch()`/`fundRequest()` is permanently lost, not refunded to caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native-token payment and forward the entire `msg.value` to Uniswap V2's `swapETHForExactTokens`, but never capture or forward back any unspent dust ETH the router returns. Because the router refunds dust to its immediate caller (`EvmHost` itself, since `EvmHost` is the one invoking the router with `{value: msg.value}`), any overpayment beyond the exact amount needed to buy `post.fee`/`get.fee`/`amount` worth of fee token is permanently absorbed into `EvmHost`'s own balance, with no sweep or forwarding mechanism to return it to the original payer.

### Finding Description
All three payable entry points share the identical pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called. The standard UniswapV2 router implementation buys exactly `fee` tokens and refunds `msg.value - amounts[0]` dust ETH to its caller — which here is `EvmHost` (`address(this)`), not `_msgSender()` (the original dispatcher/app). `EvmHost` accepts this refund via its `receive()` function, so the dust silently accumulates in the contract's own balance. None of these three functions read the `amounts` return value, track `msg.value - amounts[0]`, or forward any remainder back to `_msgSender()`.

This is exactly the same bug class as the reported `LMPVaultRouterBase._processEthIn` issue — native ETH accepted by a payable entrypoint has no guaranteed refund path back to the payer under a normal (non-exact) payment amount — except here the loss occurs on the **success path**, not merely a revert path, making it strictly worse: it fires every single time a caller overpays even slightly.

The codebase's own other dispatch paths demonstrate the correct pattern is well understood and simply missing here. `IntentGatewayV2.placeOrder` explicitly captures the swap output and refunds the true remainder to `msg.sender`: [4](#0-3) 

Moreover, `HyperbridgeLzEndpoint.quote()` explicitly documents and relies on the (false) assumption that `EvmHost.dispatch` refunds unused native value to the caller, and deliberately overpays by 2x based on that assumption: [5](#0-4) 

Since `EvmHost.dispatch` does not actually refund the caller, every `dispatch{value: msgValue}(request)` call routed through this LZ adapter (or any other `HyperApp`/dApp using native payment with any safety margin) permanently forfeits the unused portion into `EvmHost`'s balance.

### Impact Explanation
This affects the core message dispatch path (`EvmHost.dispatch`, reachable by any unprivileged relayer, HyperApp, token bridge, or intent-related contract paying fees in native token) and the fee-top-up path (`fundRequest`, reachable by any user funding a pending request). Because Uniswap V2 pricing shifts between the moment a caller quotes/estimates the required native amount and the moment the transaction executes, virtually any caller that adds a reasonable slippage/safety buffer (as the codebase's own `HyperbridgeLzEndpoint` explicitly does with a 2x buffer) will lose the unspent difference permanently, with no recovery mechanism anywhere in `EvmHost.sol`. This is a systemic, protocol-wide, permanent loss of user/app funds on the single most common transaction type in the system (dispatching a cross-chain message).

### Likelihood Explanation
High. This triggers on the success path of ordinary usage — no adversarial input, malicious admin, or edge-case revert is required. Any caller that does not pass the razor-exact wei amount for the swap (which is effectively guaranteed given price movement between off-chain quoting and on-chain execution, and confirmed by the codebase's own 2x-buffer pattern in `HyperbridgeLzEndpoint`) loses funds. This will occur routinely in production.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    Address.sendValue(payable(_msgSender()), msg.value - amounts[0]);
}
```

### Proof of Concept
1. A `HyperApp` (e.g. `HyperbridgeLzEndpoint`) quotes the native fee for a `DispatchPost` and, per its own documented 2x-buffer strategy, calls `IDispatcher(_host).dispatch{value: 2 * quotedFee}(request)`.
2. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: 2 * quotedFee}(post.fee, path, address(this), block.timestamp)` buys exactly `post.fee` feeToken and the Uniswap router refunds the leftover `~quotedFee` ETH to `msg.sender` of the swap call, which is `EvmHost` itself.
3. `EvmHost.dispatch` returns without ever inspecting or forwarding this leftover ETH; it remains permanently in `EvmHost`'s balance.
4. Repeat for `fundRequest` and `dispatch(DispatchGet)` — same result each time any caller overpays even by 1 wei beyond the exact swap requirement.
5. Verify: `address(evmHost).balance` grows by the overpaid amount after each such call, and no function in `EvmHost.sol` exists to withdraw/sweep or return that balance to the original payers.
