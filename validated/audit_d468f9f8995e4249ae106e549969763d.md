### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated headers while HMAC only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as fully authenticated once `Utils::HmacValidator.validate(request)` passes, then forwards `request.shop`, `request.topic`, and `request.webhook_id` to the app's handler as trustworthy metadata. However, the HMAC signature only ever covers the raw request body — none of these header-derived identity fields are bound to the signature, breaking the intended equality `hmac-signed bytes == bytes acted upon`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from client-supplied HTTP headers, entirely outside the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC and then immediately constructs `WebhookMetadata` from these unauthenticated header fields, passing them to the app's handler as if the whole request — including the shop identity — had been verified: [4](#0-3) 

The library's own documentation reinforces the false assumption that `process` fully verifies the webhook's origin, including the shop it claims to be from: [5](#0-4) 
and explicitly tells integrators to trust `data.shop` for routing/attribution: [6](#0-5) 

**Root cause equality that should hold but doesn't:** `bytes verified by HMAC == bytes used to identify the tenant (shop)`. In this implementation, `bytes verified` = `raw_body` only, while `bytes used to identify the tenant` = `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value, which is never mixed into the HMAC computation.

### Impact Explanation
Because the shop-domain header is unauthenticated, an attacker who can obtain any single valid `(raw_body, hmac)` pair for the target app (e.g., by installing the app on their own low-privilege development store and capturing one of their own legitimate webhook deliveries) can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it never inspects headers), so `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that uses `data.shop` to look up per-tenant state, associate the webhook payload with a shop record, or fetch/act on that shop's stored access token (as the gem's own documentation examples encourage) will process attacker-controlled data under the wrong tenant identity — a cross-tenant confusion enabling data corruption, unauthorized state changes, or triggering shop-scoped business logic against a shop the attacker does not control. This satisfies the Critical bar of cross-tenant access achieved purely as an unprivileged internet user with no `api_secret_key`, no access token, and no privileged account required.

### Likelihood Explanation
Exploitation only requires: (1) ability to install the target app on an attacker-owned development/trial store (a normal, unprivileged action any Shopify Partner can take), (2) capturing one legitimate webhook delivery to obtain a valid `(raw_body, hmac)` pair, and (3) replaying that request to the app's public webhook URL with a forged shop-domain header. No secrets, tokens, or elevated access are needed — the HMAC secret is never touched because the attacker reuses a signature Shopify itself generated for them. This is a low-effort, repeatable attack against any application built on this gem that trusts `WebhookMetadata#shop` for tenant attribution, which the gem's documentation actively encourages.

### Recommendation
Bind the tenant/topic identity to the signed payload rather than trusting header values verbatim:
- Include the header-derived `shop`, `topic`, and `webhook_id` values as part of the HMAC-signed input (mirroring how Shopify's own server-side check could be strengthened), or
- Cross-validate the `shop` header against an independently known value (e.g., the shop associated with the specific webhook subscription/registration ID) before dispatching to the handler, or at minimum
- Update `Utils::HmacValidator`/`Webhooks::Request` so `to_signable_string` incorporates the relevant Shopify headers, and update documentation to clearly state that `shop`/`topic`/`webhook_id` are NOT covered by the HMAC and must be independently corroborated by the host application before being used for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker-shop.myshopify.com` and lets it register a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's callback URL with headers:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over body B>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: ...
   ```
   and raw body `B`.
3. Attacker replays the exact same body `B` and the exact same `X-Shopify-Hmac-Sha256` value to the app's endpoint, but changes only:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes the HMAC only over `request.to_signable_string` (`= B`) — this still matches, so validation succeeds.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the host application's handler processes the (attacker-controlled) body as though it legitimately originated from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
