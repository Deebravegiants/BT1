### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and handed to the app's webhook handler as trusted identifiers. Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant who legitimately installs the app can capture one of their own validly-signed webhook deliveries and replay it to the app with the `shop-domain` header rewritten to a victim shop, producing a request that still passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the body) against the secret: [3](#0-2) 

`Registry.process` trusts the HMAC check as proof of authenticity for the whole request, then forwards the unauthenticated `shop` (and `topic`, `webhook_id`) straight to the host application's handler: [4](#0-3) 

The identity binding that should hold is:
`shop header used by handler == shop the HMAC actually authenticates`

Since the HMAC only authenticates the body bytes and is computed with a secret shared by all shops installing the app, this equality does not hold: the HMAC proves "this body was produced by an app secret holder" but says nothing about which shop it belongs to. Any party who is a legitimate installer of the app (i.e., an ordinary, unprivileged merchant/attacker running their own free/dev store) receives real, correctly-signed webhook deliveries for their own store. Because the shop identity is carried only in an unsigned header, that party can replay the exact same raw body + HMAC pair while substituting the `X-Shopify-Shop-Domain` header of a different, victim shop. `HmacValidator.validate` still returns `true` (only the body is checked), and `Registry.process` passes the attacker-chosen `shop` value into `WebhookMetadata`, which the host application will treat as an authenticated event from the victim's tenant.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an attacker who only controls their own shop's app installation can forge webhook events (e.g., `app/uninstalled`, GDPR `customers/redact`, `orders/create`, etc.) that the host application will process as coming from a victim merchant's shop, since `request.shop` is passed through unauthenticated to `handler.handle`. Depending on what the host app does with these events (revoking/deleting session data, mutating victim records, triggering data exports), this is a cross-tenant access primitive achievable purely by an unprivileged internet user who has legitimately installed the app on their own store — no access token, leaked secret, or privileged account required.

### Likelihood Explanation
Any user can install a publicly listed app (or an app with a public install URL) on a free development store, which is enough to receive genuine webhook deliveries signed with the shared `api_secret_key`. Capturing and replaying an HTTP request with one header changed is trivial, and nothing in `Request`, `HmacValidator`, or `Registry` re-derives or re-validates the `shop` value against the signed content.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the authenticated request, e.g.:
- Include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, matching them against a copy embedded in the (signed) body where possible, or
- Require host applications to confirm the `shop` header corresponds to a shop with an active, previously stored session/installation before trusting the event, and document this as a hard requirement of `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled development store `attacker-shop.myshopify.com`.
2. Trigger a webhook whose body content is attacker-controllable/predictable (e.g., a `customers/redact` GDPR webhook, or any webhook with a fixed/empty body), and capture the raw HTTP request, including the valid `X-Shopify-Hmac-Sha256` header and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Replay the identical request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes the (unchanged) raw body: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the request never actually originated from, nor was authenticated for, that shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
