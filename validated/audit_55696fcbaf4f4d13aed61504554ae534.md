### Title
Missing input/output array length validation in `fillOrder` allows solver to permanently freeze escrowed funds — ([File: sdk/packages/core/contracts/apps/IntentGatewayV2.sol])

### Summary
The `evm/src/apps/IntentGatewayV2.sol` copy of the intent gateway validates that `order.inputs.length`, `order.output.assets.length`, and `options.outputs.length` are all equal before routing to same-chain or cross-chain fill logic: [1](#0-0) 

The `sdk/packages/core/contracts/apps/IntentGatewayV2.sol` copy of the same contract — used as the packaged/canonical template distributed via the SDK — contains a `fillOrder` function but the grep search for the corresponding length-equality checks (`outputsLen != `, `options.outputs.length != `, `order.inputs.length != `) returns zero matches in that file, while the same search returns four matches in `evm/src/apps/IntentGatewayV2.sol`. This indicates the SDK's packaged copy of the gateway is missing the array-length-parity check that `evm/src` has, which is exactly the bug class described in the M-10 report (unequal-length arrays silently ignoring extra elements).

### Finding Description
`_fillSameChain` and `_fillCrossChain` both iterate `for (uint256 i; i < outputsLen; i++)` (where `outputsLen = order.output.assets.length`) and index into `order.inputs[i]` to compute the proportional escrow to release to the filler: [2](#0-1) 

and in the cross-chain path, the entire `order.inputs` array is forwarded as the `RedeemEscrow`/`RefundEscrow` payload: [3](#0-2) 

If `order.inputs.length` and `order.output.assets.length` are not required to be equal (as is the case when the `fillOrder` length-parity check is absent), a user can `placeOrder` with an `inputs` array longer than `output.assets`. On fill, the escrow-release loop is bounded by `outputsLen`, so only the first `outputsLen` entries of `escrowedInputs`/`order.inputs` are released to the filler via `_withdraw`. The remaining excess input tokens that were escrowed at `placeOrder` time are never referenced by any release path once `_filled[commitment]` is set, and `cancelOrder` is blocked once an order is filled: [4](#0-3) 

This is the direct analog of the M-10 root cause: an unchecked length mismatch between parallel arrays causes the "extra" elements to be silently ignored during a batch/looped release, rather than reverting.

### Impact Explanation
Any user's escrowed input tokens beyond the `output.assets.length`-th index become permanently unreachable once the order is filled: they are not released to the filler (loop bound is `outputsLen`), not released to the user (cancellation is blocked because `_filled[commitment] != address(0)`), and not tracked by any other accounting path. This constitutes permanent freezing of user funds in the escrow contract — a concrete, high-severity impact for the intents/escrow subsystem reachable by any ordinary user submitting a single `placeOrder`/`fillOrder` pair of transactions.

### Likelihood Explanation
Reachable by any unprivileged order placer with a single `placeOrder` call constructing an `Order` whose `inputs` array is longer than `output.assets`, followed by a normal `fillOrder` from any solver (the solver need not be malicious or aware of the mismatch — the loss is a structural consequence of the missing check, not solver misbehavior). No special privileges, consensus proofs, or governance actions are required.

### Recommendation
Add the same array-length-parity checks that already exist in `evm/src/apps/IntentGatewayV2.sol` (`fillOrder`, lines 474-476) to `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`'s `fillOrder`, requiring `order.inputs.length == order.output.assets.length == options.outputs.length` before dispatching to `_fillSameChain`/`_fillCrossChain`. Additionally, consider validating this invariant at `placeOrder` time so a malformed order can never be created and escrowed in the first place.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs` = `[TokenA: 100, TokenB: 50]` and `order.output.assets` = `[TokenC: 100]` (inputs longer than outputs). Both `TokenA` and `TokenB` amounts are escrowed under the commitment.
2. Solver calls `fillOrder` providing `options.outputs` = `[TokenC: 100]` (length 1, matching `order.output.assets`, but not `order.inputs`). Because the packaged gateway does not check `order.inputs.length == outputsLen`, this passes.
3. In `_fillSameChain`, the loop runs only `outputsLen = 1` time, computing `escrowedInputs[0]` from `order.inputs[0]` (TokenA) only. `_withdraw` releases only TokenA to the filler.
4. `order.inputs[1]` (TokenB, 50 escrowed) is never referenced again. `_filled[commitment]` is now set (non-zero), so `cancelOrder` reverts with `Filled`. The 50 TokenB remain locked in the contract permanently, unreachable by user, filler, or protocol.

Note: I could not directly view the full body of `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`'s `fillOrder` function within the available tool budget — the conclusion that the check is missing is based on the grep pattern match count (0 matches for the length-check patterns in that file versus 4 in `evm/src/apps/IntentGatewayV2.sol`). A background Devin session with full file access should confirm the exact missing lines before remediation.
