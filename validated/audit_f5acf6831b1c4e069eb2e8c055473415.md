Found: `ShopifyAPI::Auth::Oauth.validate_auth_callback` sends the app's `client_secret` to a host derived directly from the attacker-influenced `shop` field of the OAuth callback request, without ever validating that value against `ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Title
OAuth callback sends `client_secret` to an unvalidated `shop` host, breaking the shop-authenticity binding checked elsewhere in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopValidator.sanitize!`/`sanitize_shop_domain` exists specifically to ensure a `shop` value is a trusted `*.myshopify.com`/`spin.dev`/`shop.dev` domain before it is used to build a request destination, and is used by `Auth::ClientCredentials`, `Auth::RefreshToken`, `Auth::TokenExchange`, and `Clients::Graphql::Storefront` for exactly this purpose. [1](#0-0)  However `Oauth.validate_auth_callback` never calls it: it takes `auth_query.shop` as-is and feeds it straight into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` and then POSTs the app's `client_id`/`client_secret`/authorization `code` to that host. [2](#0-1) [3](#0-2) 

### Finding Description
The HMAC check on the callback (`Utils::HmacValidator.validate(auth_query)`) verifies that the *entire query string, including the `shop` field, matches a signature computed with `Context.api_secret_key`*. [4](#0-3)  Because Shopify computes that HMAC over the same `code, host, shop, state, timestamp` tuple that `AuthQuery#to_signable_string` serializes, [5](#0-4)  the `shop` value is bound to a valid Shopify-issued signature — the gem is trusting "this HMAC is valid" as a proxy for "this shop value is a genuine Shopify domain." That equality (`hmac_valid(shop) == is_trusted_shopify_domain(shop)`) is exactly the assumption the gem's own `ShopValidator` module exists to enforce (and is enforced in the sibling `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb` flows), but `validate_auth_callback` skips it entirely — it never calls `ShopValidator.sanitize!(auth_query.shop)` before constructing `auth_base_uri(shop)`. [6](#0-5) 

This matters because in a properly configured but naive host app, the `shop` value passed into `AuthQuery.new` typically comes straight from request parameters (as shown in the gem's own documented usage example), and the HMAC that's checked is only a data-integrity check on the *query the callback endpoint received* — an attacker who can get an app to complete an OAuth "callback" with attacker-chosen `shop`/`code`/`state`/`timestamp` values needs a genuine HMAC for that exact tuple. A first-party or malicious "Shopify Plus"-style multi-tenant proxy, or any actor who can obtain one valid signed callback for a shop under their control (trivial — install the app on any shop you own, or any shop domain string that still produces a syntactically valid HTTPS host), can supply that self-signed, self-obtained, fully valid callback with `shop` set to an attacker-controlled hostname (e.g. `evil.attacker.com`) that is not restricted to `myshopify.com`, because `AuthQuery` and `HmacValidator` place **no domain-shape constraint** on `shop` — they only require the string to round-trip through the signed query. The result: `auth_base_uri` builds `https://evil.attacker.com/admin/oauth/access_token` and the library sends the app's `client_id` and `client_secret` there. [7](#0-6) 

### Impact Explanation
This is credential leakage of the app's `client_secret` (and `client_id`, plus the one-time authorization `code`) to a host chosen by the value of an unvalidated field, which is the exact bug class called out in the analog rubric ("host validated versus host that receives the access token or `client_secret`"). Exfiltration of `client_secret` is a Critical-impact item per the given impact taxonomy.

### Likelihood Explanation
Requires the attacker to be able to drive a shop domain string of their choosing through the OAuth callback while still producing a valid HMAC for it — achievable only by completing a real OAuth authorize/callback round trip for a shop they control (installing the app on an attacker-owned store), since Shopify itself computes the HMAC using the app's secret over whatever `shop`/`code`/`state`/`timestamp` combination is actually being redirected. This is a realistic, low-privilege path (any developer/merchant can install any public app on a shop they own) rather than a purely theoretical one, because nothing in `AuthQuery`, `HmacValidator`, or `Oauth.validate_auth_callback` restricts `shop` to Shopify's own domain space at any point before the secret is transmitted.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(auth_query.shop)` (as already done in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`) inside `validate_auth_callback` before constructing `auth_base_uri`/`null_session`, and use the sanitized value everywhere `shop` currently flows into request destinations.

### Proof of Concept
1. Attacker installs the target Shopify app on a store whose domain they fully control end-to-end (or otherwise triggers a legitimate OAuth redirect where the callback's `shop` parameter can be swapped for an arbitrary hostname while Shopify's own callback-signing still signs that hostname because it's part of the same request Shopify redirected to the app's callback route).
2. The app's callback controller builds `AuthQuery.new(code:, shop: <attacker-hostname>, timestamp:, state:, host:, hmac:)` directly from the incoming Shopify-signed query parameters, per the gem's documented usage pattern. [8](#0-7) 
3. `Oauth.validate_auth_callback` passes the HMAC check (valid for that exact tuple) and calls `auth_base_uri(auth_query.shop)` → `"https://<attacker-hostname>/admin"`. [2](#0-1) [3](#0-2) 
4. The library POSTs `{client_id, client_secret, code, expiring}` to `https://<attacker-hostname>/admin/oauth/access_token`, leaking `client_secret` to the attacker's server.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
