## Finding: Marketplace commission fee is fetched live at settlement, not locked at listing creation, letting the `FeeSchedule` owner redirect a seller's sale proceeds after a listing is placed

### Title
Marketplace commission fee can be changed after a listing is created and before it settles, diverting seller proceeds without consent - (File: `aptos-move/move-examples/marketplace/sources/coin_listing.move`)

### Summary
This is the direct Aptos analog of the Putty `fee` bug. A `Listing` stores only a *reference* to its `Object<FeeSchedule>` rather than the commission rate itself. At purchase/auction-completion time, `coin_listing::complete_purchase` calls `fee_schedule::commission(fee_schedule, price)` to compute the marketplace cut, which reads whatever commission is *currently* configured on the `FeeSchedule` object — not the rate that existed when the seller listed the asset. [1](#0-0) [2](#0-1) 

### Finding Description
`FeeSchedule` is a standalone object whose owner (`creator`) can mutate the commission at any time via `set_fixed_rate_commission` / `set_percentage_rate_commission`, guarded only by `object::is_owner(marketplace, signer::address_of(creator))` — no restriction tied to any specific outstanding listing: [3](#0-2) [4](#0-3) 

`Listing` (in `listing.move`) stores `fee_schedule: Object<FeeSchedule>` — a pointer, not a snapshot of the fee terms — alongside `seller` and `start_time`: [1](#0-0) 

When a sale is finalized (`purchase`, `complete_auction` → `complete_purchase`), the commission is computed with the *current* fee schedule state, not one captured at listing creation: [5](#0-4) 

`fee_schedule::commission` simply reads whatever `FixedRateCommission`/`PercentageRateCommission` resource currently exists under the `FeeSchedule` object address: [6](#0-5) 

Only the `listing_fee` (paid once, up front, at listing creation) is captured immediately; the commission is deferred entirely to settlement time: [7](#0-6) 

Root cause: the custody invariant "the fee split agreed to at listing creation must be honored at settlement" is not enforced. The `FeeSchedule` object owner can raise the commission (up to `numerator == denominator`, i.e. 100%) between the time a seller lists an asset (e.g. an auction that may run for a long duration, or a fixed-price listing left open indefinitely) and the time the sale is completed by any third party caller (`complete_auction` is permissionless — `completer: &signer` is unconstrained).

### Impact Explanation
At purchase completion, `commission_charge = fee_schedule::commission(fee_schedule, price)` is deducted from the payment before the remainder is sent to the seller: [8](#0-7) 

If the `FeeSchedule` owner raises the commission to 100% (`numerator == denominator`, permitted by `set_percentage_rate_commission`'s only check `numerator <= denominator`) after a listing/auction is created but before it settles, `actual_commission_charge = min(coin::value(&coins), commission_charge)` consumes the entire remaining sale price, leaving the seller with **zero proceeds** instead of the amount implied by the fee rate that existed when they agreed to list. This is a direct, non-recoverable diversion of custody-held sale value from the rightful seller to the fee address — matching the "custody accounting corruption that moves value to the wrong holder" impact class.

### Likelihood Explanation
Likelihood is high in any deployment where the marketplace operator (fee schedule owner) is distinct from, or not fully trusted by, sellers, or where a compromised/malicious fee-schedule admin key exists. No cooperation from the seller or buyer is required; the fee-schedule owner unilaterally calls a standard entry function (`set_percentage_rate_commission`/`set_fixed_rate_commission`) at any point before a pending listing/auction settles. Auctions in particular can remain open for extended periods (`auction_end_time`), widening the exploit window.

### Recommendation
Snapshot the fee terms (commission numerator/denominator or fixed amount) into the `Listing`/`FixedPriceListing`/`AuctionListing` struct at creation time and use that captured value in `complete_purchase`, rather than re-reading the live `FeeSchedule` object. Alternatively, record a fee-schedule version/timestamp at listing creation and reject settlement (or refund the seller) if the fee schedule has since been mutated, mirroring the mitigations accepted in the original Putty finding.

### Proof of Concept
1. Marketplace owner creates a `FeeSchedule` with `commission = 1%` via `fee_schedule::init`.
2. Seller lists an NFT via `coin_listing::init_auction` (or `init_fixed_price`) referencing that `FeeSchedule` object; buyer/bidder places or intends to place a bid/purchase at price `P`, expecting to receive ~99% of `P`.
3. Before the auction ends (or before a fixed-price purchase occurs), the `FeeSchedule` owner calls `fee_schedule::set_percentage_rate_commission(creator, marketplace, 1, 1)` (100% commission). [9](#0-8) 
4. Any account calls `coin_listing::complete_auction` (permissionless) or the buyer calls `purchase`. `complete_purchase` computes `commission_charge = fee_schedule::commission(fee_schedule, price)` = `price`, so `actual_commission_charge = min(coin::value(&coins), commission_charge) = price`. [8](#0-7) 
5. The seller receives `coin::deposit_coins(seller, coins)` with `coins` now containing `0`, while the entire sale price is routed to `fee_schedule::fee_address`, confirming the diversion of the seller's sale proceeds without their consent.

    inline fun complete_purchase<CoinType>(
        completer: &signer,
        purchaser_addr: address,
        object: Object<Listing>,
        coins: Coin<CoinType>,
        type: String,
    ) {
        let token_metadata = listing::token_metadata(object);

        let price = coin::value(&coins);
        let (royalty_addr, royalty_charge) = listing::compute_royalty(object, price);
        let (seller, fee_schedule) = listing::close(completer, object, purchaser_addr);

        // Take royalty first
        if (royalty_charge != 0) {
            let royalty = coin::extract(&mut coins, royalty_charge);
            aptos_account::deposit_coins(royalty_addr, royalty);
        };

        // Take commission of what's left, creators get paid first
        let commission_charge = fee_schedule::commission(fee_schedule, price);
        let actual_commission_charge = math64::min(coin::value(&coins), commission_charge);
        let commission = coin::extract(&mut coins, actual_commission_charge);
        aptos_account::deposit_coins(fee_schedule::fee_address(fee_schedule), commission);

        // Seller gets what is left
        aptos_account::deposit_coins(seller, coins);

    public entry fun set_fixed_rate_commission(
        creator: &signer,
        marketplace: Object<FeeSchedule>,

    ) acquires FeeSchedule, FixedRateCommission, PercentageRateCommission {
        let fee_schedule_signer = remove_commission(creator, marketplace);

        let updated_resource = type_info::type_name<FixedRateListingFee>();
        event::emit(Mutation { marketplace: signer::address_of(&fee_schedule_signer), updated_resource });
    }

        move_to(&fee_schedule_signer, PercentageRateCommission { denominator, numerator });
        let updated_resource = type_info::type_name<FixedRateListingFee>();
        event::emit(Mutation { marketplace: signer::address_of(&fee_schedule_signer), updated_resource });
    }

    #[view]
    public fun commission(
        marketplace: Object<FeeSchedule>,
        price: u64,
    ): u64 acquires FixedRateCommission, PercentageRateCommission {
        let fee_schedule_addr = assert_exists_internal(&marketplace);
        if (exists<FixedRateCommission>(fee_schedule_addr)) {
            borrow_global<FixedRateCommission>(fee_schedule_addr).commission
        } else if (exists<PercentageRateCommission>(fee_schedule_addr)) {
            let fees = borrow_global<PercentageRateCommission>(fee_schedule_addr);
            math64::mul_div(price, fees.numerator, fees.denominator)
        } else {
            0
        }
    }
