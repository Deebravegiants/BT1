Audit Report

## Title
CORS Origin Allowlist Bypass via Improper Suffix Matching in Gateway User Server - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` validates wildcard CORS entries (e.g. `*.example.com`) using `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, without verifying a dot boundary. This lets any origin whose hostname merely ends with the configured suffix (e.g. `evil-ethereum.org` matching an allowlist for `*.ethereum.org`) be treated as an allowed subdomain.

## Finding Description
`isAllowedOrigin` strips the `*.` from a configured wildcard entry and performs a raw suffix comparison against the request's `Origin` host, with no check that the preceding character is a `.`: `core/services/gateway/network/httpserver.go` lines 184-190. This function is called directly from `handleRequest`, which echoes the raw, attacker-controlled `Origin` header value into the `Access-Control-Allow-Origin` response header whenever `isAllowedOrigin` returns true (lines 195-202). No other authentication or origin-boundary check exists in this path; the exact-match branch (line 181) is bypassed entirely by the wildcard branch's flawed logic. The existing test suite in `httpserver_test.go` only exercises correct subdomain matches and does not test hostile suffix-collision cases, so the bug is not caught by current tests.

## Impact Explanation
When a Gateway operator configures a wildcard `CORSAllowedOrigins` entry (a supported and documented configuration pattern per the code and tests), an attacker who registers or hosts content on any domain sharing the configured suffix without being a true subdomain (e.g. `evil-ethereum.org` vs. allowed `*.ethereum.org`) can have their origin echoed back in `Access-Control-Allow-Origin`. This lets an attacker-controlled web page issue authenticated-looking cross-origin browser requests to the Gateway's user-facing JSON-RPC endpoint and read the response, defeating the intended origin restriction — an allowlist bypass in the Gateway's cross-origin access control.

## Likelihood Explanation
Exploitation requires only (1) a Gateway operator configuring a wildcard CORS origin, a normal supported configuration, and (2) an attacker registering/hosting a domain with a matching suffix — no privileged access, credentials, or node compromise needed. The attack is triggerable directly by an unprivileged browser client via a crafted `Origin` header, making it realistically and repeatably exploitable.

## Recommendation
Fix `isAllowedOrigin` to require a proper subdomain boundary — i.e., `originHost` must equal the base domain exactly or end with `.` + the base domain — rather than a bare suffix match:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```
Add regression tests using hostile suffix-collision hostnames (e.g., `evil-ethereum.org`, `notethereum.org`) to prevent regressions.

## Proof of Concept
1. Configure Gateway `UserServerConfig.CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP POST to the Gateway's user-facing endpoint with header `Origin: https://evil-ethereum.org`.
3. `isAllowedOrigin` computes `allowedHost = "ethereum.org"` after stripping `*.`, then evaluates `strings.HasSuffix("evil-ethereum.org", "ethereum.org")`, which is `true`.
4. Server responds with `Access-Control-Allow-Origin: https://evil-ethereum.org`, confirming the bypass; a Go unit test mirroring `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` but asserting rejection of `https://evil-ethereum.org` would fail against current code, demonstrating the vulnerability.
