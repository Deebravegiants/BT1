### Title
`Wallet#updateSeed` mutates persisted seed metadata with no lock check or seedId ownership validation - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet#updateSeed` writes attacker-supplied `label`/`dateUpdated` fields into `#seedMetadataAtom` for an arbitrary `seedId` without ever calling `#assertWalletIsUnlocked` or verifying that the `seedId` belongs to the caller's session, unlike its sibling mutators `addSeed` and `removeManySeeds`. It is exposed directly on the `walletApi` surface (`features/wallet/api/index.js`), so any caller reachable via the RPC bridge can invoke it regardless of wallet lock state or seed ownership.

### Finding Description
`addSeed` and `removeManySeeds` both start with `await this.#assertWalletIsUnlocked()` before mutating wallet state: [1](#0-0) [2](#0-1) 

`updateSeed`, however, only asserts that `seedId` and `label` are truthy, then unconditionally merges attacker-controlled values into the metadata atom: [3](#0-2) 

There is no `#assertWalletIsUnlocked()` call and no check that `seedId` is the primary seed or one of the caller's extra seeds (contrast with `removeManySeeds`, which validates against `primarySeedId` and the actual `extraSeedsIds`). This function is exported unguarded through the wallet API/RPC surface: [4](#0-3) 

As a result, a caller can invoke `updateSeed({ seedId: <any string>, label: <attacker string> })` while the wallet is locked (`#isLocked === true`) or while targeting a `seedId` that has nothing to do with the caller's own seeds, and the write to `#seedMetadataAtom` (a persisted atom) will succeed silently.

### Impact Explanation
This breaks the "locked means locked" invariant: persisted wallet metadata (`seedMetadataAtom`) can be tampered with while the wallet is locked or without any relation to the requesting origin/account. While `label`/`dateUpdated` are not secret key material, this is an unauthorized, unscoped write to persisted wallet state reachable from the RPC surface without consent or lock enforcement — a metadata-integrity/authorization-bypass issue consistent with "privilege/consent bypass on wallet state mutation."

### Likelihood Explanation
Highly feasible and repeatable: no special preconditions beyond having RPC access to the `wallet.updateSeed` method (already the case for `addSeed`/`removeManySeeds` per the API surface), and no ownership or lock check to defeat. A single call with an arbitrary `seedId`/`label` reproduces the issue every time.

### Recommendation
Add `await this.#assertWalletIsUnlocked()` at the start of `updateSeed`, and validate that `seedId` corresponds to the primary seed or an existing extra seed (mirroring the ownership checks in `removeManySeeds`) before mutating `#seedMetadataAtom`; reject unknown `seedId` values instead of blindly spreading `previous[seedId]`.

### Proof of Concept
Unit test in `features/wallet/module/__tests__/index.test.js` style:
```js
it('throws when updateSeed is called while wallet is locked', async () => {
  const wallet = createWallet(/* ...deps with seedMetadataAtom spy... */)
  // do not call wallet.unlock()
  await expect(wallet.updateSeed({ seedId: 'victim-seed-id', label: 'attacker-label' }))
    .rejects.toThrow('wallet is locked')
  expect(seedMetadataAtom.set).not.toHaveBeenCalled()
})

it('throws when updateSeed targets a seedId not owned by the unlocked session', async () => {
  await wallet.unlock({ passphrase })
  await expect(wallet.updateSeed({ seedId: 'unrelated-seed-id', label: 'x' }))
    .rejects.toThrow(/no seed matches|not found/i)
})
```
Expected (current, vulnerable) behavior: both calls succeed and `seedMetadataAtom.set` is invoked with attacker-chosen data. Expected (fixed) behavior: both calls throw before any mutation occurs.
