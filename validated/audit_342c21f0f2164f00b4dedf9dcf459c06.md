## Analysis

**Equality claimed:** `sum(handleOut UTXO amounts across circomData.erc20TokenAddresses) == net change in every token/asset that Emporium's `stack.ops` touched during `runAction`.`

**Trace:** In `EmporiumUpgradeable.runAction`, the post-call reconciliation loop only iterates `i` over `circomData.erc20TokenAddresses` [1](#0-0) . `handleOut` is only ever invoked for indices in that caller-supplied array [2](#0-1) . If a victim's CASE 2 op is `vault.deposit(amount)` and `circomData.erc20TokenAddresses` lists only the deposit token, the share tokens minted to `address(this)` (Emporium) are never observed, never transferred out, and never turned into a UTXO — they remain resident in the Emporium contract. Nothing in `Hinkal.sol`'s own balance/slippage check constrains this either, since that check also only loops over `circomData.erc20TokenAddresses` of the caller's own transaction [3](#0-2) . So the equality is broken: real net change (share tokens increase) ≠ sum of UTXO amounts (0 for share token).

Regarding the exact sweep mechanism proposed in the question (a later attacker's `transact()` with `erc20TokenAddresses=[shareToken]` "mints a UTXO of exactly that leftover amount" via `handleOut`): this does **not** work as literally stated. `balanceChange` in `runAction` is computed as `balancesAfter[i] - balancesBefore[i]` (a *delta* measured live at the start/end of that specific call, adjusted by that same call's own `deltaAmountChanges[i]`) [4](#0-3) . A pre-existing stranded balance is already included in both `balancesBefore` and `balancesAfter` and cancels out unless the attacker's own ops cause additional net inflow during their own call. Forcing `deltaAmountChanges[i] < 0` (to "claim" the stranded balance as funded-then-returned) would require the attacker to actually own shielded UTXOs of that token, which the in-circuit constraint `inTotal + amountChanges === outTotal` prevents from being forged.

However, the underlying **impact is still real and worse**: CASE 2 ("Stateless Interaction") lets `stack.ops[i]` call *any* `op.endpoint` with *any* `op.callData`, restricted only by blocking the `callHinkalWallet`/`doSendToRelay` selectors [5](#0-4) . Any unprivileged attacker can set `op.endpoint = shareToken` and `op.callData = abi.encodeWithSelector(IERC20.transfer.selector, attackerEOA, strandedAmount)`. Since the low-level call executes with `msg.sender == Emporium`, this transfers the entire stranded (or any other) token balance held by Emporium directly to the attacker's EOA — completely bypassing `handleOut`, the UTXO/balance-delta reconciliation, and `circomData.erc20TokenAddresses` altogether. `onlyAllowedRecipient` only restricts who may call `runAction` (i.e., `Hinkal.sol`) [6](#0-5) ; it does not restrict what `op.endpoint`/`op.callData` an attacker's own `EmporiumStack` may target.

### Title
Value stranded at Emporium due to incomplete `erc20TokenAddresses` accounting is drainable by any attacker via unrestricted CASE 2 calls - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.handleOut`/`runAction` only account for tokens explicitly listed in `circomData.erc20TokenAddresses`, so any token produced by a CASE 2 op but omitted from that list (e.g. vault share tokens from `vault.deposit(amount)`) is left permanently unaccounted and resident on the Emporium contract. Separately, CASE 2 stateless ops impose no restriction on `op.endpoint`/`op.callData` beyond two blocked selectors, so any unprivileged attacker can directly call `token.transfer(attacker, balance)` from Emporium's own context to steal that (or any other) resident balance in one transaction.

### Finding Description
The reconciliation loop in `runAction` (lines 132-151) and `handleOut` (lines 162-184) index exclusively over `circomData.erc20TokenAddresses`. A victim depositing into an ERC-4626-style vault whose `erc20TokenAddresses` lists only the deposit asset causes minted share tokens to sit unaccounted at `address(this)` — no UTXO is minted for them, and neither `Hinkal.sol`'s balance/slippage check nor Emporium's own check ever inspects that token. This breaks the intended invariant that every token balance change caused by `stack.ops` is captured by an equal-and-opposite UTXO. Because CASE 2 places no allowlist on `op.endpoint` (only two wallet-callback selectors are blocked), any subsequent unprivileged attacker can construct an `EmporiumStack` with an op `{ endpoint: shareToken, callData: transfer(attacker, strandedBalance) }`, submit it through `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction`, and directly exfiltrate the stranded balance — independent of whether that token is even listed in their own `erc20TokenAddresses`.

### Impact Explanation
Critical: permanent freezing of victim funds (minted share value is never represented as a UTXO and cannot be recovered by the victim through normal protocol flows) which converts into direct theft, since any subsequent unprivileged attacker can drain the exact stranded amount (or any other balance resident at Emporium) in a single transaction with no special privileges.

### Likelihood Explanation
Requires only: (1) any external action whose op writes value to a token not enumerated in `erc20TokenAddresses` (a plausible integration gap for vault/staking-style deposits, and also possible from simple slippage/dust), and (2) any attacker submitting one `transact()` call with a CASE 2 op targeting the stranded token's `transfer` function. No signature, wallet, or role is required beyond normal unprivileged access to `Hinkal.transact`, and the attack is trivially repeatable against any balance Emporium accumulates from any source.

### Recommendation
Enforce on-chain that all tokens whose balance changes during `stack.ops` execution are captured: e.g., restrict CASE 2 `op.endpoint` calls from directly invoking arbitrary `transfer`/`transferFrom`-style functions on tokens not explicitly declared, or require the circuit/off-chain prover to attest to and the contract to verify an exhaustive token list (e.g., via balance snapshot diffing across a superset of "known-touched" tokens, or disallowing raw ERC20 calls in CASE 2 outside of `Transferer` helper flows). At minimum, add an allowlist for CASE 2 `op.endpoint` targets to prevent direct token-contract calls from Emporium's context to arbitrary recipients.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC4626-like `vault` (deposit token `DAI`, share token `sDAI`), and register `vault` as an op endpoint.
2. Victim calls `Hinkal.transact` with `externalActionId = Emporium`, `erc20TokenAddresses = [DAI]` only, and a CASE 2 op `{endpoint: vault, callData: deposit(amount)}`. Assert `vault.balanceOf(Emporium) == amount` (sDAI held by Emporium) after the call, and assert the returned `UTXO[]` contains no entry with `erc20Address == sDAI` (only a `DAI` UTXO for any leftover, if any).
3. Attacker (unrelated EOA) calls `Hinkal.transact` with `externalActionId = Emporium` and a CASE 2 op `{endpoint: sDAI, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount)}`. Assert this succeeds (no selector/endpoint restriction blocks it) and that `sDAI.balanceOf(attacker) == amount` afterward, while `sDAI.balanceOf(Emporium) == 0`.
4. Assert the equality break explicitly: `net sDAI change caused by victim's ops (== amount) != sum(handleOut UTXO amounts for sDAI in victim's tx) (== 0)`, and show the attacker's follow-up call recovers exactly `amount` with no proof of prior ownership.
