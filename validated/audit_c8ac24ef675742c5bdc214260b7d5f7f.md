### Title
`findMatchingWithdrawal` matches by `assetId` only, so duplicate-token withdrawals in one batch report the wrong leg's status/txHash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a specific withdrawal leg by looking up the bridge's status API response using only the NEAR `assetId` (`nep141:<near_token_id>`), never the per-route `index` carried on `WithdrawalIdentifier`. When a batch contains two or more PoA withdrawals of the *same* token in the same NEAR intent tx, both legs' `watchWithdrawal` polls converge on the same first-matching record from `.find()`, so a failed/refunded leg can be reported `completed` with the successful leg's `txHash`.

### Finding Description
The broken equality is: *the `(status, txHash)` returned for withdrawal identifier `i` must correspond to the `i`-th actual on-chain withdrawal leg the bridge processed for that route*, i.e. `describeWithdrawal(wid_i) == statusOf(leg_i)`. Instead the code establishes only `describeWithdrawal(wid_i) == statusOf(firstLegWithSameAssetId)`.

Trace:
- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns `index` per `bridge.route` (a counter keyed by `bridge.route`, incremented for every withdrawal routed to that bridge), and calls `bridge.createWithdrawalIdentifier({withdrawalParams: w, index: currentIndex, tx: args.intentTx})`.
- `PoaBridge.createWithdrawalIdentifier` (`poa-bridge.ts:295-311`) stores that `index` on the resulting `WithdrawalIdentifier`, but nothing downstream in the PoA path ever reads it again.
- `watchWithdrawal` (`withdrawal-watcher.ts:20-78`) polls `bridge.describeWithdrawal({...args.wid, logger})` and returns whatever `{status, txHash}` comes back for that call.
- `PoaBridge.describeWithdrawal` (`poa-bridge.ts:313-343`) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, and `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)`.
- The code comment directly above `findMatchingWithdrawal` (`poa-bridge.ts:409-417`) admits: *"multiple withdrawals of the same token in a single transaction are not supported"* — but this "unsupported" case is never rejected anywhere (no validation in `validateWithdrawal`, `createWithdrawalIntents`, or `createWithdrawalIdentifiers` blocks duplicate `assetId` entries within a batch).

Exploit flow: an integrator forwards attacker-controlled `withdrawalParams[]` (per the stated attacker model) containing two PoA legs for the same token (e.g., two `nep141:btc.omft.near` withdrawals to different destination addresses/amounts) in one signed intent/tx. Both legs get the same `tx.hash` and same `assetId`, differing only by the SDK-internal per-route `index` (0 and 1), which `describeWithdrawal` ignores. If the bridge status API returns multiple records for that tx/token (one `COMPLETED`, one `FAILED`/refunded), `.find()` returns the same first record for *both* `describeWithdrawal` calls — so the promise for the refunded/failed leg (index 1) also resolves to `{status: "completed", txHash: <leg-0's-hash>}` instead of `failed`.

Existing guards do not catch this: `supports()`/`validateWithdrawal()` validate per-leg address/amount but never check for duplicate `assetId` within a batch; `compareAddresses`/`validateAddress` are irrelevant to this path; the intents contract's own signature/nonce checks only guarantee the *withdraw intent* was authorized, not that off-chain status reporting maps 1:1 to legs. Mixing HOT/PoA/Omni routes in the same batch does not itself cause cross-route confusion, because dispatch to the correct bridge's `describeWithdrawal` is done per-route in `createWithdrawalIdentifiers`; the actual reachable defect is confined to same-route (PoA), same-token duplicates.

### Impact Explanation
An integrator that calls `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` and credits or refunds a user based on the returned `(status, txHash)` per index can be induced to treat a refunded/never-executed PoA leg as `completed`, using the other leg's real destination `txHash` as "proof". This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category: the integrator may pay out for a transfer that never happened on the failed leg, while the genuine completed leg's `txHash` is duplicated across two logical withdrawals. This is repeatable per batch as long as the attacker (or a counterparty whose withdrawal params are forwarded) can construct a batch with duplicate same-token PoA legs.

### Likelihood Explanation
Preconditions: (1) the integrator's flow allows an attacker-influenced batch to contain two-or-more PoA withdrawal legs for the *identical* NEAR token in one tx; (2) the PoA bridge backend must actually return multiple distinct withdrawal records for that token/tx (its behavior for such duplicate legs is not fully controlled by this repo, and the code comment itself notes the POA API doesn't currently support disambiguating this case either); (3) one of the legs must end up in a different terminal state (`FAILED`) than the other (`COMPLETED`) for the misreport to be observable as a double-payout rather than a harmless duplicate report of the same status. Attacker cost is a single valid batch withdrawal call; feasibility depends on integrator behavior (crediting per-index without additional destination-side verification) and on the bridge backend's actual handling of duplicate-token legs, which is outside this repo's control and only partially verifiable from the code alone.

### Recommendation
Disambiguate withdrawal legs beyond `assetId`: either (a) reject/validate at withdrawal-creation time (`createWithdrawalIntents`/`validateWithdrawal` or a new pre-check in `createWithdrawalIdentifiers`) that a batch may not contain more than one PoA leg with the same `assetId`, or (b) once the PoA bridge API supports disambiguation (e.g., by amount/destination), extend `findMatchingWithdrawal` to match on `(assetId, destinationAddress, amount)` and consume matched records so repeated calls don't collide on the same first `.find()` hit.

### Proof of Concept
```ts
// vitest, mocking only poaBridge.httpClient.getWithdrawalStatus (HTTP mock)
it("misreports status when batch has duplicate-token PoA legs", async () => {
  vi.mocked(poaBridge.httpClient.getWithdrawalStatus).mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "leg0-hash", /* ... */ } },
      { status: "FAILED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: null, /* ... */ } },
    ],
  });

  const bridge = new PoaBridge({ envConfig: configsByEnvironment.production, xrplRpcUrls: [] });
  const commonTx = { hash: "near-tx-hash", accountId: "test.near" };
  const assetId = "nep141:btc.omft.near";

  const leg0 = await bridge.describeWithdrawal({
    landingChain: Chains.Bitcoin, index: 0,
    withdrawalParams: { assetId, amount: 100000n, destinationAddress: "addrA", feeInclusive: false },
    tx: commonTx,
  });
  const leg1 = await bridge.describeWithdrawal({
    landingChain: Chains.Bitcoin, index: 1,
    withdrawalParams: { assetId, amount: 200000n, destinationAddress: "addrB", feeInclusive: false },
    tx: commonTx,
  });

  // Broken equality: leg1 should reflect the FAILED record for its own withdrawal,
  // but it incorrectly returns the same COMPLETED/leg0-hash result as leg0.
  expect(leg0).toEqual({ status: "completed", txHash: "leg0-hash" });
  expect(leg1).toEqual({ status: "completed", txHash: "leg0-hash" }); // should be { status: "failed", reason: "FAILED" }
});
```

Note: this PoC demonstrates the code-level defect deterministically (both calls hit `.find()` and return the identical first record). Whether real-world exploitation via an integrator-forwarded batch is actually reachable end-to-end depends on the live PoA bridge API's behavior for duplicate-token legs in one tx, which could not be fully confirmed from this repo alone.
