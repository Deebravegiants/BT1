This confirms the vulnerability. The webhook `Registry.process` only validates `Utils::HmacValidator.validate(request)`, which computes the HMAC over `to_signable_string` — and for `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, and `webhook_id` fields are read straight from unauthenticated headers and are never part of the signed payload [2](#0-1) . `Registry.process` passes `request.shop` directly into `WebhookMetadata` given to the app's handler after only checking the body HMAC [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, and `HmacValidator.validate` only checks that HMAC against the raw body. The `shop`, `topic`, and `webhook_id` values, which are trusted and forwarded to the app's webhook handler as the identity of the originating shop, come from HTTP headers that are completely outside the HMAC's coverage.

### Finding Description
The intended binding is: `hmac == HMAC(api_secret_key, full_request_identity)` where "full request identity" should include which shop the event is claimed to be for. Instead the binding actually enforced is `hmac == HMAC(api_secret_key, raw_body)` only [1](#0-0) , while `shop` is read unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [4](#0-3) .

Because a single app's `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app (an "unprivileged internet user" relative to other tenants of the same app) receives genuine webhooks from Shopify with a valid `hmac-sha256` computed over a body they can fully observe (and, for many topics, largely control, e.g. by editing their own product/order data to shape the JSON body). Since the header carrying `shop-domain` is never part of the signed content, that attacker can take a `(raw_body, valid_hmac)` pair produced for their own shop and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Utils::HmacValidator.validate(request)` will still succeed because it only checks the body [5](#0-4) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: request.shop` (the attacker-controlled header) with `topic`, `webhook_id`, `api_version` also unauthenticated [6](#0-5) .

This is structurally the same class of bug as the reported analog: a value used by downstream logic to identify the tenant/coverage (`shop` here, `amount` in the report) is not included in the cryptographic binding (`HMAC` here, `coverageMap` update in the report), so the "identity" that logic trusts can be overwritten/spoofed independently of the verified data.

### Impact Explanation
This crosses a tenant boundary: a merchant installing the app can make the app process forged webhook events (uninstall notices, order/customer/GDPR events, etc.) attributed to a different shop than the one that actually holds the app's access token/session, since apps commonly key their session/data lookups off `WebhookMetadata#shop`. Depending on the handler logic, this can lead to cross-tenant data corruption, unauthorized data deletion (e.g. spoofed `shop/redact` or `app/uninstalled` for a shop the attacker doesn't own), or state confusion between tenants — matching the "cross-tenant access" Critical impact class.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even trial) installer of the target app so they can observe real `(body, hmac)` pairs for topics whose body content they influence, then replay with a modified `shop-domain` header at the app's webhook endpoint. No knowledge of `api_secret_key` or any other tenant's credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified content (or otherwise cryptographically bind the header-derived shop to the request, e.g. by checking it against the shop from an active session/HMAC-protected mapping) instead of trusting header values that fall outside `to_signable_string`.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`.
2. Trigger a webhook whose body content is attacker-controlled or predictable (e.g. update a product title to a chosen value, causing `products/update`), and capture the resulting `X-Shopify-Hmac-Sha256` header and raw body from Shopify's real webhook delivery.
3. Replay an HTTP POST to the app's webhook endpoint with the same raw body and `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and desired `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC [7](#0-6) .
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [8](#0-7) , causing the app to act on data as if it originated from `victim-shop`, despite never having received a real webhook for that shop.
