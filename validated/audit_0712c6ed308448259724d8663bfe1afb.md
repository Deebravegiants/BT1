## Title
Webhook `shop-domain` header is not covered by the Shopify HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and are never bound to the signature. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then forwards `request.shop` — an unverified header value — to the application's webhook handler as the tenant identity of the event.

### Finding Description
`to_signable_string` in the `Request` class returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to that same body: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it validates the body bytes, not the shop header: [3](#0-2) 

`Registry.process` performs exactly that check and then immediately trusts `request.shop` as the authenticated tenant identity passed to the app's handler: [4](#0-3) 

Because the app's `client_secret`/API secret is shared across all shops that install the app (it is not per-shop), any unprivileged internet user who can install the app on their own store (or otherwise obtain one legitimate `(raw_body, hmac)` pair produced by Shopify for any shop) possesses a body+signature pair that is valid for the shared secret regardless of which shop it was originally addressed to. That user can then replay the same raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it never inspects the shop header, and `Registry.process` will dispatch a `WebhookMetadata` object carrying the attacker-chosen `shop` value as if it were verified.

This breaks the identity binding `shop_header == HMAC-authenticated(shop)`: the shop value acted upon by the handler is not the shop that was cryptographically bound by the signature.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to decide which tenant's data to read or mutate (a standard multi-tenant pattern) can be made to apply an attacker-supplied payload against a victim shop's tenant context, since the `shop` field the handler receives is not authenticated by the HMAC at all. This is a cross-tenant access primitive reachable by any unprivileged actor able to obtain one valid signed webhook body (e.g., by installing the app for free on their own store), without needing the app's `api_secret_key`, an access token, or any privileged position.

### Likelihood Explanation
Likelihood is high for apps that trust `WebhookMetadata.shop` (the gem's own documented output) as the tenant identifier, since:
- No secret material needs to be recovered by the attacker — they only replay a body+signature pair they legitimately received for their own shop.
- The webhook HTTP endpoint is by design internet-reachable and unauthenticated aside from the HMAC.
- Spoofing the `X-Shopify-Shop-Domain` header requires only crafting a raw HTTP request.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or independently verify that `request.shop` corresponds to a shop with an existing, valid session/installation before trusting it in `Registry.process`. At minimum, document that `WebhookMetadata#shop` is not covered by the signature and must be cross-checked by the host app against known installed shops before use.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture one legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`, and `client_secret` is shared across all shops using the app).
2. POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds (it only checks `B` against `H`), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the attacker's payload to be processed under the victim shop's tenant context.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
