### Title
Missing refund of excess native token in fee-swap of `dispatch()`/`fundRequest()` exposes users to sandwich/MEV loss - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()` and `EvmHost.fundRequest()` convert user-supplied native token into `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens`, using the caller's full `msg.value` as the implicit input cap and a fixed `post.fee` / `amount` as the exact output. [1](#0-0) [2](#0-1)  Unlike the analogous swap wiring in `IntentGatewayV2.sol`, which explicitly captures the router's returned `amounts[0]` and refunds the unspent portion of `msgValue` back to `msg.sender`, `EvmHost.dispatch()`/`fundRequest()` discard the return value entirely and never refund any leftover ETH to the original caller. [3](#0-2) 

### Finding Description
`swapETHForExactTokens` on UniswapV2Router refunds any ETH left over (after acquiring the exact `post.fee`/`amount` output) back to the immediate caller — here, that is `EvmHost` itself, since `EvmHost` is the one invoking the router with `{value: msg.value}`. `EvmHost` has no logic afterward to forward that refunded ETH back to `_msgSender()` (the actual end user who paid for `dispatch`/`fundRequest`), and no user-supplied maximum-input parameter exists to bound how much of `msg.value` the swap may legitimately consume; the entire `msg.value` acts as the de-facto (and only) input cap. [1](#0-0) 

This mirrors the reported bug class: the swap's protective bound (there, `amountOutMin`; here, effectively the acceptable `amountIn`) is not derived from an explicit user-chosen slippage parameter but instead is implicit and manipulable — a searcher can sandwich the pool immediately before the `dispatch()`/`fundRequest()` transaction to inflate the ETH price of `feeToken()`, forcing the swap to consume close to the caller's entire `msg.value` to acquire the fixed `post.fee` amount of `feeToken()`. Because there is no refund path back to the caller, any ETH “saved” by the router (the difference between what the user sent and what was truly needed at the fair price) is retained inside `EvmHost` rather than returned, and value that should have gone back to the user is instead extractable by the attacker's sandwich and/or stranded in the contract.

By contrast, the codebase's own reference pattern in `IntentGatewayV2._openOrder` correctly tracks `amounts[0]` (actual ETH spent) and refunds `msgValue - amounts[0]` to `msg.sender`, confirming that the intended, safe design requires capturing and refunding the swap's actual input consumption — a step `EvmHost.dispatch()`/`fundRequest()` omit. [4](#0-3) 

### Impact Explanation
Any user who dispatches a POST request or funds a request by paying with native token (`msg.value`) through `EvmHost.dispatch()`/`fundRequest()` is exposed to MEV sandwich attacks that inflate the effective price of the swap, and — because unused ETH is never returned to them — the user permanently loses the value difference between what they intended to spend and what the manipulated swap actually consumed, with the surplus becoming stuck in `EvmHost` rather than being refunded. This is a direct, no-privilege, single-transaction fund-loss vector reachable by any relayer/app calling the dispatcher.

### Likelihood Explanation
High likelihood: `dispatch()` and `fundRequest()` are core, permissionless, frequently-used entry points for any app/relayer paying with native token, and sandwiching an on-chain UniswapV2 swap with a known fixed output is a standard, low-cost MEV technique requiring no special permissions — only observing pending transactions to the `EvmHost` contract.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in both `dispatch()` and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2._openOrder`. Additionally, consider allowing the caller to supply an explicit `amountInMax` (rather than relying on `msg.value` as an implicit, unbounded cap) so users can protect themselves against unfavorable execution prices instead of merely bounding by however much ETH they happened to send.

### Proof of Concept
1. Attacker monitors the mempool for an `EvmHost.dispatch(post)` (or `fundRequest`) call sent with `msg.value` and a `post.fee` target.
2. Attacker front-runs with a large swap on the same UniswapV2 pool (WETH → feeToken) to move the price, then back-runs to restore it after the victim's transaction, extracting the price difference.
3. The victim's `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes at the manipulated price, consuming far more ETH than the fair-price amount to acquire the fixed `post.fee` amount of `feeToken()`. [5](#0-4) 
4. Any ETH refunded by the router lands in `EvmHost`'s balance, not the victim's; `EvmHost.dispatch()` never forwards it back, so the victim receives no refund regardless of how much ETH was actually needed versus sent, unlike the refund-safe pattern in `IntentGatewayV2`. [4](#0-3)
