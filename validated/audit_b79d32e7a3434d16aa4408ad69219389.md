## Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` values are consumed unauthenticated — the HMAC only covers the raw body, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body [1](#0-0) . However, the tenant-identifying fields the handler actually consumes — `shop`, `topic`, `webhook_id`, `api_version` — are read directly from HTTP headers and are never included in the signed content [2](#0-1) . This breaks the identity binding `verified_bytes (body) == data acted on (shop header)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, to_signable_string)` and compares it against the `shopify-hmac-sha256` header using `OpenSSL.secure_compare` [4](#0-3) . This proves only that the *body bytes* were produced by a holder of `api_secret_key` — it says nothing about the `shop`, `topic`, or `webhook_id` headers, which are parsed independently from the request headers, entirely outside the signature: [5](#0-4) 

`Registry.process` then passes these unauthenticated header values straight to the app's handler as the tenant key: [1](#0-0) 

Crucially, `api_secret_key` is a single app-wide secret, shared across every shop that has installed the app — it is not a per-shop credential. Consequently, any party who can legitimately obtain one valid `(body, hmac)` pair for a webhook topic the app subscribes to (e.g. by having their own shop install the app and receiving one genuine webhook, or by observing/replaying an intercepted webhook) can replay that exact body+HMAC pair while swapping only the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header. The HMAC check still passes (body unchanged, same shared secret), but the handler now executes attacker-chosen webhook data under a victim shop's tenant identity.

### Impact Explanation
Any handler that keys authorization, data mutation, or tenant-scoping decisions off `WebhookMetadata#shop` (an extremely common pattern — e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or any handler that looks up/updates records `WHERE shop = data.shop`) can be tricked into acting on an arbitrary victim shop identifier while the actual payload content belongs to the attacker's own tenant. This is a cross-tenant confusion/spoofing primitive: the HMAC boundary that is supposed to bind "this webhook is authentically from shop X" is not actually enforced for the shop identity, only for the body bytes.

### Likelihood Explanation
Exploitation requires only:
1. The attacker's own shop to install the target app (to legitimately receive one signed webhook and observe its body+HMAC), and
2. The ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint (trivial — any internet-reachable webhook receiver accepts this).

No possession of `api_secret_key`, no access token, and no privileged account are required beyond the attacker's own low-privilege shop install — this satisfies the "unprivileged internet user" threat model.

### Recommendation
Bind the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) into the signed content that `HmacValidator` verifies, or otherwise cryptographically tie them to the body before trusting them (e.g., verify the signature over `headers + body` as Shopify's platform actually does when generating recommendations, or require the receiving app to cross-check `shop` against an independently known/authorized shop list rather than trusting the header verbatim). At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id` are **not** covered by the HMAC and must not be used as a sole tenant-authorization key by consuming applications.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` installs the app; app registers a webhook for topic `app/uninstalled`.
2. Shopify sends a genuine webhook to the app: body `{}`  (or any captured real payload), headers:
   ```
   shopify-topic: app/uninstalled
   shopify-hmac-sha256: <valid HMAC over body using api_secret_key>
   shopify-shop-domain: attacker.myshopify.com
   ```
3. Attacker resends the identical HTTP request to the same webhook endpoint, only replacing the header:
   ```
   shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5)  — this still passes because `to_signable_string` only re-derives from `@raw_body`, which is unchanged.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` [7](#0-6) , and the app's handler executes attacker-controlled logic under the victim's tenant identity.
