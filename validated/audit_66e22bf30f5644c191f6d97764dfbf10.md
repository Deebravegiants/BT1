The `to_signable_string` method for `Webhooks::Request` (used by `Utils::HmacValidator.validate`) is defined as only `@raw_body` [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` fields are all read directly from unauthenticated HTTP headers [2](#0-1) . The HMAC validator only checks that `to_signable_string` matches the signature computed with the app's secret [3](#0-2) , so the `shop-domain` header is never covered by the signature. `Registry.process` trusts `request.shop` as the tenant identity and passes it straight to the app's webhook handler [4](#0-3) .

### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, while `shop`, `topic`, and `webhook_id` are taken from HTTP headers that are excluded from the HMAC computation. `Utils::HmacValidator.validate` verifies solely that the body's HMAC matches the app's secret; it never binds the `shop-domain` header (or `topic`/`webhook_id`) into that signature. Because Shopify's HMAC secret (`client_secret`) is shared across every shop installing the same app, anyone who can legitimately receive one signed webhook for their own shop (e.g., a merchant/partner using the app) can capture the `(raw_body, hmac)` pair from that delivery and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `Registry.process` will accept it as valid (`Utils::HmacValidator.validate(request)` succeeds because only the body is checked) and hand `WebhookMetadata.new(shop: request.shop, ...)` — carrying the attacker-chosen shop — to the host application's webhook handler.

### Finding Description
The identity binding that should hold is: `shop_bound_by_HMAC == shop_acted_on`. In this gem that equality is broken:
- Signature covers: `@raw_body` only [1](#0-0) .
- Value acted on / delivered to the handler: `request.shop`, sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed body [5](#0-4) .
- `HmacValidator.validate` only recomputes the HMAC over `to_signable_string` and compares to the `hmac` header/value; it has no notion of `shop`, `topic`, or `webhook_id` [3](#0-2) .
- `Registry.process` trusts `request.shop` as-is once `Utils::HmacValidator.validate(request)` passes, forwarding it to the app's handler as the tenant identity [4](#0-3) .

Since the app's `client_secret` is shared for all shops that install it (it is not a per-shop secret), a legitimate webhook recipient for their own shop can compute/observe a valid `(body, hmac)` pair and resend that exact same body+hmac with a different `shop-domain` header value. The signature still validates because the header was never part of the signed content.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an app relying on `WebhookMetadata#shop` (populated straight from `request.shop`) to select which merchant's data/record to update, delete, or notify about can be tricked into performing that action against a different, victim shop, using only a replayed (unmodified) webhook body that a merchant legitimately received for their own store. This crosses a tenant boundary using no credentials beyond what any existing app-installing merchant already has, matching the "cross-tenant access" high/critical impact category.

### Likelihood Explanation
Exploitability depends on a payload whose body doesn't already encode the shop (many mandatory/compliance webhook payloads and generic event webhooks carry only IDs, not the shop domain), and the app must key any actions off `WebhookMetadata#shop` rather than independently re-deriving/verifying shop identity. Given many host apps are documented to trust `data.shop` from this exact gem's helper, likelihood is moderate — it requires an attacker who already runs a shop with the app installed (to obtain one legitimately signed webhook) but no further privilege.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable content (or otherwise cryptographically bind them, e.g., by having `to_signable_string` incorporate the normalized headers along with the body), so any header tampering invalidates the signature. Document clearly that `WebhookMetadata#shop` is currently unauthenticated header data and should not be used as a sole tenant selector without a lookup keyed by a separately stored/verified webhook subscription id.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker.myshopify.com`) and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` computed by Shopify over `B` with the app's shared `client_secret`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `to_signable_string` still returns `B` [1](#0-0) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H` — validation passes [6](#0-5) .
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and if the host app acts on `data.shop` (e.g., to select which store's records to modify), it performs that action against the victim shop instead of the attacker's own shop.
