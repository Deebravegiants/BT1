### Title
Single-step `Bonding.transferCreator` can permanently freeze a token's future creator fees to an unreachable address - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.transferCreator` reassigns the fee-attribution `creator` role for a launched token in a single, unilateral step, with only a zero-address check and no acceptance step from the incoming address. If the current creator mistypes or misconfigures `newCreator`, all future creator-fee accruals for that token are permanently redirected to an address nobody can claim from, with no recovery path. This is the same bug class as the OpenZeppelin `Ownable.transferOwnership` single-step report, but the actual privileged/reachable path in this codebase is `Bonding.transferCreator`, not a contract owner.

### Finding Description
`transferCreator` is defined as: [1](#0-0) 

```solidity
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
```

The only validation is `newCreator != address(0)` and `newCreator != info.creator`. There is no acceptance/claim step by `newCreator`, unlike the pattern the project itself uses elsewhere: `FeeVault` explicitly adopts `Ownable2StepUpgradeable` for its owner precisely to avoid this exact bug class, as documented in its own comment: [2](#0-1) 

The `creator` role set by `transferCreator` is the sole key used for future fee attribution: `Zap` forwards fee USDC to `FeeVault` and calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`, where `creator` comes from `Bonding.tokenInfo(token).creator`. [3](#0-2) 

`FeeVault.accrue` credits `creatorBalance[creator]` unconditionally to whatever address is passed, and `claim()` only pays out to `msg.sender`'s own balance: [4](#0-3) 

There is no owner-level override, sweep, or reassignment mechanism for `creatorBalance` — funds accrued to an address are only claimable by that exact address calling `claim()` itself.

### Impact Explanation
If a creator calls `transferCreator` with a `newCreator` address that is fat-fingered, belongs to an exchange/contract that cannot call `claim()`, or whose private key is unknown, then every subsequent buy/sell fee on that token (0.25% of volume, per the fee split documented in `docs/contracts-scope.md`) is credited in `FeeVault.creatorBalance[newCreator]` and becomes **permanently unclaimable** — there is no recovery, no owner override, and no way to redirect `creatorBalance` back. This is a direct, irreversible freezing of creator funds for the life of the token (which can trade indefinitely both pre- and post-graduation, since fees accrue on curve and post-grad trades alike). Because `transferCreator` is reachable by any token's creator with a single unprivileged transaction and has no safety net, this matches the report's core concern (accidental, irrecoverable role transfer) mapped onto alt.fun's actual privileged surface.

### Likelihood Explanation
Likelihood is the same as in the original report: this requires no attacker, only a benign operational mistake (typo, wrong-chain address format, copy-paste error, or transferring to a contract without `claim` support) by a token creator performing a legitimate action. Given `transferCreator` is a normal, expected creator operation (e.g., handing a token off to a new team or DAO), the class of accidental fat-finger error is realistic and the resulting freeze is silent — fees keep accruing to the black-holed address until someone notices `claim()` is not being called by the intended party.

### Recommendation
Convert `transferCreator` into a two-step handoff analogous to `Ownable2Step`: store a `pendingCreator` on `TokenInfo` when the current creator calls `transferCreator`, and only finalize the switch (`info.creator = pendingCreator`) when `pendingCreator` itself calls a new `acceptCreator(tokenAddress)` function. This guarantees the new address is live and can call contracts before fee attribution is redirected to it, eliminating the risk of permanently stranding future creator fees.

### Proof of Concept
1. Creator launches a token via `Bonding.launch`, becoming `tokenInfo[token].creator`.
2. Token trades normally through `Zap.buy`/`Zap.sell`; each trade calls `FeeVault.accrue(token, creator, ...)`, crediting `creatorBalance[creator]`, verifiable via `test_transferCreator` in `packages/contracts/test/Bonding.t.sol` which exercises the same function: [5](#0-4) .
3. Creator calls `bonding.transferCreator(token, newCreator)` with a mistyped/unreachable `newCreator` (passes the `!= address(0)` check but is not a controlled EOA/contract).
4. All subsequent trades on `token` now accrue creator fees to `creatorBalance[newCreator]` in `FeeVault`.
5. Since only `newCreator` itself can call `FeeVault.claim()` to withdraw `creatorBalance[newCreator]`, and no admin/owner function can reassign or sweep `creatorBalance`, those fees are permanently locked in the vault.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
        $.creatorBalance[msg.sender] = 0;
```
