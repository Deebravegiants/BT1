### Title
Panic in `receipt_filter_fn` when a stale `GlobalContractDistribution` receipt cannot be resolved to a current shard after resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The external report describes a `for`-loop that iterates over a shared, ordered resource (`withdrawPriority`) with no failure isolation: a single bad entry causes the entire caller-facing operation to `revert`, freezing an unrelated resource (all user withdrawals) until manual intervention. The closest reachable analog in nearcore is `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` in [1](#0-0) , which drains a shared, ordered, persistent queue (the delayed receipt queue) and, for one specific receipt kind, can hit an unhandled `Err` that is turned into a **panic** via `.unwrap()`, rather than a contained, per-item failure — the runtime's own convention for isolating faults, as elsewhere it uses `?`/`map_err` to keep such failures local (see `Runtime::process_delayed_receipts`, `validate_receipt`, `StorageInconsistentState`).

### Finding Description
`receipt_filter_fn` is called inside the delayed-receipt drain loop that every validator/RPC node executing a chunk runs deterministically: [2](#0-1) 

It computes `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()`. For `GlobalContractDistribution` receipts, `receiver_shard_id` can return `Err(EpochError::ShardingError(...))` when the receipt's `target_shard` predates the current shard layout by more than what `ShardLayout::resolve_to_current_shard` can resolve: [3](#0-2) 

`ShardLayout::resolve_to_current_shard` explicitly documents that only `ShardLayoutV3` (used for dynamic resharding, with the cumulative `shards_split_map`) can walk an arbitrary number of resharding generations; `V0/V1/V2` layouts (the historically used "static resharding" layouts) fall back to a **single-generation** lookup via `get_children_shards_ids`: [4](#0-3) 

So if a `GlobalContractDistribution` receipt (created from a user-submitted `DeployGlobalContract` transaction) is delayed long enough — e.g. under chunk congestion, gas-limit backpressure, or storage-proof-size limiting, both of which are normal admission paths documented in `process_incoming_receipts`/`process_delayed_receipts` — that **two** shard splits occur on a `V0/V1/V2` layout while it sits in the persistent delayed queue, `resolve_to_current_shard` returns `None`, `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics deterministically for every node applying that chunk.

Notably, nearcore's own regression test explicitly documents and defends against exactly this class of bug for the V3 (dynamic resharding) case, confirming the developers are aware the unguarded lookup is dangerous, but the fix/guard is scoped only to V3 layouts: [5](#0-4) [6](#0-5) 

The test comment states in plain terms: *"The fix only works with V3 shard layouts (dynamic resharding). With static resharding, the shard layout doesn't maintain a full split history"* — i.e. the panic path in `receipt_filter_fn` is not proven safe (and by the code's own logic, is not safe) for `V0/V1/V2` layouts undergoing two or more successive resharding events while a `GlobalContractDistribution` receipt is delayed.

This mirrors the reported bug class precisely: a loop draining a shared, ordered structure that all future work depends on (the delayed receipt queue vs. the `withdrawPriority` queue) has no failure containment for one class of item, and an unhandled failure condition (`Err` from `receiver_shard_id`) is not checked before being used, causing the whole operation (chunk application) to fail — except here failure means a `panic!`/process abort across every node applying the chunk, which is a full chain/shard halt rather than a single reverted user transaction.

### Impact Explanation
If triggered, every honest node applying the affected chunk hits the same `.unwrap()` panic deterministically (this is not a malicious-input/consensus-divergence bug — it is a shared-input crash), producing a **chain stall** for the shard: block production for that shard cannot progress until node operators patch the binary or otherwise clear the offending state. This is strictly worse than the reported analog (temporary illiquidity fixable by a manager) because there is no way to "skip" the entry via governance action short of a software patch — the delayed queue is a persistent trie structure that will be re-processed identically on any resynced/patched node until it drains, so all nodes must be patched consistently.

### Likelihood Explanation
Reaching this requires: (1) a `DeployGlobalContract` transaction (permissionless, any account) that produces a `GlobalContractDistribution` receipt targeting a shard; (2) sufficient chunk congestion/gas-limit pressure on the receiving shard to push that receipt into the persistent delayed queue for an extended period (also attacker-achievable by spamming compute-heavy transactions, as demonstrated by the test's `burn_gas_raw` saturation loop); and (3) two resharding events on a `V0/V1/V2` ("static resharding") shard layout occurring while the receipt is delayed. Condition (3) depends on whether static resharding (as opposed to the newer `ShardLayoutV3`/dynamic resharding) is still an active mechanism for triggering shard splits in production (e.g. protocol-version-gated splits), which I was not able to fully confirm from the available index — this is the main source of uncertainty in this finding.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with proper error propagation (return `Result` from `pop`/`receipt_filter_fn` and surface it as a `RuntimeError`/`StorageInconsistentState`, consistent with how the sibling `process_delayed_receipts` handles invalid delayed receipts), and/or extend `resolve_to_current_shard` for `V0/V1/V2` layouts to walk the full historical `get_children_shards_ids` chain (multi-generation) rather than a single generation, so stale `GlobalContractDistribution` receipts can always be resolved regardless of how many resharding generations have elapsed.

### Proof of Concept
1. On a network still using `ShardLayoutV0/V1/V2` (static resharding), submit a `DeployGlobalContract` transaction from an account on shard `S`.
2. Saturate shard `S`'s chunk compute budget every block (e.g. via `burn_gas_raw`-style heavy `FunctionCall` transactions, as done in `test_stale_global_contract_distribution_after_double_resharding`'s saturation loop) so the resulting `GlobalContractDistribution` receipt is pushed into `DelayedReceiptQueue` instead of being executed immediately (`runtime/runtime/src/lib.rs` `process_incoming_receipts` delayed-push path).
3. Trigger/await two successive shard-split (resharding) events on the static layout while the receipt remains delayed.
4. Stop saturating and let the delayed queue drain; `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, which calls `receiver_shard_id(&shard_layout)` → `resolve_to_current_shard` (single-generation fallback for V0/V1/V2) → `None` → `Err(EpochError::ShardingError)` → `.unwrap()` panics, crashing every node applying that chunk for the shard.     pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    /// Resolve any historical shard ID to a current descendant shard ID.
    /// For V3 layouts this uses the complete `shards_split_map`.
    /// For older layouts it falls back to `get_children_shards_ids` (single generation only).
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        match self {
            Self::V0(_) | Self::V1(_) | Self::V2(_) => {
                self.get_children_shards_ids(shard_id).map(|c| c[0])
            }
            Self::V3(v3) => v3.resolve_to_current_shard(shard_id),
        }
    }
