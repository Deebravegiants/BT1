### Title
Unauthenticated HEAD-only staleness check in `#fetchConfig` lets a MITM/compromised remote-config host indefinitely pin a stale, permissive config by echoing the cached `Last-Modified`/`ETag` - ([File: features/remote-config/module/index.ts])

### Summary
`RemoteConfig#fetchConfig` decides whether to fetch fresh config data purely by comparing the `Last-Modified`/`ETag` header of a `HEAD` response against the value already persisted in `remoteConfigAtom`, with no cryptographic integrity check on that header. An attacker who can control or MITM the remote-config endpoint can permanently answer every `HEAD` request with the previously-seen header value, forcing `update()` to always return `{}` and never fetch or apply the real (fixed) config, e.g. one that revokes a compromised auto-approve dapp.

### Finding Description
`update()` reads the last persisted `{ config, lastModified }` from `remoteConfigAtom` and passes `lastModified` into `#fetchConfig` [1](#0-0) . Inside `#fetchConfig`, if a `currentLastModified` is already known, the request method is downgraded from `get` to `head` [2](#0-1) . The response's modification indicator is computed purely from the `Last-Modified` or `ETag` response headers via `getModificationIndicator`, and if it matches the cached value, the function short-circuits and returns `{}` without ever issuing (or trusting the result of) a `GET` [3](#0-2) [4](#0-3) . Back in `update()`, when `#fetchConfig` returns `{}`, `changes` evaluates to falsy and `this.#current` and the persisted atom are left untouched [5](#0-4) .

There is no cryptographic signing/verification of the config payload or its freshness headers, and no fallback mechanism (e.g., forcing a full `GET` every N polling cycles regardless of header match) to bound how long a `HEAD`-only "unmodified" response can be trusted. Because `load()` polls on a fixed interval (`ms('2m')` by default) forever without ever forcing a full re-fetch [6](#0-5) , an attacker positioned on the network path to the remote-config host (or controlling/compromising that host/CDN) can simply keep echoing the same `Last-Modified`/`ETag` value on every `HEAD` request indefinitely. This keeps `remoteConfigAtom` and `#current` pinned to whatever config was last legitimately fetched, even after the real server publishes a tightened config (e.g., disabling a compromised auto-approve dapp entry). No existing guard (integrity check, TTL cap, forced periodic `GET`) breaks this loop.

### Impact Explanation
This maps to a remote-config "authenticity/staleness" invariant break: the wallet's operative security policy (auto-approve allowlists, feature flags, dapp trust lists, etc., whatever `remoteConfigAtom` drives) can be frozen by the attacker at a point in time favorable to them, blocking legitimate remote revocations/tightenings from ever propagating to affected clients as long as the attacker maintains the MITM/compromised-host position. The impact is scoped to configuration staleness/denial of a security fix rather than direct key/signing compromise, but it does allow continued operation under an attacker-preferred, more permissive policy (e.g., a dapp that should have been de-listed from auto-approve keeps being auto-approved).

### Likelihood Explanation
This requires the stated precondition that the attacker controls or can MITM the remote-config HTTP responses (e.g. compromised CDN/DNS/network path) — under that precondition the exploit is fully repeatable and trivial: consistently reply to `HEAD` requests with the last-known `Last-Modified`/`ETag` value. No cryptographic signature exists on the header or payload to prevent this, and no periodic forced `GET`/TTL cap exists to bound staleness.

### Recommendation
Do not trust `Last-Modified`/`ETag` alone as an unmodified signal for security-relevant config. Options: (1) cryptographically sign the remote config payload and verify the signature on every fetch regardless of caching headers, decoupling trust from HTTP caching metadata; (2) periodically force a full `GET` (bypassing the `HEAD` short-circuit) on a bounded schedule (e.g., every N poll cycles or after a max staleness duration) so a stuck `HEAD`-only response cannot pin the config forever; (3) validate returned config content/hash against an expected value obtained through a secondary channel before treating `{}` (unmodified) as authoritative.

### Proof of Concept
Integration test plan:
1. Stand up a fake `fetch` where `HEAD` requests always return headers `{ 'Last-Modified': 'FIXED_VALUE' }` regardless of the "real" server-side config version, and `GET` requests (if ever issued) return an updated config body with a bumped `lastModified`.
2. Seed `remoteConfigAtom` with `{ config: <permissive config with compromised dapp auto-approved>, lastModified: 'FIXED_VALUE' }`.
3. Call `RemoteConfig#update()` repeatedly (simulating multiple `load()` poll cycles).
4. Assert that `remoteConfig.getAll()` never reflects the updated/tightened config and that no `GET` request is ever issued after the first `HEAD`, demonstrating indefinite staleness under attacker-controlled headers — i.e., there is no time/cycle bound (`maxStaleCycles`/TTL) after which a forced `GET` occurs to reconcile with server-published changes.
