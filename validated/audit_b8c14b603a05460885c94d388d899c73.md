### Title
Missing source-chain/proof-height binding check in `HandlerV2.handlePostRequests`/`handleGetResponses` allows unverified request provenance on EVM hosts - ([File: evm/src/core/HandlerV2.sol])

### Summary
The Vela advisory's root cause is that a webhook consumer trusted attacker-supplied payload metadata (which repo/ownership a webhook "belongs to") without cross-checking it against data that was actually verified, letting an attacker relabel ownership. The Hyperbridge analog is in `evm/src/core/HandlerV2.sol`'s `handlePostRequests`/`handleGetResponses`: the handler verifies a Merkle-Mountain-Range membership proof against the state commitment of `request.proof.height.stateMachineId`, but never checks that the delivered request's own `source` field (or, for `GetResponse`, the response's originating chain) actually equals that verified state-machine id. Destination `IApp` contracts (`HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, `HostManager.onAccept`, intents apps, LZ endpoint, etc.) all treat `request.source`/`request.from` as an authenticated field for authorization decisions (`UnauthorizedSource`, governance gating), so any gap between "which chain's commitment root the proof was checked against" and "which chain the request claims to be from" is a provenance-spoofing primitive.

### Finding Description
`HandlerV2.handlePostRequests` (`evm/src/core/HandlerV2.sol:181-210`) does the following per leaf:
- checks `leaf.request.dest.equals(host.host())`
- checks the request hasn't timed out
- verifies the MMR membership proof against `host.stateMachineCommitment(request.proof.height).overlayRoot`

It never checks `leaf.request.source` against `request.proof.height.stateMachineId`. The same omission exists in `handleGetResponses` (lines 217-247), which only checks that the response's *request* commitment is known locally (`meta.sender == address(0)`), not that the response's claimed origin matches the state machine whose root was just verified. [1](#0-0) 

Compare this to the equivalent Substrate/pallet-ismp path, `modules/ismp/core/src/handlers/request.rs`, which treats exactly this binding as a required, explicit, security-critical check: [2](#0-1) 

```rust
let source_chain = req.source_chain();
// in order to allow proxies, the host must configure the given state machine
// as it's proxy and must not have a state machine client for the source chain
let allow_proxy = host.is_allowed_proxy(&msg.proof.height.id.state_id) &&
	check_state_machine_client(source_chain);
// check if the request is allowed to be proxied
if source_chain != msg.proof.height.id.state_id && !allow_proxy {
	Err(Error::RequestProxyProhibited { meta: req.clone().into() })?
}
```

The comment and dedicated `Error::RequestProxyProhibited` make clear the protocol designers consider "the request's claimed `source` differs from the state machine whose commitment the proof was actually verified against" to be a distinct, must-reject condition, separate from and in addition to MMR/membership verification. The EVM `HandlerV2`/`EvmHost` pair has no analogous check or `is_allowed_proxy`/router concept at all — it only relies on the leaf hash (which includes `source`) being present in the proven root, with no explicit assertion that the root's own state-machine identity agrees with the value the destination app will read out of `request.source`.

Every downstream EVM app treats `request.source` as authenticated identity for security decisions, e.g.: [3](#0-2) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
    PostRequest calldata request = incoming.request;
    bytes memory expectedSource = _supportedChains[request.source];
    if (expectedSource.length == 0) revert UnsupportedChain();
    if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();
    ...
```

This design assumes the handler already guaranteed `request.source` is trustworthy solely because the leaf verified against *some* known state-commitment root — but the handler never confirms that root belongs to the state machine named in `request.source` itself. Any connected/whitelisted-but-lower-trust state machine whose own outbound dispatch path can be induced (by a malicious contract/module on that chain, a misconfigured proxy-style host, or a future EVM "router" host) to insert a leaf naming an arbitrary `source` would be delivered to any EVM destination as if it genuinely originated from that spoofed chain, exactly mirroring the Vela bug's "attacker crafts payload fields that downstream logic trusts without validating against the verified channel."

### Impact Explanation
If a `source` value can be set inconsistently with the actually-verified state-machine height (e.g., through a chain acting as a relay/proxy, or a bug in that chain's own dispatch logic), an attacker can:
- Bypass `UnauthorizedSource`/`_supportedChains` checks in `HyperFungibleToken`/`WrappedHyperFungibleToken`, causing unbacked minting or unauthorized ERC20 releases (Impact: unbacked mint / theft of escrowed funds).
- Forge governance-class `PostRequest`s that `HostManager.onAccept` would otherwise gate on Hyperbridge-origin checks, enabling unauthorized host/handler/admin rotation (Impact: unauthorized app action / forged message delivery).
- Spoof intent-settlement messages to `IntentGatewayV2`/`ExtrinsicIntents`, redirecting escrow release (Impact: theft of escrowed funds).

This satisfies the "forged message delivery / unauthorized app action / unbacked mint" acceptance criteria, reached purely from a relayer submitting a crafted `PostRequestMessage`/`GetResponseMessage` to the permissionless `HandlerV2`.

### Likelihood Explanation
Exploitability is gated on whether any state machine currently connected to a given EVM `EvmHost` can have a leaf inserted into its own MMR/state commitment whose `PostRequest.source` differs from that chain's true identity (e.g., via a malicious/careless module on that chain, or a host explicitly configured as a proxy/router). I was not able to fully confirm within the available tool budget whether the current `EvmHost` dispatch path (the Solidity mirror of `pallet_ismp`'s dispatcher) unconditionally hardcodes `source = host.host()` for every outgoing `PostRequest`, which would limit — but not eliminate — the practical blast radius (Substrate side still needed an explicit `is_allowed_proxy` allow-list even though its own dispatcher also sets `source` at insertion time, precisely because such proxy/router configurations exist and are supported). Given that the Substrate implementation treats this as mandatory defense-in-depth worth a dedicated error variant, and the EVM implementation has zero equivalent check or router/proxy allow-list mechanism, this is a structural, code-verifiable gap rather than a purely defense-in-depth nicety, and should be rated as a real finding pending confirmation of any current or planned EVM proxy/router state machine.

### Recommendation
In `HandlerV2.handlePostRequests` and `handleGetResponses`, after resolving `request.proof.height`/`message.proof.height`, add an explicit check binding `leaf.request.source` (and the response's originating request source, for `handleGetResponses`) to `proof.height.stateMachineId`, rejecting the message unless that state machine is on an explicit, governance-controlled proxy allow-list (mirroring `is_allowed_proxy`/`RequestProxyProhibited` in `modules/ismp/core/src/handlers/request.rs`). This closes the parity gap between the Substrate and EVM handler implementations and removes reliance on downstream `IApp` contracts to implicitly assume `request.source` was already validated against the verified state-machine identity.

### Proof of Concept
Conceptual (cannot be fully constructed without confirming a chain whose dispatcher permits caller-controlled `source`):
1. Identify/compromise a state machine `Y` connected to the target `EvmHost` whose own outbound-dispatch stack can be made to insert a `PostRequest` leaf with `source = X` (a different, trusted chain, e.g. the address recorded in `HyperFungibleToken._supportedChains[X]`) into `Y`'s MMR.
2. Wait for/relay the consensus update that stores `Y`'s state commitment on the target `EvmHost`.
3. Submit `HandlerV2.handlePostRequests(host, message)` with `message.proof.height.stateMachineId = Y` and `leaf.request.source = X`; the MMR membership check passes because the leaf genuinely exists in `Y`'s proven root, and no code path checks `request.source == proof.height.stateMachineId`.
4. `EvmHost.dispatchIncoming` delivers to `HyperFungibleToken.onAccept`, which reads `request.source == X`, passes `UnauthorizedSource`, and mints tokens as if genuinely bridged from `X`.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
