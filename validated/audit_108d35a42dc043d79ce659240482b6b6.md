### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook purely by validating the HMAC of the raw request body, then hands the `shop` value taken from an *unsigned* HTTP header straight to the application's webhook handler. Because the shop identity is never part of the signed content, any actor able to replay a validly-signed webhook body can attach a different `shop` header and have it processed as if it belonged to another merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, by contrast, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header and is never mixed into the signable content: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string` (i.e., the raw body): [3](#0-2) 

`Webhooks::Registry.process` gates processing on that HMAC check, but then builds the `WebhookMetadata` object it hands to the app's handler using `request.shop`, which was never covered by the signature: [4](#0-3) 

This breaks the identity binding: `shop-header-value == shop-value-bound-by-hmac` does not hold. The equality that should be enforced — "the shop attributed to a webhook equals the shop the signature actually covers" — is never checked. `hmac` only proves "this body was produced with the app's secret", not "this body belongs to shop X".

### Impact Explanation
Any unprivileged party who can obtain one validly HMAC-signed webhook body (e.g., by installing the app on their own development store and capturing a webhook Shopify legitimately sends them — an ordinary, unprivileged action requiring no secrets) can resend that exact body to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only checks the raw body against the secret, and `Registry.process` will invoke the host application's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Host applications (which are documented to key per-tenant persistence, notifications, or business logic off `WebhookMetadata#shop`) will attribute attacker-controlled webhook content to another merchant's tenant — a cross-tenant data-integrity break. Per the given severity rubric this is a cross-tenant access issue (Critical).

### Likelihood Explanation
Obtaining one legitimately-signed webhook body requires only having the app installed on any shop (including the attacker's own free/dev store) — no access to the `api_secret_key`, no privileged account, and no interception of TLS is needed. Crafting the replay request (same body + same HMAC header, forged shop header) is trivial HTTP manipulation reachable directly from the internet whenever the webhook endpoint is publicly exposed, which is the standard, documented deployment model for this gem's webhook flow.

### Recommendation
Bind the `shop` identity into the value that is actually verified. Practical fixes:
- Extend `VerifiableQuery`/`HmacValidator` for webhooks so `to_signable_string` (or an additional check) incorporates the `shop` header along with the body, or
- Have `Registry.process` independently confirm that the shop asserted in the webhook body/topic-specific metadata (where available) matches the header shop before invoking the handler, and document/require host apps to treat `webhook_id` + registered subscription shop as the source of truth rather than the raw header alone.

### Proof of Concept
1. Install the target app on an attacker-controlled development shop (`attacker.myshopify.com`) and trigger any subscribed webhook topic (e.g. `orders/create`). Capture the raw HTTP request Shopify sends, including the `x-shopify-hmac-sha256` header and body.
2. Resend that exact captured request to the app's public webhook endpoint, but replace `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers, and `Utils::HmacValidator.validate` (in `lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only rehashes `@raw_body`, which is unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` (in `lib/shopify_api/webhooks/registry.rb`) invokes the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host application to process attacker-supplied data under `victim.myshopify.com`'s tenant context.
