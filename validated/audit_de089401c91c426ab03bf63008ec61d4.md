### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the destination host for the `/admin/oauth/access_token` POST request (which carries the app's `client_id`/`client_secret`) directly from the unvalidated `dest` claim of an attacker-supplied session token, unlike every other credential-bearing flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) which all call `Utils::ShopValidator.sanitize!` before using the shop value to build the request host.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `JwtPayload.new(session_token)` [1](#0-0) , then uses `jwt_payload.shop` (the JWT `dest` claim, with `https://` stripped) unsanitized to build the session used to target the HTTP client: [2](#0-1) 

`JwtPayload` only verifies the signature (against `Context.api_secret_key`), expiry/`nbf`/`iat` leeway, and that `aud == Context.api_key` [3](#0-2) . It never validates that `dest`/`iss` is a genuine Shopify domain — `shop` is simply `@dest.gsub("https://", "")` [4](#0-3) .

`HttpClient#initialize` then uses `session.shop` directly as the request host: `@base_uri = "https://#{api_host || session.shop}"` [5](#0-4) , and the POST body containing `client_id`/`client_secret` is sent there [6](#0-5) .

Contrast this with the sibling methods in the same modules, which all call `Utils::ShopValidator.sanitize!(shop)` — which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before constructing the credential-bearing session:
- `ClientCredentials.client_credentials` [7](#0-6) 
- `RefreshToken.refresh_access_token` [8](#0-7) 
- `TokenExchange.migrate_to_expiring_token` (same module, same secret-bearing pattern) [9](#0-8) 

`ShopValidator` itself exists precisely for this purpose [10](#0-9) , but `exchange_token` — the flow explicitly recommended for embedded apps in the docs (`docs/usage/oauth.md`) — never calls it.

The binding this breaks: the host that receives the `client_secret` must equal a host that Shopify actually controls (`host == trusted Shopify domain`). In `exchange_token`, the host instead equals `dest` claim value(from the caller-supplied token), which the app author never proves is Shopify. Session tokens (`session_token`) are typically obtained from the browser/App Bridge context in an embedded app and, depending on host-app wiring, could be attacker-influenced input reaching `exchange_token` directly (the API accepts an arbitrary `session_token: String` with no host-side check that it actually came from Shopify's iframe postMessage channel). Since `JwtPayload` verifies the signature using the app's own `api_secret_key`, an attacker without that secret cannot forge a token; however, this analysis could not conclusively verify a session-token forgery path within this gem alone — the exploitability depends on whether a caller can get an arbitrarily-signed or replayed token with a malicious `dest` value past `JwtPayload`'s signature check into `exchange_token`. Because it depends on an external validity assumption (that any JWT passing signature verification necessarily has a trustworthy `dest`), this is presented as a code-consistency/defense-in-depth gap rather than a proven, self-contained exploit.

### Impact Explanation
If a `dest` value could ever pass `JwtPayload` verification while pointing at a non-Shopify host, the impact would be SSRF carrying the app's `client_id`/`client_secret` to an attacker-controlled server (Critical: client_secret exfiltration). Given the uncertainty about forging a validly-signed token noted above, actual impact is best framed as "missing defense-in-depth" that the surrounding sibling methods (`ClientCredentials`, `RefreshToken`, `migrate_to_expiring_token`) all implement, but `exchange_token` — the primary/recommended flow — omits.

### Likelihood Explanation
Low-to-uncertain: requires a validly HS256-signed JWT (verified against `Context.api_secret_key`) with `aud == api_key` but a `dest` claim pointing to a non-Shopify host, which this analysis could not concretely demonstrate as attacker-obtainable purely from this gem's code.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` to the `dest`-derived shop value in `TokenExchange.exchange_token` before constructing `shop_session`/before it is used as the HTTP client's target host, mirroring `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Not conclusively demonstrable purely within this gem: constructing a JWT with a non-Shopify `dest` that still passes `JwtPayload`'s HS256 signature check requires either possession of `Context.api_secret_key`/`old_api_secret_key` or an as-yet-unidentified way to get such a token accepted by `exchange_token`'s caller. Given the strict scope rule to reject theoretical findings requiring credentials not otherwise reachable, this finding should be treated as a code-consistency/defense-in-depth gap rather than a fully proven Critical/High exploit chain.

module ShopifyAPI
  module Utils
    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
