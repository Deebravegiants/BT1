## Title
Emporium wallet fee payment lets anyone drain an arbitrary token from a `HinkalWallet` because the wallet owner's signature never binds the fee token or recipient - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` lets a `HinkalWallet` (a persistent, stateful wallet holding real ERC20/ETH balances) be operated through EIP-712-signed `EmporiumStack` operations. The wallet owner's signature only commits to `ops`, `maxFee`, `deadline` and `emporiumMessage` [1](#0-0) . It never binds `circomData.feeStructure.feeToken` or `circomData.relay`, which are entirely controlled by whoever submits the `Hinkal.transact()` call. `payRelayFees` uses these unbound fields to pull funds directly out of the wallet via `doSendToRelay` [2](#0-1) , breaking the equality between "what the signer authorized" and "what asset/recipient actually moves."

### Finding Description
The wallet owner's EIP-712 signature is computed as:
```
EMPORIUM_SIGNATURE_TYPEHASH(circomData.emporiumMessage, hash(stack.ops), stack.maxFee, stack.deadline)
``` [1](#0-0) 

The only bound guard against unbounded fee extraction is `require(circomData.feeStructure.flatFee > stack.maxFee)` revert [3](#0-2) , which only caps the *amount*, not the *token* or the *recipient (relay)*.

In `payRelayFees`, when `circomData.erc20TokenAddresses` is empty (or none of its entries match the fee token with a negative delta), `foundToken` stays `false`, and the code unconditionally pays `feeStructure.flatFee` of `feeStructure.feeToken` to `circomData.relay` from the wallet:
```solidity
if (!foundToken && feeStructure.flatFee != 0) {
    require(signerAddress != address(0), "Gas Token in Emporium is not found");
    payRelay(circomData.relay, signerAddress, feeStructure.flatFee, feeStructure.feeToken);
}
``` [4](#0-3) 

`payRelay` then calls `sendToRelayFromWallet`, which invokes `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, erc20TokenAddress)` [5](#0-4) . `HinkalWallet.doSendToRelay` is only gated by `onlyEmporium`, i.e. it trusts whatever token/amount/recipient the Emporium contract passes in [6](#0-5) .

Critically, `circomData` (including `feeStructure.feeToken`, `feeStructure.flatFee`, `relay`, and `erc20TokenAddresses`) is fully controlled by the `Hinkal.transact()` caller and only needs to be internally consistent with the caller's own EdDSA/ZK proof (`getHashedCalldata`/`calldataHash` self-consistency check) [7](#0-6) . When the Emporium action is used with `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to a minimal circuit input `formInputEmporiumMin` that only proves `emporiumMessage`, `timeStamp`, `calldataHash` [8](#0-7)  — meaning the caller needs no real shielded balance or existing UTXO at all, just a self-made keypair and a matching proof. `dimensionsCheck` permits `tokenNumber == 0` with all arrays empty, so `Hinkal.transact()`'s balance-diff loop over `erc20TokenAddresses` never executes [9](#0-8) , and `payRelayFees`'s per-token loop is skipped entirely, guaranteeing `foundToken == false`.

Thus, any unprivileged EOA who obtains a previously-issued, unused `EmporiumStack` signature (`v, r, s`, `signerAddress`, `ops`, `maxFee`, `deadline`, matching `emporiumMessage`) for a wallet — for example by front-running its legitimate submission, or if a keeper/relay leaks it before submission — can construct their *own* `circomData` with `erc20TokenAddresses = []`, `feeStructure.feeToken` set to any valuable token the target wallet holds, `feeStructure.flatFee = stack.maxFee`, and `relay` set to their own address, then call `Hinkal.transact()` with a trivial self-generated zero-balance proof. This drains `stack.maxFee` units of an arbitrary token from the wallet straight to the attacker, without the wallet owner ever having authorized that specific token or recipient.

### Impact Explanation
This is direct, unauthorized theft of shielded/persistent user funds held in a `HinkalWallet`: a wallet op (`doSendToRelay`) moves an asset chosen by an attacker, to a recipient chosen by an attacker, in an amount the signer never bound to a specific token — meeting the "unauthorised asset movement" / theft-of-user-funds criteria for Critical impact.

### Likelihood Explanation
The attack requires only: (1) observing/obtaining one valid, unused `EmporiumStack` signature for the target wallet (plausible under any relay/mempool-based submission flow, since the signature by design is meant to be submitted by a third party), and (2) submitting a trivially-constructible zero-balance Emporium proof, requiring no capital and no privileged role — matching the "unprivileged EOA" analog class.

### Recommendation
Include `feeStructure.feeToken`, `feeStructure.flatFee` semantics tied to a specific token, `circomData.relay`, and `circomData.erc20TokenAddresses`/`amountChanges` in the `EMPORIUM_SIGNATURE_TYPEHASH` that `stack.signerAddress` signs, so the wallet owner explicitly authorizes which asset and recipient can be debited, not just a numeric cap.

### Proof of Concept
1. Wallet owner signs an `EmporiumStack` (`ops`, `maxFee = M`, `deadline`, `emporiumMessage = N`) intending fee to be paid in token `USDC` via a legitimate relay flow — this signature is broadcast/visible before being submitted on-chain.
2. Attacker (no funds required) generates a fresh throwaway EdDSA keypair and constructs a Groth16 proof for the Emporium-min circuit with `erc20TokenAddresses = []`.
3. Attacker builds `circomData` with `externalActionData.externalActionMetadata = abi.encode(stack)` reusing the intercepted `(v,r,s,signerAddress,ops,maxFee,deadline)` and `emporiumMessage = N` (unchanged, so signature check passes), but sets `feeStructure = { feeToken: WETH, flatFee: M, variableRate: 0 }` and `relay = attacker`.
4. Attacker calls `Hinkal.transact()` before the legitimate submission consumes `emporiumMessage = N`.
5. `verifyWallet` succeeds (signature only checks `ops`/`maxFee`/`deadline`/`message`) [10](#0-9) ; `payRelayFees` hits the `!foundToken` branch and calls `doSendToRelay(attacker, M, WETH)` on the victim's wallet, transferring `M` WETH to the attacker [4](#0-3) .

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
