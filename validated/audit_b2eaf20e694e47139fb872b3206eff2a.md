### Title
Webhook `shop-domain` Header Not Bound by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is read separately and never included in the HMAC-covered content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` dispatched to the app's handler, breaking the intended identity binding `HMAC-verified bytes == (body, shop)` down to `HMAC-verified bytes == body only`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`, and `shop` is derived independently from the `shop-domain` header, outside the signed content [2](#0-1) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to construct `WebhookMetadata` passed to the app's registered handler, with no cross-check that the shop matches the tenant the signed body actually originated from: [3](#0-2) .

Because the HMAC secret (`Context.api_secret_key`) is the app's single shared `client_secret` used for **all** shops that install the app — not a per-shop secret — any merchant who installs the app receives legitimately-signed webhook deliveries (body + valid HMAC) addressed to their own shop. That merchant can capture a `(raw_body, hmac)` pair from their own legitimate webhook traffic and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a different shop that also uses the app. `HmacValidator.validate` will still report a valid signature (it only checks the body bytes), and `Registry.process` will dispatch to the handler with the forged `shop` value, since `shop` is asserted from the header but not covered by the equality the HMAC is supposed to enforce: `signed_bytes == (body)` vs. the value actually acted upon, `(body, shop)`.

### Impact Explanation
If an app handler keys any tenant-scoped side effects (updating records, granting entitlements, invalidating state, writing audit logs, etc.) off `WebhookMetadata#shop` without an independent verification that this shop legitimately owns the payload, an unprivileged existing installer of the app can inject attacker-controlled webhook events attributed to another merchant's shop. This is a cross-tenant boundary violation: an unprivileged user (any merchant who installed the app) can make the app process arbitrary signed-looking webhook content under the identity of a different tenant, i.e., `shop_claimed_in_metadata != shop_that_actually_produced_the_signed_bytes`.

### Likelihood Explanation
Exploitation requires only that the attacker be one legitimate (if low-privilege) installer of the target app — no access to `api_secret_key`, access tokens, or the target shop's credentials is needed, and no TLS interception or social engineering is required. Capturing one's own valid webhook deliveries is trivial (they are delivered to the app's public webhook endpoint), and replaying with a modified header is a standard HTTP request.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise verify out-of-band that the `shop-domain` header corresponds to a shop actually registered/known to the app before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should not construct `WebhookMetadata` from an unauthenticated header field once HMAC validation has only proven the body's integrity — the shop identity used downstream must be independently established (e.g., cross-checked against the set of shops for which the app has an active session/webhook subscription).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. The app (using the shared `client_secret`) delivers a legitimate webhook to attacker's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`
   - Body: `{"id": 1, ...}`
3. Attacker captures `(raw_body, hmac)` and resends the request to the app's webhook endpoint, changing only the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this as before; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the (unchanged) HMAC [4](#0-3) .
5. `Registry.process` passes, and the handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)` [5](#0-4)  — the app processes attacker-controlled data under `victim.myshopify.com`'s identity.

Note: Whether this results in a concrete exploitable impact depends on how a given host application's webhook handler uses `WebhookMetadata#shop`; this finding demonstrates the gem-level failure to bind the identity, which is the necessary precondition for the cross-tenant impact.
