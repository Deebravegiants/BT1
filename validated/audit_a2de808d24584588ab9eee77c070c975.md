### Title
`IntentGatewayV2.withdraw` on Tron reverts the entire escrow release when any input token has zero remaining escrow, permanently freezing multi-token order settlement - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.withdraw` (used for both `RedeemEscrow`/fill settlement and `RefundEscrow`/cancellation) checks `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` for every token in the withdrawal request's token list, without first skipping entries where the amount being released is legitimately zero. This mirrors the reported Rio pattern: a value that is a valid "nothing more to do here" outcome (zero) is treated as an unconditional error, reverting the entire settlement transaction instead of completing the parts that are still owed.

### Finding Description
`withdraw()` at [1](#0-0)  iterates `body.tokens` and, for each token, unconditionally reverts with `UnknownOrder` if `_orders[body.commitment][token] == 0`, then transfers `amount` and decrements `_orders[body.commitment][token] -= amount`.

Compare this to the newer/base `IntentsBase._withdraw` implementation which explicitly guards against this exact situation: [2](#0-1)  — it does `if (amount == 0) continue;` before checking `escrowed == 0`, so a token entry with nothing left to release is simply skipped rather than causing a hard failure.

The Tron contract lacks this skip. Any settlement path that legitimately produces a `body.tokens[i].amount == 0` and/or a fully-consumed `_orders[commitment][token] == 0` entry for one of several input tokens in a multi-token order will cause the *entire* `withdraw()` call — covering all other tokens for that order — to revert with `UnknownOrder`. Because `withdraw()` is the single execution path for both `RedeemEscrow` (fill settlement) and `RefundEscrow` (cancellation), this blocks release of every other token's legitimately-owed escrow in the same call, not just the zero-value one.

This is directly analogous to the reported Rio bug: a routine, expected zero condition (no more balance owed for one component) is used as a signal to revert an operation that should otherwise complete for the remaining components.

### Impact Explanation
If reachable, this permanently freezes escrowed user/solver funds for any multi-input-token order whose settlement or cancellation path produces a zero-valued token entry: neither the fill's `RedeemEscrow` delivery nor a `RefundEscrow` cancellation could ever succeed for that order once the offending token entry is included in `body.tokens`, since the transaction always reverts. This is a permanent freezing-of-funds condition (in-scope: token bridger / intent solver / user path), matching High severity criteria (concrete permanent freezing of funds via a route that fails to deliver a settlement message).

### Likelihood Explanation
Likelihood depends on whether the Tron contract's callers (`onAccept` decoding `WithdrawalRequest.tokens`, and any cancel/refund path) can actually construct a `body.tokens` entry with `amount == 0` or a commitment whose escrow for a given token was already fully consumed before this call runs. I was not able to fully verify this within the available context — the surrounding `placeOrder`/cancel logic in the Tron file, and whether this contract supports the same partial-fill or multi-input-token flows as `IntrinsicIntents.sol`, could not be completely traced before this analysis window ended. The base `IntentsBase._withdraw` explicitly guarding `amount == 0` strongly suggests this was a known, previously-hit edge case that was fixed in the base/EVM implementation but not backported to the Tron fork, which increases confidence that the code path is reachable but I could not confirm a concrete triggering order shape with certainty.

### Recommendation
Add the same `if (amount == 0) continue;` guard used in `IntentsBase._withdraw` to the Tron `IntentGatewayV2.withdraw` function before the `_orders[body.commitment][token] == 0` check, so that a token with nothing left to release is skipped instead of aborting the whole settlement. Alternatively, port the Tron contract's escrow-release logic to reuse the shared `IntentsBase`/`IntrinsicIntents` implementation to avoid this kind of divergence between forks.

### Proof of Concept
Not fully constructible from the available index: reproducing this requires confirming (from `placeOrder`/fill/cancel code earlier in `evm/tron/contracts/apps/IntentGatewayV2.sol`, which I could not completely read before the session ended) that a `WithdrawalRequest.tokens` array can contain a zero-amount entry, or that `_orders[commitment][token]` can reach zero for one input token while other input tokens for the same commitment still carry escrow.
