### Title
Emporium CASE 2 stateless ops allow arbitrary `address(this)`-context calls, enabling theft of any non-ERC20 asset (e.g. LP NFTs) held by the Emporium contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 "Stateless Interaction" branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract itself, with `op.endpoint` and `op.callData` fully attacker-controlled and unrestricted (only the wallet-related selectors are blacklisted). Because Emporium can end up holding non-ERC20 assets (e.g. an ERC721 LP-NFT minted to it via a prior user's CASE 2 op, accepted unconditionally by `Transferer.onERC721Received`), any subsequent attacker can craft a `transact` whose CASE 2 op calls `token.transferFrom(emporium, attacker, tokenId)`, which succeeds trivially since `msg.sender == owner` in that call. The ERC20/ETH balance-conservation loop in `runAction` (lines 122-151) never sees this because it only iterates `circomData.erc20TokenAddresses`.

### Finding Description
The claimed broken equality is: `asset_owner_before(NFT) == victim's stealth-address-controlled position` should hold, but after the attack `owner_of(tokenId)_after == attacker` with zero corresponding entry in `deltaAmountChanges`/`utxoSet`.

Code path:
1. A victim's earlier `transact` performs an external action (e.g. adding LP to a Uniswap-V3-like pool) via a CASE 2 op: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:102-113` — `op.endpoint.call{value: op.value}(op.callData)` executes with `msg.sender == address(EmporiumUpgradeable)`. If the pool mints an ERC721 position NFT to `msg.sender`, the NFT is minted to Emporium, and `Transferer.onERC721Received` (`contracts/Transferer.sol:19-26`) unconditionally accepts it with no bookkeeping tying it to the victim.
2. Emporium's balance-conservation logic (`EmporiumUpgradeable.sol:85-151`) only calls `getBalancesForArray(circomData.erc20TokenAddresses)` (`contracts/Transferer.sol:169-176`), which is exclusively ERC20/ETH `balanceOf`. There is no tracking whatsoever of ERC721/ERC1155 holdings.
3. An attacker submits their own `transact` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []` (or unrelated tokens), and an `EmporiumStack` containing a CASE 2 op: `endpoint = nftContract`, `callData = transferFrom(emporium, attacker, victimTokenId)`, `invokeWallet = false`, `stack.signerAddress = address(0)`.
4. `verifyWallet` (`EmporiumUpgradeable.sol:302-316`) only checks/marks `usedMessages[circomData.emporiumMessage]`; when `signerAddress == address(0)` it returns immediately with **no signature check at all**, and there is no restriction on `op.endpoint`/`op.callData` beyond blocking the `callHinkalWallet`/`doSendToRelay` selectors.
5. The call executes as `nftContract.transferFrom(emporium, attacker, tokenId)` with `msg.sender == Emporium` (the actual, unconditional owner), so any `_isApprovedOrOwner` check trivially passes — no approval needed, no revert.
6. The subsequent ERC20 balance loop (lines 132-151) sees `balancesAfter[i] == balancesBefore[i]` for every listed token (since none are NFTs), so `balanceChange == 0` for all `i`, `utxoSet` stays empty, and the transaction completes cleanly with zero footprint in `amountChanges`/UTXO accounting.

None of the existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `rootHashExists`, the slippage/balance-diff `require`s in `Hinkal.transact`) constrain non-ERC20 assets or the target/calldata of CASE 2 ops — they are scoped entirely to the `circomData.erc20TokenAddresses` array.

### Impact Explanation
Direct theft of any non-ERC20/ETH asset owned by the Emporium contract (e.g., an LP position NFT, staking receipt NFT, or any ERC721/ERC1155 a victim's earlier stateless op caused to be held by Emporium) by an unprivileged attacker, with zero cost beyond gas and a trivially satisfiable proof for the minimal "Emporium" circuit input. This is a direct theft of a user's shielded/in-flight position with no compensating entry in the value-conservation accounting, matching the Critical severity bar. It is repeatable against any asset Emporium is later found to hold.

### Likelihood Explanation
Preconditions: some prior victim transaction must have caused Emporium to become the owner of a non-ERC20 asset (a realistic outcome any time a CASE 2 op interacts with a protocol that mints/returns a position token to `msg.sender`, e.g. Uniswap V3 NFT positions, since the call is made with Emporium as `msg.sender`). Given the CASE 2 code path's unrestricted `endpoint.call(callData)`, the token address and tokenId are public on-chain, so the attacker only needs to submit one `transact` crafting `EmporiumStack.ops` accordingly; this requires only standard unprivileged capabilities (crafting `CircomData`, `Dimensions`, and generating a valid proof for their own, potentially empty/zero UTXO set).

### Recommendation
Restrict CASE 2 stateless calls so Emporium can never act as `msg.sender` for calls that could move assets it holds on behalf of others without accounting: e.g., require every stateless `op.endpoint.call` to route through a per-transaction ephemeral proxy/wallet rather than executing directly as `address(this)`, or maintain an explicit on-chain escrow/ownership registry for any non-ERC20 asset Emporium receives (mirroring the ERC20 balance-diff accounting) and disallow `transferFrom`/similar selectors targeting registered assets unless the caller proves ownership via a valid nullifier for that specific asset. At minimum, add allow-listing of `op.endpoint` targets and forbid arbitrary `transferFrom`/`safeTransferFrom`-shaped calldata originating from Emporium's own context in CASE 2.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, `HinkalHelper`/`Hinkal`, and a mock ERC721 (`MockLPNFT`) representing an LP position, with a `mint(address to)` function mimicking a position manager minting to `msg.sender`.
2. Victim `transact` #1: CASE 2 op with `endpoint = MockLPNFT`, `callData = mint(address(this))` semantics such that the NFT is minted to `msg.sender` (i.e., Emporium) with `tokenId = 1`. Assert `MockLPNFT.ownerOf(1) == address(Emporium)`.
3. Record `balancesBefore = getBalancesForArray(erc20TokenAddresses)` for whatever tokens are used, if any.
4. Attacker `transact` #2: `erc20TokenAddresses = []` (or unrelated tokens), CASE 2 op with `endpoint = MockLPNFT`, `callData = transferFrom(address(Emporium), attacker, 1)`, `stack.signerAddress = address(0)`, valid Groth16 proof for the minimal Emporium circuit input.
5. Assert the call does not revert, `MockLPNFT.ownerOf(1) == attacker`, and `balancesBefore == balancesAfter` for every listed ERC20 (i.e., `balanceChange == 0` for all `i` in the loop at `EmporiumUpgradeable.sol:132-151`), demonstrating the theft occurred with zero footprint in the value-conservation equation.
