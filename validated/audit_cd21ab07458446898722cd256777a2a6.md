## Title
Webhook shop identity is taken from an unauthenticated HTTP header while the HMAC only signs the request body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Registry.process` verifies proves nothing about the `shop-domain` header. The tenant identity actually consumed by app code (`request.shop`, forwarded into `WebhookMetadata`) is read straight from that unauthenticated header. This is exactly the "field acted on but not covered by the HMAC" analog: the value verified (raw body) and the value used to bind the event to a tenant (shop header) are different bytes.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `HmacValidator.validate` computes and compares the signature only over `to_signable_string`: [2](#0-1) 

Meanwhile, `Request#shop` — the value that identifies which merchant/tenant the webhook belongs to — is pulled directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the host app's handler: [4](#0-3) [5](#0-4) 

The identity binding this code implicitly assumes is:

```
shop_bytes_verified_by_hmac == shop_bytes_used_to_process_the_event
```

In reality the equality is:

```
shop_bytes_verified_by_hmac == "" (shop is not part of the signable string at all)
shop_bytes_used_to_process_the_event == unauthenticated header value
```

An attacker who legitimately installs the app on their own shop can subscribe a webhook to a callback URL they control (or otherwise capture) and obtain a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair that Shopify signed with the app's real `api_secret_key` for their own tenant. Because the signature never covers the shop header, the attacker can replay that exact body+HMAC to the app's real webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g. a victim's `victim-shop.myshopify.com`). `HmacValidator.validate` still succeeds (body/HMAC are untouched), and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, i.e., a forged webhook event is delivered under another merchant's identity.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select per-tenant state (session lookup, database row scoping, cache keys, triggering side effects like data deletion for GDPR topics, etc.) can be made to process attacker-controlled webhook content while believing it originated from a different, victim shop. This is a cross-tenant identity confusion caused purely by this gem's own webhook verification code, matching the report's bug class of "value acted upon is not the value covered by the authentication mechanism."

### Likelihood Explanation
Any user can install the app on their own store (a normal, unprivileged action), configure a webhook subscription pointing to their own listener to capture a validly-signed `(body, hmac)` pair, and then send an HTTP request directly to the app's public webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or privileged access are required beyond the ability to install the app and send one HTTP request, so likelihood is high for any app relying on `request.shop`/`WebhookMetadata.shop` for tenant scoping.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed payload verification, or independently authenticate the `shop-domain` header against a value derived from data that is covered by the signature (e.g., validate the header against the shop associated with a session/webhook-id lookup instead of trusting it directly). At minimum, document that consumers must not treat `WebhookMetadata#shop` as authenticated and must additionally verify it out-of-band (e.g. against the shop tied to the webhook subscription/topic combination retrieved from Shopify).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and creates a webhook subscription (any topic) pointing to a listener they control.
2. Shopify delivers a request to the attacker's listener with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this is a legitimately signed pair.
3. Attacker sends `POST /webhooks` (the real app's webhook endpoint) with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any topic header value the registry recognizes.
4. `HmacValidator.validate(request)` returns `true` because it only checks `B`/`H` (`lib/shopify_api/webhooks/request.rb` lines 35-38, `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
5. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host application to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
