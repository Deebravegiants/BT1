### Title
Webhook HMAC validation signs only the raw body, letting any app installer spoof `shop-domain`/`topic` and forge webhooks as another merchant - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `Utils::HmacValidator` checks never covers the `shop-domain`, `topic`, or `webhook-id` headers. Any entity that can obtain one genuinely-signed webhook (e.g., a merchant who installs the app on their own store) can replay that exact body+HMAC to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop, and the signature will still validate.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw HTTP body: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers and are never mixed into the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values: [4](#0-3) 

Because the app's webhook secret (`Context.api_secret_key`) is shared across every shop that installs the app, a merchant who installs the app on their own store receives genuine, validly-signed webhook deliveries for that store. Since the signature only binds to the body, that same signed body can be replayed against the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header changed to any other shop. `HmacValidator.validate` will still return `true`, because it only re-derives the HMAC from the (unchanged) body and secret - it never checks that the header-supplied `shop`/`topic`/`webhook_id` match anything cryptographically. This breaks the intended binding: **bytes verified by the HMAC (raw body) ≠ fields acted on by the handler (`shop`, `topic`, `webhook_id`)**.

### Impact Explanation
This lets an unprivileged app-installer forge webhook events that appear to originate from a different merchant's shop (cross-tenant spoofing), or relabel the topic of an event they legitimately received. Any downstream logic that trusts `WebhookMetadata#shop`/`#topic` after `Registry.process` succeeds (which is the gem's documented contract: HMAC-validated ⇒ trustworthy `shop`) will act on forged, cross-tenant data - e.g., writing/altering shop-scoped state, triggering GDPR/redact flows, or other side effects attributed to a shop the attacker doesn't control. This matches "cross-tenant access" (Critical).

### Likelihood Explanation
Any user who can install the app on a store of their own (a completely unprivileged, standard interaction - no access token, `client_secret`, or leaked credential needed) automatically receives real signed webhook traffic they fully control the delivery of, and can replay it with a modified `shop-domain` header. No secret material is required to mount the attack; only the ability to receive and resend an HTTP request.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) as part of `to_signable_string`, or otherwise cryptographically bind them to the payload before computing/verifying the HMAC, so a valid signature can only correspond to one specific `(shop, topic, body)` tuple rather than to the body alone.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app: headers include `X-Shopify-Hmac-Sha256: <validHmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, and some JSON body `B`.
3. Attacker captures this request and resends it to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (keeping body `B` and the same `X-Shopify-Hmac-Sha256` value unchanged).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) using `Context.api_secret_key` and succeeds, because `B` and the secret are unchanged.
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: B, ...)`, causing the app to process forged data as if it came from `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
