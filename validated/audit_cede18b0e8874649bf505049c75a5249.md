Confirmed: `ShopValidator.sanitize!` is never invoked anywhere in the webhook processing path (`registry.rb`, `request.rb`), so no shop-domain sanitization/validation guard exists to catch this divergence.

### Title
`Webhooks::Registry.process` dispatches on `topic`/`shop`/`webhook_id` headers never covered by the HMAC signature - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` only verifies that the raw request body was HMAC-signed with the app secret via `Utils::HmacValidator.validate`, then uses `request.topic`, `request.shop`, and `request.webhook_id` — all read from unsigned HTTP headers — to select the handler and build the `WebhookMetadata` passed to it. Because `Webhooks::Request#to_signable_string` returns only `@raw_body`, an attacker who possesses any single valid `(body, hmac)` pair (e.g. from a webhook Shopify legitimately delivered to their own development shop) can replay that exact body/HMAC to the app's webhook endpoint with forged `x-shopify-topic` and `x-shopify-shop-domain` headers, and the app will treat the forged topic and shop as authenticated.

### Finding Description
The intended binding is: `request.topic == request.shop == request.webhook_id ⊆ signable_string` — i.e., every value the handler acts on should be inside the string HMAC-verified against `Context.api_secret_key`. In the actual code this binding is broken:

- `Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `topic`, `shop`, and `webhook_id` are all read straight from HTTP headers, none of which feed into `to_signable_string`: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the received `hmac` header, so it only proves the body's authenticity, not the headers: [3](#0-2) 
- `Registry.process` raises only if the body-HMAC check fails, then unconditionally trusts `request.topic` to select the handler and `request.shop`/`request.webhook_id` to build `WebhookMetadata` handed to the handler: [4](#0-3) 

Attacker flow: the attacker creates their own development shop, installs the app, and lets Shopify legitimately deliver one webhook to their endpoint, capturing the exact `raw_body` and `x-shopify-hmac-sha256` value Shopify computed with the shared `api_secret_key`. The attacker then sends their own POST directly to the app's public webhook endpoint using that identical body and HMAC value, but substitutes `x-shopify-topic` with a topic of their choosing (any topic registered in `@registry`, including the mandatory privacy topics if the host app routes those through `process`) and `x-shopify-shop-domain` with an arbitrary victim shop domain. `HmacValidator.validate` still returns `true` because the signature only ever covered `raw_body`, which is unchanged. `Registry.process` then dispatches to whatever handler is registered for the forged topic and calls `handler.handle` with `WebhookMetadata#shop` set to the forged victim domain and `WebhookMetadata#webhook_id` set to an attacker-chosen ID. No guard in this gem's webhook code (`ShopValidator.sanitize!` is never invoked in this path) rejects the mismatch between the signed body and the unsigned routing/identity headers.

### Impact Explanation
Any host app whose webhook handlers use `data.shop` or `data.topic` from `WebhookMetadata` to key merchant-specific data (session/token lookup, tenant-scoped writes, GDPR data-request/redact handling, etc.) can be made to act on a forged shop domain and forged topic while the code path believes it passed HMAC verification — i.e., an unauthenticated value (the header-derived shop/topic) is trusted as if it were authenticated. This is repeatable against arbitrary victim shop domains using only a single self-obtained valid body/HMAC pair, giving cross-tenant impact bounded only by what the specific host app's handler does with `data.shop`/`data.topic`.

### Likelihood Explanation
Preconditions are met by any unprivileged attacker under the stated model: create a dev shop, install the app, receive one legitimate webhook (near-zero cost), then send a single forged HTTP POST to the app's public webhook endpoint. No secrets, no privileged access, and no interaction with the victim are required. This is fully repeatable per victim shop and per topic registered in the app's `Registry`.

### Recommendation
Include `topic`, `shop`, and `webhook_id` (and any other header value the handler relies on) inside the HMAC-signed material, or independently verify `shop` against the app's list of installed/known shops (e.g., via `ShopValidator.sanitize!` plus a session/install lookup) before dispatching, and derive `topic` only from a value that is itself authenticated rather than trusting the unsigned header.

### Proof of Concept
```ruby
# test/webhooks/registry_signature_coverage_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistrySignatureCoverageTest < Test::Unit::TestCase
      def setup
        super
        ShopifyAPI::Webhooks::Registry.clear
        @raw_body = "{}"
        @hmac_b64 = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, @raw_body),
        )
      end

      def test_forged_topic_and_shop_survive_hmac_validation
        received_topic = nil
        received_shop = nil

        handler_a = TestHelpers::FakeWebhookHandler.new(->(data) { received_topic = "a-called" })
        handler_b = TestHelpers::FakeWebhookHandler.new(->(data) {
          received_topic = data.topic
          received_shop = data.shop
        })

        ShopifyAPI::Webhooks::Registry.add_registration(topic: "topic/a", path: "path", delivery_method: :http, handler: handler_a)
        ShopifyAPI::Webhooks::Registry.add_registration(topic: "topic/b", path: "path", delivery_method: :http, handler: handler_b)

        # Attacker captures a legitimate (body, hmac) pair for topic/a on their own shop,
        # then replays it unchanged except for forged topic/shop headers.
        forged_headers = {
          "x-shopify-topic" => "topic/b",
          "x-shopify-hmac-sha256" => @hmac_b64, # unchanged: signature only ever covered @raw_body
          "x-shopify-shop-domain" => "victim-shop.myshopify.com",
          "x-shopify-webhook-id" => "attacker-chosen-id",
        }
        forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: forged_headers)

        # Binding under test: request.topic/shop are claimed to be authenticated because
        # HmacValidator.validate(request) == true. Assert this equality does NOT hold:
        assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request)) # signature check passes
        assert_equal(@raw_body, forged_request.to_signable_string)        # signature covers body only
        refute_includes(forged_request.to_signable_string, "topic/b")
        refute_includes(forged_request.to_signable_string, "victim-shop.myshopify.com")

        ShopifyAPI::Webhooks::Registry.process(forged_request)

        # handler_b (selected via the forged, unsigned topic header) fired with the forged shop
        assert_equal("topic/b", received_topic)
        assert_equal("victim-shop.myshopify.com", received_shop)
      end
    end
  end
end
```
This demonstrates that `HmacValidator.validate` returning `true` does not imply that `request.topic` or `request.shop` are authenticated, and that `Registry.process` dispatches and passes these forged values downstream regardless.
