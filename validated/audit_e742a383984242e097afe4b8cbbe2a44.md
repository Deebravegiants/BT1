### Title
`computeTonConnectHash` encodes `domain_len` using UTF-16 code-unit length instead of UTF-8 byte length, causing `computeIntentHash` to diverge from the settlement hash for non-ASCII TON Connect domains - ([File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts])

### Summary
`computeTonConnectHash` writes the 4-byte big-endian `domain_len` field using JavaScript's `domain.length` (UTF-16 code units), while the actual `domain` bytes appended right after are produced with `TextEncoder().encode(domain)` (UTF-8 bytes). For any TON Connect `domain` string containing non-ASCII characters, these two lengths differ, so the byte stream fed into `sha256()` is wrong and the resulting hash diverges from the hash the on-chain `intents.near` contract computes for the same signed payload. This breaks the equality `computeIntentHash(multiPayload) == intent_hash` returned by `publishIntent`/`waitForSettlement`, which `signAndSendIntent`'s `onBeforePublishIntent` hook relies on (`packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts:88-97`).

### Finding Description
The broken equality is:
`computeIntentHash(multiPayload)` (JS-local, byte pre-hash built in `computeTonConnectHash`) `==` `intent_hash` reported by the relay/contract for the *same* signed `ton_connect` multiPayload.

Root cause, `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts:70-71`:
```
numberToBigEndian(domain.length, 4),
new TextEncoder().encode(domain),
```
`domain.length` counts UTF-16 code units of the JS string, not the number of UTF-8 bytes that `TextEncoder().encode(domain)` actually produces. For an ASCII-only domain the two counts coincide, so the bug is silent for typical DNS-style domains. But nothing in this file, in `MultiPayload`'s schema, or in the `ton_connect` signer path constrains `domain` to ASCII — it is a free-form string threaded through from whatever signs the payload (the dApp/integrator-supplied TON Connect domain value), matching the "counterparty whose strings an integrator forwards into the SDK" attacker model. Whenever a non-ASCII multi-byte character appears in `domain` (e.g. an emoji or non-Latin business/domain string embedded by an integrator), `domain.length` (UTF-16 units) is smaller than the actual UTF-8 byte count, so the 4-byte length field written into the pre-image is wrong, and `sha256(message)` in `computeTonConnectHash` (`packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts:50-94`) yields a value that does not match what the same bytes would hash to under a byte-length-correct implementation — i.e. it does not match the hash the contract/relay computes over the equivalent, correctly-length-prefixed bytes.

This is exercised through `signAndSendIntent`: `computeIntentHash(multiPayload)` is computed and handed to `onBeforePublishIntent` *before* `publishIntent` is called (`packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts:85-97`), while the actual settlement hash the integrator later polls for via `waitForSettlement`/`intent_hash` comes from the relay based on the contract's own (byte-length-correct) hashing. All other standards in this codebase (`erc191.ts`, `tip191.ts`, `webauthn.ts`, `sep53.ts`, `raw-ed25519.ts`, `nep413.ts`) consistently derive length fields from `TextEncoder().encode(...).length` (or Borsh string serialization, which is also byte-length based), confirming byte-length is the correct convention and that `ton-connect.ts` is the outlier.

The existing regression test suite (`packages/intents-sdk/src/intents/intent-hash.test.ts`) validates `computeIntentHash` against the real on-chain `simulate_intents` result for every standard, including one non-ASCII case for `erc191` (café), but has no non-ASCII `domain` case for `ton_connect` — so this specific divergence is untested and would not be caught by CI as it stands.

### Impact Explanation
An integrator who persists `intentHash` from `onBeforePublishIntent` and later matches it against the relay-reported `intent_hash` (or polls `waitForIntentSettlement`) for a `ton_connect`-signed withdrawal with a non-ASCII `domain` value will never observe a match: the locally computed hash and the contract/relay's settlement hash differ. This causes the integrator to either treat a successfully settled withdrawal as permanently stuck (requiring manual reconciliation) or to erroneously treat it as a second, still-unconfirmed intent — leading to double-crediting/double-refund risk. This matches the **High** severity category ("a status or hash misreport making an integrator credit or refund twice" / "a withdrawal stuck until manual intervention").

### Likelihood Explanation
Preconditions: the integrator must use `onBeforePublishIntent` (or otherwise call `computeIntentHash` client-side) to track a `ton_connect`-standard signed intent whose `domain` string contains at least one non-ASCII character. This requires no privileged access — any dApp/integrator supplying (or forwarding from an end user's wallet context) a non-ASCII TON Connect domain triggers it deterministically and repeatably on every such call. The likelihood is bounded by how commonly `domain` values are non-ASCII in practice (typical DNS domains are ASCII/punycode), but the SDK does not enforce or normalize this, so any integrator that allows internationalized domain values is exposed every time.

### Recommendation
In `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`, compute `domain_len` from the UTF-8-encoded byte length, not the JS string length:
```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```
reusing the already-encoded `domainBytes` instead of separately calling `domain.length` and `TextEncoder().encode(domain)`. Add a non-ASCII `domain` regression test to `intent-hash.test.ts`/`ton-connect.test.ts` that compares against the on-chain `simulate_intents` result (as already done for the `erc191` café case) to lock in the fix.

### Proof of Concept
Vitest plan (`packages/intents-sdk/src/intents/intent-hashes/ton-connect.test.ts`):
1. Build two `ton_connect` `MultiPayload` fixtures identical except `domain`: one ASCII (`"near.com"`), one with a non-ASCII domain (e.g. `"nëar.com"` or any string containing multi-byte UTF-8 characters), keeping `payload.text`, `address`, `timestamp` fixed.
2. Compute `hashA = computeTonConnectHash(payloadAscii)` and confirm it matches a reference hash computed with a byte-length-correct reference implementation (`domainBytes.length` used for `domain_len`).
3. Compute `hashB = computeTonConnectHash(payloadNonAscii)` and compute `hashBReference` using the byte-length-correct reference implementation over the same bytes.
4. Assert `hashB !== hashBReference` on the current code (demonstrating the divergence), i.e.:
   ```ts
   expect(computeTonConnectHash(payloadNonAscii)).not.toEqual(referenceHash(payloadNonAscii));
   ```
   where `referenceHash` is a small local helper that mirrors `computeTonConnectHash` but uses `TextEncoder().encode(domain).length` for `domain_len`.
5. Optionally, extend the existing `sim()` harness in `intent-hash.test.ts` (which calls `intents.near`'s `simulate_intents` via RPC) with a non-ASCII-domain `ton_connect` case to prove the divergence against the real on-chain hash, exactly mirroring the existing `erc191` café assertion pattern.
