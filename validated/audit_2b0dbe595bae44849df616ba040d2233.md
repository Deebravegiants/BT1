### Title
`EmporiumUpgradeable.verifyWallet` EIP-712 signature omits `relay` recipient and fee token, allowing unauthorized redirection of wallet funds - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The `EmporiumOperation`/`EmporiumSignature` EIP-712 typed data that a `HinkalWallet` owner (`stack.signerAddress`) signs to authorize an Emporium action binds only `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline`. It never binds the `relay` address or the `feeToken` that actually receive the wallet's funds. Whoever assembles the surrounding `CircomData` (a relay/prover, not the wallet owner) freely chooses `circomData.relay` and `circomData.feeStructure.feeToken`, and the wallet's `doSendToRelay` unconditionally sends the fee to that unauthorized recipient in that unauthorized token, up to `maxFee`.

### Finding Description
`verifyWallet` recovers the signer from a hash that covers only `emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline`: [1](#0-0) 

The only monetary bound actually enforced is `flatFee <= maxFee`: [2](#0-1) 

After verification passes, `payRelayFees`/`payRelay` withdraw `relayFee` (bounded by `maxFee` but not tied to a specific recipient) from the signer's own `HinkalWallet` via `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, erc20TokenAddress)`, where `relay` and `erc20TokenAddress` come directly from `circomData`, not from the signed payload: [3](#0-2) 

`HinkalWallet.doSendToRelay` executes the transfer with no further authorization check beyond `onlyEmporium`, moving the wallet's own token balance to whatever `relay` address is supplied: [4](#0-3) [5](#0-4) 

`circomData.relay` and `circomData.feeStructure` (which contains `feeToken`) are supplied by whoever submits the transaction and are only bound to the shielded-note owner's EdDSA proof (via `calldataHash`/`signedMessageHash`), a completely different key from the wallet owner's ECDSA `signerAddress`: [6](#0-5) 

Because these two signers are distinct, the wallet owner's EIP-712 signature is analogous to the liquidator's signature in H-1: it authorizes a value-moving action ("pay up to `maxFee`") without binding the critical parameter that determines *who* receives the funds and *in what token* — just as the liquidation signature omitted nonces binding it to a specific, unchanged state. Anyone holding a previously-issued, still-unused (`emporiumMessage` not yet consumed) wallet signature can wrap it into a `CircomData` submission with `relay` = attacker address and `feeToken` = any token the wallet holds, and legally withdraw up to `maxFee` of that token from the victim's `HinkalWallet` to themselves.

### Impact Explanation
This permits theft of relay/protocol fee funds directly from a user's `HinkalWallet` contract, redirected to an address never approved by the wallet owner's signature, and even in a token the owner never approved for relay payment (since `feeToken` is also unauthenticated). This is unauthorized asset movement a wallet owner never authorized, matching the High-impact criteria ("theft ... of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised").

### Likelihood Explanation
Any actor who can obtain/relay a signed `EmporiumStack` (e.g. an intermediary "relay" service that is supposed to submit the transaction on the user's behalf, or an off-chain component that leaks/reuses the signed payload before submission) can construct the accompanying `CircomData` themselves, since none of the security-relevant recipient fields are part of the signed hash. No special privileges are required beyond being the one who submits the on-chain transaction with a valid proof for the corresponding shielded leg.

### Recommendation
Include `relay` and `feeStructure.feeToken` (and ideally the full `feeStructure`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` payload that `stack.signerAddress` signs, so the wallet owner explicitly authorizes the fee recipient and token, not just an upper bound on the amount.

### Proof of Concept
1. Wallet owner `W` signs an `EmporiumStack` off-chain intending relay `R1` to submit and be paid `maxFee` in token `T1`, expecting `emporiumMessage = m`.
2. Before `R1` submits, a different party (e.g., `R2`, who somehow obtains the signed `(v,r,s,ops,maxFee,deadline)` tuple, for instance from a shared mempool/relay-network gossip) builds `CircomData` with `circomData.relay = R2`, `circomData.feeStructure.feeToken = T2` (any token `W`'s wallet holds), and the required valid EdDSA proof for the shielded leg (obtainable if `R2` also colludes with or is the entity constructing the proof for the transaction, which is standard in the current design since provers assemble `CircomData` themselves).
3. `EmporiumUpgradeable.runAction` → `verifyWallet` recovers `W` successfully because `relay`/`feeToken` are not part of the signed hash; `flatFee <= maxFee` check passes.
4. `payRelayFees` → `sendToRelayFromWallet` → `HinkalWallet(W).doSendToRelay(R2, flatFee, T2)` sends `flatFee` of `T2` from `W`'s wallet to `R2`, even though `W` never named `R2` or `T2`.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }

    function payRelay(
        address relay,
        address signerAddress,
        uint256 relayFee,
        address erc20TokenAddress
    ) internal {
        if (relay == address(0) || relayFee == 0) {
            return;
        }

        if (signerAddress == address(0)) {
            sendToRelay(relay, relayFee, erc20TokenAddress);
        } else {
            sendToRelayFromWallet(
                relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }
    }
