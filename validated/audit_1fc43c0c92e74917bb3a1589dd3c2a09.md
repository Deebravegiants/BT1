### Title
Emporium-min proof path lets attacker insert unconstrained nullifiers/commitments unbacked by any circuit or balance check - (File: contracts/Hinkal.sol, contracts/CircomDataBuilder.sol, circuits/MainEVMCircuitMin.circom)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which builds a public-input vector containing only `emporiumMessage`, `timeStamp`, and `calldataHash` [1](#0-0) . The corresponding circuit, `MainEVMCircuitMin.circom`, only constrains `outTimeStamp`, `calldataHash`, and derives `message` from a private `messageSeed` - it contains no Merkle root, nullifier, or commitment logic whatsoever [2](#0-1) . Meanwhile `Hinkal.transact` calls `insertNullifiers(circomData.inputNullifiers, ...)` and `insertCommitments(circomData.outCommitments, ...)` unconditionally, without gating them by `erc20TokenAddresses.length` [3](#0-2) . Since `inputNullifiers`, `outCommitments`, `rootHashHinkal`, `amountChanges`, and `stealthAddressStructure` are excluded both from the minimal public-input vector and from `calldataHash` (which only covers `publicSignalCount`, `relay`, `emporiumMessage`, `externalActionData`, `slippageValues`, `hookData`, `encryptedOutputs`, `onChainEncryptedOutput`, `feeStructure`, `onChainCreation`, `originalSender`, `extraData`) [4](#0-3) , these fields are entirely free-form attacker-supplied calldata on this path — analogous to the `Ln.sol` bug class where a value is used in a critical computation without being validated against the domain the surrounding proof/equation actually guarantees.

### Finding Description
`Hinkal.transact` performs three checks before mutating state: proof verification against `inputForCircom`, root-hash existence, and (for the internal/external transact branch) a per-token balance-conservation loop over `circomData.erc20TokenAddresses` [5](#0-4) . When the Emporium-min path is taken (`erc20TokenAddresses.length == 0`), that balance-conservation loop trivially does not execute, so no equality is enforced between on-chain balance deltas and `amountChanges`/UTXO amounts. Despite this, `insertNullifiers` and `insertCommitments` are still invoked using `circomData.inputNullifiers` and `circomData.outCommitments`, which are attacker-controlled arrays that were never bound by:
1. The circuit's public signals (`MainEVMCircuitMin` only outputs `message` and takes `outTimeStamp`/`calldataHash` as public) [6](#0-5) .
2. `calldataHash`, since `inputNullifiers`, `outCommitments`, `amountChanges`, `rootHashHinkal`, and `stealthAddressStructure` are omitted from both `getHashedCalldata1` and `getHashedCalldata2` [4](#0-3) .
3. The full `getSignedMessageHash`/`formBasicInput` path, which is only used in `formInputNormal` and is skipped entirely for `formInputEmporiumMin` [7](#0-6) .

This breaks the intended equality that every inserted nullifier/commitment must be derived from a SNARK proof tying it to a real Merkle leaf and a conserved value — the exact class of bug the rules describe as "a nullifier reusable... or a value-bearing leaf left unspendable" / "a (leaf, root) pair the circuit accepts that the tree never produced."

### Impact Explanation
If `dimensionsCheck` (whose full body was only partially inspectable) does not independently tie `inputNullifiers`/`outCommitments` array shape to a value that is itself bound by the proof, an attacker using the Emporium-min path can:
- Insert `outCommitments` for arbitrary amounts with no corresponding deposit or spent UTXO (unbacked shielded value minting), or
- Submit `inputNullifiers` belonging to legitimate, unspent commitments of other users, permanently freezing those users' funds (their real UTXOs become unspendable because the nullifier is now marked used), or
- Replay/pre-empt nullifiers to cause denial of legitimate withdrawals.

Each of these matches the Critical impact bar ("minting shielded value without backing or double spend", "permanent freezing of user funds", "proof or nullifier verification bypass").

### Likelihood Explanation
Reaching this path requires only that the caller set `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses = []`, both of which are ordinary user-supplied calldata fields with no privileged role required — any unprivileged EOA can construct this transaction. The only remaining gate is whatever `dimensionsCheck` enforces on the shape of `inputNullifiers`/`outCommitments`; I was not able to fully inspect the beginning of `HinkalHelper.dimensionsCheck` (only lines 121-240 were retrieved) or the `Dimensions` struct definition, so I cannot confirm with certainty whether an additional length-consistency check independently defeats this specific construction. This is a genuine gap in my verification, not an assumption resolved in the exploit's favor.

### Recommendation
- Ensure every field the contract acts on when mutating tree state (`inputNullifiers`, `outCommitments`, `amountChanges`, `rootHashHinkal`, `stealthAddressStructure`) is included in `calldataHash` (or the equivalent signed/public-input commitment) on *all* code paths, including `formInputEmporiumMin`.
- Alternatively, require `inputNullifiers.length == 0 && outCommitments.length == 0` whenever the Emporium-min circuit is used, and enforce this explicitly in `dimensionsCheck`/`performHinkalChecks` rather than relying on the loop over `erc20TokenAddresses` in `Hinkal.transact`.
- Add an explicit circuit constraint (Merkle root + nullifier + commitment calculators) to any "min" circuit variant that is permitted to trigger nullifier/commitment insertion, mirroring `MainEVMCircuit.circom`.

### Proof of Concept
1. Attacker calls `Hinkal.transact` with:
   - `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `circomData.erc20TokenAddresses = []`, `amountChanges = []`, `slippageValues = []` (satisfying the `formInputEmporiumMin` routing condition) [8](#0-7) 
   - `circomData.inputNullifiers` set to nullifiers of a victim's unspent UTXOs, and/or `circomData.outCommitments` set to self-chosen commitments for arbitrary amounts.
   - A valid Groth16 proof for `MainEVMCircuitMin`, which only requires knowledge of `messageSeed` — no relation to `inputNullifiers`/`outCommitments` is required [6](#0-5) .
2. `performHinkalChecks` verifies `calldataHash` (which never covered `inputNullifiers`/`outCommitments`) and calls `formInputForCircom`, producing the 3-element input vector [9](#0-8) .
3. `verifyProof` succeeds against the minimal circuit; the `erc20TokenAddresses` loop in `Hinkal.transact` does not execute (length 0), so no balance/slippage equality is checked [10](#0-9) .
4. `insertNullifiers(circomData.inputNullifiers, ...)` and `insertCommitments(circomData.outCommitments, ...)` execute using the attacker-chosen, unverified arrays [3](#0-2) .

Note: I could not fully confirm whether `dimensionsCheck`'s unshown initial lines (before line 121) independently block this by tying `inputNullifiers`/`outCommitments` length to `erc20TokenAddresses.length` or to a proof-bound `Dimensions` value — this remains an open verification gap given the tool-call budget.

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }

        CircomData calldata circomData,
        Dimensions calldata dimensions,

            (circomData.originalSender == address(0) &&
                circomData.relay != address(0)) ||

            CircomDataBuilder.getHashedCalldata(circomData) ==

        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
