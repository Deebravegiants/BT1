## Title
Unbounded `need_take_pnl_coin`/`need_take_pnl_pc` accumulators can overflow `u64` and permanently DoS deposit/withdraw/swap/withdrawpnl — (File: `program/src/processor.rs`)

## Summary
Similar to the PoolTogether M-07 finding — where `maxDeposit()` never accounts for already-accrued, unclaimed fees, so the fee recipient's later mint can overflow and revert — Raydium's `Processor::calc_take_pnl` keeps accumulating unclaimed "pnl" fee amounts into `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` (both `u64`) via unchecked `.unwrap()` on `checked_add`, with no upper bound check anywhere in `Deposit`, `Withdraw`, `SwapBaseIn(V2)`, `SwapBaseOut(V2)`, or `WithdrawPnl`. Once these accumulators approach `u64::MAX`, any subsequent call into `calc_take_pnl` — including the one made by `process_withdrawpnl` itself — panics, permanently freezing every instruction that touches the pool.

## Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` derives the "real" tradable/depositable/withdrawable reserves by subtracting the accrued-but-unclaimed pnl fee from the raw vault balances: [1](#0-0) 

This helper is invoked by every state-changing, unprivileged instruction — `process_deposit`, `process_withdraw`, `process_swap_base_in`/`_v2`, `process_swap_base_out`/`_v2` — as well as by the privileged `process_withdrawpnl`: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Each of these calls (except `WithdrawOnly` withdrawals) also calls `Self::calc_take_pnl`, which unconditionally accumulates newly-computed pnl fee into the `u64` state fields using `.unwrap()` with no saturating/ceiling logic: [6](#0-5) 

The only place these counters are ever reset to zero is `process_withdrawpnl`, which itself first calls `calc_take_pnl` again (to compute the latest delta) before doing the transfer: [7](#0-6) 

Exactly like the PT bug — where the limit-computing function (`maxDeposit`) is blind to the pending fee liability, letting deposits accumulate state that later makes the fee-claim mint overflow and revert — here nothing in `process_deposit`/`process_withdraw`/`process_swap_*` checks whether pushing more volume through the pool would cause `need_take_pnl_pc`/`need_take_pnl_coin` to approach `u64::MAX`. Once a swap (or any pnl-accruing operation) causes `checked_add(...).unwrap()` to be called on values that would overflow `u64`, the transaction panics. Because `calc_take_pnl` is on the hot path of literally every economically meaningful instruction (`Deposit`, `Withdraw`, all four swap variants, and `WithdrawPnl`), this single overflow point becomes a total, un-recoverable DoS: even the privileged `pnl_owner` cannot call `WithdrawPnl` to drain and reset the counter, because that instruction re-invokes the same panicking code path first.

## Impact Explanation
Once the accumulators approach `u64::MAX`, all subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`, `SwapBaseInV2`, `SwapBaseOutV2`, and `WithdrawPnl` instructions for that AMM pool will panic and fail. This permanently locks all LP and swapper funds held in the pool's coin/pc vaults, since no instruction path exists to reduce `need_take_pnl_coin`/`need_take_pnl_pc` other than the very code that panics. This is a concrete permanent freezing of user/LP funds, matching the accepted impact classes.

## Likelihood Explanation
Reaching `u64::MAX` (~1.8e19) requires the cumulative pnl fee (in raw token base units, post-decimal-normalization) to grow to that scale. This is most feasible for pools pairing a low-price, high-decimal-count, huge-total-supply token — exactly the class of token cited in the original PT report (e.g., meme-coins with 9-decimal supplies in the trillions) — which are extremely common on Solana. An attacker/arbitrageur can accelerate this by repeatedly trading against the pool to generate price movement (impermanent-gain pnl accrues on every deposit/withdraw/swap call), incrementally pushing `need_take_pnl_pc`/`need_take_pnl_coin` toward the overflow boundary until any ordinary subsequent transaction (their own or another user's) triggers the panic.

## Recommendation
- Use `checked_add` and return an explicit `AmmError` (e.g. `AmmError::CalculationOverflow`) instead of `.unwrap()` in `Processor::calc_take_pnl` when updating `state_data.need_take_pnl_pc`/`need_take_pnl_coin`.
- Add an explicit sanity cap on `need_take_pnl_pc`/`need_take_pnl_coin` relative to vault balances, and/or auto-clamp pnl accrual so it can never push the accumulator past a safe threshold.
- Ensure `WithdrawPnl` can always successfully drain accrued fees even in edge-case states (e.g., by not re-deriving new pnl via `calc_take_pnl` when the existing `need_take_pnl_*` values are already large, or by allowing partial/forced draining independent of the pnl-accrual computation).

## Proof of Concept
1. Deploy/target an AMM pool for a token pair where one side is a high-supply, low-decimal-value token (large raw `u64` amounts relative to real value), matching the token classes cited in the original PT report.
2. Repeatedly submit `SwapBaseIn`/`SwapBaseOut` transactions (attacker-controlled accounts/amounts) that create price movement, causing `Processor::calc_take_pnl` (program/src/processor.rs:167-281) to keep adding to `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` each call (lines 244-254).
3. Continue until the accumulated value is close to `u64::MAX`; the next call to any of `Deposit`, `Withdraw`, `SwapBaseIn(V2)`, `SwapBaseOut(V2)`, or `WithdrawPnl` triggers `checked_add(...).unwrap()` to panic because the addition would overflow `u64`.
4. From this point on, every instruction touching the pool (including `WithdrawPnl`, which itself calls `calc_take_pnl` at processor.rs:1495-1502 before doing any transfer) fails, permanently freezing all coin/pc vault funds and LP positions in the pool.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
