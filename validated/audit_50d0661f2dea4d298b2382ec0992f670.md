## Finding: Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing on webhook replay

### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are trusted without being covered by the HMAC signature, enabling cross-tenant shop spoofing via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` value taken from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header to build the `WebhookMetadata` passed to the app's handler. The header is never included in the signed material, so an attacker who possesses one valid `(raw_body, hmac)` pair can replay it with an arbitrary `shop` header value and have it accepted as an authentic webhook for a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers and are not part of the signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the body only) and compares it against the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` gates entirely on that HMAC check, then builds `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identifier handed to the app-supplied `handler.handle`: [4](#0-3) 

This breaks the intended identity binding:
`shop attributed to webhook payload` == `shop that actually generated/authenticated the payload`

Because only the raw body is HMAC-covered, the equality does not hold: the `shop` (and `topic`/`webhook_id`) header can be swapped freely for any HMAC-valid body without invalidating the signature check.

### Impact Explanation
An unprivileged internet user can install the app on their own (attacker-controlled) shop — a normal, unprivileged action for any public Shopify app — and thereby obtain a genuine `(raw_body, hmac)` pair for a webhook event on their own store (e.g. `orders/create`, `customers/data_request`). By resending that exact body/HMAC pair directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain, the attacker causes the gem to construct `WebhookMetadata` claiming the event belongs to the victim shop, even though `HmacValidator.validate` still returns `true` (it never looked at the shop header). Any app logic keyed on `WebhookMetadata#shop` (e.g., writing/updating shop-scoped records, triggering GDPR redaction against the wrong tenant, or other shop-scoped side effects) is misattributed to a shop the attacker does not own — a cross-tenant confusion enabled purely by this gem's `Registry.process`/`HmacValidator` design.

### Likelihood Explanation
Likelihood is high for any app that relies on `ShopifyAPI::Webhooks::Registry.process` and trusts `WebhookMetadata#shop` for authorization/tenant-scoping decisions (a documented, expected usage pattern of this gem). No secret material is required — only a single legitimately-signed webhook body from the attacker's own shop and the ability to POST to the app's public webhook endpoint with custom headers.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed/verified material (or otherwise cryptographically bind them to the body, e.g. by additionally validating shop/topic against Shopify-supplied signed data), so the shop attributed to a webhook cannot be altered without invalidating the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal unprivileged action for a public app).
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid over `B` with the app's real secret), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker crafts a new POST to the same endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` (lines 12-31) recomputes the HMAC over `B` only and it matches `H`, so validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though the actual authenticated originator was `attacker.myshopify.com`.
