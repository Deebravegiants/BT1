### Title
Webhook `shop-domain` Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from unauthenticated HTTP headers and are never part of the signed material. `Registry.process` trusts these header-derived values once the body-only HMAC check passes, allowing an attacker who owns any shop that has installed the app to replay a legitimately-signed webhook body against a different shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (none of which were part of the signed bytes) to build `WebhookMetadata` and dispatch to the topic handler: [4](#0-3) 

The identity binding that should hold is:
`hmac_signed_bytes == (shop, topic, webhook_id, body)` for the data that the handler acts on.

In this implementation, the actual binding is:
`hmac_signed_bytes == body only`, while `shop == attacker_supplied_header`.

Because the webhook signing secret (`Context.api_secret_key`, the app's client secret) is identical for every shop that installs the app, any merchant/attacker who installs the app on their own store can trigger a legitimate webhook for a topic they control (e.g., `products/create`, `orders/create`, or any topic the app subscribes to) and capture a valid `(body, x-shopify-hmac-sha256)` pair signed with the app's secret. That pair remains valid forever for that exact body, regardless of which shop it is replayed against, because the shop domain is never part of the signed content.

The attacker then re-sends that exact body and HMAC to the app's public webhook endpoint but swaps `x-shopify-shop-domain` (or `shopify-shop-domain`) to the victim shop. `Registry.process` re-validates the HMAC (which still matches, since only the body is checked), and dispatches the handler with `shop: request.shop` set to the victim's domain, `WebhookMetadata` construction shown above.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide: verifying "this request body genuinely originated from Shopify for *this* topic and *this* shop" collapses into "this body was signed with the app's secret for *some* shop, at some point." Depending on the app's webhook handlers, this enables cross-tenant data corruption/attribution — e.g., an attacker-controlled payload (product/order/customer data from the attacker's own store) being processed and persisted as if it belonged to the victim shop, or state-changing topics (like uninstall/redact-style handlers) being fired against a victim shop the attacker doesn't control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to control at least one shop with the target app installed (a low bar — most Shopify apps are installable on free development/partner stores) and knowledge of the app's public webhook endpoint (also typically discoverable/public). No access token, `api_secret_key`, or privileged credentials of the app itself are required — only a shop the attacker legitimately controls.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or independently authenticate/authorize the `shop` value (e.g., validate it against a known/registered shop list, or bind the HMAC to a per-shop secret/session) before using it to route or persist webhook data in `Registry.process` and `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g., `products/create`), capturing the raw POST body `B` and its `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's shared `client_secret`).
2. Attacker sends a POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds.
4. The handler for that topic is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process/attribute attacker-controlled data as belonging to the victim shop.
