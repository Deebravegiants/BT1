### Title
Front-runnable, unprivileged external DEX pool seeding corrupts bonding-curve graduation liquidity split - ([File: aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move])

### Summary
The external report shows that a Uniswap-style AMM can be permanently griefed when an attacker permissionlessly pre-creates/pre-funds a liquidity pair at a deterministic address before the protocol tries to seed it, corrupting the reserve-ratio math the protocol relies on. The Aptos-native analog exists in `bonding_curve_launchpad`'s `graduate()` flow: it hands off the bonding-curve's accumulated APT/FA reserves to the permissionless `swap` DEX (`aptos-move/move-examples/swap`), whose pool-creation and liquidity-minting functions read *live, donation-manipulable* store balances rather than any protected internal accounting.

### Finding Description
`liquidity_pairs::graduate()` [1](#0-0)  transitions a bonding-curve token to a public DEX pool by:
1. Calling `router::create_pool_coin<AptosCoin>(fa_object_metadata, false)`, which is a permissionless `public entry fun` that simply calls `liquidity_pool::create` [2](#0-1) .
2. Calling `add_liquidity_coin_entry_transfer_ref`, which computes `optimal_amount_1`/`optimal_amount_2` via `router::optimal_liquidity_amounts` and withdraws those exact amounts from the bonding curve's own APT `CoinStore` and `fa_store` using `TransferRef` [3](#0-2) .
3. Unconditionally burning whatever LP tokens result from this deposit by sending them to `@0xdead` [4](#0-3) .

Because `liquidity_pool::create` and `liquidity_pool::mint` are both callable directly and permissionlessly by anyone through `swap::router` before `graduate()` ever runs, an attacker can:
- Pre-create the exact APT-wrapper/FA pool for the token that is about to graduate (the FA metadata object address is deterministic and publicly computable via `bonding_curve_launchpad::get_fa_obj_address`).
- Seed it with a skewed token ratio using `liquidity_pool::mint`, which computes minted LP tokens purely from **live balances** of `token_store_1`/`token_store_2` (`fungible_asset::balance(store_1)`, `fungible_asset::balance(store_2)`) [5](#0-4)  — not any value the bonding-curve module controls or validates.

When `graduate()` subsequently calls `add_liquidity_coin_entry_transfer_ref`, the "optimal" split of the bonding curve's real APT/FA holdings is computed against this attacker-controlled, already-skewed reserve ratio, and the resulting LP-token mint amount (`math64::min(token_1_liquidity, token_2_liquidity)`) is determined by the smaller, ratio-mismatched side [6](#0-5) . Since the LP tokens minted from the bonding-curve's deposit are then burned to `@0xdead` regardless of amount, the effective ownership of the pool's *total* reserves (attacker's pre-seeded deposit + bonding-curve's forced deposit at the wrong ratio) is permanently fixed at the moment of graduation with no recovery mechanism — the attacker's earlier LP position captures a disproportionate share of the combined pool that now also contains the launchpad's real APT/FA, while the launchpad's own contribution's excess (the non-optimal side) remains uncredited/mis-valued in the pool.

The custody invariant broken: the bonding-curve module's `graduate()` assumes the DEX pool it is about to interact with is either freshly created by itself or otherwise has a reserve ratio matching its own internal bonding-curve state. Because pool creation and liquidity provisioning on `swap::liquidity_pool` are fully permissionless and rely solely on live balances rather than any oracle/commitment tied to the bonding curve, an unprivileged actor can corrupt this assumed state before `graduate()` executes.

### Impact Explanation
This allows an unprivileged attacker to permanently misappropriate a portion of the real APT and FA value that the bonding-curve module custodies on behalf of all of its token holders at the moment of graduation, since:
- The LP tokens representing ownership of the newly combined pool are burned irrecoverably to `@0xdead` right after minting, so there is no path to correct a mis-priced deposit after the fact.
- The bonding curve's contributed assets (up to 90% of its real APT/FA reserves) are deposited into a pool whose price the attacker controls at deposit time, effectively enabling value extraction analogous to the classic ERC-4626/Uniswap "donate-then-deposit" share-dilution attack, but with permanent custody consequences here due to the LP burn.

This meets the custody-grade bar: it is a supply/custody accounting corruption that moves real APT/FA value to the wrong holder (the pre-seeding attacker) at the exact point the launchpad transfers custody of the bonding-curve reserves to the external pool, with no admin/governance assumption required and no recovery rights (burned LP).

### Likelihood Explanation
High likelihood: `router::create_pool_coin` and `liquidity_pool::mint` are `public`/`public entry` functions callable by anyone, and the FA's metadata address (hence the pool's expected pairing) is deterministically computable ahead of time via `get_fa_obj_address`. Any observer monitoring bonding-curve tokens approaching the `APT_LIQUIDITY_THRESHOLD` [7](#0-6)  can pre-create and pre-fund the pool in a prior transaction/block with no special privileges or capital lock-up risk beyond the tokens they choose to seed.

### Recommendation
- In `graduate()`, verify (and abort if not true) that the target `swap::liquidity_pool` for the FA/AptosCoin-wrapper pair does not already exist before calling `router::create_pool_coin`, or alternatively have `bonding_curve_launchpad` create/own the pool object itself using a reserved/derived address that only it can seed.
- If the pool must be allowed to pre-exist, compute the deposit split using a price/ratio sourced from the bonding curve's own internal, tamper-proof state (`fa_reserves`/`apt_reserves`) rather than trusting `router::optimal_liquidity_amounts`'s live-balance-derived ratio, and enforce slippage/min-amount checks reflecting the bonding curve's expected price.
- Avoid unconditionally burning the resulting LP tokens without validating that the deposit ratio actually matched the intended price; consider retaining/attributing LP tokens to the protocol or token holders rather than an irrecoverable burn.

### Proof of Concept
1. Attacker observes a bonding-curve FA (`name`, `symbol`) nearing `APT_LIQUIDITY_THRESHOLD` in `liquidity_pairs::swap_apt_to_fa`.
2. Attacker calls `router::create_pool_coin<AptosCoin>(fa_metadata, false)` to create the `AptosCoinWrapper/FA` pool ahead of graduation (permissionless, no dependency on the launchpad).
3. Attacker calls `liquidity_pool::mint` (via router's add-liquidity entry) depositing a small, deliberately skewed ratio of wrapped-APT to FA (e.g., far more FA than APT relative to the bonding curve's true internal price), receiving LP tokens for a minimal contribution priced favorably to themselves.
4. A subsequent normal user swap crosses the graduation threshold in `swap_apt_to_fa`, invoking `graduate()`.
5. `add_liquidity_coin_entry_transfer_ref` computes `optimal_amount_1/2` against the attacker-skewed pool ratio and withdraws the bonding curve's real APT/FA accordingly; the resulting LP mint (`math64::min(...)`) undervalues the bonding curve's deposit relative to its true worth, and those LP tokens are burned to `@0xdead`.
6. Attacker holds LP tokens representing a disproportionately large claim on the combined pool (which now contains the launchpad's genuine reserves) and can redeem them for more value than they originally contributed, at the expense of the bonding-curve token holders' collectively custodied reserves.

Note: I was not able to fully verify the exact signature/permission level of `router::add_liquidity_coin` and `router::optimal_liquidity_amounts` (only partial `grep` results were available before tool budget ran out), so the precise parameter validation inside those functions should be re-confirmed by a follow-up session with full file access before treating this as fully proven end-to-end; the core permissionless-pool-creation/funding root cause in `liquidity_pool.move`/`router.move` and the burn-to-dead-address design in `liquidity_pairs.move::graduate` are, however, directly confirmed from the code shown above.

        liquidity_pair: &mut LiquidityPair,

    fun add_liquidity_coin_entry_transfer_ref<CoinType>(
        transfer_ref: &TransferRef,
        lp: &signer,
        fa_store: Object<FungibleStore>,
        token_2: Object<Metadata>,
        is_stable: bool,
        amount_1_desired: u64,
        amount_2_desired: u64,
        amount_1_min: u64,
        amount_2_min: u64,
    ) {
        // Wrap APT into a FA. Then, determine the optimal amounts for providing liquidity to the given FA - APT pair.
        let token_1 = coin_wrapper::get_wrapper<CoinType>();
        let (optimal_amount_1, optimal_amount_2, _) = router::optimal_liquidity_amounts(
            token_1,
            token_2,
            is_stable,
            amount_1_desired,
            amount_2_desired,
            amount_1_min,
            amount_2_min,
        );
        // Retrieve the APT and FA from the liquidity provider.
        // `transfer_ref` is used to avoid circular dependency during graduation. A normal transfer would require
        // visiting `bonding_curve_launchpad` to execute the custom withdraw logic. `transfer_ref` bypasses the need to
        // return to `bonding_curve_launchpad` by not executing the custom withdraw logic.
        let optimal_1 = coin::withdraw<CoinType>(lp, optimal_amount_1);
        let optimal_2 = fungible_asset::withdraw_with_ref(
            transfer_ref,
            fa_store,
            optimal_amount_2
        );
        // Place the APT and FA into the liquidity pair.
        router::add_liquidity_coin<CoinType>(lp, optimal_1, optimal_2, is_stable);
    }

    /// Mint LP tokens for the given liquidity. Note that the LP would receive a smaller amount of LP tokens if the
    /// amounts of liquidity provided are not optimal (do not conform with the constant formula of the pool). Users
    /// should compute the optimal amounts before calling this function.
    public fun mint(
        lp: &signer,
        fungible_asset_1: FungibleAsset,
        fungible_asset_2: FungibleAsset,
        is_stable: bool,
    ) acquires FeesAccounting, LiquidityPool {
        let token_1 = fungible_asset::asset_metadata(&fungible_asset_1);
        let token_2 = fungible_asset::asset_metadata(&fungible_asset_2);
        if (!is_sorted(token_1, token_2)) {
            return mint(lp, fungible_asset_2, fungible_asset_1, is_stable)
        };
        // The LP store needs to exist before we can mint LP tokens.
        let pool = liquidity_pool(token_1, token_2, is_stable);
        let lp_store = ensure_lp_token_store(signer::address_of(lp), pool);
        let amount_1 = fungible_asset::amount(&fungible_asset_1);
        let amount_2 = fungible_asset::amount(&fungible_asset_2);
        assert!(amount_1 > 0 && amount_2 > 0, EZERO_AMOUNT);
        let pool_data = liquidity_pool_data(&pool);
        let store_1 = pool_data.token_store_1;
        let store_2 = pool_data.token_store_2;

        // Before depositing the added liquidity, compute the amount of LP tokens the LP will receive.
        let reserve_1 = fungible_asset::balance(store_1);
        let reserve_2 = fungible_asset::balance(store_2);
        let lp_token_supply = option::destroy_some(fungible_asset::supply(pool));
        let mint_ref = &pool_data.lp_token_refs.mint_ref;
        let liquidity_token_amount = if (lp_token_supply == 0) {
            let total_liquidity = (math128::sqrt((amount_1 as u128) * (amount_2 as u128)) as u64);
            // Permanently lock the first MINIMUM_LIQUIDITY tokens.
            fungible_asset::mint_to(mint_ref, pool, MINIMUM_LIQUIDITY);
            total_liquidity - MINIMUM_LIQUIDITY
        } else {
            // Only the smaller amount between the token 1 or token 2 is considered. Users should make sure to either
            // use the router module or calculate the optimal amounts to provide before calling this function.
            let token_1_liquidity = math64::mul_div(amount_1, (lp_token_supply as u64), reserve_1);
            let token_2_liquidity = math64::mul_div(amount_2, (lp_token_supply as u64), reserve_2);
            math64::min(token_1_liquidity, token_2_liquidity)
        };
        assert!(liquidity_token_amount > 0, EINSUFFICIENT_LIQUIDITY_MINTED);
