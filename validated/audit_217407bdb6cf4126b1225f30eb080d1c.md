## Finding

### Title
POA Bridge withdrawal status matches by `assetId` only, causing multiple same-token withdrawals in one batch to report identical status/txHash - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
When a caller submits a batch of withdrawals that includes **two or more withdrawals of the same token** (same `assetId`) in a single intent transaction, the PoA bridge's withdrawal-status lookup does not disambiguate between them. `findMatchingWithdrawal` selects the *first* API-returned withdrawal whose `near_token_id` matches the requested `assetId`, ignoring the withdrawal's `index`. As a result, `describeWithdrawal()` for withdrawal index 0 and index 1 (both same token) can resolve to the exact same destination `txHash` and `"completed"` status, even though only one of the two withdrawals actually settled.

### Finding Description
`createWithdrawalIdentifiers` assigns a per-bridge-route `index` to each withdrawal in a batch: [1](#0-0) 

For the PoA bridge, `createWithdrawalIdentifier` builds a `WithdrawalIdentifier` carrying that `index`, but `describeWithdrawal` never uses it to select the correct entry from the PoA API response — it looks up the match purely by `assetId`: [2](#0-1) 

`findMatchingWithdrawal` explicitly documents (and accepts) this limitation: [3](#0-2) 

The same pattern (and same caveat) exists in the sibling implementation used for POA deposits/withdrawals in `internal-utils`: [4](#0-3) 

The equality that should hold is: *the withdrawal-status report for identifier `(tx, index, assetId)` reflects the on-chain outcome of that specific withdrawal.* Because the match key omits `index`, when two withdrawals in the same NEAR transaction share an `assetId` (e.g., two BTC withdrawals to different destination addresses/amounts in one `processWithdrawal` batch call, which the SDK explicitly advertises as supported — "Batch Processing: Process multiple withdrawals at a time"), both `watchWithdrawal` polls converge on the *same* API entry (`.find()` returns the first match for both indexes). If withdrawal #0 completes and #1 is still pending (or vice versa), both are reported as `"completed"` with the identical destination `txHash`.

### Impact Explanation
This directly matches the "status or hash misreport making an integrator credit or refund twice" High-severity category: an integrator relying on `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` for a batch containing duplicate-token withdrawals would receive two "completed" confirmations pointing at the same destination transaction hash. Depending on integrator bookkeeping, this can cause double-crediting internal ledgers (treating both withdrawal legs as fulfilled based on one real on-chain transfer) or mask the fact that the second withdrawal never actually landed, leaving user funds effectively stuck without any error being surfaced (since `describeWithdrawal` reports `"completed"`, not `"pending"`/`"failed"`).

### Likelihood Explanation
This does not require any malicious actor — it triggers under ordinary use of the documented batch-withdrawal feature whenever a batch includes ≥2 withdrawals of the same `assetId` via the PoA route (e.g., a user withdrawing BTC to two different addresses in one call, or a solver batching multiple client withdrawals of the same token). The code's own comments confirm the maintainers are aware only single-token-per-batch is truly safe, but nothing in `supports()`/`validateWithdrawal()` prevents or warns against constructing such a batch through the public `IntentsSDK` API.

### Recommendation
- Reject (or explicitly document/guard against) batches containing multiple withdrawals with the same `assetId` routed through PoA bridge until the upstream API supports disambiguation.
- If/when the POA API adds per-withdrawal correlation data (e.g., a NEAR receipt/output index or explicit correlation id), thread that through `WithdrawalIdentifier` and use it in `findMatchingWithdrawal` instead of `assetId` alone, in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`.
- As an interim mitigation, when more candidate withdrawals match the same `assetId` than have been resolved so far, correlate by sorting both the requested withdrawals and the API results by `amount` (as the code comment itself suggests) rather than returning the first match unconditionally.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `signAndSendIntent` + `createWithdrawalCompletionPromises`) with `withdrawalParams` = `[{ assetId: "nep141:btc.omft.near", amount: A, destinationAddress: addr1 }, { assetId: "nep141:btc.omft.near", amount: B, destinationAddress: addr2 }]` routed via PoA bridge.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals (both route `poa_bridge`). [5](#0-4) 
3. Once the PoA relayer settles the first BTC transfer (to `addr1`) but the second is still pending, `getWithdrawalStatus` returns one `COMPLETED` entry with `near_token_id: "btc.omft.near"`.
4. `describeWithdrawal({ index: 0, ... })` and `describeWithdrawal({ index: 1, ... })` both call `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which `.find()`s the same single entry and returns it for **both** indexes: [6](#0-5) 
5. Both `watchWithdrawal` promises resolve `{ status: "completed", txHash: "<addr1's tx>" }`, even though the withdrawal to `addr2` (amount `B`) has not actually landed — an integrator awaiting both promises will treat both legs as fulfilled based on a single real transfer.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
