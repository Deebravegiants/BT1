### Title
Non-embedded OAuth session ID is an unauthenticated, predictable value used to key session lookup — cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` trusts the raw browser cookie value as the session identifier with no cryptographic verification, while the gem itself generates that session id as a deterministic, guessable string derived only from the public shop domain (and, for online sessions, a user id). This breaks the intended identity binding between "session id accepted by the gem" and "session id that was actually established through a verified OAuth/JWT flow."

### Finding Description
For the cookie-based (non-embedded) path, `current_session_id` returns `cookie_session_id(cookies)`, which is simply the value of the `shopify_app_session` cookie with no signature or HMAC check: [1](#0-0) [2](#0-1) 

Contrast this with the embedded/JWT path, `session_id_from_shopify_id_token`, where the session id is only derived after `Auth::JwtPayload.new(id_token)` cryptographically verifies the JWT signature against `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

The cookie path has no equivalent binding. The session ids themselves are deterministic and computable from public information: offline session ids are `"offline_#{shop}"` and online session ids are `"#{shop}_#{associated_user.id}"`: [5](#0-4) 

And the `SessionCookie` set by the gem after `validate_auth_callback` (non-embedded case) carries exactly this predictable id as its plaintext value, again with no signing: [6](#0-5) [7](#0-6) 

The gem's own documentation instructs host apps to feed the raw `cookies` hash into `current_session_id` for non-embedded apps to obtain the id used to look up the persisted `Session` (containing the access token): [8](#0-7) 

The equality that should hold is: `session id trusted for lookup == id bound to a completed, verified OAuth handshake for that browser`. Instead the gem enforces: `session id trusted for lookup == whatever bytes appear in a cookie named shopify_app_session`, with the "legitimate" value being a string any client can construct from public data (`shop` domain) with no server-side secret involved.

### Impact Explanation
An unprivileged internet user who merely knows (or guesses/enumerates) a target shop's `.myshopify.com` domain — a public value — can set their own browser's `shopify_app_session` cookie to `offline_<victim-shop>.myshopify.com` when visiting a non-embedded app built with this gem. Following the gem's documented flow, the app calls `current_session_id` (returns the attacker-chosen string verbatim) and uses it to load the persisted `Session` object for that shop, which contains the shop's real OAuth access token. This is cross-tenant access to another merchant's session/access token without ever completing OAuth, without any secret, and without XSS or cookie theft — the attacker directly sets the value themselves.

### Likelihood Explanation
High for offline sessions: the id is exactly `"offline_" + shop`, and shop domains are public/discoverable, requiring no guessing beyond that. For online sessions the attacker additionally needs the target user's numeric Shopify user id, which is lower effort than defeating any cryptography — no secret key, TLS interception, or privileged access is needed either way.

### Recommendation
Do not treat the raw cookie value as a trusted session identifier. Either sign/HMAC the cookie value with the app's secret and verify it in `cookie_session_id`, or bind the cookie to a server-side-generated, unguessable session token unrelated to the deterministic `shop`/`user_id` scheme, verifying it the same way the JWT path verifies signatures in `Auth::JwtPayload`.

### Proof of Concept
1. Attacker learns/guesses a victim shop's domain, e.g. `victim-shop.myshopify.com` (public).
2. Attacker visits the host app (built on this gem, non-embedded) and sets browser cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
3. Host app, following the documented pattern, calls:
   ```ruby
   session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)
   # => "offline_victim-shop.myshopify.com" (attacker-supplied, unverified)
   session = MyApp::SessionRepository.load_session(session_id)
   ```
4. `load_session` returns the real, previously stored `Session` for `victim-shop`, including its access token, because the gem's `cookie_session_id` (`lib/shopify_api/utils/session_utils.rb:68-71`) performed no verification that this cookie value was ever legitimately issued to this browser.
5. The app now acts on behalf of the victim shop for the attacker's request — cross-tenant access.

          if Context.embedded?

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
