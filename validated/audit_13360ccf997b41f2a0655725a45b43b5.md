### Title
Webhook Shop Identity Spoofing via HMAC Signature Not Covering `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but the `shop` value that is subsequently trusted and handed to the host application's handler is read from an HTTP header that is never included in the signed bytes. This breaks the identity binding: `shop == request.shop` is never actually verified by the HMAC, only `hmac == HMAC(secret, raw_body)` is.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` show that only `@raw_body` is signed: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled straight from request headers (`shopify-shop-domain`, etc.) with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (from the unsigned header) to build the `WebhookMetadata` that is dispatched to the app's handler: [3](#0-2) 

`ShopifyAPI::Utils::HmacValidator.validate` confirms the HMAC check only compares the computed signature of `to_signable_string` (the body) against the received HMAC — it never touches headers: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that has installed the app, any user who installs the app on their own store (an ordinary, unprivileged action available to any internet user for a public app) legitimately receives webhook deliveries with a valid `(body, hmac)` pair signed with that shared secret. Since headers are not part of the signed bytes, that attacker can replay the exact same `body`/`x-shopify-hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will accept the HMAC as valid (it only checks the body) and will call the host handler with `WebhookMetadata` claiming the payload originated from the victim's shop. This is the analog of the reported bug class: a field that is acted on (`shop`) is not covered by the authentication check (`HMAC`), letting an attacker who controls one side of the identity equality (`hmac` verified) forge the other side (`shop`).

### Impact Explanation
This allows cross-tenant confusion/spoofing: an attacker-controlled webhook payload (for actions the attacker can trigger on their own store, e.g. `orders/create`, `app/uninstalled`, `shop/update`) can be delivered to the host application labeled as belonging to a different, victim shop, since the shop identity is not authenticated by the HMAC. Depending on how the host app's webhook handlers key off `shop` (e.g., to write victim shop-scoped data, trigger uninstall cleanup, revoke sessions, etc.), this constitutes cross-tenant access/manipulation, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker can install the target app on any of their own accessible development/trial stores (a normal, unprivileged action for public apps) to obtain one valid `(raw_body, hmac)` pair signed with the shared `api_secret_key`, then replay it directly to the app's webhook endpoint with a forged `shopify-shop-domain` header. No access token, `client_secret`, or privileged credential of the victim is required.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unsigned header: either include the shop domain in the HMAC-signed material, cross-check the header `shop` against the shop that Shopify's webhook subscription was registered for (server-side, per-topic-and-shop expectation), or otherwise validate that the delivering shop is consistent with data embedded in the (signed) body before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com`, triggering an event (e.g., `orders/create`) so Shopify delivers a webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's shared `api_secret_key`.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value.
3. Attacker sends a new POST to the same webhook endpoint reusing the identical raw body and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic`/`x-shopify-webhook-id` as desired.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) calls `Utils::HmacValidator.validate`, which only recomputes HMAC over the raw body (`lib/shopify_api/utils/hmac_validator.rb:26-31`) — validation succeeds.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, letting the attacker impersonate the victim shop's webhook stream to the host application.
