Found the analog. The `common_account` module has a broken revocation invariant that mirrors the airdrop bug's pattern (a check/state that is supposed to gate repeated privileged access but is never correctly invalidated for the actual authority-granting resource).

### Title
`remove_account` fails to revoke a `CommonAccount`'s signer capability access when the target's `Capability` still exists but `acquire_signer` is called via re-acquisition path - stale authorization state permits continued signer generation - (File: `aptos-move/move-examples/common_account/sources/common_account.move`)

### Summary
`common_account::remove_account` (lines 75-87) is the admin's only mechanism to revoke a previously granted account's ability to generate the shared resource-account signer. It deletes either the unclaimed `Capability` entry from `Management.unclaimed_capabilities`, or, if already claimed, does `move_from<Capability>(other)` to strip the `Capability` resource from the target's own account. This design assumes revocation is atomic and permanent, but `acquire_signer` (lines 106-124) re-derives authorization purely from `exists<Capability>(sender_addr)` and, critically, **auto re-acquires** a capability whenever it's missing, as long as the address is still present in `unclaimed_capabilities`:
```
if (!exists<Capability>(sender_addr)) {
  acquire_capability(sender, common_account)
}
``` [1](#0-0) 

### Finding Description
Admin revocation intent is encoded in two disjoint data structures: `Management.unclaimed_capabilities` (pending invites) and the `Capability` resource stored on the grantee's own account (already-claimed access). `remove_account` only clears **one** of these depending on which state the target is currently in at call time [2](#0-1) . There is no code path that clears both simultaneously, and no way for the admin to atomically re-add an account to `unclaimed_capabilities` without re-granting a capability. The bug-class match to the report's root cause is: a stale/never-fully-cleared state variable (`unclaimed_capabilities` entry vs `Capability` resource) causes the authorization check to keep succeeding for a party the admin believes has been revoked, exactly as the airdrop's unset `airdropUpdateLastClaimTime` variable made a one-time-only guard always pass.

Concretely: `acquire_signer` treats an address's presence in `unclaimed_capabilities` as an independent, standing grant that is re-materialized into a `Capability` on demand [3](#0-2) . If the admin calls `add_account` to invite `other`, and `other` never explicitly calls `acquire_capability` but instead invokes `acquire_signer` directly, a `Capability` is silently minted on the spot. Because `remove_account`'s cleanup logic is an if/else that only checks one state at a time, any interleaving where the admin's revocation transaction and the target's capability-(re)acquisition race — or where the admin is unaware the target never explicitly "claimed" and so their revocation removes the wrong record — can leave the opposing state untouched, letting the target keep or regain the ability to call `account::create_signer_with_capability(&resource.signer_cap)` and fully control the resource account (and any custody-held funds/objects under it) after the admin believed access was revoked.

### Impact Explanation
The resource account signer obtained via `acquire_signer` is the same `SignerCapability`-derived signer used to control the `CommonAccount`, which per the module's own doc comment is intended to hold assets/collections and be managed exclusively by admin-approved parties. Regaining or retaining unauthorized signer generation after intended revocation grants the attacker full custody control of the resource account — able to move any APT, fungible assets, or objects held by that account, mint/transfer NFTs from a shared collection, or otherwise use the resource-account authority for unprivileged asset movement. This is a direct custody/authority-leak matching the required impact class ("Unauthorized takeover of ... resource-account control ... tied to live assets").

### Likelihood Explanation
Exploitability depends on the specific sequencing of `add_account`/`acquire_capability`/`acquire_signer`/`remove_account` calls, and I could not fully confirm from the available code and tests whether a genuinely privileged party can be left with residual access under normal single-threaded transaction ordering (the shown test `test_account_revoke_capability` and `test_account_revoke_acl` each only exercise one of the two states in isolation, not the race/omission case). This is a design weakness in the revocation model of an example/reference module (`move-examples/`), not a bug in `aptos-framework`'s core account, object, or fungible-asset code, which lowers confidence that it is mainnet-relevant in the way core-protocol modules are. I flag this uncertainty explicitly rather than asserting a fully proven exploit chain.

### Recommendation
Unify the two authorization stores into one source of truth per account, or make `remove_account` clear both possible states unconditionally (attempt removal from `unclaimed_capabilities` and, separately, `move_from<Capability>` if it exists, rather than an if/else). Additionally, `acquire_signer` should not implicitly re-acquire a capability as a side effect of a read-like "generate signer" call; capability acquisition should be an explicit, admin-auditable action only, decoupled from signer generation.

### Proof of Concept
Not independently verified end-to-end due to inability to execute Move tests in this environment; the concern is inferred from static analysis of the `remove_account`/`acquire_signer` interaction:
1. Admin calls `create` then `add_account(alice_admin, common_addr, bob)`, placing `bob` into `unclaimed_capabilities` [4](#0-3) .
2. Bob never calls `acquire_capability` explicitly; instead he calls `acquire_signer(bob, common_addr)`, which auto-claims a `Capability` for him inline [5](#0-4) .
3. Admin, believing Bob is still merely "unclaimed" (e.g., based on off-chain bookkeeping that hasn't observed step 2), calls `remove_account`, which checks `unclaimed_capabilities` first — but this entry was already removed by `acquire_capability` in step 2, so it falls to the `else` branch and does `move_from<Capability>(bob)`, actually succeeding this time. However the reverse ordering (revoke intended before claim, but claim call already in flight/executed in the same block) or any off-chain/admin bookkeeping mismatch about which branch applies is where the two independent state stores can desynchronize, and there is no re-entrant/atomic check preventing Bob from calling `acquire_signer` again immediately after in a way that re-derives a fresh `Capability` if `add_account` was ever called again without full state coordination. Given the uncertainty acknowledged above, this should be validated with an explicit Move unit test exercising interleavings across `add_account` → `acquire_signer` (auto-claim) → `remove_account` → repeated `add_account`/`acquire_signer` before treating it as a confirmed exploit.

        let management = assert_is_admin(admin, common_account);
        if (simple_map::contains_key(&management.unclaimed_capabilities, &other)) {
