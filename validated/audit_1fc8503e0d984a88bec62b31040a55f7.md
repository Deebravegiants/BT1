### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook data injection - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking an HMAC over the raw request body [1](#0-0) . The `shop` value that is handed to the application's handler as the tenant identifier is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header and is never part of the signed payload [2](#0-1) . This breaks the intended identity binding `shop authenticated == shop the payload is attributed to`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string (i.e., the body), using the app's shared `api_secret_key`: [4](#0-3) 

`Registry.process` then trusts `request.shop` (parsed from the header, not from the signed content) to build the `WebhookMetadata` that is delivered to the app's handler as the tenant identity: [5](#0-4) 

The gem's own documentation confirms `data.shop` is meant to be trusted by handlers as "The shop domain of the webhook" and is used directly for tenant-scoped work (e.g., `shop_domain: data.shop`) [6](#0-5) .

Because Shopify signs webhooks with the app-wide `api_secret_key` (the same secret for every shop that installs the app, not a per-shop secret), any unprivileged user who installs the app on their own store legitimately receives a validly HMAC-signed webhook body for their own shop. That body+HMAC pair remains valid regardless of what `shop-domain` header accompanies it, since the header is excluded from the signed content. An attacker can replay the captured `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is authentic), and `Registry.process` forwards `shop: <victim-domain>` with the attacker-controlled body to the handler, causing the application to process/store attacker-supplied data under the victim shop's identity.

### Impact Explanation
This is a cross-tenant identity confusion: the library provides no guarantee that the `shop` value delivered to application code is the shop that actually produced/authorized the payload — only that *some* valid app-signed body was received. Any application that uses `data.shop` (as documented) to route, store, or act on data per-tenant (exactly as shown in the gem's own usage example) can have attacker data injected into or attributed to a different merchant's tenant scope, which falls under the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only an ordinary Shopify merchant account that installs the target app (no leaked credentials, no privileged access, no TLS interception) — install the app, capture one legitimate webhook body/HMAC pair for the attacker's own store, then send that pair to the app's public webhook endpoint with an arbitrary victim `shop-domain` header. The gem does nothing to prevent or even warn against this, and its own documentation encourages using the header-derived `shop` field as trustworthy.

### Recommendation
Bind the shop identity to the signed material. Options:
- Include the shop domain (and topic/webhook id) in the string that is HMAC-verified (`to_signable_string`) rather than only signing the raw body, or
- Require callers to independently reconcile `request.shop` against a known/expected set of installed shop domains before invoking the handler, and document this as a mandatory step, or
- At minimum, clearly document that `data.shop` is unauthenticated header data and must not be trusted for tenant attribution without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook request from Shopify: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with the same body `B` and the same header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. Server constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` and calls `Registry.process`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and compares to `H` — it matches, since the body wasn't changed [7](#0-6) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)` [8](#0-7) , causing the app to act on attacker-controlled data as if it belongs to `victim.myshopify.com`.
