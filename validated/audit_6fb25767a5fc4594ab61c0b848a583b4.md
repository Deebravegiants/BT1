### Title
`createBackgroundRpc` port handler exposes privileged wallet RPC methods with no sender/origin authentication - ([File: libraries/browser-extension-rpc/src/index.js])

### Summary
`createBackgroundRpc` (aliased as `createRPC` in `libraries/browser-extension-rpc/background.js`) accepts any `chrome.runtime.onConnect` port whose `name` matches the expected port name and immediately wires it into an RPC channel with the exposed `methods` set, without ever validating who the caller is [1](#0-0) . This mirrors the PoolTogether `rngComplete` bug class: a privileged operation is reachable by any caller because the only check performed is on a caller-supplied/attacker-controllable value (`port.name`), not on caller identity.

### Finding Description
`createBackgroundRpc` registers a single `chrome.runtime.onConnect` listener. Inside `handlePortConnect`, the only gating condition is:
```
if (port.name !== name) return
```
There is no check on `port.sender.id` (extension id) or `port.sender.origin`/`port.sender.url` before the connecting port is wrapped in a `PortTransport`, an `RPC` instance is created, and `rpc.exposeMethods(methods)` is invoked, exposing every method in `methods` to whoever opened the port [2](#0-1) [3](#0-2) .

In a Chrome extension, `chrome.runtime.onConnect` fires for connections from:
- the extension's own UI pages/popup (the intended caller),
- any other page/extension listed in `externally_connectable` (if configured), and
- in some configurations, content scripts injected into arbitrary web pages, which can call `chrome.runtime.connect({ name })` using the extension ID leaked to the page (e.g., via `window.postMessage` bridges such as `content.js`/`inapp.js` in the same package, which relay data between the page context and the extension) [4](#0-3) [5](#0-4) .

Because `name` (the port name, e.g. `'app'`) is a known constant (`DEFAULT_PORT_NAME = 'app'`) rather than a secret, any code able to reach `chrome.runtime.connect` for this extension can open a port with that name and satisfy the only check present, then call any method exposed via `methods` (the wallet's `@exodus/headless`/`wallet-sdk` API surface, as shown by the intended usage pattern in `@exodus/sdk-rpc`'s README: `rpc.exposeMethods(walletSdkApi)`) [6](#0-5) . This is functionally identical to `rngComplete` lacking a `msg.sender == rngAuctionRelayer` check: the intended caller (the extension's own UI) is never distinguished from any other party that can reach the entry point.

### Impact Explanation
If `methods` passed to `createBackgroundRpc` includes privileged wallet operations (transaction signing, message signing, seed/key export, unlock, etc. — the same class of API surfaced by `@exodus/headless`/`@exodus/message-signer`/`@exodus/tx-signer`), an unauthenticated caller able to open a port to the background script could invoke those operations directly, bypassing whatever UI-side consent/authorization flow was intended to gate them. This is a direct wallet-compromise-class impact (unauthorized signing / secret disclosure) analogous to the H-02 finding, where the missing caller check allowed reward theft.

### Likelihood Explanation
Likelihood depends on (a) whether `externally_connectable` or a content-script bridge exposes the extension ID/port name to untrusted pages, and (b) what specific `methods` object is passed to `createBackgroundRpc` at the integration point (not fully visible in the indexed portion of the repo — the actual wiring in the browser-extension app that calls `createRPC`/`createBackgroundRpc` with the full wallet API was not found in the available index). Given the package explicitly documents itself as "Creates the various RPC channels used in the browser extension" and ships a `content.js`/`inapp.js` window-bridge pair intended to relay page-context messages into these same channels, the port is plausibly reachable from web-page content, making this a credible, non-mocked, unprivileged-caller trust-boundary gap rather than a theoretical one.

### Recommendation
In `handlePortConnect` (`libraries/browser-extension-rpc/src/index.js`), validate the connecting port's sender before wiring it to `methods`:
- Reject ports whose `port.sender.id !== chrome.runtime.id` (i.e., not from the extension's own pages) unless explicitly whitelisted.
- If external connections are intentionally supported, maintain an explicit allow-list of expected `sender.id`/`sender.origin` and reject anything else, mirroring the `if (msg.sender != rngAuctionRelayer) revert NotRelayer();` pattern from the reference finding.
- Ensure `content.js`/`inapp.js` bridges never relay privileged method names/arguments without an equivalent origin check at the boundary where page-context data enters the extension messaging system.

### Proof of Concept
Conceptual PoC (cannot be executed without the full extension manifest/wiring, which is not present in the indexed files):
1. A malicious web page (or malicious extension listed as externally connectable) calls `chrome.runtime.connect({ name: 'app' })` targeting the wallet extension's ID.
2. `handlePortConnect` in `libraries/browser-extension-rpc/src/index.js:47-62` only checks `port.name === 'app'` and accepts the connection, calling `rpc.exposeMethods(methods)`.
3. The malicious caller sends a JSON-RPC request over the port invoking a privileged method (e.g., a signing or key-export method exposed in `methods`), which the background script executes without ever verifying the port originated from the extension's own trusted UI.

Note: The exact `methods` object passed into `createBackgroundRpc` in production, and the extension manifest's `externally_connectable` configuration, were not found in the indexed portion of the repository, so full end-to-end exploitability against a specific privileged method could not be confirmed from the available context.

```javascript
export const createBackgroundRpc = ({
  name = DEFAULT_PORT_NAME,
  methods,
  serialize,
  deserialize,
  onData,
  onConnect,
  onDisconnect,
}) => {
  const rpcManager = new RPCManager()

  const handlePortConnect = (port) => {
    const id = port.sender.tab?.id || port.sender.documentId

    if (port.name !== name) return

    const rpc = createRpc({ port, methods, serialize, deserialize, onData })

    port.onDisconnect.addListener(() => {
      rpc.end()
      onDisconnect?.()
    })

    rpcManager.add(id, rpc)

    onConnect?.()
  }

  chrome.runtime.onConnect.addListener(handlePortConnect)

  return rpcManager
}
```

```javascript
import channels from '@exodus/browser-extension-channels'
import { createWindowRpcTransport } from '@exodus/window-rpc-transport'

import { getIcon, getTitle } from './src/metadata.js'

const metadata = new Promise((resolve) => {
  window.addEventListener('load', async () => {
    const title = getTitle()
    const icon = await getIcon()
    resolve({ title, icon })
  })
})

export const createRPCProxy = ({ extensionName, channelName }) => {
  if (typeof extensionName !== 'string' || typeof channelName !== 'string') {
    throw new TypeError(`Unable to create RPC because channelName or extensionName are missing`)
  }

  const channel = channels[channelName]
  const transport = createWindowRpcTransport({
    name: `${extensionName}-${channelName}`,
    target: `${extensionName}-${channelName}-window`,
  })

  transport.on('data', async (event) => {
    const isResponse = !JSON.parse(event).method
    const senderMetadata = await metadata
    const options = { senderMetadata }

    if (isResponse) {
      channel.sendMessage(event, options)
    } else {
      channel.call(event, options).then(transport.write)
    }
  })

  channel.onMessage((message, sender) => {
    if (sender.tab) return
    transport.write(message)
  })
}
```
