### Title
Webhook HMAC signature does not bind the `shop` (or `topic`/`webhook_id`) header, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` entirely from HTTP headers, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body [1](#0-0) [2](#0-1) . Because the same app `client_secret` is used to compute the HMAC for webhooks delivered to *every* shop that installs the app, a merchant who legitimately installed the app can capture a body+HMAC pair from their own real webhook deliveries and replay it with a forged `shop-domain` header pointing at a different, victim shop. `Webhooks::Registry.process` trusts `request.shop` for tenant attribution without any re-validation against the signature [3](#0-2) , so the app's webhook handler will process attacker-controlled data as if it originated from the victim shop.

### Finding Description
The identity binding that should hold is:
`shop_claimed_in_signed_payload == shop_the_handler_attributes_the_event_to`

In this gem that equality is never enforced, because the signed payload (`to_signable_string`) is just the raw HTTP body: [4](#0-3) 

while `shop`, `topic`, `api_version`, and `webhook_id` — all of which drive dispatch and tenant attribution — come from unauthenticated headers: [5](#0-4) 

`HmacValidator.validate` only re-computes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header value; it never mixes in `shop`, `topic`, or `webhook_id`: [6](#0-5) 

`Registry.process` then trusts `request.shop` directly to build the `WebhookMetadata` handed to the app's handler, using it as the tenant key with no additional check: [3](#0-2) 

Since Shopify uses a single `client_secret` per app across all installing shops, any shop that has installed the app already possesses valid `(body, HMAC)` pairs from its own real webhook traffic. Because the header fields are outside the signed data, that same valid HMAC can be replayed with an arbitrary `shop-domain` (and `topic`/`webhook_id`) header value, and the signature check will still pass.

### Impact Explanation
This breaks the tenant isolation boundary between shops installing the same app — a Critical-severity cross-tenant access issue per the stated impact criteria. A merchant who is unprivileged with respect to any *other* merchant's data can forge webhook deliveries that the app attributes to that other shop, potentially triggering tenant-scoped side effects (e.g. data updates, uninstall/GDPR handling, order/inventory processing) keyed off `request.shop`/`WebhookMetadata#shop`, without ever compromising the victim's credentials or the app's `client_secret`.

### Likelihood Explanation
Likelihood is high for any app that (a) allows multiple shops to install it (the normal case for any public/embedded Shopify app) and (b) has webhook handlers whose behavior depends on the `shop` (or `topic`/`webhook_id`) value from `WebhookMetadata`, which is the documented and expected usage pattern of this library's webhook handling API. No secrets beyond what the attacker's own shop already legitimately receives (its own valid webhook bodies+signatures) are required.

### Recommendation
Include the identity fields that drive dispatch/attribution — at minimum `shop`, `topic`, and ideally `webhook_id`/`api_version` — in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the signature (e.g., verify the signature over `"#{shop}|#{topic}|#{raw_body}"` instead of `raw_body` alone), so that a valid HMAC for one shop's payload cannot be replayed with a different `shop-domain` header. At minimum, document and/or enforce that host applications must cross-check the delivered `shop` against a shop they know installed the app before trusting the payload, but the safer fix is to make `to_signable_string` incorporate the header fields that `Registry.process` relies on for tenant attribution.

### Proof of Concept
1. Attacker legitimately installs the target app on `attacker-shop.myshopify.com`.
2. Shopify delivers a real webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC-SHA256(client_secret, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. The attacker (controlling their own endpoint/proxy in front of the app, or simply observing app logs/responses) records `B` and `H`.
3. Attacker sends a new POST request directly to the app's webhook endpoint with the identical body `B` and identical header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header [7](#0-6) .
5. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, which still equals `H`, so validation succeeds [2](#0-1) .
6. `Webhooks::Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [3](#0-2) , causing the app to act on attacker-supplied data as if it were an authentic event from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
