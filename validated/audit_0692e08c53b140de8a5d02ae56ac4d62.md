### Title
Data-uploader commits PCP upload queue entries as complete even on permanent upload failure, causing silent loss of biometric custody package data - (File: src/agents/data_uploader.rs)

### Summary
The Sherlock finding describes `AssetManager.withdraw()` always returning `true` and having callers unconditionally update accounting as if the full amount was retrieved, even when only a partial amount was actually withdrawn — permanently writing off the undelivered remainder. The same "treat terminal outcome as success regardless of actual result" pattern exists in orb-core's data-uploader agent: `Agent::upload_pcp` returns the same `(tier, id)` tuple whether the personal-custody-package (PCP) upload actually succeeded or permanently failed, and the caller unconditionally commits (deletes) the queue entry based solely on that tuple, without checking whether the upload actually completed.

### Finding Description
`Agent::upload_pcp` in `src/agents/data_uploader.rs` retries the backend upload in a loop, but the loop can terminate in two different states:
- Success (`Ok(())` branch) — `break`.
- Permanent failure (`Err(err)` branch, when the error is a client error) — also `break`, without ever having successfully uploaded the data. [1](#0-0) 

In both cases, the function returns `(tier, id)` — there is no signal distinguishing a successful upload from a permanently-failed one. This return value is consumed in `Agent::run`'s `FuturesUnordered` loop, which unconditionally calls `queues[...].commit(id).await` for every completed future: [2](#0-1) 

`Queue::commit` deletes the corresponding persisted PCP data from disk (in the persistent-queue variant) regardless of whether the upload actually succeeded: [3](#0-2) 

This exactly mirrors the AssetManager bug class: the "withdraw" (upload) operation can partially/fully fail, yet the bookkeeping (`commit`) treats the operation as fully complete, permanently discarding data that was never actually delivered — with no retry path and no error surfaced to the signup plan, which already considers the PCP "sent" once it hands it off to the data-uploader agent asynchronously.

### Impact Explanation
Tier-1/Tier-2 personal-custody-package data includes iris codes, normalized iris images, and face-identifier embeddings gathered during biometric capture (built in `build_pcp`, `src/plans/mod.rs`). If a permanent (client-error) failure occurs while uploading these tiers, the queue entry is committed/deleted as if delivery succeeded, causing silent, unrecoverable loss of biometric custody data for that signup, with no mechanism to detect the discrepancy or retry. This can impair downstream fraud/audit capabilities that rely on the custody package being retrievable, and there is no accounting distinguishing delivered vs. lost packages — a direct analog to the "funds written off as if delivered" impact in the original report.

### Likelihood Explanation
This requires only a legitimate signup plus a transient backend/client-side error (e.g., an expired auth token, malformed request, or backend-side rejection classified as a 4xx) during the tier-1/tier-2 async PCP upload — a realistic and not-infrequent network/backend condition, comparable in probability to the "Strategy liquidity squeeze" precondition in the original report.

### Recommendation
Change `upload_pcp` to return whether the upload actually succeeded (e.g., `Result<(u8, u64), (u8, u64)>` or an explicit success flag), and only call `queue.commit(id)` on confirmed success. On permanent failure, either retry later (e.g., re-push into the queue) or explicitly mark/report the item as permanently failed instead of silently deleting it, ensuring the discrepancy between "queued" and "actually delivered" biometric data is never masked.

### Proof of Concept
1. During a signup, tier-1/tier-2 PCP packages are queued for background upload via `orb.data_uploader...send(Input::Pcp(...))` (`src/plans/mod.rs`, around lines 613-636).
2. In `data_uploader::Agent::run`, `upload_pcp` is dispatched for the package; suppose the backend rejects the request with a 4xx (client) error on every retry.
3. In `upload_pcp`, the `Err(err)` branch detects `status.is_client_error()` and `break`s out of the retry loop without ever completing the upload; it still returns `(tier, id)`.
4. Back in `run`, `uploaders.next()` yields `(tier, id)`, and `queues[...].commit(id).await` unconditionally deletes the entry.
5. The tier-1/tier-2 biometric custody data for this signup is now permanently gone from local storage and was never received by the backend — with no error surfaced and no retry, exactly analogous to `AssetManager.withdraw()` reporting success while writing off the undelivered remainder.

    async fn commit(&mut self, id: u64) {
        match self {
            Self::Memory { .. } => {}
            Self::Persistent { path, next_id, in_progress, .. } => {
                *in_progress = in_progress.checked_sub(1).expect("shouldn't go negative");
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during commit, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {
                        if *in_progress == 0 {
                            *next_id = 0;
                        }
                    }
                }
            }
        }
    }
