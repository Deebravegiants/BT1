## Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the raw request body against the `X-Shopify-Hmac-Sha256` header, then dispatches to the app's handler using the `shop` and `topic` values taken from separate, **unauthenticated** headers. Because those identity fields are never covered by the HMAC, any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own store) can replay that body to the app's webhook endpoint while freely rewriting the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers, causing the app to process attacker-supplied data under a victim shop's tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`, i.e., the raw body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication, then uses the unauthenticated `request.topic` and `request.shop` values to route and identify the tenant for the handler call: [4](#0-3) 

The binding that should hold is:
`hmac_verified(raw_body) == hmac_verified(raw_body, shop, topic)`

but the library only satisfies `hmac_verified(raw_body)`. An unprivileged user who installs the target app on their own development/test store is a legitimate recipient of correctly HMAC-signed webhook bodies for that store. Nothing prevents them from capturing such a signed body and re-POSTing it to the app's webhook endpoint with `X-Shopify-Shop-Domain` set to any other shop the app serves (and/or `X-Shopify-Topic` changed to a different registered topic). `Utils::HmacValidator.validate` will still return `true` (the body/secret pair is genuinely valid), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` equal to the forged victim domain and/or a forged topic, since `shop`/`topic` are never part of what was authenticated.

### Impact Explanation
This breaks the tenant-identity binding the whole webhook system relies on: the app's business logic (order/customer/GDPR/app-lifecycle handlers, which typically write to per-shop storage keyed by `shop`) can be triggered against an arbitrary victim shop's tenant record using data an attacker controls (their own shop's webhook body), and/or under a topic the payload was never actually generated for (e.g. replaying a low-sensitivity payload as `customers/redact` or `app/uninstalled`). This is a cross-tenant access/data-integrity issue reachable by any user who can install the app once, satisfying the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is meaningful: obtaining a validly-signed webhook body requires only installing the app on a self-controlled store (a normal, unprivileged action for any Shopify Partner/merchant), and forging arbitrary HTTP headers on a replayed POST requires no special access, no `api_secret_key`, and no TLS interception — only knowledge of the app's public webhook URL.

### Recommendation
Bind the `shop` (and ideally `topic`) header values into the signable string used for HMAC verification, or otherwise cryptographically/contextually verify that the `X-Shopify-Shop-Domain` header matches an install actually associated with the delivered event (e.g., cross-check against Shopify's mandatory webhook delivery metadata, or require correlating the webhook's `webhook_id`/shop against a registration record known to the app). At minimum, document that `shop`/`topic` headers are unauthenticated and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook, e.g. for `customers/create`.
2. Shopify delivers a webhook to the app with a body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different registered `X-Shopify-Topic`).
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and calls the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <forged-topic>, body: parsed(B), ...)`, causing the handler to act on victim-shop's data/state using attacker-controlled content.
