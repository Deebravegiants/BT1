## Title
Silent ERC20 transfer failures in `CallDispatcher.dispatch` let `IntentGatewayV2`/`IntentsBase` credit escrow for tokens that were never actually received — (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`CallDispatcher.dispatch` only checks the boolean `success` return of a low-level `.call()`, never the ABI-encoded return data of the call. For any ERC20 token whose `transfer`/`transferFrom` returns `false` on failure instead of reverting (the classic "ZRX-style" non-compliant token from the referenced report), the outer `.call()` still reports `success == true` even though the token transfer silently failed. `IntentGatewayV2` and `IntentsBase` route their predispatch/postdispatch "sweep back to gateway" transfers through this exact path using raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` calls, and unconditionally update escrow accounting immediately after, regardless of whether the token movement actually happened.

### Finding Description
`CallDispatcher.dispatch` executes each `Call` with a raw low-level call and only reverts if the call itself reverts: [1](#0-0) 

This is the exact "unverified ERC20 return value" bug class from the referenced report: a call to `transfer()`/`transferFrom()` on a token that returns `bool` (rather than reverting) and returns `false` on failure will make `to.call{value: call.value}(call.data)` return `success = true`, because the EVM call itself did not revert — only the returned boolean payload indicates failure, and that payload is discarded.

`IntentGatewayV2.placeOrder`'s predispatch sweep-back path builds these unchecked transfer calls and dispatches them through `CallDispatcher`: [2](#0-1) 

Immediately after the `dispatch()` call returns, the balances are re-measured and `order.inputs[i].amount` / dust accounting are updated as if the transfer definitely succeeded: [3](#0-2) 

The same unchecked-transfer pattern recurs in the Tron variant of the gateway: [4](#0-3) 

and in the postdispatch output sweep in `IntentsBase._execute`, where dust/escrow bookkeeping (`emit DustCollected`) is emitted based on the pre-sweep `balanceOf`, not on confirmation that the swept tokens actually landed at their destination: [5](#0-4) 

Note that the *direct* pulls from users (`safeTransferFrom`) elsewhere in these contracts do correctly use OpenZeppelin's `SafeERC20`, e.g.: [6](#0-5) 
But the internal dispatcher-mediated sweep calls bypass `SafeERC20` entirely and instead rely on `CallDispatcher`'s bare `success` check, reintroducing exactly the unchecked-return-value hazard `SafeERC20` exists to prevent.

### Impact Explanation
If a predispatch swap uses (or a malicious order specifies) an ERC20 input token that returns `false` on transfer failure instead of reverting, the "transfer tokens from call dispatcher back to IntentGateway" step can silently fail while `CallDispatcher.dispatch` reports success. The subsequent balance measurement (`IERC20(token).balanceOf(address(this)) - balancesBefore[i]`) would then correctly show zero tokens received in the ideal case — but in the Tron/IntentsBase variants, escrow crediting (`_orders[commitment][token] += reducedInputs[i].amount`) happens unconditionally using the pre-computed `reducedInputs[i].amount`, not the amount actually verified to be received, meaning the gateway can be credited with escrow it never actually holds. This is a direct path to under-collateralized escrow: the protocol later pays real assets (fills, refunds) against phantom escrow balances, producing insolvency/loss of funds for other users or the protocol treasury.

### Likelihood Explanation
Reachable from a single, unprivileged `placeOrder` call by any user, since the user fully controls which input token address is used and can select (or in principle deploy) a token contract with this non-reverting, boolean-false-on-failure behavior in combination with predispatch/postdispatch calldata that they also control. No privileged role is required.

### Recommendation
Route every ERC20 interaction executed via `CallDispatcher` (and any other raw `.call` performing `transfer`/`transferFrom`/`approve`) through a return-data-aware check equivalent to OpenZeppelin's `SafeERC20`: after `success` is confirmed, decode `returndata` when non-empty and `require` it equals `true`; when `returndata.length == 0`, require the target has code. Apply this uniformly in `CallDispatcher.dispatch`, or refactor the gateway sweep logic to use `SafeERC20.safeTransfer` directly on the gateway/dispatcher rather than building raw encoded calls, and make escrow accounting strictly conditional on the verified balance delta rather than the pre-computed intended amount.

### Proof of Concept
1. Deploy a non-standard ERC20 (`EvilToken`) whose `transfer` never reverts and instead returns `false` on failure (mirroring the ZRX pattern from the report).
2. User calls `IntentGatewayV2.placeOrder` with `order.predispatch.call`/`assets` configured so that `EvilToken` is used as an `order.inputs` token and the predispatch step is arranged so that the dispatcher's `EvilToken` balance is insufficient at sweep time (e.g., by having the predispatch call transfer the tokens elsewhere first).
3. The sweep call `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` executes via `CallDispatcher.dispatch`; `EvilToken.transfer` returns `false`, but the raw `.call` succeeds, so `CallDispatcher` does not revert.
4. In the Tron/`IntentsBase` variant, `_orders[commitment][token] += reducedInputs[i].amount` credits escrow for tokens the gateway never received, which can subsequently be withdrawn/filled against, draining real backing assets from other orders.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
