## Title
Webhook shop-domain and topic headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never covered by the signature, yet they are handed to the app's webhook handler as trusted identity/routing data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . All other request attributes — `topic`, `shop`, `webhook_id`, `api_version` — are pulled from headers with no cryptographic binding to the body or the HMAC: [2](#0-1) .

`Registry.process` verifies only the body's HMAC via `Utils::HmacValidator.validate(request)`, then dispatches to a handler chosen by the unauthenticated `topic` header and passes the unauthenticated `shop` header straight through as the tenant identity: [3](#0-2)  This mirrors the report's bug class: the code verifies "did this come from an authorized signer" (HMAC over body, using the app's shared secret) but never verifies "does the claimed shop/topic correspond to what was actually authorized" — i.e., `shop`/`topic` are fields acted upon but not covered by the HMAC.

`HmacValidator.validate` confirms only `verifiable_query.to_signable_string` (the body, for webhooks) is hashed and compared: [4](#0-3) 

Because `shop` and `topic` are not part of the signed content, a valid `(raw_body, hmac)` pair captured from one genuine webhook delivery remains valid for **any** `shop-domain` and **any** `topic` header value an attacker chooses to attach to it. Any party that can observe at least one authentic webhook delivery for the app (e.g., a merchant who has installed the app on their own store and can see webhook traffic sent to their own endpoint, or anyone who can capture a delivery in transit) can replay the same body+HMAC with a different `shop-domain` header (naming another tenant) and/or a different `topic` header, and `Registry.process` will accept it as authentic, invoking the handler with `shop: <attacker-chosen-shop>` and `topic: <attacker-chosen-topic>`: [5](#0-4) 

The documentation reinforces that host apps are expected to trust these fields as-is (`data.shop`, `data.topic`) without any additional verification step: [6](#0-5)  and the example handler in the docs (`ShopifyAPI::Webhooks::Registry.process`) does not suggest any secondary shop/topic authentication: [7](#0-6) 

### Impact Explanation
This breaks the identity binding `verified_signer == claimed_shop` (and `verified_signer == claimed_topic`). A multi-tenant app that keys any per-tenant logic off `WebhookMetadata#shop` (e.g., attributing data to a shop record, triggering `app/uninstalled` cleanup, or `customers/redact`/`shop/redact` GDPR handlers) can be tricked into acting on behalf of a shop the attacker does not control, or into believing a different topic occurred, using only a body+HMAC pair the attacker legitimately received for their own tenant. This is a cross-tenant identity-confusion vector reachable by any unprivileged merchant/user of the app who can observe one webhook delivery.

### Likelihood Explanation
Requires the attacker to have observed at least one authentic `(raw_body, hmac)` pair for the app (trivially available to any merchant who has installed the app, since their own webhook deliveries are visible to them), and requires the receiving app to trust `WebhookMetadata#shop`/`#topic` for authorization decisions, which is exactly what the gem's own documentation and example handler encourage. No possession of `api_secret_key` or other credentials is needed — the attacker replays a signature they already legitimately received.

### Recommendation
Bind `shop`, `topic`, and other routing/identity fields into the HMAC-signed content (or otherwise cryptographically verify them against the body/webhook_id via Shopify's Admin API), and document that `WebhookMetadata#shop`/`#topic` must not be trusted for authorization without additional verification (e.g., cross-checking `webhook_id` against Shopify's API, or maintaining a per-shop webhook secret if supported).

### Proof of Concept
1. App installs the gem's webhook handling as documented, subscribing to `app/uninstalled` for shop A and shop B.
2. Attacker installs the app on shop A (their own store) and observes a legitimate webhook delivery for topic `orders/create`, body `B`, with header `X-Shopify-Shop-Domain: shop-a.myshopify.com` and a valid `X-Shopify-Hmac-Sha256` computed over `B`.
3. Attacker replays the same raw body `B` and HMAC to the app's webhook endpoint, but sets `X-Shopify-Topic: app/uninstalled` and `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds (HMAC only covers `B`), and `Registry.process` invokes the `app/uninstalled` handler with `shop: "shop-b.myshopify.com"` [3](#0-2) , causing the app to tear down or otherwise act on shop B's data/session without shop B ever having sent that event.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
