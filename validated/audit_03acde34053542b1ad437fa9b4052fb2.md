### Title
Multi-token order escrow permanently frozen if any single input/output token becomes non-transferable (paused/blacklisted) - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` iterates over every token in a `WithdrawalRequest` and calls `IERC20.safeTransfer` unconditionally in a single atomic loop. If any one of the escrowed tokens in a multi-input order is an external stablecoin (e.g. USDC/USDT) whose issuer pauses transfers or blacklists the `IntentGatewayV2` contract or the beneficiary, that single `safeTransfer` call reverts and the whole `_withdraw` call reverts — permanently blocking release of *all* other, unaffected tokens escrowed under the same order commitment, and preventing the order from ever finalizing (`_filled` write and `EscrowReleased`/`EscrowRefunded` are inside the same reverted transaction).

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` allows a user to escrow an arbitrary set of `TokenInfo[] inputs`, which can include any ERC20 token, including centralized stablecoins with admin pause/blacklist capability (USDC, USDT), consistent with how `WrappedHyperFungibleToken.send()` and other apps in this codebase accept arbitrary `IERC20` tokens via `safeTransferFrom`/`safeTransfer`. [1](#0-0) 

When an order is filled or cancelled, settlement funnels through `IntentsBase._withdraw`, which loops over `body.tokens` and performs an unconditional `safeTransfer` for each token in the same transaction: [2](#0-1) 

This function is invoked from three entry points, all of which are single, atomic, non-retriable calls:
- Cross-chain `onAccept` for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) message kinds, gated only by relayer/source authentication, not by any per-token isolation: [3](#0-2) 
- `onGetResponse`, used for source-chain cancellation once the destination confirms the order was never filled: [4](#0-3) 
- Same-chain fills via `IntrinsicIntents._fillSameChain`, which also ends with `_withdraw`-equivalent escrow release logic for multi-token orders.

Because a single order commitment can escrow several different tokens (`order.inputs` is an array, as exercised in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` with combined USDC/DAI orders), and because the relayed cross-chain `RedeemEscrow`/`RefundEscrow` message carries the *entire* `order.inputs` list as `body.tokens` in one dispatch (`_fillCrossChain`/`_cancelFromDest` build `_body(...)` from `order.inputs` directly): [5](#0-4) [6](#0-5) 

there is no way to redeliver a "resume where it left off" message that skips the frozen token — ISMP records a reverted delivery as undelivered and any resubmission replays the identical body, so the transfer of the frozen token will always be attempted and always fail, blocking the release of the co-escrowed healthy tokens indefinitely.

### Impact Explanation
If any token used as an order input becomes non-transferable at settlement time (issuer pause, blacklist of the `IntentGatewayV2` contract address, or blacklist of the beneficiary/solver address for USDC/USDT-style tokens), the entire escrowed value under that order commitment — including any other, healthy tokens bundled in the same order — becomes permanently locked in the contract with no governance or user recovery path in `_withdraw`. This is a permanent freezing of funds for legitimate solvers (who already delivered outputs) and users (awaiting refunds), matching the "permanent freezing of funds" acceptance criterion, and can affect any order that mixes a blacklist-capable stablecoin with other assets.

### Likelihood Explanation
Medium likelihood: it requires an external token issuer (Circle/Tether-style admin) to pause or blacklist a specific address, which is outside the protocol's control but is a documented, realistic, non-malicious-admin risk for USDC/USDT — assets these intent-based swap protocols are explicitly designed to route (as shown by USDC usage throughout the test suite). It does not require any malicious behavior from Hyperbridge governance, relayers, or the gateway's own admin — only ordinary external stablecoin compliance action, which has occurred historically (e.g. USDC freezes of specific addresses, Tether pauses).

### Recommendation
Make `_withdraw` resilient to a single failing token transfer, e.g.: (1) wrap each per-token transfer in a try/catch (or low-level call) so a revert on one token does not block the others, tracking any failed transfer as a separate claimable balance the beneficiary can withdraw later once the token issue is resolved; or (2) process each token's release independently (separate storage bookkeeping per token rather than one atomic loop) so a stuck token cannot hold hostage escrow for co-mingled healthy assets in the same order.

### Proof of Concept
1. User places a same-chain or cross-chain order via `placeOrder` with two input tokens: USDC and DAI, both escrowed under one `commitment` in `_orders[commitment][token]`.
2. Solver fills the order; on the cross-chain path this dispatches a `RedeemEscrow` message whose `WithdrawalRequest.tokens` contains both USDC and DAI amounts (`_fillCrossChain` uses `order.inputs` directly).
3. Before the settlement message is delivered, Circle blacklists the `IntentGatewayV2` contract address (or the solver's beneficiary address) on USDC.
4. The relayer delivers the `RedeemEscrow` proof; `onAccept` calls `_withdraw`, whose loop reaches the USDC `safeTransfer` and reverts (blacklisted `to`/`from`), reverting the whole transaction.
5. `_filled[commitment]` is never set, `_orders[commitment][DAI]` is never decremented, and the DAI amount — which has nothing to do with the blacklist — remains stuck in the contract indefinitely alongside the frozen USDC, since every future relay attempt replays the same failing `WithdrawalRequest`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
