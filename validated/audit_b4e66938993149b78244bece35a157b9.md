### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop as soon as `Utils::HmacValidator.validate(request)` passes. However the HMAC only ever covers the raw request body — the `shop-domain`, `topic`, and `webhook-id` headers that the gem hands to the app's handler as the tenant identity are never part of the signed material. Any holder of one legitimately-signed webhook payload (obtainable simply by installing the app on their own store) can replay that exact body while substituting an arbitrary `shop-domain` header, and the signature still validates. This breaks the identity binding `HMAC-verified bytes == shop attributed to the event`, letting an unprivileged app installer impersonate any other tenant's webhook stream.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers, with no cryptographic linkage to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check and then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because Shopify signs webhooks with the app's single, shop-independent `client_secret` (the same secret is used for every shop that installs the app), any correctly-signed `(body, hmac)` pair remains valid no matter which shop's domain header accompanies it. The gem's own documentation instructs developers to key downstream tenant logic directly off `data.shop`: [5](#0-4) 

So the identity binding that should hold — "the shop credited with an event equals the shop whose signed bytes produced it" — is not enforced anywhere in this gem.

### Impact Explanation
An unprivileged internet user can freely obtain a valid `(topic, hmac, body)` webhook triple by installing the app on their own (e.g. free/dev) Shopify store, since the HMAC secret is shared across all shops of the same app. They can then POST that body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. `Registry.process` will pass HMAC validation and hand the attacker-controlled `body`/`shop` pair to the app's handler as if it were a genuine event for the victim tenant. Any app that follows the documented pattern of using `data.shop` to look up the victim's session/store record for that webhook (the standard, encouraged integration pattern) will process attacker-supplied data under the victim's tenant identity — this is a cross-tenant access/data-injection primitive (e.g. forging `app/uninstalled`, `orders/create`, `customers/data_request`, or billing-related events against a shop the attacker does not control).

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented pattern of trusting `data.shop`/`data.topic`, since no additional binding check exists in the library layer to prevent it, and the only prerequisite is a free app install by the attacker on any store.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed material `to_signable_string` returns, or otherwise cryptographically bind them to the payload before `HmacValidator.validate` is evaluated, so that a signature computed for shop A's event cannot be replayed and attributed to shop B. At minimum, document loudly that `data.shop` is not authenticated by the HMAC and must be cross-checked against a known/registered shop list by the host application before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers/receives a genuine webhook delivery, capturing the raw body and the `X-Shopify-Hmac-Sha256` header — both valid per `HmacValidator.validate` against the app's shared `client_secret`.
3. Attacker POSTs the identical raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) validates the HMAC successfully (it never inspected the shop header) and invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: attacker_body ...)`, exactly as if Shopify itself had sent this event for the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
