### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking that `hmac-sha256` matches the raw request body, then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers verbatim to build the `WebhookMetadata` passed to the app's handler. Because none of these headers are part of the signed payload, an attacker who can obtain one genuine, HMAC-valid webhook (e.g. by installing the merchant's app on their own Shopify store and receiving a real webhook for it) can replay that same body/HMAC pair while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. The signature check still passes because it never touches those headers.

### Finding Description
- `Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`: [2](#0-1) .
- For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated HTTP headers: [3](#0-2) .
- `Registry.process` performs the HMAC check and then immediately trusts `request.shop`/`request.topic` to construct the metadata object handed to the app's handler, with no cross-check that the shop header matches the shop the HMAC secret actually belongs to: [1](#0-0) .

The identity binding broken is: **shop authenticated (implicitly, by virtue of a valid HMAC computed with the app's shared secret) ≠ shop stored/acted upon (`request.shop`, taken from an unsigned header)**. Since the app-level `client_secret` is shared across all shops installing the app (it is not per-shop), any tenant of the app can generate a genuinely HMAC-valid webhook body for their own shop and then relabel it as coming from any other shop.

### Impact Explanation
This is a cross-tenant integrity issue: a malicious merchant/tenant of a multi-tenant Shopify app can forge webhook deliveries "from" another merchant's shop. Depending on how the host app's `WebhookHandler.handle` uses `data.shop`, this can be leveraged to: trigger mandatory GDPR webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) or ordinary topic handlers (e.g. `app/uninstalled`, `orders/*`) against a victim shop's tenant record, causing unauthorized data deletion, incorrect state transitions, or data corruption scoped to another tenant — a cross-tenant access/write vulnerability.

### Likelihood Explanation
Likelihood is non-trivial but not trivial either: the attacker needs at least one real HMAC-valid webhook payload, which any user who can install the app on their own dev/test store can obtain (webhooks are delivered to the app's endpoint, and the attacker controls that endpoint since it's their own installation). They then only need to modify the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header when replaying/forging the POST to the app's webhook endpoint — no access token, `client_secret`, or privileged access is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-verified signable content (or otherwise cryptographically bind them), or require the host application to independently authenticate/verify that the shop-domain header corresponds to a shop that actually has this app installed and is the origin of that specific webhook delivery, rather than trusting the header unconditionally once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a genuine webhook delivery, e.g. for topic `customers/redact`, with body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes: [4](#0-3) .
4. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: ..., ...)`: [5](#0-4) , causing the app to process a redact/uninstall/other action against the victim's tenant data instead of the attacker's own.
