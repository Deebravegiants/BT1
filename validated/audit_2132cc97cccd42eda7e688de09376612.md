### Title
Webhook Shop-Domain Spoofing — HMAC Signature Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with the webhook's `shop`. In reality, the HMAC signature only covers the raw request body — never the `x-shopify-shop-domain` header that the gem uses to identify which tenant the webhook belongs to. An attacker who can obtain one validly-signed webhook body (trivially available to them by installing the app on their own store and receiving a real webhook) can replay that exact body with a forged `shop-domain` header pointing at a victim shop, and the gem will report it as authentic.

### Finding Description
The binding that should hold is:

`hmac_valid(body, secret) == true` **should imply** `shop_in(request) == shop_that_Shopify_actually_sent_this_for`

but the gem only proves the left-hand side and silently reuses an unauthenticated header for the right-hand side.

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `ShopifyAPI::Webhooks::Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed payload: [2](#0-1) 

- `HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header — it never touches `shop`: [3](#0-2) 

- `Registry.process` treats a passing HMAC check as full authentication, then forwards the unauthenticated `request.shop` straight to the app's handler as the tenant identifier: [4](#0-3) 

- The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify," and that `data.shop` is a trustworthy field to key downstream work off of (e.g. `perform_later(shop_domain: data.shop, ...)`), so host apps are explicitly encouraged to rely on `data.shop` without a second authentication check: [5](#0-4) [6](#0-5) 

Because the same app-wide `Context.api_secret_key` is used to sign webhooks for *every* installed shop, and the signature never incorporates the shop, any party that has installed the app on their own store — an ordinary, unprivileged merchant/attacker — can:
1. Trigger (or simply receive) a real webhook for their own store, capturing a body + a valid HMAC computed with the app's shared secret.
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` passes (body/HMAC pair is genuine), `Registry.process` accepts it, and the handler executes with `data.shop` set to the victim's domain, even though Shopify never sent this event for that shop.

### Impact Explanation
This crosses a tenant boundary using only the attacker's own (unprivileged) app installation — no access token, `client_secret`, or victim credentials are required. Depending on how the host app persists or acts on webhook data keyed by `data.shop` (order/product upserts, inventory sync, billing/usage events, deletion webhooks, etc.), this allows an attacker to inject or forge events that are recorded against another merchant's tenant, satisfying the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on any shop (the normal, unprivileged path for installing a public Shopify app), since:
- No secrets need to be guessed or leaked — a legitimate signed body is obtained through normal webhook delivery.
- Webhook topics with attacker-influenceable body content (e.g., `products/update`, `app/uninstalled`, `customers/create` triggered by the attacker's own store actions) provide many opportunities to shape the replayed payload.
- The victim shop domain is public information (`{shop}.myshopify.com`), so no special reconnaissance is required to target a specific tenant.

### Recommendation
Bind the shop identity into the value that is actually verified, e.g. include the `shop-domain` (and ideally `topic`/`webhook-id`) header in the signable string used to compute/verify the HMAC, or otherwise separately authenticate that the `shop-domain` header matches an installation the app expects for that specific webhook body before forwarding it as trusted to the handler. At minimum, the documentation for `Registry.process` should stop asserting full authenticity of `data.shop` unless the shop is actually cryptographically bound to the signature.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g. update a product) to receive a real HTTP webhook delivery: `raw_body = B`, headers include `x-shopify-hmac-sha256: H` (valid for secret `S`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay to the app's webhook endpoint:
```
POST /callback/products/update
x-shopify-topic: products/update
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: <any>
x-shopify-api-version: <any>

B
```
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because `H` is a valid HMAC of `B` under the shared secret `S` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `ShopifyAPI::Webhooks::Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:190-199`), even though Shopify never issued this event for `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
