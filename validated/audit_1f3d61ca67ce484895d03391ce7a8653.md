Webhook `shop-domain`, `topic`, `api_version`, and `webhook_id` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop, topic, API version, and webhook ID that identify the tenant and event are taken directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then hands the unauthenticated header-derived `shop` value straight to the application's webhook handler as the tenant identity, breaking the equality "bytes verified == bytes acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from HTTP headers, with no relation to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the `VerifiableQuery` (i.e., over `@raw_body` only, per `to_signable_string`), then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all header-derived and unverified — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only ever compares the computed HMAC against `verifiable_query.to_signable_string`, which for `Request` is the body — never the headers: [4](#0-3) 

The equality that should hold but does not: `HMAC-verified bytes (raw body) == bytes used to establish tenant identity (shop-domain header, topic header, webhook-id header, api-version header)`. Because the `shop` field acted on by the application (via `WebhookMetadata#shop`, documented as "The shop domain of the webhook") is never part of the signed content, any entity capable of obtaining one genuinely-signed webhook body (e.g., an unprivileged merchant who has installed the app on their own store and receives real Shopify webhooks addressed to their own `shop-domain`) can replay that same signed body to the target app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. The gem will report `Utils::HmacValidator.validate` as `true` (since it only checks the body) and forward the forged `shop` value to the application's handler as if it were authenticated tenant identity.

### Impact Explanation
This directly enables cross-tenant confusion: an unprivileged internet user/merchant, without ever possessing the app's `client_secret` or another shop's access token, can cause the host application to process webhook data under the identity of an arbitrary target shop. Downstream applications rely on `WebhookMetadata#shop` (per the gem's own documented usage in `docs/usage/webhooks.md`) as the trusted tenant key to route webhook processing, enqueue jobs, and write to per-shop data stores. Forging this value breaks the tenant boundary the gem is supposed to enforce via HMAC validation, meeting the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented pattern (`ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`), since the vulnerable code path is exactly the one the gem instructs developers to use, and no privileged secret is required by the attacker — only the ability to become an app-installing merchant and capture one legitimate signed webhook body for replay with modified headers.

### Recommendation
Include the tenant/event-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable content, or otherwise cryptographically bind them to the signed body (e.g., construct the signable string as a canonical concatenation of body + these header values) so that `HmacValidator.validate` fails if any of these fields are altered independently of the signed body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and legitimately triggers a webhook (e.g., `orders/create`), receiving from Shopify a request with a valid `x-shopify-hmac-sha256` header computed over the JSON body using the app's `api_secret_key`.
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate` recomputes HMAC over `to_signable_string` (the unchanged body) and it matches, per: [5](#0-4) 
4. `Registry.process` proceeds to call the handler with `shop: request.shop` set to `"victim-shop.myshopify.com"`, per: [6](#0-5) 
5. The host application processes/attributes the webhook payload to `victim-shop.myshopify.com`, despite the payload actually originating from and belonging to `attacker-shop.myshopify.com` — a cross-tenant confusion the HMAC check was supposed to prevent.
