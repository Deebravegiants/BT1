Confirmed: `WebhookMetadata.shop` [1](#0-0)  is populated directly from the unauthenticated `shopify-shop-domain` header, and the HMAC signature (`VerifiableQuery#hmac`/`to_signable_string`) covers only the raw body, never the shop, topic, or webhook-id headers.

### Title
Webhook `shop` attribution is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching to the app's handler with a `WebhookMetadata` struct that includes `shop`. In reality, only the raw HTTP body is authenticated via HMAC; the `shop` (and `topic`/`webhook_id`) values are read straight from HTTP headers that are never included in the signed material. This breaks the equality the gem implicitly promises to host apps: `verified(bytes) == attributed(shop)`.

### Finding Description
- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 
- `ShopifyAPI::Webhooks::Request#shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cross-check against anything cryptographically bound: [3](#0-2)  and [4](#0-3) 
- `Utils::HmacValidator.validate` computes/compares the signature purely over `to_signable_string` (the body), never over headers: [5](#0-4) 
- `Registry.process` validates HMAC and then builds `WebhookMetadata` straight from `request.shop`, handing it to the app's handler as trusted tenant identity: [6](#0-5) 
- The gem's own documentation instructs developers to trust `data.shop` from the handler callback as "The shop domain of the webhook", implying it is verified: [7](#0-6)  and states processing "will verify the request did indeed come from Shopify": [8](#0-7) 

Because the API secret (`client_secret`) is shared by the app across every merchant/tenant that installs it (not per-shop), any merchant who installs the app receives genuine Shopify-signed webhooks (valid `hmac`) for events on their own shop, HMAC'd with the same app-wide secret used for all other tenants. A malicious merchant can capture one such legitimate `(raw_body, hmac)` pair sent to the app's shared webhook endpoint, then replay it while altering only the `shopify-shop-domain` header to name a victim shop. `HmacValidator.validate` still succeeds (it never inspected the header), and `Registry.process` forwards the forged `shop` value into `WebhookMetadata`, causing the host application to process attacker-supplied webhook content as though it originated from a different, unrelated tenant.

### Impact Explanation
This crosses a tenant boundary the gem is expected to enforce: an unprivileged/low-privileged actor (any merchant who can install the app, no elevated credentials or `api_secret_key` needed) can forge the shop identity of processed webhook events for any other tenant using the same app, causing the host app to create/update records, trigger business logic, or store data under an incorrect shop context. This matches "Critical - cross-tenant access."

### Likelihood Explanation
Any merchant able to install a public/multi-tenant app already receives real webhooks (and thus a valid `(body, hmac)` pair) without needing the app's `api_secret_key`, an access token, or any privileged account — satisfying the reachable-path requirement without out-of-scope prerequisites. The only requirement is the ability to intercept/replay their own inbound HTTP webhook request and edit one header, which is fully in the attacker's control since the webhook endpoint is on the host app's server and headers are attacker-supplied transport metadata, not secrets.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) values into the signed material checked by `HmacValidator`, or independently verify that the shop domain in the request belongs to a shop with an active, previously-established session/webhook registration before trusting it in `WebhookMetadata`. At minimum, document and enforce that host applications must not treat `data.shop` as authenticated without additional server-side verification (e.g., matching against `Context`-known installed shops), or extend `Request#to_signable_string` verification to include the header value in a way that mirrors how Shopify signs it.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` (any merchant can do this for a public app).
2. Shopify sends a legitimate webhook to the app's shared endpoint: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker intercepts this request (e.g., via their own reverse proxy/logging, since it's their own traffic) and replays it to the same endpoint, changing only the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and hmac `H` unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replayed_headers)` yields `request.shop == "victim-shop.myshopify.com"` while `request.hmac == H`.
5. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(client_secret, B)`, which equals `H`, so validation passes: [9](#0-8) 
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled content attributed to `victim-shop`. [10](#0-9)
