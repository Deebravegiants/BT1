### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by checking only the HMAC over the raw request body, while the `shop` (and `topic`/`webhook-id`) values used to route and label the payload come from separate, unsigned HTTP headers. An attacker who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared `client_secret` (e.g., by receiving a genuine webhook for their own shop, since the same app `client_secret` is used across all shop installations of a public app) can resubmit that exact body/HMAC to the app's webhook endpoint while forging the `shopify-shop-domain` header to name a different, victim shop. The signature still validates because it only covers `raw_body`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then dispatches the handler using the unauthenticated `request.shop`: [3](#0-2) 

The identity binding that should hold is: `shop value cryptographically bound in the signed payload == shop value the handler acts on`. Here that equality is broken — `HmacValidator.validate` only proves "this body was signed with `client_secret`", not "this body concerns shop X". Since `client_secret` is shared across every shop that has the app installed, any merchant/attacker who installs the target app on their own store legitimately receives real webhooks with valid HMACs. They can capture one `(raw_body, hmac)` pair and replay it against the app's public webhook endpoint with a spoofed `shopify-shop-domain`/`x-shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` still returns `true` because it recomputes the HMAC over `raw_body` alone: [4](#0-3) 

The handler then receives `WebhookMetadata` carrying the attacker-controlled `shop`, causing the app to process the replayed payload as if it originated from the victim tenant.

### Impact Explanation
This crosses a tenant boundary: an app using this gem's webhook verification helper as designed can be made to attribute attacker-supplied webhook content to a different merchant's `shop` identity, without ever touching that merchant's own credentials. Depending on how the host app's webhook handlers use `shop` (e.g., to look up sessions, update local records, trigger business logic, or forward data), this enables cross-tenant data confusion/injection — matching the "cross-tenant access" impact category, since the security boundary the gem is supposed to enforce (HMAC-verified authenticity bound to a specific shop) does not actually bind the claimed shop to the signature.

### Likelihood Explanation
Exploitability requires only: (1) the attacker being an unprivileged user who can install the target app on their own (potentially free/dev) store to receive at least one genuine webhook and its HMAC, and (2) the app's webhook endpoint being internet-reachable (which it is, by design, to receive Shopify's webhook POSTs). No access token, `client_secret`, or privileged account is needed — only observation of one legitimately-received webhook for an app the attacker can freely install. This is realistic for any public multi-tenant Shopify app.

### Recommendation
Bind the shop (and topic/webhook id) into the signed material checked during verification, or independently authenticate the shop header against a value that is itself provably tied to the signed body (for example, requiring the host application to correlate the shop header against a previously-established, per-shop webhook secret/session rather than trusting an unsigned header verified only against a global HMAC). At minimum, document explicitly that `request.shop` is not authenticated by `HmacValidator.validate` and must not be trusted for tenant-sensitive decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a real webhook, capturing `raw_body` and its `shopify-hmac-sha256` header (valid because signed with the app's shared `client_secret`).
2. Attacker POSTs the exact same `raw_body` and `hmac` to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only hashes `raw_body`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim.myshopify.com"`, even though the payload actually originated from the attacker's own store. [6](#0-5)
