## Title
Webhook Shop-Domain Spoofing via HMAC That Only Signs the Request Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds authenticity to the raw request body only. The `shop-domain` header — the field the registry trusts to attribute a webhook to a tenant — is never included in the HMAC-signed material. Any party that can obtain one valid `(body, hmac)` pair for the app's shared secret can replay it with an arbitrary `shop-domain` header and have `ShopifyAPI::Webhooks::Registry.process` treat the payload as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from the (unauthenticated) `shop-domain` header: [2](#0-1) 

`HmacValidator.validate` computes the signature over `to_signable_string` (the body) and compares it with the header HMAC — it never touches `shop`: [3](#0-2) 

`Registry.process` then trusts `request.shop` directly and hands it to the handler as the authoritative tenant identity, with no separate binding check: [4](#0-3) 

The identity binding that should hold is:
`shop asserted in the trusted, HMAC-verified data == shop the handler acts on`

but the actual binding enforced by the code is only:
`HMAC(body) == received_hmac`

`shop` is completely outside that equation. Since a single app uses one `api_secret_key` shared across every shop that installs it, any merchant who installs the app on their own store can generate a genuine `(body, hmac)` pair (e.g. by triggering an `orders/create` webhook for their own store), then send that identical `body` + `hmac-sha256` header directly to the app's public webhook endpoint while substituting an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header value naming a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` passes `request.shop` (the attacker-chosen value) straight to the handler via `WebhookMetadata`.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook processing: the shop identity delivered to the handler is attacker-controlled while the HMAC only proves "some shop registered to this app sent this body." Any handler logic that keys off `WebhookMetadata#shop` (e.g., to look up a stored session/access token, to mutate per-shop state, or to act on behalf of that shop, as is the documented usage pattern in `docs/usage/webhooks.md`) can be made to act against a shop the attacker does not control — a cross-tenant confusion/impersonation primitive rooted entirely in this gem's webhook verification code.

### Likelihood Explanation
Exploitation requires no secrets beyond what any merchant already has: installing the target app on a shop they control (a normal, unprivileged action) is enough to mint a valid `(body, hmac)` pair, because the signing secret is shared across all shops for a given app. Webhook endpoints are public HTTP(S) endpoints reachable directly by any internet user, not just from Shopify's IPs, so replaying the captured request with a modified `shop-domain` header is straightforward.

### Recommendation
Include the shop domain (and ideally topic) in the signed/verified material, or independently verify that the `shop-domain` header corresponds to a shop actually registered/authorized for this app before dispatching to a handler — e.g., cross-check against a shop this app has an active session for, or bind shop into the HMAC computation the way Shopify's own webhook signing intends it to be scoped per-recipient. At minimum, document that consumers must independently validate `WebhookMetadata#shop` against known/authorized shops before trusting it, and consider validating it isn't reachable to the same body+hmac used for another shop.

### Proof of Concept
1. Install the vulnerable app on attacker-owned store `attacker-shop.myshopify.com`.
2. Trigger a webhook (e.g. `orders/create`) and capture the raw POST body `B` and its `x-shopify-hmac-sha256` header value `H` sent by Shopify (valid because it's `HMAC_SHA256(app_secret, B)`).
3. Send a new POST directly to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: orders/create`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (only `B`/`H` checked).
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing shop-scoped handler logic to run against the victim shop's identity using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
