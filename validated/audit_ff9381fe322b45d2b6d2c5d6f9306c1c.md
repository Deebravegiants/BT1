### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let msg.value be counted once per entry, minting unbacked shielded ETH - (File: contracts/Hinkal.sol / contracts/HinkalHelper.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`HinkalHelper.dimensionsCheck` and `checkOnchainCreation` never enforce that `circomData.erc20TokenAddresses` entries are unique, and `Hinkal.transact`'s balance-reconciliation loop computes `balanceDif` per array index using `getBalancesForArray`, which simply re-reads `address(this).balance` for every index that equals `address(0)`. If an attacker lists `address(0)` twice, both indices see the *same* `oldBalances[i]`/`newBalances[i]` pair, and the formula `balanceDif = newBalances[i] + msg.value - oldBalances[i]` therefore adds the single `msg.value` to two independent per-index balance equations, letting the attacker satisfy two separate `amountChanges[i] + utxoAmount` terms with one real ETH deposit.

### Finding Description
The equality that should hold is: **one unit of real ETH inflow (`msg.value`) backs exactly one accounting term (one `amountChanges[i]` or on-chain/off-chain UTXO) in the balance equation**. The code breaks this equality as follows.

In `Hinkal.transact`, balances are snapshotted per-index with `getBalancesForArray(circomData.erc20TokenAddresses)`: [1](#0-0) 

The per-token loop then computes, for every index where `erc20TokenAddresses[i] == address(0)`: [2](#0-1) 

`getBalancesForArray`/`getERC20OrETHBalance` return `address(this).balance` for every `address(0)` slot with no de-duplication: [3](#0-2) 

Because `msg.value` is already credited to `address(this).balance` by the EVM before `oldBalances` is even read (line 78, after the `payable` call), the `+ msg.value` term in line 103 exists specifically to compensate for that single pre-credit, so that for one `address(0)` entry, `balanceDif == msg.value` (matching the single real deposit). If the attacker supplies `erc20TokenAddresses = [address(0), address(0), ...]`, both indices read the *identical* `oldBalances[i]`/`newBalances[i]` (same underlying `address(this).balance` at the same two points in time), so **both** indices independently compute `balanceDif = msg.value` (or `msg.value + D` if some other on-chain balance change `D` also occurred). Each index's `require` (line 137-146) is checked independently:

```
balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount
```

The attacker can therefore set `amountChanges[0] = X` and `amountChanges[1] = X` (both satisfied by the same single `msg.value = X`), causing two off-chain shielded outputs of `X` each to be validly created by the proof/circuit — or, in the Emporium (`_externalActionId != 0`) path, cause `EmporiumUpgradeable.runAction` to also process the duplicated index and create a duplicate `UTXO` for the same real balance change: [4](#0-3) 

Neither `dimensionsCheck` nor `checkOnchainCreation` reject duplicate entries in `erc20TokenAddresses` — they only check array lengths and `onChainCreation`/`amountChanges` relationships, never uniqueness of the token list: [5](#0-4) 

`_internalTransact`/`_externalTransact` also iterate `erc20TokenAddresses` by index without deduplication, so per-index `deltaAmountChange`/transfer logic runs independently for each duplicate slot: [6](#0-5) 

None of the existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `rootHashExists`, `verifyProof`, `nonReentrant`) check for duplicate token addresses; the circuit itself (`MainEVMCircuit.circom`) constrains `inTotal + amountChanges === outTotal` per-slot but has no on-chain-visible mechanism forcing slot addresses to be distinct — distinctness must be enforced by the smart contract, and it is not.

### Impact Explanation
An attacker deposits `X` ETH once via `msg.value` but, by listing `address(0)` twice in `erc20TokenAddresses` (with matching `amountChanges` values consistent with a single `msg.value`), causes the balance-equation check to pass for two independent accounting terms backed by the same ETH. This lets the attacker mint two shielded UTXOs (or one shielded UTXO plus a duplicated on-chain commitment via the Emporium path) worth `X` each from a single `X` deposit — i.e., minting shielded value without backing, directly matching the Critical "minting shielded value without backing (protocol insolvency)" category. The attack is repeatable per transaction and scales with however many duplicate `address(0)` slots the attacker/circuit dimensions allow.

### Likelihood Explanation
The attacker needs only: (1) to deposit their own ETH via `msg.value`, (2) craft `CircomData` with duplicate `address(0)` entries in `erc20TokenAddresses` and consistent `amountChanges`/`onChainCreation`/`slippageValues` arrays of matching dimension, and (3) generate a valid proof for their own UTXOs proving the (attacker-chosen) `amountChanges` per slot — no privileged role, relay, or victim key is required. `dimensionsCheck` only validates array-length parity, not address uniqueness, so this is fully within reach of an unprivileged EOA with the ability to build custom circuit inputs, which the rules state is in-scope attacker capability.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` in `HinkalHelper.dimensionsCheck` (e.g., reject any duplicate address, and specifically forbid more than one `address(0)` entry), and/or compute the ETH balance delta and `msg.value` credit exactly once globally in `Hinkal.transact` rather than per-index, so that `msg.value` cannot be redistributed across multiple accounting slots.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with a mocked/no-op external action or use internal transact (`externalActionId == 0`).
2. Build `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `onChainCreation = [false, false]`, `amountChanges = [X, X]`, `slippageValues = [0, 0]`, and matching `outCommitments`/`encryptedOutputs` describing two shielded UTXOs of value `X` each (for two different stealth outputs, both token `address(0)`).
3. Generate a valid proof locally satisfying the circuit's `inTotal + amountChanges === outTotal` per slot (both slots independently consistent since circuit has no cross-slot address-uniqueness constraint).
4. Call `hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
5. Assert: (a) `address(this).balance` only increased by `X` (`newBalances[i] - oldBalances[i] == 0` net of the single `msg.value`), while (b) two shielded UTXO commitments of value `X` each were inserted (`insertCommitments` called with two entries), i.e., total minted shielded value (`2X`) exceeds the real backing ETH (`X`) — violating `msg.value backing == exactly one accounting term`.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }

            deltaAmountChanges[i] = _calculateDeltaAmount(circomData, i);

                transferERC20TokenOrETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    uint256(-deltaAmountChanges[i])
                );
            }
        }

        return
            IExternalActionV2(circomData.externalActionData.externalAddress)
                .runAction(circomData, deltaAmountChanges);
    }
