## Analysis Result

### Title
Intent Gateway escrow can be permanently frozen because `_withdraw`'s push-transfer to an attacker-influenced beneficiary can be made to revert forever, with no timeout-based recovery - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The `Cooler` bug lets a lender force a default by becoming unable to receive the repayment token (USDC blacklist), since `repay()` performs a mandatory push-transfer to the lender before the loan can be settled. Hyperbridge's Intent Gateway has the same push-transfer-blocks-settlement shape in its cross-chain escrow release path: `IntentsBase._withdraw` (and its sibling in `sdk/packages/core/contracts/apps/IntentGatewayV2.sol::withdraw`) unconditionally pushes escrowed tokens to a beneficiary address supplied in the incoming cross-chain message, and reverts the whole `onAccept` call if that transfer fails.

### Finding Description
In `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`), a solver fills an order on the destination chain, output tokens are delivered to the user immediately, and a `RedeemEscrow` message is dispatched back to the source chain with `beneficiary = msg.sender` (the solver) via `_post`: [1](#0-0) 

Critically, `_post` dispatches this message with `timeout: 0`: [2](#0-1) 

A `timeout` of `0` means the request never expires, and neither `IntentsBase` nor `ExtrinsicIntents` implements `onPostRequestTimeout` — there is no fallback recovery path at all for this message.

When the relayer later delivers the `RedeemEscrow`/`RefundEscrow` proof, `onAccept` calls `_withdraw`, which does an unconditional `IERC20.safeTransfer` to the beneficiary decoded from the cross-chain body: [3](#0-2) 

If the input token is a blacklist-capable stablecoin (e.g. USDC) and the beneficiary address is (or becomes) blacklisted, this `safeTransfer` reverts, which reverts the entire `onAccept` transaction — including the `_filled[body.commitment] = beneficiary` bookkeeping. Because the transfer will deterministically fail on every retry, and because there is no timeout path (`timeout: 0`, no `onPostRequestTimeout`), the message can never be delivered successfully. The identical pattern also exists in `withdraw()` of `evm/tron/contracts/apps/IntentGatewayV2.sol:691-730`, used for `RedeemEscrow`/`RefundEscrow` settlement there as well.

The same beneficiary-controlled field is used for the `RefundEscrow` path emitted from `_cancelFromDest` (destination-chain cancellation, permissionless after expiry), where `beneficiary = order.user` — a value the order creator fully controls at order-placement time.

### Impact Explanation
Once an order is filled cross-chain, `_filled[commitment]` is set as *finalized on the destination chain* (irreversible — the user already received their output tokens there). The only path to release the source-chain escrow to the solver, or to refund the user via a destination-initiated cancellation, is via the `RedeemEscrow`/`RefundEscrow` message. If the on-chain push-transfer to the message's beneficiary can be made to revert (blacklist, or any token that reverts transfers to a specific address), the input tokens escrowed on the source-chain `IntentGatewayV2`/`ExtrinsicIntents` contract become permanently unrecoverable: there is no timeout, no alternate beneficiary path, and cancellation-from-source (`_cancelFromSource`) would also fail because the destination `_filled` slot is provably non-empty (`Filled()` revert on `onGetResponse`). This is a permanent freezing of escrowed user/solver funds, matching the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Reachability requires only ordinary, unprivileged use of the Intent Gateway (placing and filling a cross-chain order) plus a beneficiary address that is (or becomes) blacklisted by the escrowed input token's issuer — the exact same precondition accepted as valid in the original Cooler finding. No admin/governance/relayer privilege is required to trigger the stuck state; a solver or order creator only needs to control (or already own) an address subject to token-level blacklisting.

### Recommendation
Do not perform mandatory push-transfers as part of message settlement that can be permanently blocked by the recipient/token. Instead, credit escrow release amounts to an internal, pull-based balance keyed by `(commitment, token, beneficiary)` and let the beneficiary withdraw separately (or allow specifying an alternate withdrawal address), so a single token/recipient failure cannot revert `onAccept` and strand the entire escrow. Additionally, consider setting a real timeout (not `0`) on `RedeemEscrow`/`RefundEscrow` dispatches and implementing `onPostRequestTimeout` to provide a recovery path.

### Proof of Concept
1. User places a cross-chain order on chain A, escrowing USDC as input, expecting DAI as output on chain B.
2. Solver (whose address is already, or later becomes, blacklisted by Circle for USDC) fills the order on chain B via `_fillCrossChain`, delivering DAI to the user — this transfer succeeds and is final.
3. `_post` dispatches a `RedeemEscrow` message back to chain A with `beneficiary = solver`, `timeout: 0` (`ExtrinsicIntents.sol:128-142`, `207-212`).
4. A relayer submits the proof; `onAccept` → `_withdraw` attempts `IERC20(USDC).safeTransfer(solver, amount)` (`IntentsBase.sol:468`), which reverts because the solver is blacklisted.
5. The entire `onAccept` call reverts every time it is retried (deterministic failure); because `timeout == 0`, no `onPostRequestTimeout` refund path exists.
6. On chain A, the escrowed USDC (`_orders[commitment][usdc]`) remains locked forever — it cannot be released to the solver, and cancellation via `_cancelFromSource` is blocked by `Filled()` since chain B already recorded the order as filled.

    function _post(Order calldata order, bytes memory body, uint256 relayerFee, uint256 nativeFee) internal {
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: relayerFee,
            payer: msg.sender
        });
        if (nativeFee > 0) {
            IDispatcher(host()).dispatch{value: nativeFee}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
