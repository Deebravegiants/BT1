### Title
Permanent Loss of ISMP Messages When Event-Range Queries Fail Due to Provider Size/Range Limits - (File: `tesseract/messaging/messaging/src/lib.rs`, `tesseract/messaging/evm/src/provider.rs`, `tesseract/messaging/substrate/src/provider.rs`)

### Summary
The relayer's inbound messaging loop advances its `previous_height` cursor to the new finalized height regardless of whether the underlying `query_ismp_events` call succeeded. When a source chain emits enough events in a single state-machine-update window that the RPC/`eth_getLogs`/`ismp_queryEvents` response exceeds a node's size or block-range limit (the same failure class as the Gravity Bridge `check_for_events` 10 MB log-size bug), the query errors out, the error is only logged, and the cursor is advanced past the range anyway — permanently dropping any Post/Get/Response events emitted in that window instead of retrying with a reduced/chunked range.

### Finding Description
`handle_update` calls `chain_b.query_ismp_events(*previous_height, state_machine_update.clone())` and on `Err`, simply logs and substitutes `Default::default()` for events: [1](#0-0) 

Immediately after, regardless of whether the query succeeded or failed, if `events.is_empty()` the code unconditionally advances the cursor and returns `Ok(())`: [2](#0-1) 

There is no distinction between "no events actually existed in this range" and "events could not be fetched because the query failed" — both paths advance `previous_height` to `state_machine_update.latest_height` and the range is never queried again.

The underlying `query_ismp_events` implementations are themselves vulnerable to the exact byte/range-limit failure mode described in the report. On the EVM side, chunking is opt-in and effectively disabled by default (`chunk_size` defaults to `1_000_000_000`, i.e. the whole range is queried in one call unless explicitly configured otherwise), and any chunk that errors is dropped rather than retried with a smaller range: [3](#0-2) 

On the Substrate side, chunking is fixed at 100 blocks, but a failing chunk is likewise just logged and skipped rather than subdivided/retried, so `Ok(events)` returned to the caller can silently be missing events from a sub-range that could not be served by the RPC node: [4](#0-3) 

Because the caller (`handle_update`) has no way to know a partial/total failure occurred (it only sees a `Result` that is `Ok` with a shorter list, or an `Err` it converts into an empty list) and advances the cursor unconditionally, any events in the failed range are permanently lost from the relay's perspective — there is no re-query, no error propagation that would halt cursor advancement, and no chunk-splitting-on-error logic (which is exactly what the original report's fix recommends: detect the size/range error and retry with a halved range).

### Impact Explanation
Requests, responses, and get-requests emitted by chain_b within an event range that trips an RPC provider's log/response size or block-range cap are never delivered to chain_a (or Hyperbridge). Since the cursor (`previous_height`) is a single monotonically advancing value shared by every consumer of that range, this is not a transient retry — it is a permanent skip. Funds or messages tied to those dropped requests/responses (e.g., token bridge mints, cross-chain calls, GET-request responses) can become permanently stuck/unrelayed unless an operator manually detects the gap and re-triggers processing out-of-band. This matches "permanent freezing of funds" / "a route unable to deliver messages."

### Likelihood Explanation
This is triggerable by ordinary usage, not any privileged actor: any user (or set of users) submitting enough dispatch/request/response traffic on a source chain between two state-machine-update checkpoints can produce a log volume that exceeds a relayer's RPC provider's size or `eth_getLogs`/range limits — public RPC providers commonly cap block ranges and response sizes well below what's needed for busy chains. Because `EvmClient`'s default configuration performs no chunking at all (`chunk_size` defaults to 1e9, i.e., unchunked), even moderate traffic against a size-limited provider can trigger this without requiring an adversarial validator set, matching the "large validator sets/rapid updates" root cause of the original H-04 finding but for ISMP event volume instead of Gravity validator-set-update volume.

### Recommendation
- Distinguish "empty because no events existed" from "empty/partial because the query failed," and do not advance `previous_height` past a range whose query failed or returned partial results.
- On error, detect provider size/range-limit errors specifically and retry with the block range halved (as recommended in the original report), recursively, combining all sub-range results before returning.
- Make `chunk_size` default to a conservative value in `tesseract/messaging/evm/src/provider.rs` instead of effectively unchunked (`1_000_000_000`), and apply the same halve-and-retry strategy in `tesseract/messaging/substrate/src/provider.rs` for individual failing 100-block chunks instead of dropping them.
- Persist/alert on any range that could not be fully queried so operators can detect and recover stuck ranges rather than silently losing them.

### Proof of Concept
1. Configure a relayer's EVM `chain_b` client against an RPC provider that caps `eth_getLogs` response size or block range (a very common public-provider constraint).
2. Drive enough Post/Get request or response emissions on `chain_b` within one state-machine-update interval that the unchunked `eth_getLogs` call in `EvmClient::query_ismp_events` (default `chunk_size = 1_000_000_000`) exceeds the provider's size/range limit and returns an error.
3. Observe `handle_update` log `"Error querying events from source chain"`, substitute an empty event list, and then log `"Skipping latest finalized height ... no new messages"` before advancing `previous_height` to `state_machine_update.latest_height`.
4. Confirm the events actually emitted in that block range are never queried again (the cursor has moved past them permanently) and therefore never relayed to `chain_a`/Hyperbridge.

	async fn query_ismp_events(
		&self,
		previous_height: u64,
		event: StateMachineUpdated,
	) -> Result<Vec<Event>, Error> {
		let full_range = (previous_height + 1)..=event.latest_height;
		if full_range.is_empty() {
			return Ok(Default::default());
		}

		let mut events = vec![];
		let chunk_size = self.config.query_batch_size.unwrap_or(1_000_000_000);
		let chunks = full_range.end().saturating_sub(*full_range.start()) / chunk_size;
		for i in 0..=chunks {
			let start = (i * chunk_size) + *full_range.start();
			let end = if i == chunks { *full_range.end() } else { start + chunk_size - 1 };
			let result = self.events(start, end).await;
			match result {
				Ok(batch) => events.extend(batch),
				Err(err) => {
					log::error!(
						target: crate::LOG_TARGET, "Error while querying events in range {}..{} from {:?}: {err:?}",
						start,
						end,
						self.state_machine
					);
				},
			}
		}

		Ok(events)
	}

	async fn query_ismp_events(
		&self,
		previous_height: u64,
		event: StateMachineUpdated,
	) -> Result<Vec<Event>, anyhow::Error> {
		let range = (previous_height + 1)..=event.latest_height;
		if range.is_empty() {
			return Ok(Default::default());
		}

		let mut events = vec![];
		let chunk_size = 100;
		let chunks = range.end().saturating_sub(*range.start()) / chunk_size;
		for i in 0..=chunks {
			let start = (i * chunk_size) + *range.start();
			let end = if i == chunks { *range.end() } else { start + chunk_size - 1 };
			let params = rpc_params![
				BlockNumberOrHash::<H256>::Number(start as u32),
				BlockNumberOrHash::<H256>::Number(end as u32)
			];
			let response = self
				.rpc_client
				.request::<HashMap<String, Vec<Event>>>("ismp_queryEvents", params)
				.await;
			match response {
				Ok(response) => {
					let batch = response.values().into_iter().cloned().flatten();
					events.extend(batch)
				},
				Err(err) => {
					log::error!(
						target: crate::LOG_TARGET, "Error while querying events in range {}..{} from {:?}: {err:?}",
						start,
						end,
						self.state_machine
					);
				},
			}
		}

		Ok(events)
	}
