### Title
Webhook shop/topic/webhook-id identity is trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook's `shop`, `topic`, `api_version`, and `webhook_id` as authenticated once `Utils::HmacValidator.validate` succeeds, but the HMAC signature only ever covers the raw request body. The tenant-identifying `shop-domain` header (and the other headers) is never part of the signed material, so an attacker who can obtain any one valid `(body, hmac)` pair for the app's `api_secret_key` can replay it with an arbitrary `shop-domain` header and have it processed by the app as an authentic webhook for a different, attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are pulled straight from HTTP headers and are not part of that signable string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only verifies the body bytes (`verifiable_query.to_signable_string`) against the HMAC: [3](#0-2) 

`Registry.process` gates entirely on that HMAC check, then forwards the *unverified* `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight into `WebhookMetadata`, which app handlers use to key data per tenant: [4](#0-3) 

This is the same class of bug as the external report: the library "verifies" one thing (HMAC over the body) while implicitly presenting other fields (the shop identity) as if they were covered by that same verification — an equality that does not actually hold:

`HMAC-verified(body) == HMAC-verified(shop, topic, webhook_id)` is assumed by `Registry.process`, but only the left-hand side is true. The `shop` field that binds a webhook to a specific merchant tenant is never bound by the signature.

### Impact Explanation
Because `api_secret_key` is shared across all shops installed on a given app, any shop that installs the app can capture one legitimate webhook (body + HMAC) delivered to their own endpoint, then replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will validate the HMAC successfully (it never checked the header) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that uses `request.shop`/`WebhookMetadata#shop` to look up sessions, write per-tenant records, or trigger actions scoped to "the shop in the webhook" can be made to act on/for the wrong tenant — a cross-tenant data confusion condition rooted entirely in this gem's own webhook-processing code, not in host-app misuse.

### Likelihood Explanation
No access token, `api_secret_key`, or privileged account is required beyond what any legitimate (even free/dev) installer of the target app already has: install the app once, capture a single webhook delivery, and replay it with a forged `shop-domain` header. The reused body content (e.g., a generic `app/uninstalled` or a webhook with attacker-controlled body) combined with header substitution is trivial to script.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or independently authenticate `request.shop` against the shop associated with the app installation before constructing `WebhookMetadata`, so that `Registry.process` cannot be tricked into attributing a validly-signed body to an arbitrary shop.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com` (any free installation works).
2. Capture a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `HMAC(api_secret_key, B) == H`), per `HmacValidator.validate_signature`: [3](#0-2) 
3. Resend the same body `B` and the same `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` validates the HMAC using only `B`/`H` (`to_signable_string` returns `B`), which succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from, nor was ever validated against, that shop: [6](#0-5)
