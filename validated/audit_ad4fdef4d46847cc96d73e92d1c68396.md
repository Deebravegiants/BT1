### Title
Webhook shop-domain (and topic/api-version/webhook-id) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are taken from unauthenticated HTTP headers — are passed straight through to the app's handler as trusted identity/routing metadata.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against this signable string [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never part of the signed material [3](#0-2) . `Registry.process` verifies only the HMAC and then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler [4](#0-3) .

The security-relevant equality the gem is supposed to guarantee is: *"the shop/topic bound to this HMAC-signed payload" == "the shop/topic delivered to the handler."* Because the header values sit entirely outside the HMAC scope, that equality does not hold — the gem only proves "the body was signed by our secret," not "this body belongs to this shop/topic." Documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4)  and that `data.shop`/`data.topic` can be trusted to route/store per-tenant work [6](#0-5)  — but the gem does not actually bind those fields to the signature.

### Impact Explanation
An unprivileged internet user who controls even one shop (a legitimate low-privilege merchant/developer account, not requiring the app's `client_secret` or an access token) can capture a genuine Shopify-delivered, correctly-HMAC-signed webhook body sent to their own shop, then replay that exact body to the target app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a different, victim shop. Because `HmacValidator.validate` only checks the body bytes, the forged request passes verification, and `Registry.process` hands the handler a `WebhookMetadata` object whose `shop`/`topic` are attacker-controlled and disconnected from what Shopify actually signed for that tenant [4](#0-3) . Since most integrations (per this gem's own documented usage pattern) key session lookup, job dispatch, or data writes off `data.shop`, this enables cross-tenant data injection into a victim shop's records (e.g., spoofed `orders/create`, `app/uninstalled`, or other lifecycle events attributed to a shop the attacker does not own) — a cross-tenant boundary violation with no valid access token or `client_secret` required by the attacker.

### Likelihood Explanation
Moderate-to-high: the attacker needs only ordinary access to one shop capable of receiving webhooks from the target app (e.g., installing the target app once on a shop they control, or intercepting/replaying their own outbound webhook traffic), no privileged credentials, no TLS interception, and no social engineering. The exploit path exists entirely within this gem's `Webhooks::Request`/`Registry` code, independent of host-application mistakes, since the header parsing and metadata construction happen inside the gem itself.

### Recommendation
Bind the security-relevant headers into the HMAC-verified material, or otherwise cryptographically tie `shop`, `topic`, `webhook_id`, and `api_version` to the signed body (e.g., include them in the canonical string that is HMAC'd, or cross-check `shop` against the webhook subscription/session records the app already registered for that topic) so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` cannot be satisfied by a payload whose header-derived identity has been altered.

### Proof of Concept
1. Attacker owns/installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) — captures the raw JSON body and its valid `X-Shopify-Hmac-Sha256` header.
2. Attacker replays the identical raw body and valid HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the body (the only signed content) is unchanged [8](#0-7) .
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [9](#0-8) , and any downstream logic keyed on `data.shop` now acts on the victim tenant using attacker-supplied data.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
