### Title
Zero-clamped artifact size limit disables the response-size cap on workflow binary/config fetches, allowing an unbounded-size download - ([File: core/services/workflows/artifacts/v2/store.go])

### Summary
`Store.FetchWorkflowArtifacts()` computes `MaxResponseBytes` for the outbound HTTP fetch of a workflow's WASM binary/config by calling a size limiter and clamping any negative value to `0` before passing it to the fetcher. In the HTTP fetcher implementation actually used for URL-based artifact retrieval, a `MaxResponseBytes` of `0` is treated as "no limit" rather than "use the default/deny", so the size-limiting protection silently disables itself instead of enforcing a bound - directly analogous to `VoltBurn.buyNSendToVoltTreasury()` allowing a caller-influenced parameter of `0` to disable slippage protection.

### Finding Description
`makeLimiters()` builds `ArtifactLimiters.MaxBinarySize` / `MaxConfigSize` from settings-backed upper-bound limiters [1](#0-0) . When fetching artifacts, `FetchWorkflowArtifacts()` calls `Limit(ctx)` and explicitly clamps a negative result to `0`:

```go
maxBinarySize, err := h.limiters.MaxBinarySize.Limit(ctx)
...
} else if maxBinarySize < 0 {
    maxBinarySize = 0
}
req := ghcapabilities.Request{
    URL:              binaryURL,
    MaxResponseBytes: safeUint32(uint64(maxBinarySize)),
    ...
}
binary, err = h.fetchFn(ctx, messageID(binaryURL, workflowID), req)
``` [2](#0-1) 

The same pattern is repeated for the config URL fetch [3](#0-2) .

The `ghcapabilities.Request.MaxResponseBytes` field is documented as: *"Maximum number of bytes to read from the response body. If the gateway max response size is smaller than this value, the gateway max response size will be used."* [4](#0-3)  — this documentation implies `0` is only meant to signal "use a smaller/default cap," never "no cap at all."

However, the concrete `FetcherFunc` implementation used for URL-based artifact fetches, `newHTTPFetcher`, interprets `0` literally as "apply no `MaxBytesReader` limit whatsoever":
```go
reader := resp.Body
if req.MaxResponseBytes > 0 {
    reader = http.MaxBytesReader(nil, resp.Body, int64(req.MaxResponseBytes))
}
data, err := io.ReadAll(reader)
``` [5](#0-4) 

This contrasts with the sibling gateway HTTP client implementation, which treats `requestSize == 0` as "fall back to the default cap" rather than "disable the cap":
```go
func maxReadBytes(sizes readSize) uint32 {
	if sizes.requestSize == 0 {
		return sizes.defaultSize
	}
	return min(sizes.defaultSize, sizes.requestSize)
}
``` [6](#0-5) 

So the two implementations of the same "0 means what?" contract diverge: one path (`httpclient.go`) fails safe (falls back to a bounded default), the other (`fetcher.go`, used for artifact fetching) fails open (removes the cap entirely). Combined with the `store.go` code explicitly producing `0` whenever the settings-backed limiter reports a negative bound, any settings/limiter state that resolves to "unlimited" (negative) is silently converted into "completely unbounded, unenforced" reads from an attacker/workflow-owner-controlled URL, exactly mirroring the reported pattern: a caller-influenced value of `0` is meant to represent "protection value not set / minimal," but is instead interpreted by the enforcement code as "protection disabled."

### Impact Explanation
An unprivileged workflow owner supplies `binaryURL`/`configURL` when registering a workflow; these are fetched by the node over plain HTTP with no cap once the limiter is in a state that resolves to `< 0` (e.g., misconfigured/negative "unlimited" setting). Because `newHTTPFetcher` skips `http.MaxBytesReader` entirely when `MaxResponseBytes == 0`, the DON node will read an arbitrarily large response body into memory from a URL the low-privilege caller controls, enabling a memory-exhaustion / resource-consumption impact against the node process. This is a quota-bypass condition: the byte-size quota that is intended to always be enforced can be silently disabled by a value that should represent "no explicit limit configured," not "no limit period."

### Likelihood Explanation
Likelihood depends on whether the per-workflow `WASMBinarySizeLimit`/`WASMConfigSizeLimit` settings can realistically resolve to a negative value in production (the code path explicitly anticipates and handles this case, which suggests it is a real, reachable state, e.g., an org/workflow override configured as "unlimited"). If so, exploitation requires no special privilege beyond being able to register a workflow with a binary/config URL — a standard, low-privilege workflow-registration action.

### Recommendation
Do not let `MaxResponseBytes == 0` mean "unbounded" in `newHTTPFetcher`. Either:
- Reserve a distinct sentinel (e.g., a dedicated "unlimited" flag or a very large explicit default) rather than reusing the zero value for two different meanings ("no override" vs. "no limit"), or
- Change `newHTTPFetcher` to always apply a hard maximum (fail-safe default) when `MaxResponseBytes == 0`, matching the fail-safe behavior already implemented in `core/services/gateway/network/httpclient.go`'s `maxReadBytes`, so that no reachable configuration state can produce a completely unbounded HTTP body read from an attacker/workflow-owner-supplied URL.

### Proof of Concept
1. Configure (or cause, via settings resolution) `cresettings.Default.PerWorkflow.WASMBinarySizeLimit` (or `WASMConfigSizeLimit`) to resolve to a negative `Limit(ctx)` value for a given workflow/owner scope.
2. `FetchWorkflowArtifacts()` clamps this to `maxBinarySize = 0` and passes `MaxResponseBytes: 0` to `ghcapabilities.Request` [7](#0-6) .
3. Register a workflow (unprivileged action) whose `binaryURL` points to an HTTP server the attacker controls that streams an effectively unbounded response body.
4. `newHTTPFetcher` sees `req.MaxResponseBytes == 0` and skips `http.MaxBytesReader`, calling `io.ReadAll(resp.Body)` directly [5](#0-4) , causing the node to buffer the entire attacker-controlled response in memory with no upper bound, unlike the intended size-limited fetch.

**Note on verification limits:** I could not confirm within the available tool budget whether `cresettings.Default.PerWorkflow.WASMBinarySizeLimit`/`WASMConfigSizeLimit` (defined in the `chainlink-common` settings package, outside this repo's index) can actually resolve to a negative value in practice, or whether `newHTTPFetcher` is exclusively used for this code path versus other fetchers (e.g., `newFileFetcher`) in some deployments. A Devin session with full repository/dependency access would be needed to confirm the exact settings semantics for "unlimited" and confirm end-to-end reachability from an unprivileged workflow-registration request.

// makeLimiters constructs ArtifactLimiters from cfg, or uses defaults if cfg is nil.
func makeLimiters(lf limits.Factory) (limiters *ArtifactLimiters, err error) {
	limiters = new(ArtifactLimiters)
	configSizeLimit := cresettings.Default.PerWorkflow.WASMConfigSizeLimit
	limiters.MaxConfigSize, err = limits.MakeUpperBoundLimiter(lf, configSizeLimit)
	if err != nil {
		return
	}

	secretsSizeLimit := cresettings.Default.PerWorkflow.WASMSecretsSizeLimit
	limiters.MaxSecretsSize, err = limits.MakeUpperBoundLimiter(lf, secretsSizeLimit)
	if err != nil {
		return
	}

	binarySizeLimit := cresettings.Default.PerWorkflow.WASMBinarySizeLimit
	limiters.MaxBinarySize, err = limits.MakeUpperBoundLimiter(lf, binarySizeLimit)
	return
}
