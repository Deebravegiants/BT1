### Title
Dual-precision rounding mismatch in `calc_take_pnl` causes drift between real pool balances and the `TargetOrders` PnL basis, mis-accounting protocol PnL reserves - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes the amount of accrued trading profit to reserve for the pnl owner in two independent representations — a high-precision "sys-decimal" value (`delta_x`/`delta_y`) and a native-token-decimal value (`pc_pnl_amount`/`coin_pnl_amount`) — using two separate floor-division chains on the same underlying `diff_x`/`diff_y`. These two values are not guaranteed to be consistent representations of the same amount, exactly the class of bug described in the Ajna report where two parallel accounting paths (one representing "assumed" percentage-based bookkeeping, one representing the actually-transferred amount) diverge due to independent rounding, corrupting the protocol's internal ledger over time.

### Finding Description
`calc_take_pnl` is called from the fully permissionless `Deposit`/`Withdraw` instruction handlers (`process_deposit`, `process_withdraw`), which any liquidity provider can trigger. Inside it: [1](#0-0) 

- `delta_x`/`delta_y` are computed at `sys_decimal_value` precision by floor-dividing `diff_x`/`diff_y` (the *raw*, unrestored growth in the invariant) by `pnl_numerator/pnl_denominator`.
- `pc_pnl_amount`/`coin_pnl_amount` are computed by first restoring `diff_x`/`diff_y` to *native token decimals* via `Calculator::restore_decimal` (itself a lossy floor-division, see `program/src/math.rs` lines 96-104), and only then floor-dividing by `pnl_numerator/pnl_denominator` a second time.

`restore_decimal(diff_x) * n/d` (native-decimal path, floor twice) is not algebraically guaranteed to equal `restore_decimal(diff_x * n/d)` (equivalent to the sys-decimal path) because integer floor-division does not commute with multiplication. As a result the two computed quantities can differ by up to several units in the smaller decimal space.

These two divergent values feed two different, supposedly-synchronized ledgers:
- `pc_pnl_amount`/`coin_pnl_amount` are subtracted from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (the *real*, native-decimal pool balances used for every subsequent LP-mint, LP-redeem and swap calculation) and accumulated into `amm.state_data.need_take_pnl_pc/coin` (the amount later paid out via `process_withdrawpnl`). [2](#0-1) 
- `delta_x`/`delta_y` (sys-decimal) are used by the callers (`process_deposit`, `process_withdraw`) to update `target_orders.calc_pnl_x`/`calc_pnl_y` — the stored "last-k" reference point that the *next* `calc_take_pnl` invocation compares against the *real* current balances to determine newly accrued PnL: [3](#0-2) [4](#0-3) 

Because the stored reference (`calc_pnl_x`/`calc_pnl_y`) is decremented by `delta_x`/`delta_y` while the real pool balance is decremented by the independently-rounded `pc_pnl_amount`/`coin_pnl_amount`, the two ledgers silently drift apart on every single deposit/withdraw call — exactly the "two bookkeeping paths that assume the same split but don't reconcile" pattern flagged in the Ajna finding (there: 90%/10% split reconciled via two different rounding-prone computations; here: the sys-decimal vs. native-decimal PnL split).

### Impact Explanation
The comparison that gates whether/how much PnL is taken on the next call is `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_pnl_y_amount` where `calc_pc_amount`/`calc_pnl_y_amount` are `restore_decimal(target.calc_pnl_x/y, …)`: [5](#0-4) 
Since the stored basis is derived from the drifted `calc_pnl_x`/`calc_pnl_y` rather than the exact amount actually removed from the pool, every subsequent PnL extraction is computed against a systematically-biased reference. This causes the protocol to reserve (`need_take_pnl_pc/coin`, later paid out to the `pnl_owner` via `process_withdrawpnl`) an amount of tokens that is not exactly reconcilable with the true trading-fee growth, meaning LP-owned pool funds (`total_pc_without_take_pnl`/`total_coin_without_take_pnl`, which directly determine LP mint/redemption ratios) can be silently and cumulatively skewed on every deposit/withdraw, in favor of or against LPs depending on rounding direction. Given deposits/withdrawals are frequent and fully user-triggered, this drift compounds across the pool's lifetime, degrading the correctness of the pool's PnL accounting and, in aggregate, LP redemption fairness.

### Likelihood Explanation
`calc_take_pnl` executes on essentially every `Deposit` and `Withdraw` transaction, both of which are open to any unprivileged user with attacker-chosen amounts — no special accounts, signer privileges, or non-default configuration are required. The rounding mismatch is deterministic and occurs on virtually every call where accrued PnL is non-zero, so the divergence is continuously and automatically triggered rather than requiring a crafted edge case.

### Recommendation
Derive `pc_pnl_amount`/`coin_pnl_amount` directly from `delta_x`/`delta_y` via a single `restore_decimal` call (i.e., `pc_pnl_amount = restore_decimal(delta_x, pc_decimals, sys_decimal_value)`), instead of independently computing `diff_pc_pnl_amount` and re-multiplying by `pnl_numerator/pnl_denominator`. This guarantees that the amount subtracted from the real pool balance (`total_pc_without_take_pnl`) and the amount subtracted (in sys-decimal terms) from the stored `target_orders.calc_pnl_x` basis represent the exact same underlying value, eliminating the dual-rounding drift.

### Proof of Concept
Root-cause code paths (no additional harness needed to see the divergence — it is a pure arithmetic property of the existing code):

1. `diff_x`/`diff_y` computed once: [6](#0-5) 
2. Path A (sys-decimal): `delta_x = diff_x * pnl_numerator / pnl_denominator` (single floor division): [7](#0-6) 
3. Path B (native-decimal): `diff_pc_pnl_amount = restore_decimal(diff_x, pc_decimals, sys_decimal_value)` (floor division) then `pc_pnl_amount = diff_pc_pnl_amount * pnl_numerator / pnl_denominator` (second floor division): [8](#0-7) 

For concrete values where `sys_decimal_value` has more precision than the native decimals (e.g. `sys_decimal_value = 10^6`, `pc_decimals = 9` used in the repo's own unit tests such as `test_calc_take_pnl`/`test_calc_pnl_precision`), pick `diff_x` such that `diff_x * pnl_numerator` is not evenly divisible by `pnl_denominator` at the sys-decimal scale but becomes divisible (or rounds differently) after `restore_decimal` rescales it to native decimals. Because `restore_decimal` performs its own floor `(val * 10^native_decimal) / sys_decimal_value`, the two computation orders (`floor(restore(diff_x))*n/d` vs `restore(floor(diff_x*n/d))`) are provably non-equal for a subset of inputs, producing a discrepancy between `pc_pnl_amount` (native, drives real vault subtraction and `need_take_pnl_pc`) and `restore_decimal(delta_x)` (the true equivalent of what is recorded against `target_orders.calc_pnl_x` in `process_deposit`/`process_withdraw`). This discrepancy accumulates on every deposit/withdraw call, analogous to the Ajna `claimDelegateReward`/`_updateTreasury` split mismatch.
