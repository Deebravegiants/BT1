This confirms the vulnerability path: `Registry.process` validates only `Utils::HmacValidator.validate(request)`, whose signable string is the raw body only, yet the trust-critical `shop` field consumed by handlers is read straight from an attacker-controlled header, unauthenticated.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` succeeds, then hands `request.shop` to the app's handler as the tenant identity for that event. But the HMAC is computed only over the raw JSON body, never over the `shop` (or topic/webhook-id) header, so the header can be swapped freely on an otherwise-genuine, validly-signed webhook without invalidating the signature.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, `api_version`, or `webhook_id`: [2](#0-1) 

Those same unauthenticated header-derived fields, in particular `shop`, are what `Registry.process` forwards to the registered handler as the tenant identity once the HMAC check "passes": [3](#0-2) 

The `client_secret`/`api_secret_key` used to sign webhooks is the same across every shop that has installed the app (it is not per-shop). Any merchant who installs the app is a legitimate, unprivileged recipient of correctly-signed webhooks for their own shop. That merchant can replay one of their own genuinely-signed webhook bodies to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true`, because it only ever re-derives the signature from `@raw_body`, and `Registry.process` will invoke the handler with `data.shop` set to the attacker-chosen victim domain. This breaks the intended identity binding: `shop authenticated by HMAC == shop acted upon by the handler`.

Downstream apps (per the gem's own documented usage pattern) use `data.shop` to look up sessions/records and perform actions scoped to that shop: [4](#0-3) 

Since the gem is the one that parses headers, verifies the signature, and constructs the `WebhookMetadata` handed to the handler, this is a defect in the gem's own trust boundary, not merely "the host app ignoring documented API."

### Impact Explanation
An attacker who is any paying/free merchant that installs the app (unprivileged relative to other tenants) can forge the `shop` attribution of a webhook event to any other shop domain, causing the host application to process/act on data under a victim's tenant context (cross-tenant access) using an attacker-supplied but validly-HMAC'd payload. This matches the Critical "cross-tenant access" impact category, since it lets one tenant inject events falsely attributed to another tenant's identity, potentially triggering resource creation, GDPR-webhook side effects, notifications, or record updates against the wrong shop's stored session/data.

### Likelihood Explanation
Requires only: (1) installing the app as any shop (a normal signup, not a privileged action), (2) triggering an event to receive one genuinely-signed webhook for the attacker's own shop, and (3) POSTing that captured body with a modified `shop`-domain header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's credentials is needed. This is realistically exploitable by any unprivileged internet user who can install the target app.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable payload used for HMAC verification (or otherwise cryptographically bind them to the body before comparison), and reject requests where the header-derived identity fields do not match a value bound into the verified signature. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should not silently omit the shop-domain header from what `HmacValidator` verifies.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, becoming a legitimate merchant.
2. Attacker triggers an `orders/create` webhook for their own shop and captures the raw POST: body `B`, and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the same request to the app's webhook endpoint, but changes only the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, leaving body `B` and `x-shopify-hmac-sha256: H` untouched.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` (`B`) and matches `H` — validation succeeds: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and was signed for `attacker-shop.myshopify.com`: [6](#0-5)
