## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` implements wildcard CORS matching by stripping the `*.` prefix from a configured allowlist entry and then checking `strings.HasSuffix(originHost, allowedHost)`, without verifying that the matched suffix is preceded by a `.` boundary. This lets an origin such as `evilethereum.org` incorrectly satisfy an allowlist entry of `*.ethereum.org`, because the raw string ends with `ethereum.org` without actually being a subdomain of it.

## Finding Description
The wildcard branch of `isAllowedOrigin` is:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [1](#0-0) 

This check is unanchored: it does not require the character preceding the matched suffix to be `.`, so `evilethereum.org` (which ends in the literal characters `ethereum.org`) passes the same as a legitimate subdomain like `remix.ethereum.org`. The result of `isAllowedOrigin` directly controls whether `Access-Control-Allow-Origin` is reflected back with the request's `Origin` header on the gateway's user-facing HTTP endpoint: [2](#0-1) 

The existing regression tests only cover true-positive subdomain matches (`remix.ethereum.org`, `another.valid.domain.com`, `example.gov`) and do not test the suffix-collision case, so this gap is unguarded by any existing check.

## Impact Explanation
This is a real logic bug in an in-scope file with a broken security invariant (wildcard scoping), but the CORS feature is opt-in and off by default: the shipped sample config sets `CORSEnabled = false` and `CORSAllowedOrigins = []`, requiring an operator to explicitly enable CORS and configure a wildcard entry for this to matter. Even when enabled, exploitation additionally requires an attacker to register a domain with the matching literal suffix (e.g. `evilethereum.org`) and lure a victim's browser to a page on that domain so the browser sends the crafted `Origin` header and reads the credentialed cross-origin response. This combination — operator-chosen wildcard configuration plus victim browser interaction to realize any user-facing impact — falls into the explicitly excluded categories of "misconfiguration" and "victim social engineering" required to complete the exploit chain, even though the raw string-matching flaw itself is real and could be demonstrated via direct HTTP request against a locally configured gateway.

## Likelihood Explanation
Low-to-moderate in a narrow, opt-in configuration path. It requires the gateway operator to enable CORS and add a wildcard allowlist entry (not default behavior), and for any concrete cross-user impact it additionally requires an attacker to control a suffix-colliding domain and get a victim's browser to visit it — this is not something a purely unprivileged network client can trigger against a node/gateway in its default or typical configuration without an operator opting into wildcard CORS and a victim being socially engineered into visiting the attacker's page.

## Recommendation
Anchor the wildcard suffix match to a subdomain boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Add a regression test for suffix-collision domains (e.g., `evilethereum.org` against `*.ethereum.org`).

## Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP request to the gateway's user-facing endpoint with header `Origin: https://evilethereum.org`.
3. Observe `isAllowedOrigin` returns `true` and the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, matching the pattern of the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` test. [3](#0-2)
