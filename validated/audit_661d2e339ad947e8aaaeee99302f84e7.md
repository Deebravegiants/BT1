### Title
Token dust-donation to the curve `Pair` permanently disables the supply-based graduation trigger, freezing curve-raised LT and the 250M LP reserve - ([File: packages/contracts/src/Bonding.sol])

### Summary
Any unprivileged address can call `IERC20(token).transfer(pairAddress, 1)` to send a tiny amount of the launched `Token` directly to its curve `Pair`. Because the protocol's supply-based graduation trigger is an exact-equality check (`IPair.tokenBalance() == 0`), a single wei of donated dust that a buy can never fully drain permanently prevents that check from ever being satisfied again, mirroring the external report's root cause: an unprivileged fund transfer that breaks a hard equality invariant relied on by the state machine, causing a permanent stall of the dependent logic path.

### Finding Description
Graduation in `Bonding.sol` fires on a dual trigger, documented in `docs/contracts-scope.md` and `packages/contracts/AGENTS.md`:
- **USD trigger:** `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K`.
- **Supply trigger:** `IPair.tokenBalance() == 0` — explicitly described as covering "flat/bear markets where $9K is never reached" [1](#0-0) .

`tokenBalance()` on `Pair.sol` is a live `balanceOf` read on the launched `Token` contract, not the internal stored `_pool.tokenReserve` [2](#0-1) . Any address can call the standard ERC20 `transfer` on the launched `Token` to send it directly to the `Pair` address — this is a normal, permissionless, unrestricted ERC20 transfer, not gated by `Router`/`BONDING_ROLE`.

Because the supply trigger requires the balance to hit **exactly** zero, a griefer only needs to send 1 wei of the token to the pair at any point while the curve still has unsold supply. Curve buys (`Router.buy` → `Pair.transferToken`) only ever *decrease* the real ERC20 balance by the amount the AMM math computes; they never zero out a balance that includes attacker-donated dust that the AMM math has no knowledge of, since `_computeBuy`'s cap only limits `tokensOut` to `realBalance`, it doesn't force `realBalance` down to precisely 0. Once the last legitimate buy consumes all curve-sold tokens, the leftover donated wei keeps `tokenBalance()` permanently at ≥1, so `tokenBalance() == 0` can never become true again. There is no sell-back, burn, or sweep of this dust available to anyone outside of `_prepareGraduationLiquidity`, which is only reachable *after* a graduation trigger has already fired — a chicken-and-egg lock.

If the same token's LT reserve is in a flat/bear market (explicitly acknowledged as a real, non-adversarial scenario the supply trigger exists to handle), the USD trigger will also never fire. With both triggers permanently disabled, `canGraduate()` can never return true, so `_enterGraduating`/`triggerGraduation`/`finalizeGraduation` become permanently unreachable for that token [3](#0-2) .

### Impact Explanation
This permanently freezes value that is designed to be released at graduation:
- The 250M `lpReserve` tokens held in `Bonding` for that token (`LP_RESERVE`) can never be delivered to the HyperSwap LP or burned, since `_prepareGraduationLiquidity`/`finalizeGraduation` never execute [4](#0-3) .
- All real LT raised by the curve (`ltFromPair`, computed from `Pair.k()` and stored reserves) remains stranded inside the `Pair`, since it is only drainable via `Router.graduate`, itself only callable from `_enterGraduating`/`_prepareGraduationLiquidity` [5](#0-4) .
- The token can never migrate to the graduated HyperSwap V2 pool, permanently denying traders/creator/LP the intended post-graduation venue and LP lock (`LPLock.recordLock` is never called).

This is a permanent freeze of protocol/LP-bound funds triggerable by any unprivileged wallet for the cost of a dust transfer, satisfying the "permanent freezing of trader, creator or LP funds" impact bar.

### Likelihood Explanation
Likelihood is high: the attack requires only holding (or briefly acquiring, e.g., via a tiny buy) 1 wei of the launched `Token` and calling a standard ERC20 `transfer` to the publicly-known `Pair` address — no special role, no capital at risk beyond gas, and it can be executed proactively on any newly-launched token before it nears full sellout, especially those paired with LTs that see flat/declining exchange rates (a normal, expected market condition the docs themselves call out as the reason the supply trigger exists).

### Recommendation
Do not rely on an exact-equality live `balanceOf` check for a security/liveness-critical trigger. Either:
- Track sold/remaining curve supply in `Bonding`/`Pair`'s own internal state (not `balanceOf`) so it is immune to external donations, or
- Change the supply trigger to `tokenBalance() <= <accounted-for stored value>` / a threshold rather than strict `== 0`, and unconditionally sweep/burn any donated dust as part of every buy (not only at graduation) so `tokenBalance()` never carries unaccounted-for dust past a completed sellout.

### Proof of Concept
1. `Zap.createToken(...)` launches `TOKEN_A` paired with an LT whose exchange rate is expected to stay flat/declining (bear-market condition, no attacker control needed for this half).
2. Attacker acquires 1 wei of `TOKEN_A` (e.g., via the smallest possible `Zap.buy`) and calls `IERC20(TOKEN_A).transfer(pairAddress, 1)` directly on the `Pair` contract — an unrestricted standard ERC20 call reachable by anyone.
3. Legitimate buyers continue purchasing on the curve via `Zap.buy` → `Bonding.buy` → `Router.buy`, driving the real curve-sold balance down. `Router.buy`'s overflow cap (`_computeBuy`) caps `tokensOut` at `pair.tokenBalance()`, but this only limits the maximum sale size — it never zeroes out the attacker's donated wei sitting alongside the legitimately-sold-down balance.
4. Once all legitimately curve-sellable tokens are exhausted, `Pair.tokenBalance()` permanently reports `≥1` due to the donated dust. Combined with the LT's flat/bear exchange rate never crossing the USD threshold, `Bonding.canGraduate(TOKEN_A)` permanently returns `false`.
5. `Bonding.triggerGraduation(TOKEN_A)` reverts with `NotGraduatable` forever; `_enterGraduating`/`finalizeGraduation` are unreachable, permanently stranding the 250M `lpReserve` tokens and all curve-raised LT for `TOKEN_A`.

    ///      `tokensForLP` for zero-gap LP seeding, burns the LP excess.
    ///
    ///      Price equality: `tokensForLP / ltFromPair = tokenReserve / assetReserve`,
    ///      with `ltFromPair = assetReserve - virtualLtReserve` (the LT
    ///      actually raised by the curve, excluding the launch-time virtual
    ///      seed; the seed is recovered as `Pair.k() / TOTAL_SUPPLY`, see
    ///      `_launchTimeVirtualLtReserve`). Substituting gives LP price =
    ///      `assetReserve / tokenReserve` = curve close marginal price.
    ///      Donations of LT directly to the pair don't move the stored
    ///      `assetReserve`, so they're excluded from `ltFromPair`.
    ///
    ///      Token-side donations are handled by `unsoldBurned`: any tokens
    ///      sitting in the pair beyond the curve's accounting are burned.
    ///
    ///      With virtual `tokenReserve = totalSupply` and `curveSupply = 75%`,
    ///      the parabola `tokensForLP(sold) = sold·(S−sold)/S` peaks at
    ///      `S/4 = LP_RESERVE` when `sold = S/2`, so `tokensForLP ≤ LP_RESERVE`
    ///      is mathematically invariant. The cap is defensive.
    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
