### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by verifying an HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers that are never included in the signed payload. `Registry.process` trusts `request.shop` and hands it directly to the app's handler as the tenant identifier, breaking the binding `signed_bytes == acted_on_bytes` for the shop field.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from caller-supplied HTTP headers, with no cryptographic binding to the body: [2](#0-1) .

`HmacValidator.validate` verifies exactly that signable string (the body) against the app's shared `api_secret_key`: [3](#0-2) .

`Registry.process` performs only this body-HMAC check, then immediately constructs `WebhookMetadata` from the *header-derived* `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` and passes it to the app's handler: [4](#0-3) . `WebhookMetadata.shop` is a plain `String` const with no further validation: [5](#0-4) .

Because the `api_secret_key` (the HMAC key) is shared across *all* shops that install the app — it is not per-shop — any body+HMAC pair that is valid for one installation is valid for every installation of the same app. The gem never checks that the header-supplied `shop-domain` corresponds to the shop whose data is actually reflected in the signed body.

Binding that should hold: `hmac_valid(body, secret) ⇒ shop_header == shop_that_produced(body)`. In this implementation, `hmac_valid(body, secret)` only proves "some webhook body for this app was HMAC-signed by Shopify"; it proves nothing about which shop's `shop-domain` header should accompany it. The equality the code implicitly (and incorrectly) assumes is `verified_bytes(body) == acted_on_identity(shop_header)`, but `shop_header ∉ verified_bytes`.

### Impact Explanation
This is a tenant-binding break: a party who can obtain any one legitimately-signed webhook body/HMAC pair for the app (e.g., a merchant who has installed the app themselves and can observe webhooks delivered to their own endpoint, or any party who can capture a body+HMAC in transit) can replay that exact body+HMAC to the victim app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or legacy `x-shopify-shop-domain`) header value naming a different shop. `Registry.process` will accept the HMAC (it only checks the body) and dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop. Any app logic that is keyed off `data.shop` (looking up sessions/tokens, writing per-shop data, triggering shop-scoped side effects, cache invalidation, billing, etc.) can be made to execute attributed to a shop that never actually sent that webhook — a cross-tenant identity-binding violation reachable by an unprivileged actor holding only one valid webhook sample for the shared app secret.

### Likelihood Explanation
Any developer using an app built on this gem receives inbound webhook deliveries whose headers are fully attacker-controllable if the request reaches the handler through anything other than a byte-for-byte trusted channel (and even Shopify's own deliveries pass headers separately from the signed body). No access token, `api_secret_key`, or privileged credential is required by the attacker — they only need one valid body+HMAC pair for the shared app secret, obtainable simply by being a legitimate (even trial) merchant using the same app. This is fully reachable through documented gem usage (`ShopifyAPI::Webhooks::Request.new` + `Registry.process`), not a misuse of an undocumented API.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-signed payload verification, or otherwise cryptographically bind the header-derived `shop` to the specific installation/session before dispatching to the handler (e.g., validate that `shop` corresponds to a shop with a currently valid, stored session/access token for this app, rather than trusting the header value outright). At minimum, document and enforce that `WebhookMetadata.shop` must be cross-checked by the host application against a known/authenticated shop registry before use, or extend `to_signable_string` to incorporate the shop domain into what is hashed.

### Proof of Concept
1. As a merchant with the target app installed on `attacker-shop.myshopify.com`, trigger any webhook event and capture the delivered request: raw body `B`, and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)` and `secret` is the app's single shared `api_secret_key`).
2. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a topic the app has a handler for).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `to_signable_string` (`== B`) against `H`.
4. `Registry.process(request)` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though `victim-shop` never produced this webhook — demonstrating the shop-attribution spoof, matching the finding at [4](#0-3)  and [6](#0-5) .
