### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating the HMAC over the raw request body only, but then hands the `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — to the app's webhook handler as if they were verified. The binding the gem should guarantee is `hmac_valid(body) ⇒ (body, shop) are both authentic`, but what it actually guarantees is only `hmac_valid(body) ⇒ body is authentic`. The `shop` field that host applications use to attribute the webhook to a tenant is never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, independent of the signed content: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` — which internally calls `request.to_signable_string` (the raw body) — and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the HMAC over `verifiable_query.to_signable_string` (the body) and compare against the `hmac` header value — the `shop-domain` header plays no role in this computation at all: [4](#0-3) 

Because the `shop-domain` header is outside the HMAC's coverage, the equality the app relies on — `authenticated_shop == handler_shop` — does not hold. Two requests with the exact same JSON body (and therefore the exact same valid HMAC digest for a given secret) but different `shop-domain` headers will both pass `HmacValidator.validate`, yet be routed to the handler as coming from different shops.

### Impact Explanation
Any application built on top of this gem is instructed to key its data lookups/writes off of `WebhookMetadata#shop` (as documented and demonstrated in the webhook handler tests), because the gem markets this field as verified once HMAC validation passes. Since `shop` is not bound to the HMAC, an attacker who can produce (or capture and replay) any single validly-signed webhook body for one shop can resubmit it with an arbitrary `shop-domain` header value, causing the host app to process/store data under a different tenant's identity — a cross-tenant data integrity issue at the trust boundary this gem is responsible for establishing.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and possession of one validly HMAC-signed webhook body (which is routinely observable since it is delivered to a merchant-controlled, network-reachable URL, and identical generic bodies — e.g., mandatory compliance topics such as `shop/redact` — are broadcast in the same JSON shape to all merchants). No access token, `client_secret`, or privileged account is needed; only the header, which is completely unauthenticated, needs to change.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values inside the string that is HMAC-verified, or otherwise cryptographically bind them to the signed payload, so that `Registry.process` cannot be tricked into associating a validly-signed body with an attacker-chosen shop.

### Proof of Concept
1. Capture (or otherwise obtain) one genuine webhook delivery for topic `shop/redact` — body `B`, header `x-shopify-hmac-sha256: H`, header `x-shopify-shop-domain: victim-shop.myshopify.com`. Since `H = HMAC(secret, B)` and `H` does not depend on the shop header, `H` remains valid for body `B` regardless of the shop header value.
2. Replay the same `raw_body: B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but set `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds, because the shop header is irrelevant to the digest: [4](#0-3) 
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: request.shop, ...)`, where `request.shop` is `"attacker-shop.myshopify.com"`: [5](#0-4) 
5. The host application, trusting the HMAC-validated `data.shop` to attribute the event, processes it under `attacker-shop.myshopify.com`'s tenant context even though the shop header was never part of the authenticated bytes.
