## Custody Analog Found

### Title
Unchecked zero/uncontrolled `to` address in `object::transfer`/`transfer_raw` permanently locks object-held assets outside the safe burn/unburn recovery path - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
The external report flags `EthBridge.depositERC20To` for accepting an unchecked `_to` address, allowing deposits to `address(0)` that can never be retrieved. The Aptos-native analog is in `aptos_framework::object`: the general-purpose ownership-transfer entry points (`transfer`, `transfer_call`, `transfer_raw`, `transfer_with_ref`) accept an arbitrary `to: address` with **no validation** that the destination is a controllable/receivable address. Unlike the framework's dedicated `burn()` path, which explicitly tracks the `original_owner` in a `TombStone` so the object can later be reclaimed via `unburn()`, a direct `transfer`/`transfer_raw` call to an uncontrolled address (e.g. `@0x0`) sets `ObjectCore.owner` to that address with no tombstone and no recovery mechanism.

### Finding Description
`transfer_raw_inner` unconditionally reassigns `object_core.owner = to` with only an ungated-transfer check performed upstream — it never validates that `to` is a real, controllable account or excludes reserved/zero addresses: [1](#0-0) 

Compare this to the module's own designated burn flow, which is aware that losing recoverability is dangerous and therefore records `original_owner` before moving ownership to `BURN_ADDRESS`, and provides `unburn()` to reverse it: [2](#0-1) 

Because `unburn()` only works when a `TombStone` resource exists at the object address, an object whose ownership is moved via the *ordinary* `transfer`/`transfer_call`/`transfer_raw` entry points (rather than through `burn()`) to `@0x0` or any other address nobody can produce a signer for has no path back — `unburn` will abort with `EOBJECT_NOT_BURNT` since no `TombStone` was created: [3](#0-2) 

Any custody-relevant object can be moved this way, including a `FungibleStore` object that holds a fungible-asset balance — `fungible_asset::create_store` returns an `Object<FungibleStore>`, and its balance/withdraw rights are gated purely on `ObjectCore.owner`: [4](#0-3) 

Once such a store's `owner` field is set to `@0x0` via `object::transfer`, only a signer for `@0x0` could satisfy `withdraw_sanity_check`'s owner check, which no ordinary account can produce, permanently freezing the balance.

### Impact Explanation
This breaks the custody invariant that "object creation, transfer, burn, extensibility, and ownership refs must preserve the intended controller" and that custody invariants must hold "across deposit, withdraw, transfer, split, merge, burn, and store-creation paths." A transfer to an uncontrolled address permanently locks the underlying object and any fungible-asset value held in an owned `FungibleStore`, with no tombstone-based recovery, unlike the intentional `burn()`/`unburn()` design. This is a non-recoverable loss of object-held value, directly analogous to the EthBridge zero-address deposit bug where funds became permanently stuck.

### Likelihood Explanation
`object::transfer`, `transfer_call`, and `transfer_raw` are `public entry`/`public` functions callable by any object owner with no privilege beyond owning the object, and `to` is a caller-supplied raw `address` with zero validation. This is trivially triggerable by a mistaken UI/relayer/dApp integration passing a zero or otherwise uncontrolled address (the same class of user error the original EthBridge report was about), making the likelihood of accidental fund loss non-trivial across any application built on top of generic object transfers (including fungible-asset stores).

### Recommendation
Add a validation check in `transfer_raw`/`transfer_raw_inner` (and `transfer_with_ref`) rejecting `to == @0x0` (and ideally any other well-known unspendable/reserved addresses) unless the caller explicitly goes through the `burn()` path that records recoverability via `TombStone`. This preserves the framework's own stated design intent that burning to an unrecoverable address should be an explicit, trackable action rather than an unguarded side effect of a generic transfer call.

### Proof of Concept
1. Account `A` owns a `FungibleStore` object (or any `Object<T>`) with `allow_ungated_transfer = true` holding value.
2. `A` calls `object::transfer_call(A, object_addr, @0x0)` (or the typed `transfer`/`transfer_raw` variants).
3. `transfer_raw_inner` sets `ObjectCore.owner = @0x0` with no `TombStone` created: [5](#0-4) 
4. Any subsequent `fungible_asset::withdraw` call against that store requires a signer whose address equals `@0x0`, which cannot be produced by any user; `object::unburn` also cannot restore it since `exists<TombStone>(object_addr)` is false, permanently locking the value.

    inline fun transfer_raw_inner(object: address, to: address) {
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,
                },
            );
            object_core.owner = to;
        };

    /// Add a TombStone to the object.  The object will then be interpreted as hidden via indexers.
    /// This only works for objects directly owned and for simplicity does not apply to indirectly owned objects.
    /// Original owners can reclaim burnt objects any time in the future by calling unburn.
    /// Please use the test only [`object::burn_object_with_transfer`] for testing with previously burned objects.
    public entry fun burn<T: key>(owner: &signer, object: Object<T>) {
        let original_owner = signer::address_of(owner);
        assert!(is_owner(object, original_owner), error::permission_denied(ENOT_OBJECT_OWNER));
        let object_addr = object.inner;
        assert!(!exists<TombStone>(object_addr), EOBJECT_ALREADY_BURNT);
        move_to(&create_signer(object_addr), TombStone { original_owner });
    }

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
