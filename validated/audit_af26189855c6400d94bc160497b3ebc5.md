### Title
Interest accrual overflows before the borrow-index cap and permanently freezes a whale market - ([File: common/src/rates/simulate.rs])

### Summary
`accrue_step` unconditionally calculates `borrowed * borrow_index` before applying the borrow-index ceiling. For a sufficiently large debt position, sustained interest can push that product beyond `i128::MAX` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, causing every accrual-triggering operation on that market to revert permanently. [1](#0-0) [2](#0-1) 

### Finding Description
Every pool mutation first accrues the market through `interest::global_sync`, which repeatedly calls `accrue_step` for elapsed-time chunks. [3](#0-2)  The first operation inside `accrue_step` is `scaled_to_original(borrowed, borrow_index)`, an `i128`-bounded multiplication. [4](#0-3)  Although `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, the raw debt-share balance can be large enough that `borrowed * borrow_index` overflows well before that cap is reached. [5](#0-4) 

The regression test demonstrates the reachable state: a billion-unit 18-decimal market at 98% utilization eventually makes `update_indexes` return `MathOverflow` while the stored borrow index is still below its configured cap. [6](#0-5)  Afterward, withdrawals and repayments fail because both paths perform the same accrual before their accounting. [7](#0-6) 

### Impact Explanation
Once the product crosses the `i128` boundary, all market operations that synchronize interest become unusable: `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, liquidation settlement, and other market-touching paths cannot proceed. [8](#0-7)  Suppliers cannot withdraw and borrowers cannot repay through the controller’s public `withdraw` and `repay` entrypoints. [9](#0-8)  This permanently freezes funds in the affected market absent a contract upgrade. [3](#0-2) 

### Likelihood Explanation
An unprivileged account can create the preconditions by supplying the borrowable asset, supplying enough collateral in another listed market, and borrowing a very high percentage of that liquidity through `Controller::borrow`. [10](#0-9)  The attack requires a very large token position, a market configuration whose caps permit it, and enough elapsed time for the index to grow into the vulnerable range. [11](#0-10)  These economic and configuration requirements reduce likelihood, but they do not require privileged calls or malformed storage. [10](#0-9) 

### Recommendation
Constrain the index before unscaling debt so that `borrowed.raw() * effective_borrow_index.raw()` cannot exceed `i128::MAX`, or use a wider intermediate representation with an explicit bounded conversion for accrued-interest calculations. [12](#0-11)  In particular, calculate an effective per-market cap such as `min(MAX_BORROW_INDEX_RAY, i128::MAX / borrowed.raw())` before `calculate_supplier_rewards` and `update_supply_index` perform RAY-value multiplication. [13](#0-12)  Add a regression asserting that withdrawal, repayment, and `update_indexes` remain callable at the documented maximum representable market size. [14](#0-13) 

### Proof of Concept
1. Using an unprivileged address, call `Controller::supply` to provide a very large balance of an 18-decimal borrowable asset and sufficient collateral in another listed market. [15](#0-14) 
2. Call `Controller::borrow` for approximately 98% of the supplied borrowable liquidity. [16](#0-15) 
3. Advance ledger time until the borrow index grows enough that `borrowed * borrow_index` exceeds `i128::MAX`, while remaining below `MAX_BORROW_INDEX_RAY`. [2](#0-1) 
4. Call the controller’s `update_indexes` path; `accrue_step` panics during `scaled_to_original` before it can apply the index cap. [1](#0-0) 
5. Subsequent `withdraw` and `repay` calls hit the same accrual panic, leaving the market frozen. [3](#0-2) [7](#0-6)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");

        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
