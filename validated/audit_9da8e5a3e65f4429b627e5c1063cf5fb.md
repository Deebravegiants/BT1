### Title
Webhook HMAC validation does not bind the `shop-domain` header, allowing shop impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body (`to_signable_string` returns `@raw_body`), while the `shop` (and `topic`, `webhook_id`) values are read directly from unauthenticated HTTP headers (`x-shopify-shop-domain`, etc.). `Utils::HmacValidator.validate` only verifies that the body matches the HMAC computed over `to_signable_string` — it never covers the header values. `Webhooks::Registry.process` then trusts `request.shop` as the authoritative tenant identity and forwards it unmodified to the app's handler via `WebhookMetadata`.

### Finding Description
The intended security property is: `shop header used by the handler == shop bound into the cryptographic signature`. In this gem that equality does not hold.

- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it (constant-time) to `verifiable_query.hmac`. [3](#0-2) 
- For `Webhooks::Request`, `to_signable_string` is only `@raw_body`; none of the `shopify-*` headers are included. [2](#0-1) 
- `request.shop`, `request.topic`, and `request.webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC. [7](#0-6) 
- `Registry.process` validates only the body's HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop` header value, handing it to the integrator's webhook handler as the trusted tenant identity. [4](#0-3) 
- The gem's own documentation instructs integrators to treat `data.shop` as "The shop domain of the webhook" — i.e., as an authenticated field they can key business logic and per-tenant lookups on. [6](#0-5) 

Because Shopify signs the webhook body using the app's shared secret and the resulting HMAC is independent of the `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers, an unprivileged attacker who has ever observed one legitimate webhook delivery for *any* shop (e.g., their own development store subscribed to the same app, or a payload leaked via logs/network capture) possesses a `(body, hmac)` pair that remains valid for that body regardless of which shop header accompanies it. The attacker can resend that exact body to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain (and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`). `HmacValidator.validate` still returns `true` because it only checks the body against the secret, and `Registry.process` will happily route the payload to the correct topic handler tagged as if it came from the victim shop.

### Impact Explanation
This breaks the tenant-isolation guarantee webhook consumers rely on: cross-tenant data injection/impersonation. An app that uses `data.shop` to decide which tenant's records to update, uses `data.shop` to look up the `Session`/access token for follow-up API calls, or logs/audits based on `data.shop` can be made to process or attribute attacker-supplied (but Shopify-signed-for-a-different-shop) data as belonging to an arbitrary victim shop. This matches the "Critical - cross-tenant access" category, since the identity binding (`shop` claim to signature) that the gem is expected to enforce for a multi-tenant SaaS app is absent.

### Likelihood Explanation
Requires only that the attacker previously observe one valid `(raw_body, hmac)` pair for the shared app (e.g., from their own installed test shop, which any developer/attacker can install for free) plus the ability to POST to the app's public webhook endpoint with custom headers — both are trivially available to an unprivileged internet user; no `api_secret_key` or access token is required.

### Recommendation
Bind the shop/topic/webhook identity into the signed material, or independently verify that the shop asserted in the header matches an expected/registered shop for the topic before trusting it. At minimum, document (or better, enforce in `Utils::HmacValidator`/`Webhooks::Request`) that `shop`, `topic`, and `webhook_id` headers are unauthenticated and must not be used for tenant-sensitive decisions without additional verification (e.g., cross-checking against the shop present in the parsed body, or requiring integrators to validate the shop is one they have an active installation/session for).

### Proof of Concept
1. App has a webhook handler registered for topic `orders/create` that keys DB writes/API session lookups by `data.shop`.
2. Attacker installs the app on their own store `attacker.myshopify.com`, triggers an `orders/create` webhook, and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(secret, B)`).
3. Attacker also knows/guesses `victim-shop.myshopify.com` (a shop that also uses this app — publicly discoverable via app store reviews, etc.).
4. Attacker crafts a new POST to the app's webhook endpoint with the exact same body `B` and the exact same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` succeeds (only `B` and `H` are checked; see `lib/shopify_api/webhooks/request.rb#L35-L38` and `lib/shopify_api/utils/hmac_validator.rb#L26-L31`), and `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to act on attacker-controlled data under the victim shop's identity.
