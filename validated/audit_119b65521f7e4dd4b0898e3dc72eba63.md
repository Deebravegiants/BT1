### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/utils/hmac_validator.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC of the raw body, then hands the handler a `WebhookMetadata` object built from `shop`, `topic`, `webhook_id`, and `api_version` — none of which are covered by that HMAC. Any actor who can produce one genuinely-signed `(raw_body, hmac)` pair (e.g., by triggering a webhook on their own installed shop) can resend that exact body/HMAC to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop, and the library will report it as an authenticated webhook for the victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string` (i.e., the body) — the `shop`, `topic`, `webhook_id`, and `api_version` values are never part of the signed material: [2](#0-1) 

Yet `Registry.process` treats a successful HMAC check as authenticating the *entire* request, including the shop identity, and forwards `request.shop` (read straight from an attacker-controllable header, `x-shopify-shop-domain`) to the app's handler untouched: [3](#0-2) 

The `shop` header itself is parsed with no cross-check against the signed body: [4](#0-3) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the binding the library implicitly promises is `hmac_verified(shop) == shop_used_by_handler`, but what is actually true is `hmac_verified(raw_body) == raw_body`, while `shop_used_by_handler` is taken from an unauthenticated header.

### Impact Explanation
Because the app's webhook processing pipeline (`Registry.process` → handler) uses the unauthenticated `shop` value to attribute the event, an attacker who is any merchant/installer of the app (or anyone who can capture one legitimate `(body, hmac)` pair — e.g., from their own store's webhook traffic, since the HMAC key is the app's single `client_secret` shared across all tenants) can submit a forged HTTP request directly to the app's public webhook endpoint with a victim's shop domain in the header. The handler will process attacker-controlled event data as if it originated from the victim shop, i.e., cross-tenant data injection/spoofing — matching the Critical impact category "cross-tenant access."

### Likelihood Explanation
The webhook endpoint is a public HTTP route by design (that's the entire point of webhooks), and the library does nothing beyond the body-HMAC check — no IP allowlisting, no nonce/replay protection, and no binding of `shop`/`topic`/`webhook_id` to the signature. Any user capable of installing the app and generating one webhook event (an ordinary, unprivileged action) obtains all they need to forge cross-tenant requests, so likelihood is high wherever an app trusts `WebhookMetadata#shop` for tenant selection, as the documented usage pattern encourages: [5](#0-4) 

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified material, or otherwise require the caller to independently corroborate `request.shop` against the session/shop the request claims to be for before dispatching to handlers, rather than relying on a body-only HMAC to vouch for header-derived identity fields.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook (e.g. `orders/create`), capturing the resulting `raw_body` and `x-shopify-hmac-sha256` value from the real Shopify request.
2. Attacker sends a new HTTP request directly to the app's webhook route with:
   - the same `raw_body` and `x-shopify-hmac-sha256` captured above (still valid since HMAC only covers the body)
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic` matching the same topic
3. `HmacValidator.validate` succeeds because only the body is checked:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
)
```
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on behalf of the victim tenant using attacker-supplied event data.

          received_signature = verifiable_query.hmac

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
