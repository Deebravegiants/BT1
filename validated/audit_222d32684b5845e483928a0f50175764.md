### Title
Unbounded RAY debt valuation overflows before the borrow-index cap and permanently freezes a market - ([File: common/src/rates/index.rs])

### Summary
Accrual multiplies the market-wide scaled debt by the proposed borrow index before applying the `MAX_BORROW_INDEX_RAY` cap or otherwise bounding the resulting debt value. Once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, interest accrual panics, and every pool mutation that synchronizes the market first becomes unusable. [1](#0-0) [2](#0-1) 

### Finding Description
`update_borrow_index` computes `old_index.mul(interest_factor)` and only compares the result with `MAX_BORROW_INDEX_RAY` afterward. [3](#0-2)  `calculate_supplier_rewards` then computes both `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`; the latter multiplication can exceed the `i128` RAY-value domain even when the returned index is still below the nominal index cap. [4](#0-3) 

The documented arithmetic limit confirms this ordering: position and market totals can overflow before the stated index ceiling is reached, blocking repayment and withdrawal because those paths accrue first. [5](#0-4)  The in-repository regression test reproduces the condition with a one-billion-token, 18-decimal market at 98% utilization and demonstrates that the next index update fails below `MAX_BORROW_INDEX_RAY`. [6](#0-5) 

A user can establish the state through ordinary `supply` and `borrow` calls and later invoke controller `update_indexes` for the affected `HubAssetKey`; `update_indexes` loads each market and calls `interest::global_sync`. [7](#0-6) [8](#0-7)  Withdrawals and repayments also route through operations that synchronize and resolve market positions before committing state. [9](#0-8) [10](#0-9) 

### Impact Explanation
This is permanent freezing of user funds rather than a temporary fail-closed condition. After the overflow point, `last_timestamp` is not committed because `global_sync` panics before `mark_accrued` and `Cache::commit`, so every subsequent operation retries the same overflowing accrual. [11](#0-10) [12](#0-11) 

Suppliers cannot withdraw the market’s cash, borrowers cannot repay or be liquidated through the affected market, and ordinary index updates cannot repair the index. [13](#0-12)  Because the panic occurs before index capping, the intended `MAX_BORROW_INDEX_RAY` bound does not provide a recovery or graceful interest cutoff. [14](#0-13) 

### Likelihood Explanation
The trigger is permissionless but requires an exceptionally large market: at 18 decimals, approximately one billion whole tokens produce `1e36` RAY shares, and the `i128` value ceiling is only about 170 times that amount. [15](#0-14)  A sustained high-utilization market can grow the debt index past that multiplier well below the nominal `10^36` borrow-index ceiling. [16](#0-15) 

The attack does not require governance, privileged pool calls, oracle manipulation, token semantics, or a malicious external contract; it requires market configuration and liquidity that admit the necessary scaled totals, followed by permissionless use of `supply`, `borrow`, and `update_indexes`. [7](#0-6) [8](#0-7) 

### Recommendation
Bound index growth against the largest index whose debt valuation remains representable, not only against `MAX_BORROW_INDEX_RAY`. Before calculating supplier rewards, clamp the proposed borrow index to approximately `min(MAX_BORROW_INDEX_RAY, floor(i128::MAX * RAY / borrowed))`, applying the same value-domain ceiling to supply-index calculations. Alternatively, perform debt valuation and reward splitting in an unbounded/widened representation and store only a safely capped result. Add a regression assertion that a market reaching the valuation ceiling continues to permit repayment, withdrawal, liquidation, and index updates instead of trapping during accrual. [1](#0-0) [17](#0-16) 

### Proof of Concept
The existing test constructs the condition and proves the freeze:

1. Create an 18-decimal market and collateral market.
2. Supply `1_000_000_000 * 10^18` base units to the debt market.
3. Supply enough collateral to borrow 98% of that market.
4. Advance ledger time until utilization-driven interest accrual produces a borrow index above roughly `170 * RAY`.
5. Call controller `update_indexes(caller, vec![hub_asset])`; `calculate_supplier_rewards` panics in `borrowed.mul(new_borrow_index)` before the index cap is applied.
6. Subsequent `withdraw` and `repay` calls fail with `MathOverflow` because they must accrue first. [18](#0-17) 

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

t.advance_time(YEAR_SECS);
assert_contract_error(
    t.try_update_indexes_for(&["BIG18"]),
    errors::MATH_OVERFLOW,
);
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The test explicitly records that the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, proving the valuation overflow precedes the intended cap. [19](#0-18)

    borrowed: Ray,
    new_borrow_index: Ray,

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
