### Title
Webhook Shop-Domain Spoofing via HMAC That Only Covers the Body, Not the Routing Header - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes and routes an incoming webhook using `request.shop`, but the HMAC signature verified by `Utils::HmacValidator.validate` only ever covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` (and `topic`/`webhook_id`/`api_version`) values are pulled straight from unauthenticated HTTP headers and handed to the host application's handler as if they were verified. This is the same class of bug as the Sherlock finding: a field that is *acted on* (the tenant-identifying `shop`) is not covered by the cryptographic check that is supposed to bind the whole request together.

### Finding Description
`ShopifyAPI::Webhooks::Request#initialize` builds the request purely from caller-supplied headers and raw body, with no cross-check between them: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body` — none of the headers (`shop`, `topic`, `webhook_id`, `api_version`) are part of the signable string.

`HmacValidator.validate` verifies the HMAC strictly against that signable string: [3](#0-2) 

`Registry.process` then trusts the (unauthenticated) `request.shop` header value to build the metadata delivered to the app's own webhook handler: [4](#0-3) 

Because the same `api_secret_key` is shared by every shop that has the same app installed, and only the raw JSON *body* is bound by the HMAC, any party who can install the app on their own store (an "unprivileged internet user" — no special credentials for the victim tenant needed) can capture a legitimately-signed `body` + `hmac` pair from their own shop's webhook delivery, then replay that exact `body`/`hmac` to the target endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` will still succeed because the HMAC never covered those headers, yet `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body came from the victim shop.

This breaks the identity binding:
`shop value the HMAC actually authenticates (none — only body is signed)` ≠ `shop value the handler/host app treats as authenticated (the header value used for tenant-scoped side effects)`.

### Impact Explanation
Any host application built on `Registry.process`/`Request` that keys tenant-scoped behavior off `data.shop` (e.g., looking up which merchant record to update, crediting orders, updating inventory, writing audit logs, or triggering per-tenant business logic) can be fed attacker-crafted payloads falsely attributed to an arbitrary victim shop that has the same app installed. This is a cross-tenant data-injection/spoofing vector: an attacker with no access to the victim's credentials can cause processing of fabricated events "as" the victim tenant, corrupting or manipulating that tenant's state — squarely in the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's webhook verification as an end-to-end trust boundary (which is the documented, intended usage — see `Registry.process` raising `InvalidWebhookError` solely based on `HmacValidator.validate`). The only prerequisite for the attacker is installing the app on their own (attacker-controlled) shop — a normal, unprivileged action — to obtain a validly-signed body/HMAC pair, and knowledge of the victim shop's `myshopify.com` domain (public information).

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify via Shopify's provided combination, or require the app to independently confirm the `shop` domain is one it has an active session for before trusting webhook-derived data). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant-scoped authorization decisions without additional verification.

### Proof of Concept
1. Attacker creates/installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g. for `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts an HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged, so HMAC stays valid)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (swapped from `attacker-shop.myshopify.com`)
   - Header `x-shopify-topic: orders/create`
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`, per [3](#0-2) .
   - `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the spoofed `victim-shop.myshopify.com`, per [5](#0-4) .
4. The host application's registered handler receives and processes attacker-controlled order data believing it originated from `victim-shop.myshopify.com`, with no cryptographic check having ever bound `shop` to the signed payload.
