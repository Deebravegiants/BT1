### Title
Webhook `shop` field is not covered by HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body [1](#0-0) , while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers without being part of that signable string [2](#0-1) . `Registry.process` validates the HMAC over the `Request` object and, if it passes, dispatches the handler using `request.shop` taken straight from the header [3](#0-2) .

### Finding Description
This mirrors the reported analog class: "a field acted on but not covered by the HMAC." The equality that should hold is:
`bytes_covered_by_HMAC == bytes_the_application_trusts_for_tenant_identity`

Here that equality is broken:
- `to_signable_string` = `@raw_body` only [1](#0-0) 
- `shop` = `shopify_header("shop-domain")`, an independent, attacker-controllable header not included in the signed bytes [4](#0-3) 

`HmacValidator.validate` only checks that `hmac` matches `HMAC(secret, to_signable_string)` [5](#0-4) . Since `to_signable_string` is just the raw body, an attacker who possesses any single valid `(raw_body, hmac)` pair signed by the app's real secret (e.g., by triggering a webhook on their own, attacker-owned shop, which is a normal, unprivileged action) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true` because the HMAC only binds the body, not the shop header. `Registry.process` then invokes the merchant's webhook handler with `WebhookMetadata` carrying the forged `shop` value [6](#0-5) , causing the host application to process (and typically persist/act on) data under the identity of a shop the attacker does not own.

### Impact Explanation
This breaks the tenant-identity binding that webhook consumers rely on: a valid HMAC is treated as proof that "this event body belongs to this shop." Because the `shop` header is unauthenticated, an attacker can force an application to attribute a legitimately-signed payload to an arbitrary victim shop, resulting in cross-tenant data confusion/injection (e.g., a webhook handler that updates local records keyed by `shop` would apply attacker-supplied body data to the victim shop's records). This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is Medium-High: no privileged credentials are required. Any developer can freely install an app or generate real webhook traffic from a shop they control to obtain a valid `(raw_body, hmac)` pair, then replay it with a different `shop-domain` header value to the same public webhook endpoint. This is a purely internet-facing endpoint with no additional authentication beyond the HMAC that this gem itself provides.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in `to_signable_string`, or otherwise cryptographically bind them to the payload before verifying the HMAC, so a valid signature can only be replayed for the exact shop, topic, and body it was issued for. Alternatively, require the handler layer to independently authenticate/authorize the `shop` value (e.g., cross-check against a known installed-shop registry) before trusting it to act on tenant-specific data.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and has installed the target app, so Shopify sends the attacker a real webhook: `raw_body = '{"id":1,...}'`, header `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body>`.
2. Attacker resends the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint but changes the header to `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present) [7](#0-6) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches, so validation passes [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop [9](#0-8) .

        end

      end
