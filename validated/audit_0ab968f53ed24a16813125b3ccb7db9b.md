Audit Report

## Title
Unbounded, linearly-scanned `allowListedRequests` slice causes DoS on Vault gateway request authorization - (File: `core/capabilities/vault/allow_list_based_auth.go`, `core/services/workflows/syncer/v2/workflow_registry.go`)

## Summary
Every incoming Vault gateway request is authorized via `allowListBasedAuth.findAllowlistedItemWithRetry`, which fetches a full copy of the in-memory `allowListedRequests` slice and linearly scans it, retrying up to 10 times with a 3-second sleep between attempts. [1](#0-0)  This slice is populated by `syncAllowlistedRequests` from the on-chain `WorkflowRegistry`, appending new entries with no upper bound and only pruning by (attacker-controlled) expiry, and the test suite confirms the syncer accepts and stores well beyond the per-query pagination cap (1,001+ entries) without any application-level limit. [2](#0-1) [3](#0-2) 

## Finding Description
`GetAllowlistedRequests` copies and returns the entire in-memory slice on every call, and `fetchAllowlistedItem`/`findAllowlistedItemWithRetry` performs a linear scan over this copy up to 11 times per incoming request (once per retry). [4](#0-3) [5](#0-4)  There is no map-based/indexed lookup keyed by request digest and no cap on the number of entries a linked owner may register on-chain — the fetch path only paginates in chunks of `MaxResultsPerQuery` (1,000) but does not bound the total count. [6](#0-5) 

However, calling `AllowlistRequest` on the `WorkflowRegistry` contract is not available to a fully unauthenticated/unprivileged actor: the test helpers consistently require the caller to first complete `LinkOwner`/`requireVaultLinkOwner` (a signed ownership-proof linking step) before `AllowlistRequest` succeeds. [7](#0-6) [8](#0-7)  The exact on-chain access-control logic for `AllowlistRequest` (e.g., whether it is restricted to the caller's own linked-owner identity, requires per-DON-family authorization, or has any per-owner rate/count limit) lives in the Solidity contract source, which was not found in the indexed codebase (only the Go bindings/wrappers and deployment/test helpers were located). This is a material gap: the claim's likelihood assessment hinges on how cheap/permissionless it is for an attacker to become a "linked owner" and repeatedly call `AllowlistRequest`, and that access-control surface could not be verified from what's indexed.

## Impact Explanation
If growth of `allowListedRequests` is indeed feasible by a normal (non-admin) linked owner without any on-chain rate limit, then the per-request authorization cost (copy + linear scan, up to 11× per request) would scale with total list size across every Vault DON node, degrading `HandleGatewayMessage` latency for `secrets.create/update/delete/list` for all users and risking gateway-side `RequestTimeoutError`. [9](#0-8) [10](#0-9)  This is a real architectural weakness in the code that was reviewed (unbounded collection scanned in a hot path), and it does map to an in-scope DoS/availability impact category if the on-chain preconditions are as cheap as claimed.

## Likelihood Explanation
Likelihood cannot be conclusively assessed to be "moderate-to-high" without visibility into the WorkflowRegistry Solidity contract's access control and any per-owner/per-DON constraints on `AllowlistRequest` (rate limits, fees, or maximum active entries), since that contract source was not retrievable from the index. The linking step required before allowlisting (`LinkOwner` with a signed ownership proof) suggests this is not available to a fully anonymous/unauthenticated caller, but "linked owner" may still be attainable by any address holding an EVM key, which is a low bar. Without confirming the absence of any protocol-level cap or cost multiplier in the contract, the severity/likelihood claimed in the original report cannot be fully corroborated from the indexed codebase — the Go-side data-structure inefficiency (linear scan, no cap) is real, but the on-chain gating that determines actual exploitability by an "unprivileged" party is unverified.

## Recommendation
- Verify (in the Solidity `WorkflowRegistry` contract, not available in this index) whether `AllowlistRequest` has any per-owner cap, fee, or rate limit; if none exists, add one.
- Replace the linear `fetchAllowlistedItem` scan with an O(1) lookup (e.g., `map[[32]byte]*WorkflowRegistryOwnerAllowlistedRequest` keyed by `RequestDigest`) built once per sync tick in `syncAllowlistedRequests`, rather than copying and linearly scanning the full slice inside `AuthorizeRequest`.
- Cap the maximum number of active allowlist entries retained in memory, and/or decouple the "wait for propagation" retry loop from repeated full re-scans.

## Proof of Concept
Not independently reproducible from the indexed codebase because the on-chain access-control/rate-limit logic for `AllowlistRequest` could not be located (only Go bindings and system-test helpers were indexed, not the `.sol` source). The Go-side inefficiency (`findAllowlistedItemWithRetry` linear scan + `GetAllowlistedRequests` full copy, `syncAllowlistedRequests` unbounded append) is verifiable directly, but confirming end-to-end exploitability by an unprivileged actor requires reviewing the contract's `AllowlistRequest`/`LinkOwner` permission model, which is outside what could be found here. Recommend starting a Devin session with full repository/filesystem access to inspect the Solidity `WorkflowRegistry` contract before treating this as a confirmed, exploitable-by-unprivileged-actor DoS.

func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)
			w.allowListedRequests = activeAllowlistedRequests
			w.lastSeenAllowlistedRequestsCount = totalAllowlistedRequests
			w.lggr.Debugw("synced allowlisted requests",
				"newRequestsNum", len(newAllowListedRequests),
				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()
		}
	}
}

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
