Confirmed. The gem's documentation explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and delivers `data.shop` to the app's handler as the trusted tenant identifier [2](#0-1) , but the actual HMAC computation only covers the raw body, not the `shop-domain` header.

### Title
`Webhooks::Request` HMAC verification excludes `shop-domain`/`topic`/`webhook_id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated ("did indeed come from Shopify") purely on the basis of `Utils::HmacValidator.validate(request)` succeeding [3](#0-2) . But the HMAC signature only signs the raw HTTP body — it never covers the `shop-domain`, `topic`, `webhook_id`, or `api_version` headers that are subsequently trusted and handed to the app's handler as the identity of the shop that generated the event.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [4](#0-3) , and `HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) using the app's `client_secret` [5](#0-4) . Meanwhile, `Request#shop`, `#topic`, and `#webhook_id` are all read directly from HTTP headers with zero cryptographic binding to the signed body [6](#0-5) .

`Registry.process` validates only the HMAC, then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` fields and dispatches it to the app-registered handler [3](#0-2) .

This breaks the intended identity binding: `HMAC(body, client_secret) == received_signature` should imply `(body, shop) is authentic`, but the implementation only proves `HMAC(body, client_secret) == received_signature` for `body` alone — `shop` (and `topic`/`webhook_id`) float free of the signature. Since a single app's `client_secret` is shared across every shop that installs the app, any shop that legitimately receives a webhook for its own tenant obtains a `(body, valid_hmac)` pair signed with the same secret used for all other installs of that app. That merchant (an otherwise unprivileged holder of a legitimate install, with no access to another merchant's credentials or access token) can replay the identical body+HMAC to the app's webhook endpoint while swapping only the `shop-domain` header to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the header [7](#0-6) , and `Registry.process` forwards attacker-chosen `shop` to the handler as if Shopify itself vouched for it [8](#0-7) .

### Impact Explanation
Any app built on this gem that uses `data.shop` from the webhook handler to select which tenant's records to read, write, or key by (exactly as shown in the gem's own documented example, which passes `data.shop` straight into `shop_domain:` for background processing) can be tricked into applying a legitimate merchant's own webhook payload under a different, attacker-chosen shop domain [9](#0-8) . This is a cross-tenant identity-binding break consistent with the report's bug class: "a field acted on but not covered by the HMAC."

### Likelihood Explanation
Exploitation requires only that the attacker (1) operate their own legitimate install of the target app (any merchant can install most public apps) so they receive real, validly-signed webhooks for their own shop, and (2) be able to send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header — no secrets, tokens, or privileged access are needed beyond what any customer of the app already has.

### Recommendation
Bind the shop/topic/webhook identity into the signed material verified by `HmacValidator`, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it in `Registry.process`, rather than relying solely on the body HMAC while treating header-derived fields as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, causing Shopify to send a legitimate webhook: body `{"id":123,...}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays this exact body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the app's shared `client_secret` [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, and performs tenant-scoped actions (e.g., enqueuing a background job keyed by `shop_domain: data.shop`) against the victim tenant [8](#0-7) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
