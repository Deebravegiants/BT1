Confirmed: `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`, line 190) only calls `Utils::HmacValidator.validate(request)`, which only checks `request.hmac` against `request.to_signable_string` (the raw body) — never against `shop`, `topic`, or `webhook_id`. The `shop`, `topic`, and `webhook_id` values are read straight from headers and forwarded unchecked to the handler.

### Title
Webhook `shop`, `topic`, and `webhook_id` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the merchant-identifying `shop`, `topic`, and `webhook_id` fields are taken directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values to route and label the payload passed to the app's handler, without verifying that Shopify actually signed that specific `(shop, topic, body)` combination.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature exclusively to `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic tie to the signature: [3](#0-2) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the raw body) with the shared secret — it never touches headers: [4](#0-3) 

`Registry.process` performs only this body-signature check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` object passed to the app's handler: [5](#0-4) 

The binding the gem should guarantee is: `hmac_valid(secret, raw_body) == true` implies `(shop, topic, webhook_id, raw_body)` was exactly what Shopify sent. In reality the equality only holds for `raw_body`; `shop`, `topic`, and `webhook_id` are outside the HMAC's domain. Any party who can obtain one validly-signed webhook body+HMAC pair from Shopify (e.g., by installing the app on their own development/partner store and receiving a legitimate webhook, since the `api_secret_key` is shared across all shops using the app) can replay that same body and HMAC to the app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values. `Registry.process` will still accept it, because the signature check never examined those headers, and will invoke the handler for the (attacker-chosen) topic claiming it originated from an (attacker-chosen) shop.

### Impact Explanation
This breaks the identity binding the host application relies on: the shop and topic used to route/authorize the webhook are not the shop and topic Shopify actually signed. A host application that uses `data.shop` from `WebhookMetadata` to select which tenant's data to update (a documented, expected usage pattern of this gem) can be made to apply an attacker-controlled body under a different shop's identity, or relabel a payload as a different topic than the one that was actually signed — a cross-tenant confusion condition. This satisfies the Critical impact category of cross-tenant access.

### Likelihood Explanation
Exploitation requires no possession of the `api_secret_key`, access token, or any privileged credential — only the ability to install the app on any shop (including a free development store) to receive one legitimately HMAC-signed webhook delivery, and then replay it with modified headers to the same public webhook endpoint. This is achievable by any unprivileged internet user who can install the target Shopify app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. via a separate signature covering headers+body), so that `Utils::HmacValidator.validate` fails whenever any of these fields is altered independently of the body.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker-shop.myshopify.com` and subscribe to webhook topic `orders/create`.
2. Capture a legitimate webhook delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid per `Utils::HmacValidator.validate`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Replay the exact same body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com` and/or `x-shopify-topic` to a different registered topic (e.g. `customers/update`).
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against `H`.
5. The registered handler for the spoofed topic is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` and the attacker-supplied body/topic, even though Shopify never signed that combination.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
