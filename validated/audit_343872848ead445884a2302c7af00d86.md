### Title
`ConnectedOrigins.getConnectedAccounts()` Leaks Addresses of All Wallet Accounts to Any Trusted Origin, Ignoring Per-Origin Account Scoping - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins.add()` accepts a `walletAccount` parameter meant to scope a dApp connection to a specific wallet account, and persists it on the origin record [1](#0-0) . However, `getConnectedAccounts()` never reads or filters by that stored `walletAccount` field — it unconditionally returns addresses for every account in `connectedAccountsAtom` (effectively every enabled wallet account) for any trusted origin [2](#0-1) . This mirrors the reported `VaultRouter.setMarket()` bug class: a caller-supplied scoping argument is accepted and stored, but a different/broader internal state variable (`connectedAccountsAtom`, populated from `enabledWalletAccountsAtom`) is used in the actual authorization-relevant computation, silently collapsing an intended one-per-origin (or restricted-list) relationship into a "same shared account set for everyone" relationship.

### Finding Description
When a dApp connects via `connectedOrigins.add({ origin, walletAccount, ... })`, the intention conveyed by the `walletAccount` field is that the origin's connection is scoped to that account [3](#0-2) . But `getConnectedAccounts({ origin })` only checks `isTrusted({ origin })` and then builds its result set by iterating over `Object.keys(accounts)` from `#connectedAccountsAtom.get()`, which is populated by `#getAccounts()` over *all* `enabledWalletAccountsAtom` entries, not filtered by the origin's `walletAccount` value [4](#0-3) [5](#0-4) . As a result, the stored per-origin `walletAccount` scoping field is dead data with respect to the account-disclosure path — exactly analogous to `VaultRouter.setMarket()` overwriting the caller-supplied `vault` with the global `coreVault`, causing all registered entities to collapse onto one shared resource regardless of the argument passed in.

### Impact Explanation
Any origin that becomes `trusted` (via `connectedOrigins.add(...)` / auto-approve flows) can retrieve addresses (for all asset names it has been granted, `connectedAssetName`/`assetNames`) belonging to *every* enabled wallet account in the wallet, not just the account(s) the user intended to expose to that origin. This is a cross-account privilege bleed: information (addresses) belonging to unrelated wallet accounts is disclosed to a dApp/origin that was never explicitly connected to those accounts, undermining the wallet's multi-account isolation model documented for `WalletAccount`s and the connected-origins feature.

### Likelihood Explanation
This does not require any special/privileged access — it triggers on the standard `getConnectedAccounts({ origin })` code path invoked whenever a trusted dApp requests connected accounts, which is a routine, unprivileged web3/dApp interaction [6](#0-5) . Existing unit tests only exercise scenarios where a single wallet account set is active and do not assert per-origin `walletAccount` filtering, so the gap is not caught by current test coverage [7](#0-6) .

### Recommendation
Determine the intended relationship: if a connection should be scoped to the specific `walletAccount` stored on the origin record, `getConnectedAccounts()` must filter `accounts` down to that `walletAccount` (and any explicitly-approved additional accounts) instead of returning every entry from `#connectedAccountsAtom`. If multiple accounts per origin are intentionally supported, an explicit list of authorized wallet accounts per origin must be maintained and enforced in `getConnectedAccounts()`, rather than relying on the global enabled-accounts set.

### Proof of Concept
1. User connects `wallet_A` to `evil.com` via `connectedOrigins.add({ origin: 'evil.com', walletAccount: 'wallet_A', connectedAssetName: 'ethereum', trusted: true })`.
2. User has additional wallet accounts `wallet_B`, `wallet_C` enabled in `enabledWalletAccountsAtom` for personal, unrelated purposes.
3. `evil.com` calls the exposed `connectedOrigins.getConnectedAccounts({ origin: 'evil.com' })` RPC.
4. Per `getConnectedAccounts()` [8](#0-7) , the origin only being trusted (not scoped to `wallet_A`) results in the response including addresses for `wallet_A`, `wallet_B`, and `wallet_C` — disclosing addresses of accounts the user never connected to `evil.com`.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
