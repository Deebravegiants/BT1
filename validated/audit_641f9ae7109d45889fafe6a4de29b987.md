## Title
Webhook `shop-domain`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, but `to_signable_string` — the value that `Utils::HmacValidator` actually verifies against the `hmac-sha256` header — returns only `@raw_body`. Any attacker who obtains one genuinely-signed `(body, hmac)` pair (e.g. by installing the app on their own shop and triggering a webhook) can resend that exact body/HMAC pair with an arbitrary `shopify-shop-domain` header, and the gem will accept it as authentic and attribute the event to a victim shop of the attacker's choosing.

### Finding Description
`Webhooks::Registry.process` authenticates a webhook solely via: [1](#0-0) 

`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` accessor: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no HMAC coverage: [3](#0-2) 

The equality that should hold is:

`shop authenticated (bound into the HMAC signature) == shop the handler acts on (`request.shop`, taken from the `shopify-shop-domain` header)`

Because the header is not part of `to_signable_string`, this equality is broken: the HMAC only proves "this body was signed with the app's secret for *some* event," not "this body belongs to *this* shop." `Registry.process` passes `request.shop` straight into the handler's `WebhookMetadata` without any additional binding check: [1](#0-0) 

This is directly analogous to the reported `EnsureClosure` bug class: a piece of state (the third vertex / here, the shop-identifying header) that participates in the trust decision is not actually covered by the check that is supposed to bind it (the vertex's `homSet`/`homs` state / here, the HMAC signature), so a downstream consumer treats it as verified when it is not.

### Impact Explanation
An attacker who legitimately installs the app on their own shop (a normal, unprivileged install — no leaked credentials or `api_secret_key` needed) can trigger a webhook for a topic the app has registered, capturing a valid `(raw_body, hmac-sha256)` pair signed with the app's real `api_secret_key`. They can then POST that identical body and HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers with a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the raw body, and the host application will process attacker-controlled webhook data under the victim shop's identity — a cross-tenant data-integrity/confusion issue (e.g. forging `orders/create`, `app/uninstalled`, or GDPR-topic events as if they came from a shop the attacker never controls).

### Likelihood Explanation
Likelihood is Low/Moderate: it requires the attacker to be an app-installing merchant able to trigger a webhook for themselves (a low bar for public apps) and to know/guess a victim shop's `.myshopify.com` domain (which is generally public/discoverable). No secret key or privileged access is required, satisfying the "unprivileged internet user" bar. The impact (cross-tenant confusion of webhook-driven state) is High.

### Recommendation
Bind the identifying fields into the signed payload verification, e.g., have `Webhooks::Request#to_signable_string` incorporate `shop`, `topic`, and `webhook_id` alongside the raw body (or otherwise cryptographically bind them), so that a captured `(body, hmac)` pair cannot be replayed under a different shop/topic/webhook context. At minimum, document/enforce that host applications must cross-check `request.shop` against a shop they have an active session/install record for before trusting the webhook payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a registered webhook topic (e.g. `orders/create`), capturing the raw body `B` and the resulting `shopify-hmac-sha256` header value `H` (both legitimately produced by Shopify using the app's real `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with:
   - body `B`
   - `shopify-hmac-sha256: H`
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload was never generated by or for that shop, per [4](#0-3) .
