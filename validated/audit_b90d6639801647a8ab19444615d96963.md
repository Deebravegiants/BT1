Confirmed: `Registry.process` builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, all of which come from unauthenticated HTTP headers, while `HmacValidator.validate(request)` only verifies `request.to_signable_string`, which returns solely `@raw_body`.### Title
Webhook shop-tenant identity spoofing via HMAC that covers only the raw body, not the shop-domain header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) and other dispatch metadata (`topic`, `webhook_id`, `api_version`) from unauthenticated HTTP headers, while `to_signable_string` — the value actually protected by HMAC — returns only the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant key passed to the app's `WebhookHandler`. This breaks the identity binding `authenticated_bytes == identity_used_by_app`, since the shop header is never covered by the signature.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` gates only on this body-HMAC check, then builds `WebhookMetadata` — passed to the app's handler as the trusted tenant/session identity — directly from `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) [5](#0-4) 

Because the HMAC secret (`api_secret_key`) is scoped to the **app**, not to an individual shop, any merchant who installs the app receives genuinely-signed webhook deliveries (valid `hmac` over some body) for their own store. Since the header fields are outside the signed payload, that same valid `(body, hmac)` pair can be replayed by the attacker directly against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped to a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will dispatch to the handler with `data.shop` equal to the attacker-chosen victim domain and attacker-controlled `data.body`.

This is the "bytes verified versus bytes parsed" / "shop authenticated versus shop stored as identity key" analog: the equality that should hold is `verified_bytes ⊇ identity_used_downstream`, but here `verified_bytes = raw_body` while `identity_used_downstream = header["shop-domain"]`, and these are disjoint.

### Impact Explanation
Any app built on this gem that uses `data.shop` from `WebhookMetadata` to key persistence, trigger per-tenant business logic, or attribute incoming data to a specific merchant session is exposed to cross-tenant data/state confusion: an attacker (a legitimate but malicious app installer on their own store) can inject attacker-controlled webhook payloads that the app will process as if they originated from an arbitrary victim shop domain that also has the app installed. This satisfies the "cross-tenant access" criterion under the Critical impact tier, since the app's trust boundary between tenants is bypassed using only the app-wide (not shop-specific) HMAC secret that the attacker legitimately possesses via their own installation's webhook deliveries.

### Likelihood Explanation
Medium-to-High. No special access beyond installing the app on an attacker-controlled store (a standard unprivileged action) is required to obtain a valid `(body, hmac)` pair. The webhook endpoint is by design internet-reachable (Shopify must be able to POST to it), so replaying a captured payload with a modified `shop-domain` header is a simple HTTP request forgeable by anyone who can install the app once.

### Recommendation
Bind the header-derived identity fields into the signed payload verification, e.g. include `shop`, `topic`, and `webhook_id` in the HMAC-protected value (or use a per-shop/session-bound secret / require that the resolved shop match a known, previously-authorized session before trusting `data.shop`). At minimum, document and enforce that consumers must independently verify `data.shop` against their own session store rather than treating it as trusted, and consider signing over `headers + body` rather than body alone.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook delivery, e.g. for `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `api_secret_key` over `B`).
2. Attacker sends a forged HTTP POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged, so `H` is still a valid HMAC over the body)
   - Header `X-Shopify-Hmac-Sha256: H`
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (swapped)
   - Header `X-Shopify-Topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `HmacValidator.validate(request)` recomputes HMAC over `@raw_body` (still `B`) and succeeds via `OpenSSL.secure_compare`.
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` to the app's handler, which will process/store the attacker's payload `B` under the victim shop's tenant context.
