### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC, but the HMAC only covers the raw request body — not the `shop-domain` header that is subsequently trusted as the tenant identity for the webhook payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` + `to_signable_string`. Its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats HMAC success as full authentication of the request, then forwards the *unauthenticated* `shop` header straight to the app's handler: [4](#0-3) 

The identity binding that should hold is: `HMAC-verified bytes == shop attribution used by the handler`. In fact the equality is broken: `HMAC` verifies only `raw_body`, while `shop` (and `topic`/`webhook_id`) come from headers outside that MAC. Any party who can obtain one legitimately-signed webhook body/HMAC pair for their own shop's tenant (e.g., an unprivileged Shopify shop owner installs the app and receives a real webhook for their own store) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim shop). `HmacValidator.validate` will still return `true` because it only checks the body against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the attacker-chosen `shop`.

### Impact Explanation
This crosses a tenant boundary: an attacker who controls one legitimate (even their own, free-trial) shop's webhook traffic can impersonate any other shop for webhook processing purposes, because `shop` is unauthenticated relative to the signature that gates trust. Depending on how the host application uses `WebhookMetadata#shop` (order fulfillment status, customer PII redaction requests, shop deauthorization triggers, `shop/redact` mandatory topic, etc.), this enables cross-tenant data corruption or disclosure driven entirely from this gem's own trust decision (`Registry.process` accepting HMAC-body-only validation as proof of shop identity).

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one valid `(body, hmac)` pair signed with the app's `api_secret_key` — which is achievable by installing the app on the attacker's own store and capturing its own legitimate webhook deliveries (no leaked secrets or privileged access required), then replaying the exact bytes to the public webhook endpoint with a forged `shop-domain` header. No TLS interception or credential theft is needed.

### Recommendation
Include the shop domain (and topic/webhook id) in the HMAC-signed material, or independently verify that the `shop` header corresponds to a shop that this specific webhook subscription actually belongs to (e.g., cross-check against the shop that owns the given `webhook_id`/subscription) before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's secret), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the *same* body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H` → returns `true`.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host app processes attacker-controlled data as if it originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
