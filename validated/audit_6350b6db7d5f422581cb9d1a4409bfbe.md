### Title
`destinationTx[i]` in batched `processWithdrawal` can report the wrong withdrawal's outcome when two withdrawals share the same `assetId` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the status/txHash for withdrawal index `i` by calling `findMatchingWithdrawal`, which matches purely on `assetId` (via `near_token_id`), ignoring `WithdrawalIdentifier.index`, `amount`, and `destinationAddress`. When a batched `processWithdrawal` call contains two or more withdrawals with the same `assetId` but different `amount`/`destinationAddress`, `destinationTx[i]` can reflect a different withdrawal's on-chain outcome (or repeatedly resolve to the same record for multiple indices), breaking the STATUS TRUTH invariant `(status, txHash)[i] == outcome of withdrawal[i]`.

### Finding Description
The claimed equality is: `destinationTx[i].hash == on-chain result of signed withdrawal[i]` for every `i` in a batch produced by `IntentsSDK.processWithdrawal`.

Trace:
- `processWithdrawal` (packages/intents-sdk/src/sdk.ts:793-857) signs and settles a batch of `withdrawalParams`, then calls `waitForWithdrawalCompletion` → `createWithdrawalCompletionPromises` (sdk.ts:557-609), returning an array of promises, one per index, resolved via `watchWithdrawal`.
- `createWithdrawalIdentifiers` (packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107) assigns each withdrawal an `index` per bridge route via `bridge.createWithdrawalIdentifier` (poa-bridge.ts:295-311), so `WithdrawalIdentifier.index` does carry the correct per-item index.
- `watchWithdrawal` (withdrawal-watcher.ts:20-78) calls `bridge.describeWithdrawal({...args.wid, ...})` (poa-bridge.ts:313-343), which is the only place the on-chain result is looked up.
- `describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (poa-bridge.ts:317-322, 409-427), and the matcher does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — **it uses only `assetId`**, never `index`, `amount`, or `destinationAddress`. The `.find()` call returns the *first* array element matching that `assetId`, regardless of which withdrawal (by amount/destination) it actually corresponds to.
- The identical bug exists in the parallel implementation `findMatchingWithdrawal` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153`, with an explicit code comment acknowledging it: "NOTE: Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported."

Attacker/trigger: An unprivileged caller (or an integrator forwarding attacker-controlled `withdrawalParams`, e.g., a counterparty-supplied `assetId`/`destinationAddress`) simply submits a batched `processWithdrawal` call with two withdrawal items that share the same `assetId` but differ in `amount` and/or `destinationAddress`. No special privilege or contract misuse is required — this is standard batch usage of the public SDK API.

Existing guards do not prevent this: `validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, and `FeeExceedsAmountError` all operate on withdrawal *creation/signing*, not on the *status-matching* step; none of them re-validate that the returned `destinationTxHash`/status for index `i` corresponds to withdrawal `i`'s specific `amount`/`destinationAddress`. The `WithdrawalIdentifier.index` field is computed correctly upstream but is never consumed by the matching logic (`findMatchingWithdrawal` never reads `.index`), so the safeguard exists in data but is not wired into the matching function.

### Impact Explanation
This is a status/hash misreport: the caller-visible `BatchWithdrawalResult.destinationTx[i]` (and the single-mode `destinationTx` returned from `processWithdrawal`) can report the txHash/completion status belonging to a *different* withdrawal in the same batch when two batch items share an `assetId`. An integrator that credits or refunds users per-index based on `destinationTx[i]` (e.g., "withdrawal 0 completed to hash X, therefore mark user A's withdrawal as done") could attribute the wrong outcome to the wrong user — e.g., marking user A's withdrawal complete based on user B's transfer, or vice versa. This matches the High severity category "a status or hash misreport making an integrator credit or refund twice" (or credit the wrong party). It is repeatable on every batched call containing same-`assetId` items and requires no special permissions — just constructing a batch with a repeated `assetId`.

### Likelihood Explanation
Preconditions: the batch must use the PoA bridge route (or InternalTransfer route, using the same shared `findMatchingWithdrawal` pattern) and contain ≥2 withdrawals with identical `assetId`. This is an entirely ordinary usage pattern (e.g., batch-processing multiple users' withdrawals of the same token), so likelihood is high for any integrator that batches withdrawals of a popular token. No special attacker cost: any caller who can invoke `processWithdrawal`/`waitForWithdrawalCompletion` with a same-token batch triggers it; it is fully repeatable and doesn't depend on race conditions beyond the POA API returning items in an order/composition that doesn't align 1:1 with request order (which the code's own comments admit is unsorted and ambiguous).

### Recommendation
Extend the POA withdrawal-status matching to disambiguate same-`assetId` withdrawals within a batch, e.g., by matching on `(assetId, amount, destinationAddress)` tuple, or — if the POA API doesn't expose per-request identifiers — sort both the local withdrawal params and the API's returned withdrawals by `amount` (as the existing code comment already suggests) before pairing them positionally, and consume `WithdrawalIdentifier.index` to enforce a stable pairing. At minimum, throw/flag an explicit `UnsupportedBatchWithdrawalError` when a batch contains duplicate `assetId` entries routed through PoA bridge, rather than silently returning a result that can be misattributed.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}

	async processWithdrawal(
		args: ProcessWithdrawalArgs<WithdrawalParams | WithdrawalParams[]>,
	): Promise<WithdrawalResult | BatchWithdrawalResult> {
		const withdrawalParams = Array.isArray(args.withdrawalParams)
			? args.withdrawalParams
			: [args.withdrawalParams];

		// Step 1: Estimate fee
		const feeEstimation = await (() => {
			if (args.feeEstimation != null) {
				return Array.isArray(args.feeEstimation)
					? args.feeEstimation
					: [args.feeEstimation];
			}

			return this.estimateWithdrawalFee({
				withdrawalParams,
				logger: args.logger,
			});
		})();

		// Step 2: Sign and send intent
		const { intentHash } = await this.signAndSendWithdrawalIntent({
			withdrawalParams,
			feeEstimation,
			referral: args.referral,
			intent: args.intent,
			logger: args.logger,
		});

		args.logger?.info("Intent published", { intentHash });

		// Step 3: Wait for intent settlement
		const intentTx = await this.waitForIntentSettlement({
			intentHash: intentHash,
			logger: args.logger,
		});

		args.logger?.info("Intent settled", { txHash: intentTx.hash });

		// Step 4: Wait for withdrawal completion
		const destinationTx = await this.waitForWithdrawalCompletion({
			withdrawalParams,
			intentTx,
			logger: args.logger,
		});

		if (!Array.isArray(args.withdrawalParams)) {
			return {
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				feeEstimation: feeEstimation[0]!,
				intentHash,
				intentTx,
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				destinationTx: destinationTx[0]!,
			};
		}

		return {
			feeEstimation,
			intentHash,
			intentTx,
			destinationTx,
		};
	}
