### Title
Global (unscoped) `requestID` keyspace in the HTTP trigger gateway handler lets one workflow's in-flight request block or spoof rejection of an unrelated workflow's request - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The gateway's `httpTriggerHandler` deduplicates in-flight HTTP-trigger requests using a single map keyed only by the client-supplied JSON-RPC `requestID`, with no workflow or owner scoping. Any unprivileged caller can trigger a spurious `ErrConflict` failure for a completely unrelated workflow's legitimate request simply by using the same `requestID` while that other request is in flight — the same root-cause pattern as the reported "excessive `require`" bug, where a check meant to apply to a specific condition (or tenant) is applied globally and causes unrelated, otherwise-valid transactions/requests to fail unexpectedly.

### Finding Description
`HandleUserTriggerRequest` validates and authorizes a trigger request per-workflow (via `authorizeRequest`, which checks the caller's JWT against the specific `workflowID`), then calls `setupCallback`: [1](#0-0) 

`setupCallback` stores the callback in `h.callbacks`, a map declared as `map[string]savedCallback // requestID -> savedCallback`: [2](#0-1) 

The key is `requestID`, which is the raw client-supplied JSON-RPC `req.ID` — there is no workflow ID, workflow owner, or org scoping baked into the key. Since `requestID` is fully attacker-controlled and the map is shared across all workflows served by this DON/shard, two different, unrelated workflows (owned by different, unrelated users) that happen to submit the same `requestID` concurrently will collide: the second caller's fully valid, properly-authorized request is rejected with `jsonrpc.ErrConflict`, exactly like an unrelated `require` check causing an unrelated transaction to revert.

This mirrors the reported bug class: a shared/global piece of state (there, `RENCRV_VAULT.blockLock`; here, the global `callbacks` map keyed only by `requestID`) is checked unconditionally against a value that has no logical relationship to the current caller's tenant/workflow, causing an unrelated, legitimate request to fail.

### Impact Explanation
- A caller (any unprivileged workflow owner able to send HTTP trigger requests through the gateway) can deny service to another, completely unrelated workflow's execution by reusing/guessing a `requestID` value while that other workflow's request is in flight (the entry lives in `h.callbacks` until the response is aggregated or until the async reaper cleans it up).
- Because request IDs are often simple counters or predictable values chosen by client SDKs, accidental collisions across different tenants are also plausible, not just adversarial ones, causing legitimate executions to spuriously fail with `ErrConflict`.
- This is a resource-shared unprivileged-actor DoS/false-rejection vector at the internet-facing gateway; it does not require any privileged access — only knowledge of a request ID coincidentally in flight.

### Likelihood Explanation
Likelihood is moderate: an attacker needs to (a) know or guess a `requestID` that another workflow is likely to use concurrently, or (b) simply flood many trigger requests with common/short/sequential IDs to increase collision probability with any other tenant's traffic on the same DON. Since `requestID` values are visible/predictable in many SDK usages (e.g., request counters, timestamps), an attacker submitting a request with a colliding ID while a victim's request is in flight will deterministically block the victim.

### Recommendation
Scope the in-flight/dedup key by tenant, not just by the raw client-chosen `requestID`. Compose the map key from `workflowID` (or workflow owner) plus `requestID` (e.g., `workflowID + "::" + requestID`), analogous to how the vault gateway request pipeline prefixes the request ID with the authorized owner before further processing (`authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID`): [3](#0-2) 

Apply the same idea in `setupCallback`/`HandleNodeTriggerResponse` (and the `callbacks` map) so uniqueness is enforced only within a workflow's own request-ID namespace, eliminating unrelated cross-tenant collisions.

### Proof of Concept
1. Workflow A (owner X) sends an HTTP trigger request through the gateway with `requestID = "1"`. It passes `authorizeRequest` (valid JWT for workflow A) and reaches `setupCallback`, registering `h.callbacks["1"]`.
2. Before workflow A's request completes, an unrelated Workflow B (owner Y, a different user with a valid JWT for workflow B) sends its own, entirely legitimate HTTP trigger request also using `requestID = "1"`.
3. Workflow B's `authorizeRequest` succeeds (it's a valid request for workflow B), but `setupCallback` finds `h.callbacks["1"]` already present (from workflow A) and returns:
```
h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, "requestID: 1 has already been used...")
```
as shown at: [4](#0-3) 

Workflow B's valid, unrelated request fails with `ErrConflict` purely because of an unrelated workflow's in-flight request sharing the same client-chosen ID — the existing test `TestHttpTriggerHandler_HandleUserTriggerRequest/duplicate_request_ID` confirms the check fires purely on `requestID` collision without workflow scoping: [5](#0-4)

```go
func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
```
