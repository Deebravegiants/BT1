### Title
`EvmHost.dispatch()` / `fundRequest()` pay a fixed relayer fee via a single-block, unguarded Uniswap V2 spot swap - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)` and `fundRequest()` convert the caller's `msg.value` native token into the exact `feeToken()` amount needed to cover the relayer fee by calling `IUniswapV2Router02.swapETHForExactTokens` directly against the configured `_hostParams.uniswapV2` pool, with no TWAP, no external price sanity check, and no caller-supplied `amountInMax`/slippage bound beyond `msg.value` itself. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the WBGL report: a protocol-critical value (here, the native/fee-token exchange rate used to fund cross-chain relayer fees) is read from a single, live AMM pool's reserves in the same transaction it is consumed, with no TWAP or oracle cross-check. The docs for the companion `HyperApp.quote()` helper explicitly acknowledge this fragility ("Uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks. Only use it off-chain for frontend fee estimation") [4](#0-3) , but `EvmHost.dispatch`/`fundRequest` perform the equivalent operation on-chain, unconditionally, for every native-token dispatch.

Unlike a naive "price used to mint tokens" bug, the amount of `feeToken` the relayer is compensated with is fixed (`post.fee` / `get.fee` / `amount`), and `swapETHForExactTokens` only draws as much ETH from `msg.value` as the pool currently requires, refunding the rest. So a manipulated pool changes how much native token the *dispatcher* pays for a fixed `feeToken` payout to relayers/host, not how much the relayer receives. Concretely:
- If an attacker (via flash loan or large trade) skews the pool so `feeToken` is temporarily *cheap* relative to WETH, then calls `dispatch()`, they can obtain the exact same `feeToken` fee payment for far less native token than the pool's fair-value price, at the AMM's LPs' expense. This is a classic sandwich/manipulation profit taken from the configured `uniswapV2` pool's liquidity, executed atomically through a Host function that has no minimum-price protection.
- Because no `amountInMax` less than `msg.value` is enforced and there's no oracle deviation check (unlike `SimplexPaymaster._getOraclePrice`, which validates staleness/positivity of a Chainlink feed) [5](#0-4) , this path has strictly weaker protection than other fee-oracle code in the same repo.

### Impact Explanation
The impact is bounded and does not rise to core-protocol fund theft, unbacked minting, forged delivery, or unsound state commitment: the relayer/Host still receives the exact `feeToken` amount specified by the dispatcher, and native token beyond what the pool currently demands is refunded to the caller rather than lost by the Host contract. The loss (if any) accrues to the configured Uniswap V2 pool's liquidity providers via ordinary sandwich/arbitrage, not to Hyperbridge's own balances, relayer compensation, or message-delivery guarantees. I could not find a downstream path where this spot price is cached or used to determine mint/burn amounts, escrow releases, or bid comparisons (which would elevate this to the WBGL-style "attacker mints more of an asset than backed" scenario) — `IntentGatewayV2.sol`'s Uniswap references were only partially explored and I was not able to fully confirm whether any fund-affecting logic there consumes a similarly unguarded spot price.

### Likelihood Explanation
Likelihood is comparable to the underlying report only if `_hostParams.uniswapV2` is configured against a genuinely thin pool (e.g., a governance-chosen fee-token pool with low liquidity on some deployed chain); any unprivileged caller can trigger `dispatch()`/`fundRequest()` with `msg.value` to interact with this swap on every call, so the attack surface is reachable from a single transaction with no special privileges.

### Recommendation
Add a caller- or governance-configurable maximum acceptable native-token input (i.e., pass an explicit `amountInMax` to `swapETHForExactTokens` instead of implicitly bounding by `msg.value`), and/or cross-check the Uniswap V2 quote against a TWAP or a secondary oracle (mirroring `SimplexPaymaster`'s Chainlink staleness/positivity checks) before executing the swap in `dispatch()` and `fundRequest()`.

### Proof of Concept
Not constructed — this assessment is based on static review of `EvmHost.sol`'s `dispatch`/`fundRequest` swap calls and the documented sandwich-attack warning for the equivalent `HyperApp.quote()` helper; no on-chain PoC was run to quantify the exact extractable value in a specific deployed pool.

    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
