### Title
Missing lower-bound check on `virtualLtReserve` lets a high-priced LT collapse the bonding curve's K to zero, enabling free/unbacked token drains via the `Router._computeBuy` overflow-cap branch - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._deployAndSeed` computes the launch-time virtual LT reserve as `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate` and only guards the *upper* bound (`revert ExchangeRateTooLow()` when `virtualLtReserve > type(uint112).max / 4`) [1](#0-0) . There is no lower-bound / zero check: if the paired LT's `exchangeRate()` exceeds `VIRTUAL_LIQUIDITY_USD * 1e18`, integer division rounds `virtualLtReserve` down to `0`, and that value is permanently baked into the pair's invariant via `Pair.mint`'s `k = totalSupply * virtualLtReserve` [2](#0-1) . This is the same bug class as JLSEC-2026-831's divide-by-zero (an unguarded ratio computed from attacker/environment-controlled input degenerates the math), except here the degenerate value is silently baked into an immutable on-chain invariant rather than reverting, turning it into fund loss instead of a mere DoS.

### Finding Description
`Router._computeBuy`'s overflow-cap branch back-calculates the LT actually owed when a buy would exceed the pair's real token balance:
```
uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
amountInUsed = cappedReserveAsset - reserveAsset;
``` [3](#0-2) 

If `k == 0` (because `virtualLtReserve` rounded to `0` at launch), then for any `cappedReserveToken > 0`, `(0 + cappedReserveToken - 1) / cappedReserveToken` floors to `0`, so `cappedReserveAsset = 0`. With the pair's `reserveAsset` starting at `virtualLtReserve = 0` too, `amountInUsed = 0 - 0 = 0`. Any buyer hitting the overflow-cap path (trivially achieved by requesting a buy larger than the curve's remaining real balance, e.g. the standard "oversized buy" pattern already exercised by `test_inv_capBindingBuy...` in `GraduationInvariants.t.sol`) receives the entire real curve-token balance (`curveSupply`, 750M tokens) for `amountInUsed = 0` LT — i.e., free, unbacked tokens.

This is reachable purely through `Zap.createToken` (permissionless launch against any BounceTech LT whose `exchangeRate()` happens to exceed `VIRTUAL_LIQUIDITY_USD * 1e18`, e.g. a leveraged token tracking a high-priced underlying) followed by `Zap.buy`/`Bonding.buy` — both explicitly in-scope, unprivileged entry points. No malicious LT logic or privileged role is required; the bug is entirely in alt.fun's own reserve-seeding arithmetic in `Bonding.sol`.

### Impact Explanation
Once `k == 0` is locked in, the curve is permanently degenerate:
- Any buy that trips the overflow-cap branch drains the entire real token balance of the pair for zero (or near-zero) LT payment — an outright unbacked-token payout / theft of the token supply meant to back the eventual liquidity pool.
- Because `virtualLtReserve` is also read on-the-fly via `Pair.k() / Token.TOTAL_SUPPLY()` in graduation (`canGraduate`, `_launchTimeVirtualLtReserve`, `_prepareGraduationLiquidity`) [4](#0-3) , a zero virtual reserve corrupts `realLtRaised` accounting and the zero-gap LP-seeding math (`tokensForLP = ltFromPair × reserve0 / reserve1`), which can seed the HyperSwap V2 pool at a wrong price or freeze funds in `Bonding` between phases.
- This satisfies the "unbacked token payout" / "LP seeded away from curve close price" impact bars required by the validation rules.

### Likelihood Explanation
Likelihood depends entirely on whether a BounceTech LT with `exchangeRate() > VIRTUAL_LIQUIDITY_USD * 1e18` can exist and be paired at launch. Given the documented design targets a ~$3K opening market cap (i.e. `VIRTUAL_LIQUIDITY_USD` on the order of 3000 in 18dp USD terms) [5](#0-4) , this requires an LT priced above roughly $3,000 per unit — plausible for a leveraged token tracking a high-priced underlying (e.g. BTC-leverage), and entirely permissionless to trigger: any creator can call `Zap.createToken` against such an LT, or wait for/choose an LT whose price naturally crosses this line. I was not able to confirm the exact numeric value of `VIRTUAL_LIQUIDITY_USD` from the available index (the constant's definition line was not retrievable within tool limits), so the precise threshold price is unverified — this is the main uncertainty in this analog and should be checked directly against `Bonding.sol`'s constant declaration before treating this as confirmed-exploitable at current LT prices.

### Recommendation
In `Bonding._deployAndSeed`, add an explicit lower-bound guard immediately after computing `virtualLtReserve`, rejecting `virtualLtReserve == 0` (or below some safe minimum, e.g. reverting with a new `ExchangeRateTooHigh`/`VirtualReserveTooSmall` error) before it is passed into `Router.addInitialLiquidity` / `Pair.mint`. This mirrors the existing symmetric upper-bound check and prevents any launch from ever locking in a zero-`k` curve.

### Proof of Concept
1. Deploy (or identify) a `MockLeveragedToken`/BounceTech LT with `exchangeRate()` set above `VIRTUAL_LIQUIDITY_USD * 1e18` (e.g. `lt.setExchangeRate(VIRTUAL_LIQUIDITY_USD_18dp + 1)`).
2. Call `Zap.createToken(...)` pairing the new token with this LT — `_deployAndSeed` computes `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate == 0`, passes the upper-bound check trivially, and `Pair.mint` locks in `k = totalSupply * 0 = 0`.
3. As any unprivileged trader, call `Zap.buy` (or `Bonding.buy` directly, mirroring `test_inv_capBindingBuy...` in `GraduationInvariants.t.sol`) with an oversized LT amount so `Router._computeBuy` enters its overflow-cap branch.
4. Observe `amountInUsed == 0` (or near-zero) while `tokensOut == curveSupply` (750M tokens) is transferred to the buyer — confirming the entire real token balance was obtained for free, and inspect `bonding.canGraduate`/`_prepareGraduationLiquidity` behavior for the resulting corrupted `realLtRaised`/`tokensForLP` values.
