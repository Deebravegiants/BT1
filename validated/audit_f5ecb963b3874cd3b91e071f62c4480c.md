Audit Report

## Title
Value-transfer `CALL`s always get `ReentrancyProtection::AllowReentry`, defeating the stipend-based anti-reentrancy heuristic - (File: substrate/frame/revive/src/vm/evm/instructions/contract.rs)

## Summary
In `run_call`, the match expression that decides `add_stipend`/`ReentrancyProtection` places the `(false, _) => (true, ReentrancyProtection::AllowReentry)` arm before the stipend-heuristic arm `(_, true) => (true, ReentrancyProtection::AllowNext)`, and Rust evaluates match arms in source order. Because the first arm matches on `value.is_zero() == false` alone (via the wildcard on the second tuple slot), every nonzero-value `CALL` — including the canonical Solidity `.transfer()`/`.send()` shape (`value != 0`, `gas_limit == CALL_STIPEND` = 2300) — is routed to `AllowReentry` instead of the intended `AllowNext`, making the second arm unreachable for that call shape.

## Finding Description
The code at [1](#0-0)  is exactly as described:

```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

Since Rust match arms are tested top-to-bottom and the first arm's pattern `(false, _)` matches any tuple where the first element is `false` (i.e., `value.is_zero()` is `false`, meaning a nonzero transfer) regardless of the second element, the `(_, true)` arm intended to special-case `gas_limit == CALL_STIPEND` can never be reached when `value != 0`. This result (`add_stipend`, `reentracy`) directly feeds into `interpreter.ext.call(...)` at [2](#0-1)  which passes `reentracy` as the reentrancy-protection parameter for the call. This confirms the code behaves precisely as the claim states: the branch ordering makes the stipend heuristic structurally dead for any nonzero-value call, including the standard `.transfer()`/`.send()` idiom that carries nonzero value with `gas_limit == 2300`.

## Impact Explanation
If the `ReentrancyProtection::AllowNext` variant is meant to impose a tighter reentrancy restriction than `AllowReentry` (as strongly implied by the enum names and the accompanying code comment "protect against re-entrancy when we grant the stipend"), then this ordering bug silently downgrades the protection applied to the exact call pattern it claims to guard: nonzero-value calls forwarding the classic 2300 gas stipend. This is the call shape solc emits for `.transfer()`/`.send()`, a widely used real-world reentrancy-guard idiom, so the runtime's own defense mechanism for this pattern never engages.

## Likelihood Explanation
The `(value != 0, gas_limit == CALL_STIPEND)` condition is reached through completely unprivileged contract execution — any account can deploy contracts and issue ordinary `CALL` instructions with this exact value/gas combination, which is the default output of Solidity's `.transfer()`/`.send()` compilation. No governance, admin, or node-level privilege is required to trigger the code path.

## Recommendation
Reorder the match so the stipend-heuristic arm is evaluated before the blanket nonzero-value arm:
```rust
let (add_stipend, reentracy) = match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND)) {
    (_, true) => (true, ReentrancyProtection::AllowNext),
    (false, _) => (true, ReentrancyProtection::AllowReentry),
    (_, _) => (false, ReentrancyProtection::AllowReentry),
};
```
This ensures any call with `gas_limit == CALL_STIPEND` receives `AllowNext` regardless of value, matching the documented intent, while only calls with unrestricted gas and nonzero value receive `AllowReentry`.

## Proof of Concept
1. Add a unit test directly against `run_call`'s match logic (or an equivalent standalone match expression) asserting that for `value != 0 && gas_limit == CALL_STIPEND`, the computed `reentracy` should be `ReentrancyProtection::AllowNext`; this assertion fails against the current code, which yields `AllowReentry`.
2. At the integration level, deploy a victim contract using the `checks → .transfer(amount) → effects` pattern and an attacker contract whose fallback reenters the victim during the `.transfer()` call, then verify whether the reentrant call is permitted under `AllowReentry` versus blocked under `AllowNext`, confirming the practical effect of the misordered match arms.
