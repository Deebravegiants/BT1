## Title
Log Forging via Unsanitized Login Email in LDAP Authenticator - (File: core/sessions/ldapauth/ldap.go)

## Summary
`SessionsController.Create` binds the unauthenticated caller's JSON body directly into `sr.Email` and forwards it unmodified to `ldapAuthenticator.CreateSession`, which logs the raw value via `l.lggr.Infof` without stripping CR/LF characters, unlike the sibling `oidcauth` implementation which explicitly sanitizes the same field before logging. This lets an unauthenticated caller of `POST /sessions` inject forged log lines into the node's operational/audit log stream.

## Finding Description
`SessionsController.Create` performs `c.ShouldBindJSON(&sr)` with no character-level validation on `Email` [1](#0-0) , then calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` [2](#0-1) . For LDAP-configured nodes this reaches `ldapAuthenticator.CreateSession`, which logs the client-controlled `sr.Email` unescaped on the success path:
`l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)` [3](#0-2) , and similarly logs `escapedEmail` (which is only LDAP-filter-escaped via `ldap.EscapeFilter`, not CRLF-stripped) on the `FindUser` failure branch [4](#0-3) . `ldap.EscapeFilter` only escapes LDAP metacharacters, not newlines, so CR/LF pass through untouched.

This is a real regression relative to the sibling authenticator: `oidcauth.CreateSession` explicitly strips `\n` and `\r` from the same field before an equivalent `Infof` call [5](#0-4) , confirming this exact sanitization gap was previously recognized and fixed in one authenticator but not in `ldapauth`.

## Impact Explanation
This allows an unauthenticated client to inject arbitrary content, including fabricated log lines resembling successful admin logins, into the node's log/audit output. This is a log/audit integrity issue rather than an authentication bypass, data exfiltration, or fund-movement issue — it does not grant unauthorized session creation, privilege escalation, or access to secrets. It matches the "log forging" bug class but has no confidentiality or availability impact and does not itself achieve any of the higher-severity in-scope impact categories (auth bypass, key exfiltration, unauthorized job run/fund movement, gateway impersonation, allowlist bypass, cross-user response corruption).

## Likelihood Explanation
The path is reachable by any unauthenticated network client since `/sessions` is the login endpoint by design, and requires only an LDAP-authentication-configured deployment to exercise `ldapAuthenticator.CreateSession`. The specific exploit requires either a successful LDAP bind/local fallback (to hit line 435) or a `FindUser` lookup failure post-bind (to hit line 418) — both realistic outcomes under attacker control of credentials/timing.

## Recommendation
Apply the same CRLF/control-character stripping used in `core/sessions/oidcauth/oidc.go` to `sr.Email` (and `escapedEmail`) before any `lggr.Infof`/`Errorf`/`Warnf` call in `core/sessions/ldapauth/ldap.go`. Consider centralizing this sanitization for all `SessionRequest`-consuming authenticators to avoid future regressions.

## Proof of Concept
1. Configure a chainlink node with LDAP authentication enabled.
2. Send `POST /sessions` with `{"email": "attacker@example.com\n2026-09-13T12:00:00Z INF Successful LDAP login request for user admin@example.com - admin", "password": "..."}`.
3. Trigger either the success branch (line 435) or the `FindUser` failure branch (line 418) and observe the injected newline splitting the log entry into a forged extra line in the node's log output.
