## Title
`EvmHost.dispatch()` prices its native→feeToken swap off a single-block, sandwichable AMM quote with no minimum-output/slippage protection — ([File: evm/src/core/EvmHost.sol])

### Summary
Like `USSDRebalancer.getOwnValuation()`, which trusted an unprotected, single-block Uniswap V3 `slot0` read to drive a state-changing action, `EvmHost.dispatch()`/`dispatch(DispatchGet)`/`fundRequest()` price and execute a real-money swap using the current spot reserves of a configured Uniswap V2-compatible router/wrapper, with the exact output amount (`post.fee`/`get.fee`/`amount`) fixed and no caller-supplied `amountInMax` guard beyond "spend all of `msg.value`." Any address can call `dispatch{value: msg.value}(...)` directly on `EvmHost` — this is exactly the "unprivileged message dispatcher" path the scope calls out.

### Finding Description
`EvmHost.dispatch(DispatchPost)` (and the `DispatchGet` and `fundRequest` variants) swap native token for the exact required fee amount using the pool's live price: [1](#0-0) 

The router used is `_hostParams.uniswapV2`, which on real deployments is one of the project's own wrapper contracts (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`) that translate the V2-style call into a V3/V4 exact-output swap priced by the pool's current tick/sqrtPrice — i.e., a spot price, not a TWAP: [2](#0-1) 

The wrapper's own quoting helper also reads a live, single-call price (`quoteExactOutputSingle`), the same class of "read current pool state, trust it" pattern as the `USSDRebalancer.getOwnValuation()` `slot0` read: [3](#0-2) 

Because `EvmHost.dispatch()` sets `amountInMaximum: msg.value` (the entire ETH sent) with no separate slippage bound and no minimum-output check other than "amountOut == post.fee," the swap executes at whatever price the pool has *at that instant in the block*, which an attacker can move arbitrarily via a preceding same-block trade (classic sandwich / spot-price manipulation), because there is no TWAP or oracle cross-check anywhere in this path — the same root cause SensoYard flagged in `getOwnValuation()`.

### Impact Explanation
An attacker can manipulate the router/wrapper's pool price immediately before a victim's `dispatch{value: ...}(...)` call (front-running/sandwiching), forcing the exact-output swap to consume far more of the victim's `msg.value` than fair value would require. The refund path (`RefundFailed` guard notwithstanding) only returns whatever ETH is *left over* after the swap consumes the manipulated price — so a victim who computed `msg.value` off-chain from a pre-manipulation quote can have most or all of their native token consumed by the swap, receiving the same `post.fee` in feeToken but losing the price-manipulation premium to the attacker's LP position, or their transaction can revert entirely (denial of dispatch) if the manipulated price makes the required input exceed `msg.value`. This is a direct value-extraction path reachable by anyone dispatching a message with native-token payment — a core, unprivileged, permissionless entry point of the protocol (`IDispatcher.dispatch`).

### Likelihood Explanation
High. `dispatch()` with `msg.value > 0` is a documented, encouraged payment path (native-token fee payment is explicitly supported and marketed as convenient for end users), the docs themselves warn that `quote()` "uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks," confirming the project is aware the *read* side is manipulable — but the *execution* side (`dispatch`'s actual swap) carries the identical unprotected spot-price exposure and is not similarly called out or mitigated on-chain. Any MEV searcher/validator can trivially sandwich a pending `dispatch()` transaction, and low-liquidity fee-token/WETH pools (a realistic condition on many supported EVM chains) make this cheap to execute profitably.

### Recommendation
- Require callers of `dispatch()`/`fundRequest()` to supply an explicit `maxNativeIn` (slippage bound) rather than implicitly spending all of `msg.value`.
- Prefer a TWAP-based or bounded price check (e.g., compare the spot quote against a recent moving-average price and revert if deviation exceeds a configurable threshold) before executing the swap, mirroring the recommended fix for `getOwnValuation()`.
- Alternatively, disallow native-token payment on `dispatch()` for high-value/production configurations and push users toward the exact fee-token path (`dispatchWithFeeToken`), which has no swap and no manipulable pricing.

### Proof of Concept
1. Attacker observes a pending `dispatch{value: v}(DispatchPost{fee: F, ...})` transaction in the mempool targeting `EvmHost` whose `_hostParams.uniswapV2` points at the low-liquidity `UniV3UniswapV2Wrapper`/pool used for `WETH → feeToken`.
2. Attacker front-runs with a large trade that moves the pool's spot price against WETH (e.g., buys a large amount of feeToken from the pool), inflating the ETH required to buy exact `F` feeToken via `exactOutputSingle`.
3. Victim's `dispatch()` call executes `swapETHForExactTokens(F, [WETH, feeToken], address(this), block.timestamp)` at the manipulated price — as shown at [1](#0-0) , consuming most/all of `msg.value` for the same `F` output, or reverting outright since `amountInMaximum` (the whole `msg.value`) may fall short of the manipulated price required.
4. Attacker back-runs by selling the feeToken back into the pool, capturing the price differential extracted from the victim's excess ETH — the same "manipulate the spot read/execution to force a mispriced outcome" bug class described in the external `getOwnValuation()` report, but here directly draining value from a live dispatch instead of just triggering a bad rebalance decision.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }

        uint256[] memory amounts = new uint256[](2);
        amounts[0] = spent;
        amounts[1] = amountOut;

        return amounts;
    }
