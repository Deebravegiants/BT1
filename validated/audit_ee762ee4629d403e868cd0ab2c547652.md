### Title
Uniswap V4 Spot-Price Oracle Manipulation in Simplex Intent Solver's Venue Pricing (`getExoticTokenPrice` / `computeDirectPoolPriceUsd`) - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
Simplex's intent-solver pricing engine derives the USD price of "exotic" output tokens directly from a Uniswap V4 pool's instantaneous `sqrtPriceX96`-derived mid price (`sdkPool.token0Price`/`token1Price`), with no TWAP or size-aware execution model. The only defense is an optional, static-reference deviation check (`checkPriceGuard`) that bounds drift from an admin-configured number but does not detect or resist same-block/flash-loan manipulation of the pool itself. This mirrors the reported Uniswap V2 `getTokenPrice` bug class — pricing purely from live reserves/tick with no manipulation resistance — applied to the path a solver uses to price and fill user intents.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` (chain, exoticToken) iterates the solver's hydrated V4 positions and calls `computeDirectPoolPriceUsd`, which reads the pool's current mid price straight from the SDK pool object: [1](#0-0) 

This price feeds `FXFiller.resolveLegRates` in the intent-filling strategy, which uses it as the fill rate for curveless (venue-priced) trading pairs: [2](#0-1) 

The only check on this quote is `checkPriceGuard`, which compares the live quote to a static, operator-configured `referencePrice` within `maxDeviationBps`: [3](#0-2) 

The project's own internal documentation states the guard is the *only* defense and does not account for pool fee tier or execution size/impact: [4](#0-3) 
and the product docs explicitly acknowledge pool-based pricing "trusts the live pool," leaving the solver "exposed to a manipulated, stale, or thin pool": [5](#0-4) 

Critically:
- `referencePrice`/`maxDeviationBps` are **optional** ("omit both to leave the chain unguarded"), so a chain/position can be configured with no manipulation defense at all.
- Even when configured, the guard only bounds *how far* the manipulated price can drift from a static number — an attacker can move the pool price up to (but within) the allowed band in a single transaction (e.g., via a flash-loan swap) immediately before triggering/timing an intent fill, and the solver will still treat the manipulated spot price as valid.
- The price is read fresh on each pricing call (`state.refresh()` then `computeDirectPoolPriceUsd`) with no time-weighting, so a single-block manipulation is sufficient — there is no TWAP, no minimum observation window, and no execution-size/impact adjustment despite the code reading and storing the pool's fee tier (`pos.fee`) without ever applying it.

### Impact Explanation
An attacker who can move a configured V4 pool's spot price (flash loan or large swap, reversed after) can force the Simplex solver to price a curveless pair's fill at an artificially favorable rate to the attacker (within or, on unguarded chains, entirely outside any bound). Because this price directly determines the amount of output tokens the solver delivers when filling a user's cross-chain/same-chain intent order, the attacker can extract value directly from the solver's escrowed/vaulted inventory — a concrete theft of solver funds executed through the legitimate `fillOrder` intent-filling path. This is Medium/High severity: it results in direct loss of solver-held funds through a manipulable pricing oracle used in the intents/escrow fill flow.

### Likelihood Explanation
Likelihood is Medium: the vulnerability is only live on chains/pairs configured for venue-based (curveless) pricing with a V4 position (`[vault.uniswapV4]`), and further reduced if an operator configures `referencePrice`/`maxDeviationBps`. However, that guard is optional and even when present only bounds drift relative to a static number rather than detecting intra-block manipulation, and any attacker with capital (or flash-loan access) to move the specific pool's price can time a manipulation immediately before a fill without needing any special privilege — this is reachable by any unprivileged actor able to trigger a swap on the referenced pool and place/trigger an intent fill.

### Recommendation
Replace or supplement the instantaneous `sdkPool.token0Price`/`token1Price` read with a time-weighted average price (TWAP) sourced from the pool's oracle observations (or an external, manipulation-resistant oracle such as Chainlink, similar to the pattern already used in `SimplexPaymaster._getOraclePrice`). Apply the pool's fee tier and a size/impact term when deriving the execution price rather than extending the raw mid price linearly across the full quantity. Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory for any venue-priced (curveless) pair rather than optional, and consider bounding the maximum single-block price change accepted for pricing purposes.

### Proof of Concept
1. Operator configures a curveless pair (e.g., `USDC`/`CNGN`) priced solely from a `[vault.uniswapV4]` position, without setting `referencePrice`/`maxDeviationBps` (this is an explicitly supported, documented configuration — [6](#0-5) ).
2. Attacker takes a flash loan and swaps a large amount through the referenced V4 pool in one transaction, shifting `sqrtPriceX96` and thus `token0Price`/`token1Price` far from the fair market rate.
3. In the same or a closely following block, attacker (or a colluding party) submits an intent order targeting the manipulated pair; `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` returns the manipulated mid price (`sdkPool.token1Price`/`token0Price` at lines 261/270 of `UniswapV4FundingPlanner.ts`), unchecked since no guard is configured.
4. Solver fills the order at the manipulated rate, delivering more output tokens than the fair-value rate justifies, funded by liquidity withdrawn from the solver's own V4 position (`planWithdrawalForToken`).
5. Attacker reverses the flash-loan swap, restoring the pool price and profiting from the difference between the manipulated fill price and true market value, at the solver's expense.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
