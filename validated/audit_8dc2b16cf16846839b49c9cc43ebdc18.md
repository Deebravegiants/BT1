### Title
Permanent Freezing of Locked Funds via Unhandled ERC20 Transfer Revert in `WrappedHyperFungibleTokenUpgradeable.onAccept` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol / sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
The reported LayerZero bug shows a receiver whose token account can be frozen, and the mitigation was to gracefully emit an event instead of reverting so that a single frozen receiver cannot brick the whole instruction. Hyperbridge's `WrappedHyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken` "unlock" path does the opposite: it has **no** graceful handling for a beneficiary that cannot receive the underlying ERC20 (blacklisted, frozen, or otherwise non-compliant), so delivery of that specific cross-chain transfer permanently reverts.

### Finding Description
`onAccept` in `WrappedHyperFungibleTokenUpgradeable.sol` unlocks the underlying ERC20 directly to an attacker/sender-controlled `beneficiary` address with no fallback: [1](#0-0) 

If `_underlying` is a token with transfer restrictions (e.g. a USDC-style blacklist, or any pausable/frozen-account token), `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` reverts whenever the beneficiary is or becomes non-compliant. Unlike the report's mitigated LayerZero path (`emit!(FrozenWithdrawn)` instead of reverting), there is no branch here to detect the failure and emit an event/queue the funds for later withdrawal — the entire `onAccept` call reverts.

Crucially, the destination beneficiary (`message.to`) is fully attacker-controlled from the source-chain `send()` call: [2](#0-1) 

and the underlying tokens are already locked in the contract on the source chain at `send()` time: [2](#0-1) 

Because `onAccept` always reverts for that specific request, no relayer can ever successfully deliver the message. The only recovery path is `onPostRequestTimeout`, which requires the request to have an enforced timeout: [3](#0-2) 

`timeout` is a caller-supplied `uint64` field of `SendParams` with no minimum/floor enforced in `_buildDispatchPost`: [4](#0-3) 

If a `timeout` of `0` is used (a value commonly interpreted across ISMP host implementations as "no timeout enforced"), the locked funds can never be reclaimed through the timeout path either, since a timeout proof cannot be submitted for a request that never expires. Even when a timeout is set, the funds remain locked and unusable for the entire timeout window purely because of an unhandled revert condition that the report's remediation pattern (event-emit fallback) was specifically designed to avoid.

The identical unguarded `safeTransfer` pattern exists in the non-upgradeable sibling contract `WrappedHyperFungibleToken.sol`.

### Impact Explanation
This directly matches the "permanent freezing of funds" acceptance criterion: tokens locked via `send()` on the source chain become permanently undeliverable and unrecoverable whenever the chosen (or later blacklisted/frozen) beneficiary cannot accept the underlying ERC20, and no timeout was set (or the timeout is exhausted while the condition persists, if the underlying restriction is not lifted by the token issuer). This is a High severity finding because it can permanently lock arbitrary amounts of value with a single unprivileged `send()` call, requiring no privileged access — only a standard cross-chain token transfer to a non-compliant/blacklisted address.

### Likelihood Explanation
Likelihood is Medium-High: it requires the underlying wrapped ERC20 to implement transfer restrictions (blacklisting, pausing, freezing) — common for major stablecoins like USDC/USDT which are realistic candidates for `WrappedHyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken` deployments — and either a `timeout` of `0`/very long value, or the restricted state persisting through the timeout window. Any unprivileged user calling `send()` can trigger this against themselves or, via griefing, target another party's locked funds path if beneficiary compliance changes after dispatch.

### Recommendation
Mirror the report's remediation: detect the failure mode before attempting the transfer (or catch it) instead of letting `onAccept` revert unconditionally. Concretely:
- Wrap the `safeTransfer`/native push in a try/catch (or pre-check compliance where the token exposes it) and, on failure, emit an event and credit the beneficiary's amount to an internal "pending withdrawal" ledger that an admin/beneficiary can claim later once compliant, rather than reverting the whole delivery.
- Alternatively/additionally, enforce a sane minimum and maximum bound on `timeout` in `_buildDispatchPost`/`send()` so a `0`/unbounded timeout cannot be used to make a stuck transfer unrecoverable forever.
- Apply the same fix to both `WrappedHyperFungibleTokenUpgradeable.sol` and `WrappedHyperFungibleToken.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleTokenUpgradeable` wrapping a USDC-like token with blacklist functionality on chain A (source) and chain B (destination).
2. Attacker (or any user) calls `send()` on chain A with `params.to` set to an address that is already blacklisted on the underlying token on chain B, and `params.timeout = 0`. Tokens are locked in the contract via `safeTransferFrom`.
3. A relayer submits the proof and calls `onAccept` on chain B. `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` reverts because `beneficiary` is blacklisted.
4. Every subsequent relay attempt for this exact request reverts identically; because `timeout = 0`, no `onPostRequestTimeout` refund is ever obtainable.
5. The locked underlying tokens on chain A remain permanently inaccessible — not refundable (no timeout) and not deliverable (recipient always rejects), demonstrating permanent freezing of funds achievable by any unprivileged sender.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(incoming.request.body, (HyperFungibleTokenUpgradeable.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
