Based on my research, I found a concrete instance of the target bug class: an identity field (`shop`) that is acted upon by the trust boundary but not covered by the HMAC signature.

### Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` (the tenant identity used by host applications to route/process webhooks) as a value read directly from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that this gem validates covers *only* the raw request body bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `api_version` are all pulled straight from unauthenticated headers via `shopify_header`, with no inclusion in the signable string: [2](#0-1) [3](#0-2) 

Validation is performed generically by `Utils::HmacValidator.validate`, which only calls `verifiable_query.to_signable_string` and `verifiable_query.hmac`: [4](#0-3) 

Because Shopify signs webhooks with the app's single, shop-independent `client_secret`, the HMAC only proves "this body byte-stream was signed with our app's secret" — it proves nothing about which shop the header claims to be for. This is the same class of bug as the report's core issue: a value that is trusted and acted upon (`feeRecipient` / here, `shop`) is not properly bound/verified at the point of use — the equality that should hold, `shop (verified by signature) == shop (used for tenant routing)`, does not, because `shop` is never part of the verified bytes.

### Impact Explanation
An unprivileged internet user who controls (or has intercepted) one legitimately-signed webhook payload+HMAC pair from Shopify (e.g., delivered to their own shop's installation of the app, or any endpoint they can observe) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will return `true` because the HMAC only checks body integrity against `Context.api_secret_key`/`old_api_secret_key`, never checking that the `shop` header matches anything cryptographically bound to that body. Any host application that trusts `Request#shop` (a value this gem itself validates as "authentic" once `HmacValidator.validate` passes) to select which tenant's data to update will process the payload under the wrong shop, resulting in cross-tenant data confusion — writing or triggering side effects (e.g., order/product/app-uninstalled events) against a shop other than the one that actually sent the webhook.

### Likelihood Explanation
Requires the attacker to have observed at least one valid webhook (trivial if they run their own shop with the same app installed, which is a normal, unprivileged action for any Shopify merchant), and requires the host app to key its webhook processing off `request.shop` after `HmacValidator.validate` succeeds — the exact intended and documented usage pattern of this gem's webhook API. No secrets, tokens, or elevated access are needed.

### Recommendation
Include `shop` (and ideally `topic`/`api_version`) in the signable string bound to the HMAC verification, or otherwise cryptographically bind the claimed shop domain to the signed payload before it is used for tenant-scoped routing, so that `HmacValidator.validate` cannot succeed for a body/HMAC pair paired with a mismatched or forged shop header.

### Proof of Concept
1. Attacker installs the victim app on their own shop (`attacker-shop.myshopify.com`), triggering a legitimately Shopify-signed webhook with valid `X-Shopify-Hmac-Sha256` and body.
2. Attacker captures the raw body and HMAC header.
3. Attacker (or any network position able to reach the app's public webhook endpoint) POSTs the exact same body and HMAC header to the endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds `shop` from the forged header [5](#0-4) , while `HmacValidator.validate(request)` still succeeds because it only checks `@raw_body` against the shared `client_secret` [4](#0-3) .
5. The host application, trusting the gem's validated `request.shop`, processes the webhook as if it belongs to `victim-shop.myshopify.com`.
