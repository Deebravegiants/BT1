### Title
Webhook shop attribution (`x-shopify-shop-domain`) is not covered by the HMAC signature, allowing shop spoofing via header substitution on a captured webhook payload - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only ever covers the raw request body. This breaks the equality "authenticated bytes == bytes acted upon": Shopify's HMAC guarantees the integrity of the JSON body, not of the shop-domain header that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler as the tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (attacker-controllable, at the HTTP layer) header, independent of that signed body: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string` (i.e., the body), never incorporating `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed into the app's `WebhookMetadata`, with no separate check that `shop` corresponds to the signed payload: [4](#0-3) 

Because the HMAC is computed over the body only, two requests with identical bodies but different `x-shopify-shop-domain` headers produce the exact same valid HMAC. An unprivileged attacker who has obtained (or can predict/replay) one legitimately-signed webhook body — e.g., by observing their own store's webhook traffic, which is delivered over plain, attacker-observable HTTP endpoints configured by the merchant/app — can resend that same body to the app's webhook endpoint with the `shop` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never checked the header, so `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, while the signature only proves the body originated from Shopify for *some* shop, not for the shop claimed in the header.

The bound equality that should hold is: `shop authenticated by HMAC == shop acted upon by handler`. Instead, `shop` is parsed unauthenticated (header) versus the value verified by the signature (body only) — directly matching the "bytes verified vs. bytes parsed" / "field acted on but not covered by the HMAC" analog class.

### Impact Explanation
If a host application relies on `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry.process` to select which tenant's data record/session to update (a documented and expected usage pattern of this gem), an attacker can force cross-tenant data to be attributed to, or written under, a different shop than the one Shopify actually signed the payload for. This is a cross-tenant identity-binding bypass rooted entirely in this gem's `HmacValidator`/`Webhooks::Request` implementation, not a host-app misuse of an undocumented API — the gem's own public webhook-processing contract exposes `shop` as a trusted field.

### Likelihood Explanation
Requires the attacker to already possess one validly-signed webhook body for their own shop (trivial: any app owner can trigger and capture their own webhooks) and the ability to POST to the app's public webhook endpoint with modified headers — no access token, `client_secret`, or privileged credential needed. This is a realistic unprivileged-internet-user scenario.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the HMAC-signable content (or otherwise cryptographically bind them to the signed body) inside `Utils::VerifiableQuery`/`Webhooks::Request`, so `HmacValidator.validate` fails if any of these header-derived fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` triggers a webhook; attacker captures the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` computed by Shopify over `B`.
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` despite the payload never actually being signed/sent for that shop.
