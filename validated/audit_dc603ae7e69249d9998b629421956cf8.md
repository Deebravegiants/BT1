I have confirmed the vulnerability. `WebhookMetadata.shop` (used by every registered `WebhookHandler` to determine which tenant a webhook belongs to) is populated directly from an unauthenticated HTTP header, while the HMAC signature that Registry.process() validates covers only the raw request body.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` value that identifies *which tenant* the webhook belongs to is read from the unauthenticated `x-shopify-shop-domain` header and is never included in the signed content, so it can be freely modified without invalidating the HMAC.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` is decoded purely from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` handed to the host application's handler: [4](#0-3) 

`HmacValidator.validate` confirms this — it only ever signs/verifies `verifiable_query.to_signable_string`, which for a webhook `Request` is the raw body and nothing else: [5](#0-4) 

`WebhookMetadata.shop` is the only tenant-identifying value exposed to host application handlers: [6](#0-5) 

The broken identity binding, stated as an equality that should hold but does not:
`shop covered by HMAC signature` == `shop trusted by WebhookMetadata.shop`
In this implementation, the left side is the empty set (the signature covers only `raw_body`), while the right side is an attacker-controllable HTTP header, so the equality never holds.

Because the HMAC secret (`api_secret_key`/`old_api_secret_key`) is an app-level secret shared across *all* shops that install the app — not a per-shop secret — any merchant who installs the app on their own store (an "unprivileged internet user" action requiring no special credentials) can obtain a webhook payload/body plus a *valid* HMAC signature for that exact body. Because the signature never covers the `shop-domain` header, that same (body, hmac) pair remains valid when replayed with the `x-shopify-shop-domain` header changed to an arbitrary target shop.

### Impact Explanation
This crosses a tenant boundary: `Registry.process` will accept the forged webhook as authentic, and the handler will act on it believing it originates from the victim shop specified in the (attacker-controlled) header, even though the payload was generated by/for the attacker's own store. Depending on how the host application uses `WebhookMetadata.shop` (e.g., to look up which merchant record to update, decrement inventory for, mark an order paid for, etc.), this enables cross-tenant data manipulation using a webhook that is provably "HMAC valid" per this library's own validation logic. Per the impact taxonomy, this is a cross-tenant access issue (Critical).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires an attacker to (1) install the target app on a shop they control (permitted to any internet user for public apps) to obtain one legitimately-signed webhook body/HMAC pair, and (2) replay that request against the app's public webhook endpoint with a modified shop-domain header. No access token, `client_secret`, or leaked credentials are required — only the ability to receive one webhook as an ordinary merchant.

### Recommendation
Bind the tenant-identifying header values into the signed content, or otherwise authenticate them independently of the raw-body HMAC. For example, extend `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) to require that `shop` (and ideally `topic`/`webhook_id`) match values recovered from a source that Shopify itself signs together with the body — at minimum, applications/library consumers should be warned/forced to cross-check `request.shop` against the shop associated with the session/webhook subscription that was registered via `Registry.register`, rather than trusting the header verbatim once the body's HMAC checks out.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and configure a webhook subscription (e.g., `orders/create`).
2. Capture an inbound webhook HTTP request: headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and raw JSON body `B`. `<H>` is a valid `HMAC-SHA256(api_secret_key, B)`.
3. Replay this exact request to the app's public webhook endpoint, changing only the header `x-shopify-shop-domain` to `victim-shop.myshopify.com` (leaving body `B` and `x-shopify-hmac-sha256: <H>` untouched).
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `<H>`, so validation succeeds: [7](#0-6) 
5. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the payload body actually originated from the attacker's shop, demonstrating the cross-tenant identity confusion.
