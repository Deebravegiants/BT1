### Title
Webhook processor trusts the unsigned `shop-domain` (and `topic`) header as tenant identity, breaking the binding to the HMAC-covered payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied, unauthenticated `shop-domain` header straight to the app's handler as the tenant identifier. The identity binding `hmac_signed_bytes == bytes_the_handler_trusts_as_the_shop` does not hold, because the signature never covers the `shop` field that downstream handler code uses to route/attribute the webhook to a merchant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header value: [2](#0-1) 

`Registry.process` gates on that HMAC check, then constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — all of which are read directly from caller-supplied HTTP headers with no cryptographic binding to the signed body: [3](#0-2) [4](#0-3) 

`WebhookMetadata.shop` is a `const` field passed as-is into the app-defined `WebhookHandler#handle` contract: [5](#0-4) 

Because the app's `api_secret_key` is shared across every shop that installs the app, any unprivileged user can install the app on a shop they control and receive a legitimate `(raw_body, hmac)` pair signed with that shared secret. They can then replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds, because it only checks the body bytes — never the shop header — and `Registry.process` dispatches the payload to the handler labeled with the attacker-chosen `shop`. This is exactly the report's bug class: "bytes verified" (the raw body) diverge from "bytes acted on" (the `shop` field used for tenant attribution).

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which merchant's session/access token to look up, or which tenant's records to create/update/delete based on the webhook body, can be made to apply an attacker's own webhook event data under a victim shop's identity — a cross-tenant data integrity/confusion issue reachable without any credential, access token, or client_secret belonging to the app. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on any shop the attacker controls (a normal, unprivileged action any developer/merchant can perform), (2) capturing one legitimate webhook delivery (body + HMAC) sent to their own app endpoint, and (3) resending it with a forged `shop-domain` header. No secrets, tokens, or privileged access are required, and the gem does nothing to prevent it — it never signs or otherwise authenticates the header fields it exposes on `WebhookMetadata`.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is cryptographically verified, or otherwise cross-check `request.shop` against an out-of-band authenticated source (e.g., only trust `shop` if it matches a value bound into the payload/signature) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are NOT covered by the HMAC and must not be used by host apps as an unauthenticated tenant selector without additional verification (e.g., confirming the shop has an existing stored session before trusting the webhook as belonging to it).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (no privileged access required).
2. Attacker triggers/receives any webhook (e.g., `orders/create`) to the app's public endpoint and records the exact `raw_body` and the `x-shopify-hmac-sha256` value delivered — both signed with the app's single, shared `api_secret_key`.
3. Attacker replays a raw HTTP POST to the same endpoint with the identical body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` succeeds because `to_signable_string` only reflects `raw_body`, which is unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` from the forged header and invokes the app's handler as if the event genuinely originated from the victim shop (`lib/shopify_api/webhooks/registry.rb:188-199`).
