### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator` verifies binds solely to the body bytes. The `shop`, `topic`, and `webhook_id` values are read straight from HTTP headers and are never part of the signed material, yet `Registry.process` trusts them to route and label the webhook to a specific merchant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the `@raw_body` is included. `Registry.process` validates that signature and then immediately uses the unauthenticated `request.shop` header to build the `WebhookMetadata` passed to the app's handler: [2](#0-1) 
`Request#shop`, `#topic`, and `#webhook_id` are all pulled from headers with no cryptographic binding to the HMAC: [3](#0-2) 

This breaks the identity binding: `HMAC-verified(body)` == `shop-attributed-to(body)` does not hold. Since a merchant who installs the app is a legitimate holder of at least one genuinely-signed webhook (body + valid HMAC pair) for their own shop, they can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`) header for a different, victim shop. `HmacValidator.validate` only recomputes the HMAC over `raw_body`, so it still returns true, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding gap in a security-relevant primitive of this gem (webhook authentication). Any host application that relies on `WebhookMetadata#shop` (or `topic`) returned by this gem to decide which merchant's session/store the payload applies to inherits an unauthenticated field masquerading as an authenticated one. An attacker who is themselves a legitimate merchant of the app can obtain a genuinely-signed body/HMAC pair (e.g., from a benign topic like `app/uninstalled` or any webhook with attacker-controlled or predictable body content) and relabel it as belonging to another shop, causing the receiving app to process attacker-controlled but validly-"authenticated" data under another tenant's identity. This matches the Critical bar of cross-tenant access via a gem-level authentication check that answers permissively on an unbound field.

### Likelihood Explanation
Exploitability only requires the attacker to be an installed merchant of the target app (no special privileges within Shopify's platform, no `client_secret`, no leaked credentials) and the ability to send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header — something entirely within reach of an "unprivileged internet user" who has installed a copy of the app. The gem itself performs no cross-check between the signed body and the header-derived shop/topic, so the flaw is deterministic, not conditional on host-app misuse of documented APIs.

### Recommendation
Bind the identity fields into the HMAC-signed material, or otherwise reject webhooks whose header-derived `shop`/`topic` cannot be independently corroborated:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (matching what Shopify actually signs, if Shopify includes headers in its HMAC scheme), or
- Cross-validate the `shop` header against an actively-tracked session/shop store keyed by data that is itself authenticated (e.g., only accept webhooks for shops with an existing valid offline session, and treat mismatches as invalid), rather than trusting the header value verbatim in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, thereby causing Shopify to send a legitimately HMAC-signed webhook (e.g. `orders/create`) to the app's registered endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
2. Attacker captures `B` and `H` (they control the shop, so they can trigger and observe this delivery, e.g. by placing a test order or configuring a proxy in front of their own store's webhook receiver if they self-host, or simply crafting `B` themselves if body content is attacker-influenced for the topic in question).
3. Attacker sends a forged POST to the app's webhook endpoint with body `B`, `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because `to_signable_string` only covers `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes `HMAC(secret, B)` and compares to `H`, per [4](#0-3) .
6. `Registry.process` proceeds to invoke the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: ..., ...)` per [5](#0-4) , causing the host app to act on data it believes is authenticated as coming from the victim shop.
