### Title
Webhook tenant identity (`shop`, `topic`) is not covered by the HMAC signature, allowing cross-tenant spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over `@raw_body` only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers that are never included in the signed bytes. `Registry.process` accepts any request whose body/HMAC pair is valid, then blindly trusts the header-derived `shop` value to build `WebhookMetadata` passed to the app's own webhook handler.

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, bytes_that_include_shop)`. Instead the actual binding implemented is `hmac == HMAC(secret, raw_body)`, with `shop` (and `topic`, `api_version`, `webhook_id`) taken from headers entirely outside that signed scope, per `to_signable_string` at [2](#0-1)  versus `shop` at [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (the raw body) — never the headers — as the signed content per `HmacValidator#validate_signature` at [7](#0-6) . Once that check passes, `request.shop` is passed straight through to `handler.handle` as the trusted tenant for that event, per [1](#0-0) .

Because the `shop-domain` header sits entirely outside the signed bytes, any `(raw_body, hmac)` pair that is valid for one shop's genuine webhook delivery remains a valid `(raw_body, hmac)` pair no matter which `shop-domain` header value accompanies it. This breaks the intended identity binding "the HMAC-authenticated request corresponds to the shop named in its metadata" — the HMAC only proves "this body was generated by the party holding `api_secret_key`," not "this body was generated for shop X."

### Impact Explanation
An app that uses `data.shop` from `WebhookMetadata` to determine which tenant's records to create/update/delete (the documented and expected usage, per `docs/usage/webhooks.md`) can be made to apply attacker-influenced webhook data under an arbitrary victim shop's identity, since the shop field carries no cryptographic binding to the payload that was actually signed. This is a cross-tenant integrity issue in how the gem's `Request`/`Registry` abstraction reports authenticated identity to host applications, even though the underlying HMAC computation is correct for the body itself.

### Likelihood Explanation
Exploiting this requires the attacker to possess a valid `(raw_body, hmac)` pair, which in turn requires either the app's `api_secret_key` or a genuine webhook delivery whose header they can then alter before it reaches the app's endpoint — the latter requiring network positioning between Shopify and the app (out of scope per the interception exclusion), or the app forwarding/re-emitting untrusted header values it received from a source other than Shopify's direct POST. Absent such a forwarding path, the gem's own code does not give an unprivileged internet user, with no secret and no network position, a way to independently mint a valid body/hmac pair for an arbitrary victim shop.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the payload), and use a canonicalized combination of raw body plus these header values in `to_signable_string`, so the identity claimed by `request.shop` is provably part of what the app's `api_secret_key` actually signed.

### Proof of Concept
Not concretely demonstrable purely within this gem's code without an external capability (network interception or genuine possession of the `api_secret_key`) to obtain a valid `(raw_body, hmac)` pair and then swap the `shop-domain` header before it is verified; per the test fixtures at [8](#0-7) , `HmacValidator.validate` will accept any `shop-domain` header alongside a fixed valid `(raw_body, hmac)` pair, since `to_signable_string` never references `shop`.
