### Title
Webhook shop/topic/version identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers when constructing `WebhookMetadata` and dispatching to the app's handler.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` as just the raw request body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.), which are never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` from those same unauthenticated headers, handing them to the app's handler as trusted identity data: [3](#0-2) 

The `HmacValidator.validate` call only proves that whoever produced the request body knows `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared across every shop/tenant that has installed the app (not a per-shop secret), the HMAC check establishes "the sender knows the app's client_secret" — it does **not** establish "this event pertains to shop X." The identity binding the app actually relies on (`request.shop` used as the tenant key) is never covered by the signature. Equality that should hold but doesn't:
`shop_claimed_in_header == shop_the_signature_actually_authenticates` — the right-hand side doesn't exist; the signature authenticates only the body bytes.

An unprivileged internet user who has ever received one legitimate webhook for their **own** shop (e.g., by installing the target app on a store they control, which is a normal, unprivileged action for any public app) can capture a valid `(raw_body, x-shopify-hmac-sha256)` pair. Because the signature never binds to the shop domain, topic, or webhook id, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers with values belonging to a **different** shop. `Registry.process` will pass HMAC validation (since only the body changed... more precisely, the body is unchanged and thus still valid) and will hand the handler a `WebhookMetadata` claiming to be from the victim shop, with a webhook id/topic of the attacker's choosing.

### Impact Explanation
If the host application uses `data.shop` (as universally documented and shown in this gem's own `docs/usage/webhooks.md` example, which does `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) to look up the victim's stored session/access token and perform tenant-scoped actions (fulfillments, order updates, metafield writes, GDPR data flows, etc.), an attacker can inject fabricated events attributed to a shop they do not control. This is a cross-tenant integrity/confidentiality break: the attacker forges events "as" another merchant's shop, potentially triggering privileged automation (e.g., fulfillment creation, refund processing, customer data export) against the victim's store using the victim's own stored access token, without ever compromising that token. This matches the Critical "cross-tenant access" impact category, since the identity boundary between tenants is broken purely by header substitution.

### Likelihood Explanation
Likelihood is Medium-High for apps that follow the gem's own documented pattern (trusting `data.shop`/`data.topic` for dispatch and enqueuing without independently verifying the shop against a known/subscribed session, or without deduplicating/verifying `webhook_id` against Shopify's registered subscription for that specific shop). The prerequisite — installing the app on an attacker-owned shop to obtain one valid `(body, hmac)` pair — is trivial and requires no privileges beyond being a normal merchant/user of a public app. No secret leakage, TLS interception, or privileged account is required.

### Recommendation
- Bind the identity fields into the signed payload: verify the webhook not just via body HMAC but by additionally confirming `shop`, `topic`, and `webhook_id` against Shopify by re-fetching or cross-checking the subscription (e.g., confirm the shop actually has an active session/installation and that the `webhook_id` was registered for that specific shop before trusting `data.shop`).
- At minimum, document prominently (both in `docs/usage/webhooks.md` and in `WebhookMetadata`) that `shop`, `topic`, `api_version`, and `webhook_id` are **not** covered by the HMAC and must not be trusted for authorization/tenant-scoping decisions without an independent verification step (e.g., checking the shop has a valid, previously-established session before acting).
- Consider rejecting/flagging webhook requests where the claimed `shop` does not correspond to a currently active session managed by the host app, pushing this guidance into the library's `Registry.process` contract.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`.
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent for that event (this pair is valid because it was legitimately signed by Shopify using the app's `client_secret`).
3. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but changes:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic` and `X-Shopify-Webhook-Id` to arbitrary/desired values.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only recomputes HMAC over `@raw_body` [1](#0-0)  — validation succeeds because the body is unchanged.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [5](#0-4)  and, following the gem's documented pattern, dispatches tenant-scoped work believing it originated from the victim's store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
