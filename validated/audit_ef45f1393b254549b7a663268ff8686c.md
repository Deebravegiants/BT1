Based on my investigation, the core factual claims in this report hold up against the actual code:

1. `GatewayHandler.HandleGatewayMessage` does log the raw request at debug level before any authorization or parsing occurs: `reqLggr.Debugw("received message from gateway", "req", req)` [1](#0-0) .

2. `jsonrpc.Request[json.RawMessage]` (from `chainlink-common/pkg/jsonrpc2`, an external dependency not indexed in this repo, so I could not inspect its internal `String()`/`MarshalLogObject` implementation) carries an `Auth` field that is confirmed throughout the codebase to hold a bearer/JWT token — e.g. `req.Auth = createTestJWTToken(...)` and helper functions explicitly strip it before building the outbound wire request (`outboundRequestWithoutAuth` sets `req.Auth = ""`) [2](#0-1) , and the authorizer treats `req.Auth` as the credential distinguishing JWT-based vs allowlist-based auth paths [3](#0-2) .

3. The `Debugw` call happens before `ProcessRequest`/`AuthorizeRequest` is invoked in the switch statement, confirming the log is unconditional and unguarded by any auth check [4](#0-3) .

4. Elsewhere in the same file, when logging is auth-aware, the code deliberately avoids leaking the raw token, using `"hasAuth", req.Auth != ""` instead of the field itself [5](#0-4) , which underscores that the raw `Debugw("received message from gateway", "req", req)` call is inconsistent with the pattern used elsewhere for the same sensitive field.

One point I could not fully verify: whether the `jsonrpc.Request` type has a custom `String()`/`MarshalLogObject`/zap-compatible redaction method defined in the external `chainlink-common` package that could mask `Auth` before it hits the log sink. This type lives in an external Go module (`github.com/smartcontractkit/chainlink-common/pkg/jsonrpc2`) that isn't part of this repo's indexed source, so I cannot confirm or rule out built-in redaction there. However, nothing in this repo's own code or tests suggests such redaction exists, and the pattern of explicitly stripping `Auth` before serialization/logging elsewhere in the codebase (`outboundRequestWithoutAuth`, `hasAuth` boolean logging) strongly suggests no such redaction is relied upon.

Given the exploit path is real (unprivileged client → JSON-RPC request with `Auth` set → node logs the full struct including `Auth` at debug level, before authorization), the broken security assumption is concrete (credential exposure in log output requires only enabling debug logging, a common operational configuration), and the impact (token exfiltration enabling request impersonation) maps to an in-scope category, this claim is valid.

Audit Report

## Title
JWT Bearer Token Exposed in Verbose Gateway Handler Logs - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire incoming `jsonrpc.Request[json.RawMessage]` object — including its `Auth` field, which carries the caller's bearer/JWT token — at debug level, before any parsing or authorization occurs. Enabling debug/verbose logging on a node causes every caller's authentication token to be written unredacted into the node's log stream.

## Finding Description
The handler's entry point logs the raw request unconditionally: [1](#0-0) 

`req.Auth` is used throughout the codebase as the transport for a signed JWT used to authorize the request against the vault authorizer's JWT-based path: [3](#0-2) . Test helpers and clients construct requests with `req.Auth` set to a signed token and explicitly scrub it before further use (`outboundRequestWithoutAuth` sets `req.Auth = ""`) [2](#0-1) , confirming its sensitivity is well understood elsewhere in the code. Notably, the authorizer's own debug/error logging near the same field deliberately avoids emitting the raw token, instead logging only `"hasAuth", req.Auth != ""` [5](#0-4)  — showing the raw dump in `HandleGatewayMessage` is inconsistent with the safer pattern used elsewhere in the same package.

The log statement fires prior to the `switch req.Method` block that performs authorization via `ProcessRequest`/`AuthorizeRequest`, so it is not gated by any auth check [4](#0-3) .

## Impact Explanation
If a node operator (or any party with access to the node's debug/verbose logs — log aggregation, support bundles, etc.) enables debug logging, every caller's JWT auth token passing through the vault gateway handler is captured in plaintext in the logs. Because that token is the credential used to authorize vault operations (secrets create/update/list) on behalf of a specific workflow owner/org, its exposure allows replay to impersonate that caller against the vault gateway — matching the "gateway request impersonation" impact category.

## Likelihood Explanation
Any normal, unprivileged client sending a JSON-RPC request through the gateway to a node's vault handler triggers this log line, since it executes for every inbound message regardless of subsequent authorization outcome. The only precondition is that the node has debug-level logging enabled, which is a realistic and common operational/troubleshooting configuration rather than an exotic misconfiguration.

## Recommendation
Do not log the raw `req` object in `HandleGatewayMessage`. Log only non-sensitive fields already captured by `requestLogger` (method, request ID, gateway ID), and if the full payload is needed for debugging, construct a redacted copy that zeroes/masks `req.Auth` before passing it to `Debugw`, consistent with the `hasAuth` boolean pattern already used in `authorizer.go`.

## Proof of Concept
1. Run a node with the vault gateway handler configured, with debug-level logging enabled.
2. As an unprivileged client, send a JSON-RPC request (e.g., `vaulttypes.MethodSecretsList`) through the gateway with `Authorization: Bearer <token>` (i.e., `req.Auth` populated), following the same construction pattern as `tryJWTSignedVaultSecretsUpdate` [6](#0-5) .
3. Inspect the node's debug logs for the line `"received message from gateway" req=...` emitted at [7](#0-6) ; confirm the `Auth` token value is present in the log output and can be extracted and replayed.

	return a.authorizeJWTBasedAuth(ctx, req)
