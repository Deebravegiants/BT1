### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC is computed only over the raw request body. The `shop`, `topic`, and `webhook_id` values that are actually used to route and label the event are read from HTTP headers that are never part of the signed payload, breaking the equality "headers trusted for identity == bytes covered by the HMAC."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, and `webhook_id` are pulled directly from HTTP headers, with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of the entire request's authenticity, then dispatches using the unauthenticated header values: [4](#0-3) 

Because the shared secret (`Context.api_secret_key`) is the same for every shop that installs the app (it is the app's `client_secret`, not a per-shop key), any legitimate installer of the app receives real webhook deliveries with a valid HMAC over a given raw body. That attacker can then replay the same body/HMAC pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain`, `x-shopify-topic`, and/or `x-shopify-webhook-id` headers to arbitrary values. The HMAC check still passes (it never inspected those headers), and `WebhookMetadata` is built with the attacker-chosen `shop`/`topic`/`webhook_id`: [5](#0-4) 

This is the same class of defect as the "fake token" report referenced: an entity (there, the ERC20 token address; here, the `shop`/`topic` claims) is acted upon by business logic without being bound to the piece of data that was actually authenticated (there, no validation at all; here, HMAC covers only the body, not the headers that identify the tenant).

### Impact Explanation
Any consumer application built on this gem that uses `WebhookMetadata#shop` to key data by tenant (a extremely common pattern, since that's the field's entire purpose) can be made to attribute attacker-controlled webhook payloads to a victim shop it has never had any relationship with, or to relabel a payload under a different topic than what was actually delivered. This is a cross-tenant identity-binding break reachable by any actor who can install the app on any shop (a normal, unprivileged action) and capture one real webhook delivery — no access to `api_secret_key`, access tokens, or the app's infrastructure is required.

### Likelihood Explanation
Likelihood is high: capturing a legitimate webhook delivery only requires installing the app (or using a store the attacker controls) and observing one webhook call; forging arbitrary HTTP headers on a replayed request to the app's public webhook endpoint requires no special capability.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (or otherwise cryptographically bind them, e.g., by canonicalizing header+body into `to_signable_string`) in the HMAC-covered payload before comparing signatures, or have `Registry.process` cross-check these header values against fields present inside the verified body when Shopify's webhook payload includes them.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a shop they legitimately control) and triggers/receives a real webhook, capturing `raw_body`, `x-shopify-hmac-sha256`, and other headers.
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because the signed content (`raw_body`) is unchanged, and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, ...)`, exactly as demonstrated by the header composition used in the existing test setup: [6](#0-5)
