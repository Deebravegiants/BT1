## Title
Unrestricted Arbitrary Calls via the Shared `CallDispatcher` Allow Draining of Un-Swept Token Balances — (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` routes every order's `predispatch`/`postdispatch` calldata through a single, protocol-wide `CallDispatcher` instance (`_params.dispatcher`), the same architectural pattern as the audited `OpportunityAdapter._callTargetContract`. `CallDispatcher.dispatch` performs unrestricted `.call{value}(data)` to any attacker-chosen `to` with attacker-chosen `data`, with the only check being that `to` has code. Because the dispatcher is a **single shared contract used by every user's order**, not an isolated per-user instance, any user can submit a cheap order whose calldata calls `approve(attacker, type(uint256).max)` on an arbitrary ERC20 from the dispatcher. Combined with the fact that the gateway's automatic sweep logic only recovers tokens explicitly declared in `order.inputs`/`order.output.assets`, any token balance that ends up on the dispatcher outside those declared sets (e.g. from another user's DeFi-routing calldata, or from an attacker's own crafted follow-up transfer) becomes permanently drainable by the holder of that standing approval — exactly the allowance-abuse pattern described in the external report.

### Finding Description
`CallDispatcher.dispatch` in `evm/src/utils/CallDispatcher.sol:44-62` executes an arbitrary, caller-supplied `Call[]` with no allowlist on target or selector: [1](#0-0) 

This dispatcher is a single deployment referenced by every order via `_params.dispatcher`, not deployed per user/per order, as seen in both the predispatch path in `IntentGatewayV2.placeOrder`: [2](#0-1) 

and the postdispatch path in `IntentsBase._execute`: [3](#0-2) 

Crucially, the automatic sweep-back that follows dispatch only recovers the balances of tokens that are explicitly declared as `order.inputs` (predispatch) or `order.output.assets` (postdispatch) — it iterates `inputsLen`/`outputsLen` and pulls `IERC20(token).balanceOf(dispatcher)` for those specific tokens only: [4](#0-3) [5](#0-4) 

Any ERC20 token that the dispatcher ends up holding but that is *not* declared in that specific order's `inputs`/`output.assets` (for example, an intermediate token produced by another user's DeFi-composition calldata, per the documented "swap-then-escrow" and "fill-then-act" patterns) is never automatically swept and can sit on the dispatcher indefinitely.

Because `dispatch()` places no restriction on the call's target or selector, a user can submit their own low-cost order whose `predispatch.call`/`output.call` includes a `Call{to: <any ERC20>, data: approve(attacker, type(uint256).max)}`. This executes with `msg.sender == CallDispatcher`, permanently granting `attacker` an unlimited allowance over that token *from the dispatcher*. From then on, whenever any balance of that token (dust, un-declared intermediate tokens from other users' composed calls, or direct transfers-in) sits on the dispatcher, `attacker` can call the ERC20 contract's `transferFrom(dispatcher, attacker, amount)` directly — completely bypassing `IntentGatewayV2` — draining funds that belong to other users or to the protocol.

This is structurally identical to the reported `OpportunityAdapter` bug: an unprivileged caller can direct a shared, allowance-capable contract to make an arbitrary call, and the resulting approval/allowance state is not isolated per user, so it can be weaponized against value the contract holds on behalf of others.

### Impact Explanation
An attacker can permanently self-approve on any ERC20 token from the shared `CallDispatcher` at negligible cost (one order with minimal escrow), then drain any token balance the dispatcher subsequently accumulates that falls outside the declared input/output set for the order that produced it. Since `CallDispatcher` is explicitly designed to route composable DeFi calls (swaps, lending interactions) on behalf of arbitrary users' orders, and the sweep logic is scoped only to declared tokens, this is a realistic path to persistent, unbounded theft of funds transiting through the gateway's shared execution helper — not a resource-only or no-impact issue.

### Likelihood Explanation
Likelihood is high for the setup step: any unprivileged user can place a trivial order with malicious `predispatch.call`/`output.call` to obtain the standing approval, since `CallDispatcher.dispatch` performs no validation on call target/selector beyond `extcodesize(to) != 0`. The subsequent drain requires the dispatcher to actually hold a balance of the approved token outside the declared sweep set, which depends on other orders' composability usage (swaps producing extra/different tokens) — a documented, encouraged usage pattern (`Calldata support` for swap-then-escrow and fill-then-act), making the precondition realistically reachable over time rather than purely theoretical.

### Recommendation
Do not allow arbitrary `approve`/allowance-granting calls to persist on a shared `CallDispatcher`. Either:
1. Restrict `CallDispatcher.dispatch` to disallow ERC20 `approve`/`increaseAllowance`/`permit`-style selectors on tokens, or force allowances to be reset to zero after each `dispatch()` invocation (revoke any approvals granted mid-call before returning).
2. Follow the report's own remediation pattern: deploy an isolated `CallDispatcher` per order/user via `Create2`, so no approval or residual balance set by one user's calldata can ever be reachable by another user.
3. Additionally, make the sweep-back logic recover the *full* balance of every token actually touched by the dispatched calls (not only the tokens pre-declared in `order.inputs`/`order.output.assets`), so no token balance is ever left resident on the shared dispatcher between transactions.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with a minimal `predispatch` (or `fillOrder`/`placeOrder` with `output.call`) whose `Call[]` (decoded by `ICallDispatcher.dispatch`, see `evm/src/apps/intentsv2/IntentsBase.sol:498-503` / `evm/src/apps/IntentGatewayV2.sol:258`) contains `Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})`.
2. This executes with `msg.sender == CallDispatcher`, so `USDC.allowance(CallDispatcher, attacker) = type(uint256).max` — a state that outlives the transaction.
3. At any later time, if `CallDispatcher` holds a USDC balance that is not part of the specific order's declared `inputs`/`output.assets` sweep set (e.g., an intermediate token from another user's composed swap-then-escrow/fill-then-act calldata, per `docs/content/developers/evm/intent-gateway/overview.mdx:87-112`), the attacker calls `USDC.transferFrom(CallDispatcher, attacker, USDC.balanceOf(CallDispatcher))` directly on the token contract — no interaction with `IntentGatewayV2` required — draining the balance.

            Call memory call = calls[i];

                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
