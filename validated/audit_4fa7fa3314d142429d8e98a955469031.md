### Title
Cross-tenant webhook spoofing via unsigned `X-Shopify-Shop-Domain` header trusted by `Registry.process` - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the raw webhook body's HMAC via `Utils::HmacValidator.validate`, then trusts `request.shop`, which is read straight from the unsigned `X-Shopify-Shop-Domain` header, to build `WebhookMetadata` passed to the app's handler. Because the HMAC secret (`Context.api_secret_key`) is a single app-wide secret shared across every shop that installs the app, and the signature covers only `@raw_body`, an attacker who owns a legitimately-installed shop can capture their own validly-signed webhook and replay it with the shop header swapped to a victim shop domain, and it will pass validation.

### Finding Description
The broken binding: `request.shop` (unauthenticated, header-derived) is treated as if it were bound to `request.hmac`/`@raw_body` (the only authenticated material), i.e. the code assumes `HMAC_valid(raw_body) => shop_header_is_authentic`, but no such equality actually holds.

Code path:
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` reads the unsigned `shop-domain` header: [2](#0-1) 
- `HmacValidator.validate_signature` recomputes HMAC over `verifiable_query.to_signable_string` (i.e., body only) using `Context.api_secret_key`, a single app-wide secret shared by all shops that install the app: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata` dispatched to the handler: [4](#0-3) 

Exploit flow: attacker installs the target app on their own shop `attacker.myshopify.com` (a legitimate, unprivileged action), registers a webhook, and receives a real Shopify-signed callback: body `B`, header `X-Shopify-Hmac-Sha256` = HMAC(`B`, app's shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`. The attacker then POSTs the identical `B` and identical HMAC header to the app's shared webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. Since `to_signable_string` never includes the shop header, `HmacValidator.validate` still succeeds (the secret is the same app-wide secret regardless of which shop sent it), and `Registry.process` dispatches `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` to the handler, which now believes attacker-originated webhook data belongs to the victim tenant.

No existing guard closes this gap: `HmacValidator.validate` only proves the request was HMAC-signed by *some* installation of the app (it does not, and structurally cannot, prove which shop), and `Registry.process` performs no cross-check between the authenticated body/topic and the claimed shop domain.

### Impact Explanation
Any app that keys per-tenant logic off `WebhookMetadata#shop` (e.g. updating victim-shop records, deciding fulfillment, GDPR/redact handling, billing) can be fed attacker-controlled webhook data attributed to an arbitrary victim shop. This is a cross-tenant data-integrity/confidentiality issue: attacker gets one legitimately-signed message accepted under another tenant's identity, repeatable for every webhook topic and for any victim shop domain the attacker chooses (victim shop domains for merchants using an app are often guessable/discoverable), matching the Critical/cross-tenant category.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's capability: register a free/development shop, install the target app on it (a standard, permitted action), register at least one webhook topic to receive one authentic signed callback, then replay it to the shared webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secrets, tokens, or victim cooperation are required, and the attack is repeatable per topic/victim.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` as authenticated. At minimum, cross-validate the shop domain in `Registry.process` against the shop the app expects for that specific installation/session context (e.g., look up an active session/shop tied to the webhook's `X-Shopify-Webhook-Id`/subscription rather than trusting the header), or require app code to independently confirm the claimed shop is one that actually has this webhook topic registered for it before dispatching. Document clearly that `WebhookMetadata#shop` is not covered by the HMAC signature and must not be trusted for authorization decisions without further verification.

### Proof of Concept
```ruby
# test/webhooks/registry_spoof_test.rb
require "test_helper"

class RegistrySpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: RecordingHandler.new
    )
  end

  def test_cross_tenant_webhook_spoof
    body = '{"id":1,"note":"attacker-controlled-data"}'
    hmac = OpenSSL::HMAC.digest("sha256", "secret", body)
    b64  = Base64.strict_encode64(hmac)

    # This is exactly what attacker received on their own shop:
    attacker_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => b64,
      "x-shopify-shop-domain" => "attacker.myshopify.com",
      "x-shopify-api-version" => "2024-01",
      "x-shopify-webhook-id" => "1",
    }

    # Replayed to victim with only the shop header swapped
    spoofed_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

    request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)

    ShopifyAPI::Webhooks::Registry.process(request) # does not raise -> HMAC still validates

    assert_equal "victim-shop.myshopify.com", RecordingHandler.last_data.shop
    assert_equal "attacker-controlled-data", JSON.parse(RecordingHandler.last_data.body.to_json)["note"]
    # Binding check: signature is valid for body B, yet claimed shop != originating shop
    assert ShopifyAPI::Utils::HmacValidator.validate(request)
  end
end
```
This demonstrates that `HmacValidator.validate(request) == true` while `request.shop` (`"victim-shop.myshopify.com"`) has no cryptographic relationship to the signed body, proving the binding `HMAC_valid(raw_body) => shop_header_authentic` does not hold.
