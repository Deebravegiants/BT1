### Title
Webhook Shop-Domain Spoofing via HMAC Scope Mismatch - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to fully "verify the request did indeed come from Shopify" before dispatching the webhook to the app's handler, but the HMAC signature computed by the gem only covers the raw request body, never the `shop-domain` header that is handed to the handler as the tenant identifier. An attacker who can obtain any body+HMAC pair signed with the app's shared secret (e.g. by installing the app on their own shop and receiving a real, validly-signed webhook) can replay that same body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will report the request as fully verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate header that is never part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC strictly over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` gates entirely on this HMAC check and then forwards `request.shop` (the unauthenticated header) as the tenant identity to the app's handler: [4](#0-3) 

The gem's own documentation asserts that calling `process` "will verify the request did indeed come from Shopify," and separately documents `data.shop` as a trusted field ("The shop domain of the webhook") without qualification: [5](#0-4) [6](#0-5) 

The identity binding broken is: `shop authenticated-by-HMAC` ≠ `shop delivered-to-handler`. The HMAC only authenticates the byte-string of the body; the `shop-domain` header used for tenant routing/dispatch is parsed but never bound to those authenticated bytes.

### Impact Explanation
Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any unprivileged internet user can become a legitimate, low-privilege tenant (install the target app to their own free/dev store) and thereby legitimately receive real webhook deliveries with valid HMAC signatures for their own shop. They can then capture one such (body, HMAC) pair and replay it directly to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a victim shop. `Registry.process` will validate successfully (the HMAC still matches the unmodified body) and will invoke the app's handler with `WebhookMetadata(shop: <victim-shop>, body: <attacker-controlled data>)`. Any host application that uses `data.shop` to key its persistence/dispatch layer (exactly as the gem's own documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied data under the victim shop's tenant record. This is a cross-tenant data-integrity breach directly enabled by a gap in this gem's own verification guarantee.

### Likelihood Explanation
High feasibility: the attack requires no secrets, no privileged account, and no interception — only the ability to install the target Shopify app on a shop the attacker controls (freely available via Shopify dev/partner stores) and the ability to POST an HTTP request with custom headers to the app's public webhook URL. The HMAC secret never needs to be known or broken; a legitimately-issued signature is reused verbatim.

### Recommendation
Bind the identity used for tenant dispatch to the authenticated bytes. Options:
- Include the `shop-domain` (and `webhook-id`/`topic`) in the HMAC-signable string (`to_signable_string`) so any header tampering invalidates the signature, or
- Independently verify that the shop asserted in the header corresponds to a shop known to have an active/registered webhook subscription (e.g., cross-check `webhook_id` against Shopify's API for that shop) before dispatching, or at minimum
- Update the documentation to explicitly state that only the raw body is authenticated and that `shop`/`topic`/`webhook_id` headers are NOT covered by the HMAC, so host applications do not treat `data.shop` as a verified tenant identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` — both valid under the app's real `api_secret_key`.
2. Attacker sends a forged HTTP POST directly to the app's registered webhook path:
   ```
   POST /callback/orders/create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <any>
   Body: B
   ```
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...}))`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, which matches `H`, so `process` passes validation: [7](#0-6) 
5. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and, following the gem's own documented handler pattern, applies attacker-controlled data to the victim shop's tenant record.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
