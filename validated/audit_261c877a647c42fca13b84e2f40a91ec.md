### Title
Webhook shop-tenant identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the webhook HMAC to the raw body only, while `shop`, `topic`, `webhook_id` and `api_version` are read straight from HTTP headers with no cryptographic binding to that signature. `Registry.process` validates the HMAC and then blindly trusts `request.shop` as the tenant identity handed to the app's handler. Because a Shopify app's `client_secret` (and thus its webhook HMAC secret) is shared across every merchant that installs the app, any unprivileged user who installs the app on their own store can capture one of their own genuinely-signed webhook deliveries and replay it against the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop, producing a request that still passes HMAC validation but is attributed to the victim tenant.

### Finding Description
`to_signable_string` only returns `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers that are never fed into the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely against `to_signable_string` (i.e., the body) with the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately forwards the *unverified* `request.shop` header value to the app's handler as the authoritative tenant identity: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body, api_secret_key) ⇒ shop_header == shop_that_actually_sent(body)`

but the library only proves `hmac_valid(body, api_secret_key)`; it never proves the second half of that equality. Since `api_secret_key` is the same for every merchant that installs a given app, possession of one valid `(body, hmac)` pair from *any* shop is sufficient to forge a request that will validate for *any other* shop, simply by changing the `shopify-shop-domain` header.

### Impact Explanation
This breaks the shop/tenant identity binding without requiring the attacker to know `api_secret_key`, an access token, or any victim credential — only the ability to install the app on an attacker-owned store (a normal, unprivileged action for public apps). The forged request is processed with `WebhookMetadata#shop` set to the victim's domain: [5](#0-4) 
Any app whose webhook handlers key persistence, cache invalidation, or business logic (e.g., `app/uninstalled`, `orders/create`, `shop/update`) off `data.shop` can be made to attribute attacker-controlled data to a victim tenant — a cross-tenant access/injection primitive, matching the "Critical – cross-tenant access" impact class.

### Likelihood Explanation
The attack requires only: (1) installing the target app on an account the attacker controls (trivial for any public app), (2) capturing one legitimate webhook delivery (trivially logged by the attacker's own endpoint), and (3) replaying it with a modified `shopify-shop-domain` header to the shared webhook endpoint. No secret material, token, or privileged access is needed, making this practically reachable by any unprivileged internet user targeting a multi-tenant Shopify app built on this library.

### Recommendation
Bind the tenant/topic/webhook identity into the verified signature surface rather than trusting raw headers post-hoc: derive `shop` from a source that is cryptographically tied to the request (e.g., cross-check against a per-shop registered webhook subscription/state, or require verification that the delivering shop matches an installation record) before dispatching to handlers, and document/require that handler implementations never trust `WebhookMetadata#shop` as a security boundary without such a check.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one delivery's raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker POSTs `B` with header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` to the app's public webhook endpoint.
4. `Utils::HmacValidator.validate` succeeds (it only checks `B` against `H`) — [6](#0-5) .
5. `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` — [5](#0-4)  — even though the request never originated from Shopify on behalf of `victim.myshopify.com`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
