## Analog Found

### Title
`CallDispatcher.dispatch()` has no caller restriction, letting anyone drain any token/ETH balance left in the shared cross-app dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The Wazuh CVE-2023-50260 bug class is: a component intended to only ever execute pre-validated, trusted commands (`host_deny`, gated behind the active-response allowlist) instead accepts attacker-influenced content and executes it with elevated privileges because the validation guarding *who* can trigger execution and *what* gets executed is missing/incomplete. The direct analog in Hyperbridge is `CallDispatcher`, the shared execution primitive used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to run arbitrary attacker/solver-supplied `Call[]` batches. `dispatch(bytes)` is `external` with **no caller restriction whatsoever** — it does not check `msg.sender`, and it is not `onlyHost`, `onlyGateway`, or reentrancy-guarded.

### Finding Description
`CallDispatcher.dispatch` decodes an ABI-encoded `Call[]` and blindly executes each call against `call.to` with `call.value` from whatever native/ERC20 balance the `CallDispatcher` currently holds: [1](#0-0) 

This contract is intentionally shared infrastructure across multiple apps — `IntentsBase._execute` sends order-specified assets to it and invokes `dispatch` [2](#0-1) , and `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` forward `message.data` to the same dispatcher pattern [3](#0-2) . The design assumes each caller sweeps its own dust back out in the same transaction — the docs explicitly acknowledge this is fragile: *"Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution."*

Because `dispatch()` has no access control and the receive function is also unrestricted (`receive() external payable {}`), any value that ends up sitting in the `CallDispatcher` — stray native ETH, an unswept ERC-20 balance left behind when a swap/route produces a token that isn't in the caller's expected sweep list, or a still-live ERC-20 approval granted to a third-party spender during a `Call[]` that wasn't fully consumed — is directly reachable and stealable by *any* unprivileged address. An attacker does not need to interact with the Intent Gateway or the HFT apps at all; they can call `CallDispatcher.dispatch()` themselves with a `Call[]` that transfers out any token balance or spends down any outstanding allowance the dispatcher holds, since the contract has no notion of "this call must originate from one of the registered gateways."

This is structurally the same failure mode as the CVE: a privileged execution path (`host_deny` spawn / `CallDispatcher.dispatch`) that is supposed to be reached only through a validated, gated flow instead accepts and executes attacker-supplied "commands" (shell string / `Call[]`) because the entry point performs no authorization check on the caller.

### Impact Explanation
Any token or native balance transiently or accidentally retained by the shared `CallDispatcher` (dust from swap slippage, unswept output tokens in flows not enumerated by the caller's sweep loop, or outstanding ERC-20 allowances left after a partially-consuming `Call[]`) can be stolen by an arbitrary external address, with no relationship to the order/message that produced the balance. Given the dispatcher is shared across the Intent Gateway, `HyperFungibleToken`, and `WrappedHyperFungibleToken`, this is a cross-app theft surface rather than one confined to a single app's accounting.

### Likelihood Explanation
Exploitability requires the `CallDispatcher` to actually hold value at the moment of attack. The `_execute` sweep in `IntentsBase` only sweeps the assets it knows to expect (`outputsLen` entries) [4](#0-3) , so any DeFi routing calldata that produces a token not accounted for in that list (e.g., reward tokens, extra swap-path output, rounding remainders on multi-hop routes) leaves a balance in the dispatcher that persists past the transaction and is then permissionlessly drainable. The project's own comments acknowledge the allowance-lingering risk as a known caveat rather than an enforced invariant, indicating this is a realistic operational condition, not a purely theoretical one.

### Recommendation
Restrict `CallDispatcher.dispatch` to an allowlisted set of caller contracts (the registered gateway/app addresses), or make the dispatcher per-caller/per-order (e.g., deploy an ephemeral or `msg.sender`-scoped dispatcher, or require `dispatch` to be invoked only via `delegatecall`/internal library so it never holds standalone balance). At minimum, add a reentrancy guard and an explicit sweep-everything path invoked atomically by the trusted app before control returns to any external context, and avoid contracts registering unlimited approvals to the shared dispatcher.

### Proof of Concept
1. A solver fills an Intent Gateway order whose `output.call` routes through a DEX aggregator that occasionally returns a small amount of an incentive/reward token not present in `order.output.assets`, or where the executed route grants an ERC-20 `approve` to a router for more than is ultimately spent.
2. `IntentsBase._execute` only builds sweep calls for the known `outputsLen` tokens [4](#0-3) ; the reward token balance or the residual allowance remains on the `CallDispatcher` after the transaction completes.
3. Any attacker (unrelated to the order) calls `CallDispatcher.dispatch(abi.encode([Call({to: rewardToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — no permission check prevents this [5](#0-4)  — or calls `dispatch` with a `Call` that invokes `transferFrom` against the leftover approval, moving the funds to themselves.

```text
    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
