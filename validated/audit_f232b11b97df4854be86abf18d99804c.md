### Title
Missing pre-deserialization size gate in `decode_signed_transaction` allows borsh allocation amplification DoS via public RPC - ([File: chain/jsonrpc/src/api/transactions.rs])

### Summary
`decode_signed_transaction` base64-decodes an attacker-supplied string and immediately calls `SignedTransaction::try_from_slice(&bytes)` with no check of `bytes.len()` against any transaction-size limit before deserialization begins. Because borsh derives length-prefixed collection deserialization (e.g. `Vec<u8>` for `FunctionCallAction::args`, `Vec<String>` for method-name-like fields, `Vec<Action>`) that allocate memory sized from the attacker-controlled length prefix before the reader has verified that many bytes actually exist in the buffer, a small crafted payload can trigger allocation far larger than the wire size, well before `ValidatedTransaction::check_valid_for_config`/`validate_actions` (in `runtime/runtime/src/verifier.rs`) or any gas/size metering ever executes.

### Finding Description
The RPC entry point is: [1](#0-0) 

This function is reached directly from `RpcSendTransactionRequest::parse`, used by both `broadcast_tx_async`/`broadcast_tx_commit`/`send_tx`: [2](#0-1) 

There is no size check on `bytes` (the base64-decoded payload) prior to calling `try_from_slice`. All size/limit validation that exists in the codebase (`max_receipt_size`, `LimitConfig`, action validation via `validate_transaction`/`validate_transaction_actions`) only runs after a `SignedTransaction`/`Transaction` object has already been fully constructed: [3](#0-2) 

The only `MAX_TRANSACTION_SIZE_BYTES`-style gate found in the repo lives in `chain/network` (peer-message/proto conversion), which is applied to P2P-relayed messages, not to the direct HTTP JSON-RPC submission path — confirming the RPC path has no equivalent pre-check.

The root cause is architectural: nearcore's own RPC deserialization code never validates the raw byte length of the payload against `max_transaction_size` (or any bound) before invoking `try_from_slice`, unlike the defense present at the network layer. Borsh's length-prefixed collection deserialization for types such as `Vec<u8>` (`FunctionCallAction::args`) reads a 4-byte length prefix and allocates a buffer of that declared size before confirming the remaining input actually contains that many bytes, so a payload of only a few bytes that declares a large length can force a disproportionately large allocation attempt prior to any error being returned. This lets an attacker convert a modest base64 request (well under the 10MB HTTP body limit) into a memory-allocation spike, independent of and prior to the transaction/action validation gates in `verifier.rs`.

### Impact Explanation
This maps to the "node panic or unbounded resource use" impact class: an unprivileged account holder (or even an unauthenticated caller, since RPC transaction submission requires no on-chain permission) can send crafted base64 payloads to `broadcast_tx_async`/`broadcast_tx_commit`/`send_tx` repeatedly, forcing the RPC node to attempt large memory allocations before any cost is charged or any size/action validation occurs. Repeated requests can exhaust node memory/CPU, causing degraded RPC availability or process termination (OOM kill), a liveness impact scoped to the RPC node.

### Likelihood Explanation
Preconditions are trivial: normal, direct access to a public JSON-RPC endpoint, no special privileges, and a payload within the existing 10MB HTTP body limit. The attack is fully reproducible and repeatable, and can be scripted to hit multiple RPC nodes simultaneously, amplifying the effect. Note: the precise magnitude of memory amplification depends on the pinned `borsh` crate's internal Vec/String deserialization allocation strategy (an external dependency behavior I could not fully verify from the repo alone, since `borsh`'s source is not part of this codebase) — but regardless of the exact amplification factor, the codebase itself lacks any defense-in-depth check comparable to the network-layer size gate, so the RPC path is structurally exposed to this class of issue.

### Recommendation
Add an explicit length check in `decode_signed_transaction` (or in the base64-decoding step) that rejects payloads whose raw byte length exceeds the configured `max_transaction_size` (mirroring `RuntimeConfig`'s transaction/receipt size limits and/or `chain/network`'s `MAX_TRANSACTION_SIZE_BYTES`) before calling `SignedTransaction::try_from_slice`. Consider also using a streaming/limited-length borsh reader or `try_from_slice_with_limit`-style API if available, so that even nested collection length prefixes cannot request allocations beyond the remaining input size.

### Proof of Concept
Integration test plan:
1. Construct a minimal borsh byte sequence representing a `SignedTransaction` where `Transaction.actions` contains a single `Action::FunctionCall` whose `args` field's length prefix (`u32`) is set to a large value (e.g. `u32::MAX` or several hundred MB) while the actual byte buffer following the prefix is only a few bytes (deliberately truncated/invalid).
2. Base64-encode this small buffer (well under the 10MB HTTP limit) and POST it via `send_tx`/`broadcast_tx_async` to `decode_signed_transaction`.
3. Measure peak process memory / allocation size during the call to `SignedTransaction::try_from_slice(&bytes)`.
4. Assert either (a) the call fails fast with a bounded-memory error due to a length pre-check comparing `bytes.len()` to `max_transaction_size`, or (b) currently, that allocation is attempted proportional to the declared (attacker-controlled) length rather than the actual payload size — demonstrating the missing gate.

fn decode_signed_transaction(value: String) -> Result<SignedTransaction, RpcParseError> {
    let bytes = near_primitives::serialize::from_base64(&value)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))?;
    SignedTransaction::try_from_slice(&bytes)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))
}

/// Validates the transaction without using the state. It allows any node to validate a
/// transaction before forwarding it to the node that tracks the `signer_id` account.
#[allow(clippy::result_large_err)]
pub fn validate_transaction(
    config: &RuntimeConfig,
    signed_tx: SignedTransaction,
    current_protocol_version: ProtocolVersion,
) -> Result<ValidatedTransaction, (InvalidTxError, SignedTransaction)> {
    if let Err(err) = validate_transaction_actions(&config, &signed_tx, current_protocol_version) {
        return Err((err, signed_tx));
    }
    ValidatedTransaction::new(config, signed_tx, current_protocol_version)
}
