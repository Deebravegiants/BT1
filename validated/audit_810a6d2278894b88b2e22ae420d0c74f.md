### Title
Cache-key collision via unpadded string concatenation in `confidentialrelay` response cache enables cross-request response confusion - (File: `core/capabilities/confidentialrelay/response_cache.go`)

### Summary
The `capExecKey` and `secretsKey` functions in `core/capabilities/confidentialrelay/response_cache.go` build cache/dedup keys by joining several dynamic-length, attacker-influenced string fields with a fixed `"/"` separator, analogous to `abi.encodePacked()` on dynamic types before hashing/keying. Because none of the joined fields are length-prefixed or delimiter-escaped, two logically distinct requests can be crafted to produce the same cache key, letting one requester's pending/cached result be delivered to (or shared with) a different workflow/execution/reference context.

### Finding Description
`capExecKey` builds the deterministic key for a capability-exec request: [1](#0-0) 

and `secretsKey` builds the key for a secrets-get request: [2](#0-1) 

Both use `strings.Join` with `"/"` as separator over dynamic strings (`WorkflowID`, `ExecutionID`, `ReferenceID`, `CapabilityID`, or `CallbackID`) taken directly from `CapabilityRequestParams`/`SecretsRequestParams`. This is the same root-cause pattern flagged in the external report: concatenating multiple dynamic-length values with a delimiter (instead of a length-prefixed/padded encoding) before using the result as a lookup/dedup key allows an attacker who controls the boundaries of these fields to shift a delimiter character into an adjacent field and produce a colliding key for a different logical request, e.g. `["wf/A", "exec", "ref", "cap"]` colliding with `["wf", "A/exec", "ref", "cap"]`.

This key is used to register and look up in-flight requests in a shared, node-wide cache: [3](#0-2) 

and to publish/complete the result that other waiters on the same key will receive: [4](#0-3) 

If a colliding key is produced for two different logical requests (e.g., from two different workflow executions/owners), `checkOrCreatePendingRequest` will treat the second, distinct request as a duplicate of the first, causing it to receive the first request's `signed` result via `completePendingRequest` — potentially returning another workflow's/owner's secret-fetch result or exec result to the colliding requester.

### Impact Explanation
The comment in `checkOrCreatePendingRequest`/`completePendingRequest` explicitly states that duplicates "wait on done and then respond with the owner's published signed result." A crafted key collision would mean a caller receives a result value that was computed and signed for a *different* logical (workflow, execution, step, capability) identity — this is a cross-request/cross-workflow response confusion. For `secretsKey`, this could mean a party receives the result meant for a different `SecretsRequestParams` tuple. Because the cache is shared across all in-flight relay requests on the node, this could result in unauthorized disclosure of secret-fetch results or capability outputs across execution contexts.

### Likelihood Explanation
Exploitability depends on whether `WorkflowID`, `ExecutionID`, `ReferenceID`, `CapabilityID`, and `CallbackID` are validated to disallow the `/` separator character elsewhere in the pipeline (e.g., at workflow registration or JSON-RPC parameter validation). I was not able to locate charset/format validation for these fields within the code retrieved, so this is uncertain — it is plausible that upstream validation (e.g. workflow ID format checks used elsewhere in the codebase) restricts these to safe charsets, which would reduce or eliminate the practical collision risk. This uncertainty should be verified directly in `confidentialrelaytypes.CapabilityRequestParams`/`SecretsRequestParams` validation code and any additional call sites that construct these params, which were not fully available in the retrieved index.

### Recommendation
Replace the delimiter-based `strings.Join` key construction with a length-prefixed or hash-based encoding that cannot produce collisions across differing field boundaries — e.g., hash each field independently (`sha256(len(a)||a||len(b)||b||...)`) or use a struct-based key (e.g., a fixed-arity tuple/map key) instead of a joined string, mirroring the recommendation to use `abi.encode()` instead of `abi.encodePacked()` for dynamic-type hashing.

### Proof of Concept
Conceptual collision (assuming no upstream restriction on `/` in these ID fields):
- Request A: `WorkflowID="wf1/extra"`, `ExecutionID="e1"`, `ReferenceID="r1"`, `CapabilityID="c1"` → `capExecKey` = `"call-capability/wf1/extra/e1/r1/c1"`
- Request B: `WorkflowID="wf1"`, `ExecutionID="extra/e1"`, `ReferenceID="r1"`, `CapabilityID="c1"` → `capExecKey` = `"call-capability/wf1/extra/e1/r1/c1"`

Both produce the identical key, so if Request A is in-flight, Request B's `checkOrCreatePendingRequest` call at [5](#0-4)  returns the pending entry for A, and B receives A's `signed` payload once A completes, rather than executing/receiving its own distinct request result.

// capExecKey is the deterministic cache key for a capability-exec request,
// built from its logical identity: the (workflow, execution, step, capability)
// tuple the relay-DON signature binds to. Avoids hashing: the fields are
// required non-empty by Validate, so a plain join is stable and debuggable.
func capExecKey(p confidentialrelaytypes.CapabilityRequestParams) string {
	return strings.Join([]string{capabilityCallDomain, p.WorkflowID, p.ExecutionID, p.ReferenceID, p.CapabilityID}, "/")
}

func (h *Handler) checkOrCreatePendingRequest(key string) (*pendingRequest, error) {
	mine := &pendingRequest{done: make(chan struct{})}
	if h.pendingRequests.Add(key, mine, cache.DefaultExpiration) == nil {
		h.lggr.Debugw("registered pending relay request, executing", "key", key)
		return nil, nil
	}
	if existing, ok := h.pendingRequests.Get(key); ok {
		if p, ok := existing.(*pendingRequest); ok {
			h.lggr.Debugw("relay request already in flight, waiting for its result", "key", key)
			return p, nil
		}
	}
	h.lggr.Errorw("pending request cache holds an entry of unexpected type", "key", key)
	return nil, fmt.Errorf("pending set holds an invalid entry for key %q", key)
}
```

// completePendingRequest publishes the owner's signed result and wakes any
// waiters. Called on the execution's success path, after the memo is set, so
// requests arriving later hit the memo instead. An owner that dies without
// completing never publishes; the TTL ages its entry out and waiters fail on
// their own deadlines, which is the "unknown failure" outcome.
func (h *Handler) completePendingRequest(key string, signed any) {
	if v, ok := h.pendingRequests.Get(key); ok {
		if pr, ok := v.(*pendingRequest); ok {
			pr.signed = signed
			close(pr.done)
		}
	}
	h.pendingRequests.Delete(key)
}
```
