### Title
Webhook shop-domain identity not covered by HMAC, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as fully authenticated once `Utils::HmacValidator.validate(request)` returns true, and then dispatches `request.shop` to the app's handler as the trusted tenant identity. However, the HMAC only ever covers the raw request body — the `shop-domain` header is never part of the signed material — so the "verified" bytes and the "shop identity used downstream" are not the same data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unauthenticated header with no cross-check against the signed content: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e. the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check and then forwards the unauthenticated `request.shop` value into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identifier: [4](#0-3) 

Because the HMAC secret is the app's single `client_secret` (`Context.api_secret_key`), shared across every shop that installs the app, any shop owner who legitimately installs the app can receive genuine Shopify-signed webhook deliveries for their own store (body + valid HMAC). Since `shop-domain` is not part of the signed bytes, that same legitimately-signed `(body, hmac)` pair can be re-POSTed by the attacker directly to the app's public, shared webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is attacker-controlled.

This breaks the intended identity binding: `hmac-verified bytes == identity attributed to those bytes`. The gem's own API (`Utils::HmacValidator.validate(request)`) is invoked against the whole `request` object, which reasonably implies the entire request — including the shop attribution used by the caller — is authenticated, but only the body is.

### Impact Explanation
An unprivileged internet user who can install the app on their own (e.g. free/dev) store can forge webhook deliveries that the host application will process believing they originated from an arbitrary victim shop, since the shop identifier the gem hands to the handler is unauthenticated. This is a cross-tenant identity-spoofing primitive at the SDK layer: any host app that relies on `Utils::HmacValidator.validate` + `WebhookMetadata#shop` (exactly as documented/intended by this gem) to trust the shop attribution inherits the exposure.

### Likelihood Explanation
No secrets, tokens, or privileged access are required — only the ability to install the app on an attacker-controlled shop (a free action for any internet user) and the ability to send a direct HTTP POST to the app's already-public webhook endpoint with a captured `(body, hmac)` pair. No TLS interception of a third party is needed, since the attacker only needs to observe traffic delivered to their own installation.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signed/verified material, or explicitly require host apps to cross-check `request.shop` against an independently-established tenant record before trusting it — and update `HmacValidator`/`Registry.process` so a passing HMAC check cannot be read as authenticating the shop header.

### Proof of Concept
1. Attacker creates/uses a free development store and installs the target app, receiving a legitimate webhook delivery to the app's single shared endpoint: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Attacker sends `POST /webhooks` (the app's real, single webhook endpoint) with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` computes HMAC over `B` only [1](#0-0)  and returns `true`.
4. `ShopifyAPI::Webhooks::Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com` [5](#0-4) , causing the app to act on the victim's tenant using attacker-supplied body content.
