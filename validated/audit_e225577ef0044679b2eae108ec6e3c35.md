### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on a validly-signed webhook - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity passed to the app's handler. Because the HMAC never covers the `shop-domain` (or `topic`/`webhook-id`) header, an attacker who can obtain one validly-signed webhook body for the app (e.g., from their own installed/dev shop) can replay it with a different `shop-domain` header and still pass HMAC validation, causing the host app to process the event under a different tenant's identity.

### Finding Description
`Registry.process` verifies authenticity like this: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the HTTP headers, including `shop-domain`, `topic`, and `webhook-id`, are entirely excluded from the signed material: [3](#0-2) 

The `shop` accessor simply reads the unauthenticated header: [4](#0-3) 

This `shop` value (and `topic`/`webhook_id`) is then handed directly to the app's webhook handler as the trusted tenant identity for the event, without any binding to the HMAC-verified bytes: [1](#0-0) 

The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_shop`. In this implementation, `hmac_signed_bytes = raw_body` while `shop_used_by_handler = header["shopify-shop-domain"]`, which are disjoint — the HMAC never covers the field that determines which tenant the event is attributed to.

### Impact Explanation
An attacker who legitimately controls (or has installed) the app on their own shop receives real, validly-HMAC-signed webhooks from Shopify for that shop (all shops of a given app share the same `api_secret_key`, so the HMAC computation is identical regardless of shop). Because the signature covers only the body, the attacker can replay that captured request to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header for a victim shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and dispatch the handler with `WebhookMetadata.shop` set to the victim's domain. Depending on how the host app implements its handlers (a documented, expected use of this gem's `shop` metadata field), this enables cross-tenant confusion — e.g., forging an `app/uninstalled` or `shop/redact` event attributed to a shop the attacker does not control, or injecting attacker-controlled body content that the host app processes as if it came from the victim tenant. This crosses a tenant boundary using only the app's shared secret material that any installed shop already legitimately possesses via genuine Shopify traffic, which is a cross-tenant access vector.

### Likelihood Explanation
Requires the attacker to have (or create) a shop where the app is installed — a normal, unprivileged action available to any internet user who installs a public/dev app — and to capture one legitimate webhook delivery for that shop (feasible since it is delivered to a URL the attacker/app developer controls or can proxy). No access to `api_secret_key` or any merchant's access token is needed. The replay only requires modifying an HTTP header the gem never authenticates.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the HMAC-signed material (e.g., bind them into `to_signable_string` or verify them via an additional signature/derivation from the body/shop pair) so the shop identity cannot be altered independently of the HMAC-verified bytes. At minimum, document and/or enforce that the `shop` used by `Registry.process` must be re-validated against a source that is covered by the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's endpoint with headers:
   `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and body `B`.
3. Attacker captures this request (e.g. via their own reverse proxy/logging in front of the endpoint they control, or via ngrok during development) and replays it to the app's webhook endpoint, changing only:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
   leaving `x-shopify-hmac-sha256` and body `B` unchanged.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`, the raw body) and compares — this succeeds because the body wasn't altered.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-supplied data under the victim's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
