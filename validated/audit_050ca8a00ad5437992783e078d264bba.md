### Title
Attacker-controlled route venue drains the caller's wallet by piggybacking a token transfer onto the caller's `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller relays caller-supplied `swap` bytes verbatim to the configured router via `router.execute_strategy(&controller, &amount_in, swap)` inside `swap_tokens` (contracts/controller/src/strategies/swap.rs:13-55). The route payload names venue (pool) and token addresses that the router calls without any allowlist; the threat model itself documents that "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (docs/explanation/threat-model.md:154-165). This is the on-chain shape of CVE-2026-12605: an attacker-chosen destination (the SSRF host / rogue hop pool) executes inside the victim's authenticated context and exfiltrates the victim's assets (the `gfresttoken` / the caller's token balances) to an attacker-controlled address.

### Finding Description
`swap_tokens` authorizes exactly one nested `token_in.transfer(controller, router, amount_in)` on behalf of the controller via `authorize_transfer_as_current` (common/src/token.rs:36-52), then invokes the router under the flash guard. The route bytes come from the caller and are not restricted to governance-vetted venues; `swap_tokens_or_passthrough` (swap.rs:57-72) is reached from `swap_debt`, `swap_collateral`, `multiply`, and `repay_debt_with_collateral`.

A malicious route names an attacker-deployed "pool" contract. When the router invokes it during hop dispatch, that contract calls `token::Client::transfer(victim_caller, attacker, wallet_balance)`. Because the victim is the authorizing root of the transaction, recording mode attaches this transfer as a child of the victim's own `swap_collateral` auth entry, and enforcing mode executes it if the victim signs the simulated tree — exactly the tested behavior in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`, which shows `WALLET_BALANCE` of an unlisted, protocol-unrelated token moving from Alice to the attacker inside a benign-looking `swap_collateral` that still pays fair output and passes all post-checks (`RouterOverspend`, `NoSwapOutput`, solvency gates).

No controller-side mitigation exists: the controller cannot see or bound transfers made from the caller by third-party code placed on the stack by the route, and its balance-delta checks only cover the controller's own `token_in`/`token_out` balances (swap.rs:40-54).

### Impact Explanation
Theft of user funds: the victim loses any token balance in their wallet that the rogue venue names — unbounded by `amount_in`, the payload minimum, or the final risk gates (threat-model.md:158-161). The swap itself can still succeed normally, so the theft is invisible to protocol accounting.

### Likelihood Explanation
Requires a victim to sign a transaction whose simulated auth tree contains the extra child entry — directly analogous to the CVE's `UI:R` authenticated-admin precondition. An unprivileged attacker only needs to get the crafted route bytes to the victim (phishing quote, malicious frontend/aggregator, or a doctored quote service response). The mechanism is fully demonstrated by the in-repo test double (`UnlistedPoolRouter`/`RogueHopPool`) and recorded auth-tree assertion.

### Recommendation
Constrain routes to a governance-managed allowlist of venue/pool addresses enforced before or inside `execute_strategy` (mirroring the Blend-pool approval model in `authorize_repay_pulls`, contracts/controller/src/external/blend.rs:103-120), or have the router reject any sub-invocation it did not self-authorize. Until then, clients must refuse to sign any authorization tree containing a child entry other than the single expected input transfer, as the threat model prescribes.

### Proof of Concept
1. Attacker deploys a contract `RogueHopPool` with a `swap()` method that calls `token.transfer(victim, attacker, victim_balance)` on a token the victim holds (need not be protocol-listed).
2. Attacker crafts route bytes naming `RogueHopPool` as a hop venue and convinces the victim to run `swap_collateral(caller=victim, account_id, spoke_id, collaterals, debt_asset, swap=route, ...)` (or `swap_debt`/`multiply`/`repay_debt_with_collateral`).
3. Simulation (recording mode) attaches `token.transfer(victim → attacker, balance)` as a child of the victim's `swap_collateral` authorization entry; the swap still pays a fair output, so nothing looks wrong besides the extra auth child.
4. Victim signs the simulated tree; enforcing mode executes the nested transfer. The test asserts `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and a normal credited `supply_balance` (rogue_hop_pool_transfer_joins_caller_auth_tree.rs:224-226).

Uncertainty note: this exposure is already documented in `docs/explanation/threat-model.md:154-165` with a client-side mitigation, so a reviewer may classify it as a documented design limitation rather than a code defect; however, the on-chain enforcement gap (no venue allowlist in the controller/ router dispatch path reachable from in-scope `swap.rs`) is what makes the leak possible.
