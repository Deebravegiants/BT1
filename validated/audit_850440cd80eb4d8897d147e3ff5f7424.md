This confirms the analog. In the OAuth callback flow, `AuthQuery#to_signable_string` explicitly includes `shop` in the HMAC-signed string [1](#0-0) , so the shop identity is cryptographically bound to the signature. By contrast, in the webhook flow, `Request#to_signable_string` returns only the raw body [2](#0-1) , while `shop` is read directly from an HTTP header that is never included in the signed payload [3](#0-2) . `Registry.process` validates the HMAC and then passes `request.shop` straight into `WebhookMetadata` handed to the app's handler with no cross-check against the body or any other shop-bound claim [4](#0-3) , and `WebhookMetadata.shop` is a plain unauthenticated field [5](#0-4) .

### Title
Webhook `shop` field is not covered by HMAC, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw request body only, but exposes `shop` (and `topic`, `api_version`, `webhook_id`) purely from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` when building `WebhookMetadata` for the app's handler, so the identity binding "HMAC-verified bytes == the shop the data belongs to" does not hold.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMACs it with `Context.api_secret_key` [6](#0-5) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop` accessor reads the `shopify-shop-domain` / `x-shopify-shop-domain` header directly, with no HMAC coverage [3](#0-2) .

The library's `api_secret_key` is a single, app-wide (client) secret shared across every shop that has installed the app — it is not a per-shop secret. Since the signed content is the body only, and `shop` sits outside the signature, `HmacValidator.validate` proves only "this body was signed with the app's secret," never "this body belongs to this `shop`." `Registry.process` then does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

This is exactly the identity-binding gap called out in the analog bug class: a field (`shop`) that is acted upon (used to attribute/route the webhook payload to a tenant) but not covered by the authentication mechanism (HMAC). Compare with `AuthQuery`, where `shop` is explicitly part of the signed string [1](#0-0) , showing the library's own OAuth code treats `shop` as security-relevant data that must be bound to the signature — a discipline not applied to webhook requests.

Any application built on this gem that calls `WebhookHandler#handle` and uses `data.shop` to key persistence, cache invalidation, redaction, or any per-tenant action (as the gem's own mandatory topics `shop/redact`, `customers/redact`, `customers/data_request` [7](#0-6)  strongly imply it will) inherits this gap: the equality the code implicitly assumes, `hmac_verified_bytes.shop == header.shop`, does not hold, because `header.shop` is outside `hmac_verified_bytes`.

### Impact Explanation
This breaks the tenant-attribution boundary the gem is supposed to enforce for webhook delivery. Because the signing secret (`api_secret_key`) is shared across all shops of the app, any shop that can get the app to emit a webhook with attacker-influenced body content (e.g., naming a product, adding a note, or other webhook-triggering actions performed within their own store) obtains a validly-HMAC'd `(body, hmac)` pair. If that request can be replayed to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain, the app's handler will process attacker-controlled body content while believing it originated from — and belongs to — the victim tenant. Depending on what the host app does with `data.shop` (e.g., look up per-shop settings, apply redaction, write to per-shop stores), this can result in cross-tenant data corruption, spoofed redaction/GDPR requests against another shop, or state confusion between tenants.

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger a real webhook delivery (an event with a valid HMAC computed by Shopify using the app's secret) and then resend/replay that request to the app's webhook endpoint with a modified `shop-domain` header. This is plausible for any malicious/compromised merchant who has installed the app, since they control body content of many webhook-triggering events on their own store, and the header carrying `shop` is not part of the cryptographic proof at all — no secret material needs to be recovered, only the header needs to be rewritten on replay.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the HMAC-signed content for webhooks, or otherwise verify header-derived shop identity against a value carried inside the HMAC-covered body/payload before using it for any tenant-scoped action. At minimum, document that `WebhookMetadata#shop` must not be trusted as authenticated and require host apps to cross-check it against their own shop/session records before performing tenant-scoped side effects.

### Proof of Concept
1. App has installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both under the same `api_secret_key`.
2. Attacker (owner/operator of `shop-a`) triggers a webhook-eligible event with attacker-chosen body content (e.g., creates a product with a crafted title/description that maps to `body`).
3. Shopify delivers the webhook to the app's endpoint: headers include `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`.
4. Attacker (who controls network access to the app's public webhook endpoint, as this is a normal internet-exposed route) resends the identical `raw_body` and `hmac` header, but rewrites `x-shopify-shop-domain` to `shop-b.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` succeeds — it only reXwvalidates `raw_body` against the secret, per `to_signable_string` returning `@raw_body` [2](#0-1) .
6. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: <attacker body>, ...))` [4](#0-3) , and the app now processes attacker-supplied data as if it belongs to `shop-b`.
