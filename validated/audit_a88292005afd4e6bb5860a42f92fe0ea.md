### Title
Attacker-craftable extreme HyperSwap pre-seed drives `_swapBudget`-capped rebalance to fully drain one side, causing `LPLock.recordLock`'s `ZeroAmount` revert to permanently brick `finalizeGraduation` and freeze all curve funds - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding._seedRebalancing` caps the hostile-pre-seed rebalance swap at 99% of the available inventory via `_swapBudget` [2](#0-1)  specifically to guarantee `_routerDepositAndDispose` always has a non-zero amount on both sides to deposit. The contract's own natspec on `_swapBudget` documents the failure mode this is meant to prevent: for a sufficiently extreme pre-seed the unconstrained swap input can still exceed the capped budget, the swap consumes the entire capped budget of one side, `_routerDepositAndDispose` observes `remToken == 0` or `remLT == 0` and skips `addLiquidity` entirely [3](#0-2) , and `finalizeGraduation` returns `liquidity = 0` [4](#0-3) . The comment explicitly states this was intended to be defused by the 1% reserve, but concedes: "It only kicks in for catastrophic pre-seeds beyond our budget capacity, where the alternative is bricking" [5](#0-4) . `LPLock.recordLock(tokenAddress, lpPair, liquidity)` is called unconditionally right after with that zero `liquidity` value [6](#0-5) , and `recordLock` explicitly reverts `if (amount == 0) revert ZeroAmount();` [7](#0-6) .

### Finding Description
`finalizeGraduation` is permissionless and is the only path out of `Lifecycle.Graduating` [8](#0-7) . Any revert inside it leaves the token permanently frozen in `Graduating`, where trading is already frozen — no buy/sell can succeed (`Bonding.buy`/`sell` gate on `Lifecycle.Curve`).

The revert path requires an attacker (an ordinary unprivileged wallet) to:
1. Front-run `_ensureUniswapV2Pair` by calling `factory.createPair(token, lt)` and then self-fund a `pair.mint(attacker)` at a hostile, massively skewed (TOKEN, LT) ratio between phase 1 (`_enterGraduating`, which caches `tokensForLP`/`ltFromPair`) and phase 2 (`finalizeGraduation`).
2. Size the pre-seed reserves so the unconstrained `_noFeeSwapInput` (the amount needed to rebalance the pool to the curve-close ratio) exceeds `_swapBudget(available)` — i.e. 99% of the swappable inventory — on the side that becomes the swap input.

When this happens, `_pairRebalance` executes the swap capped at 99% of that side's balance, fully consuming the swap-input side down to (or effectively to) zero once the leftover 1% is insufficient relative to rounding/fees, or — in the documented catastrophic case — the swap output side of the OTHER token also lands at exactly zero balance in `Bonding`. `_routerDepositAndDispose` then sees `remToken == 0` or `remLT == 0` and its `if (remToken > 0 && remLT > 0)` guard skips `addLiquidity` [3](#0-2) , returning `liquidity = 0`. `finalizeGraduation` unconditionally forwards this `0` to `LPLock.recordLock`, which reverts with `ZeroAmount`, unwinding the entire `finalizeGraduation` transaction — including the `info.lifecycle = Lifecycle.Graduated` write that had already executed in memory [9](#0-8) .

Because the token is stuck in `Lifecycle.Graduating` (not `Curve`), `triggerGraduation` also reverts (`TokenIsGraduating`), and there is no retry path with different parameters — `_enterGraduating`'s cached `PendingGraduation` amounts are fixed, so every subsequent `finalizeGraduation` call hits the identical zero-liquidity revert.

### Impact Explanation
This permanently freezes the token: every curve buyer's tokens (unable to sell, since `Bonding.sell` requires `Lifecycle.Curve`), the creator's/protocol's pending fee accrual for that token going forward, and the curve-raised LT (already drained via `Router.graduate` in phase 1 and sitting in `Bonding`) all become permanently unreachable — there is no rescue function for a token stuck in `Graduating`. This is a permanent freezing-of-funds impact directly analogous to the CVE's "hang or frequently repeatable crash (complete DOS)" class: the contract's core lifecycle-completion function becomes permanently unusable for the targeted token, and any keeper retry reproduces the identical revert deterministically.

### Likelihood Explanation
The attack requires no privileged role — anyone can front-run `Factory`/`UniswapV2Factory.createPair` and self-fund a `pair.mint`. The protocol's own natspec on `_swapBudget` explicitly acknowledges this exact scenario is only defended for "realistic" pre-seed sizes and concedes it can still be triggered by "catastrophic pre-seeds beyond our budget capacity" [10](#0-9) . The dedicated end-to-end hostile-pre-seed integration suite (`HostilePreSeed.t.sol`) that would have caught this scenario has been removed, per the AGENTS.md admission that "the wrong-opening-price / LP-capture scenarios, attacker-no-profit, leftover recovery, and concurrent-graduation isolation properties are no longer enforced by automated tests" [11](#0-10) , so a regression or an attacker-discovered edge case sized just past the 1%-budget margin is plausible and not something CI would currently catch.

### Recommendation
In `_routerDepositAndDispose`, when `remToken == 0 || remLT == 0` after the rebalance, fall back to `_seedDirectMint` (as `_pairRebalance`'s `false` return already does) instead of silently producing `liquidity = 0`. Alternatively, have `finalizeGraduation` special-case a `liquidity == 0` result by routing to a guaranteed-nonzero fallback deposit before calling `LPLock.recordLock`, or have `LPLock.recordLock` accept and record a zero-liquidity lock (removing the `ZeroAmount` revert) so `finalizeGraduation` can never revert regardless of the swap outcome, preserving the documented brick-resistance guarantee end-to-end.

### Proof of Concept
1. Launch a token normally and drive it to `Lifecycle.Graduating` via a threshold-crossing buy (as in `_enterGraduating` in `test/TwoPhaseGraduation.t.sol`).
2. Front-run: call `IUniswapV2Factory.createPair(token, lt)`, then `transfer` a massively skewed pre-seed to the pair (e.g., overwhelmingly TOKEN-heavy relative to `tokensForLP`/`ltFromPair`, sized so the required no-fee rebalance input against the LT side exceeds `_swapBudget(_ltSwapInventory(lt, protectedLT))`), then call `pair.mint(attacker)`.
3. Call `bonding.finalizeGraduation(tokenAddress)`. Trace through `_seedRebalancing` → `_pairRebalance` (swap capped at 99% of LT inventory) → `_routerDepositAndDispose`, sized so the LT side's remaining balance after the capped swap is `0`.
4. Observe `_routerDepositAndDispose` returns `liquidity = 0`; `finalizeGraduation`'s call to `LPLock.recordLock(tokenAddress, lpPair, 0)` reverts with `ZeroAmount`.
5. Confirm the token remains in `Lifecycle.Graduating` and every subsequent call to `finalizeGraduation(tokenAddress)` reverts identically, with `triggerGraduation` also reverting (`TokenIsGraduating`), demonstrating permanent freezing.
