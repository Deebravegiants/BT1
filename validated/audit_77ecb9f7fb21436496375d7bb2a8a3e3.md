### Title
Non-ASCII `domain` causes `computeTonConnectHash` to use UTF-16 length instead of UTF-8 byte length, producing wrong intent hash - (File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts)

### Summary
`computeTonConnectHash` encodes the TON Connect `domain_len` field using `domain.length` (JS string length, i.e. UTF-16 code units) while the actual bytes appended to the hashed message are `new TextEncoder().encode(domain)` (UTF-8 bytes). For any `domain` containing characters outside the BMP-ASCII single-UTF-16-unit range (e.g. `café`, CJK), these two lengths diverge, so the locally computed hash no longer matches the hash produced by the official TON Connect sign-data algorithm (which uses UTF-8 byte length per the TON Connect spec referenced in the file's own docstring).

### Finding Description
The claimed equality is: `computeIntentHash(multiPayload)` (locally computed by the integrator, per `packages/intents-sdk/src/intents/intent-hash.ts:68-73`) `==` the `intent_hash` returned by the relayer's `publishIntent` for the same signed payload (`packages/internal-utils/src/solverRelay/publishIntent.ts:16-34`).

In `computeTonConnectHash` (`packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts:50-94`), the message layout is: [1](#0-0) 

Line 70 uses `numberToBigEndian(domain.length, 4)` — `domain.length` is a native JS string property counting UTF-16 code units, not bytes. Line 71 then appends `new TextEncoder().encode(domain)`, the actual UTF-8-encoded bytes. For ASCII-only domains these are numerically identical, masking the bug in all existing tests (`ton-connect.test.ts` uses `"near.com"`, `"tonconnect-demo-dapp-with-wallet.vercel.app"`, `"ton-connect.github.io"` — all pure ASCII). For a domain like `"café.com"`, `domain.length === 8` but `TextEncoder().encode(domain).length === 9` (é is 2 UTF-8 bytes but 1 UTF-16 code unit); for CJK domains the divergence is larger (1 UTF-16 unit vs 3 UTF-8 bytes per character).

The `domain` field originates from the TON wallet's `TonConnect` `signDataSignature` response and flows unmodified from `signature.signatureData.domain` into the `MultiPayload` at `packages/internal-utils/src/utils/prepareBroadcastRequest.ts:57-67`, then gets sent to the relayer via `publishIntents`/`publishIntent`.

Because the SDK's local hash uses the wrong length field, it diverges from the correct TON Connect message hash (which is what any spec-compliant hasher, including presumably the relayer/contract-side verifier, would compute). This breaks the STATUS TRUTH equality: an integrator that persists `computeIntentHash(multiPayload)` from `onBeforePublishIntent` and later polls/matches against the `intent_hash` actually returned by `publishIntent` (or produced by settlement) will never find a match for TON Connect flows with non-ASCII domains.

No existing guard catches this: `computeTonConnectHash` does not validate or normalize `domain` before use, and there is no assertion comparing local hash to any external computation before it's persisted.

### Impact Explanation
This is a status/hash misreport (High category): the integrator believes the intent it tracks locally never settles (since its computed hash never appears as settled), and may retry/resubmit the withdrawal, double-sending against what it believes is a fresh submission while the original TON-signed intent may still be valid and processed under its true (correct) hash on the relayer/contract side. This can result in the same funds being withdrawn twice if the integrator's retry logic re-signs and resubmits rather than merely re-polling. The affected party is the integrator/user relying on `computeIntentHash` for local status tracking of `ton_connect` intents specifically.

### Likelihood Explanation
Preconditions: a TON Connect flow where the wallet's `domain` field (typically the dApp's hostname) contains non-ASCII characters. Standard web hostnames are ASCII (or punycode-encoded IDN), so this is a low-likelihood but plausible scenario for IDN-hosted dApps or wallets that pass the human-readable Unicode form of an internationalized domain instead of punycode. The bug is deterministic and 100% reproducible whenever `domain` contains any multi-byte-UTF-8 character; the attacker does not need special privileges — this is a structural encoding bug in the SDK triggered by data legitimately flowing through the standard TON Connect sign flow.

### Recommendation
Replace `domain.length` with the UTF-8 byte length actually being hashed, e.g.:
```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```
computing `domainBytes` once and reusing it for both the length prefix and payload, matching the same pattern already used correctly for `payloadData` (`payloadData.length` at line 74 is UTF-8 byte length of `payloadSchema.text`, computed via `TextEncoder`, not `payloadSchema.text.length`).

function numberToBigEndian(num: number, bytes: number): Uint8Array {
	const result = new Uint8Array(bytes);
