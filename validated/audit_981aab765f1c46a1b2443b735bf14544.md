### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2` (Tron) escrow withdrawal allows permanent loss of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.sol` (Tron variant) redeems/refunds escrowed order funds and sweeps dust by making a low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checking that the *call itself* did not revert (`success`), never decoding/validating the boolean return value that ERC20 `transfer` is supposed to return.

### Finding Description
In `withdraw()` and in the `SweepDust` branch of `onAccept()`, token payouts use: [1](#0-0) 

and [2](#0-1) 

In each case, `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();` only guards against the call reverting. It never inspects the returned ABI-encoded boolean. Many TRC20/ERC20 tokens (including some USDT-style tokens, and any token whose `transfer` implementation returns `false` on failure instead of reverting — e.g. paused tokens, blacklisted-recipient checks, insufficient-balance edge cases in custom tokens) will return `success == true` from the low-level `.call` while the encoded return data is `false`, meaning the transfer silently did not happen.

Despite this, the surrounding accounting in `withdraw()` unconditionally proceeds to decrement escrow and mark the order as filled/refunded: [3](#0-2) 

`_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` are executed even if the token transfer silently failed. Once `_filled` is set, the `onGetResponse` guard `if (incoming.response.values[0].value.length != 0) revert Filled();` at line 739 prevents the withdrawal from ever being retried, and the escrow accounting is already zeroed out.

This is a real-world variant of the bug class described in the external report — a token transfer that does not follow the strict "revert-on-failure, revert-on-non-boolean-return" ERC20 assumption embedded in the code causes funds to be silently stuck rather than delivered — except here the manifestation is inverted: instead of `transfer()` reverting unexpectedly (as with USDT on Ethereum), the code fails to detect a non-reverting `false` return, so it advances state as if the transfer succeeded.

### Impact Explanation
If the withdrawal beneficiary token transfer returns `false` without reverting (a realistic possibility on Tron/TRC20 tokens and for various compliant-but-unusual ERC20 implementations, e.g. tokens with pausing, blacklists, or supply caps that return `false` on failure), the escrowed tokens remain permanently locked inside the `IntentGatewayV2` contract: the internal escrow ledger (`_orders`) has already been decremented and the order is marked `_filled`, so neither the solver/beneficiary nor the original depositor can ever redeem or refund those tokens again. This is a direct permanent freezing of user/solver funds in the cross-chain intent settlement flow, reachable by any solver or relayer that triggers order redemption/refund once such a token is involved.

### Likelihood Explanation
The path is reached whenever `onAccept` processes a `RedeemEscrow`/`RefundEscrow` request (via `authenticate()` + `withdraw()`) or a `SweepDust` request — both are normal, expected parts of the intent lifecycle triggered by relayed ISMP messages after a solver fills or an order is cancelled/refunded, not by any privileged or malicious actor. The likelihood of triggering the specific failure mode depends on whether a listed input/output token exhibits non-reverting `false`-return-on-failure behavior, which is common enough among ERC20/TRC20 tokens (this is exactly the class of token the `SafeERC20` pattern is designed to guard against, and the codebase elsewhere consistently uses `SafeERC20.safeTransfer`/`safeTransferFrom`, e.g. in the EVM `IntentGatewayV2.sol` predispatch/refund paths and in `WrappedHyperFungibleToken.sol`, showing the Tron variant is an inconsistent, unguarded exception).

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` for escrow/refund/fee payouts and in the `SweepDust` branch of `onAccept()`) with OpenZeppelin's `SafeERC20.safeTransfer`, which both checks the low-level call success and, if return data is present, decodes and requires it to be `true`. This matches the pattern already used consistently elsewhere in the codebase (e.g. `IERC20(token).safeTransferFrom(...)` in the same file's `placeOrder`/predispatch logic, and `IERC20(_underlying).safeTransfer(...)` in `WrappedHyperFungibleToken.sol`).

### Proof of Concept
1. An order's input/output token list includes a token `T` whose `transfer` function returns `false` on failure instead of reverting (e.g., a paused/blacklist-gated token, or certain TRC20 tokens on Tron).
2. A solver fills the order; hyperbridge relays a `RedeemEscrow` request to the destination-chain `IntentGatewayV2` (Tron), triggering `onAccept` → `authenticate` → `withdraw(body, false)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting (e.g., the token's `transfer` catches the failure condition internally and returns `false` rather than reverting) — `success` is `true`.
4. The code does not check the returned boolean, so it proceeds to `_orders[body.commitment][token] -= amount` and sets `_filled[body.commitment] = beneficiary`, emitting `EscrowReleased`.
5. The beneficiary never actually received the tokens (`transfer` returned `false`), but the escrow accounting shows the order as filled with zero remaining escrow — the tokens are stuck in the contract with no code path left to reclaim them, since `_filled` blocks any retry via `onGetResponse`'s `Filled()` revert.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
