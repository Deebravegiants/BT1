### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all read from separate HTTP headers that are never included in the signed content. `Registry.process` validates the HMAC over the body alone and then trusts the unauthenticated `shop` (and `topic`/`webhook_id`) headers when constructing `WebhookMetadata` passed to the host app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that method returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body-only verification) before dispatching `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata`, which is what the host app's `WebhookHandler#handle` receives and treats as authenticated tenant context: [3](#0-2) [4](#0-3) 

The broken identity binding is: `shop_that_actually_produced_this_HMAC-valid_body == shop_header_claimed_in_the_request`. Since `Context.api_secret_key` is the app's single client secret shared across every shop that has the app installed (not a per-shop secret), any unprivileged internet user who installs the app on their own store receives genuine, validly-HMAC-signed webhook deliveries. Because `shop`/`topic`/`webhook_id` are outside the signed content, that same attacker can replay the intercepted body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the untouched body, and the forged `shop`/`topic` are handed to the host app as if authentic.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled shop's webhook payload can be attributed to a different (victim) shop domain, or delivered to a handler under an arbitrary topic/webhook id, entirely defeating the purpose of HMAC verification as a tenant-authentication mechanism. Any host application that uses `WebhookMetadata#shop` to select the tenant's stored session/access token, or to gate per-shop business logic, will act on forged tenant identity backed by a "valid" signature. This satisfies the Critical bar for cross-tenant access.

### Likelihood Explanation
Exploitability only requires the attacker to install the target app on any shop they control (a routine, unprivileged action available to any Shopify merchant/developer) and capture one webhook delivery for that shop, then replay it with modified headers against the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable content (or otherwise cryptographically bind them to the payload/signature), so `HmacValidator.validate` fails if any of these values are altered after Shopify signed the webhook. At minimum, `Request#to_signable_string` should incorporate the same fields the registry and downstream handler treat as authenticated identity (`shop`, `topic`, `webhook_id`).

### Proof of Concept
1. Attacker creates their own dev store `attacker.myshopify.com` and installs the target app (using the app's single, shared `client_secret`).
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON `body`.
3. Attacker replays the exact same `body` and `x-shopify-hmac-sha256` to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `@raw_body` only, which is unchanged, so validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `victim.myshopify.com`, and the host app's handler processes attacker-controlled data as if it originated from the victim shop.
