### Title
RAY-value overflow during accrual can permanently freeze a large lending market - ([File: common/src/rates/simulate.rs])

### Summary
`accrue_step` converts the market’s scaled borrow and supply shares into RAY-denominated values before updating the indexes. Although intermediate multiplication is safely widened to `I256`, the final `i128` conversion still panics when `shares * index / RAY` exceeds the RAY-value domain. A sufficiently large, highly utilized market can therefore cross the representable-value boundary before either index reaches its configured cap. Every state-changing pool operation accrues first, so the resulting `MathOverflow` permanently blocks repayment, withdrawal, liquidation, bad-debt cleanup, and rate-parameter updates absent a contract upgrade. [1](#0-0) [2](#0-1) 

### Finding Description
The accrual path calls `scaled_to_original` for `borrowed * borrow_index` and `supplied * supply_index` before selecting the borrow rate and calculating the next index. [1](#0-0)  `scaled_to_original` delegates to `Ray::mul`, and `Ray::mul` returns an `i128` RAY value. [3](#0-2) [4](#0-3) 

The fixed-point implementation protects the intermediate product by widening it to `I256`, but it intentionally panics with `MathOverflow` if the final quotient cannot be represented as `i128`. [5](#0-4) [6](#0-5)  Thus, the vulnerable bound is not merely the intermediate `x * y`; it is the final RAY-denominated market value, approximately `scaled_shares * index / RAY < i128::MAX`.

The repository’s stress test demonstrates the condition: a market holding one billion 18-decimal whole tokens produces `1e36` raw RAY shares, while `i128::MAX` permits only about 170 times that value. At 98% utilization on the steep test curve, index growth reaches that boundary before `MAX_BORROW_INDEX_RAY`, and the next accrual panics inside `scaled_to_original`. [7](#0-6) [8](#0-7) 

An unprivileged actor can create the required state through the controller’s public supply and borrow flows by supplying or borrowing a `(hub_asset, amount)` leg within the market’s configured caps, then later call `Controller::update_indexes(caller, vec![hub_asset])` to execute accrual. [9](#0-8) [10](#0-9) 

### Impact Explanation
Once the boundary is crossed, `accrue_step` panics before it returns updated indexes, so no subsequent market mutation can load a synced cache. [11](#0-10) [2](#0-1) 

Withdrawals call `ops::load_leg`, repayments call the same synced loader, borrows and supplies do likewise, and liquidation or bad-debt seizure paths also require the market cache to be accrued before accounting. [12](#0-11) [13](#0-12) [14](#0-13) 

The test explicitly verifies that both withdrawal and repayment revert with `MATH_OVERFLOW` after the cliff is reached. [15](#0-14)  This permanently freezes all supplier cash in the affected market and prevents borrowers from repaying or being liquidated through ordinary contract calls; recovery would require a privileged contract upgrade rather than an available unprivileged path. [16](#0-15) 

### Likelihood Explanation
Triggering the condition requires an exceptionally large listed market, sufficient collateral and liquidity to sustain high utilization, configured caps large enough to admit the position, and enough elapsed ledger time for index growth. [17](#0-16)  The documented arithmetic domain allows roughly 170 billion whole-token-equivalent RAY value at index one, but a market with `1e36` scaled shares reaches the boundary once an index exceeds roughly `170 * RAY`. [18](#0-17) 

The likelihood is therefore market-dependent rather than universal, but no malformed token, oracle manipulation, privileged call, or bad external route is required once a listed market’s caps and liquidity admit the required size. [19](#0-18) [9](#0-8) 

### Recommendation
Enforce the representable RAY-value domain at admission and before each index update.

Specifically:

- Calculate market-specific index ceilings from current scaled totals, such as `borrow_index <= floor(i128::MAX * RAY / borrowed)` and `supply_index <= floor(i128::MAX * RAY / supplied)`, with the required rounding headroom.
- Clamp accrual to those ceilings before calling `calculate_supplier_rewards` or `update_supply_index`, rather than allowing valuation of an unrepresentable new index.
- Reject new supply or borrow positions that would make the market unable to accrue safely at the configured maximum index.
- Add regression coverage proving that repayment, withdrawal, liquidation, and bad-debt cleanup remain executable at the market-specific arithmetic ceiling.
- Avoid representing accrued market totals solely in `i128` if indexes are allowed to grow independently of market size.

The current index cap only bounds the index itself at `10^36`; it does not account for the scaled-share multiplier, which is why value overflow can occur first. [20](#0-19) [21](#0-20) 

### Proof of Concept
The repository already contains an executable scenario:

1. Create an 18-decimal market using the steep test curve.
2. Supply `1_000_000_000 * 10^18` native units.
3. Supply sufficient collateral in another market.
4. Borrow 98% of the first market.
5. Advance ledger time in yearly increments and invoke `update_indexes(caller, vec![hub_asset])`.
6. Accrual eventually returns `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
7. Subsequent withdrawal and repayment attempts return the same `MATH_OVERFLOW`. [22](#0-21)

    let amount = action.amount;

    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
