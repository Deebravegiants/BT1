### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header that is never included in the HMAC-signed payload. `Registry.process` validates only the raw body against the HMAC and then hands the unauthenticated `shop` header straight to the app's webhook handler, breaking the binding `hmac_signed_bytes == bytes_acted_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e. the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` performs exactly this body-only check and then passes the **unauthenticated** `request.shop` (and `topic`, `webhook_id`, `api_version`) into `WebhookMetadata`, which is delivered to the app's handler as trusted tenant context: [4](#0-3) 

Because a single `api_secret_key` is shared across all shops installed on an app (it is not per-shop), any party who can obtain one valid `(raw_body, hmac)` pair — for example by installing the app on a shop they control and capturing a genuine webhook delivery, or by intercepting/replaying a webhook sent to the app's public endpoint — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. The signature still validates because `shop` is never part of the signed bytes, yet `Registry.process` reports the event as belonging to the attacker-chosen `shop`.

This breaks the identity binding: `hmac(raw_body)` verified == authenticity of `(raw_body, shop, topic)` acted upon, when in reality only `raw_body` is authenticated.

### Impact Explanation
This crosses a tenant boundary: an app handler that keys persistence, redaction, or business logic off `WebhookMetadata#shop` (e.g. mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics, or `app/uninstalled`/`orders/create` style processing) can be made to act on a shop that never actually sent the event. This enables cross-tenant data forgery/corruption or spurious tenant deletion/redaction — a Critical-class cross-tenant access issue per the report's scope.

### Likelihood Explanation
Exploitation requires only: (1) the ability to reach the host app's public webhook endpoint (an unprivileged internet capability once the endpoint is known), and (2) one legitimately-signed `(body, hmac)` sample, which an attacker can trivially obtain by installing the target app on their own shop (a normal, low-privilege action) and observing any webhook Shopify sends them. No access token, `client_secret`, or leaked credentials are needed — only the gem's own webhook-processing code path is used.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material verified by `HmacValidator`, or otherwise cryptographically bind the shop domain to the signature (e.g. Shopify's actual webhook contract signs the raw body and relies on TLS-terminated, Shopify-only delivery — if this gem is meant to be usable behind arbitrary ingress, the header-derived `shop` should not be trusted for authorization decisions without additional verification, such as cross-checking against a known/registered shop list or including it in the signed payload).

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop (`attacker-shop.myshopify.com`) so that Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`.
2. Capture the raw body and the valid `hmac` header from that delivery.
3. Replay an HTTP POST to the same app endpoint with the identical raw body and `hmac` header, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only re-hashes `raw_body`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to process attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
