### Title
Cross-tenant webhook forgery via `shop` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the tenant-identifying `shop` value used to route the webhook to the host application's handler is taken from an HTTP header that is never included in the signed content. This breaks the intended identity binding: `hmac_verified_bytes == request.shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the HMAC-signed data: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then hands `request.shop` straight to the app's handler as the tenant identifier, with no additional check that this shop matches the shop whose secret validated the body: [4](#0-3) 

Because `ShopifyAPI::Context.api_secret_key` is the app's single client secret shared across every installed shop (not a per-shop secret), any `(raw_body, hmac)` pair that is valid for one tenant is valid for **all** tenants. An unprivileged user who has installed the app on their own shop (Shop A) can capture a legitimately-delivered webhook (body + `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com`. `Utils::HmacValidator.validate` will still pass, because it never inspects the `shop` header: [5](#0-4) 

The handler is then invoked with `WebhookMetadata` claiming the victim shop, even though the payload actually originated from the attacker's own store: [6](#0-5) 

This equality that the design assumes but never enforces:
`shop used for tenant routing (request.shop) == shop that produced the HMAC-signed body`
is false after the forged replay, breaking the identity boundary between tenants.

### Impact Explanation
This is a cross-tenant data-integrity break: an attacker-controlled webhook body (crafted by triggering events on their own store, e.g. `orders/create`, `customers/update`, `app/uninstalled`) can be attributed to a victim shop of the attacker's choosing. Any host application that uses `WebhookMetadata#shop` to look up/update per-tenant records (which is the intended and documented usage pattern) can be made to write, delete, or act on the wrong tenant's data using attacker-supplied content — satisfying the "cross-tenant access" criterion for Critical/High impact.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate, unprivileged merchant who has installed the app on their own store (a normal, unprivileged action — no `api_secret_key`, access token, or leaked credentials are needed) and to be able to send an arbitrary HTTP request to the app's public webhook receiving endpoint with attacker-chosen headers, both of which are ordinary internet-facing capabilities. The vulnerable code path (`Utils::HmacValidator.validate` + `Registry.process`) is exactly the path documented for apps to use to authenticate and dispatch webhooks.

### Recommendation
Include the tenant-identifying header(s) (at minimum `shop-domain`, ideally `topic` and `webhook-id` as well) in the HMAC-signable content, or, at minimum, require host applications to independently authenticate `request.shop` (e.g., verifying it against a per-shop stored secret/HMAC or a known-installed-shop list) before trusting it. `Utils::HmacValidator` and `Webhooks::Request#to_signable_string` should be changed so that the value used to identify the tenant is provably bound to the same bytes that were verified.

### Proof of Concept
1. Install the target app on attacker-owned Shop A (unprivileged, normal merchant action).
2. Trigger a webhook delivery (e.g., `orders/create`) to the app's registered endpoint; capture the raw body `B` and the `x-shopify-hmac-sha256: H` header. `H = HMAC-SHA256(api_secret_key, B)` — valid because `to_signable_string` returns only `B`.
3. Replay the request to the same endpoint, keeping `B` and `H` unchanged, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic`, `x-shopify-webhook-id` as desired.
4. `Utils::HmacValidator.validate` succeeds (only `B`/`H` are checked).
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as if it belonged to the victim tenant.
