## Analysis

CVE-2018-14357 is a case where a remote server supplies attacker-controlled data (an IMAP `mailboxes` command with backquote metacharacters) that is trusted and automatically fed into a privileged execution path (shell command execution) without proper authentication/sanitization of the acting identity.

The closest reachable analog in Hyperbridge is in `pallet-hyper-fungible-token`'s `on_accept` handler, which automatically executes an embedded "command" (a SCALE-encoded runtime call) upon receiving a cross-chain message, and — when no signature is attached — derives the *dispatch origin's identity* purely from an ABI-decoded field of the incoming message body, which is not independently authenticated at the destination.

### Root cause

In `on_accept`, after decoding the `Message` (`from`, `to`, `amount`, `data`) from the ISMP request body, optional calldata is executed: [1](#0-0) 

If `SubstrateCalldata.signature` is `None`, the dispatch origin is derived directly from `message.from` — a field taken from attacker/contract-supplied request body — with no cryptographic proof binding it to the actual token sender: [2](#0-1) 

That derived origin is then used to dispatch an arbitrary, attacker-chosen `RuntimeCall` (filtered only by `BaseCallFilter`, not by any authorization tied to `from`): [3](#0-2) 

The pallet's own documentation confirms this is the intended (not incidental) behavior: "If no signature is provided, the origin is derived from the sender address in the cross-chain message." [4](#0-3) 

The `SubstrateCalldata` type itself only supports two authentication modes — a MultiSignature check, or none at all: [5](#0-4) 

### Why this matters

The `from` bytes inside the ABI-encoded `Message` are set entirely by whatever logic the source-chain contract implements when constructing the outgoing request — the destination pallet has no way to independently verify that `from` actually corresponds to the account that authorized the tokens or the call. I was unable to fully confirm from the indexed contents whether `HyperFungibleToken.sol`'s `send()` function strictly binds `from` to `msg.sender` or allows a caller-supplied value (the Solidity source for `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` was not available in the index to verify this precisely). If `from` is attacker-influenceable at the source (e.g. via a caller-supplied parameter, a compromised/malicious integrating contract, or any code path where `from` isn't tied to `msg.sender`), an attacker can forge the identity of an arbitrary beneficiary and get an arbitrary, unsigned `RuntimeCall` dispatched under that beneficiary's origin on the destination chain — a direct "unauthorized app action" per the scan's acceptance criteria, and structurally analogous to CVE-2018-14357's pattern of automatically executing an attacker-influenced instruction under a trusted identity without adequate validation.

Given the uncertainty about the Solidity-side guarantee (which I could not verify due to indexing limits on that specific contract), I flag this as a **plausible but not fully confirmed** analog. If you need the exact Solidity `send()` implementation confirmed, a Devin session with full repo access would be needed to inspect `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` directly.

### Title
Unsigned cross-chain calldata dispatches arbitrary RuntimeCall under an origin derived from an unauthenticated message field - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`on_accept` in `pallet-hyper-fungible-token` allows a cross-chain message's optional `call_data` to be dispatched as a `RuntimeCall` under an origin derived solely from the `Message.from` field when no `MultiSignature` is supplied, with no cryptographic proof that the acting party actually controls that origin.

### Finding Description
When decoding an incoming `PostRequest`, the pallet extracts `SubstrateCalldata` from `message.data` and, if `signature` is `None`, computes the dispatch origin purely from `message.from` (mapped via `EvmToSubstrate::convert` for EVM sources, or copied directly for substrate sources), then dispatches the embedded `runtime_call` under `RawOrigin::Signed(origin)`. This trusts the `from` field's authenticity implicitly, relying entirely on the source-chain contract to have set it correctly, rather than requiring cryptographic proof at the destination. [6](#0-5) 

### Impact Explanation
If `from` can be influenced by anything other than a strictly-enforced `msg.sender` on the source chain, an attacker could impersonate any beneficiary and have arbitrary runtime calls dispatched under that beneficiary's account authority on the destination chain — potentially transferring assets, executing privileged calls, or performing other unauthorized actions gated only by `BaseCallFilter`.

### Likelihood Explanation
Reachable via a single cross-chain message delivered through the normal `on_accept` path (any relayed `PostRequest` targeting a registered `ContractToAsset` pair), requiring no privileged role — only that `call_data` be included without a signature. Likelihood hinges on whether the paired EVM contract enforces `from == msg.sender`, which could not be confirmed from the available index.

### Recommendation
Require the `MultiSignature` path unconditionally for any `call_data` execution (removing the no-signature fallback), or otherwise cryptographically bind `message.from` to the actual transaction initiator on the source chain before using it to derive a dispatch origin.

### Proof of Concept
Not constructible with certainty without confirming the source-chain contract's handling of the `from` field; would require inspecting `HyperFungibleToken.sol`'s `send()` implementation to determine if `from` is caller-controlled.
