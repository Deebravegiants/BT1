### Title
Encrypted storage lacks key-binding/AAD, enabling ciphertext key-swap (cut-and-paste) cross-key/origin confusion - ([File: adapters/storage-encrypted/src/storage.ts])

### Summary
`createStorageEncrypted` encrypts/decrypts values using only the plaintext buffer, never binding the storage `key` (or namespace) as additional authenticated data. This means a ciphertext stored under one key can be copied verbatim into another key's slot in the underlying raw storage, and `get()` on the new key will decrypt and `JSON.parse()` it successfully, since `decrypt()` only validates ciphertext integrity against the shared crypto secret, not against which logical key it belongs to.

### Finding Description
`transformOnWrite` calls `encrypt(Buffer.from(JSON.stringify(value)))` and stores only the resulting base64 ciphertext — the `key` parameter is not passed to `encrypt` at all: [1](#0-0) 

`transformOnRead(ciphertextB64, key)` receives the `key`, but it is used solely for the error-logging message (`logger.warn(\`Failed to decrypt value for key: ${key}\`, err)`), not passed into `decrypt()`: [2](#0-1) 

The underlying `CryptoFunctions` interface only supports `encrypt(data: Buffer): Promise<Buffer>` / matching `decrypt`, with no AAD/context parameter at all: [3](#0-2) 

The generic `transformStorage` wrapper that plumbs `key` through `get`/`set`/`namespace` also does not enforce any binding of the transformed value to the key — it simply forwards `key` to the `onRead`/`onWrite` callbacks, which the encrypted-storage adapter ignores for cryptographic purposes: [4](#0-3) 

Because the ciphertext carries no cryptographic tie to its storage key or namespace, any ciphertext blob encrypted under the same shared secret is fully valid and decryptable under any other key/namespace serviced by the same `cryptoFunctionsPromise`. An attacker (or buggy/compromised component) with only raw write access to the underlying storage backend (e.g., localStorage/IndexedDB/chrome.storage — not the encryption key itself) can copy the ciphertext from key `trustedOriginX` to key `trustedOriginY`; `encryptedStorage.get('trustedOriginY')` will decrypt without error and `JSON.parse` will yield origin X's approval object as if it belonged to origin Y. No integrity check ties the plaintext's semantic content or the ciphertext to the destination key, so nothing in the read path detects the swap.

### Impact Explanation
This breaks the encrypted storage layer's key/origin isolation invariant: data logically scoped to one key or namespace (e.g., a "trustedOriginX-approved" flag or per-account secret) can be relocated by raw storage manipulation to another key/namespace and be accepted as legitimate for that target identity. Depending on what data model consumers store under per-origin/per-account keys in this adapter (e.g., dapp connection approvals, per-account settings), this enables privilege/approval confusion across origins or accounts without needing the encryption secret — a cross-origin/account privilege confusion primitive.

### Likelihood Explanation
Exploitability requires write access to the raw underlying storage keyspace but not the encryption secret — a precondition matching e.g. a malicious/compromised extension component, another origin with storage write access in a shared storage backend, or any code path that can write raw key/value pairs (this is explicitly the stated precondition of the question). Given that precondition, the attack is deterministic and trivially repeatable: copy ciphertext bytes from source key to destination key, then call `get(destinationKey)`.

### Recommendation
Bind the storage key (and namespace prefix) as authenticated context to the ciphertext. Concretely: pass the fully-qualified key/namespace path into `encrypt`/`decrypt` as AAD (if the underlying crypto function supports AEAD with associated data), or, if not, prepend/append the key to the plaintext before encryption and verify it matches the requested key after decryption in `transformOnRead`, rejecting (throwing) on mismatch instead of silently returning the wrong-context data.

### Proof of Concept
Unit test plan (extending `adapters/storage-encrypted/test/index.spec.ts` style):
1. Create `encryptedStorage` wrapping an in-memory raw storage with a shared `cryptoFunctionsPromise`.
2. `await encryptedStorage.set('trustedOriginX', { approved: true, origin: 'X' })`.
3. Read the raw underlying ciphertext value for `trustedOriginX` directly from the wrapped raw storage (bypassing the encrypted adapter).
4. Write that same raw ciphertext value directly into the raw storage under key `trustedOriginY` (simulating attacker's raw-storage write access).
5. Call `await encryptedStorage.get('trustedOriginY')`.
6. Assert: the call resolves (no decryption error) and returns `{ approved: true, origin: 'X' }` — i.e., origin Y is granted origin X's approval — demonstrating the missing key-binding/AAD check.

```typescript
  const transformOnRead = async (ciphertextB64: string | undefined, key: string) => {
    const { decrypt } = await cryptoFunctions
    if (!ciphertextB64) return

    const ciphertext = Buffer.from(ciphertextB64, 'base64')
    let decrypted
    try {
      decrypted = await decrypt(ciphertext)
    } catch (err) {
      if (swallowDecryptionErrors && isDecryptionError(err as Error)) {
        logger.warn(`Failed to decrypt value for key: ${key}`, err)
        return
      }

      throw err
    }

    return JSON.parse(decrypted.toString())
  }
```
