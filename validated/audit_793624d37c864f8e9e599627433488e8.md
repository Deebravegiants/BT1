### Title
Unchecked ERC20 `transfer()` return value in escrow withdrawal allows silent-failure token loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` on Tron uses `SafeERC20.safeTransferFrom` for pulling in user-chosen input tokens at order placement, but its escrow-release path (`withdraw()`) and dust-sweep path (`onAccept`'s `SweepDust` branch) release tokens with a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` while only checking that the call did not revert — the actual boolean return data from `transfer()` is discarded and never inspected.

### Finding Description
In `withdraw()`, escrowed input tokens (freely chosen by the order-placing user, not a whitelisted set) are released like this: [1](#0-0) 

and fee-token payouts follow the identical pattern: [2](#0-1) 

The same unsafe pattern also appears in the dust-sweep governance branch of `onAccept`: [3](#0-2) 

`(bool success,) = token.call(...)` only reflects whether the low-level call itself reverted; it does not decode/verify the returned `bool` that ERC20's `transfer()` is supposed to return on failure. A token that returns `false` instead of reverting on a failed transfer (paused token, blacklist/sanctions-list rejection, insufficient balance handled non-reverting, or any non-standard/malicious ERC20 chosen by a user when placing an order) will make `success == true` even though no tokens moved. Notably, elsewhere in the very same contract (deposit path) `SafeERC20.safeTransferFrom` is used correctly, showing the release path was implemented with a weaker, unsafe substitute: [4](#0-3) 

Because `withdraw()` unconditionally decrements the escrow accounting and (on finalize) permanently marks the order as filled/refunded regardless of whether the token transfer actually succeeded: [5](#0-4) 

the escrowed balance and order state are irreversibly consumed even when the beneficiary receives nothing.

### Impact Explanation
`withdraw()` is invoked from the `RedeemEscrow`/`RefundEscrow` branch of `onAccept()` — reached whenever a relayer delivers a valid cross-chain settlement/refund message from a registered peer `IntentGatewayV2` — and from `onGetResponse()` for source-chain cancellation: [6](#0-5) 

Since input tokens are chosen freely by the order-placing user (not restricted to a protocol whitelist), a user (or a token deployer colluding with a "solver") can place an order using a token whose `transfer()` can be made to return `false` without reverting. When that order settles or is refunded, `_orders[...] -= amount` fires and, on finalize, `_filled[commitment]` is permanently set, yet the beneficiary (solver or user) receives zero tokens. The tokens become permanently stuck in the gateway contract with no remaining accounting path to reclaim them — a permanent freezing/loss of escrowed user funds, matching the Medium-severity classification given in the referenced report for contracts that can hold user-defined assets.

### Likelihood Explanation
Reachable from a single relayed ISMP message (or same-chain `RedeemEscrow`/`RefundEscrow`/`onGetResponse` delivery) with no privileged role required; the only precondition is that the order's input/fee token is one whose `transfer()` returns `false` on failure instead of reverting, which is a known real-world pattern in the broader ERC20/TRC20 ecosystem (and can be trivially deployed by an attacker as the order's own input token). This makes exploitation practical for any unprivileged intents user.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer()`/`safeTransferFrom()` (already imported and used elsewhere in this same contract), which reverts on both call failure and a `false` boolean return, ensuring escrow accounting is never advanced past a transfer that did not actually succeed.

### Proof of Concept
1. Deploy a malicious/non-standard ERC20 token `T` whose `transfer()` implementation returns `false` (no revert) whenever a certain condition holds (e.g., always, or once balance drops below a threshold).
2. User places an order via `placeOrder` using `T` as an input token; `T` is pulled in successfully via `safeTransferFrom` at deposit time (line 405), so escrow is funded normally.
3. A solver fills the order on the destination chain and the settlement message triggers `onAccept` → `withdraw()` on the source chain (or the same-chain path calls the equivalent release logic).
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes `T.transfer()`, which returns `false` without reverting; `success` is `true` because the call itself did not revert.
5. `_orders[commitment][token] -= amount` executes and `_filled[commitment] = beneficiary` is set, finalizing the order — but the beneficiary's `T` balance never increased. The escrowed `T` tokens remain stuck in the `IntentGatewayV2` contract permanently, with no code path left to retrieve them for the affected user/solver.
