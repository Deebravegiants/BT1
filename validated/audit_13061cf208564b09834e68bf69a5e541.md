### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, and `webhook_id` fields—read directly from unauthenticated HTTP headers—are exposed to and trusted by the handler dispatch logic. Because the same app-level `api_secret_key` signs webhook bodies for every shop that installs the app, an attacker who legitimately installs the app on their own shop can capture a validly-HMAC'd webhook body that Shopify sent for their own tenant, then replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. The signature still validates (it only covers the body bytes), so the host application processes attacker-supplied data as if it originated from the victim shop — a cross-tenant data injection.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are all read straight from caller-controlled HTTP headers with no cross-check against the signed content: [2](#0-1) 

`Registry.process` validates the HMAC using exactly that `to_signable_string` value, then dispatches to the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever hashes `verifiable_query.to_signable_string`, so any header not included there (here, all headers) is unauthenticated: [4](#0-3) 

This breaks the intended identity binding: the gem implicitly claims `hmac_valid(body) == shop_is_authentic(shop_header)`, but the two are disjoint — the HMAC proves only "Shopify (or anyone who can reproduce this exact body+secret) sent this exact byte sequence," not "this byte sequence belongs to shop X." Since `api_secret_key` is shared across all shops that install a given app (a single app serves many merchants), any merchant who installs the app can trivially obtain a body+valid-HMAC pair for their own shop and then relabel it as belonging to a different, victim shop by swapping the `shop-domain` header on replay.

### Impact Explanation
This is a cross-tenant boundary violation: an unprivileged attacker (any user who can install the app on a shop they control — a normal, unprivileged action for public/embedded Shopify apps) can make the host application record or act on attacker-chosen webhook payload data under the identity of an arbitrary victim shop domain. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the merchant's stored access token/session, writing to that shop's database row, or triggering shop-scoped side effects), this can lead to data corruption, spoofed events, or logic bypass scoped to a shop the attacker does not own — matching the "cross-tenant access" criterion.

### Likelihood Explanation
Practical: an attacker only needs their own (free/dev) Shopify shop with the target app installed and any webhook subscription, no leaked secrets, tokens, or social engineering are required. Capturing one valid `(raw_body, hmac)` pair for their own shop and replaying it with a modified `shop-domain` header is trivial once the webhook endpoint is known (it's the app's public configured callback URL).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the same authenticity guarantee as the body: either include these values in the HMAC-signable string, or independently verify that the `shop` conveyed in the header matches an active, installed session/shop that the app expects for that HMAC-validated request, before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays the exact same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (== `B`); the check passes since `H` still matches `B`. [3](#0-2) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, so the host application processes attacker-supplied data as belonging to `victim.myshopify.com`, despite the attacker never having access to that shop.
