### Title
Predictable, Unsigned Session-Cookie Value Lets an Unprivileged Caller Claim Any Shop's Persisted Session (Cross-Tenant Access) - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
The gem generates the non-embedded session-cookie value from fully predictable, non-secret data (the shop's `myshopify.com` domain, or `shop_userid`) and, on the read path, trusts whatever string is presented in the `shopify_app_session` cookie as the session identity with no cryptographic binding to a completed OAuth flow. Because the value is not signed or otherwise tied to the browser that actually finished OAuth, any caller who can send a raw HTTP request with a crafted `Cookie` header can impersonate a legitimate, already-onboarded shop.

### Finding Description
During the OAuth callback, the gem builds the cookie whose value is the raw session id: [1](#0-0) 

That session id is fully deterministic and derived only from public information: [2](#0-1) 

`SessionCookie` itself is a plain, unsigned value container — no HMAC, no encryption, no expiry-bound MAC: [3](#0-2) 

On the read side, `current_session_id`/`cookie_session_id` return the cookie's raw contents verbatim, with zero verification that it was ever issued by this gem's own OAuth flow to this caller: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`shop that actually authenticated (completed OAuth in this browser)` == `shop key used to look up the persisted Session/access token`.

Because the "session key" side of that equation is just `"offline_#{shop}"` (100% public/guessable — the shop domain is visible on the storefront) or `"#{shop}_#{user_id}"` (shop is public, `user_id` is a small integer), and the cookie is never signed, an attacker who never performed OAuth can produce the exact same string and present it as their own `Cookie` header (HttpOnly only blocks browser JS from reading/writing it — it does not stop a raw HTTP client from setting an arbitrary `Cookie` header on a request it sends itself). If the host application follows this gem's documented pattern of looking up its session store by the id returned from `current_session_id`, it will return the real, previously-persisted `Session` (with a genuine access token) for the target shop, even though that shop's user never authenticated this request.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: any unprivileged internet user, without ever installing the app or obtaining credentials, can cause the host application to load and use another (legitimate) merchant's stored `Session`/access token purely by supplying a guessable cookie value. This is cross-tenant access to another merchant's Admin API session, satisfying the "Critical – cross-tenant access" bar.

### Likelihood Explanation
No secret, TLS interception, or local access is required — only knowledge of the target's `*.myshopify.com` domain (public) for the offline-session case, which is the most common non-embedded session type. This is directly reachable through the gem's own documented `SessionUtils.current_session_id` / `cookie_session_id` API, not a misuse of undocumented behavior.

### Recommendation
Do not use a predictable, attacker-derivable string as the sole session-cookie value. Sign the cookie contents (e.g., HMAC with `api_secret_key`, similar to `Utils::HmacValidator`) or use an opaque, unguessable random session identifier, and verify the signature/nonce in `cookie_session_id` before trusting the embedded shop/session id.

### Proof of Concept
1. Target shop `targetshop.myshopify.com` legitimately installed the app previously (offline session persisted server-side).
2. Attacker sends a raw request to any endpoint of the host app that resolves the session via this gem, e.g.:
   `curl https://victim-app.example.com/some_protected_route -H "Cookie: shopify_app_session=offline_targetshop.myshopify.com"`
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_targetshop.myshopify.com"` unchanged (`lib/shopify_api/utils/session_utils.rb:29-36`).
4. The host app's session storage (built exactly as the gem's docs instruct) looks up and returns the real, previously stored `Session` for `targetshop.myshopify.com`.
5. Subsequent `ShopifyAPI::Clients::Rest::Admin`/`Graphql::Admin` calls made with that session execute against the target shop's store using its real access token — full cross-tenant compromise without ever completing OAuth as that shop.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
