### Title
JWT replay-cache TOCTOU race allows duplicate HTTP-trigger workflow execution with a single-use JWT - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The DTLS anti-replay CVE is a bug-class of "replay/duplicate-processing protection mishandled under concurrent/edge conditions." The closest reachable analog in this codebase's internet-facing gateway is the JWT replay guard used to authorize unprivileged HTTP-trigger requests in `WorkflowMetadataHandler.Authorize`, which performs its "already used?" check and its "mark as used" write as two separate, non-atomic critical sections.

### Finding Description
`Authorize` verifies the request JWT, then checks for replay, then checks signer authorization, and only then records the JWT ID as used: [1](#0-0) 

The replay cache itself protects its internal map with a `sync.RWMutex`, but `isReplay` and `recordUsage` are independent lock acquisitions rather than one atomic "check-and-set" operation: [2](#0-1) 

Because `HandleUserTriggerRequest` (the path reachable directly from an unprivileged HTTP client) calls `h.authorizeRequest` → `h.workflowMetadataHandler.Authorize` per inbound request with no per-JWT/per-jti serialization, two (or more) requests carrying the identical signed JWT can both call `isReplay(claims.ID)` before either has called `recordUsage(claims.ID)`. Both calls observe "not yet seen" and both proceed to be treated as authorized, each triggering its own downstream workflow execution fan-out: [3](#0-2) [4](#0-3) 

This is structurally the same class of bug as `ALPINE-CVE-2016-2181`: a replay/duplicate-detection mechanism that is not evaluated atomically against the event it is meant to gate, so a narrow timing window permits duplicate acceptance of a value that is supposed to be single-use. In contrast, the Vault capability's analogous replay guard (`RequestReplayGuard.CheckAndRecord`) correctly performs the "seen?" check and the "record" write under one held lock, closing this exact race: [5](#0-4) 

That vault-side implementation is proof the codebase recognizes this hazard class and hardens against it elsewhere — but the gateway's HTTP-trigger JWT cache was not built the same way.

### Impact Explanation
An unprivileged external client possessing one valid, signer-authorized, single-use trigger JWT (e.g., obtained through the normal issuance flow, or replayed from a legitimately observed request) can send it concurrently to trigger the same workflow multiple times before the replay cache converges. This is a request-impersonation/duplicate-authorization bypass: the JWT is meant to authorize exactly one workflow execution ("Please generate a new one with new id (jti)" is the explicit intended guarantee), but the race lets an attacker cause more than one execution from that single grant, i.e., "unauthorized job run" in excess of what was authorized. Given `sendWithRetries`/`sendToShard` fan out to all DON nodes per accepted call, each successful race hit results in a full duplicate execution trigger being forwarded to the workflow DON.

### Likelihood Explanation
Exploitation requires only sending the same signed request/JWT twice in fast succession from an unprivileged HTTP client — no privileged access, no node compromise, and no cryptographic break is needed. The window is narrow (two independent mutex-protected calls back-to-back) but is a classic, well-understood TOCTOU pattern that is reliably exploitable by firing near-simultaneous requests (e.g., from multiple parallel connections), especially under normal internet-facing request concurrency/latency jitter.

### Recommendation
Make replay check-and-record atomic in `jwtReplayCache`, mirroring `RequestReplayGuard.CheckAndRecord`: add a single method (e.g. `checkAndRecord(jti string) bool`) that holds the write lock for both the existence check and the insertion, and call it once from `Authorize` instead of the separate `isReplay`/`recordUsage` calls.

### Proof of Concept
1. Obtain a valid signed trigger JWT for a workflow (`claims.ID` = jti-X) that is properly authorized for the target `workflowID`.
2. Fire two (or more) HTTP requests carrying the identical JWT to the gateway's HTTP-trigger endpoint essentially simultaneously (e.g., using concurrent goroutines/connections to minimize the gap between the `isReplay` and `recordUsage` calls for each).
3. Both requests can pass `h.jwtCache.isReplay(claims.ID)` as `false` before either executes `h.jwtCache.recordUsage(claims.ID)` — this window exists because the two operations are not guarded together.
4. Both calls to `Authorize` return successfully with the same authorized key, and `HandleUserTriggerRequest` proceeds to call `sendWithRetries`/`sendToShard` twice, resulting in two separate downstream workflow-execute triggers dispatched to the DON for what should be a single-use JWT.

Note: I was unable to execute/reproduce this race live (no runtime/terminal access in this mode); the above is derived purely from static code-path analysis of `Authorize`, `jwtReplayCache`, and the calling `HandleUserTriggerRequest` flow. If precise timing behavior under production load needs empirical confirmation (e.g., actual race-window width, or whether any upstream de-duplication by request ID incidentally narrows exploitability), a Devin session with test/runtime access would be needed to build and run a concurrency PoC.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
