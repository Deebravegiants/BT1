Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying `Utils::HmacValidator.validate(request)`, which checks the HMAC over `request.to_signable_string` — the raw request body only. The `shop` value that is then handed to the host app's `WebhookHandler#handle` (as the trusted tenant identifier in `WebhookMetadata`) comes from the `shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a header and is not part of that signable string: [2](#0-1) 

`Registry.process` verifies the HMAC and then dispatches directly using `request.shop`, without ever tying the shop identity to the signed bytes: [3](#0-2) 

The resulting `WebhookMetadata.shop` is treated by the host application as the authenticated tenant for the event: [4](#0-3) 

Because Shopify signs every merchant's webhook for a given app with the **same** `client_secret` (`Context.api_secret_key`), any actor who can install the app on their own shop (e.g. a free development store) will receive genuinely-HMAC'd webhook deliveries. The identity binding that should hold is:

`HMAC(raw_body, client_secret) valid  ⇒  shop header == shop the body actually originated from`

but the code only checks `HMAC(raw_body, client_secret) valid`, and separately trusts `shop-domain` header verbatim. These two are not bound together, so an attacker can take a legitimately-signed payload from their own shop's webhook (or simply the raw JSON body they control from their own install, replayed with a substituted header) and re-POST it to the app's webhook endpoint with `x-shopify-shop-domain` set to a **victim** shop's domain. The HMAC still validates (it is computed only over the body, using the same app secret), so `Registry.process` calls the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload never came from that shop.

### Impact Explanation
This breaks the tenant/shop authentication boundary that `Registry.process` is supposed to enforce via HMAC validation, satisfying the "Cross-tenant access" Critical impact criterion. Depending on how the host app consumes `WebhookMetadata.shop` (nearly universal pattern: look up/act on data keyed by shop domain), an attacker can:
- Trigger app-side data mutations, deletions, or state changes attributed to a shop they don't operate.
- Send a forged `app/uninstalled`, `shop/redact`, or `customers/data_request` event for a shop they don't control, causing wrongful token revocation, data deletion, or GDPR-workflow abuse against another tenant.
- Poison per-shop caches, billing/usage records, or audit logs keyed by the spoofed shop domain.

### Likelihood Explanation
Exploitability requires only: (1) the ability to install the target app on any shop under the attacker's own control (any developer/free trial store, which is available to any unprivileged internet user through the Shopify App Store or dev-store signup), and (2) capturing/crafting an HMAC-valid body for that shop, then replaying it with a substituted `shop-domain` header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged credential is required — the attacker only ever uses their own legitimately-issued webhook deliveries.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`) values into the signed material actually verified, or explicitly cross-check the header-derived shop against a value obtained from a trusted, signed source (e.g., verify the shop is one that this app instance has genuinely installed, and/or include the headers in the HMAC computation as Shopify's raw webhook spec allows via `to_signable_string`). At minimum, document/require that `WebhookHandler` implementations independently verify `data.shop` against known installed shops before trusting it, and consider making `Registry.process` reject webhooks whose declared `shop` was not established as installed via OAuth/token-exchange for this app instance.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a free dev store) and receives a legitimate webhook, e.g. `orders/create`, with:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body B, using app's client_secret>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - raw body `B`
2. Attacker replays the exact same raw body `B` and HMAC header to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Utils::HmacValidator.validate` returns `true` because the HMAC is computed only over the raw body, which is unchanged and still matches the app secret: [5](#0-4) 
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim-shop.myshopify.com"`, even though the body content/data actually pertains to `attacker-shop.myshopify.com`. [6](#0-5)
