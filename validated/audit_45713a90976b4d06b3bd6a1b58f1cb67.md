Confirmed: the webhook `shop` (and `topic`) fields delivered to app handlers are read straight from unauthenticated HTTP headers and never covered by the HMAC signature, which is computed over the raw body only.

### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only that the raw request body matches the HMAC signature, then passes the `shop` value taken from the `x-shopify-shop-domain` header — which is never part of the signed material — to the app's handler as the authoritative tenant identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhook requests that method returns only the raw body: [1](#0-0) [2](#0-1) 

The `shop` accessor is populated straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is attacker-controlled input on the wire and has no cryptographic relationship to the HMAC signature: [3](#0-2) [4](#0-3) 

`Registry.process` only checks the HMAC (which validates the body bytes), then immediately forwards the unauthenticated `request.shop` header value to the registered handler as the tenant identity for the webhook, alongside the HMAC-verified body: [5](#0-4) 

The identity binding that should hold is: `shop == shop_that_produced_this_HMAC`. In reality the code only proves `hmac == HMAC(body, secret)`; `shop` (and `topic`, `webhook_id`, `api_version`) are bytes parsed from headers, not bytes verified. Any party capable of relaying a validly-signed webhook body — for example a malicious or compromised merchant/shop that receives its own genuine webhooks from Shopify and replays them toward the same app endpoint with a forged `x-shopify-shop-domain` header — can cause the app to process the payload as if it belonged to a different shop. Since `api_secret_key` is shared across all shops installing the same app, every shop that has legitimately received at least one webhook (which is guaranteed as soon as the app is installed) already possesses valid `(body, hmac)` pairs signed with the one shared secret, and can freely relabel them to any target shop domain.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide via webhook processing: an app relying on `ShopifyAPI::Webhooks::Registry.process` and the `shop` field of `WebhookMetadata` to select which merchant's data to update, look up, or credit will act on cross-tenant data using an attacker-chosen shop identity, i.e. cross-tenant access — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Exploitation requires no privileged credentials beyond having received one legitimate webhook for any shop under the same app (which happens automatically post-install for every merchant), and only involves replaying an HTTP POST with a swapped header — well within reach of an ordinary internet-capable actor who controls one tenant.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the signature, e.g. by having `to_signable_string` concatenate the relevant headers with the raw body, and reject requests where the header-derived shop does not match a value independently verifiable through the signed payload.

### Proof of Concept
1. App receives a legitimate webhook for `victim-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker (who operates `attacker-shop.myshopify.com`, installed on the same app, and thus also periodically receives genuinely-signed webhooks with body `B'` and matching `H'`) crafts a new HTTP request to the app's webhook endpoint using body `B'` and signature `H'` (both valid and self-consistent, produced by Shopify for the attacker's own shop) but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `HMAC(B') == H'`, which holds.
4. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B'), ...)` — the app now processes attacker-controlled data under the victim shop's identity. [6](#0-5)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
