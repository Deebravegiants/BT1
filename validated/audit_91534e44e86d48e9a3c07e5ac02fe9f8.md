### Title
Webhook `shop` domain is not covered by HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that are handed to the app's handler are read directly from unauthenticated HTTP headers, so the HMAC check does not bind the shop identity to the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, and `webhook_id` are pulled from HTTP headers that are never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` / `validate_signature` compute and compare the HMAC using `verifiable_query.to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` gates on that same HMAC and then forwards the header-derived `request.shop` (along with `topic`/`webhook_id`) straight to the app's handler as trusted identity data: [4](#0-3) 

The binding the gem should guarantee is:
`HMAC-valid(raw_body) == HMAC-valid(raw_body, shop, topic, webhook_id)`

but it only guarantees the former. Because the webhook HTTP endpoint is public (any unprivileged internet user can POST to it — that's the whole point of the delivery mechanism), an attacker who is a legitimate merchant/developer of their own shop can:
1. Install the app on their own store (unprivileged, no special access) and receive a legitimately Shopify-signed webhook — a valid `(raw_body, hmac)` pair for a topic they control (e.g. `orders/create`).
2. Replay that exact `raw_body` and `hmac` value directly to the app's public webhook endpoint, but substitute the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret-derived HMAC — the substituted `shop` header is never part of the signed data.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)`, attributing the attacker's own (legitimately signed) payload to the victim shop.

The gem's own documentation instructs implementers to key downstream logic directly off `data.shop`: [5](#0-4) 

so this is the gem's documented, intended usage pattern — not a misuse of the API by the host application.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide for webhook processing: `shop == authenticated_shop` does not hold, because `shop` is attacker-controlled header data while only the body is authenticated. A host app that stores/updates per-merchant records keyed by `data.shop` (exactly as the docs instruct) can be made to apply an attacker's own webhook data (order, product, GDPR, app-uninstalled, etc.) against a victim shop's record, or vice versa — a cross-tenant data-integrity/confidentiality issue. Depending on topic (e.g. `app/uninstalled`, `shop/redact`), this could also be used to trigger destructive per-tenant actions against a shop the attacker does not own.

### Likelihood Explanation
High likelihood in practice: the attack requires no secrets, tokens, or privileged access — only the ability to install the app on any shop (self-service on the Shopify platform) to harvest one legitimately signed `(body, hmac)` pair per topic of interest, then replay it with a forged `shop` header to the app's public webhook endpoint. No brute force or cryptographic break of the HMAC is needed at all.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material that `HmacValidator` verifies, e.g. include the `x-shopify-shop-domain` header (and topic) in `to_signable_string`, or require the host application to independently verify that `request.shop` matches a shop for which a session/installation is known before trusting `data.shop`, and document this requirement prominently. At minimum, `Registry.process` should not treat the header-derived `shop` as authenticated merely because the body HMAC passed.

### Proof of Concept
1. Install a Shopify app that uses this gem on attacker-owned shop `attacker.myshopify.com`, and let it receive a real webhook (e.g. `orders/create`) — capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Craft a new HTTP POST to the app's webhook endpoint with:
   - The identical raw body and `x-shopify-hmac-sha256` value captured above.
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any value, not the attacker's own domain).
   - `x-shopify-topic` and `x-shopify-webhook-id` copied or forged (also unauthenticated).
3. `ShopifyAPI::Utils::HmacValidator.validate` passes because it only checks the raw body: [6](#0-5) 
4. `Registry.process` invokes the registered handler with `data.shop == "victim-shop.myshopify.com"` and the attacker's own body content, despite Shopify never having sent this webhook for that shop.
