Audit Report

## Title
CORS wildcard-origin suffix-match bypass allows any attacker-registered domain to pass as an allowed subdomain - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `UserServerConfig` HTTP endpoint implements a custom CORS origin allowlist (`isAllowedOrigin`) supporting wildcard subdomain entries such as `https://*.ethereum.org`. The wildcard match strips the `*.` prefix and then only checks `strings.HasSuffix(originHost, allowedHost)`, without requiring a `.` boundary before the suffix, so any attacker-registered domain that merely ends with the configured suffix (e.g. `evilethereum.org`) is treated as a trusted subdomain.

## Finding Description
`isAllowedOrigin` parses the request `Origin` header and each configured allowed origin into scheme/host/port, and for wildcard entries strips `*.` from `allowedHost` then performs an unanchored `strings.HasSuffix(originHost, allowedHost)` check: [1](#0-0) . This lacks any boundary requirement (e.g. requiring the character preceding the suffix match to be a literal `.`), so `evilethereum.org` satisfies `HasSuffix("evilethereum.org", "ethereum.org")` despite not being a subdomain of `ethereum.org`.

This return value is consumed directly in `handleRequest`, which reflects the attacker-controlled `Origin` header back verbatim as `Access-Control-Allow-Origin` once `isAllowedOrigin` returns true: [2](#0-1) .

The existing test suite (`TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) only exercises the case where the origin doesn't end with the configured suffix at all (`https://ethereum.remix.org` vs `*.ethereum.org`), and does not test the sibling-domain suffix-collision case, so the bypass is untested: [3](#0-2) .

## Impact Explanation
This affects the Gateway's `UserServerConfig` endpoint, an internet-facing API intended to be reachable from browsers with a restricted origin allowlist (integration test config uses `CORSAllowedOrigins = ["https://remix.ethereum.org"]`). If an operator uses the supported wildcard allowlist feature (e.g. `*.ethereum.org`), any attacker who registers a sibling domain sharing the suffix can have their malicious webpage's `fetch()` requests receive a reflected `Access-Control-Allow-Origin`, letting them read JSON-RPC responses returned via `ProcessRequest` that were only meant to be exposed to legitimate subdomains of the trusted parent domain — a cross-origin response disclosure of the same class as the referenced Vite CORS CVE.

## Likelihood Explanation
Exploitability only requires an attacker to register any domain ending in the configured allowed suffix (e.g. `evilethereum.org`) and lure a victim's browser to it while it can reach the Gateway's user-facing port. No authentication, operator privilege, or host access is required — this is a standard unprivileged web-attacker scenario, and the flaw is reachable purely through normal HTTP requests with a crafted `Origin` header.

## Recommendation
Fix the wildcard suffix check in `isAllowedOrigin` to require a `.` boundary immediately preceding the suffix match:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Add regression tests covering sibling-domain suffix collisions (e.g. `evilethereum.org` against `*.ethereum.org`).

## Proof of Concept
1. Configure the Gateway `UserServerConfig` with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From a browser hosted at `https://evilethereum.org`, send `fetch('https://gateway.example.com/user', {method:'POST', body:'...'})`.
3. `isAllowedOrigin` evaluates `strings.HasSuffix("evilethereum.org", "ethereum.org")` as `true`, and `handleRequest` sets `Access-Control-Allow-Origin: https://evilethereum.org`, letting the attacker's page read the response despite `evilethereum.org` not being a subdomain of `ethereum.org`.
4. As a unit test: add a case to `httpserver_test.go` similar to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` using origin `https://evilethereum.org` against allowed `https://*.ethereum.org`, and assert that `Access-Control-Allow-Origin` is currently (incorrectly) populated.
