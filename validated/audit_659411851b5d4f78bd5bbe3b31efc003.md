### Title
Webhook `shop-domain` header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` reads the shop identity for an incoming webhook from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Any party who can obtain one valid `(body, hmac)` pair for a webhook — e.g. a merchant who has installed the app and received a legitimate webhook for their own shop — can resend that identical body/HMAC pair while substituting the `shop-domain` header for a different (victim) shop, and the gem will accept it as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from an unauthenticated header with no cryptographic tie to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header — i.e., it authenticates the body bytes only, never the shop header: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity for the event and hands it to the app's handler alongside the body, without any cross-check that the body content actually belongs to that shop: [4](#0-3) 

The equality the gem should enforce is: `shop_that_HMAC_authenticates == shop_delivered_to_the_handler`. In reality the gem only enforces `HMAC(secret, raw_body) == received_hmac`; `shop` is completely outside that equation. Any entity capable of triggering a legitimate webhook for shop A (i.e., any merchant who has installed the app — an "unprivileged" party relative to other tenants) can capture the resulting `(raw_body, hmac)` pair from their own delivery and replay it against the app's webhook endpoint with the `shop-domain` header changed to shop B. `Utils::HmacValidator.validate` still returns `true` because the signature only certifies the body bytes, and `Registry.process` will invoke the topic handler with `shop: "shop-B.myshopify.com"` and shop A's body content.

### Impact Explanation
This breaks the tenant isolation the webhook signature is supposed to guarantee. A malicious merchant (any app installer) can inject arbitrary, attacker-shaped webhook payloads (product/order/customer/app-uninstalled events, etc., since they control their own shop's data that generates the body) into another merchant's tenant context inside the host application. Depending on how the host app trusts `WebhookMetadata#shop` (typically used to select which stored `Session`/access token to act with, or which DB tenant row to update), this enables cross-tenant data corruption, unauthorized state changes performed with the victim's access token, or injection of fabricated records attributed to a shop that never sent that event — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is realistic: obtaining a valid `(body, hmac)` pair requires no secret knowledge — any merchant who installs the app automatically receives such pairs whenever Shopify fires a webhook for their store (they can simply capture their own app's inbound requests, e.g., via their own proxy/logging). The only additional step is replaying the exact bytes to the app's public webhook endpoint with a different `shop-domain` header, which is a standard HTTP-level manipulation requiring no cryptographic material and no privileged access to Shopify or the target app.

### Recommendation
Bind the shop identity cryptographically to the authenticated payload before trusting it:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header value in the string that is HMAC-verified (e.g., have `to_signable_string` incorporate the shop/topic headers alongside the raw body), or
- Cross-check `request.shop` against a shop identifier embedded in the verified body payload, or
- At minimum, document/require the host app to verify that `request.shop` matches an existing, previously-established session/tenant before trusting the webhook, and warn that the current header is unauthenticated in `ShopifyAPI::Webhooks::Request`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it happen to receive a real webhook (e.g. `products/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify — both are visible to the attacker as the receiving party.
2. Attacker resends the identical raw body and HMAC header to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`:
```
POST /webhooks HTTP/1.1
Host: app.example.com
x-shopify-topic: products/create
x-shopify-hmac-sha256: <captured-valid-hmac>
x-shopify-shop-domain: victim-shop.myshopify.com
Content-Type: application/json

<captured-raw-body>
```
3. `ShopifyAPI::Webhooks::Request.new` parses the headers successfully (all required headers present).
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` — this matches the captured hmac because the body is byte-identical to what Shopify originally signed; validation passes: [5](#0-4) 
5. `Registry.process` calls the app's registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to act on the victim tenant using attacker-controlled data.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
