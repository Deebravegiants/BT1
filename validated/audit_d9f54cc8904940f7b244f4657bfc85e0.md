## Finding

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. Any party who can obtain one genuinely-signed webhook body/HMAC pair for their *own* shop (trivial, since anyone can register a free development store and install a public app) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will accept it as authentic for the spoofed shop.

### Finding Description
`Registry.process` authenticates a webhook solely via:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop` is read straight from an HTTP header that plays no part in the signable string: [4](#0-3) 

That unauthenticated `shop` value is then trusted downstream and handed directly to the app's handler as the tenant identifier: [1](#0-0) 

The equality the gem is implicitly (and incorrectly) treating as verified is:
`shop authenticated by HMAC == shop attributed to the processed webhook data`

but in reality only `raw_body authenticated by HMAC == raw_body` holds — the `shop` header is never part of what is signed, so it can be freely substituted without invalidating the signature.

### Impact Explanation
Because the HMAC secret (`api_secret_key`) is per-app, not per-shop, any of an app's own merchants (or anyone who installs a public app on a free/trial store) can capture one legitimately-signed `(raw_body, hmac)` pair from their own shop's webhook delivery, then forge new HTTP requests to the app's webhook endpoint with that same body/HMAC but an attacker-chosen `shop-domain` header pointing at a different, victim merchant. `Registry.process` will pass HMAC validation and invoke the app's handler with `WebhookMetadata` claiming the data belongs to the victim shop. Depending on how the host app uses `data.shop` to route/store data, this enables cross-tenant data injection or corruption (e.g., attacker-controlled order/product data being attributed to another merchant's tenant), satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on any shop (including the attacker's own free development store) to obtain one valid `(body, hmac)` pair for the shared `api_secret_key`, plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No access token, secret, or privileged account is required beyond what any app-installing merchant already has.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`) into the signed material, or otherwise cryptographically tie the header values to the signature — e.g., include the `shop-domain` header in `to_signable_string`, or require host applications to cross-check `request.shop` against an independently-established per-shop record (e.g., a shop known to have an active session) before trusting webhook payload attribution. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target public app on their own (free) development store `attacker.myshopify.com`, triggering a real webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker replays the request to the same app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a real merchant of the app that attacker does not control).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present) and `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(api_secret_key, B) == H`, which is unaffected by the shop header change. [1](#0-0) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"` and `body` is the attacker's own order payload, even though Shopify never actually sent this webhook for `victim.myshopify.com`.
