## Analog Vulnerability Found

### Title
Webhook Shop and Topic Identity Not Bound to HMAC Signature Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` and `topic` identity fields used downstream by `ShopifyAPI::Webhooks::Registry.process` come from unauthenticated HTTP headers. The HMAC check therefore proves the body was signed with the app's secret, but never binds that signature to the shop or topic the caller claims in the headers — the same "value used after/without being covered by the integrity check" flaw described in the reference report, just in header/body form instead of pre/post-removal state.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` and `topic` — the values that determine *which tenant* and *which event* is dispatched — are pulled straight from client-supplied HTTP headers, which are never part of the signed material: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.topic` and `request.shop` to select a handler and construct the metadata delivered to the app: [4](#0-3) 

Equality that should hold but doesn't: `shop_claimed_in_header == shop_that_actually_produced_the_signed_body`. The HMAC only proves `body` was produced by a holder of `Context.api_secret_key`; it says nothing about which shop or topic that body belongs to.

### Impact Explanation
Any merchant who has installed the app on their own store (an ordinary, unprivileged relationship — no `api_secret_key`, access token, or admin privilege required) can trigger a legitimate webhook delivery to capture a valid `(raw_body, hmac)` pair signed by Shopify with the app's shared secret. They can then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers with a victim shop's domain or a more sensitive topic (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`). Because `Registry.process` never checks these headers against the signed content, the forged request passes validation and the handler executes with `shop: <victim shop>`, i.e., cross-tenant data manipulation in the host application, satisfying the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
The attack requires only: (1) installing the target app on an attacker-controlled store (standard, unprivileged), (2) performing an action that triggers any registered webhook to capture a valid body/HMAC pair, and (3) sending a crafted HTTP request with swapped headers to the app's public webhook endpoint. No secret material, TLS interception, or social engineering is needed, and the flow exactly follows the gem's documented `Registry.process(request)` usage pattern, so this is not a case of the host ignoring the documented API.

### Recommendation
Bind `shop` and `topic` into the material that is verified — e.g., include them in `to_signable_string`, or independently verify `request.shop` against a known, previously-established session/tenant before dispatching, so a valid body signature for one shop/topic cannot be replayed under a different shop or topic claim.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and register a webhook handler for a sensitive topic (e.g. `customers/redact`).
2. Perform the triggering action in `attacker-shop` so Shopify sends a legitimately HMAC-signed webhook `(raw_body, hmac)` to the app's endpoint.
3. Intercept/replay that exact `raw_body` and `hmac` to the same endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against `hmac`. [5](#0-4) 
5. The handler executes with `shop: "victim-shop.myshopify.com"`, causing the host app to perform tenant-scoped actions (data deletion, redaction, uninstall cleanup, etc.) against a shop the attacker does not control.
