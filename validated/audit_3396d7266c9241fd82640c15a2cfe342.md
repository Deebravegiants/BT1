### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` dispatches to application handlers are read from HTTP headers that are excluded from the HMAC computation. Any holder of a single valid `(body, hmac)` pair — which is trivially obtainable by any unprivileged user who installs the app on their own store and receives one legitimate webhook — can replay that pair with arbitrary `shop`/`topic`/`webhook_id` headers and pass HMAC validation, causing the host application's webhook handler to process attacker-chosen content under an arbitrary shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read directly from (attacker-controllable) headers, entirely independent of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., only the body), then looks up the handler by the unauthenticated `topic` and forwards the unauthenticated `shop`, `webhook_id`, and `api_version` straight into the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm this: the signature check is `HMAC(secret, verifiable_query.to_signable_string)`, i.e. `HMAC(secret, raw_body)` for webhooks — nothing about `shop`, `topic`, or `webhook_id` factors into the comparison: [4](#0-3) 

The identity binding that should hold is: `shop header used by the handler == shop that Shopify actually generated this HMAC for`. Because the HMAC is computed over `raw_body` alone, this equality is never enforced — `shop` (and `topic`/`webhook_id`) can be swapped freely as long as the `(raw_body, hmac)` pair itself is valid for *some* webhook delivery, from *any* shop, to *any* topic subscribed by the app.

### Impact Explanation
An unprivileged attacker who is able to install the app on their own development/trial store (a normal, unprivileged action) will receive genuine, validly-signed webhook deliveries for that store. Because the signature covers only the body, the attacker can replay the exact same `(raw_body, x-shopify-hmac-sha256)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain, and/or substituting `x-shopify-topic`/`x-shopify-webhook-id` with any topic the app has registered a handler for. `Registry.process` will pass HMAC validation and dispatch the (attacker-chosen) body to the handler tagged with the victim's shop and the attacker's chosen topic. Depending on how the host application's handler uses `WebhookMetadata#shop` (commonly used to select the tenant's DB record/session to act on), this can result in cross-tenant data corruption, incorrect billing/subscription state changes, or triggering of privileged webhook flows (e.g. `shop/redact`, `app/uninstalled`) against a shop the attacker does not control. This satisfies the "cross-tenant access" Critical impact category since the shop-to-request binding is broken without needing the app's `client_secret` or any credential.

### Likelihood Explanation
Likelihood is high given the low bar to exploit: the attacker needs only to install the app on any shop they control (an ordinary, unprivileged action for any Shopify developer) to capture one legitimately signed webhook body/HMAC pair, then replay it with modified headers to the app's public webhook endpoint. No secret material, session, or elevated access is required — only that the host application trusts `shop`/`topic` from `WebhookMetadata` as delivered by this gem.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed payload used for verification (or otherwise cryptographically bind them to the body), so that tampering with any of these fields invalidates the signature. At minimum, document prominently that only the raw body is authenticated and that header-derived fields must not be trusted by handlers without additional verification (e.g., cross-checking `shop` against the session/tenant the webhook subscription was registered for).

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker-shop.myshopify.com`; the app registers a webhook (e.g. for `app/uninstalled`).
2. Capture a legitimate delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H == Base64(HMAC-SHA256(secret, B))`).
3. Replay a POST request to the same app's webhook endpoint with:
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - body `B` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (attacker-chosen)
   - `X-Shopify-Topic: app/uninstalled` (or any topic registered by the app)
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, independent of the shop/topic headers.
5. `Registry.process` invokes the app's `app/uninstalled` handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the host app to act (e.g., deactivate, wipe data, or downgrade) as if the victim shop had uninstalled, despite no such event occurring on the victim's store.
