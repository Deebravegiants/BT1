### Title
Webhook `shop-domain` and `topic` headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, but the `shop` (and `topic`) values that the handler receives and trusts as the authenticated tenant identity are taken from unauthenticated headers. An attacker who can obtain one valid `(raw_body, hmac)` pair for a webhook delivered to their own shop can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop, and the app will process the request as if it legitimately originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC of the signable string (the body) and then dispatches the handler using `request.shop` and `request.topic` taken straight from the headers, with no cross-check that these values were part of what was signed: [3](#0-2) 

`HmacValidator.validate` computes/verifies the signature purely from `verifiable_query.to_signable_string` (the body) and the shared `api_secret_key`: [4](#0-3) 

The library's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify" and explicitly hands `data.shop` to the app's handler as trustworthy tenant context: [5](#0-4) 

The broken identity binding is: `shop header authenticated by HMAC` ≠ `shop header actually delivered to the handler as `WebhookMetadata#shop``. Since the `shop-domain` and `topic` headers are not included in `to_signable_string`, a valid HMAC only proves the app's secret produced that specific body — it proves nothing about which shop or topic the body is associated with.

### Impact Explanation
Any actor who can get one legitimate webhook body+HMAC pair delivered by Shopify (e.g., an ordinary merchant with a normal, unprivileged install of the app on their own store, triggering any subscribed webhook topic for their own shop) can capture that `(raw_body, x-shopify-hmac-sha256)` pair and POST it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header. `HmacValidator.validate` will still succeed because it never inspects those headers, and `Registry.process` will call the registered handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain. If the host application uses `data.shop` to look up per-tenant state, write to a victim shop's records, or make authorized API calls on the victim's behalf using the (falsely) associated shop identity, this results in cross-tenant data injection/corruption in a multi-tenant app — satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
The attacker only needs the ability to receive at least one real webhook for their own store (any normal, unprivileged merchant installation of the app on a shop they control) and the ability to send arbitrary HTTP requests to the app's public webhook callback URL — no `api_secret_key`, access token, or elevated privilege is required. This is a realistic and unprivileged attacker capability.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the HMAC-signed material, or otherwise cryptographically/independently bind them to the verified body (e.g., verify the shop against Shopify by an authenticated follow-up call, or require the app to independently confirm the tuple `(shop, topic, webhook_id)` is one it actually registered/expects) before trusting `WebhookMetadata#shop` for any tenant-scoped action.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app and triggers a subscribed webhook topic (e.g., `orders/create`), producing a legitimate raw body `B` and a legitimate `x-shopify-hmac-sha256: H = HMAC(secret, B)` from Shopify.
2. Attacker captures the pair `(B, H)` (their own webhook delivery, no interception of others' traffic needed).
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, but header `x-shopify-shop-domain: victim-shop.myshopify.com` (and any `x-shopify-topic` they like).
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to treat attacker-supplied content as though it came from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
