### Title
Two-phase graduation permanently freezes curve funds if phase 2 (`finalizeGraduation`) ever reverts after phase 1 (`_enterGraduating`) has already committed irreversible state — ([File: packages/contracts/src/Bonding.sol])

### Summary
The CVE moves a device-type mutation (`team_dev_type_check_change`) to the end of `team_port_add` because the original code committed an irreversible state change *before* all validation checks had passed, and the kernel has no way to unwind that change if a later check fails. `alt.fun`'s graduation flow has the identical shape at the protocol level: `_enterGraduating` (phase 1) permanently drains the curve and flips `lifecycle: Curve → Graduating` in one transaction, and only a *separate*, later transaction (`finalizeGraduation`, phase 2) performs the remaining validation/seeding. Because Solidity's atomicity only protects a single transaction, splitting the "mutate" and "validate" halves across two transactions reproduces exactly the bug class the patch fixes: an early, irrecoverable mutation with no rollback path if the later step fails.

### Finding Description
`Bonding._enterGraduating` is the phase-1 half of graduation. It unconditionally flips the lifecycle and drains the curve before any of the LP-seeding validation in phase 2 has run: [1](#0-0) 

This is deliberately split across transactions per the project's own documentation, because HyperEVM's small block gas ceiling can't fit both phases in one tx: [2](#0-1) 

Phase 2, `finalizeGraduation`, is the only function that can move the token out of `Lifecycle.Graduating`. It performs pair creation/seeding and then a one-shot `LPLock.recordLock` call, finally flipping lifecycle to `Graduated`: [3](#0-2) 

Once phase 1 has run, `Bonding.buy` and `Bonding.sell` both revert for that token (`TokenIsGraduating`), and there is no alternate entry point to un-graduate, retry with fallback parameters, or refund the drained LT/burned tokens back to the curve — `finalizeGraduation` is the sole gate, exactly mirroring the kernel bug's "no way to restore" property once `team_dev_type_check_change` had already run. The project's own `AGENTS.md` acknowledges this exact fragility as the single most important invariant to preserve — "Phase 2 must never revert under any pre-seed shape" — and has built an entire defensive subsystem (`_seedRebalancing`, `_pairRebalance`, `_routerDepositAndDispose`, `_noFeeSwapInput`) purely to keep that promise: [4](#0-3) 

That the team had to build a dedicated "brick resistance" defense specifically for this scenario is itself evidence that the underlying architecture — an irreversible phase-1 commit gated behind a phase-2 that must never fail — is the same anti-pattern as the CVE: a state mutation with no unwind path if the subsequent validation doesn't hold. Any future change to `_enterGraduating`, `finalizeGraduation`, `_prepareGraduationLiquidity`, or the seeding helpers that regresses the "never revert" guarantee (which `AGENTS.md` explicitly flags as easy to break and requiring re-running three separate invariant test suites) reintroduces a permanently bricked token: LT already drained via `Router.graduate` and 250M reserve tokens already burned/parked in `Bonding` in phase 1 become permanently unrecoverable, with trading frozen and no way back to `Lifecycle.Curve`.

### Impact Explanation
If `finalizeGraduation` reverts for any token (e.g., a future regression in the seeding helpers, an interaction with a non-canonical LT/hook, or a gas-budget violation in the documented 2.5M-gas ceiling under an adversarial pre-seed shape), that token is stuck in `Lifecycle.Graduating` forever:
- All curve-raised LT (drained out of the Pair in phase 1 via `Router.graduate`) is trapped inside `Bonding` with no sweep/refund path back to traders or the pair.
- The 250M reserve tokens computation (`tokensForLP`/`lpBurned`) has already been pinned and is unusable.
- Both `buy` and `sell` permanently revert for the token, so no trader, creator, or LP can ever exit — a permanent freeze of funds, not merely a stuck state.

### Likelihood Explanation
Low-to-medium under the current code, since the team has invested substantial, explicitly-documented defensive engineering (`_seedRebalancing`/`_pairRebalance`/`_routerDepositAndDispose`/`_noFeeSwapInput` plus dedicated brick-resistance tests) specifically to keep `finalizeGraduation` from ever reverting. However, the architecture itself — an irreversible phase-1 state commit with a single, must-never-fail phase-2 gate and zero fallback/abort path — is structurally the same anti-pattern the CVE patches, and `AGENTS.md` itself flags this as the most fragile part of the codebase, requiring the full invariant suite to be re-run on any touch. I could not fully verify (within available tool budget) every internal revert condition inside `_prepareGraduationLiquidity`, `_seedUniswapV2Direct`, and `LPLock.recordLock`, so I cannot conclusively prove a currently-reachable revert path in phase 2 with the evidence gathered — this should be treated as a structural/architectural finding rather than a confirmed exploitable bug in the current code.

### Recommendation
Add either (a) a permissionless recovery/retry path for tokens stuck in `Lifecycle.Graduating` that lets `finalizeGraduation` be retried with alternate seeding strategies or safely aborted back to `Curve` with drained funds restored, or (b) formal, enforced invariants (fuzzed against arbitrary LT behavior, not just HyperSwap pre-seed shapes) proving `finalizeGraduation` truly cannot revert for any token state reachable from phase 1, with CI gating any PR that touches the graduation path on those invariants.

### Proof of Concept
Not exploitable with a concrete PoC against the current code without identifying a specific revert-inducing input, since I could not fully audit `_prepareGraduationLiquidity` / `_seedUniswapV2Direct` / `LPLock.recordLock` within the available tool budget. The structural PoC is: any future change (or currently-unknown edge case) that causes `finalizeGraduation` to revert for a token already in `Lifecycle.Graduating` permanently freezes that token's curve-raised LT and reserve tokens, since no other function can move the token's lifecycle forward or backward.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```

**File:** packages/contracts/AGENTS.md (L83-93)
```markdown
- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).
- **Virtual token reserve.** At launch, `Pair.reserve0 = totalSupply (1B)` while only `curveSupply = 75%` (750M) of real tokens are transferred to the pair. The other 250M (`LP_RESERVE`) sit in `Bonding` for graduation. This extends the curve beyond the sellable supply, which is what makes dynamic LP seeding work cleanly.
- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
- **Parabola invariant.** With `V_t_init = totalSupply` and `curveSupply = 75%`, the function `tokensForLP(sold) = sold·(S−sold)/S` peaks at `S/4 = LP_RESERVE`. The cap in `_prepareGraduationLiquidity` is defensive — it can never bind in normal operation.
- **Overflow buy cap.** `Router.buy` caps `tokensOut` at the pair's real balance and back-calculates the LT consumed, so the last buy cannot exceed remaining supply. `Zap.buy` returns the unused LT (`ltMinted - amountInUsed`) directly as LT — not redeemed, to avoid re-incurring the LT redemption fee on dust — while unconverted USDC and the fee over-charge are refunded in USDC. `Bonding.buy` returns `(tokensOut, amountInUsed)` for this reason.

All 7 zero-gap invariants must still pass; the phase-1-fits-in-small-block budget assertion (1.8M) must still hold; the brick-resistance regression test must still pass.
