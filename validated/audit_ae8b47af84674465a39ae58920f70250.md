### Title
Reentrancy via unchecked external call before escrow decrement in `IntentGatewayV2.withdraw` (Tron variant) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` implements its own `withdraw()` routine that violates the Checks-Effects-Interactions pattern the mainline EVM contracts (`IntentsBase._withdraw`) deliberately follow. Unlike `IntentsBase.sol`, which decrements `_orders[commitment][token]` **before** any external transfer, the Tron variant's `withdraw()` calls out to the beneficiary/token **before** updating escrow accounting for each token entry.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2.sol` is invoked from `onAccept` (RedeemEscrow/RefundEscrow) and `onGetResponse`, both triggered by relayed ISMP messages that any relayer can deliver by supplying a valid state proof — this is the standard, permissionless settlement path for a filled or cancelled cross-chain intent order: [2](#0-1) [3](#0-2) 

Inside `withdraw`, for each token in the withdrawal request, the code performs a low-level `.call` to transfer native ETH/TRX or ERC20 tokens to the `beneficiary` **before** decrementing the escrow balance for that token: [4](#0-3) 

This is the opposite ordering of the audited/fixed mainline implementation, `IntentsBase._withdraw`, which decrements `_orders[commitment][token]` immediately after computing the escrowed balance and **before** performing the transfer: [5](#0-4) 

The check guarding this loop only verifies `_orders[commitment][token] != 0` (non-zero), not that it is `>= amount`, so a beneficiary that controls both the escrow input token list (via `placeOrder`, which allows duplicate token entries that additively accumulate into the same `_orders[commitment][token]` slot, see `placeOrder` line 463) and a malicious `receive()`/token callback can re-enter during the native-token `.call` at line 703, before the corresponding decrement at line 710 executes.

### Impact Explanation
If the beneficiary is a contract, the native-token transfer at line 703 (`beneficiary.call{value: amount}("")`) hands control to attacker code before the escrow ledger is updated. Because escrow entries for the same token can be duplicated/split across multiple `WithdrawalRequest.tokens` entries (mirroring `order.inputs`), and the balance check is a simple non-zero check rather than a sufficiency check, a reentrant call into any other unprivileged, reachable function that reads/mutates `_orders[commitment][token]` during this window (e.g., a same-chain fill/withdraw path or a second concurrently in-flight settlement referencing the same commitment/token) can observe stale (not-yet-decremented) escrow state, enabling double payout of the same escrowed funds — a direct theft-of-funds / permanent-freezing risk against the intent escrow.

### Likelihood Explanation
Likelihood is high for the specific token(0)/native-asset branch, since the external call unconditionally executes with attacker-controlled fallback code whenever the beneficiary address is a contract, and no reentrancy guard exists on `withdraw`, `onAccept`, or `onGetResponse` in this file. The primary constraint is that `onAccept`/`onGetResponse` are `onlyHost`-restricted, so a directly self-recursive call is blocked; however, the vulnerable ordering (external call before effects) remains a structural CEI violation that the maintainers already fixed in the mainline `IntentsBase.sol` contract (see the `IntrinsicIntentsReentrancyTest.sol` regression suite explicitly documenting and testing this exact bug class), and it was left unaddressed in this parallel Tron implementation, indicating the fix was not propagated.

### Recommendation
Apply the same CEI fix used in `IntentsBase._withdraw` to the Tron `IntentGatewayV2.withdraw`: decrement `_orders[commitment][token]` (and the `_filled` finalize state) **before** performing the external transfer for each token, i.e.:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount; // effects first
// then perform the transfer
```
Apply the identical ordering fix to the fee-token release block and add a `nonReentrant` guard as defense-in-depth, consistent with the mainline contract's pattern.

### Proof of Concept
1. Attacker places a same-chain/cross-chain order via `placeOrder` with `order.inputs` containing a token entry of type `address(0)` (native asset), and arranges (via duplicate `WithdrawalRequest.tokens` entries mapped from `order.inputs`, or via a second in-flight settlement referencing the same commitment/token) for `_orders[commitment][address(0)]` to be read twice before being decremented.
2. Attacker's contract is set as `beneficiary` (`bytes32(uint256(uint160(attackerContract)))`).
3. A relayer delivers the RedeemEscrow/RefundEscrow message; `onAccept` → `withdraw` executes the loop; at `beneficiary.call{value: amount}("")` (line 703), attacker's `receive()` fires before line 710's decrement executes.
4. During the reentrant window, attacker's fallback triggers a code path that reads `_orders[commitment][address(0)]` (still non-zero) to trigger a second payout for the same commitment/token before the original decrement lands, resulting in double-spend of escrowed funds.
