### Title
POA Bridge withdrawal status/tx-hash misattribution across same-asset withdrawals in one batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status of a specific withdrawal by matching only on `assetId`, ignoring the `index`/destination/amount that uniquely identify which withdrawal within a batch it is describing. When a caller submits multiple withdrawals of the same token (same `assetId`) but to different destination addresses/amounts within a single NEAR intent transaction, the SDK will report the wrong withdrawal's completion status/tx hash for a given `WithdrawalIdentifier`.

### Finding Description
`createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` (lines 80-107) builds one `WithdrawalIdentifier` per entry of the caller-supplied `withdrawalParams` array for a single `intentTx`, assigning a per-bridge-route `index` in submission order. Nothing prevents a caller from supplying two withdrawals with the same `assetId` but different `destinationAddress`/`amount` in one call.

For the POA route, `PoaBridge.createWithdrawalIdentifier` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:295-311`) stores the `index` in the identifier, but `describeWithdrawal` (lines 313-343) never uses that index to disambiguate; instead it calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (lines 318-322, defined at 409-427), which is:
```
function findMatchingWithdrawal(withdrawals, assetId) {
  return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
This performs an equality match on `assetId` alone — not on `destinationAddress` or `amount`. The code's own comment acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported... POA API doesn't currently support this case either" (lines 409-416). But there is no guard anywhere in the SDK (`createWithdrawalIdentifiers`, `signAndSendWithdrawalIntent`, `waitForWithdrawalCompletion`) that rejects or warns on this input shape — the caller can freely construct such a batch, and the SDK will silently mismatch statuses instead of failing loudly.

Consequence: `watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:20-78`) uses `bridge.describeWithdrawal` to decide when a promise for a *specific* withdrawal index resolves as completed and with which `txHash`. If two withdrawals of the same asset (e.g., withdrawal #0 to address A, withdrawal #1 to address B) are in flight, both `describeWithdrawal` calls will match the *same* single entry returned by the POA API `getWithdrawalStatus` response (since the match is assetId-only), so both `WithdrawalIdentifier`s resolve to the same status/txHash even though only one of the two withdrawals is actually described by that API entry.

### Impact Explanation
This breaks the equality "the withdrawal identifier described equals the on-chain outcome actually reported." An integrator that batches multiple same-token withdrawals to different destinations in one intent (a legitimate use case the public API does not forbid) can have withdrawal B falsely reported "completed" with withdrawal A's `txHash` (or vice versa) before it has actually settled on-chain, or have a failed/pending withdrawal wrongly marked completed. Per the report's impact classes, this is a status/hash misreport that could cause an integrator to credit or release funds based on an unrelated transaction hash, or fail to detect an actually-failed withdrawal — a High-severity class of issue (status misreport causing double credit or premature release).

### Likelihood Explanation
Requires no privileged access — any integrator/caller who batches ≥2 same-`assetId` POA-bridge withdrawals in a single `signAndSendWithdrawalIntent`/withdrawal-params call, going to distinct destinations, triggers this. The code path is reachable through the standard public SDK surface (`packages/intents-sdk/src/sdk.ts`, `core/withdrawal-watcher.ts`) with no validation rejecting duplicate-asset batches, so the precondition is easy to hit unintentionally, and the resulting misreport is silent (no error thrown).

### Recommendation
In `PoaBridge.describeWithdrawal`/`findMatchingWithdrawal`, disambiguate by more than `assetId` — additionally match on `destinationAddress` and `amount` (or reject/track consumed entries so each POA API withdrawal record can only satisfy one `WithdrawalIdentifier`). Alternatively, have `createWithdrawalIdentifiers`/`supports` explicitly detect and reject batches containing duplicate `assetId` values routed to the POA bridge until the POA API supports disambiguation, so integrators get a clear error instead of a silent cross-attribution of status.

### Proof of Concept
1. Caller submits one NEAR intent transaction containing two POA-bridge withdrawal intents for the same `assetId` (e.g., `nep141:zec.omft.near`) — withdrawal #0 to destination A for amount X, withdrawal #1 to destination B for amount Y.
2. `createWithdrawalIdentifiers` produces two `WithdrawalIdentifier`s with `index: 0` and `index: 1`, both same `assetId`, sharing the same `tx.hash` [1](#0-0) .
3. Once the POA bridge settles withdrawal #0 (to A) as `COMPLETED`, both `describeWithdrawal` calls (for index 0 and index 1) call `findMatchingWithdrawal(response.withdrawals, "nep141:zec.omft.near")`, which returns the same single completed entry for A regardless of which identifier is queried [2](#0-1) [3](#0-2) .
4. `watchWithdrawal` for withdrawal #1 (destined for B) resolves as `{ status: "completed", txHash: <A's transfer_tx_hash> }` even though B's withdrawal has not settled — the reported `txHash` does not correspond to the on-chain outcome for B [4](#0-3) .

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
