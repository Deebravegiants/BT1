### Title
Missing sender/channel authentication before processing `RequestState` in Orb-relay client allows unauthorized session-state disclosure - ([File: orb-relay-client/src/client.rs])

### Summary
In `PollerAgent::main_loop`, incoming relay payloads are authenticated by comparing `src.id` against the expected paired party's ID (`self.config.dst_id`) — this is orb-core's analog of the "authenticate the message with channel-id/sender" check that Allora's `OnRecvPacket` was found to be missing. However, this authentication check is bypassed entirely for one specific message type: `self_serve::app::v1::RequestState`. The code checks for a `RequestState` match *before* verifying `src.id`, and if matched, unconditionally replays `self.last_message` back on the stream without ever validating that the request came from the authenticated counterpart.

### Finding Description
The relay stream handling loop is: [1](#0-0) 

```rust
message = response_stream.next() => {
    match message {
        Some(Ok(RelayConnectResponse {
            msg: Some(relay_connect_response::Msg::Payload(RelayPayload {
                src: Some(src), dst, seq, payload: Some(payload),
            })),
        })) => {
            if self_serve::app::v1::RequestState::matches(&payload).is_some() {
                sender_tx.send(self.last_message.clone()).await...
            } else if src.id != self.config.dst_id {
                tracing::error!("Skipping received message from unexpected source: ...");
            } else {
                self.handle_message(...).await?;
            }
        }
```

For every other message type, the code enforces `src.id != self.config.dst_id` (i.e., verifies the message actually originates from the paired Orb/App entity that this client session is bound to) before accepting/buffering it — this is the equivalent of the "channel-id/sender authentication" the report calls for. For `RequestState`, that check is entirely skipped: the branch order means any entity able to deliver a `RequestState` payload to this client's relay stream — regardless of its `src.id` — causes the client to immediately resend `self.last_message` (the last state/payload sent by this side, e.g. an `AnnounceOrbId`, `CaptureStarted`, or other self-serve orb/app state payload) back onto the wire.

### Impact Explanation
`self.last_message` can contain session-relevant state (e.g., `AnnounceOrbId` carrying the Orb ID, or other self-serve signup state announced to the paired App). Because the `RequestState` branch is dispatched before source authentication, an unauthenticated or mismatched sender on the relay channel can trigger replay/disclosure of the last message intended for the legitimate paired party, without needing to pass the `src.id == dst_id` check the rest of the protocol relies on. This breaks the intended trust boundary between the Orb and its paired App session and can lead to cross-session state leakage in the self-serve signup flow (orb_relay signup announcement/state), which is the entry point used in `do_signup`/`orb_relay_announce_orb_id` (`src/plans/mod.rs`).

### Likelihood Explanation
Likelihood depends on whether the underlying `orb-relay` transport/server enforces routing so that only the intended paired entity can push a `RequestState` payload onto a given client's stream. Within `orb-relay-client` itself — the code reachable and auditable here — there is no defense-in-depth check on `src` for this message type, unlike every other payload type. Given the explicit `// TODO: We need to split auth and subscription...` comment directly above this loop acknowledging that auth/subscription separation is incomplete, this gap is a genuine, currently-reachable weakness in the client-side trust boundary, even if partially mitigated by server-side routing that isn't visible in this repo.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of (or apply it uniformly to) the `RequestState::matches` branch so that replay of `last_message` only occurs for authenticated sources, matching the authentication applied to all other incoming payload types.

### Proof of Concept
Conceptual (client-side) trigger, given a relay server that forwards a `RequestState` payload to a client's stream from a source whose `src.id` does not equal `self.config.dst_id`:
1. Attacker delivers a `RelayPayload` containing a `self_serve::app::v1::RequestState` payload with an arbitrary/mismatched `src.id`.
2. `main_loop` matches `RequestState::matches(&payload).is_some()` first, skipping the `src.id != self.config.dst_id` check entirely.
3. `sender_tx.send(self.last_message.clone())` executes unconditionally, replaying the last state payload back over the stream to whoever/wherever routes to that sender. [2](#0-1) 

I was not able to inspect the relay server-side routing/authorization logic (not present in this repo), so I cannot confirm whether server-side controls independently prevent an unmatched `src.id` from reaching this branch in practice — this should be verified server-side as well.
