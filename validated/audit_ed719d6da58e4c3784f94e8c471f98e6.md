## Title
Webhook Shop/Topic Spoofing via HMAC Not Covering Header-Derived Identity Fields - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats `shop`, `topic`, `webhook_id`, and `api_version` as trusted, tenant-identifying fields, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies covers only the raw request body. Since the webhook signing secret (`Context.api_secret_key`) is a single app-wide secret shared across every shop that installs the app, any shop that receives one legitimate webhook can replay that exact signed body to the app's endpoint while forging the `shop-domain`/`topic` headers to impersonate a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw HTTP body — none of the identity-bearing headers are part of the signed content: [2](#0-1) 

`Registry.process` only checks this body-only HMAC before dispatching to the handler with the *header-derived* (unauthenticated) `shop`, `topic`, `webhook_id`, and `api_version`: [3](#0-2) 

This breaks the intended identity binding: `bytes verified (raw_body HMAC) != bytes/fields acted on (shop, topic, webhook_id headers used to route/attribute the event)`. Because `api_secret_key` is one value shared by the app across *all* installing shops (not shop-scoped), a valid `(raw_body, hmac)` pair obtained from a webhook delivered to shop A remains cryptographically valid when replayed with shop B's domain in the `X-Shopify-Shop-Domain` header. The library has no mechanism to detect or reject this, since it never binds `shop`/`topic` into the signed payload.

### Impact Explanation
This is a cross-tenant boundary violation: an attacker who legitimately installs the app on their own store (an "unprivileged internet user" from the app's perspective) can attribute arbitrary genuine-looking webhook events to any other shop using the app, without ever obtaining the victim's credentials. Any host application that uses `WebhookMetadata#shop`/`#topic` to select which merchant's records to update, delete, or reconcile (the documented and expected usage pattern) can be tricked into applying attacker-controlled data changes to a different tenant's data — a cross-tenant access/integrity violation.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs their own legitimate installation of the target app (which any merchant can obtain, since app installation itself requires no special privilege), trigger an action that generates a webhook with a body shape they find useful, capture the raw body + valid `hmac-sha256` header from that delivery, and POST it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header. No knowledge of `api_secret_key` or any victim credential is required — only observation of one's own legitimately delivered webhook.

### Recommendation
Bind the tenant-identifying fields into the verified signature, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signed payload (e.g., derive/verify them from a signed envelope rather than raw headers), and document that `Registry.process` callers must independently confirm the reporting shop is one they registered a webhook for/expect, rather than trusting `request.shop` as authenticated solely because the body HMAC passed.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com` and on victim's shop `victim.myshopify.com`.
2. Attacker triggers an event (e.g., `orders/create`) on their own shop, and Shopify delivers a webhook to the app with body `B` and header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC(api_secret_key, B)`), along with `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry.process` succeeds because it only checks `HMAC(api_secret_key, B) == H`, which is unaffected by the header change: [4](#0-3)  The handler is invoked with `data.shop == "victim.myshopify.com"`, even though the event actually originated from the attacker's shop.
