### Title
Webhook `shop` and `topic` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw HTTP body only, while the `shop` and `topic` values that the registry uses to dispatch and attribute the webhook are taken from unauthenticated HTTP headers. Any actor who can obtain a single genuine `(body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing the webhook Shopify sends them) can replay that exact body/HMAC pair while freely rewriting the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers. `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and invoke the registered handler with an attacker-chosen `shop` and `topic`, breaking the identity binding between "HMAC-authenticated bytes" and "shop/topic acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` and `topic` are read straight from request headers, with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to a handler using the unauthenticated `request.topic`, and constructs `WebhookMetadata` using the unauthenticated `request.shop`: [4](#0-3) 

The identity equality that should hold is: `shop_that_HMAC_authenticates == shop_the_handler_acts_on`. In this implementation, the HMAC authenticates only the byte-for-byte body, not the `shop-domain` or `topic` headers, so this equality is not enforced. Any party in possession of one valid `(raw_body, hmac)` pair for the app (trivially obtainable by installing the app on their own store, since the app's `client_secret`/HMAC key is shared across all shops using the app) can resubmit that exact pair to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header. `HmacValidator.validate` will still return `true` because it never looks at those headers, and `Registry.process` will hand the attacker-chosen `shop` (and `topic`) straight to the host application's webhook handler as if Shopify had certified it.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker with no relationship to the victim shop can cause the app's webhook handler to run with `shop` set to an arbitrary victim `myshopify.com` domain, and with an arbitrary `topic`, including mandatory compliance topics (`customers/redact`, `shop/redact`, `customers/data_request`). Any host application logic that trusts `WebhookMetadata#shop`/`#topic` (which is the intended, documented contract of the gem) to scope data writes/deletes/GDPR actions per-tenant can be tricked into performing actions against, or attributed to, a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The bar to exploit is low: the attacker only needs one legitimate webhook delivery for the target app, which is easy to obtain by installing/using the app on any shop (including a free development store) and capturing the resulting webhook POST body and `X-Shopify-Hmac-Sha256` header. No access to the app's `client_secret`, access tokens, or any privileged credential is required — this is precisely the "field acted on but not covered by the HMAC" analog called out in the rules.

### Recommendation
Bind `shop` and `topic` cryptographically to the authenticated payload, e.g. by including the `shopify-shop-domain` and `shopify-topic` header values in the HMAC-signable string (as Shopify's own HMAC scheme is only defined over the raw body today, so this requires the gem to perform an additional application-level binding check), or at minimum have `Registry.process` cross-check that the `shop`/`topic` headers are consistent with values embedded in the verified body where the webhook payload includes them, and document/require host applications to independently verify shop provenance (e.g., against a known list of installed shops) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook (e.g. `products/create`). Shopify sends the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared secret), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: products/create`.
2. Attacker replays the exact same `B` and `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and, if desired, `X-Shopify-Topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only recomputes the HMAC over `B`, which is unchanged.
4. `Registry.process` looks up the handler by the attacker-controlled `request.topic` and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the host application's handler executes believing Shopify certified this event for `victim-shop.myshopify.com`. [5](#0-4)

          received_signature = verifiable_query.hmac
