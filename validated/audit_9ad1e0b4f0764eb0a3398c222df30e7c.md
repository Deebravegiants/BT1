### Title
Missing sender-module authentication in `BandwidthManager.onAccept` allows any Hyperbridge/Polkadot pallet to spoof `pallet-bandwidth` governance and drain treasury funds - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.onAccept` authenticates an inbound ISMP `PostRequest` only by checking that the message came through the configured host (`onlyHost`) and that `request.source` equals the Hyperbridge/nexus state machine id. It never checks `request.from`, i.e. it never verifies that the message actually originated from `pallet-bandwidth` (`PALLET_BANDWIDTH_MODULE_ID = "BWMARKET"`) on that chain. Because any pallet or account on the source state machine can dispatch an ISMP POST request addressed to an arbitrary destination module, any actor controlling a pallet/module on the Hyperbridge parachain (or, if that parachain permits arbitrary XCM-triggered dispatch, any sufficiently privileged extrinsic origin there) can forge a message that `to`-addresses `BandwidthManager` and carries a `Withdraw` or `SetTiers` action, and `BandwidthManager` will execute it as if it were genuine governance from `pallet-bandwidth`.

### Finding Description
`onAccept` performs the following checks, in order: [1](#0-0) 

1. `onlyHost` – restricts the caller to the configured `EvmHost`.
2. `request.source.equals(IDispatcher(_host).hyperbridge())` – restricts the *chain* the message must come from to the Hyperbridge/nexus state machine.

It never checks `request.from` against `PALLET_BANDWIDTH_MODULE_ID`. Contrast this with the sibling apps in the same codebase, all of which additionally authenticate the sending *module* on the source chain:

- `HyperFungibleToken`/`BridgeToken` check the source chain **and** that `from` equals the registered pallet id (`_supportedChains[source]`), reverting with `UnauthorizedSource` otherwise: [2](#0-1) 
- `HostManager`/`IntentGatewayV2` additionally gate delivery on a specific authorised relayer address before decoding any action, as documented in the codebase's own security hardening notes: [3](#0-2) 

`BandwidthManager` has neither of those protections. Once a request clears `onlyHost` and the coarse chain-level `source` check, the first body byte is decoded as `OnAcceptActions` and dispatched unconditionally to either `SetTiers` (rewrites `tierPrice`, affecting future purchasers) or `Withdraw` (transfers arbitrary `amount` of arbitrary `token`, including ERC20 or native ETH, to an arbitrary `beneficiary`): [4](#0-3) 

The `source` check alone is insufficient authentication: `source` only identifies *which chain* the ISMP message came from, not *which module/pallet on that chain* dispatched it. On a general-purpose Polkadot-style parachain (the id checked here is a Polkadot parachain, "nexus"/hyperbridge), any pallet capable of dispatching an ISMP `POST` request (which is the entire point of `pallet-ismp`'s permissionless dispatch API) can address its request to `BandwidthManager`'s address on the destination EVM chain and forge an identical wire body to `BandwidthPurchaseMsg`'s counterpart governance actions. `EvmHost.dispatchIncoming`/`HandlerV2.handlePostRequests` only verify that the *state commitment* proof is valid for the claimed source chain and that the request is addressed to this chain/module — they do not, and cannot, know which pallet's logic is "supposed" to speak for a given application-level protocol; that is left to each `IApp.onAccept` implementation, which is exactly the check every other app in this repo performs and `BandwidthManager` omits.

### Impact Explanation
This directly matches the Chainswap bug class: a missing/insufficient sender-authorization check on a cross-chain message handler leads to unauthorized privileged actions being accepted as if from a whitelisted, trusted source. Here the consequence is concrete theft of protocol funds: the `Withdraw` action transfers arbitrary ERC20 or native token balances held by `BandwidthManager` (accumulated fee-token revenue from `purchase()` calls) to an attacker-chosen `beneficiary`, and `SetTiers` lets an attacker rewrite bandwidth pricing to manipulate the storefront. Both are single-message, single-transaction reachable given a forged (but otherwise correctly proven, since the check that's missing has nothing to do with consensus/MMR proof validity) dispatch from any pallet on the Hyperbridge/nexus chain.

### Likelihood Explanation
Likelihood is High: no special privilege beyond the ability to dispatch an ISMP POST request from *some* pallet on the Hyperbridge parachain (nexus) is required — this is a permissionless, general-purpose capability of `pallet-ismp`, not a governance-only or admin-only action. The attacker does not need to compromise consensus, the relayer, or any admin key; they only need to construct a POST request whose `to` field is `BandwidthManager`'s address and whose body matches the expected `OnAcceptActions` encoding, then have it relayed like any ordinary message (the relaying/proof-submission path is unprivileged and permissionless per `HandlerV2.handlePostRequests`).

### Recommendation
Add a check in `BandwidthManager.onAccept` (and anywhere else `from` should be pinned) requiring `request.from` to equal `PALLET_BANDWIDTH_MODULE_ID`, mirroring `HyperFungibleToken`'s `_supportedChains`/`UnauthorizedSource` pattern, e.g.:
```solidity
if (!request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```
placed alongside the existing `source` check before decoding `OnAcceptActions`. Consider also adopting the same relayer-allowlist gate used by `BridgeToken`/`HostManager`/`IntentGatewayV2` for defense in depth on this governance surface.

### Proof of Concept
1. Attacker controls (or is) any pallet on the Hyperbridge/nexus parachain capable of dispatching an ISMP POST request (a routine, permissionless capability of `pallet-ismp`).
2. Attacker dispatches a POST request with:
   - `source` = nexus/Hyperbridge state machine id (satisfied trivially, since the attacker's pallet genuinely lives on that chain)
   - `to` = `BandwidthManager`'s address on the target EVM chain
   - `from` = attacker's own pallet id (anything other than `"BWMARKET"`)
   - `body` = `bytes.concat(bytes1(uint8(OnAcceptActions.Withdraw)), abi.encode(Withdrawal({token: feeToken, beneficiary: attacker, amount: BandwidthManager.balance})))`
3. A relayer (anyone, permissionlessly) submits the proof through `HandlerV2.handlePostRequests`, which validates the MMR/consensus proof for the claimed source chain/height — a proof that is legitimately obtainable since the message genuinely was dispatched and included on that chain, just not by `pallet-bandwidth`.
4. `EvmHost.dispatchIncoming` calls `BandwidthManager.onAccept`, which passes `onlyHost` and `request.source.equals(hyperbridge)`, decodes `Withdraw`, and transfers the entire fee-token balance to the attacker's `beneficiary` address.

Note: full confirmation that a Hyperbridge/Polkadot pallet can freely choose an arbitrary `to` value for a dispatched POST request (i.e., that `pallet-ismp`'s dispatch API does not itself pin `from`/`to` pairs at the runtime level) could not be independently verified from the indexed portions of the pallet code in this session; the analysis above is based on the EVM-side contract logic and the documented dispatch/authentication pattern used consistently by every other `IApp` in this repository (`BridgeToken`, `HyperFungibleToken`, `HostManager`, `IntentGatewayV2`), all of which explicitly authenticate `request.from` and `BandwidthManager` alone does not.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
