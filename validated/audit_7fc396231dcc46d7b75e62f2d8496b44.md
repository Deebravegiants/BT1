Confirmed root cause. The `WebhookMetadata.shop` field is passed directly to app-provided handlers as the tenant identifier ` [1](#0-0) `, and `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `request.shop` ` [2](#0-1) `, while the `Request`'s `to_signable_string` (the HMAC-covered payload) is only the raw body — the `shop-domain` header is excluded ` [3](#0-2) `.

### Title
Webhook shop identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop-domain` header from the HMAC-signed payload. `Registry.process` validates the HMAC against only the body and then dispatches `request.shop` (parsed from the unsigned header) to the host app's `WebhookHandler` as the tenant identifier in `WebhookMetadata`.

### Finding Description
`HmacValidator.validate` computes/verifies the signature over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` alone [4](#0-3) . The `shop` accessor is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed string [5](#0-4) . `Registry.process` raises only if the body HMAC fails, then immediately builds `WebhookMetadata` using `request.shop` as the trusted tenant identity passed to the handler [2](#0-1) .

This breaks the intended identity binding: `shop-in-signed-payload == shop-used-for-tenant-routing`. In this gem, the signed payload contains no shop identity at all — only the body bytes are covered. An unprivileged holder of any one genuinely-signed webhook (i.e., a merchant who has installed the app themselves and can trigger their own webhook events, such as `orders/create` or `app/uninstalled`) can capture a legitimate `(raw_body, hmac)` pair for their own shop and re-send it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. Because the HMAC only covers the body, the forged request still passes `Utils::HmacValidator.validate` and is dispatched to the handler with `data.shop` set to the victim's domain.

### Impact Explanation
If the host application (following this gem's documented API, i.e., trusting `WebhookMetadata#shop` as the tenant to act on — this is the field explicitly designed for that purpose) uses this value to select which merchant's session/store/data record to update, an attacker-controlled shop can cause tenant-scoped mutations, data disclosure, or state changes attributed to a shop they do not own — a cross-tenant access issue.

### Likelihood Explanation
Exploitation only requires a normal, unprivileged merchant install of the target app (no `api_secret_key`, access token, or privileged account needed) plus the ability to trigger one webhook for their own shop and replay it with a modified header, which is straightforward HTTP header tampering against the app's own public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the signed body (e.g., derive/verify shop identity from a Shopify-issued token rather than an unsigned header), so `to_signable_string` covers everything `WebhookMetadata` exposes to handlers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. updates an order), receiving `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds, since `B` and `H` are unchanged [6](#0-5) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs its business logic as if the event genuinely originated from the victim shop [7](#0-6) .
