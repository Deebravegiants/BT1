## Title
Unchecked ERC20 return value in `withdraw`/`SweepDust` allows non-compliant or false-returning tokens to permanently freeze escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent funds and swept protocol dust using a raw low-level `.call()` with the `IERC20.transfer` selector, checking only the call's `success` flag and never decoding/validating the returned boolean. [1](#0-0) [2](#0-1) 

### Finding Description
The external report's bug class is about ERC20 tokens that don't strictly follow the standard (either not returning a boolean at all, or returning `false` on failure instead of reverting). The correct fix, applied consistently elsewhere in this same contract for *inbound* transfers (`safeTransferFrom`) via `using SafeERC20 for IERC20;`, is absent from the *outbound* release paths:

- `onAccept`'s `SweepDust` branch: `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount)); if (!success) revert TransferFailed();` [2](#0-1) 
- `withdraw()` (called for both `RedeemEscrow` and `RefundEscrow` requests, and for solver escrow release and fee release): `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();` [3](#0-2) 

This pattern only checks whether the external call itself reverted; it does **not** decode the returned data to confirm the token reported `true`. For any ERC20 that signals failure by returning `false` (rather than reverting) — a well-documented non-compliance pattern — the `_orders[commitment][token]` accounting is unconditionally decremented (line 710) even though no tokens were actually moved to the beneficiary. The escrowed balance is silently written off while the underlying tokens remain stuck in the contract, since `_orders[...]` has already been zeroed and cannot be re-claimed through `withdraw` (guarded by `if (_orders[body.commitment][token] == 0) revert UnknownOrder();`) or through any other exposed recovery path. [4](#0-3) 

The same file correctly uses `safeTransferFrom` for taking tokens in (`placeOrder`, fill flows), showing the codebase is aware SafeERC20 is required for non-compliant tokens, but the fix was not applied symmetrically to the outbound `transfer` calls in `withdraw`/`SweepDust`. [5](#0-4) 

### Impact Explanation
This path is reached whenever Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` message to release a solver's or user's escrowed input tokens, or when the protocol sweeps dust. If the escrowed token (or the fee token) is one that returns `false` on failure instead of reverting, the contract will treat the transfer as successful, decrement/delete the escrow record, and the tokens remain permanently locked in the `IntentGatewayV2` contract with no way for the intended beneficiary to reclaim them. This is a permanent freezing-of-funds condition reachable by any solver/user who fills or places an order denominated in such a token — an unprivileged, single-transaction/relayed-message path (intent solver / relayer delivering the ISMP message), matching the "intents escrow" and "relayer fee/reward accounting" reachable classes in scope.

### Likelihood Explanation
Likelihood is moderate: it requires a token used in an order/escrow that is non-standard in the specific way of returning `false` on failed transfer (e.g., insufficient contract balance from fee-skimming, blacklisting, or pausable tokens), or that has some out-of-balance edge case that makes the transfer legitimately fail without reverting. Given IntentGatewayV2 is designed to be permissionless with arbitrary ERC20 tokens specified per-order (`TokenInfo.token`), and Tron's ecosystem includes many non-standard TRC20 tokens, the likelihood of encountering such a token is realistic, especially since the contract already had to special-case fee-on-transfer tokens elsewhere in the codebase, showing awareness that non-standard tokens are expected inputs.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` in this same contract) for the outbound transfers in `withdraw()` and the `SweepDust` branch of `onAccept`, replacing the raw `.call()` + `success`-only check with `IERC20(token).safeTransfer(beneficiary, amount)` (and same for `feeToken` and `req.beneficiary`). This ensures both non-compliant no-return-value tokens and tokens that return `false` are handled correctly (the former no longer reverts spuriously, and the latter causes the whole transaction to revert instead of silently deleting escrow accounting).

### Proof of Concept
1. Deploy a TRC20/ERC20-like token whose `transfer` function returns `false` (instead of reverting) when, e.g., the contract's own balance is insufficient, or when the recipient is blacklisted — a common but non-compliant implementation pattern.
2. A user places an order via `placeOrder` using this token as an input; tokens are correctly pulled in via `safeTransferFrom`, and `_orders[commitment][token]` is credited. [6](#0-5) 
3. A solver fills the order and Hyperbridge later delivers a `RedeemEscrow` request; `onAccept` routes into `withdraw(body, false)`. [7](#0-6) 
4. Inside `withdraw`, the token's `transfer` call executes without reverting but returns `false` (e.g., beneficiary got blacklisted by the token issuer after order placement, or the contract lacks sufficient balance due to a prior similar bug). `success` is `true` (the call executed), so `TransferFailed` is never triggered.
5. `_orders[body.commitment][token] -= amount;` proceeds, permanently zeroing/reducing the escrow record even though the beneficiary never received the tokens. The tokens are now stranded in the `IntentGatewayV2` contract with no code path to recover them for that beneficiary.
