The webhook HMAC binding gap is the strongest analog found in this gem.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-identity spoofing on legitimate webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC of the raw request body, but the shop identity that the handler ultimately acts on is read from an HTTP header that is never included in that signature. The binding the gem should enforce — `HMAC-verified bytes == shop-attributed bytes` — does not hold, because `shop` is derived from a header the signature does not cover.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately forwards the (unauthenticated) `request.shop` value to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature over `to_signable_string` (the body) using the app's single `api_secret_key`/`old_api_secret_key` — the same secret is shared by every shop that installed the app, so a valid signature only proves "some install of this app produced this body," not "this body belongs to shop X": [4](#0-3) 

Because the shop field is "acted on but not covered by the HMAC," any party who receives one legitimate webhook for their own (legitimately installed) shop can capture the valid `(body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), and `WebhookMetadata.shop` is set to the attacker-chosen victim domain: [5](#0-4) 

This breaks the identity binding the audited Go report also flagged as the root-cause pattern (a value trusted/acted upon that isn't covered by the authenticator that's supposed to bind it).

### Impact Explanation
This is a cross-tenant integrity/confidentiality issue: an attacker who merely installs the app on their own store (an ordinary, unprivileged action requiring no stolen credentials) can cause the host application, which relies on this gem's `WebhookMetadata#shop` as the trusted shop identity, to process, store, or act on data under an arbitrary victim shop's identity. Depending on the handler, this can corrupt another merchant's data, trigger redact/compliance actions against the wrong shop, or desynchronize webhook-driven state across tenants — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any legitimate app installer on any shop can obtain a valid `(body, hmac)` pair for one of the app's webhook topics simply by having the topic delivered to their own store (no secret theft required), then replay it against the shared webhook endpoint with a modified shop header. No privileged access, TLS interception, or knowledge of `api_secret_key` is needed — only ordinary use of the app by any unprivileged internet user who can install it.

### Recommendation
Bind the shop identity into the authenticated material: include the `shop` (and ideally `topic`/`webhook_id`) in `to_signable_string`, or independently verify that the `shopify-shop-domain` header matches a shop for which the caller is separately authenticated (e.g., cross-check against the shop bound to the access token/session used to register the webhook, or maintain a per-shop webhook secret/allow-list). At minimum, document that host applications must not trust `WebhookMetadata#shop` without an independent authorization check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, causing Shopify to legitimately deliver a webhook (e.g., `orders/create`) with headers `x-shopify-hmac-sha256: H` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`.
2. Attacker replays an HTTP POST to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and successfully matches `H` (line `hmac_validator.rb:28-31`).
4. `process` proceeds to invoke `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` (`registry.rb:198-199`), even though the body content actually originated from `attacker-shop.myshopify.com`.
