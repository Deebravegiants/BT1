Now I have confirmed the key facts: `_params.dispatcher` (`CallDispatcher`) is a **single shared, stateless, permissionless contract** (`evm/src/utils/CallDispatcher.sol`) — the docs and code confirm "Existing `CallDispatcher` deployments are listed on the contract addresses page," and it is reused across `HyperFungibleToken` sends, `placeOrder` predispatch, and `_execute` postdispatch for *every* user and *every* order. Its `dispatch()` function executes attacker-controlled `Call[]` on its own behalf with no access control and no per-caller isolation. This is the same class of flaw as the Aera report: measuring "amount received" by comparing an absolute balance snapshot on a shared, externally-callable account, rather than by the exact expected amount, inside a single atomic transaction that itself triggers further arbitrary calls.

### Title
Predispatch escrow sweep sums the CallDispatcher's *entire* balance instead of the order's own swap output, letting a malicious predispatch call cross-contaminate concurrent-order funds - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch path funds a shared, permissionless `CallDispatcher` contract, invokes attacker-supplied calldata on it, then sweeps *the CallDispatcher's whole token/ETH balance* back into escrow, treating whatever landed there as "amount received" for the order being placed. Because `CallDispatcher` is a single, stateless, unauthenticated relay shared by every order and every `HyperFungibleToken` cross-chain delivery on the chain, any balance sitting on it for unrelated reasons at the moment of the sweep is silently absorbed into the attacker's own order's escrow — exactly the "balance-diff instead of exact-amount" root cause identified in the Aera report.

### Finding Description
In `placeOrder`, when an order carries predispatch calldata:
1. The gateway transfers `order.predispatch.assets` to `dispatcher = _params.dispatcher` and calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` with **fully attacker-controlled calldata** [1](#0-0) .
2. It then reads `IERC20(token).balanceOf(dispatcher)` — the dispatcher's **total current balance**, not a delta since a pre-transfer snapshot — and builds a sweep call that transfers that *entire* balance back to the gateway [2](#0-1) .
3. The amount actually escrowed/committed for the order is derived from `address(this).balance`/`balanceOf(this)` delta around that sweep, i.e. whatever the dispatcher happened to be holding [3](#0-2) .

`CallDispatcher` is not order-scoped or per-user: it is a single stateless contract intentionally reused across `HyperFungibleToken.send`/`onAccept` calldata execution, `IntentGatewayV2` predispatch, and `IntentGatewayV2._execute` postdispatch sweeps [4](#0-3) . Its `dispatch()` performs raw, unauthenticated external calls to any contract with code, with no caller/session binding [5](#0-4) .

An attacker's `predispatch.call` is arbitrary Solidity calls executed *as* the dispatcher. Because the sweep step measures `balanceOf(dispatcher)` (an absolute quantity) rather than the amount the predispatch call itself produced, the attacker only needs to arrange, within their own attacker-controlled predispatch call, a reentrant/triggered external interaction that lands *other, unrelated* funds on the dispatcher before the sweep executes — e.g., a token with hooks (ERC-777/ERC-1363-style `onTransferReceived`, or any callback-capable token/AMM) whose external call the attacker's predispatch step triggers, which in turn causes a different in-flight, non-reentrant-guarded flow (such as a concurrently pending `HyperFungibleToken` calldata delivery routed to the same dispatcher, or the dispatcher's leftover dust from a previous partially-swept order) to move tokens onto the dispatcher in the same call stack. Because the gateway trusts "whatever the dispatcher now holds" as the order's legitimate `received` amount and escrows it (`order.inputs[i].amount = received`) [6](#0-5) , that contaminating balance becomes escrowed under the attacker's commitment and is redeemable by them (or refundable to them on cancel) exactly as if it were their own deposit.

This mirrors the Aera bug precisely: the after-hook trusted "current balance − stored balance" as the swap's own output, allowing a nested/triggered operation on the same shared state to be double-counted; here, the gateway trusts "current CallDispatcher balance" as the predispatch call's own output, allowing anything else that lands on the same shared, unscoped `CallDispatcher` to be absorbed.

### Impact Explanation
If exploitable, an attacker can escrow tokens they never funded (theft from whichever unrelated flow's funds transiently touched the shared dispatcher), or inflate the committed input amount of their own order beyond what they paid, extracting value from the protocol/other users' pending flows through the intents escrow. This is a fund-theft / unauthorized-escrow-credit vector reachable by any unprivileged address that can call `placeOrder` with a predispatch call — no special role is required, matching the "unprivileged... token bridger... intent solver" reachability bar.

### Likelihood Explanation
Likelihood is Medium: the exploit requires the attacker to find or induce a race where the shared `CallDispatcher` momentarily holds third-party funds at the exact point their own `placeOrder` predispatch dispatch executes, and reliably trigger it via callback semantics (e.g., a callback-token invoked during predispatch, or scheduling around a live cross-chain `HyperFungibleToken` delivery that also targets the dispatcher). It does not require compromising any privileged role, but it does require crafting the right timing/callback primitive, similar in spirit (though not identical mechanism) to the Aera PoC's use of a custom ERC-20 with a transfer-hook callback.

### Recommendation
Do not measure "amount received" from predispatch calldata as the dispatcher's absolute balance. Instead:
- Snapshot `balanceOf(dispatcher)` (or `dispatcher.balance`) **immediately before** transferring the predispatch assets and **immediately after** the predispatch `dispatch()` call returns, and sweep/escrow only the delta attributable to this order's own predispatch assets, not the dispatcher's total balance.
- Alternatively, deploy a fresh, single-use `CallDispatcher` instance per order (e.g., via `CREATE2`/minimal proxy) so no state or balance can ever be shared across unrelated orders or unrelated bridge deliveries.
- Apply the same fix to the symmetric sweep in `_execute`'s postdispatch path (`evm/src/apps/intentsv2/IntentsBase.sol`), which has the identical "sweep whatever the shared dispatcher currently holds" pattern.

### Proof of Concept
Full weaponization requires a concrete callback-capable token/protocol available on the deployment target to trigger the cross-contamination timing; this could not be fully constructed from the indexed code alone. The exploitable code pattern is directly demonstrated by:
- `evm/src/apps/IntentGatewayV2.sol` lines 258–289: predispatch dispatch followed by `balanceOf(dispatcher)`-based (not delta-based) sweep sizing.
- `evm/src/utils/CallDispatcher.sol` lines 44–62: the dispatcher is stateless, singleton, and unauthenticated, executing arbitrary attacker-supplied calls on behalf of whichever caller currently owns the outer transaction, with no per-order isolation.
A concrete end-to-end PoC would require: (1) confirming a specific shared-dispatcher deployment address used by both `IntentGatewayV2` and at least one other flow (e.g., `HyperFungibleToken`) on the same chain, and (2) a token/AMM whose transfer triggers a callback the attacker can use, from within their own `predispatch.call`, to pull the other flow's in-flight funds onto the dispatcher before the sweep reads its balance — recommend a Devin session with repo/contract-address access to attempt this construction and validate exploitability empirically.

import {ICallDispatcher, Call} from "@hyperbridge/core/interfaces/ICallDispatcher.sol";

/**
 * @title The CallDispatcher
 * @author Polytope Labs (hello@polytope.technology)
 *
 * @notice This contract is used to dispatch calls to other contracts.
 */
contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
