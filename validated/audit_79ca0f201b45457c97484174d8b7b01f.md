### Title
Webhook `shop` (and `topic`/`webhook_id`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator` checks authenticates the *body bytes* only, never the `shop-domain`, `topic`, or `webhook-id` headers that `Registry.process` later trusts and hands to the app's handler as the shop identity for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as simply `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read directly from the (unauthenticated) `shopify-shop-domain` header with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then forwards the header-derived `shop` straight into `WebhookMetadata`, which is passed to the app's handler as the authenticated tenant identity: [3](#0-2) 

The HMAC is computed using `Context.api_secret_key`, which is the app's single global secret shared across *all* shops that installed the app - it is not shop-specific: [4](#0-3) 

The equality that is supposed to hold is: `shop that produced the HMAC-covered bytes == shop attributed to the event by the handler`. Because `shop` is a header field never included in `to_signable_string`, this equality is never enforced — the gem authenticates "these are genuine Shopify-signed bytes" but not "these bytes are about shop X." The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," implying it is trustworthy/verified: [5](#0-4) [6](#0-5)  — but nothing in the gem's own verification logic actually binds the shop header to the signature.

### Impact Explanation
Any actor who can obtain one legitimate Shopify-signed webhook body+HMAC pair for *any* shop that shares the app's secret (e.g., by simply installing the app on their own store and triggering an event, which requires no special privilege) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`/`X-Shopify-Topic`) headers for a victim shop. `HmacValidator.validate` will still pass because it only checks the body bytes, and the handler will receive `WebhookMetadata` claiming the payload belongs to the victim shop. This is a cross-tenant identity-confusion vulnerability: an app that keys any tenant-scoped action (data storage, redaction processing, deduplication via `webhook_id`, audit logs, billing events, etc.) off `data.shop` can be made to apply attacker-controlled data/events under another merchant's identity.

### Likelihood Explanation
The prerequisite (obtaining one valid signed webhook for a shop using the same app) is trivially satisfiable by any user who installs the target app on their own development/test store — no leaked secrets, no privileged access, and no interaction with the victim is required. The forged header injection is a simple HTTP replay.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signable string within `ShopifyAPI::Webhooks::Request#to_signable_string` (or otherwise cryptographically bind them, e.g., by only trusting `shop` as returned from Shopify's registered domain for the session/shop that the app independently already tracks), so that any tampering with those headers invalidates the signature.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers `orders/create` and captures the resulting webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`, and `secret` is the same for every shop of this app).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` computes `HMAC(secret, B)` and compares to `H` — it matches, so `Errors::InvalidWebhookError` is not raised: [7](#0-6) 
4. `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and passed to the app's handler as if it were a genuine event for the victim shop.
