### Title
Webhook Shop Domain Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (tenant identity) delivered to the application's webhook handler is taken from an HTTP header that is never included in the signed material. This breaks the identity binding `hmac-verified bytes == bytes used to identify the tenant`, letting anyone who can obtain one valid `(body, hmac)` pair (e.g., from a legitimate webhook delivered to their own shop) replay it against the app's webhook endpoint with an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value, causing the host application to process the payload as belonging to a different merchant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors, by contrast, are read straight from attacker-controllable headers with no cryptographic binding: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then forwards the unauthenticated `request.shop` value straight to the application's registered handler as the tenant identifier: [4](#0-3) 

`HmacValidator.validate` in turn calls `validate_signature`, which computes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header — it never incorporates the shop header into the signed/verified bytes: [5](#0-4) 

Because the `Context.api_secret_key` used to compute the HMAC is a single, app-wide secret shared across every merchant using the app (not a per-shop secret), any body+HMAC pair that is valid for one shop's webhook is also a valid HMAC for the *same body* claimed to originate from any other shop. An unprivileged user needs no special privilege beyond installing the app on their own store (a normal, self-service action) to obtain a legitimately signed `(raw_body, hmac)` pair from Shopify's real webhook delivery. They can then submit an HTTP request directly to the app's public webhook endpoint, keeping the captured `raw_body` and `hmac` header (so `HmacValidator.validate` still succeeds), but substituting the `shopify-shop-domain` header with a victim shop's domain. `WebhookMetadata.shop` — the value most host applications key their persistence/session lookups and business logic on — will then equal the victim shop's domain even though the signed body has nothing to do with that shop.

This is exactly the identity-binding gap called out in the report's bug class: a field (`shop`) is acted upon by downstream logic but is not covered by the HMAC that is supposed to authenticate the whole webhook request.

### Impact Explanation
This enables cross-tenant confusion: an attacker-controlled shop can cause the merchant application to attribute arbitrary (attacker-chosen) webhook body content to a different, victim shop. Depending on what the host app does in its webhook handler (e.g., updating order/inventory records, billing state, or session/tenant-scoped data keyed by `shop`), this can lead to cross-tenant data corruption or logic confusion — meeting the "cross-tenant access" class of Critical impact defined by the scope, since the authenticated identity (the shop the body's HMAC actually vouches for, i.e., none/any shop under the same api_secret_key) and the identity acted upon (the shop header value trusted by the handler) diverge.

### Likelihood Explanation
Likelihood is elevated by the facts that: (1) the webhook endpoint is a public HTTP endpoint reachable by any internet user, (2) obtaining one valid `(raw_body, hmac)` pair only requires installing the app on the attacker's own store and receiving one real webhook — no elevated privilege or leaked secret needed, and (3) the api_secret_key/HMAC is shared across every shop, so the captured pair is universally replayable with a swapped shop header. This is a purely mechanical vulnerability inherent to this gem's `Webhooks::Request`/`Registry` implementation.

### Recommendation
Bind the shop identity into the verified material, or otherwise ensure the shop used for business logic is only trusted for the shop that is cryptographically bound to the request. Options:
- Include the `shop-domain` header (and other identity-bearing headers such as `topic`/`webhook_id`) in the HMAC signable string, so `HmacValidator.validate` fails if the shop header is altered after signing.
- Alternatively, require host applications to independently corroborate `request.shop` against a known, previously-registered shop/session record before trusting it (and document this loudly), rather than presenting it as an authenticated field of `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any real webhook event, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent (this HMAC is computed with the app-wide `api_secret_key`, shared across all shops).
2. Replay an HTTP POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC: [6](#0-5) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host application processes attacker-controlled body content under the victim's tenant identity.
