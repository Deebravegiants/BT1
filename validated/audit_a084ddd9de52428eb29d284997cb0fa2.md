### Title
Missing WebAuthn `client_data.type` validation allows cross-ceremony signature replay for transaction authorization - (File: `types/src/transaction/webauthn.rs`)

### Summary
`PartialAuthenticatorAssertionResponse::verify` and `verify_arbitrary_msg` deserialize `client_data_json` into `CollectedClientData` and check only the `challenge` field against the expected transaction digest before running signature verification over `authenticator_data || SHA-256(client_data_json)`. The `ty` field of `CollectedClientData` (which per the WebAuthn spec must be `webauthn.get` for an assertion, distinguishing it from `webauthn.create` registration ceremonies and other ceremony types such as Secure Payment Confirmation's `payment`, whose test fixtures — `SPC_ATTESTATION_OBJECT` — are present in this same file) is never inspected. [1](#0-0) [2](#0-1) 

### Finding Description
The WebAuthn signature scheme used here signs over `authenticator_data || SHA-256(client_data_json)` for both assertion (`webauthn.get`) and, per the WebAuthn attestation format, registration/self-attestation ceremonies — the byte structure that is actually signed is essentially identical, differing primarily in the `type` string embedded in `client_data_json`. The spec-mandated defense against this is for the relying party to explicitly assert `clientDataJSON.type == "webauthn.get"` before accepting a response as a valid authentication assertion. This codebase never performs that check: `collected_client_data.ty` is parsed but discarded. [3](#0-2) 
As a result, any signed WebAuthn payload from the same key pair whose `challenge` happens to equal `SHA3-256(raw_txn)` — regardless of whether it was produced for a registration ceremony, a login ceremony on an unrelated site, or a Secure Payment Confirmation — will be accepted as valid Aptos transaction authorization when routed through `AnySignature::WebAuthn` inside `SingleKeyAuthenticator`/`AccountAuthenticator`, as exercised end-to-end (including real API transaction submission) in `api/src/tests/webauthn_secp256r1_ecdsa.rs`. [4](#0-3) 

### Impact Explanation
This breaks the custody-relevant binding that only an actual "please authorize this Aptos transaction" ceremony should be able to move funds/authority from an account keyed to a WebAuthn/passkey credential. A malicious or compromised website that a victim has registered a passkey with (or that requests a payment-confirmation-style assertion) can set the WebAuthn `challenge` to `SHA3-256(attacker_chosen_raw_txn)` for its own ceremony (of any `type`), capture the resulting valid signature, and replay it against the Aptos network as if it were a normal transaction signature, moving assets out of the victim's account without the victim ever intending to authorize an Aptos transaction.

### Likelihood Explanation
Exploitability depends on an attacker-controlled or attacker-influenced website being able to set the WebAuthn `challenge` value shown to the victim's authenticator to an attacker-chosen Aptos transaction digest, and on the victim approving that ceremony believing it to be unrelated (e.g., a login or payment confirmation) to an on-chain transfer. This requires social-engineering/phishing setup but no protocol-level secret; the cryptographic check that should prevent it (`ty == webauthn.get`) is simply absent from the code.

### Recommendation
In `PartialAuthenticatorAssertionResponse::verify` and `verify_arbitrary_msg`, after deserializing `CollectedClientData`, explicitly assert `collected_client_data.ty == ClientDataType::Get` (i.e., `webauthn.get`) and reject otherwise, matching WebAuthn §7.2 step 11 relying-party verification requirements.

### Proof of Concept
1. Construct a `CollectedClientData` with `challenge = base64url(SHA3-256(target_raw_txn))` but `ty` set to `ClientDataType::Create` (or any non-`Get` value) instead of `webauthn.get`.
2. Serialize to `client_data_json`, sign `authenticator_data || SHA-256(client_data_json)` with the victim's registered Secp256r1 key (as would occur in a registration/self-attestation or unrelated ceremony).
3. Build `PartialAuthenticatorAssertionResponse::new(signature, authenticator_data, client_data_json)` and call `paar.verify(&target_raw_txn, &public_key)`.
4. Observe `verify` returns `Ok(())` even though `ty != "webauthn.get"`, as neither `verify` nor `verify_arbitrary_msg` check the `ty` field. [5](#0-4)

    fn sign_webauthn_transaction(
        raw_txn: &RawTransaction,
        collected_client_data: CollectedClientData,
        authenticator_data: &[u8],
        private_key: &Secp256r1EcdsaPrivateKey,
    ) -> SignedTransaction {
        let public_key = Secp256r1EcdsaPublicKey::from(private_key);

        let client_data_json = serde_json::to_vec(&collected_client_data).unwrap();
        let client_data_hash = sha256(client_data_json.as_slice());

        let signature_material = [authenticator_data, &client_data_hash].concat();
        let signature = private_key.sign_arbitrary_message(signature_material.as_slice());
        let assertion_signature = AssertionSignature::Secp256r1Ecdsa { signature };

        let partial_authenticator_assertion_response = PartialAuthenticatorAssertionResponse::new(
            assertion_signature,
            authenticator_data.to_vec(),
            client_data_json,
        );
        let public_key = AnyPublicKey::Secp256r1Ecdsa { public_key };
        let signature = AnySignature::WebAuthn {
            signature: partial_authenticator_assertion_response,
        };
        let authenticator = SingleKeyAuthenticator::new(public_key, signature);
        let account_authenticator = AccountAuthenticator::SingleKey { authenticator };
        let txn_authenticator = TransactionAuthenticator::SingleSender {
            sender: account_authenticator,
        };
        SignedTransaction::new_signed_transaction(raw_txn.clone(), txn_authenticator)
    }
