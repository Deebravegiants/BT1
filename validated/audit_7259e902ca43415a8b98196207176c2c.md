### Title
Balance‑aliasing ("double‑entry token") lets an attacker mint shielded value against a single real balance delta counted twice across two `erc20TokenAddresses` entries - (File: `contracts/Hinkal.sol` / `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`Hinkal.transact` snapshots per‑token balances with `getBalancesForArray`, which calls `balanceOf`/ETH‑balance independently for every entry of the attacker‑supplied `erc20TokenAddresses` array, and then checks, index by index, that `balanceDif == amountChanges[i] + utxoAmount(i)`. Nothing in Solidity or in the circuit verifies that these addresses correspond to economically distinct assets — only that their raw numeric values differ. An attacker can deploy a second contract whose `balanceOf` mirrors the real output token's balance for the vault (a "double‑entry" alias) and add it as an extra token index in the same `transact` call; the single real balance increase produced by the LiFi swap then satisfies the equality check twice, once for the genuine output UTXO and once for extra shielded output tied to the alias, minting shielded value the vault never received.

### Finding Description
Equality claimed to hold, per token index `i`:
`balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` [1](#0-0) 

The invariant the protocol needs is: net real tokens entering Hinkal == `sum(amountChanges) + sum(on-chain UTXO amounts minted)` summed **once per real asset**. `getBalancesForArray` computes `oldBalances`/`newBalances` per index independently via `balanceOf`: [2](#0-1) 

The only uniqueness guard on `erc20TokenAddresses` is the circuit's `distinctErc20AddressChecks`, which forces pairwise `IsEqual` on the raw numeric address values to be `0` — i.e. it only forbids literally identical addresses, it cannot and does not check whether two *different* contract addresses share or mirror the same underlying balance: [3](#0-2) 

`dimensionsCheck`/`checkOnchainCreation` in `HinkalHelper` likewise only validate array lengths and onChainCreation/amountChanges relationships, never that tokens are economically independent: [4](#0-3) 

Attack construction:
1. Attacker deploys `AliasToken` whose `balanceOf(hinkal)` is defined to equal `RealOutputToken.balanceOf(hinkal)` (e.g., it reads/derives from the same storage or simply forwards the read), while its `transfer`/`transferFrom` need not move anything for this to work, since `_externalTransact` never pulls tokens in for a positive `deltaAmountChanges[i]` — it only pushes tokens **out** for negative deltas: [5](#0-4) 
2. Attacker crafts `circomData` with `dimensions.tokenNumber = 3`: index 0 = real input token, index 1 = real output token, index 2 = `AliasToken`. `ExternalActionSwap.swap` only ever touches indices 0 and 1 by hard‑coded position: [6](#0-5) 
It performs the LiFi swap and transfers `amountToSendToHinkal` of the real output token into Hinkal, producing exactly one `utxoSet` entry tagged with the real output token address.
3. Because `AliasToken.balanceOf(hinkal)` mirrors the real output token's balance, `Hinkal.transact`'s loop computes, for index 2, `balanceDif == amountToSendToHinkal` even though no independent asset named `AliasToken` was ever transferred, and `utxoSet` contains no entry for it (`utxoAmount == 0`).
4. The attacker sets `amountChanges[2] = amountToSendToHinkal` (an off-chain/circuit-only positive change) so the on‑chain equality `balanceDif == amountChanges[2] + 0` holds trivially, since it is literally the same real delta already used to satisfy index 1.
5. On the circuit side, this positive `amountChanges[2]` with `inTotal = 0` for token index 2 forces `outTotal = amountChanges[2]`, i.e. the attacker mints off‑chain shielded output commitments worth `amountToSendToHinkal` for the fictitious `AliasToken`, backed by nothing — the real value was already fully accounted for by the genuine output‑token UTXO.

Net result: the vault received `amountToSendToHinkal` of real tokens once, but the attacker walks away having created shielded value for `2 * amountToSendToHinkal` (real output UTXO + alias shielded UTXOs). None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, the slippage `require`, or `distinctErc20AddressChecks` detect this because they all operate purely on the numeric address values and independent `balanceOf` snapshots — none of them can express "these two addresses are the same underlying asset."

The `slippageValues[i]` negative detail from the prompt is not required to make the double-count itself succeed (the floor `balanceDif >= slippageValues[i]` is trivially satisfied by a positive mirrored delta); a negative slippage value only widens the attacker's room to additionally siphon real value out of the vault on the genuine token leg while still passing the floor check, compounding the loss.

### Impact Explanation
This mints shielded value without any matching deposit, i.e. protocol insolvency: the attacker can withdraw/spend shielded UTXOs whose face value exceeds what the vault actually holds. This matches the Critical category "minting shielded value without backing." It is repeatable per swap transaction and scales with the swap size and the number of alias token slots the attacker chooses to add (`tokenNumber` is attacker-controlled), and costs only gas plus deployment of a trivial mirroring contract.

### Likelihood Explanation
Preconditions are all within the attacker's stated control: they can deploy arbitrary token contracts, craft `CircomData`/`Dimensions` fields (including `tokenNumber`, `erc20TokenAddresses`, `amountChanges`, `slippageValues`), and generate their own valid proof for their own UTXOs (the circuit constraints on `amountChanges`/`outTotal` are satisfiable by the attacker for tokens they control off-chain). No privileged role, relay, or victim funds are needed — the attacker only needs one legitimate swap through the LiFi external action to create the real balance delta that gets double counted. This is realistically exploitable with a Foundry fork test deploying a simple `balanceOf`-mirroring token and one call to `Hinkal.transact`.

### Recommendation
Do not rely solely on raw address inequality for token accounting. Either (a) require an authoritative registry/allowlist of ERC20 tokens usable in `erc20TokenAddresses` (so attacker-deployed alias contracts cannot be used), or (b) restructure the balance-diff accounting so that `utxoAmount`/`amountChanges` for indices not actively touched by the external action's `utxoSet` must have `balanceDif == 0`, or (c) have `getBalancesForArray` fail closed / re-derive balances from a canonical source per unique underlying asset rather than trusting each attacker-supplied address's `balanceOf` independently. At minimum, the external action (`ExternalActionSwap.swap`) should assert that it returns UTXOs (or zero balance deltas) for every `erc20TokenAddresses` index it does not explicitly move funds for, rather than leaving the generic loop in `Hinkal.transact` to accept any `amountChanges`/`utxoAmount` combination that happens to match an incidental `balanceOf` read.

### Proof of Concept
1. Deploy `RealOutputToken` (any standard ERC20 used by the LiFi router as swap output).
2. Deploy `AliasToken` with `balanceOf(a) == RealOutputToken.balanceOf(a)` for all `a`.
3. Register the swap external action; fund an EOA with `InputToken`, generate a valid Hinkal deposit UTXO for it.
4. Craft `CircomData` with `dimensions.tokenNumber = 3`, `erc20TokenAddresses = [InputToken, RealOutputToken, AliasToken]`, `amountChanges = [-inputAmount, 0, swappedAmount]`, `onChainCreation = [false,false,false]`, `slippageValues` set to permissive/negative values, and off-chain outputs that mint one UTXO of `swappedAmount` for `RealOutputToken` (matching the real `utxoSet`) and one UTXO of `swappedAmount` for `AliasToken` (backed by nothing).
5. Generate the corresponding proof locally (attacker controls all private inputs for their own UTXOs) and call `Hinkal.transact`.
6. Assert: `RealOutputToken.balanceOf(hinkal)` increased by exactly `swappedAmount` (vault received value once), while the shielded tree now contains new commitments totaling `2 * swappedAmount` in claimed value (`RealOutputToken` UTXO + `AliasToken` UTXO) — i.e. `vault balance delta (swappedAmount) < credited UTXO value (2 * swappedAmount)`, confirming shielded value was minted without backing.

    function swap(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) internal returns (UTXO[] memory utxoSet) {
        address inputToken = circomData.erc20TokenAddresses[0];
        uint256 inputAmount = uint256(-deltaAmounts[0]);

        if (inputToken == circomData.feeStructure.feeToken) {
            inputAmount -= circomData.feeStructure.flatFee;
        }

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );

        uint256 relayFee = circomData.feeStructure.flatFee;

        uint256 hinkalFee = hinkalHelper.calculateRelayFee(
            swappedAmount,
            0,
            circomData.feeStructure.variableRate
        );

        if (circomData.feeStructure.feeToken == outputToken) {
            sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
        } else {
            sendToRelay(
                circomData.relay,
                relayFee,
                circomData.feeStructure.feeToken
            );
            sendToRelay(circomData.relay, hinkalFee, outputToken);
        }

        uint256 totalFee = hinkalFee +
            (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
        uint256 amountToSendToHinkal = swappedAmount - totalFee;

        transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);

        utxoSet = new UTXO[](1);
        utxoSet[0] = UTXO({
            amount: amountToSendToHinkal,
            erc20Address: outputToken,
            stealthAddressStructure: circomData.stealthAddressStructure,
            timeStamp: block.timestamp
        });
    }
