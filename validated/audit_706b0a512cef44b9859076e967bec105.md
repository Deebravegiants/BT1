### Title
Stored `account.owner` used for spend authorization instead of live NFT owner lets a prior holder keep borrowing and withdrawing after transferring the position NFT - ([File: contracts/controller/src/account.rs])

### Summary
Every value-moving controller entrypoint authorizes the caller against the `owner` field stored inside the persisted `Account` struct, which is written once at account creation and never restamped from the position NFT. After the NFT (the real ownership record) is transferred, the *previous* owner still satisfies `require_owner_or_delegate`, so they can keep borrowing and withdrawing against collateral they no longer own.

### Finding Description
`create_account` stores `owner` inside the `Account` struct at mint time (`account.rs:64-70`), and `get_account` / `get_account_borrow_only` load that stored struct without re-reading NFT ownership. `is_owner_or_delegate` returns `true` whenever `caller == *owner` (`account.rs:120-127`), and `require_owner_or_delegate` gates `process_borrow` (`debt.rs:42-43`) and `process_withdraw` (`supply.rs:149-150`) on that stored value.

The protocol itself treats the NFT as the source of truth: `require_account_owner` calls `storage::account_owner` (NFT `owner_of`) for `renew_account`/`add_delegate`/`remove_delegate` (`account.rs:143-148`), and the permissionless declarations state that NFT `transfer` "moves the whole account" (`scripts/permissionless_entrypoints.txt:111`). Yet the spend path never consults the NFT owner — it only checks the stale stored field. Both `process_borrow` and `process_withdraw` also take an arbitrary `to`/`recipient`, bounded only by `require_external_recipient` (external, non-protocol address), so the ex-owner can direct proceeds to a fresh address they control.

### Impact Explanation
A user who sells or transfers their position NFT — e.g., an account with collateral — does not actually relinquish control. The transferor can immediately `borrow` to themselves up to the solvency limit and `withdraw` all withdrawable collateral, leaving the NFT buyer holding debt against drained collateral. This is theft of user funds perpetrated by a single unprivileged address (the ex-owner) using the in-scope entrypoints `borrow` and `withdraw`.

### Likelihood Explanation
Requires only a victim willing to buy/receive a position NFT; NFT transfers are an advertised, permissionless feature (`position-nft::transfer`). The attacker needs no privileges, no oracle manipulation, and no cooperation — `caller.require_auth()` is their own signature. The cost is the value of the NFT they sell, which they may recover from the buyer anyway. Medium likelihood: it depends on the secondary market for position NFTs existing, but the contract actively exposes and documents transfers.

Uncertainty note: I could not fully confirm within this review whether any helper re-stamps `account.owner` from the NFT on load in `storage::get_account`; if it does, this finding is void. Nothing in `account.rs`, `debt.rs`, or `supply.rs` shows such a refresh, and the existence of a separate NFT-owner check (`require_account_owner`) used only for renewal/delegate paths indicates the two owner sources are known to diverge.

### Recommendation
In `require_owner_or_delegate` (or in `storage::get_account`), resolve the owner via `storage::account_owner` (live NFT `owner_of`) rather than the `Account.owner` field set at mint, or update `Account.owner` on NFT transfer via a controller-mediated hook. Ensure delegate lookups also key off the live owner so stale grants from a previous owner cannot remain active.

### Proof of Concept
1. Alice supplies USDC collateral via `controller::supply`, creating `account_id` with `Account.owner = Alice`.
2. Alice calls `position-nft::transfer(from=Alice, to=Bob, token_id=account_id)`; Bob now owns the NFT and `storage::account_owner` returns Bob.
3. Alice calls `controller::borrow(caller=Alice, account_id, [(ETH, X)], to=Some(Eve))`. `require_owner_or_delegate` compares `caller` to stored `Account.owner` (still Alice) and passes; ETH is drawn to Eve against Bob's collateral, and `enforce_post_pool_solvency` passes because collateral remains.
4. Alice calls `controller::withdraw(caller=Alice, account_id, [(USDC, 0 /*all*/)], to=Some(Eve))` up to the solvency floor; `require_owner_or_delegate` again passes on the stale owner.
5. Bob's account is left with residual collateral backing Alice-created debt, which liquidators can then seize; Alice and Eve captured the borrowed ETH plus withdrawn USDC.
