This confirms the asymmetry: for the OAuth `AuthQuery`, `shop` is explicitly included in the signed payload (`to_signable_string`, [1](#0-0) ), but for webhooks, `Request#to_signable_string` returns only `@raw_body`, excluding `shop`, `topic`, and `webhook_id`, all of which are read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC of the body and then trusts `request.shop`/`request.topic` to build `WebhookMetadata`, which is handed to the app's per-tenant handler [3](#0-2) [4](#0-3) .

### Title
Webhook HMAC only signs the request body while `shop`/`topic`/`webhook_id` used for tenant routing are trusted from unauthenticated headers, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` by defining `to_signable_string` as the raw HTTP body only [5](#0-4) , while the `shop`, `topic`, and `webhook_id` fields that `Registry.process` uses to build the `WebhookMetadata` passed to the app-supplied handler are read verbatim from HTTP headers that are never part of the signed content [6](#0-5) . `HmacValidator.validate` only proves the body bytes match a valid signature for *some* HMAC secret held by the app; it proves nothing about which shop or topic that signature was intended for [7](#0-6) . This is a direct instance of "bytes verified versus bytes parsed" — the equality that should hold (`shop` used to route/act on the event == `shop` cryptographically bound to the verified signature) is broken.

### Finding Description
`Registry.process` performs authentication solely via `Utils::HmacValidator.validate(request)`, and on success trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the `WebhookMetadata` struct delivered to the host app's handler [3](#0-2) . None of these fields are part of the HMAC-signed content — only the raw JSON body is signed [5](#0-4) .

Because a single app installation shares one `api_secret_key` across every shop that installs it, any shop owner who installs the app is an "unprivileged internet user" relative to every other tenant, yet can legitimately receive HMAC-signed webhook deliveries from Shopify for their own store. Since the signature covers only the body bytes and not the shop/topic metadata, that same body+HMAC pair remains valid for HmacValidator regardless of which `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` headers accompany it. An attacker can capture a genuine signed webhook delivered to their own shop and replay it directly to the app's public webhook endpoint with the `shop`, `topic`, or `webhook_id` headers rewritten to target a different, victim tenant — the signature check still passes, and the forged metadata is handed to the handler as if authentic.

### Impact Explanation
This breaks the tenant boundary: the handler cannot distinguish an authentic webhook about shop A from a replayed/relabeled one claiming to be about shop B, meeting the Critical bar of cross-tenant access, since the identity ("which shop/topic this event is about") that downstream tenant-scoped logic depends on is not cryptographically bound to the proof of authenticity.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged onboarding action for any public/embedded app) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint — no secrets, tokens, or TLS interception are required, since the attacker supplies their own genuinely-signed body/HMAC pair captured from their own legitimate webhook traffic.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signable content for webhook requests (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed payload), or otherwise cryptographically bind them so that `HmacValidator.validate` fails if any of these routing headers are altered independently of the body.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com` and register/receive any webhook (e.g., `orders/create`) — Shopify delivers a POST with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, a JSON body, and `x-shopify-hmac-sha256` computed over that body with the app's shared `api_secret_key`.
2. Capture the raw body and the `x-shopify-hmac-sha256` value from step 1.
3. Send a new POST to the same public webhook endpoint with the identical body and HMAC header, but replace `x-shopify-shop-domain` with `victim.myshopify.com` (and/or `x-shopify-topic`/`x-shopify-webhook-id` with different values).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC [8](#0-7) ; the handler then receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker's crafted event as if it genuinely originated from the victim tenant.
