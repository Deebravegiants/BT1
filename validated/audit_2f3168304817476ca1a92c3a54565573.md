### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values purely from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). This breaks the identity binding: `hmac(secret, body) == valid` should imply `shop-domain header == true origin shop`, but the gem lets `shop` and `topic` be attacker-controlled while only the body is authenticated.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the supplied `hmac`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `hmac`, `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers with no cryptographic binding to each other: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body and then hands `request.shop` (and `request.topic`) directly to the app's webhook handler as trusted tenant identity: [3](#0-2) 

Because Shopify's webhook HMAC (per Shopify's documented webhook verification scheme, which this gem implements) is computed only over the request body/secret, and the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers are not part of that signed material, a party who possesses *any* validly-signed webhook body+HMAC pair (e.g., an unprivileged attacker who installs the app on their own free/dev store, subscribes to a webhook topic, and captures the delivered body and its valid HMAC) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header value with a victim shop's domain. `HmacValidator.validate` will still return `true` (body and HMAC are unmodified and genuinely signed by Shopify with the app's secret), yet `Request#shop` will report the victim's domain to the handler.

The binding that is broken, stated as an equality that should hold but doesn't:
`hmac_valid(body, secret) == true` is treated by callers as implying `request.shop == "the shop that actually sent this webhook"`, but in truth `request.shop` is read from a header that is entirely outside the signed material, so the equality only holds by convention/trust in transport, not cryptographically.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: any app that uses `request.shop` (as forwarded via `WebhookMetadata#shop`) to key per-tenant data (e.g., "look up/act on the record for this shop", "revoke access for this shop", GDPR `customers/redact` / `shop/redact` mandatory topics) can be tricked into applying the attacker's own webhook payload/action against a victim shop's record, since the gem presents `shop` as verified when it isn't. Given the `MANDATORY_TOPICS` include `shop/redact` and `customers/redact`, mis-attributing these to another tenant is a meaningful cross-tenant integrity issue purely through data the gem exposes as "validated." This matches the report's rubric of "cross-tenant access" (Critical) since the gem's own API misrepresents an unauthenticated header as an authenticated identity binding.

### Likelihood Explanation
Likelihood is bounded by two factors: (1) an attacker needs at least one genuine, validly-HMAC-signed webhook body from *some* shop where the app is installed (trivial for any developer/attacker who can install the target app on a free/dev store and trigger a webhook — no special privilege beyond normal app installation is required, satisfying the "unprivileged internet user" constraint); and (2) the webhook receiving endpoint must be reachable and the header can be freely set by the caller (true for any HTTP client hitting the app's public webhook route — headers are not part of any mutual-TLS or signed transport in the standard flow). This is a realistic, credential-free replay/header-substitution attack, not a theoretical one, and depends only on the gem's own `Request`/`HmacValidator`/`Registry` code, not on the host app misusing a documented contract.

### Recommendation
- Document (and enforce, if feasible) that `shop-domain` must not be treated as authenticated by itself; recommend that consuming apps independently verify `request.shop` against a known/installed shop list before acting, or
- Extend the signable material / validation so that `shop`, `topic`, and other headers relevant to tenant routing are bound into the HMAC check (this would require protocol support from Shopify, or at minimum the gem should clearly flag that only `raw_body` is authenticated), or
- Have `Registry.process` cross-check `request.shop` against the session/shop the webhook subscription was registered for, when that information is available, before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and creates/receives a webhook (e.g., `orders/create`) — this delivers a body `B` with a valid `X-Shopify-Hmac-Sha256` header `H` computed with the app's real `api_secret_key`.
2. Attacker replays this exact request to the app's public webhook endpoint, keeping `body = B` and `X-Shopify-Hmac-Sha256 = H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`) and successfully matches `H`: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, so the app processes attacker-supplied data/action as if it belongs to the victim shop: [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
