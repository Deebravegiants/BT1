### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable material from the raw request body only, while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are never part of the signed data. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields when constructing `WebhookMetadata` for the handler. Because the webhook HMAC secret (`api_secret_key`) is the same for every shop that has the app installed, any holder of one genuine, validly-signed webhook body can replay it with a forged `shopify-shop-domain` header pointing at a different (victim) shop, and the signature will still validate.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are parsed purely from headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards the header-derived `shop`, `topic`, and `webhook_id` to the handler as trusted metadata: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) against the app's single, shop-independent `api_secret_key`: [4](#0-3) 

The binding that should hold is:
`HMAC_valid(body, api_secret_key) == true` should imply `shop-domain header == the shop that actually generated this body`.

That equality does not hold here because the HMAC never covers the `shop-domain` header (nor `topic`/`webhook-id`), and the same `api_secret_key` is shared across every shop that has the app installed. Consequently, a valid signature only proves "this body was produced using the app's secret at some point," not "this body/topic/shop-id header tuple is authentic and self-consistent." An attacker who legitimately installs the app on their own store receives genuine webhook deliveries with valid `hmac-sha256` values computed over bodies they fully observe. They can then POST that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header value naming a victim shop. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop, even though the body content is the attacker's own.

This mirrors the LPDA analog directly: like `newId == finalId` being satisfied without the accompanying invariant (non-zero purchase) actually holding, here `HMAC(body)` validates without the accompanying invariant (shop identity matches the signed content) actually holding.

### Impact Explanation
Any application built on this gem that dispatches webhook handling by `WebhookMetadata#shop` (as the gem's own documented `Registry.process` flow encourages) can be made to process attacker-controlled event data attributed to an arbitrary victim shop identifier. Depending on the handler logic (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or business webhooks that trigger state changes keyed by `shop`), this enables cross-tenant data confusion or forged lifecycle events attributed to a shop the attacker does not control — a cross-tenant identity-binding failure.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on a shop they control (a normal, unprivileged action for any public/embedded app) to obtain one genuinely-signed webhook body/HMAC pair, then replay it with a forged `shop-domain` header — no access to `api_secret_key`, tokens, or the merchant's credentials is needed. This is fully reachable through the gem's own public `Webhooks::Request`/`Webhooks::Registry.process` API exactly as documented.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the HMAC-signable material, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`. At minimum, `Registry.process` (or the host application via gem-provided guidance) should be required to verify `request.shop` against a known, previously-installed shop record before acting on webhook content, rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a legitimate webhook delivery, e.g. `orders/create`, with its raw body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Send a POST to the app's webhook endpoint with:
   - `shopify-hmac-sha256: H` (unchanged)
   - body `B` (unchanged)
   - `shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `shopify-topic: orders/create` (unchanged or forged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully since header presence checks only require the headers to exist, not that they match the body: [5](#0-4) 
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes `HMAC(api_secret_key, B)` and compares to `H`: [6](#0-5) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, despite `B` never having originated from `victim-shop`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
