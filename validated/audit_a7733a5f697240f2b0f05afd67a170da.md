### Title
`Webhooks::Request#shop`/`#topic` are read from unsigned headers while `HmacValidator` only signs the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Utils::HmacValidator.validate` only verifies `Request#to_signable_string`, which is the raw HTTP body, against the `hmac-sha256` header. `Request#shop`, `Request#topic`, `Request#api_version`, and `Request#webhook_id` are all read directly from HTTP headers that are never included in the signed material. `Registry.process` trusts these header values unconditionally when constructing `WebhookMetadata`, so any request carrying a validly-signed body can be paired with an arbitrary, attacker-chosen `shopify-shop-domain`/`shopify-topic` header and still pass verification.

### Finding Description
The binding the code implicitly assumes is:

`HmacValidator.validate(request) == true` implies `request.shop` (and `request.topic`) are authentic for that request.

This binding does not hold. `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes the HMAC purely over that signable string, comparing it to the `hmac-sha256` header [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight out of `@headers` via `shopify_header`, with no participation in the signed bytes at all [3](#0-2) [4](#0-3) .

`Registry.process` then does:
```
raise ... unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [5](#0-4) 

There is no check anywhere in this path that the `shop` header actually corresponds to the shop for which the body was signed — because the body carries no shop identifier that is cross-checked, and the header carries no signature. `WebhookMetadata#shop` (the field host apps use to select which tenant's records to touch) is a `T::Struct` const populated straight from the unauthenticated header value [6](#0-5) .

Exploit flow: an attacker installs the target app on their own development shop (permitted per the threat model) and registers their own webhook endpoint, thereby obtaining at least one genuinely HMAC-signed `(raw_body, hmac)` pair produced with the app's real `api_secret_key` (which is shared across all shops that install the same app, not per-shop). The attacker then replays that exact body and `hmac-sha256` header to the app's real (shared) webhook-processing endpoint, but substitutes the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` passes because the body/HMAC pair is genuinely valid; `Registry.process` then invokes the host app's handler with `WebhookMetadata#shop` set to the victim's domain and `body` set to attacker-controlled content that was never actually sent by or associated with the victim shop.

No existing guard in this code path (`HmacValidator.validate`, `ShopValidator`, Sorbet typing) prevents this, because none of them tie the header-derived `shop`/`topic` to the signed body. `ShopValidator.sanitize!` is unrelated (used for OAuth shop param sanitization, not webhook processing).

### Impact Explanation
This is a cross-tenant authentication bypass: a request with a validly-signed body can be attributed to any shop the attacker chooses via an unsigned header, causing the host app to act on data intended for shop A as if it belonged to shop B (or to create fabricated events for a victim shop that never sent them). This maps to "Critical - authentication bypass" / cross-tenant access, since the value (`shop`) that determines whose tenant data is touched is never covered by the signature that is supposed to authenticate the request. The attack is repeatable against any victim shop domain the attacker chooses, for every webhook delivery the attacker can capture from their own installation.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own development shop with the target app installed and a webhook subscription delivering to a server they control (explicitly permitted), and (b) the ability to send an arbitrary HTTP POST to the app's shared webhook endpoint with custom headers (also permitted — attacker controls headers/body/ordering). No `api_secret_key`, access token, or other privileged credential is required; the attacker only reuses a signature that Shopify itself computed for their own legitimate webhook. This is low-cost and fully repeatable.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or independently verify that the `shopify-shop-domain` header corresponds to a shop the app actually expects for that specific webhook subscription/HMAC, before constructing `WebhookMetadata`. At minimum, document/require host apps to independently authenticate the `shop` header (e.g., cross-referencing an installed-shops list) rather than trusting `WebhookMetadata#shop` as proven-authentic solely because `HmacValidator.validate` returned true.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require "test_helper"

class RegistryShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @body = '{"id":1}'
    @hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", "secret", @body)
    )
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/x", handler: FakeHandler.new
    )
  end

  def test_same_signature_accepted_for_two_different_shops
    seen_shops = []
    FakeHandler.on_handle = ->(data) { seen_shops << data.shop }

    ["shop-a.myshopify.com", "shop-b.myshopify.com"].each do |shop|
      request = ShopifyAPI::Webhooks::Request.new(
        raw_body: @body,
        headers: {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => @hmac,
          "x-shopify-shop-domain" => shop,
          "x-shopify-api-version" => "2023-01",
          "x-shopify-webhook-id" => "1",
        },
      )
      ShopifyAPI::Webhooks::Registry.process(request) # does not raise
    end

    assert_equal ["shop-a.myshopify.com", "shop-b.myshopify.com"], seen_shops
    # Both requests, carrying the SAME body + SAME signature, were accepted
    # as authentic for TWO DIFFERENT shops.
  end
end
```
This demonstrates that `HmacValidator.validate` returning `true` (verifying only `raw_body`) does not bind to `WebhookMetadata#shop`, letting one signed payload be attributed to arbitrary tenants.
