### Title
Unbounded signature-recovery loop in BEEFY consensus verification enables cheap DoS via `handle_unsigned` - (File: `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
The BEEFY consensus verifier iterates `secp256k1_recover` over every entry in `mmr.signed_commitment.signatures` before any bound relative to the authority set size is enforced on the *upper* end, mirroring the ALPINE-CVE-2023-3817 pattern where `DH_check()` performs expensive elliptic-curve-adjacent work on attacker-controlled, unbounded input before rejecting it as invalid.

### Finding Description
`verify_mmr_update_proof` in [1](#0-0)  only checks that the *number* of signatures meets the supermajority threshold via `check_participation_threshold(signatures_length as u32, authority_set.len)` — a **lower**-bound check. There is no upper bound tying `signatures_length` to `authority_set.len`, so a submitted proof may contain arbitrarily many signature entries.

Immediately after that check, the function loops over `mmr.signed_commitment.signatures.iter()` and performs `H::secp256k1_recover` (an elliptic-curve public-key recovery, cryptographically comparable in cost class to the DH parameter checks in the CVE) for every entry, unconditionally: [2](#0-1) . Only afterward is a merkle multi-proof checked against the recovered addresses — meaning all the recovery work happens before the proof can be judged valid or bogus.

This verification path is reachable by anyone via `pallet_ismp::Call::handle_unsigned`, which is designed to accept **unsigned, feeless** ISMP messages (including `Message::Consensus`) and is validated inside `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())` — i.e., the full consensus verification (including this signature-recovery loop) runs during **transaction-pool validation**, executed by every full node that receives the gossiped extrinsic, before any fee or weight is charged: [3](#0-2) . The `Message::Consensus` variant is explicitly routed through this code (the consensus proof bytes are attacker-supplied and unauthenticated at this stage).

The only external bound on the extrinsic — and thus on `signatures.len()` — is the general Substrate max-extrinsic/block-length limit, not any BEEFY-specific cap tied to `authority_set.len`. A malicious relayer can therefore submit one proof whose `votes`/`signatures` vector is padded far beyond the real validator set size (with garbage 65-byte signatures) up to the extrinsic size ceiling, forcing every node's mempool validation to perform thousands of expensive `secp256k1_recover` calls for free before ultimately failing the merkle-membership check.

The equivalent Solidity path, `EcdsaBeefy.verifyMmrUpdateProof`, has the same structural shape (`checkParticipationThreshold` is a lower-bound-only check, followed by an unbounded `for` loop over `relayProof.signedCommitment.votes.length` calling `ECDSA.recover`) — [4](#0-3) . On EVM this is less severe because the caller pays gas for their own transaction (self-limiting, not a free-riding DoS against third parties), so it does not meet the "unprivileged, no cost to victim" DoS bar the report requires, but the same missing upper bound exists.

### Impact Explanation
On the Substrate/pallet-ismp path, this is a genuine denial-of-service primitive against the P2P/consensus-update pipeline: unsigned extrinsics are validated by *every* node in the network for free (no fee, no prior authentication) before being gossiped or included, per the pallet's own documented "unsigned transactions... executed for free" design ( [5](#0-4) ). An attacker who can craft (or replay/pad) a BEEFY consensus message can repeatedly force expensive EC recovery work onto the validating nodes' mempools at negligible cost to themselves, degrading the ability of the network to process legitimate BEEFY consensus updates and other unsigned ISMP messages — a route-unable-to-deliver-messages condition consistent with the "Validate" acceptance criteria.

### Likelihood Explanation
Medium. `handle_unsigned` and BEEFY consensus messages are exactly the class of externally-reachable, unauthenticated input the rules call out (pallet-ismp `handle_unsigned`, consensus verification). Constructing an oversized-but-structurally-valid `ConsensusMessage`/`MmrProof` SCALE encoding with a padded signature list requires no special privilege or key material — only knowledge of the (public) message format. The main mitigating factor is that on chains like Gargantua, `IsmpCallFilter` rejects any `handle_unsigned` batch carrying a BEEFY consensus message outright ( [6](#0-5) ), so the actual exposure depends on which runtime's filter configuration is deployed; I was not able to confirm within tool budget whether every production runtime (e.g. `nexus`) applies an equivalent filter, or whether any runtime accepts raw naive BEEFY updates through `handle_unsigned` unfiltered.

### Recommendation
Add an explicit upper bound on `signatures.len()` (and the EVM `votes.length`) relative to the known `authority_set.len` (e.g., reject if `signatures_length > authority_set.len`) before performing any `secp256k1_recover`/`ecrecover` calls, and/or deduplicate by `authorityIndex` up front so padding with repeated or out-of-range indices cannot inflate the recovery loop. Apply the same bound-before-work ordering used elsewhere in the codebase (e.g., the duplicate-key check in `modules/ismp/state-machines/evm/src/lib.rs` and the `MAX_PROOF_DEPTH` bound in the Pharos SPV verifier) so cost-bearing cryptographic work is only performed after cheap structural bounds are validated.

### Proof of Concept
Not independently executed (no code-execution access in this session). Conceptually: construct a `Message::Consensus` (or `ConsensusMessage`) whose `signed_commitment.signatures` vector contains, e.g., 50,000 arbitrary 65-byte blobs (satisfying only the minimum supermajority count needed to pass `check_participation_threshold`), padded up to the runtime's max extrinsic/block-length limit, and submit it via `Ismp::handle_unsigned`. Every node performing `validate_unsigned` will execute `secp256k1_recover` 50,000 times before the subsequent merkle-membership check fails, at zero fee cost to the submitter — repeated submission variants (changing bytes to bypass extrinsic-hash dedup) sustain the load.

```rust
pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
