## Title
Unchecked ERC20 transfer return value in `IntentGatewayV2.withdraw` and `onAccept` (SweepDust) allows silent transfer failures and permanent freezing of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron variant) escrows tokens for cross-chain intents and pays them out via `withdraw()` and the `SweepDust` handler inside `onAccept()`. Both paths perform ERC20 transfers with a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the call did not revert (`success`), never decoding/validating the boolean return value that `IERC20.transfer` is supposed to return. This is the same bug class as the referenced IPOR report ("transfer result value ignored") — but here it sits on the fund-release path of an escrow reachable by any relayer delivering a proven cross-chain message.

### Impact Explanation
If the escrowed token is a non-standard ERC20 that returns `false` on failure instead of reverting (e.g. insufficient balance/allowance edge cases, blacklist/pause logic, or any token whose `transfer` silently fails), `success` from the low-level `.call` will still be `true` because the call itself executed without reverting. The code then proceeds to decrement `_orders[body.commitment][token]` and mark `_filled[body.commitment] = beneficiary`, as though the payout succeeded. The beneficiary never receives the tokens, but the escrow record showing they are owed is permanently erased/marked filled, and the tokens remain stuck in the contract with no accounting path left to reclaim them. This is a permanent freezing/loss of user funds triggered purely by delivering a legitimately proven cross-chain `RedeemEscrow`/`RefundEscrow`/`SweepDust` message — reachable by any relayer, not requiring any privileged role.

### Likelihood Explanation
The `onAccept` function is called by the ISMP host for any correctly-proven incoming POST request from a counterpart `IntentGateway` instance or from Hyperbridge itself (for `SweepDust`), so the vulnerable code executes on the ordinary, unprivileged message-delivery path once a relayer submits a valid proof. The trigger condition (a token whose `transfer` returns `false` on failure rather than reverting) is a known, common non-standard ERC20 behavior, making this readily triggerable whenever such a token is configured as an escrowed input/fee token on this chain.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer` (already imported and used elsewhere in the same contract), which reverts on both call failure and a `false` boolean return, ensuring escrow accounting is never decremented unless the transfer truly succeeded.

### Proof of Concept
1. Configure/escrow an input token whose `transfer()` implementation returns `false` on failure instead of reverting (a class of tokens explicitly not handled safely by raw `.call` checks).
2. Create and fill an order so tokens are escrowed under `_orders[commitment][token]`, as done via `enterOrder`/predispatch flows.
3. Have the token enter a state where the payout transfer would fail (e.g., recipient blacklisted, contract-level pause, or any condition causing the token to return `false`).
4. A relayer delivers the proven `RedeemEscrow` (or `RefundEscrow`) message, triggering `onAccept` → `withdraw()`.
5. `token.call(...)` succeeds at the EVM call level (`success == true`) even though the token's internal `transfer` logic returned `false` and moved no funds.
6. `_orders[commitment][token] -= amount` executes and `_filled[commitment] = beneficiary` is set, permanently erasing the record that the beneficiary is still owed those tokens — the tokens remain stranded in the `IntentGatewayV2` contract with no remaining code path to recover them. [5](#0-4)
