### Title
Emporium fee-token/amount not bound to the EIP-712 signature allows an unprivileged submitter to redirect and inflate wallet-fee withdrawals from a signer's `HinkalWallet` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet()` authenticates only `emporiumMessage`, the operation list (`ops`), `maxFee`, and `deadline` via EIP-712 (`EMPORIUM_SIGNATURE_TYPEHASH`). It never binds `circomData.erc20TokenAddresses`, `circomData.feeStructure.feeToken`, or `circomData.amountChanges`/`deltaAmountChanges` to the signature. Any unprivileged submitter of `Hinkal.transact()` who obtains a valid, unused `EmporiumStack` signature (e.g. by observing it before it is relayed) can freely choose the token array and `feeStructure`, causing `payRelayFees()` to pull up to `stack.maxFee` of an arbitrary ERC20 the signer's `HinkalWallet` holds — a token that was never part of the signed `ops` or intended as the fee token — and send it to `payRelay()`/`doSendToRelay()` out of the wallet contract.

### Finding Description
`verifyWallet()` computes the EIP-712 digest solely from: [1](#0-0) 

and checks only `feeStructure.flatFee <= stack.maxFee`: [2](#0-1) 

Neither `feeStructure.feeToken`, `circomData.erc20TokenAddresses`, nor `deltaAmountChanges` are part of the signed payload. Yet `payRelayFees()` uses exactly these attacker-supplied fields to decide which token and how much to withdraw from the signer's own wallet: [3](#0-2) 

When `signerAddress != address(0)`, `relayFee = flatFee` is taken directly (not scaled by the actual amount moved) and paid via `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, erc20TokenAddress)`: [4](#0-3) 

`HinkalWallet.doSendToRelay` trusts the Emporium contract completely and transfers whatever token/amount is requested straight out of the wallet's own balance: [5](#0-4) 

Because `erc20TokenAddresses`, `amountChanges` (hence `deltaAmountChanges`), and `feeStructure` all live in `CircomData` fields that are checked against the caller's own ZK proof of ownership (not the signer's), the *transaction submitter* — not the wallet's signer — controls which token is nominated as `feeToken` and can select any ERC20 held by the victim's `HinkalWallet`, independent of what `ops` actually does. The submitter needs only:
1. Their own dust shielded balance of the target token (e.g. 1 wei) to legitimately set `deltaAmountChanges[i] < 0` for that array slot (this is proven via their own valid ZK proof, so it does not require anyone else's funds).
2. A previously signed, not-yet-consumed `EmporiumStack` for the target `stack.signerAddress` (obtained e.g. by observing it prior to relaying — the signature says nothing about the fee token, so a legitimately obtained signature for one purpose can be repurposed for fee extraction from any of the wallet's token balances).
3. `circomData.relay` set to any address currently registered in `RelayStore` (a publicly readable list via `getRelayStore()`), which requires no special privilege to *use*, only knowledge of an existing entry.

This breaks the intended equality that a `HinkalWallet` fee debit must be authorized by the signer's EIP-712 signature — the signature commits to `ops`/`maxFee`/`deadline`/`message` but not to the token or context in which `maxFee` is actually charged, so `doSendToRelay` executes a wallet asset movement the signer never authorized for that token.

### Impact Explanation
This is unauthorized asset movement out of a user's `HinkalWallet`: up to `stack.maxFee` of any ERC20 balance held by the wallet — potentially unrelated to the `ops` the user actually signed — can be siphoned off as a "relay fee" without the wallet owner's consent for that specific token/amount. This matches the "High" impact category: executing calls or moving assets a wallet owner never authorized, and can also cause temporary/permanent loss of user funds if the token drained differs from what the user intended to spend.

### Likelihood Explanation
Requires no admin/owner/relay-operator privilege — only observing (or otherwise obtaining) a legitimately-signed, unconsumed `EmporiumStack` payload before it's executed (these travel as plain off-chain signed messages meant for relaying, and nothing in the signed payload restricts which token can be charged), and holding a trivial (1-wei) shielded balance of the target token to include it as an extra `erc20TokenAddresses` entry. The exploit does not require compromising the signer's key, the relay operator, or the protocol owner.

### Recommendation
Include `circomData.erc20TokenAddresses`, `feeStructure.feeToken`, and the intended relay-fee amount/relationship to `deltaAmountChanges` in the EIP-712 digest signed by the wallet owner (`EMPORIUM_SIGNATURE_TYPEHASH`), so that the fee token and the maximum extractable amount are cryptographically committed to by the signer, not chosen by the transaction submitter at execution time. Additionally, consider requiring that `relayFee` charged from the wallet is proportional to/bounded by amounts actually flowing through the signed `ops`, rather than an independent `flatFee` field controllable per-call.

### Proof of Concept
1. Victim signs an `EmporiumStack` (`v,r,s,signerAddress,ops,maxFee=100, deadline`) intending to authorize a swap operation and expects at most 100 units of fee in the token used by `ops` (say WETH).
2. Before the intended relay submits it, an unprivileged attacker who has observed this signed payload (or a relay operator that decides to abuse it) submits `Hinkal.transact()` themselves with:
   - Their own valid ZK proof spending 1 wei of shielded DAI they own, `amountChanges[k] = -1` for a DAI entry appended to `erc20TokenAddresses`.
   - `circomData.externalActionData` pointing at `EmporiumUpgradeable`, `externalActionMetadata` = the victim's untouched `stack` (signature still valid, `emporiumMessage` unused).
   - `circomData.feeStructure = {feeToken: DAI, flatFee: 100, variableRate: 0}`.
   - `circomData.relay` = any address already registered in `RelayStore`.
3. `verifyWallet()` succeeds because `flatFee (100) <= stack.maxFee (100)` and the signature over `ops/maxFee/deadline/message` is valid — none of these checks involve the token.
4. `payRelayFees()` sees `deltaAmountChanges[k] < 0` for the DAI entry, `isFeeToken = true`, `relayFee = flatFee = 100`, and calls `sendToRelayFromWallet(relay, signerAddress, 100, DAI)` → `HinkalWallet(signerAddress).doSendToRelay(relay, 100, DAI)`, transferring 100 DAI out of the victim's wallet to `relay`, even though the victim never intended to pay any fee in DAI nor authorized this specific withdrawal.

```text
    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }
```
