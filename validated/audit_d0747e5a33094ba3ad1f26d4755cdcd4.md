### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop and topic used to route/attribute the webhook are read from unauthenticated HTTP headers. Because a single app `client_secret` signs webhooks for *every* shop that installs the app, an attacker who legitimately installs the app on their own shop can capture a validly-signed `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header, making the app process the payload as if it came from a victim shop.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from headers that are excluded from that signable string: [2](#0-1) 

`Registry.process` verifies only that the HMAC matches the body, then forwards the caller-controlled `shop`/`topic` values into the handler without any further binding check: [3](#0-2) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` against `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is the same for the app across all shops (it is not per-shop), any unprivileged internet user can install the target app on their own store, trigger a webhook to obtain a valid `(raw_body, hmac)` pair, and then POST that same body+hmac to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `shopify-topic`) for a victim shop. The equality the code implicitly (and incorrectly) relies on is:

`hmac == HMAC(secret, raw_body)` ⟹ `shop-domain header == authentic shop that generated the event`

but the right side is never checked — the shop identity is asserted, not authenticated by the HMAC.

### Impact Explanation
This breaks the tenant-identity binding used to attribute and act on webhook data. A downstream app that uses `WebhookMetadata#shop` to select which shop's session/tenant record to update (a extremely common pattern, e.g., processing `orders/create`, `app/uninstalled`, `shop/redact`, GDPR webhooks, or billing events) can be made to apply a forged shop's identity to a payload the attacker controls, i.e., cross-tenant data injection/impersonation — one of the explicitly allowed "Critical" impact categories (cross-tenant access).

### Likelihood Explanation
Any unprivileged internet user can install the target app for free on their own development/test store (a normal, unprivileged action), which lets them generate legitimately signed webhook payloads. Replaying to the app's public webhook endpoint with a modified `shop-domain`/`topic` header requires no secret knowledge and no privileged access — only a spoofable HTTP header. Likelihood is high wherever an app exposes an internet-reachable webhook endpoint built on `ShopifyAPI::Webhooks::Registry.process`, which is the library's documented usage pattern.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`) in the value that is HMAC-verified, or otherwise cryptographically bind them (e.g., verify the shop domain against the session/shop that a stored, previously-issued access token belongs to before trusting `WebhookMetadata#shop`). At minimum, document prominently that `request.shop`/`request.topic` are NOT covered by the webhook HMAC and must not be trusted for tenant routing without an independent authenticity check (e.g., cross-referencing against an existing, verified session for that shop).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally.
2. Attacker triggers any webhook topic the app subscribes to (e.g. updates a product) and captures the raw HTTP request Shopify sends to the app's webhook endpoint, including `raw_body` and the `x-shopify-hmac-sha256` header value (a valid HMAC computed with the app's shared `client_secret`).
3. Attacker crafts a new POST to the same webhook endpoint using the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `raw_body` against the HMAC.
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)` and performs shop-scoped side effects (e.g., updates records, triggers uninstall cleanup, revokes access) against the victim shop's tenant data, despite the payload never having been sent by Shopify on behalf of that shop.
