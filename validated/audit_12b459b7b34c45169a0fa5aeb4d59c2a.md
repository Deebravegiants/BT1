### Title
Missing replay cleanup lets a Get-response relayer fee be paid twice via response delivery then timeout - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse, address)` pays the relayer fee for a `GetRequest` out of `_requestCommitments[commitment]` but never deletes that mapping entry afterward, unlike every other terminal state transition in the same contract (`dispatchTimeOut` for both `GetRequestTimeout` and `PostRequestTimeout` explicitly `delete _requestCommitments[commitment]` as the very first "replay protection" step). This is analogous to the Grim Finance bug class: an unprotected state-mutating path (a message/asset accounting update triggered by an externally-supplied, single-shot delivery) fails to close out the accounting record it just consumed, letting the same underlying escrowed value be drawn down again through a second, differently-shaped call.

### Finding Description
`dispatchIncoming(GetResponse memory response, address relayer)` is the handler-restricted entry point that pays a relayer for successfully delivering a `GetResponse`: [1](#0-0) 

Note the pattern: it writes `_responseReceipts[commitment]` for its own replay protection (so the same `GetResponse` cannot be redelivered), calls `onGetResponse` on the app, and then pays `fee = _requestCommitments[commitment].fee` to the relayer — but it never clears `_requestCommitments[commitment]`.

Contrast this with the timeout paths in the same file, which treat `_requestCommitments` as the single source of truth for "has this request's fee already been settled," and explicitly delete it up front: [2](#0-1) 

`_requestCommitments` is populated once, at `dispatch()` time, for both Post and Get requests (a `GetRequest` commitment carries the same `FeeMetadata{sender, fee}` record used for a `PostRequest`): [3](#0-2) 

Because a successful `GetResponse` delivery leaves `_requestCommitments[commitment]` populated with the original `fee`, the request still looks "live" from the point of view of anything that reads that mapping. If a `GetRequestTimeout` proof for the *same* request can later be produced and delivered (the destination-chain timeout check in `handleGetResponses`/timeout handler is driven by `timestamp > timeout` on Hyperbridge's own state, not by "has a response already been recorded on this EVM host"), `dispatchTimeOut(GetRequestTimeout, meta, commitment)` will still find `meta.fee != 0` and pay it out a second time to `meta.sender`: [4](#0-3) 

The relayer already collected the fee once through the response path; the original sender now collects it again through the timeout path. This is the same root-cause shape as Grim Finance's missing state guard before crediting external value: one accounting slot (`_requestCommitments[commitment].fee`) is drained by an external call without the contract clearing the record that authorizes the drain, so a second, distinctly-routed call can drain it again.

### Impact Explanation
This directly causes duplicate payout of the fee-token escrow held by `EvmHost` — a form of unbacked/duplicated value transfer out of protocol-held funds, reachable purely through the normal, permissionless "relay a proof" flow (`HandlerV2.handleGetResponses` then later `handlePostRequestTimeouts`/`handleGetResponseTimeouts`-equivalent flow), with no privileged actor required. Every `GetRequest` fee becomes a double-spendable value once a timeout proof for that request can be produced after a response has already been delivered.

### Likelihood Explanation
Exploitability hinges entirely on whether Hyperbridge's relay-chain consensus/messaging layer (outside this EVM repo, in `pallet-ismp`/`modules/ismp/core`) refuses to emit or attest a timeout for a `GetRequest` that has already been responded to. I was not able to fully verify that cross-chain invariant within the available tool budget — the grep hits in `modules/pallets/ismp/src/lib.rs` and `modules/ismp/core/src/messaging.rs` suggest there is some "responded" bookkeeping, but I could not confirm from the retrieved code whether it is enforced strictly enough to make the sequence (deliver response → later deliver timeout for the same request) fail before it ever reaches `EvmHost.dispatchTimeOut`. If that invariant is solid, this is at minimum a hygiene/defense-in-depth gap (missing CEI cleanup that every sibling function performs); if the relay-chain side ever allows a stale/reorg'd or maliciously-crafted timeout message through after a response, this becomes directly exploitable for double payment.

### Recommendation
Delete `_requestCommitments[commitment]` inside `dispatchIncoming(GetResponse, address)` immediately after (or as part of) recording the response receipt, mirroring the "replay protection" comment and pattern already used in both `dispatchTimeOut` overloads, so the fee record cannot be read/paid a second time regardless of what the relay-chain layer allows through.

### Proof of Concept
Not fully constructible from the EVM repo alone: a concrete PoC requires confirming whether the Substrate-side `pallet-ismp` messaging path can produce a valid `GetRequestTimeout` message/proof for a request that already has a recorded `GetResponse` (i.e., whether "responded" state blocks timeout emission). Within the EVM contracts alone, the missing-delete is unconditional and independently verifiable by inspecting `dispatchIncoming(GetResponse,...)` versus the two `dispatchTimeOut` overloads cited above — the asymmetry itself is the concrete, file/line-verifiable defect; the end-to-end double-payment requires the cross-chain leg I could not confirm in this session.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
