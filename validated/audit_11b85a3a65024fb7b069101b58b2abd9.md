### Title
Webhook shop-domain identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by checking the HMAC of the raw request body only. The `shop` (and `topic`/`webhook_id`/`api_version`) values that are handed to the app's webhook handler come straight from HTTP headers that are **not** included in the HMAC-signed data, so the shop identity that the handler acts on is not cryptographically bound to the signature that proves the request is a genuine Shopify-signed payload.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the request: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body` - the JSON body bytes - and nothing else: [2](#0-1) 

`Webhooks::Request` also exposes `shop`, `topic`, `webhook_id`, and `api_version`, all sourced purely from headers via `shopify_header`, none of which participate in the signable string: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` (a header value) to build the `WebhookMetadata` object that is handed to the app's handler as the tenant identity for the event: [5](#0-4) 

The equality that should hold, but doesn't, is:
`bytes covered by HMAC (raw_body)` == `bytes the handler trusts as the tenant identity (shop header)`

Because the HMAC only proves "this body was signed with the app's secret at some point for some shop," it does **not** prove "this body belongs to the shop named in this request's headers." Any client that can reach the webhook endpoint controls the HTTP headers of the request independently of the body. If an attacker obtains any one valid `(raw_body, hmac)` pair signed for the app's secret - the easiest way being to install the app themselves on their own store and capture a real webhook delivery for a topic they control (e.g. `orders/create` triggered by placing an order in their own shop) - they can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will validate the HMAC (it only checks the body), and the handler will receive `WebhookMetadata` claiming the event is for the victim shop, with attacker-chosen body content.

The webhook docs confirm that `data.shop` is meant to be used by handlers to identify the tenant the event is about (e.g. to look up the shop's session or dispatch a background job for that shop): [6](#0-5) 

The tests for `Registry.process` show that `data.shop` is populated directly from the header and passed through unchecked against any authenticated shop identity: [7](#0-6) 

### Impact Explanation
This breaks the tenant/shop identity binding for webhook processing: an unprivileged attacker who can install the app on their own store (a normal, unprivileged action — no `api_secret_key`, access token, or other credential of the target is required) can forge webhook deliveries attributed to any other shop's domain, as long as they can produce *any* valid `(body, hmac)` pair for the shared app secret. Because `hmac-sha256` is computed only over the body and is otherwise shop-agnostic, this is possible without knowing the app's secret directly - the attacker leverages Shopify's own legitimate signing of their own shop's webhook traffic and simply swaps the `shop-domain` header on replay to point at a victim tenant. Depending on the app's handler logic (many apps key session lookups, data deletion, or state changes off `data.shop`), this enables cross-tenant impact: for example spoofing a `shop/redact` or `app/uninstalled` event for a victim shop to trigger deletion of that victim's stored data/session, or injecting attacker-controlled body content that the handler will process as if authoritative for the victim shop.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that (a) is a public app installable by arbitrary merchants (so an attacker can install it on their own store to harvest a legitimate signed webhook), and (b) has webhook handlers that key sensitive behavior off `WebhookMetadata#shop` without independently verifying that the shop is one that is expected to send this event/body pair. Since this is the documented, expected usage pattern of `Registry.process` and `WebhookMetadata`, most integrating apps are exposed to this by default, with the gem providing no independent binding between body and shop.

### Recommendation
Bind the shop identity into the same integrity check as the payload rather than trusting it from an out-of-band header. Options: (1) include the `shop-domain` header (and topic/webhook_id) in the value that is HMAC-verified (this would require Shopify to sign the header too, which the gem cannot unilaterally add - so instead), (2) require and document that consumers cross-check the incoming `shop` against a shop they already have a valid, stored session for prior to acting on webhook content, and/or (3) have `Registry.process` accept a known list/set of installed shops (or a lookup callback) and reject webhooks whose `shop` isn't recognized before invoking handlers, rather than passing raw header data straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook delivery for a subscribed topic (e.g. `orders/create`), capturing the raw body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (computed by Shopify using the app's shared secret over `B`).
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - `raw_body = B`
   - `X-Shopify-Hmac-Sha256 = H`
   - `X-Shopify-Topic = orders/create`
   - `X-Shopify-Shop-Domain = victim-shop.myshopify.com` (swapped from the original header)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`, per: [8](#0-7) [9](#0-8) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), topic: "orders/create", ...)`, and the handler acts on the victim shop's identity using attacker-controlled/attacker-obtained body content, per: [10](#0-9)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
