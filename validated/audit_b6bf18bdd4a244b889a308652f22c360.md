### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's authenticity solely via `Utils::HmacValidator.validate(request)`, which HMACs only the raw request body [1](#0-0) . The `shop` value used downstream to identify the tenant is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed payload [2](#0-1) . This breaks the binding: `shop value verified by HMAC == shop value used to attribute the event to a tenant`.

### Finding Description
`Webhooks::Request#hmac` computes the received signature from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body` [3](#0-2) . `Utils::HmacValidator.validate_signature` recomputes an HMAC over `to_signable_string` (the body) and compares it against the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) .

Critically, `Registry.process` trusts `request.shop` — derived purely from the unauthenticated `shop-domain` header — and forwards it as the tenant identifier to the host application's handler without any cryptographic binding to the verified body:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

Because Shopify computes the HMAC using only the raw body and the app's `client_secret`, a valid signature for a given body/secret pair is independent of the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers. Any party capable of relaying (or replaying) a genuinely-HMAC-valid webhook payload — e.g., a merchant/staff member on Shop A who can trigger a webhook delivery to their own endpoint, or any intermediary able to observe one valid delivery — can resend the exact same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a different tenant (Shop B). `HmacValidator.validate` will still return `true` because the signature never covered the shop header, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the event belongs to Shop B's tenant while the body actually contains Shop A's data.

The equality this breaks: **shop value covered by the HMAC signature ≠ shop value used to key the tenant-scoped webhook handler**.

### Impact Explanation
This directly enables cross-tenant data confusion inside the app's own webhook handler: the host app, following the SDK's documented usage where `WebhookMetadata#shop` is treated as the authenticated tenant identifier for the delivered payload, may write/associate Shop A's payload data (e.g., customer PII, order data, `customers/redact` requests, `app/uninstalled` events) under Shop B's session/tenant record, or trigger tenant-scoped side effects for the wrong shop. This matches the "cross-tenant access" Critical impact class, since the vulnerable binding is entirely inside this gem's `Registry.process`/`Request` implementation, not a host-application misuse of a documented contract.

### Likelihood Explanation
Exploitation requires the attacker to obtain one legitimately HMAC-signed webhook body (e.g., by being a merchant/collaborator on any shop that installs the app, or by intercepting a delivery to a non-TLS-protected relay), then replay it to the app's public webhook endpoint with a forged `shop-domain` header. No `client_secret` or access token is needed — only a previously observed valid `(body, hmac)` pair, since the header is never part of what's signed. This is a realistic outsider-observable scenario for any multi-tenant Shopify app using this gem's `Registry.process`.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the verified body (e.g., verify shop against a value embedded in the signed payload, or require that HmacValidator authenticate the header set alongside the body) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `hmac-sha256: HMAC(secret, B)`.
2. Attacker (e.g., staff/collaborator on shop-a, or a network intermediary) captures `(B, hmac)`.
3. Attacker POSTs the same body `B` and same `hmac-sha256` header to the app's webhook endpoint but with `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B)` against the header, ignoring `shop-domain` [1](#0-0) .
5. `Registry.process` calls `handler.handle` with `shop: "shop-b.myshopify.com"` and the body belonging to `shop-a`, causing the app to process shop-a's data under shop-b's tenant context [6](#0-5) .
