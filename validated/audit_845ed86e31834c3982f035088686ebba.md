### Title
Stale operator authorization status used to authorize signup instead of re-validating with backend - ([File: src/plans/mod.rs])

### Summary
The reported bug class describes an action (validator deposit allocation) being authorized using stale/cached status data instead of the most recently finalized state from the backend. In orb-core, the same class of bug exists in the operator QR-code authorization flow: once an operator's QR code is validated against the backend via `backend::operator_status::request()`, the resulting `valid`/`location_data` decision is cached into an `OperatorData` struct together with a `timestamp`, and this cached authorization is reused for all signups within `operator_qr_expiration_time` (23 hours by default) without ever re-querying the backend for the operator's current status.

### Finding Description
`verify_operator_qr_code` calls `backend::operator_status::request` [1](#0-0)  once, and the boolean/location result is stored in `OperatorData { qr_code, location_data, timestamp }` [2](#0-1) .

That cached `OperatorData` is then reused across the entire idle loop and across multiple subsequent signups as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, both in `scan_remaining_qr_codes` [3](#0-2)  and in `scan_initial_qr_codes`/`idle_wait_for_signup_request` for self-serve mode [4](#0-3) . No re-check of operator validity happens on this "fast path" — the only re-validation call, `verify_operator_qr_code`, is only performed on the "slow path" when the cached window has expired or no operator data exists yet [5](#0-4) .

This means that if the backend revokes/invalidates an operator's authorization (e.g., the operator is flagged, banned, or their account is suspended for policy violation) after the initial QR scan but before the 23-hour cache window expires, orb-core will keep treating the operator as authorized and will keep initiating signups tied to that operator ID (`distributorId` in the signup POST request [6](#0-5) ) purely based on the stale, locally cached decision, exactly analogous to the reported "deposit allocation before validator status is updated" bug class — an authorization decision made from stale state instead of the current finalized backend status.

### Impact Explanation
An operator whose authorization has been revoked by the backend (for fraud, policy violation, compromised credentials, etc.) can continue enrolling users and attributing signups to their (now revoked) operator/distributor ID for up to the full `operator_qr_expiration_time` window (23 hours by default) after revocation, since the orb never re-checks operator validity mid-window. This is a case of unauthorized signup/enrollment continuing to be attributed to a party that should no longer be trusted — a direct analog to the misattribution/misallocation risk described in the report.

### Likelihood Explanation
This requires no attacker action beyond normal operation continuing after backend-side revocation, and is a caching/state-staleness design rather than a rare edge case. It reliably triggers whenever a revocation happens mid-session (which is a plausible fraud-response workflow) and the operator/orb pair remains active, especially in self-serve deployments where the operator QR-scan-to-signup gap can span many signups over the entire expiration window.

### Recommendation
Re-validate the operator's status with the backend (`backend::operator_status::request`) periodically or before each individual signup rather than solely relying on the cached `OperatorData.timestamp` expiration window, or shorten the effective trust window and add a backend-push/poll mechanism analogous to the report's recommendation of gating new actions on a finalized status flag.

### Proof of Concept
1. Operator scans QR code; `verify_operator_qr_code` succeeds and orb-core caches `OperatorData { valid: true, timestamp: now }`.
2. Backend later revokes/invalidates this operator (e.g., detected fraud) — `operator_status::request` would now return `valid: false` if called.
3. Within the next `operator_qr_expiration_time` (up to 23h), the orb performs further signups via `scan_remaining_qr_codes`'s fast path (`operator_data.timestamp.elapsed() < operator_qr_expiration_time`), which skips calling `verify_operator_qr_code` entirely, so the revoked operator's ID is still attached to newly submitted signups.
