### Title
Order creator can grief a filling solver's escrow payout by including a maliciously pausable/blacklistable token among an order's inputs, permanently freezing that solver's proceeds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (and its non-modular sibling `IntentGatewayV2.withdraw` on the tron/legacy variant) releases every escrowed input token for an order in a single loop, transferring each one to the beneficiary unconditionally. `placeOrder` does not whitelist which ERC-20 tokens a user may specify as `order.inputs` — the only check is rejection of duplicate tokens within the same order. This mirrors the MultiRewards `getRewardForUser()` pattern where an unbounded, ungated token loop can be forced to permanently revert by a single problematic token in the set.

### Finding Description
When a user calls `placeOrder`, they freely choose the `TokenInfo[] inputs` array, including arbitrary token contract addresses, with no allow-list validation beyond duplicate rejection [1](#0-0) . These tokens are escrowed in `_orders[commitment][token]`.

When a solver later fills the order and the settlement message (`RedeemEscrow`) arrives via Hyperbridge, `onAccept` calls `_withdraw(body, false, true)`, which loops over `body.tokens` (derived directly from `order.inputs`) and calls `IERC20(token).safeTransfer(beneficiary, amount)` for every token in the list [2](#0-1) . If any single token in that list is a contract the malicious order-creator controls or has arranged to be pausable/blacklistable (e.g., a centrally-administered stablecoin-style token that can freeze a specific address, or a token that simply reverts on `transfer` to certain addresses), the `safeTransfer` call reverts, and the *entire* `_withdraw` call reverts — including the transfer of all other, legitimate escrowed tokens in that same order, and the release of accumulated `TRANSACTION_FEES` to the solver.

Because this happens inside the settlement path (`onAccept`/`_withdraw`), and there is no per-token skip/try-catch logic, a solver who has already delivered the requested output tokens to the beneficiary (an irreversible, unilateral action taken before this callback runs) has no way to force payment of the escrowed input tokens it is owed. The escrow becomes permanently stuck for that order: neither the intended solver can claim it, nor can the order creator regain it (since `_filled[commitment]` was already set, blocking cancellation paths). This is analogous to the `MultiRewards.getRewardForUser()` bug where a single malicious/paused reward token DoSes an entire token-transfer loop, except here the attacker is the order creator rather than governance-approved reward-token whitelisting — and the ungated nature of user-supplied input tokens makes the attack surface strictly worse (no governance whitelist exists at all for `order.inputs`).

The tron/legacy `IntentGatewayV2.withdraw` has the identical unguarded loop pattern using raw `call` + `TransferFailed()` revert [3](#0-2) .

### Impact Explanation
High for the affected solver: after fulfilling their side of the trade (delivering output tokens to the user/beneficiary on the destination chain, an on-chain, irrevocable action), the solver's compensation (the escrowed input tokens plus escrowed transaction fees) can be permanently frozen by including just one adversarial token among the order's inputs. This is a direct freezing-of-funds vulnerability reachable from a single `placeOrder` transaction submitted by any unprivileged user, and it also blocks the `EscrowReleased`/`EscrowRefunded` accounting for that order, since `_withdraw` never completes.

### Likelihood Explanation
Medium: The order creator (attacker) fully controls the `inputs` token list at `placeOrder` time and needs no privileged access. The only friction is convincing/incentivizing a solver to fill an order containing an attacker-controlled or externally-pausable token — but solvers evaluate orders economically and a token that looks like a normal ERC-20 at fill time (and is only paused/blacklisted against the solver's specific address afterward) is a realistic griefing vector. No governance or admin cooperation is required, unlike the original MultiRewards report's requirement that governance first whitelist a reward token.

### Recommendation
- In `IntentsBase._withdraw` (and the tron/legacy `withdraw`), replace the unconditional `safeTransfer`/`transfer` per-token with a bounded low-level call (e.g., a fixed gas stipend similar to the referenced PR 401 fix) and skip/record failed transfers rather than reverting the whole withdrawal.
- Alternatively, decouple withdrawal into a two-phase design: mark escrow released and let the beneficiary pull each token independently (pull-over-push), so one problematic token cannot block release of the others or of protocol fees.
- Consider restricting `order.inputs` to a governance-maintained token allow-list at `placeOrder` time, consistent with the report's "stringent whitelist" recommendation.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer` succeeds normally but can be made to always revert for a specific target address (e.g., via an owner-controlled blacklist), or is pausable by its owner.
2. Attacker calls `placeOrder` with `inputs = [ {token: USDC, amount: 1000}, {token: EvilToken, amount: 1} ]` and reasonable `output` assets, so the order looks attractive to solvers.
3. A solver fills the cross-chain order via `fillOrder`, delivering the requested output tokens to the beneficiary on the destination chain — this step is irrevocable.
4. Before (or as soon as) the `RedeemEscrow` settlement message reaches the source chain, the attacker calls `EvilToken.blacklist(solver)` (or `pause()`).
5. `onAccept` → `_withdraw` loops through `body.tokens`; the `IERC20(EvilToken).safeTransfer(solver, 1)` call reverts, causing the entire `_withdraw` transaction to revert.
6. The USDC escrow and transaction fees remain locked in the contract indefinitely — the solver already delivered output tokens and receives nothing, and no other code path exists to bypass the failing token in the loop.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
