This confirms the attack path. In `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`), the solver (msg.sender) fills the order and delivers output tokens directly to the beneficiary, then a `RedeemEscrow` request carrying `order.inputs` (fully attacker/order-creator-controlled, arbitrary length, arbitrary token addresses) and `beneficiary = msg.sender` (the solver) is posted back to the source chain. On the source chain, `onAccept` calls `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`), which loops over `body.tokens` and calls `IERC20.safeTransfer` (or `_sendValue` for native) to the beneficiary for every token in a single atomic loop — if any single token transfer reverts (e.g., a blacklisting token like USDC where the solver's address becomes blacklisted, or a token whose `transfer` is coded to always revert to a specific address, or the beneficiary being a contract crafted to reject a native transfer), the entire `_withdraw` call reverts. This is functionally identical to the reported `processWithdrawalQueue` bug: a single hostile item forces reversion of the whole batch.

Since `EvmHost.dispatchIncoming` (`evm/src/core/EvmHost.sol:794-818`) already implements the "permissive" pattern recommended in the report — it wraps the `onAccept` call in a low-level `.call(...)` and deletes the request receipt on failure "so it can be retried" — the host itself won't brick. But because the underlying revert condition (a malicious/blacklisting token chosen by the order creator, or a poisoned beneficiary) is deterministic, every retry of the same message will fail identically forever. That means the message can never be delivered, and the escrowed tokens for that order — including any *other, legitimate* tokens bundled in `order.inputs` alongside the malicious one — remain permanently stuck in escrow, since `_withdraw`'s per-order loop is all-or-nothing. ### Title
Order creator can permanently freeze a solver's escrowed redemption by including a reverting/blacklisting token in `order.inputs` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` iterates over an order's token list and performs an unconditional `safeTransfer`/native-value send to a single beneficiary in one atomic loop. Because `order.inputs` is fully attacker-controlled at order-placement time (arbitrary token addresses, arbitrary count), a malicious order creator can include a token designed to permanently revert transfers to a specific address (or a beneficiary crafted to reject native ETH). When a solver fills such an order cross-chain, the `RedeemEscrow` message sent back to the source chain will always fail to deliver, permanently freezing not just the poisoned token but every other legitimately escrowed token bundled in the same order.

### Finding Description
`_fillCrossChain` lets any solver fill a cross-chain order defined entirely by the order creator, then dispatches a `RedeemEscrow` request back to the source chain naming the solver (`msg.sender`) as beneficiary and `order.inputs` (creator-controlled) as the token list to release:
```solidity
_post(
    order,
    _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
    options.relayerFee,
    nativeFee
);
```
On the source chain, `onAccept` routes `RedeemEscrow`/`RefundEscrow` to `_withdraw`:
```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    ...
    for (uint256 i; i < len; i++) {
        ...
        if (token == address(0)) {
            _sendValue(beneficiary, amount);
        } else {
            IERC20(token).safeTransfer(beneficiary, amount);
        }
    }
    ...
}
```
There is no per-token failure isolation: a single reverting transfer (a token that blacklists the solver's address, a token that unconditionally reverts transfers to a chosen victim, or a fee-on-transfer/pausable token) reverts the entire loop, and thus the entire `onAccept` call.

`EvmHost.dispatchIncoming` wraps this call in a low-level `.call` and deletes the request receipt on failure specifically "so it can be retried" — this is the exact permissive-retry pattern the external report recommends. However, that mitigation only helps for *transient* failures. Here the failure condition is deterministic and attacker-chosen at order-placement time, so every relayer retry of the identical message fails identically forever. The message can never be delivered, `_filled[commitment]` is never finalized, and the tokens held in `_orders[commitment][...]` for every token in the order (including perfectly good ones like USDC/DAI) remain locked with no alternate recovery path, since the only way out of escrow is through this same `_withdraw` function.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged order creator against any solver who chooses to fill their order: the solver has already paid out real output tokens on the destination chain (per `_fillCrossChain`'s upfront `safeTransferFrom`/`_sendValue` to the beneficiary) but can never redeem the escrowed input tokens on the source chain. It also generally freezes protocol/user funds that are batched into the same order alongside the poison token, and the funds cannot be recovered by governance either since `SweepDust`/normal params updates do not touch `_orders[commitment][token]` balances (only `withdraw`/`_withdraw` does, and that always reverts for this commitment).

### Likelihood Explanation
Trivial and cheap to execute: an attacker only needs to deploy one custom ERC-20 (or use an existing blacklist-capable token that they can get the target solver blacklisted on) and include it as one of possibly several `order.inputs`, alongside legitimate high-value tokens, to bait a solver into filling. No privileged role is required, and the attack is fully attacker-timed (the token's blocking behavior can even be a targeted precondition, e.g., only reverting once a specific solver address is observed as the fill sender).

### Recommendation
Make `_withdraw`'s per-token release resilient to individual transfer failures instead of all-or-nothing:
- Use a low-level `call` (like the pattern already used in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw`/`SweepDust` functions) with `try/catch` or checked low-level calls per token, and on failure record the amount as unredeemable/recoverable-later (e.g., a per-beneficiary pull-based claim mapping) rather than reverting the whole batch.
- Alternatively, isolate each token transfer in its own external call via a minimal proxy/dispatcher so a revert in one token transfer cannot roll back the others, and expose a separate sweep/claim path for stuck balances.
- Ensure any such fallback still finalizes `_filled[commitment]`/marks the message delivered so the ISMP message is not retried forever against a deterministic failure.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer`/`transferFrom` always reverts when `to == <any address that later calls fillOrder>` (or simply always reverts for a hardcoded/blacklisted set of addresses updated by the attacker before the solver's fill lands).
2. Attacker places a cross-chain `Order` with `order.inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: 1} ]`, targeting a destination chain, with valid output assets to entice fills.
3. A solver fills the order via `fillOrder` → `_fillCrossChain`, transferring the required output tokens to the beneficiary and dispatching `RedeemEscrow` with `beneficiary = solver`, `tokens = order.inputs` (both USDC and EvilToken).
4. Relayer delivers the `RedeemEscrow` POST request to the source chain; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`, which succeeds transferring nothing yet (loop starts at i=0 with USDC succeeding) then reverts on `EvilToken.transfer(solver, 1)`.
5. `dispatchIncoming` catches the low-level call failure, deletes `_requestReceipts[commitment]`, allowing retry — but every subsequent retry hits the same deterministic revert.
6. The solver never receives their USDC redemption; both USDC and EvilToken remain frozen in `_orders[commitment][...]` permanently, while the solver has already paid the destination-side output tokens with no recourse.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
