### Title
Webhook `shop-domain` header is trusted for tenant identity without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain` header (and `topic`/`webhook-id`/`api-version` headers) to build the `WebhookMetadata` passed to the host app's handler. None of these headers are covered by the HMAC signature, so the tenant identity delivered to the app's business logic is not bound to the value that was actually authenticated.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` (which in turn calls `verifiable_query.to_signable_string`, i.e. the raw body), and then immediately forwards `request.shop`, unauthenticated, into the handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the signature purely from `to_signable_string` (the body) and the app's `client_secret`: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(client_secret, body ∥ shop)`, i.e. the shop the app believes the event came from must be cryptographically bound to the signature. Instead the actual binding enforced is `hmac == HMAC(client_secret, body)` while `shop` used by the app is read from a plain, unsigned header. This is structurally the same class of bug as the ERC4626 report: a value used downstream by business logic (`shop`, analogous to "price per share") is not actually derived from/verified against the value that was cryptographically committed to (the HMAC, analogous to the correctly-bound on-chain conversion). Here the field consumed (`shop-domain` header) is simply not covered by the HMAC at all.

Because Shopify signs webhooks per-app using the single, app-wide `client_secret` — the same secret is used for every shop that installs the app — an attacker who controls their own (possibly free/dev) shop that has the target app installed will receive legitimately-signed webhooks from Shopify for their own shop, with a valid `hmac-sha256` header computed over the body with that app's `client_secret`. Since the HMAC only covers the body and not the `shop-domain` header, the attacker can replay that exact body + HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming a victim shop. `Utils::HmacValidator.validate` still returns `true` (body and signature match), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
Any host application logic that uses `WebhookMetadata#shop` to select which tenant's records to update, delete, or otherwise act on (a very common pattern for webhook handlers, e.g. `customers/redact`, `shop/redact`, order/product sync, data deletion) can be tricked into performing that action against a shop the attacker does not own. This is a cross-tenant access primitive: the gem's own webhook-processing API delivers attacker-controlled tenant identity to the host application under the false guarantee that it passed HMAC authentication.

### Likelihood Explanation
Exploitation only requires the attacker to install the same app on a shop they control (many apps allow free installs/dev stores), capture one legitimately signed webhook, and replay it with a forged `shop-domain` header — no access to `client_secret`, access tokens, or victim credentials is needed. The `HmacValidator`/`Registry.process` path gives no indication that only the body is authenticated, which makes this easy to trigger against any app built on this gem's webhook registry.

### Recommendation
Include the `shop`/`shop-domain` (and ideally `topic`) values in the signable content that `HmacValidator` verifies, or otherwise cryptographically bind them to the request before trusting `request.shop` in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and that host apps must independently verify the shop against their own session/install records before acting on it, since today `Webhooks::Request#to_signable_string` silently implies the entire request (including headers) has been verified.

### Proof of Concept
1. Install the vulnerable app on attacker-owned Shop A; trigger any webhook topic the app subscribes to. Shopify sends a POST with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`, and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Capture the raw body and the `hmac-sha256` header value.
3. Replay the identical body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb#L26-31`) succeeds because it only checks the body against the HMAC. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-200`) invokes the app handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the app to act on behalf of the victim tenant despite the attacker never having compromised or interacted with that tenant.
