### Title
Webhook `shop` and `topic` identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that the body's HMAC matches, then dispatches the handler using the unverified `shop` and `topic` header values [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(shop || topic || body, client_secret)`, i.e., the tenant identifier (`shop`) and event type (`topic`) that the handler acts on should be cryptographically bound to the same signature that authenticates the payload. Instead, the actual binding implemented is `hmac == HMAC(body, client_secret)` only [4](#0-3) , with `shop`/`topic` sourced from `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers that are never part of the signed material [5](#0-4) .

Because the same `client_secret` is shared across every merchant install of a public app, and the app developer/attacker can install their own copy of the app on their own Shopify dev store (an unprivileged, non-victim tenant), they can legitimately trigger a webhook and capture a valid `(raw_body, hmac)` pair signed by Shopify for their own store. Since `shop` and `topic` are not part of `to_signable_string`, this same `(raw_body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop and/or the `X-Shopify-Topic` header rewritten to a different topic. `Registry.process` will accept it as authentic and invoke the registered handler with `WebhookMetadata` carrying the attacker-chosen `shop`/`topic`, crossing the tenant boundary [6](#0-5) .

### Impact Explanation
This breaks the tenant isolation guarantee webhook consumers rely on: `Registry.process` is documented as verifying "the request did indeed come from Shopify" for the claimed shop before invoking the handler. Host applications commonly use `data.shop` directly to look up per-tenant records, apply per-tenant business logic (e.g., cancel subscription, deprovision, update order/inventory state) or attribute events to a specific merchant for billing/audit purposes. An attacker with only unprivileged access to their own store (no access token, no `client_secret`, no privileged account) can forge events attributed to any other merchant shop, which is a cross-tenant access primitive.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to have at least one legitimate, low-privilege installation of the same public app (trivial — anyone can install a public Shopify app on their own free dev store) to obtain a valid `(body, hmac)` pair, and knowledge/replay of the app's public webhook URL (typically documented/discoverable). No secrets need to be leaked; only header manipulation on an HTTP POST is required.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`/`api_version`) in the material verified against the HMAC, or independently verify that `request.shop` corresponds to a shop with an active, known installation/session before dispatching the handler, rather than trusting the `X-Shopify-Shop-Domain` header at face value once only the body HMAC has been validated.

### Proof of Concept
1. Attacker installs the target public app on their own Shopify dev store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(B, client_secret)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the valid HMAC value.
4. Attacker crafts a new POST to the app's public webhook endpoint using the same body `B` and the same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [7](#0-6) ; `Utils::HmacValidator.validate` recomputes `HMAC(B, client_secret)` from `to_signable_string` (which ignores headers) and it matches, so validation passes [8](#0-7) .
6. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, `topic` as forged [9](#0-8) , causing the host application to act on data attributed to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
