I found a solid analog. The `hyper-fungible-token` pallet's calldata execution path mirrors the trailer-promotion bug class: an untrusted, out-of-band field (`message.data`/`substrate_data`) that is not covered by the message's own delivery authentication gets promoted to determine the *origin* used for a privileged runtime dispatch, in a way that a signature-optional fallback silently trusts attacker-supplied routing data.### Title
Unsigned cross-chain calldata dispatches a runtime call using an unauthenticated body field as the signer origin - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `IsmpModule::on_accept` decodes an ABI-encoded `Message` from `PostRequest.body` and, when the message carries optional calldata (`message.data`) with **no signature attached**, dispatches an arbitrary `RuntimeCall` using `RawOrigin::Signed(origin)` where `origin` is derived purely from `message.from` — a plain data field inside the ABI-encoded body, not a value covered by any signature check in that code path. [1](#0-0) 

### Finding Description
`on_accept` authenticates only that the *contract* which dispatched the request (`source`, `from` at the `PostRequest` level) is a registered bridge module via `ContractToAsset::<T>::get(source, &from)`: [2](#0-1) 

That check authenticates the module/contract identity, not any per-transfer user identity. The per-transfer identity used to authorize a privileged action later — `message.from` — lives *inside* `body`, an application-level payload that is opaque to the ISMP consensus/state-proof layer. It is the pallet's equivalent of an HTTP trailer field: it arrives after the part of the message that is actually checked against a trust anchor (the registered contract mapping), and the pallet nonetheless promotes it to carry origin-level trust when calldata execution is requested without a signature:

```rust
let origin = if let Some(signature) = substrate_data.signature {
    // ... verifies signature against beneficiary_bytes / recovers eth address
    beneficiary.clone()
} else {
    let from_bytes = message.from.as_ref();
    // origin derived directly from message.from with NO cryptographic check
    ...
};
...
runtime_call.dispatch(RawOrigin::Signed(origin.clone()))...
``` [3](#0-2) 

In the signed branch, the code verifies a real signature (Ed25519/Sr25519/Ecdsa) over `(nonce, runtime_call)` and requires the recovered key to match `beneficiary` (derived from `message.to`), which is a sound authorization for dispatching `runtime_call` as `beneficiary`. In the unsigned branch, however, there is **no cryptographic proof at all** binding `message.from` to authorization of `runtime_call` — the pallet simply trusts that whichever EVM/other bridge contract emitted this `PostRequest` set `message.from` correctly (i.e., equal to the real `msg.sender` on the source chain). That invariant is enforced (if at all) entirely by the source-chain contract implementation(s) registered in `ContractToAsset` (`HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, and their upgradeable variants), not by anything the destination pallet itself verifies. This is precisely the "trailer promoted into headers" bug class: a field that looks authoritative because it sits next to authenticated data is treated as if it went through the same authentication as the signature path, while it is really an unauthenticated convenience field whose trustworthiness depends entirely on an out-of-scope component (the specific source contract's enforcement of `from == msg.sender`, which was not verifiable within this review).

### Impact Explanation
If any currently or future registered source-chain module (any contract mapped in `ContractToAsset`) allows `message.from` to diverge from the actual caller (e.g., a permissioned relay path, a wrapped/legacy contract, or a future integration that forwards `from` on behalf of a third party), an unprivileged party can cause a `RuntimeCall` to be dispatched on Hyperbridge as an arbitrary `AccountId` with no signature check — an unauthorized privileged action (CWE-444-style request/authorization smuggling). Because `BaseCallFilter` still applies, the blast radius depends on which calls are filtered, but any allowed call (transfers, approvals, governance-adjacent extrinsics not blocked by the filter) executed under an arbitrary origin is a serious unauthorized-action primitive.

### Likelihood Explanation
Exploitability hinges entirely on whether every registered bridge contract strictly enforces `message.from == msg.sender` for all code paths that can produce a `PostRequest` accepted by this module. I was unable to confirm this invariant from the Solidity sources within the available search budget (`HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, and upgradeable variants were located but not read in full). If that invariant fully and permanently holds across every current and future registered contract, the practical exploitability of this exact bug is much lower, but the pallet still has zero independent verification of that assumption at the point of privileged dispatch — the same structural weakness as the blaze-server report (trusting an unauthenticated field for a security decision that should require explicit authentication).

### Recommendation
Do not derive a `RawOrigin::Signed` dispatch origin from `message.from` (or any other embedded/application-layer field) without an explicit signature check, mirroring the signed branch's design. If dispatching-as-sender-without-signature is intended, bind it cryptographically to a value the ISMP layer itself already authenticates (e.g., require it to equal the recorded original relayer/sender of the underlying token transfer, verified at the ISMP/consensus layer), rather than trusting a field inside `body` that only the source contract's implementation is relied upon to police.

### Proof of Concept
Not fully constructible without confirming the Solidity-side invariant on `message.from`; the concrete gap identified is: a `Message` with `data` set to `SubstrateCalldata { runtime_call, signature: None }` and an attacker-chosen `from` will cause `runtime_call.dispatch(RawOrigin::Signed(EvmToSubstrate::convert(from)))` to execute with zero signature verification, for any `from` value the emitting source contract is willing to place in the message body.
