## Analysis Result

### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator.validate`, but its `to_signable_string` returns only the raw HTTP body. The `shop` (and `topic`, `webhook_id`) values that `Registry.process` hands to the app's handler as trusted tenant identity are read straight from HTTP headers and never enter the signed material.

### Finding Description
`HmacValidator.validate` accepts any object implementing `VerifiableQuery` and checks `HMAC(secret, obj.to_signable_string) == obj.hmac`: [1](#0-0) 

For OAuth callbacks, `AuthQuery#to_signable_string` correctly folds `shop` (and `host`, `state`, `code`, `timestamp`) into the signed string, so the shop identity is cryptographically bound to the signature: [2](#0-1) 

For webhooks, however, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) [4](#0-3) 

`shop`, `topic`, and `webhook_id` are all pulled directly from attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), not from the signed body. `Registry.process` validates only the HMAC over the body, then forwards the *unsigned* header-derived `shop` value straight to the app's handler as trusted tenant metadata: [5](#0-4) 

This breaks the intended equality: "the shop the HMAC authenticates" should equal "the shop the handler acts on," but the gem only guarantees "the HMAC authenticates the body bytes," while "the handler acts on the header-supplied shop." Any request whose body bytes match a previously-observed valid `(body, hmac)` pair — regardless of which shop actually produced it — will pass `HmacValidator.validate` and be dispatched with an attacker-chosen `shop`, `topic`, and `webhook_id`.

### Impact Explanation
An unprivileged internet user who is an actual (even trial/free) merchant of the host app can:
1. Register their own store with the app and trigger a legitimate webhook (e.g., `orders/create`) to their own callback URL, capturing the exact `raw_body` and its `X-Shopify-Hmac-Sha256` value (they control the receiving endpoint/network, so this is trivial to intercept).
2. Replay that exact `(raw_body, hmac)` pair to the app's shared webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain.
3. `HmacValidator.validate` succeeds because it only checks the body bytes, and `Registry.process` calls the handler with `shop: <victim-shop>`.

If the host application uses `WebhookMetadata#shop` to look up sessions, apply tenant-scoped mutations, or route data (which is exactly the documented usage pattern in `docs/usage/webhooks.md`), this enables cross-tenant data confusion/manipulation using only self-service access to the app — no leaked credentials, no `api_secret_key`, no privileged role required. This matches the Critical category "cross-tenant access."

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem's documented webhook pattern: the attacker only needs to be a legitimate (even free-trial) merchant of the target app to generate one valid signed payload, and standard HTTP tooling to replay it with modified headers. No exploitation of Shopify's own infrastructure or secrets is required — the weakness is entirely in this gem's failure to bind `shop`/`topic`/`webhook_id` into the signed material it exposes as trustworthy metadata.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for webhook HMAC verification if a scheme change is possible, or — more compatibly — have `Registry.process` cross-check the header-derived `shop` against tenant state already known to the host app (e.g., require a session lookup keyed by `shop` to succeed before trusting the payload) and document clearly that the raw-body HMAC alone does not bind `shop`/`topic`/`webhook_id`. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is unauthenticated header data and must not be used alone to select tenant-scoped credentials/records.

### Proof of Concept
```ruby
# Attacker is a real merchant of the host app, using shop "attacker.myshopify.com"
# Step 1: attacker triggers any webhook to their own endpoint and captures:
raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
# (api_secret_key is the APP's secret, shared across all shops using this app;
#  attacker never sees it, but Shopify legitimately signs their own webhook with it)

# Step 2: attacker replays the exact same body+hmac to the shared webhook endpoint,
# forging the shop-domain header to point at a victim tenant:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true because to_signable_string == raw_body only.
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now processes data.body as if it belongs to victim-shop.myshopify.com.
``` [6](#0-5) [7](#0-6)
