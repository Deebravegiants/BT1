### Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The `Webhooks::Request` HMAC validation binds the signature only to the raw request body, while the `shop` (and `topic`/`webhook_id`) values that `Registry.process` passes to the app's webhook handler are read from unauthenticated HTTP headers. A holder of any validly-signed webhook payload for their own shop can replay it with a different `shop-domain` header and have the app process it as if it belonged to another tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, which are never included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` taken straight from the unauthenticated header, handing it to the app's registered handler without any cross-check against the signed body: [4](#0-3) 

The identity binding that is broken is: `shop_header == shop_bound_by_hmac`. In reality, `shop_bound_by_hmac` does not exist — only the body is bound. An attacker who is a legitimate merchant/app-installer for Shop A receives genuine, correctly-signed webhook deliveries (valid `hmac`, valid `raw_body`) for Shop A. Because the signature never covers the `shop-domain` header, the attacker can resend that exact signed payload to the app's webhook endpoint while substituting a different value in the `shopify-shop-domain` header (e.g., Shop B, a victim tenant). `Utils::HmacValidator.validate` still succeeds because the body is unchanged, and `Registry.process` passes the attacker-chosen `shop` value into the handler, which typical app implementations use to scope database writes/reads to a tenant.

### Impact Explanation
This is a cross-tenant boundary violation: an unprivileged/1st-party-but-limited actor (any merchant who has installed the app and can receive their own real webhooks) can cause the app to attribute webhook data to a different merchant's tenant record. Depending on the handler's semantics (e.g., `orders/create`, `app/uninstalled`, `shop/update`), this can corrupt or leak another tenant's state, or trigger tenant-scoped side effects (like disabling/altering another shop's data) — matching the "cross-tenant access" Critical impact category, since the vulnerability lives entirely in this gem's trust boundary between the cryptographically verified bytes and the header value the app is handed.

### Likelihood Explanation
Likelihood is moderate to high for any app that trusts `WebhookMetadata#shop` from `Registry.process` for tenant scoping (the documented and expected usage pattern) without independently re-verifying the shop via a stored, tenant-bound session or a separate authenticated channel. The only prerequisite is that the attacker be a legitimate webhook recipient for at least one shop (trivial to obtain by installing/publishing a test app or observing their own shop's webhook traffic), then replay the payload with a modified header — no access to `api_secret_key` or any victim credential is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body before exposing `WebhookMetadata#shop` to handlers. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used for tenant-scoped lookups without additional verification (e.g., cross-checking against the shop domain embedded in the parsed body, when available, or against a known/allow-listed shop store).

### Proof of Concept
1. Attacker installs the app for `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of BODY using api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: abc-123

   BODY (raw JSON as received)
   ```
2. Attacker resends the exact same request to the app's webhook endpoint, changing only:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   leaving `x-shopify-hmac-sha256` and `BODY` untouched.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `BODY` only and it matches, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the app's handler with `shop: "victim-shop.myshopify.com"`, even though the payload was never signed for that shop — the app processes attacker-controlled `BODY` data under `victim-shop`'s identity.
