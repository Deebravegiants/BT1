### Title
`Webhooks::Request#topic` (and `#shop`) are read from unsigned headers while only the raw body is HMAC-verified, allowing header relabelling/replay of a legitimately-signed webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Registry.process` authenticates a webhook solely via `Utils::HmacValidator.validate(request)`, which checks the signature against `request.to_signable_string` (the raw body only). `request.topic` and `request.shop` are read straight from the `shopify-topic`/`x-shopify-topic` and `shopify-shop-domain`/`x-shopify-shop-domain` headers, which are not part of the signed material. An attacker who legitimately receives one validly-signed webhook body from their own shop can resend that exact body with a different `topic` and/or `shop-domain` header and it will still pass HMAC validation, causing the registry to dispatch to a different handler and/or attribute the payload to a different shop identity.

### Finding Description
The invariant the question asks to check is:
`HMAC-verified content == content used to select the handler and the shop identity`

Tracing the code:
- `Request#initialize` normalizes headers and only requires that `topic`, `hmac-sha256`, and `shop-domain` headers exist; it does not tie them together cryptographically. [1](#0-0) 
- `Request#hmac` and `Request#topic`/`#shop` are both simple header reads via `shopify_header`, with no cross-check between them. [2](#0-1) 
- `Request#to_signable_string` returns only `@raw_body`. [3](#0-2) 
- `Registry.process` validates the HMAC over that raw body, then uses the unsigned `request.topic` to select the handler out of `@registry`, and constructs `WebhookMetadata` using the unsigned `request.shop` alongside the body. [4](#0-3) 

Because the HMAC (`X-Shopify-Hmac-SHA256`) only covers the raw body, the `topic` and `shop-domain` headers can be freely relabelled on a resend of a body the attacker legitimately obtained (e.g., from a webhook Shopify sent to the attacker's own development shop) without invalidating the signature. There is no nonce, timestamp, or delivery-id binding that ties a given signed body to the topic/shop it was originally delivered under, so the same signed body can be replayed under an arbitrary registered topic, causing the wrong handler to run, or under an arbitrary `shop-domain`, causing the body to be attributed to a different shop identity than the one Shopify actually signed it for.

No existing guard closes this gap: `HmacValidator.validate` only checks the body signature (confirmed by its sole use in `Registry.process`), and there is no `ShopValidator.sanitize!`, JWT `aud`/`sub` check, or delivery-id/timestamp check anywhere in this webhook path.

### Impact Explanation
An attacker who has received one validly-signed webhook body (from their own shop, which they fully control by installing their own app instance) can:
1. Replay it under a different `x-shopify-topic` header to force dispatch to a handler that was never intended to process that body content (handler confusion/authentication-bypass class: "forged webhook ... accepted" as an event of an attacker-chosen topic).
2. Replay it under a different `shop-domain` header, causing `WebhookMetadata.shop` to be populated with a shop identity not actually authenticated by Shopify for that payload — a cross-tenant identity-confusion primitive, since `request.shop` is the value app code typically uses to select which merchant's session/state to act on.

This directly breaks the "SINGLE IDENTITY" invariant: the shop identity consumed downstream (`request.shop`) does not come from the same authenticated source as the HMAC-verified content (the raw body). Whether this escalates to actual "theft of an Admin API access token" depends on host-app logic outside this gem (e.g., if a handler looks up and acts with a session/access token keyed off `request.shop`), so the concretely provable impact from this gem alone is the cross-tenant/authentication-bypass class, not a direct token exfiltration.

### Likelihood Explanation
Precondition: the app registers at least two webhook topics (a trivial, common configuration). Attacker cost is low — they need only their own development shop and app installation to legitimately receive one signed webhook, which is explicitly allowed under the stated threat model. The relabelling requires no secret, no TLS interception, and is repeatable indefinitely against any body/topic/shop combination the attacker has previously received a valid signature for.

### Recommendation
Bind the `topic` and `shop-domain` (and ideally `webhook-id`) values into the signable string that is HMAC-verified, or otherwise cryptographically tie the signature to those header values (e.g., verify against a canonical string that includes topic/shop/webhook-id, not just the raw body), so that relabelling any of these headers invalidates the HMAC.

### Proof of Concept
```ruby
# test/webhooks/registry_relabel_test.rb
require "test_helper"

class RegistryRelabelTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Webhooks::Registry.clear
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  end

  def test_topic_relabel_bypasses_intended_handler_binding
    called_with = []
    handler_a = Class.new { define_method(:handle) { |data:| called_with << ["A", data.topic] } }.new
    handler_b = Class.new { define_method(:handle) { |data:| called_with << ["B", data.topic] } }.new

    ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http, path: "/x", handler: handler_a)
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "carts/update", delivery_method: :http, path: "/y", handler: handler_b)

    raw_body = '{"id":1}'
    hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", ShopifyAPI::Context.api_secret_key, raw_body)).strip

    # Signature is only over raw_body -> valid for ANY topic header
    request_orders = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: { "x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => hmac, "x-shopify-shop-domain" => "victim.myshopify.com" },
    )
    request_carts = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: { "x-shopify-topic" => "carts/update", "x-shopify-hmac-sha256" => hmac, "x-shopify-shop-domain" => "victim.myshopify.com" },
    )

    ShopifyAPI::Webhooks::Registry.process(request_orders)
    ShopifyAPI::Webhooks::Registry.process(request_carts)

    # Same signed body dispatched to BOTH handlers because topic (and shop) are not covered by the HMAC
    assert_equal [["A", "orders/create"], ["B", "carts/update"]], called_with
  end
end
```
This demonstrates that the same signed `raw_body` is accepted for two different, attacker-relabelled `topic` headers (and an attacker-relabelled `shop-domain`), proving the equality `HMAC-verified content == handler/shop-selection input` does not hold.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
