### Title
Webhook HMAC covers only the request body, not the `shop`, `topic`, or `webhook-id` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw body alone, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop`, `topic`, and `webhook-id` headers to route and label the payload delivered to the app's handler. Any principal who can obtain one valid `(body, hmac)` pair signed with the app's `api_secret_key`—for example by installing the app on a shop they control and capturing a webhook Shopify sends them—can replay that exact body/HMAC pair to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain. The HMAC check still passes because it never covers the header, so the handler executes attacker-supplied JSON content under the identity of a different, victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` signs/compares only `verifiable_query.to_signable_string`, i.e. only the body, using the app-wide `api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly that body-only HMAC check and then hands the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values straight to the registered handler as trusted tenant-identifying metadata: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes the handler treats as authoritative for (shop, topic, webhook_id)`

Here it does not: the HMAC only authenticates the body, while `shop`, `topic`, and `webhook_id`—the fields the handler uses to decide *which tenant* and *which event* the payload belongs to—are taken from headers outside the signed material. Because the same `api_secret_key` (the app's single client secret) is used to sign webhooks for *every* installed shop, any shop that installs the app can capture a legitimately-signed `(body, hmac)` pair from a webhook Shopify sent to them, then re-POST that identical body/HMAC to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header pointing at a different, victim shop. `Utils::HmacValidator.validate` will accept it, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the victim's shop, delivering attacker-influenced JSON body content under that identity.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: `HmacValidator.validate` succeeds ("authenticated"), yet the `shop` value the application logic keys off is fully attacker-controlled. Any downstream code that follows this gem's documented pattern (`ShopifyAPI::Webhooks::Registry.process` → handler keyed by `data.shop`) will process, store, or act on forged data attributed to a shop the attacker doesn't own — i.e. cross-tenant access/injection, which is one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Reaching the webhook endpoint only requires being an unprivileged internet user who can install the app on a shop they control (a normal, unprivileged install flow) and can reach the app's public webhook HTTP endpoint — both are standard capabilities of any merchant using the app, with no access token, `api_secret_key`, or privileged account required. Producing at least one attacker-influenced JSON body under a topic the attacker can trigger (e.g. `products/update` with a controlled title/description) and capturing its legitimate `x-shopify-hmac-sha256` value is straightforward once the app is installed on the attacker's own shop.

### Recommendation
Include the identity-binding fields in the signed material, or otherwise cryptographically bind `shop`/`topic`/`webhook_id` to the verified body before trusting them — e.g. compute/verify the HMAC over a canonical string that includes the shop domain and topic (not just the raw body), or independently confirm (via a separate authenticated channel, such as querying the Admin API with a session already known for that shop) that the shop asserted in headers actually owns the webhook subscription/`webhook_id` before dispatching to a handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (unprivileged action) and triggers a webhook-eligible event with attacker-chosen content, e.g. updates a product description to arbitrary JSON-safe text, causing Shopify to POST a `products/update` webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over that body using the app's `api_secret_key`.
2. Attacker records the exact `raw_body` and `x-shopify-hmac-sha256` value from that request.
3. Attacker sends a new POST to the same webhook endpoint with the identical `raw_body`/`x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-webhook-id`/topic the victim is registered for).
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) passes because it only checks the body against the secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, causing the host application to process attacker data under the victim tenant's identity.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
