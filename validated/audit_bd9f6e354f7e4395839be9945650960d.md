Key finding: `calldataHash1` includes `circomData.externalActionData` in full via `abi.encode(... circomData.externalActionData ...)` at [1](#0-0) , and `formInputEmporiumMin` includes `circomData.calldataHash` as a public input constrained by the proof: [2](#0-1) . Since `externalActionData.externalActionMetadata` (the encoded `EmporiumStack`, including all `ops`) is part of `externalActionData`, it is folded into `calldataHash`, and `performHinkalChecks` independently recomputes `getHashedCalldata(circomData)` and requires it equal `circomData.calldataHash` before calling `formInputForCircom`: [3](#0-2) . So the "min" proof path does not skip integrity-binding of the ops — the attacker cannot swap in an arbitrary `EmporiumStack` after generating a proof, because `calldataHash` (checked both on-chain via `getHashedCalldata` and via the circuit constraint on `calldataHash`) ties the proof to the exact `externalActionData` bytes supplied, including `ops`. This binding does not depend on any signature; it only requires the caller to supply a self-consistent `circomData`, which any unprivileged attacker can do for their own transaction.

However, the actual exploitable gap is independent of the "min circuit" framing: `EmporiumUpgradeable.runAction`'s `verifyWallet` performs **no signature check at all** when `stack.signerAddress == address(0)`: [4](#0-3) . In that branch it only marks the `emporiumMessage` as used and returns, so an attacker can freely craft `stack.ops` (arbitrary `endpoint`, `callData`, `value`) executed as `op.endpoint.call{value: op.value}(op.callData)`, with `msg.sender` inside that call being the Emporium contract itself: [5](#0-4) . This lets an attacker have Emporium make arbitrary external calls (including calls to ERC20 tokens/endpoints Emporium has approvals for, or self-calls into other flows) as long as they can pass `performHinkalChecks` (valid proof, valid root hash, valid nullifiers for their own UTXOs).

Regarding the specific claim about `erc20TokenAddresses.length == 0`: when the token array is empty, both `Hinkal.transact`'s per-token balance/slippage-equality loop [6](#0-5)  and `EmporiumUpgradeable.runAction`'s own `balancesBefore`/`balancesAfter` accounting loop [7](#0-6)  iterate zero times — meaning **no ERC20/ETH balance accounting or slippage/utxo-consistency check is performed for any token** in that transaction. This confirms the equality the question challenges (`assets Emporium can move in a tx == assets accounted in balancesBefore/balancesAfter`) is genuinely broken when `erc20TokenAddresses.length == 0`: the `ops` loop can still move value (`op.value`, arbitrary calls) with zero balance reconciliation, so any assets moved by `ops` are never accounted, never subject to `slippageValues` checks, and never converted into UTXOs (since `utxoSet` is also sized to `erc20TokenAddresses.length == 0`, so nothing is returned as change either — any drained tokens simply leave Emporium and are not tracked into the Merkle tree at all).

This gap does not depend on the "min circuit" vs "normal circuit" selection specifically — it applies to `HINKAL_EMPORIUM_ACTION_ID` transactions with an empty `erc20TokenAddresses` array regardless of which circuit variant is used, since both `Hinkal.sol`'s and `EmporiumUpgradeable.sol`'s per-token loops are driven by the same empty array in either case. The distinguishing behavior the question describes (using the min circuit to minimize proof cost while running the exploit) is a plausible optimization for the attacker but not the root cause; the root cause is that the accounting loops key on `circomData.erc20TokenAddresses`, which the attacker fully controls and can set to length zero regardless of circuit path.

I was unable to fully confirm within available tool budget (a) whether `MainEVMCircuit`/`MainEVMCircuitMin` circuits perform any additional signal constraints tying `ops` semantics beyond the calldata hash (i.e., I could not inspect `circuits/MainEVMCircuitMin.circom` contents), and (b) whether Emporium ever legitimately holds "parked" balances of tokens outside a single in-flight transaction (i.e., whether cross-transaction balances persist that an attacker's empty-array transaction could siphon) — I could not locate a deposit/park function for Emporium balances in the reachable snippets. Given the significant uncertainty about a persistent "parked balance" state to drain, and that the question's core premise about calldataHash binding to `externalActionMetadata` (via `externalActionData`) appears to hold (which counters part of the "attacker supplies arbitrary EmporiumStack independent of proof" framing), I cannot confidently assert the full exploit chain as described without further code (particularly the circuit files and any Emporium deposit/balance-tracking logic) that the current index/tool budget did not surface.

### Title
Emporium `runAction` skips all balance/slippage accounting when `erc20TokenAddresses.length == 0`, letting unsigned ops move value unaccounted - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `circomData.erc20TokenAddresses` is empty, both `Hinkal.transact`'s per-token accounting loop and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loop execute zero iterations, so no balance, slippage, or UTXO-consistency check applies to value moved by `stack.ops`. Combined with `verifyWallet` skipping signature verification entirely when `stack.signerAddress == address(0)`, an attacker can execute arbitrary `endpoint.call{value}(callData)` operations as Emporium with no accounting, provided they can still produce a valid proof/nullifiers for their own transaction.

### Finding Description
The broken equality: "assets Emporium can move in a tx" (governed by `stack.ops` executed unconditionally in the loop at `EmporiumUpgradeable.sol:91-118`) should equal "assets accounted in balancesBefore/balancesAfter" (computed only over `circomData.erc20TokenAddresses`, `EmporiumUpgradeable.sol:85-151`, and mirrored in `Hinkal.sol:97-147`). When the attacker sets `erc20TokenAddresses.length == 0`, both accounting loops vacuously pass with zero checks, while the `ops` loop still runs unconditionally and unsigned (`verifyWallet` returns immediately for `signerAddress == address(0)`, `EmporiumUpgradeable.sol:302-316`), so any value moved via `ops` (native ETH via `op.value`, or arbitrary token transfers triggered via `op.endpoint.call`) is never reconciled, never checked against `slippageValues`, and never converted to a tracked UTXO output.

### Impact Explanation
If Emporium ever holds a native ETH balance or has standing token allowances usable via `op.endpoint.call`, an attacker can drain that value through unsigned, unaccounted ops while presenting an otherwise valid (self-consistent) proof for their own UTXOs — this would be direct theft of protocol/relay-held or in-flight funds, matching Critical severity if a real "parked balance" state exists. Repeatable per transaction as long as an exploitable balance/allowance is available.

### Likelihood Explanation
Requires (a) Emporium contract to hold a balance or approval an attacker can call out to, and (b) the attacker to craft an `EmporiumStack` with `signerAddress == address(0)` and `erc20TokenAddresses.length == 0` while still satisfying `performHinkalChecks` (valid proof/nullifiers for their own funds). I could not confirm within this investigation whether such a persistent balance/allowance state exists in this codebase, which materially affects likelihood.

### Recommendation
Require `erc20TokenAddresses.length > 0` (or otherwise bound to the actual tokens touched by `stack.ops`) whenever `stack.ops.length > 0` in `EmporiumUpgradeable.runAction`, and/or require `stack.signerAddress != address(0)` (mandatory signature) for any op that is not a pure deposit, so unsigned/self-authorized op execution cannot bypass balance accounting.

### Proof of Concept
Foundry test: deploy Emporium, fund it with ETH/ERC20 (representing a "parked" balance from a prior legitimate flow), call `Hinkal.transact` with `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, a valid proof/nullifiers for attacker's own small UTXO, and an `EmporiumStack` with `signerAddress = address(0)` and one `op` calling `endpoint.call{value: parkedBalance}(...)` to transfer Emporium's ETH to attacker. Assert Emporium's balance before/after and attacker's balance before/after to show net gain with `balancesBefore`/`balancesAfter` arrays being empty (`length == 0`) throughout.
