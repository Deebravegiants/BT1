Based on my investigation, I found a genuine analog to the reported bug class in this repo.

### Title
`rootHashHinkalIndex` field of `CircomData` is used in a critical root-validity check but is never bound by `calldataHash`, `signedMessageHash`, or the circuit's public-input vector - (File: `contracts/Hinkal.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
`Hinkal.transact()` uses `circomData.rootHashHinkalIndex` together with `circomData.rootHashHinkal` to validate that the root the proof was generated against is a legitimate, existing root: [1](#0-0) . This index field is part of the `CircomData` struct [2](#0-1)  but, unlike essentially every other security-relevant field, it is never included in the integrity hash checked against `calldataHash`, never included in the EIP-712-style `signedMessageHash`, and never passed to the circuit as a public input.

### Finding Description
`calldataHash` is computed from two helper functions that enumerate the fields that must match `circomData.calldataHash` for the transaction to be accepted: [3](#0-2) . `rootHashHinkalIndex` does not appear in either list.

`signedMessageHash`, which is the value the user's EdDSA signature actually covers (verified inside the circuit via `SignatureVerifier`), is built from a separate, explicit field list that only includes `rootHashHinkal`, not `rootHashHinkalIndex`: [4](#0-3) .

The public input vector fed into the SNARK verifier (`formBasicInput`) likewise only forwards `circomData.rootHashHinkal`, never the index: [5](#0-4) .

Yet `rootHashHinkalIndex` is directly consumed by the on-chain root-existence check that gates whether a transaction is allowed to spend against a given root: [1](#0-0) . This is exactly the accepted analog pattern: a `CircomData` field that is acted upon on-chain but sits entirely outside `calldataHash`, `signedMessageHash`, and the public-input vector, so neither the prover's signature, the calldata-integrity check, nor the ZK proof constrain its value. A relay (or any party assembling/relaying the transaction, which per the rules must be treated as an unprivileged actor) can freely choose any `rootHashHinkalIndex` value at broadcast time without invalidating the proof or the signature.

### Impact Explanation
Because the index used to look up "does this root exist / is it recent enough" is unauthenticated, the security properties that `rootHashExists` is presumably meant to enforce (e.g., binding the accepted root to a specific, bounded-recency slot in a root-history ring buffer) cannot be relied upon to correspond to what the user/prover intended. If the root-history storage recycles slots (a bounded-size array/ring buffer is a very common Merkle-root-history pattern), an attacker/relay could pair a legitimately-existing (circuit-enforced) `rootHashHinkal` value with an attacker-chosen index that happens to also store that same hash value in a stale/recycled slot, defeating any freshness or uniqueness assumption `rootHashHinkalIndex` was designed to provide. Depending on the exact semantics of `rootHashExists` (which I could not fully inspect within the available tool budget), this could weaken the intended root-freshness guarantee used in double-spend prevention.

### Likelihood Explanation
Medium confidence. I confirmed with certainty, from the source, that `rootHashHinkalIndex` is entirely unconstrained by signature, calldata-hash, and circuit public inputs — this is a hard fact from the code. What I could not fully verify (due to running out of tool iterations) is the exact internal implementation of `rootHashExists` (i.e., whether the root-history storage is a bounded ring buffer that recycles slots, which would make this concretely exploitable, or an append-only unbounded array, which would make the missing binding a harmless implementation detail).

### Recommendation
Include `circomData.rootHashHinkalIndex` in the `calldataHash` computation (e.g., add it to `getHashedCalldata1`/`getHashedCalldata2` in `contracts/CircomDataBuilder.sol`) so a relay/prover cannot alter it independently of the rest of the signed/proven transaction data, or eliminate reliance on this out-of-band index entirely (e.g., derive the correct/expected index deterministically on-chain from `rootHashHinkal` itself).

### Proof of Concept
Not fully constructible without visibility into `rootHashExists`'s storage layout (ring buffer size/overwrite behavior), which I could not locate/read within the available tool budget. I recommend a follow-up session read `Merkle.sol`/`HinkalBase.sol` for the `rootHashExists` implementation to determine whether root-history slots are ever overwritten, which would convert this from a "field with a missing binding" observation into a concretely provable double-spend/root-bypass PoC.

```text
    function getSignedMessageHash(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData,
        uint256 emporiumMessage
    ) internal pure returns (uint256) {
        // split into two encode calls to avoid "stack too deep"
        uint256 hash1 = uint256(
            keccak256(
                abi.encode(
                    chainId,
                    verifyingContract,
                    circomData.rootHashHinkal,
                    _encodeTokenAddresses(circomData.erc20TokenAddresses),
                    _encodeAmountChanges(circomData.amountChanges),
                    circomData.timeStamp,
                    _flatUint256Matrix(circomData.inputNullifiers),
                    _flatUint256Matrix(circomData.outCommitments),
                    circomData.calldataHash,
                    emporiumMessage
                )
            )
        );
        uint256 hash2 = uint256(
            keccak256(
                abi.encode(
                    circomData.stealthAddressStructure.H1x,
                    circomData.stealthAddressStructure.H1y,
                    circomData.stealthAddressStructure.H0x,
                    circomData.stealthAddressStructure.H0y
                )
            )
        );
        return
            uint256(keccak256(abi.encode(hash1, hash2))) % CIRCOM_P;
    }
```
