### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is taken from unauthenticated HTTP headers while the HMAC only covers the raw body, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates covers only the raw request body, never the headers. Any attacker who can obtain one legitimately-signed webhook delivery (e.g. by installing the app on their own shop) can replay that exact signed body while substituting the `shop`/`topic`/`webhook_id` headers, and the signature check still passes.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body` — none of `topic`, `shop`, `api_version`, or `webhook_id` (all read straight from attacker-visible HTTP headers) are included in the signable string: [3](#0-2) 

`Utils::HmacValidator.validate` only ever HMACs `verifiable_query.to_signable_string`: [4](#0-3) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header value) straight into the `WebhookMetadata` handed to the host application's handler: [5](#0-4) 

The binding the library implicitly claims to provide is:
`HMAC_valid(body, api_secret_key) == true` ⇒ `(body, shop, topic, webhook_id, api_version)` all genuinely originated from Shopify for that shop.

In reality the equality that holds is only:
`HMAC_valid(body, api_secret_key) == true` ⇒ `body` was produced by an entity that received a signed delivery for *some* shop, at *some point* — it says nothing about `shop`, `topic`, `webhook_id`, since these fields never enter the signed string. The header-derived `shop` is trusted without being cryptographically bound to the signature that authenticates the request.

### Impact Explanation
Documented usage instructs host applications to key persistence and business logic off `data.shop` from `WebhookMetadata` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), per `docs/usage/webhooks.md`: [6](#0-5) 

An unprivileged attacker who legitimately installs the app on their own store (Shop A) will receive genuinely Shopify-signed webhook deliveries whose body content they fully control (e.g. by creating orders/customers/products in Shop A with attacker-chosen field values). Because the signature covers only the body, the attacker can retransmit that exact signed body to the app's webhook endpoint while changing the `X-Shopify-Shop-Domain` header to point at a victim's shop domain (Shop B). `Utils::HmacValidator.validate` still returns `true` since the body is unmodified, and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`. This lets the attacker inject arbitrary data into another tenant's records/business logic — a cross-tenant data-integrity breach that satisfies the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any app that (a) accepts multiple shop installations (the normal SaaS model) and (b) trusts `data.shop` from the handler to scope persistence, exactly as the gem's own documentation recommends. No secrets, tokens, or privileged access are required — only a standard, self-service app install on an attacker-owned store plus the ability to POST to the app's public webhook endpoint.

### Recommendation
Bind the shop (and other trust-relevant metadata such as topic) into the HMAC-verified material, or otherwise cryptographically tie them to the signed request instead of relying on unauthenticated headers:
- Include `shop-domain`, `topic`, `api-version`, and `webhook-id` header values in the string that is HMAC-verified (in addition to the body), so any header tampering invalidates the signature; or
- Cross-check the header-derived `shop` against an independently trusted source (e.g. the shop associated with the registered webhook subscription id fetched from Shopify) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (Shop A) and registers a webhook (e.g. `customers/create`).
2. Attacker creates a customer record on Shop A with attacker-chosen field values, causing Shopify to send a legitimately HMAC-signed webhook POST to the app's callback URL with body `B` and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request (they control the receiving endpoint) and replays it to the same app endpoint, keeping body `B` and the `X-Shopify-Hmac-Sha256` header identical, but changing `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (`= B`), which is unchanged, so validation succeeds: [7](#0-6) 
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker's chosen `body`, causing the host application to attribute attacker-controlled data to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
