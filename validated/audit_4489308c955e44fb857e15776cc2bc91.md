### Title
Solver-manipulable phantom-bid median lets a single bidder set `LiquidityPool.sellRate`/`buyRate` used verbatim by `quoteIntent()` to price real intents - (File: `sdk/packages/indexer/src/services/liquidityPool.service.ts`, `sdk/packages/sdk/src/protocols/intents/LiquidityEngine.ts`)

### Summary
The `indexed_rates` intent-quoting path prices real, fund-moving `IntentGateway` orders from `LiquidityPool.buyRate`/`sellRate`, an indexer-maintained "price oracle" that is itself derived, per leg, by a `weightedMedian` selection over solver-submitted phantom bids. Because the median is a *selection* (returns one bidder's exact value) rather than a blend, a solver holding over half of a leg's weighted inventory sets the leg's price verbatim, with no additional on-chain deviation check against any independent price source before that number is consumed to size a real order's `amountIn`/`amountOut`.

### Finding Description
`aggregatePhantomBids` weights each phantom bid by the bidding solver's own on-chain inventory of the leg's output token, then picks the price via `weightedMedian`, which is documented to "return one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim" [1](#0-0) . That per-leg median is turned into a `PhantomOrderPriceSnapshotV2` and then folded into the pair-level `LiquidityPool.sellRate`/`buyRate` by `updateLiquidityPools`/`mergeChainRowsIntoPool`, using only a depth-weighted mean across chains/legs — no comparison to any independent reference price [2](#0-1) .

`IntentGateway.quoteIntent()` on the SDK then defaults to this `indexed_rates` strategy, reading `LiquidityPool.buyRate`/`sellRate` directly via `LiquidityEngine.getBuyAndSellRates()` and using it, unguarded, to compute the `amountIn`/`amountOut` a caller uses to construct a real `placeOrder` [3](#0-2) . The docs confirm this is now the default quoting strategy with "no automatic fallback to another price source" [4](#0-3) .

Placing a phantom bid is unprivileged: any solver account can bid into a phantom order's window, and the only requirement to dominate the median is holding sufficient balance of the leg's output token on the destination chain at bid-aggregation time — inventory a solver fully controls and can size specifically to win the leg (e.g., temporarily inflating a balance, or bidding through an under-subscribed leg where few other solvers hold that token) [5](#0-4) . This is structurally identical to the reported class of bug: an unprivileged party pushes a favorable value into a price feed that a subsequent, economically consequential action (there: `executeOrder`; here: `quoteIntent`-derived order construction and fill) trusts directly.

### Impact Explanation
A solver that temporarily dominates a leg's weighted inventory can push `LiquidityPool.sellRate`/`buyRate` to an arbitrary value, verbatim, for that leg/direction. Any caller using `quoteIntent()`'s default `indexed_rates` strategy to construct a cross-chain intent will then size `amountIn`/`amountOut` off that manipulated rate. Because Intent orders escrow real user funds against the input amount and pay solvers real output amounts, a skewed rate can cause users to over-pay (excess captured by the same or a colluding solver filling the order) or can make legitimate orders unfillable/mispriced, i.e., a concrete "theft or freezing of funds" vector reachable purely by an unprivileged solver submitting bids into a permissionless phantom-order auction — no admin, governance, or off-chain-only compromise required.

### Likelihood Explanation
Likelihood is bounded by needing a leg where the attacker's solver inventory dominates the weighted median (i.e., an under-subscribed leg, or an attacker willing to temporarily concentrate inventory for the bid window) and by callers actually consuming the un-guarded `indexed_rates` default rather than pinning a strategy with independent checks. Given `indexed_rates` is the SDK's default quoting path with "no automatic fallback" [4](#0-3) , and phantom bidding is open to any configured solver account, this is a realistic, low-cost griefing/self-dealing vector on thinly-bid legs.

### Recommendation
Do not let a single bidder's weighted median move the published pool rate unbounded. Options: (1) bound the leg median's contribution to the pool rate by a maximum deviation from the pool's own recent trailing rate (an on-chain-style sanity/deviation check analogous to what the original report recommends for Pyth updates), (2) require a minimum number of independent, inventory-backed bidders before a leg's median is trusted for the pool rate, and (3) have `quoteIntent()`'s `indexed_rates` strategy cross-check the indexed rate against a secondary source (e.g., the Uniswap V4 or curve-based strategies already present in the codebase) and reject/flag quotes that diverge beyond a configurable threshold, rather than consuming the indexer value unconditionally.

### Proof of Concept
1. Attacker controls (or funds) a `SolverAccount` delegated per EIP-7702, and ensures no other verified bidder holds material inventory of leg `L`'s output token on the destination chain (realistic for a newly listed or thin pair).
2. Attacker submits a single phantom bid for order commitment `C`'s leg `L`, quoting an output amount far from fair value while holding non-trivial inventory of that leg's output token so the bid is not zero-weighted.
3. When the bid window closes, `aggregatePhantomBids`'s `weightedMedian` selects the attacker's bid verbatim as `medianPrice` for leg `L`, because it is the sole (or majority-weighted) surviving quote [6](#0-5) .
4. `updateLiquidityPools` folds this into the pool's `sellRate`/`buyRate` with no independent check [2](#0-1) .
5. A victim calls `IntentGateway.quoteIntent()` (default `indexed_rates` strategy) for that pair; `LiquidityEngine.getBuyAndSellRates()` returns the manipulated rate and the victim constructs and places a real order priced off of it [7](#0-6) , resulting in an unfair fill favorable to the manipulating solver.

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

### quoteIntent(params)

Quotes an intent from the latest aggregate pool buy or sell rate published by the indexer. The pool rate is depth-weighted from fresh chain samples. Pass token addresses directly—the SDK resolves their configured symbols and decimals. No `strategy` option is needed for indexed-rate quotes.
