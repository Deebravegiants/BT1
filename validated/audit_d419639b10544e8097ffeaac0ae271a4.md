### Title
Relayer withdrawal and other Hyperbridge-originated system requests dispatch with zero fee, leaving delivery incentivized only by an opt-in, governance-gated reward allowlist that defaults to "no reward" - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer`'s `withdraw` function (relayer fee withdrawal), `pallet-ismp-host-executive`'s `update_host_params`, and other Hyperbridge-originated dispatches (intents-coprocessor, token-governor) all call `dispatch_request` with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }`. This is structurally identical to the Symmetrical `liquidatePartyB` bug class: a code path exists (`liquidatePartyB`/relayer delivery) whose designed incentive (`liquidatorShare`/relayer fee) can be zero, leaving the permissionless actor responsible for completing the action with no economic reason to do so.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  dispatches a POST request instructing the destination host manager to pay out a relayer's accumulated fees, but attaches `fee: Default::default()` (zero) and `payer: [0u8; 32]`. The same zero-fee pattern is used by `update_host_params` in [2](#0-1)  for propagating critical host-manager configuration changes.

A remediation mechanism does exist: `pallet-relayer`'s `outbound_request.rs` module lets a relayer claim a reward for delivering a Hyperbridge-originated request, keyed by `source_module_id` [3](#0-2) . But this reward is **zero by default**, and "a module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs" — governance must explicitly call `set_outbound_request_delivery_reward(module_id, amount)` to enable it per module, as documented in [4](#0-3) . Until that governance action happens for a given `module_id` (e.g. the relayer pallet's own `MODULE_ID` used for fee withdrawals, or the host-executive `PALLET_ID` used for host-param propagation), delivery of these system messages carries zero incentive from either the standard fee path or the new reward path — exactly mirroring the `liquidatePartyB` else-branch that zeroes out `liquidatorShare`.

This is a governance-configuration gap rather than a code logic bug (the mechanism to fix it exists), but the default state today (per the source) is: zero-fee dispatch + zero-reward-until-explicitly-allowlisted, so relayer fee withdrawal requests and host param updates rely purely on altruistic/bot relaying, just like the original PartyB liquidation issue relied on liquidator bots when `liquidatorShare` was zero.

### Impact Explanation
If no relayer picks up a `withdraw` request (because it is unincentivized and no altruistic/bot relayer processes it), a relayer's already-accumulated fees remain undelivered/unpaid on the destination chain indefinitely — the `Fees` entry is zeroed at dispatch time on the source side regardless of delivery success [5](#0-4) , so a stalled delivery could strand the relayer's payout. Likewise, an un-delivered `update_host_params` request means critical host-manager parameter rotations (e.g., manager address changes) never reach the destination, potentially leaving destination hosts trusting a stale/compromised manager. Both are Medium-severity availability/fund-timing issues analogous to the Sherlock M-15 finding, not outright fund theft.

### Likelihood Explanation
Low-to-medium likelihood in practice: Hyperbridge explicitly runs its own relayer bots and documents this as the intended backstop (mirroring the sponsor's response in the original Sherlock issue), and the `OutboundRequestDeliveryReward` allowlist mechanism exists precisely to close this gap once governance enables it per module. However, until governance sets a non-zero reward for the relevant `module_id`s (relayer withdrawal `MODULE_ID`, host-executive `PALLET_ID`, intents-coprocessor/token-governor module ids), these dispatches remain unincentivized by design, so any period where a module is not yet allowlisted (e.g., right after deployment, or for newly added system modules) reproduces the exact "liquidator has no incentive" condition from the referenced report.

### Recommendation
Ensure `OutboundRequestDeliveryReward` is pre-configured (non-zero) at genesis/deployment for every Hyperbridge-originated system `module_id` — the relayer pallet's own withdrawal `MODULE_ID`, the host-executive `PALLET_ID`, intents-coprocessor, and token-governor — rather than relying on a post-deployment governance call, so there is never a window where these critical system messages are undelivered due to lack of incentive.

### Proof of Concept
1. Deploy Hyperbridge without calling `set_outbound_request_delivery_reward` for the relayer pallet's `MODULE_ID`.
2. A relayer accumulates fees and calls `Pallet::withdraw`, which dispatches a POST request with `FeeMetadata { fee: 0, payer: 0 }` [6](#0-5)  and zeroes the local `Fees` entry [7](#0-6) .
3. Since `OutboundRequestDeliveryReward[MODULE_ID] == 0` by default, `process_outbound_request_delivery_claim` rejects any claim with `OutboundRequestNoRewardConfigured` [8](#0-7) , and the standard fee path pays zero — no relayer has an on-chain economic incentive to deliver the withdrawal request to the destination.

```markdown
A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

## The shape of the solution

The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.

No changes to pallet-hyperbridge or to any of the system-message dispatch sites. The reward is decoupled from the dispatch path and paid out at claim time against a destination state proof.
```
