The webhook signature‑verification flow in this gem repeats the SimplePriceOracle bug class exactly: **a value that the app trusts as an identity/tenant binding is not covered by the value that is cryptographically verified.**### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, enabling cross‑tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC‑signed content solely from the raw request body, while the `shop` (tenant identifier), `topic`, `webhook_id`, and `api_version` are all taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then dispatches the handler using the unsigned `shop` header value, which the gem's own documentation instructs developers to use as the tenant key. This is the same class of bug as the `SimplePriceOracle` report: a value that is acted upon (here, tenant attribution) is not included in the data that is cryptographically verified (the HMAC).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from HTTP headers that are never included in the signed string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body) and compare it to the `hmac` header value — the `shop` header plays no role in the equality check: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately builds `WebhookMetadata` using `request.shop`, the same unauthenticated header, and forwards it to the developer's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_header == shop_that_produced(raw_body, hmac)`

But the code only proves:
`hmac == HMAC(secret, raw_body)`

Nothing ties the `shop` header to the same origin as the body/HMAC. Consequently, an attacker who possesses one valid `(raw_body, hmac)` pair for their own shop (any merchant who installs the app receives genuinely Shopify‑signed webhooks) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. The HMAC check still passes because it never inspects the header, and `Registry.process` calls the handler with `shop: <victim shop>`.

This is exacerbated by the gem's own documentation, which explicitly instructs developers to key their persistence/queuing logic off `data.shop` without any warning that it is unauthenticated: [5](#0-4) 

Because the host application is following the gem's documented, recommended pattern (not ignoring it), this is not excluded by the "host app ignoring documented API" carve‑out.

### Impact Explanation
This breaks the tenant boundary that the webhook system is supposed to enforce: an app built with this gem's documented `data.shop` pattern can be made to process/store/enqueue a webhook body as though it belongs to a different, victim shop than the one that actually produced it. This is a cross‑tenant confusion/injection primitive — data associated with the attacker's own shop event can be attributed to an arbitrary other merchant record recognized by the host app, satisfying the "cross‑tenant access" criterion for Critical impact.

### Likelihood Explanation
Likelihood is moderate-to-high for any developer following the documented pattern: the attacker needs only (1) to be a legitimate merchant able to install the app and thereby receive at least one genuinely signed webhook (trivial, self-service), and (2) to know or guess a victim shop's `.myshopify.com` domain (public information). No access to `api_secret_key`, tokens, or privileged accounts is required — this is exploitable by any unprivileged internet user who can install the target app on their own store.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed content, or otherwise cryptographically bind `shop` to the verified payload — e.g., verify that `shop` matches a `myshopify_domain`/tenant field embedded within the JSON body itself (which is covered by the HMAC), rather than trusting the header value directly. At minimum, update `HmacValidator`/`Request#to_signable_string` so the signature check covers the header used for tenant attribution, and update the documentation to warn that `data.shop` must be corroborated against signed body content before being used as a tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the genuine Shopify request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H == HMAC_SHA256(secret, B)`).
2. Replay a forged HTTP POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since HMAC only covers body)
   - `x-shopify-shop-domain: victim.myshopify.com` (attacker-controlled/forged)
   - `x-shopify-topic`, `x-shopify-webhook-id` optionally forged too, since none are covered by the HMAC.
3. `HmacValidator.validate` succeeds because it only checks `B` against `H`.
4. `Registry.process` calls the registered handler with `WebhookMetadata` whose `shop` field is `victim.myshopify.com`, per [6](#0-5) , causing the host app (following the documented pattern in `docs/usage/webhooks.md`) to process attacker-controlled data under the victim tenant's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
