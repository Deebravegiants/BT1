### Title
Attacker-controlled route venue executes arbitrary contract code inside the caller's signed authorization tree, enabling wallet-token theft via a poisoned swap route - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy verbs (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) forward caller-supplied `swap: Bytes` route bytes to the swap aggregator. Route instructions address venue "pool" contracts by index into a caller-supplied `assets` registry, with no allowlist on the invoked address. An arbitrary attacker-deployed contract named as a hop pool is invoked mid-transaction while the caller's `require_auth` entry is still active, so any `token.transfer(victim, attacker, amount)` issued by the rogue pool is recorded as a required sub-invocation under the victim's signed auth tree. A victim who signs the simulation-produced tree (the normal blind-signing flow) silently authorizes the theft of any token in their wallet, including tokens the protocol never listed.

### Finding Description
The Langflow advisory's bug class — an endpoint that executes untrusted user-supplied code — maps directly onto the route-venue mechanism here:

1. `process_swap_collateral` / `process_swap_debt` call `swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 13–38), which authorizes one exact input transfer to the router and calls `router.execute_strategy(&controller, &amount_in, swap)`, forwarding the raw `swap` bytes without decoding them.
2. Per the router spec (`skills/xoxno-swap-aggregator/payload.md`, lines 61–100), each instruction's `idx_a` selects a **pool address from the caller-supplied `assets` registry**; venue adapters then `invoke_contract` on that address (`venues/soroswap.rs`, `venues/aquarius/pool.rs`, `venues/comet.rs`, `venues/phoenix.rs`, `venues/sushi.rs`). There is no venue/pool allowlist — opcode is constrained, the target contract is not.
3. The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the exploit mechanics end-to-end:
   - `UnlistedPoolRouter::execute_strategy` (lines 39–47) mirrors the real router: `sender.require_auth()`, pull `token_in`, `env.invoke_contract(&route.hop_pool, "swap")`, pay out.
   - `RogueHopPool::swap` (lines 62–71) calls `token.transfer(victim, attacker, amount)` on an arbitrary wallet token mid-hop.
   - In simulation/recording mode the stolen transfer is attached as a sub-invocation under the caller's `swap_collateral` auth entry (lines 195–227), and in enforcing mode the signed "poisoned tree" authorizes the theft (lines 259–268): Alice's `WALLET_BALANCE` of an unrelated token moves to the attacker while the swap itself settles fairly.
   - The host only rejects the rogue transfer when the signed tree omits it (lines 243–254) — i.e., safety depends entirely on the user inspecting the auth tree.

This is the Soroban equivalent of "untrusted user input reaches an execution primitive": the `swap` bytes are attacker-crafted code-by-reference (they select which contract runs), and the Soroban auth model makes the caller's signature cover whatever that code demands.

### Impact Explanation
Theft of user funds. Any token held in the victim's wallet — or callable via any `require_auth`-gated function on any contract — can be drained when the victim signs a route containing a malicious pool. The same primitive can invoke arbitrary contract functions requiring the victim's auth (not just token transfers), since any `victim.require_auth()` inside the invoked pool joins the caller's tree. The position operation still completes correctly (fair swap output deposited), so the victim sees a successful `swap_collateral`/`multiply` while unrelated assets are stolen.

### Likelihood Explanation
A single unprivileged address can submit the path: the attacker crafts `routeXdr` referencing their deployed pool contract in the `assets` registry and distributes the pre-built transaction/quote to victims (phishing, malicious frontend, compromised quote response). Simulation auto-records the injected transfer into the auth entries, so a wallet that signs the simulated tree without human review authorizes it. The mitigation is purely user-side auth-tree inspection, which most wallets render poorly; no on-chain check in `swap.rs` or the venue dispatch rejects unlisted pool addresses. Severity: High — requires victim signature on a poisoned route, but no protocol-side control prevents constructing or executing it.

### Recommendation
- Enforce a venue/pool allowlist (owner-maintained, per-venue) inside the router's `dispatch_hop`, so route bytes can only name registered pool contracts — `Program::decode` or hop execution should verify `assets[idx_a]` against stored whitelists.
- Alternatively/additionally, have the controller validate the route's `token_in`/`token_out` and reject routes whose pool addresses are not known venue contracts before calling `execute_strategy`.
- Document that users must inspect sub-invocations in signed auth trees; wallets/SDk should warn when the auth tree contains token transfers unrelated to the declared route assets.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working harness:
- `Scene::route_through_pool_stealing` (lines 111–125) registers `RogueHopPool` with a plan `(victim=Alice, wallet_token, to=attacker, amount)` and encodes it as the `hop_pool` in the route bytes.
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 195–227): `swap_collateral(alice, account, USDC→ETH, 5000, route)` succeeds, `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the recorded auth tree shows the `wallet_token.transfer(alice → attacker)` nested under Alice's `swap_collateral` entry.
- `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 230–268): with the simulation-produced signed tree, the rogue transfer executes; only an honest tree that omits it is refused.
- With the real router, the same primitive applies because instruction `idx_a` resolves the pool from caller-supplied `assets` with no allowlist (`skills/xoxno-swap-aggregator/payload.md` lines 61–66, 100; dispatch in `contracts/swap-aggregator/src/venues/*`). The harness substitutes a minimal router to isolate the auth-tree mechanism; the pool-invocation shape is identical.

Caveat: I verified the mechanism through the test harness and the documented router semantics; I did not read each venue adapter's dispatch line-by-line, so the exact call site that invokes the route-named pool is inferred from `payload.md` and the venue file layout rather than confirmed line numbers in `dispatch_hop`.
