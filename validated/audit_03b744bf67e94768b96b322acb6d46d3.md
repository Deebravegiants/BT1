### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw webhook body, excluding the `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body-only signable string and then trusts `request.shop` (taken directly from the unauthenticated header) as the tenant identifier passed to the app's webhook handler. This breaks the identity binding `HMAC-verified bytes == bytes the handler acts on`: the signature proves the body came from Shopify for *some* shop, but not that it came for the shop named in the header.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`, and `Request#shop` simply reads the header value with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (body only), then immediately forwards the unauthenticated `request.shop` into the handler's `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` HMAC-verifies exactly the string returned by `to_signable_string`: [4](#0-3) 

Because the `api_secret_key` is per-app (shared across every shop that installs the app) rather than per-shop, any merchant who installs the app on their own store legitimately receives real webhooks — genuine `(raw_body, hmac)` pairs signed with the app's shared secret. Since the shop-domain header is never part of the signed payload, that same attacker can replay the captured `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` passes the forged shop into `WebhookMetadata`, so the host application processes the payload as if it originated from the victim tenant.

The gem's own documentation reinforces that consumers rely on this method for authenticity: "This will verify the request did indeed come from Shopify" is stated for `Registry.process`, with no mention that the `shop` field requires independent verification.

### Impact Explanation
This is a cross-tenant identity-binding failure: a low-privilege actor (any merchant able to install the app on their own store) can forge the tenant identity attached to a legitimately-signed webhook payload and have the host application act on data under an arbitrary victim shop's identity. Depending on the handler logic built on top of `WebhookMetadata.shop` (e.g., updating shop-scoped records, triggering shop-scoped side effects), this enables cross-tenant data corruption/access — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately install the app on a shop they control (the normal, unprivileged installation flow) and capture one webhook delivery, then replay it with a modified `Shop-Domain` header to the app's public webhook callback endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is needed, making this practically exploitable by any user able to install the app.

### Recommendation
Bind the shop domain into the HMAC-covered signable string (Shopify already includes shop context indirectly, but the header itself must be authenticated) — for example, require host applications/gem code to cross-check `request.shop` against the shop associated with the session/webhook subscription that the body's resource belongs to, or, at minimum, document and enforce that `request.shop` must never be trusted without an independent shop-to-webhook-id mapping check server-side before processing.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` (normal, unprivileged flow).
2. Trigger a subscribed webhook topic (e.g., `orders/create`) on the attacker's own shop; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header — both are valid because they're signed by Shopify with the app's shared `api_secret_key`.
3. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) verifies successfully because it only hashes `@raw_body`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to act as though the webhook originated from the victim tenant.
