### Title
Webhook Shop Domain and Topic Not Bound to HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the raw HTTP body against the HMAC signature. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are never included in the signed payload, yet they are trusted and forwarded verbatim to the app's webhook handler as the identity of the shop the event belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from request headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. the body only) and does not verify that the `shop` header is bound to that signature: [3](#0-2) [4](#0-3) 

The equality this breaks is: `shop (validated by HMAC) == shop (delivered to the app's handler as WebhookMetadata#shop)`. In reality only `body (validated by HMAC) == body (used to build WebhookMetadata)` holds; `shop` is never part of the signed material.

Because Shopify signs every merchant's webhook with the same app-level `api_secret_key` (there is no per-shop signing key), a merchant who has legitimately installed the app can capture a webhook Shopify sends for their own shop (valid `hmac-sha256` header for that exact body) and resubmit that same body/HMAC pair directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header for a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body's signature, so `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and `body` set to attacker-controlled content: [5](#0-4) 

The library's own documentation reinforces this trust boundary confusion, presenting `data.shop` as a verified identity to key downstream work off of, and describing `process` as verifying "the request did indeed come from Shopify" without qualifying that only the body — not the shop attribution — is authenticated: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any app that uses `WebhookMetadata#shop` (as the docs' own example does, e.g. `shop_domain: data.shop`) to attribute webhook effects to a tenant — updating that shop's local records, triggering GDPR/redact flows, invalidating or refreshing sessions, etc. — can be made to apply attacker-supplied webhook bodies to an arbitrary victim shop identifier. This is a cross-tenant confusion vulnerability: an unprivileged but legitimately-installed merchant can make the app believe attacker-controlled data belongs to a shop they do not control, without needing the app's `client_secret`, an access token, or any privileged credential — only their own (valid, unmodified) HMAC-signed webhook body and a rewritten header on replay.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as an ordinary merchant, (2) capturing one legitimate webhook delivery for that shop (any topic, e.g. `orders/create`, whose body content the merchant fully controls), and (3) resubmitting the exact same body/HMAC to the app's public webhook endpoint with the `shop-domain` header changed. No TLS interception, credential theft, or privileged access is required — the attacker acts entirely from their own tenant boundary.

### Recommendation
Bind the shop identity to the HMAC-verified material, e.g. by including `shop`/`topic` in `to_signable_string`, or by requiring callers to independently confirm the delivered `shop` against a shop the app has an active/expected session or subscription for before trusting `WebhookMetadata#shop`. At minimum, document explicitly in `docs/usage/webhooks.md` that `shop`, `topic`, and `webhook_id` are NOT covered by the HMAC and must be independently validated by the host application before being used for any tenant-scoped action.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app.
# Step 1: capture a real webhook Shopify sends to the app for their own shop.
captured_body = '{"id": 1, "note": "attacker controlled content"}'
captured_hmac_header = "..." # valid base64 HMAC-SHA256(captured_body, api_secret_key), obtained honestly

# Step 2: replay directly against the app's public webhook endpoint,
# swapping only the shop-domain header (not covered by the signature).
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac_header, # unchanged, still valid for captured_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (body/HMAC untouched);
#    handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled JSON)
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
