## Finding: Permissionless `CallDispatcher.dispatch()` Allows Theft of Any Residual Balance

The CVE describes an access-control failure in a file-upload feature that lets any user trigger arbitrary code execution. The closest reachable analog in this codebase is `CallDispatcher.dispatch()` — a shared, unauthenticated entry point that executes arbitrary attacker-supplied calls using the contract's own held balance, with **no caller restriction whatsoever**.

### Title
Unrestricted `CallDispatcher.dispatch()` allows any caller to drain the dispatcher's ETH/token balance via arbitrary calls - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a single, shared utility contract used by `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` and their upgradeable variants to execute arbitrary "predispatch"/"postdispatch"/bridged calldata during order fills and token transfers. Its `dispatch(bytes memory encoded)` function is `external` with no modifier, no caller allow-list, and no ownership check [1](#0-0) . It also has an unrestricted `receive()` that accepts native ETH from anyone [2](#0-1) .

### Finding Description
Every caller of `dispatch` supplies an ABI-encoded `Call[]` array (`to`, `value`, `data`); the function loops and low-level `.call{value: call.value}(call.data)`s each target using the CallDispatcher's own held balance as the value source [3](#0-2) . Because `dispatch` has no `onlyOwner`/`onlyIntentGateway`/allow-list gate, this is reachable directly by any address — not just the intended callers (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`).

The docs explicitly acknowledge the dispatcher "holds tokens temporarily during execution" between the asset-transfer step and the sweep-back step of `placeOrder`'s predispatch flow [4](#0-3) , and that this same contract is a canonical, chain-wide deployment shared by multiple apps ("Existing `CallDispatcher` deployments are listed on the contract addresses page"). Any ETH sent to its `receive()` (accidental transfer, dust, or leftover from a predispatch call that produced excess native output before the sweep completes) or any ERC20 balance left in the contract between the transfer-in and sweep-back calls is, for the duration it sits there, stealable by literally any external account, since nothing restricts who may invoke `dispatch`.

This is the same bug class as CVE-2023-29657: a function that should only be reachable by a trusted, authenticated caller (the file manager's own upload logic / here, the IntentGatewayV2/HyperFungibleToken contracts that are supposed to be the sole orchestrators of dispatcher calls) is instead open to any unauthenticated party, letting them drive execution/state changes (asset transfers) they should never be able to trigger.

### Impact Explanation
Any native ETH or ERC-20 balance transiently or accidentally held by the shared `CallDispatcher` can be swept to an attacker-chosen address by a front-run or opportunistic call to `dispatch()`, since the function performs `to.call{value: call.value}(call.data)` against the dispatcher's own balance with a target and value fully controlled by the caller. This is concrete theft of funds reachable from a single unprivileged transaction, matching "concrete theft ... of funds" in the validation criteria.

### Likelihood Explanation
The dispatcher is used continuously by `IntentGatewayV2.placeOrder`'s predispatch swap-then-escrow flow and by `HyperFungibleToken`/`WrappedHyperFungibleToken`'s calldata-execution-on-receive flow, both of which route real user value through the same shared contract instance across many chains and integrations. Any transient balance window (dust from a swap producing more output than required, ETH sent directly to `receive()`, or a sweep that doesn't fully clear due to fee-on-transfer tokens) creates an exploitable window for any bot watching the chain to call `dispatch()` and claim the balance before the legitimate sweep executes it in the same or a later transaction.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., an `onlyAuthorizedCaller` modifier checking `msg.sender` against a registry of `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` instances, or deploy a dedicated per-caller dispatcher instance instead of sharing one canonical instance across all integrations), and consider disallowing unsolicited native-ETH deposits via `receive()`.

### Proof of Concept
1. Any ETH lands in the shared `CallDispatcher` (e.g., via direct transfer to `receive()`, or as leftover native output from an `IntentGatewayV2.placeOrder` predispatch swap that produces more ETH than `order.inputs` requires, before `_execute`'s sweep call executes).
2. An attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: address(dispatcher).balance, data: ""})]))` directly — no authorization check blocks this since `dispatch` is unrestricted `external`.
3. The low-level call at [5](#0-4)  sends the entire dispatcher ETH balance to the attacker.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
