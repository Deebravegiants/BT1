### Title
Escrowed funds can be permanently frozen if a beneficiary/user is blacklisted by a USDC/USDT-style token, with no mechanism to redirect the recipient - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The IntentGateway's escrow release path hardcodes the recipient of escrowed tokens to whatever address is baked into the `Order` (the `beneficiary` for fills, or `order.user` for cancellations/refunds), and calls `IERC20.safeTransfer` directly to that address with no way for the order creator, solver, or protocol to redirect funds to a different address. If that address is later blacklisted by a token contract such as USDC or USDT, the transfer will permanently revert and the escrowed funds become unrecoverable.

### Finding Description
`_withdraw` in `IntentsBase.sol` is the single function that releases escrowed tokens for fills, partial fills, refunds, and cancellations. It transfers tokens straight to `beneficiary`, an address decoded from the (immutable, hash-committed) `WithdrawalRequest`/`Order` struct, with a plain `safeTransfer`: [1](#0-0) 

This is reached from three places:
- `_fillSameChain` (`IntrinsicIntents.sol`), which resolves `beneficiary` from `order.output.beneficiary` and pays it directly via `IERC20(token).safeTransferFrom(msg.sender, beneficiary, ...)` before ever reaching `_withdraw` for the input-side escrow release to the solver: [2](#0-1) 
- `_fillCrossChain` (`ExtrinsicIntents.sol`), which pays the destination-chain `beneficiary` directly, then on settlement calls `_withdraw` on the source chain to pay the solver: [3](#0-2) 
- `cancelOrder` → `_cancelSameChain` / `_cancelFromSource` / `_cancelFromDest`, all of which ultimately call `_withdraw` with `beneficiary = order.user` to refund the original depositor.

Once `placeOrder` is called, `order.user`, `order.output.beneficiary`, and all other order fields are frozen into the `commitment = keccak256(abi.encode(order))` hash used everywhere as the order's identity key: [4](#0-3) [5](#0-4) 

Any settlement, refund, or cancellation of that order must reference the exact same `Order` struct to reproduce the commitment hash (`fillOrder`, `cancelOrder` both recompute `keccak256(abi.encode(order))` and match it against stored `_orders`/`_filled` state) — see `fillOrder`/`cancelOrder`: [6](#0-5) [7](#0-6) . There is no `updateBeneficiary`, no override parameter for `beneficiary`/`user`, and no fallback/pull-payment pattern anywhere in the withdrawal path — the address is fixed at order-placement time and used for the life of the order.

If the `user` (refund recipient) or `output.beneficiary` (fill recipient) address is blacklisted by the underlying ERC20 (USDC's/USDT's blacklist mechanism reverts `transfer`/`transferFrom` to a blacklisted address) at any point between order placement and settlement/cancellation:
- A same-chain or cross-chain fill's beneficiary-side transfer in `_fillSameChain`/`_fillCrossChain` will revert, blocking the solver from ever filling the order (freezing the escrowed input tokens indefinitely, since `_filled[commitment]` is only set on success and any revert unwinds it).
- A cancellation via `_withdraw(body, isRefund=true, ...)` back to `order.user` will revert every time it's attempted, since `order.user` can never be changed — permanently trapping the escrowed tokens with no recovery path.

### Impact Explanation
Escrowed input tokens (USDC/USDT or any blacklist-capable ERC20) placed into `IntentGatewayV2` can become permanently frozen and unrecoverable by their owner if the owner (or a beneficiary they specify) is blacklisted by the token issuer after order placement. This is a direct, protocol-level loss of user funds with no admin recourse in the code (no sweep-to-alternate-address, no beneficiary update, no pull-based withdrawal). Given IntentGateway routes escrow of arbitrary user-supplied ERC20 tokens including stablecoins with centralized blacklist authority, this is a realistic freeze-of-funds vector.

### Likelihood Explanation
Likelihood is Medium: it requires the token issuer (Circle/Tether) to blacklist a specific user or beneficiary address, which is a rare but real occurrence (sanctions compliance, exploit-related freezes). Because `IntentGateway` explicitly targets ERC20 tokens including canonical stablecoins for cross-chain swaps, and any address (attacker-controlled solver as beneficiary, or the user's own address) can be blacklisted independent of the protocol's control, this is squarely in scope, matching the reported bug class (borrower/depositor blacklisted by asset contract, freezing an otherwise-withdrawable balance).

### Recommendation
Add a pull-based withdrawal / recipient-redirection mechanism to `_withdraw` (and the corresponding fill-time direct-payment paths in `_fillSameChain`/`_fillCrossChain`): if the direct `safeTransfer`/`safeTransferFrom` to the stored `beneficiary`/`user` reverts, credit the amount to an internal balance mapping keyed by `(beneficiary, token)` that the address (or a delegate it nominates in advance) can later withdraw to an alternate address, instead of reverting the whole settlement/cancellation and leaving funds stuck against a single immutable address.

### Proof of Concept
1. User calls `placeOrder` with `order.user = attackerAddr` (their own address) and input token = USDC, escrowing e.g. 1000 USDC (see `IntentGatewayV2.placeOrder`, `evm/src/apps/IntentGatewayV2.sol:194-415`).
2. Circle blacklists `attackerAddr` on USDC for unrelated reasons before the order is filled.
3. No solver can fill the order profitably before `order.deadline`, or the user decides to cancel.
4. User calls `cancelOrder` after the deadline; this routes to `_cancelSameChain`/`_cancelFromDest`/`_cancelFromSource`, all ending in `IntentsBase._withdraw(body, isRefund=true, finalize=true)` with `beneficiary = order.user = attackerAddr` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`).
5. `IERC20(USDC).safeTransfer(attackerAddr, amount)` reverts because `attackerAddr` is blacklisted; the entire `cancelOrder` transaction reverts.
6. Every future call to `cancelOrder` for this commitment reverts identically since `order.user` is fixed by the hash-committed `Order` struct — the escrowed 1000 USDC is permanently locked in the `IntentGatewayV2` contract with no code path to redirect it to an unblacklisted address.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }
