### Title
Webhook `shop-domain` Identity Is Not Bound by the HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by HMAC-verifying the raw request body, while the `shop` (tenant) identity is read from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, which is never included in the signed material. This breaks the intended equality `hmac_signed_bytes == tenant_identity_bytes`, letting anyone who can obtain one valid `(body, hmac)` pair from Shopify (e.g., by triggering a webhook to their own, legitimately installed shop) replay that exact body with a forged `shop-domain` header claiming to be a different merchant. The signature check still passes because it never covered the shop header.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw HTTP body — nothing else: [2](#0-1) 

But the `shop` attribute — the value used downstream to identify *which tenant* the webhook data belongs to — is parsed straight out of an unauthenticated header, with no relation to the signed bytes: [3](#0-2) 

`Registry#process` verifies the HMAC and then dispatches to the app's handler using that same unauthenticated `shop` value as the tenant identity: [4](#0-3) 

Because a single `Context.api_secret_key` is shared by the app across *all* shops that install it, any merchant who has the app installed can trigger a webhook delivery to themselves with a body that gets a validly-computed HMAC from Shopify. Nothing in `Request#initialize` or `Registry.process` binds that `hmac`/`body` pair to the `shop-domain` header it originally arrived with: [5](#0-4) 

An attacker can therefore replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a different `shop-domain` header value belonging to a victim merchant. `HmacValidator.validate` still returns `true` because it only re-checks the body against the secret; `Registry.process` then calls the handler with `shop: request.shop` set to the victim's domain, causing the app to process attacker-controlled webhook data as if it originated from the victim tenant — a violation of the equality `shop_that_signed_the_request == shop_the_handler_believes_sent_it`.

### Impact Explanation
This is a cross-tenant boundary break: the identity (`shop`) that the app's webhook handler trusts is not cryptographically tied to the same bytes that were HMAC-verified. An attacker with only an ordinary, unprivileged install of the app on their own store can inject attacker-controlled webhook payloads (order data, product data, GDPR payloads, etc.) that the host app will process as belonging to a different, unrelated merchant's shop — meeting the Critical "cross-tenant access" bar defined in scope.

### Likelihood Explanation
The only capability required is a normal merchant account with the vulnerable app installed (no `api_secret_key`, access token, or privileged access needed), the ability to trigger any webhook topic on their own store (e.g., updating a product/order to fire `products/update`/`orders/updated`), and the ability to send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — all trivially available to any unprivileged internet user who is a merchant of the target app.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the verified HMAC/body pair before trusting it — e.g., by validating that the resolved `shop` corresponds to a session/installation record already known to the app for that specific webhook delivery, or by having `to_signable_string` incorporate the shop domain (matching how Shopify's webhook payload itself embeds shop-scoped identifiers) so a replay with a substituted header invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker performs an action that triggers a webhook (e.g., updates a product), causing Shopify to POST a body `B` with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and a valid `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's `client_secret` over `B`) to the app's webhook endpoint.
3. Attacker intercepts/replays this exact `(B, H)` pair to the same endpoint but rewrites the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-22`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` dispatches to the app's handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to ingest attacker-controlled data under the victim's tenant context.
