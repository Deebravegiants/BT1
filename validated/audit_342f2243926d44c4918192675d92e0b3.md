### Title
Webhook shop identity is taken from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only the HMAC over the raw request body, but then trusts the `shop` value taken from the `x-shopify-shop-domain` HTTP header — a field that is never included in the signed payload — and hands it to the app's handler as the authoritative tenant identity for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the HMAC-signed string: [2](#0-1) 

`Registry.process` validates the HMAC (body-only) and then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identifier passed to the app's handler: [3](#0-2) 

The `HmacValidator.validate` call only proves the request body was produced/signed using the app's `api_secret_key` — this secret is shared across *every* shop that has installed the app, so it never binds the signature to a particular shop: [4](#0-3) 

Because the signature never covers `shop-domain`, the identity check that this codebase relies on breaks the equality:
`shop authenticated by HMAC` ≠ `shop used to identify the tenant (request.shop from header)`

There is no additional domain/format validation (e.g., `ShopValidator`) applied to `request.shop` in the webhook path — that validator is only used in the OAuth/token-exchange code paths, confirmed by its usages: [5](#0-4) 

Since any merchant that installs the app receives genuinely-signed webhook deliveries (with the same, app-wide `api_secret_key`), a malicious merchant can capture a valid `(raw_body, hmac)` pair from their own install and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates (it only covers `raw_body`), and the app's handler is called with `data.shop` equal to the attacker-chosen victim domain, effectively spoofing which tenant the event is attributed to.

### Impact Explanation
This crosses the tenant boundary this gem is meant to enforce: it lets an unprivileged, already-installed merchant forge the *tenant identity* of arbitrary webhook events for other merchants, without needing that merchant's access token or `client_secret`. Depending on how a host application uses `data.shop` (looking up sessions, gating GDPR/`shop/redact`-style compliance actions, updating per-shop records, revoking data, etc.), this enables cross-tenant data corruption or unauthorized actions against a different merchant's stored state — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop have the app installed (an unprivileged position) and be able to intercept or predict one legitimately-delivered webhook body/HMAC pair (e.g., a `app/uninstalled` or other webhook with static/predictable body content). No secrets, tokens, or elevated access are required — replay/tamper of the `shop-domain` header is trivial once a valid `(body, hmac)` pair is obtained.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload verification, or otherwise cryptographically bind `request.shop` to the signed body before trusting it — e.g., validate that the `shop-domain` header corresponds to a known, previously-authorized shop for this app (cross-checked against stored sessions) rather than trusting it outright, and reject webhooks whose shop domain fails `ShopValidator` sanitization against the app's trusted domains.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g. body `{}` with header `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `api_secret_key` (shared across all installs of the app).
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully since only body/hmac/topic/shop-domain presence is checked, not their binding.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature only covers `raw_body`, unaffected by the header change (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. The app's handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though Shopify never issued this webhook for that shop (`lib/shopify_api/webhooks/registry.rb:198-199`).

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
