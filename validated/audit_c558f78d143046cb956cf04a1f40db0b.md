### Title
Unbounded `GetRequest.keys` array lets an attacker force disproportionate proof-verification/relaying costs for a fixed fee - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchGet)` accepts an arbitrary-length `keys` array and only ever collects a single, flat `get.fee` for the whole request, with no validation that the fee scales with the number of keys or that the array is bounded. Downstream, both the relayer and `HandlerV2`/`pallet-ismp`'s response handling must fetch and verify a storage proof for every key in the array before the request can be considered processed.

### Finding Description
`EvmHost.dispatch(DispatchGet memory get)` builds a `GetRequest` directly from the caller-supplied `keys` array without checking its length, and stores a single `FeeMetadata{sender, fee}` for the whole request: [1](#0-0) 

On the response side, `HandlerV2.handleGetResponses` and the substrate `state-coprocessor` pallet must verify a state/storage proof against every key in the request before it is considered delivered: [2](#0-1) [3](#0-2) 

There is no minimum-fee-per-key or maximum-key-count enforcement anywhere in the dispatch path (`EvmHost.sol`, `HyperApp.sol`'s `quote`/`dispatchWithFeeToken`, or the docs' own examples of building `keys[]` from an arbitrary-length input array): [4](#0-3) 

An attacker can therefore dispatch a single `GetRequest` with a very large `keys` array (e.g. thousands of storage slots) while paying the same fixed `fee` as a request with one key. Any party — a self-relaying user, a third-party relayer, or Hyperbridge's own state-coprocessor pallet processing the response — is forced to build and verify a correspondingly large multiproof/storage proof to process that single request, at a cost that is completely decoupled from what the attacker paid.

### Impact Explanation
This mirrors the referenced bug class: an unprivileged caller can cheaply create an artifact (here, one oversized GET request instead of many small receipts) whose required downstream processing cost is unbounded and not compensated. Because `handleGetResponses` and the coprocessor's `on_response` verification loop over every key before the request/response is marked processed, this can be used to grief relayers into unprofitable/expensive submissions, or — if such a request must be processed before some invariant can hold (e.g. commitment cleanup, timeout handling) — to indefinitely inflate the gas required for any party who must finish processing it. This is a Medium-severity denial-of-service / economic-griefing issue against the ISMP messaging pipeline rather than a fund-theft bug.

### Likelihood Explanation
Likelihood is moderate: dispatching a `DispatchGet` with an oversized `keys` array requires no special privilege beyond paying the flat `fee` (which can be minimal or even the configured minimum), and the relevant validation gap (no per-key fee floor, no key-count cap) is present in the current contract logic. The main mitigating factor is that a rational relayer/self-relayer may simply decline to service an unprofitable request (as the profitability gating in the relayer's `fees.rs`/`events.rs` shows it filters candidates by profitability), which reduces — but does not eliminate — actual exploitation, since some path (self-relay, or a mandatory internal processing pass) can still be forced to pay the disproportionate cost.

### Recommendation
- Enforce a maximum number of `keys` per `DispatchGet`/`GetRequest`, or scale the required `fee` proportionally to `keys.length` (and/or total key byte size), similar to how `BandwidthGate` already meters response bytes in the coprocessor.
- Reject dispatches whose `fee` is below a per-key minimum in `EvmHost.dispatch(DispatchGet)`.

### Proof of Concept
1. Attacker calls `IDispatcher(host).dispatch(DispatchGet{ dest, height, keys: <N very large keys>, timeout, fee: minimal, context, payer })` via `EvmHost.dispatch` (`evm/src/core/EvmHost.sol:974-1013`), paying only the flat `fee`.
2. The request is committed with a single `FeeMetadata{sender, fee}` regardless of `keys.length`.
3. Once Hyperbridge produces the `GetResponse` (verifying all N keys against the destination state root, see `modules/pallets/state-coprocessor/src/impls.rs:133-155`), a relayer/self-relayer must submit `HandlerV2.handleGetResponses` (`evm/src/core/HandlerV2.sol:217-247`), whose multiproof and calldata size — and therefore gas cost — grow with N, while the compensation stayed fixed at the low `fee` paid in step 1.

Note: I could not fully verify whether pallet-ismp enforces any hard cap on `GetRequest.keys` length at the extrinsic/weight level (the codebase index did not surface a `MaxKeys`-style bound in the dispatcher/router types), so the exact practical ceiling on N is unconfirmed and would need direct inspection of `modules/ismp/core/src/router.rs` and the substrate dispatch extrinsic weights in a full checkout.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }

function readMultipleSlots(
    address contract_,
    bytes32[] memory slots,
    uint256 height,
    bytes memory dest
) public payable returns (bytes32) {
    // Construct keys for multiple slots
    bytes[] memory keys = new bytes[](slots.length);
    for (uint256 i = 0; i < slots.length; i++) {
        keys[i] = bytes.concat(bytes20(contract_), slots[i]);
    }
    
    DispatchGet memory getRequest = DispatchGet({
        dest: dest,
        height: height,
        keys: keys,
        timeout: 0,
        fee: msg.value,
        context: abi.encode(contract_, slots)
    });
    
    return IDispatcher(_host).dispatch{value: msg.value}(getRequest);
}
