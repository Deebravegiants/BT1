### Title
Missing reentrancy guard on Tron `IntentGatewayV2.placeOrder` allows attacker-controlled `predispatch.call` to reenter before escrow accounting is updated - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements `placeOrder` without any `nonReentrant`/`ReentrancyGuard` protection, unlike the canonical EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) which inherits `ReentrancyGuardTransient` and guards `placeOrder`/`fillOrder` with `nonReentrant` [1](#0-0) . In `placeOrder`, when an order carries `predispatch` calldata, the function transfers predispatch assets to the dispatcher and invokes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — a call whose target/data is entirely attacker-supplied — before the escrow accounting update `_orders[commitment][token] += reducedInputs[i].amount` is applied.

### Finding Description
`placeOrder` on Tron computes the order `commitment`, then, if `order.predispatch.call.length > 0`, transfers predispatch assets to `_params.dispatcher` and executes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [2](#0-1) . The dispatched call content is user-supplied as part of the `Order` struct submitted by `msg.sender`, so the caller fully controls what `dispatch()` executes. Only after this external call returns does the function credit escrow: `_orders[commitment][token] += reducedInputs[i].amount` [3](#0-2) . This is a Checks-Effects-Interactions violation: an external, attacker-influenced interaction (`dispatch`) happens before the effect (escrow state update).

Because there is no reentrancy lock anywhere in this contract (confirmed by grep: no `nonReentrant`/`ReentrancyGuard` matches in `evm/tron/contracts/apps/IntentGatewayV2.sol`), a solver-controlled `predispatch.call` payload that routes through the `CallDispatcher` back into `IntentGatewayV2` (e.g., re-entering `placeOrder`, `fillOrder`, or `cancelOrder`) can execute against inconsistent intermediate state — most notably, before `_orders[commitment][...]` reflects the amount the outer call is about to escrow, and while `_nonce` has already been incremented for the outer order but its `commitment`/escrow linkage is not yet finalized.

This mirrors the reported bug class in the external report (fee deduction/transfer occurring before the corresponding pool-state update in `_fundPool`), generalized here to the intent-gateway `placeOrder` flow: an external call precedes the internal accounting write, and nothing prevents reentrant execution during the external call window.

By contrast, the canonical `evm/src/apps/IntentGatewayV2.sol` guards this same code path with `nonReentrant` [1](#0-0) , and the audited fix history in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` shows the project is aware of and defends against reentrancy in the intents module by setting `_filled[commitment]` before any external transfer in `_fillSameChain`/`_fillCrossChain` [4](#0-3) [5](#0-4) . The Tron variant, being a separate, independently-maintained copy of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`), has neither of these protections applied to `placeOrder`'s predispatch path.

### Impact Explanation
An attacker who controls the `predispatch.call` payload of their own order can reenter the gateway mid-`placeOrder` execution, while `_orders[commitment][token]` for the in-flight order has not yet been credited and while intermediate dispatcher balances are being manipulated. Depending on what the reentrant call reaches (e.g., a second `placeOrder` with a colliding/crafted commitment, or interaction with escrow/dust bookkeeping), this can be leveraged to desynchronize the gateway's internal escrow ledger from actual token custody — leading to under- or over-credited escrow entries, incorrect dust emission, or state that lets a subsequent `fillOrder`/`withdraw` drain more than was actually escrowed. This is a fund-safety issue in a user-reachable, single-transaction entry point (`placeOrder`), matching High severity for unbacked/mismatched escrow accounting in a token bridging/intents contract.

### Likelihood Explanation
High reachability: `placeOrder` is a public, unprivileged, single-transaction entry point that any user can call with arbitrary `order.predispatch.call` content whenever `order.predispatch.assets.length > 0`. The only preconditions are that `_params.dispatcher` is configured and the attacker crafts calldata that the `CallDispatcher` forwards back into `IntentGatewayV2`. No governance, node, or off-chain trust is required — exactly the class of "solver/order-placer initiated" reentrancy the audit-report and hint set call out.

### Recommendation
Add a reentrancy guard (e.g., OpenZeppelin `ReentrancyGuard`/`ReentrancyGuardTransient`, mirroring `evm/src/apps/IntentGatewayV2.sol`) to `placeOrder`, `fillOrder`, and `cancelOrder` in the Tron contract. Additionally, restructure `placeOrder` to follow Checks-Effects-Interactions: compute and write `_orders[commitment][token]` (and any other escrow bookkeeping) before invoking `ICallDispatcher(dispatcher).dispatch(...)`, or ensure the dispatcher's `dispatch()` cannot re-enter privileged gateway functions (e.g., by having the dispatcher itself enforce a "no external targets equal to the gateway" allowlist, in addition to the reentrancy lock).

### Proof of Concept
Concrete step-by-step exploitation could not be fully constructed without the `CallDispatcher` implementation details and confirmation of what deployed instances of the Tron gateway are live/reachable; this assessment is based on static code-flow analysis showing (1) the external `dispatch()` call at [6](#0-5)  precedes the escrow-state write at [7](#0-6) , and (2) the total absence of any reentrancy guard on this contract, confirmed via grep across `evm/tron/contracts/apps/**`. A background engineering session with access to the `CallDispatcher` implementation and a Tron/EVM test harness would be needed to build and run an end-to-end forge/hardhat PoC analogous to `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`.
