### Title
Webhook shop domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, excluding the `X-Shopify-Shop-Domain` (and topic/webhook-id) headers from the HMAC-covered content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` (parsed straight from the unauthenticated header) as the tenant identifier handed to the app's webhook handler. Any party capable of obtaining one genuinely Shopify-signed webhook delivery (e.g., a malicious merchant who has installed the app on their own store) can replay that exact signed body while swapping the shop-domain header to impersonate a different, victim tenant, since the signature never covered that header.

### Finding Description
The `hmac` field is computed by Shopify over the raw JSON body only, and `Request#to_signable_string` mirrors that by returning `@raw_body`: [1](#0-0) 

`shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never part of the signed bytes: [2](#0-1) 

`Registry.process` verifies only the body HMAC, then passes `request.shop` straight into `WebhookMetadata`, which is delivered to the app's handler as the authoritative tenant identifier for that webhook event: [3](#0-2) 

The documented handler contract explicitly instructs apps to key their processing (e.g., DB lookups, job enqueueing) on `data.shop`: [4](#0-3) 

The bug: the invariant `shop-used-by-handler == shop-that-was-actually-cryptographically-authenticated` is broken. HMAC only proves "this body byte-sequence was produced with the app's secret at some point," not "this event actually pertains to shop X." Any entity that can obtain one legitimately-signed webhook body (any merchant that has the app installed, since `api_secret_key` is shared across all tenants of the app and Shopify itself signs the payload for every install) can capture that valid `(body, hmac)` pair and resend it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header pointing at a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because the signature check is only over `@raw_body`, and the forged shop value flows unauthenticated into the handler.

### Impact Explanation
This breaks the tenant isolation boundary of the gem: the `shop` value that app code is told to trust as the authenticated origin of a webhook event is not actually bound to the cryptographic signature. A malicious (but otherwise legitimate, unprivileged) installer of the app can inject spoofed webhook events attributed to another merchant's shop, corrupting or manipulating that victim's data/state inside the host app (e.g., triggering `orders/create`-style side effects, replaying an app-uninstall or GDPR webhook against a shop the attacker doesn't own, or poisoning data keyed by `shop`). This is a cross-tenant access/data-integrity violation reachable without any credentials beyond normal, low-privilege app installation.

### Likelihood Explanation
Any user of the app who installs it on their own store automatically receives real, validly-signed webhook deliveries for topics the app subscribes to (this is normal, unavoidable Shopify behavior). Capturing one such delivery (from their own store's traffic to the app, which they fully control) and replaying it with a different `X-Shopify-Shop-Domain` header requires no secret material, no privilege escalation, and no interaction with the victim — only a basic HTTP replay to the app's public webhook endpoint. This is straightforward and repeatable for any installer.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified content, or otherwise cryptographically/authoritatively verify that the `shop-domain` header matches the shop the webhook subscription was registered for (e.g., cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription via a stored mapping, or include these headers in the signable string if Shopify's signing scheme is updated to support it). At minimum, document/require that consuming applications independently verify `request.shop` corresponds to a shop with an active, known installation/session before trusting it, since the gem cannot currently prove this binding on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggering a legitimate webhook (e.g., `orders/create`) delivery from Shopify to the app's webhook endpoint, with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `api_secret_key`.
2. Attacker captures this `(raw_body, hmac_header)` pair from their own traffic.
3. Attacker resends the identical `raw_body` and `hmac_header` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`@raw_body` only) — it matches, since the body is unchanged.
5. `WebhookMetadata.shop` is set to `"victim-shop.myshopify.com"` and forwarded to the app's handler, which processes attacker-controlled data as if it originated from the victim's shop. [3](#0-2) [5](#0-4)
