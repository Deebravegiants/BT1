### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook using an HMAC computed only over the raw request body, but the `shop` value that the gem hands to the app's webhook handler is read from an unsigned HTTP header. Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret and is identical for every merchant shop that has installed the app, any shop that received a legitimately signed webhook can replay that body+HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the header, and the gem will accept it as valid.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is taken directly and unauthenticated from the `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string` (the raw body) using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorizing the entire request, including the unsigned `shop` header, and forwards it straight to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the code fails to enforce:
`shop authenticated by the HMAC` (nothing — the signable string contains no shop identifier) `≠ shop delivered to the handler` (`request.shop`, taken from an attacker-controllable header).

Since the API secret is per-app, not per-shop, any merchant who installs the app can obtain a validly-signed `(body, hmac)` pair (e.g., by triggering any webhook topic on their own store, or via any endpoint that echoes an HMAC computed with the same secret). That attacker can then POST the exact same body and HMAC to the app's webhook receiver while setting `shopify-shop-domain` to a victim shop that also uses the app. `HmacValidator.validate` will succeed because it never looks at the `shop` header, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-chosen-body>, ...)`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the gem lets an attacker who controls one tenant (their own installed shop) inject arbitrary, attacker-chosen webhook payloads that are attributed to a different tenant (the victim shop) inside the host application. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop records, honoring GDPR `customers/redact`/`shop/redact` requests, toggling per-shop settings, writing to a shop-scoped database row) executes against the victim's data using attacker-controlled content — a cross-tenant access violation.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop have the app installed (no special privilege, no leaked credentials, no access token) and that they can reach the app's public webhook HTTP endpoint. The gem itself performs no check that `request.shop` matches an expected/authenticated tenant, so any host app that trusts `WebhookMetadata#shop` after `Registry.process` succeeds is exposed. Likelihood is high for any app using the gem's default webhook processing without independently re-verifying the shop out-of-band.

### Recommendation
Bind the shop domain into the signed content, or otherwise authenticate it independently of the header before trusting it:
- Include the `shopify-shop-domain` header value in the HMAC signable string (this would require a corresponding server-side change on Shopify's part) — not feasible unilaterally, so instead:
- Have `Registry.process` (or `HmacValidator`) cross-check `request.shop` against the set of shops the app actually expects to receive webhooks for (e.g., shops with an active session/offline token on file) before invoking the handler, rejecting webhooks for shops that have no corresponding stored session/access token.
- Document clearly that `request.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without an additional shop-membership check by the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, which shares the same `client_secret` (`Context.api_secret_key`) as every other shop using the app.
2. Attacker triggers any webhook delivery to their own endpoint (or crafts one) with body `B`, obtaining a valid signature:
   `hmac = HMAC-SHA256(api_secret_key, B)` — computed exactly as in [5](#0-4) 
3. Attacker replays a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged, attacker-controlled)
   - `shopify-hmac-sha256`: the same valid `hmac`
   - `shopify-shop-domain`: `victim-shop.myshopify.com`
   - `shopify-topic`: any registered topic
4. `ShopifyAPI::Webhooks::Request.new` builds the request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only the body is checked.
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_from_B, ...))`, causing the host app to act on attacker-controlled data as if it originated from `victim-shop`.
