This confirms the vulnerability: the `shop` field in `WebhookMetadata` is sourced directly from the unauthenticated `shopify-shop-domain` HTTP header, while `HmacValidator.validate` only signs `request.to_signable_string`, which returns `@raw_body` exclusively — headers including `shop` are never part of the HMAC-covered bytes.

### Title
Webhook `shop` identity is trusted from an HMAC-unprotected header, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop` value pulled from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header when building the `WebhookMetadata` passed to the app's handler. The header is never included in the signed bytes, so its integrity is not covered by the "did this come from Shopify with this content" guarantee that the HMAC provides.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads directly from headers, which are excluded from that signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature over `to_signable_string` (i.e., body only) and compares it against the `hmac` field — it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` validates only this body HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop`, and calls the app's handler with it: [4](#0-3) 

The identity binding that should hold is: `shop the HMAC authenticates == shop delivered to the handler`. In reality: `HMAC authenticates raw_body bytes only`, while `shop is parsed from an independent, unsigned header`. Per the documented gem contract, apps are expected to use `data.shop` as the tenant identifier for processing (see `docs/usage/webhooks.md`, which shows `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this field is treated as trustworthy tenant-identifying data by design.

### Impact Explanation
An unprivileged internet user who can install the app on their own shop (a benign, low-privilege action any Shopify merchant can take) can capture one legitimate Shopify-delivered webhook (raw body + valid `x-shopify-hmac-sha256`) for their own shop. Because the app's webhook endpoint is a plain public HTTP(S) route, the attacker can then POST that exact same body and HMAC to the app while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and the handler receives `WebhookMetadata` claiming the payload belongs to the victim shop. If the host application uses `data.shop` to select which shop's stored session/state to update (the documented, intended usage pattern), this allows cross-tenant data confusion/corruption — e.g., injecting an attacker-controlled but seemingly-legitimate webhook body (for topics whose payload content is attacker-influenced, such as `app/uninstalled`, order or product webhooks the attacker's own shop can trigger) under a victim shop's identity.

### Likelihood Explanation
Likelihood is dependent on the host application's use of `data.shop` (host apps are encouraged by the gem's own documentation to rely on it), but the underlying binding gap is fully attacker-reachable without any credentials: no `api_secret_key`, access token, or privileged account is required — only the ability to send arbitrary HTTP requests to the app's public webhook endpoint and to have obtained one genuine webhook (trivially done by installing the app on an attacker-owned development shop).

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable string, or otherwise cryptographically bind them to the payload (e.g., verify `shop` against Shopify's `X-Shopify-Shop-Domain` only after confirming the app has an active, matching webhook subscription/session, and document that host apps must not trust the header shop value without independent verification). At minimum, `HmacValidator`/`Request` should not present `shop` as an authenticated field via `WebhookMetadata` without this binding.

### Proof of Concept
1. Attacker installs app on `attacker-shop.myshopify.com` and lets Shopify send a real webhook, capturing `raw_body` and `x-shopify-hmac-sha256`.
2. Attacker POSTs to the app's public webhook route with the same `raw_body`/`hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` [1](#0-0)  — validation passes.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` [5](#0-4)  and delivered to the host app's handler as if Shopify itself asserted this shop identity for this payload.
