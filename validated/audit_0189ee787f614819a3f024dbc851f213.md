## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` value that is subsequently handed to the application's webhook handler comes from the `X-Shopify-Shop-Domain` header, which is never included in the signed content. Because the app's `api_secret_key` is a single value shared across every shop that has the app installed, any merchant who installs the app can capture one of their own genuinely-signed webhook deliveries and replay it to the app's endpoint with the `shop-domain` header rewritten to a victim shop, causing the app to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` reads the shop identity straight from an HTTP header: [1](#0-0) 

The HMAC that authenticates the request is computed only over the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the received HMAC against `to_signable_string` (the raw body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs this single check and then forwards the *unauthenticated* `shop` header value straight to the application handler: [4](#0-3) 

The identity binding that should hold is: `shop claimed in the event handed to the app == shop that Shopify actually generated/signed the payload for`. That binding is broken because the signature only binds `(body, api_secret_key)`, never `(shop, body, api_secret_key)`. Since `api_secret_key` is one value shared by the app across *all* installed shops, an unprivileged user who installs the app on their own store (no special privilege required) legitimately receives HMAC-signed webhooks for their own shop. They can capture a `(body, hmac)` pair from their own delivery and POST it to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to any other tenant's domain. `HmacValidator.validate` still succeeds (it never looked at the shop header), so `Registry.process` will call the handler with `WebhookMetadata` carrying the forged victim shop alongside attacker-controlled `body`/`topic`.

### Impact Explanation
This is a cross-tenant confusion: the application receives an event it will treat as authentic for the victim shop, but the payload/topic content is entirely attacker-controlled (limited to whatever they can produce with a legitimately signed webhook from their own store, e.g. by manipulating their own store's data or by choosing among the topics they can trigger). Depending on how the host app's webhook handlers act on `shop` + `body` (e.g. cache invalidation, data sync, deletion flows tied to lifecycle topics like `app/uninstalled`, `shop/redact`, `customers/redact`), this can lead to unauthorized state changes or data exposure scoped to a shop the attacker does not control — a cross-tenant access boundary violation.

### Likelihood Explanation
Likelihood is high for any app builder relying on this library's webhook signature check as the sole authentication of `topic`/`shop`/`webhook_id`, since none of those fields are bound to the signature. Exploitation only requires being a legitimate (unprivileged) merchant who has installed the target app — no `api_secret_key` leak, token theft, or privileged access is required, since the secret is shared across the app's whole install base by design.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signable content that `HmacValidator` verifies, or otherwise cryptographically bind the `X-Shopify-Shop-Domain` header to the HMAC (e.g. include it in the signed string, or require callers to independently confirm the shop against a known/allow-listed value derived from a trusted source, not from an attacker-repeatable header) before it is forwarded into `WebhookMetadata` and handed to application handlers.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook subscription/topic and capture the genuine delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
3. Replay the request to the same webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb#L12-31`) succeeds because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-199`) calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the app treats attacker-controlled data as authenticated for the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
