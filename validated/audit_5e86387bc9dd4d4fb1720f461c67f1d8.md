### Title
`WalletAccounts#removeMany` performs no lock-state check, allowing account/hardware-key deletion while wallet is locked - ([File: features/wallet-accounts/src/module/wallet-accounts.ts])

### Summary
`WalletAccounts#removeMany` mutates `walletAccounts` and `#hardwareWalletPublicKeys`, persists via `#walletAccountsInternalAtom.set`, and triggers `#updateFusion` with zero reference to lock state anywhere in the function or its call chain. Unlike other RPC-facing wallet-state operations in the codebase (e.g. `addressProviderApi`), the `walletAccountsApi` exposes `removeMany` directly from `walletAccounts.removeMany` with no `lockedAtom` gate wrapping it.

### Finding Description
`removeMany` in `features/wallet-accounts/src/module/wallet-accounts.ts` [1](#0-0)  only guards against `fillIndexGapsOnCreation` being disabled and against removing the default account — it never calls into any locked-state or auth dependency before deleting entries and calling `#walletAccountsInternalAtom.set(...)`.

The method is exposed verbatim through the public API surface: `walletAccountsApi` wires `removeMany: walletAccounts.removeMany` directly [2](#0-1) , with no `lockedAtom` dependency declared for this API at all [3](#0-2) .

This differs from the established pattern in `features/address-provider/api/index.js`, where every wallet-account-scoped operation is wrapped by `withWalletAccountInstance`, which explicitly checks `if (await lockedAtom.get()) throw new Error('address-provider: wallet should be unlocked')` before touching wallet-account data [4](#0-3) . `wallet-accounts`'s own module/API layer has no analogous check.

Additionally, the atom `removeMany` writes through (`walletAccountsInternalAtomDefinition`) is wired to the default `storage` interface without the `unsafeStorage` alias override that other atoms in the same feature explicitly use (e.g. `activeWalletAccountAtomDefinition` aliases `unsafeStorage` to `storage` [5](#0-4) , `features/wallet-accounts/src/index.ts` start="54" end="65" />). In the production adapter wiring, the default `storage` id resolves to the encrypted storage adapter (`createEncryptedStorage`) [6](#0-5) , whose reads are deferred until `unlock()` resolves crypto functions [7](#0-6) ; however its own test suite explicitly demonstrates that `delete()` succeeds while locked [8](#0-7) , and the storage-encrypted module's `set()` semantics under a locked state were not verifiable from available code (the source file `adapters/storage-encrypted/src/index.js` was not accessible in this index). Combined with atom-level caching/dedupe (`dedupe(withSerialization(...))`) that can serve previously-decrypted in-memory values without touching underlying storage, there is a real possibility that once the wallet has been unlocked at least once in a session, `walletAccountsInternalAtom.get()`/`.set()` operate purely off cached in-memory state and do not require re-validating lock state, letting `removeMany` complete successfully after a subsequent lock.

### Impact Explanation
If reachable while locked, `removeMany` would allow deletion of wallet accounts and hardware wallet public key entries without unlocking — degrading the account list and weakening downstream signing/approval scoping (default-account fallback logic in `removeMany` reassigns the active account to `DEFAULT_WALLET_ACCOUNT` [9](#0-8) ), and pushes the mutated state to Fusion sync via `#updateFusion`, propagating the corruption. This does not directly disclose secrets or private keys but violates the "locked means locked" invariant for wallet metadata/state mutation.

### Likelihood Explanation
Feasibility depends entirely on whether the RPC/module boundary in the deployed client (browser extension, mobile, desktop) gates dispatch to `walletAccountsApi` methods by lock state before invoking them — a boundary that lives outside `features/wallet-accounts` and outside what I was able to fully trace or verify (I could not locate a generic app-wide "block API dispatch while locked" middleware, nor could I confirm the exact locked-state semantics of `storage-encrypted`'s `set()`). Given the module itself has zero internal check and the API factory doesn't inject `lockedAtom`, the invariant currently relies entirely on that external, unverified boundary or on caching behavior of the atom layer.

### Recommendation
Add an explicit lock-state check to `WalletAccounts#removeMany` (and ideally `disableMany`, `updateMany`, `createMany`) mirroring the `withWalletAccountInstance` pattern in `addressProviderApi`: inject `lockedAtom` as a dependency of `walletAccountsApi` and reject calls with `if (await lockedAtom.get()) throw new Error(...)` before any mutation, rather than relying on outer RPC/module boundaries or atom-level storage semantics to enforce the invariant.

### Proof of Concept
Unit test plan for `features/wallet-accounts/src/module/__tests__/index.test.ts`:
1. Instantiate `WalletAccounts` via `prepare()` with `fillIndexGapsOnCreation: true` and a mocked `lockedAtom` (or a `#walletAccountsInternalAtom` backed by a real `createEncryptedStorage` instance that has not been `.unlock()`ed after an initial unlocked load, simulating re-lock).
2. Populate wallet accounts while "unlocked" (crypto functions resolved), then simulate lock by never resolving crypto functions again / setting `lockedAtom` to `true`.
3. Call `walletAccounts.removeMany(['exodus_1'])` directly.
4. Expected (secure) assertion: the call rejects with a "wallet is locked" style error and `walletAccountsInternalAtom.set` is never invoked.
5. Current actual behavior: no such rejection exists in `removeMany`; the test would need to demonstrate whether the underlying atom's `get`/`set` block indefinitely (safe) or resolve from cache (vulnerable) — this final determination requires access to `storage-encrypted`'s `set()` implementation, which was not available in this index.

  removeMany = async (names: string[]) => {
    if (!this.#fillIndexGapsOnCreation) {
      throw new Error(
        'removeMany can only be used in conjunction with fillIndexGapsOnCreation. Please disable instead.'
      )
    }

    const currentWalletAccounts = await this.#getInternalWalletAccountsWithFallback()
    const walletAccounts = { ...currentWalletAccounts }
    const active = await this.#activeWalletAccountAtom.get()

    for (const name of names) {
      if (name === DEFAULT_WALLET_ACCOUNT) {
        throw new Error("Can't remove default walletAccount")
      }

      if (walletAccounts[name]?.isHardware) delete this.#hardwareWalletPublicKeys[name]
      delete walletAccounts[name]
    }

    if (equalWalletAccounts(currentWalletAccounts, walletAccounts)) return

    if (names.includes(active)) {
      await this.setActive(DEFAULT_WALLET_ACCOUNT)
    }

    await this.#walletAccountsInternalAtom.set(walletAccounts)
    await this.#savePublicKeys()
    await this.#updateFusion()
  }
