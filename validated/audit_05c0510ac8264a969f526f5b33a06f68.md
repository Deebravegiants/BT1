### Title
Missing Storage Gap in `IntentsBase` Diamond-Inherited by Upgradeable `IntentGatewayV2` Risks Storage Collision on Future Upgrades - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase` is the shared storage-holding base contract of a diamond inheritance graph (`IntentsBase` → `IntrinsicIntents`, `ExtrinsicIntents` → `IntentGatewayV2`) that backs a live, upgradeable UUPS proxy deployed identically across many chains. It declares all of the gateway's persistent state (`_filled`, `_nonce`, `_params`, `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, `_relayer`) with no reserved storage gap at the end of the contract.

### Finding Description
`IntentsBase` lays out storage sequentially and the team has deliberately hand-documented exact slot numbers because downstream logic depends on them: `_filled` at slot 2 is referenced by cross-chain storage proofs via `FILLED_SLOT_BIG_ENDIAN_BYTES` [1](#0-0) , and `_relayer` is packed behind `_paused` at slot 13, appended "last to preserve existing storage slots" [2](#0-1) .

Despite this precision, `IntentsBase` reserves no `__gap` array, unlike other upgradeable contracts in the same codebase that do reserve gaps (e.g. `SimplexPaymaster` reserves `uint256[48] private __gap;` right after its own state) [3](#0-2) . `IntentGatewayV2` is a concrete UUPS-upgradeable proxy contract (confirmed by `ERC1967Proxy`, `upgradeToAndCall`, and a documented live mainnet proxy address) that inherits `IntentsBase` through two sibling contracts, `IntrinsicIntents` and `ExtrinsicIntents` [4](#0-3) . Because `IntentGatewayV2` is deployed and upgraded live (see `testLiveProxyIsArmedAndGovernedOnlyByItsRelayer` operating on `LIVE_GATEWAY` on a mainnet fork) [5](#0-4) , any future implementation upgrade that appends a new state variable to `IntentsBase` — the pattern the team already relies on for evolving state (e.g. `_paused`/`_relayer` were appended this way in a past change, per `docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md`) — would land at the same slot occupied by whatever `IntrinsicIntents` or `ExtrinsicIntents` declare first, silently corrupting escrow-critical state (`_orders`, `_filled`, `_partialFills`) or gateway configuration (`_params`, `_relayer`) on the live proxy.

### Impact Explanation
`IntentGatewayV2` custodies live user escrow (`_orders` mapping backing intent-based cross-chain swaps) and enforces the single-authorized-relayer trust boundary (`_relayer`) that gates `onAccept`/`onGetResponse` delivery of Hyperbridge-relayed governance and escrow-redemption messages. A storage collision introduced by a routine upgrade that adds a field to `IntentsBase` could overwrite `_relayer` (opening the relayer gate to an unintended address, or bricking authorized delivery), overwrite `_params.host`/`_params.dispatcher` (redirecting trusted host/dispatcher addresses), or corrupt escrow accounting in `_orders`/`_filled`, enabling theft of escrowed funds or a permanent freeze of user assets. Given `IntentsBase` is the diamond's shared storage root for a contract governed entirely by cross-chain upgrade messages (`Execute` → `upgradeToAndCall`), this is a protocol-level upgrade-safety defect with fund-custody consequences, meeting Medium severity.

### Likelihood Explanation
Exploitation does not require malicious intent from any actor described as out-of-scope (admin/governance) — it is a latent defect that manifests the moment the Hyperbridge team performs a routine, well-intentioned upgrade that adds a new field to `IntentsBase` (exactly the pattern already used once for `_paused`/`_relayer`). The codebase's own layout comments ("Appended last to preserve existing storage slots") show this exact operation is anticipated and expected to recur, making collision a realistic, foreseeable outcome of normal maintenance rather than a purely theoretical one. Likelihood is Medium: it is not exploitable by an external attacker directly, but it is a structural upgrade-safety gap in a live, actively-upgraded contract holding user funds.

### Recommendation
Add an explicit storage gap at the end of `IntentsBase` (and re-verify/pad the sibling contracts `IntrinsicIntents` and `ExtrinsicIntents` if they hold state) following OpenZeppelin's convention, e.g. `uint256[50] private __gap;` sized to the current slot usage, consistent with the gap already used in `SimplexPaymaster`. Document the exact slot budget consumed so far (as is already done informally in comments) and enforce it going forward with a storage-layout diff check (e.g. `forge inspect --pretty storage-layout` comparison) in CI before any upgrade is shipped.

### Proof of Concept
Conceptual layout collision:
1. Current `IntentsBase` ends with `_paused` (slot 13, byte 0) and `_relayer` (slot 13, bytes 1-20) — no gap reserved after.
2. `IntrinsicIntents`/`ExtrinsicIntents` (siblings inheriting `IntentsBase`) begin declaring their own state immediately after, at whatever slot the compiler assigns following `IntentsBase`'s last variable.
3. A future upgrade adds `uint256 public newFeature;` to `IntentsBase` (the same "append last" pattern the team used for `_relayer`).
4. On the upgraded implementation, the compiler assigns `newFeature` to the slot immediately after `_relayer`, which is the exact slot currently occupied by the first storage variable of `IntrinsicIntents`/`ExtrinsicIntents`.
5. Post-upgrade, reads/writes to that sibling variable now alias `newFeature`, and vice versa — corrupting whichever escrow/config state was there, with no revert or safety check to detect it (confirmed no `__gap` exists to absorb the new slot) [6](#0-5) .
