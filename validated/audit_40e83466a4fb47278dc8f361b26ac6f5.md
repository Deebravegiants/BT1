### Title
Webhook `shop-domain`/`topic` headers are trusted for shop attribution but are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the *unauthenticated* `shop-domain` header straight to the app's handler as the shop identity. Any party who can obtain one valid `(body, hmac)` pair for the app's shared `api_secret_key` — e.g. a merchant who legitimately installed the app and receives real webhooks for their own shop — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The signature still validates because the shop header is never part of the signed content, so the handler executes attacker-chosen data under an attacker-chosen shop identity.

### Finding Description
The equality that should hold is:

`shop authenticated by HMAC == shop passed to the handler as the tenant identity`

but the code only signs the body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`HmacValidator.validate` verifies the signature purely against `to_signable_string` (i.e. `@raw_body`): [2](#0-1) 

Yet `Registry.process` treats HMAC success as proof of the *entire request's* authenticity and forwards the caller-supplied `shop`, `topic`, `api_version`, and `webhook_id` headers — none of which are signed — directly into the handler payload: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`request.shop`/`request.topic` are read straight from attacker-controlled headers with no cross-check against the signed payload: [4](#0-3) 

Because Shopify apps use a single `api_secret_key` shared across *all* installed shops, an attacker who is a merchant with the app installed (an unprivileged, non-admin actor from the app's perspective) can:
1. Receive a genuine webhook for their own shop, capturing `raw_body` and its valid `x-shopify-hmac-sha256`.
2. POST that identical `(raw_body, hmac)` pair to the app's public webhook endpoint, but with `x-shopify-shop-domain` (and optionally `x-shopify-topic`) rewritten to point at a victim shop.
3. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the shared secret; `Registry.process` then invokes the handler with `shop: <victim>` and the attacker's chosen body content.

This is the direct analog of the report's rounding bug class: a field that is *acted upon* (`shop`, used as the tenant/session key for downstream processing) is not covered by the integrity check (`HmacValidator`/`to_signable_string`), breaking the intended binding between "who Shopify's shared-secret proves sent this" and "which tenant the data is attributed to."

### Impact Explanation
This crosses the tenant boundary that `WebhookMetadata.shop` is meant to enforce: application code that stores/updates data keyed by `data.shop` (e.g., updating a customer record, order status, or app-installation state for a shop) can be made to write attacker-controlled data into another merchant's tenant context, using a validly-signed payload. This matches the Critical "cross-tenant access" impact category, since the vulnerability lets one authenticated app user (any installed shop) inject data attributed to a different, victim shop.

### Likelihood Explanation
Exploitation requires only:
- The attacker to be a legitimate but unprivileged installer of the target app (to obtain one real, validly-signed webhook body/HMAC pair), and
- The app's webhook endpoint to be reachable over the internet (it necessarily is, since Shopify itself must reach it).

No access to `api_secret_key`, access tokens, or any privileged credential is required — only reuse of a signature the attacker legitimately received for their own tenant. This is a realistic "unprivileged internet user" scenario per the analog rules.

### Recommendation
Bind the shop (and ideally topic) into the signed material, or otherwise enforce that `request.shop` matches an expectation independent of the header itself:
- Include the `shop-domain` header value in the HMAC computation (`to_signable_string`) so any substitution invalidates the signature, or
- Require the caller of `Registry.process` to pass the expected shop (from the registered session/install record it is calling on behalf of) and assert `request.shop == expected_shop` before invoking the handler, or
- At minimum, document prominently that `Registry.process` does not authenticate the `shop-domain`/`topic`/`webhook-id`/`api-version` headers and that consuming applications must independently verify shop identity (e.g., against their own installed-shops table) before trusting `WebhookMetadata.shop`.

### Proof of Concept
1. App has two installed shops: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both under the same Shopify app / `api_secret_key`.
2. Attacker's shop receives (or attacker triggers) a real webhook, e.g. `orders/create`, with body `B` and valid header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker sends a forged POST directly to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same HMAC(secret, B)>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <arbitrary>
   x-shopify-api-version: 2024-01

   <body B, attacker-controlled JSON content>
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses these headers/body without objection (`lib/shopify_api/webhooks/request.rb:1-73`).
5. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the shared secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process attacker-supplied data as if it originated from `victim-shop`.
