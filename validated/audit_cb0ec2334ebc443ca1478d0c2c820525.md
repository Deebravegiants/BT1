## Analysis Result

### Title
Shared, permissionless `CallDispatcher.dispatch()` lets any user plant persistent ERC20 approvals and later drain tokens belonging to unrelated orders - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` mirrors the JOJO `withdraw()` bug class: it exposes an unrestricted `dispatch(bytes)` entrypoint that executes an attacker-supplied `Call[]` (arbitrary `to`/`value`/`data`) with the dispatcher itself as `msg.sender`, and it is used as a **single shared singleton** across every `IntentGatewayV2` order and every `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer, rather than being deployed or scoped per order.

### Finding Description
`CallDispatcher.dispatch()` has no access-control modifier and blindly forwards every encoded call: [1](#0-0) 

Because `dispatch()` is `external` with no `onlyGateway`/`onlyHost` restriction, **anyone** can call the deployed `CallDispatcher` directly (not just through `IntentGatewayV2` or the HFT contracts) and instruct it to execute arbitrary calls in its own context — including `IERC20.approve(attacker, type(uint256).max)` for any token.

The same `CallDispatcher` instance is reused for every order's predispatch/postdispatch flow: [2](#0-1) 
and for the token-bridge calldata-execution feature on `onAccept`: [3](#0-2) 

Deployment scripts confirm one `CallDispatcher` is deployed and wired into both `IntentGatewayV2` and `HyperFungibleToken`/`WrappedHyperFungibleToken`: [4](#0-3) [5](#0-4) 

Only the tokens explicitly listed in `order.inputs` / `order.output.assets` are swept back after a call sequence runs; any other token balance that transiently lands on the dispatcher (fee-on-transfer remainders, reward tokens picked up by a swap, rounding dust, etc.) is left behind and not tracked per-order: [6](#0-5) 

The docs acknowledge the dispatcher "holds tokens temporarily during execution" and warn against unlimited approvals, but frame the risk as limited to the order placer's own funds: [7](#0-6) 

That framing misses the cross-order impact: since `CallDispatcher` is a *shared, stateful* contract with no per-order isolation, an attacker can place one order (or call `dispatch()` directly) whose `predispatch.call`/`output.call` contains `token.approve(attackerContract, type(uint256).max)`. That approval is permanent ERC20 state on-chain, granted by the `CallDispatcher` address. From that point on, whenever *any other, unrelated* order's flow causes that token to transiently sit on the same `CallDispatcher` (predispatch assets in flight, unswept dust, or output assets before the sweep call executes), the attacker can call `token.transferFrom(dispatcher, attacker, amount)` directly on the ERC20 contract — completely bypassing `IntentGatewayV2`/`CallDispatcher` access checks — and steal it.

### Impact Explanation
An unprivileged order-placer can permanently corrupt a protocol-wide shared contract (`CallDispatcher`) by planting a spender approval, then later exploit it to steal token balances that belong to other users' in-flight orders or to protocol-owned dust destined for governance sweep. This is a direct analog of the JOJO finding: an "optional calldata" feature that performs unrestricted external calls turns a shared, fund-adjacent contract into a theft vector for arbitrary ERC20 balances routed through it.

### Likelihood Explanation
Likelihood is non-trivial but requires timing: the attacker needs the dispatcher to hold a balance of the approved token at the moment they exploit the stale allowance (e.g., front-running another user's predispatch transfer within the same block, or picking off leftover dust of non-order tokens that is never automatically swept). Because `dispatch()` can be invoked completely independently of any order (anyone can call the deployed `CallDispatcher` directly), the attacker fully controls when to plant the approval and can repeatedly poll/monitor the dispatcher's balances to time the `transferFrom`.

### Recommendation
- Restrict `CallDispatcher.dispatch()` so it can only be invoked by the trusted gateway/HFT contracts (`onlyCaller`/allow-list), removing the ability for arbitrary external accounts to call it directly.
- Avoid a shared, stateful dispatcher: either deploy a fresh, single-use `CallDispatcher` (e.g., via `CREATE2`/minimal proxy) per order/call batch, or have the dispatcher revoke any approvals it granted before returning control (e.g., `approve(target, 0)` cleanup at the end of `dispatch`).
- Sweep *all* token balances (not just the ones explicitly listed in `order.inputs`/`order.output.assets`) off the dispatcher after each `dispatch()` call so no cross-order dust can accumulate.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `predispatch.call = abi.encode([Call({to: USDC, value: 0, data: approve(attackerContract, type(uint256).max)})])`. This executes via `ICallDispatcher(dispatcher).dispatch(...)`, and `CallDispatcher` (the caller as seen by USDC) grants `attackerContract` unlimited USDC allowance.
2. At any later time, when a victim's `placeOrder`/`fillOrder` transaction (or the protocol's own dust-sweep) causes USDC to transiently sit in the same `CallDispatcher` address (e.g., during the predispatch-transfer step before the sweep `dispatch` call executes, or leftover dust from swaps that isn't part of `order.output.assets`), the attacker calls `USDC.transferFrom(dispatcher, attackerContract, USDC.balanceOf(dispatcher))` directly on the USDC contract, using the stale approval from step 1 — no interaction with `IntentGatewayV2` needed.
3. The stolen USDC never returns to the victim's order or the protocol's dust accounting.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
