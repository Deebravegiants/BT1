## Finding

### Title
Silent ERC20 transfer failures in Tron `IntentGatewayV2.withdraw`/`SweepDust` permanently freeze escrowed user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens using raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` instead of OpenZeppelin's `SafeERC20.safeTransfer`, and only checks that the call did not *revert* — it never decodes/validates the ABI-encoded boolean return value. A non-reverting ERC20 (one that returns `false` on failure instead of reverting) can therefore have its `transfer` call "succeed" at the call level while moving zero tokens, yet the contract still finalizes escrow accounting as if delivery happened.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` releases escrow to a beneficiary: [1](#0-0) 

For every non-native token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only guards against the call reverting; it never inspects the returned `bool`. Per EIP-20, a compliant token is not required to revert on failure — it may legitimately return `false`. With such a token, `success` is `true` (the low-level call executed without reverting) even though no tokens were transferred, so execution proceeds to:
```solidity
_orders[body.commitment][token] -= amount;
```
and, at the top of the function, `_filled[body.commitment] = beneficiary;` was already set unconditionally before any transfer is attempted: [2](#0-1) 

The identical unchecked-return pattern is repeated for the transaction-fee payout in the same function, and again in the `SweepDust` handler inside `onAccept`: [3](#0-2) [4](#0-3) 

This directly mirrors the report's root cause: an unchecked ERC20 return value lets a non-reverting token's failed transfer be silently treated as a success, corrupting the protocol's internal accounting of who holds funds. Notably, the rest of the codebase (the non-Tron `IntentGatewayV2.sol`, `IntentsBase.sol`, `IntrinsicIntents.sol`, `HyperFungibleToken.sol`) consistently uses `SafeERC20`'s `safeTransfer`/`safeTransferFrom`, which does decode and check the return value — the Tron file is the outlier that reintroduces this exact bug class: [5](#0-4) 

### Impact Explanation
`withdraw()` is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests, which are triggered by relayed, authenticated ISMP messages that finalize cross-chain intent settlement (single relayed message → fund release path). Once `_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented, the order is permanently marked complete with no retry path, regardless of whether the beneficiary actually received the tokens. If the escrowed/output token is a non-reverting ERC20 that returns `false` on a failed transfer (e.g., paused state, blacklist, transient balance/allowance edge case on the token's own logic), the beneficiary's funds remain trapped in the `IntentGateway` contract while the protocol's bookkeeping shows the order as filled/refunded — a permanent freezing (and effectively de facto loss) of user/solver funds with no recovery mechanism, satisfying the required "permanent freezing of funds" impact bar. The same silent-failure risk applies to `SweepDust`-driven token payouts to `req.beneficiary`.

### Likelihood Explanation
The bug is only triggered when the configured input/output/fee token is a non-reverting ERC20; today's chosen tokens likely revert-on-failure, keeping likelihood low in the current default configuration. However, since token support is admin/params-configurable (`setParams`/`UpdateParams`) rather than hardcoded, and the report class explicitly hinges on "if the protocol adds a non-reverting token," this is a realistic medium-likelihood latent bug rather than a purely theoretical one — consistent with the external report's own severity framing.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept` with OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` elsewhere in this same file), so that both call-reversion and false-boolean-return failure modes cause the transaction to revert instead of silently finalizing escrow state.

### Proof of Concept
1. Admin configures (via `setParams`/`UpdateParams`) an output/fee token that is a standard-compliant ERC20 which returns `false` instead of reverting when a transfer cannot be completed (e.g., a token with a `frozen`/`paused` recipient check that returns `false`).
2. A user's order escrows this token; a relayer delivers a `RedeemEscrow` ISMP message that reaches `onAccept` → `withdraw()`.
3. The intended beneficiary address happens to be blocked/frozen on the token (or any other condition causing the token's `transfer` to return `false` without reverting).
4. `token.call(...)` returns `(true, abi.encode(false))`; the code only checks `success == true` and proceeds.
5. `_filled[body.commitment]` is already set and `_orders[body.commitment][token] -= amount` executes, permanently marking the order filled/refunded even though zero tokens were transferred — the escrowed tokens remain stuck in the `IntentGateway` contract with no way for the beneficiary to reclaim them.
