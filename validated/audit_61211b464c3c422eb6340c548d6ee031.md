### Title
`CallDispatcher.dispatch()` has no caller authentication and can be called by anyone, permanently exposing any residual token/ETH balance on the shared dispatcher to theft - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is `external` with zero access control — no `msg.sender` check restricting it to `IntentGatewayV2`/`IntentsBase`/`HyperFungibleToken`. It executes attacker-supplied `Call[]` (arbitrary `to`, `value`, `data`) using whatever native ETH and token balance the `CallDispatcher` currently holds. This is the same bug class as the JOJO report: an externally reachable function that performs arbitrary `approve`/`call` on assets sitting in the contract, with no verification that the caller is the trusted orchestrator.

### Finding Description
`CallDispatcher.dispatch` decodes an arbitrary `Call[]` from `encoded` and executes each call with the contract's own balance/context, with no restriction on who can invoke it: [1](#0-0) 

`CallDispatcher` is used as a shared, single, reusable "untrusted execution" sink across every order/transfer in `IntentGatewayV2`/`IntentsBase` (predispatch/postdispatch) and `HyperFungibleToken`/`WrappedHyperFungibleToken` (calldata-execution on mint/unlock). Funds are transferred to it, `dispatch()` is invoked with the order/message's calldata, and any assets matching the expected output token set are swept back: [2](#0-1) 

The sweep is scoped strictly to `outputsLen` tokens (`order.output.assets`) known ahead of time — any token balance left on the dispatcher that is *not* one of those explicitly enumerated output tokens (e.g., an intermediate/reward token produced by a multi-hop swap, fee-on-transfer remainder, or accidental/direct ETH sent to the dispatcher's `receive()`) is never collected and is left sitting on the `CallDispatcher` indefinitely: [3](#0-2) 

Because `dispatch()` has no caller check, anyone — not just `IntentGatewayV2`/`IntentsBase`/`HyperFungibleToken` — can call `CallDispatcher.dispatch()` directly with a crafted `Call[]` (e.g., `{to: leftoverToken, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)}`) to sweep out any such un-enumerated residual balance for themselves, exactly analogous to how the JOJO `JOJOFlashLoan()` let an attacker approve/pull assets sitting in `FlashLoanLiquidate`/`FlashLoanRepay` because those functions never checked `msg.sender == JUSDBank`.

### Impact Explanation
Any token or native ETH balance that accumulates on the single, shared `CallDispatcher` — from any user's order, across the protocol's lifetime, whenever postdispatch/predispatch calldata produces output outside the exact enumerated `order.output.assets`/`order.predispatch.assets` set, or ETH is sent to its `receive()` — is permanently and trivially stealable by any unprivileged address. This is a direct theft-of-funds vector reachable from a single unprivileged transaction, satisfying High/Medium severity per the theft-of-funds criterion.

### Likelihood Explanation
Likelihood is elevated because: (1) `dispatch()` is a bare `external` function with no modifier or authentication whatsoever, so exploitation requires no privileged position — only for a non-enumerated residual balance to exist on the dispatcher at any point; (2) the dispatcher is shared across every order/message flowing through `IntentGatewayV2`, `IntentsBase`, `HyperFungibleToken`, and `WrappedHyperFungibleToken`, so any single order whose postdispatch/predispatch calldata yields residual tokens not in the declared output/asset set (a common occurrence with DEX swaps, reward tokens, or slippage remainders) creates a window of exposure; (3) any attacker can simply monitor the dispatcher's on-chain balances and race to call `dispatch()` before the next legitimate sweep captures that token.

### Recommendation
Add caller authentication to `CallDispatcher.dispatch()` restricting it to the trusted contracts that are permitted to route calls through it (e.g., an immutable/whitelisted set of caller addresses set at construction, or an `onlyOwner`/`onlyAuthorized` modifier checked against `IntentGatewayV2`, `IntentsBase`-derived contracts, and `HyperFungibleToken`/`WrappedHyperFungibleToken`), mirroring the JOJO report's recommendation to check `msg.sender` against the trusted orchestrator before executing arbitrary calls.

### Proof of Concept
1. Any order's postdispatch calldata (`order.output.call`) executes a swap that yields a small amount of an intermediate/reward token not listed in `order.output.assets` (i.e., `outputsLen` sweep never checks it) — see the sweep logic in `IntentsBase._execute` at `evm/src/apps/intentsv2/IntentsBase.sol:504-533`, which only iterates tokens the order declared.
2. That intermediate token balance remains on `CallDispatcher` after the transaction completes.
3. Attacker (unrelated to any order) calls `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls = [Call({to: intermediateToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]`.
4. Since `dispatch()` performs no caller check (`evm/src/utils/CallDispatcher.sol:44-61`), the call succeeds and the attacker receives the token balance that legitimately belonged to the protocol/dust-sweep mechanism.

```text
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
```
