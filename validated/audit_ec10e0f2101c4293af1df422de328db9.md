## Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC validated in `ShopifyAPI::Webhooks::Registry.process` never covers the `shop`, `topic`, or `webhook_id` values that are read straight from attacker-controllable HTTP headers. An unprivileged internet user who can obtain any single valid `(raw_body, hmac)` pair for the app (e.g., a webhook triggered on their own installed/test shop) can resubmit that exact body/HMAC to the app's webhook endpoint while swapping the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers to arbitrary values, since none of them are bound by the signature.

### Finding Description
The gem's `VerifiableQuery` interface only requires an `hmac` and a `to_signable_string`, and `HmacValidator.validate` checks the HMAC exclusively against `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be the raw body only: [2](#0-1) 

But `topic`, `shop`, `api_version`, and `webhook_id` are all pulled independently from HTTP headers that are never part of the signed string: [3](#0-2) 

`Registry.process` uses exactly these unauthenticated fields to select the handler and to build the tenant identity (`shop`) passed into the application's handler: [4](#0-3) 

The equality the gem is supposed to guarantee is: `shop-that-was-cryptographically-authenticated == shop-that-the-handler-acts-on`. Because `shop` (and `topic`/`webhook_id`) sit outside `to_signable_string`, that equality does not hold — the HMAC only proves "this body was produced with the app's secret for *some* webhook," not "this body belongs to this shop/topic."

Before the attacker's request: `HmacValidator.validate` passes only for `(body, hmac)` pairs Shopify actually generated for a specific shop/topic, and `request.shop`/`request.topic` are assumed to correspond to that same webhook.
After the attacker's request: an attacker resubmits a Shopify-generated `(body, hmac)` pair they legitimately received (e.g., from a webhook Shopify sent for their own shop) but with a different `shopify-shop-domain` / `shopify-topic` header. `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `@raw_body`, which is unchanged. `Registry.process` then dispatches to the handler for the spoofed topic and constructs `WebhookMetadata` with `shop: request.shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (or `#topic`) coming out of `ShopifyAPI::Webhooks::Registry.process` to select tenant context, write to per-shop storage, or branch handler logic will process attacker-supplied body content under a victim shop's identity or under a different topic than the one Shopify actually signed. This is a cross-tenant integrity issue: it lets a merchant/attacker who runs their own Shopify app installation feed forged, cryptographically-"valid" webhook events labeled with another merchant's shop domain into the app's webhook handlers.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own working app installation capable of receiving at least one legitimate webhook from Shopify (trivial for any developer/merchant able to install the app), and (2) the ability to POST to the app's public webhook endpoint with custom headers, which is inherent to any HTTP-facing webhook receiver. No access token, `client_secret`, or privileged account is required — this fits the "unprivileged internet user" threat model. The gem provides no mechanism to bind `shop`/`topic`/`webhook_id` into the signature, so every consumer of this library is exposed unless they add their own extra validation, which the library does not document as required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the value that is HMAC-verified, or independently cross-check them against a value the app already associates with the shop (e.g., look up the shop by webhook subscription id fetched via an authenticated API call) before constructing `WebhookMetadata` and dispatching to handlers in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw request: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B` under the app's real `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs to the app's public webhook endpoint the same `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `HmacValidator.validate` recomputes the HMAC over `request.to_signable_string` (`= B`) and it matches `H`, so validation succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's B>, ...)`, causing attacker-controlled data to be processed under the victim shop's tenant identity.
