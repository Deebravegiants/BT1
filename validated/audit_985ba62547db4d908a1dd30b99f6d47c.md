### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant data spoofing via `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `HmacValidator` only covers the raw request body, never the headers. `Registry.process` trusts this unauthenticated `shop` value and forwards it directly to the app's webhook handler. This breaks the identity binding `hmac_signed_bytes == authenticated_tenant_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from a header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field — for `Request`, that string is exclusively the raw body, never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands `request.shop` (the unverified header) to the app's handler as the tenant identifier, with no cross-check against any known/installed shop or against data actually present in the signed body: [4](#0-3) 

Because the endpoint is a plain HTTP POST route the app exposes publicly (per the documented Rails example, `request.headers.to_h` and `request.raw_post` are passed straight into `Request.new`), an attacker fully controls every header of the request, including `x-shopify-shop-domain`, while only the raw body must match a previously-obtained valid `(body, hmac)` pair to pass validation: [5](#0-4) 

This is the exact bug class from the referenced report generalized to this gem's rule set: "a field acted on but not covered by the HMAC." In the Ulysses report, the fee/shares math used a value (`sum(pos')-sum(neg')`) that wasn't actually recomputed against the real post-state, letting the attacker exploit the mismatch between the simulated and real state to extract value belonging to the pool. Here, the analogous mismatch is between the bytes actually authenticated (`raw_body` only) and the bytes acted upon to select which tenant's data is affected (`shop` header) — the equality `authenticated_bytes == identity_used_by_handler` does not hold.

### Impact Explanation
An attacker who legitimately owns and operates their own Shopify store with the target app installed will genuinely receive real, correctly-HMAC-signed webhook deliveries from Shopify for their own shop (e.g. `orders/create`, `customers/create`, etc. — normal traffic any merchant naturally receives). Because the signature is computed only over the body, the attacker can capture one such `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` will pass the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. If the app's handler uses `data.shop` to select which tenant's records to create/update/delete (the documented and expected usage pattern), the attacker's own data is written into, or attributed to, another merchant's tenant — a cross-tenant data-integrity/confusion issue, potentially escalating to cross-tenant access depending on what the handler does with `body`/`shop` (e.g., customer PII ingestion, order creation, GDPR/customer-data-request webhooks bound to the wrong shop). This satisfies the Critical impact category "cross-tenant access."

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one authentic `(body, hmac)` pair, which is trivially obtainable by installing the app on any shop they control (free/cheap in the Shopify ecosystem) and capturing a real inbound webhook. No secrets, tokens, or privileged access are required — only an ordinary merchant account and the ability to POST to the app's public webhook route, both squarely within "unprivileged internet user" capability. The vulnerability is fully within this gem's own code path (`Request`, `HmacValidator`, `Registry.process`) and does not rely on the host app ignoring documented guidance — the documented usage pattern in `docs/usage/webhooks.md` is exactly what enables the exploit.

### Recommendation
Bind the `shop` (and ideally `topic`) identity into the value authenticated by the HMAC, or otherwise re-derive/validate `shop` independently of attacker-controlled headers before it is trusted by handlers:
- Include the `shop-domain` (and `topic`) header bytes in `to_signable_string` if Shopify's real signing scheme permits it, or
- Require callers/handlers to independently validate that `request.shop` corresponds to a shop with an active, stored session/installation for this app before processing, and document this as a mandatory step rather than leaving it entirely to handler implementers, or
- At minimum, add an explicit warning in `Registry.process`/docs that `request.shop` is unauthenticated header data and must never be trusted for tenant-scoping without an independent lookup against installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and configures a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook POST to the app's endpoint with headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker crafts a new POST to the same app endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` builds the request from these headers; `Utils::HmacValidator.validate` succeeds because it only hashes `raw_body`: [6](#0-5) 
6. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's own body content, and — following the documented pattern of trusting `data.shop` — processes/persists it under the victim tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
