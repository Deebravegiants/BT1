Audit Report

## Title
Path traversal in workflow artifact HTTP fetcher via unvalidated `filepath.Join` on attacker-controlled URL - (File: `core/services/workflows/syncer/v2/fetcher.go`)

## Summary
`newHTTPFetcher` builds the fetch URL by joining the configured base path with `req.URL` via `filepath.Join`, which collapses `..` sequences across the combined path, and it never validates that the resulting path is still contained within the configured base path — unlike the sibling `newFileFetcher`, which performs an explicit `strings.HasPrefix(fullPath, basePath+separator)` check. Since `req.URL` is populated directly from the on-chain workflow registry's `binaryURL`/`configURL` fields, a workflow registrant can supply a `../` traversal payload to redirect the fetch to an unintended path on the configured artifact-storage host.

## Finding Description
`newHTTPFetcher` at `core/services/workflows/syncer/v2/fetcher.go:243-261` computes `cleanPath := strings.TrimPrefix(filepath.Clean(req.URL), "/")` and then sets `u.Path = filepath.Join(u.Path, cleanPath)`. `filepath.Join` internally calls `Clean` on the combined string, so `..` segments in `cleanPath` are resolved relative to `u.Path` (the base path), not confined to it. There is no subsequent check that the resulting `u.Path` remains prefixed by the original base path — contrast this with `newFileFetcher` at lines 222-231, which explicitly re-validates containment after the join. This value (`req.URL`) originates from `binaryURL`/`configURL` in `Store.FetchWorkflowArtifacts` (`core/services/workflows/artifacts/v2/store.go:144-183`), which come from the on-chain Workflow Registry — data controlled by whoever registers a workflow, not by the node operator.

## Impact Explanation
This is only reachable when a node operator has explicitly configured `CRE.WorkflowFetcher.URL` as an `http`/`https` base URL, which is a deliberate operator opt-in that bypasses the DON/gateway-based fetch (`core/services/cre/cre.go:813-815`, `core/cmd/shell.go:300-305`). This is a documented, intentional bypass mode. Given that reachability fundamentally depends on the node operator choosing a non-default configuration mode, the "attacker" here is not a fully unprivileged network client hitting the node's public API — it is a workflow registrant interacting with a feature the operator deliberately enabled to point at their own artifact-storage host. The realistic impact is limited to redirecting requests to other paths on the *same host* the operator already configured as the artifact source (since `filepath.Join` operates on the URL's path component only, not host/scheme), which typically constrains the blast radius to other tenants'/workflows' artifacts co-located on that same storage service, not arbitrary internal SSRF targets.

## Likelihood Explanation
Exploitation requires (1) an operator-level decision to enable the direct HTTP `WorkflowFetcher` bypass instead of the default gateway consensus path, which is not the default node configuration, and (2) a workflow registration containing a crafted `binaryURL`/`configURL`. Given rule constraints that reject findings requiring "operator-only" or "misconfiguration" preconditions, and that the primary attack surface here is gated behind an explicit non-default operator configuration choice, this significantly weakens the case for treating it as an unprivileged, always-reachable node vulnerability.

## Recommendation
In `newHTTPFetcher`, after computing `u.Path = filepath.Join(basePath, cleanPath)`, verify the resulting path is still prefixed by the original base path (mirroring the check in `newFileFetcher`) and reject the request otherwise.

## Proof of Concept
1. Configure `CRE.WorkflowFetcher.URL = https://storage.example.com/workflows`.
2. Register a workflow whose `binaryURL` is `../../other-tenant/secret.bin`.
3. `newHTTPFetcher` computes `u.Path = filepath.Join("/workflows", "../../other-tenant/secret.bin")`, resolving outside `/workflows`, causing the node to fetch content from an unintended path on the configured host.
