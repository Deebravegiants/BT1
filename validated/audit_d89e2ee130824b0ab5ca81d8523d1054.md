### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` identity used for dispatch and tenant attribution comes from an unauthenticated header. This breaks the equality `shop authenticated by HMAC == shop acted upon by the handler`.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and `request.hmac`: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac`/`Request#shop` are both read from HTTP headers that are never mixed into the signed string: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only compares `compute_signature(verifiable_query.to_signable_string, secret)` against the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is a single app-level secret shared across all shops installing the app (not shop-specific), any party who can obtain one genuinely-signed webhook body+HMAC pair (e.g., by installing the app on their own store and receiving a webhook for a topic they control, such as `app/uninstalled`, `customers/data_request`, or any topic with attacker-controlled content) can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` still returns `true` because the signature check never looked at the shop header, and `Registry.process` forwards the attacker-chosen `request.shop` straight into `WebhookMetadata`, which is what handlers use to identify the tenant: [4](#0-3) 

The equality that should hold is `shop bound by HMAC == shop the handler acts on`; instead the shop is trusted purely from a plaintext header while only the JSON body is cryptographically bound.

### Impact Explanation
This allows cross-tenant data confusion/injection: an attacker-controlled shop can craft webhook payloads (with content they choose, e.g., in `app/uninstalled`, `shop/redact`, or custom topics carrying attacker-supplied fields) that pass HMAC validation and get attributed by the host application to a victim shop of the attacker's choosing. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., looking up or mutating per-shop records, revoking sessions, deleting data, updating billing state), this can lead to cross-tenant access or cross-tenant state corruption for another merchant, without the attacker ever possessing that merchant's credentials.

### Likelihood Explanation
Exploitation requires: (1) the attacker to be a merchant who has installed the app (a normal, low-privilege, unauthenticated-relative-to-other-tenants position achievable by any internet user who installs a public app), (2) knowledge of the app's public webhook endpoint (typically documented/discoverable), and (3) the ability to POST directly to that endpoint outside of Shopify's delivery pipeline (bypassing IP/network restrictions if any exist at the host-application layer, which is outside this gem's control). The gem itself provides no mitigation — `Registry.process` and `HmacValidator` never verify that the signed body's implicit context (topic/shop) matches the header-supplied `shop`/`topic`, so if the host app exposes the endpoint without additional network-level restriction, the attack is straightforward to mount.

### Recommendation
Bind the tenant-identifying headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC before trusting them. Since Shopify's wire format signs only the body, the gem should treat `shop`/`topic`/`webhook_id` headers as unauthenticated metadata and require the host application to independently verify that `request.shop` corresponds to a shop actually authorized/installed for this app (e.g., cross-check against a known session/store record) before acting on webhook content — and document this requirement prominently, since `Registry.process` currently gives callers no signal that `shop` is unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets Shopify deliver a normal webhook, e.g. for `app/uninstalled`, capturing the raw POST: headers (`x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-webhook-id`) and the raw JSON body.
2. Attacker resends the identical body and the identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`@raw_body`, unchanged) — validation succeeds: [5](#0-4) 
4. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [6](#0-5) 
5. Any handler logic keyed on `data.shop` for tenant-scoped effects (session teardown, data deletion, state changes) now operates against the victim shop's identity using attacker-supplied body content.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
