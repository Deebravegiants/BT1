### Title
Unvalidated `total_leaves`/`leafCount` in BEEFY Parachain Heads Merkle Multi-Proof Enables Forged State Commitments - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The BEEFY consensus verifier accepts a relayer-supplied `total_leaves` (Substrate) / `leafCount` (EVM) value that determines the tree structure used to verify the parachain-heads merkle multi-proof against `heads_root`. This value is never cryptographically committed to by the relay chain validators and is not validated against the actual/expected number of parachains, mirroring the LineaRollup `l2MerkleTreesDepth` bug class where an unvalidated tree-size/depth parameter is trusted at face value during proof verification.

### Finding Description
`ParachainProof` carries a `total_leaves: u32` field supplied by the relayer as part of the unsigned `ConsensusMessage`: [1](#0-0) 

`verify_parachain_headers` passes this attacker-controlled value straight into `MerkleProof::verify` as the tree size, which determines how the k-index/multi-proof reconstruction algorithm groups and hashes the supplied proof nodes into a root: [2](#0-1) 

The only value that is actually authenticated by the BEEFY validator signatures is the MMR root (and, transitively, the `heads_root` embedded as MMR leaf extra data). The *size/depth* of the parachain-heads tree used to interpret a given multi-proof against that root is not part of any signed commitment — it is taken as-is from the relayer's message. This is the exact bug class described in the report and explicitly called out in the project's own documentation on merkle proof design: [3](#0-2) 

The EVM-side `EcdsaBeefy.sol` has the identical pattern — `proof.leafCount` is taken directly from the submitted `ParachainProof` struct and fed into `MerkleMultiProof.VerifyProof` without any check against a known/expected parachain count: [4](#0-3) 

Because the multi-proof verification algorithm derives k-indices and layer boundaries purely from the supplied leaf indices and the supplied `total_leaves`/`leafCount`, an attacker who controls this parameter can attempt to construct a "phantom" tree shape (too shallow or too deep relative to the real parachain-heads tree) that hashes to the same `heads_root`, allowing forged/incorrect parachain header inclusion to be accepted as valid — precisely analogous to Issue #2/#3 in the external report (proving intermediate nodes or phantom leaves due to a mismatched, unconstrained depth/size parameter).

### Impact Explanation
If a malicious or buggy relayer submits a mismatched `total_leaves`/`leafCount`, the multi-proof verification could accept a forged parachain header inclusion or reject legitimate ones. Since `verify_parachain_headers`/`verifyParachainHeaderProof` produces the `IntermediateState`/state commitments that pallet-ismp and downstream ISMP consumers rely on for state membership/non-membership proofs of cross-chain messages, a successful forgery would result in an unsound state commitment being accepted by the light client — enabling forged message delivery for that parachain, or a permanent inability to deliver/verify legitimate messages from the affected parachain (denial of the route), both of which are explicitly in-scope high-impact outcomes.

### Likelihood Explanation
Consensus updates (BEEFY `ConsensusMessage` submission) are permissionless/unsigned-relayer-driven operations — any relayer can submit a consensus proof, similar to how `l2MerkleTreesDepth` in the original report was attacker/operator-controlled input. The exploit does not require compromising validators or governance, only crafting a proof whose depth/size metadata disagrees with the real tree, i.e., it is reachable from a single relayed consensus message.

### Recommendation
Bind `total_leaves`/`leafCount` to a value that is independently verifiable or cryptographically committed — e.g., commit the parachain-heads leaf count as part of the signed BEEFY payload/MMR leaf extra data, or validate it against the locally-tracked known set of registered para IDs before use. Additionally, bound the tree depth/size to a sane maximum, and reject proofs whose declared size and shape are inconsistent with the number/values of `leaf_indices` supplied, following the mitigation model the report recommends (include the depth/size in what's cryptographically committed, and validate its bounds before verification).

### Proof of Concept
Not executable from the index alone (no local BEEFY testnet/harness available here), but the exploit path is:
1. Relayer submits a `ConsensusMessage` with a valid signed BEEFY commitment/MMR proof (so `heads_root` is accepted as authentic).
2. In the same message, the relayer supplies a `ParachainProof.total_leaves` (or `leafCount` on EVM) that differs from the real parachain-heads leaf count, alongside crafted `proof` items designed so that `MerkleProof::verify`/`MerkleMultiProof.VerifyProof` reconstructs `heads_root` from a forged/incorrect parachain header entry.
3. If successful, `verify_parachain_headers`/`verifyParachainHeaderProof` returns an `IntermediateState`/`ParachainHeader` for a header that was never actually included in the true parachain-heads tree, corrupting the state commitment used by ISMP for subsequent message proofs.

/// Verifies the inclusion of parachain headers in the parachain heads root via a merkle multi proof
pub fn verify_parachain_headers<H: Keccak256>(
	heads_root: H256,
	parachain_proof: ParachainProof,
) -> Result<Vec<ParachainHeader>, Error> {
	if parachain_proof.parachains.is_empty() {
		return Ok(vec![]);
	}

	let mut indexed_leaf_hashes = Vec::with_capacity(parachain_proof.parachains.len());

	for para_header in &parachain_proof.parachains {
		let leaf = (para_header.para_id, para_header.header.clone());
		let hash: [u8; 32] = H::keccak256(&leaf.encode()).into();
		indexed_leaf_hashes.push((para_header.index as usize, hash));
	}

	indexed_leaf_hashes.sort_by_key(|(index, _)| *index);

	let (leaf_indices, leaf_hashes): (Vec<usize>, Vec<[u8; 32]>) =
		indexed_leaf_hashes.into_iter().unzip();
	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(parachain_proof.proof.clone());
	let valid = merkle_proof.verify(
		heads_root.0,
		&leaf_indices,
		&leaf_hashes,
		parachain_proof.total_leaves as usize,
	);

## Second Pre-image Attacks

[Second pre-image attacks](https://en.wikipedia.org/wiki/Merkle_tree#Second_preimage_attack) arise when merkle tree proof schemes do not check the tree depth when verifying merkle proofs. This allows for attackers to construct either arbitrarily deep or shallow trees that have the same root hash as the verifier’s, in order to fool the verifier that some forged items are in the original tree.

In order to mitigate this, given our current proof scheme, **it is necessary that the verifier knows the number of items in the tree**. The height of the tree can be computed from it's leaf count and compared to the length of the 2D proof array (which encodes the height of the tree). If they do not match then the proof can safely be rejected because it describes a different tree and is  attempting to perform a pre-image collision attack.

    // @dev Verifies that some parachain header has been finalized, given the current trusted consensus state.
    function verifyParachainHeaderProof(bytes32 headsRoot, ParachainProof memory proof)
        internal
        pure
        returns (IntermediateState[] memory)
    {
        uint256 len = proof.parachains.length;
        MerkleMultiProof.Leaf[] memory leaves = new MerkleMultiProof.Leaf[](len);
        IntermediateState[] memory intermediates = new IntermediateState[](len);

        for (uint256 i = 0; i < len; i++) {
            Parachain memory para = proof.parachains[i];
            Header memory header = Codec.DecodeHeader(para.header);
            if (header.number == 0) revert IllegalGenesisBlock();

            leaves[i] = MerkleMultiProof.Leaf(
                para.index,
                keccak256(bytes.concat(ScaleCodec.encode32(uint32(para.id)), ScaleCodec.encodeBytes(para.header)))
            );

            StateCommitment memory commitment = header.stateCommitment();
            intermediates[i] =
                IntermediateState({stateMachineId: para.id, height: header.number, commitment: commitment});
        }

        if (len > 0) {
            bool valid = MerkleMultiProof.VerifyProof(headsRoot, proof.proof, leaves, proof.leafCount);
            if (!valid) revert InvalidMmrProof();
        }

        return intermediates;
    }
