### Title
Starknet address validation accepts felt values ≥ the Starknet field prime, letting withdrawals target an address that cannot exist on-chain - (`packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
`validateStarknetAddress` only checks that the destination is a `0x`-prefixed hex string of 1–64 hex digits; it never checks the numeric value against the Starknet field prime (`2^251 + 17*2^192 + 1`). A 64-hex-digit value larger than the prime is not a valid felt252 and cannot correspond to any real Starknet account, yet `validateAddress`/`OmniBridge.validateWithdrawal` accept it and let the SDK build and sign a withdrawal intent to it.

### Finding Description
The broken equality: "value accepted by `validateAddress(address, Chains.Starknet)`" should equal "value that is a valid felt252 address on Starknet (i.e. `< STARKNET_PRIME`)". The implementation only enforces the equality "matches `/^0x[a-fA-F0-9]{1,64}$/`", which is a strictly weaker condition: [1](#0-0) 

A 64-hex-digit string can represent any value up to `2^256 - 1`, but Starknet's field prime is `2^251 + 17*2^192 + 1 ≈ 3.618e75`, far smaller than the max value representable in 64 hex digits. So an address like `0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff` passes the regex but is not a valid felt on Starknet.

Call path: `OmniBridge.validateWithdrawal` calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` and only rejects on `false`: [2](#0-1) 

Nothing later in `validateWithdrawal`, `createWithdrawalIntents`, `createWithdrawIntentsPrimitive`, or `deriveOmniWithdrawIntentParams` re-checks the numeric magnitude of the destination address — `omniAddress(ChainKind.Strk, destinationAddress)` is a plain string-formatting call, not a validator: [3](#0-2) 

The value is embedded verbatim as `recipient` in the `ft_withdraw` intent's `msg`, which is what the intents contract and the Omni Bridge relayer act on: [4](#0-3) 

None of the other guards catch this: `compareAddresses` only checks for equality with the token contract address (`DestinationAddressMatchesTokenAddressError`), `supports()`/`assert` checks concern asset/route validity and fee values, and the intents contract's own signature/nonce checks operate on the NEAR intent, not on the semantic validity of an embedded Starknet felt. The existing test suite only verifies length bounds and format, never the field-prime bound: [5](#0-4) 

### Impact Explanation
The `ft_withdraw` intent is signed and submitted with a `recipient` that is not a valid Starknet felt/address. Once relayed to the Omni Bridge connector on Starknet, the contract cannot credit any real account with this value — the withdrawn funds are debited from the user's intents balance but cannot be delivered, and there is no legitimate recovery path since the destination never existed. This matches the Critical category: "funds delivered to a wrong address/chain/contract with no recovery." Each call to `validateWithdrawal`/`createWithdrawalIntents` with such a destination is independently exploitable/repeatable, since the format check never changes.

### Likelihood Explanation
Preconditions: an Omni Bridge withdrawal route with `Chains.Starknet` as destination (`4fd76f4: Add starknet support for Omni Bridge`). Attacker cost is zero — any unprivileged NEAR Intents user (or integrator forwarding an attacker/counterparty-supplied `destinationAddress`) can simply provide a 64-hex-digit value ≥ the field prime; this requires no special access, only a normal SDK call with a crafted `destinationAddress`. The condition is easy to hit unintentionally too (e.g. from address generation/typo bugs on the caller side), increasing real-world exposure beyond deliberate attack.

### Recommendation
In `validateStarknetAddress`, after the regex check, parse the hex value as a `BigInt` and reject values `>= STARKNET_PRIME` (`2n**251n + 17n*2n**192n + 1n`), matching how `validateAleoAddress` checks `x >= P` for its own field prime elsewhere in the same file.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { validateAddress } from "../src/lib/validateAddress";
import { Chains } from "../src/lib/caip2";

const STARKNET_PRIME = 2n ** 251n + 17n * 2n ** 192n + 1n;

describe("validateStarknetAddress field-prime bound", () => {
  it("accepts a 64-hex value that exceeds the Starknet field prime (bug)", () => {
    const oversized = `0x${"f".repeat(64)}`; // 2^256-1, >> STARKNET_PRIME
    const numericValue = BigInt(oversized);

    // Left side: what the SDK currently believes
    const acceptedBySdk = validateAddress(oversized, Chains.Starknet);

    // Right side: ground truth — is this a valid felt/address on Starknet?
    const isValidFelt = numericValue < STARKNET_PRIME;

    expect(acceptedBySdk).toBe(true);   // current (buggy) behavior
    expect(isValidFelt).toBe(false);    // ground truth: NOT a valid felt
    expect(acceptedBySdk).not.toBe(isValidFelt); // equality is broken
  });
});
```
This test mocks nothing beyond calling the pure function; it demonstrates that `validateAddress` returns `true` for a destination that is provably not a valid Starknet felt, confirming the DESTINATION TRUTH equality is violated.

/**

 * Starknet addresses are felt252 (252-bit field elements) represented as
 * hex strings with 0x prefix (up to 64 hex characters)

function validateStarknetAddress(address: string): boolean {
	return /^0x[a-fA-F0-9]{1,64}$/.test(address);
}
