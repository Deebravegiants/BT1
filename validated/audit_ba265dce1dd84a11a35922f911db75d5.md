### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw request body only, while the shop identity used to route the webhook to the host application's tenant-specific handler is read from a separate, unauthenticated header. Any party who possesses one validly-signed webhook body/HMAC pair can replay it with a different `shop-domain` header and it will still pass HMAC validation, letting them impersonate any other shop to the consuming app.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are pulled from HTTP headers that are never part of the signed material: [2](#0-1) 

`HmacValidator.validate_signature` recomputes the signature only over `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then forwards the caller-supplied, unauthenticated `request.shop` value straight into the tenant-identifying `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding the code implicitly relies on is:
`HMAC-validated(body)` == `tenant-identity(shop header)`

but the actual code only proves `HMAC-validated(body)` and never proves `HMAC-validated(shop)`. Since the `shop-domain` header is excluded from the signable string, it can be freely substituted post-hoc without invalidating the signature, as long as the attacker has *any* prior legitimately signed body (e.g. from their own store's webhook, or from a topic whose body is generic/predictable like `app/uninstalled` or a webhook with attacker-controlled content such as `orders/create` in the attacker's own dev/test store).

### Impact Explanation
This breaks the shop/tenant authentication boundary that the gem is expected to enforce for `Registry.process`: any user who can install the app on one shop (attacker-controlled shop) and receive one legitimately-signed webhook can relabel it as belonging to an arbitrary victim shop, and the gem will still report `hmac valid` and dispatch it to the host application's webhook handler tagged with the victim's shop domain. Depending on how the host application uses `WebhookMetadata#shop` (most `shopify_app`-style apps use it to look up/act on per-tenant records), this enables cross-tenant data injection/corruption using attacker-controlled webhook bodies — satisfying the "cross-tenant access" criterion (Critical).

### Likelihood Explanation
Requires only an unprivileged actor who can install the app on their own store (a normal, unprivileged onboarding step for any embedded/public Shopify app) and can then issue raw HTTP requests to the app's public webhook endpoint (no `api_secret_key` or Shopify's private credentials are ever needed — only a captured/legitimate body+HMAC pair). Because the signature never binds the shop header, capturing and replaying a webhook with a substituted `shop-domain` header is trivial and repeatable.

### Recommendation
Include the shop identity in the signed material, or otherwise cryptographically bind `shop` to the payload before trusting it for handler dispatch. Concretely:
- Change `Request#to_signable_string` (or add a distinct verification step in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified, not just the raw body.
- Alternatively, require the consuming application to cross-check `request.shop` against a shop that it independently trusts (e.g., an installed/known shop record) before acting on the webhook, and document this requirement prominently since the current API silently exposes an unauthenticated `shop` accessor.

### Proof of Concept
1. App is installed on attacker's own store `attacker-shop.myshopify.com`. Attacker triggers/receives a legitimate webhook, e.g. `orders/create`, with raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a new POST to the app's webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — validation succeeds because `to_signable_string` never includes the shop header.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`.
5. The host application processes attacker-controlled body content under the identity of `victim-shop.myshopify.com`, despite the request never having originated from Shopify on behalf of that shop.
