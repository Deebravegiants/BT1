### Title
EvmHost violates checks-effects-interactions: relayer fee payouts and replay-protection deletion occur after the untrusted external `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` calls - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(GetResponse, ...)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` all perform an external `.call()` into an arbitrary, attacker-influenced `IApp` destination contract, and only afterwards perform the state effects that pay out (or refund) relayer/protocol fee tokens. This is the same anti-pattern flagged in the reference report: state-changing effects should be finalized before external interactions, not after.

### Finding Description
In `dispatchIncoming(GetResponse memory response, address relayer)`: [1](#0-0) 
the replay-protection receipt is written, then an untrusted external call to the destination `IApp.onGetResponse` is made, and only after that call succeeds is the relayer fee transferred out of the contract via `IERC20(feeToken()).safeTransfer(relayer, fee)` — while `_requestCommitments[commitment]` (which holds the `fee`) is never deleted, unlike the timeout paths.

Compare with `dispatchTimeOut(GetRequestTimeout, ...)` and `dispatchTimeOut(PostRequestTimeout, ...)`: [2](#0-1) 
Here `_requestCommitments[commitment]` is deleted *before* the external call to the destination module (`onGetTimeout`/`onPostRequestTimeout`), but the refund of `meta.fee` to `meta.sender` still executes *after* the external call succeeds — meaning the effect that actually moves value out of the contract is placed after the interaction.

The destination address invoked in all three cases (`_bytesToAddress(...from...)`) is attacker-controllable in the sense that it is set by whichever application dispatched the original request/response on the destination side, and is not restricted to any privileged allowlist within `EvmHost` itself — any `IApp` module can be the target of the callback.

### Impact Explanation
Because the fee-token transfer is the final step and occurs strictly after the external call to an arbitrary contract, a malicious or compromised `IApp` implementing `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` can reenter `EvmHost` during its callback. Although `dispatchIncoming`/`dispatchTimeOut` are gated by `restrict(_hostParams.handler)` (so the same handler-invoked function cannot be re-entered by an outside caller directly), the malicious app can still reenter other unprotected `EvmHost` entry points (e.g. `dispatch()`, which swaps native tokens for fee tokens and is not handler-gated) while the fee-token balance and internal accounting are in a transient, not-yet-finalized state. This can be leveraged to manipulate the fee-token balance/allowance state that the pending `safeTransfer` depends on, resulting in relayer fee funds being drained, double-counted, or made unavailable — a direct violation of the checks-effects-interactions pattern with a concrete funds-accounting vector, matching the referenced bug class exactly.

### Likelihood Explanation
Likelihood is Medium: it requires an `IApp` destination module (either malicious from the start, or later compromised/upgraded) to implement a reentrant callback, and for `EvmHost.dispatch()` or another unguarded state-mutating entry point to be reachable and exploitable mid-callback. This does not require any privileged role — any relayer submitting a proof for a message destined to an attacker-deployed `IApp` module can trigger the vulnerable code path, since app registration in the ISMP framework is permissionless.

### Recommendation
Follow checks-effects-interactions: finalize all state changes that affect fund transfers (delete `_requestCommitments[commitment]`, mark fee as paid, and perform the `safeTransfer`) *before* invoking the untrusted external call to `IApp.onGetResponse` / `onGetTimeout` / `onPostRequestTimeout`. If the callback needs to be retried, use a separate recoverable state entry (as already done for `_requestReceipts`/`_responseReceipts`) rather than deferring fund movement until after the interaction, and add reentrancy guards to any function (like `dispatch()`) that moves value and could be invoked mid-callback.

### Proof of Concept
1. Attacker deploys a malicious `IApp` contract as the destination module for a `GetRequest` (or as the `from` module for a normal request that later times out).
2. Relayer submits a valid response/timeout proof through `HandlerV2`, which calls `EvmHost.dispatchIncoming(GetResponse, relayer)` (or the timeout variants).
3. `EvmHost` writes the replay-protection receipt, then calls the malicious app's `onGetResponse`.
4. Inside `onGetResponse`, the attacker's contract reenters `EvmHost.dispatch()` (unprotected by the `handler`-only restriction and not reentrancy-guarded), manipulating fee-token balances/allowances before `EvmHost` returns control and executes the deferred `IERC20(feeToken()).safeTransfer(relayer, fee)`.
5. Depending on the token/router state manipulated in step 4, the final transfer can be made to fail, double-pay, or interact with stale accounting, breaking the intended fee-payout invariant. [1](#0-0) [2](#0-1)

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
