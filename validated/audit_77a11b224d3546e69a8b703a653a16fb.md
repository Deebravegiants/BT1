### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw body only, while the `shop` (and `topic`) values used by the app to attribute the webhook to a tenant are taken from unauthenticated headers, breaking the binding `authenticated_bytes == acted_on_shop`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `Request#shop` and `Request#topic` are read from the `shopify-shop-domain`/`x-shopify-shop-domain` and `shopify-topic` headers, which are never part of the signed string [2](#0-1) . `Registry.process` only calls `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (i.e., only the body) against `Context.api_secret_key` [4](#0-3) . After that single check passes, `request.shop` is forwarded unmodified as the tenant identity to the app's webhook handler [3](#0-2) .

Because `api_secret_key` is the app's single client secret shared across all merchant shops that install the app, any party who can obtain one validly-signed webhook body/HMAC pair (e.g., from their own shop's installation, which legitimately receives Shopify-signed webhooks) can resend that same `raw_body`+`hmac` to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. The HMAC still validates because the header is not part of the signed content, so `Registry.process` executes the handler believing the event originated from the victim shop, breaking the identity binding `shop authenticated == shop acted upon`.

### Impact Explanation
This is a cross-tenant boundary break: an attacker controlling one legitimate shop installation can forge webhook events (including mandatory GDPR topics like `customers/redact`, `customers/data_request`, `shop/redact`, or business events like `orders/create`, `app/uninstalled`) attributed to any other shop's tenant data in the host app, without possessing that shop's access token or the app's `client_secret`. This maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) being able to run/own any shop that installs the target app to legitimately receive a signed webhook, and (2) sending an arbitrary HTTP POST to the target app's public webhook endpoint with a spoofed `shopify-shop-domain` header while replaying the captured body/HMAC. No secrets, tokens or privileged access are required beyond normal use of the app as an unprivileged merchant/installer, which matches the "unprivileged internet user" threat model.

### Recommendation
Include `shop` (and `topic`, `webhook_id`, `api_version`) in the signed/verified material, or otherwise cryptographically bind the header-derived tenant identity to the signature — e.g., verify the HMAC over `shop-domain header + raw_body` (matching Shopify's documented practice of validating headers alongside body per-topic), and reject requests where the shop the webhook claims to be from cannot be independently corroborated (e.g., against the session/shop that originally registered for that topic).

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and installs the target app, receiving genuine Shopify-signed webhooks such as `customers/redact` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a forged HTTP POST to the app's webhook endpoint with the exact same body `B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` (`Request#to_signable_string`) and succeeds, since `B` and `H` are unchanged [1](#0-0) [5](#0-4) .
4. The registered handler is invoked with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to process/act on data as if the event legitimately originated from the victim shop.
