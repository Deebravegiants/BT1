## Title
Fee-on-transfer tokens cause escrow over-crediting and fund freezing in the Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol:338-469`) computes escrowed amounts from the user-requested `order.inputs[i].amount` and never measures the actual token balance the gateway receives via `safeTransferFrom`. Any unprivileged user who places an order using a fee-on-transfer ERC20 as an input token causes the contract's internal escrow ledger `_orders[commitment][token]` to be credited for more tokens than the contract actually holds.

### Finding Description
In the non-predispatch branch, tokens are pulled with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and the escrow is then unconditionally incremented by `reducedInputs[i].amount`, which is derived purely from `order.inputs[i].amount` (minus the protocol fee percentage) — not from any post-transfer balance delta: [1](#0-0) 

The `reducedInputs` values used for the escrow credit and for the commitment hash are computed earlier, entirely from `order.inputs[i].amount` (the caller-specified amount) with no adjustment for fee-on-transfer deduction: [2](#0-1) 

The predispatch branch has the same issue: it computes `dust = balance - requiredAmount` using the *dispatcher's* balance (to catch overpayment/excess), but still credits escrow with `reducedInputs[i].amount`, which was derived from the pre-transfer `order.inputs[i].amount`, not the amount actually swept into the gateway after fee-on-transfer deductions: [3](#0-2) 

This is in contrast to the mainline EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`), which was explicitly hardened against this exact bug class: it snapshots gateway/dispatcher balances before and after each transfer and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment and crediting escrow: [4](#0-3) [5](#0-4) 

The Tron deployment of `IntentGatewayV2` never received this fix, so it remains vulnerable to the fee-on-transfer accounting mismatch described in the external report.

### Impact Explanation
Because escrow (`_orders[commitment][token]`) is credited for the full requested amount instead of what was actually received, the gateway's internal bookkeeping overstates its real token balance for that order. When the order is later filled or refunded and a solver/beneficiary attempts to withdraw the escrowed amount via `_withdraw`/`onAccept`, the contract will attempt to `safeTransfer` more tokens than it physically holds for that token, either:
- Reverting the withdrawal, permanently freezing both the solver's committed output tokens and the user's remaining input escrow (deadlock, since the order can never be fully settled), or
- Succeeding by draining balance that belongs to other users' unrelated escrowed orders of the same token, causing insolvency and fund loss for unrelated order holders once they attempt to withdraw.

This satisfies "permanent freezing of funds" / concrete fund-loss criteria: escrow is unbacked by actual token balance, and the erroneous state is written directly into the commitment/escrow used to authorize withdrawal.

### Likelihood Explanation
This is reachable by any unprivileged user calling `placeOrder` with a fee-on-transfer token as an input asset — no privileged role or special conditions required beyond selecting such a token, which the contract does not restrict. Given stablecoins like USDT have contractual code paths for enabling transfer fees (as noted in the original report), this could be triggered even by ordinary tokens that add/enable such fees post-deployment, or immediately by deliberately deploying/using a fee-on-transfer token as bait to lock others' funds.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol`: measure the actual balance received by the gateway (and, for the predispatch path, the dispatcher) via balance-before/balance-after snapshots around each `safeTransferFrom`/sweep, and use that measured amount — not the caller-supplied `order.inputs[i].amount` — for computing `reducedInputs`, the commitment hash, and the escrow credit in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with an input token that charges e.g. 1% fee-on-transfer, requesting `amount = 1000e18`.
2. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; the gateway actually receives only `990e18` due to the token's transfer fee.
3. `reducedInputs[0].amount` was computed earlier as `1000e18` (minus any protocol fee), not `990e18`.
4. `_orders[commitment][token] += reducedInputs[0].amount` credits escrow for `~1000e18` (or the protocol-fee-reduced version of that number), while the gateway's actual token balance is only `990e18`.
5. When a solver later fills the order and attempts to redeem the escrow for the full credited amount via the `RedeemEscrow`/`onAccept` path (shared `_withdraw` logic), the `safeTransfer` call attempts to move more tokens than the contract holds, reverting and freezing funds, or succeeding at the expense of other users' escrowed balances of the same token.
