### Title
`drop_oldest()` evicts the newest queued biometric package instead of the oldest, causing stale personal-custody data to jam the upload queue - ([File: src/agents/data_uploader.rs])

### Summary
The reported Andromeda bug is a class of "accounting/queue-eviction mismatch" issue: an entity is supposed to remove/settle the correct queue element, but a value/element different from the one intended is actually removed, causing incorrect items to remain stuck while others are wrongly discarded, jamming the queue. The `orb-core` `data_uploader` agent's in-memory `Queue::drop_oldest` implements the analogous flaw: it is invoked to make room for a new personal-custody package (PCP, biometric upload data) by removing the *oldest* queued entry, but it actually removes the *most recently pushed* entry.

### Finding Description
`Queue` maintains a `VecDeque<Pcp>` (in the live, non-persistent path) where new PCPs are appended with `push_back` [1](#0-0) , and normal dequeuing for upload correctly takes from the front (`pop_front`, oldest-first, FIFO) [2](#0-1) .

However, `drop_oldest`, which is called specifically to evict the oldest package once the queue reaches its `dropping_threshold` before pushing a new one [3](#0-2) , removes from the **back** of the deque instead of the front: [4](#0-3) 

Since `push_back` appends to the back and `drop_oldest` also pops from the back, the function actually discards the most recently pushed (i.e., newest) entry in the queue rather than the truly oldest one. The genuinely oldest entries (pushed first, at the front) are never evicted by this mechanism and persist in the queue indefinitely as long as new pushes keep triggering `drop_oldest`.

This mirrors the root cause pattern in the Sherlock report: an operation intended to reconcile/settle one specific queue element instead operates on the wrong one, producing incorrect queue state and blocking/starving proper processing of the intended items.

### Impact Explanation
The `data_uploader` queue carries `Pcp` (personal custody package) entries containing raw biometric capture data destined for backend upload/retention, tagged with `signup_id` and `user_id` [5](#0-4) . Because `drop_oldest` discards the newest arrival instead of the oldest, under sustained load (tier queue at its dropping threshold), the freshly captured biometric package for the most recent signup is silently dropped and never uploaded, while stale packages from earlier signups remain stuck in the queue occupying capacity. This is a genuine biometric-upload/retention integrity defect: current signups' custody data can be permanently lost from the upload pipeline while older/stale entries block the queue, which is directly analogous to the reported "queue blocking due to inaccurate accounting" impact.

### Likelihood Explanation
This code path is reachable in production: the live queue variant used by `Agent::run` is always the in-memory `Queue::Memory` variant (`Queue::new_memory()`), not the `#[allow(dead_code)]` `Persistent` variant [6](#0-5) . The eviction path triggers automatically whenever a tier's queue length reaches `pcp_tier{1,2}_dropping_threshold`, which is a normal operational condition under sustained signup throughput or slow/unavailable backend uploads [7](#0-6) , making this readily reachable without any attacker action.

### Recommendation
Change `drop_oldest` to evict from the front of the deque (`pop_front`) to match the FIFO semantics used elsewhere (`push_back`/`pop_front`), so the actual oldest entry is discarded and newly captured biometric packages are preserved and uploaded:
```rust
async fn drop_oldest(&mut self) {
    match self {
        Self::Memory { queue } => {
            queue.pop_front();
        }
        ...
    }
}
```

### Proof of Concept
1. Configure `pcp_tier1_dropping_threshold = 2`.
2. Push PCP `A`, then `B` → queue = `[A, B]` (A oldest, B newest).
3. Push PCP `C`: queue length (2) equals threshold, so `drop_oldest()` fires before the push, calling `pop_back()` → removes `B` (the newest), leaving `[A]`; then `C` is pushed → queue = `[A, C]`.
4. Repeat with `D`: `drop_oldest()` removes `C` (again the newest just added), leaving `[A]`, then pushes `D` → queue = `[A, D]`.
5. Entry `A` (the true oldest) is never evicted despite repeated overflow events, while every subsequent freshly-pushed package (`B`, `C`, ...) is discarded before ever being uploaded — confirming the queue keeps stale data and drops the newest biometric packages instead of the intended oldest ones.
