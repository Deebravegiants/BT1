The webhook `Registry.process` verifies the HMAC over `request.hmac` computed via `Utils::HmacValidator.validate(request)`, and `Request#to_signable_string` returns only `@raw_body`. `Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed content.### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-domain spoofing / cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the shop identity used to route and label the webhook data (`request.shop`) is read from an HTTP header that is never included in the signed payload. This breaks the intended binding "shop that produced a valid HMAC == shop the app processes data for."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `Utils::HmacValidator.validate`: [1](#0-0) 

`hmac` is derived from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop` is read directly from the `shop-domain` header, which is not part of the signed material at all: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header) to the app handler as the tenant identifier, with no additional check that this shop matches anything cryptographically tied to the signed body: [4](#0-3) 

The `HmacValidator` computes the signature over `to_signable_string` and compares it to the value taken from the (also attacker-controlled, but that's fine since it's part of the check) `hmac-sha256` header — but it never binds `shop`: [5](#0-4) 

Because all shops that install the same app share one `api_secret_key`, the HMAC over the body only proves "this request was signed with my app's secret" — not "this specific shop sent this specific body." An attacker who controls (or has installed the app on) shop A can capture one legitimately signed webhook body+HMAC pair for shop A (e.g., by triggering a webhook event on their own store, which they fully control), then replay that exact `raw_body`/`hmac-sha256` pair to the victim app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with shop B's domain. The HMAC check still passes (it only checks the body), and `Registry.process` will call the handler with `shop: "shop-B.myshopify.com"` even though the payload was never actually associated with shop B.

This maps directly to the requested analog class: "a field acted on but not covered by the HMAC" — here, the `shop` field used for tenant routing is completely outside the HMAC's protected scope, unlike the OAuth `AuthQuery`, which explicitly includes `shop` inside `to_signable_string` (see `lib/shopify_api/auth/oauth/auth_query.rb:34-43`) precisely to prevent this class of bug for the OAuth callback flow. The webhook `Request` object omits the same protection.

### Impact Explanation
This is a cross-tenant integrity violation: an attacker can cause data attributed to their own shop's webhook body to be processed under a victim shop's identity inside the host application. Depending on how the host app's `WebhookHandler#handle(data:)` uses `data.shop` (e.g., to look up the shop's session/access token, write records, or gate business logic per-tenant), this can lead to cross-tenant data corruption, incorrect access-token lookups being triggered for the wrong shop, or injected fake events (e.g., fraudulent `orders/create`, `app/uninstalled`, `shop/redact`) being attributed to a victim's store — all without possessing that victim's credentials. This satisfies the "cross-tenant access" criteria for a High-severity finding, since the identity binding between the authenticated bytes (raw body) and the claimed tenant (`shop` header) is never verified.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on at least one shop they control (a normal, unprivileged action for anyone using the Shopify App Store) in order to obtain one valid `(raw_body, hmac-sha256)` pair, and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers — both of which are within reach of any unprivileged internet user/merchant. No access token, `client_secret`, or privileged credential is needed.

### Recommendation
Bind the shop domain into the signed material, or otherwise cryptographically tie the header-derived `shop` value to the authenticated request:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string` so the HMAC covers them, mirroring the approach already used for `AuthQuery` (which signs `shop` alongside `code`/`host`/`state`/`timestamp`).
- If the header cannot be added to Shopify's HMAC computation (since Shopify controls what it signs), the gem should not treat the "shop" header as authenticated at all after HMAC validation and should surface a documented warning to the host app that `data.shop` must be cross-checked against server-side webhook subscription bookkeeping (e.g., a `webhook_id`-to-shop mapping recorded at webhook registration time) rather than trusted purely as-is.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., updates an order) to receive a real Shopify webhook POST containing:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `raw_body: {...}`
2. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the victim app's webhook endpoint, replacing the header:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the signed body never actually originated from or was validated against that shop.
