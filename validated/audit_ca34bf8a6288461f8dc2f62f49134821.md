### Title
An attacker can keep an insolvent account permanently above the bad-debt dust gate by topping up its existing collateral via `supply`, blocking permissionless `clean_bad_debt` socialization - ([File: contracts/controller/src/positions/liquidation/mod.rs](contracts/controller/src/positions/liquidation/mod.rs))

### Summary
Analogous to PartyA front-running `emergencyClosePosition` by flipping the quote's admission status, any unprivileged address can keep the permissionless bad-debt cleanup path unusable: `clean_bad_debt` requires remaining collateral at or below the fixed `BAD_DEBT_USD_THRESHOLD` ($5 WAD), while third-party `supply` lets anyone top up collateral positions an account already holds. By donating enough tokens to push `total_collateral` just above $5, the attacker makes `socialize_bad_debt` revert with `CannotCleanBadDebt`, indefinitely postponing the supply-index write-down that socializes the bad debt.

### Finding Description
The permissionless cleanup gate lives in `socialize_bad_debt` in `contracts/controller/src/positions/liquidation/mod.rs:212-235`:

```rust
let admits = match gate {
    BadDebtGate::DustCapped => {
        is_socializable_bad_debt(totals.total_debt, totals.total_collateral)
    }
    ...
};
assert_with_error!(env, admits, CollateralError::CannotCleanBadDebt);
```

The `DustCapped` predicate requires `total_debt > total_collateral` **and** `total_collateral <= 5 USD`. Meanwhile, `process_supply` in `contracts/controller/src/positions/supply.rs` only restricts third parties to hub assets the account already supplies (`require_third_party_existing_supply`, lines 78-97); an insolvent account still holds a supply position in its collateral asset, so anyone can call `supply(caller=attacker, account_id=victim, spoke_id, assets=[(victim's collateral key, dust)])` and add to it. A deposit is solvency-improving and passes `validate_position_entry_gates` whenever the listing is not `paused`/`frozen`.

Each time a liquidation (or cleanup attempt) is pending, the attacker tops the account's collateral above $5. When collateral later falls below $5 again (further liquidations or price drift), the top-up only needs to cover the gap, so the recurring cost is bounded by roughly $5 plus price drift per cycle — and the donated collateral is consumed by liquidation/cleanup, never returned.

### Impact Explanation
`clean_bad_debt` is the only non-privileged way to crystallize protocol losses: it writes off the unbacked debt against the market's supply index (`bad_debt::execute_bad_debt_cleanup`). While it is blocked, the supply index is never written down, so suppliers can keep withdrawing at an unimpaired index against debt that will never be repaid — a slow leak that converts latent bad debt into real protocol insolvency. The only fallback is the owner-gated `force_socialize_bad_debt`, which requires a timelocked governance operation (see `docs/reference/runbooks/force-socialize-bad-debt.md`), so the attacker can hold the protocol in an unsocialized state for the entire governance delay and resume afterward. This maps to "protocol insolvency" plus temporary freezing of the cleanup function, comparable in severity to the reference report (Medium).

### Likelihood Explanation
The attack is cheap and repeatable: the cost per cycle is only the amount needed to push collateral above $5 of WAD value, bounded by the dust threshold itself. It requires no privileges, no leaked keys, and no oracle manipulation — just `supply` calls on an insolvent account that already holds the collateral asset. The main precondition is an account sitting in the insolvent band near the dust gate and at least one of its collateral listings being open for entry (`paused`/`frozen` entry flags would block the top-up, though cleanup itself bypasses those flags). Partial liquidations naturally grind collateral down toward the gate, giving the attacker frequent cheap re-block opportunities.

### Recommendation
Make the dust gate resistant to donation top-ups, for example by tracking "collateral contributed by the owner" versus third-party top-ups, or by snapshotting eligibility at insolvency detection time. Simpler alternatives: allow `clean_bad_debt` when `total_collateral <= threshold` OR when the account was already insolvent before the latest third-party supply delta (i.e., exclude third-party-supplied value added after insolvency from the dust-gate comparison), or let permissionless cleanup proceed whenever `debt > collateral` and collateral minus recent third-party donations is at or below the threshold. At minimum, document that owner-only `force_socialize_bad_debt` may be needed promptly for accounts that strangers are topping up.

### Proof of Concept
1. Alice supplies $100 USDC and borrows $80 ETH-value equivalent; price moves make the account insolvent with, e.g., $4 collateral against $6 debt.
2. A keeper calls `clean_bad_debt(attacker-free caller, account_id)` — it reverts? No: currently it would succeed. So before it is mined, the attacker front-runs with `supply(attacker, account_id, spoke_id, [(usdc_hub_key, amount)])` where `amount * usdc_price > $1`, pushing `total_collateral` above $5.
3. `clean_bad_debt` now reverts with `CannotCleanBadDebt` (`socialize_bad_debt`, mod.rs:229-235) because `is_socializable_bad_debt(D, C)` fails the `C <= $5` leg.
4. A liquidator partially liquidates the account, dragging collateral below $5 again; the attacker repeats step 2 with a smaller top-up. The donated tokens are seized by liquidation or become revenue on eventual cleanup, but the index write-down — and thus loss socialization — is deferred for as long as the attacker keeps paying under-$5 top-ups, and suppliers withdraw at the unimpaired index in the meantime.

The relevant code paths: `process_supply` / `require_third_party_existing_supply` (`contracts/controller/src/positions/supply.rs:40-97`), `process_clean_bad_debt` / `socialize_bad_debt` (`contracts/controller/src/positions/liquidation/mod.rs:196-243`).
