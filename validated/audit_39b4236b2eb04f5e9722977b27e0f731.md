## Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

## Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC exclusively over the raw request body, while the `shop` and `topic` values used for handler dispatch and tenant attribution are read from HTTP headers that are never included in the signed content. This breaks the intended binding `hmac-signed(shop, topic, body) == request(shop, topic, body)`; in reality the gem only enforces `hmac-signed(body) == request(body)`, leaving `shop`/`topic` fully attacker-controlled as long as some valid `(body, hmac)` pair is known.

## Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` and `topic` are pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `to_signable_string` (the body only): [3](#0-2) 

`Registry.process` then uses these unauthenticated fields for the two security-relevant decisions: which handler runs (`request.topic`) and which tenant the payload is attributed to (`request.shop`, forwarded into `WebhookMetadata`): [4](#0-3) 

Because every shop that installs a given app shares the same `client_secret` (and therefore the same HMAC key), any merchant who legitimately installs the app on their own store receives real webhooks with valid `(body, hmac)` pairs. Since the `shop-domain` and `topic` headers are outside the signed content, that same attacker can resend the identical body/HMAC while rewriting the `shop-domain` header to a victim shop's domain (or the `topic` header to route the body to a different handler). `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will happily execute the handler believing the data originated from the victim shop.

This is the same class of bug as the reported `SuperPositions.onlyMinter()` issue: the code performs its identity/authorization check against a value that is not the one cryptographically bound to the trusted assertion (there, `formImplementationId` instead of the state registry id; here, header-derived `shop`/`topic` instead of a value covered by the HMAC).

## Impact Explanation
This enables cross-tenant confusion: a shop that has valid access to the app's webhook endpoint (any merchant who installs the app) can cause the app's webhook handler to believe a payload belongs to a different, victim shop, or can redirect payloads to a different topic handler than Shopify sent. Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`), this can be leveraged to trigger tenant-scoped actions (data deletion/redaction, session revocation, config changes) against a shop the attacker does not own — a cross-tenant impact.

## Likelihood Explanation
Any user can install the app on a free/dev Shopify store to obtain a legitimately signed `(body, hmac)` webhook, then replay it to the app's public webhook endpoint with a forged `shop-domain`/`topic` header (and/or the endpoint's own client-side header parsing, since headers are attacker-controlled at the HTTP layer regardless of TLS termination). No access token, `client_secret`, or privileged account is required — only the ability to install the app once, which is an unprivileged action.

## Recommendation
Bind `shop` and `topic` into the HMAC-signed content (or otherwise cryptographically authenticate them, e.g. by having `to_signable_string` incorporate a canonical representation of shop+topic+body, matching what Shopify actually signs), so `HmacValidator.validate` fails if either header is altered relative to the signed request. At minimum, `Registry.process` should not attribute a webhook to `request.shop` unless that value can be proven consistent with the authenticated body content (e.g., cross-checked against a shop identifier embedded in the signed payload).

## Proof of Concept
1. Attacker installs the target app on their own Shopify store (`attacker.myshopify.com`) — unprivileged, self-service.
2. Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: shop/update`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`.
3. Attacker captures this request and resends it to the same endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and/or changing `x-shopify-topic` to a more sensitive topic like `shop/redact`).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks the untouched raw body.
5. `ShopifyAPI::Webhooks::Registry.process` runs the corresponding handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the request never originated from Shopify on behalf of that shop.
