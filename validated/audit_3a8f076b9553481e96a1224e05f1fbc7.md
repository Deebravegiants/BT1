CASE-2 Emporium ops let any unprivileged user plant a permanent, unauthenticated ERC20 approval from the shared Emporium contract to an attacker-controlled spender - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE-2 "Stateless Interaction" branch executes `op.endpoint.call{value: op.value}(op.callData)` for any `op` supplied inside the attacker's own `circomData.externalActionData.externalActionMetadata`, with the only guard being a selector blacklist against `callHinkalWallet`/`doSendToRelay`. Nothing prevents `op.endpoint` from being an arbitrary ERC20 token and `op.callData` from being `approve(attackerSpender, type(uint256).max)`, which grants a standing ERC20-level allowance from the shared `Emporium` contract to an attacker-controlled address, exercisable later by anyone holding that allowance with a plain, unprivileged `transferFrom` call requiring no Hinkal proof.

### Finding Description
The broken equality: an allowance created as a side effect of a user's authenticated `transact` call should only ever be exercisable through that same user's subsequent Hinkal-gated call — but ERC20 `approve` semantics grant the approved spender a standing right usable by **any** caller, at **any** future time, completely outside Hinkal's `performHinkalChecks`/`verifyProof`/`onlyAllowedRecipient` gating.

Path:
1. Attacker calls `Hinkal.transact` with their own valid proof over their own UTXOs (unprivileged, self-authored). `circomData.externalActionData.externalActionId` points to the Emporium action, so `Hinkal._externalTransact` (contracts/Hinkal.sol:234-261) calls `EmporiumUpgradeable.runAction`.
2. `runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-118) decodes an attacker-chosen `EmporiumStack` from `externalActionMetadata`. Setting `stack.signerAddress = address(0)` makes `verifyWallet` return immediately (line 314-316, no signature needed) and forces every op into the CASE-2 branch (`op.invokeWallet && stack.signerAddress != address(0)` is false).
3. For a CASE-2 op, the only filter is the selector blacklist at lines 104-110; there is no allowlist on `op.endpoint`, and no restriction preventing `op.callData` from being `IERC20.approve`. The unused `APPROVE_SELECTOR` constant in `contracts/Constants.sol:11` confirms such a guard was never wired in.
4. The call `op.endpoint.call{value: op.value}(op.callData)` (line 112) executes with `msg.sender == address(Emporium)`, so `token.approve(attackerSpender, type(uint256).max)` sets `allowance[Emporium][attackerSpender] = max` — a persistent state change on the token contract, external to Hinkal's balance/UTXO accounting.
5. Because the attacker can deposit `0` (or minimal) amount of that token, `balanceChange` computed in `runAction` (lines 132-150) stays `<= 0` and is skipped by `handleOut`, so the whole transaction succeeds cleanly, leaving the approval planted with no funds moved and no anomaly in `Hinkal`'s balance-diff checks (`balanceDif == amountChanges[i] + utxoAmount`, contracts/Hinkal.sol:134-146), since those checks only constrain the *caller's own* balance/UTXO delta, not Emporium's external allowance state.
6. Later, whenever the shared `Emporium` contract ends up holding a nonzero balance of that same token (e.g., dust/residue left after another user's swap that doesn't fully sweep back via `handleOut`, or from any other future deposit flow that leaves a transient/residual balance), the attacker calls `attackerSpender.transferFrom(emporium, attacker, amount)` directly as a plain EOA transaction — no proof, no `Hinkal.transact`, no `onlyAllowedRecipient` gate — and drains it.

Existing guards do not prevent this: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the balance-diff/slippage requires in `Hinkal.sol` only validate the *attacker's own* transaction's UTXO/balance consistency; none of them constrain what arbitrary calls a CASE-2 op may make against arbitrary `op.endpoint` contracts, and none of them expire or revoke ERC20 approvals set as a side effect of an op.

### Impact Explanation
The attacker gains a standing, unlimited ERC20 allowance from the protocol-wide shared `Emporium` contract to an address they fully control, for any token of their choosing, obtainable in a single unprivileged self-authored transaction at near-zero cost. This allowance is permanent (never expires, never re-checked by Hinkal) and is exercisable repeatedly, forever, by a plain `transferFrom` call with no further authorization. Any balance of that token subsequently held by `Emporium` — whether from swap residue/dust, partial fills, or any other flow that does not atomically sweep 100% of the balance out in the same call — becomes directly stealable. This matches "executing calls or moving assets a wallet owner or prover never authorised" (High) and, to the extent balances tied to other users' in-flight deposits or protocol/relay fee tokens ever transiently sit in `Emporium`, escalates toward direct theft of shielded/in-flight funds (Critical). Repeatability is unbounded — the attacker can plant such approvals for every token the Emporium ever touches.

### Likelihood Explanation
Preconditions: attacker only needs the ability to generate a valid proof over their own UTXOs and choose `externalActionMetadata` freely (fully in scope for an unprivileged user per the rules). No victim cooperation, no privileged role, and no reentrancy is required to plant the approval — it is a single self-authored `transact` call. The only uncertainty is whether/when `Emporium` actually holds a drainable balance of the targeted token at the moment of exploitation; this depends on downstream behavior of swap/other Emporium ops (e.g., whether `handleOut` always sweeps 100% of balance in the same atomic call). This part could not be independently confirmed for every possible op/token combination within the available index, so the "planting" step is fully verified and critical, while the "harvesting" step's magnitude depends on how much residual balance realistically accumulates — but the underlying authority-bypass is real and present in `EmporiumUpgradeable.runAction` regardless.

### Recommendation
In `EmporiumUpgradeable.runAction`'s CASE-2 branch, block any `op.callData` whose selector matches `IERC20.approve`/`increaseAllowance`/`permit`-style functions (or, more robustly, disallow `op.endpoint` from being called with any calldata that would set an allowance from `address(this)`), or require CASE-2 ops to target a pre-registered allowlist of endpoints rather than fully attacker-controlled `op.endpoint`/`op.callData`. Additionally, ensure `Emporium` never carries a standing token balance between transactions (assert `getBalancesForArray` returns to a known baseline at the end of every `runAction`), so that even a leaked approval has nothing to drain.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as the registered external action for a chosen `externalActionId`), a test ERC20 `TokenX`, and an `AttackerSpender` contract implementing `drain(address emporium, address token, address to, uint256 amount)` that calls `IERC20(token).transferFrom(emporium, to, amount)`.
2. As `attacker` (unprivileged EOA), deposit a minimal/zero amount of `TokenX` into the Hinkal pool to obtain a spendable UTXO and locally generate a valid proof for a `transact` call whose `CircomData.externalActionData` points at `Emporium`, with `externalActionMetadata` encoding an `EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: address(TokenX), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, address(attackerSpender), type(uint256).max) }] }`.
3. Call `Hinkal.transact(...)` and assert it succeeds; assert `TokenX.allowance(address(emporium), address(attackerSpender)) == type(uint256).max`.
4. Simulate residual balance: have a second, unrelated `victim` deposit `TokenX` via a normal Emporium swap op that leaves dust (or, simplest for POC, directly `deal(address(tokenX), address(emporium), residueAmount)` to model a realistic post-swap leftover), establishing `TokenX.balanceOf(emporium) == residueAmount > 0`.
5. As `attacker`, call `attackerSpender.drain(address(emporium), address(TokenX), attacker, residueAmount)` directly — a plain EOA call, **no Hinkal proof, no `transact` call**.
6. Assert the call succeeds and `TokenX.balanceOf(attacker)` increased by `residueAmount` while `TokenX.balanceOf(emporium)` dropped to 0, proving unauthorized fund extraction via the pre-planted approval, fully independent of any subsequent `runAction`/Hinkal gating.
