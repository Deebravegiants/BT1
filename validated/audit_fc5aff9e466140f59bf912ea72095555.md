### Title
Accumulated `Pair.swap` "+1" K-invariant slack can underflow-revert `Router._computeBuy`/`_computeSell`, permanently bricking a curve's trading and graduation - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Router.sol])

### Summary
Zebra's CVE panicked because `orchard`'s transaction-verification code assumed a curve point could never be the identity and called `unwrap()` without checking, so a spec-valid-but-unhandled edge case crashed the node. `alt.fun`'s bonding-curve math has the analogous shape: `Router._computeBuy` / `Router._computeSell` perform unchecked `uint256` subtractions (`reserveToken - k/newReserveAsset`, `reserveAsset - k/newReserveToken`) that assume the pool's live reserve product never falls below the immutable `k` recorded at `Pair.mint`. `Pair.swap`'s "+1" K-invariant check does not enforce that assumption — it only enforces `(newTokenReserve+1)*(newAssetReserve+1) >= k`, which *permits* the true product `newTokenReserve*newAssetReserve` to sit strictly below `k`. Every trade through the curve can widen this gap, and once it does, the unchecked subtraction in the quote math underflows and reverts with a Solidity `Panic(0x11)`, exactly like the unhandled `unwrap()` in the CVE.

### Finding Description
`Pair.swap` enforces the invariant with a `+1` slack on both reserves: [1](#0-0) 

This means after any swap, the *actual* product `newTokenReserve * newAssetReserve` can be smaller than the fixed `_pool.k` (set once at `mint`, never recomputed) by up to `newTokenReserve + newAssetReserve + 1`: [2](#0-1) 

`Router._computeBuy` and `Router._computeSell` both assume the opposite — that `reserveToken * reserveAsset >= k` always holds — and compute the quote with an unchecked subtraction: [3](#0-2) [4](#0-3) 

If `k / newReserveAsset` (buy path) or `k / newReserveToken` (sell path) ever rounds up to a value larger than the corresponding stored reserve — which the `+1` slack from prior swaps makes possible, especially for a small trailing trade that barely changes `newReserveAsset`/`newReserveToken` — the subtraction underflows and the call reverts with an arithmetic-underflow panic instead of a handled error. This is functionally identical to the CVE's root cause: an unchecked operation (`unwrap()` there, unchecked `uint256` subtraction here) that assumes an invariant the surrounding protocol does not actually guarantee for every reachable state, reachable purely through normal unprivileged trading (`Bonding.buy`/`Bonding.sell` → `Router.buy`/`Router.sell`, or the `Zap` variants).

Both `buy` and `sell` on the curve route exclusively through these two internal functions, and `Bonding.canGraduate`/`triggerGraduation` also depend on `IPair.getReserves()`/`k()` staying self-consistent; once a token's `Pair` reaches a state where the K-slack gap is large enough relative to its reserves, ordinary buy/sell calls at certain sizes revert, and there is no owner or keeper function that can repair `_pool.k` or `_pool.tokenReserve/assetReserve` (both are private, mutated only via `onlyRouter` `mint`/`swap`).

### Impact Explanation
Any unprivileged trader interacting with `Bonding.buy`/`Bonding.sell` (or `Zap`'s wrapped variants) drives ordinary swaps through `Pair.swap`'s slack-tolerant K-check. Because the slack is one-directional (it only ever lets the real product sag below `k`, never above), the gap can only grow with more trading activity, and any user — not just an attacker — can eventually land a trade size that trips the underflow revert in `_computeBuy`/`_computeSell`. Once that state is reached for a given `(tokenReserve, assetReserve)` pair, that specific trade size (and nearby sizes) will always revert; because `_pool.k`, `_pool.tokenReserve`, and `_pool.assetReserve` can only be mutated through `Router` (gated to `Bonding`, gated to `BONDING_ROLE`), there is no permissionless or admin repair path. This can:
- Freeze traders' ability to sell tokens back into LT (funds effectively stuck on the curve) — a direct freezing-of-trader-funds impact.
- Prevent the curve from crossing `canGraduate`'s USD/supply thresholds via normal buys, stalling graduation and stranding the creator's/traders' capital in `Lifecycle.Curve` indefinitely.
Both outcomes match the "permanent freezing of trader/creator funds" bar in the validation criteria.

### Likelihood Explanation
The `+1` K-slack is baked into every `Pair.swap` call and is exercised on every single curve trade — this is not a rare or attacker-only path, it's the pair's only invariant check. The window in which `_computeBuy`/`_computeSell`'s unchecked subtraction underflows depends on the exact reserve sizes and trade size at the moment the accumulated slack outweighs the marginal change from a small trailing trade; an attacker can deliberately narrow that window by repeatedly trading minimal amounts to accumulate the maximum permitted slack each time (the `+1` allowance is taken every swap, so it compounds over many trades), then submit a small buy/sell to trigger the revert deterministically. This makes it a Medium-likelihood, attacker-acceleratable griefing vector rather than a purely theoretical one, while still being reachable by an ordinary trader without any privileged role.

### Recommendation
Replace the unchecked subtractions in `Router._computeBuy`/`_computeSell` with saturating math (as already used defensively elsewhere in this codebase, e.g. `Bonding._sweepLTToOwner`'s `bal > keep ? bal - keep : 0` pattern) or cap the quote at the smaller of the naive result and the pair's live real balance, and additionally tighten `Pair.swap`'s invariant check from `(newTokenReserve+1)*(newAssetReserve+1) >= k` to a form that does not let the real product recede below `k` at all (or bound the cumulative slack), so `Router`'s downstream math can safely assume `reserveToken * reserveAsset >= k` holds for every state it will ever read.

### Proof of Concept
Conceptual sequence, using only unprivileged `Bonding.buy`/`Bonding.sell` calls on a freshly launched token's curve:
1. Attacker repeatedly calls `Bonding.buy` with the smallest amounts the LT's `minTransactionSize` allows. Each call goes through `Router.buy` → `Pair.swap`, and each `Pair.swap` call is only required to satisfy `(newTokenReserve+1)*(newAssetReserve+1) >= k`, letting the *true* product `newTokenReserve*newAssetReserve` end up up to `newTokenReserve+newAssetReserve+1` below `k` every time: [5](#0-4) 
2. After enough such trades, the accumulated shortfall between the true reserve product and `k` is large enough that, for a subsequent small `Bonding.sell` (or `Bonding.buy`), `Router._computeSell`'s `k / newReserveToken` (or `_computeBuy`'s `k / newReserveAsset`) rounds to a value exceeding the stored `reserveAsset` (or `reserveToken`): [6](#0-5) 
3. That call reverts with an unhandled Solidity arithmetic-underflow panic (`Panic(0x11)`) instead of a controlled error, and there is no function anywhere in `Router.sol`/`Pair.sol`/`Bonding.sol` that can adjust `_pool.k`/`_pool.tokenReserve`/`_pool.assetReserve` to recover — any trader attempting that trade size against that pair is permanently blocked, and if it blocks the threshold-crossing buy, the token can never reach `canGraduate` via that path either.

Note: precisely quantifying the minimum number of trades / trade sizes needed to force the underflow deterministically requires running the exact fixed-point arithmetic against representative `k`/reserve magnitudes (dependent on the LT's live `exchangeRate()` and `TOTAL_SUPPLY`), which is outside what static code reading can confirm — a Devin session with Foundry access could fuzz/simulate `Pair.swap` + `Router._computeBuy`/`_computeSell` against realistic reserve values to nail down the exact trigger sequence and confirm the panic in a test.

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
