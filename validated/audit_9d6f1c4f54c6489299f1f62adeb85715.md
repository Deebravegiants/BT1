### Title
Webhook `shop-domain` (and `topic`) header is trusted for tenant routing while being excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (and `topic`, `webhook-id`, `api-version`) values used to route the webhook to a specific merchant's handler are read directly from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` after only validating the body's HMAC, breaking the identity binding between "HMAC-authenticated bytes" and "tenant/shop the data is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are parsed straight from headers, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `computed_signature` (over `to_signable_string`, i.e. the body only) against the received HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately dispatches to the app's handler using the unauthenticated `request.shop` value as the tenant identifier: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`bytes covered by HMAC (raw_body)` ≠ `bytes used to select the tenant (shop-domain header)`.

Because the `x-shopify-shop-domain` header sits outside the signed payload, any entity capable of producing one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — which any shop that has installed the app can trivially obtain by triggering a real webhook from its own store — can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen value, not the shop that actually produced the signed body.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: an app relying on `ShopifyAPI::Webhooks::Registry.process` to attribute incoming webhook data to `request.shop` can be made to process a validly-signed payload under a victim shop's identity. Depending on how the host app uses the `shop` value returned in `WebhookMetadata` (e.g., to look up/update per-shop records, load a session, or key data writes), this enables cross-tenant data injection/corruption — an attacker-controlled webhook body attributed to a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since the shop identity binding the gem is meant to guarantee via HMAC validation does not actually cover the field used for tenant routing.

### Likelihood Explanation
Reaching this requires only: (1) the ability to install the target app on any Shopify store (an unprivileged internet user can create a free/dev store and install a public app), (2) triggering one legitimate webhook delivery to observe a valid `(raw_body, hmac)` pair for a chosen body, and (3) sending a forged HTTP request directly to the app's public webhook endpoint with that same body/HMAC but a different `x-shopify-shop-domain` header. No access token, `client_secret`, or privileged account is required — only interaction with the gem's public, documented `Registry.process` entry point.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is cryptographically verified, or otherwise cross-check it against a source of truth before trusting it for routing:
- Include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or
- After HMAC validation, require host applications to explicitly verify `request.shop` against the shop associated with the session/webhook registration they expect, rather than trusting the header value implicitly, and document this requirement clearly in `Registry.process`'s contract.
- At minimum, expose/require a shop allow-list check in `Registry.process` so header-derived tenant identity is validated against known installed shops before dispatch.

### Proof of Concept
```ruby
# Attacker owns Shop A (any store, e.g. a free dev store) with the target app installed.
# Step 1: Attacker triggers a real webhook from Shop A and captures the raw body + HMAC
#         Shopify sent for it (e.g. via a request bin, or by writing a temporary handler).
raw_body = '{"id":123,"note":"hello"}'
hmac     = "<value of x-shopify-hmac-sha256 header Shopify sent for the above body>"

# Step 2: Attacker crafts a forged HTTP POST to the app's public webhook endpoint,
#         reusing the exact same body/HMAC pair, but swapping the shop-domain header
#         to a victim shop that also has the app installed.
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,                     # unchanged, still matches raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Step 3: HmacValidator.validate only checks raw_body vs hmac -> passes.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Step 4: Registry.process dispatches to the handler with shop == "victim-shop.myshopify.com",
#         even though that shop never sent this webhook.
ShopifyAPI::Webhooks::Registry.process(request)
```
`request.shop` reaches the handler unauthenticated relative to the HMAC, demonstrating the broken binding. [4](#0-3)

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
