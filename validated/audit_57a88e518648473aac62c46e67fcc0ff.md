### Title
`arePrivateKeysLocked` leaks seed-presence via distinguishable throw-vs-boolean response - ([File: features/keychain/module/keychain.js])

### Summary
`Keychain.arePrivateKeysLocked` converts caller-supplied seed buffers into seed IDs and then calls the private `#checkPrivateKeysLocked` helper, which throws an assertion error for seed IDs that are not present in `#seedLockStatus` but returns a boolean (`true`/`false`) for seed IDs that are known. An unprivileged caller who can invoke the RPC-exposed `keychain.arePrivateKeysLocked([seedBuffer])` can therefore distinguish "this seed is not in the wallet" (rejected promise) from "this seed is in the wallet" (resolved boolean), creating a seed-presence oracle.

### Finding Description
`arePrivateKeysLocked` is exposed unmodified through the RPC surface: `sdks/headless/src/features/keychain-rpc/index.js` wraps the keychain module with `createRpcFeature('keychain', api)` [1](#0-0) , and the SDK API layer forwards the call verbatim: `arePrivateKeysLocked: (seeds) => keychain.arePrivateKeysLocked(seeds)` [2](#0-1) .

The core implementation is:
```js
async arePrivateKeysLocked(seeds = []) {
  assert(Array.isArray(seeds), 'seeds must be an array')
  const seedIds = await getUniqueSeedIds(seeds)
  return this.#checkPrivateKeysLocked(seedIds)
}
``` [3](#0-2) 

and:
```js
#checkPrivateKeysLocked(seedIds) {
  if (!seedIds?.length) {
    return Object.values(this.#seedLockStatus).some(Boolean)
  }
  return seedIds.some((seedId) => {
    assert(
      Object.hasOwn(this.#seedLockStatus, seedId),
      `cannot check lock state for unknown seed "${seedId}"`
    )
    return this.#seedLockStatus[seedId]
  })
}
``` [4](#0-3) 

`seeds` accepts raw 64-byte buffers, and `getUniqueSeedIds` deterministically derives a `seedId` from any supplied buffer via `getSeedId` (from `@exodus/bip32`) with no ownership or validation check on the input seed itself [5](#0-4) . Because `#checkPrivateKeysLocked` throws only when the derived `seedId` is absent from `#seedLockStatus`, an attacker who submits a guessed seed can tell from the response type alone (rejection vs. `true`/`false`) whether that exact seed is currently loaded in the wallet, and if so whether it is locked. This existing test explicitly documents the boolean vs. resolved-value semantics for known seeds: `expect(await keychain.arePrivateKeysLocked([seed])).toBe(false)` [6](#0-5) , while `#checkPrivateKeysLocked`'s assert path (unknown seed) is not covered by resolved value handling and simply propagates as a rejection to the RPC caller.

No origin binding, account scoping, or authentication guard exists in this code path to prevent an unprivileged RPC caller from invoking `arePrivateKeysLocked` with arbitrary buffers, since the RPC feature registration performs no such check [7](#0-6) .

Regarding the second half of the question (spoofing the lock check to make other code believe keys are unlocked): this is **not** exploitable, because all sensitive operations (`exportKey`, `signBuffer`, `#getPrivateHDKey`, etc.) independently call `#assertPrivateKeysUnlocked` against the same internal `#seedLockStatus` state rather than trusting any externally-supplied lock value [8](#0-7) . `arePrivateKeysLocked` is read-only and cannot influence that internal state, so it cannot be used to bypass the real lock gate elsewhere.

### Impact Explanation
This is a narrow information-disclosure oracle limited to seed *presence/lock-state*, not private key or mnemonic material. An attacker must already possess the exact 64-byte seed bytes they want to test (e.g., from a suspected/partially-known or weak/leaked mnemonic) to derive a matching `seedId`; the oracle only confirms whether that specific already-known seed is loaded/unlocked in the target wallet instance. It does not allow recovering an unknown seed, does not leak private keys, and does not enable unauthorized signing or a lock-bypass for real cryptographic operations.

### Likelihood Explanation
Reachable directly via a single RPC call `keychain.arePrivateKeysLocked([guessedSeedBuffer])` with no authentication or origin check evident in the RPC wrapper, requiring only that the keychain RPC surface is reachable (a stated precondition). It is trivially repeatable and requires no privileged state, matching the differential test described (compare responses for a known-existing vs. non-existing seed, pre/post `lockPrivateKeys()`).

### Recommendation
Make `arePrivateKeysLocked` return a uniform, non-distinguishing result for unknown seeds instead of throwing (e.g., treat "seed not present" identically to "locked" or introduce a dedicated non-error sentinel), so that resolved value and error paths are indistinguishable for absent vs. locked/unlocked known seeds. Alternatively, restrict `arePrivateKeysLocked` (and any seed-derivation entry points reachable from RPC) to only accept internally-tracked `seedId` strings rather than raw seed bytes, removing the ability for external callers to test arbitrary guessed seed material against wallet state.

### Proof of Concept
```js
// integration test extending features/keychain/module/__tests__/lock-private-keys.test.js
it('leaks seed presence via throw-vs-boolean side channel', async () => {
  const keychain = await createKeychain({ seed })
  const unknownSeed = await mnemonicToSeed({ mnemonic: 'abandon'.repeat(12), validate: false })

  // Known seed: resolves with boolean (no throw), regardless of lock state
  await expect(keychain.arePrivateKeysLocked([seed])).resolves.toBe(false)

  // Unknown/guessed seed: rejects with assertion error
  await expect(keychain.arePrivateKeysLocked([unknownSeed])).rejects.toThrow(
    /cannot check lock state for unknown seed/
  )

  // After locking, known seed still resolves (true) vs unknown still rejects -> distinguishable oracle persists across lock state
  keychain.lockPrivateKeys()
  await expect(keychain.arePrivateKeysLocked([seed])).resolves.toBe(true)
  await expect(keychain.arePrivateKeysLocked([unknownSeed])).rejects.toThrow(
    /cannot check lock state for unknown seed/
  )
})
```
Expected assertions confirm that resolved-boolean vs. rejected-promise behavior differs solely based on whether the guessed seed is present in the wallet, independent of lock state, demonstrating the seed-presence oracle.
