Confirmed root cause: the identity binding claimed by the gem's webhook processing pipeline is broken.

### Title
Webhook `shop-domain` and `topic` headers are trusted for routing/tenant-identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches the event using the `shop` and `topic` values pulled from HTTP headers that are never part of the signed material. This breaks the equality that a caller of this gem implicitly relies on: `hmac_verified(payload) == shop_the_event_is_attributed_to`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry#process` only proves that `@raw_body` was signed with `Context.api_secret_key` [2](#0-1) . However, `#shop`, `#topic`, and `#webhook_id` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), which are completely outside the HMAC's signed scope [3](#0-2) . After HMAC validation succeeds, `Registry#process` looks up the handler by `request.topic` and calls `handler.handle` passing `shop: request.shop` straight from that header, without cross-checking it against anything derived from the signed body [4](#0-3) .

Because `api_secret_key` is shared across all shops/tenants of a single app (it's not shop-specific), any party who can obtain one genuine `(raw_body, hmac)` pair for a topic the app is subscribed to — for example, by owning a development/free Shopify store and installing the target app, or by observing/replaying a webhook delivery to the app's public endpoint — can present that exact `(raw_body, hmac)` pair again while substituting a different value for the `X-Shopify-Shop-Domain` header. The gem will still assert `Utils::HmacValidator.validate(request)` is true (the body/signature pair is unchanged and valid), and will then dispatch the handler with `shop:` set to the attacker-chosen tenant identifier and `body:` set to the attacker's own shop's payload.

The invariant that should hold is: **the shop identity acted upon by the handler == the shop that produced the HMAC-covered payload**. Currently: `shop_used_for_dispatch (header, unauthenticated) != shop_that_signed_the_payload (body, authenticated)`.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (built directly from `request.shop`) as the tenant key for locating a merchant's session/access token or for writing merchant-scoped data will process, store, or act on attacker-controlled content under a victim shop's identity. This is a cross-tenant confusion vector: an attacker can inject or misattribute webhook-driven data across the multi-tenant boundary the gem is supposed to preserve, using only a legitimately-obtained webhook from their own (possibly free/dev) store.

### Likelihood Explanation
No secret key, access token, or privileged account is required — only the ability to receive one valid webhook delivery for a topic the target app subscribes to (trivially available to anyone who installs a public app or has a dev store), plus the ability to replay/modify the unauthenticated `shop-domain` header when delivering the crafted HTTP request to the app's webhook endpoint. This is fully exploitable by an unprivileged internet-reachable actor and requires no interaction with `client_secret` or access tokens.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material used by `to_signable_string`, or otherwise cryptographically/contextually bind the header-derived `shop` to the signed body (e.g., require the host application to independently verify `request.shop` against an expected/allow-listed shop for the session before dispatch, and document this requirement prominently). At minimum, `Registry#process` should not treat `request.shop`/`request.topic` as trusted routing/tenant keys purely because `Utils::HmacValidator.validate` returned true.

### Proof of Concept
1. Attacker installs the target app on their own (e.g., free development) Shopify store, `attacker-shop.myshopify.com`, and subscribes to a webhook topic the app registers (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's public endpoint with body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and a valid `X-Shopify-Hmac-Sha256` computed over `B` using the app's shared `api_secret_key`.
3. Attacker captures this request and resends it to the same endpoint, keeping `B` and the HMAC header byte-for-byte identical, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the HMAC [2](#0-1) .
5. The registered handler is invoked with `shop: "victim-shop.myshopify.com"` and `body:` equal to the attacker's own webhook payload `B`, letting the attacker inject data/events attributed to `victim-shop.myshopify.com` in the host application [6](#0-5) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
