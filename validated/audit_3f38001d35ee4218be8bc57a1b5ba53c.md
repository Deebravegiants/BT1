### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with a `shop` value meant to identify the tenant. In reality, the HMAC signature computed by `HmacValidator` only covers the raw request body; the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from unauthenticated HTTP headers and are never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body, and compares it to the `hmac` header: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC and then forwards the unauthenticated `shop` value directly to the app's handler as the tenant identifier: [4](#0-3) 

The gem's own documentation asserts that `process` "will verify the request did indeed come from Shopify" and instructs developers to key their per-tenant logic (e.g. `shop_domain: data.shop`) off `data.shop`, implying it is trustworthy: the documented example is `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`.

The broken binding, expressed as an equality that should hold but doesn't:
`shop_header_used_for_tenant_routing == shop_that_HMAC_actually_authenticates`

Because only the body is signed, this equality never holds — `shop` (and `topic`/`webhook_id`) can be swapped to any value while the HMAC over the body remains valid.

### Impact Explanation
An unprivileged attacker who has legitimately installed the app on their own store (or otherwise obtained any one validly-signed webhook body/HMAC pair issued by Shopify with the app's secret, e.g. by triggering an `orders/create` event on their own shop) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns true because it only checks the body, and `Registry.process` passes the attacker-chosen `shop` value to the handler as if it were authenticated. Any host application that uses `data.shop` to route or persist tenant data (the exact pattern documented in `docs/usage/webhooks.md`) will ingest attacker-controlled data attributed to a different shop, i.e. cross-tenant data injection.

### Likelihood Explanation
Reasonably likely: the attacker needs no secrets or special access beyond installing the app on their own store (which is available to any developer/merchant) and issuing an ordinary webhook-triggering action, then replaying the captured request with a modified header to the same, publicly-reachable webhook endpoint. The gem's documentation actively encourages using `data.shop` as an authenticated tenant key, so real integrations are exposed to this by following the documented usage pattern rather than misusing the API.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed body), so that any of these identity-carrying fields cannot be altered without invalidating the signature. At minimum, document clearly that only the body is authenticated by `HmacValidator` and that `data.shop`/`data.topic` must not be trusted for tenant routing without additional verification (e.g., cross-checking against the session/shop the webhook subscription was registered for).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., creates an order), causing Shopify to POST a validly HMAC-signed request to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H` (correctly computed over `B`, verifiable since `to_signable_string` returns only `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` and re-POSTs the same body/HMAC to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only [5](#0-4)  — validation succeeds because `B` and `H` are unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop` header and invokes the app handler [6](#0-5) , causing the host app to process/store attacker data under `victim-shop.myshopify.com`'s tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
