### Title
`msg.value` credited independently to every `address(0)` slot in `erc20TokenAddresses`, allowing duplicate-token calls to mint 2x unbacked shielded ETH per real deposit - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` iterates `circomData.erc20TokenAddresses` and, for every entry equal to `address(0)`, computes `balanceDif = newBalances[i] + msg.value - oldBalances[i]` independently per index, then checks `balanceDif == amountChanges[i] + utxoAmount(i)` per index [1](#0-0) . Because `oldBalances`/`newBalances` are read via `getERC20OrETHBalance(address(0)) == address(this).balance` [2](#0-1) , `msg.value` is already baked into both readings equally when address(0) appears more than once, so `balanceDif` evaluates to the exact same numeric value (`msg.value` when no ETH otherwise moves) at every duplicated index, and `utxoAmount(i)` is also identical at every duplicated index because it is computed by scanning the *entire* `utxoSet` and matching purely on `erc20Address == erc20TokenAddresses[i]` [3](#0-2) .

### Finding Description
The broken equality: the protocol intends `sum over unique tokens of (real balance change) == sum over unique tokens of (off-chain amountChanges + on-chain utxoAmount)`, i.e. every unit of real ETH backs exactly one accounting term. Instead, the per-index loop in `transact` treats each *array slot* independently rather than each *unique token*, so a duplicated `address(0)` slot lets one real `msg.value` satisfy two independent per-slot equalities.

Concretely, if the attacker submits `erc20TokenAddresses = [address(0) (i1), address(0) (i2), ...]`, both with `onChainCreation[i] == false` and no on-chain UTXOs of `address(0)` are created by `DepositOnChainUtxosExternalAction.runAction` (so `utxoAmount(i1) == utxoAmount(i2) == 0`), then:
- Constraint at i1: `msg.value == amountChanges[i1] + 0`
- Constraint at i2: `msg.value == amountChanges[i2] + 0`

Both are independently satisfiable by setting `amountChanges[i1] = amountChanges[i2] = msg.value`, i.e. the attacker deposits `msg.value` once but the balance equation at line 137-146 [4](#0-3)  is satisfied twice, once per slot, letting the circuit's per-slot `inTotal + amountChanges === outTotal` constraint mint two independent shielded output notes each worth `msg.value`, for a total of `2 * msg.value` in newly minted shielded ETH against a single real ETH deposit.

Note: if instead one of the duplicated slots has `onChainCreation[i]=true` (an on-chain UTXO is actually created for that slot), the shared `utxoAmount` term (which sums matches across the *whole* `utxoSet`, not per-slot) is counted at both indices too, which self-cancels and forces the other slot's `amountChanges` to zero — that particular sub-case is not exploitable. The exploitable case requires both duplicated `address(0)` slots to rely on `amountChanges` (`onChainCreation=false`) with no on-chain UTXOs for `address(0)`, only `DepositOnChainUtxosExternalAction`'s "at least one UTXO total" requirement being satisfied by an unrelated token/index [5](#0-4) .

None of `performHinkalChecks`, `rootHashExists`, `insertNullifiers`, or the balance/slippage `require`s deduplicate `erc20TokenAddresses` by address; the per-index loop structurally assumes each array slot is a distinct token. I was not able to fully confirm within the available index whether `dimensionsCheck` inside `HinkalHelper.performHinkalChecks` or the circuit's public-input binding rejects duplicate token addresses across slots, or whether the circuit ties each `amountChanges[i]` slot to an independently-verifiable output note unconstrained by physical token uniqueness — this is the main remaining uncertainty and should be checked against `HinkalHelper.sol`'s `dimensionsCheck`/`checkOnchainCreation` and `MainEVMCircuit.circom`'s per-slot `inTotal+amountChanges===outTotal` wiring before treating this as fully proven.

### Impact Explanation
If the duplicate-slot path is not rejected elsewhere, the attacker mints shielded ETH balance greater than the ETH actually deposited into the contract, directly causing protocol insolvency — matching the Critical category "minting shielded value without backing." The attack is repeatable per transaction and scales linearly with the number of duplicated `address(0)` (or any other token) slots included in a single call.

### Likelihood Explanation
Preconditions: attacker must be able to submit `erc20TokenAddresses` with a duplicated token entry, generate a valid proof whose public inputs match this array (fully in attacker's control since they're only spending/creating their own UTXOs), and route through `DepositOnChainUtxosExternalAction` (or any `externalActionId` where `deltaAmounts[i]==0` and no UTXO is forced per token) to keep `utxoAmount(i)=0` for the duplicated slots. Feasibility hinges entirely on whether `dimensionsCheck`/circuit constraints reject duplicate token addresses in the public-input array — this was not fully verified from the available index. Assuming no such rejection exists, the attack is low-cost (one transaction, self-generated proof) and fully repeatable.

### Recommendation
Aggregate `balanceDif`, `amountChanges`, and `utxoAmount` by unique token address before applying the balance-equation check, rather than iterating over raw array slots — e.g., require `erc20TokenAddresses` to contain no duplicates (enforced in `dimensionsCheck`/`performHinkalChecks`), or restructure the loop in `Hinkal.transact` to sum `amountChanges[i]` and `utxoAmount` across all slots sharing the same address before comparing to a single `balanceDif` computed once per unique token.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with `DepositOnChainUtxosExternalAction` registered.
2. Craft `circomData.erc20TokenAddresses = [address(0), address(0), SOME_ERC20]` with `onChainCreation = [false, false, true]`.
3. Set `externalActionMetadata` (`utxoAmounts`) so that index 0 and 1 (address(0)) have empty UTXO arrays, and index 2 (`SOME_ERC20`) has one UTXO satisfying `countUtxos > 0`.
4. Generate a proof where `amountChanges[0] = amountChanges[1] = msg.value` and `deltaAmounts[0]=deltaAmounts[1]=deltaAmounts[2]=0`.
5. Call `transact` with `msg.value = X` ETH.
6. Assert: `address(this).balance` increases by exactly `X`, but the sum of minted off-chain shielded output value for `address(0)` (via `amountChanges[0]+amountChanges[1]`) equals `2X`, i.e. `mintedShieldedETH > actualETHBalanceDelta` — confirming the equality `msg.value backing == exactly one accounting term` is violated.     function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
            }
        }

        emit BlockedUtxosCreated();
    }
