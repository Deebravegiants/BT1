### Title
Authorization bypass for `blockOwnerDeletion=true` via UID-only owner-reference matching in `newBlockingOwnerDeletionRefs`/`indexByUID` - (File: plugin/pkg/admission/gc/gc_admission.go)

### Summary
`indexByUID` builds a lookup of the old owner references keyed solely by `ref.UID`, and `newBlockingOwnerDeletionRefs` uses that map to decide whether a blocking owner reference in the new object is "new" (requiring authorization) or already existed (skipping authorization). Because the match is done purely on `UID` and ignores `Kind`/`Name`/`APIVersion`, an attacker who already has one legitimately-authorized blocking owner reference can reuse its `UID` on a completely different, unauthorized owner object and have the admission check treat it as unchanged, skipping the required finalizers/delete authorization check.

### Finding Description
`Validate` in `plugin/pkg/admission/gc/gc_admission.go` computes `newBlockingRefs := newBlockingOwnerDeletionRefs(attributes.GetObject(), attributes.GetOldObject())` [1](#0-0)  and only runs the per-owner authorization loop over the entries returned by that function [2](#0-1) .

`newBlockingOwnerDeletionRefs` determines which refs are "new" blocking refs by indexing the old object's owner references purely by UID via `indexByUID`: [3](#0-2) 
and then, for each blocking ref in the new object, looks it up only by UID to decide whether authorization is required: [4](#0-3) 

Because the lookup key is `ref.UID` alone (not the full owner identity of `APIVersion`/`Kind`/`Name`/`UID`), an attacker can:
1. Legitimately obtain a persisted object with an authorized blocking owner reference, e.g. `{UID: U, Kind: "ConfigMap", Name: "cm1", BlockOwnerDeletion: true}` (attacker has delete/finalizers rights on `cm1`).
2. Submit an update where the owner reference now points to a completely different, unauthorized resource but reuses the same `UID: U`, e.g. `{UID: U, Kind: "Secret", Name: "secret1", BlockOwnerDeletion: true}`.
3. In `newBlockingOwnerDeletionRefs`, `indexedOldRefs[U]` returns the old ConfigMap ref, `oldRef.BlockOwnerDeletion` is `true`, so `wasNotBlocking` is `false`, and the new (Secret) ref is *not* added to `ret`.
4. `newBlockingRefs` ends up empty, so `Validate` returns `nil` without ever calling `ownerRefToDeleteAttributeRecords`/`Authorize` for the Secret — the finalizers/delete authorization check on the actual (new) owner is skipped entirely.

The earlier "cannot set an ownerRef on a resource you can't delete" check only verifies the attacker can delete the dependent object being updated, not the owner referenced, so it does not protect against this bypass [5](#0-4) .

### Impact Explanation
An unprivileged user who can `update`/`patch` `ownerReferences` on a resource they own can set `blockOwnerDeletion=true` against an arbitrary owner object (e.g., a Secret or a cross-namespace/system resource) without possessing `update`/`finalizers` permission on that owner, as long as they know or control a UID value already used by one of their own previously-authorized blocking owner references. This lets the attacker block garbage-collector deletion of resources they are not authorized to protect/interfere with, a scoped authorization-bypass matching the "admission/authorizer bypass — setting a protected field without required authorization" bounty impact class.

### Likelihood Explanation
Exploitation requires only: (1) ability to create/update an object with owner references and (2) prior legitimate authorization to set one blocking owner reference (trivial for a user updating a resource they own, e.g. referencing their own ConfigMap). The attacker fully controls the `metav1.OwnerReference.UID` field in the request payload — it is not cross-validated against the actual UID of the referenced object — so reusing a known UID across two update requests is straightforward and repeatable.

### Recommendation
Change `indexByUID`/`newBlockingOwnerDeletionRefs` to match owner references by their full identity (`APIVersion`, `Kind`, `Name`, and `UID`), not `UID` alone, e.g. index by a composite key or use `apiequality.Semantic.DeepEqual` comparison of the ref identity fields (excluding `BlockOwnerDeletion`/`Controller`) before treating an old ref as matching a new ref.

### Proof of Concept
Add a table-driven test in `plugin/pkg/admission/gc/gc_admission_test.go` (or new test) for `newBlockingOwnerDeletionRefs`:
- `oldObj`: owner references `[{UID: "u1", Kind: "ConfigMap", Name: "cm1", BlockOwnerDeletion: true}]`.
- `newObj`: owner references `[{UID: "u1", Kind: "Secret", Name: "secret1", BlockOwnerDeletion: true}]`.
- Assert `newBlockingOwnerDeletionRefs(newObj, oldObj)` returns a slice containing the Secret ref (i.e., `len(result) == 1` and `result[0].Kind == "Secret"`), proving the changed-owner-identity blocking ref is correctly flagged as new and subject to authorization.
- Currently the function returns an empty slice, demonstrating the bypass; after the fix it must return the Secret ref so `Validate` runs the finalizers authorization check against it.

func indexByUID(refs []metav1.OwnerReference) map[types.UID]metav1.OwnerReference {
	ret := make(map[types.UID]metav1.OwnerReference)
	for _, ref := range refs {
		ret[ref.UID] = ref
	}
