## Title
BandwidthManager.purchase() reverts with underflow when the host's fee token has more than 18 decimals - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` computes a decimal-scaling factor as `10 ** (18 - dec)`, where `dec` is `IERC20Metadata(feeToken).decimals()`. If the host's configured fee token has more than 18 decimals, `18 - dec` underflows in Solidity's checked arithmetic (0.8.17) and the call reverts, permanently bricking bandwidth purchases for that fee token.

### Finding Description
`purchase()` is a permissionless, unprivileged entry point that any bandwidth purchaser calls to top up an app's message-bandwidth allowance on `pallet-bandwidth` via Hyperbridge. Tier prices are stored in 18-decimal units and scaled to the fee token's native decimals before the `safeTransferFrom` pull: [1](#0-0) 

```solidity
uint256 total18d = price18d * months;
address feeToken = IDispatcher(_host).feeToken();
uint8 dec = IERC20Metadata(feeToken).decimals();
uint256 scale = 10 ** (18 - dec);
if (total18d % scale != 0) revert PriceNotRepresentable();
uint256 amount = total18d / scale;
```

`feeToken` is read from `IDispatcher(_host).feeToken()` and is not validated for its decimal count anywhere in this contract. If `dec > 18` (which is a legitimate ERC20 property some tokens use, e.g. YAM-style tokens with 24 decimals), the subtraction `18 - dec` underflows a `uint8`/arithmetic expression and Solidity's default checked math causes every call to `purchase()` to revert with a panic, regardless of caller, tier, or amount.

This is the same bug class flagged in the referenced Sense `AutoRoller.sol` report: an unguarded `10**(18 - decimals)` that assumes `decimals <= 18`.

Notably, the codebase elsewhere (`evm/src/utils/VWAPOracle.sol`) already handles this correctly with a three-way branch (`==18`, `<18` multiply, `>18` divide): [2](#0-1) 

confirming the underflow in `BandwidthManager.sol` is an oversight rather than an accepted design limit — the accompanying docs even acknowledge the risk but dismiss it as "not a concern in practice": [3](#0-2) 

### Impact Explanation
If the fee token configured on the `IsmpHost` for a given `BandwidthManager` deployment has more than 18 decimals, `purchase()` becomes permanently unusable — every call reverts. Since bandwidth purchases are the sole mechanism to top up an app's `pallet-bandwidth` allowance from that chain, this permanently freezes the ability of apps on the affected chain to purchase message-relay bandwidth through this route, a denial-of-service on legitimate message dispatch capacity funding with no workaround short of redeploying the contract.

### Likelihood Explanation
The trigger does not require any malicious actor — it only requires the network's designated ISMP fee token to have `decimals > 18`, a property some real-world ERC20 tokens (and some deliberately chosen fee tokens) exhibit. Any unprivileged caller invoking `purchase()` under such a configuration hits the revert deterministically on every attempt.

### Recommendation
Mirror the pattern already used in `VWAPOracle._normalizeAmount` (`evm/src/utils/VWAPOracle.sol#L240-L248`): branch on `dec` relative to 18 and handle `dec > 18` by dividing instead of subtracting-then-exponentiating, e.g.:

```solidity
uint256 amount;
if (dec == 18) {
    amount = total18d;
} else if (dec < 18) {
    uint256 scale = 10 ** (18 - dec);
    if (total18d % scale != 0) revert PriceNotRepresentable();
    amount = total18d / scale;
} else {
    amount = total18d * (10 ** (dec - 18));
}
```

### Proof of Concept
1. Deploy `BandwidthManager` and set `_host` to an `IsmpHost` whose `feeToken()` returns an ERC20 with `decimals() == 24` (e.g. a mock token as used in `evm/tests/foundry/VWAPOracleTest.sol#L98` for testing high-decimal tokens).
2. Governance configures a tier via `onAccept`/`SetTiers` so `tierPrice[tier] > 0`. [4](#0-3) 
3. Any user calls `purchase(app, tier, months, chain)`. [5](#0-4) 
4. The line `uint256 scale = 10 ** (18 - dec);` underflows (`18 - 24`), causing a panic revert (`0x11`) on every subsequent call, permanently blocking all bandwidth purchases through this manager for that fee token.

Two implications:

1. **Fee tokens with `decimals > 18` would underflow `(18 - dec)`.** This is not a concern in practice — the supported fee tokens are all `≤ 18` decimals.
2. **Tier prices must be representable at the local fee-token's decimals after multiplication by `months`.** A tier priced at `10**12` (a hypothetical sub-penny SKU) and a 6-decimal fee token would revert with `PriceNotRepresentable()` because the 18-decimal value doesn't divide cleanly. Set tier prices to multiples of `10**12` to keep them clean on 6-decimal fee tokens.
