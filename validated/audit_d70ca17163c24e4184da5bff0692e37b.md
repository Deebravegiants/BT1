### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on a validly-signed webhook payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the shop identity used by the application (`request.shop`, sourced from the `X-Shopify-Shop-Domain` HTTP header) is never included in the signed material. This breaks the intended binding `shop authenticated == shop acted upon`, letting a holder of any one validly-signed webhook body relabel it as belonging to a different, arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`, i.e. the body, and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates only on this body HMAC, then immediately trusts `request.shop` (the header) as the tenant identity handed to the app's handler: [4](#0-3) [5](#0-4) 

Because the signature only binds `raw_body`, two requests with the same body but different `X-Shopify-Shop-Domain` header values produce the **same valid HMAC**. Any party who legitimately receives (or can otherwise obtain) one authentic webhook body/HMAC pair for their own shop can retransmit that exact body with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain, and `HmacValidator.validate` will still return `true`. The application then dispatches `WebhookMetadata.new(shop: <attacker-chosen domain>, ...)` to the handler, i.e., the equality `shop cryptographically proven == shop acted upon` is false — the shop field is entirely outside the HMAC's coverage.

### Impact Explanation
This is a cross-tenant confusion primitive: the gem itself hands the app a shop identity that is not authenticated, even though the surrounding code path claims to have validated the webhook ("Invalid webhook HMAC." check gives false assurance). Any app built on this gem's documented `Registry.process`/`WebhookHandler` API that keys server-side state (session lookup, uninstall/GDPR handling, data deletion, token revocation, etc.) off `WebhookMetadata#shop` can be made to perform that action against an arbitrary victim shop using an attacker-controlled but validly-HMAC'd payload — meeting the "cross-tenant access" bar. This is a defect in the gem's own `Request`/`HmacValidator`/`Registry` implementation, not a misuse of the API by the host app, since the documented contract is "HMAC validated ⇒ header data such as shop is trustworthy."

### Likelihood Explanation
Obtaining one authentic, replayable body+HMAC pair is straightforward for common low-value/no-secret-bearing topics (e.g., `app/uninstalled`, `shop/redact`, `customers/redact` bodies are often small/predictable, and an attacker who installs the app on their own store can legitimately receive several signed webhooks and immediately reuse the body/HMAC while only changing the shop header). No possession of `api_secret_key` or any access token is required — only a network position to POST to the app's webhook endpoint with attacker-chosen headers, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Include the shop-identifying header (and ideally topic/api-version) inside the HMAC-covered signable string, or otherwise cryptographically bind them to the body (e.g., verify the shop domain embedded in the JSON payload, where present, matches the header, or extend `to_signable_string` to canonicalize `shop-domain` + `raw_body`). At minimum, document/enforce that `request.shop` must never be trusted independent of a payload-embedded, HMAC-covered shop identifier.

### Proof of Concept
1. App installs on `attacker.myshopify.com`; Shopify sends a genuine webhook, e.g. `app/uninstalled`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the identical raw body `B`, identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `to_signable_string` returns `B`, unaffected by the header change. [1](#0-0) 
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` and matches `H` — validation passes. [3](#0-2) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to treat the event (e.g., uninstall/redact) as belonging to `victim.myshopify.com` despite no cryptographic proof tying that shop to the event. [6](#0-5)
