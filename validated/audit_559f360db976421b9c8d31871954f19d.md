### Title
Opaque user-supplied `swap_xdr` routes through an unallowlisted venue let an attacker contract drain the caller's wallet under the caller's own signed auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Like the koko advisory, where a legitimate session interface hands user input to a dangerously powerful interpreter (the MongoDB shell executing `child_process`), the controller's strategy verbs hand an opaque, attacker-constructed `swap_xdr` blob to the swap router, which invokes whichever `pool` contract the payload names. No venue allowlist exists, so a crafted route puts attacker code on the call stack inside the victim's authorized invocation, where it can issue a `token.transfer` from the victim's address. Simulation records that transfer as a child of the victim's `swap_collateral` auth entry; if the victim signs the simulated tree — the normal wallet flow — the host executes the theft.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 25-38) forwards the `swap` bytes verbatim to `router.execute_strategy` and grants only a bounded input-transfer auth on the controller side. The router it calls keeps no allowlist of the pool/token addresses named in the payload — the threat model states this explicitly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md`, lines 154-165). An unprivileged attacker reaches this via `swap_collateral`, `multiply`, `swap_debt`, or `repay_debt_with_collateral` by supplying a route whose hop `pool` is an attacker-deployed contract. That contract runs mid-transaction and calls `token.transfer(victim, attacker, amount)`; because the victim is the authenticated root of the invocation, the host records it under the victim's auth entry, and it executes if the victim signs that tree — exactly what `simulateTransaction`-driven signing produces.

### Impact Explanation
Theft of user funds: arbitrary tokens in the victim's wallet (not just the routed swap input) can be transferred to the attacker. The repo's own adversarial test proves the end-to-end movement: `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows Alice's entire `wallet_token` balance moved to the attacker, and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the same transfer executing under enforced auth once the simulated (poisoned) tree is signed (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, lines 194-269). Neither the payload `min_out` nor the post-swap health-factor gate bounds the loss, because the stolen amount never touches the swap accounting.

### Likelihood Explanation
Medium likelihood. The attacker must get the victim to submit an attacker-crafted route (phished quote, malicious frontend, or compromised quote server serving a poisoned `routeXdr`), and Soroban requires the rogue transfer to appear in the signed auth tree. However, Soroban wallets do not meaningfully display nested sub-invocations to users, so a victim signing "the swap" typically signs whatever simulation returned. The threat model itself concedes the mitigation is off-chain: "A client must decode the route it signs and refuse an authorization tree with any other child" — nothing in the contracts prevents the poisoned route from being constructed or executed. This matches the advisory's UI:R profile: an authenticated user's normal action is the exploit vector.

### Recommendation
Enforce protection in-protocol rather than relying on every client to audit auth trees:

- Add a governance-controlled venue/pool allowlist (or venue attestation) consulted before executing strategy routes, so hop `pool` addresses must be registered contracts.
- Alternatively, have the controller restrict strategy entrypoints to routes it can structurally validate — e.g., reject `swap_xdr` whose decoded hops reference addresses outside a published registry — so an attacker cannot name arbitrary contracts.
- At minimum, expose a view that returns the decoded hop addresses for a given `swap_xdr` so integrators can check them without re-implementing the XDR decoder.

### Proof of Concept
The in-repo test is a working PoE. Sketch of the attack:

1. Attacker deploys `RogueHopPool` with a `swap()` that calls `token::Client::new(&wallet_token).transfer(&victim, &attacker, &amount)` (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, lines 51-72).
2. Attacker serves a route whose hop `pool` = `RogueHopPool`, with a fair `min_out` so the swap itself looks honest (lines 111-125).
3. Victim calls `controller.swap_collateral(victim, account_id, USDC, swap_in, ETH, route)`; `swap_tokens` forwards the route to the router, which invokes `RogueHopPool.swap`. The rogue transfer is recorded as a sub-invocation of the victim's `swap_collateral` auth entry (lines 214-222).
4. Victim signs the simulated tree (default wallet behavior). Host enforces the signed tree and the `transfer` executes: victim's `WALLET_BALANCE` → attacker, while the victim still receives the "fair" `FAIR_OUT_ETH` swap output so nothing on-chain looks anomalous (lines 224-227, 265-268).

The control in the same test shows an honest route under a minimal tree behaves correctly, isolating the root cause to the unallowlisted, payload-named callee.
