Audit Report

## Title
Bearer/JWT authentication token logged in plaintext via Debug-level request logging in the Vault gateway handlers - (File: core/services/gateway/handlers/vault/handler.go, core/capabilities/vault/gw_handler.go)

## Summary
Both the connector-side (`core/capabilities/vault/gw_handler.go`) and the public HTTP-facing (`core/services/gateway/handlers/vault/handler.go`) Vault gateway handlers log the full `jsonrpc.Request[json.RawMessage]` object via `Debugw`, which includes the `Auth` field carrying the caller's bearer/JWT token used to authenticate Vault operations. This occurs at `handler.go:403` before authorization completes, and at `gw_handler.go:182` and `gw_handler.go:231` for gateway-relayed messages, exposing the raw credential to log output whenever Debug-level logging is enabled.

## Finding Description
`handler.go:394-403` receives the inbound request and immediately calls `h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)` before any authorization check (`h.requestProcessor.ProcessRequest` is called afterward at line 427). Similarly, `gw_handler.go:180-182` logs `reqLggr.Debugw("received message from gateway", "req", req)` immediately on receipt, and `gw_handler.go:226-231` logs the full outgoing `response` object via `Infow("Sent message to gateway", "resp", response)`.

The `Auth` field is confirmed as a live bearer/JWT credential by its usage throughout `system-tests/tests/smoke/cre/vault_don_test_helpers.go`, where `jsonRequest.Auth` is explicitly extracted and set as `Authorization: Bearer <token>` header (e.g. lines 550-559, 1241-1249), and by `core/capabilities/vault/authorizer.go` and `jwt_based_auth.go`, which pass `req.Auth` directly into JWT validation (`v.validateToken(ctx, req.Auth)` at `jwt_based_auth.go:189`).

By contrast, the authorization pipeline (`core/capabilities/vault/authorizer.go:106,110,114,117`) and `gateway_vault_request_processor.go:270-276` consistently log only `"hasAuth", req.Auth != ""` — a deliberate pattern showing the codebase's authors intended to avoid logging the raw token. There also exists a dedicated test, `TestVaultHandler_InvalidParamsDoesNotLogRawParams` (`core/services/gateway/handlers/vault/handler_test.go:1016-1058`), which explicitly asserts that raw request *params* are not leaked into logs at Info level or above — but this test explicitly carves out and ignores "the pre-existing whole-request Debug log" (per its own comment at line 1019), confirming the maintainers are aware of, and have consciously left unaddressed, the whole-request Debug-level log containing `Auth`.

No redaction, `String()`/`LogValue()` override, or masking mechanism exists on the `jsonrpc.Request`/`Response` types (defined in the external `chainlink-common/pkg/jsonrpc2` package) to protect the `Auth` field from being serialized into logs when the whole struct is passed to a structured logger.

## Impact Explanation
When Debug-level logging is enabled, an unprivileged caller's bearer/JWT token — used to authorize `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList` operations against the Vault DON — is written verbatim into node/gateway logs. Anyone with read access to those logs (log aggregation, support bundles, misconfigured shipping) could extract and replay the token to impersonate the original caller and perform unauthorized vault-secret operations under that owner's identity. This maps to the "gateway request impersonation" / "key/secret exfiltration" impact category.

## Likelihood Explanation
Exploitability is strictly gated on Debug-level logging being enabled, which is not the production default. This reduces but does not eliminate real-world exposure, since Debug logging is a common temporary troubleshooting configuration; once enabled, every routed Vault request unconditionally leaks its token with no way to suppress just this field.

## Recommendation
- Remove the raw `req`/`request`/`resp` struct from the `Debugw`/`Infow` calls at `core/services/gateway/handlers/vault/handler.go:403` and `core/capabilities/vault/gw_handler.go:182,231`.
- Replace with explicit minimal field lists (`method`, `requestID`, `hasAuth`), matching the safe pattern already used in `authorizer.go` and `gateway_vault_request_processor.go`.
- Add a redacting `LogValue()`/`String()` method on the shared `jsonrpc.Request`/`Response` types in `chainlink-common/pkg/jsonrpc2` so any future ad-hoc logging of the whole struct is safe by default.

## Proof of Concept
1. Start a chainlink node/gateway with the Vault capability enabled and `Log.Level = 'debug'`.
2. Send an authorized `SecretsCreate` request to the gateway HTTP endpoint with header `Authorization: Bearer <token>` (mirroring `sendVaultSignedOCRRequestToGateway`, `system-tests/tests/smoke/cre/vault_don_test_helpers.go:547-559`).
3. Inspect logs: the line `Debugw("handling vault request", ..., "request", req)` in `handler.go:403` (and correspondingly `Debugw("received message from gateway", "req", req)` in `gw_handler.go:182`) contains the full request struct including the plaintext `Auth` bearer token.
