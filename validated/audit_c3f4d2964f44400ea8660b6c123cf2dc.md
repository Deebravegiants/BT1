### Title
Session identifier trusted directly from an unsigned client cookie, enabling cross‑tenant session hijacking - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw, unauthenticated value of the `shopify_per_user_session` cookie as the trusted session identifier for both the embedded (cookie‑fallback) and non‑embedded OAuth flows, with no cryptographic binding to the browser that completed OAuth. Because session identifiers are built from fully predictable, public data (`"#{shop}_#{user_id}"` or `"offline_#{shop}"`), any unprivileged user who can set a cookie on their own browser can impersonate another shop's session id and, if the host app uses that id to fetch a stored session/access token (the documented usage pattern), obtain another merchant's Shopify access token.

### Finding Description
`SessionUtils.current_session_id` reads the session id straight out of the cookie jar with no signature check: [1](#0-0) [2](#0-1) 

The value that ends up in that cookie is produced during `Oauth.validate_auth_callback` and assigned into the response cookie with `SessionCookie.new(value: session.id, ...)` for non‑embedded apps: [3](#0-2) 

The documented controller example sets this cookie with a plain (unsigned, unencrypted) `cookies[...] =` assignment — only `secure`/`http_only` flags are applied, no `cookies.signed`/`cookies.encrypted`: [4](#0-3) 

Session ids themselves are deterministic, predictable strings derived only from public data (the shop's `myshopify.com` domain and, for online sessions, a numeric user id): [5](#0-4) 

The intended binding is:
`session_id_returned_by_current_session_id == session_id_cryptographically_bound_to_the_browser_that_completed_OAuth_for_that_shop`

What is actually implemented is:
`session_id_returned_by_current_session_id == raw_bytes_of_a_client_supplied_cookie`

Because the cookie carries no HMAC/signature and its expected contents (`offline_{shop}` or `{shop}_{user_id}`) are guessable/enumerable — `myshopify.com` shop domains are public, and `offline_{shop}` requires no user id at all — an attacker only needs to set this one cookie value in their own browser to have `current_session_id` return an identifier belonging to a *different* shop's session.

### Impact Explanation
Any host application built on this gem's documented, standard non‑embedded OAuth flow (or the embedded cookie‑fallback branch) that follows the intended pattern — retrieve `current_session_id`, then look up the corresponding stored `Session`/access token by that id — will hand the caller a session/access token belonging to an arbitrary victim shop, purely from a self‑set cookie value. This is cross‑tenant access to another merchant's Shopify Admin access token, satisfying the "cross-tenant access" / credential-theft impact tier: an unprivileged internet user (needing no shop access token, no `client_secret`, no leaked credential) can pivot into another tenant's authenticated session.

### Likelihood Explanation
High. No secret material is required to exploit this — only knowledge of the target's `*.myshopify.com` domain (public) is needed for offline sessions (`offline_#{shop}`), and for online sessions only a small numeric user id is additionally needed. The vulnerable code path (`SessionUtils.current_session_id` → `cookie_session_id`) is exactly the mechanism the gem documents for retrieving the session id to hand to session storage lookups, so any app that follows the documented flow is affected without deviating from the library's own guidance.

### Recommendation
Do not trust the raw cookie value as an authoritative session identifier. Either:
- Sign/encrypt the session cookie (e.g., require the host to use `cookies.signed`/`cookies.encrypted`, and document this explicitly instead of showing an unsigned `cookies[...] =` example), or
- Bind the session cookie value to a server-side, unguessable nonce established during `validate_auth_callback` (rather than the deterministic `shop`/`shop_user_id` string), and validate that nonce in `current_session_id` before returning a trusted session id.

### Proof of Concept
1. Victim's shop `victim-shop.myshopify.com` installs the app; app performs offline OAuth via `Oauth.validate_auth_callback`, which sets cookie `shopify_per_user_session=offline_victim-shop.myshopify.com` (per `lib/shopify_api/auth/oauth.rb` line 106-109 and `SessionUtils.offline_session_id`).
2. Attacker, an unrelated unprivileged user, opens the same app in their own browser and manually sets the cookie `shopify_per_user_session=offline_victim-shop.myshopify.com` (guessable since the shop domain is public).
3. Attacker triggers any authenticated request in the host app; the app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` with zero verification (`lib/shopify_api/utils/session_utils.rb` lines 32-37, 68-71).
4. The host app looks up the stored `Session` for that id and uses its access token to make Admin API calls on the attacker's behalf, but scoped to `victim-shop.myshopify.com` — a full cross‑tenant compromise.
