## Analysis

I found a valid analog in the Tron variant of `IntentGatewayV2.placeOrder`. Unlike the EVM version (`evm/src/apps/IntentGatewayV2.sol`), which snapshots `balancesBefore`/`balancesAfter` around the sweep from the `CallDispatcher` to measure the *actual* amount received before crediting escrow (protecting against fee-on-transfer tokens skimming value), the Tron version credits escrow using a value computed before the sweep transfer actually executes, structurally the same class of bug as the reported `checkForBalance()` issue: a balance/amount check is performed against a value that does not reflect what was actually transferred, so it can't prevent the loss it's meant to guard against.

### Title
Escrow credited from dispatcher's pre-transfer balance, not actual amount received by the gateway for predispatch fee-on-transfer/lossy tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the predispatch path of `placeOrder`, the Tron `IntentGatewayV2` computes `dust = balance - requiredAmount` and credits `_orders[commitment][token] += reducedInputs[i].amount` **before** the sweep `Call` (`ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`) actually executes and moves tokens from the dispatcher to the gateway. `balance` is `IERC20(token).balanceOf(dispatcher)`, i.e., what the dispatcher holds prior to transferring it onward — not what the gateway ends up holding.

### Finding Description [1](#0-0) 

The loop at lines 418–446 computes `balance` (the dispatcher's pre-sweep token balance), builds a `transferCalls[i]` to sweep that `balance` to `address(this)`, computes `dust = balance - requiredAmount`, and immediately credits escrow (`_orders[commitment][token] += reducedInputs[i].amount`) — all using pre-transfer, requested-amount-derived figures. Only *after* the loop completes does it call `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` to actually perform the sweep transfer.

Compare this with the reviewed EVM version, which explicitly snapshots `balancesBefore[i]` before the sweep and computes `received = balanceAfter - balancesBefore[i]` after the sweep executes, then mutates `order.inputs[i].amount` to the real received value before computing protocol fees and the commitment: [2](#0-1) 

For any token with non-standard transfer semantics (fee-on-transfer, rebasing, or one that silently returns less than requested — the exact bug class flagged in the analog report as "the vault will get a fraction of a coin less than expected"), the Tron contract will escrow `reducedInputs[i].amount` (derived from the user-requested `order.inputs[i].amount`) even though the gateway actually received less. The `reducedInputs`/`commitment` themselves are also computed earlier, at lines 348–385, strictly from `order.inputs[i].amount` (the requested amount), with no correction step for actual-received value anywhere in the Tron contract's predispatch branch.

### Impact Explanation
The escrow ledger (`_orders[commitment][token]`) can be inflated beyond the token balance actually held by the gateway contract. Downstream, `fillOrder`/redemption paths pay out of this escrow ledger, so the contract can become insolvent for that token — the first several fills/redemptions succeed by transferring out tokens that were never actually deposited, at the expense of the last redeemer whose transfer will revert (fund freezing) or, if other users' funds pooled in the same token address are commingled, a subsidy from other orders' escrow (fund theft from other order holders). This satisfies "concrete theft or permanent freezing of funds" — a single user orchestrating a predispatch call with a fee-on-transfer/deflationary token as an input can extract escrow credit exceeding what they actually deposited.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with `predispatch.call.length > 0 && predispatch.assets.length > 0` and an input token that is fee-on-transfer or otherwise transfers less than the nominal amount. Whether such tokens are within the deployment's supported asset set is a chain-specific/governance decision, but the contract itself performs no allowlisting or actual-balance verification to prevent it — the EVM sibling contract explicitly added the balancesBefore/after guard for exactly this reason, confirming the maintainers treat it as an in-scope threat model for this dispatch path.

### Recommendation
Mirror the EVM contract's fix in the Tron contract: snapshot `balancesBefore[i] = balanceOf(address(this))` (or `address(this).balance` for native) prior to executing `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`, execute the sweep, then compute `received = balanceOf(address(this)) - balancesBefore[i]` afterward. Use `received` (capped by `requiredAmount`, with any excess reported via `DustCollected`) instead of `balance` for the dust calculation and instead of `order.inputs[i].amount`/`reducedInputs[i].amount` for the escrow credit and commitment hash.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a predispatch-capable order flow and configure an input token that charges a 5% transfer fee (fee-on-transfer ERC20).
2. User calls `placeOrder` with `predispatch.assets` containing the fee-on-transfer token, `predispatch.call` a no-op dispatch, and `order.inputs[0].amount = 1000` of that token.
3. Dispatcher ends up holding `950` after the predispatch transfer fee (`IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` at line 405 already lost 5%). `balance = IERC20(token).balanceOf(dispatcher) = 950`.
4. Since `950 < requiredAmount(1000)` this specific example reverts at line 429 (`InvalidInput`), but with a smaller fee (e.g., 0.5%) or a `requiredAmount` set lower than the sent amount, `balance ≥ requiredAmount` passes, and the transfer sweep (`transfer(address(this), balance)`) itself will only deliver `balance * (1 - feeBps)` to the gateway due to the second application of the transfer fee — yet `_orders[commitment][token]` is credited with `reducedInputs[i].amount` computed from the original `requiredAmount`, not the post-sweep received value, over-crediting escrow relative to the gateway's real token balance.
