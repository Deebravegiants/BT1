### Title
Cross-chain decimal down-scaling in `pallet-hyper-fungible-token`'s `on_accept`/`on_timeout` can round the credited amount to zero, burning/locking user tokens on the source chain with no corresponding mint on the destination - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token` bridges tokens between a substrate chain and EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts. Amounts are always transported on the wire in the EVM contract's decimals, and the pallet converts down to local decimals with a plain integer division that truncates. Because the source-chain contract already irreversibly burned or escrowed the sender's full amount before dispatch, any amount smaller than the decimal scaling factor is converted to `0` on delivery, permanently destroying the user's funds while crediting them nothing.

### Finding Description
`convert_to_balance` performs the ERC20 → local-balance conversion by dividing and truncating to a string, with no minimum-amount check: [1](#0-0) 

This is invoked in `on_accept` (inbound transfer credited to the beneficiary) and again in `on_timeout` (refund of the original sender): [2](#0-1) [3](#0-2) 

`register_token`/`update_token` only guarantee `erc_decimals >= local_decimals` (never the reverse), which is exactly the precondition under which `convert_to_balance`'s division can truncate to zero: [4](#0-3) 

On the EVM side, a `WrappedHyperFungibleToken` (or `HyperFungibleToken`, which burns) irrevocably takes custody of `params.amount` of the underlying token *before* dispatch, with no minimum-amount check, and forwards that exact `uint256` amount in the message body: [5](#0-4) 

If a user sends an amount smaller than `10 ** (erc_decimals - local_decimals)` (e.g. any amount below `1e6` wei of an 18-decimal token bridging to a 12-decimal native asset, as documented for the `BridgeToken` scaling factor), `convert_to_balance` returns `0`. `on_accept` then proceeds normally: it transfers/mints `amount = 0` to the beneficiary (a no-op that doesn't error), still emits `TokenReceived`, and the ISMP delivery is reported as successfully processed: [6](#0-5) [7](#0-6) 

Because a successful `on_accept` never returns an error, the ISMP relayer path treats the message as delivered — there is no timeout/refund path triggered, and the user's original tokens (already burned/escrowed on the source chain) are gone with nothing credited on the destination. Even the `on_timeout` refund path is subject to the identical truncation, so an unlucky small-dust transfer can also fail to be refunded correctly.

The exact same 18-decimal EVM ↔ 12-decimal-nexus scaling factor is documented for `BridgeToken`, confirming this is a live, reachable configuration rather than a hypothetical: [8](#0-7) 

### Impact Explanation
This is a direct, permanent loss-of-funds bug reachable by any unprivileged user calling `HyperFungibleToken.send()`/`WrappedHyperFungibleToken.send()` (or the substrate `send` extrinsic in the opposite direction) with a small enough amount relative to the configured decimal spread between chains. The user's tokens are burned/escrowed on the source chain, and the destination chain mints/releases zero tokens to them, with the request still marked as successfully delivered. This matches the "Medium" severity of the reported analog: no attacker action is required beyond choosing (or being tricked/defaulted into, e.g. by a UI passing a raw wei amount) a small transfer amount.

### Likelihood Explanation
Likelihood is realistic wherever `erc_decimals > local_decimals` is configured (explicitly supported and documented, e.g. `BridgeToken`'s 18 vs 12 decimals, or any ERC20 with 18 decimals paired against a lower-decimal substrate asset like a 6-decimal stablecoin). No special privileges are needed — a normal user transaction with a small amount (dust, a rounding error in a UI, or a deliberately crafted small transfer to grief another chain's operations) triggers the truncation. The registration-time invariant (`erc_decimals >= local_decimals`) actively guarantees that this scaling-down code path is exercised on every inbound message for such asset pairs.

### Recommendation
- In `convert_to_balance`, reject (return an error) rather than silently truncate when the computed local balance is `0` but the input `value` was non-zero, so `on_accept`/`on_timeout` fail loudly instead of consuming the message.
- Enforce a minimum transferable amount in the `send()` path (both in the pallet and in the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts) equal to at least `10 ** (erc_decimals - local_decimals)`, so a message that would round to zero can never be dispatched in the first place.
- Consider having `on_accept` explicitly error (rather than proceed) when the converted `amount` is `0`, ensuring the request fails/times out and the source-chain refund path in `on_timeout` is triggered instead of silently discarding funds.

### Proof of Concept
1. Register a native asset `X` with `local_decimals = 12` and configure a peer EVM chain with `erc_decimals = 18` (satisfies the `config.decimals >= local_decimals` check in `register_token`).
2. On the EVM `HyperFungibleToken` for `X`, call `send()` with `amount = 999_999` (i.e., `< 10^6`), destined for the substrate chain.
3. The EVM contract burns/escrows the full `999_999` wei from the sender and dispatches the ISMP `Send` message carrying `amount = 999_999` in the message body.
4. On delivery, `on_accept` computes `erc_decimals - local_decimals = 6`, so `convert_to_balance` divides `999_999 / 10^6 = 0` (integer division, per `modules/pallets/hyper-fungible-token/src/impls.rs` lines 43-52).
5. `on_accept` mints/transfers `0` to the beneficiary, still emits `TokenReceived { amount: 0, .. }`, and returns `Ok`, meaning the ISMP request is recorded as successfully handled.
6. Net effect: the sender's `999_999` wei were irreversibly burned/escrowed on the EVM chain, and the beneficiary received `0` tokens on the substrate chain — funds are permanently lost.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }
