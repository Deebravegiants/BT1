### Title
Webhook shop-domain and topic identity fields are unauthenticated (not covered by HMAC), enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-covered "signable string" from only the raw request body, while the `shop-domain` and `topic` values are read directly from unauthenticated HTTP headers and then handed to the app's webhook handler as trusted identity fields. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then blindly forwards the header-derived `shop` and `topic` to the handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop` and `Request#topic` are read straight from headers, which are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` only checks this body HMAC, then dispatches directly to the handler using the unauthenticated `request.topic` and `request.shop`: [4](#0-3) 

The documented handler contract explicitly treats `data.shop` as "The shop domain of the webhook" and the sample handler code uses it directly as the tenant key (`shop_domain: data.shop`) to drive downstream per-shop work: [5](#0-4) 

This breaks the identity binding: `shop` verified by HMAC (none — it's not signed) ≠ `shop` used by the host application as the session/tenant key. Because the HMAC only proves the body bytes are unmodified and genuinely signed by Shopify with the app's secret, but does not bind that body to the specific `shop-domain` or `topic` header values, an attacker who possesses one valid `(raw_body, hmac)` pair — for example a legitimate webhook delivered to a shop they themselves installed the app on — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (any other merchant's domain) and/or an arbitrary `X-Shopify-Topic` header. The gem will report `Utils::HmacValidator.validate` as successful (since it only checks the body) and hand the forged shop/topic to the handler as if Shopify itself vouched for them.

### Impact Explanation
This is a cross-tenant identity confusion: the library's own validated contract (`process` succeeding, `WebhookMetadata#shop`/`#topic` being trustworthy) is violated. A host application that follows the gem's documented pattern (uses `data.shop` as the tenant/session key to route work, e.g. enqueue background jobs, apply order/product changes, or trigger mandatory compliance flows like `customers/redact`) can be made to process attacker-controlled body content under a victim shop's identity, or have a webhook body intended for one topic reinterpreted under a different, sensitive topic (e.g. faking `app/uninstalled` or a GDPR compliance webhook for a shop the attacker doesn't own). This meets the "cross-tenant access" bar because the gem asserts a security guarantee (`process` = "verify the request did indeed come from Shopify" per the gem's own doc) that does not actually cover the shop/topic binding.

### Likelihood Explanation
Moderate. The attacker needs a genuine `(raw_body, hmac)` pair, which is trivially obtainable by installing the target app on a shop the attacker controls (a normal unprivileged flow — no special access token or secret is required), then replaying that captured body+HMAC to the same endpoint with forged `shop-domain`/`topic` headers. No knowledge of `api_secret_key` is needed since the attacker reuses a valid signature they legitimately received. Real-world exploitability depends on whether the specific handler implementation relies solely on `data.shop`/`data.topic` for security-sensitive branching (common per the gem's own documented handler pattern), but the gem itself provides no defense against this substitution.

### Recommendation
Bind the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers into the HMAC-signed content (or otherwise cryptographically bind them to the body) rather than trusting them as raw, unauthenticated headers. At minimum, `Registry.process` should not forward header-derived `shop`/`topic` to handlers as though they were verified by the HMAC check that only covers the body.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid and correctly signed with the app's secret since Shopify sent them.
2. Replay this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com` (a shop the attacker does not control) and/or replace `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers unconditionally: [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it checks only the body against the secret — it never inspects `shop` or `topic`: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` carrying the attacker-forged `shop`/`topic`, and any host app that keys work off `data.shop` (as the gem's own documentation instructs) processes attacker-supplied content under `victim.myshopify.com`'s identity.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
