Based on the investigation, I found a strong analog to the reported TOKI fee-drift bug within Hyperbridge's Simplex intent-filler package.

### Title
Disabled overfill clamp lets a manipulated Uniswap V4 venue price drain a Simplex filler's LP inventory on price drift - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
Simplex's FX filler strategy prices venue-quoted legs (curveless, USD-stable-anchored pairs) directly from a Uniswap V4 pool's spot price and, once computed, no longer clamps the payout to the user's requested amount plus a small overfill tolerance. The per-leg loss bound (`maxOverfillBps`) that used to cap output has been deliberately reduced to a warning-only check, so an order placer able to move the V4 pool's spot price (or catch it during a drift/thin-liquidity moment) can force the filler to pay out far more of the exotic token than the order requests, draining the filler's Uniswap V4 position/vault — the same "ignored price drift, fee/clamp too weak" root cause as the TOKI report, applied to an intent-solver's own reserves.

### Finding Description
`resolveLegRates` in [1](#0-0)  prices a curveless, USD-anchored leg directly off the live Uniswap V4 pool mid-price (`venueUsdPrice`), gated only by `checkPriceGuard`, which rejects a fill only when the pool's quote deviates from a **static, operator-configured** `referencePrice` by more than `maxDeviationBps` — and only when a guard is configured at all (`referencePrice`/`maxDeviationBps` are optional, per [2](#0-1) ).

Once a rate is resolved, the computed `policyMaxOutput` (the amount the filler will actually pay) is compared to an `overfillCeiling` derived from the user's requested `output.amount`, but the clamp itself has been disabled — the code only warns and still fills the full unclamped amount: [3](#0-2) 

The accompanying decision doc confirms this was an intentional, acknowledged trade-off: "the clamp at the overfill-ceiling block is still a no-op assignment... Restoring the payout makes that ceiling meaningful again and it should be either re-armed or deleted outright." [4](#0-3) 

The venue-pricing flow itself is documented as lacking execution-cost/impact protection beyond the static reference-deviation guard: "`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost." [5](#0-4) 

This mirrors the TOKI M-03 bug class precisely: a fee/clamp mechanism that is supposed to price in cross-venue price drift is present in the code path but has been neutralized (binary/no-op check instead of an economically meaningful bound), letting a counterparty extract the difference between the quoted price and the "real" price, funded out of the protocol's/solver's own reserves (here, the Uniswap V4 LP position(s) backing `[vault.uniswapV4]`).

### Impact Explanation
An order placer who can push (via a flash swap, low-liquidity pool, or simply timing against a stale/thin V4 pool state) the venue quote away from fair value — but still within the operator's configured `maxDeviationBps` band, or against an unguarded chain where no `referencePrice` is set at all (guard fields are optional) — can construct an order whose `output.amount` is deliberately understated relative to `policyMaxOutput`. Because the overfill clamp is a no-op, the filler pays the full unclamped `policyMaxOutput`, funded from wallet balance and then from `UniswapV4FundingPlanner.planWithdrawalForToken`, which withdraws liquidity directly from the operator's Uniswap V4 position [6](#0-5) . Repeated fills at manipulated prices drain the LP position, i.e., concrete theft of solver-held funds via a reachable, unprivileged path (any order placer submitting an intent order).

### Likelihood Explanation
Medium: exploitation requires either an unguarded chain/position (guard fields are optional and off by default) or moving/timing the V4 spot price within the configured deviation band, both of which are realistic for a thin exotic-token pool such as the cNGN/USDC pairs this feature targets. The bug is also explicitly acknowledged in-repo as a known, deliberately left weakness pending re-arming.

### Recommendation
Re-enable a real clamp on `policyMaxOutput` for venue-priced legs (or restrict the disabled clamp to curve-priced legs only, where the curve itself already encodes acceptable size/price), and/or make `checkPriceGuard` mandatory (not optional) for any pair funded from Uniswap V4, incorporating execution-cost/impact (pool fee tier, depth) rather than only comparing to a static reference. Add regression tests that a manipulated or thin V4 pool cannot force an overfill beyond `maxOverfillBps` of the user's requested output.

### Proof of Concept
1. Operator configures a `[vault.uniswapV4]` position for an exotic/USD pair with no `referencePrice`/`maxDeviationBps` guard (both optional), or with a wide deviation band.
2. Attacker (order placer) manipulates or waits for the V4 pool's spot price to sit at the edge of (or outside, if no guard) fair value.
3. Attacker places an intent order with `output.amount` set low relative to the manipulated `policyMaxOutput` the filler will compute from the skewed venue price.
4. `calculateProfitability`/fill path in `fx.ts` computes `rawPolicyMaxOutput` from the skewed venue rate, logs an "Overfill ceiling exceeded" warning, but does not clamp — `targetOutput = policyMaxOutput` is paid in full [7](#0-6) .
5. The shortfall is funded via `UniswapV4FundingPlanner.planWithdrawalForToken`, withdrawing from the LP position; repeating the order drains the position over successive fills.
