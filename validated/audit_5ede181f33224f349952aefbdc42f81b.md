## Title
Unbounded `TokenInfo[]` arrays in `IntentGatewayV2` orders let a griefer force out-of-gas reverts that block escrow release and entire message batches - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
`placeOrder` accepts an `Order` whose `inputs` and `output.assets` arrays have no maximum length. `_withdraw` and `_execute` (and their Tron-contract equivalents) later iterate over these arrays performing a storage write plus an external `transfer`/native-value send per element, without any bound or per-iteration gas cap. An order crafted with a very large number of tokens can be made to consume gas linearly with array length, to the point that any transaction which must process that order's withdrawal/refund/response callback runs out of gas and reverts unconditionally.

### Finding Description
`placeOrder` only checks `order.inputs.length == 0` and rejects duplicate output tokens; it never caps the number of elements in `order.inputs` or `order.output.assets`: [1](#0-0) 

Later, escrow release loops over the full token list, performing a storage read/write and an external call (`_sendValue`/`safeTransfer`) per entry, with no length limit: [2](#0-1) 

The Tron variant of the same function has an identical unbounded loop: [3](#0-2) 

`_execute` similarly loops over `outputsLen` (order-controlled) to sweep tokens back after dispatcher execution: [4](#0-3) 

Crucially, the cross-chain refund path is triggered via an ISMP GET response callback (`onGetResponse` → `withdraw`), which is invoked by `HandlerV2.handleGetResponses` in a plain loop with no try/catch around `host.dispatchIncoming`: [5](#0-4) 

Because `dispatchIncoming` is called unprotected inside the loop, if the destination app's callback (`onGetResponse` → `_withdraw`) reverts — e.g., due to running out of gas while iterating a huge, attacker-supplied `tokens` array — the revert propagates and reverts the **entire** `handleGetResponses` transaction, including all unrelated GET responses batched in the same call. This is directly analogous to the reported Tokemak `LMPVault._withdraw` issue: an unbounded loop over an attacker-influenced/unbounded set, invoked from a path that must succeed for other users' funds to move, can be forced into out-of-gas failure.

### Impact Explanation
- **Permanent freezing of the griefer's own escrow** is the direct consequence for the order that has the oversized token array: `_withdraw`/`withdraw` can never fit inside a block's gas limit, so `RedeemEscrow`/`RefundEscrow` processing for that specific commitment can never complete, permanently locking the escrowed assets in the gateway contract.
- **Blocking of a message-delivery route** is the more severe systemic effect: because `handleGetResponses` (and analogously `handlePostRequests`/`onAccept` flows) delivers a *batch* of independent messages in a single transaction without isolating per-message failures, a single crafted, oversized order response mixed into (or preceding) a batch by a relayer will make that batch unconditionally revert, denying delivery of otherwise-valid, unrelated messages routed through the same handler call. This matches the "route unable to deliver messages" acceptance criterion.
- Severity: Medium — funds tied to the crafted order are frozen, and honest relayers/solvers can be forced into wasted gas or blocked delivery when batching messages that include such an order's response.

### Likelihood Explanation
Placing an order is fully permissionless and unprivileged (`placeOrder` has no ACL, no array-length checks). Any user can create an order with hundreds or thousands of token legs at negligible cost (the array elements do not need distinct amounts backed by large capital — only distinct token addresses need be supplied since duplicate check only applies to `output.assets`, not `inputs`). No special privileges, collusion, or precondition beyond calling `placeOrder` and later triggering the cross-chain cancel/refund flow are required, making this directly reachable from a single dispatched request/relayed proof as required by the scan rules.

### Recommendation
- Enforce a hard cap (e.g., `MAX_TOKENS`) on `order.inputs.length` and `order.output.assets.length` in `placeOrder` in `evm/src/apps/IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol`, sized so that `_withdraw`/`_execute`/`withdraw` are guaranteed to complete within a small, predictable, and safely-bounded gas budget.
- In `HandlerV2.handleGetResponses` / `handlePostRequests`, wrap the per-message `host.dispatchIncoming` call in a try/catch (or otherwise isolate per-message execution, e.g., via a low-level call with a gas stipend and receipt tracking) so a single reverting/OOG application callback cannot block delivery of the rest of the batch.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs` containing N (e.g., 2,000) distinct dummy ERC-20 token addresses, each with a minimal nonzero `amount`, and approves/transfers the required tiny amounts for each token, per `evm/src/apps/IntentGatewayV2.sol:194-330` (no length cap enforced).
2. Attacker calls `cancelOrder`, causing a GET request to be dispatched with `context` containing the `WithdrawalRequest{tokens: order.inputs}` (all N tokens) per `evm/tron/contracts/apps/IntentGatewayV2.sol:559-586` (same pattern on EVM `IntentGatewayV2`/`IntentsBase`).
3. When the response is later delivered via `HandlerV2.handleGetResponses`, `host.dispatchIncoming` invokes `onGetResponse` → `withdraw`/`_withdraw`, which loops N times performing an external token transfer + storage write per token (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`). At sufficiently large N this loop exceeds the block gas limit and reverts.
4. Because `handleGetResponses` calls `dispatchIncoming` without try/catch (`evm/src/core/HandlerV2.sol:241-246`), the revert bubbles up and reverts the whole batch, meaning: (a) the attacker's own escrow is permanently unwithdrawable, and (b) any other GET responses a relayer chooses to batch together with this one also fail to deliver.
