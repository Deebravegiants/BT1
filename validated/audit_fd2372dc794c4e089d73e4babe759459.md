Confirmed. The webhook HMAC only authenticates the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` come from unauthenticated headers and are passed straight into the handler as trusted tenant/routing identity.

### Title
Webhook HMAC validation only covers the raw body, letting an attacker replay a signed payload while spoofing the shop and topic - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Registry.process` verifies binds nothing but the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never covered by the HMAC, yet they are forwarded unauthenticated into `WebhookMetadata` and used by the host app to route/attribute the event.

### Finding Description
`Registry.process` validates a webhook solely with: [1](#0-0) 
which calls `Utils::HmacValidator.validate(request)`. That validator recomputes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 
For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [3](#0-2) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read from headers that are entirely outside the signed material: [4](#0-3) 
`Registry.process` then trusts these unauthenticated fields to build the metadata handed to the app's handler: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `HMAC-authenticated bytes == bytes the app attributes to (shop, topic)`. Because the shop/topic/webhook-id headers are not part of the signed string, this equality does not hold — the HMAC only proves "this body was produced with the app's `api_secret_key` at some point," not "this body belongs to this shop or this topic." Since the gem's `client_secret`/`api_secret_key` is shared across every shop that has the app installed (it is not per-shop), any unprivileged internet user who can get one legitimate webhook delivered for their own store (e.g., installing the app on their own dev/test shop and generating any webhook event) obtains a `(raw_body, hmac)` pair that will pass `HmacValidator.validate` unconditionally, regardless of which shop, topic, or webhook id headers accompany it.

### Impact Explanation
An attacker can replay that captured `(raw_body, hmac)` pair to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a victim shop that also has the app installed, and/or setting `X-Shopify-Topic` to a different, more sensitive topic (e.g. spoofing `customers/data_request`/`shop/redact` handling logic, or triggering handlers keyed by shop). `Registry.process` will accept it as authentic for that victim shop because HMAC validation succeeds. Any host application logic that uses `WebhookMetadata#shop` as a tenant key (e.g., looking up/mutating per-shop data) can be made to act on the wrong tenant using attacker-controlled body content, which is a cross-tenant integrity/confusion issue attributable to a gem-level authentication gap rather than host misuse.

### Likelihood Explanation
Getting one authentic webhook delivered to an attacker-controlled endpoint requires only installing the (presumably public) app on a shop the attacker controls and triggering any subscribed event — no privileged credentials, access tokens, or `api_secret_key` knowledge are needed. Forging the HTTP headers on the replayed request is trivial for any internet-reachable caller of the webhook endpoint. This is squarely reachable through the gem's own documented `Registry.process` / `Webhooks::Request` API, not by ignoring documented usage.

### Recommendation
Include the shop domain, topic, and webhook id in the signed material that `HmacValidator` verifies (or otherwise cryptographically bind them, e.g. by validating them against Shopify-issued metadata retrievable via the API), so that the body signature cannot be replayed under different tenant/topic headers. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` alongside the raw body before computing/verifying the HMAC.

### Proof of Concept
1. Install the app (or use `Tylerpinwa/shopify-api-ruby--023`'s test harness) on attacker-owned shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` value `H` — both are valid because `H = HMAC(secret, B)` computed with the app's single, shared `api_secret_key`.
2. POST the same body `B` and header `H` to the app's webhook endpoint, but set:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: customers/data_request` (or any registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this succeeds since `B` and `H` are unmodified.
4. `Registry.process` dispatches the registered handler for the spoofed topic with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "customers/data_request", body: parsed(B), ...)`, causing the host app to process attacker-controlled content as though it were an authentic event from `victim.myshopify.com`.
