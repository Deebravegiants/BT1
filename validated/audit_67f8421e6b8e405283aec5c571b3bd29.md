Confirmed: the main EVM `evm/src/apps/intentsv2/IntentsBase.sol` correctly uses `SafeERC20`'s `safeTransfer`/`safeTransferFrom` throughout (`_withdraw`, `_sweepDust`, `placeOrder` in `evm/src/apps/IntentGatewayV2.sol`). But the Tron port at `evm/tron/contracts/apps/IntentGatewayV2.sol` diverges: its `withdraw()` and the `SweepDust` branch of `onAccept()` use raw low-level `.call()` with `IERC20.transfer.selector` and only check the boolean `success` returned by the low-level call itself — they never decode/verify the ERC20's own returned boolean. This is exactly the unsafe-transfer bug class from the report, reachable by any solver/relayer delivering a `RedeemEscrow`/`RefundEscrow`/`SweepDust` cross-chain message.

### Title
Unchecked ERC20 return value in escrow withdrawal and dust sweep leads to fund loss for non-reverting tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` and the `SweepDust` handling in `onAccept()` of the Tron `IntentGatewayV2` release escrowed intent funds using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level call did not revert, never inspecting the ABI-decoded boolean return value that ERC20 `transfer` is supposed to produce.

### Finding Description
In `withdraw()`, escrow accounting is decremented (`_orders[body.commitment][token] -= amount;`) immediately after the raw call "succeeds," but success here means only that the call did not revert — not that tokens actually moved: [1](#0-0) 

The same unchecked pattern appears in the `SweepDust` branch of `onAccept`: [2](#0-1) 

And for transaction fee redemption: [3](#0-2) 

Many legacy/non-standard ERC20 tokens (e.g. paused-transfer, blacklist-based, or simply non-compliant tokens) return `false` on failure instead of reverting. A low-level `.call()` to such a token, when it returns `false`, still reports `success = true` at the Solidity call level (the call didn't revert), so the `if (!success) revert TransferFailed();` guard does not catch it. The result: the gateway believes the beneficiary was paid and irreversibly decrements/deletes the escrow entry (`_orders[...] -= amount` or `delete _orders[...][TRANSACTION_FEES]`), while the beneficiary never actually receives the tokens.

This directly contrasts with the correct pattern used elsewhere in the codebase (the primary/non-Tron `IntentsBase._withdraw` and `_sweepDust`, and `HyperFungibleToken`/`WrappedHyperFungibleToken`), which consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` that reverts on both call failure and a `false` return: [4](#0-3) [5](#0-4) 

### Impact Explanation
This is a permanent, unbacked freezing/loss of escrowed user or solver funds on the Tron deployment for any token integrated with the IntentGateway that returns `false` rather than reverting on transfer failure (a well-documented class of ERC20 non-compliance). Once `withdraw()` runs, the order is marked `_filled` and escrow is decremented/deleted, so there is no retry path — the beneficiary (user on refund, or solver on fill) permanently loses the escrowed asset while the protocol's internal accounting shows it as already paid out. This matches the "permanent freezing of funds" / "unbacked accounting" impact class for a Medium/High severity finding, since it is triggered on the standard message-delivery path (`onAccept` invoked by the authenticated relayer relaying a `RedeemEscrow`/`RefundEscrow`/`SweepDust` cross-chain message), not by a malicious admin.

### Likelihood Explanation
Likelihood depends on whether any token routed through the Tron IntentGateway is non-reverting on failure (e.g., paused, blacklist-gated, or insufficient-allowance-tolerant tokens returning `false`). Given IntentGateway is a general-purpose, permissionless intents/token-bridging surface designed to support arbitrary ERC20 assets specified by users/solvers in `TokenInfo.token`, and Tron's ecosystem includes several non-standard token implementations, the precondition is realistic rather than theoretical. The bug fires automatically on the normal `RedeemEscrow`/`RefundEscrow`/`SweepDust` delivery path with no additional attacker action required beyond selecting/whitelisting such a token in an order.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` (lines 706, 720) and in the `SweepDust` branch of `onAccept()` (line 674) with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw` and `_sweepDust`. This ensures both call failure and a `false` boolean return revert the transaction, preventing escrow state from being finalized without the tokens actually moving.

### Proof of Concept
1. Deploy (or use an existing) ERC20 token on Tron whose `transfer` function returns `false` on failure instead of reverting (e.g., because the recipient is blacklisted, or the contract is paused) rather than reverting.
2. A user places an intent order via `IntentGatewayV2.placeOrder` escrowing this token as an input (`_orders[commitment][token] = amount`).
3. The order is filled/cancelled, and Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` message via `onAccept`, invoking `withdraw(body, isRefund)`.
4. If the intended beneficiary is in a state that causes the token's `transfer` to return `false` (e.g., blacklisted, or the token is momentarily paused), `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` still returns `success = true` at the Solidity level (only the inner boolean is `false`).
5. `withdraw()` proceeds past the `if (!success) revert TransferFailed();` check, decrements `_orders[body.commitment][token] -= amount`, and marks `_filled[body.commitment] = beneficiary`.
6. The beneficiary never receives the tokens, and the escrow can never be re-claimed since the order is already marked filled/refunded — permanent loss of the escrowed funds.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
