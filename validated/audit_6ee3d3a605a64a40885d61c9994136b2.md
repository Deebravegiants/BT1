## Title
`placeOrder` Never Validates `order.destination` Against Registered Gateway Instances, Permanently Freezing Escrow for Unfillable/Uncancellable Orders - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` (source chain, "Layer 1" in the analogy) escrows the user's input tokens for *any* `order.destination` string the caller supplies, with no check that a corresponding `IntentGateway` instance is registered for that destination via `_instances`. The destination-side validity of the trade — whether a gateway actually exists there to fill it, and whether a `RedeemEscrow`/settlement message can even route back — is only discovered later, deep in the cross-chain settlement path (`_instance()` reverting with `UnknownInstance` in `_post`/`_authenticate`). This mirrors the reported bug class exactly: the entry point that takes user funds performs no upfront rejection of a trade that is provably invalid downstream, and there is no Layer-1 mechanism to reject it before escrow is taken.

### Finding Description
`placeOrder` stamps `order.source`, `order.nonce`, deducts fees, and escrows `order.inputs` unconditionally: [1](#0-0) 

Nowhere in this function — nor in `fillOrder`'s shared pre-checks — is `order.destination` checked against the registered gateway mapping `_instances`: [2](#0-1) 

The only place that resolves `_instances` is `_instance()`, called lazily by `_authenticate` (verifying an *incoming* message's source) and by `_post` (dispatching the settlement message *back* to `order.source` after a fill): [3](#0-2) [4](#0-3) 

`fillOrder` on the destination chain only checks that `currentChain == order.destination` (i.e., that this contract believes itself to be the named destination) and does not consult `order.source`'s registration status at all — `_instance(order.source)` is only invoked deep inside `_fillCrossChain` → `_post` after the solver has already delivered output tokens: [5](#0-4) 

Concretely, two invalid-trade classes escrow user funds with no L1 rejection:
1. **`order.destination` names a chain/state-machine ID with no deployed `IntentGateway`.** No solver can ever call `fillOrder` there (there is no gateway to call), so the order can never be filled. The user's only recovery is `cancelOrder` from the source chain, which requires a Hyperbridge `DispatchGet` proof from a block on that destination chain after the deadline — for a chain with no state-machine/consensus client configured on Hyperbridge (the common case for a genuinely unsupported/typo destination), no such proof can ever be produced, and the destination-side cancel route is equally unreachable since there is no gateway there to call `cancelOrder`. Funds become permanently frozen.
2. **`order.destination` names a real, live gateway chain, but `order.source`'s state-machine ID is not registered in that destination gateway's own `_instances` mapping** (asymmetric/partial governance registration is possible since `_addDeployment` is a per-chain, per-direction governance action: [6](#0-5) ). In this case a solver *can* be lured into calling `fillOrder`, delivering real output tokens to the beneficiary and executing any attached calldata (`_execute`), but the subsequent `_post(order, ...)` call reverts with `UnknownInstance` because `_instance(order.source)` fails — the whole `fillOrder` transaction reverts, but a solver who structured the calldata/predispatch to have already extracted value, or who is simply griefed into wasted gas repeatedly, has no way to know this without an off-chain integrity check, since the source chain accepted the order without validating the round-trip is even possible.

The report's underlying complaint — "the system expects a transfer/order to be valid on the receiving/settlement side, but nothing on the initiating side rejects an order that is provably going to fail there" — maps directly onto `placeOrder` never checking `_instances[keccak256(order.destination)] != address(0)` (and, for full safety, that the reverse registration on the destination for `order.source` exists) before taking custody of user funds.

### Impact Explanation
This causes **permanent freezing of user funds**: any order placed with a destination chain lacking a registered/reachable `IntentGateway` deployment (a fat-fingered chain ID, a chain later deprecated by governance, or a chain that was never onboarded) escrows real tokens that can never be released by a fill, and — for chains without Hyperbridge consensus support — can never be released by cancellation either, since the source-side cancel path depends on producing a storage proof from the destination chain via Hyperbridge's `DispatchGet`/consensus verification. This is a direct, unbacked loss of user funds with no adversarial action required beyond a single malformed `placeOrder` call, which the UI/SDK could easily emit if fed a bad chain identifier since the contract layer performs no defense-in-depth check.

### Likelihood Explanation
Medium-to-High. `order.destination` and `order.source` are raw `bytes`/`string` state-machine identifiers supplied by the SDK/caller with no on-chain whitelist check at the point of escrow (`docs/content/developers/evm/intent-gateway/placing-orders.mdx` confirms these are caller-supplied fields). Any client-side bug, stale configuration, unsynchronized governance registration across the two `IntentGateway` deployments, or a user interacting directly with the contract can trigger this — no attacker collusion or special privileges are needed, and once triggered, it is unrecoverable by any party.

### Recommendation
Add an on-chain check in `placeOrder` (and ideally as a shared internal helper referenced by both `_fillCrossChain`'s dispatch path and `placeOrder`) that reverts with `UnknownInstance` unless `_instances[keccak256(order.destination)] != address(0)` before any tokens are transferred into escrow. This is exactly the "Layer 1 mechanism, like a smart contract, to reject any trade that would be considered invalid" that the external report recommends, applied to `IntentGatewayV2`'s cross-chain order placement instead of `PheasantNetworkBridgeChild`. Where possible, also expose/verify bidirectional registration (source knows destination gateway, destination is expected to know source gateway) so a `fillOrder` cannot succeed in delivering output tokens only to fail irrecoverably in the settlement dispatch back to source.

### Proof of Concept
1. Governance registers `IntentGatewayV2` instances for chains A and B normally, but chain C is either never deployed or later deprecated (its entry in `_instances` on A is never set, or genuinely has no Hyperbridge consensus support).
2. A user on chain A calls `placeOrder` with `order.destination = "C"` and real ERC-20 `inputs`. `placeOrder` performs no destination-registration check and escrows the tokens: [1](#0-0) 
3. No `IntentGateway` contract exists to be called on chain C, so `fillOrder` can never be executed there — the order can never be filled.
4. The user attempts `cancelOrder` from chain A after the deadline, which requires a `DispatchGet` proof of the (nonexistent) `_filled` slot on chain C via Hyperbridge; without a configured/verifiable consensus client for chain C this request can never be proven and delivered, so `_cancelFromSource` never completes.
5. The escrowed tokens remain locked in the `IntentGatewayV2` contract on chain A indefinitely, with no code path to release them — matching the analog's "no mechanism rejects incorrect trades" root cause.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }
    }

    /**
     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }
