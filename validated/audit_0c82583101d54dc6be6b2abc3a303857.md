## Title
Unbounded recursive `RuntimeCall` decoding in the Hyper Fungible Token module allows a remote-chain sender to crash collator block execution via stack overflow — ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The `webonyx/graphql-php` advisory describes a recursive-descent parser with no depth limit that lets an attacker submit a small, deeply nested payload and crash the process via C-stack exhaustion (SIGSEGV), because the recursion is unbounded and uncatchable. The same bug class — unbounded recursive decoding of an attacker-controlled, self-referential structure — exists in Hyperbridge's `pallet-hyper-fungible-token` (HFT) inbound message handler, which decodes a cross-chain-supplied `RuntimeCall` with a plain `Decode::decode` call instead of a depth-limited decode.

### Finding Description
When an HFT transfer message arrives from a remote chain and carries non-empty `message.data`, the module module decodes an embedded `SubstrateCalldata` and then decodes its `runtime_call` bytes into the destination runtime's `RuntimeCall` enum: [1](#0-0) [2](#0-1) 

`T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` uses the plain, mutually-recursive `parity-scale-codec` `Decode` implementation with **no recursion depth limit**, unlike the sibling `call-decompressor` pallet, which explicitly guards the structurally identical case: [3](#0-2) [4](#0-3) 

That pallet uses `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)` specifically because `RuntimeCall` is a self-referential, recursively-decoded type (via `Sudo::sudo{ call: Box<RuntimeCall> }`, `Utility::batch{ calls: Vec<RuntimeCall> }`, `Proxy::proxy{ call: Box<RuntimeCall> }`, etc.) — the codebase's own regression test documents that an attacker who nests such calls ~1000 deep can drive the SCALE decoder's recursive-descent to stack exhaustion: [5](#0-4) 

The HFT module's `Message::data` field, which feeds `substrate_data.runtime_call`, is fully attacker-controlled: it is delivered as the payload of an ISMP `Post` request originating from *any* remote (possibly untrusted/permissionless) source chain that the destination runtime's ISMP router accepts as a valid `IsmpModule::on_accept` call for the HFT app ID. Unlike `call-decompressor::decode_and_execute`, which enforces `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT = 4`, the HFT path performs an unguarded `Decode::decode`, reproducing exactly the vulnerability class the advisory describes: an unbounded, mutually-recursive decoder walking attacker-supplied bytes with no depth counter, bounded only by the native call-stack size, and thus capable of overflowing the stack.

### Impact Explanation
A stack overflow during SCALE decoding is not a catchable `Result::Err` — like the graphql-php case, it manifests as an uncatchable runtime abort (Rust `abort()`/segfault) rather than a graceful decode failure, because Rust's stack-overflow guard-page trap is not something `on_accept`'s `Result<Weight, anyhow::Error>` can intercept. Because ISMP message execution (`handle_unsigned` -> `on_accept`) happens deterministically during **block execution**, every collator/validator executing the block containing the malicious HFT message would independently hit the same overflow at the same nesting depth and crash simultaneously — this is a consensus-critical crash, not a per-request DoS, potentially halting block production on the affected parachain until operators patch and re-sync. This satisfies the "route unable to deliver messages" / unsound-message-handling class the scan targets, reached via an unprivileged token bridger submitting a crafted cross-chain transfer.

### Likelihood Explanation
Exploitation only requires the attacker to control the source-chain side of an ISMP dispatch that the destination treats as a valid HFT message (i.e., be a legitimate but malicious sender on any chain connected via Hyperbridge to a parachain running `pallet-hyper-fungible-token`), and to supply a `Message.data` blob encoding `SubstrateCalldata { runtime_call: <deeply nested RuntimeCall bytes>, .. }`. Given the codebase's own PoC in `pallet_call_decompressor.rs` shows ~1000 levels of `Sudo(Box<..>)` nesting is sufficient to exhaust the stack for that structurally identical decode, the same payload size and technique directly transfers to the HFT decode path. No governance, validator, or admin privilege is required — only the ability to originate a cross-chain HFT transfer with calldata, which is by design a permissionless dispatch surface.

### Recommendation
Replace the unbounded `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` in `modules/pallets/hyper-fungible-token/src/module.rs` with a depth-limited decode, mirroring the fix already applied in `call-decompressor`:
```rust
let runtime_call = T::RuntimeCall::decode_all_with_depth_limit(
    MAX_HFT_CALLDATA_DECODE_DEPTH_LIMIT,
    &mut &*substrate_data.runtime_call,
)
.map_err(HftError::RuntimeCallDecodeError)?;
```
Audit `SubstrateCalldata::decode` itself and any other nested/boxed fields for the same unguarded `Decode::decode` pattern, and add a regression test analogous to `decompress_stack_exhaustion_poc` that submits an HFT message with a deeply nested `RuntimeCall` and asserts a clean decode error rather than a crash.

### Proof of Concept
1. Construct `inner_call = RuntimeCall::System(Call::remark { remark: vec![] })`.
2. Wrap it ~1000 times: `nested = RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(nested) })` (same construction already used in `decompress_stack_exhaustion_poc`, `modules/pallets/testsuite/src/tests/pallet_call_decompressor.rs:320-328`).
3. `encode()` the nested call and place the bytes in `SubstrateCalldata.runtime_call`; SCALE-encode that into `Message.data` of an HFT `PostRequest`.
4. Deliver this as an ISMP `Post` request to the destination parachain's HFT module via `handle_unsigned`/`on_accept`, invoking `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` at `modules/pallets/hyper-fungible-token/src/module.rs:189`.
5. Because this call path is unguarded (no `decode_all_with_depth_limit`), the collator executing the block crashes with a stack overflow instead of returning `HftError::RuntimeCallDecodeError`, unlike the guarded `call-decompressor` path which returns a clean error for the identical payload shape.

#[test]
fn decompress_stack_exhaustion_poc() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		use crate::runtime::RuntimeCall;
		use codec::Encode;

		let inner_call = RuntimeCall::System(frame_system::Call::remark { remark: Vec::new() });

		let mut nested_calls =
			RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(inner_call) });

		for _ in 1..1000 {
			nested_calls =
				RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(nested_calls) });
		}

		let encoded = nested_calls.encode();
		let mut buffer = vec![0u8; 1000000];
		let compressed = zstd_safe::compress(&mut buffer[..], encoded.as_slice(), 3).unwrap();
		let final_compressed_call = buffer[..compressed].to_vec();

		let res = pallet_call_decompressor::Pallet::<Test>::decompress_call(
			RuntimeOrigin::none(),
			final_compressed_call.to_vec(),
			encoded.len() as u32,
		)
		.err()
		.unwrap();

		assert_eq!(
			res,
			DispatchError::Module(ModuleError {
				index: 10,
				error: [3, 0, 0, 0],
				message: Some("ErrorDecodingCall")
			})
		);
	});
}
