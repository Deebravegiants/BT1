### Title
Unvalidated/Unpropagated Native Value in Cross-Chain `lzReceive` Delivery via `HyperbridgeLzEndpoint` - (File: sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol)

### Summary
`HyperbridgeLzEndpoint` acts as a LayerZero V2 endpoint adapter that routes messages through Hyperbridge's ISMP protocol. It never encodes or propagates the native value (`msg.value`/`nativeFee`) paid on the source chain into the cross-chain body, and its two inbound-delivery paths (`onAccept` and `retryPayload`) handle `msg.value` inconsistently and without any validation against what the sender originally paid — mirroring exactly the bug class described in the external report for LayerZero `_lzReceive` handlers.

### Finding Description
When a message is sent via `send()`, the caller may attach `msg.value` (native fee) which is used purely to fund the ISMP relayer fee via a Uniswap swap; it is never encoded into the outbound ISMP body: [1](#0-0) 

On the destination, `onAccept` decodes the body (which contains no native-value field) and delivers the message by calling `lzReceive` on the destination OApp with **no value at all**: [2](#0-1) 

If that initial call reverts, the payload is stored for later recovery. Crucially, the permissionless recovery path `retryPayload` forwards **arbitrary attacker-supplied `msg.value`** to the OApp's `lzReceive`, with no check against any value that was ever encoded in, or associated with, the original message: [3](#0-2) 

This is the same root cause identified in the external report: the receiving side of a cross-chain message executes `lzReceive`/`_lzReceive` without validating that the native value accompanying execution matches what the source-chain sender intended (encoded and committed as part of the message). Here it is worse than the original finding because:
1. The "happy path" (`onAccept`) always delivers with zero value, silently dropping any native value the source sender paid for (`MessagingFee.nativeFee` reported back to the caller in `send()` at line 311 is misleading — that native value funds Hyperbridge relayer/swap fees only, not the destination `lzReceive` call).
2. The retry path lets *any* unprivileged caller attach any `msg.value` amount to a permissionless call to a third party's `lzReceive`, with the destination OApp having no way to authenticate that the value corresponds to a legitimate cross-chain instruction rather than an attacker's own funds injected on retry.

### Impact Explanation
Any OApp built on top of `HyperbridgeLzEndpoint` that trusts `msg.value` inside `lzReceive` (a common OApp pattern for airdrop/gas-drop composability, native refunds, or value-gated logic, and explicitly the pattern LayerZero's own integration checklist warns about) is exposed to:
- Forged/unauthenticated native value being injected during `retryPayload`, since the endpoint contract itself would be the apparent trusted caller (`onlyEndpoint` on the OApp side passes because the call originates from `HyperbridgeLzEndpoint`), yet the actual `msg.value` was supplied by an arbitrary permissionless caller of `retryPayload`, not verified against anything in the message.
- Silent loss/mismatch of intended native value on normal delivery, since `onAccept` always delivers with value `0` regardless of what was paid on the source chain, breaking any downstream logic expecting the value to arrive atomically with the message.

This satisfies "unsound state commitment / unauthorized app action" for downstream OApps relying on the endpoint's value semantics, reachable directly by a single relayed message (`retryPayload` is callable by anyone, permissionlessly).

### Likelihood Explanation
Medium: exploitability depends on whether a given OApp integrated behind `HyperbridgeLzEndpoint` actually branches on `msg.value` in `lzReceive` (as many LayerZero OApps that support gas-drop/native-drop features do). The retry path is permissionless and unauthenticated by design (`retryPayload` has no access control besides the stored-payload-hash check), so exploitation requires no privileged role — any address can trigger it with attacker-chosen `msg.value`.

### Recommendation
Encode the intended native value as part of the ISMP `body` in `send()` (alongside `guid`, `srcEid`, `sender`, `nonce`, `receiver`, `message`), and validate/forward exactly that committed amount when delivering via both `onAccept` and `retryPayload`. If the endpoint cannot itself fund that value trustlessly (since ETH sent on the source chain isn't bridged), it should, at minimum, require `retryPayload` callers to supply exactly the value recorded at dispatch time (funded from a locked/escrowed balance) rather than accepting arbitrary `msg.value`, and document that OApps must not treat `msg.value` in `lzReceive` as authenticated unless this value-commitment mechanism is enforced.

### Proof of Concept
1. Deploy an OApp behind `HyperbridgeLzEndpoint` that performs privileged logic gated on `msg.value` inside `lzReceive` (e.g., only mints/refunds if `msg.value >= X`).
2. A legitimate cross-chain message is sent via `send()` with `msg.value = 0` (fee token payment). `onAccept` calls `lzReceive` and it reverts due to insufficient value, so the payload is stored (`InboundPayloadStored`) per lines 384-396.
3. Any unprivileged third party calls `retryPayload(receiver, origin, guid, message)` and attaches `msg.value = X` ETH of their own choosing (line 431: `lzReceive{value: msg.value}(...)`), satisfying the OApp's value-gated branch and triggering privileged logic that was never authorized/paid for by the original sender — with the attacker's own funds being used to spoof an "on-chain paid" execution path that the OApp believed came pre-validated through the endpoint.

    function retryPayload(
        address receiver,
        Origin calldata origin,
        bytes32 guid,
        bytes calldata message
    ) external payable {
        bytes32 stored = _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];
        if (stored == bytes32(0) || stored == NIL_PAYLOAD_HASH || stored != keccak256(abi.encode(guid, message))) {
            revert InvalidPayloadHash();
        }

        // Clear first; if the retry reverts, this deletion rolls back with the rest of the tx and
        // the payload remains recoverable.
        delete _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];

        ILayerZeroReceiver(receiver).lzReceive{value: msg.value}(origin, guid, message, msg.sender, "");
        emit InboundPayloadResolved(receiver, origin.srcEid, origin.sender, origin.nonce);
    }
