### Title
Webhook `shop`/`topic`/`webhook_id` Header Fields Are Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate`. The `shop`, `topic`, `webhook_id`, and `api_version` values — read straight from HTTP headers — are never included in the HMAC-signed payload, yet they are the values used to route the request and to identify which merchant/tenant the data belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the tenant/routing metadata is parsed from headers independently of the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` only checks the HMAC of the request (i.e., of `@raw_body`) before dispatching to the handler with the unauthenticated `shop`/`topic`/`webhook_id` values: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that the HMAC-signed bytes originated from`. Instead, the gem only verifies `HMAC(raw_body, api_secret_key) == received_hmac`; the `shop-domain`, `topic`, and `webhook-id` headers are bytes that are *parsed* but never *verified*. Because `OpenSSL::HMAC.hexdigest` is computed purely over `@raw_body`, any request with a body+HMAC pair that once validated for one shop/topic combination will validate identically if the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers are swapped to any other value — the check in `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) has no visibility into those headers at all.

An attacker who is able to obtain any single valid `(raw_body, hmac)` pair sent to the app's public webhook endpoint (e.g., from a webhook fired for the attacker's own shop where the app is installed) can replay that exact body/HMAC to the same endpoint while substituting the `x-shopify-shop-domain` header for a victim shop and/or the `x-shopify-topic` header for a different registered topic. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over the untouched body, and `Registry.process` will happily dispatch `WebhookMetadata.new(topic: <attacker-chosen>, shop: <victim-shop>, body: <attacker-controlled>, ...)` to the host application's handler as if it were an authentic message from the victim tenant.

### Impact Explanation
This breaks the tenant identity binding the gem is expected to enforce for webhook authenticity: the `shop` value acted upon by the handler (used by virtually all host apps to scope database writes, session lookups, and business logic per-merchant) is not covered by the cryptographic proof at all. This enables cross-tenant data confusion/injection — an attacker can make the host application believe attacker-supplied webhook content originated from a different merchant's store, and can also relabel the topic to trigger a different, more sensitive handler (e.g., `customers/redact`, `shop/redact`) using a body/HMAC obtained under an entirely different topic. This matches the "Critical - cross-tenant access" impact category, since the gem's own authentication primitive (`HmacValidator`) is the only defense host apps are told to rely on for webhook trust, and it does not bind the routing/tenant fields to the signature.

### Likelihood Explanation
Exploitability requires only the ability to (a) obtain one legitimately-signed webhook body+HMAC pair — trivially available to any developer/attacker who installs the app on their own development store and receives real webhooks — and (b) send a crafted HTTP POST directly to the app's public webhook endpoint with modified headers, which is possible for any unprivileged internet user since the endpoint is by design internet-facing and does not require any prior secret. No access token, `api_secret_key`, or privileged access is needed.

### Recommendation
Include the routing/tenant identifiers (`shop`, `topic`, and ideally `webhook_id`) as part of the signed content verified by `HmacValidator`, or otherwise cryptographically bind them (e.g., derive/validate the shop domain from a separate trusted channel, such as looking up the webhook subscription by `webhook_id` against Shopify's API and confirming the shop before trusting the header). At minimum, `Webhooks::Request#to_signable_string` should not omit the header fields that downstream handlers use to determine tenant and topic.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify sent.
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (swapped)
   - `x-shopify-topic: orders/create` (unchanged or swapped to any registered topic)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers without any check that they match the shop that actually signed `B`: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B, api_secret_key)` and compares it to `H` — this succeeds since `B` and `H` are untouched: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the host application to process attacker-controlled data attributed to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
