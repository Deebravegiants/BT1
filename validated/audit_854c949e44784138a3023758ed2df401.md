### Title
Shared-identity arbitrary call in `EmporiumUpgradeable.runAction` CASE 2 lets any user drain another user's unconsumed router/Permit2-style allowance because the stolen token can be omitted from the attacker's own `erc20TokenAddresses` array - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes `op.endpoint.call(op.callData)` directly from `msg.sender == Emporium`, a singleton contract shared by every Hinkal user, so any approval/allowance a prior user's op grants to a router (Permit2-style `permit`/`approve`) is recorded under Emporium's address and remains usable by anyone who can route another call through Emporium. The balance-safety checks that should catch such leakage — `EmporiumUpgradeable.runAction`'s `balancesBefore/After` loop and `Hinkal.transact`'s `oldBalances/newBalances` loop — only iterate over `circomData.erc20TokenAddresses`, an array whose *contents* are never validated by `dimensionsCheck`/`performHinkalChecks` (only its *length* is checked against `dimensions.tokenNumber`), so an attacker can simply omit the token being stolen from their own array and the drain goes completely unchecked.

### Finding Description
The claimed broken equality is **AUTHORITY**: `authorised_signer == actual_beneficiary` must hold for every value that leaves Emporium's custody. It is violated because:

1. In CASE 2, the call is made with `msg.sender == Emporium` regardless of which user initiated it: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:102-113`. Any allowance/permit granted to a router during this call is keyed to Emporium's address, not to the depositing user.
2. Victim tx: a CASE-2 op grants a router an allowance (via `approve`, or a Permit2-style `permit`/`permitTransferFrom`-granting call) with `owner == Emporium`, then only partially consumes it in the same op (e.g. slippage-limited swap). The residual allowance persists in the router/Permit2 contract's storage, untouched by Hinkal.
3. Attacker tx: `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction`, again CASE 2, with `op.endpoint = router` and `op.callData` calling the router's transfer-consuming function to pull the residual amount from Emporium to the attacker's own address.
4. The only guard against unauthorized state changes is the balance delta check at `EmporiumUpgradeable.sol:122-151` (`balanceChange < 0` reverts) and the mirrored check in `Hinkal.sol:78-146`. Both loops iterate strictly over `circomData.erc20TokenAddresses`, an array supplied by the *attacker* for *their own* transaction.
5. `HinkalHelper.dimensionsCheck` (`contracts/HinkalHelper.sol:64-171`) only requires `circomData.erc20TokenAddresses.length == dimensions.tokenNumber` — it never constrains *which* tokens appear in the array, and the zk proof only binds amounts/nullifiers/commitments for the tokens the attacker chooses to declare. If the attacker simply excludes the stolen token from `erc20TokenAddresses`, neither `balancesBefore/After` (Emporium) nor `oldBalances/newBalances` (Hinkal) ever sample that token's balance, so the theft is invisible to every existing safety require — `handleOut`, the slippage require, and the `balanceDif == amountChanges + utxoAmount` equation are all simply never evaluated for that token.

The proof/circuit for the attacker's transaction constrains only the fields it is given; it places zero constraint on a token that is not listed, so this is exactly "a field acted on that the proof never constrained."

### Impact Explanation
Direct theft of another user's (or the protocol's residual) ERC20 balance/allowance held by the shared `Emporium` contract, paid out to an attacker's own address as raw ERC20 (bypassing the shielded UTXO accounting entirely). This matches **Critical**: direct theft of in-flight/shielded user funds via a call the wallet owner never authorised, with no proof or balance constraint catching it. The attack is repeatable against any dangling allowance left by any past CASE-2 operation (from any user, or even the protocol's own swap integrations), and costs the attacker only the gas for a normal `transact()` call plus a valid proof for their own (unrelated) UTXOs/deposit.

### Likelihood Explanation
Preconditions: (a) some prior CASE-2 op left a non-zero, non-invalidated allowance/permit with `owner == Emporium` on an external router/Permit2-style contract (a very common pattern for swap/DEX routers, and not prevented anywhere in this codebase's CASE-2 path, which allows arbitrary `op.endpoint.call(op.callData)`); (b) the attacker knows the router address and remaining amount (both are either public on-chain state or inferable from the victim's transaction). No privileged role is needed — the attacker only needs to construct their own valid `CircomData`/proof for an unrelated deposit/UTXO and simply choose not to list the target token in `erc20TokenAddresses`. This is fully within the attacker capabilities defined by the rules (craft every CircomData field, choose endpoints/callData).

### Recommendation
- Do not allow CASE 2 to execute calls that create durable state (approvals/permits) attributable to Emporium's own address; either force such approval-granting calls through CASE 1 (per-user `HinkalWallet`, which isolates state per signer) or require any allowance be reset to zero within the same op.
- Independently, close the "omitted token" bypass: derive the token list Emporium/Hinkal must balance-check from something the circuit/proof actually constrains (e.g., include a commitment to the full token set touched by `op.callData`/`op.endpoint`, or require `erc20TokenAddresses` to cover every token whose balance could plausibly change during the external call), rather than trusting an attacker-chosen array whose contents are unconstrained.
- Alternatively, revoke/zero any outstanding approvals Emporium made to external spenders at the end of every `runAction` call (sweep pattern), so no allowance survives across transactions.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a mock ERC20 `Token`, and a mock router `MockRouter` that exposes `grantAllowance(address spender, uint256 amount)` (simulating a Permit2-style `permit`) and `pull(address from, address to, uint256 amount)` gated by that allowance (simulating `permitTransferFrom`/`transferFrom`).
2. Victim flow: craft a valid proof/CircomData for a CASE-2 op stack with `op.endpoint = router`, `op.callData` = `grantAllowance(router_spender, N)` followed by a second op that calls `pull(Emporium, someDest, X)` with `X < N` (partial consumption), executed via `Hinkal.transact`. Assert after this tx: `Token.allowance(Emporium, router) == N - X > 0` (side effect 1) and `Token.balanceOf(Emporium) == N - X` residual (side effect 2).
3. Attacker flow: craft a second, independent valid proof/CircomData (attacker's own deposit/UTXO, unrelated to the token above) whose `circomData.erc20TokenAddresses` **excludes** `Token`. In its `EmporiumStack`, add a CASE-2 op with `op.endpoint = router`, `op.callData = pull(Emporium, attacker, N - X)`.
4. Call `Hinkal.transact` with the attacker's proof. Assert:
   - Before: `Token.balanceOf(Emporium) == N - X`, `Token.balanceOf(attacker) == 0`.
   - After: `Token.balanceOf(Emporium) == 0`, `Token.balanceOf(attacker) == N - X`.
   - The transaction does **not** revert with `BalanceChangeShouldBePositive` (proving the omitted-token bypass), and no `slippage param is violated` / `Balance Diff Should be equal...` require in `Hinkal.sol` fires (since `Token` isn't in `erc20TokenAddresses`).
   - This demonstrates `authorised_signer (attacker's own proof) != actual_beneficiary (attacker receiving victim-backed Emporium funds)` while all on-chain requires pass.
