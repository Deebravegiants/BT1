### Title
Emporium Min-proof path lets any prover run unauthenticated `EmporiumStack` ops that sweep arbitrary tokens/ETH held by the Emporium contract - (File: contracts/CircomDataBuilder.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin.circom`) only proves `message == Poseidon(messageSeed)` for an attacker-chosen `messageSeed` - it never binds the proof to any UTXO, nullifier, or spending key. Combined with `EmporiumUpgradeable.verifyWallet` skipping ECDSA verification entirely when `stack.signerAddress == address(0)`, and `runAction`'s balance accounting loop iterating zero times over the empty `erc20TokenAddresses` array, an unprivileged attacker can submit an `EmporiumStack` whose `ops` execute arbitrary calls as the Emporium contract, with zero economic accounting.

### Finding Description
The broken equality is: *"assets Emporium can move in a tx == assets accounted for in `balancesBefore`/`balancesAfter`"* (`EmporiumUpgradeable.sol` lines 85-151). This holds only for tokens listed in `circomData.erc20TokenAddresses`; when that array is empty, both `balancesBefore` and `balancesAfter` are empty arrays, and the reconciliation loop `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` never executes [1](#0-0) [2](#0-1) .

Path to reach this state:
1. `formInputForCircom` selects the minimal input builder whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [3](#0-2) .
2. `formInputEmporiumMin` emits only `[emporiumMessage, timeStamp, calldataHash]` as public signals - critically it omits `getSignedMessageHash` (used in the normal path to cryptographically bind `externalActionData`, i.e. the `EmporiumStack`, to a UTXO owner's private key) and omits `rootHashHinkal`, `inputNullifiers`, `amountChanges` [4](#0-3) .
3. `MainEVMCircuitMin.circom` proves nothing except `message <== Poseidon(1)([messageSeed])`, where `messageSeed` is a private input the prover picks freely, with no linkage to any spending authority [5](#0-4) . Any attacker can trivially generate a valid proof for a min-dimension verifier.
4. `Hinkal.transact` still checks `rootHashExists(circomData.rootHashHinkal, ...)`, but since `rootHashHinkal` is not part of the verified public input for the min path, this check is decoupled from the proof and satisfiable with any historical root [6](#0-5) .
5. `_externalTransact` computes `deltaAmountChanges = new int256[](0)` and calls `EmporiumUpgradeable.runAction` [7](#0-6) .
6. In `runAction`, `verifyWallet` is called with the attacker-supplied `EmporiumStack`. If `stack.signerAddress == address(0)`, the function marks `emporiumMessage` used and returns immediately, performing **no ECDSA signature check whatsoever** on the `ops` array [8](#0-7) .
7. The `ops` loop then executes attacker-controlled `endpoint.call{value: op.value}(op.callData)` for each stack entry (as long as the selector isn't `callHinkalWallet`/`doSendToRelay`) - this executes as `msg.sender == Emporium` [9](#0-8) .
8. Because `erc20TokenAddresses` is empty, the before/after balance snapshot, the `BalanceChangeShouldBePositive` check, and `handleOut` distribution never execute for whatever asset the `ops` actually move - the theft is completely unaccounted for.

Root cause: the "Min" proof path was designed for cases with no shielded-pool token movement, but it is reachable with an arbitrary, attacker-crafted `EmporiumStack` whose `ops` are authorized purely by an ECDSA signature check that is *skippable* by setting `signerAddress == 0`, with no fallback authorization (e.g., proof-bound authorization) for that branch. This differs from the normal path, where `getSignedMessageHash` (embedding `externalActionData`) is a public/private signal actually verified by the full circuit, providing an alternate authorization route not available in the min path.

### Impact Explanation
Any funds resident at the Emporium contract's address - native ETH or ERC20 tokens left over from prior legitimate multi-step operations (dust, un-swept swap outputs/rewards in tokens not declared in a prior transaction's `erc20TokenAddresses`, or fees) - can be swept by an unprivileged attacker via arbitrary calls (e.g., `token.transfer(attacker, balance)`) executed with Emporium's identity, with zero signature check and zero balance accounting. This is theft of protocol/in-flight funds parked at Emporium and is repeatable each time new residual balance accrues at the contract, matching the "theft of protocol/relay fees" / "temporary or permanent freezing"/"theft of in-flight user funds" impact categories, up to Critical severity depending on how much value transiently sits at Emporium between operational steps.

### Likelihood Explanation
Preconditions: (a) a verifier registered for the min-dimension/Emporium `verifierId` combination (implied by the existence of `MainEVMCircuitMin.circom` and the dedicated code path, i.e., this is a supported production flow, not dead code); (b) some non-trivial balance temporarily or permanently resident at the Emporium contract address, which is plausible given multi-step swap/DeFi interactions routed through `ops`. Attacker cost is minimal (self-generated trivial proof, no deposit required, no signature needed). The attack is fully self-contained and repeatable whenever Emporium holds a sweep-able balance.

### Recommendation
Require `stack.signerAddress != address(0)` (i.e., always enforce EIP-712 signature verification for `EmporiumStack.ops`) regardless of `erc20TokenAddresses.length`, or, for the truly no-signer case, cryptographically bind the `ops` array to the proof itself (include a hash of `stack.ops`/`externalActionMetadata` in `formInputEmporiumMin`'s public signals, verified against a private input the circuit constrains to a legitimate spending key or an explicit "no-op" allowance). Additionally, the min-path should not allow arbitrary `endpoint.call` unless there is an equivalent authorization guarantee to the normal path's `getSignedMessageHash` binding.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `VerifierFacade` with a registered verifier for the Emporium-min `verifierId` (`buildVerifierId(Dimensions{0,0,0}, HINKAL_EMPORIUM_ACTION_ID)`), and deploy `EmporiumUpgradeable` as an allowed recipient.
2. Fund the Emporium contract directly (simulating residual balance) with an ERC20 token, e.g., `token.transfer(emporium, 1000e18)`.
3. As an unprivileged EOA, construct `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{v:0,r:0,s:0,signerAddress:address(0), ops:[EmporiumOperation{endpoint: address(token), invokeWallet:false, value:0, callData: abi.encodeCall(token.transfer,(attacker,1000e18))}], maxFee:0, deadline:0})`.
4. Generate a trivial proof for `MainEVMCircuitMin` with self-chosen `messageSeed`, compute `message = Poseidon(messageSeed)`, set `calldataHash = getHashedCalldata(circomData)`, use any existing `rootHashHinkal`/index.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert: `token.balanceOf(attacker)` increases by `1000e18` and `token.balanceOf(emporium)` decreases by `1000e18`, while `balancesBefore`/`balancesAfter` inside `runAction` (both empty arrays) never reflect or gate this movement - i.e., the equality "assets moved == assets accounted for" is violated (LHS = 1000e18, RHS = 0).
