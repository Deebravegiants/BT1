Webhook `shop` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an inbound webhook using an HMAC that is computed only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` to route and attribute the webhook come from unauthenticated HTTP headers that are never part of the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers via `shopify_header`, with no cryptographic binding to the body they accompany: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks that the HMAC over `to_signable_string` (i.e. the raw body) matches, using `Context.api_secret_key`: [4](#0-3) 

`Registry.process` trusts `request.shop` (and `request.topic`) as the tenant/topic identity for dispatching to the handler, immediately after the HMAC check passes: [5](#0-4) 

This breaks the identity binding: **shop authenticated (via signature) ≠ shop stored/used as the tenant key**. The HMAC only proves "the app's secret key was used to sign this exact byte string (the body)"; it proves nothing about which shop or topic that body is attributed to. Since a single app's `client_secret` is shared across every shop that installs the app, any merchant who has legitimately installed the app (an unprivileged, non-admin actor with respect to other tenants) will receive genuine webhooks with a valid HMAC computed over their own shop's body. Because the signature never binds `shop`/`topic`/`webhook_id` to the body, that same valid `(body, hmac)` pair can be resubmitted to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header changed to a different, victim tenant. `HmacValidator.validate` will still pass (it only checks the body/hmac pair), and `Registry.process` will hand the attacker-supplied `shop` value straight to the app's webhook handler as if it were authentic, causing the host application to store or act on data under the wrong tenant.

### Impact Explanation
This is a cross-tenant data integrity/attribution breach: an attacker who is a legitimate merchant on Shop A can cause the app to process and store data as if it originated from Shop B, without ever needing Shop B's credentials or `client_secret`. This matches the "cross-tenant access" Critical impact category, since the identity boundary between tenants relies entirely on an unauthenticated header rather than anything covered by the cryptographic signature.

### Likelihood Explanation
Reaching this path requires no privileged credentials — only that the attacker be a valid installer of the app on at least one shop (which grants them a genuine, validly-signed webhook payload) and the ability to POST directly to the app's public webhook endpoint with a modified `shop-domain`/`topic` header, which is entirely under an external caller's control since these are plain HTTP headers, not signed parameters.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable content that is verified by the HMAC (or otherwise cryptographically bind them to the body before dispatch), so that any modification to these header-derived identity fields invalidates the signature. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for tenant/topic attribution unless the gem's signature verification is extended to cover them.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body `B`.
2. The attacker (the operator of shop-a, an unprivileged party with respect to shop-b) captures this exact HTTP request (headers + raw body `B` + its valid HMAC).
3. The attacker replays the identical request to the app's public webhook endpoint, but rewrites `X-Shopify-Shop-Domain` to `shop-b.myshopify.com` (leaving body `B` and the HMAC header untouched).
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` (unchanged) and it matches, so validation succeeds: [6](#0-5) 
5. `Registry.process` proceeds to call the handler with `shop: request.shop` set to `"shop-b.myshopify.com"`, causing the app to process/store the order data `B` (really belonging to shop-a) under shop-b's tenant record: [7](#0-6)
