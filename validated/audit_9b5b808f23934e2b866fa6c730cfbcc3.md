### Title
Orb-local signup success is treated as authoritative and diverges from backend-verified enrollment state in user-centric signups - ([File: src/plans/mod.rs])

### Summary
In the `user_centric_signup` code path, `MasterPlan::do_signup` derives the final enrollment outcome purely from a locally-computed `SignupReason` (pipeline success + local fraud check) and never calls the backend enrollment/verification flow (`signup_post`/`signup_poll`) that is used for the normal (non-user-centric) path. This is structurally the same accounting-desync bug class as the RocketPool `nETH` report: one code path computes "success/credited" state from a locally observed value, while the authoritative, independently-verified value (backend confirmation) is computed on a separate path and is not enforced to match it.

### Finding Description
`MasterPlan::do_signup` computes `signup_reason` purely from local orb-side signals: [1](#0-0) 

For `user_centric_signup == true` (and `ignore_user_centric_signups == false`, the default), this locally-derived `signup_reason` is written directly into `debug_report.enrollment_status` and used as `result.success`, with the backend-verifying `enroll_user()` call (which POSTs the signup and polls the backend for a `Completed`/`success` verdict) **skipped entirely**: [2](#0-1) 

The only backend confirmation for the non-user-centric branch happens through `enroll_user::Plan::run`, which posts to `/api/v2/signups/{id}` and polls `signup_poll` until the backend reports `Completed`/`success` (covering backend-side duplicate detection, legacy-signup checks, in-flight matches, and backend fraud detection): [3](#0-2) 

In the FOSS build, the local `detect_fraud` step that feeds `signup_reason` is a no-op — `N_FRAUD_CHECKS` is hard-coded to `0` and `detect_fraud` always returns `Ok(false)`: [4](#0-3) [5](#0-4) 

So for any `user_centric_signup` flow, `signup_reason` reduces to `Normal` as long as the local biometric pipeline produces output (`pipeline.is_some()`), regardless of whether the backend would consider this signup valid, non-duplicate, or non-fraudulent. `user_centric_signup` itself is sourced from `authenticated_app_data` returned by the backend's user-status endpoint and is nominally hash-verified against `qr_code.user_data_hash`: [6](#0-5) [7](#0-6) 

This mirrors the nETH bug class precisely: the "amount minted" (here, the Orb's locally recorded `enrollment_status`/`result.success` and everything gated on it, e.g., PCP upload continuation and UI success signaling) is computed from one code path (local pipeline/fraud outcome), while the "collateral" (backend's authoritative record of whether the signup was actually accepted, deduplicated, and passed server-side fraud checks) is computed on a separate, independent path that is bypassed for this signup type. Nothing enforces that these two values match.

### Impact Explanation
Because the backend enrollment/verification call is skipped for `user_centric_signup` sessions, the Orb can locally report/upload a signup as `Success`/`Normal` while the backend never confirms, deduplicates, or fraud-checks that specific signup. With fraud checks stripped to no-ops in this build, essentially any biometric capture that yields pipeline output is locally treated as a successful, legitimate, unique enrollment. This creates a state-bleed between the Orb's local bookkeeping and the backend's ground truth — enabling misattributed or duplicate signup completion states to be recorded and surfaced (UI success signal, PCP upload continuation, `signup_finished(success=true)` DBus signal) without backend-side confirmation that the enrollment is unique/valid, analogous to the nETH desync between minted supply and actual collateral.

### Likelihood Explanation
The trigger requires only a legitimate signup session where the backend/app sets `user_centric_signup = true` (a supported, documented product mode, not a privileged operator action) and default configuration (`ignore_user_centric_signups = false`, which is the shipped default per `Config::default`): [8](#0-7) 

No hardware bypass, malicious peer, or admin access is required — a normal user going through a standard self-serve/app-driven signup flow exercises this code path. The main uncertainty is whether the production backend independently re-validates/enforces the enrollment server-side out-of-band of this specific call chain (not visible in this repository, which only contains the Orb-side code) — this cannot be fully verified from `orb-core` alone.

### Recommendation
- Do not let the Orb's local `signup_reason` (pipeline/fraud outcome) alone determine final enrollment success for `user_centric_signup` flows; always cross-check with an authoritative backend confirmation before marking `enrollment_status`/`result.success`, the same way the non-user-centric path calls `enroll_user`/`signup_post`/`signup_poll`.
- If a lighter-weight backend confirmation is desired for user-centric signups, ensure it still performs backend-side duplicate/fraud verification, and that the Orb's recorded success is contingent on it, not solely on local computation.
- Given fraud checks are fully stripped in this build (`N_FRAUD_CHECKS = 0`), any code path relying on `detect_fraud`'s result as if it were meaningful should be re-audited to confirm it doesn't silently grant "always non-fraudulent" outcomes.

### Proof of Concept
1. Backend authorizes a session with `authenticated_app_data.user_centric_signup = true` (a supported app-driven signup flow) and a valid `user_data_hash`.
2. User completes biometric capture; `biometric_pipeline` returns `Some(pipeline)`.
3. `detect_fraud` unconditionally returns `Ok(false)` (see `src/plans/mod.rs:1392-1406`), so `signup_reason = SignupReason::Normal`.
4. In `do_signup` (`src/plans/mod.rs:639-656`), because `user_centric_signup && !ignore_user_centric_signups`, `enrollment_status` is set to `enroll_user::Status::Success` directly from `signup_reason`, and `enroll_user()`/`signup_post`/`signup_poll` (the only backend-verifying call) is never invoked.
5. `result.success = true` is reported, `signup_finished(success=true)` is emitted, and PCP tiers are uploaded — all without any backend confirmation that this specific signup was accepted, unique, or fraud-free.
