### Title
Webhook shop identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` is read from the unauthenticated `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` only checks that the body bytes match the app-wide `Context.api_secret_key`-derived HMAC; it never verifies that the `shop` value is the one the signature was actually generated for. `Registry.process` then passes this unauthenticated `request.shop` straight into `WebhookMetadata` and the app's handler.

### Finding Description
Compare the two sides of the binding that should hold: "shop the HMAC was computed for" == "shop the handler trusts and acts on."

- The HMAC secret (`Context.api_secret_key`) is the same for every shop installed on the app — it is not shop-specific. [6](#0-5) 
- `Request#to_signable_string` signs only `@raw_body`; the `shop` field returned by `Request#shop` is taken from a header that is never part of the signed content. [7](#0-6) 
- `Registry.process` validates the HMAC of the body, then unconditionally forwards `request.shop` to the handler as the tenant identity for the event. [4](#0-3) 

Because the same app secret signs every merchant's webhooks and the shop header sits outside the signature, an unprivileged internet user who controls (or has installed the app on) their own shop can capture a legitimate, validly-signed webhook body that Shopify sent them, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and the handler executes believing the event originates from the victim shop. This breaks the identity binding "shop authenticated" == "shop the handler stores/acts on," letting an attacker inject fabricated events attributed to an arbitrary tenant.

### Impact Explanation
This crosses the Critical bar for "cross-tenant access": an attacker with no relationship to the victim shop can make the app process webhook data as if it came from that victim shop, purely by forging an unauthenticated header, since the HMAC never binds shop identity to the payload.

### Likelihood Explanation
Medium-to-High: obtaining one genuine, validly-signed webhook body requires only installing the app on any (even the attacker's own) shop — a normal, unprivileged action. No secrets, tokens, or credentials of the victim are needed; only the header needs to be forged in the replayed HTTP request, which any caller of the app's public webhook endpoint controls.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload before `Registry.process` trusts `request.shop`. At minimum, cross-check `request.shop` against a known/registered shop list independent of the header, and treat body-HMAC validity and shop-domain trust as separate, both-required checks rather than conflating them.

### Proof of Concept
1. Install/operate the app for `attacker.myshopify.com`; capture a legitimate webhook Shopify sends for that shop, including its raw body and valid `Shopify-Hmac-Sha256` header.
2. Replay the exact same HTTP request to the app's webhook endpoint, changing only `Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `hmac_validator.rb` returns `true` because it only compares the HMAC of `@raw_body`, which is unchanged. [6](#0-5) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is now `victim.myshopify.com`, even though Shopify never signed anything asserting that shop. [8](#0-7)
