Based on the investigation, there is a legitimate identity-binding break in the webhook processing path.### Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate an inbound webhook using an HMAC that covers only the raw request body, then hand the caller-supplied `shop-domain` header — unauthenticated — to the app as the tenant identity for the webhook.

### Finding Description
`Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` passes: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value supplied by the caller: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the Shopify-supplied headers are part of the signed material: [3](#0-2) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from attacker-controllable HTTP headers with no cryptographic binding to the signature: [4](#0-3) 

After the body-only HMAC check succeeds, `Registry.process` builds `WebhookMetadata` using this unverified `request.shop` and forwards it directly to the app-provided handler as the tenant identity for the event: [1](#0-0) [5](#0-4) 

The identity binding that should hold is:
`shop header value used by the handler == shop that Shopify actually signed the payload for`

Because `HMAC(body)` is computed with the app-level `Context.api_secret_key`, which is the same secret for every shop that has installed the app, and the signature covers *only* the body, this equality does not actually hold: any body+HMAC pair that is valid for tenant A's installation remains a valid HMAC pair regardless of which `shop-domain` header accompanies it. An attacker who can install the app on their own (attacker-controlled) store, or who otherwise obtains one genuine `(raw_body, hmac)` pair for that installation, can resend that exact body and signature to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `Utils::HmacValidator.validate` still succeeds because the header is not part of `to_signable_string`, and `Registry.process` dispatches the event to the handler labeled with the attacker-chosen `shop`.

This directly matches the documented rule category: "a field acted on but not covered by the HMAC." The `docs/usage/webhooks.md` guidance states that `Registry.process` "will verify the request did indeed come from Shopify," but the verification only proves the body's authenticity for *some* installation of the app, not that the accompanying tenant claim is genuine: [6](#0-5) 

### Impact Explanation
This breaks the tenant boundary the gem is relied upon to enforce for webhook dispatch. A handler that uses `WebhookMetadata#shop` to select which merchant's session/access token/data to update, or that treats webhook receipt as evidence of authenticity for a specific store, can be tricked into applying attacker-supplied body content under another shop's identity (e.g., forcing state changes, faking `app/uninstalled` or order/customer events, or corrupting per-tenant caches keyed by `shop`) — a cross-tenant confused-deputy condition, which falls under the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on any shop they control (a routine, unprivileged action for any Shopify merchant/developer) in order to obtain one genuine `(body, hmac)` pair signed with the app's shared secret, then replay it with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — this is reachable by any unprivileged internet/Shopify user who can create a store and trigger one webhook.

### Recommendation
Bind the tenant identity into the authenticated material before trusting it:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed string (if Shopify's webhook signature scheme is extended to support it), or
- Independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation known to the app before dispatching to the handler, rather than trusting the header value as-is, and
- Update `docs/usage/webhooks.md` to clarify that `process` only authenticates the payload body, not the `shop-domain`/`topic`/`webhook_id` headers, so host applications know they must independently validate tenant identity.

### Proof of Concept
1. Attacker creates a development/trial store `attacker.myshopify.com` and installs the target app, registering a webhook (e.g. `orders/create`).
2. Shopify sends a webhook to the app's endpoint: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, header `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `B` and the valid HMAC value.
4. Attacker (or a script) sends a forged request to the same app endpoint with the identical body `B` and HMAC, but sets `shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `HMAC(secret, B)`, per `Webhooks::Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` (line 36-38), which excludes all headers.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-199) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the app's handler, which now processes attacker-controlled data under the victim's tenant identity.
