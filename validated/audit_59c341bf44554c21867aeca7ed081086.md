### Title
Webhook shop/topic identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, and `webhook_id` values used by the handler dispatch and passed to app code come from unauthenticated HTTP headers. This breaks the identity binding `hmac_signed_bytes == bytes_that_determine_the_shop/topic`, allowing a party who possesses one valid `(body, hmac)` pair for the app's shared `api_secret_key` to relabel that payload as belonging to any other shop or topic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is computed purely from the `hmac-sha256` header value: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac` using the app's `api_secret_key`: [3](#0-2) 

But `shop`, `topic`, and `webhook_id` are read straight from headers, entirely outside the signed material: [4](#0-3) 

`Registry.process` only checks the HMAC of the body, then dispatches using the unauthenticated `request.topic` and `request.shop` values: [5](#0-4) 

These values are placed directly into `WebhookMetadata`, the struct the host app's `WebhookHandler#handle` implementation is expected to trust for tenant attribution: [6](#0-5) 

The binding that should hold is:
`HMAC(api_secret_key, signed_bytes) == received_hmac` **and** `signed_bytes` includes `shop ‖ topic ‖ webhook_id`.

What actually holds is only:
`HMAC(api_secret_key, raw_body) == received_hmac`, with `shop`, `topic`, `webhook_id` supplied unsigned.

Because Shopify's app `api_secret_key` is a single value shared across *all* shops that have installed the app (it is not per-tenant), any party that can obtain one legitimate `(raw_body, hmac)` pair for the app — e.g. a merchant who has installed the app on their own store and receives/observes the webhook Shopify sends to the app's endpoint for their own shop, or replays a webhook the app already accepted — can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers for a different, victim shop. The gem's `HmacValidator.validate` will still return `true`, because the header values it never inspects are not part of `to_signable_string`.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates the *bytes* (body) but the host application, following this gem's documented API (`WebhookMetadata#shop`, `#topic`), is led to believe `shop`/`topic` are equally authenticated. Any host app that uses `data.shop` from `WebhookMetadata` to select which merchant's session/record to update (a standard integration pattern) can be tricked into applying data intended for one shop to a different shop, or into invoking handlers for a topic that was never actually sent for that data — a cross-tenant access primitive that fits the Critical impact bucket (cross-tenant access) defined in scope.

### Likelihood Explanation
Exploitation requires only:
1. Access to one valid webhook body+HMAC pair generated using the app's shared `api_secret_key` — trivially obtainable by any merchant who has installed the app on their own (attacker-controlled) shop, since Shopify delivers real webhooks with valid HMACs to the app for every installed shop.
2. The ability to send an HTTP request to the app's public webhook endpoint with forged `x-shopify-shop-domain`/`x-shopify-topic` headers and the captured body — no secret knowledge or privileged access is required for this step.

No `api_secret_key`, access token, or social engineering is needed; the only prerequisite is being an ordinary merchant/installer of the target app, which is squarely an "unprivileged internet user" relative to other tenants of the same app.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed material, or otherwise cryptographically bind them to the body before verification — e.g. compute the signable string as a canonical concatenation of `raw_body`, `shop`, and `topic` rather than `raw_body` alone in `Request#to_signable_string`. Until the signed payload covers these fields, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and that host applications must independently verify the shop against their own session store before trusting webhook content for tenant-scoped operations.

### Proof of Concept
1. App `A` is installed on shops `victim.myshopify.com` and `attacker.myshopify.com`, both sharing the same `api_secret_key`.
2. Shopify sends a legitimate webhook to `A`'s endpoint for `attacker.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over BODY using api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   BODY: {"id": 123, ...}
   ```
   The attacker (owner of that shop) observes/logs this raw body and HMAC.
3. The attacker resends the identical body and HMAC to `A`'s webhook endpoint, only changing the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same HMAC, unchanged>
   x-shopify-shop-domain: victim.myshopify.com
   BODY: {"id": 123, ...}
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `HmacValidator.validate` calls `verifiable_query.to_signable_string` (the body only) and successfully matches the HMAC, per [2](#0-1)  and [7](#0-6) .
5. `Registry.process` accepts the request and dispatches `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` to the app's handler, per [5](#0-4) , even though Shopify never sent this webhook for `victim.myshopify.com`.

          received_signature = verifiable_query.hmac
