### Title
`describeWithdrawal` matches withdrawal status by `assetId` only, causing status/tx-hash misattribution between concurrent same-asset withdrawals in one batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain withdrawal status for a specific `WithdrawalIdentifier` by fetching all withdrawals associated with the originating NEAR tx hash and then picking the first one whose token matches the requested `assetId`, ignoring withdrawal index, destination address, or amount. When a single NEAR intent transaction contains multiple withdrawals of the same token (e.g. a batch withdrawal to two different destination addresses), every one of those withdrawals resolves to the *same* matched record, so distinct withdrawal requests can be reported with another withdrawal's `txHash`/status.

### Finding Description
`getWithdrawalStatusWithRetry` queries the bridge by `args.tx.hash` only [1](#0-0) , returning the full list of withdrawals tied to that NEAR transaction. `describeWithdrawal` then narrows this list down using `findMatchingWithdrawal`, which selects by asset only: [2](#0-1) 

```
function findMatchingWithdrawal(...) {
  return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [3](#0-2) 

The code comment explicitly acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) .

`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` per withdrawal that carries the `index` and full `withdrawalParams`, but `describeWithdrawal` never uses `args.index`, `args.withdrawalParams.destinationAddress`, or `args.withdrawalParams.amount` to disambiguate — only `assetId` [5](#0-4) . `sdk.createWithdrawalCompletionPromises` (and `waitForWithdrawalCompletion`) invoke `describeWithdrawal` independently, per index, for each withdrawal in a batch that shares the same `intentTx` [6](#0-5) . If two withdrawals in the batch share the same `assetId` (e.g. two USDC withdrawals to different addresses initiated in one NEAR transaction — a normal, unprivileged batching pattern already supported by the SDK's array-based `withdrawalParams` API), `.find()` returns the *same* array element (whichever appears first) for both requests. As a result, the second withdrawal's caller receives the first withdrawal's `status`/`txHash` (or vice versa) — an equality break between "the withdrawal status reported" and "the actual on-chain outcome of *that specific* withdrawal."

### Impact Explanation
This breaks the "status reported must equal the on-chain outcome" invariant listed as a valid analog class. Concretely: if a batch contains two same-token withdrawals to different destination addresses, an integrator polling `describeWithdrawal`/`waitForWithdrawalCompletion` for withdrawal #2 can be told it `completed` with withdrawal #1's `txHash` while #2 is still pending or has a different outcome. This can cause an integrator to credit/mark-complete a withdrawal that hasn't actually settled to the correct destination, or to double-credit based on one real completion mistakenly attributed to two logical withdrawals — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category in the rules.

### Likelihood Explanation
This requires no malicious or privileged actor — it triggers under normal use whenever a caller batches ≥2 withdrawals of the same asset in a single `withdrawalParams` array/intent tx via the SDK's own supported multi-withdrawal APIs (`sdk.estimateWithdrawalFee`, `sdk.createWithdrawalCompletionPromises`, `sdk.waitForWithdrawalCompletion`) [7](#0-6) . Because the bug is acknowledged in a code comment as a known limitation rather than a defensive check, there is no guard preventing this scenario from occurring in production integrations that batch same-token withdrawals.

### Recommendation
Disambiguate matched withdrawals using more than `assetId`: match additionally by `destinationAddress`/`amount`, or — per the code's own suggested fix — sort both the API response list and the local `withdrawalParams` list deterministically (e.g., by amount, since relayer fees are identical for same-token withdrawals) and pair them positionally instead of using `Array.find` on asset alone. Until fixed, the SDK should either reject/serialize batches containing duplicate `assetId` withdrawals in a single intent tx, or surface a clear error instead of silently misattributing status.

### Proof of Concept
1. Submit one NEAR intent tx containing two POA-bridge withdrawal intents for the same `assetId` (e.g. `nep141:usdc.omft.near`) with different `destinationAddress` values (SDK already supports arrays of `withdrawalParams` sharing one `intentTx`, see `sdk.ts` lines 557–608).
2. Call `sdk.waitForWithdrawalCompletion({ intentTx, withdrawalParams: [w1, w2] })`.
3. Internally, both calls to `describeWithdrawal` hit `getWithdrawalStatusWithRetry` with the same `tx.hash`, retrieving both withdrawal records.
4. `findMatchingWithdrawal` for each call runs `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`, returning the *same first* matching record for both `w1` and `w2` regardless of which one it is intended for.
5. If `w1` completes first while `w2` is still pending on-chain, the caller polling for `w2`'s status receives `w1`'s `completed` status and `txHash`, incorrectly reporting `w2` as completed.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
