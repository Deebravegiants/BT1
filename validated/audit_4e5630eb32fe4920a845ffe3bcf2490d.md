## Finding: Fee-on-transfer tokens cause unbacked minting in `WrappedHyperFungibleToken.send()`

`WrappedHyperFungibleToken` and its upgradeable variant lock the underlying ERC20 on the home chain via `safeTransferFrom` but never verify the actual amount received before encoding the cross-chain message. If a fee-on-transfer (or deflationary) token is configured as `_underlying`, the locked balance is less than `params.amount`, yet the full `params.amount` is minted on the remote `HyperFungibleToken` — an unbacked mint. This is exactly the same bug class as the Allo `_fundPool`/`increasePoolAmount` report (accounting state diverging from actual token custody), but here it is far more severe because the divergent value directly drives cross-chain minting rather than a local accounting variable.

Notably, `IntentGatewayV2.sol` in this same codebase was explicitly hardened against this class of bug (see `placeOrder`'s balance-snapshot pattern and its dedicated fee-on-transfer test suite), but `WrappedHyperFungibleToken.sol`/`WrappedHyperFungibleTokenUpgradeable.sol` were not.

### Title
Unaccounted fee-on-transfer deduction in `WrappedHyperFungibleToken.send()` causes unbacked cross-chain minting - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`send()` pulls `params.amount` of the underlying ERC20 via `safeTransferFrom` but never checks the wrapper's actual balance delta. The unchecked `params.amount` is then embedded in the cross-chain `Message` and dispatched via ISMP. On the destination chain, `HyperFungibleToken.onAccept()` mints exactly `message.amount`, which can exceed what the wrapper actually locked when the underlying token charges a transfer fee.

### Finding Description
In `send()`: [1](#0-0) 

The ERC20-mode branch calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` without snapshotting `balanceOf(address(this))` before/after. `_buildDispatchPost` then encodes `params.amount` verbatim into the `Message.amount` field: [2](#0-1) 

On the remote chain, `HyperFungibleToken.onAccept()` mints `message.amount` unconditionally: [3](#0-2) 

If `_underlying` charges even a small transfer fee, the wrapper's locked balance is `params.amount - fee`, but `params.amount` tokens are minted on the destination — the wrapped supply becomes larger than the locked collateral. This is the identical root cause described in the report (fee-on-transfer deduction not reflected in the state that downstream logic relies on), except the downstream consumer here is a cross-chain mint rather than a local `poolAmount` variable, making the consequence unbacked supply inflation instead of a mere accounting mismatch.

The same pattern exists in the upgradeable variant: [4](#0-3) 

The symmetric unlock path (`onAccept` transferring `message.amount` back out) has the same problem in reverse — if the wrapper itself becomes the sender of a fee-on-transfer token, `safeTransfer` will deliver less than `message.amount` to the beneficiary, and because escrow bookkeeping is implicit (just the wrapper's raw balance), later unlocks for other users can revert once the wrapper is drained faster than its recorded "escrow": [5](#0-4) 

### Impact Explanation
This produces unbacked minting on the remote `HyperFungibleToken` — every `send()` call with a fee-on-transfer underlying mints strictly more tokens on the destination than are actually custodied on the home chain. Over repeated use this insolvency compounds: eventually a legitimate unlock/withdrawal on the home chain will revert because `_underlying.balanceOf(wrapper)` is insufficient, permanently freezing the funds of whichever user attempts to redeem last. Both "unbacked mint" and "permanent freezing of funds" are explicitly in-scope impacts.

### Likelihood Explanation
Reachable by any unprivileged token bridger calling `send()` — no privileged role is required to trigger the divergence once the pool owner has configured a fee-on-transfer/deflationary ERC20 as `_underlying` (a legitimate, permissionless integration choice, not an admin-malice assumption). The codebase's own `IntentGatewayV2` fee-on-transfer test suite demonstrates that fee-on-transfer tokens are an anticipated integration case for this protocol, increasing the likelihood such a token is eventually paired with `WrappedHyperFungibleToken`.

### Recommendation
In `send()`, snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the measured delta (actual received amount) — not `params.amount` — when building `Message.amount` for the dispatched request, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder()`: [6](#0-5) 

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and `configure()`s it with an ERC20 that charges a 1% transfer fee as `_underlying`.
2. User calls `send({amount: 1000e18, ...})`. `safeTransferFrom` moves 1000e18 tokens from the user, but the wrapper only receives 990e18 (10e18 burned/redirected as fee) since `_underlying.balanceOf(address(this))` only increases by 990e18.
3. `_buildDispatchPost` still encodes `amount: 1000e18` in `Message`, and the ISMP POST is dispatched with this value.
4. On the destination chain, `HyperFungibleToken.onAccept()` mints exactly 1000e18 to the beneficiary.
5. The wrapper now custodies 990e18 of the underlying but 1000e18 of wrapped supply exists on the destination chain — a 10e18 unbacked mint. Repeating this with more `send()` calls further drains the collateral ratio until a subsequent bridge-back unlock reverts due to insufficient wrapper balance.

        bytes memory dest = _supportedChains[params.dest];

        bytes memory body = abi.encode(HyperFungibleToken.Message({

            data: params.data

            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        Message memory message = abi.decode(request.body, (Message));

        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
