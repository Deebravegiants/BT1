### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's `hmac-sha256` header against the raw request body only, then hands the caller the `shop` value taken from a separate, unsigned `x-shopify-shop-domain` header. The equality the gem should guarantee — "the shop attributed to this webhook" == "the shop whose secret actually produced the HMAC" — is not enforced, because `shop` never enters the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then immediately trusts `request.shop`, passing it into `WebhookMetadata` that is handed to the app's handler as the tenant identifier for the payload: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (here, just the body) and compares it against the `hmac` header: [4](#0-3) 

This is the mirror image of the reported staking/unstaking finding: two operations that should be governed by one bound state (there, "allowed to stake" vs. "allowed to unstake"; here, "the body Shopify signed" vs. "the shop this body is attributed to") are actually independent because the binding was never enforced. Any legitimately-signed webhook body from Shopify (e.g. captured or replayed by a party who can observe/replay HTTP traffic reaching the app, or a proxy/load balancer bug that lets headers be altered while the body/HMAC pass through untouched) can be delivered with an attacker-chosen `shop-domain` header and will pass HMAC validation, because the header is never part of what's HMAC'd.

### Impact Explanation
If a host application uses the `shop` field from `WebhookMetadata` (as the documented API return of `Registry.process` intends) to key data by shop/tenant, an attacker who can influence or replay the unauthenticated header (e.g. a misconfigured proxy, a shared endpoint receiving webhooks for multiple shops, or any component sitting between Shopify and the app that does not independently pin headers to the signed body) can cause data destined for Shop A to be recorded, and acted upon, under Shop B's identity. This is a cross-tenant data misattribution issue since the shop binding that determines which merchant a webhook payload belongs to is not covered by the cryptographic signature the gem verifies.

### Likelihood Explanation
Likelihood is limited: the attacker cannot forge the HMAC itself (that still requires the real `api_secret_key` shared only between Shopify and the app), so the attack surface is header manipulation on an already-signed, in-flight webhook request rather than plain forgery. This requires a component that can decouple headers from body (e.g. a reverse proxy bug, shared/multiplexed webhook endpoint across shops, or interception at a layer before the gem's HMAC check but after Shopify's dispatch) — realistic in multi-tenant deployments that use one endpoint for many shops, but not exploitable purely from being an unprivileged internet client without such an intermediary condition. It doesn't cross the "requires TLS interception" exclusion since the requirement is header/body decoupling on the receiving side, not intercepting Shopify's outbound TLS.

### Recommendation
Include `shop` (and ideally `topic`, `api-version`, `webhook-id`) in the signable string so the HMAC binds the shop identity to the payload, or otherwise have `Registry.process` re-derive/verify the shop independently rather than trusting a header that sits outside the verified digest.

### Proof of Concept
1. A multi-tenant app terminates the webhook `POST` at a shared endpoint used for many installed shops.
2. Shopify sends a legitimately signed webhook for `shop-a.myshopify.com` (correct `hmac-sha256` over the raw body).
3. Something in the app's own request pipeline (proxy rewrite, header injection from an untrusted forwarder, request smuggling, etc.) causes the `x-shopify-shop-domain` header seen by `ShopifyAPI::Webhooks::Request` to read `shop-b.myshopify.com` while the body and its HMAC are untouched.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes, because only `@raw_body` is hashed: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the body actually belonging to `shop-a`, causing the app to process/store shop-a's data under shop-b's tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
