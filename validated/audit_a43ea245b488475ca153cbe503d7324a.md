### Title
Unregistered state-machine sources authenticate as the IntentGateway's own address via the `instance()` fallback - (File: evm/src/apps/intentsv2/IntentsBase.sol / evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.authenticate()` validates the source of an incoming ISMP `PostRequest` by comparing the request's `from` address against `instance(request.source)`. When a given `stateMachineId` has never been registered in `_instances`, `instance()` does not reject the lookup — it silently falls back to `address(this)` [1](#0-0) .

### Finding Description
`instance(bytes calldata stateMachineId)` returns `_instances[keccak256(stateMachineId)]`, or `address(this)` if that slot is unset:

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
``` [1](#0-0) 

This mirrors the Discourse bug class: a value normally validated against a whitelist (a "domain" in Discourse, a "registered peer instance" here) has an unvalidated/under-specified encoding path (an *unset* mapping entry, analogous to an unparsed/encoded input) that resolves through a default/fallback branch instead of being rejected outright. The consuming logic (`authenticate`) trusts that fallback the same way the Discourse code trusted the raw/undecoded domain portion of a crafted email.

Because `IntentGatewayV2` and its deployments are commonly deployed at deterministic, identical addresses across multiple EVM-compatible chains (a documented pattern in this repo, e.g. CREATE2/factory deployments), an attacker who can get a request accepted from *any* state machine id that:
1. Hyperbridge/ISMP is willing to relay a proof for (i.e., a supported consensus client exists, or a permissionless/attacker-controlled chain such as a solochain or L2 that can be spun up and whitelisted), and
2. Is not yet present in `_instances` for this particular gateway deployment,

can have `request.from` set to `address(this)` (the gateway's own deployed address on the attacker chain, trivially achievable since the attacker controls deployment on their own chain or forges the `from` field of a message dispatched from a permissionless/attacker-influenced source chain) and have it treated as an authenticated instance of the IntentGateway. This bypasses the intended "only registered peers" allowlist check identically to how the Discourse bug let a crafted address bypass the intended domain allowlist.

### Impact Explanation
`authenticate()` gates every privileged inbound `RequestKind` the gateway processes from ISMP — including `RedeemEscrow`, `RefundEscrow`, `SweepDust`, `UpdateParams`, and `NewDeployment` [2](#0-1) . A forged/unregistered-source message that authenticates as `address(this)` could trigger `RedeemEscrow` for orders it never legitimately filled, `SweepDust` to redirect funds, or `UpdateParams`/`NewDeployment` to corrupt the gateway's peer/registration state — all without the source chain having a state machine ID ever explicitly registered as a trusted peer by governance. This is a concrete path to theft of escrowed intent funds or unauthorized app-state mutation, satisfying the "unauthorized app action" / "forged message delivery" impact bar.

### Likelihood Explanation
Exploitability depends on whether an attacker can get Hyperbridge to accept and relay a proof from a state machine ID that (a) is not yet registered in this gateway's `_instances` mapping and (b) is a source the attacker fully controls (e.g., a permissionless standalone/solochain with a GRANDPA/BEEFY client, or a chain onboarded before the gateway operator registers its `_instances` entry). This is plausible during the rollout window for any new chain — the gap between a chain being added to Hyperbridge's consensus-client whitelist and the IntentGateway operator calling whatever admin function populates `_instances` for that chain is exactly the exposure window, similar to how the Discourse bug required a maliciously crafted but syntactically valid input rather than any privileged access.

### Recommendation
`instance()` should not silently default to `address(this)` for unregistered state machine IDs. Either:
- Revert (or have `authenticate()` revert) when `_instances[keccak256(stateMachineId)] == address(0)`, requiring every peer — including same-chain-address deployments — to be explicitly registered, or
- If the `address(this)` fallback is intended only for the gateway's *own* home chain, restrict it to that one specific `HostStateMachine`/chain ID rather than "any unregistered source."

### Proof of Concept
1. Governance/relayer onboards a new state machine (e.g., a new L2 or solochain) to Hyperbridge's consensus clients, but the `IntentGatewayV2` operator has not yet called the `_instances`-setting admin function for that chain.
2. Attacker deploys (or already controls) a contract at the same address as the target `IntentGatewayV2` on the new chain (trivial via CREATE2/factory redeploy, since the attacker fully controls their own chain's state), and dispatches an ISMP `PostRequest` with `from = address(this)` and a `RequestKind` payload such as `RedeemEscrow`.
3. Once relayed and proven via the (legitimately whitelisted) consensus client, `authenticate()` calls `instance(request.source)`, finds no entry, returns `address(this)`, and the check `instance(request.source) != module` passes.
4. The forged request is processed as if it came from a trusted peer instance, allowing unauthorized escrow redemption or parameter/deployment updates.

Note: I could not fully verify the exact conditions under which a state machine can be "supported by ISMP consensus but unregistered in `_instances`" in production deployment procedure (e.g., whether onboarding runbooks always register `_instances` atomically with consensus-client whitelisting) — this would need confirmation from the deployment/ops runbooks, which were not available in the indexed content.
