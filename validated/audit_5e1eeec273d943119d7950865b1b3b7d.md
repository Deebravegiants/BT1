### Title
Emporium's `runAction` executes value-bearing external calls whose native-ETH movement is not covered by the pre/post balance equation - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes arbitrary low-level calls (`op.endpoint.call{value: op.value}(op.callData)`) with a caller-supplied `EmporiumStack`, and only reconciles the "success" of those calls against the balances of the tokens explicitly listed in `circomData.erc20TokenAddresses` [1](#0-0) . If a caller omits `address(0)` (native ETH) from `erc20TokenAddresses`, any ETH moved by `op.value` during the "Stateless Interaction" branch is never checked against a before/after balance delta, breaking the balance equality the rest of the contract relies on.

### Finding Description
`runAction` computes `balancesBefore`/`balancesAfter` only for `circomData.erc20TokenAddresses` [2](#0-1) . In the "Stateless Interaction" case (`stack.signerAddress == address(0)`), `verifyWallet` returns immediately without any EIP-712 signature check, only marking the `emporiumMessage` nonce used [3](#0-2) . The op's `endpoint`, `value` and `callData` are freely chosen by whoever submits the proof/transaction, since this metadata (`circomData.externalActionData`) is only hashed into `calldataHash`/`getHashedCalldata1` [4](#0-3)  — the circuit commits to it but does not constrain its content beyond that hash. The only selector-level restriction blocks calls to `callHinkalWallet`/`doSendToRelay` [5](#0-4) ; nothing restricts `endpoint` or `value`.

After the loop of calls, the reconciliation only iterates `circomData.erc20TokenAddresses` [6](#0-5) . If the caller simply does not include `address(0)` in that array, any ETH sent out via `op.value` in the stateless branch is invisible to the "`balanceChange = balancesAfter[i] - balancesBefore[i]`" equation — it is neither charged against `deltaAmountChanges` nor caught by the `BalanceChangeShouldBePositive` revert. `getERC20OrETHBalance`/`getBalancesForArray` in `Transferer.sol` treat `address(0)` as the native-ETH balance sentinel [7](#0-6) , so omitting it from the tracked array is sufficient to fully bypass native-value accounting for that call.

This is the same root defect the external report flags (a low-level `.call` whose outcome/side-effects are trusted without being fully reconciled against the actual state it is supposed to move) — here it manifests as "value moved by an external action but not counted in the balance equation," one of the explicitly in-scope analog classes.

### Impact Explanation
Any unprivileged party who can submit a valid Hinkal transaction routed through the Emporium external action (with a legitimate, otherwise-unrelated proof and `erc20TokenAddresses` that excludes `address(0)`) can encode a stateless `EmporiumOperation` with `endpoint = attacker address`, `value = <Emporium's ETH balance>`, `callData = ""`. `runAction` will execute the call, transferring that ETH out of the Emporium contract, and the subsequent balance loop — which never examines ETH because `address(0)` was excluded — will not detect or revert the transfer. Emporium is meant to custody in-flight shielded/relay funds during composed operations, so any ETH sitting there (from prior deposits, relay fees, or partially completed multi-op flows) is subject to outright theft. This is a direct, permissionless theft of protocol/user funds held in-flight, i.e. Critical impact.

### Likelihood Explanation
Exploitation requires only the ability to submit a normal Hinkal transaction with a valid ZK proof for the attacker's own (otherwise legitimate) shielded balance and to route it through the Emporium external action with attacker-chosen `EmporiumStack` bytes — no signer/relay/owner privileges, no self-destructed contract, and no special timing are needed. The stateless path is explicitly designed to be usable without a wallet signature, so the barrier to triggering this is low; the only precondition is that Emporium hold a nonzero ETH balance at call time.

### Recommendation
- **Short term:** In `EmporiumUpgradeable.runAction`, always include `address(0)` in the balance-tracking set used for `balancesBefore`/`balancesAfter` regardless of what is passed in `circomData.erc20TokenAddresses`, or explicitly forbid/zero out `op.value` for calls in the stateless branch unless `address(0)` is present and reconciled.
- **Long term:** Reconcile balances for every asset actually touched by an op (native ETH and any token approved/transferred), independent of caller-supplied lists, and document that low-level `.call` success does not guarantee intended state changes occurred — enforce state reconciliation, not call-success, as the security boundary.

### Proof of Concept
1. Attacker deposits/holds a small shielded balance in Hinkal and prepares a normal withdrawal/transact proof for token `X` (any ERC-20), with `circomData.erc20TokenAddresses = [X]` (deliberately omitting `address(0)`).
2. Attacker sets `circomData.externalActionData.externalActionId` to Emporium's ID and encodes `externalActionMetadata` as an `EmporiumStack` with:
   - `signerAddress = address(0)` (stateless path, no signature required),
   - `ops = [{ endpoint: attackerEOA, invokeWallet: false, value: <Emporium ETH balance>, callData: "" }]`.
3. Attacker submits the transaction to Hinkal; `_externalTransact` calls `EmporiumUpgradeable.runAction` [8](#0-7) .
4. `runAction` executes `op.endpoint.call{value: op.value}("")`, sending Emporium's ETH to `attackerEOA`; `success` is `true` (plain value transfer) [9](#0-8) .
5. The post-call balance loop only iterates `[X]`, so the ETH outflow is never checked, and the call completes and mints/returns the normal UTXO for token `X` as if nothing unusual happened [10](#0-9) .

Note: I was not able to fully verify from the indexed files whether any additional off-chain/relay-side validation exists that would reject an `erc20TokenAddresses` array omitting `address(0)` before a proof is generated, since such validation (if any) would live in off-chain SDK/relayer code not present in `contracts/**`/`circuits/**`. If such a check exists purely off-chain, it would not constitute an on-chain guarantee and the on-chain contract itself remains exploitable by any party who bypasses that off-chain layer.
