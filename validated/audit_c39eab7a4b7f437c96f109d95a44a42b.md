Based on my investigation, I found a legitimate analog in pallet-ismp's consensus client freezing mechanism.

### Title
Permanently frozen consensus client with no on-chain recovery path once a fraud proof is submitted, contradicting the protocol's documented governance-unfreeze design - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`freeze_client` in `modules/ismp/core/src/handlers/consensus.rs` can be triggered by any permissionless "fisherman" submitting a valid `FraudProofMessage`. The freeze is implemented as a one-way flag (`FrozenConsensusClients`) with no corresponding unfreeze path in `pallet-ismp`, unlike the documented design intent, permanently disabling the route for that consensus/state machine.

### Finding Description
The `freeze_client` handler [1](#0-0)  verifies a fraud proof and then calls `host.freeze_consensus_client(msg.consensus_state_id)`. The `IsmpHost` implementation for `pallet-ismp` sets a boolean flag with no reverse operation: [2](#0-1) [3](#0-2) 

Both `update_client` and `validate_state_machine` (used for all request/response processing) reject any activity once this flag is set: [4](#0-3) [5](#0-4) 

Nowhere in `pallet-ismp` is `FrozenConsensusClients` cleared. The protocol documentation itself confirms this is a hard dead-end requiring an entirely new consensus client rather than governance recovery of the frozen one: [6](#0-5) 

This directly contradicts the design intent documented elsewhere in the same repository, which describes governance being able to unfreeze the client after the byzantine condition resolves: [7](#0-6) [8](#0-7) 

This is structurally analogous to the Compound Open Oracle bug: an unprivileged/self-triggerable invalidation action (`invalidateReporter` ↔ `freeze_client`) that shuts down the update path, with no built-in recovery mechanism to resume the *same* logical channel — forcing a full re-initialization (`create_client`, which allocates a fresh `ConsensusClientId`/`ConsensusStateId`, not a "repair" of the frozen one) equivalent to the oracle's "re-deploy the view" fallback.

### Impact Explanation
Once frozen, `pallet-ismp` can no longer process any consensus updates or route requests/responses for that consensus client's state machines — this is a "route unable to deliver messages" condition. Because `create_client` establishes a brand-new consensus/state identifier rather than restoring the frozen one, in-flight commitments, pending requests, and any app-level integrations keyed to the old `consensus_state_id`/`StateMachineId` are permanently orphaned, and every counterparty integration (light clients, relayers, apps referencing the old IDs) must be re-pointed. This can be triggered by a single fraud-proof submission from any unprivileged party, without any admin or governance action, and once triggered there is no path in the pallet to reverse it — only full replacement.

### Likelihood Explanation
`freeze_client` is explicitly designed to be permissionlessly callable by any fisherman submitting a valid conflicting-consensus-proof pair. No stake or special role is required. A genuine equivocation/fork event on the counterparty (which is exactly the scenario this mechanism exists to catch) will trigger it, and the design doc's promised governance recovery is absent from the actual pallet implementation, making the "stuck forever" outcome the routine, not exceptional, result of any detected fault.

### Recommendation
Add a governance-gated `unfreeze_consensus_client` extrinsic in `pallet-ismp` (mirroring the intended design in `consensus-proofs.mdx`) that clears `FrozenConsensusClients` for a given `consensus_state_id` after off-chain confirmation that the byzantine condition has been resolved, without requiring a new `consensus_client_id`/`consensus_state_id` allocation, so in-flight commitments and cross-references to the frozen state machine are preserved.

### Proof of Concept
1. An unprivileged fisherman observes (or, in a hypothetical exploit, self-manufactures via a compromised/complicit validator subset) two conflicting `ConsensusUpdate` proofs for the same consensus state.
2. Fisherman submits `Message::FraudProof(FraudProofMessage{ proof_1, proof_2, consensus_state_id, signer })` through `handle_incoming_message` [9](#0-8) .
3. `freeze_client` verifies the proof and calls `host.freeze_consensus_client(...)`, setting `FrozenConsensusClients::<T>::insert(client, true)` permanently [3](#0-2) .
4. Any subsequent `update_client` call for that `consensus_state_id` fails at `host.is_consensus_client_frozen` [4](#0-3) , and all request/response validation for state machines under that client fails at `validate_state_machine` [5](#0-4) .
5. No extrinsic in `pallet-ismp` clears `FrozenConsensusClients`; recovery requires `create_client` to mint a wholly new consensus/state identity, permanently orphaning everything referencing the old one — confirmed in-repo documentation: "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead" [6](#0-5) .

```rust
/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}
```

```text
The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs. This may arise from double signing or eclipse attacks. The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state. In this state it can no longer process new consensus messages as well as new requests & responses. Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead.
```
