## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable content from the raw request body only, while the `shop` value used to route and process the webhook is read from an HTTP header that is never included in that signature. An attacker who can obtain any one validly-signed `(body, hmac)` pair for the app (e.g., by installing the public app on their own store and capturing its legitimate webhook delivery) can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The request still passes HMAC validation, but the handler is invoked believing the event originated from the victim tenant.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature strictly from `to_signable_string` (the body) and compares it to the supplied `hmac`; it never incorporates `shop`, `topic`, or any other header: [4](#0-3) 

This is the exact bug class described in scope: "bytes verified versus bytes parsed" / "a field acted on but not covered by the HMAC" — the gem verifies the body's integrity but *acts on* (routes tenant-identifying logic by) the unauthenticated `shop` header. The boundary broken is: `shop bound by HMAC == shop acted upon by handler`, which does not hold; the equality that should hold is `HMAC(body) covers shop` but instead `HMAC(body) covers body only, shop is independent`.

### Impact Explanation
Any actor who can install the app on a Shopify store they control (an ordinary, unprivileged action available to any internet user with a Shopify Partner/dev store) receives legitimately-signed webhook deliveries for their own shop. Because the `shop` header is unauthenticated, they can replay that same signed body to the app's public webhook endpoint with the header rewritten to name a different (victim) shop. The app's `WebhookHandler#handle` will process the payload as if it came from the victim tenant — e.g., triggering tenant-scoped side effects such as data updates, cache invalidation, entitlement changes, or state resets keyed by `data.shop`, depending on how the integrating app uses this value. This is a cross-tenant identity-confusion vector, matching the "cross-tenant access" Critical-impact category defined for this analysis.

### Likelihood Explanation
Medium-to-High: the only prerequisite is the ability to receive one legitimately signed webhook for a shop the attacker controls (trivial for a public app) and the ability to send an HTTP request to the app's public webhook callback endpoint with attacker-chosen headers — both are unprivileged, internet-reachable actions requiring no secrets, tokens, or credentials.

### Recommendation
Bind `shop` (and ideally `topic`/`api-version`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body (for example, requiring the shop domain to be embedded in the signed payload/body rather than trusted from a header, or maintaining a server-side mapping from a signed webhook identifier to the expected shop and rejecting mismatches). At minimum, document/require consumers to independently validate that `data.shop` corresponds to a shop with an active, verified installation/session before acting on webhook content.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimately signed webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body `B` and same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — this still matches, since `B` is unchanged.
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-controlled header value `"victim-shop.myshopify.com"` and invokes the app's handler as if the event came from the victim shop. [5](#0-4)
