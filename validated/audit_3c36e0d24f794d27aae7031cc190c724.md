### Title
Unprivileged dust deposit can force a lower LTV snapshot and freeze an indebted account’s exits - ([File: contracts/controller/src/positions/supply.rs](contracts/controller/src/positions/supply.rs))

### Summary
A third-party `supply` call can add dust to an existing collateral position and unconditionally restamp that position to the currently listed LTV, even when the liquidation-threshold portion of the risk update is deliberately gated off. [1](#0-0) [2](#0-1)  This lets an unprivileged address apply a pending LTV reduction to a victim’s account without the victim’s authorization. [3](#0-2)  Once the refreshed LTV makes LTV-weighted collateral lower than debt, later `borrow` and `withdraw` transactions fail the post-operation solvency gate with `InsufficientCollateral`. [4](#0-3) [5](#0-4) 

### Finding Description
`process_supply` permits a caller who is not the account owner or delegate to supply only markets already present in the victim’s `supply_positions`. [3](#0-2)  The deposit path then calls `merge_supply_leg`, which invokes `refresh_supply_risk_params` using `RiskRefreshScope::FullTuple`. [6](#0-5) [7](#0-6) 

`refresh_supply_risk_params` writes the current `effective_config.loan_to_value` before it runs the gated liquidation-parameter update. [8](#0-7)  The gate can return early for an adverse liquidation tuple when the account’s hypothetical health factor is below `1.05`, but that early return occurs after the LTV write. [9](#0-8)  Consequently, a dust top-up can persist a lower LTV even when the liquidation threshold, bonus, and fees remain unchanged. [10](#0-9) 

Risk accounting uses each stored position’s `min(loan_to_value, liquidation_threshold)` to calculate `ltv_collateral`. [11](#0-10)  Both `borrow` and `withdraw` call `enforce_post_pool_solvency`, which first restamps listed supply LTVs and then requires `ltv_collateral >= total_debt`. [12](#0-11) [4](#0-3)  A sharp LTV reduction can therefore leave a still-healthy account unable to withdraw collateral because the reduced LTV component drops below its debt even though the unchanged liquidation threshold keeps `health_factor >= 1`. [13](#0-12) [14](#0-13) 

### Impact Explanation
The attacker can temporarily freeze withdrawals and new borrowing for an indebted victim by paying a minimal amount of an already-held collateral asset into the victim’s account. [3](#0-2)  This is analogous to the reported bug class because an unauthenticated peer uses a small attacker-controlled input to force a threshold transition that terminates an otherwise usable session. [15](#0-14) 

The frozen state persists until the victim repays enough debt, collateral prices rise, governance restores a compatible LTV, or the liquidation threshold itself makes the account liquidatable. [4](#0-3) [16](#0-15)  The impact is Medium: the attacker donates the trigger collateral and does not directly seize the victim’s funds, but the victim can lose access to collateral while remaining solvent under the liquidation threshold. [14](#0-13) 

### Likelihood Explanation
The attack requires a listed collateral asset whose current spoke configuration has a lower LTV than the victim’s stored snapshot. [17](#0-16)  After such a parameter change, any authenticated third party can trigger the update because foreign supply is intentionally allowed for an existing supply leg and requires no victim approval. [3](#0-2) [18](#0-17) 

The attacker does not need to manipulate prices, own a delegate grant, or pass a minimum transfer amount beyond the controller’s positive-payment rules. [19](#0-18) [20](#0-19)  A regression-style harness test already demonstrates that a third-party top-up applies a reduced LTV and causes a subsequent borrow to fail with `InsufficientCollateral`. [21](#0-20) 

### Recommendation
Apply the risk refresh atomically for the whole tuple: compute whether the gated liquidation tuple can be applied, and only then commit the new `loan_to_value` together with the permitted threshold, bonus, and fee update. [8](#0-7) [9](#0-8)  Alternatively, require owner-or-delegate authorization for supply transactions that would restamp an existing account’s risk parameters, while retaining ungated permissionless top-ups only when no stored parameter changes. [3](#0-2) 

A safer implementation should move `position.loan_to_value = effective_config.loan_to_value` behind the same safety decision used for liquidation-affecting changes when the account has debt, or add a dedicated post-refresh solvency precondition that rejects a third-party restamp which would make `ltv_collateral < total_debt`. [22](#0-21) [23](#0-22) 

### Proof of Concept
1. Alice creates a normal account and supplies 10,000 units of collateral asset `C`. [24](#0-23) 
2. Governance changes `C`’s listing from a higher LTV to 5,000 BPS while retaining an account-compatible liquidation threshold of 5,500 BPS. [25](#0-24) 
3. Mallory calls `supply(caller = Mallory, account_id = alice_id, spoke_id = alice_spoke, assets = [(hub_asset(C), 1)])`. [26](#0-25) 
4. The call succeeds because `C` is already an existing supply position, and `merge_supply_leg` writes the new LTV before applying the gated liquidation tuple. [27](#0-26) [15](#0-14) 
5. Alice’s stored LTV becomes 5,000 BPS, and a subsequent `borrow` that was previously viable fails with `CollateralError::InsufficientCollateral`. [28](#0-27) 
6. If Alice already has debt greater than the new `min(LTV, LT)`-weighted collateral, `withdraw` also fails at the same post-pool gate, freezing collateral exits until the account is repaired or liquidated. [5](#0-4) [23](#0-22)

/// Requires debt coverage by LTV-weighted collateral, health factor >= 1, and
/// the configured collateral floor. Debt-free accounts skip all three checks.
pub(crate) fn require_post_pool_risk_gates(env: &Env, cache: &mut Context, account: &Account) {
    if account.debt_free() {
        return;
    }

    let totals = risk::calculate_account_risk_totals(
        env,
        cache,
        &account.supply_positions,
        &account.borrow_positions,
    );

    assert_with_error!(
        env,
        totals.ltv_collateral >= totals.total_debt,
        CollateralError::InsufficientCollateral
    );

    spec_hooks::solvency_gate_checked(account);

    assert_with_error!(
        env,
        totals.health_factor >= Wad::ONE,
        CollateralError::InsufficientCollateral
    );

/// Sums collateral in USD WAD, flooring valuation and risk weighting.
/// Uses each position's stored `min(LTV, liquidation_threshold)`.
pub(crate) fn calculate_ltv_collateral_wad(
    env: &Env,
    cache: &mut Context,
    supply_positions: &Map<HubAssetKey, AccountPositionRaw>,
) -> Wad {
    cache.load_markets(&supply_positions.keys());

    let mut ltv = Wad::ZERO;
    for (hub_asset, position) in iter_typed_positions(supply_positions) {
        let feed = cache.cached_price(&hub_asset.asset);
        let market_index = cache.cached_market_index(&hub_asset);

        let value = position_value_floor(
            env,
            position.scaled_amount,
            market_index.supply_index,
            feed.price,
        );

        let effective_ltv = position.loan_to_value.min(position.liquidation_threshold);
        ltv = ltv.checked_add(env, effective_ltv.apply_to_wad_floor(env, value));
    }
    ltv
}
