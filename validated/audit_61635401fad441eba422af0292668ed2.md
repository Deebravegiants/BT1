### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC signature over the raw HTTP body only. The `shop` (tenant identity) is read from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, which is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated header value as the shop context handed to the app's webhook handler, breaking the intended binding `hmac == HMAC(secret, body)` ⇒ `shop == request.shop`.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [4](#0-3) . For webhooks, `to_signable_string` is defined to return only `@raw_body`, never touching headers [1](#0-0) . Meanwhile `shop` is derived purely from the `shop-domain` header [2](#0-1) , which is attacker-controllable input to the app's HTTP endpoint (headers are not part of the cryptographic proof).

`Registry.process` uses this unauthenticated `shop` value directly to build `WebhookMetadata` passed to the app's handler, after only checking that the *body* HMAC is valid: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [3](#0-2) .

Because every shop that installs the same app shares one `api_secret_key` [5](#0-4) , an unprivileged attacker who legitimately controls one shop (e.g. a free/dev store that installs the app) receives real, validly-signed webhook deliveries from Shopify for their own shop. Since the HMAC only signs the body — and many webhook payloads (e.g. `app/uninstalled`, `shop/redact`, minimal-payload topics) do not embed the originating shop's domain inside the JSON body itself — the attacker can replay the exact same `raw_body` + `hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop that also has the app installed. `HmacValidator.validate` still succeeds (it never inspected the header), and `Registry.process` forwards `shop: <victim-shop>` to the app's handler as if Shopify itself sent that event for the victim shop.

This exactly matches the reported bug class: a field (`shop`) that is acted upon (used as the tenant/session key handed to the handler) but not covered by the integrity check (HMAC), breaking the equality `verified_bytes == acted_upon_identity`.

### Impact Explanation
This enables cross-tenant confusion: an attacker-controlled webhook body can be attributed to an arbitrary victim shop that has the same app installed, as long as the attacker can obtain any validly-signed webhook (from their own store) whose body doesn't uniquely identify the shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the shop's session/access token, to trigger data deletion for `customers/redact`/`shop/redact`, or to update shop-scoped state), this can lead to cross-tenant data corruption or spoofed mandatory-compliance webhook processing against a shop the attacker does not own — a cross-tenant access impact.

### Likelihood Explanation
Medium: the attacker must (a) legitimately install the app on a shop they control (a normal, free/self-serve action for many app types) to obtain a validly-signed webhook, and (b) find a webhook topic whose body doesn't embed the shop domain, and (c) target a host app that trusts `WebhookMetadata#shop` for tenant-scoped actions without independent verification. No secret material or privileged account is required from the attacker.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material for webhook requests, or otherwise cryptographically bind the header-derived `shop` value to the verified body before it is handed to handlers — for example, verify `shop` against a value embedded in the signed payload, or reject/flag requests where the shop cannot be corroborated by data in the signed body.

### Proof of Concept
```ruby
# Attacker installs App on their own shop "attacker.myshopify.com" and receives
# a legitimate webhook delivery from Shopify, e.g. for "app/uninstalled":
raw_body = '{}'  # many topics ship minimal/empty JSON bodies
hmac_b64 = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# This hmac is valid for *any* shop, since it only signs raw_body:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker substitutes victim's domain
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation because to_signable_string only returns raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process forwards the unauthenticated shop header to the handler:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "app/uninstalled",
#                                              shop: "victim-shop.myshopify.com", ...))
```
