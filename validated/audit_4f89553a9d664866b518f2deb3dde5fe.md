### Title
Webhook shop-domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` used to build `WebhookMetadata` from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` verifies covers only the raw request body. Since the app's `api_secret_key` is shared across every shop that installs the app, a merchant who legitimately installs the app on their own store can obtain a validly-signed webhook body/HMAC pair and replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop, breaking the binding between "the entity whose signature was verified" and "the shop attributed to the delivered data."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed content: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and the app's `api_secret_key`, never referencing `shop`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and, once it passes, unconditionally trusts `request.shop` to construct the `WebhookMetadata` handed to the host application's handler — the value app developers use to identify which tenant/shop the event belongs to (e.g., to look up that shop's stored session/access token): [4](#0-3) 

The identity binding that should hold is:
`shop that was cryptographically verified == shop attributed to the delivered webhook data`

Because the HMAC secret (`Context.api_secret_key`) is identical for all shops that install a given app, and the signature never binds `shop`, this equality does not hold. Any shop that installs the app is an "unprivileged internet user" with respect to every other tenant of the same app, yet it can capture a body+HMAC pair from a webhook Shopify legitimately delivered to it (valid under the shared secret) and resend that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (body+HMAC match), and `Registry.process` forwards `WebhookMetadata.shop == <victim shop>` with attacker-controlled `body` content to the app's handler.

### Impact Explanation
This is a cross-tenant confusion vulnerability: a party with no relationship to a victim shop can cause the app to process events that are attributed to that victim shop. Depending on how the host application (following this gem's documented API) uses `WebhookMetadata#shop`/`#body` — e.g., looking up the victim's stored access token/session to act on their behalf, updating tenant-scoped records keyed by `shop`, or triggering side effects — this can result in cross-tenant data corruption or the attacker's payload being processed under another merchant's identity, matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires the attacker to be able to install the app themselves (a normal, unprivileged action for any Shopify merchant/developer for public apps) and to be able to send arbitrary HTTP requests with attacker-chosen headers to the app's public webhook endpoint — both are within reach of an unprivileged internet user. No access token, `client_secret`, or leaked credential is needed; the shared HMAC secret's validity is obtained legitimately through the attacker's own install.

### Recommendation
Bind the verified `shop` to the signature: include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the signable content that `HmacValidator` verifies, or otherwise cross-check the `shop` field against a value derivable from the signed payload (e.g., a `shop_id`/`shop_domain` embedded in and covered by the HMAC-signed body) before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must be independently corroborated (e.g., against the shop already stored for the delivered `webhook_id`) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (legitimate, unprivileged action).
2. Shopify delivers a real webhook to the app's endpoint: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`, and `api_secret_key` is shared across all installs of the app).
3. Attacker captures `B` and `H`, then sends a forged HTTP POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this passes. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: B ...)`, causing the host app to process attacker-controlled data attributed to the victim shop.
