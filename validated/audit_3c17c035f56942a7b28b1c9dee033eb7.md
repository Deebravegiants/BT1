### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC that is computed **only over the raw request body**, then hands the caller-supplied, unauthenticated `shop-domain` header to the app's webhook handler as the trusted tenant identifier. This breaks the identity binding `shop the HMAC was computed for == shop passed to the handler`, mirroring the reported bug class where a privilege/identity check is performed on a value (`client[newClient].required`) that is not actually bound to the entity being validated (`msg.sender`) — here, the *authenticated bytes* (body) and the *identity field consumed by the app* (shop) are decoupled.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `#shop` is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the *body* bytes were signed with the secret) and then immediately forwards `request.shop` — the unauthenticated header — into `WebhookMetadata`, which is the struct handed to the app's `WebhookHandler#handle`: [3](#0-2) 

`WebhookMetadata#shop` is a plain `String` field with no cryptographic linkage back to the signed body: [4](#0-3) 

`HmacValidator.validate` confirms only that `to_signable_string` (the body) matches the HMAC — it never inspects or binds the `shop` header: [5](#0-4) 

So the equality the gem should enforce is:
`shop bound inside the HMAC-signed payload == shop the app uses to select tenant data`

but what it actually enforces is:
`HMAC(raw_body) is valid` AND (separately, unauthenticated) `shop = header["shop-domain"]`

Any request whose body+HMAC pair is valid for *some* shop (e.g. a shop that legitimately installed the app and can trigger/capture its own genuine webhook deliveries) can be replayed with a modified `shop-domain` header. Because that header is outside the signed content, `Registry.process`/`WebhookMetadata` will report an attacker-chosen `shop` value to the app while the HMAC still validates successfully — since only the body is checked, not the header combination.

### Impact Explanation
This is a Critical-tier cross-tenant issue: an app that (as documented/intended) uses `WebhookMetadata#shop` from this gem to look up per-tenant session/access tokens or to key GDPR redact/data operations (`shop/redact`, `customers/redact`, `customers/data_request` — the very topics this gem hardcodes as mandatory) can be made to act on/for the wrong tenant. Because `shop` here is the identity key applications use to select the store's stored access token or perform destructive operations, a mismatch between the authenticated bytes and the trusted identity field crosses a tenant boundary — exactly the class of "shop authenticated versus shop used as a key" binding break called out in the rules.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair — obtainable by any shop that has legitimately installed the app and receives its own real webhook deliveries (no `api_secret_key` or privileged access needed, satisfying the "unprivileged internet user" constraint, since a shop merchant/owner triggering their own app's webhook is not a privileged actor with respect to *other* tenants). They then replay that exact body with the HMAC header unchanged but substitute an arbitrary `shop-domain` header value. The likelihood depends on the host application actually trusting `WebhookMetadata#shop` as an authorization/lookup key without independently re-verifying it against its own webhook subscription records — a pattern the gem's documentation and struct design actively encourage, since `shop` is presented as part of the "verified" metadata alongside `topic`/`body` after `HmacValidator.validate` succeeds.

### Recommendation
- Include `shop` (and ideally `topic`, `webhook_id`) in the HMAC-signed payload verification, or otherwise cryptographically bind the header values consumed downstream to the same authenticated context as the body.
- At minimum, document explicitly that `WebhookMetadata#shop` is derived from an unauthenticated header and must be cross-checked by the host app against its own known/registered shops before use as a lookup key.
- Add a regression test asserting that a request with a mutated `shop-domain` header (but original raw body/HMAC) is rejected or flagged, mirroring the report's recommendation to add a unit test that would have caught the missing binding.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shared_secret",
  host_name: "app.example.com",
  scope: "read_products",
  is_embedded: true,
  api_version: "2024-01",
)

# 1. Attacker's own shop ("attacker.myshopify.com") legitimately installed the app
#    and receives a real Shopify webhook delivery -> captures the raw body + valid HMAC.
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_secret", raw_body)
).strip

# 2. Attacker replays the SAME body/HMAC but swaps the shop-domain header
#    to point at a victim tenant "victim.myshopify.com".
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim.myshopify.com", # forged, unauthenticated
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "wh_1",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HmacValidator.validate only checks raw_body against the HMAC -> passes.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will hand the handler shop: "victim.myshopify.com"
# even though that HMAC was never computed with victim's data in mind,
# and the "shop-domain" header was never authenticated.
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle receives WebhookMetadata(shop: "victim.myshopify.com", ...)
```
This demonstrates that `request.shop` reaching `WebhookMetadata` is fully attacker-controlled independent of HMAC validation success, breaking the intended binding between the authenticated payload and the tenant identity used by the application.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
