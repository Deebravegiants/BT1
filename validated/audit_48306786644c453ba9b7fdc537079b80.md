### Title
Unlimited slippage during `Withdraw` due to optional/bypassable minimum-amount check - (`program/src/processor.rs`)

### Summary
Raydium's AMM `Withdraw` instruction accepts `min_coin_amount` and `min_pc_amount` as `Option<u64>` fields. The slippage-protection check in `process_withdraw` is only executed when **both** values are `Some`; if a caller submits a withdraw with these fields omitted (`None`), the check is skipped entirely and the withdrawal proceeds with zero minimum-output enforcement, mirroring the reported `emergencyExit()` pattern of relying on an implicit "proportional trade" assumption instead of enforcing a real minimum.

### Finding Description
The `WithdrawInstruction` struct defines the minimum-amount fields as optional: [1](#0-0) 

During unpacking, if the instruction payload does not include the extra 16 bytes, both fields default to `None`: [2](#0-1) 

In `process_withdraw`, the actual slippage guard is gated behind an `is_some() && is_some()` check, meaning it is entirely bypassed whenever the caller (or a wallet/SDK that constructs the instruction) omits the minimum amounts: [3](#0-2) 

If this branch is skipped, the computed `coin_amount`/`pc_amount` (derived proportionally from the current pool reserves via `InvariantPool::exchange_pool_to_token`) are transferred to the user with no floor, regardless of what the pool's instantaneous reserves are at execution time: [4](#0-3) [5](#0-4) 

Because Solana transactions can be seen in the mempool/leader queue before confirmation, an attacker can front-run a pending `Withdraw` transaction that has no minimum set with a large `SwapBaseIn`/`SwapBaseOut` that skews the coin/pc ratio in the pool, causing the victim's proportional withdrawal to redeem far less value than expected, then back-run with an opposite swap to restore the price and capture the extracted value — the same "assumption of proportional trades doesn't hold against front-running" root cause identified in the external report.

### Impact Explanation
An LP submitting a `Withdraw` without specifying `min_coin_amount`/`min_pc_amount` (a valid, program-accepted instruction encoding) can have their redeemed `coin_amount`/`pc_amount` reduced to a fraction of fair value via sandwich manipulation of the pool reserves, resulting in direct loss of LP funds during withdrawal. This is a fund-loss vulnerability reachable from a single attacker-controlled transaction pair around a victim's own transaction, with no privileged access needed.

### Likelihood Explanation
Likely, since many integrators/SDKs may omit the optional slippage parameters (as they are optional in the instruction schema, unlike swap instructions where `minimum_amount_out` is mandatory), and MEV/sandwich bots on Solana routinely monitor mempool/priority transactions for exactly this kind of unprotected withdrawal.

### Recommendation
Make `min_coin_amount`/`min_pc_amount` mandatory (non-optional) fields for the `Withdraw` instruction, or reject the instruction with `AmmError::InvalidInput` when both are `None`, so slippage protection cannot be silently bypassed the way `SwapBaseIn`/`SwapBaseOut` already enforce mandatory `minimum_amount_out`/`max_amount_in` checks (see the unconditional checks at [6](#0-5) ).

### Proof of Concept
1. Victim LP submits `Withdraw{amount, min_coin_amount: None, min_pc_amount: None}` (a valid encoding per `instruction.rs` unpack/pack logic).
2. Attacker observes the pending transaction and front-runs it with a large `SwapBaseIn` (or `SwapBaseOut`) skewing `total_pc_without_take_pnl`/`total_coin_without_take_pnl` in the pool.
3. Victim's `Withdraw` executes; because both `min_*_amount` are `None`, the check at `program/src/processor.rs:1780-1786` is skipped, and `coin_amount`/`pc_amount` are computed from the now-skewed reserves and transferred without any floor.
4. Attacker back-runs with the opposite swap to restore the price, pocketing the difference extracted from the victim's withdrawal.
