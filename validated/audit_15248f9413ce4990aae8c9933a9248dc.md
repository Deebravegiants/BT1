### Title
Status/hash misreport for batched same-asset POA withdrawals causes wrong-withdrawal completion confirmation - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
The SDK explicitly supports batch withdrawals — multiple withdrawal legs derived from a single signed intent/NEAR transaction, tracked via `sdk.createWithdrawalCompletionPromises` / `watchWithdrawal`, with the documented guarantee that "array index of returned promise matches array index of input `withdrawalParams`" [1](#0-0) . For the POA bridge route, however, the per-withdrawal status lookup does not honor this index; it matches purely by `assetId`, so when two (or more) withdrawals in the same batch use the same token, both distinct `WithdrawalIdentifier`s resolve to the very same backend record.

### Finding Description
`PoaBridge.describeWithdrawal` resolves the on-chain outcome for a given `WithdrawalIdentifier` by calling `findMatchingWithdrawal`, which searches the bridge's response array for the first entry whose `near_token_id` matches the identifier's `assetId` — it never uses `args.index` (or amount/destination) to disambiguate: [2](#0-1) [3](#0-2) 

The same unindexed matching exists in the internal-utils equivalent used by the older `waitForWithdrawalCompletion` path: [4](#0-3) 

The code comment openly acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but nothing in `watchWithdrawal`, `createWithdrawalCompletionPromises`, or `createWithdrawalIdentifier` rejects or warns about this case — the SDK's public batch-withdrawal API (`WithdrawalParams[]`, per-index promises) permits building exactly this configuration, e.g. withdrawing the same NEP-141 asset to two different destination addresses/amounts within one signed intent. `createWithdrawalIdentifier` builds one identifier per leg carrying an `index`, but that index is discarded by `describeWithdrawal`: [5](#0-4) 

`watchWithdrawal` treats whatever `describeWithdrawal` reports as ground truth and resolves/rejects the caller's promise for that specific withdrawal accordingly: [6](#0-5) 

This breaks the equality "a status/hash reported for identifier N equals the on-chain outcome of withdrawal N": both leg-0 and leg-1 promises will report the *same* status and `transfer_tx_hash`, even though they are for different destination addresses/amounts. If leg 0 actually completed and leg 1 is still pending or failed (or vice versa), the integrator's promise for leg 1 will resolve with leg 0's `completed` status and `txHash`, or a `failed` reason belonging to a different withdrawal entirely.

### Impact Explanation
An integrator using `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` for a batch containing two same-asset legs (a real, SDK-supported pattern per the RFC's "USDC to Solana + BTC refund" example generalized to two same-token legs) can be told withdrawal #1 "completed" with a transaction hash that actually belongs to withdrawal #0. Downstream logic that credits/marks-settled based on this per-index promise (as illustrated in the RFC's own recovery/backpressure examples, `saveSuccess(index, tx)`) would incorrectly mark the second withdrawal as settled using the first withdrawal's proof, i.e., a status/hash misreport that can make an integrator credit or refund twice, or fail to catch that one of the two withdrawals actually failed. This matches the High-severity bucket ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
Requires only that a user's intent/withdrawal batch contains two POA-bridge withdrawals of the same underlying token (no malicious actor needed — any legitimate multi-leg withdrawal request with a repeated asset triggers it), and it always happens deterministically once that condition is met since `.find()` always returns the same first match for both identifiers.

### Recommendation
Disambiguate `findMatchingWithdrawal` using the withdrawal's `index` together with amount/destination (or, at minimum, reject/throw a clear "unsupported: duplicate asset in batch" error at `createWithdrawalIdentifier`/`supports` time instead of silently returning a stale/wrong match), and stop describing indistinguishable same-asset legs as independently confirmed until the POA API can disambiguate them by order or metadata.

### Proof of Concept
1. Build a NEAR intent with two POA-bridge withdrawal legs for the same NEP-141 asset (e.g., 100 USDC to address A, 50 USDC to address B), producing `withdrawalParams[0]` and `withdrawalParams[1]`.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams, intentTx })`, yielding two identifiers with `index: 0` and `index: 1` but the same `assetId`.
3. The POA bridge indexer processes leg 0 first (`COMPLETED`, `transfer_tx_hash: "hashA"`) while leg 1 is still `PENDING`.
4. Both `describeWithdrawal` calls hit `findMatchingWithdrawal(withdrawals, assetId)`, which `.find()`s the same first array entry for both identifiers, so promise[1] also resolves `{ status: "completed", txHash: "hashA" }` even though withdrawal #1 has not actually landed on-chain — evidenced directly by the "Currently only matches by assetId" comment and code at [3](#0-2) .

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
