Found a valid analog: the `Webhooks::Request#shop` value is trusted (bound into `WebhookMetadata`) without being covered by the HMAC signature. `to_signable_string` for a webhook request only signs `@raw_body` (the JSON payload bytes), never the `shop`/`shop-domain` header. `Utils::HmacValidator.validate` therefore only proves that the body bytes were produced with the secret key — it says nothing about which shop the header claims to be from.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing tenant impersonation in `Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only the raw request body [1](#0-0) . `Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it against the `hmac-sha256`/`X-Shopify-Hmac-SHA256` header [2](#0-1) [3](#0-2) . The `shop` accessor, however, is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header [4](#0-3) , which is never part of the bytes that get HMAC-verified.

### Finding Description
`Webhooks::Registry.process` verifies the HMAC and then, without any further check, forwards `request.shop` to the handler as the tenant identity for the webhook event:

```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [5](#0-4) 

The equality that should hold is: *the `shop` bound into `WebhookMetadata` == the `shop` that was cryptographically authenticated by the HMAC*. In this gem, the HMAC only authenticates `@raw_body` bytes — the `shop-domain` header is parsed but never bound into the signed string [6](#0-5) . Since HTTP headers are attacker-controllable independently of the body (an attacker who can reuse/replay a validly-signed body — e.g. a webhook payload captured from their own shop, whose HMAC secret is the same shared `client_secret` for every shop of that app) can attach an arbitrary `shop-domain` header while keeping the same signed body, causing `Utils::HmacValidator.validate` to still return `true` while `request.shop` reports a different (victim) shop.

This breaks the tenant-identity binding the host application relies on: `WebhookMetadata#shop` is what an app developer's `handler.handle` implementation is documented to trust as "this event came from shop X," per the `HmacValidator` contract that "valid HMAC ⇒ trustworthy request." Because `shop` is outside the signed payload, that implication does not hold.

### Impact Explanation
This is a cross-tenant identity confusion at the boundary the gem is supposed to protect: `Utils::HmacValidator.validate` is the only authentication check performed in `Registry.process` before `shop` is treated as trusted, yet `shop` isn't cryptographically bound. A host application built on this gem's documented API (using `WebhookMetadata#shop` from `Registry.process` as the authenticated tenant) can process a request as belonging to shop A when the HMAC only proves body authenticity, not header authenticity — enabling cross-tenant data confusion (e.g., writes/deletes keyed off the wrong shop, or GDPR `customers/redact` / `shop/redact` handlers acting on the wrong tenant). This matches the Critical category of cross-tenant access via a broken identity binding.

### Likelihood Explanation
Exploitation requires the attacker to have at least one validly-signed webhook body (obtainable from their own installed shop, since the shared app secret signs all shops' webhook bodies identically per app) and control over the HTTP headers of the request delivered to the app's webhook endpoint — a realistic scenario for any app exposing a webhook endpoint reachable by something other than Shopify's own delivery infrastructure (e.g., a proxy, test harness, or any code path that constructs `Webhooks::Request` from attacker-influenced headers/body pairs), which is exactly the scenario `Request.new(raw_body:, headers:)` is designed to accept as raw untrusted input.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the verified body (e.g., verify against a per-shop webhook secret, or require the caller to pass the expected shop and compare it against a value derived from a trusted, HMAC-covered source) before allowing `Registry.process` to hand `request.shop` to handlers as authenticated tenant identity.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both webhooks signed with the same app `client_secret`.
2. Attacker captures a legitimately delivered webhook body+HMAC for `shop-a` (e.g., from their own shop).
3. Attacker sends a POST to the app's webhook endpoint with the same raw body and HMAC header, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body` [1](#0-0) .
5. `Registry.process` calls `handler.handle` with `shop: "shop-b.myshopify.com"` [7](#0-6) , even though the signed payload never attested to `shop-b`.

          end
        end

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
