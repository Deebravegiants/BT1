### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken directly from HTTP headers. However, the HMAC signature only ever covers the raw response body, never these header-derived identity fields, so the `shop` value that the handler receives is not cryptographically bound to the signature that "proves" the request came from Shopify.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers with no verification against the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the data passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, which for webhooks is the raw body only: [4](#0-3) 

The identity binding this breaks (as an equality) is:
`shop used by handler (request.shop, from header) == shop that HMAC-signed data actually originated from`
This equality is never checked — the HMAC only proves `raw_body` was signed by the app's secret; it says nothing about which shop's header value accompanied that body.

The library's own documentation reinforces the false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 
This wording implies the entire request (including the shop identity) is verified, when in fact only the body bytes are.

### Impact Explanation
Any unprivileged internet user can install the target app on their own (attacker-controlled) development/test shop, which is a normal, unprivileged onboarding action. Shopify will deliver legitimate webhooks to the app's registered HTTP endpoint for that shop, each with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's `client_secret`, plus an `X-Shopify-Shop-Domain` header equal to the attacker's own shop. Because the HMAC never binds the shop-domain header, the attacker can replay the exact same `(raw_body, hmac)` pair to the same endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop that also has the app installed. `HmacValidator.validate` will still pass (body/HMAC unchanged), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. Depending on how the host application uses `data.shop` (e.g., to select which merchant's session/database row to update), this leads to cross-tenant data confusion/injection — writing or acting on data under an unauthorized shop's tenant context.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that only relies on this gem's `Registry.process`/`HmacValidator` for authenticity, since:
- Getting a valid `(body, hmac)` pair only requires installing the app on any shop (no privileged access needed).
- The webhook endpoint is a public HTTP endpoint by design (no additional secret is required to submit a forged header set with a captured valid body/HMAC).
- The vulnerability is purely a property of this gem's verification logic (`to_signable_string` excluding headers), independent of any host-app misconfiguration, so it is not a "host ignoring documented API" case — the documented API (`Registry.process`) itself doesn't bind shop identity to the signature.

### Recommendation
Include the identity-relevant headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., derive/verify shop identity from a value embedded in the signed body, or require the shop to be confirmed against a previously-established, per-shop webhook secret/session rather than trusting the header value verbatim). At minimum, update `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` so the signable string incorporates the shop domain header, and update `HmacValidator.validate` accordingly so a body/HMAC pair captured for shop A cannot be replayed with shop B's identity headers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal unprivileged install).
2. The app receives a legitimate webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker crafts a new POST request to the same webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a shop known to have the app installed, e.g., discovered via the app’s public listing/customers).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the app's controller and passed to `Registry.process`.
5. `Utils::HmacValidator.validate(request)` at `lib/shopify_api/utils/hmac_validator.rb:12-31` succeeds because it only recomputes HMAC over `B`.
6. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:188-200` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled webhook content under the victim shop's tenant context.

          received_signature = verifiable_query.hmac
