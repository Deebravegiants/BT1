### Title
Webhook `shop-domain` identity spoofing — HMAC covers only the raw body, not the shop identity field trusted by handlers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` succeeds, then hands the request's `shop` field — read straight from an unauthenticated HTTP header — to the app's `WebhookHandler` as trusted tenant identity. The HMAC never covers that field, so it can be detached from the signature that "authenticated" the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that value: [2](#0-1) .

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e., the body) and secure-compares it to the received `hmac`: [3](#0-2) . It performs no check that `shop` is part of, or consistent with, the signed payload.

`Registry.process` uses this HMAC check as the sole gate before trusting the request, then forwards `request.shop` into `WebhookMetadata` unchanged: [4](#0-3) . `WebhookMetadata.shop` is a plain `String` const with no further validation: [5](#0-4) .

**Identity binding broken (as an equality):**
`shop_header_claimed_by_request == shop_that_the_HMAC_actually_authenticates`
Before the attack: both sides are naturally equal because Shopify signs and delivers the webhook for the shop that generated it.
After the attack: an entity that receives *any* legitimate webhook for its own store (a normal, unprivileged merchant that installed the app) possesses a valid `(raw_body, hmac)` pair signed with the app's single shared `client_secret` — the same secret is used for every shop that installs the app. That merchant can replay the exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a *different, victim* shop. `HmacValidator.validate` still returns `true` (it only checks the body), so `Registry.process` treats the forged request as authentic and calls the handler with `WebhookMetadata.shop == <victim shop>` even though the HMAC never attested to that shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged app user (any merchant who has installed the app and can receive at least one real webhook) can make the app process and act on webhook data while flagging it as belonging to any other shop of their choosing, without possessing that other shop's session or access token. Depending on how the host app's `WebhookHandler` implementation uses `data.shop` (e.g., to look up/update the tenant's local record, mark orders paid, trigger data-redaction flows, or select which merchant's Session/API credentials to use for a follow-up API call), this can lead to cross-tenant data corruption or unauthorized actions attributed to a shop the attacker doesn't control. This matches the "cross-tenant access" impact class from an identity field that is verified for integrity but not bound to the value the app treats as authoritative — directly analogous to the reported StartTLS class of bug: a check succeeds on a narrower guarantee than the caller relies on.

### Likelihood Explanation
Likelihood is high for any app that installs a `WebhookHandler` and trusts `WebhookMetadata#shop` (a documented, exposed field) without independently re-validating it against a known/installed shop list. No credentials beyond a normal app installation (available to any unprivileged merchant) are required, and the whole point of `Registry.process` succeeding is to give downstream code an assurance of authenticity that the shop field does not actually carry.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed payload verification path, or explicitly document/enforce that `WebhookHandler` implementers must cross-check `data.shop` against a shop known to have a valid, stored session/installation before trusting it — the current API surface (`Registry.process` raising `InvalidWebhookError` only on body HMAC failure) implies a stronger authenticity guarantee than it delivers for the `shop` field.

### Proof of Concept
1. Merchant A installs the app and normally receives a legitimate webhook, e.g.:
   `POST /webhooks` with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-for-body>` and some `raw_body`.
2. Merchant A captures this `(raw_body, hmac)` pair (trivial — it's their own legitimate traffic).
3. Merchant A resends the identical `raw_body`/`x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` (`Request#to_signable_string`) [1](#0-0) .
5. The handler executes with `WebhookMetadata.new(topic: ..., shop: "shop-victim.myshopify.com", body: ..., ...)` [6](#0-5) , causing the app to act as though the event genuinely originated from `shop-victim`.

          received_signature = verifiable_query.hmac

        end
